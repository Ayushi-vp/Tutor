20. AI evaluation & data  (new track: key evals, ids ev1–ev12, group Learn, pillar llm)
──────────────────────────────────────────────────────────────────────────────────────────────────
Create a NEW "AI evaluation & data" track (prep-console/content/tracks/evals.json, ev1–ev12)
following the shared rules at the top of C:\ra_projects\Tutor\NEW-TRACK-PROMPTS.txt. Sources in
prep-console/content/topics/evals/. Nav label "Evals & data", icon EV, placed after aieng
(--group Learn --after aieng), pillar llm.

The senior question this track answers: "How do you know your LLM feature works, and how do you know
it still works next week?"

  ev1   Why evals are the job: eval-driven development, the eval pyramid (unit checks → model-graded →
        human → online), and what goes wrong without them
  ev2   Building a golden set: sampling real traffic, coverage of slices, size from a confidence
        interval, labelling guidelines, keeping it fresh, and contamination
  ev3   Metrics for generative output: exact match, F1, BLEU/ROUGE and why they fail, embedding
        similarity, task-specific checks, pass@k, and calibrated scores
  ev4   LLM-as-judge: rubric design, pointwise vs pairwise, reference-guided grading, known biases
        (position, verbosity, self-preference) and how to measure and correct them against humans
  ev5   Human evaluation and labelling ops: guidelines, inter-annotator agreement (Cohen's/Fleiss'
        kappa, Krippendorff's alpha), adjudication, annotator quality and cost
  ev6   Evaluating RAG: retrieval metrics (recall@k, MRR, nDCG) vs generation metrics (faithfulness,
        groundedness, answer relevance), component vs end-to-end evals
  ev7   Statistics of evals: confidence intervals, bootstrap, paired comparisons, how many examples you
        need to detect a 2-point difference, variance from sampling temperature, and seeds
  ev8   Online evaluation: A/B tests for LLM features, implicit feedback (thumbs, edits, retries,
        abandonment), interleaving, guardrail metrics, and when offline and online disagree
  ev9   Red-teaming and safety evals: threat models, adversarial sets, jailbreak and injection suites,
        automated red-teaming, and severity scoring
  ev10  Synthetic data: generating eval and training data with LLMs, filtering, dedup, diversity,
        model collapse risk, and when synthetic data lies to you
  ev11  Data curation for fine-tuning: sourcing, cleaning, dedup (exact, MinHash/near-dup), quality
        filters, mixtures, decontamination, licensing and PII
  ev12  Evals in CI and production: regression gates, eval-set versioning, tracing, sampling
        production for review, alerting on quality drift, and the eval dashboard a team actually uses

Overlap to avoid (prereqs — link, go deeper, don't repeat): lm14 (evaluating LLMs), lm15
(hallucination), lm18 (prompt injection), ae3 (monitoring & drift), ae7 (LLMOps, CI evaluation),
ml7 (metrics, ROC/PR), ml16 (offline vs online), math6 (hypothesis testing), math7 (A/B testing
statistics), rs8 (evaluating reasoning). Read them first.

Worked examples with real numbers: a 95% CI on a 78% pass rate from 200 examples; bootstrap on a
paired comparison; kappa from a 2×2 agreement table; judge-vs-human agreement before and after
swapping answer order; recall@5 and nDCG@5 for one query by hand; MinHash similarity for two near-
duplicate documents; the sample size to detect a 2-point win in an online test.

Sources: the original papers (e.g. "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena", the RAGAS
paper, HELM), official docs of eval tools (OpenAI Evals, Inspect from UK AISI, promptfoo, or similar —
verify they still exist), first-party engineering posts on eval practice. Labs: stdlib Python, e.g. a
bootstrap CI calculator, a kappa calculator, a tiny eval harness with a stub "model" function and a
regression gate, a MinHash near-dup detector.

(--group Learn --after evals), pillar llm.

The senior question this track answers: "Design, build, evaluate and run an agent that does real work
without burning money or doing damage."

  ag1   What an agent is (and isn't): workflows vs agents, the autonomy spectrum, when NOT to build an
        agent, and the cost/latency/reliability maths of multi-step loops (0.95^n)
  ag2   The agent loop: ReAct, plan-and-execute, reflection/self-critique, stopping conditions, and
        how tool calls are represented in the message history
  ag3   Designing tools: names, descriptions and JSON schemas the model uses well, granularity,
        error messages as prompts, idempotency, and returning the right amount of data
  ag4   Model Context Protocol (MCP) and tool protocols: hosts, clients, servers, transports, tools vs
        resources vs prompts, auth, and when to write an MCP server
  ag5   Context engineering for agents: what goes in the window each step, summarising/compacting
        history, context rot, retrieval inside the loop, and prompt caching for agents
  ag6   Memory: working memory, scratchpads, long-term memory stores, episodic vs semantic memory,
        what to write, what to forget, and memory poisoning
  ag7   Planning and control flow: task decomposition, graphs/state machines (LangGraph-style),
        routers, parallel tool calls, and human-in-the-loop checkpoints
  ag8   Multi-agent systems: orchestrator–worker, handoffs, debate, sub-agents with isolated context,
        when multi-agent helps and when it just multiplies cost and failure
  ag9   Code-executing and computer-use agents: sandboxes (containers, gVisor, Firecracker microVMs),
        filesystem and network policy, browser/computer-use agents and their failure modes
  ag10  Agent security: indirect prompt injection through tools, the "lethal trifecta" (private data
        + untrusted content + exfiltration), least-privilege tools, confirmation gates, audit logs
  ag11  Reliability and durable execution: retries, timeouts, checkpointing long runs, resumability
        (Temporal-style workflows), idempotent side effects, and budget limits
  ag12  Evaluating agents: task success, trajectory evaluation, tool-call accuracy, benchmarks
        (SWE-bench, τ-bench, WebArena, GAIA — verify current versions), simulated users, and
        variance across runs
  ag13  Cost, latency and model routing: tokens per task, caching, small-model routing, parallelism,
        early exit, and a cost model for an agent at 100k tasks/day
  ag14  Agents in production: tracing and observability (OpenTelemetry GenAI conventions), common
        failure modes (loops, tool hallucination, giving up, over-eagerness), incident review, and a
        launch checklist

Overlap to avoid (prereqs — link, go deeper, don't repeat): lm16 (agents, tools and function
calling), lm18 (prompt injection & guardrails), ae4 (structured output), ae6 (prompt and context
engineering), ae2 (cost modelling), hd7 (agent platform design), rs7 (reasoning models in products),
the evals track ev1–ev12 (especially ev4, ev9, ev12), k8s/os13 for sandboxing. Read them first.

Worked examples with real numbers: success rate of a 10-step chain at 95% per step; a full message
history for a 3-tool-call ReAct episode (show the actual JSON); token growth across 20 steps with and
without compaction; prompt-cache savings on a long agent run (verify current provider cache pricing
on the day); cost per task and per day under two routing policies.

Sources: the ReAct paper, Anthropic's "Building effective agents", the MCP specification
(modelcontextprotocol.io — verify the current spec version and transport names), provider tool-use
docs, OpenTelemetry GenAI semantic conventions, Simon Willison on the lethal trifecta, SWE-bench /
τ-bench papers, Temporal docs, Firecracker/gVisor docs. Agent APIs change fast: date every
provider-specific claim. Labs: stdlib Python with a scripted fake LLM (a function that returns canned
tool calls) so the loop runs offline, e.g. a ReAct loop with two tools and a step budget, a tool-schema
validator, a minimal MCP-style JSON-RPC server over stdio, a trajectory scorer.

The senior question this track answers: the ML system design round at Meta / Google / Amazon /
Netflix / Spotify-style companies — "design the feed / search / recommendations, and improve it".

  rec1  The anatomy of a recommender/search stack: candidate generation → ranking → re-ranking →
        business rules, why it is multi-stage, and the latency budget for each stage
  rec2  Classical information retrieval: inverted index, TF-IDF, BM25, query processing, and why
        lexical search still wins on some queries
  rec3  Collaborative filtering: user–item matrix, neighbourhood methods, matrix factorisation (ALS,
        SGD), implicit feedback and negative sampling
  rec4  Two-tower models and embedding retrieval: training with in-batch negatives, sampling bias
        correction, ANN serving, and refreshing embeddings
  rec5  Hybrid search: lexical + dense, reciprocal rank fusion, query understanding (spelling,
        expansion, intent), and semantic search for RAG vs for users
  rec6  Ranking models: from logistic regression and GBDTs to deep models (Wide & Deep, DCN, DLRM),
        feature crosses, embedding tables, and multi-task ranking (click, like, watch-time)
  rec7  Learning to rank: pointwise, pairwise (RankNet), listwise (LambdaMART), and cross-encoder
        re-rankers
  rec8  Ranking metrics: precision/recall@k, MRR, MAP, nDCG, coverage, diversity, novelty,
        calibration — and why offline gains often vanish online
  rec9  Features and data: user/item/context features, real-time vs batch features, feature stores,
        logging for training (log-and-wait), and training/serving skew in ranking
  rec10 Biases and feedback loops: position bias, selection bias, popularity bias, inverse
        propensity weighting, counterfactual evaluation, and filter bubbles
  rec11 Cold start and exploration: new users/items, content-based fallbacks, multi-armed bandits
        (ε-greedy, UCB, Thompson sampling), contextual bandits
  rec12 Re-ranking and business logic: diversity (MMR), freshness, fairness/exposure, deduplication,
        ads blending, and multi-objective optimisation
  rec13 Online experimentation for ranking: A/B tests, interleaving, novelty effects, long-term
        metrics and holdouts, and network effects
  rec14 LLMs in search and recommendation: LLM re-rankers, generative retrieval, conversational
        recommenders, LLM-generated features/labels, and cost at QPS

Overlap to avoid (prereqs — link, go deeper, don't repeat): lm9 (RAG), lm10 (embeddings & vector
search), db15 (pgvector/HNSW in a DBMS), in11 (typeahead), hd3 (real-time recommendation system design),
hd8 (feature store), ml7 (metrics), ml14 (feature engineering & training/serving gap), ml16 and

Worked examples with real numbers: BM25 score for one query and two documents by hand; one ALS step on

The senior question this track answers: every system design follow-up that starts "and how do users,
services and tenants authenticate and get authorised?"

  au1   Authentication vs authorisation vs accounting, identities (users, services, machines,
        agents), threat model, and where auth lives in an architecture (gateway, service, database)
  au2   Passwords done right: hashing (bcrypt, scrypt, Argon2id), salts and peppers, credential
        stuffing, rate limiting and lockout, breach checks, and password reset flows
  au3   Sessions and cookies: server-side sessions, cookie flags (HttpOnly, Secure, SameSite), CSRF,
        session fixation, logout and revocation
  au4   Tokens and JWTs: structure, signing (HS256 vs RS256 vs EdDSA), validation checklist, the
        classic JWT bugs (alg=none, key confusion), expiry, refresh tokens and rotation, JWT vs
        opaque tokens
  au5   OAuth 2.0: roles, grants (authorization code, client credentials, device code), scopes,
        PKCE, redirect URI validation, and what OAuth 2.1 changes (verify its status on the day)
  au6   OpenID Connect and SSO: ID tokens vs access tokens, discovery and JWKS, SAML at a high level,
        enterprise SSO, and social login pitfalls
  au7   MFA and passwordless: TOTP (RFC 6238), push, SMS weaknesses, WebAuthn/passkeys, phishing
        resistance, and account recovery as the weakest link
  au8   Authorisation models: ACLs, RBAC, ABAC, ReBAC (Google Zanzibar), policy engines (OPA,
        Cedar), and where to enforce (centralised vs in-service)
  au9   Multi-tenancy and isolation: tenant IDs in every query, row-level security, noisy neighbours,
        per-tenant keys, and the classic cross-tenant data-leak bugs (IDOR/BOLA)
  au10  Service-to-service identity: API keys, mTLS, SPIFFE/SPIFFE IDs, workload identity in
        Kubernetes and the cloud, short-lived credentials, and zero trust in practice
  au11  Secrets management: vaults, KMS and envelope encryption, rotation, secrets in CI and
        containers, leaked-key response
  au12  Auth for AI systems: per-user permissions in RAG (document-level ACLs at retrieval time),
        agents acting on behalf of users (delegated OAuth, token exchange RFC 8693), MCP auth, and
        audit trails

Overlap to avoid (prereqs — link, go deeper, don't repeat): swe13 (security for software engineers),
net7 (cookies and CORS), net9 (TLS, PKI, mTLS), net14 (zero trust), sc2 (API gateways), k8s5 (supply

The senior question this track answers: "Which cloud building blocks would you use, how are they
wired and secured, what does it cost, and what happens when a zone or region fails?" Teach the

  cl1   The cloud model: regions, availability zones, edge locations, the shared-responsibility

  cl3   Cloud networking: VPCs, subnets (public/private), route tables, internet and NAT gateways,

  cl9   Infrastructure as code: Terraform (state, plan/apply, modules, drift, locking), CloudFormation

  cl10  Reliability on the cloud: multi-AZ vs multi-region, RTO/RPO, backups and snapshots, health

  cl12  Cost and FinOps: pricing models (on-demand, reserved, savings plans, spot), the hidden costs

  cl13  Cloud security and governance: account/organisation structure, guardrails (SCPs), encryption
        and KMS, secrets, network isolation, compliance basics, and common breach patterns (public
        buckets, leaked keys)
  cl14  ML and LLM workloads on the cloud: GPU instances and capacity, managed ML platforms
