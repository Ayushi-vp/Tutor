A finance team asks for help with supplier invoices. Every day about 2,000 PDFs arrive by email. Someone has to read each one, find the supplier, match it to a purchase order (PO), check that the amounts agree, and either approve it for payment or flag it. An engineer, excited by a demo they saw, builds an "invoice agent": a language model with tools to read PDFs, search the purchase-order database, look up suppliers and approve payments, plus a system prompt that says "process this invoice". In the demo it is magical. It reads an invoice, searches for the order, notices a missing line, looks up the supplier's history and writes a careful note.

Two weeks into production the picture is different. The average invoice takes the agent eleven model calls and forty seconds. The monthly bill is eight times the estimate. About one invoice in twelve ends badly: the agent searched for the wrong order number and gave up, or looped re-reading the PDF, or, twice, approved a payment for an invoice whose amounts did not match because it had misread a total. Nobody can say exactly how often each failure happens, because every run takes a different path. Meanwhile a colleague rewrites the same job as five fixed steps in code: extract fields with one model call into a schema, look up the purchase order by exact number, compare amounts in code, ask the model to explain mismatches, route mismatches to a person. It costs a seventh as much, finishes in six seconds, and its failures fall into three categories you can count.

The agent was not a bad idea because agents are bad. It was a bad idea because this task has a known shape, and the agent was paying, in money, time and reliability, for flexibility the task did not need. Other tasks are different: "figure out why this customer's integration broke" has no fixed shape; the next step depends on what the logs say. There, a fixed workflow cannot cope and an agent earns its cost.

This lesson is about telling those situations apart, and about the arithmetic that makes the difference concrete. It gives a precise definition of an agent, lays out the spectrum of designs between a single model call and a fully autonomous system, walks through the five workflow patterns that solve most problems people first throw an agent at, and works the maths of multi-step loops: why ten steps at 95% each succeed only 60% of the time, how detection and retries change that, how tokens and latency grow with steps, and how to compare designs by cost per successful task. It ends with a decision procedure for when not to build an agent at all. Everything later in this track, from the agent loop (ag2) to production operations (ag14), assumes you can make that call.

Who decides what happens next?

Strip away the frameworks and the hype, and one question separates an agent from everything else built with language models: who decides what happens next? In ordinary software, your code decides. It calls function A, checks the result, then calls B or C. When you add a language model to such a program, the model might classify an email or write a paragraph, but the program still decides the order of operations. Anthropic's widely used definitions draw the line exactly there. A workflow is a system "where LLMs and tools are orchestrated through predefined code paths". An agent is a system where LLMs "dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks".

In an agent, the model looks at the task and what it has learned so far, and picks the next action: search the database, read a file, run a test, ask the user a question, or declare that it is finished. Your code executes that action, reports the result back, and asks the model again. The order of operations, how many there are and when to stop are decided at run time by the model. That ownership of the control flow (the sequence of steps and the choice of which comes next) is the definition. Calling tools is not: a workflow can call tools at fixed points, and an agent is only as capable as the tools it is given.

An analogy: a recipe and a chef

A workflow is a recipe. Someone who knew the dish worked out the steps in advance; the cook follows them, using skill at each step (chopping, judging when the onions are soft) but not deciding the order. Recipes are reliable, quick to follow and easy to check: if the cake fails, you can find which step went wrong. An agent is a chef handed a basket of ingredients and a goal ("make dinner for six, one guest is vegetarian"). The chef tastes, adjusts, discovers the fish is off and changes plan. That flexibility is what you want when the situation cannot be predicted, and it is wasted, even risky, when it can: a chef asked to bake the same cake two thousand times a day will occasionally improvise when you wanted the recipe.

The analogy breaks in one important way. A human chef remembers everything that happened in the kitchen. The model remembers only what is in its context window: the instructions, the tool results and its own previous messages. If your code fails to report that a step failed, the model will carry on as if it succeeded. An agent's "awareness" is exactly as good as the information your loop feeds back to it, which is why so much of this track is about what goes into that loop.

The autonomy spectrum

Workflow and agent are the two ends of a range, not two boxes. Between a single model call and a long-running autonomous system there are several useful stopping points, each handing the model one more kind of decision.

At level 0, one model call does one job: extract the fields from this invoice into a schema. At level 1, code strings several calls together in a fixed order. At level 2, a model makes one choice among paths you wrote ("this is a refund request", so take the refund path). At level 3, the model may choose tools and their arguments for a small, fixed number of steps, for example "look up whatever you need, at most three calls, then answer". At level 4, the model runs an open loop: it keeps acting until it decides it is done, bounded only by budgets. At level 5, runs last minutes to hours, may spawn sub-agents, keep memory across sessions and pause for people.

The three numbers that move along the spectrum

Moving right changes three numbers, and the rest of this lesson is about them. Reliability: every model decision is a chance to be wrong, and chances multiply across steps. Cost: every step is a model call that re-reads an ever longer history. Latency: steps happen one after another, so they add up. What you buy with those costs is coverage: the ability to handle cases nobody wrote a path for. The engineering job is to sit as far left as the task allows, and to move right only where the coverage is worth it, measured, not assumed.

If you stop reading here, keep this: an agent is defined by the model owning the control flow; that ownership is a cost paid for flexibility; and the default answer to "should this be an agent?" is "show me the cases a workflow cannot handle, and the numbers".

1. A working definition, and the parts of an agent

Put precisely, an agent has four parts. A model that reads the current context and produces either an action or a final answer. A set of tools, functions your code exposes with names, descriptions and argument schemas, through which the model acts. A loop, written in ordinary code (the orchestrator or harness), that calls the model, executes requested tools, appends results and repeats. And environment feedback: the results, errors and observations that come back from the world after each action, which are the only way the model learns whether it is making progress. lm16 walked through one round of that loop; ag2 takes it apart step by step.

Two further properties distinguish a real agent from a model that happens to call a tool. The number of steps is not known in advance: it depends on what the tools return. And the model decides when the task is finished, by returning a final answer instead of another tool call. Code still sets the outer limits, called budgets: a maximum number of steps, tokens, dollars or seconds, after which the loop stops regardless of what the model wants. An agent without budgets is not more autonomous; it is unbounded, which is a bug.

A useful test when someone describes a system: ask "could you draw the flowchart of every possible run before seeing the input?" If yes, it is a workflow, however many model calls it makes. If the honest answer is "it depends on what it finds", it is an agent, at least in part.

2. The workflow patterns, one by one

Before building an agent, check whether one of the five workflow patterns from Anthropic's "Building effective agents" (December 2024) fits. They cover a surprising share of real tasks, and each is easier to test because its paths are known.

Prompt chaining splits a task into fixed sequential steps, each a model call that consumes the previous output, with optional code checks ("gates") in between. Example: write an outline, check in code that it has the required sections, write the document from the outline, then translate it. Each call does one easier thing, which tends to raise accuracy at the price of some latency. Use it when a task decomposes cleanly into stages that are always the same.

Routing classifies the input and sends it to a specialised path: refund requests to one prompt with refund tools, technical questions to another with documentation retrieval, easy questions to a small cheap model and hard ones to a large one. The classification is the only model decision about control flow, and you can evaluate it directly as a classifier with a confusion matrix.

Parallelisation runs several calls at once. In sectioning, independent parts of a task run side by side, such as one call answering the user and another screening the request for policy violations, which is faster than doing both in one prompt and keeps each instruction focused. In voting, the same task runs several times and the answers are combined, for instance three independent reviews of code for vulnerabilities, flagging if any finds one. Voting trades cost for reliability when errors are at least partly independent.

Orchestrator-workers lets a central model break the task into subtasks at run time and hand each to a worker call, then combine the results. It looks like an agent, and it is the pattern closest to one, but the structure is usually just two levels (plan, then do), and you can bound the number of workers. Example: a code change where the orchestrator decides which files need edits and a worker edits each.

Evaluator-optimiser has one call produce an output and another critique it against explicit criteria, looping until the critique passes or a limit is reached. Example: literary translation, where a critic can point out nuances the first draft missed. It works when there are clear evaluation criteria and iteration measurably helps.

Agents, in the same article's words, fit "open-ended problems where it's difficult or impossible to predict the required number of steps, and where you can't hardcode a fixed path." The guidance that follows is the most quoted line of the piece in practice: start with the simplest solution, often a single well-prompted call with retrieval, and add complexity only when it measurably improves outcomes.

3. Reliability: why steps multiply

Suppose each step of a run succeeds with probability p, independently of the others, and the run succeeds only if every step does. Then the run succeeds with probability pn for n steps. This is the same arithmetic as a chain of components in series: the chain is weaker than its weakest link because every link must hold.

Work it for a 10-step task at 95% per step: 0.95 × 0.95 = 0.9025 after two steps; 0.8574 after three; 0.7738 after five; and 0.9510 = 0.5987 after ten. A component that is "95% reliable" produces a 10-step task that works three times in five. The table shows how fast this decays.

A handy derived number is the reliability half-life: the step count at which success falls to 50%. Solve pn = 0.5 to get n = ln 0.5 / ln p. If your typical task needs 30 decisions, per-step reliability has to be well above 97% before the agent is right more often than not.

This arithmetic has three consequences that shape everything later in the track. First, removing steps is a reliability technique, not just a speed-up: a tool that does in one call what took three (ag3) changes the exponent. Second, per-step quality matters more the longer the task, which is why long-horizon agents need the strongest models while short routers can use small ones (ag13). Third, the formula is only true for undetected, unrecovered, independent errors, and each of those words is a lever, as the next section shows.

4. Detection, recovery and correlation

Real agents do not fail silently at every error. When a tool call has a misspelt name, the orchestrator returns an error and the model fixes it next step. When code fails a test, the agent sees the failure. Let d be the probability that a failed step is detected (by a tool error, a validation check or a test), and suppose a detected failure is retried once with the same success rate p. The effective per-step success becomes:

p_eff = p + (1 − p) × d × p

Work it for p = 0.95 and d = 0.8: 0.95 + 0.05 × 0.8 × 0.95 = 0.95 + 0.038 = 0.988. Ten steps now succeed with probability 0.98810 ≈ 0.886, up from 0.599. One retry on detected errors took a 60% task to 89%. With perfect detection (d = 1), peff = 1 − (1 − p)2 = 0.9975 and ten steps give 97.5%. The lesson is that detection is worth as much as raw quality: an agent whose errors announce themselves can be much more reliable than its per-step rate suggests, which is why tools should fail loudly with specific error messages (ag3), and why verifiers such as tests are so valuable.

Two forces push the other way. Silent errors are wrong results that look right: a plausible but wrong order number, an amount misread from a PDF, a function that compiles but computes the wrong thing. They get d = 0 and pass straight through. And correlated errors break the independence assumption. If the agent misunderstands the task in step 1 ("follow up with everyone" read as "all customers ever" rather than "people on this ticket"), every later step is wrong in the same direction, and retrying with the same context reproduces the same misunderstanding. Correlation makes the real distribution bimodal: many runs that go fine, and a cluster that go wrong from the start. That is why the most effective recovery changes something, such as a clearer error, a different tool, a re-read of the instructions or a question to the user, rather than just trying again.

5. Consistency: pass@k and pass^k

A per-run success rate hides a second question: does the agent succeed on the same task every time? Two metrics from ev1 make this explicit. pass@k is the chance that at least one of k independent attempts succeeds, 1 − (1 − p)k; it is the right measure when a person or a verifier can pick the good attempt, as with code that must pass tests. pass^k is the chance that all k attempts succeed, pk; it is the right measure when the agent must work every time, as with a support agent serving thousands of customers with the same kind of problem.

At p = 0.8 the two diverge sharply: pass@4 = 1 − 0.24 = 0.998, pass^4 = 0.84 = 0.41. The same agent is "almost always able to do it" and "usually not reliable at it". τ-bench (Yao et al., June 2024), a benchmark of simulated customers talking to tool-using agents in retail and airline domains, introduced pass^k for this reason; it reported that GPT-4o succeeded on under half of the tasks and that pass^8 in the retail domain was below 25%. When you hear an agent's success rate, ask which of these it is, and on how many trials.

6. Cost: what a run actually bills

Each step of an agent is a full model call, and the input to step k is everything so far: system prompt and tool definitions, the task, and every previous model output and tool result. If the starting context is C0 tokens and each step adds Δ tokens (the model's output plus the tool result), step k (counting from 0) reads C0 + kΔ tokens, and a run of n steps reads in total:

total_input = n × C0 + Δ × n(n − 1)/2

The second term grows with the square of the number of steps. ae2 worked this for caching; here is the comparison that decides architecture. Prices are Claude Sonnet 5.5's list prices, checked on 6 October 2026: $2 per million input tokens and $10 per million output tokens.

The agent. C0 = 4,000 tokens (instructions, eight tool definitions, the invoice text), Δ = 1,000 tokens per step, 300 output tokens per step, n = 10 steps. Input = 10 × 4,000 + 1,000 × 45 = 85,000 tokens, which costs 85,000 × $2 / 106 = $0.170. Output = 3,000 tokens, $0.030. Total about $0.20 per run before caching.

The workflow. Three calls (extract, explain mismatch, draft note), each about 3,000 input and 400 output tokens. Input 9,000 tokens is $0.018; output 1,200 tokens is $0.012. Total $0.03 per run.

So the agent is about seven times more expensive per run. Caching the repeated prefix (ag5, ae2) narrows the gap a lot, since most of those 85,000 input tokens are a re-read history, but it does not close it: output, the growing tail and the extra calls remain.

7. Cost per successful task, including failures

Price per run is the wrong unit, because runs that fail still bill tokens and still need someone to finish the job. The fair unit is expected cost per task: token cost plus the cost of whatever happens when the system fails, divided over all tasks. Suppose a failed or declined task goes to a person, at $4 of staff time each (about five minutes, fully loaded).

Take the invoice case and give each design realistic success rates. The agent handles every kind of invoice and succeeds on 80% of them. The workflow handles only the 60% of invoices that match a purchase order cleanly, and on those it succeeds 90% of the time; the other 40% (missing PO numbers, split shipments, credit notes) it routes straight to a person.

The general rule: agents pay for themselves through coverage of the long tail, and only if their success rate on that tail is good. A hybrid, the workflow for the 60% clean cases and the agent only for the rest, typically beats both: 0.6 × ($0.03 + 0.1 × $4) + 0.4 × ($0.20 + 0.2 × $4) = $0.258 + $0.40 = $0.66. (That treats the agent's 80% success on all invoices as its success on the hard 40% too, which is optimistic, so measure it.)

Two more terms belong in a full model. Risk cost: the expected damage of a wrong action, probability times impact. An agent that approves a mismatched invoice once per thousand at an average loss of $2,000 adds $2 per task, more than everything above; that is why high-impact actions get approval gates (ag10) rather than being left to the model. And variance: the 95th-percentile run may take 30 steps and cost ten times the mean, so budgets cap it (ag11, ag13).

8. Latency: steps add up

Each step waits for the model's time to first token (the delay before output begins, which grows with input length), then for the output to be generated at some tokens per second, then for the tool to run. Steps are sequential: step 4 cannot start until step 3's result is known. A rough per-step budget for a mid-size model in late 2026: 0.8 s to first token on a mostly cached prompt, 300 output tokens at 80 tokens per second (3.75 s), and 0.5 s of tool time, about 5 seconds a step. Ten steps take about 50 seconds. The three-call workflow takes about 7-8 seconds, and two of its calls could run in parallel.

That difference decides product shape. Fifty seconds is fine for a background job that emails a result, tolerable for a coding assistant showing progress, and unacceptable for a chat reply where users expect an answer within a few seconds. Agents in interactive products usually stream intermediate progress ("searching orders… found 2… checking amounts") to make waiting bearable, and push slow work to the background.

9. When not to build an agent

Put the pieces together and a decision procedure falls out. Do not build an agent, or keep the agentic part small, when:

  • The path is known. If you can write down the steps for 90% or more of cases, a workflow (with a router for the variants) will be cheaper, faster and more accurate. Use an agent, if at all, for the remainder.
  • Outcomes cannot be verified. Without tests, invariants or a grader, the agent's errors are silent, detection is near zero, and the pn decay applies in full.
  • Actions are irreversible and cannot be gated. If the agent's actions move money, delete data or message customers, and a person cannot approve them, the risk cost may dominate.
  • The latency budget is a few seconds. Multi-step loops cannot meet it.
  • Volume is high and value per task is low. At 100,000 tasks a day, $0.17 of extra tokens per task is $17,000 a day; the task had better be worth it (ag13 builds this cost model fully).
  • You have no eval set. Without one you cannot tell whether the agent beats the simpler design, so you are guessing.

10. Three products, three decisions

Invoice processing. The path is known for most invoices; amounts can be checked in code; payment approval is high impact. Decision: a workflow (extract into a schema, look up the PO by exact number, compare in code, route mismatches), with an optional agentic investigator for the 40% of messy cases that drafts a recommendation for a person rather than approving anything itself.

Customer support with refunds. Conversations vary, so some flexibility pays: the customer may need an order found by description, a policy explained, a replacement arranged. Decision: a workflow skeleton (authenticate in code, load the customer's orders), then a bounded tool loop (level 3, perhaps a 6-step budget) for the conversation, with the refund tool enforcing a policy limit in code and requiring approval above it. The agent proposes; code disposes.

Fixing a failing test in a codebase. The path depends entirely on what the code and the error say, and the test suite is a cheap, automatic verifier. Actions happen in a sandbox (ag9) and are reviewed before merge. Decision: an agent (level 4), with a step and token budget, because this is exactly the open-ended, verifiable, high-value task agents suit. It is no accident that coding agents were the first agents with large commercial adoption: they combine high value per task with cheap verification.

Verification asymmetry is the real enabler

The tasks where agents work well share a property: checking a result is much cheaper than producing it. A test suite verifies a bug fix in seconds; a compiler verifies syntax instantly; a database query verifies that a record now exists. That asymmetry converts silent errors into detected ones, which (section 4) can raise a 10-step task from 60% to nearly 90% without any change to the model. Where verification is as hard as the task itself, such as judging whether a research summary is complete or whether a strategy memo is sound, errors stay silent and agents degrade along the raw pn curve. A senior designer therefore looks for, or builds, the verifier before deciding on autonomy: invariants that can be checked in code, a re-read of state after every write, reconciliation totals, or an independent grader validated against people (ev4). If no verifier can be built, the human stays in the loop as the verifier.

Time horizons and why the frontier keeps moving

METR, a non-profit research group that measures what AI models can do autonomously (Kwa et al., March 2025), proposed measuring agents by the length of task they can complete, expressed in how long a skilled human takes. Their "50% time horizon" is the human task length at which a model succeeds half the time. They reported Claude 3.7 Sonnet at around 50 minutes and found the frontier horizon doubling roughly every seven months from 2019, with signs of acceleration in 2024. The reliability arithmetic explains why such a metric moves smoothly: a longer task means more decisions, so a modest gain in per-step reliability and in error recovery stretches the horizon a lot (from 95% to 99% per step moves the half-life from 13.5 to 69 decisions). Two cautions matter in interviews. The horizon at 80% success is much shorter than at 50%, and production usually needs the former. And the tasks are software tasks with automatic scoring, the most favourable domain for agents; horizons elsewhere are shorter.

Scaffolding has a shelf life; controls do not

Agent systems contain two kinds of structure. Some compensates for current model weaknesses: forcing a written plan before every action, splitting a task across many narrow sub-agents because one context gets confused, re-asking the model to double-check routine outputs. Some encodes the deployment's requirements: budgets, permissions, approvals, audit logs, durable execution, evals. The first kind tends to become unnecessary, and sometimes harmful, as models improve; a fixed planner can stop a stronger model from adapting to what it finds. The second kind never goes away, because it exists for the business, not for the model. Building the first kind thin and removable, and the second kind as solid infrastructure, is a design stance that survives model generations. In practice it means re-running the eval with scaffolding removed whenever a significantly better model ships.

Autonomy is a dial per action, not per system

"How autonomous is your agent?" is usually the wrong question; the better one is "which decisions does it make alone, and which need a person or a rule?" A coding agent may edit files freely in a sandbox, run tests freely, but need approval to push to a shared branch and never be allowed to touch production credentials. A support agent may look up anything about the authenticated customer, issue refunds up to $50, and escalate anything above. Designing autonomy per action, by reversibility and blast radius, lets one system be fully autonomous for 95% of its decisions and tightly supervised for the 5% that matter. The cost model from the body extends naturally: each action class has its own error rate, impact and approval cost, and the dial is set where expected damage plus approval cost is smallest.

Correlated failure makes averages misleading

Because failures correlate within a run (a wrong reading of the task poisons every step after it) and across runs (the same kind of input confuses the model every time), agent outcomes are lumpier than a per-step rate suggests. The aggregate success rate can look healthy while one slice of tasks, say invoices in a particular layout or support requests about one product, fails almost always. That has two consequences. Evaluation must be broken down by slice (ev2) and measured with several trials per task to see consistency (pass^k). And remedies should target the slice: a better tool or a workflow path for that layout fixes more than a generic prompt change.

The economics of the human in the loop

Human review is often treated as a safety cost, but it is also an input to the cost model, and it scales. If an agent completes 80% of tasks and escalates 20%, reviewer capacity sets the system's throughput: at 100,000 tasks a day and five minutes per escalation, that is 1,667 staff hours a day. Improving the agent from 80% to 90% halves that, which may be worth far more than any token saving. Conversely, an approval step on every action is cheap per action but expensive in aggregate and causes approval fatigue, where reviewers click "approve" without reading. Good designs make approvals rare and meaningful, by making safe actions safe by construction (sandboxes, limits) and reserving human attention for genuinely risky ones.

Evaluating the decision, not just the agent

"AI Agents That Matter" (Kapoor et al., 2024) showed that on several agent benchmarks, simple baselines such as retrying or escalating to a stronger model matched elaborate agent designs at a fraction of the cost, and argued that agent results should always be reported on a cost-accuracy plot. The practical lesson for a team: whenever you evaluate an agent, evaluate the simplest credible alternative on the same tasks (a single call with retrieval, a workflow, a "retry three times" baseline) and plot both on cost against success. If the agent is not on the frontier of that plot, it is the wrong design, however impressive its traces look.

How the wrong choice shows up in production

Over-agentic designs show a recognisable signature. The distribution of steps per task is wide, with a long tail, even though the tasks look similar; cost per task varies tenfold between runs; failures are hard to categorise because every run took a different path; and engineers spend their time reading traces of the agent rediscovering the same procedure. When a large share of runs follow the same tool sequence, that sequence is a workflow waiting to be written: mine the traces for frequent paths (a simple count of tool-call sequences is enough) and move the common ones into code.

Under-agentic designs show the opposite signature: the workflow's "other" or "escalate" bucket keeps growing, people add more and more special-case branches, the router's confusion matrix shows many inputs that fit no class well, and the human queue fills with cases that need a few lookups rather than judgement. That is the long tail where a bounded agent can earn its cost.

The metrics that inform the decision

Track, per task type: success rate with confidence intervals and its pass^k over repeated trials; the distribution of steps (median, p95, max); cost per run and cost per successful task; the share of tasks escalated to people and the human minutes they consume; p50 and p95 latency; and the rate of high-impact actions, with how many were approved, rejected or reverted. Plotting success rate against step count is especially telling: if success falls steeply for runs above, say, 12 steps, long runs are mostly flailing, and a lower budget plus earlier escalation will save money without losing successes.

A public case: τ-bench and consistency

The τ-bench paper (Yao, Shinn, Razavi and Narasimhan, June 2024) built two simulated domains, retail and airline, each with a database, domain tools, a written policy the agent must follow and a language-model "user" with a hidden goal. Success was judged by comparing the final database state with the expected one, a verifiable outcome. Its headline finding was not only that GPT-4o, the strongest function-calling agent tested, solved under half of the tasks, but that it was inconsistent: run the same task eight times and the chance of succeeding on all eight was below 25% in retail. That is precisely the gap between pass@k and pass^k, and between a demo and a product. For anyone deciding whether to put an agent in front of customers, the question it teaches is "how often does it get the same case right every time?", which a single-run success rate cannot answer. ag12 returns to τ-bench and its successors when building agent evals.

A well-known pattern: the reasonable-but-wrong interpretation

Many agent incidents involve no attacker and no bug in the usual sense. The agent interprets an ambiguous instruction reasonably but wrongly and the system lets it act at scale: "clean up old branches" deletes branches someone still needed, "reply to everyone waiting" emails hundreds of customers with a stale template. The common root cause is a design that gave an open-ended agent broad write access to a task a workflow, or an agent that proposes a plan for approval, would have handled. The structural fixes recur: narrow default scope, a dry-run mode that lists intended actions, a cap on actions per run, approval when a run would touch more than a handful of records, and an eval case for each such incident. ag14 covers incident review in detail.

Knobs teams actually turn

The levers, roughly in the order they pay off: move frequent paths into code; give tools coarser, task-level operations so fewer steps are needed; add verifiers that turn silent errors into detected ones; set step and cost budgets from the observed distribution of successful runs; route easy tasks to a cheaper model or a workflow; and keep humans on high-impact actions. Each change is re-measured on the eval set before shipping, because almost every one trades something, and the trade is only visible in numbers.

Model three designs with a task mix of 60% "clean" and 40% "messy" tasks: a workflow (3 calls at $0.01 each; succeeds 90% on clean, routes all messy to a human), an agent (simulated with your chain; 10 steps; pick p so it succeeds about 80%), and a hybrid (workflow for clean, agent for messy). Charge $4 for every task a human must handle. Print expected cost per task for each.
  5. Finally, add correlation: with probability 0.1 a run "misreads the task" and every step fails undetected. Re-run step 2 and watch what happens to the gain from retries.

What to look for. The simulated rates should match p**n within about a percentage point, and the 0.95 row should pass 60% at 10 steps. With detection and one retry, the 10-step rate should jump to about 89%. Cost per run should have a 95th percentile well above its mean, because retries add steps and later steps are the most expensive. The design comparison should reproduce the lesson's ordering (hybrid cheapest, then agent, then workflow) and flip when you raise the workflow's coverage from 60% to 90%. With correlated misreads, retries cannot recover those runs: the success ceiling drops to 90% whatever you do per step, which is why recovery must change something rather than repeat it.

Decide: the expense-report agent

A product manager wants an "expense agent" for 40,000 expense reports a month. Each report has receipts (photos or PDFs), a policy to check (meal limits, required approvals, allowed categories), and an outcome: approve, reject with a reason, or send to the employee's manager. Today, three people do this; about 70% of reports are routine (all receipts readable, all within limits), 25% need one clarification or a policy judgement, and 5% are messy (missing receipts, foreign currencies, split costs). A wrong approval costs on average $60 in recovered funds and staff time; a wrong rejection costs about $8 in employee annoyance and rework. Should this be an agent? Design it, and estimate cost per report.

Answer

Shape first. The routine 70% has a writable path: extract each receipt into a schema with one model call, check the policy rules in code (limits, categories, required approvals are rules, not judgement), approve if everything passes. That is a workflow, and the policy check should not be in a model at all: code applies rules deterministically and auditably. The 25% needing judgement (is this a business meal? is this vendor a hotel?) is a routing plus single-call problem: ask the model a narrow question with the policy clause and the receipt, and have it propose an outcome. Only the messy 5% might benefit from a bounded agent that can look up exchange rates, search past reports or draft a clarification email, and even there the agent should propose, not decide.

Where the human sits. Approvals of policy-compliant routine reports can be automatic. Rejections and anything from the judgement or messy buckets go to the manager with the model's recommendation and evidence, because wrong approvals are expensive and wrong rejections annoy people. The agent never approves on its own judgement.

Cost estimate. Workflow for 70%: say 4 extraction calls (one per receipt) at about $0.005 each plus code, $0.02 per report. Judgement 25%: add one call at about $0.01, $0.03 per report, plus a manager glance (1 minute, about $1). Messy 5%: bounded agent, 8 steps, roughly $0.15 in tokens, plus 4 minutes of manager time, about $4. Expected: 0.70 × $0.02 + 0.25 × ($0.03 + $1) + 0.05 × ($0.15 + $4) = $0.014 + $0.2575 + $0.2075 ≈ $0.48 per report, about $19,000 a month, most of it human time on the hard cases. Add risk: if automatic approvals have a 0.5% error rate at $60, that is 0.70 × 0.005 × $60 = $0.21 per report; it is worth an audit sample of auto-approvals to measure and drive that down.

What to tell the product manager. An all-agent design would cost several times more in tokens, be slower, and put judgement where rules belong, while saving almost none of the human time, which sits in the hard cases either way. Build the eval first (300 historical reports with known outcomes), ship the workflow for routine reports, measure, and add the bounded agent for the messy bucket only if it beats "send it to a person" on that bucket's numbers.
