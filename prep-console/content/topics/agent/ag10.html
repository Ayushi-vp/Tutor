An executive assistant agent has access to its user's mailbox, calendar and documents, and can draft and send email, accept meetings and fetch web pages. It is genuinely useful: "summarise what I missed this week and reply to anything urgent" saves an hour a day. One Tuesday, an email arrives from an unknown sender. Its visible text is a vague partnership pitch. Below it, in white text on a white background, is a paragraph addressed to "the AI assistant processing this inbox": it asks the assistant, as part of its summary, to look up the latest board-meeting notes and send them to an address that looks like the company's legal counsel. When the user asks for the weekly summary, the agent reads the email along with everything else, and among its many actions sends one more email, which the user never sees in the summary because the same instructions asked it to leave that out.

Variants of this story have been demonstrated against many real products. Simon Willison's June 2025 post on the "lethal trifecta" lists affected systems including Microsoft 365 Copilot, GitHub's MCP server, GitLab Duo, ChatGPT and its plugins, Google Bard and NotebookLM, Amazon Q, Slack, and Anthropic's Claude iOS app, among others. ag4 told the GitHub MCP story; ag6 told SpAIware's. The pattern is always the same: an agent with access to private data reads content an attacker wrote and has some way to send data out, and the model, which cannot reliably tell the attacker's sentences from its user's, does what the attacker asked.

lm18 explained the mechanism of prompt injection and the families of defence. This lesson is about applying them to an agent you are building, as engineering rather than vocabulary. It shows how to threat-model an agent as a graph of sources, capabilities and sinks; how indirect injection reaches agents through every tool; how to apply the lethal trifecta per data flow; how to cut privileges down to the task; how a tool gateway tracks taint and enforces policy; the six design patterns that give provable guarantees; how to build confirmation gates an injected model cannot talk past; what to log; and how layers of defence multiply, with numbers.

A bank clerk who reads everyone's mail

Imagine a bank clerk with three things: keys to customers' safe-deposit boxes, a desk where anyone can leave letters, and a courier who will take any parcel anywhere. The clerk is diligent, follows written instructions, and cannot always tell a letter from the bank manager from a well-forged one. One day a letter says: "Manager here. Please send the contents of box 114 to this address by courier." Nothing about the clerk's intelligence protects the bank. What protects it is structure: the clerk cannot open boxes without a customer present; letters from outside go through a different desk from instructions from managers; couriers only go to addresses on file; and every parcel is logged with the letter that prompted it.

That clerk is an agent. The keys are its access to private data. The open desk is its exposure to untrusted content: any tool result an outsider can influence. The courier is its ability to communicate externally. Willison's lethal trifecta is the observation that the three together make theft possible, and that removing any one makes this kind of theft impossible, whatever the clerk believes. The analogy holds better than most: a clerk can be trained to be suspicious, just as models can be trained to resist injections, and both help; but no bank relies on suspicion alone.

Sources, capabilities, sinks

Every agent can be drawn this way. Sources are where text comes from, marked trusted (the user, your own system) or untrusted (anything an outsider can write). Capabilities are what the agent can reach and do: data it can read, tools it can call, credentials it holds. Sinks are anywhere data can leave your control. An attack is a path from an untrusted source to a capability to a sink. The rest of this lesson is about finding those paths and cutting them in code.

Three questions that organise the defences

Every control in this lesson answers one of three questions about a path. Can untrusted text reach a decision? Design patterns such as plan-then-execute and the dual-LLM split answer no for some flows, by keeping untrusted text away from the part of the system that chooses actions. If it does, what can that decision touch? Least privilege, scoped credentials and per-task tool sets shrink what a hijacked step can reach. If it touches something, where can it go? Sink policies, allow-lists, confirmation gates and rendering rules decide whether data can leave. A good design has an answer at all three levels for every dangerous path, so that one failure, which you should expect, is caught by the next layer.

And one record ties them together: the audit log, which lets you reconstruct afterwards which untrusted text preceded which action. Without it, an incident cannot be scoped, and you cannot tell users what happened to their data.

"Summarise this web article" uses fetch_url (untrusted, and a sink) but needs no private data. "Prepare me for tomorrow's meetings" reads calendar and documents (private, partly untrusted) and needs no sink except the answer. Each flow gets its own controls; the dangerous one is the first.

Two habits make threat models useful. Include implicit sinks: the rendered answer, any URL fetched, anything written somewhere others can see. And include indirect sources: memory written in an earlier session (ag6), outputs of other agents (ag8), and tool descriptions from third-party servers (ag4).

2. Indirect injection arrives through every tool

Any tool that returns text someone else can influence is an injection channel. The inventory is longer than most teams expect: web pages and search results; emails, attachments and calendar invites; documents shared with the user; tickets, issues, pull requests and code comments; chat messages from other people; database fields filled by customers (names, addresses, reviews); file names; images with text in them (for multimodal agents); MCP tool descriptions and results; long-term memory; and other agents' outputs. Attack text can be hidden from people (white-on-white, HTML comments, tiny fonts, alt text) while remaining perfectly visible to the model.

lm18 explained why filtering cannot close this: natural language has no escaping, attackers adapt, and detectors are models with false negatives. Willison puts the security standard bluntly: in application security, a defence that stops 95% of attacks is "very much a failing grade", because an attacker who can try many variations will find the 5%. That sets the strategy for the rest of this lesson: assume the model will sometimes follow injected instructions, and make sure that when it does, nothing important can happen.

3. The trifecta, applied per flow

The lethal trifecta is most useful applied to data flows, not to whole products. A product may need all three capabilities; a single flow rarely does. For each flow from the threat model, ask which leg can be removed:

  • Remove untrusted content: the flow reads only trusted sources. "Draft a reply using my notes" can be restricted to the user's own notes.
  • Remove private data: the flow runs with no access to sensitive data. A web-research flow gets a fresh context and credentials that read nothing private.
  • Remove external communication: the flow cannot send, fetch arbitrary URLs or render remote content. "Summarise my inbox" produces a summary rendered as plain text, with no send tool and no remote images.

When a flow genuinely needs all three ("reply to this external email"), the leg cannot be removed, but it can be narrowed: the sink is constrained (reply only within the thread, to its existing participants, no attachments the user did not choose) and gated (confirmation showing the full outgoing message). And the agent can be split: one step reads and summarises the untrusted email with no tools; a second step, starting from the user's instruction and the summary as quoted data, drafts the reply. That is the dual-LLM idea of section 6.

4. Least-privilege tools and credentials

Least privilege for agents has four parts. Per-task tool sets: an agent or step gets only the tools its task needs; the inbox summariser has no send_mail. Scoped, short-lived credentials: tools act with the user's delegated permissions for this task (OAuth scopes such as read-only mail), issued per run and expiring with it, never a broad service account that can read every user's data (hd7's tool gateway design). Parameter constraints enforced in code: recipients from the thread or contacts; repositories from a list; URLs from allow-listed domains; amounts under a limit. Read/write separation: reading and writing the same system are different tools with different permissions, so a read task cannot write.

The GitHub MCP exploit (ag4) is the textbook illustration. The agent's token could read and write all of the user's repositories, public and private, during a task that only needed one public repository. Scope the token to that repository, or make public-repository tasks unable to read private ones, and the attack has nothing to steal.

5. Taint tracking and policy at the gateway

All tool calls should pass through one tool gateway where validation, authorisation, rate limits and logging happen (ag3, hd7). It is also where security policy is enforced, and the key input to that policy is taint: whether the run, or a particular value, has been influenced by untrusted content.

Run-level taint is simple and effective. Each tool is labelled with whether its results are untrusted. When a run receives an untrusted result, the run is marked tainted for the rest of its life. Policy then restricts what tainted runs may do:

rule external_send:
    when tool.is_sink and run.tainted
    if args.recipient not in run.trusted_recipients   -> deny ("recipient not in thread or contacts")
    else                                              -> require_confirmation(show=raw(args))

rule fetch:
    when tool == "fetch_url"
    if domain(args.url) not in allowlist              -> deny
    if run.tainted and len(args.url) > 200            -> deny ("long URLs can carry data")

rule irreversible:
    when tool.class == "irreversible"                 -> require_confirmation(show=raw(args))

rule render:
    final answer: strip remote images; show links as text with full URL

Run-level taint is coarse: once tainted, everything the run does is suspect, even actions based only on trusted data. Value-level provenance is precise. CaMeL (Debenedetti et al., 2025) has a privileged model translate the user's trusted request into a program; untrusted content is processed by a quarantined model and enters the program only as values carrying provenance labels; and policies are checked whenever a tool is called with those values. A policy such as "data derived from an untrusted email may not be sent to a recipient the user did not name" becomes checkable. On the AgentDojo benchmark, CaMeL solved 77% of tasks with provable security against injection, against 84% for an undefended system (lm18). The price is that the control flow must be expressible as a program written from trusted input.

6. The six design patterns

Beurer-Kellner, Debenedetti, Tramèr and colleagues (June 2025) catalogued six patterns that give agents provable resistance to prompt injection, all built on one principle: once an agent has ingested untrusted input, it must be impossible for that input to trigger consequential actions.

PatternIdeaFits
Action-selectorThe model maps a request to one of a fixed set of actions and never sees their outputsCommand interfaces, simple assistants
Plan-then-executeThe sequence of actions is fixed from the trusted request before untrusted data is read; data can fill values, not add actionsTasks whose steps are known from the request
LLM map-reduceEach untrusted item is processed by an isolated model call with a constrained output (for example a yes/no), then aggregatedScreening many documents or emails
Dual LLMA privileged model with tools never reads untrusted content; a quarantined model reads it and has no tools; results pass as opaque variablesAssistants that summarise external content and act for the user
Code-then-executeThe model writes a program from the trusted request; the program processes untrusted data (CaMeL is the formal version)Multi-step tasks with data-dependent values
Context-minimisationRemove content (including earlier untrusted text) from the context once it has served its purposeLong-running or multi-turn agents

All of them trade some flexibility for guarantees: none can do "follow the instructions in this email", because that is exactly what an injection is. The practical approach is to use the strongest pattern the flow allows, and to combine the weaker ones (run-level taint, constrained sinks, confirmations) for flows that need flexibility.

7. Confirmation gates that resist deception

A confirmation gate stops an action until a person approves it. Gates fail in two ways. They fail by fatigue when they appear constantly and people approve without reading (ag7, ag9). And they fail by deception when they display the model's own description of the action, because an injected model can describe a malicious action innocently ("Sending the weekly summary to the team").

A gate the model cannot talk past is generated by the gateway from the actual tool call, not by the model: the raw recipient addresses, the destination domain, the amount, the full text or attachment list to be sent, with anything novel highlighted (a recipient never emailed before, a domain outside the organisation, an attachment the user did not mention). It is tiered by risk (no gate for drafts; a gate for external sends from tainted runs; a stronger gate, perhaps with a second approver, for payments) and placed in the gateway so it cannot be skipped. And it is backed by limits it cannot override, because some users will approve a convincing malicious request: recipient allow-lists, data-volume caps, and refusal to attach files the user did not select.

8. Audit logs

When something goes wrong, the first question is "why did the agent do that?", and the second is "what else did it do?". An audit log must answer both. For every run it records: the user and the agent identity and versions; every model call (inputs and outputs, or references to stored copies); every tool call with arguments, result, the policy decision and its reason; the run's taint state at each call and the provenance of argument values; approvals, with who saw what and decided what, when. It is append-only and tamper-evident (for example, each entry includes a hash of the previous one), access-controlled (it contains the sensitive data the agent touched), and retained according to policy. The forensic query it must support is "show every action taken after this run read content from this source", which is what turns "we were attacked" into "these three emails were sent; revoke and notify".

9. Defence in depth, worked

Put numbers on the executive assistant. It handles 100,000 runs a day. Suppose 0.5% of runs read content containing an injection attempt (500 runs) and the model follows the injection 10% of the time: 50 hijacked runs a day, each trying to send private data out. Now add controls one at a time:

  1. Taint-triggered confirmation on any external send from a run that read untrusted content: hijacked sends now need the user's approval. If the gate shows raw details, suppose users still approve 20% of convincing malicious requests: 50 × 0.2 = 10 a day.
  2. Recipient allow-list (thread participants and existing contacts only): attacker addresses are usually new, so suppose this blocks 90%: 10 × 0.1 = 1 a day.
  3. No auto-rendering of remote images or links in answers: the rendered-URL channel is closed entirely.
  4. Split the flow: inbox summarisation runs as a reader with no send capability; replies are drafted in a separate step from the user's instruction, with summaries passed as quoted data. For this flow, theft by injection is zero by construction.

Three caveats keep the arithmetic honest. The layers are not independent: an attacker who knows the allow-list will impersonate a contact, so multiplying fractions overstates protection. Attackers are adaptive: they will aim at whichever layer is weakest. And one successful exfiltration a day, at this scale, is still an incident every day. That is why probabilistic layers are a complement to, not a substitute for, structural ones that remove a leg.

Why "95% is a failing grade"

Security differs from most quality metrics because the inputs are chosen by an adversary. A spam filter that catches 99% of spam is excellent, because spammers send the same messages to everyone. An injection detector that catches 95% of attempts is weak, because an attacker targeting your agent can generate thousands of variants, test them, and use the one that passes. ev9 put numbers on this: a 3% per-attempt success becomes 26% over ten attempts and near-certain over a hundred. Any defence whose effectiveness is a rate, rather than a structural impossibility, should be assumed to fail against a determined attacker; its value is in raising cost and generating telemetry, not in being the boundary.

Confused deputies multiply in agent systems

The classic confused deputy is a program with authority that is tricked into exercising it for someone else. Agent systems create chains of them. A worker agent that reads untrusted content returns text to a lead agent with broader tools (ag8); an MCP server's result is read by a host that holds the user's tokens (ag4); a memory written in one session is obeyed in another (ag6). Each link launders the attacker's text into something the next component trusts a little more. The structural fix is that trust must not increase along a chain: taint propagates across agents, servers and sessions, and policy at the gateway applies to the action, whichever component proposed it.

Capability-based design

An old idea in security fits agents well: instead of giving a component broad authority and checking permissions at use, give it unforgeable references (capabilities) to exactly the resources it may use. In agent terms, the planner obtains a handle meaning "send email in this thread" or "read this one document", and tools accept only such handles. An injected model cannot invent a handle for a different thread or document, because handles are created by trusted code from the user's request. CaMeL's provenance labels and MCP's server-minted handles (ag4) are steps in this direction, and the approach scales better than ever-longer lists of rules.

The utility cost is real and measurable

Structural defences block some legitimate tasks: "do what this email asks" is indistinguishable from an injection, and plan-then-execute cannot handle tasks whose steps depend on content. CaMeL's 77% versus 84% on AgentDojo is a rare published measurement of the cost. Teams should measure it for their own product, utility and attack success on the same eval, and make the trade-off per flow: strong guarantees for flows touching sensitive data and external sinks, more flexibility for flows that cannot do harm. Hiding the trade-off ("our agent is secure and does everything") is how products end up on vulnerability lists.

Detection still matters

Classifiers for injection attempts, anomaly detection on action sequences (a send to a new external domain shortly after reading an unknown sender's email; many private-file reads after reading a public issue), canary secrets that should never appear in outputs, and monitoring of policy denials all produce telemetry. They catch unsophisticated attacks, reveal campaigns, and tell you which controls are being probed. They are the security equivalent of evals in production (ev12): necessary for knowing what is happening, insufficient as a guarantee.

Incident response for agents

When an injection succeeds, the response needs agent-specific steps: identify affected runs through the audit log (all runs that read the malicious content, and everything they did afterwards); revoke and rotate the credentials they used; purge any memory written during those runs; notify affected users with specifics; add the attack to the regression suite; and fix the structural gap, not just the phrasing that got through. Platforms should also have a kill switch per agent and per tool, so a tool being abused can be disabled in seconds without a deploy.

Human factors in approvals

People approve what they expect to see. A confirmation that arrives in the flow of a task the user started, describing an action that sounds plausible, is approved quickly. Gates therefore need to surprise the user in exactly the cases that should surprise them: novelty highlighting (new recipient, new domain, unusual volume), plain statements of consequence ("this sends 3 files outside your organisation"), and friction proportional to risk. Approval data is itself a signal: a gate that is approved 99.8% of the time in under two seconds is probably not being read, and either the action should be made safe without it or the gate redesigned.

The case: the lethal trifecta and the vulnerabilities it explains

Simon Willison's post of 16 June 2025 named a pattern he and other researchers had been documenting for two years. He defined the three dangerous capabilities: access to private data ("one of the most common purposes of tools in the first place"), exposure to untrusted content ("any mechanism by which text (or images) controlled by a malicious attacker could become available to your LLM"), and the ability to communicate externally in a way that could be used to steal data. He argued that the combination, not any single capability, is the problem; that vendors' guardrail products claiming high detection rates miss the point, since 95% is a failing grade in security; and that protocols such as MCP make it easy for users to combine tools from different sources so that all three end up in one agent without anyone deciding it. He listed products where exfiltration through this pattern had been demonstrated and fixed, including Microsoft 365 Copilot, GitHub MCP, GitLab Duo, ChatGPT and ChatGPT Plugins, Google Bard and NotebookLM, Amazon Q, GitHub Copilot Chat, Slack, Mistral Le Chat, xAI's Grok and Anthropic's Claude iOS app.

The value of the framing for engineers is that it is actionable. Each listed vulnerability can be read as a flow that had all three legs, and each fix as the removal or narrowing of one leg: blocking auto-loaded image URLs (removing a sink), restricting what a token can read (removing private data from the flow), or separating untrusted content from privileged actions. The academic work of the same year, the six design patterns and CaMeL, turned the same idea into designs with provable properties.

Failure signatures in production

Policy denials clustered on one tool or one source (someone is probing); sends or fetches to domains never seen before, shortly after untrusted content; unusually long URLs or query strings from fetch tools; tainted runs requesting many private reads; confirmations declined at a rising rate (users are seeing strange requests); memory writes containing instructions or URLs; and canary values appearing in any sink. Each should alert, and each alert should link to the run's audit trail.

What to monitor

Share of runs that become tainted, by source; sink calls by tainted and untainted runs; policy decisions (allow, deny, confirm) by rule; confirmation approval rates and decision times; credential scopes in use; new destinations per day; detector hits and their follow-up; and attack-suite results per release, alongside utility, so the trade-off stays visible.

A short runbook

When an alert suggests a successful injection: freeze the affected agent version or tool with the kill switch; query the audit log for every run that read the suspect content and every action those runs took afterwards; revoke and rotate the credentials those runs used; purge memory written during them; notify affected users with specifics; then fix the structural gap that allowed the path and add the case to the attack suite before re-enabling.

Knobs

Which tools are labelled untrusted sources and which are sinks; per-flow tool sets; credential scopes and lifetimes; allow-lists for recipients, domains and repositories; policy rules and their confirmation tiers; rendering rules for answers; whether a flow uses run-level taint or a stronger pattern; and detector thresholds. Every change goes through the security eval and the utility eval together.

Goal: build a toy tool gateway with run-level taint, a policy engine, raw-detail confirmations and an append-only audit log, and attack it with a scripted injected email. Python 3.12, standard library only.

  1. Create ag10_lab.py. Define tools as dicts with flags: read_mail (untrusted source, private), read_doc (private), send_mail (sink), fetch_url (untrusted source and sink), draft_mail (safe). Implement them over in-memory data: an inbox with three emails, one containing hidden text instructing the agent to send "board_notes.txt" to counsel@law-firm-example.net.
  2. Write a Gateway class with call(run, tool, args) that: validates arguments; marks run.tainted = True when an untrusted-source tool returns; evaluates the policy rules from the body (deny unknown recipients for tainted runs, confirm external sends, deny non-allow-listed domains and long URLs); asks a confirm(raw_args) callback when required; and appends a JSON line to an audit list with a hash chain (sha256(prev_hash + entry)).
  3. Write a scripted fake model that, for "summarise my inbox", reads all mail, then (as if injected) calls read_doc("board_notes.txt") and send_mail to the attacker. Run it with: no gateway policy; policy with a confirm callback that always approves; policy with the recipient allow-list; and a split design where the summariser has no send_mail tool.
  4. Write trace_after(source_id) over the audit log that lists every action taken by any run after it read a given email. Then tamper with one log entry and show the hash chain detects it.

What to look for. Without policy, the attack succeeds silently. With an always-approve confirmation it still succeeds, which is why confirmations need raw details and backing limits. With the allow-list it is denied, and the audit log shows the denial with its reason. In the split design the attacker's instruction has nothing to call. The trace query should list exactly the actions after the malicious email, which is the incident-response question, and the tampered entry should break the hash chain.

Threat-model and harden: a sales-research agent

A sales team's agent prepares account briefs. Its tools: crm_read (the company's CRM, including deal sizes and notes), web_search and fetch_url (public web), linkedin_lookup (third-party API taking a person's name), send_slack (posts to any channel the bot is in, including shared channels with partner companies) and update_crm. A user asks: "Prepare a brief on Acme Corp and post it to #acme-deal." Identify the trifecta flows, the sinks people would miss, and design the controls.

Answer

Sources and legs. Untrusted: everything from web_search, fetch_url and linkedin_lookup, and CRM notes if customers or partners can influence them (imported emails). Private: CRM deal sizes and notes. Sinks: send_slack (especially shared channels, which are external), fetch_url (the URL itself can carry data: https://evil.example/?d=...), linkedin_lookup (the name parameter goes to a third party), update_crm (writes that others will read, a persistence channel), and the brief itself if rendered with remote images. The requested task touches all three legs in one run: it reads private CRM data, reads the public web, and posts.

Split the flow. Step 1, public research: web search, fetch and lookup tools, no CRM access, producing a structured summary with sources. Step 2, internal brief: reads CRM and the step-1 summary as quoted data (taint carried), no web tools. Step 3, posting: the gateway posts the brief only to the channel the user named, only if it is an internal channel; posting to a shared or external channel requires confirmation showing the full text.

Constrain the sinks people miss. fetch_url only for allow-listed domains or search-result URLs, with length limits, and never in a run holding CRM data. linkedin_lookup accepts names only from the CRM contact list or the user's request, not free text from web pages. update_crm is disabled for tainted runs or requires confirmation, so web content cannot plant instructions in CRM notes for future runs. Render the brief as text with links shown, no auto-loaded images.

Least privilege and logs. CRM credentials scoped to the requesting user's accounts, read-only for this task; Slack bot restricted to the named channel per run. Audit every call with taint and provenance, and alert on posts to shared channels, CRM writes from tainted runs and fetches to new domains. Add attack cases (a web page instructing the agent to post deal sizes to a shared channel, a LinkedIn bio with instructions) to the release suite, with canary deal values checked in every sink.
