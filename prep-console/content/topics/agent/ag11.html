A data-operations agent is migrating customer records from an old CRM to a new one. It is a good agent task: each record needs judgement (merging duplicates, mapping odd fields, flagging conflicts), and it will take about three hours for 2,000 accounts. At step 140, two hours in, the platform team deploys a routine update and the worker running the agent is replaced. The run is gone. Someone restarts it. The new run starts from account one, re-migrates 600 accounts that were already done, creates duplicates for the 40 whose migration had a non-idempotent "create" call, and re-sends 40 welcome emails to customers who had already received one. It also costs twice as much, and because model outputs vary, it merges some duplicates differently the second time.

Two days later, the model provider has a 20-minute partial outage. Every agent on the platform retries failed calls immediately, three times each, in lock-step; load on the provider triples during the outage; the outage lasts longer; and a run that looped on a failing call while its budget counter lived in memory crashes, restarts with a fresh counter, and loops again, spending $300 overnight.

None of this is specific to language models. It is what happens to any long-running process with side effects in a world where machines restart, networks drop and dependencies fail, and distributed-systems engineering solved most of it long ago: classify failures, retry carefully, time out everything, record progress durably, make side effects idempotent, and cap what a run can consume. What is specific to agents is that the orchestrator's next decision comes from a non-deterministic model, so "just re-run it" is not even the same computation, and that agents increasingly run for hours.

This lesson brings those techniques to agents. It covers the taxonomy of failures and who handles each; retries with backoff, jitter and budgets, worked on Temporal's default schedule; timeouts; journals and replay; Temporal-style durable execution, where workflows orchestrate and activities act; idempotent side effects and sagas; and budgets that survive restarts. It also works out, with a simple model, how much restarting from scratch costs as runs get longer.

A ledger, not a memory

Think of how a careful bookkeeper works. Every transaction is written in the ledger before the money moves, and each entry has a reference number. If the bookkeeper is interrupted mid-afternoon, anyone can pick up the ledger, see exactly what has been done, and continue from the next line. If a payment's confirmation never arrived, they do not simply pay again; they look up the reference number with the bank to see whether it went through. And there is a spending limit written on the first page that nobody may exceed, however the day goes.

A durable agent works the same way. The ledger is the journal: every model response, tool call and result, written before the next action. The reference numbers are idempotency keys. Picking up the ledger after an interruption is replay. Checking with the bank before paying again is check-then-act. And the limit on the first page is a budget stored in the ledger, not in someone's head, so a new bookkeeper inherits it.

The analogy breaks in one instructive place. A bookkeeper who restarts the day's work from the morning's notes will make the same decisions again. An agent restarted from scratch will not: the model may choose different actions on a second pass. That is why durable agents record the model's outputs too, and on replay reuse them rather than asking again.

Record, replay, continue

Where do these ideas apply? Everywhere a run touches something outside itself. A model call can fail; a tool call can fail or hang; the worker running the loop can disappear; a person may take a day to answer. Each boundary needs an answer to the same three questions: if this fails, will we notice (timeouts, heartbeats), can we safely try again (classification, idempotency), and where do we resume from (the journal). A design review of an agent can walk through its boundaries one by one with those questions and find most reliability gaps in an afternoon.

It also helps to see the three time scales involved. Retries operate over seconds to minutes and hide brief blips from the run. Durability operates over minutes to days and hides process failures and long waits from the user. Budgets operate over the whole run and turn the unbounded failures, loops and runaway spending, into bounded, explained stops.

Two rules carry most of the weight. Record before you proceed: nothing happens next until the outcome of this step is durably written. Replay instead of re-executing: after an interruption, rebuild state from the record, using recorded model outputs and tool results, and do real work only from the first step without a recorded result. The only gap is a call that was sent but whose result was not recorded before the crash; idempotency keys close it. Around these rules sit three supporting practices: careful retries for transient failures, timeouts on everything, and budgets that bound the worst case.

2. Retries done right

A retry is safe when the failure is transient and the operation is idempotent (or keyed). Then three questions remain: how long to wait, how many times, and how to avoid making things worse.

Exponential backoff waits longer after each failure. Temporal's default activity retry policy is a clean reference: initial interval 1 second, backoff coefficient 2.0, maximum interval 100 times the initial interval (100 seconds), unlimited attempts, and the wait before each retry is the smaller of initial × coefficientretries and the maximum. The schedule is:

Retry12345678910
Wait (s)1248163264100100100

Ten retries wait 427 seconds in total, and with unlimited attempts the activity keeps trying every 100 seconds until a timeout stops it. That suits infrastructure blips in background work. For a model call in an interactive agent, where a user is waiting, cap the attempts (perhaps 3-5) or set an overall deadline, and surface the failure.

Jitter randomises each wait (for example, a random value between zero and the computed backoff, "full jitter"). Without it, every client that failed at the same instant retries at the same instant, producing synchronised spikes that can keep a recovering service down.

Honour retry-after when the server provides it: it knows better than your formula when capacity will return.

Retry budgets cap retries as a fraction of normal traffic, say 10%, across a client or a fleet. During a provider incident, a fleet sending 1,000 requests per second with three immediate retries per failure and a 30% failure rate would add 900 requests per second of retries (1,000 × 0.3 × 3), nearly doubling the load on a service that is already failing. A 10% budget caps the extra at 100 per second.

Circuit breakers stop calling a dependency that is failing consistently: after the error rate passes a threshold, calls fail fast for a cooling-off period, then a few test calls decide whether to close the breaker. For agents, an open breaker on a model endpoint can trigger fallback to another region, provider or model. Fallback models must be evaluated in advance on the same tasks, because a different model is a different agent (ag12).

3. Timeouts at every level

Every external call needs a timeout, or a single hung connection can stall a run indefinitely. Timeouts nest:

  • Per attempt: for a model call, a time-to-first-token limit and an overall limit matched to the expected output length; Anthropic recommends streaming or the Batch API for requests that might exceed 10 minutes, since idle connections can be dropped. For a tool call, a limit from its latency profile (p99 plus margin).
  • Per operation across retries: the total time allowed including all attempts and backoff.
  • Heartbeats for long tools: a tool that runs for minutes reports progress periodically; if heartbeats stop, the system knows the worker died rather than waiting for the full timeout.
  • Per step and per run: deadlines that bound everything beneath them.

Temporal names these precisely, which makes it a useful vocabulary even if you do not use it. Start-To-Close limits one attempt of an activity; Schedule-To-Close limits the whole activity including retries; Schedule-To-Start limits how long a task may wait for a worker (detecting a starved fleet); and Heartbeat timeout detects silent failure of long activities. The documentation requires at least one of Start-To-Close or Schedule-To-Close and strongly recommends Start-To-Close, because the server relies on it to retry an attempt whose worker vanished. The design rule is arithmetic: per-attempt timeout × attempts + total backoff must fit inside the operation's limit, and operations must fit inside the step and run deadlines, or the outer deadline will cut retries short unpredictably.

4. The journal: record before you proceed

A durable agent appends to a journal before each next action. The entries, in order:

{"run": "r-7f3", "seq": 41, "type": "model_response", "step": 14, "content": [...], "usage": {...}}
{"run": "r-7f3", "seq": 42, "type": "tool_call", "step": 14, "tool": "crm_create",
 "args": {...}, "idempotency_key": "r-7f3:14:0"}
{"run": "r-7f3", "seq": 43, "type": "tool_result", "step": 14, "ok": true, "result": {...}}
{"run": "r-7f3", "seq": 44, "type": "budget", "steps": 14, "usd": 1.83, "input_tokens": 412000}
{"run": "r-7f3", "seq": 45, "type": "approval_request", "step": 15, "action": {...}}

On resume, a new worker loads the journal, rebuilds the message history and state, and walks forward. Steps with recorded results are replayed: their model responses and tool results come from the journal; nothing is called. The first step without a recorded result is where real work resumes. If its tool call was recorded as sent (seq 42) but has no result (no seq 43), the worker retries it with the same idempotency key, or for tools without keys, first checks whether the effect already happened.

Why record model responses rather than call the model again? Because the model is non-deterministic: called again with the same history, it may choose a different action. The run that already happened chose crm_create at step 14; a resumed run that chose crm_update instead would diverge from reality, and every later step would be built on a world that does not exist. The journal, not the model, is the source of truth about what has happened. It also makes runs reproducible for debugging and evaluation (ag12, ag14), and it is where prompt-cache-friendly append-only history (ag5) comes from naturally.

5. Durable execution engines: workflows and activities

Building journals, replay, timers and retries by hand is possible (hd7's platform does it on a database), but durable-execution engines package the pattern. Temporal is the best-known open-source example, and its model maps cleanly onto agents.

Code is split in two. A workflow is orchestration code that must be deterministic: given the same history, it must issue the same commands in the same order. Its progress is recorded as an event history, and after a crash the engine re-runs the workflow code against the history, a process called replay, to rebuild its state. Anything non-deterministic (network calls, clocks, random numbers) is forbidden inline; Temporal's documentation says to put such work in activities, which "execute outside the replay path and are automatically retried", or to use the SDK's replay-safe APIs for time and randomness. If code changes make replay issue different commands from the history, the engine raises a non-determinism error.

An agent loop maps onto this directly:

@workflow
def agent_run(task, budget):
    state = init_state(task, budget)
    while not state.done:
        check_budget(state)                                  # deterministic
        resp = call_activity(call_model, state.request(),    # recorded in history
                             retry=model_retry, timeout=model_timeout)
        state.append(resp)
        for call in resp.tool_calls:
            if needs_approval(call):
                decision = wait_for_signal("approval", call.id, timeout=hours(24))
                if not decision.approved: state.append_denied(call); continue
            result = call_activity(run_tool, call,
                                   key=f"{run_id()}:{state.step}:{call.index}",
                                   retry=tool_retry(call.tool), timeout=tool_timeout(call.tool))
            state.append(result)
        if state.history_too_long(): continue_as_new(state.compacted())

Model calls and tool calls are activities, each with a retry policy and timeouts; their results land in the event history, so replay reuses them and the model is never asked twice. Human approvals arrive as signals; waiting for one holds no worker, just a durable timer. Budgets are workflow state, so they survive restarts. Event histories have limits (51,200 events or 50 MB per execution, with warnings at 10,240 events or 10 MB, per Temporal's documentation), so a very long agent uses Continue-As-New to end the execution and start a fresh one carrying a compacted state, which pairs naturally with ag5's compaction. Large payloads, such as long model responses or tool results, are best stored externally with references in the history.

6. Idempotent side effects, check-then-act and sagas

Across a network, a request whose response was lost may or may not have been executed. Exactly-once execution is therefore impossible to guarantee from the client side; what is achievable is effectively-once: deliver at least once, and make repeats harmless. Three techniques, in order of preference:

  • Idempotency keys (ag3): send a key that identifies the intended operation; the server stores it with the result and returns the stored result for repeats. Derive it from the run and step (r-7f3:14:0) or from a business key, never from the attempt.
  • Check-then-act: for systems without key support, look up whether the effect already happened (does a record with this external reference exist?) before retrying. This has a race window, so pair it with a natural unique constraint where possible.
  • Naturally idempotent operations: prefer "set status to closed" over "toggle status", "upsert by external id" over "create".

Multi-step side effects need a saga: a sequence of steps where each completed step has a compensating action that semantically undoes it. Booking a trip: reserve the flight (compensation: cancel), reserve the hotel (compensation: cancel), charge the card (compensation: refund). If the hotel fails permanently after the flight succeeded, run the flight's compensation. Compensations are themselves side effects, so they too are keyed, retried and journalled. Where an action cannot be compensated (an email cannot be unsent), place it last, or put a reservation or confirmation step before it.

7. Budgets that survive

Budgets bound the worst case. Per run: steps, input and output tokens, money, wall-clock time, and per-tool call counts (ag2). Per user and per tenant: daily or monthly quotas. Fleet-wide: a global spend rate with alerts. Three engineering rules make them real:

  • Durable: budget counters are part of the run's journalled state, updated in the same write as the step they account for. A counter in memory resets on every restart, which is exactly when runaway runs restart most.
  • Checked before spending: the orchestrator checks the remaining budget before each model or tool call, including estimating the call's cost (input tokens are known before sending).
  • Graceful at the limit: on exhaustion, stop cleanly, record which budget ran out, ask the model for a brief handover summary with a small reserved allowance, and escalate or return a partial result. A run that simply dies leaves no trace of how far it got.

8. The cost of restarting from scratch, worked

How much does durability matter? Model interruptions (deploys, crashes, host losses) as random events arriving at an average interval of M hours, and a task that needs T hours of uninterrupted work. If any interruption sends the task back to the start, the expected total time is M(eT/M − 1), a standard result for restarts under exponentially distributed failures. With M = 6 hours:

Task length TP(interrupted at least once)Expected time, restart from scratchMultiplier
1 hour15%1.09 h1.09×
3 hours39%3.89 h1.30×
6 hours63%10.3 h1.72×

The multiplier grows exponentially with task length, and cost (tokens, sandbox time) grows with it. With per-step checkpoints, an interruption costs about one step plus the resume overhead, so the multiplier stays close to 1 at any length. And the table understates the problem, because restarts also repeat non-idempotent side effects and may take different paths, which no multiplier captures. For runs of minutes, checkpointing is good hygiene; for runs of hours, it is the difference between a product and a demo.

Why replay needs recorded model outputs

Classic durable execution assumes deterministic orchestration and non-deterministic activities. Agents make the orchestration itself depend on a non-deterministic component: the next action is chosen by a model. The resolution is to treat each model call as an activity, so its output is recorded, and to make the code that reacts to that output deterministic. Then replay is faithful: the same recorded outputs lead to the same decisions. Two subtleties follow. Changing the prompt-building code between a crash and a resume changes what would have been sent, but replay does not send it again, so the resumed run's earlier context reflects the old code; that is correct, since it reflects what the model actually saw. And sampling parameters, model versions and tool definitions belong in the journal too, so a run can be explained later.

Workflow versioning

Durable runs outlive deploys. If version 8 of the orchestration code makes different decisions at a point where version 7's run is paused, replaying version 7's history under version 8's code produces a non-determinism error or, worse, a silent divergence. Durable engines provide versioning mechanisms (marking code paths with version branches so old histories take old branches), and platforms can run old and new workers side by side until old runs drain. Anthropic's description of rainbow deployments for its research agents is the same idea at the deployment level. The minimum discipline is to store the code version in each run, keep schemas backward compatible, and test resuming the previous release's journals in CI.

Poison pills and quarantine

Some runs fail every time: a document that crashes the parser, a state that triggers a bug, a tool call that times out deterministically. With unlimited retries and automatic resume, such a run can consume workers forever and starve others. Detect repeated failures of the same run or step (by count and by fingerprint of the error), stop retrying, move the run to a quarantine state with its journal intact, and alert. A person can inspect, fix and resume it, or abandon it with an explanation to the user.

Backpressure and fairness

Model providers enforce rate limits per organisation, typically in requests and tokens per minute. A fleet of agents that ignores them gets 429s; one that respects them needs a shared view of capacity. Token-bucket limiters per model endpoint, per tenant quotas so one customer's batch of long runs cannot starve others, and queues that admit new runs only when capacity exists are standard. Durable runs make this easier: a run that cannot get capacity can wait cheaply, parked, rather than spinning.

Hedged requests trade cost for tail latency

For latency-sensitive steps, a client can send a second identical request if the first has not responded within, say, the 95th-percentile latency, and use whichever finishes first. This cuts tail latency substantially at the cost of extra calls (bounded by how often the hedge fires). For model calls it doubles the cost of the hedged fraction and can return different outputs; it should be used only for idempotent, read-only calls, only for a small tail, and with the losing call cancelled. ag13 returns to the latency-cost trade-off.

Mid-stream failures

Streaming responses fail differently: the server can return HTTP 200 and then send an error event partway through, after some output has arrived. Anthropic's documentation notes that such errors do not follow the standard error mechanisms. A durable loop should treat a partial streamed response as a failed attempt (never journal half a tool call as the model's response) and retry the whole call, which is another reason for idempotent tools: a partial stream must never trigger an action.

Test failure, not just success

Reliability machinery is only trustworthy if it has been exercised. Chaos testing for agents means, in staging: killing workers at random points within steps (especially between sending a tool call and recording its result); injecting provider errors and latency; making tools hang; and deploying new versions while runs are in flight. The assertions are concrete: every run completes or stops with a recorded reason, no side effect is duplicated, budgets hold across restarts, and resumed runs make the same decisions the journal says they made.

Durability does not replace correctness

A durable runtime guarantees the run continues; it does not guarantee the run is right. A model that misread the task at step 3 will, after a perfectly faithful replay, continue to act on the misreading. Durability should be paired with verification (ag1, ag2) and with the ability for a person to inspect a run mid-flight, correct its state or plan, and resume, which a journal makes possible and a pure in-memory loop does not.

The case: durable execution in practice (Temporal) and resumable agents (Anthropic)

Temporal's documentation captures the general pattern this lesson applies to agents. Activities carry retry policies whose default (1-second initial interval, doubling, capped at 100 seconds, unlimited attempts) is tuned for infrastructure faults; workflows do not retry by default, because a workflow failure usually means a bug or a business decision rather than a blip. Timeouts are explicit and layered (Schedule-To-Start, Start-To-Close, Schedule-To-Close, Heartbeat), with Start-To-Close strongly recommended because the server relies on it to recover from lost workers. Workflow code must be deterministic so the event history can be replayed, and non-deterministic work belongs in activities. Histories have limits (51,200 events or 50 MB) and very long executions continue as new. Each of these is a direct answer to a failure in the opening story: lost progress, synchronised retries, hung calls, and runs that grow without bound.

Anthropic's account of operating its multi-agent research system shows the same lessons arriving from the agent side. The post notes that in long-running stateful agents, minor system failures can be catastrophic because errors compound, so the team built the ability to resume from where the agent was when an error occurred rather than restarting, combined model-driven adaptation (letting the agent know a tool failed so it can work around it) with deterministic safeguards such as retry logic and regular checkpoints, added full production tracing to diagnose non-deterministic failures, and used rainbow deployments so that updates did not break agents mid-run.

Failure modes and their signatures

Duplicate side effects: two records, two emails, two charges for one intent; missing or per-attempt idempotency keys. Lost runs: runs that vanish on deploys; state in memory, not journalled. Divergent resumes: resumed runs that redo or contradict earlier steps; the model was re-called during replay. Retry amplification: request volume to a provider spikes during its incident; no jitter, no budget, retries stacked across layers (SDK plus your code plus a gateway). Budget leaks: runs exceeding limits after restarts; counters not durable. Stuck runs: runs waiting forever on a tool with no timeout or heartbeat. Poison pills: the same run crashing workers repeatedly.

What to monitor

Retry rates by error class and dependency; circuit-breaker state changes; requests per second including retries versus first attempts; resumes per run and the step at which they occurred; replay duration; duplicate operations prevented by idempotency keys (a healthy non-zero number shows the keys are working); budget exhaustion by type; time spent waiting on approvals and external events; quarantined runs; and event-history size per run against limits.

Knobs

Retry policies per dependency (initial interval, coefficient, cap, attempts, non-retryable errors); retry budget fraction; breaker thresholds and fallback targets; timeouts per attempt, operation, step and run; heartbeat intervals for long tools; journal granularity; Continue-As-New thresholds; budget limits per run, user and tenant; quarantine thresholds. Tune them from incident reviews and chaos testing: kill workers mid-step, inject provider errors and slow tools in staging, and check that runs resume correctly with no duplicate effects.

Design: making an overnight reconciliation agent durable

A finance agent runs every night for about four hours. For each of 1,500 invoices it fetches the bank transaction feed, matches transactions to invoices (with model judgement for fuzzy matches), posts matched payments to the ledger (a non-idempotent API you do not control), and emails a summary to the controller at the end. Recent problems: a deploy at 02:00 restarted three runs from the beginning and posted 180 payments twice; a bank-feed outage made the agent retry every 2 seconds for 40 minutes; and one night a looping run cost $410. Design the fixes.

Answer

Durable orchestration. Run the agent as a durable workflow (Temporal or an equivalent journal on a database). Each invoice is a step: fetch, match (model call as an activity, output recorded), post, record. Journal every model response and tool result before proceeding. On restart, replay from the journal and resume at the first invoice without a recorded post. Drain workers at step boundaries during deploys, and keep the previous code version running until its runs finish.

Effectively-once posting. The ledger API has no idempotency keys, so wrap it: before posting, check whether a payment with this invoice id and bank transaction id already exists (check-then-act); post with that pair stored in the ledger's reference field; and maintain your own table of posted (invoice, transaction) pairs with a unique constraint, written in the same journal step. A resumed run that finds the pair already posted records the existing result instead of posting again. Reconcile the 180 duplicates by querying for pairs posted twice and reversing one of each (a compensating action), with the controller's approval.

Retries and outages. Classify bank-feed errors: 5xx and timeouts retryable with exponential backoff and jitter (for example 5 s doubling to a 10-minute cap), 4xx not. Cap the fetch activity with a schedule-to-close timeout (say 60 minutes); if exceeded, pause the workflow and alert rather than hammer the feed. Add a circuit breaker so all runs stop calling the feed when it is down, and resume on recovery.

Budgets. Durable per-run budgets: steps (1,500 invoices plus margin), model tokens and dollars (from the typical $X per invoice times count, plus 30%), wall time (6 hours), and a per-invoice step cap to catch loops on one invoice. Counters live in the journal. At exhaustion, stop, record which budget, email the controller a partial summary and a list of unprocessed invoices.

Summary email. Send once at the end with an idempotency key of the run date, so a resumed run cannot send it twice. Monitor duplicate-prevention hits, resumes per night, breaker openings and budget stops.
