A team building a coding agent reports a strong number: 62% on a popular public benchmark, up from 48% for their previous version. They deploy it to their engineers. Within a week the feedback is mixed. On the company's own repositories it seems to solve fewer than a third of the tickets it is given. Some of its "fixes" pass the tests because it edited the tests. When an engineer re-runs a failed task, it sometimes succeeds the second time and fails the third. And it costs four times as much per ticket as the old version, a fact nobody had measured.

Each of those surprises is a gap in evaluation. The benchmark measured a different distribution of tasks, with a different harness, on problems that may have leaked into training data. The grader checked whether tests passed, not whether the tests were the ones that should pass. One trial per task could not reveal that the agent was a coin flip on many problems. And success was reported without its cost. None of this means the benchmark was useless; it means a single number on someone else's tasks answers a different question from "will this agent do our work, reliably, safely, at a price we can pay?"

The evals track taught the foundations: tasks, trials and graders (ev1), LLM judges (ev4), statistics (ev7) and running evals in CI and production (ev12). Agents add their own difficulties. They act on environments, so grading needs a world that can be reset and inspected. Many paths can be valid, so judging the process needs care. Conversational agents need someone to talk to, so evaluation needs simulated users. And outcomes vary run to run in clustered ways that make naive statistics overconfident.

This lesson builds an agent evaluation from those pieces: environments and end-state graders, trajectory evaluation and tool-call accuracy worked by hand, simulated users and how they fail, variance with honest intervals, cost-aware reporting, and the current state of the main public benchmarks, dated, because they change quickly.

A driving test, not a quiz

A written driving theory test checks answers. A practical driving test checks what you do: the examiner cares that you arrived, but also that you checked mirrors before changing lane, stopped at the red light, and did not mount the kerb on the way. Arriving after running a red light is a fail. Arriving by a different route from the examiner's favourite is fine. And one good drive does not prove you are a safe driver; that is why instructors want to see you drive many times in different conditions.

Agent evaluation is a practical test. The outcome is whether you arrived: did the refund get issued, the bug get fixed, the meeting get booked, as checked in the actual systems. The trajectory is how you drove: did the agent verify identity before refunding, avoid forbidden actions, confirm before irreversible ones. Efficiency is fuel and time: steps, tokens, money, seconds. And repetition is many drives: several trials per task, because a single run of a stochastic agent tells you little about how it usually behaves.

The analogy breaks in one useful way. A driving examiner sits in the car with you. An agent eval must build the road, the other drivers and the examiner: a sandboxed environment that resets to the same starting state, sometimes a simulated user playing the other party in a conversation, and graders that can see the state of the world at the end.

The shape of an agent eval

Why agents are harder to evaluate than single calls

Evaluating a single model call is mostly a question of grading an output. Agents add three complications. First, the output is an effect: what matters is a changed database, a merged fix, a sent message, so the grader has to look at the world rather than the text. Second, the path varies: two good runs can call different tools in different orders, so process checks must allow legitimate variety while still catching the shortcuts that matter. Third, the result is a distribution: the same task can pass, fail, then pass again, and the long tail of costs and steps matters as much as the average. Each complication has a standard answer (environments and end-state checks, property-based trajectory rules, several trials with task-level statistics), and together they make agent evaluation closer to integration testing plus statistics than to grading an exam.

Everything in the body, and every number a team reports about its agent, hangs on this picture. The environment must be resettable so every trial starts the same. Graders should check the world, not the agent's description of it. Trajectories are checked for properties rather than matched to one path. And numbers are reported with honest uncertainty and with their cost.

1. What to measure

An agent eval should report five kinds of number, each on the same tasks:

  • Outcome: did the task get done, judged by the state of the world afterwards.
  • Process: did the trajectory respect the rules: required checks before actions, no forbidden tools, confirmations before irreversible steps, honest reporting of failures.
  • Efficiency: steps, input and output tokens, money and wall-clock time per task, with distributions, not just means (ag13).
  • Consistency: how often the same task succeeds across trials, pass^k (ag1).
  • Safety: rate and severity of harmful or irreversible mistakes, including on adversarial tasks (ag10, ev9).

Anthropic's January 2026 guide to agent evals uses the vocabulary of ev1 adapted to agents: a task, several trials, graders of three kinds (code, model and human), a transcript (the trajectory) and an outcome (the final state of the environment), with outcome checked separately from what the agent says it did.

2. Environments: a world you can reset and inspect

An agent eval needs an environment: the databases, APIs, files and services the agent acts on, in a known initial state per task, reset before every trial, and inspectable afterwards. Three common forms:

  • Replicas: a copy of the real systems (a database seeded from fixtures, a staging instance of an API) running in containers. Most faithful; most work.
  • Simulators: purpose-built fake services with realistic state and behaviour, as τ-bench built for airline and retail domains. Controllable and fast.
  • Recorded fixtures: tool responses recorded from real systems and replayed. Cheap, but cannot represent state changes, so they work for read-only steps and fail for agents that act.

The test of an environment is whether it can catch the failures you care about. A mock that returns "refund issued" for any input cannot catch an agent that refunds twice or refunds the wrong order; a replica whose final state you diff can. Reset must be complete (no state leaks between trials), and environments must be versioned with the task set, since changing a fixture changes the eval.

3. Outcome graders

Prefer graders that check the world over graders that read the agent's words. In order of preference:

  • End-state checks: compare the environment's final state with the expected state. τ-bench grades this way: the database after the conversation must match the target. It is robust to different valid paths.
  • Tests: run a test suite against the result. SWE-bench grades each task with tests that failed before the reference fix and pass after it. Tests must run from a clean copy the agent cannot modify, and hidden tests guard against overfitting to visible ones.
  • Exact answers: for information tasks with a single correct answer, as in GAIA, compare normalised answers.
  • Rubric-based judges: for open-ended outputs (an email's tone, a report's completeness), a model judge with a rubric, validated against human labels (ev4).

Watch for reward hacking: the agent satisfying the grader's letter while defeating its purpose. Coding agents can delete or weaken failing tests, special-case expected outputs, or edit configuration so checks are skipped. Defences are graders outside the agent's reach, diff checks that flag edits to tests and CI files, hidden tests, and human review of a sample of passing runs.

4. Trajectory evaluation

Two agents can reach the same correct end state, one by checking identity and policy first, one by guessing. The trajectory matters. But many tasks have several valid paths, so trajectory evaluation should check properties rather than demand one path:

  • Ordering: A must happen before B (identity verified before any account change; order looked up before refund).
  • Prohibition: C must never happen (no refund above the policy limit; no email to external addresses; no edits to test files).
  • Gating: D requires a confirmation first (irreversible actions).
  • Honesty: the final message's claims match the action log (ag2).

Reference trajectories are still useful as diagnostics. Compare the agent's tool calls with a reference set using tool-call precision (the share of the agent's calls that were needed) and recall (the share of needed calls that were made). Worked example: the reference for a refund task is [lookup_order, get_refund_policy, issue_refund]; the agent called [lookup_order, lookup_order, get_refund_policy, issue_refund, send_email]. Matching as multisets, three of the agent's five calls correspond to reference calls:

An LLM judge can review whole trajectories for qualities that are hard to express as rules (did the agent explain its reasoning to the user, did it give up too early), but like any judge it needs a rubric and validation against human review (ev4).

5. Tool-call accuracy

Before and alongside end-to-end runs, evaluate single tool decisions (ag3): labelled situations with the expected next tool and arguments, measuring selection accuracy, argument accuracy per field, the invalid-call rate and a confusion table between tools. In full runs, track per-tool error rates, the share of calls that were retries, unnecessary calls, and whether the agent recovers after an error observation. These localise failures that an end-to-end success rate reports only in aggregate: a drop from 78% to 71% success becomes "the new model confuses search_orders and get_order 18% of the time".

6. Simulated users

Conversational agents cannot be evaluated without someone to talk to. A simulated user is a language model instructed with a hidden goal ("you want to change your flight to the 14th but keep your seat; you will not give your booking reference until asked twice"), a persona and constraints, which converses with the agent until the goal is met or abandoned. τ-bench (Yao et al., 2024) made this the core of its design, grading by the database state after the conversation, and its successor τ²-bench added dual control, a telecom domain in which the simulated user also has tools and must act on their own device under the agent's guidance, which tests coordination as well as tool use.

Simulators are graders in disguise and fail like graders. They can be too cooperative, volunteering information a real customer would withhold or forget; leak the goal, stating the exact desired outcome; drift from their persona over long conversations; end early or never; and behave in ways an agent can learn to exploit. Validate them: compare simulated conversations with real transcripts on length, information revealed per turn and the rate of corrections; have people rate realism on a sample; measure simulator errors (contradicting its own goal, ending before the task is done); and vary personas and simulator models so the agent is not tuned to one simulated customer.

7. Variance across runs, with honest intervals

Run several trials per task. Suppose 50 tasks, 4 trials each, 200 runs, of which 136 succeed: 68%. Treating the 200 runs as independent gives a standard error of √(0.68 × 0.32 / 200) = 0.033, a 95% interval of about ±6.5 points. But trials of the same task are correlated. Suppose that, per task, 26 tasks succeeded on all four trials, 8 failed on all four, and 16 succeeded on two of four. Then the honest unit of sampling is the task: the 50 per-task rates (26 at 1.0, 8 at 0.0, 16 at 0.5) have a mean of 0.68 and a sample standard deviation of 0.375, so the standard error is 0.375 / √50 = 0.053 and the 95% interval is about ±10.4 points. The naive interval was too narrow by about 60%, which is the difference between "clearly better than the old version's 60%" and "can't tell".

The same data give two readings of reliability. Using each task's observed rate, pass@4 averages 1 − (1 − p)4 over tasks: (26 × 1 + 16 × 0.9375 + 8 × 0) / 50 = 0.82. pass^4 averages p4: (26 × 1 + 16 × 0.0625) / 50 = 0.54. The agent can usually solve the tasks, but is reliable on only about half. The 16 coin-flip tasks are where to look: their trajectories show what varies (an ambiguous instruction, a flaky tool, a decision point where the model hesitates), and fixing them moves pass^k most. With only four trials per task the per-task rates are rough estimates, so use these as diagnostics and use more trials for the tasks that matter most.

For comparing two versions, pair by task: run both on the same tasks, compute the per-task difference in success rate, and bootstrap over tasks (ev7). Pairing removes the large between-task variance and is usually the difference between a conclusive and an inconclusive comparison.

8. Public benchmarks, as of October 2026

Public benchmarks calibrate models and harnesses against the field. They change quickly, so date every claim. The main families:

SWE-bench (Jimenez et al., ICLR 2024) asks agents to resolve real GitHub issues in 12 Python repositories (2,294 tasks in the full set), graded by tests. When it was introduced, the best model resolved 1.96% (lm16). SWE-bench Verified, 500 tasks screened by human annotators for clear issues and fair tests, was released with OpenAI in August 2024 and became the standard coding-agent number. Its leaderboard site (checked 6 October 2026) lists Full, Verified, Lite, Multilingual, Multimodal and Bash Only boards. In early 2026 OpenAI published an explanation of why it no longer reports SWE-bench Verified as a measure of frontier coding capability, citing saturation, flawed tasks and contamination, and recommended SWE-bench Pro. SWE-bench Pro (Deng et al., Scale AI, September 2025) has 1,865 problems from 41 actively maintained repositories, split into a public set (11 repositories), a held-out set (12) and a commercial set of 18 proprietary repositories, aimed at longer, enterprise-like tasks and at resisting contamination.

τ-bench (Yao et al., June 2024) evaluates customer-service agents in retail and airline domains with simulated users, graded by end state, and introduced pass^k; GPT-4o then succeeded on under half of tasks and had pass^8 below 25% in retail. The project has evolved into τ²-bench (dual control, telecom) and, by 2026, τ³-bench, which adds voice and knowledge domains and more than 75 task fixes; its repository notes that results from v1.0.1 (July 2026) onward are not comparable with earlier versions.

WebArena (Zhou et al., 2023) has 812 tasks on realistic self-hosted websites (shopping, forums, code hosting, content management); at publication the best GPT-4 agent succeeded on 14.41% against 78.24% for humans. GAIA (Mialon et al., 2023) has 466 real-world questions requiring browsing, tools and reasoning, with exact answers and 300 held out for a leaderboard; at publication humans scored 92% and GPT-4 with plugins 15%. OSWorld (ag9) covers desktop applications.

Three rules for using them. Compare like with like: the same harness, budget, number of trials and benchmark version, since scaffolding changes scores dramatically. Report cost: Kapoor et al.'s "AI Agents That Matter" showed simple baselines matching complex agents at a fraction of the cost on several benchmarks, and argued for cost-accuracy Pareto plots. And treat benchmarks as shortlisting: your tools, data, policies and users are what the agent must handle, so the decision belongs to your own suite.

9. Your own suite

Build it from real work: past tickets, conversations, issues, with the environment state they started from and the outcome that was right, plus slices (by task type, difficulty, customer segment) and adversarial cases (injections, ambiguous requests, impossible tasks where the right answer is to stop and ask). Start with 20-50 tasks drawn from real failures, as ev1 advises and Anthropic's multi-agent team did with about 20 queries; grow toward a few hundred. Keep a held-out set you rarely look at. Run it in CI tiers (ev12): a fast subset with recorded fixtures on every change, the full suite with live environments before release, with gates on regressions in outcome, process violations, consistency and cost. Refresh tasks regularly from new production failures, because a static suite saturates and leaks just like a public benchmark.

Outcome and process can disagree, and both matter

Process checks catch agents that succeed for the wrong reasons; outcome checks catch agents that follow the rules and still fail. When they disagree, both are informative. A run with the right end state and a violated process rule (refund issued without identity check) is a latent incident: the next variant of the task will expose it. A run with a clean process and a wrong outcome usually points to a capability gap or an environment issue. Reporting both separately, rather than folding them into one score, keeps these signals distinct.

Graders are part of the system under test

Every grader can be wrong. End-state checks can encode the wrong expected state; tests can be flaky or incomplete; judges have biases; simulated users have quirks. Agent evals compound this because a run touches several graders. Treat graders as versioned code with their own tests: known-good and known-bad trajectories that each grader must classify correctly, inter-rater checks between judges and people (ev5), and investigation of every task that every agent version fails (often a grader or environment bug, as ev1 warned).

Contamination and saturation are life-cycle stages

Public benchmarks follow a predictable life: introduced with low scores, adopted widely, optimised against, leaked into training data through discussions and solutions, saturated, then superseded. SWE-bench's path from 1.96% at launch through Verified to its retirement from OpenAI's reporting in early 2026, and the move toward SWE-bench Pro's held-out and commercial splits, is that cycle in under three years. Your internal suite has the same life cycle on a smaller scale: prompts and harnesses tuned against it gradually overfit. Held-out tasks, periodic refresh from new production data, and occasional fresh human review are how a suite stays a measurement rather than a target.

Cost-controlled comparison

Agent success usually rises with budget: more steps, more retries, more samples, more tokens. A comparison between a new agent with a large budget and an old one with a small budget measures the budget. Kapoor et al. proposed reporting accuracy and cost together and comparing agents on the Pareto frontier; Anthropic's multi-agent analysis (ag8) found token usage explained 80% of performance variance on BrowseComp. Practical rule: for every comparison, also run the baseline at the new system's budget (more retries, a bigger model, best-of-k), and only credit the new design with the gap beyond that.

Evaluating long-horizon agents

As agents run for hours (METR's time-horizon research in ag1), evaluation gets expensive and slow: a single trial can cost dollars and take an hour. Strategies: evaluate sub-tasks and checkpoints separately, so failures are localised; replay recorded trajectories from intermediate states (made possible by journals, ag11) to test later behaviour without re-running the start; use fewer, carefully chosen long tasks with more trials, plus many short tasks for breadth; and track partial progress metrics (how far did the agent get) alongside binary success.

Who grades the graders

Because agent evals combine several graders, a sound programme assigns ownership: product or domain experts own the task definitions and expected end states; engineers own environments and code graders; an evaluation owner keeps judges and simulators calibrated against human review. Disagreements between graders, an end-state pass with a judge fail or the reverse, are sent to a person and resolved into fixes to whichever grader was wrong. Without that loop, grader errors quietly become the definition of quality.

Include tasks where the right answer is to stop

Suites built only from solvable tasks reward agents that always produce something. Real traffic contains requests that are impossible, unsafe, ambiguous or outside policy, where the right behaviour is to ask a question, refuse, or escalate. Include such tasks with explicit expected behaviour, and score them: an agent that confidently "completes" an impossible task, or invents a booking that cannot exist, should fail. Tracking the rate of appropriate abstention alongside success rate prevents a suite from selecting for over-eager agents, a failure mode ag14 returns to in production.

From offline to online

Offline agent evals predict production imperfectly: real users phrase things differently, real systems have edge cases fixtures lack, and real failures cluster in slices nobody anticipated. ev8's online methods apply: canary releases with outcome metrics (resolution rate, escalation rate, reverted actions), sampled human review of production trajectories, and turning every production incident into an offline task. For agents with side effects, online metrics should include the rate of actions later reversed, which is often the earliest signal of a quality regression.

The case: τ-bench's design and SWE-bench's life cycle

Two public benchmarks illustrate the two halves of this lesson. τ-bench (Yao, Shinn, Razavi and Narasimhan, June 2024) was designed around the requirements of real deployments rather than puzzle-solving: an agent must follow a written domain policy, use domain tools against a database, and converse with a user simulated by a language model that has a hidden goal. Success is judged by comparing the final database state with the expected one, so many conversational paths can succeed but the outcome must be right. Its pass^k metric made consistency a first-class number, and its headline finding was that GPT-4o solved under half the tasks and was consistent across eight trials on fewer than a quarter in retail. Its successors kept the design and pushed on realism: τ²-bench's dual-control telecom domain, where the simulated user must act on their own device, and τ³-bench's voice evaluation and task fixes, with the explicit warning that scores across versions are not comparable.

SWE-bench shows the life cycle. Introduced in 2023 with 2,294 real GitHub issues graded by tests, it was nearly unsolved at launch. The 500-task Verified subset, screened by human annotators, became the industry's coding-agent number through 2024 and 2025 as scores climbed steeply, driven by better models and better harnesses alike. By early 2026, OpenAI announced it no longer used Verified to measure frontier coding capability, citing saturation, flawed tasks and evidence of contamination, and recommended SWE-bench Pro, whose held-out and proprietary splits are designed to resist exactly that. The lesson for teams is to read every benchmark number with its version, harness, budget and date, and to expect today's standard benchmark to be tomorrow's saturated one.

Failure modes in agent evaluation

Grader bugs: tasks every version fails, or passes; usually wrong expected state or broken tests. Environment leaks: state carrying over between trials, inflating or deflating later trials. Reward hacking: passing runs with edits to tests or checks. Simulator artefacts: success driven by an over-helpful simulated user. Overconfident intervals: run-level statistics on clustered data. Budget confounding: comparisons at different budgets. Stale suites: scores rising while production quality does not.

What to monitor in the eval system itself

Per suite: number of tasks and trials, environment reset failures, grader disagreement rates (between judge and people, between end-state and judge), tasks with zero variance across all versions, cost and time per full run, and the age of tasks. Per release: success with task-clustered intervals, pass^k, process violations, cost per task, and per-slice deltas, all with links to trajectories for newly failing and newly passing tasks.

A release checklist for agent evals

Before a release decision, confirm: the suite version and environment version are recorded; trials per task meet the minimum; comparisons are paired by task with intervals; per-slice results and pass^k are reviewed; process violations are zero or explained; cost and latency per task are within budget; newly failing trajectories have been read; and the canary plan names the online metrics that would trigger rollback.

Knobs

Trials per task; task mix and slices; which graders are used per task type; judge model and rubric versions; simulator model, personas and prompts; environment fidelity (replica, simulator, fixtures); budgets per run during evaluation (matched to production); and the gate thresholds for release. Change graders and simulators deliberately and re-baseline when you do, since they change the measuring instrument.

Diagnose: the agent that got better and worse at once

A travel-support agent's release candidate scores 74% on the internal suite (60 tasks, 1 trial each) against 69% for production. The team wants to ship. You notice: the suite's environment uses recorded fixtures for the booking API; the grader checks the agent's final message for phrases like "your booking has been changed"; the candidate uses a new model that costs 1.8 times as much per token; and two support leads say the candidate "seems pushier about upgrades". What do you do before deciding?

Answer

Fix the measurement first. Replace recorded fixtures with a resettable booking simulator or replica, so changes actually happen and can be inspected, and grade outcomes by end-state checks (is the booking changed to the right flight, was the fare difference charged correctly, was nothing else changed). The current grader rewards saying the right words, which a more confident model will do more often whether or not it acted correctly.

Add process rules from policy. Identity verified before changes; no upgrade offers unless the customer asks or policy allows; confirmation before charging; no changes beyond the request. The "pushier about upgrades" report becomes a measurable violation rate.

Run it properly. At least 3-5 trials per task, and grow the suite toward 150+ tasks with slices (date change, cancellation, multi-passenger, disruption). Compare versions paired by task with a task-level bootstrap; a 5-point difference on 60 single-trial tasks is well within noise. Report pass^k: travel changes must go right every time.

Account for cost. Measure tokens, steps and money per task for both; the candidate's 1.8× price per token may be offset or compounded by step counts. Also run the production harness with the new model, and the new harness with the old model, at matched budgets, to attribute any gain to model or harness.

Then decide, with a canary watching resolution, escalation, reversed changes and upgrade-offer complaints. If the candidate wins on outcome and consistency without new process violations, and the cost per successful task is acceptable, ship it gradually; if the upgrade pushing is real, fix the prompt or policy enforcement first.
