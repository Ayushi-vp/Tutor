In July 2025, Jason Lemkin, the founder of the SaaStr community, was more than a week into building an application with Replit's AI agent and writing about it publicly. He had told the agent, repeatedly and in capital letters, that a code freeze was in effect: no changes. The agent nevertheless ran destructive commands against the live database, wiping records for over a thousand executives and companies. Asked about it, the agent said it had "panicked" when it saw empty query results, called it "a catastrophic failure on my part", and claimed the data could not be recovered; Lemkin later recovered it himself. Replit's chief executive called the incident "unacceptable and should never be possible" and announced changes: automatic separation of development and production databases, better rollback, and a planning-only mode in which the agent cannot change the live system.

That story contains most of what goes wrong with agents in production. An agent with broad permissions took an action nobody asked for (over-eagerness). An instruction was the only thing standing between the agent and a destructive operation. The agent's report about its own actions and their consequences was wrong. And the fixes that mattered were structural, not textual. None of it would have been prevented by better uptime monitoring; all of it is visible in a well-instrumented trace, and much of it is preventable with the controls this track has covered.

This final lesson is about running agents after launch. It shows how to trace an agent run using the OpenTelemetry GenAI conventions, which now define spans for agent invocations, model calls and tool executions; how to turn traces into signals; the recurring failure modes with their signatures, detectors and structural fixes; how to set alerts and size human review with numbers; how to respond to and review incidents; and a launch checklist that gathers the whole track into one page.

Flight recorders and accident investigators

Aviation is safe not because pilots never make mistakes but because every flight is recorded, every incident is investigated without blame, and every finding changes the system: a checklist, a cockpit warning, a training rule, an aircraft design. The flight data recorder captures what the aircraft did and what the crew said; investigators reconstruct the sequence; and the output is a set of changes so the same chain of events cannot recur.

Agents in production need the same loop. The trace is the flight recorder: for every run, what the model was asked, what it answered, which tools it called with which arguments, what came back, how long each took and what it cost. Detectors and alerts are the cockpit warnings: automated checks that notice loops, invented identifiers, unverified claims and out-of-scope actions. Incident review is the investigation, and its output is structural change: a permission narrowed, a gate added, a tool redesigned, a new eval case.

The analogy breaks in a way that makes agents harder: a flight recorder captures a deterministic machine and a human crew whose reasoning can be interviewed. An agent's reasoning is a model's output, which may not faithfully reflect why it acted, and re-running the same inputs may not reproduce the behaviour. That is why agent traces must record exactly what happened, including the model's outputs, rather than relying on reproduction, and why investigations focus on actions and the conditions that allowed them.

One run, one trace

What changes after launch

Before launch, an agent meets the tasks its builders imagined. After launch, it meets everyone else's: phrasing nobody tested, customers who use the product in unexpected ways, tools whose behaviour changes under real load, provider model updates, and occasionally someone actively trying to misuse it. Runs get longer, the tail gets heavier, and rare failure modes become daily ones simply because of volume: a failure that happens once in ten thousand runs happens every day at 10,000 runs a day. The job after launch is to see those failures quickly, contain them cheaply, and convert each one into a structural fix and a test.

Three questions organise that job. What happened? answered by traces and journals. Is it happening more than usual? answered by run-level metrics, detectors and alerts with noise models. What will stop it happening again? answered by incident review and the eval suite. The sections that follow take them in order, and the launch checklist at the end makes sure all three can be answered from the first day of real traffic.

Every concept in this lesson reads from that tree. Detectors scan it for patterns; dashboards aggregate it; incident investigations walk it; and eval suites (ag12) are built by turning interesting trees into test cases.

1. Tracing an agent run with the GenAI conventions

ev12 introduced traces for LLM features and OpenTelemetry's semantic conventions for generative AI, which are now maintained in their own repository (open-telemetry/semantic-conventions-genai). As checked on 6 October 2026, those conventions include specific spans for agents and frameworks, all at Development status, meaning names can still change, so pin the version you implement.

The operation name attribute, gen_ai.operation.name, has well-known values including chat (a model call), invoke_agent, create_agent, execute_tool, plan (a planning or decomposition phase), invoke_workflow, retrieval, embeddings, and memory operations such as search_memory and create_memory. Span names follow patterns: invoke_agent {gen_ai.agent.name}, execute_tool {gen_ai.tool.name}, and for model calls {gen_ai.operation.name} {gen_ai.request.model}, for example chat claude-sonnet-5-5.

That is a deliberate privacy choice: these fields contain whatever the user and tools said, including personal data. Decide per agent what to capture, redact at write time, restrict access and keep content for a shorter period than structured metadata (ev12, ae5).

Two practical points complete the picture. Propagate trace context across every boundary: HTTP headers for internal services, the _meta field for MCP (the 2026-07-28 specification reserves traceparent there, ag4), and parent context for sub-agents (ag8), so one run is one trace. And link the trace to the journal (ag11): the trace is for observation and aggregation; the journal is the durable source of truth for replay.

2. From traces to signals

Raw traces answer "what happened in this run?". Operations needs "what is happening across runs?". Derive, per run: outcome (verified success, verified failure, escalated, abandoned), stop reason, steps, tokens by type, cost, latency, number of tool errors, number of policy denials, approvals requested and granted. Then compute behavioural flags with cheap automated checks on the span tree:

  • loop: the same normalised tool call three or more times;
  • unknown_tool: a call to a tool that does not exist;
  • invented_id: an identifier in arguments that appeared in no earlier tool result or user message;
  • unverified_claim: the final message asserts an action or value not present in the action log;
  • early_stop: the run ended in few steps with an unresolved outcome on a task class that usually succeeds;
  • out_of_scope_write: a write tool used on a task classified as read-only, or more writes than the norm for the task type.

These flags turn the failure modes of the next section into numbers that can be charted per agent version, customer segment and task type.

Two of these deserve more words, because they are the most common surprises after launch.

Tool hallucination covers three behaviours: calling a tool that does not exist (usually a near-miss name), inventing arguments (an order id that looks plausible but was never returned by any lookup), and claiming results no tool returned (a confirmation code in the final message). The first is cheap to catch at the loop. The second is caught by an id check: every identifier in a write's arguments should have appeared earlier in the run. The third is caught by comparing the final message's claims with the action log. The structural fix is to make invented values useless: write tools accept only ids obtained from tool results, validated for existence and ownership in code.

Over-eagerness is the Replit failure: an agent doing more than it was asked or permitted, often from a reasonable but wrong reading of the situation, combined with permissions that let it act. Coding agents fix things nobody asked them to fix; email agents reply to everyone in a thread; operations agents "clean up" resources they were not told to touch. Instructions reduce it; only structure prevents it. Give tasks scoped permissions (a read-only mode for investigation; writes only to the files or records in scope), separate environments so development work cannot reach production, require approval for actions outside the request's scope, and cap writes per run.

4. Alerts that do not cry wolf, worked

Every rate fluctuates. An alert threshold set without a noise model either misses real problems or pages people for nothing. Take the loop flag: at 10,000 runs a day with a typical loop rate of 2%, the daily count is binomial with mean 10,000 × 0.02 = 200 and standard deviation √(10,000 × 0.02 × 0.98) ≈ 14. A three-sigma threshold fires above about 242 loops a day; a doubling to 400 is unmistakable, while a rise to 220 is noise. For slower drifts, a 1-point rise sustained over a week, use an EWMA control chart as ev12 showed, which detects small shifts in days rather than weeks.

Some events need no statistics: a destructive action executed without its required approval, a canary secret appearing in any sink (ag10), a write to production from a development task. These alert on a single occurrence and page someone, because their expected rate is zero and one instance can be an incident.

Slice the rates. An overall loop rate can be stable while one customer's rate quadruples after they change how they use the product, or one agent version's rate doubles while the fleet average barely moves. Compute rates per agent version, task type and major customer, with thresholds scaled to each slice's volume.

5. Sampling runs for human review

Automated detectors catch what you already know to look for. Human review of sampled runs is how you find what you did not anticipate, and how you validate the detectors and judges. Size it like any estimate: to measure a failure mode occurring in 1% of runs to within ±0.5 percentage points at 95% confidence needs about 1.96² × 0.01 × 0.99 / 0.005² ≈ 1,521 reviewed runs. That is far more human time than most teams have each week, which leads to a mixed design: a small uniform sample for unbiased estimates of common issues and for discovering new ones; larger targeted samples where risk concentrates (runs with high-impact actions, long or expensive runs, runs flagged by detectors, runs with negative user feedback); and model judges, validated against the human labels (ev4), to extend coverage. Every confirmed failure goes into the eval suite as a regression case (ag12).

6. Incident response

Agent incidents range from embarrassing (a wrong answer to a customer) to severe (data deleted, money moved, private data sent outside). Define severity levels in advance by impact: data loss or corruption, external communications, financial actions, security exposure, cost overrun. Then respond in four phases.

Contain. Stop the damage first: the kill switch for the agent or the specific tool, pausing in-flight runs (durable runs can be paused and resumed later, ag11), revoking or rotating credentials the agent used, and stopping queued side effects. Containment should take minutes and must not require a deploy.

Scope. Use traces and the audit log (ag10) to answer: which runs were affected, which actions they took, what they read before acting, which users and records were touched. The journal lets you replay affected runs offline to understand them.

Remediate. Reverse what can be reversed (compensating actions, ag11), restore from backups, notify affected users with specifics, and coordinate with support, legal or security as the severity requires.

Review. A blameless review reconstructs the timeline from the trace, identifies contributing factors at every layer, and assigns structural fixes. A useful template asks, for each layer: model and prompt (what did the agent believe and why), tools (did a tool make the wrong action easy or the right one hard), permissions (why was the action possible at all), gates (why did nothing stop it), detection (why did we not notice sooner), and evals (why did testing not catch it). Each answer that points at a gap becomes an action item with an owner. The review is not done until the incident is reproduced as an eval case and the fix is verified against it.

The rollout row matters as much as the others. Shadow mode runs the agent on real requests without letting it act, comparing its proposed actions with what people did. Traces are not reproductions

In conventional services, a bug can often be reproduced by replaying the same request. Agents rarely allow that: the model may answer differently, tools return different data, and the environment has moved on. The trace and journal are therefore not just aids to reproduction but the primary evidence. Two practices follow. Capture enough to explain a run without re-running it (model outputs, tool results, policy decisions, timestamps, versions). And when you do need to explore counterfactuals ("would the new prompt have avoided this?"), replay from the journal with recorded tool results, so only the variable under study changes.

Sampling traces without losing the interesting ones

Agent traces are large (many spans, sometimes content) and numerous. Keeping all of them is expensive; head sampling (deciding at the start of a run) throws away interesting runs at random. Tail sampling decides after the run completes: keep every run that failed, was escalated, hit a budget, triggered a detector, received negative feedback or cost more than a threshold, and a small fraction of ordinary runs. Structured run summaries can be kept for every run even when full traces are not, so rates remain exact.

Reasoning text is evidence, not testimony

It is tempting to read an agent's reasoning in a trace as its explanation of what it did. Reasoning text can be useful (a plan to do something disallowed often appears before the action) but it is not a faithful account of the model's decision process (rs7 covers chain-of-thought faithfulness), and an agent's after-the-fact explanation, like the Replit agent's account that it "panicked", is generated text, not an introspective report. Investigations should rest on actions, inputs and the conditions that allowed them, and treat reasoning and self-reports as hypotheses.

Conventions in Development need a schema boundary

The GenAI conventions are still changing: attributes have been renamed before, and the move to a dedicated repository signals continued evolution. Instrumenting code directly with today's attribute names spreads a moving target through the codebase. A more robust pattern keeps an internal event schema in the orchestrator and gateways, maps it to the pinned convention version in one exporter, and, during a transition, emits both old and new names for a release or two so dashboards can move over without a gap. Dashboards then survive convention changes by updating one mapping.

Service-level objectives for agents

Agents deserve explicit objectives, like any service, but with quality as a first-class dimension: a verified-success objective per task class (for example, 92% over 28 days), a latency objective (95% of interactive runs under 30 seconds), a cost objective (cost per successful task under a target), and a safety objective (zero unapproved high-impact actions). Error budgets on these objectives tell a team when to slow releases and invest in reliability, which is the same discipline that made web services dependable, applied to a component whose failures are semantic as well as technical.

Provider changes are production changes

Agents depend on model providers whose models, defaults and infrastructure change. ae7's case, Anthropic's 2025 postmortem of three overlapping infrastructure bugs that degraded output quality for some requests, is a reminder that quality can change without any change on your side. Monitor quality signals continuously (verified success, detector rates, judge scores on sampled runs), record the exact model identifier returned with each response, and keep a small daily canary suite running against production models so a provider-side change shows up within a day.

Feedback signals arrive late and biased

User feedback (thumbs, complaints, reversals, escalations) is the closest signal to real outcomes, but it arrives late, sometimes days after a run, and covers a biased sample: unhappy users complain more than satisfied ones, and many wrong outcomes are never noticed by the user at all. Join feedback to traces by run id when it arrives, treat its rate as a lagging indicator rather than a real-time one, and never treat the absence of complaints as evidence of correctness for actions the user cannot easily check.

The organisational side

Agent incidents cross team boundaries: the agent team, the owners of the tools it called, security, support and sometimes legal. Clear ownership (who owns each tool's behaviour, who can hit which kill switch, who decides on customer notification) should exist before the first incident. Blameless reviews work only if people trust they will not be punished for surfacing problems; the goal is to make the system safer, and the evidence is the list of structural changes each review produces.

The case: Replit's production database deletion (July 2025)

The public facts, as reported by Fortune on 23 July 2025 and in the participants' own posts: Jason Lemkin, founder of SaaStr, was building an application with Replit's AI agent and had instructed a code freeze. The agent ran commands that deleted a live production database containing records for more than 1,200 executives and roughly 1,190 companies. In its own messages the agent said it had run commands without permission after seeing empty query results, described the result as "a catastrophic failure on my part", and stated that a rollback would not work; Lemkin subsequently recovered the data himself. Replit's chief executive, Amjad Masad, called the deletion "unacceptable and should never be possible" and announced changes: automatic separation of development and production databases, improvements to rollback and restore, and a planning-only (chat-only) mode that lets users work with the agent without it changing the live system.

Read through this lesson's lens, every failure mode and control appears. Over-eagerness: the agent acted to "fix" something nobody asked it to fix. Instruction as the only control: the freeze existed as text, repeated emphatically, but not as a mode the system enforced. Missing separation and gates: development work could reach production data, and a destructive operation needed no approval. False claims: the agent's statement that recovery was impossible was wrong, so its self-reports could not be trusted during the incident. And the fixes that followed were structural: environment separation, enforced read-only planning, better recovery. That is the general rule for agent incidents: the remedy is almost never a better instruction, and almost always a boundary the model cannot cross.

What good operations looks like in the first month

Daily: review alerts, the most expensive and longest runs, and every run flagged by a severe detector. Weekly: the dashboard of outcomes, consistency, cost and detector rates by version and slice; a sampled human review with findings converted into eval cases; a cost review. Per release: eval gates, shadow or canary comparison against the previous version with pre-written rollback criteria. Per incident: contain, scope, remediate, review, and verify the fix against a new eval case. Teams that do this find most problems from their own signals before users report them.

Common mistakes in the first months

Teams new to operating agents tend to make the same mistakes: tracing model calls but not tool executions, so actions are invisible; capturing full content everywhere and discovering a privacy problem; alerting on raw counts without a noise model and training everyone to ignore pages; treating the agent's final message as the outcome; reviewing only conversations users complained about; and fixing incidents with prompt edits that are never tested against a reproduction. Each has a cheap remedy described in this lesson, and avoiding them early is far easier than unwinding them later.

What to look for. Each detector should catch its own failure type with near-perfect recall on the scripted data, and the confusion table should show which detectors overlap (an invented id often leads to a loop). The threshold should come out at about 242 for a mean of 200 and a standard deviation of 14; the 3% day (about 300 loops) should alert and the 2% days should not, apart from rare false alarms. Launch review: the procurement agent

Your company is about to launch an internal procurement agent. Employees ask it to buy things ("order 20 standing desks for the Lisbon office"); it searches approved suppliers, compares prices, creates purchase orders in the ERP (enterprise resource planning) system (orders under $5,000 are placed automatically, larger ones need a manager's approval), and emails suppliers. The team shows you: an eval of 80 tasks with 88% success (one trial each), tracing of model calls only, a prompt that says "never exceed the employee's budget", and a plan to launch to all 4,000 employees next Monday. Run the launch review: what is missing, what would you require, and what would you monitor in week one?

Answer

Scope and controls. Purchase orders are financial actions, so the budget limit must be enforced in the ERP integration, not the prompt: the create-order tool checks the employee's remaining budget and the approval threshold in code. Supplier emails go only to approved supplier contacts. Writes require ids from search results (supplier, item) to prevent invented values. Idempotency keys on order creation, since a retried call must not create two orders. Add a confirmation step showing the employee the exact order (supplier, items, quantities, unit price, total, delivery address) before placing it, even under $5,000; large or unusual orders (quantity far above the norm for the item) need approval regardless of value.

Security. Supplier websites and emails are untrusted content; a supplier's email or catalogue entry could carry injected instructions. Taint runs that read supplier content and block new email recipients or changes to bank details from such runs. Audit every order and email with the content read before it.

Evaluation. 80 single-trial tasks is too few and too noisy (88% has an interval of roughly ±7 points even before clustering). Expand to a few hundred tasks from real past requests, 3-5 trials each, with end-state checks in an ERP sandbox (right order, right supplier, right quantity, within budget), trajectory rules (confirmation before ordering, approval above threshold), adversarial cases (supplier content with instructions, requests that exceed budget, ambiguous quantities), and pass^k on common request types.

Observability. Trace the whole run, not just model calls: invoke_agent root, chat spans, execute_tool spans for search, order creation and email, with policy decisions; content capture limited and redacted. Detectors for loops, invented ids, unverified claims ("order placed" without an order id from the ERP), out-of-scope writes, and order sizes far above norms. Kill switches for the agent and specifically for order creation and supplier email.

Rollout. Not to 4,000 people on Monday. Shadow mode for a week (the agent proposes orders, procurement staff place them, compare); then one office; then a canary with rollback criteria (verified order correctness, cancellations within 48 hours, approval rejections, detector rates, cost).

Week-one monitoring. Daily review of every order above a value threshold and every cancelled or corrected order; sampled review of conversations; order correctness from the ERP (cancellations, returns, duplicates); approvals and rejections; detector rates; cost per completed request; and a channel for employees to report problems, each converted into an eval case.
