A travel company builds an agent that plans business trips. It is good at understanding what a traveller wants, but the actual inventory lives elsewhere: airlines, hotel chains and a corporate-card provider each run their own agents, built on different frameworks, by different teams, behind different security perimeters. The travel agent cannot call their internal tools, and they would never let it. What it can do is ask: "book a refundable seat on a morning flight to Berlin under this fare policy", and let the airline's agent decide how. Without a shared protocol, every pair of companies negotiates a custom integration, with its own way of describing what an agent can do, tracking a job that takes twenty minutes, asking a clarifying question, proving who is calling, and reporting the result. With five partners that is five integrations; with fifty it is a full-time team.

This is the problem interoperability protocols address, and in 2025–26 two became widely adopted. The Model Context Protocol (MCP, ag4) standardised how an agent uses tools and data: one agent, many capabilities it drives directly. Agent2Agent (A2A) standardised how one agent delegates a task to another, independent agent: opaque collaborators, long-running work, clarifying questions, artifacts. Around them, smaller protocols cover the edges: AG-UI for streaming an agent's work to a user interface, and AP2 for proving a user authorised a payment. The field moves monthly, so every claim in this lesson about versions and adoption is dated.

Senior interviews probe this with "MCP or A2A, and why?", "how would two companies' agents trust each other?", "what happens when the remote agent times out halfway through a booking?" and, most usefully, "would you even split this into multiple agents?". Good answers know what each protocol standardises and, just as important, what it leaves to you: semantics, trust, failure handling and the decision not to add a network hop.

This lesson recaps MCP briefly, then works through A2A 1.0 in detail: agent cards and discovery, tasks and their states, messages, parts and artifacts, the operations and their three wire bindings, streaming and push notifications, and versioning. It covers authentication and trust between vendors, failure and timeout semantics, the other protocols with real adoption on the day of writing, and the architecture question of when not to use any of them. The lab builds a toy two-agent exchange over a JSON task protocol in the standard library.

A note on what "agent-to-agent" means in practice today. Most production traffic between agents in 2026 is still between agents owned by one organisation, often over plain APIs or a framework's own conventions, and the cross-company A2A deployments the Linux Foundation describes are concentrated in areas like supply chain, financial services, insurance and IT operations, where many independent parties already exchange structured work. So the skill interviewers test is less "recite the A2A spec" and more "know when a protocol boundary is warranted, what it gives you, and what you still have to build around it".

Tools you drive versus contractors you hire

Think about how a building company works. Some things it does with its own tools: a drill, a ladder, a measuring tape. It decides exactly what each tool does and when, and the tool returns immediately. Other things it hires out: the electrical work goes to a licensed electrician. The builder does not tell the electrician which wire to cut; it describes the job ("wire the kitchen to code, budget £3,000"), the electrician plans the work with their own tools, may come back with questions ("do you want under-cabinet lighting?"), takes days, and hands over a certificate at the end. The builder needs a way to find electricians, check their licences, track the job, answer questions and receive the result, but never sees inside the electrician's van.

MCP is the standard for tools: an agent sees each tool's name, description and input schema and calls it with arguments of its choosing. A2A is the standard for hiring contractors: an agent finds another agent by its published Agent Card, sends a task in natural language and structured parts, tracks it through states, answers questions when the remote agent needs input, and receives artifacts. The remote agent is opaque: its prompts, tools, model and memory are its own business.

The analogy breaks in one way that matters for security: a human contractor is unlikely to be talked into stealing from you by a note left in your kitchen, while an agent can be manipulated by content it reads. Messages from a remote agent are untrusted input to your own model, however reputable the vendor.

The protocol stack around an agent

What a protocol can and cannot standardise

A protocol can standardise the envelope: how to find an agent, how to describe what it offers, how to start, track, question, cancel and finish a piece of work, how to authenticate, how to signal errors and versions. It cannot standardise meaning. When the travel agent asks the airline agent for "a refundable morning flight", the two must agree on what refundable and morning mean, which details are required, and what a good answer looks like. Skills in an Agent Card are described in natural language, with tags and examples; whether the remote agent really does what its card says is learned by testing, contracts and experience. Keep that limit in mind: interoperability protocols remove plumbing work, not integration judgement.

A short history, because versions matter

MCP was open-sourced by Anthropic in late 2024 and adopted quickly by AI platforms and developer tools; by the time the Linux Foundation formed the Agentic AI Foundation around it in December 2025, the foundation counted over 10,000 MCP servers. A2A was announced by Google in April 2025 with about 50 partners, donated to the Linux Foundation in June 2025, went through 0.2 and 0.3 releases during 2025, and reached 1.0 in March 2026. Interviewers sometimes test whether you know these are recent and still moving: an answer that says "as of the 1.0 specification" or "in the 2026-07-28 MCP revision" shows you know which version you are describing, and that you would check before building on a detail.

A reader who stops here should remember: MCP is for tools you control, A2A is for other agents you delegate to, both are envelopes, and every protocol hop is a cost you should only pay at a real boundary.

A rule of thumb follows. If you would describe the interaction as "call this function", it is a tool, and MCP (or a plain API) fits. If you would describe it as "get this done and tell me when it's finished", and the other side has its own judgement, state and owners, it is a task for another agent, and A2A fits.

2. MCP in one paragraph

As covered in ag4: an MCP host (the agent application) runs clients that connect to servers; servers expose tools (callable functions with JSON Schema inputs), resources (readable data) and prompts (templates). Messages are JSON-RPC over stdio for local servers or Streamable HTTP for remote ones; the 2026-07-28 revision made the protocol stateless; remote servers use OAuth 2.1 authorisation. Tool names, descriptions and results all land in the model's context, which is why tool descriptions are prompt surface and why MCP servers are supply-chain dependencies. Nothing in this lesson changes that; A2A sits beside it.

3. A2A's building blocks

A2A, in its 1.0 specification (released 12 March 2026; 1.0.1 on 28 May 2026), defines a small data model.

  • Agent Card: the remote agent's self-description, a JSON document with its name and description, a list of supported interfaces (each a URL, a protocol binding and a protocol version), the provider organisation, capabilities (streaming, push notifications, extended card), security schemes and requirements, default input and output media types, and skills.
  • Skill: one capability, with an id, a name, a natural-language description, tags, example requests and accepted input and output types.
  • Message: one turn, with a role (user or agent), a messageId, optional taskId and contextId, and parts.
  • Part: the smallest unit of content: text, a file reference, or structured data.
  • Task: the stateful unit of work, with an id, a contextId, a status (state plus an optional agent message), a history and artifacts.
  • Artifact: an output of the task, made of parts: a document, an image, a JSON result.
  • Context: an id grouping related tasks and messages into one conversation.

4. Discovery

Clients find Agent Cards in three ways, per the specification: a well-known URI, https://{domain}/.well-known/agent-card.json; registries or catalogues that curate cards; and direct configuration. The well-known path makes the domain the anchor of identity: if TLS proves you are talking to supplier.example, the card served there is the one that domain publishes. Cards can be cached (the specification gives guidance) but must be refreshed, because interfaces, versions and skills change. Details an agent does not want to publish can go in an extended Agent Card, returned only to authenticated clients through GetExtendedAgentCard.

A2A 1.0 lets a card carry signatures: JSON Web Signatures (RFC 7515) over the card's content after canonicalising it with the JSON Canonicalization Scheme (RFC 8785), so any client can check that the card was published by the holder of a given key, even if it was obtained from a registry rather than the agent's own domain. A signature proves origin and integrity, not good behaviour.

5. The task lifecycle

A task moves through eight states. Four are active: submitted (accepted, not started), working, input-required (the agent needs something from the client to continue, with a message explaining what) and auth-required (the agent needs additional authorisation, such as the end user's consent to access their account). Four are terminal: completed, failed, canceled and rejected (the agent declined the task). Once a task is terminal it accepts no more messages; a follow-up becomes a new task in the same context.

SendMessage returns immediately with either a direct Message (for simple interactions) or a Task; with return_immediately unset, it waits until the task reaches a terminal state, and with it set to true it returns as soon as the task is created. Errors map to binding-specific codes: for example TaskNotFoundError is JSON-RPC −32001 and HTTP 404, TaskNotCancelableError −32002, UnsupportedOperationError −32004 and VersionNotSupportedError −32009.

7. Streaming, push notifications and polling

Three ways to follow a long task. Streaming: SendStreamingMessage (or SubscribeToTask for an existing task) returns a stream, over SSE in the HTTP bindings, that begins with the Task object and continues with TaskStatusUpdateEvent and TaskArtifactUpdateEvent objects until the task ends. It suits a client that is online and wants live progress. Push notifications: the client registers a webhook URL for the task; the agent POSTs status and artifact updates to it. It suits tasks that run for minutes or hours, and server-to-server integrations where nobody holds a connection open. The specification tells clients to process notifications idempotently because duplicates may be delivered, and the agent must only send to URLs it is willing to call, since a webhook URL supplied by a client is a classic server-side request forgery vector. Polling: GetTask at intervals, simplest and the universal fallback after a reconnect.

8. Versioning

A2A identifies protocol versions by major.minor (1.0); patch releases do not change compatibility. Clients must send an A2A-Version header (or request parameter) on every request; agents must process the request using that version's semantics or return VersionNotSupportedError. An empty header is treated as 0.3, so pre-1.0 clients continue to work with agents that still support 0.3. An agent can advertise several interfaces with different versions in its card, which lets providers migrate clients gradually. The A2A 1.0 release also introduced multi-tenancy features, modernised security flows and signed cards, according to the Linux Foundation's announcement.

9. Authentication, authorisation and trust between vendors

Trust has layers, and A2A provides hooks for each rather than a single answer.

  • Server identity: TLS on the agent's domain, plus a signed Agent Card if you obtained it elsewhere.
  • Client authentication: the card's security schemes say what the agent accepts (OAuth 2.0, OpenID Connect, API keys and others); the client obtains credentials out of band and presents them on each request. The specification is explicit that identity is established at the transport layer, not inside message content.
  • Authorisation: the remote agent must authorise every operation and only show a client the tasks it may see. For actions on a user's behalf, use delegated, scoped credentials (au12) rather than a powerful shared key.
  • In-task authorisation: if mid-task the agent needs more permission, such as a user's consent to read their bank data, it moves the task to auth-required and the client resolves it, possibly by asking its own caller, all the way up to a human. The specification warns that this state change by itself authorises nothing; credentials obtained for one request must not be assumed to cover later ones.
  • Behavioural trust: none of the above proves the remote agent does what its card says, handles your data well or resists manipulation. That comes from contracts, security reviews, testing, monitoring and limiting exposure: send the minimum data a task needs, validate artifacts against schemas, and treat every message from the remote agent as untrusted content for your model (ag10).

10. Failure and timeout semantics

Distributed tasks fail in partial ways, and A2A gives you the vocabulary to handle them, not the policy.

Duplicate sends. If the network fails after you send, you do not know whether the task was created. Retry with the same messageId; the specification allows agents to use it to detect duplicates, so check that your partner's agent does, and make your own A2A server do so. Get and list operations are naturally idempotent; cancel is idempotent.

Deadlines. The protocol has no global timeout. Set your own deadline per task, based on what your caller can tolerate, and when it expires send CancelTask, then read the task's final state. Cancel is a request: the agent may answer TaskNotCancelableError or may already have done irreversible work. Anything with side effects (a booking, a payment) needs idempotency keys and a compensating action on the remote side.

Stalls. A task in input-required or auth-required waits for you indefinitely unless you time it out. Decide who answers questions (your agent, your user) and how long you wait.

Partial results. Artifacts can stream in before a task fails; decide whether partial results are usable, and mark them.

Disconnects. If a stream drops, resubscribe or poll; if your webhook was down, list tasks by context and state to catch up.

Version and capability errors. Check the card's capabilities before using streaming or push; handle VersionNotSupportedError by negotiating an interface you both support.

11. The other protocols with real adoption

On 9 October 2026, beyond MCP and A2A, three adjacent efforts had visible adoption. AG-UI, the Agent-User Interaction Protocol from the CopilotKit community, is an open, event-based protocol for connecting agents to user-facing applications: messages, tool calls and state changes streamed to a front end so any compliant UI can render any compliant agent. AP2, the Agent Payments Protocol from Google's agentic-commerce effort, extends A2A with cryptographically signed mandates that record a user's authorisation for a purchase; the Linux Foundation's April 2026 announcement counted more than 60 supporting organisations in payments and financial services. And commerce-specific protocols (such as UCP, which the same announcement describes as compatible with AP2 mandates) sit on top for shopping flows. On governance, MCP moved to the Linux Foundation's Agentic AI Foundation when it was formed on 9 December 2025, alongside Block's goose and OpenAI's AGENTS.md; A2A is a separate Linux Foundation project. Names and positions in this space change quickly; check the projects' pages before relying on any of them.

12. When not to split into communicating agents

Interoperability protocols make it easy to build systems out of many agents, which makes it easy to build systems that are slower, costlier and less reliable than they need to be. Each A2A hop adds a network round trip and authentication, serialises context into messages (losing whatever the remote side is not told), runs another model with its own errors, and adds a partial-failure mode. Reliability multiplies: if each hop succeeds 95% of the time, a chain of five succeeds 0.95⁵ ≈ 77% of the time. Latency adds: five hops of a few seconds each is a long wait.

So the default inside one team, one codebase and one trust domain is not A2A. Use tools for capabilities, plain function calls or in-process sub-agents for decomposition (ag8), and a single agent where one will do. Reach for A2A when there is a real boundary: another organisation, another team that owns and deploys its agent independently, a different security or compliance domain, or a capability you buy rather than build. Even then, ask whether a plain API (deterministic, testable, cheap) would serve better than an agent; A2A is for when the other side genuinely needs judgement and conversation.

13. A delegation, end to end

Put the pieces together with the travel example. The trip-planning agent needs a refundable morning flight to Berlin for an employee.

  1. Discovery (once, cached): it fetches https://agents.airline.example/.well-known/agent-card.json, verifies the card's JWS signature against the airline's published key, sees a JSON-RPC interface at protocol version 1.0, a book-flight skill, streaming and push support, and an OAuth 2.0 scheme requiring a bookings scope.
  2. Credentials: it obtains a token for the corporate account, scoped to bookings for this traveller, through the company's identity provider (token exchange, au12).
  3. Send (t = 0): SendStreamingMessage with a messageId stored against the trip request, a text part with the goal and a data part with structured constraints (date, cabin, fare rules, cost centre). The stream opens with a Task in state working.
  4. Clarification (t ≈ 9 s): a status update moves the task to input-required: "Two refundable options: 07:10 at €412 or 09:45 at €389. Which?" The planner checks the travel policy, picks the cheaper compliant option, and sends a message with the same taskId.
  5. Authorisation (t ≈ 14 s): the airline agent moves the task to auth-required because the fare exceeds the company's pre-approved limit for that route. The planner escalates to the employee's manager through its own UI; approval arrives after 6 minutes; the planner sends the approval reference.
  6. Completion (t ≈ 6 min 30 s): artifacts arrive (a booking record as structured data, an e-ticket as a file part) and the task ends in completed. The planner validates the booking data against its schema before telling the traveller.
  7. Failure path: had the stream dropped at step 4, the planner would resubscribe; had it hit its 15-minute deadline in auth-required, it would cancel, read the final state, and tell the traveller the booking was not made, or that it was made if the cancel came too late.

Notice where the protocol helped (finding the agent, the states, the clarifying turn, the authorisation pause, structured artifacts) and where your design did the work (credentials, policy, deadlines, validation, the human approval). That division is the whole lesson in one trace.

14. Choosing between MCP, A2A and a plain API, worked

Three integrations from one company's backlog show the decision. A currency-conversion service: deterministic, instant, schema-shaped; expose it as an MCP tool or call its API. A vendor's contract-review service that reads a contract, asks which jurisdiction applies, and returns a marked-up document after an hour of work by its own agent and lawyers: goal-shaped, long-running, conversational, owned by another company; A2A. An internal "summary agent" and "translation agent" that another team built inside the same product, called synchronously from one workflow: same codebase, same trust domain, same deploy cadence; make them functions or in-process sub-agents and skip the protocol. The questions behind each answer are always the same: is the other side deterministic or does it exercise judgement, is the work quick or long, and is there an ownership or trust boundary between us?

Opaqueness is a feature and a cost

A2A deliberately hides the remote agent's internals: its prompts, tools, model and memory. That protects the provider's intellectual property and security, lets it change implementation freely, and keeps your context small. The cost is that you cannot debug inside it, cannot inspect why it reached a decision, and cannot easily reproduce a failure. Plan for that asymmetry: ask partners for task-level logs or trace exports, insist on structured artifacts you can validate, and keep your own records of every message sent and received.

Semantic interoperability is the hard part

Two agents can speak A2A perfectly and still fail to cooperate because their skills mean different things. A skill described as "book travel" might expect an approved budget code; another expects a traveller profile id. Teams handle this with structured data parts that follow agreed JSON schemas for important skills, examples in the card that pin down expected inputs, contract tests run against the partner's agent in a sandbox, and A2A's extension mechanism for domain-specific conventions. The protocol's natural-language skills are a starting point for discovery, not a contract.

Why three bindings

JSON-RPC came first and matches MCP's style; gRPC suits high-throughput internal service meshes; HTTP+JSON fits existing API gateways, caching and tooling. A2A 1.0 requires functional equivalence across them, with an error-code mapping table, so an organisation can pick the binding that fits its infrastructure. The practical advice: pick one binding per integration, test it, and do not assume a partner supports all three; the card lists exactly what it offers.

Observability across organisations

When a task spans your agent and a vendor's, a slow or wrong answer has two halves. Correlate them with ids: the task and context ids A2A provides, plus your own trace id passed in message metadata or request headers if both sides agree to carry it. Record every state transition with timestamps in your traces (ag14), so you can say "the vendor's agent sat in working for 14 minutes" rather than "the booking was slow". Agree on retention and redaction of exchanged content, because traces of cross-company messages contain both companies' data.

Registries and the discovery problem

The well-known URI solves "what does this domain's agent offer?" but not "which agent should I use for this?". Organisations with many agents build registries: a catalogue of cards with ownership, environment, version, data classification and access policy, searched by skill and tags. The Linux Foundation's announcement lists registry consolidation on A2A's roadmap. Until a standard exists, treat your registry as a governance tool: it is where you enforce who may call which agent, verify signatures, and alert when a card changes.

Agents calling agents calling agents

Delegation chains compound every problem: latency, cost, reliability, and especially authority. If your agent delegates to a vendor's agent, which delegates to a subcontractor's, the user's permissions should narrow at each hop, not widen. A2A's auth-required state propagates authorisation requests up the chain to a human, and token exchange with narrowing scopes (au12) keeps each hop's authority minimal. Set a maximum delegation depth in policy; unbounded delegation is how small errors become expensive incidents.

Comparing with plain APIs

Many "agent-to-agent" integrations would be better as ordinary APIs: deterministic endpoints with schemas, versioning, rate limits and service-level agreements. Use A2A when the remote side must interpret goals, ask clarifying questions, or plan multi-step work under its own control. If the remote work is always the same function, an API is cheaper, faster, easier to test and easier to trust, and your agent can still call it as an MCP tool.

Testing integrations you do not control

With an opaque remote agent, testing shifts to the boundary. Maintain a contract-test suite per partner skill: representative requests with expected artifact schemas and properties, clarifying-question paths (does it ask for the PO number when missing?), refusal paths (does it reject out-of-scope tasks?), and failure paths (duplicate messageIds, cancellation mid-task, expired credentials). Run it against the partner's sandbox on a schedule and whenever their card changes. Because the remote agent is a model, run each case several times and track pass rates rather than single outcomes (ag12); a partner upgrade that drops a skill's pass rate from 98% to 85% is an incident even if nothing else changed.

Failure modes in practice

Duplicate side effects. A retry without the same messageId, or an agent that ignores it, creates two bookings. Test duplicate handling explicitly with every partner.

Zombie tasks. Tasks left in working or input-required forever because nobody owned the timeout. Sweep for non-terminal tasks older than their deadline.

Card drift. A partner changes a skill's behaviour or required inputs without changing its description. Pin card versions, diff cards on refresh, and run contract tests.

Webhook abuse. Push-notification URLs pointing at internal addresses, or unauthenticated webhooks accepting forged updates. Validate URLs, authenticate deliveries, and deduplicate.

Cross-agent injection. A partner's agent relays instructions from content it read. Treat its output as untrusted and keep it away from contexts with private data and outbound tools.

Unnecessary agents. Internal "microagents" talking A2A to each other inside one product, each hop adding seconds and failure modes. Collapse them.

What to monitor

Per partner agent and skill: task volume, state distribution and time in each state, terminal outcome rates (completed, failed, rejected, canceled), time to first artifact, duplicate-send rate, cancellations that did not stop work, version negotiation errors, authentication failures, and validation failures on artifacts. Alert on rising input-required stalls and on any change to a partner's Agent Card.

Operational practices that pay off

Keep an integration runbook per partner: contacts, escalation path, how to disable the integration quickly, and how to reconcile tasks with the partner's own records after an outage. Store every message and artifact you exchange, with redaction, for at least as long as the business process needs to be auditable. Version your own A2A server's card carefully: add skills and fields compatibly, announce removals in advance, and keep the previous protocol version's interface available while clients migrate. And track cost: a remote agent's work is often billed per task, so a retry storm or a looping clarification can cost real money on both sides.

        if self.path == "/.well-known/agent-card.json": return self.reply(CARD)
        self.reply({"error": "not found"}, 404)
    def do_POST(self):
        if self.headers.get("A2A-Version", "0.3") != "1.0":
            return self.reply({"jsonrpc": "2.0", "id": None, "error": {"code": -32009, "message": "VersionNotSupported"}})
        req = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        p, rid = req.get("params", {}), req["id"]
        if req["method"] == "SendMessage":
            msg = p["message"]
            if msg["messageId"] in SEEN:                       # retry of the same message
                return self.reply({"jsonrpc": "2.0", "id": rid, "result": {"task": TASKS[SEEN[msg["messageId"]]]}})
            tid = msg.get("taskId") or str(uuid.uuid4())
            TASKS.setdefault(tid, {"id": tid, "contextId": str(uuid.uuid4()), "artifacts": []})
            TASKS[tid]["status"] = {"state": "TASK_STATE_WORKING"}
            SEEN[msg["messageId"]] = tid
            text = " ".join(part.get("text", "") for part in msg["parts"])
            threading.Thread(target=work, args=(tid, text), daemon=True).start()
            return self.reply({"jsonrpc": "2.0", "id": rid, "result": {"task": TASKS[tid]}})
        if req["method"] == "GetTask":
            return self.reply({"jsonrpc": "2.0", "id": rid, "result": TASKS[p["id"]]})
        if req["method"] == "CancelTask":
            TASKS[p["id"]]["status"] = {"state": "TASK_STATE_CANCELED"}
            return self.reply({"jsonrpc": "2.0", "id": rid, "result": TASKS[p["id"]]})
        self.reply({"jsonrpc": "2.0", "id": rid, "error": {"code": -32601, "message": "Method not found"}})

def call(method, params, version="1.0"):
    body = json.dumps({"jsonrpc": "2.0", "id": str(uuid.uuid4()), "method": method, "params": params}).encode()
    req = urllib.request.Request(CARD["supportedInterfaces"][0]["url"], body,
                                 {"Content-Type": "application/json", "A2A-Version": version})
    return json.loads(urllib.request.urlopen(req, timeout=5).read())

def wait(task_id, deadline_s=5):
    end = time.time() + deadline_s
    while time.time() < end:
        t = call("GetTask", {"id": task_id})["result"]
        if t["status"]["state"] not in ("TASK_STATE_SUBMITTED", "TASK_STATE_WORKING"):
            return t
        time.sleep(0.1)
    call("CancelTask", {"id": task_id}); raise TimeoutError(task_id)

Design: delegating to a supplier's agent

Your procurement agent must ask suppliers' agents to quote and then place orders. Three large suppliers expose A2A 1.0 agents; a dozen small ones only have REST APIs. Orders above $10,000 need a human approver. Design the integration: protocols, discovery, auth, failure handling and security.

Answer

Protocols. For the three A2A suppliers, delegate quoting and ordering as A2A tasks, because their agents negotiate (alternatives, delivery dates, clarifying questions). For the REST-only suppliers, wrap their APIs as MCP tools (or plain API clients); do not invent agents where a deterministic API exists.

Discovery and onboarding. Keep a registry of approved supplier agents: card URL, pinned version, verified JWS signature, allowed skills, data classes you may send. Refresh cards daily and alert on changes; run contract tests against each supplier's sandbox before enabling a new card version.

Auth. Use the security scheme each card declares, with credentials scoped to your organisation and to quoting versus ordering. For orders above $10,000, your side requires human approval before sending the order message; if a supplier's agent moves a task to auth-required (for example to confirm a credit check), route it to the approver, and never treat that state as approval by itself.

Failure handling. Every SendMessage carries a messageId stored with your purchase-order id; retries reuse it. Set deadlines per skill (quotes 10 minutes, orders 1 hour), then cancel and check the final state; reconcile orders against the supplier's order system, because a cancel may arrive after the order was placed. Use push notifications for orders, with authenticated, deduplicated webhook handling. Time out input-required stalls and escalate to a buyer.

Security. Send only what each task needs (no internal budgets or other suppliers' quotes). Validate quote artifacts against a schema; treat any free text from supplier agents as untrusted, never letting it choose your next tool call, and keep supplier output out of contexts that hold other suppliers' data. Log every message and state transition with your trace id for audit.
