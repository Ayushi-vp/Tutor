A team starts building an internal agent in early 2025 with the most popular framework of the moment. Six months later they are fighting it: the prompt the model actually receives is assembled somewhere inside the library and they cannot easily see it, a minor upgrade changed how tool errors are reported, and the multi-agent abstraction they adopted because it was there turned a two-tool assistant into four agents passing messages. They rewrite on a second framework. A year after that, the second framework's vendor announces a successor and puts the old one into maintenance mode. The team's actual logic, its tools, prompts and business rules, was never the problem; the scaffolding around it was.

The opposite story is just as common. A team writes its own loop because "it's only thirty lines", then spends a quarter adding checkpointing so long runs survive deploys, a way to pause for human approval and resume the next day, retries that do not double-charge customers, parallel tool calls, streaming to the UI and tracing that shows what happened in step 14 of a failed run. They have built a framework, with fewer users and less testing than the ones they avoided.

Senior interviews ask about this directly: "LangGraph or the OpenAI Agents SDK?", "would you use a framework at all?", "how do you avoid lock-in?". The interviewer is not looking for a favourite library. They want to hear what a framework actually provides, which of those things your system needs, what each choice costs, and how you would stay able to change your mind, because the landscape changes every few months.

This lesson separates what frameworks give you (the loop, state, tool schemas, memory, tracing, durability, human checkpoints, orchestration) from what they cost. It contrasts graph and state-machine designs with conversation-driven ones, surveys the frameworks that matter on 9 October 2026 with their versions verified on that day, sketches the same small refund agent in two of them, works through lock-in, and ends with the "just write the loop yourself" answer and when it is the right one. The lab is that hand-written loop, in the standard library, with a scripted fake model.

One more reason the question matters: the framework decision is often made in the first week of a project, by whoever writes the prototype, and then inherited by everyone who operates the system for years. Making it deliberately, with requirements written down and an exit plan, is one of the cheapest ways a senior engineer can save a team months later.

Web frameworks, again

Web developers have had this argument for twenty years. You can write a web service directly on the HTTP server interface, use a micro-framework that gives you routing and little else, or use a full framework with an object-relational mapper, authentication, admin pages and migrations. None is right in general. A tiny webhook receiver needs nothing; a large product with many developers benefits from conventions; a high-performance service may outgrow any framework's defaults. Agent frameworks are the same argument, a decade younger and moving much faster. The analogy breaks in one important way: web frameworks are mature, stable and well understood, while agent frameworks are a few years old, change their APIs often, and wrap a component (the model) whose behaviour they cannot fully control. That raises the value of understanding the code underneath.

What sits under any agent

Two ways to own control flow

The deepest difference between frameworks is who decides what happens next. In graph-based designs you draw the flow in code: a node that calls the model, a node that runs tools, a node that checks policy, edges between them, some conditional. The model makes decisions only where the graph lets it. In conversation-driven designs the model decides at every step which tool to call, whether to hand off to another agent, and when it is done; the code supplies tools and guardrails. Graphs are predictable, inspectable and easy to pause at known points; conversations are flexible and short to write. Most real systems mix them, as ag7 describes: a graph for the parts that must happen in order, with free-running agents inside some nodes.

What changes when a model is part of the runtime

Ordinary frameworks orchestrate deterministic code: the same input gives the same path. Agent frameworks orchestrate a component that is non-deterministic, slow, expensive and occasionally wrong. That changes what you want from them. You want to see exactly what the model was given, because most bugs are context bugs. You want to pause and resume, because steps can take minutes and humans may need to approve them. You want to replay and test with a fake model, because real model calls are costly and vary. And you want guardrails in code, because the model cannot be trusted to follow rules on its own. Judge every framework on those four needs before its feature list.

A sixty-second decision

When an interviewer asks "which framework?", a crisp answer runs: "First, do I need durability or human pauses? If yes, a graph framework or our existing workflow engine. If not, is it a single loop with a few tools? Then I write the loop or use a lightweight SDK. If the agent mostly works with files and code on one vendor's model, that vendor's harness is worth a look. In every case, tools, prompts and state stay in our code, and tracing goes to OpenTelemetry, so the choice is reversible." That answer shows you know what frameworks are for and that you plan for change.

A reader who stops here should remember: the loop is small, the hard parts are durability, human checkpoints and observability, and the most important design choice is who owns the control flow.

1. What a framework actually gives you

Strip any agent framework down and you find the loop from ag2: send the conversation and tool schemas to the model; if it returns tool calls, execute them and append the results; repeat until it returns a final answer or a budget runs out. 2. Graph and state-machine designs

In a graph framework, the run has a state (a typed object, often including the message list), and the program is a set of nodes that read and update that state and edges that say which node runs next. A conditional edge picks the next node by inspecting the state, for example "if the last model message contains tool calls, go to the tool node, otherwise end". A checkpointer saves the state after each step, which gives durability and makes interrupts possible: the graph pauses before a node, waits as long as needed for a human, and resumes from the saved state. LangGraph's StateGraph, Microsoft Agent Framework's workflows, Google ADK 2.0's Workflow runtime and CrewAI's Flows all follow this model with different vocabularies.

Graphs shine when the process has required steps (verify identity before changing an address), regulated checkpoints (approval above a threshold), parallel branches with a join, or long waits. They make behaviour inspectable: you can draw the graph and point to where a decision happens. Their cost is rigidity and boilerplate for open-ended tasks, where the "graph" degenerates into "model node, tool node, loop".

3. Conversation-driven designs

In a conversation-driven framework, an agent is a model plus instructions, tools and guardrails, and a runner executes the loop. Multi-agent behaviour comes from handoffs (another agent takes over the conversation) or agents as tools (one agent calls another and gets a result back, keeping control), as described in ag8. The OpenAI Agents SDK, the Claude Agent SDK and CrewAI's Crews work this way. They are concise and flexible: adding a capability means adding a tool or an agent, not redrawing a graph. Their cost is that control flow lives in the model's decisions, so guarantees ("always check the policy before refunding") must be enforced inside tools, guardrails or hooks rather than by the structure of the program.

The picture also explains why teams mix the two. The parts of a process that must happen, in order, with evidence (verify, approve, record) belong in a graph or workflow where they are guaranteed and auditable. The parts that need judgement (understanding a messy request, choosing which records to look at, drafting a reply) belong in a free-running agent inside a node, with its own tools and budget. Asking "which steps must be guaranteed?" before "which framework?" usually decides the architecture, and the framework choice follows from it. A useful test: if a compliance reviewer asked you to prove that a step always happens before another, could you point to code, or only to a prompt? If only to a prompt, that step belongs in the graph.

  • LangGraph (LangChain; 1.2.14). A graph framework for stateful, long-running agents: StateGraph, nodes and conditional edges, checkpointers for durable execution, interrupts for human-in-the-loop, short- and long-term memory, streaming, and integration with LangSmith for tracing, evaluation and deployment.   • OpenAI Agents SDK (openai-agents 0.23.1). 5. The same agent in two frameworks

Take a small agent: a support assistant with two tools, lookup_order(order_id) and issue_refund(order_id, amount), where refunds need human approval. Here is a sketch in each style. Treat these as sketches of the shape, written against the libraries' documented abstractions on the day of writing; check current signatures before running.

OpenAI Agents SDK (conversation-driven).

from agents import Agent, Runner, function_tool

@function_tool
def lookup_order(order_id: str) -> dict:
    """Return the order's total and status."""
    return orders_api.get(order_id)

@function_tool
def issue_refund(order_id: str, amount: float) -> dict:
    """Refund an order. Requires a human approval token."""
    if not approvals.is_approved(order_id, amount):        # policy enforced in code
        return {"status": "pending_approval", "ticket": approvals.request(order_id, amount)}
    return payments.refund(order_id, amount, idempotency_key=f"refund-{order_id}")

support = Agent(name="Support", tools=[lookup_order, issue_refund],
                instructions="Look up the order before refunding. Never refund more than the total.")
result = Runner.run_sync(support, "Please refund order A-100")
print(result.final_output)

The model decides to look up the order and then call the refund tool; the approval rule lives inside the tool, so it holds whatever the model does. A human approval that takes hours means the run ends with "pending approval" and a later run picks it up.

LangGraph (graph-based).

from langgraph.graph import StateGraph, MessagesState, START
from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.checkpoint.memory import InMemorySaver

tools = [lookup_order, issue_refund]                 # plain functions with docstrings
model = chat_model.bind_tools(tools)

def call_model(state: MessagesState):
    return {"messages": [model.invoke(state["messages"])]}

g = StateGraph(MessagesState)
g.add_node("model", call_model)
g.add_node("tools", ToolNode(tools))
g.add_edge(START, "model")
g.add_conditional_edges("model", tools_condition)   # to "tools" if tool calls, else end
g.add_edge("tools", "model")
app = g.compile(checkpointer=InMemorySaver(), interrupt_before=["tools"])

cfg = {"configurable": {"thread_id": "ticket-881"}}
app.invoke({"messages": [("user", "Please refund order A-100")]}, cfg)
# ... the run pauses before each tool step; a reviewer inspects the pending call, then:
app.invoke(None, cfg)                                 # resume from the checkpoint

Here the pause is structural: the graph stops before tool execution, the state is saved under a thread id, and a reviewer can inspect the pending tool call and resume (in production you would interrupt only before the refund, for example with a separate refund node or LangGraph's interrupt function, and use a durable checkpointer backed by a database instead of memory). Same tools, same prompt; the difference is where the approval lives and how a long pause is survived.

6. The loop you can write yourself

The lab contains a complete hand-written version of this agent in about 60 lines of standard-library Python: tool schemas derived from type hints and docstrings, a loop with a step budget, an approval gate for tools that need it, tool errors returned to the model instead of crashing, a trace entry per step, and an idempotent refund. Adding streaming, real retries and tracing to OpenTelemetry would roughly double it. Adding durable checkpoints and resumable human approval is where it gets substantial, unless you already run a workflow engine such as Temporal, in which case each model call and tool call becomes an activity and the engine provides durability, retries and timers.

7. What frameworks cost

Visibility. The most common complaint, and the one Anthropic's post leads with: abstraction layers obscure the prompts and responses. When the model misbehaves, you need to see exactly what it received: system prompt, tool schemas as serialised, message history after any trimming. If that assembly happens inside the library, find where and log it.

Churn. Agent frameworks are young. The OpenAI Agents SDK was at version 0.23 in October 2026, so semantic versioning permits breaking changes; others have reached 1.x or 2.x but change quickly; Microsoft replaced AutoGen with a new framework within two years. Pin versions, read changelogs, and budget for upgrades.

Defaults. Frameworks choose defaults you did not: retry policies, history trimming, tool error formats, and sometimes broad capabilities. The Claude Agent SDK, for example, gives the model Claude Code's full toolset by default, and its documentation shows using an allowed-tools list and permission modes to restrict it. Review every default against your security and cost requirements (ag9, ag10).

Weight. Dependencies, cold-start time and the number of stack frames between your code and the model call. Runtime overhead is usually small next to model latency, but debugging through deep abstraction stacks is not.

Lock-in. State and checkpoint formats, prompt templates embedded in library code, tracing that assumes a vendor platform, and patterns (crews, handoffs) that do not map one-to-one onto another framework.

8. Choosing

A short decision guide follows from all this:

  • Write the loop yourself when the agent is a single loop with a handful of tools and simple flow, when you need tight control over context and caching, when security review requires understanding every line, or when you already have a durable workflow engine to provide checkpoints and retries.
  • Use a graph framework (LangGraph, Microsoft Agent Framework workflows, ADK Workflows) when you need durable, resumable runs, human checkpoints at defined steps, parallel branches, or auditable flows.
  • Use a lightweight conversation framework (OpenAI Agents SDK, CrewAI Crews) when you want quick multi-agent conversations with handoffs and built-in tracing, and durability is not central.
  • Use a vendor harness (Claude Agent SDK) when you want that vendor's battle-tested tools and context management, for example a coding or file-working agent built on Claude.

Whatever you choose, keep the layer that is always yours portable: tools as plain functions or MCP servers with their own authorisation, prompts in your repository, business state in your database, tracing on OpenTelemetry, and a thin adapter between them and the framework.

9. Evaluating a framework in a two-week spike

Framework comparisons online measure features; your decision should measure fit. A practical spike takes two engineers about two weeks. Start by writing down requirements in priority order: languages, model providers, durability and resume, human-in-the-loop, parallelism, streaming, tracing back end, deployment target, security constraints (sandboxing, secrets, data residency), and team familiarity. Pick two or three candidates plus a hand-written baseline. Build the same representative agent in each: real tools against staging systems, one approval step, one deliberate failure (a tool timeout, a crash mid-run), streaming to a simple UI and traces to your collector.

Then score what matters in practice. How many lines did each take, and how many of them are yours versus glue? Can you print the exact request sent to the model at every step without reading library source? What happens when you kill the process mid-run and restart it: does it resume, does it repeat a side effect? How easy is it to swap the real model for a scripted fake in a unit test? Do traces arrive in your collector with prompts, tool arguments, token counts and latencies, redacted as required? How often has the library made breaking changes in the past year, who governs it, and what licence does it use? Finally, write down the exit plan for the winner: what you would rewrite to leave it. The candidate with the best fit and the cheapest exit usually wins over the one with the longest feature list.

10. Frameworks and the infrastructure you already have

Many companies already run infrastructure that overlaps with agent frameworks. A durable workflow engine (Temporal, cloud step functions, or an in-house job system) already provides checkpoints, retries, timers and human-task queues: an agent can be a workflow whose activities are model calls and tool calls, with the loop in workflow code. An API gateway already provides authentication, rate limits and logging for tools. An observability stack already collects traces. In that setting, a heavy agent framework duplicates what you have and creates two places to look when something fails. The lighter choice, a hand-written loop or a lightweight SDK used only for its model and tool abstractions, plugged into the existing workflow engine and observability, is often better. Conversely, a team without such infrastructure gets the most from a full framework, because it supplies durability and tooling they would otherwise build.

Durability semantics differ, and they matter

"Durable" can mean different things. Graph frameworks typically checkpoint state at step boundaries: after each node (or each super-step of parallel nodes) the state is written to the checkpointer, and resume restarts from the last saved step. Workflow engines such as Temporal record an event history of every activity call and result, and replay the workflow code deterministically on recovery, which is stronger but requires deterministic orchestration code. In both, the external world is not rolled back: a tool call that completed just before a crash may run again on resume. Know your framework's checkpoint boundary, put side effects in their own steps, and make them idempotent.

State schema evolution

Long-running agents keep state for hours or days. When you deploy a new version whose state type has a new field or a renamed node, in-flight runs must still load. Graph frameworks persist state in their own formats; plan migrations as you would for a database: add fields with defaults, keep old node names working until runs drain, and test resuming old checkpoints with new code.

Testing agents built on frameworks

Agents are hard to test because the model is non-deterministic and expensive. Every framework worth using should let you replace the model with a scripted fake (as the lab does) so you can test control flow, tool wiring, approvals, error handling and budgets deterministically and cheaply, then run model-in-the-loop evaluations separately (ag12). If a framework makes faking the model awkward, that is a real cost.

Tracing and the OpenTelemetry question

Most frameworks ship tracing, but often to their own platform first (LangSmith, OpenAI's tracing dashboard, vendor consoles). For production you usually want traces in your existing observability stack, following the OpenTelemetry GenAI semantic conventions (ag14), so that agent spans sit next to database and HTTP spans. Check whether the framework exports OpenTelemetry natively or through an integration, and whether it records the exact prompts and tool arguments you need, with redaction.

Parallelism and concurrency

Parallel tool calls and parallel branches cut latency (ae10), but frameworks differ in how they run them: threads, async tasks, separate processes. Shared state updated by parallel branches needs merge rules (LangGraph uses reducer functions on state fields), and parallel side effects need the same idempotency care as serial ones. A hand-written loop can run independent tool calls concurrently with a thread or async pool in a few lines, which is often all you need.

Where the frameworks are converging

By late 2026 the major frameworks look more alike than they did in 2024: most combine free-running agents with some graph or workflow layer, most can use MCP servers as tools, several speak A2A, most offer checkpointing and human-in-the-loop in some form, and most trace to OpenTelemetry or can be made to. The differences that remain are in defaults, ergonomics, ecosystem integration and how much they hide. That convergence is another reason to invest in your own portable layer rather than in a framework's particular idioms.

Context management is the real product

LangChain's reply to Anthropic makes a point worth taking seriously: the hardest part of a reliable agent is controlling what goes into the model's context at each step: which history to keep, how to summarise it, which tool results to include and how to format them, what instructions to repeat (ag5). A framework that hides this is a liability; one that gives you explicit, inspectable control over it is valuable. When evaluating, look specifically at how history is trimmed or compacted, whether you can intercept and edit the message list before every model call, how tool results are serialised, and whether system prompts or tool descriptions are injected by the library without your knowledge.

Language and runtime fit

Frameworks are not equally available everywhere. Python has the widest choice; TypeScript has strong options (LangGraph.js, the OpenAI and Claude SDKs, Mastra and others); .NET teams have Microsoft Agent Framework; Java and Go have fewer mature options, though A2A and MCP SDKs exist in those languages. If your services and your team live in one language, a framework in another adds a deployment and skills boundary. Sometimes the right answer is a small agent service in Python behind an API for the rest of the system; sometimes it is a hand-written loop in the language you already run, using the model provider's SDK directly.

Team scale changes the answer

A single engineer can keep a hand-written loop coherent. Ten teams building fifty agents cannot, unless there is a shared internal platform. At that scale, organisations either adopt one framework as a standard, with internal libraries for tools, tracing and approvals on top, or build a thin internal agent platform (hd7) with its own loop, tool registry, policy engine and observability, using frameworks only where they add something. Either way, the shared layer is the asset; the framework underneath is replaceable. Interviewers asking about frameworks at a large company are often really asking how you would design that shared layer.

The public case: "Building effective agents" and its reply

In December 2024 Anthropic published "Building effective agents", distilled from its work with teams building agents across industries. It drew the distinction this track uses: workflows, where LLMs and tools are orchestrated through predefined code paths, and agents, where LLMs dynamically direct their own processes and tool usage. On frameworks it was direct: it suggested developers start by using LLM APIs directly, because many patterns can be implemented in a few lines of code; warned that frameworks often create extra layers of abstraction that can obscure the underlying prompts and responses, making them harder to debug, and make it tempting to add complexity when a simpler setup would suffice; and advised that if you use one, you ensure you understand the underlying code. The page now notes that the tooling landscape has changed since, and names frameworks including Anthropic's own Claude Agent SDK and AWS's Strands Agents. LangChain answered in "How to think about agent frameworks", arguing that the hard part of production agents is reliably controlling what goes into the model's context, and that the value of a framework lies in durable execution, human-in-the-loop, memory and observability that teams otherwise rebuild. The two essays together are the best short framing of the debate: start simple and stay close to the prompts; adopt a framework for the infrastructure you genuinely need, and make sure it lets you see and control the context.

Failure modes in production

Upgrade breakage. A minor version changes how tool errors or message history are formatted; quality drops without a code change on your side. Pin versions and run your evaluation suite on every upgrade.

Invisible context. The model behaves strangely and nobody can say what it saw, because history trimming or prompt assembly happens inside the library. Log the final request payload for every model call, with redaction.

Replayed side effects. Resume after a crash repeats a payment or an email. Idempotency keys and side-effect nodes with clear checkpoint boundaries prevent it.

Checkpoint growth. Checkpointers store full state at every step; long-running threads accumulate gigabytes. Set retention, compact old checkpoints and store large artifacts by reference.

Permission defaults. An agent built on a vendor harness can read, write or execute more than intended because nobody restricted its tool list. Review defaults in security review.

Accidental multi-agent. Because the framework makes it easy, a single-agent task is split into several agents, multiplying cost and latency (ag8). Justify every extra agent.

Migrating between frameworks

Migrations happen: Microsoft's guides for moving from AutoGen and Semantic Kernel to Agent Framework exist because many teams need them. A migration goes smoothly when tools, prompts and state already live outside the framework: you rewrite the orchestration and adapters, re-run your evaluation suite, compare traces, and switch traffic gradually. It goes badly when business logic lives in framework callbacks and state lives only in a proprietary checkpoint format.

A worked migration plan

Suppose a team must move a production agent from a framework entering maintenance mode to its successor. Week one: inventory what the agent depends on (tools, prompts, state formats, tracing, deployment) and write a parity checklist. Week two: extract tools and prompts into framework-neutral modules if they are not already, behind the existing framework, and ship that refactor alone. Weeks three and four: rebuild orchestration on the new framework using the same tools and prompts; run the evaluation suite on both and compare traces case by case. Week five: shadow the new version on live traffic (both run, only the old one acts), then canary a small percentage with monitoring on success rate, cost per task, latency and escalations. Keep the old version deployable until in-flight long-running runs have drained, because their checkpoints are in the old format. The refactor in week two is what makes the rest predictable, and it is also the step that would have made the migration unnecessary to fear in the first place.

Goal: write the agent loop yourself, with tool schemas derived from code, an approval gate, a step budget, error handling, a trace and an idempotent side effect, using a scripted fake model so it runs offline. About 10 minutes, Python 3.12 standard library only.

import inspect, json, time

# --- tools: plain functions; the schema is derived from type hints -------------------------
ORDERS = {"A-100": {"total": 42.0, "status": "delivered", "refunded": False}}

def lookup_order(order_id: str) -> dict:
    """Return the order's total and status."""
    return ORDERS.get(order_id, {"error": "not found"})

def issue_refund(order_id: str, amount: float) -> dict:
    """Refund part or all of an order. Needs human approval."""
    o = ORDERS[order_id]
    if o["refunded"]:
        return {"error": "already refunded"}            # idempotent side effect
    o["refunded"] = True
    return {"refunded": amount}

TOOLS = {f.__name__: f for f in (lookup_order, issue_refund)}
NEEDS_APPROVAL = {"issue_refund"}
PY2JSON = {str: "string", float: "number", int: "integer", bool: "boolean"}

def schema(f):
    params = inspect.signature(f).parameters
    return {"name": f.__name__, "description": inspect.getdoc(f),
            "input_schema": {"type": "object", "required": list(params),
                             "properties": {n: {"type": PY2JSON[p.annotation]} for n, p in params.items()}}}

# --- a scripted fake model so the lab runs offline ----------------------------------------
SCRIPT = [
    {"tool": "lookup_order", "args": {"order_id": "A-100"}},
    {"tool": "issue_refund", "args": {"order_id": "A-100", "amount": 42.0}},
    {"text": None},                                  # final answer, written from the last result
]
def fake_model(messages, tools):
    turn = sum(1 for m in messages if m["role"] == "assistant")
    step = SCRIPT[min(turn, len(SCRIPT) - 1)]
    if "text" in step:
        last = messages[-1]["content"]
        return {"text": f"Could not refund: {last['error']}." if "error" in last
                        else f"Refunded ${last['refunded']:.2f} for order A-100."}
    return step

# --- the loop: this is what a framework wraps ---------------------------------------------
def run(user_msg, model=fake_model, approve=lambda name, args: True, max_steps=6):
    messages, trace = [{"role": "user", "content": user_msg}], []
    tool_specs = [schema(f) for f in TOOLS.values()]
    for step in range(max_steps):
        t0 = time.perf_counter()
        out = model(messages, tool_specs)
        messages.append({"role": "assistant", "content": out})
        if "text" in out:                                         # final answer
            trace.append({"step": step, "final": out["text"]})
            return out["text"], trace
        name, args = out["tool"], out["args"]
        if name not in TOOLS:
            result = {"error": f"unknown tool {name}"}
        elif name in NEEDS_APPROVAL and not approve(name, args):
            result = {"error": "denied by human"}
        else:
            try:
                result = TOOLS[name](**args)
            except Exception as e:                                # tool errors go back to the model
                result = {"error": repr(e)}
        messages.append({"role": "tool", "name": name, "content": result})
        trace.append({"step": step, "tool": name, "args": args, "result": json.loads(json.dumps(result)),
                      "ms": round((time.perf_counter() - t0) * 1000, 2)})
    return "Stopped: step budget exhausted.", trace

print(json.dumps(schema(issue_refund), indent=1))
answer, trace = run("Please refund order A-100", approve=lambda n, a: a["amount"] <= 50)
print(answer)
for t in trace:
    print(t)
answer, _ = run("Refund it again")                               # second run: idempotency
print(answer, ORDERS["A-100"])

What to look for. The printed schema for issue_refund was built from the function's type hints and docstring, which is what frameworks do when you decorate a function as a tool. The first run looks up the order, passes the approval check (the amount is at most $50), refunds and answers; the trace has one entry per step with the tool, arguments, a snapshot of the result and timing. Note that the trace stores a copy of each result: an earlier version of this lab stored the live dictionary, and the first step's trace later showed the order as already refunded, a small example of why traces must snapshot data. The second run shows idempotency: the tool refuses a second refund and the final answer reports it rather than claiming success. Now change the approval rule to a["amount"] <= 20 and see the denial flow back to the model; set max_steps=1 to see the budget stop the run. Each of these is a feature frameworks advertise; together they are about 60 lines.

Choose a framework, or not

Your team is building three agents: (1) an internal assistant that answers questions about company policy using a search tool, single turn; (2) an onboarding agent that runs over several days, provisions accounts in five systems, waits for a manager's approval at two points, and must survive deploys; (3) a coding agent that edits repositories and runs tests in a sandbox. The company standard is Python, traces go to an OpenTelemetry collector, and you use more than one model provider. Recommend an approach for each.

Answer

(1) Policy assistant: write the loop. One model, one or two tools, single turn: a hand-written loop with tool schemas from functions, a step budget, OpenTelemetry spans and prompt caching is a few hundred lines you fully control. A lightweight SDK would also work, but adds little.

(2) Onboarding agent: graph framework or workflow engine. Multi-day runs, two human approvals and survival across deploys are exactly what durable checkpoints and interrupts provide. Use LangGraph or Microsoft Agent Framework workflows with a database-backed checkpointer, or, if the company already runs Temporal, model each provisioning step as an activity and call the model from activities. Make every provisioning call idempotent and put each in its own step; test resuming old checkpoints after a deploy; export traces to the collector.

(3) Coding agent: vendor harness or a lightweight SDK with sandboxing. File editing, shell and test running are hard to get right; the Claude Agent SDK provides Claude Code's tools, permissions and hooks if Claude is the model, with the tool list restricted and execution inside a sandbox (ag9); with other providers, the OpenAI Agents SDK's sandbox agents or a hand-written loop over a sandbox API. Because the company uses multiple providers, keep the coding agent's tools behind your own interfaces so the model or harness can be swapped.

Across all three: tools as plain functions or MCP servers with their own authorisation, prompts in the repository, business state in your database, OpenTelemetry tracing, pinned framework versions, and an evaluation suite that runs on every upgrade.
