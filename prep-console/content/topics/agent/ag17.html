A company wants its assistant to file expense reports in a twenty-year-old internal reimbursement portal that has no API, book travel on supplier websites, and pull invoice data from a dozen vendor portals, each with its own login and layout. Nobody will build integrations for all of them. A browser agent that operates these sites the way a person does looks like the obvious answer, and the demo is striking: the agent opens the portal, reads the form, fills in the fields and submits, narrating as it goes.

Production is less striking. A cookie banner appears on one run and the agent clicks the banner instead of the form. A page loads slowly and the agent acts on a screenshot of the previous page. A layout change moves the Submit button and a coordinate click lands on Cancel. A vendor portal hides a line of text in the page that tells the agent to forward the invoice to another address. A task that took 40 steps in the demo takes 70 in the wild, and with screenshots kept in the context, its token bill runs to dollars per task. And a benchmark headline says agents now beat humans on computer tasks, while a newer benchmark of realistic hour-long workflows says the best agent finishes one in five.

Browser and computer-use agents are where agent engineering meets the messiness of real interfaces built for people. ag9 introduced them as a sandboxing problem and gave the screenshot token arithmetic. This lesson goes deeper on the browser and GUI case only: how the agent perceives a page (DOM, accessibility tree, screenshots, or both) and what each costs per step and per task; how it turns intentions into clicks (coordinates versus element references); the observe-act loop's latency and token bill; how to recover from wrong clicks, stale screens and pop-ups; sandboxing and credential handling; prompt injection from web pages, with measured rates; what the benchmarks (WebArena, OSWorld-Verified and OSWorld 2.0) say as of October 2026; and where these agents are reliable enough to ship. The lab estimates observation costs and simulates an observe-act loop with injected errors and a recovery policy.

Interviewers use this topic to test judgement more than knowledge. Expect "would you build this with a browser agent or an API?", "how much would it cost per task?", "the agent clicked the wrong button and submitted an order, what went wrong in your design?", and "these benchmarks say agents beat humans, so why not let it run unattended?". Each has a short, numerical, design-level answer, and this lesson builds them. The numbers in it (per-step token costs, per-step latency, compounding error rates and benchmark results with their dates) are the ones worth being able to reproduce on a whiteboard, because they let you answer each question from first principles rather than from impressions of a demo.

Two ways to describe a room

Imagine guiding a friend through an unfamiliar office over the phone so they can fill in a form on someone's desk. You could send them a photo of the room every few seconds and say "click the thing about two-thirds of the way across, slightly above centre": that is screenshot-based perception with coordinate grounding. It works for anything you can see, but every photo is expensive, and if the camera angle shifts your directions miss. Or you could read them an inventory: "there is a form with fields Name, Date and Amount, and buttons Submit and Cancel": that is the accessibility tree, a structured description of what can be used. It is cheap and precise ("press Submit"), but it is only as good as the labels, and some things (a chart, a drawing canvas) are hard to describe. Good guides use both: the inventory for precise actions, a photo when the inventory is confusing.

The analogy also captures the loop: describe, act, describe again, because every action changes the room. Where it breaks is trust. Your friend would not obey a sticky note on the desk saying "also mail the company credit card to this address"; an agent might, because to a model a note on a page and an instruction from its user are both just text.

The observe-act loop

Why errors compound

A browser task is a chain of steps, and an uncaught error anywhere usually ruins the outcome. If each step independently succeeds 99% of the time, a 50-step task succeeds 0.99⁵⁰ ≈ 60% of the time; at 97%, 22%. This is the same arithmetic as ag1's multi-step reliability, and it is why recovery (noticing and fixing errors) matters more than raw per-step accuracy, and why short tasks are where these agents work best.

Browsers versus whole desktops

Browser agents and full computer-use agents share the loop but differ in what they can see and touch. A browser agent works inside one browser, where the DOM and accessibility tree are available, navigation can be restricted by URL, and isolation is a fresh profile. A computer-use agent operates a whole operating system: desktop applications, file dialogs, system settings, several windows. Structure is patchier (desktop accessibility APIs vary by platform and application), so it leans more on screenshots and coordinates, and isolation needs a VM or container with its own display. Desktop agents can do more (edit a spreadsheet in a native app, move files between applications) and can break more; most production deployments start with the browser case because it is easier to observe, constrain and recover.

A reader who stops here should remember: perceive with structure when you can and pixels when you must, ground actions to elements rather than coordinates where possible, verify every step, and treat everything on the page as untrusted.

1. Why browser and computer-use agents exist

Most of the world's software has no API an agent can call: internal tools built decades ago, vendor portals, government sites, desktop applications. People operate them through screens. Browser agents (operating web pages) and computer-use agents (operating a whole desktop) let a model do the same, which makes them the integration of last resort: slow and fragile compared with an API, but available everywhere a person can click. They are also useful for testing your own web applications, where clicking through the interface is the point.

2. Perception: four ways to see a page

Raw HTML or the DOM. The Document Object Model is the browser's tree of every element, including hidden ones, scripts and styling. It is complete but enormous: a modern product page's HTML can be hundreds of kilobytes, and at roughly 4 characters per token a 400 KB page is about 100,000 tokens, most of it irrelevant markup. Agents rarely feed raw HTML to the model; they extract from it.

The accessibility tree. Browsers build a parallel tree for assistive technology such as screen readers: each element with a role (button, link, textbox, heading), an accessible name ("Checkout", "Email address") and states (checked, disabled, expanded). It strips layout and styling, so it is far smaller: if a page has 600 relevant nodes at about 48 characters each, that is about 7,200 tokens. Its quality depends on the page's accessibility markup: well-built sites expose clean names; canvas-based apps, custom widgets and careless markup expose little.

Interactive elements only. Filtering the tree to things that can be clicked or typed into (links, buttons, inputs, selects) with their names and short context gives the cheapest structured view: 120 elements at about 40 characters is about 1,200 tokens. It suits navigation and form filling, but loses the page's content, so the agent may need to request text separately.

Screenshots. An image of the viewport shows exactly what a person sees, including images, charts, canvas apps and visual cues such as which field is highlighted. As ag9 computed, at one visual token per 28×28-pixel patch a 1280×800 screenshot is 46 × 29 = 1,334 tokens. Screenshots work on any application, including desktop software with no accessibility tree, but give the model nothing to target except coordinates, and show only what is in the viewport.

Hybrid. Many strong agents combine a structured view for precise targeting with a screenshot for visual context, or use the tree by default and fall back to screenshots when the tree is poor. Microsoft's Playwright MCP server, for example, operates through structured accessibility snapshots by default, describing itself as using the accessibility tree rather than pixel-based input, with vision available as an optional capability.

4. Action grounding: coordinates or element references

Grounding is turning "click the Checkout button" into a concrete operation. With coordinates, the model outputs a pixel position on the screenshot and the harness moves the mouse there. This works for anything visible, including desktop apps and canvases, but has failure modes that are easy to miss: the screenshot sent to the model may be scaled (a 2560×1600 display sent at 1280×800 means every coordinate must be doubled, and an off-by-scale bug makes every click land up and to the left), the page may scroll between observation and action, and a layout shift (an image loading above the button) moves the target. Errors are silent: a click on empty space or the wrong button produces no error, just a wrong state.

With element references, the structured snapshot gives each element an identifier, and the model says "click ref 47"; the harness resolves the reference to the actual element at action time, wherever it now is, and can report an error if it no longer exists. This is precise, robust to scrolling and layout shifts, and makes failures visible. It depends on a usable DOM or accessibility tree.

Set-of-Mark prompting (Yang et al., 2023) bridges the two: the harness overlays numbered boxes on interactive regions of the screenshot, and the model answers with a number, which the harness maps back to an element or a box centre. It gives a vision model the precision of references while keeping the visual context. Specialised grounding models (several appear on the OSWorld leaderboard as "specialized models") are trained specifically to map instructions to screen locations, and some agents use them as a separate component: a large model plans the action in words, a grounding model finds the target.

5. The loop's latency

Each step costs an observation (capturing a screenshot or snapshot, tens to hundreds of milliseconds), a model call (time to first token plus a short output, often one to several seconds with a large model, more with extended reasoning), executing the action, and waiting for the page to settle (network requests, rendering; from milliseconds to seconds). Three to eight seconds per step is typical, so a 30-step task takes two to four minutes, and long tasks much longer. That rules browser agents out of interactive request-response flows; they are background jobs with progress updates. Levers: fewer, higher-level actions (one "fill form with these values" instead of eight field-by-field steps), smaller observations, a faster model for routine steps with escalation to a stronger one for decisions, and parallel independent tasks in separate sandboxes.

6. Recovering from errors

The characteristic errors are known, and so are the recoveries:

  • Stale observations. The screenshot was taken before the page finished loading, so the agent acts on an old view. Recovery: wait for stability (no pending network requests, no layout changes for a short interval, or a specific element present) before observing.
  • Interruptions. Cookie banners, newsletter modals, chat widgets, permission prompts cover the page. Recovery: detect and dismiss them with known patterns before acting; treat persistent blockers as a reason to stop and ask.
  • Misclicks. The action landed on the wrong element. Recovery: verify after each action that the expected change happened (URL changed, field contains the typed value, the expected element appeared), and if not, backtrack (browser back, close dialog, clear field) and retry, possibly with a different grounding method.
  • Navigation dead ends. The target is in a menu, below the fold or on another page. Recovery: scroll, open menus, use the site's search, and keep a short record of where it has been to avoid loops.
  • Lost constraints. Over many steps the agent forgets a requirement ("refundable fares only"). Recovery: keep task constraints in a structured state that is re-shown every step, not only in the original message, and check them before committing.
  • Irreversible steps. Submitting, paying, sending, deleting. Recovery is impossible after the fact, so checkpoint before them and require confirmation.

The lab simulates a 12-step task with per-step probabilities of a stale view (10%), a pop-up (5%) and a misclick (8%). A naive loop that never checks finishes 4.5% of the time, matching 0.77¹² ≈ 4.3%. Verifying after each action raises success to 54%: misclicks and stale views are now caught, but undismissed pop-ups still block it. Adding pop-up handling gives 100% at about 17 steps instead of 12; adding stability waits gets the same success in fewer steps (15.7), because waiting costs less than misclicking and recovering. Real error rates differ, but the shape is general: recovery behaviours, not per-step accuracy, decide whether long tasks finish.

7. Sandboxing and credentials

ag9 covered the isolation spectrum; for browsers, the specifics are these. Run each task in a fresh, isolated browser profile (or a VM for full computer use), so no cookies, saved passwords or sessions from other tasks or from the user's own browsing are available. Restrict navigation to an allowlist of domains for the task. Block or quarantine downloads, and do not let the agent install extensions. Credentials live in a vault; when a login form appears, the harness fills the fields directly from the vault, so usernames, passwords and card numbers never appear in the model's context or logs. Two-factor prompts and CAPTCHAs go to a human through a takeover flow; agents should not try to defeat CAPTCHAs, which exist precisely to stop automated access and whose circumvention can break sites' terms. When the task ends, log out and destroy the profile. These controls also limit the damage of the next section.

8. Prompt injection from web pages

A browser agent reads untrusted content on every step, so injection (ag10, ae13) is its central security problem. Pages can carry instructions in visible text, in text hidden from people but present in the DOM or accessibility tree (hidden form fields, off-screen elements, aria-labels, white-on-white text), in URLs and page titles, and in images that contain text. Anthropic's August 2025 report on piloting a Chrome extension agent is the best public measurement: across 123 test cases representing 29 attack scenarios, browser use without its safety mitigations had a 23.6% attack success rate, reduced to 11.2% with mitigations, and on a set of four browser-specific attack types (such as hidden form fields and injections through URL text and tab titles) the mitigations cut success from 35.7% to 0%. The mitigations it described were site-level permissions the user can grant or revoke, asking the user before high-risk actions such as publishing, purchasing or sharing personal data, and blocking certain high-risk site categories.

The lesson matches ae13's: filtering reduces attacks, but the residual rate is far from zero, so bound what a fooled agent can do. Keep sessions for unrelated sites out of the profile, so an injection on a shopping page cannot reach your email. Require confirmation, generated from page state by code rather than described by the model, before consequential actions. Do not let page content trigger actions outside the task's domains. And log enough (observations and actions) to investigate afterwards.

9. Benchmarks, as of 9 October 2026

WebArena (Zhou et al., 2023) runs agents on 812 tasks across self-hosted copies of realistic websites (an e-commerce store, a forum, a code-hosting site, a content-management system, maps) and checks functional correctness of the end state. At publication the best GPT-4-based agent succeeded on 14.41% against 78.24% for humans. Many variants followed (visual, enterprise and verified editions), and reported scores have risen steeply; because official and third-party leaderboards differ in protocol, quote current numbers only from the leaderboard you are comparing against.

OSWorld (Xie et al., 2024) runs 369 tasks on real operating systems (Ubuntu, Windows, macOS) with applications such as browsers, office suites, image editors and code editors, checked by execution-based scripts. Humans succeeded on 72.36%; the best model of the time on 12.24%, struggling mainly with GUI grounding and operational knowledge. In July 2025 the authors revised it as OSWorld-Verified, fixing community-reported task problems and re-running results under unified settings. In its official results table, by August 2026 the best entry was an agentic framework at 90.19% (Intelligence-Indeed Agent, July 2026) and the best general model was Claude Fable 5 at 85.96% (August 2026), both at a 100-step limit, above the original human baseline. Read that as the benchmark saturating: short, well-specified tasks with a step budget are largely solved by the best systems.

OSWorld 2.0 (June 2026), from the same group, is a deliberate response: 108 long-horizon workflows on 31 self-hosted websites and applications, grounded in realistic artefacts and user data, each taking people a median of about 1.6 hours and requiring an average of 318 tool calls for a frontier model, compared with about 30 in OSWorld 1.0. Under its primary binary metric at 500 steps, the best system (Claude Opus 4.8 with maximum thinking and batched tool calls) completed only 20.6% of tasks, with a 54.8% partial score; GPT-5.5 was far more token-efficient but plateaued near 14%. The authors report that agents rarely fail at basic GUI control any more; they lose track of constraints, miss information that arrives mid-task, guess rather than ask the user, and skip verification.

10. Where they are reliable enough to ship

Put the arithmetic, the benchmarks and the security picture together and a practical boundary appears. Browser and computer-use agents are ready, with the controls in this lesson, for: short, bounded tasks on known sites (tens of steps, not hundreds); tasks whose results are reviewed before they matter (filling a form that a person submits, drafting an order a person confirms); read-only work (extracting data from portals without APIs, research and comparison); internal legacy tools operated under supervision; and automated testing of your own web applications, where flakiness is visible and cheap. They are not ready to run long, open-ended workflows with irreversible steps unattended, which is exactly what OSWorld 2.0 measures, nor to hold broad credentials in sessions exposed to arbitrary web content. And wherever an API exists, an API call beats them on every axis.

11. One task, step by step

Trace a short real-world task: "download last month's invoice from the vendor portal". With an accessibility-tree observation of about 3,000 tokens on this simple site, a 4,000-token prefix and history trimming to the last three observations, each step sends roughly 10,000 to 14,000 input tokens.

  1. Navigate to the portal's login page (high-level action; the harness loads the URL from the task's allowlist). Wait for stability; observe.
  2. The tree shows username and password fields and a Sign in button. The model asks to log in; the harness fills both fields from the vault and clicks Sign in, so the credentials never appear in the context.
  3. A cookie banner covers the dashboard. The harness's banner handler dismisses it before the next observation.
  4. The model clicks "Billing" by element reference; verification confirms the URL changed to the billing page.
  5. The model selects last month in a date filter; verification reads back the filter's value.
  6. The model clicks the download link for the invoice; verification confirms a PDF arrived in the sandbox's download folder with a plausible size.
  7. The model reports completion; the harness checks the file exists, is a PDF and contains the expected invoice month before marking the task done.

Seven steps, around 80,000 input tokens and perhaps 40 seconds. Notice that most reliability came from the harness: the vault login, the banner handler, the verification after each action and the final outcome check. The model's job was to choose among a handful of clearly named elements. That is the pattern for agents that work: let deterministic code do everything it can, and ask the model only for the decisions that need judgement.

Designing the action space

The set of actions the model can take shapes reliability as much as the model does. Low-level actions (click at x, y; type text; press key) are universal but make every task long. Higher-level actions (fill this form with these values; select this option; go to this URL; extract this table) shorten tasks and move precise work into deterministic code, but must be implemented and maintained per interaction type. Most production browser agents mix them: high-level actions where structure is available, low-level ones as a fallback. Fewer steps means fewer chances to err and a smaller token bill.

Accessibility quality varies, so plan for fallbacks

A structured view is only as good as the page's markup. Well-built sites expose clear roles and names; single-page apps with custom components, canvas-rendered tools (diagram editors, maps, games) and pages built without accessibility in mind expose little or misleading structure. Detect when the tree is poor (few named interactive elements, unlabeled buttons) and switch to screenshot grounding for that page. As a side benefit, improving your own site's accessibility makes it easier for agents to use, the same way it helps people using screen readers.

Coordinate systems are a classic bug

Coordinate grounding involves at least three coordinate systems: the physical screen (with a device pixel ratio, often 2 on high-density displays), the CSS-pixel viewport, and the image sent to the model (often downscaled to fit token limits). A click must be transformed back from model-image coordinates to screen coordinates, accounting for scaling and scroll offset at the moment of the click. Getting this wrong produces agents that are "almost right" everywhere, which is worse than a clear failure. Test grounding with known targets at several resolutions and scroll positions.

Keeping long tasks on track

OSWorld 2.0's failure analysis points away from clicking and toward task management: lost constraints, missed mid-task information, guessing instead of asking, skipped verification. The countermeasures are the long-horizon practices of ag5 and ag11: a structured task state (goal, constraints, decisions made, open questions) kept outside the transcript and shown every step; explicit checkpoints where the agent re-reads constraints and verifies progress; a rule to ask the user when information is ambiguous rather than guess; and verification steps before declaring success (re-open the record, check the submitted values). These cost steps but are what separate a 20% agent from a usable one.

Reading leaderboards carefully

Computer-use results depend heavily on protocol: the step limit (OSWorld-Verified reports 15, 50 and 100 steps), whether the accessibility tree is provided in addition to screenshots, whether coding-based actions are allowed, whether multiple rollouts are taken, the scaffold around the model, and which task subset was run (OSWorld-Verified allows excluding 8 tasks with network dependencies). The official OSWorld-Verified table records these columns for exactly this reason. Compare systems only under matching settings, and prefer evaluations on your own tasks (ag12) for decisions.

Anti-bot measures and terms of service

Many sites detect and block automated browsing, rate-limit it, or prohibit it in their terms. A browser agent that works today may be blocked tomorrow, and circumventing protections can create legal and reputational risk. For production use on third-party sites, check terms, identify your agent honestly where possible, respect rate limits, and prefer official APIs or partnerships when volume grows. For your own sites, consider offering agent-friendly interfaces (APIs, MCP servers, or A2A agents, ag15) rather than forcing agents through the UI.

Routing models inside the loop

Not every step needs the strongest model. Many steps are routine (dismiss a banner, click the clearly named next button, scroll), while a few are decisions (which fare satisfies the constraints, whether a discrepancy needs the user). A common optimisation runs routine steps on a smaller, faster model or a specialised grounding model and escalates to a large reasoning model for decisions, verification and recovery after failures. It cuts latency and cost substantially, at the price of a router that must recognise which steps are hard; misrouting a decision to the small model is how constraints get lost. Evaluate the routed system end to end, not the components separately.

Evaluating your own browser agent

Public benchmarks are a starting point, not an acceptance test. Build an evaluation set from your real target sites and tasks: either self-hosted copies of the sites (as WebArena does) or a staging environment with resettable state. Check outcomes in the target system (the record exists with the right values), not the agent's claim. Run each task several times, because runs vary, and report success with confidence intervals (ag12). Include tasks with injected pop-ups, slow pages, layout changes and malicious page text, and tasks where the correct behaviour is to stop and ask. Re-run the suite whenever a target site changes, the model changes, or the harness changes; for third-party sites, a scheduled canary run catches redesigns before users do.

The public case: what OSWorld 2.0 found

In June 2026 the XLANG Lab at the University of Hong Kong and collaborators released OSWorld 2.0 because their own earlier benchmark had stopped discriminating between strong agents: on OSWorld-Verified, top systems were scoring in the high 80s. The new benchmark has 108 workflows built from authentic artefacts, such as submitting an expense claim by following a tutorial PDF, operating a legacy reimbursement portal, extracting amounts from noisy receipts, tracing evidence across email and a bank site, reacting to a new email that changes the task, recovering hidden information from an earlier report, and stopping to ask the user when an inconsistency needs clarification. People take a median of about 1.6 hours per task; agents averaged hundreds of steps. Under the primary binary metric at 500 steps, the best system completed 20.6% of tasks (54.8% partial credit), and GPT-5.5 plateaued near 14% while using far fewer tokens. The benchmark also includes separate safety reports on safety-sensitive actions. The authors' summary of failure is the most useful production guidance in the paper: agents now handle basic GUI control and coding, but lose track of constraints, miss information that arrives mid-task, guess rather than ask, and skip verification, struggling most when a task depends on hidden state they must recover. Those are design problems for the harness and the task model as much as for the model.

Failure modes in production

Silent wrong actions. A misclick or a stale observation leads to a wrong but plausible end state, reported as success. Verification steps and outcome checks against the target system are the defence.

Site drift. A redesign breaks selectors, labels or layouts overnight; success rates on one site drop sharply. Monitor success per site and alert on drops.

Runaway runs. Loops between two pages or repeated failed clicks burn steps and tokens. Enforce step and time budgets and detect repeated states.

Injection incidents. A page persuades the agent to visit another site or submit data. Confirmations, domain allowlists and isolated profiles contain them; logs reveal them.

Blocked automation. Sites start serving CAPTCHAs or blocking the agent's traffic. Route to human takeover and revisit whether an API or partnership is needed.

What to monitor

Per site and task type: success rate verified against the target system, steps and tokens per task, time per task, recovery events (backtracks, retries, pop-up dismissals), human takeovers and confirmation rates, blocked navigation attempts outside the allowlist, injection-detector hits, and cost. Keep screenshots or snapshots of each step for a sample of runs, with sensitive fields redacted, for debugging and audit.

A staged rollout

Introduce a browser agent in stages. First, shadow mode: the agent runs alongside the people currently doing the work, its results are compared but never used. Second, assisted mode: the agent prepares the work (fills the form, drafts the order) and a person reviews and submits; measure how often they change something. Third, supervised autonomy on the task types and sites where assisted mode showed high agreement, with confirmations kept for irreversible steps and a sample of runs reviewed weekly. Expand site by site, keep the human fallback queue staffed, and roll back a site to assisted mode automatically when its success rate drops. This pace matches the evidence: agents are strong on short, well-specified steps and weak on long tasks with hidden state, so autonomy should grow where measured reliability does.

import math, random

# ---------- Part 1: what does one observation cost? -----------------------------------------
def screenshot_tokens(w, h, patch=28):            # one visual token per 28x28 patch (see ag9)
    return math.ceil(w / patch) * math.ceil(h / patch)

def text_tokens(chars):                            # rough rule: ~4 characters per token
    return math.ceil(chars / 4)

page = {"raw_html_chars": 400_000, "ax_nodes": 600, "chars_per_ax_node": 48,
        "interactive_nodes": 120, "chars_per_interactive": 40}
obs = {
    "raw HTML":               text_tokens(page["raw_html_chars"]),
    "accessibility tree":     text_tokens(page["ax_nodes"] * page["chars_per_ax_node"]),
    "interactive elements":   text_tokens(page["interactive_nodes"] * page["chars_per_interactive"]),
    "screenshot 1280x800":    screenshot_tokens(1280, 800),
    "screenshot + ax tree":   screenshot_tokens(1280, 800) + text_tokens(page["ax_nodes"] * page["chars_per_ax_node"]),
}
STEPS, PREFIX, PRICE = 30, 5_000, 2.00              # steps per task, fixed prompt tokens, $ per M input
print(f"{'observation':24s} {'tokens/step':>11s} {'task input (keep all)':>22s} {'keep last 3':>12s}")
for name, t in obs.items():
    keep_all = sum(PREFIX + t * k + 150 * k for k in range(1, STEPS + 1))
    keep3 = sum(PREFIX + t * min(k, 3) + 150 * k for k in range(1, STEPS + 1))
    print(f"{name:24s} {t:11,d} {keep_all:15,d} (${keep_all*PRICE/1e6:5.2f}) {keep3:9,d}")

# ---------- Part 2: an observe-act loop with injected errors and a recovery policy ---------
random.seed(4)
P_MISCLICK, P_POPUP, P_SLOW = 0.08, 0.05, 0.10      # per-step error probabilities
GOAL_STEPS = 12                                      # correct actions needed to finish

def run_task(policy, max_steps=40):
    progress, steps = 0, 0
    while progress < GOAL_STEPS:
        if steps >= max_steps:
            return False, steps                      # step budget exhausted
        steps += 1
        r = random.random()
        if r < P_SLOW:                               # screenshot taken before the page settled
            if policy["wait_for_stable"]:
                steps += 1                           # wait, re-observe, then act correctly
                progress += 1
                continue
            r = P_SLOW + P_POPUP                     # acting on a stale view = a misclick
        if r < P_SLOW + P_POPUP:                     # cookie banner / modal blocks the page
            if policy["dismiss_popups"]:
                steps += 1; progress += 1            # close it, then act
                continue
            return False, steps                      # stuck behind the modal
        if r < P_SLOW + P_POPUP + P_MISCLICK:        # clicked the wrong element
            if policy["verify_after_act"]:
                steps += 2                           # notice, go back, retry
                progress += 1
                continue
            return False, steps                      # silently wrong: task fails at the end
        progress += 1
    return True, steps

policies = {
    "naive":            {"wait_for_stable": False, "dismiss_popups": False, "verify_after_act": False},
    "verify only":      {"wait_for_stable": False, "dismiss_popups": False, "verify_after_act": True},
    "verify + popups":  {"wait_for_stable": False, "dismiss_popups": True,  "verify_after_act": True},
    "full recovery":    {"wait_for_stable": True,  "dismiss_popups": True,  "verify_after_act": True},
}
for name, pol in policies.items():
    results = [run_task(pol) for _ in range(5_000)]
    ok = [s for done, s in results if done]
    print(f"{name:14s} success {len(ok)/len(results):6.1%}   mean steps when successful "
          f"{sum(ok)/max(len(ok),1):5.1f}")

What to look for. Design: a vendor-portal invoice agent

Finance wants an agent to download invoices from 15 vendor portals every week (each with its own login and layout, none with an API), extract invoice number, date, amount and tax, and enter them into the company's accounting system, which has an API. Volume is about 600 invoices a week. Design it, including perception, grounding, recovery, security and what a human still does.

Answer

Split the work. The accounting system has an API, so the agent never uses its UI: entering invoices is a deterministic API call after validation. Only the portal part needs a browser agent, and it is read-only apart from logging in and downloading.

Perception and grounding. Use accessibility-tree snapshots with element references for navigation (login forms, invoice lists, download buttons) and fall back to screenshots on portals with poor markup. Prefer high-level actions: "open invoices page", "download all invoices since date". Extract fields from the downloaded PDFs with a document-extraction step and validate (totals add up, tax rate plausible, vendor matches), rather than reading them off the screen.

Recovery. Wait for stability, dismiss known banners, verify after each step (the invoice list loaded, the file downloaded with the expected name), backtrack on failure, cap steps per portal and retry the portal once later. Keep per-portal notes (where the invoices page is, quirks) as structured configuration that humans can edit.

Security. One disposable browser profile per portal run; credentials filled by the harness from a vault; domain allowlist per portal; downloads limited to PDF and scanned before use; no other sessions present, so an injected instruction on a vendor page cannot reach anything else; confirmation is not needed because nothing irreversible happens in the browser, but any instruction-like text in invoices or pages is ignored by design (extraction, not obedience).

Humans and monitoring. Humans handle two-factor prompts and CAPTCHAs through a takeover queue, review invoices that fail validation, and fix portal notes when a site changes. Monitor success per portal, steps and cost per run, validation failure rates and takeovers; a sudden drop on one portal means a redesign. At about 600 invoices a week, also ask the three largest vendors for API or e-invoicing access, which removes most of the browser work.
