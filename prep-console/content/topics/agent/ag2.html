The first agent most engineers write is about forty lines long, and it works on the first try. A user asks a question, the model asks for a tool, the code runs it, the model answers. Then it meets real traffic. One afternoon every request starts failing with an HTTP 400 error, "tool_use ids were found without tool_result blocks immediately after", because a new code path logged a message between the model's tool call and its result. The next week a support customer is told their refund has been issued when the refund service actually timed out; the loop caught the exception and returned an empty string, so the model saw what looked like success. A research agent burns $40 overnight calling the same search with slightly different wording 300 times. A coding agent's long file edit is cut off by the output limit mid-JSON and the loop crashes trying to parse half a tool call.

None of these failures is about the model being unintelligent. Each is about the loop: the short piece of ordinary code that sits between the model and the world, decides what the model sees, executes what it asks for, and decides when to stop. ag1 established that an agent is defined by the model owning the control flow. The loop is what that ownership runs inside, and its details decide whether the agent is reliable, affordable and honest about what it did.

This lesson takes the loop apart. It starts with the shape of the loop as code and the exact representation of tool calls in the message history, using a complete three-tool episode written out as the JSON that actually travels to and from the API, with token counts per call. It then covers the stop reasons a response can carry and the stopping conditions a loop must add of its own; the ReAct pattern in detail, including what its own authors found goes wrong; the plan-and-execute alternative and when it is cheaper; and reflection, which helps only when there is something real to reflect on. The case is the ReAct paper's error analysis, which predicted the looping failure you will meet in production.

A detective's notebook

Picture a detective who cannot leave the office and has no memory between visits, but has an assistant who can go anywhere. Every time the detective is consulted, the assistant hands over the whole case notebook: the original question, every note the detective wrote, every errand the detective ordered, and every report the assistant brought back. The detective reads it all, writes a new note ("the butler's alibi depends on the train time"), and either orders one more errand ("check the 6:15 timetable") or writes the solution. The assistant runs the errand, pastes the report into the notebook, and comes back.

That is an agent loop. The detective is the model. The notebook is the message history, and because the detective has no memory, the notebook is the entire state of the investigation. The errands are tool calls; the reports are tool results, also called observations. The assistant is the loop: your code, which decides whether each errand is allowed, runs it, writes down exactly what happened, including failures, and decides when the investigation has gone on long enough.

The analogy shows two things that are easy to miss. First, the detective only knows what is in the notebook. If the assistant writes "timetable checked" when the station was closed, the detective will reason from a fiction. Honest, specific observations are the assistant's main job. Second, the notebook grows with every visit, and the detective re-reads all of it every time. Long investigations get slow and expensive for that reason alone.

Where the analogy breaks: a real detective decides how long to investigate based on judgement and a sense of cost. The model has no inherent sense of cost and only a rough sense of progress, so the assistant must impose limits from outside.

The loop as a picture

Each pass through the loop is one step. The model's response carries a stop reason, a field saying why it stopped generating: because it finished, because it wants a tool run, because it hit its output limit, or because it refused. The loop branches on that. Tool requests go through validation and execution, and their results are appended to the history. Then the loop checks its budgets and goes round again.

Three families of loop

Within this skeleton, there are three broad ways to organise the model's thinking. In ReAct (reason and act), the model decides one action at a time, seeing every result before the next decision. In plan-and-execute, the model writes a plan first and the steps are carried out with fewer model calls, replanning only if something goes wrong. In reflection patterns, the model reviews its output or its failed attempt, writes down what to do differently, and tries again. Real agents mix them. The body of this lesson shows each with numbers, and shows that the choice is mostly about how predictable the task's path is and what feedback is available.

1. The loop in code

Here is a complete loop in Python-like code against Anthropic's Messages API, with the stopping conditions this lesson argues for. Read it once now; each part is explained below.

def run_agent(task, max_steps=12, max_cost_usd=0.50, deadline_s=120):
    messages = [{"role": "user", "content": task}]
    cost, start, seen = 0.0, time.monotonic(), Counter()
    for step in range(max_steps):
        resp = client.messages.create(model=MODEL, system=SYSTEM, tools=TOOLS,
                                      max_tokens=2048, messages=messages)
        cost += price(resp.usage)                  # input, output, cache tokens
        messages.append({"role": "assistant", "content": resp.content})
        trace(step, resp)                          # every call is logged

        if resp.stop_reason == "end_turn":
            return finish(messages)                # verify outcome in code
        if resp.stop_reason == "max_tokens":
            return retry_bigger_or_stop(messages)  # never run a half call
        if resp.stop_reason == "refusal":
            return escalate("refused", messages)

        results = []
        for block in resp.content:                 # may be several (parallel)
            if block.type != "tool_use":
                continue
            key = (block.name, json.dumps(block.input, sort_keys=True))
            seen[key] += 1
            if seen[key] >= 3:
                out, err = ("You have made this exact call 3 times. Try a different "
                            "approach, or explain what is blocking you."), True
            else:
                out, err = execute(block.name, block.input)   # never raises
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": out, "is_error": err})
        messages.append({"role": "user", "content": results})

        if cost > max_cost_usd or time.monotonic() - start > deadline_s:
            return stop("budget", messages)
    return stop("max_steps", messages)

Four design decisions are already visible. The history is a plain list you own, appended to and never edited in place, so it can be logged, replayed and resumed (ag11). The function execute never raises: it validates arguments against the schema, checks permissions, runs the tool, and converts any failure into a string plus an error flag, because an exception would end the run with the model none the wiser. Every exit path has a reason (end_turn, max_tokens, refusal, budget, max_steps), which becomes a metric. And repeated identical calls are caught by the loop, not left to the model to notice.

2. How a tool call travels: the message format

Providers differ in naming, but every tool-calling API encodes the same three things: the tool definitions you offer, the model's request to call one, and your result, linked to the request by an identifier.

In Anthropic's Messages API (as documented on 6 October 2026), a message's content is a list of typed content blocks. An assistant message that calls a tool contains a tool_use block with three fields: id (a unique string such as toolu_01…), name, and input, a JSON object matching the tool's input_schema. The response's stop_reason is "tool_use". Your reply is a user message whose content contains a tool_result block with the matching tool_use_id, the content (a string or a list of text, image or document blocks), and optionally "is_error": true.

Three rules from the documentation matter for loop code. The tool results must immediately follow the assistant message that requested them; nothing may come between. In that user message, the tool_result blocks must come first, with any text after them. And when the model requests several tools in one turn (parallel tool use), all their results go in that one user message. Break the first two and the API returns a 400 error; break the pairing silently, for example by attaching results to the wrong ids, and the model will reason from swapped data.

OpenAI's Responses API encodes the same idea differently: the model's output contains a function_call item with a call_id, a name and arguments, which is a JSON string you must parse rather than an object; you return a function_call_output item with the same call_id and an output string. The parse step is one more place to handle malformed output, unless strict mode (ae4) guarantees the schema. Libraries and protocols that sit above these APIs, including MCP (ag4), translate between such formats, but the loop logic is identical.

3. A full ReAct episode, on the wire

Here is a complete three-tool episode, written as the request bodies the loop sends. The task: a customer, already authenticated as C-881 by the application, writes "Order A17, the headphones arrived with the left side dead. Can I get half my money back?" Three tools are offered: lookup_order(order_id), get_refund_policy(category, reason) and issue_refund(order_id, amount, reason). The system prompt and tool definitions are about 1,230 tokens including the provider's tool-use system prompt (286 tokens on Claude Sonnet 5.5 per Anthropic's pricing page).

Call 1. The request carries the system prompt, the tools and one message:

"messages": [
  {"role": "user", "content": "Order A17, the headphones arrived with the left side dead. Can I get half my money back?"}
]

The response (about 70 output tokens):

{"role": "assistant", "stop_reason": "tool_use", "content": [
  {"type": "text", "text": "I'll look up order A17 first."},
  {"type": "tool_use", "id": "toolu_01", "name": "lookup_order",
   "input": {"order_id": "A17"}}
]}

The loop checks that A17 belongs to customer C-881 (the authenticated identity comes from the application, never from the model), runs the lookup and appends two messages: the assistant message above, unchanged, and a user message with the result.

Call 2. The request now carries three messages:

"messages": [
  {"role": "user", "content": "Order A17, the headphones arrived ... half my money back?"},
  {"role": "assistant", "content": [
    {"type": "text", "text": "I'll look up order A17 first."},
    {"type": "tool_use", "id": "toolu_01", "name": "lookup_order", "input": {"order_id": "A17"}}]},
  {"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_01",
     "content": "{\"order_id\":\"A17\",\"item\":\"Aria headphones\",\"category\":\"audio\",\"price\":120.00,\"currency\":\"GBP\",\"delivered\":\"2026-09-28\",\"status\":\"delivered\"}"}]}
]

The response (about 75 tokens) reasons from the observation and asks for the policy:

{"role": "assistant", "stop_reason": "tool_use", "content": [
  {"type": "text", "text": "Delivered 2026-09-28, 8 days ago, audio category. Checking the policy for items damaged on arrival."},
  {"type": "tool_use", "id": "toolu_02", "name": "get_refund_policy",
   "input": {"category": "audio", "reason": "damaged_on_arrival"}}
]}

Call 3 appends that message and the result {"window_days":30,"partial_refund_max_pct":50,"photo_required":false} (about 55 tokens) as toolu_02's tool_result. The model now has everything it needs:

{"role": "assistant", "stop_reason": "tool_use", "content": [
  {"type": "text", "text": "Within the 30-day window; partial refunds up to 50% are allowed. 50% of 120.00 is 60.00."},
  {"type": "tool_use", "id": "toolu_03", "name": "issue_refund",
   "input": {"order_id": "A17", "amount": 60.00, "reason": "damaged_on_arrival"}}
]}

Before executing, the loop applies business rules in code: the amount is at most 50% of the recorded price, the order belongs to the customer, the refund is under the auto-approval limit (say £75), and the call carries an idempotency key derived from the run and step so a retry cannot refund twice (ag3, ag11). It runs and returns {"refund_id":"R-5521","status":"issued","amount":60.00}.

Call 4 carries all seven earlier messages. The response has stop_reason: "end_turn" and a text block: "I've issued a refund of £60.00 (half the £120.00 price) for order A17, reference R-5521. It should reach your card in 3-5 working days." The loop then verifies in code that refund R-5521 exists for A17 with amount 60.00 before telling the customer anything is done.

4. ReAct, properly

The episode above is ReAct in modern clothing. In the original paper (Yao et al., 2022, published at ICLR 2023) the model wrote plain text in a fixed format, "Thought: …", "Action: search[Aria headphones]", and the harness parsed the action with string matching and appended "Observation: …". Native tool calling replaced the parsing: the text block is the thought, the tool_use block is the action, and the tool_result is the observation. Many current models also reason internally before each call; on Anthropic's newer models this interleaved thinking happens between tool calls automatically, and the documentation requires the loop to pass the returned thinking blocks back unchanged within a tool-use turn, so your history code must preserve every block type it receives rather than keeping only text and tool calls.

Why interleave reasoning with acting? The paper compared four prompting styles with PaLM-540B. Standard prompting answers directly. Chain-of-thought (CoT) reasons in text before answering but cannot look anything up. Act calls tools without written reasoning. ReAct does both. On HotpotQA (multi-hop questions answered with a Wikipedia search tool) and FEVER (fact verification), ReAct reduced the main weakness of CoT, invented facts, and beat Act because the written thoughts let it decompose the question and track what it had found. The best results came from combining them, switching between ReAct and self-consistent CoT depending on confidence: 35.1 exact match on HotpotQA and 64.6% accuracy on FEVER, against 29.4 and 56.3 for CoT alone.

More instructive than the scores is the paper's error analysis on HotpotQA, which reads like a preview of production agent failures:

Category (share of sampled cases)ReActCoT
Success: correct reasoning and answer94%86%
Success: right answer, flawed reasoning6%14%
Failure: reasoning error (incl. repetitive loops)47%16%
Failure: search returned nothing useful23%—
Failure: hallucination0%56%
Failure: label ambiguity29%28%

Grounding in observations eliminated hallucination as a failure cause. In exchange, two new failure classes appeared that are entirely about the loop. Nearly a quarter of failures were uninformative search results that derailed the reasoning, a tool-design problem (ag3). And nearly half were reasoning errors, a large part of which the authors describe as the model "repetitively generates the previous thoughts and actions" and failing "to jump out of the loop". Every production agent team meets this loop. The fixes are loop-level: informative empty results, duplicate-call detection, per-tool caps and an explicit way to give up.

5. Stop reasons and stopping conditions

A response's stop reason is the first signal the loop reads. Anthropic's documented values (checked 6 October 2026) are:

Stop reasonMeaningWhat the loop should do
tool_useThe model requests one or more client toolsValidate, execute, append results, continue
end_turnThe model finished naturallyTreat as "claims done"; verify, then return
max_tokensOutput hit your max_tokens limitIf a tool_use block is incomplete, retry with a higher limit; never execute a partial call
stop_sequenceA custom stop string was producedHandle per your protocol
pause_turnA provider-run (server) tool loop hit its iteration limitSend the assistant content back to let it continue
refusalThe model declinedStop and escalate, or try a fallback per policy
model_context_window_exceededThe response filled the context windowTreat as truncated; compact history (ag5)

Stop reasons only report what the model did. The loop needs its own stopping conditions, because the model has no built-in sense of cost and only an approximate sense of progress:

  • Step budget: a maximum number of iterations, set from the distribution of steps in successful runs (just above the 95th-99th percentile).
  • Cost budget: tokens priced into dollars, including cache and reasoning tokens, since one step with a huge tool result can cost more than ten small ones.
  • Wall-clock deadline: for interactive tasks especially, since tools can hang.
  • Per-tool caps: at most N web searches, at most one refund per run.
  • No-progress detection: the same normalised call repeated, the same error three times, or no new information in the last K steps. The first response is a corrective observation; the second is a stop.
  • Verified completion: where the outcome can be checked in code, end_turn triggers the check, and a failed check either gives the model the evidence and a small extra budget or escalates.
  • External interrupt: a user cancelling, an operator kill switch, or an approval being denied.

When a budget stops a run, end it gracefully: one last model call with a tiny budget asking for a summary of what was done and what is blocking, the stop reason recorded, and the case handed to a person or returned to the user honestly. A run that simply dies leaves no trace of how far it got.

6. Plan-and-execute

ReAct decides one step at a time, which is adaptive but means a full model call, re-reading the whole history, for every tool call. Plan-and-execute separates the two: a planner call writes a list of steps; an executor carries them out, by code where steps are mechanical or by smaller model calls where they are not; and a final call combines the results. If a step fails or a result contradicts the plan, the planner is called again to replan.

ReWOO (Xu et al., 2023) pushed this to its limit. The planner writes the whole plan with placeholders for results, for example #E1 = lookup_order[A17], #E2 = get_refund_policy[#E1.category]; the tools run in order with no model calls in between; and a solver reads all the evidence at once. The paper reported about five times fewer tokens and four points higher accuracy than a ReAct-style baseline on HotpotQA, because the long history is never re-read step by step.

Apply that to the refund episode. Plan-and-execute uses two model calls: the planner (1,270 input, about 120 output for the plan) and the solver (the prefix plus the plan plus the evidence, about 1,560 input, 110 output). That is 2,830 input tokens instead of 5,915, and two sequential model latencies instead of four. On predictable paths the saving is real.

The cost is blindness. The planner wrote "issue_refund" before knowing the delivery date. If the order had been delivered 45 days ago, outside the 30-day window, a blind plan would refund anyway unless something checks. Two rules follow. Side effects must never be planned blind: plans may gather information freely, but any write must be gated by a check, in code or in a fresh model decision, that sees the observations it depends on. And plans must be cheap to abandon: when results deviate, replan with the evidence so far rather than pushing on. In practice many production agents are hybrids: a short written plan at the start (which also makes the agent's intent visible and reviewable), ReAct-style execution that consults and updates the plan, and replanning when a step fails.

7. Reflection and self-critique

Reflection is a step in which the model reviews its output or its trajectory and writes down conclusions to use next. The best-known version, Reflexion (Shinn et al., 2023), runs an agent on a task, gets a feedback signal (a unit test result, an environment's success flag, a heuristic that detects loops), asks the model to write a short verbal reflection on why it failed ("I assumed the list was sorted; the test with unsorted input failed"), stores that in an episodic memory, and retries with the reflection in context. On the HumanEval coding benchmark it reached 91% pass@1, above the 80% the paper cites for GPT-4 at the time, without any weight updates.

The key ingredient is the external signal. Huang et al. ("Large Language Models Cannot Self-Correct Reasoning Yet", ICLR 2024) tested intrinsic self-correction, asking a model to review and fix its own reasoning with no new information, and found that models often fail to improve and sometimes get worse, changing correct answers into incorrect ones. That fits the arithmetic of ag1: a critic that is itself unreliable, looking at the same evidence, adds a new chance of error rather than detection.

So reflection belongs where something new has arrived: after a failing test (put the failure output in the reflection prompt), after a tool error (ask what assumption was wrong before retrying), after a separate checker or grader rejects the output (the evaluator-optimiser pattern of ag1), or between attempts at a task with a success signal. In a loop, it is usually cheapest as a prompt instruction ("when a tool returns an error, state what you will change before calling again") rather than a separate model call. As a separate call, it should be measured on the eval for both directions: how often it fixes wrong outputs and how often it breaks right ones.

8. Errors inside the loop

Errors arrive at three levels, and each belongs in a different place. Transport and transient errors (a model API rate limit, a network timeout on an idempotent read) are retried in code with backoff, invisibly to the model, because a model retry costs a full step and may change the request. Tool errors the model can act on (unknown order id, invalid date format, permission denied, no results) go back as a tool_result with is_error: true and a message written for the model: what was wrong and what to try. Anthropic's documentation gives the same advice ("Rate limit exceeded. Retry after 60 seconds." rather than "failed") and notes that with invalid calls the model typically retries two or three times with corrections. Errors in the model's output itself (a truncated tool call, malformed arguments when strict schemas are not enforced) are handled by the loop: retry with a larger output limit, or return a validation error naming the field. ag3 treats error messages as prompts in detail; the loop's job is to guarantee that every failure becomes an honest observation and that none is silently converted into success.

The transcript is the program counter

In a conventional program, the state of a computation is in variables and the call stack. In an agent, the only state the model can see is the transcript: everything it knows about what has happened, what it intended and what remains is encoded in those messages. That has engineering consequences. Editing the history (dropping a failed attempt, rewriting an old result) changes what the agent "remembers", which is powerful for compaction (ag5) but dangerous if done carelessly, because a removed failure can be repeated. Replaying a run means replaying the transcript, so you must store exactly what was sent and received, including blocks you do not display, such as thinking blocks. And durability (ag11) is mostly a matter of persisting the transcript after every step so that a crashed run can resume from it.

Stopping is a classifier with two error types

Every stopping rule makes two kinds of mistake. It can stop too early, cutting off runs that would have succeeded (false stop), or too late, letting doomed runs burn budget (missed stop). Raising the step limit trades the first for the second. Thinking of stopping this way makes it measurable: on the eval set, plot success rate and mean cost against the step limit, or against the no-progress threshold, and pick the point where cutting further loses successes faster than it saves money. The same logic applies to the model's own decision to stop: premature end_turn with an incomplete task is a false stop, and verification in code is how you catch it.

Why ReAct loops repeat themselves

Repetition is not mysterious. A language model predicts likely continuations of its context, and once the context contains several near-identical thought-action pairs, repeating the pattern is a likely continuation. Uninformative observations make it worse: if the search returns "no results", the context contains no new information that would make a different action more likely. That is why the fixes work on the context, not on the prompt's instructions: an observation that adds information ("you have tried these three queries; none matched; product codes look like AR-1234") changes the distribution of next actions, while an instruction at the top of the system prompt saying "don't repeat yourself" is far away and weakly weighted by then.

Planning horizon and replanning cost

The choice between ReAct and plan-and-execute can be framed as a bet on how often observations surprise the plan. If the plan survives contact with reality a fraction s of the time, expected cost is roughly s × (plan + execute + solve) + (1 − s) × (plan + partial execute + replan + …). When s is high (lookups, report generation, data pipelines), planning wins clearly. When it is low (debugging, open research), ReAct's per-step adaptation is cheaper than repeated replanning. Measuring s on traces, the share of runs where the executed path matched the initial plan, turns an architectural debate into a number.

Shaping the first and last step

Shaping the first and last step is an underused loop lever. On APIs and models that support it, forcing a specific tool on the first call (a named tool_choice, or OpenAI's required or named function) guarantees, for example, that the agent always reads the case record before doing anything else. Support varies by model: Anthropic's documentation (checked 6 October 2026) says Claude Opus 5.5, Sonnet 5.5 and Fable 5.1 reject forced tool choice, accepting only auto and none. The portable way to get the same guarantee is in the loop: run the first read yourself in code and put its result in the initial context, which also saves a model step. A finish tool, a tool whose schema is the structured final answer (status, summary, actions taken, open questions), makes the end of the run machine-readable and lets the loop validate it like any other call, instead of parsing free text. Both shrink the space of trajectories without fixing the whole path, keeping flexibility in the middle where it is useful.

Reasoning is not always faithful

The thoughts in a ReAct trace are useful for debugging but are not a guaranteed account of why the model chose an action (rs7 discusses chain-of-thought faithfulness). A trace may say "checking the policy because the item is damaged" when the model would have called the same tool anyway. For audit and incident review, rely on the actions and observations, which are facts in your log, and treat the thoughts as hypotheses about intent. For safety monitoring, thoughts are still valuable signals, since a plan to do something disallowed often appears in text before the action.

Stateful APIs do not remove the cost

Some APIs keep conversation state on the provider's side, so you send only the new message and a reference to the previous response. That simplifies code and saves bandwidth, but the model still processes the full history each turn, and you are still billed for it (caching applies similarly). The trade-offs are control and portability: compaction, audit, replay and provider switching all need the transcript in your own store. Many teams use provider state for convenience in prototypes and their own journal in production.

Failure signatures and what they mean

HTTP 400 on tool results. An orphaned tool_use id, text placed before tool_result blocks, or a message inserted between call and result. Almost always a bug in history management, typically introduced by a new feature (logging, a "please wait" message, compaction) that touches the message list. Fix with a validator that checks the pairing invariant before every request, and a unit test that builds histories through every code path.

Claimed but failed actions. The final message says "done" but the system of record disagrees. Causes: an exception converted into an empty success, a missing is_error, or a premature end_turn. Track the rate of runs where the post-run verification fails; it should be near zero for actions and is a leading indicator of a loop bug.

Loops. Many steps with near-identical calls. Measure the share of runs with a repeated normalised call, and the distribution of steps per run: a second hump far to the right of the main distribution is the loop population. ReAct's own analysis predicted this; uninformative tool results are the usual trigger.

Truncation. Rising counts of max_tokens stops, often after someone adds a tool whose arguments are large (whole files, long emails). Raise the limit for those steps or redesign the tool to take smaller arguments (an edit with a diff rather than a full rewrite).

Budget exhaustion. Runs ended by step, cost or time budgets. Some are healthy (hard tasks escalated); a sudden rise after a model or prompt change usually means a regression in the agent's ability to finish, and is often visible a day before success-rate metrics move.

The case: ReAct's own error analysis

The ReAct paper is usually cited for its success rates, but its most practical section is a hand-labelled error analysis on HotpotQA comparing ReAct with chain-of-thought (Table 2 of the paper). Chain-of-thought's dominant failure was hallucination, 56% of its failures; ReAct's was 0%, because each claim could be checked against a retrieved page. But ReAct introduced two new failure classes that CoT could not have: 23% of failures came from search results that were empty or unhelpful, and 47% were reasoning errors, a large part of which were the model repeating earlier thoughts and actions without escaping the loop. The authors also found that ReAct's grounding came at some cost in flexibility of reasoning, and that the best results combined ReAct with self-consistent chain-of-thought, falling back from one to the other on low confidence.

Read as an engineer, that table is a specification for a production loop. Grounding through tools solves the hallucination problem. In exchange, you must design tools whose empty or failed results are informative, and loops that detect and break repetition. The same paper anticipates two more production practices: it limited ReAct to a fixed number of steps on each task, and it backed off to a different strategy when the loop failed to produce an answer, which is a step budget and a fallback.

What to log and monitor

Per run: the stop reason (model finish, each budget type, refusal, truncation, interrupt), steps, input, cached and output tokens, cost, wall time, and the post-run verification result. Per step: the request size, which tools were called with which normalised arguments, durations, errors and whether each error was transient (retried in code) or shown to the model. Aggregates worth alerting on: the 400-error rate, claimed-but-failed rate, loop rate, truncation rate and budget-stop rate, each broken down by agent version so that a prompt or model change that degrades the loop is caught quickly. ag14 builds the full tracing setup on the OpenTelemetry conventions.

Knobs

Step and cost budgets set from successful-run percentiles; no-progress thresholds (repeat count, window); max_tokens per step type; parallel tool calls on or off; forced first tool; a finish tool; the reflection instruction on errors; and whether to plan first. Change one at a time and measure on the eval with several trials per task, because loop changes affect both success and cost.

Debug: the agent that says it worked

A travel-booking agent has three tools: search_flights, hold_seat and book. Customers complain that the agent sometimes says "Your flight is booked, confirmation XK42Q" when no booking exists. In the traces you find: the book tool occasionally times out after 30 seconds; the loop's tool wrapper catches all exceptions and returns "{}"; on 3% of runs the final message contains a confirmation code that does not appear in any tool result. Explain what is happening and design the fix.

Answer

What is happening. When book times out, the wrapper converts the failure into an empty JSON object with no error flag. To the model, {} after a booking call looks like a successful call that returned nothing interesting, so it reports success. Because it has no real confirmation code, it produces a plausible-looking one, a hallucination triggered by the loop, not by the model's knowledge. The timeout itself may or may not have booked the seat, which is a second problem: the true state is unknown.

Fix the observation. Return failures as is_error: true results with specific text: "book timed out after 30 s; the booking may or may not have been made; call get_booking_status with hold_id H-19 before retrying". Never convert exceptions into empty success.

Fix the side effect. Give book an idempotency key derived from the run and the hold (ag3, ag11), so a retry after a timeout cannot create a second booking, and add get_booking_status so the true state can be checked. Retry the timed-out call in code with the same key before the model sees anything; only show the model an error if the status remains unknown.

Fix the claim. Derive the final status from the action log, not the model's text: the loop knows whether book returned a confirmation. Add a post-run check that any confirmation code in the final message appears in a tool result for this run; if not, block the message and escalate. Track the claimed-but-failed rate; it should drop to zero.

Prevent recurrence. Add eval cases where book times out, returns an error, and succeeds slowly, and assert both the final message and the booking state. Add a lint or test that the tool wrapper never returns a success-shaped result from an exception path.
