A coding agent is asked to fix a flaky test. In the first ten minutes it does well: it reads the test, searches for the function under test, opens three files, runs the suite and spots a race condition. By step 40 something has changed. It re-opens a file it already read, proposes a fix it tried and reverted at step 18, and edits a file the user said at the start must not be touched. Its run has cost $6, three times the usual. Nothing crashed and no limit was hit. The agent is simply working inside a context window that now holds 140,000 tokens: the full output of six test runs, eleven file reads, two abandoned approaches, the original instructions now far behind it, and its own earlier wrong guesses, which it keeps half-believing.

Every agent faces this. ag2 showed that the history is the agent's entire state and that it grows every step. That growth has two costs. The obvious one is money and latency: every step re-reads everything, so input tokens grow with the square of the step count. The less obvious one is quality. Models do not use long contexts uniformly well; accuracy falls as input grows, distractors pull answers off course, constraints mentioned once early are followed less faithfully, and the model conditions on its own failed attempts. Anthropic's engineering team calls the discipline of managing this context engineering: curating, at every step, which tokens the model sees.

This lesson works through it with numbers. It starts with the anatomy of the window on one step and how to order it. It then covers context rot and the evidence for it, works token growth over 20 steps with and without compaction, and walks the strategies from lightest to heaviest: returning less, clearing old tool results, compacting into structured summaries, notes outside the window, retrieval inside the loop and sub-agents. It finishes with prompt caching for long runs, using current prices, including the counter-intuitive result that compaction can cost more than doing nothing once caching is on.

A desk, not a filing cabinet

Picture the context window as a desk. On it you can spread whatever papers you need to do the next piece of work. Papers you are not using still take up space and catch your eye. Nobody tidies the desk for you: every report your assistant brings back is dropped on top, and after a long day the important note about what the client forbade is under forty pages of printouts. A good worker keeps a clean desk: the brief and rules pinned at the top, the current task in the middle, a notebook of decisions to one side, and a filing cabinet across the room for everything else, fetched when needed.

The analogy maps directly. The pinned material is the system prompt and tool definitions: stable, always there. The notebook is structured notes the agent writes and re-reads. The current work is the task, the recent steps and the latest tool results. The filing cabinet is everything outside the window: the full transcript, documents, previous runs, reachable through tools. Context engineering is deciding what stays on the desk.

The analogy breaks in two ways worth knowing. A person can glance over a pile and ignore it; a model reads every token on every step and is paid for each one. And a person's attention to the top page does not fade because the pile is large; a model's does, which is the subject of section 2 of the body.

What goes in the window on each step

Two ordering principles pull in the same direction here. For caching, anything that never changes during the run should come first, because a provider can only reuse a prefix that is byte-for-byte identical to an earlier request (ae2). For attention, the material the next decision depends on should be near the end, because models use the beginning and end of long contexts more reliably than the middle (ae6's "Lost in the Middle" case). So: tool definitions and system prompt first, then the task, then compressed older history, then recent steps, then a short progress note restating the goal and constraints, then the newest tool result.

The three levers

Every technique in this lesson pulls one of three levers. Put less in: smaller tool results, fewer tool definitions, references instead of documents. Take things out: clear old tool results, compact history, drop failed attempts. Move things elsewhere: notes in a file, raw history in a store, exploration in a sub-agent's separate context. And one technique changes the price rather than the size: caching the stable prefix so that re-reading it costs a tenth as much. The art is combining them so the window stays small, relevant and cache-friendly at the same time, because, as section 7 shows, the levers interfere with each other.

2. Context rot: why more context can mean worse answers

It would be convenient if a model's accuracy depended only on whether the needed information is somewhere in the window. It does not. In July 2025 Chroma published a study of 18 models, including GPT-4.1, Claude 4, Gemini 2.5 and Qwen3 families, on deliberately simple tasks whose difficulty stayed fixed while the input grew. Performance degraded as input length increased, "often in surprising and non-uniform ways". Three findings matter for agents. When the question and the relevant passage were less semantically similar, accuracy fell faster with length, and real agent questions are rarely phrased like the passages that answer them. Distractors, passages that resemble the answer but are wrong, hurt, and some hurt much more than others. And on LongMemEval, a conversational-memory benchmark, models given only the relevant ~300 tokens did consistently better than the same models given the full ~113,000-token history.

Anthropic's context-engineering guide explains the mechanism informally as an attention budget: a transformer relates every token to every other token, so as the context grows, attention is spread over more pairs and each relevant token gets a smaller share; models are also trained mostly on shorter sequences. The practical consequences for agents are specific:

  • Stale tool output competes with current output. Six versions of the same test log are six candidate answers to "what is failing?"; the model may read the wrong one.
  • Early constraints fade. "Don't modify the migrations folder", said once at the top, competes with 100,000 tokens of later material.
  • Failed attempts persist. A wrong hypothesis written at step 12 is still in the window at step 40, and models condition on their own earlier text, so the error can resurface.

So the target is not "fits in the window" but "the smallest window that contains what the next decision needs". A million-token window, available at standard pricing on Claude models from the 4.6 generation per Anthropic's pricing page, raises the ceiling; it does not change that target.

3. Token growth over 20 steps, worked

Take a run with a 6,500-token starting context (4,500 tools, 1,500 system, 500 task) that adds 2,500 tokens per step (300 of model output and 2,200 of tool result). The context the model reads at step k is 6,500 + 2,500(k − 1):

Context read (no compaction)6,50016,50029,00041,50054,000

Without compaction, the total input billed over 20 steps is the sum of an arithmetic series: 20 × 6,500 + 2,500 × (0 + 1 + … + 19) = 130,000 + 2,500 × 190 = 605,000 tokens. At Claude Sonnet 5.5's $2 per million input (checked 6 October 2026) that is $1.21, plus 20 × 300 = 6,000 output tokens at $10 per million, $0.06: $1.27 for a run whose distinct content is only 54,000 tokens.

With compaction, use this rule: after a step, if the next context would exceed 30,000 tokens, replace all history except the last two steps with a 2,000-token structured summary. After step 10 the next context would be 31,500, so compaction leaves 6,500 + 2,000 + 2 × 2,500 = 13,500. The context then grows again by 2,500 per step: 13,500 at step 11, 16,000, 18,500, 21,000, 23,500, 26,000, 28,500 at step 17, when the next would be 31,000, so it compacts again to 13,500, giving 13,500, 16,000, 18,500 for steps 18-20. The total billed input is 372,500 tokens, 38% less than 605,000, and the peak context is 29,000 rather than 54,000.

Compaction is not free. Each compaction is an extra model call that reads the current context (about 31,500 tokens) and writes a 2,000-token summary: without caching, about 31,500 × $2/106 + 2,000 × $10/106 = $0.083. Two compactions add $0.17, so the uncached compacted run costs about 372,500 × $2/106 + $0.06 + $0.17 ≈ $0.97 against $1.27. Section 7 shows how caching changes this picture.

4. The lightest lever: put less in

The cheapest token is the one never added. ag3's rules about tool results are context engineering at the source: return the fields the next decision needs, paginate, offer a concise format, truncate with a note on how to get more. A tool that returns 400 tokens instead of 6,000 saves those tokens on every later step of the run. The same applies to tool definitions: an agent that loads only the 8 tools its task needs instead of all 40 saves 9,600 tokens per step. And output counts too: asking the model to write a one-line rationale before each action rather than an essay keeps the per-step growth small.

5. Take things out: clearing and compaction

Tool-result clearing is the lightest way to remove tokens already in the history. Once a tool result has been used, replace it with a placeholder such as "[result of read_file src/db.py cleared; call again if needed]", keeping the model's own messages and the most recent few results intact. It needs no model call and is easy to reason about. Anthropic offers it as a server-side feature (as of 6 October 2026, the clear_tool_uses_20250919 context edit, in beta): by default it triggers above 100,000 input tokens and keeps the three most recent tool uses, with options to exclude named tools and to clear at least a minimum number of tokens each time. You can implement the same in your own loop. In the worked example, clearing all but the last three results drops each older step from 2,500 to about 350 tokens.

Compaction rewrites older history into a summary, removing the model's old reasoning as well as old results. Its danger is that summaries are lossy and the summariser does not know what will matter later. The classic losses are exact identifiers (a file path, an order id, a version number), constraints stated once ("never touch migrations/"), and negative knowledge (approach X was tried and failed because Y), whose loss makes the agent try X again. The remedy is a schema rather than a free-form "summarise the conversation":

## Goal (as currently understood, including user refinements)
## Constraints and rules (verbatim where possible)
## Decisions made and why
## Approaches tried that failed, and why
## Current state (what is true now: files changed, tests status, ids)
## Open questions / blockers
## Next steps

Fill it with a model call (the agent's own model, or a cheaper one if quality holds on your eval), validate in code that each section is present and that every identifier mentioned in the last few steps survives, keep the most recent steps verbatim, and store the full uncompacted transcript outside the window so nothing is irrecoverably lost. Anthropic's guide describes its coding agent preserving "architectural decisions, unresolved bugs, and implementation details" while discarding redundant tool outputs, which is the same idea.

6. Move things elsewhere: notes, retrieval and sub-agents

Structured note-taking gives the agent a file or store outside the window (a NOTES.md, a to-do list, a progress record) and tools to read and update it. Notes survive compaction intact because they are not part of the summarised history, and re-reading them brings the goal and constraints back near the end of the context. Anthropic's guide cites an agent playing Pokémon that kept precise tallies and objectives across thousands of steps by maintaining its own notes. The progress note in the primer's figure is a small version of this, rewritten each step.

Retrieval inside the loop, or just-in-time context, keeps lightweight references in the window (file paths, document titles, ids) and lets the agent fetch content with tools when it decides it needs it, rather than pre-loading everything that might be relevant. A coding agent that greps for a symbol and opens two files spends perhaps 3,000 tokens; pre-loading the twenty files that might matter would spend 60,000 on every step. The trade-off is extra steps and the risk that the agent does not look where it should, which good search tools (ag3) and a short map of the corpus in the system prompt mitigate. lm9's retrieval pipeline becomes a tool here, called at the agent's discretion, and its results are subject to the same size discipline as any tool result.

Sub-agents move whole explorations out of the parent's window. The parent gives a focused task ("find every place the retry logic is configured and report file, line and setting") to a separate run with its own fresh context; the sub-agent may read fifty files, but returns only a condensed answer, which Anthropic's guide puts at typically 1,000 to 2,000 tokens. The parent's context grows by the summary, not the exploration. The costs, more total tokens, an extra layer of latency and information lost at the boundary, are the subject of ag8.

7. Prompt caching for long runs, worked

Prompt caching (ae2) fits agent loops almost perfectly, because each step's request starts with exactly the previous step's request. The provider stores the processed prefix; the next request reads it from cache and processes only the new tokens. On Anthropic's API (checked 6 October 2026) the rules that matter for agents are:

  • Pricing: a five-minute cache write costs 1.25× the input price and a one-hour write 2×; a cache read costs 0.1× on most models (0.05× on Claude Opus 5.5, 0.025× on Fable 5.1). For Sonnet 5.5: input $2, write $2.50, read $0.20 per million tokens.
  • Prefix order: the cache is built in the order tools, then system, then messages, and a change at one level invalidates that level and everything after it.
  • Breakpoints: up to four explicit cache_control breakpoints per request, or automatic caching with one top-level setting that moves the breakpoint to the last cacheable block as the conversation grows; the API looks back at most 20 blocks from a breakpoint for a matching entry.
  • Minimum length: 512 tokens for the newest models such as Sonnet 5.5 and Opus 5.5, but 4,096 for Haiku 4.5; shorter prefixes are silently not cached.
  • Lifetime: five minutes by default, refreshed on each read, or one hour at the higher write price.
  • Verification: each response reports cache_creation_input_tokens, cache_read_input_tokens and input_tokens (the uncached tokens after the last breakpoint); total input processed is their sum.

Now price the 20-step run with caching on and no compaction. Step 1 writes its 6,500 tokens. Every later step reads the previous step's whole context from cache and writes the 2,500 new tokens. Reads total 605,000 − 54,000 = 551,000 tokens (every context except the last is re-read once); writes total 6,500 + 19 × 2,500 = 54,000 tokens.

Input cost falls from $1.21 to $0.245, about 80%. Notice that writes and reads cost about the same here: in an agent, each new token is paid once at the premium and then read cheaply many times, so the saving depends on how many later steps re-read it. On Claude Opus 5.5 ($4 input, $5 write, $0.20 read) the same run's input falls from $2.42 to $0.38, about 84%, because its cache reads are a twentieth of input.

Now combine caching with compaction. Each compaction rewrites history after the stable 6,500-token prefix, so everything after it must be written to cache again, and the summary call adds its own cost (about $0.032 with caching: reading ~29,000 cached tokens, writing ~2,500, and generating 2,000 output tokens). The compacted, cached run comes to about $0.279 + 2 × $0.032 ≈ $0.34, slightly more than the $0.305 of the uncompacted cached run.

The lesson generalises. Compaction and clearing edit history, and any edit invalidates the cache from that point on. So with caching on: compact rarely and in large chunks (Anthropic's clear_at_least parameter exists for this reason), keep the edited region as late as possible, keep the stable prefix untouched, and choose compaction thresholds for quality and window limits rather than for cost. On long runs the balance shifts back: at 100 steps, an uncompacted context would reach 254,000 tokens per step, and even at the cache-read price the re-reads, plus context rot, make periodic compaction worthwhile.

8. Designing for the cache

Most cache failures in agents come from small, innocent changes to the prefix. The checklist:

  • No volatile content in the system prompt. A timestamp, request id, user's name or "today is…" line at the top changes every request. Put such facts in the latest user message, or (on the newest Claude models) as a mid-conversation system message, which Anthropic's documentation suggests to preserve the cache.
  • Deterministic tool lists. Build tool definitions in a fixed order; tools aggregated from several MCP servers must be sorted, not iterated from a set. Do not add or remove tools mid-run.
  • Fixed settings within a run. Changing tool_choice, thinking or effort settings between steps invalidates parts of the cache.
  • Append-only history. Never rewrite earlier messages casually; batch any clearing or compaction.
  • Lifetime that matches the pauses. If steps can wait longer than five minutes (slow tools, human approvals), the five-minute cache expires; a one-hour lifetime costs 2× on writes but avoids a full rewrite after every pause.
  • Measure. Log the three usage fields per step and alert when the cache-read share of input drops.

Why models condition on their own mistakes

A language model predicts continuations of its context, and its own earlier outputs are part of that context. If step 12 contains a confident but wrong claim ("the bug is in the parser"), later steps are generated in a world where that claim was made, and contradicting it requires evidence strong enough to overcome it. This is one reason long agent runs can drift: errors are not just persistent, they are self-reinforcing. Removing a failed attempt from the history, or replacing it with a single line stating that it was tried and why it failed, gives later steps a cleaner prior. It also explains why reflection without new evidence (ag2) is weak: the critic reads the same contaminated context.

Summaries compound their losses

A run that compacts several times summarises summaries. Each pass is lossy, and details that survived one pass because they seemed relevant may be dropped by the next, which sees them only as compressed text. After four or five compactions, the agent's knowledge of the early run can be a vague paraphrase. Defences: keep durable facts in structured notes that are carried forward verbatim rather than re-summarised; make the summary schema cumulative (sections are updated, not rewritten); keep identifiers in a separate, append-only list; and keep the raw transcript outside the window so a later step, or a person, can look something up.

Provider caching and the model's KV cache

Prompt caching is the provider exposing, and pricing, a mechanism inside the serving stack: the stored key and value tensors for a processed prefix, the KV cache of lm13. That is why caching depends on exact token prefixes (the tensors for a token depend on every token before it), why changing anything earlier invalidates everything later, and why a cache hit also cuts time to first token: the provider skips the prefill work for the cached part. It also explains provider limits such as minimum lengths and lifetimes, which reflect the cost of holding tensors in fast memory. Self-hosted serving stacks expose the same idea as prefix caching, with the same design rules.

Context poisoning and persistence of bad data

Once something enters the history it is re-read on every step until removed. That includes hallucinated facts the model wrote itself, wrong results from a buggy tool, and instructions injected through tool results (ag10). A single poisoned item can steer dozens of later steps. Context management is therefore also a hygiene tool: clearing old results limits how long injected text stays in view, and compaction with a schema that records facts with their sources (which tool, which step) makes it easier to notice and drop a fact that came from an untrusted place. It is not a security boundary, though; ag10's controls still apply.

Long context versus retrieval is an empirical question per task

There is a genuine trade-off between stuffing a large window and retrieving selectively. Long context avoids retrieval errors, where the agent never fetches the passage it needs; retrieval avoids context rot and cost. Which wins depends on the task: tasks needing synthesis across many parts of a corpus may do better with more in context, while needle-finding tasks do better with retrieval. The only reliable way to choose is to evaluate both on your tasks, measuring accuracy, cost and latency, rather than following a rule of thumb. Model generations also shift the balance, so the comparison should be re-run when models change.

Evaluating context strategies

Context changes are easy to get wrong silently: a compaction prompt that drops one constraint type will pass most evals and fail a specific slice. Useful evaluations replay long recorded trajectories with different strategies and compare task success, cost and specific failure signatures: repeated completed work, re-tried failed approaches, violated early constraints, wrong identifiers after compaction. Include "needle" checks: plant a constraint early and test whether it is respected at step 40 with each strategy. And evaluate at the step counts that actually occur in production, since strategies that are neutral at 10 steps can matter greatly at 100.

Thinking blocks and context

Reasoning models add a new kind of content to the history: thinking blocks. Providers differ in whether earlier turns' thinking is kept in context and billed as input; Anthropic's documentation (checked 6 October 2026) says its newest models keep prior turns' thinking by default, while some earlier models stripped it, and offers a clear_thinking context edit. Keeping thinking preserves the cache and the model's own reasoning thread; clearing it saves tokens but invalidates the cache at that point. As with tool results, the choice is a measured trade-off, and dropping thinking blocks inconsistently is a common cause of unexpected cache misses.

The case: Anthropic's context-engineering guide and Chroma's context-rot study

Two public sources from 2025 frame the practice. Anthropic's applied AI team published "Effective context engineering for AI agents" in September 2025, arguing that as agents run longer the core skill shifts from writing prompts to curating the whole context each step. It introduced the "attention budget" framing for context rot; recommended system prompts at the "right altitude" (specific enough to guide, general enough to give heuristics); favoured just-in-time retrieval through tools over pre-loading; and described three techniques for long-horizon work that this lesson uses: compaction (as in its coding agent, preserving decisions and unresolved issues while discarding redundant tool output, with tool-result clearing as the lightest form), structured note-taking (persistent notes such as a NOTES.md, with the Pokémon-playing agent keeping tallies across thousands of steps), and sub-agents that explore in their own contexts and return 1,000-2,000-token summaries.

Chroma's "Context Rot" report (Hong, Troynikov and Huber, July 2025) supplied the measurements. Across 18 models, accuracy fell as input length grew on tasks whose difficulty was held constant, including a trivial task of reproducing repeated words, where models under-generated, misplaced the unique word and produced tokens not in the input as sequences grew. Lower similarity between question and answer passage steepened the decline; distractors had non-uniform but real effects; and, surprisingly, models did better on shuffled haystacks than on logically coherent ones. On LongMemEval, focused inputs of about 300 tokens beat full histories of about 113,000 tokens across model families. Together the two sources make the case quantitatively: a bigger window is capacity, not capability.

Failure modes and their signatures

Cache miss storms. Cost per run jumps while steps stay flat; the cache-read share of input falls toward zero. Usual causes: a timestamp or id added to the system prompt, nondeterministic tool ordering, a middleware that edits history, or a change of TTL needs after a slow tool was added.

Post-compaction amnesia. Agents redo finished work, retry abandoned approaches or break constraints shortly after a compaction. Compare failure rates in the 5 steps after compaction with other steps; fix the summary schema and carry constraints in notes.

Context overflow. Responses fail with context-limit errors (Anthropic reports a model_context_window_exceeded stop reason), usually from one very large tool result or a long run without compaction. Cap result sizes and set a compaction threshold well below the limit.

Rot without overflow. No errors, but success falls with step count. Plot success against context length at the decision point; a downward slope says the window is too full of stale material.

What to monitor

Per step: input tokens split into cache read, cache write and uncached; output and thinking tokens; context size; size of each tool result. Per run: steps, compactions, clearings, peak context, cost, success. Fleet-wide: cache-read share of input (it should be high and stable for long runs), distribution of peak context, success rate by peak-context bucket, and the post-compaction failure rate. Alert on drops in cache share and on rises in peak context after releases.

Knobs

Tool result size limits; number of tool definitions loaded; clearing trigger and number of recent results kept; compaction threshold, summary schema and recent-steps-kept; whether notes are re-read every step or periodically; cache lifetime; and whether exploration goes to sub-agents. Tune them on replayed long trajectories, and re-tune when the model changes, since newer models tolerate longer contexts differently.

Diagnose: the research agent that got worse and pricier

A research agent answers analysts' questions by searching internal reports and the web. Runs average 35 steps. After a release that (a) added a line "Current time: {now}" to the top of the system prompt, (b) raised the search tool's results from 5 to 20 per query, and (c) switched from a five-minute to no explicit cache setting with automatic caching, the cost per run rose from about $0.90 to $3.10 and analysts report that answers more often cite an outdated figure that was corrected later in the same run. Explain what happened and what you would change.

Answer

Cost. Change (a) is the big one: a timestamp at the top of the system prompt makes every request's prefix differ from the previous one at the system level, so on every step the whole context (tools are before the system prompt and may still hit, but the system prompt and all messages miss) is written to cache at 1.25× instead of read at 0.1×. Over 35 steps with a growing context, that turns a mostly-cached run into a mostly-written one, roughly a threefold cost increase on input. Change (b) adds to it: four times as many search results per call, re-read on every later step, increases per-step growth and therefore the quadratic total. Change (c) is not itself the problem; automatic caching works if the prefix is stable. Confirm by reading the usage fields: cache_read_input_tokens should have collapsed and cache_creation_input_tokens risen.

Quality. More results per search means more distractors and more stale figures in the window. When a figure is corrected at step 20, the earlier version from step 6 is still there, often several times, and the model sometimes cites it, which is classic context rot: the right fact is present but competes with similar wrong ones.

Fixes. Move the current time out of the system prompt into the user message (or a late system message on models that support it), and add a test asserting byte-identical prefixes between consecutive steps. Return 5 results by default with a concise format and let the agent ask for more. Clear search results after they have been processed, keeping only those the agent marked as sources. Have the agent maintain a structured "facts and sources" note, where a corrected figure replaces the old one, and re-read it before writing the answer. Re-run the eval on replayed runs and compare cost, cache share and the rate of outdated citations before and after.
