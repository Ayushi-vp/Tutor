An operations team asks an agent to organise a three-day offsite: flights for eight people from four cities, a hotel near a venue, the venue itself, all within a budget the finance lead must approve. The first version is a single ReAct loop with search and booking tools. It works, in the sense that eventually something is booked. It takes 61 steps and nine minutes, searching flights for one person at a time. It books the hotel before confirming the venue is available on those dates, and the venue turns out to be full. It asks for budget approval by writing "Shall I go ahead?" in the chat; the organiser replies two days later, by which time the agent's process has been restarted by a deploy and the run is gone. The flight prices it quoted have changed anyway.

None of these failures needs a smarter model. They need structure. Some of the task's order is known before the agent starts: the venue constrains the dates, the dates constrain flights and hotel, and nothing gets booked before the budget is approved. Some of the work is independent and could happen at once: eight people's flight searches do not depend on each other. And one step depends on a human, who will answer on their own schedule, so the run must be able to stop, survive, and resume exactly where it was, re-checking anything that might have gone stale.

This lesson is about adding that structure without throwing away what makes an agent useful. It covers task decomposition into dependency graphs; plans as validated data; graphs and state machines, using LangGraph's model as a concrete reference but showing the ideas in plain code; routers and the cost of their mistakes; parallel tool calls with the latency arithmetic; and human-in-the-loop checkpoints that pause, persist and resume safely. The theme is the same as ag1's autonomy spectrum, applied inside one system: fix in code the parts of the flow you know, and leave the model the decisions that genuinely depend on what it finds.

A project plan with a smart team

Think of how a competent project manager runs a job like the offsite. They write a plan with dependencies ("venue first; then hotel and flights; then approval; then bookings"). They hand independent pieces to several people at once ("you three search flights, you look at hotels"). They insist on sign-off before money is spent, and they write everything down so that if they are off sick, someone else can pick up the folder and continue. Within each task, the people use their judgement; the plan does not tell them which website to search or how to compare options.

That is the target shape for a structured agent. The plan is a dependency graph. The people are nodes: some are model calls with tools, some are plain code, one is a human. The folder is the run's saved state, written after every step. The sign-off is a checkpoint the flow cannot skip. The analogy breaks where it is most useful to notice: people push back when a plan is wrong. A model following a graph will keep following it unless you build in points where results are checked and the plan can change.

Who decides each transition

In this picture, some transitions are fixed in code: intake always leads to planning, approval always precedes booking, booking always leads to verification. Some are conditional: after assembling options, the run goes to approval if an option fits the budget, or back to the planner if nothing does; after approval, it books or replans depending on the human's answer. Inside nodes such as the planner and the searches, the model works with full freedom. That split, structure where it is known, judgement where it is needed, is the whole idea.

What structure buys, and what it costs

Structure is not free. Every fixed edge is a decision you made in advance, and it is wrong whenever reality differs from what you expected; every node is code to write, test and version; and a graph that pauses for people needs storage, notifications and expiry logic. What you get back is predictability (the expensive mistakes become impossible rather than unlikely), speed (independent work runs at once), survivability (a run can stop for a week and continue), and visibility (time, money and failures are attributable to named steps). The judgement call in every design is which of those benefits a particular part of the task actually needs.

Four tools for adding structure

This lesson uses four mechanisms, each answering a different question. Decomposition answers "what are the parts and how do they depend on each other?" Graphs and state machines answer "which transitions are allowed, and where is progress saved?" Routers answer "which path does this request take?" Parallel calls answer "what can happen at once?" And human checkpoints answer "where must a person decide, and how does the run wait for them?" They combine freely: a router in front of several graphs, each graph with parallel fan-out and a checkpoint, each node possibly a small agent loop.

1. Task decomposition

Decomposition breaks a goal into sub-tasks, each with a clear objective and a way to tell it is done. It helps in three ways that map onto ag1's arithmetic. Smaller sub-tasks are easier for the model to do correctly, raising per-step reliability. Sub-tasks with completion checks turn silent errors into detected ones. And independent sub-tasks can run in parallel, cutting latency.

Write the offsite as sub-tasks with dependencies:

IdSub-taskDepends onEst. time
T1Confirm dates, budget, attendees and constraints with the organiser—1 min
T2Find venues available on the datesT140 s
T3Search flights for each of 8 attendeesT18 × 5.5 s serial, ~10 s parallel
T4Find hotels near each candidate venueT230 s
T5Assemble 2-3 complete options with total costT2, T3, T415 s
T6Organiser chooses an option and approves the budgetT5minutes to days
T7Book venue, hotel, flights; verify eachT660 s

These dependencies form a DAG (directed acyclic graph): one-way arrows, no cycles, so there is always an order in which every sub-task's prerequisites finish first. The longest chain of dependencies, the critical path, sets the minimum completion time even with unlimited parallelism: here T1 → T2 → T4 → T5 → T6 → T7. T3 (flights) is off the critical path as long as it finishes before T4 does, so it can run concurrently with T2 and T4 at no cost to total time. Doing T3 serially in a ReAct loop would add about 44 seconds to the critical path for no reason.

Who writes the decomposition? For recurring task types, a person does, once, as a workflow graph. For open-ended tasks, a planner model call does, at run time. Either way, the decomposition should be data the system can check, not prose the model might later reinterpret.

2. Plans as validated data

When a model produces a plan, ask for structure:

{"steps": [
  {"id": "T2", "goal": "Venues in Lisbon for 8 people, 12-14 Nov",
   "tool": "search_venues", "depends_on": ["T1"],
   "done_when": "at least 2 venues with confirmed availability"},
  {"id": "T3", "goal": "Cheapest refundable flights per attendee",
   "tool": "search_flights", "depends_on": ["T1"], "for_each": "attendees",
   "done_when": "one option per attendee under 400 EUR or flagged"},
  ...
]}

Code then validates it before anything runs: every depends_on id exists; a topological sort succeeds (no cycles); every tool is on the allowed list; no step with side effects appears before the approval step; estimated cost fits the budget. A plan that fails validation goes back to the planner with the specific error, exactly like a bad tool call (ag3). An executor then runs every step whose dependencies are complete, in parallel where possible, checks each step's completion criterion, and records status in the state.

Plans are hypotheses. ag2 described the risk of planning blind; the practical defence is explicit replanning triggers: a step fails after its retries; a completion check fails; a result invalidates a later step's assumption (the venue is full, so the hotel search near it is pointless); the cost estimate is exceeded; or the user changes the goal. On a trigger, the planner is called again with the current state and the evidence, and produces a revised plan for the remaining work. Minor surprises should not trigger replanning, or the agent spends its budget re-planning.

3. Graphs and state machines

A state machine describes a process as named states and the transitions allowed between them. Order processing is a classic one: created → paid → shipped → delivered, with cancelled reachable only from the first two. The value is in what it forbids: an order cannot ship before it is paid, whatever any component wants. Agent graphs generalise this. The ingredients are:

  • A state object: everything the run knows (task, history, plan, results, pending approvals, budgets used), with explicit rules for how updates combine.
  • Nodes: functions that read the state and return updates. Some call a model, some call tools, some are plain code, one may be a human.
  • Edges: fixed transitions (after book, always verify) or conditional ones (after assemble, go to approve if within budget, else planner), where a function, possibly a model call, picks the destination.
  • Checkpoints: a saved snapshot of the state after each step, keyed by a run or thread id, so a run can pause, crash or be redeployed and resume.

LangGraph, a widely used open-source framework, is a concrete example of this model (as documented on 6 October 2026). You declare a StateGraph over a typed state whose fields can have reducers, rules for merging updates such as appending messages instead of overwriting them; add nodes and edges, including add_conditional_edges; compile the graph with a checkpointer that persists state after each step; and invoke it with a thread_id. A Send object fans work out to parallel copies of a node (map-reduce), and a Command lets a node both update state and choose the next node. Graph runs also have a recursion limit on the number of steps, a built-in step budget.

None of this requires a framework. The core fits in a few dozen lines of Python:

def run(graph, state, start, store, run_id):
    node = state.get("_next", start)
    while node != "END":
        update, next_node = graph[node](state)        # node returns (update, next)
        state = merge(state, update)                  # apply reducers
        state["_next"] = next_node
        store.save(run_id, state)                     # checkpoint every step
        if next_node == "WAIT_FOR_HUMAN":
            return "paused"                           # release compute
        node = next_node
    return "done"

Notice that the agent loop of ag2 is itself a two-node graph with a cycle: call_model → (if tool_use) run_tools → call_model, or (if end_turn) END. A graph-based design embeds such loops as nodes where open-ended work is needed and surrounds them with fixed structure. The benefits are concrete: each node can be unit-tested with recorded inputs; forbidden transitions are impossible by construction rather than by instruction; checkpoints make long runs survivable; and the trace shows time and cost per node.

4. Routers

A router is a conditional edge at the front of the system: classify the request, send it down a specialised path with its own prompt, tools, model and policies. Anthropic's workflow patterns list routing as a basic building block (ag1). Its value is focus: the refund path carries refund tools and policy, the technical path carries documentation retrieval, easy questions go to a small cheap model (ag13). Its risk is that every downstream path inherits its errors.

Evaluate a router like a classifier. Suppose a labelled set of 1,000 support requests: 400 refunds, 350 technical, 250 general. The router gets 94% right overall, but the confusion matrix shows 24 refund requests (6% of refunds) sent to the general path, which has no refund tools. The overall number hides the expensive error: a misrouted refund produces a frustrated customer and a repeat contact, while a technical question misrouted to general is merely answered less well. Weigh errors by their cost, not by count.

Three standard defences: a fallback for low-confidence classifications (route to a general path that has the union of the risky tools, or ask a clarifying question); a reroute tool on each path so an agent that discovers the request belongs elsewhere can hand off; and monitoring of the route mix and of downstream signals such as repeat contacts per route, because traffic drifts and a router trained on last quarter's requests degrades quietly.

5. Parallel tool calls

Modern models can request several tool calls in a single response. On Anthropic's API, by default Claude may return several tool_use blocks in one assistant turn (you can disable this with disable_parallel_tool_use); OpenAI's equivalent is controlled by parallel_tool_calls. The documentation is explicit that the API does not prescribe execution order: you may run the calls concurrently, sequentially or in any combination, but you must return one tool_result per call, all in the next user message, and if you choose not to run a call (because an earlier one in a sequential batch failed), you still return a result for it with is_error and an explanation such as "Not executed: the preceding write_file call failed."

The latency arithmetic for eight independent flight searches, with a model call taking about 3 seconds and a search about 2.5 seconds:

Sequentially in a ReAct loop, each lookup is a model call plus a search: 8 × (3 + 2.5) = 44 seconds, and eight model calls each re-reading a growing history. In parallel: one model call that writes all eight requests (about 4 seconds for the longer output), eight concurrent searches (about 3 seconds, the slowest), and one model call to use the results (3 seconds): about 10 seconds and two model calls. LLMCompiler (Kim et al., ICML 2024) generalised this: a planner emits a DAG of function calls, a task-fetching unit dispatches calls whose inputs are ready, and an executor runs them in parallel. Against ReAct it reported latency speed-ups of up to 3.7 times, cost savings of up to 6.7 times and accuracy gains of up to about 9%.

Parallelism has limits and hazards. The speed-up is bounded by the slowest call and by dependencies: if each result decides the next call, nothing can be parallelised. Bursts of concurrent calls hit rate limits, so cap concurrency per tool. Partial failures become routine (six of eight succeed), so every call needs its own timeout and its own result. And calls with side effects or shared state, such as creating a folder and writing into it, or two bookings drawing on one budget, should run sequentially or be coordinated. A good default is: read-only calls in parallel, writes in sequence.

Fan-out can also be done by the graph rather than the model: the planner's for_each: attendees becomes eight parallel copies of the search node (LangGraph's Send), each with its own small context, joined by an assembly node. That keeps eight people's search results out of one shared context, which helps with ag5's context rot.

6. Human-in-the-loop checkpoints

A human-in-the-loop checkpoint is a point where the run stops and a person decides. Put them where a person's judgement changes outcomes:

  • Before irreversible or high-impact actions: payments, bookings, deletions, external messages, production changes.
  • At plan approval for long or expensive tasks, where catching a misunderstanding early saves the whole run.
  • On low confidence or unusual cases: the router is unsure, the amounts are unusually large, the request matches no known pattern.

Mechanically, a checkpoint is an interrupt. The run saves its full state (history, plan, the pending action with its exact arguments) under its run id, emits an approval request to a queue or interface, and stops consuming compute: no worker, no open connection, no model call waiting. When the person answers (approve, edit, or reject with a reason), the system loads the state, injects the decision and continues. In LangGraph this is an interrupt(value) call inside a node, which requires a checkpointer and a thread_id, and the run is resumed by invoking the graph with Command(resume=decision). Its documentation states an important rule that applies to any implementation that re-executes steps: on resume, the node restarts from its beginning, so code before the interrupt runs again, and "side effects called before interrupt should (ideally) be idempotent". A node that creates a draft booking and then interrupts will create a second draft on resume unless the creation is idempotent (ag3) or moved after the interrupt.

Three further rules make checkpoints work in practice. Show the exact action: "Book Hotel Avenida, 4 rooms, 12-14 Nov, €2,184 total, refundable until 5 Nov" rather than "Shall I go ahead?". Expire approvals and re-validate: if the answer comes three days later, prices and availability may have changed, so the action is re-checked in code before execution and re-approval requested if it differs materially. Mind the cache: a run paused longer than the provider's cache lifetime will re-write its prefix on resume (ag5), which is usually acceptable but worth knowing when costing long-paused runs.

Approval fatigue is the main failure. A checkpoint on every action trains people to click "approve" without reading, which gives false assurance. Keep checkpoints rare and meaningful by making routine actions safe by construction: sandboxes, limits, reversible operations and allow-lists (ag9, ag10). hd7's platform design cites Anthropic's report that sandboxing reduced permission prompts in Claude Code by 84% in internal use, which is the direction to aim for.

Structure has a shelf life; constraints do not

ag1 distinguished scaffolding that compensates for model weakness from controls that encode business rules. The same split applies to graphs. A planner node that forces the model to write a step list, or a fixed sequence of "search, then summarise, then answer", may help a weaker model and hinder a stronger one that would investigate more efficiently. An approval node before payments or a verification node after bookings encodes a rule that holds whatever the model. Keep the first kind thin and measured (try removing it when models change) and the second kind solid and tested. Teams that over-graph early often end up with dozens of nodes encoding yesterday's model limitations.

State design is where parallel graphs go wrong

When branches run in parallel and all write to the shared state, the merge rule for each field decides whether the result is correct. If two flight-search branches both write results with an overwrite rule, one branch's results vanish. Reducers (append, merge-by-key, max) make the intent explicit, and a good rule is that parallel branches write only to their own keys, with a fan-in node combining them. Large results belong in storage, with references in the state, so checkpoints stay small and fast to write.

Checkpoint granularity and re-execution

Checkpointing after every node means a crash loses at most one node's work, but on resume that node runs again from its start. If the node made a model call, the call is repeated (and may answer differently); if it made a tool call with side effects, the side effect may be repeated. Two mitigations combine well: make side-effecting operations idempotent with keys derived from the run and node, and record model and tool results in the journal so that a re-executed node can replay recorded results instead of calling again. ag11 develops this as durable execution; frameworks differ in how much of it they provide, so check what yours actually does.

Versioning graphs with runs in flight

A graph that pauses for days will meet deploys. A checkpoint saved under graph version 7 refers to node names, state fields and edges of version 7. If version 8 renames a node or changes a field's meaning, resuming the old checkpoint can fail or silently follow the wrong path. Treat graph definitions like database schemas: store a version with each checkpoint; keep old versions runnable until their runs drain, or write explicit state migrations; prefer additive changes; and include "resume a checkpoint from the previous release" in the test suite.

Routing errors are asymmetric

A router's mistakes cost different amounts depending on direction: sending a simple question to the expensive path wastes money; sending a refund request to a path without refund tools loses a customer. So a router should not be tuned for accuracy alone. Assign costs to each cell of the confusion matrix, choose thresholds that minimise expected cost, and bias ambiguous cases toward the path that can handle more (or ask a question). rs7 makes the same argument for routing between fast and reasoning models, and ag13 applies it to cost.

Human time is part of the critical path

In a run with an approval, the human's response time usually dominates the wall clock by orders of magnitude, so latency engineering elsewhere matters less than making approval fast: clear summaries, the right approver notified on the right channel, defaults for routine cases, batching of related approvals, and escalation when an approval waits too long. Measuring time-to-approval and approval rates per checkpoint is how you find checkpoints that are slow, ignored, or always approved (and therefore candidates for automation with a rule).

Testing graphs

A graph is easier to test than a free loop, but only if you use that. Unit-test each node with recorded inputs and fixed model outputs (a scripted fake model, as in the labs); test each conditional edge's routing function on a table of states; test whole paths with a scripted model that follows the happy path, a failure path and a replanning path; and test the pause-and-resume cycle, including resuming after a simulated crash in every node. These tests are deterministic and cheap, which frees the expensive model-in-the-loop evals (ag12) for questions only a real model can answer.

Event-driven resumption

Paused runs should be resumed by events (an approval submitted, a webhook from a booking system, a timer expiring) rather than by workers polling. That lets thousands of paused runs cost nothing but storage. The resumption handler loads the checkpoint, re-validates anything time-sensitive, and continues. The same mechanism handles external callbacks, such as a long-running job finishing, which is how agents integrate with asynchronous systems without holding resources while they wait.

The case: LLMCompiler and LangGraph's interrupt semantics

Two public sources capture the two sides of this lesson. LLMCompiler (Kim, Moon, Tabrizi, Lee, Mahoney, Keutzer and Gholami; ICML 2024) attacked the latency and cost of sequential ReAct loops. Its function-calling planner writes the set of calls needed and their dependencies; a task-fetching unit dispatches each call once its inputs are available, substituting earlier results into later arguments; and an executor runs ready calls in parallel. Compared with ReAct on its benchmarks, the paper reports latency speed-ups of up to 3.7 times, cost savings of up to 6.7 times, and accuracy improvements of up to about 9%, the last because fewer intermediate model calls means fewer chances to go astray. It is a clean demonstration that control-flow structure, not model choice, decided much of the cost and latency.

LangGraph's documentation on interrupts captures the operational side of pausing for people. Interrupts require a checkpointer and a thread id; a run is resumed by passing Command(resume=...), whose value becomes the return value of the interrupt call; and, crucially, the interrupted node restarts from its beginning on resume, so any code before the interrupt runs again. The documentation's warning that side effects before an interrupt should be idempotent, with the example of records being created twice, is exactly the class of bug that appears in production when teams add approvals to existing nodes.

Failure modes and their signatures

Approval queues backing up: time-to-approval rises and runs expire; usually too many checkpoints or the wrong approvers. Rubber-stamping: approval rates near 100% with decision times of a second or two; the checkpoint is not adding judgement. Duplicate side effects after resume: two drafts, two emails, two bookings; non-idempotent work before an interrupt. Rate-limit errors in bursts: parallel fan-out without concurrency caps. Partial-failure confusion: the agent reports success when some parallel calls failed; results not reported per call. Plan drift: executed steps diverge from the plan without a replan; the plan was not consulted or not updated. Recursion or step-limit stops: graphs that cycle without converging. Resume failures after deploy: checkpoints from an older graph version.

What to monitor

Per node: invocations, duration, cost, errors. Per run: path taken through the graph, replans, parallel batches and their partial-failure rate, time paused, and outcome. Per checkpoint: requests, approval, edit and rejection rates, time to decision, expiries. Per router: route distribution, confidence distribution, fallback rate, and downstream signals per route (repeat contacts, escalations). And for releases: the number of in-flight runs on each graph version and resume errors.

A note on frameworks

Graph frameworks such as LangGraph provide state schemas, checkpointers for several databases, interrupts, streaming and tracing integrations, which is a lot of code you would otherwise write. The costs are an extra abstraction between you and the model calls, API churn (frameworks for agents change quickly; check the semantics of the version you run, as this lesson did for interrupts), and the temptation to add nodes because the framework makes it easy. Anthropic's advice in "Building effective agents" applies: if you use a framework, understand the code underneath it, and be ready to replace a framework feature with a few lines of your own when its behaviour does not match what you need.

Knobs

Which steps are fixed and which are model-decided; replanning triggers; concurrency limits per tool; whether the model or the graph does fan-out; checkpoint placement and approval expiry; router thresholds and fallbacks; step and recursion limits. As always, change one at a time and measure success, cost, latency and human time on the eval set.

What to look for. Serial search should take around the sum of the sleeps (roughly 18 seconds for eight searches), and parallel search with four workers around two batches of the slowest call (5-6 seconds); with eight workers, about the slowest single call. Redesign: the quarterly report agent

A finance agent produces a quarterly report for each of 30 business units. Today it is one ReAct loop per unit: it queries the data warehouse several times, computes metrics, drafts commentary, and emails the draft to the unit head. Problems: runs take 25 minutes each and are run one after another overnight; about 1 in 10 drafts contains a number that does not match the warehouse because the model did arithmetic itself; twice a draft was emailed before the finance lead reviewed it; and when the warehouse is slow, runs time out and start again from scratch. Redesign the control flow.

Answer

Make the known structure explicit. A graph per unit: fetch_data (fixed, parameterised SQL queries run by code, not composed by the model), compute_metrics (code, so every number is exact and traceable), draft_commentary (model node: writes narrative around the computed numbers, which it receives as a table it may not change), check_numbers (code: every number in the draft must match a computed metric, else back to drafting with the mismatches listed), review (human interrupt), send (idempotent email with a key per unit and quarter), verify_sent.

Parallelise across units. Thirty units are independent: fan out the 30 graphs with a concurrency cap matched to the warehouse's capacity (say 5), and within each unit run independent queries in parallel. Total time becomes roughly six batches of the slowest unit rather than 30 × 25 minutes, and the model only does the commentary step.

Make the human checkpoint unskippable. send is reachable only from review with an approval recorded; the finance lead sees the draft, the metrics table and the diff from last quarter, and can approve, edit or reject. Batch approvals: one review screen listing all 30 units, so the lead is not interrupted 30 times. Approvals expire if data is refreshed.

Make it survive slowness. Checkpoint after every node so a warehouse timeout retries fetch_data only, with backoff, rather than restarting the run; record query results so a re-executed node does not re-query unnecessarily. The email node's idempotency key prevents duplicate sends on resume.

Measure. Number mismatches caught by check_numbers (should fall to zero reaching review), time per unit and per node, time to approval, and any send without an approval record (alert).
