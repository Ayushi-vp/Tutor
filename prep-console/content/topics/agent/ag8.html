A startup builds an "AI software company": a product-manager agent writes requirements, an architect agent designs, a coder agent implements, a tester agent writes tests, and a reviewer agent approves. The demo is charming, with agents politely handing work to each other. In use, it costs five times as much as a single coding agent with the same tools, takes three times as long, and passes fewer tests. Reading the traces shows why: the coder never saw the product manager's conversation with the user, so it misses a constraint; the reviewer reverses the coder's library choice, the coder reverses it back; the tester writes tests against the architect's design, which the coder deviated from for a good reason nobody recorded. Most of the tokens go to agents summarising and restating each other's work.

Across town, another team builds a research assistant in which a lead agent breaks a question into eight sub-questions, sends eight sub-agents to search the web in parallel, each in its own fresh context, and combines their findings. It answers broad questions much better than their single agent, faster, with better citations. Anthropic reported exactly this shape of result for its own research system in June 2025: a multi-agent design beat a single agent by 90.2% on its internal research evaluation, while consuming far more tokens.

Both teams used "multi-agent systems". One got coordination overhead and lost context; the other got parallelism and clean contexts. The difference was not the framework or the model. It was whether the work genuinely split into independent pieces that did not need to share decisions. Cognition, the company behind the Devin coding agent, published "Don't Build Multi-Agents" the day before Anthropic's post, arguing the first team's case from experience: actions carry implicit decisions, and agents that do not share full context make conflicting ones.

This lesson gives you the tools to tell the cases apart. It covers what counts as a multi-agent system, the main patterns (orchestrator–worker, handoffs, debate and critique, sub-agents for context isolation), the token and latency arithmetic of splitting work, the published failure taxonomy, and a decision procedure that ends where every architecture decision in this track ends: compare against the simpler design with the same budget, on your tasks.

A newsroom, not a relay race

Picture two ways of producing a long investigative story. In a newsroom, an editor plans the piece and sends several reporters to cover separate angles: one to court records, one to interview former employees, one to the financial filings. Each comes back with a short memo of findings and sources. The editor, who holds the whole story in mind, writes it. The reporters do not need to know what each other found, and the editor never reads the full court transcript, only the memo. That works because the angles are separable and one person owns the narrative.

Now picture a relay: one writer drafts the opening, hands a summary to a second who writes the middle, who hands a summary to a third who writes the ending. Each writer sees only a summary of what came before, makes their own choices of tone and emphasis, and the result reads like three different stories. That fails because writing one story involves decisions that have to be shared.

Multi-agent systems behave the same way. Several model instances, each with its own context, do well when work splits into separable parts with one owner who integrates the results (the newsroom), and badly when the parts are coupled and every hand-off loses decisions (the relay). The analogy breaks in one way: human reporters bring different experience and catch each other's mistakes; instances of the same model given similar context mostly make the same mistakes.

The patterns

A multi-agent system is any design in which several model instances, each with its own context and role, communicate to complete a task. The main shapes: orchestrator–worker (a lead delegates sub-tasks to workers and integrates results); handoffs (control of a conversation passes from one specialist to another); debate or critique (peers propose and challenge answers); and agent-as-tool (an agent calls a sub-agent like a function and keeps control). Pipelines, where fixed stages pass work along, are workflows (ag7) whose stages happen to be agents. In every shape the costs are the same three: more model calls and tokens, information lost at each boundary, and more ways for things to go wrong.

A quick test before building one

Before drawing boxes and arrows, ask three questions about the task. Can it be split into parts that need no decisions from each other while they run? Is there one obvious owner who can integrate the results? And is a single context genuinely too small or too slow for the work? If any answer is no, the default is one agent, possibly with read-only sub-agents for exploration. If all three are yes, a lead with parallel workers is worth prototyping, and the first thing to build is the comparison against one agent given the same budget, because that comparison is what decides whether the extra machinery stays.

1. What problem multi-agent actually solves

Strip away the metaphors of teams and companies, and there are three concrete benefits a multi-agent design can deliver. Parallelism: independent sub-tasks run at the same time, cutting wall-clock time. Context isolation: each agent's context holds only what its sub-task needs, so no single context fills with everything (ag5's context rot). Specialisation: different agents can have different instructions, tools, permissions and even models suited to their part. Anything else, such as "agents collaborating" or "emergent intelligence", should be treated as a hypothesis to measure, not a benefit to assume.

And there are three concrete costs. Tokens: more model calls, briefs and summaries; Anthropic reports agents in general use about four times the tokens of chat interactions and its multi-agent system about fifteen times. Information loss: every boundary passes a brief down and a summary up, and whatever is not in them is lost. Coordination failures: duplicated work, gaps, conflicting outputs, agents ignoring each other, loops. The design question is always whether the benefits on a specific task exceed these costs.

2. Orchestrator–worker, in detail

In the orchestrator–worker pattern a lead agent analyses the task, plans sub-tasks, starts workers (often in parallel), and synthesises their results. Anthropic's research system is the best-documented production example: a Claude Opus 4 lead and Claude Sonnet 4 sub-agents searching in parallel. Its engineering write-up distils several lessons that apply generally.

Delegation specs matter more than anything else. Early versions gave workers short instructions like "research the semiconductor shortage", and workers duplicated each other's searches or left gaps. What worked was a detailed brief for each worker: the objective, the output format, which tools and sources to use, and clear boundaries separating its job from the others'. Think of it as writing a ticket for a contractor who has no other context and cannot ask questions.

Effort must be scaled explicitly. Models are poor at judging how much work a task needs, so the lead's prompt embedded rules: simple fact-finding uses one agent with 3-10 tool calls; direct comparisons use 2-4 sub-agents with 10-15 calls each; complex research uses more than 10 sub-agents with clearly divided responsibilities. Without rules, the system spawned many agents for simple questions.

Parallelism happens at two levels. The lead starts 3-5 sub-agents at once rather than one after another, and each sub-agent makes 3 or more tool calls in parallel (ag7). Together these cut research time by up to 90% for complex queries, per the same post.

Workers return condensed results. A sub-agent may read dozens of pages but returns a summary, typically 1,000-2,000 tokens in Anthropic's context-engineering guidance, ideally structured (findings with sources) so the lead can check coverage and synthesise reliably.

3. Sub-agents as context isolation, worked

The least appreciated benefit of sub-agents is arithmetic. A single agent doing a long research task accumulates everything in one context, and its input tokens grow with the square of its steps (ag5). Splitting the same work into sub-agents bounds each context.

Single agent. 30 steps; starts with a 5,000-token context (instructions, tools, task); each step adds 3,000 tokens (a search result or page excerpt plus the model's note). Total input = 30 × 5,000 + 3,000 × (0 + 1 + … + 29) = 150,000 + 3,000 × 435 = 1,455,000 tokens. Its final context is 5,000 + 3,000 × 29 = 92,000 tokens, deep into the range where context rot bites.

Lead plus four sub-agents. Each sub-agent runs 12 steps, starting from 3,500 tokens (shorter instructions plus its brief) and adding 3,000 per step: 12 × 3,500 + 3,000 × 66 = 42,000 + 198,000 = 240,000 tokens each, 960,000 for four. The lead runs 8 steps from 5,000 tokens, adding about 1,000 per step on average (its own reasoning plus four 1,500-token summaries arriving over the run): 8 × 5,000 + 1,000 × 28 = 68,000. Total: 1,028,000 tokens, about 30% less, and no context exceeds 3,500 + 3,000 × 11 = 36,500 tokens.

Caching (ag5) discounts the re-reads that make the single agent expensive, narrowing the gap. And real multi-agent systems are rarely used for "the same work": they search more broadly because they can, which is where Anthropic's fifteenfold multiplier comes from. The arithmetic says multi-agent is not inherently wasteful; the usage pattern decides.

4. Handoffs

A handoff transfers control of a conversation or task from one agent to another. A customer-support system might have a triage agent that identifies the problem and hands off to a billing agent or a technical agent, each with its own instructions and tools. Agent frameworks typically implement a handoff as a special tool the model calls ("transfer to billing"); the framework then switches which agent's instructions and tools are active. Contrast agent-as-tool, where the main agent calls a specialist with a sub-task and receives a result, staying in control throughout.

Handoffs force four decisions. What context travels: the full history keeps every detail but brings noise and the previous agent's assumptions; a structured summary (customer, problem, what has been tried, what the customer wants) is focused but can drop details, so critical fields should be explicit. Whose permissions apply: the billing agent should have billing tools and the customer's authorisation, not inherit everything the triage agent could do. Loop prevention: agents can pass a confused user back and forth ("that's a billing question" / "that's a technical question"); cap handoffs per conversation and forbid handing straight back without new information. Escalation: when no agent fits, a person should take over, with the summary.

5. Debate and critique

In multi-agent debate (Du et al., 2023), several model instances answer a question independently, then read each other's answers and reasoning and revise, over several rounds, converging on a final answer. The paper reported improvements in mathematical and strategic reasoning and in factual accuracy, with the same procedure applicable to black-box models. A simpler cousin is the critic or evaluator-optimiser pattern (ag1): one agent drafts, another critiques against criteria, and the first revises.

These patterns work when error diversity is high: the agents make different mistakes, so comparing answers reveals errors. They fail when diversity is low: instances of one model with similar prompts and the same evidence share blind spots, converge on the same wrong answer, and may become more confident in it. ag2's discussion of self-correction applies: a critic with no new information is weak. Ways to raise diversity are different models, different prompts or assigned stances, different evidence or tools, and above all an external check (tests, retrieval, a calculator). And the cost is agents × rounds model calls, so compare against cheaper alternatives such as sampling several answers and voting (self-consistency) before adopting debate.

6. When multi-agent helps, and when it just multiplies cost and failure

Anthropic's write-up states the conditions under which its multi-agent approach paid off: tasks valuable enough to justify the token cost, heavy parallelisation, information exceeding a single context window, and interfacing with many complex tools. It names poor fits just as clearly: domains requiring all agents to share the same context, tasks with many dependencies between agents needing real-time coordination, and most coding tasks, which have fewer truly parallelisable parts.

Cognition's essay explains the poor fits with two principles. Share context, and share full agent traces, not just individual messages: a sub-agent that receives only its sub-task misses the decisions and nuances in the rest of the conversation. Actions carry implicit decisions, and conflicting decisions carry bad results: every piece of work embeds choices (style, structure, assumptions), and parallel workers make them independently. Their example: two sub-agents building parts of a Flappy Bird clone return a Super Mario-style background and a bird that does not fit it, leaving the integrating agent an impossible job. Their recommendation is a single-threaded agent with continuous context by default, with a dedicated compression step for very long tasks, which they note is hard to get right.

The two positions are consistent once you separate reads from writes. Parallel agents gathering information (searching, reading, analysing separate sources) make few decisions that conflict, and their outputs can be combined by one owner: Anthropic's case. Parallel agents producing parts of one artefact make coupled decisions that conflict: Cognition's case. A practical rule follows: parallelise exploration and research; keep production of a single coherent output in one agent, or in strictly sequential steps with full context passed along.

7. How multi-agent systems fail

Cemri et al. ("Why Do Multi-Agent LLM Systems Fail?", 2025) analysed more than 1,600 execution traces across seven open-source multi-agent frameworks and built a taxonomy, MAST, of 14 failure modes in three categories, with expert annotators agreeing at a Cohen's kappa of 0.88 (ev5). Specification issues (called system design issues in the abstract) include failing to follow the task or role specification, step repetition, context loss and being unaware of termination conditions. Inter-agent misalignment includes conversation resets, failing to ask for clarification, task derailment, withholding information, ignoring other agents' input, and a mismatch between an agent's stated reasoning and its actions. Task verification includes premature termination and missing or incorrect verification. Their conclusion is that many failures stem from specification and coordination, not raw model capability, and need structural fixes.

The reliability arithmetic of ag1 explains why coordination is fragile. If a result needs all four workers to succeed and each succeeds 90% of the time independently, the chance all four do is 0.94 = 0.66. If the lead checks each worker's output against its brief and re-delegates once on failure (detection plus retry), each worker's effective success rises to 1 − 0.12 = 0.99 and all four reach 0.994 ≈ 0.96. Verification at the boundary is the single most effective coordination control, which matches MAST's third category.

8. Designing the boundaries

If you do build multi-agent, most of the engineering is at the boundaries. Use structured messages: briefs with explicit fields (objective, constraints, output schema, budget) and results with explicit fields (findings, sources, confidence, open questions), so information is not lost in prose. Give each agent its own budget and the lead a total budget, enforced in code. Give each agent least privilege: workers that only read get only read tools. Decide between message passing and a shared blackboard (a store all agents read and write); blackboards make shared context easier and conflicts more likely, so give each agent its own keys. Propagate a trace id through every agent so one run's tree of calls can be inspected (ag14). And put verification at every fan-in: the lead checks each result against its brief before using it.

Is it the architecture or the tokens?

Anthropic's analysis of its research system on the BrowseComp benchmark found that three factors explained 95% of performance variance, and token usage alone explained 80%; the others were the number of tool calls and the model choice. That is both an explanation and a warning. Multi-agent architectures are an effective way to spend more tokens productively, because parallel contexts let a system read far more than one context could hold. But a comparison between a multi-agent system and a single agent with a fraction of the budget mostly measures the budget. The honest baseline is a single agent with the same token and time budget, perhaps with compaction or notes (ag5) to make long runs workable. Only the gap over that baseline is the architecture's contribution.

Implicit decisions and the information bottleneck

Cognition's second principle can be stated in information terms. Each agent makes many small decisions that are not written down: a variable naming scheme, an interpretation of an ambiguous requirement, a source it decided to distrust. A summary passed across a boundary carries only the decisions its writer thought important. Downstream agents then act on a partial picture and make their own, possibly incompatible, decisions. The more coupled the task, the more of those unrecorded decisions matter. Passing full traces reduces the loss but brings back the long context that sub-agents were meant to avoid. This is the central trade-off: isolation buys focus and parallelism by spending shared understanding.

Synchronous orchestration is a bottleneck

In Anthropic's system, the lead waits for all sub-agents of a batch before continuing. That keeps coordination simple, but the slowest sub-agent sets the pace and the lead cannot steer workers mid-flight or start using early results. The post notes that asynchronous execution would allow more parallelism but adds complexity in coordinating results, keeping state consistent and propagating errors. This is ag7's critical-path reasoning applied to agents: synchronous fan-in is easy to reason about and wastes time; asynchronous fan-in is efficient and harder to get right.

Correlated errors make agent votes less informative than they look

Voting and debate assume errors are at least partly independent. With the same model, similar prompts and the same evidence, errors are strongly correlated: if one instance misreads an ambiguous source, the others likely will too. Three agreeing agents are then not three pieces of evidence but roughly one. Measuring this is straightforward: on an eval set, compute how often agents err on the same items compared with what independence predicts. If correlation is high, spend the budget on diversity (another model, retrieval, a tool-based check) rather than on more copies.

Trust between agents is a security boundary

An agent that reads untrusted content can be injected (lm18), and its output then becomes trusted-looking input to the next agent. In a lead–worker system, a worker that reads a malicious web page can return a "summary" containing instructions, which the lead, holding broader tools, may follow. Handoffs can carry injected instructions into an agent with more privileges. The rule from ag10 applies at every boundary: inter-agent messages are data, high-impact tools are guarded by code-level policy regardless of which agent requests them, and a run's exposure to untrusted content is tracked across all its agents.

Deploying long-running multi-agent systems

Multi-agent runs are long and stateful, which makes deployment awkward: a new version of the lead's prompt or the worker's tools can break runs that started on the old version. Anthropic describes using rainbow deployments, keeping old and new versions running side by side and shifting traffic gradually so that in-flight agents finish on the version they started with. Combined with checkpointing so that runs resume after failures rather than restarting (the post notes that minor failures otherwise compound unpredictably in stateful agents), this is ag7's graph-versioning problem at a larger scale, and ag11 covers the durable-execution machinery underneath.

Evaluating at two levels

A multi-agent system needs evaluation of the end result (did the report answer the question correctly, with valid citations?) and of the parts (did each worker follow its brief, did the lead's plan cover the question, did synthesis drop findings?). Anthropic reported that a single LLM judge with a rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) was more consistent than several judges, that starting with about 20 representative queries was enough to see large effects early, and that human testers still caught problems automation missed, such as a preference for SEO-optimised content farms over authoritative sources. Per-agent metrics make failures attributable; end-to-end metrics keep the system honest.

The case: Anthropic's research system versus Cognition's warning

In June 2025 two companies with large agent deployments published opposite-sounding advice a day apart. Cognition's "Don't Build Multi-Agents" (Walden Yan, 12 June) argued from building coding agents that multi-agent architectures are fragile: context is not shared, sub-agents' implicit decisions conflict, and a single-threaded agent with continuous context is more reliable. Anthropic's "How we built our multi-agent research system" (13 June) described a production research feature in which a Claude Opus 4 lead with Claude Sonnet 4 sub-agents outperformed a single Opus 4 agent by 90.2% on an internal research evaluation, cut research time by up to 90% on complex queries through two levels of parallelism, and used about 15 times the tokens of a chat interaction.

Read together, they agree on the boundary. Anthropic itself lists coding and tasks requiring shared context or tight coordination as poor fits, and its system succeeded on breadth-first research, where sub-agents read separate sources and one lead writes the answer. Cognition's failure cases are parallel writes to one artefact. Both emphasise context: Anthropic through detailed delegation specs and condensed, structured returns; Cognition through sharing full traces. And Anthropic's production notes (checkpointing so failures resume rather than restart, full tracing to debug non-determinism, rainbow deployments for long-running agents, and the synchronous-execution bottleneck) describe what it costs to operate such a system once it works.

Failure signatures

Duplicated work: several workers run the same searches; briefs lack boundaries. Gaps: parts of the question no worker covered; the plan was not checked against the question. Conflicting outputs: workers' results contradict or do not fit together; coupled decisions were parallelised. Lost constraints: a requirement stated to the lead never reached the worker that needed it. Agent ping-pong: handoffs back and forth without progress. Over-spawning: many sub-agents for simple requests; missing effort-scaling rules. Summary hallucination: a worker's summary claims findings not in its sources; no verification at fan-in.

What to monitor

Per run: number of agents spawned, steps and tokens per agent, the share of tokens in briefs and summaries (overhead), duplicate tool calls across agents, handoff count, time waiting for the slowest worker, and outcome. Per agent type: brief-compliance rate (from a grader), error and retry rates, and summary length. Fleet-wide: cost per successful task compared with the single-agent baseline, kept running as a shadow comparison on a sample of traffic so you notice when a model upgrade makes the simpler design good enough.

When a multi-agent run goes wrong

Debugging starts from the trace tree: which agent was spawned with which brief, what each returned, and what the lead did with it. Most incidents resolve to one of three answers: the brief was missing a constraint, a worker's summary dropped or invented something, or the lead synthesised past a gap without noticing. Each has a structural fix (brief templates, summary schemas with sources, coverage checks at fan-in) and each deserves a regression case in the eval.

Knobs

Effort-scaling rules (agents and tool calls by complexity); brief templates; summary schemas and length limits; concurrency caps; which model each role uses (a strong lead and cheaper workers is common); verification at fan-in; handoff limits; and the switch that routes simple requests to a single agent. Each is tuned against the end-to-end eval and the per-agent metrics.

Decide: three proposals for multi-agent

Your team proposes three multi-agent designs. For each, decide whether to build it as multi-agent, a single agent, or a workflow, and say why. (a) A due-diligence assistant that, for a target company, investigates its financials, litigation history, leadership, competitors and press coverage, producing a 10-page brief. (b) A feature-building assistant where one agent writes the backend API, another the frontend, and a third the tests, in parallel, for the same feature. (c) A customer-service system with a triage agent that hands off to billing, technical and account agents.

Answer

(a) Multi-agent, orchestrator–worker. The five areas are separable reads from different sources, each larger than fits comfortably in one context, and the value per brief is high. A lead writes a plan and detailed briefs (objective, sources, output schema with citations, effort limit), five workers research in parallel in fresh contexts and return structured findings, and the lead (or a synthesis step) writes the brief from the findings, with a citation-check step. Verify each worker's output against its brief before synthesis. Baseline against a single agent with the same budget on 20 past companies; keep the design only if it wins on quality per dollar or turnaround time.

(b) Single agent, not parallel agents. Backend, frontend and tests for one feature share decisions: data shapes, names, error handling, edge cases. Parallel agents will make those decisions independently and conflict, Cognition's Flappy Bird problem. Use one coding agent with full context, tests as the verifier, and optionally exploration sub-agents that only read (search the codebase, read the API docs) and return summaries. If the work is large, split it sequentially (API contract first, written down, then each part with the contract in context), not in parallel.

(c) A router plus specialised agents is reasonable, but prefer agent-as-tool or a router to free-form handoffs. The request kinds are distinct and need different tools and permissions, which is ag7's routing case. Free-form handoffs between three agents risk ping-pong and lost context. A cleaner design: a router (with fallback) selects one specialised agent per conversation; that agent can call others as tools for sub-questions, keeping control; any handoff passes a structured summary (customer, issue, actions taken), is limited to one or two per conversation, re-authorises tools for the new agent, and escalates to a person when unresolved. Monitor misroutes and repeat contacts per route.
