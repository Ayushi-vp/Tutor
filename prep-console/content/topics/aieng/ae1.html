A small team builds a support assistant in a week. It is ten lines of code around a model API: take the customer's message, send it with a paragraph of instructions, print the answer. In the demo it is impressive. Then it launches to fifty thousand customers, and the problems arrive in a predictable order.

On day one, answers take eight seconds to appear and people close the tab. On day three, the model provider has a forty-minute outage and the assistant shows a stack trace to everyone. In week two, the bill is three times the estimate because a handful of users paste entire contracts into the chat and every follow-up question resends them. In week three, a customer screenshots the assistant confidently promising a refund that the company's policy does not allow, and the screenshot ends up in front of a tribunal. And through all of it, when someone asks "why did the bot say that?", nobody can answer, because nothing recorded which instructions, which documents and which model version produced that particular reply.

That last story is not hypothetical. In Moffatt v. Air Canada (2024), a customer asked the airline's website chatbot about bereavement fares, was told he could buy a full-price ticket and claim the discount within 90 days, and later found the airline's actual policy did not allow claims after travel. The airline argued, among other things, that the chatbot was responsible for its own statements. The tribunal called this "a remarkable submission" and held the airline liable.

None of these failures is about the model being bad. They are failures of the system around the model: no streaming, no fallback, no limits on context, nothing grounding policy answers in policy documents, no tracing. AI engineering is the discipline of building that system, and its first lesson is anatomy: what the parts are, what each is for, and how a request moves through them.

This lesson builds that anatomy from a single request. It starts with the two phases of text generation, because they explain where time goes. Then it walks the stages one at a time: the gateway, the orchestrator and its state, retrieval, the model gateway and router, inference and streaming, output checks, and tracing. It traces one chat request with a timing for every stage, works out why latency percentiles do not add and why availability multiplies, and covers caching, multi-tenancy and agent loops at the senior level. The production section returns to the Air Canada case and asks which layers would have prevented it. Later topics in this track go deep on cost (ae2), monitoring (ae3), structured output (ae4), privacy (ae5), prompts and context (ae6), release engineering (ae7) and classic ML serving (ae8); here you get the map they all hang from.

A restaurant, not a chef

Think of a busy restaurant. The chef is brilliant, fast and creative, and is the reason people come. But a restaurant is not a chef. There is a host who checks reservations and turns people away when the room is full. There is a waiter who takes the order, asks about allergies, and writes a ticket in a standard format. There is a pantry where ingredients are fetched before cooking. There is an expediter at the pass who checks every plate before it leaves the kitchen: right dish, right table, nothing on it that should not be. There is a ticket system that records every order, when it was fired and when it went out, so that when a customer complains the manager can reconstruct what happened. And when the chef is off sick, there is a second cook who can make a simpler version of the menu.

A production LLM application has the same shape. The model is the chef. The gateway is the host: it checks who you are and whether you are allowed in right now. The orchestrator is the waiter plus the pantry: it turns the user's message into a complete, well-formed request for the model, fetching documents, conversation history and tool definitions. The model router decides which cook gets the order. The output checks are the expediter. Tracing is the ticket system. A fallback model is the second cook.

The analogy breaks in one important way, and it is the reason AI engineering exists as a discipline. A good chef is consistent and knows when a dish has gone wrong. A language model is neither. It can produce a different answer to the same request, and it delivers a wrong answer in exactly the same confident tone as a right one. It also remembers nothing between orders: everything it knows about your company, your user and this conversation must be in the ticket. So the system around it has to do work a restaurant does not: supply all the context on every call, check outputs that look fine but are wrong, and record enough to explain any answer later.

The big picture in five moves

First, the request is admitted: the gateway confirms who the user is, whether they are within their limits and whether the request is a sane size. Second, the request is assembled: the orchestrator loads the conversation so far, retrieves documents relevant to the question, and builds the prompt from the system instructions, the retrieved context, the history and the new message. Third, the request is answered: the model gateway sends it to a chosen model, which processes the prompt and generates a reply, possibly calling tools in between. Fourth, the answer is checked and delivered: output checks validate format, citations and safety while the tokens stream back to the user. Fifth, everything is recorded: a trace links every stage so the request can be debugged, its cost attributed and its quality evaluated later.

The requirements that shape every choice

Before designing anything, state the non-functional requirements, because each one pulls the architecture in a direction. Latency: for chat, the first token should appear in well under a second or two, and the whole answer within a few seconds of reading time. Quality: measured on an evaluation set built from real questions, not by impression. Cost: per request and per user per month, with a budget. Reliability: an availability target, and a defined behaviour when the model provider is down. Safety and privacy: what must never be said, and what data must never leave the system. Debuggability: the ability to explain any individual answer. A demo meets none of these by accident; a product meets them by design.

If you stop here, keep this picture: the model is a powerful, unreliable, memoryless component; the application around it admits, assembles, answers, checks and records; and every one of those stages costs time, can fail, and needs to be visible in a trace.

1. What the ten-line demo is missing

Here is the demo, in the shape almost every LLM project starts with:

def answer(user_message):
    resp = client.messages.create(
        model="some-model",
        max_tokens=1024,
        system="You are a helpful support assistant for Acme.",
        messages=[{"role": "user", "content": user_message}],
    )
    return resp.content[0].text

It works, and everything an interviewer will ask about is missing from it. There is no identity: anyone can call it as often as they like, which means anyone can spend your money. There is no memory: the second message in a conversation arrives without the first. There is no knowledge: the model knows nothing about Acme beyond one sentence, so questions about Acme's refund policy are answered from the model's general sense of what refund policies usually say, which is exactly the Air Canada failure. There is no streaming: the user sees nothing until the whole answer exists. There is no timeout, retry or fallback: when the provider is slow or down, so is the product. There is no check on the output. And there is no record of what happened. Each section below adds one of these, and together they are the anatomy.

2. Two phases of generation, and why they decide latency

To understand where time goes, recall how a model produces text (lm5, lm13). Everything is measured in tokens, chunks of text of roughly four characters of English. The model's context window is the maximum number of tokens it can handle in one call, input plus output.

Generation happens in two phases. In prefill, the model reads the entire prompt at once. Because all prompt tokens are known, the computation for them runs in parallel on the GPU, and at the end the model has cached the keys and values for every prompt token and produces the first output token. In decode, the model produces one token at a time: each new token requires a pass through the whole model that reads all the cached state, so tokens come out at a fairly steady rate.

These phases define the two latency numbers that matter. Time to first token (TTFT) is everything before the first output token: network, your own pipeline stages, waiting in the provider's queue, and prefill. Time per output token (TPOT) is the gap between successive tokens during decode. Total time is roughly TTFT + output tokens × TPOT. With a TTFT of 0.6 s, a TPOT of 20 ms and a 250-token answer, the total is 0.6 + 250 × 0.02 = 5.6 seconds. Two conclusions follow immediately. The length of the answer dominates total time, so asking for concise answers is a latency feature, not just a style choice. And the user can start reading after 0.6 seconds if, and only if, you stream.

Prefill time grows with prompt length: a 30,000-token prompt with a whole contract in it takes noticeably longer to prefill than a 3,000-token one, and occupies more GPU memory for its cached state. That is why the amount of context you assemble (section 5) is a latency decision as well as a cost decision.

3. The gateway: who are you, and are you allowed right now?

The API gateway (sc2) is the first service every request reaches. For an LLM product it has four jobs. Authentication: verify the session or API key and attach the user's identity, tenant (the customer organisation they belong to) and permissions to the request, because later stages (retrieval in particular) must only show this user what they are allowed to see. Rate limiting: cap requests per user per minute, and, specific to LLMs, cap tokens per user per day, because one request can cost a thousand times another. A token-based quota stops one user pasting a novel into every message from consuming the whole budget. Validation: reject requests that are too large (a maximum message size in characters or estimated tokens), malformed or obviously abusive before any expensive work happens. Admission under load: when the system is saturated, it is better to reject some requests quickly with a clear "busy, try again" than to accept everything and time out for everyone.

The gateway is cheap (milliseconds) and it is where cost control starts. Many teams also put the first privacy step here: detecting and masking personal data before it reaches logs or the model (ae5 covers how).

4. The orchestrator, and where conversation state lives

The orchestrator is the application code that handles one request end to end: it loads state, runs retrieval and tools, builds the prompt, calls the model, applies checks and returns the stream. It should be stateless: it keeps nothing about a user in its own memory between requests. Conversation history, user preferences and caches live in an external store (Redis for fast session data, Postgres for durable history), loaded at the start of each request and written at the end. Statelessness is what lets you run twenty identical orchestrator instances behind a load balancer, restart any of them during a deploy, and scale up on Monday morning, all without losing a conversation.

A model API is itself stateless: it remembers nothing between calls. So "conversation memory" means the orchestrator resends the history on every turn. That has a cost that grows with the conversation. If each turn adds 150 tokens of user message and 250 of answer, turn 10 carries about 3,600 tokens of history, and turn 40 about 15,600. Every one of those tokens is prefilled (time) and billed (money) on every turn. So the orchestrator needs a history policy: keep the last N turns verbatim, summarise older ones, or retrieve relevant earlier turns. ae6 covers the token budget in detail; the architectural point is that history management is the orchestrator's job, not the model's.

5. Assembling the prompt: retrieval and tools

The prompt the model finally sees is assembled from several sources, usually in this order: the system prompt (the fixed instructions that set role, rules and format), tool definitions, retrieved context, conversation history, and finally the user's new message. Fixed content goes first deliberately: providers offer prefix caching, which reuses the processed state of an unchanged prompt beginning across requests and bills those tokens at a discount (ae2 does the arithmetic), and it only works if the prefix is byte-for-byte identical.

Retrieval (lm9, lm10) gives the model knowledge it does not have. The orchestrator turns the user's question into an embedding (a vector representing its meaning), searches a vector index for the most similar document chunks, often combines that with keyword search, and then reranks the candidates with a slower, more accurate model to keep the best few. For the Air Canada question, retrieval should return the current "Bereavement travel" policy text, and the system prompt should tell the model to answer policy questions only from retrieved policy text and to cite it. Retrieval must also be permission-aware: the search is filtered by the tenant and access rights the gateway attached, so one customer's documents can never appear in another's answer.

Tools (lm16) let the model take actions or fetch live data: look up an order, check a flight's status, create a ticket. The model emits a structured tool call; the orchestrator, not the model, executes it, with the user's permissions, and feeds the result back for another model call. That loop is where agent-style features get expensive and slow, so the orchestrator enforces a maximum number of steps, a deadline and a token budget per request.

6. The model gateway and router

Between the orchestrator and the model providers sits a model gateway: a library or internal service that gives the application one interface to many models. It exists because every concern about calling models is the same across features and should be solved once.

It pins model versions: production code calls a dated model snapshot, never a moving alias, so behaviour does not change underneath you (ae7). It sets timeouts per call, separately for "no first token yet" and "stream stalled". It retries transient failures (network errors, HTTP 5xx, HTTP 429 rate-limit responses) with exponential backoff and jitter (sc12): wait roughly 0.5 s, then 1 s, then 2 s, each randomised, and give up after a small budget. It runs a circuit breaker per provider: after many failures in a short window it stops sending requests there for a while and fails fast, so threads are not tied up waiting on a dead dependency. And it implements fallbacks: if provider A is failing, send the request to provider B or to a self-hosted model whose prompts have been tested.

The model router chooses which model handles each request. The simplest router is a rule (requests from the free tier go to the small model). A better one is a cheap classifier that predicts difficulty: short factual questions to a small fast model, multi-step reasoning to a large one. Because small models are often ten to thirty times cheaper per token, routing is usually the biggest cost lever; ae2 works the numbers, and the warning that comes with it is that a misrouted hard question fails silently, so routing must be evaluated end to end.

7. Inference and streaming

The model itself runs either behind a provider's API or on your own GPUs with a serving engine such as vLLM (lm13). Either way, the response comes back as a stream. Most LLM APIs use server-sent events (SSE): the HTTP response stays open and the server writes a sequence of small events, each carrying the next few tokens, ending with a final event that carries usage counts (input, output and cached tokens). Your orchestrator reads these events and forwards them to the browser, usually as SSE or over a WebSocket.

Streaming has architectural consequences that demos never meet. Every hop between the model and the user must pass chunks through immediately: a reverse proxy or framework that buffers the response "helpfully" turns streaming back into a six-second wait. Load balancers must allow long-lived connections. Errors can now happen mid-answer: the provider can drop the stream after 120 tokens, and the client needs a way to show "the answer was interrupted" rather than a half-sentence presented as complete. And output checks must cope with seeing the answer in pieces, which is the next section.

8. Output checks, and the streaming dilemma

Model output is untrusted until checked. Typical checks: format (if code will parse it, does it match the schema? ae4), grounding (do the cited documents exist, and do they say what the answer claims?), safety (a classifier for content the product must not produce), policy (no promises of refunds or discounts the rules do not allow), and redaction (no personal data that this user must not see). These are often called guardrails.

The dilemma is that the strongest checks need the whole answer, and streaming shows the answer before it is whole. There are three practical answers. Buffer a little: hold back the first sentence or so, check it, then stream the rest with chunk-level checks; this adds a few hundred milliseconds to TTFT. Check as you go and retract: run fast checks on each chunk, and if one fails, stop the stream and replace the partial text with a safe message. Or split by consequence: stream free text, but treat anything that will trigger an action (a refund, an email, a database write) as a structured result that is validated in full before anything happens. The last rule is non-negotiable: nothing consequential should ever act on a partial or unchecked model output.

9. Tracing: being able to answer "why did it say that?"

A trace is the record of one request's path through the system. It is made of spans, each a timed operation (gateway, embed query, vector search, rerank, model call, tool call, output check) with attributes. All spans of a request share a trace id, so they can be assembled into one timeline. OpenTelemetry has standard attribute names for model calls, so traces from different tools line up.

For an LLM application the attributes are what make the trace useful. On the model-call span: model name and pinned version, provider request id, prompt template version, input tokens, cached input tokens, output tokens, latency to first token, total latency and cost. On the retrieval span: the query, the ids and scores of the chunks returned, and the index version. On tool spans: arguments, result size, errors. On the request: the user's tenant, the feature, the route the router chose, which checks fired. With this you can answer the three questions that every incident review asks: what did the model see, which version of everything produced this answer, and what did it cost. Storing full prompts and outputs is powerful and is also a store of user data, so it needs the redaction and retention rules in ae5.

The assistant is a RAG chat with an input safety check. If you wanted the whole answer sooner, the only real lever is fewer output tokens or a faster model.

11. Why latency percentiles do not add

Medians describe a typical request; users and SLOs care about the slow ones. The p95 latency is the time within which 95% of requests finish. It is tempting to give every stage a p95 budget and add them up. That is wrong, and the direction of the error matters.

Each stage's time varies from request to request. The p95 of a stage describes its own bad days. For the whole chain to hit the sum of the p95s, every stage would have to have a bad day on the same request, which is rare if the stages vary independently: the slow vector search on one request is usually paired with a normal rerank. The lab simulates the request above 20,000 times with realistic spread on each stage. The stage p95s add up to about 1,400 ms, but the end-to-end p95 of TTFT is about 1,190 ms. Summing p95s overestimates when stages are independent.

But stages are often not independent, and then the error flips. When the whole system is under load, everything slows together: the vector database, the reranker and the model provider's queue all get busy at the same peak hour. Correlated slowness makes the tail much worse than an independent model predicts. The practical lesson is the same either way: you cannot reason your way to the end-to-end distribution from per-stage numbers; you measure it from traces, and you find the stage that dominates the tail by looking at slow traces, not at averages. In LLM systems that stage is usually the model call, because queueing at the provider varies far more than anything in your own stack.

12. Why availability multiplies

Latency percentiles do not add, but availabilities of hard dependencies (stages the request cannot succeed without) in series do multiply. If the gateway, guardrail service, retrieval, reranker and model provider are each available 99.9% of the time and fail independently, a request succeeds only if all five work: 0.999⁵ = 0.99501, or 99.50%. Over a 30-day month (43,200 minutes) that is about 216 minutes of failure, roughly 3.6 hours, where each component's own SLO promised 43 minutes. To reach 99.9% end to end by tightening components alone, each would need 0.999^(1/5) ≈ 99.98%, five times less downtime per component.

The way out is to break the multiplication. Make stages optional: if the reranker times out, use the vector search's top five; if the guardrail service is down, fall back to a cheaper local heuristic (with care: for some products failing closed, refusing to answer, is the right choice for safety checks). An optional stage no longer appears in the product. Add redundancy to the stages that cannot be optional: two independent providers at 99.9% fail together only 0.1% × 0.1% = 0.0001% of the time, so the model link becomes 99.9999%. With both changes the chain is 0.999 × 0.999 × 0.999999 ≈ 99.80%. And cache: requests answered from a cache never touch the fragile path at all.

13. Caches at three levels

Caching in LLM systems happens at three distinct levels, with different risks. An exact-match cache stores answers keyed on the normalised request (lowercased, whitespace collapsed, plus the user's permission scope); it is safe and helps for repeated questions such as product FAQs. A semantic cache stores answers keyed on the request's embedding and returns a stored answer when a new request is similar enough; it catches paraphrases, and it is dangerous, because "how do I cancel my order" and "how do I cancel my subscription" are close in embedding space and have different answers. Its similarity threshold must be tuned on labelled near-miss pairs, and personalised or time-sensitive answers must never enter it. Prefix caching happens at the model: the processed state of an unchanged prompt beginning (system prompt, tool definitions, a long document) is reused across requests, which cuts prefill time and is billed at a discount. It never returns a wrong answer; it only rewards you for keeping the prompt's fixed part fixed and first. ae2 puts numbers on all three.

Semantic caches need a tested threshold and a scope

A semantic cache turns a similarity score into a decision: above some threshold, reuse a stored answer. The threshold is a classifier boundary, and it should be chosen like one. Collect pairs of real past requests, label whether the same answer is correct for both, and plot the false-hit rate (wrong answer served) against the hit rate as you vary the threshold. A threshold chosen by eye ("0.9 looks safe") often serves wrong answers for short questions, where a single changed word flips the meaning while the embedding barely moves. The cache key must also include everything that changes the right answer: the tenant, the user's permission set, the language, the prompt and model version (so a release invalidates old answers), and for time-sensitive topics the date. Anything personalised ("what's my balance") must bypass the cache entirely. Many teams find the safe hit rate on open-ended chat is low and keep semantic caching for narrow, high-repetition flows like FAQ bots.

Multi-tenancy reaches into every layer

A business product serves many customer organisations (tenants) from shared infrastructure, and isolation has to be enforced at every layer that stores or retrieves content, not just at login. The retrieval index filters by tenant on every query, ideally enforced in the data layer (separate namespaces or mandatory filters) rather than trusted to application code. Caches include the tenant in their keys. Logs and traces are tagged with tenant so deletion requests and access audits work. Rate limits and token quotas are per tenant so one customer's batch job cannot starve the others, which matters doubly on self-hosted GPUs, where a tenant sending 30,000-token prompts consumes prefill capacity that delays everyone else's first token. Cost attribution per tenant is what lets the business price the product.

Bounding agent loops

An agent loop (lm16) multiplies everything: each step is a model call with a growing context, and the number of steps is decided by the model. If a typical request takes 3 steps but 2% of requests wander for 25, those 2% can dominate cost and tail latency. The orchestrator must enforce budgets the model cannot override: a maximum step count, a total token budget, and a wall-clock deadline that is propagated into every tool call (so a tool started at second 28 of a 30-second budget gets 2 seconds, not its default 30). When a budget runs out, the loop returns the best partial answer or an honest "I couldn't complete this" rather than failing silently. Monitoring the distribution of steps per request, not its average, is how you catch a prompt change that makes the agent loop.

Retries, idempotency and side effects

Retrying a model call that only produces text is harmless apart from cost. Retrying a step that performs an action is not. If the model's tool call says "issue a refund of $50" and the orchestrator's connection to the payments service times out after the refund was applied, a naive retry refunds $100. Tools with side effects need idempotency keys: the orchestrator generates a unique key per intended action (for example the trace id plus the step number), the downstream service records which keys it has executed, and a repeated request with the same key returns the original result instead of acting again. The same thinking applies to user-level retries: a user who presses "regenerate" should not trigger the action twice.

Tail latency: hedging and timeouts

When the model call dominates the tail, two techniques from large-scale systems apply. A hedged request sends a duplicate to a second replica or provider if the first has not produced a first token within, say, the p90 time, and uses whichever answers first. It cuts tail latency substantially at the cost of a few percent extra load, but with paid APIs the duplicate is billed, so hedge only on the first-token wait (cancel the loser immediately) and only when the extra cost is worth it. Timeouts should be separate for time to first token and for gaps between chunks: a stream that has delivered 200 tokens and then stalls for 20 seconds is a failure, even though a total-time timeout of 60 seconds has not fired.

Rate limits are a capacity plan

Providers limit each account to some number of requests and tokens per minute. Those limits are your real capacity ceiling, and they behave like any shared resource: near the limit, 429 errors rise, retries add load, and latency climbs. Treat the provider limit as a capacity plan. Track headroom (tokens per minute used versus allowed) as a metric with an alert, smooth bursty background work through a queue so it never competes with interactive traffic, and keep interactive and batch workloads on separate keys or projects so a nightly summarisation job cannot cause daytime chat failures.

The model is an untrusted component

The unifying principle at the senior level is that the model's output is untrusted input to the rest of your system, for two reasons. It can be wrong (lm15): a fluent, confident answer about a refund policy that does not exist. And it can be steered (lm18): text in a retrieved document or a user message can instruct it. So the system never lets model output alone make a consequential decision. Policy facts come from retrieved, versioned sources and are checked against them. Actions require validated structured calls, permission checks done by the orchestrator with the user's own rights, and confirmation for anything irreversible. High-stakes topics have deterministic answers or human escalation. This is what the Air Canada tribunal effectively demanded: whatever the chatbot says, the company has said.

Configuration is part of the release

An LLM application's behaviour depends on far more than its code: the prompt templates, the pinned model versions, sampling parameters, retrieval settings (chunk size, number of chunks, reranker), the embedding model and index version, tool schemas and guardrail thresholds. Any of them can change answers. Mature teams bundle all of them into one versioned release, stamp the release id on every trace, and roll changes out gradually with evaluation gates. That process is the subject of ae7; the architectural requirement here is only that these settings live in versioned configuration, not scattered through code and dashboards.

Failure modes you will meet

Provider degradation. The symptom is rising TTFT, more HTTP 429 and 5xx errors, and streams that stall. It is often partial: one region, one model, one account's rate limit. The trace breakdown shows the model span growing while your own stages are flat. Mitigations are the model gateway's job: circuit breaker, fallback provider, shedding low-priority traffic, and a status banner rather than errors.

Context bloat. Prompt sizes creep upward: longer histories, more chunks "for safety", a new tool definition. Cost and TTFT rise together, slowly enough that no single deploy looks guilty. The signal is input tokens per request, tracked per feature over weeks, and the fix is an explicit token budget (ae6).

Runaway loops and retries. An agent that does not converge, or a retry policy without a budget, multiplies calls. The signal is calls per request and the tail of steps per request; the fix is hard budgets and alerts on cost per hour.

Silent quality regressions. A prompt tweak, a model version change or a re-built index changes answers without any error. Nothing in system metrics moves. The signals are evaluation scores on sampled traffic, user feedback, escalation rates and guardrail trigger rates (ae3), and the defence is release gating (ae7).

Ungrounded consequential answers. The model answers a policy or pricing question from its general knowledge instead of your documents, and a customer acts on it. Nothing errors; the first signal may be a complaint. That is the Air Canada case.

The case: Moffatt v. Air Canada (2024)

The facts are set out in the Civil Resolution Tribunal of British Columbia's decision of 14 February 2024. After his grandmother died in November 2022, Jake Moffatt used the chatbot on Air Canada's website while researching flights. The chatbot's answer, which he screenshotted, said that Air Canada offers reduced bereavement fares and that "If you need to travel immediately or have already travelled and would like to submit your ticket for a reduced bereavement rate, kindly do so within 90 days of the date your ticket was issued by completing our Ticket Refund Application form." The words "bereavement fares" in the answer linked to Air Canada's "Bereavement travel" page, which said the policy did not apply to requests made after travel was completed. Relying on the chatbot, he bought a Vancouver to Toronto flight for $794.98 and a return for $845.38, then applied for the reduced rate within the 90 days. Air Canada refused; in February 2023 a representative admitted the chatbot had provided "misleading words" and said the airline would update it.

Before the tribunal, Air Canada argued it could not be held liable for information provided by its agents, servants or representatives, including a chatbot. Tribunal member Christopher Rivers wrote that in effect "Air Canada suggests the chatbot is a separate legal entity that is responsible for its own actions. This is a remarkable submission. While a chatbot has an interactive component, it is still just a part of Air Canada's website. It should be obvious to Air Canada that it is responsible for all the information on its website. It makes no difference whether the information comes from a static page or a chatbot." The tribunal found the airline had not taken reasonable care to ensure the chatbot was accurate, and did not accept that a customer should have to double-check one part of the website against another. It found the bereavement fares would have cost $979.48 against the $1,630.36 paid, and ordered Air Canada to pay $812.02: $650.88 in damages, $36.14 in pre-judgment interest and $125 in tribunal fees.

The money is small; the principle is not. Read as an architecture review, the chatbot answered a consequential policy question in a way that contradicted the company's own policy page, and nothing in the system caught it. The layers in this lesson map directly onto what would have: retrieval of the current policy text with the instruction to answer only from it; an output check that the answer's claims are supported by the cited passage (the passage said the opposite); a deterministic answer or a human handoff for refund-eligibility questions; an evaluation set of policy questions run before every change; and traces recording which policy version each answer used, so the error could be found and fixed across all affected conversations, not just the one that reached a tribunal.

What to watch on a dashboard

For each feature: request rate; TTFT and total latency at p50, p95 and p99, broken down by stage from traces; error rate split by cause (provider 5xx, 429, timeout, guardrail block, validation failure); fallback and retry rates; input, cached and output tokens per request; cost per request and per tenant per day; cache hit rates at each level; calls per request for agent features; and the quality signals from ae3 (feedback, escalations, sampled evaluation scores). Alert on rates of change, not only absolute values: a fallback rate that goes from 0.1% to 5% is an incident even though 95% of requests still succeed on the primary path.

Knobs people actually turn

Maximum output tokens per feature, which bounds both cost and the length of the tail. Number of retrieved chunks and reranker candidates, trading quality against TTFT. History window and summarisation policy. Router thresholds that decide what goes to the large model. Timeout values for first token and for stalls. Per-tenant token quotas. Guardrail strictness, which trades false refusals against misses. Each of these is configuration, versioned with the release, and changed with an evaluation run behind it.

Goal: simulate the chat request from the body 20,000 times with realistic variation per stage, see that stage p95s do not add up to the end-to-end p95, see how much of total time is decode, and check the availability arithmetic. Standard library only; Python 3.12.

import random, statistics

random.seed(7)

# median latency (ms) and spread of each stage on the path to the FIRST token
STAGES = [                      # (name, median ms, lognormal sigma)
    ("gateway (auth, rate limit)", 15, 0.3),
    ("input guardrail",            40, 0.4),
    ("embed query",                30, 0.4),
    ("vector search",              45, 0.5),
    ("rerank",                     90, 0.5),
    ("prompt assembly",             5, 0.2),
    ("queue + prefill (TTFT)",    350, 0.6),
]
DECODE_MS_PER_TOKEN, OUT_TOKENS = 20, 250   # streaming: user reads while these arrive

def sample(median, sigma):
    return median * random.lognormvariate(0, sigma)

def p(xs, q):
    xs = sorted(xs)
    return xs[int(q * (len(xs) - 1))]

N = 20_000
per_stage = {name: [] for name, _, _ in STAGES}
ttft, total = [], []
for _ in range(N):
    t = 0.0
    for name, med, sig in STAGES:
        d = sample(med, sig)
        per_stage[name].append(d)
        t += d
    ttft.append(t)
    total.append(t + DECODE_MS_PER_TOKEN * OUT_TOKENS)

print(f"{'stage':28s} {'p50':>6s} {'p95':>6s}")
for name, xs in per_stage.items():
    print(f"{name:28s} {p(xs, .5):6.0f} {p(xs, .95):6.0f}")
print(f"{'sum of stage p95s':28s} {'':6s} {sum(p(x, .95) for x in per_stage.values()):6.0f}")
print(f"{'TTFT (end to end)':28s} {p(ttft, .5):6.0f} {p(ttft, .95):6.0f}")
print(f"{'full answer (250 tokens)':28s} {p(total, .5):6.0f} {p(total, .95):6.0f}")

# availability: five hard dependencies in series vs. making two of them optional
a = 0.999
hard = a ** 5
soft = a ** 3                          # rerank and guardrail-classifier degrade instead of failing
fallback = 1 - (1 - a) ** 2            # two independent LLM providers
print(f"\n5 hard deps at 99.9%: {hard:.4%}  (~{(1 - hard) * 30 * 24 * 60:.0f} min/month down)")
print(f"3 hard deps:         {soft:.4%}  (~{(1 - soft) * 30 * 24 * 60:.0f} min/month down)")
print(f"3 hard, LLM with fallback: {a ** 2 * fallback:.4%}")

What to look for. The end-to-end TTFT p95 (1,191 ms) is well below the sum of the stage p95s (1,401 ms), because stages rarely all have a bad moment on the same request; and the model's queue and prefill stage alone contributes most of the tail. The full answer is about ten times TTFT, which is the case for streaming. Then experiment: change the model stage's sigma from 0.6 to 1.0 and watch the end-to-end p95 follow it; make the guardrail run in parallel with retrieval (take max of the two branches instead of adding) and measure the saving; or add a shared "load" factor that multiplies every stage on the same request, and see the end-to-end tail grow past the sum of p95s once slowness is correlated.

Work it out

A support assistant's request passes through gateway → input guardrail → retrieval → reranker → LLM provider. Each is independently 99.9% available. (a) What is the end-to-end availability, and how much downtime a month is that? (b) What would each component need for 99.9% overall? (c) Redesign so the product reaches at least 99.8% without improving any component. (d) The team also proposes a latency SLO by summing each stage's p95. What is wrong with that?

Answer

(a) Serial hard dependencies multiply: 0.999⁵ = 0.99501, or 99.50%. A 30-day month has 43,200 minutes, so 0.499% is about 216 minutes, roughly 3.6 hours, against the 43 minutes each component's SLO suggests.

(b) 0.999^(1/5) ≈ 0.99980: 99.98% each, which allows about 9 minutes of downtime a month per component instead of 43. Chains are expensive to make reliable component by component.

(c) Change the structure. Make the reranker optional (on timeout, serve vector search's top five) and give the guardrail a degraded mode (a local heuristic check), so neither is a hard dependency. Add a second LLM provider with prompts tested on it: if failures are independent, 1 − 0.001² = 99.9999% for that link. The chain is then gateway × retrieval × model ≈ 0.999 × 0.999 × 0.999999 ≈ 99.80%. Add caching for repeated questions and some traffic avoids the chain entirely. State the caveat: provider failures are not fully independent (shared cloud regions, your own network), so measure correlated failures.

(d) Percentiles do not add. If stages vary independently, the sum of p95s overstates the end-to-end p95 (in this lesson's simulation, 1,401 ms summed versus 1,191 ms measured), because it is rare for every stage to be slow on the same request. If stages slow down together under load, the true tail can exceed the sum. Either way the SLO must be set on the measured end-to-end distribution from traces, with per-stage budgets used only as guides for where to look.
