An accounts-payable team automates invoice entry. A language model reads each scanned invoice and returns the vendor, date, total, currency and purchase-order number as JSON, which a script loads into the finance system. In testing on fifty invoices it is flawless. In the first week of production it processes 40,000. About 400 crash the loader: some answers are wrapped in markdown code fences, some have a trailing comma, some give the total as "£1,240.50" instead of a number, one says the date is "3rd March". That is the visible failure, and it is the easy one, because a crash is noticed.

The invisible failure is worse. Among the invoices that loaded successfully, a few hundred have a purchase-order number that does not appear anywhere on the document: the model filled the field because the format seemed to want a value. A few dozen have the right total in the wrong currency. They pass every check because they are perfectly formatted, and they are paid.

This is the core problem of structured output. A language model produces text one token at a time from probabilities; nothing in that process knows about your schema unless you make it. Code downstream, on the other hand, needs exact contracts: these keys, these types, these allowed values, every time. Bridging the two is one of the most common tasks in AI engineering (extraction, classification, routing, form filling, tool calls in agents all depend on it), and one of the most common interview topics, because it tests whether a candidate understands both how generation works and how production systems fail.

The stakes grow with agents. When a model's structured output is not a record to be filed but a tool call to be executed (issue a refund, send an email, update a customer record), a malformed object is a crashed workflow and a valid object with a wrong value is an action taken on the wrong thing. The same engineering that makes invoice extraction reliable is what makes tool use safe enough to ship, which is why the topic sits at the centre of every agent design review.

This lesson starts from what JSON and JSON Schema are, then climbs a ladder of reliability: prompting with examples, validating and retrying (with the failure rate and expected cost of a retry loop worked by hand), native tool calling, and constrained decoding, with the logit mask worked on a single generation step. Then it covers schema design, semantic validation that catches valid-but-wrong output, field-level evaluation, streaming and tool-call safety. The public case is OpenAI's 2024 launch of Structured Outputs, which published how far prompting alone falls short and how constrained decoding closes the gap.

A form with boxes, not a blank page

Ask a new colleague to "write down the invoice details" and you get a paragraph, a list, perhaps a note about the coffee stain. Give them a printed form with labelled boxes (vendor, date as DD/MM/YYYY, total, a tick box for the currency) and you get something a clerk can type in without reading it twice. The form does not make the colleague more accurate about the numbers; it makes their answer usable. It also gives absence a place: a box labelled "PO number (write NONE if absent)" stops people inventing one to fill the space.

Structured output is the form for a language model. The format is usually JSON (JavaScript Object Notation), a text format of objects written in braces, with keys in quotes, values that are strings, numbers, true/false, null, arrays or nested objects:

{"vendor": "Acme Ltd", "invoice_date": "2026-03-03", "total": 1240.5,
 "currency": "GBP", "po_number": null}

The boxes and their rules are the schema, usually written in JSON Schema, a standard for describing which keys must be present, what type each value has, which values are allowed (an enum such as GBP, EUR or USD) and whether extra keys are permitted. In Python, libraries such as Pydantic let you write the schema as a class and generate the JSON Schema from it.

The analogy breaks in an instructive way. A person filling in a form can see all the boxes at once and plan. A language model writes left to right, one token at a time, and at each step simply picks a likely next token. Nothing stops it writing a quote where a number belongs, closing the object early, or adding a friendly sentence before the brace, unless the generation process itself is constrained. That is why there is a ladder of techniques, and why the top rung works differently from the others.

Where each defence sits in a request

It helps to picture the techniques on the request path from ae1. Before the call, the orchestrator puts the schema and a couple of examples into the prompt (rung one) and, if the provider supports it, passes the schema to the API with strict mode on (rung four), or declares it as a tool (rung three). During the call, a constrained decoder inside the provider's inference engine filters every token. After the call, the orchestrator checks the stop reason (was the output cut off, or refused?), parses and validates against the schema even when strict mode was on (cheap insurance, and essential when it was not), runs semantic checks against its own data, and only then lets anything act on the result. If validation fails, the repair loop (rung two) goes back to the model with the error; if that fails too, the request goes to a fallback: a stronger model, a human queue, or an honest error. Every one of those outcomes is logged with the schema, prompt and model versions, because a rising failure rate is usually the first sign that something upstream changed.

If you stop here: give the model a schema, enforce it with constrained decoding when the provider or engine supports it, validate anyway, give absence an explicit legal value, and remember that a valid object can still be wrong, so check its values against your own data before anything acts on it.

1. The contract: JSON Schema in five minutes

A JSON Schema is itself a JSON document. For the invoice, a minimal one says the output is an object with five keys, all required, no others allowed, with types and allowed values:

{
  "type": "object",
  "properties": {
    "vendor":       {"type": "string"},
    "invoice_date": {"type": "string", "format": "date"},
    "total":        {"type": "number"},
    "currency":     {"type": "string", "enum": ["GBP", "EUR", "USD"]},
    "po_number":    {"type": ["string", "null"]}
  },
  "required": ["vendor", "invoice_date", "total", "currency", "po_number"],
  "additionalProperties": false
}

Read it line by line. type fixes the kind of value. format: date asks for an ISO date (YYYY-MM-DD). enum limits currency to three values. po_number may be a string or null, so absence has a legal representation. required lists keys that must appear, and additionalProperties: false forbids any other key. In Python the same contract is a Pydantic class with five typed fields; the library generates this schema and validates data against it, returning precise errors.

2. Three layers of failure

Output can fail the contract at three levels, and each level needs a different defence. Syntax: the text is not parseable JSON at all, because of a markdown code fence around it, a trailing comma, a comment, an unescaped quote inside a string, a sentence before the brace, or truncation when generation hit the token limit mid-object. Schema: the JSON parses but breaks the rules: a missing key, an extra key, a total that is the string "£1,240.50", a currency of "£" or "pounds", a date of "3rd March". Semantics: everything is valid and the values are wrong: the total of a different invoice on the same page, a date in the wrong year, a purchase-order number that does not exist, a currency inferred from the vendor's country rather than read from the document.

The ladder's first three rungs reduce syntax and schema failures; constrained decoding eliminates them. Nothing in the ladder addresses semantics, which is why section 8 exists.

3. Rung one: prompting and tolerant parsing

The baseline is to describe the format in the prompt and show it. Put the schema (or a compact description) in the system prompt, give two or three examples including the awkward cases (a document with no PO number showing null, a total with a currency symbol in the source becoming a plain number), say "return only the JSON object", and set temperature to 0 for extraction. Some APIs let you prefill the start of the response with {, which stops preambles.

Then parse tolerantly but not loosely. Strip a surrounding code fence, which is the single most common harmless failure. Do not try to "fix" broken JSON with regular expressions beyond that: a parser that guesses where a missing quote goes produces wrong data silently. Check the stop reason in the response: if generation stopped at max_tokens, the object is truncated and should be treated as a failure, with a larger limit or a smaller task.

4. Rung two: validate and retry, with the arithmetic

Whatever comes back is validated against the schema. If it fails, a repair prompt sends the original request, the invalid output and a short error written for the model ("total has the wrong type (str); total must be a number like 1240.5"), and asks for a corrected object. This catches most failures, at a cost in money and latency that is easy to work out.

Take an extractor on Claude Haiku 4.5 ($1 per million input tokens, $5 per million output). Each attempt sends 1,500 input tokens and returns 200 output tokens: 1,500 × 1 / 10⁶ + 200 × 5 / 10⁶ = $0.0015 + $0.0010 = $0.0025. A repair sends the original 1,500 tokens plus the 200-token bad output plus a 50-token error: 1,750 input tokens and another 200 output, $0.00275. Suppose traffic is 97% easy documents that fail 0.5% of the time and 3% hard ones (poor scans, unusual layouts) that fail 20% of the time. The first-attempt failure rate is 0.97 × 0.005 + 0.03 × 0.20 = 0.00485 + 0.006 = 1.085%.

Now the crucial modelling choice: are repair attempts independent of the first failure? They are not. An easy document that failed by bad luck is usually fixed by one repair (say 90% of the time), but a hard document fails for a reason the model will meet again (say repairs work only half the time). After one repair, failures are 0.00485 × 0.10 + 0.006 × 0.50 = 0.000485 + 0.003 = 0.35%; after two, 0.0000485 + 0.0015 ≈ 0.15%; after three, about 0.08%. At 500,000 requests a day that is roughly 5,400 failures with no retries, 1,750 with one, 775 with two and 390 with three. The lab's simulation gets 1.10%, 0.35%, 0.15% and 0.08%. Notice two things: the residual failures are almost all hard documents, so each extra retry only halves them, and if failures had been independent at 1.085% with a 90% repair rate you would have predicted 0.11% after one retry and 0.01% after two, an optimistic answer by an order of magnitude.

The expected cost is the first attempt plus the probability of each repair times its cost: $0.0025 + 0.01085 × $0.00275 + 0.0035 × $0.00275 ≈ $0.00254, under 2% extra. Money is not the problem with retries. Latency is: a repair is a whole extra model call, perhaps another two seconds, and it lands on about 1% of requests, which is exactly the p99. And the leftover failures still need a destination: a human review queue, escalation to a stronger model, or a clearly reported error, never a silent drop.

5. Rung three: native tool calling

Most model APIs support function (tool) calling (lm16): you declare a function with a name, a description and a JSON Schema for its arguments, and the model returns a structured call instead of free text. Models are trained heavily on this format, so it is more reliable than JSON described in a prompt, and it gives you a clean place for the arguments that the API returns already parsed. Even when you do not want to "call" anything, declaring a single record_invoice tool and requiring the model to use it is a common way to get structured output. Without strict mode it is still probabilistic: arguments can miss required fields or have wrong types, so validation stays.

6. Rung four: constrained decoding, worked on one step

Recall how generation works (lm8). At each step the model produces a logit, a raw score, for every token in its vocabulary, typically 100,000 or more; these become probabilities and one token is sampled. Constrained decoding inserts a filter between the logits and the sampling: any token that would make the output impossible to complete validly gets its logit set to minus infinity, so its probability becomes zero, and the remaining probabilities are renormalised to sum to 1.

Work one step. The schema is an object with one required key, value, of type number. The model has generated {"value": so far. Its five most likely next tokens are a double quote " at 0.40 (it is about to write the number as a string), 12 at 0.30, null at 0.15, 1 at 0.10 and } at 0.05. The grammar says a number must come next: a digit or a minus sign. The quote, null (not allowed: the type is number, not nullable) and the closing brace (the value is required) are masked. The two digit tokens remain with 0.30 and 0.10, which renormalise to 0.30 / 0.40 = 0.75 and 0.10 / 0.40 = 0.25. The model's strongest preference, which would have produced "12" as a string and failed validation, is now impossible.

Doing this efficiently is the hard part. The set of valid next tokens depends on everything generated so far, tokens are multi-character fragments that can straddle grammar boundaries (a single token might be {" or val), and the check must run for a 100,000-token vocabulary at every step without slowing generation. Engines therefore compile the schema once into a grammar and an index over the vocabulary. Willard and Louf (2023) showed how to do this with a finite-state machine indexed over the vocabulary, at O(1) average cost per token; this is the approach behind the Outlines library. A finite-state machine can enforce regular structure but not unlimited nesting, so engines that need recursive schemas use a context-free grammar (CFG), which can describe arbitrarily nested brackets; XGrammar is a widely used fast CFG engine. Hosted APIs do the same behind a flag: OpenAI's structured outputs and strict tools, Anthropic's JSON outputs and strict tool use.

7. What constrained decoding does not fix

The provider documentation is explicit about the gaps, and interviewers like candidates who know them. Refusals: if the model declines a request for safety reasons, the refusal takes precedence over the schema; it is reported separately (a refusal flag, or a stop reason of "refusal") and must be handled as its own outcome. Truncation: if generation hits max_tokens before the object closes, the output is incomplete and invalid; check the stop reason. First-request latency: each new schema must be compiled; OpenAI said typical schemas take under 10 seconds the first time and complex ones up to a minute, and Anthropic caches compiled grammars for 24 hours from last use, so frequently changing schemas pay the cost repeatedly. Supported subset: providers support only part of JSON Schema. Anthropic, for example, rejects recursive schemas, numeric limits such as minimum and maximum, string length limits and most array-length constraints, requires additionalProperties: false, and outputs required properties before optional ones. Constraints the engine cannot enforce must be checked afterwards. And, always, values: the guarantee is about form, not truth.

8. Semantic validation: valid but wrong

After the object is structurally valid, check that its values make sense, using rules and data the model does not have. Cross-field rules: line items sum to the total within rounding; the due date is after the invoice date. Lookups: the vendor exists in your vendor master; the PO number exists and belongs to that vendor; the product id is a real product. Plausibility: the date is not in the future or decades in the past; the amount is within the usual range for this vendor. Source grounding: for high-value fields, check that the extracted string actually appears in the document text (a cheap test that catches invented PO numbers). Permissions: for tool calls, the user is allowed to do this to this object.

Failures here can go back to the model with an actionable message ("the line items sum to 1,180.50 but total is 1,240.50; re-read the total") or straight to a human queue when the model cannot know the answer. Either way, log which rule failed: the distribution of failing rules is the best map of where the extraction is weak.

9. Measuring extraction quality per field

Aggregate "accuracy" hides the field that is always wrong. Evaluate each field separately on a labelled set. Strings and dates use exact match after normalisation; numbers use a tolerance; enums use a confusion matrix (how often EUR is read as GBP). Nullable fields need three numbers, because there are two ways to be wrong. Work an example: 200 labelled invoices, 120 with a PO number and 80 without. The model outputs a PO number on 128 of them: 110 correct, 6 wrong values on invoices that have one, and 12 invented values on invoices that have none; on the other 72 it outputs null (4 misses where a PO existed, 68 correct nulls).

  • Precision of non-null outputs: 110 / 128 = 85.9%: when it gives a PO number, it is right 86% of the time.
  • Recall: 110 / 120 = 91.7%: it finds 92% of the PO numbers that exist.
  • Invention rate on absent fields: 12 / 80 = 15%: on invoices with no PO number, it makes one up 15% of the time.

The third number is the one finance cares about, and it is invisible to schema validation and to recall. It is also the one most improved by schema design: a required field with an explicit null, an instruction that null is expected and acceptable, and an example with null in the prompt. A source-grounding check (does the string appear in the document?) catches most of the rest.

10. Putting it together: one extraction call

Here is the whole pattern in provider-neutral Python, the shape that most production extractors converge on. The model call is a placeholder for whichever SDK you use; the structure around it is the point.

def extract_invoice(doc_text, max_repairs=1):
    messages = build_prompt(doc_text)                     # schema + examples, null allowed
    for attempt in range(max_repairs + 1):
        resp = call_model(messages, schema=INVOICE_SCHEMA, strict=True)
        if resp.stop_reason == "refusal":
            return route_to_human(doc_text, reason="refusal")
        if resp.stop_reason == "max_tokens":
            return route_to_human(doc_text, reason="truncated")
        record, error = validate_schema(resp.text)        # insurance even in strict mode
        if record is not None:
            error = semantic_check(record, doc_text)        # totals, lookups, grounding
            if error is None:
                return record
        messages = add_repair_turn(messages, resp.text, error)
    return route_to_human(doc_text, reason=error)

Four details carry the weight. Refusals and truncation are handled as their own outcomes, before parsing, because they are the documented exceptions to the schema guarantee. Schema validation runs even with strict mode, because it costs microseconds and protects you if a model, schema or provider setting changes. Semantic checks share the repair loop, so a total that does not match the line items gets one chance at correction with a specific error. And every exit that is not a clean record goes to a human with a reason, so nothing is dropped silently and the reasons can be counted on a dashboard.

11. Streaming structured output

Users do not want to wait for a 600-token object to finish before seeing anything. A partial JSON parser reads the stream as it arrives and exposes fields as they complete, so a UI can fill in the vendor and date while the line items are still being generated. Because generation order follows schema order (with the provider-specific caveat that required properties may be emitted before optional ones), put the fields the user needs first at the top. Validate the complete object at the end and correct the display if needed, and never let a partial object trigger an action.

Format constraints and reasoning quality

Forcing a model into a format from its first token changes what it computes. Tam et al. (2024) compared the same tasks with free-form answers and with format restrictions (JSON, XML, YAML, and format-restricting instructions) and found a significant decline in reasoning ability under format restrictions, with stricter constraints generally hurting more. The mechanism is intuitive: a model that would have reasoned for a paragraph before answering is pushed straight into producing a value. Three mitigations work. Let the model reason first, in a thinking block or a free-text field placed before the answer fields, because left-to-right generation means early fields can inform later ones; a "reasoning" field after the "answer" field is a justification written after the fact. Split the task: one call reasons and answers in free text, a second cheap call (or a parser) converts the answer into the schema. Keep the reasoning short and on task; Anthropic's documentation warns that a schema property asking for the model's step-by-step reasoning can trigger a refusal and recommends asking for a short explanation instead.

Why tokens make grammar enforcement hard

A grammar is written over characters, but the model emits tokens, and the two do not align. One token might be {" (two grammar symbols), another value (part of a key), another ":. The engine must know, for each grammar state, which tokens can be consumed entirely, or partly with a valid continuation. Naively that means checking every vocabulary entry against the grammar at every step: 100,000 string checks per token. The insight of Willard and Louf was to precompute, for each state of the grammar's automaton, the set of tokens that can follow, so the per-step work becomes a lookup. CFG engines extend this with a stack for nesting and handle the tokens whose validity depends on the stack separately. There is also a subtle quality issue: forcing a tokenisation the model would not naturally use (splitting a word into unusual tokens because the grammar boundary falls mid-token) can push the model off its training distribution. Good engines allow tokens that cross boundaries so the model can use its natural tokenisation.

Enums, descriptions and the size of the choice

Enums are the most effective constraint in a schema: they turn free text into a classification, make evaluation easy (a confusion matrix) and remove spelling variants. Their failure mode is size and ambiguity. A 300-value enum of product categories is hard for the model to choose from well and hard for you to evaluate. Split it hierarchically (category, then subcategory in a second step) or let retrieval narrow the candidates first. Make values self-describing and mutually exclusive, and put short definitions in the field description, because the description is the model's only documentation. Include an explicit "other" or "unknown" value so the model has a legal answer when nothing fits; otherwise it is forced to pick the nearest wrong one.

Schema evolution and versioning

A schema is an API between the model step and downstream consumers, and it changes: new fields, renamed enum values, a field that becomes nullable. Treat it like any API contract (swe7). Version it, keep old consumers working (add fields rather than rename them), and stamp the schema version on every output and trace. On the model side, a schema change is a prompt change: it changes behaviour and must go through evaluation (ae7). With hosted constrained decoding it also has an operational cost: a new schema compiles on first use, and changing the output format can invalidate prompt caches.

Tool-call robustness

Tool calls are structured output whose consequence is an action. Beyond schema enforcement, the application must treat arguments as untrusted (lm18): validate them against business rules and the requesting user's permissions in code; require explicit confirmation for irreversible or high-value actions; use idempotency keys so that a retried call does not repeat a payment or an email; and return errors the model can act on ("order 1234 is already shipped; cancellation is not possible, offer a return instead") rather than generic failures. Some providers do not apply strict schemas to parallel tool calls (OpenAI's launch post said structured outputs were not compatible with parallel function calls), so check before relying on it in agents.

Long documents and per-field provenance

Extraction from a 60-page contract does not fit the "one call, one object" pattern. Split the document into sections, extract candidate values per section with the location they came from (page and character offsets), then merge with explicit rules (latest amendment wins; conflicting values go to review). Keep the provenance in the output: a field with a citation can be verified by a reviewer in seconds, and the source-grounding check becomes trivial. Confidence per field, from the model's log-probabilities where available or from agreement between two extractions, lets you route only uncertain fields to humans instead of whole documents.

Self-hosted engines

When you serve open models yourself (lm13), constrained decoding comes from the serving engine or a library: vLLM and SGLang integrate grammar backends such as XGrammar and Outlines, and llama.cpp supports grammars natively. The trade-offs to know are compile time for complex schemas (cache compiled grammars by schema hash), per-token overhead under large batches (engines differ, so benchmark at your batch size), and interaction with speculative decoding, where draft tokens must also be checked against the grammar.

Failure modes in production

Format drift after a model change. A model update changes formatting habits: JSON now arrives inside code fences, or the model adds a sentence before it. Without constrained decoding the parse-failure rate jumps overnight. The GPT-4 drift study (ae3) saw exactly this with code: a June 2023 version wrapped code in markdown fences and directly executable outputs fell from over 50% to 10%. Pin versions, parse tolerantly for fences, alert on parse-failure rate per model version, and move to strict schemas.

Truncation on long outputs. A batch of large documents produces objects that end mid-array. The stop reason says max_tokens, but nobody checks it, and a lenient parser "repairs" the truncated JSON by closing brackets, silently dropping line items. Treat max_tokens as failure, size limits per document type, and split long extractions.

Invented values. Schema-valid, plausible, wrong. The signal is semantic checks failing (lookups that find no such PO), source-grounding failures, and field-level evaluation on a labelled weekly sample. The fix is schema design (explicit nulls), grounding checks and human review for high-value fields.

Retry storms. A prompt change raises the first-attempt failure rate from 1% to 15%; every failure triggers up to three repairs; call volume rises 30% and latency at p95 doubles, while the final failure rate looks fine. Alert on retries per request, not only on final failures.

The case: OpenAI's Structured Outputs launch (August 2024)

On 6 August 2024 OpenAI introduced Structured Outputs in its API and, unusually, published both its measurements and its implementation approach. On its evaluations of complex JSON Schema following, gpt-4-0613 with prompting alone scored less than 40%. The company then trained a new model, gpt-4o-2024-08-06, to understand complicated schemas; it reached 93% on the same benchmark. OpenAI's own conclusion is the lesson of this topic: "despite this model's performance improvements (93% on our benchmark), it still did not meet the reliability that developers need to build robust applications." So it added a deterministic engineering layer, and with Structured Outputs (strict mode) the model scored a perfect 100%.

The post describes the mechanism: constrained decoding, in which after every token the inference engine determines which tokens are valid next and masks the rest, lowering their probability to zero. The schema is converted into a context-free grammar (chosen over finite-state machines because CFGs can express nested and recursive structures), preprocessed once and cached. That preprocessing is why "the first request with a new schema incurs a latency penalty": typical schemas under 10 seconds, complex ones up to a minute. The post also listed the limits that this lesson's body walks through: only a subset of JSON Schema; the model can still fail to follow the schema if it refuses an unsafe request (flagged with a refusal field) or if generation reaches max_tokens first; structured outputs do not prevent mistakes in the values, such as a wrong step in a calculation; and the feature was not compatible with parallel function calls at launch. It credited open-source work (Outlines, jsonformer, Instructor, Guidance, Lark) as inspiration.

The three numbers (under 40%, 93%, 100%) are the clearest public evidence for the ladder. Prompting alone is not a contract. Training gets close but remains probabilistic, and 93% at a hundred thousand requests a day is seven thousand failures. Only constraining the decoder turns a rate into a guarantee, and even then only for structure. Anthropic's documentation for its equivalent feature makes the same claims and caveats: responses are guaranteed schema-compliant through constrained decoding, with refusals and max_tokens as the exceptions, a compile step on first use cached for 24 hours, and a list of unsupported schema features.

Choosing the rung for your stack

In practice the choice is made by what your model and provider support. If you call a hosted API with strict structured outputs or strict tool use, use it for every machine-consumed output: it removes a whole failure class for a small first-request compile cost. If you serve open models, enable the serving engine's grammar backend and benchmark its overhead at your batch size. If you are stuck with a model or endpoint without constraints (an older model, some fine-tuned deployments, a provider feature that does not support your schema shape), use tool calling where available, plus validation and one repair, and accept a measured residual failure rate with a human queue behind it. In all three cases the post-call layer is identical: stop-reason handling, validation, semantic checks, logging. Teams that standardise that layer in one shared library find that switching providers or models changes one line, not every feature.

What to monitor

Parse-failure and schema-failure rates per model version, schema version and prompt version; stop-reason distribution (a rise in max_tokens stops means truncation); refusal rate; retries per request and their latency; semantic-rule failure counts by rule; null rates per nullable field (a sudden drop in nulls often means invention); per-field accuracy on the weekly labelled sample; and the size of the human review queue. Each has a clear owner and a threshold set from its normal variance (ae3).

import json, random, re

random.seed(1)
SCHEMA = {"vendor": str, "invoice_date": str, "total": (int, float),
          "currency": ("GBP", "EUR", "USD"), "po_number": (str, type(None))}
DATE = re.compile(r"^\d{4}-\d{2}-\d{2}$")

def validate(text):
    """Return (record, None) or (None, error message written for the model)."""
    text = re.sub(r"^```(?:json)?\s*|\s*```$", "", text.strip())   # tolerate code fences
    try:
        rec = json.loads(text)
    except json.JSONDecodeError as e:
        return None, f"Output was not valid JSON ({e.msg} at char {e.pos}). Return only the JSON object."
    if set(rec) != set(SCHEMA):
        return None, f"Keys must be exactly {sorted(SCHEMA)}; got {sorted(rec)}."
    for k, rule in SCHEMA.items():
        v = rec[k]
        if k == "currency" and v not in rule:
            return None, f"currency must be one of {list(rule)}; got {v!r}."
        if k != "currency" and not isinstance(v, rule):
            return None, f"{k} has the wrong type ({type(v).__name__}); total must be a number like 1240.5."
    if not DATE.match(rec["invoice_date"]):
        return None, f"invoice_date must be YYYY-MM-DD; got {rec['invoice_date']!r}."
    return rec, None

Work it out

A prompt-only extractor parses and validates 99.2% of the time. You add one repair retry that fixes 80% of the failures it sees. Each first attempt costs $0.0025 and each repair $0.00275. (a) At 500,000 requests a day, how many still fail, and what is the expected cost per request? (b) Should you add a second retry? (c) What changes with constrained decoding, and what does not?

Answer

(a) Residual failure rate: 0.008 × 0.20 = 0.0016, or 0.16%: 800 failed requests a day. As a percentage it looks like a rounding error; as a daily count it is a support queue. Expected cost: $0.0025 + 0.008 × $0.00275 = $0.002522, under 1% extra.

(b) If the second retry worked as well as the first, failures would fall to 0.032% (160 a day). In practice failures cluster on hard inputs (poor scans, unusual layouts) that fail for the same reason every time, so the second retry fixes far fewer, perhaps half, leaving around 400. It also adds another full call of latency to requests already in your p99. A better destination for persistent failures is a stronger model or a human queue.

(c) With constrained decoding, syntax and schema failures go to zero by construction, apart from refusals and output truncated at max_tokens, which you detect from the stop reason. OpenAI's launch numbers make the point: under 40% schema adherence with prompting for gpt-4-0613, 93% for a model trained on schemas, 100% with constrained decoding. What does not change: values can still be wrong. Keep semantic validation (totals add up, PO numbers exist, dates plausible), measure per-field accuracy and invention rates on labelled samples, and route uncertain fields to people.
