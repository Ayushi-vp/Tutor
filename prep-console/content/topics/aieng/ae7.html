A support bot's prompt is edited about twice a week. One Tuesday someone makes a "small wording tweak" to make answers friendlier. Nine days later, the complaints team notices a pattern: customers disputing refunds are being told politely that their case is noted, instead of being escalated to a human as policy requires. The tweak had softened a sentence the model was using as its cue to escalate. Nothing crashed, no metric on the engineering dashboard moved, and for nine days several hundred customers with legitimate disputes were stuck. When the team asks which version of the prompt each affected conversation used, they find the prompt version was never logged.

Software engineering solved most of this problem decades ago for code: version control, automated tests on every change, gradual rollouts, monitoring and fast rollback. LLM applications need the same discipline, but the thing being released is different. Behaviour changes when a prompt's wording changes, when a provider updates or retires a model, when sampling parameters or tool descriptions change, when the retrieval index is rebuilt with new documents or a new embedding model, and even when the provider changes its serving infrastructure underneath a model whose name has not changed. Tests are harder too: outputs are free text, graders are themselves models, and results are noisy.

That last point is not hypothetical. In September 2025 Anthropic published a postmortem describing three infrastructure bugs that intermittently degraded Claude's responses between August and early September. Its own benchmarks, safety evaluations, spot checks and canary deployments did not catch them; user reports did, and even those were confusing. If the provider's own release process can miss quality regressions, an application team without one has no chance.

This lesson builds that release process. It starts with everything that changes an LLM feature's behaviour and how to version it as one release. Then evaluation in CI: suite tiers, comparing two versions on the same items with a paired test worked by hand, slice gates and must-pass cases, and how to keep noisy gates from being flaky. Then online rollout: shadow, canary and ramp, with the sample-size arithmetic that decides how big and how long a canary must be. Then rollback, tracing and incident response. The case is Anthropic's postmortem, read as an LLMOps review.

Changing a recipe in a restaurant chain

A restaurant chain wants to change its signature dish. It would never simply email the new recipe to five hundred kitchens. First the change is written down as a numbered version, with what changed and why. Then the test kitchen cooks old and new side by side for a panel of tasters, the same tasters on the same day, and checks not only "which is better overall" but specific promises: still under the calorie limit on the menu, still safe for the nut-allergy version. Then the new recipe goes to three restaurants for a week while managers watch complaints, leftovers and reorders, compared with similar restaurants still on the old recipe. Only then does it roll out to all. Every plate's ticket records which recipe version it was. And if complaints spike, any kitchen can switch back to the old card that afternoon.

That is LLMOps in miniature. The written, numbered recipe is a versioned release. The side-by-side tasting is an offline eval comparing versions on the same items. The specific promises are must-pass checks and slice floors. The three restaurants are a canary, compared against a control. The ticket is the trace with the version stamped on it. Switching back is rollback.

The analogy breaks in two instructive places. A recipe produces roughly the same dish every time; an LLM can produce different answers to the same input, so tests must account for randomness. And a restaurant controls its ingredients; an LLM application rents its most important one, the model, from a supplier who can change it, retire it, or have a bad week in its own kitchen.

Why LLM features need more of this than ordinary code

Ordinary software has two properties that make testing comparatively easy: the same input gives the same output, and a test either passes or fails. LLM features have neither. The same input can give different outputs from run to run; "correct" is often a judgement rather than an equality; and the space of inputs is open-ended natural language, so no test suite covers it. Those three facts explain the shape of LLMOps. Because outputs vary, comparisons are statistical, on many items, with noise measured. Because correctness is a judgement, graders are rubrics, calibrated judges and humans, and they need versioning too. Because inputs are open-ended, offline tests are never enough on their own, so releases go out gradually and production feeds new cases back into the tests. Add a supplier who can change the model or its serving stack without your involvement, and continuous probing of production becomes the final layer.

If you stop here: version everything that changes behaviour as one release; compare old and new on the same eval items, by slice, with must-pass checks for critical behaviour; release gradually with guardrail metrics and automatic rollback; stamp versions on every trace; and turn every incident into new tests.

1. Everything that changes behaviour

Start with an inventory, because anything missing from it can change answers without anyone knowing. For a typical RAG assistant: the code of the orchestrator; the prompt templates (system prompt, few-shot examples, repair prompts, judge prompts); the model identifier for each call and its sampling parameters (temperature, top-p, max tokens, reasoning effort); tool schemas and descriptions (ae6: they are prompts); retrieval settings (chunk size and overlap, the embedding model, the index build and its documents, number of chunks, reranker model and threshold); guardrails (safety classifiers and their thresholds, validation rules); routing rules between models (ae2); and the provider's serving stack, which you do not control but must observe. A change to any one of them is a release.

2. Versioning: one manifest per release

Each artefact gets a version, and a release manifest ties a consistent set together under one id:

support-bot release 2026.10.02-1
  prompt.system        v43   (git sha 8f2c1e0)
  prompt.examples      v12
  model.answer         claude-sonnet-5-5 (pinned snapshot), temperature 0.3, max_tokens 800
  model.router         claude-haiku-4-5, threshold 0.62
  tools                schema v7
  retrieval            index 2026-09-28 (embed model v3, chunk 500/50), k=6, reranker v2
  guardrails           safety-clf v5 @ 0.85, refund-escalation rule v2
  eval suite           v31, judge prompt v9 on pinned judge model

Three rules make the manifest useful. Pin model snapshots rather than aliases, so a provider's update cannot change your behaviour unannounced (ae3's GPT-4 drift study is why). Stamp the release id on every request's trace (ae1), so any metric can be broken down by release and any conversation traced to the exact versions that produced it. And keep prompts and parameters in configuration loaded at run time from version control or a prompt registry, behind feature flags, so they can be changed and rolled back without redeploying code, while still going through review and the same gates as code. Eval datasets and judge prompts are versioned too: a score is only comparable with another score from the same suite version.

3. What goes into an eval suite

An eval suite (lm14) is a versioned set of cases plus graders. Its contents come from four places. A golden set of representative real requests with reference answers or rubrics, sampled across intents and slices. Must-pass cases for critical behaviour: refund disputes must escalate, medical-emergency messages must get the safety response, the bot must never quote a price. Regression cases from every past incident and production failure found by monitoring (ae3); this is how the suite remembers. And adversarial and safety cases: prompt injections, jailbreak attempts, requests for other users' data (lm18, ae5). Graders match the output type: exact or structured checks where possible (did it call the escalate tool? does the JSON validate?), a calibrated LLM judge with a rubric for free text, and periodic human review to keep the judge honest.

Suites run in tiers, because running everything on every change is slow and expensive. A fast suite of a few hundred items runs on every pull request in minutes, including all must-pass cases, and posts a comparison to the PR. The full suite (thousands of items, all slices, safety tests) runs before a release is promoted. Nightly or weekly runs cover exhaustive and expensive tests and judge calibration. And a small probe suite runs continuously against production, which the case study shows is not optional.

4. Comparing two versions on the same items, worked

The core offline question is: is version 2 better than version 1, and is it worse anywhere that matters? Because both versions run on the same items, the right analysis is paired. Items both versions pass, or both fail, say nothing about the difference. Only the disagreements do: let b be the number of items version 1 passes and version 2 fails, and c the reverse. McNemar's test asks whether c and b differ more than chance would explain; with enough disagreements, z ≈ (c − b) / √(b + c).

The lab runs a 500-item suite with four slices. Overall, version 1 passes 90.0% and version 2 passes 92.4%. There are 19 items that flip to pass and 7 that flip to fail: z = (19 − 7) / √26 = 12 / 5.10 = 2.35, comfortably beyond 1.96, so the improvement is real. A team gating on the aggregate would ship. Now look at the slices:

Every gain came from billing and account; every loss came from refund disputes, which fell 14 points. On only 50 items that is still clear (7 flips in one direction, none in the other). This is exactly the story at the top of the lesson, and a gate with a slice floor (no slice may drop more than, say, 3 points) or a must-pass rule on refund escalations blocks it. Then a person reads the seven flipped items, which is usually where the explanation is.

A practical release gate combines three checks: non-inferiority overall (the new version is not worse than the old by more than a small margin, beyond noise), slice floors on every important slice, and zero failures on must-pass cases. Improvements are welcome but not required; many releases (cheaper model, shorter prompt) aim to be "no worse" rather than "better".

5. Noise, flaky gates and how to set thresholds

Two sources of randomness make LLM evals noisy: the model's sampling (two runs of the same version give different outputs) and the judge's (an LLM judge can score the same output differently). A gate set tighter than this noise is flaky: it blocks good changes at random, people learn to re-run until it passes or to override it, and it stops protecting anything. The fix starts with measurement. Run the current version on the suite several times and record the spread of scores; that is the run-to-run variance. Then reduce it where you can: temperature 0 for deterministic tasks, several samples per item averaged for creative ones, a pinned judge model and rubric with temperature 0, structured checks instead of judges wherever possible. Set thresholds above the remaining noise; if three runs of the same version span 1.5 points, a gate at "no drop greater than 1 point" will fire on nothing. And use paired comparisons, which cancel much of the per-item difficulty noise that independent comparisons suffer from.

6. Wiring evals into CI

In practice: a pull request that touches prompts, tool definitions, retrieval settings or orchestration code triggers the fast suite against both the PR's version and the main branch's version (cached where unchanged), and a bot posts a report: overall and per-slice scores for both, the McNemar result, must-pass failures, and links to every flipped item with both outputs side by side. Merging requires the gate to pass or an explicit, logged override by an owner. Promotion of a release to the online stages requires the full suite. Expensive runs go through batch endpoints at half price (ae2), and judge results are cached by (input, output, judge version) so unchanged outputs are not re-judged. The cost of this is real but small next to the cost of nine days of mishandled refund disputes.

7. Online rollout: shadow, canary, ramp

Offline evals only cover what someone thought to put in them. Online stages catch the rest with a growing blast radius. In shadow mode the new version receives copies of live requests and its outputs are logged, not shown: it finds integration bugs, latency and cost changes, and differences in output distributions (length, refusal rate, tool-call rate) at zero user risk, and outputs can be judged against the current version's. A canary then serves the new version to a small random share of users (say 5%), with the rest as the control, behind a feature flag that keeps each user on one version for the duration (switching mid-conversation confuses both users and metrics). If guardrail metrics (errors, latency, escalation and complaint rates, judged quality on sampled traffic, cost per request) stay within bounds, the share is ramped, typically 5%, 25%, 50%, 100%, with a hold at each step. For changes whose value must be proven, not just their safety, a proper A/B test on the outcome metric replaces the ramp (ml16).

8. How big must a canary be? The arithmetic

A canary is a statistical test, and its size decides what it can see. Suppose the guardrail metric is the share of conversations that end badly (escalated with a complaint, or thumbs-down), currently 5%, and you want to catch a rise to 6%. The standard sample-size formula for comparing two proportions p₀ and p₁, with one-sided significance α and power 1 − β, is

n per arm = [ z(1−α) × √(2 p̄ (1 − p̄)) + z(1−β) × √(p₀(1−p₀) + p₁(1−p₁)) ]² / (p₁ − p₀)²

with p̄ the average of p₀ and p₁. With α = 5% (z = 1.645), power 80% (z = 0.842), p₀ = 0.05 and p₁ = 0.06: p̄ = 0.055, so √(2 × 0.055 × 0.945) = 0.322 and the first term is 1.645 × 0.322 = 0.530; √(0.0475 + 0.0564) = 0.322 and the second term is 0.842 × 0.322 = 0.271. The bracket is 0.801, squared 0.642, divided by 0.01² = 0.0001: about 6,400 conversations per arm. At 200,000 conversations a day, a 5% canary sees 10,000 a day, so this check needs most of a day. A bigger regression is quicker to see: 5% to 7.5% needs about 1,160 per arm, and 10% to 13% about 1,400.

Two consequences shape real rollout policies. First, the effect sizes a canary can detect in a reasonable time are large, so canaries are a safety net for big regressions (and crashes, latency and cost, which show up immediately); subtle quality regressions must be caught offline, where paired comparisons are far more sensitive. Second, the temptation to watch the dashboard and stop at the first significant blip is a statistical trap: checking repeatedly inflates the false-alarm rate. Either fix the checkpoints in advance (decide at each ramp step), or use sequential testing methods designed for continuous monitoring.

9. Rollback, by design

Rollback is only fast if it was designed in. Prompts, model choices, routing thresholds and guardrail settings live behind flags, so reverting is a configuration change measured in seconds, and the canary controller can do it automatically when a guardrail metric breaches its bound. Retrieval changes need blue/green indexes: build the new index alongside the old, switch traffic by flag, and keep the old one warm until the new one has proven itself; a re-embedding with a new embedding model cannot be reversed by flipping a version string if the old index was deleted. Some effects cannot be rolled back at all: emails sent, refunds issued, records written by tools during a bad release. For those the defences are upstream: confirmation steps, idempotency keys (ae1) and deterministic rules for critical policies, so that a bad prompt cannot take a consequential action on its own.

10. Tracing and incident response

When something goes wrong, the first questions are always the same: since when, for whom, and which change? Traces stamped with the release id answer the first two by breaking metrics down by release, time, tenant and slice, and the deployment log answers the third. An LLM incident runbook adds steps that ordinary services do not need. Check the provider's status page and your probe suite: is the model itself behaving differently? Compare traces of bad responses with good ones from the same release: is it a particular slice, prompt branch or retrieved document? Roll back first and diagnose second, if a recent release is a plausible cause. Afterwards, a blameless postmortem (sc13) produces two kinds of follow-up that are specific to LLM systems: the failing conversations become eval cases (so the suite can never miss this again) and the detection gap becomes a monitor or a probe.

11. Releasing retrieval changes

Changes to retrieval deserve their own gate, because they alter what the model sees rather than how it behaves, and generation-level evals can miss them. Before a new chunking scheme, embedding model or document set goes live, run a retrieval eval: a set of questions with the ids of the documents that answer them, measuring recall@k (does the right chunk appear in the top k?) and the rank of the first relevant chunk (lm9, lm10), sliced by document type and language. Then run the end-to-end suite, because better recall does not always mean better answers if chunks became longer or noisier (ae6). Build the new index alongside the old (blue/green), shadow queries against both and compare overlap of retrieved results: a release that changes the top-5 for 40% of queries deserves more scrutiny than one that changes 3%. And remember that content changes are releases too: a bulk import of new documents can shift answers as much as a prompt edit, so large ingestions go through the same eval and are stamped with an index version on every trace.

12. Upstream changes: deprecations and migrations

Pinning a model snapshot protects you from silent changes, and it starts a clock: providers publish deprecation and retirement dates for old snapshots, and an application still pinned on retirement day breaks. Track those dates as dependencies. A model migration is a full release: run the full suite with the current prompt on the new model, expect differences (newer models often follow instructions more literally, ae6), adjust the prompt, compare cost and latency (new tokenizers change token counts, ae2), shadow, canary and ramp. Keep the old model as a fallback until the new one has been through a full business cycle. Embedding-model migrations are the heaviest, because every document must be re-embedded and the index rebuilt before the switch.

Judges are dependencies too

An LLM judge that grades eval outputs has its own model version, prompt and biases (lm14). If the judge model is updated, scores can move with no change in the system being judged, and a release gate can pass or fail for reasons that have nothing to do with the release. So the judge is pinned and versioned like any dependency, its rubric prompt lives in version control, and its agreement with human labels is measured on a fixed calibration set whenever anything about it changes, and periodically otherwise. When the judge must change, re-score a reference set with both judges and either re-baseline the historical scores or report the step change explicitly, so trend charts are not silently broken. A cheap trick that catches judge drift: include a handful of fixed outputs (known good, known bad) in every eval run; their scores should never change.

Non-inferiority, equivalence and the margin

Many LLM releases are not trying to be better: a cheaper model, a shorter prompt, a refactor of the orchestration code. The right statistical question is then non-inferiority: is the new version worse than the old by more than an acceptable margin δ? You test that the difference is greater than −δ, rather than testing for any difference. The margin is a product decision (how much quality would you trade for a 40% cost cut?) and it must be stated before the experiment, not chosen after seeing the result. With paired data the sample needed to show non-inferiority depends on the disagreement rate between versions: two versions that disagree on 5% of items need far fewer items than two that disagree on 30%.

Multiple metrics, multiple slices, multiple chances to be fooled

A release report with 12 slices and 6 metrics contains 72 comparisons. At a 5% significance level, three or four will look significant by chance even when nothing changed. Two defences. Pre-register what blocks a release (must-pass cases, a short list of critical slices and guardrail metrics) and treat everything else as diagnostic, to be read, not gated. And for critical slices, rely on paired counts and effect sizes large enough to matter (the refund slice lost 7 items and gained none, which is not a chance pattern), rather than on p-values from many small tests.

Testing infrastructure changes for numerical equivalence

The case study's bugs were not prompt or model changes; they were changes to how the same model was served: request routing, a runtime performance optimisation, a compiler's handling of a top-k operation. Teams that self-host models (lm13) face the same class of risk whenever they change the serving engine, quantisation (lm12), kernels, hardware or batching. Benchmarks are a blunt tool for this, because a model "often recovers well from isolated mistakes", as Anthropic put it, so a bug that corrupts one token in a thousand barely moves accuracy. More sensitive checks compare implementations directly: run identical prompts through the old and new serving paths and compare next-token probability distributions (for example the KL divergence per position, or how often the top token agrees), check for out-of-distribution outputs such as unexpected scripts or characters (the detection test Anthropic added), and run these checks continuously on production replicas, not only in staging.

Who may change a prompt

Moving prompts out of code into a registry lets product and domain experts iterate quickly, which is often the point: the support lead knows the refund policy better than any engineer. It also means people outside the engineering review process can change production behaviour. The resolution is to give configuration the same controls as code, not to take it away from those experts: changes go through review by an owner, the same eval gates, the same staged rollout, and an audit log of who changed what. A good registry makes the safe path the easy one: an editor that shows the eval diff before saving, and a publish button that starts a canary rather than switching all traffic.

Debuggability versus data retention

Incident response wants full traces of every conversation, kept for a long time. Privacy wants minimal data kept briefly (ae5). The case study shows the tension is real: Anthropic noted that its internal privacy and security controls limited engineers' access to user interactions not reported as feedback, which protected users and slowed the investigation. Practical compromises: keep redacted traces by default with short retention; keep structural metadata (versions, token counts, stop reasons, guardrail decisions, character-set statistics) longer, because it contains little personal data and catches many problems; make it easy for users to submit an interaction as feedback, which creates consented, inspectable examples; and build replay tools that reproduce a request from its manifest and redacted inputs.

Ownership

Every LLM feature needs a named owner for its quality metrics, its eval suite and its runbook, just as every service has an owner for its SLOs. Without one, eval suites rot (nobody adds regression cases), gates get overridden, and dashboards nobody watches fill up with signal. A weekly ritual helps more than tooling: review the flipped items from recent releases, the newest production failures and the error-analysis categories (ae3), and decide what to add to the suite.

Failure modes in production

The unlogged version. A quality complaint arrives and nobody can tell which prompt, model or index produced the answer. Every investigation starts with archaeology. Fix: release manifest id on every trace, and a deployment log of every configuration change.

The aggregate that hid a slice. A release improves the average and breaks a minority flow (the refund escalation story; a language; an enterprise tier with custom instructions). Fix: slice floors and must-pass cases in the gate, and per-slice guardrail metrics in the canary.

The flaky gate everyone overrides. A gate with thresholds inside the noise blocks good changes at random; overrides become routine; the gate stops protecting anything. Fix: measure run-to-run variance, set thresholds above it, track override frequency as a metric.

The provider-side regression. Quality drops with no release on your side. Your release-based dashboards show nothing because the release did not change. Fix: continuous probe suites against production with fixed prompts and known answers, alerting on changes; provider status monitoring; and a fallback model already evaluated.

The irreversible release. A bad prompt triggers a tool that sends emails or issues credits for an hour before rollback. Fix: confirmation and limits on consequential tools, deterministic rules for critical policies, and canaries that start small for any release touching tools.

The case: Anthropic's postmortem of three overlapping bugs (2025)

On 17 September 2025 Anthropic published a technical postmortem of three infrastructure bugs that "intermittently degraded Claude's response quality" between August and early September 2025. It opened by stating that the company never reduces model quality because of demand, time of day or server load, and that the problems were due to infrastructure bugs alone. Claude is served through Anthropic's own API, Amazon Bedrock and Google Cloud's Vertex AI, on three hardware platforms (AWS Trainium, NVIDIA GPUs and Google TPUs), with "strict equivalence standards" so users get the same quality on every platform; that complexity is the background to everything that followed.

The first bug was a context-window routing error. From 5 August some Sonnet 4 requests were misrouted to servers configured for the upcoming one-million-token context window, initially about 0.8% of requests. On 29 August a routine load-balancing change increased the share; at the worst hour, on 31 August, 16% of Sonnet 4 requests were affected, and about 30% of Claude Code users who made requests in the period had at least one message routed to the wrong server type. Because routing was "sticky", a user who hit a wrong server tended to keep hitting it, so some users saw consistently degraded responses while others saw none. The second was output corruption: a misconfiguration deployed to TPU servers on 25 August, from a runtime performance optimisation, occasionally gave high probability to tokens that should rarely appear, producing Thai or Chinese characters in English answers or obvious syntax errors in code; it affected Opus 4.1 and Opus 4 from 25 to 28 August and Sonnet 4 from 25 August to 2 September, and was rolled back on 2 September. The third was an approximate top-k miscompilation: a rewrite of the token-sampling code deployed on 25–26 August removed an earlier workaround and exposed a latent bug in the XLA:TPU compiler's approximate top-k operation, which sometimes returned completely wrong results for certain batch sizes and configurations; its behaviour changed with unrelated factors such as surrounding operations and whether debugging tools were enabled. Anthropic switched to exact top-k with higher precision, accepting a small efficiency cost.

The section on detection is the LLMOps lesson. Anthropic's validation "ordinarily relies on benchmarks alongside safety evaluations and performance metrics", with spot checks and deployment to small canary groups first, and these "simply didn't capture the degradation users were reporting, in part because Claude often recovers well from isolated mistakes". Privacy controls limited engineers' access to user interactions that were not reported as feedback. Each bug produced different symptoms on different platforms at different rates, so reports looked like random, inconsistent degradation, and when negative reports spiked on 29 August the team did not immediately connect them to a standard load-balancing change. Anthropic's stated changes: more sensitive evaluations that reliably differentiate working from broken implementations; quality evaluations run continuously on true production systems, to catch problems like the routing error; and faster debugging tooling for community feedback without sacrificing privacy, plus a request that users keep reporting problems through the feedback buttons.

For application teams, three lessons transfer directly. Benchmarks that average over many items are insensitive to failures that corrupt a small fraction of tokens or requests, so release gates need targeted checks (character-set anomalies, format validity, probes with exact expected outputs) as well as averages. Evaluation has to run on the production path, continuously, because staging and canaries can be configured differently from the traffic that actually breaks. And release attribution matters: being able to line up a quality signal against every change (including "routine" infrastructure changes) is what turns a confusing month into a one-day investigation.

What to monitor

Per release and per slice: judged quality on sampled traffic, guardrail metrics (escalations, complaints, thumbs-down, errors), latency and cost; canary versus control with confidence intervals at each ramp step; probe-suite results against production, alerting on any change; gate pass rates, override counts and eval run-to-run variance; judge calibration agreement; and the age of the oldest unresolved regression case. Every metric is broken down by release id, so the first question in any incident has an answer.

Goal: build a small release gate: compare two prompt versions on the same 500 eval items with paired counts and McNemar's z, overall and per slice, block on a slice regression; then compute canary sample sizes for several effect sizes and simulate a canary decision. Standard library only; Python 3.12. The "model" is simulated: each item has a difficulty shared by both versions, which is what makes results paired.

import math, random
from statistics import NormalDist

random.seed(3)
Z = NormalDist().inv_cdf

# ---- 1. offline gate: compare prompt v1 and v2 on the SAME eval items ----
SLICES = {"billing": 200, "account": 150, "refund_dispute": 50, "other": 100}
P_PASS = {  # (v1, v2) chance of passing per slice: v2 is better overall but worse on refunds
    "billing": (0.88, 0.93), "account": (0.85, 0.90),
    "refund_dispute": (0.96, 0.80), "other": (0.90, 0.91)}

rows = []
for sl, n in SLICES.items():
    p1, p2 = P_PASS[sl]
    for _ in range(n):
        skill = random.random()                         # shared item difficulty -> paired results
        rows.append((sl, skill < p1, skill < p2 or random.random() < 0.02))

def report(rows, label):
    n = len(rows)
    a1 = sum(r[1] for r in rows) / n; a2 = sum(r[2] for r in rows) / n
    b = sum(r[1] and not r[2] for r in rows)            # v1 right, v2 wrong
    c = sum(r[2] and not r[1] for r in rows)            # v2 right, v1 wrong
    z = (c - b) / math.sqrt(b + c) if b + c else 0.0
    print(f"{label:15s} n={n:3d}  v1 {a1:.1%}  v2 {a2:.1%}  flips +{c}/-{b}  McNemar z={z:+.2f}")
    return a2 - a1, z

d, z = report(rows, "ALL")
fail = []
for sl in SLICES:
    ds, zs = report([r for r in rows if r[0] == sl], sl)
    if ds < -0.03:                                      # gate: no slice may drop > 3 points
        fail.append(sl)
print("GATE:", "BLOCK, regressions in " + ", ".join(fail) if fail else "PASS")

# ---- 2. canary: how much traffic to detect a rise in a bad-outcome rate? ----
def n_per_arm(p0, p1, alpha=0.05, power=0.8):
    pbar = (p0 + p1) / 2
    num = Z(1 - alpha) * math.sqrt(2 * pbar * (1 - pbar)) + Z(power) * math.sqrt(p0 * (1 - p0) + p1 * (1 - p1))
    return math.ceil(num ** 2 / (p1 - p0) ** 2)

for p0, p1 in [(0.05, 0.06), (0.05, 0.075), (0.10, 0.13)]:
    n = n_per_arm(p0, p1)
    print(f"detect {p0:.1%} -> {p1:.1%}: {n:,} requests per arm "
          f"(= {n / 10_000:.1f} days at a 5% canary of 200k/day)")

# ---- 3. simulate the canary decision for a version whose escalation rate really rose ----
n = n_per_arm(0.05, 0.06)
base = sum(random.random() < 0.05 for _ in range(n)) / n
can = sum(random.random() < 0.06 for _ in range(n)) / n
se = math.sqrt(base * (1 - base) / n + can * (1 - can) / n)
zc = (can - base) / se
print(f"canary bad-outcome rate {can:.2%} vs control {base:.2%}: z={zc:.2f} -> "
      f"{'ROLL BACK' if zc > Z(0.95) else 'continue ramp'}")

Design the pipeline

Your team changes the support bot's prompt about twice a week. Last month a "small wording tweak" made the bot stop escalating refund disputes to humans; it was noticed after 9 days through complaints. The bot handles 200,000 conversations a day, and about 2% are refund disputes, of which normally 97% are escalated. Design the process and tooling that would have caught it, and say how quickly a canary alone could have detected it.

Answer

Offline, before any user saw it:

  • Eval set with the right slice: a few hundred refund-dispute conversations from history, labelled "must escalate", plus other escalation categories. Escalation is checked deterministically (did the model call the escalate tool?), not by a judge.
  • Must-pass gate: escalation recall on that slice must stay at or above 97% (its normal level), regardless of aggregate gains. The PR report shows per-slice deltas and the flipped conversations; this change would have shown dozens of flips to "no escalation" and been blocked at review.
  • Versioned prompts in a registry, reviewed by an owner, with the release id stamped on every trace, so the affected conversations could be found in minutes.

Online: a 5% canary with escalation rate by intent as a guardrail metric. Canary refund disputes: 200,000 × 5% × 2% = 200 a day. If the escalation rate fell from 97% to, say, 60%, that is a huge effect: after one day the canary's 200 disputes would show about 120 escalations against an expected 194, a gap of roughly 15 standard errors (√(0.97 × 0.03 / 200) ≈ 1.2 points). Automatic rollback would have fired within hours. Had the tweak only reduced escalation to 92%, detection would take a few days, which is why the offline must-pass gate matters most.

Defence in depth: a deterministic rule or small classifier that forces escalation for refund-dispute intents regardless of what the model decides, because critical policies should not depend on prompt wording alone.

After the incident: add the failed conversations as regression cases, document the escalation policy as a tested requirement, and add escalation-rate-by-intent to the production dashboard with an alert.
