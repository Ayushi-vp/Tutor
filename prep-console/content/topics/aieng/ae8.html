A data scientist builds a churn model in a notebook. On last year's data it is excellent: it ranks customers who later left far above those who stayed. The team ships it: an engineer re-implements the feature calculations in the online service, the model file is copied to a server, and the retention team starts calling the customers it flags. Three months later the results are disappointing, and nobody can say why. Was it the model? The features? The data? Which version of the model is even running? Nobody wrote down which data snapshot it was trained on, the notebook has been edited since, and the online service computes one feature slightly differently, in a way that affects one customer in five.

This is the normal fate of a model without a production system around it. Training a model is a one-off act; running one is a continuous process. Data arrives every day and changes shape. Upstream teams alter tables they do not know you depend on. Models have to be retrained, compared with the one in production, approved, deployed without breaking anything, and rolled back when they misbehave. Predictions have to reach other systems at the right speed and cost. And every one of those steps can quietly diverge from what was tested.

A 2015 paper from Google engineers, "Hidden Technical Debt in Machine Learning Systems", gave this its enduring name. Its central picture is a small box labelled "ML code" in the middle of a large diagram of everything else a real system needs: configuration, data collection, feature extraction, data verification, machine resource management, analysis tools, process management, serving infrastructure and monitoring. The paper argued that ML systems have all the maintenance problems of ordinary software plus a set of their own, and that the debt is easy to incur and hard to see.

It is also the background against which LLM applications are judged. Interviewers for AI-engineering roles routinely ask candidates to design a classic pipeline (a fraud model, a recommender, a churn predictor) alongside an LLM system, partly because the ideas transfer and partly because real products contain both.

This lesson covers the classic machine-learning lifecycle that AI engineers are expected to know even when they mostly build LLM applications: data validation, point-in-time features and feature stores, reproducible training and experiment tracking, evaluation gates and the model registry, the serving patterns (batch, online, streaming) with their costs worked by hand, and training/serving skew, worked through an example and caught by a feature check you can run. The case is the technical-debt paper itself, read as a checklist. The last section maps the whole lifecycle onto LLM applications, because the ideas carry over almost one for one.

A bakery, not a recipe

A recipe that produces a wonderful loaf in a home kitchen is not a bakery. A bakery receives flour from suppliers every morning and checks it (is it the right type, is it damp, did the delivery arrive at all?). It has written, versioned recipes so that every baker makes the same loaf, and a log of which flour batch and which recipe version went into each tray. It tastes new recipes against the current one before switching. It decides which products are baked overnight for the morning shelves and which are made to order while the customer waits. And it watches what comes back: complaints, unsold loaves, a supplier whose flour has quietly changed.

A production ML system is the bakery. The recipe is the model. The flour checks are data validation; the versioned recipes and batch logs are experiment tracking, the model registry and lineage; tasting old against new is evaluation against the champion; the overnight bake versus made-to-order is batch versus online serving; and watching what comes back is monitoring (ae3). The failure in the opening story has a bakery equivalent too: the morning shift measures salt with a different spoon than the recipe was written for, and every loaf is subtly wrong while the recipe itself is perfect. That is training/serving skew.

Where the analogy breaks: a recipe does not change its behaviour when the flour changes slightly, but a model can change how it uses every input when one input shifts (Sculley et al. call this "changing anything changes everything"), and a model's predictions can change the very data it is later retrained on.

One month in the life of a production model

Follow the churn model through a month on a working platform. On the first of the month a scheduled pipeline pulls the latest customer and outcome data; validation checks find that a partner feed arrived with 40% fewer rows than usual and stop the run, and the data team fixes the feed the same day. The rerun builds point-in-time-correct training rows from the feature store, trains a challenger and records the run. The challenger beats the champion on last month's held-out customers overall and on every region, and is calibrated, so a reviewer approves it and it is registered as version 14. It runs in shadow for two days next to version 13, scoring the same customers; its predictions differ where expected and its served features match training. The nightly batch job then switches to version 14. Through the month, monitoring compares served features with training, tracks the share of customers flagged, and records outcomes as customers renew or leave. Nothing heroic happens, which is the point: every step that could have gone quietly wrong had a check.

If you stop here: validate data before you train on it; build features only from information available at prediction time, with the same code in training and serving; make every training run reproducible and every model version traceable in a registry; serve in batch unless freshness demands otherwise; and log what the model actually received in production so you can check it against what it was trained on.

1. From notebook to lifecycle

In a notebook, the workflow is linear and done once: load data, engineer features, train, evaluate, admire. In production it becomes a loop that runs indefinitely. Ingest new data from its sources. Validate it. Compute features. Train a candidate model reproducibly and track the run. Evaluate it against the model currently in production, on recent data and on slices. Register the approved model with its lineage. Deploy it through staged rollout. Serve predictions in the pattern the use case needs. Monitor inputs, outputs and outcomes, and trigger the next turn of the loop. Google's MLOps guidance describes maturity in these terms: at level 0 every step is manual and models are rarely updated; at level 1 the training pipeline is automated so models can be retrained continuously; at level 2 the pipeline itself is built, tested and deployed through CI/CD. Most teams sit between 0 and 1, and the most valuable step is usually automating validation and evaluation, not training.

2. Data ingestion and validation

Data is the model's most important input and the one most likely to change without warning. Data validation runs automated checks on every new batch before anything is trained on it: the schema (expected columns and types, no new or missing fields), ranges and domains (ages between 18 and 120, currency in a known list), null and default rates (a feature that is suddenly 30% null or 30% zero), volume (today's partition has a similar number of rows to yesterday's), freshness (the latest event is recent), and distribution against the previous run (the PSI checks of ae3). A failed check stops the pipeline with a clear message instead of producing a model. Tools such as TensorFlow Data Validation infer a schema from historical statistics and flag anomalies; Great Expectations and similar libraries let teams write checks as code. Upstream, data contracts make the producer's obligations explicit: the team that owns a table agrees its schema, meaning and freshness, and changes go through a process that notifies consumers. Sculley et al. call unstable data dependencies one of the costliest forms of ML debt; contracts and validation are the repayment.

3. Features: point-in-time correctness and feature stores

A feature is a transformation of raw data into a model input (ml14): "days since last purchase", "number of support tickets in the last 30 days", "average basket value". Two properties matter in production. The first is point-in-time correctness. Each training example represents a moment when a prediction would have been made; its features must use only data that existed at that moment. If a churn label is defined as "left within 60 days of 1 March", the ticket-count feature must count tickets up to 1 March, not up to today. A naive join of today's tickets table onto historical labels leaks the future (customers who were already leaving filed angry tickets after 1 March), offline metrics look wonderful, and production disappoints (ml9). The fix is an as-of join: for each row, take the latest feature values with a timestamp at or before the row's prediction time.

The second is consistency between training and serving, the subject of section 8. A feature store addresses both. Features are defined once, as code. An offline store keeps their history and builds point-in-time-correct training sets; an online store keeps the latest values in a low-latency database for serving. Both are fed by the same definitions, so the model sees the same feature in both places. Feature stores also make features reusable across models and teams, which reduces the "pipeline jungle" of near-duplicate feature code that Sculley et al. describe.

4. Reproducible training and experiment tracking

A training run is reproducible if, months later, you can say exactly what produced a model and rerun it to get an equivalent one. That requires five things recorded together: the code commit; an immutable data snapshot or version (a dated table partition, a dataset version in a tool such as DVC or lakeFS); the feature definitions and their versions; the full configuration including hyperparameters and random seeds; and the environment, typically a container image with pinned library versions. Training runs are orchestrated as pipelines (Airflow, Kubeflow, Dagster, or a cloud vendor's pipelines), so each step's inputs and outputs are explicit and steps can be rerun individually. Experiment tracking (MLflow, Weights & Biases and similar) records each run's parameters, metrics, artefacts and the versions above, so runs can be compared and the winner traced. Exact bit-for-bit reproduction is often impossible on GPUs, because some kernels are non-deterministic; the practical goal is statistical reproducibility: a rerun gives a model with the same metrics within noise.

5. Evaluation gates: champion versus challenger

A newly trained model is a challenger; the model in production is the champion. Promotion requires the challenger to beat, or at least match, the champion on the same evaluation data, and the evaluation data should be recent (a held-out slice of the latest period, since that is closest to tomorrow's traffic), sliced (by segment, region, product, and protected attributes where lawful), and checked for more than the headline metric: calibration (ml15), stability of predictions for the same customers, latency and size. For high-stakes models a human reviews the evaluation report and approves. This is the same gate logic as ae7, applied to weights instead of prompts: paired comparisons on the same data, slice floors, and must-pass checks for critical behaviour.

6. The model registry

An approved model goes into a model registry: a catalogue of model versions, each with its artefact (the serialised model or container), its lineage (the training run, code commit, data snapshot and feature versions that produced it), its evaluation results, and its approval status. Registries such as MLflow's let teams attach aliases or stages ("champion", "staging") to versions, and deployments refer to the alias or version rather than to a file path. Three things follow. Any prediction can be traced back through the version that made it to the data it was trained on, which regulators in credit and insurance require. Rolling back is a pointer change: move the "champion" alias to the previous version. And undeclared consumers become visible, because loading a model goes through the registry's access controls rather than a copied file.

7. Serving patterns: batch, online, streaming

How predictions reach the systems that use them is the biggest architectural choice, and it is driven by when the inputs exist and how fresh the prediction must be.

Batch inference scores everything on a schedule and writes predictions to a table the application looks up: nightly churn scores, weekly recommendations, daily demand forecasts. It is the simplest pattern to build, test, debug and roll back (re-run last night's job with the previous model), and the cheapest. Its limit is freshness: a prediction is up to a cycle old, and it can only score entities known in advance. Online inference computes a prediction per request inside a latency budget: fraud scoring in the payment path, search ranking, pricing a quote. Inputs that only exist at request time (this transaction's amount, this query) force it. It needs an always-on service, an online feature store, timeouts and a fallback (rules or a default) when the model is slow or down. Streaming inference runs the model inside a stream processor (sc18) on events as they arrive, with features computed over time windows: sensor anomaly alerts, real-time fraud patterns across many transactions. Many products are hybrid: candidates and embeddings computed in batch, a light online model ranking them with session context.

Put rough numbers on the cost difference for one model. Batch: score 10 million customers at 50,000 rows per second on one machine: 10,000,000 / 50,000 = 200 seconds, about 3.3 minutes a night. Online: serve 2,000 requests per second at peak, each needing 5 ms of CPU: 2,000 × 0.005 = 10 cores fully busy, doubled for headroom and redundancy to 20 cores running around the clock, plus the online feature store. Batch uses roughly a hundredth of the compute, and the gap is why "could this be a nightly table?" is the first question to ask.

8. Training/serving skew, worked

Training/serving skew is any difference between what the model saw in training and what it receives in production. Its usual cause is two implementations of the same feature: a SQL or Spark job in the training pipeline, and a re-implementation in the online service, written by a different person in a different language months later. Other causes: a feature computed from a table that changes after the fact (Google's Rules of ML warns that data in a joined table may differ between training and serving time), a batch feature that is stale online, or different library versions.

Work an example. The churn model uses "days since last purchase", transformed as log(1 + days). About 18% of customers have never bought anything, so the raw value is missing. The training pipeline fills missing values with the training-set median, 14 days, so these customers get log(15) = 2.708. The online service, re-implemented later, fills missing with 0, reasoning "no purchase, zero days", so they get log(1) = 0, which is the value for a customer who bought something today. The model's churn score is a logistic function of the feature, here σ(−2 + 0.9 × (x − 2.5)). For a never-purchased customer, the training-consistent score is σ(−2 + 0.9 × 0.208) = σ(−1.81) = 0.14; the served score is σ(−2 + 0.9 × (−2.5)) = σ(−4.25) = 0.014. A tenfold drop, for one customer in five. With the retention team calling everyone above 0.10, the flagged share falls from 70.8% to 52.8% of customers: exactly the 18% who never bought, silently dropped. Every offline metric is perfect, because offline evaluation uses the training pipeline's features.

Two checks catch it, and the lab runs both. Check 1, distributions: log the features the model receives in production (Rules of ML #29 says the best way to train like you serve is to save the features used at serving time) and compare them with the training features. The share of zeros is 0.0% in training and 18.0% in serving, and the PSI across deciles is 0.72, far above any reasonable threshold (ae3). Check 2, replay: take logged raw inputs, run them through the training transformation, and diff with what was served. 18.0% of requests mismatch, and every mismatch has missing purchase history, which points straight at the cause. Prevention is structural: one implementation of each transformation used by both paths (a shared library, a serialised preprocessing pipeline, or a feature store), unit tests that feed the same raw inputs through both paths, and training future models on logged served features so any remaining difference is learned rather than hidden.

9. Deployment strategies and rollback

Model deployment uses the staged strategies of ae7. Shadow first: the challenger scores live requests alongside the champion without its predictions being used, which catches missing features, skew, latency and prediction-distribution differences safely. Then a canary or an A/B test on a share of traffic, measuring business outcomes with the sample sizes those effects require (ml16). Blue/green deployment keeps the old model serving until the new one is proven. For batch models the equivalents are simpler: write the challenger's predictions to a separate table, compare, and switch the table the application reads. Rollback is a registry alias change for online models and a re-run for batch ones, provided the previous version is still in the registry and its features still exist.

10. Closing the loop: monitoring and retraining

Once deployed, the model is monitored in the layers of ae3: system health, input drift per feature against training, output distribution (the share of positive predictions), calibration and accuracy as labels arrive (with the label delay tracked explicitly), and the business outcome. Sculley et al. list three checks worth having from day one. Prediction bias: in a working system the distribution of predicted labels should usually match the distribution of observed labels; a gap is a cheap, useful alarm. Action limits: for systems that act in the world (bidding, marking spam, declining payments), enforce sanity limits on how often they act. Upstream producers: monitor the data sources and hold them to service levels that reflect the ML system's needs. Retraining is triggered by schedule, by drift or degradation, or by new labelled data, and each retrained model goes back through validation, evaluation, registry and staged deployment. Automation of that loop is the step from MLOps level 0 to level 1.

11. The same lifecycle for LLM applications

An LLM application has the same skeleton with different organs, which is why this lesson closes the track. Data validation becomes validation of documents before indexing (encoding, duplicates, personal data, ae5) and of eval data. Features and feature stores become retrieval indexes and context assembly (ae6), and skew becomes the difference between the context assembled in evaluation and in production. Training runs become builds of prompts, indexes and occasionally fine-tunes, recorded in a release manifest (ae7). Test sets become eval suites with judges. The model registry becomes a prompt and configuration registry plus pinned model snapshots. Deployment, monitoring and retraining become staged rollouts, drift and quality monitoring (ae3), and the logs-to-evals loop. And many LLM products still contain classic models (a router predicting which LLM to use, an intent classifier, a reranker) that need the full classic lifecycle in this lesson.

Entanglement: changing anything changes everything

Sculley et al.'s first point is that ML systems resist the modularity that keeps ordinary software maintainable. In a model with features x₁…xₙ, changing the distribution of x₁ can change the weights and use of all the others; adding or removing a feature does the same. They call this the CACE principle (Changing Anything Changes Everything) and note it applies equally to hyperparameters, sampling, convergence thresholds and data selection. The practical consequence is that there is no such thing as a small change to a model's inputs: a "harmless" upstream fix to one feature can shift predictions everywhere, which is why every change goes through full evaluation and why monitoring must cover all features, not just the one that was touched. Ensembles of isolated models help only partly, because improving one member can make the ensemble worse if its errors become more correlated with the others'.

Correction cascades and undeclared consumers

Two forms of hidden coupling recur. A correction cascade appears when a model for a slightly different problem is built by learning a correction on top of an existing model's output: quick to build, but now improving the base model can break the corrected one, and cascades of corrections become impossible to improve without breaking something. Undeclared consumers appear when a model's predictions are written to a table or log that other teams quietly start using; change the model and an unknown system downstream breaks, or worse, those consumers feed back into the model's own inputs. Defences: publish predictions through an interface with access control and an owner, register consumers, and treat a model's output schema and semantics as an API with versioning (swe7).

Data dependencies cost more than code dependencies

Code dependencies are found by compilers and static analysis; data dependencies are found by incidents. Unstable data dependencies are inputs produced by other systems whose behaviour changes over time (another team's model, a mapping table that gets "improved"); the paper's mitigation is to consume a versioned copy and upgrade deliberately. Underutilised data dependencies are inputs that add little: legacy features made redundant by newer ones, features added as a bundle under deadline pressure, features that gave a tiny gain at a large complexity cost. Each is a liability, because if its source breaks, the model breaks. The paper recommends regular leave-one-feature-out evaluations to find and remove them; deleting features is real engineering work and deserves credit as such.

Feedback loops

Live models influence their own future training data. A direct feedback loop: a recommender's choices determine which items get clicks, and next week's model is trained on those clicks. A hidden feedback loop: two systems influence each other through the world, such as two models on the same page whose outputs change the behaviour the other learns from. The paper notes the theoretically correct tool for direct loops is often a bandit algorithm rather than plain supervised learning. In practice, teams keep a small randomised or exploration slice whose data is unbiased (ae3), log the model's propensities (the probability with which each action was chosen) so later training can correct for the bias, and look for slow drifts that coincide with model releases.

Configuration debt

Mature ML systems carry enormous configuration: which features are used, data selection windows, preprocessing switches, model settings, special cases ("feature A was incorrectly logged from 9/14 to 9/17"; "feature D is not available in production, so a substitute must be used"). The paper observes that the lines of configuration can far exceed the lines of code and that each is a potential mistake. Its principles for configuration systems are worth quoting in an interview: it should be easy to specify a configuration as a small change from a previous one; hard to make manual errors; easy to see the difference between two configurations; easy to check basic facts automatically (number of features used, transitive closure of data dependencies); possible to detect unused or redundant settings; and configurations should undergo code review and live in a repository. LLM applications inherit all of this in their prompt, retrieval and routing configuration (ae7).

Latency engineering for online models

In online serving the model's own compute is often the smallest part of the latency budget. Fetching features dominates: a fraud model that needs 40 features from five services can spend most of its 50 ms budget on network calls. The levers are precomputation (compute slow-moving features in batch and store them in the online store), co-location (the feature store in the same zone as the model service), caching per entity, parallel fetches with per-call timeouts, and a degraded mode that predicts with defaults or a simpler model when a feature is missing, logging that it did so. Model-side optimisations (smaller models, quantisation, compiled runtimes such as ONNX Runtime) matter once features are under control. As with LLM pipelines (ae1), the end-to-end tail is measured with traces, not added up from stage averages.

Reproducibility and governance in regulated domains

In credit, insurance, hiring and healthcare, an organisation may have to explain or reproduce a specific historical decision years later. That requires the registry's lineage, the logged features actually used for that prediction (not recomputed from today's tables, which may have changed), the exact model version and preprocessing, and the decision threshold in force at the time. Model risk management functions also require documented validation before deployment, independent review, and change control that treats a retrained model as a new model. The engineering consequence is the same as for privacy (ae5): logging and retention must be designed for the obligations, and the cheapest time to design them is before the first model ships.

Failure modes in production

Skew from two implementations. The online service computes a feature differently from the training pipeline: a missing-value rule, a timezone, a unit, a rounding, a stale lookup. Offline metrics stay perfect; online performance quietly underdelivers. Signal: served-feature distributions versus training, replay mismatches. Fix: one shared transformation, logged served features, training on logs.

Leakage in training data. Offline accuracy is spectacular and production is mediocre, because training features used information from after the prediction time. Signal: a large, persistent gap between offline and online metrics that skew checks do not explain. Fix: point-in-time joins and a feature store; audit features whose source tables are updated after the fact.

Upstream schema or semantic change. A producer renames a field, changes a unit or starts emitting a new category. Without validation the pipeline trains on garbage or the online service silently fills defaults. Fix: data validation that fails loudly, data contracts, and monitoring of null and default rates per feature.

Stale batch predictions. The nightly job fails and the application keeps reading yesterday's table, then last week's. Nothing errors. Fix: freshness checks on prediction tables with alerts, and an explicit maximum age after which the application falls back.

The model nobody can reproduce. A regulator or an incident review asks why a decision was made; the training data has been overwritten and the notebook edited. Fix: immutable data snapshots, registry lineage, logged features per decision.

The case: "Hidden Technical Debt in Machine Learning Systems" (Sculley et al., 2015)

D. Sculley and colleagues at Google published this paper at NeurIPS 2015, and it remains the most cited description of why ML systems are expensive to maintain. It deliberately offers no new algorithm. Instead it uses the software-engineering idea of technical debt (shortcuts that speed delivery now and cost more later) to argue that ML systems "have a special capacity for incurring technical debt, because they have all of the maintenance problems of traditional code plus an additional set of ML-specific issues", and that this debt is hard to detect because it exists at the system level rather than in the code.

The paper's catalogue is the deep section above in compact form. Boundary erosion: entanglement and the CACE principle, correction cascades, undeclared consumers. Data dependencies: unstable and underutilised inputs (legacy features, bundled features, epsilon features, correlated features), with leave-one-feature-out evaluation and versioned signals as remedies. Feedback loops, direct and hidden. ML-system anti-patterns: glue code, pipeline jungles, dead experimental code paths, abstraction debt and "smells" such as plain-old-data types and multiple-language systems. Configuration debt, with the principles of good configuration. And dealing with changes in the external world: fixed thresholds that go stale, and the need for live monitoring of prediction bias, action limits and upstream producers. Its Figure 1, the small "ML code" box surrounded by configuration, data collection, feature extraction, data verification, machine resource management, analysis tools, process management tools, serving infrastructure and monitoring, is reproduced in countless MLOps talks; the text adds that a mature system "might end up being (at most) 5% machine learning code and (at least) 95% glue code", and draws the conclusion that it can be cheaper to build a clean native solution than to keep wrapping generic packages.

The paper also names a cultural cause: a hard line between "research" and "engineering" roles produces black-box packages that engineers must glue together and that researchers do not maintain. Its recommendation is teams that reward deleting features, reducing complexity, improving reproducibility and monitoring as much as they reward accuracy gains. Ten years on, most of the industry's MLOps tooling (feature stores, registries, data validation, experiment tracking) can be read as a product built to pay down one item in this catalogue, and LLM applications have recreated nearly every item in new forms: prompts as configuration debt, retrieval indexes as unstable data dependencies, agent tool chains as correction cascades. The paper's closing test still works as an interview answer: a useful question about any change is how easily an entirely new algorithmic approach could be tested at full scale.

What to monitor

Per model: data-validation failures by check and source; feature null, zero and default rates and PSI against training (from logged served features); replay mismatch rate on a sample; prediction distribution and prediction bias against observed labels; label delay and, once labels land, accuracy and calibration by slice; prediction-table freshness for batch models; online latency per stage including feature fetches, and fallback rate; action counts against action limits; and registry state (which version serves each surface, who approved it, when it was last retrained).

Goal: reproduce the skew example: a training transform that fills missing purchase history with the median and a serving transform that fills it with zero; catch the difference with a distribution check and a replay check; measure the effect on churn scores; and compare batch and online capacity for the same model. NumPy from the existing gpt_env (Python 3.12).

import numpy as np
rng = np.random.default_rng(8)

# raw customer records: days since last purchase (NaN for customers who never bought)
def raw_batch(n):
    days = rng.exponential(20, n)
    days[rng.random(n) < 0.18] = np.nan            # 18% have never purchased
    return days

TRAIN_MEDIAN = 14.0                                  # computed once from the training snapshot

def transform_train(days):                           # offline pipeline (warehouse SQL, in Python here)
    return np.log1p(np.where(np.isnan(days), TRAIN_MEDIAN, days))

def transform_serve_buggy(days):                     # re-implemented in the online service
    return np.log1p(np.nan_to_num(days, nan=0.0))   # 'missing means zero days' -> looks like a fresh buyer

def model_score(x):                                  # churn model trained on transform_train features
    return 1 / (1 + np.exp(-(-2.0 + 0.9 * (x - 2.5))))

def psi(a, b, bins):
    pa = np.histogram(a, bins)[0] / len(a); pb = np.histogram(b, bins)[0] / len(b)
    pa, pb = np.clip(pa, 1e-4, None), np.clip(pb, 1e-4, None)
    return float(np.sum((pb - pa) * np.log(pb / pa)))

train_x = transform_train(raw_batch(100_000))
live_raw = raw_batch(20_000)
served_x = transform_serve_buggy(live_raw)           # what the model actually received (logged)

# check 1: distribution of the served feature vs the training feature
bins = np.quantile(train_x, np.linspace(0, 1, 11)); bins[0], bins[-1] = -1, 99
print(f"share of feature == 0:  training {np.mean(train_x == 0):.1%}   serving {np.mean(served_x == 0):.1%}")
print(f"PSI(training, serving) = {psi(train_x, served_x, bins):.3f}")

# check 2: replay - recompute the TRAINING transform on logged raw inputs and diff
replayed = transform_train(live_raw)
mismatch = ~np.isclose(replayed, served_x)
print(f"replay mismatch rate: {mismatch.mean():.1%} of requests (all with missing purchase history: "
      f"{np.isnan(live_raw[mismatch]).all()})")

# impact: churn scores for the affected customers
s_ok, s_bad = model_score(replayed[mismatch]), model_score(served_x[mismatch])
print(f"affected customers' mean churn score: correct {s_ok.mean():.2f} vs served {s_bad.mean():.2f}")
print(f"flagged for retention offer (score > 0.1): correct {np.mean(model_score(replayed) > 0.1):.1%} "
      f"vs served {np.mean(model_score(served_x) > 0.1):.1%}")

# batch vs online capacity for the same model
customers, rows_per_s = 10_000_000, 50_000
peak_rps, cpu_ms, headroom = 2_000, 5, 2
print(f"\nbatch: {customers:,} rows / {rows_per_s:,} rows/s = {customers / rows_per_s / 60:.1f} min of one machine per night")
print(f"online: {peak_rps:,} rps x {cpu_ms} ms CPU x {headroom} headroom = {peak_rps * cpu_ms / 1000 * headroom:.0f} cores, 24/7")

Tested output (Python 3.12.10, NumPy):

PSI(training, serving) = 0.717
replay mismatch rate: 18.0% of requests (all with missing purchase history: True)
affected customers' mean churn score: correct 0.14 vs served 0.01
flagged for retention offer (score > 0.1): correct 70.8% vs served 52.8%

batch: 10,000,000 rows / 50,000 rows/s = 3.3 min of one machine per night

What to look for. Both checks point at the same 18% of requests, and the replay check also says why (every mismatch has missing history), which a distribution check alone cannot. The affected customers' scores collapse from 0.14 to about 0.01 and they disappear from the retention list, while any offline evaluation, which uses the training transform, would look perfect. Then list what must be versioned and logged so a prediction made last month can be reproduced.

Answer
  • (a) Batch: weekly cadence, humans act on it, no latency need. A scheduled job writes scores to a table; the cheapest and easiest to debug.
  • (b) Online: the decision sits in the payment path within tens of milliseconds and depends on this transaction (amount, merchant, device) plus fresh velocity features (transactions in the last minute) from an online store. Needs timeouts and a rules fallback when the model or a feature is unavailable, and action limits on decline rates.
  • (c) Streaming: continuous events (50,000 per second); windowed features per sensor (rolling mean and slope over five minutes) computed in a stream processor, with the model inside it and alerts within seconds.
  • (d) Hybrid: candidate items and user embeddings precomputed in batch; a light online ranker uses session context (what was just viewed) at request time.
  • (e) Batch: a nightly job writes forecasts to a table used by replenishment; freshness of a day is fine.

Reproducibility requires: the model version in the registry with its lineage (training code commit, immutable training-data snapshot, feature definitions and versions, configuration and seeds, container image); the exact input features used at prediction time, logged rather than recomputed (source tables may have changed); preprocessing and threshold configuration in force at the time; and for online models the request log with timestamp, model version and response. Without logged features you can reproduce the model but not the prediction.
