A software company's support assistant answers about 70,000 questions a day. Its finance team notices that the monthly bill for the model has tripled since launch while traffic has only doubled, and asks engineering to "add caching". Three engineers hear three different requests. One turns on the provider's prompt caching and is surprised when the bill goes up the next week. One puts Redis in front of the API keyed on the user's message and gets almost no hits, because people never type the same sentence twice. The third adds a semantic cache that matches questions by meaning, gets a 90% hit rate in a day, and a week later is in an incident review because customers asking how to cancel a subscription were told how to cancel an order.

All three were "caching", and all three were reasonable ideas applied without the model of what each cache stores, when it is correct, and what it costs. In an LLM application there are three quite different things you can reuse: the model's internal computation for a prompt prefix that repeats, a stored answer for a request that repeats exactly, and a stored answer for a request that merely looks similar. They differ in how much they save, how often they are wrong, how they go stale and how they leak data.

Caching is also one of the few levers that cuts cost and latency together, which is why interviewers for AI engineering roles ask about it so often: "how would you cut the cost of this feature by half?", "why did turning on caching increase our bill?", "how would you design a semantic cache, and how do you pick the threshold?" The expected answer is not a list of products. It is a cost model, a correctness argument and an isolation story.

This lesson owns the topic end to end. It starts with where work can be reused, then explains provider prompt caching mechanically and with the pricing, TTLs and limits as documented on the day of writing, shows how to structure prompts so the stable part is cached, and works the economics by hand. It then covers exact-match response caches and their keys, semantic caches with a threshold sweep that puts numbers on hit rate versus wrong answers, prefix caching in self-hosted engines, invalidation, tenant isolation and the timing side channel, and finally how to measure the saving without fooling yourself. The cost model from ae2 is assumed; this lesson goes deeper on the caches themselves.

Three things you can reuse

Think of a busy restaurant kitchen. Some preparation is the same for every order: stock simmering, vegetables chopped, sauces made. Doing it once at the start of service and reusing it for every plate is pure gain, as long as the recipe does not change. That is prompt caching: the model's processing of the unchanged part of your prompt, kept and reused. Some orders are identical (table 4 and table 9 both want the soup of the day); you could ladle the second bowl from the same pot without cooking twice. That is an exact-match response cache. And some orders are merely similar: "the pasta, no cheese" versus "the pasta, no garlic". A kitchen that serves the first plate for the second order because they look alike is fast and occasionally wrong in ways the customer notices. That is a semantic cache.

The analogy holds in the important ways: the first kind of reuse is always correct and only saves preparation; the second is correct when orders are truly identical; the third trades correctness for hit rate. It breaks in one: in a kitchen you can see what you are reusing, while an LLM cache's mistakes are invisible until a user complains, so measurement has to be designed in.

Where each cache sits on the request path

What each one depends on

A prompt cache depends on prefix stability: the same bytes at the start of many prompts, arriving close enough together that the entry has not expired. A response cache depends on request repetition: the same question, or the same automated call, recurring. A semantic cache depends on meaning repetition plus an embedding that separates questions needing different answers. Most applications get the largest, safest saving from the prompt cache, a modest one from exact-match caching of automated or templated calls, and should treat semantic caching as a product decision about acceptable error.

A reader who stops here should remember: prompt caching saves computation and is always correct but must be designed for; exact-match caching is correct if the key captures everything that matters; semantic caching is a bet you must price.

What to do first

The order of work follows from those properties. Start with the prompt cache, because it is correct by construction and usually the largest saving: measure how much of each feature's input is a stable prefix, restructure prompts so that prefix comes first, place breakpoints, and watch the cache-read share of input tokens climb. Next, look for automated or templated calls that repeat exactly (classification of near-identical alerts, descriptions for the same product, evaluation reruns) and put an exact-match cache in front of them. Only then consider a semantic cache, and only after you have replayed real traffic, labelled what a cached answer would have got wrong, and put a price on a wrong answer. Many teams discover at that point that a curated FAQ with semantic matching is the version of semantic caching they actually want.

A note on latency

Caches cut latency as well as cost, but by different amounts. A response-cache hit returns in milliseconds instead of seconds, which users notice. A prompt-cache hit shortens time to first token by roughly the prefill time of the cached prefix, which for a 10,000-token prefix on a fast model is a few hundred milliseconds, but does nothing for the time spent generating the answer. If latency is the main goal, ae10 covers the full budget; caching is one line in it.

1. What a prompt cache stores

When a model reads a prompt, the prefill phase computes, for every token in every layer, a key and a value vector (lm5). For a 10,000-token system prompt, that is most of the work of answering a short question. Because of the causal mask, the keys and values for token 5,000 depend only on tokens 1 to 5,000, so if the next request begins with exactly the same 10,000 tokens, those keys and values are exactly the same. A prompt cache keeps them and lets the next request start its prefill at token 10,001. The provider saves GPU time, which it passes on as a discount on those tokens, and your time to first token drops because less prefill runs.

Two consequences follow directly from the mechanism. First, matching is by prefix: the cache can only reuse a run of tokens from the start. A single changed token at position 200 makes the stored state for every later position invalid, because their keys and values were computed while attending to the old token 200. Second, it is exact: "Hello" and "hello" are different tokens; reordered tool definitions are a different prefix. Prompt caching never changes the output, because the model computes the same state either way; it only skips recomputing it.

2. Provider prompt caching, as documented on 9 October 2026

The mechanics are the same everywhere, but the controls and prices differ and change often, so check the current documentation. On the day this lesson was written:

Anthropic (Claude API). You mark a cache breakpoint with cache_control on a content block, or set it once at the top level for automatic caching, which places the breakpoint on the last cacheable block and moves it forward as a conversation grows. The prefix is built in the order tools, system, messages; a change at one level invalidates that level and everything after. Up to 4 breakpoints per request. Entries live 5 minutes by default and the lifetime is refreshed free on each hit; a 1-hour TTL is available. Pricing multipliers on the base input price: 5-minute writes 1.25×, 1-hour writes 2×, reads 0.1× on most models, 0.05× on Claude Opus 5.5 and Sonnet 5.5, and 0.025× on Claude Fable 5.1. Minimum cacheable prefix: 512 tokens on the newest models, 1,024 to 4,096 on others (4,096 on Haiku 4.5); shorter prompts are processed without caching and without an error. On each request the system checks back at most 20 blocks from a breakpoint for an earlier entry, so in a long, fast-growing conversation a second breakpoint may be needed. Caches are isolated per workspace.

OpenAI. Caching is on by default. For GPT-5.6 and later there are implicit and explicit modes: implicitly, a breakpoint is placed at the end of the latest eligible message; explicitly, you mark breakpoints yourself, and content after the last one is billed at the plain input rate without a write charge. Each request can create up to four cache writes. Writes cost 1.25× the input rate and reads 0.1× (0.05× on GPT-6.1 Sol), the minimum prefix is 1,024 tokens, and an entry stays eligible at least 30 minutes after its last write or reuse. Older models use implicit caching only, report cached tokens in multiples of 128, keep entries "around 5 to 10 minutes of inactivity, up to one hour" in memory or up to 24 hours with extended retention, and route requests to machines by a hash of the prefix plus an optional prompt_cache_key; above about 15 requests per minute for one prefix, traffic can overflow to machines without the entry.

Both providers report cached tokens in the response's usage fields (for Anthropic, cache_creation_input_tokens and cache_read_input_tokens; for OpenAI, cached tokens within the input token details). Those fields are the raw data for every saving calculation in this lesson.

3. Structuring prompts so the stable part comes first

Order the prompt from most stable to least stable:

  1. Tool definitions, in a fixed order with deterministic serialisation.
  2. The system prompt: role, rules, output format.
  3. Static reference material: policy documents, product catalogue summaries, few-shot examples.
  4. Per-tenant or per-user context that is stable within a session.
  5. Conversation history, appended to, never rewritten.
  6. Retrieved snippets for this turn, and the new user message.

Then hunt for anything variable in the early layers. The classic offenders: a timestamp or "today's date" at the top of the system prompt (move it to the end, or round it to the day); the user's name in the first line; a request ID in a header that gets templated into the prompt; tools added or removed per request; JSON serialised with unordered keys; A/B experiments that alter one sentence of the system prompt (each variant is its own prefix, halving traffic per prefix); and history that is summarised and rewritten every turn, which changes the prefix each time. ae2's example of a timestamp making every request a cache miss is the most common real case.

Place breakpoints at the end of the last block that is identical across the requests you want to share an entry. A breakpoint placed after a variable block writes a new entry on every request, paying the write premium for nothing. If a stable prefix falls just short of the minimum length, it can be worth padding it with useful static content (more examples, fuller instructions) to cross the threshold: OpenAI's guide works this through and finds expanding a prefix to 1,024 tokens pays across 10 requests if the original was at least about 221 tokens.

4. The economics, worked by hand

Take Claude Sonnet 5.5's published prices on the day of writing: $2 per million input tokens, $10 per million output, 5-minute writes at 1.25× ($2.50/M) and reads at 0.05× ($0.10/M). A request has a 10,000-token stable prefix, 500 variable input tokens and 300 output tokens.

With hit rate h, the expected cost is 0.005h + 0.029(1 − h) = 0.029 − 0.024h. It equals the uncached $0.024 when h = 0.005/0.024 ≈ 0.21. Above a 21% hit rate caching saves money; below it, caching costs more. At h = 0.9, the cost is $0.0074, a 69% saving; at h = 0.99, $0.0052, 78%. The output tokens are untouched, so the ceiling on the saving is set by how much of the bill is the cacheable prefix.

The hit rate is set by traffic per prefix within the TTL. If requests for one prefix arrive at random at rate λ and the TTL T is refreshed on every hit, a request hits whenever the previous one for that prefix came less than T ago, which happens with probability 1 − e^(−λT). At one request a minute with a 5-minute TTL that is 1 − e^(−5) ≈ 99%; at one every 20 minutes, 1 − e^(−0.25) ≈ 22%, right at break-even. That is why per-user prefixes cache badly and per-tenant or global prefixes cache well, and why a 1-hour TTL, at 2× the write price, is worth it only when inter-arrival times sit between five minutes and an hour.

5. Exact-match response caches

A response cache stores the model's answer and returns it for a later request that is the same. It saves the whole call, output included, and returns in milliseconds. It is safe when the answer is a deterministic function of the key, so it fits automated and templated calls best: classifying a support ticket, extracting fields from a known document, generating the description for a product ID, answering a fixed frequently-asked-question (FAQ) button, or re-running the same evaluation prompt. It fits free-form chat poorly, because people rarely type the same thing twice and because conversational answers depend on history.

The design work is in the key. Hash a canonical form of everything that determines the answer: provider and model version (a model upgrade must not serve old answers), prompt template version, system prompt hash, parameters (temperature, maximum tokens, response format, tools), versions or content hashes of any retrieved documents, the tenant and the user's permission scope (au12), and the normalised input (trimmed whitespace, consistent Unicode, perhaps lower-cased if case never matters). Store the answer with its creation time, the model version and a TTL appropriate to how fast the underlying facts change. For sampled outputs (temperature above 0), caching freezes one sample; that may be fine for an FAQ and wrong for a "give me ideas" feature where users expect variety.

A simple worked case: an internal tool classifies 400,000 support tickets a day, and 35% of them are near-duplicates generated by the same alert (identical text after normalising timestamps and IDs). An exact-match cache keyed on normalised text plus classifier version saves 140,000 calls a day with zero change in answers. The normalisation step, deciding which parts of the input do not matter, is where the saving comes from and where bugs hide.

6. Semantic caches: the threshold trade-off

A semantic cache embeds each incoming request (lm10), searches a vector index of previous requests, and if the nearest one's cosine similarity is at least a threshold τ, returns that request's stored answer instead of calling the model. On a miss it calls the model and stores the new request and answer. It turns paraphrases ("How do I reset my password?", "forgot my password, what now?") into hits, which is why hit rates look so attractive in demos.

The cost is wrong answers. Embedding similarity measures how alike two texts look, not whether they need the same answer. Near-misses, requests that are worded almost identically but differ in one decisive detail, are the danger: cancel my order versus cancel my subscription, refund for Pro versus refund for Team, "does it support Python 3.12" versus "3.13". A low threshold catches them as hits.

The lab simulates this: 400 question intents with Zipf-like popularity, a fifth of them with a near-miss twin, 20,000 queries as noisy paraphrases, and a cache that stores every miss. Sweeping the threshold:

The net column puts money on both sides: each hit saves a $0.01 model call, and each wrong answer costs $0.50 (a support contact, a refund, a frustrated user). Net per query = hit rate × ($0.01 − wrong rate × $0.50). At τ = 0.90: 0.776 × (0.01 − 0.0071 × 0.50) = 0.776 × 0.00645 ≈ $0.0050, so $4.99 per thousand. At τ = 0.80 the 19% wrong rate makes each hit cost about nine cents on average, a loss of $85 per thousand queries despite a 98% hit rate. These numbers come from a toy distribution; with your embedding model and traffic the curve will be different, and the method is the point: replay real queries, label whether the cached answer would have been acceptable, and pick the threshold where net value peaks, with a margin for drift.

Two refinements matter in practice. A single global threshold is a crude decision boundary: dense regions of embedding space (many similar but distinct questions) need a higher threshold than sparse ones. vCache (ICLR 2026) learns a threshold per cached entry online, targeting a user-set error bound, and reports up to 12.5× higher hit rates and 26× lower error rates than static-threshold baselines. And the safest semantic caches do not cache arbitrary generated answers at all: they match requests against a curated set of approved answers (an FAQ), so a hit can only ever return text a human has checked, and they partition by tenant and language.

7. Prefix caching in self-hosted serving

If you run your own model with an engine such as vLLM (lm13), prefix caching is your responsibility, and the mechanism is visible. vLLM stores the KV cache in blocks of 16 tokens by default. It identifies each full block by a hash of the block's tokens together with the hash of everything before it, plus extras that change the computation (LoRA adapter, image inputs, a cache salt); since version 0.11 the default hash is SHA-256, a cryptographic hash, which makes accidental collisions between different prefixes practically impossible. When a request arrives, the engine hashes its prompt block by block and reuses every block already in GPU memory, computing only from the first missing block. Only full blocks are cached. Blocks still referenced by running requests stay; blocks no longer referenced go onto a free queue and are evicted least-recently-used when memory is needed.

Two engineering consequences. First, hit rate depends on routing: with eight replicas behind a round-robin load balancer, each prefix is cached in up to eight places and each copy sees an eighth of the traffic. Prefix-aware routing (hash the first few blocks and send matching requests to the same replica, with a fallback when that replica is overloaded) raises hit rate sharply, at some cost to load balance. Second, capacity: cached prefixes compete with running requests for GPU memory, so a heavily cached deployment may offload cold blocks to CPU memory or storage through KV-offloading connectors, trading transfer time for recomputation.

8. Invalidation

Every cache needs an answer to "when is this entry wrong?". Prompt caches handle themselves: a changed prefix simply misses, and a model update starts from empty. Response caches do not. The robust pattern is versioned keys: include the model version, the prompt template version and the versions of any data the answer depends on in the key, so a deploy or a document update creates new keys and old entries age out by TTL, instead of trying to find and delete affected entries. For data that changes unpredictably (prices, stock, policies), either keep TTLs shorter than the acceptable staleness or purge by event (a document update publishes its ID, and entries tagged with it are dropped). Expect a cache stampede after a deploy: every key misses at once and the full traffic hits the model; warm the cache from recent traffic or ramp the deploy gradually.

9. Tenant isolation and the timing side channel

Any shared cache is a channel between the parties that share it. For response caches, the risk is obvious: user B receives an answer generated for user A that contains A's data. Partition keys by tenant and by permission scope; never semantically match across tenants; and do not cache answers built from per-user data at all unless the key includes the user.

The subtler risk is timing. A cache hit is faster than a miss, so anyone who can send a prompt and time the response can test whether someone else recently sent the same prefix. Gu et al. (Stanford, ICML 2025) built statistical audits for exactly this and ran them against 17 API providers in September and October 2024. They detected prompt caching in 8 and global cache sharing (across all customers) in 7, including OpenAI's text-embedding-3-small API, which was patched after their disclosure; Anthropic's and OpenAI's chat APIs shared caches only within an organisation, as their documentation stated. Today both document per-organisation or per-workspace isolation. In self-hosted engines, vLLM supports a per-request cache_salt mixed into the first block's hash, so only requests with the same salt can share blocks. Within an organisation, consider per-user isolation when prompts contain sensitive data that other users must not be able to probe.

10. Measuring the saving honestly

Start from token-level usage, not hit counts. For each request, compute what it would have cost with no caching (all input at the plain rate, the model called even when a response cache answered) and what it did cost (cache writes at their premium, reads at their discount, response-cache hits at zero model cost but with embedding and lookup costs). Sum by feature and tenant. Then add the infrastructure: the vector database, the cache store, embedding calls on every request (including misses), and engineering time. For semantic caches, sample hits, have someone or a calibrated judge check whether the cached answer was acceptable for the new question, and charge wrong answers at a realistic cost.

The cleanest validation is a holdout: route a small random slice of traffic (say 2%) with response caching disabled, and compare cost per request, latency and quality metrics against the cached majority. Without a holdout, savings claims tend to be inflated by counting hits on requests that only exist because of the cache (retries, prefetching) or by ignoring the quality cost of wrong hits.

Hit rate under skewed traffic

Request popularity is usually heavy-tailed: a few prompts or prefixes account for most traffic. With Zipf-like popularity, a small cache captures most of the benefit, because the head of the distribution is hit constantly while the tail rarely repeats within any TTL. This is why per-tenant prompt prefixes cache well for large tenants and poorly for small ones, and why a response cache's hit rate plateaus quickly as it grows. When estimating savings before building, plot the cumulative share of traffic covered by the top N distinct prefixes or normalised requests; the curve tells you the achievable hit rate far better than an average.

Prompt caching for agents and long conversations

Agent loops (ag5, ag13) resend the whole growing context every step, so input tokens grow roughly with the square of the number of steps. Prompt caching turns most of that into reads, provided the context is append-only: the earlier steps never change, each step adds tool results and the model's turn at the end. Practices that break this include rewriting earlier tool results, re-ordering the tool list when tools are enabled dynamically, and compaction that rewrites history. Compaction is sometimes necessary, but each rewrite costs a full write of the new prefix, so compact in large, infrequent steps rather than a little every turn. Anthropic's 20-block lookback is a concrete version of the same concern: if one turn adds more than 20 blocks (many parallel tool results), the next request's breakpoint may be too far past the last written entry, and a second breakpoint is needed.

Caching changes the distribution of answers

A response cache makes repeated questions get identical answers. That can be a feature (consistency, auditability) or a bug (an unlucky sample is now served to everyone; a creative feature stops varying). It also hides model changes: after an upgrade, cached old answers keep appearing until they expire, which confuses A/B tests and quality monitoring. Tag every response with whether it came from a cache and which model produced it, and exclude cached responses from evaluations of the current model.

Cache what is deterministic upstream

Often the safest large saving is not caching answers but caching the expensive deterministic steps before the model: embeddings of documents and frequent queries, retrieval results for a query and index version, tool results for idempotent calls (a product lookup, a currency rate with a short TTL), and parsed or summarised versions of long documents. These caches are correct by construction (same input, same output), they shrink prompts, and they leave the model to generate a fresh answer from fresh context.

Semantic caching as a classification problem

Deciding "can request B reuse A's answer?" is binary classification, and a cosine threshold is a one-feature classifier. It can be improved like any classifier: features beyond the embedding (exact match of key entities such as product names, numbers and negations), a small trained model that predicts answer equivalence, or an LLM verifier on candidate hits (which costs a model call but a cheap one). The economics then compare the verifier's cost with the saving and the reduced error. The decision should always be framed by the asymmetric costs: false hits (wrong answers) are usually far more expensive than false misses (an unnecessary model call).

Why the providers price writes above reads

A cache entry occupies accelerator or host memory for its lifetime, and the provider's routing must send later requests to wherever it lives. The write premium pays for storing state that may never be reused; the read discount reflects the prefill computation skipped. Longer TTLs cost more to write because the memory is held longer. This framing predicts the right behaviour: write only what will be reused, and choose the TTL from measured inter-arrival times. It also explains overflow behaviour: a single extremely hot prefix can exceed what one machine serves, so the provider spreads it, and some requests land where the entry is not.

Speculative and partial reuse

Research systems go further than exact prefixes: reusing KV state for documents that appear in different positions in different prompts (with corrections for the positional mismatch), or composing cached segments. These can raise reuse in retrieval-heavy workloads where the same documents appear in different orders, but they no longer guarantee identical outputs. In production today, treat anything beyond exact-prefix reuse as an approximation that needs its own quality evaluation.

The public case: auditing prompt caching across 17 API providers (Gu et al., ICML 2025)

Researchers at Stanford asked a question every multi-tenant cache should be asked: can one customer tell whether another customer's prompt is cached? They built a statistical test: send prompts that should be cache misses and prompts constructed to be cache hits, measure response times, and test whether the two timing distributions differ, at three levels of sharing (per user, per organisation, global). In September and October 2024 they audited 17 providers, detected prompt caching in 8, and detected global cache sharing in 7, meaning that in principle an attacker could learn whether anyone had sent a given prompt prefix. Anthropic's and OpenAI's chat APIs showed per-organisation sharing, exactly as their documentation stated; OpenAI's text-embedding-3-small API showed global sharing, which was patched after the researchers' disclosure. The timing also leaked architecture: it suggested OpenAI's embedding model is a decoder-only transformer, which had not been public. The lesson for engineers is that a cache is part of your security boundary: document its sharing level, partition it, and test it.

Failure modes

Hit-rate collapse after a deploy. A new system prompt version (or an innocent timestamp) changes the prefix and every request becomes a write. Alert on the ratio of cache-read to cache-write tokens per feature, not just on cost.

Bill increase from writes. Many distinct prefixes with low reuse, breakpoints after variable content, or a 1-hour TTL on sparse traffic. Usage fields show write tokens far exceeding read tokens.

Stale answers. A response cache keeps serving an answer after the policy document changed, or after a model upgrade. Versioned keys and short TTLs on fact-dependent answers prevent it.

Wrong semantic hits. Users receive answers to a different question; it shows up as complaints, escalations and odd thumbs-down clusters. Sample hits weekly for correctness; break down hit rate and complaint rate by intent.

Cross-tenant leakage. A key without the tenant, or a semantic index shared across tenants, returns one customer's answer to another. Treat it as a security incident, not a cache bug.

Routing dilution. In self-hosting, more replicas without prefix-aware routing lowers per-replica hit rate, so adding capacity can make each request more expensive.

What to put on the dashboard

Per feature and tenant: token-weighted prompt-cache hit rate, write versus read tokens, estimated saving against the uncached counterfactual, time to first token for hits versus misses; for response caches, hit rate, entry age at hit, invalidations per deploy; for semantic caches, hit rate by threshold band, audited wrong-hit rate, and complaints on cached versus uncached answers. Review the holdout comparison monthly.

Knobs and when to turn them

For prompt caching: breakpoint placement (after the last stable block), TTL (5 minutes for steady traffic, longer only when measured inter-arrival times sit between five minutes and an hour), and on OpenAI's older models a stable prompt_cache_key per shared prefix to improve routing, split across a few keys when one prefix exceeds about 15 requests per minute. For response caches: TTL per answer type, normalisation rules, and which features are allowed to use the cache at all. For semantic caches: the threshold, the set of answers eligible to be served from cache, partitioning, and the sampling rate for correctness audits. Change one knob at a time and read the effect on the holdout comparison, because caching changes interact: a better prompt cache makes each model call cheaper, which lowers the value of every response-cache hit and moves the semantic threshold that pays.

import numpy as np
rng = np.random.default_rng(7)
DIM, INTENTS, QUERIES = 64, 400, 20_000
CALL_COST, WRONG_COST = 0.01, 0.50     # $ saved per hit, $ cost per wrong cached answer

def unit(v): return v / np.linalg.norm(v, axis=-1, keepdims=True)

centres = unit(rng.standard_normal((INTENTS, DIM)))
for k in range(0, INTENTS, 5):          # every 5th intent gets a near-miss twin
    centres[k + 1] = unit(centres[k] + rng.normal(0, 0.04, DIM))
popularity = 1 / np.arange(1, INTENTS + 1) ** 1.1
popularity /= popularity.sum()
intents = rng.choice(INTENTS, QUERIES, p=popularity)
spread = rng.uniform(0.02, 0.06, QUERIES)[:, None]
queries = unit(centres[intents] + rng.standard_normal((QUERIES, DIM)) * spread)

def run(threshold):
    emb = np.empty((QUERIES, DIM)); lab = np.empty(QUERIES, int); n = hits = wrong = 0
    for q, it in zip(queries, intents):
        if n:
            sims = emb[:n] @ q
            j = int(sims.argmax())
            if sims[j] >= threshold:
                hits += 1; wrong += lab[j] != it; continue
        emb[n], lab[n] = q, it; n += 1  # miss: call the model and cache the answer
    return hits / QUERIES, wrong / max(hits, 1), n

for t in (0.80, 0.85, 0.90, 0.93, 0.95, 0.97):
    h, w, n = run(t)
    print(f"{t:.2f}  hit {h:6.1%}  wrong/hit {w:6.2%}  entries {n:6d}  "
          f"net ${1000 * h * (CALL_COST - w * WRONG_COST):+.2f} per 1k")

What to look for. As the threshold rises, hit rate falls and wrong answers fall faster; the cache also grows, because more paraphrases become separate entries. With these settings the low thresholds lose money despite near-perfect hit rates, and the net value peaks around 0.90 to 0.93. Now change WRONG_COST to 5.00 (a wrong answer triggers a refund) and watch the best threshold move up; change the twin noise from 0.04 to 0.08 (near-misses less similar) and watch low thresholds become safer. That sensitivity is the argument for tuning on your own traffic.

Current cost. Input 31,560 tokens × $2/M = $0.0631; output 250 × $10/M = $0.0025; total about $0.066 per question.

Prompt caching. Order the prompt as system prompt, then that company's handbook (stable for a month), then the question, with a breakpoint after the handbook. The cached prefix is 31,500 tokens. With 1.25× writes and 0.05× reads: hit ≈ 31,500 × $0.10/M + 60 × $2/M + $0.0025 ≈ $0.0058; miss ≈ 31,500 × $2.50/M + … ≈ $0.081. Hit rate by company: a company with 2,000 questions over 9 working hours averages one every 16 seconds, so nearly every request hits on a 5-minute TTL; one with 5 a day averages one every ~2 hours and almost always misses, so caching costs it about 24% more. Use the 5-minute TTL for large tenants; for tiny tenants either skip caching or consider whether a 1-hour TTL (2× write) gets their hit rate above break-even. For the large tenants the saving approaches 90% of the per-question cost.

Response caching. HR questions repeat ("how many vacation days", "parental leave policy"). An exact-match cache on normalised question text, keyed by company and handbook version, catches true repeats. A semantic cache over generated answers is risky (policies differ by country, seniority, contract type: classic near-misses); instead, build a curated FAQ per company from the most frequent questions, reviewed by HR, and semantically match only against that set with a high threshold tuned on replayed questions.

Invalidation and isolation. Include the handbook version in every key, so the monthly update invalidates cleanly; partition everything by company; record cache source on each answer. Measurement: compute counterfactual cost from usage fields, keep a 2% holdout without response caching, and audit semantic hits weekly.
