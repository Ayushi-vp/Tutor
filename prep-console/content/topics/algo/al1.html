Picture two candidates given the same problem: given an array of integers and a target, return the indices of two numbers that add up to the target. The first one recognises it, says "hash map", types a solution in four minutes in silence, and announces "done". The interviewer asks "what if the array can be empty?" and the code crashes. They ask "why a hash map?" and get "it's the standard approach". The second candidate spends two minutes asking whether the array is sorted, whether there is always an answer and whether the same element can be used twice; works one example on the whiteboard; says the obvious double loop is O(n²); notices that for every number the inner loop is just searching for one specific value; and concludes that a hash map turns that search into a constant-time lookup. They code it in six minutes, then trace it on their example and on an empty array. The second candidate took longer and gets the stronger score.

That surprises many people, because they think a coding round is a test of whether you know the answer. It is not. Interviewers usually score you on four separate dimensions: problem solving (did you find a good approach and can you justify it), coding (is the code correct, clean and idiomatic), verification (did you test it and find your own bugs) and communication (could the interviewer follow your thinking and work with you). Knowing the answer helps only the first, and only if you can explain it.

Without a method, three things go wrong under pressure. You freeze when you do not recognise the problem, because there is no next step to fall back on. You rush into code with a half-formed idea and have to rewrite it. And you finish with code you have never checked, so the interviewer finds the bug instead of you. A method fixes all three: it always gives you a next move, it makes you choose an approach before you type, and it builds testing into the end.

This lesson gives you that method — seven steps you can use on every problem in this track — and the reasoning behind each one. It also introduces the idea that drives all the later lessons: most efficient solutions are a brute force with one kind of repeated work removed, and each pattern is a standard way of removing one kind of repeated work.

The mental model: a doctor's consultation, not a quiz

A good way to think about a coding round is a doctor seeing a patient. A doctor does not hear "my chest hurts" and immediately write a prescription. They ask questions (where, since when, what makes it worse), examine the patient, form a first diagnosis, rule out the dangerous possibilities, decide on a treatment, and then check whether it worked. A doctor who prescribed instantly might sometimes be right, but you would not trust them, and they would be badly wrong whenever the case was unusual. The interviewer is watching for the same thing: a process that is reliable on problems you have never seen, not a lucky guess on one you have.

The analogy breaks in one place. A real doctor works alone; in an interview the "patient" — the interviewer — knows the answer and wants you to succeed. They will answer questions, give hints, and tell you when you are going down a wrong path, but only if they can follow what you are doing. That is why communication is a full quarter of the score.

The seven steps

Here is the whole method at a glance. Each step is explained in detail in the next section.

  1. Understand. Restate the problem in your own words and ask clarifying questions.
  2. Examples. Work two or three small inputs by hand, including at least one edge case.
  3. Brute force. Say the simplest correct solution and its complexity.
  4. Optimise. Find the repeated work in the brute force and choose the pattern that removes it.
  5. Agree. Summarise the approach and complexity and get a nod before coding.
  6. Code. Write it top-down, with clear names, talking through decisions.
  7. Verify. Trace the code by hand on your example and on the edge cases; fix bugs out loud.

Notice the shape of the timeline. Roughly the first twenty minutes involve no code at all. Beginners find this uncomfortable, because typing feels like progress. But a correct approach agreed in minute 18 usually becomes correct code by minute 35, while an unexamined idea typed in minute 4 often becomes a rewrite in minute 25 and unfinished code at the end.

The steps are not a rigid script. On an easy problem steps 3 and 4 may take thirty seconds together; on a hard one you may loop between steps 2 and 4 several times. What matters is that you always know which step you are in, so that you always have a next move.

If you remember one sentence from this primer, make it this: the optimal solution is usually the brute force with one kind of repeated work removed. Step 4 — find the repetition, pick the pattern that removes it — is where the rest of this track lives.

Step 1 — Understand: restate and clarify

Start by saying the problem back in your own words: "So I get an unsorted list of integers and a target, and I return the two indices whose values add to the target." This takes ten seconds and catches misunderstandings that would otherwise cost you the round, such as returning values when the interviewer wanted indices.

Then ask clarifying questions. Problems are often underspecified on purpose, and the missing details change the solution. A short checklist covers almost everything:

  • Size. How large can the input be? (This decides the complexity you need — see the next lesson, al2.)
  • Values. Can numbers be negative, zero or very large? Are strings ASCII or Unicode? Can there be duplicates?
  • Shape. Is the input sorted? Can it be empty? Is a graph connected, directed, possibly cyclic?
  • Output. What exactly do I return — indices or values, one answer or all, in what order? What if there is no answer?
  • Environment. Can I modify the input? Is it a stream I see once, or all in memory?

You do not need to ask all of them every time; ask the ones whose answers would change your approach. For Two Sum, "is it sorted?" matters (sorted input allows a two-pointer solution with no extra memory), "can the same element be used twice?" matters, and "is there always exactly one answer?" decides what you return otherwise. Write the answers down where you and the interviewer can see them.

Step 2 — Examples: work it by hand

Before thinking about algorithms, solve two or three small inputs yourself. Choose them deliberately: one normal case, one that exercises a tricky rule, and one edge case. For Two Sum with target 9:

  • [2, 7, 11, 15] → indices [0, 1], a normal case.
  • [3, 3] → [0, 1], duplicates that together form the answer.
  • [5] → no answer, which tests what you return.

Examples do two jobs. They confirm you and the interviewer agree on the expected output before any code exists. And — this is the part beginners miss — the way you solve the example by hand is often the algorithm. When you look at [2, 7, 11, 15] and target 9, your eye sees 2 and immediately looks for 7. That "look for the complement" move is the hash-map solution. Pay attention to what your brain does on an example; it is usually smarter than your first formal idea.

Make examples big enough to be representative. An example of length 2 hides most bugs. Five to eight elements, not sorted, with a duplicate, is a good default.

Step 3 — Brute force: the simplest correct solution

Now say the most direct solution that is definitely correct, and its cost. For Two Sum: "Try every pair with two nested loops and return the first pair that sums to the target. That is O(n²) time and O(1) extra space." Big-O notation describes how the work grows as the input grows: O(n²) means doubling n roughly quadruples the work. (The next lesson, al2, teaches how to compute it and how to match it to the input size.)

Do not code the brute force unless the interviewer asks or you are completely stuck. Saying it takes one minute and earns three things: proof that you understood the problem, a correct fallback if nothing better appears, and — most importantly — a concrete object to optimise. It is much easier to improve a specific slow algorithm than to invent a fast one from nothing.

Step 4 — Optimise: find the repeated work, then the pattern

Look at the brute force and ask: what does it compute again and again? In the Two Sum double loop, the inner loop asks, for a fixed a[i], "is there a j with a[j] == target − a[i]?" That is a search for one specific value, repeated n times, and each search costs O(n). A structure that answers "have I seen this value, and where?" in constant time is a hash map. Replace the inner loop with a lookup and the whole thing becomes O(n) time and O(n) space.

If you are stuck, go back to step 2 with a new example, chosen to be bigger or more awkward. Solve it by hand, slowly, and write down what you are keeping track of in your head. Those things you track — "the largest value so far", "the last place I saw this letter" — are your variables and data structures.

Step 5 — Agree before coding

Summarise in two or three sentences: "I'll scan once, keeping a map from value to index. For each number I check whether target minus it is already in the map; if so I return both indices, otherwise I store the current one. O(n) time and O(n) space. Does that sound good?" This is a cheap checkpoint. If the interviewer wanted something else — constant space, or all pairs — you find out now, not after coding. Interviewers frequently say at this point "great, go ahead" or "can you do it without extra memory?"; both are useful.

Step 6 — Code: top-down, readable, narrated

Write the code in the order you would explain it. Start with the function signature and the main loop; if a piece is fiddly, call a helper function with a good name and write it afterwards (for example in_bounds(r, c) or merge(left, right)). Use names that carry meaning (seen, need, left) rather than a, b, tmp. Before a loop, say its invariant — the statement that stays true every time around — because most loop bugs are invariant bugs.

def two_sum(nums, target):
    seen = {}                       # value -> index of an earlier element
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:            # invariant: seen holds nums[0..i-1]
            return [seen[need], i]
        seen[x] = i                 # store after checking: no reuse of i
    return []                       # agreed: empty list when no pair

Notice the small decisions, each spoken aloud: check before storing so an element cannot pair with itself; store the first index of a duplicate value is fine because we return as soon as a pair is found; return an empty list for no answer, as agreed in step 1. Narrate decisions like these, not keystrokes.

When you find a bug during the trace, say so plainly, explain the cause, make the smallest fix, and re-trace the part you changed. Finding your own bug is scored as a positive; it is exactly the verification skill the rubric looks for.

A second walk-through: a problem you do not recognise

The method earns its keep on problems you have not memorised. Take: "Given a list of daily temperatures, for each day return how many days you must wait for a warmer temperature, or 0 if none." Restate: for each index, the distance to the next strictly larger value to its right. Clarify: can there be up to 10⁵ days (yes), are temperatures integers (yes), what about equal temperatures (not warmer, keep waiting). Example: [73, 74, 75, 71, 69, 72, 76, 73] → [1, 1, 4, 2, 1, 1, 0, 0]. Brute force: for each day scan right until a warmer one, O(n²) — 10¹⁰ steps at n = 10⁵, too slow.

Now the optimise step. Solve the example by hand and watch what you track. Walking left to right, days 71 and 69 are "still waiting"; when 72 arrives it answers 69 and then 71, but not 75. The waiting days always form a decreasing run of temperatures, and a new warmer day answers the most recent waiting days first. "Most recent first" is a stack. So: keep a stack of indices still waiting; for each new day, pop while the top is colder and record the distance; then push the new day. Each index is pushed and popped once, so O(n) total. You have just derived the monotonic stack (lesson al8) without knowing its name — which is the point of the method.

How to talk: communication as a skill

The communication dimension is not about talking constantly. It is about keeping the interviewer able to follow and help you. Three habits do most of the work. Signpost: "I'm going to handle the empty case first, then the main loop." Explain decisions: "I'm using a deque here because I pop from the front." Announce silence: "Let me think about the boundary for thirty seconds." When you are stuck, think out loud about what you have tried and why it fails — that is when interviewers give hints, and they can only give a useful hint if they know where you are.

Why the brute-force-then-optimise route works so often

Most interview problems are designed by taking a natural brute force and asking for something faster. The fast solution therefore almost always reuses information the brute force throws away. The double loop in Two Sum recomputes "where is the complement?" from scratch for every i, even though the elements before i never change. Prefix sums reuse the sum of a[0..i−1] instead of re-adding it. Dynamic programming reuses answers to subproblems. Monotonic stacks reuse the fact that some elements can never be the answer again. When you look at a brute force and ask "what am I throwing away that I could keep?", you are asking the question the problem setter designed the problem around.

The best conceivable runtime as a target

The best conceivable runtime is the lowest complexity that any solution could possibly have, usually because it must at least read the input or write the output. Printing all subsets of n elements cannot be faster than O(2ⁿ) because there are 2ⁿ of them; finding the maximum of an unsorted array cannot be faster than O(n) because any unread element could be the maximum. This gives you a stopping rule — if you are at the best conceivable runtime, stop optimising time and look at space or code clarity — and a direction: if you are at O(n log n) and the best conceivable is O(n), ask what is forcing the log factor (usually a sort or a heap) and whether you really need full order.

Recognition versus derivation

Pattern recognition is real and valuable — that is why the DSA list in this app is grouped by pattern. But there is a trap: recognition gives you the what without the why. Interviewers probe the why with variations: "now the array is a stream", "now values can be negative", "now return all pairs". A sliding-window solution to "longest subarray with sum ≤ k" works only because all values are non-negative (so extending the window never decreases the sum); a candidate who recognised it but did not derive it will not notice when a follow-up allows negatives and breaks the method. Each later lesson therefore names the precondition of its pattern — the property of the input that makes it valid. Saying it unprompted is one of the clearest strong signals in a coding round.

Invariants are how you write loops that are right the first time

An invariant is a sentence that is true at the start of every iteration of a loop. For binary search: "if the target exists, it lies in a[lo..hi]". For the two-sum map: "seen contains exactly the elements before i". If you state the invariant first, three things become mechanical: initialisation (make it true before the first iteration), the loop body (keep it true), and termination (when the loop stops, the invariant plus the stopping condition gives you the answer). Most off-by-one bugs come from an invariant that was never stated, so the code mixes two slightly different ones — for example half the code thinks hi is inclusive and half thinks it is exclusive.

Choosing a language and using its library well

Use the language you are fastest and most accurate in; for most interviews Python is a strong choice because the code is short and close to pseudocode. Know its standard tools cold: collections.Counter, defaultdict and deque, heapq (a min-heap), bisect (binary search on sorted lists), sorted(key=...), and functools.cache for memoisation. Also know their costs: list.pop(0) and x in some_list are O(n), slicing copies, and string concatenation in a loop can be quadratic. Using the library well is scored as code quality; using an O(n) call inside a loop by accident turns your O(n) solution into O(n²), and interviewers notice.

Follow-ups are the second half of the problem

Strong interviewers plan one or two follow-ups: a constraint change (stream instead of array, memory limit, very large values), a generalisation (k numbers instead of two), or a production angle (how would you test this, what if it ran on a thousand machines). Answering these well depends on the understanding you built while deriving the solution. Before you finish, it is worth asking yourself the obvious follow-up and mentioning it: "If the input didn't fit in memory, I'd …". That shows the senior habit of thinking past the immediate task.

In the interview room

This lesson's "production" is the interview itself — the real conditions you will perform under. The common failure modes are predictable, and each has a specific fix.

Coding too early. The symptom is a rewrite in the middle of the round. The cause is starting to type an idea that has not been checked against an example. The fix is the agreement step: never type until you can say the approach and its complexity in two sentences and the interviewer has nodded.

Silent struggle. The symptom is two or three minutes of silence. The interviewer cannot tell whether you are close to an insight or lost, so they cannot help, and the communication score drops. The fix is to think out loud about what you have tried and why it fails — that gives the interviewer an opening for a hint.

Over-engineering. Classes, generic helpers and exhaustive input validation for a 25-line problem. It costs time and hides the algorithm. Write a function, validate only what you agreed in step 1, and mention what production code would add rather than writing it.

Untested "done". The interviewer then traces your code and finds the bug, which moves credit from you to them. Always trace before saying you are finished.

Ignoring the time. In a 45-minute round with two problems, spending 35 minutes on the first one is a common way to fail. Ask at the start whether there will be more than one problem, and keep a rough clock: about 20 minutes per medium problem.

Online and remote variants

Many companies now run the first stage as an online assessment (OA): an automated test on a platform such as HackerRank or CodeSignal, typically two problems in 60–90 minutes, scored by hidden test cases. The method still applies, but compressed: read the constraints first (they tell you the complexity needed), write a brute force if you cannot see the optimal one quickly (partial credit from passing some tests is real), and test edge cases yourself because the hidden tests will. In live remote rounds on a shared editor, you usually cannot run code, so step 7 by hand is essential. Some companies now run rounds where an AI assistant is allowed; the same method applies, and the scoring shifts towards how well you specify, check and correct the assistant's output — steps 1, 2 and 7 matter even more.

Finally, panic after a bad first problem. Rounds are scored as a whole, and many offers include one shaky problem. Reset deliberately: take a breath, restate the next problem, and run the method from step 1.

How this maps to real engineering

The method is not interview theatre. Clarifying requirements, working examples, starting from a simple correct version, finding the bottleneck, agreeing on the design, writing readable code and testing it is how good engineers work on real tickets. Profilers in production play the role of step 4: they show you which repeated work dominates. That is why companies keep using this format; it is a small, timed version of the job.

Practise the method on one problem with a timer, and build the habit of testing a fast solution against a brute force — a technique called stress testing that you will reuse in every lesson.

  1. Set a 20-minute timer. Take Two Sum (or any problem from the DSA list you have not seen). Do steps 1–5 on paper, out loud, before writing code. Write the clarifying questions and your three examples down.
  2. Code the brute force and the optimised version in one file, stress.py: 
    import random

def brute(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return True
    return False

def fast(nums, target):
    seen = set()
    for x in nums:
        if target - x in seen:
            return True
        seen.add(x)
    return False

for trial in range(20000):
    n = random.randint(0, 8)
    nums = [random.randint(-5, 5) for _ in range(n)]
    target = random.randint(-10, 10)
    if brute(nums, target) != fast(nums, target):
        print("MISMATCH", nums, target)
        break
else:
    print("all 20000 random tests agree")
  3. Run python stress.py. You should see "all 20000 random tests agree".
  4. Now plant a bug: in fast, move seen.add(x) above the if. Run again. The script prints a small failing input such as [3] 6 almost immediately — the element is paired with itself.

What this proves: small random inputs with a tiny value range find edge cases (duplicates, negatives, empty lists) far faster than hand-picked tests, and the failing case is small enough to trace by hand. Comparing booleans (does a pair exist?) instead of indices avoids false alarms when several answers are valid.

Run the method on an unseen problem

The interviewer says: "Given a string, return the first character that does not repeat anywhere in it." Go through steps 1–5 out loud. What do you ask, what examples do you use, what is the brute force, and what is the optimised plan?

Answer

Understand: restate it ("return the earliest character whose total count is one"). Ask: what to return if none (say an empty string or None — agree one); is it case-sensitive; ASCII or Unicode; how long can the string be? Examples: "leetcode" → "l"; "loveleetcode" → "v"; "aabb" → none; "" → none; "z" → "z". Brute force: for each position, scan the whole string counting that character; return the first with count 1 — O(n²) time, O(1) space. Optimise: the repeated work is counting the same character again and again; count every character once with a hash map (or a 26-slot array for lowercase ASCII) in one pass, then make a second pass in the original order and return the first character with count 1. O(n) time, O(k) space where k is the alphabet size. Agree: "Two passes: count with a Counter, then scan in order for count 1; O(n) time, O(alphabet) space." Verify: trace "loveleetcode": counts l2 o2 v1 e4 t1 c1 d1; the second pass hits l(2), o(2), v(1) → "v". Edge cases: empty string returns the agreed sentinel; "aabb" scans everything and returns it too. A likely follow-up is "the string is a stream and you must answer after each character" — keep counts plus an ordered structure of characters seen once (an OrderedDict or a queue with lazy removal).
