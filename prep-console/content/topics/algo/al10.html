A hospital emergency department does not treat patients in arrival order. A nurse assigns each arriving patient a priority, and whenever a doctor becomes free, the most urgent waiting patient goes next. Patients keep arriving and leaving, so the "most urgent" one keeps changing. If the department kept the waiting list fully sorted, every arrival would mean re-sorting; if it kept the list unsorted, every time a doctor became free someone would scan the whole list. Neither is good when hundreds of patients pass through.

That situation — a collection that keeps changing, where you repeatedly need only the best element — is what a priority queue handles, and a binary heap is how it is almost always built. A heap gives you the minimum (or maximum) instantly and lets you insert or remove in O(log n) time. For a million elements, that is about 20 steps per operation instead of a million.

Interview problems use heaps in a handful of recognisable patterns. Top-k: the k largest, closest, or most frequent items among n, in O(n log k) — far better than sorting when k is small. Two heaps: the median of a stream, maintained as numbers arrive. K-way merge: combining k sorted lists or streams. Greedy scheduling: meeting rooms, CPU task order, choosing projects, reorganising strings — always "pick the best available option now", where a heap holds the options. Dijkstra's shortest-path algorithm (al20) is also a heap at its core.

This lesson explains how a heap works inside (because interviewers sometimes ask you to implement one, and because knowing the mechanics explains the costs), how to use Python's heapq correctly, and each of the patterns above with a worked example.

The mental model: a company org chart where every boss outranks their reports

Imagine an organisation chart drawn as a tree, with one rule: every manager is more senior (here, "smaller", for a min-heap) than the people who report to them. Nothing is said about how two colleagues on the same level compare, or about cousins in different departments. But the rule alone guarantees one thing: the person at the top of the chart is the most senior of everyone. That is a heap: a tree where each parent is no larger than its children, which puts the minimum at the root.

The heap is kept as a complete binary tree — each manager has at most two reports, and the levels fill left to right with no gaps. That shape keeps the tree's height at about log₂ n, and it lets the whole tree live in a plain array with no pointers at all: the root is index 0, and the children of index i are 2i + 1 and 2i + 2; the parent of i is (i − 1) // 2.

Two operations keep the rule true. To push, put the new element in the next free spot at the bottom and let it "climb": while it is smaller than its parent, swap them. To pop the minimum, take the root, move the last element into the root's place, and let it "sink": while it is larger than its smaller child, swap them. Each walks at most the height of the tree, so both are O(log n). Peeking at the minimum is just reading index 0.

Where the analogy breaks: in a real organisation you might ask "who is the third most senior person?" and expect the chart to tell you. A heap cannot answer that cheaply. It only knows the top. If you need arbitrary order queries (the k-th smallest, everything between two values), use a sorted structure instead. A heap's strength is exactly and only "give me the best one, repeatedly, while things change".

It is also worth fixing the vocabulary. A priority queue is the abstract idea: a collection you can add items to, each with a priority, and from which you can always remove the highest-priority item. A binary heap is one concrete way to build it. Other implementations exist — a sorted list (cheap removal, expensive insertion), an unsorted list (cheap insertion, expensive removal), a balanced search tree (both O(log n), more memory and more general) — but the heap wins for the common case because it is compact, simple and fast. In interviews, "priority queue" and "heap" are used interchangeably.

That narrow strength is also why a heap beats full sorting in so many problems. If you need the 10 largest numbers out of a billion, sorting all billion does far more work than necessary; a heap that only ever holds 10 candidates does about a billion cheap comparisons and a few log₂ 10 ≈ 3-step adjustments. Paying only for the order you actually use is the recurring theme of this lesson.

Inside the heap: push and pop, traced

Start from the heap array [1, 3, 2, 7, 4, 5, 9] in the figure. Push 0: append it at index 7, whose parent is (7 − 1) // 2 = 3 (value 7). 0 < 7, swap → index 3; parent is index 1 (value 3), swap → index 1; parent is index 0 (value 1), swap → index 0. Result: [0, 1, 2, 3, 4, 5, 9, 7]. Three swaps for a heap of 8: log₂ 8 = 3.

Pop from that: return 0, move the last element (7) to the root: [7, 1, 2, 3, 4, 5, 9]. Sift down: children of 0 are 1 and 2; the smaller child is 1, and 7 > 1, so swap → [1, 7, 2, 3, 4, 5, 9]. Children of index 1 are indices 3 and 4 (values 3 and 4); smaller is 3, 7 > 3, swap → [1, 3, 2, 7, 4, 5, 9]. Index 3 has no children; stop. Always swap with the smaller child, or the heap rule would break between the two children.

def sift_up(h, i):
    while i > 0 and h[(i - 1) // 2] > h[i]:
        p = (i - 1) // 2
        h[i], h[p] = h[p], h[i]
        i = p

def sift_down(h, i):
    n = len(h)
    while True:
        smallest, l, r = i, 2 * i + 1, 2 * i + 2
        if l < n and h[l] < h[smallest]: smallest = l
        if r < n and h[r] < h[smallest]: smallest = r
        if smallest == i: return
        h[i], h[smallest] = h[smallest], h[i]
        i = smallest

Interviewers occasionally ask you to implement a heap from scratch; those two functions plus push (append, sift up) and pop (swap root with last, pop last, sift down the root) are the whole thing. heapify — turning an arbitrary array into a heap — calls sift_down on every non-leaf index from (n // 2) − 1 down to 0, and costs O(n), not O(n log n) (the deep layer explains why).

Using heapq correctly

Python's heapq works on an ordinary list and is always a min-heap:

import heapq
h = []
heapq.heappush(h, 5); heapq.heappush(h, 1); heapq.heappush(h, 3)
h[0]                      # 1, peek
heapq.heappop(h)          # 1
heapq.heapify(data)       # in place, O(n)
heapq.heappushpop(h, x)   # push then pop, faster than two calls
heapq.nlargest(k, data)   # convenience top-k
heapq.nsmallest(k, data, key=...)

Three practical rules prevent most bugs. Max-heap: push −x and negate on the way out. Priorities with payloads: push tuples (priority, item); tuples compare element by element, so the priority decides. Ties: if two priorities are equal, Python compares the next field, and if that is an object without ordering (a ListNode, a dict), you get TypeError: '<' not supported. Insert a tie-breaker that is always comparable — an index or an increasing counter: (priority, count, item). The heapq documentation recommends exactly this.

Pattern 1: top-k with a size-k heap

"Find the k largest elements" (or the k-th largest). Keep a min-heap holding the k largest seen so far. Its root is the smallest of those k — the current k-th largest, and the threshold a newcomer must beat.

def kth_largest(nums, k):
    h = []
    for x in nums:
        heapq.heappush(h, x)
        if len(h) > k:
            heapq.heappop(h)          # drop the smallest of k+1
    return h[0]

Trace nums = [3, 2, 1, 5, 6, 4], k = 2: the heap goes [3] → [2, 3] → push 1, pop 1 → [2, 3] → push 5, pop 2 → [3, 5] → push 6, pop 3 → [5, 6] → push 4, pop 4 → [5, 6]. Root 5 is the 2nd largest. Cost O(n log k) time and O(k) memory, which beats sorting (O(n log n)) when k is small, and works on a stream that never ends — "Kth Largest Element in a Stream" is this function split into a constructor and an add method.

The same shape answers many questions by changing the key. K closest points to the origin: keep the k smallest distances, so use a max-heap of size k (push (−distance², point)) and pop the farthest whenever it grows past k. Top k frequent elements: count with a Counter, then keep a min-heap of size k over (count, value) pairs.

Two alternatives are worth naming. Quickselect partitions around a random pivot and recurses into one side only, finding the k-th largest in O(n) average time — faster, but O(n²) worst case and not suitable for streams. Bucket sort fits frequencies: counts are between 1 and n, so make an array of n + 1 lists indexed by count and read from the top; that is O(n) for top-k frequent.

Pattern 2: two heaps for the running median

"Numbers arrive one at a time; after each, report the median." Sorting after every insert is O(n log n) each. Instead split the numbers into two halves: a max-heap lo holding the smaller half and a min-heap hi holding the larger half. Keep every element of lo ≤ every element of hi, and keep the sizes equal or lo one larger. Then the median is lo's top (odd count) or the average of both tops (even count).

class MedianFinder:
    def __init__(self):
        self.lo, self.hi = [], []          # lo: max-heap via negation
    def add(self, x):
        heapq.heappush(self.lo, -x)
        heapq.heappush(self.hi, -heapq.heappop(self.lo))  # move lo's max up
        if len(self.hi) > len(self.lo):                   # rebalance
            heapq.heappush(self.lo, -heapq.heappop(self.hi))
    def median(self):
        if len(self.lo) > len(self.hi):
            return -self.lo[0]
        return (-self.lo[0] + self.hi[0]) / 2

The "push into lo, move lo's max to hi, rebalance" sequence is a neat way to avoid comparing x with the tops by hand: it guarantees the ordering invariant (lo's max ends up no larger than hi's min) and the size invariant in three lines. The sliding-window median adds removals, which a heap cannot do directly; the standard fix is lazy deletion — record elements to delete in a counter and discard them when they reach a top.

Pattern 3: k-way merge

"Merge k sorted lists." Merging two lists takes the smaller of two heads; merging k lists needs the smallest of k heads, repeatedly — a priority queue of size k.

def merge_k_lists(lists):
    h = [(node.val, i, node) for i, node in enumerate(lists) if node]
    heapq.heapify(h)
    dummy = tail = ListNode()
    while h:
        val, i, node = heapq.heappop(h)
        tail.next = node; tail = node
        if node.next:
            heapq.heappush(h, (node.next.val, i, node.next))
    return dummy.next

Each of N total nodes is pushed and popped once in a heap of size at most k: O(N log k). The index i is the tie-breaker that stops Python from comparing two ListNodes. The same structure solves "smallest range covering one element from each of k lists" (also track the current maximum among the heads; the range is [heap min, current max]), "k-th smallest element in a sorted matrix" (rows are k sorted lists), and "find k pairs with the smallest sums" (a heap of candidate index pairs, expanded lazily). It is also how external sorting merges sorted runs from disk.

Pattern 4: greedy scheduling

Many problems have the shape "at each moment, choose the best available option", where options become available over time. Sort the inputs by when they become available, and keep the available options in a heap keyed by "best".

Meeting Rooms II (minimum rooms needed): sort meetings by start; keep a min-heap of end times for meetings in progress. For each meeting, if the earliest end is ≤ its start, that room is free — pop it. Push the new meeting's end. The largest heap size during the sweep is the answer. For [[0, 30], [5, 10], [15, 20]]: push 30; at 5, earliest end 30 > 5, push 10 (two rooms); at 15, earliest end 10 ≤ 15, pop it, push 20 (still two). Answer 2.

Single-Threaded CPU: tasks have an enqueue time and a processing time; the CPU, when idle, picks the available task with the shortest processing time (ties by index). Sort by enqueue time; keep a min-heap of (processing time, index) for tasks that have arrived; when the heap is empty, jump the clock to the next enqueue time.

IPO: you have capital w and may complete at most k projects, each needing some capital and giving a profit. Sort projects by required capital. Each round, push the profits of every project you can now afford into a max-heap, then take the largest profit. Taking the best affordable project is safe because capital only grows, so anything affordable now stays affordable later.

Reorganize String / Task Scheduler: always place the most frequent remaining character (or task) that is not blocked. A max-heap of counts plus a small queue or "held-back" slot for the item that just ran implements it. For Task Scheduler there is also a closed-form answer, (f − 1)(n + 1) + m capped below by the number of tasks, where f is the maximum frequency and m how many tasks share it — worth deriving once by drawing the frames.

Recognising the pattern

Reach for a heap when you repeatedly need the minimum or maximum of a collection that changes: "k largest / smallest / closest / most frequent", "median of a stream", "merge k sorted", "schedule", "earliest finishing", "most profitable available", "next event in time order", or a shortest path with weights. If you need the extreme only once, a single scan is enough; if you need full order once, sort. A heap is for repeated extremes under change.

Why heapify is O(n)

Bottom-up heapify calls sift_down on each non-leaf node. A node at height h (distance from the bottom) sifts down at most h levels. In a complete tree of n nodes, about n/2 nodes are leaves (height 0, no work), n/4 have height 1, n/8 height 2, and so on. The total work is at most n·(1/4·1 + 1/8·2 + 1/16·3 + …) = n·Σ h/2^(h+1) = n. Intuitively, the expensive sifts happen only near the root, where there are very few nodes. Pushing elements one at a time does the opposite — most elements are inserted at the bottom and may climb the full height — which is why it is O(n log n). This is a classic "explain the analysis" question.

Heapsort, and why it is rarely used

Heapify, then pop n times placing each popped element at the end of the array: that sorts in O(n log n) worst case with O(1) extra memory — heapsort. It beats quicksort's worst case and mergesort's memory, yet libraries rarely use it as the main sort because its memory access pattern jumps around the array (index i to 2i + 1), which is cache-unfriendly, and it is not stable. Its main production role is as the fallback in introsort: when quicksort's recursion gets too deep (a sign of bad pivots), switch to heapsort to guarantee O(n log n).

Decrease-key, lazy deletion and Dijkstra

Dijkstra's algorithm needs to lower a node's tentative distance when a shorter path is found ("decrease-key"). A textbook indexed heap tracks each element's position so it can sift it up in O(log n). heapq has no such operation, so Python implementations push a new (distance, node) entry and skip stale entries when they are popped ("if d > dist[node]: continue"). This is lazy deletion: the heap may hold up to E entries instead of V, so operations cost O(log E) = O(log V²) = O(2 log V), the same order. It is simpler and usually faster in practice. The same trick handles "remove an arbitrary element" for sliding-window medians and for task cancellation in schedulers.

Tie-breaking and stability

Heaps are not stable: two elements with equal priority can come out in either order. When order among equals matters — first-come-first-served among equal priorities, or a required tie rule like "smallest index first" in Single-Threaded CPU — encode it in the key: (priority, arrival_counter, item). The counter also prevents comparisons between payloads that are not orderable. For max-heaps with tie rules, be careful which fields you negate: for "largest profit, then smallest index", push (−profit, index).

d-ary heaps and other variants

A d-ary heap gives each node d children instead of two. The tree is shallower (log_d n levels), so sift up is cheaper, while sift down compares d children per level. When pushes and decrease-keys outnumber pops — as in Dijkstra on dense graphs — a 4-ary heap is often faster, and the Go runtime uses a 4-ary heap for its timers. Fibonacci heaps achieve amortised O(1) decrease-key, giving Dijkstra O(E + V log V) in theory, but their constant factors make them slower in practice than a binary or d-ary heap. For interviews, knowing that the binary heap is the practical default, and why, is enough. If asked to design a priority queue that supports changing priorities efficiently, describe an indexed heap: alongside the array, keep a dict from item to its array position, and update it on every swap, so decrease-key can find the item in O(1) and sift it in O(log n).

When a heap is the wrong tool

If you need the k-th element under arbitrary insertions and deletions, or range queries ("how many values between a and b"), a heap cannot help; use a balanced search tree (or sortedcontainers.SortedList), a Fenwick tree over compressed values (al27), or an order-statistics tree. If the priorities are small integers, a bucket queue (an array of lists indexed by priority) gives O(1) operations. And if you only need the top k once over static data, sorted(data)[-k:] is simpler and fine unless n is very large; say so before reaching for a heap to show you choose tools by need.

In the interview room

Heap solutions are short, so the bugs are in the details. The most common: forgetting that heapq is a min-heap (pushing positive values when you need the largest first); negating on the way in but not on the way out; pushing tuples whose second field is not comparable and crashing on ties; popping from an empty heap; and using a heap of size n when a heap of size k was the point (O(n log n) instead of O(n log k), and O(n) memory). Another subtle one is modifying an element in place after pushing it — the heap does not know and its order breaks. Treat heap entries as immutable and push new ones.

Interviewers often follow up on complexity choices: "why O(n log k) and not O(n log n)?", "could you do better than a heap?" (quickselect or bucket sort), and "what if the data is a stream?" (the size-k heap still works; quickselect does not). For the median, the follow-up is usually "now support removal" (lazy deletion) or "what if all numbers are integers between 0 and 100?" (a counting array with a running pointer gives O(1) per operation).

For scheduling problems, the follow-up is a proof: "why is picking the earliest-ending room or the most profitable affordable project optimal?". Have a one-sentence exchange argument ready: if an optimal plan chose something else at that moment, swapping in the greedy choice does not make it worse.

On online assessments, heap problems often come disguised as simulations: "servers process requests; when a server is free it takes the oldest highest-priority request", "workers finish jobs at different times; find when the last job finishes". Simulating time step by step is too slow when times go up to 10⁹; the fix is an event-driven simulation where a heap of (time, event) pairs lets you jump directly to the next interesting moment.

In real systems

Priority queues are built into a lot of infrastructure. Event loops keep timers in a min-heap keyed by expiry time: libuv, the library under Node.js, stores timers in a binary min-heap, and each loop iteration looks at the root to know how long it may sleep. Search engines collect the top-k results with a bounded heap — Apache Lucene's PriorityQueue keeps the k best-scoring documents while scoring millions, discarding anything below the current k-th score, exactly the size-k pattern from this lesson. Network routers and OSPF-style routing protocols run Dijkstra's algorithm with a priority queue to compute shortest paths. Job schedulers and message brokers (for example, priority queues in RabbitMQ) order work by priority. Streaming analytics compute "top-k trending items" over windows with heaps combined with approximate counters. Discrete-event simulators — used to model networks, factories and queues — are a priority queue of future events processed in time order. When an interviewer asks how you would build "a service that returns the 10 most popular products in the last hour", a size-k heap over counts is the core of the answer.

def topk_heap(a, k):
    h = []
    for x in a:
        if len(h) < k: heapq.heappush(h, x)
        elif x > h[0]: heapq.heapreplace(h, x)
    return sorted(h, reverse=True)

a = [random.random() for _ in range(2_000_000)]
for name, f in (("heap", lambda: topk_heap(a, 10)),
                ("sort", lambda: sorted(a, reverse=True)[:10])):
    t = time.perf_counter(); r = f(); print(name, f"{time.perf_counter()-t:.2f}s")

Design with a heap

"Design a service that, at any moment, returns the 10 most frequently searched queries in the last 60 minutes. There are about 5,000 searches per second." Sketch the data structures and the costs, and say what you would approximate if memory were tight.

Answer

Keep per-minute buckets: a ring of 60 dictionaries, each mapping query → count for that minute, plus a running dictionary total[query] = count over the last 60 minutes. On each search, increment the current minute's bucket and total (O(1)). When a minute rolls over, subtract the expiring bucket's counts from total (deleting zero entries) and reuse the bucket — amortised O(1) per search. To answer top-10, run a size-10 min-heap over total's items: O(u log 10) for u distinct queries in the window, which may be hundreds of thousands, so cache the answer and recompute every few seconds rather than per request. That is accurate but stores every distinct query in the hour. If memory is tight, replace exact counts with a Count-Min sketch (fixed memory, slight overestimates) and keep a small heap of candidate heavy hitters (the "top-k with sketch" approach used in streaming systems), or use the Space-Saving algorithm, which tracks only m counters and guarantees to contain every query whose frequency exceeds N/m. Mention the trade-off: exactness versus memory, and recompute-on-read versus maintain-on-write.
