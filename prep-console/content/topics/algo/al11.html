A team calendar has 40 people, each with a list of meetings for the week, and you are asked: "when can all 40 meet for an hour?" Or: "how many rooms does the building need so that no meeting is double-booked?" Or: "a booking system receives reservations one by one — reject any that clash with an existing one". These are interval problems. Each meeting is a range on the time line, and the questions are about how the ranges overlap.

The brute force compares every interval with every other: with 10⁵ meetings that is 5 × 10⁹ comparisons, and many questions (merge everything that overlaps, transitively) are awkward even then. The fix is almost always the same first step: sort. Once intervals are sorted by start, an interval can only overlap the ones just before it, so a single left-to-right scan replaces the all-pairs comparison. The whole problem becomes O(n log n) for the sort and O(n) for the scan.

What changes from problem to problem is the sort key and what the scan keeps. Merging keeps the current block. Choosing the most non-overlapping intervals sorts by end instead, for a reason worth understanding. Counting how many intervals are active at once turns each interval into two events — a start and an end — and sweeps over them. Comparing two lists of intervals walks them with two pointers. And the booking-calendar problem keeps intervals in sorted order as they arrive.

This lesson works through each of those shapes with traces, the greedy proofs behind the sort-by-end choice, the boundary questions (do touching intervals overlap?) that cause most bugs, and the sweep-line technique that generalises to the famous skyline problem.

The mental model: a time line and a sweeping hand

Draw every interval as a bar on a horizontal time line. Now imagine a vertical line — a sweep line — moving from left to right across the picture. As it moves, it touches some bars. Most of the time nothing interesting happens; the set of touched bars changes only when the line reaches the start or the end of some bar. Those are the events. Any question about overlaps — how many bars are touched at once, where the free gaps are, which bars merge into one block — can be answered by stopping only at the events, in sorted order, and updating a small amount of state.

That one picture contains most of the lesson. The merged blocks are the stretches where the count is above zero: [1, 6] and [7, 11]. The maximum overlap is the highest point of the count, 3 — the number of meeting rooms needed. The free time is where the count is zero: before 1, between 6 and 7, after 11. Different problems read different features off the same sweep.

The second thing to fix in your mind is the overlap test. Two intervals [a, b] and [c, d] overlap exactly when each starts before the other ends: a ≤ d and c ≤ b. The opposite — they do not overlap — is "one ends before the other starts": b < c or d < a. If you ever find yourself writing four cases ("c inside [a, b], or d inside, or …"), stop and use the two-comparison test instead.

Where the analogy breaks: on a picture, touching bars look like they meet, but whether they overlap depends on meaning. A meeting from 1 to 2 and another from 2 to 3 can use the same room; a closed numeric range [1, 2] and [2, 3] share the point 2. This boundary decision — closed intervals, where touching counts, or half-open intervals [a, b), where it does not — changes ≤ to < in the code and changes the order of events at equal times. It is the most common source of wrong answers in interval problems, so it is the first clarifying question to ask.

A final framing that ties this lesson to earlier ones: the sweep's running count is exactly the difference-array idea from al3, applied to sorted event points instead of every index. When coordinates are small and dense, a difference array is simplest; when they are large or sparse, sort the events. Same idea, different storage.

Merging overlapping intervals

Sort by start. Then each interval either overlaps the block you are building (it starts at or before the block's end) or begins a new block. Overlap is transitive along the sorted order, so one pass suffices.

def merge(intervals):
    intervals.sort(key=lambda iv: iv[0])
    out = []
    for s, e in intervals:
        if out and s <= out[-1][1]:            # overlaps the current block
            out[-1][1] = max(out[-1][1], e)    # extend (max: it may be inside)
        else:
            out.append([s, e])
    return out

Trace [[1, 5], [3, 6], [8, 11], [7, 9], [4, 5]] sorted to [[1, 5], [3, 6], [4, 5], [7, 9], [8, 11]]: start [1, 5]; [3, 6] overlaps → [1, 6]; [4, 5] overlaps but ends earlier → still [1, 6] (this is why you need max, not just "take e"); [7, 9] starts after 6 → new block; [8, 11] overlaps → [7, 11]. Result [[1, 6], [7, 11]], matching the figure. Change <= to < if touching intervals should stay separate.

Inserting into a sorted list

If the existing intervals are already sorted and non-overlapping, inserting one new interval does not need a sort. Walk once in three phases: copy everything that ends before the new interval starts; absorb everything that overlaps it, widening the new interval to cover them; copy the rest.

def insert(intervals, new):
    out, i, n = [], 0, len(intervals)
    s, e = new
    while i < n and intervals[i][1] < s:        # entirely before
        out.append(intervals[i]); i += 1
    while i < n and intervals[i][0] <= e:       # overlapping
        s = min(s, intervals[i][0]); e = max(e, intervals[i][1]); i += 1
    out.append([s, e])
    out.extend(intervals[i:])                   # entirely after
    return out

O(n). The two loop conditions are the overlap test split in half: "ends before the new one starts" and "starts before the new one ends".

Selecting non-overlapping intervals: sort by end

"Remove the minimum number of intervals so the rest do not overlap." Flip it: keep the maximum number of non-overlapping intervals; the answer is n minus that. This is the classic activity selection problem, and its greedy rule is: sort by end, and take every interval that starts at or after the end of the last one taken.

def erase_overlap_intervals(intervals):
    intervals.sort(key=lambda iv: iv[1])
    kept, last_end = 0, float("-inf")
    for s, e in intervals:
        if s >= last_end:            # compatible (touching allowed here)
            kept += 1; last_end = e
    return len(intervals) - kept

Why the end, not the start? Among all intervals, the one that finishes first leaves the most room for everything after it. The exchange argument: take any optimal selection; its first interval ends no earlier than the greedy's first choice (which ends earliest of all). Swap it for the greedy's choice — the rest of the optimal selection still fits, because the greedy interval ends even sooner — so there is an optimal solution that agrees with the greedy's first step. Repeat for the remaining intervals. Sorting by start fails on [[1, 100], [2, 3], [4, 5]]: it would take [1, 100] first and block both short meetings.

Minimum arrows to burst balloons is the same algorithm in disguise. Sort balloons by end, shoot at the first balloon's end (the latest point that still hits it, so it hits as many others as possible), skip every balloon that starts at or before that point, and repeat. The number of arrows equals the maximum number of pairwise disjoint balloons.

Intersecting two interval lists

Given two lists of disjoint, sorted intervals, return their intersection. Two pointers, one per list (al5). The overlap of the current pair is [max(starts), min(ends)], non-empty if its start ≤ its end. Then advance the pointer whose interval ends first: it cannot overlap anything later in the other list, because those start later still.

def interval_intersection(A, B):
    i = j = 0; out = []
    while i < len(A) and j < len(B):
        lo = max(A[i][0], B[j][0]); hi = min(A[i][1], B[j][1])
        if lo <= hi: out.append([lo, hi])
        if A[i][1] < B[j][1]: i += 1
        else: j += 1
    return out

Counting overlaps: events, or a heap

"Minimum number of meeting rooms" is "maximum number of intervals active at the same time". Two equivalent methods.

Sweep with events. Turn each meeting into two events, (start, +1) and (end, −1). Sort them, and walk with a running count; the maximum count is the answer. The order of events at the same time encodes the boundary decision: for meetings, an end at 10 and a start at 10 should not need two rooms, so process the end first — sorting tuples (time, delta) does that automatically because −1 < +1.

def min_rooms(intervals):
    events = []
    for s, e in intervals:
        events.append((s, 1)); events.append((e, -1))
    events.sort()                      # at equal time, -1 (end) before +1
    cur = best = 0
    for _, d in events:
        cur += d; best = max(best, cur)
    return best

Heap of end times. Sort meetings by start and keep a min-heap of the end times of meetings currently using rooms (al10). For each meeting, if the earliest end is ≤ its start, that room is free — pop it; then push the new end. The heap size never shrinks below what is needed, and its peak is the answer. The heap version is useful when you also need to know which room each meeting gets.

A third variant uses two sorted arrays — all starts, all ends — and two pointers: walk the starts; if the next start is before the earliest unused end, allocate a room; otherwise reuse one by advancing the end pointer. It is the sweep without building tuples.

Booking calendars: intervals arriving one at a time

"My Calendar I": bookings arrive online; accept a booking [s, e) only if it does not overlap any accepted one. Keep accepted bookings sorted by start (a list maintained with bisect, or a balanced tree). For a new booking, find where it would go; it is valid if the previous booking ends at or before s and the next booking starts at or after e — only the two neighbours can conflict, because the stored bookings do not overlap each other.

import bisect
class MyCalendar:
    def __init__(self): self.starts, self.ends = [], []
    def book(self, s, e):
        i = bisect.bisect_right(self.starts, s)
        if i > 0 and self.ends[i - 1] > s: return False   # previous overlaps
        if i < len(self.starts) and self.starts[i] < e: return False  # next overlaps
        self.starts.insert(i, s); self.ends.insert(i, e)
        return True

The search is O(log n); Python list insertion is O(n), which is fine for the problem's limits, and a balanced tree (or sortedcontainers.SortedList) makes it O(log n). "My Calendar II" (allow double but not triple bookings) and "III" (report the maximum overlap after each booking) switch to the sweep: keep a sorted map from time to delta, add +1 at s and −1 at e, and sweep it to compute the running maximum — O(n) per booking, acceptable for small n, or a segment tree with lazy propagation for large n (al27).

The skyline problem: a sweep with a heap

Buildings are rectangles [left, right, height] on a common ground line; output the outline's key points, where the maximum height changes. Sweep x from left to right. The state is the multiset of heights of buildings covering the current x; the answer changes when the maximum of that multiset changes. A max-heap holds the active heights; ended buildings are removed lazily (keep their right edge in the heap entry and pop entries whose right edge is ≤ x before reading the top).

import heapq
def get_skyline(buildings):
    events = sorted({l for l, r, h in buildings} | {r for l, r, h in buildings})
    res, live, i, n = [], [], 0, len(buildings)     # live: (-height, right)
    buildings.sort()
    for x in events:
        while i < n and buildings[i][0] <= x:        # add buildings starting here
            heapq.heappush(live, (-buildings[i][2], buildings[i][1])); i += 1
        while live and live[0][1] <= x:               # drop ended buildings
            heapq.heappop(live)
        h = -live[0][0] if live else 0
        if not res or res[-1][1] != h:
            res.append([x, h])
    return res

Processing all buildings that start at x before reading the maximum, and dropping all that end at x, handles the tricky equal-coordinate cases (a building ending exactly where a taller one starts, or two buildings starting together) without hand-crafted event ordering. O(n log n).

Coordinate compression

When interval endpoints go up to 10⁹ but there are only 10⁵ intervals, there are at most 2 × 10⁵ distinct coordinates that matter. Sort the distinct endpoints and replace each by its rank (rank = {x: i for i, x in enumerate(sorted(set(points)))}). Now a difference array or a segment tree of size 2 × 10⁵ works. Be careful with what the gaps mean: between compressed coordinates i and i + 1 lies a real stretch of length points[i + 1] − points[i], which matters if you are measuring total covered length rather than counting.

Free time and gaps

"Employee Free Time" gives each person's busy intervals (sorted) and asks for the finite stretches when everyone is free. The answer is the complement of the union of all busy intervals: merge everything, then read the gaps between consecutive merged blocks. If there are k people with N intervals in total, flattening and sorting is O(N log N); a k-way merge with a heap (one pointer per person, al10) produces the intervals in start order in O(N log k) without a full sort, and you can merge on the fly. "Find a common one-hour slot for all attendees within working hours" is the same idea plus a final filter on gap length and a clip to [9:00, 17:00). Representing the working-hours boundary as two extra "busy" intervals — before 9:00 and after 17:00 — is a neat way to avoid special cases at the ends.

Recognising the pattern

Interval problems mention ranges, meetings, bookings, schedules, segments, coverage, or "overlap". Decide three things first: does touching count as overlapping; what to sort by (start for merging and inserting, end for selecting and arrows); and what state the scan keeps (current block, last end, running count, heap of ends, or an ordered set). Then the code is a sort and a loop.

Which greedy problems sort by end, and why

Activity selection (maximum non-overlapping), minimum arrows, and "minimum points to stab all intervals" are the same problem and all sort by end. The proof is the exchange argument given in the body, and it hinges on one property: among intervals compatible with what you have taken so far, the earliest-ending one is never worse than any other choice, because it constrains the future least. Weighted activity selection (each interval has a value, maximise the total) breaks the greedy — a long, valuable interval can beat several short cheap ones — and needs dynamic programming: sort by end, and for each interval i take max(dp[i − 1], value[i] + dp[p(i)]) where p(i) is the last interval ending before i starts, found by binary search. That is O(n log n) and a common follow-up.

Interval graph colouring equals maximum overlap

"Minimum rooms" is graph colouring on an interval graph (intervals are vertices, overlaps are edges). Colouring general graphs is NP-hard, but interval graphs are special: the minimum number of colours equals the size of the largest clique, which is the maximum number of intervals sharing a point. The sweep computes that clique size, and the heap-based assignment (give each meeting the room that frees up earliest) constructs a colouring with exactly that many colours. It is a nice example of structure turning an intractable problem into an O(n log n) one, and it explains why the greedy room assignment is optimal.

Half-open intervals as a design choice

Many systems standardise on half-open intervals [start, end): Python's range and slicing, C++ iterators, time ranges in calendars and databases. The benefits are concrete: the length is end − start with no +1; consecutive intervals [a, b) and [b, c) tile a range without overlap or gap; and an empty interval is simply start == end. Adopting half-open intervals in interval code removes most off-by-one errors: the overlap test becomes a < d and c < b, and events at the same time sort ends before starts. When a problem gives closed intervals of integers, you can convert to half-open by adding one to every end.

Beyond one dimension: rectangle union and sweep with a segment tree

"Total area covered by a set of axis-aligned rectangles" is the 2D generalisation. Sweep a vertical line across x; events are the left and right edges of rectangles. Between consecutive events, the covered area is (Δx) × (total covered length on the y-axis). Maintaining that covered y-length as y-intervals are added and removed needs a segment tree over compressed y-coordinates that stores, per node, a cover count and the covered length — O(n log n) overall. This is the canonical "sweep line plus a data structure" problem, and recognising it as such (rather than rasterising the plane) is the senior insight.

Counting pairs of overlapping intervals

"How many pairs of intervals overlap?" looks quadratic but is O(n log n). Sort by start and sweep; when an interval starts, every interval currently active overlaps it, so add the active count before incrementing it. With a heap of end times (or two sorted arrays of starts and ends and binary search: the number of intervals that start before my end minus those that end before my start), each interval contributes in O(log n). This "count at the moment of arrival" trick turns many pair-counting problems into a single sweep, and it is the same idea as counting subarrays at each right end in al6.

Interval trees and stabbing queries

If intervals are stored long-term and you must answer "which intervals contain point x?" or "which overlap [a, b]?" many times, sorting once and scanning per query is O(n). An interval tree — a balanced search tree keyed by start, where each node also stores the maximum end in its subtree — answers overlap queries in O(log n + k) for k results, because whole subtrees whose maximum end is before a can be skipped. Databases use related structures (R-trees for spatial data, GiST indexes in PostgreSQL support range types with overlap operators), and genome browsers use them to find features overlapping a region. In interviews, describing the augmentation ("store the max end per subtree to prune") is usually enough.

In the interview room

Interval questions are judged heavily on boundary handling, so ask the clarifying question out loud: "if one meeting ends at 10 and another starts at 10, is that a conflict?" Then make the code consistent with the answer: ≤ or < in the overlap test, and the order of events at equal times. The other frequent bugs are: forgetting max when extending a merged block (an interval contained in the current block would shrink it); sorting by the wrong key for selection problems; mutating the input list when the caller did not expect it (sort a copy if in doubt); and assuming the input is sorted when it is not. Test with an empty list, a single interval, nested intervals, touching intervals, and identical intervals.

For the greedy ones, expect "why does sorting by end work?". Answer with the exchange argument and the counterexample for sorting by start; it takes thirty seconds and is exactly what the question is probing. For Meeting Rooms II, interviewers often accept either the heap or the event sweep, then ask for the other — knowing both, and that they compute the same maximum clique, is a strong signal.

Interval problems also appear in online assessments with large coordinates (up to 10⁹) where a candidate's instinct is to build an array over the time line. Read the constraints: if coordinates are large but n is moderate, sort events or compress coordinates instead.

A useful meta-habit: before coding, sketch two or three intervals on a number line, including a nested pair and a touching pair, and run your planned rule on the sketch. Interval bugs are visual, and a ten-second drawing catches most of them before they reach the code.

In real systems

Calendar and scheduling software is interval logic end to end: free/busy computation merges every attendee's busy intervals and returns the gaps, and room-booking systems check new reservations against neighbours exactly like My Calendar. Cloud schedulers and batch systems track reserved capacity over time as a sweep of +resources and −resources events. In genomics, tools such as bedtools merge, intersect and subtract millions of genomic intervals (genes, reads, variants) using sorted sweeps — the merge in this lesson is literally bedtools' core operation. Databases support range types and exclusion constraints (PostgreSQL can enforce "no two bookings for the same room overlap" with a GiST index), and time-series and log stores prune data by time ranges, merging overlapping retention and compaction windows. Network stacks track received byte ranges — TCP selective acknowledgements report which ranges have arrived, and the receiver merges ranges as gaps fill. In each case the engineering lesson is the interview lesson: sort first, then sweep, and be explicit about endpoints.

    import random, heapq

def merge(iv):
    out = []
    for s, e in sorted(iv):
        if out and s <= out[-1][1]: out[-1][1] = max(out[-1][1], e)
        else: out.append([s, e])
    return out

def covered_points(iv):                 # brute force on integer points
    return sorted({x for s, e in iv for x in range(s, e + 1)})

def rooms_sweep(iv):                    # half-open meetings [s, e)
    ev = sorted([(s, 1) for s, e in iv] + [(e, -1) for s, e in iv])
    cur = best = 0
    for _, d in ev: cur += d; best = max(best, cur)
    return best

def rooms_brute(iv):
    return max([sum(s <= t < e for s, e in iv) for t in range(0, 25)], default=0)

for _ in range(3000):
    iv = []
    for _ in range(random.randint(0, 7)):
        s = random.randint(0, 20); iv.append([s, s + random.randint(0, 4)])
    m = merge([x[:] for x in iv])
    assert covered_points(m) == covered_points(iv)
    assert all(m[i][1] < m[i+1][0] for i in range(len(m) - 1))
    meetings = [x for x in iv if x[1] > x[0]]
    assert rooms_sweep(meetings) == rooms_brute(meetings), meetings
print("merge and rooms agree with brute force")

Weighted scheduling: when the greedy breaks

"Each job has [start, end, profit]. Choose non-overlapping jobs to maximise total profit (touching allowed). n ≤ 5 × 10⁴." Why does the sort-by-end greedy fail, and what is the O(n log n) solution?

Answer

The greedy maximises the number of jobs, not their profit: with [1, 10, 100], [1, 2, 1], [3, 4, 1], it takes the two short jobs (profit 2) instead of the long one (profit 100). Use dynamic programming over jobs sorted by end. Let ends be the sorted end times and dp[i] the best profit using the first i jobs. For job i (0-based) with start s and profit p, find j = bisect_right(ends, s) — the number of jobs that end at or before s, which are all compatible with it. Then dp[i + 1] = max(dp[i], dp[j] + p): skip job i, or take it plus the best compatible prefix. The answer is dp[n]. Sorting is O(n log n) and each step does one binary search, so O(n log n) total, O(n) memory. This "sort by end + binary search for the last compatible job" is a pattern worth recognising; it reappears in problems like "maximum number of events you can attend with values".
