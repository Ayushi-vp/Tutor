"Generate every valid combination of n pairs of parentheses." "List all the ways to choose numbers from this list that add up to 7." "Solve this Sudoku." "Can this word be traced through adjacent letters on this grid?" These problems ask you to search through a huge space of possibilities — all subsets, all orderings, all placements — for the ones that satisfy some rules. There is no clever formula; the answer really does require trying possibilities. The question is how to try them systematically, so you never miss one, never repeat one, and abandon hopeless ones as early as possible.

That systematic search is called backtracking. You build a candidate solution one choice at a time; after each choice, you explore everything that can follow from it; when you have finished (or the choice turns out to be a dead end), you undo it and try the next option. It is how you would solve a maze with a piece of chalk: walk until you hit a dead end, back up to the last junction, take a different turn.

Backtracking is built on recursion, which many people find slippery at first, so this lesson starts there: how to write a recursive function you can trust. Then it introduces the choose–explore–unchoose template and applies it to each classic family — subsets, combinations, permutations, partitions, grid search, N-Queens and Sudoku — including the two techniques interviewers probe most: handling duplicate inputs without producing duplicate outputs, and pruning branches that cannot succeed.

These problems are recognisable from their constraints. If n is at most about 15 or 20, or the problem says "return all", the setter is telling you an exponential search is expected. Your job is to write it cleanly, explain its complexity, and prune it well.

Thinking recursively: trust the smaller call

A recursive function solves a problem by calling itself on a smaller version of the same problem. It has two parts: a base case, which is small enough to answer directly, and a recursive case, which reduces the problem and combines the answer. The mental trick that makes recursion easy is to trust the recursive call: assume it correctly solves the smaller problem, and only ask "given that, how do I solve this one?". Do not try to trace every level in your head.

For example, "how many subsets does a list of n elements have?" Base case: the empty list has one subset (the empty one). Recursive case: take the first element; every subset of the rest either gets it or not, so the count doubles: subsets(n) = 2 × subsets(n − 1). You never pictured all eight subsets of three elements; you trusted the smaller answer.

The mental model for backtracking: a maze with chalk

Searching all possibilities is like exploring a maze to find every exit. At each junction you have several corridors. You pick one, mark it with chalk, and keep going. If you reach an exit, you write it down. If you reach a dead end — or a place where the rules say you cannot possibly reach an exit — you walk back to the last junction, rub out the chalk, and try the next corridor. When every corridor at a junction has been tried, you back up further. You will visit every reachable place exactly once along each path, and the chalk marks mean you never walk in circles.

The maze is the decision tree: the root is "no choices made yet", each edge is one choice, and each leaf is a complete candidate. Backtracking walks this tree depth-first.

The template: choose, explore, unchoose

Almost every backtracking solution has the same skeleton:

def backtrack(state):
    if is_solution(state):
        record(copy of state)
        return                       # or continue, if solutions can extend
    for choice in choices(state):
        if not valid(state, choice):
            continue                 # prune
        apply(choice, state)         # choose
        backtrack(state)             # explore
        undo(choice, state)          # unchoose

Filling in the blanks — what the state is, what the choices are at each step, what makes a choice invalid, and when a state is a solution — is the whole design. "Unchoose" is what makes it backtracking: the state is shared and mutated in place, so every change must be reversed before trying the next option, leaving the state exactly as it was.

Where the maze analogy breaks: in a real maze, two different routes can lead to the same room, and a good explorer would notice. Plain backtracking does not — it may explore the same sub-situation many times via different paths. When that happens and the answer for a sub-situation does not depend on how you got there, memoisation turns the search into dynamic programming (covered in the deep layer and in al21).

Subsets: two ways to see the same tree

Include/exclude. For each element in turn, branch twice: take it or skip it. Depth n, two branches per level, 2ⁿ leaves, each leaf a subset.

def subsets(nums):
    res, path = [], []
    def go(i):
        if i == len(nums):
            res.append(path[:]); return
        path.append(nums[i]); go(i + 1); path.pop()   # take nums[i]
        go(i + 1)                                      # skip nums[i]
    go(0)
    return res

Start-index loop. The figure's version: every node is a subset; from a node, extend with any element after the last one chosen.

def subsets(nums):
    res, path = [], []
    def go(start):
        res.append(path[:])                 # every node is an answer
        for i in range(start, len(nums)):
            path.append(nums[i])
            go(i + 1)
            path.pop()
    go(0)
    return res

Both produce 2ⁿ subsets. Copying each costs up to n, so the total is O(n·2ⁿ) time; the recursion depth is n. The start-index form generalises better, because combinations, combination sums and partitions all use it.

Notice path[:]. path is one list shared by the whole search; appending path itself would store a reference to that list, and by the end of the search every stored "subset" would be the same, empty list. This is the single most common backtracking bug.

Combinations and combination sums

Combinations (choose k of n) are the start-index subset search, recording only when the path has length k — and pruning when there are not enough elements left to reach k (if len(path) + (n − i) < k: break).

Combination Sum: candidates may be reused any number of times; find all combinations summing to a target. The state is the path and the remaining target. Two details make it work: recurse with i (not i + 1) so the same candidate can be chosen again, and sort the candidates so that once one is too large, all later ones are too, and the loop can stop.

def combination_sum(cands, target):
    cands.sort(); res, path = [], []
    def go(start, remain):
        if remain == 0:
            res.append(path[:]); return
        for i in range(start, len(cands)):
            if cands[i] > remain: break          # sorted: prune the rest
            path.append(cands[i])
            go(i, remain - cands[i])            # i, not i+1: reuse allowed
            path.pop()
    go(0, target)
    return res

Trace candidates [2, 3, 6, 7], target 7: from [], take 2 → remain 5 → take 2 → 3 → take 2 → 1 → 2 > 1, break; back, take 3 → 0, record [2, 2, 3]; … take 7 from [] → record [7]. Result [[2, 2, 3], [7]]. The start index is what prevents [2, 3, 2] and [3, 2, 2] from appearing as separate answers: within one path, indices never decrease.

Handling duplicates: skip equal values at the same depth

If the input contains duplicates — Subsets II with [1, 2, 2], or Combination Sum II where each candidate is used once — the plain search produces duplicate outputs: choosing the first 2 or the second 2 at the same position leads to identical subtrees. The fix: sort, then in the loop skip an element equal to the previous one at the same depth.

for i in range(start, len(nums)):
    if i > start and nums[i] == nums[i - 1]:
        continue          # same value already tried as this position's choice
    ...

The condition i > start is the key. At a given depth, the first copy of a value is tried; later copies would only repeat it. But deeper in the tree, after the first 2 has been chosen, the loop starts at the next index, where the second 2 is the first element — so it is allowed, and [2, 2] is produced exactly once. For [1, 2, 2], the subsets are [], [1], [1, 2], [1, 2, 2], [2], [2, 2].

Permutations: track what is used

Permutations use every element once in every order, so there is no start index; instead, any unused element may come next. Keep a used array.

def permute(nums):
    res, path, used = [], [], [False] * len(nums)
    def go():
        if len(path) == len(nums):
            res.append(path[:]); return
        for i in range(len(nums)):
            if used[i]: continue
            used[i] = True; path.append(nums[i])
            go()
            path.pop(); used[i] = False
    go()
    return res

n choices at depth 0, n − 1 at depth 1, …, so n! leaves and O(n·n!) work. For duplicates (Permutations II), sort and add: skip i if i > 0 and nums[i] == nums[i − 1] and not used[i − 1]. That rule means a second copy of a value can only be placed after the first copy has been placed, which forces equal values into a fixed relative order and removes the duplicates.

Pruning with constraints: Generate Parentheses

"All valid strings of n pairs of parentheses." A naive search generates all 2^(2n) strings of brackets and filters the valid ones. Better: never build an invalid prefix. A prefix stays valid if you add "(" while fewer than n have been used, and ")" while fewer closes than opens have been used.

def generate_parenthesis(n):
    res, path = [], []
    def go(open_, close):
        if len(path) == 2 * n:
            res.append("".join(path)); return
        if open_ < n:
            path.append("("); go(open_ + 1, close); path.pop()
        if close < open_:
            path.append(")"); go(open_, close + 1); path.pop()
    go(0, 0)
    return res

For n = 3 this produces exactly the 5 valid strings and visits only valid prefixes. The count is the n-th Catalan number, about 4ⁿ / n^1.5 — the search does work proportional to the output, which is the best possible. The general lesson: check constraints as early as possible, on partial solutions, not at the leaves.

Backtracking on a grid: Word Search

"Does the word exist in the grid as a path of adjacent cells, each used at most once?" Start a depth-first search from every cell; at depth k, the current cell must equal word[k]. The state includes which cells are on the current path, and that state must be restored when backing up.

def exist(board, word):
    R, C = len(board), len(board[0])
    def dfs(r, c, k):
        if k == len(word): return True
        if not (0 <= r < R and 0 <= c < C) or board[r][c] != word[k]:
            return False
        saved, board[r][c] = board[r][c], "#"          # choose: mark visited
        found = any(dfs(r + dr, c + dc, k + 1)
                    for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)))
        board[r][c] = saved                            # unchoose: restore
        return found
    return any(dfs(r, c, 0) for r in range(R) for c in range(C))

Overwriting the cell with "#" is a cheap visited marker that needs no extra set, and restoring it is the "unchoose". Forgetting the restore makes later searches from other starting cells see a corrupted board — a very common bug. Worst case O(R·C·4·3^(L−1)) for a word of length L: from each start, four first moves and at most three onward (you cannot go back). Simple pruning helps a lot in practice: if the board does not contain enough of each letter in the word, return false immediately; and searching from the end of the word when its last letter is rarer than its first shrinks the tree.

Partitioning: Palindrome Partitioning

"Return all ways to split a string into palindromes." The choices at each step are "where does the next piece end?". From start index s, for each end e ≥ s with s[s..e] a palindrome, take that piece and recurse from e + 1. Precomputing is_pal[i][j] (true if s[i..j] is a palindrome) with a small DP in O(n²) makes every check O(1). The output can have up to 2^(n−1) partitions (a string of identical letters), so the search is exponential by necessity.

Constraint search: N-Queens

Place n queens on an n×n board so none attack each other. Place one per row (two in a row would attack), so the choice at depth r is a column. A column conflicts if it is already used, or if a queen sits on the same diagonal. All cells on one diagonal share r − c; all cells on one anti-diagonal share r + c. Three sets give O(1) conflict checks:

def solve_n_queens(n):
    res, cols, diag, anti, place = [], set(), set(), set(), []
    def go(r):
        if r == n:
            res.append(["." * c + "Q" + "." * (n - c - 1) for c in place]); return
        for c in range(n):
            if c in cols or r - c in diag or r + c in anti: continue
            cols.add(c); diag.add(r - c); anti.add(r + c); place.append(c)
            go(r + 1)
            cols.remove(c); diag.remove(r - c); anti.remove(r + c); place.pop()
    go(0)
    return res

For n = 8 there are 92 solutions, and the search explores roughly 2,000 partial placements rather than 8⁸ ≈ 16.7 million, because conflicts are caught as soon as each queen is placed.

Sudoku: choose the most constrained cell

A Sudoku solver is backtracking over empty cells with digits as choices. Keep sets of used digits for each row, column and box (box index = (r // 3) * 3 + c // 3). The single most effective improvement is the MRV heuristic (minimum remaining values): at each step, fill the empty cell with the fewest legal digits. A cell with one option is forced (no branching), and a cell with zero options means the current branch is dead, which is discovered immediately rather than many levels later. With MRV and O(1) legality checks, typical puzzles solve in milliseconds; without it, hard puzzles can take much longer.

Complexity: count the tree

The cost of a backtracking search is (number of nodes in the explored tree) × (work per node). Useful reference counts: subsets 2ⁿ, permutations n!, combinations C(n, k), balanced parentheses the Catalan number, phone letters up to 4ⁿ. Add the cost of copying each solution (O(n)) and state the recursion depth (usually n, the solution length). For constraint searches like N-Queens and Sudoku there is no clean formula; say that the worst case is exponential and that pruning makes practical cases fast.

Returning one solution versus all solutions

Many problems only need to know whether a solution exists, or to return any one (Sudoku, Word Search). Then the recursive function returns a boolean, and as soon as a recursive call returns true, every level returns true immediately without trying further options — the search stops at the first success. Problems that ask for all solutions or a count must keep going after a success. Mixing the two — returning early from an "all solutions" search, or continuing after success in an existence check — is a frequent source of wrong or slow code, so decide which kind you are writing before you start.

Recognising the pattern

Backtracking fits when the problem says "all" (all subsets, permutations, combinations, partitions, paths, boards), when n is small (≤ 15–20), or when it asks for any solution to a puzzle with constraints. Before coding, write down the state, the choices, the pruning rule and the solution test, and decide how duplicates are handled.

Pruning: feasibility, bounds and ordering

Three kinds of pruning make backtracking practical. Feasibility pruning cuts a branch when the partial solution already violates a constraint (a queen under attack, a remaining sum below zero, more closing than opening brackets). Bound pruning cuts a branch when even the best possible completion cannot beat the best solution found so far — the basis of branch and bound for optimisation problems such as "the fewest coins" or "the shortest tour": if the current cost plus an optimistic estimate of the remainder already exceeds the best found, stop. Ordering does not cut branches by itself but changes which are explored first: trying the most constrained variable first (MRV) finds dead ends early, and trying the most promising value first finds good solutions early, which tightens bounds. Each pruning rule needs a one-sentence justification that it only removes hopeless branches.

From backtracking to dynamic programming

Consider Word Break ("can the string be split into dictionary words?"). Backtracking tries a first word, recurses on the rest, and backtracks on failure. On a string like "aaaa…ab" with dictionary {"a", "aa", "aaa"}, the same suffix is reached by many different splits of the prefix, and each time it is re-explored: exponential time. But the answer for a suffix does not depend on how the prefix was split. Caching the result per start index (functools.cache) collapses the search to n distinct subproblems with O(n) work each: O(n²). That transformation — notice repeated subproblems whose answers are path-independent, then memoise — is exactly how dynamic programming arises from recursion (al21). It does not apply when the state includes the whole path (Word Search's visited cells) or when you must output every solution.

Bitmasks as state

For small n, a set of chosen items can be a single integer whose bits mark membership. Subsets of n elements are just the integers 0 to 2ⁿ − 1, so they can be generated without recursion: [[nums[i] for i in range(n) if mask >> i & 1] for mask in range(1 << n)]. In permutation-like searches, a bitmask "used" set is hashable and cheap, which makes memoisation possible: "shortest path visiting all nodes" or "can we partition into k equal-sum subsets" memoise on (mask, …) and become bitmask DP with 2ⁿ·n states (al23, al24). N-Queens solvers use three bitmasks for columns and diagonals and find free positions with bit tricks, which is the fastest known simple implementation.

Meet in the middle

When n is around 40, 2⁴⁰ ≈ 10¹² is too many, but 2²⁰ ≈ 10⁶ is fine. Split the items into two halves, enumerate all subset sums of each half by backtracking, sort one list, and for each sum in the other list binary search for the complement. This solves subset-sum-like problems for n ≈ 40 in O(2^(n/2) · n). It is a useful card to play when the constraint is slightly too large for plain backtracking.

Recursion depth and iterative backtracking

Backtracking depth is the solution length — at most n, often small — so the call stack is rarely a problem; Python's default limit of 1,000 is plenty for subset and permutation problems. Grid searches are the exception: a DFS that can wander through a large grid may recurse once per cell, and a 300×300 grid has 90,000 cells. For those, use an explicit stack (al8, al16). Also be aware that the cost of copying a path at every node, rather than only at solutions, can dominate; copy only when recording.

Generators and lazy search

In Python, a backtracking function can yield each solution instead of appending it to a list, and recursive calls use yield from. The caller then consumes solutions one at a time and can stop early (next(gen) for "any one solution"), and memory stays proportional to the recursion depth rather than the number of solutions. This is how itertools.permutations and combinations behave, and it is the right shape for searches whose full output would not fit in memory.

Exact cover and Dancing Links

N-Queens, Sudoku and many tiling puzzles are instances of exact cover: choose rows of a 0/1 matrix so every column is covered exactly once. Knuth's Algorithm X solves exact cover by backtracking, always branching on the column with the fewest options (MRV again), and his "Dancing Links" implementation stores the matrix as circular doubly linked lists so that removing and restoring rows and columns — the choose and unchoose steps — are O(1) pointer updates. It is a beautiful example of designing a data structure around the undo operation of backtracking.

In the interview room

Backtracking code is graded on three things: correctness of the state management, duplicate handling, and the complexity explanation. The frequent bugs: appending path instead of a copy; forgetting to undo a change (popping the path but not unmarking used, or not restoring a grid cell); recursing with i + 1 when reuse is allowed (or i when it is not); skipping duplicates without sorting first, or with i > 0 instead of i > start; and mutable default arguments (def go(path=[])) that leak between calls. Test with an empty input, a single element, and an input with duplicates.

Explain complexity by counting the tree: "there are 2ⁿ subsets, each copied in O(n), so O(n·2ⁿ) time, O(n) extra space for the recursion besides the output". For pruned searches, say the worst case and why pruning helps. Interviewers often ask how to speed up a slow backtracking solution; the answers are better pruning, better ordering (MRV), memoisation if subproblems repeat, or a different algorithm if the problem has more structure than the search exploits.

Be ready to write the same search iteratively or as a generator. Some interviewers ask for a generator that yields solutions lazily (yield path[:] inside the recursion, and yield from go(...) for recursive calls), which is how you would expose a search over a huge space without materialising everything in memory.

One more practical point: when an online assessment problem has n ≤ 20 and the obvious approach is exponential, write the backtracking cleanly first and only then optimise. A correct exponential solution that passes the given limits is the intended answer far more often than candidates expect.

When the search is slow in a live round and you have a few minutes, the highest-value improvements are almost always the same three: sort the choices so that failures happen early (largest numbers first, most constrained cell first), add a cheap feasibility check on partial solutions, and break symmetry (do not try equivalent choices twice, such as placing an item into two empty buckets). Say which one you are adding and why; interviewers value the reasoning as much as the speed-up.

In real systems

Backtracking search is the engine inside many practical tools. SAT solvers — which check whether a Boolean formula can be satisfied, and are used for hardware verification, package dependency resolution and planning — descend from the DPLL backtracking algorithm, enhanced with constraint propagation and clause learning. Package managers like pip's resolver and Debian's apt explore candidate versions and backtrack on conflicts. Constraint solvers for timetabling, staff rostering and logistics use backtracking with heuristics like MRV. Regular-expression engines in Python, Java and JavaScript use backtracking to match patterns, which is why some patterns take exponential time on adversarial inputs (catastrophic backtracking, the cause of real outages); engines like RE2 avoid backtracking entirely to guarantee linear time. Prolog's execution model is backtracking search. Even type inference and parsing with ambiguous grammars rely on it. The interview lessons — explicit state, careful undo, early pruning, smart ordering — are exactly the concerns of those systems.

Design the search

"Given an array of up to 16 positive integers and k, can the array be partitioned into k subsets with equal sums?" Design a backtracking solution, its pruning, and say what you would do if it were too slow.

Answer

First checks: if sum % k ≠ 0, return false; target = sum / k; if the largest element exceeds target, return false. Sort the numbers in decreasing order — placing big numbers first fails fast. State: an array of k bucket sums. For each number in order, try putting it into each bucket whose sum plus the number is ≤ target; recurse to the next number; undo. Success when every number is placed (all buckets must then equal target). Pruning: (1) capacity — skip a bucket if it would overflow; (2) symmetry — if two buckets currently have the same sum, trying the number in the second is pointless, so skip a bucket whose sum equals an earlier bucket's sum (in particular, only try one empty bucket); (3) decreasing order, as above. These make typical inputs fast. If still too slow, switch to bitmask DP over used elements: dp[mask] = the fill level of the current bucket after using the elements in mask (or −1 if unreachable); for each mask and unused element i with dp[mask] + nums[i] ≤ target, set dp[mask | 1 << i] = (dp[mask] + nums[i]) % target. The answer is dp[full] == 0. That is O(2ⁿ · n) ≈ 10⁶ operations for n = 16 — guaranteed, unlike the search.
