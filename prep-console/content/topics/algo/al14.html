Your file system is a tree: folders contain folders and files. So is a web page (the HTML document object model), a company's reporting structure, the parsed form of every program a compiler reads, and the index that lets a database find one row among a billion. When an interviewer asks a tree question, they are testing whether you can reason about data that branches — and whether you are comfortable with the recursion that branching data invites.

Tree problems make up a large share of coding interviews, and they have a reputation for being either trivially short or baffling. "Maximum depth" is three lines. "Maximum path sum" is also about ten lines, but most candidates cannot find those ten lines under pressure. The difference is not cleverness; it is knowing a small number of reusable shapes. Almost every binary tree solution is one of: a traversal in a particular order; a recursion that passes information down to children; a recursion that returns information up to parents; or a recursion that returns one thing up while updating a global answer on the side. Binary search trees add one more idea — an ordering that lets you discard half the tree at each step.

This lesson builds those shapes in order: the vocabulary and traversal orders (depth-first and level by level, recursive and iterative); top-down versus bottom-up recursion; the "return one thing, track another" pattern behind diameter and maximum path sum; the BST property and the classic BST bug; lowest common ancestor; building a tree from traversals; and serialisation. Each is worked through with a trace on a small tree.

The mental model: a family tree, and asking your children

A binary tree is a family tree in which each person has at most two children, called left and right. The person at the top is the root; people with no children are leaves. A person's subtree is that person plus all their descendants. Two measures matter constantly: the depth of a node is how many generations below the root it is, and the height of a node is how many generations its longest line of descendants goes down.

Now the key idea. Suppose the root wants to know "how many generations does our family span?". The root does not need to look at everyone. It asks its left child "how deep does your branch go?", asks its right child the same, takes the larger answer and adds one for itself. Each child answers by asking its own children, and so on down to the leaves, whose answer is immediate. That is recursion on trees: a node's answer is computed from its children's answers. Because every subtree is itself a tree, the same function works at every level.

Two directions of information

Tree recursions move information in one of two directions, and choosing correctly is most of the design.

  • Top-down: the parent tells the child something about the path above it — "you are at depth 3", "the largest value above you is 8", "your value must lie between 2 and 9". The child uses it and passes an updated version down. Answers are usually collected at the leaves or in a shared result.
  • Bottom-up: the child tells the parent something about the subtree below it — "my subtree has height 4", "my subtree sums to 17", "my subtree is balanced". The parent combines its children's answers into its own.

Some problems need both, and the hardest ones return one value up (for the parent's use) while updating a separate global answer that involves both children. Recognising which direction a problem needs is the first question to ask.

Where the family analogy breaks: a family can have more than two children, and real trees in software often do (file systems, the HTML DOM, B-trees with hundreds of children per node). Everything in this lesson generalises — loop over the children instead of naming left and right — but binary trees dominate interviews because they keep the code short. The other break: in a family you can ask your parent a question, but a tree node usually has no pointer to its parent. Problems that need to go "up" from an arbitrary node (distance k, for instance) must first record parents themselves.

One more practical point about cost: almost every tree algorithm in this lesson visits each node a constant number of times, so it is O(n) time; the extra space is the recursion depth, O(h). Saying "O(n) time and O(h) space, where h is log n if balanced and n if degenerate" covers the complexity question for most tree problems in one sentence.

Depth-first traversals: recursive and iterative

class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val, self.left, self.right = val, left, right

def inorder(node, out):
    if not node: return
    inorder(node.left, out)
    out.append(node.val)          # move this line up for pre-order, down for post-order
    inorder(node.right, out)

Recursion is the clearest form, but interviews often ask for the iterative version, and Python's recursion limit makes it necessary for very deep trees. Iterative in-order uses a stack to remember the nodes whose left subtrees you are exploring:

def inorder_iter(root):
    out, stack, node = [], [], root
    while node or stack:
        while node:                 # go as far left as possible
            stack.append(node); node = node.left
        node = stack.pop()          # leftmost unvisited node
        out.append(node.val)
        node = node.right           # then its right subtree
    return out

Iterative pre-order is simpler — pop a node, record it, push its right child then its left child (so the left is processed first). Iterative post-order is the trickiest; a common trick is to do a modified pre-order (node, right, left) and reverse the output.

Level-order traversal

Breadth-first traversal visits nodes level by level, using a queue. The one technique to know is how to separate levels: read the queue's length at the start of a level, and pop exactly that many nodes.

from collections import deque
def level_order(root):
    if not root: return []
    res, q = [], deque([root])
    while q:
        level = []
        for _ in range(len(q)):          # exactly the nodes of this level
            node = q.popleft()
            level.append(node.val)
            if node.left: q.append(node.left)
            if node.right: q.append(node.right)
        res.append(level)
    return res

On the figure's tree this gives [[4], [2, 6], [1, 3, 5, 7]]. Variants are small edits: Right Side View takes the last value of each level; Zigzag reverses every other level; minimum depth returns the level number of the first leaf found, which BFS finds before exploring deeper levels — an advantage over DFS when the tree is lopsided.

Top-down recursion: passing information down

"Count the good nodes: a node is good if no node on the path from the root to it has a larger value." Each node needs to know the maximum value on the path above it — information that flows down.

def good_nodes(root):
    def go(node, max_above):
        if not node: return 0
        good = 1 if node.val >= max_above else 0
        m = max(max_above, node.val)
        return good + go(node.left, m) + go(node.right, m)
    return go(root, float("-inf"))

Other top-down problems: "Path Sum" (pass the remaining target down; succeed at a leaf where it reaches zero), "Path Sum II" (pass the path down and backtrack — append on entry, pop on exit, al13), "sum root-to-leaf numbers" (pass the number formed so far: cur * 10 + node.val), and BST validation (pass bounds down, below).

Bottom-up recursion: returning information up

"Is the tree height-balanced (every node's subtrees differ in height by at most one)?" A node can only decide after knowing its children's heights — information that flows up. A neat trick returns −1 to mean "unbalanced", so one function returns both the height and the verdict:

def is_balanced(root):
    def height(node):
        if not node: return 0
        l = height(node.left)
        if l == -1: return -1
        r = height(node.right)
        if r == -1 or abs(l - r) > 1: return -1
        return 1 + max(l, r)
    return height(root) != -1

This is O(n). The naive version — compute heights separately at every node — is O(n²) on a degenerate tree, because each height call walks the whole subtree again. Returning combined information in one pass is the bottom-up pattern's main advantage.

Comparison problems are bottom-up too. Same Tree: both null, or equal values and same left and same right. Symmetric Tree: compare the left subtree with the mirror of the right (left.left with right.right, left.right with right.left). Subtree of Another Tree: at each node of the big tree, run Same Tree against the small one — O(m·n) — or serialise both with null markers and use a substring search for O(m + n).

Return one thing, track another: diameter and maximum path sum

"The diameter is the number of edges on the longest path between any two nodes." The longest path through a given node goes down its left side as far as possible and down its right side as far as possible: left height + right height. But the parent cannot use a path that bends at its child — a path through the parent can only continue down one side of the child. So the function returns the height (what the parent can use) and updates a global with the bent path (the candidate answer).

def diameter(root):
    best = 0
    def height(node):
        nonlocal best
        if not node: return 0
        l, r = height(node.left), height(node.right)
        best = max(best, l + r)          # path bending at this node
        return 1 + max(l, r)             # path the parent can extend
    height(root)
    return best

Binary Tree Maximum Path Sum (values can be negative; a path can start and end anywhere) is the same shape with sums instead of heights. Define gain(node) = the best sum of a path that starts at node and goes down one side. A negative child gain is better ignored (take 0 instead). At each node, the best path bending there is node.val + max(0, gain(left)) + max(0, gain(right)); the gain returned to the parent is node.val + max(0, gain(left), gain(right)).

def max_path_sum(root):
    best = float("-inf")
    def gain(node):
        nonlocal best
        if not node: return 0
        l = max(0, gain(node.left)); r = max(0, gain(node.right))
        best = max(best, node.val + l + r)
        return node.val + max(l, r)
    gain(root)
    return best

Trace on root −10 with children 9 and 20, where 20 has children 15 and 7: gain(9) = 9; at 20, gains 15 and 7, best = 20 + 15 + 7 = 42, return 20 + 15 = 35; at −10, l = 9, r = 35, candidate −10 + 9 + 35 = 34 < 42. Answer 42 — a path that never touches the root. Initialising best to −∞, not 0, matters for all-negative trees.

Binary search trees

A binary search tree (BST) adds an ordering: every key in a node's left subtree is smaller than the node's key, and every key in its right subtree is larger. That makes search like binary search: compare with the node, go left or right, and discard the other subtree. Search, insert and delete each follow one root-to-leaf path, O(h). An in-order traversal visits keys in sorted order — the most useful fact about BSTs in interviews.

Validating a BST is the classic trap. Checking only left.val < node.val < right.val at each node accepts trees like 5 → (left 4, right 6 → (left 3)), where 3 sits in 5's right subtree but is smaller than 5. Every node must respect bounds from all its ancestors, which is top-down information:

def is_valid_bst(root):
    def ok(node, lo, hi):
        if not node: return True
        if not (lo < node.val < hi): return False
        return ok(node.left, lo, node.val) and ok(node.right, node.val, hi)
    return ok(root, float("-inf"), float("inf"))

The alternative is to run an in-order traversal and check that each value is strictly greater than the previous one.

K-th smallest in a BST: run the iterative in-order traversal and stop at the k-th popped node, O(h + k). LCA in a BST: walk from the root; if both p and q are smaller, go left; if both are larger, go right; otherwise the current node splits them and is the answer, O(h). Convert a sorted array to a balanced BST: the middle element is the root, recursively build each half — O(n), height ⌈log₂(n + 1)⌉.

Lowest common ancestor in a general binary tree

Without the BST ordering, you cannot decide which way to go, so search both sides. The recursive function returns the node if it is p or q (or None if neither is in this subtree); if both children report a non-null result, p and q are on different sides and this node is their LCA.

def lca(node, p, q):
    if node is None or node is p or node is q:
        return node
    l, r = lca(node.left, p, q), lca(node.right, p, q)
    if l and r: return node         # p and q on different sides
    return l or r                   # both on one side, or only one found so far

O(n). It works even when p is an ancestor of q: the search returns p as soon as it reaches it, and p is indeed the LCA. (It assumes both nodes exist in the tree; if that is not guaranteed, count how many were actually found.)

Building a tree from traversals

Given pre-order [3, 9, 20, 15, 7] and in-order [9, 3, 15, 20, 7], rebuild the tree (values unique). The first pre-order value, 3, is the root. In the in-order list, everything left of 3 ([9]) is the left subtree and everything right ([15, 20, 7]) is the right subtree. The left subtree has 1 node, so the next 1 pre-order value (9) belongs to it, and the rest ([20, 15, 7]) to the right. Recurse.

def build_tree(preorder, inorder):
    idx = {v: i for i, v in enumerate(inorder)}
    it = iter(preorder)
    def build(lo, hi):                      # in-order range [lo, hi)
        if lo >= hi: return None
        v = next(it)                        # next pre-order value is this root
        node = TreeNode(v)
        node.left = build(lo, idx[v])       # left first: matches pre-order
        node.right = build(idx[v] + 1, hi)
        return node
    return build(0, len(inorder))

The dictionary of in-order positions makes each split O(1), so construction is O(n). Consuming pre-order with an iterator in the same order as the recursion (root, left, right) avoids computing pre-order index ranges.

Serialisation

To store a tree as a string and rebuild it exactly, write a pre-order traversal with an explicit marker for every missing child, such as "1,2,#,#,3,4,#,#,5,#,#". The markers make the encoding unambiguous (a traversal without them cannot distinguish a left-only child from a right-only child). Deserialise with the same recursion: read a token; "#" means None; otherwise make a node and build its left then right subtree from the following tokens. Both directions are O(n). Level-order with markers (the format LeetCode uses to display trees) works too.

Going up: parent pointers

"All Nodes Distance K in Binary Tree" asks for nodes k edges from a target, which can be up through ancestors and then down other branches. Trees only point downwards, so first run a DFS that records each node's parent in a dict. Now the tree is effectively an undirected graph; run a BFS from the target, stepping to left, right and parent, with a visited set, for exactly k levels. This "turn the tree into a graph" move recurs whenever a problem needs to travel upwards.

Recognising the pattern

For any tree problem, ask: does each node need information from above (top-down) or from below (bottom-up)? Is the answer a single global value built from local candidates (track a global)? Is it about levels or shortest distance from the root (BFS)? Does the BST ordering let me discard subtrees? Then write the function signature first — its parameters are the top-down information and its return value is the bottom-up information.

Why BSTs need balancing

Inserting the keys 1, 2, 3, …, n into a plain BST in that order builds a chain where every node has only a right child: height n − 1, and every operation O(n). Self-balancing BSTs fix this by restructuring with rotations — local rearrangements of a parent and child that preserve the in-order sequence while changing heights. AVL trees keep every node's subtree heights within one of each other (height ≤ about 1.44 log₂ n); red-black trees enforce a looser colouring rule (height ≤ 2 log₂(n + 1)) with fewer rotations per update, which is why they are the usual choice in standard libraries (C++ std::map, Java TreeMap, the Linux kernel's scheduler and memory areas historically). Python has no built-in balanced BST; the third-party sortedcontainers uses a list-of-lists design instead. In interviews you are rarely asked to implement rotations, but you should know why balancing exists and what guarantee it buys.

Tree DP: returning tuples

Some bottom-up problems need more than one value from each child. "House Robber III": houses form a binary tree, adjacent (parent–child) houses cannot both be robbed; maximise the total. Each node returns a pair (best if this node is robbed, best if it is not). If robbed, its children must not be: rob = val + left.skip + right.skip. If skipped, each child may be either: skip = max(left) + max(right). The answer is the max of the root's pair. Returning a tuple per node turns what looks like an exponential choice into O(n) — this is dynamic programming on trees (al23), and the same shape solves "minimum cameras to monitor a tree" (three states per node) and "maximum independent set on a tree".

Morris traversal: O(1) extra space

Recursive and stack-based traversals use O(h) space. Morris in-order traversal uses O(1) by temporarily threading the tree: for a node with a left subtree, find its in-order predecessor (the rightmost node in the left subtree) and point that predecessor's right child back to the node. Then go left. When you later arrive back at the node through the thread, you know the left subtree is done: remove the thread, visit the node, and go right. Every edge is traversed a constant number of times, so it is O(n) time. It is a favourite "can you do it in constant space?" follow-up; the key sentence is "use the null right pointers of predecessors as temporary return links, and restore them".

Many LCA queries: binary lifting

The recursive LCA is O(n) per query. For q queries on a static tree, preprocess once: record each node's depth and its 2ᵏ-th ancestor for every k up to log n (up[k][v] = up[k − 1][up[k − 1][v]]). To answer LCA(u, v), lift the deeper node to the same depth using the binary representation of the depth difference, then lift both together from the largest k downwards while their ancestors differ; the parent of where they stop is the LCA. Preprocessing is O(n log n) and each query O(log n). The same table answers "k-th ancestor" queries, and the technique ("jump pointers at powers of two") reappears in skip lists and in sparse tables (al27).

Counting tree shapes and why recursion fits

The number of distinct binary tree shapes with n nodes is the n-th Catalan number (1, 1, 2, 5, 14, 42, …), the same sequence that counts balanced parenthesis strings (al13). This is not a coincidence: a tree is a root plus a left tree and a right tree, so count(n) = Σ count(i) · count(n − 1 − i), which is the Catalan recurrence. "Unique Binary Search Trees" asks exactly for this number, and "Unique Binary Search Trees II" asks you to generate them all by recursing on every possible root. The recursive definition of trees — a node with two smaller trees — is why recursion is the natural language for them.

Recursion depth and iterative post-order

A degenerate tree with 10⁵ nodes makes a recursive traversal exceed Python's default limit of 1,000 frames. Options: raise the limit with sys.setrecursionlimit (risky — the C stack can still overflow and crash the interpreter), or rewrite iteratively. For bottom-up computations that need children's results first, iterative post-order can use a stack of (node, visited_flag) pairs: push (node, False); on popping a False entry, push (node, True) then the children; on popping a True entry, all children have been processed and their results (stored in a dict) can be combined. Mentioning this when the interviewer says "the tree can have 10⁵ nodes in a line" shows awareness of the runtime, not just the algorithm.

In the interview room

Tree problems reward a clear function signature. Before coding, say what the recursive function takes (the top-down information) and what it returns (the bottom-up information), and whether a separate global is updated. "height(node) returns the height of node's subtree and updates best with the longest path bending at node" is a complete plan; the code follows in a few lines.

The common bugs are predictable. Forgetting the None base case (or handling leaves but not empty trees). Confusing height conventions (edges versus nodes) and being off by one in diameter. Validating a BST with local parent–child comparisons. Using 0 instead of −∞ as the initial best in max-path-sum. Using == on node values instead of is on node identities in LCA when values can repeat. Mutating a shared path in Path Sum II without popping. And for BFS, forgetting to snapshot len(q) before the inner loop, which mixes levels. Test on an empty tree, a single node, a left-only chain, and a tree with negative values.

Interviewers often follow up on complexity with "what if the tree is very deep?" (recursion limit; iterative traversal), "what if there are many queries?" (precompute subtree sizes, parents, or binary lifting), and "what if the BST is unbalanced?" (O(n) operations; self-balancing trees). For hard problems like max path sum, they usually ask you to explain why the return value and the global answer differ — have the "a parent can only extend a one-sided path" sentence ready.

Finally, draw. A five-node tree on the whiteboard, with the values your function returns written next to each node, is the fastest way to check a bottom-up recursion and the most convincing way to explain it.

On online assessments, tree inputs usually arrive as a level-order list with nulls (LeetCode's format) or as parent arrays and edge lists. Converting edges into an adjacency list and treating the tree as a graph rooted at node 0 is often the cleanest route, and it makes BFS and DFS from al16 directly applicable.

In real systems

Trees are everywhere in production systems. Databases index tables with B-trees and B+ trees — balanced trees with hundreds of children per node, so that a lookup among a billion rows touches only three or four disk pages (the database track covers them in depth). File systems store directories as trees, and many (ext4's htree, Btrfs, APFS) use B-tree variants internally. Browsers parse HTML into the DOM tree and lay out pages by traversing it; CSS selectors are matched by walking it. Compilers and interpreters parse source code into abstract syntax trees — Python's own ast module exposes them — and run optimisation passes as tree traversals. Git stores each commit's snapshot as a tree of tree objects, and Merkle trees (each node a hash of its children) let Git, blockchains and distributed databases like Cassandra detect differences between replicas by comparing hashes top-down. Machine-learning decision trees and gradient-boosted ensembles are, literally, binary trees evaluated root to leaf. The interview skills — choosing the traversal, passing state down, aggregating results up — are the same ones those systems use.

    import random
from itertools import combinations

class T:
    def __init__(s, v, l=None, r=None): s.val, s.left, s.right = v, l, r

def rand_tree(n, lo=0, hi=9):
    if n == 0: return None
    k = random.randint(0, n - 1)
    return T(random.randint(lo, hi), rand_tree(k, lo, hi), rand_tree(n - 1 - k, lo, hi))

def diameter(root):
    best = 0
    def h(n):
        nonlocal best
        if not n: return 0
        a, b = h(n.left), h(n.right); best = max(best, a + b); return 1 + max(a, b)
    h(root); return best

def diameter_brute(root):                  # BFS from every node over an undirected view
    adj, stack = {}, [(root, None)]
    while stack:
        n, p = stack.pop()
        if not n: continue
        adj.setdefault(n, [])
        if p: adj[n].append(p); adj[p].append(n)
        stack += [(n.left, n), (n.right, n)]
    def far(s):
        dist, q = {s: 0}, [s]
        for u in q:
            for w in adj[u]:
                if w not in dist: dist[w] = dist[u] + 1; q.append(w)
        return max(dist.values())
    return max((far(s) for s in adj), default=0)

def valid(n, lo=float("-inf"), hi=float("inf")):
    return not n or (lo < n.val < hi and valid(n.left, lo, n.val) and valid(n.right, n.val, hi))

def inorder(n): return inorder(n.left) + [n.val] + inorder(n.right) if n else []

for _ in range(3000):
    t = rand_tree(random.randint(0, 9))
    assert diameter(t) == diameter_brute(t)
    vals = inorder(t)
    assert valid(t) == all(a < b for a, b in zip(vals, vals[1:]))
print("diameter and BST validation agree with brute force")

Choose the direction

For each problem, say whether you pass information down, return it up, or both, and write the function signature. (a) Sum of all root-to-leaf numbers, where each path's digits form a number. (b) Count the subtrees whose values are all equal (uni-value subtrees). (c) The longest path where consecutive nodes differ by exactly one (Binary Tree Longest Consecutive Sequence, parent to child only). (d) Flatten the tree into a linked list in pre-order, in place.

Answer

(a) Down: go(node, cur) with cur = cur·10 + node.val; at a leaf return cur, otherwise return go(left) + go(right). (b) Up plus global: is_uni(node) -> bool; a node is uni-value if both children are uni-value (None counts) and each existing child's value equals node.val; increment a global count when true. Evaluate both children before combining, so every subtree is counted — short-circuiting with and would skip the right subtree. (c) Down is simplest: go(node, parent_val, length) where length becomes length + 1 if node.val == parent_val + 1 else 1, updating a global maximum; a bottom-up version returning "longest consecutive path starting here going down" also works. (d) Up: flatten(node) -> tail returns the last node of the flattened subtree; flatten the left and right, then splice: left_tail.right = node.right, node.right = node.left, node.left = None, and return the right tail (or left tail, or node). Alternatively the O(1)-space Morris-like loop: for each node with a left child, attach the right subtree to the rightmost node of the left subtree, move the left subtree to the right, and advance.
