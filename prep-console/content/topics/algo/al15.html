Type "algo" into a search box and, before you finish, it suggests "algorithm", "algorithms book", "algolia". Behind that box is a set of millions of past queries, and every keystroke must find the ones that start with what you have typed so far — in a few milliseconds. A hash set of the queries is no help: it can tell you instantly whether "algorithm" is in the set, but not which entries begin with "algo", short of scanning all of them.

The same problem appears in many guises. A spell checker wants to know whether any dictionary word starts with "recie" so it can stop suggesting along that path. A Boggle solver walks a grid of letters and must abandon a path as soon as no word begins with the letters collected so far. An internet router receives a packet for address 203.0.113.42 and must find, among hundreds of thousands of stored address prefixes, the longest one that matches. All of these are prefix questions.

A trie (from retrieval, usually pronounced "try") answers them by storing strings as paths in a tree, one character per edge. All words starting with "algo" share the same first four edges, so finding them means walking four steps from the root and then looking only at what lies below. The cost of a lookup depends on the length of the word, not on how many words are stored.

This lesson builds a trie from scratch, then applies it to the interview classics: wildcard search, Word Search II (the hard grid problem that becomes tractable only with a trie), autocomplete and search suggestions, replacing words by their roots, and a surprising use on numbers — a trie over bits that finds the pair with the maximum XOR. It also covers when a trie is the wrong tool and a sorted array or hash set is better.

The mental model: a dictionary's thumb index, taken all the way

A printed dictionary has tabs on the edge for each first letter: open at "C" and you have skipped every word starting with other letters. Imagine tabs inside the "C" section for the second letter, tabs inside "CA" for the third, and so on. To look up "cart" you follow tab C, then A, then R, then T. To list every word beginning with "car", you follow three tabs and read everything in that section. That nested set of tabs is a trie.

In code, each node is a small object with two things: a map from a character to the child node for that character, and a flag saying "a complete word ends here". The root represents the empty prefix. The path from the root to any node spells a prefix; the node "is" that prefix.

Three operations follow directly. Insert walks the word from the root, creating children that do not exist yet, and sets the end flag on the last node. Search walks the word and succeeds only if every step exists and the final node has the end flag (so "car" is found, "ca" is not). startsWith walks the prefix and succeeds if every step exists, ignoring the flag. Each takes one step per character: O(L) for a string of length L, no matter whether the trie holds ten words or ten million.

Where the thumb-index analogy breaks: a book's tabs cost nothing, but a trie's nodes cost memory, and there is one node per distinct prefix. Words with long unshared tails ("supercalifragilistic") create a long chain of single-child nodes. The deep layer covers how compressed tries merge those chains. The other break: a dictionary is sorted, so you can also find the "car…" section by binary search on the pages. For a fixed word list, a sorted array with binary search is often a strong, memory-light alternative — knowing when to prefer it is part of the senior answer.

It also helps to compare the three ways of answering "which words start with car?". Scanning a list checks every word: O(n·L). A hash set cannot answer at all without the same scan. A trie walks three nodes and then enumerates only the matching subtree: O(3 + size of the answer). For a dictionary of a million words and a prefix matching twenty of them, that is the difference between millions of character comparisons and a few dozen steps. The trie pays for this in memory and in build time — O(total characters) to insert everything — which is why it suits workloads with many prefix queries over the same set.

A rule of thumb for recognising trie problems: if the brute force repeatedly asks "is this string a prefix of something in my set?" or "which items in my set start with this?", a trie turns each such question into a walk of a few steps.

Implementing a trie

class TrieNode:
    __slots__ = ("children", "end")
    def __init__(self):
        self.children = {}          # char -> TrieNode
        self.end = False

class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word):
        node = self.root
        for ch in word:
            node = node.children.setdefault(ch, TrieNode())
        node.end = True

    def _walk(self, s):
        node = self.root
        for ch in s:
            node = node.children.get(ch)
            if node is None:
                return None
        return node

    def search(self, word):
        node = self._walk(word)
        return node is not None and node.end

    def starts_with(self, prefix):
        return self._walk(prefix) is not None

Trace inserting "car", "cart", "cat", "dog" into an empty trie: "car" creates nodes c, ca, car and flags car. "cart" walks c, ca, car (all existing) and creates cart, flagging it. "cat" walks c, ca and creates cat. "dog" creates d, do, dog. That is 8 nodes plus the root for 13 characters of input — the shared "ca" and "car" saved five. search("ca") finds the node but its flag is false; starts_with("ca") is true; search("cab") falls off at "b" and is false.

Children can be a dict (flexible, any alphabet) or a fixed list of 26 slots indexed by ord(ch) − 97 (faster in compiled languages, wasteful when most slots are empty). In Python, a dict is the usual choice; __slots__ trims the per-node memory. Two useful extras: a count field incremented on every insert passing through a node (answers "how many words start with this prefix?" and supports deletion), and storing the whole word at its end node instead of a boolean (convenient when a search needs to report which word it found).

Wildcard search: Add and Search Words

"Support addWord and search, where the search pattern may contain '.', which matches any single letter." Normal letters follow one child; a '.' must try every child. That is a depth-first search over the trie:

def search(self, pattern):
    def dfs(node, i):
        if i == len(pattern):
            return node.end
        ch = pattern[i]
        if ch == ".":
            return any(dfs(child, i + 1) for child in node.children.values())
        child = node.children.get(ch)
        return child is not None and dfs(child, i + 1)
    return dfs(self.root, 0)

A pattern without dots costs O(L). A pattern like "..." can visit every node at depth 3, which for a large dictionary is many — but still far fewer than all words, because only paths of the right length are explored, and any stops at the first match. A practical optimisation is to keep separate tries per word length, so a pattern only searches words of its own length.

Word Search II: a trie plus grid backtracking

"Given an m×n letter grid and a list of up to 3 × 10⁴ words, return all words that can be traced through adjacent cells (each cell used once per word)." Running the single-word Word Search (al13) for every word repeats the same grid exploration thousands of times. The trie lets one backtracking pass serve all words at once: walk the grid and the trie in lockstep, and stop the moment the letters collected so far are not a prefix of any word.

def find_words(board, words):
    root = TrieNode()
    for w in words:                                  # build the trie
        node = root
        for ch in w:
            node = node.children.setdefault(ch, TrieNode())
        node.end = w                                 # store the word itself
    R, C, found = len(board), len(board[0]), []

    def dfs(r, c, parent):
        ch = board[r][c]
        node = parent.children.get(ch)
        if node is None:
            return                                   # not a prefix: prune
        if node.end:
            found.append(node.end); node.end = False # record once
        board[r][c] = "#"                            # mark visited
        for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
            nr, nc = r + dr, c + dc
            if 0 <= nr < R and 0 <= nc < C and board[nr][nc] != "#":
                dfs(nr, nc, node)
        board[r][c] = ch                             # restore
        if not node.children and not node.end:
            parent.children.pop(ch)                  # prune exhausted branch

    for r in range(R):
        for c in range(C):
            dfs(r, c, root)
    return found

Three details make it fast and correct. Storing the word at its end node avoids rebuilding it from the path. Clearing node.end after recording prevents the same word being reported from several starting cells. And removing a trie node once it has no children and no word left means later searches do not even enter that branch — after all the words under a prefix are found, the prefix disappears from the trie, and the remaining search space shrinks as you go. Without the trie, each grid path would be compared against every word; with it, the work is bounded by the number of grid paths that spell prefixes of real words.

Autocomplete and search suggestions

"Search Suggestions System": as the user types each character of a search word, return up to three products (lexicographically smallest) that start with the typed prefix. Two good solutions illustrate the trie-versus-array trade-off.

Trie with cached suggestions. Insert products in sorted order; at each node passed through, append the product to a list kept at that node if the list has fewer than three entries. Because insertion is in sorted order, each node's list holds the three smallest products with that prefix. A query walks one node per typed character and reads its list — O(1) per keystroke after the walk.

Sorted array and binary search. Sort products; for each prefix, i = bisect_left(products, prefix) is the first product ≥ prefix, and the next up to three products are the answer if they start with the prefix. No extra structure, O(log n) per keystroke, and minimal memory. For a static product list this is often the better engineering choice; the trie wins when products are added continuously or when suggestions are ranked by a changing score.

Real autocomplete ranks by popularity rather than alphabet. The same idea applies: each trie node caches its top k completions by score. Updating a score means walking the word's path and adjusting each cache, which is O(L · k) — acceptable because reads vastly outnumber updates.

Prefix replacement and shortest roots

"Replace Words": given roots such as "cat", "bat", "rat" and a sentence, replace every word by the shortest root that is a prefix of it ("cattle" → "cat"). Insert the roots in a trie, and for each word walk the trie character by character, stopping at the first node with an end flag — that is the shortest root. If the walk falls off the trie before reaching any end flag, the word has no root and stays as is. Total O(total characters), compared with checking every root against every word.

Building words one letter at a time

"Longest Word in Dictionary": find the longest word that can be built one character at a time, where every prefix along the way is also a word (for "world", the words w, wo, wor, worl must all be present). In trie terms: find the deepest node reachable from the root by passing only through nodes with the end flag set. A DFS that only enters flagged children, exploring children in alphabetical order, finds it and naturally returns the lexicographically smallest among the longest.

Tries over bits: maximum XOR

"Find the maximum value of a[i] XOR a[j]." The brute force is O(n²). XOR is 1 in a bit position exactly when the two bits differ, and a 1 in a high bit outweighs all lower bits combined. So, for a number x, the best partner is the one that differs from x in the highest possible bit, then — among those — in the next highest, and so on. That is a greedy walk down a trie of the numbers' bits.

def find_maximum_xor(nums, B=31):
    root = {}
    for x in nums:                       # insert bits, most significant first
        node = root
        for b in range(B, -1, -1):
            node = node.setdefault((x >> b) & 1, {})
    best = 0
    for x in nums:
        node, cur = root, 0
        for b in range(B, -1, -1):
            bit = (x >> b) & 1
            if 1 - bit in node:          # opposite bit available: XOR gets a 1 here
                cur |= 1 << b; node = node[1 - bit]
            else:
                node = node[bit]
        best = max(best, cur)
    return best

O(n · B) for B bits — linear for fixed-width integers. For [3, 10, 5, 25, 2, 8], the answer is 5 XOR 25 = 28. The same binary trie answers "maximum XOR of x with any element ≤ m" when combined with offline sorting (insert elements in increasing order as the limit grows), and "count pairs with XOR below k" with per-node counts.

Deleting words

Deletion is occasionally asked and is a good test of care. With per-node counts, delete walks the word's path, decrements each node's count, clears the end flag at the last node, and removes any child whose count drops to zero (that whole branch now belongs to no word). Without counts, delete recursively: unset the end flag, and on the way back up remove a child if it has no children and no end flag. Either way, check first that the word is actually present, or the counts will go wrong.

Shortest unique prefixes

"For each word, return the shortest prefix that identifies it uniquely among the list" (as used for compact command abbreviations). Insert all words with per-node counts. For each word, walk its path and stop at the first node whose count is 1 — only this word passes through it, so the prefix up to there is unique. If no such node exists (the word is a prefix of another word), the whole word is needed. This is O(total characters) and a neat example of how a single counter per node unlocks a question that would otherwise require comparing every pair of words.

Recognising the pattern

Reach for a trie when the problem involves prefixes ("starts with", autocomplete, shortest root, longest common prefix), when a search must be pruned as soon as a partial string cannot be extended (grid word search, Boggle, wildcard patterns), or when you need the best match bit by bit (maximum XOR, longest-prefix match). If the words are static and you only need prefix ranges, consider a sorted array with binary search instead.

Memory: the real cost of a trie

A trie node in Python is an object plus a dict; even with __slots__, each node costs on the order of 100–250 bytes, and there is one node per distinct prefix. A dictionary of 500,000 English words has a few million prefixes, which can mean hundreds of megabytes — many times the size of the words as plain strings. In C or Rust, a node with 26 child pointers is 208 bytes on a 64-bit machine, mostly null. This is why production systems rarely use naive tries for large static sets. The alternatives are a sorted array with binary search (minimal memory, prefix ranges in O(log n)), a compressed trie, or a finite-state automaton.

Compressed tries (radix trees)

Most nodes deep in a trie have a single child: after "supercal" there is only one way to continue in an English dictionary. A compressed trie (radix tree, or PATRICIA tree for the binary version) merges every chain of single-child nodes into one edge labelled with a whole substring. The number of nodes drops to at most 2n − 1 for n strings, and lookups still read each character once. Insertion occasionally splits an edge when a new word diverges in the middle of a label. Radix trees are used in the Linux kernel (for the page cache and IP routing tables historically), in HTTP routers that match URL paths, and in Ethereum's Merkle Patricia trie.

Many patterns at once: Aho–Corasick

To find every occurrence of many patterns (say, 10,000 banned words) in a long text, building a trie of the patterns is the first step. Aho–Corasick adds failure links: from each node, a pointer to the node for the longest proper suffix of its prefix that is also a prefix in the trie — the same idea as the KMP failure function (al26), generalised from one pattern to a trie. Scanning the text then follows trie edges when possible and failure links when not, never moving backwards in the text, and reports matches in O(text length + number of matches). It powers multi-keyword search tools such as grep -F with many patterns and many intrusion-detection systems.

Suffix tries, suffix trees and suffix arrays

Inserting every suffix of a text into a trie gives a structure in which "does pattern P occur in the text?" is just "is P a prefix of some suffix?" — an O(|P|) walk. A naive suffix trie has O(n²) nodes; a compressed version, the suffix tree, has O(n) nodes and can be built in O(n) with Ukkonen's algorithm, but it is intricate and memory-hungry. The suffix array — the starting positions of all suffixes, sorted — gives most of the same power with far less memory, using binary search for pattern queries, and is the practical choice in bioinformatics and full-text indexes. In interviews, knowing that these exist and what they answer is usually enough; the related rolling-hash and KMP techniques are covered in al26.

Tries for numbers and ranges

Binary tries generalise beyond maximum XOR. With per-node counts they answer "how many stored numbers x satisfy x XOR q < k?" by walking q's bits and, at each level where k has a 1, adding the count of the subtree that keeps the XOR bit 0 (all of those are smaller) before following the branch that matches k's bit. They also act as a sorted set of integers: the minimum is the leftmost path, the k-th smallest is found with subtree counts, and the structure supports insert and delete in O(B). In competitive programming these "XOR tries" are a standard tool; in interviews, the maximum-XOR problem is the usual entry point, and follow-ups probe whether you can add counts to answer counting questions.

Ternary search trees and automata

A ternary search tree stores one character per node with three children — less than, equal, greater — combining a trie's prefix walk with a BST's compact nodes. It uses much less memory than a 26-way trie and supports prefix queries and near-neighbour searches. At the other extreme, a minimal acyclic automaton (DAWG) shares common suffixes as well as prefixes, and finite-state transducers attach outputs to edges; Apache Lucene stores its term dictionary as an FST, compressing millions of terms into a structure small enough to keep in memory while still supporting prefix and fuzzy queries.

In the interview room

Trie questions are mostly about clean implementation and knowing when the trie earns its place. Common bugs: confusing search and startsWith (forgetting the end flag, or checking it in startsWith); creating nodes during a search (using setdefault in a lookup, which silently grows the trie); recording the same word several times in Word Search II; forgetting to restore grid cells; and mutating a dict while iterating over it when pruning. Test with a word that is a prefix of another ("car" and "cart"), an empty string if allowed, and a search that falls off midway.

Expect the trade-off questions: "why not a hash set?" (no prefix queries, no pruning), "how much memory does this use?" (one node per distinct prefix; mention compression), and "how would you scale autocomplete?" (cached top-k per node, compression, sharding, or a sorted array). A senior-sounding answer names the alternative and picks based on whether the word set is static and how queries look.

For Word Search II specifically, interviewers often look for the two pruning improvements — clearing found words and deleting exhausted trie branches — because without them the solution may time out on large inputs with many overlapping words. Mentioning that you would also skip words whose letters do not all appear on the board is a nice extra.

On online assessments, trie problems frequently arrive as "count strings in a list that have a given prefix" for many queries, or "for each word, find the shortest unique prefix". Both are a single insertion pass with per-node counts followed by walks: the shortest unique prefix of a word ends at the first node on its path whose count is 1.

When choosing a representation for children, say why: a dict is flexible and compact for sparse alphabets; a fixed array of 26 is faster to index and natural in Java or C++ but wastes memory on sparse nodes; a sorted list of (char, child) pairs saves memory at the cost of a small linear or binary search per step. The choice rarely changes the asymptotic answer, but naming it shows the interviewer you think about constants and memory.

In real systems

Prefix trees and their relatives are infrastructure. Internet routers forward every packet by longest-prefix matching on the destination address against routing tables of hundreds of thousands of prefixes; implementations use compressed binary tries (the Linux kernel's IPv4 table is an LC-trie, a level-compressed variant) or hardware TCAMs. Search engines and databases store term dictionaries as tries or finite-state transducers — Lucene's FST is the reason Elasticsearch can hold large term dictionaries in memory and answer prefix and fuzzy queries quickly. Autocomplete services cache ranked completions per prefix, often precomputed offline. Spell checkers and keyboard prediction walk tries of words weighted by frequency. Web frameworks route URLs with radix trees of path segments. And in blockchains, Ethereum's state is a Merkle Patricia trie, combining a compressed trie with hashes so that any account's state can be proven with a short path of hashes.

Design and estimate

"You must support two operations on a growing set of up to 10⁶ product names (average 20 characters): add(name) and countPrefix(p), which returns how many names start with p. Queries vastly outnumber adds." Propose a design and estimate memory, and give an alternative if memory were capped at 200 MB in Python.

Answer

Design: a trie with a counter on each node, incremented along the path on every add (O(L) per add), so countPrefix walks p and returns the counter at its node (O(|p|), or 0 if the walk falls off). Memory: worst case one node per character, 2 × 10⁷ nodes; real product names share prefixes, so perhaps several million nodes. At roughly 150–250 bytes per Python node (object + dict + int), that is likely 1–4 GB — too much. Alternatives under 200 MB: (1) keep names in a sorted list (or sortedcontainers.SortedList for dynamic inserts in about O(log n)) and answer countPrefix with two binary searches: bisect_left(names, p) and bisect_left(names, p + "￿"); the difference is the count — O(log n) per query, memory roughly the strings themselves (around 20 bytes plus ~50 bytes of object overhead each, about 70 MB for 10⁶ names, plus the list). (2) A compressed trie storing edge labels as string slices reduces node count to at most 2n. (3) Batch adds and rebuild a sorted array periodically if writes are rare. State the choice: with queries dominating and memory capped, the sorted structure is the pragmatic answer; the trie is the textbook one.
