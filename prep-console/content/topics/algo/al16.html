A social network wants to suggest "people you may know": friends of your friends who are not yet your friends. A navigation app needs the fewest stops between two stations. A build system must know whether changing one file affects another. A package manager must decide whether a set of dependencies contains a loop. A puzzle asks for the fewest one-letter changes that turn "hit" into "cog". These look like different problems, but each is about things (people, stations, files, packages, words) and connections between them. Each is a graph problem.

Trees (al14) were the special case where everything hangs from one root and there are no loops. General graphs allow anything: connections in both directions or one, many paths between the same two places, cycles, separate islands that are not connected at all. That freedom is exactly why so many real problems are graphs — and why the two basic ways to explore a graph, depth-first search and breadth-first search, are among the most important algorithms you will learn.

The good news is that most graph interview questions reduce to a short list of moves: build an adjacency list from the input; run DFS or BFS with a visited set; and read the answer off the traversal — the number of times you had to start a new search (components), the BFS level at which you reached the target (shortest path), whether you ran into a vertex you were still exploring (a cycle), or a colouring that never clashed (bipartite).

This lesson builds those moves carefully: vocabulary and representations; DFS, recursive and iterative; BFS and why it finds shortest paths; components, cloning, bipartite checks and cycle detection; weighted queries like Evaluate Division; implicit graphs where the vertices are puzzle states; and, at the senior end, bidirectional BFS, Euler paths and bridges. Grids, which are the most common graphs in interviews, get their own lesson next (al17).

The mental model: a map of towns and roads

Picture a map with towns (vertices) and roads (edges). Some roads are two-way (an undirected graph); some are one-way streets (a directed graph). Some roads have a length or toll written on them (a weighted graph); in an unweighted graph every road counts the same. The map may be in several pieces with no roads between them — each piece is a connected component. And roads may form loops (cycles), so a careless traveller can drive in circles forever.

There are two natural ways to explore such a map from your home town. The first is like an explorer with a ball of string: take any road, keep going to new towns as long as you can, and when you hit a town with no unexplored roads, follow the string back to the last town that still has one. That is DFS. The second is like dropping a stone in a pond: first visit every town one road away, then every town two roads away, then three, in expanding rings. That is BFS. Both visit every reachable town once; they differ in the order, and the order is what makes each one good at different questions.

Representing the map

Interview inputs usually arrive as an edge list — pairs like [[0, 1], [1, 2], …]. Before exploring, convert it to an adjacency list: for each vertex, the list of its neighbours.

from collections import defaultdict
graph = defaultdict(list)
for u, v in edges:
    graph[u].append(v)
    graph[v].append(u)          # omit this line for a directed graph

An adjacency list uses O(V + E) memory and lets you loop over a vertex's neighbours in time proportional to how many it has. The alternative, an adjacency matrix (a V×V table of booleans or weights), answers "is there an edge from u to v?" in O(1) but costs O(V²) memory and O(V) to list neighbours — good for dense graphs with a few thousand vertices, bad for sparse ones with a million.

Where the map analogy breaks: real maps are drawn on a plane, but graph vertices have no positions, and many interview graphs are never drawn at all. In Word Ladder the vertices are words and the edges are "differ by one letter"; in a sliding puzzle the vertices are board configurations. These are implicit graphs — you generate neighbours on demand from the rules instead of storing edges. Recognising that a puzzle is a graph search over states is often the whole insight.

The cost of both traversals is the same and worth stating precisely: each vertex is visited once and each edge is examined once (twice for undirected edges, once from each end), so O(V + E) time, plus O(V) for the visited set. When the interviewer asks for complexity, use both variables, not "O(n)".

DFS: recursive and iterative

def dfs(graph, start):
    seen = {start}
    def go(u):
        for v in graph[u]:
            if v not in seen:
                seen.add(v)
                go(v)
    go(start)
    return seen

def dfs_iter(graph, start):
    seen, stack = {start}, [start]
    while stack:
        u = stack.pop()
        for v in graph[u]:
            if v not in seen:
                seen.add(v)
                stack.append(v)
    return seen

Both return the set of vertices reachable from start. The recursive version is shortest and is what you use when you need to do work after exploring a vertex's descendants (cycle detection, topological order, bridges). The iterative version avoids Python's recursion limit — a path-shaped graph with 10⁵ vertices would crash the recursive one — but visits vertices in a slightly different order (it explores the last-pushed neighbour first). For pure reachability the order does not matter.

The seen set is what keeps the traversal finite on graphs with cycles: without it, A → B → A → B … would never end. In trees you could skip it because there are no cycles; in graphs you never can.

Connected components

To count components in an undirected graph, loop over every vertex; whenever you find one not yet seen, you have found a new component — count it and run a traversal from it to mark the whole component.

def count_components(n, edges):
    graph = defaultdict(list)
    for u, v in edges:
        graph[u].append(v); graph[v].append(u)
    seen, count = set(), 0
    for s in range(n):
        if s in seen: continue
        count += 1
        seen.add(s); stack = [s]
        while stack:
            u = stack.pop()
            for v in graph[u]:
                if v not in seen:
                    seen.add(v); stack.append(v)
    return count

Looping over all vertices, not just those in the edge list, matters: an isolated vertex with no edges is its own component. "Number of Provinces" (an adjacency matrix input) and "Graph Valid Tree" (n − 1 edges and exactly one component) are variants. Union-find (al19) solves the same problem in a different way and is better when edges arrive over time.

BFS and shortest paths in unweighted graphs

from collections import deque
def bfs_dist(graph, src):
    dist = {src: 0}
    q = deque([src])
    while q:
        u = q.popleft()
        for v in graph[u]:
            if v not in dist:              # first discovery = shortest
                dist[v] = dist[u] + 1
                q.append(v)
    return dist

Why the first discovery is along a shortest path: BFS processes vertices in non-decreasing order of distance. All distance-0 vertices (just the source) are processed first, discovering all distance-1 vertices; those are all processed before any distance-2 vertex, and so on. A vertex at distance k cannot be discovered before every vertex at distance k − 1 has been processed, so when it is first discovered, it is from a vertex at distance k − 1 — a shortest route. The distance dictionary doubles as the visited set.

Two habits make BFS correct and fast. Mark when you push, not when you pop: otherwise a vertex with many already-discovered neighbours is pushed many times. And to reconstruct the path, store a parent pointer when you discover each vertex (parent[v] = u) and walk back from the target.

Cloning a graph

"Given a node of a connected undirected graph, return a deep copy." The copy must have the same structure, including cycles. Traverse the original and keep a dict from each original node to its copy; the dict is also the visited set.

def clone_graph(node):
    if not node: return None
    copies = {node: Node(node.val)}
    q = deque([node])
    while q:
        u = q.popleft()
        for v in u.neighbors:
            if v not in copies:
                copies[v] = Node(v.val)
                q.append(v)
            copies[u].neighbors.append(copies[v])
    return copies[node]

Every edge is copied exactly when it is examined from u's side, so each copy ends up with the same neighbours as its original. The same "map from old to new" idea solves Copy List with Random Pointer (al9).

Two-colouring: is the graph bipartite?

A graph is bipartite if its vertices can be split into two groups with every edge going between the groups — like a graph of people and the projects they work on. Try to colour it with two colours so no edge joins two vertices of the same colour: give the start vertex colour 0, its neighbours colour 1, their neighbours colour 0, and so on. If you ever find an edge between two vertices of the same colour, it is impossible.

def is_bipartite(graph, n):
    color = {}
    for s in range(n):
        if s in color: continue
        color[s] = 0; q = deque([s])
        while q:
            u = q.popleft()
            for v in graph[u]:
                if v not in color:
                    color[v] = 1 - color[u]; q.append(v)
                elif color[v] == color[u]:
                    return False
    return True

A graph is bipartite exactly when it has no cycle of odd length — a triangle, for instance, can never be two-coloured. "Possible Bipartition" (split people who dislike each other into two groups) is this algorithm with a story.

Cycle detection

Undirected: during DFS, every edge leads either to an unvisited vertex or back to a visited one. Reaching a visited vertex that is not the one you just came from (your parent) means there is a second route to it — a cycle.

Directed: "visited" is not enough. In the graph A → B, A → C, C → B, DFS from A visits B, finishes it, then visits C and sees B again — but there is no cycle. What matters is whether you reach a vertex that is still on the current path. Use three states: 0 = unvisited, 1 = in progress (on the recursion stack), 2 = done.

def has_cycle(graph, n):
    state = [0] * n
    def dfs(u):
        state[u] = 1
        for v in graph[u]:
            if state[v] == 1: return True          # back edge to the current path
            if state[v] == 0 and dfs(v): return True
        state[u] = 2
        return False
    return any(state[u] == 0 and dfs(u) for u in range(n))

This three-colour DFS is also the basis of DFS-based topological sorting (al18), where the order in which vertices become "done" gives a reverse topological order.

Weighted queries: Evaluate Division

Given equations like a/b = 2.0 and b/c = 3.0, answer queries like a/c. Each variable is a vertex; a/b = 2 gives an edge a → b with weight 2 and b → a with weight 1/2. The value of x/y is the product of weights along any path from x to y — any path gives the same answer if the equations are consistent. Answer each query with a DFS from x, carrying the running product, returning it when y is reached; if y is unreachable or either variable is unknown, the answer is −1. For a/c: a → b (2) → c (3) gives 6. This shows that graph edges can carry values that combine along paths, which is the stepping stone to shortest paths with weights (al20).

Implicit graphs: Word Ladder

"Transform 'hit' into 'cog' by changing one letter at a time, every intermediate word in the dictionary; return the length of the shortest sequence." The vertices are words, edges join words differing by one letter, and the question is a shortest path in an unweighted graph: BFS. The engineering question is how to find a word's neighbours quickly. Comparing it with all N dictionary words costs O(N·L) per word. Instead, index the dictionary by wildcard patterns: "hot" belongs to "*ot", "h*t" and "ho*". Two words are neighbours exactly when they share a pattern, so a word's neighbours come from L lookups.

def ladder_length(begin, end, words):
    words = set(words)
    if end not in words: return 0
    patterns = defaultdict(list)
    for w in words:
        for i in range(len(w)):
            patterns[w[:i] + "*" + w[i+1:]].append(w)
    q, seen = deque([(begin, 1)]), {begin}
    while q:
        w, d = q.popleft()
        for i in range(len(w)):
            for nxt in patterns[w[:i] + "*" + w[i+1:]]:
                if nxt == end: return d + 1
                if nxt not in seen:
                    seen.add(nxt); q.append((nxt, d + 1))
    return 0

The total cost is about O(N·L²) — N words, L patterns each, and building each pattern string costs L. Puzzles like "Open the Lock" (turn wheels to reach a combination, avoiding dead ends) and "Minimum Genetic Mutation" are the same shape: states as vertices, legal moves as edges, BFS for the fewest moves.

Directed reachability: who can reach whom

In directed graphs, "can u reach v?" is not symmetric, and a few standard tricks help. To find every vertex that can reach a target t (for example, every course that eventually requires a given course, or every state from which a game can be won), traverse the reversed graph from t: build an adjacency list with every edge flipped and run BFS or DFS from t. To find vertices that can both reach and be reached from each other — strongly connected components — run Kosaraju's algorithm (DFS to get a finishing order, then DFS on the reversed graph in reverse finishing order) or Tarjan's single-pass variant; both are O(V + E). "Find Eventual Safe States" (vertices from which every path ends at a terminal vertex) is a nice interview example: reverse the graph and peel off terminal vertices with a Kahn-style queue, or run the three-colour DFS and mark vertices that never reach an in-progress one.

Multi-source and level-limited traversals

Two small variations come up constantly. Multi-source BFS starts with several vertices in the queue at distance 0 — for example, "distance from each house to its nearest hospital" starts from all hospitals at once. One BFS then gives every vertex its distance to the nearest source in O(V + E), instead of one BFS per source. Depth-limited traversal stops expanding at a given level: "friends within two hops" is BFS that does not enqueue anything beyond distance 2. Both are covered on grids in the next lesson, where they are most common.

Recognising the pattern

Think "graph" whenever the problem has entities and pairwise relationships (friends, prerequisites, flights, equations, adjacent cells, one-move-apart states). Then choose: BFS for fewest steps or level-by-level questions in unweighted graphs; DFS for reachability, components, cycles, and anything needing post-order work; weighted shortest paths need al20; ordering by dependencies needs al18; connectivity under incremental edges needs al19.

Edge classification and what DFS reveals

During a DFS of a directed graph, every edge u → v falls into one of four classes, determined by v's state when the edge is examined. A tree edge leads to an unvisited vertex (it becomes part of the DFS tree). A back edge leads to an in-progress ancestor — these exist exactly when the graph has a cycle. A forward edge leads to an already-finished descendant, and a cross edge leads to a finished vertex in another branch. In undirected graphs only tree and back edges occur. This classification is the theory behind cycle detection, topological sorting (a DAG has no back edges, so reverse finishing order is a valid topological order), and strongly connected components (Tarjan's and Kosaraju's algorithms).

Bridges and articulation points

A bridge is an edge whose removal disconnects the graph; an articulation point is a vertex whose removal does. Tarjan's algorithm finds both with one DFS. Each vertex gets a discovery time disc[u] and a low-link value low[u] = the smallest discovery time reachable from u's DFS subtree using tree edges downward plus at most one back edge. For a tree edge u → v: if low[v] > disc[u], nothing in v's subtree can reach u or above except through u–v, so it is a bridge; if low[v] ≥ disc[u] (and u is not the root), u is an articulation point. The root is an articulation point when it has two or more DFS children. Networks use this to find single points of failure — exactly the "Critical Connections" problem.

Euler paths and Hierholzer's algorithm

An Euler path uses every edge exactly once. In an undirected graph it exists when the graph is connected (ignoring isolated vertices) and has zero or two vertices of odd degree; in a directed graph, when at most one vertex has out-degree − in-degree = 1 (the start), at most one has −1 (the end), and all others are balanced. Hierholzer's algorithm builds it in O(E): walk from the start, consuming edges, until stuck; the stuck vertex is the end of a sub-tour; back up, and splice in further tours from vertices that still have unused edges. The elegant implementation appends each vertex to the route only when it has no unused edges left, then reverses the route. Reconstruct Itinerary is exactly this with a lexicographic tie-break (always take the smallest remaining destination). Euler paths also show up in DNA assembly (de Bruijn graphs) and in "crack the safe" (a de Bruijn sequence).

Bidirectional BFS

If each state has b neighbours and the target is d steps away, BFS explores about b^d states. Searching from both ends and stopping when the frontiers meet explores about 2·b^(d/2) — for b = 10 and d = 6, two million versus twenty thousand. Implement it by keeping two visited dicts and always expanding the smaller frontier one full level; when a newly discovered state is in the other side's dict, the shortest path length is the sum of the two depths. It needs the target in advance and, for directed graphs, the ability to follow edges backwards. Word Ladder benefits dramatically; it is a common follow-up.

Iterative DFS that matches the recursive order

The simple stack-based DFS marks a vertex when it is pushed, which visits vertices in a different order from recursion and, more importantly, does not give you a "finished" moment for post-order work. When you need the recursive semantics without recursion (cycle detection, topological order, Tarjan), keep a stack of (vertex, iterator over neighbours) frames: look at the top frame, advance its iterator; if there is an unvisited neighbour, mark it in progress and push its frame; if the iterator is exhausted, the vertex is finished — pop it and do the post-order work. This reproduces the recursive behaviour exactly and handles graphs of any depth.

Graph size and memory in practice

Adjacency lists in Python cost a list object per vertex plus a reference per edge end, so a graph with 10⁶ vertices and 10⁷ edges needs on the order of a gigabyte — feasible but not free. Large graph systems use compressed sparse row (CSR) format: one array of all neighbour ids, sorted by source vertex, plus an offsets array saying where each vertex's neighbours start; this is how SciPy's sparse matrices and many graph libraries store graphs, and it makes BFS cache-friendly. Knowing that the dict-of-lists is an interview convenience, and CSR is the production layout, is useful in system-design follow-ups about social graphs or road networks.

In the interview room

Graph questions usually begin with modelling, so say out loud what the vertices and edges are and whether the graph is directed or weighted: "courses are vertices, a prerequisite is a directed edge from prerequisite to course". Then name the traversal and why. Interviewers reward that framing because it is the step most candidates skip.

The common bugs are: forgetting the visited set (infinite loops on cycles); marking visited on pop instead of push (duplicate work, time-outs on large inputs); building an undirected graph with edges in one direction only; iterating only over vertices that appear in edges, missing isolated ones; using two states instead of three for directed cycle detection; and recursion depth errors on long paths in Python. Test with a disconnected graph, a single vertex, a self-loop if allowed, and a graph with a cycle.

For complexity, say O(V + E) and explain: each vertex is enqueued once, each edge examined once (twice for undirected). For implicit graphs, estimate the number of states and the cost of generating neighbours — Word Ladder's O(N·L²) is a good example to rehearse. Expect follow-ups such as "now edges have weights" (Dijkstra, al20), "now edges arrive one at a time" (union-find, al19), and "now the graph has a billion edges" (distributed BFS, external memory, or sampling).

On online assessments, graph problems are often disguised as grids, as "friend circles", or as dependency lists. Building the adjacency list correctly from the given format — 0- or 1-based vertex ids, directed or not, duplicates allowed — is where many hidden tests are failed, so read the input description twice.

A final interview habit: after writing the traversal, say what would change for a very large graph. "If the graph did not fit in memory, I would store adjacency on disk in CSR form and run BFS level by level, or use a distributed framework" is the kind of one-line extension that shows you know where the interview version stops.

In real systems

Graph traversal runs constantly in production. Garbage collectors decide which objects are still in use by traversing references from root objects (stack variables, globals) and freeing everything unreachable — the "mark" phase of mark-and-sweep is a graph traversal, and CPython's gc module runs a cycle detector over container objects to collect reference cycles that reference counting cannot. Web crawlers explore the link graph breadth-first from seed pages, using a frontier queue and a visited set of URLs, at the scale of billions of pages. Social networks compute "people you may know" from two-hop neighbourhoods and degrees of separation with BFS. Build tools (Bazel, Make) and package managers walk dependency graphs to decide what to rebuild or install and to detect cycles. Network operators compute reachability and single points of failure (bridges) in their topologies. And knowledge graphs and graph databases (Neo4j, Amazon Neptune) answer queries by traversing edges, often BFS with depth limits.

    dist, q = {s: 0}, deque([s])

def brute_dist(g, s, n):                     # relax edges n times (Bellman-Ford style)
    d = {s: 0}
    for _ in range(n):
        for u in list(d):
            for v in g[u]:
                if v not in d or d[u] + 1 < d[v]: d[v] = d[u] + 1
    return d

def has_cycle(g, n):
    st = [0] * n
    def dfs(u):
        st[u] = 1
        for v in g[u]:
            if st[v] == 1 or (st[v] == 0 and dfs(v)): return True
        st[u] = 2; return False
    return any(st[u] == 0 and dfs(u) for u in range(n))

def is_dag_brute(g, n):                      # DAG iff some ordering puts every edge forward
    return any(all(pos[u] < pos[v] for u in range(n) for v in g[u])
               for perm in permutations(range(n)) for pos in [{x: i for i, x in enumerate(perm)}])

Model it, then pick the traversal

"An airline has n airports and a list of direct flights (u, v), each usable in both directions. A traveller at airport s wants to know (a) every airport reachable, (b) the minimum number of flights to airport t, and (c) whether some airport's closure (removing all its flights) would split the reachable network. Constraints: n ≤ 10⁵, flights ≤ 2 × 10⁵." Describe each solution and its cost.

Answer

Model: airports are vertices, flights are undirected unweighted edges; build an adjacency list in O(V + E). (a) Reachability: DFS or BFS from s with a visited set, O(V + E); use the iterative version to avoid recursion limits with 10⁵ vertices. (b) Minimum flights: BFS from s, recording distances (and parents if the route is needed); the distance of t when first discovered is the answer, or "unreachable" if never discovered. O(V + E). Bidirectional BFS from s and t speeds it up in practice. (c) This asks for articulation points within s's component: one DFS with Tarjan's discovery and low-link values, O(V + E); a vertex u (not the root) is an articulation point if some DFS child v has low[v] ≥ disc[u], and the root is one if it has at least two DFS children. Write the DFS iteratively (an explicit stack of (vertex, neighbour index) frames) because recursion depth can reach 10⁵. If the question were about a single flight being critical, look for bridges instead (low[v] > disc[u]).
