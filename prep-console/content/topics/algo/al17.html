A satellite image is a grid of pixels labelled land or water; how many islands are there? A warehouse floor plan is a grid with shelves as obstacles; what is the shortest route for a robot from the dock to bin 42? A fire spreads to adjacent cells every minute; when will it reach the exit? A paint program's bucket tool recolours every pixel connected to the one you clicked. Each of these is a graph problem on a grid, where the cells are the vertices and adjacency is the edges.

Grid problems are the single most common kind of graph problem in interviews — candidate reports from Google and other large companies repeatedly mention islands, spreading processes, mazes and shortest paths on boards. They are popular because they test graph thinking without the overhead of parsing a graph, and because they come in a natural ladder of difficulty: counting islands is a warm-up; "nearest exit for every cell" needs multi-source BFS; "shortest path if you may break up to k walls" needs BFS over an expanded state; "fewest walls to break" needs a weighted search that turns out to be simpler than Dijkstra.

This lesson works up that ladder. It starts with the mechanics that every grid solution shares — direction arrays, bounds checks, and how to mark cells — then covers flood fill and islands, the border-first trick, BFS shortest paths, multi-source BFS, BFS with state, 0-1 BFS, and finally matrix simulation problems (rotate, spiral, set zeroes, game of life) that are about index arithmetic rather than search. By the end, a new grid problem should look like a choice among a handful of templates.

The mental model: a chessboard where each square knows its neighbours

Think of a chessboard. Every square is a place you can stand; from a square you can step to the squares directly above, below, left and right (a rook's single step), or also diagonally (a king's step). That is a graph, but nobody would write down its edge list — the edges follow from the geometry. A grid problem gives you the board (a list of lists) and the rules for which squares you may stand on; the graph is implicit.

Every grid solution has the same three ingredients. A direction array lists the steps: DIRS = ((1, 0), (-1, 0), (0, 1), (0, -1)) for 4-connectivity, plus the four diagonals for 8-connectivity. A bounds check rejects steps that fall off the board: 0 <= nr < R and 0 <= nc < C. And a visited marker stops you from processing a cell twice — either a set of (r, c) pairs, a boolean matrix, or overwriting the cell itself (turning land into water as you visit it) when modifying the input is allowed.

Which visited marker to use is a small but real decision. Overwriting cells is the fastest and uses no extra memory, but it destroys the input and can confuse later logic that reads the original values (for example, if a later step needs to know which cells were land). A seen set of tuples is clean and non-destructive but slower for millions of cells. A boolean matrix of the same shape is a good middle ground. Say which you choose and why — interviewers notice when a candidate silently mutates the input.

With those three ingredients, a grid is a graph with V = R·C vertices and at most 4·R·C edges, so a full DFS or BFS costs O(R·C). The art is in choosing which traversal, where it starts, and what counts as a state.

Where the chessboard analogy breaks: on a chessboard every move is the same, but in grid problems moves can have different costs (stepping onto an obstacle costs a removal), and your position alone may not capture everything that matters (how many removals you have left, which keys you are carrying). When that happens, the true vertices of the search are not cells but (cell, extra information) pairs — the state space is bigger than the board. Recognising that is the main step up from medium to hard grid problems.

Finally, some grid problems are not searches at all. Rotating an image, printing a matrix in spiral order, or updating Conway's Game of Life in place are simulation problems: the difficulty is index arithmetic and doing updates without destroying information you still need. They are covered at the end.

The grid template

DIRS = ((1, 0), (-1, 0), (0, 1), (0, -1))

def neighbours(r, c, R, C):
    for dr, dc in DIRS:
        nr, nc = r + dr, c + dc
        if 0 <= nr < R and 0 <= nc < C:
            yield nr, nc

Get two conventions right once and keep them: rows first, columns second (grid[r][c], R = number of rows = len(grid), C = len(grid[0])), and the bounds check before indexing. Swapping r and c, or R and C, is the most common grid bug and only shows up on non-square grids — always test one.

Flood fill and counting islands

"Count the islands": scan every cell; each time you meet land you have not visited, you have found a new island — count it and flood-fill all of it so you do not count it again.

from collections import deque
def num_islands(grid):
    R, C = len(grid), len(grid[0])
    count = 0
    for r in range(R):
        for c in range(C):
            if grid[r][c] != "1": continue
            count += 1
            grid[r][c] = "0"                     # mark when enqueued
            q = deque([(r, c)])
            while q:
                cr, cc = q.popleft()
                for nr, nc in neighbours(cr, cc, R, C):
                    if grid[nr][nc] == "1":
                        grid[nr][nc] = "0"
                        q.append((nr, nc))
    return count

Overwriting land with water is a free visited marker, but it destroys the input; if the caller needs the grid intact, use a seen set or copy the grid first, and say which you are doing. The same skeleton gives Max Area of Island (count cells per flood and keep the maximum) and Flood Fill (recolour instead of counting — with the guard that if the new colour equals the old one, do nothing, or the fill will loop forever since recoloured cells still "match").

Using BFS rather than recursive DFS here is deliberate: a fully-land 1000×1000 grid is one island of a million cells, and a recursive flood would exceed Python's recursion limit.

Border-first floods

"Surrounded Regions": flip to 'X' every region of 'O's that is completely surrounded by 'X's — that is, not connected to the border. Deciding for each region whether it touches the border is awkward. Turn it around: every 'O' connected to a border 'O' is safe; everything else is captured. So flood from all border 'O's first, marking them safe, then flip every unmarked 'O'.

"Number of Enclaves" (land cells from which you cannot walk off the grid) is the same: sink all land connected to the border, then count what remains. "Pacific Atlantic Water Flow" uses the same reversal for flow: rather than asking for each cell "can water flow from here to both oceans?" (one search per cell), run one search from all Pacific border cells and one from all Atlantic border cells, moving uphill (to neighbours at least as high, since water flows downhill), and intersect the two reached sets. Searching from the targets backwards instead of from every source forwards is a powerful general trick.

Shortest paths: BFS on the grid

In an unweighted grid, BFS from the start gives the fewest steps to every reachable cell (al16). "Shortest Path in Binary Matrix" asks for the shortest 8-directional path of 0-cells from the top-left to the bottom-right corner:

def shortest_path_binary_matrix(g):
    n = len(g)
    if g[0][0] or g[n-1][n-1]: return -1
    D8 = [(dr, dc) for dr in (-1, 0, 1) for dc in (-1, 0, 1) if dr or dc]
    q, g[0][0] = deque([(0, 0, 1)]), 1          # mark start visited
    while q:
        r, c, d = q.popleft()
        if (r, c) == (n - 1, n - 1): return d
        for dr, dc in D8:
            nr, nc = r + dr, c + dc
            if 0 <= nr < n and 0 <= nc < n and g[nr][nc] == 0:
                g[nr][nc] = 1
                q.append((nr, nc, d + 1))
    return -1

Carrying the distance in the queue tuple is one style; processing level by level with for _ in range(len(q)) and a level counter is the other. Either way, check blocked start or end cells first.

Multi-source BFS: nearest source and simultaneous spreading

"For every cell, the distance to the nearest 0" (01 Matrix), "fill each empty room with the distance to its nearest gate" (Walls and Gates), "how many minutes until all oranges rot" (Rotting Oranges): each involves many sources. Running one BFS per source costs O(sources × R·C). Instead, put all sources in the queue at distance 0 and run one BFS. The rings grow outward from every source simultaneously, and each cell is first reached from its nearest source — exactly the figure above.

def oranges_rotting(grid):
    R, C = len(grid), len(grid[0])
    q, fresh = deque(), 0
    for r in range(R):
        for c in range(C):
            if grid[r][c] == 2: q.append((r, c))
            elif grid[r][c] == 1: fresh += 1
    minutes = 0
    while q and fresh:
        for _ in range(len(q)):                  # one minute = one level
            r, c = q.popleft()
            for nr, nc in neighbours(r, c, R, C):
                if grid[nr][nc] == 1:
                    grid[nr][nc] = 2; fresh -= 1
                    q.append((nr, nc))
        minutes += 1
    return -1 if fresh else minutes

Trace a 3×3 grid [[2, 1, 1], [1, 1, 0], [0, 1, 1]]: minute 1 rots (0, 1) and (1, 0); minute 2 rots (0, 2) and (1, 1); minute 3 rots (2, 1); minute 4 rots (2, 2). Answer 4. The loop condition while q and fresh stops counting minutes once nothing is fresh, and the final check catches oranges that can never be reached.

BFS with extra state

"Shortest path from top-left to bottom-right if you may walk through up to k obstacles." Position alone is no longer enough to describe where you are in the search: standing on a cell with 3 removals left is a better situation than standing there with 0 left. So the vertices of the search are states (r, c, remaining), and BFS runs over states.

def shortest_path_with_removals(grid, k):
    R, C = len(grid), len(grid[0])
    if k >= R + C - 2: return R + C - 2          # can walk straight through
    start = (0, 0, k)
    q, seen = deque([(0, 0, k, 0)]), {start}
    while q:
        r, c, rem, d = q.popleft()
        if (r, c) == (R - 1, C - 1): return d
        for nr, nc in neighbours(r, c, R, C):
            nrem = rem - grid[nr][nc]            # obstacle costs one removal
            if nrem >= 0 and (nr, nc, nrem) not in seen:
                seen.add((nr, nc, nrem))
                q.append((nr, nc, nrem, d + 1))
    return -1

The state space has R·C·(k + 1) states, so this is O(R·C·k). An optimisation keeps, per cell, the most removals left with which it has been reached, and skips a state unless it improves on that — a cell reached earlier (fewer steps) with more removals dominates. The early exit when k ≥ R + C − 2 handles the case where the shortest Manhattan route is always available. The same "BFS over (cell, extra)" idea solves mazes with keys and doors (state includes a bitmask of keys collected, al24), "shortest path visiting all nodes" (state includes a visited mask), and problems where direction or momentum matters.

0-1 BFS: moves that cost 0 or 1

"Minimum number of obstacles to remove to get from the top-left to the bottom-right." Now the question is not the fewest steps but the fewest removals: stepping into an empty cell costs 0, into an obstacle costs 1. That is a weighted shortest path, which normally needs Dijkstra (al20). But with weights of only 0 and 1, a deque does the job: when you relax an edge of cost 0, push the neighbour to the front (it has the same cost as the current cell); for cost 1, push it to the back. The deque then always holds cells in non-decreasing order of cost — at most two distinct values — so cells are processed in cost order, as Dijkstra would, without a heap.

def min_obstacles(grid):
    R, C = len(grid), len(grid[0])
    INF = float("inf")
    dist = [[INF] * C for _ in range(R)]
    dist[0][0] = 0
    dq = deque([(0, 0)])
    while dq:
        r, c = dq.popleft()
        for nr, nc in neighbours(r, c, R, C):
            w = grid[nr][nc]
            if dist[r][c] + w < dist[nr][nc]:
                dist[nr][nc] = dist[r][c] + w
                if w == 0: dq.appendleft((nr, nc))
                else: dq.append((nr, nc))
    return dist[R - 1][C - 1]

Each cell can be pushed a few times (when its distance improves), but the total work is O(R·C). Recognising "costs are only 0 and 1" saves a heap and a log factor; problems like "minimum cost to make at least one valid path" (following the arrow is free, changing it costs 1) are the same algorithm.

Labelling islands: Making A Large Island

"You may change at most one 0 to 1; what is the largest island possible?" Re-flooding the grid for every candidate 0 is O((R·C)²). Instead, flood once and give each island an id (2, 3, 4, … written into the grid) and record its size in a dict. Then, for each 0, look at its four neighbours, collect the distinct island ids (two neighbours may belong to the same island — use a set), and the island formed by flipping this 0 has size 1 + the sum of those islands' sizes. Take the maximum, and remember the case with no 0 at all (the whole grid is one island). O(R·C). This "label components once, then answer local questions from the labels" approach is reusable.

Matrix simulation: index arithmetic, in place

A separate family of grid questions needs no search. Rotate Image (90° clockwise in place): transpose (swap a[i][j] with a[j][i] above the diagonal), then reverse each row. Spiral Matrix: keep four boundaries (top, bottom, left, right); walk right along top, down along right, left along bottom, up along left, shrinking each boundary after its side is done, and stop when they cross — checking after each side, because a single remaining row or column must not be walked twice. Set Matrix Zeroes in O(1) extra space: use the first row and first column as marker storage for which columns and rows must be zeroed, with two extra booleans remembering whether the first row and column themselves contained a zero. Game of Life in place: every cell's next state depends on its neighbours' current states, so encode transitions with extra values (for example 2 = alive→dead, 3 = dead→alive), compute all of them using "value is 1 or 2" to mean currently alive, then make a second pass to finalise. Diagonal Traverse: cells on one anti-diagonal share r + c, so iterate s from 0 to R + C − 2 and reverse every other diagonal. The common thread is preserving information you still need while overwriting — write the plan as "what does each cell's value mean during the pass?" before coding.

Recognising the pattern

On a grid, ask in order: Is it counting or labelling connected regions (flood fill)? Does the border matter (flood from the border)? Is it fewest steps (BFS) from one source or the nearest of many (multi-source BFS)? Does a move consume something (BFS over states)? Do moves have costs 0/1 (0-1 BFS) or arbitrary costs (Dijkstra, al20)? Can moves only go right/down (then it is dynamic programming, al22, not search)? Or is it pure index manipulation (simulation)?

When the grid problem is really dynamic programming

If movement is restricted to right and down (or any direction that never revisits a cell), the grid becomes a directed acyclic graph, and the best path to a cell depends only on the best paths to its predecessors. That is dynamic programming, not search: "Unique Paths", "Minimum Path Sum" and "Maximal Square" fill a table row by row in O(R·C) with no queue (al22). The tell is the movement rule. With four-directional movement, paths can wander back, the graph has cycles, and you need BFS or Dijkstra. "Longest Increasing Path in a Matrix" is a hybrid: moves go in all four directions, but only to strictly larger values, which makes the graph acyclic — so DFS with memoisation (al23) works.

A* search: BFS with a sense of direction

BFS and Dijkstra expand outward in all directions equally, which wastes work when you know where the target is. A* orders cells by f = g + h, where g is the cost so far and h is a heuristic estimate of the remaining cost — on a 4-connected grid with unit steps, the Manhattan distance |r − tr| + |c − tc|. If h never overestimates (it is admissible), A* still finds an optimal path, and it typically explores a narrow corridor towards the target instead of a full disc. With h = 0 it reduces to Dijkstra. Games and robotics use A* (often with refinements like jump point search on uniform grids); in interviews, mentioning it as the optimisation for single-target pathfinding on large maps is a good senior-level addition.

Correctness of 0-1 BFS

Dijkstra's invariant is that the next vertex taken is one with the smallest tentative distance. In 0-1 BFS the deque maintains a stronger structure: its contents always have distances d or d + 1 for some d, with all the d's at the front. Popping from the front therefore takes a minimum-distance vertex. Relaxing a 0-edge produces distance d, pushed to the front, preserving the order; relaxing a 1-edge produces d + 1, pushed to the back, also preserving it. A vertex may be pushed more than once if its distance improves, so either skip stale entries when popped (if their recorded distance is larger than dist) or accept a few redundant relaxations. The structure generalises: for small integer weights 0..k, a bucket queue (Dial's algorithm) gives O(V·k + E).

Encoding cells and state compactly

Cells can be encoded as a single integer r·C + c, which is cheaper to hash than a tuple and lets you use flat arrays for visited flags and distances. For BFS with extra state, encode (r, c, s) as (r·C + c)·S + s. In Python, tuples are fine for interview-sized inputs, but on online assessments with 10⁶ cells and tight time limits, flat lists indexed by an integer encoding can be several times faster. Bit tricks extend this: a visited set of keys collected can be a bitmask, and the full state a single integer.

Grids with portals, teleports and one-way cells

Some grids add irregular edges: snakes and ladders (a square jumps to another), portals that connect two distant cells, conveyor cells that force a direction. The template barely changes — the neighbour function adds the special edges — but the analysis does: the grid may no longer be "nearby cells only", and BFS remains correct only while every move costs the same. "Snakes and Ladders" is a good example: number the squares, map each to its row and column (the board snakes, so alternate rows run in opposite directions — a classic index-arithmetic trap), follow any ladder or snake after each die roll, and BFS for the fewest rolls.

Grids and union-find

Static island counting is a traversal, but some grid problems add land over time: "Number of Islands II" turns water cells into land one at a time and asks for the island count after each step. Re-flooding after every addition is O((R·C)²). Union-find (al19) handles it in near-constant time per addition: each new land cell starts as its own island (count + 1) and is unioned with any land neighbours (count − 1 for each successful union). Choosing union-find for incremental connectivity and BFS/DFS for one-off traversal is a common interview distinction.

In the interview room

Grid problems are where small mechanical mistakes cost the most. The frequent ones: swapping rows and columns (only visible on non-square grids); checking bounds after indexing instead of before; forgetting to mark the start cell visited; marking on pop instead of push (cells enqueued many times, time-outs on large grids); recursing on large grids and hitting the recursion limit; mutating the input when the problem or caller expects it unchanged; and, in multi-source BFS, counting one extra minute at the end. Write the direction array and bounds check once, at the top, and test on a 1×1 grid, a 1×n grid, a non-square grid, and a grid with no sources or no targets.

Interviewers frequently escalate a grid problem one rung at a time — islands, then largest island, then "flip one cell", then "cells added over time" — or shortest path, then "with k removals", then "minimum removals". Each rung changes the template (flood fill → labelling → union-find; BFS → BFS over states → 0-1 BFS). Saying which template applies and why, before coding, is the strongest signal you can give, and it is exactly what reports from Google-style loops emphasise: the grid is easy; choosing the right search is the test.

State the complexity in grid terms: O(R·C) for one traversal, O(R·C·k) for BFS over k extra states, and the queue's memory. If the interviewer mentions very large grids (a map of a city at metre resolution), mention A* for single-target routing and chunked processing for whole-grid passes.

Finally, ask whether diagonal moves count, whether you may modify the input, and what to return when the target is unreachable. Those three questions settle most of the ambiguity in grid problems before you write a line.

On online assessments, grid inputs can be large (10³ × 10³ = 10⁶ cells). Pure-Python BFS over a million cells with tuple keys can take a couple of seconds; flat lists indexed by r·C + c, a precomputed neighbour check, and avoiding function calls in the hot loop keep it within limits. When you see a large grid and a tight limit, mention these constant-factor fixes.

In real systems

Grid algorithms are everywhere in imaging, games and robotics. The paint-bucket tool in image editors is flood fill; computer-vision pipelines run connected-component labelling (scikit-image's measure.label, OpenCV's connectedComponents) to find blobs, characters or cells in microscope images — the same island labelling as this lesson, optimised with union-find and two-pass scans. Distance transforms (each pixel's distance to the nearest edge) are multi-source BFS or two-pass DP and are used in OCR, robotics and medical imaging. Game engines compute paths for characters with A* on tile grids or navigation meshes, and real-time strategy games use multi-source "flow fields" — one BFS from the goal giving every tile a direction — so thousands of units can path-find at once. Robots plan on occupancy grids, where cells are free, occupied or unknown, and route with A* or its variants. Geographic information systems run flood-style analyses on elevation rasters to compute watersheds and water flow — Pacific Atlantic Water Flow is a toy version.

    import random, heapq
from collections import deque

D = ((1, 0), (-1, 0), (0, 1), (0, -1))

def nearest_zero(g):
    R, C = len(g), len(g[0]); dist = [[-1] * C for _ in range(R)]; q = deque()
    for r in range(R):
        for c in range(C):
            if g[r][c] == 0: dist[r][c] = 0; q.append((r, c))
    while q:
        r, c = q.popleft()
        for dr, dc in D:
            nr, nc = r + dr, c + dc
            if 0 <= nr < R and 0 <= nc < C and dist[nr][nc] == -1:
                dist[nr][nc] = dist[r][c] + 1; q.append((nr, nc))
    return dist

def nearest_zero_brute(g):                  # no walls: Manhattan to the closest zero
    R, C = len(g), len(g[0]); zs = [(r, c) for r in range(R) for c in range(C) if g[r][c] == 0]
    return [[min(abs(r - a) + abs(c - b) for a, b in zs) for c in range(C)] for r in range(R)]

def zero_one(g):
    R, C = len(g), len(g[0]); INF = 10**9; d = [[INF] * C for _ in range(R)]
    d[0][0] = 0; dq = deque([(0, 0)])
    while dq:
        r, c = dq.popleft()
        for dr, dc in D:
            nr, nc = r + dr, c + dc
            if 0 <= nr < R and 0 <= nc < C and d[r][c] + g[nr][nc] < d[nr][nc]:
                d[nr][nc] = d[r][c] + g[nr][nc]
                (dq.appendleft if g[nr][nc] == 0 else dq.append)((nr, nc))
    return d[R-1][C-1]

def dijkstra(g):
    R, C = len(g), len(g[0]); best = {(0, 0): 0}; h = [(0, 0, 0)]
    while h:
        d, r, c = heapq.heappop(h)
        if d > best[(r, c)]: continue
        for dr, dc in D:
            nr, nc = r + dr, c + dc
            if 0 <= nr < R and 0 <= nc < C:
                nd = d + g[nr][nc]
                if nd < best.get((nr, nc), 10**9): best[(nr, nc)] = nd; heapq.heappush(h, (nd, nr, nc))
    return best[(R-1, C-1)]

for _ in range(500):
    R, C = random.randint(1, 6), random.randint(1, 6)
    g = [[random.choice((0, 1, 1)) for _ in range(C)] for _ in range(R)]
    if any(0 in row for row in g): assert nearest_zero(g) == nearest_zero_brute(g)
    assert zero_one(g) == dijkstra(g), g
print("multi-source BFS and 0-1 BFS match brute force / Dijkstra")

Choose the grid template

A building floor is a grid of open cells '.', walls '#', exits 'E', and a single fire source 'F'. Each minute you move one cell (4 directions), and the fire spreads to all open neighbouring cells. You start at 'S'. Can you reach an exit before the fire reaches it, and what is the fewest minutes? You may not enter a cell the fire has reached by the time you would arrive.

Answer

Two BFS passes. First, a BFS from the fire source (multi-source if there could be several fires) computes fire_time[r][c], the minute the fire reaches each cell (infinity if never; walls block it — decide with the interviewer whether exits burn). Second, a BFS from 'S' over cells, where moving into (nr, nc) at minute t + 1 is allowed only if t + 1 < fire_time[nr][nc] (strictly earlier, unless the problem says arriving at the same minute as the fire is allowed at the exit — a classic boundary question to ask). The first exit reached in the second BFS gives the fewest minutes; if none is reachable, the answer is −1. Both passes are O(R·C). If the person could also wait in place, waiting never helps in this version because the fire only grows, so BFS still works. A harder variant — "what is the latest you can leave and still escape?" — adds binary search on the start delay (al7) around the second BFS: O(R·C·log(R·C)).
