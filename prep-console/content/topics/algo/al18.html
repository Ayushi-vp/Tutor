A university lists its courses with prerequisites: Data Structures needs Programming 1; Algorithms needs Data Structures and Discrete Maths; Machine Learning needs Algorithms and Linear Algebra. A student asks, "in what order can I take them?" — or, more worryingly, "can I take them at all?", because if some careless department made Course A require B and B require A, nobody can ever finish.

The same question appears everywhere dependencies exist. A build system must compile libraries before the programs that link them. A package manager must install a package's dependencies first. A spreadsheet must recompute a cell only after the cells it refers to. A data pipeline orchestrator runs each job after its inputs are ready. A deep-learning framework computes gradients by walking its computation graph backwards. Each needs an order in which every task comes after all of its prerequisites — a topological order — and each needs to detect the impossible case, a circular dependency.

The brute force — try orderings until one satisfies every constraint — is factorial. The real algorithms are linear, O(V + E), and simple enough to write in a dozen lines. This lesson teaches both standard methods: Kahn's algorithm, which repeatedly takes a task with no unmet prerequisites, and the DFS method, which uses the order in which a depth-first search finishes. Then it applies them to the interview classics — Course Schedule I and II, Alien Dictionary, parallel scheduling with durations, recipes, the centres of a tree — and shows how a topological order unlocks dynamic programming on graphs: longest paths, earliest finish times and path counts.

The mental model: getting dressed

Some clothes must go on before others: underwear before trousers, socks before shoes, trousers before shoes and belt, shirt before tie and jacket. Other pairs do not care: socks and shirt can go in either order. If you draw an arrow from each item to every item that must come after it, you get a directed graph of dependencies. Getting dressed is choosing an order that never goes against an arrow. There are many valid orders — you might put on your watch first or last — but there are rules, and a circular rule ("shoes before socks, socks before shoes") would make dressing impossible.

A directed graph with no circular chain of arrows is a DAG (directed acyclic graph). Every DAG has at least one item with no arrows coming in — something you can put on right now. That observation is the whole of Kahn's algorithm: put on anything that has no unmet prerequisites, cross out its arrows (it no longer blocks anything), and repeat.

The key number for each vertex is its in-degree: how many arrows point into it — how many prerequisites are still unmet. A vertex is ready when its in-degree is zero. Taking it decrements the in-degree of everything it points to. If the graph has a cycle, the vertices on it can never reach in-degree zero (each waits for the previous one), so the algorithm stops with some vertices never taken. That is how cycles are detected: count how many vertices were output.

Where the dressing analogy breaks: in real life you would notice a contradictory rule immediately, but in a graph with thousands of vertices, a cycle can be long and hidden ("A needs B needs C … needs A" through fifty packages). The algorithm does not find where the cycle is, only that one exists; if you need the cycle itself, the DFS method can report it, because a cycle shows up there as an edge back to a vertex still on the current path.

It is also worth contrasting the two directions you might draw edges. "A requires B" can be drawn A → B (pointing at what you need) or B → A (pointing at what becomes possible). Both are legitimate graphs, but Kahn's algorithm reads most naturally with the second: edges point from earlier to later, in-degree counts what you are waiting for, and the output order is the order of execution. If you draw the first, you will get the reverse order, which is fine as long as you know it and reverse at the end. Choose one convention at the start and state it.

One more framing that pays off later: once you have a topological order, you can process vertices so that everything a vertex depends on has already been processed. That is exactly the condition dynamic programming needs, and it turns problems like "longest path" — hopelessly hard on general graphs — into a single linear pass on a DAG.

Kahn's algorithm

from collections import deque, defaultdict
def topo_sort(n, edges):                 # edges: (u, v) means u before v
    graph = defaultdict(list)
    indeg = [0] * n
    for u, v in edges:
        graph[u].append(v)
        indeg[v] += 1
    q = deque(i for i in range(n) if indeg[i] == 0)
    order = []
    while q:
        u = q.popleft()
        order.append(u)
        for v in graph[u]:
            indeg[v] -= 1
            if indeg[v] == 0:            # last prerequisite just finished
                q.append(v)
    return order if len(order) == n else []   # [] signals a cycle

Trace with n = 6 and edges 5→2, 5→0, 4→0, 4→1, 2→3, 3→1. In-degrees: 0:2, 1:2, 2:1, 3:1, 4:0, 5:0. Start the queue with [4, 5]. Pop 4 → order [4]; 0 drops to 1, 1 drops to 1. Pop 5 → [4, 5]; 2 drops to 0 (enqueue), 0 drops to 0 (enqueue). Pop 2 → 3 drops to 0 (enqueue). Pop 0 → no outgoing edges. Pop 3 → 1 drops to 0 (enqueue). Pop 1. Order [4, 5, 2, 0, 3, 1], length 6, so no cycle. Every edge points forward: 5 before 2 and 0, 4 before 0 and 1, 2 before 3, 3 before 1.

Each vertex is enqueued once and each edge decremented once: O(V + E) time and O(V + E) space. The queue order is a free choice; any vertex with in-degree zero may go next, which is why many valid orders exist.

The DFS method

A depth-first search finishes a vertex only after finishing everything reachable from it. So if u → v, v finishes before u (unless v is on the current path, which would be a cycle). Reversing the finishing order therefore puts u before v for every edge.

def topo_sort_dfs(n, edges):
    graph = defaultdict(list)
    for u, v in edges: graph[u].append(v)
    state, out = [0] * n, []                 # 0 new, 1 in progress, 2 done
    def dfs(u):
        state[u] = 1
        for v in graph[u]:
            if state[v] == 1: return False   # back edge: cycle
            if state[v] == 0 and not dfs(v): return False
        state[u] = 2
        out.append(u)                        # post-order: after all descendants
        return True
    for u in range(n):
        if state[u] == 0 and not dfs(u): return []
    return out[::-1]

Both methods are O(V + E). Kahn's is iterative (no recursion-limit worries), gives levels for free, and adapts to "smallest order first" with a heap. The DFS method is natural when you are already doing a DFS for other reasons, and it finds the actual cycle if you keep the current path. In interviews, Kahn's is usually the safer default; know both.

Course Schedule I and II

These are the canonical problems. Course Schedule I ("can you finish all courses?") is cycle detection: run Kahn's algorithm and compare the number of processed courses with the total. Course Schedule II ("return an order") returns the order itself. One detail trips people up: the input pairs are usually [course, prerequisite], meaning the prerequisite comes first, so the edge is prerequisite → course. Write that line carefully; reversing it produces a reverse order that looks plausible and fails the tests.

Alien Dictionary: building the graph is the hard part

"Words from an alien language are given in sorted order; return a valid ordering of its letters, or '' if none." The topological sort is routine; the insight is how to extract edges. Compare each pair of adjacent words. The first position where they differ tells you one fact: the letter in the first word comes before the letter in the second. Nothing after that position tells you anything (just as "cat" < "dog" says only that c < d). And if one word is a prefix of the other, the shorter must come first — if a longer word precedes its own prefix ("abc" before "ab"), the input is invalid.

def alien_order(words):
    graph = {c: set() for w in words for c in w}
    indeg = {c: 0 for c in graph}
    for a, b in zip(words, words[1:]):
        for x, y in zip(a, b):
            if x != y:
                if y not in graph[x]:
                    graph[x].add(y); indeg[y] += 1
                break
        else:                                 # no difference found
            if len(a) > len(b): return ""     # "abc" before "ab": invalid
    q = deque(c for c in indeg if indeg[c] == 0)
    order = []
    while q:
        c = q.popleft(); order.append(c)
        for d in graph[c]:
            indeg[d] -= 1
            if indeg[d] == 0: q.append(d)
    return "".join(order) if len(order) == len(graph) else ""

On ["wrt", "wrf", "er", "ett", "rftt"]: wrt/wrf gives t → f; wrf/er gives w → e; er/ett gives r → t; ett/rftt gives e → r. The order is w, e, r, t, f — "wertf". Using a set for each letter's neighbours avoids counting the same edge twice, which would leave an in-degree that never reaches zero. Only adjacent pairs are needed, because sortedness is transitive: if w1 < w2 < w3, the constraint between w1 and w3 follows from the other two.

Levels: how many rounds?

"Parallel Courses": any number of courses can be taken in a semester once their prerequisites are done; how many semesters are needed? Run Kahn's algorithm level by level — process exactly the vertices currently in the queue as one semester, collecting newly ready vertices for the next.

semesters, done = 0, 0
while q:
    semesters += 1
    for _ in range(len(q)):
        u = q.popleft(); done += 1
        for v in graph[u]:
            indeg[v] -= 1
            if indeg[v] == 0: q.append(v)
return semesters if done == n else -1

The number of levels equals the number of vertices on the longest path, as in the figure. Find All Possible Recipes is the same machinery with a twist: supplies are the initial queue, recipes are vertices whose in-degree is their number of ingredients, and a recipe that reaches zero becomes available as an ingredient for others.

Durations: earliest finish times and the critical path

"Parallel Courses III": each course takes some number of months, any number can run in parallel, and a course can start when all its prerequisites are finished. The minimum total time is the longest path through the DAG, weighted by durations. Process in topological order, keeping each course's earliest finish time:

finish = time[:]                                  # a source finishes after its own duration
q = deque(i for i in range(n) if indeg[i] == 0)
start = [0] * n
while q:
    u = q.popleft()
    finish[u] = start[u] + time[u]
    for v in graph[u]:
        start[v] = max(start[v], finish[u])       # wait for the slowest prerequisite
        indeg[v] -= 1
        if indeg[v] == 0: q.append(v)
return max(finish)

This is dynamic programming along the topological order: when a vertex is popped, all its prerequisites have been finalised, so its start time is known exactly. The chain of courses that determines the maximum is the critical path — delaying any course on it delays the whole programme, while courses off it have slack. Project managers use the same calculation under the name critical path method.

Peeling leaves: the centres of a tree

"Minimum Height Trees": for an undirected tree, which vertices, chosen as root, give the smallest height? The answer is the tree's centre — one vertex or two adjacent ones — and it is found by peeling: remove all leaves (degree 1), which may create new leaves; remove those; continue until at most two vertices remain.

def find_min_height_trees(n, edges):
    if n <= 2: return list(range(n))
    adj = defaultdict(set)
    for u, v in edges: adj[u].add(v); adj[v].add(u)
    leaves = [i for i in range(n) if len(adj[i]) == 1]
    remaining = n
    while remaining > 2:
        remaining -= len(leaves)
        nxt = []
        for leaf in leaves:
            nb = adj[leaf].pop()
            adj[nb].remove(leaf)
            if len(adj[nb]) == 1: nxt.append(nb)
        leaves = nxt
    return leaves

This is Kahn's algorithm on an undirected tree, with "degree 1" playing the role of "in-degree 0". The last vertices to be peeled are the ones farthest from every leaf, which is exactly the centre. O(n).

Specific orders: smallest and unique

When the problem wants the lexicographically smallest valid order, replace the FIFO queue with a min-heap: heapq.heappop always takes the smallest ready vertex. This costs O((V + E) log V). Conversely, to check whether the topological order is unique (Sequence Reconstruction), watch the queue: if it ever contains two or more vertices, either could go next, so at least two orders exist. The order is unique exactly when the queue size is one at every step — which happens when consecutive vertices in the order are all joined by edges.

Dynamic programming on DAGs

Many "best path" and "count paths" questions are easy on DAGs and hard otherwise. Process vertices in topological order and relax their outgoing edges:

  • Longest path: dist[v] = max(dist[v], dist[u] + w). On general graphs the longest simple path is NP-hard; on a DAG it is O(V + E).
  • Shortest path with negative weights: dist[v] = min(dist[v], dist[u] + w) in topological order handles negative edges in O(V + E), no Bellman–Ford needed (because there are no cycles).
  • Number of paths from s to t: ways[v] += ways[u].

Every dynamic programming problem is secretly a DAG — subproblems are vertices, "depends on" is an edge — and the order in which you fill a DP table is a topological order of that DAG. This is the bridge to al21.

Implicit DAGs

Some topological-sort problems never mention a graph. "Longest Increasing Path in a Matrix" has an edge from each cell to any neighbour with a strictly larger value; strictness guarantees no cycles, so the cells form a DAG, and the longest path can be found by Kahn's algorithm (peeling cells with no smaller neighbour, level by level, counting levels) or by DFS with memoisation. "Largest colour value in a directed graph" runs Kahn's algorithm while carrying a 26-entry count per vertex. When a problem's moves can only go "upwards" in some quantity — value, time, length — look for the hidden DAG.

Recognising the pattern

Look for prerequisites, dependencies, "must happen before", build or install order, ordering clues from sorted data (Alien Dictionary), rounds or semesters, earliest completion with durations, or "can all tasks be finished?" (cycle detection). Build edges from "before" to "after", compute in-degrees, and run Kahn's algorithm; add levels, durations, a heap or a uniqueness check as the question requires.

Why Kahn's algorithm is correct

Two facts carry the proof. First, every finite DAG has a vertex with in-degree zero: if every vertex had an incoming edge, you could walk backwards along incoming edges forever, and in a finite graph you would eventually revisit a vertex — a cycle. Second, removing a vertex and its outgoing edges from a DAG leaves a DAG. So as long as vertices remain, one is ready; taking it is safe because nothing points into it from the remaining vertices. Each vertex is output only after all its predecessors have been output (its in-degree reached zero only when the last one was removed), so every edge points forward in the output. Conversely, if the graph has a cycle, no vertex on the cycle can reach in-degree zero before the others, so none is ever output, and the output is shorter than V.

Cycles in dependency graphs: finding and breaking them

Kahn's algorithm tells you a cycle exists; users want to know which. After Kahn stops, the vertices with positive in-degree are exactly those on a cycle or downstream of one. To extract an actual cycle, run the three-state DFS on that remainder and, when you hit an in-progress vertex, walk back along a parent array (or slice the current path) to print the cycle. Package managers and build tools report errors exactly like this ("dependency cycle: a → b → c → a"). More generally, contracting every strongly connected component (Tarjan or Kosaraju, O(V + E)) into a single vertex always yields a DAG — the condensation — which you can then sort topologically. This is how compilers order mutually recursive functions and how 2-SAT is solved.

Enumerating all topological orders

Occasionally a question asks for every valid order (all ways to schedule tasks). That is backtracking on top of Kahn: at each step, try each currently available vertex, decrement its neighbours' in-degrees, recurse, and restore. The number of orders can be enormous — n! for n independent tasks — so this is only feasible for small graphs, and counting orders exactly is #P-complete in general. For small n (≤ 20), bitmask DP over the set of already-placed vertices counts them in O(2ⁿ · n): a vertex can be placed when all its predecessors are in the mask.

Topological order in machine learning systems

Deep-learning frameworks record operations into a computation graph, which is a DAG from inputs and parameters to the loss. The forward pass evaluates nodes in topological order; backpropagation visits them in reverse topological order, so that each node's gradient is complete (all contributions from the nodes that consumed its output have been accumulated) before it is propagated to its inputs. PyTorch's autograd engine does exactly this, and graph compilers such as XLA and TorchInductor schedule fused kernels by topological order of the operator graph. Being able to say "backprop is a reverse topological traversal that accumulates gradients" connects this lesson directly to AI-engineering interviews.

Shortest paths on DAGs, including negative edges

On a general graph, negative edge weights force Bellman–Ford's O(V·E) (al20). On a DAG they are harmless: relax edges in topological order and every vertex's distance is final when it is processed, because all paths into it come from vertices processed earlier. This gives O(V + E) shortest and longest paths, even with negative weights, and it is the reason scheduling problems with durations (which are longest-path problems) are easy when the dependencies are acyclic. It is also why dynamic programming works at all: the DP table's fill order is a topological order of the subproblem DAG.

Incremental and parallel topological sorting

In build systems and data pipelines the graph changes and execution is parallel. Python's graphlib.TopologicalSorter exposes the parallel form directly: get_ready() returns all nodes whose prerequisites are done, workers process them concurrently, and done(node) unlocks dependents — Kahn's algorithm with the queue handed to a thread pool. Systems like Bazel and Airflow do the same at scale, additionally caching results so unchanged subgraphs are skipped. When edges are added online, dynamic topological-order algorithms maintain an order with less than full recomputation, but in practice systems often just re-sort, because O(V + E) is cheap compared with running the tasks.

In the interview room

Topological-sort problems are graded mostly on modelling. Say the vertices, the edge direction and its meaning out loud ("edge from prerequisite to course; in-degree is unmet prerequisites"). The frequent bugs are: reversing the edge direction from the input pairs; forgetting vertices that appear in no edge (they still need to be in the output, with in-degree zero); adding duplicate edges and double-counting in-degrees (Alien Dictionary); missing the invalid-prefix case in Alien Dictionary; and returning a partial order instead of signalling the cycle. Test with no edges, a single cycle of length two, a self-loop if allowed, and disconnected components.

Expect "how do you detect a cycle?" (output count less than V, or a back edge in DFS), "is the order unique?" (queue size one throughout), "what if you need the smallest order?" (heap), and "what if tasks have durations and run in parallel?" (DP along the order — the critical path). For Alien Dictionary, interviewers often ask why only adjacent pairs matter; answer with transitivity of sorted order.

Complexity is O(V + E) for both methods; mention O((V + E) log V) when using a heap. For very large dependency graphs, mention that Kahn's algorithm parallelises naturally — every vertex in the queue can run at once — which is how real build systems use it.

On online assessments, these problems often appear as "task scheduling" stories with prerequisites given as strings or nested lists. Map names to integer ids with a dict first; it keeps the in-degree array simple and avoids subtle bugs with missing keys.

A useful extra in interviews: when you finish Course Schedule, mention how you would report which courses are blocked. After Kahn's algorithm stops early, every course with a remaining positive in-degree is blocked — either on a cycle or depending on one — and a short DFS over those finds a concrete cycle to show the user. That kind of "what would the error message say?" thinking is what distinguishes a production mindset from a puzzle mindset.

In real systems

Topological sorting is one of the most deployed graph algorithms. Make, Bazel, Gradle and other build systems order compilation by dependencies and run independent targets in parallel; Bazel's remote execution farms out entire levels of the DAG. Package managers (pip's resolver, npm, apt) compute install orders and report dependency cycles. Workflow orchestrators such as Apache Airflow, Prefect and Dagster model pipelines explicitly as DAGs and schedule tasks when their upstream tasks succeed. Spreadsheets recalculate cells in dependency order and flag circular references. Database migration tools order migrations by declared dependencies. Compilers schedule instructions within a basic block by the data-dependency DAG, and deep-learning frameworks run forward passes in topological order and backward passes in reverse. Python itself ships graphlib.TopologicalSorter in the standard library for exactly these jobs.

    import random
from collections import deque, defaultdict

def kahn(n, edges):
    g, indeg = defaultdict(list), [0] * n
    for u, v in edges: g[u].append(v); indeg[v] += 1
    q = deque(i for i in range(n) if indeg[i] == 0); out = []
    while q:
        u = q.popleft(); out.append(u)
        for v in g[u]:
            indeg[v] -= 1
            if indeg[v] == 0: q.append(v)
    return out if len(out) == n else None

def dfs_topo(n, edges):
    g = defaultdict(list)
    for u, v in edges: g[u].append(v)
    st, out = [0] * n, []
    def go(u):
        st[u] = 1
        for v in g[u]:
            if st[v] == 1 or (st[v] == 0 and not go(v)): return False
        st[u] = 2; out.append(u); return True
    return out[::-1] if all(st[u] or go(u) for u in range(n)) else None

def valid(order, n, edges):
    pos = {v: i for i, v in enumerate(order)}
    return len(order) == n and all(pos[u] < pos[v] for u, v in edges)

for _ in range(2000):

    perm = random.sample(range(n), n)                    # hidden true order
    edges = [(perm[i], perm[j]) for i in range(n) for j in range(i + 1, n) if random.random() < 0.3]

Model a build system

A monorepo has 50,000 build targets and 300,000 "depends on" edges. Each target has a build time. (a) How do you find an order to build everything on one machine? (b) With unlimited machines, what is the minimum wall-clock time? (c) A developer changes one target; which targets must be rebuilt, and in what order? (d) The build fails with "cycle detected" — how do you report the cycle?

Answer

Model: vertices are targets; edge dependency → dependent (build the dependency first); in-degree = number of dependencies. (a) Kahn's algorithm, O(V + E) ≈ 350,000 steps; any output order works on one machine. (b) DP along the topological order: finish[v] = time[v] + max(finish[u] over dependencies u); the answer is max(finish), the critical path length. With limited machines it becomes a scheduling problem (NP-hard in general), handled with list-scheduling heuristics such as "run the ready task with the longest remaining critical path first". (c) The targets that must rebuild are those reachable from the changed target along dependency → dependent edges: BFS from it to collect the affected set S, then build S in topological order (Kahn restricted to S, counting only in-edges from inside S). Caching by content hash, as Bazel does, can skip targets whose inputs did not actually change. (d) Run Kahn; the vertices left with positive in-degree are on or behind a cycle. Run a three-state DFS over those, keeping the current path in a stack; when an edge reaches an in-progress vertex, the path from that vertex to the top of the stack is the cycle — print it as "a → b → c → a".
