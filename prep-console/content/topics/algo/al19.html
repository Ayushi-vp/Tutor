A social network receives a stream of friendship events: Asha befriends Ben, Ben befriends Chen, Dev befriends Ema, Chen befriends Dev. After each event, the product wants to know: are two given people in the same circle? How many separate circles are there? With a few people you could redraw the groups each time. With 10 million users and 100 million events, running a BFS after every event — O(V + E) each time — would never finish.

The question has a special shape that makes it much easier than general graph search. Groups only ever merge; nobody is ever separated. And you never need the path between two people, only whether they are in the same group. A structure built exactly for that — union-find, also called disjoint set union (DSU) — answers "same group?" and performs "merge these groups" in amortised time so close to constant that, for any practical input, it is constant.

Union-find shows up in interviews in two ways. Directly: counting components, detecting the edge that creates a cycle, merging accounts that share an email, checking whether a set of equations can all be true, counting islands as land is added. And as a building block: Kruskal's minimum spanning tree algorithm is "sort the edges, then use union-find to skip edges that would create a cycle". It is also a classic "implement this data structure" question, where interviewers look for the two optimisations that make it fast.

This lesson builds union-find from a naive version to the optimised one, explains why the two heuristics — path compression and union by rank — matter, then applies it to each problem family, including weighted union-find for ratio queries and the trick of mapping rows and columns into one id space.

The mental model: clubs with presidents

Imagine every person belongs to exactly one club, and every club has a president. To find out whether two people are in the same club, ask each of them "who is your president?" — if the answers match, they are in the same club. To merge two clubs, one president agrees to report to the other; from then on, the second president leads everyone.

The trick that makes this cheap is that nobody needs to know their president directly. Each person only knows one other person to ask — their parent — and asking repeatedly ("who do you report to?") eventually reaches someone who reports to themselves: the president, or root. That is the find operation. Merging two clubs (union) only changes one pointer: the root of one club starts pointing to the root of the other. Thousands of members join a new club with a single change, because they all reach the new president through their old one.

The danger is that the chains of "ask your parent" can get long — if every union hangs a big club under a single person, find might walk a long way. Two simple rules prevent this. Union by rank (or size): when merging, the smaller (or shorter) tree goes under the larger one, so trees stay shallow. Path compression: after find walks a path to the root, every node on that path is re-pointed straight at the root, so the next find on any of them is one step. With both rules, a long sequence of operations averages out to effectively constant time each.

Where the club analogy breaks: in a real club, people can leave. Union-find cannot split a group — there is no record of which merges created it, and path compression has erased the original structure anyway. If a problem needs to remove connections, union-find alone will not do; the deep layer covers the workarounds.

It helps to compare costs concretely. Suppose 10⁶ people and 10⁷ friendship events, with a "same circle?" query after each event. Re-running BFS after each event would cost on the order of 10⁷ × 10⁷ operations — impossible. Union-find does about 10⁷ unions and 10⁷ pairs of finds, each a handful of pointer steps: a few seconds even in Python. The gap is not a constant factor; it is the difference between an answer and no answer.

A good way to recognise union-find problems is the phrase pattern "are these in the same group?" plus "groups merge over time" — or any problem where you would otherwise re-run a connectivity search after every change.

From naive to fast

The most naive version stores each element's group id directly (quick-find): find is O(1), but union must relabel every member of one group, O(n). The parent-forest version (quick-union) makes union cheap — link one root to the other — but without care the trees can become chains, making find O(n). Union by rank and path compression fix that.

class DSU:
    def __init__(self, n):
        self.parent = list(range(n))       # each element is its own root
        self.size = [1] * n
        self.count = n                     # number of groups

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path halving
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                   # already together: this edge adds a cycle
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra                # attach the smaller tree under the larger
        self.parent[rb] = ra
        self.size[ra] += self.size[rb]
        self.count -= 1
        return True

Three details are worth saying aloud. find uses path halving — each node on the path is pointed at its grandparent as the loop goes — an iterative form of compression that avoids recursion and has the same guarantees. union returns whether a merge actually happened, which many problems need (it is the cycle test). And count is maintained incrementally, so "how many groups?" is O(1). The recursive full-compression version, if parent[x] != x: parent[x] = find(parent[x]); return parent[x], is shorter but can hit Python's recursion limit on a long chain before compression has flattened it.

Trace with n = 8: union(1, 2) → root 1 gets 2 (count 7). union(3, 4) → count 6. union(2, 4): find(2) = 1, find(4) = 3, sizes equal, 3 goes under 1 (count 5). union(5, 6), union(6, 7) → 5's group {5, 6, 7} (count 3: groups {0}, {1,2,3,4}, {5,6,7}). union(3, 7): find(3) = 1 (size 4), find(7) = 5 (size 3), so 5 goes under 1 (count 2). Now find(7) walks 7 → 5 → 1 and halving shortens the path. Are 2 and 6 connected? find(2) = 1 = find(6), yes.

Counting components and spotting cycles

"Number of Connected Components in an Undirected Graph": create a DSU of n, union every edge, return count. "Graph Valid Tree": a tree on n nodes has exactly n − 1 edges and no cycle; check the edge count, then union every edge and fail if any union returns False (both ends already connected, so this edge would close a cycle). "Redundant Connection": a tree with one extra edge; the first edge (in input order) whose union returns False is the one to remove.

def find_redundant_connection(edges):
    dsu = DSU(len(edges) + 1)            # nodes are 1..n
    for u, v in edges:
        if not dsu.union(u, v):
            return [u, v]

These are short because union-find answers exactly the question asked. DFS can solve them too, but re-checking connectivity after each edge is where union-find's incremental nature wins.

Grouping by shared attributes: Accounts Merge

"Each account is a name and a list of emails; two accounts belong to the same person if they share any email. Merge them." The elements to group are emails. Within one account, all emails belong together, so union each email with the account's first email. Accounts that share an email become connected through it.

def accounts_merge(accounts):
    parent, owner = {}, {}
    def find(x):
        parent.setdefault(x, x)
        while parent[x] != x:
            parent[x] = parent[parent[x]]; x = parent[x]
        return x
    for name, *emails in accounts:
        for e in emails:
            owner[e] = name
            parent[find(e)] = find(emails[0])      # union with the first email
    groups = defaultdict(list)
    for e in owner:
        groups[find(e)].append(e)
    return [[owner[root]] + sorted(es) for root, es in groups.items()]

A dict-based parent lets emails (strings) be elements directly. This version skips union by size for brevity; with path halving it is still fast. Sorting each group dominates the cost: O(E log E) for E emails.

Equivalence first, then contradictions: equality equations

"Given equations like 'a==b' and 'b!=c' over 26 variables, can all be true at once?" Equalities define groups (equality is transitive); inequalities are constraints between groups. So: union the variables of every '==' equation first; then, for each '!=' equation, if both variables share a root, they are forced equal and the system is unsatisfiable. The order matters — checking an inequality before processing a later equality could miss a contradiction.

Mapping two kinds of things into one id space: stones

"Stones sit on a grid; a stone can be removed if another stone shares its row or column. What is the maximum number of removable stones?" Within any group of stones connected by shared rows or columns, you can remove stones one at a time (always a leaf of a spanning tree of the group) until one remains. So the answer is stones − number of groups. The neat modelling trick: instead of unioning stones with each other (O(n²) pairs), union each stone's row with its column, treating rows and columns as the elements. Two stones in the same row share that row element; two in the same column share the column element. Keep rows and columns in different id ranges (for example row r → r, column c → c + 10001).

def remove_stones(stones):
    parent = {}
    def find(x):
        parent.setdefault(x, x)
        while parent[x] != x:
            parent[x] = parent[parent[x]]; x = parent[x]
        return x
    for r, c in stones:
        parent[find(r)] = find(c + 10001)
    roots = {find(x) for x in parent}
    return len(stones) - len(roots)

This "make the attributes the elements" move recurs: union people with the groups they belong to, or words with the synonyms they are equivalent to, rather than comparing every pair of items.

Online connectivity: Number of Islands II

"An R×C grid starts as water; positions are turned into land one at a time; after each, report the number of islands." Re-running flood fill after each addition is O(R·C) per step. With union-find over cell ids r·C + c: when a cell becomes land, add it as a new set (count + 1), then union it with each of its four neighbours that are already land (each union that merges two different roots does count − 1). Skip positions that are already land. Each addition costs O(α(R·C)) amortised. This is the clearest demonstration of why union-find exists: the graph grows, and the question is asked after every change.

Weighted union-find: ratios and offsets

"Evaluate Division" (a/b = 2, b/c = 3, what is a/c?) was solved with DFS in al16. Union-find can store a value on each parent link: w[x] = x / parent[x]. When find compresses x's path to the root, it multiplies the weights along the way so that w[x] becomes x / root.

parent, w = {}, {}
def find(x):
    if parent[x] != x:
        p = parent[x]
        root = find(p)
        w[x] *= w[p]               # x/p * p/root = x/root
        parent[x] = root
    return parent[x]

def union(a, b, k):                # record a / b = k
    for v in (a, b):
        if v not in parent: parent[v], w[v] = v, 1.0
    ra, rb = find(a), find(b)
    if ra != rb:
        parent[ra] = rb
        w[ra] = k * w[b] / w[a]    # ra/rb = (a/ra)^-1 * (a/b) * (b/rb)

def query(a, c):
    if a not in parent or c not in parent or find(a) != find(c): return -1.0
    return w[a] / w[c]             # (a/root) / (c/root)

For a/b = 2 and b/c = 3: after both unions, a/c = w[a] / w[c] = 6. The same idea with additive offsets answers "how far apart are these two items?" in relative-positioning problems, and with parity bits (offset mod 2) checks bipartiteness incrementally — "Possible Bipartition" with edges arriving online.

Kruskal's minimum spanning tree

A minimum spanning tree connects all vertices of a weighted undirected graph with the least total edge weight. Kruskal's algorithm is greedy: sort edges by weight and take each edge that connects two different components (union returns True), skipping those that would form a cycle. Stop after n − 1 edges.

def min_cost_connect_points(points):
    n = len(points)
    edges = sorted((abs(x1 - x2) + abs(y1 - y2), i, j)
                   for i, (x1, y1) in enumerate(points)
                   for j, (x2, y2) in enumerate(points) if i < j)
    dsu, total, used = DSU(n), 0, 0
    for w, i, j in edges:
        if dsu.union(i, j):
            total += w; used += 1
            if used == n - 1: break
    return total

Sorting dominates: O(E log E). Its correctness rests on the cut property — the lightest edge crossing any division of the vertices into two sides belongs to some MST — and on the fact that forests form a matroid, so the greedy is optimal (al12). For dense graphs like this complete one, Prim's algorithm is often better (al20).

Listing groups and their sizes

Many problems want the groups themselves at the end: the merged accounts, the members of each island, the size of the largest friend circle. Union-find does not store members, but recovering them is easy: after all unions, loop over every element, compute its root with find, and append it to a list keyed by root. That is O(n·α(n)). Sizes are even cheaper if you maintain size at the roots during union, as the DSU class does: the largest group is max(size[r] for r in roots). If you need members during the process (for example, to notify everyone in a merged group), keep a member list at each root and, on union, extend the larger list with the smaller one; each element moves at most log₂ n times (its group at least doubles each time it moves), so the total is O(n log n).

Recognising the pattern

Reach for union-find when groups merge and never split, when you need "same group?" or "how many groups?" after many merges, when an edge's arrival should be checked for creating a cycle, or when items are equivalent through shared attributes (emails, rows and columns, synonyms). If the graph is static and you also need paths or distances, BFS/DFS may be simpler.

Why both heuristics, and what α(n) means

Union by rank alone keeps every tree's height at most log₂ n: a tree of rank r has at least 2^r nodes, because its rank only increases when two trees of equal rank merge, doubling the minimum size. So find is O(log n). Path compression alone gives O(log n) amortised as well. Together, Tarjan proved in 1975 that m operations cost O(m·α(n)), where α is the inverse of the Ackermann function — a function that grows so fast that α(n) ≤ 4 for any n you could ever store; the first n with α(n) = 5 is a tower of exponents vastly larger than the number of atoms in the universe. The intuition: compression makes nodes skip ever-larger stretches of rank, and the number of times a node's "skip level" can increase is bounded by an iterated logarithm of an iterated logarithm, and so on. In interviews, "amortised inverse Ackermann, effectively constant" is the expected phrase; and it is worth adding that union by size works as well as by rank and is more useful in practice because the sizes are often needed anyway.

Deletions: offline reversal and rollback

Union-find cannot undo a union, because path compression destroys the information needed. Three workarounds exist. Offline reversal: if all operations are known in advance, process them backwards — start from the final state, and deletions become unions. This solves problems like "remove these edges one by one; after each removal, how many components remain?" in O((V + E)·α). Rollback DSU: drop path compression, keep union by size, and push every parent change onto a stack so the last union can be undone exactly; find becomes O(log n). Combined with a segment tree over time ("each edge exists during an interval of operations"), this gives offline dynamic connectivity in O(m log m log n). Fully dynamic connectivity structures support online insertions and deletions in polylogarithmic amortised time, but they are research-grade and rarely implemented in interviews — naming them is enough.

Kruskal versus Prim, and single-linkage clustering

Kruskal needs the edges sorted: O(E log E). It is ideal for sparse graphs given as edge lists. Prim grows one tree from a start vertex, always adding the cheapest edge leaving it, using a heap (O(E log V)) or, for dense graphs, an array of best distances scanned in O(V) per step (O(V²) total, better than sorting V²/2 edges). If you stop Kruskal early, when k components remain, the components are exactly the clusters of single-linkage hierarchical clustering with k clusters — the same algorithm used by SciPy's linkage(method="single"). That connection is a nice bridge from DSA to machine learning.

Union-find in type inference and compilers

Hindley–Milner type inference — the algorithm behind type inference in ML, OCaml, Haskell and (in spirit) parts of Rust and TypeScript — represents type variables as union-find elements. Unifying two types ("these must be the same") is a union; finding what a type variable stands for is a find. Compilers also use union-find for alias analysis (which pointers may refer to the same memory), register coalescing, and computing equivalence classes of program variables. These are examples where near-constant merges over millions of elements are essential.

Parity and bipartiteness with union-find

Store, for each node, the parity (0 or 1) of the path to its parent. find accumulates parity along the path (XOR), giving each node's parity relative to its root. Adding an edge u–v that says "u and v are on opposite sides" either links two roots with the parity chosen to make it true, or — if u and v already share a root — checks that their parities differ; if they are equal, the graph has an odd cycle and is not bipartite. This handles bipartiteness online as edges arrive, which BFS colouring cannot do without recomputation.

Percolation and connectivity thresholds

A classic simulation asks: in a grid where each cell is open with probability p, at what p does a path of open cells connect top to bottom? Opening cells one by one and union-ing with open neighbours, with two virtual nodes connected to the whole top and bottom rows, answers "does it percolate yet?" with a single find comparison after each opening. Monte Carlo runs estimate the threshold (about 0.593 for site percolation on a square grid). The same virtual-node trick — one extra element standing for "the border" or "the outside" — simplifies many grid problems, such as Surrounded Regions solved with union-find.

In the interview room

Interviewers who ask union-find usually want to see the implementation with both optimisations and a clear explanation of what each buys. Write the class with find, union that returns a boolean, and a count; say "path compression flattens trees on find; union by size keeps them shallow; together amortised inverse Ackermann". Common bugs: comparing parent[x] instead of find(x); unioning non-root nodes (parent[a] = b instead of parent[find(a)] = find(b)), which silently breaks groups; forgetting to decrement the count only on successful merges; off-by-one node numbering (1-based inputs with a 0-based array of size n); and recursive find on a long chain hitting the recursion limit. Test with repeated unions of the same pair, a union of an element with itself, and a long chain.

Recognition is the other half. The tell-tale phrases are "groups", "merge", "connected", "same component", "redundant", "equivalent", and anything where edges arrive over time. A strong answer also says when not to use union-find: if the graph is static and the question needs paths or distances, BFS is simpler; if edges are deleted, union-find needs an offline trick.

A good follow-up to anticipate: "what if the elements are strings?" (dict-based parent, created lazily); "what if there are 10⁸ elements?" (arrays of 32-bit integers rather than Python lists, or sharding by component); "can you list the members of a group?" (union-find does not store members — either group by find at the end, or keep a member list at each root and merge the smaller into the larger, which costs O(n log n) total).

On online assessments, union-find problems often hide behind stories about friend circles, network cables, or "how many groups after these operations". Reading the operations as unions and the questions as finds or counts is usually the whole insight; the implementation is the same twenty lines every time, so it is worth having them memorised.

In real systems

Union-find appears wherever equivalence classes are built incrementally. Image processing labels connected components in two passes — the first assigns provisional labels and records which labels touch in a union-find, the second replaces each label by its root — which is how OpenCV and scikit-image label blobs efficiently. Network design and clustering use Kruskal's algorithm; single-linkage clustering in SciPy is Kruskal stopped early. Entity resolution systems (deciding which customer records refer to the same person) union records that share strong identifiers such as email or phone, exactly like Accounts Merge, at the scale of billions of records in distributed versions. Compilers use union-find in type inference and alias analysis. Physics and materials simulations use it for percolation. And distributed graph systems compute connected components with label-propagation variants of the same idea, iteratively pointing each vertex at the smallest label in its neighbourhood until the labels stop changing.

    import random
from collections import defaultdict

class DSU:
    def __init__(s, n, compress=True, by_size=True):
        s.p, s.sz, s.count, s.c, s.b = list(range(n)), [1] * n, n, compress, by_size
    def find(s, x):
        while s.p[x] != x:
            if s.c: s.p[x] = s.p[s.p[x]]
            x = s.p[x]
        return x
    def union(s, a, b):
        ra, rb = s.find(a), s.find(b)
        if ra == rb: return False
        if s.b and s.sz[ra] < s.sz[rb]: ra, rb = rb, ra
        s.p[rb] = ra; s.sz[ra] += s.sz[rb]; s.count -= 1; return True

def bfs_components(n, edges):
    g = defaultdict(list)
    for u, v in edges: g[u].append(v); g[v].append(u)
    seen, comps = set(), 0
    for s in range(n):
        if s in seen: continue
        comps += 1; stack = [s]; seen.add(s)
        while stack:
            u = stack.pop()
            for v in g[u]:
                if v not in seen: seen.add(v); stack.append(v)
    return comps

for _ in range(2000):
    n = random.randint(1, 12)
    edges = [(random.randrange(n), random.randrange(n)) for _ in range(random.randint(0, 15))]
    d = DSU(n)
    for u, v in edges: d.union(u, v)
    assert d.count == bfs_components(n, edges)
print("DSU component counts match BFS")

def height(d, x):
    h = 0
    while d.p[x] != x: x = d.p[x]; h += 1
    return h
n = 100_000
for c, b in ((False, False), (False, True), (True, True)):
    d = DSU(n, c, b)
    for i in range(1, n): d.union(i, i - 1)    # adversarial chain of unions
    print(f"compress={c!s:5} by_size={b!s:5} max height={max(height(d, x) for x in range(0, n, 997))}")

The height lines show the effect of the heuristics on a chain of 100,000 unions: with neither, trees grow tall (the exact height depends on which root goes under which); with union by size they stay tiny; with both, flatter still. If the no-heuristic case is slow, reduce n.

What this proves: union-find computes the same components as a graph search, and the heuristics are what keep find paths short — without them, an unlucky union order can make find walk long chains.

Pick the structure

For each scenario, choose BFS/DFS or union-find and justify it in one sentence. (a) A static road network; find the shortest route between two cities by number of roads. (b) Servers are linked one cable at a time; after each cable, report whether the network is fully connected. (c) Given 10⁵ synonym pairs, decide for 10⁵ sentence pairs whether they are equivalent word by word. (d) Cables can also be cut; after each event, report the number of connected groups, with all events known in advance. (e) Find whether a static graph is bipartite.

Answer

(a) BFS: a static graph and a shortest-path question; union-find knows nothing about paths. (b) Union-find: connections only accumulate, and "fully connected" is count == 1 after each union — O(α) per cable instead of a BFS each time. (c) Union-find over words: union each synonym pair, then two sentences are equivalent if they have the same length and find(word) matches position by position — fast, and transitive synonyms ("happy ~ glad ~ joyful") are handled automatically. (d) Union-find processed offline in reverse: start from the final set of cables, walk the events backwards turning cuts into unions, record the count at each step, and reverse the answers. (e) BFS/DFS two-colouring is simplest for a static graph; a parity union-find also works and is the better choice if edges arrive online.
