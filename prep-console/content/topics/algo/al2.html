You have just written a solution in an interview. It is correct: you traced it on your examples and the edge cases. The interviewer nods and asks, "What's the time complexity?" You say "O(n)", because there is one for loop. They ask, "What about the in check inside it?" You realise the in is on a list, so each check scans the whole list, and the real cost is O(n²). With 10⁵ elements, that is the difference between a fraction of a second and several minutes.

The same gap appears in online assessments, but more brutally. The platform runs your code on hidden tests with up to 10⁵ or 10⁶ elements and a time limit of one or two seconds. A correct O(n²) solution passes the small tests and fails the large ones with "Time Limit Exceeded", and you get partial credit at best. The problem statement told you this would happen: the line 1 ≤ n ≤ 10⁵ was a hint about which complexity was expected, if you knew how to read it.

Complexity analysis is the tool for both situations. It lets you predict, before you write or run anything, whether an approach is fast enough, and it lets you explain precisely why one solution beats another. It is also the language interviewers use in every round: "can you do better?" means "can you reach a lower complexity class?", and you cannot answer that without knowing which class you are in.

This lesson teaches you to count work: what big-O means and why it drops constants; how to analyse loops (including the nested loops that are secretly linear), recursion and amortised operations; how to measure memory; the hidden costs of common Python operations; and — the most practical skill of all — how to turn the input constraints into the target complexity before you design anything.

The mental model: counting steps as the input grows

Imagine you are looking for a friend's name in a printed phone book. One way is to read every name from the first page until you find it. Another is to open the book in the middle, see whether the name comes earlier or later in the alphabet, and repeat on the correct half. For a book with 1,000 names, the first method can take 1,000 looks; the second takes about 10. For a book with a million names, the first takes up to a million looks and the second about 20. The interesting thing is not the exact counts; it is how they grow. Making the book a thousand times bigger makes the first method a thousand times slower, and the second barely slower at all.

That is what complexity analysis captures: how the amount of work grows as the input grows. We count basic steps — a comparison, an addition, an array access, a hash lookup — as functions of the input size, usually called n. Then we keep only the part that dominates for large n.

Big-O in one paragraph

If an algorithm does 3n² + 10n + 50 steps, then for n = 1,000 the 3n² term is 3,000,000 and the rest is about 10,000: the n² term is everything. Big-O notation writes this as O(n²): it keeps the fastest-growing term and drops constant multipliers. Dropping the 3 is deliberate: constant factors depend on the machine, the language and the compiler, while the growth rate depends only on the algorithm. Formally, O(g(n)) is an upper bound — the work is at most a constant times g(n) once n is large enough — but in interviews people use it to mean "this is the growth class".

The class is not a detail; it decides whether the program is usable at all.

Where the analogy breaks: the phone-book picture suggests only time matters. Memory has a complexity too — space complexity, how much extra memory grows with n — and many interview follow-ups ("can you do it in constant space?") are about that dimension instead.

Counting a single loop

Start with the simplest case. This function looks at each element once and does constant work per element:

def total(a):
    s = 0
    for x in a:      # runs n times
        s += x       # O(1) each
    return s

The loop body runs n times and costs O(1) each time, so the total is O(n). The rule for sequential code is to add: two loops one after another are O(n) + O(n) = O(n). The rule for nested code is to multiply the number of times the inner body runs, which is where most mistakes happen.

Nested loops: count how many times the inner body runs

Two full nested loops over n elements run the inner body n × n = n² times: O(n²). A triangular loop, where the inner loop starts at the outer index, runs it (n−1) + (n−2) + … + 1 = n(n−1)/2 times. That is half as much, but half is a constant factor, so it is still O(n²).

Not every nested loop is quadratic. This is the key exception, and you will see it in every sliding-window and two-pointer solution:

left = 0
for right in range(n):              # n iterations
    add(a[right])
    while window_invalid():         # how many times in total?
        remove(a[left])
        left += 1

The inner while loop can run many times in one outer iteration, but each time it runs, left increases by one, and left never decreases and never exceeds n. So over the entire run, the inner body executes at most n times. Total work: n (outer) + n (inner, across all iterations) = O(n). The lesson: count the total number of executions of each line across the whole run, and look for a quantity that only moves in one direction. This technique has a name, the aggregate method, and it is the simplest kind of amortised analysis.

Logarithms: halving and doubling

A logarithm answers the question "how many times can I halve n before reaching 1?". log₂ 8 = 3 because 8 → 4 → 2 → 1. Any loop that halves (or doubles) a quantity each step runs O(log n) times:

i = n
while i > 1:
    i //= 2          # runs about log2(n) times

Binary search halves the search range each step, so it is O(log n). A balanced binary tree with n nodes has height about log₂ n, so walking from root to leaf is O(log n), which is why heap operations and balanced-tree lookups are O(log n). The base of the logarithm does not matter in big-O, because log₂ n and log₁₀ n differ only by a constant factor. Useful values to memorise: log₂ 10³ ≈ 10, log₂ 10⁶ ≈ 20, log₂ 10⁹ ≈ 30.

O(n log n) appears whenever you do a logarithmic operation for each of n elements (n heap pushes) or a linear amount of work at each of log n levels (merge sort). It is also the cost of comparison-based sorting, which cannot do better: there are n! possible orderings and each comparison at best halves the possibilities, so you need about log₂(n!) ≈ n log₂ n comparisons.

Recursion: the recursion tree

For a recursive function, draw the tree of calls, write the work done in each call (excluding its recursive calls), and add it all up. Take merge sort: a call on n elements does O(n) work merging and makes two calls on n/2 elements.

Compare the naive recursive Fibonacci: fib(n) calls fib(n-1) and fib(n-2) and does O(1) work itself. The tree branches twice at every level and has depth n, so it has roughly 2ⁿ nodes (more precisely about 1.6ⁿ). Exponential time comes from branching recursion whose branches recompute the same thing; memoisation (storing each answer the first time) collapses the tree to n distinct calls. That observation is the foundation of dynamic programming (al21).

A shortcut for divide-and-conquer recurrences of the form T(n) = a·T(n/b) + f(n) is the master theorem. You rarely need it formally in interviews; it is enough to know three results: T(n) = 2T(n/2) + O(n) is O(n log n) (merge sort); T(n) = T(n/2) + O(1) is O(log n) (binary search); T(n) = 2T(n/2) + O(1) is O(n) (visiting every node of a balanced tree).

Amortised analysis: expensive sometimes, cheap on average

A Python list is a dynamic array: a block of memory with some spare capacity. Appending is cheap while there is spare room. When the block is full, the list allocates a larger block and copies everything — an O(n) operation. So is append O(1) or O(n)?

Both, depending on how you ask. A single append can be O(n). But because CPython grows the block proportionally (by roughly an eighth plus a little, so capacity keeps growing geometrically), each expensive copy of n elements is followed by on the order of n cheap appends before the next one. If the array doubled each time, the copies over n appends would total n/2 + n/4 + … ≤ n elements; with a smaller growth factor the total is a larger constant times n, but still O(n). So n appends cost O(n) in total, and the amortised cost per append is O(1). The same reasoning makes hash-table insertion amortised O(1) (occasional rehashing) and the sliding-window inner loop O(1) per step on average.

The growth must be proportional for this to work. If the array grew by a fixed 100 slots each time, a copy would happen every 100 appends, and the copies would total about n²/200 — quadratic.

Space complexity: what counts

Space complexity counts the extra memory the algorithm needs beyond the input, as a function of n. Three sources are easy to forget. The recursion stack: each active call holds a frame, so a recursion of depth d uses O(d) space even if the function allocates nothing. Implicit copies: a[1:] creates a new list of n−1 elements; a recursive function that passes slices therefore uses O(n²) memory in total across a chain of calls, where passing indices would use O(n). The output: by convention, memory for the answer itself is usually not counted, but say so.

Python also has a practical limit: the default recursion limit is 1,000 frames. A DFS on a path-shaped graph with 10⁵ nodes will crash with RecursionError. You can raise the limit with sys.setrecursionlimit, but the robust fix is an explicit stack.

Reading the constraints: the most useful table in this track

A typical machine runs roughly 10⁸ simple operations per second in compiled languages; pure Python manages about 10⁷. Problem setters choose input limits so that the intended complexity fits in about a second. So you can work backwards from the constraint to the algorithm before designing anything:

Putting it together: analysing a complete solution

Here is how to analyse a realistic solution line by line, the way you would say it in an interview. The task: return the k most frequent words in a list of n words, ties broken alphabetically.

from collections import Counter
import heapq

def top_k(words, k):
    counts = Counter(words)                         # (1)
    return heapq.nsmallest(k, counts,               # (2)
                           key=lambda w: (-counts[w], w))

Line (1) hashes each word once. If the average word length is L, hashing costs O(L) per word, so building the counter is O(n·L) time and O(u·L) space, where u is the number of distinct words. Line (2) keeps a heap of size k while scanning the u distinct words; each push or pop is O(log k), so it is O(u log k) time and O(k) extra space. Total: O(n·L + u log k) time, O(u·L) space. In an interview you would usually treat L as a small constant and say "O(n + u log k), which is O(n log k) in the worst case where all words are distinct". Notice three habits: naming every variable that matters (n, u, k, L), justifying each term by the operation that causes it, and simplifying only at the end, saying what assumption the simplification makes.

Compare the alternative of sorting all distinct words by (−count, word): O(u log u). When k is much smaller than u, the heap is better; when k is close to u, they are the same. Saying that trade-off unprompted is the kind of answer that separates "knows big-O" from "uses big-O to choose".

Your algorithm's complexity is only as good as the operations it uses. These Python operations look cheap but cost O(n) (or more):

Big-O, big-Omega and big-Theta: say what you mean

Strictly, big-O is only an upper bound: binary search is O(n) too, because log n ≤ n, even though that is a useless statement. Big-Omega (Ω) is a lower bound, and big-Theta (Θ) means both — the growth is pinned down exactly up to constants. In conversation and interviews, "O" is used to mean Θ, and that is fine. Where the distinction matters is lower bounds for problems: "any comparison sort is Ω(n log n)" and "finding the maximum of an unsorted array is Ω(n)" are statements about every possible algorithm, and they tell you when to stop trying to optimise.

Worst, average and expected cases

Quicksort is Θ(n log n) on average but Θ(n²) in the worst case, when each pivot is the smallest or largest element (for example, a naive first-element pivot on already-sorted input). Hash tables are O(1) expected per operation but O(n) worst case if many keys collide. "Expected" usually means averaged over the algorithm's own randomness (a random pivot, a random hash seed), which makes the guarantee hold for every input with high probability, rather than averaged over some assumed distribution of inputs. That is why Python randomises the hash of strings per process: it stops an attacker crafting colliding keys to force the worst case. When an interviewer asks about a hash-map solution, "O(n) expected" is the precise phrase.

Amortised analysis beyond the aggregate method

The aggregate method adds up total cost over a sequence and divides. A more flexible view is the potential method, which treats cheap operations as saving credit for future expensive ones. For the dynamic array, charge each append 3 units: 1 pays for the write and 2 are saved; when a resize copies the elements, the saved credit pays for the copies. You will not be asked to do potential-function proofs in coding interviews, but the intuition — "cheap operations prepay for rare expensive ones, and the expensive one cannot happen again until enough cheap ones have occurred" — is how you justify union-find's near-constant operations, monotonic stack pops, and the sliding-window inner loop.

When n is not the only variable

Many problems have several size parameters, and collapsing them into one hides the real cost. A grid is R × C; a graph has V vertices and E edges; a string problem has text length n and pattern length m; a list of words has k words of average length L. Report complexity in all of them: BFS is O(V + E), not O(n); building a trie is O(total characters), not O(k). This matters because the parameters can be wildly different: a graph with 10⁵ vertices might have 10⁵ edges (sparse) or 10¹⁰ edges (dense), and an algorithm that is O(V²) is fine for the dense case and terrible for the sparse one.

Pseudo-polynomial complexity

The coin-change DP runs in O(n · amount). That looks polynomial, but it is polynomial in the value of amount, not in the number of digits needed to write it. If amount is 10⁹, the table has 10⁹ entries — too many — even though the input is tiny. Such algorithms are called pseudo-polynomial. Recognising them matters in interviews because a follow-up such as "what if amount is up to 10⁹?" means the DP no longer works and you need a different idea (math, greedy with proof, or meet-in-the-middle).

Constants and the memory hierarchy

Two O(n) algorithms can differ by 10–100× in practice. Sequential array scans run at memory bandwidth because the CPU prefetches the next cache line; pointer-chasing through a linked list or a hash table with scattered entries waits for main memory on each step (about 100 ns, versus about 1 ns for a cache hit). In Python the gap is between operations that run in C (built-ins like sum, sorted, set intersection, slicing) and operations interpreted bytecode by bytecode. This is why "O(n) in Python with a tight interpreted loop" can lose to "O(n log n) using sorted()". Mention it when relevant; it shows you know where big-O stops being the whole story, and it is the reason performance engineers measure before and after every optimisation instead of trusting the analysis alone.

In the interview room

Interviewers ask for complexity after almost every solution, and they listen for three things. First, both time and space, unprompted. Second, the right variables — "O(R·C) for the grid" or "O(V + E)", not a vague "O(n)". Third, a justification in one sentence: "each cell is pushed onto the queue at most once, and each push does four neighbour checks". A bare answer with no reasoning invites the follow-up "why?", and a wrong reason is worse than none.

The most common mistakes are predictable. Calling a sliding window O(n²) because of the nested loop (it is O(n) by the aggregate argument). Calling a hash-map solution O(1) space (the map holds up to n entries). Forgetting the recursion stack (a recursive DFS on a 10⁵-node chain is O(n) space and, in Python, a crash). Forgetting the cost of sorting at the start (a two-pointer solution on unsorted input is O(n log n), not O(n)). And missing hidden O(n) calls inside loops.

In online assessments

Online assessment platforms show you the constraints and run hidden tests with the largest allowed inputs. Read the constraints before reading the examples. If your idea's operation count at the maximum n is above about 10⁸ (10⁷ in Python), it will time out; rethink before coding. If you cannot find the intended complexity, submit the brute force anyway — partial credit for passing the small tests is common — then improve it. Also watch input reading: reading 10⁶ numbers with repeated input() calls in Python can itself take a second; use sys.stdin.read().split() or the platform's fast template.

When the interviewer asks "can you do better?", answer with the class you are aiming for and why it is plausible: "the best conceivable is O(n) because every element must be read; the log factor comes from sorting, and I only need the k largest, so a heap of size k gives O(n log k)". That shows you are reasoning about where the cost comes from, not guessing at tricks. And when you genuinely believe you are optimal, say so with the lower-bound argument; interviewers sometimes ask "can you do better?" precisely to see whether you can defend an optimal answer.

In real systems

Complexity mistakes are a classic source of production incidents, because test data is small and production data is not. A request handler that does an O(n²) de-duplication works fine with 100 items in staging and takes minutes with 50,000 items for one large customer. Regular-expression engines with backtracking can take exponential time on crafted inputs (the "ReDoS" class of incidents, such as Cloudflare's global outage in July 2019, caused by a regex with catastrophic backtracking). Hash-flooding attacks, which send many colliding keys to make a server's hash tables degrade to linear scans, are why languages randomised their hash functions around 2011–2012. The habit this lesson builds — asking "what happens when n is a thousand times bigger?" — is the same habit that prevents those incidents.

Measure complexity instead of trusting it, and see a hidden O(n) cost with your own eyes. Uses only the Python standard library.

  1. Save as growth.py: 
    import time, random
from collections import deque

def timed(f, n):
    t = time.perf_counter(); f(n); return time.perf_counter() - t

def list_membership(n):
    seen = []
    for i in range(n):
        if i in seen: pass       # O(n) scan each time
        seen.append(i)

def set_membership(n):
    seen = set()
    for i in range(n):
        if i in seen: pass       # O(1) average
        seen.add(i)

def pop_front_list(n):
    q = list(range(n))
    while q: q.pop(0)            # O(n) each

def pop_front_deque(n):
    q = deque(range(n))
    while q: q.popleft()         # O(1) each

for f in (list_membership, set_membership, pop_front_list, pop_front_deque):
    a, b = timed(f, 5_000), timed(f, 10_000)
    print(f"{f.__name__:18} n=5k {a:.4f}s  n=10k {b:.4f}s  ratio {b/a:.1f}")
  2. Run python growth.py. Look at the ratio column: doubling n should roughly double the time for an O(n) total (ratio ≈ 2) and roughly quadruple it for O(n²) (ratio ≈ 4).
  3. Expect list_membership to show a ratio near 4 and set_membership near 2. pop_front_list may look closer to linear at these sizes, because CPython's memmove is very fast; increase n to 100,000 and 200,000 for it and the quadratic ratio appears.
  4. Change one function to use slicing in a loop (q = q[1:]) and predict its ratio before running.

What this proves: the class shows up in how time scales, not in a single timing; and constant factors (C-level memmove) can hide a bad class at small n — which is exactly why tests on small data miss complexity bugs.

Read the constraints, choose the approach

Three problems, each with only its constraints shown. For each, say the complexity you are aiming for and the kind of technique it suggests. (a) "Given n ≤ 18 tasks and a compatibility matrix, find the largest set of mutually compatible tasks." (b) "Given an array of n ≤ 2 × 10⁵ integers, answer q ≤ 2 × 10⁵ queries for the sum of a[l..r]." (c) "Given a number n ≤ 10¹², find the smallest x such that x² ≥ n."

Answer

(a) n ≤ 18 means O(2ⁿ · n) ≈ 4.7 × 10⁶ is fine: enumerate all subsets as bitmasks (or backtrack with pruning) and check compatibility; the problem (maximum clique) has no known polynomial algorithm, and the constraint tells you none is expected. (b) Answering each query by looping over l..r is O(n · q) = 4 × 10¹⁰, far too slow. With 2 × 10⁵ of each, we want O(n + q) or O((n + q) log n). Since there are no updates, a prefix-sum array (al3) answers each query in O(1) after O(n) preprocessing: sum = pre[r+1] − pre[l]. If the array also changed between queries, a Fenwick tree (al27) would give O(log n) per operation. (c) n ≤ 10¹² means even O(n) is too slow, and O(√n) = 10⁶ is fine but there is better: the condition x² ≥ n is monotone in x (false, false, …, true, true), so binary search on x over [0, 10⁶] finds it in about 20 steps — O(log n). Use integer arithmetic (math.isqrt in Python) to avoid floating-point error near perfect squares.
