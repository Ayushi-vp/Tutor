Ask a programmer to count the ways to climb a staircase of 40 steps, taking one or two steps at a time, and the natural first answer is a recursive function: the ways to reach step n are the ways to reach n − 1 plus the ways to reach n − 2. It is correct, elegant — and it takes several seconds for n = 40 and hours for n = 60. The reason is that the recursion recomputes the same values again and again: ways(38) is computed once inside ways(40) directly and again inside ways(39); ways(37) is computed three times; ways(20) about ten thousand times. The tree of calls has roughly 1.6ⁿ nodes, but there are only n different questions being asked.

Write each answer down the first time you compute it, and the second time just read it. The same function, with a cache, does 40 calculations instead of 300 million. That is dynamic programming: solve each distinct subproblem once, store the answer, and build bigger answers from smaller ones.

Dynamic programming has a reputation as the hardest interview topic, and the reputation is earned in one specific way: for a new problem, it is not obvious what the subproblems are. Once you know that "dp[i] is the best total using the first i houses", House Robber is three lines. Finding that sentence is the skill. This lesson therefore focuses on how to find the state — a five-step recipe applied again and again — rather than on memorising solutions.

We start from the recursion and its exponential blow-up, introduce memoisation (top-down) and tabulation (bottom-up), and then work through the one-dimensional classics: Climbing Stairs, House Robber and its circular variant, Coin Change, Decode Ways, Word Break, Longest Increasing Subsequence (including the O(n log n) method), Maximum Product Subarray and the reductions behind Perfect Squares and Delete and Earn. Two-dimensional DP over grids and strings follows in al22, and advanced state designs in al23.

The mental model: a notebook of answers

Imagine you are asked a hard question, and to answer it you must ask yourself several easier questions, which in turn need even easier ones. If you keep a notebook and write down every answer the moment you find it, you never have to work anything out twice — and if the same easy question comes up in a hundred places, it costs you one calculation and ninety-nine lookups. Dynamic programming is exactly that notebook.

Two conditions make the notebook worth keeping. Overlapping subproblems: the same smaller questions really do come up many times (in merge sort they do not — each half is sorted once — so there is nothing to cache). Optimal substructure: the answer to a big question can be built from the answers to smaller ones — the best way to climb to step 40 combines the best ways to reach steps 39 and 38.

Two ways to fill the notebook

Top-down (memoisation): write the natural recursive function, and add a cache so that each argument is computed once. In Python, the decorator @functools.cache does it in one line. You only compute subproblems that are actually reached.

Bottom-up (tabulation): decide an order in which every subproblem's dependencies come first (for stairs, increasing n), and fill a table with a loop. No recursion, so no recursion-depth limit, and it is easy to see when only the last few entries are needed — then you keep just those, in a few variables.

Both cost the same: (number of distinct states) × (work to combine one state). For stairs, n states × O(1) work = O(n). That formula is how you will analyse every DP in this track.

A short worked count shows how dramatic the difference is. For n = 40 the plain recursion makes about 330 million calls; the memoised version makes 41. For n = 100 the plain version would make more calls than there are nanoseconds since the universe began; the memoised version makes 101. Nothing about the logic changed — only the decision to remember answers.

Where the notebook analogy breaks: a notebook works for any question, but DP only helps when the answer to a subproblem does not depend on how you reached it. In Word Search (al13), "can I finish the word from this cell?" depends on which cells the current path has already used, so there is no reusable answer to write down — the state would have to include the whole path, and there are too many paths. The art of DP is finding a small description of a subproblem that captures everything the future depends on. That description is the state.

From recursion to DP in three steps

# 1. Plain recursion: correct, exponential
def ways(n):
    if n <= 1: return 1
    return ways(n - 1) + ways(n - 2)

# 2. Memoised: each n computed once, O(n)
from functools import cache
@cache
def ways(n):
    if n <= 1: return 1
    return ways(n - 1) + ways(n - 2)

# 3. Tabulated with rolling variables: O(n) time, O(1) space
def ways(n):
    a, b = 1, 1                    # ways(0), ways(1)
    for _ in range(n - 1):
        a, b = b, a + b
    return b

This progression — recursion, then cache, then table, then rolling variables — is the standard way to arrive at a DP in an interview. Starting from the recursion makes the recurrence obvious and correct; the later steps are mechanical optimisations. Say each step out loud; interviewers value seeing you derive the DP rather than recite it.

The five-step recipe

For every DP problem, write down these five things before coding:

  1. State: what does dp[i] mean, in one precise sentence? ("dp[i] = the maximum money robbable from houses 0..i.")
  2. Recurrence: how is dp[i] computed from smaller states? Usually by considering the last decision.
  3. Base cases: the smallest states, whose answers are known directly.
  4. Order: an evaluation order in which every dependency is computed first.
  5. Answer: which state (or combination, like the maximum over all i) is the final result?

The most useful trick for step 2 is to think about the last decision. For stairs: the last move was a 1-step or a 2-step. For house robbing: the last house was robbed or skipped. For coin change: the last coin was one of the denominations. Each option leaves a smaller instance of the same problem, and the recurrence combines them — with + for counting problems, min or max for optimisation problems, or "or" for feasibility problems.

House Robber: take or skip

Houses in a row hold amounts of money; robbing two adjacent houses triggers an alarm. Maximise the loot. State: dp[i] = the most you can rob from houses 0..i. Last decision at house i: skip it (then the best is dp[i − 1]) or rob it (then house i − 1 must be skipped: dp[i − 2] + nums[i]).

def rob(nums):
    prev2, prev1 = 0, 0               # dp[i-2], dp[i-1]
    for x in nums:
        prev2, prev1 = prev1, max(prev1, prev2 + x)
    return prev1

Trace [2, 7, 9, 3, 1]: dp = 2, 7, 11 (2 + 9), 11 (max(11, 7 + 3)), 12 (11 + 1). Answer 12 (houses 0, 2, 4). Starting the rolling variables at 0 handles the base cases without special code. House Robber II puts the houses in a circle, so the first and last are adjacent. Any valid plan skips at least one of them, so run the line version twice — once on nums[1:] and once on nums[:-1] — and take the max (with a special case for a single house).

Delete and Earn looks different but reduces to House Robber: taking value v earns v for every copy and forbids v − 1 and v + 1. Sum the points per value, and you are choosing non-adjacent values to maximise total points.

Coin Change: minimise over choices

Fewest coins to make an amount, with unlimited coins of each denomination. State: dp[a] = the fewest coins that make amount a. Last decision: the last coin was some denomination c, leaving a − c. So dp[a] = 1 + min over c ≤ a of dp[a − c]. Base case dp[0] = 0. Amounts that cannot be made stay at infinity.

def coin_change(coins, amount):
    INF = float("inf")
    dp = [0] + [INF] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a and dp[a - c] + 1 < dp[a]:
                dp[a] = dp[a - c] + 1
    return -1 if dp[amount] == INF else dp[amount]

Trace coins [1, 3, 4], amount 6: dp[0..6] = 0, 1, 2, 1, 1, 2, 2. dp[6] = 1 + min(dp[5], dp[3], dp[2]) = 1 + min(2, 1, 2) = 2 (two 3s). The greedy answer (4 + 1 + 1) is three coins — which is why this is a DP problem. Complexity O(amount × number of coins). Perfect Squares is the same algorithm with the squares 1, 4, 9, … as coins.

A counting variant, "how many combinations make the amount" (Coin Change II), uses + instead of min — but must avoid counting the same combination in different orders, which changes the loop order; that subtlety belongs to knapsack problems in al22.

Decode Ways: counting with validity rules

Digits map to letters (1 → A, …, 26 → Z); count the ways to decode a digit string. State: dp[i] = the number of ways to decode the first i characters. Last decision: the last letter used either the final one digit or the final two digits.

def num_decodings(s):
    prev2, prev1 = 1, 1 if s and s[0] != "0" else 0   # dp[0], dp[1]
    for i in range(2, len(s) + 1):
        cur = 0
        if s[i - 1] != "0":                 # one-digit letter 1..9
            cur += prev1
        if "10" <= s[i - 2:i] <= "26":      # two-digit letter 10..26
            cur += prev2
        prev2, prev1 = prev1, cur
    return prev1

Zeros are the whole difficulty: "0" cannot stand alone, so "06" is not decodable as one letter, and "30" has no valid two-digit reading. Trace "226": dp = 1 (empty), 1 ("2"), 2 ("2,2" or "22"), 3 ("2,2,6", "22,6", "2,26"). Comparing two-character strings with "10" ≤ x ≤ "26" works because both have exactly two digits.

Word Break: DP over prefixes

Can a string be split into words from a dictionary? State: dp[i] = whether the first i characters can be segmented. Last decision: the last word is s[j:i] for some j. So dp[i] is true if some j has dp[j] true and s[j:i] in the dictionary.

def word_break(s, words):
    wordset, maxlen = set(words), max(map(len, words), default=0)
    dp = [True] + [False] * len(s)
    for i in range(1, len(s) + 1):
        for j in range(max(0, i - maxlen), i):
            if dp[j] and s[j:i] in wordset:
                dp[i] = True; break
    return dp[len(s)]

Limiting j to within the longest word length avoids checking impossible splits. This is the DP that backtracking turns into when you memoise on the start index (al13): the answer for a suffix never depends on how the prefix was split.

Longest Increasing Subsequence: two solutions

A subsequence keeps the original order but may skip elements. The LIS of [10, 9, 2, 5, 3, 7, 101, 18] has length 4 (for example 2, 3, 7, 18).

O(n²) DP. State: dp[i] = the length of the longest increasing subsequence ending at index i. "Ending at i" is the crucial choice — it tells you the last element, so you know which earlier elements can precede it. Recurrence: dp[i] = 1 + max(dp[j]) over j < i with nums[j] < nums[i] (or 1 if none). Answer: max over all i.

O(n log n) with tails. Keep an array tails where tails[k] is the smallest possible last element of an increasing subsequence of length k + 1 seen so far. This array is always sorted. For each x, find the first tail ≥ x with binary search and replace it with x (a subsequence of that length can now end lower, which can only help), or append x if it is larger than every tail (extending the longest subsequence).

import bisect
def length_of_lis(nums):
    tails = []
    for x in nums:
        i = bisect.bisect_left(tails, x)
        if i == len(tails): tails.append(x)
        else: tails[i] = x
    return len(tails)

For non-decreasing subsequences use bisect_right. To reconstruct the actual subsequence, also record, for each element, the index of its predecessor (the element at tails position i − 1 when it was placed) and walk back from the last element placed at the final length.

Maximum Product Subarray: carry two values

Kadane's algorithm (al3) tracks the best sum ending at each index. Products are different: multiplying by a negative number turns the smallest product into the largest. So the state must hold two values per index: the maximum and the minimum product of a subarray ending there.

def max_product(nums):
    hi = lo = best = nums[0]
    for x in nums[1:]:
        cands = (x, hi * x, lo * x)
        hi, lo = max(cands), min(cands)    # computed from the old hi and lo together
        best = max(best, hi)
    return best

Trace [2, 3, −2, 4]: (hi, lo) = (2, 2) → (6, 3) → (−2, −12) → (4, −48); best = 6. With [−2, 3, −4]: (−2, −2) → (3, −6) → (24, −12); best 24, found only because the minimum was carried. This is a general lesson: when one value per state is not enough to decide the future, add what is missing to the state.

Partition Equal Subset Sum: a preview of knapsack

"Can the array be split into two subsets with equal sums?" That is "is there a subset summing to total / 2?". State: reachable[s] = whether some subset of the elements processed so far sums to s. For each number x, every reachable s makes s + x reachable. Iterating s from high to low ensures each number is used at most once.

def can_partition(nums):
    total = sum(nums)
    if total % 2: return False
    target = total // 2
    reach = [True] + [False] * target
    for x in nums:
        for s in range(target, x - 1, -1):   # backwards: each x used once
            reach[s] = reach[s] or reach[s - x]
    return reach[target]

This is the 0/1 knapsack pattern, developed fully in al22. O(n × target) time, O(target) space.

Counting, optimising and deciding: three flavours of the same recurrence

The same subproblem structure supports three kinds of question, and the only change is how options are combined. For "how many ways?" add the options (Climbing Stairs, Decode Ways). For "what is the best?" take a min or max (House Robber, Coin Change). For "is it possible?" take a logical or (Word Break, Partition Equal Subset Sum). Recognising which flavour you need tells you the combining operator and the identity value for impossible states: 0 for counting, infinity (or minus infinity) for optimising, false for deciding. Mixing them up — for instance initialising a min-DP's impossible states to 0 — is a common source of wrong answers.

Recognising the pattern

Suspect DP when the problem asks for a count of ways, a minimum or maximum, or whether something is possible, over choices made in sequence; when the brute force is a recursion with repeated arguments; or when greedy fails on a small example. Then run the five-step recipe, starting from "what is the last decision?".

Finding the state: what does the future depend on?

The state must contain exactly the information that the remaining decisions depend on. In House Robber, the future (houses i + 1 onward) depends only on whether house i was robbed — and that is folded into "best total up to i, with i possibly robbed", because the recurrence looks back two steps. In Maximum Product Subarray, the future depends on both the largest and smallest product ending at i, so both go in the state. In stock problems with a cooldown (al23), the future depends on whether you hold a share and whether you sold yesterday, so the state is (day, holding, cooling). A useful test: if two different histories lead to the same state, must the best continuation be the same? If not, the state is missing information. And if the state space is too large to fit the constraints, look for information you can drop.

DP as a shortest path on a DAG

Every DP is a computation on a directed acyclic graph: states are vertices, and an edge from state A to state B means "B's value uses A's". Optimisation DPs are shortest or longest paths on that DAG, counting DPs count paths, and the evaluation order is a topological order (al18). Coin Change is the shortest path from amount 0 to the target in a graph where each coin is an edge of weight 1. This view explains why DP needs acyclic dependencies — a cycle would mean a state depends on itself — and why some problems can be solved either by DP or by BFS/Dijkstra (Perfect Squares, Coin Change) with the same complexity.

Reconstructing the solution, not just its value

Interviews often ask for the actual choice: which houses, which coins, which subsequence. Two methods. Store a parent pointer alongside each dp entry (the choice that achieved the optimum) and walk back from the answer. Or recompute: starting from the final state, check which option in the recurrence achieves the stored value and step into it. Both add O(states) memory or time. Rolling-variable space optimisations usually destroy the information needed for reconstruction, so if the path is required, keep the full table (or keep parent pointers only).

Why the tails method for LIS is correct

Two invariants carry it. First, tails is strictly increasing: if tails[k] ≥ tails[k + 1] for some k, the subsequence ending at tails[k + 1] would contain a length-(k + 1) prefix ending at something smaller than tails[k + 1] ≤ tails[k], contradicting tails[k] being the smallest such end. Second, after processing a prefix, tails[k] is the minimum possible end of a length-(k + 1) increasing subsequence in that prefix: placing x at position i = bisect_left(tails, x) extends the best length-i subsequence (whose end tails[i − 1] < x) and can only lower tails[i]. The method is known as patience sorting, after a card game in which you deal cards onto piles; the number of piles is the LIS length. It generalises: the number of strictly increasing piles needed to cover a sequence equals the length of its longest non-increasing subsequence (a consequence of Dilworth's theorem).

When memoisation is not enough: exponential states

Memoisation only helps if the number of distinct states is manageable. A recursion whose arguments include a whole set or path (which items have been used, which cells visited) can have exponentially many distinct states, and caching them all just converts exponential time into exponential memory. Sometimes the set can be encoded compactly — a bitmask for up to about 20 items gives 2²⁰ ≈ 10⁶ states, which is fine (bitmask DP, al23) — and sometimes it cannot, in which case the problem needs backtracking with pruning or a cleverer formulation. Estimating the state count before writing the memoised function is the habit that prevents surprises.

Top-down pitfalls in Python

@functools.cache makes memoisation trivial, but three things bite. Recursion depth: a memoised function on n = 10⁵ recurses 10⁵ deep and raises RecursionError — tabulate instead, or raise the limit with care. Unhashable arguments: lists cannot be cache keys; pass indices or tuples. Cache lifetime: a module-level cached function keeps its cache across test cases, which can exhaust memory or, if the function closes over changing data, return stale answers; define the cached function inside the solving function so the cache is fresh each call, or call cache_clear().

In the interview room

The most effective approach is to narrate the recipe: "Let dp[i] be …; the last decision is …; so dp[i] = …; base cases …; I'll fill i from small to large; the answer is …". Writing those five lines before code turns a scary DP problem into a structured one, and it is exactly what interviewers want to hear. If you do not see the state immediately, start with the brute-force recursion, identify its arguments, and add memoisation — a correct top-down DP is a perfectly good answer, and you can tabulate afterwards.

The common bugs: an off-by-one between "first i elements" and "up to index i" (pick one convention and say it); wrong base cases (Decode Ways with a leading '0'; Coin Change initialising dp[0] to infinity); using a sentinel like −1 for "impossible" and then taking a min over it (use infinity); iterating the wrong way in 0/1 knapsack (forwards reuses items); updating rolling variables in the wrong order (compute the new value from the old ones, then shift, or use tuple assignment). Test with the smallest inputs (empty, one element) and a case where greedy fails.

State complexity in the "states × work per state" form: "amount × coins states-transitions, so O(amount · k) time, O(amount) space". Expect follow-ups that change the state: "now houses are in a circle", "now return the coins used", "now amounts go up to 10⁹" (DP over amounts is pseudo-polynomial, so it no longer works — look for math or a different method).

A final interview habit: when you finish, say what would make the DP impossible. "This works because amount is at most 10⁴; if amounts were up to 10⁹ the table could not fit and I'd need a different idea." That one sentence shows you understand the pseudo-polynomial nature of many DPs and is a common senior-level probe.

On online assessments, DP problems often come with constraints that point to the state size: n ≤ 10⁵ suggests a 1D DP with O(1) or O(log n) transitions; n ≤ 5,000 allows O(n²); a value bound like "amount ≤ 10⁴" suggests DP over values. Matching the constraint to the state count before coding saves you from writing a correct DP that times out.

In real systems

Dynamic programming runs inside many systems you use daily. Diff tools (git diff, code review views) align two files with a longest-common-subsequence style DP, optimised by Myers' algorithm. Spell checkers and fuzzy search rank suggestions by edit distance, a two-dimensional DP (al22). Speech recognisers and part-of-speech taggers find the most likely sequence of hidden states with the Viterbi algorithm — a DP over (time, state). Bioinformatics aligns DNA and protein sequences with Needleman–Wunsch and Smith–Waterman, both DP. TeX breaks paragraphs into lines by minimising a "badness" score over all possible break points with the Knuth–Plass DP, which is why its paragraphs look better than greedy line-filling. Reinforcement learning's value iteration is Bellman's dynamic programming equation applied repeatedly. Richard Bellman, who coined the term in the 1950s, later wrote that he chose "dynamic programming" partly because it sounded impressive and was hard to object to — "programming" then meant planning, not coding.

    import random, bisect
from functools import cache
from itertools import combinations

calls = 0
def ways_plain(n):
    global calls; calls += 1
    return 1 if n <= 1 else ways_plain(n - 1) + ways_plain(n - 2)
ways_plain(25); print("plain recursion calls for n=25:", calls)

@cache
def ways_memo(n):
    return 1 if n <= 1 else ways_memo(n - 1) + ways_memo(n - 2)
ways_memo(25); print("memoised distinct calls:", ways_memo.cache_info().currsize)

def coin_dp(coins, amt):
    INF = float("inf"); dp = [0] + [INF] * amt
    for a in range(1, amt + 1):
        dp[a] = min((dp[a - c] + 1 for c in coins if c <= a), default=INF)
    return dp[amt]

def coin_brute(coins, amt, k=0):
    if amt == 0: return 0
    best = float("inf")
    for i in range(k, len(coins)):
        if coins[i] <= amt: best = min(best, 1 + coin_brute(coins, amt - coins[i], i))
    return best

def lis_fast(a):
    t = []
    for x in a:
        i = bisect.bisect_left(t, x)
        t[i:i+1] = [x]
    return len(t)

def lis_brute(a):
    return max([r for r in range(len(a) + 1) for c in combinations(a, r)
                if all(c[i] < c[i+1] for i in range(len(c) - 1))], default=0)

for _ in range(300):
    coins = random.sample(range(1, 8), random.randint(1, 3)); amt = random.randint(0, 20)
    assert coin_dp(coins, amt) == coin_brute(coins, amt)
    a = [random.randint(0, 6) for _ in range(random.randint(0, 9))]
    assert lis_fast(a) == lis_brute(a), a
print("coin change and LIS match brute force")

Find the state

"You are given costs for 1-day, 7-day and 30-day travel passes and a sorted list of days in the year (1–365) on which you will travel. Find the minimum total cost to cover all travel days." Apply the five-step recipe.

Answer

State: dp[d] = the minimum cost to cover all travel days up to and including day d (for d from 0 to 365, or to the last travel day). Recurrence: if d is not a travel day, dp[d] = dp[d − 1] (no need to buy anything new). If it is, the last pass bought covers day d and was one of three kinds: dp[d] = min(dp[d − 1] + cost1, dp[max(0, d − 7)] + cost7, dp[max(0, d − 30)] + cost30). Base case: dp[0] = 0. Order: d increasing. Answer: dp[last travel day]. Complexity O(365), O(365) space, or O(30) with a circular buffer. Trace with days [1, 4, 6, 7, 8, 20] and costs [2, 7, 15]: dp[1] = 2, dp[4] = 4, dp[6] = 6, dp[7] = min(8, 7, 15) = 7 (a 7-day pass covering days 1–7), dp[8] = min(9, dp[1] + 7 = 9, 15) = 9, dp[20] = 11. A greedy "buy the 7-day pass whenever you have 3+ trips in the week" can be wrong on other inputs; the DP considers every option. An alternative state indexes the travel-day list instead of calendar days (dp[i] over the i-th travel day, with binary search for how far a pass reaches), which matters if the calendar were much longer than 365 days.
