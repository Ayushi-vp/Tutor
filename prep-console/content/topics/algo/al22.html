Type "recieve" into a search box and it asks "did you mean receive?". To make that suggestion, the system needs to measure how close two words are: how many single-letter changes turn one into the other. Run git diff and it shows exactly which lines were added and removed between two versions of a file, not just "these files differ". A bioinformatics pipeline aligns a new DNA read against a reference genome, allowing for mutations and gaps. All three rest on the same idea: compare two sequences by filling a table whose rows are prefixes of one and whose columns are prefixes of the other.

One-dimensional DP (al21) handled a single sequence: the best answer up to index i. Many problems need two indices: the first i characters of one string against the first j of another; row r and column c of a grid; the first i items against a remaining capacity w. The tables get bigger, but the recipe is identical — define dp[i][j] in one sentence, think about the last decision, set the base cases, fill in a valid order — and the classic problems in this family are among the most frequently asked: Longest Common Subsequence, Edit Distance, Unique Paths, Maximal Square, the knapsack family (Partition Equal Subset Sum, Coin Change II, Target Sum), Distinct Subsequences, Interleaving String, palindromes and Regular Expression Matching.

This lesson covers three groups: grid DP, two-string DP and knapsack. It shows the table for each, traces the key recurrences, explains the subtle choices that make or break the knapsack variants (loop direction and loop order), and shows how to cut memory from a full table to a single row.

The mental model: filling a spreadsheet

Picture a spreadsheet where each cell's formula refers only to cells above it and to its left. You can fill it row by row, left to right, and every formula's inputs are ready when you reach it. That is a two-dimensional DP. The cell at row i, column j stores the answer to one subproblem; the formula is the recurrence; the first row and column are the base cases; the answer usually sits in the bottom-right corner.

For two strings a and b, the standard choice is: row i stands for the first i characters of a, column j for the first j characters of b, with an extra row 0 and column 0 for the empty prefixes. Then dp[i][j] answers the question for those two prefixes, and the last decision is about the last characters, a[i−1] and b[j−1]: do they match, and if not, which one do we drop or change?

Why the extra row and column for empty prefixes? Because the base cases live there. "The LCS of anything with the empty string is 0" and "turning a prefix of length i into the empty string takes i deletions" are the facts every other cell is built from. Including them as row 0 and column 0 means the main loop needs no special cases for the first character, which removes the most common source of off-by-one errors in string DP. The price is that the table indices are shifted by one from the string indices: cell (i, j) talks about characters a[i − 1] and b[j − 1]. Say that convention out loud once and stick to it.

Grids work the same way with physical rows and columns: if you may only move right or down, the best (or number of) paths to a cell depends only on the cell above and the cell to its left. Knapsack uses a table of items against capacities: row i means "using only the first i items", column w means "with capacity w".

Where the spreadsheet analogy breaks: a spreadsheet keeps every cell, but a DP often does not need to. If each row's formulas only read the previous row, you can overwrite as you go and keep two rows — or even one, with care about the order in which cells are overwritten. That is where most of the subtlety in this lesson lives, especially for knapsack, where the direction you sweep a single row decides whether items can be reused.

A final framing that ties these together: in every case, the table is a DAG of subproblems (al18), and filling it row by row is a topological order. Whenever you are unsure of a loop order, ask "when I compute this cell, have all the cells it reads already been computed?".

Grid DP: paths, costs and squares

Unique Paths: count the right/down paths from the top-left to the bottom-right of an m×n grid. The last move into (r, c) came from above or from the left: dp[r][c] = dp[r−1][c] + dp[r][c−1], with the first row and first column equal to 1. Since each row only reads the previous row and the current row's left neighbour, one row of memory suffices:

def unique_paths(m, n):
    row = [1] * n
    for _ in range(1, m):
        for c in range(1, n):
            row[c] += row[c - 1]        # row[c] was "above", row[c-1] is "left"
    return row[-1]

With obstacles (Unique Paths II), set dp to 0 at obstacle cells. Minimum Path Sum replaces + with min and adds the cell's cost: dp[r][c] = grid[r][c] + min(dp[r−1][c], dp[r][c−1]). These are DP rather than BFS because the right/down rule makes the grid a DAG; if four-directional moves were allowed, you would need Dijkstra (al20).

Maximal Square: the largest square of 1s in a binary matrix. Let dp[r][c] be the side of the largest all-ones square whose bottom-right corner is (r, c). If the cell is 1, the square can extend as far as the smallest of the squares ending above it, to its left and diagonally above-left — each of those limits it in one direction:

def maximal_square(matrix):
    R, C = len(matrix), len(matrix[0])
    dp, best = [0] * (C + 1), 0
    for r in range(R):
        prev_diag = 0                     # dp[r-1][c-1] before it is overwritten
        for c in range(1, C + 1):
            saved = dp[c]                 # this is dp[r-1][c]
            if matrix[r][c - 1] == "1":
                dp[c] = 1 + min(dp[c], dp[c - 1], prev_diag)
                best = max(best, dp[c])
            else:
                dp[c] = 0
            prev_diag = saved
    return best * best

The one-row version needs the diagonal value, which has already been overwritten by the time you need it; saving it in a variable before overwriting is the standard trick, and it appears again in edit distance.

Longest Common Subsequence

State: dp[i][j] = the length of the longest common subsequence of a[:i] and b[:j]. Last decision: if a[i−1] == b[j−1], the best common subsequence of these prefixes can end with that shared character, so dp[i][j] = dp[i−1][j−1] + 1. If they differ, at least one of them is not in the best subsequence, so drop one: dp[i][j] = max(dp[i−1][j], dp[i][j−1]). Base cases: an empty prefix has LCS 0.

def lcs(a, b):
    n, m = len(a), len(b)
    dp = [[0] * (m + 1) for _ in range(n + 1)]
    for i in range(1, n + 1):
        for j in range(1, m + 1):
            if a[i - 1] == b[j - 1]:
                dp[i][j] = dp[i - 1][j - 1] + 1
            else:
                dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])
    return dp[n][m]

On the figure's strings, ABCBDAB and BDCAB, the answer is 4. To recover a subsequence, start at dp[n][m] and walk back: if the characters match, record the character and move diagonally; otherwise move to whichever neighbour (up or left) holds the larger value. O(n·m) time and space, or O(min(n, m)) space for the length alone.

Edit Distance

The minimum number of insertions, deletions and substitutions that turn a into b. State: dp[i][j] = the edit distance between a[:i] and b[:j]. Base cases: turning a[:i] into an empty string takes i deletions (dp[i][0] = i); building b[:j] from nothing takes j insertions (dp[0][j] = j). Last decision: if a[i−1] == b[j−1], no edit is needed for them: dp[i][j] = dp[i−1][j−1]. Otherwise, the last operation was one of three, each costing 1:

  • delete a[i−1]: dp[i−1][j] + 1
  • insert b[j−1] at the end: dp[i][j−1] + 1
  • substitute a[i−1] with b[j−1]: dp[i−1][j−1] + 1
def min_distance(a, b):
    n, m = len(a), len(b)
    prev = list(range(m + 1))              # row i-1; starts as row 0
    for i in range(1, n + 1):
        cur = [i] + [0] * m
        for j in range(1, m + 1):
            if a[i - 1] == b[j - 1]:
                cur[j] = prev[j - 1]
            else:
                cur[j] = 1 + min(prev[j], cur[j - 1], prev[j - 1])
        prev = cur
    return prev[m]

"horse" → "ros" has distance 3: replace h with r (rorse), delete r (rose), delete e (ros). Two rows of memory suffice. If only insertions and deletions are allowed, the distance is n + m − 2·LCS(a, b): every character outside the LCS must be deleted from a or inserted from b.

Counting with two strings: Distinct Subsequences

"How many distinct ways does t appear as a subsequence of s?" (for example, "rabbbit" contains "rabbit" in 3 ways, choosing which b to drop). State: dp[i][j] = the number of ways t[:j] appears as a subsequence of s[:i]. Last decision about s[i−1]: either do not use it (dp[i−1][j] ways), or, if it equals t[j−1], use it to match the last character of t[:j] (dp[i−1][j−1] ways). Add them — it is a counting problem. Base cases: dp[i][0] = 1 (the empty t appears once in anything), dp[0][j] = 0 for j > 0.

With one row, iterate j downwards so that dp[j − 1] still holds the previous row's value when it is read — the same direction trick as 0/1 knapsack below.

Feasibility with two strings: Interleaving String

"Is s3 formed by interleaving s1 and s2, keeping each one's character order?" State: dp[i][j] = whether s3[:i + j] can be formed from s1[:i] and s2[:j]. The last character of s3[:i + j] came either from s1 (needs dp[i−1][j] and s1[i−1] == s3[i+j−1]) or from s2 (needs dp[i][j−1] and s2[j−1] == s3[i+j−1]). It is a logical-or DP. Check len(s1) + len(s2) == len(s3) first. A greedy that takes from whichever string matches fails when both match — the DP is needed precisely to explore both options.

Palindromes

Longest palindromic substring: a palindrome mirrors around its centre, which is either a character (odd length) or a gap between two characters (even length). Expanding around each of the 2n − 1 centres while the ends match finds the longest in O(n²) time and O(1) space — usually simpler than a table.

def longest_palindrome(s):
    best = ""
    for center in range(2 * len(s) - 1):
        l, r = center // 2, (center + 1) // 2      # odd: l == r; even: r = l + 1
        while l >= 0 and r < len(s) and s[l] == s[r]:
            l -= 1; r += 1
        if r - l - 1 > len(best):
            best = s[l + 1:r]
    return best

The DP formulation, pal[i][j] = (s[i] == s[j]) and pal[i+1][j−1], filled by increasing length, is useful when you need all palindromic substrings (counting them, or palindrome partitioning in al13 and al23). Longest palindromic subsequence (not contiguous) is LCS of the string and its reverse, or dp[i][j] over the substring s[i..j] filled by increasing length.

The knapsack family

Knapsack problems choose items with weights (and maybe values) under a capacity. The 2D state is dp[i][w] = the best value using the first i items with capacity w. The last decision is about item i: skip it (dp[i−1][w]) or take it (dp[i−1][w − wt_i] + val_i, if it fits). In one dimension the row for item i is computed from the row for item i − 1 in place — and the direction of the capacity loop decides which problem you solve.

# 0/1 knapsack: each item at most once  -> capacity DOWNWARDS
for wt, val in items:
    for w in range(W, wt - 1, -1):
        dp[w] = max(dp[w], dp[w - wt] + val)

# unbounded knapsack: items reusable    -> capacity UPWARDS
for wt, val in items:
    for w in range(wt, W + 1):
        dp[w] = max(dp[w], dp[w - wt] + val)

Partition Equal Subset Sum (al21) is 0/1 feasibility with target total/2. Target Sum (assign + or − to each number) reduces to it: if P is the sum of the numbers given +, then P − (total − P) = target, so P = (total + target)/2, and the answer is the number of subsets summing to P — 0/1 counting, capacity downwards, with ways[0] = 1.

Counting problems add one more subtlety: combinations versus permutations. Coin Change II asks how many combinations of coins make an amount — {1, 2} and {2, 1} are the same. Put the coins in the outer loop: each combination is then built in a fixed coin order, so it is counted once.

def change(amount, coins):          # combinations
    ways = [1] + [0] * amount
    for c in coins:                 # outer: coins
        for a in range(c, amount + 1):
            ways[a] += ways[a - c]
    return ways[amount]

Combination Sum IV asks how many ordered sequences sum to a target — (1, 2) and (2, 1) are different. Put the total in the outer loop, so that at every total every number can be the last one added: for t in range(1, target + 1): for x in nums: if x <= t: ways[t] += ways[t − x]. Swapping the two loops swaps the answers; for coins [1, 2] and amount 3, combinations give 2 ({1,1,1}, {1,2}) and sequences give 3 (111, 12, 21).

Regular Expression Matching

Match a string s against a pattern p containing '.' (any character) and '*' (zero or more of the preceding element). State: dp[i][j] = whether s[:i] matches p[:j]. If p[j−1] is a letter or '.', it must match s[i−1] and the rest must match: dp[i−1][j−1]. If p[j−1] is '*' (applying to p[j−2]), there are two options: use zero copies — skip the "x*" pair: dp[i][j−2]; or use one more copy — if s[i−1] matches p[j−2], consume s[i−1] and stay on the same pattern position: dp[i−1][j]. The base case dp[0][j] handles patterns like "a*b*" that match the empty string: dp[0][j] = dp[0][j−2] when p[j−1] is '*'. O(n·m). This is the same table as edit distance with different rules — the general lesson is that once you can do prefix DP on two strings, many "hard" string problems become a few recurrence lines.

Recognising the pattern

Two indices: two strings or sequences compared (match, align, transform, interleave, subsequence counts), a grid with monotone moves, or items against a capacity. Write dp[i][j] in one sentence, decide what happens to the last element(s), add the empty-prefix row and column, and check whether one row of memory suffices. For knapsack, decide once/reusable (loop direction) and combinations/sequences (loop order) before coding.

Linear-space reconstruction: Hirschberg's trick

Two rows are enough to compute an LCS length or an edit distance, but reconstructing the alignment seems to need the whole n×m table — 10⁸ cells for two 10⁴-character strings. Hirschberg's algorithm (1975) recovers it in O(n + m) space and O(n·m) time by divide and conquer: compute the last row of the DP for the first half of a against b, and the last row for the reversed second half of a against reversed b; the column j that maximises the sum of the two is where an optimal alignment crosses the middle row; recurse on the two halves. The total work is about twice the plain DP. Bioinformatics tools use this idea to align long sequences without exhausting memory.

How diff actually works

LCS-based diff on n-line files is O(n·m), too slow for large files that differ only slightly. Myers' algorithm (1986), the default in git, views the problem as a shortest path in the "edit graph" (the same grid as the LCS table, where diagonal moves on matching lines are free) and explores it by increasing number of edits D, giving O((n + m)·D) — fast when the files are similar, which they usually are. Git also offers "patience" and "histogram" diffs, which anchor on lines that appear exactly once in both files to produce more human-readable diffs. Python's difflib uses yet another approach (a Ratcliff–Obershelp-style longest-matching-block heuristic), which is why its output can differ from git's.

Edit distance variants

Real spell checkers tune the basic recurrence. Damerau–Levenshtein adds transposition of adjacent characters ("teh" → "the" costs 1), one extra case looking back two positions. Weighted edit distance gives different costs to different operations — substituting keys that are adjacent on a keyboard is cheaper. When only small distances matter (say, at most k = 2), a banded DP fills only cells with |i − j| ≤ k, cutting the work to O(k·n); Levenshtein automata go further and test a whole dictionary against a word in linear time, which is how Lucene implements fuzzy queries.

Knapsack is NP-hard, and why the DP is still fine

The 0/1 knapsack decision problem is NP-complete, yet the DP solves it in O(n·W). There is no contradiction: W is a number, and the input encodes it in log W bits, so O(n·W) is exponential in the input size — pseudo-polynomial. With W up to 10⁴ or 10⁵ the DP is fast; with W up to 10¹⁸ it is useless. For large W and small n (n ≤ 40), meet in the middle (al13) works; for large W with small values, swap the roles and do DP over value (dp[v] = the minimum weight achieving value v). For feasibility questions such as subset sum, a Python integer used as a bitset — bits |= bits << x for each item — performs the whole capacity loop in machine words, often 50 times faster than the list version.

Scoring alignments: from edit distance to Needleman–Wunsch

Bioinformatics generalises edit distance with a scoring scheme: a match earns a positive score, a mismatch costs according to a substitution matrix (some amino-acid swaps are common and cheap, others rare and expensive), and gaps cost a penalty that often has an "opening" cost plus a smaller "extension" cost per character (affine gaps, which need three DP tables instead of one). Needleman–Wunsch maximises the score over a global alignment; Smith–Waterman finds the best local alignment by allowing any cell to restart at zero and taking the best cell anywhere in the table. Interview questions rarely go this far, but recognising that "edit distance with weights" is the same table with different costs shows that you understand the recurrence rather than memorising it.

Choosing the fill order for interval-like 2D tables

Not every 2D table is filled row by row. For palindromes and other problems on a substring s[i..j], dp[i][j] depends on dp[i+1][j−1], dp[i+1][j] or dp[i][j−1] — shorter substrings — so the table must be filled by increasing length (or i from n−1 down to 0 with j increasing). Getting this wrong reads uncomputed cells and silently produces garbage. This "fill by length" order is the hallmark of interval DP, developed in al23 for problems like Burst Balloons, where the split point inside the interval is the last decision.

In the interview room

For two-string problems, say the state with the prefix convention explicitly: "dp[i][j] is the edit distance between the first i characters of word1 and the first j of word2, so dp has (n + 1) × (m + 1) cells and row 0 means the empty prefix." That one sentence prevents most index bugs. The common mistakes: forgetting the empty-prefix row and column (and then special-casing i = 0 everywhere); indexing the strings with i instead of i − 1; wrong base cases (edit distance needs i and j, not 0; Distinct Subsequences needs dp[i][0] = 1); in one-row versions, overwriting the diagonal before reading it; and in knapsack, the wrong loop direction or loop order. Test with an empty string, identical strings and completely different strings.

Expect the space follow-up ("can you use less memory?" — rolling rows, and what you lose: reconstruction) and the reconstruction follow-up ("return the actual LCS / the edits"). For knapsack, interviewers love asking why the loop goes backwards; answer with the "it still holds the previous item's value" explanation. For Coin Change II versus Combination Sum IV, have the two-coin example ready to show why loop order changes the count.

Complexity is states × transitions: O(n·m) for two strings, O(R·C) for grids, O(n·W) for knapsack — and mention that the last is pseudo-polynomial, which is why constraints on W matter.

On online assessments, two-string DP problems are often disguised: "minimum operations to make two lists equal", "how many ways to form a word from a sequence of letter tiles", "can this log be produced by merging these two traces". Look for two sequences whose prefixes interact; that is the signal for a dp[i][j] table.

A final practical tip: when a 2D recurrence feels slippery, fill a 4×4 corner of the table by hand on a tiny example before coding, including row 0 and column 0. It takes two minutes, catches wrong base cases and wrong neighbour choices immediately, and gives you a test case to trace the code against afterwards.

In real systems

These tables run in tools you use every day. Git's diff is built on Myers' edit-graph algorithm, a shortest-path view of the LCS table. Spell checkers and search engines rank corrections by edit distance (often Damerau–Levenshtein), and Lucene's fuzzy queries use Levenshtein automata to match terms within distance 1 or 2. Bioinformatics aligns DNA and protein sequences with Needleman–Wunsch (global alignment, an edit-distance DP with scoring) and Smith–Waterman (local alignment), and with banded and seeded heuristics such as BLAST for genome-scale searches. Plagiarism detection and code-similarity tools compare token sequences with LCS-like measures. Knapsack formulations appear in resource allocation — choosing which features fit a release, which ads fit a budget, which cache entries to keep under a memory limit — usually solved with DP when capacities are small and with heuristics or integer programming when they are not.

    import random
from functools import cache
from itertools import combinations

def edit_dp(a, b):
    prev = list(range(len(b) + 1))
    for i in range(1, len(a) + 1):
        cur = [i] + [0] * len(b)
        for j in range(1, len(b) + 1):
            cur[j] = prev[j-1] if a[i-1] == b[j-1] else 1 + min(prev[j], cur[j-1], prev[j-1])
        prev = cur
    return prev[-1]

def edit_rec(a, b):
    @cache
    def go(i, j):
        if i == 0: return j
        if j == 0: return i
        if a[i-1] == b[j-1]: return go(i-1, j-1)
        return 1 + min(go(i-1, j), go(i, j-1), go(i-1, j-1))
    return go(len(a), len(b))

def knap(items, W, downwards):
    dp = [0] * (W + 1)
    for wt, val in items:
        rng = range(W, wt - 1, -1) if downwards else range(wt, W + 1)
        for w in rng: dp[w] = max(dp[w], dp[w - wt] + val)
    return dp[W]

def knap_01_brute(items, W):
    return max(sum(v for _, v in s) for r in range(len(items) + 1)
               for s in combinations(items, r) if sum(w for w, _ in s) <= W)

Design the table

"Given two strings, find the minimum ASCII sum of deleted characters needed to make them equal." Define the state, recurrence and base cases, give the complexity, and explain how it relates to LCS.

Answer

State: dp[i][j] = the minimum total ASCII value of characters deleted from s1[:i] and s2[:j] to make the two prefixes equal. Base cases: dp[0][j] = sum of ord(c) for c in s2[:j] (delete everything in s2's prefix); dp[i][0] = sum of ord(c) for c in s1[:i]. Recurrence: if s1[i−1] == s2[j−1], keep both: dp[i][j] = dp[i−1][j−1]. Otherwise delete one of the last characters: dp[i][j] = min(dp[i−1][j] + ord(s1[i−1]), dp[i][j−1] + ord(s2[j−1])). Answer: dp[n][m]. O(n·m) time, O(m) space with two rows. Relation to LCS: the characters you keep form a common subsequence, so the problem is equivalent to finding the common subsequence with the maximum ASCII sum ("weighted LCS"), and the answer is (ASCII sum of s1) + (ASCII sum of s2) − 2 × (that maximum). Writing it either way is correct; the direct deletion DP avoids the extra step. For "sea" and "eat": keep "ea", delete s (115) and t (116), total 231.
