"Return the number of ways, modulo 10⁹ + 7." Many counting problems end with that sentence, and many candidates lose points there — not on the algorithm, but on the arithmetic: dividing residues directly, forgetting to reduce after a multiplication, getting negative results from a subtraction. Other problems give an n up to 10¹⁵ and ask for something that obviously needs n steps, which is only possible with a closed formula and fast exponentiation. Still others are about gcds, primes, digits, or recurring decimals, or ask you to shuffle or sample "uniformly at random" — where a plausible-looking implementation is subtly biased.

None of this is advanced mathematics. It is a toolkit of a dozen facts and five or six algorithms that every competitive programmer and most strong interviewees know cold: modular arithmetic and inverses, binary exponentiation, Euclid's algorithm, the sieve of Eratosthenes, combinations with precomputed factorials, cycle detection in number sequences, long division with remainder tracking, and the correct algorithms for shuffling, weighted picking and reservoir sampling.

A useful way to see the whole lesson is as a set of answers to one question: "the obvious method needs a huge number or a huge loop — what is the shortcut?" Huge results are tamed by working with remainders. Huge exponents are tamed by squaring. Huge gcd computations are tamed by Euclid's remainders. Huge prime searches are tamed by sieving. Huge counting problems are tamed by formulas with factorials. Each shortcut is a few lines of code once you know it exists.

The payoff is large for the effort. These tools turn up inside dynamic programming (counts modulo a prime), inside hashing and string matching (al26 builds rolling hashes on modular arithmetic), in system-design follow-ups (sampling a stream, weighted load balancing), and as standalone easy and medium questions. This lesson presents each tool with the reasoning behind it, a trace, and the language-specific pitfalls that make otherwise correct code fail.

The mental model: clock arithmetic

On a 12-hour clock, 9 o'clock plus 5 hours is 2 o'clock: you add and then keep only the remainder after dividing by 12. That is modular arithmetic, and the modulus is 12. The remarkable property that makes it useful is that you can take remainders at any point without changing the final remainder: (9 + 5) mod 12 = ((9 mod 12) + (5 mod 12)) mod 12. The same holds for subtraction and multiplication. So a count that would be a 500-digit number can be tracked as its remainder modulo 10⁹ + 7 the whole way through, by reducing after every addition and multiplication.

Division is the exception. On a 12-hour clock, "half of 4 o'clock" could be 2 or 8 — division is not even well defined. With a prime modulus p it works, but not by dividing the remainders. Instead, every non-zero number b has a modular inverse b⁻¹, with b · b⁻¹ ≡ 1 (mod p), and dividing by b means multiplying by b⁻¹. Fermat's little theorem gives a formula: b⁻¹ = b^(p−2) mod p. Computing that power for p ≈ 10⁹ needs the second tool of this lesson.

The second mental model is "big numbers want logarithms". Whenever an input can be as large as 10⁹ or 10¹⁸ and the naive method loops that many times, look for a method that halves the problem each step: binary exponentiation for powers, Euclid's algorithm for gcds (which shrinks the numbers at least by half every two steps), binary search for roots (al7). If a problem says "n up to 10¹⁵", it is promising you an O(log n) solution exists.

Where the clock analogy breaks: a clock has no negative hours, but programs compute differences, and remainders of negative numbers depend on the language. Python always returns a remainder with the sign of the modulus, so (3 − 5) % 7 is 5 — exactly the clock answer. Java and C++ return −2. When a subtraction can go negative in those languages, add the modulus before reducing: ((a − b) % m + m) % m. Even in Python, it is a habit worth showing, because interviewers know code gets ported.

Two small facts about Python save time in interviews: pow(b, e, m) is built in and fast, and integers never overflow, so you can check a modular computation against the exact one on small inputs (compute the true answer with big integers, then reduce it) — a quick way to debug a wrong answer in a counting problem.

Finally, keep floating point out of exact problems. 0.1 + 0.2 is 0.30000000000000004 in binary floating point, and math.sqrt of a large perfect square can come out one off when converted to int. For exact integer roots use math.isqrt; for fractions use integers (numerator and denominator reduced by their gcd) or Python's fractions.Fraction.

Modular arithmetic, done right

MOD = 10**9 + 7
add = (a + b) % MOD
sub = (a - b) % MOD                 # Python: always non-negative; elsewhere add MOD first
mul = a * b % MOD
div = a * pow(b, MOD - 2, MOD) % MOD   # Fermat inverse; MOD must be prime and b % MOD != 0
inv = pow(b, -1, MOD)               # Python 3.8+: modular inverse directly

Reduce after every operation. In a DP that counts paths, write dp[i] = (dp[i − 1] + dp[i − 2]) % MOD, not a reduction at the very end. In Python the final answer would be the same, but intermediate numbers with thousands of digits make each step slow; in fixed-width languages, they overflow. Why 10⁹ + 7? It is prime (so inverses exist for every non-zero residue), it is larger than 10⁹ (so answers have room), and the product of two residues is below 2⁶³ (so a 64-bit multiply never overflows before the reduction). 998244353 is the other common choice, picked for number-theoretic transforms.

Binary exponentiation

To compute bᵉ, write e in binary. b¹³ = b⁸ · b⁴ · b¹ because 13 = 1101₂. The powers b, b², b⁴, b⁸ come from repeated squaring, and you multiply in the ones whose bit is set (the figure). Iteratively:

def power(b, e, m):
    result = 1
    b %= m
    while e > 0:
        if e & 1:                    # this bit contributes b^(2^k)
            result = result * b % m
        b = b * b % m                # next power of two
        e >>= 1
    return result

O(log e) multiplications. Python's built-in pow(b, e, m) does exactly this in C; use it in real code, but be ready to write the loop. Pow(x, n) for floating-point x and possibly negative n is the same loop without the modulus: if n < 0, replace x with 1/x and n with −n. Count Good Numbers (n up to 10¹⁵) is a closed form, 5^⌈n/2⌉ · 4^⌊n/2⌋ mod p, computed with two fast powers. Super Pow (aᵇ mod 1337 where b is given as an array of digits) uses aᵇ = (a^(b without its last digit))¹⁰ · a^(last digit), recursing over the digits with fast power at each step.

The same squaring idea works for anything you can multiply associatively. Raising a 2×2 matrix to the n-th power computes the n-th Fibonacci number in O(log n) — the standard answer to "can you compute fib(10¹⁸) mod p?" — and the technique generalises to any linear recurrence.

gcd, lcm and Euclid

The greatest common divisor of a and b equals the gcd of b and a mod b, because any common divisor of a and b also divides a − qb = a mod b, and vice versa. Repeat until the second number is 0:

def gcd(a, b):
    while b:
        a, b = b, a % b
    return a

Trace gcd(48, 18): (48, 18) → (18, 12) → (12, 6) → (6, 0) → 6. Each two steps at least halve the larger number, so it is O(log min(a, b)) — even for 18-digit numbers, under a hundred steps. lcm(a, b) = a // gcd(a, b) * b (divide first to keep numbers small). Python provides math.gcd and math.lcm.

gcd shows up in surprising places. "Greatest Common Divisor of Strings": if s + t == t + s, both are repetitions of a common block, and its length is gcd(len(s), len(t)); otherwise there is none. Reducing fractions — for example, the slope between two points as (dy/g, dx/g) with a sign convention — makes equal slopes hash equally in "max points on a line". "Water jug" problems (can you measure exactly z litres with jugs of x and y?) are answered by Bézout's identity: yes exactly when z is a multiple of gcd(x, y) and z ≤ x + y.

The extended Euclidean algorithm also returns integers x, y with ax + by = gcd(a, b). When gcd(b, m) = 1, the x in bx + my = 1 is the inverse of b modulo m — this is how inverses are computed when the modulus is not prime.

Primes: trial division and sieves

To test one number n, trial division up to √n suffices: if n = a · b with a ≤ b, then a ≤ √n. That is O(√n) — fine up to about 10¹². To find all primes up to n ("Count Primes"), the sieve of Eratosthenes is far better: start with every number from 2 marked prime; for each i that is still marked, cross out its multiples starting from i·i (smaller multiples were already crossed out by smaller primes).

def count_primes(n):
    if n < 3: return 0
    is_p = bytearray([1]) * n
    is_p[0] = is_p[1] = 0
    i = 2
    while i * i < n:
        if is_p[i]:
            is_p[i*i::i] = bytearray(len(range(i*i, n, i)))   # cross out multiples
        i += 1
    return sum(is_p)

The total work is n · (1/2 + 1/3 + 1/5 + …) over primes up to √n, which is O(n log log n) — almost linear. The slice assignment crosses out a whole arithmetic progression in C. For factorising many numbers up to n, a variant stores each number's smallest prime factor; then any number factorises by repeatedly dividing by its smallest prime factor, O(log n) steps.

Counting: combinations modulo a prime

"Unique Paths" in an m×n grid is C(m + n − 2, m − 1); many counting problems reduce to binomial coefficients. For exact values with small n, math.comb is fine. For many queries modulo a prime with n up to 10⁶, precompute factorials and inverse factorials once:

def build(n, MOD=10**9 + 7):
    fact = [1] * (n + 1)
    for i in range(1, n + 1):
        fact[i] = fact[i - 1] * i % MOD
    inv = [1] * (n + 1)
    inv[n] = pow(fact[n], MOD - 2, MOD)          # one Fermat inverse
    for i in range(n, 0, -1):
        inv[i - 1] = inv[i] * i % MOD            # 1/(i-1)! = i / i!
    return fact, inv

def ncr(n, r, fact, inv, MOD=10**9 + 7):
    if r < 0 or r > n: return 0
    return fact[n] * inv[r] % MOD * inv[n - r] % MOD

Only one modular exponentiation is needed; the rest of the inverse factorials follow by multiplying back down. Each query is then O(1). Pascal's triangle (C(n, r) = C(n − 1, r − 1) + C(n − 1, r)) avoids inverses entirely and works for any modulus, but costs O(n²). Other counting staples: the number of subsets of n items is 2ⁿ; arrangements of n items with repeated groups is n! divided by the factorials of the group sizes; the Catalan numbers C(2n, n)/(n + 1) count balanced bracket sequences and binary tree shapes (al13, al14).

Digits: plus one, happy numbers, big multiplication

Digit problems test careful iteration. Plus One (a number as a list of digits): walk from the right, turning 9s into 0s while carrying; if you run off the front, prepend a 1 (999 → 1000). Happy Number: replace n by the sum of the squares of its digits repeatedly; is 1 reached? The values quickly drop below a few hundred (a number with d digits maps to at most 81·d), so the sequence must eventually repeat. Detect the cycle with a set of seen values, or with Floyd's fast and slow pointers (al5) for O(1) memory — the same algorithm as linked-list cycle detection, applied to the function n → digit-square-sum(n).

Multiply Strings forbids converting to integers, so implement grade-school multiplication: an array of m + n digits; digit i of a times digit j of b adds into position i + j + 1 (indexing from the left), carrying into i + j. Strip leading zeros. O(m·n). Reverse Integer and String to Integer (atoi) add a 32-bit overflow check — in Python, compare against 2³¹ − 1 and −2³¹ explicitly, since nothing overflows by itself.

Recurring decimals: remainders reveal the cycle

"Fraction to Recurring Decimal": 4/333 = 0.(012). Do long division by hand and notice what determines the next digit: only the current remainder. So if a remainder ever repeats, the digits from its first occurrence will repeat forever. Record the position at which each remainder first appeared:

def fraction_to_decimal(num, den):
    if num == 0: return "0"
    sign = "-" if (num < 0) ^ (den < 0) else ""
    num, den = abs(num), abs(den)
    q, r = divmod(num, den)
    out, seen = [sign + str(q)], {}
    if r == 0: return out[0]
    out.append(".")
    while r and r not in seen:
        seen[r] = len(out)               # where this remainder's digit goes
        q, r = divmod(r * 10, den)
        out.append(str(q))
    if r:                                # repeated remainder: insert parentheses
        out.insert(seen[r], "(")
        out.append(")")
    return "".join(out)

There are fewer than den possible remainders, so the loop runs at most den times. The sign handling (XOR of the two signs) and the zero case are the usual traps.

Randomness: weighted picks, shuffles and reservoirs

Random Pick with Weight: index i should be returned with probability w[i] / Σw. Lay the weights end to end on a line of length total = Σw, draw a uniform integer r in [1, total], and find which segment contains it: the first prefix sum ≥ r, found with bisect_left. O(n) setup, O(log n) per pick.

import random, bisect, itertools
class Solution:
    def __init__(self, w):
        self.prefix = list(itertools.accumulate(w))
    def pickIndex(self):
        r = random.randint(1, self.prefix[-1])
        return bisect.bisect_left(self.prefix, r)

Shuffle: the Fisher–Yates algorithm fills positions from the end. For i from n − 1 down to 1, choose j uniformly from 0..i and swap a[i] with a[j]. Every permutation arises from exactly one sequence of choices (n choices, then n − 1, …), so each has probability 1/n!. The tempting alternative — swap each a[i] with a random index from the whole array — produces nⁿ equally likely choice sequences, and since nⁿ is not divisible by n! for n ≥ 3, some permutations must be more likely than others. For n = 3: 27 sequences over 6 permutations cannot be uniform.

Reservoir sampling picks a uniform random element from a stream whose length you do not know (a linked list, a log file, a network feed) in one pass. Keep the first item; at the i-th item, replace the kept one with probability 1/i. The figure shows why it is uniform. For a sample of k items, keep the first k, and at item i (i > k) replace a uniformly chosen reservoir slot with probability k/i. "Linked List Random Node" and "Random Pick Index" (uniform among indices of a target value) are direct applications.

Recognising the pattern

"Modulo 10⁹ + 7" → reduce every step, inverses for division, precomputed factorials for combinations. "n up to 10¹⁵" → closed form plus fast power, or matrix power for recurrences. gcd, lcm, fractions, divisibility, "measure exactly" → Euclid. Primes up to n → sieve. Digit sequences that might loop → cycle detection. "Uniformly at random", "with probability proportional to", "from a stream" → Fisher–Yates, prefix sums with bisect, reservoir sampling.

Practice in the DSA list: Plus One, Happy Number, Greatest Common Divisor of Strings, Pow(x, n), Count Primes, Multiply Strings, Fraction to Recurring Decimal, Super Pow, Random Pick with Weight, Count Good Numbers, Unique Paths (al22, also a binomial coefficient).

Why Fermat's inverse works, and when it does not

Fermat's little theorem says that for prime p and b not divisible by p, b^(p−1) ≡ 1 (mod p). Multiply both sides by b⁻¹: b^(p−2) ≡ b⁻¹. Two conditions are essential. The modulus must be prime — for composite m, use the extended Euclidean algorithm, and the inverse exists only if gcd(b, m) = 1. And b must not be a multiple of p: dividing by something congruent to 0 is meaningless, which matters in nCr when n ≥ p (then factorials contain p, and you need Lucas' theorem, which computes C(n, r) mod p from the base-p digits of n and r). Euler's theorem generalises Fermat: b^φ(m) ≡ 1 (mod m) when gcd(b, m) = 1, where φ(m) counts integers below m coprime to it — the basis of RSA.

The Chinese remainder theorem

If you know x mod 3 = 2, x mod 5 = 3 and x mod 7 = 2, then x mod 105 is determined (it is 23). In general, for pairwise coprime moduli, the remainders modulo each determine the remainder modulo their product, and an efficient construction uses modular inverses. It appears in problems about cyclic schedules ("when do these three periodic events coincide?"), in computing with very large numbers by working modulo several primes in parallel, and in cryptography. Interviews rarely require the construction, but recognising "coincidence of periodic events" as CRT (or lcm, when the offsets are all zero) is useful.

Primality testing for big numbers

Trial division is hopeless for 18-digit numbers (√10¹⁸ = 10⁹ divisions). The Miller–Rabin test checks whether n behaves like a prime with respect to a few bases a, using fast modular exponentiation: write n − 1 = 2ˢ·d and check whether a^d ≡ 1 or a^(2ʳd) ≡ −1 for some r. For 64-bit integers, a specific small set of bases makes the test deterministic. Pollard's rho algorithm factors large composites using — once again — Floyd's cycle detection, on the sequence x → x² + c mod n. These are well beyond typical interviews, but they show how the basic tools (fast power, cycle detection) compose into serious algorithms.

Bias in naive random number use

Uniform randomness is easy to break. random.randint(0, 2**32) % n is biased whenever n does not divide the range, because some remainders occur one extra time; libraries avoid this with rejection sampling (draw again if the value falls in the incomplete last block). Generating "rand7() from rand5()" works the same way: combine two calls into a uniform number in 0..24, accept it only if it is below 21, and return it mod 7. Shuffling with sorted(a, key=lambda _: random.random()) is uniform in practice (ties have negligible probability) but O(n log n); the classic bug is sorting with a random comparator, which is biased and can break some sort implementations. For security-sensitive randomness (tokens, keys), use the secrets module, not random, whose Mersenne Twister generator is predictable from its outputs.

Matrix exponentiation for linear recurrences

Any sequence defined by a fixed linear recurrence — Fibonacci (f(n) = f(n−1) + f(n−2)), tribonacci, the number of ways to tile a 2×n board, the number of length-n strings avoiding a pattern described by a small automaton — can be written as "state vector × fixed matrix = next state vector". Raising the k×k matrix to the n-th power with binary exponentiation computes the n-th term in O(k³ log n). For Fibonacci, [[1, 1], [1, 0]]ⁿ contains f(n + 1), f(n) and f(n − 1), so f(10¹⁸) mod p needs about 60 2×2 matrix multiplications. When an interviewer follows up a DP with "now n is 10¹⁸", this is usually the answer they want, provided the DP's transition does not depend on n.

Floating point and exactness

Binary floating point cannot represent most decimal fractions exactly, so equality tests and accumulated sums drift: summing 0.1 ten times gives 0.9999999999999999. Exact problems should stay in integers — compare fractions by cross-multiplying, represent money in cents, use math.isqrt for integer square roots (int(math.sqrt(n)) can be off by one for n near 10¹⁶ and above), and use fractions.Fraction or decimal.Decimal when rational or decimal exactness is required. When floats are unavoidable (geometry, probabilities), compare with a tolerance and say so.

In the interview room

Math-flavoured problems are graded on correctness at the edges. The common bugs: dividing residues directly instead of multiplying by an inverse; reducing only at the end (slow in Python, overflow elsewhere); negative remainders when porting to other languages; forgetting the sign or zero cases in Fraction to Recurring Decimal and in Pow(x, n) with negative n; off-by-one bounds in sieves (crossing out from 2i instead of i², or looping i while i < n instead of i·i < n — correct but slower); and biased shuffles. Test with 0, 1, negative inputs, the largest allowed input, and a case where the modulus actually matters.

Interviewers often probe understanding: "why 10⁹ + 7?", "why can you not divide modulo p?", "prove your shuffle is uniform", "why is Euclid's algorithm logarithmic?", "what if the stream length is unknown?". Each has a two-sentence answer in this lesson; practise saying them. For randomness questions, giving the probability argument (the telescoping product for reservoir sampling, the n! sequences for Fisher–Yates) is what distinguishes a strong answer.

When n is huge, say the closed form first and then the algorithm: "the answer is 5^⌈n/2⌉ · 4^⌊n/2⌋, and I'll compute each power with binary exponentiation in O(log n)". Interviewers appreciate seeing the mathematical simplification separated from the implementation.

On online assessments, the most common math-related failures are not conceptual but mechanical: a missing modulus on one line of a DP, an intermediate product that overflows in Java, or a floating-point comparison that fails on one hidden test. A final pass over your code checking every multiplication and subtraction for "is this reduced?" takes a minute and catches most of them.

Finally, keep the toolkit's limits in mind out loud: "Fermat's inverse needs a prime modulus", "the sieve needs O(n) memory, so for n = 10¹⁰ I would use a segmented sieve", "Fisher–Yates needs a good random source". Stating the precondition with the technique is the senior habit.

In real systems

This toolkit underpins a lot of infrastructure. Hash tables and hash functions use modular arithmetic, often with prime moduli, and rolling hashes for string matching and deduplication (al26) update hash values modulo a large prime in O(1). Public-key cryptography is modular exponentiation and inverses at scale: RSA encrypts with c = mᵉ mod n using exactly binary exponentiation, and computes its private key with the extended Euclidean algorithm. Checksums such as the Luhn algorithm on credit-card numbers and ISBN check digits are modular arithmetic on digits. Data platforms sample huge streams with reservoir sampling to compute approximate statistics or keep representative logs; load balancers route requests with weighted random choice; A/B testing systems assign users to variants by hashing user ids modulo the number of buckets; and online games and card apps must shuffle with Fisher–Yates (a widely reported 1999 online-poker flaw came from a shuffle with too little randomness, which let attackers predict hands).

def fisher_yates(a):
    a = a[:]

Count, then compute

"A rectangular grid has m rows and n columns (m, n ≤ 10⁶). A robot moves only right or down from the top-left to the bottom-right. How many paths are there modulo 10⁹ + 7? Now add: the robot must pass through a given cell (r, c). And: there are 100 forbidden cells it must avoid." Give an efficient method for each.

Answer

All paths: a path is a sequence of (m − 1) down moves and (n − 1) right moves, so the count is C(m + n − 2, m − 1). With m, n up to 10⁶, a DP table of 10¹² cells is impossible; precompute factorials and inverse factorials up to 2 × 10⁶ in O(m + n) and answer in O(1). Through (r, c): paths from the start to (r, c) times paths from (r, c) to the end: C(r + c, r) · C((m − 1 − r) + (n − 1 − c), m − 1 − r), both from the same tables. Avoiding 100 forbidden cells: sort the forbidden cells by (row, column) and add the target as a final "cell". Let bad[i] = the number of paths from the start to forbidden cell i that avoid every earlier forbidden cell: bad[i] = paths(start, i) − Σ over j before i that can reach i of bad[j] · paths(j, i). The answer is the same formula evaluated for the target. That is O(k²) binomial evaluations for k forbidden cells — 10⁴ — plus the factorial precomputation. This inclusion–exclusion by "first forbidden cell hit" is a standard technique, and it shows how combinatorics plus modular inverses solves grid problems far beyond what a DP table could hold.
