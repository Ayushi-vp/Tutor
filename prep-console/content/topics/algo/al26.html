Every editor has "find", every log viewer has search, and every genome pipeline looks for short DNA patterns inside billions of letters. The simplest method — line the pattern up at each position of the text and compare character by character — is what most people write first, and on ordinary English it is fast. But consider searching for "aaaaab" in a text of a million "a"s. At every position, the comparison matches five characters before failing on the sixth, and then the method shifts by one and starts again from scratch. For a pattern of length m and text of length n, that is about n·m comparisons. The naive method keeps throwing away what it just learned: after matching "aaaaa", it already knows the next text characters are "aaaa" — yet it re-reads them.

Linear-time string matching is about not throwing that knowledge away. KMP precomputes, from the pattern alone, how far it can safely shift after a mismatch, so the text pointer never moves backwards. The Z-function computes, for every position, how long a prefix of the string matches there, reusing earlier matches. Rabin–Karp takes a different route: it compares numbers instead of strings, using a hash of each text window that can be updated in O(1) as the window slides.

These algorithms matter in interviews beyond "implement strStr". The KMP prefix function directly answers questions about a string's structure — its smallest period, whether it is a repetition, its longest prefix that is also a suffix, its longest palindromic prefix. Rolling hashes solve "repeated DNA sequences" and, with binary search, "longest duplicate substring". This lesson develops each tool from the naive method, with traces, and explains the pitfalls — especially the hash collisions that make rolling-hash solutions fail on adversarial tests.

The mental model: never re-read the text

Imagine reading a long scroll through a narrow slot, looking for a particular phrase. Each time you fail to match, you must decide where the phrase could next begin. The naive approach rewinds the scroll to one character after the last starting point — you re-read text you have already seen. A smarter reader asks: "of the characters I just matched, is there a later point where the phrase could already be partly underway?" If the pattern is "abcabd" and you matched "abcab" before failing, the last two characters "ab" are also the start of the pattern — so you can continue as if "ab" were already matched, without moving the scroll back at all.

That question — "what is the longest piece at the end of what I matched that is also a beginning of the pattern?" — depends only on the pattern, not on the text, so it can be precomputed for every possible amount matched. The answer is the prefix function (also called the failure function or LPS, for "longest proper prefix which is also suffix"): lps[i] is the length of the longest proper prefix of pattern[0..i] that is also a suffix of it. A prefix that is also a suffix is called a border.

A second way to think about the same knowledge is the Z-function: for each position i of a string, z[i] is how many characters starting at i agree with the start of the string. Searching for a pattern P in a text T then becomes computing Z of P + "#" + T (the "#" is a character in neither) and reporting positions where z equals len(P).

The third idea abandons character comparison: give each window of the text a numeric fingerprint (a hash) that can be updated in O(1) when the window slides, and compare fingerprints. If the fingerprints differ, the strings differ; if they match, the strings are probably equal — and you verify. That is Rabin–Karp.

To put numbers on the difference: searching a 10⁶-character text for a 10⁴-character pattern that keeps almost matching costs the naive method about 10¹⁰ character comparisons — minutes in Python. KMP, Z and Rabin–Karp all do about 2 × 10⁶ steps. On friendly text all three methods look equally fast, which is exactly why the worst case has to be reasoned about rather than measured on examples.

Where the scroll analogy breaks: a real reader keeps a memory of the text, but KMP keeps only one number — how much of the pattern is currently matched. All the cleverness lives in the pattern's precomputed table. Rolling hashes break the analogy differently: they do not "read" the text in the human sense at all, which is why they need a verification step that the comparison-based algorithms do not.

The naive method and its worst case

def naive_find(t, p):
    for i in range(len(t) - len(p) + 1):
        if t[i:i + len(p)] == p:      # O(m) comparison
            return i
    return -1

O(n·m) in the worst case: text "aaa…a" (n characters), pattern "aa…ab" (m characters). Every alignment matches m − 1 characters before failing. For n = 10⁶ and m = 10⁴ that is 10¹⁰ character comparisons. (Python's slicing and comparison run in C, which hides the cost on small inputs, but not the growth.)

The prefix function

lps[i] = the length of the longest proper prefix of p[0..i] that is also a suffix of p[0..i]. For p = "aabaaab":

Computing it naively per position is O(m²) or worse. The linear algorithm extends the previous border when possible and, when not, falls back to the next-shorter border — which is the longest border of the current border, already stored in the table:

def prefix_function(p):
    lps = [0] * len(p)
    k = 0                                 # length of the current border
    for i in range(1, len(p)):
        while k and p[i] != p[k]:
            k = lps[k - 1]                # fall back to a shorter border
        if p[i] == p[k]:
            k += 1                        # extend the border by one character
        lps[i] = k
    return lps

Trace i = 5 in "aabaaab": the previous border has length k = 2 ("aa"). p[5] = 'a' and p[2] = 'b' differ, so fall back to k = lps[1] = 1 ("a"); now p[5] = 'a' equals p[1] = 'a', so k becomes 2. lps[5] = 2. At i = 6, p[6] = 'b' equals p[2] = 'b', so k = 3. The fallback is safe because any border of p[0..i] minus its last character is a border of p[0..i−1], and the borders of a string, from longest to shortest, are exactly the chain lps[k − 1], lps[lps[k − 1] − 1], …. Linear time: k grows by at most one per iteration and every fallback shrinks it, so the total number of fallbacks is at most m.

KMP search

Scan the text once with j = the number of pattern characters currently matched. On a match, advance j; on a mismatch, fall back with j = lps[j − 1] (the text pointer stays put); when j reaches m, report a match and fall back to continue searching for overlapping matches.

def kmp_find_all(t, p):
    lps, j, out = prefix_function(p), 0, []
    for i, ch in enumerate(t):
        while j and ch != p[j]:
            j = lps[j - 1]
        if ch == p[j]:
            j += 1
        if j == len(p):
            out.append(i - len(p) + 1)
            j = lps[j - 1]                # allow overlapping matches
    return out

O(n + m) time, O(m) extra space. An equivalent formulation computes the prefix function of p + "#" + t directly: positions where the value equals m mark the ends of matches. Either is fine in an interview; the combined-string version means you only write one loop.

What the prefix function tells you about a string

The last value, lps[−1], is the longest proper prefix of s that is also a suffix. Three interview problems are just that number:

  • Longest Happy Prefix: return s[:lps[−1]].
  • Smallest period: p = len(s) − lps[−1]. If a border of length b exists, s is "periodic with period n − b": shifting by n − b lines it up with itself. The longest border gives the smallest period.
  • Repeated Substring Pattern (is s a repetition of a shorter block?): yes exactly when lps[−1] > 0 and len(s) is divisible by the smallest period. "abcabcabc": lps[−1] = 6, period 3, 9 % 3 = 0 → yes. "abcab": lps[−1] = 2, period 3, 5 % 3 ≠ 0 → no.

Shortest Palindrome ("add the fewest characters in front of s to make it a palindrome") needs the longest palindromic prefix of s; everything after it must be mirrored at the front. A prefix of s is a palindrome exactly when it equals the corresponding suffix of reverse(s). So build lps for s + "#" + reverse(s): the final value is the length k of the longest prefix of s that matches a suffix of reverse(s) — the longest palindromic prefix. The answer is reverse(s[k:]) + s. The "#" separator stops a border from spanning both halves.

The Z-function

z[i] = the length of the longest substring starting at i that is also a prefix of s (z[0] is conventionally n or 0). For "aabxaab": z = [−, 1, 0, 0, 3, 1, 0]. The linear algorithm keeps the interval [l, r) — the rightmost window known to match a prefix — and reuses it:

def z_function(s):
    n = len(s); z = [0] * n
    l = r = 0                                # s[l:r] matches s[0:r-l]
    for i in range(1, n):
        if i < r:
            z[i] = min(r - i, z[i - l])      # reuse what is known inside the window
        while i + z[i] < n and s[z[i]] == s[i + z[i]]:
            z[i] += 1                        # extend by direct comparison
        if i + z[i] > r:
            l, r = i, i + z[i]
    return z

Inside [l, r), the substring starting at i is a copy of the substring starting at i − l (since s[l:r] copies the prefix), so z[i − l] is a lower bound, capped at r − i because beyond r nothing is known. Every iteration of the inner while loop that succeeds pushes r to the right, so the total work is O(n). To search for P in T, compute z of P + "#" + T and report every i where z[i] == len(P) (the match starts at i − len(P) − 1 in T).

Rabin–Karp and rolling hashes

A polynomial hash treats a string as a number in base B, reduced modulo a large prime M: hash(s) = (s[0]·B^(m−1) + s[1]·B^(m−2) + … + s[m−1]) mod M. The key property is that sliding a window by one character updates the hash in O(1):

new_hash = ((old_hash - t[i] * B^(m-1)) * B + t[i + m]) mod M

— remove the outgoing character's contribution, shift everything up one power, and add the incoming character.

def rabin_karp(t, p, B=911382323, M=(1 << 61) - 1):
    n, m = len(t), len(p)
    if m > n: return -1
    high = pow(B, m - 1, M)
    hp = ht = 0
    for i in range(m):
        hp = (hp * B + ord(p[i])) % M
        ht = (ht * B + ord(t[i])) % M
    for i in range(n - m + 1):
        if hp == ht and t[i:i + m] == p:          # verify on a hash match
            return i
        if i + m < n:
            ht = ((ht - ord(t[i]) * high) * B + ord(t[i + m])) % M
    return -1

Expected O(n + m). The verification step costs O(m) only on hash matches, which for random-looking data are almost always true matches. The modulus here is a 61-bit Mersenne prime, which makes accidental collisions extremely rare; with a modulus near 10⁹ and millions of windows, collisions become likely (see the deep layer), so verification or a second hash is essential.

Applications of rolling hashes

Repeated DNA Sequences: every 10-letter substring that occurs more than once. With only four letters, encode each in 2 bits; a window of 10 letters is a 20-bit integer, updated by code = ((code << 2) | letter) & ((1 << 20) − 1). That is a perfect (collision-free) rolling hash. Count codes in a dict and report those seen twice.

Longest Duplicate Substring: the longest substring appearing at least twice. If a duplicate of length L exists, a duplicate of length L − 1 exists too (drop a character), so "a duplicate of length L exists" is monotone — binary search on L (al7). For each candidate L, roll a hash over all windows of length L and look for a repeated hash, verifying actual equality for candidate pairs. O(n log n) expected. It is a showcase of combining patterns: binary search on the answer, a sliding window, and hashing.

Comparing substrings in O(1): precompute prefix hashes H[i] = hash(s[:i]) and powers of B. Then hash(s[l:r]) = (H[r] − H[l]·B^(r−l)) mod M, and any two substrings can be compared in O(1) (probabilistically). This answers many queries such as "do s[a:b] and s[c:d] match?", "longest common prefix of two suffixes" (binary search with hash comparisons) and "is s[l:r] a palindrome?" (compare with the prefix hashes of the reversed string).

Rotations and repeated copies

Rotate String: goal is a rotation of s exactly when len(goal) == len(s) and goal occurs in s + s — every rotation of s appears as a window of s + s. Repeated String Match: the fewest copies of a whose concatenation contains b. Any match must fit in ⌈len(b)/len(a)⌉ copies, or one more copy if the match begins partway through a; test those two with a linear search, else −1.

Palindromes in linear time: Manacher, briefly

Longest Palindromic Substring is O(n²) with expand-around-centre (al22). Manacher's algorithm makes it O(n) with the same idea as the Z-function: keep the rightmost palindrome found so far, and for a new centre inside it, the mirror centre's radius gives a lower bound, so you only expand beyond what is known. Implementations insert a separator between characters ("#a#b#a#") so odd and even lengths are handled uniformly. It is rarely required in interviews, but knowing that the Z-style "reuse the rightmost known window" trick has a palindrome version is a good senior aside.

Wildcards and approximate matching

Real searches often allow uncertainty. A pattern with single-character wildcards ("a?c") breaks KMP's border logic, because a wildcard matches different characters at different alignments; simple approaches split the pattern at wildcards and search for the pieces, or use bit-parallel algorithms (Shift-Or, also called Bitap) that keep a bitmask of "partial match states" per text character and handle wildcards and character classes naturally. Approximate matching ("occurrences with at most k mismatches or edits") extends Bitap with k + 1 bitmasks, which is how the classic agrep tool worked, or uses the edit-distance DP (al22) restricted to a band. These are rarely interview questions in full, but they explain why "fuzzy find" in editors feels instant: bit-parallelism processes 64 pattern positions per machine instruction.

Recognising the pattern

Use a linear-time matcher when a problem searches for a pattern in a long text with worst-case guarantees, or asks about a string's self-overlap: periods, repetitions, longest prefix-suffix, palindromic prefixes (KMP or Z). Use rolling hashes when you must compare many substrings of the same length (sliding windows, duplicate detection) or arbitrary substrings in O(1) after preprocessing — and always handle collisions.

Why KMP is linear, precisely

In the search loop, i (the text index) increases by exactly one per iteration, and j (characters matched) increases by at most one per iteration. Each execution of j = lps[j − 1] strictly decreases j. Since j never goes below zero, the total number of decreases over the whole run is at most the total number of increases, which is at most n. So the inner while loop runs at most n times in total, and the search is O(n); the prefix function's construction is O(m) by the same argument. This is the aggregate method from al2, and it is the answer to the common follow-up "the while loop inside the for loop — is it quadratic?".

KMP as an automaton, and Aho–Corasick

The prefix function defines a finite automaton with states 0..m (characters matched) and transitions for each character: on a match go to j + 1, otherwise follow failure links until a match or 0. Precomputing the full transition table (m × alphabet) makes each text character a single table lookup, which is how some hardware and high-throughput matchers work. Building the same structure on a trie of many patterns — failure links pointing to the longest proper suffix that is a prefix of some pattern — gives the Aho–Corasick automaton (al15), which finds all occurrences of thousands of patterns in one pass over the text. It is the standard engine for multi-keyword search, antivirus signatures and intrusion detection.

Collision probability and anti-hash tests

For two fixed different strings and a random base, a polynomial hash modulo a prime M collides with probability at most about m/M. But in "find any repeated window" you compare N windows pairwise, and by the birthday effect the expected number of colliding pairs is about N²/(2M). With N = 10⁶ windows and M ≈ 10⁹, that is around 500 false collisions — certain trouble without verification. With M = 2⁶¹ − 1 it is about 2 × 10⁻⁷. Worse, with a fixed known base and modulus (or with "natural overflow" modulo 2⁶⁴ in C++), testers can construct strings that collide deliberately — the Thue–Morse sequence breaks any hash modulo 2⁶⁴. The defences are a random base chosen at run time, a large prime modulus or two independent moduli, and verification on matches when correctness matters more than speed.

Suffix arrays and the LCP array

A suffix array lists the starting positions of all suffixes of a string in sorted order; the LCP array gives the longest common prefix of each adjacent pair. Together they answer many string questions deterministically: the longest repeated substring is the maximum LCP value; the number of distinct substrings is n(n+1)/2 − Σ LCP; pattern search is a binary search over the sorted suffixes. Construction is O(n log n) with prefix doubling (sorting by the first 1, 2, 4, … characters using ranks) or O(n) with SA-IS, and Kasai's algorithm computes LCP in O(n). Bioinformatics and full-text indexes (the FM-index used in genome aligners like BWA and Bowtie) build on them. In interviews, naming the suffix array as the deterministic alternative to binary-search-plus-hashing for Longest Duplicate Substring shows breadth.

Prefix-function automata for counting strings

A harder family asks "how many strings of length n over an alphabet do not contain a given pattern?" or "contain it exactly k times?". Build the KMP automaton of the pattern (states 0..m, with a transition for every character computed from the failure links), then run a DP over (length so far, automaton state): from each state, each character leads to the next state, and reaching state m means the pattern appeared. That is O(n · m · alphabet), and with matrix exponentiation over the automaton (al25) it handles n up to 10¹⁸. It is a beautiful combination of string matching and dynamic programming, and it also underlies counting with several forbidden patterns via Aho–Corasick.

What real libraries use

Production string search rarely uses textbook KMP. GNU grep relies on Boyer–Moore-style algorithms, which compare from the end of the pattern and can skip ahead by up to m characters on a mismatch — sublinear on typical text — together with a DFA engine for regular expressions. CPython's str.find historically used a simplified Boyer–Moore–Horspool with a bloom-filter skip, and since Python 3.10 switches to the Crochemore–Perrin two-way algorithm for longer needles, which guarantees linear time with constant extra memory. Knowing that the built-in is linear-time is why "just use in" is acceptable in real code, while implementing KMP or Z remains the expected interview demonstration.

In the interview room

String-algorithm questions reward a crisp definition and a clean loop. State the definition first ("lps[i] is the length of the longest proper prefix of p[0..i] that is also a suffix"), trace it on a short pattern, then write the code. The common bugs: forgetting that "proper" excludes the whole string (lps[0] = 0); using if instead of while for the fallback, which only tries one shorter border; not falling back after a full match, which misses overlapping occurrences; omitting the separator in s + "#" + t tricks, which lets borders span both parts; and, for rolling hashes, negative values before the modulus in languages where % can return negatives, forgetting to precompute B^(m−1), and skipping verification. Test with a pattern longer than the text, an empty pattern if allowed, all-equal characters, and overlapping matches ("aaa" in "aaaaa" occurs three times).

Expect "why is it linear?" (the aggregate argument), "how would you handle many patterns?" (Aho–Corasick or a trie), and, for hashing, "what about collisions?" (verify, or double hash, plus the birthday estimate). When a problem can be solved with either KMP or hashing, choose the one you can write correctly under pressure and mention the other; interviewers care more about correctness and justification than about the specific technique.

On online assessments, string-matching problems often disguise themselves as "how many times does this pattern occur in this long log", "the smallest block that repeats to form this string", or "the longest prefix that also appears at the end". Each maps to one of the identities in this lesson; recognising the identity is usually the hard part.

Finally, remember the separator rule for every concatenation trick (s + "#" + t, p + "" + t): the separator must be a character that cannot occur in either string, or borders and Z-values can run across the boundary and report false matches. In Python, a character outside the input alphabet such as "" is a safe choice for text problems.

In real systems

Rolling hashes are a workhorse of data infrastructure. rsync synchronises files over a network by computing a cheap rolling checksum of every window of the local file and comparing it against block checksums sent from the remote side, confirming candidates with a strong hash — Tridgell and Mackerras's 1996 report describes the design. Backup and deduplication systems (and tools like restic and borg) split files into chunks at positions where a rolling hash of the last few dozen bytes hits a target pattern ("content-defined chunking"), so inserting a byte only changes nearby chunks. Plagiarism detectors such as MOSS fingerprint documents with Rabin hashes and the winnowing algorithm. Search tools combine Boyer–Moore skipping, automata and SIMD scanning; antivirus engines and network intrusion detection systems (Snort, Suricata) run Aho–Corasick over traffic; and genome aligners index reference genomes with suffix-array-based FM-indexes to find billions of short reads. The interview ideas — reuse what you have matched, hash windows incrementally, verify on collision — are exactly their design principles.

Pick the tool

For each task, choose KMP/Z or rolling hashes (or both) and outline the solution. (a) Given a string of length 10⁵, find its shortest prefix that, repeated (possibly with a partial copy at the end), reproduces the string. (b) Given two strings of length 10⁵, find the length of their longest common substring. (c) Count the distinct substrings of a string of length 5,000. (d) For 10⁵ queries (l1, r1, l2, r2), decide whether s[l1:r1] == s[l2:r2].

Answer

(a) KMP: the answer is the prefix of length len(s) − lps[−1] (the smallest period); a partial final copy is allowed, so no divisibility check is needed. O(n). (b) Binary search on the length L (a common substring of length L implies one of length L − 1); for each L, put the rolling hashes of all length-L windows of the first string in a set and check the second string's windows against it, verifying hits. O((n + m) log n) expected. A suffix automaton or a suffix array of a + "#" + b gives deterministic O(n log n) or O(n). (c) With n = 5,000 there are about 12.5 million substrings; for each length L, roll hashes over the n − L + 1 windows and add them to a set (or use a 64-bit pair of hashes to make collisions negligible), summing distinct counts: O(n²) hash operations, about 1.25 × 10⁷. Deterministically, a suffix array gives n(n+1)/2 − Σ LCP in O(n log n). (d) Precompute prefix hashes and powers once in O(n); each query compares (lengths first, then) hash(s[l1:r1]) and hash(s[l2:r2]) in O(1) — use two moduli or a 61-bit modulus so 10⁵ comparisons are effectively collision-free.
