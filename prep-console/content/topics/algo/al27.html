A trading dashboard shows the total volume traded in any time window a user selects, while new trades keep arriving. A game keeps a leaderboard of a million players and must answer "how many players have a score below 4,250?" every time someone looks at their rank, while scores change every second. A calendar service must report, after each new booking, the maximum number of meetings overlapping at any moment. All three combine two kinds of operation on the same data: queries over a range and updates.

Prefix sums (al3) answer range sums in O(1), but they are frozen: change one element and every later prefix changes, an O(n) rebuild. Recomputing each range query from scratch is the opposite trade — O(1) updates, O(n) queries. With a million elements and a million mixed operations, either extreme costs on the order of 10¹² steps. The structures in this lesson meet in the middle: O(log n) for both, so a million operations take around twenty million steps.

The two workhorses are the Fenwick tree (binary indexed tree), a dozen lines of code for prefix sums with point updates, and the segment tree, which handles any associative operation — sums, minimums, maximums, gcds — over arbitrary ranges, and with lazy propagation supports updates to whole ranges too. For data that never changes, a sparse table answers range minimums in O(1). Combined with coordinate compression, these structures also solve counting problems that do not look like range queries at first: smaller elements after each position, inversions, range sums within bounds.

This lesson builds each structure from the idea behind it, with a trace, and then applies them to the interview hards that require them. It is the most "advanced" lesson in this track, but each structure rests on one simple idea: precompute answers for a well-chosen family of ranges, and answer any query by combining a few of them.

The mental model: a company's reporting hierarchy

Imagine a company where each team leader knows the total sales of their team, each department head knows the total for their teams, and the CEO knows the company total. To find the sales of any group of consecutive teams, you do not ask every salesperson; you ask a few managers whose groups exactly cover the range — a department head here, a couple of team leaders at the edges. When one salesperson closes a deal, only the people above them in the hierarchy — their team leader, department head and the CEO — need to update their totals. Both questions and updates touch only a handful of people, about one per level of the hierarchy.

A segment tree is exactly that hierarchy built over array positions: the root covers the whole array, each node's two children cover its left and right halves, and each node stores the combined value (sum, min, …) of its range. A tree over n positions has about log₂ n levels, so any range can be covered by O(log n) nodes and any point update changes O(log n) nodes.

A Fenwick tree is a cleverer, flatter version of the same idea for prefix sums. It uses a single array where entry i stores the sum of a block of positions ending at i, whose length is the lowest set bit of i (al24). Those blocks are arranged so that any prefix [1, i] is tiled by at most log₂ i of them, found by repeatedly removing the lowest set bit of i, and any position is contained in at most log₂ n of them, found by repeatedly adding the lowest set bit.

The cost argument is worth making concrete. With n = 10⁶ positions, a segment tree has about 2 × 10⁶ nodes and depth 20. A point update rewrites 20 node values; a range query combines at most about 40 node values (two partial nodes per level). Compare that with recomputing a range sum over up to a million elements, or rebuilding a million prefix sums after each update. Both structures turn "touch everything" into "touch one node per level", which is the same logarithmic trick as binary search and heaps, applied to ranges.

Where the company analogy breaks: real managers can summarise anything about their teams, but these structures can only summarise with an operation that combines two summaries into the summary of the union — an associative operation like sum, min, max or gcd. "The median sales of a team" cannot be combined from two halves' medians, so a plain segment tree cannot answer range medians. And for Fenwick trees, the operation must also be invertible (subtraction undoes addition) to answer arbitrary ranges as prefix(r) − prefix(l − 1).

The Fenwick tree

Use 1-based positions. Let lowbit(i) = i & −i, the value of i's lowest set bit (al24). Entry tree[i] holds the sum of a over the block (i − lowbit(i), i]. So tree[8] covers positions 1–8, tree[6] covers 5–6, tree[7] covers just 7.

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.t = [0] * (n + 1)              # 1-based

    def add(self, i, delta):                # a[i] += delta, i is 1-based
        while i <= self.n:
            self.t[i] += delta
            i += i & -i                     # next block that contains i

    def prefix(self, i):                    # sum of a[1..i]
        s = 0
        while i > 0:
            s += self.t[i]
            i -= i & -i                     # strip the block just used
        return s

    def range_sum(self, l, r):              # sum of a[l..r]
        return self.prefix(r) - self.prefix(l - 1)

Trace prefix(7): 7 = 111₂ → add tree[7] (block 7..7), strip lowbit → 6 = 110₂ → add tree[6] (block 5..6), strip → 4 = 100₂ → add tree[4] (block 1..4), strip → 0. Three blocks tile 1..7. Trace add(5, δ): 5 = 101₂ → tree[5], add lowbit → 6 = 110₂ → tree[6], → 8 = 1000₂ → tree[8], → 16 > n stops. Those are exactly the blocks containing position 5.

"Range Sum Query — Mutable" is a Fenwick tree plus a copy of the array (to turn "set a[i] to v" into "add v − a[i]"). Building by n calls to add is O(n log n); an O(n) build adds each tree[i] into tree[i + lowbit(i)] once in a left-to-right pass. Remember the 1-based indexing: convert at the boundary (i + 1) and nowhere else.

Counting with a Fenwick tree over values

Many counting problems become range queries if the Fenwick tree is indexed by value instead of position. Count of Smaller Numbers After Self: for each element, how many elements to its right are smaller? Scan from right to left; keep a Fenwick tree where count[v] is the number of already-seen elements (all to the right) with value v. For each element, the answer is prefix(v − 1); then add 1 at v.

Values can be up to 10⁴ in magnitude, or 10⁹ in other problems, and negative. Coordinate compression fixes that: sort the distinct values and replace each by its 1-based rank. Only the order matters for "smaller than", so ranks give the same answers.

def count_smaller(nums):
    ranks = {v: i + 1 for i, v in enumerate(sorted(set(nums)))}
    fw, out = Fenwick(len(ranks)), []
    for v in reversed(nums):
        r = ranks[v]
        out.append(fw.prefix(r - 1))     # seen elements with smaller rank
        fw.add(r, 1)
    return out[::-1]

Trace [5, 2, 6, 1]: ranks 1→1, 2→2, 5→3, 6→4. From the right: 1 (rank 1) → 0 smaller, add; 6 (rank 4) → prefix(3) = 1, add; 2 (rank 2) → prefix(1) = 1, add; 5 (rank 3) → prefix(2) = 2. Reversed: [2, 1, 1, 0]. O(n log n). Counting inversions (pairs i < j with a[i] > a[j]) is the same scan, summing the answers. Reverse Pairs (a[i] > 2·a[j]) queries for values above 2·a[j], which needs the doubled values included in the compression, or merge sort with a two-pointer count per merge.

Count of Range Sum applies the same tool to prefix sums: the subarray i..j has sum P[j + 1] − P[i], so count pairs of prefix values whose difference lies in [lower, upper]. Scan prefixes left to right, and for each P[j] query how many earlier prefixes lie in [P[j] − upper, P[j] − lower] — a range count in a Fenwick tree over compressed prefix values — then insert P[j]. This is the "inequality between pairs of prefixes needs a sorted structure" situation flagged in al3.

The segment tree

A segment tree works for any associative operation. A clean recursive version stores node values in an array of size 4n, with node 1 as the root and children 2k and 2k + 1:

class SegTree:                                 # range minimum, point update
    def __init__(self, a):
        self.n = len(a); self.t = [float("inf")] * (4 * self.n)
        self._build(1, 0, self.n - 1, a)
    def _build(self, k, lo, hi, a):
        if lo == hi: self.t[k] = a[lo]; return
        mid = (lo + hi) // 2
        self._build(2 * k, lo, mid, a); self._build(2 * k + 1, mid + 1, hi, a)
        self.t[k] = min(self.t[2 * k], self.t[2 * k + 1])
    def update(self, i, v, k=1, lo=0, hi=None):
        if hi is None: hi = self.n - 1
        if lo == hi: self.t[k] = v; return
        mid = (lo + hi) // 2
        if i <= mid: self.update(i, v, 2 * k, lo, mid)
        else: self.update(i, v, 2 * k + 1, mid + 1, hi)
        self.t[k] = min(self.t[2 * k], self.t[2 * k + 1])
    def query(self, l, r, k=1, lo=0, hi=None):  # min of a[l..r]
        if hi is None: hi = self.n - 1
        if r < lo or hi < l: return float("inf")      # disjoint
        if l <= lo and hi <= r: return self.t[k]       # fully covered
        mid = (lo + hi) // 2
        return min(self.query(l, r, 2 * k, lo, mid),
                   self.query(l, r, 2 * k + 1, mid + 1, hi))

Three cases in the query make it O(log n): a node completely outside the range contributes the identity (∞ for min, 0 for sum); a node completely inside contributes its stored value without recursing; only nodes that partially overlap recurse, and there are at most two such nodes per level. Changing min and the identity gives range sum, max, gcd, or a product modulo p. An iterative bottom-up version — leaves at indices n..2n − 1, parent of i at i // 2 — is shorter and faster and is worth learning if you use segment trees often (see the references).

Lazy propagation: range updates

"Add v to every element in [l, r]" would touch up to n leaves. Lazy propagation applies the update to whole nodes instead: when a node's range is completely inside [l, r], update its stored value as if all its leaves had changed (for sums: add v × length; for max: add v) and record v in the node's lazy tag, meaning "my children still owe this addition". Only when a later operation needs to go below that node do you push the tag: apply it to both children (their values and their tags) and clear it.

def push(k, lo, mid, hi):                       # range add, range sum version
    if lazy[k]:
        for c, a, b in ((2 * k, lo, mid), (2 * k + 1, mid + 1, hi)):
            t[c] += lazy[k] * (b - a + 1)
            lazy[c] += lazy[k]
        lazy[k] = 0

def range_add(l, r, v, k, lo, hi):
    if r < lo or hi < l: return
    if l <= lo and hi <= r:
        t[k] += v * (hi - lo + 1); lazy[k] += v; return
    mid = (lo + hi) // 2
    push(k, lo, mid, hi)
    range_add(l, r, v, 2 * k, lo, mid); range_add(l, r, v, 2 * k + 1, mid + 1, hi)
    t[k] = t[2 * k] + t[2 * k + 1]

Queries push tags on the way down in the same way. Both operations still visit O(log n) nodes. The same pattern supports range assignment (tag = "set everything to x"), range max with range add (My Calendar III: +1 on each booking's interval, then the root's max), and range assignment with range max (Falling Squares: query the max height over a square's span, then assign max + side to that span). Coordinate compression keeps the tree small when the coordinates are large; a "dynamic" segment tree that creates nodes only when needed is the alternative when coordinates are not known in advance.

Sparse tables: O(1) range minimum on static data

If the array never changes, precompute the minimum of every range whose length is a power of two: sp[0][i] = a[i], and sp[k][i] = min(sp[k−1][i], sp[k−1][i + 2^(k−1)]) — the range of length 2ᵏ starting at i is two halves of length 2^(k−1). That is O(n log n) values. A query [l, r] picks k = floor(log₂(r − l + 1)), the largest power of two that fits, and covers the range with two blocks of that length, one starting at l and one ending at r:

def query(l, r):
    k = (r - l + 1).bit_length() - 1
    return min(sp[k][l], sp[k][r - (1 << k) + 1])

The two blocks overlap, which is fine for min because min(x, x) = x — the operation is idempotent. For sums, overlap would double-count, so sparse tables are only for idempotent operations (min, max, gcd, bitwise AND/OR). O(1) per query makes them ideal for many queries on static data, such as LCA via Euler tour (al14) or the "minimum over a sliding range" step inside other algorithms.

Merge sort as a counting tool

Counting inversions, smaller-after-self, reverse pairs and range sums can also be done during merge sort. While merging two sorted halves, every time an element from the right half is placed before remaining left-half elements, it is smaller than all of them — that count is the number of inversions it forms across the halves. Variations count pairs satisfying a[i] > 2·a[j] with a separate two-pointer pass before each merge. The complexity is O(n log n), the same as a Fenwick tree, and it needs no compression. Which to use is a matter of taste; Fenwick trees are easier to adapt to online queries, merge sort to pair-counting with arbitrary conditions.

Recognising the pattern

Reach for these structures when a problem mixes range queries with updates, when the constraints (n and q up to 10⁵) rule out O(n) per operation, or when a counting problem asks "how many earlier/later elements are smaller/larger/in a range" — that is a Fenwick tree over compressed values. Static range minimum suggests a sparse table; range updates suggest lazy propagation.

Why the Fenwick tree works

Write a prefix length i in binary, say 13 = 1101₂ = 8 + 4 + 1. The prefix [1, 13] splits into consecutive blocks of lengths 8, 4 and 1: [1, 8], [9, 12], [13, 13]. Those are exactly the blocks stored at tree[8], tree[12] and tree[13], because tree[j] covers the block of length lowbit(j) ending at j. Removing the lowest set bit of 13 gives 12, then 8, then 0 — walking those blocks from right to left. For updates, the blocks containing position p are those tree[j] with j ≥ p and j − lowbit(j) < p; adding the lowest set bit repeatedly enumerates exactly them. Both walks visit at most one index per bit, O(log n). The structure is implicit — no pointers, no node objects — which is why it is so compact and cache-friendly.

Fenwick variants: range updates and 2D

A Fenwick tree over a difference array supports range add and point query. Supporting range add and range sum needs two Fenwick trees: maintain B1 and B2 so that prefix(i) = B1.prefix(i) · i − B2.prefix(i); a range add of v on [l, r] does B1.add(l, v), B1.add(r + 1, −v), B2.add(l, v·(l − 1)), B2.add(r + 1, −v·r). It is a neat algebraic trick and an alternative to lazy segment trees for sums. A 2D Fenwick tree nests the loops over rows and columns to answer rectangle sums under point updates in O(log R · log C) — "Range Sum Query 2D — Mutable".

Order statistics with a Fenwick tree

A Fenwick tree counting values acts as a dynamic multiset with rank queries: the rank of x is prefix(x). The inverse — the k-th smallest — can be found in O(log V) by binary lifting: start at position 0, and for each power of two from the largest down, if pos + step ≤ V and tree[pos + step] < k, move to pos + step and subtract tree[pos + step] from k. Because tree[pos + step] is exactly the count in the next block, the walk descends the implicit tree like a binary search. This gives leaderboards ("what score is the 1000th best?") and sliding-window medians with O(log V) operations.

Square-root decomposition and offline tricks

When an operation is not associative or the update is awkward for a segment tree, splitting the array into about √n blocks of √n elements, each with a precomputed summary, gives O(√n) per operation — for n = 10⁵ about 300 steps, often fast enough and much simpler. Mo's algorithm orders offline range queries so that moving from one range to the next adds and removes few elements, answering q queries in O((n + q)√n) for problems like "number of distinct values in a range" that resist segment trees. Offline processing more generally — sorting queries by their right endpoint and sweeping — turns many hard online problems into a Fenwick tree sweep; "count distinct values in [l, r]" is solved by sweeping r and keeping, per value, only its last occurrence marked in a Fenwick tree.

Choosing what a node stores

The real design question for a new segment-tree problem is "what summary of a range lets me combine two adjacent ranges into the summary of their union?". For sums it is the sum; for minimums the minimum. For "longest run of 1s in a range with flips", a node needs the length of its longest run, its longest prefix run, its longest suffix run and its length — the run across the boundary is the left child's suffix run plus the right child's prefix run. For "number of inversions in a range", a node would need more than a few numbers, which is a sign that a segment tree is the wrong tool. Practise by writing the merge function first; if you can write it in a few lines, the rest of the segment tree is boilerplate.

Beyond the basics

Segment trees extend in many directions. Storing a richer summary per node (best prefix sum, best suffix sum, best subarray sum, total) answers "maximum subarray sum in a range with updates" — the merge of two children combines those four numbers. Persistent segment trees keep every past version by copying only the O(log n) nodes an update changes, enabling queries on historical states and "k-th smallest in a range" in O(log n). Segment trees over time support offline dynamic connectivity with a rollback union-find (al19). For interviews, the essential skills are the three basic structures, lazy propagation for range updates, and the ability to say what summary a node must store for a new query.

In the interview room

Range-query structures are long enough that bugs hide easily, so structure your answer: name the operations needed ("point update and range sum"), pick the simplest structure that supports them (Fenwick unless you need min/max or range updates), state the complexity, and then code. The common bugs: mixing 0-based and 1-based indices in a Fenwick tree (convert once at the API boundary); forgetting that "set a[i] = v" is "add v − a[i]"; querying prefix(l) instead of prefix(l − 1) for a range starting at l; segment tree arrays that are too small (allocate 4n); wrong identity values (0 for sums, ∞ for min); forgetting to push lazy tags before recursing, or pushing with the wrong length; and compressing coordinates without including every value you will query (Reverse Pairs needs 2·a[j]).

Test with a single element, a full-range query, a query on one position, and an update followed by a query that includes and excludes the updated position. If time allows, compare against a brute-force array on random operations — the lab does exactly that.

Interviewers often accept a simpler solution first. If n is small (≤ 10³), say so and offer the O(n²) or sorted-list approach, then describe the O(n log n) structure. For problems like Count of Smaller Numbers After Self, mentioning both the Fenwick and the merge-sort solutions shows breadth. And if a problem only needs static data, a sparse table or prefix sums is the better answer — reaching for a segment tree when prefix sums suffice is a mild negative signal.

On online assessments, the tell-tale constraint is "n, q ≤ 10⁵ (or 2 × 10⁵) with updates between queries". Any per-operation O(n) loop times out at 10¹⁰ total work, which is the cue for a Fenwick or segment tree.

A last interview tip: write the brute-force version alongside the structure (a plain list with O(n) operations) and mention that you would fuzz one against the other. It costs two minutes, and it is exactly how experienced engineers gain confidence in index-heavy code.

In real systems

Peter Fenwick designed his structure in 1994 for arithmetic coding, where a compressor must maintain cumulative frequencies of symbols that change as it adapts — the original "prefix sums with updates" application. Leaderboards need rank queries over changing scores: Redis sorted sets implement them with skip lists whose links store span lengths, which is the same "combine a few precomputed range counts" idea in linked form, giving O(log n) ZRANK. Time-series databases and monitoring systems store pre-aggregated rollups at several resolutions (per minute, hour, day) so a dashboard query over an arbitrary window combines a few coarse buckets with a few fine ones — a segment tree over time in spirit. Order books in trading systems maintain aggregate quantities over price levels for fast "volume up to price p" queries. Game engines and geographic systems use segment-tree and interval-tree variants for collision and range searches, and database engines use similar hierarchical summaries (zone maps, min/max per block) to skip data that cannot match a range predicate.

Fuzz the Fenwick tree and a segment tree against a plain list with random updates and queries.

    import random

class Fenwick:
    def __init__(s, n): s.n, s.t = n, [0] * (n + 1)
    def add(s, i, d):
        i += 1
        while i <= s.n: s.t[i] += d; i += i & -i
    def prefix(s, i):                      # sum of a[0..i-1]
        r = 0
        while i > 0: r += s.t[i]; i -= i & -i
        return r

class SegMin:
    def __init__(s, a):
        s.n = len(a); s.t = [float("inf")] * (2 * s.n)
        s.t[s.n:] = a
        for i in range(s.n - 1, 0, -1): s.t[i] = min(s.t[2 * i], s.t[2 * i + 1])
    def set(s, i, v):
        i += s.n; s.t[i] = v
        while i > 1: i //= 2; s.t[i] = min(s.t[2 * i], s.t[2 * i + 1])
    def query(s, l, r):                    # min of a[l..r-1]
        res, l, r = float("inf"), l + s.n, r + s.n
        while l < r:
            if l & 1: res = min(res, s.t[l]); l += 1
            if r & 1: r -= 1; res = min(res, s.t[r])
            l //= 2; r //= 2
        return res

for _ in range(300):
    n = random.randint(1, 40); a = [random.randint(-9, 9) for _ in range(n)]
    fw, sg = Fenwick(n), SegMin(a)
    for i, v in enumerate(a): fw.add(i, v)
    for _ in range(200):
        i = random.randrange(n); v = random.randint(-9, 9)
        fw.add(i, v - a[i]); sg.set(i, v); a[i] = v
        l = random.randrange(n); r = random.randint(l + 1, n)
        assert fw.prefix(r) - fw.prefix(l) == sum(a[l:r])
        assert sg.query(l, r) == min(a[l:r])
print("Fenwick sums and segment-tree minimums match a plain list")

What this proves: both structures stay exactly consistent with the array under arbitrary interleavings of updates and queries — the property that makes them safe to rely on — and fuzzing against a brute-force list is the fastest way to catch index errors.

Choose and justify

For each scenario, choose a structure and give the cost per operation. (a) A static array of 10⁶ temperatures; 10⁶ queries for the coldest reading between two days. (b) An array of 10⁵ stock prices that change; queries for the total over a range. (c) The same array, but updates are "add x to every price in [l, r]" and queries are "maximum price in [l, r]". (d) A stream of 10⁵ scores; after each new score, report how many earlier scores are strictly higher. (e) 10⁵ integers and 10⁵ offline queries "how many distinct values are in a[l..r]?".

Answer

(a) Sparse table: O(n log n) ≈ 2 × 10⁷ preprocessing, O(1) per query; no updates are needed, and min is idempotent so overlapping blocks are fine. (b) Fenwick tree: O(log n) point update and O(log n) range sum via two prefix queries. (c) Segment tree with lazy propagation: range add tags and range max queries, O(log n) each; a Fenwick tree cannot do range max. (d) Fenwick tree over compressed scores (compress offline if all scores are known; otherwise a Fenwick tree over the value range or a balanced tree / SortedList): for each score, answer seen − prefix(rank) (elements with rank greater than it), then add 1 at its rank. O(log n). (e) Offline sweep: sort queries by r; sweep i from left to right, and for value a[i], if it was seen before at position p, do fw.add(p, −1); then fw.add(i, +1) and record last[a[i]] = i. Each value is now marked only at its last occurrence up to i, so for queries with r = i the answer is fw.range_sum(l, r). O((n + q) log n). This "keep only the last occurrence" trick is a standard way to count distinct elements in ranges.
