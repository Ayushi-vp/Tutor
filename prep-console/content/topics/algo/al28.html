"Design an LRU cache with O(1) get and put." "Design a set that supports insert, delete and getRandom, each in O(1)." "Design a snapshot array." "Design an iterator over a nested list." These "design a class" questions are a fixture of coding interviews, and they test something different from algorithm puzzles. There is rarely a clever idea to discover. Instead, you must meet several complexity targets at once — and no single standard structure meets them all. A hash map finds keys in O(1) but has no order. A linked list moves nodes in O(1) but cannot find them. An array picks a random element in O(1) but deletes from the middle in O(n). The answer is always a combination, kept consistent on every operation.

These questions also mirror real engineering more closely than most interview problems. Every web service has caches with eviction policies; databases keep versions of data for snapshots; operating systems and message brokers use ring buffers; every collection library has iterators. Interviewers like the format because it reveals how you decompose requirements, choose building blocks, reason about invariants, and handle edge cases — exactly what you do when designing a component at work.

This lesson gives a method for any design question, then applies it to the classics: LRU and LFU caches, the O(1) randomised set, snapshot arrays and time-versioned keys, browser history, circular queues, lazy iterators (peeking, nested-list flattening, BST traversal), the All O'one structure, and a miniature Twitter feed. Each design is presented with the invariant that ties its parts together, because a forgotten update to one part is the bug interviewers see most.

The mental model: a toolbox and a requirements list

Think of a carpenter given a list of jobs and a toolbox. No single tool does every job, but each job is easy with the right tool, and the craft is choosing a small set of tools that covers the list. In data-structure design, the jobs are the operations with their required complexities, and the tools are the primitives you already know:

PrimitiveCheap atExpensive at
hash map / setfind, insert, delete by key — O(1)order, min/max, random element
dynamic arrayindex access, append, pop end, random element — O(1)insert/delete in the middle — O(n)
doubly linked listinsert/remove a known node, move to front/back — O(1)find a node — O(n)
heapmin/max O(1), push/pop O(log n)find/delete arbitrary — O(n)
sorted list + bisectsearch, predecessor — O(log n)insert in the middle — O(n)
balanced tree / SortedListordered ops — O(log n)constants and memory
deque / ring bufferpush/pop at both ends — O(1)middle access

The pattern behind most O(1) designs is a hash map that points into an ordered structure. The map provides "find it in O(1)"; the ordered structure (a linked list, an array, a list of buckets) provides "the oldest", "the most frequent", "a random one" or "the next" in O(1). The map stores, for each key, its exact position in the ordered structure, so the two can be updated together.

A method for any design question

  1. List the operations and their targets. Write them down: get O(1), put O(1), evict least recent O(1).
  2. Find the hardest pair. Usually two operations that no single primitive supports together (find by key and find the oldest; delete by value and pick at random).
  3. Combine primitives so each operation is cheap in at least one of them, and make one point into the other.
  4. State the invariant that ties them together, in one sentence.
  5. Walk every operation and check it maintains the invariant, including edge cases (capacity 0 or 1, updating an existing key, removing the last element).

Most designs in this lesson are variations on three shapes: map + linked list (LRU, LFU's buckets, All O'one), map + array (randomised set, snapshot histories, circular buffers), and stack of pending work (iterators). Recognising which shape a new question needs is usually the moment it becomes easy.

Where the toolbox analogy breaks: a carpenter's tools are independent, but data structures in a design share data, and every update must touch all of them. Forgetting to delete a key from the map when its node is evicted, or to update the moved element's index after a swap, leaves the structures disagreeing — a bug that often surfaces only several operations later. The invariant in step 4 is your defence: after writing each method, re-read it against the invariant.

LRU cache

Operations: get(key) and put(key, value), both O(1), evicting the least recently used key when over capacity. The hardest pair is "find by key" (hash map) and "find and move the oldest" (ordered list). Combine a dict from key to node with a doubly linked list ordered by recency, using sentinel head and tail nodes:

class Node:
    __slots__ = ("key", "val", "prev", "next")
    def __init__(self, key=0, val=0):
        self.key, self.val, self.prev, self.next = key, val, None, None

class LRUCache:
    def __init__(self, capacity):
        self.cap, self.map = capacity, {}
        self.head, self.tail = Node(), Node()        # sentinels
        self.head.next, self.tail.prev = self.tail, self.head

    def _unlink(self, n):
        n.prev.next, n.next.prev = n.next, n.prev

    def _push_front(self, n):
        n.prev, n.next = self.head, self.head.next
        self.head.next.prev = n
        self.head.next = n

    def get(self, key):
        n = self.map.get(key)
        if n is None: return -1
        self._unlink(n); self._push_front(n)        # now most recent
        return n.val

    def put(self, key, value):
        if key in self.map:
            n = self.map[key]; n.val = value
            self._unlink(n); self._push_front(n)
            return
        n = Node(key, value)
        self.map[key] = n; self._push_front(n)
        if len(self.map) > self.cap:
            lru = self.tail.prev                    # least recent
            self._unlink(lru); del self.map[lru.key]

Each node stores its key so that eviction can delete the map entry — a detail that is easy to forget. Trace capacity 2: put(1, 1), put(2, 2) → list 2, 1. get(1) → list 1, 2. put(3, 3) → list 3, 1, 2, over capacity, evict 2. get(2) → −1. In Python, collections.OrderedDict implements the same structure: move_to_end(key) on access and popitem(last=False) to evict. Interviewers usually accept it after you explain what it does internally, or ask you to write the linked list.

LFU cache

Evict the least frequently used key, breaking ties by least recently used. Now there are two orderings: by frequency, and by recency within a frequency. The O(1) design keeps:

  • key → (value, freq),
  • freq → OrderedDict of keys with that frequency (insertion order = recency within the bucket),
  • min_freq, the smallest frequency present.
from collections import defaultdict, OrderedDict
class LFUCache:
    def __init__(self, capacity):
        self.cap, self.kv, self.buckets, self.min_freq = capacity, {}, defaultdict(OrderedDict), 0

    def _touch(self, key):                          # increment a key's frequency
        val, f = self.kv[key]
        del self.buckets[f][key]
        if not self.buckets[f]:
            del self.buckets[f]
            if self.min_freq == f: self.min_freq += 1
        self.buckets[f + 1][key] = None
        self.kv[key] = (val, f + 1)

    def get(self, key):
        if key not in self.kv: return -1
        self._touch(key)
        return self.kv[key][0]

    def put(self, key, value):
        if self.cap == 0: return
        if key in self.kv:
            self.kv[key] = (value, self.kv[key][1]); self._touch(key); return
        if len(self.kv) == self.cap:
            old, _ = self.buckets[self.min_freq].popitem(last=False)   # LFU, then LRU
            if not self.buckets[self.min_freq]: del self.buckets[self.min_freq]
            del self.kv[old]
        self.kv[key] = (value, 1); self.buckets[1][key] = None
        self.min_freq = 1                           # a new key always has frequency 1

The subtle parts: min_freq only ever increases by one when its bucket empties during a touch (the touched key moves to min_freq + 1, so that bucket exists), and it resets to 1 on every new insertion. Capacity 0 must be handled explicitly. Everything is O(1).

Insert, delete and getRandom in O(1)

getRandom needs an array (pick a random index). Delete by value needs a hash map (find it). But deleting from the middle of an array is O(n). The trick: order does not matter, so move the last element into the deleted slot and pop the end.

import random
class RandomizedSet:
    def __init__(self):
        self.vals, self.pos = [], {}               # pos[v] = index of v in vals
    def insert(self, v):
        if v in self.pos: return False
        self.pos[v] = len(self.vals); self.vals.append(v); return True
    def remove(self, v):
        if v not in self.pos: return False
        i, last = self.pos[v], self.vals[-1]
        self.vals[i], self.pos[last] = last, i      # move last into the hole
        self.vals.pop(); del self.pos[v]
        return True
    def getRandom(self):
        return random.choice(self.vals)

The order of the two lines in remove matters when v is itself the last element: setting pos[last] = i and then deleting pos[v] (the same key) leaves the map correct. With duplicates allowed, map each value to a set of indices and perform the same swap, updating the moved value's index set.

Versioned data: Snapshot Array and Time Map

Snapshot Array: set(index, val), snap() returning a snapshot id, and get(index, snap_id) returning the value at that snapshot. Copying the array on each snap is O(n). Store history per index instead: a list of (snap_id, value) changes. set appends (current_snap, val), or overwrites the last entry if it already belongs to the current snapshot. get binary-searches the last change with snap_id ≤ the requested id.

import bisect
class SnapshotArray:
    def __init__(self, n):
        self.hist = [[(-1, 0)] for _ in range(n)]   # (snap_id, value); -1: initial 0
        self.snap_id = 0
    def set(self, i, v):
        h = self.hist[i]
        if h[-1][0] == self.snap_id: h[-1] = (self.snap_id, v)
        else: h.append((self.snap_id, v))
    def snap(self):
        self.snap_id += 1
        return self.snap_id - 1
    def get(self, i, sid):
        h = self.hist[i]
        k = bisect.bisect_right(h, (sid, float("inf"))) - 1
        return h[k][1]

set and snap are O(1); get is O(log k) for k changes at that index; memory is proportional to the number of sets. Time Based Key-Value Store is the same design keyed by strings with timestamps (al7). This "append-only history plus binary search" structure is how databases implement multi-version reads, in simplified form.

Bounded and navigable sequences

Circular queue (fixed capacity k): an array of size k, a head index and a size. The tail position is (head + size) % k. Tracking the size, rather than separate head and tail indices alone, removes the ambiguity between "full" and "empty" when head and tail coincide.

class MyCircularQueue:
    def __init__(self, k): self.a, self.head, self.size, self.k = [0] * k, 0, 0, k
    def enQueue(self, x):
        if self.size == self.k: return False
        self.a[(self.head + self.size) % self.k] = x; self.size += 1; return True
    def deQueue(self):
        if self.size == 0: return False
        self.head = (self.head + 1) % self.k; self.size -= 1; return True
    def Front(self): return self.a[self.head] if self.size else -1
    def Rear(self): return self.a[(self.head + self.size - 1) % self.k] if self.size else -1

Browser History: visit(url), back(steps), forward(steps). Keep an array of pages, a current index and an end index. visit writes at current + 1 and sets end = current (logically discarding forward history without deleting anything); back and forward clamp current within [0, end]. All O(1). The two-stack version is simpler to describe but costs O(steps) per navigation.

Lazy iterators

An iterator should produce one element per call without precomputing everything. The pattern: keep a stack of pending work, and on each call do just enough to expose the next element.

BST Iterator (in-order, next and hasNext): keep the stack of nodes on the path of left children (the iterative in-order traversal of al14, spread across calls).

class BSTIterator:
    def __init__(self, root):
        self.stack = []; self._push_left(root)
    def _push_left(self, node):
        while node: self.stack.append(node); node = node.left
    def next(self):
        node = self.stack.pop()
        self._push_left(node.right)              # next smallest lies down the right subtree's left spine
        return node.val
    def hasNext(self):
        return bool(self.stack)

A single next can push many nodes, but every node is pushed once and popped once over the whole traversal: amortised O(1) per call, O(h) memory. Flatten Nested List Iterator keeps a stack of iterators over the nested lists; hasNext descends into lists until an integer is exposed (or everything is exhausted), buffering it for next. Doing the descent in hasNext (rather than next) matters because empty nested lists like [[]] must make hasNext return false. Peeking Iterator caches one element ahead of the underlying iterator so peek can return it without consuming it; fill the cache in the constructor.

All O'one: buckets of keys in a linked list

inc(key), dec(key), getMaxKey(), getMinKey(), all O(1). Counts change by exactly one, so a key only ever moves to a neighbouring count. Keep a doubly linked list of buckets in increasing count order, each bucket holding the set of keys with that count, and a map from key to its bucket. inc moves a key from its bucket to the next one (creating a bucket with count + 1 immediately after if it does not exist) and deletes the old bucket if it becomes empty. dec moves it to the previous bucket (or removes the key at count 1). The minimum key is any key in the first bucket and the maximum any key in the last. It is the LFU idea — frequency buckets — with direct access to both extremes.

A tiny Twitter: merging feeds

postTweet(user, tweet), follow, unfollow, and getNewsFeed(user) returning the 10 most recent tweets from the user and the people they follow. Store each user's tweets in a list with a global increasing timestamp, and followees in a set. The feed is a k-way merge of reverse-chronological lists (al10): push the newest tweet of each relevant user into a max-heap, pop the newest overall, and push that user's next older tweet; stop after 10.

import heapq, itertools
from collections import defaultdict
class Twitter:
    def __init__(self):
        self.clock = itertools.count()
        self.tweets = defaultdict(list)             # user -> [(time, id)]
        self.follows = defaultdict(set)
    def postTweet(self, u, tid):
        self.tweets[u].append((next(self.clock), tid))
    def follow(self, a, b):
        if a != b: self.follows[a].add(b)
    def unfollow(self, a, b):
        self.follows[a].discard(b)
    def getNewsFeed(self, u):
        heap = []
        for v in self.follows[u] | {u}:
            if self.tweets[v]:
                i = len(self.tweets[v]) - 1
                t, tid = self.tweets[v][i]
                heap.append((-t, tid, v, i))
        heapq.heapify(heap); feed = []
        while heap and len(feed) < 10:
            _, tid, v, i = heapq.heappop(heap); feed.append(tid)
            if i:
                t, nid = self.tweets[v][i - 1]
                heapq.heappush(heap, (-t, nid, v, i - 1))
        return feed

Cost O(F + 10 log F) for F followees. Guarding follow against following yourself and using discard (not remove) for unfollow avoids common errors.

Rate limiting and hit counting

"Design a hit counter: hit(timestamp) and getHits(timestamp) returning hits in the last 300 seconds." A deque of timestamps works (pop from the front while older than timestamp − 300), but memory grows with traffic. A fixed design uses a ring of 300 buckets indexed by timestamp % 300, each storing (the second it represents, count): on a hit, if the bucket's stored second is stale, reset it; getHits sums buckets whose stored second is within the window. Memory is O(300) regardless of traffic and each operation is O(300) or O(1) with a running total. It is the sliding-window counter from al6 expressed as a data-structure design, and the same ring-of-buckets idea underlies rate limiters and per-second metrics in monitoring agents.

Recognising the pattern

"Design a class with operations X, Y, Z in O(…)" means: list the operations, find the conflicting pair, and combine primitives — usually a hash map pointing into an ordered structure (linked list, array, buckets, per-key history). Then state the invariant and check every operation against it.

Amortised bounds in iterator designs

Lazy iterators trade a uniform per-call cost for a good average. The BST iterator's next can push h nodes, but the total pushes over a full traversal is n, so n calls cost O(n): amortised O(1). The same aggregate argument (al2) justifies the nested-list iterator. In an interview, state both bounds: "worst case O(h) for a single call, amortised O(1), memory O(h)". If an application needs a hard per-call bound (real-time systems), a structure with threaded pointers (Morris-style, al14) or a precomputed array may be preferable, at the cost of memory or mutation.

Thread safety and real caches

Interview caches are single-threaded; real ones are not. A naive LRU guarded by one lock serialises every read, because even get modifies the list. Production designs reduce contention by sharding the cache into many independent LRUs keyed by hash, by recording accesses in per-thread buffers that are applied to the list in batches (Caffeine's design in Java), or by abandoning exact LRU. Redis, for instance, approximates LRU by sampling a handful of keys and evicting the oldest among them, which avoids maintaining a global list at all; its LFU mode uses a small logarithmic counter per key with decay. CPU caches use pseudo-LRU with a few bits per set. Knowing that "exact LRU is a hash map plus linked list, and real systems approximate it for concurrency and memory" is a strong senior answer to the usual follow-up.

Expiry and lazy deletion

Caches often need time-to-live expiry as well as size-based eviction. Scanning for expired entries is O(n); the usual techniques are lazy deletion — check an entry's expiry when it is read and treat it as missing if stale — plus a background sweep that samples keys or walks a min-heap (or timing wheel) ordered by expiry time. The heap approach has the stale-entry issue from al10: when a key is refreshed, its old heap entry remains and must be skipped when popped. Memcached and Redis both combine lazy expiry on access with periodic active expiry.

Versioning, copy-on-write and persistence

Snapshot Array stores per-element histories. An alternative for snapshotting whole structures is copy-on-write: share the data between versions and copy only what an update changes. Persistent data structures (persistent arrays as trees, persistent segment trees, the hash array mapped tries behind Clojure's and Scala's immutable maps) give every version O(log n) access while sharing almost all memory. Databases implement snapshot isolation with multi-version concurrency control, keeping several versions of each row with transaction timestamps — conceptually the (version, value) lists of this lesson, plus garbage collection of versions no transaction can see.

Choosing between exactness and memory

Several designs have cheaper approximate versions that production systems prefer. Exact LFU needs per-key counters and buckets; Redis's LFU keeps an 8-bit logarithmic counter per key and decays it over time, trading precision for a fixed tiny footprint. Exact distinct counts need a set; HyperLogLog estimates them in kilobytes. Exact top-k needs counts for every key; Count-Min sketches plus a small heap approximate it (al10). In an interview, deliver the exact design first, then mention where you would approximate at scale and what you would lose — that shows judgement about real constraints rather than only puzzle-solving.

Testing designs: model-based fuzzing

Design bugs usually involve sequences of operations, which hand-written tests miss. The effective technique is model-based testing: implement a trivially correct but slow reference ("a list of keys in recency order" for LRU, "a Python set and a random.choice over list(set)" for the randomised set), generate random sequences of operations, and compare outputs after each operation. A few thousand random sequences of length 50 find almost every invariant violation. Libraries like Hypothesis automate this with stateful testing. Mentioning it — and doing it in the lab — shows how you would gain confidence in a design beyond the examples.

In the interview room

Start by restating the operations and targets, then name the combination before writing code: "a dict from key to node and a doubly linked list by recency; the invariant is that the map and the list contain the same keys". Interviewers grade the decomposition as much as the code. Ask about edge cases up front: capacity 0, updating an existing key, behaviour on missing keys, whether values can repeat.

The common bugs are bookkeeping slips: not storing the key in the node (so eviction cannot delete the map entry); forgetting to move an updated key to the front in put; deleting from the map but not the list, or vice versa; updating the moved element's index after the pop instead of before in RandomizedSet; mishandling the case where the removed element is the last one; min_freq not reset on insert in LFU; hasNext that does not handle empty nested lists; and off-by-one errors in circular indices. After writing each method, re-check it against the invariant line by line.

Expect scale follow-ups: "how would this work with multiple threads?" (locks, sharding, approximate eviction), "the cache is distributed across machines" (consistent hashing of keys to nodes, each running a local LRU), "values are large" (store sizes and evict by total bytes, not count), and "the feed has celebrity users" (hybrid push/pull fan-out). Having one or two sentences for each turns a coding question into a small system-design conversation, which senior interviewers appreciate.

On online assessments, design problems are graded by hidden sequences of calls, often including the edge cases above. A quick local test that replays the example sequence and a few hand-made edge sequences (capacity 1, repeated puts of the same key, removing the last element) catches most failures before submission.

A final habit for these rounds: once the code is written, walk one complete scenario out loud through all structures at once — "put a, put b, get a, put c at capacity 2: map has a and c, list is c then a, b was evicted from both". Saying the state of every structure after each step is the fastest way to catch the forgotten update before the interviewer does.

In real systems

These designs are everywhere. Python's own functools.lru_cache is a dict plus a circular doubly linked list, exactly this lesson's LRU. Memcached uses per-slab LRU lists; Redis offers approximated LRU and LFU eviction policies by sampling; CDNs and browsers cache objects with LRU-like policies plus expiry; database buffer pools use LRU variants (often with "midpoint insertion" or clock algorithms) to keep hot pages in memory. Ring buffers are the backbone of high-throughput systems: the Linux kernel's io_uring and network drivers use them to pass work between producer and consumer without locking, and the LMAX Disruptor built a trading platform on a single ring buffer. Versioned key-value storage with timestamps is how databases provide snapshot reads (MVCC) and how systems like Bigtable store multiple cell versions. Social feeds are built from per-user timelines merged or precomputed exactly as in the Twitter design, with hybrid fan-out for accounts with huge follower counts.

    import random

class SlowLRU:                                   # reference model: list in recency order
    def __init__(self, cap): self.cap, self.order, self.vals = cap, [], {}
    def get(self, k):
        if k not in self.vals: return -1
        self.order.remove(k); self.order.append(k); return self.vals[k]
    def put(self, k, v):
        if k in self.vals: self.order.remove(k)
        self.order.append(k); self.vals[k] = v

        if random.random() < 0.5:
            assert a.get(k) == b.get(k)
        else:
            v = random.randint(0, 99); a.put(k, v); b.put(k, v)
print("LRU matches the reference model")

Design under new requirements

"Design a cache with capacity C supporting get(key) and put(key, value, ttl_seconds), O(1) average per operation. Entries expire ttl seconds after their last put. When full, evict the least recently used entry among those not yet expired; expired entries should be removed first." Describe the structures, the invariant, and how expiry is handled.

Answer

Start from LRU: a dict key → node (storing key, value and expires_at) and a doubly linked list by recency with sentinels. Add expiry with lazy deletion: get checks expires_at against the current time and, if expired, unlinks the node, deletes the key and returns a miss — O(1). For "expired entries removed first" when the cache is full, keep a min-heap of (expires_at, key, version) alongside: on put, push a new entry and bump the key's version so older heap entries become stale. Before evicting, pop heap entries while the top is stale (version mismatch or key gone) — and if the top is expired, remove that key instead of the LRU one. The heap makes put O(log C) rather than strictly O(1); if O(1) is mandatory, use a timing wheel (buckets of keys by expiry second, swept as time advances) for amortised O(1). Invariant: every live key appears exactly once in the dict and once in the list; the heap may hold stale entries but never misses a live key's current expiry. Edge cases: put on an existing key refreshes both value and TTL and moves it to the front; capacity 0; a key that expires between a get's lookup and its return (use one timestamp per call). At scale, add a periodic sampler that removes expired keys so memory does not fill with dead entries that are never read — the approach Redis uses.
