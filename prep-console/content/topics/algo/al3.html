Suppose a shop keeps its daily revenue for the last year in an array of 365 numbers, and a dashboard lets managers ask "what was revenue between day 40 and day 95?" A simple implementation adds up the 56 numbers for each question. That is fine for one question. Now the dashboard is used by 2,000 store managers, each looking at 50 ranges, over ten years of data — and every question re-adds thousands of numbers that were already added for the previous question. The work is almost entirely repeated.

The same waste appears constantly in interview problems: "sum of a subarray", "how many subarrays sum to k", "apply these 10⁵ increments to ranges", "average of every window". The brute force recomputes a sum from scratch for each range, so it costs O(length) per range and O(n²) or worse overall. With n = 10⁵, that is 10¹⁰ operations and a guaranteed time-out.

The fix is one of the simplest and most useful ideas in algorithms: compute the running total once, and then any range is the difference of two running totals. Revenue from day 40 to 95 is "revenue up to day 95" minus "revenue up to day 39". Each question becomes one subtraction.

This lesson builds that idea and its relatives, in order: the prefix-sum array and its off-by-one-proof convention; prefix sums combined with a hash map to count subarrays with a target sum (one of the most-asked medium problems); the same trick with XOR and remainders; difference arrays, which run the idea backwards to make range updates cheap; 2D prefix sums for grids; and Kadane's algorithm for the maximum subarray, a neighbouring linear scan that is often grouped with them.

The mental model: the odometer

A car's odometer shows the total distance driven since the car was made. If you want to know how far you drove on a particular trip, you do not need a record of every kilometre; you note the odometer at the start and the end, and subtract. The odometer is a running total, and the trip distance is the difference of two running totals.

A prefix-sum array is an odometer for an array. For an array a, define pre[i] as the sum of the first i elements. Then the sum of any contiguous slice — any subarray a[l..r] — is the reading at the end minus the reading at the start: pre[r+1] − pre[l].

Two things in that picture are worth fixing in memory. First, pre has one more entry than a, and pre[0] = 0. This sentinel means a range that starts at index 0 needs no special case: its sum is pre[r+1] − pre[0]. Second, think of pre[i] as living on the boundary before element i. Then "sum from boundary l to boundary r+1" reads naturally, and the +1 stops being mysterious.

Building the array is one pass: pre[i+1] = pre[i] + a[i]. After that, every range sum is O(1). So q queries cost O(n + q) instead of O(n·q).

The idea generalises to any combining operation you can undo. Sums undo with subtraction. XOR undoes with XOR (x ^ x = 0), so prefix XORs give the XOR of any range. Counts are sums of 0/1 indicators, so "how many vowels in s[l..r]" is a prefix count. What does not work directly is max or min: knowing the maximum of the first 9 elements and of the first 3 does not tell you the maximum of elements 3 to 8. Those need other structures (al27).

It helps to see the cost difference concretely. With n = 100,000 and q = 100,000 queries, each covering on average half the array, the brute force adds about 5 × 10⁹ numbers — minutes in Python. The prefix version adds 100,000 numbers once and then does 100,000 subtractions: a fraction of a second. The answer is identical; only the repeated work is gone. This is the purest example of the principle from al1, "the optimal solution is the brute force with one kind of repeated work removed", and it is worth recognising the shape, because the same shape hides inside much harder problems.

The analogy breaks in one useful way: an odometer only goes forward, but you will also run the idea in reverse — storing differences so that a range update becomes two point changes. That is the difference array, covered below.

Building and using a prefix array

The canonical code, with the invariant written as a comment so the indexing is never in doubt:

def build_prefix(a):
    pre = [0] * (len(a) + 1)
    for i, x in enumerate(a):
        pre[i + 1] = pre[i] + x      # invariant: pre[i] = sum(a[:i])
    return pre

def range_sum(pre, l, r):            # inclusive l..r
    return pre[r + 1] - pre[l]

In Python, itertools.accumulate(a, initial=0) builds the same list in one line. Trace it on a = [3, 1, 4, 1, 5]: pre = [0, 3, 4, 8, 9, 14]. The sum of a[1..3] is pre[4] − pre[1] = 9 − 3 = 6, which matches 1 + 4 + 1.

When you see "many range-sum queries on an array that does not change", this is the whole solution. It is also a building block inside many other solutions: average of every window of size k is (pre[i+k] − pre[i]) / k; "is there a subarray of length at least L with average at least x" subtracts x from every element and asks about prefix sums; "pivot index" asks for i where pre[i] equals total − pre[i+1].

The key upgrade: prefix sums plus a hash map

Now a harder question: how many subarrays have sum exactly k? The brute force tries all O(n²) pairs (l, r). With prefix sums each pair is O(1), but there are still n² pairs. Where is the repeated work?

Fix the right end r. A subarray a[l..r] has sum k exactly when pre[r+1] − pre[l] = k, i.e. when pre[l] = pre[r+1] − k. So for each r we are asking: "how many earlier prefix values equal one specific number?" That is a repeated search for a specific value — the signal for a hash map (al4). Keep a dictionary from prefix value to how many times it has appeared so far; then each r takes O(1).

def subarray_sum(a, k):
    count = {0: 1}          # the empty prefix: sum 0 seen once
    run = ans = 0
    for x in a:
        run += x                        # run = pre[r+1]
        ans += count.get(run - k, 0)    # earlier prefixes equal to run-k
        count[run] = count.get(run, 0) + 1
    return ans

Three subarrays: [1, 2], [2, 1], and [1, 2, 1, −1]. Notice two decisions. The seed {0: 1} represents the empty prefix, so subarrays starting at index 0 are counted (the first hit, [1, 2], needed it). And we look up before recording the current prefix, so a subarray is never empty when k = 0.

This works with negative numbers, which is why it beats the sliding window here: a window needs "adding an element never decreases the sum", which only holds for non-negative values (al6).

Three variations use the same skeleton with a different value stored:

  • Longest subarray with sum k (or with equal 0s and 1s, after mapping 0 → −1 so the target is 0): store the first index of each prefix value instead of a count, seeded with {0: −1}. The longest subarray ending at r starts just after the earliest matching prefix.
  • Subarrays with sum divisible by k: two prefixes with the same remainder mod k differ by a multiple of k. Count remainders instead of values.
  • Subarrays with XOR equal to k: prefix XOR, and look up run ^ k, because XOR is its own inverse.

Difference arrays: cheap range updates

Now the opposite problem: you receive many updates "add v to every element of a[l..r]", and only at the end do you need the final array. Applying each update directly costs O(r − l + 1), so 10⁵ updates on 10⁵ elements is 10¹⁰ steps.

Turn the prefix idea around. Store a difference array d, where d[i] = a[i] − a[i−1] — how much the value changes at position i. The original array is the prefix sum of d. Adding v to a whole range a[l..r] changes only two differences: the value jumps up by v at l, and drops back by v at r + 1. Everything in between keeps the same differences.

def apply_updates(n, updates):          # updates: (l, r, v), inclusive
    d = [0] * (n + 1)                   # one extra slot for r + 1 = n
    for l, r, v in updates:
        d[l] += v
        d[r + 1] -= v
    out, run = [], 0
    for i in range(n):
        run += d[i]
        out.append(run)
    return out

Each update is O(1) and the rebuild is O(n), so the total is O(n + u) for u updates. This is the solution to "Corporate Flight Bookings" (seats booked on ranges of flights) and "Car Pooling" (passengers getting on at one stop and off at another: +p at pickup, −p at drop-off, and the running sum is the number on board — fail if it ever exceeds capacity). The same idea, with sorted event points instead of an array, becomes the sweep line in al11.

Prefix sums in two dimensions

For a grid, let P[r][c] be the sum of the rectangle from the top-left corner (0, 0) to (r−1, c−1), with an extra row and column of zeros as sentinels. Each cell is built from three neighbours:

P[r+1][c+1] = g[r][c] + P[r][c+1] + P[r+1][c] - P[r][c]

The rectangle above and the rectangle to the left overlap in the top-left block, which was added twice, so it is subtracted once. Querying a rectangle (r1, c1)–(r2, c2) uses the same inclusion–exclusion in reverse: take the big rectangle to (r2, c2), remove the strip above r1 and the strip left of c1, and add back their overlap, which was removed twice.

def rect(P, r1, c1, r2, c2):
    return P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1]

Building is O(R·C) and each query is O(1). This solves "Range Sum Query 2D" directly, and it is the standard trick for "count something in every k×k sub-square" problems, such as image processing filters and "largest square of 1s with sum constraints".

Kadane's algorithm: the maximum subarray

"Find the contiguous subarray with the largest sum" looks like a prefix-sum problem — maximise pre[r+1] − pre[l] — and that view works: scan r while tracking the minimum prefix seen so far. The more common formulation is Kadane's algorithm, which is really a tiny dynamic program. Let cur be the best sum of a subarray that ends exactly at the current index. For the next element x there are only two options: extend the previous best (cur + x) or start fresh at x. Take the larger:

def max_subarray(a):
    cur = best = a[0]
    for x in a[1:]:
        cur = max(x, cur + x)     # extend, or restart here
        best = max(best, cur)
    return best

Trace [-2, 1, -3, 4, -1, 2, 1, -5, 4]: cur goes −2, 1, −2, 4, 3, 5, 6, 1, 5 and best ends at 6, the subarray [4, −1, 2, 1]. Initialise from the first element rather than 0, or an all-negative array wrongly returns 0 (the empty subarray), unless the problem allows empty. The restart rule has a clean meaning: if the best subarray ending at the previous index has a negative sum, it can only hurt, so drop it.

Variants follow from the DP view. Maximum product subarray: a negative number turns the smallest product into the largest, so track both the max and min product ending here. Circular maximum subarray: the answer either does not wrap (plain Kadane) or wraps, in which case it equals total − (minimum subarray).

Prefix sums on strings and counts

Prefix sums are not only for numeric arrays. Any question of the form "how many X are in positions l..r" turns into prefix counts of a 0/1 indicator. For example, "for each query (l, r), how many vowels are in s[l..r]?" — build cnt[i+1] = cnt[i] + (s[i] in "aeiou"), and each query is cnt[r+1] − cnt[l]. If you need counts of all 26 letters for many ranges (say, "can s[l..r] be rearranged into a palindrome?"), keep 26 prefix arrays, or one prefix array of 26-element count vectors, or — the elegant version — a single prefix bitmask where bit c flips each time letter c appears. A range can be rearranged into a palindrome when at most one letter has an odd count, which is "the XOR of two prefix masks has at most one bit set". That turns a 26-letter count comparison into one XOR and a bit test (al24).

The general lesson: decide what quantity you would compute for a range in the brute force, check that it combines with an invertible operation, and store its running version.

Recognising the pattern

Reach for prefix techniques when you see: "sum/count/XOR of a subarray or range", "number of subarrays with property X" where X is about a sum, "many queries on a fixed array", "apply many range increments", or a grid with "sum of a rectangle". Check the precondition: the combine must be invertible (sum, count, XOR — not max/min), and for plain prefix arrays the data must not change between queries. If values change, move to a Fenwick tree (al27).

Before coding, run a short checklist that catches nearly every prefix bug. Is my prefix array one longer than the input, with a zero at the front? Is my range formula pre[r+1] − pre[l] for an inclusive range — and did I convert the problem's indexing (some problems give 1-based l and r) exactly once? For the hash-map version, did I seed the map with the empty prefix, and do I look up before I insert? For first-index maps, do I store only the first occurrence (for longest) or update every time (for shortest)? For difference arrays, is the array n + 1 long so that d[r+1] never goes out of bounds, and is the end of the range inclusive or exclusive in this problem? Five questions, thirty seconds, and they cover the mistakes interviewers see most often.

Why the hash map makes it linear: pairs become lookups

Many "count subarrays" problems are really "count pairs of prefixes (i, j) with i < j and some relation between pre[i] and pre[j]". When the relation is equality after a shift (pre[i] = pre[j] − k) or equality of a derived key (same remainder, same XOR), a hash map counts all such pairs in one pass: process j left to right and look up how many earlier i match. When the relation is an inequality — "count subarrays with sum at most k" with negative numbers — a hash map cannot help, because there is no single key to look up. Then you need the earlier prefixes kept in sorted order: a merge-sort count or a Fenwick tree over compressed prefix values, giving O(n log n). Recognising "equality → hash map, inequality → sorted structure" is a senior-level shortcut.

Remainders and the pigeonhole principle

"Is there a non-empty subarray whose sum is divisible by n?" — always yes for an array of n integers. There are n + 1 prefix sums (including pre[0]) but only n possible remainders mod n, so two prefixes share a remainder, and the subarray between them is divisible by n. This pigeonhole argument is the theory behind the remainder-map technique and occasionally appears as a "prove it" follow-up. It also explains a common trap: in languages like Java and C++, the remainder of a negative number is negative, so −1 % 5 is −1, not 4, and identical residues would be stored under different keys. Normalise with ((x % k) + k) % k.

Why this is O(n) time but O(n) space, and when space matters

The hash-map version stores up to n + 1 distinct prefix values. For an array of 10⁷ elements that is a dictionary of ten million entries — several hundred megabytes in Python. If the problem only needs existence ("is there a subarray with sum k?") and values are non-negative, a two-pointer window uses O(1) space. If values are bounded and small, a plain array indexed by prefix value (shifted to be non-negative) replaces the dictionary with something many times smaller and faster. Interviewers sometimes probe exactly this with "what if memory is tight?", and the answer depends on which precondition you can exploit.

Overflow and very large sums

Prefix sums grow. With 10⁵ values up to 10⁹, the total reaches 10¹⁴, which overflows 32-bit integers. Python integers are unbounded, so this never bites in Python, but in Java or C++ use 64-bit (long). If an answer is required modulo 10⁹ + 7, store prefixes mod p and compute range sums as (pre[r+1] − pre[l] + p) % p so the result is not negative. Mentioning overflow when you discuss a prefix solution is a good signal even in Python interviews, because it shows you know the code would be ported.

Higher-order differences and polynomial updates

A difference array handles "add a constant over a range". If an update adds an arithmetic progression (1, 2, 3, … over the range), take differences twice: a second-order difference array turns it into a constant number of point updates, and two prefix passes rebuild it. This generalises: adding a polynomial of degree k needs k + 1 levels of differences. It is rare in interviews but appears in harder online assessments ("add 1, 2, 3, … to a range"), and it shows the structure behind the trick: prefix sum and difference are inverse operations, like integration and differentiation.

Minimum-prefix view of the maximum subarray

Kadane's algorithm and prefix sums are two views of the same problem. The maximum subarray ending at r is pre[r+1] minus the smallest prefix before it. So scanning r while maintaining min_prefix gives best = max(best, pre[r+1] − min_prefix). This view generalises where Kadane's does not: "maximum subarray sum with length at least L" keeps the minimum over prefixes at least L positions back; "maximum subarray sum not exceeding k" needs the smallest prefix that is at least pre[r+1] − k, which requires a sorted structure and binary search — O(n log n). Knowing both views lets you adapt to whichever constraint the follow-up adds.

Static range queries beyond sums

For non-invertible operations on a static array, a sparse table precomputes the answer for every range whose length is a power of two, in O(n log n). A query for min(a[l..r]) takes two overlapping power-of-two blocks covering [l, r] and returns the min of the two, in O(1). Overlap is harmless because min and max are idempotent (min(x, x) = x); for sums, overlap would double-count, which is why sums use prefix arrays instead. When the array changes, both options give way to a segment tree, covered in al27.

In the interview room

Prefix techniques are graded on two things: whether you see that the brute force recomputes range sums, and whether your indices are exactly right. The most common failure is an off-by-one at the boundary — using pre[r] − pre[l] for an inclusive range, or forgetting the {0: 1} seed so subarrays starting at index 0 are missed. Write the invariant ("pre[i] is the sum of the first i elements") as a comment before writing the loop, and test the range that starts at index 0 and the one that ends at the last index specifically.

The second common failure is reaching for a sliding window on a sum problem with negative numbers. The window gives the right answer on the examples (which often have only positives) and wrong answers on hidden tests. Ask "can values be negative?" in step 1 of the method, and if they can, use prefix sums with a hash map.

Interviewers often extend the problem with a follow-up. "Now the array changes between queries" means a Fenwick tree. "Now return the subarray itself, not the count" means storing first indices instead of counts. "Now it is a stream" means the prefix-plus-hash-map version already works online, because it only looks backwards — say so.

Finally, expect the "explain it to me" probe. Interviewers ask "why do you seed the map with zero?" or "why do you look up before inserting?" to check that you derived the solution rather than memorised it. The best answers tie each line back to the equation pre[l] = pre[r+1] − k: the seed is the l = 0 case, and the order of operations guarantees l ≤ r so the subarray is non-empty. Candidates who can say that in one sentence each come across as fluent; candidates who say "that is how the template goes" invite a harder follow-up.

On online assessments, prefix sums are a frequent "hidden" requirement: the problem looks like a simple loop, but the constraints (n and q both up to 10⁵ or 2 × 10⁵) make the per-query loop time out. Read the constraints before you design, and if you see many queries over a static array, build the prefix array first.

In real systems

Prefix sums are everywhere once you look for them. Databases and analytics engines precompute cumulative aggregates so dashboards can answer arbitrary date ranges instantly — the revenue example from the start of the lesson. Image processing uses 2D prefix sums under the name summed-area table or integral image; the Viola–Jones face detector (2001) used them to compute thousands of rectangle features per image in constant time each, which is what made real-time face detection practical on early-2000s hardware. Time-series systems store cumulative counters (Prometheus counters are monotonically increasing running totals) and compute rates as differences between two samples — exactly the odometer model, with the same pitfall: when a counter resets because a process restarts, the difference goes negative and must be handled. Difference arrays appear in scheduling and capacity planning: booking systems record "+1 at check-in, −1 at check-out" and a running sum gives occupancy on every day.

def brute(a, k):
    return sum(1 for l in range(len(a)) for r in range(l, len(a))

def prefix_hash(a, k):
    count, run, ans = {0: 1}, 0, 0
    for x in a:
        run += x
        ans += count.get(run - k, 0)
        count[run] = count.get(run, 0) + 1
    return ans

        s += x
        while s > k and left <= right:
            s -= a[left]; left += 1
        if s == k and left <= right: ans += 1
    return ans

Diagnose the bug

A candidate writes this to count subarrays with sum k and it fails the test a = [3], k = 3 (expected 1, returns 0). Find the bug, explain it in one sentence, and fix it.

def count(a, k):
    seen, run, ans = {}, 0, 0
    for x in a:
        run += x
        seen[run] = seen.get(run, 0) + 1
        ans += seen.get(run - k, 0)
    return ans
Answer

There are two bugs. First, seen is not seeded with {0: 1}, so the empty prefix is missing and no subarray starting at index 0 can be found — that is why [3] with k = 3 returns 0. Second, the current prefix is recorded before the lookup; when k = 0 this counts the current prefix against itself, i.e. an empty subarray, so every index adds at least one spurious match. The fix is to initialise seen = {0: 1} and swap the two lines so the lookup happens before the insert. A good way to explain it out loud: "pre[l] must come from strictly earlier positions, including the empty prefix at position 0".

Choose the technique

A hotel has 10⁵ bookings, each (check-in day, check-out day), over a 365-day year. Find the maximum number of rooms occupied on any night. Which technique, what complexity, and what is the one boundary decision you must ask about?

Answer

Difference array over days: +1 at check-in, −1 at check-out, then a prefix sum gives occupancy each night and the answer is its maximum. O(bookings + days) time, O(days) space. The boundary question: does a guest occupy the room on the check-out night? Normally not — a stay [in, out) occupies nights in..out−1 — so the −1 goes at index out, not out + 1. If days were up to 10⁹ instead of 365, the array would be too large; sort the 2·10⁵ events instead and sweep them, which is the sweep-line technique of al11.
