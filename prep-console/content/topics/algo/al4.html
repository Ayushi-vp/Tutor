An engineer is asked to find which user IDs appear more than once in a log of 200,000 sign-ups. The first version compares every entry with every other entry: about 2 × 10¹⁰ comparisons. In Python that takes hours. A colleague rewrites it in five lines: walk through the log once, and for each ID ask "have I seen this before?" using a set. It finishes in a tenth of a second. Nothing clever happened to the logic; the only change is that the question "have I seen this?" went from scanning everything seen so far to a single lookup.

That question — have I seen this value, where, and how many times? — is the most common kind of repeated work in interview problems. Two Sum asks it for the complement of every element. Anagram problems ask it for every letter. "First unique character", "longest consecutive sequence", "contains duplicate within k", "group the anagrams", "count pairs with difference k", "isomorphic strings": all of them have a brute force that searches again and again, and all of them become linear when each search is replaced by a hash lookup.

Hashing is therefore the first optimisation to try in step 4 of the method. It is also a building block inside later patterns: sliding windows track counts in a map (al6), graph searches track visited nodes in a set (al16), and dynamic programming caches answers in a map (al21). Getting fluent with it pays off everywhere.

This lesson covers what a hash table actually does and what it costs; the three roles a hash structure plays (membership, position, count); the canonical-key idea for grouping; and a set of classic tricks — complement lookup, starting only from sequence starts, last-seen indices, two-way maps for bijections, and meet-in-the-middle counting — each with a worked trace.

The mental model: a coat check

At a theatre coat check, you hand over your coat and get a numbered ticket. When you come back, the attendant does not search through every coat on every rack; they read your number and go straight to that hook. A hash table works the same way. A hash function turns a key (a number, a string, a tuple) into an integer, the table uses that integer to pick a slot called a bucket, and the value is stored there. Looking the key up later recomputes the same hash and goes straight to the same bucket. No scanning, so the cost does not grow with the number of stored items.

The analogy breaks in one important way. Coat-check tickets are unique, but hash values are not: two different keys can land in the same bucket, which is called a collision. The table must handle it — by storing several entries per bucket or by probing for another free slot — and then compare the actual keys to find the right one. With a good hash function and a table that grows as it fills, collisions are rare and short, so operations are O(1) on average (expected). With a terrible hash function, or keys chosen by an attacker to collide, everything lands in one place and each operation degrades to O(n).

Three roles, two structures

In Python you use two hash structures: a set stores keys only, and a dict stores key → value pairs. Interview problems use them in three roles, and naming the role makes the design obvious:

  • Membership — "have I seen x?" — a set. Duplicate detection, visited nodes, "is the complement present?".
  • Position — "where did I see x?" — a dict from value to index (first, last, or all). Two Sum, "nearest duplicate", longest subarray with a property.
  • Count — "how many times have I seen x?" — a dict from value to count, usually collections.Counter. Anagrams, top-k frequent, majority element, window character counts.

A useful habit is to say the role and the key out loud as part of step 4: "the inner loop searches for target − x, so I want a map from value to index, keyed by value". Once you can say that sentence, the code almost writes itself, and the interviewer hears that you chose the structure for a reason rather than out of habit.

It is also worth knowing what a hash structure cannot do. It has no order: you cannot ask a set for "the smallest element greater than x" or "all keys between 10 and 20" without scanning everything. Questions like those need sorting, binary search (al7), a heap (al10) or a balanced search tree. If a follow-up adds an ordering requirement to a hashing problem, that is your cue to switch structures.

Whenever your brute force has an inner loop that answers one of those three questions, a hash structure replaces it, and the solution usually drops from O(n²) to O(n).

Membership: the set

The simplest use: detect a duplicate. Walk the array once; before adding each value, check whether it is already in the set.

def has_duplicate(a):
    seen = set()
    for x in a:
        if x in seen:
            return True
        seen.add(x)
    return False

O(n) expected time, O(n) space. Compare the two alternatives you should mention: the double loop (O(n²) time, O(1) space) and sorting then comparing neighbours (O(n log n) time, O(1) extra space with an in-place sort). Choosing between them is a time–memory trade-off, and saying so is part of a strong answer.

A set also gives fast set algebra: a & b (intersection), a | b (union), a - b (difference). "Find the common elements of two arrays" is set(a) & set(b), O(n + m).

Position: value → index, and the complement trick

Two Sum is the template for the position role, and it introduces the complement idea. For each element x, the partner we need is target − x. Instead of searching for it, we look it up among the elements already passed:

def two_sum(a, target):
    where = {}                         # value -> index, for a[0..i-1]
    for i, x in enumerate(a):
        if target - x in where:
            return [where[target - x], i]
        where[x] = i
    return []

The same move solves many "pair" problems once you write down what the partner must be. "Count pairs with difference k": the partner of x is x − k or x + k. "Count pairs whose sum is divisible by 60" (song durations): the partner of remainder r is remainder (60 − r) % 60, so count remainders in a map. "Find a pair of equal values at most k apart": store the last index of each value, and check i − last[x] ≤ k.

Which index to store depends on the question. For "longest" questions you want the first occurrence (to maximise the distance); for "nearest" or "within k" questions you want the last. For "all pairs" you store a count or a list.

Count: frequency maps

A frequency map answers "how many times does each value occur?" in one pass. Python's Counter does it in one line, and also gives most_common(k).

from collections import Counter
def is_anagram(s, t):
    return len(s) == len(t) and Counter(s) == Counter(t)

def first_unique(s):
    c = Counter(s)                 # pass 1: count everything
    for i, ch in enumerate(s):     # pass 2: in original order
        if c[ch] == 1:
            return i
    return -1

The two-pass shape is common: count everything first, then make a second pass that uses the counts. When the alphabet is small and known — lowercase English letters — a list of 26 integers indexed by ord(ch) - ord('a') does the same job faster and with fixed memory, and some interviewers like to see that you know it.

Counting also gives quick tests of feasibility. "Can the letters of magazine build note?" — every count in Counter(note) must be at most the count in Counter(magazine); in Python, not (Counter(note) - Counter(magazine)). "Can this string be rearranged into a palindrome?" — at most one letter may have an odd count.

Grouping by a canonical key

"Group these words into anagram groups" asks you to put items into the same bucket exactly when they are equivalent. The trick is to compute a canonical key: a value that is identical for equivalent items and different for non-equivalent ones. Then a defaultdict(list) does the grouping.

from collections import defaultdict
def group_anagrams(words):
    groups = defaultdict(list)
    for w in words:
        key = [0] * 26
        for ch in w:
            key[ord(ch) - 97] += 1
        groups[tuple(key)].append(w)   # list -> tuple: hashable
    return list(groups.values())

Trace it on ["eat", "tea", "tan", "ate", "nat", "bat"]: "eat", "tea" and "ate" all produce the count tuple with a, e and t equal to 1, so they share a key; "tan" and "nat" share another; "bat" is alone. Two choices of key are common. The sorted word ("".join(sorted(w))) is simplest but costs O(L log L) per word of length L. The count tuple costs O(L) plus a fixed 26. Both must be hashable: a Python list cannot be a key, because it could change after insertion and break the table, so convert it to a tuple.

Canonical keys appear well beyond anagrams. "Group strings that are shifts of each other" ("abc", "bcd", "xyz"): key = the tuple of differences between consecutive letters mod 26. "Find duplicate subtrees": key = a serialisation of each subtree. "Group points on the same line through the origin": key = the reduced fraction (dy/g, dx/g) with a sign convention. The question to ask is always "what representation is equal exactly when the items should be grouped?"

Starting only from the start: Longest Consecutive Sequence

"Given an unsorted array, find the length of the longest run of consecutive integers, in O(n)." Sorting gives O(n log n), so the O(n) requirement is a hint to use a set. Put every number in a set, and then for each number count upward while the next number is present. The danger is that this counts the same run many times: in the run 1, 2, 3, 4, starting from 1 counts 4, from 2 counts 3, and so on — O(n²) on one long run.

The fix is to only start counting from numbers that are the start of a run: x is a start exactly when x − 1 is not in the set.

def longest_consecutive(a):
    s = set(a)
    best = 0
    for x in s:
        if x - 1 not in s:             # x starts a run
            y = x
            while y + 1 in s:
                y += 1
            best = max(best, y - x + 1)
    return best

Iterating over the set (not the array) also handles duplicates for free. This "only start from the start" trick is a small instance of a general idea: when a nested loop could revisit the same elements, find a condition that assigns each element to exactly one outer iteration.

Two-way maps: bijections

"Are 'egg' and 'add' isomorphic?" — can each character of s be replaced consistently to get t, with no two characters mapping to the same one? A single map s→t checks consistency in one direction only. With s = "ab", t = "cc", the map {a: c, b: c} is consistent, yet two characters map to c, so the strings are not isomorphic. You need a second map t→s, and both must agree at every position. The same structure solves "Word Pattern" (pattern letters ↔ words). Whenever a problem says "one-to-one" or "bijection", plan for two maps.

Meet in the middle: counting with half-sums

"Given four arrays of length n ≤ 200, count tuples with A[i] + B[j] + C[k] + D[l] = 0." The brute force is O(n⁴) = 1.6 × 10⁹. Split the four arrays into two pairs. Count every possible a + b in a Counter (n² = 40,000 sums). Then for every c + d, the matching first halves are those summing to −(c + d), and the Counter tells you how many in O(1). Total O(n²). This is the complement trick applied to sums of groups rather than single elements, and it is called meet in the middle. The same idea turns subset-sum on 40 items from 2⁴⁰ (about 10¹²) into two lists of 2²⁰ (about 10⁶) sums each.

Composite keys: Sudoku and grids

Keys can be tuples, which lets one set track several facts. To validate a Sudoku board, every digit may appear once per row, column and 3×3 box. Store keys such as ("row", r, d), ("col", c, d) and ("box", r // 3, c // 3, d) in one set; if any key is already present when you add it, the board is invalid. Grid problems often use a set of (r, c) tuples for visited cells, which is clearer than a 2D boolean array when the grid is sparse or unbounded.

Counting without a map: the majority element

Sometimes a count can be kept with O(1) memory. "Find the element that appears more than n/2 times" can be solved with a Counter (O(n) space), but the Boyer–Moore majority vote does it with two variables: a candidate and a counter. Walk the array; if the counter is 0, adopt the current element as candidate; then add 1 if the element equals the candidate and subtract 1 otherwise. Each non-majority element can cancel at most one majority element, and the majority has more than half, so it survives as the final candidate. Trace [2, 2, 1, 1, 1, 2, 2]: the candidate goes 2 (count 1, 2), then 1 and 1 bring it to 0, the next 1 becomes the candidate, 2 cancels it, and the last 2 becomes the candidate with count 1 — answer 2. If the majority is not guaranteed to exist, a second pass must verify the candidate's count. Mentioning this after giving the Counter solution is a good way to answer "can you do it in O(1) space?".

Hashing, sorting or a plain array?

Three tools answer "count or find equal things", and choosing well is part of the score. A plain array indexed by value is the fastest when values are small non-negative integers or characters from a known alphabet: no hashing, no collisions, perfect cache behaviour. A hash map handles arbitrary keys in O(1) expected per operation but uses more memory per entry and gives no order. Sorting costs O(n log n), but afterwards equal items are adjacent and order-based follow-ups ("the k closest", "the next larger") become easy. A simple rule: if the key space is small and dense, use an array; if keys are arbitrary and you need one pass, use a hash map; if you need order or must save memory, sort.

Recognising the pattern

Reach for hashing when the brute force's inner loop searches for a specific value, a specific count, or "something equivalent to this". Signals in the problem statement: "duplicate", "unique", "frequency", "anagram", "pair that sums to", "group", "first non-repeating", "seen before", "O(n)" required on unsorted input. Then name the role — membership, position or count — and the key. If the key is not obvious, ask what makes two items "the same" for this problem.

How CPython's dict actually works

CPython's dict and set use open addressing: there is one array of slots, and when a key's preferred slot is taken, the table probes other slots in a pseudo-random sequence derived from the hash until it finds the key or an empty slot. Since Python 3.6 the dict is split into a compact array of entries kept in insertion order plus a sparse index table that holds positions into it — which is why iteration follows insertion order (guaranteed by the language from 3.7) and why dicts use less memory than they used to. The table resizes when it is about two-thirds full, so probes stay short; each resize rehashes everything, costing O(n), but resizes are geometric, so insertion is amortised O(1) (the dynamic-array argument from al2). Deletion leaves a "dummy" marker so probe sequences are not broken, which is why a dict that has had many deletions can be larger than its contents suggest.

Hashability and the equality contract

The rule that makes hash tables correct is: if a == b then hash(a) == hash(b). The table relies on it to look in the right bucket. That is why mutable objects such as lists are unhashable: if you inserted a list and then appended to it, its hash would change, and the entry would become unreachable. Tuples are hashable only if everything inside them is. Custom classes can define __eq__ and __hash__ together (dataclasses with frozen=True do this automatically). A classic bug is defining __eq__ without __hash__: Python then sets __hash__ to None and the objects cannot be put in sets. Another subtle one: 1 == 1.0 == True in Python, and they hash equally, so a dict treats them as the same key.

Worst cases and hash flooding

Expected O(1) assumes the keys do not collide systematically. In December 2011, researchers showed at the 28C3 conference that web frameworks in many languages could be knocked over by a single HTTP request containing thousands of form fields whose names were chosen to collide in the language's string hash; parsing the request into a hash table became quadratic and pinned a CPU for minutes. Languages responded by randomising string hashing per process (Python made it the default in 3.3 and later switched to the SipHash function). In interviews, the relevant takeaways are: say "O(1) expected"; know that integer keys in Python hash to themselves, so adversarial integer inputs can still collide on some judges; and know that sorting has no such worst case, which occasionally makes it the safer choice.

The hidden cost of big keys

Hashing a key costs time proportional to its size. Using whole substrings as keys — for example, putting every substring of length L into a set to find repeats — costs O(L) per substring, so O(n·L) overall, which is O(n²) when L is proportional to n. CPython caches the hash of a string object after computing it once, but every new slice is a new object. The professional fix is a rolling hash, which updates the hash of a sliding window in O(1) when one character leaves and one enters; it is the core of Rabin–Karp and is covered in al26. A cheaper fix for small alphabets is to encode each window as an integer (two bits per DNA letter, for instance) and update it with shifts.

Probabilistic cousins: when exactness is too expensive

A hash set of a billion URLs needs tens of gigabytes. Two structures trade exactness for memory and come up in system-design follow-ups. A Bloom filter uses a bit array and several hash functions: inserting sets k bits; a query says "definitely not present" if any bit is 0, or "probably present" otherwise — no false negatives, a tunable false-positive rate, about 10 bits per element for 1%. A Count-Min sketch keeps a small table of counters indexed by several hashes and answers frequency queries with a bounded overestimate. If an interviewer extends a hashing problem with "now the data does not fit in memory", mentioning partitioning by hash into files (so equal keys land in the same file) and these sketches shows the senior-level next step.

In the interview room

Hashing questions are usually where interviewers check fundamentals quickly, so fluency matters. The common mistakes are: using a list for membership (if x in seen_list), which silently makes the solution O(n²); using a list as a dict key and hitting TypeError: unhashable type; inserting before checking in complement problems, so an element pairs with itself; and claiming O(1) space for a solution that stores up to n entries. Say the space cost unprompted — "O(n) extra for the map" — and, if relevant, offer the sorting alternative with its O(1) extra space.

Expect the "why" probes on the clever ones. For Longest Consecutive Sequence, interviewers almost always ask why the nested loop is not quadratic; the answer is the aggregate argument (each number is counted by exactly one run, the one starting at its smallest element). For isomorphic strings, they ask why one map is not enough; have the "ab" → "cc" counterexample ready. For Group Anagrams, they ask about the complexity of the key; know that the sorted key is O(L log L) and the count key O(L).

A frequent follow-up is a constraint change that breaks hashing: "the input is a stream of a billion items and you have 1 GB of memory". Talk through partitioning (hash each item to one of k files so duplicates land together, then process each file in memory), approximate structures (a Bloom filter for membership, Count-Min for frequencies), or sorting externally.

Finally, keep an eye on what you return. Many hashing problems ask for indices, and storing values instead of indices (or the first index when the problem wants the last) is an easy way to produce plausible but wrong output. Re-read the "Output" answers from step 1 of the method before you code, and test one case where the same value appears twice.

In real systems

Hash tables are the most used data structure in production software. Caches (Memcached, Redis, an in-process functools.lru_cache) are hash maps with an eviction policy. Database hash joins build a hash table on the smaller table and probe it with rows from the larger one, turning an O(n·m) nested-loop join into O(n + m). Payment and messaging APIs store idempotency keys in a hash map so a retried request is recognised and not executed twice. Deduplication in data pipelines hashes each record (often a content hash such as SHA-256) into a set or a key-value store. Distributed systems spread keys over servers with consistent hashing, so adding a server only moves a small fraction of keys. The interview patterns — membership, position, count, canonical key — map directly onto these uses: a cache is membership plus value, a hash join is the complement trick at table scale, and deduplication is a canonical key.

Compare the set-based Longest Consecutive Sequence against a sort-based version on random data, and see what happens without the "start of run" check.

  1. Save as hash_lab.py: 
    import random, time

def by_sort(a):
    if not a: return 0
    b = sorted(set(a)); best = cur = 1
    for i in range(1, len(b)):
        cur = cur + 1 if b[i] == b[i-1] + 1 else 1
        best = max(best, cur)
    return best

def by_set(a, check_start=True):
    s, best = set(a), 0
    for x in s:
        if check_start and x - 1 in s:
            continue
        y = x
        while y + 1 in s: y += 1
        best = max(best, y - x + 1)
    return best

for _ in range(2000):
    a = [random.randint(-10, 10) for _ in range(random.randint(0, 12))]
    assert by_sort(a) == by_set(a) == by_set(a, False), a
print("all variants agree on small inputs")

big = list(range(20000)); random.shuffle(big)
for f, kw in ((by_sort, {}), (by_set, {}), (by_set, {"check_start": False})):
    t = time.perf_counter(); f(big, **kw)
    print(f.__name__, kw, f"{time.perf_counter() - t:.3f}s")
  2. Run python hash_lab.py. The first line confirms all three versions give the same answers on random small inputs.
  3. Look at the timings on one long run of 20,000 consecutive numbers. The sort and the checked set version finish in milliseconds; the unchecked version counts every suffix of the run, about 2 × 10⁸ lookups, and takes far longer.

What this proves: correctness tests on small random inputs cannot see a complexity bug — all three versions agree — but a single adversarial large input exposes it immediately. When you remove a check "because the answer is the same", time it on the worst case.

Design under a changed constraint

You solved "find all duplicate emails in a list" with a set. The interviewer now says: the list has 5 billion emails (about 150 GB) and your machine has 16 GB of memory. How do you find the duplicates exactly?

Answer

A single in-memory set will not fit, so partition first. Stream the input once and write each email to one of, say, 64 bucket files chosen by hash(email) mod 64. Equal emails always hash to the same bucket, so every duplicate pair ends up in the same file, and each file is about 150 / 64 ≈ 2.3 GB — small enough to deduplicate with an in-memory set (or to sort). Process the files one at a time and output the duplicates. Cost: two passes over the data, O(n) expected time, and disk I/O dominates. If a bucket is still too large (a very common email), split it again with a different hash seed. Mention the alternatives: an external sort followed by a linear scan for equal neighbours (also two to three passes, deterministic, no hash worst case), or a Bloom filter in front for a fast approximate first pass if a small false-positive rate is acceptable — but the question said "exactly", so the Bloom filter can only pre-filter, with a second exact check on its "maybe" answers.
