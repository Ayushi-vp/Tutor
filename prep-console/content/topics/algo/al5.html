You have a sorted list of 100,000 product prices and a gift card worth exactly 500. Is there a pair of products that uses the card exactly? The brute force checks every pair — about five billion of them. A hash map of complements (al4) does it in one pass, but uses memory for 100,000 entries and ignores the fact that the list is already sorted. There is a better way that uses the order: put one finger on the cheapest product and one on the most expensive. If the two together cost less than 500, the cheapest product is hopeless — even with the most expensive item it falls short — so move the left finger up. If they cost more, the most expensive item is hopeless — even with the cheapest it overshoots — so move the right finger down. Every step eliminates one product for good, and the fingers meet after at most 100,000 steps, using no extra memory.

That is the two-pointer technique: two indices that move through a sequence according to a rule that guarantees each move only throws away candidates that cannot be the answer. It turns pair-checking O(n²) loops into O(n) scans and in-place problems into single passes with O(1) memory.

It shows up in three shapes. Opposite ends: pointers start at both ends and move towards each other (pair sums, palindromes, container and rain-water problems). Same direction: a read pointer scans and a write pointer marks where kept elements go (removing duplicates, moving zeros, partitioning). Two sequences: one pointer per sorted input (merging, intersections, subsequence checks). Fast and slow pointers on linked lists are a fourth shape covered in al9.

This lesson teaches each shape with a worked trace and, more importantly, the safe-move argument behind it — the one or two sentences that prove the method correct. Interviewers ask for that argument often, because it separates candidates who understand the pattern from those who have only seen it.

The mental model: eliminating rows and columns

Think of all possible pairs (i, j) with i < j as the cells of a triangle-shaped grid: row i, column j. The brute force visits every cell. Two pointers stands at one cell, (l, r), and asks one question. On a sorted array with a target sum, the answer to "is a[l] + a[r] too small, too big or exact?" lets it rule out an entire row or column at once:

  • Too small: every pair in row l to the left of r has a smaller or equal sum (because a[j] ≤ a[r] for j ≤ r), so the whole rest of row l is too small. Eliminate the row: l += 1.
  • Too big: every pair in column r below l has a larger or equal sum, so the whole column is too big. Eliminate the column: r −= 1.

That picture is the whole idea, and it generalises: whenever the candidates form a grid in which the values are monotonic along both directions (increasing as you go right and down), you can start at a corner and walk a staircase, discarding a row or a column at each step. Searching a matrix whose rows and columns are both sorted works the same way.

The same-direction version uses a different model: a conveyor belt with an inspector. The read pointer is the belt bringing every item past; the write pointer is the end of the "kept" pile. Each item is inspected once; kept items are placed at the write position and the pile grows by one. Everything before the write pointer is final. Nothing ever moves backwards, so it is one pass.

A third, quieter model is worth naming because it explains why two pointers is fast at all: neither pointer ever moves backwards. In the opposite-ends version, l only increases and r only decreases, so together they make at most n moves. In the same-direction version, the read pointer makes n moves and the write pointer at most n. That monotonic movement is what turns a loop that looks like it might be quadratic into a linear one — the same aggregate argument as in al2. If you ever find yourself resetting a pointer to an earlier position, you are no longer doing two pointers, and the complexity argument no longer holds.

Where the models break: neither tells you which rule makes a move safe for a given problem. That rule is problem-specific — sortedness for pair sums, "the shorter wall limits the area" for containers, "the kept prefix is final" for compaction — and finding it is the real work. The body of the lesson shows the rule for each classic problem.

Opposite ends I: pair sum on a sorted array

def two_sum_sorted(a, target):
    l, r = 0, len(a) - 1
    while l < r:                      # pairs need two distinct indices
        s = a[l] + a[r]
        if s == target:
            return [l, r]
        if s < target:
            l += 1                    # a[l] too small for every partner <= r
        else:
            r -= 1                    # a[r] too big for every partner >= l
    return []

The comments are the safe-move argument, and you should say them while coding. The loop does at most n − 1 iterations because each one moves a pointer inward. O(n) time, O(1) space. The condition is l < r because a pair needs two different indices.

A counting variant shows the power of the elimination view. "How many pairs have sum less than target?" — when a[l] + a[r] < target, a[l] works with every index from l + 1 to r (they are all at most a[r]), so add r − l in one step and move l. When the sum is too big, move r. Still O(n) after sorting.

Opposite ends II: palindromes

Checking whether a string reads the same backwards is the simplest opposite-ends problem: compare s[l] and s[r], and move both inward while they match. The interview version adds noise — "ignore non-alphanumeric characters and case" — which tests careful pointer handling:

def is_palindrome(s):
    l, r = 0, len(s) - 1
    while l < r:
        while l < r and not s[l].isalnum(): l += 1
        while l < r and not s[r].isalnum(): r -= 1
        if s[l].lower() != s[r].lower():
            return False
        l += 1; r -= 1
    return True

The inner skipping loops repeat the l < r guard; without it, a string of only punctuation would run a pointer off the end. A follow-up, "Valid Palindrome II" (may delete at most one character), branches once at the first mismatch: check whether s[l+1..r] or s[l..r−1] is a palindrome. That is still O(n), because the branch happens once.

Fix one, two-pointer the rest: 3Sum

"Find all unique triplets that sum to zero." The brute force is O(n³). Sort the array; then for each index i, the problem "find pairs in a[i+1..] summing to −a[i]" is exactly sorted pair sum, O(n). That gives O(n²) overall. The harder part is uniqueness: the input can contain duplicates, and the output must not. Sorting makes duplicates adjacent, so skip them in two places.

def three_sum(a):
    a.sort()
    out = []
    for i in range(len(a) - 2):
        if a[i] > 0: break                     # smallest is positive: no zero sum
        if i > 0 and a[i] == a[i - 1]: continue  # same fixed value as before
        l, r = i + 1, len(a) - 1
        while l < r:
            s = a[i] + a[l] + a[r]
            if s < 0: l += 1
            elif s > 0: r -= 1
            else:
                out.append([a[i], a[l], a[r]])
                l += 1; r -= 1
                while l < r and a[l] == a[l - 1]: l += 1   # skip equal lefts
    return out

Trace on [-1, 0, 1, 2, -1, -4], sorted to [-4, -1, -1, 0, 1, 2]. i = 0 (−4): needs pairs summing to 4; the pointers find none. i = 1 (−1): needs 1; l at −1, r at 2 → sum 0, record [−1, −1, 2]; move both and skip; l at 0, r at 1 → sum 0, record [−1, 0, 1]. i = 2 is −1 again, equal to a[1], so skip it — this is what prevents [−1, 0, 1] being recorded twice. i = 3 (0): needs 0 from [1, 2], none. Result: [[−1, −1, 2], [−1, 0, 1]].

The general form is kSum: fix k − 2 elements with nested loops (each skipping duplicates), and two-pointer the last two. That is O(n^(k−1)). For 4Sum, O(n³).

Opposite ends III: Container With Most Water

Given wall heights h, choose two walls to hold the most water: area = (r − l) × min(h[l], h[r]). The brute force tries all pairs. Start with the widest container, l = 0 and r = n − 1, and ask which pointer to move. Suppose h[l] < h[r]. Any container that keeps wall l and pairs it with a wall further in has smaller width and height still capped at h[l] — so it cannot beat the current area. Every candidate involving wall l has been dominated; discard it by moving l. The rule: always move the shorter wall.

def max_area(h):
    l, r, best = 0, len(h) - 1, 0
    while l < r:
        best = max(best, (r - l) * min(h[l], h[r]))
        if h[l] < h[r]: l += 1
        else: r -= 1
    return best

When the heights are equal, moving either is safe: any container keeping one of them is narrower and still capped at that height. This is a nice example where the array is not sorted, yet the problem has its own monotonic structure that makes the move safe.

Opposite ends IV: Trapping Rain Water

Water above position i rises to the lower of the tallest wall on its left and the tallest on its right: water[i] = min(maxL[i], maxR[i]) − h[i]. A clear O(n)-space solution precomputes both arrays. The two-pointer version removes the arrays by noticing that you do not need both maxima exactly — only the smaller one. Keep left_max (tallest seen from the left so far) and right_max. If h[l] < h[r], then somewhere on the right there is a wall at least h[r], which is taller than h[l]; so for position l the limiting side is the left, and its water is left_max − h[l]. Process l and move it. Otherwise process r symmetrically.

def trap(h):
    l, r = 0, len(h) - 1
    left_max = right_max = water = 0
    while l < r:
        if h[l] < h[r]:
            left_max = max(left_max, h[l])
            water += left_max - h[l]
            l += 1
        else:
            right_max = max(right_max, h[r])
            water += right_max - h[r]
            r -= 1
    return water

On [0,1,0,2,1,0,1,3,2,1,2,1] this returns 6. It is one of the most-asked hard problems precisely because the safe-move argument is subtle; practise saying it in two sentences. (A monotonic-stack solution exists too, al8.)

Same direction: read and write pointers

"Remove duplicates from a sorted array in place and return the new length." The read pointer i visits every element; the write pointer w marks the end of the kept prefix. The invariant: a[0..w−1] holds the unique values seen so far, in order.

def remove_duplicates(a):
    if not a: return 0
    w = 1                                # a[0] is always kept
    for i in range(1, len(a)):
        if a[i] != a[w - 1]:             # new value: keep it
            a[w] = a[i]
            w += 1
    return w

The same skeleton solves "move zeros to the end" (keep non-zeros, then fill the tail with zeros), "remove all occurrences of val", and "keep at most two copies of each value" (compare with a[w − 2] instead of a[w − 1]). The output is stable — kept elements stay in their original order — because the write pointer only receives elements in scan order.

Three pointers: the Dutch national flag

"Sort an array of 0s, 1s and 2s in one pass" (Sort Colors). Keep three regions: a[0..lo−1] are 0s, a[lo..mid−1] are 1s, a[hi+1..] are 2s, and a[mid..hi] is unexamined. Look at a[mid]:

def sort_colors(a):
    lo, mid, hi = 0, 0, len(a) - 1
    while mid <= hi:
        if a[mid] == 0:
            a[lo], a[mid] = a[mid], a[lo]; lo += 1; mid += 1
        elif a[mid] == 1:
            mid += 1
        else:
            a[mid], a[hi] = a[hi], a[mid]; hi -= 1   # do not advance mid

The asymmetry is the whole difficulty. After swapping a 2 to the back, the value that arrives at mid came from the unexamined region, so it must be examined before mid moves. After swapping a 0 to the front, the value arriving at mid came from the 1s region (or is the same element), so mid can advance. Trace [2, 0, 2, 1, 1, 0] by hand once and the rule will stick; the result is [0, 0, 1, 1, 2, 2]. This three-way partition is also how quicksort handles many equal keys efficiently.

Two sequences: merging

With two sorted sequences, one pointer each, repeatedly take the smaller head and advance that pointer. That is the merge step of merge sort, and it powers "merge two sorted lists", "intersection of two sorted arrays" (advance the smaller; record when equal), and "is s a subsequence of t" (advance in t always, in s only on a match).

A classic twist: "merge nums2 into nums1, where nums1 has enough empty slots at the end". Merging from the front would overwrite elements of nums1 you have not read yet. Merge from the back instead: compare the last real elements, write the larger one into the last slot, and move left. The write position is always at or beyond the read position in nums1, so nothing unread is overwritten.

Greedy pairing: boats

"Each boat carries at most two people and a weight limit; find the minimum number of boats." Sort the weights. The heaviest person must take a boat; the best partner for them is the lightest person, because if the lightest cannot fit with them, nobody can. So: if a[l] + a[r] ≤ limit, both go (l++, r−−); otherwise the heaviest goes alone (r−−). Count a boat each step, and loop while l <= r so a final single person is counted. This is two pointers driven by a greedy exchange argument (al12).

Recognising the pattern

Reach for two pointers when: the input is sorted, or sorting is allowed and does not lose information you need; the problem asks about pairs or triplets with a sum or difference condition; it asks for in-place modification with O(1) extra space; it involves a palindrome or symmetric comparison; or it involves merging or intersecting sorted sequences. Then ask: what makes a move safe? If you can state it, you have the algorithm.

The general correctness argument

Every opposite-ends algorithm has the same proof shape. Define the candidate set as all pairs (i, j) with l ≤ i < j ≤ r. The invariant is: "if an answer exists, it lies in the current candidate set" (or, for optimisation problems, "the best answer outside the current set has already been recorded"). Each move removes one row or one column from the set, and the safe-move argument shows that nothing removed could be a better answer. When l meets r the set is empty, so every answer has been found or dominated. Saying "each move discards a row or column of the pair grid, and I can show nothing discarded could win" is a complete correctness proof in an interview.

Why sorting is sometimes not allowed

Sorting destroys the original positions. If the problem asks for indices (classic Two Sum), you must either sort (value, index) pairs — O(n log n) time and O(n) space, no better than hashing — or use a hash map. If the problem is about contiguous subarrays (sums of subarrays, windows), sorting changes which elements are adjacent and breaks the problem entirely; those need prefix sums (al3) or sliding windows (al6), not opposite-ends pointers. The question to ask before sorting is: "does the answer depend on the original order?"

Staircase search in sorted matrices

The pair-grid picture becomes literal in "search a matrix where every row and every column is sorted". Start at the top-right corner: if the value is larger than the target, the whole column below is larger, so move left; if smaller, the whole row to the left is smaller, so move down. At most R + C steps. The same staircase idea finds "the k-th smallest element in a sorted matrix" when combined with binary search on the value (count how many entries are ≤ x by walking the staircase in O(R + C)), which is a good example of patterns composing (al7).

Two pointers and the merge family

The two-sequence merge is one of the most important operations in computing. Merge sort's merge step, external sorting (merge sorted runs from disk), database sort-merge joins, and the compaction step of log-structured storage engines (merging sorted files of keys) are all the same loop: advance the pointer at the smaller head. Generalising to k sequences needs a heap to find the smallest of k heads (al10). Recognising that "merge k sorted lists" is two-sequence merging plus a heap is a standard interview step.

Floyd's algorithm on arrays: functional graphs

"Find the duplicate number" (n + 1 values in the range 1..n, read-only array, O(1) space) looks like a hashing problem but forbids the memory. View the array as a function f(i) = a[i]. Starting from index 0 and following f repeatedly must eventually repeat a value (pigeonhole), so the path is a "rho" shape: a tail leading into a cycle. Two different indices map to the duplicate value, which makes the duplicate the entrance of the cycle. Floyd's algorithm finds it: move slow by one step and fast by two until they meet inside the cycle; then restart one pointer from the beginning and move both by one step; they meet exactly at the entrance. The proof is a short distance argument (the tail length equals the distance from the meeting point to the entrance, modulo the cycle length), and it is covered with linked lists in al9. It is a favourite hard follow-up because it combines a pigeonhole argument, a graph view of an array and two pointers.

Invariants with three regions

The Dutch flag generalises to any "partition into k groups in one pass" with k − 1 boundaries plus a scan pointer, but its real value is as a model of reasoning with region invariants. Write the regions as a picture ("0s | 1s | unknown | 2s") and for each case of the scanned value, ask which region boundary moves and whether the element that arrives at the scan position has been examined. Bugs in partition code — including the famous one where quicksort degenerates on many equal keys — come from getting that question wrong. Interviewers who ask Sort Colors are usually checking exactly this reasoning.

In the interview room

Two-pointer code is short, so interviewers judge it on precision. The typical failures are: an infinite loop because some branch forgets to move a pointer; an off-by-one in the loop condition (l < r versus l <= r) — decide by asking whether a single element can be an answer on its own; duplicate triplets in 3Sum because only one of the two skip points is handled; and index errors in the inner skipping loops because the l < r guard is missing. Test with an array of all equal values and with a two-element array; those two inputs catch most of these bugs.

The second thing interviewers look for is the justification. "Why do you move the left pointer here?" is the most common follow-up for this pattern. Prepare one-sentence arguments: sorted pair sum ("a[l] is too small even with the largest remaining partner"), container ("any container keeping the shorter wall is narrower and no taller"), rain water ("the other side has a taller wall, so this side's maximum decides"). A memorised solution without the argument tends to fall apart when the interviewer changes the problem slightly.

Finally, know when not to use it. If the input is unsorted and you must return original indices, offer the hash-map solution first. If the problem is about contiguous ranges, you probably want a sliding window (al6), which is a same-direction two-pointer specialised for windows.

A good way to practise is to say the safe-move argument before writing the loop, as part of step 5 of the method ("I'll start at both ends; if the sum is too small, the left element is too small for every remaining partner, so I advance it"). If you cannot state the argument, that is a signal that the two-pointer idea may be wrong for this problem — perhaps it needs a hash map, a window or a different order — and it is far cheaper to find that out before coding than after.

On online assessments, two-pointer problems often hide behind constraints: an array of 10⁵ elements with a pair or triplet condition, and a memory limit that makes a hash map of all pairs impossible. Sorting plus two pointers is usually the intended solution there.

In real systems

The merge loop is everywhere in data infrastructure. Database engines implement sort-merge joins: when both inputs are sorted on the join key (often because an index provides that order), the join walks both with one pointer each, advancing the smaller key, in a single pass. External sorting — sorting data much larger than memory — writes sorted runs to disk and then merges them with a pointer per run. Log-structured merge (LSM) storage engines such as RocksDB and Cassandra continuously compact sorted files by merging them, dropping overwritten and deleted keys along the way — a read pointer per file and a write pointer for the output, exactly the compaction pattern from this lesson. Version-control and diff tools merge sorted lists of file paths to find added and removed files. In each case the reason is the same as in the interview: one pass, sequential reads (which disks and caches love), and constant extra memory per input.

Prove the move, then extend

An interviewer asks: "In Container With Most Water, prove that moving the shorter wall never skips the optimal container. Then: what changes if the area formula were (r − l) × max(h[l], h[r])?"

Answer

Proof: suppose h[l] ≤ h[r]. Every container that uses wall l together with some wall j where l < j < r has width j − l < r − l and height min(h[l], h[j]) ≤ h[l] = min(h[l], h[r]). So its area is strictly smaller than the current one. Therefore no container involving wall l and a wall inside the current range can beat what we have already recorded, and wall l can be discarded. Each step discards one wall, so after n − 1 steps every container has been considered or dominated. With max instead of min: the argument breaks. A taller inner wall can now increase the height, and moving the shorter wall no longer dominates anything — in fact the widest container that includes the single tallest wall is optimal: the answer is max over the tallest wall t of max(t − 0, n − 1 − t) × h[t]. The lesson for the interview: the two-pointer rule is a consequence of the problem's structure (here, min), and when the structure changes, re-derive the rule rather than reusing the code.
