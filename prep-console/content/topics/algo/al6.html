A fitness app shows "your best 7-day step streak": the largest total over any 7 consecutive days in the last year. The obvious code takes every starting day, adds up the next 7 values, and keeps the maximum — 365 × 7 additions, which is fine. Then product asks for a 30-day version over five years of minute-level heart-rate data, about 2.6 million values with a 43,200-value window. Now the obvious code does about 10¹¹ additions, and almost all of them are repeated: the window starting at minute 1,001 shares 43,199 values with the window starting at minute 1,000.

Moving the window by one position only changes two things: one value enters on the right, and one value leaves on the left. If you keep the current window's total, the next total is old total + entering value − leaving value — two operations instead of 43,200. That is the sliding window: keep a summary of a contiguous range and update it incrementally as the range moves.

Interviews use the idea constantly, usually in a stronger form where the window's size is not fixed. "Longest substring without repeating characters", "smallest subarray with sum at least target", "longest substring with at most k distinct characters", "minimum window containing all the characters of t" — each asks for the best contiguous range satisfying a condition. The brute force checks all O(n²) ranges, often with O(n) work each. A window that grows on the right and shrinks on the left visits each element at most twice and solves them in O(n).

This lesson builds the pattern from the fixed-size case to the variable "longest" and "shortest" templates, the counting trick for "number of subarrays with at most / exactly k", and the monotonic deque for window maximums. Just as important, it teaches the precondition that makes windows correct — monotonic validity — so you can tell when a window will silently give wrong answers and you need prefix sums instead.

The mental model: an inchworm

Picture an inchworm crawling along a ruler. Its head (the right pointer) reaches forward to grab the next mark; its tail (the left pointer) follows behind. The worm's body is the window: everything between tail and head. The worm never crawls backwards, and it never jumps — the head moves forward one mark at a time, and the tail moves forward only when the body must get shorter. Because both ends only move forward along a ruler of length n, the whole journey takes at most 2n moves, no matter how the body stretches and contracts along the way.

The worm also carries a small notebook: the window's summary. It might be the sum of the marks inside, a count of each letter, or the number of distinct letters. When the head grabs a new mark, the worm updates the notebook for one element entering; when the tail lets go, it updates it for one element leaving. Neither update looks at the rest of the window. That is where the speed comes from.

Three kinds of window

Almost every window problem is one of three types, and naming the type tells you the template:

  • Fixed size k: slide one step at a time; add the entering element, remove the leaving one. Example: maximum sum of k consecutive elements.
  • Variable, longest valid: grow the head every step; while the window is invalid, shrink the tail; then record the length. Example: longest substring without repeats.
  • Variable, shortest valid: grow the head every step; while the window is valid, record its length and shrink the tail. Example: smallest subarray with sum at least target.

Where the analogy breaks: a real inchworm can always shrink safely. A sliding window is only correct if shrinking never throws away something you would need later. That requires the condition to be monotonic: for "longest" problems, if a window is invalid then every bigger window containing it is invalid too (a substring with a repeat still has the repeat if you extend it). If the condition is not monotonic — sums with negative numbers are the classic case — a window gives wrong answers, and you need a different tool. Checking monotonicity takes ten seconds and is the single most important habit in this lesson.

Here is the cost comparison that justifies the effort. For "longest substring without repeating characters" on a string of 10⁵ characters, the brute force checks about 5 × 10⁹ substrings, each needing a scan to test for repeats. The window version makes at most 2 × 10⁵ pointer moves with an O(1) dictionary update each. That is the difference between hours and milliseconds, achieved without any clever data structure — only by refusing to forget what the previous window already knew.

One more framing helps when you are deciding between windows and other tools: a window answers questions about contiguous ranges. If the problem allows picking elements that are not next to each other ("subsequence", "subset", "any k elements"), it is not a window problem, however similar the wording looks.

Fixed-size windows

def max_sum_k(a, k):
    s = sum(a[:k])
    best = s
    for r in range(k, len(a)):
        s += a[r] - a[r - k]          # one in, one out
        best = max(best, s)
    return best

Trace a = [2, 1, 5, 1, 3, 2], k = 3: the first window sums to 8; sliding gives 8 − 2 + 1 = 7, then 7 − 1 + 3 = 9, then 9 − 5 + 2 = 6. Best 9 ([5, 1, 3]). O(n) time instead of O(n·k).

The summary does not have to be a sum. "Find all anagrams of p in s" uses a fixed window of length m = len(p) whose summary is the character counts. Comparing two Counters at each step costs O(alphabet); a sharper version keeps one dictionary diff of (window count − p count) per character and an integer bad = how many characters have a non-zero difference. Each add or remove changes one character's difference, and you adjust bad when that difference becomes or stops being zero. When bad == 0, the window is an anagram. That is O(1) per step and O(n) overall, and it is the same "track how many constraints are currently satisfied" idea that powers Minimum Window Substring below.

Variable window, longest valid: the template

def longest_valid(a):
    left = 0
    best = 0
    # summary = ...                    # e.g. counts, sum, distinct
    for right, x in enumerate(a):
        add(x)                          # head moves: update summary
        while not valid():              # shrink until valid again
            remove(a[left])
            left += 1
        best = max(best, right - left + 1)
    return best

Every "longest" problem fills in three blanks: what the summary is, how add and remove update it, and what valid means. Correctness rests on monotonic validity: if a[l..r] is invalid, then a[l'..r] for any l' < l is also invalid, so once the tail passes position l it never needs to come back. Complexity: each element is added once and removed at most once, so O(n) total, plus the cost of the summary updates.

Longest substring without repeating characters

Summary: a set (or counts) of the characters in the window. Valid: no character appears twice. When the head adds a character that is already present, shrink until its earlier copy leaves.

def length_of_longest_substring(s):
    last = {}                          # char -> last index seen
    left = best = 0
    for right, ch in enumerate(s):
        if ch in last and last[ch] >= left:
            left = last[ch] + 1        # jump past the earlier copy
        last[ch] = right
        best = max(best, right - left + 1)
    return best

This version jumps the tail directly instead of stepping it, using the last-seen index map from al4. The guard last[ch] >= left matters: a character last seen before the current window is not a repeat inside it, and jumping to it would move the tail backwards. Trace on "abcabcbb":

"At most k" conditions

A large family of problems has the shape "longest window with at most k of something": at most k zeros (Max Consecutive Ones III: you may flip k zeros), at most 2 distinct values (Fruit Into Baskets), at most k distinct characters. The summary is a count — zeros in the window, or a Counter plus its number of keys — and valid means the count is at most k. Each is the template with a two-line summary.

Longest Repeating Character Replacement is the cleverest member. You may replace k characters to make the window all one letter. A window can be made uniform when length − maxfreq ≤ k, where maxfreq is the count of its most frequent letter: you keep the majority letter and replace the rest. So valid = (right − left + 1) − maxfreq ≤ k.

def character_replacement(s, k):
    count = {}
    left = maxfreq = best = 0
    for right, ch in enumerate(s):
        count[ch] = count.get(ch, 0) + 1
        maxfreq = max(maxfreq, count[ch])
        while (right - left + 1) - maxfreq > k:
            count[s[left]] -= 1
            left += 1
        best = max(best, right - left + 1)
    return best

Notice that maxfreq is never decreased when the tail moves, so it can become stale (higher than the true maximum in the window). That is deliberate and safe: the answer can only grow when some window achieves a higher maxfreq than before, and a stale value only prevents shrinking below a length we have already achieved. With an alphabet of 26 you could also recompute the max exactly in O(26) per step; mentioning both shows understanding.

Variable window, shortest valid

For "shortest" problems the loop shape flips: record inside the while loop, because you want to keep shrinking as long as the window stays valid.

def min_subarray_len(target, a):        # all a[i] > 0
    left = s = 0
    best = float("inf")
    for right, x in enumerate(a):
        s += x
        while s >= target:               # valid: record, then try smaller
            best = min(best, right - left + 1)
            s -= a[left]
            left += 1
    return 0 if best == float("inf") else best

Monotonicity here is the reverse: if a window is valid (sum ≥ target), every larger window containing it is valid too, because values are positive. So once you have shrunk past a position, the windows you skipped could only have been longer.

Minimum Window Substring

The famous hard version: the smallest window of s that contains every character of t, counting multiplicity. The summary is a window Counter, plus two numbers that make the validity check O(1): required = how many distinct characters t needs, and formed = how many of them currently meet their required count.

from collections import Counter
def min_window(s, t):
    need = Counter(t)
    required, formed = len(need), 0
    have = {}
    left, best = 0, (float("inf"), 0, 0)
    for right, ch in enumerate(s):
        have[ch] = have.get(ch, 0) + 1
        if ch in need and have[ch] == need[ch]:
            formed += 1                       # this char just became satisfied
        while formed == required:             # valid: record and shrink
            if right - left + 1 < best[0]:
                best = (right - left + 1, left, right)
            out = s[left]
            have[out] -= 1
            if out in need and have[out] < need[out]:
                formed -= 1                   # just became unsatisfied
            left += 1
    n, l, r = best
    return "" if n == float("inf") else s[l:r + 1]

On s = "ADOBECODEBANC", t = "ABC" the head first reaches a valid window at "ADOBEC"; shrinking removes A and invalidates it; the head continues until "DOBECODEBA" is valid again, shrinking gives "CODEBA"; later "BANC" (length 4) is found, which is the answer. The key details are incrementing formed only when a count reaches the need exactly (not every time the character is seen) and decrementing only when it drops below. O(|s| + |t|).

Counting subarrays: the r − l + 1 trick

"How many subarrays have at most k distinct values?" After the shrink step, the window a[left..right] is the longest valid window ending at right. Every shorter window ending at right — starting at left, left + 1, …, right — is also valid (monotonicity again). That is right − left + 1 subarrays, so add that each step.

"Exactly k" is harder because validity is not monotonic in that form: shrinking can go from exactly k to k − 1. The standard trick turns it into two monotonic problems: exactly(k) = atMost(k) − atMost(k − 1). Every subarray with exactly k distinct values is counted in the first term and not the second. This solves "Subarrays with K Different Integers" and "Count Number of Nice Subarrays" (exactly k odd numbers) in O(n).

The maximum of every window: monotonic deque

"Return the maximum of every window of size k." A running sum works because subtraction undoes addition, but there is no way to "un-max". Recomputing each window is O(n·k). The insight: when a new element x arrives, every older element smaller than or equal to x can never be the maximum of any future window — x is newer (stays in the window longer) and at least as large. So keep a deque of indices whose values are strictly decreasing from front to back:

from collections import deque
def max_sliding_window(a, k):
    dq, out = deque(), []                 # indices, values decreasing
    for i, x in enumerate(a):
        while dq and a[dq[-1]] <= x:      # dominated: will never be max
            dq.pop()
        dq.append(i)
        if dq[0] <= i - k:                # front left the window
            dq.popleft()
        if i >= k - 1:
            out.append(a[dq[0]])          # front is the max
    return out

This is a monotonic deque, the queue cousin of the monotonic stack (al8). The same structure gives sliding window minimums and appears inside DP optimisations ("jump game with maximum score in the last k steps").

Choosing the summary: a short catalogue

Most of the design work in a window problem is choosing the summary, so it helps to have a catalogue. A running sum answers sum and average conditions. A count of one kind of element (zeros, vowels, odd numbers) answers "at most k of X". A Counter plus its number of keys answers "at most k distinct". A Counter plus a satisfied-constraints count answers "contains all of t" and anagram questions. A last-seen index map answers "no repeats" and lets the tail jump. A monotonic deque answers maximum and minimum. A sorted structure or two heaps answers medians and order statistics. When a new problem arrives, ask which of these the validity check needs, and whether it can be updated in O(1) (or O(log k)) when one element enters or leaves. If no summary can be updated incrementally, the problem is probably not a window problem.

Recognising the pattern — and its limit

Reach for a sliding window when the problem asks about a contiguous subarray or substring, the words are "longest", "shortest", "maximum/minimum sum of size k", "at most k", "contains all", or "number of subarrays where…", and the condition is monotonic. Before coding, test monotonicity in one sentence: "if this window is invalid, is every bigger one invalid too?" If the answer is no — typically because values can be negative — use prefix sums with a hash map (al3), or prefix sums with a sorted structure for inequalities.

Monotonic validity, stated precisely

Let P(l, r) mean "the window a[l..r] satisfies the condition". The longest-window template is correct when P is closed under shrinking: if P(l, r) holds then P(l', r') holds for every l ≤ l' ≤ r' ≤ r. Equivalently, if a window is invalid, every window containing it is invalid. Then for each right end r, the valid left ends form a suffix [L(r), r], and L(r) never decreases as r increases — which is exactly why the tail only moves forward. The shortest-window template needs the opposite: P closed under growing. Writing this down once makes it easy to classify new problems: "no repeated characters" is closed under shrinking; "sum ≥ target with positive values" is closed under growing; "sum exactly k" is neither, which is why it needs prefix sums or the at-most trick.

Why the stale maximum is correct

In Longest Repeating Character Replacement, let M be the maxfreq variable. It equals the largest frequency any window has had so far, which is at least the true frequency in the current window. The loop keeps length − M ≤ k, so the window length is at most M + k. Because M only increases, the window length never decreases below the best seen: when the true frequency is lower than M, the window simply slides (head and tail both advance by one) at the best length found so far. The recorded best only increases when M increases, and at that moment M is the true frequency of the newly added character in the current window, so the window is genuinely valid. That is a complete argument, and interviewers who know the problem sometimes ask for it.

Windows on time rather than indices

In production the window is often defined by time: "requests in the last 60 seconds", "errors in the last 5 minutes". The data structure is the same — a deque of (timestamp, value) pairs with a running summary — but the tail condition becomes "pop while front timestamp ≤ now − window". The difference from index windows is that events can be bursty, so the deque can grow large; production systems then switch to approximations: fixed buckets (one counter per second, summed over the last 60) or the sliding-window counter, which weights the previous fixed window's count by how much of it still overlaps. Recognising that an interview window problem and a rate limiter are the same structure is a good bridge into system-design follow-ups.

Window summaries that need more than O(1)

Some window questions need an order statistic: the median of each window, or "is there a pair within the window whose difference is at most t?" (Contains Duplicate III). The summary must then support insert, delete and an ordered query. Options are a balanced search tree or a sorted list (O(log k) per operation with the third-party sortedcontainers, or bisect.insort at O(k) per insert in plain Python), two heaps with lazy deletion for the median (al10), or bucketing by value range for the difference question (bucket width t + 1 means two values in the same bucket always qualify, so only neighbouring buckets need checking). The window logic stays the same; only the summary changes.

Two strings, one window

Several problems slide a window over one string while comparing it with a fixed second string (anagrams, permutation in string, minimum window). The unifying trick is to keep a count of how many constraints are currently satisfied rather than re-comparing whole count tables. Each add or remove changes one character's count, which can satisfy or break at most one constraint, so the satisfied-count changes by at most one per step. This "maintain the number of satisfied constraints incrementally" idea also appears in stream processing and in database incremental view maintenance, and it is what makes these solutions O(n) rather than O(n·alphabet).

When the window should be replaced by binary search

For "longest subarray with sum ≤ k" with only positive values, the window gives O(n). An alternative is binary search on the length (al7): for a candidate length L, check with a fixed window whether any window of length L qualifies. That is O(n log n) and worse here, but it is the right fallback when validity is monotonic in the length but the window's left end cannot be advanced incrementally — for example, when the check involves a hash of the window's contents (longest duplicate substring, al26).

In the interview room

Window problems are among the most common mediums, so interviewers see the same bugs again and again. The top ones: recording the answer in the wrong place (inside the shrink loop for a longest problem, or outside it for a shortest problem); moving the tail backwards when jumping with a last-seen map (missing the last[ch] >= left guard); updating formed every time a needed character is added instead of only when its count reaches the requirement exactly; forgetting to delete zero-count keys from a Counter when the problem counts distinct keys (len(counter) then over-reports); and an off-by-one in the window length (right − left + 1). Say the three blanks of the template — summary, add/remove, valid — before coding, and test with a string where every character is the same and one where all are distinct.

The most valuable sentence you can say is the monotonicity check: "this works because values are non-negative, so a window that is too big stays too big as it grows". It shows you know when the pattern applies. Interviewers often follow up by removing the precondition ("now values can be negative"), and the candidate who stated it immediately says "then the window breaks; I'd switch to prefix sums with a hash map".

For the deque problem, expect "why is it O(n)?" — each index is appended once and popped at most once, from either end — and "why pop elements less than or equal to the new one, not just less than?" (equal older elements are dominated too: the new one leaves the window later).

On online assessments, window problems are frequently disguised: "the longest period of days where the total rainfall stayed under X", "the smallest number of consecutive deliveries covering all product types", "for each hour, the busiest server in the last 10 minutes". Translate the story into "contiguous range + monotonic condition + summary" and the template applies directly.

In real systems

Sliding windows are a core primitive in networking and streaming. TCP's flow control is literally a sliding window over the byte stream: the sender may have a window's worth of unacknowledged bytes in flight, and the window slides forward as acknowledgements arrive (net4). Rate limiters at API gateways use sliding-window logs or counters to enforce "N requests per rolling minute" without the burst-at-the-boundary problem of fixed windows; Cloudflare has described its sliding-window counter approximation publicly. Stream processors such as Apache Flink and Kafka Streams offer tumbling (fixed, non-overlapping), sliding (fixed, overlapping) and session (gap-based) windows, and compute aggregates incrementally exactly like the running sum here. Monitoring systems compute moving averages and rolling percentiles over time windows to smooth noisy metrics and trigger alerts. The interview skill — choose a summary that updates in O(1) per event — is precisely what makes those systems cheap at millions of events per second.

    import random
from collections import Counter

def brute_longest(s):
    best = 0
    for i in range(len(s)):
        for j in range(i, len(s)):
            if len(set(s[i:j+1])) == j - i + 1:
                best = max(best, j - i + 1)
    return best

def window_longest(s):
    last, left, best = {}, 0, 0
    for right, ch in enumerate(s):
        if ch in last and last[ch] >= left:
            left = last[ch] + 1
        last[ch] = right
        best = max(best, right - left + 1)
    return best

def brute_exact(a, k):
    return sum(1 for i in range(len(a)) for j in range(i, len(a))
               if len(set(a[i:j+1])) == k)

def at_most(a, k):
    cnt, left, total = Counter(), 0, 0
    for right, x in enumerate(a):
        cnt[x] += 1
        while len(cnt) > k:
            cnt[a[left]] -= 1
            if cnt[a[left]] == 0: del cnt[a[left]]
            left += 1
        total += right - left + 1
    return total

Is it a window?

For each problem, decide whether a shrinking sliding window is correct, and if not, what to use. (a) Longest subarray whose product is less than k, all values positive. (b) Longest subarray with sum exactly k, values may be negative. (c) Shortest subarray with sum at least k, values may be negative. (d) Number of subarrays whose product is less than k, positive values.

Answer

(a) Yes: with positive values the product only grows as the window grows, so "product < k" is closed under shrinking. Grow right, multiply; while product ≥ k, divide by the left value and advance. (b) No: negatives break monotonicity. Use prefix sums with a map from prefix value to its first index; at each r, look up pre[r+1] − k (al3). (c) No for a plain window, because with negatives shrinking can increase the sum. Use prefix sums with a monotonic deque of increasing prefix values: for each r, pop from the front while pre[r+1] − pre[front] ≥ k (recording the length), and pop from the back while the back's prefix is ≥ pre[r+1] (it can never be a better left end). This is O(n) and is LeetCode's "Shortest Subarray with Sum at Least K". (d) Yes, with the counting trick: after shrinking so the product is below k, every subarray ending at r and starting in [left, r] qualifies, so add r − left + 1. Handle k ≤ 1 separately (no positive product is below 1 or 0).
