A delivery company needs to pick the size of truck for a route. It has 500 packages to deliver in order, a deadline of 5 days, and trucks that come in any capacity. Too small a truck and the packages take more than 5 days; too large and the company wastes money. What is the smallest capacity that meets the deadline? There is no obvious formula. The brute force tries capacity 1, then 2, then 3, simulating the deliveries each time, until one works. If the answer is a capacity of 400,000 kg, that is 400,000 simulations.

But there is structure here. If a capacity works, every larger capacity also works; if a capacity fails, every smaller one fails too. The answers line up as "fail, fail, fail, …, work, work, work". Finding the boundary in such a sequence is exactly what binary search does: try the middle capacity; if it works, the answer is there or smaller; if not, it is larger. Each simulation halves the range of possible answers, so about 19 simulations find the boundary among 400,000 candidates.

Most people meet binary search as "find a number in a sorted array", and that is part of it. The bigger idea — and the one interviewers lean on in medium and hard problems — is that binary search finds the boundary of any monotone yes/no question. Koko eating bananas, shipping capacity, splitting an array to minimise the largest part, placing routers as far apart as possible, finding a peak, searching a rotated array: all are binary search once you see the monotone predicate.

Binary search is also famously easy to get subtly wrong. This lesson therefore gives one template with a written invariant that handles every case, then applies it to boundaries (lower and upper bounds), rotated arrays and peaks, binary search on the answer, real-valued searches, and the hardest classic, the median of two sorted arrays.

The mental model: the guessing game, and the line of lights

In the number-guessing game ("I'm thinking of a number from 1 to 100; I'll say higher or lower"), the best strategy is to guess the middle. Each answer rules out half of the remaining numbers, so you never need more than 7 guesses for 100 numbers, or 30 for a billion. That is binary search's power: the work grows with the logarithm of the size.

A more useful picture for interviews is a long row of lights. Every light is either off or on, and all the off lights come before all the on lights. You want to find the first light that is on, but checking a light costs something (an array read, or a whole simulation). Check the middle light. If it is on, the first on-light is here or to the left; if off, it is to the right. Each check halves the stretch where the boundary can be.

That is the reframe that makes binary search reliable: stop thinking "find x" and start thinking "find the first index where pred is true". A monotone predicate is a yes/no question that is false up to some point and true from then on. For "find x in a sorted array", the predicate is a[i] ≥ x: the first true is where x is (if it exists) or where it would be inserted. For the delivery trucks, the predicate is "capacity c finishes within 5 days". The loop is identical; only the predicate changes.

Where the analogy breaks: the guessing game assumes you are told "higher" or "lower" directly. In real problems you have to construct the predicate, prove it is monotone, and pick bounds that certainly contain the answer. Those three steps — predicate, monotonicity, bounds — are where the thinking goes; the loop itself should be automatic.

A second example makes the reframe concrete. "Find the last occurrence of 7 in a sorted array" sounds like a different problem from "find the first occurrence". In the predicate view it is not: the last 7 sits just before the first element that is greater than 7, so search for the first true of a[i] > 7 and step back one. Every boundary question on sorted data — first, last, count, floor, ceiling, insertion point — becomes "first true of the right predicate, possibly minus one". You no longer need a separate variant of the loop for each question, which is exactly where most bugs come from.

Finally, keep the cost model in mind. Binary search makes about log₂(range) predicate checks. If each check is O(1) (an array read), the whole search is O(log n). If each check is an O(n) simulation, the search is O(n log range). Both are usually tiny compared with trying every candidate.

The one template

Use this template for every binary search. It finds the first index in [lo, hi) where a monotone predicate is true, returning hi if there is none.

def first_true(lo, hi, pred):
    # invariant: pred is False on [orig_lo, lo), True on [hi, orig_hi)
    while lo < hi:
        mid = (lo + hi) // 2      # lo <= mid < hi
        if pred(mid):
            hi = mid              # mid might be the first True
        else:
            lo = mid + 1          # first True is to the right of mid
    return lo                     # lo == hi: the boundary

Why it is correct: the invariant says everything left of lo is false and everything from hi onwards is true (with hi starting one past the end, meaning "assume true"). When pred(mid) is true, mid could be the first true, so we keep it by setting hi = mid. When false, mid and everything left of it are false, so lo = mid + 1. Because mid is strictly less than hi, every iteration shrinks the interval, so the loop terminates, and when lo == hi the invariant pins the boundary exactly. There is no "found it, return early" case to get wrong.

The two ways people break binary search are both avoided here. Infinite loops come from setting lo = mid (when hi = lo + 1, mid = lo and nothing changes); this template never does that. Off-by-one errors come from mixing inclusive and exclusive bounds; this template uses one convention, the half-open interval [lo, hi).

Lower bound, upper bound, and finding a target

On a sorted array, two predicates cover almost everything:

  • Lower bound: first index with a[i] ≥ x — first_true(0, n, lambda i: a[i] >= x), the same as bisect.bisect_left(a, x).
  • Upper bound: first index with a[i] > x — bisect.bisect_right(a, x).

From these: x is present if lower bound < n and a[lower] == x. The first occurrence of x is the lower bound; the last occurrence is upper bound − 1; the number of occurrences is upper − lower. "The largest element ≤ x" is at upper − 1; "the smallest element ≥ x" is at lower. Trace a = [1, 2, 2, 2, 5, 7], x = 2: lower bound = 1, upper bound = 4, so 2 occurs 4 − 1 = 3 times at indices 1..3. For x = 3: both bounds are 4, so it is absent and would be inserted at index 4.

In Python you should use bisect in real code and say so, but interviewers usually want you to write the loop once to show you can. Since Python 3.10, bisect functions accept a key argument, which helps when searching a list of tuples.

Searching a sorted matrix and other index spaces

If a matrix's rows are sorted and each row starts after the previous row ends, it is a sorted array of R·C elements written row by row. Binary search on a virtual index k in [0, R·C), reading the element at matrix[k // C][k % C]. That is O(log(R·C)). (If only rows and columns are sorted separately, use the staircase walk from al5 instead.)

The index space can be anything ordered: days, timestamps, versions. The Time-Based Key-Value Store keeps, for each key, a list of (timestamp, value) appended in increasing time order; get(key, t) needs the last entry with timestamp ≤ t, which is bisect_right(times, t) − 1.

Rotated sorted arrays

A rotated sorted array, such as [4, 5, 6, 7, 0, 1, 2], is a sorted array cut once with the halves swapped. It is not sorted, but it has a property that keeps binary search alive: whatever mid you pick, at least one of the halves [lo, mid] and [mid, hi] is sorted, because the single "drop" can only be in one of them.

Find the minimum. Compare a[mid] with the last element of the current range. If a[mid] > a[hi], the drop — and so the minimum — is to the right of mid. Otherwise the range mid..hi is sorted and the minimum is at mid or to its left. That is a monotone predicate: "a[i] ≤ a[last]" is false on the left part and true on the right part.

def find_min(a):
    lo, hi = 0, len(a) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] > a[hi]:
            lo = mid + 1          # drop is right of mid
        else:
            hi = mid              # mid..hi sorted: min at mid or left
    return a[lo]

Trace [4, 5, 6, 7, 0, 1, 2]: lo = 0, hi = 6, mid = 3 (7 > 2) → lo = 4; mid = 5 (1 ≤ 2) → hi = 5; mid = 4 (0 ≤ 1) → hi = 4. Answer a[4] = 0.

Search for a target. At each step, decide which half is sorted by comparing a[lo] with a[mid], then check whether the target falls inside the sorted half's range. If it does, search there; otherwise search the other half.

def search_rotated(a, x):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == x: return mid
        if a[lo] <= a[mid]:                    # left half sorted
            if a[lo] <= x < a[mid]: hi = mid - 1
            else: lo = mid + 1
        else:                                  # right half sorted
            if a[mid] < x <= a[hi]: lo = mid + 1
            else: hi = mid - 1
    return -1

This one uses the closed-interval style with an early return, because "find x" naturally ends when it is found; both styles are fine as long as you do not mix them. Duplicates break the "which half is sorted" test when a[lo] == a[mid] == a[hi]; the fix is to shrink lo and hi by one, which makes the worst case O(n).

Peaks: binary search without sortedness

"Find any peak" (an element larger than its neighbours, with the outside treated as −∞) in O(log n). Look at a[mid] and a[mid + 1]. If a[mid] < a[mid + 1], the values rise to the right; following the rise must eventually hit a peak, because the array ends with −∞. So a peak exists in (mid, hi]. Otherwise, a peak exists in [lo, mid]. The invariant is "a peak exists in [lo, hi]", and each step keeps it while halving the range. This is a good example to remember because it shows that the requirement is not sortedness but a guarantee about which half still contains an answer.

Binary search on the answer

Now the delivery-truck problem from the start. The general recipe has four steps:

  1. Identify the answer as a number in a known range: a speed, a capacity, a distance, a time.
  2. Write the feasibility check: "given candidate answer x, can the task be done?" Usually a greedy pass in O(n).
  3. Prove monotonicity: if x is feasible, is every larger x feasible (for minimisation)? State why.
  4. Choose bounds: lo where it is certainly infeasible or the smallest legal value, hi where it is certainly feasible. Then run the template.

Koko eating bananas: piles of bananas, h hours, Koko eats at most k bananas per hour from one pile. Find the minimum k to finish. Check(k): hours = Σ ceil(p / k) ≤ h. Monotone: a faster speed never takes more hours. Bounds: k from 1 to max(piles) (at max, each pile takes one hour, the least possible).

def min_eating_speed(piles, h):
    def ok(k):
        return sum((p + k - 1) // k for p in piles) <= h   # ceil without floats
    lo, hi = 1, max(piles)
    while lo < hi:
        mid = (lo + hi) // 2
        if ok(mid): hi = mid
        else: lo = mid + 1
    return lo

Trace piles = [3, 6, 7, 11], h = 8: lo = 1, hi = 11. mid = 6: hours 1 + 1 + 2 + 2 = 6 ≤ 8, ok → hi = 6. mid = 3: 1 + 2 + 3 + 4 = 10 > 8 → lo = 4. mid = 5: 1 + 2 + 2 + 3 = 8 ok → hi = 5. mid = 4: 1 + 2 + 2 + 3 = 8 ok → hi = 4. Answer 4. Complexity O(n log max(pile)).

The same recipe solves a whole family:

  • Capacity to ship within D days: candidates from max(weight) to sum(weights); greedy check counts days.
  • Split array largest sum (minimise the largest of k contiguous parts): candidates from max(a) to sum(a); greedy check counts parts.
  • Magnetic force / aggressive cows (place m items maximising the minimum gap): here larger answers are harder, so the predicate is "gap d is achievable" and you want the last true — use first_true on "d is not achievable" and subtract one, or flip the comparison.
  • Minimum days to make m bouquets: candidates are days; check counts bouquets formed from flowers bloomed by that day.

The tell-tale signs in a problem statement are "minimum maximum", "maximum minimum", "smallest x such that…", "at least / at most within a limit", and constraints with a huge value range (up to 10⁹) but moderate n.

Binary search on real numbers

"Find the square root of x to six decimal places" or "find the minimum time such that…" with real-valued answers. The template changes slightly: there is no "+1", so loop a fixed number of times (100 iterations halve the range by 2¹⁰⁰, far beyond double precision) or until hi − lo is below the tolerance.

def sqrt_real(x, iters=100):
    lo, hi = 0.0, max(1.0, x)
    for _ in range(iters):
        mid = (lo + hi) / 2
        if mid * mid >= x: hi = mid
        else: lo = mid
    return hi

For integer square roots, use the integer template (or math.isqrt) and avoid floating point entirely, because float rounding near perfect squares gives off-by-one answers for large inputs.

Choosing between the closed and half-open styles

You will see two styles in the wild. The closed style keeps the target in [lo, hi] inclusive, loops while lo ≤ hi, and updates with mid ± 1; it suits "find x and return early". The half-open first-true style used in this lesson keeps the boundary in [lo, hi), loops while lo < hi, and updates with hi = mid or lo = mid + 1; it suits every boundary question and search on the answer. Both are correct. The danger is mixing them — a closed-style loop condition with half-open updates is the source of most infinite loops and missed elements. Pick one as your default (the first-true style covers more problems), and switch to the other only deliberately.

Recognising the pattern

Reach for binary search when: the input is sorted or rotated-sorted; the problem asks for a first/last position, count or insertion point; a constraint makes O(n) too slow for a single query (O(log n) needed); or the answer is a number and "is x good enough?" is monotone. Then state the predicate, why it is monotone, and the bounds, before writing the loop.

Proving the feasibility check is monotone

Search on the answer is only correct if feasibility is monotone, and interviewers increasingly ask you to justify it. The argument is usually a one-line "relaxation" proof: any schedule that works with capacity c also works with capacity c + 1, because every day's load that fit under c also fits under c + 1. For maximisation problems the argument flips: if items can be placed with minimum gap d, they can be placed with any smaller gap, using the same placement. When you cannot find such an argument, be suspicious — for example, "number of distinct values in the window is at most k" is monotone in the window size, but "number of distinct values equals k" is not, and a binary search over it would silently skip answers.

The greedy check must be optimal for the fixed answer

The feasibility check usually greedily packs elements in order ("start a new day when the next package would overflow"). That greedy is only valid if it uses the minimum number of days for that capacity. For contiguous splits it is: the exchange argument says that delaying a cut never helps, because a part that could have taken one more element and did not only pushes more load onto later parts. When the order is not fixed (you may reorder packages), greedy packing becomes bin packing, which is NP-hard, and binary search on the answer no longer has a cheap check. Spotting that difference — contiguous versus arbitrary assignment — is a senior-level observation.

Median of two sorted arrays: binary search on a partition

The hard classic searches over a cut position rather than a value. Cut the shorter array A at i (i elements on the left) and the other array B at j = (m + n + 1) // 2 − i, so the two left parts together contain half the elements (the extra one when the total is odd). The cut is correct exactly when every left element is ≤ every right element, which reduces to two comparisons: A[i − 1] ≤ B[j] and B[j − 1] ≤ A[i]. If A[i − 1] > B[j], i is too far right; if B[j − 1] > A[i], i is too far left — a monotone condition over i, so binary search finds it in O(log min(m, n)). Use −∞ and +∞ for the elements just outside the arrays so empty sides need no special code. Then the median is max(left maxima) for odd totals, or the average of max(left maxima) and min(right minima) for even totals. Explaining it as "binary search on where to cut A, with B's cut determined by the half-size constraint" is the clear version interviewers hope to hear.

Ternary search and unimodal functions

When a function increases and then decreases (unimodal), you can find its maximum by comparing two interior points m1 < m2: if f(m1) < f(m2), the maximum is right of m1; otherwise it is left of m2. Each step discards a third of the range. For integer domains it is usually simpler and as fast to binary search the predicate "f(i) < f(i + 1)", which is true on the rising part and false on the falling part — exactly the peak-finding argument. Ternary search is mostly useful on real-valued convex functions (minimising a cost over a continuous parameter).

Exponential search for unbounded ranges

If you do not know an upper bound — searching an infinite sorted stream, or a predicate over all positive integers — first find one by doubling: check 1, 2, 4, 8, … until the predicate is true at 2ᵏ, then binary search within [2ᵏ⁻¹, 2ᵏ]. Total cost O(log answer), not O(log of some huge guess). The same doubling idea is behind "galloping" in Timsort's merge, which Python's own sort uses to merge runs quickly when one run's elements mostly come before the other's.

Binary search inside other algorithms

Binary search often appears as a component. The O(n log n) longest increasing subsequence keeps an array tails[k] = the smallest possible tail of an increasing subsequence of length k + 1; tails is sorted, and each new element replaces the lower bound of itself in it (al21). Sweep-line and interval problems binary search sorted event lists. "Count pairs with distance ≤ d" plus binary search on d finds the k-th smallest pair distance. Recognising binary search as a building block — "I need the first element ≥ x in a sorted structure that I maintain" — is how you get O(n log n) solutions to problems that look quadratic.

In the interview room

Binary search is where interviewers watch for precision under pressure. The failures they see most are infinite loops (lo = mid with the lower middle), returning the wrong boundary (the last false instead of the first true), off-by-one bounds for search on the answer (starting lo at 0 when a speed of 0 divides by zero, or hi too small so the true answer is outside the range), and the classic overflow in languages with fixed-size integers. Avoid all of them by saying the template, the predicate, and the bounds out loud before writing any code: "first true of 'speed k finishes within h hours', k from 1 to max pile, which is always feasible".

Testing binary search by hand has a standard checklist: empty array; one element (present and absent); target smaller than everything; target larger than everything; target equal to the first and last element; many duplicates of the target. For search on the answer, test the smallest and largest possible answers. Five minutes of this catches almost every bug.

Interviewers also probe recognition. A strong signal is spotting search on the answer from the shape "minimise the maximum" before the interviewer hints at it, and justifying monotonicity in one sentence. A weak signal is trying a DP or a greedy guess on Split Array Largest Sum without noticing the monotone structure.

Online assessments love search on the answer because it rewards recognition: the problem is phrased as an optimisation with a story ("minimum number of hours", "largest possible minimum distance"), the constraints allow values up to 10⁹, and a straightforward simulation is O(n) per candidate. If you catch yourself writing a loop over every candidate answer, stop and ask whether feasibility is monotone.

In real systems

The most famous production binary search bug: in 2006 Joshua Bloch reported that the binary search in Java's standard library (and the mergesort in many libraries) computed (low + high) / 2, which overflows when the array has more than about a billion elements. The bug had been in the JDK for nine years and in the textbook it was copied from for longer; the fix is low + (high − low) / 2 or an unsigned shift. It is the canonical example of a "correct" algorithm failing at scale. Binary search is also a daily debugging tool: git bisect binary searches commit history for the change that introduced a bug — with 1,000 commits since the last good build, about 10 test runs find the culprit. The same idea bisects configuration changes, dependency versions, or the size of input that makes a service fall over. Inside databases, B-tree indexes binary search the sorted keys within each page on the way down the tree, and time-series databases binary search block indexes to find the blocks covering a time range. Capacity planning tools effectively search on the answer: "what is the smallest instance count that keeps p99 latency under 200 ms at this load?", found by load-testing candidates chosen by bisection.

    import random, bisect

def first_true(lo, hi, pred):

    return k

Recognise and set up search on the answer

"You have n routers to place on a straight street at given candidate positions (sorted, up to 10⁵ of them, coordinates up to 10⁹). Place exactly m routers to maximise the minimum distance between any two." Describe the predicate, why it is monotone, the bounds, the check, and the complexity.

Answer

The answer is a distance d. Predicate: "we can place m routers with every gap at least d". Monotone in the decreasing direction: if gap d is achievable, any smaller gap is achievable with the same placement, so the predicate is true, true, …, true, false, false. We want the last true. Using the first-true template, search for the first d where it is not achievable and subtract one; or write the mirrored template with mid = (lo + hi + 1) // 2 and lo = mid on success. Bounds: d from 0 (always achievable) to (max − min) // (m − 1) + 1 (cannot be achievable, since m − 1 gaps cannot all exceed the total span divided by m − 1). Check: greedy — place the first router at the first position, then place each next router at the first position at least d beyond the last placed one; feasible if you place m. The greedy is optimal because placing a router as early as possible never reduces the room for later ones. Complexity: O(n) per check and about 30 checks for a 10⁹ range, so O(n log(range)) ≈ 3 × 10⁶ steps.
