Linked lists are rarely the best data structure in real code, so why do interviews ask about them so often? Because they test something specific: whether you can manipulate references precisely, without losing data, while keeping several moving parts in your head. Reverse a list, and if you reassign one pointer in the wrong order, the rest of the list becomes unreachable and is gone. Remove a node and forget the case where it is the head, and the function returns the wrong list. These are exactly the kind of small, careful, state-tracking steps that real systems code — memory allocators, caches, schedulers, parsers — is full of.

Linked lists also carry a few genuinely beautiful ideas that reappear elsewhere. Two pointers moving at different speeds can find the middle of a list in one pass, detect a cycle using constant memory, and even find exactly where the cycle starts. A dummy node before the head turns half a dozen special cases into none. And the hardest list problems — reorder a list, reverse in groups of k, sort a list — turn out to be compositions of three or four basic moves.

This lesson builds those moves one at a time: the node model and safe traversal; the dummy head; in-place reversal with a full trace; merging; fast and slow pointers for middles and cycles, including the proof behind Floyd's algorithm; gap pointers for "n-th from the end"; and then the composite problems. Along the way it covers when a linked list is the right structure at all, and why, in practice, it usually is not.

The mental model: train cars and couplings

Picture a train. Each car carries some cargo (the value) and has a coupling that hooks onto the next car (the next pointer). The engine is the head. To reach the tenth car, you walk from the engine through nine couplings — there is no way to jump straight to car ten. To insert a car between cars 4 and 5, you only need to change two couplings: unhook 4 from 5, hook 4 to the new car, and hook the new car to 5. Nothing else moves. That is the trade-off of a linked list compared with an array: insertion and removal at a known place is cheap, but finding a place means walking.

In code, a node is a tiny object:

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

The list is just a reference to its first node. The last node's next is None. Walking the list is a loop: node = head; while node: ...; node = node.next.

The one rule that prevents almost every linked-list bug: before you change a coupling, keep hold of whatever it was attached to. If you unhook car 4 from car 5 without anyone holding car 5, cars 5 onwards roll away and are lost. In code, that means saving nxt = curr.next before reassigning curr.next.

Where the analogy breaks: a real train has one engine, but a linked list can be shared — two lists may merge into a common tail, or a list can loop back on itself (a cycle) so that walking never ends. Real trains do not form loops; buggy linked lists do, and several interview problems are about detecting exactly that.

It helps to have the costs side by side. Reading the k-th element: O(1) in an array, O(k) in a list. Inserting or deleting at the front: O(n) in an array (everything shifts), O(1) in a list. Inserting or deleting next to a node you already hold: O(n) in an array, O(1) in a list (O(1) for deletion only if it is doubly linked or you hold the predecessor). Appending at the end: amortised O(1) in a dynamic array, O(1) in a list if you keep a tail reference. Memory: an array stores the elements contiguously; a list adds a reference (or two) per element and scatters the nodes. Interview problems on lists are designed around the column where lists win — rearranging nodes without copying — and they forbid the shortcut of copying values into an array, which is why constraints like "O(1) extra space" appear so often.

Finally, a note on vocabulary. In Python there are no raw memory pointers; "pointer" in linked-list problems just means a variable that refers to a node. Assigning a = b makes a refer to the same node as b — it does not copy the node. Keeping that distinction in mind (moving a reference versus changing a node's next) is half of getting these problems right.

The dummy head

Many list operations might change the first node: removing all nodes with a given value (what if the head has it?), merging two lists (which head comes first?), partitioning around a value. Without care, each needs a special case for the head. A dummy node removes the special case: create a placeholder node whose next is the real head, do the operation as if every real node had a predecessor, and return dummy.next.

def remove_elements(head, val):
    dummy = ListNode(0, head)
    prev = dummy
    while prev.next:
        if prev.next.val == val:
            prev.next = prev.next.next     # unlink; prev stays put
        else:
            prev = prev.next
    return dummy.next

Notice that when a node is removed, prev does not advance: the new prev.next has not been checked yet. That small detail is a classic bug source.

Reversal, iteratively

Reversing a list in place is the single most important list operation, because it appears inside many harder problems. Three references walk the list: prev (the already-reversed part), curr (the node being flipped), and a temporary nxt (the rest of the list, saved before flipping).

def reverse(head):
    prev, curr = None, head
    while curr:
        nxt = curr.next        # 1. save the rest
        curr.next = prev       # 2. flip this arrow
        prev = curr            # 3. advance prev
        curr = nxt             # 4. advance curr
    return prev                # new head

A recursive version exists: reverse the rest, then make the next node point back to the current one (head.next.next = head; head.next = None). It is elegant but uses O(n) stack frames and fails on long lists in Python, so present the iterative one by default.

Merging two sorted lists

Merging uses the dummy head and a tail pointer that always points to the last node of the merged result:

def merge(a, b):
    dummy = tail = ListNode()
    while a and b:
        if a.val <= b.val:
            tail.next, a = a, a.next
        else:
            tail.next, b = b, b.next
        tail = tail.next
    tail.next = a or b             # attach the leftover
    return dummy.next

No new nodes are created; existing nodes are re-linked. Using <= keeps the merge stable (equal values from a come first). This is the merge step of merge sort, and "merge k sorted lists" is the same loop with a heap choosing the smallest of k heads (al10).

Fast and slow pointers: the middle

Move slow one node per step and fast two. When fast reaches the end, slow has covered half the distance — the middle. One pass, no length needed.

def middle(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
    return slow     # odd length: exact middle; even: second middle

For 1→2→3→4→5, slow ends at 3. For 1→2→3→4, at 3 (the second middle). If you need the first middle — for example to cut a list into two halves for merge sort — use while fast.next and fast.next.next, which stops slow one node earlier on even lengths.

Fast and slow pointers: cycles (Floyd's algorithm)

If a list has a cycle, walking it never reaches None. To detect one with O(1) memory, run the same two pointers. Without a cycle, fast hits None. With a cycle, both pointers eventually enter it; from then on, fast gains exactly one node on slow per step, so the gap shrinks by one each step and they must meet — fast cannot "jump over" slow.

Finding where the cycle starts needs a second phase. Let the tail before the cycle have a nodes, the cycle have c nodes, and the meeting point be b nodes into the cycle. When they meet, slow has walked a + b steps and fast 2(a + b). Fast has also done some whole number k of extra laps: 2(a + b) = a + b + k·c, so a + b = k·c, which means a = k·c − b. Read that equation as a walk: starting from the meeting point and walking a steps around the cycle lands at (b + a) mod c = 0 — the cycle's start. And walking a steps from the head also lands at the cycle's start. So:

def cycle_start(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:                 # phase 1: they meet in the cycle
            p = head
            while p is not slow:         # phase 2: both move one step
                p, slow = p.next, slow.next
            return p                     # the cycle's first node
    return None                          # no cycle

This is the same algorithm that finds the duplicate in an array of n + 1 values in 1..n (al5), where the array defines the next pointers.

Gap pointers: n-th from the end

To remove the n-th node from the end in one pass, keep two pointers exactly n + 1 nodes apart. Start both at a dummy before the head, move fast n + 1 steps, then move both until fast is None. Now slow is the node just before the target, which is what you need to unlink it: slow.next = slow.next.next. Starting at the dummy makes "remove the head" (n equals the length) work with no special case.

Composite problems

Harder list problems are usually two or three of the moves above, glued together. Recognising the pieces is the skill.

  • Reorder List (L0 → Ln → L1 → Ln−1 …): find the middle, cut, reverse the second half, then merge by alternating nodes.
  • Palindrome Linked List in O(1) space: find the middle, reverse the second half, compare the halves node by node, and (politely) reverse it back.
  • Sort List in O(n log n): merge sort — split at the middle (first-middle variant), sort both halves, merge.
  • Reverse Nodes in k-Group: repeat "check k nodes exist, reverse k nodes, reconnect" with a pointer to the node before each group.

Reverse in k-groups is the hardest of these to get right, because of the reconnection. For each group: remember group_prev (the node before the group) and the group's first node first; reverse k nodes, which leaves prev at the new group head and curr at the node after the group; then set group_prev.next = prev (link to the new head) and first.next = curr (the old first node is now the group's tail and must link onward); finally move group_prev = first. Drawing the four nodes involved before writing the code makes it straightforward.

Rearranging by building sub-lists

A family of medium problems — Partition List (all nodes less than x before the rest, keeping order), Odd Even Linked List (all odd-position nodes, then all even-position nodes), splitting a list into k parts — shares one robust technique: walk the list once and append each node to the end of one of several new lists, each with its own dummy head and tail pointer, then stitch the lists together.

def partition(head, x):
    small = s_tail = ListNode()
    large = l_tail = ListNode()
    while head:
        if head.val < x:
            s_tail.next = head; s_tail = head
        else:
            l_tail.next = head; l_tail = head
        head = head.next
    l_tail.next = None              # crucial: cut the old link
    s_tail.next = large.next        # stitch
    return small.next

The line l_tail.next = None is the one people forget. The last node placed in the large list still points to whatever followed it in the original list — possibly a node now in the small list — which creates a cycle. Whenever you rebuild lists from existing nodes, terminate every tail explicitly.

Removing duplicates from a sorted list is the same "keep or skip" idea in its simplest form: walk with one pointer, and while the next node has the same value, skip it with curr.next = curr.next.next; only advance when the next value differs. The "remove all nodes that have duplicates" variant needs a dummy head and a prev pointer, because whole runs — possibly including the head — disappear.

Two more classics

Intersection of two lists. Two lists may share a common tail. Pointer a walks list A and then switches to B's head; pointer b walks B and then switches to A's head. If A's own part has length x, B's own part y, and the shared tail z, each pointer walks x + z + y nodes before reaching the intersection a second time, so they arrive together. If there is no intersection, both reach None together after x + y steps. O(m + n) time, O(1) space, no lengths needed.

Copy List with Random Pointer. Each node has an extra random reference to any node or None, and you must deep-copy the list. The straightforward way is a dict from each original node to its copy: one pass creates the copies, a second wires copy.next = map[orig.next] and copy.random = map[orig.random]. The O(1)-space way interleaves: insert each copy right after its original (A → A' → B → B' …), then orig.next.random = orig.random.next sets every copy's random pointer, and a final pass separates the two lists.

Add Two Numbers. Digits are stored in reverse order, so the lists can be added like grade-school addition from the least significant digit: walk both, add digits and the carry, create a node for the units digit, carry the tens. Keep going while either list has nodes or the carry is non-zero, so 5 + 5 produces 0 → 1.

Recognising the pattern

Linked-list problems announce themselves, so recognition is about choosing the move: anything that may change the head → dummy node; "reverse" anywhere → the four-line loop; "middle", "half" or "cycle" → fast and slow pointers; "from the end" → gap pointers; two sorted lists → merge. For anything else, ask which combination of those it is.

Why fast must gain exactly one step

Floyd's argument relies on the relative speed being 1: once both pointers are in the cycle, the distance from slow forward to fast decreases by exactly one each iteration (fast moves two, slow one), so it reaches zero — they cannot pass each other without meeting. With speeds 1 and 3 the gap shrinks by 2 per step and can skip over zero when the cycle length and gap are odd and even in the wrong combination, so meeting is not guaranteed on the first lap. The time bound is also clean: slow enters the cycle after a steps and is caught within c more steps, so detection is O(a + c) = O(n). Brent's algorithm is an alternative that moves only one pointer and teleports the other at powers of two; it does fewer next-pointer evaluations and is used in Pollard's rho factorisation, but Floyd's is the one interviewers expect, and the one whose second phase gives the cycle start so neatly.

Doubly linked lists and why LRU caches use them

A singly linked list cannot remove a node in O(1) unless you also hold its predecessor, because the predecessor's next must change. A doubly linked list stores prev as well, so given any node you can unlink it in O(1): node.prev.next = node.next; node.next.prev = node.prev. Combine it with a hash map from key to node and you get an LRU cache: the map finds a node in O(1), the list moves it to the front in O(1) on access, and evicting the least recently used item pops the back in O(1). Two sentinel nodes (a dummy head and a dummy tail) remove every edge case. This design is covered in detail in al28 and is exactly how Python's OrderedDict is implemented in its pure-Python version.

Memory layout: why arrays usually win

Big-O hides the most important practical fact about linked lists: their nodes are scattered in memory. An array's elements are adjacent, so the CPU loads 64-byte cache lines containing many elements and prefetches the next ones; a list traversal follows a reference to an arbitrary address at each step, which may cost a main-memory access of around 100 ns instead of about 1 ns. In Python the gap is smaller (everything is a reference to a heap object anyway), but a Python list of ints still beats a chain of node objects by a wide margin, and uses far less memory per element (8 bytes for the reference versus a full object with a dict or slots for each node). That is why Python's collections.deque is implemented as a doubly linked list of blocks of 64 elements: it keeps O(1) operations at both ends while getting most of the cache benefit of arrays.

Recursion on lists and the stack

Many list operations have elegant recursive forms — reverse, merge, remove elements, check palindrome with a "front pointer" carried through recursion. Each uses one stack frame per node, so O(n) space, and in Python a list of more than about 1,000 nodes raises RecursionError. In interviews, write the iterative version by default and mention the recursive one as an alternative. If you do use recursion (merge is the most natural), say "this is O(n) stack space; for long lists I'd make it iterative".

Skip lists: linked lists with express lanes

A skip list adds "express lane" pointers on top of a sorted linked list: each node is promoted to the next level with probability one half, so level k has about n/2ᵏ nodes. Search starts at the top level and drops down whenever the next node would overshoot, giving O(log n) expected time for search, insert and delete — like a balanced tree, but with simpler code and easy concurrent implementations. Redis uses skip lists for its sorted sets, and LevelDB and RocksDB use them for their in-memory tables. If an interviewer asks how to make a sorted linked list searchable in O(log n), a skip list is the answer they are fishing for.

In the interview room

Linked-list rounds are graded heavily on correctness under edge cases, because the code is short and the bugs are predictable. The ones interviewers see most: losing the rest of the list by reassigning next before saving it; dereferencing None (fast.next.next when fast.next is None); forgetting to return dummy.next and returning the old head instead; advancing prev after a deletion, which skips a node; and creating an accidental cycle by not setting the last node's next to None after reordering — which makes the interviewer's test harness hang. Test every solution on an empty list, a single node, two nodes, and a case that changes the head.

A strong habit is to draw the nodes and arrows before coding the tricky part — for reversal in k-groups or reorder, draw the four or five nodes around the operation, write the new arrows, then translate each arrow into one assignment, in an order that never loses a reference. Interviewers like seeing this because it is how careful engineers work, and it makes your code much more likely to be right first time.

Expect the Floyd follow-ups: "why do they meet?" (relative speed one), "why does the second phase find the start?" (a ≡ c − b mod c), and "what is the complexity?" (O(n) time, O(1) space). Being able to sketch the a, b, c picture in thirty seconds turns a memorised trick into an understood algorithm.

On online assessments and in shared editors, you often have to build test lists yourself. Write two small helpers first — one that turns a Python list into a linked list and one that turns a linked list back into a Python list with a length limit (so an accidental cycle prints a truncated list instead of hanging). They take a minute and make every later test a one-liner, and interviewers read them as a sign of an experienced engineer.

In real systems

Linked lists live where O(1) insertion and removal at a known position matter more than traversal speed. Operating-system kernels use them constantly: the Linux kernel's list_head is an intrusive circular doubly linked list (the links are embedded inside the objects themselves, so no separate node allocation is needed) used for run queues, open files, timers and device lists. Memory allocators keep free lists of available blocks, linked through the free blocks' own memory. LRU caches — in databases' buffer pools, in CDN edge caches, in functools.lru_cache — use a hash map plus a doubly linked list. Hash tables that resolve collisions by chaining keep a short linked list per bucket. Python's OrderedDict (pure-Python version) and deque (blocks) are linked structures. Elsewhere, arrays have largely replaced linked lists because of caches; Bjarne Stroustrup's well-known talk on "vector versus list" showed a vector outperforming a list even for insertion-heavy workloads at large sizes, because finding the insertion point dominates and arrays find it much faster.

Compose the moves

"Given a linked list, check whether it is a palindrome in O(n) time and O(1) extra space, and leave the list unchanged when you return." Describe the steps and the edge cases.

Answer

Step 1: find the first middle with fast and slow pointers (loop while fast.next and fast.next.next), so for 1→2→2→1 slow stops at the first 2 and for 1→2→3→2→1 at 3. Step 2: reverse the list starting at slow.next — that is the second half — with the iterative loop, keeping a reference to the reversed head. Step 3: walk p from the head and q from the reversed head, comparing values while q is not None; any mismatch means not a palindrome (record the result rather than returning immediately). Step 4: reverse the second half again and reattach it with slow.next = the re-reversed head, restoring the original list, then return the result. Edge cases: empty list and single node are palindromes (handle before step 1, or check that the loop does nothing harmful); for odd lengths the middle node stays with the first half and is never compared, which is correct. Complexity: O(n) time — four linear passes at most — and O(1) extra space. Mention the simpler O(n)-space alternative (copy values into an array and compare with its reverse) and why the interviewer's constraint rules it out.
