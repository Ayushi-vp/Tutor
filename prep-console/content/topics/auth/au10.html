In March 2019 someone downloaded data about roughly 100 million people in the United States and 6 million in Canada from Capital One's cloud storage. Capital One's own account calls it a "configuration vulnerability". The public court filings and many analyses since describe the chain: a web application firewall running on an AWS virtual machine could be tricked into making HTTP requests on the attacker's behalf — server-side request forgery, SSRF — and the attacker pointed it at the address every AWS virtual machine uses to learn about itself, the instance metadata service at 169.254.169.254. That service answered with temporary credentials for the machine's role, because it trusts anything that can reach it from the machine. The role could list and read S3 buckets. No password was stolen; no user was phished. A machine's identity was simply borrowed.

Most requests in a modern system aren't made by people at all. A checkout service calls payments; a nightly job reads a bucket; a CI pipeline deploys to production; a pod queries a database. Each of those callers is a principal (au1) and needs an identity that it can prove and the receiver can verify. The traditional answers — "it's inside the network, trust it" and "give it an API key" — are exactly what fail: network position is borrowed by anyone with a foothold, and long-lived keys end up in repositories, images and logs.

The modern answer is workload identity: credentials issued automatically to a workload by the platform it runs on, short-lived, bound to what the workload is, and exchangeable for access elsewhere. This topic builds it up. We'll look honestly at API keys; then mTLS with SPIFFE identities and how a workload gets a certificate without any pre-planted secret; Kubernetes' bound service-account tokens; federation that lets a pod or a GitHub Actions job swap a signed token for one-hour cloud credentials; the metadata service and how AWS hardened it after 2019; the arithmetic that makes short lifetimes so valuable; and finally authorisation between services — because zero trust means checking who is calling and whether they're allowed.

Staff badges in a hospital

Think of a hospital. Visitors sign in at reception and get a paper sticker. Staff are different: each has a badge with a photo and a chip, issued by HR after checking who they are, valid for a limited time, and each door reader checks the badge against a policy — nurses into wards, pharmacists into the pharmacy. Nobody gets into the pharmacy because they're "already inside the building". And if a badge is lost, it expires soon and can be cancelled.

Services need staff badges. The old alternatives look like a hospital that props internal doors open because the front door is locked (trusting the internal network), or one that gives every department a shared door code that never changes (API keys). The badge model has four ingredients, and every technology in this topic is a version of them:

  1. Attestation — someone trustworthy checks what the workload actually is before issuing anything: this is pod api-7d9f in namespace payments running as service account api on a node the platform controls.
  2. A verifiable identity document — a certificate or signed token naming the workload, issued by an authority the receivers trust.
  3. Short life and automatic renewal — hours, not months, so a stolen document soon stops working, and nobody handles the secret by hand.
  4. Policy at every door — the receiver checks the identity and whether that identity may do this.

Where the analogy breaks: hospital badges are checked by people who can notice odd behaviour; services check millions of requests per second automatically, so policies must be explicit and logged, and anomalies must be found by monitoring. And a workload can be copied — the "badge" must be bound to something the copy can't take with it, such as a private key held by the workload's own runtime.

Who the callers actually are

List the non-human callers in a typical product and the scale of the problem becomes clear: dozens of microservices calling each other; background workers reading queues and writing databases; scheduled jobs; CI/CD pipelines with deploy rights to production; data pipelines with read access to everything; third-party integrations calling your public API; monitoring agents on every node; and increasingly AI agents (au12). In most organisations these non-human identities outnumber employees many times over, and each historically got a credential someone created by hand and nobody remembers. Every one of them is a door into the system; this topic is about giving each a proper badge.

If you stop here: give every workload its own identity, issued by the platform after checking what it is; keep credentials short-lived and automatic; never trust network location; and authorise every call by caller identity, deny by default.

1. API keys, honestly

An API key is a long random string the caller sends with each request (Authorization: Bearer sk_live_… or a custom header). The server looks it up and finds which account it belongs to. Keys are simple, work with any HTTP client, and are the standard way external developers authenticate to public APIs — Stripe, OpenAI and Anthropic all issue them. Their weaknesses are the weaknesses of any long-lived shared secret:

  • They leak. Into source code and git history, container images, CI logs, crash reports, screenshots, notebooks and chat messages. Scanners crawl public repositories for key patterns continuously.
  • They live long. Rotating a key means updating every consumer, so it happens rarely, often only after an incident.
  • They identify accounts, not workloads. If five services share a key, logs can't say which one made a call, and revoking it breaks all five.
  • They're bearer credentials (au4): possession is identity.

If you issue API keys, do it well: generate them from a CSPRNG with a recognisable prefix (acme_live_) so secret scanners and your own detectors can spot them; store only a hash (SHA-256 is fine — keys are high-entropy, unlike passwords) and show the key once; let customers create several keys with scopes and expiry dates and rotate without downtime (two active keys at a time); record last-used times so stale keys can be removed; and participate in secret-scanning partner programmes so leaked keys are reported to you. For your own services talking to each other, avoid them entirely.

2. Mutual TLS with SPIFFE identities

net9 explained mutual TLS: both sides present certificates in the handshake and prove they hold the matching private keys. For service identity the interesting questions are what name goes in the client's certificate and how a workload gets a certificate without someone copying a private key onto it.

SPIFFE (Secure Production Identity Framework For Everyone, a CNCF project) answers the first. A SPIFFE ID is a URI: spiffe://trust-domain/path, such as spiffe://acme.com/billing/payments. The trust domain (acme.com, or prod.acme.com per environment) is the root of trust, backed by one set of signing keys; the path names the workload, often by convention from its platform identity — Istio uses spiffe://cluster.local/ns/<namespace>/sa/<serviceaccount>. The document that proves a SPIFFE ID is an SVID (SPIFFE Verifiable Identity Document), in two forms: an X.509-SVID, a certificate with the SPIFFE ID in its URI subject alternative name, used for mTLS; and a JWT-SVID, a JWT whose subject is the SPIFFE ID, for when end-to-end TLS isn't possible (through a load balancer that terminates TLS, say). SPIFFE's documentation prefers X.509-SVIDs because JWTs, as bearer tokens, can be replayed if intercepted.

The second question — getting the certificate safely — is answered by the Workload API and attestation. SPIRE, the reference implementation, runs a server (the CA) and an agent on every node:

  1. Node attestation. When the agent starts, it proves to the server which node it's on using evidence the platform provides — a cloud instance identity document signed by AWS or GCP, a Kubernetes projected token, a TPM quote.
  2. Workload attestation. When a process connects to the agent's Workload API (a Unix domain socket on the node), the agent asks the kernel which process is connecting and looks up its properties: in Kubernetes, the pod, namespace, service account and image; on a VM, the Unix user and binary path.
  3. Issuance. If those properties match a registration entry ("pods in namespace payments with service account api get spiffe://prod.acme.com/ns/payments/sa/api"), the agent hands the workload an SVID and the private key, plus the trust bundle (CA certificates) needed to verify others.
  4. Rotation. SVIDs are short-lived — commonly an hour to a day — and the agent pushes fresh ones before expiry over the same API.

Nothing secret was deployed with the workload; its identity came from what the platform could prove about it. In a service mesh (Istio, Linkerd and others), the mesh plays SPIRE's role — its control plane is the CA, and the proxy beside each service obtains the certificate and performs mTLS — so application code doesn't change.

3. Kubernetes service account tokens

Kubernetes has its own identity for pods: the ServiceAccount. Every pod runs as one (the namespace's default if none is set — which is why "one service account per workload" is the first hardening rule). The proof of that identity is a token.

Old clusters stored long-lived service account tokens in Secrets that never expired. Since Kubernetes 1.22, pods instead receive projected service account tokens from the TokenRequest API: JWTs signed by the cluster's service-account issuer that are bound to the specific pod (they stop working when the pod is deleted), carry an audience, and expire. The documented defaults: expirationSeconds defaults to one hour, with a minimum of 10 minutes, and the kubelet refreshes the token on disk before it expires (when it's older than 80% of its lifetime or 24 hours). A pod can mount several, one per audience:

volumes:
- name: aws-token
  projected:
    sources:
    - serviceAccountToken:
        audience: sts.amazonaws.com
        expirationSeconds: 3600
        path: token

The token's claims identify the workload precisely:

{"iss": "https://oidc.eks.eu-west-1.amazonaws.com/id/EXAMPLED539D4633E53DE1B71EXAMPLE",
 "sub": "system:serviceaccount:payments:api",
 "aud": ["sts.amazonaws.com"],
 "exp": 1791363600, "iat": 1791360000,
 "kubernetes.io": {"namespace": "payments", "serviceaccount": {"name": "api"},
                   "pod": {"name": "api-7d9f6c", "uid": "…"}}}

Because the cluster publishes OIDC discovery and a JWKS for its issuer, anything outside the cluster can verify these tokens with the techniques from au4 — which is what makes federation possible. (The Secrets that k8s9 discussed are a separate thing: application secrets stored in the cluster. Workload identity's goal is to need far fewer of them.)

4. Workload identity federation to the cloud

The pod needs to read an S3 bucket. The old way: create an IAM user, generate an access key, store it in a Kubernetes Secret. The new way: have AWS trust the cluster's token issuer and exchange the pod's token for temporary credentials. AWS calls the EKS version IAM Roles for Service Accounts (IRSA); Google Cloud and Azure have equivalents (Workload Identity Federation for GKE, Microsoft Entra Workload ID). The flow:

The trust policy on the IAM role is where security lives:

{"Effect": "Allow",
 "Principal": {"Federated": "arn:aws:iam::111122223333:oidc-provider/oidc.eks.eu-west-1.amazonaws.com/id/EXAMPLED539…"},
 "Action": "sts:AssumeRoleWithWebIdentity",
 "Condition": {"StringEquals": {
    "oidc.eks.eu-west-1.amazonaws.com/id/EXAMPLED539…:aud": "sts.amazonaws.com",
    "oidc.eks.eu-west-1.amazonaws.com/id/EXAMPLED539…:sub": "system:serviceaccount:payments:api"}}}

Drop the sub condition and every service account in the cluster can become this role. The same pattern removes static keys from CI: GitHub Actions can request an OIDC token from token.actions.githubusercontent.com whose sub encodes the repository and the branch or environment (for example repo:acme/payments:environment:production), and a cloud role can trust exactly that. A workflow triggered from a fork or another repository gets a different subject and can't assume the role. The temporary credentials returned by AssumeRoleWithWebIdentity last an hour by default (configurable up to the role's maximum session duration).

5. The metadata service, and what Capital One taught everyone

Cloud VMs get their own identity through the instance metadata service (IMDS), a link-local HTTP endpoint at 169.254.169.254 reachable only from the instance. In AWS's original version (IMDSv1), a plain GET to /latest/meta-data/iam/security-credentials/<role> returns temporary credentials for the instance's role. Anything that can make the instance send a GET to that address — including an SSRF bug in an application, or a misconfigured proxy or firewall — can steal them. That is the path public analyses describe in the 2019 Capital One incident.

In November 2019 AWS added IMDSv2, built specifically against this class:

  • Clients must first make a PUT to /latest/api/token with a header giving the token lifetime, and receive a session token; later requests must carry it in X-aws-ec2-metadata-token. Most SSRF bugs and open proxies can only issue GETs and can't set arbitrary headers.
  • The response carrying the token is sent with an IP time-to-live of 1 by default, so it can't travel beyond the instance even if the instance is misconfigured as a router; containers that need IMDS require the hop limit raised to 2.
  • Requests carrying an X-Forwarded-For header — the signature of a request relayed by a proxy — are refused a token.

Hardening checklist: require IMDSv2 on every instance (disable v1), keep the hop limit at 1 unless containers truly need metadata, give pods their own identity (IRSA, EKS Pod Identity) and block them from the node's metadata, scope instance roles to the minimum, and treat SSRF as a critical bug class (net14).

6. The arithmetic of lifetimes

Why do short lifetimes matter so much? Suppose a credential leaks at a random moment during its validity and works until it expires. The expected remaining validity at the moment of leak is half the lifetime:

CredentialLifetimeExpected usable window after a leak
API key rotated yearly365 days~182 days
API key rotated every 90 days90 days45 days
Federated cloud credentials1 hour30 minutes
Kubernetes projected token (minimum)10 minutes5 minutes

45 days versus 30 minutes is a factor of 2,160. The table understates the difference, because long-lived keys are written into more places (so they leak more often) and rotation schedules slip, while short-lived credentials are fetched at runtime and never stored. The cost moves to issuance: the token service and the platform's attestation become critical, highly available infrastructure, and a compromise of the issuer — its signing keys — is catastrophic (au4's Storm-0558 lesson again). Protect issuers' keys in HSMs or KMS and rotate them.

7. Authorisation between services, and zero trust in practice

Authentication tells the callee who is calling. The decision whether that caller may do this is authorisation, and without it mTLS everywhere still lets every service call every other. In a mesh, authorisation is expressed per service. An Istio example:

apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: {name: payments-allow, namespace: payments}
spec:
  selector: {matchLabels: {app: payments}}
  action: ALLOW
  rules:
  - from: [{source: {principals: ["cluster.local/ns/orders/sa/checkout"]}}]
    to:   [{operation: {methods: ["POST"], paths: ["/charge"]}}]

With an ALLOW policy present, anything not matched is denied. Services then add object-level checks using two identities together: the calling workload from mTLS and the end user from a propagated token (au1) — "checkout, acting for user 42, may charge user 42's saved card". Recording both is what lets you answer "who did this?" correctly.

That's what zero trust (net14, NIST SP 800-207) means for services in practice: every request carries a verifiable identity; every service enforces an explicit, default-deny policy; credentials are short-lived and bound; and network controls remain as a second layer that limits blast radius rather than the thing that grants trust.

8. Where this app sits

The Prep Console is a single service with no service-to-service calls of its own; its outbound calls are to Google's and GitHub's OAuth endpoints, authenticated with OAuth client secrets read from environment variables (au5). Its deployment documentation runs it as a background task or a Docker container behind a reverse proxy. If it grew into several services or moved to Kubernetes, the steps in this topic would replace its secrets: a service account per component, mTLS between them, and federated identity for any cloud storage, leaving the OAuth client secrets as the only long-lived credentials — stored in a secrets manager (au11).

Attestation is the root of everything

Workload identity is only as strong as the evidence used to issue it. If the issuer believes whatever a workload claims about itself, an attacker who can run code anywhere can claim to be anything. Real attestors rely on facts the workload can't forge: the kernel's view of the calling process (its cgroup, hence its pod), the kubelet's knowledge of which pod has which service account, a cloud provider's signed instance identity document, a TPM's measurement of the boot chain. Each moves trust to a lower layer, ultimately to hardware and the platform provider. Interview questions like "how does the pod prove it's the payments pod?" are asking you to name that chain.

Identity granularity

How fine should identities be? Per service account per namespace is the common choice: fine enough to write meaningful policies, coarse enough to manage. Per pod is usually too fine (pods are replaceable replicas of the same identity). Per node or per cluster is too coarse: a compromise of one workload then speaks for all of them. A useful test: if two workloads should ever have different permissions, they need different identities. Shared service accounts ("everything in this namespace runs as default") silently merge identities and are a common audit finding.

Confused deputies between services

Service identity introduces its own confused-deputy risk (au1). If the orders service may call payments, and payments trusts any request from orders, then any user who can make orders call payments with chosen parameters effectively has orders' authority. The mitigations are the same as for agents: propagate the end user's identity and authorise the pair (service, user), pass narrowly scoped tokens per hop (token exchange, au12), and design APIs so the deputy's privileges can't be steered (orders should pass "charge the cart's total for this user", not "charge amount X to card Y").

JWT-SVIDs and the bearer problem

JWT-SVIDs exist because mTLS doesn't always reach end to end: layer-7 load balancers, message queues and serverless platforms terminate or don't support TLS client authentication. A JWT-SVID is a bearer token, so audiences must be tight (one receiving service), lifetimes short (minutes), and receivers must validate exactly like any JWT. Where possible, prefer X.509 at each hop with the proxy re-establishing mTLS, or sender-constrained tokens.

Trust domains, federation and multi-cloud

A trust domain is a boundary of shared signing keys. Organisations usually have one per environment, so staging workloads can never authenticate to production. Crossing domains — another company, another cloud, an acquired business — uses federation: each side publishes a trust bundle, and policies name foreign SPIFFE IDs explicitly. The same idea underlies cloud federation: AWS trusting a GKE cluster's issuer, or GCP trusting GitHub's. Every federation is a new party that can mint identities your systems accept, so each trust relationship deserves the review you'd give a new admin account: exact issuer, exact audience, exact subject patterns, and monitoring of what it's used for.

Detecting identity misuse

Workloads are predictable, which makes misuse detectable. A payments service calls the same handful of services and cloud APIs every day; a compromised payments pod that suddenly lists S3 buckets, calls the user-admin service, or assumes its role from an IP outside the cluster stands out. Build baselines per identity — which callees, which cloud API actions, from where — from mesh telemetry and cloud audit logs, and alert on new edges. Cloud providers' own anomaly services do a version of this for role credentials (for example flagging instance credentials used from outside the instance's network). The identity name in every log line is what makes this possible; with shared keys, there's nothing to baseline.

"Secretless" still has a secret zero

Workload identity removes application secrets, but trust has to start somewhere: the cloud provider's signing keys for instance identity documents, the cluster's service-account signing key, the mesh CA's root key, the TPM's endorsement key. This is the "secret zero" problem — the first credential from which all others are derived. The engineering goal isn't zero secrets but few, well-protected ones: in HSMs or managed KMS, rotated, with tight access and audit. Compare that with a fleet holding hundreds of static keys in config files, and the improvement is in where the risk concentrates and how well it can be guarded.

Human access is also workload access

Engineers reaching production through kubectl, SSH or a database client are another service-to-service problem in disguise. The same techniques apply: short-lived certificates instead of static SSH keys (an SSH CA signing per-session certificates after SSO and MFA), just-in-time elevation with expiry (au8), and identity-aware proxies in front of internal tools. Many breaches use a stale engineer credential rather than an application bug; removing standing human credentials is as important as removing static service keys.

What fails in production

Certificate expiry outages. Short lifetimes mean rotation must never stop; when a mesh CA or SPIRE server is unhealthy for longer than certificate lifetimes, services start failing handshakes en masse. Monitor time-to-expiry across the fleet and the CA's health; make CA components highly available; alert when any workload's SVID is within a fraction of its lifetime of expiry.

Trust-policy wildcards. IRSA or GitHub OIDC roles with missing or wildcard subject conditions let unintended workloads assume privileged roles. Audit every federated trust policy for exact aud and sub.

IMDSv1 still enabled. Older AMIs or launch templates leave v1 on; any SSRF becomes credential theft. Track the share of instances enforcing v2.

Permissive mesh mode forever. Migrations start in permissive mode (accept plaintext and mTLS) and never switch to strict. Track plaintext connections and set a date.

Default service accounts. Many workloads running as default, sometimes with broad RBAC bindings; one compromise grants all of it.

Metrics

Static credentials remaining (count of long-lived keys, by owner and age); share of service-to-service traffic on mTLS; denied calls by authorisation policy (spikes after deploys mean a policy gap; steady denials from one identity mean probing or a bug); token exchanges per workload; assumptions of each cloud role by subject; minimum time-to-expiry across SVIDs; instances allowing IMDSv1.

The Capital One case, read as an engineer

Capital One's incident page says unauthorised access occurred on 22-23 March 2019, was reported to it by an external researcher through its responsible disclosure programme on 17 July, and was confirmed on 19 July; it affected about 100 million people in the US and 6 million in Canada, including about 140,000 US Social Security numbers and 80,000 linked bank account numbers. It describes the cause as a configuration vulnerability; analyses of the court filings describe the SSRF-to-metadata-to-role-credentials chain. The engineering lessons are structural: an internet-facing component's role should never be able to read bulk customer data; the metadata service shouldn't hand credentials to anything that can coax a GET out of the instance; and access to large amounts of data by an unusual principal should alert. AWS's IMDSv2 announcement four months later addressed the second point directly.

Ownership

Non-human identities need owners just as human accounts do. Every service account, role and key should have a named owning team, a purpose and a review date; orphaned identities with broad permissions are a common finding after reorganisations. Tie identity creation to the service catalogue, so that when a service is decommissioned its identities, roles and policies go with it.

Migration playbook

Inventory static credentials first (they're everywhere: environment variables, Secrets, CI settings, config files). Stand up issuance (mesh or SPIRE, cluster OIDC issuers, CI OIDC). Move cloud access to federation one role at a time, verifying with access logs that the old key is unused before deleting it. Turn on mTLS in permissive mode, then strict, namespace by namespace. Write authorisation policies from observed traffic, then enforce. Finish by scanning for leftover keys and setting a policy that new static keys need an exception with an expiry date.

Goal: simulate workload identity federation and see why trust-policy conditions and lifetimes matter — Python 3.12 standard library only. (Real clusters sign with RSA/ECDSA; this lab uses HS256 from au4 to stand in for the issuer's signature.) About 15 minutes.

  1. Issuer. Write issue_sa_token(namespace, sa, audience, ttl) producing a JWT with iss, sub = f"system:serviceaccount:{namespace}:{sa}", aud, iat, exp, signed with the "cluster key".
  2. STS. Write assume_role(role, token, now): verify signature and exp, then check the role's trust policy, a dict like {"iss": …, "aud": "sts.amazonaws.com", "sub": "system:serviceaccount:payments:api"}. On success return {"key": secrets.token_hex(8), "exp": now + 3600}.
  3. Happy path. payments/api gets credentials. Then try orders/checkout and a token with aud="vault": both refused.
  4. Misconfiguration. Change the policy to match sub with fnmatch pattern "system:serviceaccount:*". Repeat step 3: now every service account gets in.
  5. Lifetimes. Simulate 100,000 leaks at random times for credentials with lifetimes of 90 days, 1 hour and 10 minutes; compute the mean remaining validity. Compare with half the lifetime.
  6. Metadata. Model IMDSv1 (get(path) returns credentials) and IMDSv2 (put_token(headers) refuses requests with X-Forwarded-For; get(path, token) requires it). Write an "SSRF" function that can only issue GETs with attacker-chosen URLs and show it succeeds against v1 and fails against v2.

What to look for: step 3 shows audience and subject conditions doing the work; step 4 shows how one wildcard turns a scoped role into a cluster-wide one. Step 5's means land near 45 days, 30 minutes and 5 minutes. Step 6 reproduces, in miniature, why IMDSv2's PUT-and-token design defeats the SSRF chain described in the Capital One analyses.

Review: a startup's service credentials

A startup runs 12 services on EKS. Findings from a review: services call each other over plain HTTP inside the cluster with a shared header X-Internal-Key; an IAM user's access key with S3 and DynamoDB full access is stored in a Kubernetes Secret used by all pods; GitHub Actions deploys with another IAM user's keys saved as repository secrets; EC2 nodes allow IMDSv1; all pods run as the default service account. Prioritise and propose a plan.

Answer

1. Shared full-access AWS key in a Secret (highest). Every pod, and anyone who can read Secrets in that namespace, holds full S3/DynamoDB access indefinitely. Replace with IRSA (or EKS Pod Identity): one role per service with least privilege, trust policies pinned to exact sub and aud. Rotate and then delete the IAM user's key once CloudTrail shows it unused.

2. IMDSv1 on nodes. Any SSRF in any pod can take the node role's credentials. Enforce IMDSv2 with hop limit 1 and block pod access to node metadata.

3. CI keys. Replace with GitHub OIDC federation: a deploy role trusting repo:org/repo:environment:production only, used by protected-environment workflows. Delete the repository secrets.

4. Service-to-service auth. A single static header shared by 12 services identifies nobody and leaks everywhere. Introduce a mesh (or SPIRE) with mTLS — permissive, then strict — and AuthorizationPolicies per service, default deny, based on SPIFFE IDs; remove the header.

5. Service accounts. One per service, no automounted API token where the pod doesn't need the Kubernetes API, minimal RBAC.

6. Verify. Inventory remaining static credentials monthly; alert on any new IAM user keys; monitor role assumptions by subject.
