On 4 January 2023 CircleCI, a continuous-integration provider used by thousands of software companies, told every one of its customers to rotate every secret they had ever stored with it: cloud access keys, deploy keys, API tokens, OAuth tokens, SSH keys. Its incident report explains why. On 16 December 2022, malware on one CircleCI engineer's laptop stole a valid single-sign-on session — one that had already passed two-factor authentication. With it, an attacker reached production systems, spent a few days looking around, and on 22 December copied customer data, including the environment variables, tokens and keys customers had given CircleCI so their builds could deploy software. That data was encrypted at rest. It didn't matter: the attacker extracted the encryption keys from running processes. A customer noticed suspicious use of a GitHub OAuth token on 29 December, and the rest of the industry spent early January rotating credentials.

CI providers are an extreme case, but every system is full of secrets: the key that signs sessions, the database password, the OAuth client secret, the cloud credentials, the payment provider's API key. Each one is a password for something. Earlier topics replaced many of them — passkeys instead of passwords (au7), short-lived tokens instead of long ones (au4), workload identity instead of static cloud keys (au10) — but some always remain, and the ones that remain tend to be the most powerful.

This topic is about managing those well across their whole life: creating them, storing them, getting them to the code that needs them without leaving copies, encrypting data with keys that never leave hardware, rotating without outages, keeping them safe in CI pipelines and containers, and responding in minutes when one leaks. We'll work the economics of a key management service with real prices, look honestly at how this app stores its own secrets, and draw the lessons of CircleCI and of the 2025 compromise of a popular GitHub Action that printed pipelines' secrets into public logs.

The keys to the building, again

A well-run building doesn't hand out copies of the master key. It keeps master keys in a safe that can't be opened by any one person; it gives contractors a key that works for one door for one week; it logs every time a key is signed out; it changes the locks when a key goes missing; and it has a plan for the day a key is found on the pavement. Secrets management is exactly that discipline applied to credentials.

Four ideas carry the whole topic:

  • Fewer secrets. The best secret is one that doesn't exist: federation instead of a stored cloud key, a passkey instead of a password, a dynamic credential instead of a shared one.
  • A safe, not a drawer. Remaining secrets live in a secret manager — encrypted, access-controlled per identity, audited — and master keys live in a KMS backed by hardware security modules that never release them.
  • Delivered, not distributed. Code fetches secrets at runtime under its own identity, instead of secrets being copied into repositories, images, config files and laptops.
  • Replaceable at any moment. Every secret can be rotated quickly and routinely, so a leak becomes a five-minute procedure rather than a crisis.

Where the analogy breaks: a copied physical key is visible; a copied secret isn't. You can't tell from the secret itself how many copies exist or who holds them. That's why the realistic posture is to assume secrets leak and to make each one short-lived, narrowly scoped and quickly revocable — and why audit logs of who read what matter as much as the encryption.

Not all secrets are equal

It helps to sort secrets by what an attacker gains, because that decides how much effort each deserves. At the top are root secrets: token-signing keys, CA private keys, KMS master keys, the session-signing key of a web app, cloud root or organisation-admin credentials. Whoever holds one can mint identities or decrypt everything, so they belong in HSMs or KMS, are almost never read by humans, and are rotated with care. Next are broad service credentials: deploy roles, database admin passwords, CI tokens with write access to many repositories — high blast radius, and the main targets of the incidents in this topic. Then scoped credentials: one service's read-only database user, one integration's API key. At the bottom are low-value secrets such as a webhook verification token for a non-critical notification. A useful exercise for any system is to list its secrets in these tiers and ask, for each tier, how long it lives, who can read it, and how fast it can be rotated. The answers are usually most uncomfortable in the second tier.

If you stop here: eliminate what you can, put the rest in a manager with per-identity access and audit, keep master keys in a KMS, deliver at runtime, rotate routinely, and practise revoking.

1. What counts as a secret, and where secrets leak

A secret is any value whose possession grants access or lets you impersonate something: passwords and API keys, OAuth client secrets and refresh tokens, database credentials, private keys for TLS and SSH, token-signing keys, encryption keys, webhook signing secrets, and the session-signing key of a web framework. Secrets differ in blast radius: a read-only analytics key exposes one dataset; a token-signing key lets an attacker become anyone (au4).

The places secrets leak are depressingly consistent:

  • Source code and git history. A key committed and then deleted is still in history, in every clone and fork, and in the scanners that crawl public pushes continuously.
  • Container images. An ENV API_KEY=… line or a copied .env file is in an image layer forever, even if a later layer deletes it (k8s2 covers layers).
  • CI logs and artefacts. A set -x, a verbose tool, or malicious code printing variables.
  • Application logs and error trackers that record request headers, environment variables or connection strings.
  • Developer machines. Shell history, dotfiles, local .env files, browser sessions — and malware that harvests them, as at CircleCI.
  • Human channels. Tickets, chat messages, wikis and screenshots.
  • Backups and dumps of databases and machines that contain secrets in config tables or files.

The structural answer is not "be careful" but to remove the opportunities: fewer static secrets, delivered at runtime, never written to disk in plaintext, and scanned for everywhere.

2. Secret managers and dynamic secrets

A secret manager — HashiCorp Vault (now under the Business Source Licence, with the open-source OpenBao fork maintained under the Linux Foundation), AWS Secrets Manager, Google Secret Manager, Azure Key Vault — provides:

  • Encrypted storage, usually envelope-encrypted under a KMS key (section 3).
  • Per-identity access control: the payments service, authenticated by workload identity (au10), may read prod/payments/* and nothing else.
  • Audit: every read and write is logged with the caller's identity — the basis for detecting bulk reads and for scoping an incident.
  • Versioning and rotation, with built-in rotation for databases and some cloud services.
  • Dynamic secrets: instead of storing a database password, the manager holds an admin credential for the database and, when a service asks, creates a new database user with the right grants and a lease — say one hour — and drops the user when the lease ends. Each service instance has its own credential, revocation is lease expiry, and a leaked credential identifies exactly which consumer leaked it.

Delivery options, from least to most robust: environment variables injected at start (simple; leaks through process inspection and dumps; can't change without restart); files mounted into the container from the manager (the Kubernetes Secrets Store CSI driver, a sidecar agent) with tight permissions, refreshed on rotation; or the application calling the manager's API at runtime and caching values in memory. High-value secrets should avoid environment variables.

3. KMS and envelope encryption

A key management service (AWS KMS, Google Cloud KMS, Azure Key Vault keys) holds master keys inside hardware security modules (HSMs) and performs operations with them on request, under access policies, with every use logged. The key material never leaves. That's ideal for protection and awkward for volume: AWS KMS's Encrypt API accepts at most 4,096 bytes of plaintext for a symmetric key, every call is a network round trip, and calls are priced and rate-limited.

Envelope encryption resolves this:

  1. Call GenerateDataKey with the master key's ID. The KMS returns a fresh 256-bit data key twice: in plaintext, and encrypted ("wrapped") under the master key.
  2. Encrypt the data locally with the plaintext data key, using an authenticated cipher such as AES-256-GCM.
  3. Store the ciphertext together with the wrapped data key. Discard the plaintext data key.
  4. To decrypt, send the wrapped data key to the KMS's Decrypt. If your identity is allowed (and any encryption context matches), you get the plaintext data key back; decrypt locally.

Worked example: cost and latency. An API serving 1,000 requests per second decrypts a data key per request. That's 1,000 × 86,400 = 86.4 million Decrypt calls a day. AWS KMS charges $0.03 per 10,000 symmetric requests (beyond a free tier of 20,000 a month), so 86.4 million ÷ 10,000 × $0.03 = $259.20 a day, about $7,800 a month — plus a network round trip of a few milliseconds on every request, a hard dependency on KMS availability, and request-rate quotas to stay under. Now let each of 50 processes cache an unwrapped data key for 5 minutes: 86,400 ÷ 300 = 288 refreshes per process per day, × 50 = 14,400 calls a day, or about 4 cents. The trade-off is that plaintext data keys sit in memory for up to 5 minutes — exactly where CircleCI's attacker found theirs — so keep cache lifetimes short, scope data keys narrowly (per tenant, au9), and protect production memory access. Key storage itself is $1 per key per month.

Encryption context is worth using: non-secret key-value pairs ({"tenant": "acme", "purpose": "invoices"}) bound to the encryption, which must match exactly to decrypt and appear in the KMS audit log. It stops a wrapped key for one tenant being decrypted in another tenant's context and makes logs meaningful.

Rotation of master keys is cheap with envelope encryption: KMS automatic rotation creates new key material but keeps old versions for decryption, so existing data keys still unwrap and new ones use the new version. (AWS bills the first two rotations of a key at an extra $1 a month each, capped after that.)

4. Rotation without downtime

Rotation is replacing a secret with a new one and retiring the old. It fails as an outage when a secret is cut over in one step and some consumer still has the old value. The pattern that works is overlap:

  1. Create the new secret alongside the old one (a second API key, a second database user, the database's dual-password feature, a new signing key published in a JWKS before use — au4).
  2. Accept both at the verifying side.
  3. Move consumers to the new value — by updating the secret manager and letting consumers re-read, or rolling deployments.
  4. Verify from logs that the old secret is no longer used (last-used timestamps are invaluable here).
  5. Revoke the old secret.

Automating this and running it routinely (monthly, say) has a second benefit: when a secret leaks, rotation is a familiar, tested procedure measured in minutes. Teams that never rotate discover during an incident that nobody knows which services use a key. Some secrets can't overlap — a framework session key without fallback support logs everyone out on rotation — which is why features like Flask's SECRET_KEY_FALLBACKS exist (au3).

5. Secrets in containers and Kubernetes

Containers add two traps. Images are permanent: anything copied into a layer is recoverable from the image even if deleted later, and images are pushed to registries that many people can pull. Never put secrets in Dockerfiles or build contexts; use build-time secret mounts (Docker BuildKit's --mount=type=secret) for secrets needed only during build. Kubernetes Secrets aren't encrypted by default: k8s9 showed they're base64 in etcd. Configure encryption at rest with a KMS provider so etcd holds only ciphertext wrapped by a KMS key; restrict RBAC on Secrets (and remember that anyone who can create pods in a namespace can mount its Secrets); and prefer pulling from an external manager (External Secrets Operator, the Secrets Store CSI driver) so the source of truth, access control and audit live in the manager. For GitOps, where config lives in git, use encrypted forms (sealed secrets, SOPS) or references to the manager rather than plaintext.

6. Secrets in CI/CD

CI pipelines hold the most dangerous credentials an organisation has — production deploy rights, package-publishing tokens, signing keys — and run code from many sources. The practices:

  • Federate instead of storing. Use the CI system's OIDC tokens to obtain short-lived cloud credentials scoped to repository and environment (au10). Customers who did this had little to rotate after CircleCI's breach.
  • Scope by environment and branch. Production secrets only in jobs for protected branches or environments with required reviewers.
  • Keep untrusted code away from secrets. Workflows triggered by pull requests from forks must not see secrets; be especially careful with triggers that run in the base repository's context with fork-controlled code.
  • Pin third-party actions and plugins to commit SHAs. Tags can be moved. On 14 March 2025 the widely used tj-actions/changed-files GitHub Action (used in over 23,000 repositories) was compromised: its tags were pointed at malicious code that dumped the runner's memory, including secrets, into the build log — public for public repositories. CISA's alert advised identifying affected workflows, rotating any exposed secrets and pinning actions by SHA.
  • Minimise job permissions (the job's own token read-only by default), and don't print environment variables or enable shell tracing in steps that handle secrets.

7. This app's secrets, honestly

The Prep Console's secrets are few and well understood: SECRET_KEY, which signs every session cookie (au3) — whoever holds it can mint a session for any user, including administrators; the Google and GitHub OAuth client secrets (au5); and configuration such as ADMIN_EMAILS and BASE_URL, which aren't secret but are security-relevant. They live in prep-console/.env, loaded with python-dotenv at startup. The repository's .gitignore excludes .env and .env.* while keeping .env.example, which lists the fields with empty values and the command to generate a key. On the first run, the Windows start script creates .env from the example with a fresh key from secrets.token_hex(32) — 256 bits from the operating system's CSPRNG — and stops so the owner can fill in the rest. The Docker setup reads the same file through env_file. In production mode the app refuses to start without SECRET_KEY; only in dev-login or test mode does it generate a throwaway one, accepting that sessions won't survive a restart.

For a single self-hosted tool that's a sensible design. Its residual risks are the ones this topic predicts: the .env file's filesystem permissions and any machine backups that include it; secrets passed as environment variables to a container (visible to anyone who can inspect it); and rotation of SECRET_KEY, which today logs everyone out because the app doesn't configure key fallbacks. If it grew, the next steps would be a secret manager read at startup and SECRET_KEY_FALLBACKS for graceful rotation.

8. Leaked-key response

When a secret leaks, the order of operations matters, and the most common mistake is to start with cleanup:

  1. Revoke or disable the secret immediately. If that would break production, attach a deny-all policy or restrict it to known source addresses while you swap it — measured in minutes, not after a meeting.
  2. Replace it, ideally with something better (a federated role instead of a key).
  3. Investigate use: the provider's audit log for every action taken with that credential since it could first have leaked — new users, keys, roles, unusual regions or APIs, data reads.
  4. Remediate anything the attacker created or changed, and rotate other secrets they could have reached.
  5. Clean up: remove the secret from git history and other copies, purge it from logs.
  6. Prevent: secret scanning on push (GitHub's push protection blocks pushes containing recognised secrets), pre-commit hooks, scanning of images and logs, and the structural fixes — fewer static secrets.

Encryption at rest protects against a specific threat

"Encrypted at rest" is often treated as a general security property. It defends against stolen disks, snapshots and backups, and against storage-layer access that bypasses the application. It does nothing against an attacker who can act as the application, because the application can decrypt. CircleCI's report is the clearest public example: customer secrets were encrypted, and the attacker took the keys from running processes. The questions that matter are who can call decrypt (which identities, with what approvals), what's logged when they do, whether bulk decryption raises alarms, and whether keys are scoped so one decryption context can't read everything. Application-level envelope encryption with per-tenant keys and KMS-enforced identity is meaningfully stronger than storage-level encryption because it moves the decrypt decision to a place with its own policy and audit.

The secret manager as a single point of compromise

Centralising secrets improves control and creates a target. An identity with broad read access to the manager — a CI system, an admin, a misconfigured service — is a skeleton key. Contain it the way you'd contain any privileged system: per-identity, per-path policies with no wildcard reads in production; no standing human access to production secret values (access via break-glass with alerts, or via tooling that uses secrets without revealing them); authentication to the manager through workload identity; separate instances or namespaces per environment; and anomaly alerts on read patterns (one identity reading many paths it never read before). Dynamic secrets help here too: values exfiltrated from the manager expire with their leases.

Secret zero and bootstrapping

To read secrets from a manager, a workload must authenticate — with what? Historically with another secret (a Vault token baked into the image), which just moves the problem. Modern answers use platform identity (au10): Kubernetes service-account tokens, cloud instance identity, CI OIDC tokens, verified by the manager's auth methods. The irreducible secrets are then the platform's own signing keys and the manager's root of trust (Vault's unseal keys or KMS-based auto-unseal), which live in HSMs and are rarely touched. Interviewers ask "how does the service get its first secret?" to see whether you know this chain.

Detecting leaks before attackers use them

Leak detection works best when secrets are recognisable. Providers now issue keys with distinctive prefixes and checksums so scanners can find them with few false positives, and run partner programmes where code hosts report leaked keys directly to the issuer, which can revoke automatically. You can do the same for your own secrets: give them a prefix and a checksum, register the pattern with your code host's scanning, and scan logs, tickets and chat exports for the pattern. Honeytokens — fake credentials planted where an attacker would look, which alert when used — turn leaks into detections: a canary AWS key in a config file that pages security on any API call.

Memory, crash dumps and debugging

Plaintext secrets must exist in memory while used, so memory is a leak surface: crash dumps uploaded to error trackers, core files on disk, debuggers and profilers attached in production, and heap snapshots shared in tickets. (Storm-0558's investigation, au4, originally theorised a signing key in a crash dump; Microsoft later said that hadn't been confirmed, but the risk class is real and widely recognised.) Mitigations: keep secrets in memory briefly, scrub them from dumps where tooling allows, restrict who can attach debuggers or download dumps from production, and prefer operations where the secret never enters application memory — signing inside a KMS or HSM rather than loading the private key.

Signing without holding the key

The safest place for a signing key is somewhere the application can use but never read. KMS and HSMs offer Sign operations: the application sends a digest, the KMS signs it with a non-exportable key, and every signature is logged against the caller's identity. Token issuers, release-signing pipelines and certificate authorities increasingly work this way, which turns "the key leaked" — a permanent compromise — into "an identity was misused to request signatures", which is time-bounded, logged and revocable by changing one policy.

Rotation frequency is a risk calculation

How often should you rotate? au10's arithmetic applies: a secret that leaks at a random time is usable for, on average, half its rotation period. But rotation itself has risk (outages from imperfect overlap) and cost. The pragmatic answer: rotate high-value static secrets on a schedule that your automation makes boring (monthly or quarterly), rotate immediately on any suspicion, prefer dynamic or federated credentials where frequency becomes irrelevant, and use rotation drills to prove the procedure works. A secret that can't be rotated without a coordinated outage is itself a finding.

Failure modes

Rotation outages: a database password is changed in one step; services holding the old one in connection pools fail as connections recycle. Use overlap, and test rotation in staging.

Secret manager unavailability: services that fetch secrets at startup can't start during an outage, and autoscaling stalls. Cache secrets in memory with sensible lifetimes, make the manager highly available, and decide which services may start with cached values.

KMS throttling: per-request decrypts hit quota limits under load, causing errors that look unrelated. Cache data keys; batch where possible.

Orphaned secrets: keys for decommissioned services still valid years later. Inventory with owners and last-used timestamps; expire unused secrets.

Leaky observability: logs and traces with Authorization headers, connection strings or full environment dumps. Redact at the logging library, scan log storage for secret patterns.

Metrics

Number of static secrets by type, owner and age; share past their rotation date; secrets with no reads in 90 days (candidates for deletion); secret-scanning findings per week and time to revoke; KMS decrypt rate and throttles per service; secret manager read anomalies; percentage of CI deployments using OIDC federation instead of stored keys.

CircleCI 2023, read as an engineer

From CircleCI's report: malware on an engineer's laptop on 16 December 2022 stole a 2FA-backed SSO session; the attacker used it to access production, conducted reconnaissance from 19 December and exfiltrated data on 22 December, including customer environment variables, tokens and keys; the data was encrypted at rest but the attacker extracted encryption keys from running processes; a customer alerted CircleCI to suspicious GitHub OAuth activity on 29 December; CircleCI disclosed on 4 January 2023 and advised every customer to rotate all secrets, stating that anything stored after 5 January could be considered secure. Its follow-up changes included tighter production access, step-up authentication, new detections, and moves towards automatic OAuth token rotation and more granular GitHub app permissions. For customers, the lesson was concrete: those who had replaced stored cloud keys with OIDC federation had little to rotate; those with dozens of long-lived keys spent days finding and replacing them.

Ownership and inventory

Secrets without owners are the ones that never get rotated and are still valid years after their service was turned off. Keep an inventory — generated, not hand-maintained — from the secret manager, cloud IAM (access keys and their last-used dates), CI settings and code scanning, with an owning team, purpose and rotation date for each. Review it quarterly and delete what nobody claims. Tie secret creation to the service catalogue, so decommissioning a service also revokes its credentials. And give developers a paved road: a one-line way to get a secret into a service from the manager, so that pasting a key into an environment file is never the easiest option.

Third parties hold your secrets too

CI providers, monitoring vendors, deployment platforms and SaaS integrations all hold credentials into your systems. CircleCI's incident made every customer's stored keys a risk overnight. Keep a list of which vendors hold which credentials, prefer integrations that use federation or narrowly scoped, short-lived tokens, and rehearse rotating everything a given vendor holds — because when a vendor discloses a breach, that's the procedure you'll be running under time pressure.

Practising response

Run a leak drill quarterly: pick a real (non-critical) secret, declare it leaked, and time the team from declaration to revocation, replacement, and confirmation of no unauthorised use. Drills expose missing runbooks, unknown consumers and rotation procedures that require someone on holiday. The metric to drive down is time to revoke.

Goal: implement envelope encryption, rotation with overlap, and a secret scanner with Python 3.12's standard library. The standard library has no AES, so this lab uses a teaching cipher — an HMAC-SHA256 keystream with an HMAC tag (encrypt-then-MAC) — that illustrates the structure; never use it for real data. About 15 minutes.

  1. Toy KMS. A class holding a master key (secrets.token_bytes(32)) that exposes only generate_data_key(context) → (plaintext key, wrapped key) and decrypt(wrapped, context), logging every call. Wrapping uses the teaching cipher with the context bound into the tag.
  2. Envelope. Encrypt a JSON record with a data key; store {ciphertext, wrapped_key, context}; decrypt via the KMS. Then try decrypting with a different context (tenant=initech): it must fail.
  3. Cost model. Count KMS calls for 10,000 simulated requests with no caching and with a 300-second cache per process across 5 processes and a simulated clock; multiply by $0.03 / 10,000.
  4. Rotation. Keep {"current": k2, "previous": k1} for an HMAC-signed API token; verify with either; sign only with current; show tokens signed with k1 still verify until you drop it.
  5. Scanner. Write a regex scanner for patterns such as AKIA[0-9A-Z]{16}, -----BEGIN [A-Z ]*PRIVATE KEY-----, ghp_[A-Za-z0-9]{36} and long high-entropy strings (compute Shannon entropy per token). Run it over a sample directory with a planted fake key and over this app's .env.example.

What to look for: the KMS log shows every decrypt — that's the audit property. The wrong-context decrypt fails, illustrating encryption context. The cost model reproduces the body's ratio of thousands to one. Rotation never breaks verification. The scanner finds the planted key and nothing in .env.example, whose secret fields are empty — confirming the template is safe to commit.

Respond: "our deploy key is in a public repository"

At 14:05 a security researcher emails: a public GitHub repository belonging to one of your engineers contains a file with an AWS access key ID and secret for an IAM user named deploy-bot, committed 3 days ago. deploy-bot has AdministratorAccess and is used by your CI system to deploy 40 services. Walk through the next two hours and the next two weeks.

Answer

14:05-14:15, contain. Assume the key was found by scanners within minutes of the push three days ago. Deactivate the access key now. If deploys break, accept that; if a critical deploy must go out, issue a temporary new key to CI only and plan to remove it. Don't wait to delete the repository.

14:15-15:00, investigate. CloudTrail across all regions for that access key ID since the commit (and before, in case of other leaks): new IAM users, keys, roles or policy changes; EC2/GPU launches in unusual regions (crypto-mining is the common first use); S3 reads of sensitive buckets; changes to CloudTrail itself or to GuardDuty. Check billing for anomalies.

15:00-16:05, remediate. Delete any attacker-created users, keys, roles and resources; restore any changed policies; rotate any secrets readable with admin rights that the attacker might have read (Secrets Manager values, SSM parameters) if logs show access. Have the engineer delete the repository file and history, and ask GitHub support to purge cached views if needed.

Next two weeks, prevent. Replace deploy-bot with OIDC federation from CI: a role per environment with a trust policy pinned to repository and environment, permissions scoped to deployment rather than AdministratorAccess. Delete the IAM user. Enable push protection and secret scanning for the organisation and personal repositories of employees where policy allows; add pre-commit scanning; add a honeytoken key in likely places; set an alert for any IAM user key creation. Run a leak drill in a month to confirm time-to-revoke is under 15 minutes.
