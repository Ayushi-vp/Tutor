On 18 October 2023, someone logged into Cloudflare's Okta tenant as one of Cloudflare's own administrators. They didn't have the administrator's password, and they didn't pass a second-factor prompt. They didn't need to. Days earlier, a Cloudflare employee had opened a support case with Okta and, as support engineers often ask, attached a HAR file — a recording of their browser's network traffic, made to help debug a problem. That recording contained the employee's session cookie. An attacker who had broken into Okta's support system with a stolen credential read the file, lifted the cookie, put it in their own browser, and was logged in. Cloudflare's security team spotted the activity and contained it, more than 24 hours before Okta told them anything was wrong. Other Okta customers had the same experience.

That story is the whole of this topic in miniature. Logging in is expensive — a password, a second factor, maybe a hardware key. So once you've done it, the server hands your browser a small token, the session, and from then on that token is you. The password and the MFA prompt protect the front door; the session cookie walks straight past it. Stealing, forging, fixing, riding and failing to revoke sessions are where a large share of real account takeovers happen.

This topic explains how sessions work end to end. We'll compare server-side sessions with signed client-side sessions, decoding the real signed cookie this app (the Prep Console) uses. We'll set every cookie flag deliberately and see what each defends against, work through cross-site request forgery with a trace, show how session fixation turns a login into a gift for the attacker, and then deal with the uncomfortable part: timeouts, logout that actually logs out, revocation for millions of sessions, and newer defences such as device-bound sessions for when the cookie is stolen anyway.

The cloakroom ticket

You hand your coat to a cloakroom attendant. They don't memorise your face; they give you a numbered ticket, 047, and put a matching tag on your coat. When you come back, you show the ticket, and you get the coat. The ticket is a session: proof that you are the person who handed over coat 047, so you don't have to prove who you are again.

Notice what the ticket is and isn't. Anyone holding ticket 047 gets the coat — the attendant doesn't check it's you. That's a bearer credential, and it's why theft matters so much. The number must not be guessable: if tickets are numbered 001, 002, 003, anyone can make up a valid one, which is why real session IDs are long random strings. And the cloakroom keeps a list: when you collect your coat, ticket 047 is crossed off, and a copy of the ticket made earlier is now worthless. That's revocation, and it only works because the attendant keeps state.

Now a second cloakroom that keeps no list. Instead, the ticket itself says "coat on hook 47, issued 19:02" and is stamped with a seal only the cloakroom can make. Any attendant, even one who wasn't there when you arrived, can check the seal and fetch your coat — no shared list needed, which is lovely when there are twenty attendants in different rooms. But there's no way to cross a ticket off. If someone photocopies your sealed ticket, the copy carries a valid seal until the date on it passes. That's a signed client-side session, and it's what Flask — and so this app — uses by default.

Where cookies come in

On the web, the ticket travels in a cookie (net7 covers the mechanics): the server sends Set-Cookie: prep_session=…, the browser stores it and sends it back with every request to that site. The browser attaching the cookie automatically is what makes sessions convenient — and is exactly what cross-site request forgery exploits, because the browser attaches it even when another site triggered the request. Cookie attributes are the controls: Secure (HTTPS only), HttpOnly (invisible to page scripts), SameSite (whether to attach it to requests started by other sites), plus Domain, Path and lifetime.

Four ways to attack a session

It helps to name the attacks up front, because each defence in this topic answers one of them. Guess it: predict or brute-force a valid session ID — defeated by long random IDs. Steal it: read the cookie off the network, out of a script, out of the browser's files, or out of a log or support upload — limited by Secure, HttpOnly, short lifetimes, redaction and device binding. Ride it: make the victim's own browser send a request that carries their cookie, without ever seeing the cookie — cross-site request forgery, defeated by SameSite, tokens and origin checks. Plant it: give the victim a session the attacker already knows, and wait for them to log in — session fixation, defeated by issuing a new session at login. And behind all four sits the question of ending it: if you can't revoke a session, every other defence has a clock that only runs out at expiry.

If you stop here: a session is a bearer ticket; make it unguessable, keep it off the wire and out of scripts, don't let other sites make the browser use it, give it a lifetime, and make sure you can cancel it.

1. Why sessions exist

HTTP is stateless: each request stands alone. After a successful login — a password check that deliberately takes tens of milliseconds (au2), or an OAuth round trip through Google that takes seconds (au5) — the server needs a way to recognise the next request from the same browser without repeating that. The answer, for browser applications, is to issue a session and put a reference to it in a cookie. Each later request carries the cookie; the server maps it back to "user 12, logged in at 09:14 with MFA".

Everything in this topic follows from one property: the cookie is a bearer credential. The server checks the cookie, not the person. Anyone who presents it — from any computer — is user 12. So the design goals are: make it impossible to guess or forge, hard to steal, impossible for other sites to use through the victim's browser, short-lived, and revocable.

2. Server-side sessions

The classic design. At login the server generates a random session ID, stores a record in a session store — a database table or an in-memory store such as Redis — and sends the ID in a cookie:

sid = secrets.token_urlsafe(32)            # 256 random bits, 43 URL-safe characters
redis.set("sess:" + sha256(sid), json.dumps({"uid": 12, "auth_time": now, "mfa": True}),
          ex=1800)                         # idle timeout 30 min
Set-Cookie: __Host-sid=<sid>; Secure; HttpOnly; SameSite=Lax; Path=/

On each request: read the cookie, look up the record, check it hasn't expired, refresh its idle timer. On logout: delete the record. The cookie is meaningless without the store.

How random is random enough? OWASP requires at least 64 bits of entropy. Here's the arithmetic. Suppose a million sessions are active and an attacker can make 10,000 guesses a second against your API. Each guess hits a valid session with probability 106 ÷ 264. Expected time to a hit is 264 ÷ (104 × 106) = 1.84 × 1019 ÷ 1010 ≈ 1.8 × 109 seconds ≈ 58 years. At 128 or 256 bits the number is absurdly large, and random bytes are free, so use 256. What breaks this is not short IDs but predictable ones: IDs from timestamps, counters, or a non-cryptographic random generator whose state can be recovered from a few outputs. Always use secrets (Python), crypto.randomBytes (Node) or your framework's generator.

A nice hardening detail: key the store by a hash of the session ID, not the ID itself. Then a leaked Redis snapshot or a debugging dump of the session table doesn't contain usable cookies.

Costs: a store read on every request (sub-millisecond for Redis, but it's a dependency every request now has), writes to refresh the idle timer (rate-limit those to once a minute per session), and a store that must be shared by all app servers and highly available — if it's down, nobody is logged in.

3. Signed client-side sessions — this app's cookie, decoded

The alternative puts the session data in the cookie, with a signature. Flask does this by default, and the Prep Console uses it. Its cookie is named prep_session, and the backend sets these options: SESSION_COOKIE_HTTPONLY=True, SESSION_COOKIE_SAMESITE="Lax", SESSION_COOKIE_SECURE true when the configured BASE_URL starts with https://, and PERMANENT_SESSION_LIFETIME of 30 days. At login it calls session.clear(), sets session["uid"] = uid and marks the session permanent.

A Flask session cookie has three dot-separated parts, all in URL-safe base64 (no padding):

eyJ1aWQiOjEyfQ . aQX4Mg . Hk2yR1…
└─ payload ──┘   └ time ┘  └ signature ┘
  • Payload: eyJ1aWQiOjEyfQ decodes to {"uid":12}. Anyone can decode it — paste it into any base64 decoder. Signed is not encrypted. (Flask compresses large payloads and marks them with a leading dot.)
  • Timestamp: the time the cookie was signed, as base64 of a big-endian integer of seconds since 1970. When loading, Flask passes max_age equal to the 30-day lifetime, so a cookie signed more than 30 days ago is rejected even if the browser still sends it.
  • Signature: an HMAC over "payload.timestamp". Flask uses the itsdangerous library with SHA-1 as the hash and a key derived from SECRET_KEY by HMAC with the salt "cookie-session". (HMAC-SHA1 remains secure as a MAC; SHA-1's collision weakness doesn't break HMAC.)

Verification is: recompute the HMAC with the server's key over the first two parts and compare with the third using a constant-time comparison. If a user edits the payload to {"uid":1}, the signature no longer matches and Flask treats the session as empty. If they keep the payload and forge a signature, they need SECRET_KEY — which is why the app refuses to start in production without one, and in dev mode generates a random one so sessions don't survive a restart. au4 recomputes exactly this kind of HMAC by hand for a JWT.

Two subtleties of the real configuration are worth knowing. First, Flask's SESSION_REFRESH_EACH_REQUEST defaults to true, so for permanent sessions every response re-issues the cookie with a fresh timestamp: the 30 days are measured from the last request, a sliding expiration. Second, the app re-reads the user row on every request (load_user), so a disabled or deleted user is cut off immediately even though their cookie is still cryptographically valid. That re-read is the app's revocation mechanism — coarse (per user, not per session), but real.

What the app can't do with this design is revoke one stolen cookie while leaving the user logged in elsewhere. Logout calls session.clear(), which makes the response overwrite the browser's cookie with an empty session — but a copy taken earlier still carries a valid signature and, used regularly, keeps sliding forward. The backstops are disabling the user or rotating SECRET_KEY, which logs out everyone. For a small invite-only study tool, that trade-off is reasonable. For a product with admins and customers, you'd add a per-user session_version inside the signed payload and compare it with the database on each request — "log out everywhere" then increments the version and every older cookie fails.

4. Cookie attributes, set deliberately

net7 introduced the attributes; here is the recommended session cookie and why each part is there:

Set-Cookie: __Host-sid=Vb3kq9…; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=28800
  • Secure: never sent over plain HTTP, so a network attacker on café Wi-Fi can't read it even if a page is somehow loaded over http://. Pair it with HSTS (the Strict-Transport-Security header, which this app sends when served over HTTPS) so the browser never makes plain-HTTP requests to the site at all.
  • HttpOnly: document.cookie can't see it, so a cross-site scripting (XSS) payload — attacker-controlled JavaScript running in your page — can't read and exfiltrate it. It can still make requests as the user while the page is open, so HttpOnly limits XSS, it doesn't neutralise it.
  • SameSite=Lax: not attached to cross-site subrequests (images, iframes, fetches) or cross-site POSTs, but attached when the user follows a link to your site, so they arrive logged in. Strict also withholds it on those top-level navigations — safer, but users following a link from email land logged out. None (which requires Secure) sends it everywhere and is only for genuinely cross-site embedded use.
  • __Host- prefix: browsers only accept a cookie whose name starts with __Host- if it is Secure, has Path=/ and has no Domain attribute. That makes it host-only: blog.example.com can't set or overwrite a cookie for app.example.com, which shuts down cookie-tossing and some fixation attacks. (The weaker __Secure- prefix only requires Secure.)
  • Domain: omit it unless you need sharing across subdomains. Domain=example.com sends the session to every subdomain, including the marketing site run by a third party.
  • Max-Age / Expires: without them, the cookie is deleted when the browser session ends (though browsers that restore tabs often keep them). This is only a hint; the server's own expiry check is the control.

A site, for SameSite purposes, is the scheme plus the registrable domain: https://app.example.com and https://blog.example.com are the same site, while example.com and example.net are different. Same-site is broader than same-origin, which matters below.

5. Cross-site request forgery, traced

CSRF exploits the browser's helpfulness: it attaches your cookies to requests to a site no matter which page caused them. Here's an attack on an app whose session cookie has SameSite=None and no other defence:

The defences, roughly in order of how you'd layer them:

  1. Never change state on GET. GETs are sent by links, images and prefetchers, and SameSite=Lax deliberately lets top-level GET navigations carry the cookie. A GET /delete?id=5 endpoint is forgeable with an image tag.
  2. SameSite=Lax or Strict on session cookies. Since Chrome 80 (2020), Chromium-based browsers treat cookies without a SameSite attribute as Lax, which killed most classic CSRF. But not every browser applies that default, and it doesn't stop same-site attackers — a compromised subdomain or one hosting user content is same-site.
  3. A CSRF token. The synchronizer token pattern stores a random value in the server-side session and embeds it in each form or sends it in a header; the server compares. A cross-site page can't read the token, so it can't include it. With signed or stateless sessions, the signed double-submit cookie pattern sets a random value (HMAC-bound to the session) in a cookie and requires it in a header too.
  4. Check where the request came from. Browsers send an Origin header on cross-origin and on POST requests; reject state-changing requests whose Origin isn't yours. Modern browsers also send fetch metadata headers: Sec-Fetch-Site: cross-site on a state-changing request is a clear reject.
  5. Require a custom header. An HTML form can't set custom headers. A script on another site can only add one through fetch, which triggers a CORS preflight (net7); if your server doesn't approve that origin, the browser never sends the real request.

The Prep Console uses layers 1, 2 and 5: its cookie is SameSite=Lax, and a before_request hook rejects any method other than GET, HEAD and OPTIONS unless the request carries X-Prep-Client: 1, returning 403 "missing X-Prep-Client header". The front end's API client always adds the header. It's a cheap, robust defence for a JSON API used only by its own front end — provided the app never enables credentialed CORS for other origins, and accepting that same-origin XSS can set any header.

A word on login CSRF: forging a login request so the victim ends up signed in as the attacker. The victim then saves a payment card or search history into the attacker's account. Protect login forms with the same CSRF defences, and for OAuth logins use the state parameter (au5) — which Authlib, the library this app uses, generates and checks automatically.

6. Session fixation

In a fixation attack the attacker doesn't steal your session — they give you theirs. Trace it:

  1. Attacker visits the site anonymously and receives session ID A1.
  2. Attacker gets the victim's browser to use A1: a link to an old site that accepts ?sessionid=A1 in the URL, or a cookie set from a sibling subdomain the attacker controls (Domain=example.com).
  3. Victim logs in. A naive server looks up session A1 and marks it "user 12, authenticated".
  4. Attacker, still holding A1, is now logged in as user 12.

The fix is one line in the right place: issue a brand-new session ID at login (copying over any pre-login data you need, such as a cart) and destroy the old one. Do the same on every privilege change — step-up authentication, switching tenant, an admin starting to impersonate a user. Never accept session IDs from URL parameters. And use __Host- cookies so a sibling subdomain can't plant one. With Flask's signed sessions there's no server-side ID to fix, and the app's session.clear() before setting uid ensures nothing from the anonymous session carries into the authenticated one.

7. Timeouts and the session lifecycle

Two clocks, both enforced on the server:

  • Idle timeout: end the session if it hasn't been used for a while. It protects the shared or unattended computer. OWASP's typical ranges are 2-5 minutes for high-value applications (banking) and 15-30 minutes for lower-risk ones.
  • Absolute timeout: end the session after a fixed time regardless of activity — OWASP suggests 4-8 hours for office-day applications. It's what bounds a stolen session that the attacker keeps alive by using it. Sliding expiration alone (each use extends the session) never bounds it.

Consumer products usually choose long "remember me" sessions — weeks — because forcing daily logins drives users away; they compensate with re-authentication before sensitive actions (change email, password or payout details; view saved card numbers; delete the account) and step-up checks based on auth_time. Store auth_time and the methods used (amr, e.g. password plus OTP) in the session so policies can ask "was MFA used within the last 15 minutes?".

The Prep Console's 30-day permanent session, refreshed on every request, is effectively a sliding 30-day session with no absolute cap. For a study tool used daily that's a deliberate convenience choice; its compensating control is that admin capability is tied to the email list in configuration and that disabling a user takes effect on the next request.

8. Logout and revocation

Logout must do three things: invalidate the session on the server (delete the store record, or bump the version for signed sessions), clear the cookie in the browser (Set-Cookie with the same name, path and domain and Max-Age=0), and revoke anything derived from the session, such as refresh tokens (au4). For sites with many tabs or subdomains, the Clear-Site-Data: "cookies", "storage" response header asks the browser to wipe the site's cookies and local storage in one go.

Beyond user logout there are four revocation scenarios, and a good design supports all of them: logout everywhere (user-initiated, after losing a device), admin revocation (offboarding an employee, suspending an abuser), event-driven revocation (password reset, MFA change, email change — all should end other sessions), and incident revocation (a bug leaked session tokens; you must kill every session issued in a window). With server-side sessions keep a user → session IDs index for the first three, and an "issued at" field for the last. With signed sessions, a per-user version handles the first three; the fourth needs a global "reject anything issued before T" setting or key rotation.

9. When the session is stolen anyway

Most session theft today isn't guessing or sniffing; it's copying. Infostealer malware on a user's machine reads the browser's cookie database and ships it to the attacker, who imports it into their own browser. Support artefacts leak too: Okta's 2023 breach exposed HAR files that customers had uploaded to support cases, containing live session tokens that were then replayed against customer Okta tenants. Logs, error trackers and analytics tools that capture full request headers are a third source.

Defences, from cheapest to strongest:

  • Limit lifetime — short idle and absolute timeouts for privileged sessions; admin consoles should demand fresh, phishing-resistant authentication often.
  • Detect anomalies — a session that suddenly appears from a new country, ASN or user-agent can be forced to re-authenticate. Treat IP as a signal, not a binding: mobile users change IPs legitimately, and corporate users share them.
  • Step up before sensitive actions, so a stolen session can browse but not change the account's recovery email.
  • Bind the session to the device cryptographically. Chrome's Device Bound Session Credentials (DBSC) register a private key held in the device's TPM (trusted platform module, a tamper-resistant chip) with the site at login; the site then issues short-lived cookies that the browser must keep refreshing by signing a challenge with that key. A copied cookie works only until it expires, minutes later, because the copier can't produce the signature. Google made DBSC generally available in Chrome on Windows with Chrome 146 in 2026, enabled by default for Google accounts; other sites can adopt the same protocol.
  • Keep tokens out of artefacts — redact cookies and Authorization headers from logs and error reports, and tell users (and support staff) to sanitise HAR files, as Okta recommended afterwards.

The revocation–scalability spectrum

Every session design picks a point on a spectrum. At one end, every request checks a central store: revocation is instant, cost is a lookup per request. At the other end, a self-contained signed token is checked locally: zero lookups, revocation only at expiry. In between are the practical designs: signed cookies carrying a version checked against a cacheable per-user value; local caches of session records with a TTL of seconds; short-lived signed tokens refreshed against a store every few minutes (au4's access-and-refresh-token pattern); and push-based revocation, where a revocation event is broadcast to every server's cache. The right point depends on how fast you must revoke (seconds for an admin offboarding, minutes for a user logout) and how much a store lookup costs relative to request latency. Interviewers like the follow-up "what's your revocation latency?" — answer in seconds and say which mechanism gives it.

Same-site is not same-origin

SameSite cookies protect against cross-site requests, where a site is scheme plus registrable domain. Any subdomain of your registrable domain is same-site, so a request from user-content.example.com or a forgotten staging.example.com to app.example.com carries Lax and even Strict cookies. Hosting user-generated content or third-party marketing pages on a subdomain of your main domain therefore weakens CSRF protection, and a subdomain takeover (a dangling DNS record pointing at a deprovisioned cloud resource that an attacker claims) gives an attacker a same-site foothold that can also toss cookies onto the parent domain. Mitigations: host user content on a separate registrable domain (as GitHub does with githubusercontent.com), use __Host- cookies, and add origin-level checks (Origin or Sec-Fetch-Site equal to your exact origin) on top of SameSite.

Session data minimisation

What goes in a session record is a design decision with security consequences. Store identifiers and facts about the authentication event (user ID, tenant, auth_time, amr, device ID), not authorisation results ("is_admin: true") or user profile data. Cached authorisation goes stale: an admin demoted mid-session keeps admin rights until the session ends. The Prep Console follows this: the cookie holds only a uid, and admin status is recomputed from configuration on every request. When you must cache permissions for performance, cache them separately with a short TTL and invalidate them on role changes.

Concurrency limits and session listing

Products for regulated industries often limit concurrent sessions ("at most three devices") and show users their active sessions with device, location and last activity, with a revoke button. Both require a server-side index of sessions per user. Concurrency limits need a policy for the (n+1)th login — reject it, or evict the oldest — and the eviction policy matters: "evict oldest" lets an attacker who logs in kick out the real user, while "reject newest" lets the real user be locked out by an attacker who got in first. Notifying the user on each new session is the safeguard either way.

Why HttpOnly cookies beat tokens in localStorage for browsers

Single-page apps often store access tokens in localStorage and send them in an Authorization header, partly because it sidesteps CSRF. The cost is that any XSS can read localStorage and exfiltrate the token for use from anywhere, for as long as it's valid. An HttpOnly cookie can't be read by script, so XSS is limited to acting within the open page. The modern recommendation for browser apps — the "backend for frontend" (BFF) pattern, covered with OAuth in au5 — is to keep tokens on a server component and give the browser only an HttpOnly, SameSite session cookie, then defend CSRF with the techniques above. That's the architecture this app has: the OAuth tokens from Google or GitHub are used once on the server during login and never reach the browser.

Signing keys for sessions are crown jewels

With signed sessions, whoever holds the signing key can mint a session for any user — including administrators — with no login at all. That makes SECRET_KEY as sensitive as a database root password: generate it from a CSPRNG with at least 256 bits, never commit it, inject it from a secrets store (au11), and plan rotation. itsdangerous supports a list of keys — signing with the newest, verifying with any — so you can rotate without logging everyone out at once; Flask exposes that through SECRET_KEY_FALLBACKS in recent versions. An exposed key requires immediate rotation without fallback, accepting a global logout, because any cookie the attacker minted would otherwise remain valid.

Device binding, in more detail

DBSC's design is worth understanding because it shows how to defeat cookie theft without changing how sites use cookies. At login the server asks the browser to start a bound session; the browser creates a key pair, keeps the private key in the TPM where it can't be exported, and registers the public key with the server. The server then issues cookies with short lifetimes. When one is about to expire, the browser calls a refresh endpoint, signs a server challenge with the TPM key, and receives a fresh cookie. Malware that copies the cookie jar gets cookies that expire within minutes; to keep using the session it would need to use the TPM key on the victim's machine, which raises the cost from "copy a file once" to "maintain live control of the device". It doesn't stop malware that acts in the victim's browser in real time, and it relies on the TPM being present, but it removes the cheap, scalable form of session theft.

Symptoms of session problems

Mass logouts — a spike in login traffic and support tickets — usually mean the session store lost data, a signing key was rotated without fallback, or a cookie attribute change (Domain, Path, name) made browsers send an old cookie the server no longer recognises. Roll out cookie changes by accepting both old and new for a transition period.

Users logged out on some browsers only: SameSite=Strict breaking login links from email, Safari's tracking prevention limiting cookie lifetimes for cookies set via JavaScript, or a third-party embed needing SameSite=None.

Hijacking signals: one session ID used from two distant geographies within minutes; a session's user-agent changing mid-session; sensitive-setting changes shortly after a new-device session appears; admin actions from residential proxies. Cloudflare's detection of the Okta-derived session in 2023 came from exactly this kind of monitoring of admin activity.

Metrics and knobs

Active sessions per user (high counts suggest sharing or abuse); session store latency and error rate; session creation rate (spikes accompany credential stuffing); share of sessions with MFA; time from revocation request to enforcement; idle and absolute timeout values per application tier; re-authentication prompt rate (too high annoys users, too low means step-up isn't protecting much).

Operational hygiene

Redact Cookie, Set-Cookie and Authorization headers in access logs, APM traces and error trackers by default. Teach support teams never to ask for unsanitised HAR files and provide a sanitising tool. Make session revocation a first-class admin feature with an audit trail. Keep a runbook for "session tokens may have leaked": identify the issuance window, revoke sessions issued in it, rotate keys if signed sessions are involved, and force re-authentication for admins.

Testing sessions

Session bugs are easy to test for and rarely tested. A useful automated suite: log in and assert the session cookie carries Secure, HttpOnly, SameSite and the expected prefix; assert the session ID changes across login; log out and replay the old cookie, expecting 401; disable the user and replay, expecting 401; send a state-changing request without the CSRF token or header and with a foreign Origin, expecting 403; wait past (or fake) the idle and absolute timeouts and expect re-authentication. The Prep Console's backend tests exercise several of these paths through Flask's test client, which is the cheapest place to catch a regression — a refactor that drops a cookie flag is invisible in manual testing.

The Okta case, as a timeline

Okta's security post of 20 October 2023 says a threat actor used a stolen credential to access its support case management system and viewed files uploaded by certain customers as part of recent support cases, including HAR files containing cookies and session tokens; Okta revoked the embedded session tokens and notified affected customers. Cloudflare's post says the attacker hijacked a session token from a ticket a Cloudflare employee had created, used it on 18 October with administrative privileges, compromised two employee accounts within its Okta tenant, and was contained; Cloudflare detected it more than a day before Okta's notification. Cloudflare's recommendations — hardware MFA everywhere including at third-party support providers, monitoring for new Okta users and session anomalies, and reviewing session expiry to limit hijacking — map directly onto this topic. The deeper lesson: the most privileged sessions in your company may be sitting in a vendor's support system as debug attachments.

Goal: build and break a signed session cookie in the Flask format with Python 3.12's standard library, then add revocation. About 15 minutes.

  1. Sign. Derive a key like itsdangerous does: key = hmac.new(SECRET, b"cookie-session", "sha1").digest(). Payload: base64url (no padding) of json.dumps({"uid": 12}, separators=(",", ":")). Timestamp: base64url of int(time.time()).to_bytes(4, "big"). Signature: base64url of hmac.new(key, f"{payload}.{ts}".encode(), "sha1").digest(). Join with dots.
  2. Verify. Write load(cookie, max_age) that recomputes the signature, compares with hmac.compare_digest, checks the timestamp is within max_age, and returns the payload.
  3. Tamper. Change the payload to {"uid":1} but keep the signature; confirm load rejects it. Decode the original payload without the key to see that signed isn't secret.
  4. Expire. Forge a timestamp 31 days old (re-signing it) and load with a 30-day max_age: rejected.
  5. Revoke. Add "v": 1 to the payload and keep versions = {12: 1}. Make load reject a cookie whose v is below versions[uid]. "Log out everywhere" by setting versions[12] = 2; the old cookie now fails.
  6. Entropy. Print secrets.token_urlsafe(32) and its length; compute 2**64 / (1e4 * 1e6) / 3.156e7.

What to look for: a valid cookie decodes for anyone but verifies only with the key; changing one character of the payload breaks verification; the stale timestamp fails even with a correct signature; and only step 5's server-side version makes an existing cookie revocable. Step 6 prints 43 characters and about 58 years. If you have this app's SECRET_KEY locally, your step-1 cookie format should match the real prep_session structure (payload, timestamp, signature).

Diagnose: "users stay logged in after we disable them… sometimes"

An internal admin tool uses signed client-side session cookies containing {"uid": 42, "role": "admin"}, valid for 14 days with sliding expiration. When HR offboards an employee, IT sets users.active = false. A security review found an offboarded admin used the tool three days later. The login page also accepts ?next= and ?sid= parameters "for legacy links". List what's wrong and fix it.

Answer

1. Revocation doesn't exist. The server never reads users.active on requests; the signed cookie is self-sufficient for 14 days and slides forward with use. Fix: on every request load the user and reject inactive ones (as this app's load_user does), and add a per-user session version so offboarding and "log out everywhere" invalidate all cookies immediately. For an admin tool, consider server-side sessions outright.

2. Authorisation is cached in the cookie. role: admin stays true after a demotion. Store only the uid; compute role from the database (cached for seconds at most).

3. No absolute timeout. Sliding 14-day expiry means an actively used stolen cookie never dies. Add an absolute cap — hours for an admin tool — and an idle timeout of 15-30 minutes, both checked server-side using timestamps in the signed payload.

4. Session fixation via ?sid=. Accepting session IDs from the URL lets an attacker plant a known session. Remove it, issue a new session at login, and use a __Host- cookie.

5. Open redirect via ?next=. Validate it is a relative path on this site, or attackers chain it into phishing.

6. Step-up. Require fresh MFA (auth_time within 15 minutes) for destructive admin actions, and log them with the session ID hash. Finally, investigate the three days of activity using those logs, and rotate the signing key if there's any chance cookies were minted.
