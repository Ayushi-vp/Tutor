Before OAuth, if a website wanted to read your Gmail contacts to find friends who already used it, it asked for your Gmail password. You typed it in; the site logged in as you, scraped your contacts, and — you hoped — forgot the password. It could equally have read all your email, sent messages as you, or kept the password forever. There was no way to give the site only your contacts, only for now, and no way to take access back short of changing your password everywhere it had been typed.

OAuth exists to fix that. It lets you grant an application a limited, revocable token to do a specific thing on your behalf — "read your contacts", "post to this one calendar" — without the application ever seeing your password. Today it sits behind nearly every "Sign in with Google", every GitHub integration, every app that connects to Slack, and every enterprise API that issues tokens to its partners. It's also behind the sign-in to this app: when you click "Sign in with GitHub", the Prep Console's backend runs an OAuth 2.0 flow and asks GitHub for exactly two scopes, read:user and user:email.

Delegation has its own failure modes. In April 2022 GitHub discovered that an attacker held OAuth tokens that GitHub users had granted to two trusted integrations, Heroku and Travis CI. The tokens had been stolen from those companies, not from GitHub, and they worked exactly as the users had consented — which included reading private repositories. The attacker cloned private code from dozens of organisations, including npm's. Every token was legitimately issued; the protocol worked as designed; the damage came from what a delegated token can do in the wrong hands.

This topic builds OAuth 2.0 from the problem up: the four roles; the authorization code grant as actual HTTP requests, with a PKCE verifier hashed to its challenge by hand; the other grants and when to use each; scopes and consent; the validation rules — state, redirect URIs, client authentication — that turn the protocol from a sketch into something secure; the attacks that the 2025 security best current practice (RFC 9700) closes; and what the long-awaited OAuth 2.1 consolidates, along with its actual status today.

The valet key

Many cars come with a valet key: it starts the engine and opens the driver's door, but not the boot or the glovebox, and some cars limit the speed while it's in use. You give the valet that key, not your main key. That's the core idea of OAuth: instead of handing over your master credential (the password), you hand over a limited one (an access token) that does only what's needed and can be cancelled.

The analogy needs one extension to be accurate. In OAuth you don't cut the valet key yourself; a trusted locksmith does it, after checking you're the car's owner and asking you exactly which doors to allow. The valet never meets the locksmith's check of your identity; they just receive the limited key.

Map that onto OAuth's four roles:

  • Resource owner — you, who own the data (the car).
  • Client — the application that wants access (the valet): a photo-printing website, a CI service, a mobile app.
  • Authorisation server (AS) — the trusted locksmith: it logs you in, shows you what the client is asking for, gets your consent, and issues tokens. Google, GitHub, Okta, Microsoft Entra ID, or your company's own.
  • Resource server (RS) — the API holding the data (the car): Google Photos API, GitHub API. It accepts access tokens and enforces what they allow.

The shape of every flow

All the variations you'll meet share one shape. First the client asks the authorisation server for permission, naming what it wants (scopes) and where to send the answer (a redirect URI). Then the authorisation server deals with the user directly — login, consent — so the client never touches their credential. Then the authorisation server hands back something the client can turn into a token, through a path that only the genuine client can complete. Finally the client uses the token at the resource server until it expires, and uses a refresh token, if it has one, to get another. Most of the security rules in this topic exist to protect the third step: making sure that "something" can't be redirected, intercepted, replayed or injected on its way back.

What OAuth is not

OAuth 2.0 is about authorisation — getting a token to call an API. It is not, by itself, a login protocol. The access token is addressed to the resource server, and nothing in OAuth 2.0 tells the client, in a standard and verifiable way, who the user is. Sites that implemented "log in with X" by fetching a token and calling some profile endpoint have been tricked into logging attackers in as victims. The standard authentication layer on top of OAuth is OpenID Connect, which adds a signed ID token addressed to the client — au6's subject. You'll see that this app uses OpenID Connect with Google and plain OAuth plus GitHub's profile API with GitHub, and why that difference matters.

If you stop here: OAuth hands a client a limited token instead of a password, through a trusted authorisation server, after the user consents. The rest of this topic is the precise choreography that keeps that token from ending up with anyone else.

1. The authorization code grant, as HTTP

OAuth defines several grants — ways for a client to obtain a token. The one that matters most is the authorization code grant, used whenever a user is present. It has two halves: a front channel through the user's browser (redirects), and a back channel directly from the client to the authorisation server. Here it is end to end, with PKCE, for a printing site at https://print.example using an authorisation server at https://as.example.

Step 0 — registration (once). The client is registered with the AS and receives a client_id (public identifier, here print-app) and, if it's a confidential client, a way to authenticate (a client secret or a private key). It registers its exact redirect URI: https://print.example/oauth/callback.

Step 1 — the client prepares. It generates three random values and stores them in the user's session: state (for CSRF), a PKCE code_verifier, and — for OpenID Connect only — a nonce. It computes the PKCE code_challenge from the verifier (section 2 does this by hand).

Step 2 — redirect to the authorisation endpoint. The client responds to the user's click with a redirect:

HTTP/1.1 302 Found
Location: https://as.example/authorize?response_type=code
  &client_id=print-app
  &redirect_uri=https%3A%2F%2Fprint.example%2Foauth%2Fcallback
  &scope=photos.read
  &state=af0ifjsldkj
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256

Step 3 — the user authenticates and consents. The browser follows the redirect. The AS logs the user in (password, passkey, SSO — the client sees none of it), checks the redirect URI exactly matches the registered one, and shows a consent screen: "Print.example wants to view your photos." The user approves.

Step 4 — redirect back with a code. The AS records the code with the client ID, redirect URI, user, scopes and code challenge, and redirects:

HTTP/1.1 302 Found
Location: https://print.example/oauth/callback?code=SplxlOBeZQQYbYS6WxSbIA
  &state=af0ifjsldkj&iss=https%3A%2F%2Fas.example

The code is short-lived (RFC 6749 recommends at most 10 minutes; most servers use well under one) and single-use. The iss parameter (RFC 9207) names the AS that issued it — section 6 explains why.

Step 5 — the client checks state. The callback compares state with the value in the user's session and rejects the request if they differ or if there's no flow in progress.

Step 6 — exchange the code (back channel). The client's server calls the token endpoint directly over TLS:

POST /token HTTP/1.1
Host: as.example
Content-Type: application/x-www-form-urlencoded
Authorization: Basic cHJpbnQtYXBwOnMzY3JldA==        (client_id:client_secret)

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fprint.example%2Foauth%2Fcallback
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

The AS authenticates the client, looks up the code, checks it's unused, unexpired, issued to this client, for this redirect URI, and that SHA-256 of the verifier matches the stored challenge. Then:

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{"access_token":"2YotnFZFEjr1zCsicMWpAA","token_type":"Bearer",
 "expires_in":3600,"refresh_token":"tGzv3JOkF0XG5Qx2TlKWIA","scope":"photos.read"}

Step 7 — call the API. GET https://photos.example/v1/albums with Authorization: Bearer 2YotnFZFEjr1zCsicMWpAA.

2. PKCE, computed by hand

PKCE (Proof Key for Code Exchange, RFC 7636, pronounced "pixy") was designed for apps that can't keep a client secret — a mobile app's secret can be extracted from its binary. Without it, anyone who intercepts the code can redeem it: on a phone, a malicious app can register the same custom URL scheme (printapp://callback) and receive the redirect. PKCE makes the code redeemable only by the instance that started the flow, by using a one-time secret created per flow.

The code_verifier is a high-entropy random string of 43-128 characters from the unreserved URL alphabet. The usual recipe is 32 random bytes, base64url-encoded, giving 43 characters. RFC 7636's Appendix B uses these 32 bytes:

[116, 24, 223, 180, 151, 153, 224, 37, 79, 250, 96, 125, 216, 173, 187, 186,
 22, 212, 37, 77, 105, 214, 191, 240, 91, 88, 5, 88, 83, 132, 141, 121]
→ code_verifier = dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

With method S256, the code_challenge is base64url(SHA-256(ASCII(code_verifier))). Note that it hashes the 43 ASCII characters of the verifier, not the original 32 bytes. SHA-256 of those 43 bytes is:

13d31e961a1ad8ec2f16b10c4c982e0876a878ad6df144566ee1894acb70f9c3
= [19, 211, 30, 150, 26, 26, 216, 236, 47, 22, 177, 12, ...]

Base64url-encode the 32-byte digest. Take the first three bytes, 19, 211, 30: in bits 00010011 11010011 00011110; regroup into sixes 000100 111101 001100 011110 = 4, 61, 12, 30; in the base64url alphabet that's E, 9, M, e. Continuing over all 32 bytes and dropping the padding gives the 43-character challenge:

code_challenge = E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM

The challenge goes out in step 2 through the browser, where anyone might see it — which is fine, because SHA-256 can't be inverted to find the verifier. The verifier goes out only in step 6, on the back channel. An attacker who intercepted the code in step 4 doesn't have the verifier; the AS hashes whatever they send, gets a mismatch, and refuses. The weaker method plain sets the challenge equal to the verifier and should only be used if a client truly can't compute SHA-256.

PKCE turned out to be useful well beyond mobile apps. It also defeats authorization code injection, where an attacker plants a stolen code into a legitimate client's callback in the attacker's own browser session: the client redeems it with the verifier from the attacker's session, which doesn't match. That's why RFC 9700 requires PKCE for public clients and recommends it for confidential ones too.

3. The other grants

Client credentials. No user: a service gets a token for itself.

POST /token
Authorization: Basic <client_id:secret>     (or a signed client assertion)
grant_type=client_credentials&scope=invoices.read

The token represents the client, so authorisation is about what that client may do. Use it for backend jobs, service-to-service calls across organisations, and partner integrations that act as themselves. au10 discusses replacing the shared secret with workload identity.

Device authorization grant (RFC 8628). For devices without a usable browser or keyboard — TVs, CLIs on remote servers, IoT. The device requests a code; the AS returns a device_code, a short user_code like WDJB-MJHT and a verification_uri. The device displays "Go to example.com/device and enter WDJB-MJHT" and polls the token endpoint every few seconds with the device code. The user approves on their phone; the next poll returns tokens. Its risk is phishing: the flow is designed so the person approving isn't on the device, so an attacker can start a flow and persuade a victim to enter the code. Consent screens must name the device and client clearly.

Refresh token grant. grant_type=refresh_token&refresh_token=… returns a new access token (and, with rotation, a new refresh token, as in au4).

Deprecated grants. The implicit grant returned the access token directly in the redirect's URL fragment (#access_token=…), designed in 2012 for browser apps that couldn't make cross-origin token requests. It put tokens in browser history and within reach of any script, couldn't use refresh tokens safely, and couldn't bind the token to the client. RFC 9700 says clients SHOULD NOT use it. The resource owner password credentials (ROPC) grant had the client collect the user's password and send it to the token endpoint — exactly the anti-pattern OAuth exists to remove — and RFC 9700 says it MUST NOT be used. Single-page apps now use the authorization code grant with PKCE.

SituationGrant
Server-side web app, user presentAuthorization code + PKCE, confidential client
Single-page appAuthorization code + PKCE (ideally via a backend-for-frontend)
Mobile / desktop appAuthorization code + PKCE via the system browser (RFC 8252)
TV, CLI, IoTDevice authorization grant
Service acting as itselfClient credentials
Keep a session goingRefresh token (rotated for public clients)

4. Scopes and consent

A scope is a string naming a permission the client requests: photos.read, repo, read:user. The AS shows requested scopes on the consent screen, may let the user deselect some, and records the granted set in the token (the response's scope field says what was actually granted, which may be less than requested — clients must check). Resource servers then refuse operations outside the token's scopes.

Two design points matter in interviews. First, scopes are coarse capabilities of the client, not a full authorisation model. A token with repo lets the client do repository things as this user; whether this user may touch a given repository is still the resource server's per-object decision (au8). Second, scope design is product design: too broad (repo grants full read/write to all public and private repositories) and every integration becomes a skeleton key, which is exactly what made the 2022 Heroku and Travis CI token theft damaging; too fine and consent screens become unreadable. Providers move towards fine-grained, resource-limited grants — GitHub's fine-grained personal access tokens and GitHub Apps, for example, can be limited to specific repositories.

This app requests read:user user:email from GitHub — enough to read the profile and the list of email addresses with their verified flags — and openid email profile from Google. Neither grants access to repositories or mail. Minimal scopes are the cheapest blast-radius control there is.

5. Client types and client authentication

RFC 6749 distinguishes confidential clients, which can keep a credential secret (a server-side web app), from public clients, which can't (a mobile app, a single-page app, a CLI distributed to users). Confidential clients authenticate at the token endpoint. Options, from weakest to strongest:

  • Client secret via HTTP Basic or a form field. Simple; the secret is a long-lived shared password that leaks like any other (au11).
  • private_key_jwt: the client signs a short-lived JWT assertion with its private key; the AS verifies with the registered public key. No shared secret ever crosses the wire.
  • mTLS client authentication (RFC 8705): the client presents a certificate in the TLS handshake (net9), and the token can be bound to it.

Public clients have no credential, which is why PKCE matters so much for them: it's the only thing proving the redeemer started the flow.

6. The validation rules that make it secure

OAuth's security lives in a handful of checks. RFC 9700, the OAuth 2.0 Security Best Current Practice published in January 2025, collects them.

Exact redirect URI matching. The AS compares the requested redirect URI with the registered ones by exact string comparison. History shows why: allowing https://print.example/* lets an attacker pick https://print.example/redirect?to=evil.example if the site has any open redirector, and the browser carries the code onward (the Referer header or the redirect itself delivers it). Wildcard subdomains fail the same way when any subdomain can be taken over. The single exception is the port of loopback redirects (http://127.0.0.1:{any port}/callback) used by native and CLI apps, which bind a random free port.

CSRF protection on the callback. Without it, an attacker can start a flow with their own account, stop before the callback, and trick the victim's browser into loading callback?code=ATTACKERS_CODE. The victim is now logged in as the attacker (login CSRF), or has linked the attacker's cloud storage to their account and uploads files into it. The state parameter, bound to the user's session, prevents this; PKCE does too, because the attacker's code was issued against the attacker's challenge.

Short-lived, single-use codes. If a code is presented twice, the AS should refuse and SHOULD revoke tokens already issued from it — the second use means someone else has it.

Mix-up defence. A client that works with several authorisation servers can be confused by an attacker-controlled one into sending a code from the honest AS to the attacker's token endpoint. The iss parameter in the authorisation response (RFC 9207) lets the client check the response came from the AS it sent the user to. Distinct redirect URIs per AS help too.

No tokens in URLs. Access tokens must not be sent in query strings, where they end up in logs and referrers — use the Authorization header.

Audience-restricted, least-privilege tokens. Tokens should name the resource server they're for (resource indicators, RFC 8707) and carry only needed scopes, so a token leaked from one API can't be replayed at another.

Refresh token protection for public clients. Either sender-constrain them (DPoP, mTLS) or rotate them with reuse detection (au4).

Pushed Authorization Requests (PAR, RFC 9126) go further for high-value clients: instead of putting parameters in the browser redirect, where they can be read or altered, the client POSTs them directly to the AS and receives a short-lived request_uri reference to put in the redirect. Financial-grade profiles (FAPI) require it.

7. OAuth 2.1: what it consolidates, and its status

OAuth 2.0 (RFC 6749) dates from 2012; a decade of fixes lives in separate documents. OAuth 2.1 folds them into one specification without adding new mechanisms: PKCE required for the authorization code grant; implicit and ROPC grants removed; exact redirect URI matching; bearer tokens not allowed in query strings; refresh tokens for public clients sender-constrained or one-time use; and the guidance of RFC 9700, RFC 8252 (native apps) and the browser-apps best practice incorporated.

Its status needs saying precisely, because it has been "nearly done" for years. As of this writing (October 2026), the latest version is draft-ietf-oauth-v2-1-16, dated 3 September 2026: an active Internet-Draft of the IETF OAuth working group, not an RFC, with a working-group milestone of December 2026 to submit it to the IESG (the body that approves documents for publication). Check the datatracker for later news. The practical point for interviews: you don't need to wait for it. Every OAuth 2.1 requirement already exists in published RFCs, and building to the 2.1 rules today is simply building to RFC 9700. Specifications that adopted it early — the Model Context Protocol's authorisation rules for remote servers (ag4) are written against OAuth 2.1 — rely on that.

8. This app's flow, line by line

The Prep Console is a confidential OAuth client of Google and GitHub, using the Authlib library (version 1.8 in its environment) with Flask:

  • Registration. At startup, if GOOGLE_CLIENT_ID is set, it registers Google with server_metadata_url pointing at Google's OpenID Connect discovery document and scope openid email profile. If GITHUB_CLIENT_ID is set, it registers GitHub with explicit authorize and token URLs and scope read:user user:email. Secrets come from environment variables.
  • Start. GET /auth/login/<provider> calls authorize_redirect(redirect_uri), where the redirect URI is BASE_URL + "/auth/callback/<provider>", or the request's own host if BASE_URL isn't set. Authlib generates state and, because Google's scope includes openid, a nonce; it saves them in the Flask session and returns the 302.
  • Callback. GET /auth/callback/<provider> calls authorize_access_token(). Authlib reads code and state, loads and clears the saved state data (a mismatch raises an error), exchanges the code at the token endpoint authenticating with the client secret, and for Google parses and validates the ID token against the saved nonce. Any exception — denied consent, state mismatch, expired code — is logged and the user is sent to /?auth=failed.
  • Identity. For Google, the app requires email_verified in the ID token's claims. For GitHub, which isn't used as an OpenID Connect provider here, it calls GET /user and GET /user/emails with the access token and accepts only an email that is both primary and verified.

Two honest observations. PKCE isn't configured — Authlib only adds it when the client registration sets code_challenge_method — so the flow relies on the client secret plus state. That matches RFC 9700's rules for a confidential client (PKCE is recommended, not required, for them), and adding code_challenge_method: "S256" to the client options would be a one-line hardening. And redirect URI exactness is enforced on the providers' side: if the app ever built a redirect URI from a forged Host header (only possible without BASE_URL), Google and GitHub would refuse it as unregistered — the registered-URI check is what makes that safe.

Why the back channel exists

The browser is a shared, observable channel: URLs go into history, server logs, analytics, browser extensions, and Referer headers to third parties. Everything that passes through redirects should be assumed visible to someone. OAuth's design therefore puts only short-lived, single-use, bound artefacts on the front channel (the code, state, the challenge) and keeps bearer credentials (tokens) on the back channel, where the client and AS talk directly over TLS and the client can authenticate. Every deprecated pattern — implicit grant, tokens in query strings, ROPC — violates that split. When you evaluate any new auth flow, ask which artefacts cross which channel and what an observer of the front channel could do with them.

Consent phishing and malicious OAuth apps

Because OAuth is legitimate delegation, attackers increasingly don't steal credentials at all; they get users to grant a malicious application access. A phishing email links to a real Microsoft or Google consent screen for an app named "Document Viewer" requesting mail read access; the user approves; the attacker's app now has a token that survives password changes and MFA. Defences live at the AS and the organisation: admin consent requirements for high-risk scopes, publisher verification, restricting which apps users may consent to, and monitoring new grants. In January 2024 Microsoft reported that the actor it calls Midnight Blizzard got in through a password-sprayed legacy test account, then abused a legacy test OAuth application that had elevated access to Microsoft's corporate environment to grant mail access to applications it created, and read senior leaders' mailboxes — an example of OAuth applications themselves being the privileged identity worth attacking.

Tokens are the user's consent, frozen

A delegated token keeps working when the user changes their password, unless the provider ties token lifetime to credential changes, and a refresh token can keep minting access tokens for months. That's the property the 2022 GitHub incident exploited: tokens users had granted to Heroku and Travis CI, stolen from those companies, still carried full repository access. Senior designs bound this: refresh tokens with absolute lifetimes, revocation on password reset and security events, user-visible lists of authorised apps with one-click revoke, provider-side anomaly detection per client, and integrator-side storage of tokens encrypted with keys in a KMS.

Native apps and redirect capture

Mobile apps receive the redirect through one of three mechanisms (RFC 8252): a private-use URI scheme (com.example.app:/callback), a claimed HTTPS URL (Android App Links, iOS Universal Links, verified by a file on the domain) or a loopback IP redirect for desktop apps. Private-use schemes can be claimed by any app, which is exactly why PKCE exists. Claimed HTTPS links are verified to belong to the app, closing that gap. RFC 8252 also requires an external user agent (the system browser or an in-app browser tab such as ASWebAuthenticationSession or Custom Tabs), never an embedded web view: an embedded view lets the app read what the user types — including their password — and doesn't share the browser's existing sessions, so users can't tell a legitimate login from credential theft.

Browser-based apps and the BFF

A single-page app is a public client running in the most hostile environment there is. Even with PKCE, its tokens live in JavaScript-accessible memory, and any XSS can use or exfiltrate them. The IETF's browser-apps guidance ranks architectures: best is a backend-for-frontend that acts as a confidential client and holds tokens server-side, with the browser holding only an HttpOnly session cookie (au3); next is a token-mediating backend that obtains tokens but hands short-lived access tokens to the browser; last is a pure browser client with PKCE, rotating refresh tokens and ideally DPoP. This app is, in effect, the first: the OAuth flow and tokens stay in the Flask backend, and the browser only ever sees its session cookie.

Authorisation server metadata and discovery

Clients need to know an AS's endpoints, supported grants, PKCE methods and signing keys. RFC 8414 standardises a metadata document at /.well-known/oauth-authorization-server; OpenID Connect's discovery document (/.well-known/openid-configuration) is the older, widely used equivalent. Using metadata rather than hard-coding URLs makes key rotation and endpoint changes painless and enables the iss check against mix-up. Protected resource metadata (RFC 9728) lets an API tell clients which authorisation servers it accepts — the mechanism MCP's auth uses for remote servers, which au12 revisits.

Rich authorisation requests

Scopes are strings, which is too coarse for "pay €45.00 to this IBAN, once". RFC 9396 (Rich Authorization Requests) adds an authorization_details JSON parameter that can describe structured, specific grants, shown on the consent screen and recorded in the token. It's used in open banking and is a natural fit for agents acting on a user's behalf with tightly bounded permissions (au12).

Failure modes in real deployments

redirect_uri mismatch errors after a deployment: the app's computed redirect URI changed (new domain, trailing slash, http vs https behind a proxy) and no longer exactly matches the registered one. This is why the Prep Console builds it from an explicit BASE_URL when deployed behind a proxy, and uses ProxyFix so the scheme and host it sees match what the user sees.

"Invalid state" / CSRF errors: the session cookie carrying state didn't survive the round trip — SameSite=Strict on the session cookie (the return from the AS is a cross-site navigation, so Lax is needed), a different hostname for start and callback, or multiple tabs starting flows that overwrite each other's state. Authlib keys saved state by the state value itself, which tolerates parallel flows.

Clock skew breaking ID-token or client-assertion validation (au4).

Token endpoint outages blocking logins and refreshes for every client; access tokens already issued keep working until expiry, so refresh traffic is the load to plan for.

Over-broad scopes accumulating as product teams add features; periodic scope reviews and incremental authorisation (ask for more only when the feature is used) keep integrations least-privilege.

What to monitor as an authorisation server operator

Grants per client per day; consent rates; failed token exchanges by reason (invalid code, PKCE mismatch, redirect mismatch, client auth failure — a spike in PKCE mismatches can indicate code-injection attempts); code reuse events; refresh-token reuse; API call patterns per client (sudden enumeration of organisations or bulk cloning, as in 2022); new third-party apps gaining many users quickly (possible consent phishing).

The 2022 GitHub incident, read as an engineer

GitHub's security alert says it identified on 12 April 2022 an attacker using stolen OAuth user tokens issued to two third-party integrators, Heroku (several Heroku Dashboard client IDs) and Travis CI. The attacker authenticated to the GitHub API with those tokens, listed victims' organisations, chose targets and cloned private repositories. The intrusion was discovered because the attacker used an AWS API key, found in a private npm repository cloned this way, to access npm's production infrastructure. GitHub stated the tokens were not stolen from GitHub — it doesn't store them in usable form — and revoked tokens associated with the affected applications, notifying users and the integrators. The engineering lessons: delegated tokens are high-value secrets at every integrator, not just at the provider; broad, long-lived scopes multiply blast radius; and API usage anomalies per client are a provider's best early-warning signal.

Testing an OAuth integration

Before launch, run a short adversarial checklist against your own client and server: change one character of the redirect URI (expect rejection); replay a code (expect rejection and revocation); redeem a code with the wrong verifier and with none (expect rejection); load the callback with a code from another session (expect a state error); drop state entirely; request scopes you never registered; and confirm tokens never appear in URLs, logs or the browser. Each test corresponds to a published attack class, and most take minutes with a scripted HTTP client.

Build or buy

Running an authorisation server is a security product in itself: key management, consent UX, client registration, abuse monitoring, and the long tail of RFCs. Most teams should use a managed provider or a mature open-source server (Keycloak, Ory Hydra, Authentik and others) and spend their effort on scope design, client policies and monitoring. As a client, use a maintained library (Authlib, as this app does) rather than hand-rolling the redirect and state handling.

Goal: compute a PKCE challenge, build an authorisation request, and simulate an authorisation server that enforces PKCE, state and exact redirect matching — Python 3.12 standard library only. About 15 minutes.

  1. Reproduce RFC 7636. Encode the 32 bytes from Appendix B with base64url (no padding) — you should get dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk. Hash its ASCII with hashlib.sha256, base64url the digest: E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM.
  2. Fresh values. Write new_flow() returning state = secrets.token_urlsafe(16), a verifier from secrets.token_urlsafe(32) and its challenge. Build the authorisation URL with urllib.parse.urlencode.
  3. Toy AS. Write authorize(params) that checks redirect_uri against a registered list by exact string equality, then stores {code: (client_id, redirect_uri, challenge, expires, used)} and returns redirect_uri?code=…&state=….
  4. Token endpoint. Write token(form) that rejects unknown, expired or used codes, mismatched redirect URIs, and verifiers whose S256 hash doesn't match; on success marks the code used and returns a random access token.
  5. Attacks. (a) Request https://print.example/oauth/callback/../evil and https://print.example.evil.com/cb as redirect URIs — both rejected. (b) "Intercept" a code and redeem it with a different verifier — rejected. (c) Redeem a valid code twice — second attempt rejected. (d) Make the client's callback check state against its session and feed it a code with a different state — rejected.

What to look for: step 1 matches the RFC's values exactly, proving the challenge is computed over the verifier's ASCII. Every attack in step 5 fails at a different check — redirect matching, PKCE, single use, state — and each corresponds to a real attack class in RFC 9700. Notice that an observer of every URL in steps 2-3 sees the challenge and code but never the verifier.

Review: a partner integration platform's OAuth setup

Your company exposes a REST API to partners. The OAuth setup today: partners register any redirect URI prefix (https://partner.com/); the authorisation server supports implicit, password and authorization code grants; codes live 30 minutes and can be redeemed more than once; one scope, api, grants everything; refresh tokens never expire; partners authenticate with client secrets emailed to them. A partner reports a customer saw unexpected API activity. What do you change, in what order?

Answer

Contain first. Look up the affected customer's grants: which clients hold tokens, when issued, which API calls were made. Revoke the suspicious grants and tokens; rotate that partner's client secret.

1. Redirect URIs (highest risk). Prefix matching lets an attacker use any open redirector or attacker-influenced page on partner.com to receive codes or implicit-grant tokens. Require exact registered URIs; migrate partners by collecting their current callback URLs from logs.

2. Kill the implicit and password grants. Implicit puts tokens in URL fragments; password grant hands customers' passwords to partners. Move every partner to authorization code + PKCE. Announce a deadline; monitor usage to find stragglers.

3. Codes. Single use, revoking tokens issued from a reused code; lifetime under a minute; require PKCE and the iss response parameter.

4. Scopes. Split api into resource-and-action scopes (orders.read, orders.write, customers.read), with incremental consent; existing grants keep api until re-consent, then expire.

5. Token lifetimes. Access tokens 15-60 minutes; refresh tokens with rotation and reuse detection, absolute lifetime (say 90 days) and revocation on customer password reset. Give customers a page listing authorised partners with a revoke button.

6. Client authentication. Replace emailed secrets with private_key_jwt (partners register a public key) or mTLS; at minimum, secrets delivered through a portal, shown once, rotatable.

7. Detection. Per-client anomaly detection on API usage (volume, breadth of customers touched, new IP ranges), alerts on code and refresh-token reuse.
