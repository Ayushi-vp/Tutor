In June 2023 the identity company Descope published a finding it called nOAuth. Microsoft's identity platform (then Azure AD, now Entra ID) let a user set the email address on their own account without proving they owned it, and put that address in the email claim of the tokens it issued. Plenty of applications had added "Log in with Microsoft", and many of them did the obvious thing on first login: if a user with that email already exists, sign them into that account. So an attacker could create a Microsoft account, set its email to the victim's address, click "Log in with Microsoft" on a vulnerable app, and land in the victim's account — even if the victim had never used Microsoft at all. Descope found it in apps used by millions.

In January 2025 Truffle Security showed a different route to the same place. When a startup fails, its domain eventually lapses. Buy it, create Google Workspace accounts for the old addresses — hr@startup.com, alice@startup.com — and click "Sign in with Google" on the SaaS tools the startup used. Google honestly asserts a verified email; tools that key users on email let the new owner in. Truffle reported logging into Slack, Notion, Zoom and an HR system holding Social Security numbers this way, and estimated over 100,000 such domains were for sale.

Neither is a cryptographic failure. The tokens were genuine and correctly signed. Both are failures of the part of single sign-on that lives in your application: deciding which local account a federated identity belongs to. That decision, plus validating the identity statement correctly, is what this topic is about.

We'll see why OAuth alone isn't a login protocol and what OpenID Connect adds; take an ID token apart and validate it step by step, computing the at_hash binding by hand; use Google's live discovery document and key set to see rotation in action; look at SAML, still the backbone of enterprise SSO, and the signature-wrapping bugs that keep recurring in it; design SSO for a multi-tenant business product; and finish with account linking and logout. The worked example throughout is this app's own sign-in, which uses Google as an OpenID provider, GitHub as a plain OAuth provider, and links both to an invite list by verified email — a design with exactly the trade-offs the stories above illustrate.

Passport control vs the valet key

au5's analogy for OAuth was a valet key: a limited key that lets someone do a job on your behalf. A valet key tells the car nothing about who is holding it. If a hotel wanted to know who you are, being handed your valet key would be a poor way to find out — anyone could have been given one.

Authentication needs a different document: a passport. A passport is issued by an authority both sides trust, states who you are, is addressed to "whom it may concern" at border control, has a validity period and is hard to forge. OpenID Connect adds exactly that to OAuth: alongside the access token (the valet key, for APIs), the authorisation server issues an ID token (the passport, for your application). The ID token says "this is user 1094… at Google, who authenticated at 09:14 using a password and a security key, and this statement is for application prep-console, in answer to request n-0S6_WzA2Mj".

Where the analogy breaks: a real passport is reused at many borders, while an ID token is single-purpose — addressed to one application and bound to one login request. Showing someone else's ID token to a different application, or replaying an old one, must fail. Most of ID token validation exists to enforce that.

What changes for your application

Federation changes what your application is responsible for. It no longer stores passwords, runs MFA or handles password resets — the IdP does. It still validates the identity statement it receives (a short list of checks you must get exactly right), decides which local account that identity maps to, decides whether that person may join this tenant at all, issues and manages its own session, and copes when the IdP is unavailable or the user loses access to it. The first two are where nearly every federated-login vulnerability in this topic lives; the IdP's cryptography is rarely the weak point.

The words

OpenID Connect (OIDC) is a thin identity layer on top of OAuth 2.0, published by the OpenID Foundation. In OIDC vocabulary, the authorisation server is an OpenID provider (OP) — in everyday speech, the identity provider (IdP) — and the client application is the relying party (RP), because it relies on the provider's statement. A client asks for authentication by including the scope openid in an ordinary authorization code request (au5); the token response then contains an id_token next to the access_token.

Single sign-on (SSO) is what you get when many applications rely on the same IdP: the user authenticates once at the IdP and then each application gets its own statement of identity without a new password prompt. "Sign in with Google" is consumer SSO. Corporate SSO — every employee app trusts the company's Okta or Entra ID — is the enterprise version, and there the dominant protocol is often SAML rather than OIDC.

If you stop here: OIDC gives your app a signed passport (ID token) for the user, addressed to your app and bound to your login request. Validate it carefully, identify the user by the issuer plus the subject identifier inside it, and be very careful about what you treat as "the same person".

1. Why an access token isn't a login

Suppose an app implements "Log in with Provider" using plain OAuth: it gets an access token through the code flow, calls the provider's profile API with it, and logs in whoever the profile says. With the authorization code flow and a correct state check, that can be safe, because the app itself just obtained the token for this browser session. But many early implementations — especially mobile apps and those using the implicit grant — accepted an access token handed to them by the client side. An attacker who runs any app that the victim logs into with the same provider receives an access token for the victim, and can present it to the vulnerable app as "proof" of login. This is token substitution: the access token was never addressed to the vulnerable app, and nothing in it says so.

OpenID Connect fixes this by issuing a token that is addressed to the client — the ID token, with aud equal to the client's client_id — and bound to the specific login request by a nonce. The rule that follows is simple: authenticate users from a validated ID token (or, if the provider doesn't speak OIDC, from an API call made with a token your own back channel just obtained in a flow protected by state). The Prep Console uses both patterns: Google as an OpenID provider, GitHub through its REST API after its own code exchange.

2. The ID token, claim by claim

An ID token is a JWT (au4). A typical Google ID token payload looks like this (illustrative values):

{
  "iss": "https://accounts.google.com",
  "azp": "1234-abc.apps.googleusercontent.com",
  "aud": "1234-abc.apps.googleusercontent.com",
  "sub": "109486733219834471235",
  "email": "ada@example.com",
  "email_verified": true,
  "at_hash": "bJYTDxMKsNbRWDl-JNK8wQ",
  "nonce": "n-0S6_WzA2Mj",
  "name": "Ada Lovelace",
  "iat": 1791360000,
  "exp": 1791363600
}
  • iss (issuer) — who made the statement. Must exactly match the provider's issuer from configuration.
  • sub (subject) — the provider's stable, unique identifier for the user, never reassigned within that issuer. The pair (iss, sub) is the only identifier OIDC guarantees.
  • aud (audience) — the client ID(s) the token is for. azp (authorised party) names the client the token was issued to when there are several audiences.
  • exp, iat — expiry and issue time. Optional auth_time says when the user actually authenticated (which may be earlier, if the IdP reused its session).
  • nonce — the random value the client sent in the authorisation request.
  • at_hash — a hash of the access token returned with it (section 3).
  • acr and amr — how strongly and by what methods the user authenticated (for example amr: ["pwd", "hwk"], password plus hardware key), used for step-up decisions (au1).
  • Profile claims such as email, email_verified, name, picture — useful attributes, but attributes, not identifiers.

3. Validating an ID token, step by step

OIDC Core gives the validation rules. For a token from the authorization code flow:

  1. Algorithm and key. Accept only algorithms the provider advertises (Google's discovery document lists exactly RS256). Fetch keys from the provider's jwks_uri, choose by kid, verify the signature (au4's checklist applies in full).
  2. Issuer. iss must exactly equal the issuer in the provider's metadata.
  3. Audience. aud must contain your client_id; if it has more than one value, azp must be your client_id. This is the check that kills token substitution.
  4. Time. exp in the future and iat recent, with a small leeway for clock skew. If you requested max_age, check auth_time.
  5. Nonce. Equal to the value stored in this user's session when the flow started; then delete it, so the token can't be replayed.
  6. at_hash. If an access token came in the same response, recompute and compare.
  7. Your own rules, such as requiring email_verified, a hosted-domain claim for workforce logins, or a minimum acr.

at_hash by hand. The rule: hash the ASCII of the access token with the hash function matching the ID token's algorithm (SHA-256 for RS256), take the left-most half of the bytes, and base64url-encode. For the access token 2YotnFZFEjr1zCsicMWpAA:

SHA-256("2YotnFZFEjr1zCsicMWpAA") = 6c96130f130ab0d6d158397e24d2bcc1 c9a5e73ae081f6e983f1c7b545d24a4c
left 16 bytes                     = 6c96130f130ab0d6d158397e24d2bcc1
base64url, no padding             = bJYTDxMKsNbRWDl-JNK8wQ

If the ID token's at_hash is bJYTDxMKsNbRWDl-JNK8wQ, the access token and ID token came from the same response; an attacker can't swap in a different access token (for example one for their own account) without breaking the signed ID token.

How this app does it. Authlib, which the Prep Console uses, performs these checks in its parse_id_token when authorize_access_token() sees an ID token and a stored nonce. Reading its source (version 1.8): it limits algorithms to the discovery document's id_token_signing_alg_values_supported; builds the key set from the provider's JWKS and, on an unknown kid, refetches the JWKS once with force=True — exactly the rotation behaviour au4 recommended; sets the expected iss from the metadata; validates aud against the app's client ID, the nonce, and at_hash (because an access token is present); and allows 120 seconds of clock leeway. The app's own rule follows: if not info.get("email_verified"): return _finish("unverified").

4. Discovery and JWKS, live

An OpenID provider publishes a discovery document at {issuer}/.well-known/openid-configuration. Fetching Google's while writing this lesson returned, among other fields:

"issuer": "https://accounts.google.com",
"authorization_endpoint": "https://accounts.google.com/o/oauth2/v2/auth",
"token_endpoint": "https://oauth2.googleapis.com/token",
"userinfo_endpoint": "https://openidconnect.googleapis.com/v1/userinfo",
"jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
"id_token_signing_alg_values_supported": ["RS256"],
"code_challenge_methods_supported": ["plain", "S256"]

and the jwks_uri listed two RSA keys with different kids, both RS256. Two keys at once is rotation in progress: Google publishes the next key before using it and keeps the previous one until its tokens expire, so any client that refetches on an unknown kid never notices. The Prep Console registers Google with just server_metadata_url pointing at that document; everything else — endpoints, algorithms, keys — is discovered.

The userinfo endpoint returns the same profile claims when called with the access token. It's useful when the ID token is kept small, but its response isn't signed by default, so treat it as a profile lookup and take identity from the validated ID token's sub.

5. Hybrid flows, briefly

OIDC also defines response types that return an ID token directly from the authorisation endpoint, through the browser (code id_token, the "hybrid" flow), so the client can validate identity before redeeming the code; and an implicit id_token response type. These use c_hash (a hash of the code, like at_hash) to bind front-channel artefacts. In current practice the plain authorization code flow with PKCE is preferred for nearly everything; you'll mostly meet hybrid flows in older enterprise integrations and in financial-grade profiles.

6. SAML in one page

SAML 2.0 (Security Assertion Markup Language, an OASIS standard from 2005) predates OIDC and still dominates enterprise SSO between corporate IdPs (Okta, Entra ID, ADFS, Ping) and SaaS apps. Its vocabulary: the IdP; the service provider (SP), which is your application; and the assertion, a signed XML document about the user.

An SP-initiated login:

  1. The user visits the app, which redirects them to the IdP with a base64-encoded AuthnRequest carrying a request ID.
  2. The IdP authenticates the user.
  3. The IdP returns an HTML page with a form that auto-submits a SAMLResponse by POST to the SP's assertion consumer service (ACS) URL.
  4. The SP validates: the XML signature with the IdP certificate from the configured metadata; Issuer; Audience equals the SP's entity ID; Recipient equals the ACS URL; the time window (NotBefore, NotOnOrAfter); InResponseTo equals the request ID it sent (or, for IdP-initiated logins, that unsolicited responses are allowed); and that the assertion ID hasn't been seen before.
  5. The SP reads the NameID and attributes and creates its own session.

Conceptually it maps one-to-one onto OIDC: assertion ↔ ID token, Audience ↔ aud, InResponseTo ↔ nonce, IdP metadata ↔ discovery document. The differences are practical: XML instead of JSON, delivery through a browser POST instead of a back channel, certificate-based keys exchanged manually in metadata files, and an XML signature model that is notoriously easy to get wrong.

Signature wrapping. An XML signature covers an element identified by an ID attribute, not the whole document. If one piece of code verifies "the element with ID abc is signed" while another reads "the first Assertion element", an attacker can keep the genuinely signed element somewhere harmless and insert a forged assertion where the reader looks. In March 2025 GitHub's security team published two such bypasses in ruby-saml (CVE-2025-25291 and CVE-2025-25292, fixed in 1.18.0): the library used two different XML parsers, which built different trees from the same input, so an attacker holding any one valid signed response from an organisation's IdP could construct assertions for any user. The structural defences: verify and read from the same parsed tree, check the element you consume is the element that was signed, reject responses with more than one assertion or with DTDs, and update SAML libraries promptly.

7. Enterprise SSO for a multi-tenant product

B2B products must let each customer bring its own IdP. The design pieces:

  • Connections per tenant. Each tenant configures an OIDC or SAML connection: metadata URL or file, client credentials, attribute mapping.
  • Domain verification. A tenant claims acme.com by publishing a DNS TXT record. Only then does the app route @acme.com users to Acme's IdP.
  • Home realm discovery. The login page asks for an email, looks up the domain, and sends the user to the right IdP (or to password/social login if none).
  • Scoped trust. An assertion from Acme's connection may only log users into Acme's tenant, and may only assert emails in Acme's verified domains. Otherwise a malicious tenant's IdP — which they fully control — can assert ceo@victim.com. This is the multi-tenant version of the Storm-0558 lesson: a key trusted for one population must not be accepted for another.
  • Provisioning. Just-in-time (JIT) provisioning creates a user on first login with default roles. SCIM (System for Cross-domain Identity Management, RFCs 7643/7644) lets the IdP push creates, updates and — crucially — deactivations, so leavers lose access when HR offboards them rather than when their session happens to expire.
  • Enforcement. Tenants usually want "SSO only" for their domain: no password login or social login bypass, with one or two break-glass admin accounts for when the IdP is down.

8. Account linking: the dangerous part

Every app with more than one login method faces the question: when a federated identity arrives, which local account does it belong to? The options, from safest to riskiest:

  1. Key on (iss, sub) only. Each provider identity is its own account; linking a second provider requires being logged in already and explicitly connecting it. Safest; users who forget which button they used end up with duplicate accounts.
  2. Link by verified email at first login, then pin (iss, sub). On first login with a provider, if the email is verified by that provider and matches an existing account, link — and record the (iss, sub). Later logins must present the same sub; a different sub with the same email is an alert, not a silent re-link. This handles the "I signed up with GitHub, now I use Google" case and resists lapsed-domain takeovers.
  3. Link by email on every login. Whoever currently controls an address owns the account. Vulnerable to unverified email claims (nOAuth), reassigned addresses (a company reuses jobs@), and lapsed domains (Truffle 2025).

The Prep Console is in the third category, deliberately simple for an invite-only study tool. Its users table has a unique, case-insensitive email column; complete_login() lowercases the email, refuses disabled users, refuses unknown emails that are neither admins nor invited, then upsert_user()s by email, recording the latest provider. It mitigates the nOAuth class correctly: it only accepts Google emails with email_verified true and GitHub emails flagged both primary and verified. What it doesn't do is record the provider's sub (or GitHub's numeric user id), so if an invited address ever came under someone else's control, they could sign in as that user. For a handful of invited friends that's an acceptable trade; for a product, option 2 is the standard answer.

One more provider-specific trap: GitHub's /user profile email is user-chosen and optional, while /user/emails lists addresses with verification flags. Using the profile email instead of a verified entry from /user/emails recreates nOAuth on GitHub. The app reads the right endpoint.

Pairwise subject identifiers

By default an OpenID provider gives the same sub to every client ("public" subject type), which lets colluding relying parties correlate a user across services. OIDC also defines pairwise identifiers: a different sub per client (or per sector of related clients), so two apps can't join their data on it. Apple's Sign in with Apple goes further with private relay email addresses. The design consequence for you: sub is only meaningful together with iss and, with pairwise providers, with your client ID — if you change client IDs or consolidate apps, existing sub values may not carry over, which is a migration you must plan.

Why email is so tempting and so dangerous

Email is the one identifier every provider shares and users recognise, so it's the natural join key across providers and the natural way to invite people. But it has three properties that make it a poor identity key. It's mutable: users change addresses, and some IdPs let them set arbitrary ones. It's reassignable: organisations recycle addresses, and domains lapse and get bought. And its verification semantics differ per provider: Google's email_verified means Google has seen proof of control at some point; an enterprise IdP's email may be whatever an admin typed. Microsoft's post-nOAuth guidance and the xms_edov claim (email domain owner verified) are attempts to give relying parties enough information to decide. A robust design treats email as the bootstrap for linking, then pins the stable identifier, and treats any later mismatch as a security event.

IdP-initiated SSO

SAML allows the IdP to send an unsolicited assertion — the user clicks an app tile in the corporate portal and arrives logged in, with no prior request from the SP. It's convenient and widely demanded, and it removes the InResponseTo binding, so a captured assertion can be replayed (within its validity window) or injected into another user's browser (login CSRF). Mitigations: short assertion lifetimes (a few minutes), a cache of seen assertion IDs, and — for OIDC — the "third-party-initiated login" pattern, where the IdP just redirects the user to the app's login URL and the app starts a normal SP-initiated flow with fresh state and nonce. Prefer that wherever customers allow it.

The IdP is a single point of compromise

Federation concentrates trust. If an attacker controls the IdP — or its signing key — they can authenticate as anyone at every relying party. "Golden SAML" attacks, used in the 2020 SolarWinds-related intrusions, stole on-premises ADFS token-signing certificates to forge SAML assertions for cloud services. Storm-0558 (au4) was the OIDC-era equivalent with a stolen signing key. Defences sit mostly with the IdP operator (HSM-protected keys, rotation, monitoring), but relying parties contribute: pin the expected issuer and keys per tenant, alert on logins with unusual claims or from unusual IdP configurations, and keep enough logs — assertion ID, issuer, subject, signing key — to answer "which logins used the compromised key?".

Logout is the hard part of SSO

Login is a pull: each app asks the IdP when it needs a user. Logout would need a push: the IdP must tell every app that a session ended. OIDC offers RP-initiated logout (the app redirects to the IdP's end-session endpoint), front-channel logout (the IdP loads each app's logout URL in hidden iframes — increasingly broken as browsers block third-party cookies), and back-channel logout (the IdP POSTs a signed logout token containing iss, sub and sid to each app's server). Back-channel logout is the robust choice but requires the app to keep server-side sessions indexed by the IdP's sid — another argument for server-side sessions in enterprise products (au3). Many organisations sidestep the problem by keeping app sessions short and using SCIM deprovisioning for the case that really matters: someone leaving.

Step-up and acr values

A relying party can ask for stronger authentication by sending acr_values or max_age in the request ("re-authenticate within the last 5 minutes, with a phishing-resistant method"), and must verify the returned acr, amr and auth_time, because an IdP may ignore the request. This lets an app keep a relaxed session for browsing and demand fresh, strong authentication — through the IdP, not its own password prompt — before a sensitive action. It only works if the IdP actually supports the requested level, which varies a lot between consumer and enterprise providers.

Third-party cookie deprecation and federation

Several SSO features — front-channel logout, silent token renewal in hidden iframes, session checks — relied on the IdP's cookies being sent in third-party contexts. Browsers have been restricting those (Safari and Firefox block them by default). The W3C's Federated Credential Management API (FedCM) moves the browser into the loop, letting it mediate federated sign-in without third-party cookies; Google's sign-in libraries have moved to it in Chrome. For architecture answers, the point is that federation flows built on redirects and back channels keep working, while anything relying on hidden iframes needs rethinking.

Common SSO incidents

Certificate expiry: SAML IdP signing certificates expire (often after one to three years), and if the SP's metadata isn't updated, every login for that tenant fails. Symptoms: a sudden 100% SSO failure for one customer. Prevent with metadata URLs that SPs refresh automatically, expiry monitoring per connection, and overlapping certificates during rollover.

Clock skew on SAML NotBefore windows or ID token iat checks; allow a minute or two.

Attribute drift: a customer changes their IdP's attribute mapping (email moves from one attribute to another, or NameID format changes) and users get duplicate accounts or "user not found". Key on stable identifiers and alert when a known user arrives with a different subject.

Duplicate accounts after users sign in with a different provider than they signed up with — a support burden that tempts teams into risky automatic email linking.

Library vulnerabilities: SAML libraries have had a steady stream of signature-validation CVEs; track them and patch within days.

Metrics

Login success rate per connection and per provider; validation failures by reason (signature, audience, issuer, expired, nonce, InResponseTo); time to first login after a new connection is configured (onboarding friction); assertions per IdP key (to scope a key compromise); subject mismatches for known emails (possible takeover attempts); share of users provisioned by SCIM vs JIT; days until each connection's certificate expires.

The cases, as engineering lessons

Descope's nOAuth disclosure (20 June 2023) found that Entra ID's email claim was mutable and unverified, and that apps merging accounts on it were exploitable; Microsoft responded with the xms_edov claim and an option to remove unverified email claims, plus guidance against authorising on email or upn. Truffle Security's January 2025 research bought lapsed startup domains, recreated employee mailboxes in Google Workspace and signed into SaaS products used by those startups; it found sub would have prevented the takeover but reported that some downstream services found it unreliable, and argued providers should offer a stable workspace and user identifier. GitHub's March 2025 ruby-saml write-up showed a library-level bypass that let anyone with one valid signed response sign in as anyone. All three share a lesson: the protocol's guarantees are narrow, and the security of SSO depends on how the application maps assertions to accounts and on the quality of the libraries that parse them.

Support and recovery

Federated users still get locked out: a personal Google account is lost, a GitHub account is deleted, a company changes IdP. Support teams then face requests to "move my account to a new login", which is an account-takeover vector if handled on trust. Define the process in advance: re-verification through an existing channel (the old email still receiving mail, a tenant admin vouching for an employee), a waiting period with notification to the old identity, and an audit record. For enterprise tenants, route these requests to the tenant's own admins rather than your support desk.

Build or buy

Supporting OIDC for consumer login is straightforward with a library like Authlib. Supporting enterprise SSO well — dozens of IdP quirks, SAML, SCIM, domain verification, certificate rotation — is a product in itself, which is why many B2B companies use an identity platform or an SSO broker for it. Whichever you choose, own the account-linking rules and the tenant-scoping checks yourself; those are where the takeovers happen.

About 15 minutes.

  1. Look at real metadata. Fetch https://accounts.google.com/.well-known/openid-configuration with urllib.request and print issuer, jwks_uri and id_token_signing_alg_values_supported. Fetch the jwks_uri and print each key's kid and alg. How many keys are published?
  2. at_hash. Compute it for 2YotnFZFEjr1zCsicMWpAA: SHA-256, first 16 bytes, base64url without padding. Expect bJYTDxMKsNbRWDl-JNK8wQ.
  3. Mint test ID tokens. Reuse au4's HS256 signer to make tokens with the claims shown in the body, then variants: wrong aud, wrong nonce, expired, at_hash for a different access token, email_verified: false.
  4. Validator. Write validate_id_token(tok, client_id, issuer, nonce, access_token) implementing the body's steps 2-7; each variant should fail with a distinct reason.
  5. Linking. Keep accounts = {email: {"subs": set()}}. Implement policy A (link by email every time) and policy B (link by verified email the first time, then require the stored (iss, sub)). Simulate: the real user logs in with sub 111; later a "lapsed domain" login arrives with the same email and sub 999.

What to look for: step 1 normally shows two keys — rotation in progress. Each step-3 variant is caught by a different check, showing that signature validity alone would have accepted them all. In step 5, policy A logs the newcomer into the old account; policy B refuses and flags it, which is the defence against the 2025 lapsed-domain takeovers.

Diagnose: "a contractor logged into a customer's workspace"

Your B2B app supports Google login, Microsoft login and per-tenant SAML. Users are keyed by email. A customer, Initech (domain initech.com, SAML-enforced), reports that someone accessed their workspace as bob@initech.com through "Log in with Microsoft" at a time when Bob was on holiday. Bob's Microsoft account doesn't exist. What likely happened, what do you check, and what do you change?

Answer

Likely cause. An nOAuth-style attack: someone created or used a Microsoft Entra account whose email attribute was set to bob@initech.com without verification, logged in with Microsoft, and your app matched the email to Bob's existing account. A second contributing failure: Initech enforces SAML, yet your app let a social login reach an account in a SAML-enforced domain.

Check. Login logs for that session: provider, issuer, tenant ID (tid) and sub of the Microsoft token, the claims received (was there xms_edov? was email from an unverified attribute?). All other logins where provider ≠ the user's usual provider and email matched an existing account. What the session accessed.

Contain. Revoke that session and any tokens; notify Initech; disable Microsoft login for SAML-enforced domains immediately.

Fix. (1) Enforce SSO per verified domain: users in initech.com may only authenticate through Initech's connection. (2) Store and pin (iss, sub) per linked identity; link a new provider only when the user is already logged in, or by verified email on first login with the identifier then pinned. (3) For Microsoft, accept email for linking only with a domain-verified signal (xms_edov) or not at all. (4) Alert on any login where the email matches but the stored subject doesn't. (5) Add tests for unverified-email and mismatched-subject cases to the login suite.
