For years, First American Financial — one of the largest title-insurance companies in the US — let customers view their documents through web links that contained a sequential document number. Change the number by one and you saw someone else's mortgage paperwork. No login was required. In May 2019 the journalist Brian Krebs reported that the system exposed hundreds of millions of documents going back to 2003: bank account numbers and statements, mortgage and tax records, Social Security numbers, wire transfer receipts, driver's licence images. The US Securities and Exchange Commission later put the count at more than 800 million document images, found that the company's own security staff had identified the vulnerability months before the journalist did but it never reached management, and fined the company $487,616.

That is the most direct form of a multi-tenancy failure: a shared system serving many customers, with nothing checking that the person asking for a record belongs to the customer who owns it. Most SaaS leaks are subtler — a cache keyed without the customer ID, a search index queried without a filter, a background job that forgot which customer it was working for — but the shape is identical. In a shared system, every layer must know whose data it's touching.

Multi-tenancy is how almost all software-as-a-service is built: one deployment, many customer organisations ("tenants"), sharing servers, databases and queues because that's what makes SaaS affordable. The senior question this topic answers is "how do you keep tenants apart?" — not just their data, but their performance and their failures. We'll compare the isolation models (database per tenant, schema per tenant, shared tables); follow the tenant ID from the token to the query; write an IDOR bug and fix it; enforce tenancy in the database with PostgreSQL row-level security, including the two traps that silently disable it; extend the boundary to caches, search, queues, files and logs; contain noisy neighbours with quotas and shuffle sharding, worked with real combinatorics; and use per-tenant encryption keys for blast radius and deletion. The Prep Console's per-user scoping — every row keyed by user_id — is the small version of the same idea.

The apartment building

Think of a block of flats. Every tenant shares the building's structure, plumbing, lifts and front door; that's what makes rent cheaper than a detached house. But each flat has its own lock, its own post box and its own meter, and the building manager's master key is kept in a safe and its use is logged. If the post boxes weren't labelled, or one flat's tenant could run the hot water for the whole building dry, or the lift went to any floor regardless of whose key you used, sharing would stop being acceptable.

A multi-tenant system is that building. Tenants share compute, databases and networks for cost; isolation is the set of locks, labels and meters that make sharing safe. There are three kinds of isolation to provide:

  • Data isolation: tenant A can never read or change tenant B's data, through any path.
  • Performance isolation: tenant A's load can't make the system unusable for tenant B (the noisy neighbour).
  • Failure isolation: a bug triggered by tenant A's data, or a bad deployment, affects as few other tenants as possible (blast radius).

The analogy has a limit worth stating: in a building, the locks are physical and the same for everyone. In software, every new feature is a new door, and someone has to remember to fit a lock to it. That's why the most robust designs make the boundary automatic — enforced by the framework, the data layer and the infrastructure — rather than relying on each developer remembering.

Who is "the tenant"?

A tenant is the unit you promise to keep apart. In business software it's the customer organisation — Acme's whole workspace, with all its users. In a consumer product it may simply be each user, which is how the Prep Console works: every learner's progress is private, so each user is effectively a tenant of one. Some products have two levels (a reseller with many end customers, or an organisation with many workspaces), and then isolation must hold at both. Naming the unit precisely matters, because it decides what goes in every key, filter and log line, and what you tell customers when something goes wrong.

A spectrum of sharing

How much to share is the first design decision. At one end, each tenant gets its own database (or its own deployment entirely): the silo model. In the middle, tenants share a database server but each has its own schema: the bridge model. At the other end, everyone shares the same tables, and every row carries a tenant_id: the pool model. (The names come from AWS's SaaS architecture guidance, and they're widely used.)

If you stop here: carry a verified tenant ID through every layer, make every data access filter by it — ideally enforced by the data layer so a forgotten filter fails closed — keep one tenant's load from hurting others, and test the boundary as seriously as you test features.

2. Tenant context: from token to query

Every request must establish its tenant from something the client can't forge, then carry it to every layer:

  1. Authenticate the user (au3-au6). The token or session yields the user and either a tenant claim or a list of memberships.
  2. Select and verify the tenant. Users in several tenants pick one (a header, a subdomain such as acme.app.example, a path segment); the server checks the user is a member of that tenant on every request. A tenant ID from the request is a claim to be verified, never a fact.
  3. Bind the verified tenant into request context — a request-scoped variable the data layer reads — so handlers can't accidentally use a different one.
  4. Propagate it to everything the request causes: downstream service calls (in the internal token, au1), queued jobs (in the message, verified when consumed), log lines and traces (as a field), and the database session (section 4).

The Prep Console does the single-user version: the session yields uid, load_user() verifies it against the database on each request and stores the row in g.user, and every progress query takes g.user["id"] — never a user ID from the URL or body. Each user is, in effect, a tenant of one.

3. An IDOR bug and its fix

Here's the classic bug in a Flask-style API for a pooled invoices table:

@app.get("/api/invoices/<int:invoice_id>")
@login_required
def get_invoice(invoice_id):
    row = db.execute("SELECT * FROM invoices WHERE id = %s", (invoice_id,)).fetchone()
    if row is None:
        abort(404)
    return jsonify(dict(row))

Three faults. The lookup is by ID alone, so any logged-in user of any tenant can read any invoice: change 17 to 18 and Acme's user reads Initech's invoice — exactly First American's flaw, minus the missing login. The response returns every column (SELECT *), including internal fields such as cost price or notes the user's role mayn't see (property-level exposure, au1). And there's no audit of who read what.

The fix scopes by tenant in the query, returns 404 for invisible objects, selects only allowed fields, and checks the role:

@app.get("/api/invoices/<int:invoice_id>")
@login_required
def get_invoice(invoice_id):
    t = g.tenant                                   # verified from the session, never the request
    authorize(g.user, "invoice.read", tenant=t)    # function-level: role allows reading invoices
    row = db.execute(
        "SELECT id, number, amount, status, issued_at FROM invoices "
        "WHERE id = %s AND tenant_id = %s", (invoice_id, t.id)).fetchone()
    if row is None:
        abort(404)                                 # same answer for 'not yours' and 'missing'
    audit("invoice.read", resource=invoice_id, tenant=t.id)
    return jsonify(dict(row))

And the test that would have caught it, generated for every route that takes an ID:

def test_invoice_cross_tenant(client_acme, invoice_of_initech):
    r = client_acme.get(f"/api/invoices/{invoice_of_initech.id}")
    assert r.status_code == 404

Scoping by tenant in each query is necessary but fragile: one forgotten clause anywhere is a leak. The next section makes the database enforce it too.

4. Row-level security in PostgreSQL

Row-level security (RLS) lets the database add a filter to every query on a table according to a policy. For tenancy:

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;          -- apply to the table owner too

CREATE POLICY tenant_isolation ON invoices
  USING      (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);

USING filters rows that queries can see, update or delete; WITH CHECK stops inserts or updates that would write a row for another tenant. If RLS is enabled and no policy applies, PostgreSQL shows no rows — default deny. The true argument to current_setting means "return NULL instead of an error if unset"; tenant_id = NULL is never true, so a request that forgot to set the tenant sees nothing rather than everything. Now the buggy handler above returns 404 for Initech's invoice even though its query forgot the tenant clause — the database added it.

The application sets the tenant at the start of each transaction:

BEGIN;
SELECT set_config('app.tenant_id', '6f1c…acme-uuid', true);   -- true = local to this transaction
SELECT id, amount FROM invoices WHERE id = 18;                 -- returns nothing: 18 is Initech's
COMMIT;

Two traps silently switch RLS off, and both are common:

Trap 1: who bypasses RLS. Superusers and roles with the BYPASSRLS attribute always bypass it. The table owner bypasses it too unless the table has FORCE ROW LEVEL SECURITY. Many applications connect as the same role that ran the migrations and therefore owns the tables — so without FORCE, RLS does nothing for them. The robust setup is a separate application role that owns nothing, has no BYPASSRLS, and is granted only the privileges it needs, plus FORCE on every tenant table as a belt-and-braces measure.

Trap 2: connection pools. db13 explained that pools reuse database sessions. If the application runs SET app.tenant_id = 'acme' at session level and the pool — PgBouncer in transaction mode, or an application pool that doesn't reset state — hands that connection to the next request, which is for Initech and forgets to set its own tenant, the Initech request runs as Acme. Using SET LOCAL or set_config(…, true) inside a transaction scopes the value to that transaction, so it can't leak, and if a request forgets to set it, the NULL-means-nothing behaviour fails closed.

RLS has costs. Policies add predicates to every query, so tenant_id must lead the relevant indexes (it usually should anyway — composite primary keys like (tenant_id, id) keep each tenant's rows together). Functions used in policies should be simple and marked appropriately so the planner can use indexes. Some operations — cross-tenant maintenance jobs, analytics — need a separate, audited role that bypasses RLS deliberately. And RLS expresses tenant boundaries well but complex per-object authorisation poorly; it's a backstop for au8's checks, not a replacement.

5. Beyond the database

Data lives in many places besides the primary database, and each needs the tenant boundary:

  • Caches. Every key must include the tenant: t:acme:settings, not settings. A shared cache key is a cross-tenant leak that only appears under load. HTTP caches and CDNs need Vary or private caching for tenant-specific responses (net7).
  • Search indexes. Shared indexes store tenant_id on every document, and every query must filter on it inside the search engine (not by post-filtering results). Per-tenant indexes or aliases are an option for large tenants.
  • Queues and jobs. Messages carry the tenant; consumers set tenant context from the message before touching data, and validate it. A job runner that defaults to "no tenant" with an RLS-bypassing role is a classic leak.
  • Object storage. Prefix keys by tenant (s3://bucket/acme/…), grant service access by prefix, and make pre-signed download URLs short-lived. Never let a user-supplied path choose the prefix.
  • Analytics and warehouses. Copies of production data often lose RLS. Keep tenant IDs, restrict who can query across tenants, and audit it.
  • Logs, traces and error trackers. Payloads in logs mix tenants; restrict access, redact sensitive fields, and include tenant ID as a field so access can be scoped and incidents scoped.
  • AI features. Embedding stores and retrieval indexes are search indexes with the same rules; a shared vector index queried without a tenant filter will happily retrieve another customer's documents into a prompt. au12 covers permission-aware retrieval.

6. Noisy neighbours

Performance isolation fails in predictable places: one tenant's bulk import saturates database I/O; a tenant's report runs a full-table scan; a tenant's integration retries in a tight loop; a single huge tenant's queue backlog delays everyone else's jobs. The defences:

  • Per-tenant rate limits and quotas at the edge (sc12): requests per second, concurrent requests, payload sizes, storage, jobs in flight — sized by plan tier, with clear 429 responses.
  • Fair scheduling for shared work: per-tenant queues serviced round-robin, or weighted fair queuing, so a tenant who enqueues a million jobs waits behind themselves, not in front of everyone.
  • Database guards: statement timeouts, per-role connection limits, and moving heavy reporting to replicas or a warehouse.
  • Isolation for the largest tenants: their own pool, cell or silo.
  • Per-tenant metrics: you can't fix what you can't attribute — record tenant on resource usage so the noisy tenant is visible.

7. Shuffle sharding, worked

Sharding tenants across workers (sc7) limits how many tenants a worker failure affects, but everyone on a shard shares its fate: a tenant whose requests crash the process (a "poison pill") takes down every tenant on its shard. Shuffle sharding, described in the Amazon Builders' Library, gives each tenant a random combination of workers instead.

Take 8 workers. Plain sharding into 4 shards of 2 puts a quarter of tenants on each shard; a poison-pill tenant kills its shard and 25% of tenants go down. With shuffle sharding, each tenant gets a random pair of the 8 workers. There are C(8, 2) = 28 distinct pairs. When the poison tenant crashes its two workers:

  • Tenants with exactly the same pair lose everything: about 1 in 28 of them, 3.6%.
  • Tenants sharing one of the two workers lose half their capacity but stay up — if clients retry on their other worker.
  • Everyone else is unaffected.

Scale it: 100 workers with 5 per tenant gives C(100, 5) = 75,287,520 combinations. With 10,000 tenants, the expected number sharing the poison tenant's exact five workers is 10,000 ÷ 75,287,520 ≈ 0.00013 — effectively none. The insight is combinatorial: the number of possible shards grows enormously with small shard sizes, so correlated failures between tenants become rare without giving each tenant dedicated workers.

8. Per-tenant encryption keys

Encrypting data at rest with one key for everything protects against a stolen disk, not against a confused application. Per-tenant keys add three properties. Using envelope encryption (au11), each tenant has a data key that encrypts its data, and that data key is itself encrypted ("wrapped") by a key-encryption key in a key management service (KMS).

  • Blast radius: a leaked or misused data key exposes one tenant.
  • Customer control: enterprise customers can require a customer-managed key (CMK, sometimes "bring your own key") in their own KMS account. The service must call their KMS to unwrap the tenant's data key; the customer sees every use in their own logs and can revoke access, which stops the service reading their data.
  • Crypto-shredding: to delete a departed tenant's data from backups, replicas and logs you can't easily rewrite, destroy their key. Without it the ciphertext is noise. This is often the only practical way to meet deletion obligations across years of backups.

The costs are operational: a KMS call on the data path (cache unwrapped data keys in memory for minutes), key rotation per tenant, and an availability dependency — if a customer revokes their key or their KMS is down, their data is unavailable, by design.

Cells: isolating failures, not just data

Large SaaS providers increasingly run cell-based architectures: many complete, independent copies of the stack (each with its own databases, queues and services), each serving a subset of tenants, with a thin routing layer in front. A bad deployment, a poison-pill request or a database failure affects one cell's tenants. Cells also make tiering natural — an enterprise tenant can have a dedicated cell — and cap the size any one database must reach. The hard parts are the router (which must be extremely simple and highly available, since it's shared), moving tenants between cells, and cross-cell features such as global search or users who belong to tenants in different cells.

Tenant-aware identity

Isolation starts at login. In B2B products a user often belongs to several tenants, and the identity system must model memberships, roles per tenant and tenant-specific SSO (au6). Two bugs recur. The "tenant switch" bug: the UI switches to tenant B but an API keeps using the tenant from a token issued for tenant A, or vice versa, mixing data. And the "cross-tenant IdP" bug: tenant A's SAML connection asserts a user with an email in tenant B's domain, and the app logs them into tenant B. Both are fixed by treating tenant as part of the authenticated context, verified per request, and scoping IdP trust to each tenant's verified domains.

Side channels between tenants

Even with perfect access checks, shared infrastructure can leak information indirectly. Timing differences reveal whether an object exists. Shared caches can leak through timing ("is this URL cached?"). Unique constraints across tenants leak existence ("that email is already registered" on a global users table reveals another tenant's user). Aggregate features — "popular in your industry" — can expose another tenant's data if computed from too few tenants. Defences: per-tenant uniqueness where possible, uniform responses, minimum aggregation sizes (k-anonymity), and treating any cross-tenant computation as a data-sharing decision that needs review.

Cross-tenant vulnerabilities in cloud platforms

Cloud providers are the largest multi-tenant systems of all, and researchers have repeatedly found cross-tenant bugs in managed services — for example Wiz's 2021 "ChaosDB" report on Azure Cosmos DB, where a feature's misconfiguration exposed keys that could access other customers' databases. Two lessons carry over to any SaaS. Features added for convenience (notebooks, integrations, admin consoles) often run with broad internal privileges, so they're where tenant boundaries break. And the provider's response matters: rotating every potentially exposed credential and notifying affected tenants quickly is part of the design.

Migrating tenancy models

Products often start pooled and later need silos for large customers, or start with schemas and hit catalog limits. Moving a tenant is a data migration with a correctness bar of "zero cross-tenant rows": copy by tenant ID with change-data capture, verify with per-table counts and checksums, cut over routing in the tenant directory during a brief write freeze, and keep the old copy read-only until verified. Designing tables from day one with tenant_id in every primary key and every unique constraint makes this — and RLS, and sharding by tenant — far easier.

Canary tenants and continuous verification

Code review and tests check the paths you thought of. Continuous verification checks the ones you didn't. Seed a few canary tenants with distinctive marker strings in every field type — names, titles, file contents, embeddings — and continuously run, as other tenants, every read surface the product has: search, autocomplete, exports, notifications, AI answers, analytics dashboards. Any appearance of a marker outside its tenant pages someone. It's cheap, it catches regressions in layers that unit tests rarely cover (caches, indexes, async pipelines), and it turns "we believe tenants are isolated" into a measured claim you can show auditors.

Admin and internal tooling

Internal tools — support consoles, data-fix scripts, analytics notebooks — legitimately cross tenant boundaries, and they're where isolation is weakest because they're built quickly for trusted users. Treat them as products with their own authorisation: just-in-time, ticket-bound access per tenant, read-only by default, every action logged to the affected tenant's audit trail, and a deliberately separate database role that bypasses RLS only for those tools. A support console that can query any tenant with one search box is a breach waiting for one compromised employee account.

Compliance shapes architecture

Regulation turns isolation choices into requirements: data residency (EU tenants' data stays in EU regions), contractual deletion timelines (crypto-shredding), audit rights (per-tenant audit logs), and customer-managed keys for regulated industries. Mapping each requirement to a mechanism early — which tier gets silos, which regions, which key model — avoids retrofitting isolation into a pooled system under contract pressure.

How cross-tenant leaks actually surface

Usually from customers: "I can see another company's name in my dropdown." The causes are almost always in the secondary layers — a cache key, a search query, an autocomplete endpoint, an export job, a GraphQL resolver for a nested field. When it happens: disable the feature, identify every request that could have crossed (logs with tenant and resource IDs make this possible), notify affected tenants with facts, and add a regression test plus a structural fix (RLS, a mandatory tenant parameter in the data layer) rather than just patching the one query.

Signals to monitor

Any authorisation decision where resource tenant ≠ caller tenant (alert on one); per-tenant request rate, CPU, database time and queue depth (noisy-neighbour attribution); per-tenant error and latency SLOs, not just global ones (a global p99 hides one tenant's outage); 404 rates on ID-taking endpoints per caller (IDOR probing — First American's scraping would have shown as one client fetching many sequential IDs); canary-tenant markers appearing outside their tenant; and RLS configuration drift (a check that every tenant table has RLS enabled and forced).

Operational knobs

Quota sizes per plan tier; fair-scheduling weights; statement timeouts; the threshold at which a tenant graduates to a dedicated pool or cell; shuffle-shard size (larger shards give more capacity per tenant and more overlap); data-key cache lifetimes for per-tenant encryption (longer is cheaper, shorter honours CMK revocation sooner).

First American, as an engineering post-mortem

Krebs's May 2019 report described document links on First American's site containing a sequential number that could be incremented to retrieve other customers' documents without authentication, with records back to 2003. The SEC's June 2021 order says the EaglePro application exposed over 800 million images including Social Security numbers and financial information; that information-security staff had found the vulnerability months before the journalist's report but hadn't remediated it or escalated it to the executives responsible for disclosure; and the company agreed to a $487,616 penalty. The engineering lessons stack neatly: an object-level check on every document fetch would have prevented it; unguessable, expiring, recipient-bound links would have contained it; monitoring for sequential access would have detected scraping; and a vulnerability process that escalates critical findings with deadlines would have closed it months earlier.

Communicating with tenants

B2B customers increasingly ask, in security questionnaires, exactly how their data is isolated: which model, whether RLS or per-tenant keys are used, how support access works, and how a cross-tenant incident would be detected and disclosed. Being able to answer with mechanisms and evidence (test results, canary monitoring, audit logs) rather than assurances is part of the product.

Right-sizing again

The Prep Console is a pool of users in one SQLite file with owner scoping in every query and per-user deletion (DELETE FROM … WHERE user_id = ? across tables when an admin removes a user). With a handful of invited users there's no noisy-neighbour problem to speak of and no need for RLS, which SQLite doesn't have anyway. If it became a product for schools, each school would be a tenant, and everything in this topic would start to apply.

Goal: reproduce an IDOR, fix it, simulate a pooled-connection tenant leak and the transaction-scoped fix, and check shuffle-sharding numbers — Python 3.12 standard library only (sqlite3, itertools, random, math). About 15 minutes.

  1. Data. In sqlite3 (in memory), create invoices(id INTEGER PRIMARY KEY, tenant TEXT, amount REAL) and insert rows for acme and initech.
  2. IDOR. Write get_invoice_v1(session, invoice_id) that ignores session["tenant"]. As Acme, fetch an Initech invoice. Then get_invoice_v2 with AND tenant = ? returning None → "404".
  3. Enforced filter. SQLite has no RLS, so emulate it: create views per tenant is awkward; instead write a TenantDB wrapper whose query(sql, params) refuses SQL that doesn't contain tenant = :tenant and always binds :tenant from its own context. Show the buggy query raising an error instead of leaking.
  4. Pool leak. Simulate a pool: a list of "connection" dicts holding a tenant setting. Request 1 sets it at "session level" and returns the connection; request 2 (Initech) forgets to set it and reads Acme's data through the wrapper. Then change to "transaction level": the wrapper clears the setting on release, and an unset tenant returns no rows.
  5. Shuffle sharding. With math.comb, print C(8,2) and C(100,5). Simulate 10,000 tenants each assigned random.sample(range(8), 2); pick a poison tenant and count tenants fully down, half down and unaffected. Repeat with 100 workers and 5 each.

What to look for: step 2's v1 returns another tenant's invoice although the user is logged in; v2 returns "404". Step 3 turns a forgotten filter into an exception — the "fail closed" property RLS gives in PostgreSQL. Step 4 reproduces the connection-pool leak and shows that clearing per-transaction state makes the forgetful request see nothing. Step 5 shows about 357 of 10,000 tenants (1/28) fully down with 8×2, and almost certainly none with 100×5.

Incident: "customer sees another company's projects in search"

Your pooled multi-tenant project tool (PostgreSQL with tenant_id columns, Elasticsearch for search, Redis cache, PgBouncer in transaction mode) gets a ticket: a user at Acme typed "roadmap" in search and saw a project titled "Initech 2027 roadmap". Database queries all include tenant filters according to code review. Investigate and fix.

Answer

Contain. Disable search (or force a tenant filter at the proxy in front of Elasticsearch) immediately. Preserve logs.

Hypotheses, most likely first. (1) The search query builder omits the tenant filter on some path — a new "global search" endpoint, autocomplete, or a query type where the filter is added as a scoring clause (should) rather than a filter (must). Check the actual query sent for that request ID. (2) The indexer wrote Initech's project into a document with Acme's tenant_id — for example a background job that lost tenant context and defaulted. Check the indexed document's tenant field. (3) A cache: search results cached under a key without the tenant (search:roadmap). Check Redis keys for that pattern. (4) Less likely for search, but check: a database session variable set at session level leaking through PgBouncer to the indexer.

Scope. From search logs, find all requests where returned documents' tenant differs from the caller's tenant during the exposure window; that list is who saw what. Notify affected tenants with specifics.

Fix structurally. Route all search through one client library that requires a tenant and adds it as a mandatory filter; use filtered aliases or per-tenant indexes for large tenants; prefix every cache key with tenant; carry tenant in job messages and set it from the message; use SET LOCAL for any session variables; add a CI test that runs every search endpoint as tenant A against data seeded only in tenant B and expects zero hits; add a production check that drops (and alerts on) any search hit whose tenant differs from the caller's.
