A marketing team prints a QR code on two million cereal boxes. The code points at https://shop.example.com/campaigns/2026/spring/landing?utm_source=box&utm_medium=print&utm_campaign=cereal-q2&variant=b — 130 characters. That is too long for a clean QR code, ugly in a text message, and the moment someone renames the campaign page, two million printed boxes point at a 404. So the team shortens it to sho.rt/k3Pq9Za. Now the QR code is small, the link fits anywhere, the destination can be changed without reprinting, and — the part the marketing team actually pays for — every scan is counted: when, from which country, on which phone.

That small service carries a big promise. The cereal boxes will sit in cupboards for a year; the link must keep working for all of them. If the shortener goes down for ten minutes, every link it ever issued is broken for ten minutes, across every printed page, email and social post that contains one. And the traffic is nothing like evenly spread: most links are clicked a handful of times in their first days and then never again, while one link in a celebrity's post can draw thousands of clicks per second.

This is why "design a URL shortener" is the classic warm-up question. The product fits in one sentence, so the whole hour goes on engineering: how many requests, how much storage, how to generate a short code that is unique without every server asking a central authority, how to answer redirects in a few milliseconds, how to count clicks without slowing anything down, and what breaks when one link goes viral. Each of those is a small version of a problem every larger system has.

This lesson follows the order an interviewer expects. First the requirements, functional and non-functional. Then the back-of-envelope estimates, worked by hand: requests per second, storage per year, bandwidth and cache size. Then the API and the data model, the high-level architecture, and three deep dives: generating codes (including the base62 arithmetic and why hashing is the weak answer), the redirect hot path (where 301 versus 302 turns out to be a caching question), and asynchronous click analytics. It ends with bottlenecks, failure modes and trade-offs, a real case from Bitly and Google, and a lab where you build a collision-free, unguessable code generator.

The mental model: a coat check with a ledger

Think of a theatre coat check. You hand over a bulky coat (the long URL) and get back a small numbered ticket (the short code). Later, anyone holding the ticket gets the coat back (the redirect). The attendant's job is to issue tickets that are never duplicated and to find the coat quickly when a ticket comes back. Now add a ledger: every time a ticket is presented, the attendant notes the time and who presented it (the analytics). That is the whole system.

The analogy breaks in two useful places. First, a coat check returns each coat once; a short link is "presented" again and again, potentially millions of times, so the system is overwhelmingly about the lookup, not the issuing. Second, a real coat check has one attendant with one book of tickets. A shortener has dozens or hundreds of servers issuing codes at the same time, and they must never hand out the same code twice — without phoning each other before every ticket. Both breaks point at the two problems the interview is really about: a read-heavy lookup at scale, and unique ID generation without coordination.

Two paths, very different weights

Every design decision follows from noticing that there are two paths through the system and they have nothing in common.

The write path (create a link) happens rarely — tens of times per second — and can afford to be a little slow; a person waiting 200 milliseconds for their short link once does not notice. It has to be correct: the code must be unique, and the link must be durably stored before we return it, because the user is about to print it.

The read path (follow a link) happens hundreds of times as often and must be fast and almost never fail, because a broken redirect is a broken link in someone's email. It is a single key lookup: code in, URL out. The interesting engineering is making that lookup avoid the database almost entirely, using caches at several layers.

A third, quieter path hangs off the read path: analytics. Each redirect produces an event ("code k3Pq9Za was followed at 09:14:03 from Brazil on Android"). These events are the paid product, but they must never slow down or break the redirect, so they are handed to a queue and processed later.

The shape of the hour

Interviewers expect a recognisable flow, and following it is half the score: clarify requirements (five minutes), estimate the load (five to seven), sketch the API and data model, draw the high-level design, then spend the biggest block on two or three deep dives the interviewer cares about, and close with bottlenecks, failures and trade-offs. For a URL shortener the deep dives are nearly always the same three: how to generate the code, how to make redirects fast and correct, and how to collect analytics. A reader who stops here already has a correct picture: a tiny, rare write path that hands out unique codes; a huge, fast read path that is a cached key lookup; and an asynchronous side channel for clicks.

1 · Requirements: say what you are building before you build it

Functional requirements are what the system does. For a shortener: (1) given a long URL, create a short link and return it; (2) when anyone visits the short link, redirect them to the long URL; (3) optionally let the user choose a custom alias (sho.rt/spring-sale instead of a random code); (4) optionally let links expire at a set time; (5) record clicks and show per-link statistics. State the ones you will design and push the rest out of scope out loud: user accounts, billing, link previews and the internals of malware scanning. Naming them shows you know they exist without spending the hour on them.

Non-functional requirements are how well it must do it, and they drive the architecture far more than the features do. Redirects should be fast — a common target is a p99 under 50 ms worldwide, where p99 means 99% of requests are faster than that. Redirects must be highly available, because downtime breaks every link ever issued; aim for 99.99% (about 4.3 minutes of downtime a month). Links must be durable: once you return a short link, losing it is unacceptable. Creation can be slower and slightly less available. Click statistics can lag by seconds or minutes.

Then ask the question that shapes the ID design: are codes permanent? If a code may never be reused, the code space must be sized for every link the service will ever create. Ask also whether the same long URL should always get the same code. Usually the answer is no: two marketing campaigns pointing at the same page want separate statistics, so each create request gets a fresh code.

2 · Back-of-envelope estimates, worked by hand

Pick round assumptions, say them, and compute. Assume 100 million new links per month and a read-to-write ratio of 100:1 (each link is clicked 100 times on average over its life). Useful constant: a month is 30 × 86,400 = 2,592,000 seconds, about 2.6 million.

Write QPS. 100,000,000 ÷ 2,600,000 ≈ 38, call it 40 creates per second. Traffic is not flat — daytime peaks run several times the average — so allow 5× for peak: about 200 per second. That is nothing; one relational database handles it.

Read QPS. 100 × 100 million = 10 billion redirects a month. 10,000,000,000 ÷ 2,600,000 ≈ 3,850, call it 4,000 redirects per second on average and about 20,000 per second at a 5× peak. This is the number the design must serve.

Storage. Each link row holds the code (7 bytes), the long URL (average perhaps 100-200 bytes, maximum a few kilobytes), owner id, timestamps, flags and index overhead. Round to 500 bytes per link. Per year: 1.2 billion links × 500 B = 600 GB per year; five years is 6 billion links and 3 TB. With three replicas for durability that is 9 TB on disk — big for one machine's RAM, ordinary for a few machines' disks.

Bandwidth. A redirect response is tiny: status line, a Location header with the long URL, a few other headers, about 500 bytes. 4,000/s × 500 B = 2 MB/s, or 16 megabits per second on average and about 80 Mbit/s at peak. Creates are negligible: 40/s × 1 KB = 40 KB/s. Bandwidth is not a constraint here — say so and move on, which is itself a sign of judgement.

Click data. Analytics grows faster than links. Each click event (code, timestamp, country, referrer, user agent, a hashed IP) is about 200 bytes. 4,000/s × 200 B = 800 KB/s; × 86,400 s ≈ 69 GB per day, about 25 TB per year of raw events. This is why analytics gets its own storage designed for appends and aggregation, not the link table.

Cache size. Click traffic is heavily skewed: most links get almost all their clicks in their first days. When Google retired goo.gl it reported that more than 99% of its links had no activity in the previous month. So cache only the links clicked recently. If 20 million links are "hot" at any time, 20 million × 500 B = 10 GB, roughly 20 GB with the per-key overhead of a cache like Redis. That fits on one cache node with a replica. Say the conclusion out loud: the working set fits in memory, so the database is almost never on the read path.

Code length. Base62 uses the characters 0-9, a-z and A-Z: 62 symbols, all safe in a URL without escaping. A code of length k has 62k possible values. 626 = 56,800,235,584 (about 57 billion) and 627 = 3,521,614,606,208 (about 3.5 trillion). At 1.2 billion links a year, six characters last about 47 years and seven last about 2,900. For a service the size of Bitly — 600 million shortens a month, 7.2 billion a year — six characters would run out in under eight years. Seven characters is the safe answer.

3 · The API

Three endpoints cover the requirements. Creation and stats are a versioned JSON API; the redirect lives at the root of the short domain because the short URL is the product.

POST /v1/links
  body:  {"url": "https://...", "alias": "spring-sale"?, "expires_at": "2027-01-01T00:00:00Z"?}
  201 → {"code": "k3Pq9Za", "short_url": "https://sho.rt/k3Pq9Za"}
  409 if the alias is taken; 400 if the URL is invalid or blocked

GET /{code}
  301/302 with Location: <long url>      (see deep dive B for which)
  404 if unknown; 410 Gone if expired or deleted

GET /v1/links/{code}/stats?from=...&to=...
  200 → {"clicks": 18234, "by_day": [...], "by_country": {...}}

Two details earn points. First, the create call should accept an idempotency key header, a client-chosen unique string, so that a client retrying after a timeout gets the same link back instead of creating two. (Idempotent means "same effect whether it runs once or several times".) Second, creation is authenticated and rate-limited per user or API key, because an open create endpoint becomes a spam and phishing tool within days.

4 · The data model

The only hot query is "code → long URL", so the link table is keyed by the code:

links(
  code        CHAR(7) PRIMARY KEY,   -- or VARCHAR for custom aliases
  long_url    TEXT NOT NULL,
  owner_id    BIGINT,
  created_at  TIMESTAMP,
  expires_at  TIMESTAMP NULL,
  is_custom   BOOLEAN,
  status      SMALLINT              -- active / disabled / deleted
)
index on (owner_id, created_at)      -- "my links" page; not on the hot path

This is a pure key-value access pattern, so a relational database (Postgres, MySQL) or a key-value store (DynamoDB, Cassandra) both work. A relational database is fine at 40 writes per second and gives you a unique constraint for aliases; a managed key-value store gives you sharding and multi-region replication without operating it. Either is a defensible answer if you say why.

Clicks live elsewhere: an append-only event log, aggregated into a table like clicks_daily(code, day, country, count) in a columnar analytics store. Never put a click_count column on the link row. An update per click would turn the read-only redirect into a write, at 20,000 per second, concentrated on the most popular rows — the worst possible lock contention. Say that out loud: it is the first real design decision in the interview.

5 · High-level design and the critical path

The architecture in the primer has stateless redirect servers and API servers (stateless means any server can handle any request, so you add servers to add capacity), a cache, a sharded link store, an ID allocator and a click queue. Separating redirect servers from API servers is worth a sentence: the redirect fleet has one job, a different scaling curve and a stricter availability target, and a bug in the stats endpoint should never be able to take redirects down.

Walk the critical path — a redirect — step by step with numbers, using the sequence diagram below. The browser resolves sho.rt and connects to the nearest CDN edge (net12). If the edge has a cached redirect for this code, it answers in a few milliseconds and your servers never see the request. On an edge miss, the request reaches a redirect server, which asks Redis for the code (about half a millisecond inside a data centre). On a cache hit, it builds the redirect response, publishes a click event to the queue without waiting for an acknowledgement, and returns. On a cache miss, it reads the link store (a primary-key lookup, one to five milliseconds), writes the result into Redis with a TTL, and continues. A cache miss for an unknown code should also be cached briefly as "not found", so a bot scanning random codes cannot hammer the database.

The write path is short. The API server validates the URL (scheme is http or https, length under a limit, not on a blocklist), takes the next ID from its local block, turns it into a code (deep dive A), inserts the row, optionally writes it into the cache (so the first click after a big announcement is a hit), and returns. If the user supplied an alias, the server inserts with the alias as the key and relies on the primary-key uniqueness constraint to reject duplicates; a "check, then insert" sequence races when two users ask for spring-sale at the same instant.

6 · Deep dive A: generating the short code

This is what the question is actually about. Walk through the options, show why each weak one fails, and land on one.

Option 1: hash and truncate. Hash the long URL (MD5 gives 128 bits, SHA-256 gives 256) and take the first 7 base62 characters. Hashes are long, so truncation is mandatory, and truncation brings collisions: two different URLs whose hashes share the same first 7 characters. The birthday bound says how soon. Among n random values drawn from N possibilities, the expected number of colliding pairs is about n² ÷ 2N, so a collision becomes likely when n reaches roughly √N. For 7 characters, √(3.5 trillion) ≈ 1.9 million. A service creating 40 links per second passes that in under a day; after a year of 1.2 billion links, a new link has a 1.2 billion ÷ 3.5 trillion ≈ 1-in-2,900 chance of colliding. So every write must read the database first to check, and retry with a salt on a collision. It works, but it adds a read to every write and a retry loop, and it makes the same URL always produce the same code, which is wrong for campaigns.

Option 2: random codes. Generate 7 random base62 characters and insert with a uniqueness constraint, retrying on conflict. Same birthday maths, same per-write check (the insert itself is the check), and retries grow as the space fills. Workable at small scale.

Option 3: one database auto-increment counter, encoded in base62. No collisions by construction: every number is used once. Encoding is plain base conversion. To encode 1,000,000,000: divide by 62 repeatedly and keep the remainders. 1,000,000,000 = 62 × 16,129,032 remainder 16; 16,129,032 = 62 × 260,145 remainder 42; 260,145 = 62 × 4,195 remainder 55; 4,195 = 62 × 67 remainder 41; 67 = 62 × 1 remainder 5; 1 = 62 × 0 remainder 1. Reading the remainders from last to first gives 1, 5, 41, 55, 42, 16. With the alphabet 0-9a-zA-Z, 1 → 1, 5 → 5, 41 → F (36 is A), 55 → T, 42 → G, 16 → g: 15FTGg, padded to 015FTGg. Decoding multiplies back: ((((1×62+5)×62+41)×62+55)×62+42)×62+16 = 1,000,000,000. Two problems remain. A single counter is a coordination point — every create in every region waits on one database row — and a single point of failure. And the codes are sequential: if your link is 015FTGg, then 015FTGh is someone else's link, and anyone can enumerate the whole corpus.

Option 4 (the answer): counter ranges, permuted, then base62. A small ID allocator — a row in Postgres updated in a transaction, or a key in etcd or ZooKeeper — hands each API server a block of, say, one million consecutive numbers ("you own 41,000,000 to 41,999,999"). The server assigns numbers from its block in memory with no coordination at all, and asks for a new block when half the current one is used, so a slow allocator never blocks a write. If a server crashes, the unused part of its block is simply lost; losing even a thousand blocks a year is a billion numbers out of 3.5 trillion — irrelevant. Allocation load is tiny: at 40 creates per second, the whole fleet needs a new block about every seven hours.

To make codes unguessable, the server does not encode the raw number. It first passes it through a keyed permutation: a function that scrambles numbers using a secret key but is a bijection — every input maps to exactly one output and no two inputs share an output — so uniqueness is preserved. A small Feistel network does this (deep section explains how). With the lab's key, 41,000,000 becomes 1,443,535,562,791 (code ppGo6RV) and 41,000,001 becomes 1,037,662,089,729 (igEAnAd); nobody can predict a neighbour without the key. Then base62-encode the permuted number. The lab builds exactly this.

Why not just use a Snowflake ID, Twitter's coordination-free ID format? Snowflake packs 41 bits of millisecond timestamp, 10 bits of machine id and 12 bits of sequence into a 64-bit number, which avoids the allocator entirely. But a 63-bit number needs 11 base62 characters (6210 ≈ 8.4 × 1017 is too small for 263 ≈ 9.2 × 1018), and short is the whole point. Snowflake solves "unique and roughly time-sorted"; a shortener needs "unique and short", which a dense counter gives.

7 · Deep dive B: the redirect hot path and the 301/302 question

An HTTP redirect is a response with a 3xx status and a Location header; the browser then requests that URL. 301 Moved Permanently means "this address has moved for good"; 302 Found means "it is elsewhere for now". The common interview line is "use 302, because browsers cache 301 forever and you lose analytics". That is half right. Caching is controlled by the Cache-Control header (net7). A 301 sent without caching headers may be cached by browsers indefinitely, and then repeat clicks never reach you, your analytics undercount, and you can never change or delete that link for that user. But a 301 sent with Cache-Control: private, max-age=90 may be cached by the browser for only 90 seconds and not by shared caches (private).

You can check what real shorteners do. Requesting a Bitly link on 2 October 2026 returned HTTP/2 301 with cache-control: private, max-age=90; a TinyURL link returned 301 with cache-control: no-store, no-cache, must-revalidate. Both choose 301 — search engines (and SEO, search engine optimisation) treat a permanent redirect as passing the destination's ranking signals — and both control caching explicitly so they keep seeing clicks. So the senior answer is: the status code expresses meaning, the cache header expresses freshness, and you choose both. 302 (or 307, which also forbids changing the request method) is the simple safe choice; 301 with a short private max-age is what the market leaders ship.

The same header logic governs your own CDN. You may let the edge cache a redirect for a short time (seconds to minutes) using a CDN-specific header such as Surrogate-Control or CDN-Cache-Control that browsers ignore, so a viral link is answered at the edge while browsers still re-ask. Every cache layer you add is a place a deleted link survives, so each needs a bounded TTL and a purge path.

The rest of the hot path is cache sizing and hit ratio. With 10 GB of hot links in Redis and heavy skew, a hit ratio of 95% or better is realistic. At 20,000 redirects per second, a 95% hit ratio sends 1,000 reads per second to the link store; at 99%, only 200. Spread over 8 shards, even the worse case is 125 reads per second per shard — trivial for a primary-key lookup. Shard the link store by a hash of the code, because the only query is by code: every lookup goes to exactly one shard, and hashing spreads keys evenly. Do not shard by owner: one large customer would put all their links, and their traffic, on one shard.

8 · Deep dive C: click analytics without slowing the redirect

Clicks are the revenue, so they must not be lost, but they must never be on the critical path. The redirect server publishes an event — a record that something happened — to a durable queue or log and returns immediately. Bitly described exactly this: when a link is "decoded" into a redirect, the decode service publishes one event to NSQ, its open-source message queue, and separate services consume it — one archives to HDFS and S3, one powers real-time analytics, one builds longer-term history, one annotates. The producer knows nothing about the consumers, so adding a new one changes nothing on the redirect path.

The consumers do the expensive work. They drop bots and link-preview fetchers (chat apps and email scanners request links that no human clicked), enrich with country from the IP address and device from the user agent, and aggregate counts per link per hour or day into a columnar store, which is a database that stores each column together so "sum clicks by day" reads only the needed columns. Unique visitors are counted with HyperLogLog, a sketch that estimates distinct counts in about 12 KB with roughly 1% error, instead of storing every visitor id. The raw events are archived so a bug in aggregation can be fixed by reprocessing. If the queue is unavailable, the redirect server buffers a bounded number of events locally and drops the oldest beyond that — losing a few clicks is acceptable, failing a redirect is not.

9 · Bottlenecks, failure modes and trade-offs

Hot keys and stampedes. All requests for one code hit one cache key and, on a miss, one shard. When a viral link's cache entry expires, thousands of simultaneous misses can overload that shard and break every other link on it. Fixes: single-flight on miss (one request refills, others wait), refresh-ahead for hot keys, serve stale on error, and edge caching. The drill works this through with numbers.

Cache down. If Redis fails, 20,000 reads per second fall on the link store. Either size the store to survive that (8 shards at 2,500 reads per second each is plausible for primary-key lookups) or shed load and rely on the CDN while the cache recovers. Say which.

Allocator down. Servers keep using their current blocks; fetch the next block at 50% usage so there are hours of buffer. Run the allocator on a replicated store.

Deletes and expiry. Check expires_at and status on every redirect (return 410 Gone), run a background sweep, and on deletion purge the CDN and the cache. Write a tombstone rather than deleting the row, so a lagging replica cannot resurrect it.

Abuse. Shorteners are favourite tools for hiding phishing links. Check new URLs against a malicious-URL list (Google Safe Browsing is a common one), rate-limit creation, rescan destinations periodically (a harmless page can turn malicious later) and support fast takedown. Return 404 quickly for unknown codes and cache the negative result.

Multi-region. Serve redirects from every region's cache and replica; accept that a new link becomes readable in other regions after replication lag (usually under a second), and give each region its own ID blocks so regions never collide.

The trade-offs to name in the close: counter-plus-permutation over hashing (no read per write, but an allocator to run); 301-with-short-max-age versus 302 (SEO versus simplicity); edge caching of redirects (lower latency and cost versus slower deletion); a relational store versus a managed key-value store (constraints and familiarity versus built-in sharding and replication). Summarise in three sentences: ID blocks give coordination-free unique codes and a permutation makes them unguessable; the working set fits in memory so the database is off the hot path; analytics is asynchronous so a click never slows a redirect.

How a Feistel permutation makes a counter unguessable

A Feistel network splits a number into two halves, L and R, and runs a few rounds of: new L = R, new R = L XOR F(key, R), where F is any keyed function — for example the first bytes of an HMAC (a keyed hash) of R. XOR (exclusive or) of a value with the same thing twice gives the original back, so each round can be undone by anyone holding the key, even though F itself is not reversible. That makes the whole network a bijection on numbers of that bit width, for any choice of F. With 21-bit halves it permutes the 42-bit range 0 to 242−1 (about 4.4 trillion), slightly bigger than the 627 ≈ 3.5 trillion code space. To land inside the smaller range, use cycle walking: if the output is too large, apply the permutation again to that output, and repeat until it fits. Because a permutation's cycles return to the starting region, this always terminates (on average after about 1.25 steps here) and remains a bijection on the code space. Four rounds with a secret key are enough to defeat casual enumeration; this is not a cryptographic guarantee against a determined attacker who collects many codes, so links to truly sensitive resources still need authentication on the destination.

The birthday bound, precisely

For n uniformly random codes in a space of N, the probability of at least one collision is approximately 1 − e−n²/2N. It reaches 50% at n ≈ 1.18√N. For 7 base62 characters that is about 2.2 million codes; for 8 it is about 17 million. That is why "use a longer hash prefix" does not rescue hash-and-truncate at scale: you only move the problem by a square root. The lab measures it: 200,000 URLs hashed to 5 characters (916 million values) gave 19 collisions against a predicted 21.8. Interviewers like candidates who can produce this estimate in their head: n²/2N with n = 200,000 and N ≈ 9.2 × 108 gives 4 × 1010 / 1.8 × 109 ≈ 22.

Hot keys: why the average lies

Consider the drill's numbers: 20,000 redirects per second, 94% cache hit ratio, 8 shards. The 6% that miss is 1,200 per second, 150 per shard — comfortable. But traffic per key follows a heavy-tailed distribution, and the misses are not spread evenly in time. A link taking 8,000 requests per second lives on one shard; at the instant its cache entry expires, all 8,000 requests per second miss together. The cure is to make the miss cheap and rare for hot keys specifically: single-flight (also called request coalescing) lets the first missing request fetch while the rest wait on the same in-flight result, turning 8,000 database reads into one; refresh-ahead refreshes keys that are read near the end of their TTL; TTL jitter (adding a random few percent to each TTL) stops many keys written at the same moment from expiring at the same moment; and hot-key promotion moves keys above a request-rate threshold to the edge or replicates them across several cache nodes, so one key is no longer one machine's problem.

Custom aliases, Bloom filters and reserved namespaces

Aliases share the code key space, so they must not collide with generated codes now or in the future. Two clean rules: require aliases of 8 or more characters (generated codes are exactly 7), or require at least one character the generator never emits, such as a hyphen. Uniqueness among aliases is enforced by the primary-key constraint on insert. A Bloom filter — a bit array where each key sets a few bit positions chosen by hash functions — can sit in front of the "is this alias taken?" check on the create page. If any of the alias's bits is zero, the alias is definitely free; if all are one, it is probably taken and you check the database. False positives cost one extra lookup; false negatives cannot happen. At this write rate it is an optimisation, not a necessity, and saying so is better than presenting it as essential.

Why not just a managed key-value store?

DynamoDB, Bigtable or Cassandra with multi-region replication solve the link store's sharding, replication and failover, and at this access pattern (single-key reads and writes, no joins) they are a natural production choice. Say that — then list what you still build: the ID scheme (these stores have no global counter), the cache and edge layers (a single-digit-millisecond store is still slower and costlier per read than an in-memory cache or an edge hit), the analytics pipeline, deletion propagation across caches, and abuse handling. Distinguishing what a managed service removes from what it does not is a signal of seniority.

Moving the redirect to the edge

At ten times the scale, the next step is to answer most redirects without reaching your origin servers at all. Edge platforms offer small key-value stores replicated to every point of presence, and edge functions that can look up a code, return the redirect and emit a click event. Hot links are pushed to the edge store; the long tail falls through to the origin. The trade-off is consistency: edge key-value stores are typically eventually consistent, taking seconds to propagate a write, so a brand-new link or a takedown is briefly not visible everywhere. For new links you can fall through to origin on an edge miss; for takedowns you need a purge path and an origin-side check for the most sensitive cases.

Durability before acknowledgement

The create call must not return a short link until the row is durably stored — written to the primary and, ideally, to at least one replica (synchronous or semi-synchronous replication). If the primary fails after acknowledging but before replicating, the user prints a link that does not exist. This is a place where the shortener deliberately chooses consistency over latency, as Bitly put it: shortening is synchronous because they would rather return an error than a link that does not work.

The real case: Bitly's numbers and choices

Bitly's lead application developer, Sean O'Connor, described the production system in a 2014 talk summarised by High Scalability. The scale then: 6 billion clicks a month and 600 million shortens a month, about 2,300 redirects and 230 creates per second on average (6 × 109 ÷ 2.6 × 106 s and 6 × 108 ÷ 2.6 × 106 s). Note the ratio: 10 reads per write, not 100. Interview assumptions are just assumptions; a real service with many API users shortening links that are rarely clicked looks very different, and it pushes the design toward a faster write path and bigger code space (at 7.2 billion links a year, six characters would last under eight years).

The architecture choices match this lesson. Of about 400 servers, roughly 30 handled all external traffic — shortens, redirects, API and web — while the rest stored data and ran analytics, crawling and text processing: the redirect itself is cheap, and the analytics is where the hardware goes. Shortening was synchronous for speed and consistency: "don't want to give out the same shortened URL to multiple users; rather give an error than a link that doesn't work". Metrics were completely asynchronous: when a link is decoded into a redirect, an event goes onto a queue and is consumed independently by an archive service (HDFS and S3), real-time analytics, long-term history and annotation. Bitly built and open-sourced NSQ, the real-time message queue that carries these events. They also argued for events ("X happened") over commands ("do X") because the producer then needs no knowledge of its consumers.

The other public lesson is about permanence. Google stopped creating goo.gl links in 2018 and announced in July 2024 that all goo.gl links would return 404 after 25 August 2025, noting that more than 99% of them had no activity in the last month. After pushback about links embedded in "countless documents, videos, posts and more", Google updated the plan on 1 August 2025: only links that had shown no activity in late 2024 would be deactivated, and all others preserved. Two lessons: the skew is extreme (which is why a small cache works), and the promise of permanence outlives the business — design for codes that never need to be reused, and storage that is cheap enough to keep forever.

Failure modes you will see

Hot-shard brownouts. Symptom: redirect errors for an unrelated slice of links (one shard's worth) during a viral event. Cause: a hot key's cache miss storm. Seen in metrics as one shard's latency and CPU spiking while others are flat. Fix: single-flight, refresh-ahead, edge promotion.

Undercounted clicks. Symptom: customers' own analytics show more visits than yours. Causes: redirects cached too long in browsers or the CDN, or queue back-pressure dropping events. Watch the ratio of edge-served redirects to logged clicks, and queue depth and drop counters.

Inflated clicks. Symptom: a link shared in a chat app shows clicks seconds after posting with nobody reading it. Cause: link-preview bots and email security scanners following every link. Filter by known user agents, by the absence of follow-up behaviour, and by timing.

Zombie links after takedown. Symptom: a deleted phishing link still redirects for some users. Cause: a cache layer with a long TTL or no purge. Fix: bounded max-age everywhere, purge on delete, tombstones.

Domain-level blocking. If abusers use your shortener heavily, email providers and browsers start flagging the whole short domain, breaking every customer's links. Fight it with creation-time scanning, rate limits, periodic rescans and fast abuse response; many enterprises use their own branded short domain partly for this reason.

What to monitor

Redirect p50/p99 latency and error rate per region; cache hit ratio overall and for the top 1,000 keys; per-shard read rate and latency (skew shows here first); CDN offload ratio; ID allocator block consumption and time until the next block is needed; create rate, rejection rate and blocklist hits; click-queue depth, consumer lag and dropped events; and 404 rate on unknown codes, whose spikes usually mean someone is scanning.

Goal: build the code generator from deep dive A and see why it beats hashing. Python 3.12, standard library only, about 5 seconds to run.

"""Short codes three ways: base62 of a counter, a keyed permutation of the counter,
and hash-and-truncate. Python 3.12, standard library only."""
import hashlib, hmac

ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
SPACE = 62 ** 7                      # 3,521,614,606,208 seven-character codes

def encode(n: int, width: int = 7) -> str:
    out = []
    while n:
        n, r = divmod(n, 62)
        out.append(ALPHABET[r])
    return "".join(reversed(out)).rjust(width, "0")

def decode(code: str) -> int:
    n = 0
    for ch in code:
        n = n * 62 + ALPHABET.index(ch)
    return n

KEY = b"rotate-me-and-keep-me-secret"

def _round(half: int, i: int) -> int:
    mac = hmac.new(KEY, f"{i}:{half}".encode(), hashlib.sha256).digest()
    return int.from_bytes(mac[:3], "big")        # 21-bit halves fit in 3 bytes

def feistel42(x: int) -> int:
    """A bijection on 0..2**42-1: 4 rounds over two 21-bit halves."""
    left, right = x >> 21, x & (2**21 - 1)
    for i in range(4):
        left, right = right, left ^ (_round(right, i) & (2**21 - 1))
    return (left << 21) | right

def permute(n: int) -> int:
    """Cycle-walk: 2**42 > 62**7, so re-apply until we land inside the code space."""
    x = feistel42(n)
    while x >= SPACE:
        x = feistel42(x)
    return x

if __name__ == "__main__":
    print("space:", f"{SPACE:,}")
    for n in (0, 61, 62, 125, 3_844, 1_000_000_000):
        print(f"{n:>13,} -> {encode(n)}   round-trip ok: {decode(encode(n)) == n}")

    N = 200_000
    seq = [encode(n) for n in range(10_000_000, 10_000_000 + N)]
    perm = [encode(permute(n)) for n in range(10_000_000, 10_000_000 + N)]
    print("\nsequential:", seq[:3], " permuted:", perm[:3])
    print("collisions  sequential:", N - len(set(seq)), " permuted:", N - len(set(perm)))

    # Hash-and-truncate: first 5 base62 chars of SHA-256(url). 62**5 = 916,132,832 codes.
    urls = [f"https://example.com/item/{i}" for i in range(N)]
    trunc = [encode(int.from_bytes(hashlib.sha256(u.encode()).digest(), "big") % 62**5, 5)
             for u in urls]
    expected = N * (N - 1) / (2 * 62**5)
    print(f"hash-truncate to 5 chars: {N - len(set(trunc))} collisions "
          f"(birthday estimate {expected:.1f})")
  1. Save as shortcode.py and run python shortcode.py.
  2. Check the encode table: 61 → 000000Z and 62 → 0000010 show base62 "carrying" exactly like 9 → 10 in decimal, and 1,000,000,000 → 015FTGg matches the long division in the body.
  3. Compare sequential and permuted: consecutive counters give 000FXsk, 000FXsl, 000FXsm (enumerable) versus unrelated-looking codes, and both report 0 collisions for 200,000 ids, because a bijection cannot collide.
  4. Read the hash-truncate line: about 19-22 collisions among 200,000 URLs in a 916-million space, matching the birthday estimate n²/2N. Change the width to 7 and N to 62**7 in the last block: the estimate drops to about 0.006, but a production system with a billion links would expect about 142,000 collisions (1018 ÷ 7 × 1012).
  5. Change KEY and rerun: the permuted codes change completely, which is why the key must be stable and secret — rotate it and new links can collide with old ones unless you also switch to a fresh counter range.
Work it out

Your shortener serves 20,000 redirects/s at peak. Redis holds 20M hot links and has a 94% hit rate. The database is 8 shards, each handling 1,500 reads/s comfortably. A campaign link goes viral: it alone takes 8,000 requests/s.

(a) What database load do you see normally? (b) What happens when the viral link's cache entry expires? (c) What do you change?

Answer

(a) Normal load. 6% of 20,000 = 1,200 reads/s reaching the database, spread over 8 shards = 150/s each. Comfortably within budget; the cache is doing its job.

(b) The expiry. The viral link lives on exactly one shard. When its cache entry expires, the 8,000 requests/s for that one code all miss simultaneously and land on a single shard that can take 1,500/s. That shard is now at 5× capacity, so it queues, then times out — and because it also serves a 1/8 slice of everything else, 12.5% of all links in the system stop resolving because one link went viral. This is a cache stampede turning into a hot-shard failure.

(c) The fixes, in order:

  • Single-flight on cache miss. The first request to miss takes a short lock and refills; the others wait a few milliseconds for it rather than each querying the database. This alone turns 8,000 database queries into 1. It is the single highest-value change and should be your first answer.
  • Do not let hot keys expire on a timer. Refresh-ahead: when a key is read and its TTL is nearly up, refresh it asynchronously while still serving the old value. Popular links then never have a miss window at all.
  • Serve stale on error. If the database is unavailable or slow, return the last known value rather than failing. For a redirect this is almost always correct — an out-of-date destination beats a broken link.
  • Push the hottest links to the CDN. A link taking 8,000 rps should be served as an edge-cached redirect and never reach your origin. Promote keys above a rate threshold automatically.

The lesson to state: a 94% hit rate sounds excellent and tells you almost nothing, because cache performance under skew is decided by what happens to the hot keys, not by the average. The failure here was not insufficient cache capacity — it was the absence of a policy for the miss.

Estimate it

A client tells you they will shorten 600 million links a month (Bitly's 2014 volume) and each link averages 10 clicks. Should codes be 6 or 7 characters, how many redirects per second must you serve, and how much click data will you store per year at 200 bytes per event?

Answer

Code length. 600M × 12 = 7.2 billion links a year. 626 ≈ 56.8 billion lasts 56.8 ÷ 7.2 ≈ 7.9 years — too short for permanent codes. 627 ≈ 3.52 trillion lasts about 489 years. Choose 7.

Redirects. 600M × 10 = 6 billion clicks a month ÷ 2.6M seconds ≈ 2,300/s average, about 11,500/s at a 5× peak. Creates: 600M ÷ 2.6M ≈ 230/s, peak ~1,150/s — still easy, but now worth an ID scheme with no per-write read.

Click data. 6 billion × 12 months × 200 B = 14.4 TB per year of raw events, before replication. Aggregates per link per day are far smaller; keep raw events in cheap object storage for reprocessing.

What to say: the read:write ratio here is 10:1, not the 100:1 textbook figure, so the write path deserves more attention than usual — which is exactly why Bitly kept shortening synchronous and spent its hardware on analytics.
