It is 02:13 and the on-call engineer for a payments API is paged: latency on every endpoint has tripled. The cause, found twenty minutes later, is a single customer whose nightly reconciliation script has a bug — it retries every failed call immediately, forever, from 400 threads. That one customer is now sending 30,000 requests per second, and the database behind the API is spending its time on them while every other customer times out. There is a rate limit of 100 requests per second per API key, written into the gateway years ago. It is enforced separately on each of 60 gateway machines, so the customer is actually allowed 6,000 per second. And the counters reset at the top of every second, so even that is exceeded in bursts.

A rate limiter exists so that one client, by accident or on purpose, cannot consume capacity that belongs to everyone. Inside one process it is a small algorithm — a counter or a bucket of tokens — and the low-level design case ld2 builds those. The problem changes completely when the limit must hold across a fleet: dozens or hundreds of gateway nodes in several regions, each seeing a slice of each client's traffic, all needing to agree on one count, within a millisecond, for every single request, without the limiter itself becoming the thing that takes the API down.

That is a distributed systems problem in miniature. Shared counters invite races. A central store adds a network hop and a dependency. Local counters are fast but disagree. Regions are 100 ms apart. Clocks differ. And the limiter must decide what to do when its own store is unreachable — allow everything, or reject everything — which is a business decision dressed as a technical one.

This lesson works through the design in interview order: requirements; estimates (decisions per second, store sizing, memory per algorithm, latency budget); the API and rule model; the high-level design and the critical path of one check; then three deep dives. The first replays fixed window, sliding log, sliding counter and token bucket on the same request trace, so their differences are concrete. The second is the race in a naive Redis INCR + EXPIRE and the atomic Lua fix. The third is local versus global limits, multi-region limits, and fail-open versus fail-closed. The real cases are Stripe's account of its four limiters and Cloudflare's per-data-centre counting; the lab replays all four algorithms on one trace and reproduces the check-then-act race.

The mental model: one club, many doors, one clicker

Picture a nightclub with a fire limit of 300 people. With one door and one bouncer holding a clicker, enforcing it is trivial: click in, click out, stop at 300. Now the club opens six doors to handle the queue. Each bouncer has a clicker, and each sees only the people at their door. If each stops at 50 (300 ÷ 6), the limit holds — until one door gets twice the queue of the others and turns people away while the club is half empty. If each bouncer radios the others before letting anyone in, the count is right, but every entry waits for a radio call, and if the radio dies, nobody knows what to do. The compromises are the interesting part: bouncers report their counts every minute; or the manager hands each bouncer a strip of 20 wristbands, and they come back for more when they run out.

Every piece of that maps onto the design. The doors are gateway nodes behind a load balancer. The clicker is a counter or token bucket per client key. The radio is a call to a shared store (Redis is the usual choice). Reporting every minute is periodic synchronisation; the strip of wristbands is a token lease. The question of what to do when the radio fails is fail-open versus fail-closed.

The analogy breaks in two useful places. A club has one fire limit; an API has many overlapping limits per request — per API key, per endpoint, per IP address, per organisation — all checked together. And a person is one unit, while requests differ hugely in cost: a cheap read, an expensive search, an LLM call generating 4,000 tokens. The limiter has to count in the right units.

What the service actually does

Strip away the algorithms and a rate limiter service answers one question per request: given these descriptors (who is calling, what they are calling) and this cost, allow or reject — and if rejecting, when should they retry? The answer must come back in about a millisecond, because it sits on the path of every request. It must be correct enough that a misbehaving client is actually stopped, and cheap enough that checking does not cost more than the requests it protects. And it must degrade gracefully, because a limiter that fails by rejecting everything is an outage you built yourself.

Where the limiter lives

You can put the limiting logic in three places, and an interviewer will ask why you chose one. In the client library: cheap, but you do not control clients. In the gateway or sidecar in front of services (sc2): every request passes through it, it knows the API key after authentication, and it can reject before any backend work happens — the usual answer. Or as a separate rate-limit service that gateways call over the network (Envoy's global rate limit service works this way): rules and logic are centralised, at the cost of one more network hop. A common compromise is a thin limiter client library inside the gateway that talks directly to Redis, with rules pushed from a central service — the shape drawn above.

1 · Requirements

Functional. (1) Define rules: a limit (for example 100 requests per second, or 1,000 per minute) on a combination of descriptors — API key, organisation, endpoint, IP address, user tier. (2) For each request, check all matching rules with a cost (default 1) and return allow or reject, the remaining allowance and the time until reset. (3) Return HTTP 429 Too Many Requests with a Retry-After header on rejection, and rate-limit headers on every response. (4) Change rules at runtime without deploys, including shadow mode (log what would be rejected without rejecting). (5) Expose metrics: decisions per rule and key, top limited keys. Out of scope, said aloud: billing-grade monthly quotas (which need durable exact counting — mention it as a separate system), DDoS mitigation at the network layer (net14), and bot detection.

Non-functional. Added latency under about 1 ms at p50 and 2-5 ms at p99. Accuracy: within a few percent of the configured limit; small overshoot is acceptable, systematic under-admission of good clients is not. Availability: the limiter must never be the reason the API is down. Scale: hundreds of thousands to millions of decisions per second across regions. Fairness: one client cannot consume another's allowance.

Clarifying questions. What is being protected — capacity (so approximate is fine) or money (so be strict)? Are limits per second, per minute, per day? Does the limit need to be global across regions, or per region? Do requests have different costs (an LLM call counts tokens)? What should happen if the limiter's store is down? The answers pick the algorithm and the failure policy.

2 · Back-of-envelope estimates

Assume an API platform with 500,000 requests per second at peak across 3 regions, 10 million active API keys, and 3 rules checked per request (per key per second, per key per endpoint per minute, per IP per minute).

Checks per second. 500,000 × 3 = 1.5 million rule evaluations per second. If all three rules for a request are evaluated in one call to the store (possible when their keys live on the same shard, explained below), that is 500,000 store calls per second.

Store throughput. Redis executes commands on one thread per shard; a small Lua script doing a few hash reads and writes takes on the order of tens of microseconds. Plan conservatively for 50,000 script calls per second per shard: 500,000 ÷ 50,000 = 10 primaries worldwide, 15-20 with 50% headroom, each with a replica. Per region, the busiest might carry 40% of traffic: 200,000 calls per second, 6-8 primaries.

Memory, by algorithm. A token bucket needs two numbers per key and rule (tokens, last refill time); stored as a small Redis hash with its key name and overhead, about 100 bytes. 10M keys × 3 rules × 100 B = 3 GB. A fixed window or sliding-window counter is similar (one or two counters). A sliding-window log stores one entry per accepted request in the window: at a limit of 1,000 per minute, a busy key has up to 1,000 sorted-set entries at roughly 64 bytes each — 64 KB per key. If even 1 million keys were near their limits, that is 64 GB for one rule, and 10 million would be 640 GB. That single estimate is why logs are reserved for low limits.

Latency budget. If the API's p99 target is 200 ms, the limiter can have 2-5 ms of it. An in-region round trip to Redis is roughly 0.2-1 ms, which fits. A cross-region round trip is 50-150 ms, which does not: global limits cannot be checked synchronously across regions on every request. The estimate decides a later deep dive.

Bandwidth. A check request and reply are a few hundred bytes: 500,000 × 300 B = 150 MB/s spread across gateways and shards — not a constraint.

3 · The API

Two APIs: the internal check API the gateway uses, and what the end client sees.

POST /v1/ratelimit/check                      (internal; usually gRPC)
  {domain: "public_api",
   descriptors: [{api_key: "k_123"}, {api_key: "k_123", route: "/v1/search"}, {ip: "203.0.113.7"}],
   cost: 1}
  → {decision: "OVER_LIMIT",
     statuses: [{rule: "key_per_sec",  limit: 100,  remaining: 0,  reset_after_ms: 400},
                {rule: "key_route_min", limit: 1000, remaining: 212, reset_after_ms: 31000},
                {rule: "ip_per_min",   limit: 600,  remaining: 590, reset_after_ms: 52000}]}

Client response on rejection:
  HTTP/1.1 429 Too Many Requests
  Retry-After: 1
  RateLimit-Limit: 100
  RateLimit-Remaining: 0
  RateLimit-Reset: 1
  {"error": {"type": "rate_limit_error", "message": "100 requests/second per API key exceeded"}}

A request is allowed only if every matching rule allows it, and a rejected request should not consume allowance from the rules that would have allowed it — a detail the multi-rule script in deep dive B handles by deciding every rule before spending from any. 429 is defined in RFC 6585; the RateLimit-* header names come from an IETF draft, and many APIs still use their own X-RateLimit-* names. The point is that clients can see their remaining budget and slow down before they hit the wall.

4 · The data model

rules (config store, versioned, pushed to gateways):
  {id: "key_per_sec", domain: "public_api", match: {api_key: "*"},
   algorithm: "token_bucket", capacity: 100, refill_per_sec: 100,
   shadow: false, fail_mode: "open"}
  {id: "login_per_ip", match: {route: "/login", ip: "*"},
   algorithm: "sliding_counter", limit: 10, window_s: 60, fail_mode: "closed"}

counters (Redis, sharded by hash tag, all with TTLs):
  rl:{k_123}:key_per_sec          → hash {tokens: 37.5, ts: 1767000000.123}
  rl:{k_123}:key_route_min:/v1/search:29450000 → integer (current window count)
  rl:{ip:203.0.113.7}:ip_per_min:29450000      → integer

The braces are a Redis Cluster hash tag: only the part inside {…} is hashed to pick a shard, so every counter for API key k_123 lands on the same shard and one script can read and update them together. The IP rule has a different tag and may live elsewhere, so in practice per-key rules are batched into one call and the IP rule is a second call (or is enforced locally). Every counter carries a TTL (time to live: an expiry after which Redis deletes the key) so idle keys disappear; nothing about a rate limit needs to live longer than its window.

5 · High-level design and the critical path

One request, step by step: (1) The load balancer sends it to any gateway node. (2) The gateway authenticates it and extracts descriptors (API key, route, client IP). (3) It matches descriptors against its cached rules — a pure in-memory step. (4) For the key's rules, it calls the Redis shard owning {k_123} with one Lua script, passing each rule's parameters and the cost. The script reads the counters, refills or slides them, decides for all rules, and only if all allow, spends from all of them; it returns the decision and remaining counts. (5) The gateway adds rate-limit headers and either forwards the request or returns 429. (6) It emits a decision metric asynchronously. Total added latency: one in-region round trip plus microseconds of script time.

Around this path sit the rules service (stores rule versions, validates them, pushes them to gateways, supports shadow mode and gradual rollout) and observability (which keys are being limited, by which rule, and how often the limiter failed open). The limiter client in each gateway also holds a local token bucket per key as a coarse backstop for when Redis is slow or unreachable.

6 · Deep dive A: four algorithms on one request trace

ld2 builds the four algorithms inside one process. Here the point is to see how differently they behave on the same traffic, because choosing between them is a product decision. The rule is 4 requests per 10 seconds. A single client sends 12 requests at t = 1, 6, 8, 9, 9.5, 10.5, 11, 12, 14, 17, 19 and 23 seconds. For the windows, "window 0" is [0, 10), "window 1" is [10, 20) and "window 2" is [20, 30).

Fixed window. Count accepted requests per window; reject when the window's count has reached 4. Window 0 accepts t = 1, 6, 8, 9 and rejects 9.5. At t = 10 the count resets: 10.5, 11, 12 and 14 are accepted, then 17 and 19 rejected. Window 2 accepts 23. Total accepted: 9. Look at the 8 seconds from t = 6 to t = 14: 7 requests got through against a limit of 4 per 10 s — nearly twice the limit, because the boundary at t = 10 wiped the count. That is the fixed window's defining flaw.

Sliding-window log. Keep the timestamp of each accepted request; a new request is allowed if fewer than 4 accepted timestamps fall in the trailing 10 seconds (t − 10, t]. At t = 9.5 the log holds 1, 6, 8, 9 → reject. At 10.5 the window is (0.5, 10.5], still 4 → reject. At 11 the window (1, 11] has dropped t = 1 → 3 → accept. At 12 and 14: 6, 8, 9, 11 → reject. At 17: (7, 17] holds 8, 9, 11 → accept. At 19: (9, 19] holds 11, 17 → accept (9 has just left). At 23: accept. Total 8, and no 10-second span ever holds more than 4. Exact — at the price of storing every timestamp.

Sliding-window counter. Keep only the counts for the current and previous fixed windows, and estimate the trailing-window count as previous × (fraction of the previous window still inside the trailing window) + current, assuming the previous window's requests were evenly spread. Allow if the estimate plus this request's cost is at most 4. At t = 10.5: previous = 4, 0.5 s into window 1 so 95% of the previous window overlaps: 4 × 0.95 + 0 = 3.8; 3.8 + 1 = 4.8 > 4 → reject. At 11: 3.6 → reject; at 12: 3.2 → reject. At 14: 4 × 0.6 = 2.4 → accept (current becomes 1). At 17: 4 × 0.3 + 1 = 2.2 → accept. At 19: 0.4 + 2 = 2.4 → accept. At 23 (window 2, previous = 3): 3 × 0.7 = 2.1 → accept. Total 8 — the same count as the exact log, from two numbers. It differs in which requests pass: it rejected 11 (which the log allowed) and allowed 14 (which the log rejected), because its "evenly spread" assumption is wrong for a window whose four requests were bunched at the end. Cloudflare measured this approximation on 400 million requests and found 0.003% wrongly allowed or limited.

Token bucket. Capacity 4 tokens, refilled at 0.4 tokens per second (4 per 10 s — the same long-run rate), starting full. Each request needs 1 token. t = 1: 4 → 3. t = 6: 3 + 5 × 0.4 = 5, capped at 4 → 3. t = 8: 3.8 → 2.8. t = 9: 3.2 → 2.2. t = 9.5: 2.4 → 1.4 (accepted — the bucket still holds part of its burst allowance). t = 10.5: 1.8 → 0.8. t = 11: 1.0 → 0. t = 12: 0.4 → reject. t = 14: 1.2 → 0.2. t = 17: 1.4 → 0.4. t = 19: 1.2 → 0.2. t = 23: 1.8 → 0.8. Total 11. The bucket is the most permissive here because it expresses "4 per 10 s" as "a burst of 4, then 0.4 per second", which lets through anything not faster than the drip once the burst is spent. Over a long run its average still converges to 0.4 per second.

The choice is about what the limit means to the customer. "No more than 1,000 per minute, ever" is a sliding window. "Up to 100 per second sustained, with short bursts allowed" is a token bucket, and it is what most public APIs advertise (Stripe's request-rate limiter is a token bucket; Anthropic's API documents its limits as token buckets). Fixed windows survive where counts must line up with calendar periods.

7 · Deep dive B: shared counters and the race

The naive version. Each gateway does: count = GET key; if count < limit, INCR key and allow; else reject. Every individual Redis command is atomic, but this is two commands with a decision between them. Suppose the limit is 100 and the count is 99. Gateways A and B each receive a request at the same moment. A runs GET → 99. B runs GET → 99. Both decide "under the limit". A runs INCR → 100. B runs INCR → 101. Both requests are allowed. With 50 gateways all receiving requests for a key that is at its limit during a burst, the overshoot can be tens of requests per window. This is the check-then-act race (os4) in a distributed costume.

A better order, and a new race. INCR returns the new value atomically, so "INCR first, then compare" removes the first race: A gets 100 (allowed), B gets 101 (rejected). For a fixed window, the key also needs an expiry so it resets. The Redis documentation's own example does exactly this: INCR key; if the result is 1 (the key was just created), EXPIRE key 1. And it flags the race: if the client crashes, times out or is killed after the INCR but before the EXPIRE, the key exists without an expiry. It never resets. Its count grows past the limit and stays there, and that user is rejected forever — until someone deletes the key by hand. Under load, with timeouts and deploys killing gateway processes mid-request, "rare" happens daily across a fleet.

The atomic fix: one Lua script. Redis runs a Lua script to completion without running any other command in between; its documentation describes the guarantee as all of the script's effects having either not yet happened or already happened. So read, decide and write become one indivisible step, in one network round trip:

-- fixed window: KEYS[1] = counter key, ARGV[1] = limit, ARGV[2] = window seconds
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end
if n > tonumber(ARGV[1]) then return 0 end
return 1

A token bucket needs real decision logic — refill by elapsed time, compare, spend — so a script is the natural home for it:

-- token bucket: KEYS[1] = bucket key; ARGV = capacity, refill_per_sec, cost
local cap, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local t = redis.call('TIME')                          -- the store's clock, not the gateway's
local now = tonumber(t[1]) + tonumber(t[2]) / 1e6
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap                  -- missing key = full bucket
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + math.max(0, now - ts) * rate)
local allowed = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))  -- idle until full = forget
return {allowed, tostring(tokens)}

Three details carry the design. The clock comes from Redis's TIME, so every decision for one key uses one timeline; if each gateway passed its own time, a node whose clock ran 200 ms fast would refill buckets early, and the math.max(0, …) guard exists because time can still step backwards after a failover. (Older Redis versions re-ran scripts on replicas, which made reading the clock unsafe; Redis switched to replicating a script's effects by default in 5.0 and exclusively in 7.0.) The expiry is the time to refill from empty to full: after that, a missing key and a full bucket are the same thing, so forgetting it is free. The return value includes the remaining tokens so the gateway can fill rate-limit headers.

Multiple rules in one call. To check "per key per second" and "per key per endpoint per minute" together, the script takes several keys, computes every rule's decision first, and spends from all only if all allow. Redis Cluster requires every key a script touches to be in the same slot, which is what the {k_123} hash tag guarantees.

Without scripts. If scripts are not available (some managed caches restrict them), make each step individually safe: SET key 0 EX 60 NX creates the counter with its expiry in one atomic command if it does not exist, and a following INCR can no longer leak an expiry-less key. Memcache-based designs like Cloudflare's rely on atomic increments on keys that already include the window number, and let the cache's own eviction and expiry clean up.

8 · Deep dive C: local versus global, regions, and failure policy

Purely local. Each gateway enforces limit ÷ N with an in-memory bucket. Zero added latency, no dependency. The problems: (1) uneven traffic — a client using one long-lived HTTP/2 connection lands all its requests on one node and gets only 1/N of its limit; (2) fleet changes — when autoscaling moves N from 20 to 40, every client's effective limit silently halves unless every node learns the new N; (3) burst overshoot — a client spread across all nodes can spend each node's full burst capacity simultaneously.

Purely central. Every check is a round trip to the shard owning the key: accurate (within the algorithm's own approximation), about 0.5 ms in-region, and a dependency on every request. This is what Stripe describes: token buckets in a central Redis.

Hybrids, with the overshoot computed. Periodic sync: each node counts locally and every 100 ms pushes its delta to Redis and pulls the global count. Between syncs, each node decides on stale information. Worked bound: limit 1,000 per minute for a key, 20 nodes, and the key has 50 requests of allowance left. If the client suddenly sends to all 20 nodes, each node believes 50 remain and can allow up to 50 before the next sync — up to 1,000 admitted against 50, a large overshoot for an abusive client. The fix is to give each node only a share: allow at most remaining ÷ N per interval, which over-restricts clients concentrated on one node. Token leasing: a node takes a lease of tokens from the central bucket (say 10% of remaining, at least 1) and spends them locally, returning to Redis only when the lease runs out. Overshoot is bounded by the outstanding leases; round trips drop by the lease size; unused leases are returned or expire. This is the "strip of wristbands" from the primer, and it is the usual answer for very high-rate keys.

Multiple regions. The estimate already ruled out a synchronous cross-region call per request. Three workable designs: (1) Per-region limits. Split the global limit by each region's traffic share (a customer with 60% of traffic in us-east gets 60% of the limit there); simple and common, but wrong when a client's traffic shifts regions. (2) Local enforcement, asynchronous reconciliation. Each region counts locally and broadcasts its counts every second or so; each region enforces against local count plus the last-known remote counts. The overshoot is bounded by the client's rate in other regions times the sync delay: at 300 requests per second in each of three regions and a 1-second delay, up to 600 extra. Counters that only grow within a window merge cleanly across regions (sum the per-region counts), which is the idea behind a grow-only counter, one of the simplest CRDTs (conflict-free replicated data types: structures whose copies can be merged in any order and still agree). (3) Route the client to one place. Cloudflare relies on anycast sending traffic from one IP address to the same data centre under normal conditions, so it counts per data centre and never needs a global counter; the trade-off it accepts is that a client whose traffic is split across locations is counted separately in each.

Fail-open versus fail-closed. When Redis is slow or unreachable, the limiter must decide without its data. Fail open means allow; fail closed means reject. For general API limits, failing closed turns a limiter outage into a total API outage; Stripe states it fails open and accepts that rate limiting is briefly not enforced. The mature version is fail open with a backstop: when the store is unavailable, each gateway falls back to its local bucket at limit ÷ N (or somewhat higher), so a flood is still bounded. For limits whose purpose is to stop abuse that costs real money or security — login attempts (credential stuffing), SMS or email sends (toll fraud), payouts — fail closed, or fall back to a strict local limit. Whatever the policy, the limiter call needs a hard timeout (2-5 ms) and a circuit breaker (sc12), because a limiter that waits 30 seconds for a dead Redis is worse than either policy. Make the policy per rule, as in the data model's fail_mode, and emit a metric for every fallback decision.

9 · Bottlenecks, failure modes and trade-offs

Hot keys. One customer at 100,000 requests per second puts all its checks on one Redis shard. Options: split its counter into k sub-keys with different hash tags, each holding limit ÷ k, and pick a sub-key at random per request; or give that customer leased tokens so most checks are local.

Failover resets. Redis replication is asynchronous; when a primary fails, the replica may be a few milliseconds to seconds behind, so some counters reset or step back. For rate limiting, a brief over-admission after a failover is acceptable — another reason not to use this system for billing-grade quotas, which need durable, exactly-once counting.

Retry storms. Rejected clients that retry immediately multiply the load the limiter sees and keep themselves rejected. Return Retry-After, document backoff with jitter, and consider charging rejected requests a small cost so tight retry loops stay limited.

Rule mistakes. A rule with limit 0, or one whose match pattern accidentally covers every key, is an instant self-inflicted outage. Validate rules, roll them out in shadow mode first, then to a fraction of keys, and keep rollback one click away.

The limiter as a dependency. Each gateway call to Redis is another thing that can be slow. Keep connections pooled, scripts loaded (call by SHA, reload on the "no such script" error after failover), and the timeout tight.

Trade-offs to close on. Accuracy versus latency (central versus local versus leased); exactness versus memory (log versus counters); bursts versus smoothness (token bucket versus sliding window); availability versus protection (fail-open versus fail-closed, chosen per rule); global versus regional (synchronous checks are too slow, so global limits are approximations).

Stripe's four limiters: rate limiting is one of several layers

Stripe's write-up separates four mechanisms, and the separation is the lesson. A request rate limiter caps each user's requests per second (with bursts allowed) and fires constantly — Stripe says it rejected millions of requests in a month. A concurrent requests limiter caps how many requests a user has in flight (their example is 20), which catches clients hammering expensive endpoints; it fired about 12,000 times in a month. A fleet usage load shedder reserves a share of capacity for critical requests — with a 20% reservation, non-critical traffic above its 80% allocation is rejected. And a worker utilisation load shedder sheds traffic by priority tier when workers are overloaded; it rejected about 100 requests in the month. The first two are per-client fairness; the last two protect the service as a whole regardless of who is sending. An interview answer that only has the first is incomplete.

Concurrency limiting done safely

A counter of in-flight requests (INCR at start, DECR at finish) leaks forever when a request's process dies between the two. The robust form stores request ids: a sorted set per client with each in-flight request's id scored by its start time. On start, a script removes members older than the maximum request duration (cleaning up crashed requests), checks the set's size against the limit, and adds the new id if allowed; on finish, it removes the id. The timeout-based cleanup turns a leak into a bounded delay.

GCRA: one number per key

The generic cell rate algorithm stores, per key, a single timestamp: the "theoretical arrival time" (TAT) of the next request if the client sent at exactly the allowed rate. For a rate of one request per T seconds and a burst tolerance τ, a request at time t is allowed if t ≥ TAT − τ; if allowed, TAT becomes max(TAT, t) + T. It makes the same decisions as a token bucket but needs one value and one comparison, which makes it cheap in a script and easy to expire. ld2 derives it in detail.

Counting in the right unit: tokens for LLM APIs

For an LLM API a request is the wrong unit: one call may process 200 tokens, the next 200,000, and GPU cost scales with tokens. Providers limit requests per minute and tokens per minute, often input and output separately. The difficulty is that output tokens are unknown when the request is admitted. Anthropic's documentation describes one concrete answer: limits on requests, input tokens and output tokens per minute, implemented as token buckets; input tokens estimated at the start of a request and adjusted to the actual count; output tokens counted in real time as they are produced, so the max_tokens parameter does not count against the limit; and, for most models, input tokens read from the prompt cache not counted at all. In a design you build, the general pattern is reserve, then reconcile: charge what you know at admission (input tokens from the tokenizer, plus perhaps an estimate of output), stream the response while charging output as it is generated, and refund or charge the difference at the end. The limiter's script takes a cost argument precisely so this works.

Priorities and fairness inside a limit

Not all requests from one customer are equal: a checkout call matters more than an analytics export. Tiered buckets — separate allowances per priority, or a shared bucket where low-priority requests must leave a reserve of tokens untouched — let a customer's critical traffic keep flowing while their batch jobs are throttled. Across customers, weighted fair sharing of a common capacity (each tenant gets a share proportional to its plan, unused share is lent out) is the multi-tenant version, and is how GPU capacity is often divided on shared inference platforms.

Quotas are a different system

"10 million requests per month, then billing stops you" sounds like a rate limit with a long window, but its requirements are opposite: it must be durable (a Redis failover must not reset a month's usage), exact enough to bill, and auditable. Build it as an append-only usage log aggregated into a database, checked asynchronously with a small allowance of overage, and keep the per-second rate limiter as the fast, approximate, forgetful system it should be.

Adaptive limits

Static limits are guesses. Adaptive systems change the admitted rate from feedback: when backend latency or error rates rise, lower the global admission rate (the way TCP's congestion control backs off), and raise it slowly when healthy. Per-client limits then protect fairness, while the adaptive limit protects the service. The risk is oscillation, so changes are damped and bounded.

The real cases: Stripe and Cloudflare

Stripe (Paul Tarjan, "Scaling your API with rate limiters", 2017) describes the four limiters above, implemented with the token bucket algorithm on a centralised Redis (or ElastiCache) store. Three operational choices stand out. It fails open: if Redis is unavailable, requests continue, because the limiter should never be the cause of an outage. It dark-launches every limiter, watching the traffic it would have blocked before enforcing. And it returns 429 for rate limiting and 503 for load shedding, so clients can tell "you are sending too much" from "we are overloaded". The write-up also makes the case that rate limiting is a reliability feature for the provider, not a punishment for clients: the request-rate limiter fires constantly, and that is it working.

Cloudflare ("How we built rate limiting capable of scaling to millions of domains", 2017) faced a different scale: limits configured by millions of customers on traffic arriving at data centres worldwide. Two decisions made it tractable. First, count per data centre: anycast routing normally sends one client IP to the same location, so a per-location counter sees all of that client's traffic, avoiding cross-location coordination and its latency; counters live in a memcache cluster (behind Twemproxy) in each location. Second, the sliding-window counter: two numbers per counter, updated with atomic increments and no transactions. Its worked example — 42 requests in the previous minute, 18 so far in the current one, 15 seconds in — estimates 42 × 0.75 + 18 = 49.5 requests against a limit of 50. Measured on 400 million requests from 270,000 sources, only 0.003% were wrongly allowed or limited, with an average 6% difference between the real and approximate rates.

Put side by side, the two cases show the axis interviewers want you to reason along: Stripe needs per-customer correctness across a fleet in a few regions and centralises in Redis; Cloudflare needs global scale and pushes counting to the edge, trading cross-location accuracy for latency and availability.

Failure modes you will see

The permanently blocked user. Symptom: one key rejected forever after a deploy. Cause: a counter created without an expiry (the INCR-then-EXPIRE race). Detection: alert on limiter keys with no TTL (TTL key returns −1). Fix: atomic scripts, plus a sweeper for the existing bad keys.

Silent fail-open. Symptom: an abusive client is not limited during an incident. Cause: Redis timeouts triggering fail-open without anyone noticing. Detection: a metric and alert on fallback decisions.

Limits halving after autoscaling. Symptom: customers complain of 429s at half their contracted rate. Cause: local limits computed as limit ÷ N with a stale or new N. Fix: central counting, or nodes that learn N from the fleet registry.

Hot shard. Symptom: p99 limiter latency rises on one Redis shard. Cause: one large customer or a scraping IP. Fix: split the key or lease tokens.

What to monitor

Decisions per second by rule and outcome; top limited keys; limiter call latency (p50/p99) and timeout rate; fallback (fail-open/closed) decisions; Redis CPU and memory per shard; keys without TTL; shadow-mode would-reject counts before every rule rollout; and, from the client side, 429 rate per customer, since a sudden rise usually means a client bug, not an attack.

Goal: replay the four algorithms on the lesson's request trace, then reproduce the check-then-act race with threads and fix it with an atomic step. Python 3.12 standard library, a few seconds.

"""Four rate limiters on one trace, then the GET-then-INCR race vs an atomic check."""
import threading, time

LIMIT, WIN = 4, 10.0
TRACE = [1, 6, 8, 9, 9.5, 10.5, 11, 12, 14, 17, 19, 23]

def fixed(ts):
    counts, out = {}, []
    for t in ts:
        w = int(t // WIN); ok = counts.get(w, 0) < LIMIT
        if ok: counts[w] = counts.get(w, 0) + 1
        out.append(ok)
    return out

def sliding_log(ts):
    log, out = [], []
    for t in ts:
        log = [a for a in log if a > t - WIN]; ok = len(log) < LIMIT
        if ok: log.append(t)
        out.append(ok)
    return out

def sliding_counter(ts):
    counts, out = {}, []
    for t in ts:
        w = int(t // WIN)
        est = counts.get(w - 1, 0) * (WIN - (t - w * WIN)) / WIN + counts.get(w, 0)
        ok = est + 1 <= LIMIT
        if ok: counts[w] = counts.get(w, 0) + 1
        out.append(ok)
    return out

def token_bucket(ts, cap=4, rate=0.4):
    tokens, last, out = cap, 0.0, []
    for t in ts:
        tokens = min(cap, tokens + (t - last) * rate); last = t
        ok = tokens >= 1 - 1e-9                       # tolerate float rounding
        if ok: tokens -= 1
        out.append(ok)
    return out

for fn in (fixed, sliding_log, sliding_counter, token_bucket):
    res = fn(TRACE)
    print(f"{fn.__name__:>16}: " + " ".join("✓" if r else "✗" for r in res) + f"  ({sum(res)} allowed)")

# --- the race: 50 gateways, one key at its last 10 units of allowance -------------
store, lock = {"k": 90}, threading.Lock()              # the lock stands in for Redis's single thread

def naive(results):                                    # GET, think, INCR: three separate steps
    seen = store["k"]; time.sleep(0.002)               # network hop + gateway logic
    if seen < 100:
        with lock: store["k"] += 1
        results.append(True)

def atomic(results):                                   # what one Lua script does
    with lock:
        if store["k"] < 100: store["k"] += 1; results.append(True)

for fn in (naive, atomic):
    store["k"], results = 90, []
    threads = [threading.Thread(target=fn, args=(results,)) for _ in range(50)]
    for t in threads: t.start()
    for t in threads: t.join()
    print(f"{fn.__name__:>6}: allowed {len(results)} with 10 remaining; counter ends at {store['k']}")
  1. The first block should print 9, 8, 8 and 11 allowed — the same marks as the timeline figure. Change TRACE to put 4 requests at t = 9.1-9.9 and 4 at t = 10.1-10.9 and watch the fixed window let all 8 through.
  2. The race block: the naive version typically allows far more than 10 (often all 50), because every thread reads 90 before any write lands; the atomic version allows exactly 10 and the counter ends at 100.
  3. Set the token bucket's rate to 0.1 and cap to 1: it becomes a strict "one per 10 s" limiter. Then try cap=8, rate=0.4 to see how capacity controls burst size independently of the long-run rate.
Work it out

Your API gateway fleet has 40 nodes behind a round-robin load balancer. A customer's contract says 2,000 requests per minute. Today each node runs a local token bucket of 50 per minute (2,000 ÷ 40). (a) The customer's SDK uses 4 long-lived HTTP/2 connections. What rate do they actually get? (b) Autoscaling takes the fleet to 80 nodes for a sale and nobody updates the bucket size. Now what? (c) Propose a design and estimate its Redis load if the customer sends at their full limit and 5,000 other customers average 300 per minute.

Answer

(a) HTTP/2 multiplexes all requests over a connection, and a connection-level load balancer pins each connection to one node. Four connections reach at most 4 nodes, each allowing 50 per minute: 200 per minute, a tenth of the contract. The customer sees 429s at 10% of their limit and files a ticket — a correct "limit" configured in a way that is wrong for real traffic.

(b) With 80 nodes, a client spread evenly across all nodes could get 80 × 50 = 4,000 per minute, twice the contract, while the pinned customer still gets 200. Local limits are wrong in both directions depending on traffic shape and fleet size.

(c) Central token buckets in Redis, one script call per request: the customer at 2,000 per minute is 33 calls per second; 5,000 others at 300 per minute is 5,000 × 5 = 25,000 calls per second. Total about 25,000 calls per second — within one shard's capacity at the 50,000 planning figure, but use 3 shards with replicas for headroom and failure tolerance. Keep a local bucket per node at 2,000 ÷ N × 2 as a fail-open backstop. If one customer later grows to 100,000 per minute, lease tokens to nodes in batches of, say, 20 to cut its Redis calls by 20× with overshoot bounded by 40 nodes × 20 = 800 tokens.

Diagnose it

After a gateway deploy, a handful of customers are rejected on every request with "100 requests/second exceeded", even when they send one request per minute. Other customers are fine. Redis shows their counter keys with values in the tens of thousands. What happened and what do you change?

Answer

Their counter keys have no expiry. The limiter runs INCR and, if the result is 1, a separate EXPIRE. During the deploy, gateway processes were killed between those two commands for a few keys, so those keys were created without a TTL. They never reset; every request increments them further; the comparison fails forever. Confirm with TTL key, which returns −1 (no expiry) for the affected keys. Immediate fix: delete or set expiries on keys with no TTL. Real fix: make creation and expiry atomic — a Lua script that does INCR and EXPIRE together, or SET key 0 EX 1 NX before INCR — and add an alert on limiter keys without a TTL. The general lesson: in a distributed limiter, every multi-step update is a race the next deploy will find.
