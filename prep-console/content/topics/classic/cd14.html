It is the last ten minutes of a weekly programming contest. Fifty thousand people are racing to finish the hardest problem, and every few seconds thousands of them press Submit. Each submission is a program written by a stranger, in one of twenty languages, that the platform must compile and run against dozens of hidden test inputs, each under a strict time and memory limit, and the verdict — Accepted, Wrong Answer, Time Limit Exceeded — must come back in seconds, because the leaderboard, and people's rankings, depend on it.

Now look at the same moment from a security engineer's chair. Among those fifty thousand programs, some are buggy (an infinite loop, a recursion that eats all memory), some are careless (printing gigabytes of output), and some are deliberately hostile: a fork bomb, an attempt to read the expected answers from disk, to open a network connection into the data centre, or to exploit a kernel bug and take over the machine. The platform's whole business is executing untrusted code on its own hardware, at scale, on purpose.

And from a fairness point of view: two identical programs must get the same verdict. A solution that runs in 1.8 seconds against a 2-second limit must not be rejected because it shared a machine with a memory-hungry neighbour. A participant whose code was judged during the end-of-contest burst must not lose rank because the queue was slow — or at least the ranking must depend on when they submitted, not when the judge got to it.

This lesson works through the design in interview order: requirements; estimates (submissions per second in normal times and in a contest's peak minute, CPU-seconds per submission, cores, test-data and submission storage, leaderboard reads); API and data model; the high-level design and the life of one submission; then three deep dives. The first is the submission queue — priorities, idempotency and burst capacity. The second is sandboxing untrusted code, layer by layer, from Linux users and namespaces through cgroups and seccomp to gVisor and Firecracker microVMs. The third is per-test time and memory limits, output checking and the live leaderboard. The real cases are Judge0 and its 2024 sandbox escapes, and the Firecracker paper's numbers for microVM isolation; the lab is a toy judge you can run.

The mental model: an exam hall with sealed rooms

Picture a national exam where candidates do not write answers but hand in sealed instructions, and an invigilator carries them out. Each instruction set is executed in a sealed room: no windows (no network), a fixed amount of desk space (memory), a stopwatch that only runs while the invigilator is actually working (CPU time), a wall clock on the door that ends the session regardless (wall-clock limit), and a rule that the answer key never enters the room — the invigilator copies the room's output onto a sheet, walks it outside, and a marker compares it with the key. Candidates wait in a queue in the hallway; during the busiest hour, more rooms are opened in advance. A noticeboard in the lobby shows the rankings, updated as results come in.

Each element maps onto the design. The queue in the hallway is the submission queue. The sealed rooms are sandboxes, and their walls are layers: who the program runs as, what it can see (namespaces), how much it can use (cgroups and rlimits), which kernel services it may request (seccomp), and whether it shares the building's foundations at all (a container shares the host kernel; gVisor or a microVM does not). The stopwatch and wall clock are CPU time and wall-clock time limits. The marker outside is the checker. Opening rooms in advance is a pre-warmed pool. The noticeboard is the leaderboard.

The analogy breaks where computers are both stronger and weaker than rooms. A room's walls are physical; a sandbox's walls are software, and every one has had bugs — which is why there are several of them. And a human invigilator can be trusted to copy output faithfully; the judge's own code that copies files in and out of the sandbox is itself an attack surface, as Judge0's 2024 vulnerabilities showed.

Three kinds of traffic

A judge platform carries three very different loads. Browsing — reading problem statements, editorials, discussion — is ordinary cacheable web traffic. Execution — "Run" against your own input and "Submit" against hidden tests — is CPU-heavy, bursty, untrusted, and goes through a queue to an isolated worker fleet. Results and rankings — verdict notifications and leaderboards — are small writes and very heavy reads during contests. The design keeps them apart so that a contest's execution burst never slows the problem pages, and a leaderboard refresh storm never touches the judges.

Interviewers asking for "LeetCode" usually want to hear three things: that you treat code execution as an asynchronous, queued job; that you take sandboxing seriously and can name its layers and why each exists; and that you can size a contest burst and design a leaderboard. 1 · Requirements

Functional. (1) Browse problems with statements, examples and constraints. (2) "Run" code against the examples or custom input and see output. (3) "Submit" code in one of about 20 languages; it is compiled and run against hidden tests under per-test time and memory limits; the user sees a verdict, runtime and memory, and for practice (not contests) the first failing test. (4) Contests: a fixed time window, a set of problems, scoring with penalties, and a live leaderboard. (5) Submission history per user. Out of scope, said aloud: editorials and discussion, problem authoring tools (though test validation matters), plagiarism detection beyond a mention, and payments.

Non-functional. Security first: no submission may affect the host, other submissions, the network or test data. Fairness: the same code gets the same verdict; time measurements are stable. Latency: verdicts in a few seconds normally, and bounded during contests. Burst capacity: contest peaks are an order of magnitude above normal. Durability: an accepted submission is never lost; contest rankings are reproducible from stored submissions.

Clarifying questions. How many users and submissions per day? How large are the biggest contests? Which languages (interpreted languages need different limits)? Do we show which test failed? ICPC-style or score-based ranking? Is the platform also used to run AI-generated code at scale (model evaluation, agents)? That last one changes the throughput target by orders of magnitude.

2 · Back-of-envelope estimates

Assumptions: 2 million daily active users, 1 million submissions per day in normal times, and twice as many "Run" executions; a big weekly contest with 50,000 participants over 90 minutes.

Normal rate. 1,000,000 ÷ 86,400 ≈ 12 submissions per second average, about 35 at a 3× daily peak. Runs add 2× that: about 100 executions per second at peak.

Cost of one submission. Compilation: about 1-2 CPU-seconds for C++ or Java, near zero for Python. Tests: say 30 hidden tests, most small, a few at maximum size; total runtime for an accepted solution averages about 1 CPU-second, while a Time-Limit-Exceeded one burns its full limit on at least one test. Plus sandbox setup. Call it 3 CPU-seconds per submission on average, about 1 for a run.

Cores, normal. 35 submissions × 3 s + 70 runs × 1 s ≈ 175 cores busy at peak. Judges should run one job per physical core for stable timing, so this is about 200 cores — a dozen or so 16-core machines.

Contest peak. Suppose participants average 6 submissions each: 50,000 × 6 = 300,000 submissions in 5,400 seconds ≈ 55 per second on average. Submissions cluster in the first minutes and especially the last ten; assume the peak minute runs at 5× average, about 280 per second. At 3 CPU-seconds each: 840 cores busy, on top of normal traffic — four to five times the everyday fleet, for 90 minutes a week. That is the case for elastic capacity with pre-scaling before the contest.

Queue depth if under-provisioned. If only 400 cores are available at that peak, the fleet completes about 133 submissions per second while 280 arrive: the queue grows by about 147 per second, 8,800 per minute; after ten minutes, the last submission waits about 88,000 ÷ 133 ≈ 11 minutes. That is why contest judges are sized for the peak, and why contest submissions get priority over practice traffic.

Storage. Source code averages about 2 KB: 1M × 2 KB = 2 GB per day, about 730 GB per year — tiny. Test data: 3,000 problems with up to tens of megabytes of tests each, say 50 MB on average: 150 GB. Every judge machine can cache all of it locally (or the hot subset for a contest), which avoids fetching tests per submission.

Leaderboard reads. 50,000 participants refreshing every 30 seconds: about 1,700 reads per second, plus spectators. Writes: one score update per Accepted verdict, a few dozen per second. Read-heavy and cacheable for a few seconds.

3 · The API

     → 202 {submission_id, status: "queued"}
GET  /v1/submissions/{id}

GET  /v1/submissions/{id}/events          (server-sent events: queued → compiling → running 12/30 → judged)
POST /v1/run          {problem_id, language, source, stdin}   → 202 {run_id}   (examples or custom input)
GET  /v1/contests/{id}/leaderboard?page=1  → {rows: [{rank, user, solved, penalty, per_problem: [...]}]}
GET  /v1/contests/{id}/rank/me            → {rank, solved, penalty}

Submission is a 202 Accepted: the server has stored the job, not judged it. Progress is pushed with server-sent events (net11), with polling as a fallback. Source size is capped (for example 64 KB) at the API, because a 50 MB "source file" is itself an attack.

4 · The data model

            verdict, time_ms, memory_kb, failed_test, judged_by, attempt, created_at)

Test data is versioned by content: fixing a wrong test creates a new version, and every verdict records which version it was judged against, so rejudging after a fix is explicit and reproducible. Submissions record created_at — the time the user pressed Submit — and contest penalties use that time, never the judging time, so a slow queue cannot cost anyone rank.

5 · High-level design and the life of a submission

(1) The browser posts source; the API checks size, language, contest window and the user's submission rate, writes the source to storage and a row with status queued, and publishes a job (submission id, problem, language, priority) to the queue. (2) A judge worker that has a free core pulls the highest-priority job. (3) It ensures the problem's test data at the right version is in its local cache. (4) It compiles the source inside a sandbox with compile-time limits (compilers can be attacked too, and a template can expand forever). (5) For each test: create a fresh sandbox (or reset one), mount the binary and that test's input only, run with limits, collect stdout, exit status, CPU time and peak memory, destroy the sandbox, and compare the output with the expected output outside the sandbox. Stop at the first failure (practice and ICPC contests) or run all tests (partial-score contests). (6) Write the verdict with a conditional update — only if the submission is still in a non-final state — and acknowledge the job. (7) Publish an event; the browser receives it. (8) If the submission is in a contest and Accepted, the scorer recomputes the participant's standing and updates the leaderboard.

6 · Deep dive A: the submission queue

Pull, not push. Workers pull jobs when they have a free core. A push model (a dispatcher sends jobs to workers) must know every worker's load and handle a worker that accepts a job and dies; pulling makes load balancing automatic — a busy worker simply does not ask — and the queue tracks in-flight jobs.

Delivery guarantees. A worker that takes a job has it hidden from others for a visibility timeout (longer than the worst-case judging time, say 2 minutes). If the worker acknowledges, the job is gone; if it crashes, the job reappears and another worker runs it. That is at-least-once delivery, so judging must be idempotent: the verdict write is UPDATE submissions SET … WHERE submission_id = ? AND status IN ('queued','running'). A zombie worker that finishes late finds the row already judged and its write matches nothing. A submission that has crashed workers three times goes to a dead-letter queue and is marked internal error — and investigated, because crashing the worker from inside a sandbox should be impossible.

Priorities and fairness. Three classes: contest submissions first, practice submissions second, runs third. Within a class, interleave users so one person submitting 50 times in a minute does not starve everyone else (per-user round robin, or a per-user cap on in-flight jobs). Rate-limit submissions per user at the API — useful for capacity and against brute-forcing hidden tests.

Separate pools per language image. Each language needs its toolchain inside the sandbox image: compilers for C++, Java, Rust, Go; interpreters for Python and JavaScript. Workers can carry all of them (simpler scheduling) or be pooled by language (smaller images, better cache locality). Many judges use one big image per worker and per-language run configurations; a few heavy toolchains get their own pool.

Burst capacity, worked. From the estimates, a contest's peak minute needs about 840 cores. The fleet should scale out before the contest starts, triggered by the contest schedule, not by queue depth — machines take minutes to boot and warm caches, and the first burst arrives in the first minute. During the contest, autoscale on queue age (the oldest job's waiting time) rather than CPU, because CPU at 100% is the goal; age tells you users are waiting. Pre-warmed sandboxes help too: Firecracker's paper sizes Lambda's pool of pre-booted microVMs with Little's law — pool size equals creation rate times creation latency — so at 125 ms per microVM, one pooled VM covers every 8 creations per second. At 280 submissions per second each creating one VM, keep about 280 × 0.125 = 35 ready.

7 · Deep dive B: sandboxing untrusted code

The threat model. List what a submission might do, because each item maps to a defence: (1) consume resources — infinite loops, allocating all memory, a fork bomb (spawning processes until the machine cannot create any more), writing until the disk fills, printing gigabytes; (2) reach things it should not — the network (internal services, cloud metadata endpoints, the internet), other submissions' files, the expected outputs, the judge's own code and credentials; (3) escalate — exploit a bug in the kernel or in the judge's handling of sandbox files to run code outside the sandbox; (4) interfere — slow down neighbours so their timings change. A sandbox is a stack of layers, each of which addresses some of these, so that one failing layer is not a breach.

Layer 1 — an unprivileged identity. Run as a dedicated user id with no rights to anything, with every Linux capability dropped (capabilities are the individual privileges root normally has, such as changing file ownership or binding low ports), and with no_new_privs set so nothing executed later can gain privileges, for example through a set-user-id binary.

Layer 2 — namespaces: what it can see. New namespaces (os13) give the process its own view: a PID namespace, so it sees only its own processes and cannot signal anyone else's; a mount namespace with a read-only root file system containing only the language runtime, a small writable tmpfs for scratch, and the input of the current test; a network namespace with no interfaces except loopback, so no packets leave; and IPC (inter-process communication), UTS (hostname) and user namespaces so shared memory, hostname and user ids are private too. Test expected outputs are never mounted.

Layer 3 — limits: how much it can use. A cgroup (control group) caps resources and measures them: memory.max (say 256 MB; exceeding it triggers the out-of-memory killer inside the group only), pids.max (say 64, which defeats a fork bomb), and cpu.max to cap CPU use; the cgroup's cpu.stat gives exact CPU time and memory.peak the high-water mark. rlimits add per-process limits: RLIMIT_FSIZE on file size (output larger than, say, 64 MB is killed with SIGXFSZ), RLIMIT_NOFILE on open files, RLIMIT_CPU as a second CPU-time stop, RLIMIT_STACK for deep recursion. The judge reads stdout through a pipe and stops reading beyond its own output cap.

Layer 4 — seccomp: which kernel services it may ask for. Every interaction between a program and the outside world is a system call. A seccomp filter is a small program the kernel runs on every system call to allow it, return an error, or kill the process. A judge uses an allow-list: the calls a compiled C++ program or the Python interpreter actually needs (read, write, mmap, brk, exit, a few others), and nothing else — no socket, no ptrace, no mount, no new namespaces. This cuts the amount of kernel code reachable from the sandbox from hundreds of system calls to a few dozen. DMOJ's judge, for example, builds its sandbox on seccomp; isolate, used by contest systems and Judge0, builds on namespaces and control groups.

Layer 5 — not sharing the host kernel. Everything above runs on the host's kernel. The allow-list shrinks the attack surface, but every allowed system call still executes host kernel code, and kernel bugs reachable from ordinary calls are found every year. For a public service running anonymous code, the strong answer is to put the hardened sandbox inside a boundary that does not expose the host kernel directly. gVisor is a user-space application kernel: the sandboxed program's system calls are intercepted and implemented by gVisor's own kernel (the Sentry), which itself uses a small set of host calls. Its default "systrap" platform intercepts calls using seccomp's trap mechanism; a KVM platform uses hardware virtualisation. Overhead is low for compute-heavy code and noticeable for programs that make many system calls. Firecracker takes the virtual-machine route with a minimal device model: each job gets a microVM with its own guest kernel under KVM (the hypervisor built into the Linux kernel). Its NSDI 2020 paper reports under 5 MB of memory overhead per microVM, booting to application code in under 125 ms, and up to 150 microVMs created per second per host; it runs AWS Lambda and Fargate.

The judge's own code is part of the sandbox. The worker copies files in, reads files out, changes ownership, and cleans up. Each of those, done on paths inside the sandbox, can be redirected by a hostile program that leaves a symbolic link where the judge expects a file. Judge0's 2024 advisories are the textbook case: the judge wrote a run script into the sandbox directory, and a submission could pre-create a symlink at that path so the write landed on an arbitrary host file (CVE-2024-28185); a related bug ran chown on an attacker-controlled path (CVE-2024-28189); together they gave a full escape, fixed in version 1.13.1. The defences: create a fresh sandbox per run so nothing persists, never follow symlinks when touching sandbox paths (open with O_NOFOLLOW, operate relative to a directory file descriptor), and treat every file the sandbox produced as hostile input.

8 · Deep dive C: limits, checking and the leaderboard

CPU time versus wall-clock time. CPU time is time the program actually executed on a processor; wall-clock time is elapsed real time. The verdict uses CPU time, because it does not depend on how busy the machine is. But a program that calls sleep(100) or blocks on reading stdin uses no CPU and would never hit a CPU limit, so there is also a wall-clock limit, set looser (for example, the CPU limit times 2.5) to kill it. Judge0's public instance shows the shape in its defaults: a 2-second CPU limit with 0.5 seconds of extra grace, and a 5-second wall-clock limit.

A worked per-test timeline. Problem limit: 2.0 s CPU per test, 256 MB. A submission runs 30 tests. Tests 1-16 take 0.01-0.4 s each. Test 17, the largest, uses 2.6 s of CPU before the judge kills it at the limit plus grace: verdict Time Limit Exceeded on test 17, total CPU reported 2.5 s (the cut-off). Another submission reads all input, then sleeps waiting for more: CPU 0.1 s, but wall time reaches 5 s, and it is killed — also TLE, because "idleness limit exceeded" is a time failure from the user's point of view. A third allocates a 300 MB array: the cgroup's memory limit triggers an out-of-memory kill, memory.peak shows 256 MB, and the verdict is Memory Limit Exceeded, not Runtime Error, because the judge checks the cgroup's out-of-memory event counter before interpreting the signal.

Making time stable. Runtimes vary with cache and memory-bandwidth contention, CPU frequency changes and hyperthread siblings. Judges pin each run to one physical core, keep hyperthread siblings idle (or disable simultaneous multithreading), fix the CPU frequency, and run one job per core. Even so, measurements vary by a few percent, so limits are set at 2-3× the reference solution's time, and submissions within a few percent of the limit may be rerun and given the better time. Slower languages get per-language limits (or multipliers); a Python solution of the intended complexity can be 10-50× slower than C++.

Checking output. Outputs are compared outside the sandbox by mode: exact; token-based, splitting both outputs on whitespace so trailing spaces and line ending styles do not matter; floating point with a tolerance, accepting an answer if its absolute or relative error is at most, say, 1e-6; or a custom checker — a trusted program, run in its own limits, that reads the test input, the contestant's output and the reference output, and decides (needed when any valid shortest path or any valid assignment is acceptable). Checkers must be robust to garbage output, because the output is untrusted.

The live leaderboard. Ranking rules differ, so encode them in one number that sorts correctly. ICPC-style rules (from the International Collegiate Programming Contest) rank by problems solved (more is better), then by penalty time (less is better): for each solved problem, minutes from the start to the accepted submission plus 20 minutes for each earlier wrong attempt on it. Worked example: Asha solves A at minute 12 (no wrong tries) and B at minute 47 (two wrong tries): 2 solved, penalty 12 + 47 + 2 × 20 = 99. Ben solves A at minute 9 and B at minute 58 with no wrong tries: 2 solved, penalty 67 — Ben ranks above Asha. Store each participant in a Redis sorted set with score = solved × 1,000,000 − penalty: Asha 1,999,901, Ben 1,999,933. A descending range query (ZREVRANGE lb:{contest} 0 49) returns the top 50 in order; ZREVRANK returns one participant's rank; each update is O(log n), trivial for 50,000 members.

Updates must be idempotent. When a verdict arrives, the scorer does not add to a score; it recomputes the participant's solved count and penalty from their stored submissions (using submit times, not judge times) and writes the result. A redelivered verdict, a rejudge after a test fix, or a disqualification all produce correct standings by recomputation. Reads are cached: the top pages for a few seconds at the CDN, a participant's own row from the sorted set. Many contests freeze the public board in the final hour — the system keeps updating internally and reveals the final standings afterwards — which also removes the refresh storm when the queue is busiest.

9 · Bottlenecks, failure modes and trade-offs

End-of-contest backlog. Without pre-scaling, the last ten minutes create a queue that delays verdicts by many minutes (the estimate showed 11). Penalties use submit time, so ranks are fair, but participants cannot react to a Wrong Answer in time. Pre-scale from the schedule, prioritise contest jobs, and shed "Run" traffic first.

Wrong test data. A bad expected output marks correct solutions wrong. Validate tests when a problem is authored (run the reference and several alternative solutions, run an input validator), and support rejudging all submissions for a problem against a new test version.

Timing drift across machines. A new hardware generation runs everything 30% faster, so old limits become generous. Calibrate limits per machine class (or run judges on one class), and record which class judged each submission.

Escape attempts. A worker crashing, an unexpected system call killed by seccomp, a file outside the sandbox changing — each is a signal. Alert on them, keep worker hosts disposable (recycled often, holding no secrets), and keep the judge fleet on its own network segment with no route to internal services.

Trade-offs to close on. Isolation versus overhead (container, gVisor, microVM). Fresh sandbox per test (strongest) versus per submission (cheaper). Stop at first failure (cheap, standard) versus run all tests (partial credit, more CPU). Precise timing (one job per physical core, wasted capacity) versus density. Leaderboard freshness versus read load (cache seconds, freeze at the end).

Why a fresh sandbox per test, or at least per submission

Reusing a sandbox between runs saves setup time but leaves state behind: files in tmpfs, processes that escaped the kill (a forked child that outlived its parent), changed permissions, symlinks planted for the next run. Each is a way for one submission to influence another, or for a planted link to redirect the judge's next file operation. Creating a fresh sandbox from an immutable template per submission (and resetting the writable layer per test) removes the whole class of problems; with microVMs, snapshot-and-restore makes this fast enough.

Killing everything, reliably

Killing a sandboxed program means killing every process it created, including ones that tried to escape by double-forking. Two mechanisms do this robustly: the PID namespace (when its first process, the namespace's init, exits, the kernel kills every other process in the namespace) and the cgroup (cgroup v2's cgroup.kill file kills every process in the group at once). Relying on killing the process id you started is not enough: a child that forked and detached keeps running, holding CPU and memory that the next submission's timing then competes with, and possibly lingering long enough to tamper with the next run's files.

Compilation is untrusted too

Compilers are large programs fed with hostile input. C++ templates can be made to expand exponentially, an #include of /dev/random can hang a preprocessor, and a 2 KB source can produce a gigabyte of error messages. Compile inside the same sandbox with its own time, memory and output limits, and never on the worker's host directly.

Memory limits differ by language runtime

"256 MB" is not one thing across languages. The JVM reserves a large virtual address space and manages its own heap, so a per-process address-space limit (RLIMIT_AS) can stop Java or Go from even starting while they would never touch that memory; judges therefore limit and measure real memory with the cgroup and set the runtime's own heap flag (for Java, -Xmx) slightly below the problem's limit so the program fails with its own out-of-memory error rather than a kill. Runtimes also carry a baseline — an idle JVM or Python interpreter uses tens of megabytes before the solution allocates anything — so many judges subtract a measured per-language baseline from the reported peak, or raise limits per language. Whatever the policy, measure it on the judge's own platform and publish it with the problem, because contestants tune to it.

Interactive problems

Some problems require a dialogue: the judge's interactor program asks questions and the submission answers, with the next question depending on the answer (for example, guessing a number with limited queries). The worker runs the interactor and the submission in two sandboxes connected by pipes, enforces limits on both, and must handle deadlocks where each waits for the other — the wall-clock limit is what resolves those.

Determinism and rejudging

A verdict should be reproducible from the stored source, the test version, the language version and the judge configuration. Record all of them per submission. Then a rejudge — after fixing a test, after upgrading a compiler, after discovering a timing problem — is a batch job that replays submissions through the same pipeline at low priority, and the results can be compared before they are published.

Plagiarism detection after contests

Copying is detected by comparing accepted solutions pairwise after normalising away superficial changes: strip comments and whitespace, rename identifiers, and compare token sequences or syntax trees (tools in the MOSS family use fingerprints of token n-grams to make this fast across thousands of solutions). Flags go to human review; similar solutions to easy problems are common and innocent.

The judge as an AI evaluation backend

Code-generation models are evaluated by running their outputs: generate k programs per problem and report pass@k, the fraction of problems where at least one of the k passes hidden tests. A benchmark of 1,000 problems at k = 100 is 100,000 sandboxed executions per evaluation run, and agents that write and run code during a task need the same sandbox on their critical path with sub-second start. That is why open-source judges now describe themselves as execution backends for AI-generated code as well as for people, and why microVM pools and snapshot restore matter: the throughput target can be 100× a contest's.

The real cases: Judge0's sandbox escapes and Firecracker's isolation numbers

Judge0 is a widely used open-source code execution system: an API that accepts source code, runs it in a sandbox built on isolate (the contest sandbox developed for programming olympiads, based on namespaces and control groups), and returns statuses that map directly onto contest verdicts — In Queue, Processing, Accepted, Wrong Answer, Time Limit Exceeded, Compilation Error, several Runtime Error variants by signal, Internal Error. Its public instance documents the per-submission limits a judge exposes, with defaults and maximums: CPU time limit 2 s (maximum 15), extra CPU time 0.5 s, wall-clock limit 5 s (maximum 20), memory 128,000 KB (maximum 256,000), up to 60 processes or threads by default, a 1,024 KB maximum file size, and support for both waiting synchronously and asynchronous callbacks.

In 2024, three advisories showed where such systems actually break. In CVE-2024-28185, Judge0 wrote a run_script file into the sandbox directory before execution; a submission could create a symbolic link at that path beforehand, so the judge's write went to an arbitrary file on the host, allowing code execution outside the sandbox. CVE-2024-28189 showed that the judge ran chown on an untrusted path inside the sandbox; with a symlink, that changed ownership of files outside, and it could be used to bypass the first fix. A third, CVE-2024-29021, was a server-side request forgery in the default configuration that could lead to unsandboxed code execution as root. All were fixed in version 1.13.1. The lesson is the one this lesson's sandbox section ends on: the isolation primitives held; the trusted code handling sandbox files was the weak point.

Firecracker (Agache et al., NSDI 2020) is the reference for running many untrusted workloads per host with VM-grade isolation. AWS built it because the usual choice — containers (cgroups, namespaces, seccomp-bpf) with low overhead but a shared kernel, or full virtual machines with strong isolation and high overhead — was unacceptable for multi-tenant serverless. Firecracker keeps KVM and replaces the heavyweight device emulator with a minimal one; the paper reports under 5 MB of memory overhead per microVM, boot to application code in under 125 ms, and up to 150 microVMs created per second per host, and it runs Lambda and Fargate. The paper also gives the pool-sizing rule used above: Lambda keeps a small pool of pre-booted microVMs, sized by Little's law as creation rate times creation latency.

Failure modes you will see

Flaky TLEs. Symptom: the same submission alternates between Accepted and TLE. Cause: noisy neighbours or frequency scaling. Fix: one job per physical core, fixed frequency, and automatic reruns of near-limit results.

Queue starvation by one user. Symptom: everyone's verdicts slow while one account submits hundreds of times. Fix: per-user in-flight caps and rate limits (cd12).

Disk full on workers. Symptom: internal errors across many submissions. Cause: sandboxes not cleaned up, or output files written outside tmpfs limits. Fix: tmpfs with size limits, fresh sandboxes, and worker recycling.

Leaderboard storms. Symptom: API latency spikes in the last minutes. Cause: uncached leaderboard reads hitting the database. Fix: sorted set plus a few seconds of cache, or a freeze.

What to monitor

Queue depth and oldest-job age per priority class; verdict latency p50/p99; worker CPU and per-job CPU time distribution; internal-error and dead-letter rates; seccomp kills and unexpected worker crashes (security signals); verdict distribution per problem (a sudden jump in WA suggests bad test data); leaderboard read rate and cache hit ratio during contests.

Goal: build a toy judge that runs a submission against several tests in a subprocess with a time limit, compares output, and assigns verdicts — then see why the real thing needs a sandbox. Python 3.12 standard library. Memory limits use the resource module, which exists on Linux and macOS (WSL on Windows); on native Windows the script still runs, without the memory limit.

"""Toy judge: run code per test with a time limit, compare output, assign a verdict.
NOT a sandbox: it runs code as you. Only feed it code you wrote."""
import os, subprocess, sys, tempfile, time
try:
    import resource                                 # POSIX only
except ImportError:
    resource = None

TESTS = [("3 4\n", "7\n"), ("10 -2\n", "8\n"), ("1000000000 1000000000\n", "2000000000\n")]
SUBMISSIONS = {
    "correct":  "a, b = map(int, input().split())\nprint(a + b)\n",
    "wrong":    "a, b = map(int, input().split())\nprint(a - b)\n",
    "slow":     "a, b = map(int, input().split())\nwhile True: pass\n",
    "crash":    "a, b = map(int, input().split())\nprint(a // 0)\n",
    "memory":   "x = bytearray(512 * 1024 * 1024)\nprint(1)\n",
    "trailing": "a, b = map(int, input().split())\nprint(a + b, end='   \\n\\n')\n",
}
TIME_LIMIT_S, MEM_LIMIT = 1.0, 256 * 1024 * 1024

def limits():                                       # runs in the child before exec
    resource.setrlimit(resource.RLIMIT_AS, (MEM_LIMIT, MEM_LIMIT))
    resource.setrlimit(resource.RLIMIT_CPU, (3, 3))      # CPU backstop above the wall limit

def tokens(s):                                      # token-based checker: ignore whitespace
    return s.split()

def judge(source):
    with tempfile.TemporaryDirectory() as d:
        path = os.path.join(d, "main.py")
        with open(path, "w") as f: f.write(source)
        for i, (inp, expected) in enumerate(TESTS, 1):
            t0 = time.perf_counter()
            try:
                p = subprocess.run([sys.executable, path], input=inp, capture_output=True,
                                   text=True, timeout=TIME_LIMIT_S * 2,     # wall-clock backstop
                                   preexec_fn=limits if resource else None, cwd=d)
            except subprocess.TimeoutExpired:
                return f"TLE on test {i}"
            wall = time.perf_counter() - t0
            if p.returncode != 0:
                kind = "MLE" if "MemoryError" in p.stderr else "RE"
                return f"{kind} on test {i} (exit {p.returncode})"
            if wall > TIME_LIMIT_S:
                return f"TLE on test {i} ({wall:.2f}s)"
            if tokens(p.stdout) != tokens(expected):
                return f"WA on test {i}: got {p.stdout.strip()!r}, want {expected.strip()!r}"
    return "Accepted"

for name, src in SUBMISSIONS.items():
    print(f"{name:>9}: {judge(src)}")
  1. Run it. Expect Accepted, WA on test 1, TLE on test 1, RE on test 1, MLE (on POSIX; on Windows the 512 MB allocation probably succeeds and prints Accepted-looking output, which then fails as WA) and Accepted for the trailing-whitespace version thanks to the token checker.
  2. Change tokens to exact comparison (s == expected) and see "trailing" become Wrong Answer — the reason judges normalise whitespace.
  3. Note what this toy cannot stop: a submission could read files in your home directory, open network connections, or fork processes. List which sandbox layer from the lesson blocks each one; that list is the design.
Estimate it

You run a judge for a contest with 80,000 participants over 2 hours. History says participants average 5 submissions, 40% of all submissions arrive in the last 20 minutes, and a submission costs 3 CPU-seconds. Each judge machine has 32 physical cores and you run one job per core. (a) How many machines for the last 20 minutes? (b) How many if you planned for the average? (c) What happens to the last submitters under (b)?

Answer

Total submissions: 80,000 × 5 = 400,000. Last 20 minutes: 40% = 160,000 in 1,200 s = 133 per second. CPU needed: 133 × 3 = 400 cores busy; at 32 cores per machine, 13 machines, say 16 with headroom for failures and timing slack.

(b) Average: 400,000 ÷ 7,200 s = 56 per second × 3 = 167 cores, about 6 machines.

(c) With 6 machines (192 cores, 64 submissions per second) facing 133 per second, the queue grows by about 69 per second: after 20 minutes, about 83,000 waiting, and the last submission is judged roughly 83,000 ÷ 64 ≈ 1,300 s — about 22 minutes after the contest ends. Ranks remain fair if penalties use submit time, but nobody in the final 20 minutes gets feedback in time to fix a wrong answer, which is a failed contest from the participants' point of view. Pre-scale to the peak from the schedule; contests are known in advance, so this is cheap insurance.

Diagnose it

A security review finds that the judge worker, after each run, copies /sandbox/output.txt to the results store and then runs chown -R judge /sandbox before cleaning up. Submissions run as an unprivileged user with namespaces, cgroups and seccomp. Why is this still dangerous, and how do you fix it?

Answer

The worker runs outside the sandbox with more privileges, and it touches paths the submission controlled. A submission can replace output.txt with a symbolic link to a sensitive host file (the worker then reads it and publishes it as output) or create links inside /sandbox pointing to host directories (the recursive chown then changes ownership of host files) — the pattern behind Judge0's CVE-2024-28185 and CVE-2024-28189. The isolation primitives are intact; the trusted code around them is not. Fixes: capture output through a pipe from the process's stdout instead of a file; if files are needed, open them with O_NOFOLLOW relative to a directory file descriptor and reject anything that is not a regular file; never run recursive ownership or permission changes on sandbox content; and throw away the whole sandbox (fresh per run) rather than cleaning it up in place.
