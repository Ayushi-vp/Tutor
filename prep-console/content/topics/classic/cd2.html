Priya sends "running 10 min late, start without me" to a group of six colleagues while walking into a lift. Her phone shows one grey tick, then the lift doors close and the signal drops. Two colleagues are on the underground with no signal; one has the app open on a laptop and a phone at once; one has uninstalled and reinstalled the app yesterday. Ten minutes later, everyone must see that message, exactly once, in the right place relative to the messages around it — and Priya must see two ticks, then blue ticks as people read it.

Sending a message sounds like a single database insert. What makes chat hard is two facts the URL shortener never faced. First, the server must push to the client rather than wait to be asked, so the system holds a live connection open to every online device — hundreds of millions of them. Second, the recipient is frequently not there: phones sleep, go through tunnels and switch networks constantly, so "deliver this message" usually means "deliver it at some unknown later time, to several devices, over a connection that may break halfway".

Every interesting problem follows from those two facts: where the millions of connections live and how a sender's server finds the recipient's; how to make sure nothing is lost when either side drops mid-send; how to show messages in the same order on every device when phone clocks disagree; what "delivered" and "read" mean and how to store them cheaply in a 500-person group; and how a phone that was offline for a week catches up.

This lesson works through the problem in interview order: requirements, estimates (messages per second, concurrent connections, storage per year, bandwidth, registry size), the API and data model, the high-level design, and three deep dives — connection management, delivery receipts and ordering, and storage and offline sync — followed by failure modes and trade-offs. The real case is Discord's public account of storing trillions of messages and fanning them out to millions of concurrent users, and the lab simulates a lossy network to show how retries plus deduplication give exactly-once results.

The mental model: a shared notebook and a set of doorbells

Picture each conversation as a numbered notebook kept at the post office. When anyone in the conversation says something, a clerk writes it on the next numbered line — line 4,811, line 4,812 — and only then tells the sender "got it". Every member has a doorbell (their open connection); when a new line is written, the clerk rings the doorbells of everyone who is home. Members who are out find a note when they return: "you have read up to line 4,790", and they simply read lines 4,791 onward from the notebook.

This picture contains the whole design. The notebook is a durable per-conversation log: it is the source of truth, and its line numbers — sequence numbers — define the order everyone sees. The doorbells are the real-time delivery path: fast, but only an optimisation, because anyone who misses a ring catches up from the notebook. The note "read up to line 4,790" is a high-water mark: one number per person per conversation, not a tick on every line.

The analogy breaks in two places worth knowing. A real clerk is one person; our clerk is thousands of servers, so "the next line number" must be assigned by whichever server owns that conversation, without consulting the others. And a real doorbell either rings or does not; a network can deliver a ring twice, deliver it late, or lose the reply "I heard it", which is why the protocol needs retries and duplicate detection.

Three moving parts

Gateways (also called connection servers) hold the open connections. A WebSocket (net11) is an HTTP connection upgraded into a long-lived two-way channel; either side can send at any moment. Gateways do little computation but hold a lot of state: each connection costs memory for buffers, encryption state and session data.

The message service receives a send, assigns the sequence number, appends to the log, acknowledges the sender, and hands the message to fan-out.

The fan-out and delivery path works out who should receive the message (one person or a whole group), finds which gateway holds each recipient's connection, and pushes it there — or, if the recipient is offline, triggers a mobile push notification to wake their app.

Why not just a database and polling?

The simplest possible chat app stores messages in a table and has every phone ask "anything new?" every few seconds. It works for a classroom project and fails at scale for two reasons you can compute. With 250 million connected devices polling every 5 seconds, the servers answer 50 million requests per second, and nearly all of them say "nothing new" — the system spends almost all its capacity on empty answers. And a message waits on average half the polling interval before anyone even asks for it, so making delivery feel instant means polling more often, which multiplies the empty requests further. Push over an open connection inverts both: an idle connection costs some memory and a heartbeat every half minute, and a message leaves the server the instant it is stored. Polling survives only as a fallback when a network blocks long-lived connections.

The other naive design — sending the message straight from the sender's connection to the recipient's connection, and storing it afterwards — fails on durability. If the recipient is offline, there is nowhere to deliver to; if a server crashes between receiving and storing, the message is gone although the sender saw it leave. Storing first and delivering second is the only order in which "one tick" can be an honest promise.

A reader who stops here has the right picture: write to the conversation's log first, assign the order there, acknowledge, then ring the doorbells; anyone who missed a ring catches up from the log. Everything else in the hour is detail on how to do each of those steps at the scale of hundreds of millions of devices.

1 · Requirements

Functional. One-to-one and group messaging (groups up to, say, 500 members); text plus media attachments (images, voice notes, video); delivery and read receipts; message history that syncs to all of a user's devices; online presence ("online", "last seen"); push notifications when the app is closed. Out of scope, said out loud: voice and video calls, stories, payments, and the internals of spam detection.

Non-functional. When both people are online, a message should arrive within about 500 ms at p99 (99% of messages faster). Messages must never be lost once the sender sees one tick. Every member of a conversation sees the same order. History is kept for years. The system must work on poor mobile networks where connections drop every few minutes. Availability target for sending: 99.99%.

The scoping question that matters most: is it end-to-end encrypted? If yes, the server stores ciphertext it cannot read, which removes server-side search, server-generated previews and content-based spam filtering. Ask early; the deep section covers what changes.

2 · Back-of-envelope estimates

Assume 500 million daily active users (DAU), each sending 40 messages a day.

Send rate. 500M × 40 = 20 billion messages a day. A day has 86,400 seconds, so 20,000,000,000 ÷ 86,400 ≈ 231,000 messages per second on average. Chat traffic peaks in the evening; allow 3×, about 700,000 per second at peak.

Delivery rate. Sends are not deliveries. If 90% of messages are one-to-one (one recipient) and 10% go to groups averaging 50 members, each send produces on average 0.9 × 1 + 0.1 × 50 = 5.9 deliveries. Peak deliveries ≈ 700,000 × 5.9 ≈ 4.1 million per second. Quote this ratio: groups are a tenth of sends and most of the work, which justifies a queue between storing and delivering.

Concurrent connections. If half of daily users are connected at the evening peak, that is 250 million open connections. How many per server? WhatsApp reported in January 2012 that it pushed a single 24-core FreeBSD server running Erlang past 2 million TCP connections. With encryption state, application buffers and headroom for failover, plan on 200,000-500,000 per gateway: 250M ÷ 250,000 = about 1,000 gateways. At roughly 40 KB of memory per connection (kernel buffers, TLS state, session), 250M × 40 KB = 10 TB of RAM across the fleet, 10 GB per gateway. Gateways are sized for memory and connection count, not CPU.

Heartbeats. Mobile networks and NAT devices silently drop idle connections, so each client sends a heartbeat (a tiny "still here" frame) perhaps every 30 seconds. 250M ÷ 30 ≈ 8.3 million heartbeats per second — more frames than real messages. They are tiny and handled entirely by the gateway, but they are a reason the gateway tier is separate and lean.

Connection registry. One entry per connected device, about 100 bytes (user id, device id, gateway id, timestamp): 250M × 100 B = 25 GB, which fits in a sharded in-memory store. Lookups run at the delivery rate, millions per second, so it must be in memory and sharded.

Message storage. A text message with metadata (ids, sequence, sender, timestamps, flags) is about 200 bytes. 20B × 200 B = 4 TB per day, about 1.5 PB per year, roughly 4.4 PB with three replicas. Media is far larger: if 5% of messages carry a 200 KB attachment, that is 1 billion × 200 KB = 200 TB a day, fifty times the text. Media goes to blob storage with a CDN in front; only a reference goes in the message.

Bandwidth. Text ingress at peak: 700,000 × 200 B = 140 MB/s ≈ 1.1 Gbit/s; delivery egress about 5.9× that, ≈ 6.6 Gbit/s, plus protocol overhead. Spread over 1,000 gateways this is trivial per machine. Media bandwidth is the large number and is served by the CDN.

3 · The API

Chat has two kinds of interface. Over the WebSocket, client and server exchange small typed frames:

client → server   SEND   {client_msg_id, conv_id, body | media_ref}
server → client   ACK    {client_msg_id, conv_id, seq, server_ts}        (one tick)
server → client   MSG    {conv_id, seq, sender, body, server_ts}
client → server   RECV   {conv_id, up_to_seq}                            (two ticks)
client → server   READ   {conv_id, up_to_seq}                            (blue ticks)
both ways         PING / PONG                                            (heartbeat)

Over plain HTTPS, for things that are not real-time: GET /v1/conversations/{id}/messages?after_seq=4790&limit=100 for sync and scrollback; POST /v1/media which returns a pre-signed upload URL so the client uploads straight to blob storage; and conversation management (create group, add member). Note the client_msg_id: a unique id the phone generates for each message and reuses on every retry. It is what makes retries safe.

4 · The data model

messages(
  conv_id, bucket,            -- partition key: conversation + time bucket
  seq,                        -- clustering key: order inside the partition
  client_msg_id, sender_id, body_or_ciphertext, media_ref, server_ts, flags
)
conversations(conv_id, type, member_ids, last_seq, created_at)
members(conv_id, user_id, delivered_up_to, read_up_to, joined_seq)
user_inbox(user_id, conv_id, last_seq)        -- "which conversations changed"

Partition by conversation. The dominant queries are "the last 50 messages of this conversation" and "everything after seq N in this conversation". Both read one contiguous range of one partition if the table is partitioned by conversation and sorted by seq. In a wide-column store (sc8) — Cassandra, ScyllaDB, HBase — the partition key decides which nodes hold the row and the clustering key sorts rows inside the partition, which is exactly this shape. Partitioning by user would scatter one conversation over every member's partition.

Bound the partition. A busy channel can live for years and grow without limit, and huge partitions hurt compaction, repair and balance. Add a time bucket to the partition key: Discord found that about 10 days of messages per bucket kept even its largest channels under 100 MB per partition. Fetching recent history reads the newest bucket first and walks back only if needed.

Receipts as high-water marks. delivered_up_to and read_up_to are one row per member per conversation. People read in order, so "read up to 4,812" says everything a per-message flag would. In a 500-member group with 1,000 messages a day, per-message receipt rows would be 500,000 writes a day for one group; high-water marks are at most a few thousand small updates, and can be batched.

A per-user inbox records which conversations have new messages, so a phone returning from a week offline asks "what changed since my cursor?" instead of polling every conversation it belongs to.

5 · High-level design and the critical path

Walk a one-to-one send through the system, step by step, using the sequence diagram. Priya's phone sends SEND {client_msg_id: "p-7f3a", conv: 88, body: "running late"} over her WebSocket to gateway A. Gateway A forwards it to the message service instance that owns conversation 88 (conversations are assigned to instances by consistent hashing on conv_id, so one owner orders each conversation). The owner checks whether p-7f3a was already stored — if so it returns the existing sequence number — otherwise it assigns seq = 4,813, appends to the message store with a quorum write (written to two of three replicas before returning, a few milliseconds), and sends ACK {p-7f3a, seq 4,813} back. Priya sees one tick. Only now does it publish the message to the fan-out queue.

A delivery worker takes it, reads the members of conversation 88 (just Sam for one-to-one), and looks up Sam's devices in the connection registry. Sam's phone is on gateway B, so the worker forwards MSG {conv 88, seq 4,813} to B, which writes it to Sam's socket. Sam's app stores it locally and sends RECV {conv 88, up_to 4,813}; the service updates Sam's delivered_up_to and relays it to Priya: two ticks. When Sam opens the chat, READ flows the same way: blue ticks.

If Sam is offline, the registry has no entry. The worker asks the push service (APNs for iPhone, FCM for Android) to send a notification, and stops. When Sam's phone wakes and reconnects, it sends its delivered_up_to for each changed conversation and receives everything after it. Media follows a side path: Priya's app first uploads the photo directly to blob storage with a pre-signed URL (a temporary, signed permission to upload one object), then sends a normal message whose body is the media reference. Gateways never carry megabytes.

6 · Deep dive A: holding 250 million connections

A gateway is an event-driven server (net13): one thread watches thousands of sockets with epoll or kqueue and only does work when a socket has data, so an idle connection costs memory, not CPU. The memory per connection — kernel send and receive buffers, TLS state, a session object — is the binding constraint, which is why gateways are tuned to shrink buffers and why languages with lightweight processes (Erlang at WhatsApp and Discord, Go elsewhere) are popular here.

Finding a recipient. Every delivery must answer "which gateway holds Sam's phone?". The usual answer is a connection registry: when a device connects, its gateway writes device → gateway into an in-memory store with a TTL of, say, 90 seconds, refreshed on every heartbeat. A gateway that crashes never deletes its entries, so the TTL is what eventually removes them; without it, deliveries would be sent to a dead server forever. The alternative is to consistent-hash each user to a fixed gateway, removing the lookup, but then a reconnecting client must reach that specific gateway, which fights with load balancing and makes failover messy. Most systems keep the registry.

Detecting dead connections. TCP does not tell you promptly that a phone went into a tunnel. Heartbeats (WebSocket ping/pong frames) every 20-60 seconds, with a connection declared dead after two or three misses, keep the registry honest and keep NAT devices on mobile networks from silently dropping idle connections.

Reconnect storms. When a gateway dies, its clients all reconnect at once. TLS handshakes are CPU-heavy, so 200,000 handshakes arriving in one second can overload the gateways that should absorb them. Clients must reconnect with exponential backoff and jitter — wait a random time that grows after each failure — so the load spreads over tens of seconds.

7 · Deep dive B: delivery receipts and ordering

Why exactly-once is impossible, and what to do instead. Suppose Priya's phone sends a message and the acknowledgement never arrives. Either the message never reached the server, or it did and the ack was lost on the way back. The phone cannot tell which, so it must resend — and if the first copy was stored, there are now two. No protocol over an unreliable network removes this ambiguity. So the system provides at-least-once delivery (every message arrives one or more times) and removes duplicates using the client_msg_id: the server, on append, returns the existing sequence number if it has already seen that id; each receiver drops any message whose sequence number it already has. The combination gives exactly-once effects: each message appears once on every screen.

Ordering. Phone clocks are wrong by seconds or minutes, and timestamps tie. Instead, the single owner of each conversation assigns a monotonically increasing seq as it appends. Everyone sorts by seq, so everyone sees the same order. There is no global order across conversations — none is needed, and avoiding it is what lets ordering scale: each conversation has its own tiny sequencer. Ownership moves (on failover or rebalancing) must hand over the last seq safely, typically by reading last_seq from the store with a conditional write (only succeed if the stored value is still what I read), so two owners cannot issue the same number.

Gaps. Messages can arrive out of order, especially with several delivery workers. A receiver that has applied up to 4,811 and receives 4,813 holds it in a buffer and waits for 4,812; if it does not arrive within a second or two, the client asks the server for "everything after 4,811". The receiver therefore always applies a contiguous prefix of the log, and its high-water mark — the highest seq with nothing missing below it — is exactly what it reports in RECV.

The three ticks as storage. One tick: the sender's ACK, which depends only on the store. Two ticks: some (or, in a group, every) recipient device's delivered_up_to has passed this seq. Blue: read_up_to has passed it. Because both are high-water marks, the sender's app can compute every message's tick state from a handful of numbers. For a group, the server can send the sender an aggregate ("delivered to 6 of 6") rather than a stream of individual receipts.

8 · Deep dive C: storage, offline sync and group fan-out

The store. At 231,000 writes per second and petabytes per year, with reads that are range scans within one conversation, a wide-column store is the natural fit: writes go to an in-memory table and a commit log and are flushed sequentially to disk (cheap), and a conversation's recent messages sit together on disk. Discord's history is the textbook illustration — covered in the production section — including two traps of this model: hot partitions (one very busy channel concentrating reads on the three replicas that hold it) and tombstones (deletes recorded as markers that readers must skip until compaction removes them).

Offline sync. When a phone reconnects after a week, it sends its cursor for the user inbox; the server returns the list of conversations whose last_seq moved, and for each the phone requests messages after its local high-water mark, in pages of a few hundred. Nothing about this path is special: the same append-only log serves live delivery, scrollback, offline catch-up and new-device sync. That is the payoff of the log-first design.

Group fan-out. A message to a 500-member group is written once to the conversation's partition. Fan-out then produces up to 500 deliveries, but each is just a push of an already-stored message to an online device, or a push notification (often collapsed: one "12 new messages" notification rather than twelve). Copying the message into 500 per-user inboxes would multiply storage by 500 and is only justified when members need independent retention or, with end-to-end encryption, when each copy is encrypted separately — which Sender Keys exist to avoid. Very large groups and broadcast channels also cap or throttle presence and typing indicators, which otherwise fan out on every keystroke.

9 · Bottlenecks, failure modes and trade-offs

Gateway crash: clients reconnect with jittered backoff and sync from their high-water marks; nothing is lost, only delayed. Registry stale entries: bounded by the TTL; deliveries to a dead gateway fail fast and fall back to push. Store hot partition: a celebrity channel concentrates reads; coalesce identical reads in a service layer and cache the newest page. Queue backlog: delivery latency rises but sends still succeed, because the store write happened first — the system degrades to "slow" rather than "lossy". Push provider outage: offline users are not woken; they catch up whenever they next open the app. Presence storms: presence is high-volume and low-value; throttle it and accept tens of seconds of staleness, and be ready to switch it off under load first.

The trade-offs to name: at-least-once plus dedup instead of impossible exactly-once; per-conversation ordering instead of a global order (scales, and is all users perceive); write-once fan-out instead of per-member copies (less storage, but every read hits the shared partition); a registry lookup per delivery instead of fixed user-to-gateway hashing (flexible failover for one more hop). Close with the sentence that ties it together: durable per-conversation log first, real-time push second, because it explains ordering, offline delivery, receipts and history in one idea.

End-to-end encryption changes the architecture, not just the payload

With end-to-end encryption (E2EE), only devices hold the keys, so the server stores and forwards ciphertext. The consequences are structural. Server-side search must move to the client (each device indexes its own decrypted history). Spam and abuse detection loses message content and must rely on metadata — send rates, account age, how many recipients block or report a sender — plus user reports that include the messages the reporter chooses to reveal. Push notifications cannot contain the text, so they say "new message" and the app wakes, fetches and decrypts. Link previews must be generated by the sender's device. And multi-device becomes a cryptographic problem: each device is its own identity with its own keys, a new device was not present when old messages were encrypted, and history transfer has to come from an existing device.

Why Sender Keys exist

Pairwise encryption in a group means encrypting each message once for every member device: a 500-member group with two devices each is 1,000 encryptions and 1,000 ciphertexts per message. Sender Keys flip this: each sender generates a group sending key, distributes it once to every member device over the pairwise encrypted channels, and then encrypts each message once with it. The server fans out one ciphertext, which restores the write-once fan-out design. The cost is that removing a member requires every sender to rotate their key, so group membership changes are expensive — another reason large E2EE groups are capped.

Ownership of a conversation and fencing

"One owner assigns sequence numbers" hides a hard question: what if two instances both believe they own conversation 88 during a failover? Both would issue seq 4,813 for different messages. The defence is to make the store, not the instance, the final arbiter: the append is a conditional write ("insert seq 4,813 only if it does not exist") or the owner holds a lease with a fencing token — a number that increases on every ownership change, which the store checks and rejects if it is older than the newest it has seen. A deposed owner's writes then fail instead of silently forking the order.

Multi-device semantics

With a phone, a laptop and a tablet, "delivered" and "read" become per-device for delivery but per-user for display: if Sam reads on the laptop, the phone should stop showing the message as unread. That means two kinds of high-water marks — per device for delivery bookkeeping, per user for read state — and syncing the user-level read mark to all the user's devices as an event. Messages sent from the laptop must also appear on Sam's own phone, so each send fans out to the sender's other devices too.

Presence is a fan-out problem in disguise

"Online now" sounds trivial, but each status change must reach everyone who can see it. A user with 300 contacts whose status changes 100 times a day (50 times online, 50 times offline) produces 30,000 presence deliveries a day; across 500 million users that is 15 trillion, far more than real messages. Discord saw exactly this: when a user came online, the guild (server) published presence to every connected session, which in large guilds overwhelmed the guild process. Mitigations: send presence only for conversations currently on screen, batch and debounce changes, use coarse states ("last seen recently"), and switch presence off for very large groups.

Deletion and editing on an append-only log

Edits and "delete for everyone" are new events appended to the log (edit seq 4,813 → new text; delete 4,813), which clients apply on top. The original row may also be overwritten or tombstoned in the store. Two consequences: deletes are not instant in a replicated store (they propagate as tombstones), and mass deletion can make reads slow — Discord's 2017 incident, where a channel with a single visible message forced Cassandra to scan millions of tombstones on every load, is the canonical example. Honest framing for interviews: you can remove it from the server and from compliant clients, but not from screenshots.

The busiest single conversation sets a ceiling

Per-conversation ordering scales across conversations, but one conversation has one owner, so its send rate is limited by how fast that owner can append and replicate. A quorum write of a few milliseconds, done one at a time, would cap a conversation at a few hundred messages per second. The owner therefore batches: it collects the messages that arrive in a short window (say 5 ms), assigns them consecutive sequence numbers, and writes them in one batch, which raises the ceiling to many thousands per second while keeping the order. Conversations that need more than that — a broadcast channel with millions of viewers during a live event — are a different product: few writers, huge read fan-out, often rate-limited "slow mode" for senders, and delivery via a pub/sub tier designed for one-to-many reads rather than the per-conversation log.

The client is half the system

Mobile chat apps keep a local database (usually SQLite) holding recent conversations, the local high-water marks, and an outbox of messages not yet acknowledged. The outbox is what makes sending work in a lift: the message is written locally with its client_msg_id and shown with a clock icon, and a background loop resends until an ACK arrives, surviving app restarts. The local database is also why the server can be stateless about what each device has seen beyond a few numbers: the device remembers its own position and asks for what comes after. Designs that ignore the client tend to invent server-side per-device queues that are expensive and unnecessary.

Why not Kafka as the message store?

Kafka is a log, so it is tempting. But Kafka partitions are designed for sequential consumption by a few consumers, not for billions of independent conversations each needing random access ("the 50 messages before seq 4,790 in conversation 88"). You cannot have a Kafka partition per conversation, and putting many conversations in one partition makes fetching one conversation a scan. Use Kafka (or similar) as the fan-out queue between the store and delivery workers, and a wide-column store keyed by conversation for the log itself.

The real case: how Discord stores and fans out messages

Discord has written unusually detailed public posts about this exact system. In 2017 it described moving messages out of a single MongoDB replica set — at 100 million stored messages the data and index no longer fitted in RAM and latency became unpredictable — into Cassandra. The primary key became ((channel_id, bucket), message_id): partition by channel plus a static time bucket, cluster by message id. Message ids are Snowflakes, so they are unique and sort by time; creation timestamps alone could not be the clustering key because two messages can share one. On import, Cassandra warned about partitions over 100 MB; bucketing about 10 days of messages per partition kept the largest channels under that. At the time, Discord was storing more than 120 million messages a day on a 12-node cluster with replication factor 3.

The same post describes the tombstone trap. Six months in, Cassandra began running 10-second stop-the-world garbage collection pauses. The cause was a public server's channel that took 20 seconds to load: it contained one message, because its owners had deleted millions through the API, and Cassandra had to scan millions of tombstones on every read. Discord shortened tombstone lifetime from 10 days to 2 (it ran repairs nightly, which made that safe) and taught its query code to remember and skip empty buckets.

The 2023 sequel, "How Discord Stores Trillions of Messages", picks up at the start of 2022 with 177 Cassandra nodes and trillions of messages, frequent pages, unpredictable latency, compaction backlogs and garbage-collection tuning. The worst problem was hot partitions: reads and writes used quorum consistency, so one overloaded channel-bucket slowed every query touching those nodes. Two changes fixed it. First, data services in Rust between the API and the database, with roughly one endpoint per query and a key feature, request coalescing: if many users request the same row at once, one worker queries the database and all requesters subscribe to its result. Requests are routed by channel id with consistent hashing, so every reader of a busy channel reaches the same instance and coalesces. Second, a migration to ScyllaDB, a Cassandra-compatible database written in C++ without a garbage collector. A Rust migrator moved data at up to 3.2 million messages per second in about nine days; the cluster went from 177 Cassandra nodes to 72 ScyllaDB nodes (9 TB of disk each, versus about 4 TB). Historical message fetch p99 dropped from 40-125 ms to 15 ms, and insert p99 from 5-70 ms to a steady 5 ms.

On the connection side, Discord's "How Discord Scaled Elixir to 5,000,000 Concurrent Users" explains fan-out inside a large server: each user's WebSocket session is an Erlang process, each guild is a process, and publishing to a guild with 30,000 online users made one process call send 30,000 times at 30-70 µs each — 900 ms to 2.1 s per event. Their fix (Manifold) groups recipients by the machine they live on and sends one message per machine, which then fans out locally. The same post describes a registry stampede: nearly five million sessions retrying lookups against ten registry processes until requests piled up and memory ran out — solved by a semaphore that makes callers give up early when too many requests are outstanding.

WhatsApp made the connection-density point early. In January 2012 it reported pushing a single server — 24 cores, about 103 GB of RAM, FreeBSD and Erlang — past 2 million TCP connections. That is an engineering record, not a capacity plan: a production fleet keeps far fewer per box so that losing one machine does not drop millions of users at once, and so the survivors have room for the reconnect wave. The lesson for an estimate is that connection count per server is bounded by memory and blast radius, not by CPU.

Failure modes and what to watch

Delivery latency creep: track send-to-deliver p50/p99 end to end, split by one-to-one versus group; rising group latency with flat one-to-one latency points at fan-out workers. Reconnect storms: watch connection rate and TLS handshake CPU per gateway; a spike after any deploy means draining is too abrupt. Registry accuracy: count deliveries routed to gateways that no longer hold the device. Store health: per-partition read rates (to catch hot channels), compaction backlog, tombstones scanned per read. Push: provider error rates and the share of messages delivered only after the user opened the app. Duplicates: server-side dedup hits per second; a sudden rise usually means acks are being lost somewhere.

Goal: see at-least-once delivery plus deduplication give exactly-once results, and see sequence numbers and a high-water mark repair out-of-order arrival. Python 3.12, standard library, runs instantly.

"""At-least-once delivery over a lossy network, made exactly-once in effect.
Sender retries until acked; server dedups on client_msg_id and assigns a per-conversation seq;
receiver applies messages in seq order and reports a high-water-mark receipt. Python 3.12 stdlib."""
import random

random.seed(7)
LOSS = 0.3                                   # 30% of packets in each direction vanish

class Server:
    def __init__(self):
        self.log, self.seen, self.next_seq = [], {}, 1
    def append(self, client_id, text):
        if client_id in self.seen:           # retry of something we already stored
            return self.seen[client_id]
        seq = self.next_seq; self.next_seq += 1
        self.log.append((seq, client_id, text)); self.seen[client_id] = seq
        return seq                           # durable before ack (a list stands in for disk)

class Receiver:
    def __init__(self):
        self.applied, self.buffer, self.hwm = [], {}, 0
    def on_packet(self, seq, text):
        if seq <= self.hwm or seq in self.buffer:
            return "duplicate dropped"
        self.buffer[seq] = text
        while self.hwm + 1 in self.buffer:   # apply only contiguous seqs: gaps wait
            self.hwm += 1
            self.applied.append(self.buffer.pop(self.hwm))
        return f"receipt: delivered up to {self.hwm}"

server, rx, sends = Server(), Receiver(), 0
for i, text in enumerate(["hi", "are you there?", "lunch at 1?", "ok", "bring the slides"]):
    cid = f"alice-{i}"                       # client-generated id, reused on every retry
    while True:
        sends += 1
        if random.random() < LOSS:           # request lost before reaching server
            continue
        seq = server.append(cid, text)
        if random.random() < LOSS:           # ack lost: alice will retry the same cid
            continue
        break

# Fan-out to the receiver: shuffled order, every packet sent twice, some lost.
packets = [(s, t) for s, _, t in server.log] * 2
random.shuffle(packets)
for seq, text in packets:
    if random.random() < LOSS:
        continue
    print(f"seq {seq} arrives -> {rx.on_packet(seq, text)}")
missing = [s for s, _, _ in server.log if s > rx.hwm]
for seq, _, text in server.log:              # reconnect: "give me everything after hwm"
    if seq > rx.hwm:
        rx.on_packet(seq, text)
print(f"\nsender attempts {sends} for 5 messages; server log has {len(server.log)} rows")
print("replayed after reconnect:", missing)
print("receiver shows:", rx.applied)
  1. Run it. The sender loop shows retries: about 17 attempts to land 5 messages at 30% loss, yet the server log has exactly 5 rows, because a retry carrying the same client_msg_id gets back the sequence number already assigned.
  2. Read the receiver lines: seq 4, 3 and 2 arrive first and the receipt stays at 0 — they are buffered, not shown, because seq 1 is missing. When 1 arrives the high-water mark jumps to 4 in one step. Later copies are dropped as duplicates.
  3. Check the final line: the receiver shows the five messages in send order, once each.
  4. Set LOSS = 0.6. Now some messages never arrive during fan-out, and the "replayed after reconnect" line shows the client fetching everything after its high-water mark — the offline-sync path doing the work.
  5. Break it on purpose: remove the if client_id in self.seen check in Server.append. The log now contains duplicates with different sequence numbers, and the receiver shows repeated messages — exactly the bug a client-generated id exists to prevent.
Work it out

A chat service has 400M users, 60% online at peak. Each chat server holds 150,000 WebSocket connections using about 40 KB of memory per connection. Peak send rate is 600,000 messages/s, of which 15% go to groups averaging 80 members.

(a) How many chat servers and how much memory? (b) What is the actual delivery rate? (c) A datacentre holding 20% of connections fails. What happens in the next 60 seconds?

Answer

(a) Concurrent connections: 400M × 0.6 = 240M. At 150k per server that is 1,600 chat servers, and at 40 KB per connection each server holds 150,000 × 40 KB = 6 GB of connection state alone — before buffers, TLS state or the application. That memory figure is why chat servers are provisioned for RAM rather than CPU, and it is worth stating.

(b) Delivery amplification. Direct messages: 600,000 × 0.85 = 510,000 sends, each delivering to 1 recipient = 510,000 deliveries/s. Group messages: 600,000 × 0.15 = 90,000 sends × 80 members = 7.2M deliveries/s. Total ≈ 7.7M deliveries/s, roughly 13× the send rate. Group traffic is 15% of sends and 94% of delivery work — which is the whole argument for fanning out notifications against a shared log rather than writing a copy per recipient.

(c) The datacentre failure. 48M connections drop at once. Three things happen in sequence, and the order matters:

  • A reconnect storm. 48M clients attempt to reconnect. Without exponential backoff and jitter they arrive as a synchronised wave, and the surviving datacentres — already at capacity — are hit with 48M TLS handshakes in a few seconds. Handshakes are CPU-expensive, so this can take down the healthy capacity that just absorbed the failure. Jitter is the load-bearing fix.
  • Registry staleness. The connection registry still lists those users on dead servers until the heartbeat TTL expires. During that window, deliveries are routed into a black hole. This is exactly why entries carry a short TTL refreshed by heartbeat rather than being deleted on clean disconnect — a crashed server never gets to clean up.
  • Capacity. The remaining 1,280 servers must absorb 240M connections, which needs 1,600 servers' worth of memory. They cannot, so you must have provisioned N+1 across failure domains, or you shed the excess and those users stay disconnected.

Critically, no messages are lost. Everything was durably written to the conversation log before the sender was acknowledged, so reconnecting clients replay from their last sequence number and catch up. The outage is a latency and availability event, not a durability one — and being able to say precisely which of those three properties broke is the mark of someone who has run a system like this.

Diagnose it

Users in one very large public group (40,000 members, a few hundred online at any moment, but a big announcement just went out) report that the whole app is slow — even their one-to-one chats. Your dashboards show three database nodes at 100% CPU and every other node idle. What is happening and what do you change?

Answer

What is happening. The announcement made thousands of members open the same channel at once, so thousands of identical "latest 50 messages" reads hit the one partition (channel + newest bucket) holding them. That partition lives on three replicas — the three hot nodes. Those nodes also hold slices of many other conversations, and with quorum reads every query touching them waits, so unrelated one-to-one chats slow down. This is Discord's hot-partition problem.

What to change. (1) Coalesce identical concurrent reads in a service layer and route requests by channel id with consistent hashing, so one database query serves every simultaneous reader. (2) Cache the newest page of very active channels for a second or two. (3) Rate-limit or stagger fan-out notifications for huge groups, so members do not all fetch in the same instant. (4) Longer term, cap group size or move very large broadcast channels to a separate tier designed for one-to-many reads. The point to make: adding database nodes does not help, because the load is on one key, not spread across many.
