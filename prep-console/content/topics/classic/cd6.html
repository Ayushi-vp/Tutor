Meera saves a 200 MB presentation on her laptop at the office, closes the lid and catches a train. On the train, on her phone, she opens the same presentation — and expects to see the version she just saved. At home she edits it on her desktop, while a colleague she shared the folder with edits the same file from an airport lounge with no signal. Both expect their work to be safe when everything reconnects. Neither expects their home broadband to re-upload 200 MB because a single slide title changed.

A file sync service promises three things that pull against each other. It must be efficient: hundreds of millions of devices editing files all day cannot each re-send whole files. It must be correct: every device eventually agrees on the contents of every folder, edits made offline are not lost, and a rename of a folder with 100,000 files does not turn into 100,000 downloads. And it must be durable to a degree few systems attempt: people store their tax records and baby photos here and assume they will never disappear.

The trick that makes all three possible is to stop thinking of a file as a single object. Instead, a file is a list of blocks, each named by a fingerprint of its content. Blocks never change once written, so storing, copying and verifying them is easy and identical blocks are stored once. All the mutable, tricky state — which file is at which path, which version is current, who can see what, what changed since a device last looked — lives in a separate, transactional metadata journal. Most of the interview is about the protocol between those two halves.

This lesson follows the interview flow: requirements; estimates (stored bytes, metadata rows, change events, upload bandwidth, notification connections, block index size); API and data model; the high-level upload and download paths; deep dives on chunking and delta sync, on the metadata journal and conflicts, and on deduplication and the block store; then failure modes and trade-offs. The real case is Dropbox's own engineering writing — its sync protocol and its Magic Pocket block store — and the lab measures how many chunks an edit forces you to upload with fixed-size versus content-defined chunking.

The mental model: a library of numbered pages and a catalogue

Imagine a library where every page of every book is stored separately in a vast warehouse, and each page is labelled with a fingerprint of its exact text. A book is not stored as a book: it is a catalogue card that lists, in order, the fingerprints of its pages. If two books share an identical page — the same copyright notice, the same appendix — the warehouse keeps one copy and both cards point at it. When an author fixes a typo on page 37, the warehouse receives one new page, and the catalogue gets a new card listing the same fingerprints as before except for page 37. The old card stays in a drawer, so the previous edition can be reassembled any time.

Now map it across. The warehouse is the block store: content-addressed, immutable blocks keyed by their SHA-256 hash. The catalogue cards are blocklists, and the catalogue is the metadata journal: each row records one version of one file as a list of block hashes, under a path in a namespace. Fixing a typo is delta sync: only changed blocks travel. Keeping old cards is version history at almost no cost. Sharing identical pages is deduplication.

The analogy breaks in one important way: a typo fix does not shift the rest of a printed page, but inserting bytes into a file shifts everything after the insertion. If pages were cut at fixed byte offsets, inserting one sentence near the start would change every page after it. That is the chunking problem, and it is the first deep dive.

The two halves and their characters

The block store holds almost all the bytes (exabytes at Dropbox scale) but has a trivially simple interface: put a block under its hash, get a block by its hash, never update. Because blocks are immutable, any copy is as good as any other, caches never need invalidating, and corruption is detectable by re-hashing. The metadata service holds tiny rows but billions of them, and every hard question lives here: what is the current version of this path, what changed since cursor N, was this edit based on the latest version, who can see this folder, what happens on a rename. It must be transactional, because a half-applied rename or a lost version is a correctness bug users notice.

What the client does

It is easy to treat the desktop client as a thin uploader, but half the system lives there. The client watches the file system for changes, waits for a file to stop changing (a document being saved may be written several times in a second), splits and hashes it, and keeps a local database recording, for every file, the version it last synced and the blocklist of that version. That local state is what lets it answer three questions without asking the server: did this file really change since the last sync, which blocks of a new version do I already hold on disk, and was my edit based on the latest server version? It also keeps a queue of pending operations so work survives restarts and offline periods. A design that ignores the client ends up inventing expensive server-side per-device state that the client could hold far more cheaply.

A reader who stops here has the right picture: files become lists of content-addressed blocks; the client uploads only blocks the server lacks and then commits a new version to a per-namespace journal; other devices follow the journal with a cursor and fetch blocks they lack. Everything else is making each of those steps fast, safe and private at scale.

1 · Requirements

Functional. Sync a folder across a user's devices; upload and download files of any size; keep version history and allow restoring old versions and deleted files; share folders with other users with permissions; work offline and reconcile on reconnect; selective sync (choose which folders live on which device). Out of scope, said aloud: real-time collaborative editing inside a document (a different design, where many people type into one document at once and the system merges individual keystrokes rather than whole file versions), full-text search inside files, and previews.

Non-functional. A change on one online device appears on the others within seconds. No silent data loss, ever — durability far beyond ordinary databases. Efficient on slow and metered connections: never re-send bytes the server already has. Correct under concurrent edits, renames and moves. Scales to hundreds of millions of users and many billions of files.

The clarifying question: what happens when two devices edit the same file offline? "Last write wins" makes the design simpler and loses data; "never lose data" forces conflict detection and conflicted copies. Do not assume — ask.

2 · Back-of-envelope estimates

Assume 100 million users, 20 million daily active, an average of 10 GB stored per user and 1,000 files per user. (For scale: Dropbox reported 500 million sign-ups and 500 PB of user data in 2016 — about 1 GB per sign-up, with heavy users far above that.)

Stored bytes. 100M × 10 GB = 1,000 PB = 1 EB of logical data. Consumer data has a lot of duplication (the same installers, shared documents, forwarded photos); assume deduplication removes 30%, leaving 700 PB unique. Storage overhead for durability — erasure coding at about 1.5× rather than three full replicas — brings raw disk to roughly 1 EB.

Metadata rows. 100M × 1,000 = 100 billion files, each with a current version row and some history. At about 500 bytes per row (namespace, path, blocklist reference, size, timestamps, version), current versions alone are 50 TB; with history, several times that. Small in bytes compared with content, enormous in row count and query rate — this is the real hard part, and saying so early is a good signal.

Change events. 20M active users × 100 file changes a day = 2 billion commits a day ÷ 86,400 ≈ 23,000 commits per second, about 70,000 at peak. Most are small: saves of documents, new photos, renames.

Upload bandwidth. If the average commit carries 100 KB of genuinely new blocks after dedup and delta, 2B × 100 KB = 200 TB a day ÷ 86,400 ≈ 2.3 GB/s ≈ 18.5 Gbps sustained ingest. Substantial but ordinary, and it flows straight into the block store.

Block index. 700 PB of unique blocks. If the average block is about 1 MB (many files are smaller than the 4 MB maximum, and the last block of each file is short), that is 7 × 1017 ÷ 106 = 700 billion blocks. At about 64 bytes per entry (32-byte hash plus location and checksum), the index is about 45 TB: far beyond one machine, and read on every upload (does this hash exist?) and every download (where is it?).

Notification connections. Desktop clients stay connected all day. If 50 million devices hold a long-poll connection that times out and is re-established every 60 seconds, that is 50M ÷ 60 ≈ 830,000 idle re-polls per second, plus the real notifications. The notification tier is a connection-holding problem like a chat gateway.

3 · The API

Dropbox's desktop protocol, as its engineers described it, maps directly onto a clean API:

commit(namespace, path, blocklist, base_version)   → ok(journal_id) | need_blocks([hashes]) | conflict
store_batch([(hash, bytes)])                       → ok           (block servers; size-limited batches)
list(cursors: {namespace: journal_id})             → [new journal rows], new cursors
retrieve_batch([hashes])                           → [(hash, bytes)]
longpoll(cursors)                                  → "changed" | timeout
share(namespace, user, role) · restore(path, journal_id) · move(path, new_path)

Two details matter. commit carries the base_version — the version the client's edit started from — which is how the server detects conflicts. And every call is safe to retry: storing a block twice is a no-op (the hash is the key), and a commit with the same blocklist and base is idempotent.

4 · The data model

blocks       hash (SHA-256) → bytes                    -- block store, immutable, global
block_index  hash → (cell, bucket, checksum)           -- sharded index (Magic Pocket: MySQL)
journal      (namespace_id, journal_id) PK,            -- append-only; journal_id increases
             path, blocklist, size, mtime, deleted, author_device
latest       (namespace_id, path) → journal_id         -- current version per path
namespaces   namespace_id, owner, members, permissions -- user roots and shared folders
mounts       (user_root_ns, path) → namespace_id       -- where a shared folder appears

Dropbox's description gives the shape directly. A namespace is the root of a directory tree: each user has a root namespace, and every shared folder is a namespace mounted inside one or many root namespaces. Every file on the server is identified by (namespace, relative path). Each file is split into blocks of 4 MB (the last may be smaller), hashed with SHA-256; the list of hashes is the blocklist. The Server File Journal is an append-only table where each row is one version of a file, with a journal id that increases monotonically within a namespace. The journal is sharded by namespace, so all changes to one folder tree are ordered and can be applied transactionally.

Three consequences to state. History is free: old journal rows remain, and restoring is committing an old blocklist again. A move within a namespace is a metadata change; blocks never move. And because a shared folder is its own namespace, sharing a folder with a thousand people does not copy anything — each member's root simply mounts it.

5 · High-level design and the critical paths

Upload, step by step (sequence diagram below). The client's file watcher notices deck.pptx changed. The client splits it into blocks, hashes each, and calls commit(ns, "/work/deck.pptx", [h1…h50], base=812). The metadata server checks the user can write there, that version 812 is still current (no conflict), and which hashes are unknown. Two are new, so it replies need_blocks([h8, h9]). The client uploads those two blocks to the block servers, which store them and record them in the block index. The client commits again; now every hash is known, the server appends a journal row with journal id 813, and the file officially has a new version. Blocks first, metadata last: the journal never points to a block that does not exist, so a crash mid-upload leaves at worst some orphaned blocks, never a broken file.

Download. Meera's phone holds a long-poll on the notification service. The journal advance triggers "namespace changed". The phone calls list with its cursor (812) and receives row 813 with its blocklist. It checks which blocks it already has locally — in the old version of the same file, in other files, in a cache of recently deleted files — and retrieves only the missing ones, then reconstructs the file and atomically replaces the local copy. Its cursor becomes 813.

6 · Deep dive A: chunking and delta sync

Fixed-size blocks. Dropbox's format is simple: 4 MB blocks at fixed offsets. For edits that overwrite bytes in place — most edits to databases, disk images, many binary formats — only the touched blocks change. For a 200 MB file where one slide's bytes change in place, that might be one or two blocks: 4-8 MB instead of 200 MB.

The insertion problem. Now insert 50 KB at the 30 MB mark. Every byte after the insertion moves 50 KB later. Block 8 (28-32 MB) contains the edit; blocks 9 to 50 now each start 50 KB earlier in the original content than before, so every one has a different hash. Forty-three blocks — 172 MB — must be re-sent for a 50 KB change. The lab measures the same effect at small scale: inserting 100 bytes into a 2 MiB file makes 196 of 257 fixed 8 KiB chunks new.

Two fixes. The first is an rsync-style delta inside changed blocks. The rsync algorithm (Tridgell and Mackerras) lets one side compute, for its old copy, a cheap rolling checksum and a strong hash per small window; the other side slides a window over its new data, uses the rolling checksum to find candidate matches at any byte offset, and confirms with the strong hash. Shifted content is found wherever it moved, and only literal new bytes plus references are sent. Dropbox says it uses compression and rsync to minimise the size of its block transfers.

The second fix is content-defined chunking (CDC): choose block boundaries from the content itself. Slide a rolling hash over the data — a hash of the last few dozen bytes that can be updated in constant time as the window moves one byte — and cut a boundary wherever the hash's low bits are all zero. With 13 low bits, a boundary occurs on average every 213 = 8,192 bytes. Because the decision depends only on nearby bytes, an insertion changes boundaries only near the edit: once the window has moved past the inserted bytes, it sees exactly the same content as before and cuts at exactly the same places. Minimum and maximum chunk sizes stop pathological inputs (long runs of zeros, adversarial data) from producing tiny or huge chunks.

The costs of CDC are CPU on the client (a hash update per byte — fast with Gear-style hashes that need one shift, one add and one table lookup per byte), variable chunk sizes, and many more index entries if chunks are small. Systems that use CDC (backup tools such as restic, and the Low-Bandwidth File System research before them) typically aim for chunks in the kilobyte to megabyte range. A practical hybrid is large fixed blocks for storage and indexing plus rsync-style deltas on the wire for changed blocks, which is the combination Dropbox describes.

7 · Deep dive B: the journal, cursors and conflicts

Cursors. Each client stores, per namespace, the last journal id it has applied. "What changed since 812?" is a range scan of one namespace's journal. This single mechanism serves live sync (a nudge, then a list), offline catch-up (a week of changes is just a longer list), and a brand-new device (cursor 0, then the client downloads blocks for the latest versions, perhaps lazily). It is the same idea as a chat's per-conversation sequence number, and naming the parallel shows pattern recognition.

Conflicts. Meera and her colleague both edit deck.pptx starting from version 812, offline. Meera's laptop reconnects first and commits with base 812: accepted as 813. The colleague's laptop then commits with base 812, but the current version is 813. The server rejects it as a conflict. The client then commits its version under a new path such as deck (Ravi's conflicted copy).pptx, so both edits survive and a human decides. Notice what was not used: timestamps. Clocks on two laptops can disagree by minutes; causality — "was this edit based on the current version?" — is what defines a conflict. Automatic merging is possible only for formats the system understands; for arbitrary binary files no correct merge exists, so the honest design surfaces the conflict.

Moves and renames. Within a namespace, moving a folder is a metadata operation; implemented naively as one row per descendant it is 100,000 writes for a big folder, so systems keep stable file or directory ids, or record the move as one journal entry that clients apply locally by moving files rather than re-downloading them. Moves between namespaces (from your private folder into a shared one) change who can see the data and must be modelled as an add in one journal and a delete in the other, applied together.

Streaming sync. In the basic protocol, a downloading client cannot start until the upload has fully committed. Dropbox's streaming sync lets the metadata server remember the blocklist from the first, failed (need-blocks) commit in memcache and include it in other clients' list results as "prefetchable", so a downloading client can fetch blocks as they arrive and be nearly done when the commit lands — Dropbox reported sync latency improvements of up to 2× for large files. The memcache state is deliberately non-durable: if it is lost, sync simply falls back to the basic protocol.

8 · Deep dive C: deduplication and the block store

Content addressing makes deduplication automatic: when a client's commit lists a hash the server already has, from any file, nothing is uploaded. Copying a 200 MB folder, restoring an old version, or uploading a file a colleague already shared costs only metadata. The block store needs an index from hash to physical location, and Dropbox's Magic Pocket shows how one is built at exabyte scale: blocks of up to 4 MB, compressed and encrypted, keyed by SHA-256; grouped into 1 GB buckets; buckets replicated onto volumes of storage machines and later erasure coded for efficiency; volumes inside self-contained cells of about 50 PB; and a Block Index mapping hash → (cell, bucket, checksum) that is a giant sharded MySQL cluster. Every block is stored in at least two geographic zones, with cross-zone replication within one second of upload.

Deduplication has a privacy cost. If dedup crosses users, an attacker can upload a specific file and observe that nothing was transferred, learning that someone already stored it — enough to confirm possession of a leaked document, or to brute-force a low-entropy file such as a form with a few variable fields. Mitigations: deduplicate only within a user or namespace; deduplicate on the server after the client has uploaded anyway (saves storage, not bandwidth); or salt hashes per user. Each gives up some savings, which is the trade-off to state.

9 · Bottlenecks, failure modes and trade-offs

Metadata hot spots: a single namespace shared by a 10,000-person company concentrates commits on one journal shard; batch small commits, rate-limit per namespace and split very large shared trees. Garbage collection: a block is deletable only when no version anywhere references it; keep reference counts with periodic full verification, delay deletion, and never risk deleting a referenced block. Partial uploads: orphaned blocks from abandoned commits are harmless and collected later. Sync loops: two clients rewriting a file in turn, usually because of name normalisation or case-insensitive file systems; tag writes with the originating device and detect echoes. Notification outage: clients fall back to periodic list calls; sync slows but stays correct, because the journal, not the nudge, is the source of truth. Block store zone outage: reads served from the other zone; writes go to a healthy zone and replicate later.

The trade-offs to close on: fixed blocks plus rsync deltas (simple index, good for in-place edits) versus content-defined chunking (robust to insertions, more CPU and index entries); global versus scoped deduplication (storage savings versus a privacy side channel); conflicted copies versus automatic merge (never lose data versus convenience); and the two-store split itself — immutable content-addressed blocks where scale lives, transactional metadata where correctness lives.

Causality, not clocks, decides what is a conflict

Comparing modification times across devices fails in practice: clocks drift, time zones and daylight-saving changes confuse naive code, and a device that was off for a month may have a wildly wrong clock. The question that matters is whether one version knew about the other. With a single server-assigned journal per namespace, the base version on each commit answers it exactly. In a system without a central sequencer — devices syncing peer to peer over a LAN, for example — version vectors do the job: each device keeps a counter, each version carries the vector of counters it has seen, and two versions conflict when neither vector is greater than or equal to the other in every position. Timestamps remain useful for display and for naming conflicted copies, never for deciding correctness.

Sharing turns a tree into a graph

Once a folder is shared it appears in several users' trees, possibly at different paths and nested inside folders with different permissions. "What can this user see?" stops being a path-prefix check. Modelling each shared folder as its own namespace, mounted into each member's root, keeps permissions and the change journal attached to the namespace rather than inherited down paths — so changing a share's members is one update, not a rewrite of every descendant, and each member's client follows that namespace's journal with its own cursor. Dropbox's own description uses exactly this abstraction.

The notification channel is a scale problem of its own

Fifty million connected clients must learn about changes within seconds. Polling the journal every three seconds would be over 16 million list calls a second, nearly all returning nothing. Long polling, or a persistent connection carrying only a "namespace changed" nudge, means the expensive list call happens only when something actually changed. The notification tier holds connections, maps namespaces to the connections interested in them (a user with 40 shared folders listens on 41 namespaces) and fans out nudges — the same connection-registry problem as a chat gateway, with far fewer messages per connection.

Selective sync and placeholders

A user with 2 TB in the cloud and a 256 GB laptop cannot hold everything locally. Modern clients show every file as a placeholder whose content is downloaded on open, using operating-system integration (file provider extensions on macOS, the cloud files API on Windows). This turns opening a file into a potential network operation, adds states such as "evicted" to the client's model, and is where much real-world complexity and many bug reports live. It also makes the block-level design pay off again: opening a large file can fetch its blocks in parallel, and blocks already present in other local files need not be downloaded.

Encryption versus deduplication

True end-to-end encryption means the server holds ciphertext encrypted with keys only the user has. Identical plaintext from two users then encrypts differently, so cross-user deduplication disappears, as do server-side previews and search. Convergent encryption derives each block's key from the hash of its plaintext, so identical blocks encrypt identically and dedup returns — but so does the confirmation-of-file attack, plus dictionary attacks on predictable files. There is no free option: a product chooses server-side encryption at rest with full dedup (Magic Pocket encrypts blocks at rest), or end-to-end encryption for selected folders with dedup scoped to them.

Durability arithmetic

Dropbox states an annual durability design target of over 99.9999999999% — twelve nines — for Magic Pocket. Intuitively: if a block is lost with probability 10−12 a year, then across 700 billion blocks you expect 0.7 lost blocks a year, which is why the target has to be that extreme. It is achieved by storing every block in at least two zones, erasure coding within a zone so data survives several simultaneous disk failures, spreading each machine's data over hundreds of others so a failed disk is rebuilt in parallel from many sources (shrinking the window in which a second failure could hurt), and verifying data continuously so silent corruption is found and repaired before redundancy runs out.

Boring technology for the index

Magic Pocket's engineers wrote that they could have built a distributed hash table or trie for the Block Index and instead "just opted for a giant sharded MySQL cluster", which simplified development and minimised unknowns, and that the system avoids quorum-style consensus where it can in favour of centralised coordination done in a fault-tolerant way — one master per cell, kept off the data path. The lesson for interviews is general: an index of hundreds of billions of fixed-size rows looked up by key is exactly what a sharded relational database does well, and operational familiarity is worth more than theoretical elegance. Choosing a well-understood component and explaining why it suffices is a senior signal, not a lack of ambition.

The sync loop is the failure you will actually debug

Two clients each see the other's write as new, rewrite the file and commit, forever, burning bandwidth and version history. Common causes are subtle: macOS and Linux normalise Unicode file names differently, so café.txt becomes two different byte strings; Windows and macOS file systems are case-insensitive by default while the server is case-sensitive, so Report.pdf and report.pdf chase each other; an application rewrites a file whenever it opens it, changing only a timestamp inside. Defences: normalise names to one canonical form, treat case-insensitive collisions explicitly, ignore echoes of the client's own commits (by device id and journal id), and rate-limit rewrites of the same path with an alert.

The real case: Dropbox's sync protocol and Magic Pocket

Dropbox has described both halves of this design in its own engineering posts. The sync protocol post explains the abstractions: a namespace is the root of a directory tree, each user owns a root namespace, and every shared folder is a namespace mounted within one or many root namespaces; a file is identified by namespace and relative path. Files are partitioned into 4 MB blocks hashed with SHA-256, and the list of hashes is the blocklist. The Server File Journal is the metadata database — "an append-only record where each row represents a particular version of a file" — with a journal id that increases monotonically within each namespace. Block servers keep a key-value store from hash to encrypted contents and know nothing about users or files; metadata servers hold users, namespaces and the journal. A client first tries to commit a blocklist; the server replies "need blocks" for unknown hashes; the client uploads them in size-limited batches and commits again. Idle clients hold a long-poll connection to a notification server; downloading clients call list with their per-namespace cursors, check for blocks locally first, then retrieve the rest. Dropbox pipelines all of this across files with separate threads for watching, hashing, committing, storing, listing, retrieving and reconstructing, and uses compression and rsync to shrink transfers. Streaming sync, which lets downloads start before the upload commits, improved sync latency by up to 2×.

The storage half is Magic Pocket. Dropbox announced in March 2016 that it had grown past 500 million sign-ups and 500 PB of user data (up from about 40 PB in 2012), and had moved from storing file content on Amazon S3 to its own infrastructure: a dark launch mirroring data in August 2014, serving files exclusively in-house from 27 February 2015, and over 90% of user data in-house by 7 October 2015, ahead of its 30 October goal, with no major disruptions or data loss. The design targets annual durability of over 99.9999999999% and availability over 99.99%. Its architecture post describes an immutable block store: blocks up to 4 MB, compressed and encrypted, keyed by SHA-256; aggregated into 1 GB buckets, replicated and later erasure coded; organised into cells of about 50 PB (each with a single master that coordinates repair but sits off the data path); and indexed by a Block Index that is "a giant sharded MySQL cluster" — chosen over a custom distributed key-value store because Dropbox already ran thousands of MySQL nodes. Every block lives in at least two zones, replicated across zones within a second of upload. Mutability lives above the block store, in the file journal — exactly the split this lesson teaches.

Failure modes and what to monitor

Sync latency end to end (commit on device A to file present on device B), by file size. Need-blocks ratio and bytes uploaded per committed byte, which show whether delta sync and dedup are working. Commit conflicts and conflicted copies created per day (a spike can mean a client bug, not users). Journal shard latency and the busiest namespaces. Notification lag and long-poll connection counts. Block store health: repair queue length, time to re-protect after a disk failure, and checksum verification failures found by background scrubbing. Orphaned block volume and garbage-collection lag. And client-side metrics — the share of devices stuck in a sync loop or with a growing pending-upload queue — because many real failures are only visible from the client.

Goal: measure how many chunks an edit forces you to upload with fixed-size chunks versus content-defined chunks. Python 3.12, standard library, a few seconds.

"""Fixed-size vs content-defined chunking: how many chunks must be re-uploaded after an edit?
Python 3.12 stdlib. Content-defined boundaries use a Gear rolling hash (as in FastCDC)."""
import hashlib, random

random.seed(42)
GEAR = [random.getrandbits(64) for _ in range(256)]   # one random 64-bit value per byte value
MASK = (1 << 13) - 1                                   # cut when low 13 bits are 0: ~8 KiB average
MIN, MAX = 2 * 1024, 64 * 1024

def fixed_chunks(data, size=8 * 1024):
    return [data[i:i + size] for i in range(0, len(data), size)]

def cdc_chunks(data):
    chunks, start, h = [], 0, 0
    for i, byte in enumerate(data):
        h = ((h << 1) + GEAR[byte]) & 0xFFFFFFFFFFFFFFFF   # the hash "forgets" bytes older than 64
        length = i + 1 - start
        if (length >= MIN and (h & MASK) == 0) or length >= MAX:
            chunks.append(data[start:i + 1]); start, h = i + 1, 0
    if start < len(data):
        chunks.append(data[start:])
    return chunks

def digests(chunks):
    return [hashlib.sha256(c).hexdigest() for c in chunks]

def report(name, before, after):
    have = set(digests(before))
    new = [c for c in after if hashlib.sha256(c).hexdigest() not in have]
    print(f"{name:>15}: {len(after):4d} chunks, {len(new):4d} new, "
          f"{sum(map(len, new)):>9,} bytes to upload")

original = random.randbytes(2 * 1024 * 1024)            # a 2 MiB file
edits = {
    "overwrite 100 B": original[:500_000] + b"X" * 100 + original[500_100:],
    "insert 100 B":    original[:500_000] + b"X" * 100 + original[500_000:],
    "insert at start": b"header v2\n" + original,
}
for label, edited in edits.items():
    print(f"\n{label}:")
    report("fixed 8 KiB", fixed_chunks(original), fixed_chunks(edited))
    report("content-defined", cdc_chunks(original), cdc_chunks(edited))

sizes = [len(c) for c in cdc_chunks(original)]
print(f"\nCDC chunk sizes: avg {sum(sizes) // len(sizes):,} B, min {min(sizes):,}, max {max(sizes):,}")
  1. Run it on the 2 MiB random file. For an in-place overwrite of 100 bytes, both schemes upload one chunk: fixed chunking is perfect for in-place edits.
  2. For a 100-byte insertion at 500,000 bytes, fixed chunking reports about 196 new chunks (about 1.6 MB to upload) while content-defined chunking reports 1 new chunk (about 17 KB). The boundaries after the insertion realigned.
  3. For an insertion at the very start (a new header line), fixed chunking must re-send all 257 chunks; CDC still sends one.
  4. Read the last line: average CDC chunk size is about 12 KB — the 8 KiB from the 13-bit mask plus the 2 KiB minimum — with a spread from the minimum up to tens of kilobytes. Change MASK to (1 << 16) - 1 and the average grows to about 48 KB, held down by the 64 KiB maximum (many chunks now hit it): fewer index entries, more bytes per edit.
  5. Try deduplication: append edits["copy"] = original and note zero new chunks — a duplicated file costs only metadata, which is also the privacy side channel discussed in deep dive C.

A user edits a 200 MB video project file. The edit inserts 50 KB of data 30 MB into the file. Chunk size averages 4 MB.

(a) With fixed-size chunking, how much must be uploaded? (b) With content-defined chunking? (c) The same user then duplicates the folder to make a backup. What is stored?

Answer

(a) Fixed-size chunking. The file is 50 chunks of 4 MB. Inserting 50 KB at offset 30 MB shifts every subsequent byte by 50 KB, so chunk boundaries at fixed offsets now fall on different content. Chunks 1–7 (0–28 MB) are unchanged. Chunk 8 contains the edit, and every chunk after it has shifted content and therefore a different hash. Upload: chunks 8 through 50 = 43 chunks ≈ 172 MB for a 50 KB edit — an amplification of roughly 3,500×. (An rsync-style delta of each changed block against the old version would find the shifted content and shrink the wire transfer dramatically, which is why fixed-block systems pair blocks with rsync; but 43 new blocks are still stored.)

(b) Content-defined chunking. Boundaries are determined by a rolling hash over the content itself, so after the inserted region the hash window re-synchronises with the original content within one chunk. Chunks before the edit are identical. The chunk containing the edit changes, and occasionally one following chunk changes as the boundary re-aligns. Upload: ~1-2 chunks ≈ 4-8 MB, and with smaller average chunk sizes, considerably less.

That is a 20× or greater reduction from one design choice, and it is the entire justification for the extra complexity of a rolling hash. Worth stating the cost honestly: chunk sizes become variable, you need a minimum and maximum to avoid pathological cases, and chunking is CPU work on the client.

(c) Duplicating the folder. Every block already exists in content-addressed storage, so the client hashes the chunks, asks which the server lacks, and the answer is none. Zero bytes are uploaded and zero new blocks are stored. What is created is metadata: a new set of file rows pointing at the same block hashes — a few kilobytes for a folder that appears to consume another 200 MB of the user's quota.

This exposes a real product question worth raising: does the user's quota count logical bytes or physical bytes? Consumer products bill logical (you appear to use 400 MB) because billing on dedup would mean your bill changes when a stranger uploads the same file — which is both confusing and a privacy leak. It also means storage revenue and storage cost are decoupled, which is why dedup is so valuable to the provider. Noticing that the technical choice has a billing consequence is exactly the kind of connection senior candidates make.

Diagnose it

After a client release, support tickets report "my files keep showing as syncing" and version history for some files grows by hundreds of versions a day with no visible changes. Most affected users share folders between a Mac and a Linux machine, and the affected files have accented characters in their names. What is going on?

Answer

A sync loop caused by Unicode normalisation. The same visible name (for example résumé.pdf) can be stored as precomposed characters (é as one code point) or decomposed (e followed by a combining accent). If one platform's file system or the new client normalises differently from the server, each client sees the other's path as a different file — or sees its own file renamed — and commits a "change" that the other then reverts. Each round trip creates a version. Fix: normalise all paths to one canonical form before hashing or comparing, migrate existing rows, make clients ignore echoes of their own commits by device and journal id, and add an alert on per-path commit rate so the next loop is caught by monitoring rather than by users.
