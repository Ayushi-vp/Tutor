Two engineers start a company. They rent one virtual machine from a cloud provider, install a database and a web server on it, and launch. It works. Six months later they have paying customers, and three things happen in the same quarter.

First, the machine's underlying host fails and the provider retires it. The machine restarts on new hardware, but the database files were on the instance's local disk, which doesn't survive a move, and the last backup is four days old. Second, a security researcher emails them: a storage bucket holding customer uploads is readable by anyone on the internet. They assumed "the cloud is secure" covered that; it doesn't. Third, a big outage in the provider's largest region takes them down for five hours, along with half the internet — and their status page, hosted in the same region, goes down with them, so customers can't even see that they know.

None of these is exotic. Each comes from not knowing the basic shape of what a cloud provider sells. What fails together and what fails separately (an instance, a building, a whole region). Which jobs the provider does and which stay yours. Which services are pinned to one building, which are spread across a region, and which are "global" but secretly managed from one place. The cloud is not one big reliable computer; it is a very large set of rentable parts with carefully defined boundaries, and every design decision in later topics — networks, databases, disaster recovery, cost — is about using those boundaries deliberately.

This lesson builds the map. It explains what "the cloud" is in operational terms (an API in front of pooled hardware, billed by use); the difference between the control plane that changes things and the data plane that runs them; regions, availability zones and edge locations as latency and failure boundaries; zonal, regional and global resources; the shared-responsibility model; the service models from virtual machines to serverless to SaaS; how to choose a region with real numbers; and the AWS, Google Cloud and Azure names for the same building blocks. The case is AWS's 2017 S3 outage in us-east-1, which shows almost every idea in one afternoon.

The easiest way into the cloud is to think of it as renting from a very large, very automated landlord.

Imagine a company that owns hundreds of warehouses full of identical shelving and machinery, spread across a few dozen cities. You never visit. You send a form — "I'd like four machines of this size, a locked storage room of 500 GB, and a private corridor connecting them" — and seconds later they exist, and a meter starts running. Send another form and they disappear, and the meter stops. That form is an API call (a request to the provider's web service), the machines are virtual machines, the storage room is a disk or a bucket, and the corridor is a virtual network.

The landlord groups its warehouses deliberately. Each city where it operates is a region: "US East (N. Virginia)", "Europe (Frankfurt)". A region is not one building. It is several separate sites, each called an availability zone (AZ), placed kilometres apart, each with its own power supply, cooling and network links, so a fire, a flood or a substation failure in one doesn't reach the others. The sites are linked by fast private fibre, so a machine in one zone can talk to a machine in another in a millisecond or two. On top of this, the landlord has hundreds of small kiosks — edge locations — in many more cities, which don't rent machines but run network services close to people: caching web content, answering DNS queries, filtering attacks.

Two more ideas complete the picture. First, the landlord and the tenant split the work, and the split is written down: the landlord guards the buildings, the machines and its own software; you guard what you put inside and who you give keys to. This is the shared-responsibility model, and most cloud security failures happen on the tenant's side of it. Second, you can rent at different levels of finish. You can rent bare machines and install everything yourself (IaaS, infrastructure as a service); rent a managed database or runtime and just use it (PaaS and managed services); hand over a function and pay per run (serverless); or rent finished software (SaaS). The more finished the thing you rent, the less you operate and the less you control.

Where the analogy breaks: a real landlord's building is either standing or not. Cloud services fail in subtler ways. The software that runs a whole region is shared across its zones, so a bad deployment or a software bug can take out every zone at once even though the buildings are fine. And the forms you send — the API — are themselves a service that can fail while everything already running keeps working. Those two facts, regional software as a shared failure domain and the split between the API that changes things and the systems that run them, are the two ideas in this lesson that matter most for senior-level design.

1. What a cloud provider actually sells

The most-cited definition is NIST's (the US National Institute of Standards and Technology, special publication 800-145, 2011). It lists five essential characteristics, and each one is worth reading as an engineering fact rather than marketing:

  • On-demand self-service. You get resources by calling an API, not by raising a ticket. A virtual machine typically takes tens of seconds to a couple of minutes to boot; a bucket exists the moment the call returns.
  • Broad network access. Everything is reached over the network through standard protocols — HTTPS APIs, SSH, database wire protocols.
  • Resource pooling. Many customers share the same physical hardware, separated by virtualisation and access control. You don't know or care which server you are on, which is why the provider can move you when hardware fails.
  • Rapid elasticity. You can add or remove capacity quickly, often automatically. "Quickly" has limits: the provider's spare capacity in a zone is finite, and your account has quotas.
  • Measured service. Usage is metered and billed: per second of instance time, per gigabyte-month stored, per million requests, per gigabyte transferred. Every architecture decision in the cloud is also a billing decision, which is why cl12 exists.

NIST also names deployment models: public cloud (a provider's shared infrastructure, sold to anyone), private cloud (the same style of self-service infrastructure run for one organisation), community cloud (shared by a group with common requirements), and hybrid (a combination connected together). This track is about public clouds, with AWS as the main example.

2. Everything is an API call: control plane and data plane

When you click "launch instance" in a web console, the console calls the same public API that the command-line tool and the SDKs call. A launch looks like this with the AWS CLI (this needs an AWS account; it's shown so you can see the shape):

aws ec2 run-instances --region us-east-1 \
  --image-id ami-0abc1234example --instance-type t4g.small \
  --subnet-id subnet-0123example --count 1

That request goes to the EC2 control plane: the set of services that authenticate you, check your permissions and quotas, choose a physical host in the zone your subnet lives in, allocate a network interface and an IP address, attach a disk built from the image, and start the virtual machine. It returns an instance ID like i-0a1b2c3d4e5f67890 long before the machine has finished booting. From then on, the running instance's network traffic, disk reads and CPU are handled by the data plane: the hypervisor on the host, the virtual network fabric, the storage servers behind the disk.

The split exists in every service. For S3, CreateBucket and PutBucketPolicy are control plane; GetObject and PutObject are data plane. For DNS (Route 53), creating a hosted zone or changing a record is control plane; answering a DNS query is data plane. The general term for control-plane actions is CRUDL: create, read, update, delete, list.

Why this matters: the two halves are built differently on purpose. Control planes are complex (many steps, many dependencies, workflow engines, databases of configuration) and run at low request rates. Data planes are simpler, handle vastly more traffic, and are engineered to keep working when the control plane is down — an instance keeps running and serving traffic even if nobody can launch a new one. AWS's fault-isolation whitepaper puts it bluntly: data planes are designed to be more available than control planes. So the rule senior engineers apply is: during an incident, depend only on data planes. Have capacity already running, DNS records already in place with health checks that flip them automatically, and credentials already issued. Don't plan to fix an outage by launching, creating or reconfiguring things.

A second consequence: control-plane APIs are often eventually consistent. The EC2 API documentation warns that right after you create a resource, a following call that describes or uses it may briefly fail with "not found", because the change hasn't propagated to every part of the control plane yet. Scripts and infrastructure tools retry with backoff for this reason (cl9 returns to this).

3. Regions

A region is a named geographic area where the provider runs a full, largely independent copy of its services: its own EC2 control plane, its own S3, its own DynamoDB, its own deployments of each service's software. On 7 October 2026 AWS listed 39 regions with 124 availability zones (and announced two more regions, in Saudi Arabia and Chile); Google Cloud listed 43 regions with 130 zones; Azure lists its regions and which of them have zones in its documentation. Each region has a code — us-east-1, eu-central-1, ap-south-1 — that you pass on every API call. Calling the API in one region doesn't show you resources in another: an instance in Frankfurt is invisible to describe-instances in Virginia.

Region independence is the reason regions are the unit of disaster recovery. Because each region runs its own copy of the software, a bad deployment or a software bug in one region's DynamoDB should not affect another region's. Providers deploy changes to one region (and inside it, one zone) at a time precisely so a bad change hits a limited area. It also means data does not leave a region unless you, or a service you configured, move it — which is what makes regions the unit of data residency, the legal requirement that certain data stay in certain countries.

There is one level above regions on AWS: the partition. The commercial regions form the aws partition; China's regions (aws-cn) and the US government's GovCloud regions (aws-us-gov) are separate partitions with separate accounts, separate control planes and separate identity systems. Nothing is shared across partitions, which is why resource names (ARNs, covered below) include the partition.

4. Availability zones

An availability zone is one or more physical data centres inside a region with separate, redundant power, networking and connectivity. AWS's fault-isolation whitepaper says zones in a region are "meaningfully distant from each other, up to 60 miles (~100 km)", far enough that a utility failure, flood, fire or earthquake shouldn't hit two at once, but close enough for synchronous replication "with single-digit millisecond latency". Generators and cooling are not shared, and zones are fed from different power substations. Azure's documentation gives the same picture: zones typically several kilometres apart and usually within 100 km, with a target inter-zone round trip of under about 2 ms.

That latency is the whole point. Synchronous replication means a write is acknowledged only after it is stored in two places. If the places are 2 ms apart, every write costs about 2 ms extra — acceptable for a database. If they were 65 ms apart (Virginia to Frankfurt), every committed transaction would wait 65 ms, which is why cross-region replication is almost always asynchronous (the write is acknowledged locally and copied later, so a region loss can lose the last few seconds of writes — the RPO you met in sc17).

Zones change how you deploy everything. A managed database in "Multi-AZ" mode keeps a standby in a second zone and fails over to it automatically. A load balancer has nodes in each zone you enable. An autoscaling group spreads instances across zones. The EC2 service-level agreement shows the provider's own view of the arithmetic: on 7 October 2026 it promised 99.5% monthly uptime for a single instance, but 99.99% for the region-level case of instances deployed across two or more zones.

Two practical details trip people up. First, zone names are per account. AWS maps the physical zones to the letters us-east-1a, -1b and so on randomly for each account, so everyone's "a" isn't the same overloaded building. The stable name is the AZ ID, like use1-az1, which means the same physical zone for every account. You need AZ IDs whenever two accounts must agree on a location. Second, cross-zone traffic costs money on AWS: $0.01 per GB in each direction between zones in the same region on 7 October 2026 (from the AWS price list), so a chatty service sending 50 TB a month across zones pays about $1,000 for the privilege. Azure, by contrast, states that it does not charge for data transfer between zones in a region. cl3 and cl12 return to this.

5. Edge locations, Local Zones and other extensions

Regions are few and large; users are everywhere. Providers fill the gap with smaller sites. Edge locations (points of presence, PoPs) run network-facing services close to users: the CDN cache (CloudFront on AWS), authoritative DNS (Route 53), web application firewalls and DDoS protection, and lightweight edge compute. AWS listed more than 750 CloudFront PoPs plus 15 regional edge caches on 7 October 2026; Google listed more than 200 network edge locations. You don't run virtual machines there; you configure services that run there. net12 covers how traffic is steered to them.

Between the two sit extensions of a region. A Local Zone (AWS had 46) places a small set of services — instances, disks, some databases — in a metropolitan area for single-digit-millisecond latency to users there; it hangs off a parent region and depends on it for its control plane. Wavelength Zones sit inside telecom operators' 5G networks. Outposts are racks of AWS hardware installed in your own data centre, managed from a parent region. Each extension trades breadth of services and independence for proximity.

6. Zonal, regional and global resources

Every resource you create has a scope, and the scope tells you what fails with it and what you must do for resilience. This is the single most useful table to memorise:

The scope also differs between providers, which matters when you translate a design. On AWS a subnet lives in exactly one zone, so "three zones" means three subnets per tier. On Azure and Google Cloud a subnet is regional and spans zones; you choose zones per resource instead. A Google Cloud VPC network is global — one network can have subnets in many regions — whereas an AWS VPC or an Azure virtual network is regional. Same concepts, different boundaries.

"Global" deserves care. Global services still separate control and data planes, and AWS's whitepaper lists where their single control planes live. In the aws partition, IAM's control plane is in us-east-1, as are those of AWS Organizations, Route 53 (public and private DNS), CloudFront, and the certificate service used by CloudFront; Route 53 Application Recovery Controller and Global Accelerator keep theirs in us-west-2. The data planes — checking a request's signature and permissions, answering DNS queries, serving cached content — are distributed to every region or edge location. So a us-east-1 problem shouldn't stop your eu-west-1 application from authenticating requests, but it could stop you creating a new IAM role or editing a DNS record anywhere. Even some regional-looking actions have a global dependency: creating or deleting any S3 bucket checks global name uniqueness in us-east-1, and SDKs historically defaulted to the global STS (temporary-credential) endpoint, which is in us-east-1, unless configured to use a regional one.

7. Naming things: accounts and ARNs

Resources belong to a container that is also the unit of billing and of security isolation. On AWS that container is an account (a 12-digit number); on Google Cloud it is a project; on Azure it is a subscription holding resource groups. Many organisations run dozens or hundreds of accounts — one per environment and team — under an organisation; cl13 covers that structure. Every AWS resource has an ARN (Amazon Resource Name) that encodes the partition, service, region, account and resource:

arn:aws:s3:::invoices-prod-eu                         (S3: no region or account in bucket ARNs)
arn:aws:ec2:eu-central-1:123456789012:instance/i-0a1b2c3d4e5f67890
arn:aws:iam::123456789012:role/payments-api           (IAM: global, so no region)

Notice the empty region field for IAM — the name itself tells you the resource is global. ARNs matter because permissions (cl2) are written against them.

8. The shared-responsibility model

AWS's wording is the standard one. The provider is responsible for "security of the cloud": "protecting the infrastructure that runs all of the services offered in the AWS Cloud" — facilities, hardware, the hypervisor, the network, and the software of its managed services. The customer is responsible for "security in the cloud", and that responsibility "will be determined by the AWS Cloud services that a customer selects".

The phrase "determined by the services" is the key. For EC2, the customer owns "the guest operating system (including updates and security patches), any application software or utilities installed by the customer on the instances, and the configuration of the AWS-provided firewall (called a security group)". For abstracted services such as S3 and DynamoDB, AWS runs the infrastructure, OS and platform, and customers "are responsible for managing their data (including encryption options), classifying their assets, and using IAM tools to apply the appropriate permissions". Some controls are explicitly shared: AWS patches the infrastructure, you patch your guest OS and applications; AWS configures its devices, you configure your OS, databases and applications; AWS trains its staff, you train yours.

The single most important consequence: identity and access configuration is always yours. A bucket made public by a policy, an access key committed to a repository, a role that any account in the world can assume — none of these are provider failures, and cl2 and cl13 spend most of their time on them.

9. Service models: from virtual machines to SaaS

The same small web application — an HTTP API, a PostgreSQL database and a nightly report job — can be run at five levels of "finish". Walking it through each makes the trade-offs concrete:

  • IaaS. Rent three virtual machines (EC2, Compute Engine, Azure Virtual Machines). Install the OS packages, the runtime, PostgreSQL, a cron daemon. You patch, back up, monitor disks, fail the database over by hand or with your own tooling. Most control, most work. Cost: about $0.0168 an hour for a t4g.small in us-east-1, so roughly $12 a month per machine, plus disks.
  • Managed services (PaaS-style). Keep the API on a VM or container, but rent PostgreSQL as a managed service (RDS, Cloud SQL, Azure Database for PostgreSQL). The provider installs, patches, backs up and fails over the database; you choose size, parameters and who can connect. A db.t4g.micro PostgreSQL instance was $0.016 an hour single-zone and $0.032 multi-zone on 7 October 2026 — you pay double for the standby, which is the honest price of zone failover.
  • Containers as a service (CaaS). Package the API as a container image (k8s1–k8s3) and run it on Fargate, Cloud Run or Azure Container Apps: no servers to manage, you choose CPU and memory per task. Or run Kubernetes (EKS, GKE, AKS), where the provider runs the control plane and you run what's on it.
  • Serverless functions (FaaS). Turn the report job into a function (Lambda, Cloud Run functions, Azure Functions) triggered by a schedule. It runs a few minutes a night and costs cents; when idle it costs nothing. Maximum run time, cold starts and concurrency limits now become your design constraints — cl5 is about exactly this.
  • SaaS. Replace the reporting with a hosted analytics product. You configure it and give it data; the vendor runs everything. You inherit its availability, its data location and its security posture, which you now have to assess as a vendor risk.

"Serverless" is used more broadly than functions: any service where you never size servers and pay for use — S3, DynamoDB on-demand, SQS — is often called serverless. The useful test is: do I provision capacity, and do I pay when idle? If no and no, it's serverless in the sense that matters for cost and operations.

11. Choosing a region, worked with numbers

A company in London is launching a product whose customers are mostly in the UK and Germany, with a growing group in India. Walk the decision in the order of what's hardest to change.

Step 1: hard constraints. Contracts with German enterprise customers require personal data to stay in the EU. That removes us-east-1 as the primary and points at an EU region: Frankfurt (eu-central-1), Ireland (eu-west-1) or others. (London, eu-west-2, is in the UK, which is outside the EU, so check whether contracts say "EU" or "EEA or adequate country" — a legal question, not a technical one.) Then check the services: if the product needs a particular GPU instance type or managed model, confirm it is offered in the candidate region. Instance families launch region by region; on 7 October 2026, for example, the p5.48xlarge (8 × H100) appeared in the on-demand price lists for us-east-1, us-west-2, Mumbai, Tokyo and São Paulo but not for Frankfurt.

Step 2: latency. Light in optical fibre travels at about two-thirds of its speed in a vacuum, roughly 200,000 km/s, so every 100 km of fibre adds about 0.5 ms one way, 1 ms round trip. Real paths are longer than great circles and pass through routers, so measured round trips are typically 1.5–2× the floor. Great-circle distances give the floors:

PathDistanceMinimum round trip
London ↔ Frankfurt~640 km~6 ms
London ↔ N. Virginia~5,900 km~59 ms
Mumbai ↔ Frankfurt~6,560 km~66 ms
Mumbai ↔ N. Virginia~12,900 km~129 ms

A page that needs four sequential round trips to the API (a TLS handshake, an auth call, two data calls) costs about 25 ms of pure physics from London to Frankfurt and about 260 ms or more from Mumbai to Frankfurt. Frankfurt is fine for the UK and Germany; Indian users will notice, and the mitigations are a CDN for static content, fewer round trips, and — if the business grows there — a second regional deployment in Mumbai (ap-south-1).

Step 3: price. From the AWS price list on 7 October 2026, an m7i.large Linux instance cost $0.1008/hour in us-east-1, $0.12075 in Frankfurt (+20%), $0.10605 in Mumbai (+5%), $0.1302 in Tokyo (+29%) and $0.16065 in São Paulo (+59%). For a fleet of 40 such instances running all month (730 hours), Frankfurt costs 40 × 730 × 0.12075 ≈ $3,526 against $2,943 in Virginia — a real but secondary difference next to residency and latency. Data transfer prices differ by region too.

Step 4: quotas and capacity. New accounts start with modest per-region quotas, for example on the number of vCPUs of on-demand instances, and GPU quotas often start at zero. Request increases well before launch. Large instance types can be scarce in a particular zone; spreading across zones and keeping a second instance type as a fallback helps (cl4).

Decision: primary region eu-central-1 across three zones; backups copied to a second EU region for disaster recovery; CDN in front; revisit a Mumbai deployment when Indian traffic justifies the operational cost.

Static stability is the design principle behind zones

AWS's Builders' Library describes how EC2 itself is built to be statically stable: when a zone fails, the instances in the other zones keep running without anything needing to happen — no new launches, no configuration changes, no control-plane calls. The same principle applies to your systems. A service running at 60% utilisation in each of three zones loses a third of its capacity when one zone fails, and the remaining two must run at 90%: survivable. A service running at 85% in each zone would need 127% in the remaining two, so it must scale up during the incident, which means calling the EC2 control plane at exactly the moment thousands of other customers are trying to do the same in the same region. Pre-provisioning enough capacity to absorb a zone loss costs money every day; it buys you not depending on the most contended resource during an incident. For N zones, the steady-state utilisation ceiling is (N−1)/N: 67% for three zones, 75% for four.

Zones are independent for hardware, not for software

Zones are built so that physical events don't correlate: different substations, separate cooling, separate buildings. But every zone in a region runs the same build of the same regional services, configured by the same automation. A bad configuration push, a latent bug triggered by load, or a dependency that every zone shares (DNS automation for a regional endpoint, a regional metadata store) fails them together. Providers reduce this with zone-by-zone deployments and cell-based architectures, but they can't eliminate it, and the largest incidents in AWS's public history — S3 in 2017, the internal network event in December 2021, DynamoDB's DNS race in October 2025 — were regional, not zonal. For a senior design, this is the reason "multi-AZ" and "disaster recovery" are separate line items.

Capacity is finite, and it's per zone

"Rapid elasticity" is a statistical promise, not a guarantee. Each zone has a finite number of hosts of each type. When demand for a type spikes — a popular GPU, or everyone failing over after an incident — launches fail with an insufficient-capacity error even though your quota allows them. That's why providers sell capacity reservations (pay to hold capacity whether you use it or not) and why autoscaling groups are configured with several instance types and all zones. For GPU work, capacity is often the binding constraint rather than price, and cl14 treats it as a first-class design input.

Data gravity and lock-in are mostly about data and identity, not compute

Moving a stateless service between regions or providers is a deployment exercise. Moving 500 TB of data is not: at $0.09/GB for internet egress from AWS, that's about $46,000 in transfer charges alone (AWS and the other major providers have announced waivers of egress charges for customers leaving entirely, under conditions — check current terms), plus weeks of copy time and a cutover plan. Identity is the other anchor: hundreds of IAM roles, trust relationships and policies written in one provider's language. Managed services add a third: an application built on DynamoDB's API and semantics doesn't run on Cosmos DB without changes. A senior answer to "how do we avoid lock-in" is to be deliberate about which of these you accept in exchange for what, not to avoid managed services wholesale.

Partitions and sovereign regions are separate clouds

China (aws-cn) and GovCloud (aws-us-gov) are separate partitions: different accounts, separate IAM, separate control planes, service sets that lag the commercial partition. Providers are building more such separations for sovereignty requirements — clouds operated by in-country staff, with control planes inside a jurisdiction. Designs that assume "one AWS" (cross-account roles, a single organisation, global services) don't extend across partitions. If a product must serve such a market, plan it as a second deployment with its own identity and tooling.

The provider's abstraction has a shape you will hit

Every managed service exposes limits that come from its internals: maximum object sizes, request rates per key prefix or partition, connection limits, maximum function durations, API rate limits on the control plane. These are documented per service as quotas (some adjustable, some fixed). Senior engineers read the quota page before choosing a service, because a design that needs 10× a hard limit is a redesign, not a support ticket. cl10 returns to quotas as a reliability risk.

Pricing follows the architecture of the provider

Prices reveal what's expensive for the provider. Inbound data is free because it fills otherwise idle capacity; outbound internet traffic is billed because it consumes transit. Cross-zone traffic on AWS costs $0.01/GB each way because it crosses metro fibre between buildings. Standby replicas cost as much as primaries because they occupy the same hardware. Reading a price sheet as a description of the provider's costs helps you predict which designs will be cheap — and is the theme of cl12.

Characteristic failures

The single-zone production system. Everything works until a zone has a power or network event; then the database, which nobody configured as Multi-AZ, is unreachable for hours. Symptom: a zone-specific event on the provider's health dashboard and 100% errors. Prevention: an inventory of every stateful component and its zone placement, and a rule in infrastructure-as-code reviews that production data stores are multi-zone.

The multi-zone design with a zonal single point. Compute spans three zones, but there's one NAT gateway in one zone, or one cache node, or a self-managed database primary. When that zone fails, the "multi-AZ" system fails. NAT gateways are a classic case because they are created per zone and cost money each, so teams create one (cl3).

Gray failure in a zone. A zone doesn't fail cleanly; it gets slow, or loses a fraction of packets. Health checks pass, but latency and errors rise for requests routed there. The mitigation is zonal observability (metrics broken down by zone) and the ability to shift traffic away from a zone — AWS offers zonal shift for load balancers in Route 53 Application Recovery Controller for this reason.

Hidden regional dependencies. The application runs in eu-west-1, but the CI/CD system, the container registry, the secrets store, the status page or the identity provider is in us-east-1. A us-east-1 event then blocks deploys, sign-ins or communication even though production is fine. Inventory where your tooling runs.

Control-plane dependent recovery. The runbook says "launch replacement instances" or "update the DNS record". During a large regional event, those APIs are throttled or failing. Prefer pre-provisioned capacity and health-check-driven DNS failover.

Quota and capacity surprises. A launch day or a failover hits the per-region vCPU quota, or a zone has no capacity for the chosen instance type. Monitor quota utilisation (Service Quotas exposes it as metrics), request headroom ahead of events, and configure instance-type diversity.

What to watch

The provider's own signals: the AWS Health Dashboard (with account-specific events for your resources), Google Cloud Service Health and Azure Service Health. Your own: error rate and latency broken down by zone and region, quota utilisation, and the inventory of resource scopes. Many teams subscribe health events to their alerting so a provider notice reaches on-call before customers do.

The case: Amazon S3 in us-east-1, 28 February 2017

At 9:37 AM PST, an S3 team member was debugging a slow billing system and ran an established playbook command to remove a small number of servers from one S3 subsystem. One input was entered incorrectly, and a much larger set of servers was removed — including servers supporting two other subsystems: the index subsystem, which manages the metadata and location of every object in the region, and the placement subsystem, which allocates storage for new objects. Both had to be fully restarted, which they hadn't been in years, and the restart and safety checks took longer than expected because of the region's growth. The index subsystem began serving requests again at 12:26 PM and was fully recovered at 1:18 PM; placement finished recovering at 1:54 PM.

Because S3 is a dependency of other services, the impact spread: the S3 console, new EC2 instance launches, EBS volumes that needed data from S3 snapshots, and Lambda were impaired. AWS's own Service Health Dashboard couldn't be updated until 11:37 AM because its administration console depended on S3, so AWS communicated through Twitter and a banner. AWS changed the tool to remove capacity more slowly and to refuse to take any subsystem below its minimum capacity, audited other tools for the same risk, and prioritised splitting the index subsystem into smaller cells to cut recovery time.

Read as an engineer, the event shows the ideas of this lesson in order. The failure was regional software, so all zones were hit at once. Recovery took much longer than the fault (seconds to type, hours to restart) because rarely exercised restart paths are slow. Dependencies chain: services you didn't know used S3 failed with it. A monitoring system that shares fate with what it monitors goes dark exactly when needed. And human operations on a control plane need guard rails proportional to blast radius.

Goal: build a small model of regions, zones and resource scopes, and use it to answer "what survives this failure?" and "how much headroom do I need?" — Python 3.12 standard library only. About 15 minutes. No cloud account needed.

  1. Inventory. Write a list of dicts describing a system: {"name": "api-1", "scope": "zonal", "region": "eu-central-1", "az": "euc1-az1", "tier": "api"}, plus two more API instances in az2 and az3, a database primary in az3 and a standby in az2, one NAT gateway in az1, an S3 bucket (regional) and an IAM role (global, home region us-east-1 for its control plane).
  2. Failure function. Write survivors(inventory, failed), where failed is a set of zone IDs or region names. A zonal resource dies if its zone or region failed; a regional one if its region failed; a global one survives (note separately whether its control plane's region failed).
  3. Tier check. For each tier, report whether at least one member survives. Fail zone euc1-az1: which tier loses all members? (Expect the NAT tier.) Fail eu-central-1: everything regional and zonal is gone.
  4. Headroom. Write max_util(n_zones) returning (n−1)/n, and needed_util(load, per_zone_capacity, n, lost=1). With 3 zones of 100 units and total load 210, what utilisation do the survivors run at after one loss?
  5. Latency floor. Write a haversine function and compute minimum round trips (2 × km ÷ 200,000 km/s) for London–Frankfurt and Mumbai–Virginia.

What to look for: step 3 shows that "multi-AZ" is a property of every tier, not of the system — one zonal NAT gateway breaks it. Step 4 gives 105% for the survivors, so 210 units of load is too much for three zones of 100: the ceiling is 200 (67% each). Step 5 should give about 6 ms and 129 ms, matching the table in the body.

Needs an AWS account (optional): aws ec2 describe-availability-zones --region eu-central-1 --query "AvailabilityZones[].[ZoneName,ZoneId]" --output table lists your zone names next to their AZ IDs; compare with a colleague's account to see the mapping differ.

Review: "we're highly available"

A team describes its production system in us-east-1: an Application Load Balancer across three zones; six API instances in an autoscaling group across three zones, running at about 80% CPU at peak; a PostgreSQL database on RDS in single-AZ mode with daily snapshots; one NAT gateway; a Redis cache on one node; the status page and CI runners on a VM in the same region. Their runbook for a zone failure says: "the autoscaling group will launch replacements; restore the database from the latest snapshot if needed." Identify the risks in priority order and propose changes.

Answer

1. Single-AZ database (highest). A zone failure takes the only database down, and restoring from a daily snapshot means up to 24 hours of lost data and an hour or more to restore. Switch to Multi-AZ (synchronous standby, automatic failover in about a minute or two), and enable point-in-time recovery so RPO is minutes for logical errors too.

2. Zonal single points: one NAT gateway, one Redis node. Losing the NAT gateway's zone cuts outbound internet for all private instances; losing the Redis node either stalls the API or stampedes the database. Use one NAT gateway per zone with per-zone routes, and a replicated cache with automatic failover — or make the API survive a cold cache.

3. Not statically stable. At 80% utilisation across three zones, losing one puts the survivors at 120%. The runbook relies on launching replacements during a regional rush on capacity. Run at most ~65% at peak (or add capacity so that two zones carry peak), and treat autoscaling as a bonus.

4. Shared fate for tooling. The status page and CI in the same region go dark in a regional event, exactly when needed. Move the status page off the provider or to another region; make sure deploys and break-glass access don't depend on us-east-1 alone.

5. Missing disaster recovery. Nothing survives a regional event. Decide RTO/RPO with the business (sc17); at minimum copy backups to another region and rehearse a restore (cl10).

6. Test it. Run a zone-evacuation game day (shift traffic away from one zone, fail the database over) and measure.
