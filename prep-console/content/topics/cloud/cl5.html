A team building a photo-sharing feature writes its upload handler as a function. It's wonderful: no servers, deploys in seconds, costs a few dollars a month. So they write everything else as functions too — a resize function, a moderation function, a notification function, an indexing function, stitched together with a workflow service, with images passed between steps through object storage.

Then a marketing campaign brings ten times the usual traffic in an hour. Requests start failing with "Rate exceeded" because all the functions share one account-wide concurrency quota and the indexing backlog has eaten it. The database behind the notification function falls over because 900 function instances opened 900 connections at once. Some users get two notifications, because a timed-out step was retried after it had already sent one. And at the end of the month the bill's biggest lines aren't compute at all: they're workflow state transitions and storage requests from passing images between steps.

Nothing here is a bug in the platform. Each is a property of the serverless execution model that the team never had to think about at low volume: how execution environments are created and reused, how concurrency is counted and capped, how each kind of event source retries, what a cold start is, and how the pricing units behave at scale. The same properties are what make serverless excellent for the right workloads — bursty event handling, glue between managed services, jobs that run a few minutes a day.

This lesson takes the functions-as-a-service model apart using AWS Lambda as the concrete system. It covers the execution environment and its lifecycle, cold starts and the tools against them, concurrency maths and limits, the three invocation models and their retry semantics, timeouts and payload limits, a worked cost comparison against a container at 1 million and 100 million requests a month, and the signals that serverless is the wrong answer. The case is Prime Video's 2023 write-up of moving a monitoring service from Step Functions and Lambda to a monolith on containers and cutting its cost by more than 90%.

Think of a function platform as a hotel with an unusual check-in policy. You don't rent a room by the month. Each time a guest (a request) arrives, the hotel gives them a room for exactly as long as they need it and bills you by the minute, scaled by the size of the room. When the guest leaves, the room isn't torn down; it's kept made up for a while in case another guest of the same kind arrives, who can then walk straight in. If many guests arrive at once and no prepared rooms are free, the hotel has to prepare new ones, and those guests wait in the lobby while it does. The hotel has a rule that your company can't occupy more than a certain number of rooms at once, across all your guests of all kinds.

Map it across. The room is an execution environment: a small, isolated virtual machine (a microVM) with the memory you configured, your code and its runtime. A request occupies one environment for its duration (on standard Lambda, one request per environment at a time). Preparing a new room is the Init phase — start the runtime, load your code, run your initialisation — and a guest who waits for it experiences a cold start. A room kept made up is a warm environment, frozen between requests and reused. The occupancy rule is the concurrency quota. And the per-minute, per-room-size billing is the GB-second.

The model gives you three things that are hard to get otherwise: no capacity planning (environments appear as requests arrive), no idle cost (frozen environments are free and unused functions cost nothing), and strong isolation (each environment is its own microVM). It takes away three things: control over the machine, long-running work (a request may run at most 15 minutes), and cheapness at high steady volume, because you pay a premium for every unit of work in exchange for paying nothing for idle.

A useful way to hold the whole model in your head is as three dials you never see on a server. The memory dial sets the size of each room and, with it, how much CPU the guest gets and how much each minute costs. The concurrency dial is the occupancy rule — for the account, and optionally per function. The timeout dial is the maximum stay. Almost every serverless incident is one of these dials set without thinking about the others: memory too low so requests run long, which raises concurrency, which hits the occupancy limit; or a timeout longer than the caller's patience, so work continues after nobody is waiting for it.

Where the analogy breaks: a hotel's lobby is a polite queue. Lambda's is not, for synchronous calls — if no room is available and you're at your occupancy limit, the guest is turned away immediately with an error (a throttle), and it's the caller's job to try again. Only asynchronous and queue-fed invocations wait in a real queue. Knowing which kind of caller you have decides how your system behaves at the limit.

1. The execution environment

Lambda runs each environment in a Firecracker microVM — a minimal virtual machine monitor AWS built for this purpose and described in an NSDI 2020 paper, designed to boot in about 125 ms with a few megabytes of overhead per VM. That's what lets Lambda give every environment a hardware-virtualisation boundary (stronger than containers sharing a kernel, k8s1) while creating them on demand.

You configure an environment mainly through memory: 128 MB to 10,240 MB in 1 MB steps. CPU is allocated in proportion to memory; per the Lambda quotas page, at 1,769 MB a function has the equivalent of one vCPU, and at 10,240 MB up to six. Network bandwidth per environment is 625 Mbps by default. Each environment has a /tmp directory of 512 MB to 10,240 MB, a limit of 1,024 file descriptors and 1,024 processes or threads. Code is a zip (50 MB zipped upload, 250 MB unzipped including layers) or a container image up to 10 GB. You choose x86_64 or arm64; Arm is about 20% cheaper per GB-second.

On standard Lambda, an environment handles one request at a time. Ten simultaneous requests need ten environments. That one fact explains most of what follows: concurrency maths, connection storms against databases, and why globals are safe within an environment.

2. The lifecycle, phase by phase

AWS's documentation describes the lifecycle as phases, each started by an event to the runtime and to any extensions (helper processes for telemetry, secrets and the like):

  • Init. Start extensions, bootstrap the runtime (the Python interpreter, the JVM, the Node.js process) and run your code outside the handler — imports, SDK clients, configuration, connection pools. On-demand functions get 10 seconds for Init; if it doesn't finish, Lambda retries Init at the first invocation under the function timeout. (With provisioned concurrency, SnapStart or Managed Instances, init can run much longer.) Since 1 August 2025, Init is billed for every configuration; previously, managed runtimes packaged as zip files didn't pay for it.
  • Invoke. Lambda calls your handler with the event. The function timeout, at most 900 seconds (15 minutes), bounds this phase, including time extensions spend after the handler returns.
  • Freeze. When the handler and extensions report done, Lambda freezes the environment. Nothing runs and nothing is billed. Globals, open connections and files in /tmp remain. Background threads you started also freeze and resume on the next request, which surprises people.
  • Thaw and reuse. The next request for the same function version may land on a frozen environment, which thaws and goes straight to Invoke: a warm start.
  • Shutdown. Eventually Lambda retires the environment, giving extensions up to 2,000 ms to clean up. AWS states it recycles environments every few hours even for functions invoked continuously, so nothing can live forever.

Failures reset the environment: if a handler crashes or times out, Lambda tears down the runtime and the next request on that environment pays a new ("suppressed") Init, which shows up as extra duration in the next REPORT log line.

Every invocation ends with a REPORT line in the function's logs, which is the best place to see all of this in numbers:

REPORT RequestId: 527cb862-… Duration: 118.42 ms Billed Duration: 119 ms
Memory Size: 512 MB Max Memory Used: 141 MB Init Duration: 412.07 ms

Init Duration appears only on cold starts. Billed duration is rounded up to the millisecond.

3. Cold starts: anatomy and remedies

A cold start is the latency a request experiences when it waits for a new environment: placing and booting the microVM, downloading the code, and Init. AWS's documentation says cold starts typically occur in under 1% of invocations and range from under 100 ms to over a second. The variation comes from a few sources: the runtime (compiled languages and lightweight interpreters start faster than a JVM loading a framework), the package size (more to download and load), and above all what your init code does (importing a large ML library, fetching secrets, opening connections).

Three facts make cold starts matter more than "under 1%" suggests. They concentrate at scale-out moments — a burst that needs 400 new environments produces 400 cold starts in the same few seconds, exactly at the busiest time. They concentrate on low-traffic functions, where every request may find no warm environment. And they compound in call chains: a request that passes through three functions can hit three cold starts.

The remedies, roughly in order of cost:

  1. Do less at init. Import only the modules you need (AWS's own example: load the DynamoDB client, not the whole SDK), make rarely used dependencies lazy, keep packages small, avoid network calls in init that could be deferred.
  2. Choose the runtime and memory deliberately. More memory brings more CPU, which shortens CPU-bound init; Arm and x86 differ by workload — measure.
  3. SnapStart. For supported runtimes (Java, Python, .NET), Lambda runs Init once when you publish a version, snapshots the initialised memory and disk, and restores new environments from it. Code must be "snapshot-safe": anything unique created during init (random seeds, IDs, temporary credentials, connections) is cloned into every restored environment, so it must be regenerated in an after-restore hook.
  4. Provisioned concurrency. Lambda keeps N environments initialised for a version at all times; requests up to N never cold-start. You pay for the provisioned capacity whether used or not — $0.0000033334 per GB-second on Arm in us-east-1 (October 2026), about 25% of the on-demand duration price — plus a reduced duration rate when invoked. Ten 1 GB environments provisioned all month cost about 10 × 1 × 730 × 3,600 × $0.0000033334 ≈ $87.60.

4. Concurrency: the number that governs everything

Concurrency is how many requests a function is handling at the same moment — on standard Lambda, the number of busy environments. It follows from Little's law: average concurrency = arrival rate × average duration. An API receiving 400 requests per second, each taking 150 ms, runs at 400 × 0.15 = 60 concurrent executions. Double the duration (a slow database) and concurrency doubles with no change in traffic — which is why downstream slowness turns into concurrency exhaustion.

Two limits bound it (October 2026 defaults):

  • Account concurrency per region: 1,000 concurrent executions by default, shared by every function in the account in that region, raisable to tens of thousands. New accounts may start lower. When it's exhausted, synchronous calls fail with 429 TooManyRequestsException.
  • Per-function scaling rate: each function can add up to 1,000 execution environments every 10 seconds. A function idling at 50 environments that suddenly needs 2,500 reaches it no sooner than about 25 seconds later, given enough account quota.

Two settings shape it per function. Reserved concurrency sets aside N from the account pool for a function and also caps it at N — the cap is often the more useful half, because it stops one function from starving the rest or from flooding a database. Provisioned concurrency, above, pre-initialises environments and doesn't by itself cap anything.

Work an example. A flash sale sends 5,000 requests per second to a checkout function averaging 200 ms: concurrency 1,000. That's the entire default account quota. Every other function in the account — order processing, the webhook handler — now throttles too. The fix is not only "raise the quota": reserve concurrency for checkout (and cap the less important functions), raise the account quota ahead of the event, and check the database can take 1,000 concurrent clients (it usually can't; use RDS Proxy or a queue).

5. Invocation models and their retry semantics

How a function is invoked decides what happens on errors, throttles and overload. There are three models:

Synchronous. The caller waits for the response: API Gateway, function URLs, Application Load Balancers, and direct Invoke calls with RequestResponse. Request and response payloads are limited to 6 MB each (streamed responses up to 200 MB). Errors and throttles return to the caller, which decides whether to retry. A client retrying aggressively during a throttle makes the overload worse (sc12): use backoff with jitter.

Asynchronous. S3 notifications, SNS, EventBridge and Invoke with InvocationType=Event hand the event to Lambda, which puts it in an internal queue and returns HTTP 202 immediately; payloads are limited to 1 MB. Per the documentation: on function errors (including timeouts) Lambda retries twice, waiting about one minute and then two; on throttles and system errors it returns the event to the queue and retries for up to six hours by default, with backoff growing to five minutes. Events older than the maximum event age, or that fail every attempt, are discarded unless you configure an on-failure destination or a dead-letter queue. The documentation also warns that the same event may be delivered more than once even without errors, and that under extreme backlog events can expire before being processed.

Polling (event source mappings). For SQS, Kinesis, DynamoDB Streams, Kafka and others, Lambda runs pollers that read records and invoke the function synchronously with batches. For a standard SQS queue, the documentation describes the default scaling: five concurrent batches when messages appear, adding up to 300 concurrent invocations per minute while messages remain, to a maximum of 1,250 by default; a maximum concurrency setting (2 to 1,000) caps it, and a provisioned mode scales faster at extra cost. If the function fails, the batch's messages become visible again after the queue's visibility timeout and are retried until the queue's redrive policy moves them to a dead-letter queue — unless the function reports a partial batch response listing only the failed IDs. For streams, records are processed in order per shard, so a failing record blocks its shard until it succeeds, expires or a bisect/skip setting moves past it.

Two design rules follow. First, every handler must be idempotent, because every model can deliver duplicates. Second, put a queue between bursts and fragile downstreams: an API function that writes to a database at whatever rate requests arrive will eventually take the database down; one that writes to SQS, with a consumer capped by maximum concurrency, lets the backlog absorb the burst.

Set the function timeout deliberately. It should be longer than the work normally takes (with margin) and shorter than whatever waits for it: API Gateway's integration timeout for synchronous APIs, and less than the SQS visibility timeout for queue consumers (AWS recommends a visibility timeout of at least six times the function timeout). A function that times out after its caller has already given up wastes money and may still perform side effects.

One more resource: connections. Because each environment is separate, 500 concurrent executions open 500 database connections. Relational databases often can't take that. Solutions: RDS Proxy (a managed connection pool in front of the database), data stores designed for many short connections (DynamoDB over HTTPS), and caps on concurrency.

7. Cost: Lambda against a container, worked

Take a typical JSON API: 512 MB on Arm, 120 ms average billed duration, behind an API Gateway HTTP API. Compare with an ECS service on Fargate Arm: two tasks of 1 vCPU and 2 GB (two for availability across zones), each measured to serve 60 requests per second at the latency target, behind an Application Load Balancer, autoscaling above two tasks at high load. Prices are us-east-1 from the AWS price list on 7 October 2026; free tiers are ignored.

Lambda per million requests: GB-seconds = 1,000,000 × 0.5 × 0.12 = 60,000; × $0.0000133334 = $0.80; requests $0.20; HTTP API $1.00 per million. Total $2.00 per million with API Gateway, $1.00 with a function URL instead.

Fargate: each task costs 1 × $0.03238 + 2 × $0.00356 = $0.0395 an hour; two tasks for 730 hours = $57.67. The load balancer is $0.0225 an hour ($16.43) plus capacity units (about $6–9 at these volumes). About $80–83 a month as a floor.

The crossover moves with every assumption. Double the duration to 240 ms and Lambda's compute doubles, moving the crossover down; drop it to 30 ms and Lambda stays competitive much longer. Bursty traffic hurts containers, which must be sized for the peak, while Lambda only pays for what runs. And the floor matters: a container service rarely runs on less than two tasks, while a function at zero traffic costs zero. That's why many systems use both: functions for low-volume and spiky edges, containers for the steady core.

8. Beyond the classic model

AWS has added options that change some of these trade-offs; know they exist and what they trade. Lambda durable functions checkpoint progress so a function can wait — for a callback, a timer, a human approval — for up to a year without paying for idle compute, with quotas on operations and stored state per execution. Lambda Managed Instances run functions on EC2 instances in your account, with several concurrent requests per environment and longer timeouts (up to 90 minutes) for asynchronous and most queue-driven invocations; you get EC2 pricing levers in exchange for capacity on your side of the line. Other providers' function services differ in details that matter: Google Cloud Run functions run on Cloud Run and can handle many concurrent requests per instance; Azure Functions has several hosting plans with different scaling and timeouts. Check concurrency-per-instance semantics before translating a design.

Why one request per environment is a deliberate choice

Standard Lambda's one-request-per-environment rule makes the programming model simple — no thread safety, no request interleaving, memory per request is predictable — and makes isolation strong. It costs efficiency for I/O-bound work: an environment waiting 100 ms on a database is billed for that wait and can't serve anyone else, whereas a container serving 80 concurrent requests overlaps their waits. That's the root of the pricing crossover and of the connection-storm problem. Platforms that allow concurrency per instance (Cloud Run, Lambda Managed Instances) recover the efficiency and bring back the thread-safety and noisy-request concerns.

Throttling is back-pressure, and it needs somewhere to go

When a function hits its concurrency limit, the platform is telling the system to slow down. Where that signal goes depends on the invocation model. Synchronous callers receive 429s and must back off; if they retry immediately they multiply load (the retry storm of sc12). Asynchronous invocations queue the pressure inside Lambda for up to six hours — invisible unless you watch the async event age and dropped-event metrics. Event source mappings convert it into queue depth, which is the healthiest form: visible, durable and drained at the rate you allow. Designing a serverless system is largely deciding where each burst waits.

Orchestration and data passing can dominate the bill

Fine-grained serverless designs pay for the glue: workflow state transitions, queue and topic requests, object-storage requests for intermediate data, logs per invocation. At low volume these are pennies; at high frequency they scale with the number of steps times the number of items, not with the amount of real work. Prime Video's monitoring service performed several state transitions per second of every stream and moved frames between components via S3; those two lines, not Lambda compute, were the problem. A useful review question is "what does one unit of business work cost, broken down by service?" — if orchestration and storage requests exceed compute, the granularity is wrong.

Memory tuning is a cost optimisation with a non-obvious shape

Because CPU scales with memory, a CPU-bound function's duration often falls almost in proportion as memory rises, until it reaches the code's own parallelism limit (a single-threaded handler gains little beyond about one vCPU's worth, 1,769 MB). In that range GB-seconds stay roughly flat while latency improves, so more memory is free speed. Beyond it, cost rises linearly with no latency benefit. I/O-bound functions barely speed up at all, so they should run at the smallest memory that fits. The practical method is a sweep: invoke the function with a realistic payload at several memory sizes, record duration and cost per invocation, and pick the knee of the curve — open-source tools such as AWS Lambda Power Tuning automate exactly this.

Deployments, versions and aliases are how you ship safely

Each publish creates an immutable numbered version; an alias such as live points at a version and can split traffic between two (for example 90/10) for a canary. Event sources and API integrations should point at aliases, not $LATEST, so a deploy is an alias update you can roll back in seconds. New versions start with no warm environments, so a deploy produces a wave of cold starts; shifting traffic gradually (CodeDeploy's linear or canary configurations) spreads them out and lets alarms stop a bad version before it takes all traffic.

Observability needs to follow events, not hosts

There's no host to log into. Every invocation produces logs and metrics (invocations, errors, throttles, duration, concurrency, iterator age for streams, async event age), and traces need context propagated through events — a trace ID carried in message attributes from the API function through the queue to the consumer. Without it, a request that fans out through five functions and two queues can't be followed. Structured logs with request IDs, and alarms on throttles, error rates, dead-letter queue depth and iterator age, are the minimum (cl11).

The security model is strong, and so is the blast radius of a bad role

Each environment is a microVM, so co-tenant isolation is excellent. But a function's execution role (cl2) is the whole of its authority, and functions are often given broad roles because they're "small". An injection bug in a function with s3:* or dynamodb:* on * is as dangerous as one in a server with the same permissions. Give each function its own least-privilege role, keep secrets out of environment variables when they're sensitive (use a secrets manager with caching), and remember that event payloads from S3 keys, queue messages or webhooks are untrusted input.

Failure modes and their symptoms

Account concurrency exhaustion. Unrelated functions start throttling at the same time as one function's burst. Metrics: ConcurrentExecutions near the account limit, Throttles across functions. Fix: reserved concurrency for critical functions and caps on others, quota increases, separate accounts for noisy workloads.

Downstream overload. A database or third-party API fails as soon as traffic grows, because concurrency scales with requests. Fix: a queue in between and maximum concurrency on the consumer; connection pooling via RDS Proxy.

Duplicate side effects. Double emails, double charges. Cause: retries across any invocation model. Fix: idempotency keys with conditional writes.

Poison messages. One bad message fails forever, retried each visibility timeout, or blocks a stream shard. Fix: redrive policies to dead-letter queues, partial batch responses, bisect-on-error and maximum record age for streams.

Visibility timeout too short. Messages processed twice because they reappear while still being handled. Fix: visibility timeout at least six times the function timeout.

Silent async backlog. Events from S3 or EventBridge wait in Lambda's internal queue during throttling and some expire. Metrics: AsyncEventAge, AsyncEventsDropped. Fix: on-failure destinations, more concurrency, or an SQS queue you control.

Cold-start latency spikes. P99 jumps during deploys (new versions start cold) and bursts. Fix: SnapStart or provisioned concurrency on latency-critical functions, smaller init, warm-up before shifting traffic.

Timeout cascades. A function times out after its API Gateway caller has already given up, while still writing. Fix: timeouts nested from the outside in.

What to watch

Per function: invocations, errors, throttles, P50/P99 duration, init duration and cold-start rate, concurrent executions, cost per invocation. Per source: queue depth and age of oldest message, stream iterator age, async event age and drops, dead-letter queue depth.

The case: Prime Video's monitoring service (March 2023)

Prime Video's Video Quality Analysis team wrote about a service that monitors every live stream customers watch for perceptual defects such as block corruption, frozen video or audio/video sync problems. It had three components: a media converter that turns streams into frames and audio buffers, defect detectors that analyse them, and orchestration. The first version was a distributed system of serverless components — AWS Step Functions for orchestration, Lambda for detectors — which the authors note was a good choice for building quickly. But as they onboarded streams it hit a hard scaling limit at around 5% of the expected load, and its cost was too high to run at scale.

Two mechanisms caused it. Step Functions orchestration performed multiple state transitions for every second of every stream, reaching account limits, and Step Functions charges per state transition. And the media converter uploaded frames to an S3 bucket from which each detector downloaded them, so the number of Tier-1 S3 requests (which include PUTs, at $0.005 per 1,000 in us-east-1 in October 2026) was very large. The team moved all components into a single process running in an ECS task on EC2, passing frames in memory and orchestrating inside the instance. The components stayed the same, so much of the code was reused; detectors now scale vertically, and when they outgrew one instance the team ran clones of the service, each with a subset of detectors, behind a lightweight request distributor. They reported that infrastructure cost fell by over 90%, that the service could handle thousands of streams with room to grow, and that EC2 compute savings plans could lower costs further.

The authors' own conclusion is the right one to repeat in an interview: microservices and serverless components work at high scale, but whether to use them has to be decided case by case. What went wrong was granularity: per-second orchestration and bulk data passed through storage between components, both billed per operation.

Goal: simulate a function platform's concurrency, cold starts and throttling, and build the cost crossover — Python 3.12 standard library only. About 20 minutes; no cloud account.

  1. Environments. Write a discrete-event simulation (a heapq of arrival and completion events) of one function: a pool of warm environments, a cold-start delay of 400 ms when no warm one is free, a duration drawn from random.expovariate with mean 150 ms, an account concurrency limit, and environments that expire after 10 idle minutes.
  2. Steady load. Feed 100 requests per second for 10 minutes. Check that average concurrency ≈ 100 × 0.15 = 15 (Little's law) and that the cold-start fraction falls below 1% after the first seconds.
  3. Burst. Jump to 2,000 requests per second for 30 seconds with a limit of 1,000. Count throttles, cold starts and P99 latency during the burst. Add a per-function scale-up rate of 1,000 new environments per 10 seconds and rerun.
  4. Queue instead. Put arrivals into a FIFO list consumed with a maximum concurrency of 200. Report peak backlog and how long it takes to drain.
  5. Costs. Write lambda_cost(req, mem_gb, dur_s, arm=True, gateway=True) and fargate_cost(req) from section 7 and print the table for 1M, 10M, 100M and 1B requests; then find the crossover by bisection.

What to look for: step 2 reproduces Little's law; step 3 shows the burst's first seconds full of cold starts and, at the limit, throttles that the caller must handle; step 4 shows zero throttles but a backlog that drains over time — the trade a queue makes. Step 5 should give $2, $20, $200 and $2,000 for Lambda with the gateway against about $80, $80, $83 and $394, with a crossover near 40 million requests a month.

Needs an AWS account (optional): deploy a hello-world function, invoke it twice with aws lambda invoke --function-name hello --log-type Tail out.json, and decode the base64 LogResult: the first REPORT line includes Init Duration, the second doesn't.

Diagnose: the campaign that broke the serverless backend

A retail app's backend is all Lambda in one account: an API function behind API Gateway (P50 80 ms, P99 1.2 s), an order-processing function triggered asynchronously by EventBridge, an email function consuming an SQS queue (visibility timeout 30 s, function timeout 60 s), and a nightly report function. During a campaign: API errors spike with 429s; customers receive duplicate confirmation emails; the PostgreSQL database hits its connection limit; some orders are processed hours late; the report function fails too. What happened, and what do you change?

Answer

Shared concurrency. All functions share the account's regional quota (1,000 by default). The API's burst plus order processing consumed it, so the API got 429s and the report function throttled. Fix: reserved concurrency for the API, caps on order processing and email, a quota increase before campaigns, and possibly a separate account for batch work.

Database connections. Each concurrent environment opened its own PostgreSQL connection; hundreds of environments exceeded the database's limit. Fix: RDS Proxy, connections created once per environment (outside the handler), and caps on concurrency for functions that write to the database.

Duplicate emails. The SQS visibility timeout (30 s) is shorter than the function timeout (60 s): slow sends made messages reappear and be processed again. Also, delivery is at-least-once anyway. Fix: visibility timeout ≥ 6 × function timeout (360 s), an idempotency key per order in a table with a conditional write before sending, and partial batch responses.

Late orders. EventBridge invokes the order function asynchronously; under throttling, Lambda kept the events in its internal queue and retried for up to six hours. Fix: alarm on async event age, configure an on-failure destination, or route events to an SQS queue you control with visible depth and a capped consumer.

Tail latency. P99 of 1.2 s suggests cold starts during the burst on top of database waits. Fix: trim init, consider SnapStart or modest provisioned concurrency for the API during campaigns.

Then reconsider shape. If the API runs at high steady volume after the campaign, compare its monthly Lambda plus API Gateway cost with a container service; keep functions for the event-driven edges.
