An ML team trains its first large model. The dataset — 400 million images — sits in a bucket as 400 million separate files, because that's how it arrived. Checkpoints go to a shared network file system because the training script expects a path. The trained weights are copied onto each inference server's disk by hand.

Three weeks later the problems pile up. Data loading is the bottleneck: the GPUs sit idle 60% of the time waiting for images, and the bucket returns "503 Slow Down" errors. The shared file system bill is larger than the GPU bill's rounding error should allow, because it charges per gigabyte read and the job rereads the dataset every epoch. A job crashes halfway through writing a checkpoint, and the next run resumes from a corrupted file nobody noticed was incomplete. Someone's cleanup script deletes the "old" checkpoints prefix — which was the only copy of the best run. And when traffic grows, new inference servers take twenty minutes to start because they copy 140 GB of weights over a slow path.

Each of these comes from treating storage as one thing. Cloud providers offer three different shapes — object, block and file — each built for a different access pattern and priced differently, and inside object storage a ladder of storage classes with rules that can save or waste millions. Getting the shape right decides whether the GPUs are fed, whether checkpoints are safe, and whether the storage bill is a rounding error or a line item.

This lesson explains how each shape works underneath: S3's object model, durability and consistency, storage classes and lifecycle rules, request-rate and multipart mechanics; EBS volumes, snapshots and local NVMe; EFS and FSx for Lustre. It then works the ML cases with real numbers — a 70B-parameter checkpoint, a dataset of small files, model weights for serving — and closes with Canva's move of 130 petabytes to a colder class, which shows how to decide with data rather than instinct.

Picture three ways of keeping things for a company.

The first is a huge warehouse run by someone else. You hand over a sealed box with a label ("datasets/v3/shard-00042"), get a receipt, and later ask for it back by label. You can't open a box in the warehouse and change one page; to change anything you send a whole new box with the same label. The warehouse is enormous, cheap per box, keeps copies in several buildings so it practically never loses one, and serves thousands of people at once — but every trip costs a small fee and takes a moment. That's object storage: S3, Google Cloud Storage, Azure Blob Storage.

The second is a filing cabinet bolted to your desk. You can open any drawer, change one page, add a note to a folder, instantly. Only you can use it, and it's in your office — if the building burns, so does the cabinet, unless you photocopied it to the warehouse. That's block storage: an EBS volume attached to one instance in one zone, on which the operating system puts a normal file system.

The third is a shared office library. Everyone on the floor can open the same folders, edit the same files, see each other's changes. It's convenient, but it costs more per shelf than the warehouse, and when a hundred people rush in at once the librarian becomes the bottleneck. That's file storage: EFS (shared NFS) or a parallel file system like FSx for Lustre built for many readers.

The prices tell the story: in us-east-1 in October 2026, a gigabyte-month cost $0.023 in S3 Standard, $0.08 on a gp3 volume and $0.30 in EFS Standard — about 13 times S3. So a sensible default for large data is the warehouse, with block for things a single machine must change quickly, and file only where many machines genuinely need a shared tree.

For ML work the mapping is usually simple. Training data and checkpoints belong in the warehouse, packed into large boxes. Each training node's scratch work — unpacking a shard, staging a checkpoint before upload — happens on the desk cabinet or, faster still, on the node's own local NVMe disks. A shared library is worth paying for only when a framework insists on file paths and many machines must read the same files at very high speed; then a parallel file system that fronts the warehouse gives the best of both. Getting this mapping right is most of the work; the rest of the lesson explains the mechanics and the numbers that justify it.

Where the analogy breaks: the warehouse isn't slow in aggregate. One request takes a hundred milliseconds or so, but you can send thousands at once, and large jobs routinely pull tens of gigabits per second per instance from S3. Throughput comes from parallelism, not from any single trip — which is the key to using it well for ML.

1. The object model

S3 stores objects in buckets. A bucket lives in one region and has a globally unique name. An object is identified by its key — any UTF-8 string up to 1,024 bytes, such as datasets/v3/shard-00042.tar — and consists of data (up to 48.8 TiB) plus metadata (content type, user-defined headers, tags). The namespace is flat: the slashes are just characters, and "folders" in consoles are a display trick. LIST operations can group keys by a delimiter and a prefix, which is how directory-like browsing works.

The operations are few: PUT (create or replace a whole object), GET (read all of it or a byte range), HEAD (metadata), DELETE, LIST, COPY, and multipart upload. There's no append, no partial overwrite, no atomic rename (a "rename" is a copy plus a delete, which for a large prefix is many requests and not atomic). Each operation is an HTTPS request, authorised by IAM and bucket policies (cl2), and billed: in us-east-1 in October 2026, $0.005 per 1,000 PUT, COPY, POST or LIST requests and $0.0004 per 1,000 GETs on S3 Standard.

With versioning enabled on a bucket, a PUT to an existing key creates a new version rather than replacing the old one, and a DELETE adds a "delete marker" that hides the object while keeping its versions. Versions are billed as storage, so versioned buckets need lifecycle rules that expire noncurrent versions.

2. Durability and availability, and what they don't cover

S3 Standard is designed for 99.999999999% (eleven nines) durability and 99.99% availability, storing data across at least three availability zones (from the storage-class comparison table, October 2026). Eleven nines is a statement about hardware loss: if you store ten million objects, you can on average expect to lose one every 10,000 years. AWS achieves it with redundancy across devices and zones (erasure coding — fragments plus parity spread so that missing pieces can be rebuilt) and constant background checking and repair.

Durability is not protection from yourself. A lifecycle rule with the wrong prefix, a script with aws s3 rm --recursive, a compromised credential, ransomware that overwrites objects with encrypted copies — S3 will durably store the result. The protections are layered: versioning (undo overwrites and deletes), Object Lock (make versions immutable for a retention period; in compliance mode not even the root user can shorten it), restrictive delete permissions, and replication to a bucket in another account and possibly another region (cl10 covers backups and RPO). The classes ending "One Zone" store data in a single zone and are not resilient to losing that zone.

3. Consistency and conditional writes

Since December 2020, S3 has provided strong read-after-write consistency: after a successful PUT or DELETE of an object (new or overwritten), every subsequent GET, HEAD or LIST reflects it, in every region. Werner Vogels described the engineering behind this in 2021: S3 added a replicated, strongly consistent witness that tracks the latest version of each object's metadata and lets caches know when they're stale, so reads can be both fast and current. Before that, overwrites and LISTs were eventually consistent, and big-data tools needed extra consistency layers.

Strong consistency doesn't make concurrent writers safe. Two clients writing the same key at the same time both succeed and the last write wins. Conditional writes fix this. If-None-Match: * makes a PUT succeed only if the key doesn't exist (otherwise 412 Precondition Failed); If-Match: <ETag> makes it succeed only if the object still has the version you read. That's enough to build create-once semantics (a checkpoint manifest that must not be overwritten), optimistic concurrency (read, modify, write-if-unchanged) and simple locks — Terraform's S3 backend now uses this for state locking (cl9).

Intelligent-Tiering does it per object based on observed access (30 days without access to the infrequent tier, 90 days to the archive-instant tier) for a monitoring fee — attractive for large objects with unknown patterns, costly for billions of small ones.

5. Performance: request rates, latency and parallelism

AWS's performance guide (October 2026) gives the numbers to design with. S3 supports at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per partitioned prefix, and there's no limit on the number of prefixes; it scales gradually, and while it scales you may see 503 Slow Down errors, which clients should retry with backoff. Latency for small objects, and time to first byte for large ones, is roughly 100–200 ms. Throughput comes from concurrency: a single instance can drive up to 100 Gb/s from S3 with enough parallel requests, and fleets reach terabits per second.

Multipart upload is how large objects are written fast and safely. You initiate an upload, send parts (5 MiB to 5 GiB each, up to 10,000 parts, numbered so order doesn't matter) in parallel, then complete it, at which point S3 assembles the object atomically: readers see either the old object or the whole new one. Failed parts are simply retried. The arithmetic: a 125 GB object needs parts of at least 125 GB ÷ 10,000 = 12.5 MB; with 64 MiB parts it's about 1,863 parts, each a separate PUT. Until completed or aborted, uploaded parts are stored and billed but invisible in normal listings — a classic hidden cost, fixed with an AbortIncompleteMultipartUpload lifecycle rule. On the read side, byte-range GETs let many connections download different parts of one large object in parallel.

For latency-sensitive access there's S3 Express One Zone: "directory buckets" in a single zone you choose, designed for consistent single-digit-millisecond access, at a higher storage price ($0.11/GB-month) but much cheaper requests ($0.00113 per 1,000 PUTs, $0.00003 per 1,000 GETs). It suits hot intermediate data near compute — shuffle data, a training job's cache — not the primary copy of anything.

And every instance type has its own EBS bandwidth limit, so a large volume on a small instance can't reach the volume's numbers.

Snapshots are point-in-time copies of volumes, stored in S3 (at $0.05/GB-month in October 2026) and incremental: the first copies all used blocks, later ones only changed blocks. New volumes can be created from them in any zone of the region, and snapshots can be copied to other regions — the basic block-level backup and migration tool. A volume restored from a snapshot loads blocks lazily from S3 on first access, so first reads are slow unless you pre-warm.

Instance store is different: NVMe SSDs physically in the host (the d in names like m7gd, and standard on GPU training instances), with very high throughput and low latency, and no durability — the data disappears when the instance stops, terminates or its host fails. It's the right place for caches, scratch space, shuffle data, and staging checkpoints before upload, never for the only copy.

7. File storage: EFS and FSx for Lustre

EFS is a managed NFS (v4.1) file system: regional by default (data stored across zones, with mount targets in each zone's subnets), growing and shrinking automatically with no provisioning. Many instances, containers and functions can mount it at once with full POSIX semantics — rename, append, locks. The price in us-east-1, October 2026: $0.30/GB-month in Standard, $0.025 in Infrequent Access, $0.008 in Archive, plus, in the default elastic throughput mode, $0.03 per GB read and $0.06 per GB written. A training job that reads a 10 TB dataset 20 times through EFS elastic throughput pays 200 TB × 1,024 × $0.03 ≈ $6,144 in read charges on top of $3,072 a month for storage — against $235 a month to store it in S3 Standard and read it without per-GB fees inside the region.

FSx for Lustre is a managed parallel file system: data is striped across many storage servers so that hundreds of clients can read and write at aggregate throughputs of hundreds of GB/s, with POSIX semantics. Persistent SSD deployments are priced by throughput tier — for example $0.145/GB-month for 125 MB/s per TiB and $0.60 for 1,000 MB/s per TiB (us-east-1, October 2026). It can be linked to an S3 bucket: files appear in the file system and are loaded lazily from S3 on first access, and results can be exported back. It's the standard answer when an HPC or ML framework insists on a POSIX path and needs very high throughput. Other FSx flavours (NetApp ONTAP, OpenZFS, Windows File Server) serve enterprise file workloads.

8. Choosing storage for datasets, checkpoints and weights

Datasets: shard them. Take an image dataset of 400 million files averaging 100 KB (about 40 TB). Stored as-is in S3, one epoch is 400 million GETs: $160 in request charges per epoch, and at 5,500 GETs per second per prefix about 20 hours per prefix — you'd need dozens of prefixes and thousands of concurrent connections just to keep up. Packed into 1 GB shards (tar files or a record format such as WebDataset, TFRecord or Parquet), it's 40,000 objects: 40,000 GETs per epoch ($0.016), read sequentially with large range requests, limited by network bandwidth rather than request rates. Shuffling happens in a buffer across several shards. Storage cost is the same either way: 40 TB × 1,024 × $0.023 ≈ $942 a month in Standard.

Checkpoints: parallel, atomic, tiered. A checkpoint of a 70B-parameter model trained with mixed-precision Adam holds bf16 weights (2 bytes per parameter), FP32 master weights (4) and two FP32 Adam moments (4 + 4): 14 bytes per parameter, about 980 GB. (gpu9 explains why each piece exists.) With 64 GPUs on 8 nodes, each node writes about 122.5 GB. The pattern:

  1. Copy GPU state to host memory or local NVMe (instance store), then let training continue — only this copy pauses the GPUs.
  2. Upload each node's shard with multipart upload, 64–128 MiB parts, many in parallel.
  3. When every shard is complete, write a small manifest — step number, shard keys, checksums — with If-None-Match: *. Readers load only checkpoints that have a manifest, so a crash mid-upload leaves no half-checkpoint that looks valid.
  4. Lifecycle: keep recent ones hot, move daily ones to Glacier Instant Retrieval, expire the rest, abort incomplete uploads after a day.

Price the retention policy: the last five hourly checkpoints in Standard are 4,900 GB × $0.023 ≈ $112.70 a month. One checkpoint per day for 90 days is 88,200 GB: $2,028.60 a month in Standard, $352.80 in Glacier Instant Retrieval. Requests are negligible (about 15,000 part PUTs per checkpoint ≈ $0.08). Milestone checkpoints and the final model go under Object Lock and are replicated to another account.

Model weights for serving: stage close to the GPU. A 70B model in bf16 is 140 GB. New inference instances need it fast, because cold start time is capacity lost during scale-out (k8s14). Options in order of speed: weights already on local NVMe (from a warm pool or a previous run); pulled from S3 with highly parallel range GETs at several GB/s per instance (140 GB at 5 GB/s ≈ 28 seconds); a shared cache (FSx for Lustre or a node-local cache) so many instances don't each pull from S3; worst, a single-stream copy at a few hundred MB/s (several minutes). Container images with the weights baked in are convenient for small models and slow for large ones, because image layers are pulled and unpacked sequentially.

Why object storage scales where file systems struggle

A POSIX file system promises a single, consistent tree: rename is atomic, a directory listing reflects every create and delete, appends from several writers interleave correctly. Keeping those promises across many servers requires coordinating metadata on every operation, which is why shared file systems have metadata servers that become bottlenecks and why their prices are higher. Object storage drops the promises that need coordination — no rename, no partial writes, no hierarchy — so each key can be handled independently, partitioned by key range across a fleet, and scaled by splitting partitions. That's the origin of the per-prefix request rates: S3 partitions its index by key, and a "partitioned prefix" is one slice of it. Hot slices are split as load grows, which is why scaling is gradual and why bursts against one prefix see 503s first.

How strong consistency was added without a global lock

S3's metadata is cached heavily for speed; the old eventual consistency came from caches that could briefly serve stale metadata after an overwrite. Vogels's 2021 description of the change: S3 introduced a replicated, highly available component that tracks the order of writes per object, and caches consult it cheaply to learn whether their view is current, with a protocol designed so that the common case stays fast and the system remains available when parts fail. The point for designers is that strong consistency became a property you get for free per object, not a transaction across objects: there's still no multi-object atomic commit, which is why checkpoint and table formats (Iceberg, Delta Lake) use a manifest or log written last.

The small-files problem is a cost and a latency problem

Every object carries fixed overheads: a request fee, 100-plus milliseconds of latency, index entries, and in colder classes minimum billable sizes and per-object metadata. When objects are small, those overheads dominate the bytes. Small files also hurt everything downstream: LIST operations return 1,000 keys per call, so a prefix of 100 million objects takes 100,000 LIST calls to enumerate; lifecycle transitions cost per object; inventory and replication scale with object count. The remedies are always some form of packing — shards, record files, columnar formats with large row groups — plus an index when random access is needed.

Data loaders are distributed systems

Feeding 64 GPUs at, say, 2 GB/s each means 128 GB/s from storage. That needs thousands of concurrent requests spread across many prefixes, retries for 503s and timeouts, prefetching far enough ahead to hide 100–200 ms latency, and shuffling that doesn't require random access to individual samples. Libraries built for this (streaming dataset loaders, S3 connectors for PyTorch, Mountpoint for Amazon S3 for sequential file access) package these patterns. When the framework can't stream from S3, a parallel file system linked to the bucket provides POSIX paths at the cost of provisioning throughput.

Checkpoint frequency is an optimisation problem

Checkpointing costs GPU time (the pause to copy state) and storage; not checkpointing costs the work lost when a failure happens. With mean time between failures M for the whole job and checkpoint cost C (in time), the classic first-order result (Young's formula) puts the optimal interval near √(2 × C × M). For a large job whose fleet sees a failure every 6 hours on average and whose checkpoint copy pauses training for 2 minutes, that's √(2 × 2 × 360) ≈ 38 minutes. Faster checkpointing (async upload, in-memory replicas on peer nodes) lowers C and so allows more frequent checkpoints and less lost work — which is why large training systems invest in it.

Replication has its own consistency and cost model

Cross-region and same-region replication copy new objects asynchronously to another bucket, usually within minutes; S3 Replication Time Control adds an SLA-backed target of 15 minutes for most objects. Replication doesn't copy objects that existed before it was enabled unless you run a batch job, doesn't by default replicate deletes (a protection against propagating mistakes), and bills inter-region transfer per GB plus storage in the target. For disaster recovery that makes the RPO for objects minutes rather than zero, and it makes replication a cost line proportional to write volume — relevant when checkpoints write a terabyte an hour.

Encryption choices have cost consequences

All new S3 objects are encrypted at rest by default with S3-managed keys. Using customer-managed KMS keys (SSE-KMS) adds control and an audit trail of key use (cl13, au11), but each object operation can call KMS, which has request quotas and charges; S3 Bucket Keys cut those calls by deriving a bucket-level data key. For high-request workloads — millions of small reads — forgetting bucket keys shows up as KMS throttling and a surprising KMS line on the bill.

Failure modes and their symptoms

503 Slow Down. A new workload hammers one prefix faster than S3 has partitioned it. Symptoms: bursts of 503s and retries, rising latency. Fix: spread keys across prefixes, ramp up gradually, retry with exponential backoff and jitter (SDKs do), and reduce request counts by packing.

Accidental deletion. A cleanup job, a mistyped prefix or an over-eager lifecycle rule removes data. With versioning, restore by deleting delete markers or copying old versions back; without it, the data is gone. Prevention: versioning, Object Lock for critical data, delete permissions limited to a few roles, lifecycle rules reviewed like code.

Hidden storage growth. Noncurrent versions, incomplete multipart uploads and forgotten replication targets grow quietly. Storage Lens and inventory reports show them; lifecycle rules fix them.

Transitions that lose money. Lifecycle rules move billions of small objects to IA or Glacier classes: transition fees and minimum sizes exceed savings. Filter rules by object size; model the break-even first.

EBS performance ceilings. A database on gp3 hits its provisioned IOPS or throughput (or the instance's EBS bandwidth): latency climbs, VolumeQueueLength grows. Raise gp3 IOPS/throughput or move up an instance size.

Snapshot restores are slow at first. A volume created from a snapshot fetches blocks lazily; a database restored this way runs slowly until warmed. Pre-warm by reading the volume, or use fast snapshot restore for critical volumes.

Shared file system bottlenecks and bills. Many clients on EFS hit throughput or per-operation limits, or elastic throughput charges balloon. Measure bytes read per job; move bulk data to S3.

What to watch

Per bucket: storage by class and version state, object count and average size, requests by type, 4xx/5xx rates, first-byte latency, replication lag; per volume: IOPS and throughput against provisioned, queue length, burst balance on older types; per file system: throughput, metadata operations, per-GB access charges. Storage Lens gives organisation-wide views of most of these.

The case: Canva moves 130 PB to Glacier Instant Retrieval (May 2023)

Canva's engineering blog describes an S3 estate of about 230 petabytes and more than 300 billion objects, with the largest bucket at 45 PB. Much of it was user-uploaded media, already partly in Standard-IA. Using S3 Storage Class Analysis, the team found two patterns: in Standard, retrieval "falls drastically after the first 15 days" — Standard held about 10% of the bytes but 60–70% of the accesses; Standard-IA held about 90% of the bytes and a flat 30–40% of accesses over time. That's the signature of data that's rarely read but must still load in milliseconds when a user opens an old design: a fit for Glacier Instant Retrieval.

The decision turned on object size and transition fees. Glacier IR bills at least 128 KB per object and charges $0.02 per 1,000 objects to transition in, so moving tiny objects costs more than it saves; Canva calculated a point around 20 KB below which Standard is cheaper, and limited the move to buckets whose average object size was 400 KB or larger, where payback would come within six months. Moving roughly 80 billion objects cost $1.6 million once; the result is about $300,000 a month saved ($3.6 million a year), with about 130 PB now in Glacier IR.

The engineering lesson is the method: measure access by age, measure object size distribution, compute the transition cost and the payback period per bucket, and only then write the lifecycle rule. The same three numbers decide every storage-class question, from a team's log bucket to a 45-petabyte media store.

Design and estimate: storage for an ML platform

A team runs: (1) a 25 TB training corpus of text, currently 50 million JSON files of ~500 KB; (2) fine-tuning jobs on 8-GPU nodes that checkpoint a 13B-parameter model (mixed-precision Adam) every 30 minutes over 2-day runs, about 20 runs a month; (3) an inference fleet that scales from 4 to 40 instances, each loading the 26 GB bf16 weights; (4) application logs of 2 TB a month, mostly 8 KB objects, needed for 30 days and kept a year for audit. Propose storage for each, estimate monthly storage cost in us-east-1 with the lesson's prices, and name the main risk.

Answer

1. Corpus. Repack into ~1 GB shards (Parquet or JSONL compressed — often 3–5× smaller); keep in S3 Standard. Uncompressed: 25 × 1,024 × $0.023 ≈ $589/month; compressed 4× ≈ $147. Requests become trivial (25,000 objects). Risk: losing the corpus — enable versioning and replicate the canonical copy to another account.

2. Checkpoints. 13B × 14 bytes ≈ 182 GB per checkpoint. Each run writes 96 over two days; keep only the last 3 per run hot plus the final one. Stage to local NVMe, multipart upload, manifest last. Hot set across concurrent runs (say 3 runs at a time × 3 checkpoints): ~1.6 TB in Standard ≈ $38/month; final checkpoints, 20 a month × 182 GB = 3.6 TB per month added, moved to Glacier IR after 7 days at $0.004 ≈ $15 per month for each month's batch, growing. Lifecycle: expire intermediate checkpoints after 2 days, abort incomplete uploads after 1 day. Risk: hidden growth from not expiring intermediates — 96 × 182 GB × 20 runs ≈ 349,000 GB a month if kept, ~$8,000/month in Standard.

3. Weights. One copy in S3 (26 GB, pennies). Instances pull with parallel range GETs to local NVMe at startup (26 GB at a few GB/s ≈ 10 s), or from a warm pool. Risk: 36 instances scaling out simultaneously each pulling 26 GB — fine for S3, but check startup scripts parallelise and don't serialise on a single stream.

4. Logs. 8 KB objects make IA and Glacier classes a loss (128 KB minimum; per-object transitions on 2 TB ÷ 8 KB ≈ 268 million objects a month ≈ $5,400 at $0.02 per 1,000). Instead batch logs into larger objects (for example hourly compressed files per service) before storage, then lifecycle to Glacier Flexible Retrieval at 30 days and expire at 365. If batching is impossible, keep them in Standard for 30 days, then export a compacted archive and delete the originals. Risk: transition and request fees exceeding storage costs.
