A startup runs PostgreSQL on a virtual machine it set up on day one. It works for two years. Then, on one Saturday, the disk fills with WAL files because a replica fell behind; the database stops accepting writes; the person who set it up has left; nobody knows whether last night's backup script still runs (it stopped eight months ago when a credential rotated). The team spends a weekend recovering and on Monday decides to "move to a managed database".

They pick the managed service, click through the defaults, and feel safe. But the defaults were single-zone, with seven days of backups. Their Lambda functions open a new connection per request, and during the next traffic spike the database hits its connection limit. They add a read replica for analytics, and customers start seeing their own updates "disappear" for a few seconds because some reads now go to the lagging replica. They add DynamoDB for a new activity feed, partitioned by date, and every write for today goes to one partition, which throttles while the table shows plenty of unused capacity. And they put a cache in front of everything, which works beautifully until a cache failover sends every read to the database at once.

Managed databases remove the work of running database software — installing, patching, backing up, replacing failed hardware, failing over. They don't remove the need to understand the database. Each service has a model underneath: how it replicates, how it fails over and what clients see during it, how it partitions data, what it counts as a unit of capacity and how it charges for it. Those models decide whether the system is available, correct and affordable.

This lesson takes the main managed data services in turn, using AWS as the concrete case: RDS and its Multi-AZ and replica options, Aurora's separated storage, DynamoDB's partitions and capacity modes (with a capacity calculation for a real workload), managed Redis and Valkey caches, connection management from serverless and containers, and how to decide between managed and self-hosted. The case is DynamoDB's 2015 outage, which shows a managed database failing in a way no customer could have configured away.

A managed database is like moving from owning a car to a full-service lease. The leasing company handles servicing, replaces parts when they fail, keeps a spare car ready, and keeps the logbook. You still choose the model, decide who's allowed to drive, decide how much luggage it must carry, and — crucially — you still drive. If you drive into a wall, the lease doesn't undo it; if the spare car takes two minutes to arrive, your passengers wait two minutes.

The cloud offers several kinds of managed data service, each with a different model underneath:

  • Managed relational databases (RDS for PostgreSQL, MySQL and others; Cloud SQL; Azure Database for PostgreSQL) run a normal database engine on a dedicated instance with attached storage. The provider adds automated backups, patching, a standby for failover, and read replicas. It's the same PostgreSQL you'd run yourself, operated for you.
  • Cloud-native relational databases (Aurora, AlloyDB, and distributed SQL such as Spanner) change the architecture: compute is separated from a shared, replicated storage layer, so replicas and failover don't need full copies of data.
  • Managed key-value and document stores (DynamoDB, Firestore, Cosmos DB) are built as distributed services from the start: data is spread across many partitions by key, capacity is bought in request units, and there are no servers to see.
  • Managed caches (ElastiCache and MemoryDB on AWS, Memorystore, Azure Cache for Redis) run in-memory stores — Valkey, Redis or Memcached — on nodes you size, with replication and failover.

Whatever the service, three questions decide most designs. How does it fail over, and what do clients see while it does? How does it scale — up (bigger instance), out for reads (replicas) or out for everything (partitions)? And what is the unit of capacity you pay for — instance-hours, request units, gigabytes of memory? The rest of the lesson answers those three questions for each service.

A good first pass at choosing among them follows the data's access patterns rather than fashion (sc8). If the data is relational — many entities joined in flexible queries, with transactions across them — start with managed PostgreSQL or MySQL, and reach for Aurora when you need faster failover, many low-lag replicas or storage that manages itself. If every access is "get or update the items for this key" at very high or very spiky rates, a key-value store like DynamoDB scales without servers, provided you can design keys that spread load. If the same few objects are read far more often than they change, put a cache in front of whichever store holds the truth. Most real systems use two or three of these together, each for the access path it serves best, and the hard work is keeping them consistent enough with each other.

Where the analogy breaks: the leasing company's spare car is yours alone. A managed database's control systems — the metadata that says which server holds which data, the automation that runs failovers — are shared by every customer in the region. When they have a problem, every customer has it at once, and nothing in your configuration can opt you out. That's what the 2015 DynamoDB case shows.

1. What "managed" covers, precisely

For RDS, AWS runs: provisioning the instance and storage, installing the engine, minor-version patching in a maintenance window you choose, OS patching, automated daily snapshots plus continuous transaction-log backup (enabling point-in-time recovery within a retention window you set, up to 35 days), failure detection and failover in Multi-AZ deployments, storage autoscaling if enabled, and metrics. You own: instance class and storage type, Multi-AZ and replica topology, engine parameters (via parameter groups), major version upgrades (you schedule them), schema and queries, users and grants, network placement and security groups, encryption choices, backup retention and copy-to-another-region, and how your application behaves during failover.

The split matters most in incidents. A runaway query, a missing index, a migration that locks a table, a connection storm, a disk filled by a forgotten replication slot — all happen on a managed database just as on your own, and the provider won't fix them.

2. RDS Multi-AZ failover, traced

In a Multi-AZ DB instance deployment, RDS keeps a synchronous standby in another zone: the primary writes each transaction to its own EBS storage and to the standby's before acknowledging the commit. The standby serves no traffic. Your application connects through a DNS name such as orders.c9akciq32.eu-central-1.rds.amazonaws.com, which resolves to the primary's IP.

When RDS detects a failure — the primary host unhealthy or unreachable, its storage failed, the zone impaired, or during OS patching or an instance modification — it promotes the standby and changes the DNS record to point at it. The documentation gives typical failover times of 60–120 seconds, longer with large transactions to recover. Trace what the application sees:

  1. T+0: the primary stops responding. Existing connections hang or reset; queries in flight fail; uncommitted transactions are lost (committed ones are safe on the standby).
  2. T+0 to ~T+60–120 s: RDS detects, promotes and flips DNS. New connection attempts fail or time out.
  3. After the flip: clients that re-resolve DNS connect to the new primary. Clients that cached the old IP keep trying the dead host. AWS specifically warns that some JVM configurations cache DNS forever and recommends a DNS TTL of no more than 60 seconds.
  4. Applications must retry failed transactions — idempotently, since a transaction might have committed just before the failure without the client seeing the acknowledgement.

The cost is double the instance price: a db.m7g.large PostgreSQL instance was $0.168 an hour single-AZ and $0.337 Multi-AZ in us-east-1 on 7 October 2026, and gp3 storage $0.115/GB-month single-AZ against $0.23 Multi-AZ. Commit latency rises slightly because every commit crosses zones. A Multi-AZ DB cluster variant runs a writer and two readable standbys across three zones with faster failover — useful when you want both read scaling and quicker recovery.

3. Read replicas and lag

A read replica is a separate instance kept up to date by asynchronous replication (PostgreSQL streaming replication, MySQL binlog replication). It serves read-only queries and can be in another zone or region; it can be promoted to a standalone primary for disaster recovery. Because replication is asynchronous, replicas lag — usually milliseconds to seconds, more under write bursts or when a long-running query on the replica holds back replay.

Lag creates anomalies (sc6): a user updates their profile and the next page, read from a replica, shows the old value; two consecutive requests hit different replicas and see time go backwards. The fixes are routing rules: reads that must reflect the user's own recent writes go to the primary (for a few seconds after a write, or always for that session); dashboards and analytics go to replicas; replicas lagging beyond a threshold are taken out of rotation. RDS exposes ReplicaLag per replica.

4. Aurora: separating compute from storage

Aurora (MySQL- and PostgreSQL-compatible) keeps the engine's query processing but replaces its storage. The database instances don't write data pages to their own disks; the writer sends redo log records to a distributed storage service that maintains the cluster volume. The Aurora paper (SIGMOD 2017) describes six copies of each 10 GB segment of data, two in each of three zones, with writes acknowledged when four of six copies have them and reads needing three of six — so the volume survives losing a whole zone plus one more copy for reads, and keeps accepting writes after losing a zone. The storage nodes apply log records to pages themselves, which is why Aurora writes far less across the network than a database shipping full pages.

Consequences for design: replicas (up to 15) read the same volume, so adding one doesn't copy data, and they lag only by the time to apply log records to their caches, typically tens of milliseconds; failover promotes a replica that already sees all committed data; storage grows automatically (up to 256 TiB on recent engine versions) and you pay for what's used. In us-east-1, October 2026: a db.r7g.large Aurora PostgreSQL instance was $0.276 an hour, storage $0.10/GB-month plus $0.20 per million I/O requests in the Standard configuration, or $0.225/GB-month with no I/O charges in I/O-Optimized (AWS's guidance: choose it when I/O is 25% or more of the Aurora bill). Aurora Serverless v2 adjusts instance capacity in fine increments for variable load.

5. DynamoDB: partitions and keys

DynamoDB stores items (up to 400 KB each) in tables. Every item has a primary key: a partition key alone, or a partition key plus a sort key. DynamoDB hashes the partition key to choose a partition — a replicated unit of storage and throughput — and keeps items with the same partition key together, ordered by sort key. A query reads one partition key's items, optionally a range of sort keys; a scan reads everything and is expensive.

The rule that drives every design, from the developer guide: each partition delivers at most 3,000 read units and 1,000 write units per second (and holds roughly 10 GB). A table with 20,000 write units of capacity spread over 20 partitions can absorb 20,000 writes per second only if the writes spread across partition keys; if 30% of writes share one partition key, that key's partition caps them at 1,000 per second and they throttle while the table looks under-used.

Two mechanisms soften this. Burst capacity lets a provisioned partition briefly use capacity it didn't use in recent minutes. Adaptive capacity moves unused throughput from cold partitions to hot ones and splits partitions whose keys are hot, isolating frequently accessed items (the 2022 DynamoDB paper describes how this evolved). Neither lets a single item exceed one partition's limits: a single item read 600 times per second with strong consistency at 20 KB per read (5 read units each) already uses all 3,000 read units of its partition. Hot single items need caching (DynamoDB Accelerator or ElastiCache) or a redesign.

Global secondary indexes (GSIs) let you query by another key. Each is effectively another table, maintained asynchronously from the base table, with its own partitions and its own write capacity: every write that changes indexed attributes costs write units in the GSI too. A GSI whose key is low-cardinality (say status) becomes a hot partition, and a throttled GSI can throttle writes to the base table.

6. DynamoDB capacity, worked

Capacity units (from the developer guide): one read capacity unit (RCU) is one strongly consistent read per second of an item up to 4 KB, or two eventually consistent reads; one write capacity unit (WCU) is one write per second of an item up to 1 KB. Sizes round up. Transactional reads and writes cost double. On-demand mode bills the same units per request (read and write request units) rather than per hour.

A personalisation service needs 12,000 reads per second of 6 KB user-profile items (eventually consistent is fine) and 1,500 writes per second of 2.5 KB items, with one GSI that projects all attributes.

  • Reads: 6 KB rounds up to two 4 KB units = 2 RCU strongly consistent, 1 RCU eventually consistent. 12,000 × 1 = 12,000 RCU.
  • Writes: 2.5 KB rounds up to 3 WCU per write. Base table 1,500 × 3 = 4,500 WCU; the GSI another 4,500. 9,000 WCU in total.
  • Partitions: the base table needs at least max(12,000 ÷ 3,000, 4,500 ÷ 1,000) = 4.5, so five or more partitions, with keys spread evenly; the GSI likewise.

Scaling behaviour differs too. 7. Managed caches: ElastiCache with Valkey, Redis OSS or Memcached

A cache keeps hot data in memory so reads take a fraction of a millisecond and the database sees fewer queries (sc3 covers patterns: cache-aside, write-through, TTLs, stampedes). ElastiCache runs the engine on nodes you size, or as a serverless option billed by data stored and compute units. In 2024 Redis changed its licence away from open source, and the Linux Foundation's Valkey fork continued the BSD-licensed code; ElastiCache supports Valkey alongside Redis OSS and Memcached and prices it lower — in us-east-1 on 7 October 2026 a cache.r7g.large (13.07 GiB) node was $0.1752 an hour with Valkey against $0.219 with Redis OSS (20% less), and serverless data storage $0.084 against $0.125 per GB-hour.

The production-relevant knobs: cluster mode shards keys across node groups by hash slot so memory and throughput scale out; each shard has a primary and replicas, ideally in other zones, with automatic failover; eviction policy decides what's dropped when memory fills (for a pure cache, evict least-recently-used keys across all keys); persistence is limited — a cache is not a database, and replication is asynchronous, so a failover can lose recent writes. Where a Redis-compatible store must be durable, AWS offers MemoryDB, which logs writes durably across zones before acknowledging.

The design principle is to make the database survive the cache being empty. Measure the database's capacity against the uncached read rate; if it can't take it, add request coalescing (one fetch per key per miss storm), staggered TTLs, a warm-up procedure after failover, and replicas so a node loss doesn't empty a shard.

8. Connections from serverless and containers

Relational databases handle a limited number of connections well; PostgreSQL in particular uses a process per connection. Modern compute multiplies connections: 50 container replicas with a pool of 20 each is 1,000 connections; 500 concurrent Lambda environments with one each is 500 (cl5). RDS Proxy (or self-managed PgBouncer) sits between clients and the database, keeps a small pool of real connections and multiplexes many client connections onto them; it also holds client connections during a failover and reconnects to the new primary, shortening what applications see. The trade-off of transaction-level pooling is that session state — prepared statements, temporary tables, session variables, advisory locks — can't be relied on across transactions.

Why Aurora ships logs instead of pages

A traditional database writes each change several times: to the write-ahead log, to data pages, to a double-write buffer, and — with replication — all of that again on the replica, often over the network. The Aurora paper's argument is that in the cloud the network, not the disk, is the bottleneck, so Aurora sends only redo log records to storage; storage nodes materialise pages from the log in the background. Quorums of 4/6 for writes and 3/6 for reads, spread two per zone, mean losing a zone (two copies) leaves writes possible, and losing a zone plus one more node still leaves the data readable and repairable. Segments of 10 GB can be re-replicated quickly, which shrinks the window of vulnerability after a failure. The design pushes durability and replication into a shared service, which is why Aurora replicas are cheap and failover is fast — and why Aurora's storage is a dependency shared by every cluster in the region.

Admission control is how DynamoDB stays predictable

The 2022 DynamoDB paper describes the system's central promise: predictable single-digit-millisecond latency at any scale. To keep it, every partition enforces its throughput limit (originally by dividing the table's provisioned capacity equally among partitions, which made hot keys throttle under-used tables), and the system evolved toward bursting, adaptive capacity, splitting partitions for heat as well as size, and global admission control across request routers. Throttling is therefore a feature: rather than letting a hot key degrade everyone on a storage node, DynamoDB rejects excess requests early. Clients must back off and retry (SDKs do); designs must spread keys so that throttling is rare.

Retries are the most common way managed services fail at scale

A dependency slows down; clients time out and retry; the retries add load; the dependency slows further. The 2015 DynamoDB event followed exactly this shape inside AWS, between storage servers and the metadata service, and recovery required pausing requests to let the service drain. The same happens between your application and a managed database: a failover or a slow query causes connection retries from hundreds of clients, which delays recovery. Bounded retries with exponential backoff and jitter, circuit breakers that stop calling a struggling dependency, and token-bucket retry budgets (as AWS SDKs implement) are the countermeasures (sc12).

Consistency choices are part of the price

In DynamoDB, a strongly consistent read costs twice an eventually consistent one, transactions cost twice again, and GSIs are only eventually consistent. In RDS, synchronous Multi-AZ adds commit latency and doubles instance cost; asynchronous replicas are cheap and lag. In caches, consistency with the database is whatever your invalidation logic makes it. A senior design states, per access path, what consistency it needs and pays only for that: balances and inventory decrements need strong consistency; profile reads and feeds rarely do.

Single-table design trades flexibility for efficiency

DynamoDB practitioners often put several entity types in one table, with generic key attributes such as PK = CUSTOMER#123 and SK = ORDER#2026-10-07#981, so a single query returns a customer and their recent orders together. The benefit is fewer round trips and fewer tables to provision; the cost is that access patterns must be known up front, because a new query shape may need a new GSI or a data migration, and the table becomes hard to read for people used to relational schemas. It's the clearest example of designing the data around queries rather than the other way round (db11), and the right answer depends on how stable the access patterns are.

Backups and restores are the part teams never test

Automated backups and point-in-time recovery are easy to enable and hard to trust until exercised. Restoring an RDS database creates a new instance — new endpoint, empty caches, cold storage that loads lazily from snapshots — and takes time proportional to size; a multi-terabyte restore can take hours before performance is normal. DynamoDB PITR restores into a new table. A realistic recovery plan includes how long the restore takes, how the application is repointed, and how data written after the restore point is reconciled. cl10 turns this into RTO and RPO numbers.

Failure modes and their symptoms

Failover pain. Errors for one to two minutes, then some clients recover and others don't. Causes: long DNS caching, connection pools that never drop dead connections, non-idempotent retries. Fix: low DNS TTL, pool validation and timeouts, RDS Proxy, idempotent transactions, and a regular failover test (reboot with failover).

Connection exhaustion. "too many connections" or high memory on the database during scale-out of clients. Fix: proxies and pools, concurrency caps, fewer and better-sized pools.

Replica lag incidents. Users see stale data; lag climbs during bulk writes or long replica queries. Fix: lag-aware routing, read-your-writes routing, moving analytics to a separate replica or system.

Storage and I/O surprises. RDS storage full (enable storage autoscaling and alarms), IOPS or throughput limits on gp3, Aurora I/O charges growing with inefficient queries.

DynamoDB throttling. ProvisionedThroughputExceededException or on-demand throttles while the table's aggregate usage looks low — a hot key or hot GSI. Fix: key redesign, write sharding, caching, more capacity on the GSI; CloudWatch Contributor Insights shows the most accessed keys.

Cache stampede. Database load spikes when a popular key expires or the cache fails over. Fix: request coalescing, TTL jitter, early refresh, replicas.

Maintenance surprises. Minor version upgrades or OS patches in the maintenance window cause a failover; major versions reach end of standard support and start costing extended-support fees. Track engine versions and plan upgrades.

What to watch

RDS/Aurora: CPU, freeable memory, connections, read/write IOPS and latency, replica lag, storage free, deadlocks and long transactions (Performance Insights or Database Insights). DynamoDB: consumed versus provisioned capacity per table and GSI, throttled requests, latency, hot keys. Caches: hit rate, evictions, memory, CPU per shard, replication lag, connections. For all: error rates from the application's point of view and failover events.

The case: DynamoDB in us-east-1, 20 September 2015

AWS's summary describes how DynamoDB's storage servers work: each holds partitions of customers' tables, and each periodically confirms its membership — the set of partitions it's responsible for — with an internal metadata service. If a server can't get its membership within a time limit, it retries and stops serving those partitions until it can. In the months before the event, customers had rapidly adopted global secondary indexes, which add partitions; tables with many partitions and several GSIs had doubled or tripled their contribution to membership lists, so some membership responses had grown large enough that processing them took close to the time limit.

At 2:19 AM PDT a brief network disruption affected a portion of storage servers. Many re-requested membership at once; some responses exceeded the time limit; those servers retried; the retries kept the metadata service overloaded, so more requests timed out. Storage servers without membership stopped serving requests, and DynamoDB's error rate in the region reached about 55% by 2:37 AM. Adding capacity to the metadata service was hard while it was saturated, so at 5:06 AM AWS paused requests to it, letting load fall, then added capacity and gradually re-enabled traffic; DynamoDB recovered by 7:10 AM. Other services that depend on DynamoDB were affected: SQS saw elevated errors (without data loss), EC2 Auto Scaling had API errors and a scaling backlog that lasted until 10:52 AM, and CloudWatch had missing and delayed metrics. AWS increased metadata capacity, lengthened timeouts, added monitoring of membership size and processing time, and planned to split the metadata service into multiple instances.

Read as an engineer: a managed database is a distributed system with internal dependencies you can't see; growth of an internal quantity (membership size) moved it towards a timeout cliff quietly; retries turned a brief network event into a long outage; and recovery required deliberately shedding load. For your own designs, it argues for bounded retries, alarms on things approaching limits rather than only on failures, a way to shed load, and — for systems that must survive such events — a second region (sc17, cl10).

Goal: build a DynamoDB capacity and cost calculator and a hot-partition simulator in Python 3.12 (standard library only). About 20 minutes; no cloud account needed.

  1. Units. Write rcu(size_kb, consistency) and wcu(size_kb, transactional=False) following the rounding rules (4 KB reads, 1 KB writes; eventual halves, transactional doubles). Check 3 KB strong reads → 1, 6 KB eventual → 1, 2.5 KB write → 3.
  2. Price. Write provisioned_cost(rcu, wcu, target=0.7) and on_demand_cost(rru_per_s, wru_per_s, avg_to_peak) with the October 2026 prices. Reproduce the section 6 table and find the average-to-peak ratio where they break even.
  3. Partitions. Write min_partitions(rcu, wcu) and then simulate traffic: 20 partitions, each capped at 1,000 WCU/s; generate 15,000 writes per second where a share s of writes go to one key and the rest are uniform over 100,000 keys hashed to partitions (use hashlib.md5). Report throttled writes for s = 0, 0.05 and 0.2.
  4. Sharding. Repeat with the hot key split into 10 suffixes. How much does throttling drop, and how many reads would a full read of the hot key now need?
  5. Replica lag. Simulate a primary receiving writes and a replica applying them with a random 0–2 s delay; issue a read 500 ms after each write from the replica and count stale reads.

What to look for: step 2 shows provisioned at about $7,728 and on-demand at about $18,725, breaking even near 41% average-to-peak. Step 3 shows no throttling when uniform, and heavy throttling at s = 0.2 (3,000 writes per second at one partition capped at 1,000) despite 20,000 total capacity. Sharding into 10 keys removes most of it. Step 5 shows roughly 75% of reads stale under a uniform 0–2 s lag — the read-your-writes problem in numbers.

Diagnose: "the database is slow every morning"

An e-commerce API runs on ECS (60 tasks at peak, each with a connection pool of 25) against RDS PostgreSQL db.r7g.xlarge Multi-AZ, plus two read replicas used for "all GET endpoints", and ElastiCache Valkey (single node) for product data with a 1-hour TTL set at deploy time. Every morning around 09:00: p99 latency rises from 80 ms to 2 s, the primary's CPU hits 95%, connections approach max_connections (1,600), replica lag reaches 8 seconds, and customers report that items added to their cart vanish when they refresh. Explain each symptom and propose fixes in priority order.

Answer

Connections: 60 tasks × 25 = 1,500 connections at peak, close to 1,600. PostgreSQL spends memory and CPU per connection. Fix: put RDS Proxy (or PgBouncer) in front, cut per-task pools to a handful, and size from measured concurrency.

CPU spike at 09:00: the cache was loaded at deploy time with a fixed 1-hour TTL, so popular keys expire together; if deploys happen early morning, the morning peak meets synchronised expiry and a single cache node: a stampede to the database. Fix: TTL jitter, request coalescing on misses, early refresh of hot keys, and a replicated cache (primary plus replica in another zone) so a node loss doesn't empty it.

Replica lag: the morning write burst (carts, orders) plus heavy read load on the replicas delays replay to 8 seconds.

Vanishing cart items: GET endpoints read from replicas; a user adds an item (write to primary) and refreshes (read from a replica 8 s behind): read-your-writes is broken. Fix: route reads of the user's own cart and orders to the primary (or keep carts in a store designed for it — DynamoDB keyed by user, or the cache with write-through), and use replicas only for catalogue and analytics reads; alarm on lag and remove lagging replicas from rotation.

Then capacity: once connections and stampedes are fixed, re-measure CPU; consider Aurora with low-lag replicas if read scaling is still needed, and test failover under morning load with the proxy in place.
