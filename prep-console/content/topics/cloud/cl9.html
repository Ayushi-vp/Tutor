A team builds its first production environment by clicking through the cloud console: a VPC, subnets, security groups, a load balancer, a database, IAM roles. It takes two weeks and works. Six months later they need a staging environment that matches production. Nobody remembers every setting. The staging copy differs in a dozen small ways — a security group rule, a parameter group, a subnet route — and a bug that appears only in production can't be reproduced. A year later an auditor asks who changed a firewall rule in March and why; there's no record. Then someone, debugging, deletes a "test" security group that production depended on.

Infrastructure as code (IaC) fixes this by describing infrastructure in files that live in version control, are reviewed like application code, and are applied by a tool that makes the cloud match them. Staging becomes the same code with different inputs; the history of every change is in Git; reviewers see exactly what will change before it changes.

But IaC brings its own failure modes, and they're severe because the tool acts on whole environments at machine speed. A plan line that says "must be replaced" on a database means delete and recreate. A lost state file makes the tool forget what it manages. Two engineers applying at once can corrupt state. A blank variable with a silent default can schedule a deletion a year in the future — exactly what happened to an Australian pension fund's private cloud on Google Cloud in 2024.

This lesson explains how IaC tools actually work, using Terraform as the concrete system: configuration, state and providers; what plan and apply do and how to read a plan; state storage, locking and the secrets inside state; modules and refactoring; drift; how CloudFormation, CDK and Pulumi differ; and how teams promote changes through environments safely with CI. The case is Google Cloud's UniSuper incident, a lesson in what defaults in provisioning tools can do.

Think of infrastructure as code as an architect's drawings plus a building contractor who never improvises.

The drawings (configuration files) describe what the building should look like when finished: three floors, these rooms, these doors, this wiring. They don't say "first pour the foundation, then raise the walls" — the contractor works out the order from the dependencies (walls need a foundation, wiring needs walls). That's what declarative means.

The contractor keeps a site ledger (state): "room 2.14 in the drawings is the physical room behind door B-207". Without the ledger, the contractor walking onto an existing site can't tell which rooms are theirs to manage and which belong to someone else, and would start building duplicates.

Before any work, the contractor produces a work order (plan): "add a window to room 2.14; repaint 3.02; demolish and rebuild 1.05 because you moved its load-bearing wall". The client reviews it — and the word "demolish" is the one to look for. Then the contractor does exactly the work order (apply) and updates the ledger. Only one contractor may work from the ledger at a time (locking). And if someone changes the building without telling the contractor — knocks through a wall on a weekend — the building has drifted from the drawings, and the next work order will either undo the change or be confused by it.

The value of the model comes from three properties. Changes are reviewable: a pull request shows the code change and the plan shows its effect. Environments are repeatable: the same code with different inputs builds the same structure. And applies are convergent: running the same configuration twice makes no further changes, so the tool can be run routinely to correct drift.

Several tools implement this model. Terraform and its open-source fork OpenTofu work across every major cloud and hundreds of other services through plugins; CloudFormation is AWS's own service, which keeps the ledger for you and undoes a failed job automatically; CDK and Pulumi let you write the drawings in ordinary programming languages. They differ in who stores the ledger, how failures are handled and which language you write, but they share the loop of desired state, recorded state, preview and apply — so once you can read a Terraform plan, the others are variations on a theme. This lesson uses Terraform for the mechanics because its plan output makes every step explicit.

Where the analogy breaks: a real contractor would notice that "demolish room 1.05" means losing the furniture inside and would ask. An IaC tool doesn't know that a database contains data. It sees an object whose attributes changed in a way the API can't apply in place, and its answer is delete and recreate. Every safety property — review, protection against destroy, backups — has to be added deliberately by people who understand what the objects hold.

1. Configuration, providers and resources

A Terraform configuration is a directory of .tf files in HCL (HashiCorp Configuration Language). It declares providers — plugins that translate resource definitions into API calls for one platform — and resources, each with a type and a local name:

terraform {
  required_version = "~> 1.16"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "services/orders/terraform.tfstate"
    region       = "eu-central-1"
    encrypt      = true
    use_lockfile = true
  }
}

provider "aws" { region = "eu-central-1" }

variable "instance_type" {
  type = string
  validation {
    condition     = can(regex("^(m7g|c7g)\\.", var.instance_type))
    error_message = "Use a Graviton m7g or c7g type."
  }
}

resource "aws_security_group" "api" {
  name   = "orders-api"
  vpc_id = data.aws_vpc.main.id
}

resource "aws_instance" "api" {
  ami                    = data.aws_ami.al2023.id
  instance_type          = var.instance_type
  subnet_id              = data.aws_subnet.app_a.id
  vpc_security_group_ids = [aws_security_group.api.id]
  tags = { Service = "orders", Env = "prod" }
}

A few things to notice. Version constraints pin Terraform and the provider (Terraform 1.16.5 and OpenTofu 1.13.1 were the current releases in early October 2026). data sources read existing objects without managing them. The variable has no default and a validation block, so a missing or wrong value fails rather than silently becoming something else. And the instance refers to aws_security_group.api.id — that reference is how Terraform learns the security group must exist first.

2. Plan: refresh, graph, diff

terraform plan does four things:

  1. Load state from the backend.
  2. Refresh: for each resource in state, call the provider's read API to get its current attributes. A resource that was deleted outside Terraform disappears from the refreshed view.
  3. Build the dependency graph from references between resources, data sources and modules. Independent branches can run in parallel (10 operations at a time by default).
  4. Diff desired against current for every resource and classify it: + create, ~ update in place, -/+ destroy and recreate (replace), - destroy, or no change.

Here's a realistic excerpt after someone changes the instance type and moves the instance to another subnet:

  # aws_instance.api must be replaced
-/+ resource "aws_instance" "api" {
      ~ id            = "i-0a1b2c3d4e5f67890" -> (known after apply)
      ~ instance_type = "m7g.large" -> "m7g.xlarge"
      ~ private_ip    = "10.20.4.17" -> (known after apply)
      ~ subnet_id     = "subnet-0aa1" -> "subnet-0bb2" # forces replacement
        tags          = { "Env" = "prod", "Service" = "orders" }
    }

Plan: 1 to add, 0 to change, 1 to destroy.

The instance type alone would be an in-place update (stop, change type, start). The subnet change can't be applied to an existing instance — an instance's network interface lives in its subnet — so the provider marks it # forces replacement. Read every plan for three things: the summary counts (anything "to destroy"?), every -/+ and what forces it, and whether the number of resources touched matches the size of the change you intended. A one-line change that plans 40 updates means something else is going on (a provider upgrade changing defaults, drift, or a variable that feeds many resources).

By default a replacement destroys first and then creates. For things that must not have a gap — a load balancer target, a DNS record — lifecycle { create_before_destroy = true } reverses the order. For things that must never be destroyed by Terraform, lifecycle { prevent_destroy = true } makes any plan that would destroy them fail. Cloud-side protections (RDS deletion protection, S3 Object Lock, termination protection) add a second layer that doesn't depend on Terraform configuration being right.

3. Apply, and what happens when it fails halfway

terraform apply (ideally of a saved plan: terraform plan -out=tfplan, then terraform apply tfplan) walks the graph and calls provider create, update and delete operations, writing state as each completes. Apply is not a transaction. If it fails halfway — an API error, a quota, a timeout — resources already created exist and are recorded in state; the rest aren't. The next plan picks up from there. Some providers mark partially created resources as tainted, so the next apply replaces them. Cloud APIs' eventual consistency (cl1) causes occasional failures right after creation ("not found" for something just created), which providers handle with retries.

CloudFormation behaves differently: a stack update that fails rolls back to the previous state automatically, because CloudFormation owns the state and the ordering. That's safer for many failures and slower and occasionally stuck ("UPDATE_ROLLBACK_FAILED") for others.

4. State: storage, locking and secrets

State is a JSON document. A fragment:

{
  "version": 4,
  "serial": 212,
  "lineage": "4f1c9d4e-…",
  "resources": [{
    "mode": "managed", "type": "aws_instance", "name": "api",
    "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
    "instances": [{ "attributes": {
        "id": "i-0a1b2c3d4e5f67890", "instance_type": "m7g.large",
        "private_ip": "10.20.4.17", "subnet_id": "subnet-0aa1" } }]
  }]
}

The serial increases on every write; the lineage identifies this state's history, so Terraform refuses to overwrite a state from a different lineage. Three rules follow.

Store it remotely and durably. A local terraform.tfstate on a laptop is the single most common cause of lost infrastructure ownership. Use a backend: on AWS an S3 bucket with versioning (so a corrupted or deleted state can be restored — HashiCorp's backend documentation "highly recommends" it), encryption, public access blocked, and access only for deploy roles and a break-glass group.

Lock it. Two concurrent applies against the same state can interleave API calls and lose writes. With use_lockfile = true, the S3 backend creates a lock object beside the state using an S3 conditional write that succeeds only if no lock exists (cl6), and deletes it at the end; the second run sees the lock and stops. The older approach — a separate DynamoDB table holding lock items — is marked deprecated in the S3 backend documentation and slated for removal. HCP Terraform and other remote backends lock natively.

Treat it as secret. State records every attribute Terraform tracks. If you create a database with password = random_password.db.result, that password is in state in plain text, and anyone who can read the bucket can read it. Mitigations, in order of preference: let the service own the secret (RDS can generate and store the master password in Secrets Manager); use ephemeral values and write-only arguments in current Terraform, which are used during a run but never written to state or plan files; restrict and audit read access to state; and, with OpenTofu, encrypt state client-side.

5. Modules

A module is a directory of Terraform code with input variables and outputs. The root configuration is a module; it can call others:

module "orders_db" {
  source  = "git::https://github.com/acme/tf-modules.git//postgres?ref=v3.4.1"
  name    = "orders"
  size    = "medium"          # module maps sizes to instance classes
  env     = var.env
  vpc_id  = module.network.vpc_id
}

Good modules encode decisions rather than exposing every argument: the postgres module above might always turn on Multi-AZ in prod, encryption, deletion protection, backups of 14 days and performance insights, and accept only a size and a name. That's how a platform team makes the safe path the easy path. Version modules with semantic version tags and pin them (?ref=v3.4.1 or registry version constraints), so a module change reaches environments only when each environment's code is updated to the new version — which is the hook for promotion.

6. Refactoring, importing and drift

Code changes shape over time, and Terraform identifies resources by address (module.orders_db.aws_db_instance.this). Renaming or moving a resource changes its address, which by default means destroy the old, create the new. Three blocks prevent that:

  • moved { from = aws_instance.api to = module.api.aws_instance.this } tells Terraform the object is the same; the plan shows a move, not a replace.
  • import { to = aws_s3_bucket.logs id = "acme-logs-prod" } adopts an existing resource into state on the next apply, shown in the plan first; Terraform can generate starter configuration for it.
  • removed { from = aws_s3_bucket.legacy lifecycle { destroy = false } } stops managing a resource without deleting it.

Drift is reality diverging from code. terraform plan -refresh-only shows how managed resources changed outside Terraform without proposing to fix them; an ordinary plan would propose to revert them. Teams run a scheduled plan per root module and alert on any diff (the -detailed-exitcode flag returns exit code 2 when there are changes). The more durable fix is organisational: in environments managed by code, humans get read-only console access and a break-glass path for emergencies, and emergency changes are back-ported into code immediately.

The licence row has practical weight. In August 2023 HashiCorp moved Terraform from the open-source Mozilla Public License to the Business Source License, which restricts offering competing products; the community forked the last open version as OpenTofu under the Linux Foundation, and the two have since diverged in features (OpenTofu added client-side state encryption, for example). IBM acquired HashiCorp in 2025. For most end users either tool works; organisations with policies about open-source licences, or vendors building on the tool, choose deliberately.

The deeper difference is who owns state and rollback. CloudFormation's managed state and automatic rollback suit teams that want AWS to handle failure; Terraform's explicit state and plans suit multi-cloud estates and teams that want to read exactly what will happen. CDK and Pulumi trade reviewable declarative files for the abstraction power of real programming languages — loops, functions, classes, tests — which is excellent for platform teams building reusable constructs and risky when programs grow imperative logic that's hard to review.

8. Environments and promotion

The goal is that production runs exactly what was tested in staging, and that each environment's differences are small and explicit. A layout that achieves it:

  • One account per environment (cl13), so permissions, quotas and blast radius are separated by the strongest boundary AWS has.
  • Root modules per environment and layer: envs/prod/network, envs/prod/data, envs/prod/services/orders, each with its own state in that environment's state bucket.
  • Shared modules versioned in a module repository or registry; each environment's root pins versions.
  • Environment differences as variables in each root module (sizes, counts, domain names), reviewed when they change.

The pipeline enforces the rules people forget under pressure: policies checked on every plan (no public S3 buckets, encryption on, required tags, no IAM wildcards), applies only from the protected branch, production applies from a saved plan someone approved, and an automatic stop on destroy or replace of stateful resources. Provider versions are locked by the dependency lock file (.terraform.lock.hcl) committed with the code, so a new provider release can't change behaviour silently between staging and production.

Why providers force replacement, and how to see it coming

A resource's attributes fall into three groups in the provider's schema: those the API can change in place, those it can't change at all after creation (marked ForceNew in the provider's code), and computed ones the API decides. Replacement isn't Terraform being cautious; it's the cloud API's model of the object. A subnet's CIDR can't change because addresses are allocated from it; a KMS-encrypted volume can't become unencrypted. Provider documentation lists which arguments force new resources, and reviewers who know the common ones (names, identifiers, network placement, encryption, engine types) catch dangerous plans quickly. Policy checks on the plan JSON make it mechanical: list all actions containing "delete" for resource types that hold data.

State is a distributed-systems problem in miniature

A state file is a single shared record updated by multiple actors: CI pipelines, engineers running plans locally, and the cloud itself changing underneath. Locking gives mutual exclusion; serial numbers and lineage detect stale or foreign writes; versioning gives recovery. What it doesn't give is coordination across states: two root modules that both reference the same security group by data lookup can each make changes that conflict. Splitting states for blast radius therefore needs clear ownership — every real object managed by exactly one state — and interfaces (outputs, parameter-store values) between them.

Plans are predictions, not guarantees

"Known after apply" values, provider-side defaults, eventual consistency and other actors mean the apply can do things the plan didn't fully show: an attribute computed at apply time triggers a second update on the next plan; a resource created by the cloud as a side effect (a default security group, an automatically created log group) appears as drift later; two pipelines racing on different states change shared reality. Mature teams treat a clean follow-up plan ("no changes") after every apply as the confirmation that the apply converged, and investigate any persistent diff ("perpetual diff") as a bug in configuration or provider.

Policy as code turns review into guarantees

Human review catches intent problems; it misses patterns that recur across hundreds of changes. Policies evaluated against the plan JSON — with Open Policy Agent, HashiCorp Sentinel, or scanners like Checkov — enforce invariants every time: every S3 bucket has public access blocked, every RDS instance in prod is Multi-AZ with deletion protection, every security group rule allowing 0.0.0.0/0 is on port 443 of a load balancer, every resource carries cost-allocation tags (cl12). The same policies can run in the cloud as guardrails (SCPs, AWS Config rules) for changes made outside the pipeline. The combination — prevent in CI, detect in the account — is the standard governance pattern (cl13).

Testing infrastructure code

Infrastructure code can be tested at several levels, each catching different mistakes. Static checks (format, validate, linters, policy scans) catch syntax and known-bad patterns in seconds. Plan-level tests assert on the plan JSON — this change creates exactly one bucket with encryption on — without touching the cloud; Terraform's built-in test framework can run such assertions, and mock providers make them cheap. Integration tests apply modules to a disposable account, check that the result works (the database accepts connections, the endpoint returns 200) and destroy it; they're slow and cost money, so they run on module changes rather than every commit. The most valuable test is often the simplest: applying the same commit to staging before production, with a follow-up plan that shows no changes.

Abstraction levels and who owns them

Infrastructure code tends to settle into layers: a foundation layer (accounts, organisation policies, networks, DNS) owned by a platform team and changed rarely; a shared-services layer (clusters, shared databases, observability); and service layers owned by product teams, built from platform modules. Each layer has a different change rate, blast radius and reviewer set, and keeping them in separate states with separate pipelines matches the code structure to the organisation. Kubernetes manifests deployed by GitOps (k8s12) usually sit on top, with Terraform providing the cluster and its cloud dependencies; mixing the two in one tool tends to produce dependency cycles.

Failure modes and their symptoms

Accidental replacement of stateful resources. An innocent-looking change (a renamed identifier, a moved subnet, a provider upgrade) plans -/+ on a database or bucket. Symptom: data loss after apply, or a failed apply blocked by deletion protection. Prevention: prevent_destroy, cloud-side deletion protection, plan policies that stop on destroys, and reviewers trained to read replace markers.

Lost or corrupted state. A local state file deleted, a state overwritten by an old copy, a manual edit gone wrong. Symptom: plans that want to recreate everything. Recovery: restore a previous version from the versioned bucket, or re-import resources. Prevention: remote, versioned backend; no manual state edits outside reviewed import/moved blocks.

Stale locks. A CI job killed mid-apply leaves a lock; every later run fails with "Error acquiring the state lock". Confirm the job is dead, then force-unlock with the lock ID.

Drift fights. A setting changed by hand (or by an autoscaler, or another tool) is reverted by every apply and changed again, flapping. Fix ownership: manage it in one place, or use ignore_changes for attributes owned by something else (such as an autoscaling group's desired count).

Provider upgrade surprises. A new major provider version changes defaults or schemas; the next plan touches hundreds of resources. Upgrade deliberately, one environment at a time, reading the upgrade guide and the plan.

Secrets in state and logs. Passwords visible to anyone with bucket read access, or printed in CI plan output. Use ephemeral/write-only values, sensitive outputs, and restricted state access.

Slow, contended monolith states. Long plans and teams queuing on one lock. Split by layer and ownership.

What to watch

Drift detected per root module, failed applies, time since last successful apply per environment (code that hasn't been applied in months is usually drifted), plans with destroys, lock wait times, and the number of resources not managed by any IaC (from AWS Config or tag audits).

The case: Google Cloud and UniSuper, May 2024

UniSuper, an Australian pension fund, ran its systems on a Google Cloud VMware Engine (GCVE) private cloud. Google's own write-up, published on 25 May 2024, describes what happened. When the private cloud was first deployed in 2023, Google operators used an internal tool to provision it and left one parameter blank. Nobody knew that the tool interpreted the blank as a fixed one-year term with automatic deletion at its end. A year later the system deleted the private cloud — across two zones — and, because the deletion wasn't a customer request, no notification was sent. Google called it an isolated incident affecting one customer's one private cloud, and said nothing like it had happened before in Google Cloud.

Recovery took several days of round-the-clock work by Google and UniSuper: rebuilding the private cloud, restoring network and security configuration, restoring applications and recovering data. What made recovery possible were backups stored in Google Cloud Storage, which the deletion didn't touch, and a third-party backup system. Google deprecated the internal tool, made that step fully automated and controlled by customers through the user interface, scrubbed its database and manually reviewed every GCVE private cloud for the same risk, and corrected the behaviour so the deployment workflow can't schedule automatic deletion this way.

The lessons generalise to any provisioning code, including your Terraform. A blank input should be an error, not a silent default — variables without defaults, with validation. Destructive behaviour should never be implicit: deletion, expiry and replacement must be visible in what reviewers see. Deletion of production infrastructure needs layers of protection and should notify someone. And backups must sit outside the blast radius of the system that provisions and deletes — another account, another project, ideally another provider — because the tool that can create everything can also delete everything.

Goal: build a tiny "plan and apply" engine with state and a lock in Python 3.12 (standard library only), and reproduce the behaviours in this lesson. About 25 minutes; no cloud account needed.

  1. Fake cloud. A dict of objects keyed by generated IDs, with create(type, attrs), read(id), update(id, attrs) and delete(id). Mark some attributes as force-new per type, e.g. {"instance": {"subnet"}, "db": {"encrypted", "engine"}}.
  2. Plan. Given desired config (a dict of address → type and attributes) and state (address → ID), refresh by reading each ID; classify each address as create, update, replace (if any changed attribute is force-new) or destroy (in state, not in config). Print a plan in the lesson's format with a summary line.
  3. Apply and state. Execute the plan, writing state after each operation with an incrementing serial, saved as JSON with json.dump. Make one operation raise an exception halfway and show that the next plan resumes correctly.
  4. Drift. Change an attribute directly in the fake cloud; show that a refresh-only comparison reports it and that a normal plan proposes to revert it.
  5. Lock. Implement a lock with os.open(path, os.O_CREAT | os.O_EXCL) (create only if absent, like S3's If-None-Match). Run two "applies" in threads and show the second one fails to acquire the lock until the first releases it.
  6. Guardrail. Add a protected_types = {"db"} check that refuses to apply any plan containing destroy or replace for those types — then try changing a db's encrypted attribute.

What to look for: step 2 marks a subnet change as replace and a size change as update; step 3 shows apply isn't atomic but converges on the next run; step 4 is exactly how drift looks in real plans; step 5 shows why concurrent applies need a lock; step 6 shows a guardrail stopping the accidental replacement that the UniSuper case and many smaller incidents are about.

Needs an AWS account and Terraform (optional, not runnable here): with the backend block from section 1, terraform init then terraform plan -refresh-only -detailed-exitcode exits 0 with no drift and 2 when managed resources changed outside Terraform.

Review: a pull request to production infrastructure

A pull request titled "Rename orders DB and move API to new subnets" changes three things in envs/prod/services/orders: aws_db_instance.orders gets identifier = "orders-prod-v2" (was "orders-prod"); aws_instance.api moves to subnet_id = data.aws_subnet.app_b.id; and a module bump from postgres v3.4.1 to v4.0.0. The posted plan says "Plan: 3 to add, 41 to change, 3 to destroy". The author says "just renames, should be harmless". What do you check, and what do you ask for before approving?

Answer

1. The destroys. Three destroys with three adds means three replacements. The RDS identifier forces replacement — on a production database that's delete-and-recreate. Check deletion protection and prevent_destroy; either way, don't approve. Ask: is the rename needed? If yes, do it as a migration (snapshot and restore to a new instance, cut over, then remove the old one) or accept the old name and add a tag.

2. The instance move. The subnet change forces replacement of the API instance: there will be a gap unless create_before_destroy is set and traffic is drained through the load balancer. Ask how capacity is maintained; ideally instances are in an autoscaling group and this is a launch-template change, not an instance replacement.

3. The 41 changes. A major module version (v4.0.0) likely changed defaults or resource structure. Read the module changelog and the plan's per-resource diffs: are they tag changes, or parameter-group changes that reboot the database? Ask to split the PR: module upgrade alone, applied first in dev and staging, then prod.

4. The third destroy. Find it. Unexplained destroys are the most dangerous lines in a plan; often a resource moved inside the new module version without a moved block.

5. Process. Ask for the same change to have been applied in staging from the same commit, a saved plan for prod, and policy checks that block destroy/replace of RDS automatically next time. Approve only the parts that are genuinely in-place.
