Imagine you join a food-delivery company as its first ML engineer. The product runs on a PostgreSQL database with tables for customers, restaurants, orders and payments, and the mobile app sends a stream of events — "opened app", "searched for sushi", "added to basket" — to a logging service. Your first task sounds simple: train a model that predicts whether an order will be late, so the app can warn customers.

You ask for data. Someone gives you read access to the production database. Your first query, which scans two years of orders and joins them to restaurants, runs for forty minutes and, while it runs, the checkout page gets slow enough that the on-call engineer comes looking for you. You try a read replica instead. The query finishes, but now you notice the data is only the current state of each order: the status column says delivered, and there is no trace of when it said preparing or picked_up, which are exactly the moments your model needs. The courier's location at prediction time has been overwritten thousands of times. Orders that were cancelled and hard-deleted are simply gone, so your training set quietly over-represents successful orders. And the app events are not in the database at all; they sit in compressed log files on a server that rotates them away after a week.

None of this is a modelling problem. It is a data problem, and it is the normal situation in every company. Production systems are built to run the product right now, not to remember the past or to answer big questions about it. Data engineering is the discipline of getting data out of those systems, keeping its history, reshaping it into tables that analysts and models can use, and doing all of that correctly, repeatably and at a cost the company can afford. ML teams depend on it more than anyone: a model is only as good as the training set, and a training set is the output of a pipeline.

This lesson is the map for the whole track. It walks a single piece of data from the production database to a training set and names every stop: the sources (OLTP databases and event streams), the ways to extract data from them (dumps, incremental queries, change data capture), where it lands (a lake on object storage, a warehouse, or a lakehouse), the layers it moves through, the choice between batch and streaming, the choice between ETL and ELT, and who owns each part. It finishes with one complete, sized pipeline and a real case: how Uber's platform evolved through four generations as these trade-offs bit. Later topics take each stop apart in detail.

The mental model: a water system

Think of a city's water system. Water starts in many sources — rivers, reservoirs, wells — each run by someone else, each with its own quality. Pipes carry it to a treatment plant, where it is filtered, tested and treated in stages. Treated water goes into storage tanks, and from there into a network that delivers it to homes, factories and fire hydrants, each needing different pressure and purity. If a source is contaminated and nobody tests, every tap downstream gets bad water, and the people who notice first are the ones furthest from the cause.

A data pipeline has the same shape. The sources are the production systems: the application's databases and its event streams. Ingestion is the set of pipes that copy data out of them. The storage is the lake, the warehouse or both. Transformation is the treatment plant: cleaning, deduplicating, joining and aggregating in stages. The consumers are dashboards, analysts, feature stores and training jobs, each with different needs for freshness and shape. And as with water, the expensive failures are silent contamination upstream: a renamed column, a duplicated day of events, a time zone change that nobody tested for, discovered weeks later as a model that quietly got worse.

The analogy breaks in one useful place. Water is consumed and gone; data can be kept. The most important design decision in a modern data stack is to keep the raw data, exactly as it arrived, in cheap storage, so that any later stage can be rerun when a bug is found or a new question is asked. A water plant that discovers a filter was broken last month cannot re-treat last month's water. A data platform that kept its raw layer can.

The whole picture in five moves

First, data is born in two kinds of places. An OLTP (online transaction processing) database — PostgreSQL, MySQL, DynamoDB — holds the current state of business entities: this order, this customer, this balance. An event stream records things that happened, one record per event — clicks, page views, sensor readings, model predictions — usually written into Kafka, a durable append-only log (you met it in sc10).

Second, data is extracted. For a database, that means copying either the whole table, the rows that changed, or — best — the database's own log of every change, which is called change data capture (CDC). For event streams, it means reading the log continuously.

Third, data lands in analytical storage: a data lake (files, ideally in the columnar Parquet format, in object storage such as Amazon S3), a data warehouse (a managed analytical database such as Snowflake, BigQuery or Redshift), or a lakehouse, which is a lake whose tables carry extra metadata that gives them database-like guarantees.

Fourth, data is transformed in layers: raw as landed, then cleaned and conformed, then shaped for a specific use. These are commonly called bronze, silver and gold.

Fifth, data is consumed: dashboards and analysts query gold tables; ML pipelines build features and training sets; some results are pushed back into production systems.

If you stop reading here, keep three ideas. Production systems are the source of truth but are the wrong place to analyse; everything else is a derived copy. Keep the raw copy, because it is what lets you fix mistakes. And choose freshness deliberately: every minute of freshness you buy costs money and correctness effort, so buy it only where the model or the business needs it.

1. Where data is born: OLTP databases and event streams

An OLTP database stores the current state of the business. A row in orders says that order 81723 belongs to customer 553, costs 23.40 and is delivered. When the courier picks the food up, the application runs UPDATE orders SET status = 'picked_up' WHERE id = 81723, and the old value is overwritten. The database is optimised for this: thousands of small reads and writes per second, each touching one or a few rows through an index, each inside a transaction. It keeps history only incidentally, in its write-ahead log (WAL) — the log it appends every change to before applying it, so it can recover after a crash — and it recycles that log as soon as it no longer needs it.

An event stream is the opposite. It never updates anything; it appends a new record every time something happens: {"event":"add_to_basket","user":553,"item":"sushi-12","ts":"2026-10-08T12:03:11Z"}. Events are produced by mobile apps, web servers, payment providers, sensors and, increasingly, by ML systems themselves (every prediction and its inputs, logged for later training). They usually go into Kafka or a managed equivalent (Amazon Kinesis, Google Pub/Sub — cl8 covers the managed services): a durable, partitioned log that keeps messages for a configured retention period (Kafka's default broker setting is seven days) so several consumers can read at their own pace.

This distinction matters for everything that follows. A database table has a current state you can copy at any moment, but its history is lost unless you capture changes as they happen. An event stream has no current state at all — it is history — but if nobody reads and stores it before retention expires, it is gone. Both point to the same lesson: capture continuously, store durably, derive everything else.

A third, smaller category is external data: files from partners, third-party APIs, public datasets, documents scraped for an LLM corpus. These arrive in batches, in whatever format the provider chose, and need the same landing-and-cleaning treatment.

2. Getting data out of a database: three extraction methods

There are three ways to get data out of an OLTP database, and the choice decides what questions you can answer later.

Full snapshot (dump). Copy the whole table every time: SELECT * FROM orders, or a database export tool. It is simple and always consistent with the source at the moment of the copy. Its costs grow with the table, not with the changes: a 500 GB table copied nightly reads 500 GB from the production database even if only 2 GB changed. Worse, it captures only the state at copy time. If an order went from placed to preparing to picked_up to delivered between two nightly copies, the lake only ever sees placed (yesterday) and delivered (today). Snapshots are fine for small reference tables (a list of 3,000 restaurants) and for a one-off initial load.

Incremental query. Copy only rows changed since the last run, using a column the application maintains: SELECT * FROM orders WHERE updated_at > :last_high_water_mark. Much cheaper, and a common first step. But it has three well-known holes. It cannot see hard deletes, because a deleted row has no updated_at to match. It misses any write path that forgets to bump updated_at (a bulk fix run by hand, a trigger-less migration). And it races with long transactions: if a transaction starts at 10:00:00, writes updated_at = 10:00:00, but commits at 10:00:07, and your extract at 10:00:05 records "high-water mark = 10:00:05", the next run looks for rows after 10:00:05 and never sees that row. Teams patch this with an overlap window (re-read the last few minutes each time and deduplicate), which works but is a heuristic. It still loses intermediate states between runs.

Log-based change data capture (CDC). Read the database's own change log: PostgreSQL's WAL through logical decoding (a feature that turns WAL records into row-level changes), or MySQL's binlog (its binary replication log). Every committed insert, update and delete arrives as an event, in commit order, with the before and after values of the row. A tool such as Debezium runs as the reader and publishes each change to a Kafka topic. CDC is the only method that sees every change and every delete, and it puts very little load on the database because it reads a log the database writes anyway. Its costs are operational: a connector to run, a replication slot on the database that holds WAL until the reader confirms it (if the reader stops, WAL piles up on the primary's disk), and schema changes that flow through the stream. de8 is entirely about doing this well.

A worked trace makes the difference concrete. Suppose order 81723 has this life on Tuesday: inserted at 12:00 as placed, updated at 12:04 to preparing, 12:21 to picked_up, 12:40 to delivered; and order 81724 is inserted at 12:10 and hard-deleted at 12:15 because it was a duplicate click. A nightly snapshot at 02:00 Wednesday sees one row: 81723 delivered. An hourly incremental query sees 81723 at 13:00 as delivered (the 12:04 and 12:21 states fell between runs) and never sees 81724 at all. CDC emits six events: c(81723, placed), u(81723, preparing), c(81724), d(81724), u(81723, picked_up), u(81723, delivered). Only the CDC stream lets a model ask "how long did restaurants take to start preparing on Tuesday lunchtime?" — and only CDC lets the lake mirror the deletion.

3. The data lake: files in object storage

Once data is out, it needs somewhere to live. The cheapest durable place to keep petabytes is object storage — Amazon S3, Google Cloud Storage, Azure Blob Storage (cl6 explains how they work). A data lake is simply data kept as files in such storage, organised by convention into folders such as s3://lake/bronze/orders_cdc/date=2026-10-08/part-0001.parquet, and read by whatever engine needs it: Spark, Trino, a warehouse, a Python training job.

Three properties make lakes attractive. First, cost: storage is priced per byte-month and is much cheaper than a database's provisioned disks, and you pay for compute only while a job runs. Second, compute–storage separation: the data sits in one shared place and many engines, sized independently, read it — a nightly Spark job with 200 cores, an analyst's SQL engine, a GPU training job — without copying it into each one. Third, openness: if the files are in an open format such as Parquet (a columnar file format, taught in de2), no vendor owns your data.

A bare lake also has well-known weaknesses. It is schema-on-read: the files enforce nothing, so a producer that starts writing price as a string breaks readers only when they read it. A "table" is just whatever files are in a folder, so a reader listing the folder while a writer is halfway through adding files sees a partial table; there are no transactions. You cannot update or delete one row without rewriting whole files, which makes GDPR deletion requests painful. And because every small write creates a file, lakes accumulate millions of tiny files, each of which costs a request to open (de2 and de3 cover this "small-files problem"). Lakes that ignore these problems become what people call data swamps.

4. The data warehouse: a managed analytical database

A data warehouse is a database built for analytics: columnar storage, compression, massively parallel scans, and plain SQL. Snowflake, Google BigQuery, Amazon Redshift and Azure Synapse are the common cloud warehouses. You load data in, and you get what a lake lacks: schemas enforced on write (schema-on-write), transactions, updates and deletes, access control at the column and row level, and an optimiser that tunes storage for you. Analysts love warehouses because they just work.

The trade-offs are cost and lock-in. Warehouse storage and compute are usually priced higher than raw object storage and a self-managed engine (de13 works through real prices), the data sits in the vendor's internal format, and non-SQL workloads — a PyTorch job reading 2 TB of training rows — either pay to export or use a connector that was not designed for that throughput. The traditional result was two copies: the lake for raw data and ML, the warehouse for BI, kept in sync by pipelines and frequently disagreeing.

5. The lakehouse: database guarantees on open files

The lakehouse is the attempt to have one copy. Its key ingredient is a table format — Apache Iceberg, Delta Lake or Apache Hudi. A table format adds a small amount of metadata next to the Parquet files: a log or tree of metadata files that lists exactly which data files belong to the table at each version. A writer adds new data files, then atomically swaps the table's "current version" pointer to a new metadata file that includes them. Readers always follow the pointer, so they see either the old version or the new one, never a half-written state. That one trick gives you atomic commits, concurrent writers that detect conflicts, row-level updates and deletes (by rewriting or marking affected files), schema evolution, and time travel — querying the table as of an older version, which ML teams use to reproduce exactly the data a model was trained on. de4 opens up how this works.

A catalog sits on top: a service that maps prod.orders to the table's current metadata location and handles the atomic pointer swap. Hive Metastore, AWS Glue, Databricks Unity Catalog, Apache Polaris (an Iceberg catalog Snowflake donated to the Apache Software Foundation) and Iceberg's REST catalog protocol are examples. The lakehouse paper by Armbrust, Ghodsi, Xin and Zaharia (CIDR 2021, linked in the references) argues that with these layers, plus caching and good file layout, one open copy can serve both BI and ML. In practice the major warehouses now read, and increasingly write, Iceberg and Delta tables too, so "lake versus warehouse" has become "which engine on which open tables".

6. Layers: bronze, silver and gold

Inside the lake or lakehouse, data moves through layers. The names come from Databricks' "medallion architecture", but the idea is older and universal.

Bronze (also called raw or landing) holds data exactly as it arrived: CDC events with their before and after images, JSON app events, partner CSV files. It is append-only and kept for a long time. Its job is to be the replayable record of what the sources said. You never fix data in bronze; you fix the code that reads it.

Silver (cleaned, conformed, sometimes "staging" or "core") holds typed, validated, deduplicated tables with consistent keys and time zones. For CDC data, silver usually holds two shapes: a current-state table (the latest version of each order, produced by merging the change events) and a history table (every version with valid-from and valid-to times). Event data is deduplicated on an event ID, has its timestamps normalised to UTC, and has bad records quarantined into a side table rather than silently dropped.

Gold (marts, serving, "curated") holds tables shaped for a use: a daily revenue fact table for finance, a dimensional model for BI (de10), a feature table keyed by customer and time, or a training set with a fixed snapshot of labels. Gold tables are where business definitions live — what counts as an "active customer", which orders count as "late".

The value of layers is rerunnability. If a bug in the deduplication logic is found in March, you fix it and recompute silver from bronze for the affected days, then gold from silver; the sources are never touched. The cost is storage (three copies of some data) and more tables to own. Small teams often merge silver and gold; nobody serious skips bronze.

7. Batch versus streaming

Batch processing runs a job over a bounded set of input — "all events for 2026-10-07" — and finishes. A scheduler starts it after the input is complete, it reads the input, writes the output, and stops. Batch is cheap (machines exist only while the job runs, and can be spot instances), easy to reason about (the input does not change while you process it), and easy to rerun (just run the same day again). Its cost is latency: an hourly job means data is between one and two hours old; a daily job means up to a day or more.

Stream processing runs continuously over unbounded input, handling each event or small group of events as it arrives, and updates its output in seconds. You met the basic model in sc18; de9 goes deep. Streaming buys freshness, but it costs always-on machines, more complex correctness (events arrive late and out of order, the job keeps state such as running counts that must survive crashes), and harder operations (a job that never ends is harder to test, deploy and backfill). Micro-batch sits between: a streaming engine such as Spark Structured Streaming that actually runs a tiny batch every few seconds or minutes. Many "real-time" pipelines are micro-batches every five minutes, which is much simpler and good enough.

The decision is about the decay of value. Ask: how much worse is the decision if the data is an hour old? For a monthly revenue report, not at all. For a fraud model scoring a card payment, enormously — the attacker has already made fifty more payments. For a recommendation model, it depends on the feature: a user's long-term genre preferences can be a day old; "what they clicked in the last five minutes" cannot. So mature ML platforms stream a small number of time-critical features into an online feature store and build everything else, including training sets, in batch.

8. ETL versus ELT

ETL — extract, transform, load — is the older pattern: pull data from the sources, transform it in a separate processing engine (historically a dedicated ETL tool, later Spark), and load only the finished result into the warehouse. It made sense when warehouse storage and compute were expensive and fixed in size: you did not want raw junk in your expensive database.

ELT — extract, load, transform — loads raw data into the warehouse or lakehouse first and runs the transformations there, usually as SQL. It became the default once cloud warehouses made compute elastic and storage cheap. The raw copy is kept (that is your bronze layer), transformations are just SQL models that anyone who knows SQL can read and change, and a bug fix is a rerun inside the warehouse rather than a re-extract from production. Tools such as dbt organise these SQL models into a dependency graph with tests (de11).

ETL has not disappeared. You still transform before loading when the raw data must not land at all (personal data that legal says may not be stored, or secrets in logs), when the transformation is not expressible in SQL (parsing PDFs, running an ML model over images, tokenising a text corpus for LLM pre-training), or when the volume makes loading raw data into a warehouse uneconomic. In a lakehouse the line blurs: Spark jobs that read bronze and write silver are "transform after load" even though they run outside a warehouse.

9. Who owns what

A data platform is a chain of teams, and its failures are usually at the hand-offs. A typical split in a product company looks like this.

Product (application) engineers own the source databases and event schemas. They decide that orders.status gets a new value held_for_review, or that the app's search event drops a field. They are not usually thinking about the training set three hops downstream.

A data platform team owns the infrastructure: Kafka, CDC connectors, the lake buckets and table formats, the catalog, the orchestrator, the Spark and SQL engines, access control and cost. They make ingestion boring and reliable.

Analytics engineers (or data engineers embedded in domains) own the silver and gold models: the business definitions, the tests on them, and their freshness.

ML engineers and data scientists own features, labels and training sets, and — through logging — part of the data that flows back in.

The classic incident is a product engineer renaming a column in a harmless-looking migration, the CDC pipeline faithfully propagating it, a silver job filling the old column with nulls, and a model trained on those nulls a week later. Nobody did anything wrong in their own box. The structural fixes — data contracts, schema compatibility checks in the producer's CI, lineage that shows downstream impact, and quality tests at each layer — are the subject of de11. For now, notice that ownership is a design decision just as much as the choice of file format. A related organisational pattern, data mesh, pushes ownership of published datasets into the domain teams themselves, with the platform team providing self-service tooling.

10. A whole pipeline, sized

Put it together for the food-delivery company. The numbers are illustrative but realistic for a mid-size product.

Sources. PostgreSQL holds 400 million orders (about 600 bytes per row with indexes excluded, so roughly 240 GB) and receives 2 million new orders a day, each updated on average 5 times: about 12 million row changes a day, or about 140 per second on average and perhaps 1,000 per second at the dinner peak. The app emits 1.5 billion events a day at about 400 bytes of JSON each: roughly 600 GB a day raw, or about 17,000 events per second on average.

Ingestion. Debezium reads the WAL and publishes order changes to a Kafka topic; at around 1 KB per change event (before and after images in JSON), that is about 12 GB a day — trivial for Kafka. App events go to their own topic with 48 partitions (at ~17,000 events/second, each partition handles about 350 per second, leaving plenty of headroom for a 5× peak). A landing job writes both topics to bronze every 10 minutes.

Bronze. Written as Parquet, the 600 GB of JSON events compresses to roughly 60–120 GB a day, because columnar encoding and compression remove the repeated field names and low-cardinality values (de2 shows why with real byte counts). Ten-minute landing creates 144 files per topic partition per day unless something compacts them — 48 × 144 ≈ 6,900 files a day for the event topic alone — which is why a compaction step (de3) runs hourly.

Silver. An hourly Spark job merges order change events into an Iceberg orders_current table and appends them to an orders_history table with valid-from and valid-to columns; another deduplicates events on event_id and normalises timestamps.

Gold. A daily job builds fact_orders for finance and a training set for the late-delivery model: one row per order at the moment it was placed, with features computed from the history table as of that moment and the label (late or not) attached once delivery completes. That last detail — joining features as of the prediction time, not as of today — is the point-in-time correctness problem hd8 introduced and de12 builds out at scale.

Streaming path. A Flink job reads the same two topics and maintains rolling features — orders at this restaurant in the last 15 minutes, average preparation time in the last hour — in an online feature store, so the model at serving time sees values minutes old. Because both paths read the same topics, the batch-built training features and the streamed serving features come from the same events, which is how you keep them consistent.

End-to-end freshness: serving features in seconds; silver within about 70 minutes; the training set daily. Every one of those numbers is a choice, and the rest of this track is about making each choice well.

Why compute–storage separation won

Older warehouses and Hadoop clusters coupled storage and compute: data lived on the disks of the same machines that processed it, which was efficient for scans (data locality) but meant you sized the cluster for the larger of your storage or your peak compute, and paid for it all the time. When networks inside cloud data centres became fast enough that reading from object storage was close to reading local disks for large sequential scans, the trade flipped. Separation lets a company keep five petabytes in object storage at storage prices, spin up 2,000 cores for a two-hour backfill and then release them, and run a dozen engines over the same data. The price is latency per request — every object read is an HTTP call with tens of milliseconds of first-byte latency — which is why file sizes, file counts and caching dominate lakehouse performance tuning (de2, de3, de13).

Open formats change the economics of engines

When data sits in a warehouse's internal format, the warehouse is the only efficient way to read it, so switching vendors means migrating petabytes. When data sits in Parquet files managed by Iceberg or Delta in your own bucket, an engine is just a client: Spark for heavy transformations, Trino or a warehouse for interactive SQL, DuckDB or Polars on one machine for small jobs, and PyTorch data loaders for training, all reading the same tables. This is why the warehouse vendors added support for open table formats: customers wanted to keep one copy. The consequence for a senior engineer is that engine choice becomes a per-workload decision with real cost differences, which de13 works through.

Reprocessing is the feature that pays for everything

The single most valuable property of a well-designed data platform is the ability to recompute any derived table from raw inputs, deterministically. It is what lets you fix a bug retroactively, add a new feature with two years of history on day one, and rebuild a training set exactly as it was for an audit. It requires three things: raw data retained long enough (bronze in the lake, because Kafka retention is days, unless you use Kafka's tiered storage to push old segments to object storage), transformations that are deterministic functions of their inputs (no "now()" in the logic, no dependence on run order), and outputs that can be atomically replaced for a date range (the idempotent overwrite pattern of de7). Teams that skip any of the three end up unable to answer "what was the data on the day we trained model v17?", which is increasingly a regulatory question as well as an engineering one.

Lambda and Kappa, revisited

sc18 introduced the Lambda architecture (a batch path for correctness plus a streaming path for freshness) and the Kappa architecture (one streaming path, reprocessing by replaying the log). The deeper point is about what forced Lambda into existence: early stream processors could not handle late data, keep durable state or produce exactly-once output, so their results were provisional until the batch caught up. The Dataflow model (Akidau et al., VLDB 2015) showed that a single model with event-time windows, watermarks and triggers can express both bounded and unbounded computation, and engines such as Flink and Beam implemented it. What survives of Lambda in modern platforms is not two code paths for one metric but two freshness tiers over the same events: streamed features for serving, batch-built tables for training and reporting, with logging and shared definitions keeping them consistent.

Freshness is a product requirement with a price

"Real-time" is not a requirement; "the fraud model must see payments made in the last 60 seconds" is. A useful habit is to write freshness as a service-level objective for each table — "silver.orders is at most 75 minutes behind the source 99% of the time" — and attach a cost. Going from daily to hourly batch multiplies the number of job runs by 24 and often the fixed overhead per run (cluster start-up, file listing, small output files) by the same factor. Going from hourly to streaming replaces scheduled jobs with always-on clusters and adds state management. A useful senior move in an interview is to ask what decision the data feeds, how fast the value decays, and whether a cheaper tier with a small streaming exception meets it.

The two directions of flow: reverse ETL and logged predictions

Data does not only flow from production to analytics. Reverse ETL pushes modelled data back into operational systems: customer segments into the CRM, a nightly-computed "likely to churn" score into the database the app reads, batch features into an online key-value store. And ML systems are sources in their own right: every prediction, its inputs and its eventual outcome should be logged as events, because that log is the cleanest training data you will ever get (rec9's log-and-wait pattern). Treat both directions as first-class pipelines with owners, schemas and tests; a reverse-ETL job that silently stops leaves the product running on stale scores, which is worse than an obvious outage.

Data mesh and its limits

Data mesh, an organisational approach popularised by Zhamak Dehghani, treats datasets as products owned by the domain team that produces them, with a central platform providing self-service tooling and global governance. It fixes the bottleneck of one central data team that understands no domain deeply. Its risks are fragmentation (twenty teams, twenty definitions of "active user"), uneven quality, and duplicated infrastructure if the platform is weak. In practice most companies land on a hybrid: domains own their published silver tables under contracts, a central team owns the platform and a small set of company-wide gold definitions.

How data stacks fail in production

Silent upstream schema change. A source column is renamed, retyped or repurposed. CDC passes it through; a downstream job that selects the old column by name gets nulls, or a job that casts a string to a number gets errors on some rows and drops them. Symptom: a feature's null rate jumps on a specific date, a model degrades a week later. Defence: schema compatibility checks at the producer, null-rate and volume checks on silver tables, alerts on the first bad day (de11).

Duplicates and gaps at ingestion. Kafka and CDC deliver at least once, so restarts produce duplicates; an extraction job that crashed between "write files" and "record the high-water mark" re-extracts the same rows. Conversely, a connector that was down longer than the retention window leaves a hole. Symptom: daily counts 3% too high, or a missing hour in an hourly chart. Defence: deduplicate on a stable key in silver, make every load idempotent, and monitor per-hour row counts against the source.

Replication slot runaway. A PostgreSQL CDC connector stops consuming; the replication slot keeps all WAL since its last confirmed position; the primary's disk fills and the production database goes down. This is one of the few ways an analytics pipeline can take down the product. Defence: alert on slot lag in bytes, cap retained WAL (max_slot_wal_keep_size in PostgreSQL 13 and later), and have a runbook to drop the slot and re-snapshot.

Time and time zones. A job partitions events by the server's local date instead of UTC, or by processing time instead of event time, so late events land in the wrong day and daylight-saving changes create 23- and 25-hour days. Symptom: a spike and dip around midnight, mismatched daily totals between two systems. Defence: UTC everywhere in storage, event time for business logic, and explicit handling of late data (de7, de9).

Cost blow-ups. An analyst's query scans an unpartitioned 200 TB table; a streaming job writes a file every second; a backfill runs at full cluster size for a week. Symptom: the monthly bill. Defence: partition pruning, compaction, query cost guards and budgets (de3, de13).

What to watch

For every important table: freshness (time since the newest record), volume (rows per partition versus the same weekday last week), null and distinct rates for key columns, and duplicate keys. For ingestion: Kafka consumer lag, CDC slot lag, connector restarts. For jobs: duration, input size and failures per run, plotted over weeks, because pipelines decay gradually. For cost: spend per pipeline and per team.

The case: Uber's platform through four generations

Uber's engineering blog post "Uber's Big Data Platform: 100+ Petabytes with Minute Latency" (October 2018, linked in the references) is a rare public account of a data stack evolving under real growth, and almost every idea in this lesson appears in it.

Before 2014, Uber's data fit in a few OLTP databases (MySQL and PostgreSQL), a few terabytes in total. The first generation added a Vertica warehouse fed by ad hoc ETL jobs. It grew to tens of terabytes within months, with several hundred users, and hit the classic warehouse limits: data arrived as JSON without schema enforcement, ingestion was fragile, and old data had to be deleted to control cost.

The second generation moved to a Hadoop data lake: raw data landed once in HDFS (the Hadoop distributed file system, the on-premises predecessor of object-storage lakes) as Parquet, queried by Presto, Spark and Hive — the ELT idea, with compute separated from the warehouse. It scaled to tens of petabytes and over 100,000 batch jobs a day. But it was snapshot-based: the post describes ingestion that reconverted a 100+ TB table each run even though only about 100 GB of it was new each day, taking over 20 hours with more than 1,000 Spark executors, and data latency of 24 hours. Small files also strained HDFS.

The third generation, built in 2017, introduced Hudi, an open-source Spark library that adds upserts, deletes and incremental pulls on top of HDFS and Parquet — one of the three table formats de4 covers. Instead of rewriting whole tables, ingestion merged only the changed rows every 10–15 minutes, cutting latency from 24 hours to under one hour, with modelled tables built in under 30 minutes. The post reports over 100 PB in HDFS and over 3,000 raw tables by then. The planned fourth generation targeted 5-minute raw latency and merge-on-read tables that write small delta files and merge them later.

The lessons generalise: snapshots stop scaling long before the data does; incremental, log-based ingestion into transactional tables on open files is what made both freshness and cost manageable; and small files and write amplification are the recurring tax. Those are the problems de2 to de8 take apart one by one.

Goal: see with your own eyes what incremental extraction misses and what a change log keeps. Python 3.12 standard library only (sqlite3); about 10 minutes.

  1. Create a file extract.py. Make an in-memory SQLite database with a table orders(id INTEGER PRIMARY KEY, status TEXT, updated_at INTEGER) and a second table changelog(seq INTEGER PRIMARY KEY AUTOINCREMENT, op TEXT, id INTEGER, status TEXT, at INTEGER).
  2. Add three triggers on orders — AFTER INSERT, AFTER UPDATE and AFTER DELETE — that insert a row into changelog with op 'c', 'u' or 'd'. Triggers stand in for a database's write-ahead log here: real CDC reads the log instead and needs no triggers.
  3. Replay the worked trace from the body using integer minutes as time: insert order 1 as placed at 0, update to preparing at 4, insert order 2 at 10, delete order 2 at 15, update order 1 to picked_up at 21 and delivered at 40.
  4. Simulate an hourly incremental extract: SELECT * FROM orders WHERE updated_at > 0 run once at minute 60. Then print the whole changelog.
  5. Try next: run the incremental extract every 10 minutes instead, and count how many intermediate states it still misses.

What to look for. The incremental extract returns a single row — order 1, delivered — while the changelog has six rows, including order 2's creation and deletion. The extract cannot tell you that order 2 ever existed, so a downstream table built from it would never remove a copy of order 2 picked up by an earlier run either. Running it every 10 minutes catches more states but still misses any change between runs and still never sees the delete. This is the whole argument for log-based CDC in six rows.

Design: a pipeline for a churn model

A subscription video service wants a weekly-retrained churn model. Sources: a PostgreSQL subscriptions table (20 million rows, plan changes and cancellations as updates; occasional hard deletes for GDPR requests) and a playback event stream (3 billion events a day). The model needs, for each subscriber on each Sunday, features such as "hours watched in the last 28 days" and "number of plan downgrades in the last 90 days", and a label "cancelled within the following 30 days". Analysts also want a daily active-subscribers dashboard. Sketch the pipeline: extraction method per source, layers, batch or streaming, and how you make the training set reproducible.

Answer

Extraction. The subscriptions table needs history (plan downgrades over 90 days, the exact state each Sunday) and deletes (GDPR), so use log-based CDC from the WAL into Kafka, not snapshots or updated_at queries. Playback events go straight into Kafka from the players.

Layers. Bronze: the raw CDC topic and raw playback events landed to the lake every 10–15 minutes as Parquet, compacted hourly. Silver: a subscriptions_history table with valid-from and valid-to per version, plus subscriptions_current; playback deduplicated on event ID with UTC event-time timestamps, aggregated into a daily per-subscriber watch-time table. Gold: the dashboard table (daily active subscribers) and a weekly training table with one row per subscriber per Sunday.

Batch or streaming. Batch throughout: weekly retraining and a daily dashboard need nothing fresher than hourly. Streaming would add cost and complexity without value.

Point-in-time correctness. Features for Sunday d must use only data with event time before d (and, more strictly, data that had actually arrived by then); the label looks forward 30 days, so the most recent four Sundays cannot be labelled yet and must be excluded. Plan downgrades come from the history table filtered to valid-from in (d−90, d].

Reproducibility. Store silver and gold as Iceberg or Delta tables; record, for each training run, the snapshot ID (or version) of every input table and the code version. Retraining or auditing model v17 means reading those exact snapshots with time travel. GDPR deletes must still propagate to old snapshots eventually, so snapshot retention is a policy decision agreed with legal — de4 and de12 return to this tension.
