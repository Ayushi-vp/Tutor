A subscription company trains a model to predict which customers will upgrade to the premium plan. The training table is built by joining a year of customer activity to the customers table, which has a plan column and a region column. Offline, the model is excellent: AUC 0.94. In production it is barely better than random. The post-mortem finds the cause in one join. The customers table holds each customer's current state, so for every activity row from last spring the join attached this autumn's plan — and customers who upgraded in the meantime appear as premium customers all year. The model learned "premium customers upgrade to premium", which is perfectly predictive in the training table and useless at prediction time, when the customer has not upgraded yet.

A week later finance raises a different problem: revenue by region for the second quarter changed between two runs of the same report, though no data was deleted. A sales reorganisation had moved 300 accounts to new regions, and the report joined orders to the current region of each account. The same query, run twice, told two different stories about the past.

Both failures are modelling failures, not pipeline failures. The data was complete, fresh and deduplicated; it was simply shaped to answer "what is true now" when the questions were "what was true then". This is the central problem of modelling data for ML: every training example is a question about the past ("given what we knew at 14:05 on 3 March, did this user upgrade within 30 days?"), and the tables must make the past answerable. db12 introduced dimensional modelling and the idea of slowly changing dimensions for analytics. This lesson goes deeper where ML needs it: the SCD types and how to build type 2 history correctly from CDC and from snapshots; as-of joins and their subtle bugs; wide denormalised tables and when they are the right answer; entity-centric feature tables built on a spine of entity and time; and the storage arithmetic of daily snapshots versus SCD2. The case is GitLab's public data handbook, a rare published set of production modelling standards.

The mental model: a company directory and its archive

A company keeps a staff directory: name, team, office, manager. When someone moves team, the directory is edited and the old team is gone. That is fine for "who should I email today?" — the directory answers questions about now. But an auditor asking "who approved this expense on 3 March, and which team were they in then?" cannot use it. They need the archive: every version of every person's record, each stamped with the dates it was valid. To answer, they look up the version of the approver's record whose validity period contains 3 March.

Data tables work the same way. A current-state table is the directory. A history table — a type 2 slowly changing dimension — is the archive: one row per version, each with valid_from and valid_to. Looking up "the version valid at the time of the event" is an as-of join. A model's training example is always an auditor's question: what did we know about this customer at the moment we would have made the prediction?

Two more ideas complete the picture. Instead of an archive of changes, some offices photocopy the whole directory every evening — a daily snapshot. It is easy to search ("open the copy for 3 March") but takes a shelf per day even if nobody moved, and misses moves that were reversed within a day. And for convenience, some reports staple the relevant directory details onto every expense form when it is filed — a wide denormalised table. Lookups become unnecessary, but if a detail was wrong, every stapled copy must be corrected.

The analogy breaks at scale and speed: a data platform keeps archives for hundreds of millions of entities, built automatically from change streams, and answers millions of as-of lookups in a single training-set build. Getting the boundaries of each validity interval exactly right — to the second, in one time zone, without overlaps or gaps — is where real systems go wrong.

Hold on to one sentence for the rest of the lesson: every row you join must be the version that was true — and known — at the moment the row you are joining to describes. Analytics sometimes deliberately breaks that rule ("show last year's revenue by today's sales regions"), and that is fine when it is a stated choice. ML must never break it, because a model is evaluated on how well it predicts the future from the past, and a table that quietly mixes the two makes that evaluation meaningless.

The lesson moves from the simplest structures to the ML-specific ones: grain, facts and dimensions; the SCD types; how a type 2 table is built and checked; the as-of join and its bugs; wide tables; and finally entity-centric feature tables and the spine that turns them into a training set.

1. Grain, facts and dimensions: the recap that matters

db12 covered dimensional modelling in full; three points from it carry this lesson. A fact table records events or measurements at a declared grain — one row per order line, per impression, per account per day — with foreign keys to dimensions and numeric measures. A dimension describes an entity (user, product, merchant, campaign) with descriptive attributes. And the grain must be explicit, because it determines which keys are unique, which measures can be summed, and whether a join multiplies rows (de6's exploding joins are grain mismatches).

Kimball's methodology distinguishes three kinds of fact tables, and all three appear in ML work. Transaction facts have one row per event (a payment, a click) — the raw material for features and labels. Periodic snapshots have one row per entity per period (account balance per day) — the natural shape of entity-centric feature tables. Accumulating snapshots have one row per process instance updated as it passes milestones (an order with placed, paid, shipped and delivered timestamps) — the natural shape for labels such as "delivered late".

2. Slowly changing dimensions

Dimension attributes change: a user upgrades their plan, moves country, changes email; a product changes category or price; a merchant's risk tier is revised. A slowly changing dimension (SCD) policy decides what the table keeps. The numbered types come from Kimball:

  • Type 0 — never change (the original value is kept, e.g. sign-up country).
  • Type 1 — overwrite. Only the current value exists. Simple; history is gone.
  • Type 2 — add a new row per change, with validity dates. Full history.
  • Type 3 — keep a previous-value column (plan, previous_plan). Limited history.
  • Type 4 — keep current values in the dimension and history in a separate table.
  • Type 6 — a hybrid (1 + 2 + 3): type 2 rows plus a type 1 "current value" column on every version, so a query can group by either the historical or the current attribute.

The choice is per attribute and per question. Customer email can be type 1 (nobody analyses historical emails). Plan, region, risk tier and anything a model might use should be type 2, because a model's training example must see the value as of its prediction time. In practice the platform keeps a full type 2 history (or the raw CDC history it is built from) for important entities and lets consumers derive the other types as views.

3. Anatomy of a type 2 dimension

A type 2 table has one row per version of each entity:

The pieces and the rules they must obey:

  • A surrogate key (user_sk) identifies one version. It lets a fact row point to the exact version it was recorded against, and distinguishes versions of the same natural key (user_id). A deterministic choice such as a hash of (natural key, valid_from) makes rebuilds reproducible.
  • The validity interval is half-open: [valid_from, valid_to) — a version is valid from its start, inclusive, up to but excluding its end. Then the end of one version equals the start of the next, and any instant belongs to exactly one version. Closed intervals (BETWEEN) double-count the boundary instant; intervals that end one second before the next starts leave gaps.
  • The current version has an open end, represented by a far-future sentinel (9999-12-31) or null. Sentinels make range predicates simpler (dbt's dbt_valid_to_current option exists for this reason); nulls need COALESCE in every join.
  • Invariants: exactly one current row per natural key (unless the entity is deleted); no overlapping intervals per key; no gaps between consecutive versions; valid_from < valid_to. These are testable (de11), and every one of them is violated by some real pipeline.
  • All timestamps in UTC. A validity boundary in local time shifts by an hour twice a year and disagrees with facts recorded in UTC.

4. Building type 2 from CDC

CDC (de8) gives every committed version of each source row, ordered by log position, with commit timestamps — exactly what type 2 needs. The construction for each natural key:

  1. Order the key's change events by log position.
  2. Each create or update starts a version: valid_from = the event's commit time (source.ts_ms); the previous version's valid_to = the same time.
  3. A delete closes the current version (valid_to = delete time) and, depending on policy, adds a version marking the entity deleted.
  4. The last version stays open.

Incrementally, each batch of changes (say, every hour) touches only the keys that changed: in one MERGE (de4), close each changed key's open version by setting its valid_to and is_current = false, and insert the new versions. A common implementation stages the batch as "rows to close" plus "rows to insert" and merges them on the surrogate key. With a table format, the batch commits atomically, so readers never see a key with two open versions or none.

Edge cases decide correctness. Two changes to the same key with the same commit timestamp (within one transaction, or within a second at coarse precision) would produce a zero-length interval; order by log position and either keep only the last version for that instant or add a sequence number. Updates that do not change any tracked attribute (a last_login touch on a table where you track only plan and region) should not create versions — compare tracked attributes, or the history fills with noise. And a batch that arrives out of order (a replay of older changes) must not reopen closed history; guard with log positions as in de8.

5. Building type 2 from snapshots

Without CDC, history is built by comparing periodic snapshots of the current table. dbt's snapshots are the standard tool: on each run, dbt compares the source with the snapshot table and, for changed rows, invalidates the old version and inserts a new one, maintaining dbt_valid_from, dbt_valid_to, dbt_scd_id and dbt_updated_at. Its timestamp strategy (recommended in the dbt docs) detects change when the source's updated_at is newer than at the last run and uses that value as valid_from; its check strategy compares a list of columns, for sources without a reliable timestamp. Hard deletes are ignored by default; since dbt 1.9 the hard_deletes option can invalidate them (close the version) or record them as a new_record with dbt_is_deleted = true.

The limitation is in the docs' own instruction: snapshots must run on a schedule, and they record state only when they run — "between hourly and daily", the docs suggest. A user who upgraded at 10:00 and downgraded at 15:00 on the same day appears, in a daily snapshot, never to have upgraded. With the check strategy and no source timestamp, valid_from is the run time, not the change time, so a change made at 09:00 and captured at 23:00 is backdated by nothing — features computed for events between 09:00 and 23:00 see the old value. For analytics that may be acceptable; for ML features with intraday dynamics, prefer CDC-built history.

6. As-of joins, and how they go wrong

An as-of join attaches to each fact the dimension version valid at the fact's time:

SELECT f.*, d.user_sk, d.plan, d.region
FROM   fct_purchases f
JOIN   dim_user_scd2 d
  ON   d.user_id = f.user_id
 AND   f.purchased_at >= d.valid_from
 AND   f.purchased_at <  d.valid_to        -- half-open; sentinel for current

For user 553, a purchase at 2026-03-10 matches version 901 (free) and one at 2026-04-01 matches 902 (pro), as in the figure. The same logic is available as a dedicated operator in several engines: pandas' merge_asof (match each row to the most recent row with time ≤ its own), and native ASOF JOIN syntax in DuckDB, Polars' join_asof and some warehouses; in Spark it is a range join, which is expensive unless both sides are partitioned by the key (a bucketed join, de3) or the engine has range-join optimisations.

The classic bugs, each of which has caused real model and report errors:

  • Closed intervals (BETWEEN valid_from AND valid_to): a fact at exactly the boundary instant matches two versions and is duplicated.
  • Overlapping versions from a buggy SCD2 build: some facts match two rows, silently doubling them.
  • Gaps: facts in the gap match nothing and disappear from an inner join — or get null attributes in a left join.
  • Facts before the first version: an event at 09:11 for a user whose first version starts at 09:12 (sign-up recorded slightly later than the first event) is dropped. Backdate the first version to the entity's creation time, or use a left join and handle nulls.
  • Time zone or precision mismatch: facts in local time or truncated to the day, dimensions in UTC to the millisecond.
  • Using processing time instead of event time on either side.

A useful guard: count rows before and after every as-of join (a left join must preserve the fact count exactly; an inner join's drop rate should be near zero and monitored).

7. Late-arriving dimensions and early-arriving facts

Facts and dimensions often arrive through different pipelines with different delays. A purchase can arrive for a merchant whose dimension row has not landed yet (an early-arriving fact, or equivalently a late-arriving dimension). The options: hold the fact until the dimension arrives (simple, delays the fact); insert an inferred member — a placeholder dimension row with the natural key and "unknown" attributes — so the fact joins now, then overwrite the placeholder's attributes when the real row arrives (type 1 on the placeholder) and let later versions follow normally; or rebuild the affected joined output when the dimension arrives (the lookback of de7). For ML training sets, the safest is to build training rows only once all inputs for their time range are complete — which training already needs for label maturity.

8. Wide denormalised tables

A star schema keeps dimensions separate and joins at query time. A wide denormalised table (sometimes called One Big Table, OBT) pre-joins a fact with all the dimension attributes its users need: each purchase row carries the user's plan and region, the product's category and brand, the merchant's tier, as they were at purchase time.

The traditional objection is storage: repeating "Electronics > Phones" on a billion rows. In columnar formats this objection mostly disappears. de2 measured it: a column with 8 distinct strings costs 3 bits per row with dictionary encoding, and a few kilobytes if the rows are sorted so values form runs. Adding 30 low-cardinality dimension attributes to a 2-billion-row fact might add a few gigabytes, not terabytes.

The real trade-offs are elsewhere. For wide tables: no joins at query time (faster, cheaper, and no chance of a user writing the as-of join wrong), simple for BI tools and for training jobs that want one table per dataset. Against: when a dimension attribute is corrected (a product was miscategorised for a month), every affected fact row must be rewritten; definitions must be kept consistent with the source dimensions; schemas with hundreds of columns strain metadata, memory and readability; and if the table was built with current-state joins, the leakage is baked into every row and invisible to its users. The middle path many teams take: keep facts and SCD2 dimensions as the source of truth, and materialise wide tables from them, with as-of joins, for specific consumers — a BI mart, a training dataset — treating the wide table as a disposable, rebuildable output.

9. Entity-centric ML tables and the spine

ML features are mostly about entities: a user's purchase count in the last 30 days, an item's click-through rate, a merchant's chargeback rate. An entity-centric feature table has one row per entity per point in time — typically per entity per day (a periodic snapshot), or per entity per validity interval (an SCD2-shaped feature table where a new row starts whenever any feature changes).

A training set is then assembled around a spine: the set of (entity, prediction time) pairs for which you want examples. For a churn model, the spine might be every active subscriber every Sunday; for a click model, every impression (user, item, impression time). To each spine row:

  1. Attach features point-in-time: values computed only from data available before the prediction time. With daily feature snapshots computed at the end of each day D from data up to D, a prediction at time t on day D may use snapshot D−1 (or the snapshot strictly before t); using snapshot D would include events after t.
  2. Attach the label by looking forward over the label window: cancelled in (t, t + 30 days].
  3. Drop spine rows whose label window has not closed (immature labels).

Worked size. 5 million active subscribers, a weekly spine over 52 weeks: 260 million spine rows. Joining 200 daily user features (about 1 KB per user per day after compression) point-in-time and a 30-day label gives a training table of about 260 million rows — perhaps 100 GB in Parquet. The feature table it reads, at 5 million users × 365 days × 1 KB, is about 1.8 TB as daily snapshots; as SCD2-shaped intervals (most features change less than daily) it may be a fraction of that. de12 builds this join at scale and covers the subtle "available at" versus "event time" distinction.

10. Modelling labels

Labels deserve the same care as features, and they have their own shapes. Most ML labels are outcomes after a prediction time: churned within 30 days, clicked within 1 hour, charged back within 90 days, delivered late. The natural source for them is either a transaction fact table (every cancellation event, every chargeback) or an accumulating snapshot (one row per order with timestamps for each milestone). Three modelling rules prevent most label bugs.

Derive labels from events, not from current state. "Is the customer premium now?" is not "did they upgrade within 30 days of t?". A current-state column such as upgraded_at holds only the latest value and loses repeated events; a fact table of plan changes keeps them all and lets the label be computed for any t.

Record when the label became known. A chargeback for a March payment may be filed in May. A training set built in April must treat that payment as not (yet) charged back, or it will use information from the future of its own build date. Keeping both the outcome's event time and its arrival time lets you build training sets "as of" any date and measure how labels mature — for example, what fraction of eventual chargebacks are known 30, 60 and 90 days after the payment.

Make the label window explicit and close it. Every training row's window (t, t + W] must have fully passed before the row is used, and the window length must be the same for all rows. Mixing rows whose windows are complete with rows whose windows are cut off by the build date silently lowers the positive rate for recent rows, which the model then learns as a time trend that does not exist.

With labels modelled as event facts with arrival times, and features as SCD2 or daily entity tables, the training-set build becomes a mechanical pair of joins around the spine — backwards for features, forwards for labels — that can be reproduced for any as-of date.

GitLab's handbook (the case below) describes a common hybrid: build SCD2 with dbt snapshots, then expand validity periods into daily-grain records for analysis, so users get the simplicity of daily rows over a history stored compactly.

Bitemporal modelling: when you also need "when did we know?"

SCD2 records valid time — when a fact was true in the world. ML adds a second axis: transaction time or knowledge time — when the platform learned it. A plan change made on 1 March but recorded (or corrected) on 5 March was true from 1 March, but a model making a prediction on 3 March could not have known it. A purely valid-time as-of join on 3 March returns the new plan — leakage. A bitemporal table keeps both: each version has valid_from/valid_to and recorded_from/recorded_to, and a point-in-time training join asks for the version valid at t as recorded by t. CDC commit time is usually close to transaction time for live changes, but backdated corrections, late batch loads and manual fixes break the equivalence. Feature stores address this with an "available at" or "created" timestamp on every feature row (hd8, de12); the modelling principle is the same.

Surrogate keys in fact tables: pin the version at write time or resolve at read time

Kimball's classic practice is to write the dimension's surrogate key into the fact row when the fact is loaded — the fact permanently points to the version that was current then. That makes joins equi-joins (fast), but it bakes in the version current at load time, which is wrong for late-arriving facts and becomes stale if history is later corrected. The lakehouse alternative stores only natural keys and timestamps in facts and resolves versions with as-of joins at read or materialisation time, so corrections to history propagate automatically. A pragmatic split: resolve at materialisation time for wide tables and training sets (as-of join once, then equi-access), keep natural keys plus event time in the base facts.

Entity resolution and conformed keys

Entity-centric modelling assumes you know which rows refer to the same entity. In practice a "user" has an anonymous device ID before login, a user ID after, and different IDs in the payments and marketing systems. A conformed user dimension with a mapping table (device → user, with validity intervals of its own, since devices change hands and accounts merge) is a prerequisite for features that span systems. Getting it wrong produces both leakage (merging a device's post-login behaviour into pre-login predictions) and fragmentation (one person counted as three). Treat identity mappings as SCD2 tables in their own right.

Data vault and activity schema

Two alternative modelling styles appear in interviews. Data vault separates hubs (business keys), links (relationships) and satellites (descriptive attributes with history, essentially SCD2 per source), optimising for auditable, insert-only integration of many sources; marts and wide tables are then built on top. The activity schema models everything as one stream of (entity, activity, timestamp, features) rows and builds datasets by temporal joins between activities ("first purchase after a visit"). Both make history and time first-class, which suits ML; both add a layer between sources and the tables users query. The deep point is that every successful approach keeps an append-only, time-stamped record of what was known when, and derives convenient shapes from it.

Modelling for reproducible training sets

A training set is itself a fact table with a precise grain (one row per spine entity-time), and it deserves the same discipline: a declared grain, documented feature definitions with the as-of rule each uses, the label definition and window, the time range and the exclusion rules (immature labels, test accounts), and the versions of every input table (snapshot IDs). Materialise it as an immutable, versioned dataset rather than a view, because a view over mutable tables changes under you (de4's drill). When a model behaves oddly, this metadata is what lets you answer "did the data change or did the model?"

Feature tables as intervals, not days

Daily feature snapshots are the default shape for entity-centric features because they are easy to compute and to join (match on date). But many features change rarely — a user's country, a merchant's category, a lifetime count that changes only on activity — and storing them daily wastes space proportional to entities × days. An interval-shaped feature table stores a new row only when some feature value changes, with validity intervals like an SCD2 dimension; joins become range joins, but storage shrinks dramatically for slow-moving features. Feature stores often keep the canonical data as timestamped rows (entity, feature values, event or creation time) and implement the as-of join themselves, which is equivalent to treating every row as the start of an interval that ends at the next row for the same entity. Choosing between daily and interval shapes is a storage-versus-query-cost decision best made per feature group: fast-changing aggregates daily, slow attributes as intervals.

Nested data in analytical models

Columnar formats support nested and repeated fields (structs, lists, maps — db12's Dremel encoding), which offer a third option between a separate dimension table and flattening everything into columns. An order row can carry a list of line items; a user row can carry a list of recent sessions. Nesting keeps one-to-many data together without a join and without exploding the parent row, which suits training examples that need sequences (the last 50 items a user viewed). The costs are engine support (some tools handle nested types poorly), awkward SQL for filtering inside lists, and the temptation to build unbounded lists that grow forever. Bound them (last N events) and document their as-of semantics like any other feature.

How data models fail in production

Current-state joins in historical work. The most common and most damaging: training sets and historical reports joined to type 1 tables. Symptoms: excellent offline metrics that collapse online; historical reports that change on rerun. Defences: SCD2 for any attribute used in history or features, as-of joins enforced in shared libraries or feature stores, and review of training-set code for joins to current tables.

Broken SCD2 invariants. Overlapping versions (a rerun inserted versions twice), multiple current rows, gaps after a failed batch, zero-length versions from same-timestamp changes. Symptoms: duplicated or missing facts after as-of joins. Defences: invariant tests on every build, idempotent MERGE logic, position-based ordering.

History that is not really history. SCD2 built from daily snapshots presented as complete history; intraday changes missing; deletes ignored. Symptoms: features that disagree with logged online values. Defences: document capture granularity; prefer CDC-built history for features.

Grain drift. A table documented as one row per user per day acquires duplicates after a source change (a second device row, a late correction appended rather than merged). Symptoms: inflated counts, exploding joins downstream. Defences: uniqueness tests on declared grain keys.

Wide-table staleness. A wide training table is materialised once and reused after the dimensions it was built from are corrected; or a wide BI table silently uses current attributes. Defences: lineage from wide tables to their inputs and versions, rebuild on upstream corrections, naming that makes the as-of rule explicit.

What to watch

For SCD2 tables: current rows per key (must be 1), overlap and gap counts, versions created per batch (a spike means noise or a bug), and reconciliation of current rows against the source. For as-of joins: input versus output row counts and the share of facts with no matching version. For training sets: the distribution of the gap between feature timestamps and prediction times (any negative gap is leakage).

The case: GitLab's public data warehouse handbook

Few companies publish their internal data-modelling standards; GitLab's data team does, as part of its public company handbook (the Enterprise Data Warehouse pages linked in the references). It is a useful reference precisely because it is a set of working conventions for a production warehouse rather than a textbook.

The handbook states that the team follows the Kimball methodology and organises models in layers that will look familiar from de1: source-aligned models, preparation models, a common dimensional layer and marts. Dimensions are prefixed dim_ and facts fct_; dimensions carry surrogate keys (named with an _sk suffix), and facts reference dimensions through surrogate keys, with a _pk primary key per fact table. The grain of each model is to be "carefully considered to balance user needs with performance requirements", and shared, conformed dimensions are described in Kimball's terms as a "conformance bus" that lets multiple subject areas be integrated and compared.

On history, the handbook distinguishes current and historical viewpoints ("data analysis typically requires two viewpoints: current and historical") and states that slowly changing dimensions are created using dbt's snapshot functionality, which compares the current state with the previous snapshot on each run and tracks changes through valid-from and valid-to dates. It then describes expanding those validity periods into daily-grain records in the common schema — the hybrid from section 11 — "making time-based analysis more intuitive while maintaining consistency with our dimensional model", and lists practices such as clear current-record indicators, consistent grain across related models and documented validity periods. Read alongside this lesson, it shows the trade-offs being made deliberately in production: snapshot-based SCD2 (simple, captures state at run time), daily expansion for usability, and naming and key conventions that make grain and joins explicit.

Goal: build a type 2 dimension from a change log, then compare an as-of join with a current-state join on the same facts. Python 3.12 standard library (sqlite3); about 15 minutes.

  1. Create changes(user_id, plan, changed_at) with user 553: free at 2026-01-01, pro at 2026-03-15, cancelled at 2026-06-02; user 554: free at 2026-02-01, pro at 2026-02-20. Create purchases(user_id, purchased_at, amount) with a few rows per user spread over January–July.
  2. Build dim_user_scd2 with SQL window functions: valid_from = changed_at and valid_to = COALESCE(LEAD(changed_at) OVER (PARTITION BY user_id ORDER BY changed_at), '9999-12-31'), plus is_current.
  3. Check the invariants with queries: one current row per user; for consecutive versions, valid_to equals the next valid_from.
  4. As-of join: purchases to dim_user_scd2 on user_id with purchased_at >= valid_from AND purchased_at < valid_to; sum amount by plan. Then join purchases to only the current rows and sum by plan again.
  5. Try next: add a purchase exactly at 2026-03-15 and rewrite the join with BETWEEN valid_from AND valid_to; count the output rows.

What to look for. The as-of join attributes each purchase to the plan the user had at the time; the current-state join attributes all of user 553's purchases to "cancelled" and all of 554's to "pro", so revenue by plan differs completely — the leakage of the introduction in a dozen rows. The BETWEEN version returns one more row than there are purchases: the boundary purchase matched two versions.

Keep the script: it is the smallest possible version of the point-in-time join that de12 scales up to billions of rows.

Diagnose and redesign: the upgrade model that leaked

The upgrade-prediction model from the introduction was trained on a table built like this: one row per customer per day of activity in the last year, joined on customer_id to customers (current state: plan, region, seats, account_manager), with label "upgraded to premium within 30 days after the activity date", computed from the plan column's current value and an upgraded_at column that holds the latest upgrade date. Offline AUC 0.94; online near random. Identify every leak and design the tables and training-set build that fix them. The source is a PostgreSQL database with CDC available.

Answer

Leaks. (1) plan joined at current state: customers who later upgraded appear premium on every historical row — the label is effectively a feature. (2) seats and account_manager also change around upgrades (sales assigns a manager when a deal is in progress; seat counts grow at upgrade), so they leak the future too. (3) The label uses upgraded_at, which holds only the latest upgrade; customers who upgraded, downgraded and upgraded again get the wrong dates, and the 30-day window is computed from the wrong event. (4) Rows from the last 30 days have immature labels: a customer who will upgrade next week is labelled negative. (5) One row per active day over-weights very active customers and correlates rows, inflating offline metrics further.

Tables. From CDC, build dim_customer_scd2 with versions of plan, region, seats and account_manager, half-open validity intervals in UTC, invariant tests. Build fct_plan_changes (one row per plan change event, from the same CDC stream) — the source of labels.
