A team spends three months improving a recommendation model. Offline, every iteration is better: the final version beats production by four points of AUC. Online, it loses. After a long investigation, the cause turns out to be the training data, not the model. User features were joined to impressions by event time, but the feature pipeline ran nightly and published at 04:00, so an impression at 01:00 in the training set saw a feature value that, in production, would not exist for three more hours. The model had learned to lean on the freshest features, which in production were always staler than in training. Months of offline gains were measuring a leak.

A second team trains a language model. Halfway through a three-week run on 512 GPUs, a node fails; the job restarts from a checkpoint, but the data loader starts its shards from the beginning of the epoch. A few hundred billion tokens are seen twice, a few hundred billion never. Nobody notices until evaluation shows odd memorisation of certain documents. A third team discovers that its fine-tuning set contains near-duplicates of its evaluation set — the benchmark score was partly recall.

These are failures of the training-data pipeline — the last stage between the lakehouse and the GPU. It has requirements no other consumer has. It must be temporally correct at the level of individual rows, because a model will exploit any leak. It must be reproducible, because models are compared, audited and debugged against the exact data they saw. It must have the right distribution — sampled, stratified, deduplicated and decontaminated on purpose. And it must be fast and resumable: a 512-GPU job costs thousands of dollars an hour, so the data loader must never be the bottleneck and must restart exactly where it stopped.

This lesson builds such a pipeline step by step: point-in-time joins at billions of rows and the subtle difference between event time and availability time; dataset versioning; negative downsampling with calibration correction, stratified and hash-based sampling, and honest splits; exact and near-duplicate removal at scale, with FineWeb's surprising finding that more deduplication can make data worse; sharded formats and how to size them for a GPU cluster; deterministic shuffling and resumption; and streaming tokenisation and sequence packing for LLM pre-training.

The mental model: a printing press for exams

Think of a national exam board producing millions of exam papers. The questions must be drawn only from material taught before the exam date — no question about next term's syllabus (point-in-time correctness). Every printed paper must be traceable: which question bank version, which printing run, which settings (versioning). The mix of easy and hard questions, and of topics, is chosen deliberately, and if hard questions are under-represented on purpose to save paper, the marking scheme must account for it (sampling and calibration). The same question must not appear twice in one paper, and no question may be a copy of one in the published practice papers that students memorised (deduplication and decontamination). And the papers are printed in numbered bundles, shipped to thousands of exam halls, each hall receiving a different, random-looking but recorded set of bundles; if a delivery truck breaks down, the board knows exactly which bundles each hall still needs (sharding, shuffling and resumption).

A training-data pipeline does all of these things for a model instead of a student. The analogy's lesson is that each step is a separate, checkable stage with its own failure mode, and the expensive failures — a leaked question, a duplicated bundle, a lost delivery — are the ones that are invisible until the results come in.

Where the analogy breaks: exam boards print once; training sets are rebuilt often, by code, from tables that change underneath. So the pipeline must be automated and deterministic, and every stage must leave enough metadata behind that a dataset can be rebuilt or audited months later.

The rest of the lesson follows the figure from left to right, and it helps to know in advance which property each stage protects. The joins protect temporal correctness: no row may know anything from after its prediction time. Versioning protects reproducibility: the same version must always mean the same bytes. Sampling and splits protect the distribution: the model should learn from, and be evaluated on, the traffic it will face. Deduplication and decontamination protect honesty: no example should count more than intended, and no test item should leak into training. Sharding and the loader protect throughput and continuity: GPUs should never wait, and a crash should never duplicate or skip data.

A useful habit is to ask, for any training-data pipeline you are shown in an interview or a design review, "which of these five properties does each stage guarantee, and how would I know if it broke?" Most real incidents turn out to be a stage that silently stopped guaranteeing its property — a join that started using event time, a sample that stopped being deterministic, a loader that lost its position — while every job kept reporting success.

1. What the pipeline promises the trainer

Before mechanics, fix the contract between a training-data pipeline and a training job. The pipeline delivers a dataset that is: correct (point-in-time, deduplicated, decontaminated, with the intended distribution); immutable and versioned (the same version always contains the same bytes); described (a manifest of shards, row counts, schema, and how it was built); and servable at speed (sharded so that many workers can read in parallel, in a deterministic order that survives restarts). The training job promises in turn to record which dataset version, seed and sample positions it used. Everything below implements one of these promises.

2. Point-in-time joins at scale

de10 defined the spine and the point-in-time join on small data. At production scale — 5 billion impressions a week, feature tables with tens of versions per user — the implementation decides whether the join takes 20 minutes or 20 hours.

The naive range join. JOIN features f ON f.user_id = i.user_id AND f.available_at <= i.ts AND i.ts < f.next_available_at. Engines execute this as an equi-join on user_id followed by a filter on the range, so every impression of a user is first paired with every version of that user's features. A user with 2,000 impressions and 300 feature versions generates 600,000 intermediate pairs to keep 2,000 rows; heavy users dominate the cost and skew the job (de6). It is correct, and it is the slowest option.

Union, sort and carry forward. Stack impressions and feature versions into one table with a type column, sort by (user_id, time, type) so a feature version at the same instant as an impression sorts first, and use a window function to carry the latest feature values forward: LAST_VALUE(f.x, TRUE) OVER (PARTITION BY user_id ORDER BY time ROWS UNBOUNDED PRECEDING) (the second argument ignoring nulls), then keep only impression rows. Cost: one shuffle and one sort of both inputs together, linear in their combined size. Works in any SQL engine with window functions.

Bucketed merge-asof. Partition (or pre-bucket, de3) both sides by user_id into the same partitions, sort each partition by time, and run a merge-asof inside each partition: one pass that walks impressions and feature versions together, attaching the latest version whose availability time is ≤ the impression time. This is what feature stores do internally, and it is available as merge_asof in pandas per partition (Spark's applyInPandas or mapInArrow), or as native as-of joins in engines that have them. With both sides pre-bucketed, there is no shuffle at all; each task streams its bucket.

Sizes for a weekly build: 5 billion impressions at 40 bytes of keys and timestamps is 200 GB; user feature versions, 200 million users × 7 daily versions × 2 KB of features is 2.8 TB — the feature side dominates, so project only the features the model uses (perhaps 300 bytes, 420 GB). With 2,000 buckets, each task merges about 100 MB of impressions with 210 MB of features in one sorted pass. A naive range join on the same data, for a heavy user with 20,000 impressions and 7 versions, does 140,000 comparisons for that user alone — fine — but with hourly feature versions (168 per week) and bot users with millions of impressions, it explodes; the carry-forward and merge-asof forms do not.

3. Event time versus availability time

The most common leak in production training pipelines is subtle. A feature "purchases in the last 7 days" for day D is computed by a batch job from events up to the end of D and published at 04:00 on D+1. Its event time horizon is D 23:59:59; its availability time is D+1 04:00. A prediction at D+1 02:00 in production used the value for D−1 (published at D 04:00), because D's value did not exist yet. A training join on event time ("latest feature with horizon ≤ prediction time") attaches D's value — two hours fresher than production ever has — and the model learns to rely on freshness it will never get.

The fix is to record, for every feature row, when it became available (the publish or commit time — table-format commit timestamps are a good source, de4), and join on that. Streaming features have the same issue at smaller scale: a value computed from events up to 12:00:00 is written to the online store at 12:00:40 after watermark delay (de9). And the cleanest fix, for any feature that already exists in production, is log and wait (rec9): log the exact feature values served with each request, and train on the logs, so training sees precisely what serving saw. Availability-time joins are then needed only for backfilling new features over periods before they were logged.

4. Labels at scale

Labels are joined forward in time, and their own mechanics matter. For each spine row with prediction time t and label window W, the label is computed from outcome events in (t, t + W]: a click within 30 minutes, a purchase within 7 days, a chargeback within 90 days. Implementation mirrors the feature join — union-sort-and-scan forward or a bucketed merge — with an extra rule: a spine row is only emitted once its window has closed relative to the outcome data's completeness (the latest fully loaded outcome partition). Chargeback-style labels that arrive weeks late need the outcome's arrival time recorded too (de10), so a training set built "as of" date B counts only outcomes that had arrived by B. Measure the label's maturity curve — the fraction of eventual positives observed after 1, 7, 30 and 90 days — to choose W and the exclusion window.

5. Versioning and reproducibility

A training dataset version should be enough to rebuild the data bit for bit, or at least to reread exactly what a model saw. The minimum record:

  • The snapshot ID (or version) of every input table at build time — Iceberg snapshot IDs or Delta versions (de4).
  • The code version (commit hash) and full configuration: time range, filters, spine definition, feature list, label window, sampling rates, seeds.
  • A manifest of the output: every shard's path, size, row count and checksum; the schema; summary statistics (label rate, row counts per split, null rates of key features).
  • Retention that matches the model's audit needs. Input snapshots expire (Iceberg's default expiry age is 5 days, de4), so either tag the input snapshots with matching retention or — usually simpler and cheaper — keep the materialised training set itself, which is far smaller than its inputs.

Materialise, do not recompute. A training set defined as a SQL view over current tables changes whenever any input changes: late data, corrections, backfills (de4's drill). Writing the result once, as immutable shards with a manifest, turns "the data the model saw" into an object you can point at. Tools such as lakeFS or DVC version files in object storage with Git-like semantics; table-format tags do the same for tables; a simple convention — an immutable path per version plus a manifest file — is enough for many teams.

6. Sampling, stratification and splits

Negative downsampling. Click and fraud data are heavily imbalanced: perhaps 1 click per 100 impressions. Keeping all negatives wastes compute on easy examples; keeping a fraction r of negatives (say 5%) cuts the dataset roughly twentyfold. But it changes the prior: the model learns odds that are 1/r times too high. Facebook's 2014 ads paper ("Practical Lessons from Predicting Clicks on Ads at Facebook") gives the correction for a model trained on downsampled data: if the model predicts p′, the calibrated probability is p = p′ / (p′ + (1 − p′) / r), equivalently p′r / (p′r + 1 − p′). Worked: r = 0.05 and a prediction of 0.5 give 0.05 / (0.05 + 0.5) ≈ 0.091; a prediction of 0.2 gives 0.01 / (0.01 + 0.8) ≈ 0.0123. The alternative is to weight each kept negative by 1/r in the loss, which keeps outputs calibrated without post-correction, at the cost of noisier gradients. Either way, measure calibration on an unsampled validation set. The same paper reports that, for its boosted-tree click models, training on only 10% of the data cost about 1% in normalised entropy, and that among negative downsampling rates of 0.1, 0.01, 0.001 and 0.0001 the best performance came at 0.025 — evidence that downsampling is a tuning knob with an optimum, not just a cost saving.

Deterministic, hash-based sampling. rand() < 0.05 picks different rows on every rebuild, breaking reproducibility, and different rows on different partitions after a retry. Use a hash of a stable key: keep a negative if hash(impression_id, "neg-sample-v1") mod 10,000 < 500. The same rows are chosen every time, across engines, and changing the salt string ("v2") draws a new, equally reproducible sample. Sample by entity when the model should see whole entities (all of a sampled user's rows): hash(user_id) mod 100 < 10.

Stratification. Uniform sampling under-represents rare but important segments — new users, small countries, rare item categories. Stratified sampling sets rates per stratum (keep all impressions from new users, 5% of negatives from established ones) and records the rate per row so weights or corrections can be applied per stratum.

Splits that match production. ml9 covered why: random splits leak future information and leak entities across train and test. Training pipelines should produce time-based splits (train on weeks 1–10, validate on week 11, test on week 12, with a gap at least as long as the label window between them so labels do not straddle) and group splits where entities recur (all rows of a user, or all near-duplicate documents of a cluster, in the same split). Assign splits by hashing the group key, so the assignment is stable across rebuilds.

7. Deduplication at scale

Duplicates in training data waste compute, over-weight repeated content, encourage memorisation and — when they cross into evaluation sets — inflate scores. ev11 worked MinHash by hand; here is how it runs on billions of documents.

Exact duplicates. Normalise each document (Unicode normalisation, whitespace, perhaps lowercase), hash it (a 64- or 128-bit hash), and group by hash — a single shuffle on the hash, keeping one document per group. For tabular training rows, exact duplicates usually mean pipeline bugs (double loads, exploding joins) and should be caught by uniqueness tests on the grain key (de11) rather than removed silently.

Near duplicates with MinHash and LSH. For each document: extract shingles (word n-grams), compute a MinHash signature of k values (each the minimum of a different hash function over the shingles), and split it into b bands of r values (k = b × r). Two documents with Jaccard similarity s share at least one band with probability 1 − (1 − sr)b. FineWeb's settings make this concrete: 5-grams, 112 hash functions in 14 bands of 8, targeting documents at least 75% similar. At s = 0.75: s8 ≈ 0.100, so the chance of sharing a given band is 0.1 and of sharing at least one of 14 is 1 − 0.914 ≈ 0.77; at s = 0.5: 0.58 ≈ 0.0039 and 1 − (1 − 0.0039)14 ≈ 0.053; at s = 0.9: 0.98 ≈ 0.43 and nearly 1. The banding makes the decision sharply threshold-like around the target.

The distributed job: (1) map each document to 14 records (band_index, band_hash, doc_id); (2) shuffle by (band_index, band_hash) so documents sharing a band meet; (3) within each bucket, emit candidate pairs (or link every member to the bucket's first member, which is linear in bucket size); (4) find connected components of the candidate graph — iteratively with union-find in a distributed algorithm — and (5) keep one document per component. Volumes: 10 billion documents × 14 band records × ~24 bytes ≈ 3.4 TB of shuffle — large but routine. Two practical hazards: enormous buckets caused by boilerplate shared by millions of pages (cookie banners, templates), which should be capped or handled by removing boilerplate before hashing; and transitive chaining, where A~B and B~C link A and C even if they are dissimilar, which slightly over-removes.

Where to dedup is a quality decision. FineWeb (Penedo et al., 2024) ran exactly this experiment, described in the case below: deduplicating across all crawl snapshots removed far more data and produced a worse model than deduplicating each snapshot independently. Dedup is not just cleaning; it reshapes the distribution, and its scope should be chosen by downstream ablations.

Decontamination. The same machinery, run between training data and evaluation sets (n-gram overlap or MinHash against benchmark items), removes training documents that contain test material, so evaluation measures generalisation rather than recall (ev11).

8. Sharded datasets for large-scale training

A training job on N nodes, each with several data-loader workers per GPU, wants every worker reading large sequential chunks from its own files, with no coordination, no small random reads from object storage, and a cheap way to shuffle. That is what shards provide: the dataset split into many files of moderate size, each read start to finish by one worker.

Common formats:

  • WebDataset: each shard is a POSIX tar file; files making up one sample share a basename (000123.jpg, 000123.json); shards are numbered and listed in brace notation (train-{000000..012345}.tar). Readers stream tar files sequentially, so any storage that supports streaming reads works.
  • MDS (MosaicML Streaming): sample shards plus an index file, designed for streaming from object storage with local caching, deterministic shuffling and resumption; the writer's default shard size limit is 1 << 26 bytes (64 MiB).
  • Parquet shards: natural for tabular training data; row groups give sub-file granularity (de2).
  • Token binaries for LLMs: a flat array of token IDs per shard with an index of document offsets, memory-mapped by the loader (section 10).
  • TFRecord and similar record-oriented formats in the TensorFlow ecosystem.

Sizing shards: big enough that per-file overhead (open latency of tens of milliseconds on object storage, metadata) is negligible and reads are sequential; small enough that there are many more shards than workers, so shards can be shuffled and balanced, and that a partially read shard at a restart is not a large waste. Worked: a 10 TB image dataset on 64 nodes × 8 GPUs × 4 workers = 2,048 workers. With 64 MiB shards there are about 150,000 shards — about 73 per worker per epoch — good shuffle granularity, and each shard takes well under a second to read at 100 MB/s. With 10 GB shards there would be 1,000 shards — fewer than workers — and some workers would sit idle.

9. Shuffling and deterministic resumption

Gradient descent assumes batches are roughly independent samples of the data. If shards were written in a sorted order — by date, by source, by label — and the loader reads shards sequentially, batches are dominated by one date or source at a time, which slows or biases training. Streaming loaders therefore shuffle at two levels: the order of shards (a seeded permutation per epoch) and the order of samples within a worker, via a shuffle buffer that holds samples from several shards and draws randomly. WebDataset exposes both as pipeline stages (shuffle over shard URLs and over samples, with buffers of about a thousand samples suggested as a starting point). Shuffle quality depends on the buffer size relative to shard size and, more than anything, on how shards were written: shuffling rows before writing shards (a global shuffle at build time) makes even a modest loader buffer sufficient.

MosaicML Streaming makes shuffling deterministic and elastic. Samples are partitioned across a fixed number of canonical nodes (by default the number of physical nodes at the start), and its default shuffle algorithm, py1e, spreads each shard's samples over a range of at most shuffle_block_size samples (default max(4,000,000 / num_canonical_nodes, 1 << 18)), with all randomness derived from a seed (default 9176). The docs recommend a shuffle block at least ten times the number of samples in a shard for good quality. Because the order is a function of the seed, epoch and canonical layout, a job can resume mid-epoch exactly — and on a different number of physical nodes — by recomputing the order and skipping the samples already consumed.

Deterministic resumption is worth insisting on. Without it, a restart either replays from the start of the epoch (duplicating up to a full epoch of samples — a real problem when training on the data only once, as in LLM pre-training) or starts fresh shards (skipping data). The loader's state to checkpoint is small: the seed, the epoch and the number of samples consumed per rank.

10. Streaming tokenisation and packing for LLM pre-training

LLM pre-training data is text at enormous scale — FineWeb alone is 15 trillion tokens — and the model consumes fixed-length sequences of token IDs. Between the two sit tokenisation and packing.

Tokenisation maps text to integer IDs with a fixed vocabulary (byte-pair encoding and its variants). Two strategies exist. Pre-tokenise: run the tokenizer once in a distributed batch job and write token IDs to binary shards; training then reads integers with no CPU cost, deterministically. Tokenise on the fly: stream text and tokenise in data-loader workers; this keeps the tokenizer and the mixture flexible but costs CPU on training nodes and makes exact resumption harder, because token counts per document are not known in advance. Large production runs usually pre-tokenise; mixture and tokenizer research often streams.

Storage width. GPT-2's vocabulary of 50,257 fits in an unsigned 16-bit integer (maximum 65,535), so nanoGPT's preparation script writes uint16 binaries. Llama 3's vocabulary of 128,256 does not; it needs 4 bytes per token (or a 17-bit packing scheme). Storage for 15 trillion tokens: 30 TB at 2 bytes, 60 TB at 4 bytes — before any replication.

Packing. Documents have arbitrary lengths; sequences have a fixed length L (say 8,192). Padding each document to L would waste most of the compute on short documents. Instead, concatenate tokenised documents into one stream, separated by an end-of-sequence (EOS) token, and cut the stream into consecutive chunks of L tokens. A sequence then contains several documents, and a long document spans several sequences. Two refinements: attention masks that prevent tokens attending across document boundaries within a packed sequence (supported by recent attention kernels via per-document position information), and position IDs that restart at each document. Whether cross-document attention matters is an empirical question; the bookkeeping cost is small.

Mixtures. A pre-training corpus combines sources — web, code, books, papers, multilingual text — with target proportions that differ from their raw sizes. Writing each source to its own shard streams and sampling between streams by weight at load time keeps mixtures adjustable (and lets them change during training, as in curriculum or annealing phases); pre-mixing sources into the same shards freezes the mixture.

Throughput check. Token data is compact, so bandwidth is rarely the constraint. A 512-GPU run where each GPU processes about 3,000 tokens per second consumes about 1.5 million tokens per second — 3 MB/s at 2 bytes per token, 6 MB/s at 4. Images and video are another matter: 2,048 workers each needing 50 images per second at 150 KB is about 15 GB/s from storage, which requires local caching, large sequential reads and enough decode CPU. Always compute the loader's required throughput and compare it with storage and CPU capacity before blaming the GPUs.

Why the feature store's join is a sort, not a lookup

A training-set join looks like many lookups — for each example, find the feature value valid at its time — and a naive implementation issues them one by one against a key-value store. At billions of examples, random lookups are hopeless; the efficient algorithm turns the problem into sorting. Sort examples and feature versions by (key, time) and a single merge pass resolves every lookup sequentially. This is why point-in-time joins are implemented as bucketed sort-merge in batch engines, why pre-bucketing both sides by entity pays off for repeated builds, and why incremental builds (only new spine rows, joined against feature versions after the last build's horizon plus each key's last version before it) are possible. It is also the deep reason feature stores separate an offline store (columnar, sorted, historical) from an online store (key-value, latest only): the access patterns are sorting and lookup, and no single storage layout serves both.

Sampling changes what the model is optimising

Every sampling decision is an implicit reweighting of the loss. Negative downsampling reweights classes; stratified sampling reweights segments; capping examples per user (common to stop power users dominating) reweights users; deduplication reweights content by removing repeats. Some of these are intended (you do not want bots to dominate), some are accidental. The principled view: decide the distribution you want the model to be good on — usually production traffic, sometimes a balanced view of users — and treat every sampling choice as importance sampling relative to it, recording rates per row so weights can be applied in the loss or in evaluation. Evaluate on data sampled like production, not like the training set.

Deduplication interacts with quality and memorisation

Research on language models found that training data with many repeated sequences increases memorisation and that deduplication improves efficiency (Lee et al. 2021, ev11's case). FineWeb's ablation adds the caution that what deduplication leaves behind can be worse than what it removes, because content repeated across many crawls is disproportionately popular, well-maintained pages, while content unique to an old crawl is disproportionately junk. Two practical consequences: choose dedup scope (per snapshot, per source, global) by ablation, and apply quality filters as well as dedup rather than assuming dedup implies quality. A related subtlety is that exact duplicates are sometimes signal — a frequently re-shared article is popular for a reason — so some pipelines downweight rather than remove.

Data loaders are distributed systems with failure modes

At thousands of workers, the loader shows the same pathologies as any distributed system (cl6's deep section made the same point). Synchronised behaviour causes thundering herds: every rank finishing an epoch at once and fetching new shards at once. Long-tail latency from object storage makes the slowest worker gate the step, because synchronous data-parallel training waits for every rank. Imbalanced shard assignment leaves some ranks with less data at the end of an epoch. Remedies borrowed from systems design: prefetch with a deep queue, local caches of upcoming shards, randomised or staggered fetches, balanced assignment by sample count rather than shard count, and observability — per-rank data wait time is the metric that tells you whether the GPUs are starved.

The tokenizer is part of the data contract

Pre-tokenised datasets bind the data to a tokenizer version: vocabulary, normalisation rules, special-token IDs. A mismatch — training with one tokenizer's IDs and serving with another's — produces a model that sees gibberish, and subtler mismatches (a changed normalisation rule, a different EOS ID) produce subtle degradation. Treat the tokenizer as a versioned artefact recorded in the dataset manifest, checksum its files, and validate at training start that the dataset's tokenizer version equals the one the model configuration expects. The same applies to image preprocessing (resize, crop, normalisation constants) and to feature normalisation statistics in tabular models.

Incremental builds versus full rebuilds

Rebuilding eight weeks of training data every week re-does seven weeks of identical work. Incremental builds append only the newest week's spine rows, joined against feature versions as of their own times, and keep earlier weeks' materialised rows — which is correct only if nothing upstream changed for those weeks. Late labels, feature backfills (de7) and bug fixes all change history, so incremental pipelines need a rule for when to rebuild: track the input snapshot IDs each week's rows were built from, and rebuild a week whenever any of its inputs changed for its time range. That turns a training set into an incremental materialised view with explicit invalidation — cheaper to maintain, and still reproducible because each week's provenance is recorded.

How training-data pipelines fail

Temporal leakage. Event-time joins where availability time was needed; features computed with outcome information; labels whose windows were open at build time. Symptoms: offline metrics far better than online; online performance improving as the model ages (because live data catches up). Defences: availability-time joins, logged features, leakage tests (every feature timestamp ≤ prediction time), and comparing offline-joined values with logged online values.

Unreproducible datasets. Training sets built from views over mutable tables; random sampling without fixed seeds; inputs expired. Symptoms: cannot rebuild the data for a model under investigation; "same" pipeline gives different row counts. Defences: pinned snapshots, hash-based sampling, materialised versions with manifests.

Distribution surprises. Downsampling without calibration correction (probabilities systematically too high); a stratum accidentally dropped by a join; duplicates inflating some entities. Defences: summary statistics in the manifest compared with previous versions (label rate, counts per segment), calibration checks on unsampled validation data.

Contamination. Evaluation items present in training data, often via near-duplicates or scraped copies. Symptoms: implausibly high benchmark scores; memorised answers. Defences: decontamination with n-gram or MinHash matching against all evaluation sets before each training run.

Loader starvation and bad resumption. GPUs waiting on data; duplicated or skipped samples after restarts. Symptoms: GPU utilisation dips at shard boundaries; per-rank data wait times; loss spikes after restarts. Defences: prefetching and caching, throughput tests before large runs, deterministic loaders with checkpointed state, and verifying after a test restart that the sample sequence continues exactly.

What to watch

For each dataset version: row counts per split and stratum, label rate, feature null rates and distributions versus the previous version, duplicate rate, contamination hits, and build time. For each training run: per-rank data wait time per step, samples per second versus target, cache hit rate, and the loader state at each checkpoint.

The case: FineWeb's deduplication ablations (2024)

"The FineWeb Datasets: Decanting the Web for the Finest Text Data at Scale" by Guilherme Penedo and colleagues at Hugging Face (arXiv, June 2024, revised October 2024) describes building a 15-trillion-token pre-training corpus from 96 Common Crawl snapshots, and — unusually — publishes the ablations behind each pipeline decision, including a 1.3-trillion-token educational subset, FineWeb-Edu, that improved knowledge and reasoning benchmarks.

The deduplication study is the part every data engineer should know. The team used MinHash deduplication, which scales across many CPU nodes, with each document's word 5-grams and 112 hash functions split into 14 buckets of 8 hashes, targeting documents at least 75% similar. Their first approach was global: deduplicate across all 96 snapshots iteratively, starting with the most recent snapshot and moving to older ones, each deduplicated against everything already kept. For the oldest snapshots this removed as much as 90% of the data. Yet models trained on a 350-billion-token random sample of the globally deduplicated dataset showed little improvement over a model trained on non-deduplicated data and scored well below the RefinedWeb baseline.

To understand why, they took one old snapshot (2013-48) and trained two models: one on the roughly 31 billion tokens that global deduplication had kept, and one on 171 billion tokens obtained by deduplicating, within that snapshot alone, the roughly 460 billion tokens that global deduplication had removed. The model trained on the removed data did better. Visual inspection confirmed that the kept 10% contained more ads, incoherent keyword lists and badly formatted text: content that appears in only one old crawl is disproportionately low quality, while good pages recur across crawls and were therefore "duplicates". The alternative — deduplicating each snapshot independently with the same parameters — produced about 20 trillion tokens and, sampled across all snapshots, matched RefinedWeb's performance; FineWeb's released pipeline uses per-snapshot deduplication followed by further filtering.

The lessons generalise beyond LLMs. Every stage of a training-data pipeline changes the distribution the model learns from; obvious-seeming steps (more dedup is better) can backfire; and the only reliable judge is a downstream ablation — train small models on variants of the data and compare. That makes training-data pipelines experimental systems as much as ETL: they need versioning, cheap rebuilds and recorded configurations precisely so such ablations can be run and trusted.

Goal: pack a toy corpus into fixed-length token sequences, write uint16 shards with an index, and read them back in a seeded, resumable order. Uses NumPy from gpt_env; about 15 minutes.

  2. Concatenate all documents with EOS between them into one stream. Cut it into sequences of L = 1,024 tokens; drop the remainder. Count how many sequences contain at least one EOS and how many documents span two sequences.
  3. Write the sequences into shards of 64 sequences each (arr.tofile("shard-00007.bin")) and a manifest.json with each shard's file name, sequence count and SHA-256 checksum.
  4. Write a reader: given seed and epoch, compute a permutation of all (shard, row) positions with np.random.default_rng(seed + epoch).permutation(n), read sequences with np.memmap, and yield batches of 8.
  5. Resume test: read 37 batches, "crash", create a new reader with the same seed and epoch, skip 37 × 8 positions, and read 5 more batches. Compare with batches 38–42 of an uninterrupted run.

What to look for. Packing should waste no positions except the final remainder, and many documents should cross sequence boundaries — the reason for per-document masks. Each shard is exactly 64 × 1,024 × 2 bytes = 131,072 bytes, and the checksums let you verify a copy. The resumed batches must be identical to the uninterrupted ones: the order is a pure function of seed, epoch and position, so the only state worth checkpointing is the number of samples consumed.

Design: a weekly training set for an ads click model

An ads team retrains weekly on the last 8 weeks of impressions: 2 billion impressions a week, a 1.2% click rate, clicks attributed within 1 hour. Features: user features from a daily batch job published at 05:00 UTC (200 features), ad features updated hourly by a streaming job, and request-context features logged with each impression. The model's predicted probabilities are used in auction bidding, so calibration matters. Training runs on 64 GPUs that consume about 400,000 examples per second in total. Design the training-data pipeline: joins, labels, sampling, splits, versioning, format and loader.

Answer

Spine and labels. Spine = impressions (impression ID, user, ad, timestamp, logged context). Label = a click attributed to the impression within 1 hour; build each week once the attribution window and the click pipeline's completeness for that week have closed (exclude the last 2 hours plus any click-ingestion lag).

Features. Context features come from the impression log itself (what serving saw). Ad features: logged at serving if possible; otherwise an availability-time as-of join to the hourly stream's versions, using each version's write time. User features: as-of join on availability time — an impression at 02:00 on day D uses the snapshot published at 05:00 on D−1 (covering data to the end of D−2), never the one published on D. Implement both joins as bucketed merge-asof: bucket impressions and feature versions by user ID (and by ad ID for the ad join) into the same bucket counts, sorted by time.

Sampling. 16 billion impressions over 8 weeks with 1.2% positives: keep all clicks (~190 million) and 10% of non-clicks via hash(impression_id, "neg-v3") mod 1000 < 100 (~1.58 billion), about 1.77 billion rows. Record r = 0.1 per row; either weight negatives by 10 in the loss or correct predictions with p = 0.1p′ / (0.1p′ + 1 − p′) before bidding, and verify calibration on an unsampled validation week.

Splits. Train on weeks 1–7, validate on week 8 (unsampled, or sampled with weights), with no user-level leakage concerns beyond time because the model is evaluated on future traffic — the time split is what matters.

Versioning. Pin snapshot IDs of the impression, click and feature tables; record code commit, sampling salt and rates; write Parquet shards (or MDS) of about 128 MB with a manifest of checksums and per-shard counts; keep the materialised version for as long as models trained on it are in production plus the audit period.

Loader. 1.77 billion rows at ~1 KB each is ~1.8 TB, about 14,000 shards of 128 MB — about 220 per GPU per epoch. Rows are globally shuffled before sharding, so a modest buffer suffices. Throughput: 400,000 examples/s × 1 KB = 400 MB/s across 64 GPUs — achievable from object storage with prefetching and a few workers per GPU; cache shards on local NVMe for multi-epoch runs. Use a seeded, deterministic order and checkpoint samples consumed per rank so restarts resume exactly.
