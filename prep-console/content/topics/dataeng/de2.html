A data platform team at a retailer lands its clickstream in the lake as gzip-compressed JSON lines, one file per minute per web server. It works on day one. A year later the folder holds 40 TB in 9 million files. A data scientist asks a simple question — how many purchases per country per day last quarter — and the query reads all 40 TB, because to find the two fields it needs (event type and country), the engine must decompress and parse every byte of every JSON object. It spends the first eleven minutes just listing and opening files, before it reads a single event. The query costs real money, takes over an hour, and fails twice when a single malformed line with an unescaped quote makes the parser give up.

The same data rewritten as Parquet, compacted into files of a few hundred megabytes and sorted by event type, answers the question by reading two columns out of twelve, skipping every row group whose statistics show no purchases, and touching perhaps 1% of the bytes. Nothing about the hardware changed. The difference is entirely in how the bytes are arranged inside the files, and how many files there are.

This is why file formats are the first technical topic of the track. Every engine you will meet later — Spark, a warehouse, DuckDB, a PyTorch data loader — spends most of its time reading files, and the format decides how many bytes it must read, how much CPU it spends decoding them, how many requests it makes to object storage, and whether a filter can skip data at all. ML pipelines feel this acutely: a training set is often the widest table in the company, read many times, and a feature pipeline that scans a year of events every night pays for a bad layout every night.

This lesson starts with the text formats (CSV and JSON) and why they hurt, then the binary row format Avro, then takes a Parquet file apart: row groups, column chunks and pages, the footer, each encoding, compression codecs, statistics and predicate pushdown, with byte counts measured from a real one-million-row file written with pyarrow. It finishes with the small-files problem and Uber's account of saving petabytes by changing codecs and column layout.

The mental model: a filing cabinet versus a pile of letters

Imagine you keep a record of every customer interaction. In the first office, each interaction is a handwritten letter, and the letters are piled in order of arrival. Every letter says, in full sentences, "On the eighth of October, customer five-five-three, in Germany, viewed product sushi-12." To count purchases by country, you must pick up every letter and read every sentence. That is CSV and JSON: human-readable, self-describing in a loose way, and expensive to read in bulk.

In the second office, the clerk keeps a filing cabinet. Each drawer covers a block of time (that is a row group). Inside each drawer, there is a separate folder for each kind of information — one for dates, one for customers, one for countries, one for event types (those are column chunks). The country folder does not repeat "Germany" ten thousand times; it has a small code sheet at the front (1 = Germany, 2 = France…) and then a list of codes (that is dictionary encoding), and where the same code appears many times in a row it just writes "1, repeated 400 times" (that is run-length encoding). On the front of each drawer is a label: "dates from 08:00 to 10:24; event types from add_to_cart to view" (those are statistics). And there is an index card at the back of the cabinet listing every drawer and folder and where it sits (that is the footer).

To count purchases by country, the clerk reads the index card, opens only the "event type" and "country" folders, and skips any drawer whose label proves it contains no purchases. Most of the cabinet is never opened. That is Parquet.

The analogy breaks in two places worth knowing. A real cabinet can be updated by slipping a letter into a folder; a Parquet file cannot be changed after it is written, so updates mean writing new files (and table formats, in de4, track which files are current). And the clerk's labels only help if the drawers are organised: if every drawer holds a random mix of dates and event types, every label says "everything", and the clerk must open every drawer. That second point — layout matters as much as format — is the bridge to de3.

The formats in one picture

There are two axes. Text versus binary: text formats (CSV, JSON) store values as characters that must be parsed; binary formats store typed values directly. Row versus columnar: row formats store each record's fields together (good for writing and reading whole records); columnar formats store each field's values together (good for reading a few fields of many records). CSV and JSON are text and row-oriented. Avro (and Protobuf, used by many services) is binary and row-oriented. Parquet and ORC are binary and columnar.

A reader who stops here should remember that a columnar file lets a query read only the columns it uses, that encodings make repeated and ordered values nearly free, that statistics let readers skip whole slices of rows, and that all of this assumes reasonably large, well-organised files.

1. The text formats: CSV and JSON

CSV (comma-separated values) stores one record per line and separates fields with commas. It has no types: 00123 may be a string with leading zeros or the number 123, and only the reader decides. It has no standard for nulls (empty field, NULL, \N, NA are all in use), for quoting (a field containing a comma must be quoted; a field containing a quote must double it; a field containing a newline breaks naive line-based readers) or for character encodings. It has no schema beyond an optional header line. To read one column, a reader must still scan and tokenise every byte of every line, because column boundaries are only discovered by parsing.

JSON (JavaScript Object Notation), usually stored as JSON lines (one object per line), fixes some of this: it has strings, numbers, booleans, null, arrays and nested objects, and every record names its fields. The price is size — every record repeats every field name — and a type system too weak for data work: no distinction between integers and floats beyond the digits, no dates or timestamps (they become strings), and numbers that some parsers silently turn into 64-bit floats, losing precision above 253. JSON is also schema-on-read: one producer writing "price": "12.50" instead of 12.5 is invisible until a reader chokes.

Both formats are row-oriented text, so they share three costs: bytes (text representations are several times larger than binary ones), CPU (parsing text is slow — often slower than reading the bytes from storage), and fragility. They are fine at the edges of a platform — a partner's daily drop, a human-readable export, raw logs landed into bronze exactly as received — and wrong as the storage format for anything queried repeatedly.

2. Avro: compact binary rows with a schema

Apache Avro is a binary, row-oriented format designed for data in motion. Records are encoded field after field with no field names and no delimiters: integers as variable-length zig-zag encoded numbers (small values take 1 byte), strings as a length followed by bytes. The reader knows how to decode the bytes because it has the schema, a JSON document listing each field's name and type. An Avro object container file puts that schema in the file header, then a 16-byte random sync marker, then blocks of records (each block compressed as a unit), each followed by the sync marker again. A reader dropped into the middle of a file can scan for the marker to find the next block boundary, which makes Avro files splittable across parallel tasks.

Avro's distinguishing feature is schema resolution. A reader can use a different schema from the writer's: fields are matched by name, a field the reader expects but the writer did not write is filled from the reader schema's default value, fields the writer wrote but the reader does not want are skipped, and some type promotions (int to long, float to double) are allowed. This is what lets producers and consumers of a Kafka topic evolve independently, and why Avro, together with a schema registry that stores each schema version, is a common choice for CDC events and service messages (de8 covers registries and compatibility modes). For analytical scans, though, Avro has the row-format problem: reading one field means decoding every field before it in every record.

3. Parquet: the anatomy of a columnar file

Apache Parquet was created in 2013 by engineers at Twitter and Cloudera, inspired by Google's Dremel paper (db12 introduced Dremel's nested columnar encoding). It is now the default storage format of most lakes and lakehouses. Its structure has four levels.

A file begins with the 4 magic bytes PAR1. It contains one or more row groups, each a horizontal slice of rows — for example rows 0 to 99,999. Within a row group, the values of each column are stored contiguously as a column chunk, so a reader that needs only two columns reads only those two chunks. Each column chunk is divided into pages, the unit at which values are encoded and compressed: optionally a dictionary page first, then data pages. At the very end is the footer: a FileMetaData structure serialised with Apache Thrift, followed by a 4-byte footer length and PAR1 again.

The footer holds the schema; the number of rows; and for every row group, for every column chunk, the byte offset and size, the codec, the list of encodings used, the number of values and the statistics (minimum, maximum, null count). It is at the end because the writer only knows those offsets after it has written the data; it writes everything in one sequential pass and then writes the index. A reader therefore starts at the end. On object storage, a typical reader issues one ranged GET for the last few tens of kilobytes of the file (which usually contains the whole footer), parses it, decides which row groups and columns it needs, and then issues ranged GETs for just those byte ranges, often merging nearby ranges into one request.

How big are these units? The Parquet project's documentation recommends large row groups (it says 512 MB to 1 GB) so that a row group matches a large sequential read. Real writers use their own defaults: parquet-java (used by Spark and Hive) targets 128 MB row groups (parquet.block.size) and 1 MB pages, and limits pages to 20,000 rows; pyarrow 25 caps a row group at 1,048,576 rows by default and uses 1 MB data pages and a 1 MB dictionary page limit. These defaults are checked against the current parquet-java README and pyarrow 25.0.1 documentation as of October 2026, and they change over time, so check the version you run.

5. Dictionary encoding and the RLE/bit-packing hybrid

Plain encoding writes values back to back: 8 bytes per 64-bit integer, and for strings a 4-byte length followed by the bytes. That is why event_type takes 9.36 MB plain: one million strings averaging about 5 characters, plus 4 bytes of length each.

Dictionary encoding collects the distinct values of the column chunk into a dictionary page and replaces each value with its index. event_type has 8 distinct values, so the dictionary is 8 short strings and the data pages hold one million indices between 0 and 7. Those indices are then stored with Parquet's RLE/bit-packing hybrid encoding (the specification calls the combination RLE_DICTIONARY). Bit-packing stores each index in the fewest bits that can hold the largest: 8 values need 3 bits (23 = 8), so one million indices take 3,000,000 bits = 375,000 bytes. The measured column is 379,818 bytes — 375,000 for the codes plus the dictionary and page headers. country, with 50 values, needs 6 bits (26 = 64 ≥ 50): 750,000 bytes predicted, 754,766 measured. The arithmetic is exact because the encoding is that simple.

The RLE (run-length encoding) half of the hybrid kicks in when the same index repeats: instead of bit-packing 400 copies of "2", it writes "2, repeated 400 times" in a couple of bytes. In our file the event types are in random order, so runs are short and bit-packing does all the work. When the same table is sorted by event_type and then country, the event_type column becomes 8 long runs and shrinks from 380 KB to 2.9 KB; country becomes 400 runs (50 per event type) and shrinks to 3.9 KB.

Dictionary encoding has a limit. The dictionary itself must fit in its page limit (1 MB by default in both pyarrow and parquet-java). event_id is unique: its dictionary would need a million entries, so after the first ~131,000 values (1 MB ÷ 8 bytes) the writer gives up — dictionary fallback — and writes the rest of the chunk in plain encoding. The footer records both encodings (PLAIN, RLE, RLE_DICTIONARY), and the column ends up slightly larger than plain (8.27 MB versus 8.00 MB) because of the wasted dictionary. user_id, with 200,000 distinct values, also overflows its dictionary partway through. High-cardinality columns are where general-purpose compression has to do the work instead.

6. Delta encoding for ordered numbers

Some columns are neither repetitive nor random: they are ordered. event_id increases by exactly 1 per row; ts increases by an average of 86 milliseconds. Storing each value in 8 bytes wastes almost all of the bits. Delta encoding (DELTA_BINARY_PACKED in Parquet) stores the first value, then the differences between consecutive values, in blocks; within each block it subtracts the smallest difference and bit-packs the remainders. For event_id every difference is 1, so every remainder is 0 and needs 0 bits: writing this column with delta encoding produced 24,000 bytes instead of 8,000,000 — essentially just block headers. For ts, gaps range from 0 to a few hundred milliseconds, needing around 9 bits each: 1.17 MB instead of 8 MB, uncompressed. pyarrow does not choose delta encoding by default; you request it per column with column_encoding={"ts": "DELTA_BINARY_PACKED"} and use_dictionary turned off for that column. Spark's parquet-java writer uses delta encodings automatically only for the newer "v2" data pages.

Parquet has other encodings for specific shapes: DELTA_LENGTH_BYTE_ARRAY and DELTA_BYTE_ARRAY for strings (the latter stores shared prefixes once, which suits sorted URLs or keys), and BYTE_STREAM_SPLIT for floating-point numbers, which writes all the first bytes of the values, then all the second bytes and so on. Floats rarely repeat exactly, but their high-order bytes (sign and exponent) are very similar, so splitting them out gives the compression codec long runs of similar bytes. Uber reported in 2022 that byte-stream split alone does not shrink data but improves what a codec achieves afterwards.

7. Nulls and definition levels

How does Parquet store price, which is null on 90% of rows? It does not store the nulls as values. Alongside each optional column it stores definition levels: for a flat optional column, one small number per row, 1 if the value is present and 0 if it is null, encoded with the same RLE/bit-packing hybrid (1 bit per row, with long runs of zeros collapsing). The value stream then holds only the 100,000 real prices. Plain, that is 100,000 × 8 bytes = 800 KB plus about 125 KB of 1-bit levels, which matches the measured 0.96 MB; with dictionary encoding (many prices repeat at two decimal places) it drops to 0.40 MB. Nested data (lists and structs) adds repetition levels that record where each list begins — the Dremel idea db12 described — but you rarely need to think about them unless you are debugging a writer.

8. Compression codecs

After encoding, each page can be compressed with a general-purpose codec. The common ones are Snappy (very fast, modest ratio; the default in pyarrow and in Spark's Parquet writer), zstd (Zstandard: much better ratio at modest CPU cost, with levels 1 to 22), gzip (good ratio, slow to decompress), and LZ4 (very fast). Codecs work on bytes, finding repeated byte sequences, so they help most on what encodings left behind. The measured table shows it: Snappy halves the integer and timestamp columns, which still contain long runs of identical high-order bytes, but does nothing for event_type and country, which bit-packing already squeezed to near their information content (Snappy even added a few hundred bytes of framing). zstd goes much further on integers — event_id 1.28 MB versus Snappy's 4.28 MB — because it finds longer-range patterns.

Because compression is per page, a reader decompresses only the pages it reads, and pages from different columns can be decoded in parallel. Decompression speed matters more than compression speed for tables that are written once and read many times; zstd decompresses fast at any level, which is why many lakes moved to it. The trade-off is write-time CPU: high zstd levels are slow to compress.

9. Statistics and predicate pushdown

Every column chunk's metadata in the footer can carry statistics: minimum value, maximum value and null count. Writers can also add a page index — a ColumnIndex with min and max per page and an OffsetIndex with each page's location — so a reader can skip individual pages, not just whole row groups. (pyarrow writes chunk statistics by default but the page index only when you pass write_page_index=True.) Optionally a writer adds a Bloom filter per column chunk: a compact bit array that can say "this value is definitely not in this chunk", useful for equality lookups on high-cardinality columns like IDs. parquet-java leaves Bloom filters off by default.

Predicate pushdown is the engine passing a query's filter down to the reader. Suppose the same one million events are written with 10 row groups of 100,000 rows, sorted by time, and a query asks for WHERE ts >= '12:00' AND ts < '13:00'. The footer (7.6 KB for this file, versus 1.4 KB for the one-row-group file) lists each row group's ts range. Measured:

Two of ten row groups survive, and of those only the columns in the SELECT are fetched (column projection). If the query selects event_type and country, the reader fetches about 2/10 of their 1.1 MB plus the ts chunks needed to apply the filter exactly — perhaps 1.2 MB of a 15 MB file. The engine still applies the filter row by row inside the surviving row groups; statistics only tell it what it can safely ignore.

This is the most important practical fact about statistics: they describe the data, they do not organise it. Sort order is a choice the writer makes, and choosing it trades one column's pushdown and compression against another's. When the measured table was sorted by event_type and country, those two columns shrank to almost nothing, but ts grew from 4.58 MB to 5.61 MB and event_id from 4.28 MB to 4.89 MB (Snappy), the file as a whole grew from 15.1 MB to 15.6 MB, and the time filter above would no longer skip anything. de3 covers how to choose, and techniques such as Z-ordering that cluster on several columns at once.

10. ORC in one section

ORC (Optimized Row Columnar) came from the Hive project at about the same time as Parquet and has the same core ideas with different names. A file is divided into stripes (64 MB by default) instead of row groups; within each stripe, columns are stored as streams; every 10,000 rows (the row index stride) ORC records min/max and positions, giving page-like skipping built in; and the file and stripe footers hold metadata. ORC has rich encodings and optional Bloom filters, and the current ORC documentation lists zstd as the default codec. ORC remains strong in Hive- and Trino-heavy shops; Parquet won broader ecosystem support (Spark's default, pandas, Arrow, DuckDB, every warehouse's external tables, every table format), so new platforms usually standardise on Parquet.

11. The small-files problem

Everything above assumed reasonably large files. Real lakes often have the opposite. A streaming job that commits every minute, a Spark job with 2,000 tasks each writing its own file into each of 50 partitions, a pipeline that appends one file per incoming API call — each produces thousands or millions of small files. Each file carries fixed costs that do not shrink with its size:

  • Listing: object stores return at most 1,000 keys per list request (S3's ListObjectsV2 limit), so 1,000,000 files need 1,000 sequential-ish list calls before planning can even begin — unless a table format's metadata already lists them (de4).
  • Opening: at least one request to read the footer and one or more for data, each with tens of milliseconds of first-byte latency on object storage.
  • Scheduling: engines such as Spark create read tasks from files and byte ranges; with tiny files, task launch overhead (tens of milliseconds each) dominates. Spark mitigates this by packing small files together into one task, treating each file as costing an extra 4 MB (spark.sql.files.openCostInBytes) when packing up to 128 MB per task (spark.sql.files.maxPartitionBytes).
  • Worse files: a 1 MB Parquet file has one tiny row group, little for dictionaries and codecs to find, a footer proportionally large, and statistics that are fine-grained but must be read separately for each file.
  • Metadata: catalogs, table-format manifests and (on HDFS) the NameNode's memory all grow with file count.

Size it. One day of events, 100 GB after encoding. As 100,000 files of 1 MB, a full scan needs about 100 list calls, at least 200,000 GET requests (footer plus data per file), and — even at 200 concurrent requests and 30 ms each — about 30 seconds of pure request latency before counting any data transfer; Spark plans tens of thousands of tasks. As 800 files of 128 MB, it needs one list call, about 1,600 GETs plus ranged reads within files, and a few hundred tasks. The bytes read are the same; the overhead differs by two orders of magnitude. At the request price (S3 Standard GETs are fractions of a cent per thousand), the money is small; the time and the planning overhead are not.

The cures are on both sides. On write: buffer longer before committing, repartition or coalesce before writing so each task writes one file per output partition, and size output files deliberately (many writers have a target file size option). After write: compaction, a maintenance job that rewrites small files into large ones — safe only when a table format commits the swap atomically, which de3 and de4 build on. A common target is files of 128 MB to 1 GB, with row groups of 64–256 MB inside them so a large file still splits into parallel read tasks.

Why columnar plus vectorised reading is a CPU story, not just an I/O story

Bytes saved on disk are obvious; less obvious is that columnar files also make the CPU faster. When a reader decodes a page, it produces a batch of thousands of values of one type laid out contiguously in memory — the Apache Arrow in-memory format is the common target. The engine then runs tight loops over those arrays: compare every timestamp in the batch to the filter bound, producing a bitmap; sum every price where the bitmap is set. Such loops use SIMD instructions (one instruction operating on 4–16 values) and stay in the CPU cache. A row format forces the engine to walk record by record, branching on each field. This is why Spark's vectorized Parquet reader (on by default) and engines like DuckDB are so much faster than row-at-a-time readers even on cached data. It is also why dictionary-encoded columns can sometimes be filtered without decoding: compare the filter to the 8 dictionary entries once, then scan the 3-bit codes.

Statistics have sharp edges

Min/max statistics are only useful if the reader trusts them, and there have been real bugs. Early Parquet writers computed string min/max with signed byte comparison, which is wrong for non-ASCII UTF-8, so readers learned to ignore string statistics from old writer versions; Parquet later added a ColumnOrder field to the footer and new min_value/max_value fields with defined ordering. Long strings make statistics large, so writers truncate them (parquet-java's column-index truncate length is 64 bytes); a truncated max must be rounded up so it is still an upper bound. Floating-point NaN breaks ordering and is handled specially. The practical lesson: when a pushdown that should work does not, inspect the footer — statistics may be missing, truncated, or deliberately ignored for that writer version.

Choosing row-group and file sizes is a three-way trade

Row groups trade pushdown granularity, memory and parallelism. A row group is buffered in memory by the writer until it is flushed (so a 1 GB row group across 200 columns needs a lot of writer memory), is the finest unit a reader can skip with chunk statistics, and is typically the unit of parallel splitting when an engine divides one big file across tasks. Very large row groups give long sequential reads and good compression but coarse skipping and few splits; very small ones give fine skipping but many seeks and a large footer. The page index loosens the trade by allowing page-level skipping inside large row groups. For object storage, where each request costs tens of milliseconds, the practical sweet spot is files of hundreds of megabytes with row groups of roughly 64–256 MB; for a training data loader doing random access, smaller row groups (or a dedicated shard format, de12) are better.

Schema evolution at the file level, and why IDs beat names

Each Parquet file carries its own schema, so a table made of many files may contain several schema versions. Engines reconcile them by matching column names: a new nullable column reads as null in old files; a dropped column is ignored. Renames are the trap: if price is renamed to unit_price, old files have price and new ones unit_price, and a by-name reader sees two half-empty columns. Iceberg solves this by writing a numeric field ID into each Parquet column's schema and resolving by ID, so a rename is a metadata-only change and old files still map correctly. Type changes are harder: widening int to long can be read safely; anything else usually means rewriting data. Avro sidesteps much of this with explicit reader/writer schema resolution and aliases. This is one of the main reasons de4's table formats exist.

Formats for ML data are under pressure

Parquet was designed for analytical scans, and ML workloads stress it in new ways. Training tables can have thousands of feature columns, making footers megabytes long and metadata parsing a real cost. Embedding columns are fixed-length float vectors that compress poorly and are better stored as fixed-size lists with byte-stream split. Data loaders want random access to individual rows for shuffling, which row-group-oriented files serve badly. Newer formats such as Lance (built around fast random access and vector search) and research formats like Nimble (from Meta, aimed at very wide tables) target these needs; the common practical response is still Parquet with tuned row groups for preprocessing, then conversion into training shards (de12). It is worth knowing the pressures exist, and being able to explain them, rather than knowing every new format's name.

Encryption and integrity

Parquet supports modular encryption: the footer and individual columns can be encrypted with different keys, so a table can expose non-sensitive columns to everyone while only principals with the right key decrypt, say, an email column. Pages can also carry CRC checksums (pyarrow's write_page_checksum, off by default) to detect corruption. Both are worth knowing because ML feature tables frequently mix sensitive and non-sensitive columns, and silent corruption in a training set is otherwise invisible.

How file formats hurt in production

The JSON-forever bronze layer. Raw JSON is landed "temporarily" and never converted; analysts query it directly. Symptom: queries whose cost and runtime scale with total history, frequent parse failures, and type confusion (the same field as string in some files and number in others). Fix: convert to typed Parquet in silver with schema enforcement, and quarantine records that do not parse.

Small files from streaming and over-partitioned writes. Symptom: Spark jobs whose driver spends minutes planning, tens of thousands of tiny tasks each running for milliseconds, slow listings, a table-format metadata tree that keeps growing. Check file count and median file size per partition; a median under 32 MB is a red flag. Fix: coalesce or repartition before writing, longer trigger intervals, scheduled compaction.

Pushdown that silently stopped working. Symptom: a query that used to read a few gigabytes reads terabytes, after a writer change. Causes: a new writer that omits statistics, timestamps written as strings, a lost sort order, or a filter wrapped in a function (WHERE date(ts) = …) that the reader cannot push down. Check the query's "files read / bytes read" metrics and the footers of new files.

Precision and type drift. Timestamps written as INT96 (a legacy Impala/Hive encoding) by one writer and as INT64 microseconds by another; decimals written as doubles; integers that overflowed because a source widened its column. These show up as subtly wrong values in features, not as errors. Fix: pin types in the data contract and test new files against it.

Dictionary blow-up and memory. Writers buffering a whole row group of a very wide table can run out of memory; readers decoding large dictionaries for many columns at once can too. Symptom: writer OOM on wide feature tables. Fix: smaller row groups for wide tables, fewer columns per file, or splitting the table.

Tools and metrics

pyarrow.parquet.ParquetFile(path).metadata (used in the lab) and the parquet-cli tool from parquet-java print row groups, column chunk sizes, encodings, codecs and statistics. Query engines report files and bytes scanned per query — the single most useful number for spotting a format or layout problem. Track per table: file count, median and p10 file size, bytes per row, and compression ratio over time.

The case: Uber's file-format cost work (2022)

In "Cost Efficiency @ Scale in Big Data File Format" (Uber Engineering blog, 25 January 2022, by Xinli Shang, Zheng Shao and Mohammad Islam), Uber describes reducing storage in its Parquet-dominated lake by changing how files are written, not what they contain. Before the project, the lake mainly used gzip and Snappy. On their ten largest Hive tables with zstd at the default level 3, they measured about 7% less storage than gzip, about 39% less than Snappy, and about 79% less than uncompressed. Read cost did not suffer: in their query benchmarks zstd's vCore-seconds were close to Snappy's on a full scan and much lower on queries with shuffles, filters and aggregations, because less data was read and moved. Testing levels 1 to 22 on 65 one-gigabyte files, they found size gains flattened while write time kept rising, and chose level 19 only for one-off offline conversion of existing gzip data.

They also contributed tooling upstream: zstd support in parquet-java that no longer depended on Hadoop's native library (PARQUET-1866, in Parquet 1.12.0), a "trans-compression" command to recompress existing files without decoding the data (PARQUET-1949), and a column-pruning tool that copies files while skipping unused columns about 20 times faster than rewriting them with Spark (PARQUET-1800), after identifying unused columns from lineage and query audit logs. And they measured sort order: on one table with a UUID, a timestamp and latitude/longitude, sorting rows by UUID then time cut data size by 32%. Every idea in this lesson — codec choice, column removal, sort order — was worth petabytes at their scale.

Goal: write a real Parquet file and read its anatomy and statistics yourself. Uses pandas and pyarrow from C:\ra_projects\how-to-train-your-gpt\gpt_env (pyarrow 25); about 15 minutes.

  1. Build a table of 1,000,000 rows with NumPy: event_id as np.arange, ts as sorted random milliseconds within one day, user_id as random integers up to 200,000, event_type chosen from 8 strings with uneven probabilities, country from 50 codes. Convert with pa.table({...}).
  2. Write it three ways with pq.write_table: compression="none", "snappy" and "zstd"; also write it as CSV with pyarrow.csv.write_csv. Print os.path.getsize for each.
  3. Open the Snappy file with md = pq.ParquetFile(path).metadata. For each column, print md.row_group(0).column(i).encodings, total_uncompressed_size, total_compressed_size and the statistics min/max.
  4. Rewrite with row_group_size=100_000, print each row group's ts min and max, then read with pq.read_table(path, columns=["event_type"], filters=[("ts", ">=", t12), ("ts", "<", t13)]).
  5. Try next: shuffle the rows before writing (table.take(np.random.permutation(n))) and print the row-group ranges again.

What to look for. CSV should be roughly 3–4 times the Snappy file. event_type's encoded size should be close to 1,000,000 × 3 bits = 375 KB, and country's close to 750 KB — the bit-packing arithmetic made visible. event_id's encodings should list both RLE_DICTIONARY and PLAIN: the dictionary fallback. With 10 sorted row groups, each ts range covers about 2.4 hours, so the filter can skip eight of them; after shuffling, every range spans the whole day and nothing can be skipped.

Diagnose: the 40-minute feature query

A nightly feature job computes, for each user, purchase counts over the last 7 days from a table silver.events. The table is 90 days of Parquet in S3, 300 GB in total, partitioned by date (one folder per day). The query filters event_type = 'purchase' and the last 7 days. It used to take 4 minutes; it now takes 40. The Spark UI shows it reads all 7 partitions fully: 23 GB, 240,000 files, 240,000 tasks. A month ago an upstream team switched landing from hourly batches to a streaming job with a 10-second trigger. What happened, and what do you change?

Answer

Diagnosis. The date filter works (7 of 90 partitions), but inside each day there are now about 34,000 files (240,000 ÷ 7), averaging about 100 KB each (23 GB ÷ 240,000). That is the streaming job: one file per task per trigger. With 8,640 ten-second triggers a day and a handful of tasks per trigger, tens of thousands of files a day is exactly what to expect. The job is dominated by per-file overhead: listing, a footer read and a data read per file, and task scheduling — 240,000 tasks at even 10 ms of overhead each is 40 minutes of task time before any real work. The tiny files also kill pushdown: each holds a few seconds of mixed event types, so per-file statistics for event_type span many values, and every file must be opened just to learn that.

Fix in the short term. Compact each day into files of roughly 256 MB–1 GB: 23 GB ÷ 7 ≈ 3.3 GB per day becomes about 4–13 files per day. Sort within each compacted file by event_type then ts, so the purchase rows (about 2% of events) sit in a few row groups and the others are skipped from statistics. Run compaction daily (or hourly for the current day) as a maintenance job, and use a table format so the swap is atomic and readers never see duplicates.

Fix in the long term. Make the streaming writer coalesce its output (fewer tasks writing, a longer trigger such as one minute if freshness allows) and give the landing table a file-count and median-file-size check with an alert. Expected result: the 7-day read becomes about 30–90 files and, with sorting, reads well under 1 GB — back to a few minutes or less.
