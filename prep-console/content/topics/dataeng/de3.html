A B2B software company stores every customer "engagement" — an email opened, a link clicked — in a lake table, and wants each customer organisation's data to be easy to find and easy to delete. So it partitions the table by organisation and by day: one directory per org per date. It sounds tidy. But 90% of the organisations are small and produce a few thousand engagements a day — a few hundred kilobytes. Every org-day directory gets its own files, and those files are tiny: a sampled partition has 175 files of about 7 KB each. The table reaches more than four million files. Running a batch of 200,000 updates now takes over eight hours, because every update has to find, open and rewrite files across thousands of directories.

This is a real story, told by Salesforce engineering in 2020, and its punchline is that nothing was wrong with the data, the engine or the hardware. The table's layout — how rows were divided into directories and files and in what order — was wrong for the data's shape. The fix was a different layout: partition only by organisation, cluster the rows inside each partition by date, and keep files in a sensible size range. A batch of 25 million updates and deletes then finished in 15 minutes.

de2 showed that a single Parquet file can skip most of its bytes if its rows are well ordered. This lesson steps up a level to the whole table: how rows are divided into partitions, how they are ordered within files, how two tables can be laid out so a join needs no network shuffle, and how to keep the layout healthy as small writes keep arriving. For ML, layout decides whether a feature backfill over two years reads 2 TB or 200 TB, whether a training-set join runs in minutes or hours, and whether a GDPR deletion request is a quick rewrite or a week-long job.

You will learn Hive-style partitioning and pruning, how to choose partition columns with numbers for too many and too few partitions, how writers decide how many files they create, bucketing for joins, sort order and its effect on statistics, multi-column clustering with Z-order and Hilbert curves worked out by hand, and compaction — then the Salesforce case in detail.

The mental model: a library

A library with a million books has to decide how to arrange them. The first decision is which rooms to put books in: fiction in one room, science in another, history in a third. A reader looking for a chemistry book walks straight into the science room and ignores the rest of the building. That is partitioning, and walking past the other rooms is partition pruning.

The second decision is the order of books on the shelves within each room. If science books are shelved alphabetically by author, a reader looking for a particular author goes to one shelf; a reader looking for every book about chemistry must check every shelf. Shelve by subject instead and the chemistry reader goes to one bay, while the author search gets hard. That is sort order: whichever key you sort by gets fast lookups, and other keys do not.

Too many rooms is a real failure. If the library makes a separate room for every author, there are a hundred thousand rooms, most holding two books; readers spend their day opening doors. Too few rooms (one giant hall) means every reader searches everything. The useful middle is a few dozen rooms, each large enough to be worth having, with sensible shelving inside.

A clever librarian can also shelve by two things at once — not perfectly by either, but well enough by both — by grouping books into small blocks that are similar in subject and author. That is what Z-order and Hilbert clustering do with columns. And because new books arrive every day and get dropped on a returns trolley, someone has to periodically put them on the proper shelves, in order. That is compaction.

The analogy is imperfect in one important way: a library has one copy of each book, and moving books is cheap. A table's files are immutable, so "re-shelving" means rewriting files, which costs compute proportional to the data rewritten. Layout changes are therefore planned like small migrations, not done casually.

The levels of layout

From coarse to fine, a lake table's layout has four levels, and each one helps a different kind of query:

  1. Partitions — directories (or, in table formats, metadata groupings) by the value of a partition column such as date. Pruned by the planner before reading anything.
  2. Buckets (optional) — within a partition, a fixed number of files chosen by hashing a key. Used to join or aggregate without moving data.
  3. Files — each with per-column min/max statistics, either in its own footer or recorded in table-format metadata. Skipped by statistics when values are clustered.
  4. Row groups and pages inside files — the de2 level of skipping.

Keep this picture: partitions for the coarse filter everyone uses, ordering within partitions for the next most common filters, and file sizes kept healthy throughout.

1. Hive-style partitioning and how pruning works

The convention most engines understand comes from Apache Hive: a partitioned table is a directory whose subdirectories are named column=value. A table partitioned by date has date=2026-10-07/, date=2026-10-08/ and so on, each containing Parquet files. The partition column is usually not stored in the files; its value comes from the directory name. A table can have several partition columns, nested: date=2026-10-08/country=DE/.

When a query arrives, the planner looks at its filter. If the filter constrains a partition column — WHERE date = '2026-10-08', WHERE date BETWEEN '2026-10-01' AND '2026-10-07' — it computes which partition values can match and lists or looks up only those directories. This is partition pruning, and its saving is total: the excluded partitions cost nothing, not even a listing. A catalog such as the Hive Metastore or AWS Glue stores the list of partitions with their locations, so the planner can find them without listing the bucket at all.

Worked example. An events table holds three years of data at 300 GB of Parquet per day: 1,095 partitions, about 330 TB. A query for one day prunes 1,094 partitions and reads at most 300 GB — 0.09% of the table — before any file statistics are consulted. A query for the last 7 days reads 2.1 TB. A query with no date filter (say, "all purchases by user 553 ever") reads all 330 TB unless something else skips data; partitioning does nothing for it.

Pruning has pitfalls that come from the partition column living outside the data. If the table is partitioned by date but a query filters on the event timestamp — WHERE ts >= '2026-10-08 00:00' — the planner does not know that ts and date are related, and prunes nothing; users must remember to add the redundant date filter. If a writer derives date from ts in a local time zone while readers assume UTC, rows near midnight sit in the "wrong" partition and date filters silently drop them. Partition values are strings in directory names, so a filter like WHERE month = 3 against directories named month=03 can mismatch. And filters wrapped in functions (WHERE year(date) = 2026) may or may not be pushed into pruning depending on the engine.

Iceberg's hidden partitioning fixes the first two problems (de4 covers the metadata that makes it possible). The table declares its partitions as a transform of a real column — PARTITIONED BY (day(ts)) — and the writer computes the partition value itself. A query filtering on ts is translated into a partition filter automatically, users never see or fill a separate date column, and the transform is defined in UTC once, for everyone.

2. Choosing partition columns: too few, too many

A good partition column has three properties. It is used in the filters of most queries (otherwise pruning rarely happens). It has low cardinality at the chosen granularity (a few hundred to a few thousand values over the table's life, not millions). And it leaves each partition large: Delta Lake's best-practice guide says you can partition by a column if you expect each partition to hold at least 1 GB, and advises against high-cardinality columns such as a user ID. For event and fact tables, the answer is nearly always a date; very large tables use hour; small tables (under a terabyte or so) often do best with no partitions at all and good file statistics.

Now the arithmetic of getting it wrong.

Too many. The same 300 GB/day table partitioned by date, country (200 values) and event_type (20 values) has up to 4,000 partitions a day and 1.46 million a year. The average partition holds 75 MB — already smaller than one good file. But real data is skewed: if the top 5 countries carry 60% of traffic, the other 195 countries share 120 GB across 3,900 partitions, about 31 MB each, and the long tail of small country-and-event combinations holds a few kilobytes. Then the write makes it worse. A Spark job with 500 tasks, where each task holds a random slice of the day's events, writes one file for every partition it has rows for — potentially 500 × 4,000 = 2 million files a day, most of them a few kilobytes. Every query on this table pays for listing and opening them, and the planner and catalog choke on the metadata.

Too few. The same table with no partitions at all: 330 TB in about 650,000 files of 512 MB. A query for one day must, at minimum, examine every file's statistics. In a plain Hive-style table that means opening every footer — hundreds of thousands of requests. In an Iceberg or Delta table the per-file min/max are already in the metadata, so if the files are written roughly in time order, the planner can skip all but the ~600 files of the right day from metadata alone; this is why table formats make partitioning less critical. But if files mix days (because late data was appended or files were compacted without regard to time), nothing can be skipped.

The middle. Partition by date only: 1,095 partitions of 300 GB, about 600 files each of 512 MB. Then use ordering within each day (sections 5–7) for the second and third most common filters. That is the default design for large event tables, and you should need a reason to depart from it.

3. How writers create files, and how to control the count

To understand file counts you need one fact about distributed writers: in Spark (and most engines), the data is split across tasks — independent units of work that run in parallel — and each task writes its own output files. A task opens one file for each partition value it has rows for, and rolls over to a new file when one reaches a size or row limit. So:

files written ≈ Σ over tasks of (partitions that task touches), plus extra files when any one task's data for a partition exceeds the maximum file size.

If rows arrive at tasks randomly, every task touches every partition, and the count is tasks × partitions. Writing one day (one partition) with 500 tasks gives 500 files of 600 MB on average — fine. Writing 24 hourly partitions with the same 500 tasks gives 12,000 files of 25 MB — not fine. The cure is to repartition by the partition column before writing: a shuffle (moving rows between tasks over the network so that rows with the same key end up together; de5 explains shuffles in depth) that sends all rows of hour 0 to one set of tasks, hour 1 to another, and so on. In Spark this is df.repartition("hour").write.partitionBy("hour"), or setting a target number of tasks per partition; Iceberg's write.distribution-mode=hash asks the engine to do this automatically, and range distribution additionally sorts.

Repartitioning introduces its own risk: skew. If one hour holds 40% of the day (a promotion went live), the one task writing it takes 40% of the job's data and the job waits for it. Engines address this by splitting large partitions across several tasks (adaptive execution, de5), or you add a secondary key — repartition("hour", "bucket") — so each hour is spread over a few tasks, each producing a few large files.

A second write-time trap concerns overwrite. Spark's default static partition overwrite mode means that INSERT OVERWRITE into a partitioned table without a partition specification deletes all partitions and writes the new data — one missing WHERE clause and three years of data are gone. Dynamic mode (spark.sql.sources.partitionOverwriteMode=dynamic) replaces only the partitions present in the new data, which is what an idempotent daily job wants (de7 builds on this). Table formats add safer verbs: Delta's replaceWhere and Iceberg's overwrite-by-filter replace exactly the rows matching a predicate, atomically.

4. Bucketing: laying out two tables so a join needs no shuffle

Partitioning helps filters. Bucketing helps joins and aggregations. When two large tables are joined on user_id, the engine normally shuffles both so that rows with the same user_id land in the same task — moving terabytes over the network (de6 sizes this). Bucketing does that work once, at write time: each row's user_id is hashed and taken modulo a fixed number of buckets, say 512, and each bucket's rows are written to their own file (or set of files) within each partition. If the other table is bucketed the same way — same column, same number of buckets, same hash function — then rows in bucket 37 of one table can only match rows in bucket 37 of the other. The engine joins bucket 0 with bucket 0, bucket 1 with bucket 1, and so on, with no shuffle. A related name for this, used for Spark with table formats that expose their layout, is a storage-partitioned join.

Worked numbers. Joining a 2 TB events table to a 200 GB user-features table on user_id with a shuffle moves about 2.2 TB through the network and through each executor's local disks. If both are bucketed into 512 buckets, each of the 512 tasks reads about 4 GB of events and 400 MB of features from its own bucket files and joins them locally; nothing crosses the network. If this join runs every night for model training, that is 2.2 TB of shuffle avoided every night.

Bucketing's costs are rigidity and compatibility. The bucket count is fixed at write time; if the table grows 10× the buckets become 10× larger, and changing the count means rewriting everything. Every writer must use the same scheme, including incremental writers that append. And hash functions differ between systems: Hive's bucketing and Spark's built-in bucketing use different hashes, so a Spark job cannot assume a Hive-bucketed table's layout; Iceberg defines its bucket(N, col) transform precisely in its specification (a 32-bit Murmur3 hash), which is what lets different engines agree. Bucket on a key you join on repeatedly, choose the count for buckets of roughly hundreds of megabytes to a gigabyte, and keep counts that divide one another (256 and 512) so tables at different sizes can still line up.

5. Sort order within partitions

Inside a partition, the order in which rows are written decides the statistics of each file and row group — and de2 showed that statistics only help when values are clustered. Suppose a day's 300 GB is written as 600 files in random order. Every file contains every event_type and nearly the full range of user_id, so a filter on either skips nothing. Sort the day by event_type before writing, and each file holds one or two event types: a query for purchases (2% of events) reads about 12 files instead of 600. Sort by user_id instead, and each file holds a narrow range of user IDs: a lookup for one user reads one file.

A sort also improves compression, as de2 measured: sorted columns become long runs. But you can only sort by one thing first. Sorting by event_type, user_id gives perfect locality for event_type, good locality for user_id within each event type, and none for anything else — a lookup by user_id alone must now check one range in each of the 20 event-type groups, about 20 files instead of one. Every sort key is a decision about which queries get fast.

Sorting has a cost: a global sort of a 300 GB partition is a full shuffle (range-partition by the sort key, then sort within each task). That is why sorting is usually done once, in a compaction or "optimise" job after data has settled, rather than on every small incremental write.

6. Clustering on several columns: Z-order

What if queries filter by user_id about as often as by country, and a sort on either leaves the other unserved? A space-filling curve maps points in several dimensions to one sequence such that points near each other in all dimensions tend to be near each other in the sequence. Sorting rows by that sequence number clusters them in all dimensions at once — not as tightly as a dedicated sort would for any one, but well for each.

The simplest is the Z-order (or Morton) curve, computed by interleaving bits. Take two columns, each mapped to small integers (real implementations first map values to ranks or ranges). Let x be a user bucket from 0 to 3 and y a day from 0 to 3, each written in two bits: x = x1 x0, y = y1 y0. The Z-value interleaves them: z = y1 x1 y0 x0. So (x = 2, y = 1) is x = 10, y = 01, giving z = 0 1 1 0 = 6. Computing all sixteen cells gives the grid in the figure. Sorting by z and cutting the rows into four equal files gives files holding z = 0–3, 4–7, 8–11 and 12–15, and each of those is a 2×2 square.

Generalise: with a sort on one column, a filter on that column reads about 1/N of the files and a filter on another column reads all of them; with a two-column Z-order, a filter on either reads about 1/√N. With 600 files per day, that is 1 versus 600 for the sorted design and about 25 versus 25 for Z-order. If queries split evenly between the two columns, Z-order's average (25) beats the sort's average (about 300) by a wide margin. If 95% of queries filter on one column, the sort wins.

The weakness of Z-order is visible in the grid: the curve makes long jumps (from 3 to 4, or from 7 to 8, it leaps across the grid), so some consecutive z-values are far apart in space and some files cover awkward shapes when the cut points fall mid-square. A Hilbert curve is a different space-filling curve that also visits every cell but always steps to an adjacent cell, so it never jumps; files cut from a Hilbert ordering tend to be more compact regions and statistics tighter. Apache Hudi introduced both Z-order and Hilbert layout optimisation (its blog post from December 2021 explains the construction), and other systems use them too.

In practice you rarely compute curves yourself. Delta Lake offers OPTIMIZE table ZORDER BY (col1, col2); Iceberg's rewrite_data_files procedure accepts a sort order or a Z-order strategy; Delta's newer liquid clustering (from Delta 3.1, with up to four clustering columns, not combinable with partitioning or ZORDER) declares clustering keys on the table and applies them incrementally each time OPTIMIZE runs. Two rules hold everywhere: cluster only on columns that real queries filter on, and use as few as possible — two or three, not eight, because each additional column dilutes the locality of the others.

7. Compaction

Layouts decay. Every streaming micro-batch, every hourly append and every merge that rewrites a few rows adds new, usually small, files that are not in the sorted or clustered order. A table that was perfectly laid out on Monday has thousands of small, unsorted files by Friday. Compaction is the maintenance job that restores the layout.

There are two kinds. Bin-packing simply groups small files into output files near a target size without changing row order — cheap, fixes file counts, does not fix clustering. Sort or cluster compaction rewrites the data in the desired order (a sort or a Z-order), which fixes statistics too but costs a shuffle. A common pattern is bin-packing frequently (hourly, on recent partitions) and sorting or clustering less often (daily, once late data has stopped arriving for a partition).

Sizes and defaults vary by system, so check the version you run. As of Iceberg 1.12, the default write.target-file-size-bytes is 512 MB with 128 MB Parquet row groups; Salesforce's tests on Delta found 64–256 MB worked best for their merge-heavy workload against a 1 GB default for OPTIMIZE. The principle is stable: big enough that per-file overhead is negligible (hundreds of megabytes), small enough that a single file is not a straggler task and that rewrites for updates and deletes do not rewrite gigabytes to change one row.

Compaction must be atomic: readers must see either all the old small files or all the new large ones, never both (duplicates) or neither (missing data). On a plain Hive-style table there is no safe way to do this while readers are active, which is why plain lakes rarely compacted and accumulated small files. Table formats (de4) make compaction a single commit that removes the old files from the table and adds the new ones; readers on the old snapshot keep reading the old files until they finish, and the old files are deleted later by a cleanup job. They also detect conflicts: if a concurrent update touched the same files, the compaction commit fails and retries instead of resurrecting deleted rows.

8. A worked design

Put the pieces together for the event table used throughout: 300 GB of Parquet a day, landed by a streaming job every minute, queried in three ways — by date range for dashboards (most queries), by event_type within a date range for feature pipelines, and by user_id for debugging and per-user training examples.

  • Partitioning: by day of the event timestamp (Iceberg day(ts), or a date column in UTC if Hive-style). 365 partitions a year, 300 GB each.
  • Landing: the streaming writer coalesces to 8 tasks, producing about 8 files a minute — 11,520 small files a day of about 26 MB. Acceptable for a few hours.
  • Hourly bin-pack of the current day's new files into 512 MB files: about 600 files at the end of the day.
  • Daily cluster of each day once it is three days old (late data has settled): rewrite with a sort on event_type, user_id, or a Z-order on both if user lookups are frequent. Cost: rewriting 300 GB a day — a modest Spark job.
  • Bloom filters on user_id, so per-user lookups skip files and row groups even across event-type groups.

Result: a one-day dashboard query reads 600 files; a purchases-in-the-last-week feature query reads about 7 × 12 = 84 files; a debugging lookup for one user over a week reads at most about 7 × 20 file ranges, and Bloom filters cut that further. Without the clustering step, the last two would read 4,200 files each.

File-level statistics make partitioning less central

In a plain Hive-style lake, partitions were the only skipping mechanism that worked before opening files, because file statistics lived in each file's footer and reading them meant opening the file. Table formats move per-file statistics (min, max, null counts per column) into their metadata, so the planner can skip files from metadata alone. This changes the design calculus: a table with no partitions but well-clustered files can prune as well as a partitioned one, without the risk of over-partitioning. It is why Delta's liquid clustering explicitly replaces partitioning for many tables, and why a common modern recommendation is to partition only very large tables, and only by a coarse time column. Partitions still matter for operations — retention ("drop data older than two years" is a cheap metadata delete of whole partitions), GDPR rewrites scoped to a partition, and concurrency, because writers touching different partitions rarely conflict.

Clustering columns should come from query logs, not intuition

The right sort or clustering keys are an empirical question: which predicates appear in the queries that cost the most? Most engines record per-query predicates and bytes scanned, and table formats record files read. A useful exercise is to rank columns by the scan bytes of queries that filter on them; the top one or two are the clustering keys. Uber's file-format post (de2) used query audit logs the same way to find columns nobody read. Re-check periodically, because workloads drift: a new ML feature pipeline that filters by merchant_id may make yesterday's layout wrong.

The mapping step before the curve

Z-order needs small integers, but real columns are strings, timestamps and 64-bit IDs with skewed distributions. Interleaving the raw bits of a timestamp and a user ID would let the high-order bits of the timestamp dominate. Implementations therefore first map each column to a rank or range bucket — for example by sampling the data to find quantiles and replacing each value by its quantile index — so each dimension contributes evenly. Skew still bites: if 30% of rows share one country, the quantile mapping cannot spread them, and files will hold that country's rows across a range of user IDs. This is a reason to check file-level statistics after clustering instead of assuming it worked.

Write amplification: the hidden price of layout

Every layout rewrite reads and writes data that has not changed. If a day's partition is bin-packed every hour for 24 hours, then clustered once, each byte may be written three or four times before it settles — write amplification, the same concept db5 introduced for LSM-tree storage engines. For large tables this is real compute money. Ways to reduce it: compact only partitions that crossed a small-file threshold, avoid re-compacting files already above target size, use incremental clustering (only rewrite unclustered files, as liquid clustering does), and leave the hot current partition with more small files while it is still changing.

Partitioning for streaming and for deletes

Streaming writes favour a time partition matching the commit granularity, so each micro-batch touches one or two partitions and concurrent compaction rarely conflicts with the writer. Delete-heavy workloads — GDPR erasure, the Salesforce update-heavy table — favour layouts where a delete touches few files: clustering by the deletion key (customer or organisation ID) so one customer's rows sit in a few files. There is a direct tension with time-based clustering, which spreads one customer across every day's files. Teams resolve it by choosing the primary access pattern, or by keeping deletion vectors (de4) so a delete marks rows instead of rewriting files and the rewrite is batched.

Layout for ML training reads

Training jobs read differently from analytics: they read many columns, often whole partitions, sometimes in random order. Partition pruning still matters (train on the last 90 days), but column statistics matter less, and file sizes matter more — a data loader with 64 workers wants at least that many files of reasonable size to parallelise over, and wants files whose row order is not correlated with the label (a file sorted by event_type feeds the model all clicks then all purchases unless the loader shuffles across files). de12 builds training shards for this; the layout lesson here is that a table optimised for analytical filters may need a different, shuffled export for training.

Granularity should follow the data, and can change

A table's right partition granularity changes as it grows. A new product's events at 2 GB a day are best unpartitioned or partitioned by month; at 300 GB a day, by day; at 10 TB a day, by hour. In a Hive-style table, changing granularity means rewriting everything, so teams over-partition early "for the future" and suffer small files for years. Iceberg's partition evolution removes that pressure: changing month(ts) to day(ts) is a metadata change, new data is written with the new spec, old files keep the old one, and the planner prunes each set with its own spec. The design lesson is to choose the granularity that is right for today's volume and plan to evolve it, rather than guessing at the size the table will be in three years.

Failure modes and their symptoms

Over-partitioning. Planning takes minutes; the catalog or metastore is slow; file counts per day in the hundreds of thousands; median file size in kilobytes. Usually caused by a second or third partition column with a long tail, or a high-cardinality partition column added "for convenience". Fix: drop to a single coarse partition column, cluster on the rest, compact.

Pruning silently lost. A query that scanned one day starts scanning everything. Causes: a filter on a different column than the partition column, a function wrapping the partition column, a type mismatch (string versus date), or a view that strips the predicate. Check the physical plan for partition filters and the bytes-scanned metric.

Accidental full overwrite. Static overwrite mode and a missing partition clause replace the entire table. Defence: dynamic overwrite mode by default, overwrite-by-filter in table formats, row-count checks after each write (a daily job that suddenly writes 1% of the usual rows, or deletes 99%, should fail loudly), and snapshot retention long enough to roll back.

Skewed write tasks. Repartitioning by date makes one task write a whole hot day; the job's last task runs for an hour. Fix: add a secondary distribution key or let adaptive execution split skewed partitions.

Compaction conflicts and runaway cost. Compaction collides with streaming writers or merges and fails repeatedly, or rewrites the same large files every run. Fix: compact partitions the writer no longer touches, filter candidate files by size, and watch compaction compute as its own cost line.

What to watch

Per table and partition: file count, median and 10th-percentile file size, rows per file, and the ratio of bytes scanned to bytes returned for the main queries. Per query: partitions and files scanned versus total. Per maintenance job: bytes rewritten per run (write amplification) and commit conflicts.

The case: Salesforce's engagement table (October 2020)

Salesforce's engineering blog post "Boost Delta Lake Performance with Data Skipping and Z-Order" (Michael Zhang, 20 October 2020) describes a Delta Lake table of email and web engagements for many customer organisations, with heavy update and delete traffic (engagements are mutated after the fact). The table was first partitioned by OrgId and EngagementDate, giving S3 paths like {orgId}/{EngagementDate}/{file}.parquet. Their traffic model explains what went wrong: engagements per organisation per day ranged from about 2,800 for a small org to nearly 2 million for the largest, at roughly 150 bytes each, so daily data per org ranged from about 422 KB to 295 MB — and around 90% of orgs were small, giving partitions under 500 KB. The table had over 4 million files; a sampled partition held 175 files of about 7 KB.

Running Delta's OPTIMIZE brought the count to about 135,000 files, but small files came back to over 3 million as writes continued — compaction alone could not fix a scheme whose partitions were inherently tiny. The redesign partitioned by OrgId only and Z-ordered by EngagementDate inside each org, relying on Delta's per-file statistics (collected by default on the first 32 columns) for date skipping. They benchmarked maximum file sizes from 4 MB to 1 GB, 14 runs each, on a dataset of 4,830 orgs and 1.5 billion engagements with 5.4 million mutation requests, and found 64, 128 or 256 MB best for their workload, versus Delta's 1 GB default for OPTIMIZE output. The result: the original design took over 8 hours for a batch of 200,000 mutations; the final design processed 25 million updates and deletes in 15 minutes, against a goal of 10 million per hour. (The two batch sizes differ, so this is not a like-for-like speedup, but the direction is unambiguous.)

Three lessons carry over. Partition columns must be judged against the distribution of data per partition, not the average — the long tail of small orgs made the scheme fail. Compaction cannot rescue a layout whose natural partition size is far below a good file size. And the best file size depends on the workload: merge-heavy tables prefer smaller files than scan-heavy ones, because every update rewrites whole files.

What to look for. out_date should have 7 files (one per day); out_many up to 7 × 50 × 8 = 2,800, with a median size a few percent of out_date's and the smallest only a few kilobytes — the long tail of rare countries. The filtered fragment list should contain one fragment instead of seven: pruning happened from directory names alone, before any file was opened. After sorting, each row group's event_type min and max should be equal or adjacent, which is what lets a filter skip row groups.

Design: lay out a training-features table

An ML platform keeps a user_daily_features table: one row per user per day, 50 million users, 400 feature columns, about 2 KB per row in Parquet — so about 100 GB a day, kept for two years. Access patterns: (a) the nightly training-set builder reads the last 90 days for a random 10% sample of users; (b) a debugging tool fetches all days for one user; (c) a GDPR job deletes all rows for a list of a few thousand users each week. The current table is partitioned by date and user_id % 1000. Critique it and propose a layout, with numbers.

Answer

Critique. date × 1,000 buckets-as-partitions gives 1,000 partitions a day and 730,000 over two years. Each holds 100 MB a day — smaller than ideal but not tiny. The real problems are elsewhere: the training read (a) touches every one of the 1,000 partitions for each of 90 days, i.e. 90,000 directories, and reads all of them in full because a 10% user sample has members in every bucket; the debugging read (b) prunes to one bucket but still visits 730 daily partitions; the GDPR job (c) touches a few thousand users spread over all 1,000 buckets and every day — it rewrites nearly every file in the table every week.

Proposal. Partition by date only (730 partitions of 100 GB, ~200 files of 512 MB each). Within each day, sort by user_id so each file covers a narrow ID range; enable file-level statistics in a table format and Bloom filters on user_id. Make the training sample deterministic on a hash of user_id (e.g. hash(user_id) % 10 = 0) so it is stable across days and reproducible.

Effect. (a) Training still reads 90 days and, for a 10% sample spread across ID ranges, most files — column projection matters more here than skipping, so read only the needed feature columns. If the training job always uses the same sample, consider bucketing by hash(user_id) % 10 as a single extra partition level (10 buckets, 10 GB each — large enough) so the sample reads one-tenth of the data. (b) Debugging prunes nothing on date but skips by statistics to one file per day: 730 small ranged reads. (c) GDPR deletes: with Iceberg or Delta, use merge-on-read deletes or deletion vectors so the weekly job writes small delete files or marks rows instead of rewriting, and run a monthly compaction that applies them. Each user now lives in one file per day, but a few thousand random user IDs still land in most of each day's ~200 files, so a copy-on-write delete would rewrite nearly the whole table every week; deletion vectors or merge-on-read are what make the weekly job cheap, and the monthly compaction pays the rewrite once.
