It is 02:00 and the nightly job that refreshes silver.orders is halfway through. It has deleted yesterday's Parquet files from the table's folder and written 300 of the 600 new ones when its executor is pre-empted and the job dies. At 02:05 the feature pipeline starts and reads the folder: it sees half a day of orders and builds features from them. At 02:30 the retried job runs again and writes all 600 files — but the 300 from the failed attempt are still there, so the folder now holds 900 files and every order from that half-day appears twice. Nobody notices until a week later, when a model trained on those features has learned that Tuesday nights are unusually busy.

That is life with a plain data lake. A table is "whatever files are in the folder", and changing it means adding and deleting files one at a time. There is no way to make several file changes appear at once (atomicity), no way to stop a reader seeing a half-finished change (isolation), no record of what the table looked like yesterday, no way to change one row without rewriting files by hand, and no safe way for two jobs to write at the same time. Engineers worked around it with conventions — write to a temporary folder and rename it; never read during the batch window; keep a "_SUCCESS" marker file — but object storage has no atomic folder rename, and conventions break under retries, concurrency and human error. Databricks' Delta Lake paper reports that in the first years of its cloud service, around half of support escalations were caused by exactly these corruption, consistency and performance problems.

Table formats — Apache Iceberg, Delta Lake and Apache Hudi — fix this with one idea: keep a small, versioned record of exactly which files form the table, and change the table by atomically installing a new version of that record. Everything a lakehouse offers — transactions, time travel, updates and deletes, schema evolution, safe compaction, fast planning over millions of files — follows from it.

This lesson builds the idea from scratch: the metadata structures of Iceberg (a tree) and Delta (a log), with a nod to Hudi (a timeline); how a commit is made atomic on storage that has no transactions; how concurrent writers are reconciled; how updates and deletes work with copy-on-write, merge-on-read and deletion vectors; time travel; schema and partition evolution; catalogs; and the maintenance jobs without which a table slowly rots. Versions and defaults are checked against Iceberg 1.12 (spec v3), Delta Lake 4.4 and Hudi 1.2 as of October 2026.

The mental model: a ledger of files

Imagine a warehouse full of sealed boxes. Boxes are never opened or changed once sealed (Parquet files are immutable). The warehouse's inventory is not "whatever is on the shelves" — new boxes are placed on shelves all the time, some are being thrown out, some were left by workers who went home mid-task. Instead, the warehouse keeps a ledger: page 1 says "the inventory is boxes A and B"; page 2 says "add C"; page 3 says "remove B, add B′ (a corrected copy)". To know the inventory, you read the ledger, not the shelves. A box on the shelf that the ledger does not mention does not exist as far as anyone is concerned.

Now the guarantees fall out. Atomicity: a change becomes real only when its ledger page is written, and a page is written in one go — before that, any new boxes on the shelves are invisible. Isolation: a reader who opened the ledger at page 2 keeps using page 2 even while page 3 is written, so they see a consistent inventory. Time travel: to know the inventory last Tuesday, read the ledger up to the page written last Tuesday — as long as the boxes it lists have not been thrown out yet. Updates: to "change" a box, seal a corrected copy and write a page that swaps them. And concurrency: if two clerks both try to write page 4, only one can succeed; the other must re-read page 4 and decide whether their change still makes sense on top of it.

Where the analogy breaks: a real ledger is one book, but a table's ledger can itself become large (millions of files, thousands of versions), so the formats need tricks — summaries, checkpoints, a tree of smaller ledgers — to keep reading it fast. And the "only one clerk can write page 4" rule must be enforced by something; on object storage that is the hardest part, and it is where Iceberg, Delta and Hudi differ most.

Three formats, one idea

Apache Iceberg (created at Netflix, now an Apache project) organises the ledger as a tree: a top metadata file points to a list of snapshots; each snapshot points to a manifest list; each manifest list points to manifests; each manifest lists data files with their statistics. A catalog holds the pointer to the current top file. Delta Lake (created at Databricks, now a Linux Foundation project) organises it as a log: numbered JSON files in a _delta_log folder, each listing files added and removed, with periodic Parquet checkpoints summarising everything so far. Apache Hudi (created at Uber, the Gen-3 platform in de1) organises it as a timeline of actions in a .hoodie folder, with a strong focus on record-level upserts.

Hold on to two sentences: the table is the metadata, not the folder; and a commit is one atomic step that installs a new version of the metadata.

1. Iceberg's metadata, level by level

Start at the bottom. Data files are ordinary Parquet (or ORC or Avro) files, written once and never modified. Iceberg writes a numeric field ID for every column into each Parquet file's schema, which matters for evolution (section 7).

A manifest is an Avro file listing a set of data files. For each file it records the path, the file format, the partition values, the record count, the file size and per-column statistics: value counts, null counts, and lower and upper bounds. By default in Iceberg 1.12, statistics are collected for the first 100 columns, with string bounds truncated to 16 characters (write.metadata.metrics.default is truncate(16)). A manifest can also list delete files (section 5). Each entry has a status — added, existing or deleted — and the sequence number of the commit that added it.

A manifest list is an Avro file, one per snapshot, listing that snapshot's manifests. For each manifest it records the path, how many files it adds or deletes, and a partition summary: for each partition field, the lower and upper bound of the values the manifest covers. This is what lets a planner skip whole manifests: if a manifest's dates range from October 1st to 4th, a query for October 7th never opens it.

A snapshot is the state of the table after one commit: an ID, a parent snapshot ID, a timestamp, a sequence number, the operation (append, overwrite, delete, replace), a summary (files added, rows added) and the path of its manifest list.

The table metadata file is a JSON file at the top: the table's UUID and location, the format version, all schemas the table has had and the current one, all partition specs and the default one, sort orders, properties, the list of snapshots and the current snapshot ID, plus a log of previous metadata files. Each commit writes a new metadata file (00003-….metadata.json); the old ones remain, and Iceberg keeps track of up to 100 previous ones by default.

The catalog holds, for each table name, the location of the current metadata file. It is the one mutable thing in the whole design.

Planning a query walks down this tree. For SELECT … WHERE date = '2026-10-07': ask the catalog for the current metadata file; read it and find the current snapshot; read its manifest list; skip manifests whose partition summary excludes October 7th; read the remaining manifests; skip data files whose partition value or column bounds exclude the filter; hand the surviving files (with their sizes, for splitting into tasks) to the engine. No directory is ever listed. The Iceberg specification states the goal directly: planning should take O(1) remote calls in the size of the table, not a number that grows with partitions or files.

2. Delta's transaction log

Delta Lake keeps its metadata in a _delta_log directory inside the table directory. Each commit is a JSON file named with the version number zero-padded to 20 digits: 00000000000000000000.json for version 0, …01.json for version 1, and so on. Each file holds one JSON action per line: add (a data file joins the table, with its size, partition values and statistics — record count, per-column min, max and null counts), remove (a data file leaves, with a deletion timestamp), metaData (schema, partition columns, properties), protocol (the minimum reader and writer versions and the table features a client must support), txn (an application's progress marker, section 9) and commitInfo (who did what).

The state of the table at version v is obtained by replaying actions from version 0 to v: the set of files that were added and not later removed, plus the latest metadata and protocol. Replaying ten thousand JSON files would be slow, so writers periodically write a checkpoint: a Parquet file (…10.checkpoint.parquet) containing the complete reconciled state at that version. The Delta paper says its clients write checkpoints every 10 transactions by default. A small _last_checkpoint file points to the most recent checkpoint so readers do not have to list the log directory. Reading the table is then: read _last_checkpoint; read that checkpoint (a columnar file, so even millions of file entries load quickly and can be filtered by their statistics); list and replay the few JSON commits after it.

The protocol has evolved through table features: instead of bumping a single version number for every new capability, a table declares which features it uses (deletionVectors, columnMapping, rowTracking, v2Checkpoint and so on), and a client must support all of them to read or write it. A recent addition, catalog-managed tables, makes a catalog the source of truth for which commits succeeded, moving Delta closer to Iceberg's catalog-centred design.

3. Hudi's timeline, briefly

Apache Hudi keeps a timeline in the table's .hoodie directory: an ordered record of actions such as commits, delta commits, compactions, cleans and rollbacks, each with a state (requested, in-flight, completed). Data is organised into file groups, each identified by an ID and holding all versions of a set of records; a record key maps to exactly one file group through Hudi's index. That record-level indexing is Hudi's distinctive strength: an upsert of a million changed rows can find which file groups hold those keys without scanning the table, which is why Uber built it for CDC ingestion. Hudi offers copy-on-write and merge-on-read table types (section 5) and runs table services — compaction, clustering, cleaning — often inline with the writer. Hudi 1.x reworked the timeline (an LSM-tree-based archived timeline) and added non-blocking concurrency control; the rest of this lesson uses Iceberg and Delta for detail because their metadata models are simpler to trace, but the ideas transfer.

4. Atomic commits and optimistic concurrency

Every format commits the same way: do all the work invisibly, then make it visible in one atomic step.

For an Iceberg append: (1) write new Parquet data files; (2) write a new manifest listing them; (3) write a new manifest list containing the new manifest plus the existing manifests of the base snapshot; (4) write a new metadata file adding the new snapshot and making it current; (5) ask the catalog to change the table's pointer from the base metadata file to the new one, only if the pointer still points to the base. Step 5 is a compare-and-swap (CAS). Steps 1–4 write only new files that nothing references, so a crash in the middle leaves the table untouched (and some orphan files to clean up later). The specification describes this precisely: "An atomic swap of one table metadata file for another provides the basis for serializable isolation." How the catalog implements the swap varies — a lock in the Hive Metastore, a conditional update in a database for JDBC catalogs, a versioned update in AWS Glue, a server-side check in a REST catalog — but the contract is the same.

For a Delta commit: (1) write new data files; (2) write the next log entry, version r+1, only if no other writer has written it. The Delta paper describes how this mutual exclusion was achieved on each store: atomic put-if-absent on Google Cloud Storage and Azure Blob Storage, atomic rename on HDFS and Azure Data Lake Storage, and — because S3 at the time had neither — a separate lightweight coordination service in Databricks deployments (open-source Delta offered a DynamoDB-backed log store for multi-cluster writes to S3). Amazon S3 added conditional writes (a PUT with If-None-Match that fails if the object exists) in August 2024, which gives object stores a native put-if-absent; whether a given Delta or Iceberg version uses it depends on the version and configuration, so check the docs for yours.

What happens when two writers race? Both read the same base version, both do their work, both try to commit. One wins. The loser's CAS or put-if-absent fails. It does not give up immediately: it reads what the winner committed and asks whether its own change conflicts. Two appends of new files never conflict — the loser simply rebuilds its metadata on top of the winner's snapshot (in Iceberg, a new manifest list containing both sets of manifests) and tries again. A compaction that rewrote files A and B conflicts with a winner that deleted rows from file A, because committing the compaction would resurrect those rows; it must fail and be redone. Iceberg's spec phrases it as: a change that rewrites files can be re-applied to a new snapshot if all of the rewritten files are still in the table. This is optimistic concurrency: no locks are held while working, conflicts are detected at commit, and retries are cheap when conflicts are rare. Iceberg 1.12 retries a commit 4 times by default, starting with a 100 ms wait.

The design has a limit worth stating: it serialises commits per table. It works beautifully for tens or hundreds of large commits per hour; a thousand small commits per second would spend all their time retrying. That is why streaming writers commit per micro-batch, not per event, and why "lakehouse as OLTP database" is a misuse.

5. Updates and deletes: copy-on-write, merge-on-read, deletion vectors

Data files are immutable, so how do you delete user 553's rows or apply yesterday's CDC updates? There are two strategies.

Copy-on-write (CoW). Find every data file containing a row to change; write a new version of each file with the rows removed or updated; commit a snapshot that removes the old files and adds the new ones. Readers see ordinary data files and pay nothing. Writers pay a lot: to delete 1 row from a 512 MB file, they rewrite 512 MB. If a day's CDC touches 1% of rows spread randomly across 600 files, it touches nearly all 600 files, and CoW rewrites the whole 300 GB partition to change 3 GB. Iceberg 1.12 uses CoW by default for deletes, updates and merges (write.delete.mode, write.update.mode, write.merge.mode all default to copy-on-write).

Merge-on-read (MoR). Leave the old data files alone. Write the changes separately — new rows in new data files, and a record of which old rows are gone — and have readers combine them. Iceberg spec v2 introduced two kinds of delete files: position deletes (this file, row positions 17, 4,022, 90,113) and equality deletes (any row where user_id = 553). Iceberg spec v3 adds binary deletion vectors: a compact bitmap per data file marking deleted positions, stored in Iceberg's Puffin format; Delta Lake has had deletion vectors as a table feature for several versions, attached directly to the file's add action in the log. Writes become small — a CDC batch writes its new rows plus a few kilobytes of deletion bitmaps — but every reader must load the deletes for each data file and filter them out, so reads slow down as deletes accumulate, until a compaction rewrites the affected files with the deletes applied.

Iceberg uses sequence numbers to make MoR correct: every commit gets the next sequence number, and a delete file applies only to data files with a lower (or, for position deletes, equal) sequence number. That way a delete of "user 553" committed at sequence 40 does not delete a new row for user 553 inserted at sequence 41. Equality deletes, flexible for streaming upserts, are expensive for readers because every data file must be checked against every applicable equality predicate; the in-development spec v4 no longer allows writing new equality deletes.

Hudi expresses the same choice as table types: a copy-on-write table rewrites base files; a merge-on-read table appends changes to row-based log files next to each columnar base file and compacts them later.

6. Time travel

Because old snapshots and their files are kept until expired, any engine can read the table as it was: in Spark SQL, SELECT * FROM prod.events VERSION AS OF 8172634 or TIMESTAMP AS OF '2026-10-01 00:00:00' for Iceberg and Delta alike (syntax varies slightly by engine). The engine just starts the planning walk from an older snapshot (Iceberg) or replays the log to an older version (Delta). Iceberg also has branches and tags — named references to snapshots, with their own retention — so you can tag the snapshot a model was trained on (model-v17-train) and keep it past normal expiry, or write to a branch to validate changes before publishing them to main.

For ML this is the cheapest reproducibility tool there is. Record, alongside each trained model, the snapshot ID of every input table; months later you can rebuild exactly the same training set, compare it with today's, or explain to an auditor what the model saw. The limit is retention: snapshot expiry deletes the files behind old snapshots. In Iceberg 1.12, history.expire.max-snapshot-age-ms defaults to 5 days for the expire operation; in Delta, VACUUM deletes unreferenced files older than 7 days by default. Long-term reproducibility therefore needs tags with explicit retention, or a copy of the training set itself (de12).

7. Schema evolution and partition evolution

A table's schema changes over its life. Iceberg makes most changes metadata-only by tracking columns by field ID, not by name. Every column gets a unique ID when created; data files store values under those IDs. Then:

  • Add a column: new ID, new schema; old files have no such ID, so readers return null (or, in spec v3, a declared default value).
  • Drop a column: remove the ID from the current schema; old files still contain the data but no reader asks for it.
  • Rename: change the name attached to the ID; files are untouched and still map correctly.
  • Reorder: change the order in the schema; nothing else.
  • Widen a type: safe promotions such as int to long or float to double are allowed; other type changes are not, because old files cannot be reinterpreted.

Contrast with name-based matching in plain Parquet (de2): a rename there splits a column into two half-empty ones, and dropping a column then re-adding one with the same name would resurrect old values. Delta originally matched by name; its columnMapping table feature adds ID- or name-based physical mapping so renames and drops become metadata-only too.

Partition evolution is Iceberg's equivalent for layout. Because partitions are transforms recorded in metadata (de3's hidden partitioning), you can change the spec — from month(ts) to day(ts), say — and only new data is written with the new spec. Each data file records which spec it was written with, and the planner prunes each group of files with its own spec. No rewrite, and old queries keep working.

8. Catalogs

The catalog is the entry point and the commit arbiter. For Iceberg it is mandatory (it holds the pointer); common choices are the Hive Metastore, AWS Glue, a JDBC database, Nessie, and implementations of the Iceberg REST catalog protocol, an open HTTP API that lets any engine talk to any compliant catalog (Apache Polaris, Unity Catalog, and catalogs built into cloud warehouses implement it). Delta tables are self-describing — the log in the table directory is the source of truth — but are usually registered in a catalog for names and access control, and catalog-managed Delta tables make the catalog the commit authority. In practice, the catalog is also where governance lives: who can read which table, which columns are masked, which credentials an engine gets for a table's storage. Choosing a catalog is as much an organisational decision as a technical one, because it decides which engines can see and write which tables.

9. Streaming writes and exactly-once

A streaming job that writes micro-batches into a table must not duplicate a batch after a crash. Delta's txn action solves this cleanly: the writer commits each batch's files together with an application ID and batch version in the same atomic log entry. On restart it reads the last committed version for its application ID from the log and skips any batch already committed. Iceberg writers achieve the same by storing the streaming source's progress (for example the last committed batch ID or Kafka offsets) in the snapshot summary and checking it on restart. The principle — commit the output and the progress marker atomically together — returns in de9.

10. A worked trace

Follow an Iceberg table prod.orders through four commits.

  1. Create: metadata v1.json, schema with field IDs 1 (order_id), 2 (user_id), 3 (amount), 4 (ts); partition spec day(ts); no snapshots. Catalog → v1.json.
  2. Append (S1): two data files, A (Oct 7) and B (Oct 8), 1 million rows each. New manifest m1 lists A and B with bounds; manifest list L1 lists m1; v2.json adds S1. Catalog CAS v1 → v2.
  3. Append (S2): file C (Oct 8, late arrivals, 50,000 rows). Manifest m2 lists C; manifest list L2 lists m1 and m2 — m1 is reused, not copied. v3.json. Catalog v2 → v3.
  4. Delete WHERE user_id = 553 (S3), merge-on-read: 12 matching rows found in A and C. Write a deletion vector for A (positions of its 9 rows) and one for C (3 rows); manifest m3 lists them; L3 lists m1, m2, m3; v4.json. Catalog v3 → v4.

Now a query at S3 reads A (skipping 9 rows), B and C (skipping 3 rows). A query VERSION AS OF S1 reads only A and B with no deletes. If a compaction later rewrites A and C with the deletes applied into A′, it commits S4 removing A, C and both deletion vectors and adding A′. Files A and C remain in storage, reachable from S1–S3, until expire_snapshots removes those snapshots; then A, C, the deletion vectors and the unreferenced manifests are deleted. Only at that moment is user 553's data physically gone.

11. Maintenance

Every table format needs regular housekeeping, and the jobs are similar across formats:

  • Compaction — rewrite small data files and fold in delete files or deletion vectors (Iceberg rewrite_data_files, Delta OPTIMIZE, Hudi compaction and clustering). de3 covered why.
  • Snapshot expiry / VACUUM — remove old snapshots from metadata and delete files no longer referenced by any retained snapshot (Iceberg expire_snapshots, Delta VACUUM, Hudi cleaning). Bounds storage growth and is required for deletes to be physical.
  • Orphan-file removal — delete files in the table location that no snapshot ever referenced, left behind by failed writes (Iceberg remove_orphan_files; Delta's VACUUM covers them). Must use a safety margin (files younger than a few days might belong to an in-progress write).
  • Metadata upkeep — Iceberg rewrite_manifests to merge many small manifests and cluster them by partition so planning prunes well; Delta checkpoints and log cleanup (log entries older than the log retention period, 30 days by default, are removed after a checkpoint covers them).

Skip these and the table rots in predictable ways: planning slows as manifests or log entries pile up, reads slow as small files and deletes accumulate, storage bills grow because every version of every file is kept, and "deleted" personal data stays on disk.

Why Iceberg chose a tree and Delta a log

Delta's log is the simplest possible design: append one file per commit, summarise periodically. Its weakness is that every reader must load the full current file list (from the checkpoint plus recent commits) before pruning — for a table with tens of millions of files that is a big checkpoint, though columnar and parallelisable. Iceberg's tree makes reuse explicit: an append writes one new manifest and a new manifest list that points to all the old manifests, so commit cost is proportional to the change, and planning reads only the manifests whose partition summaries match. The cost is more small files in the metadata layer and the need for manifest rewriting. Delta has moved towards the tree in practice — V2 checkpoints with sidecar files split the checkpoint into pieces — and Iceberg v4 restructures metadata again for performance. The deep point is that both are trying to make "which files are in the table, and which can I skip" cheap at billions of rows and millions of files, with different defaults for how much work happens at commit versus at read.

Isolation levels: serializable versus snapshot

Both formats give readers snapshot isolation. For writers, the strength depends on what is validated at commit. Iceberg lets an operation choose: a serializable delete checks that no conflicting data was added in matching partitions since its base snapshot (so a concurrent append of user 553's new row would make the delete fail), while snapshot isolation only checks that the files it rewrote were not changed. Delta offers WriteSerializable (the default — it lets blind appends proceed concurrently with other operations) and Serializable. The practical effect: with weaker isolation, more operations commit concurrently without retries, and in rare cases the result is not equivalent to any serial order — the classic write-skew anomaly (db9). For most pipelines, append-heavy workloads at the default level are right; for jobs whose correctness depends on "no new matching rows appeared while I worked", ask for serializable.

Row lineage and change feeds

Downstream incremental processing needs to know which rows changed between two snapshots. Delta's change data feed writes explicit change files (cdc actions) recording inserted, updated (pre- and post-image) and deleted rows, so a consumer can read "changes since version 812". Iceberg can compute appended files between snapshots cheaply (incremental reads of appends), and spec v3 adds row lineage — a stable row ID and the sequence number at which each row last changed — so engines can produce row-level change streams even across rewrites. This turns a table into a source for the next pipeline stage without scanning it, which is exactly what bronze-to-silver-to-gold incremental pipelines want.

Interoperability and its traps

Because all three formats store data as Parquet and differ only in metadata, translation layers can generate one format's metadata from another's: Delta's UniForm writes Iceberg (and Hudi) metadata alongside the Delta log, and Apache XTable (incubating) translates between all three. This lets a Databricks-written table be read by an Iceberg-only engine. The traps are features without equivalents (deletion vectors in a format version a reader does not support, column mapping modes, different timestamp semantics), one-way synchronisation (the translated metadata is usually read-only), and lag between the primary commit and the translated one. Treat interop as a way to read across ecosystems, not to have two writers on two formats.

The catalog is becoming the database

Early lakehouse designs prized being catalog-light: Delta tables were self-describing, and Iceberg's catalog only held a pointer. The direction since is the opposite. Catalogs now arbitrate commits (Delta catalog-managed tables), vend short-lived storage credentials per table, enforce row and column access policies, plan scans server-side (Iceberg REST's scan planning endpoints), and coordinate multi-table commits. The consequence for design: the choice of catalog increasingly determines which engines can participate, how governance works, and whether features like multi-table transactions are available — so treat it as core infrastructure with its own availability and disaster-recovery plan, not a detail.

Format versions are a compatibility contract

Upgrading a table to a new format version or enabling a table feature is a one-way door for every reader and writer. As of October 2026, Iceberg's specification lists versions 1, 2 and 3 as complete and adopted, with version 4 under active development; Iceberg 1.12 still creates v2 tables by default. Spec v3 adds deletion vectors, row lineage, default column values, variant, geometry and geography types and nanosecond timestamps — valuable, but an engine without v3 support cannot read such a table at all. Delta's table features work the same way: enabling deletionVectors raises the table's reader requirements. Before upgrading, inventory every engine and version that touches the table, including the long tail (a data-science laptop running an old library, a partner's reader), and test.

How table formats fail in production

Commit contention. Many writers (a streaming job, a compaction job, a GDPR delete, a backfill) commit to the same table; retries pile up and some fail with "commit failed: base metadata changed" or Delta's ConcurrentModificationException/ConcurrentAppendException. Symptoms: rising commit latency, failed maintenance jobs. Fixes: schedule maintenance away from peak writes, scope compaction to partitions the stream no longer writes, batch small writers, and use isolation levels that let blind appends proceed.

Metadata bloat. A streaming writer committing every 10 seconds creates 8,640 snapshots a day, each with at least one new manifest. Planning slows; the metadata JSON grows (it lists every retained snapshot); the Delta log needs frequent checkpoints. Fixes: longer commit intervals, regular snapshot expiry, manifest rewrites, and monitoring of manifest count and metadata file size.

Delete-file accumulation. A merge-on-read table under CDC accumulates delete files or deletion vectors; reads get slower each day until queries time out. Fix: compaction that targets files with many deletes, triggered by delete ratio.

Orphans and runaway storage. Failed jobs leave gigabytes of unreferenced files; nobody runs orphan removal; storage cost grows 20% a quarter with no growth in the table. Or the reverse: an orphan-removal job with too short a safety window deletes files an in-flight write was about to commit, corrupting the table. Fixes: run cleanup with a margin of several days, alert on the gap between storage bytes and table bytes.

Engine incompatibility after an upgrade. Someone enables deletion vectors or upgrades to Iceberg v3 for one engine's benefit; another engine can no longer read the table. Fix: a compatibility matrix and a change process for table features.

Time travel that is not there. A model audit asks for the training data from four months ago; snapshots older than five days were expired. Fix: tag snapshots used for training, with documented retention, and record snapshot IDs with every model.

What to watch

Per table: snapshots retained, commits per hour, commit retries and failures, manifest count or log entries since last checkpoint, data files and median size, delete files and deleted-row ratio, storage bytes versus bytes referenced by the current snapshot, and age of the oldest retained snapshot. Iceberg exposes much of this as metadata tables you can query directly (prod.orders.snapshots, .manifests, .files); Delta exposes DESCRIBE HISTORY and DESCRIBE DETAIL.

The case: the Delta Lake paper (VLDB 2020)

"Delta Lake: High-Performance ACID Table Storage over Cloud Object Stores" by Armbrust and colleagues at Databricks, CWI, UC Berkeley and Stanford (PVLDB volume 13, 2020) is the clearest primary account of why table formats exist and how they behave. The motivation section quantifies the object-store problem: S3's LIST returns at most 1,000 keys per call and each call takes tens to hundreds of milliseconds, so listing a dataset with millions of objects sequentially can take minutes; reading per-file Parquet footers for statistics adds a high-latency read per file. The paper reports that in Databricks' cloud service from 2014 to 2016, around half of support escalations were due to data corruption, consistency or performance issues from cloud storage strategies, and that Delta Lake later reduced that fraction to nearly none.

The design described is the one in this lesson: data objects in Parquet, a _delta_log of JSON records with add and remove actions carrying per-file statistics, Parquet checkpoints written every 10 transactions by default, a _last_checkpoint file, and atomic creation of the next log record via put-if-absent, atomic rename or (on S3, which then had neither) a lightweight coordination service. Its experiments make the metadata argument concrete. On small tables with between 1,000 and 1,000,000 partitions, Hive took more than an hour to find the objects in a table with only 10,000 partitions and Presto more than an hour at 100,000; listing plain Parquet on Databricks took 450 seconds at 100,000 partitions; Delta took 108 seconds with 1 million partitions, and 17 seconds when the log was cached. A Z-ordering experiment on a 100-file network-flow table showed that a global sort on four fields let queries on the first field skip 99% of files and on the other three skip 0%, while Z-ordering on all four skipped between 44% and 67% for each field (54% on average versus 25% for the single sort), and that on a 500 TB production dataset multi-attribute queries could skip 93% of the data. Loading 400 GB of TPC-DS data into Delta took about the same time as writing plain Parquet, showing that collecting statistics costs little.

The paper's discussion of limitations is as instructive as its results: serialisable transactions only within a single table, streaming latency bounded by object-store latency (seconds, not milliseconds), and a design aimed at relatively few, large write transactions. Every one of those still holds for the formats today.

Goal: build a toy table format in 60 lines and watch atomic commits, conflicts and time travel work. Python 3.12 standard library only; about 15 minutes. (Real Iceberg or Delta needs Spark or a dedicated library — not installed here.)

  1. In a folder toy/, a "data file" is a small JSON list of rows written once with a random name. The table's metadata is a series of files meta/v00001.json, v00002.json, …, each holding {"files": [...], "parent": n}.
  2. Write commit(new_files, removed_files, base_version): build the new file list from the base version, then create meta/v{base+1:05d}.json with open(path, "x") — exclusive creation, which fails with FileExistsError if the file exists. That is your put-if-absent.
  3. Write read(version=None): find the highest version (or the requested one), load its file list, and return all rows from those data files.
  4. Append two batches, then delete one row copy-on-write: write a new data file without the row and commit with the old file in removed_files.
  5. Simulate a race: call commit twice with the same base_version. Catch the second FileExistsError, re-read the latest version, check whether its removed files overlap the winner's, and retry.

What to look for. read() after the delete returns one fewer row, but read(version=2) still returns it — time travel — and the old data file is still on disk until you write a "vacuum" that deletes files no retained version lists. The second concurrent commit must fail, not overwrite: exclusive creation is doing the job a catalog's compare-and-swap does. Kill the script between writing a data file and committing, and notice the orphan file that no version references.

Diagnose: the training set that changed under us

A team retrains a ranking model weekly from an Iceberg table silver.impressions (one row per impression, with a click label). They record the training date but not table snapshots. Last week's model is much worse than the previous one; when they rerun the previous week's training script today, they get a different row count from what was logged at the time, and the old model's metrics cannot be reproduced. Meanwhile, the table has a streaming writer committing every 30 seconds, a nightly CDC merge that corrects late click labels (merge-on-read), a weekly compaction, and expire_snapshots with default settings. Explain what is going on and redesign for reproducibility.

Answer

What changed. Rerunning "the same query for the same date range" today reads the current snapshot, which includes every late-arriving impression and every corrected label committed since — so the row count and labels differ from what the original run saw. That is expected behaviour, not a bug: the table is mutable history. The team cannot go back to the original data because they did not record the snapshot ID, and with default expiry (snapshots older than about five days are removed when the job runs) the snapshots from the original run, and any files only they referenced, are gone.

Why last week's model may be worse. Candidates: the training run read the table while the nightly merge's corrections were only partly applied for the most recent days (labels for very recent impressions are still changing — clicks arrive late), or a compaction coincided with the read (harmless — snapshot isolation — but worth ruling out), or the label-correction job itself changed behaviour. Without snapshot IDs you can only compare aggregate statistics of the two training sets, which is why the next step is the redesign.

Redesign. (1) At training time, resolve the current snapshot ID of every input table and read at that snapshot explicitly; log the IDs, code version and row counts with the model. (2) Tag the snapshot (train-2026-10-08) with retention matching the model's audit period, or materialise the training set as its own immutable table or file set (de12) — the tag keeps all table files of that snapshot alive, which may be expensive on a high-churn table. (3) Exclude the most recent days whose labels are still changing (a label-maturity window, e.g. only impressions older than 3 days), so a training set does not depend on when it was built. (4) Reduce snapshot churn: a 30-second streaming commit interval creates 2,880 snapshots a day; a few minutes is usually enough and makes metadata and retention cheaper.
