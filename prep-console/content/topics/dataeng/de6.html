Almost every ML dataset is a join. A training set for a recommender joins billions of impressions to user features, item features and click labels. A fraud model joins transactions to card history, merchant profiles and chargebacks. An LLM fine-tuning pipeline joins documents to quality scores and deduplication clusters. On a laptop with pandas, a join is one line and finishes instantly. On a cluster, it is the operation most likely to make a job slow, expensive, wrong, or all three.

Consider an ads team building a daily training table: 4 billion impressions joined to 50 million advertisers. The job usually runs in 25 minutes. One day it runs for nine hours and then dies with an executor out-of-memory error. Nothing in the code changed. What changed was that a single advertiser — a large retailer launching a campaign — accounted for 30% of the day's impressions. The engine sends every row with the same key to the same task so it can be joined; one task got 1.2 billion rows, its sort buffer overflowed to disk again and again, and eventually the hash table for its output did not fit at all. 1,999 tasks finished in 40 seconds; one ran all night.

Another day, a different team's training set doubles in size overnight. The model's offline metrics jump — then the online test fails. Someone had added a second row per user to the user-features table (one per device); the join turned each impression into two, every user with two devices was counted twice, and the model learned from duplicated examples. No error, just a wrong result.

Both failures come from not knowing what a distributed join physically does. This lesson fixes that. It shows the three strategies an engine like Spark uses — broadcast hash, sort-merge and shuffle hash — with the bytes each moves and the memory each needs; how Spark chooses and how adaptive execution changes its mind; why output can explode; what skew is and why it defeats more hardware; and the toolkit for fixing it: broadcasting, AQE's skew splits, salting, isolating hot keys and pre-aggregating, each worked with sizes. It ends with memory arithmetic for spill and OOM, and Facebook's account of running a 60 TB, 90 TB-shuffle Spark job.

The mental model: matching name tags at a conference

A conference has 20,000 attendees spread over 100 rooms, and 300 speakers who each need to meet the attendees registered for their session. Every attendee must end up in the same place as their speaker. There are two ways to arrange it.

Send the speakers everywhere. Print each speaker's details on a sheet and photocopy the whole booklet of 300 sheets into every room. Now each room can match its own attendees against the booklet, and no attendee has to move. This works because the booklet is small. That is a broadcast join: copy the small table to every worker, never move the big one.

Move everyone by session. If, instead, the "speakers" were 15,000 mentors, photocopying them into every room is absurd. So everyone — attendees and mentors — walks to the room assigned to their session number: session 1 to room 1, session 2 to room 2, and so on. Each room then matches its own people. That is a shuffle join: both sides are redistributed by key, then each worker matches its share. It always works, but everyone has to walk.

Now the trouble. If one session is the keynote, with 8,000 registered attendees, then under "move everyone by session" one room receives 8,000 people while the other 99 average 120. The keynote room overflows into the corridor (that is spill), matching takes forever there, and the conference cannot start the next activity until it is done. That is skew. Adding more rooms does not help: the keynote is still one session going to one room. What helps is splitting the keynote across several rooms with a copy of the speaker's materials in each (salting, or Spark's automatic skew split), or handling the keynote separately (isolating the hot key), or using the photocopied-booklet approach if the speaker side is small (broadcast).

The analogy also explains exploding joins. If a session has two speakers listed and 100 attendees, "matching" produces 200 attendee–speaker pairs. If the speaker list accidentally lists each speaker twice, every attendee appears twice in the output. Joins multiply.

Where the analogy breaks: people can be counted at the door, but an engine must estimate sizes before it starts and often guesses wrong. That is why modern engines re-plan joins after they see real sizes (adaptive execution) — the equivalent of moving the keynote to the main hall once registrations come in.

Keep three questions in mind for every join you write at scale. How big is each side after filtering and projection — is one small enough to copy everywhere? What is the grain of each side — is the side you expect to be unique really one row per key? And how are the keys distributed — does any single value own a large share of the rows? The answers decide the strategy, the correctness of the output, and whether the job finishes.

1. What any distributed join must do

An equi-join (ON a.key = b.key) needs every pair of rows with equal keys to meet in one task. On a single machine (db7), a hash join loads the smaller input — the build side — into a hash table keyed on the join key, then streams the larger input — the probe side — and looks each row up; a sort-merge join sorts both inputs by key and walks them together like merging two sorted lists. Distributed engines use the same two algorithms, plus a decision about how to get matching rows into the same task: copy one side everywhere, or redistribute both by key.

2. Broadcast hash join

In a broadcast hash join, the small table is collected to the driver, serialised, and sent to every executor, which builds a hash table from it once and shares it across its tasks. Each task of the big table's stage then probes the hash table with its own partition — no shuffle of the big table at all. The whole join happens inside the scan stage of the big table.

Worked costs. Join a 2 TB (after projection) events table to a 50 MB merchants table on a cluster of 200 executors. Network: 50 MB × 200 = 10 GB of broadcast traffic, versus shuffling 2 TB + 50 MB for a shuffle join. Memory: each executor holds the merchants hash table. In-memory rows are decoded and uncompressed and the hash table has overhead, so 50 MB of Parquet might occupy 150–250 MB in memory — trivial against a 16 GB heap. Time: the 2 TB scan stage proceeds as if there were no join, plus a fast lookup per row.

Two further properties make broadcast joins special. They are immune to skew on the big side: a hot merchant's 400 GB of events are spread over many scan tasks by file layout, not gathered by key, so no task gets all of them. And they work for non-equi conditions too (a broadcast nested-loop join can evaluate a.ts BETWEEN b.start AND b.end), which a shuffle cannot partition on.

Their limits are memory and the driver. Every executor needs the whole small side in memory alongside its running tasks, and the driver must collect and build it first. Spark refuses to broadcast a relation larger than 8 GB, and in practice anything above a gigabyte or two risks executor or driver memory pressure; the broadcast must also finish within spark.sql.broadcastTimeout (300 seconds by default). Spark broadcasts automatically when the estimated size of a side is below spark.sql.autoBroadcastJoinThreshold — 10 MB by default in Spark 4.2 — a conservative number that teams with large executors commonly raise to tens or a few hundred megabytes. You can also force it with a hint: big.join(F.broadcast(small), "merchant_id") or /*+ BROADCAST(m) */ in SQL.

A broadcast join can only broadcast the side that is not "preserved" by an outer join: for big LEFT JOIN small, Spark can broadcast small; for small LEFT JOIN big, broadcasting big is required, which is usually impossible, so that join must shuffle.

3. Sort-merge join

A sort-merge join (SMJ) is Spark's default when neither side is small. Both sides are shuffled by hash(key) mod N into N partitions (two map stages, one per side, which can run concurrently). In the join stage, each task receives partition i of both sides, sorts each by key, and walks the two sorted streams: when keys are equal, it emits the matching pairs; otherwise it advances the side with the smaller key.

Its strength is robustness. Sorting can spill: if a partition does not fit in execution memory, the sorter writes sorted runs to disk and merges them, so a 20 GB partition is slow but completes. The merge phase itself needs to hold in memory only the rows for the current key on one side (Spark buffers the matching rows of one side for each key, spilling them too if a single key has a huge number of rows). Its costs are both shuffles and both sorts.

Worked costs. Events (2 TB after projection) join user features (300 GB) on user_id. Shuffle write and read: about 2.3 TB, each byte written to a local disk, sent over the network, and read back. With 2,000 shuffle partitions (AQE coalescing as needed), each join task receives about 1 GB of events and 150 MB of user features. On executors with about 1.2 GB of execution memory per task, sorting 1 GB of compressed shuffle data that expands in memory will spill a few times — acceptable. With the default 200 partitions, each task would receive 11.5 GB: heavy spill, long tasks, high risk of failure. Choosing N so that partitions are a few hundred megabytes is the main tuning lever for SMJ, and AQE helps by coalescing small ones.

4. Shuffle hash join

A shuffle hash join (SHJ) shuffles both sides like SMJ but, instead of sorting, builds a hash table from one side's partition in each task and probes it with the other. Skipping the sort saves CPU — often a lot when partitions are small. The risk is memory: the whole build-side partition must fit in the task's memory as a hash table (Spark's implementation can fall back in some cases, but it is far less spill-friendly than sorting). Spark prefers SMJ by default (spark.sql.join.preferSortMergeJoin is true) and uses SHJ when hinted (/*+ SHUFFLE_HASH(u) */) or when AQE sees that all post-shuffle partitions are below spark.sql.adaptive.maxShuffledHashJoinLocalMapThreshold — which is 0 (disabled) by default in Spark 4.2, so you must opt in. SHJ is a good choice when one side is moderately sized (too big to broadcast) and partitions are small and evenly sized.

5. How Spark chooses, and how to override it

At planning time, for an equi-join Spark roughly does the following: if a hint is present, use it (when both sides carry different hints, BROADCAST takes priority over MERGE, which takes priority over SHUFFLE_HASH, over SHUFFLE_REPLICATE_NL); otherwise, if one side's estimated size is under the broadcast threshold and the join type allows broadcasting that side, broadcast it; otherwise, if both sides are bucketed or partitioned compatibly in storage, join without a shuffle (de3); otherwise sort-merge join. Estimated sizes come from file sizes and table statistics, adjusted for filters and projections, and can be badly wrong — especially after other joins, aggregations or UDFs.

AQE corrects some of this at runtime. After the shuffle map stages, it knows each side's real size and can convert a planned SMJ into a broadcast hash join if one side came in under spark.sql.adaptive.autoBroadcastJoinThreshold (which defaults to the same value as the static threshold), and it can convert SMJ to SHJ when partitions are small enough and the threshold is set. Note the asymmetry: converting to broadcast after both sides were shuffled saves the sort and the reduce-side shuffle read (Spark can read the big side's shuffle output locally), but not the map-side shuffle write already done. Getting the broadcast right at planning time — with a hint, a higher threshold or good statistics — saves more.

Always check the chosen strategy in explain() or the SQL tab: BroadcastHashJoin, SortMergeJoin or ShuffledHashJoin, and whether BroadcastExchange or Exchange hashpartitioning nodes appear beneath it.

6. Output size and exploding joins

For an inner equi-join, the output has, for each key k, Lk × Rk rows, where Lk and Rk are the counts of k on each side. When one side is unique per key (a dimension table, a features table with one row per user), output ≤ the other side's size. When both sides have duplicates, output can be enormous.

Worked example. A table of 50 million product views is joined to a 2 million-row table of product reviews on product_id, intending to attach each product's average rating. But reviews has one row per review, not per product. A popular product with 200,000 views and 5,000 reviews produces 1 billion rows by itself. The job runs for hours and writes terabytes. The fix is to aggregate reviews to one row per product before the join. The general rule: know the grain of both sides, and assert uniqueness of the side you believe is unique (SELECT key, count(*) … HAVING count(*) > 1, or a data test, de11).

In ML pipelines, exploding joins are worse than slow; they are silently wrong. Duplicated training examples change class balance and the effective weight of users with more devices or more rows. A training-set builder should check row counts before and after each feature join: a left join of impressions to unique-per-user features must produce exactly as many rows as impressions.

Two related tools avoid explosions. A semi join (LEFT SEMI JOIN, or WHERE EXISTS) keeps left rows that have at least one match, without duplicating them — the right tool for "keep events from users who are in the test group". An anti join (LEFT ANTI JOIN) keeps left rows with no match — "events from users not in the blocklist".

7. Skew: why one key ruins a stage

Real key distributions are rarely uniform. User activity, product popularity, merchant volume, words and URLs follow heavy-tailed distributions, often close to a Zipf distribution, where the k-th most common key occurs in proportion to roughly 1/k. Add the artificial hot keys every dataset has — nulls, empty strings, a "default" or "unknown" category, test and bot accounts, a placeholder merchant ID — and a few keys can own a large fraction of all rows.

A shuffle join or group-by sends all rows of one key to one partition, so the partition holding a hot key is as large as that key's data, however many partitions there are. Worked example: 2 TB of events over 2,000 shuffle partitions should be 1 GB per partition. If one advertiser owns 30% of events, its partition receives 600 GB. Its task, with about 1.2 GB of execution memory, must sort 600 GB — spilling hundreds of times its memory to disk — and runs for hours, while the other 1,999 tasks finish in about a minute each. The stage, and so the job, takes as long as that one task. Doubling the cluster or the partition count makes the other tasks faster and leaves the straggler unchanged.

8. Fixing skew

Work through the options in roughly the order you should consider them.

(a) Remove junk keys. If the hot key is null, empty or a placeholder, it usually should not be joined at all: nulls never match in an inner or left equi-join (null ≠ null), yet they are shuffled into one partition anyway. Filter them before the join (for a left join, handle them separately and union them back with null columns). This is the cheapest fix and the most common.

(b) Broadcast the other side. If the side without the hot key is small enough, broadcasting it removes the shuffle and therefore the skew. 14 MB of merchants is a broadcast; 300 GB of user features is not — but the hot keys' rows of user features may be tiny, which leads to (d).

(c) Let AQE split skewed partitions. With AQE on (Spark 3.2+ default), a sort-merge join partition is treated as skewed when it is larger than spark.sql.adaptive.skewJoin.skewedPartitionFactor (5.0) times the median partition size and larger than skewedPartitionThresholdInBytes (256 MB). AQE splits it into sub-partitions of about the advisory size (64 MB) by grouping the map-output blocks, and duplicates the other side's corresponding partition for each sub-partition. In the example, the 600 GB partition becomes thousands of 64 MB pieces, or fewer larger ones, each joined against a copy of the matching user-features partition. It applies to the join types where splitting is valid (for example, the skewed side of an inner join, or the left side of a left outer join), and by default it is skipped if splitting would force an extra shuffle downstream (spark.sql.adaptive.forceOptimizeSkewedJoin, false). It also cannot help skew inside a group-by on the hot key if the aggregate needs all rows together. Check the SQL tab: a skew-split join is marked as such.

(d) Isolate hot keys. Find the hot keys (count by key, take those above a threshold). Split the big side into hot and normal rows. Join the normal rows with the usual shuffle join. Join the hot rows against only the hot keys' rows of the other side, which are few, using a broadcast join — no shuffle, no skew. Union the two results. This is explicit, predictable, and fast; its cost is code complexity and a list of hot keys that must be recomputed as data drifts.

(e) Salt the hot keys. When the other side's hot-key rows are too big to broadcast (both sides are large for that key), spread the key over N partitions artificially. On the big side, add a column salt = floor(rand() * N) for hot-key rows (0 for others). On the other side, replicate each hot-key row N times with salt = 0 … N−1 (others get 0). Join on (key, salt). Worked numbers: the hot advertiser's 600 GB of events with N = 150 becomes 150 partitions of 4 GB; if that advertiser has 2 GB of rows on the other side, replication adds 150 × 2 GB = 300 GB of shuffle — significant, but far better than one 600 GB task. Salting multiplies the other side by N for hot keys, so choose N from the hot key's size divided by a target partition size, and salt only hot keys.

(f) Pre-aggregate. If the job joins and then aggregates per key (spend per advertiser with advertiser attributes), aggregate the big side to one row per key first — the partial aggregation before the shuffle (de5) makes this cheap and skew-resistant because each map task sends one partial result per key — and join the small aggregate. Many skewed joins disappear once you notice the output grain was coarser than the input.

(g) Change the grain or the key. Sometimes the skew comes from joining at the wrong grain: joining impressions to "campaign" when "campaign × day" would spread the load and is what the features actually need.

9. Spill and executor OOM, with arithmetic

Memory decides whether a join is slow (spill) or dead (OOM). Two numbers matter: memory available per task, and the in-memory size of what a task must hold.

Memory per task. From de5: a 16 GB heap gives about 9.4 GB of unified memory; with 8 cores, about 1.2 GB per concurrent task if nothing is cached. A 32 GB heap with 4 cores gives about 4.7 GB per task.

In-memory size. Shuffle data is compressed and serialised; Parquet is encoded and compressed. In memory, rows are decoded into Spark's binary row format (each row with a null bitmap, fixed 8-byte slots for fixed-width fields and variable-length data appended), and hash tables add pointers and empty slots. A rough planning factor is that data expands 2–5× from compressed file or shuffle size to in-memory hash-table size, depending on column types and compression ratio — measure on your data.

Worked: a shuffle hash join where the build-side partition is 800 MB of shuffle data. At a 3× expansion it needs about 2.4 GB of memory, which does not fit in 1.2 GB per task; on an executor with 4 cores and 4.7 GB per task, it fits. A broadcast of a 1.5 GB table (on disk) may need 4–6 GB in every executor plus on the driver while building it — on 16 GB executors that leaves little room for tasks, causing heavy spill everywhere, and at worst an OOM in the driver. A sort-merge join with a 10 GB partition and 1.2 GB per task will spill roughly eight times its memory to disk and survive, slowly.

When joins OOM, the order of remedies is: fix skew (most "OOM" joins are skewed joins); reduce what each task holds (more partitions for even data, project fewer columns before the join, filter earlier); prefer SMJ over SHJ for large partitions; reduce concurrency per executor (fewer cores per executor, so each task gets more memory); only then add memory. For PySpark jobs, also check whether the error is a container kill from Python worker memory rather than the JVM heap (de5).

10. A worked training-set join

Build a daily training table: 3 billion impressions (projected to 12 columns, about 600 GB in shuffle format) joined to item features (5 million items, 400 MB projected), advertiser features (2 million advertisers, 150 MB), and user features (250 million users, 250 GB projected). Cluster: 100 executors, 8 cores, 32 GB heap (about 2.3 GB of execution memory per task).

  1. Item and advertiser features: broadcast both. 550 MB × 100 executors = 55 GB of network; in memory perhaps 2 GB per executor — acceptable on a 32 GB heap. Raise the broadcast threshold or use hints, since the defaults would not broadcast them. These joins happen inside the impressions scan with no shuffle, and the hot advertiser problem from the introduction disappears.
  2. User features: shuffle join on user_id. 850 GB of shuffle; 4,000 partitions gives about 210 MB per partition, comfortable for sort-merge. Check skew: bots and power users. Filter known bots first; let AQE split any remaining skewed partitions.
  3. Checks: assert features tables are unique per key; assert output row count equals impressions; record null rates for each joined feature (a sudden jump means a key mismatch, such as a type change from integer to string IDs).

Better still for a daily job: bucket impressions and user features by user_id into the same number of buckets so the user join needs no shuffle at all (de3), and make the features point-in-time correct (de12).

Why the planner's size estimates are so often wrong

A planner estimates a join input's size from file sizes or table statistics and then multiplies by estimated selectivities of every filter and join on the way. Each estimate assumes independence and uniformity — "the filter keeps 10% of rows", "each key matches 1.2 rows" — and errors compound multiplicatively through a plan. After two or three joins, estimates can be off by orders of magnitude in either direction. That is why Spark's static broadcast threshold is conservative (a wrongly broadcast 5 GB table is a disaster, a missed broadcast of a 50 MB table only a slowdown), and why AQE's runtime statistics are such a large improvement: it replaces estimates with measurements at every shuffle boundary. The residual risk is decisions made before the first shuffle, such as the broadcast of a scanned table; good table statistics and explicit hints remain the tools there.

AQE's skew split, mechanically

A sort-merge join partition on the reduce side is the concatenation of one block from each map task. AQE splits a skewed partition by grouping those map-output blocks into contiguous ranges whose total is about the target size, creating sub-partitions that each read a subset of map outputs. Each sub-partition must still meet every matching row from the other side, so the other side's corresponding partition is read in full by each sub-task — "replicated". Two consequences follow. First, if a single map task's block for the hot partition is itself enormous (because the input was clustered by that key), AQE cannot split below one block. Second, if both sides are skewed on the same key, splitting both would require pairing every left piece with every right piece — a cross-product of sub-tasks — which is why skew in both inputs for the same key is the hardest case and often needs pre-aggregation or redesign.

Join ordering and the size of intermediates

In a multi-way join, the order matters as much as the strategy. Joining a 3-billion-row fact table first to a selective dimension filter (say, "campaigns in the experiment", 2% of rows) and only then to large feature tables means the expensive joins process 60 million rows instead of 3 billion. Catalyst applies some reordering (and the cost-based optimiser, when enabled with statistics, applies more), but analysts and pipeline authors should consciously put the most selective joins and filters first, turn "filter by membership" joins into semi joins or broadcasts, and avoid accumulating wide intermediate rows — projecting columns away before each join reduces both shuffle bytes and memory per row.

Bloom-filter joins and runtime filtering

When a selective small side joins a large one, much of the large side's data is shuffled only to find no match. Runtime filtering builds a compact summary of the small side's keys — a min/max range, an IN-list, or a Bloom filter — and applies it to the large side's scan before the shuffle, sometimes even pruning files and row groups (dynamic partition pruning prunes whole storage partitions when the join key is a partition column of the large table). Spark includes dynamic partition pruning and, in recent versions, runtime Bloom-filter injection for some joins; the effect can be dramatic for star-schema queries. Check the plan for dynamicpruning or Bloom-filter expressions on scans to see whether it applied.

Skew in aggregations and windows

Joins are not the only skewed operations. A groupBy on a hot key is usually rescued by partial aggregation, because each map task reduces its share of the key to one partial result before the shuffle — but only for decomposable aggregates (sum, count, min, max, average via sum and count). Exact distinct counts, medians, collect_list and window functions partitioned by the hot key need all of a key's rows in one task. Remedies: approximate algorithms (HyperLogLog for distinct counts, t-digest or KLL for quantiles), two-stage aggregation with a salt (aggregate by key and salt, then by key), or redesigning the computation to a finer grain. Window functions over a skewed partition column are a particular trap in feature engineering ("for each user, the previous 50 events") — bot users with millions of events create gigantic window partitions; capping events per user before the window is often both correct and necessary.

When a different engine or layout is the real fix

Repeated daily joins of the same huge tables are a design smell. Options that remove the join cost rather than tuning it: storage-partitioned joins on co-bucketed tables (no shuffle); incremental processing that joins only new rows against stable tables; denormalising slowly changing attributes into the fact table at write time (de10); serving lookups from a key-value store during feature computation for small, frequently joined dimensions; or, for data that fits on one large machine, a single-node engine whose in-memory hash join avoids network shuffles entirely (de13).

Failure modes and their symptoms

The straggler. A stage at 99% for hours. UI: max shuffle read and duration far above median, spill on one task. Cause: skewed key. Fix: section 8, starting with junk keys.

The plan flip. A job's runtime jumps by 5–20× with no code change. UI/SQL plan: a BroadcastHashJoin became SortMergeJoin (dimension grew past the threshold, or statistics changed), or the reverse — a broadcast that is now too big fails with a broadcast timeout or driver OOM. Fix: hints or thresholds based on measured sizes; keep plans of critical jobs and alert on strategy changes.

The explosion. Output rows or bytes far exceed inputs; jobs run out of disk on shuffle; training sets double. Cause: non-unique keys on a side believed unique, or a missing join condition. Fix: uniqueness tests, row-count assertions, and aggregating to the right grain before joining.

Silent key mismatch. Join succeeds but most feature columns are null. Causes: type mismatch (string "00123" versus integer 123), case or whitespace differences, IDs from different systems, time-zone shifted date keys. Fix: null-rate checks per joined feature, explicit casts and normalisation in silver.

Executor and driver OOM. Containers killed or Java OOMs during joins. Causes: skew, oversized broadcasts, shuffle hash joins on big partitions, too many cores per executor for the memory. Fix: section 9.

Shuffle fetch failures at scale. Very large shuffles with many map tasks and partitions stress shuffle services and networks; lost executors cause map-stage recomputation. Fix: fewer, larger tasks; external or remote shuffle; tuned shuffle-service thread and connection settings.

What to watch

For each join-heavy stage: the ratio of max to median shuffle read (alert above about 10–20), spill per task, the chosen join strategy, input and output row counts of each join (from the SQL tab's metrics), and null rates of joined columns in the output. For each table that is frequently a join's small side: its size over time relative to your broadcast threshold.

The case: Facebook's 60 TB Spark pipeline (2016)

In "Apache Spark @Scale: A 60 TB+ production use case" (Facebook Engineering blog, 31 August 2016, by Avery Ching, Sital Kedia and Shuojie Wang), Facebook described replacing an entity-ranking data pipeline built as three logical stages, each split into hundreds of smaller Hive jobs sharded by entity_id, which took roughly three days to run and offered no easy way to track progress. The Spark replacement combined the stages into one job, eliminating two temporary tables, and at full scale read 60 TB of compressed input and performed a 90 TB shuffle and sort — the core of a join-and-aggregate pipeline at a scale where every effect in this lesson is magnified.

The post is valuable because it lists what broke. Task counts: with a 256 MB HDFS block size the job had over 250,000 tasks; raising the input split size to 2 GB cut the task count 8× (de5's partition sizing). Fetch failures in a 90 TB shuffle were common enough that they raised the maximum number of fetch failures per stage from 4 to 20 and fixed a case where fetch failures caused duplicate task runs. The driver became unresponsive from O(N²) bookkeeping when adding tasks (fixed in SPARK-13279). Executors hit out-of-memory errors in the sorter when its pointer array could not grow; forcing a spill instead raised capacity from 4 to 24 tasks per host (SPARK-13958) — exactly the spill-versus-OOM boundary of section 9. Performance fixes included a sorter memory leak worth about 30% CPU, caching shuffle index files to cut total shuffle fetch time by 50% (reducers had spent 10–15% of their time waiting on fetches), and avoiding reopening a file per partition in shuffle writes, worth up to 50% CPU at high partition counts. After several months in production the Spark pipeline showed 4.5–6× less CPU time, 3–4× less reserved CPU time and about 5× lower latency than the Hive pipeline.

Many of these fixes are now in Spark itself, and AQE (Databricks' May 2020 post reports 32 TPC-DS queries sped up by more than 1.1× and up to 8×) automates partition coalescing, join conversion and skew splitting. But the shape of the problems is unchanged: at scale, the cost of a join is its shuffle, its memory per task and its slowest partition.

Goal: see skew appear from a realistic key distribution, and watch salting and isolation flatten it. Python 3.12 standard library; about 15 minutes.

  1. Generate 2,000,000 join keys for a "big" table from a Zipf-like distribution over 100,000 keys: weight key k by 1 / k and use random.choices(range(1, 100_001), weights=w, k=2_000_000). Add 100,000 None keys to mimic nulls.
  2. Hash-partition into 200 partitions (hash(k) % 200, with nulls going to partition 0 as a single hash value would). Print the min, median and max partition sizes and the top 5 keys by count.
  3. Drop the null keys and recompute. Then isolate the top 10 keys (send them to a separate "broadcast" path) and recompute the remaining partition sizes.
  4. Instead of isolating, salt the top 10 keys with N = 20 ((k, random.randrange(20))) and recompute. Count how many extra rows the "small" side would need: 19 extra copies of each of the 10 hot keys' rows.
  5. Try next: change the partition count to 2,000 before any fix and note which statistic does not improve.

What to look for. With 1/k weights, key 1 alone holds about 8% of rows (1 / H(100,000) ≈ 1/12.1), so the max partition is many times the median — and the null partition is the biggest of all. Dropping nulls, then isolating or salting the hot keys, should bring max/median close to 1–2. Raising the partition count shrinks the median but leaves the max almost untouched, because one key cannot be split by hashing.

Estimate and design: a skewed ads join

A daily job joins impressions (4 billion rows, 1.6 TB after projection) to advertiser_features (50 million rows, one per advertiser, 40 GB after projection) on advertiser_id, then writes the joined training rows. Cluster: 150 executors, 8 cores each, 16 GB heap. Today one advertiser has 30% of impressions; 2% of impressions have a null advertiser_id. The job planned a sort-merge join with 2,000 shuffle partitions. Estimate what happens, then propose a fix with numbers.

Answer

What happens. Both sides are shuffled by advertiser_id: about 1.64 TB. Evenly spread, 2,000 partitions would be about 820 MB each. But the hot advertiser's 30% is 480 GB, all in one partition, and the 2% nulls (32 GB) all hash to one partition too. With 16 GB heaps and 8 cores, each task has about 1.2 GB of execution memory, so the hot task sorts 480 GB through 1.2 GB — hundreds of spill rounds — and runs for hours; 1,998 tasks finish in about a minute each. AQE's skew split would qualify (480 GB is far above 5 × the median and 256 MB) and is the first thing to verify in the SQL plan; if the job writes directly after the join, no extra shuffle is needed and the split should apply.

Fix 1: nulls. Null never matches in the join; filter those 80 million rows out before the shuffle (or, if the training set needs them, union them back with null features after the join). Saves 32 GB of shuffle and removes the second straggler.

Fix 2: the hot advertiser. The other side has one row per advertiser, so the hot advertiser's features are one row. Isolate it: split impressions into the hot advertiser's rows and the rest; join the hot rows to that single features row with a broadcast (a 1-row table) — no shuffle; join the rest with the normal sort-merge join; union. The remaining shuffle is about 1.1 TB + 40 GB over 2,000 partitions: about 570 MB each, comfortable. Alternatively, notice that 40 GB of advertiser features is close to broadcastable if projected further: if the model needs 6 columns totalling 2 GB, broadcasting it (2 GB × 150 executors = 300 GB of network, perhaps 5–6 GB in memory per executor) removes the impressions shuffle entirely — but on a 16 GB heap that leaves too little room, so with these executors isolation is the better choice.

Fix 3: guardrails. Recompute the hot-key list daily from a cheap count by advertiser; alert when any key exceeds, say, 1% of rows; assert output row count equals filtered input impressions (one features row per advertiser).
