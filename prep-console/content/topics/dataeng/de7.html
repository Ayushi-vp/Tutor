The feature pipeline for a churn model is a dozen steps: land yesterday's app events, land the subscriptions CDC changes, deduplicate both, rebuild the current-state subscriptions table, aggregate events per user per day, compute 7-, 28- and 90-day rolling features, join labels, write the training table, train, evaluate, publish. At first a cron entry runs a shell script at 02:00 that runs each step in turn. It works for a month.

Then the events landing job runs late one night, and the aggregation starts at 02:00 regardless, on half a day of events; the model trains on it and nobody knows. Another night the deduplication step fails halfway; the script stops, so nothing downstream runs, and the fix is "rerun the whole thing", which re-lands events that were already landed — every event from that night now exists twice. A bug is found in the 28-day feature; it needs recomputing for the last six months, which means running the script with a fake date 180 times, sequentially, for nine days. And when the training table is late, the first person to notice is the data scientist whose morning experiment is using yesterday's data.

None of these is a Spark problem or a SQL problem. They are orchestration problems — dependencies, retries, partial failure, reruns, history, late data, deadlines — and pipeline design problems: whether each step can be safely run again, whether it knows which slice of time it is responsible for, and whether "the step succeeded" means "the data is right". Every ML platform runs on hundreds or thousands of such pipelines, and most data incidents trace back to one of these questions answered badly.

This lesson covers both halves. On the orchestration side: DAGs of tasks, how Airflow schedules runs and what logical dates and data intervals mean (including a subtle change in Airflow 3), asset-centric orchestration in Dagster and Airflow, sensors, pools and retries. On the design side: the idempotent, interval-parameterised task that makes everything else safe; backfills with real numbers; late-arriving data and lookback windows; and freshness SLAs and alerting. The case is Shopify's account of running Airflow with more than 10,000 DAGs and 150,000 runs a day.

The mental model: a bakery's production schedule

A bakery makes bread every day. The work is a chain of steps with dependencies: mix dough, let it rise, shape, bake, cool, package, deliver. Some steps can happen in parallel (croissant dough and sourdough are independent); others must wait (you cannot bake before shaping). A production manager holds the schedule — the orchestrator. The chain of steps is the DAG; each step is a task; each day's batch is a run, labelled by the day the bread is for.

A good bakery has habits that map directly onto good pipelines. Each batch is labelled with the day it is for, and a baker making "Tuesday's sourdough" uses Tuesday's order list, not whatever orders happen to be on the board when they start — interval-parameterised tasks. If a batch is burnt, the baker throws away that batch and bakes it again; they never put a second batch of Tuesday's sourdough on the shelf next to the first — idempotent overwrite, not append. If the flour delivery is late, the mixing step waits for the delivery rather than mixing with half a bag — a sensor waiting for upstream data. If an oven trips its breaker, the baker resets it and tries again a few minutes later — retry with backoff. The bakery promises cafés their bread by 06:00, and the manager is warned at 05:30 if the bake is not finished — a deadline alert. When the recipe for rye is fixed, the bakery cannot re-bake last month's bread, but a data platform can: rerunning old days with the new code is a backfill.

And there is the late-order problem. A café calls at 09:00 to add to yesterday's order — data arriving after its interval was processed. A sensible bakery either keeps yesterday's batch open for a few hours, or bakes a small top-up later and corrects yesterday's invoice — a lookback window that reprocesses recent days.

Where the analogy breaks: bread is consumed, data is kept and reread. That makes the bakery's "throw away the bad batch and remake it" rule even more important for data, because every downstream consumer reads whatever is on the shelf, and duplicated or half-made batches persist and propagate.

If you remember one rule from this lesson, make it this: a task is a function of its interval. Given "2026-10-07", it reads the inputs for 2026-10-07, computes, and replaces the output for 2026-10-07 — nothing about the wall clock, nothing about what happened on the previous run. Every capability the orchestrator offers (retries, reruns, backfills, recovery after an outage) is only safe when tasks follow that rule, and almost every pipeline incident in the production section below is a violation of it.

1. Pipelines as DAGs

A pipeline is a set of steps with dependencies. Written down as a graph — each step a node, each "must finish before" an edge — it is a directed acyclic graph (DAG): directed because dependencies have a direction, acyclic because a step cannot (transitively) depend on itself. The DAG makes three things explicit that a shell script hides: which steps can run in parallel (those with no path between them), what must be rerun when a step changes (everything downstream of it), and where a failure stops progress (everything downstream of the failed step, and nothing else).

An orchestrator runs DAGs. At minimum it: decides when a DAG should run (a schedule, or an event such as new upstream data); starts tasks when their dependencies have succeeded; retries failed tasks according to policy; enforces timeouts and concurrency limits; records the state, logs and timing of every run; lets operators rerun, clear or skip tasks and backfill past intervals; and alerts. Apache Airflow (created at Airbnb in 2014, now an Apache project) is the most widely used; Dagster, Prefect, Argo Workflows and cloud services (AWS Step Functions, Google Cloud Composer — a managed Airflow) are common alternatives. Versions here are as of October 2026: Airflow 3.3.

2. How Airflow works

In Airflow, a DAG is defined in a Python file. Tasks are created from operators — templates such as a SQL operator, a Spark-submit operator, a Kubernetes-pod operator, or a plain Python function decorated with @task. Dependencies are declared with >>. The main components:

  • The scheduler parses DAG files, decides which DAG runs are due according to each DAG's timetable, creates runs, and queues task instances whose upstream tasks have succeeded.
  • The executor decides where queued tasks run: in local processes, on Celery workers, or as Kubernetes pods (one pod per task).
  • The metadata database (PostgreSQL or MySQL) stores every DAG run and task instance with its state — queued, running, success, failed, up_for_retry, skipped — plus history.
  • The API server and UI show runs, logs and graphs, and let operators trigger, clear and backfill. In Airflow 3, task code talks to Airflow through a Task SDK and an API rather than reading the metadata database directly.

A DAG run is one execution of the DAG. Each run has a logical date, and with interval-based timetables a data interval — the slice of time the run is responsible for. The classic daily schedule (Airflow 2's default for cron expressions, the CronDataIntervalTimetable) works like this: the run for data interval 2026-10-07 00:00 → 2026-10-08 00:00 is triggered after the interval ends, at 2026-10-08 00:00; its logical date is the interval start, 2026-10-07. This "the run for Tuesday happens on Wednesday" behaviour confuses everyone once and then makes sense: you can only process a day once it is over.

Airflow 3 changed the default for DAGs that pass a bare cron string to schedule=: they now use the CronTriggerTimetable (the [scheduler] create_cron_data_intervals setting defaults to false). A trigger timetable "does not address the concept of data interval": the run triggered at 2026-10-08 00:00 has a logical date of 2026-10-08 00:00, and its data_interval_start and data_interval_end are both that same instant — unless you construct the timetable with an interval, for example one day, in which case the interval ends at the trigger time. A DAG written for Airflow 2 that computes its date range as [data_interval_start, data_interval_end) therefore processes an empty range after an upgrade, silently. Airflow 3 also removed several old template variables (execution_date, prev_ds, next_ds, yesterday_ds and others), turned catchup off by default (creating a DAG with a start date in the past no longer creates a run for every missed day), and renamed datasets to assets. The robust practice: pin the timetable explicitly in each DAG, and compute the partition a run is responsible for in one place, by a documented rule, and pass it to every task.

Two more building blocks. A sensor is a task that waits until something is true — a file exists, a partition has been published, an upstream DAG's task succeeded — checking periodically or, in deferrable mode, without occupying a worker slot while it waits. A pool is a named limit on concurrent tasks (say, at most 4 tasks hitting the production replica), used to protect shared resources.

A minimal daily DAG (Needs Airflow 3; not run):

from datetime import timedelta
from airflow.sdk import dag, task
from airflow.timetables.trigger import CronTriggerTimetable

@dag(schedule=CronTriggerTimetable("0 3 * * *", timezone="UTC",
                                   interval=timedelta(days=1)),
     catchup=False, max_active_runs=4,
     default_args={"retries": 3, "retry_delay": timedelta(minutes=5),
                   "retry_exponential_backoff": True,
                   "execution_timeout": timedelta(hours=2)})
def user_features():
    @task
    def build(data_interval_start=None, data_interval_end=None):
        day = data_interval_start.date().isoformat()  # e.g. "2026-10-07"
        run_spark_job("features.py", "--date", day)    # overwrites that day only
    build()

user_features()

With the one-day interval, the run triggered at 2026-10-08 03:00 covers 2026-10-07 03:00 → 2026-10-08 03:00; computing day from data_interval_start gives 2026-10-07 — a deliberate rule, written once. (The three-hour offset leaves time for late-landing data, section 6.)

3. Tasks versus assets

Classic Airflow is task-centric: the orchestrator knows that a function ran and succeeded at a time. It does not know what data that function produced. "Is gold.user_features for 2026-10-07 up to date?" is not a question it can answer; you infer it from task states.

Asset-centric orchestration models the data itself. In Dagster, a software-defined asset is a function decorated with the asset it produces and the assets it depends on; partitioned assets declare their partitioning (daily, by region, both); materialising an asset partition is an event the orchestrator records, with metadata (row count, schema, code version). Because the graph is of assets, the orchestrator can show lineage, mark a partition stale when an upstream partition or the code changed, backfill exactly the missing or stale partitions, and attach asset checks — tests on the produced data that can block downstream materialisation. Airflow 3's assets (called datasets in Airflow 2) bring part of this to Airflow: a task can declare that it updates an asset, and another DAG can be scheduled to run when that asset is updated, instead of at a fixed time.

The practical difference shows in three situations. When upstream data is late, an asset-triggered pipeline simply runs later; a time-triggered one runs on schedule, on stale or partial data, unless a sensor stops it. When code changes, an asset-aware orchestrator can tell which partitions were built by the old code. And when something is wrong, "which assets did this training run consume, and how were they built?" has a direct answer. For ML, where training runs, feature tables and models are naturally assets, the asset model fits better; for operational workflows (call an API, send a report), tasks are fine.

4. The idempotent, interval-parameterised task

The single most important pipeline design rule: every task must be idempotent and deterministic with respect to its interval. Running the task for interval I once, twice, or a hundred times — today or a year from now — must leave its output for I in the same state, given the same inputs. Retries, reruns, backfills and recovery from partial failure all depend on it.

Three ingredients make a task idempotent.

Parameterise by interval, never by "now". A task should compute "events with event time in [2026-10-07, 2026-10-08)", not "events from the last 24 hours" or "events that arrived since the last run". now(), current_date, "the latest partition" and "since the last successful run" all make the output depend on when the task ran, so a retry at 06:00 and the original run at 03:00 produce different results, and a backfill for last March produces garbage.

Read fixed inputs. The task should read the input partitions for its interval (plus any fixed lookback it needs), ideally pinned to specific versions (table-format snapshots, de4) so a rerun reads exactly what the original read. Reading mutable "current state" tables makes reruns produce different results — sometimes acceptable, but then deliberate.

Replace, don't append. The task should atomically replace its output for the interval: INSERT OVERWRITE … PARTITION (date = '2026-10-07'), Spark with dynamic partition overwrite, Iceberg overwrite with a filter, Delta replaceWhere, or BEGIN; DELETE … WHERE date = …; INSERT …; COMMIT; in a transactional database. Appending makes every retry a duplication. For tables updated by key rather than by interval (a current-state dimension), the equivalent is a MERGE on the primary key, which is idempotent if the input is fixed.

A trace shows why it matters. A task appends 10 million rows for 2026-10-07 and then fails while writing a success marker. Retry 1 appends 10 million more and fails the same way; retry 2 succeeds. The partition holds 30 million rows, and every downstream count is tripled. With an overwrite, the partition holds 10 million rows after each attempt, and the extra attempts cost only compute. This idea — tasks as pure functions of their inputs, outputs as immutable partitions replaced wholesale — was popularised as "functional data engineering" by Maxime Beauchemin, Airflow's creator.

Side effects outside tables need the same thinking. A task that sends an email, calls a payment API or publishes to Kafka cannot "overwrite"; it needs an idempotency key (derived from the interval and content) that the receiver uses to drop repeats, or a record of what was sent that the task checks first.

5. Backfills

A backfill runs a pipeline for past intervals. You need one when adding a new table or feature (history is needed for training), after fixing a bug (wrong partitions must be recomputed), after an upstream correction (the source re-delivered a bad week), or after an outage (runs that never happened). In Airflow 3, backfills are created through the CLI, API or UI and executed by the scheduler like normal runs, with options for how many run concurrently and whether to rerun intervals that already succeeded.

Size it before starting. A daily job takes 20 minutes on a 50-executor cluster; a new feature needs two years of history: 730 runs. Sequentially that is 730 × 20 min ≈ 243 hours — ten days. Running 10 at a time needs 10 × 50 = 500 executors' worth of capacity (or ten times as long per run on a shared cluster) and brings it to about a day. Running all 730 at once would swamp the cluster, the source tables and the table's commit path. Practical rules:

  • Throttle with max_active_runs, backfill concurrency settings and pools, so the backfill does not starve production runs or hammer source databases.
  • Watch for dependencies on the past. A rolling 90-day feature computed from raw events needs 90 days of input per output day; that is fine in parallel. A feature computed incrementally from the previous day's output ("yesterday's running total plus today's events") forces runs to go in order (Airflow's depends_on_past) and turns 730 parallel runs into a 10-day sequential chain. Prefer formulations that depend on inputs, not on previous outputs.
  • Consider one big job. 730 daily runs each re-reading overlapping 90-day windows read 730 × 90 = 65,700 day-partitions of input. One job that reads two years once and computes all output days with window functions reads 820 day-partitions (730 + 90 of lookback) — about 80× less input I/O — and pays the fixed overhead once. Many teams write the backfill path as a separate, range-based job for this reason.
  • Use today's code deliberately. Backfilled history is computed with the current code, so it differs from what was computed at the time. That is usually the point, but it means a model trained on backfilled features and a model trained on the original ones saw different data — record which.
  • Validate and announce. Compare row counts and key aggregates of rewritten partitions with the old ones and with independent sources; tell downstream owners, because rewriting a partition may trigger their asset-aware pipelines or change their dashboards.

6. Late-arriving data

Events do not arrive in the order or at the time they happened. Mobile apps batch events and send them when the phone reconnects; partner files arrive the next morning; CDC connectors lag during maintenance. If you measure, for each event, the gap between its event time and its arrival in the lake, you get a lateness distribution: typically most events within minutes, a long tail over hours and days. For example: 99% within 1 hour, 99.9% within 24 hours, 99.99% within 72 hours.

A daily batch job must decide when a day is "complete enough" to process and what to do with events that arrive afterwards. The usual combination:

  • Partition and compute by event time. An event from 2026-10-07 23:58 that arrives at 00:30 belongs to 10-07, not 10-08. Partitioning landing data by arrival time is fine for bronze, but silver and gold should be keyed by event time.
  • Delay the first computation to capture most late data: run the 10-07 job at 03:00 on 10-08 rather than 00:05, accepting three hours of latency to include, say, 99.5% of events.
  • Use a lookback window. Each daily run recomputes the last N days, not just the newest one: the 10-09 run recomputes 10-07, 10-08 and 10-09. Late events from 10-07 that arrived on 10-08 are thus included on the second pass. With the distribution above, a 3-day lookback covers 99.99%. Because tasks are idempotent overwrites, recomputing a day is safe.
  • Use completeness signals. Where upstream systems can say "10-07 is complete" — a partner's end-of-day marker file, a CDC connector's position past midnight, an upstream asset's published partition — use a sensor or asset dependency rather than guessing with a clock.
  • Measure what is left. Count events arriving after the lookback window closed for their day; alert if the count grows (it means the lateness distribution shifted and the window is too short).

The lookback has costs: compute (a 3-day lookback roughly triples the work of a job that processes one day of input) and instability (consumers see recent days change). ML training sets usually exclude the most recent days entirely — they are both incomplete and, for many labels, immature (a "purchased within 7 days" label is not knowable for impressions from yesterday). de9 treats the streaming version of this problem, where watermarks play the role of the lookback.

7. Retries, timeouts and failure semantics

Failures in batch pipelines are mostly transient: a spot instance reclaimed, a source database briefly overloaded, a network timeout to object storage. Retries with exponential backoff handle these — retry after 5 minutes, then 10, then 20 — so a brief outage does not need a human. Set retries per task according to what fails: a task calling a flaky external API deserves more than a pure SQL transformation, where a failure is likely a real bug and retrying wastes cluster time.

Timeouts (execution_timeout in Airflow) turn a hung task into a failure that retries or alerts, instead of a run that sits "running" forever while the deadline passes. Set them from the task's historical duration — for example, three times its 95th percentile.

Failure semantics must be explicit. Downstream tasks by default run only when all upstream tasks succeeded; trigger rules change that for cleanup or notification tasks (run even if something failed). And partial success must be impossible to mistake for success: a task that wrote some partitions and then crashed must either have its writes invisible (atomic commit, write-audit-publish) or be safe to rerun (idempotent overwrite) — ideally both.

8. SLAs, freshness and alerting

Consumers care about one thing: is the data they need ready and correct when they need it? Express that as a freshness objective for each important output — "gold.user_features for day D is published by 06:00 UTC on D+1, on 99% of days" — and alert on it, rather than on individual task timings.

Airflow 2 had task-level SLAs, which were widely found confusing and unreliable; Airflow 3 removed them. The replacement, deadline alerts (introduced in Airflow 3.1 and documented as experimental), attaches to a DAG a reference point — when the run was queued, or its logical date — plus an interval, and a callback to execute if the run has not finished by then: "if the run for logical date D has not finished 27 hours after D, notify the on-call channel". Outside the orchestrator, many teams monitor freshness on the tables themselves (time since the newest partition was published), which also catches failures of pipelines in other systems.

Good alerting is narrow. Page a human for: a deadline that will be missed, a run that failed after exhausting retries, a data check that failed on a critical asset. Do not page for individual retries, warnings or non-critical pipelines; send those to a dashboard or a daily digest. Every alert should name the owning team and link to a runbook. An orchestrator with thousands of noisy alerts is an orchestrator whose alerts are ignored.

9. Write-audit-publish

One pattern ties idempotency and quality together. A task writes its output somewhere invisible to consumers — a staging table, a staging partition, or an Iceberg branch (de4) — runs data checks on it (row counts versus expectation, uniqueness, null rates, distribution shifts), and only if the checks pass, publishes it atomically: swaps the partition in, fast-forwards the branch, or flips a view. If checks fail, nothing changes for consumers and the run fails loudly. With a table format, publish is a single commit, so consumers either see yesterday's validated data or today's validated data, never today's unvalidated data. It costs one extra write and some delay, and it is the difference between "a bad day's data got into the model" and "the training table was late by an hour while someone looked at a failed check".

Determinism is harder than it looks

"Same inputs, same outputs" fails in subtle ways. Reading "the latest snapshot" of an input table makes a rerun read different data than the original run; pin snapshot IDs or read by explicit partition. Spark output can depend on partitioning and order when the logic uses first(), row_number() without a total order, or floating-point sums whose order changes the last bits. Random sampling must be seeded from something stable (a hash of the row's key), not from a fresh seed per run. Calls to external services (currency rates, geocoding) return different answers over time; snapshot them into a table and join to the snapshot. A good test of determinism is to run a task twice for the same interval and diff the outputs — any difference is a bug waiting to surface during a backfill.

Event-driven and asset-driven scheduling change the failure modes

Time-based schedules fail by running too early on incomplete data. Asset- or event-driven schedules fail differently: storms (a widely used upstream asset updates and triggers hundreds of downstream pipelines at once), loops (a pipeline that rewrites an asset it also depends on), and silent non-runs (an upstream that never publishes means downstream never runs, and no failure is ever raised). The mitigations are the inverse: concurrency limits and debouncing for storms, cycle detection, and freshness deadlines that fire when an expected update has not happened. Most mature platforms mix both: the first layer is time-based with completeness sensors, and everything downstream is asset-triggered with deadlines.

Backfills and model training interact badly

A backfill rewrites feature history with today's code. If a model was trained on the old features and is served with features computed by today's code, that is fine and even desirable — training and serving now agree. But if a model was trained last month on the old version and is re-evaluated today on the new version of the same features, its metrics change without any change to the model. And if a backfill fixed a leakage bug (features accidentally using future data), every model trained before the fix had inflated offline metrics. Treat backfills of ML features as model-affecting events: record feature-table versions with each model (de4's snapshot IDs, de12), and re-evaluate production models after significant backfills.

Exactly-once at the pipeline level

Orchestrators give at-least-once execution: a task may run more than once (retries, manual clears, a worker that dies after finishing but before reporting success, a scheduler failover). Exactly-once effect is achieved by the task, not the orchestrator — through idempotent writes, atomic commits that include a record of what was processed, or deduplication keys. This is the same lesson as Kafka consumers (sc10) and stream processors (de9): delivery is at-least-once, and correctness comes from making repeated effects harmless.

Orchestrator scale is a real constraint

Thousands of DAGs stress the orchestrator itself. The scheduler must parse every DAG file regularly, so top-level code in DAG files that queries a database or lists a bucket slows scheduling for everyone (Airflow's best-practices guide warns against it). The metadata database grows with every task instance; without retention policies it slows the UI and makes upgrades take hours. Many DAGs scheduled at the same minute create bursts. Dynamically generated DAGs make ownership unclear. These are the problems Shopify describes in the case below; they are platform-team concerns, but ML engineers who generate a DAG per model or per experiment can create them quickly.

Choosing between Airflow and Dagster

Airflow's strengths are maturity, a huge library of operators and providers, managed offerings on every cloud, and familiarity — it is the default in most companies. Its model is task-first, with assets added later. Dagster is asset-first: lineage, partitions, staleness, asset checks and partition-level backfills are core concepts, and local development and testing of pipelines as Python code are strong. For an ML platform whose central objects are feature tables, training sets and models, Dagster's model fits naturally; for a company that already runs Airflow at scale, adopting assets and data-aware scheduling within Airflow captures much of the benefit without a migration. Either way, the design rules of this lesson — idempotent interval tasks, overwrite semantics, checks as tasks, deadlines — matter more than the tool.

Testing pipelines before they run in production

Pipelines are code and deserve tests, but the useful tests differ from application tests. Unit-test transformation logic on tiny hand-built inputs, including boundary days (daylight-saving transitions, month ends, empty days). Test the DAG structure itself: that it imports without errors, that schedules and timetables are what you intend, that every task has an owner, retries and a timeout — Airflow's best-practices guide suggests a DAG-loading test in CI. Run the pipeline end to end against a small sample or a staging environment, and test idempotency directly by running the same interval twice and diffing outputs. Finally, treat data checks as tests that run in production on every interval; they catch the problems code tests cannot, because the inputs change daily.

How pipelines fail in production

Ran on incomplete input. A time-triggered job ran before upstream data landed and produced a partial partition; downstream used it. Symptoms: a dip in daily counts, then a "recovery" when someone reran it. Defences: sensors or asset dependencies on upstream completeness, row-count checks against expectation, write-audit-publish.

Duplicates from retries. Append-based writes plus retries or manual reruns. Symptoms: counts doubled for specific days; duplicate keys. Defences: overwrite or merge semantics, uniqueness checks.

Silent empty success. A task read an empty or missing input (a path typo after a refactor, a renamed upstream table) and wrote an empty output successfully. Defences: fail on zero rows when zero is impossible; volume checks.

Timezone and interval bugs. Daylight-saving days with 23 or 25 hours; local-time partition keys; the Airflow 3 timetable change producing empty intervals; off-by-one between inclusive and exclusive interval ends. Defences: UTC everywhere, half-open intervals [start, end), explicit timetables, tests for boundary days.

Backfill side effects. A backfill overloads a production database, triggers hundreds of downstream runs, or rewrites history consumers relied on. Defences: pools and concurrency limits, reading replicas or snapshots, announcements and downstream coordination.

Orchestrator overload. Midnight bursts, slow DAG parsing, metadata database bloat. Defences: schedule spreading, DAG-file hygiene, retention and cleanup (airflow db clean), scaling the scheduler.

What to watch

Per critical output: freshness against its deadline, row counts versus expectation, check results. Per DAG: success rate, retries per run, duration trend (p50 and p95 over weeks), queue time (time between being ready and starting — a sign of capacity problems). Per platform: scheduler loop time, DAG parse time, metadata DB size, tasks queued versus running.

The case: Shopify's Airflow at scale (May 2022)

Shopify's engineering post "Lessons Learned From Running Apache Airflow at Scale" (23 May 2022, by Megan Parker and Sam Wheating) describes Airflow 2.2 running on Kubernetes with the Celery executor and a MySQL 8 metadata database, in an environment with over 10,000 DAGs, about 400 tasks running at any moment, and over 150,000 runs a day. Almost every problem they report is an orchestration-scale version of this lesson.

DAG file access. DAG files were read through a storage-bucket FUSE mount from every pod, generating heavy read load; they moved to an in-cluster NFS server, synced from the bucket, with uploads to production restricted to continuous deployment. Metadata growth. The metadata database grew until the UI slowed and upgrade migrations took hours; they adopted a 28-day retention policy enforced by a cleanup DAG — at the explicit cost of not supporting very long-running backfills — and note that Airflow 2.3 added a db clean command. Ownership. With DAGs generated at deploy time from many repositories, "who owns this DAG?" had no answer; they introduced a per-environment manifest registering each namespace's owners, source and allowed resources, enforced by a cluster policy that rejects DAGs violating their namespace's rules and can add defaults such as timeouts. Schedule clustering. Hand-written crontabs clustered at the top of the hour and at midnight, and generated DAGs added surges; they switched to deterministically randomised schedules seeded by a hash of the DAG ID, which smoothed load noticeably. Resource contention. They manage pools through reviewed configuration rather than admin UI changes, use priority weights to keep critical monitoring DAGs prompt (noting that the default weight rule, which sums downstream tasks, favours large DAGs), and isolate workloads with different needs on separate Celery queues and worker pools.

The common thread: an orchestrator is shared infrastructure whose failure modes come from scale and from many independent authors — so conventions that individual pipeline authors might skip (ownership, timeouts, spread schedules, resource pools) have to be enforced by the platform.

Goal: see how append-plus-retry corrupts a table and how an interval overwrite with a lookback stays correct under retries and late data. Python 3.12 standard library (sqlite3); about 15 minutes.

  1. Create events(event_id, event_date, arrived_date) and daily_counts(event_date, n) in an in-memory SQLite database. Insert 1,000 events for 2026-10-07 that arrived on 10-07, then 30 more for 10-07 that arrived on 10-08 (late).
  2. Write run_append(day, as_of): insert one row into daily_counts with the count of events for day that had arrived by as_of. Write run_overwrite(day, as_of): in one transaction, DELETE the row for day and insert the fresh count.
  3. Simulate a failure after the write: call run_append("2026-10-07", "2026-10-07") three times (two "failed" attempts plus a retry). Print SELECT event_date, SUM(n) FROM daily_counts GROUP BY 1. Reset and do the same with run_overwrite.
  4. Add a lookback: on "10-08", run run_overwrite for both 10-07 and 10-08 with as_of="2026-10-08". Print the counts again.
  5. Try next: write run_since_last() that counts events with arrived_date greater than a stored high-water mark, and show that rerunning it for an old day gives a different answer.

What to look for. The append version reports 3,000 for 10-07 after the retries; the overwrite version reports 1,000 however many times it runs. After the lookback, 10-07 becomes 1,030 — the late events were folded into the right day. The "since last run" version is the anti-pattern: its output depends on when it ran, so a backfill cannot reproduce history.

Design: a reliable daily training-data pipeline

A recommendation team retrains daily on impressions joined to click labels and features. Today: a cron job at 01:00 UTC runs a Spark script that appends "impressions since the last run" to training_rows, joining clicks that have arrived so far. Problems reported: some days have duplicate rows; click rates for recent days look low and then "improve" in later analyses; a feature bug found last week required a six-month recompute nobody knows how to run; and the data scientist found out about a failed run from a stale dashboard. Redesign the pipeline: orchestration, task semantics, late data, backfill path and alerting.

Answer

Task semantics. Replace "since the last run" with an explicit interval. Each run is for impression date D and writes partition D of training_rows by atomic overwrite (Iceberg overwrite-by-filter or dynamic partition overwrite). Inputs are the impressions partition D and the clicks with event time in [D, D + label window), plus point-in-time features as of each impression (de12). Retries and reruns then converge; duplicates disappear.

Late data and label maturity. Clicks arrive late and a click label needs a window (say, a click within 1 hour of the impression; late arrivals up to 48 hours). So D's training rows are not final until D + 1 h + 48 h. Schedule the first build of D at D+1 03:00 for monitoring, and rebuild D, D−1 and D−2 on each run (a 3-day lookback). Training reads only partitions older than the lookback (D ≤ today − 3), so models never train on immature labels. That explains the "low then improving" click rates — they were reading immature days.

Orchestration. An Airflow (or Dagster) DAG with an explicit timetable: sensors or asset dependencies on the impressions and clicks partitions being published; the build task; write-audit-publish with checks (row count within the weekday's historical band, uniqueness of impression ID, label rate within bounds, null rates of key features); publish; then the training DAG triggered by the published asset, not by the clock. Retries with backoff for the Spark task, an execution timeout at three times its p95 duration.

Backfill path. Because tasks are interval-parameterised and idempotent, the six-month recompute is a backfill of 180 intervals. Size it: if a day takes 15 minutes, sequential is 45 hours; run 6 concurrently in a dedicated pool for about 8 hours, or write a range job that computes all 180 days in one pass. Validate counts against the old partitions, record the new table snapshot, and re-evaluate the production model on the corrected history.

Alerting. A freshness deadline on the published training partition (for example, D ready by D+1 06:00 UTC), via deadline alerts or a table-freshness monitor, routed to the team's channel with a runbook; page only on missed deadlines and failed checks, not on retries.
