An online shop's order service saves each order to PostgreSQL and then, in the next line of code, publishes an OrderPlaced message to Kafka so the warehouse, the email service and the analytics pipeline can react. It works in testing. In production, a deploy restarts pods while requests are in flight; a few hundred orders are committed to the database, but the process dies before publishing. The warehouse never ships them. On another day Kafka is briefly unavailable; the code catches the error, logs it, and moves on — the database has the order, the event stream does not. On a third day two updates to the same order are handled by two pods; the database commits "paid" then "cancelled", but the events are published in the opposite order, so the analytics copy says "paid" forever. Weeks later, the finance team's revenue numbers in the lake disagree with the database by 0.4%, and nobody can say which orders are wrong.

This is the dual-write problem, and it is the reason data engineers distrust application-published events as a source of truth. Two writes to two systems cannot be made atomic from application code, and their order cannot be guaranteed. The same problem appears whenever a database must be copied anywhere — a lake, a search index, a cache, a feature store. For ML it is especially costly: training labels (did this order get refunded?) and features (how many orders did this user cancel?) come from those copies, and silent drift in the copy becomes silent bias in the model.

The fix is to stop asking the application to tell the world what changed, and instead read what changed from the database itself: every database keeps an ordered log of committed changes for its own recovery and replication. Change data capture (CDC) turns that log into a stream of events. de1 introduced it as the best of three extraction methods. This lesson goes inside: how CDC reads PostgreSQL's write-ahead log and MySQL's binlog, what a change event contains, how a copy is bootstrapped with snapshots without locking a live table (Netflix's DBLog algorithm, now in Debezium), how changes are applied to lake tables correctly, the outbox pattern for publishing domain events, schema registries and compatibility modes for evolving schemas, and — the question every senior interview reaches — what delivery guarantees actually hold from a database commit to a row in the lakehouse.

The mental model: a bank's ledger and a branch's photocopy

A bank's head office keeps the ledger: every deposit and withdrawal, in order, each with a sequence number. A branch office wants an up-to-date copy of every account's balance. There are bad ways to do this. The branch could phone the head office every hour and ask for every balance (a full snapshot — expensive and blind to what happened between calls). Or each teller at head office could, after updating the ledger, phone the branch with the change (a dual write — tellers forget, phone lines drop, and two tellers' calls arrive in the wrong order).

The good way: the branch gets a photocopy of the ledger itself, page by page, as it is written. It applies each entry in sequence-number order to its copy of the balances. If the courier delivers a page twice, the branch notices that it has already applied those sequence numbers and skips them. If the courier is delayed, the branch is behind but never wrong. To start, the branch needs one consistent set of balances to apply entries to — a snapshot as of some sequence number — and then applies every entry after that number. That is log-based CDC: the ledger is the write-ahead log, the sequence numbers are log positions, the photocopying service is the CDC connector, and the branch is the lake.

The analogy also shows the three hazards. Head office keeps old ledger pages until every branch confirms it has copied them — if a branch stops confirming, the pages pile up in the head office's archive until it runs out of room (a replication slot filling the disk). If head office changes the format of ledger entries (adds a column for currency), the branch must understand the new format before it arrives (schema evolution and compatibility). And if the courier can deliver a page twice, the branch must make re-applying it harmless (idempotent consumers) — exactly-once delivery is much harder to promise than exactly-once effect.

Where the analogy breaks: a bank ledger records business transactions, but a database's log records low-level row changes, including internal tables and columns that make sense only to the application. When other teams need meaningful business events rather than raw row changes, the outbox pattern lets the application write such events into the database, inside the same transaction, so they travel through the same reliable log.

Three numbers describe every CDC pipeline, and you will meet them throughout the lesson. The log position (an LSN in PostgreSQL) says how far the connector has read and orders every change. The lag — the difference between the database's current position and the connector's confirmed position, in bytes or seconds — says how far behind the copy is and how much log the database is holding for it. And the retention — how much log the database or Kafka keeps — says how long a consumer can be down before it has to start over with a fresh snapshot.

1. Why dual writes fail, precisely

Consider the order service again: db.commit(order) then kafka.send(event). There are four failure shapes. Crash between the writes: the order is committed, the event never sent — the database is ahead. Send fails after commit: same result, unless the code retries forever, which blocks the request. Reverse the order (send, then commit): now a failed commit leaves an event for an order that does not exist. Concurrency: request A commits "paid" at time 1 and request B commits "cancelled" at time 2, but B's send reaches Kafka before A's, so consumers see cancelled then paid and end in the wrong state. No amount of careful coding fixes all four, because there is no transaction spanning PostgreSQL and Kafka. Distributed transactions (two-phase commit across both) exist in theory but are rarely available, slow and operationally fragile. The two practical fixes both make the database the only thing the application writes to: CDC derives events from the database's log, and the outbox writes the event into the database.

2. How log-based CDC reads PostgreSQL

PostgreSQL writes every change to its write-ahead log (WAL) before applying it (db8). Each WAL record has a log sequence number (LSN), a monotonically increasing position such as 0/1A2B3C80. The WAL is physical — it describes changes to pages — so it cannot be consumed directly by outside tools. Logical decoding, available since PostgreSQL 9.4, turns WAL into a stream of row-level changes (this table, this row, these column values) for committed transactions, in commit order, through an output plugin. The built-in plugin is pgoutput (PostgreSQL 10+), which native logical replication uses and which Debezium uses by default.

Two database objects make it work. A publication names the tables whose changes are sent (CREATE PUBLICATION shop_pub FOR TABLE orders, order_items;). A logical replication slot represents one consumer: it records the consumer's confirmed position (confirmed_flush_lsn) and makes the server retain all WAL from the oldest position the consumer might still need (restart_lsn). When the connector restarts, it asks the slot to resume from its last confirmed position; nothing is lost, and changes after the last confirmation are re-sent — the source of at-least-once delivery.

One table setting matters: replica identity. By default, the WAL record for an update or delete carries only the primary key of the old row, so a change event's "before" image contains at most the key. ALTER TABLE orders REPLICA IDENTITY FULL makes PostgreSQL log the whole old row, at the cost of more WAL. Choose FULL when consumers need the previous values (for example, to compute "status changed from paid to cancelled" without a lookup).

The slot is also the main operational risk. WAL is retained until confirmed, so if the connector stops, retained WAL grows at the database's write rate. Debezium's documentation describes a subtler version: a connector capturing a quiet table on a busy database receives no events and so never confirms new positions, while other tables generate WAL that cannot be recycled; the remedy is heartbeats (heartbeat.interval.ms, off by default) that make the connector advance its confirmed position periodically. Worked risk: a database generating 30 GB of WAL an hour with 400 GB free disk survives a stalled slot for about 13 hours. Alert on slot lag (bytes between the current WAL position and the slot's confirmed_flush_lsn) at, say, 50 GB, and set max_slot_wal_keep_size (PostgreSQL 13+) so that a dead slot is invalidated before it takes the database down — after which the connector must re-snapshot.

3. MySQL and other databases

MySQL's equivalent is the binary log (binlog), which replicas read to replicate. For CDC it must be in ROW format (recording each changed row's before and after values, rather than the SQL statement) with full row images. Positions are a binlog file name and offset, or, with GTIDs enabled, a global transaction identifier per transaction, which lets a connector resume correctly even after failing over to a different replica. Retention is time-based (binlog expiry settings), so the risk is the opposite of PostgreSQL's: if the connector is down longer than retention, the binlog it needs is gone and it must re-snapshot. Other databases have their own logs (SQL Server's CDC tables, Oracle's redo logs via LogMiner or XStream, MongoDB's change streams), and Debezium has connectors for many of them; the concepts — position, snapshot plus stream, at-least-once — are the same.

4. The anatomy of a change event

Debezium (version 3.7 as of October 2026) runs as a source connector inside Kafka Connect, Kafka's framework for running connectors, and writes one topic per table by default (shop.public.orders). Each message has a key — the row's primary key — and a value. An update that marks order 81723 as paid looks like this (JSON converter, schema omitted, abridged):

key:   {"id": 81723}
value: {
  "before": {"id": 81723, "status": "placed", "amount": 23.40, ...},
  "after":  {"id": 81723, "status": "paid",   "amount": 23.40, ...},
  "source": {"connector": "postgresql", "db": "shop", "schema": "public",
             "table": "orders", "lsn": 24023128, "txId": 5521,
             "ts_ms": 1791460851000, "snapshot": "false"},
  "op": "u",
  "ts_ms": 1791460851230
}

op is c (create), u (update), d (delete), r (read — a row emitted during a snapshot), or t (truncate). source.ts_ms is when the change was made in the database; the top-level ts_ms is when the connector processed it — their difference is the connector's lag. The before here contains the full old row only because the table has REPLICA IDENTITY FULL. For a delete, after is null; with tombstones.on.delete (true by default) the delete is followed by a tombstone — a message with the same key and a null value — so that Kafka log compaction (which keeps only the latest message per key) can eventually remove the key entirely.

Keying by primary key matters for ordering: Kafka preserves order only within a partition, and the default partitioner sends the same key to the same partition, so all changes to order 81723 are consumed in commit order. Changes to different orders in different partitions can be consumed in any relative order — which is fine for row-level replication and a problem only if a consumer needs cross-row consistency (all rows of one transaction together). Debezium can emit transaction metadata (begin and end markers with event counts) for consumers that need to reassemble transactions. One more subtlety: if a primary key value is updated, Debezium emits a delete for the old key and a create for the new key (plus a tombstone), because the two keys may live in different partitions.

5. Bootstrapping: snapshot plus stream

The log contains only recent changes — WAL is recycled, binlogs expire — so a new copy must start from a snapshot of current state and then apply the stream from exactly the position the snapshot represents. Get the hand-over wrong and you either miss changes (stream starts after the snapshot's point) or apply them twice in a harmful order.

The classic approach (Debezium's default snapshot.mode=initial, used when no stored offsets exist) is a consistent snapshot: create the replication slot (which fixes a starting LSN), open a repeatable-read transaction whose view corresponds to that LSN, SELECT * every captured table and emit each row as an r event, then start streaming from the slot's LSN. It is correct, but for a 3 TB table it means one transaction open for many hours — holding back vacuum on a busy table (db10) and, if anything fails, starting over.

Incremental snapshots remove those limits using the algorithm from Netflix's DBLog paper (Andreakis and Papapanagiotou, 2020), which Debezium adopted in version 1.6. Streaming starts immediately. The table is read in small primary-key chunks (Debezium's default chunk is 1,024 rows), and each chunk is bracketed by watermarks written into the change log itself:

  1. Write a low watermark to the log (Debezium inserts a row into a signalling table, which appears in the change stream).
  2. SELECT the next chunk: rows with primary key between the last chunk's end and the next 1,024 keys. Hold the result in memory.
  3. Write a high watermark to the log.
  4. Continue streaming. For every change event that appears in the log between the low and high watermarks, if its key is in the held chunk, remove that row from the chunk — the log event is at least as new as the selected row, and it will be emitted in its proper place.
  5. When the high watermark arrives in the stream, emit the remaining chunk rows as r events, then move to the next chunk.

A trace with keys 1–4 in a chunk. Low watermark at log position 100. The select returns rows 1, 2, 3, 4 with their values as of the select. Meanwhile, at position 105, row 3 is updated, and at 108 row 9 (outside the chunk) is inserted. High watermark at 110. Streaming emits the update to row 3 at 105 and the insert of row 9 at 108 as normal events. At 110, the chunk is emitted minus row 3: rows 1, 2, 4. Row 3's correct latest value came from the log; if the chunk's (older) copy of row 3 had been emitted after the update, the copy would have gone backwards. No locks were taken, the chunk can be retried if the connector crashes, and a snapshot of one table can be triggered later (a newly added table, or a re-sync after a bug) by sending an execute-snapshot signal.

6. Applying changes to the lake

A CDC topic is not yet a table. Landing and applying it usually follows the layers of de1.

Bronze: append every event, as received, to a raw table partitioned by arrival date — including duplicates. This is the replayable record.

Silver current-state table: one row per primary key, the latest version. Each micro-batch (say every 5 minutes): (1) take the new events; (2) deduplicate by primary key, keeping the event with the highest log position (LSN for PostgreSQL; binlog file and position or GTID order for MySQL) — not the highest timestamp, which can tie or skew; (3) MERGE into the target: if the winning event is a delete, delete the row; if the key exists, update it; otherwise insert. To be idempotent under replays, store the applied log position in each row and apply an event only if its position is greater than the stored one (WHEN MATCHED AND s.lsn > t.lsn THEN UPDATE). Then a batch processed twice, or an older event delivered late, changes nothing.

Silver history table: every version of every row with valid_from and valid_to timestamps (from source.ts_ms) — a type 2 slowly changing dimension, which de10 builds properly. This is what point-in-time features and labels (de12) are computed from: "what was this order's status at 14:05?"

Two practical cautions. Merges are expensive on lake tables: each one rewrites or marks the files containing affected keys, so commit in batches of minutes, use merge-on-read with deletion vectors, and compact (de4). And snapshot (r) events and streamed events for the same key can interleave around the hand-over; the position-based rule handles it if snapshot rows carry the position at which they were read.

7. The transactional outbox

CDC on business tables gives other systems the database's internal structure: every column, every internal status code, every table split the service team made for its own reasons. That is fine for replicating into the lake under a contract, but poor as an API between services: renaming a column in the order service breaks every consumer.

The outbox pattern separates the two. The service adds an outbox table with columns such as id, aggregate_type (Order), aggregate_id (81723), type (OrderPaid) and payload (a versioned JSON or Avro document designed for consumers). In the same transaction as the business change, it inserts an outbox row:

BEGIN;
UPDATE orders SET status = 'paid', paid_at = now() WHERE id = 81723;
INSERT INTO outbox (id, aggregate_type, aggregate_id, type, payload)
  VALUES (gen_random_uuid(), 'Order', '81723', 'OrderPaid',
          '{"orderId": 81723, "amount": 23.40, "paidAt": "2026-10-08T12:00:51Z"}');
COMMIT;

Either both rows commit or neither does — atomicity comes from the database's own transaction. A CDC connector captures inserts on the outbox table, and Debezium's outbox event router (a single message transform, or SMT — a small per-message transformation inside Kafka Connect) routes each row to a topic per aggregate type (outbox.event.Order), keyed by aggregate_id so events for one order stay in order, with the payload as the message. Outbox rows can be deleted right after insert (the WAL still carries the insert) or cleaned periodically. Consumers receive explicit, versioned domain events; the service can refactor its tables freely as long as it keeps producing the same events. The costs: extra writes in every transaction and the discipline of designing event payloads as a public contract.

8. Schemas, registries and compatibility

Change events have schemas, and schemas change: the order service adds currency, drops legacy_flag, widens amount. Consumers need to know how to decode each message and need protection from changes that would break them.

A schema registry (Confluent Schema Registry and compatible alternatives such as Apicurio, or cloud equivalents like AWS Glue Schema Registry) stores each topic's schemas as numbered versions. Producers using Avro, Protobuf or JSON Schema serializers register the schema they write and embed its small numeric ID in each message (with Confluent's format, a magic byte plus a 4-byte ID before the payload); consumers fetch the schema by ID and decode. Messages stay compact — no field names on the wire — and every message is decodable forever, because its exact writer schema is retrievable.

When a producer registers a new version, the registry checks it against a compatibility mode:

ModeGuaranteeAllowed (Avro)Upgrade first
BACKWARD (Confluent default)New schema can read data written with the previous oneDelete fields; add fields with defaultsConsumers
FORWARDPrevious schema can read data written with the new oneAdd fields; delete fields that had defaultsProducers

*_TRANSITIVESame, against all previous versions, not just the last——
NONENo checksAnythingCoordinate manually

The Confluent documentation explains why BACKWARD is the default for Kafka: it lets consumers rewind to the beginning of a topic and read old messages with the newest schema. For CDC topics feeding a lake, where bronze is replayed from the start, BACKWARD_TRANSITIVE is the safest choice — the current reader can decode every historical event.

CDC adds a twist: the producer's schema is derived from the source table's DDL, so a database migration is a schema change. A column added as nullable maps to an optional field with a null default — BACKWARD compatible. A column dropped — compatible under BACKWARD, but downstream jobs that select it now read nulls. A rename looks like a drop plus an add: the registry may accept it, and every downstream query using the old name silently breaks. A type change from integer to string is usually rejected. The safe discipline is the expand-and-contract of db14: add the new column, populate it, migrate consumers, and only then drop the old one — coordinated with the teams downstream, ideally enforced by a data contract check in the source team's CI (de11).

9. Delivery guarantees, end to end

Walk the path from a commit to a row in the lakehouse and ask at each hop what can be lost, duplicated or reordered.

  1. Database → connector. Nothing committed is lost while the slot (or binlog) retains it. On restart the connector resumes from its last stored offset, which lags what it had actually published, so recent changes are re-sent: at-least-once. Uncommitted transactions are never emitted.
  2. Connector → Kafka. Producer retries can duplicate messages unless the producer is idempotent (Kafka's idempotent producer is on by default in modern clients, removing retry duplicates within a producer session). Since KIP-618 (Kafka 3.3), Kafka Connect supports exactly-once for source connectors: records and source offsets are written in one Kafka transaction. Debezium's documentation says it can use this, while noting that it does not implement its own deduplication and that the correctness of Kafka's exactly-once in all edge cases has not been comprehensively verified.
  3. Kafka → sink. The sink reads, writes files, commits the table, and records offsets. If it crashes after committing data but before recording offsets, it re-reads and re-applies. Table formats let a writer store its consumed offsets inside the same commit (Delta's txn action, Iceberg snapshot properties, de4), so data and progress advance atomically.
  4. Apply semantics. Even with every hop exactly-once, a reprocessing job, a re-snapshot or a manual replay will deliver events again. The MERGE by key with a log-position guard (section 6) makes duplicates and stale events no-ops.

So the defensible claim in a design review is: at-least-once delivery with per-key ordering, made into an exactly-once result by idempotent, position-aware application and atomic commit of data with offsets. Exactly-once transport features reduce how often the idempotency is exercised; they do not replace it.

10. A worked sizing

The shop's PostgreSQL handles 2,000 row changes per second at peak across captured tables (about 500 on average), generating 30 GB of WAL an hour in total. Change events average 1.5 KB in JSON with full before images, or about 400 bytes in Avro with a registry. At peak: 2,000 × 400 B = 0.8 MB/s into Kafka; per day at average rate, 500 × 86,400 × 400 B ≈ 17 GB. Kafka with 7 days of retention holds about 120 GB per replica — trivial for a cluster. Twelve partitions for the orders topic leaves each partition under 200 events per second at peak. The sink applies every 5 minutes: about 150,000 events per batch, deduplicated to perhaps 100,000 keys, merged into an Iceberg table of 400 million rows with merge-on-read deletion vectors; hourly compaction keeps read performance stable. The slot alert fires at 50 GB of lag (under two hours of WAL at peak), with max_slot_wal_keep_size at 300 GB as the last line of defence for a disk with 400 GB free.

Why commit order is the only order that matters

A database executes transactions concurrently, but its log records them in commit order, and that order is the one serial history consistent with what readers of the database saw. Timestamps from the application (updated_at) do not have this property: two transactions can set timestamps in one order and commit in the other, and clocks on different application servers disagree. That is why position-based ordering (LSN, binlog position, GTID sequence) is the right tiebreaker in merges, and why "latest by updated_at" deduplication is subtly wrong under concurrency. It is also why CDC makes "replay to time T" well-defined: applying the log up to a position yields exactly the state the database had when that position committed.

Replica sources, failover and position continuity

Reading CDC from a replica protects the primary, but positions must survive failover. In MySQL with GTIDs, a connector can resume against a promoted replica because GTIDs identify transactions globally. In PostgreSQL, logical replication slots historically existed only on the primary and were not carried over on failover, so a failover meant a new slot and a re-snapshot or a gap; PostgreSQL 17 added failover slots that can be synchronised to standbys. Whatever the database, test failover with CDC running before you need it: a gap in the change stream is silent until someone reconciles counts.

Large transactions, TOAST and other edge cases

A single transaction that updates 50 million rows (a backfill in the source database, db14) produces 50 million change events at once, all with the same commit position; consumers must cope with the burst, and logical decoding may spill large transactions to disk on the server. PostgreSQL stores large column values out of line (TOAST); with the default replica identity, an update that does not touch a toasted column does not include its value in the WAL, and Debezium emits a placeholder for "unchanged toasted value" that the sink must treat as "keep the existing value", not overwrite with the placeholder. Truncates, schema changes mid-transaction, and generated columns each have connector-specific behaviour. The lesson for a design review: read the connector's "behaviour when things go wrong" and data-type mapping sections for your source, and test with production-like data.

CDC versus event sourcing versus outbox

Three patterns get confused. CDC captures state changes the database already makes; the database's tables remain the source of truth, and events are a derived stream of row changes. Event sourcing makes the event log itself the source of truth: state is computed by folding events, which gives perfect history but makes queries and schema evolution harder (sc10 discussed its costs). The outbox sits between: tables remain the truth, and the application additionally records intent-level events in the same transaction. For data platforms, CDC is the default for ingestion; outboxes are for inter-service contracts; event sourcing is an application architecture decision that data engineers inherit rather than choose.

Exactly-once claims deserve scepticism

Kafka's exactly-once semantics (idempotent producers and transactions, KIP-98, and for Connect sources KIP-618) are real and useful, but they cover a defined scope: Kafka-to-Kafka processing and writes into Kafka with offsets. They do not make an external sink exactly-once, they depend on correct configuration on producers, brokers and consumers (consumers must read with isolation.level=read_committed), and Debezium's own documentation notes that independent testing of transaction correctness in Kafka-compatible systems has found bugs. A senior answer separates transport guarantees from end-to-end effects and puts the burden of correctness where it can be verified: idempotent writes keyed by a stable identifier and a monotonic position.

Reconciliation is part of the design

Even a well-built CDC pipeline should be checked against its source. Periodically compare counts and checksums of key ranges between the source table (or a replica) and the lake copy — for example, count and sum of a hash of each row's columns per range of primary keys — and investigate any mismatch. This catches gaps from slot invalidations, misapplied events, connector bugs and manual edits to the lake. Netflix's DBLog design explicitly supports re-selecting specific primary keys or ranges for exactly this kind of repair: a reconciliation job that finds mismatched ranges can trigger targeted re-snapshots rather than re-copying whole tables.

Choosing what to capture

Capturing every table of every service is tempting and expensive: each captured table adds WAL decoding work, topics, schemas to govern and merges to run, and it couples downstream consumers to internal tables nobody promised to keep stable. A better default is to capture the tables that analytics and ML actually need, agree a data contract for each (owner, schema policy, freshness, deletion semantics), and add tables on request. Wide tables with large text or JSON columns deserve particular thought — exclude columns consumers do not need (Debezium supports column include and exclude lists), both to save bytes and to keep sensitive data out of the stream in the first place.

How CDC pipelines fail in production

Slot-induced disk exhaustion. The connector is down, misconfigured or idle on its tables; the slot retains WAL; the primary runs out of disk. Symptoms: rising pg_wal size, slot lag growing in pg_replication_slots. Defences: slot lag alerts, heartbeats, max_slot_wal_keep_size, dropping abandoned slots, runbooks to re-snapshot.

Snapshot pain. Initial snapshots of large tables take hours, hold long transactions (blocking vacuum, bloating tables) and restart from scratch on failure. Defences: incremental snapshots, reading from replicas, throttling, and scheduling large snapshots off-peak.

Schema change breakage. A migration renames or retypes a column; the registry rejects the new schema and the connector stops (good) or accepts it and downstream queries return nulls (bad). Defences: compatibility modes, contract checks in the source repository's CI, expand-and-contract migrations, and alerts on connector failure and on null-rate jumps downstream.

Duplicates and reordering downstream. Merges keyed on timestamps rather than positions, topics not keyed by primary key, re-snapshots applied over newer data. Symptoms: rows in older states than the source, duplicate keys in "current" tables. Defences: position-guarded merges, uniqueness checks, reconciliation.

Lag. Connector throughput below the source's change rate at peak (often from large transactions or slow serialisation), or sink merges taking longer than their interval. Symptoms: growing difference between source.ts_ms and processing time; Kafka consumer lag. Defences: monitoring end-to-end lag, partitioning, batching merges, merge-on-read.

What to watch

Source: replication slot lag in bytes, WAL directory size, binlog retention versus connector downtime. Connector: status, restarts, event rate, time since last event per table (with heartbeats, a stall is visible), end-to-end lag (now minus source.ts_ms of the latest applied event). Registry: rejected schema versions. Sink: merge duration, events per batch, duplicates found, row-count and checksum reconciliation results.

The case: Netflix's DBLog (2020)

"DBLog: A Watermark Based Change-Data-Capture Framework" by Andreas Andreakis and Ioannis Papapanagiotou of Netflix (arXiv, October 2020) starts from the problem in this lesson's introduction: applications use several heterogeneous datastores — a relational database plus a search index, a cache, an analytics store — and keeping them in sync with dual writes or distributed transactions is limited in feasibility, robustness and maintainability. CDC from the transaction log is the natural answer, but logs do not contain full history, so every sync also needs the complete current state of each table, and existing approaches to getting it either locked tables, paused log processing during snapshots, or required long-running transactions.

DBLog's contribution is the watermark technique traced in section 5: it interleaves log events with rows selected from tables in chunks, using low and high watermarks written to the log to detect and discard chunk rows that changed concurrently. Selects can cover all tables, one table, or specific primary keys; progress is tracked so selects can pause and resume; log processing never stops; and the method uses no locks and has minimal impact on the source database. The paper reports that DBLog was used in production by tens of microservices at Netflix. Its idea outlived the system: Debezium's incremental snapshots, introduced in Debezium 1.6 in 2021, implement the same algorithm with a signalling table providing the watermarks, and a later Debezium release added read-only incremental snapshots for MySQL — contributed by Shopify — that derive watermarks from the binlog position instead of writing to the source, so they can run against read-only replicas.

The broader lesson is about where correctness comes from. The snapshot is not made consistent by freezing the world; it is made consistent by reasoning about positions in a single ordered log and resolving conflicts deterministically. The same idea — order by log position, make application idempotent — is what makes the rest of a CDC pipeline correct.

Goal: apply a stream of change events to a "lake" table and see why the log position, not arrival order or timestamps, must decide. Python 3.12 standard library; about 15 minutes.

  1. Write a list of change events as dicts: {"key": id, "op": "c"|"u"|"d", "after": {...} or None, "lsn": int}. Use the order history from de1: order 1 created (lsn 10), updated to preparing (lsn 20), order 2 created (lsn 25) and deleted (lsn 30), order 1 updated to picked_up (lsn 40) and delivered (lsn 50).
  2. Write apply_naive(table, events) that processes events in list order: create and update set table[key] = after, delete pops the key.
  3. Write apply_guarded(table, events) that stores (after, lsn) per key and applies an event only if its lsn is greater than the stored one; for deletes, keep a tombstone entry with its lsn so a late older event cannot resurrect the row.
  4. Build three delivery scenarios: in order; with the whole list delivered twice (a replay); and shuffled within each key's events (out of order, as from a badly keyed topic). Apply each with both functions and print the final table.
  5. Try next: add a snapshot read event {"key": 1, "op": "r", "after": {"status": "placed"}, "lsn": 15} arriving last, and check which function keeps order 1 at delivered.

What to look for. Both functions agree for in-order delivery. A replay leaves the naive table correct only by luck of ending on the same events; shuffling makes it end with order 1 in an older state or order 2 resurrected. The guarded version ends with {1: delivered} every time — the position check plus delete tombstones are what make an at-least-once, possibly reordered stream converge to the right answer.

Design: replicating payments into the lakehouse for a fraud model

A payments service runs on PostgreSQL 16 (primary plus one replica). Tables: payments (1.2 billion rows, 900 GB, 1,500 updates per second at peak as statuses change), cards (80 million rows), chargebacks (low volume, but arrives weeks after payments). The fraud team needs (a) point-in-time features such as "declines on this card in the previous hour, as of each payment", (b) labels from chargebacks, and (c) a guarantee that the lake copy matches the source. The payments team also wants other services to react to "payment captured" events without depending on their table schema. Design the ingestion.

Answer

Capture. Debezium PostgreSQL connector with pgoutput, a publication on the three tables, and REPLICA IDENTITY FULL on payments so status transitions carry before images (the extra WAL is acceptable at 1,500 updates per second; measure it). Avro with a schema registry in BACKWARD_TRANSITIVE mode. Topics keyed by primary key so each payment's changes stay ordered. Heartbeats enabled; slot lag alert at a level that leaves hours of disk headroom; max_slot_wal_keep_size as the backstop. Because PostgreSQL 16 does not synchronise logical slots to standbys (failover slots arrived in 17), document the failover runbook: a new slot and a targeted incremental re-snapshot.

Bootstrap. An incremental snapshot of payments in primary-key chunks running alongside streaming, throttled; at an assumed 40 MB/s it takes about 6–7 hours for 900 GB, with WAL retained meanwhile — check disk headroom first.

Apply. Bronze: raw events appended. Silver: payments_current via 5-minute MERGE guarded by LSN, merge-on-read with hourly compaction; payments_history with valid-from/valid-to from source.ts_ms — the basis of point-in-time features ("declines in the previous hour as of payment time" is a range query over history, de12). Chargebacks are tiny; same pipeline, and they become labels joined to payments by payment ID with the label's own timestamp, so training sets only use chargebacks known by the label cut-off date.

Events for other services. Add an outbox table; the payments service inserts a PaymentCaptured event in the same transaction as the status change; the outbox event router publishes to outbox.event.Payment keyed by payment ID. Other services consume that contract, not the CDC topics.

Guarantee. At-least-once delivery with idempotent, LSN-guarded merges, offsets committed with each table commit. A nightly reconciliation job compares row counts and hash sums per primary-key range between the replica and payments_current; mismatched ranges trigger a targeted incremental snapshot of those keys. Alert on end-to-end lag (now minus the latest applied source.ts_ms) above, say, 15 minutes.
