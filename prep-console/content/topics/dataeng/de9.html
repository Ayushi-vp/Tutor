A payments company runs a fraud model at checkout. One of its strongest features is "how many declined payments has this card had in the last ten minutes". Fraudsters testing stolen cards produce bursts of declines in minutes, so a feature computed by the nightly batch job is useless — by morning the card has been drained. So the team builds a streaming job: read payment events from Kafka, count declines per card over a sliding ten-minute window, and write the count to the online feature store, where the model reads it at checkout.

The first version counts events by the time the job sees them. It looks fine until a Kafka broker restart causes a four-minute backlog: when the job catches up, it sees eight minutes of events in two minutes and every card's count spikes; the model blocks hundreds of good customers. The second version counts by the event's own timestamp, but then the question becomes: when is the ten-minute window from 12:00 to 12:10 finished? Events from 12:09 are still arriving at 12:11 from phones on slow networks. Wait too long and the feature is stale; emit too early and it is wrong. The third version handles that, and then the job crashes during a deploy. When it restarts, should it re-read the last hour from Kafka? Then counts double. Start from now? Then a few minutes of declines vanish — exactly the minutes an attacker would exploit.

Those three problems — which clock, when is a window complete, and how to recover without losing or double-counting — are the whole subject of stream processing, and they are why streaming is harder than batch. sc18 introduced the vocabulary. This lesson builds the mechanisms: event time and processing time; tumbling, sliding and session windows; watermarks, traced event by event; late data and allowed lateness; keyed state and how big it gets; checkpoints and the barrier algorithm behind them; what end-to-end exactly-once really requires; stream joins; and how Flink, Kafka Streams and Spark Structured Streaming each implement all of this. The case is the paper that unified the model, Google's Dataflow Model (VLDB 2015).

The mental model: counting ballots that arrive by post

An election office counts ballots per polling day. Ballots are stamped with the date they were cast — their event time — but they arrive by post, so the office receives them over the following days — their processing time. Counting "ballots received today" would be meaningless: a postal strike would shift thousands of votes into the wrong day. So the office counts by the stamped date. That is the first idea: compute by event time.

Then the office must decide when a day's count is final. From experience, 99.9% of ballots arrive within three days of being cast. So the office declares: "once we are three days past a date, we consider that date complete" — a watermark. The count for Monday is announced on Thursday. A ballot for Monday that turns up on Friday is late; the office has a rule for it: count it and issue a correction (allowed lateness), file it separately for audit (a side output), or discard it. A shorter wait announces sooner but more often needs corrections; a longer wait is more complete but slower. That trade-off never goes away.

The office keeps running tallies per district — its state. If the office floods overnight, it cannot recount the ballots it already shredded, so every evening it photocopies the tallies and notes exactly which sacks of post had been opened by then — a checkpoint. After the flood, it restores the photocopied tallies and re-opens only the sacks received after that note, so nothing is lost and nothing is counted twice. And it announces results only after the evening's photocopy is safely stored, so it never has to retract an announcement because of a flood — an exactly-once sink.

The analogy breaks in scale and speed: a stream processor does this for millions of keys, thousands of times per second, with windows of seconds, and the "photocopy" of its tallies may be hundreds of gigabytes. But every mechanism in this lesson is one of these office rules, made precise.

Before the details, fix the three questions every streaming design must answer, because the rest of the lesson is organised around them. Which clock? — group by event time, so results do not depend on delays. When is a window done? — when the watermark says so, with an explicit policy for stragglers. How do we survive failure? — consistent checkpoints of state plus source positions, and sinks that make replays harmless. A design that answers all three precisely will work on any engine; a design that leaves one vague will produce numbers that are wrong in ways nobody notices until a model or an invoice depends on them.

One more framing helps. A stream processor is not a different kind of computation from a batch job; it is the same computation run incrementally. A daily batch job that counts declines per card per day and a streaming job that counts them per 10-minute window are the same aggregation over different windows, run at different times. That is why the same event-time definitions should be used in both — and why mismatches between them are bugs, not inevitable differences.

1. The streaming model

A stream processor runs a dataflow: a graph of operators (source, parse, filter, key by, window, aggregate, sink) through which records flow continuously. Each operator runs as several parallel instances. Records are routed between instances by key — all events for card 4417 go to the same instance of the windowing operator — so per-key computation needs no coordination. This is the same partitioning idea as a batch shuffle (de5), except that it never ends: the "shuffle" is a permanent network connection between operator instances.

Two things are fundamentally different from batch. The input is unbounded: there is no "end of the data" at which to compute a total, so every result must be defined over some finite piece of the stream — a window. And the job is long-running: it must survive failures, deploys and rescaling without losing or duplicating its work, which means its in-flight state must be durable. Everything in this lesson follows from those two facts.

2. Event time and processing time

Event time is when something happened, recorded in the event: the payment's authorisation timestamp, the click's client timestamp. Processing time is when the stream processor handles the event. The difference — the event's lateness — has many causes: mobile clients buffering while offline, network delays, collectors batching, Kafka producers retrying, consumer backlogs after a restart, and deliberate replays of old data. Measured on real mobile event streams, most events arrive within seconds, but a long tail arrives hours or even days late.

A computation keyed on processing time — "count events seen in this minute" — is simple and has no completeness problem (a processing-time minute is over when the clock says so). But its answer depends on delays: a four-minute backlog shifts four minutes of events into the minute the job catches up, and replaying the same data tomorrow gives a different answer. A computation keyed on event time gives the same answer however the data is delayed or replayed — which is what correctness means for features, metrics and billing — at the price of having to decide when a window of event time is complete. Use processing time only for operational concerns (timeouts, rate limiting, "emit at least every 10 seconds").

3. Windows

A window groups events by event time into finite pieces. Three shapes cover most needs.

Tumbling windows are fixed-length and non-overlapping: [12:00, 12:05), [12:05, 12:10), and so on. Each event belongs to exactly one. Use them for periodic metrics: payments per merchant per 5 minutes.

Sliding (hopping) windows have a fixed length and a slide smaller than the length: length 10 minutes, slide 1 minute gives windows [12:00, 12:10), [12:01, 12:11), …. Each event belongs to length ÷ slide = 10 windows. Use them for "in the last N minutes, updated frequently" features. Their cost is that multiplication: a naive implementation keeps and updates 10 window aggregates per key per event. A cheaper equivalent for decomposable aggregates keeps per-key counts in 1-minute buckets and sums the last 10 buckets when emitting.

Session windows are per key and close after a gap of inactivity: if a user's events are at 12:00, 12:04, 12:09 and 12:50 with a 30-minute gap, the first three form one session [12:00, 12:39) (the last event plus the gap), and 12:50 starts another. Sessions have variable length and can merge when a late event bridges two of them.

A worked count. Card 4417 has declines at event times 12:00:20, 12:03:10, 12:07:45 and 12:11:30. With tumbling 5-minute windows: [12:00, 12:05) has 2, [12:05, 12:10) has 1, [12:10, 12:15) has 1. With sliding 10-minute windows every minute: the window [12:02, 12:12) has 3 (12:03:10, 12:07:45, 12:11:30), and [12:00, 12:10) has 3 (12:00:20, 12:03:10, 12:07:45) — the feature value an online model sees at 12:12 should be the former.

4. Watermarks

When is the window [12:00, 12:05) complete? Never, strictly — a phone could be offline for a week. A watermark is the engine's working answer: a timestamp W flowing through the dataflow that asserts "no more events with event time earlier than W are expected". When the watermark passes a window's end, the window is considered complete: its result is emitted and its state is freed.

The common way to generate watermarks is bounded out-of-orderness: watermark = maximum event time seen so far − delay. Flink's WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(30)) and Spark's withWatermark("ts", "30 seconds") both express this. The delay is chosen from the measured lateness distribution: if 99.9% of events arrive within 30 seconds of the newest event time, a 30-second delay finalises windows 30 seconds after their end and leaves 0.1% of events late.

Watermarks across parallel inputs. An operator receiving from several upstream instances (several Kafka partitions) takes the minimum of their watermarks, because it may only assert "nothing earlier is coming" if it is true of every input. Flink's documentation describes the operator's event time as the minimum over all parallel input watermarks. Two consequences matter in production. A slow partition (lagging consumer, skewed key) holds back the watermark for the whole job, delaying every window. And an idle partition — one receiving no events at all — never advances its watermark and stalls the job entirely; Flink's withIdleness(Duration) marks a source idle after a timeout so it is excluded from the minimum. Spark Structured Streaming similarly takes the minimum across multiple input streams by default (spark.sql.streaming.multipleWatermarkPolicy=min; max trades correctness for progress).

The Spark guide states the guarantee precisely: a watermark delay of two hours "guarantees that the engine will never drop any data that is less than 2 hours delayed", and the guarantee is strict only in that direction — data more delayed may or may not be aggregated. That asymmetry is true of watermarks generally.

5. Late data and triggers

An event behind the watermark is late. There are three policies, chosen per use case.

Drop (the default in most engines): simplest; count the drops as a metric so you know when the delay is too short.

Allowed lateness: keep a window's state for an extra period after the watermark passes its end, and re-emit an updated result when late events arrive. Flink's default allowed lateness is zero; with one minute, the window [12:00, 12:05) is kept until the watermark reaches 12:06 and each late event triggers an updated result. Downstream must accept updates — an upsert keyed by window, not an append.

Side output: route late events to a separate stream (Flink's sideOutputLateData), for example into the lake, so a batch job can reconcile later. This is the bridge to the batch lookback of de7: streaming gives fast, mostly-complete results; batch fixes them up.

When a window emits is decided by its trigger. The default is "when the watermark passes the end" (plus each late event within allowed lateness). Early triggers emit speculative partial results before the window is complete — "every 10 seconds of processing time, emit the count so far" — so a dashboard updates live and the final value arrives at the watermark. Spark expresses the downstream side of this with output modes: append writes each window once, when the watermark finalises it; update writes rows that changed in each micro-batch (including partial window results); complete rewrites the whole result table (only practical for small results).

6. Keyed state and how big it gets

Anything a streaming operator must remember between events is state: a window's running count, the events of an open session, the buffered rows of a stream join, a deduplication set of recently seen IDs, a model's per-user features. Almost all of it is keyed state — scoped to a key and stored in the operator instance that owns that key.

State lives in a state backend. Flink offers a heap-based backend (state as Java objects in memory — fastest, limited by heap, the default if nothing is configured), an embedded RocksDB backend (state serialised in a local LSM-tree key-value store on disk, db5 — slower per access but scales to state far larger than memory), and ForSt, a newer backend designed for disaggregated state stored remotely. Kafka Streams keeps state in local RocksDB stores, each backed by a compacted Kafka changelog topic from which it can be rebuilt. Spark Structured Streaming keeps state per partition in a state store (HDFS-backed by default, with a RocksDB option) checkpointed with each micro-batch.

Size it before you build it. The fraud feature: "declines per card in the last 10 minutes, every minute".

  • Naive sliding windows: each card with activity keeps up to 10 open window aggregates. If 2 million cards are active within any 10-minute span, that is 20 million window states. At roughly 100 bytes each in RocksDB (key, window, count, overhead), about 2 GB — fine.
  • A one-hour window with 1-minute slides: 60 windows per card, about 12 GB — still fine, but checkpoints grow.
  • A stream-stream join that buffers both sides for one hour at 5,000 events per second per side, 500 bytes each: 2 × 5,000 × 3,600 × 500 B = 18 GB of buffered rows.
  • Deduplicating events by ID over 24 hours at 50,000 events per second with 40-byte entries: 50,000 × 86,400 × 40 B ≈ 173 GB — at which point an approximate structure (a Bloom filter per hour) is worth considering.

State must be bounded. Event-time windows are cleaned up by the watermark (if the watermark stalls, state grows without bound — a classic production failure). Per-key state that is not windowed needs a TTL so keys that go quiet expire (Flink's StateTtlConfig, Spark's state timeouts). Aggregate rather than buffer: keep a count, not the list of events.

7. Checkpoints: consistent snapshots of a running dataflow

A stream job's state is spread across hundreds of operator instances on many machines, changing thousands of times a second, while records are in flight between them. To survive failures, the job needs snapshots that are consistent: every operator's state must reflect exactly the same set of input records, and the snapshot must record which input positions those were, so that after a restore, replaying input from those positions neither skips nor repeats any record's effect.

Flink's answer, described by Carbone and colleagues in "Lightweight Asynchronous Snapshots for Distributed Dataflows" (2015), adapts the Chandy-Lamport distributed snapshot algorithm. Periodically (every few seconds to minutes) the coordinator asks each source to inject a barrier numbered n into its output streams and to record its current position (Kafka offsets) in checkpoint n. Barriers flow downstream with the records, never overtaking them. When an operator has received barrier n on an input, records after it on that input belong to the next checkpoint; in aligned mode, the operator buffers those records until barrier n has arrived on all its inputs. Then it snapshots its state — asynchronously, copying to durable storage (object storage, HDFS) without stopping processing — and forwards barrier n. When every operator, including sinks, has acknowledged, checkpoint n is complete.

On failure, the job restarts every operator with the state from the latest completed checkpoint and rewinds sources to the offsets recorded in it. Records after those offsets are processed again, but against state that does not yet include them — so their effect on state happens exactly once. Recovery time is roughly: detect the failure, reschedule, load the state (seconds for gigabytes from local or fast storage, minutes for hundreds of gigabytes from object storage), then catch up on the input that accumulated since the checkpoint.

Two refinements matter at scale. Incremental checkpoints (with RocksDB) upload only the files changed since the last checkpoint rather than the whole state, which makes frequent checkpoints of large state affordable. Unaligned checkpoints address backpressure: when an operator is slow, records pile up in network buffers and an aligned barrier waits behind them, so checkpoints take as long as the backlog to drain and may time out. Unaligned checkpoints let barriers overtake buffered records and store those in-flight records as part of the checkpoint, decoupling checkpoint time from backpressure at the cost of larger checkpoints. Flink also has savepoints: manually triggered, portable checkpoints used to upgrade job code, change parallelism or migrate clusters while keeping state.

8. Exactly-once, end to end

Checkpoints make state exactly-once. The output is another matter: if the sink writes results immediately and the job then fails and replays from the checkpoint, the replayed records produce the same outputs again. End-to-end exactly-once needs all three of:

  1. A replayable source whose position can be stored and rewound — Kafka offsets, files, a table snapshot. (A source that cannot rewind, such as a plain socket, gives at-most-once or at-least-once.)
  2. Consistent state snapshots tied to those positions — checkpoints.
  3. A sink that is either transactional or idempotent.
    • Transactional: the sink writes output within a transaction that stays open during a checkpoint interval and is committed only when the checkpoint completes — a two-phase commit coordinated with the checkpoint. Flink's Kafka sink does this with Kafka transactions; downstream consumers must read with isolation.level=read_committed to avoid seeing uncommitted output. Lakehouse sinks (Iceberg, Delta) commit a snapshot per checkpoint, storing the checkpoint ID in the commit so a replayed commit is recognised.
    • Idempotent: the sink writes with deterministic keys so a replayed write overwrites the same record — an upsert keyed by (card, window end) into a key-value store or database.

The transactional route costs latency: output becomes visible only at checkpoint completion, so a 60-second checkpoint interval adds up to a minute before consumers see results. That is one reason latency-sensitive features are often written with idempotent upserts to an online store rather than through a transactional Kafka sink.

The three engines implement this differently. Flink uses barrier checkpoints and two-phase-commit sinks. Kafka Streams (with processing.guarantee=exactly_once_v2) wraps each batch of processing — consuming offsets, updating state stores and their changelog topics, producing outputs — in one Kafka transaction, which is exactly-once as long as input and output are Kafka. Spark Structured Streaming records each micro-batch's input offsets in a write-ahead log in its checkpoint location before processing and commits the batch ID after the sink write; with a replayable source and an idempotent sink (or a sink such as Delta that records the batch ID with its commit), replays after failure are recognised and skipped.

9. Stream joins

Stream–stream joins match events from two streams, such as ad impressions and clicks on impression_id. Because both streams are unbounded, the engine must buffer each side's events waiting for matches, and without limits the buffers grow forever. Bound them with a time constraint plus watermarks: "a click matches an impression if the click is within 1 hour after the impression". Then once the watermark passes impression time + 1 hour, that impression can no longer match and its state is dropped. Sized earlier: an hour of buffering on both sides at 5,000 events per second is about 18 GB of state. Outer joins (emit impressions with no click) can only emit the unmatched row once the watermark proves no match is coming — so their output is delayed by the join interval plus the watermark delay.

Stream–table joins enrich events with reference data: attach merchant category to each payment. Joining against the current table is easy but not reproducible — replaying last week's payments would use today's categories. A temporal join joins each event with the version of the table valid at the event's time, using a versioned table (often built from a CDC stream, de8) — Flink SQL supports this with FOR SYSTEM_TIME AS OF. For ML features this is the streaming form of point-in-time correctness (de12).

The Dataflow model's four questions

The Dataflow Model paper organises every streaming computation around four questions. What results are computed (the transformation: sums, joins, model features)? Where in event time are they computed (windowing)? When in processing time are results materialised (triggers, driven by watermarks, with early and late firings)? How do refinements relate (accumulation mode: does each new emission replace the previous one, add to it, or retract it and emit a new value)? The power of the framing is that batch is just a special case — a bounded input with a watermark that jumps to infinity at the end — so one program can run in both modes. Apache Beam implements the model; Flink's and Spark's APIs map onto the same questions with different defaults. In an interview, answering a streaming design question in these four steps is a reliable structure.

Watermarks are a business decision

The watermark delay trades latency against completeness, and the right point depends on the cost of each error. For a fraud feature, a 30-second delay that leaves 0.1% of declines uncounted is fine — the cost of a slightly low count is small, and staleness is expensive. For billing, completeness dominates: compute a provisional figure with a short delay and a final one with a long delay or in batch. Heuristic watermarks also have a failure mode in the other direction: a source with a wrong clock (a client stamping events in the future) pushes the maximum event time forward, advancing the watermark too fast and making everyone else's events "late". Guard against it by clamping event times that are ahead of processing time, or by generating watermarks per source partition so one bad producer affects only its partition's events.

Rescaling keyed state

Changing a job's parallelism means redistributing keyed state among a different number of instances. Flink avoids rehashing every key by assigning keys to a fixed number of key groups (the job's maximum parallelism) and assigning ranges of key groups to instances; rescaling moves whole key groups. The maximum parallelism must therefore be chosen up front (changing it requires state migration), and should be comfortably above any parallelism you expect to need. Kafka Streams ties state to input partitions, so its maximum parallelism equals the partition count of the input topics — another reason to choose partition counts generously.

Backpressure is the streaming form of skew

When one operator instance cannot keep up — because of a hot key, a slow external call or garbage collection — its input buffers fill, and credit-based flow control slows its upstream instances, and theirs, back to the sources, which then fall behind on Kafka. The job does not fail; it lags. Consumer lag growing while CPU elsewhere sits idle, and one subtask marked busy at 100% in the Flink web UI, is the signature. The fixes mirror de6: find the hot key, pre-aggregate before the keyBy, split hot keys, or move slow external lookups to asynchronous I/O. Backpressure also slows aligned checkpoints, which is where unaligned checkpoints and buffer debloating help.

Streaming into the lakehouse

Writing streams into Iceberg or Delta tables combines this lesson with de2–de4. Each checkpoint (Flink) or micro-batch (Spark) becomes a table commit; frequent commits give fresh data but many small files and snapshots, so commit intervals of one to several minutes plus continuous compaction are typical. Exactly-once comes from recording the checkpoint or batch ID in the commit and skipping duplicates on recovery. For upserts (CDC into a current-state table), merge-on-read with deletion vectors keeps commits cheap. The resulting tables serve both batch training (point-in-time queries over history) and near-real-time analytics, which is the practical meaning of "streaming lakehouse".

Is streaming worth it?

A streaming job is a long-running distributed service with on-call needs: upgrades with savepoints, state migrations, watermark tuning, backpressure, checkpoint storage, and replay procedures. Batch pipelines can be rerun from scratch; streaming jobs carry state you must preserve. Before choosing streaming, quantify the value of freshness (de1): how much better is a decision made with 30-second-old data than with 15-minute-old data from a micro-batch, or hour-old data from batch? Often a 5-minute micro-batch into the lakehouse, or a streaming job for only the handful of time-critical features, captures most of the value at a fraction of the operational cost.

How stream jobs fail in production

Stalled watermark. An idle or lagging partition pins the minimum watermark; windows stop firing; state grows; outputs stop although the job is "healthy". Symptoms: output rate drops to zero, state size climbs, watermark metric frozen. Fixes: idleness detection, per-partition watermarks, alerting on watermark lag (processing time minus watermark).

Unbounded state. Missing TTL on per-key state, session windows that never close for bot keys, joins without time bounds. Symptoms: checkpoint size and duration growing daily, eventually timeouts and failed recoveries. Fixes: TTLs, time-bounded joins, capping per-key buffers.

Checkpoint failures under backpressure. Aligned barriers stuck behind full buffers; checkpoints time out; after enough failures the job restarts and falls further behind. Fixes: remove the bottleneck, unaligned checkpoints, incremental checkpoints, appropriate checkpoint timeouts.

Duplicate or missing output after restarts. Non-transactional, non-idempotent sinks; consumers reading uncommitted Kafka transactions (read_uncommitted); state restored from an older checkpoint than the sink's last commit. Fixes: the end-to-end recipe in section 8.

Clock and time bugs. Events stamped with device time far in the future or past; time zones; seconds versus milliseconds in timestamps. Symptoms: sudden bursts of late data, windows firing early. Fixes: validate and clamp event times at ingestion, count events outside a plausible range.

Deploys that lose state. Changing operator structure without stable operator IDs, or upgrading without a savepoint, starts the job with empty state. Fixes: explicit operator UIDs, savepoint-based deploys, state compatibility tests.

What to watch

Consumer lag per partition; watermark lag; records dropped as late; checkpoint duration, size and failures; state size per operator; backpressure and busy time per subtask; end-to-end latency from event time to sink commit; sink commit rate and duplicates detected downstream.

The case: the Dataflow Model (VLDB 2015)

"The Dataflow Model: A Practical Approach to Balancing Correctness, Latency, and Cost in Massive-Scale, Unbounded, Out-of-Order Data Processing" by Tyler Akidau and colleagues at Google (PVLDB volume 8, 2015) is the intellectual foundation of modern stream processing. It was written from experience with Google's internal systems (MillWheel for streaming, FlumeJava and MapReduce for batch) and the needs of customers such as billing and abuse detection, where data arrives out of order, results must eventually be correct, and the acceptable trade-off between latency, accuracy and cost differs per use case.

The paper argues that the old framing — batch for correctness, streaming for approximate low latency, and Lambda architectures running both — confuses the shape of data (bounded or unbounded) with the execution engine. Its model separates concerns into the four questions of the deep section: windowing by event time, including session windows supported by merging windows; triggers that decide when results are emitted relative to watermarks, with early and late firings; and accumulation modes describing how successive results for the same window relate (discarding, accumulating, or accumulating and retracting). Watermarks are explicitly presented as heuristics that can be too fast (causing late data) or too slow (causing latency), and the model gives users the tools — allowed lateness, late firings, retractions — to handle both.

The ideas spread quickly. Google offered the model as Cloud Dataflow and open-sourced the SDK as Apache Beam; Flink adopted event time, watermarks and triggers as first-class concepts; Spark's Structured Streaming added event-time windows and watermarks; Kafka Streams added windowing with grace periods. The paper is why "streaming can be correct" is now an uncontroversial statement, and why every engine in this lesson speaks the same vocabulary.

A practical runbook habit: before any upgrade, take a savepoint, start the new version from it in a staging environment against a copy of recent input, and compare its outputs with the running job's for the same windows. Most state-compatibility and logic regressions show up within minutes of such a shadow run.

Goal: implement event-time tumbling windows with a bounded-out-of-orderness watermark, and watch the delay trade completeness against latency. Python 3.12 standard library; about 15 minutes.

  1. Generate 10,000 events over 10 minutes of event time (one every 60 ms on average, with random jitter). Give each a lateness drawn from a skewed distribution: 95% between 0 and 2 seconds, 4.9% between 2 and 30 seconds, 0.1% between 30 and 300 seconds. Arrival time = event time + lateness; sort by arrival time.
  2. Write a processor that, for each arriving event, updates max_seen, sets watermark = max_seen − delay, adds the event to its 1-minute window if that window has not fired, otherwise counts it as late, and fires (emits and deletes) every window whose end is ≤ the watermark. Record each window's count and the arrival time at which it fired.
  3. Run with delays of 1 s, 5 s, 30 s and 120 s. For each, print the number of late events and the average firing latency (firing arrival time minus window end).
  4. Compare the emitted counts with the true counts per window (count by event time over all events).
  5. Try next: add a second "partition" whose events stop after minute 3 and compute the watermark as the minimum over both partitions — watch firing stop.

What to look for. With a 1-second delay, windows fire about a second after they end but several percent of events are late. With 30 seconds, late events fall to roughly the 0.1% tail and firing latency rises to about 30 seconds. With 120 seconds, almost nothing is late and every result is two minutes stale. The idle-partition variant reproduces the stalled-watermark incident: no window after minute 3 ever fires.

Design: real-time click-through features with a training/serving guarantee

An ads team wants a feature "click-through rate of this ad in the last 30 minutes", served online at bid time and used in training. Inputs: an impressions topic (40,000 events per second) and a clicks topic (800 per second), both in Kafka with 64 partitions, keyed by ad ID; clicks arrive up to 10 minutes after their impression, and 0.5% of events arrive more than 2 minutes late. There are 2 million active ads. Design the job: windows, watermarks, state, sink, recovery, and how training gets consistent values.

Answer

Semantics. CTR = clicks ÷ impressions per ad over a sliding 30-minute event-time window, emitted every minute. Count clicks by click event time and impressions by impression event time (the feature asks about recent activity, not attributed CTR); attributed CTR — clicks joined to their impressions — would need a stream–stream join with a 10-minute bound and belongs in training labels, not this feature.

Windows and state. Implement the sliding window as 1-minute tumbling buckets per ad with a ring of 30 buckets, holding two counters each. State: 2 million ads × 30 buckets × 2 counters, about 120 million small values — on the order of 10 GB in RocksDB with overhead, checkpointed incrementally every minute. TTL of 31 minutes per bucket so idle ads vanish.

Watermarks. Bounded out-of-orderness of about 2 minutes leaves roughly 0.5% of events late; for a ranking feature that is acceptable — count late events into the current bucket (processing-time fallback) or drop them with a metric. Mark partitions idle after 30 seconds without data so a quiet partition does not stall everything. Alert on watermark lag above 5 minutes.

Sink. Every minute, upsert (ad ID → CTR, impression and click counts, window end) into the online feature store. The upsert is idempotent, so replays after recovery rewrite the same values — exactly-once effect without transactional latency. Also write the same records to an Iceberg table every few minutes for analysis.

Recovery. Checkpoints every 60 seconds with Kafka offsets; on failure, restore state and replay at most about a minute of input (40,000 × 60 ≈ 2.4 million impressions), which takes seconds. Use savepoints for deploys, with stable operator IDs.

Training consistency. Log the feature value actually served, with the request ID, at bid time; training joins labels to the logged values (log-and-wait, rec9). For history before logging existed, recompute the feature in batch from the lake with the same 30-minute window and bucket definition, point-in-time as of each impression (de12), and verify on an overlapping week that batch and streaming values match within tolerance — differences point to late-data handling or deduplication mismatches.
