In the late 1960s, a program that wanted to know which suppliers sent parts to a project had to know exactly how the data was stored. In IBM's IMS, the hierarchical database built for the Apollo programme, records were arranged in trees: a project record, with its part records stored underneath it, and supplier records underneath those. To answer the question, your program opened the tree at a project, stepped down to the first part, stepped down to its suppliers, stepped back up, moved to the next part, and so on. Network databases following the CODASYL standard allowed more general graphs of records linked by pointers, but the program still navigated: find this record, follow that chain, read the next record in the set.

Now imagine the database team decides the data would be faster to store the other way up, with parts at the top and projects underneath. Nothing about the facts has changed. Every part is still supplied by the same suppliers to the same projects. But every program that walked the old tree is now broken, because the paths it followed no longer exist. The same happened when someone removed an index chain that was costing too much to maintain, or sorted a file in a different order: the programs that relied on that chain or that order silently produced wrong answers or stopped working.

Edgar Codd, a mathematician at IBM's San Jose research laboratory, described exactly this problem in 1970. He named three ways programs depended on storage: on the ordering of records, on the indexes that happened to exist, and on the access paths (the trees and pointer chains). His paper showed one small set of facts about parts, projects and suppliers stored in five different tree structures and pointed out that a program written for one fails on the other four. His proposal was to give programs a view of the data with no storage in it at all: just relations, which are tables of facts, and a language for asking questions about them. How the facts are laid out on disk would become the system's problem.

That idea, called data independence, is why you can add an index to a PostgreSQL table today and every query keeps returning the same answers, only faster. It is also why the vocabulary of this lesson (relations, keys, foreign keys) is the vocabulary of every database design interview.

This lesson builds the model from the ground up. You will learn what a relation, tuple, attribute and domain precisely are and where SQL tables differ from them; the full family of keys, from superkeys to foreign keys; the integrity constraints that let a database refuse bad data; the relational algebra that every query is translated into; and entity-relationship (ER) modelling, the method for turning a description of a business into a set of tables. It ends with a worked design for an LLM application's logs and the production problems that keys cause when they are chosen badly.

A ledger of facts

Think of a relational database as a set of ledgers, each recording one kind of fact. One ledger records "customer c has email e and name n". Another records "order o was placed by customer c at time t". Each line in a ledger is one fact, and every line in the same ledger has the same shape. To answer a question, you do not follow pointers from one ledger to another; you say which facts you want ("orders placed in October by customers whose email ends in example.com") and a clerk who knows how the ledgers are filed finds them. If the clerk refiles the ledgers by date instead of by customer, your question is unchanged and still gets the same answer.

The analogy breaks in one useful place. Ledger lines are written in an order and you can point at "the third line". A relation has no order at all: it is a set of facts, and asking for "the third row" only makes sense after you have said how to sort. This is not pedantry. It is the reason a database is free to store, scan and return rows in whatever order is fastest, and the reason a query without ORDER BY can return rows in a different order tomorrow.

The parts of a relation

The formal vocabulary is small. A relation is the ledger, which SQL calls a table. An attribute is a named column, such as price_cents. Each attribute draws its values from a domain, the set of values that are allowed, such as "non-negative integers" or "strings that look like an SKU". A tuple is one row: one value for each attribute, and so one fact. The degree of a relation is how many attributes it has, and its cardinality is how many tuples it has at the moment. The schema is the definition (names, attributes, domains, constraints); the instance is the data that happens to be in it now. The schema changes rarely, the instance changes with every insert.

Keys tie facts together

Because there are no pointers, the only way one fact can mention another is by value. An order row does not contain the address of a customer row; it contains the customer's identifier, customer_id = 1, and the database can find the customer with that identifier when asked. For that to work, identifiers must be unique: there must never be two customers with id 1. A set of columns that is guaranteed unique is a key, and a column that holds another table's key is a foreign key. Keys are what make a pile of independent ledgers into one connected database, and most of this lesson is about choosing and enforcing them.

From the business to the tables

The final piece of the big picture is design. Before anyone writes CREATE TABLE, someone has to decide which things the business cares about (customers, products, orders), what is recorded about each, and how they relate (a customer places many orders; an order contains many products, and a product appears in many orders). Writing that down as boxes and lines is entity-relationship modelling, introduced by Peter Chen in 1976. A small set of mechanical rules then turns the diagram into tables and foreign keys. If you get the diagram right, the tables mostly fall out; if you get it wrong (for example, you miss that a relationship is many-to-many), no amount of indexing later will fix it.

So the picture to carry is this: data is stored as sets of facts with no built-in order or pointers; keys make facts identifiable and let them reference each other by value; constraints let the database refuse facts that would make the set inconsistent; and an ER model is how you decide which sets of facts to have in the first place. Everything later in this track, from normalisation (db2) to query plans (db7) to concurrency (db9), builds on these four ideas.

1. Relations, tuples, attributes and domains, precisely

Start with the definition Codd gave. Take some sets D1, D2, …, Dn, the domains. A relation over them is a set of n-tuples where the first value comes from D1, the second from D2, and so on. Each position gets a name, the attribute, so in practice we refer to values by name (sku) rather than position. Three consequences follow directly from "a relation is a set".

First, there are no duplicate tuples. A set either contains a fact or it does not; it cannot contain the same fact twice. If the product relation contains (10, 'MUG-01', 900), inserting it again changes nothing. Second, there is no tuple order. {a, b} and {b, a} are the same set. Third, because attributes are referred to by name, attribute order does not matter either: (product_id = 10, sku = 'MUG-01') is the same tuple as (sku = 'MUG-01', product_id = 10).

Domains deserve more attention than they usually get. A domain is not just a storage type such as "32-bit integer"; it is the set of meaningful values. A quantity and a price can both be stored as integers, but they belong to different domains, and comparing one to the other is nonsense even though the database would happily do it. In SQL the domain is approximated by the column's type plus constraints: price_cents integer NOT NULL CHECK (price_cents >= 0) says "integers, not missing, not negative". PostgreSQL even has CREATE DOMAIN to name such a combination and reuse it. The tighter the domain is declared, the more bad data the database refuses on your behalf.

Codd also required values to be atomic: each attribute holds one value from its domain, not a list or a nested table. An order with a column products = 'MUG-01,TEE-M' breaks this rule. The rule is what later became first normal form (db2), and the reason for it is practical: if the products are hidden inside a string, the database cannot index them, join on them or enforce that each one exists.

2. Where SQL tables differ from relations

SQL, designed at IBM in the mid-1970s as part of the System R research prototype, implements the relational model loosely, and the differences are where real bugs come from. The first is that SQL tables are bags (multisets), not sets. A table with no primary key or unique constraint can hold the same row twice, and queries can produce duplicates even from tables that have keys: SELECT customer_id FROM orders returns one row per order, so a customer with three orders appears three times. You remove duplicates explicitly with DISTINCT. The reason SQL chose bags is cost: removing duplicates requires sorting or hashing the whole result, and the designers did not want every query to pay for it.

The second difference is order. A query result has an order only when ORDER BY asks for one. Without it, rows come out in whatever order the chosen plan produces them. A table that has always come back in insertion order (because it was read by a sequential scan of pages written in order) will suddenly come back sorted by email once an index on email makes the planner choose an index scan. Code that assumed the old order breaks without any change to the code.

The third is NULL, a marker meaning "no value here", which Codd's 1970 model did not have. NULL is not a value in the domain; it makes comparisons return a third truth value, unknown, which is why WHERE x = NULL never matches and why NOT IN with a NULL in the list returns nothing. db3 is devoted to NULL semantics; for now, note that every nullable column is a column whose meaning you must define (unknown? not applicable? not yet set?), and that a primary key can never be NULL.

The fourth is that columns in SQL do have a positional order, visible in SELECT * and in INSERT INTO t VALUES (...) without a column list. That is why production code should name its columns: adding a column to the table changes what SELECT * returns and can break a positional insert.

3. Keys: superkeys, candidate keys and the primary key

Take a concrete relation and find its keys by hand. Here is employee with five attributes and four rows:

1ana@co.comA123AnaSales
2raj@co.comB456RajSales
3li@co.comC789LiEng
4ana2@co.comD012AnaEng

A superkey is any set of attributes whose combined values are different for every tuple that could ever be in the relation. The word "could" matters: a key is a rule about the business, not an observation about today's rows. In this data, name alone looks unique except that Ana appears twice, and even if it did not, two people can share a name, so name is not a key. {emp_id} is a superkey. So is {emp_id, name}, and so is the set of all five attributes, which is always a superkey of any relation because a set has no duplicates.

A candidate key is a superkey with nothing redundant in it: remove any attribute and it stops being unique. {emp_id, name} is not a candidate key, because {emp_id} on its own is already unique. Here the business rules say each employee has one email, emails are never shared, and the same for national ids, so there are three candidate keys: {emp_id}, {email} and {national_id}. Candidate keys can have several attributes. In the order-line table later, neither order_id nor line_no is unique alone, but the pair is, so {order_id, line_no} is a candidate key; it is called a composite key.

The primary key is the candidate key you choose as the main identifier. It must be unique and NOT NULL (this is called entity integrity: every tuple must be identifiable), and it is what foreign keys in other tables will usually point to. The others become alternate keys, and the critical practical rule is that they are still keys: declare them UNIQUE. If email is a key in the business but not in the schema, two sign-up requests that arrive in the same millisecond will both check "does this email exist?", both see no, and both insert. A unique constraint is enforced by the database at write time with a unique index, so the second insert fails no matter how the requests interleave.

CREATE TABLE employee (
  emp_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text NOT NULL UNIQUE,
  national_id text NOT NULL UNIQUE,
  name        text NOT NULL,
  dept        text NOT NULL
);

How do you choose which candidate key is primary? Three properties matter. It should be stable, because a primary key is copied into every table that references it, and changing it means changing all of those copies. It should be compact, because it appears in every index on this table in some engines (MySQL's InnoDB stores the primary key inside every secondary index entry, db6) and in every foreign key column and its index. And it should be always present, because it cannot be NULL. Emails fail the first test (people change them), national ids fail the third (contractors may not have one, and you may not be allowed to store it), and emp_id passes all three, which brings us to surrogates.

4. Natural keys versus surrogate keys

A natural key is built from real-world data: an email, an ISBN, a vehicle registration, a country code. A surrogate key has no meaning outside the database; it is generated, typically as an auto-incrementing integer (GENERATED ... AS IDENTITY in PostgreSQL, AUTO_INCREMENT in MySQL) or a UUID.

The case for natural keys is that they already exist and they carry meaning: an order_line that references currency_code = 'EUR' can be read without a join, and there is no risk that the surrogate and the natural key disagree. They work well for small, slow-changing reference tables where the code is truly fixed: ISO country codes, currency codes, unit-of-measure codes.

The case for surrogate keys is stronger for anything that represents a person, an account or an event. Real-world identifiers change more often than anyone expects (people change email, companies rename, governments reissue ids), they can be long strings that bloat every index, they can be personal data that must be erased on request, and sometimes the real thing has no natural identifier at all (two log events with the same timestamp and text). A surrogate key avoids all of this. The price is that it identifies the row, not the thing: nothing stops you inserting the same customer twice with ids 41 and 42. So the standard design is both: a surrogate primary key, plus UNIQUE on each natural key. You get stable, compact references and the database still refuses duplicates.

5. Foreign keys and referential integrity

A foreign key is a set of columns in one table (the referencing or child table) whose values must appear as a primary key or unique key in another table (the referenced or parent table). Codd's paper defines it in exactly these terms, and notes that the two tables may be the same one: an employee.manager_id referencing employee.emp_id is a foreign key into its own table. Referential integrity is the rule that every non-NULL foreign key value refers to a row that exists. A NULL foreign key is allowed unless the column is also NOT NULL; it means "no parent".

Walk through what the database does to keep the rule, using orders.customer_id REFERENCES customer(customer_id):

  1. Insert or update a child row (an order with customer_id = 99): the database looks up 99 in the parent's key index. Found: the insert proceeds. Not found: the statement fails with a foreign key violation. In PostgreSQL this check also takes a lightweight lock on the parent row (FOR KEY SHARE) so that nobody can delete customer 99 between the check and your commit.
  2. Delete or update the key of a parent row (delete customer 1): the database must find child rows with customer_id = 1. This is a lookup in the child table, so it is fast only if the child column is indexed. Then it applies the foreign key's ON DELETE action.

The actions, as defined by the SQL standard and implemented by PostgreSQL:

ActionDeleting a parent that has children…Typical use

The same options exist for ON UPDATE, which applies when the parent's key value changes; with stable surrogate keys it almost never fires, which is another argument for them.

A subtle and very common performance trap: PostgreSQL requires the referenced columns to have a unique index (so the check in step 1 is fast), but it does not create an index on the referencing columns. Its documentation explains why: you might not need one, and there are many ways to index. The consequence is that deleting one customer from a database with 50 million orders and no index on orders.customer_id scans all 50 million orders to check for children. MySQL's InnoDB takes the opposite approach and creates an index on the referencing columns automatically if one does not exist. SQLite is the odd one out in another way: it parses foreign keys but does not enforce them unless each connection runs PRAGMA foreign_keys = ON, a backwards-compatibility default the lab demonstrates.

6. The other integrity constraints

Keys and foreign keys are two kinds of integrity constraint: a rule the database checks on every change and refuses to violate. The others complete the toolkit. NOT NULL says a value is required. CHECK states a condition on a single row, such as qty > 0 or end_date >= start_date. UNIQUE enforces an alternate key. PostgreSQL also has exclusion constraints, which generalise uniqueness to "no two rows may overlap", the classic use being room bookings whose time ranges must not intersect.

Why push rules into the database rather than the application? Because the database is the one place every writer passes through. Application checks are skipped by the admin script someone writes at 2 a.m., by the second service that writes to the same table, and by race conditions between two requests of the same service. A constraint is checked inside the transaction that makes the change, under the database's own concurrency control, so it holds regardless of who writes or how they interleave. Application validation is still useful for friendly error messages; the constraint is the guarantee.

Know the limits, though. A CHECK sees only the row being written, so it cannot express "at most 30 students per section" or "the order total equals the sum of its lines". Rules that span rows or tables need triggers, a transaction that reads and writes under the right locks (sc5, db9), or a design that makes the rule structural (for example, storing totals only as a view computed from the lines).

7. Relational algebra: the operations that make it a model

A data model is a structure plus operations on it. Codd's operations, refined into what is now called relational algebra, are few. Each takes one or two relations and returns a relation, so they can be chained. Using the product table from the primer and an order_line table:

  • Selection σ keeps the tuples that satisfy a condition: σprice_cents > 1000(product) returns TEE-M and CAP-RED. In SQL, WHERE.
  • Projection π keeps only some attributes: πsku(product). In pure algebra duplicates vanish automatically, because the result is a set; in SQL you need SELECT DISTINCT.
  • Cartesian product × pairs every tuple of one relation with every tuple of another: 4 products × 3 order lines gives 12 tuples.
  • Join ⋈ is a product followed by a selection on matching attributes: product ⋈product.product_id = order_line.product_id order_line keeps only the pairs where the ids match. In SQL, JOIN ... ON.
  • Union ∪, difference − and intersection ∩ combine relations with the same attributes. "Products never ordered" is πproduct_id(product) − πproduct_id(order_line).
  • Rename ρ gives a relation or attribute a new name, which you need to join a table to itself.

Work one query by hand. "SKUs of products ordered in a quantity of at least 2" is πsku(σqty ≥ 2(product ⋈ order_line)). Suppose order_line holds (100, 1, 10, 2), (100, 2, 12, 1) and (101, 1, 10, 3). The join pairs each line with its product: (10, MUG-01, 900, 100, 1, 2), (12, CAP-RED, 1200, 100, 2, 1), (10, MUG-01, 900, 101, 1, 3). Selection keeps qty ≥ 2: the two MUG-01 rows. Projection onto sku gives {MUG-01}, a single tuple, because the result is a set.

Why does this matter to an engineer who will write SQL, not algebra? Because the algebra has equivalence rules, and the database uses them. σqty ≥ 2(product ⋈ order_line) gives the same result as product ⋈ σqty ≥ 2(order_line): you can filter the lines before joining. If order_line has 100 million rows and 1% have qty ≥ 2, the second form joins one million rows instead of 100 million. The query optimiser (db7) parses your SQL into an algebra tree and rewrites it with rules like this one (push selections down, reorder joins, drop unused columns early) before choosing algorithms. You wrote what; the system decides how. That is data independence again, now as a performance feature.

8. Entity-relationship modelling

ER modelling is how you get from a conversation with the business to a schema. Chen's 1976 paper defined an entity as a "thing" which can be distinctly identified, such as a specific person, company or event, and a relationship as an association among entities. Entities of the same kind form an entity set (all customers), and each has attributes. Attributes come in a few flavours worth naming, because each maps to tables differently:

  • Simple attributes hold one atomic value (a price).
  • Composite attributes have parts (an address: street, city, postcode). They become several columns.
  • Multivalued attributes can have several values per entity (a customer's phone numbers). They become a separate table, never a comma-separated column.
  • Derived attributes can be computed from others (an order total from its lines, an age from a birth date). Usually not stored, or stored deliberately as a cache.

Relationships carry two pieces of information. Cardinality says how many entities on each side can be related: one-to-one (a user has one profile), one-to-many (a customer places many orders, each order has one customer) or many-to-many (an order contains many products, a product is in many orders). Participation says whether every entity must take part: every order must have a customer (total or mandatory participation), but a customer may have no orders yet (partial or optional). Relationships can also have attributes of their own. The quantity of a product in an order describes neither the order nor the product; it describes their pairing.

Finally, a weak entity is one that cannot be identified on its own. Line 2 means nothing until you say "line 2 of order 100"; its key is borrowed partly from its owner, so its primary key is (order_id, line_no). Weak entities almost always have mandatory participation and are deleted with their owner, which is why ON DELETE CASCADE fits them.

The common notation today is crow's foot: entities as boxes listing their attributes, relationships as lines, and symbols at each end of a line. A crow's foot (three prongs) means "many", a bar means "one", and a circle means "zero", so a bar-and-circle end reads "zero or one" and a crow's-foot-and-bar end reads "one or many".

9. From ER diagram to tables: the mapping rules

The mapping from an ER model to tables is mechanical, which is what makes ER modelling worth doing. Apply these rules in order.

  1. Each strong entity becomes a table. Simple attributes become columns, composite attributes become several columns, and one candidate key becomes the primary key (others become UNIQUE).
  2. Each multivalued attribute becomes its own table with a foreign key to the owner: customer_phone(customer_id, phone, PRIMARY KEY (customer_id, phone)).
  3. Each one-to-many relationship becomes a foreign key on the "many" side. The order holds customer_id; the customer does not hold a list of order ids. Mandatory participation of the many side becomes NOT NULL on that foreign key.
  4. Each one-to-one relationship becomes a foreign key on either side, with a UNIQUE constraint so it cannot become one-to-many. Put it on the optional side: profile.user_id UNIQUE NOT NULL REFERENCES users. Or merge the two tables if they are always created together and read together.
  5. Each many-to-many relationship becomes a junction table with a foreign key to each side; the pair is its primary key, and the relationship's own attributes become its columns.
  6. Each weak entity becomes a table whose primary key includes its owner's key, with a foreign key to the owner, usually ON DELETE CASCADE.

Apply them to a second example that interviewers love, a university. Courses have many sections; each section is taught by one instructor; students enrol in many sections and receive a grade per enrolment.

The resulting DDL, with the foreign key columns indexed (the composite primary key already indexes student_id as its leading column, so only section_id needs its own index):

CREATE TABLE course     (course_id bigint PRIMARY KEY, code text NOT NULL UNIQUE, title text NOT NULL);
CREATE TABLE instructor (instructor_id bigint PRIMARY KEY, name text NOT NULL);
CREATE TABLE section (
  section_id    bigint PRIMARY KEY,
  course_id     bigint NOT NULL REFERENCES course,
  instructor_id bigint NOT NULL REFERENCES instructor,
  term          text   NOT NULL,
  UNIQUE (course_id, term, instructor_id)
);
CREATE TABLE student (student_id bigint PRIMARY KEY, name text NOT NULL);
CREATE TABLE enrolment (
  student_id bigint NOT NULL REFERENCES student ON DELETE CASCADE,
  section_id bigint NOT NULL REFERENCES section,
  grade      text CHECK (grade IN ('A','B','C','D','F')),
  PRIMARY KEY (student_id, section_id)
);
CREATE INDEX ON section (course_id);
CREATE INDEX ON section (instructor_id);
CREATE INDEX ON enrolment (section_id);

Notice the decisions the rules forced. grade is nullable, because a student who has just enrolled has no grade yet, and that NULL has one defined meaning: "not graded yet". The UNIQUE (course_id, term, instructor_id) is a business rule we chose (one instructor does not teach two sections of the same course in a term); if that rule is false at this university, the constraint is wrong and must go. That is the general lesson: the schema is a precise statement of business rules, so writing it surfaces questions nobody had asked.

10. Modelling choices that come up in every design

Self-referencing relationships. An employee has a manager who is also an employee; a category has a parent category; a comment replies to another comment. These are one-to-many relationships from a table to itself: employee.manager_id bigint REFERENCES employee(emp_id), nullable because the CEO has no manager. Reading a whole hierarchy needs a recursive query, which db4 builds.

Subtypes. Payments can be by card or by bank transfer, with some attributes shared (amount, time) and some specific (card last four digits; IBAN). There are three classic mappings. Single table: one payment table with all columns and a kind column, specific columns nullable; simple and fast, but the database cannot require "card payments must have last4" without a CHECK per kind. Class table: a payment table for shared columns plus card_payment and bank_payment tables whose primary key is also a foreign key to payment; clean constraints, one join to read a full payment. Concrete table: separate complete tables per kind with no shared parent; no joins, but "all payments" needs a UNION and nothing can hold a foreign key to "a payment" in general. Choose by how the data is queried: mostly together → single or class table; mostly separately → concrete.

History. A product's price changes, but last month's orders must still show what the customer paid. Either copy the price into the order line at purchase time (order_line.unit_price_cents, which is not redundancy but a different fact: the price agreed in this sale), or keep a product_price(product_id, valid_from, valid_to, price_cents) table and look up the price valid at the order's time. The first is simpler and almost always right for transactions; the second is right when you need to answer "what was the price on date X" for its own sake.

Status as data. If an order moves through states, store the current state as a column constrained to known values, and, if anyone will ever ask "when did it ship?", record transitions in an order_event table rather than overwriting timestamps.

11. A real-world walk-through: logging an LLM application

Put it together on a design an AI engineer will actually meet. A support assistant answers users in conversations. Product wants to debug bad answers, the evaluation team wants to score answers against test cases, and finance wants cost per customer. Start with entities and relationships, in words.

A user has many conversations; a conversation has many messages (from the user, the assistant or a tool). Each assistant message is produced by one or more LLM calls (a retry, a tool-calling loop), each of which used one model and one prompt version. A user can leave at most one feedback rating per call. An eval case can be run against many calls, and a call can be scored by many eval cases: many-to-many, with a score on the relationship.

Apply the mapping rules. users, conversation, message, prompt_version, llm_call and eval_case are strong entities. conversation.user_id, message.conversation_id, llm_call.message_id and llm_call.prompt_version_id are foreign keys on the many side, all NOT NULL because participation is mandatory. feedback is keyed by (call_id, user_id), which enforces "one rating per user per call" structurally rather than in application code. eval_result(eval_case_id, call_id, score, judged_at) is the junction. Token counts, latency and cost in micro-dollars are attributes of llm_call; the model name is a short natural key into a small model reference table with prices.

The keys answer the three teams' questions with joins rather than guesswork: cost per customer is llm_call → message → conversation → users, grouped by user; a regression after a prompt change is llm_call grouped by prompt_version_id, joined to feedback and eval_result; and a bad answer is debugged by reading one conversation's messages and their calls. Large prompt and response bodies can be stored in object storage with only a key in the row if they bloat the table, but the relationships stay in the relational model, where the database guarantees that every rating and every cent points at a call that exists.

Closure and why optimisers exist

The most consequential property of relational algebra is closure: every operation takes relations and returns a relation. That sounds like a technicality, but it is what makes a query a composable expression rather than a procedure. Because the result of a join is itself a relation, it can be filtered, joined again, grouped or used as a subquery, and the system can treat the whole query as one tree of operations. Algebraic equivalences then hold over the tree: selections commute with each other and can be pushed below joins when they mention only one side; joins are commutative and associative, so a three-way join can be evaluated in any of several orders; projections can be pushed down to drop unneeded columns early. A cost-based optimiser (db7) enumerates equivalent trees using these rules and estimates which one is cheapest. Navigational databases had no such freedom: the program was the plan.

Sets versus bags, and what it costs

The algebra is defined on sets, SQL on bags, and some equivalences hold for one but not the other. Projection is the clearest case: in set semantics πcustomer_id(orders) has one tuple per customer, while SQL's SELECT customer_id FROM orders has one per order. Some optimisations that are valid for sets need extra care for bags; for example, rewriting a semi-join ("customers who have at least one order", WHERE EXISTS) as an ordinary join changes the result under bag semantics, because the join repeats a customer once per order. That is why optimisers treat EXISTS and IN subqueries as a distinct operator, the semi-join, rather than an inner join followed by DISTINCT. As a working engineer, the lesson is to say what you mean: use EXISTS when you mean "has at least one", not a join followed by DISTINCT, which makes the database build and then deduplicate a larger intermediate result.

Deferrable constraints and circular references

Sometimes two rows must reference each other. A department has a head_emp_id referencing an employee, and every employee has a dept_id referencing a department. Inserting either first violates a foreign key. One escape is to make one reference nullable and fill it in with an update. The cleaner one is a deferrable constraint: in PostgreSQL, REFERENCES employee DEFERRABLE INITIALLY DEFERRED makes the check run at COMMIT rather than after each statement, so a transaction can insert both rows in any order and the check sees the final, consistent state. The same feature lets you swap two values of a unique column within a transaction. This is the practical difference between NO ACTION and RESTRICT: NO ACTION respects deferral, RESTRICT never waits. The cost is that violations surface at commit, far from the statement that caused them, so use deferral narrowly.

Choosing a surrogate key format

Surrogate keys come in three main forms, and the choice interacts with storage (db5, db6). A sequence-generated bigint is 8 bytes, monotonic, and inserts always land at the right-hand edge of the B-tree index, so the index stays compact and hot pages stay in memory. Its downsides are that ids leak business volume (a competitor who signs up twice a week apart learns your growth rate) and that a single sequence is a coordination point across shards. A random UUID (version 4) is 16 bytes, can be generated anywhere without coordination, and reveals nothing, but random keys insert all over the B-tree: each insert touches a random leaf page, which on a large table means a random page read and many half-full pages from splits. A time-ordered UUID (version 7), standardised in RFC 9562 in 2024, puts a millisecond Unix timestamp in the high bits followed by random bits, so it is generated without coordination yet inserts near the right edge like a sequence. PostgreSQL 18 added a built-in uuidv7() function. Snowflake-style 64-bit ids (timestamp, machine id, counter) give the same ordering in 8 bytes, at the cost of running a generator. Whatever the format, choose the width for the lifetime of the system: 32-bit integers run out at 2,147,483,647, and the migration to 64 bits on a large table is exactly the kind of operation you do not want to do in an emergency.

Entity-attribute-value and polymorphic associations

Two designs try to escape the relational model and lose its guarantees. Entity-attribute-value (EAV) stores every fact as a row (entity_id, attribute_name, value), typically with value as text. It never needs a migration, but types, NOT NULL, uniqueness and foreign keys can no longer be declared per attribute; reading one entity with ten attributes is ten self-joins or a pivot; and the planner cannot estimate how many rows match attribute = 'color' AND value = 'red'. For sparse or user-defined attributes, a JSON column (PostgreSQL's jsonb) with expression indexes on the few fields you filter by is the modern compromise. Polymorphic associations are columns like comment.target_type and comment.target_id, where the id may refer to a post, a photo or a video depending on the type. No foreign key can be declared, because the referenced table varies by row, so orphans accumulate. The relational fix is either one nullable foreign key column per possible target with a CHECK that exactly one is set, or a shared supertype table (commentable) that posts, photos and videos each reference, so comments have a single real foreign key.

What Codd's model leaves out on purpose

The relational model says nothing about storage, indexes, concurrency or distribution, and that silence is a feature: it is a logical model, and everything else is implementation. It does not mean those things are unimportant; the rest of this track is about them. It does mean that when an interviewer asks "is MongoDB relational?" or "is a key-value store a relational database?", the precise answer is about the model: whether data is exposed as relations with declared keys and constraints and queried with a closed set of operations, not whether it is fast, distributed or written in a particular language. NewSQL systems like CockroachDB and Spanner keep the relational model and change the implementation underneath; document databases change the model itself (db11).

Running out of ids: Basecamp, November 2018

On 8 November 2018, Basecamp 3 was stuck in read-only mode for almost five hours. The company's own timeline explains why: at 7:21 a.m. Central time they were alerted that an important tracking table had run out of id numbers, because the column was an integer, which stops at 2,147,483,647, rather than a bigint, which reaches 9,223,372,036,854,775,807. The fix itself was obvious: change the column type. Executing it was not. The table was very large (that was why it had run out), so the migration was estimated at about one hour forty minutes; then the team had to verify the data across eight database servers in two data centres before going back online, and when they did, the surge of returning traffic overwhelmed a caching server.

Three lessons generalise. First, a key's type is a capacity decision; choose bigint (or a 16-byte UUID) for any table that grows with usage, because the extra four bytes per row are cheaper than any outage. Second, monitor headroom: a query over the database's sequences comparing the current value with the type's maximum, alerting at 50%, would have given months of warning. Third, every foreign key that references the id must be widened too, because a bigint parent key with an integer child column fails the moment a new parent id passes the old limit.

Unindexed foreign keys

The most common foreign-key performance problem is the one PostgreSQL's documentation warns about: the referencing column has no index. Inserts are fine (they check the parent's primary key index), so nobody notices for months. Then someone deletes a parent row, or runs a cleanup job that deletes thousands, and each delete scans the whole child table to look for references. The symptom is a delete that takes seconds or minutes, often holding locks that block other writers, with a sequential scan of the child table in the plan. The fix is an index on every foreign key column that will be used to find children, and a periodic check (catalog queries that list foreign keys with no index whose leading columns match) in CI or monitoring. In MySQL InnoDB this problem does not occur, because it creates the index for you.

Foreign keys at scale

Foreign keys only work within one database. When a system is split into services, each with its own database, or sharded so that a parent and its children can live on different machines (sc7), references cross a boundary no constraint can see. Teams then keep integrity with a mix of techniques: write paths that create parent and child in the right order and treat a missing parent as an error; soft deletes or tombstones so that parents are never physically removed while children may still point at them; asynchronous orphan detection with an anti-join on a replica; and idempotent cleanup jobs. Separately, some large MySQL users run without foreign keys even on one node because their online schema-change tools copy tables into shadow tables and swap them, which foreign keys complicate; GitHub's gh-ost states plainly that foreign key constraints are not supported. Read that as a trade-off made at a specific scale with a specific toolchain, not as advice for a 50 GB application database, where foreign keys are cheap insurance.

Natural keys that change

A system that used email as the primary key of users eventually gets the ticket "let users change their email". Every table that references users holds the email, so the change must update all of them in one transaction (ON UPDATE CASCADE can do it, but on large tables the cascade locks and rewrites many rows), and every external system that stored the email as an identifier (analytics, the billing provider, logs) now has stale references. The migration to a surrogate key touches every referencing table. The general symptom of a bad natural primary key is that a routine business change becomes a data migration.

Soft deletes and uniqueness

Many applications "delete" by setting deleted_at rather than removing rows, to allow undo and auditing. That quietly breaks unique constraints: a user who deletes their account and signs up again with the same email collides with their own soft-deleted row. The fix in PostgreSQL is a partial unique index, CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL, which enforces uniqueness only among live rows (db6 covers partial indexes). Soft deletes also mean foreign keys no longer protect you from references to "deleted" parents, so queries must filter on deleted_at consistently, which is a frequent source of bugs and a reason to prefer an archive table for data that is truly gone.

What to watch

Useful checks to run regularly: sequence or identity headroom per table; foreign keys without a supporting index; tables without a primary key (they cannot be replicated logically in many setups and make duplicate rows possible); and, where constraints are not declared, orphan counts per relationship. Constraint violations in application error logs are also a signal worth tracking: a sudden rise in unique violations often means a retry loop or a race in the write path, which the constraint is catching for you.

Goal: see the database enforce keys and foreign keys, and see what happens when it does not. Uses only Python 3.12 and the bundled sqlite3 module. Save as db1.py and run python db1.py.

import sqlite3

SCHEMA = """
CREATE TABLE customer (
  customer_id INTEGER PRIMARY KEY,
  email       TEXT NOT NULL UNIQUE,
  name        TEXT NOT NULL
);
CREATE TABLE product (
  product_id  INTEGER PRIMARY KEY,
  sku         TEXT NOT NULL UNIQUE,
  price_cents INTEGER NOT NULL CHECK (price_cents >= 0)
);
CREATE TABLE orders (
  order_id    INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL REFERENCES customer(customer_id) ON DELETE RESTRICT,
  placed_at   TEXT NOT NULL
);
CREATE TABLE order_line (
  order_id    INTEGER NOT NULL REFERENCES orders(order_id) ON DELETE CASCADE,
  line_no     INTEGER NOT NULL,
  product_id  INTEGER NOT NULL REFERENCES product(product_id),
  qty         INTEGER NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, line_no)
);
"""

def try_(db, label, sql, args=()):
    try:
        db.execute(sql, args)
        print(f"{label:<34} OK")
    except sqlite3.IntegrityError as e:
        print(f"{label:<34} REJECTED: {e}")

for fk in ("OFF", "ON"):
    print(f"--- PRAGMA foreign_keys = {fk}")
    db = sqlite3.connect(":memory:")
    db.execute(f"PRAGMA foreign_keys = {fk}")
    db.executescript(SCHEMA)
    db.execute("INSERT INTO customer VALUES (1, 'ana@example.com', 'Ana')")
    db.execute("INSERT INTO product VALUES (10, 'MUG-01', 900)")
    db.execute("INSERT INTO orders VALUES (100, 1, '2026-10-03')")
    db.execute("INSERT INTO order_line VALUES (100, 1, 10, 2)")
    try_(db, "duplicate email", "INSERT INTO customer VALUES (2, 'ana@example.com', 'X')")
    try_(db, "negative price", "INSERT INTO product VALUES (11, 'BAD', -5)")
    try_(db, "order for missing customer", "INSERT INTO orders VALUES (101, 99, '2026-10-03')")
    try_(db, "delete customer with orders", "DELETE FROM customer WHERE customer_id = 1")
    try_(db, "delete order (cascade lines)", "DELETE FROM orders WHERE order_id = 100")
    n = db.execute("SELECT count(*) FROM order_line").fetchone()[0]
    print(f"{'order_line rows left':<34} {n}")
    orphans = db.execute("""SELECT count(*) FROM orders o
                            LEFT JOIN customer c USING (customer_id)
                            WHERE c.customer_id IS NULL""").fetchone()[0]
    print(f"{'orphan orders':<34} {orphans}")

What to look for.

  1. In both runs, the duplicate email and negative price are rejected: UNIQUE and CHECK are always enforced.
  2. With foreign_keys = OFF (SQLite's default for compatibility), the order for missing customer 99 is accepted and customer 1 can be deleted while it has orders. The final anti-join counts orphan orders 1: an order whose customer does not exist. The schema declared the foreign key; nothing enforced it.
  3. With foreign_keys = ON, both are rejected with FOREIGN KEY constraint failed, deleting the order cascades to its line (order_line rows left 0), and there are no orphans.

Try next. Change ON DELETE RESTRICT on orders.customer_id to ON DELETE CASCADE and rerun: deleting the customer now silently deletes their orders and, through the second cascade, the order lines. Ask yourself whether that is ever what a shop wants. Then add a customer_phone table for a multivalued attribute with a composite primary key and confirm the same phone cannot be added twice for one customer.

The anti-join in the script (LEFT JOIN ... WHERE parent IS NULL) is the same query you would run in production to find orphans in a database that has no foreign keys.

Design: a recipe-sharing app

Users publish recipes. A recipe has a title, steps in order, and a list of ingredients with a quantity and unit each (e.g. 200 g flour). Ingredients are shared across recipes so the app can show "all recipes using basil". Users can save other users' recipes to named collections, and can rate a recipe once (1-5). Draw the ER model, then write the tables with keys, foreign keys and constraints.

Answer

Entities and relationships. User (strong). Recipe (strong), with a mandatory many-to-one to its author. Step is a weak entity of recipe: identified by (recipe_id, step_no), deleted with the recipe. Ingredient (strong, shared). Recipe-ingredient is many-to-many with attributes quantity and unit, so it is a junction. Collection belongs to one user (one-to-many); collection-recipe is many-to-many. Rating is a many-to-many between user and recipe with attribute stars, and "once per user" makes the pair its key.

users(user_id PK, email UNIQUE NOT NULL, name)
recipe(recipe_id PK, author_id FK→users NOT NULL, title NOT NULL, created_at)
step(recipe_id FK→recipe ON DELETE CASCADE, step_no, body NOT NULL,
     PRIMARY KEY (recipe_id, step_no), CHECK (step_no > 0))
ingredient(ingredient_id PK, name UNIQUE NOT NULL)
recipe_ingredient(recipe_id FK ON DELETE CASCADE, ingredient_id FK,
     quantity numeric CHECK (quantity > 0), unit text NOT NULL,
     PRIMARY KEY (recipe_id, ingredient_id))
collection(collection_id PK, owner_id FK→users NOT NULL, name NOT NULL,
     UNIQUE (owner_id, name))
collection_recipe(collection_id FK ON DELETE CASCADE, recipe_id FK ON DELETE CASCADE,
     added_at, PRIMARY KEY (collection_id, recipe_id))
rating(user_id FK, recipe_id FK ON DELETE CASCADE, stars int CHECK (stars BETWEEN 1 AND 5),
     PRIMARY KEY (user_id, recipe_id))

Indexes beyond the keys: recipe(author_id), recipe_ingredient(ingredient_id) for "all recipes using basil", collection_recipe(recipe_id), rating(recipe_id) for the average rating.

Choices worth saying out loud. Steps are rows, not a text array, so they can be reordered and edited individually; the step number is part of the key, so reordering needs a deferred unique check or a two-step renumber. "200 g flour" is split into quantity and unit so the app can scale servings; if the same ingredient can appear twice in one recipe (flour in the dough and in the dusting), the junction's key must become (recipe_id, line_no) instead. Deleting a user is not cascaded to recipes, since other people's collections reference them: decide on anonymisation instead, which is a product and legal question the schema has made visible.
