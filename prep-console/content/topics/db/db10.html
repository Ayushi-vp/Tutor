In July 2016, Uber published a long engineering post explaining why it had moved much of its data from PostgreSQL to MySQL. It became one of the most-discussed database articles of the decade, partly because it was unusually concrete. It walked through a tiny table of famous mathematicians with three indexes, updated one man's birth year (al-Khwārizmī's, from 780 to 770), and showed what each database actually wrote to disk. In PostgreSQL: a new copy of the whole row, plus a new entry in the primary key index, plus a new entry in the name index, plus a new entry in the birth-year index, all logged and all shipped to replicas, although only one column of one index had logically changed. In InnoDB: the row changed in place, the old version copied to an undo log, and only the birth-year index touched.

For Uber's workload at the time, heavily indexed tables updated constantly and replicated from the West Coast to the East Coast over expensive links, that difference turned into real money and real pain. The post listed five problems: inefficient writes, verbose replication, a table corruption bug in their PostgreSQL 9.2 version, conflicts between replica queries and replication, and upgrades that took so many hours they had stopped doing them. The PostgreSQL community replied, pointing out features Uber had not used (such as updates that skip index writes) and noting that several issues were being fixed. Both sides were largely right, and that is what makes the case useful: it shows that two databases offering the same SQL and the same ACID guarantees can behave very differently underneath, and that the differences follow directly from a few design decisions.

Those decisions are the subject of this lesson. Where does the old version of a row go when you update it: next to the new one (PostgreSQL) or into a separate undo log (InnoDB)? What do indexes point to: a physical location or a primary key? Who cleans up old versions, and what happens if cleanup falls behind? Is a connection a process or a thread? Is replication a stream of physical page changes or of logical row changes? Every one of these choices was already introduced in earlier lessons (db5, db6, db8, db9). Here they come together into two complete systems, compared side by side, with the operational failure modes each one produces, including the transaction-id wraparound that took Sentry's PostgreSQL offline for writes in 2015.

The goal is not to crown a winner. It is to let you predict, for a given table and workload, what each engine will do, and to answer the interview question that follows every mention of either database: "why that one?"

Two ways to keep history

Both engines use MVCC (db9): readers see a snapshot, so the database must keep old versions of rows around while anyone might still need them. The fundamental difference is where those old versions live.

PostgreSQL is like a notebook in which you never erase. To change a line, you strike it through (mark it with the transaction that replaced it) and write the new version somewhere else, often further down the same page. Readers looking at an older snapshot read the struck-through line; newer readers read the new one. Eventually someone has to tidy up the notebook, cutting out lines nobody can need any more: that is VACUUM.

InnoDB is like a whiteboard with a filing cabinet next to it. To change something, you first file a photocopy of the old version in the cabinet (the undo log), then rewrite the whiteboard in place. Readers who need the old version go to the cabinet and reconstruct it. Eventually someone has to empty the cabinet of copies nobody needs: that is purge.

The analogy shows the trade at once. PostgreSQL's notebook makes writing a new version simple and rolling back free (just ignore the new line), but every new version has a new location, so anything that points at the row's location, every index, may need updating. InnoDB's whiteboard keeps the row in the same place, so indexes that do not involve the changed column are untouched, but every update pays for a copy into the cabinet, and readers of old versions do extra work. In both, cleanup is mandatory, and anything that makes old versions needed for longer (a long-running transaction) makes the cleanup fall behind.

Four more differences that follow

From that core choice and a few others come the differences this lesson works through. Storage layout: PostgreSQL tables are unordered heaps; InnoDB tables are B+ trees ordered by primary key. Cleanup: PostgreSQL's vacuum scans tables for dead tuples and must also "freeze" old rows because of 32-bit transaction ids; InnoDB's purge walks the undo logs. Connections: PostgreSQL starts a process per connection; MySQL runs a thread per connection. Replication: PostgreSQL ships its physical WAL by default; MySQL ships a logical binary log of row changes. Each of these has consequences an engineer operating either database meets in the first year.

How to read the rest of this lesson

For each difference, ask three questions. What does the engine write when a row changes, and how many pages does that touch? What has to be cleaned up later, and what can stop the cleanup? And what crosses the network to a replica? Almost every production story about either database, including Uber's and Sentry's, is an answer to one of those three questions in a particular workload. The worked comparison near the end of the body applies all three to a single sessions table, so you can see how a small schema change moves PostgreSQL from the worst case to the best case for the same logical workload.

1. PostgreSQL's update path, in detail

An UPDATE in PostgreSQL finds the current visible tuple, checks it is not locked by a concurrent writer (db9), writes a new tuple containing the full new row, sets the old tuple's xmax to the updating transaction's id and its t_ctid pointer to the new tuple's location, and WAL-logs both changes. The new tuple has a new physical address (ctid). Every index on the table maps keys to ctids, so in the general case every index must receive a new entry pointing to the new tuple, even indexes on columns whose values did not change, because the old entries point to the old tuple. That is the write amplification Uber described: with a dozen indexes, updating one unindexed-by-most column still adds a dozen index entries, each WAL-logged.

The exception is the heap-only tuple (HOT) update. If no indexed column changes and the new tuple fits on the same page as the old one, PostgreSQL writes the new tuple on that page, links it from the old one, and adds no index entries at all. An index lookup still finds the old tuple's line pointer, and follows the chain within the page to the visible version. Later, when the page is accessed and the old versions are dead, PostgreSQL prunes the chain in place, redirecting the line pointer so the space can be reused without a full vacuum. HOT updates are therefore cheap: one page changed, a small WAL record.

Two conditions decide whether you get them. First, no indexed column may change; an index on updated_at or last_login disqualifies every update that touches those columns. Second, there must be free space on the page; a table filled to 100% (the default heap fillfactor) has room only after pruning or vacuum frees some. Setting ALTER TABLE … SET (fillfactor = 80) leaves 20% of each page free for new versions. The ratio of HOT updates is visible in pg_stat_user_tables as n_tup_hot_upd versus n_tup_upd, and it is one of the most useful single numbers for an update-heavy PostgreSQL table. The lab's toy model shows the effect: a mix of updates where 70% touch an indexed timestamp produces about 485 page writes in the PostgreSQL model versus 350 in the InnoDB model; drop the index on the timestamp and the PostgreSQL figure falls to under 200, because most updates become HOT.

2. InnoDB's update path, in detail

InnoDB stores the table as the primary key's B+ tree, with full rows in the leaves (a clustered index, db6). An update finds the row by primary key, writes an undo record containing the old values of the changed columns (and a pointer to the previous undo record, forming a version chain), then modifies the row in place, storing the updating transaction's id and a pointer to the undo record in hidden row fields. If the new row no longer fits (a longer string), InnoDB may have to reorganise or split the page, but the row keeps its primary key position.

Secondary indexes store (secondary key, primary key). Because the primary key does not change, only indexes containing a changed column need maintenance: InnoDB delete-marks the old secondary entry and inserts a new one. Indexes on other columns are untouched. A consistent read by an older snapshot finds the current row, sees that its transaction id is too new for the snapshot, and follows the undo chain back to the right version, reconstructing it. Secondary index entries that are delete-marked are checked against the clustered row when needed.

So InnoDB pays a different set of costs: every update writes an undo record (itself redo-logged), reads of old versions walk undo chains, and secondary index lookups need a second descent through the primary key tree. A random primary key (a UUIDv4) is especially costly because the table itself is the primary key tree, so row inserts scatter across all its leaves (db5).

3. Cleanup in PostgreSQL: VACUUM and autovacuum

Dead tuples (versions whose deleting transaction committed before every running snapshot started) occupy space until VACUUM removes them. A plain VACUUM scans the table's pages (skipping those the visibility map marks all-visible), removes dead tuples from heap pages and their entries from indexes, records free space in the free space map for future inserts and updates, and sets visibility-map bits for pages that are now all-visible, which is what makes index-only scans skip the heap (db6). It runs alongside normal reads and writes. It does not return space to the operating system except at the end of a table; VACUUM FULL rewrites the table compactly but takes an exclusive lock for the whole rewrite.

Autovacuum runs vacuum automatically. A launcher wakes every autovacuum_naptime (one minute) and, for each table, compares the number of dead tuples with a threshold: autovacuum_vacuum_threshold (50) plus autovacuum_vacuum_scale_factor (0.2) times the table's row count, and in PostgreSQL 18 capped by autovacuum_vacuum_max_threshold (100 million). For a 1,000-row table that is 250 dead tuples; for a 100-million-row table it is 20 million, which is why default settings vacuum large tables too rarely and why per-table overrides (ALTER TABLE big SET (autovacuum_vacuum_scale_factor = 0.01)) are standard practice. Autovacuum is also throttled by a cost limit so it does not swamp I/O; on busy servers that throttle often needs raising so vacuum can keep up.

The horizon matters as much as the schedule. Vacuum can only remove tuples dead to every snapshot. The oldest snapshot in the database, whether from a long report, a forgotten BEGIN in a console, an idle-in-transaction connection, a replication slot that a consumer stopped reading, or a standby with hot_standby_feedback, holds the horizon back for all tables. Vacuum then runs and removes nothing, and bloat accumulates everywhere at once. The diagnostic query is the oldest backend_xmin in pg_stat_activity and the oldest xmin or catalog_xmin in pg_replication_slots.

4. Freezing and transaction-id wraparound

PostgreSQL transaction ids are 32 bits, about 4.3 billion values, and they are compared in a circle: for any xid, about two billion ids are "in the past" and two billion "in the future". After roughly two billion more transactions, a row written long ago would suddenly appear to have been created in the future and become invisible. To prevent that, vacuum freezes tuples old enough that every transaction can see them, marking them as visible to all regardless of xid. A table's relfrozenxid records the oldest unfrozen xid it may contain, and the database's oldest such value is the distance to danger.

Normally freezing happens quietly during regular vacuums. When a table's oldest unfrozen xid is older than autovacuum_freeze_max_age (200 million transactions by default), autovacuum runs an aggressive anti-wraparound vacuum on it even if autovacuum is otherwise disabled for that table, and it cannot be cancelled by lock conflicts the way normal autovacuums can. If that still does not keep up, the server emits warnings as the remaining distance shrinks, and, per the documentation, refuses to assign new transaction ids once fewer than three million remain: ERROR: database is not accepting commands that assign new transaction IDs to avoid wraparound data loss. Reads continue; writes stop until a vacuum freezes enough rows.

A database doing 2,000 write transactions per second consumes 200 million xids in about 28 hours, so on a busy system every large table is due for an anti-wraparound vacuum every day or so, and a multi-terabyte table may take hours to scan. Wraparound outages happen when freezing is blocked (an old snapshot or replication slot holds the horizon) or simply too slow for a huge, rarely vacuumed table. Since PostgreSQL 9.6 the visibility map also records all-frozen pages, so vacuums skip pages already frozen, which made anti-wraparound vacuums of mostly static tables much cheaper.

5. Cleanup in InnoDB: purge and the history list

InnoDB's undo records must be kept as long as any read view (snapshot) might need them. Background purge threads remove undo records older than the oldest active read view, and also physically remove secondary index entries that were delete-marked. The amount of unpurged history is reported as the history list length in SHOW ENGINE INNODB STATUS. On a healthy server it stays in the thousands. A long-running transaction, including one that merely opened a consistent snapshot at REPEATABLE READ and then sat idle, prevents purge from advancing; the history list grows into the millions, undo tablespaces grow, and queries slow down because reads must walk ever-longer version chains. The fix and prevention are identical to PostgreSQL's horizon problem: find and end long transactions, and bound them with timeouts. InnoDB also has no wraparound hazard of the PostgreSQL kind, because its transaction ids are 48-bit and versions live in undo logs rather than being compared forever on every row.

6. Storage layout consequences: heap versus clustered

Beyond updates, the heap-versus-clustered choice shows up everywhere. Primary key lookups are slightly cheaper in InnoDB (one descent ends at the row) and secondary lookups slightly cheaper in PostgreSQL (one descent plus one heap fetch, versus two descents). Range scans on the primary key read physically adjacent rows in InnoDB, which is excellent if the key is chosen for locality, such as (tenant_id, created_at, id); in PostgreSQL rows are in insertion order, which is good for time-ordered inserts but has no relationship to any other key. Primary key choice matters far more in InnoDB: it is copied into every secondary index and determines where every row is inserted. Table size differs too: PostgreSQL's 23-byte tuple header plus line pointer (db5) versus InnoDB's roughly 18 bytes of row overhead (hidden transaction id and roll pointer plus a record header); both add per-row costs that matter for narrow tables.

7. Connections and memory

PostgreSQL forks a separate operating-system process for each client connection. Each process has its own private memory (catalog caches, sort and hash memory up to work_mem per operation), and all processes share shared_buffers, PostgreSQL's page cache in shared memory. The documentation suggests about 25% of RAM for shared_buffers as a starting point on a dedicated server, leaving the rest to the operating system's page cache, which PostgreSQL relies on as a second-level cache. The default max_connections is 100, and performance usually degrades well before a few hundred active connections, because of contention on shared structures, snapshot computation that scales with the number of connections, and memory. So PostgreSQL deployments put a pooler such as PgBouncer in front: thousands of client connections share a few dozen server connections, typically in transaction mode (a server connection is assigned only for the duration of each transaction, which rules out session-level features such as some prepared-statement uses and session advisory locks).

MySQL runs a thread per connection in one process, with a much cheaper per-connection cost, so thousands of connections are routine; Uber reported running close to 10,000 on some instances. InnoDB manages its own large buffer pool (innodb_buffer_pool_size, commonly set to most of the machine's memory on a dedicated server) and usually bypasses the OS page cache for data files (O_DIRECT), so it caches pages exactly once. The same rule about active connections applies, though: throughput peaks at a small multiple of the CPU core count, and beyond that more concurrent queries mean more contention, which is why MySQL also has a thread-pool plugin and why application-side pools are sized modestly (db13).

8. Replication: physical WAL versus logical binlog

PostgreSQL's built-in streaming replication sends the WAL (db8) to standbys, which replay it exactly as in crash recovery. The result is a byte-for-byte copy of the primary's data files. It is simple, complete (everything, including indexes, sequences and DDL, is replicated automatically) and fast to apply. Its costs come from being physical: the stream contains every index insertion, every full-page image and every vacuum record, so it is as verbose as the write amplification behind it, which is Uber's replication-bandwidth complaint; standbys must run the same major version, so upgrades cannot use replication; and standbys cannot have different indexes or extra tables.

MySQL replicates from the binary log, a log of committed changes separate from InnoDB's redo log. In statement format it records SQL statements (compact, but non-deterministic statements can produce different results on replicas); in row format, the default since MySQL 5.7, it records before and after images of each changed row; mixed switches between them. Because the stream is logical, replicas apply row changes through their own storage engine and maintain their own indexes, so secondary-index churn never crosses the network, replicas can run a newer version (the standard rolling-upgrade path) and can even have different indexes. GTIDs (global transaction identifiers) give each transaction a unique id so replicas can be repointed at a new primary without calculating log positions. The costs: a second log to write and fsync on every commit (InnoDB's redo log and the binlog are coordinated with an internal two-phase commit), and logical replication's classic failure modes, such as replicas silently diverging when a statement-based change behaves differently or when someone writes directly to a replica.

PostgreSQL has had logical replication built in since version 10 (2017): a publication on the source lists tables, and a subscription on the target receives row-level inserts, updates and deletes decoded from the WAL. It replicates only chosen tables (with row filters and column lists in recent versions), works across major versions (the basis of near-zero-downtime upgrades), and feeds change-data-capture tools. Its limitations: replicated tables need a primary key or replica identity, DDL is not replicated automatically, and sequences need separate handling. In 2016, Uber's options were the pglogical extension; today it is mainline.

9. Reading on replicas

Both systems serve reads from replicas, with different conflicts. On a PostgreSQL physical standby, WAL replay may need to remove row versions (because vacuum removed them on the primary) or take locks (for DDL) that conflict with a query running on the standby. The standby waits up to max_standby_streaming_delay (30 seconds by default) and then cancels the query with a "conflict with recovery" error, which is the "Poor replica MVCC support" Uber described. Turning on hot_standby_feedback makes the standby tell the primary about its oldest snapshot so the primary's vacuum keeps those versions: no more cancellations, but long standby queries now cause bloat on the primary, exactly as a long transaction there would. The usual design is to separate concerns: short OLTP reads on standbys with default settings, long analytical queries on a dedicated standby with feedback and a generous delay, or better, in a warehouse (db12).

MySQL replicas apply logical row changes through InnoDB like any other transaction, so a long read on the replica uses its own MVCC and does not block replication or get cancelled by it. The trade-off is that the replica does all the index and undo work itself, and a single-threaded apply (older configurations) or a very long query holding locks can make it lag; MySQL's multi-threaded replica applier parallelises transactions that do not conflict.

10. Upgrades and schema changes

Uber's upgrade story, shutting down, running pg_upgrade for hours, then re-copying every replica, reflected the copy mode of pg_upgrade and physical replication's version lock. Today's options are better. pg_upgrade --link hard-links the existing data files into the new cluster instead of copying them, so even multi-terabyte upgrades take minutes, and PostgreSQL 18's pg_upgrade preserves optimizer statistics so the new cluster does not start with blind plans. For downtime of seconds, logical replication into a new-version cluster, followed by a brief write pause and switchover, is the standard method. MySQL's rolling upgrade (upgrade replicas one by one, then fail over) has long been straightforward because its replication is logical.

Schema changes differ as well. PostgreSQL supports transactional DDL: ALTER TABLE, CREATE INDEX and most other DDL can run inside a transaction and roll back atomically, a large convenience for migrations; adding a nullable column or one with a constant default is instant (since version 11), and indexes can be built without blocking writes using CREATE INDEX CONCURRENTLY. MySQL's DDL is not transactional (each statement commits implicitly), but InnoDB supports many online and, since 8.0, instant operations such as adding columns, and large teams use external online schema-change tools (gh-ost, pt-online-schema-change) for the rest. db14 covers zero-downtime migrations on both.

11. A worked comparison: one workload, two engines

Take a concrete table: sessions(session_id PK, user_id, device, created_at, last_seen_at, token_count, state jsonb) with indexes on user_id, (user_id, last_seen_at) and created_at, 50 million rows, updated about 5,000 times a second (each update sets last_seen_at and token_count), and replicated to one standby in another region.

On PostgreSQL as designed, every update changes last_seen_at, which is indexed, so no update can be HOT: each writes a new heap tuple (with the whole jsonb state, possibly a new TOAST copy if it is large and changed) and four index entries (primary key, user_id, the composite, created_at), WAL-logs them with frequent full-page images, ships all of it cross-region, and leaves a dead tuple and four dead index entries for vacuum. On InnoDB, each update rewrites the row in place, writes an undo record, and updates only the (user_id, last_seen_at) index; the binlog ships one row image.

The PostgreSQL redesign is small: drop last_seen_at from the composite index if the query "sessions of a user by recency" can use (user_id) plus a sort over a handful of rows, or move last_seen_at and token_count into a narrow session_activity(session_id, last_seen_at, token_count) table with only a primary key. Now nearly all updates are HOT on a narrow table, the wide row with jsonb is rarely rewritten, and WAL volume drops several-fold. Add fillfactor = 80 on the narrow table and an autovacuum scale factor around 0.01. This is the general lesson of the Uber debate: PostgreSQL rewards schemas that keep hot, frequently updated columns narrow and unindexed; InnoDB is more forgiving of wide, heavily indexed rows with in-place updates, and less forgiving of random primary keys.

What the PostgreSQL community said in reply

Responses to the Uber post, from PostgreSQL developers and consultants, made several technical points worth knowing. First, HOT updates (since 8.3, 2008) already avoid index writes when no indexed column changes, so the "every index for every update" claim applied to updates of indexed columns or pages with no free space; the al-Khwārizmī example updated an indexed column. Second, write amplification exists in InnoDB too, in different places: undo records, the doublewrite buffer, the binlog written alongside the redo log, and secondary index updates via delete-mark and insert. Third, the corruption Uber hit was a specific 9.2 bug, already fixed, and logical replication has its own historical class of divergence bugs. Fourth, logical replication and fast upgrades were already on their way. The consensus that emerged is that Uber's workload (very wide use of secondary indexes on update-heavy tables, cross-continental physical replication, very high connection counts, and an older version they could not upgrade) genuinely fit InnoDB's design better, while the general claims did not transfer to every workload. That is a good template for answering "which is better?" in an interview: name the mechanism, then the workload property that makes it matter.

Index-organised versus heap tables, more formally

The two layouts optimise for different pointer stability. In a heap, a row's address changes on every non-HOT update, so indexes point at addresses and must change when addresses do; but addresses are short (6 bytes) and lookups need one tree. In an index-organised table, a row's logical address (its primary key) never changes on updates, so secondary indexes stay valid unless their own columns change; but the logical address may be long and every secondary lookup pays a second tree descent. Databases have explored hybrids. Oracle offers both heap tables and index-organised tables with "guess" physical addresses in secondary indexes; SQL Server lets you choose a clustered index or a heap per table. PostgreSQL's HOT chains are a hybrid of their own: within a page, the line pointer acts as a stable logical address for a chain of versions. Proposals for additional PostgreSQL table access methods, such as undo-based storage, aim to give PostgreSQL in-place updates for tables that need them; the table access method API (since version 12) exists partly to make such engines possible.

Why 32-bit transaction ids persist

Wraparound would disappear with 64-bit transaction ids, and the question of why PostgreSQL has not simply switched comes up often. The xid fields live in every tuple header, so widening them would add 8 bytes per row on disk, about a third more header overhead, and require a full on-disk format change for every existing database. Freezing is the price paid instead. Work has gone into making freezing cheaper (the all-frozen visibility-map bit, more opportunistic freezing in recent versions) and into using 64-bit "epoch plus xid" values internally where the overhead is acceptable. For operators, the practical result is unchanged: monitor age(datfrozenxid) per database and age(relfrozenxid) for the largest tables, and alert long before 2 billion, typically at a few hundred million beyond autovacuum_freeze_max_age.

Group commit across two logs in MySQL

MySQL with binary logging has two durability logs: InnoDB's redo log and the server's binlog, which must agree about which transactions committed, or a crash could leave a transaction committed in InnoDB but absent from the binlog (so replicas never receive it), or the reverse. MySQL coordinates them with an internal two-phase commit: InnoDB prepares the transaction (redo log record flushed), the binlog event is written and flushed, then InnoDB commits. On recovery, prepared transactions are committed if their events are in the binlog and rolled back otherwise. Doing this naively costs two fsyncs per commit; MySQL's binlog group commit batches the flush stages across many transactions, so throughput under concurrency remains high. The settings sync_binlog = 1 and innodb_flush_log_at_trx_commit = 1 together give full durability; relaxing either (common in older tuning guides) trades crash safety for speed exactly as asynchronous commit does in PostgreSQL (db8).

Extensions versus storage engines

The two projects extend in different directions. MySQL's pluggable storage engine API lets entirely different storage layers sit under the same SQL layer: InnoDB, MyRocks (RocksDB, an LSM tree, used at Meta to cut storage for write-heavy data), and others, with the binlog providing a common replication layer. PostgreSQL extends upward and sideways: new data types, operators, index access methods (GIN, GiST, BRIN, and pgvector's HNSW and IVFFlat), procedural languages, foreign data wrappers and, since version 12, table access methods. For AI workloads this matters directly: pgvector makes PostgreSQL a reasonable vector store alongside relational data (db15), PostGIS covers geospatial work, and the planner treats these index types like any other. MySQL 9 added a vector type, but the ecosystem of index types and extensions is where PostgreSQL has historically been stronger.

Sentry's wraparound outage, 2015

Sentry, the error-tracking service, published a candid account of an outage caused by transaction-id wraparound protection. Their primary PostgreSQL database processed a very large, continuous stream of writes; autovacuum had been unable to finish freezing one enormous table, a mapping of events to their rollups needed for every event received, and the database reached the point where it stopped accepting writes. The team faced the questions every operator in this situation faces: is the running vacuum resumable, how long will it take, will restarting with more maintenance memory or in single-user mode help or just add downtime? They let the autovacuums finish, which took hours, only to find writes still refused because one relation, the huge mapping table, was not done. Weighing a vacuum of unknown duration against data that was not critical and was recoverable from replicas, they truncated that table, and the system was fully restored five minutes later. Their note from two days afterwards is the most telling detail: a test machine was still running a single-user-mode vacuum of the same data, going on 24 hours.

The lessons generalise. Monitor xid age per table and database with alerts far ahead of the limit. Make sure autovacuum can keep up on the largest, hottest tables (more workers, higher cost limits, per-table thresholds, and, for append-heavy event tables, partitioning so old partitions are frozen once and then left alone or dropped). Make sure nothing holds the xmin horizon back for long. And design huge, low-value mapping tables so they can be dropped or rebuilt, which is what gave Sentry its fast way out.

Bloat in practice

Symptoms of a PostgreSQL bloat problem: a table or index far larger than its live data (estimated with pgstattuple or the common bloat-estimation queries), sequential scans and index scans reading many more pages than expected, n_dead_tup in pg_stat_user_tables large relative to n_live_tup, and last_autovacuum long ago for a busy table. Causes, in order of frequency: a held-back xmin horizon (long transaction, idle-in-transaction session, stale replication slot, standby feedback), autovacuum thresholds too high for a large table, autovacuum throttled too hard to finish, and update patterns that defeat HOT. Remedies: fix the horizon first, then tune per-table autovacuum, then reclaim space with REINDEX CONCURRENTLY for indexes and an online rewrite tool (such as pg_repack) for tables, since VACUUM FULL takes an exclusive lock.

InnoDB pathologies

The InnoDB equivalents: a growing history list length from long transactions; a buffer pool too small for the working set, visible as a falling hit rate and rising disk reads; random primary keys causing page splits and fragmentation in the clustered index; and replication lag from long-running transactions or a single-threaded applier. Gap-lock contention and deadlocks at REPEATABLE READ (db9) are a frequent surprise for teams coming from PostgreSQL, and some move to READ COMMITTED to reduce them, accepting non-repeatable reads. The MySQL tools are SHOW ENGINE INNODB STATUS, the performance schema and sys schema views, and information_schema.innodb_trx for finding long transactions.

Connection storms

Uber's post mentioned outages caused by application bugs that opened more active or idle-in-transaction connections than intended. This is common to both engines but especially sharp on PostgreSQL. A deploy that doubles the number of application instances, each with a pool of 20, can exceed max_connections, at which point new connections fail outright; even below the limit, hundreds of active backends contend and memory per backend adds up. Defences: a pooler in transaction mode in front of PostgreSQL, application pools sized from the database's capacity rather than the application's (db13), idle_in_transaction_session_timeout and statement timeouts per role, and alerting on connection counts by state.

Choosing for an AI product

For an AI application's operational database (users, conversations, tool state, billing, evaluation results), either engine works, and team familiarity plus the managed service you will use usually decide. Specific features tilt it: if you want vectors next to relational data with transactional consistency, PostgreSQL with pgvector is the common choice; if you expect very wide fan-out of writes with many secondary indexes and want MySQL-ecosystem sharding (Vitess), InnoDB fits. Whichever you choose, the patterns from this lesson apply to AI-shaped data: append-only logs of model calls partitioned by time so old data is dropped rather than vacuumed, narrow hot tables for frequently updated state such as token counters, no indexes on columns that change on every message, and short transactions around model calls so neither vacuum's horizon nor InnoDB's purge is held back by an agent waiting for a model.

import random

INDEXES = {"pk": {"id"}, "name": {"first", "last"}, "birth": {"birth_year"},
           "signup": {"signup_date"}, "login": {"last_login"}}

def postgres_update(changed, page_has_room):
    # new tuple version always; HOT if no indexed column changed AND it fits on the same page
    indexed = set().union(*INDEXES.values())
    hot = page_has_room and not (changed & indexed)
    writes = {"heap": 1}
    if not hot:
        writes["index entries"] = len(INDEXES)       # every index gets an entry for the new ctid
    return writes, hot

def innodb_update(changed):
    writes = {"clustered row (in place)": 1, "undo record": 1}
    touched = [n for n, cols in INDEXES.items() if n != "pk" and cols & changed]
    if touched:
        writes["index entries"] = 2 * len(touched)   # delete-mark old entry + insert new one
    return writes

random.seed(10)
workload = ([{"last_login"}] * 70 +       # most updates touch one indexed timestamp
            [{"bio"}] * 25 +              # some touch an unindexed column
            [{"birth_year"}] * 5)
pg_total = inno_total = hot_count = 0
for changed in workload:
    w, hot = postgres_update(changed, page_has_room=random.random() < 0.8)
    pg_total += sum(w.values()); hot_count += hot
    inno_total += sum(innodb_update(changed).values())

print("one update of last_login (indexed):")
print("   postgres:", postgres_update({"last_login"}, True)[0])
print("   innodb  :", innodb_update({"last_login"}))
print("one update of bio (not indexed), room on page:")
print("   postgres:", postgres_update({"bio"}, True)[0], "(HOT)")
print("   innodb  :", innodb_update({"bio"}))
print(f"100-update mix: postgres {pg_total} writes ({hot_count} HOT), innodb {inno_total} writes")
INDEXES.pop("login")                       # drop the index on the hot timestamp
pg2 = sum(sum(postgres_update(c, random.random() < 0.8)[0].values()) for c in workload)
print(f"after dropping the last_login index: postgres {pg2} writes")

What to look for.

  1. Updating the indexed last_login: PostgreSQL writes a heap tuple and 5 index entries; InnoDB writes the row in place, an undo record and 2 index operations on the one affected index.
  2. Updating unindexed bio with room on the page: PostgreSQL does a HOT update, a single heap write, cheaper than InnoDB's row plus undo.
  3. The 100-update mix: about 485 writes for PostgreSQL versus 350 for InnoDB. Dropping the index on last_login cuts PostgreSQL to under 200, because most updates become HOT.

Try next. Change page_has_room to always False (fillfactor 100 and no pruning) and see the HOT benefit vanish. Add more indexes and watch the PostgreSQL count grow linearly while InnoDB's barely moves. If you have PostgreSQL available elsewhere, run an update workload and read SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'users', then drop an index on a frequently updated column and compare; the documentation's HOT page explains what you should see.

Diagnose: the PostgreSQL that slowed down every afternoon

A SaaS company's PostgreSQL primary gets steadily slower from late morning until a nightly batch window, then recovers. Observations: table events (2 billion rows) and its indexes keep growing although rows are deleted after 30 days; n_dead_tup on several tables is in the hundreds of millions; pg_stat_activity shows an analytics user with a transaction open since 09:00 running hourly reports in the same session; there is a logical replication slot for a CDC pipeline whose consumer was decommissioned last month; age(datfrozenxid) is 1.1 billion and rising. What is happening, how urgent is it, and what do you do, in order?

Answer

Diagnosis. Two things hold back the xmin horizon: the analytics session's transaction open since 09:00 (vacuum cannot remove anything that became dead after its snapshot, so bloat builds all day; the nightly batch window presumably ends that session, which is why things recover), and the abandoned logical replication slot, which pins the catalog horizon and, for logical slots, retains WAL indefinitely. Dead tuples accumulate, tables and indexes bloat, scans read more pages, and the cache holds less useful data.

Urgency. age(datfrozenxid) at 1.1 billion is serious: it is far past the 200 million anti-wraparound trigger, so freezing has been failing to advance, and at roughly 2 billion the server will stop accepting writes. At the current rate, estimate the days remaining from the daily xid consumption and treat it as an incident now.

Actions, in order. (1) Drop the abandoned slot (pg_drop_replication_slot) after confirming its consumer is gone. (2) End the long analytics transaction and fix the client: autocommit for reports, or one transaction per report, plus idle_in_transaction_session_timeout and a statement timeout for that role; move reporting to a replica or warehouse. (3) Let autovacuum (or a manual VACUUM (FREEZE, VERBOSE) on the oldest tables, largest first, with raised maintenance_work_mem and cost limits) advance relfrozenxid; watch age(relfrozenxid) fall. (4) For events, stop deleting rows by date: partition by day or month and drop old partitions, which produces no dead tuples and needs no freezing of soon-to-be-dropped data. (5) Reclaim existing bloat with REINDEX CONCURRENTLY and an online table rewrite. (6) Add alerts: oldest transaction age, replication slot lag and activity, dead-tuple ratios on large tables, and xid age at, say, 500 million.
