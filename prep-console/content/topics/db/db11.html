In early 2015, Discord built its first version in under two months and stored everything in a single MongoDB replica set. By the end of 2015 it held 100 million messages, and by early 2017, when the company published "How Discord Stores Billions of Messages", users were sending more than 120 million messages a day, and Discord had promised to keep every one forever. MongoDB's index on (channel_id, created_at) no longer fit in memory, latency had become unpredictable, and the team needed a database that could absorb an endless, accelerating stream of writes while still answering one query instantly: "show me the latest messages in this channel".

They chose Cassandra, a wide-column database, and the interesting part of their story is not the choice but the modelling. Cassandra has no joins, no ad-hoc secondary access paths worth relying on, and no way to scan a table efficiently by anything other than its key. So the key had to be designed around the query. Their first design used the channel as the partition key, which immediately produced warnings: some channels' partitions were over 100 MB, because a busy channel lives for years and its partition grows forever. The fix was to add a time bucket, about ten days of messages, to the partition key. Then came surprises no relational database would have produced: a message that was edited and deleted at the same moment came back as a half-empty row, because every Cassandra write is an upsert resolved by last-write-wins; and writing null into unused columns created twelve deletion markers per message, which slowed reads.

This is the core of NoSQL modelling. Relational design (db1, db2) starts from the entities and their relationships, normalizes them, and trusts the query planner (db7) to answer whatever questions come later. Document, key-value, wide-column and graph databases each give up some of that generality to make particular access patterns fast at scale, typically by storing together the data that is read together and by partitioning it across machines by key. The price is that you must know your queries first, that data is often duplicated across several shapes, and that consistency guarantees are usually weaker or need explicit choices.

The system-design lesson sc8 covered when to choose each kind of store. This lesson is about how to model data once you have chosen one: what each model physically stores, how to turn access patterns into documents, partition keys, sort keys, data structures or graph edges, and which mistakes each model punishes. It works through MongoDB embedding, Discord's Cassandra tables, DynamoDB single-table design, Redis structures and property graphs, with a running example of storing an LLM chat product's conversations in each.

From "store the facts" to "store the answers"

A relational database is like a well-organised library of facts. Each fact is filed once (normalization), and the librarian, the query planner, can assemble any answer you ask for by fetching and combining facts from different shelves. That flexibility is wonderful, but it has a cost at very large scale: combining facts from different shelves means joins, and when the shelves are spread across hundreds of machines, joins become network traffic and coordination.

NoSQL databases are more like a set of pre-packed answer boxes. If the most common question is "what's in this order?", you pack each order, with its lines and shipping address, into one box, and answering the question means fetching one box. If the most common question is "what are the latest messages in this channel?", you keep each channel's messages in one sorted pile on one machine, and answering means reading the top of the pile. Fetching one box or one pile is fast and scales: different boxes live on different machines, and no question needs more than one machine.

The analogy breaks, usefully, when the questions change. A library of facts can answer a new question with a new combination. A warehouse of pre-packed boxes can only answer the questions it was packed for; a new question ("which orders contain product 42?") may need a second set of boxes packed differently, which means writing the same facts twice and keeping both copies in step. That is the central trade of NoSQL modelling: reads are designed in advance, and writes pay for it.

The four models in one sentence each

A key-value store maps a key you can construct to a value or a small data structure. A document store stores self-contained nested documents, the natural shape of an aggregate such as an order or a conversation. A wide-column store stores partitions of rows sorted by a clustering key, spread across machines by a partition key, built for enormous write volumes keyed by entity and time. A graph database stores nodes and relationships as first-class records, built for queries that walk relationships. The rest of this lesson is how to model well in each.

What you give up, and what you get

It helps to be explicit about the trade before modelling. You usually give up joins at read time, ad-hoc queries on arbitrary fields, multi-record transactions by default, and the database's enforcement of relationships (there are no foreign keys between documents or partitions). You get predictable single-digit-millisecond reads for the patterns you designed, near-linear horizontal scaling by adding machines, very high write throughput (especially in LSM-based wide-column stores), flexible record shapes, and, in managed services, little operational work. Whether that trade is good depends entirely on whether your important access patterns are known, stable and key-shaped. When they are, NoSQL models are simple and fast; when they are not, every new question becomes a remodelling project.

1. The method: access patterns first

Every NoSQL modelling exercise starts the same way, and it is the step people skip. Write down the access patterns: each read and write the application performs, with its inputs, outputs, ordering, expected frequency and latency target. For the chat product used throughout this lesson:

#Access patternInputFrequency
A1List a user's conversations, most recent first, 20 per pageuser idevery app open
A2Load the latest 50 messages of a conversation, in orderconversation idevery conversation open
A3Append a message to a conversationconversation id, messagevery high
A4Find the owner of a conversation (for authorization)conversation idevery request
A5Count messages per model per day (analytics)date rangedaily

Then, for each important pattern, design so that it is answered by a single read: one key lookup, one partition range read or one document fetch. Patterns that cannot be served that way get their own copy of the data (a second table, an index, a summary) or are moved elsewhere: analytics like A5 almost always belong in a warehouse fed by a change stream (db12), not in the operational NoSQL store. This is the opposite of relational design, where you model the domain and trust indexes and joins to answer queries later. It is not worse, just a different contract: in exchange for planning, every listed query has predictable latency at any scale.

2. Document stores: aggregates, embedding and referencing

A document store (MongoDB, Couchbase, Firestore; also PostgreSQL's jsonb when used this way) stores each record as a nested document, typically JSON or its binary form BSON, addressed by an id, with indexes on fields inside the document. The modelling unit is the aggregate: a cluster of data that is created, read and updated together, such as an order with its lines and shipping address. Storing the aggregate as one document means one read to load it and one atomic write to change it, since single-document writes are atomic.

The central decision is embedding versus referencing. Embed when the child data is owned by the parent, read with it, bounded in size and not shared: an order's lines, a user's addresses, a conversation's settings. Reference (store an id and fetch separately) when the child is shared by many parents (a product referenced from many orders; embedding would copy it everywhere and make updates painful), large, unbounded (a post's comments, a channel's messages), updated independently at a high rate, or queried on its own. Unbounded arrays are the classic document-model failure: MongoDB documents are limited to 16 MiB, each append rewrites the document, and reading the parent drags the whole array along.

For the chat product, embedding all messages in the conversation document is tempting and fails on exactly those grounds: a long agent session can contain thousands of messages, including large tool outputs. The robust design uses the subset pattern: a conversations collection with owner, title, timestamps and the last few messages embedded (enough to render a preview), and a messages collection with {conversation_id, seq, role, content, created_at} and an index on (conversation_id, seq). A1 becomes an indexed query on {owner: uid} sorted by updated_at; A2 an indexed range read on messages; A3 an insert into messages plus a small update of the conversation's preview and timestamp.

Two more document-modelling ideas recur. Schema versioning: documents in one collection can have different shapes, so include a schema_version field and migrate lazily on read or in background batches. Validation: MongoDB supports JSON Schema validators on collections, which restore some of the guarantees a relational schema gives for free; use them for required fields and types.

3. Key-value stores: structures, not just values

A key-value store maps keys to values, and every read starts from a key the application can construct. Pure key-value stores treat the value as an opaque blob; Redis, the most widely used, offers data structures as values, which changes modelling considerably. A hash holds a small record's fields (HSET conv:c2 title "sql help" owner ana), readable or updatable field by field. A list or stream holds an ordered sequence (recent messages, a job queue). A sorted set holds members ordered by a numeric score, which makes A1 natural: ZADD user:ana:convs 1759500000 c2 on every update, then ZREVRANGE user:ana:convs 0 19 returns the 20 most recent conversation ids. Sorted sets also implement leaderboards, sliding-window rate limiters and time-ordered feeds. Keys can carry a TTL (time to live), so sessions and caches expire automatically.

Key design is the whole schema: a consistent naming convention (type:id:subtype) is the closest thing to table definitions, and every access path is a key you can compute. That makes key-value stores ideal for session state, caches, counters, rate limits, feature-flag lookups and the online half of a feature store (hd8), and poor at anything needing queries by value. Redis is primarily an in-memory store, so data size is bounded by RAM and durability depends on its persistence configuration; it is usually paired with a durable system of record rather than replacing one.

4. Wide-column stores: partitions and clustering keys

Cassandra, ScyllaDB and Google Bigtable (and HBase) are wide-column stores. Discord's post gives the best short description: Cassandra is a "KKV" store. The first K, the partition key, is hashed to decide which nodes store the data (with replication, several nodes). Within a partition, rows are identified and sorted by the second K, the clustering key, and each row holds named column values (the V). A partition behaves like a sorted dictionary on one node, stored in LSM-tree SSTables (db5). The efficient operations are: read one row by full key; read a contiguous slice of a partition by clustering-key range; write anything (writes are append-only upserts and are very cheap).

Modelling is query-first, one table per query. For A2, the partition key must contain the conversation (or channel) id, because the query supplies it, and the clustering key must order messages by time. Discord's first design was exactly that, PRIMARY KEY (channel_id, message_id), with message_id a Snowflake id (a 64-bit id whose high bits are a timestamp, so ids sort by creation time and two messages created in the same millisecond still have distinct keys). The Cassandra schema, slightly simplified:

CREATE TABLE messages (
  channel_id bigint,
  bucket     int,
  message_id bigint,
  author_id  bigint,
  content    text,
  PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

The bucket came from the problem in the introduction. Cassandra can technically hold huge partitions, but Discord saw warnings for partitions over 100 MB and learned that large partitions put pressure on garbage collection during compaction and cluster expansion, and cannot be spread across nodes. A channel lives forever, so a partition keyed only by channel grows forever. The fix is bucketing: add a coarse time window to the partition key, derivable from the message id or timestamp. Discord looked at its largest channels and chose roughly 10 days per bucket to stay comfortably under 100 MB. The lab's arithmetic shows why the bucket width depends on traffic: at about 1 KB per stored message, a channel with 1,000 messages a day fills 100 MB in about 105 days, one with 50,000 a day in about 2 days. A read of "latest 50" computes the current bucket, reads from it, and if it returns fewer than 50 rows (a quiet channel), moves to the previous bucket, and so on. Discord accepted that quiet channels need several reads, because active channels, the majority of reads, find enough messages in the first bucket.

Patterns that need a different key get a different table. A1 (a user's conversations) needs partition key user_id and clustering by last activity, so it is a second table, written alongside the first. Cassandra offers materialized views and secondary indexes to do this automatically, but both have operational caveats (views have had consistency problems; secondary indexes query every node for each lookup), so most teams write both tables from the application, often in a logged batch.

5. Writes, deletes and consistency in Cassandra

Two behaviours from Discord's post are essential to modelling correctly. First, every write is an upsert and conflicts between replicas are resolved by last-write-wins per column, using write timestamps. Cassandra discourages reading before writing, so an UPDATE of one column on a row that a concurrent request deleted simply creates a row containing that column and the key. Discord saw exactly this when an edit raced a delete: a message row with text but no author, which crashed code expecting the required field. Their fix was to treat rows missing a required column as deleted and clean them up. Designs should assume any column may be absent and avoid patterns where correctness depends on reading a value and writing back a modified one; for the rare operations that truly need compare-and-set, Cassandra's lightweight transactions (based on Paxos) exist, at several times the latency of a normal write.

Second, deletes are writes. Because replicas may be temporarily unreachable, a delete must be remembered so it can be replicated, so Cassandra writes a tombstone, which reads skip and compaction removes only after gc_grace_seconds (10 days by default). Writing null to a column is a delete and creates a tombstone too. Discord's message schema had 16 columns, of which the average message set only 4, and their code wrote nulls for the other 12: twelve tombstones per message, for nothing. Writing only non-null values removed them. Delete-heavy patterns, such as using a Cassandra table as a work queue, accumulate tombstones that reads must scan, and Cassandra aborts queries that encounter too many, so queues belong in a queue system or in a database with in-place deletes.

Consistency is tunable per request: with replication factor 3, writing and reading at QUORUM (2 of 3 replicas) guarantees a read sees the latest acknowledged write (sc6 covers quorum arithmetic), while ONE is faster and may return stale data. Choosing per access pattern, QUORUM for messages a user just sent, ONE for analytics-grade reads, is part of the model.

6. DynamoDB: partition keys, sort keys and single-table design

Amazon DynamoDB is a managed key-value and document store whose primary key is either a partition key alone or a partition key plus a sort key. Items with the same partition key form an item collection, stored together and sorted by sort key, and a single Query can return a range of them (sort key equals, begins with, between, greater than). Items are limited to 400 KB. Throughput is spread across physical partitions, each of which, per AWS's documentation, delivers at most 3,000 read units and 1,000 write units per second, so a single partition key value can never exceed those rates, however much table capacity is bought.

Because DynamoDB has no joins, a popular technique called single-table design stores several entity types in one table under generic key attributes (PK, SK) chosen so that data read together shares a partition key. For the chat product: the user's profile is PK = USER#ana, SK = PROFILE; each of her conversations is PK = USER#ana, SK = CONV#2026-10-03#c2, with the date first so the sort key orders conversations by time; each message is PK = CONV#c2, SK = MSG#0001. A1 is one Query on PK = USER#ana in descending sort order, returning the profile and the conversations together. A2 is one Query on PK = CONV#c2 with SK begins_with MSG#. The lab emulates this with a SQLite table whose primary key is (pk, sk), and its query plans show each pattern as a single range search on the key.

A4 (who owns conversation c2?) needs a lookup by conversation id, which the main key does not support. A global secondary index (GSI) gives the table a second, independently partitioned key: putting GSI1PK = CONV#c2 on the conversation item lets a Query on the GSI find it, and the item's main key reveals the owner. GSIs are maintained asynchronously, so reads from them are eventually consistent, and they consume their own write capacity, since every item written that has the GSI attributes is also written to the index. A table may have up to 20 GSIs by default. The same machinery models many-to-many relationships with the adjacency list pattern in AWS's guidance: one item per edge, keyed by one side, with a GSI keyed by the other side, so both directions are a Query.

Single-table design is powerful and often over-applied. Its benefits are real when entities are read together at high scale. Its costs are a table no human can browse, entity logic encoded in string prefixes, and difficulty adding access patterns later, since a new pattern may need a new GSI and a backfill. Separate tables per entity are perfectly reasonable when entities are accessed independently.

7. Hot partitions and write sharding

All partitioned stores share one failure: a hot partition, where one key gets a disproportionate share of traffic. Examples: a viral post's like counter, a celebrity's follower list, a table keyed by today's date so all of today's writes hit one key, a single global "settings" item read on every request. In DynamoDB the per-partition limits make this concrete: a key written more than 1,000 times a second (for items up to 1 KB) will be throttled. Remedies follow a pattern. Choose high-cardinality partition keys that spread naturally (user id, not country). Write sharding: append a suffix to hot keys (LIKES#post9#0 … #9), write to a random shard, and read all ten and sum, trading read cost for write spread. Cache hot reads in front of the store. And avoid time-only partition keys for write-heavy data; combine time with an entity or a shard number. The chat product has a natural hot-partition risk in agent sessions that stream hundreds of small token updates per second into one conversation: buffer tokens and write the message once it completes, or write chunks every few hundred milliseconds rather than per token.

8. Graph databases: relationships as data

A property graph stores nodes (with labels such as User, Account, Device, and key-value properties) and relationships (typed, directed, with their own properties, such as (:User)-[:OWNS {since: 2024}]->(:Account)). The physical trick that makes graph databases different is index-free adjacency in engines like Neo4j: each node record points directly to its relationships, so following an edge costs a pointer dereference rather than an index lookup in a join table. A traversal's cost therefore grows with the number of edges actually visited, not with table sizes.

Queries are pattern matches. In Cypher, "accounts connected to a flagged account through shared devices or cards, up to four hops":

MATCH (bad:Account {flagged: true})-[:USED|PAID_WITH*1..4]-(other:Account)
WHERE other <> bad
RETURN DISTINCT other.id;

The same query in SQL is a recursive CTE (db4) over edge tables with cycle protection, joining whole tables per hop, which the planner struggles to estimate. Graph models suit fraud and risk networks, recommendations ("people who bought this also bought"), access-control inheritance through groups, network and dependency analysis, and knowledge graphs used alongside vector search in retrieval-augmented generation, where entities and their relations extracted from documents are stored as a graph and traversed to gather context. They suit poorly: bulk aggregations over all nodes (a warehouse does those better) and simple one- or two-hop lookups, which relational indexes handle just as well with simpler operations.

9. Choosing the model from the access patterns

With the four models understood, the choice for a given workload can be reasoned rather than guessed. Take each access pattern and ask what shape the answer has. If the answer is "one record by an id I already have" and nothing else, a key-value store is the simplest fit. If it is "one self-contained aggregate with nested parts, sometimes filtered by fields inside it", a document store fits. If it is "a time-ordered slice of a very long, write-heavy sequence keyed by an entity", a wide-column store fits. If it is "everything reachable within a few hops along typed relationships", a graph fits. If the patterns are varied, change often, need ad-hoc filtering and aggregation, or need transactions across entities, a relational database fits better than any of them.

Apply that to the chat product. A1 and A4 are key lookups with a small sorted list; A2 and A3 are a write-heavy, time-ordered sequence per conversation; A5 is analytics. At modest scale (millions of messages a day), a relational database answers all five with two tables and three indexes and is the right choice. At Discord's scale (well over 100 million messages a day, kept forever), A2 and A3 dominate and justify a wide-column store, while A1 and A4 can live in the same store as separate query tables or in a key-value store, and A5 moves to a warehouse fed by change data capture. The model follows the dominant access pattern at the scale you actually have, and different parts of one product legitimately use different models.

10. Keeping duplicated data consistent

NoSQL designs duplicate data deliberately: the same conversation title in the user's list and in the conversation item, the same message in a per-channel table and a per-user table, a comment count in the post document. Each duplicate needs a defined write path, the same discipline as relational denormalization (db2). The options, from strongest to weakest: a transaction across items where the store supports it (MongoDB multi-document transactions, DynamoDB TransactWriteItems for up to 100 items, Cassandra logged batches for atomicity without isolation); writing the source of truth first and updating copies from a change stream (DynamoDB Streams, MongoDB change streams, Cassandra CDC), which is eventually consistent but robust; or best-effort dual writes from the application, which drift under failures and need a reconciliation job. Choosing per duplicate, and writing the choice down, is part of the model.

Why these models partition well

The common thread of document, key-value and wide-column stores is that each record or partition is self-contained and addressed by a key, so the system can hash the key to a machine and never needs to coordinate across machines for a single-key operation. This is what the aggregate-oriented view (popularised by Sadalage and Fowler) captures: an aggregate is a natural unit of consistency, distribution and access. A relational join or a multi-row transaction crosses aggregates, which in a partitioned system means crossing machines, needing distributed coordination (two-phase commit or consensus, db8 and sc9). NoSQL systems either forbid such operations, make them explicit and expensive (DynamoDB transactions, MongoDB distributed transactions), or provide weaker guarantees. Distributed SQL databases (Spanner, CockroachDB) take the opposite path, keeping relational semantics and paying for coordination with consensus and careful data placement. Understanding this lets you predict which operations any store will make cheap: the ones that stay within one aggregate.

LSM storage underneath wide-column stores

Cassandra, ScyllaDB, HBase and Bigtable all store partitions in LSM trees (db5), which explains several modelling rules. Writes are cheap because they go to a memtable and a commit log, so write-heavy, append-mostly data fits naturally. Reads of a partition may need to merge several SSTables, so a partition whose rows were written over a long time and frequently updated costs more to read than one written once; time-bucketed partitions are written mostly within their window and then become immutable, which keeps reads cheap. Deletes are tombstones by necessity, since data is never updated in place. And time-window compaction strategies drop entire SSTables when all their data has expired, so data with a TTL and time-bucketed keys is cheap to expire, whereas row-by-row deletes are expensive. Good wide-column models align partitions with how data is written and expired.

The cost model of a DynamoDB design

DynamoDB bills reads and writes in units tied to item size: a strongly consistent read unit covers one read per second of an item up to 4 KB (an eventually consistent read costs half), and a write unit covers one write per second of an item up to 1 KB. Two consequences shape models. First, item size matters: a 20 KB item costs 5 read units per consistent read and 20 write units per write, so splitting rarely needed large attributes (a long prompt, a tool output) into a separate item or into S3 cuts cost for the common reads. Second, every GSI that includes an item is another write, so projecting only needed attributes into GSIs and avoiding unnecessary GSIs saves money directly. A Query that reads 50 small messages in one item collection is billed by total size read, rounded up to 4 KB, so item collections of small items are efficient. Reasoning in capacity units is the DynamoDB equivalent of reading a query plan.

Multi-model and convergence

The categories are blurring. PostgreSQL with jsonb, GIN indexes and pgvector is a competent document and vector store with SQL and transactions around it; MongoDB has multi-document ACID transactions, joins via $lookup, schema validation and vector search; DynamoDB has transactions and, recently, vector indexes; Redis has modules for JSON documents and search; graph query languages are being standardised as GQL (ISO, 2024), and SQL itself gained property-graph queries (SQL/PGQ) in SQL:2023. The practical consequence is that the choice is less about which model a product can express and more about its storage engine, scaling model, consistency guarantees, operational maturity and cost at your access patterns. Model the access patterns first; then the product choice is usually clear.

Schema evolution without a schema

Changing a NoSQL model is a data migration even though no DDL is run. Adding an optional field is easy: old documents simply lack it, and code handles both. Changing a key structure (a new partition key, a different sort-key format, a new GSI attribute) requires rewriting every affected item, usually by backfilling with a scan in batches while the application writes both old and new forms, then switching reads, then cleaning up: the same expand-contract pattern as relational migrations (db14), but without database support for online index builds in some stores and with capacity costs for the backfill. Versioned documents (a v attribute) and readers that tolerate multiple versions make these migrations survivable. This is the hidden cost behind "schemaless": the schema exists in every reader, and every reader must be updated.

Discord's migration, as a production pattern

Discord's 2017 migration is a template worth knowing in detail because each step generalises. They modelled from the one critical access pattern (read recent messages by channel), chose a key that served it with one partition read, and discovered the unbounded-partition problem during the import, not in production, because they loaded real data first. They dark-launched: the application wrote to both MongoDB and Cassandra and read from both, comparing, before any user depended on Cassandra; that surfaced the null author_id bug from last-write-wins before it reached users. They found the tombstone waste by looking at what was actually being written. And they accepted a known trade-off (quiet channels need more bucket reads) after measuring that most reads hit active channels. Discord later moved the same data model from Cassandra to ScyllaDB, keeping the key design; the modelling outlived the database.

Common production failures by model

Document stores: documents that grow without bound (embedded arrays of comments, events or messages) until writes slow and the 16 MiB limit is hit; missing indexes causing collection scans that look fine in development; and inconsistent document shapes after years of schema drift, crashing readers that assumed a field. Key-value: memory exhaustion and evictions in Redis when keys lack TTLs; a single huge key (a sorted set with millions of members) blocking the single-threaded server during large operations; and cache stampedes on hot keys. Wide-column: large partitions, tombstone-heavy reads, hot partitions, and slow repairs. DynamoDB: throttling on hot keys; scans used as queries (a Scan reads and bills the whole table); GSIs with insufficient capacity throttling writes to the base table; and costs dominated by oversized items. Graph: "supernodes" with millions of relationships (a celebrity, a default device id shared by many accounts) that make every traversal through them explode, needing degree limits or modelling changes.

Observability that matters

For each store, a few metrics map directly onto modelling problems. Partition-level metrics: DynamoDB's CloudWatch Contributor Insights shows the most accessed and most throttled keys; Cassandra's nodetool tablehistograms and table statistics show partition size distributions and tombstones scanned per read. Document stores: slow-query logs and plans showing collection scans; document size distributions. Redis: memory usage, evictions, keyspace hits and misses, and the slow log for large-key operations. Track these against the access-pattern list: each pattern should have a latency and cost budget, and a regression usually traces to one key, one partition or one document shape.

AI workloads on NoSQL

Several AI-system components map naturally onto these models. Online feature stores are key-value lookups by entity id with strict latency budgets (hd8), commonly on Redis or DynamoDB, fed by batch and streaming pipelines; the hot-partition and item-size rules apply directly. Chat and agent state is an append-heavy timeline per conversation, the Discord pattern, with the added twist of very large items (tool outputs, retrieved documents, images) that should be stored in object storage with pointers. Caches of LLM responses keyed by a hash of the prompt and parameters are classic key-value with TTLs. Knowledge graphs for retrieval store extracted entities and relations as a property graph, traversed to expand context around retrieved chunks. And vector search, increasingly offered inside these same stores, adds its own modelling questions (filtering, tenant isolation) covered in db15. In each case the method is the same: list the access patterns, design one cheap read per pattern, and define how duplicated data stays consistent.

Goal: size Cassandra time buckets from traffic, and emulate DynamoDB single-table design with a composite-key B+ tree to see each access pattern become one range read. Python 3.12 standard library. Save as db11.py.

LIMIT = 100 * 2**20                      # keep partitions under ~100 MB
for per_day in (1_000, 50_000, 500_000):
    days = LIMIT / (per_day * MSG_BYTES)
    print(f"channel with {per_day:>7,} msgs/day: one partition fills 100 MB in {days:8.1f} days")

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE items (pk TEXT, sk TEXT, gsi1pk TEXT, gsi1sk TEXT, data TEXT, PRIMARY KEY (pk, sk)) WITHOUT ROWID")
db.execute("CREATE INDEX gsi1 ON items (gsi1pk, gsi1sk)")      # a 'global secondary index'
rows = [
    ("USER#ana", "PROFILE",               None,           None,          {"name": "Ana"}),
    ("USER#ana", "CONV#2026-10-01#c1",    "CONV#c1",      "META",        {"title": "trip plan"}),
    ("USER#ana", "CONV#2026-10-03#c2",    "CONV#c2",      "META",        {"title": "sql help"}),

]
db.executemany("INSERT INTO items VALUES (?,?,?,?,?)", [(*r[:4], json.dumps(r[4])) for r in rows])

def query(sql, *args):
    plan = " | ".join(r[3] for r in db.execute("EXPLAIN QUERY PLAN " + sql, args))
    out = [(pk, sk) for pk, sk, *_ in db.execute(sql, args)]
    print(f"   {out}\n   plan: {plan}")

print("A1 user profile + conversations, newest first (one partition, one range read):")
query("SELECT pk, sk, data FROM items WHERE pk = ? ORDER BY sk DESC", "USER#ana")
print("A2 messages of conversation c2 in order:")
query("SELECT pk, sk, data FROM items WHERE pk = ? AND sk BETWEEN 'MSG#' AND 'MSG#~'", "CONV#c2")
print("A3 which user owns conversation c2 (inverted lookup via the GSI):")
query("SELECT pk, sk, data FROM items WHERE gsi1pk = ?", "CONV#c2")

What to look for.

  1. Part 1: at about 1 KB per message, a 100 MB partition holds about 105 days of a 1,000-message-a-day channel but only about 2 days of a 50,000-a-day channel, and a few hours of a 500,000-a-day one. Bucket width must be set from the busiest channels, which is how Discord arrived at about 10 days.
  2. A1 returns the profile and both conversations, newest first, from one item collection; the plan is a single SEARCH … USING PRIMARY KEY (pk=?).
  3. A2 is a range on the sort key within one partition: (pk=? AND sk>? AND sk<?).
  4. A3 uses the emulated GSI to go from conversation id back to its owner, the inverted access path.

Model: an LLM evaluation results store in DynamoDB

An ML platform team records evaluation results: each run evaluates one model on one dataset of 5,000 to 50,000 cases; each case result has a score, latency, token counts and a 2-20 KB output text. Access patterns: (P1) show a run's summary and its 100 worst-scoring cases; (P2) list runs for a model, newest first; (P3) compare one case's score across the last 10 runs of a model; (P4) fetch one case result's full output. About 200 runs a day; runs write results at up to 2,000 per second. Design the keys, indexes and item layout, and call out capacity risks.

Answer

Items. Run summary: PK = RUN#r1, SK = SUMMARY with model, dataset, started_at, aggregate scores. Case results: PK = RUN#r1, SK = CASE#c123 with score, latency and token counts, but not the output text; store outputs in S3 at a key derived from run and case (or as a separate item SK = OUT#c123) so the common reads stay small. P4 is then a GetItem plus an S3 fetch.

P1 worst cases. A sort key that orders by score within the run: add attributes GSI1PK = RUN#r1, GSI1SK = SCORE#0.1234#c123 (zero-padded so string order equals numeric order), and Query GSI1 ascending with Limit 100. The summary is a GetItem on the main key.

P2 runs per model. On the summary item, GSI2PK = MODEL#m7, GSI2SK = RUN#2026-10-03T12:00#r1; Query descending. Volume is small (200 runs a day across models), so no hot-partition risk.

P3 one case across runs. Add GSI3PK = MODEL#m7#CASE#c123, GSI3SK = started_at on case items, and Query the 10 newest. This index receives every case result write, so it doubles write cost; if P3 is rare, consider instead looking up the last 10 run ids via P2 and doing 10 GetItems.

Capacity risks. During a run, all 2,000 writes per second go to PK = RUN#r1, a single partition key value, which exceeds the 1,000 write units per second per-partition limit even for 1 KB items. Shard the run's case items: PK = RUN#r1#S{case_id mod 8}, and read the 8 shards in parallel for run-wide queries; GSI1's partition key needs the same treatment or the index throttles and back-pressures the table. Item sizes: keeping outputs out of the result items keeps writes at about 1 write unit each. Finally, analytics across runs (trends per dataset, per model) should come from a DynamoDB export to S3 queried by a warehouse engine, not from scans.
