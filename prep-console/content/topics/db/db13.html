The HikariCP project, maintainers of one of the most widely used Java connection pools, keeps a short wiki page called "About Pool Sizing" that begins with a scenario: a website with 10,000 users making database requests simultaneously, about 20,000 transactions per second. How big should the connection pool be? Most engineers' instinct is "big": thousands of connections, one per concurrent user, or at least hundreds. The page points to a demonstration by Oracle's Real-World Performance group in which a system's pool was cut from 2,048 connections to 96, with no other change, and response times fell from about 100 milliseconds to about 2: fifty times faster with twenty times fewer connections. Its conclusion is that even 96 was probably too many unless the database had 16 or 32 cores.

That counter-intuitive result is typical of the boundary between application code and the database, which is where a large share of real-world database performance problems actually live. The database itself may be well designed, normalized, indexed and tuned, and the application can still make it slow by opening too many connections, by asking for data one row at a time in a loop, by paginating in a way that gets slower on every page, by holding transactions open while it waits for something else, or by retrying writes in a way that duplicates them. None of these are visible in the schema. They are visible in how the application talks to the database.

Many of them come from abstractions that are genuinely useful. Object-relational mappers (ORMs) let developers work with objects rather than SQL strings, and their lazy loading, which fetches related data only when you touch it, makes code simple. It also makes it easy to write a loop that sends one query per item. GitLab's development guidelines take this seriously enough to enforce a budget: each controller, API endpoint or background worker may run at most 100 SQL queries, and the test suite raises an error when one exceeds it.

This lesson works through the application side of the database. It explains what a connection costs and how to size pools with a simple law from queueing theory, how poolers such as PgBouncer multiplex connections and what they break, how ORMs turn code into SQL and how to count and fix N+1 queries, why OFFSET pagination degrades and how keyset pagination fixes it, and the habits that keep transactions short and retries safe. The lab measures N+1 and OFFSET on a million rows. Throughout, the examples include LLM-backed services, which add a new hazard: requests that spend seconds waiting on a model while holding database resources.

The database is a shared, remote, limited resource

From inside application code, a database call looks like a function call: post.author.name, Order.objects.filter(...). That illusion is the source of most problems. Three facts break it.

First, the database is remote. Every query is a round trip over the network: serialise the request, send it, wait for the database to parse, plan and execute it, receive the result. Even inside one data centre, a round trip costs roughly a few hundred microseconds to a millisecond before the query does any work. A function call costs nanoseconds. Code that makes a hundred small database calls where one would do pays the round trip a hundred times.

Second, the database is shared. Every application instance, worker and analyst talks to the same server. Connections, locks, memory and CPU are shared among all of them, so one request's habits (holding a transaction open, scanning a large table) affect everyone else's latency.

Third, the database is limited. It can only execute as many queries truly in parallel as it has CPU cores and I/O capacity. Ask it to run more at once, and it does not get more done; it time-slices between them, adding overhead, while they contend for the same locks and buffers.

A restaurant kitchen

Think of the database as a restaurant kitchen with eight cooks (cores), and of connections as order tickets on the rail. If waiters put 8 or 16 tickets on the rail, cooks work steadily and food comes out fast. If waiters put 2,000 tickets up because there are 2,000 diners, the cooks do not cook faster; they spend their time reading tickets, switching between dishes and bumping into each other at the stove, and every dish takes longer. The right design is for waiters to hold orders at the front (the connection pool's queue) and feed the kitchen only as fast as it can cook. That is the pool-sizing result in one picture.

The analogy also covers the other topics. A waiter who goes to the kitchen once per ingredient instead of once per order is the N+1 problem. A waiter who keeps a ticket on the rail while chatting with a table, so the cooks keep the station reserved, is a transaction held open across a slow external call. And a waiter asked for "the 9,001st order of the day" who counts through the first 9,000 tickets each time is OFFSET pagination.

What this lesson gives you

Each section below turns one of those habits into a rule you can check in code review. How many connections can this service open in total, and is that a small multiple of the database's cores? Where does each transaction start and end, and does anything slow happen in between? How many queries does this endpoint run, and does the number grow with the size of the list it renders? How does this list paginate, and what happens on page 10,000? If this write is retried, can it happen twice? None of these questions needs database internals to answer, only an honest look at what the application actually sends.

1. What a connection costs

Opening a connection to PostgreSQL involves a TCP handshake, usually a TLS handshake, authentication (with SCRAM, several messages), and on the server, forking a new backend process that allocates its own memory and builds caches of catalog information as queries run. Altogether that is commonly a few milliseconds, sometimes tens of milliseconds over TLS across zones, compared with sub-millisecond simple queries. MySQL's thread-per-connection model is cheaper per connection, but the handshake and authentication costs remain. And every open connection consumes server memory whether or not it is busy: a PostgreSQL backend that has run a few queries can easily hold several megabytes, and more if queries used large work_mem sorts.

So the first rule is to reuse connections. A connection pool keeps a set of open connections and lends one to each unit of work: the application borrows a connection, runs its transaction, and returns it. Most frameworks provide one (SQLAlchemy's engine pool, HikariCP for Java, the pools in Go's database/sql and in Node drivers). The pool also acts as a limiter: when all connections are lent out, further requests wait in the pool's queue for one to come back, up to a timeout, which protects the database from overload.

2. Sizing the pool with Little's law

Little's law says that in any stable system, the average number of items inside equals the arrival rate times the average time each spends inside: L = λW. Apply it to connections. If a service runs 2,000 transactions per second and each holds a connection for 5 ms (including network time), then on average 2,000 × 0.005 = 10 connections are in use. A pool of 20 to 30 gives headroom for bursts and variance. A pool of 200 adds nothing: the extra connections sit idle, or, worse, under a burst they all become active at once and the database's work per query rises.

The upper bound comes from the database's capacity. The HikariCP guide's starting formula for a single database is connections = (core_count × 2) + effective_spindle_count, where the spindle term accounts for I/O waits on spinning disks (for SSD-backed or fully cached data it is near zero). The reasoning: with no I/O waits, a core can only run one query at a time, so connections beyond the core count just time-slice; I/O waits let a few more connections keep the CPUs busy. For a 16-core database that suggests roughly 32 active connections in total, which is far fewer than most teams configure. Their benchmark chart of PostgreSQL throughput flattens around 50 connections.

Two consequences follow. The limit is total active connections across all application instances, so pool size per instance must be divided accordingly: 10 instances × 20 connections = 200, already several times too many for a 16-core database. And the cost of holding a connection grows with everything done while holding it, so the most effective way to need fewer connections is to hold each for less time: shorter transactions, no external calls inside them, fewer round trips per transaction.

3. Poolers: PgBouncer and its modes

Application-side pools work per process. With many processes (a Python service running 200 worker processes, serverless functions that each open their own connection), the total still explodes. An external pooler sits between applications and the database and multiplexes: thousands of client connections to the pooler, a few dozen server connections from the pooler to PostgreSQL. PgBouncer is the standard choice; cloud providers offer managed equivalents. Its default_pool_size is 20 server connections per user and database pair, and its pool_mode decides when a server connection returns to the pool:

  • Session (the default): a client keeps its server connection until it disconnects. Safe for all features, but provides little multiplexing; it mostly saves connection setup time.
  • Transaction: a client gets a server connection only for the duration of each transaction. Between transactions, the same server connection may serve other clients. This is the mode that makes thousands of clients share a few dozen connections.
  • Statement: a server connection is returned after every statement, so multi-statement transactions are not allowed. Rarely used.

Transaction mode has one important consequence: session state does not survive between transactions, because the next transaction may run on a different server connection. Anything that lives in the session breaks: a plain SET search_path or SET timezone (use SET LOCAL inside the transaction, or set defaults on the role), temporary tables, session-level advisory locks (use transaction-level ones), LISTEN/NOTIFY, and cursors held across transactions. Named prepared statements were historically a problem too; PgBouncer 1.21 added tracking of protocol-level prepared statements in transaction mode, enabled with max_prepared_statements. Knowing this list prevents a class of bugs that appear only after a pooler is introduced.

4. Transactions in request code

Each request should treat a transaction as a short, precise unit: begin, do the reads and writes that must be atomic, commit. The rules that keep systems healthy are simple to state and easy to violate through frameworks:

Never hold a transaction across external work. An HTTP call to a payment provider, a message-queue publish, a file upload or an LLM request can take seconds. During that time the transaction holds its row locks (blocking other writers, db9), its snapshot (blocking vacuum, db10), and its connection (unavailable to the pool). Structure the code as: short transaction to read and perhaps reserve; commit; external call; short transaction to record the result. To make the second transaction safe against concurrent changes, use an optimistic version check or a status transition (UPDATE … WHERE status = 'pending').

Know where your framework starts transactions. Some frameworks wrap each request in a transaction automatically (Django's ATOMIC_REQUESTS, many Spring @Transactional configurations); then an external call anywhere in the request is inside it. Others use autocommit until told otherwise. Read the configuration and make transaction boundaries explicit in important paths.

Set timeouts on the database side. statement_timeout caps any single statement; idle_in_transaction_session_timeout terminates sessions that opened a transaction and stopped sending commands; lock_timeout caps waits for locks. Set them per role, so application roles get tight limits and migration or analytics roles get looser ones. Without them, one bug can hold locks and snapshots indefinitely.

5. How ORMs turn code into SQL

An ORM maps classes to tables and objects to rows. session.get(Post, 42) becomes SELECT … FROM post WHERE id = 42; changing post.title and committing becomes an UPDATE; post.author is a relationship mapped through the author_id foreign key. Two ORM mechanisms matter most for performance. The unit of work tracks changes to loaded objects and writes them together at flush or commit, which is convenient but means writes happen later than the line of code that caused them. And relationship loading decides when related objects are fetched, which is where N+1 comes from.

By default, most ORMs use lazy loading for relationships: post.author issues SELECT … FROM author WHERE id = ? the first time it is accessed. In isolation that is reasonable. In a loop over 100 posts, it is 100 extra queries. The alternatives are eager loading strategies, named differently in each ORM but the same two ideas:

Use the join for to-one relationships (each post has one author), where it adds columns but not rows. Use the batched IN query for to-many relationships (each post has many comments), where a join would repeat each post's columns once per comment and multiply rows (the db3 fan-out), and where a LIMIT on posts would cut off comments.

6. Counting an N+1, worked

The lab renders a page of 100 posts with their author names three ways, on a table of a million posts and 10,000 authors. The lazy version runs one query for the posts and then one per post for its author: 101 queries. The batched version runs the posts query and one SELECT … WHERE id IN (…) with the distinct author ids: 2 queries. The join version runs 1 query.

Because SQLite runs inside the Python process, all three are fast in the lab (about 0.5, 0.3 and 0.1 ms), which is exactly why N+1 hides in development with a local database. Add a realistic network round trip of 0.5 ms per query, as the lab does arithmetically, and the picture changes: about 51 ms for the lazy version, 1.3 ms for the batched version, 0.6 ms for the join. The query work is identical; the difference is 99 round trips. With a database in another availability zone (1-2 ms round trips) the lazy page takes 100-200 ms. And the count scales with the data: a page that lists 500 items with two lazy relationships each makes 1,001 queries.

N+1 has variants that are harder to spot: a template that touches order.customer.address.city fires three lazy loads per row; a serializer that includes a nested relationship; a loop that calls a helper which queries one row at a time; a GraphQL resolver per field. The defence is measurement. Count queries per request in tests and fail when a budget is exceeded, which is what GitLab's query count limit does with a default of 100 per controller, endpoint or worker; Django's assertNumQueries, Rails' Bullet gem and Python's nplusone library automate it. In production, pg_stat_statements shows a query shape such as SELECT … FROM author WHERE id = $1 with a call count far higher than the request rate, which is the signature of N+1.

7. OFFSET pagination and its costs

The simplest way to page through a sorted list is ORDER BY created_at, id LIMIT 100 OFFSET 900000 for page 9,001. With an index on (created_at, id), the database walks the index in order, but it must still step over the first 900,000 entries and discard them before returning the next 100: OFFSET is not a jump, it is a count. The lab measures it on a million posts: about 25 ms for that page, against about 0.1 ms for the first page, and the cost grows linearly with depth. Without a usable index it is worse: the database sorts the whole table (or keeps a top-N heap of 900,100 rows) for every page request.

OFFSET also gives wrong results when data changes between requests. A user reads page 1 (rows 1-100); a new row is inserted at the top; they request page 2 with OFFSET 100 and see row 100 again, now shifted to position 101. Deletes cause the opposite: a row is skipped. For feeds that update constantly, users see duplicates and gaps.

8. Keyset pagination

Keyset pagination (also called seek pagination) remembers where the previous page ended instead of how many rows to skip. The sort order must be total, meaning no two rows can tie, which is guaranteed by appending a unique column (usually the primary key) to the sort: ORDER BY created_at, id. The first page is an ordinary LIMIT 100. Each following page uses the last row's sort key values:

SELECT id, title FROM post
WHERE (created_at, id) > ($last_created_at, $last_id)
ORDER BY created_at, id
LIMIT 100;

The row-value comparison (a, b) > (x, y) means "a > x, or a = x and b > y", which is exactly "after the last row in sort order", and an index on (created_at, id) serves it as one descent to the starting point followed by reading 100 entries. The lab's keyset query returns the same 100 rows as OFFSET 900000 (the script asserts it) in about 0.1 ms, the same as the first page. Every page costs the same at any depth, and inserts or deletes elsewhere do not shift pages, because each page is anchored to a key, not a position. For descending feeds, flip the comparison and the sort: WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC.

Two practical notes. Some databases do not optimise row-value comparisons well (older MySQL versions in particular); the equivalent expanded form, WHERE created_at > $1 OR (created_at = $1 AND id > $2), works everywhere but may need care to use the index. And APIs should not expose raw keys: encode the last key as an opaque cursor string (often base64 of a small JSON object, sometimes signed), returned with each page and passed back for the next, which also lets the server change the sort key later. Keyset pagination gives up jumping to page 37 directly and exact total page counts; most feeds and APIs need only next and previous, and totals can be estimates.

9. Bulk writes and round trips

The N+1 lesson applies to writes too. Inserting 10,000 rows with 10,000 separate INSERT statements in autocommit mode costs 10,000 round trips and 10,000 commits, each a WAL flush (db8). The same rows in one transaction cost one commit; as one multi-row INSERT … VALUES (…), (…), … per few hundred rows, a few dozen round trips; via PostgreSQL's COPY (or the driver's bulk API), a single streaming operation that is typically an order of magnitude faster still. ORMs have bulk APIs (bulk_create, insert_many, SQLAlchemy's executemany "insertmanyvalues" mode) that bypass per-object overhead. For updates, a single UPDATE … FROM (VALUES …) or an update joined to a temporary table replaces thousands of per-row statements. Background jobs that backfill or migrate data should always batch, typically 1,000 to 10,000 rows per transaction, small enough to keep locks and transactions short and large enough to amortise round trips (db14).

10. Parameters, prepared statements and injection

Every query that includes a value from outside should send that value as a bound parameter, not by string concatenation: cursor.execute("SELECT … WHERE email = %s", (email,)), never f"… WHERE email = '{email}'". Concatenation lets input such as ' OR '1'='1 become part of the SQL, which is SQL injection, still one of the most exploited vulnerability classes (swe13). Parameters are sent separately from the SQL text, so they can never change its structure. ORMs parameterise automatically; raw SQL helpers inside ORMs (text(), raw()) need explicit parameters. Identifiers (table or column names chosen at run time) cannot be parameters and must be validated against an allow-list.

Bound parameters also enable prepared statements: the server parses and plans a statement once and executes it many times with different values, saving planning time for frequent queries. The trade-offs are the generic-plan issue for skewed data (db7) and the session-state issue with transaction-mode poolers (section 3). For LLM features that generate SQL (text-to-SQL), the same principles apply with more force: run generated queries through a read-only role with tight timeouts, never interpolate user or model text into SQL outside parameters, and validate the statement shape before execution.

11. Reading less: projections, streaming and caching

Round trips are one cost; the volume of each response is another. ORMs load whole objects by default, every column of every row, including large text and JSON columns that the page never shows. Selecting only the needed columns (SQLAlchemy's load_only, Django's only or values, Rails' select or pluck) shrinks network transfer and, more importantly, the CPU and memory spent building objects, which for large result sets often exceeds the query time itself. When a job must process millions of rows, fetch them with a server-side cursor or in keyset-ordered batches rather than loading the whole result into memory, so memory stays flat and the first rows are processed while later ones are still being read.

Caching removes queries entirely, at the price of staleness. Read-mostly reference data (plans, model price lists, feature flags) can be cached in process for seconds to minutes; per-user or per-tenant data can be cached in Redis with explicit invalidation on write. The common bug is caching inside a transaction-sensitive path, for example reading a cached balance and then writing a new one, which reintroduces the lost update that row locks were preventing (db9). Cache values you only display; read authoritative values inside the transaction that changes them.

12. Retries and idempotency

Database calls fail transiently: connections drop during failovers, serialization failures and deadlocks abort transactions (db9), statements time out. Retrying is correct only when the operation is safe to repeat. Reads are. A whole transaction aborted by a serialization failure or deadlock is (it did nothing), so the retry must re-run the entire transaction, including its reads. The dangerous case is an ambiguous failure: the connection dropped after the client sent COMMIT but before the response arrived. The transaction may or may not have committed, and blindly retrying an insert can create a duplicate order or a second charge.

The standard fix is an idempotency key: the client generates a unique key per logical operation, the server stores it under a unique constraint in the same transaction as the operation's effects, along with the result, and a retry with the same key finds the stored result and returns it instead of acting again. Natural unique constraints achieve the same where they exist (one payment per invoice id). Combine with retry policies that retry only known-transient errors (connection errors, SQLSTATE 40001 and 40P01), use exponential backoff with jitter, and cap attempts. For LLM agents, whose steps are often retried by an orchestrator, an idempotency key per tool call is what prevents a retried step from writing the same result twice.

Why too many connections hurt PostgreSQL specifically

Beyond generic CPU time-slicing, PostgreSQL has structural reasons to dislike many active connections. Computing a snapshot (db9) historically required scanning an array with an entry for every backend, so snapshot cost grew with connection count; PostgreSQL 14 substantially improved this, making many idle connections much cheaper, but active ones still contend. Every backend that touches shared buffers, the lock manager, the WAL insertion locks or the proc array takes lightweight locks (LWLocks) on shared structures, and with hundreds of active backends those locks become hot. Each backend also keeps private caches of catalog data and plans, so memory grows with connections times schema size; databases with thousands of tables (common in multi-tenant schema-per-tenant designs) can spend gigabytes on per-backend caches. The pooling answer is not just about connection setup cost; it is about keeping the number of simultaneously active backends near the hardware's real parallelism.

Queueing theory behind pool sizing

Little's law gives the average, but latency depends on variance. As utilisation of a server approaches 100%, queueing delay grows sharply (for a simple single-server queue, waiting time is proportional to ρ / (1 − ρ), where ρ is utilisation), so a database running at 95% has far longer queues than one at 70%. Pool limits decide where that queue forms. With a small pool, excess requests queue in the application, where the wait is cheap (an idle coroutine or thread), visible in pool metrics, and bounded by a timeout that can shed load gracefully. With a huge pool, the queue forms inside the database as runnable backends and lock waiters, where waiting is expensive and slows everyone. This is the same insight as the HikariCP and Oracle demonstrations, stated generally: put the queue in front of the bottleneck, not inside it. It also suggests what to monitor: pool wait time and pool timeouts are the leading indicators that the database, not the application, needs more capacity or less work.

The ORM impedance mismatch

Object graphs and relational tables represent data differently, and every ORM pays for bridging them. Objects navigate by reference (order.customer.address); tables relate by keys and are queried in sets. Objects have identity (the same customer object should appear once in memory however many orders reference it), which ORMs maintain with an identity map per session; tables have only key values. Objects have inheritance; tables need one of the subtype mappings from db1. Lazy loading is the ORM's way of making references navigable without loading the whole database, and N+1 is its natural failure mode. The practical stance most experienced teams adopt is to use the ORM for writes and simple reads (where identity maps, unit of work and validation help), configure eager loading deliberately per use case, and write SQL (or the ORM's query builder at the SQL level) for reporting, bulk operations and anything performance-critical. Treat the generated SQL as an output to review, not an implementation detail.

Pagination beyond the basics

Several refinements of keyset pagination come up in practice. Sorting by a non-unique column (price, score) always needs the unique tie-breaker, and the index must include it in the same order. Sorting by a computed or mutable value (relevance, a like count that changes) means the key of the last seen row may have changed by the next request; feeds either snapshot the ranking (store ranked ids for the session) or accept small inconsistencies. Backward pagination reverses comparison and order, then reverses the result in the application. Totals: exact COUNT(*) over large filtered sets is expensive in MVCC databases (no cached count; db9), so many products show estimates from planner statistics (EXPLAIN's row estimate or pg_class.reltuples) or "more than 10,000". For search results ranked by a relevance score in a search engine, deep pagination is usually capped altogether, because computing the 10,000th result exactly requires scoring and sorting everything before it.

Serverless and connection management

Serverless functions and autoscaling containers make connection management harder: each instance opens its own pool, instances appear and disappear by the hundred, and a traffic spike can create thousands of connections in seconds. The patterns that cope are an external pooler or managed proxy (such as PgBouncer or a cloud provider's database proxy) that absorbs client connections, very small per-instance pools (often 1-2), aggressive idle timeouts so dying instances release connections, and HTTP-based database APIs for some serverless databases that avoid persistent connections entirely. The capacity rule does not change: total active connections must stay near what the database can run in parallel.

The pool-sizing incident pattern

A recognisable incident: traffic grows, latency rises, someone raises the application's pool size from 20 to 100 per instance "to handle more load", and latency gets worse, sometimes catastrophically, because the database is now running several times more active queries than it has cores, contending on locks and memory. The Oracle demonstration cited by HikariCP is the canonical illustration: shrinking the pool from 2,048 to 96 connections improved response times about fiftyfold. The diagnostic signals are many active backends in pg_stat_activity with wait events on LWLocks or locks, database CPU not saturated by useful work, rising context switches, and application pool metrics showing connections busy but slow. The fix is the reverse of the instinct: reduce total connections to a small multiple of cores, add a pooler in transaction mode if there are many application processes, and let excess requests wait in the application, where they can be shed with timeouts.

Connection storms and exhaustion

The opposite failure is running out. PostgreSQL's max_connections (100 by default) is a hard limit, with a few slots reserved for superusers; when it is reached, new connections fail with "too many clients". Common triggers are a deploy that briefly doubles instances (old and new both running), a retry loop that opens new connections on every failure, connection leaks (code paths that borrow and never return, especially on exceptions), and idle-in-transaction sessions that hold connections indefinitely. Defences: a pooler in front, pool limits sized for deployments, leak detection in the pool library (HikariCP's leak detection threshold, SQLAlchemy's pool logging), always returning connections in finally or context managers, and alerts on connection counts by state and by application name (set application_name per service so pg_stat_activity shows who owns what).

Query budgets and visibility

GitLab's query count limit is an example of a cheap, effective guardrail: tests fail when an endpoint exceeds 100 queries, and exceptions require choosing an explicit higher threshold, so N+1 regressions are caught in code review rather than in production. Complementary production tooling: application performance monitoring that shows queries per request and the call sites that issued them; pg_stat_statements to find query shapes with call counts out of proportion to traffic; and slow-query logging with auto_explain for the long tail. A useful dashboard metric is "queries per request" per endpoint over time; a step change after a deploy is almost always a new lazy load.

Pagination in public APIs

Public APIs that started with page numbers often migrate to cursors when datasets grow: deep OFFSET pages become slow enough to time out, and integrators syncing data with page numbers miss or duplicate records as data changes during the sync. The migration path is to add cursor-based pagination alongside page numbers, cap the maximum OFFSET (for example, refuse pages beyond 100), and document that cursors are opaque. For data export use cases, offer a dedicated bulk export (a file or a change feed) rather than encouraging clients to page through millions of records.

Patterns for LLM-backed services

LLM features stress every topic in this lesson. Request durations are long (seconds of generation), so any transaction or connection held across a model call multiplies connection needs by orders of magnitude: a service doing 50 requests per second with a 4-second model call inside a transaction needs about 200 connections by Little's law; with the model call outside, perhaps 2. Agent loops issue many small database operations per step, which are prone to N+1 patterns over tool results. Streaming responses tempt per-token writes; batch them. Retries are common (rate limits, timeouts), so idempotency keys per request and per tool call are essential. And conversation history reads are a natural keyset pagination: load the last 50 messages by (conversation_id, seq) descending, then older ones on demand, never by OFFSET.

Goal: count the queries and time of N+1 versus batched versus joined loading, and compare OFFSET with keyset pagination on a deep page, using a million-row SQLite table. Python 3.12 standard library. Save as db13.py; building the table takes a few seconds.

import random, sqlite3, time

random.seed(13)
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE author (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE post (id INTEGER PRIMARY KEY, author_id INT, created_at INT, title TEXT);
CREATE INDEX post_created ON post (created_at, id);
""")
db.executemany("INSERT INTO author VALUES (?, ?)", [(a, f"author{a}") for a in range(10_000)])
db.executemany("INSERT INTO post VALUES (?,?,?,?)",
               [(p, random.randrange(10_000), p, f"post {p}") for p in range(1_000_000)])

queries = 0
def q(sql, args=()):
    global queries
    queries += 1
    return db.execute(sql, args).fetchall()

def timed(label, fn):
    global queries
    queries = 0
    t0 = time.perf_counter(); fn(); ms = (time.perf_counter() - t0) * 1000
    rtt = 0.5                                          # ms per round trip to a networked DB
    print(f"{label:<34} {queries:>4} queries  {ms:7.2f} ms in-process"
          f"  ~{ms + queries * rtt:6.1f} ms over a 0.5 ms network")

# Part 1: render a page of 100 posts with their author names
def n_plus_one():
    posts = q("SELECT id, author_id, title FROM post ORDER BY created_at DESC LIMIT 100")
    for _, author_id, _ in posts:                      # one query per post: the N
        q("SELECT name FROM author WHERE id = ?", (author_id,))
def batched():
    posts = q("SELECT id, author_id, title FROM post ORDER BY created_at DESC LIMIT 100")
    ids = sorted({a for _, a, _ in posts})
    q(f"SELECT id, name FROM author WHERE id IN ({','.join('?' * len(ids))})", ids)
def joined():
    q("""SELECT p.id, a.name, p.title FROM post p JOIN author a ON a.id = p.author_id
         ORDER BY p.created_at DESC LIMIT 100""")
timed("N+1 (lazy loading)", n_plus_one)
timed("batched IN (selectin loading)", batched)
timed("single JOIN (joined loading)", joined)

# Part 2: page 9,000 of 100 rows: OFFSET versus keyset
def offset_page():
    q("SELECT id, title FROM post ORDER BY created_at, id LIMIT 100 OFFSET 900000")
last = db.execute("SELECT created_at, id FROM post ORDER BY created_at, id LIMIT 1 OFFSET 899999").fetchone()
def keyset_page():
    q("""SELECT id, title FROM post WHERE (created_at, id) > (?, ?)

Diagnose: the dashboard endpoint that melts the database at 9 a.m.

A Python service (40 instances, each with SQLAlchemy pool_size=20, max_overflow=30) serves an admin dashboard. Every morning at 9:00 latency goes from 150 ms to 8 s and the database (16 cores) shows 600-900 active connections. The endpoint loads the user's 50 projects, and for each project displays its owner's name, its last 5 runs, and the run's model name. Projects list pages use OFFSET. Explain what is happening and fix it at the pool, query and pagination levels.

Answer

Pool. 40 instances × (20 + 30 overflow) allows up to 2,000 connections; at the 9:00 spike, hundreds become active on a 16-core database, and latency explodes from contention, not from real work. Size from capacity: target roughly 32-48 active connections in total; with 40 instances that is about 1 per instance, so put PgBouncer in transaction mode in front, set each instance's pool to about 5 with no overflow, and let requests queue with a pool timeout. Check for transactions held across slow work (any external calls in the request).

Queries. The page is a nested N+1: 1 query for projects, 50 for owners, 50 for runs, and up to 250 for run models: about 351 queries per page view, 175 ms of round trips at 0.5 ms each before any work, and hundreds of connection borrow-and-return cycles. Rewrite: projects with owners in one join (joinedload); the last 5 runs per project in one query using a window function or LATERAL (db4): SELECT … FROM project p CROSS JOIN LATERAL (SELECT … FROM run r WHERE r.project_id = p.id ORDER BY r.created_at DESC LIMIT 5) r WHERE p.owner_id = $1, with an index on run(project_id, created_at DESC); models via a join or a cached lookup table. Total: 2-3 queries. Add a query-count assertion to the endpoint's test (budget of, say, 10).

Pagination. Replace OFFSET with keyset on (updated_at, id) and an opaque cursor; deep pages become as cheap as the first, and pages stay stable as projects update.

Verify. After the change, active connections should stay near the pool cap, p99 latency should drop below the original 150 ms, and pg_stat_statements call counts for the owner and model lookups should fall by roughly fiftyfold.
