In August 2016, GitHub open-sourced a tool called gh-ost and explained why it had built it. GitHub ran on MySQL and changed its schema several times a day: new columns, new indexes, changed types, as product teams shipped features. A plain ALTER TABLE on a busy table was not an option: in default MySQL behaviour, many changes blocked the table, and even MySQL's own online DDL was online only on the server where it ran; replicated as a single statement, it made every replica stall while applying it. So GitHub, like most large MySQL users, had used pt-online-schema-change for years, a tool that builds a copy of the table with the new schema, copies rows across in chunks, keeps the copy in sync with database triggers, and swaps the tables at the end.

As traffic grew, that approach broke down. GitHub's post describes the problems: the triggers ran inside every application transaction on the table, adding parsing overhead and competing for locks on two tables at once; under heavy write load they had seen near or complete lockdowns that made a table or the whole database inaccessible; removing the triggers at the end could stall for many seconds to a minute; and a migration could not truly be paused under load, because stopping the triggers would lose changes. Some migrations could only run at night or at weekends, and others consistently caused outages. gh-ost's answer was to drop triggers entirely and follow changes by reading MySQL's replication log instead, so the migration became a separate, throttleable, pausable, testable stream of work.

The problem GitHub solved is universal. Every product changes its schema constantly, and in a system that must stay up, two constraints apply at once. The database must keep serving reads and writes while the structure changes, which means understanding exactly which operations lock or rewrite tables and for how long. And the application is deployed gradually, so for some minutes or hours the old version and the new version of the code run side by side against the same database, which means every intermediate state of the schema must work for both.

This lesson teaches how to meet both constraints. It explains what different kinds of DDL actually do in PostgreSQL and MySQL, the lock-queue trap that turns an instant change into an outage, the expand-contract pattern that makes breaking changes safe, how to write backfills that can run for days without harm, online index and constraint builds, how shadow-table tools such as gh-ost work, and how to plan verification and rollback. The lab performs a complete expand-contract column split on 50,000 rows.

Renovating a shop that never closes

Think of a schema migration as renovating a shop that stays open twenty-four hours a day. You cannot close the doors while you move the counter. So you build the new counter next to the old one first, start serving customers at both, move the stock across in small loads during quiet moments, check that nothing is missing, then put up a sign directing everyone to the new counter, wait a while in case anyone still heads to the old one, and only then remove it. At no point is the shop unable to serve a customer, and at any point before the old counter is removed, you could go back.

That is the expand-contract pattern, and the analogy captures its two essential properties. Changes are additive first: the new structure exists alongside the old before anything is removed. And there is a period of compatibility: for a while both structures are kept correct, so that both old and new staff (application versions) can work.

The analogy breaks in one dangerous place. In a database, even putting up a sign can require briefly closing the door. Most schema changes need a moment of exclusive access to the table's definition, and if someone is in the middle of a long transaction, the change waits, and while it waits, it holds the door closed for everyone else who arrives. Managing that moment is half of the craft.

Two clocks

A migration runs on two clocks at once. The database clock: how long each step locks, scans or rewrites data, which depends on table size and load. The deploy clock: how long old and new application versions coexist, which depends on the rollout process and on how long you want to keep the ability to roll back. A safe plan lists each step with its effect on both clocks: what it locks and for how long, and which application versions must be running before and after it.

The compatibility rule

One rule summarises everything in this lesson: the schema must work with both the code currently deployed and the code about to be deployed. From it follow the practical guidelines. Additions are safe, because old code ignores what it does not know about (as long as it does not use SELECT * into fixed-position structures or INSERT without column lists). Removals are safe only after no running code uses the removed thing. Changes in meaning (a column that used to hold cents now holds dollars) are never safe in place; they are a new column with a new name. And constraints can only be tightened once all writers already obey them. Each section below is this rule applied to a specific kind of change, plus the database mechanics of doing it without long locks.

1. What DDL actually does

Schema changes fall into three cost classes, and knowing which class a statement belongs to is the first thing to check. Metadata-only changes update the catalog and touch no rows: in PostgreSQL, adding a nullable column, adding a column with a constant default (since version 11, the default is stored in the catalog and returned for old rows), dropping a column (it is marked dropped and its space reclaimed by later rewrites), renaming a column or table, and changing a column's default. Scanning changes read every row to check something but do not rewrite it: adding a CHECK or foreign key constraint that is validated immediately, or setting NOT NULL. Rewriting changes rebuild every row into new storage: changing a column's type (unless the change is binary-compatible, such as raising a varchar limit), adding a column whose default is volatile (such as random() or clock_timestamp(), since each row needs its own value), and commands such as VACUUM FULL or CLUSTER. A rewrite of a 500 GB table takes as long as writing 500 GB plus rebuilding every index, and in PostgreSQL holds an ACCESS EXCLUSIVE lock throughout.

All of them also take a lock. PostgreSQL's ALTER TABLE documentation lists the lock level per subcommand: most forms take ACCESS EXCLUSIVE, which conflicts with every other lock mode including the ACCESS SHARE taken by plain SELECT (db9); a few take weaker locks (for example, VALIDATE CONSTRAINT takes SHARE UPDATE EXCLUSIVE, which allows normal reads and writes). For a metadata-only change, the ACCESS EXCLUSIVE lock is held for milliseconds. For a rewrite, it is held for the whole rewrite, which is an outage for that table.

PostgreSQL has one major advantage here: transactional DDL. A migration that adds a column, creates a table and updates some rows can run in one transaction and either fully apply or fully roll back. (The exception is CREATE INDEX CONCURRENTLY, which cannot run inside a transaction block.) MySQL commits implicitly around most DDL, so a multi-statement migration that fails halfway leaves a partial state to clean up.

2. The lock queue: how a quick change causes an outage

The most common migration outage in PostgreSQL involves a change that should have taken a millisecond. Trace it. At 10:00:00, an analyst's report starts a 90-second SELECT on orders, holding ACCESS SHARE. At 10:00:05, a deploy runs ALTER TABLE orders ADD COLUMN note text, an instant metadata change that needs ACCESS EXCLUSIVE, which conflicts with the report's lock, so it waits. At 10:00:06, a customer's checkout runs SELECT … FROM orders WHERE id = 42, needing ACCESS SHARE. That does not conflict with the report, but PostgreSQL grants locks in queue order to prevent the ALTER from starving, so the checkout waits behind the ALTER. Every subsequent query on orders joins the queue. For the next 85 seconds, until the report finishes, nobody can read or write orders. Connection pools fill with waiting requests, and the outage spreads to everything that touches the pool.

The fix is to never let DDL wait indefinitely. Run every migration statement with a short lock_timeout (for example SET lock_timeout = '3s'), so that if the lock is not granted quickly, the statement fails, the queue behind it drains immediately, and the migration tool retries after a pause, perhaps a few times with backoff. Before starting, check pg_stat_activity for long-running transactions on the table and wait for or cancel them. Many migration frameworks and linters (such as the strong_migrations gem for Rails or squawk for PostgreSQL migrations) set lock timeouts and flag dangerous operations automatically. The same principle applies in MySQL, where DDL waits for metadata locks held by open transactions; lock_wait_timeout bounds the wait.

3. Expand-contract, step by step

Take a breaking change: the users table stores a full name in name, and the product needs first_name and last_name. Dropping name breaks every running instance of the current code; adding the new columns without populating them breaks the new code's reads. The expand-contract sequence, which the lab performs on 50,000 rows:

  1. Expand the schema. Add first_name and last_name as nullable columns: metadata-only, instant. Nothing reads them yet; the old code is unaffected.
  2. Write both. Make every write also populate the new columns. Either deploy application code that writes both, or (as the lab does) add a trigger that derives the new columns whenever an old-style insert arrives, so instances that have not been redeployed still produce complete rows. The lab inserts "Ana Silva" through the old path and the trigger fills in ('Ana', 'Silva').
  3. Backfill. Populate the new columns for existing rows in small batches (section 4). The lab processes 10 batches of 5,000 and confirms no rows are missing.
  4. Verify. Compare old and new representations across all rows: the lab's check finds 0 mismatches. Never skip this; it catches parsing edge cases (names with no space, three-part names) before users do.
  5. Switch reads. Deploy code that reads the new columns, still writing both, so a rollback to the previous version still finds name correct.
  6. Stop writing the old. Deploy code that writes only the new columns. Remove the trigger.
  7. Contract. After a waiting period long enough that no rollback to an old version is plausible, add constraints on the new columns (NOT NULL, section 6) and drop name.

Every arrow in the sequence is backward compatible: at each step, the version of the code currently deployed and the version immediately before it both work. That is what makes rolling deploys and rollbacks safe. The cost is time and several deploys for what looks like one change, which is why teams reserve full expand-contract for breaking changes and apply purely additive changes in one step.

The same pattern handles other breaking changes. Renaming a column: add the new column, write both, backfill, read new, stop writing old, drop old (or, in PostgreSQL, a view or generated column can bridge). Splitting a table: create the new table, dual-write, backfill, switch reads, stop writing the old columns. Changing a type (int to bigint, text to jsonb): add a column of the new type, sync with a trigger, backfill, swap. Making a column required: deploy code that always writes it, backfill nulls, then add the constraint.

4. Backfills that do not hurt

A backfill is a data migration over existing rows, and the naive version, UPDATE users SET first_name = … WHERE first_name IS NULL in one statement, is a production hazard on a large table. In PostgreSQL it holds row locks on every row it touches for the whole statement, writes a new version of every row (doubling the table's size until vacuum catches up, db10), generates a burst of WAL that replicas must replay (causing lag) and, if it fails at 90%, rolls back everything. In MySQL it holds locks and produces a single huge binlog event that replicas apply serially.

A safe backfill is a batched, resumable job:

  • Batch by primary key range: process ids 1-5,000, then 5,001-10,000, and so on, each batch in its own short transaction. Keyset iteration on the primary key (db13) makes each batch's lookup an index range scan regardless of how far along the job is.
  • Make each batch idempotent: only touch rows that still need it (AND first_name IS NULL), so a batch that is retried or overlaps does no harm.
  • Record progress: store the last processed id, so the job can resume after a crash or a deliberate pause without starting over.
  • Throttle: sleep between batches, and slow down or pause when replica lag, CPU or latency exceed thresholds. A backfill that runs for a day at low impact is better than one that runs for an hour and degrades production.
  • Size batches by time: aim for each batch to take well under a second (typically 1,000 to 20,000 rows, depending on row size and indexes), so locks are short and progress steady.
  • Keep new writes correct: the dual write or trigger from step 2 ensures rows written during the backfill are already correct, so the backfill and live traffic never race on the same logical value.

Backfills that call external services (computing embeddings with a model, geocoding addresses) follow the same rules with extra care for rate limits and cost: the job is resumable per row, results are written with the row's id as an idempotency key, and the slow external call happens outside the database transaction (db13).

5. Building indexes online

A plain CREATE INDEX in PostgreSQL takes a SHARE lock on the table, which allows reads but blocks all inserts, updates and deletes for the entire build, which can be hours on a large table. CREATE INDEX CONCURRENTLY builds the index while allowing writes. It works in phases: it registers the index in the catalog as not yet valid (so new writes begin maintaining it), waits for all transactions that might not know about the index to finish, scans the table to build the index, waits again, scans again to add rows changed during the first scan, and finally waits for transactions with older snapshots before marking the index valid for queries. The documentation is clear about the costs: more total work, two table scans, and waiting for existing transactions, so one long-running transaction can stall the build indefinitely.

It also has a failure mode to plan for. If the build fails (a deadlock, a uniqueness violation for a unique index, a cancelled statement), the index is left behind marked INVALID: queries do not use it, but writes still maintain it, so it costs write performance until it is dropped. After every concurrent build, check SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE NOT indisvalid, and drop and retry any invalid index (with DROP INDEX CONCURRENTLY). Because the command cannot run in a transaction block, migration frameworks that wrap each migration in a transaction need a per-migration opt-out. REINDEX CONCURRENTLY rebuilds an existing index the same way, and DROP INDEX CONCURRENTLY removes one without blocking.

In MySQL, InnoDB has supported online index creation (allowing concurrent reads and writes for most of the build) since 5.6, and MySQL 8.0 added ALGORITHM=INSTANT for some column additions. The catch for replicated MySQL is the one GitHub described: an online ALTER is online on the primary, but replicas apply it as one statement, and on a replica with single-threaded apply for that table, replication stalls for the duration of the build.

6. Adding constraints without long locks

Adding a constraint to a populated table normally requires checking every existing row while holding a lock that blocks writes. PostgreSQL splits this into two steps. ALTER TABLE orders ADD CONSTRAINT orders_customer_fk FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID adds the constraint instantly and enforces it for new and updated rows only. Then ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk scans existing rows to check them, holding only a SHARE UPDATE EXCLUSIVE lock, which allows normal reads and writes. CHECK constraints work the same way.

NOT NULL used to require a full scan under ACCESS EXCLUSIVE. Since PostgreSQL 12, if a validated CHECK (col IS NOT NULL) constraint exists, ALTER COLUMN … SET NOT NULL uses it as proof and skips the scan; so the safe sequence is: add the CHECK as NOT VALID, validate it, set NOT NULL, drop the CHECK. Unique constraints are backed by unique indexes, so build the index concurrently first, then attach it with ALTER TABLE … ADD CONSTRAINT … UNIQUE USING INDEX, which takes only a brief lock. The same trick switches a primary key: build a unique index concurrently on the new key column and use ADD CONSTRAINT … PRIMARY KEY USING INDEX.

7. Shadow tables: how online schema-change tools work

When an engine cannot change a table online (or not without blocking replicas), tools rebuild the table alongside the original. All of them follow the same outline, which GitHub's post spells out: create a ghost table with the new schema; copy existing rows from the original into it in small, throttled chunks; meanwhile capture every change made to the original and apply it to the ghost; when the two are in sync, cut over by atomically renaming the original away and the ghost into its place.

The design question is how to capture changes. Trigger-based tools (pt-online-schema-change, Facebook's OSC, LHM) install triggers on the original table so every insert, update and delete is mirrored into the ghost table (or a change log) inside the same transaction. GitHub's experience with them was the reason for gh-ost: triggers add per-statement interpretation overhead, compete for locks on two tables inside application transactions, and cannot be paused, since disabling them loses changes; removing them at the end needed metadata locks that stalled for up to a minute on busy tables. gh-ost instead reads the binary log in row format (db10) and applies the changes itself, together with the row copy, as a single sequential writer. Because it controls all writes to the ghost table, it can throttle on load metrics or replica lag, pause completely (via a flag file or a command on its control socket), change chunk size while running, report progress, and test a full migration on a replica. GitHub described running continuous no-op migrations of every production table on dedicated replicas and comparing checksums of original and ghost tables, which is how they built trust in the tool. Its documented limitations include tables with foreign keys or triggers, a reminder that every online tool has preconditions to check.

PostgreSQL users have fewer such tools because the engine handles more changes online itself, but the pattern exists (pg_repack rebuilds tables online to remove bloat; logical replication can migrate to a restructured copy) and is the fallback for rewrites such as type changes on huge tables.

9. Partitioned tables make some migrations easier

Very large append-heavy tables (events, logs, LLM calls) are often partitioned by time (db10). Partitioning changes the migration picture in useful ways. A new column can be added to the parent and applies to all partitions. Indexes can be created per partition, concurrently, one partition at a time, and then attached to a parent index, so no single build has to cover the whole table. Data that needs a heavy rewrite can be migrated partition by partition, or left in old partitions behind a compatibility view while new partitions use the new structure. And retention becomes a metadata operation: detaching and dropping an old partition replaces a multi-hour DELETE and the vacuum work it would cause. Recent PostgreSQL versions can attach and detach partitions with lighter locks (DETACH PARTITION … CONCURRENTLY), which keeps even these steps online.

10. Planning, verification and rollback

A migration plan for a large or risky change should be written down and reviewed like code. For each step it states: the exact statement; its cost class (metadata, scan, rewrite) and lock level; the expected duration on production data size (measured on a copy, not guessed); the timeouts and throttles; how success is verified; and how to roll back. The application side lists which version must be deployed before and after each step.

Verification is concrete: row counts, null counts and value comparisons between old and new columns (the lab's mismatch query), constraint validation, checksums of copied tables, query plans of the critical queries after an index change, and replication lag during and after. Rollback is mostly free with expand-contract up to the contract step: roll back the application and the old structure is still correct. The contract step is the only irreversible one, so it is separated in time (days or a release cycle later) and preceded by a check that nothing still reads the old structure, for example by logging queries that reference the old column, or by revoking access to it before dropping it so any hidden reader fails loudly while recovery is still trivial.

Why PostgreSQL needs ACCESS EXCLUSIVE for metadata changes

It can seem excessive that adding a nullable column, which touches no data, needs the strongest lock. The reason is plan and catalog consistency. Every running query was planned against a particular definition of the table: its columns, their types, their positions. If the definition changed underneath a running statement, its plan and the tuple descriptors it is using could disagree with the catalog. ACCESS EXCLUSIVE guarantees no statement is using the table when its definition changes; afterwards, sessions invalidate their cached plans and catalog entries and re-plan. Some operations have been carefully relaxed (CREATE INDEX CONCURRENTLY, VALIDATE CONSTRAINT, ATTACH PARTITION with a lighter lock in recent versions, and some ALTER TABLE SET options) because the developers proved they cannot invalidate concurrent queries. That is also why the lock-queue problem is structural rather than a bug: correctness requires the brief exclusive moment, so the operational answer is to keep the wait for it short.

Fast defaults: how PostgreSQL 11 made ADD COLUMN DEFAULT instant

Before version 11, adding a column with a default rewrote the table to store the default in every row. Since 11, PostgreSQL stores a "missing value" for the column in the catalog (pg_attribute.attmissingval). Rows written before the column existed simply have fewer attributes in their tuple header; when such a row is read, the missing value is supplied. New and updated rows store the value physically. This only works when the default is the same for every existing row, which is why a constant default is instant and a volatile one such as now() evaluated per row, or gen_random_uuid(), still forces a rewrite. (A non-volatile function like now() evaluated once at ALTER time is treated as a constant.) MySQL 8.0's INSTANT algorithm uses a similar row-version idea for adding columns. Knowing the mechanism makes it easy to predict which defaults are cheap.

Migrations and replication

Schema changes interact with replication differently per engine. PostgreSQL's physical replication replays DDL as WAL records exactly as the primary performed it, including the full WAL of any rewrite, so a table rewrite produces a burst of WAL equal to the table's size plus indexes, and standbys must replay it; a concurrent index build similarly generates WAL proportional to the index. A standby running long queries may also delay applying the DDL because it conflicts with their locks, which can stall replication. PostgreSQL's logical replication does not replicate DDL at all: subscribers must be migrated separately and compatibly (add columns on the subscriber first, drop on the publisher first), which is itself an expand-contract discipline across clusters. MySQL replicates DDL as statements in the binlog, which replicas execute themselves, which is exactly why a long online ALTER on the primary becomes a long replication stall on replicas, and why gh-ost's approach of turning a migration into ordinary row writes keeps replicas flowing.

Online migrations at the data level

Some migrations are not schema changes at all but data moves: splitting a table across services, moving a tenant to another shard, re-keying data, switching storage engines. They use the same machinery at a larger scale: dual writes (or change-data-capture replication) from old to new, a backfill of historical data, shadow reads that query both and compare results without serving the new one, a gradual read cut-over by percentage or tenant, and a final write cut-over. Discord's MongoDB-to-Cassandra move (db11) and most sharding migrations (sc7) follow this script. The hard part is usually the write cut-over: making sure no write is lost or applied twice at the moment authority moves, which is solved with a brief write freeze, idempotent replays, or routing writes through a single log that both sides consume.

Testing migrations

Because migration risk depends on data size and production load, tests on a small development database catch syntax and logic errors but not duration or locking problems. Mature teams add three layers: static checks (linters that flag non-concurrent index builds, volatile defaults, type changes, missing lock timeouts and NOT NULL without the CHECK trick); rehearsals on a production-sized copy or a branch of production data (tools that create copy-on-write database clones make this cheap), measuring duration, WAL volume and locks; and canary execution in production with throttling and abort criteria. GitHub's practice of continuously migrating every table on test replicas and checksumming the result is the extreme version: it turns "will this tool corrupt data?" into a question answered by evidence every day.

GitHub's migration lessons

GitHub's account of moving from trigger-based migrations to gh-ost reads as a list of production failure modes. Trigger overhead on hot tables, invisible in testing, became lock contention under real write concurrency, to the point of near or complete lockdowns. Migrations that could not be paused under load turned traffic spikes during a migration into incidents. Removing triggers at the end stalled the table for seconds to a minute on metadata locks. Running migrations only off-peak slowed product development. The improvements gh-ost brought were operational rather than algorithmic: decoupling the migration's write load from application transactions, throttling on replica lag and load, pausing on demand, changing parameters mid-flight, reporting status over a socket, and continuous production-scale testing. Those properties (throttleable, pausable, observable, testable) are the checklist for any long-running migration job, whatever the database.

Typical migration incidents

Lock-queue outages from DDL behind a long transaction, prevented by lock_timeout and pre-checks. Accidental rewrites from a type change or volatile default on a large table, prevented by knowing the cost classes and linting migrations. Blocking index builds from a forgotten CONCURRENTLY, which block writes for the whole build. Invalid indexes left by failed concurrent builds, slowing writes silently for months. Replica lag from large backfills or replicated ALTERs, which in turn causes stale reads (sc6) and can stall failover. Breaking old code with a destructive change during a rolling deploy, producing a spike of errors from instances not yet updated. Backfill bloat from updating every row of a large PostgreSQL table, doubling its size and swamping autovacuum. Each has a standard prevention from this lesson, which is why many teams encode them in a migration linter and a written checklist.

Operating migrations

Practical rules that keep migrations boring: separate schema changes from code deploys, so each can be rolled back independently; keep migrations small and frequent rather than large and rare; run long operations (backfills, index builds on large tables) as observable jobs with progress metrics, not inside the deploy pipeline; set lock_timeout and statement_timeout for the migration role and retry on lock timeouts; check for long transactions and replication lag before starting; watch error rates, latency, locks (pg_locks, pg_stat_activity wait events) and replica lag during; and verify after. For managed databases, read the provider's notes on which operations trigger instance-level work (some parameter or storage changes reboot instances).

Migrations in AI systems

AI products add migration types that are data-heavy and slow. Re-embedding a corpus when changing embedding models is a backfill whose unit cost is a model call: run it as a resumable job keyed by chunk id, throttled by both database load and the embedding API's rate limits and budget, writing to a new vector column or table (the dimension often changes), with a new vector index built concurrently and traffic shifted gradually after offline retrieval evaluation (db15). Changing the structure of logged LLM calls or conversation messages (adding token accounting, splitting content into parts for multimodal messages) follows expand-contract on huge append-only tables, where time partitioning helps: new partitions get the new structure and old partitions can be backfilled lazily or left as they are behind a compatibility view. And feature tables used for both training and serving need migrations that keep point-in-time correctness: a backfilled feature must be computed as of each historical timestamp, not from today's data, or models trained on it will learn from the future.

Goal: perform a complete expand-contract migration on a 50,000-row SQLite table: replace name with first_name and last_name while old-style writes keep working, backfilling in batches, verifying, and finally contracting. Python 3.12 standard library (SQLite 3.35+ for DROP COLUMN). Save as db14.py.

"""Expand-contract: replace users.name with first_name/last_name while 'old' and 'new' app code both run."""
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL)")
db.executemany("INSERT INTO users (name) VALUES (?)", [(f"First{i} Last{i}",) for i in range(50_000)])

# Step 1 EXPAND: add nullable columns (cheap, no rewrite) and keep them in sync for old writers
db.executescript("""
ALTER TABLE users ADD COLUMN first_name TEXT;
ALTER TABLE users ADD COLUMN last_name TEXT;
CREATE TRIGGER sync_ins AFTER INSERT ON users WHEN NEW.first_name IS NULL BEGIN
  UPDATE users SET first_name = substr(NEW.name, 1, instr(NEW.name, ' ') - 1),
                   last_name  = substr(NEW.name, instr(NEW.name, ' ') + 1) WHERE id = NEW.id;
END;
""")
print("expand: columns added, old writers still work ->", end=" ")
db.execute("INSERT INTO users (name) VALUES ('Ana Silva')")           # old code path
print(db.execute("SELECT first_name, last_name FROM users WHERE name = 'Ana Silva'").fetchone())

# Step 2 BACKFILL in small batches by primary key range (short transactions, resumable)
BATCH, last_id, batches = 5_000, 0, 0
while True:
    with db:                                                       # one short transaction per batch
        ids = db.execute("SELECT id FROM users WHERE id > ? AND first_name IS NULL ORDER BY id LIMIT ?",
                         (last_id, BATCH)).fetchall()
        if not ids:
            break
        lo, hi = ids[0][0], ids[-1][0]
        db.execute("""UPDATE users SET first_name = substr(name, 1, instr(name, ' ') - 1),
                                       last_name  = substr(name, instr(name, ' ') + 1)
                      WHERE id BETWEEN ? AND ? AND first_name IS NULL""", (lo, hi))
        last_id, batches = hi, batches + 1
missing = db.execute("SELECT count(*) FROM users WHERE first_name IS NULL").fetchone()[0]
print(f"backfill: {batches} batches of <= {BATCH}, rows still missing: {missing}")

# Step 3 verify before switching reads
bad = db.execute("SELECT count(*) FROM users WHERE first_name || ' ' || last_name <> name").fetchone()[0]
print("verify: mismatches between old and new columns:", bad)

# Step 4 new code writes both (old column still read by any old instances still running)
db.execute("INSERT INTO users (name, first_name, last_name) VALUES ('Raj Rao', 'Raj', 'Rao')")

# Step 5 CONTRACT after every reader of 'name' is gone: drop trigger, then the old column
db.executescript("DROP TRIGGER sync_ins; ALTER TABLE users DROP COLUMN name;")
print("contract: columns now", [r[1] for r in db.execute("PRAGMA table_info(users)")])

What to look for.

  1. After the expand step, an insert using only the old name column still produces complete rows: the trigger fills ('Ana', 'Silva'). This is how instances not yet redeployed stay correct.
  2. The backfill runs 10 batches of at most 5,000 rows, each in its own transaction, and leaves 0 rows missing. Each batch is idempotent (first_name IS NULL), so rerunning the loop is harmless.
  3. Verification finds 0 mismatches between old and new representations.
  4. Only after reads and writes have moved to the new columns are the trigger and the old column dropped.

Plan: making orders.customer_id a validated foreign key and switching it to bigint

PostgreSQL 16, orders has 1.2 billion rows (700 GB), customer_id integer with no foreign key and no index, and some orphan rows from an old bug. Customer ids are at 1.8 billion and growing. Traffic is 3,000 writes per second, and the app is deployed with rolling updates. Write the migration plan: steps, locks, durations to measure, verification and rollback.

Answer

Goal decomposition. Two changes: widen to bigint (a rewrite if done with ALTER TYPE, so use expand-contract) and add a validated foreign key (NOT VALID then VALIDATE). Do the widening first, because the constraint belongs on the final column, and because the id space is the urgent risk (db1).

Steps. 1) ALTER TABLE orders ADD COLUMN customer_id_new bigint, instant, with lock_timeout = '3s' and retries. 2) Trigger on insert and update setting customer_id_new = customer_id when not supplied; deploy code that writes both. 3) Backfill by primary key in batches of about 10,000 rows, each well under a second, throttled on replica lag (target under 5 s) and write latency; at roughly 1.2 billion rows this is days, so run it as a resumable job and expect table bloat that autovacuum must absorb (tune it for this table first). 4) Verify: count(*) WHERE customer_id_new IS DISTINCT FROM customer_id by ranges. 5) CREATE INDEX CONCURRENTLY on customer_id_new (needed anyway for the foreign key's delete checks, db1); check indisvalid. 6) Clean orphans: find them with an anti-join in batches and decide with the business whether to fix, archive or delete. 7) ADD CONSTRAINT orders_customer_fk FOREIGN KEY (customer_id_new) REFERENCES customers (id) NOT VALID (instant), then VALIDATE CONSTRAINT (full scan under SHARE UPDATE EXCLUSIVE, which allows reads and writes; measure duration on a copy). 8) Deploy code reading customer_id_new. 9) In one short transaction with lock_timeout: rename customer_id to customer_id_old and customer_id_new to customer_id, adjust the trigger; deploy code that writes only the new column. 10) After a waiting period, drop the trigger and customer_id_old.

Also. customers.id must be bigint too, with its own expand-contract if it is integer, done first. Rollback: before step 9, roll back the app; the old column is still authoritative. After step 9 and before 10, the rename can be reversed in one transaction. Verification throughout: replica lag, autovacuum progress and bloat on orders, error rates per deploy, and the plan of the main orders queries after the swap.
