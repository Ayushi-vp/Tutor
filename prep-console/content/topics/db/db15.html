A team building a support assistant has its documents in PostgreSQL: articles, their sections, which customers can see which articles, when each was last updated. To add retrieval-augmented generation (hd2), they need semantic search: given a user's question, find the passages whose meaning is closest. The obvious architecture adds a separate vector database. Each chunk's embedding goes there, keyed by chunk id; at query time the service asks the vector store for the 50 nearest chunks, then asks PostgreSQL which of them the user may see and what their text is. Within weeks the problems arrive. A deleted article keeps appearing in answers because its vectors were not removed. A permission change takes minutes to reach the vector store. A customer with a small number of documents gets irrelevant results, because the 50 nearest chunks overall belonged to other customers and all were filtered out afterwards. And every incident requires debugging two systems with two consistency models.

The alternative is to put the vectors in the database that already holds everything else. The pgvector extension adds vector types, distance operators and approximate nearest-neighbour indexes to PostgreSQL, so the embedding becomes a column next to the chunk's text and tenant, a delete removes both in one transaction, and a single SQL query can find nearest neighbours, join permissions and filter by metadata. It is one of the most widely used ways to do vector search, available on every major managed PostgreSQL service.

But putting approximate search inside a relational engine raises questions that neither the vector-search lesson (lm10) nor the indexing lessons (db6) answer alone. Approximate indexes return different results from exact queries, which no other database index does. Filters, which a B-tree handles gracefully, interact badly with graph and cluster indexes. Vectors are large, so storage and memory arithmetic matter. Graph indexes have their own build, insert and vacuum costs inside an MVCC engine. And the planner, built for selectivity estimates, has to decide between an exact scan and an approximate index.

This final lesson of the track works through those questions using pgvector's own documentation as the primary source: the vector types and their costs, exact versus approximate scans, HNSW and IVFFlat inside PostgreSQL with their parameters and defaults, recall measurement, the filtering problem and its solutions (iterative scans, partial indexes, partitioning), quantisation, hybrid search, operations, and how to decide between pgvector and a dedicated vector database. The lab measures recall and latency of an IVF index on 100,000 vectors and reproduces the filtering shortfall.

A new kind of question for an old engine

Every query in this track so far asked for rows that match something: equal to a key, inside a range, containing a word. B-trees, hash indexes and GIN indexes are built for matching. Vector search asks a different question: which rows are closest to this point, in a space of hundreds or thousands of dimensions? There is no range to scan; every row has some distance to the query, and you want the k smallest. In SQL, pgvector expresses it as an ordering: ORDER BY embedding <=> :query LIMIT 10, where <=> is cosine distance.

The exact way to answer is to compute the distance to every row and keep the 10 smallest, which is what PostgreSQL does without an index. For 100,000 vectors that takes a couple of milliseconds in the lab's NumPy version; for 10 million in a database it is seconds per query, too slow for interactive use. Approximate indexes avoid most distance computations by organising vectors so that the search can head straight for the right neighbourhood: IVFFlat groups vectors into clusters and only searches the clusters nearest the query; HNSW links each vector to its neighbours in a graph and walks the graph towards the query. Both trade a little accuracy (recall) for a lot of speed, and lm10 explains their algorithms; this lesson is about how they behave inside a database.

A library catalogue analogy

Think of a library where books are shelved by topic. An exact search for "books most like this one" means comparing it with every book in the building. An IVF-style search walks to the three or four shelves whose topics are nearest and compares only those books. You will usually find the best matches, but occasionally the best book was shelved one aisle over. That is a recall miss. Now add a filter: "most similar books, but only ones in Spanish". If Spanish books are 1% of the collection, the few nearest shelves may contain only one or two of them, and you come back with fewer than you asked for, although many good Spanish books exist elsewhere. That is the filtering problem, and it is the most important practical difference between approximate vector indexes and ordinary database indexes.

One more difference shapes everything that follows. Ordinary indexes are invisible to the meaning of a query: add or drop a B-tree and the answer stays the same, only faster or slower. A vector index is part of the answer: its parameters decide which rows come back. So vector indexes need what other indexes never needed, a measurement of quality, and an owner who decides how much recall the product requires and how much latency and memory it is worth.

The rest of the lesson follows the life of a vector in PostgreSQL: how it is stored, how it is searched exactly and approximately, how indexes are tuned and measured, how filters are made to work, how vectors are compressed, how vector and keyword search are combined, and how all of this behaves in production.

1. Vector types and what they cost

pgvector adds a vector(n) type, a fixed-length array of 4-byte floats. Its README gives the storage cost exactly: 4 × dimensions + 8 bytes per vector, with up to 16,000 dimensions storable. A 1,536-dimensional embedding (a common size for OpenAI's text-embedding-3-small, for example) is 4 × 1,536 + 8 = 6,152 bytes; a million of them is about 6.2 GB of vector data alone, before row headers, other columns and indexes. Because a 6 KB value exceeds the ~2 kB TOAST threshold (db5), wide vectors are stored out of line or compressed, which matters for exact scans that must read them all. Three more types reduce or reshape the cost: halfvec uses 2-byte half-precision floats (2 × dimensions + 8 bytes, half the size, with negligible quality loss for most embedding models); bit stores one bit per dimension for binary-quantised vectors; and sparsevec stores only non-zero elements (8 bytes each plus 16), for sparse lexical embeddings.

Distances are operators. <-> is Euclidean (L2) distance, <=> is cosine distance (1 − cosine similarity), <#> is the negative inner product (negated so that, like the others, smaller means closer and ORDER BY … ASC works), and there are L1, Hamming and Jaccard operators for other types. If embeddings are normalised to unit length, as many models output, cosine distance and inner product rank results identically, and inner product is slightly cheaper to compute. Indexes are built for one operator through an operator class (vector_cosine_ops, vector_l2_ops, vector_ip_ops), and a query only uses the index if it orders by the same operator.

2. Exact search

With no vector index, SELECT id FROM chunks ORDER BY embedding <=> $1 LIMIT 10 is planned as a sequential scan feeding a top-N heapsort (db7): every vector is read and compared, and the ten best are kept. Recall is perfect by definition. Cost is linear in the number of rows: the lab's NumPy exact scan over 100,000 64-dimensional vectors takes about 2 ms; inside PostgreSQL with 1,536-dimensional vectors, scanning a million rows reads gigabytes and takes on the order of a second or more even with parallel workers.

Exact search is still the right tool more often than people expect. When a WHERE clause on an ordinary indexed column narrows the candidates first, such as one tenant's 5,000 chunks or one document's 200 chunks, the planner can use a B-tree on tenant_id to fetch those rows and compute exact distances on just them, which is fast and perfectly accurate. pgvector's README makes this point directly: exact indexes on filter columns work well for conditions that match a low percentage of rows. Exact search also provides the ground truth for measuring an approximate index's recall.

3. IVFFlat inside PostgreSQL

An IVFFlat index (inverted file with flat, uncompressed vectors) runs k-means on the vectors present when the index is built, producing lists centroids, and assigns each vector to its nearest centroid's list. A query computes distances to all centroids, picks the probes nearest lists, and computes exact distances only to the vectors in those lists. With 1,000 lists and 10 probes, a query examines about 1% of the vectors plus the 1,000 centroids.

The README's starting points: lists = rows / 1000 for up to a million rows and sqrt(rows) above that; ivfflat.probes (1 by default) set to about sqrt(lists). Setting probes equal to lists makes the search exact, at which point the planner will not bother using the index. Because the centroids come from the data present at build time, the README advises creating the index after the table has data; an index built on a nearly empty table has poor lists (its FAQ notes that too few rows for the number of lists is a common cause of missing results), and as data drifts away from the original distribution, recall degrades until the index is rebuilt. IVFFlat builds quickly and uses less memory than HNSW, but the README notes it has lower query performance for a given recall.

The lab builds an IVF index with 316 lists (√100,000) on 100,000 vectors drawn from overlapping clusters and measures recall@10 against exact search: 0.18 with 1 probe, 0.44 with 4, 0.70 with 16 and 0.83 with 32, with query time rising from about 0.2 ms to about 3 ms in its NumPy implementation. The shape is the important part: recall climbs steeply at first and then flattens, while cost grows roughly linearly in probes. Real data is often better clustered than this deliberately hard synthetic set, which is exactly why recall must be measured on your own data rather than taken from someone else's benchmark.

4. HNSW inside PostgreSQL

An HNSW index builds a multi-layer graph (lm10): every vector is a node in the bottom layer, linked to up to 2m close neighbours there and m per upper layer; a decreasing random subset of nodes also appears in higher, sparser layers. A search starts at the top layer, greedily moves towards the query, drops a layer, repeats, and at the bottom explores with a candidate list of size ef_search, returning the best results found. pgvector's defaults are m = 16 and ef_construction = 64 at build time and hnsw.ef_search = 40 at query time:

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;   -- per session, or SET LOCAL inside a transaction

Raising ef_construction or m builds a better-connected graph (higher recall at the same ef_search) at the cost of slower builds and inserts and a larger index. Raising ef_search improves recall at query time at the cost of latency, and it also caps how many rows the index scan can return: with the default of 40, a query cannot get more than 40 rows from the index, which matters for filtering (section 6) and for LIMIT values above 40. Unlike IVFFlat, HNSW needs no training step, so it can be created on an empty table and grows as rows are inserted, and its speed-recall trade-off is better, which is why it is the usual default.

The costs are build time and memory. The README notes that builds are much faster when the graph fits in maintenance_work_mem, and that PostgreSQL will print a notice when it no longer fits; parallel workers (max_parallel_maintenance_workers) also speed builds. A million 1,536-dimensional vectors need several gigabytes for the graph during the build. Inserts into an existing HNSW index are much slower than into a B-tree, since each insert runs a search to find the new node's neighbours and updates their links, so large loads should insert data first and build the index afterwards, ideally with CREATE INDEX CONCURRENTLY on a live table (db14).

5. Measuring recall

No database index before vector search changed query results; a B-tree returns exactly the rows a sequential scan would. pgvector's README warns that with an approximate index you will see different results, and it recommends monitoring recall by comparing approximate results with exact ones. A practical procedure: collect a few hundred real queries (or held-out questions from your evaluation set); compute exact top-k for each by running the query with index scans disabled (SET enable_indexscan = off in a session) or via a separate exact query; run the normal indexed query; compute recall@k as the overlap divided by k; and record latency. Then sweep hnsw.ef_search (or ivfflat.probes) and pick the smallest value that meets the target, often 0.95 or 0.99 depending on the application.

Two refinements matter for RAG. First, measure with filters applied, because filtered recall can be much worse than unfiltered recall (section 6). Second, connect recall to the end task: if the top 50 retrieved chunks are re-ranked by a cross-encoder and only the top 5 reach the model, what matters is whether the truly relevant chunks appear among the 50, so recall@50 with the production filter is the metric to tune, and answer quality on an evaluation set (hd2) is the final check.

6. Filtering: the defining problem

In a relational database almost every real vector query has filters: this tenant, this product line, documents the user may read, published after a date, in a language. With a B-tree, adding a filter can only make a query cheaper or more precise. With an approximate vector index, pgvector's README spells out what happens: filtering is applied after the index is scanned. The index scan produces candidates in order of distance (up to ef_search for HNSW, or the contents of the probed lists for IVFFlat); then the WHERE clause removes non-matching rows. If the condition matches 10% of rows, then with HNSW and the default ef_search of 40, the README calculates that only about 4 rows will match on average. The lab reproduces the effect with IVF: for a tenant owning about 1% of rows, a one-probe search returns on average 3.4 of the 10 requested results.

There are four solutions, suited to different filter shapes:

  • Iterative index scans (pgvector 0.8.0 and later). With SET hnsw.iterative_scan = strict_order (or relaxed_order, and the IVFFlat equivalents), the index scan continues past the initial candidate list until enough rows pass the filters, or until it has visited hnsw.max_scan_tuples (20,000 by default) or ivfflat.max_probes lists. Strict order guarantees results in distance order; relaxed order may return them slightly out of order for better recall, and a materialized CTE that re-sorts restores strict order. The lab's second filtered run, widening to 8 probes, returns all 10 results. This is the general-purpose fix, with the cost that very selective filters make the scan visit many nodes.
  • Partial indexes (db6) when filtering by a few distinct values: CREATE INDEX … USING hnsw (embedding vector_cosine_ops) WHERE category_id = 123. The index contains only matching vectors, so every candidate passes the filter. Practical for a handful of values; not for thousands.
  • Partitioning when filtering by many values: PARTITION BY LIST (tenant_id) gives each partition its own index, and partition pruning sends each query to the right partition. pgvector's README recommends list partitioning or separate tables for multi-tenant isolation, noting that a shared approximate index lets one tenant's vectors affect another's recall and speed.
  • Exact search on the filtered set when the filter is very selective: a B-tree on the filter column finds the few thousand matching rows and an exact distance computation on them is cheap and has perfect recall. The planner can choose this automatically when its estimates favour it; verify with EXPLAIN that it does.

Real systems combine them: partitions or partial indexes for the largest tenants or categories, exact search for the long tail of small ones, and iterative scans as a safety net for filters nobody anticipated.

7. The planner and vector queries

A vector index is used to satisfy an ORDER BY distance LIMIT k, the same way a B-tree satisfies ORDER BY created_at LIMIT k (db6). The planner compares the cost of the index scan with a sequential scan plus top-N sort, considering the filters' estimated selectivity. Two consequences follow from db7. The planner must see a LIMIT and an ORDER BY on the distance operator matching the index's operator class, written as a plain expression; wrapping the distance in another expression (ORDER BY 1 - (embedding <=> $1) DESC) can prevent index use. And row estimates for the result of an approximate index scan are crude, so in larger queries, such as a vector search joined to permissions, documents and a reranking step, it is often best to isolate the vector search in a CTE with its own LIMIT (and MATERIALIZED if needed) so that the rest of the plan works on a known small set, then join by primary key with nested loops. EXPLAIN ANALYZE shows whether the index was used (Index Scan using chunks_embedding_idx) and how many rows were removed by filters (Rows Removed by Filter), which is the direct symptom of the filtering problem.

8. Shrinking vectors: half precision and binary quantisation

Memory decides vector-search performance: an HNSW index that fits in RAM answers in milliseconds, one that does not pays random I/O for every graph hop. pgvector offers three ways to shrink. halfvec stores 2-byte floats, halving storage and index size; it can be the column type, or the index alone can be built on a cast (USING hnsw ((embedding::halfvec(1536)) halfvec_cosine_ops)), keeping full precision in the table. Half-precision indexes also raise the dimension limit: the README lists HNSW and IVFFlat index limits of 2,000 dimensions for vector, 4,000 for halfvec and 64,000 for bit, so a 3,072-dimensional embedding cannot be indexed as a plain vector but can as halfvec.

Binary quantisation keeps only the sign of each component: binary_quantize(embedding)::bit(1536) is 192 bytes, 32 times smaller than the float vector, and Hamming distance on bits is extremely fast. Recall drops, so the standard pattern, shown in pgvector's README, is to search the binary index for a larger candidate set (say 100) and re-rank those candidates by exact distance on the full vectors, keeping the top 10. Many modern embedding models also support truncating dimensions (Matryoshka-style training), so a 1,536-dimensional embedding can be cut to 512 with modest loss. All of these are trade-offs to measure with the recall procedure of section 5, not defaults to adopt blindly.

9. Hybrid search in one query

Vector search finds paraphrases but can miss exact identifiers, product codes, error messages and rare names; keyword search does the opposite. Hybrid search runs both and fuses the rankings, and in PostgreSQL both can be in one statement: full-text search with a tsvector column and GIN index (db6), ranked by ts_rank_cd, and a vector search, each producing its top 50 in a CTE. pgvector's README points to reciprocal rank fusion or a cross-encoder to combine them. RRF scores each document by the sum over lists of 1 / (k + rank) with k typically 60 (Cormack, Clarke and Büttcher, 2009), so a chunk ranked 3rd by vectors and 10th by keywords scores 1/63 + 1/70; the fused top 50 then goes to a reranker. Doing this in the database keeps both retrieval paths consistent with the same rows, permissions and deletions, which hd2 shows is where many RAG bugs come from.

10. A tuning session, step by step

Tuning a vector index is an experiment, and it goes the same way every time. Start from the defaults (HNSW with m = 16, ef_construction = 64, ef_search = 40) built on representative data. Assemble an evaluation set: a few hundred real queries with their production filters, and their exact top-k results computed with index scans disabled. Measure recall@k and p50/p95 latency at the defaults. Then sweep the query-time knob first, because it needs no rebuild: ef_search at 40, 80, 160, 320, recording recall and latency at each. Plot the curve (like the figure above) and pick the smallest setting that meets the recall target with headroom. Only if no setting reaches the target at acceptable latency, rebuild with larger m or ef_construction, which raises recall at every ef_search at the cost of build time, insert cost and index size, and sweep again.

Then repeat the measurement with filters, per filter shape: unfiltered, a large tenant, a small tenant, a recency filter. If filtered recall or result counts fall short, apply the section 6 fixes rather than raising ef_search globally, which slows every query to rescue a few. Finally, record the chosen settings next to the measured curve in the repository, set them per role or per query with SET LOCAL, and schedule the measurement to rerun after large data changes or a model change, since both move the curve. The point of the procedure is that every number in the configuration is justified by a measurement on your data, not copied from a blog post or a benchmark built on different embeddings.

11. A worked design: retrieval for a support assistant

Bring it together on the opening scenario: 3 million chunks across 2,000 tenants, a few large tenants with hundreds of thousands of chunks each and a long tail with a few hundred; 1,536-dimensional embeddings; queries need tenant isolation, per-document permissions, and recency filters.

Schema. chunks(chunk_id, tenant_id, document_id, content, content_tsv tsvector, embedding halfvec(1536), created_at) list-partitioned by tenant group: each large tenant gets its own partition with an HNSW index on embedding and a GIN index on content_tsv; small tenants share a default partition with a B-tree on (tenant_id, document_id). Storage: halfvec at 3,080 bytes per chunk, about 9 GB for vectors, with HNSW indexes adding a similar amount, comfortably within memory on a large instance.

Query. A CTE takes the top 50 by vector distance within the tenant (HNSW with ef_search 100 and iterative scan in large partitions; exact scan in the shared partition, since a small tenant's few hundred rows are cheap to compare exhaustively); another takes the top 50 by full-text rank; they are fused with RRF; the result is joined to a document-permissions table by primary key; the top 20 go to a reranker and the top 5 to the model.

Operations. Recall measured weekly per large tenant against exact search on sampled queries; deletes and permission changes are ordinary transactions, so they are immediately consistent with search; re-embedding with a new model follows expand-contract (db14). The whole retrieval path is one database, one backup, one access-control model.

Why filtered ANN is fundamentally hard

Approximate indexes achieve speed by restricting the search to a neighbourhood of the query. A filter restricts the answer to a subset of rows that may be scattered across every neighbourhood. When the filter matches a large fraction of rows, post-filtering a slightly larger candidate set works; when it matches a tiny fraction, the true answers are probably not in the query's neighbourhood of the full graph at all, and no amount of local exploration finds them cheaply. There are three families of solutions in the literature and in products. Pre-filtering (compute the matching set first, search only within it) is exact and fast for small sets but degenerates to brute force for large ones. Post-filtering with expansion (pgvector's iterative scans) is general but costs grow as selectivity falls. Filter-aware indexes build structure that knows about the filter: per-value partitions (what list partitioning gives you), graphs with extra edges so that each filter's subgraph stays connected (approaches such as ACORN, which hd2 mentions, and filtered HNSW variants in dedicated engines), or inverted lists combined with quantised vectors. Dedicated vector databases invest heavily here because filtered search is where naive designs fail; pgvector's answer combines planner choices (exact search on small filtered sets), partitioning and iterative scans.

HNSW and MVCC

Graph indexes are a slightly awkward fit for an MVCC storage engine. In PostgreSQL every update creates a new heap tuple (db10), and since the vector column is indexed, a new graph node; the old node remains in the graph, pointing to a dead tuple, until vacuum removes it. Removing a node from an HNSW graph is not like removing a B-tree entry: its neighbours lose links, and to keep the graph navigable, vacuum must repair them by reconnecting neighbours, which requires searches. pgvector implements this, but vacuum of an HNSW index on a heavily updated table is slow and resource-intensive, and between vacuums searches may spend part of their candidate budget on dead nodes, reducing effective recall (the README's FAQ lists dead tuples as one reason a query can return fewer rows than requested). Designs that minimise churn help: keep frequently updated metadata in a separate table from the embeddings so metadata updates do not create new vector tuples (the db10 narrow-table pattern), make chunks immutable and replace documents by inserting new chunks and deleting old ones in batches, and schedule REINDEX CONCURRENTLY after mass changes.

Memory arithmetic for HNSW

A rough estimate of an HNSW index's size helps capacity planning. Each node stores its vector (or the quantised form) plus neighbour lists: at the bottom layer up to 2m neighbours, each a tuple identifier of about 6-8 bytes in pgvector's on-disk format, and on average a small additional amount for upper layers (each layer holds roughly 1/m of the nodes of the layer below). With m = 16, the links add a few hundred bytes per vector; for 1,536-dimensional float vectors the vector itself (about 6 KB) dominates, so the index is roughly the size of the vector data plus 5-10%. That is why halfvec indexes halve memory and binary-quantised indexes shrink it dramatically, and why the README emphasises maintenance_work_mem during builds: building requires the graph in memory to be fast. The working set for queries is the part of the graph that searches visit, which for well-distributed queries is much of it, so in practice the index should fit in the buffer cache plus OS cache for consistent low latency.

Distance choice and normalisation

Choosing the operator is not cosmetic. Embedding models are trained with a particular similarity, usually cosine or dot product, and their documentation says which; using L2 on unnormalised vectors from a dot-product model ranks differently from what the model intended. If vectors are normalised to unit length, L2 distance, cosine distance and negative inner product all produce the same ranking (since ||a − b||² = 2 − 2a·b for unit vectors), so inner product, the cheapest to compute, is a sound choice. The index operator class must match the query's operator, or the planner will not use the index at all, which shows up as an unexpectedly slow sequential scan. Mixing models in one column is never valid: distances between embeddings from different models are meaningless, so a model change always means a new column or table.

pgvector versus dedicated vector databases

The decision is about workload shape more than features, since both sides now have HNSW, quantisation, filtering and hybrid search. PostgreSQL with pgvector is strongest when vectors are attached to relational data that is queried, joined and permissioned together; when consistency between documents, permissions and embeddings matters (deletes must stop appearing in results immediately); when the corpus is in the millions to low tens of millions of vectors per node; and when the team already operates PostgreSQL. Dedicated vector databases are strongest at hundreds of millions to billions of vectors with built-in sharding, at very high query rates with tight tail-latency targets, with very selective or complex filters served by filter-aware indexes, and with features such as multi-vector documents, built-in reranking or GPU acceleration. Many organisations start with pgvector and move only the largest, hottest collections out when measurements justify it, keeping the system of record relational and feeding the vector store by change data capture (db12).

pgvector's own guidance as a production checklist

The pgvector README is unusually candid, and its warnings map directly onto production incidents. Approximate indexes change query results, so recall must be monitored, not assumed. Filtering happens after the index scan, so selective filters return too few rows unless iterative scans, partial indexes or partitions are used; a support ticket that says "search returns only three results for our account" is almost always this. Results are limited by hnsw.ef_search (40 by default), so a query with LIMIT 100 silently returns at most 40 rows from the index unless ef_search is raised. IVFFlat indexes built on too little data have poor lists and miss results. HNSW builds are slow when the graph does not fit in maintenance_work_mem, but setting it so high that it exhausts server memory is its own outage. Shared indexes across tenants couple tenants' recall and latency. Each of these is a configuration or design choice with a documented fix, which makes the README worth reading in full before a launch.

What to monitor

Useful signals for vector search in PostgreSQL: query latency percentiles for retrieval queries, separately for each large tenant or partition; the fraction of queries returning fewer than the requested number of rows (a direct measure of the filtering problem); periodic recall@k against exact search on a sample; index size versus available memory, and buffer cache hit rates on vector indexes; dead tuples and vacuum duration on tables with vector indexes; and build times for index rebuilds. EXPLAIN ANALYZE on representative queries after every change in data volume, filters or parameters catches plans that silently fell back to sequential scans or that remove most index candidates by filter.

Capacity and cost

Vector data dominates the size of RAG databases. A million 1,536-dimensional float vectors are about 6 GB, ten million about 60 GB, plus a similar amount for HNSW indexes; at that scale, choosing halfvec, truncated dimensions or binary quantisation with re-ranking is a cost decision as much as a performance one, since the instance must hold the indexes in memory. Backups and replicas multiply the footprint. Re-embedding the whole corpus with a new model costs model API calls (or GPU time) plus a full index rebuild, so model upgrades should be planned as migrations with budgets, and old and new vectors coexist during the transition (db14).

Consistency is the quiet advantage

The opening story's failures were consistency failures: deleted articles still retrieved, permission changes lagging, two systems disagreeing. Keeping vectors in the same transactional database removes that class of bug: deleting a document and its chunks, or revoking a user's access, takes effect for the next query, because retrieval reads the same snapshot as everything else (db9). When a separate vector store is necessary, the same guarantees must be rebuilt: CDC from the database to the vector store, idempotent upserts and deletes keyed by chunk id, permission filters re-checked against the database on retrieved results, reconciliation jobs that compare ids in both stores, and tests that delete a document and assert it disappears from search. Either way, retrieval correctness is a database problem, which is why this track ends here.

Goal: measure the recall-latency trade-off of an IVF index against exact search on 100,000 vectors, and reproduce the post-filtering shortfall for a tenant owning 1% of rows. Uses NumPy (the gpt_env virtual environment, Python 3.12); PostgreSQL and pgvector are not needed, but every step maps to a pgvector setting. Save as db15.py.

import time
import numpy as np

rng = np.random.default_rng(15)
N, D, K = 100_000, 64, 10
centers = rng.normal(size=(200, D)).astype(np.float32)
X = centers[rng.integers(0, 200, N)] + 1.5 * rng.normal(size=(N, D)).astype(np.float32)
X /= np.linalg.norm(X, axis=1, keepdims=True)               # unit vectors: cosine = dot
tenant = rng.integers(0, 100, N)                             # 100 tenants, ~1% of rows each
Q = X[rng.integers(0, N, 200)] + 0.3 * rng.normal(size=(200, D)).astype(np.float32)
Q /= np.linalg.norm(Q, axis=1, keepdims=True)

def exact(q, mask=None):
    s = X @ q
    if mask is not None:
        s = np.where(mask, s, -np.inf)
    return np.argpartition(-s, K)[:K]

t0 = time.perf_counter(); truth = [set(exact(q)) for q in Q]
print(f"exact scan: {(time.perf_counter()-t0)/len(Q)*1000:.2f} ms/query over {N:,} vectors")

# IVF ('ivfflat'): k-means into lists, search the nprobe nearest lists
lists = int(np.sqrt(N))                                      # pgvector's sqrt(rows) rule above 1M; fine here
C = X[rng.choice(N, lists, replace=False)].copy()
for _ in range(10):                                          # a few Lloyd iterations
    assign = np.argmax(X @ C.T, axis=1)
    for j in range(lists):
        m = X[assign == j]
        if len(m):
            C[j] = m.mean(0) / np.linalg.norm(m.mean(0))
assign = np.argmax(X @ C.T, axis=1)
members = [np.flatnonzero(assign == j) for j in range(lists)]

def ivf(q, nprobe, mask=None, want=K):
    probe = np.argsort(-(C @ q))[:nprobe]
    cand = np.concatenate([members[j] for j in probe])
    if mask is not None:
        cand = cand[mask[cand]]                              # filter AFTER the index scan
    top = cand[np.argsort(-(X[cand] @ q))[:want]]
    return top

print(f"IVF with {lists} lists:")
for nprobe in (1, 4, 16, 32):
    t0 = time.perf_counter()
    rec = np.mean([len(set(ivf(q, nprobe)) & truth[i]) / K for i, q in enumerate(Q)])
    ms = (time.perf_counter() - t0) / len(Q) * 1000
    print(f"   probes={nprobe:>3}: recall@10 = {rec:.3f}  {ms:.2f} ms/query")

# Filtered search: one tenant (~1% of rows), post-filtering versus scanning further
mask = tenant == 7
got = [len(ivf(q, 1, mask)) for q in Q]
print(f"tenant filter, probes=1, post-filter: avg {np.mean(got):.1f} of {K} results returned")
got = [len(ivf(q, 8, mask)) for q in Q]
print(f"tenant filter, probes=8 ('iterative' widening): avg {np.mean(got):.1f} of {K} results returned")

What to look for (numbers from the test run; timings depend on the machine).

  1. Exact scan: about 2 ms per query over 100,000 64-dimensional vectors, perfect recall by definition.
  2. IVF with 316 lists (√N): recall@10 of about 0.18, 0.44, 0.70 and 0.83 at 1, 4, 16 and 32 probes, the rising-then-flattening curve you tune with ivfflat.probes. The synthetic clusters overlap heavily, making this harder than most real embeddings.
  3. Filtered to one tenant (1% of rows) with 1 probe and post-filtering: about 3.4 of the 10 requested results come back. Widening the scan to 8 probes, like an iterative scan, returns all 10.

Diagnose: "semantic search got worse after we added an index"

A RAG product stores 4 million chunks (768-dimensional vector) for 900 tenants in one PostgreSQL table. Search used exact scans with a B-tree on tenant_id and was slow for large tenants, so the team added CREATE INDEX … USING hnsw (embedding vector_l2_ops). Now large tenants are fast, but: small tenants often get 0-3 results instead of 10; some queries with LIMIT 50 return 40; the embedding model's documentation says to use cosine similarity on unnormalised outputs; and nightly re-ingestion of changed documents (deleting and reinserting about 5% of chunks) has made the table and index grow steadily. Explain each symptom and fix it.

Answer

Too few results for small tenants. The HNSW scan returns ef_search candidates (40 by default) nearest overall, then the tenant filter removes almost all of them, since a small tenant owns a tiny fraction of rows. Fix: for small tenants, keep the exact path (the planner may need help: write the query so the B-tree on tenant_id is used, or route small tenants to a query with index scans disabled); for large tenants, partition by tenant group (list partitioning) so each large tenant's index contains only its vectors; enable hnsw.iterative_scan as a safety net.

LIMIT 50 returns 40. The index scan is capped by hnsw.ef_search, 40 by default. Set SET LOCAL hnsw.ef_search = 100 (at least the LIMIT, more for recall), or enable iterative scans.

Wrong distance. The index uses vector_l2_ops, but the model is meant for cosine similarity on unnormalised vectors, so rankings differ from what the model intends, and queries ordering by <=> (cosine) would not use this index at all. Rebuild with vector_cosine_ops (concurrently), or normalise vectors on write and use inner product. Measure recall and end-task quality before and after.

Growth from re-ingestion. Deleting and reinserting 5% of chunks nightly creates dead tuples in the heap and dead nodes in the HNSW graph; vacuum on HNSW is expensive and may lag, so the index grows and searches waste candidates on dead entries. Fixes: only re-embed chunks whose content actually changed (hash the content), tune autovacuum for this table, schedule REINDEX INDEX CONCURRENTLY after large changes, and keep frequently updated metadata out of the embedding table.

Verify. Build a recall harness: 200 sampled queries per tier of tenant, exact results with index scans off, recall@10 and result counts with the production filters, run before and after each change.
