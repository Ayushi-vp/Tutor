An analyst at a subscription company is asked a simple question: which customers have never placed an order? They write the obvious query, SELECT * FROM customer WHERE customer_id NOT IN (SELECT customer_id FROM orders), test it on a small copy of the data, and see the right answer. In production it returns zero rows. Nobody notices for a month, because "no inactive customers" is good news. Then the retention team, who had been told there was no one to win back, finds 40,000 inactive accounts by another route.

The cause is one row. A data import had created a single order with customer_id set to NULL. Because of how SQL treats NULL, a single NULL in the subquery makes NOT IN unable to ever be true, so the query returns nothing at all. The PostgreSQL community's own list of common mistakes leads its SQL section with "Don't use NOT IN" for exactly this reason. The query was not slow, did not error, and looked correct. It just answered a different question from the one the analyst asked.

That is the characteristic danger of SQL. It is a declarative language: you describe the result you want and the database decides how to compute it. That makes it extraordinarily productive, since three lines can join five tables and aggregate a billion rows, but it also means the meaning of every clause has to be exactly right, because there is no step-by-step code to debug. The most common wrong answers come from a handful of places: joins that drop or duplicate rows, filters placed in the wrong clause, grouping mistakes, and NULL.

This lesson builds SQL's core from the ground up on two tiny tables you can hold in your head. You will learn the logical order in which a query is evaluated (which explains most "why can't I…" questions), every kind of join, with the exact rows each returns, grouping and HAVING, and SQL's three-valued logic, which is the root of the NULL surprises. Everything is run in the lab with Python's built-in SQLite, and the differences between SQLite, PostgreSQL and MySQL are called out where they matter. By the end you should be able to write these queries live in an interview and, more importantly, explain why a wrong one is wrong.

A query is a pipeline of table transformations

The most useful mental model of a SQL query is an assembly line. Raw tables come in at one end. Each clause is a station that takes a table and produces a new table: one station combines tables, the next throws away rows, the next sorts rows into bins, the next throws away bins, the next chooses and computes columns, the last sorts and trims. What comes out the far end is the result. Every station sees only what the previous one produced.

The catch is that SQL makes you write the stations in a different order from the one they run in. You write SELECT first, but it runs near the end. The real, logical order is this:

This order answers a surprising number of questions on its own. Why can't WHERE use COUNT(*)? Because groups do not exist yet at step 2. Why can ORDER BY use the alias n from COUNT(*) AS n? Because sorting happens after SELECT created it. Why does LIMIT 10 without ORDER BY return an arbitrary ten rows? Because there was no sort station, so "first" means whatever order the rows happened to arrive in.

The model has one important limitation: it describes what the answer means, not how the database computes it. The query planner (db7) is free to push a WHERE filter below a join, stop scanning once LIMIT is satisfied, or read rows already sorted from an index. It just has to produce the same result the logical order defines.

Two tables to keep in your head

Everything in this lesson uses the same two tables, four rows each, chosen so that each join and each NULL rule shows up. department holds Sales (10), Eng (20), Ops (30) and Legal (40). employee holds Ana (dept 10, salary 90, bonus 10), Raj (dept 20, salary 120, no bonus recorded), Li (dept 20, salary 100, bonus 5) and Sam, who has no department yet (dept NULL, salary 70, bonus 0). Note the three things that make the examples interesting: two employees share a department, two departments have no employees, and one employee has no department. Real data always has all three.

NULL in one paragraph

NULL is SQL's marker for "no value here": unknown, not applicable or not yet set. It is not zero and not the empty string. The rule that causes all the surprises is that a comparison involving NULL is neither true nor false but unknown, and WHERE, ON and HAVING keep only rows where the condition is true. Hold onto that rule; most of the second half of this lesson is its consequences.

What "declarative" buys and costs

In a general-purpose language you would answer "employees per department" with loops: for each department, scan the employees, count matches. In SQL you state the shape of the answer and the database picks the loops: a hash table built over one side, a scan of an index, or a sorted merge, depending on sizes and available indexes (db7). The benefit is that the same query stays correct and usually fast as the data grows from four rows to four hundred million. The cost is that you cannot step through it in a debugger, so correctness has to come from understanding exactly what each clause means. That is why this lesson spends as much time on meaning (which rows survive, what NULL does) as on syntax.

1. The anatomy of a SELECT

The smallest useful query names a table and some columns: SELECT name, salary FROM employee. Every addition is a step in the pipeline from the primer. WHERE salary > 95 keeps Raj and Li. ORDER BY salary DESC sorts them Raj (120), Li (100). LIMIT 1 keeps Raj. Expressions can appear in SELECT (salary * 1000 AS annual), and CASE gives conditional values: CASE WHEN salary >= 100 THEN 'senior' ELSE 'junior' END.

Three habits from production code are worth adopting now. Name columns rather than using SELECT *, so adding a column to the table does not change your result's shape or drag large columns over the network. Always pair LIMIT with ORDER BY, since without a sort the "first" rows are whichever the plan produces, and they can change when an index is added. And qualify columns with a table alias once a query has more than one table (e.name, d.dept_name), so a column added to the other table later cannot make the query ambiguous.

DISTINCT removes duplicate rows after SELECT: SELECT DISTINCT dept_id FROM employee returns 10, 20 and NULL (three rows, not four, since Raj and Li share 20, and NULL counts as one value for DISTINCT, a rule section 8 returns to). DISTINCT costs a sort or hash of the whole result, and reaching for it to "fix" duplicates is usually a sign of a join that is multiplying rows; find the join instead.

2. Inner join: only the matches

A join combines rows from two tables. Logically, it starts from the Cartesian product, every row of one table paired with every row of the other (4 × 4 = 16 pairs here), and keeps the pairs that satisfy the join condition. The database never actually builds the 16 pairs for a real join, since db7 shows the smarter algorithms, but this definition is how you work out the right answer.

SELECT e.name, d.dept_name
FROM employee e
JOIN department d ON e.dept_id = d.dept_id;

Walk the 16 pairs. Ana (10) matches Sales (10). Raj (20) and Li (20) both match Eng (20). Sam (NULL) matches nothing, because NULL = 10 is unknown, not true. Ops and Legal match no employee. Result: three rows, (Ana, Sales), (Raj, Eng), (Li, Eng). Two lessons are visible already. An inner join (the plain JOIN) drops rows with no partner on either side: Sam, Ops and Legal are gone. And a row can appear more than once: Eng appears twice because it has two employees. That is correct here, but it is the root of the fan-out bug in section 7.

Two shorthand forms exist. JOIN department d USING (dept_id) joins on equal columns with the same name and outputs the column once. NATURAL JOIN joins on every pair of same-named columns automatically; avoid it, because adding a column called name or updated_at to both tables later silently changes the join condition.

3. Outer joins: keeping the unmatched rows

An outer join returns the inner join's matches plus the rows from one or both sides that had no match, with NULL in the other side's columns. The word OUTER is optional.

These are the exact results the lab prints. A RIGHT JOIN is just a LEFT JOIN with the tables swapped, and most style guides prefer to always write LEFT so the "kept" table is always first. SQLite only gained RIGHT and FULL joins in version 3.39 (2022); MySQL still has no FULL JOIN and needs a UNION of a left and a right join to emulate one.

4. ON versus WHERE in an outer join

This is the single most common join bug, and interviewers know it. The question: list every department with its employees who earn more than 95, keeping departments that have none. Two queries look almost identical:

-- A: condition in ON
SELECT d.dept_name, e.name FROM department d
LEFT JOIN employee e ON e.dept_id = d.dept_id AND e.salary > 95;

-- B: condition in WHERE
SELECT d.dept_name, e.name FROM department d
LEFT JOIN employee e ON e.dept_id = d.dept_id
WHERE e.salary > 95;

Query A returns five rows: (Sales, NULL), (Eng, Raj), (Eng, Li), (Ops, NULL), (Legal, NULL). The salary condition is part of deciding what matches; Ana does not match Sales because she earns 90, so Sales is kept with NULL, exactly as a left join promises. Query B returns two rows: (Eng, Raj), (Eng, Li). The join first produced Sales-Ana, Eng-Raj, Eng-Li, Ops-NULL and Legal-NULL; then WHERE ran (step 2 of the pipeline) and tested e.salary > 95. For Ana, 90 > 95 is false. For Ops and Legal, NULL > 95 is unknown. Only true rows survive. The left join has silently become an inner join.

The rule: in an outer join, conditions on the optional side (the right table of a LEFT JOIN) belong in ON if they decide what counts as a match; conditions in WHERE filter the final rows and will remove the NULL-padded ones. Conditions on the preserved side (the left table) usually belong in WHERE, since in ON they would not remove left rows at all, only stop them matching. If you ever see LEFT JOIN followed by a WHERE test on a right-table column that is not IS NULL, suspect this bug.

5. Self-joins, semi-joins and anti-joins

A self-join joins a table to itself under two aliases. With a manager_id column on employee, FROM employee e LEFT JOIN employee m ON m.emp_id = e.manager_id pairs each employee with their manager; LEFT keeps the person at the top, whose manager_id is NULL. Self-joins also answer "pairs" questions, such as employees in the same department: JOIN employee b ON a.dept_id = b.dept_id AND a.emp_id < b.emp_id, where the < stops each pair appearing twice and stops people pairing with themselves. For our data that returns exactly one pair, (Raj, Li).

A semi-join asks "rows of A that have at least one match in B", without repeating A's rows per match. Departments that have employees:

SELECT dept_name FROM department d
WHERE EXISTS (SELECT 1 FROM employee e WHERE e.dept_id = d.dept_id);

This returns Sales and Eng, each once. Writing it as an inner join would return Eng twice, and "fixing" that with DISTINCT does more work for the same answer. The subquery is correlated: it refers to d.dept_id from the outer query, so logically it is evaluated per department, although the planner turns it into a single semi-join operation. WHERE dept_id IN (SELECT dept_id FROM employee) is also a semi-join and is safe, because IN only needs one true comparison.

An anti-join asks the opposite: rows of A with no match in B. Departments with no employees:

-- safe form 1
SELECT dept_name FROM department d
WHERE NOT EXISTS (SELECT 1 FROM employee e WHERE e.dept_id = d.dept_id);
-- safe form 2
SELECT d.dept_name FROM department d
LEFT JOIN employee e ON e.dept_id = d.dept_id
WHERE e.emp_id IS NULL;

Both return Ops and Legal. The tempting third form, WHERE dept_id NOT IN (SELECT dept_id FROM employee), returns zero rows on our data, because Sam's dept_id is NULL. Section 9 explains exactly why, with truth tables.

6. GROUP BY and aggregates

GROUP BY collapses rows that share values of the grouping expressions into one row per group, and aggregate functions (COUNT, SUM, AVG, MIN, MAX) summarise each group. Trace SELECT dept_id, COUNT(*), AVG(salary) FROM employee GROUP BY dept_id. Step 3 sorts the four rows into bins by dept_id: bin 10 = {Ana}, bin 20 = {Raj, Li}, bin NULL = {Sam}. GROUP BY puts all NULLs into one group, which is one of the places SQL treats NULLs as equal. Step 5 computes per bin: (10, 1, 90), (20, 2, 110), (NULL, 1, 70).

The iron rule follows from the pipeline: after step 3, each output row is a whole group, so every column in SELECT must be either a grouping expression or an aggregate. SELECT dept_id, name, COUNT(*) ... GROUP BY dept_id asks for "the name" of a group containing Raj and Li, which is undefined. PostgreSQL rejects it, and so does MySQL in its default ONLY_FULL_GROUP_BY mode. SQLite accepts it and picks a value from some row, which is a quiet source of wrong answers. PostgreSQL relaxes the rule in one principled case: if you group by a table's primary key, you may select that table's other columns, since they are functionally determined by the key (db2).

HAVING filters groups, after aggregation. Departments with at least two employees: ... GROUP BY dept_id HAVING COUNT(*) >= 2 keeps only (20, 2, 110.0). Contrast WHERE, which filters rows before they are grouped: WHERE salary > 95 GROUP BY dept_id counts only the well-paid employees in each department. A useful habit: anything that can be decided per row goes in WHERE, because removing rows early is cheaper and clearer; HAVING is only for conditions on aggregates.

Conditional aggregation computes several metrics in one pass by aggregating a CASE expression: SUM(CASE WHEN salary >= 100 THEN 1 ELSE 0 END) AS seniors. PostgreSQL has a tidier form, COUNT(*) FILTER (WHERE salary >= 100). This is the standard way to build a report row with several counts, and the building block for the pivot queries in db4.

7. Counting correctly after joins

Joins and aggregates interact in two ways that produce wrong numbers without any error.

COUNT(*) versus COUNT(column) after an outer join. Employees per department, keeping empty departments:

SELECT d.dept_name, COUNT(*), COUNT(e.emp_id)
FROM department d LEFT JOIN employee e ON e.dept_id = d.dept_id
GROUP BY d.dept_name;

The lab prints Eng 2 2, Legal 1 0, Ops 1 0, Sales 1 1. Legal has one row in the joined table, the NULL-padded one, so COUNT(*) counts it. COUNT(e.emp_id) counts non-NULL values of the employee key, which is the right answer, zero. Always count a column from the optional side after an outer join.

Fan-out from two one-to-many joins. An order with 3 lines and 2 shipments, joined to both, produces 3 × 2 = 6 rows, so SUM(line.amount) counts every line twice and COUNT(shipment.id) counts every shipment three times. This is sometimes called the chasm trap, and it is behind many dashboards whose revenue is mysteriously too high. The fix is to aggregate each child to one row per parent first, in a subquery or CTE, then join those results; or, if the second child is only a filter ("orders that have shipped"), use EXISTS, which never multiplies rows.

8. NULL and three-valued logic

SQL logic has three truth values: true, false and unknown. Any comparison with NULL using =, <>, < or > is unknown, including NULL = NULL, because two missing values are not known to be equal. The connectives extend in the only consistent way, by asking whether the unknown could change the answer:

pqp AND qp OR qNOT p
trueunknownunknowntruefalse
falseunknownfalseunknowntrue
unknownunknownunknownunknownunknown

false AND anything is false, so the unknown does not matter; true OR anything is true. Everything else involving unknown stays unknown, and crucially NOT unknown is unknown. Then the filtering rule: WHERE, ON and HAVING keep a row only when the condition is true. Unknown is treated like false for filtering, but it is not false, which is why negating a condition does not give you the complement. WHERE dept_id = 20 returns Raj and Li; WHERE NOT (dept_id = 20) returns only Ana, and Sam is in neither result.

The tools for NULL: IS NULL and IS NOT NULL test for it and always return true or false (the lab shows = NULL matching 0 rows and IS NULL matching 1). IS DISTINCT FROM compares two values treating NULLs as equal to each other: a IS DISTINCT FROM b is the "did this value change?" test you want in change detection, where a <> b misses changes to or from NULL. COALESCE(a, b, …) returns the first non-NULL argument, for defaults. NULLIF(a, b) returns NULL if a = b, the idiom for safe division: clicks / NULLIF(views, 0).

SQL is not perfectly consistent about NULL. Comparisons treat NULLs as not equal, but GROUP BY, DISTINCT, UNION and INTERSECT treat them as equal (all NULLs form one group). A UNIQUE constraint, by default, allows many NULLs, because each NULL is "unknown" and not known to collide; PostgreSQL 15 added UNIQUE NULLS NOT DISTINCT to change that. And sorting must put NULLs somewhere: PostgreSQL sorts them as larger than every value (last in ascending order, first in descending), while MySQL and SQLite sort them first in ascending order. The lab's ORDER BY dept_id shows Sam first in SQLite. Write NULLS FIRST or NULLS LAST where it matters (PostgreSQL and SQLite support it).

9. Why NOT IN fails, traced

Now the opening story can be explained exactly. dept_id NOT IN (SELECT dept_id FROM employee) becomes dept_id NOT IN (10, 20, 20, NULL), which is defined as dept_id <> 10 AND dept_id <> 20 AND dept_id <> 20 AND dept_id <> NULL.

For Ops (30): 30 <> 10 is true, 30 <> 20 is true, 30 <> NULL is unknown. true AND unknown is unknown. WHERE drops it. For Sales (10): 10 <> 10 is false, so the whole AND is false. Every department evaluates to false or unknown, never true, so the result is empty. PostgreSQL's wiki adds a second reason to avoid the form: because of these semantics the planner cannot turn NOT IN (SELECT …) into an anti-join, so it runs as a subplan, which is fast only while the subquery's result fits in memory as a hash table, and otherwise falls back to a nested scan whose cost grows with the product of the two sizes.

NOT EXISTS asks a different question: is there any employee row whose condition e.dept_id = d.dept_id is true? For Ops, Sam's row gives unknown, which simply means it is not a match; no row is a match, so NOT EXISTS is true and Ops is returned. Unknowns never "poison" EXISTS. The positive forms, IN and EXISTS, behave the same as each other, since IN only needs one true comparison and an unknown elsewhere does not stop it.

10. Aggregates and NULL

Every aggregate except COUNT(*) ignores NULL inputs. With bonuses 10, NULL, 5 and 0, the lab shows AVG(bonus) = 5.0 (15 divided by the 3 non-NULL values), while SUM(bonus) / COUNT(*) = 3.75, and COUNT(bonus) = 3 while COUNT(*) = 4. Neither average is wrong in itself; they answer different questions ("average among those with a recorded bonus" versus "average per employee, counting unknown as zero"). Decide which one the business means, and make it explicit with COALESCE(bonus, 0) if needed.

Two edge cases catch people. An aggregate over zero rows: COUNT gives 0, but SUM, AVG, MIN and MAX give NULL, so a revenue report for a day with no sales shows a blank, not 0, unless you write COALESCE(SUM(amount), 0). And COUNT(DISTINCT col) also ignores NULLs, so COUNT(DISTINCT dept_id) over our employees is 2, not 3, even though SELECT DISTINCT dept_id returns three rows.

11. Set operations: UNION, INTERSECT and EXCEPT

Joins combine tables side by side; set operations stack the results of two queries on top of each other. Both queries must return the same number of columns with compatible types, and the column names come from the first query. UNION returns rows in either result with duplicates removed; UNION ALL returns all rows of both, duplicates kept; INTERSECT returns rows in both; EXCEPT (called MINUS in Oracle) returns rows in the first but not the second.

On our data, SELECT dept_id FROM department EXCEPT SELECT dept_id FROM employee returns 30 and 40, another correct way to find empty departments. Notice that it is not fooled by Sam's NULL: set operations compare whole rows using "not distinct" semantics, the same as DISTINCT, so the NULL from employee simply has no counterpart in department and is ignored. SELECT dept_id FROM department INTERSECT SELECT dept_id FROM employee returns 10 and 20, once each.

The everyday choice is between UNION and UNION ALL. UNION must deduplicate the combined result, which means sorting or hashing all of it, and it can hide real duplicates that indicate a bug. UNION ALL is a simple append, streams without buffering, and is what you want whenever the two parts cannot overlap (this month's events plus last month's archive) or duplicates are meaningful. A good default is UNION ALL, switching to UNION only when you can say what duplicates you expect and why they should go. A common production use is stitching a partitioned or archived table back together, SELECT … FROM events_2026_09 UNION ALL SELECT … FROM events_2026_10, which is exactly what PostgreSQL's declarative partitioning does for you behind the scenes.

12. Writing SQL live: a method that avoids the traps

Interviewers ask candidates to write SQL on a whiteboard or in a shared editor, and the same five-step method works for almost every question.

First, state the grain of the answer. "One row per department" or "one row per customer per month". The grain decides what you GROUP BY and which table drives the query. Most fan-out bugs come from never saying the grain out loud.

Second, pick the driving table and decide on unmatched rows. If the answer should include departments with no employees, the query starts FROM department and uses LEFT JOIN to employee. Say the decision: "I'm using a left join so empty departments show zero."

Third, place each condition deliberately. Row filters on the driving table go in WHERE; conditions that define a match on an optional table go in ON; conditions on aggregates go in HAVING.

Fourth, aggregate at the right grain. If two one-to-many children are involved, aggregate each to the parent's grain first in a CTE. Count a key from the optional side, not *.

Fifth, walk the awkward rows. Before declaring victory, trace a parent with no children, a child with a NULL foreign key, and a group with one row through the query. This is the step that catches NOT IN and the ON/WHERE bug, and narrating it is what distinguishes a senior answer.

13. Putting it together: an LLM usage report

A realistic query an AI engineer writes weekly: per model, over the last day, the number of calls, the error rate, the average latency of successful calls and the number of distinct users, keeping models that had no calls so the dashboard shows zeros. Assume model(name) and llm_call(call_id, model, user_id, latency_ms, error_code, created_at), where error_code is NULL on success.

SELECT m.name,
       COUNT(c.call_id)                                      AS calls,
       AVG(CASE WHEN c.error_code IS NOT NULL THEN 1.0
                WHEN c.call_id IS NOT NULL THEN 0 END)       AS error_rate,
       AVG(CASE WHEN c.error_code IS NULL THEN c.latency_ms END) AS ok_latency_ms,
       COUNT(DISTINCT c.user_id)                             AS users
FROM model m
LEFT JOIN llm_call c
       ON c.model = m.name
      AND c.created_at >= now() - interval '1 day'
GROUP BY m.name
ORDER BY calls DESC;

Every rule in this lesson appears. The time filter is in ON, not WHERE, so idle models survive the left join. COUNT(c.call_id), not COUNT(*), so idle models show 0. The error rate uses IS NOT NULL and returns NULL rather than 0 for a model with no calls, because there is no rate to report. The latency average uses a CASE that yields NULL for failed calls, which AVG then skips, a compact form of conditional aggregation. And ORDER BY uses the alias because it runs after SELECT.

Bags, sets and why duplicates survive

Relational algebra (db1) is defined on sets, but SQL tables and results are bags: a row may appear several times. SQL chose bags for cost, since eliminating duplicates requires sorting or hashing the whole result, and for meaning, since a query like SELECT dept_id FROM employee is often fed to an aggregate where multiplicity matters (counting employees per department needs every row). The consequences are systematic: projection does not deduplicate, UNION does but UNION ALL does not, joins multiply rows, and IN versus join differ in multiplicity. A practical heuristic: when you are about to write DISTINCT, ask which join produced the duplicates. If the duplicates come from a one-to-many join used only as a filter, replace the join with EXISTS; if they come from a genuinely many-valued relationship, you probably want an aggregate instead.

How the planner treats subqueries

Logically a correlated subquery is evaluated once per outer row, but no serious database executes it that way when it can avoid it. PostgreSQL's planner "pulls up" EXISTS and IN (SELECT …) into semi-join operators and NOT EXISTS into anti-join operators, which can then use any join algorithm (hash, merge, nested loop with an index, db7). NOT IN (SELECT …) cannot be converted because the NULL semantics differ from an anti-join, so it remains a subplan: a hashed subplan if the planner estimates the subquery result fits in work_mem, otherwise a plain subplan that rescans for every outer row. The result is a query that is fast in testing and orders of magnitude slower once the data grows past a threshold, which the PostgreSQL wiki highlights. Scalar subqueries in SELECT, such as (SELECT COUNT(*) FROM comment c WHERE c.post_id = p.id), are often executed per row; for large outer results, a grouped join is usually better.

Lateral joins

A normal subquery in FROM cannot refer to other tables in the same FROM clause. LATERAL (PostgreSQL, MySQL 8.0.14+) lifts that restriction: the subquery is evaluated for each row of the tables to its left. Its killer use is "top N per group": for each department, its two best-paid employees, via FROM department d CROSS JOIN LATERAL (SELECT name, salary FROM employee e WHERE e.dept_id = d.dept_id ORDER BY salary DESC LIMIT 2) top. With an index on (dept_id, salary DESC) each lateral subquery is a short index scan, which beats ranking every employee with a window function (db4) when there are few groups and many rows per group.

Grouping sets, ROLLUP and CUBE

Reports often need subtotals: revenue per region and product, per region, and overall. Three GROUP BY queries joined by UNION ALL would scan the data three times. GROUP BY GROUPING SETS ((region, product), (region), ()) computes all three in one pass; ROLLUP (region, product) is shorthand for exactly that hierarchy, and CUBE (region, product) for every combination. In the output, the columns not used by a given grouping set are NULL, which is ambiguous if the data itself contains NULLs, so the GROUPING(region) function returns 1 for rows where region was rolled up. These are standard SQL, supported by PostgreSQL; MySQL has WITH ROLLUP.

Why NULL exists, and the case against it

Codd later argued that relations needed a way to represent missing information, and even proposed two kinds of NULL (missing but applicable, and inapplicable). SQL adopted one, and with it three-valued logic. Critics, notably Chris Date, have argued that NULLs break the clean logic of the model: a database with NULLs can give answers that are wrong in the real world, as NOT IN shows, and the meaning of each NULL is not recorded anywhere. The practical position most experienced designers take is in between: use NOT NULL by default, so that every nullable column is a deliberate choice; give each nullable column one documented meaning; and move optional groups of attributes into separate tables when their absence is common. Fewer NULLs means fewer three-valued surprises.

Dialect differences that matter in practice

Core SQL is standard, but enough varies that porting queries between engines is a source of bugs. Beyond NULL ordering and GROUP BY strictness: string concatenation is || in PostgreSQL and SQLite but CONCAT() in MySQL by default (where || means OR unless PIPES_AS_CONCAT is set); integer division truncates in PostgreSQL and SQLite (7 / 2 = 3) but returns a decimal in MySQL; string comparison is case-sensitive in PostgreSQL but case-insensitive under MySQL's default collations; and SQLite's flexible typing lets a text value sit in an integer column. The lesson for a team running SQLite in tests and PostgreSQL in production is that the tests will not catch these differences; run integration tests against the real engine.

The silent-wrong-answer failure mode

Most SQL bugs in production do not crash or slow anything down; they return a plausible wrong number. The NOT IN story in the introduction is the archetype, and the others in this lesson behave the same way: a WHERE clause on the optional side of an outer join that drops rows, a fan-out join that doubles revenue, an AVG that silently ignores missing values, an ungrouped column that SQLite or an old MySQL configuration filled with an arbitrary value. Because nothing fails, these bugs live for months. The defences are mostly process. Write reconciliation checks for important metrics (the sum of per-region revenue must equal total revenue; the count of customers in a segmentation must equal the count of customers). Test queries on data that includes the awkward cases: NULLs in join keys, parents with no children, children with several kinds of children. And review SQL like code, with someone asking "what happens to rows with no match?" for every join.

When NOT IN also becomes slow

The PostgreSQL wiki's second warning about NOT IN (SELECT …) is a performance cliff. A hashed subplan is used only when the planner expects the subquery result to fit in memory (governed by work_mem); above that, it falls back to rescanning the subquery result for each outer row. A query that ran in 200 ms when the subquery returned 10,000 ids can take hours when it returns 10 million, without any change in the SQL. The symptom in EXPLAIN (db7) is a SubPlan node under a filter rather than an Anti Join. Rewriting as NOT EXISTS fixes both the semantics and the plan.

Joins that explode

A missing or wrong join condition produces a Cartesian product. In development, 100 × 100 rows is 10,000 rows and nobody notices; in production, 1 million × 1 million is a trillion, and the query runs until it fills a temporary disk or is killed. Typical causes are a join condition that references the wrong alias (ON o.customer_id = o.customer_id, always true), a comma join with a forgotten WHERE predicate, or a many-to-many join through a junction table on a non-unique column. Protections include statement timeouts (statement_timeout in PostgreSQL) for application and analyst roles, row-count sanity checks in data pipelines, and always writing explicit JOIN … ON rather than comma joins so a missing condition is a syntax error rather than a cross join.

NULLs in join keys and data pipelines

Data imported from CSV files, third-party APIs and event streams is full of NULLs where your schema assumed values: an event with no user id because the user was logged out, a row from a partner with no region code. Each one silently disappears from inner joins and appears as "unknown" groups in GROUP BY. A useful production habit is to count NULLs in every join key as a data-quality metric, alert when the rate changes, and decide explicitly whether NULL-keyed rows should be dropped, bucketed as "unknown", or rejected at ingestion.

Observability for SQL

To find problem queries in a running PostgreSQL system, the standard tool is the pg_stat_statements extension, which aggregates execution counts, total and mean time and rows returned per normalized query; MySQL's equivalent is the performance schema's statement digests, and its slow query log. "Rows returned" is an underused column: a query that normally returns 50 rows and suddenly returns 50,000 is often a join bug introduced by a schema change. For LLM-related tables specifically, where engineers frequently write ad-hoc analysis queries against large call logs, give analysts a replica, a statement timeout and a read-only role, so a fan-out mistake cannot hurt the primary.

Goal: run every join type, the ON/WHERE trap, the NOT IN trap and the NULL aggregate rules on the lesson's two tables, and match each output to the text. What to look for.

  1. Row counts 3, 4, 5, 6 and 16 for inner, left, right, full and cross joins, and which rows carry None (Python's NULL).
  2. The anti-join via NOT EXISTS returns Ops and Legal, while NOT IN returns 0 row(s). Sam's NULL dept_id is the only cause: change Sam's dept_id to 10 and rerun, and NOT IN returns the same two rows as NOT EXISTS.
  3. Filter in ON gives 5 rows, filter in WHERE gives 2: the left join collapsed to an inner join.
  4. count(*) versus count(e.emp_id) differ only for Legal and Ops (1 versus 0).
  5. (5.0, 3.75, 3, 4): AVG skips the NULL bonus, the manual average does not.
  6. = NULL matches 0 rows, IS NULL matches 1, and Sam sorts first, which is SQLite's (and MySQL's) NULL ordering; PostgreSQL would put Sam last.

Diagnose: the conversion dashboard that disagrees with finance

A dashboard shows conversion per marketing campaign with this query, and finance says signup counts are too low and revenue too high:

SELECT c.name, COUNT(*) AS signups, SUM(p.amount) AS revenue
FROM campaign c
LEFT JOIN signup s   ON s.campaign_id = c.id
LEFT JOIN payment p  ON p.user_id = s.user_id
WHERE s.created_at >= '2026-09-01'
GROUP BY c.name;

Find every bug and write the corrected query.

Answer

Bug 1: WHERE on the optional side. s.created_at >= … removes campaigns with no signups (their s columns are NULL), so the left join became inner and campaigns with zero signups vanish. Move the date condition into the ON clause of the signup join.

Bug 2: fan-out. A user with three payments produces three rows, so COUNT(*) counts that signup three times (signups too high for paying users, while bug 1 lowered totals elsewhere) and every payment is summed once per matching signup row. Signups and payments are two different grains; aggregate payments per user first.

Bug 3: COUNT(*) after an outer join. A campaign with no signups would show 1. Count the signup key.

Possible bug 4: grouping by name. Two campaigns with the same name merge. Group by the id.

WITH pay AS (
  SELECT user_id, SUM(amount) AS amount
  FROM payment GROUP BY user_id
)
SELECT c.id, c.name,
       COUNT(s.user_id)               AS signups,
       COALESCE(SUM(pay.amount), 0)   AS revenue
FROM campaign c
LEFT JOIN signup s ON s.campaign_id = c.id
                  AND s.created_at >= '2026-09-01'
LEFT JOIN pay     ON pay.user_id = s.user_id
GROUP BY c.id, c.name;

Now each signup row joins to at most one pre-aggregated payment row, so nothing is multiplied. How to verify: the sum of signups across campaigns should equal SELECT COUNT(*) FROM signup WHERE created_at >= '2026-09-01' AND campaign_id IS NOT NULL, and total revenue should equal payments by those users; check both before trusting the dashboard. Also confirm with finance whether revenue should be limited to payments after the signup date, which is a definition question, not a SQL one.
