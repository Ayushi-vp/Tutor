A product manager asks three questions on a Monday morning. Who are the top three customers by revenue in each country? What is each day's revenue alongside its running month-to-date total? And how many people report, directly or indirectly, to the head of engineering? With only the SQL from db3 (joins, GROUP BY and HAVING), each of these is awkward. The first needs a correlated subquery counting how many customers in the same country earned more, run once per customer. The second needs a self-join of the revenue table to every earlier day, which for a year of data compares 365 × 365 pairs. The third cannot be written at all without knowing the depth of the org chart in advance, so people end up writing a loop in application code that sends one query per level.

All three are routine with the features in this lesson, which were added to the SQL standard in 1999 (recursive queries) and 2003 (window functions) and are now in every major engine: PostgreSQL, MySQL 8, SQL Server, Oracle, SQLite since 3.25, and every data warehouse. Window functions compute rankings, running totals and comparisons with neighbouring rows while keeping every row. Common table expressions let you name intermediate results so a long query reads like a series of steps. Recursive CTEs walk hierarchies and graphs of any depth inside the database.

These features are also the backbone of live SQL interviews. "Second-highest salary per department", "users active on three consecutive days", "split events into sessions" and "running total" are among the most-asked questions, and each has a clean window-function answer and several messy wrong ones. They also have traps: the default window frame silently includes tied rows, LAST_VALUE does not do what its name says, a recursive query over data with a cycle never ends, and older PostgreSQL versions made CTEs an optimization barrier.

This lesson builds each feature from first principles with small tables you can trace by hand, and every result in it is reproduced by the lab using Python's built-in SQLite. It ends with production concerns, including how GitLab moved its namespace hierarchy away from recursive queries when they became too slow at scale, and with AI-engineering uses such as sessionizing chat logs and tracking evaluation scores across runs.

Three new tools, one idea each

Each feature in this lesson answers one limitation of basic SQL.

CTEs answer "my query is unreadable". A query with three nested subqueries reads inside out. A common table expression lets you write WITH monthly AS (…), ranked AS (… FROM monthly …) SELECT … FROM ranked: each step named, each step reading from the one before. Think of it as assigning intermediate results to variables, except the database is free to merge the steps when it plans the query.

Recursive CTEs answer "I don't know how many levels there are". A recursive CTE has two parts: a starting query (the CEO) and a step query that finds the next level from the previous one (everyone whose manager is in the last level found). The database runs the step repeatedly until it finds nothing new. It is the SQL version of a breadth-first search, and it works for org charts, category trees, bills of materials and graph reachability.

Window functions answer "I need a group calculation but I want to keep the rows". This is the big one. GROUP BY gives one row per group. A window function gives each row a value computed from a window of related rows: its rank within its department, the sum of all rows up to it, the value in the previous row.

The window, pictured

Imagine the result rows laid out in a long list. For each row in turn, you hold up a frame, a small window, that shows some of the other rows. PARTITION BY team says the window only ever shows rows from the same team: the list is cut into independent sections. ORDER BY points DESC says how rows are arranged inside each section. The frame says which of the arranged rows the window shows for the current row: "everything from the top of my section down to me" for a running total, "the six rows before me and me" for a weekly moving average, or "the whole section" for a team average. The function then computes over what the window shows, and writes the answer onto the current row. Nothing is collapsed: four rows in, four rows out.

The analogy is close, with one twist the figure shows: under the default frame, the window extends to the current row and every row that ties with it. That rule, harmless most of the time, is behind the most common window-function bug, and section 6 traces it.

Where they fit in the pipeline

Recall the logical order from db3: FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT. Window functions are evaluated as part of SELECT, after grouping and HAVING. Two consequences follow. You cannot filter on a window function in WHERE (it does not exist yet), so "rank ≤ 3" needs an outer query around the one that computes the rank. And a window function can use aggregates: RANK() OVER (ORDER BY SUM(amount) DESC) ranks groups after GROUP BY has formed them. CTEs and subqueries simply provide tables to FROM, so they slot in at the very start.

1. Subqueries of every shape

A subquery is a SELECT inside another statement. What you can do with it depends on its shape. A scalar subquery returns one column and at most one row, so it can stand wherever a single value is allowed: SELECT name, salary - (SELECT AVG(salary) FROM employee) AS vs_avg FROM employee. If it returns two rows, the query fails at run time; if it returns none, the value is NULL. A row or list subquery appears with IN, EXISTS, ANY or ALL, as db3 covered for semi- and anti-joins. A table subquery, or derived table, appears in FROM and acts like a table for the rest of the query: FROM (SELECT dept_id, AVG(salary) AS avg_sal FROM employee GROUP BY dept_id) d.

Any of these can be correlated, meaning it refers to a column of the outer query. SELECT name FROM employee e WHERE salary > (SELECT AVG(salary) FROM employee x WHERE x.dept_id = e.dept_id) finds people paid above their own department's average. Logically the subquery runs once per outer row with that row's dept_id; physically the planner often rewrites it into a join against a pre-aggregated table. That rewrite is not guaranteed, though, and a correlated scalar subquery in SELECT over a large outer result can be executed row by row. When you see one in a slow query, consider computing the aggregate once in a derived table or CTE and joining it, or, as section 5 shows, a window function that does it in one pass.

2. Common table expressions

A common table expression (CTE) names a subquery at the front of a statement:

WITH dept_avg AS (
  SELECT dept_id, AVG(salary) AS avg_sal
  FROM employee GROUP BY dept_id
),
above AS (
  SELECT e.name, e.dept_id, e.salary, d.avg_sal
  FROM employee e JOIN dept_avg d USING (dept_id)
  WHERE e.salary > d.avg_sal
)
SELECT * FROM above ORDER BY dept_id;

Each CTE can read from those defined before it, so the query reads as a pipeline of named steps. That is the main reason to use them: a reviewer can check each step's grain and logic separately. A CTE can also be referenced several times in the main query, which a derived table cannot.

How the database executes a CTE has changed over time and differs by engine, and it matters for performance. Before PostgreSQL 12, every CTE was materialized: computed in full and stored in a temporary result before the main query ran, which made it an "optimization fence". A filter written outside the CTE could not be pushed inside it. Since PostgreSQL 12, the documentation's rule is that a non-recursive CTE with no side effects (a plain SELECT with no volatile functions) is folded into the parent query if it is referenced exactly once, and computed once if referenced more than once. You can override the choice: WITH w AS MATERIALIZED (…) forces a separate computation, useful when an expensive CTE is referenced in a way the planner misjudges, and NOT MATERIALIZED forces inlining. CTEs that modify data (WITH moved AS (DELETE … RETURNING *)) are always executed exactly once.

3. Recursive CTEs, step by step

A recursive CTE refers to itself. Its shape is fixed: an anchor member, then UNION ALL (or UNION), then a recursive member that joins the CTE's own name.

WITH RECURSIVE chain(id, name, depth, path) AS (
  SELECT id, name, 0, name                    -- anchor: the CEO
  FROM emp WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, c.depth + 1,           -- recursive: next level down
         c.path || ' > ' || e.name
  FROM emp e JOIN chain c ON e.manager_id = c.id
)
SELECT depth, name, path FROM chain ORDER BY path;

The data: Asha (id 1, no manager), Ben and Cara report to Asha, Dev and Eli report to Ben, Fay reports to Dev. The database evaluates the CTE with a working table, the rows found in the latest iteration:

  1. Anchor. Run the first SELECT: one row, (1, Asha, 0, 'Asha'). Add it to the result and make it the working table.
  2. Iteration 1. Run the recursive SELECT with chain meaning only the working table: employees whose manager_id is 1. Ben and Cara, depth 1. Add to the result; they become the working table.
  3. Iteration 2. Employees whose manager is Ben or Cara: Dev and Eli, depth 2.
  4. Iteration 3. Employees managed by Dev or Eli: Fay, depth 3.
  5. Iteration 4. Employees managed by Fay: none. The working table is empty, so recursion stops.

The result has six rows, and the lab prints them sorted by path: Asha; Asha > Ben; Asha > Ben > Dev; Asha > Ben > Dev > Fay; Asha > Ben > Eli; Asha > Cara. Sorting by the path string gives a depth-first, indented org-chart order for free, which is a handy trick for displaying trees (PostgreSQL 14 also offers a SEARCH DEPTH FIRST BY clause for this).

That last point is a hazard. If the data contains a cycle (Fay is accidentally recorded as Asha's manager), every iteration finds new rows forever and the query never ends. Defences, in order of preference: add a depth guard to the recursive member (WHERE c.depth < 50); carry the visited ids in an array and stop when the next id is already in it (WHERE NOT e.id = ANY(c.visited) in PostgreSQL); use UNION instead of UNION ALL, which discards rows already produced and so stops when a cycle only reproduces identical rows (it does not help once you carry a depth or path column, since those make every row distinct); or, in PostgreSQL 14+, the CYCLE id SET is_cycle USING path clause, which does the bookkeeping for you.

Recursive CTEs are not only for trees. Generating a calendar, WITH RECURSIVE d(day) AS (SELECT date '2026-01-01' UNION ALL SELECT day + 1 FROM d WHERE day < date '2026-12-31'), gives a row per day to left-join sparse data against (PostgreSQL also has generate_series). Walking the reverse direction, from an employee up to the CEO, just flips the join: JOIN chain c ON e.id = c.manager_id. Graph reachability, such as "every package a dependency pulls in", uses the same pattern with cycle protection.

4. Window function syntax

A window function call has the form function(args) OVER (PARTITION BY … ORDER BY … frame), all three parts optional. OVER () with nothing inside makes the whole result one partition with no order: SELECT name, salary, AVG(salary) OVER () FROM employee puts the company-wide average on every row. Adding PARTITION BY dept_id computes the average per department, still on every row. When several window calls share a definition, name it once: … OVER w … WINDOW w AS (PARTITION BY team ORDER BY points DESC), as the lab does.

Three families of functions can be used with OVER. Ranking functions (ROW_NUMBER, RANK, DENSE_RANK, NTILE, PERCENT_RANK, CUME_DIST) depend only on the partition and order. Offset functions (LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE) read a value from another row. And every ordinary aggregate (SUM, AVG, COUNT, MIN, MAX) becomes a window function when given an OVER clause, computing over the frame.

5. Ranking, traced on ties

Team A scores: Ana 90, Raj 85, Li 85, Sam 70. With PARTITION BY team ORDER BY points DESC:

ROW_NUMBER gives every row a distinct number; among the tied Raj and Li, which gets 2 is arbitrary (the lab happened to give Raj 2), and it can change between runs or after an index is added. If the result must be deterministic, add a tie-breaker: ORDER BY points DESC, name. RANK gives ties the same rank and then skips, like a sports table: two people share second, so the next is fourth. DENSE_RANK gives ties the same rank without skipping. Team B, being a separate partition, starts again at 1.

The classic uses follow directly. "Top N per group": wrap the ranked query and filter, SELECT … FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY team ORDER BY points DESC) AS rn FROM score) t WHERE rn = 1, which the lab shows returning Ana and Mo. The outer query is necessary because the window is computed after WHERE. Choose the function by what "top N" means: exactly N rows (ROW_NUMBER), everyone whose rank is at most N (RANK), or everyone with one of the N highest distinct values (DENSE_RANK). "Second-highest salary" is DENSE_RANK = 2, which correctly handles two people tied for first. Deduplication is the same pattern: keep ROW_NUMBER() OVER (PARTITION BY email ORDER BY updated_at DESC) = 1 to retain only the latest row per email.

6. Running totals, frames and the RANGE trap

Adding ORDER BY inside OVER changes an aggregate from "over the whole partition" to "over a frame that moves with the current row". The frame is specified as ROWS, RANGE or GROUPS BETWEEN start AND end, where start and end are UNBOUNDED PRECEDING, n PRECEDING, CURRENT ROW, n FOLLOWING or UNBOUNDED FOLLOWING. If you give ORDER BY but no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. If you give neither, the frame is the whole partition.

ROWS counts physical rows. RANGE works on ORDER BY values: "current row" in RANGE mode means "the current row and all its peers", rows with the same ORDER BY value. Now trace sales of 100 on day 1, 50 and 70 on day 2, and 30 on day 3:

dayamountSUM OVER (ORDER BY day) — default RANGESUM OVER (ORDER BY day ROWS …)
1100100100
250220150
270220220

With the default, both day-2 rows show 220, because each one's frame includes its peer. That is actually what you want for "revenue up to and including this day". With ROWS, the first day-2 row shows 150, but which of the two day-2 rows comes first is arbitrary, so the 150 might belong to either. The lesson: decide what the running total means. Per day: aggregate to one row per day first, then any frame works. Per event: use ROWS and a unique ordering such as ORDER BY day, sale_id.

Moving windows use explicit bounds: AVG(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) is a seven-row moving average, which is a seven-day average only if there is exactly one row per day with no gaps. With missing days, fill the calendar first (section 3's generated dates, left-joined), or use a value-based frame, RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW, which PostgreSQL supports for date and numeric orderings. GROUPS frames, a newer addition, count groups of peers rather than rows.

The frame also explains the LAST_VALUE trap. LAST_VALUE(name) OVER (PARTITION BY team ORDER BY points DESC) looks like "the lowest scorer in the team", but the default frame ends at the current row, so it returns the current row's own name (or its last peer's). Either widen the frame to ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING or use FIRST_VALUE with the order reversed.

7. LAG, LEAD and comparisons with neighbours

LAG(x, n, default) returns x from n rows earlier in the window order (n defaults to 1), or the default (NULL if omitted) when there is no such row; LEAD looks forward. They make period-over-period questions single-pass: revenue - LAG(revenue) OVER (ORDER BY month) AS change, or revenue / NULLIF(LAG(revenue, 12) OVER (ORDER BY month), 0) - 1 for year-over-year growth on monthly rows. They ignore the frame, since they address rows by offset, but they respect PARTITION BY, so LAG(ts) OVER (PARTITION BY user_id ORDER BY ts) never reads another user's event. That partition boundary is what makes the next two patterns work.

8. Gaps and islands

"Gaps and islands" is the name for problems that group consecutive values into runs. The trick is elegant. User 7 was active on days 1, 2, 3, 5, 6 and 9. Number the days in order with ROW_NUMBER: 1, 2, 3, 4, 5, 6. Subtract the row number from the day: 0, 0, 0, 1, 1, 3. Within a run of consecutive days, both the day and the row number go up by one each step, so the difference stays constant; at every gap, the day jumps by more than one and the difference changes. Grouping by the difference gives one row per streak:

SELECT user_id, MIN(day) AS start_day, MAX(day) AS end_day, COUNT(*) AS days
FROM (SELECT user_id, day,
             day - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY day) AS grp
      FROM login)
GROUP BY user_id, grp;

The lab returns (1, 3, 3), (5, 6, 2) and (9, 9, 1): streaks of three days, two days and one day. With real dates, subtract the row number as a number of days (day - (ROW_NUMBER() OVER … ) * interval '1 day' in PostgreSQL). If a user can log in twice on the same day, deduplicate first or use DENSE_RANK, otherwise the duplicate day breaks the arithmetic. "Users active on three or more consecutive days" is then HAVING COUNT(*) >= 3.

9. Sessionization: LAG plus a running sum

When "consecutive" means "within 30 minutes" rather than "the next integer", use the other standard pattern: mark boundaries, then number them with a running sum. For chat events per user:

WITH marked AS (
  SELECT user_id, event_id, ts,
         CASE WHEN LAG(ts) OVER w IS NULL
                OR ts - LAG(ts) OVER w > interval '30 minutes'
              THEN 1 ELSE 0 END AS is_new
  FROM chat_event
  WINDOW w AS (PARTITION BY user_id ORDER BY ts, event_id)
),
numbered AS (
  SELECT *, SUM(is_new) OVER (PARTITION BY user_id ORDER BY ts, event_id
                              ROWS UNBOUNDED PRECEDING) AS session_no
  FROM marked
)
SELECT user_id, session_no, MIN(ts) AS started, MAX(ts) AS ended, COUNT(*) AS events
FROM numbered GROUP BY user_id, session_no;

Trace one user with events at 10:00, 10:05, 10:50, 10:55 and 12:00. The gaps are none, 5, 45, 5 and 65 minutes, so is_new is 1, 0, 1, 0, 1. The running sum is 1, 1, 2, 2, 3: three sessions. Two details matter. The ordering includes event_id as a tie-breaker, so two events with the same timestamp are ordered deterministically, and the running sum uses ROWS, avoiding the RANGE peer behaviour of section 6. This "flag and cumulative sum" pattern generalizes to any rule for starting a new group: a status change, a price change, a new day.

10. Pivoting and unpivoting

A pivot turns row values into columns: from rows (product, month, revenue) to one row per product with a column per month. Standard SQL does it with conditional aggregation:

SELECT product,
       SUM(CASE WHEN month = '2026-01' THEN revenue END) AS jan,
       SUM(CASE WHEN month = '2026-02' THEN revenue END) AS feb,
       SUM(CASE WHEN month = '2026-03' THEN revenue END) AS mar
FROM monthly_sales GROUP BY product;

Each CASE yields the revenue only for its month and NULL otherwise, and SUM skips the NULLs, so each column sums exactly one month. The lab's version pivots team totals into two columns (330 for team A, 175 for team B). PostgreSQL's SUM(revenue) FILTER (WHERE month = '2026-01') is the same idea with tidier syntax. The limitation is that the output columns must be known when you write the query, because SQL needs a fixed result shape. For pivots whose columns depend on data, either generate the SQL in application code, use PostgreSQL's tablefunc extension and its crosstab function, or, often best, return the long format and pivot in the reporting tool.

Unpivoting goes the other way, from columns jan, feb, mar to rows. Portable SQL uses UNION ALL of one SELECT per column; PostgreSQL can do it in one pass with CROSS JOIN LATERAL (VALUES ('2026-01', jan), ('2026-02', feb), ('2026-03', mar)) AS v(month, revenue). Unpivoting is a frequent first step when cleaning spreadsheet-shaped data loaded into a database, because the long format is the normalized one (db2).

11. Distribution functions and percentiles

Three more window functions describe where a row sits in its partition's distribution. NTILE(n) splits the ordered partition into n buckets of as-equal-as-possible size and returns the bucket number: NTILE(4) OVER (ORDER BY spend DESC) labels customers as quartiles 1 to 4. With 10 rows and 4 buckets, the bucket sizes are 3, 3, 2, 2 (the extra rows go to the first buckets), and ties can be split across buckets, so NTILE is a convenience for roughly equal groups, not a statistical quantile. PERCENT_RANK() is (rank − 1) / (rows − 1), so the top row gets 0 and the bottom gets 1; for team A's scores ordered descending it gives Ana 0, Raj and Li 1/3, Sam 1. CUME_DIST() is the fraction of rows at or before the current row including its peers: Ana 0.25, Raj and Li 0.75, Sam 1.0.

For actual percentiles of a value, such as median latency, PostgreSQL uses ordered-set aggregates, which are aggregates rather than window functions: percentile_cont(0.5) WITHIN GROUP (ORDER BY latency_ms) interpolates between the two middle values, while percentile_disc(0.5) returns an actual value from the data. They work with GROUP BY (median latency per model) but not with OVER. For p95 and p99 latency over very large logs, exact percentiles require sorting every value; monitoring systems and warehouses therefore use approximate sketches such as t-digest or the APPROX_PERCENTILE family, trading a small error for constant memory. In interviews, knowing that a median needs a sort, while an average does not, is the insight being tested.

12. Choosing the tool: subquery, CTE, window or LATERAL

Many questions in this lesson can be answered several ways, and the choice affects readability and cost. Take "each employee's salary compared with their department's average". A correlated scalar subquery reads naturally but may run per row. A CTE computing averages per department, joined back, does two passes over employees and one join. A window function, AVG(salary) OVER (PARTITION BY dept_id), does it in one pass with one sort. For this shape, the window is the best default.

Now "the three most recent orders per customer". A window with ROW_NUMBER partitioned by customer and filtered to rn ≤ 3 sorts every order in the table. A LATERAL subquery per customer with ORDER BY created_at DESC LIMIT 3, backed by an index on (customer_id, created_at DESC), reads three index entries per customer. If there are 10,000 customers and 50 million orders, the second reads 30,000 rows instead of sorting 50 million. If you need the answer for a single customer, both reduce to an index scan. The rule of thumb: windows win when you need values for most rows; LATERAL with LIMIT wins when you need a few rows from each of many large groups and an index matches.

And "everything under this manager": only recursion (or a precomputed path) can do it, because the depth is unknown. Use a CTE for readability whenever a query has more than one logical step, and check the plan rather than assuming the CTE is or is not materialized. Saying this reasoning out loud in an interview, rather than reaching for the first construct that works, is what distinguishes a strong answer.

13. A worked example: evaluation trends for an LLM application

An AI team stores one row per test case per evaluation run: eval(run_id, model, prompt_version, case_id, score, created_at). They want, for each model, the latest run's mean score, the change from the previous run, the run's rank among all runs of that model, and a three-run moving average. Every tool in this lesson appears.

WITH runs AS (                            -- 1. aggregate to run grain
  SELECT run_id, model, MIN(created_at) AS started, AVG(score) AS mean_score
  FROM eval GROUP BY run_id, model
),
trend AS (                                -- 2. compare runs with windows
  SELECT model, run_id, started, mean_score,
         mean_score - LAG(mean_score) OVER m                  AS delta,
         AVG(mean_score) OVER (m ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS ma3,
         RANK() OVER (PARTITION BY model ORDER BY mean_score DESC) AS best_rank,
         ROW_NUMBER() OVER (PARTITION BY model ORDER BY started DESC, run_id DESC) AS recency
  FROM runs
  WINDOW m AS (PARTITION BY model ORDER BY started, run_id)
)
SELECT model, run_id, mean_score, delta, ma3, best_rank
FROM trend WHERE recency = 1;             -- 3. filter after the window

Step 1 fixes the grain: windows over case-level rows would compare a case to the previous case. Step 2 computes four window values in one pass; note that one window definition can be extended with a frame (m ROWS BETWEEN …). Step 3 filters on the window result in an outer query, because WHERE runs before windows. A best_rank of 1 on the latest run means it is the model's best run ever; a negative delta larger than the run-to-run noise is a regression worth a look.

How databases compute window functions

Internally, a window function is evaluated by sorting the input by the PARTITION BY and ORDER BY columns (or reading it already sorted from an index), then streaming through each partition. For ranking and LAG/LEAD, the work per row is constant once the rows are sorted. For aggregates over a frame, a naive implementation would recompute the aggregate over the whole frame for every row, which for a running sum over a million-row partition is quadratic. Real engines avoid that: for frames that start at UNBOUNDED PRECEDING they keep a running state and add each new row; for sliding frames they use the aggregate's "inverse transition" function (subtract the row leaving the frame) where one exists, as for SUM and COUNT, and fall back to recomputation or segment trees for MIN and MAX, which have no inverse. The practical consequence: the dominant cost is usually the sort, so several window functions with the same PARTITION BY and ORDER BY are nearly free once the first is computed, while windows with different orderings each need their own sort. The EXPLAIN output (db7) shows one WindowAgg node per distinct window specification, each typically above a Sort.

Indexes that serve windows

Because the sort dominates, an index matching (partition columns, order columns) can remove it. A query computing ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) over a large table benefits from an index on (user_id, created_at DESC), which delivers rows already in window order. This is the same reasoning as composite indexes for ORDER BY (db6). For "latest row per user" specifically, an alternative is PostgreSQL's DISTINCT ON (user_id) … ORDER BY user_id, created_at DESC, which with that index reads one row per user.

The cost model of recursive CTEs

A recursive CTE's cost is roughly the sum, over iterations, of joining the working table to the base table. With an index on manager_id, iteration k costs about one index lookup per row in level k, so a full walk of a tree with N nodes costs about N index lookups regardless of shape, which is excellent. Problems arise from three sources. First, the planner's row estimates for recursive CTEs are crude (it cannot know the depth), so joins on the CTE's output can get poor plans. Second, recursion over graphs rather than trees revisits nodes reachable by several paths, and UNION ALL multiplies them; UNION deduplicates at the cost of a hash table of everything seen. Third, running the walk on every request repeats work that changes rarely. Those are the cases where storing the hierarchy differently pays.

Alternative hierarchy encodings

Four encodings are worth knowing, each a trade-off between read and write cost. An adjacency list (a parent_id column) is the default: trivial to update (moving a subtree changes one row) and read with recursion. A materialized path stores each node's ancestors, as a string like /1/2/4/, a PostgreSQL array, or the ltree type; descendants are a prefix query that an index can serve, ancestors are read directly from the row, and moving a subtree rewrites the path of every descendant. A closure table stores one row per (ancestor, descendant, depth) pair, so every hierarchy question is a plain indexed join; it costs storage proportional to the sum of depths and inserts of one row per ancestor for each new node. Nested sets number nodes in a depth-first walk with left and right values, so descendants are a range query; inserting a node renumbers roughly half the tree, which is why nested sets suit nearly static hierarchies only. Interviewers like this question because the right answer depends on the read/write ratio and the size of subtree moves.

QUALIFY and dialect differences

Because window functions are computed after WHERE, filtering on them takes a wrapping subquery or CTE. Several analytical engines, including Snowflake, BigQuery, DuckDB and Teradata, add a QUALIFY clause that filters on window results directly: SELECT * FROM score QUALIFY ROW_NUMBER() OVER (PARTITION BY team ORDER BY points DESC) = 1. PostgreSQL, MySQL and SQLite do not have it. Other differences: MySQL supports window functions only from 8.0 and recursive CTEs from 8.0 too; SQLite has had window functions since 3.25 (2018); RANGE frames with interval offsets and GROUPS frames are supported in PostgreSQL 11+ and SQLite, but not everywhere; and the default recursion limit differs (SQL Server stops at 100 levels unless told otherwise, MySQL at cte_max_recursion_depth = 1,000, PostgreSQL has no built-in limit).

Determinism and reproducibility

A recurring theme is that window results depend on ordering, and ties make ordering ambiguous. ROW_NUMBER over tied values, ROWS frames over tied values, FIRST_VALUE with ties, and LAG with duplicate timestamps can all return different results between runs, between replicas, or after a plan change, without any data changing. For analytics this produces numbers that drift when re-run; for ML pipelines that build training labels or features with windows, it produces training sets that cannot be reproduced exactly. The fix is mechanical and worth making a habit: every window ORDER BY used for ROW_NUMBER, ROWS frames or offsets ends with a unique column, such as the primary key.

GitLab's namespaces: when recursion became the bottleneck

GitLab organizes groups, subgroups and projects into a hierarchy of namespaces, and permission checks, issue lists and search constantly need "all descendants of this group" or "all ancestors of this project". These were originally answered with recursive CTEs over a parent_id column. GitLab's development documentation records the outcome: recursive CTE queries had generally acceptable performance in isolation, but building larger queries around them was complex and produced slow queries. The fix was to cache each namespace's path in an indexed array column, traversal_ids, holding the ids from the root down to the namespace itself, so a namespace A.A.B stores [A, A.A, A.A.B]. Ancestors are then read directly from the row, and the root is the first element.

The descendant query is the interesting part. The array containment operator @> was found to be slow as the search space grew, so for large scopes GitLab uses the fact that PostgreSQL compares arrays element by element, like strings: all descendants of [1, 2, 3] have arrays greater than [1, 2, 3] and less than its next sibling [1, 2, 4]. A range comparison on an indexed array column is a B-tree range scan, the cheapest kind of index access (db6). The legacy recursive queries are still available for the cases that need them. It is a textbook example of trading write cost (every descendant's array must be rewritten when a group moves, which is rare) for read cost on a path that runs on nearly every request.

Runaway recursion

A recursive query over data with an unexpected cycle (a category whose parent chain loops back, a "replies to" chain corrupted by an import) never terminates under UNION ALL. In production this looks like a query whose duration grows until a timeout kills it, often with growing temporary file usage as the result accumulates. Protections: a depth guard in every recursive CTE that touches user-editable data; a constraint or trigger that prevents cycles at write time (for example rejecting an update that makes a node its own ancestor); a statement timeout on the application role; and, in PostgreSQL 14+, the CYCLE clause.

Window queries that sort too much

The usual window-function performance problem is memory and disk spent on sorting. A query computing a window over a 500-million-row event table sorts all of it by the partition and order columns; if the sort exceeds work_mem it spills to temporary files, visible in EXPLAIN ANALYZE as Sort Method: external merge Disk: …. Remedies are to filter before the window (a WHERE on date reduces the input, and remember WHERE runs first), to aggregate to a coarser grain first, to provide an index in window order, or to raise work_mem for that session. Several windows with different orderings in one query each trigger a sort, so aligning their specifications where possible is a cheap win.

Materialization surprises after upgrades

Teams upgrading from PostgreSQL 11 or earlier to 12+ occasionally see a query get slower, not faster: a CTE that used to be materialized once is now inlined and the inlined plan is worse, or a CTE with an expensive function is now evaluated many times. The reverse, much more common, is that queries speed up. Both are fixed explicitly with MATERIALIZED or NOT MATERIALIZED, and the general lesson is that any query whose performance depends on an optimizer heuristic should be checked with EXPLAIN after a major-version upgrade.

Analytics on LLM logs

AI products generate exactly the event streams these features were made for: chat messages, tool calls, model calls, ratings. Sessionization over message events defines "a conversation" for metrics; gaps-and-islands measures streaks of daily use; LAG over evaluation runs flags regressions; ROW_NUMBER keeps the latest version of a prompt or the final retry of a call. Two production habits help. Run these queries on a replica or in a warehouse, not on the primary that serves users, because a window over a large log table is a big sort. And materialize the expensive results (daily sessions, run-level scores) into summary tables on a schedule, so dashboards read small tables instead of recomputing windows over raw events on every page load.

Live SQL: retention and the second-best model

Table llm_call(call_id, user_id, model, created_at, latency_ms, rating), where rating is 1-5 or NULL. Write: (a) for each day, the number of users who made a call that day and also made one the previous day; (b) for each user, their second-most-used model (by call count), handling ties sensibly; (c) each call's latency next to the user's average latency over their previous 10 calls, excluding the current one.

Answer

(a) Day-over-day returning users. Reduce to one row per user per day, then use LAG to see each user's previous active day:

WITH days AS (
  SELECT DISTINCT user_id, CAST(created_at AS date) AS d FROM llm_call
), prev AS (
  SELECT user_id, d, LAG(d) OVER (PARTITION BY user_id ORDER BY d) AS prev_d FROM days
)
SELECT d, COUNT(*) FILTER (WHERE prev_d = d - 1) AS returning, COUNT(*) AS active
FROM prev GROUP BY d ORDER BY d;

DISTINCT first fixes the grain (several calls per day would otherwise make LAG compare a day with itself). d - 1 is date arithmetic in PostgreSQL.

(b) Second-most-used model. Aggregate, then rank:

WITH counts AS (
  SELECT user_id, model, COUNT(*) AS n FROM llm_call GROUP BY user_id, model
), ranked AS (
  SELECT *, DENSE_RANK() OVER (PARTITION BY user_id ORDER BY n DESC) AS r FROM counts
)
SELECT user_id, model, n FROM ranked WHERE r = 2;

DENSE_RANK returns every model tied for the second-highest count, and a user whose two top models tie for first gets the next distinct count as "second". If exactly one row per user is required, switch to ROW_NUMBER with a tie-breaker (ORDER BY n DESC, model) and say which tie rule you chose.

(c) Rolling average excluding the current row.

SELECT call_id, user_id, latency_ms,
       AVG(latency_ms) OVER (PARTITION BY user_id ORDER BY created_at, call_id
                             ROWS BETWEEN 10 PRECEDING AND 1 PRECEDING) AS prev10_avg
FROM llm_call;

The frame ends at 1 PRECEDING, so the current call is excluded; the first call per user gets NULL because its frame is empty. ROWS (not the default RANGE) and the call_id tie-breaker keep it exact and deterministic. This "compare to the user's own recent baseline" feature is the kind of thing an anomaly detector or an ML feature pipeline computes, and excluding the current row is what prevents label leakage.
