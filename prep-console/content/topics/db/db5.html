In 1995, Patrick O'Neil and his colleagues did a cost calculation for a bank-like system running the TPC-A benchmark at 1,000 transactions per second. Each transaction updated an account balance and appended a 50-byte row to a History table. The account updates alone already needed about 2,000 disk I/Os per second, which at roughly 40 I/Os per second per disk arm of the time meant about 50 disk arms. Then they asked: what does it cost to add an index on the History table by account id, so a customer can see their recent activity?

The answer was startling. Twenty working days of history is 576 million index entries, 9.2 GB, about 2.3 million leaf pages, far more than memory. Because account ids arrive in random order, every new history row lands on a random leaf page of the B-tree, which must be read from disk and later written back. That is another 2,000 I/Os per second, another 50 disk arms. One index doubled the disk cost of the whole system. Their paper, published in 1996, proposed a different structure for exactly this situation: the log-structured merge tree, which collects new index entries in memory and merges them into disk in large sequential batches, the way a merge sort does.

The disks have changed since then, but the tension has not. A B+ tree, the structure behind nearly every relational index, updates data in place and is superb for reads. An LSM tree, the structure behind RocksDB, Cassandra, ScyllaDB, LevelDB and many time-series and log stores, appends and merges and is superb for writes. Every storage engine is a set of choices about how bytes are laid out on pages, and those choices decide how many times each byte you write is rewritten, how many pages each query reads, and how much disk is wasted.

The engineering-at-scale lesson sc4 introduced pages, the buffer pool, B-trees and LSM trees as tools for system design. This lesson opens them up. You will see the exact layout of a PostgreSQL page and row, why a row has a two-part address, how a B+ tree node splits, the arithmetic that gives a 100-million-row index its height, how an LSM tree's memtable, SSTables, Bloom filters and compaction work together, and how to reason about write, read and space amplification with real numbers. That vocabulary is what lets you explain, rather than guess, why a UUID key slowed down inserts or why a Cassandra cluster's disk bandwidth is mostly spent on compaction.

Two filing strategies

Imagine a library that receives thousands of new index cards a day. One librarian keeps a single, perfectly sorted card catalogue: each new card is walked to its exact place among the drawers and slotted in. Finding a card is fast, since the catalogue is always sorted and you can jump straight to the right drawer. But every new card means a walk to a different drawer, and when a drawer is full it must be split into two, which means relabelling. That is a B+ tree: in-place, always sorted, read-friendly.

A second librarian keeps an inbox on the desk. New cards go into the inbox, which is kept sorted because it is small. When the inbox is full, its cards are bound into a small sorted booklet and put on a shelf. Every so often, several booklets are merged into one bigger sorted booklet, and the old ones are thrown away. Adding a card is nearly free. Finding a card means checking the inbox, then the newest booklet, then older ones, until you find it, although a quick index on each booklet's cover ("definitely not in here") lets you skip most of them. That is an LSM tree: append, sort in memory, merge later, write-friendly.

The analogy breaks in one place that matters: the second librarian's merging is not free. Every card is copied into a new booklet each time booklets are merged, so over its life a card may be copied ten or twenty times. That hidden copying is write amplification, and it is the price the LSM pays for cheap inserts.

Everything happens in pages

Both strategies work in fixed-size blocks called pages: 8 KB in PostgreSQL, 16 KB by default in MySQL's InnoDB, 4 KB by default in SQLite. A page is the unit read from disk, cached in memory (the buffer pool), written back and logged. Because reading 8 KB from an SSD costs about the same as reading 100 bytes, the whole design of a storage engine is about putting the rows a query needs into as few pages as possible, and touching as few pages as possible on each write.

So three questions describe any engine, and this lesson answers them for both designs. How are rows laid out inside a page? How are pages organised so the right one can be found? And when data changes, which pages are rewritten, and how many times?

The three amplifications

The answers boil down to three ratios, named in RocksDB's tuning guide. Write amplification is bytes written to storage divided by bytes written by the application: if you write 10 MB/s and the disk writes 30 MB/s, it is 3. Read amplification is the number of page reads per query: five pages to answer a lookup is 5. Space amplification is disk used divided by live data: 100 MB on disk for 10 MB of data is 10. A B+ tree has low read and space amplification and pays in write amplification on updates; an LSM tree has low write cost per insert and pays in reads and in compaction rewrites. Keep these three numbers in mind; every design choice below moves them.

1. Inside a page: the slotted layout

A page must hold variable-length rows, let rows be added and removed, and give each row an address that does not change when other rows move. The standard solution is the slotted page. PostgreSQL's documentation gives its exact layout for an 8 KB page:

  • A page header of 24 bytes: the page's position in the WAL (its LSN, used in recovery, db8), a checksum, flags, and two offsets, pd_lower and pd_upper, marking the start and end of free space.
  • An array of line pointers (item identifiers), 4 bytes each, growing forward from the header. Each holds the offset and length of one tuple.
  • Free space in the middle.
  • Tuples (row versions) stored from the end of the page backwards.
  • An optional special space at the very end, used by index pages (a B-tree page keeps sibling pointers there) and empty on heap pages.

A row's physical address is therefore (page number, slot number), which PostgreSQL calls the TID or ctid. You can see it with SELECT ctid, * FROM t. Indexes store TIDs, not byte offsets, so when the engine compacts a page to reclaim the space of deleted tuples, only the line pointers change, and every index entry pointing to (7, 2) is still correct.

Each tuple has its own overhead: a fixed header of 23 bytes on most machines (padded to 24 by alignment), holding the transaction ids that created and deleted this version, flags and a pointer to a newer version (the machinery of MVCC, db9), then a null bitmap if any column is NULL, then the column data, each column aligned to its type's boundary. Do the arithmetic for a narrow table of three bigints: 24 bytes of header plus 24 of data plus a 4-byte line pointer is 52 bytes per row, so about 156 rows fit in an 8 KB page, and nearly half of each row is overhead. That is why the per-row cost of PostgreSQL tables is often surprising, and why ordering columns from widest to narrowest can save the padding bytes that alignment inserts between, say, a 1-byte boolean and an 8-byte bigint.

2. Heap files and large values

A PostgreSQL table is a heap file: a sequence of pages in which rows are placed wherever there is room, in no key order. To insert, the engine consults the free space map, a small structure recording roughly how much space each page has, finds a page with enough room, and appends the tuple there. A full table scan reads pages in order; a lookup through an index follows the stored TID straight to the right page and slot. MySQL's InnoDB is different: its tables are stored inside the primary key's B+ tree, with rows in the leaves in key order, a design called a clustered index that db6 and db10 compare in detail.

A row must fit in a page, so what about a 50 KB JSON document or a 1 MB text field? PostgreSQL's answer is TOAST (The Oversized-Attribute Storage Technique). When a row would be wider than TOAST_TUPLE_THRESHOLD, normally 2 kB, PostgreSQL first compresses its large variable-length values, and if the row is still too wide, moves them into a separate TOAST table in chunks, leaving an 18-byte pointer in the row. Two consequences matter in practice. Queries that do not select the big column never read the TOAST table, so wide columns do not slow scans of the narrow ones. But updating any column of a row whose large value is TOASTed usually leaves the TOAST data in place (the docs note unchanged fields are preserved as-is), whereas fetching that value costs extra reads. Storing prompt and completion texts of LLM calls in the same table as their metadata works well for exactly this reason: the metadata scans stay fast.

3. The B+ tree: structure

A B+ tree is a balanced tree of pages. Leaf pages hold the index entries, each a key and a pointer to the row (a TID in PostgreSQL), sorted by key, and each leaf links to its left and right neighbours. Internal pages hold only separator keys and pointers to child pages: a separator says "keys below me go left, keys at or above me go right". The root is the single top page. Every leaf is the same distance from the root, so every lookup costs the same number of page reads.

A lookup for key 42 starts at the root, binary-searches its separators to find which child covers 42, reads that child, repeats, and arrives at a leaf, where it binary-searches for 42 and follows the TID to the heap. A range scan for keys 40 to 60 does one descent to the leaf containing 40, then walks right along the leaf chain until it passes 60, without returning to the upper levels. That leaf chain is the "+" in B+ tree and the reason these indexes handle BETWEEN, ORDER BY and LIMIT so well.

The power of the structure is its fan-out, the number of children per internal page. Because internal pages hold only small separators, one 8 KB page can point to hundreds of children, and the height of the tree grows with the logarithm of the row count in base several hundred.

4. Fan-out and height, worked for 100 million rows

Compute it for a PostgreSQL index on a bigint column. Each leaf entry is an index tuple: an 8-byte header (which holds the TID), the 8-byte key, plus a 4-byte line pointer, so about 20 bytes. Usable space per page is 8,192 minus the 24-byte page header and 16 bytes of B-tree special space, about 8,152 bytes. Internal pages therefore hold about 8,152 / 20 ≈ 407 entries. Leaves are built 90% full by default (the B-tree fill factor, which leaves room for later inserts), so about 366 entries per leaf.

  • Leaves: 100,000,000 / 366 ≈ 273,225 pages, about 2.1 GB.
  • Level above: 273,225 / 407 ≈ 672 pages, about 5.3 MB.
  • Level above that: 672 / 407 → 2 pages.
  • Root: 1 page.

Four levels. The lab computes the same thing and shows that a million rows need three levels and ten billion still need only four (27 million leaves, then about 67,000, then 165, then one root), which is the logarithm at work: each extra level multiplies capacity by about 400. The practical point is about memory. The upper three levels together are about 5 MB and will be in the buffer pool after the first few queries, so a lookup costs one leaf read (and one heap read) from disk at worst. That is the "find one row among billions in four reads" from sc4, with the numbers behind it.

Wider keys lower the fan-out. A 16-byte UUID makes entries about 28 bytes, fan-out about 290 and leaves about 3.1 GB for 100 million rows, still four levels. Key size affects index size and cache efficiency far more than height. A text key of 60 bytes, though, drops fan-out to about 120 and makes everything bigger, which is one reason to index short surrogate keys and keep long strings out of composite indexes when possible.

5. Inserts and page splits

To insert a key, descend to the leaf where it belongs and add the entry in sorted position. If the leaf has room, that is the whole write: one page modified. If the leaf is full, it splits: a new page is allocated, roughly half the entries move to it, the leaf chain is relinked, and a new separator key (the first key of the new page) is inserted into the parent. If the parent is also full, it splits too, and in the rare case the root splits, a new root is created and the tree grows one level taller. Growth always happens at the top, which is why every leaf stays at the same depth.

Key order now matters a great deal. With increasing keys (an identity column, a timestamp, a UUIDv7), every insert goes to the rightmost leaf. Only that one page and its parent are hot, they stay in memory, and PostgreSQL recognises the pattern and splits the rightmost page so the left half stays nearly full, so the index ends up densely packed. With random keys (UUIDv4, hashes), every insert goes to a different leaf. Once the index exceeds memory, each insert needs a random page read; splits occur everywhere, leaving pages around half to three-quarters full on average; and every leaf is dirtied repeatedly. The lab measures it in SQLite: inserting 300,000 random 16-byte keys took about 1.9 s versus about 0.5 s for sequential keys, roughly 3.5 times slower, even though both files ended up about the same size (SQLite redistributes entries among sibling pages on a split, so its fill penalty is smaller than PostgreSQL's 50/50 split). In PostgreSQL the gap widens further because of full-page writes, explained in section 9.

Deletes are handled more lazily than textbooks suggest. Real engines rarely merge underfull pages eagerly; PostgreSQL marks index entries dead and removes them during VACUUM or opportunistically when a page would otherwise split ("bottom-up deletion", added in version 14), and only fully empty pages are removed from the tree. An index that has had most of its rows deleted can therefore stay large until it is rebuilt with REINDEX.

6. The LSM tree: the write path

An LSM tree never updates data in place. Follow one write, put("user:42", "Ana"), through a RocksDB-style engine:

  1. WAL. The change is appended to a write-ahead log on disk, a sequential append, so it survives a crash.
  2. Memtable. The key and value are inserted into the memtable, an in-memory sorted structure (RocksDB uses a skip list). The write is now acknowledged. No data page was read or written.
  3. Flush. When the memtable reaches its size limit (RocksDB's write_buffer_size), it becomes immutable, a new memtable takes its place, and a background thread writes the immutable one to disk as an SSTable (sorted string table): an immutable file of key-value pairs in key order, divided into blocks, with a block index and a Bloom filter. This file lands in level 0. Its WAL segment can now be discarded.
  4. Compaction. Level-0 files overlap each other in key range, since each is a separate memtable dump. When their number reaches a trigger (level0_file_num_compaction_trigger), compaction merges them with the overlapping files of level 1, producing new non-overlapping files in level 1 and deleting the inputs. When level 1 exceeds its target size, some of its files are merged into level 2, and so on. Each level's target is about ten times the previous one (max_bytes_for_level_multiplier = 10).

Updates and deletes follow the same path. An update is just a newer version of the key; the old version stays in an older file until compaction merges the two and keeps only the newest. A delete writes a tombstone, a marker saying "this key is deleted", which hides older versions from reads and is itself dropped once compaction has carried it to the bottom level. This is what "log-structured" means: the storage is a sequence of immutable sorted runs, newest on top, rather than a set of pages edited in place.

7. The LSM tree: the read path and Bloom filters

A point read for user:42 must find the newest version. It checks the active memtable, then any immutable memtables, then each level-0 file from newest to oldest (they overlap, so any of them might hold the key), then, in each lower level, the single file whose key range covers user:42 (levels below 0 are non-overlapping, so a binary search over file boundaries picks one). The first version found, possibly a tombstone, is the answer.

Without help, a key that exists only in the bottom level costs a read in every level above it. The help is a Bloom filter per file: a bit array built from every key in the file by setting a few bit positions chosen by hash functions. To test a key, compute the same positions; if any bit is 0, the key is definitely not in the file and the file is skipped without reading its data. If all are 1, the key is probably there. RocksDB's documentation gives the trade-off: about 10 bits per key yields roughly a 1% false-positive rate, and 15.5 bits per key about 0.1%, with diminishing returns beyond that. With 10 bits per key, a lookup that passes through five levels before finding its key wastes on average 0.05 data-block reads. The cost is memory: a billion keys at 10 bits each is about 1.25 GB of filters, which must stay cached to be useful.

Range scans get no help from Bloom filters, since "keys between a and b" is not a single key to test. A range scan opens an iterator on the memtable and on every relevant file in every level and merges them, like the merge step of merge sort, skipping versions shadowed by newer ones and tombstones. That is why read amplification for range scans in an LSM tree is fundamentally higher than in a B+ tree, where the range is one contiguous walk along the leaves.

8. Compaction strategies

Compaction is where an LSM engine decides its amplification profile. Leveled compaction, RocksDB's default, keeps each level below level 0 as a single sorted run of non-overlapping files, each level about ten times larger than the one above. When a level is over its target, one file is picked and merged with the files it overlaps in the next level. Reads check at most one file per level; and since the levels above the last together hold only about 1/10 + 1/100 + … ≈ 11% of the last level's size, obsolete versions waste little space (space amplification about 1.1). The cost is writing: merging one file from level n into level n+1 rewrites the overlapping part of level n+1, which in the worst case is about ten times as much data.

Tiered (or size-tiered) compaction, the traditional default in Cassandra, lets several runs of similar size accumulate in a tier and then merges them all into one run in the next tier. Each byte is rewritten once per tier rather than up to ten times per level, so write amplification is much lower. But each tier holds several overlapping runs, so reads check more files, and a merge temporarily needs space for both the inputs and the output, so space amplification can approach 2x during large compactions. Engines offer hybrids (RocksDB's universal compaction, Cassandra's leveled and time-window strategies) that tune between the two, and time-window compaction for time-series data avoids merging old data at all, simply dropping whole files when their time range expires.

9. Write amplification, worked for both

LSM, leveled. Take 1 TB of data with a size ratio of 10: levels of roughly 1 GB, 10 GB, 100 GB and 1 TB below level 0. Follow one byte. It is written to the WAL (1) and flushed to level 0 (1). Compacting into level 1 rewrites it once (about 1). Then for each move down a level, merging its file into the next level rewrites up to about ten times as much overlapping data per byte moved: roughly 10 for each of the three moves to levels 2, 3 and 4. Upper estimate: 1 + 1 + 1 + 3 × 10 = 33. In practice, overlap is often less than the worst case, and RocksDB's own documentation describes the usual write amplification of leveled compaction as often larger than 10. At 100 MB/s of user writes, a write amplification of 25 means the disks absorb 2.5 GB/s of writes, which is why compaction bandwidth, not ingest bandwidth, is what LSM clusters are sized for.

B+ tree. The B+ tree's write amplification comes from page granularity. Updating one 100-byte row modifies one 8 KB heap page plus one leaf page per affected index. Each change writes a WAL record of roughly the row size. The dirty pages are eventually written back by a checkpoint or the background writer, 8 KB each. If successive updates hit different pages (random keys again), each 100-byte change costs at least one 8 KB page write per page it touches: write amplification of 80 or more per page. Then there are full-page writes: PostgreSQL, by default, writes the entire 8 KB image of a page to the WAL the first time the page is modified after each checkpoint, to protect against torn pages (half-written pages after a power failure, db8). With random keys and frequent checkpoints, nearly every change triggers a full-page image, which can multiply WAL volume several times. Sequential keys and longer checkpoint intervals reduce both effects because many changes land on the same few pages.

So the honest comparison is not "B-trees write once, LSM writes many times". Both amplify. B+ trees amplify by page size when updates are scattered; LSM trees amplify by level count times size ratio regardless of pattern, but write sequentially in large blocks, which SSDs and disks handle far better than scattered 8 KB writes, and compress well because files are immutable.

A useful framing from the research literature is the RUM conjecture (Athanassoulis and colleagues, 2016): an access method can minimise at most two of Read overhead, Update overhead and Memory or space overhead, and pays in the third. B+ trees choose reads and space; LSM trees choose updates and, with leveled compaction, space, paying on reads; tiered LSM chooses updates over both. Interviewers who ask "B-tree or LSM?" are looking for exactly this reasoning tied to a workload: what is the read/write ratio, are writes inserts of new keys or updates of old ones, are reads point lookups or ranges, and what is the hardware?

Why fan-out beats binary trees on disk

A balanced binary search tree over 100 million keys has height about log₂(10⁸) ≈ 27. In memory, 27 pointer hops are fine. On disk, if each node were a separate page, a lookup would cost up to 27 random reads, which on a spinning disk at around 10 ms each is a quarter of a second. The B-tree, invented by Bayer and McCreight in 1970-72, fixes this by making each node a whole page holding hundreds of keys, so the same 100 million keys need four levels. The idea generalises: whenever the cost of fetching a block is high relative to the cost of searching inside it, choose a structure with node size equal to the block size. It also explains why B+ tree performance depends on key size: fan-out is page size divided by entry size, and every halving of fan-out adds height and, more importantly, doubles the number of pages that must be cached to keep the upper levels in memory.

Index deduplication and suffix truncation

PostgreSQL 13 added B-tree deduplication: when many index entries share the same key (a status column, a foreign key with many children), the leaf stores the key once followed by a sorted list of TIDs, a "posting list", instead of repeating the key per row. Indexes on low-cardinality columns can shrink several-fold. PostgreSQL 12 added suffix truncation of separator keys in internal pages: a separator only needs enough of the key to distinguish its two children, so for composite or text keys internal entries become shorter and fan-out rises. Both are examples of a general principle: a storage engine's real-world efficiency comes from many such details layered on the textbook structure, and they are why benchmarks across major versions of the same database can differ substantially.

Write-optimised B-trees and the middle ground

The B+ tree and the LSM tree are two ends of a spectrum, and several designs sit between them. Bε-trees (used in the TokuDB and PerconaFT engines) give each internal node a buffer of pending changes; inserts go into the root's buffer, and when a buffer fills, its messages are flushed one level down in a batch. Writes are batched like an LSM tree, yet the data stays in one tree, so range scans remain efficient. InnoDB's change buffer applies the same idea narrowly: changes to secondary index pages that are not in the buffer pool are recorded and merged later, when the page is read for another reason, avoiding a random read per insert into non-unique secondary indexes. And WiredTiger (MongoDB's engine) uses a B-tree whose in-memory pages are not updated in place but carry lists of updates and are reconciled into new disk images when written, which gives it some log-structured properties. When an interviewer asks how to get LSM-like write performance without giving up B-tree reads, buffering at internal nodes is the answer they are looking for.

LSM read optimisations beyond Bloom filters

Production LSM engines add several layers to reduce read amplification. Block caches keep recently read data blocks, index blocks and filter blocks in memory, with filters and indexes often pinned. Partitioned filters and indexes split the metadata of very large files so only the needed partition is loaded. Prefix Bloom filters index a key prefix (for example a user id), so a range scan within one prefix can skip files that contain no keys with that prefix, recovering some of the range-scan cost. Ribbon filters, a newer alternative to Bloom filters in RocksDB, save roughly 30% of filter memory for the same false-positive rate at some CPU cost. And for workloads where most keys are read soon after being written, the memtable itself serves many reads. The net effect is that well-tuned LSM point-read latency is close to a B+ tree's when filters and indexes are cached; the remaining gap shows up in range scans and under compaction pressure.

Compaction debt and write stalls

An LSM engine accepts writes faster than it can permanently organise them, and the gap is compaction debt: data sitting in too many level-0 files or oversized levels. Debt raises read amplification (more L0 files to check) and space amplification (more obsolete versions). To prevent unbounded debt, engines throttle themselves. RocksDB slows writes when the number of level-0 files reaches a slowdown threshold and stops them entirely at a higher threshold, and similarly stalls when the number of unflushed memtables reaches max_write_buffer_number or estimated pending compaction bytes exceed limits. The symptom in production is a write latency graph that is flat for hours, then has sudden plateaus of high latency or errors. The fixes are more compaction threads and disk bandwidth, larger memtables to reduce L0 file count, or, if the workload is fundamentally beyond the hardware, a compaction strategy with lower write amplification.

Hardware changes the trade-off

O'Neil's 1996 analysis was driven by disk arms: random I/O was a hundred times more expensive than sequential, so turning random writes into sequential ones was worth almost any amount of extra copying. NVMe SSDs narrowed that gap enormously for reads, which made B+ trees' random leaf reads cheaper, but SSDs introduced their own concern: flash cells wear out after a limited number of program/erase cycles and must be erased in large blocks, so the device's internal garbage collection adds another layer of write amplification underneath the database's. Large sequential writes, which LSM trees produce, are kind to the SSD's internals; scattered small writes are not. Cloud block storage adds yet another dimension: you often pay per provisioned IOPS and throughput, so write amplification shows up directly on the bill. The right engine for a workload can therefore change with the storage it runs on.

The UUIDv4 primary key slowdown

A very common production story: a service launches with UUIDv4 primary keys because they can be generated in the application and reveal nothing. Insert latency is fine for months. Then the primary key index outgrows the buffer pool and insert throughput falls off a cliff, with disk read I/O climbing in step with the insert rate (each insert reads a random leaf) and WAL volume far higher than the data volume (full-page images on first touch after each checkpoint). The symptoms visible in monitoring are rising buffer-pool miss rates on the index, rising wal_bytes per transaction in pg_stat_wal (or redo log volume in InnoDB), and checkpoints writing many more pages. The fixes, in rising order of effort: switch new ids to a time-ordered format (UUIDv7, or a bigint identity), which keeps existing ids valid; increase memory so the index fits; lengthen the checkpoint interval (checkpoint_timeout, max_wal_size) to reduce full-page images, at the cost of longer crash recovery.

Bloat and fill factor

B+ tree indexes and heaps accumulate free space: half-empty pages after random splits, space from deleted or updated row versions not yet reused, pages emptied by mass deletes. PostgreSQL calls the excess bloat. Moderate bloat is harmless, but a table or index that is several times larger than its live data wastes cache and makes scans slower. Monitoring tools such as the pgstattuple extension report live versus dead space. Remedies include tuning autovacuum so dead space is reused promptly (db10), rebuilding indexes with REINDEX CONCURRENTLY, and for tables, tools that rewrite them online. Conversely, for tables with many in-place updates, PostgreSQL lets you lower the heap fillfactor (for example to 80) so pages keep free room; an updated row version can then stay on the same page, which enables heap-only tuple (HOT) updates that skip index maintenance entirely, a large write saving that db10 explains.

Running an LSM store in production

The metrics that matter for LSM engines are different from those for B+ tree databases. Watch the number of level-0 files and pending compaction bytes (compaction debt), write stall counts and durations, compaction read and write throughput relative to user write throughput (that ratio is your live write amplification), Bloom filter useful rate, block cache hit rate, and disk space headroom. Disk headroom deserves special emphasis: compaction needs temporary space for its outputs before deleting its inputs, and size-tiered compaction of the largest tier can need as much free space as the data itself; Cassandra operators have long been advised to keep substantial free disk for this reason. Tombstones are the other classic trap: a workload that deletes heavily (a queue implemented on Cassandra, for example) accumulates tombstones that reads must skip until compaction removes them, and reads that scan many tombstones can become very slow or fail, which is why LSM stores are a poor fit for queue-like delete-heavy patterns.

Choosing storage for AI workloads

AI systems produce a few characteristic storage patterns, and the amplification lens maps each to an engine. LLM call logs, traces and metrics are append-only, time-ordered and queried by time range: a B+ tree with time-ordered keys and time partitioning handles moderate rates, and LSM-based or columnar stores handle very high rates. Feature stores serving online lookups by entity key are read-heavy point lookups with periodic bulk refreshes: LSM-based key-value stores are common because the bulk refresh is a large write burst, while reads are point lookups that Bloom filters serve well. Conversation state for chat applications is read and updated per session: a B+ tree OLTP database is the natural fit. Embedding storage for vector search uses specialised index structures (db15), but the metadata alongside it still lives in one of these engines. In each case, the question is the same as in O'Neil's paper: what is written, how fast, in what key order, and how is it read?

def load(keys, label):
    path = os.path.join(tempfile.mkdtemp(), "t.db")
    db = sqlite3.connect(path)
    db.execute("PRAGMA page_size = 4096")
    db.execute("CREATE TABLE t (k BLOB PRIMARY KEY, v TEXT) WITHOUT ROWID")
    t0 = time.perf_counter()
    with db:
        db.executemany("INSERT INTO t VALUES (?, 'x')", ((k,) for k in keys))
    secs = time.perf_counter() - t0
    pages = db.execute("PRAGMA page_count").fetchone()[0]
    db.close()
    print(f"{label:<11} {pages:>6} pages  {pages * 4096 / 2**20:6.1f} MiB  {secs:5.2f} s")

N = 300_000
seq = [i.to_bytes(16, "big") for i in range(N)]       # like a sequence or UUIDv7
rnd = [os.urandom(16) for _ in range(N)]              # like UUIDv4
load(seq, "sequential")
load(rnd, "random")

What to look for.

  1. Part 1 prints leaf capacity 366, fan-out 407, and 3, 4 and 4 levels for a million, 100 million and ten billion rows: each extra level multiplies capacity by about 400.
  2. Part 2 inserts 300,000 16-byte keys in sequential and random order. On the test machine the random load took about 1.9 s versus 0.5 s for sequential, while page counts were similar (about 1,900 pages of 4 KB). The time gap comes from random inserts touching a different leaf each time, thrashing SQLite's small default page cache; sequential inserts keep hitting the same rightmost pages.

Try next. Change entry=20 to 28 (UUID keys) and 68 (60-byte text keys) and watch fan-out fall to about 290 and 120. In Part 2, add db.execute("PRAGMA cache_size = -64000") (64 MB) before inserting and rerun: when the whole index fits in cache, the random-key penalty shrinks sharply, which is exactly why UUIDv4 keys seem fine until a table outgrows memory. Finally, set N = 1_000_000 and compare again.

Estimate and choose: a telemetry store

A fleet of devices sends 200,000 readings per second, each about 100 bytes, keyed by (device_id, timestamp). Data is kept 30 days. Queries are "last hour for one device" (frequent) and "daily aggregates for all devices" (a few per day). Estimate the data volume, compare a PostgreSQL B+ tree design with a leveled LSM design for the write path, and recommend one.

Answer

Volume. 200,000 × 100 B = 20 MB/s of user data, about 1.7 TB per day, about 52 TB for 30 days before compression or overheads.

B+ tree. The key (device_id, timestamp) is not globally increasing: each device's readings are increasing, but devices interleave, so inserts land on as many different leaf pages as there are active devices. With, say, 1 million devices, the index's insert working set is a million leaf pages (8 GB), which may fit in memory, but every page is dirtied constantly and WAL carries full-page images after each checkpoint. Partitioning by day keeps each day's index small. Per-row overhead (about 24-byte tuple header plus line pointer) adds over 25% to 100-byte rows. Feasible on large hardware, but this is at the upper end of what one PostgreSQL primary handles comfortably.

Leveled LSM. Writes are WAL appends and memtable inserts. At an assumed write amplification of 15, disks absorb about 300 MB/s of compaction writes, which a few NVMe drives sustain. Immutable files compress well; time-series data often compresses 5-10x. "Last hour for one device" is a prefix range scan on recent data that mostly sits in the memtable and upper levels.

Recommendation. An LSM-based or purpose-built time-series store (with time-window compaction so expired days are dropped as whole files rather than deleted row by row), plus a pre-aggregated daily rollup table for the analytics queries, ideally in a columnar store (db12). Mention the operational cost: provision disk bandwidth for compaction, alert on L0 file count and pending compaction bytes, and keep free space for compaction outputs.
