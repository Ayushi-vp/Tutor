In 2014, an engineer at the analytics company Heap wrote up a problem every product team eventually has. Their events table held clicks, page views and form submissions for every user, stored with a JSON payload. An internal dashboard needed one number often: how many people signed up last week, where a signup is a form submission on the /signup/ page. In a synthetic test with 10 million events, of which only 3,000 were signups, the query took 45 seconds with no index.

The obvious fix was to index the three things the query filtered on: the event type, the page path and the time. With those three single-column indexes, the query fell to about 200 ms on a cold cache and 20 ms warm, a great improvement. But the three indexes took 1,026 MB of disk for a 6,660 MB table, every insert of any event now had to update all three, and the indexes could only serve this exact kind of filter. Then they tried a different index: on time only, but only for rows that are signups. That partial index took 96 kB, about ten thousand times smaller. The query ran in 2 ms warm. And because only 0.03% of events are signups, inserts of all the other events never touched it.

The story captures the whole subject. An index is not a switch you flip on a column; it is a second data structure with its own shape, size and write cost, and the art is to match its shape to the queries that matter. Which columns, in which order, covering which other columns, over which rows, using which structure? Each of those choices can change a query's cost by orders of magnitude, and each one also changes the cost of every write.

db5 showed how a B+ tree is built. This lesson is about using that structure, and its alternatives, well. You will learn how clustered and heap-organised tables differ and what that means for every secondary index; how to order the columns of a composite index from the query's predicates; when an index can answer a query on its own; partial and expression indexes; the specialised index types (hash, GIN, GiST, BRIN) for data a B-tree cannot serve; how bitmap scans combine indexes; and the costs that make "add another index" a decision rather than a reflex. The lab measures several of these effects with SQLite's query planner.

An index is a sorted copy of part of the table

The simplest accurate picture of a B-tree index is a phone book. The table is a pile of records in no useful order. The index is a separate, sorted list of one or more columns from each record, each entry ending with the record's address. To find a person, you search the sorted list, which is fast because it is sorted, and then go to the address.

Everything in this lesson follows from that picture. The order of a phone book is "surname, then first name", so it is useless for finding everyone called Ana: that is the column-order rule for composite indexes. If the phone book also printed each person's phone number next to their name, you would never need to visit the address for a phone-number question: that is a covering index. A phone book of only the doctors in town would be much thinner and still answer every question about doctors: a partial index. A book sorted by lower-cased surname finds "SMITH" and "smith" alike: an expression index. And a phone book is no help for "people whose address contains a garden": that question needs a different kind of index altogether, such as the inverted indexes used for text search.

The analogy breaks on cost. A phone book is printed once; a database index is updated on every insert, on deletes, and on any update of the indexed columns, and it competes with the table for memory. So each index is a trade: faster reads for some queries, slower writes for all of them.

Two ways to store the table itself

Before choosing indexes, know where the rows live, because it changes what an index entry points to. PostgreSQL stores rows in a heap in no particular order; every index, including the primary key, is a separate B+ tree whose entries point to a row's physical address (its TID). MySQL's InnoDB stores the rows inside the primary key's B+ tree, sorted by primary key: the table is the primary key index, which is called a clustered index. Its other indexes point to rows by primary key value, so a lookup through them descends two trees.

How a query uses an index

An index helps a query in three distinct ways, and it is worth naming them because a single index might do one, two or all three. It can find the matching rows without scanning the table, by turning a WHERE condition into a range of sorted entries. It can order them, delivering rows already sorted for ORDER BY, which also lets LIMIT 10 stop after ten rows instead of sorting everything. And it can cover the query, holding every column needed so the table is not read at all. A good index for an important query does all three. Whether the database actually uses an index is decided by its query planner (db7), which estimates the cost of each available plan from statistics about the data and picks the cheapest; an index that would read most of the table is often rightly ignored.

1. Clustered versus heap-organised tables

In a heap-organised table (PostgreSQL, also Oracle's default and SQL Server tables without a clustered index), rows live in heap pages, and an index entry is (key, TID). A lookup through any index is: descend the index B+ tree (about four page reads, the upper levels cached), then read one heap page. All indexes are equal citizens; the primary key is just a unique index.

In a clustered table (InnoDB always; SQL Server when you declare a clustered index), the primary key's B+ tree holds full rows in its leaves, in key order. A lookup by primary key is one descent that ends at the row itself, with no separate heap read. A range scan by primary key reads rows that are physically adjacent, which is excellent for "all orders of customer 7" if the primary key starts with customer_id. Secondary indexes store (secondary key, primary key value), and a lookup through them descends the secondary tree, takes the primary key, then descends the primary tree: two descents.

The design consequences are concrete. In InnoDB, the primary key should be short and increasing: short because it is copied into every secondary index entry (a 36-character string UUID adds 36 bytes to every entry of every index), and increasing because the table itself is a B+ tree and random primary keys scatter row inserts across all its leaves, the db5 problem applied to the whole table. A good clustered key can also be a gift: an InnoDB table of messages with primary key (conversation_id, message_id) stores each conversation's messages physically together, so reading a conversation is one short range scan. In PostgreSQL, where the heap is unordered, there is no such locality by default; the one-off CLUSTER command rewrites a table in an index's order but does not maintain it as rows change.

2. Composite indexes: how column order decides what is usable

A composite index on (a, b, c) stores entries sorted by a, then by b among equal a, then by c among equal (a, b). Picture the entries of an index on (user_id, ts):

(41, 900) (41, 950) (42, 100) (42, 180) (42, 250) (42, 310) (43, 120) (43, 400) ...

Now take the query WHERE user_id = 42 AND ts > 200. The matching entries, (42, 250) and (42, 310), are contiguous: the database descends to the first entry with user_id 42 and ts > 200 and reads forward until user_id changes. That is an index range that contains exactly the answer. With the columns reversed, an index on (ts, user_id) sorts by ts first:

(100, 42) (120, 43) (180, 42) (250, 42) (310, 42) (400, 43) (900, 41) (950, 41) ...

Now "ts > 200" is a contiguous range, but user 42's entries are scattered through it: the database must read every entry with ts > 200, for every user, and check user_id on each. If the table has 50,000 users, that reads roughly 50,000 times more entries than needed. The lab measures this on 400,000 rows: about 8 ms with (ts, user_id) versus about 0.003 ms with (user_id, ts), and SQLite's plan shows the difference in words: (ts>?) versus (user_id=? AND ts>?).

The general rule: an index can be used to narrow the search for the longest leading run of columns tested with equality, followed by at most one column tested with a range (<, >, BETWEEN, a LIKE prefix). Columns after the first range column can still be checked from the index entries, which avoids heap reads, but they do not narrow the range. Sorting adds a third consideration: an index delivers rows in its order, so ORDER BY ts needs no sort if the equality columns come first and ts comes next. This gives a practical ordering heuristic, sometimes called ESR: Equality columns first, then the Sort column, then Range columns. For WHERE tenant_id = ? AND status = ? AND created_at > ? ORDER BY created_at, the index is (tenant_id, status, created_at), and here the sort and range column happen to be the same.

Among equality columns, order matters less for that query but matters for other queries: put first the column that other queries also filter on alone, because an index on (a, b) also serves queries on a alone (the leftmost-prefix rule from sc4), while queries on b alone cannot use it efficiently. A popular folk rule says "most selective column first"; for pure equality lookups that do not need prefix reuse it hardly matters, since the combined range is the same either way. Before PostgreSQL 18, an index whose first column was not constrained was nearly useless for a query; version 18 added skip scan, which handles a missing leading column by jumping through its distinct values, one short range each. It helps when the leading column has few distinct values (status, region) and is no substitute for the right column order.

3. Covering indexes and index-only scans

A query is covered when every column it references is in the index. Then the database can answer from index entries alone. The lab's first plan shows SQLite saying USING COVERING INDEX ix_user_ts because the query selects only ts and filters on user_id and ts. Add a column to the SELECT list that is not in the index and every matching row needs a table lookup.

PostgreSQL 11 added INCLUDE for exactly this: CREATE INDEX ON orders (customer_id, created_at) INCLUDE (total_cents, status) stores total and status in the leaf entries as payload. They do not take part in the sort order or in uniqueness, so they can be added to a unique index without changing what "unique" means, and they do not bloat internal pages. Covering indexes are especially valuable for the hottest read paths, such as an API that lists a user's recent orders with a few fields.

In PostgreSQL there is a twist. An index entry does not record whether its row version is visible to your transaction; that information lives in the heap tuple (db9 explains MVCC). So an index-only scan consults the visibility map, a bitmap with one bit per heap page meaning "every row on this page is visible to everyone", maintained by VACUUM. For entries on all-visible pages, the heap is skipped. For others, the heap page is fetched to check. EXPLAIN ANALYZE reports this as Heap Fetches: N. On a table where recent writes have not yet been vacuumed, an index-only scan may fetch nearly every heap page and be no faster than a normal index scan, which is one of several reasons autovacuum tuning matters (db10). InnoDB has no such issue for covering secondary indexes in most cases, because visibility is checked through per-page transaction information and undo logs rather than a separate map.

4. Partial indexes

A partial index indexes only the rows satisfying a predicate: CREATE INDEX ON event (ts) WHERE kind = 'signup'. Its size and write cost are proportional to the matching rows, not the table. Heap's case gives the scale: 96 kB instead of over a gigabyte, because 0.03% of rows qualify, and inserts of non-matching rows never touch it. The lab reproduces the shape on 400,000 events with 1% signups: counting signups in a ts range took about 12 ms through a full ts index (reading every event in the range, then checking kind) and about 0.04 ms through the partial index.

For the planner to use a partial index, it must be able to prove that the query's WHERE clause implies the index's predicate. WHERE kind = 'signup' AND ts > ? clearly does. But a query using a bind parameter, WHERE kind = $1, cannot be proven to match at planning time if the plan is generic, so prepared statements sometimes miss partial indexes. Good uses are queues (WHERE status = 'pending', which stays tiny even when the table holds millions of finished jobs), soft deletes (WHERE deleted_at IS NULL), "hot" subsets (active subscriptions), and the unique-among-live-rows constraint from db1, CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL.

5. Expression indexes

An index on a column cannot serve a filter on a function of the column. WHERE lower(email) = 'ana@example.com' must compute lower() for every row, because the index is sorted by email, not by lower(email); the lab's plan shows SCAN event for a lower(path) filter. An expression index stores the computed value: CREATE INDEX ON users (lower(email)), after which the same filter becomes an index search (USING COVERING INDEX ix_lower_path (<expr>=?) in the lab). The query must use the same expression the index was built on.

Common uses: case-insensitive lookups, date truncation ((created_at::date)), and fields inside JSON (((metadata->>'model'))), which turns one important JSON key into an ordinary B-tree-indexed value with ranges and sorting. The same idea explains a frequent mistake: WHERE created_at::date = '2026-10-03' or WHERE EXTRACT(year FROM created_at) = 2026 cannot use an index on created_at. Rewrite as a range on the raw column, WHERE created_at >= '2026-10-03' AND created_at < '2026-10-04', which is "sargable" (usable by a search argument, in the old jargon). Type mismatches cause the same problem invisibly: comparing a text column to an integer parameter may wrap the column in a cast.

6. Hash indexes

A hash index stores a hash code of each key in buckets, with pointers to rows. An equality lookup hashes the search key and reads one bucket, in principle O(1) regardless of size. In PostgreSQL, hash indexes have been crash-safe (WAL-logged) only since version 10, cannot be unique, cannot be multicolumn, and support only =. Their real niche is long keys used only for equality, such as a URL or a long token: a B-tree stores the whole key in every entry and its internal pages, while a hash index stores a 4-byte hash code. For integer or UUID keys, a B-tree's three or four cached page reads are as good in practice and the B-tree also handles ranges, sorting and uniqueness, so B-tree remains the default. Many key-value stores and in-memory engines use hashing as their primary structure because they only ever need equality.

7. GIN: inverted indexes for values with many elements

Some columns hold many searchable elements per row: an array of tags, a jsonb document with many keys, a text document with many words. "Rows whose tags contain 'gpu'" is not a range in any sort order of whole values. The answer is an inverted index, which PostgreSQL implements as GIN (generalized inverted index): for each distinct element, a sorted list of the rows containing it, exactly like the index at the back of a book.

GIN serves array operators (@> contains, && overlaps), jsonb containment and key-existence operators, full-text search on tsvector columns, and trigram similarity for fuzzy text matching via the pg_trgm extension (which also makes LIKE '%term%' with a leading wildcard indexable). The cost is on writes: inserting a row with 50 words adds 50 entries scattered across the index. PostgreSQL mitigates this with the fastupdate option, on by default, which appends new entries to an unsorted pending list and moves them into the main structure in bulk during vacuum, or when the list exceeds gin_pending_list_limit (4 MB by default). The documentation spells out the trade: updates become much faster, but searches must also scan the pending list, so a large pending list slows queries, and the occasional flush can make one unlucky insert slow.

8. GiST and SP-GiST: overlap, containment and nearness

B-trees need a total order. Many data types do not have a useful one: two-dimensional points, polygons, time ranges, IP address ranges. Questions about them are "overlaps", "contains", "is within 5 km of" and "nearest to". GiST (generalized search tree) is a balanced tree like a B-tree, but each internal entry stores a bounding predicate covering everything beneath it, such as a bounding rectangle for geometry (making it an R-tree) or a covering range for ranges. A search descends into every child whose bounding predicate could satisfy the query, so lookups may follow several paths, but typically few. GiST powers PostGIS spatial queries, range-type overlap queries, nearest-neighbour searches with ORDER BY location <-> point LIMIT 10, and exclusion constraints: EXCLUDE USING gist (room_id WITH =, during WITH &&) forbids two bookings of the same room with overlapping time ranges, a rule no unique index can express. SP-GiST (space-partitioned GiST) supports non-balanced partitioning structures such as quadtrees, k-d trees and radix tries, which suit data with natural clustering like IP addresses or phone-number prefixes.

9. BRIN: summaries for huge, naturally ordered tables

A BRIN (block range index) does not index rows at all. It divides the table into ranges of consecutive pages (128 pages, 1 MB, by default) and stores a summary per range, typically the minimum and maximum of the column. A query for ts BETWEEN a AND b reads the summaries, skips every range whose min-max cannot overlap, and scans only the remaining ranges. For a 1 TB append-only log table, that is about a million ranges, so a BRIN index on ts is a few megabytes, versus tens of gigabytes for a B-tree, and costs almost nothing to maintain.

BRIN works only when the column's values correlate with physical order, which happens naturally for timestamps and sequential ids in append-only tables: each 1 MB range covers a narrow time window. If rows are updated (moving new versions elsewhere), loaded out of order, or the column is random, every range spans almost the full min-max and nothing is skipped. BRIN is approximate by nature: it returns candidate pages that are then scanned and rechecked, so it suits range scans over large fractions, not single-row lookups.

10. Bitmap scans: combining indexes

PostgreSQL has three ways to use B-tree indexes. A plain index scan walks matching entries in index order and fetches each row from the heap immediately, which means random heap access, fine for a handful of rows. An index-only scan avoids the heap where it can. A bitmap index scan walks the matching entries and only records their TIDs in an in-memory bitmap, one bit per row (or per page if memory runs short), then a bitmap heap scan reads the marked heap pages in physical order, each page once.

Two advantages follow. Reading heap pages in order, each once, is much cheaper than random fetches when thousands of rows match, so bitmap scans fill the gap between "few rows: index scan" and "most rows: sequential scan". And bitmaps can be combined: for WHERE kind = 'signup' OR path = '/pricing', PostgreSQL builds a bitmap from each index and ORs them (BitmapOr); for AND it intersects them (BitmapAnd). That is what Heap's three single-column indexes were doing. The costs: results come out in physical order, not index order, so an ORDER BY needs a sort; and if the bitmap exceeds work_mem, it becomes lossy, remembering only which pages contain matches, so every row on those pages must be rechecked (Recheck Cond and lossy blocks in EXPLAIN ANALYZE).

Do not confuse this with bitmap indexes, a stored index type in Oracle and many data warehouses, which keep one bitmap per distinct value of a low-cardinality column (one for each status, one for each region). They make AND and OR of many low-cardinality filters extremely fast on read-mostly data, but updates are expensive and lock-heavy, which is why OLTP databases rarely use them and columnar engines (db12) use similar compressed bitmaps internally.

11. What every index costs

Every index adds work to every write. An insert must add an entry to every index on the table; a delete leaves dead entries to clean up; an update of an indexed column inserts a new entry in that index. In PostgreSQL there is an extra effect: an update that changes no indexed column and finds room on the same heap page can be a HOT (heap-only tuple) update, which adds no index entries at all, but updating any indexed column, in any index, rules out HOT for that update, so all indexes get new entries. Indexing a frequently changing column like last_seen_at can therefore multiply the write cost of a table.

The other costs are space (indexes often total more than the table), cache (index pages compete with table pages for the buffer pool), WAL and replication volume (every index change is logged and shipped to replicas), and planning time (more indexes, more plans to consider). A useful rule of thumb is that each additional index on a write-heavy table costs a measurable fraction of insert throughput, so indexes should be justified by queries that run, not by columns that exist.

12. A worked design: the LLM call log

Pull it together on the table from earlier lessons: llm_call(call_id, tenant_id, user_id, model, prompt_version, status, latency_ms, cost_micros, created_at, metadata jsonb), 30 million rows a month. The query patterns, from the product: (1) a user's recent calls, newest first, 20 per page; (2) a tenant's cost by model over a date range; (3) failed calls in the last hour for alerting; (4) occasional searches by a metadata key such as an experiment flag.

Design: call_id as a bigint identity primary key (increasing, so inserts are cheap). For (1), (user_id, created_at DESC), equality then sort, so the API reads 20 entries; add INCLUDE (model, status, latency_ms) if the list view shows only those, making it index-only. For (2), (tenant_id, created_at) INCLUDE (model, cost_micros) serves the range and covers the aggregation. For (3), a partial index (created_at) WHERE status = 'error', tiny because errors are rare. For (4), resist a GIN index on the whole metadata column unless searches are frequent and varied; if one key matters, an expression index on (metadata->>'experiment'). And because the table is append-only and time-ordered, partition by month so old months can be dropped, and consider a BRIN index on created_at for analysts' wide time-range scans. Five indexes in all, each tied to a named query; none on latency_ms or cost_micros alone, which nothing filters on.

How the planner decides whether an index is worth it

The planner estimates the cost of a plan from statistics: for each column, the number of distinct values, the most common values and their frequencies, a histogram of the rest, the fraction of NULLs, and the correlation between the column's order and the physical row order. For WHERE status = 'active' it looks up the frequency of 'active'; if that is 0.8, it estimates 80% of rows. Then it compares: a sequential scan reads every page sequentially (cheap per page); an index scan reads index pages plus one heap page per matching row, each potentially random (PostgreSQL's default random_page_cost of 4 versus seq_page_cost of 1 encodes the old disk assumption that random reads cost four times sequential ones, and many teams on SSDs lower it to around 1.1). With high correlation, consecutive matching rows sit on the same page, so an index range scan reads few heap pages; with low correlation, it may read a different page per row. The crossover between index and sequential scan is often in the range of a few percent to a few tens of percent of rows, and it moves with correlation, row width and cache state. db7 walks through reading these estimates in EXPLAIN.

Multicolumn statistics and correlated predicates

By default the planner assumes conditions are independent and multiplies their selectivities. For WHERE city = 'Mumbai' AND state = 'Maharashtra' it estimates the product of the two fractions, badly underestimating, because every Mumbai row is in Maharashtra. Underestimates lead to nested-loop plans that are disastrous at the real row count. PostgreSQL's CREATE STATISTICS (version 10+) lets you declare extended statistics on column groups: functional dependencies, combined distinct counts and multi-column most-common values. They do not create an index, but they fix the estimates that decide whether an index is used. It is a frequent fix for "the query uses the wrong index" incidents.

Uniqueness is enforced by an index

Every UNIQUE and PRIMARY KEY constraint is implemented by a unique B-tree index. On insert, the database searches the index for the key, and if a live entry exists, rejects the insert; concurrent inserts of the same key are serialised on the index page so exactly one wins. This is why unique constraints are the correct tool for race-free deduplication (db1), why they cost an index's worth of space and write time, and why a "unique" check in application code is never equivalent. It also explains a subtle MVCC interaction: in PostgreSQL, a unique index may contain several entries for the same key (dead versions from updates), and the uniqueness check must consult the heap to see which are live, which is one reason heavily updated unique keys produce more work than expected.

Index-organised alternatives and secondary-index maintenance

The heap versus clustered choice has a further consequence when rows move. In PostgreSQL, an updated row usually gets a new TID, so (unless the update is HOT) every index needs a new entry pointing to the new version, which is the root of the write amplification Uber described when it moved from PostgreSQL to MySQL (db10). In InnoDB, secondary indexes point by primary key, so a row whose primary key does not change can move inside the clustered tree without touching secondary indexes; only indexes whose columns changed need updating. The price is the double lookup on reads and the bloat of wide primary keys. Neither design dominates; they place the cost on different operations, and knowing which is why the same schema can behave differently on the two engines.

Covering versus duplicating data

Covering indexes are a form of controlled denormalisation (db2): they store copies of columns in a second structure that the database keeps consistent automatically. That makes them safe, unlike application-level copies, but not free: every update of an included column updates the index, and wide INCLUDE lists can make an index nearly as large as the table. The best candidates are narrow, rarely updated columns read by very frequent queries. A covering index that includes a constantly updated column also kills HOT updates for that column, so in PostgreSQL the trade-off includes the update path, not just space.

Indexes for vector and text search

Two modern query types need structures beyond those above. Full-text relevance search ranks documents by a scoring function such as BM25 over inverted indexes; PostgreSQL's built-in full-text search provides GIN-backed matching with simpler ranking, while dedicated engines (Elasticsearch, OpenSearch, or BM25 extensions for PostgreSQL) provide the scoring at scale. Vector similarity search needs approximate nearest-neighbour indexes such as HNSW graphs and IVF clusters (lm10), which pgvector implements as PostgreSQL index access methods alongside B-tree and GIN. They share the same planner, so an ORDER BY embedding <=> $1 LIMIT 10 can use an HNSW index the way ORDER BY created_at LIMIT 10 uses a B-tree; how filters interact with those approximate indexes is the subject of db15.

Heap's partial index, generalised

Heap's numbers are worth remembering because the pattern recurs in nearly every product database: a large table where a dashboard, a queue or an alert repeatedly targets a tiny, well-defined subset. Three single-column indexes took 1,026 MB, added write cost to every event and still needed a bitmap combination at query time; a partial index on the subset took 96 kB, was essentially free to maintain, and answered in 2 ms. Look for this pattern when you see frequent queries with a fixed equality predicate on a low-frequency value (status = 'pending', kind = 'signup', is_flagged = true), and check the rows-matched-to-table-size ratio before choosing.

Finding missing indexes

The symptoms of a missing index are a query whose plan shows a sequential scan over a large table with a selective filter, high seq_tup_read on that table in pg_stat_user_tables, and the query near the top of pg_stat_statements by total time. The workflow is: identify the top queries by total time; read their plans; for each, design the index from its predicates and ORDER BY using the ESR rule; test with EXPLAIN ANALYZE on a production-sized copy; and build in production with CREATE INDEX CONCURRENTLY, which avoids blocking writes at the cost of taking longer and possibly leaving an invalid index if it fails (db14 covers this in migrations). The hypothetical-index extension hypopg lets you ask the planner whether it would use an index before building it.

Finding useless indexes

The reverse problem is just as common in mature systems: indexes added for a query that no longer exists, or duplicated by a later composite index. pg_stat_user_indexes.idx_scan counts how often each index was used since statistics were last reset; an index with zero scans over a month, on every replica, that does not back a constraint, is a candidate for removal. Check replicas because read queries routed to replicas are counted only there. Remove with DROP INDEX CONCURRENTLY, keeping the definition in version control so it can be restored quickly. MySQL 8 offers invisible indexes, which the optimiser ignores but which are still maintained, so you can test the impact of dropping one and revert instantly.

Index bloat and rebuilds

Indexes on heavily updated or deleted data accumulate dead entries and half-empty pages (db5). An index several times larger than a fresh build wastes cache and makes scans slower. PostgreSQL 12+ supports REINDEX INDEX CONCURRENTLY, which builds a replacement without blocking writes and swaps it in; it needs extra disk for the duration. B-tree deduplication (version 13) and bottom-up deletion (version 14) have reduced bloat substantially for common workloads, so check the index size after an upgrade before scheduling routine rebuilds.

When an index makes things worse

Adding an index can occasionally slow a query that was fine, because the planner now picks it based on a bad estimate. A classic case is ORDER BY created_at LIMIT 10 with a filter on a rare value: the planner walks the created_at index in order, expecting to find ten matches quickly, but the rare rows are all old, so it walks almost the whole index. The fix is a composite index that matches both filter and order, or better statistics. Production changes to indexes should therefore be validated with EXPLAIN ANALYZE on the important queries, not only the one the index was added for.

Goal: watch SQLite's planner use, misuse and ignore indexes on a 400,000-row events table: composite column order, a partial index for a rare event kind, and an expression index. Python 3.12 standard library. Save as db6.py.

import random, sqlite3, time

db = sqlite3.connect(":memory:")
db.execute("""CREATE TABLE event (id INTEGER PRIMARY KEY, user_id INT, kind TEXT,
              ts INT, path TEXT, payload TEXT)""")
random.seed(1)
kinds = ["view"] * 97 + ["click"] * 2 + ["signup"]
rows = [(i, random.randrange(50_000), random.choice(kinds), i, f"/p/{i % 500}", "x" * 50)
        for i in range(400_000)]
db.executemany("INSERT INTO event VALUES (?,?,?,?,?,?)", rows)

def plan(sql):
    return " | ".join(r[3] for r in db.execute("EXPLAIN QUERY PLAN " + sql))

def timed(sql, n=20):
    t0 = time.perf_counter()
    for _ in range(n):
        db.execute(sql).fetchall()
    return (time.perf_counter() - t0) / n * 1000

Q1 = "SELECT ts FROM event WHERE user_id = 42 AND ts > 200000 ORDER BY ts"
Q2 = "SELECT count(*) FROM event WHERE kind = 'signup' AND ts BETWEEN 100000 AND 200000"
Q3 = "SELECT id FROM event WHERE lower(path) = '/p/7'"

print("no index     :", plan(Q1), f"{timed(Q1):.3f} ms")
db.execute("CREATE INDEX ix_ts_user ON event (ts, user_id)")          # wrong order
print("(ts,user_id) :", plan(Q1), f"{timed(Q1):.3f} ms")
db.execute("CREATE INDEX ix_user_ts ON event (user_id, ts)")          # equality first
print("(user_id,ts) :", plan(Q1), f"{timed(Q1):.3f} ms")

print("signups, no partial :", plan(Q2), f"{timed(Q2):.3f} ms")
db.execute("CREATE INDEX ix_signup_ts ON event (ts) WHERE kind = 'signup'")
print("signups, partial    :", plan(Q2), f"{timed(Q2):.3f} ms")

print("lower(path), plain idx? :", plan(Q3))
db.execute("CREATE INDEX ix_lower_path ON event (lower(path))")

What to look for (timings from the test machine; yours will differ, the ratios should not).

  1. No index: SCAN event | USE TEMP B-TREE FOR ORDER BY, a full scan plus a sort, about 20 ms.
  2. (ts, user_id): the plan says (ts>?): only the range narrows the search, so it reads every user's entries after ts 200,000 and checks user_id, about 8 ms.
  3. (user_id, ts): (user_id=? AND ts>?), a few microseconds, and COVERING because the query needs only ts.
  4. Signups through the full ts index about 12 ms; through the partial index about 0.04 ms, a few hundred times faster, and the partial index holds only 1% of rows.
  5. lower(path) = … scans until the expression index exists, then searches it.

Design: indexes for a ticketing system

Table ticket(id bigint PK, org_id, assignee_id, status, priority, created_at, updated_at, subject, body text, tags text[]), 80 million rows, 5% open. Queries: (A) an agent's open tickets, highest priority first, then oldest; (B) an org's tickets created in a date range, newest first, paginated; (C) count of open tickets per org for a dashboard every minute; (D) tickets with a given tag in an org; (E) full-text search over subject and body for an org. Writes: 300 inserts and 2,000 updates per second, mostly status, assignee and updated_at changes. Propose indexes and justify each, including what you would not index.

Answer

(A) Partial composite: (assignee_id, priority DESC, created_at) WHERE status = 'open'. Equality on assignee, then the two sort columns in query order, and the partial predicate shrinks it to 5% of rows. The query can stop after one page of results.

(B) (org_id, created_at DESC): equality then the range-and-sort column. Use keyset pagination on (created_at, id) rather than OFFSET (db13), so add id as a tie-breaker: (org_id, created_at DESC, id DESC).

(C) (org_id) WHERE status = 'open', partial, so the count is an index-only scan over 4 million entries grouped by org; better, maintain a per-org open count updated in the same transaction as status changes, or a materialized summary refreshed every minute, since this runs constantly.

(D) GIN on tags: USING gin (tags), queried with tags @> ARRAY['billing'] AND org_id = ?. If tag queries are always within one org and orgs are numerous, the btree_gin extension allows (org_id, tags) in one GIN index.

(E) A generated tsvector column over subject and body with a GIN index, or a separate search engine if relevance ranking and scale matter; full-text indexes on 80 million long bodies are large and update-heavy.

What not to index: updated_at (changes on every update, would kill HOT updates and adds an entry per update), priority or status alone (low selectivity), body as a B-tree (useless). Write-path check: status and assignee_id appear in indexes (A) and (C), so updates of them are never HOT; that is accepted because those queries are the product. Lower the heap fillfactor to about 85 so other updates (updated_at) can be HOT. Verify each index with EXPLAIN ANALYZE, then watch idx_scan for a month and drop any that are unused.
