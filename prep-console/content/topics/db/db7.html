A reporting query at a mid-sized company ran in 300 milliseconds every morning for a year. One Monday it took 40 minutes, and the dashboard timed out. Nothing had been deployed. The query text was identical. The data had grown by a weekend's worth of rows, about 2%. What changed was a single decision made inside the database: which of two tables to read first, and how to join them.

Over the weekend a bulk import had loaded a few million rows into one table, and the statistics the database keeps about that table had not been refreshed. The database still believed a filter on it would match about ten rows. With ten rows, the best strategy is obvious: for each of the ten, look up its partners through an index, a few page reads each. So it chose that strategy. In reality the filter matched two million rows, and two million index lookups, most of them random reads, took 40 minutes. A different strategy, building a hash table on one side and streaming the other side through it, would have taken under a second.

This is the hidden half of SQL. Because SQL is declarative (db3), the database must decide how to compute every result: the order in which to join tables, the algorithm for each join, which index to use, when to sort. That decision is made by the query optimizer, a component that has been refined since IBM's System R in the late 1970s, and it is made from estimates. When the estimates are right, the optimizer is astonishingly good. When they are wrong, it picks plans that are wrong by factors of thousands, and the query text gives no hint why.

This lesson follows a query through the database: parsing, rewriting, planning and execution. It explains the three join algorithms with their costs worked out for real table sizes, how the optimizer estimates row counts and searches join orders, why estimation is its weak spot (a 2015 study of production-grade optimizers found estimates routinely off by orders of magnitude), and how to read EXPLAIN ANALYZE output, which is the skill that actually resolves incidents like the one above.

From text to rows in four steps

When a database receives SELECT …, it does four things. It parses the text into a tree that reflects the grammar (this SELECT list, these FROM items, this WHERE condition), rejecting syntax errors. It analyses the tree against the catalog: do these tables and columns exist, what are their types, which function does this name refer to. It rewrites the tree: views are expanded into their definitions, some subqueries are flattened into joins, constant expressions are folded. Then it plans: it considers many physical ways to compute the result, estimates the cost of each, and picks the cheapest. Finally it executes the chosen plan.

The planner as a route planner

A good analogy for the planner is a satellite navigation system. You give it a destination (the result), not a route. It knows the road network (tables, indexes, join algorithms) and has estimates of traffic on each road (how many rows each step will produce). It enumerates candidate routes, estimates the total time for each and picks the fastest. When its traffic estimates are good, it picks routes better than most humans would. When its estimates are wrong, say it believes a motorway is clear when it is jammed, it confidently sends you into the jam, and the route it picked was "optimal" for the world it believed in.

The analogy also explains the main tools for fixing bad plans. Better traffic data (refreshed or richer statistics) fixes most problems at the source. New roads (indexes) give the planner better options. And as a last resort you can forbid a road (planner settings that disable an algorithm for a session), which is like telling the satnav to avoid motorways: occasionally necessary, usually a sign the real problem is the data it is working from.

Plans are trees of operators

The chosen plan is a tree. Leaves read data: a sequential scan of a table, an index scan, a bitmap scan (db6). Inner nodes transform rows: filter, join, sort, aggregate, limit. The root produces the result. Execution in most databases follows the iterator model (also called Volcano): the root asks its child for a row, that child asks its own children, and so on, so rows flow upward one at a time, on demand. This is why LIMIT 10 can stop a huge plan early, and why some operators (a sort, the build phase of a hash join) are "blocking": they must consume their entire input before producing a first row. EXPLAIN prints this tree, indented, with the root at the top.

What you control

As an engineer you never pick the plan directly in PostgreSQL, but you control every input to it. You control the query: how predicates are written (sargable or not), whether a semi-join is expressed as EXISTS, whether a large aggregation happens before or after a join. You control the physical design: which indexes exist, whether a table is partitioned, how columns are typed. You control the statistics: when ANALYZE runs, how detailed the statistics are, and whether the planner knows about correlated columns. And you control a few settings: memory per operation, the relative cost of random reads. The rest of this lesson explains how each input feeds the decision, so that when a plan goes wrong you can tell which input to change.

1. Parsing, analysis and rewriting

The parser checks the grammar and builds a parse tree; a missing comma fails here, before any table is examined. The analyser resolves names against the catalog: orders becomes a specific table with an internal id, o.amount becomes column 3 of type integer, sum(o.amount) becomes the integer-sum aggregate. Type errors and unknown columns fail here.

The rewriter transforms the tree into an equivalent but more plannable form. Views are replaced by their defining query, so a query over a view is planned as a query over the underlying tables (which is why views normally cost nothing at run time). Simple subqueries in FROM are pulled up into the main join tree; IN and EXISTS subqueries become semi-joins, and NOT EXISTS becomes an anti-join (db3); CTEs referenced once are inlined in PostgreSQL 12+ (db4). Constant expressions such as now() - interval '1 day' are evaluated once. Outer joins are simplified to inner joins when a WHERE condition makes the NULL-padded rows impossible, which is the db3 ON-versus-WHERE trap seen from the planner's side. The output is a tree of relational algebra (db1): scans, selections, projections, joins and aggregates in no particular physical form yet.

2. The nested-loop join

Physical join algorithms are where most of the cost lives, so take them one at a time, with two concrete tables: orders with 100,000 rows in 1,000 pages, and customers with 40,000 rows in 500 pages, joined on orders.customer_id = customers.id. Costs are in page reads, the traditional unit.

A nested-loop join takes each row of the outer input and searches the inner input for matches. Its cost depends entirely on how that search is done.

  • Naive, row at a time: for each of 100,000 orders, scan all 500 customer pages. 1,000 + 100,000 × 500 = 50,001,000 page reads. Nobody does this on purpose.
  • Page at a time: for each orders page, scan customers once and compare all pairs of rows between the two pages: 1,000 + 1,000 × 500 = 501,000.
  • Block nested loop: load as many outer pages as memory allows, say 100 with 102 buffer pages, and scan the inner input once per block: 1,000 + (1,000 / 100) × 500 = 6,000.
  • Index nested loop: if customers.id has an index (it does: it is the primary key), each order probes the index: about 3-4 page reads per probe, of which the upper levels are cached, so roughly 1-2 real reads. 1,000 + 100,000 × ~1.5 ≈ 151,000 reads, many random. Worse than a hash join for the full table, but now suppose a filter leaves only 50 orders: 50 × ~1.5 ≈ 75 reads plus finding the 50 orders. Nothing beats that.

So nested loops are either terrible or ideal, depending on the size of the outer input. They are ideal for small outer inputs with an indexed inner side, which is the shape of most OLTP queries ("this user's 20 orders with their products"). They also produce their first row immediately, which suits LIMIT. They are the only algorithm that works for arbitrary join conditions such as a.ts BETWEEN b.start AND b.end, since hash and merge joins need an equality condition. And they are the algorithm behind the opening story: correct for ten outer rows, catastrophic for two million.

3. The hash join

A hash join runs in two phases. In the build phase it reads the smaller input, the build side, and inserts every row into an in-memory hash table keyed on the join column. In the probe phase it reads the larger input, the probe side, and for each row computes the hash of its join key and looks up matching rows in the table. Each input is read once.

If the build side fits in memory (PostgreSQL's limit is work_mem times a multiplier, per hash operation), the cost is one read of each: 500 + 1,000 = 1,500 page reads. If it does not fit, the classic solution is the Grace hash join: first partition both inputs by a hash of the join key into, say, 20 partition files each, so that matching rows always land in partition files with the same number; then join each pair of partitions in memory. Each input is read, written and read again: 3 × (1,000 + 500) = 4,500 page reads. PostgreSQL reports this as Batches: N greater than 1 in EXPLAIN ANALYZE; seeing many batches is a sign the hash table spilled to disk and that more work_mem for that query would help.

Hash joins need an equality join condition, have a blocking build phase (no rows come out until the build side has been read entirely), and lose any ordering of the inputs. They are the workhorse of analytical queries joining large tables, and they are robust: their cost is roughly linear in input size whatever the selectivity. That robustness is why the Leis study found engines that rely on hash joins and full scans tolerate bad estimates far better than those that lean on index nested loops.

4. The merge join

A merge join needs both inputs sorted on the join key. It then walks them together like the merge step of merge sort: compare the current keys; advance whichever side is smaller; on equality, output the matching pairs (handling runs of duplicate keys by remembering where the run started on one side). Once sorted, the join itself reads each input once: 1,500 page reads.

The cost question is the sort. If both inputs come from indexes in join-key order, or one was already sorted by an earlier step, the sort is free and the merge join is very cheap and pipelined. Otherwise each input is sorted, and an external sort of data larger than memory takes passes: with 100 pages of memory, sorting 1,000 pages needs one pass to create sorted runs and one pass to merge them, reading and writing everything each time, about 2 × 2 × 1,000 = 4,000 for orders and 2,000 for customers, so the whole sort-merge is about 7,500. Merge joins also emit rows in join-key order, which a later ORDER BY or GROUP BY on that key can use. Selinger's 1979 paper called such useful orderings interesting orders and made the optimizer keep the cheapest plan for each one, rather than only the overall cheapest, precisely so that a slightly more expensive sorted plan can win when a later step needs the order.

5. Statistics and cardinality estimation

To cost a plan, the planner must know how many rows each step produces: its cardinality estimate. It starts from statistics gathered by ANALYZE (run automatically by autovacuum in PostgreSQL after enough rows change), which samples each table and stores per column: the fraction of NULLs, the number of distinct values, a list of most common values (MCVs) with their frequencies, a histogram of the remaining values (bucket boundaries chosen so each bucket holds the same number of rows), and the correlation between value order and physical order. The default statistics target of 100 means up to 100 MCVs and 100 histogram buckets, from a sample of 300 × 100 = 30,000 rows.

From these it estimates selectivities. status = 'shipped': look up 'shipped' in the MCV list, say frequency 0.62. amount > 500: find where 500 falls in the histogram, say in the 87th of 100 buckets, so about 13% match. customer_id = $1 for a value not in the MCVs: assume the remaining rows are spread evenly across the remaining distinct values. A join's output is estimated from the distinct counts of both join columns: for a key/foreign-key join, roughly the size of the foreign-key side times the selectivity of the filters on both sides.

The weakest link is how conditions are combined. For A AND B the planner multiplies selectivities, assuming the conditions are independent. That is exact for unrelated columns and badly wrong for correlated ones: city = 'Pune' AND state = 'MH' at 1% and 10% is estimated at 0.1% of rows when the truth is 1%, a tenfold underestimate. In a multi-join query, such errors multiply through every join. Selinger's 1979 System R paper had to use magic constants for predicates it had no statistics for (a selectivity of 1/10 for column = value without an index), and modern planners still fall back to defaults for complex expressions, functions on columns and many LIKE patterns. CREATE STATISTICS on column groups (functional dependencies, multi-column distinct counts and MCVs) and expression statistics are the PostgreSQL tools that address the common cases.

6. The cost model

Given row estimates, each operator's cost is computed from simple formulas. PostgreSQL charges seq_page_cost (1.0) per page read sequentially, random_page_cost (4.0 by default) per page read at random, cpu_tuple_cost (0.01) per row processed, cpu_operator_cost (0.0025) per operator or function evaluated, and so on. A sequential scan of a 345-page, 10,000-row table with no filter therefore costs 345 × 1.0 + 10,000 × 0.01 = 445, which is exactly the Seq Scan on tenk2 … cost=0.00..445.00 in the PostgreSQL documentation's example below. Costs are reported as two numbers, startup cost (work before the first row, such as building a hash table or sorting) and total cost, because a LIMIT query cares mostly about the first, and a full result about the second.

The units are arbitrary and only meaningful for comparing plans of the same query. The default random_page_cost of 4 encodes the assumption that random reads are four times as expensive as sequential ones; on SSDs, and when most data is cached, many teams set it to about 1.1, which makes index scans more attractive. That is a legitimate tuning knob; the documentation notes it can be set per tablespace.

7. Searching for the best plan

For a single table, the planner compares access paths: sequential scan, each usable index scan, index-only scan, bitmap scan, each with its cost and its output order. For joins it must also choose an order. Three tables can be joined in 12 left-deep orders, and more if "bushy" trees (joining two join results) are allowed; the count grows factorially. System R's answer, still used by PostgreSQL, is dynamic programming: compute the cheapest plan for every single table, then for every pair of tables using the best single-table plans, then for every set of three from the best pairs, and so on, keeping for each subset the cheapest plan overall and the cheapest per interesting order. Plans that join tables with no join condition between them (cross products) are generally skipped. This finds the cheapest plan the cost model can see, but the work grows exponentially with the number of tables.

PostgreSQL therefore has limits. from_collapse_limit and join_collapse_limit (8 by default) stop the planner from merging subqueries and explicit JOINs into one search space beyond eight items; beyond that, the join order written in the query is partly kept. At geqo_threshold (12 FROM items by default) it switches from exhaustive search to the genetic query optimizer, a randomised search that is much faster but may miss the best plan. Queries with dozens of joins, common in generated SQL from ORMs and BI tools, are where planning time and plan quality both suffer.

8. Execution: iterators, pipelining and memory

The executor turns the plan tree into operators that each implement "give me the next row". A Limit node asks its child for rows until it has ten, then stops asking, and the whole subtree stops. A Nested Loop asks its outer child for a row, then asks its inner child (re-scanned with the outer row's key as a parameter) for matches. A Hash Join first drains its inner child into a hash table, then streams its outer child. Operators that pass rows along as they arrive are pipelined; operators that must see everything first (Sort, Hash, HashAggregate) are blocking and need memory.

Memory-hungry operators are bounded by work_mem (4 MB by default in PostgreSQL), per operator. A sort that exceeds it writes sorted runs to temporary files and merges them (Sort Method: external merge Disk: … in EXPLAIN ANALYZE); a hash join that exceeds it (scaled by hash_mem_multiplier) splits into batches. Modern engines add parallel query, where several worker processes each scan part of a table and their partial results are gathered (Gather nodes), and some analytical engines replace row-at-a-time iterators with vectorised execution over batches of values or compile plans to machine code, which db12 touches on for columnar stores.

9. Grouping, sorting and limits

Joins are not the only operators with several algorithms. GROUP BY can be computed two ways. A HashAggregate reads its input once and keeps a hash table with one entry per group, updating each group's running sum or count as rows arrive; it needs memory proportional to the number of groups, not rows, and outputs groups in no particular order. A GroupAggregate needs its input sorted by the grouping columns and walks it, emitting each group when the key changes; it uses almost no memory and preserves order, so it wins when the input is already sorted (from an index or a merge join) or when there are too many groups to hash. For "revenue per day over a year" with 365 groups, hashing is trivially cheap; for "count per user" over 50 million users, the hash table may exceed work_mem and spill, and a sort-based plan may be chosen instead.

Sorting has its own shortcut for the most common pattern in applications, ORDER BY … LIMIT n. A full sort of a million rows to keep ten is wasteful, so PostgreSQL uses a top-N heapsort when a LIMIT sits above a sort: it keeps only the best n rows seen so far in a small heap, which EXPLAIN ANALYZE reports as Sort Method: top-N heapsort Memory: 25kB. Better still is an index that already delivers the order (db6), in which case the plan is an index scan under a Limit node and the query reads only the first few entries. Incremental sort (PostgreSQL 13+) handles the in-between case: if rows arrive sorted by a from an index and the query wants ORDER BY a, b, it only sorts each group of equal a values by b, which can stream results and use far less memory.

DISTINCT and UNION deduplicate with the same two strategies (hash or sort), which is why db3 advised UNION ALL when duplicates are impossible: it removes an entire hash or sort operator from the plan. Window functions (db4) add a WindowAgg node, normally above a Sort on the PARTITION BY and ORDER BY columns. In every case the planner compares the strategies with the same cost model and the same row estimates, so the estimate of the number of groups (from the distinct-count statistics) matters as much for aggregation as row counts do for joins.

Read it bottom-up, like the executor runs it. The Bitmap Index Scan finds index entries with unique1 < 100: estimated 100 rows, actual 100. The Bitmap Heap Scan fetches those rows from 90 heap pages (Heap Blocks: exact=90, exact meaning the bitmap did not become lossy). The Hash node loads them into a hash table: 1,024 buckets, 1 batch (it fitted in memory), 35 kB. The Seq Scan on tenk2 streams all 10,000 rows of the other table (345 pages, all already in cache: shared hit=345, no disk reads). The Hash Join probes the table with each tenk2 row and emits 100 matches. The Sort orders them by fivethous in memory with quicksort, 74 kB.

Now the numbers on each line. cost=226.23..709.73 is startup and total cost in planner units. rows=100 in the first parentheses is the estimate; rows=100.00 in the second is the actual average per loop. width=488 is the estimated average row size in bytes. actual time=0.515..2.920 is milliseconds to the first row and to the last row, per loop. loops=1 is how many times the node ran; inside a nested loop, the inner node has loops equal to the outer row count, and you must multiply its time and rows by loops to get totals. Buffers: shared hit counts pages found in PostgreSQL's buffer cache, read pages fetched from the OS or disk.

The diagnostic habit: for every node, compare estimated rows to actual rows. Here they match everywhere, so the plan is trustworthy. In the opening story, the lowest mismatched node would have said something like rows=10 estimated and rows=2000000 actual under a Nested Loop with loops=2000000 on its inner index scan. The first node, reading from the bottom, where estimates diverge from reality by more than about ten times is almost always where the problem starts, because every decision above it was made on a wrong number.

11. Fixing a bad plan, in order

When a plan is bad, fix the cause rather than the symptom, in this order. First, the statistics. If estimates are wrong on a single table, run ANALYZE (stale statistics after bulk loads are the commonest cause); raise the statistics target for a skewed column (ALTER TABLE … ALTER COLUMN … SET STATISTICS 1000); add extended statistics for correlated columns. Second, the physical design. Add or change an index so the good plan exists and is cheap (db6). Third, the query. Rewrite NOT IN as NOT EXISTS, make predicates sargable, pre-aggregate before joining, or fix a misestimated subquery's size with a MATERIALIZED CTE. Last, planner settings, scoped to one session or role: SET enable_nestloop = off for a known reporting query, a higher work_mem for an analytical job, or adjusted random_page_cost globally on SSD storage. PostgreSQL has no built-in query hints, deliberately; the pg_hint_plan extension provides them for emergencies. MySQL and Oracle support optimizer hints in the query text. Hints freeze today's best plan into tomorrow's data, which is why they are a last resort.

Why cardinality estimation is fundamentally hard

Leis and colleagues built the Join Order Benchmark from the IMDB data set, with 113 queries that join between 3 and 16 tables, and compared the row-count estimates of several commercial and open-source optimizers against true counts for every intermediate result. All of them routinely produced large errors, and errors grew with the number of joins: a small error on each base table, multiplied through six joins under the independence assumption, becomes orders of magnitude. They then injected each system's estimates into PostgreSQL and measured the resulting plans: with one system's estimates 78% of queries ran within 2x of the plan built from true counts, with another only 53%, and every estimator occasionally produced plans that timed out. Their experiments on the cost model were reassuring by contrast: even simple cost models were good enough once cardinalities were right. The lesson for practitioners is to invest in estimates (statistics, schema design that avoids correlated predicates across joins, simpler queries) rather than in fiddling with cost constants.

Robust plans and adaptive execution

The same study found that when nested-loop joins were disabled and hash tables could grow at run time, most queries ran close to optimal despite bad estimates, because hash joins degrade gracefully when an input is bigger than expected while index nested loops degrade catastrophically. This is a general design principle: prefer operators whose cost is not very sensitive to the estimate. Several engines now go further with adaptive execution. SQL Server has adaptive joins that choose between nested loop and hash join after counting the actual rows of the first input; Oracle has adaptive plans and statistics feedback; Spark SQL's adaptive query execution re-plans between stages using actual partition sizes. PostgreSQL's planning is still fully static, which is why its EXPLAIN ANALYZE discipline matters so much.

Parameterised queries and generic plans

Planning is not free: for complex queries it can take milliseconds, comparable to execution for simple ones. Prepared statements let a client plan once and execute many times. PostgreSQL's policy is to build a custom plan using the actual parameter values for the first five executions, then compare their average cost with a generic plan that assumes typical values; if the generic plan is not more expensive, it switches to it and stops planning. For uniformly distributed data, that is a pure win. For skewed data, such as a multi-tenant table where one tenant has 40% of the rows, the generic plan built for "a typical tenant" (a nested loop over an index) can be disastrous for the big tenant. The plan_cache_mode setting can force custom or generic plans. Connection poolers and ORMs that prepare statements implicitly make this a frequent and confusing source of "same query, different speed" reports.

Join elimination and other rewrites

The rewriter and planner remove work when they can prove it is unnecessary. A LEFT JOIN to a table whose columns are not used, on that table's unique key, cannot change the result (each left row matches at most one right row and nothing from it is selected), so PostgreSQL removes the join entirely. This is why views that join many lookup tables are not as expensive as they look when queries use only some columns. Other rewrites include predicate pushdown into subqueries and views, partition pruning (skipping partitions whose bounds cannot match the WHERE clause, at plan time and, for parameters, at execution time), and transforming OR conditions on indexed columns into bitmap ORs. Knowing which rewrites exist helps you write SQL that is clear without being slow: you can write the readable version and check the plan, rather than hand-optimising.

The physical design feedback loop

The optimizer can only choose among plans that the physical design makes possible. That makes index design (db6), partitioning and statistics part of query optimisation. In practice the loop is: find the expensive queries (pg_stat_statements sorted by total time), read their plans, identify the operator that dominates time or the first misestimate, change the physical design or statistics, and verify. Tools such as auto_explain (which logs the plans of slow queries automatically, optionally with ANALYZE data) and plan visualisers make this loop faster, and capturing plans before and after deployments or upgrades is the cheapest way to diagnose a regression later.

The stale-statistics incident

The opening story is the most common query-plan incident in PostgreSQL deployments, and it has a recognisable signature. A query that was fast becomes slow right after a bulk load, a big delete, or the creation of a new table that is populated in the same transaction. EXPLAIN ANALYZE shows a nested loop whose outer input was estimated at a few rows and actually returned millions. pg_stat_user_tables shows last_autoanalyze from before the load and a large n_mod_since_analyze. Running ANALYZE on the table fixes it immediately. The permanent fix is procedural: every batch job that loads or deletes a large fraction of a table ends with ANALYZE, because autovacuum's analyze threshold (10% of the table plus 50 rows by default) can lag behind bulk changes, and because a freshly created and loaded table has no statistics at all until it runs.

Plan flips and plan instability

A subtler failure is a plan that flips between two alternatives as data slowly changes: one day the planner estimates 5,000 rows and picks a hash join, the next 4,800 and picks a nested loop, and latency doubles or halves with no deployment. Monitoring per-query latency in pg_stat_statements (mean and standard deviation of execution time) catches it; auto_explain with a duration threshold captures the slow plan when it happens. Fixes are the same hierarchy as before, aimed at making the good plan clearly cheapest: a better index, a better estimate, or a query shape whose plan is robust. Some teams on other databases pin plans (SQL Server's Query Store, Oracle's SQL Plan Management); PostgreSQL users rely on pg_hint_plan for the rare cases that need it.

Spills and memory

Sorts and hashes that spill to disk show up as external merge, multiple hash Batches, and temp read/written buffers in EXPLAIN (ANALYZE, BUFFERS), and in aggregate as temp_bytes in pg_stat_database; setting log_temp_files logs each temporary file above a size. The remedy for a specific heavy query is a higher work_mem for its session or role, not globally: because the limit applies per operation per connection, a global 256 MB with 300 connections and multi-join queries can exhaust RAM and invite the OS out-of-memory killer (os9). Analytical workloads often run under a dedicated role with a larger work_mem and a lower connection limit.

ORMs and generated SQL

Object-relational mappers and BI tools generate SQL that humans would not write: dozens of joins from eager loading, deeply nested subqueries, IN lists with thousands of literals, and every column selected. Planning time itself becomes significant (visible as Planning Time in EXPLAIN ANALYZE, sometimes larger than execution), join-order search hits the collapse limits, and estimates degrade with each join. db13 covers ORM patterns; from the optimizer's side, the practical rules are to log the generated SQL for slow endpoints, read its plan like any other, and replace the worst offenders with hand-written queries or views.

Query plans for LLM-backed features

AI features add new shapes to old plans. Retrieval queries combine an approximate vector search (whose row count the planner estimates poorly, since the index returns "the top k" rather than rows matching a predicate) with relational joins and filters for permissions and metadata; the robust shape is to fix the candidate set first (a CTE with LIMIT, or a materialized step) and then nested-loop into indexed tables by primary key. Analytics over LLM call logs are classic large-table aggregations that want hash aggregates, parallel scans and partition pruning by time. And text-to-SQL systems, where a model writes queries against your database, need guardrails grounded in this lesson: run generated SQL under a role with a statement timeout and limited work_mem, inspect EXPLAIN cost before executing, and reject plans with enormous estimated row counts or cross joins.

customers = [(c, f"c{c}") for c in range(5_000)]                  # build side: small

def nested_loop(outer, inner):            # compare every pair
    out, cmp = [], 0
    for o in outer[:2_000]:               # only 1% of orders: the full run is too slow
        for c in inner:
            cmp += 1
            if o[1] == c[0]:
                out.append((o[0], c[1]))
    return out, cmp * 100                 # scale comparisons back to all orders

def hash_join(probe, build):              # build a hash table on the small side
    table = {c[0]: c for c in build}
    return [(o[0], table[o[1]][1]) for o in probe if o[1] in table], len(build) + len(probe)

def merge_join(left, right):              # both sorted on the join key
    left, right = sorted(left, key=lambda r: r[1]), sorted(right)
    out, i, j, steps = [], 0, 0, 0
    while i < len(left) and j < len(right):
        steps += 1
        if left[i][1] < right[j][0]:
            i += 1
        elif left[i][1] > right[j][0]:
            j += 1
        else:
            out.append((left[i][0], right[j][1])); i += 1
    return out, steps

for name, fn in [("nested loop", nested_loop), ("hash join", hash_join), ("merge join", merge_join)]:
    t0 = time.perf_counter()
    rows, work = fn(orders, customers)
    ms = (time.perf_counter() - t0) * 1000
    print(f"{name:<12} rows={len(rows):>7,}  work units={work:>13,}  {ms:8.1f} ms")

# How SQLite plans the same join, without and with an index on the join column
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE customer (id INTEGER PRIMARY KEY, name TEXT)")
db.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INT, amount INT)")
db.executemany("INSERT INTO customer VALUES (?,?)", customers)
db.executemany("INSERT INTO orders VALUES (?,?,?)", orders)
db.execute("ANALYZE")
q = "SELECT c.name, sum(o.amount) FROM orders o JOIN customer c ON c.id = o.customer_id WHERE c.id < 50 GROUP BY c.name"
for label in ("before index", "after index"):
    if label == "after index":
        db.execute("CREATE INDEX ix_orders_customer ON orders (customer_id)")
        db.execute("ANALYZE")
    plan = [r[3] for r in db.execute("EXPLAIN QUERY PLAN " + q)]
    print(f"{label}: " + " | ".join(plan))

What to look for.

  1. The nested loop is run on only 1% of orders (2,000 rows) because the full run would take around a minute; its work counter is scaled to the full join: about a billion comparisons. The hash join does about 205,000 units of work (5,000 inserts plus 200,000 probes) in tens of milliseconds. The merge join's work is similar, but its time includes sorting both inputs, so it is slower than the hash join here.
  2. SQLite before the index: SCAN o | BLOOM FILTER ON c (id=?) | SEARCH c USING INTEGER PRIMARY KEY: it scans all orders, uses a Bloom filter (a bit array that cheaply rules out non-matching keys, db5) to skip orders whose customer cannot match the c.id < 50 filter, and probes customers by primary key. That is a nested loop with the big table outside.
  3. After indexing orders.customer_id: SEARCH c … (rowid<?) | SEARCH o USING INDEX ix_orders_customer: the join order flipped. It now finds the 50 customers first and probes orders through the new index, an index nested loop with the small side outside.

Try next. Change the filter to c.id < 4000 and rerun: with 80% of customers selected, check whether SQLite still prefers the index. Then remove the ANALYZE calls and see whether the plan changes: SQLite, like PostgreSQL, plans better with statistics. If you have PostgreSQL available elsewhere, run the documentation's tenk1/tenk2 query with EXPLAIN (ANALYZE, BUFFERS) and compare your output with the plan in section 10.

Diagnose: the dashboard query that went from 2 s to 9 minutes

After a migration that backfilled 30 million historical rows into events, a dashboard query slowed from 2 seconds to 9 minutes. The relevant part of EXPLAIN ANALYZE:

Nested Loop  (cost=1.13..2450.10 rows=12 width=40) (actual time=0.09..538211.4 rows=2841902 loops=1)
  ->  Index Scan using events_type_ts on events e  (cost=0.56..1180.33 rows=12 width=24)
        (actual time=0.05..19420.7 rows=2841902 loops=1)
        Index Cond: ((type = 'purchase') AND (ts >= '2026-09-01'))
  ->  Index Scan using users_pkey on users u  (cost=0.57..105.80 rows=1 width=24)
        (actual time=0.18..0.18 rows=1 loops=2841902)
        Index Cond: (id = e.user_id)

Explain what happened and what you would do.

Answer

Read bottom-up and compare estimates. The events index scan was estimated at 12 rows and returned 2,841,902: an error of about 240,000x. The users lookup is fine per call (0.18 ms) but ran 2,841,902 times (loops), so it contributed about 2.84 million × 0.18 ms ≈ 512 seconds, almost all of the 538 s. A nested loop is the right plan for 12 rows and a terrible one for 2.8 million.

Why the estimate was wrong. The backfill inserted 30 million rows, and statistics were not refreshed (autovacuum's analyze may not have run yet, or the histogram for ts still ends before September, so the planner thinks almost no rows are that recent). Possibly also correlation: type = 'purchase' and recent ts multiplied as independent.

Fix, in order. Run ANALYZE events; and re-check: the estimate should jump to millions and the planner should switch to a hash join (scan users once into a hash table, or vice versa), bringing the query back to seconds. Add ANALYZE as the final step of the backfill job. If the estimate is still badly off, add extended statistics on (type, ts) or raise the statistics target on ts. If the dashboard only needs aggregates, a pre-aggregated daily table would make it independent of the raw event volume altogether. Do not reach for enable_nestloop = off globally; at most, set it for this report's session while the root cause is fixed.
