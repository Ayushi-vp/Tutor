A payment service moves 50 from account A to account B. That is two writes: subtract 50 from A's row, add 50 to B's row. Those rows live on two different 8 KB pages in the database's memory, and eventually on two different places on disk. Now pull the power plug at the worst possible moment: A's page has been written to disk with the new balance, B's has not. When the machine restarts, 50 has vanished. Or the opposite: the client was told "transfer complete", but neither page had reached disk, and on restart the transfer never happened. Either outcome is unacceptable for a database, and both are exactly what would happen if a database simply wrote changed pages to disk in whatever order was convenient.

The guarantees that rule this out are two of the four letters of ACID (sc5). Atomicity: a transaction's changes happen entirely or not at all. Durability: once a commit is acknowledged, it survives crashes. The engineering problem is that disks write one page at a time, crashes can happen between any two writes (or in the middle of one), and writing every changed page synchronously at commit would make every transaction wait for many scattered disk writes.

The solution, used by essentially every serious database, is a log. Before changing anything on disk, the database writes a description of the change to an append-only write-ahead log (WAL), and a transaction counts as committed the moment its commit record is safely in that log. After a crash, the database reads the log and repairs the data files: it re-applies committed changes that had not reached disk and reverses uncommitted ones that had. The definitive form of this recovery algorithm is ARIES, published by C. Mohan and colleagues at IBM in 1992 and used, in variants, by DB2, SQL Server and many other systems; PostgreSQL and InnoDB use their own versions of the same ideas.

This lesson builds the machinery from the problem upward: the choices a buffer pool makes about when to write pages, what must therefore be logged, the write-ahead rule and log sequence numbers, how commit is made both durable and fast, what checkpoints are for, how torn pages are repaired, and ARIES's three recovery passes traced on a crash. It ends with what goes wrong in production, including the 2018 discovery that fsync on Linux did not always mean what PostgreSQL thought it meant.

The ledger and the diary

Picture a shop that keeps its accounts in a big ledger book, but writing in the ledger is slow because the pages are scattered around a large office. So the shopkeeper also carries a small diary. Every time money moves, they first write a line in the diary: "10:02, transfer 50 from A to B, A was 100 now 50, B was 200 now 250". Only then do they update the copy of the ledger page they keep on their desk. They walk to the office and file updated ledger pages whenever convenient, perhaps once an hour. When a customer asks "is my transfer done?", the shopkeeper says yes as soon as the diary line ending "transfer complete" is written.

If the shopkeeper faints and loses their desk papers, nothing is lost: the diary says exactly what happened, in order. On recovery they read the diary from the last time they knew the ledger was up to date, re-apply every completed transfer the ledger is missing, and reverse any half-done transfer that has no "complete" line. The diary is the write-ahead log, the ledger is the data files, and the desk copies are the buffer pool.

The analogy breaks in two useful places. A diary line is cheap because it is written at the end of a single sequential notebook, whereas ledger pages are scattered; on real storage, sequential appends are also much cheaper than scattered page writes, which is the whole performance case for the log. And real "fainting" can happen mid-word: a page can be half written when power fails, which the diary must also be able to repair.

Two rules make it work

The whole scheme rests on two ordering rules. First, the write-ahead rule: the log record describing a change must be on stable storage before the changed page is. Otherwise a page could reach disk with a change the log knows nothing about, and recovery could not undo it. Second, the commit rule: all of a transaction's log records, ending with its commit record, must be on stable storage before the commit is acknowledged. Otherwise the client could be told "done" about a change that a crash then erases.

What recovery has to do

Because pages are written lazily and in any order, at the moment of a crash the data files can contain a mixture: some committed changes missing (their pages never written) and some uncommitted changes present (their pages written early to free memory). Recovery therefore has two jobs, redo (bring forward committed changes the data files are missing) and undo (remove uncommitted changes the data files contain). The log must hold enough information for both, and each page must record which log records it already reflects, so recovery does not apply a change twice. The rest of this lesson is how those requirements are met efficiently.

1. Buffer pool policies: steal and force

All changes happen in the buffer pool, the database's cache of pages (db5). Two policy decisions about when changed (dirty) pages may or must be written determine what recovery has to handle.

Steal or no-steal: may the buffer pool write a dirty page to disk while a transaction that changed it is still running? With no-steal, uncommitted changes never reach disk, so recovery never needs to undo anything, but a long transaction that changes many pages pins them all in memory, and a transaction bigger than memory is impossible. With steal, the buffer pool may evict any dirty page when it needs room, so uncommitted changes can be on disk at a crash and must be undoable.

Force or no-force: must all of a transaction's dirty pages be written to disk at commit? With force, committed changes are always on disk, so recovery never needs to redo anything, but every commit waits for many random page writes, and a page changed by a hundred transactions in a second is written a hundred times. With no-force, commit writes only the log, and pages are written later, but committed changes may be missing from disk at a crash and must be redoable.

Real databases choose steal / no-force: it gives the buffer pool freedom to manage memory and makes commit cost one sequential log flush. The price is that the log must carry both redo information (the new value, or how to compute it) and undo information (the old value, or how to reverse the change), and recovery must do both. ARIES is designed for exactly this combination.

2. Log records and LSNs

Every change produces a log record appended to the WAL. A typical update record holds: the transaction id; the page id; what changed (for redo, the new bytes or a logical description such as "insert this tuple at slot 5"); how to reverse it (for undo, the old bytes or the inverse operation); and a pointer to the same transaction's previous log record, so a transaction's records can be walked backwards for rollback. There are also records for transaction begin, commit and abort, and for checkpoints.

Each record is identified by its log sequence number (LSN), its position in the log, which only ever increases. In PostgreSQL an LSN is a 64-bit byte offset into the WAL stream, displayed as two hexadecimal halves such as 0/16B3748; SELECT pg_current_wal_lsn() shows the current one. The crucial link between log and data is the pageLSN: every page header (db5) stores the LSN of the last log record whose change has been applied to that page. When the page is written to disk, its pageLSN goes with it. During recovery, comparing a log record's LSN with the on-disk page's pageLSN answers "is this change already in the page?" without guessing: if pageLSN ≥ record LSN, it is; otherwise it must be redone.

The write-ahead rule is enforced with LSNs too. The log manager tracks flushedLSN, how far the log is durable. Before the buffer pool writes a dirty page, it checks that the page's pageLSN ≤ flushedLSN, flushing the log first if not. That one check guarantees that no page reaches disk carrying a change the durable log does not describe.

3. Commit: durability without waiting for pages

To commit, the database appends a commit record and flushes the log through that record's LSN, typically with fsync or fdatasync on the WAL file (or an O_DSYNC write). When the flush returns, the transaction is durable: whatever happens next, the log contains every record of the transaction and recovery will redo it. The client is told "committed" only now.

A log flush has a fixed cost, from tens of microseconds on enterprise NVMe drives with power-loss protection to several milliseconds on a disk or a cloud volume. If every commit needed its own flush, a device capable of 1,000 flushes per second would cap the database at 1,000 commits per second regardless of CPU. Group commit removes the cap: when a transaction wants to flush, it either starts a flush or, if one is in progress, waits for the next one, which will cover every commit record appended in the meantime. Under load, one flush may carry dozens of commits. PostgreSQL's commit_delay setting can even wait a few microseconds deliberately to gather more commits per flush. The result is the characteristic behaviour of OLTP databases: single-transaction commit latency is about one flush, while throughput scales with concurrency.

Some applications do not need every commit to be durable. PostgreSQL's asynchronous commit (synchronous_commit = off) returns success as soon as the commit record is in the in-memory WAL buffer; the background WAL writer flushes it shortly afterwards. The documentation is precise about the risk: a crash can lose transactions committed in roughly the last three wal_writer_delay periods (200 ms by default, so up to about 600 ms), but cannot corrupt the database or apply part of a transaction, because the WAL is still replayed in order and simply ends earlier. It can be set per transaction, so a system can make payment commits synchronous and analytics inserts asynchronous.

4. Checkpoints

With no-force, data files lag behind the log indefinitely, so after a crash recovery would have to replay the log from the beginning of time, and no log could ever be deleted. A checkpoint bounds both. The simplest form would stop all activity, write every dirty page, and log "everything before here is on disk"; that is a sharp checkpoint, and stopping the database for it is unacceptable. Real systems use fuzzy checkpoints, which run while transactions continue.

In PostgreSQL, a checkpoint notes the current WAL position as its redo point, writes out every page that was dirty at that moment, spreading the writes over time to avoid an I/O spike, then fsyncs the data files and writes a checkpoint record pointing back to the redo point. Once complete, every change logged before the redo point is guaranteed to be in the data files, so crash recovery starts replay at the redo point and WAL segments older than it can be recycled (unless needed for archiving or replication). Checkpoints are triggered every checkpoint_timeout (5 minutes by default) or when WAL since the last checkpoint approaches max_wal_size (1 GB by default), whichever comes first, and checkpoint_completion_target (0.9) spreads the page writes over 90% of the interval.

The trade-off is direct. Frequent checkpoints mean less WAL to replay after a crash (faster recovery) but more page writes, because a page changed every second is written once per checkpoint instead of once per hour, and, with full-page writes, more WAL. Infrequent checkpoints mean fewer writes and less WAL but longer recovery. ARIES's checkpoints are even lighter: they write no pages at all, only the current transaction table and dirty page table to the log, and rely on background writing to keep the dirty page table short.

5. Torn pages and full-page writes

A database page is 8 KB (PostgreSQL) or 16 KB (InnoDB), but storage devices and file systems often guarantee atomicity only for smaller units, such as 4 KB sectors or blocks. If power fails while a page is being written, the page on disk can be torn: the first half new, the second half old. Redo cannot fix a torn page from a small log record, because the record says something like "set slot 5 to these bytes", which assumes the rest of the page is intact and consistent.

PostgreSQL's solution is full-page writes, on by default: the first time a page is modified after each checkpoint, the WAL record includes a complete image of the page. During recovery, replay restores that full image first, which overwrites any torn version, and then applies subsequent records normally. Because the image is logged only on the first change per checkpoint cycle, a page changed a thousand times between checkpoints costs one 8 KB image plus a thousand small records. The cost is significant when changes are scattered across many pages (random keys, db5) and checkpoints are frequent; that is why the documentation notes that shorter checkpoint intervals partly defeat themselves by increasing WAL volume. InnoDB solves the same problem differently, with a doublewrite buffer: pages are first written to a dedicated area, fsynced, then written to their real location, so a torn page can be repaired from its doublewrite copy. Both mechanisms can be disabled on storage that guarantees atomic page-sized writes.

6. ARIES recovery, traced

ARIES recovers in three passes over the log. Trace them on the lab's tiny example: pages A, B and C start on disk as 100, 200 and 300, with pageLSN −1 (no changes yet).

LSNRecordNotes
0T1 update A: 100 → 150
1T1 update B: 200 → 250
2T1 COMMITlog flushed: T1 durable
3T2 update C: 300 → 999page C then stolen to disk (pageLSN 3)
4T2 update A: 150 → 0— crash —

At the crash, disk holds A = 100, B = 200 (T1 committed but its pages were never written: no-force) and C = 999 (T2's uncommitted change was written: steal). This is the worst case: both a missing committed change and a present uncommitted one.

Analysis pass. Read the log forward from the last checkpoint (here, the start) and rebuild two tables. The transaction table: T1 has a commit record, so it is a winner; T2 has updates but no commit, so it is a loser that must be rolled back. The dirty page table: pages A, B and C were changed, each with a recLSN, the earliest LSN that might not be on disk (A: 0, B: 1, C: 3). Redo will start from the smallest recLSN.

Redo pass: repeat history. Read forward from LSN 0 and reapply every update, winners and losers alike, unless the page already has it. LSN 0: page A's pageLSN is −1 < 0, so apply: A = 150. LSN 1: B = 250. LSN 3: page C's pageLSN is 3, not less than 3, so skip; the change is already there. LSN 4: A's pageLSN is now 0 < 4, apply: A = 0. The lab prints the state after redo: A = 0, B = 250, C = 999, exactly the state in memory at the moment of the crash, including T2's uncommitted changes.

Undo pass. Roll back the losers by walking their records backwards, newest first. LSN 4 (T2, A: 150 → 0): restore A = 150, and append a compensation log record (CLR) saying "undid LSN 4". LSN 3 (T2, C: 300 → 999): restore C = 300, append a CLR "undid LSN 3". T2 has no earlier records, so it is fully rolled back; an abort record is written. Final state: A = 150, B = 250, C = 300. T1's transfer is fully present, T2 has vanished without trace, and the lab's output matches line for line.

7. Why repeat history, and why CLRs

It might seem wasteful for redo to reapply T2's changes only for undo to reverse them. ARIES's paper calls this repeating history and makes it the central idea, for two reasons. First, it makes recovery simple and uniform: after redo, every page is exactly as it was at the crash, so undo can use the same code as a normal rollback. Second, it is required for fine-grained locking: if T2 and a committed T3 both modified different rows on the same page, the page's state after T3's change depends on T2's change having happened (slot positions, free space). Reversing T2 correctly means reversing it logically on a page that includes both changes, which needs the page in its real pre-crash state.

Compensation log records make undo itself crash-safe. Each CLR records one undo action and points to the next record of the same transaction still to be undone (its undoNextLSN). If the system crashes during recovery, the next recovery's redo pass reapplies the CLRs like any other change (repeating history again), and its undo pass follows the undoNextLSN pointers, skipping work already done. CLRs are never themselves undone. This guarantees that the log grows by a bounded amount however many times recovery is interrupted, a property the ARIES authors explicitly designed for.

The same machinery handles ordinary rollbacks while the system is running, including partial rollbacks to savepoints: ROLLBACK TO SAVEPOINT s walks the transaction's records backwards to the savepoint's LSN, writing CLRs, and the transaction continues. ARIES's title mentions partial rollbacks precisely because supporting them cleanly with fine-grained locking was one of its contributions.

8. PostgreSQL: redo-only recovery thanks to MVCC

PostgreSQL implements the same principles with a twist that removes the undo pass. Its MVCC design (db9) never overwrites a row in place: an update writes a new row version and marks the old one as superseded, each version carrying the id of the transaction that created it. Whether a version is visible depends on whether its creating transaction committed, which is recorded in a separate structure, the commit log (pg_xact). An aborted transaction's row versions remain physically in the heap but are invisible to everyone, because the commit log says the transaction aborted; vacuum later reclaims the space (db10).

So PostgreSQL's WAL only needs redo information, and crash recovery is a single forward pass from the checkpoint's redo point, replaying every record. Transactions in progress at the crash have no commit record; after recovery they are simply treated as aborted, and their row versions are invisible. Abort during normal operation is nearly free: mark the transaction aborted in the commit log. The trade-off is the one PostgreSQL users know well: dead row versions accumulate and must be vacuumed, and the table holds old versions that an undo-log design would keep elsewhere.

9. InnoDB: redo log plus undo logs

MySQL's InnoDB is closer to the classical ARIES design. It updates rows in place in its clustered index (db6) and keeps the previous versions in separate undo logs, which serve both rollback and MVCC (readers needing an older version reconstruct it from undo records). Changes to data pages and to undo pages are both protected by the redo log, InnoDB's WAL. Crash recovery replays the redo log from the last checkpoint, which restores data pages and undo pages to their pre-crash state (repeating history), and then rolls back uncommitted transactions using their undo logs, often in the background after the server is already accepting connections. Torn pages are repaired from the doublewrite buffer. The innodb_flush_log_at_trx_commit setting plays the role of PostgreSQL's synchronous_commit: 1 (the default) flushes the redo log at every commit; 2 writes to the OS at commit and flushes about once a second; 0 does both about once a second.

10. Where C and I fit

This lesson is about the A and D of ACID, which the log implements. The other two letters use different machinery, and it helps to place them. Consistency in ACID means that each transaction takes the database from one state satisfying all declared constraints (keys, foreign keys, checks, db1) to another. The database enforces the declared ones, either per statement or, for deferred constraints, at commit; anything else (that debits equal credits, say) is the application's responsibility, which atomicity makes possible by ensuring the transaction's multiple writes stand or fall together. Isolation governs what concurrent transactions see of each other, implemented with locks and MVCC (sc5, db9). The two mechanisms meet at commit: a transaction's commit record is the single moment at which its changes become both durable and, for other transactions' new snapshots, visible. In PostgreSQL that moment is literally the update of its status in the commit log after the WAL flush.

A practical consequence: atomicity is per transaction, so the unit of all-or-nothing is whatever you put between BEGIN and COMMIT. Code that runs each statement in autocommit mode (the default in many drivers and ORMs) gets atomic statements, not atomic business operations. A transfer written as two autocommitted UPDATEs can still lose money in a crash between them, because each one committed on its own. The log can only protect the boundaries you declare.

11. Seeing the log in a running system

PostgreSQL exposes enough to watch this machinery work. SELECT pg_current_wal_lsn() before and after a batch, passed to pg_wal_lsn_diff(), gives the bytes of WAL the batch generated: inserting 100,000 narrow rows into a table with two indexes typically generates tens of megabytes, several times the logical data size, because every heap and index change is logged and full-page images appear for newly touched pages. pg_stat_wal reports WAL records, full-page images and bytes since the last reset, so the share of WAL that is full-page images is directly visible; a high share points at random-key writes or short checkpoint intervals. pg_waldump prints individual records: resource manager (Heap, Btree, Transaction), LSN, transaction id and description, which makes the abstract "log record" concrete. And commit latency is visible from the client: a single-row insert in its own transaction costs about one WAL flush, so timing a few thousand of them on a laptop SSD versus a cloud volume shows the flush latency that group commit and asynchronous commit exist to hide.

InnoDB exposes the equivalent through SHOW ENGINE INNODB STATUS (the LOG section lists the current LSN, the flushed LSN and the last checkpoint LSN) and performance-schema counters. In both systems, the gap between "current LSN" and "checkpoint LSN" is exactly the amount of log that crash recovery would replay right now, which is the number to watch when reasoning about recovery time.

12. Beyond crashes: archiving, PITR and replication

Crash recovery replays the WAL since the last checkpoint. Keep all WAL and you can do much more. Point-in-time recovery combines a base backup (a copy of the data files taken while the database runs, which may be internally inconsistent because pages changed during the copy) with the archived WAL from the start of the backup onwards. Restoring means putting the backup in place and replaying WAL, exactly like crash recovery, up to any chosen moment, such as one second before someone ran DELETE FROM orders without a WHERE clause. And replication (sc6) is the same stream sent continuously to standbys, which replay it as it arrives: a physical standby is a server in permanent recovery. The log is the database's single source of truth; the data files are a cache of it, rebuilt on demand.

Physical, logical and physiological logging

Log records can describe changes at different levels. Physical (value) logging records byte ranges of a page: "bytes 120-180 of page 7 were X, are now Y". It is simple and idempotent with pageLSNs, but large, and it cannot undo a change correctly if other changes have since moved things on the page. Logical logging records operations: "insert row (42, 'Ana') into table T". It is compact, but replaying it requires the database's structures to be consistent, and one logical operation may touch many pages (the heap, every index), so a crash mid-operation leaves partial state that logical replay cannot recognise. ARIES and most real systems use physiological logging: physical to a page, logical within it, such as "insert this tuple into slot 5 of page 7". Each record affects exactly one page, so pageLSN comparisons decide redo per page, while the in-page description stays compact and can be reversed logically even after the page has been reorganised. B-tree splits, which touch several pages, are logged as several page-level records, often as a "nested top action" that is never undone once complete, even if its transaction aborts, because other transactions may already be using the new pages.

What durability really depends on

Everything above assumes that when fsync returns, the data is on stable storage. That assumption has three layers of risk. The device: many drives have volatile write caches and may acknowledge writes before they reach persistent media; enterprise SSDs have capacitors to flush the cache on power loss, while some consumer drives do not and have historically ignored or mishandled flush commands. The file system and kernel: fsync semantics on errors were underspecified until recently, which the next section's incident exposed. The virtualisation layer: cloud block volumes replicate writes before acknowledging them, which is why a single fsync on a network volume may take a millisecond or more. PostgreSQL ships pg_test_fsync to measure flush latency on a given system, and a result that looks implausibly fast (tens of thousands of flushes per second on a consumer disk) usually means a cache is lying. Durability is a property of the whole stack, and a database can only be as durable as the cheapest component that claims a write is safe.

Checkpoint tuning as a write-amplification problem

Checkpoint frequency is really a write-amplification knob (db5). Each checkpoint must write every page dirtied since the previous one, once, however many times it was changed. A hot page updated 10,000 times in five minutes costs one page write per checkpoint, so longer intervals absorb more updates per write. Meanwhile, each checkpoint resets the full-page-write cycle, so the first change to each page afterwards logs 8 KB. A workload touching a million distinct pages per interval writes about 8 GB of full-page images per checkpoint whatever its logical change volume. Lengthening checkpoint_timeout from 5 to 30 minutes and raising max_wal_size accordingly can cut both page writes and WAL volume severalfold on write-heavy systems, at the cost of up to six times more WAL to replay after a crash. PostgreSQL logs a warning when checkpoints are triggered by WAL volume more often than checkpoint_warning (30 s by default), a sign max_wal_size is too small.

Commit latency, replication and the speed of light

With synchronous replication (sc6), a commit waits not only for the local WAL flush but also for one or more standbys to confirm they have received (or flushed, or applied, depending on synchronous_commit level) the commit record. Commit latency then includes a network round trip: under a millisecond within a data centre, tens of milliseconds across regions. Group commit still applies, so throughput can remain high, but each client sees the round trip. This is the physical root of the latency-versus-durability trade-off in PACELC (sc9): a commit that must survive the loss of a whole region must wait for another region to hear about it.

Distributed transactions and two-phase commit

Atomicity across two databases needs another layer. Two-phase commit (2PC) has a coordinator ask each participant to prepare: write all the transaction's records and a prepare record to its log and promise it can commit. Once all have voted yes, the coordinator logs its decision and tells everyone to commit. The protocol relies on the same WAL machinery: a prepared transaction must survive a participant crash, so its prepare record is flushed, and after recovery it is neither committed nor aborted until the coordinator says which. PostgreSQL supports this with PREPARE TRANSACTION. The weakness is blocking: if the coordinator fails after participants prepare, they hold locks until it returns. That is why large systems prefer to avoid distributed transactions (using sagas, outbox tables and idempotent consumers) or build them on consensus-replicated logs (sc9), as Spanner and CockroachDB do.

fsyncgate, 2018

In March 2018, Craig Ringer reported to the PostgreSQL hackers list a problem that shook assumptions about durability. PostgreSQL writes data pages through the OS page cache and relies on fsync at checkpoint time to make them durable, and it assumed, as LWN's write-up put it, that a successful fsync meant all data written since the last successful fsync had reached storage. But when a buffered write failed at the device level (a failing disk, a thin-provisioned volume that ran out of space), Linux file systems typically reported the error once and marked the affected pages clean, discarding the data. PostgreSQL's checkpointer saw the fsync error, logged it, and retried the checkpoint later; the retry's fsync succeeded, because there was nothing dirty left to fail, and the checkpoint completed. WAL older than that checkpoint could then be recycled, so the only copy of the lost changes disappeared too.

The fix, as the PostgreSQL wiki records, was to treat any fsync failure as fatal: PostgreSQL now PANICs, crashes, and on restart performs crash recovery from the last successful checkpoint, replaying WAL that still contains the changes. The change was backpatched to versions 9.4 through 11. Linux 4.13 had separately improved how writeback errors are tracked and reported. The incident is a sharp illustration of the deep section's point: the recovery algorithm was correct, but its foundation, the meaning of "flushed", was not what everyone thought.

Checkpoint spikes and WAL growth

Checkpoint-related production problems have recognisable shapes. I/O spikes every few minutes that hurt query latency usually mean checkpoints are triggered by WAL volume faster than they can spread their writes; the server log shows "checkpoints are occurring too frequently", and pg_stat_checkpointer (PostgreSQL 17+, previously pg_stat_bgwriter) shows many requested rather than timed checkpoints. Raising max_wal_size fixes it. WAL directory filling the disk means something is preventing WAL recycling: a failing archive_command, an inactive replication slot holding WAL for a standby that disappeared, or a very long checkpoint. This is one of the few ways a healthy PostgreSQL can stop entirely, since it cannot write WAL without space; monitor WAL directory size and replication slot lag, and set max_slot_wal_keep_size to bound what a dead slot can retain.

Long recovery after a crash

Crash recovery time is roughly WAL since the redo point divided by replay speed, and replay is single-threaded in PostgreSQL and often limited by random reads of pages not in cache. A database with a 30-minute checkpoint interval and heavy writes may need tens of minutes to start after a crash, during which it accepts no connections. The usual production answer is not faster recovery but avoiding the wait: a hot standby that is continuously replaying WAL can be promoted in seconds, and the crashed primary recovers at leisure. Plan checkpoint settings together with the failover design and measure recovery time in a drill rather than discovering it during an outage.

Durability settings that quietly weaken guarantees

Several settings trade durability for speed and are sometimes left on by accident. fsync = off in PostgreSQL disables flushing entirely and can corrupt the database on a crash; it is only for throwaway test instances. full_page_writes = off risks unrecoverable torn pages unless the storage guarantees atomic 8 KB writes. synchronous_commit = off is safe for integrity but loses recent commits. In MySQL, innodb_flush_log_at_trx_commit = 2 and sync_binlog = 0 can lose up to a second of transactions on an OS crash. Audit these as part of production readiness, and use the per-transaction forms (async commit for logs and metrics only) rather than weakening the whole server.

WAL as an integration point

Because the WAL is a complete, ordered record of changes, it has become the integration point for much of the modern data stack. Logical decoding in PostgreSQL turns WAL into a stream of row-level inserts, updates and deletes that change-data-capture tools such as Debezium publish to Kafka, feeding search indexes, caches, warehouses and, increasingly, vector indexes that must stay in sync with source documents for retrieval-augmented generation. The same ordering guarantees that make recovery correct make these consumers correct: they see committed changes, in commit order, exactly once if they track the LSN they have processed. The operational cost is the same as for replication: a consumer that stops consuming holds its replication slot and makes WAL accumulate.

"""A toy steal/no-force engine with a WAL and ARIES-style recovery (analysis, redo, undo)."""

log = []            # the WAL: list of dicts, index = LSN
disk = {"A": 100, "B": 200, "C": 300}       # values on 'disk' pages
disk_lsn = {"A": -1, "B": -1, "C": -1}      # pageLSN: last log record applied to the disk copy

def write(txn, page, new, buffer):
    old = buffer.get(page, disk[page])
    log.append({"lsn": len(log), "txn": txn, "type": "update", "page": page, "old": old, "new": new})
    buffer[page] = new

def commit(txn):
    log.append({"lsn": len(log), "txn": txn, "type": "commit"})   # flushed before we say OK

def flush_page(page, buffer):            # 'steal': a dirty page may hit disk before commit
    disk[page] = buffer[page]
    disk_lsn[page] = max(r["lsn"] for r in log if r.get("page") == page)

# ---- normal operation, then a crash ----
buf = {}
write("T1", "A", 150, buf)               # T1: move 50 from A to B
write("T1", "B", 250, buf)
commit("T1")
write("T2", "C", 999, buf)               # T2 starts, never commits
flush_page("C", buf)                     # uncommitted change stolen to disk
write("T2", "A", 0, buf)
print("disk at crash :", disk, "| T1 committed but its pages never reached disk")

# ---- recovery ----
committed = {r["txn"] for r in log if r["type"] == "commit"}
losers = {r["txn"] for r in log if r["type"] == "update"} - committed
print("analysis      : winners", sorted(committed), "losers", sorted(losers))

for r in log:                             # redo: repeat history for ALL updates
    if r["type"] == "update" and disk_lsn[r["page"]] < r["lsn"]:
        disk[r["page"]] = r["new"]; disk_lsn[r["page"]] = r["lsn"]
print("after redo    :", disk)

for r in reversed(log[:]):                # undo losers, newest first, logging CLRs
    if r["type"] == "update" and r["txn"] in losers:
        disk[r["page"]] = r["old"]
        log.append({"lsn": len(log), "txn": r["txn"], "type": "CLR", "page": r["page"], "undid": r["lsn"]})
print("after undo    :", disk)
print("CLRs written  :", [(r["lsn"], r["page"], "undid", r["undid"]) for r in log if r["type"] == "CLR"])

What to look for.

  1. disk at crash shows A = 100 and B = 200 even though T1 committed (no-force: its pages were never written) and C = 999 although T2 never committed (steal: the page was evicted early).
  2. Analysis finds winners ['T1'] and losers ['T2'].
  3. After redo, A = 0: redo repeated T2's change to A (LSN 4) as well as T1's. C was skipped because its pageLSN (3) showed the change was already on disk.
  4. After undo, A = 150, B = 250, C = 300, with CLRs at LSNs 5 and 6 recording the two undo steps.

Then add a checkpoint record after LSN 2 that stores disk_lsn, flush pages A and B at that point, and start redo from the checkpoint: notice that records 0 and 1 no longer need to be read at all.

Diagnose and design: losing the last second of orders

An e-commerce team runs PostgreSQL on a cloud VM with a network block volume. To cut commit latency from 4 ms to 0.3 ms during a sale, someone set synchronous_commit = off server-wide months ago. After a host failure, the database restarted cleanly, but 37 customers have payment confirmations from the payment provider with no matching order rows. (1) Explain exactly what happened. (2) Was the database corrupted? (3) Propose a configuration that keeps most of the latency win without losing paid orders.

Answer

(1) With asynchronous commit, the server acknowledged each order as committed once its commit record was in the in-memory WAL buffer; the WAL writer flushed it to the volume a fraction of a second later. The host failed inside that window, so the most recent commits, which clients had been told succeeded and which had triggered payment capture, were never on durable storage. Crash recovery replayed the WAL that was durable and stopped where it ended. The window is bounded, roughly up to three times wal_writer_delay (about 600 ms with defaults), which at sale traffic was enough for 37 orders.

(2) No. Recovery replayed a consistent prefix of history: every transaction is either fully present or fully absent, constraints hold, indexes match tables. The data is consistent; it is just missing the last few acknowledged commits. That is the documented contract of asynchronous commit.

(3) Restore synchronous_commit = on as the server default and use SET LOCAL synchronous_commit = off only in transactions that can be lost (page-view events, recommendation logs, LLM debug payloads). Keep orders and payments synchronous. Recover most of the latency by other means: group commit already amortises flushes under load (throughput was never the problem, latency per order was); use a volume type with lower flush latency or provisioned IOPS; make the payment flow idempotent with an outbox: write the order and an "awaiting capture" row in one synchronous transaction before calling the payment provider, so a crash can never leave a captured payment without an order. Finally, reconcile: a job comparing provider confirmations with order rows would have caught the 37 the same day.
