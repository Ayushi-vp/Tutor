A hospital's scheduling system enforces one rule: at least one doctor must be on call at all times. The "go off call" button runs a short transaction: count the doctors currently on call; if there are at least two, mark me as off call. Alice and Bob are the only two on call one evening, and both feel unwell. They press the button within the same second. Each transaction counts two doctors on call, each concludes it is safe, and each updates its own row. Both commit. Nobody is on call.

No row was written by both transactions, so no lock conflict ever happened. Each transaction, run alone, was correct. The bug exists only in the interleaving. This example, from Cahill and colleagues' work on serializable snapshot isolation and used as the opening example of Dan Ports and Kevin Grittner's 2012 paper on implementing it in PostgreSQL, is called write skew, and it happens under the default settings of most databases. The PostgreSQL developers built a whole new serializable mode for version 9.1 largely to catch anomalies like it.

The engineering-at-scale lesson sc5 introduced isolation levels, the anomalies each one allows, and a practical toolkit. This lesson goes underneath. What precisely does "serializable" mean, and how can you test a given interleaving for it by drawing a graph? How do locks implement it, and why must transactions acquire all their locks before releasing any? What exactly is stored in a PostgreSQL row so that two transactions can see two different values of it at the same moment? How does the database catch write skew without locking every row anyone reads? And what are the tools an application developer actually reaches for: atomic updates, optimistic version checks, SELECT FOR UPDATE, SKIP LOCKED queues and deadlock-safe lock ordering?

These questions matter more, not less, in AI systems. Agents that call tools against a database, pipelines that update feature tables while models read them, and evaluation jobs that claim work items from a shared queue are all concurrent writers. The mechanisms in this lesson decide whether they are safe.

The goal: as if one at a time

The simplest way to make concurrent transactions safe is not to have any: run them one after another, a serial execution. Every transaction then sees a database untouched by anyone mid-flight, and if each one preserves the business rules, the database always does. The trouble is throughput: a transaction waiting for a disk read or a network round trip would hold up everyone.

So databases interleave transactions and aim for the next best thing: a result that is indistinguishable from some serial order. That property is serializability. It does not promise any particular order (Alice-then-Bob or Bob-then-Alice), only that there is one. In the doctors example, either serial order would leave one doctor on call, so the actual interleaving, which left none, was not serializable.

Two families of mechanisms

There are two broad ways to achieve serializability, and real databases mix them. The pessimistic way prevents conflicts before they happen: a transaction must take a lock on data before using it, and conflicting transactions wait. Think of a library where you must sign out a book before reading it; if someone else has it, you wait. The optimistic way lets transactions proceed freely and checks for conflicts at the end, aborting and retrying a transaction whose view turned out to be stale. Think of a shared document where everyone edits a copy and the second person to save is told "the file changed, please merge".

A third idea changes the trade-off for reads: multi-version concurrency control (MVCC). Instead of one copy of each row, the database keeps several versions, each stamped with the transaction that created it. A reader is given a snapshot, a consistent picture of the database as of a moment, and reads the versions that were current at that moment. Writers create new versions without disturbing readers of old ones. The slogan, in PostgreSQL's documentation, is that reading never blocks writing and writing never blocks reading.

The analogy for MVCC is a wiki with page history. Editors save new revisions; a reader who opened the page at 10:00 keeps reading the 10:00 revision even if someone saves at 10:01. The cost is that old revisions pile up and must be cleaned once nobody can still be reading them (PostgreSQL's VACUUM, db10), and that "I read the 10:00 revision and decided based on it" is exactly what makes write skew possible: the decision was based on a picture that changed before the write landed.

Where each engine sits

PostgreSQL uses MVCC for all reads, row locks for writes, and, at the SERIALIZABLE level only, a detector for dangerous patterns (SSI). MySQL's InnoDB uses MVCC for plain reads and locks, including locks on gaps between index entries, for writes and locking reads. Older systems and some current ones (SQL Server by default, DB2) rely mainly on locking. Knowing which machinery is underneath tells you which anomalies to expect and which tools fix them.

1. Schedules and conflicts

Model each transaction as a sequence of reads and writes of data items: r1(x) means transaction T1 reads x, w2(y) means T2 writes y. A schedule is an interleaving of several transactions' operations, keeping each transaction's own order. Two operations conflict if they belong to different transactions, touch the same item, and at least one is a write: read-write, write-read and write-write pairs. Two reads never conflict. The order of conflicting operations is what determines the outcome; non-conflicting adjacent operations can be swapped without changing anything anyone reads or the final state.

A schedule is conflict serializable if swapping adjacent non-conflicting operations can turn it into a serial schedule. That is hard to check by trial, but there is an equivalent test. Draw a precedence graph: one node per transaction, and an edge Ti → Tj whenever an operation of Ti conflicts with a later operation of Tj. The schedule is conflict serializable if and only if the graph has no cycle, and any topological order of the graph is an equivalent serial order.

2. Precedence graphs, worked

Take the lost update: r1(x) r2(x) w1(x) w2(x). Both read x, then both write it. List the conflicting pairs in order. r1(x) before w2(x): edge T1 → T2. r2(x) before w1(x): edge T2 → T1. w1(x) before w2(x): T1 → T2. The graph has edges both ways, a cycle, so the schedule is not serializable. Concretely: if x starts at 100 and each transaction adds 10, both read 100 and both write 110; any serial order would give 120.

Now r1(x) w1(x) r2(x) w2(y). Conflicts: r1(x)/w1(x) are the same transaction, so no edge. w1(x) before r2(x): T1 → T2. r1(x) before... nothing of T2 writes x. y is only touched by T2. One edge, no cycle: serializable, equivalent to T1 then T2. The lab's checker prints exactly these two verdicts.

Databases do not build these graphs for every schedule; they enforce rules that make cycles impossible (locking) or detect the patterns that cycles require (SSI). But the graph is the definition everything else is measured against, and drawing one is the fastest way to answer "is this interleaving safe?" in an interview.

3. Locks, lock modes and two-phase locking

A lock manager grants locks on items in modes. A shared (S) lock is for reading; many transactions can hold S on the same item. An exclusive (X) lock is for writing; it is compatible with nothing. A request that conflicts with a held lock waits in a queue for that item. Locks alone do not guarantee serializability: a transaction that locks x, reads it, unlocks it, and later locks y could interleave badly with another. The protocol that makes locking correct is two-phase locking (2PL): every transaction has a growing phase in which it acquires locks and a shrinking phase in which it releases them, and it never acquires a lock after its first release.

Why does it work? If T1 → T2 is an edge, T1 held a lock on some item that T2 had to wait for, so T1 released a lock before T2 acquired it. If there were a cycle T1 → T2 → T1, T1 would have released a lock before T2 acquired one, and T2 released one before T1 acquired one; following that back, T1 would have to acquire a lock after releasing one, which 2PL forbids. The point at which each transaction holds all its locks (its lock point) defines the equivalent serial order.

Plain 2PL still allows a transaction to release a write lock before committing, letting another read its uncommitted data; if the first then aborts, the reader must abort too, a cascading abort. Strict 2PL holds all exclusive locks until commit or abort, and rigorous 2PL holds every lock until then. Lock-based databases use strict or rigorous 2PL, which is why, in them, a transaction that updates a row blocks everyone else from that row until it finishes.

Real lock managers lock at several granularities: rows, pages, tables. To check a table-level request against thousands of row locks cheaply, transactions first take intention locks on the table: IS ("I will take S locks on some rows") or IX ("I will take X locks on some rows"). A request for a full-table S lock then only needs to check for IX holders on the table. PostgreSQL's table-level lock modes are a richer version of the same idea, with eight modes from ACCESS SHARE (taken by every SELECT) to ACCESS EXCLUSIVE (taken by DROP TABLE and many ALTER TABLE forms), which is why a long-running SELECT can block an ALTER TABLE, and an ALTER TABLE waiting in the queue then blocks every later SELECT on that table (db14 returns to this).

4. Phantoms and range locks

Row locks protect rows that exist. They do nothing about rows that do not exist yet. A transaction that runs SELECT COUNT(*) FROM doctors WHERE on_call twice can get different answers if another transaction inserts a new on-call doctor in between: a phantom. Under strict 2PL with row locks only, the counting transaction locked the rows it saw, but the new row was not among them.

Preventing phantoms requires locking the condition, not just the rows. True predicate locks ("lock everything matching on_call = true") are expensive to check, so databases approximate them with index ranges. InnoDB uses next-key locks: when a locking read or a write scans an index, it locks each index record it visits and the gap before it, and it locks the gap after the last record. Another transaction trying to insert a key into a locked gap waits. A range query WHERE age BETWEEN 20 AND 30 FOR UPDATE on an indexed age column therefore blocks inserts of any age between the neighbouring existing values. Without an index on the column, the scan touches every row, and next-key locking effectively locks the whole table. These gap locks are the reason InnoDB's REPEATABLE READ prevents phantoms for locking reads, and the reason inserts in InnoDB sometimes wait or deadlock for no apparent reason: they are waiting on a gap someone else's range scan locked.

5. MVCC in PostgreSQL: row versions

PostgreSQL never updates a row in place. An UPDATE writes a new row version (a tuple) and marks the old one as replaced; a DELETE marks the current version as deleted. Each tuple header (db5) carries two transaction ids: xmin, the transaction that created this version, and xmax, the transaction that deleted or replaced it (0 if none yet). Every transaction that writes gets a 32-bit transaction id (xid) when it first writes, from an increasing counter, and the commit log (db8) records whether each xid committed or aborted. You can see these hidden columns: SELECT xmin, xmax, * FROM accounts.

Follow one account row through three transactions. Transaction 90 inserted it with balance 100 long ago and committed. Transaction 101 updates the balance to 150: the original tuple gets xmax = 101 and a new tuple (balance 150, xmin = 101, xmax = 0) is written. 101 commits. Transaction 102 then updates it to 175: the 150-tuple gets xmax = 102 and a new tuple (175, xmin = 102) is written, but 102 has not committed yet. On disk there are now three versions of one logical row:

6. Snapshots and the visibility rule, traced

Which version does a query see? It depends on its snapshot, which PostgreSQL represents with three things (shown by SELECT pg_current_snapshot() as xmin:xmax:xip_list): xmin, the oldest transaction still running when the snapshot was taken; xmax, the first transaction id not yet assigned at that moment; and xip, the list of ids that were in progress. A transaction id counts as "in the past" for the snapshot if it is below xmax, not in the in-progress list, and recorded as committed.

The visibility rule is then: a tuple is visible if its xmin is in the past (its creator committed before the snapshot) and its xmax is not (it was not deleted or replaced by a transaction that committed before the snapshot; an empty, aborted or still-running xmax does not count). Apply it to two snapshots:

  • Snapshot S1, taken before 101 committed (its xmax is 101, so 101 and later are invisible). v1: xmin 90 is in the past; xmax 101 is not, so v1 is visible. v2: xmin 101 is not in the past, invisible. v3: invisible. S1 sees 100.
  • Snapshot S2, taken after 101 committed, while 102 runs (xmax 103, in-progress list {102}). v1: xmax 101 is in the past, so v1 was replaced: invisible. v2: xmin 101 in the past; xmax 102 is in the in-progress list, so not in the past: visible. v3: xmin 102 is in progress: invisible. S2 sees 150.

Transaction 102 itself sees 175, because a transaction always sees its own changes. The lab's visibility function reproduces S1 → [100] and S2 → [150]. Two queries running at the same instant can thus see different balances, each a consistent picture: S1's world in which 101 has not happened yet, and S2's in which it has but 102 has not.

7. Isolation levels on top of MVCC

The isolation levels differ mainly in when snapshots are taken and what happens on write conflicts. At PostgreSQL's default READ COMMITTED, each statement takes a fresh snapshot, so a transaction's second SELECT can see rows committed after its first: non-repeatable reads are possible. When an UPDATE finds that its target row was changed by a concurrent transaction that has since committed, it waits for that transaction, then re-reads the newest version and re-checks its WHERE clause against it before updating. That is why UPDATE accounts SET balance = balance - 50 WHERE id = 1 is safe from lost updates even at READ COMMITTED: the arithmetic is applied to the latest committed balance.

At REPEATABLE READ, the transaction takes one snapshot at its first statement and uses it throughout: every read is repeatable and no phantoms appear in its reads. If it tries to update a row that a concurrent transaction changed and committed after the snapshot, it cannot re-read (that would break the snapshot), so it fails with could not serialize access due to concurrent update, and the application must retry. This level is snapshot isolation (SI), and it still allows write skew: the doctors example passes, because the two transactions update different rows and neither sees the other's write.

At SERIALIZABLE, PostgreSQL runs snapshot isolation plus serializable snapshot isolation (SSI) checks, described in the deep section, and aborts one transaction of any pattern that could be non-serializable. In InnoDB, the default is REPEATABLE READ, where plain SELECTs use a transaction-long snapshot but locking reads and writes see the latest committed data and take next-key locks, a hybrid that is neither pure snapshot isolation nor pure 2PL.

8. Optimistic concurrency control in the application

Many conflicts span more than one database transaction: a user opens an edit form, spends five minutes typing, and saves. Holding a database lock for five minutes is out of the question. Optimistic concurrency control (OCC) handles it with a version column. Read the row and its version when the form opens. On save, make the update conditional:

UPDATE doc SET body = $1, version = version + 1
WHERE id = $2 AND version = $3;   -- $3 = the version read when the form opened

If nobody else saved in the meantime, the version still matches, one row is updated and the version increments. If someone did, the version has moved on, zero rows are updated, and the application tells the user to reload and merge. The lab runs two writers who both read version 0: A's update affects 1 row, B's affects 0, and the final row holds A's edit with version 1; B's edit was not silently lost. The check-and-set is atomic because the UPDATE takes the row lock and evaluates the WHERE clause on the latest version. HTTP has the same pattern with ETags and If-Match headers, and many ORMs implement it automatically (JPA's @Version, for example).

OCC shines when conflicts are rare and the work before the check is cheap to redo. It degrades when conflicts are frequent: if ten workers race for the same row, nine of them do all their work and then fail. Then pessimistic locking, which makes them queue, wastes less.

9. Pessimistic row locks: SELECT FOR UPDATE and friends

When a transaction must read a row, decide, and write it back, and the decision must not be invalidated, lock the row as you read it: SELECT balance FROM accounts WHERE id = 1 FOR UPDATE. Other transactions trying to update, delete or lock that row wait until this transaction commits or aborts; plain SELECTs still read their snapshot unhindered. PostgreSQL offers four strengths, each blocking a different set of others: FOR UPDATE (strongest; taken by DELETE and by updates of key columns), FOR NO KEY UPDATE (taken by ordinary UPDATEs that do not change a unique key), FOR SHARE and FOR KEY SHARE (taken by foreign-key checks, db1, so inserting a child only conflicts with deleting the parent or changing its key, not with ordinary updates of the parent). Choosing the weakest sufficient mode reduces blocking.

Two modifiers change what happens when a row is already locked. NOWAIT fails immediately with an error instead of waiting, which suits interactive "someone else is editing this" checks. SKIP LOCKED silently skips locked rows, which is exactly what a job queue needs:

BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'pending'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- process the 10 jobs
UPDATE jobs SET status = 'done' WHERE id = ANY($ids);
COMMIT;

Ten workers running this concurrently each get a different set of ten jobs and never wait on each other: each skips rows another has locked. If a worker crashes, its transaction aborts, its locks vanish, and its jobs become claimable again. For long jobs, a variant commits a status = 'running', lease_until = now() + interval '5 minutes' claim and lets another worker reclaim expired leases, avoiding long-held transactions. A partial index on pending jobs (db6) keeps the scan cheap as completed jobs accumulate.

The atomic update is often better than any explicit lock. UPDATE events SET remaining = remaining - 1 WHERE id = $1 AND remaining > 0 reads, checks and writes in one statement under the row lock, and the affected row count says whether a ticket was obtained. No read-then-write window exists for anyone to slip into.

10. Deadlocks: detection and prevention

Locking introduces waiting, and waiting introduces the possibility of a cycle. Transaction T1 locks account 1, T2 locks account 2, then T1 requests account 2 (waits for T2) and T2 requests account 1 (waits for T1). Neither can proceed: a deadlock. Databases model it with a wait-for graph, an edge from each waiting transaction to the one holding the lock it wants; a deadlock is a cycle.

PostgreSQL does not check for cycles on every wait, which would be costly for the common case of short waits. Instead a backend that has waited for a lock longer than deadlock_timeout (1 second by default) runs the detector; if it finds a cycle, it aborts one transaction with ERROR: deadlock detected, and the log shows which statements were involved. InnoDB checks for cycles immediately when a transaction waits (with innodb_deadlock_detect, on by default) and rolls back the transaction that has done the least work. Separately, InnoDB's innodb_lock_wait_timeout (50 seconds by default) and PostgreSQL's lock_timeout (off by default) bound ordinary waits.

Prevention is the application's job. Lock rows in a consistent order: for a transfer between accounts 1 and 2, always lock the lower id first, for example SELECT … WHERE id IN (1, 2) ORDER BY id FOR UPDATE, so no two transfers can hold the locks in opposite orders. Keep transactions short, touch fewer rows, avoid user interaction or network calls inside transactions, and index the columns used to find rows to lock (so InnoDB locks fewer gaps). Then accept that deadlocks and serialization failures will still happen occasionally and write transactions so they can be retried safely: wrap them in a loop that retries on SQLSTATE 40P01 (deadlock) and 40001 (serialization failure), with a small randomised backoff.

11. A worked example: claiming evaluation jobs safely

An AI team runs a nightly evaluation of 20,000 prompts against three models, with 50 worker processes calling model APIs. Each job is a row: eval_job(id, model, case_id, status, lease_until, attempts, result). The design follows the lesson. Workers claim batches with FOR UPDATE SKIP LOCKED and immediately commit a lease (status 'running', lease_until five minutes ahead), so no database transaction stays open while a model call takes seconds. A worker that finishes writes the result with an optimistic guard, UPDATE eval_job SET status = 'done', result = $1 WHERE id = $2 AND status = 'running' AND lease_until > now(), so a worker whose lease expired (and whose job was reclaimed by someone else) cannot overwrite the newer result. A sweeper resets expired leases with the same SKIP LOCKED pattern, incrementing attempts and moving jobs that fail three times to 'dead'. Aggregate scores are computed afterwards from completed rows rather than incremented in a shared counter row, which would be a hot spot with 50 writers. Every mechanism in this lesson appears: row locks, skip-locked claiming, short transactions, optimistic checks and avoidance of a single contended row.

How SSI catches write skew without blocking

Serializable snapshot isolation rests on a theorem from Fekete and colleagues, quoted in Ports and Grittner's paper: every cycle in the serialization graph of a snapshot-isolation execution contains two consecutive rw-antidependency edges, T1 → T2 → T3, where an rw-antidependency T1 → T2 means T1 read a version of something and a concurrent T2 wrote a newer version that T1 did not see (so T1 must come before T2). In the doctors example, Alice's transaction read Bob's on-call row and Bob's transaction wrote a new version of it, and vice versa: two rw-antidependencies forming a cycle. SSI tracks reads with SIREAD locks, which block nothing but record what each serializable transaction read (rows, index pages for ranges, or whole relations when the lock table needs to save space). When a write meets a SIREAD lock held by a concurrent transaction, an rw-antidependency is recorded. If any transaction ends up with both an incoming and an outgoing rw-antidependency, the "dangerous structure", one transaction is aborted with a serialization failure. Because the check looks for the structure rather than a complete cycle, and because locks may be coarsened, there are false positives; the authors judged that acceptable, reporting serialization failure rates well under 1% on their benchmarks and a throughput cost below 7% relative to snapshot isolation (about 5% on a CPU-bound transaction-processing workload), while a strict-2PL implementation was far slower on read-heavy mixes.

Read-only transactions and deferrable snapshots

The paper's main extension concerns read-only transactions, which are common and often long. A read-only transaction can only be the first transaction (T1) of a dangerous structure, and the authors proved it can only participate in an anomaly if the structure's T3 committed before the read-only transaction took its snapshot. PostgreSQL uses this to ignore many false positives, and further introduces safe snapshots: a snapshot for which no such anomaly is possible. A transaction declared SERIALIZABLE READ ONLY DEFERRABLE waits until it can obtain a safe snapshot and then runs with no SSI tracking at all and no possibility of failure, which is ideal for long reports and backups (pg_dump --serializable-deferrable uses it). Declaring read-only transactions as such is therefore a real performance optimisation at the serializable level.

Snapshot isolation anomalies beyond write skew

Write skew is the famous SI anomaly, but not the only one. The read-only anomaly (Fekete, O'Neil and O'Neil, 2004) shows that even a transaction that writes nothing can observe a state inconsistent with any serial order: with a batch-processing transaction T2 and a receipts transaction T3, a read-only report T1 can see T3's effect without T2's although T2 must logically precede T3. This is the paper's Example 2 and is why SSI must track read-only transactions too (unless deferrable). In practice, most applications never notice these anomalies, but the ones that do are precisely the ones enforcing invariants across rows: scheduling constraints, balances across accounts, uniqueness rules that cannot be expressed as a unique index. For those, SERIALIZABLE (with retries) or explicit locking of the rows the decision depends on is required.

Materializing conflicts

When an invariant spans rows that the transactions do not both write, a classic technique is to materialize the conflict: introduce a row that every relevant transaction must write, turning write skew into an ordinary write-write conflict that snapshot isolation and locking already handle. For the doctors, add a shift row per shift and have every "go off call" transaction SELECT … FROM shift WHERE id = $1 FOR UPDATE before counting; the two transactions now serialise on the shift row. For meeting-room bookings, PostgreSQL's exclusion constraints (db6) express "no overlapping bookings" directly. Advisory locks (pg_advisory_xact_lock(key)) are a third option: application-defined locks on arbitrary integers, useful when the conflict has no natural row, such as "only one rebuild of tenant 42's index at a time".

The cost side of MVCC

MVCC's convenience has costs that show up as operational work (db10). Every update writes a whole new tuple and, unless it qualifies for a HOT update, new index entries; old versions remain until vacuum removes those that no snapshot can still see. The oldest running snapshot in the whole database sets that horizon, so one long-running transaction (or an idle-in-transaction session, or an abandoned replication slot) prevents cleanup everywhere, and tables bloat. Transaction ids are 32-bit, so PostgreSQL must periodically freeze old tuples to keep ids from wrapping around, and if vacuum falls far enough behind, it stops accepting writes to protect itself. InnoDB's undo-log design moves the same costs elsewhere: long transactions make the undo history ("history list length") grow and slow down reads that must reconstruct old versions. Either way, the rule for applications is the same: keep transactions short.

Write skew in the wild

Ports and Grittner's motivation was practical. Kevin Grittner worked for the Wisconsin court system, where, as the paper describes, data integrity was critical (warrant status information, regulatory requirements) and snapshot-isolation anomalies were a real threat because they cause silent corruption. With hundreds of tables, more than twenty programmers writing new queries, and queries generated by object-relational frameworks, analysing every pair of transactions for possible write skew and keeping that analysis up to date was simply not feasible; the database had to guarantee serializability itself. Their SSI implementation shipped in PostgreSQL 9.1 (2011). The general lesson for teams is to audit any business rule that is enforced by "read some rows, check, then write a different row": double-booking checks, spending limits summed across transactions, inventory reserved across warehouses, quotas per tenant. Each is a write-skew candidate at READ COMMITTED and REPEATABLE READ. The fixes are SERIALIZABLE with retries, a materialized conflict row, a constraint the database can enforce, or an atomic conditional update.

Lock contention and how to see it

In PostgreSQL, pg_stat_activity shows each session's state and what it is waiting for (wait_event_type = 'Lock'), and pg_blocking_pids(pid) returns who is blocking it; joining these gives a live blocking tree. pg_locks lists every held and awaited lock. Setting log_lock_waits = on logs any wait longer than deadlock_timeout, which surfaces contention long before it becomes an outage. Typical findings: a hot row (a counter, a "last updated" timestamp on a parent row touched by every child insert, a global sequence-like row); a long transaction holding row locks while it calls an external service; and DDL waiting for an ACCESS EXCLUSIVE lock behind a long query, while every new query queues behind the DDL. That last pattern turns a harmless migration into an outage; always run DDL with a short lock_timeout and retry (db14).

Idle in transaction

One of the most damaging and common problems is a session that opened a transaction and then stopped sending commands: an application that began a transaction, made a slow HTTP call, and is waiting; a developer's console session left open; a connection-pool bug that returns connections mid-transaction. Its locks block writers, and its snapshot holds back vacuum across the database. PostgreSQL's idle_in_transaction_session_timeout terminates such sessions after a set time, and pg_stat_activity shows them with state idle in transaction and an old xact_start. Setting a timeout of a minute or so for application roles is a cheap safeguard.

Retry loops done right

Serialization failures and deadlocks are part of normal operation at higher isolation levels and under contention, so the application must retry. A correct retry wraps the whole transaction, re-executing reads as well as writes (retrying only the failed statement inside an aborted transaction is impossible, since the transaction is dead); it catches only the retryable SQLSTATEs (40001, 40P01); it uses capped exponential backoff with jitter; and it gives up after a few attempts with a clear error. Side effects outside the database (sending an email, charging a card, calling an LLM) must not be repeated by retries, so they either happen after commit or are made idempotent with keys. Metrics on retry counts per transaction type reveal contention hot spots early.

Concurrency in AI applications

Agentic systems are concurrency problems with long pauses. An agent that reads state, thinks for ten seconds while a model generates, then writes, must never hold a transaction or row lock across the model call; it should use optimistic version checks or idempotency keys when it writes back, exactly like the edit-form pattern. Multiple agents updating the same shared memory or task board are a write-skew risk: two planners each see a task unassigned and assign it to themselves; claim tasks with UPDATE … WHERE assignee IS NULL (an atomic conditional update) or SKIP LOCKED. Feature pipelines that rewrite tables while online models read them rely on MVCC to give readers a consistent snapshot; swapping in a newly built table inside one transaction (rename or partition exchange) makes the change atomic for readers.

# Part 1: conflict serializability via a precedence graph
def serializable(schedule):
    """schedule: list of (txn, op, item), op in 'r'/'w'. Returns (ok, edges)."""
    edges = set()
    for i, (t1, op1, x1) in enumerate(schedule):
        for t2, op2, x2 in schedule[i + 1:]:
            if t1 != t2 and x1 == x2 and "w" in (op1, op2):
                edges.add((t1, t2))                   # t1's op must come before t2's
    txns = sorted({t for t, _, _ in schedule})
    for order in permutations(txns):                  # any topological order = OK
        pos = {t: i for i, t in enumerate(order)}
        if all(pos[a] < pos[b] for a, b in edges):
            return True, sorted(edges), order
    return False, sorted(edges), None

    return v["xmax"] is None or not done_before(v["xmax"])

snaps = {"snapshot before 101 commits": {"xmax": 101, "active": set()},
         "snapshot after 101, while 102 runs": {"xmax": 103, "active": {102}}}
for name, snap in snaps.items():
    print(f"{name:<36}", [v["val"] for v in versions if visible(v, snap)])

What to look for.

  1. The lost update has edges both ways, [('T1', 'T2'), ('T2', 'T1')], and no serial order; the second schedule has one edge and the order ('T1', 'T2').
  2. The snapshot taken before transaction 101 committed sees [100]; the one taken while 102 is running sees [150]. Exactly one version is visible to each snapshot.
  3. Both writers read version 0; A's conditional update changes 1 row, B's changes 0, and the final row is A's edit at version 1. B's application now knows it must reload and merge.

Diagnose and fix: double-booked meeting rooms

A booking service runs, at PostgreSQL's default READ COMMITTED: SELECT count(*) FROM booking WHERE room_id = $1 AND tstzrange(start_at, end_at) && tstzrange($2, $3); if 0, INSERT INTO booking …. Under load, about one in a thousand bookings overlaps another. (1) Name the anomaly and explain why no lock prevents it. (2) Would REPEATABLE READ fix it? (3) Give two robust fixes and one you would avoid.

Answer

(1) It is a phantom-driven write skew: two transactions each check that no overlapping booking exists, see none, and each insert a new row. They write different (new) rows, so there is no row to lock and no write-write conflict; the condition they checked was invalidated by an insert neither could see.

(2) No. REPEATABLE READ in PostgreSQL is snapshot isolation: both transactions still read snapshots without the other's insert, and inserts of different rows do not conflict. It only makes things more consistent within each transaction, not across them.

(3) Fix A, let the database enforce the rule: an exclusion constraint, EXCLUDE USING gist (room_id WITH =, tstzrange(start_at, end_at) WITH &&) (needs the btree_gist extension for the equality part). The second overlapping insert fails with a constraint violation regardless of isolation level or interleaving; the application turns it into "room no longer available". This is the best fix: it is declarative, race-free and also protects against other writers. Fix B, SERIALIZABLE with retries: SSI detects the rw-antidependencies (each transaction's range read conflicts with the other's insert, via SIREAD locks on the index range) and aborts one; the retry sees the other booking and declines. Correct, but every booking path must run serializable and retry. Fix C, materialize the conflict: SELECT … FROM room WHERE id = $1 FOR UPDATE before checking, so bookings for the same room serialise; correct and simple, at the cost of serialising all bookings per room.

Avoid: an application-level check with a cache or a "SELECT then INSERT" in a single statement without a constraint (still racy), or a global lock table, which serialises all bookings everywhere.
