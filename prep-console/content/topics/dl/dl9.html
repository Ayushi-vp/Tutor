You have a model you want to train: 7 billion parameters, a couple of trillion tokens of text. Two facts about the job are immediately awkward. The first is time. Training costs roughly 6 floating-point operations per parameter per token (gpu3), so this job is 6 × 7×10⁹ × 2×10¹² = 8.4×10²² operations. A single H100 GPU sustaining 400 teraFLOP/s (about 40% of its peak, a realistic figure) would need 2.1×10⁸ seconds: 6.7 years. The second fact is memory. Each parameter carries not just its own 2 bytes but a gradient, a float32 master copy and Adam's two moments, 16 bytes in all; times 7 billion is 112 gigabytes, more than the 80 GB of the largest GPU, before a single activation has been stored. So you buy eight GPUs, wrap your model in the standard data-parallel wrapper, launch — and every one of them runs out of memory in the first step. More GPUs did not make the model fit, because each one holds a complete copy.

Solving both problems at once is what distributed training is about, and the solutions have names that interviewers use as shorthand: data parallelism (many replicas, different data), tensor parallelism (split each layer across GPUs), pipeline parallelism (split the layers into stages), and combinations of them called 3D parallelism. Each buys something different and pays with communication: how many bytes must cross which link, how often, and whether the GPU can do other work while waiting. A 1,024-GPU cluster brings the 6.7 years down to 2.4 days, but only if the GPUs spend most of their time computing rather than waiting for each other, and the fastest link in the machine (NVLink between GPUs in one server, about 450 GB/s each way) is nine times faster than the network between servers (50 GB/s each way). Getting the right traffic onto the right link is the entire game.

It is also where the "systems" half of an AI-engineer interview lives. Questions like "how would you train a 70B model on 64 GPUs?" have answers built from a few pieces of arithmetic that can be done on a whiteboard: bytes per parameter, all-reduce volume, pipeline bubble fraction, tokens per GPU. This lesson derives those pieces from scratch on a 7B model, with numbers verified by a small simulation: why averaging gradients across replicas gives exactly the right answer, how ZeRO shards the 112 GB, how Megatron-LM splits a transformer's MLP so that one all-reduce is enough, how micro-batching fills a pipeline and what the bubble costs, and how the three are combined. It builds on the GPU track (gpu1 for the hardware, gpu3 for the memory arithmetic) and is deepened by gpu8 (collectives and link speeds, with the ring all-reduce derived) and gpu9 (ZeRO and FSDP in detail); here we focus on the ideas and on choosing between them. The public cases are the papers that made each technique practical: Megatron-LM, ZeRO, GPipe, the composition study behind the trillion-parameter runs, and Meta's account of Llama 3.

Three ways to cook a banquet

Imagine cooking for ten thousand guests, and one kitchen cannot do it. You have three options. You can build many identical kitchens, each cooking the full menu for a different group of guests, and after each course the head chefs compare notes so every kitchen improves its recipe the same way (data parallelism). That is easy, but every kitchen needs the entire menu, ingredients and equipment. Or you can have several chefs work at one shared counter on a single dish, each preparing part of every step and constantly passing bowls to each other (tensor parallelism); the dish gets made faster and no chef needs all the equipment, but the chefs must be shoulder to shoulder because they talk constantly. Or you can set up an assembly line: one team peels, the next chops, the next cooks, passing trays down the line (pipeline parallelism); passing a tray is cheap so the teams can be in different buildings, but at the start of service the later teams stand idle waiting for the first tray, and at the end the early teams stand idle (the bubble). Real training uses all three at once, and the skill is choosing how many of each, and which of the physical links (shoulder-to-shoulder NVLink or between-buildings network) carries which conversation.

The communication vocabulary

  • All-reduce: every GPU contributes a tensor and every GPU receives the elementwise sum (or average). Used to average gradients and to combine partial results in tensor parallelism.
  • All-gather: every GPU receives everyone's pieces, concatenated. Reduce-scatter: sum the tensors, then each GPU keeps one slice of the sum. (An all-reduce is a reduce-scatter followed by an all-gather.)
  • Point-to-point send/receive: one GPU sends a tensor to one other; used between pipeline stages.
  • NVLink / NVSwitch: very fast links between GPUs in one server (about 450 GB/s each way per GPU on an H100 server); InfiniBand or RoCE: the network between servers (about 50 GB/s each way per GPU at 400 Gb/s). This nine-fold gap decides which parallelism goes where; gpu8 derives it in detail.

Why so many pieces?

No single technique wins everywhere because each pays for something different. Data parallelism costs memory (a full copy on every GPU) but very little bandwidth. Tensor parallelism saves memory by dividing every layer but costs constant, latency-sensitive traffic. Pipeline parallelism costs almost no bandwidth but leaves GPUs idle in the bubble. The design question in every real training job is which combination of these costs your hardware and model can afford, and the answer changes with the model size, the GPU count and the network.

A first worked example

Data-parallel training on 8 GPUs with a per-GPU batch of 32 gives a global batch of 256. Each step, each GPU computes gradients on its own 32 examples; an all-reduce averages them; each GPU applies the same update. If communication overlaps with computation the throughput is nearly 8× one GPU (PyTorch's DDP paper reports near-linear scaling up to 256 GPUs). But the model, gradients and optimiser state are replicated on all 8, which is why it stops working when the model does not fit on one GPU.

1. What has to be split: the memory and compute budget

Training holds four kinds of data in GPU memory (dl1, dl5, gpu3): the parameters (2 bytes each in bf16), their gradients (2 bytes), the optimiser state (with mixed-precision Adam, a 4-byte float32 master copy of the weights plus 4 bytes each for the first and second moments: 12 bytes), and the activations saved for the backward pass. The first three are a fixed 16 bytes per parameter: 7B × 16 = 112 GB, against 80 GB of HBM on an H100. Activations depend on the batch: about 34·s·b·h bytes per layer with fused attention, for a 7B model (h = 4,096, 32 layers) at 4,096 tokens per sequence about 18 GB per sequence without checkpointing. The compute is the other budget: 6 FLOPs per parameter per token, so a step over T tokens costs 6·N·T. At a realistic 40% of a peak of 989 TFLOP/s (H100, dense bf16) a GPU sustains about 400 TFLOP/s, which is 400×10¹² / (6 × 7×10⁹) ≈ 9,500 tokens per second per GPU for this model. Two consequences drive everything: a 2-trillion-token run needs 2×10¹² / 9,500 = 2.1×10⁸ GPU-seconds (6.7 GPU-years), so it needs about a thousand GPUs to finish in days; and the 112 GB must be split or shrunk to fit.

2. Data parallelism

Every GPU (called a rank) holds a full replica of the model and processes a different slice of each batch. After the backward pass each rank holds a gradient computed on its own slice. Averaging them gives the gradient of the whole batch, so each replica applies the same update and the replicas stay identical. Why is averaging correct? The loss over a batch is the mean of per-example losses, so its gradient is the mean of per-example gradients; a mean of equal-sized groups' means is the mean of everything. The lab checks it: four workers with 16 examples each, each computing a gradient on its slice, average to exactly the full-batch gradient of 64 examples (they agree to machine precision).

The communication. The gradients are combined by an all-reduce. The standard algorithm is the ring all-reduce (gpu8 derives it): each GPU sends about 2(N − 1)/N times the size of the tensor being reduced, almost independent of N. For a 7B model in bf16 the gradients are 14 GB; on 8 GPUs each sends 2 × 7/8 × 14 = 24.5 GB per step, about 54 ms over 450 GB/s NVLink. Two points matter. First, this volume does not depend on how many tokens are in the batch: it is once per optimiser step, so the more tokens per step the smaller its relative cost. Second, it can be overlapped with computation. The backward pass produces gradients from the last layer to the first; PyTorch DDP groups them into buckets (25 MB by default) and launches each bucket's all-reduce as soon as its gradients are ready, while earlier layers are still computing, so that only the last bucket's communication is exposed. This is why data parallelism tolerates slow links and why the DDP paper reports near-linear scalability up to 256 GPUs.

Practical details that matter. All replicas must start with identical weights (DDP broadcasts them at start). Each rank must see different data (DistributedSampler, with set_epoch each epoch so shuffles differ). The effective batch is global batch = ranks × micro-batch × accumulation steps: doubling GPUs at fixed micro-batch doubles the global batch, so the learning rate and warmup must be revisited (ml4's linear scaling rule; Goyal et al. trained ImageNet with an 8,192-image batch on 256 GPUs this way), and beyond a problem-dependent critical batch size more data parallelism no longer reduces the steps needed. Layers whose statistics depend on the batch (BatchNorm, dl4) compute them per GPU unless converted to SyncBatchNorm. And gradient accumulation (several micro-batches before one step) should skip the all-reduce on all but the last micro-batch (no_sync()).

ZeRO / FSDP: data parallelism with sharded state. The waste in plain data parallelism is that every GPU holds identical copies of everything. ZeRO (Rajbhandari et al., 2019) removes the redundancy in three cumulative stages: stage 1 shards the optimiser state (the 12 bytes of master weights and moments), so each GPU keeps and updates only its 1/N slice; stage 2 also shards the gradients (a reduce-scatter instead of an all-reduce leaves each GPU only the summed slice it owns); stage 3 also shards the parameters, all-gathering each layer's weights just before it runs and freeing them after. Per-GPU model state for 7B on 8 GPUs: stage 1 keeps 14 GB weights + 14 GB gradients + 84/8 = 10.5 GB = 38.5 GB; stage 2 keeps 14 GB weights + 98/8 = 12.25 GB = 26.25 GB; stage 3 keeps 112/8 = 14 GB. Communication: stages 1 and 2 need the same total volume as plain data parallelism (the paper: "no additional communication ... while enabling up to 8x memory reduction"); stage 3 adds an all-gather of the parameters in the forward and again in the backward pass, "a modest 50% increase in communication volume" (1.5×). PyTorch's FSDP is the same idea. It is still data parallelism: each GPU runs the whole model on its own data and the mathematics of the step is unchanged (gpu9 has the details, including how FSDP prefetches the next layer's gather to hide it).

3. Tensor parallelism: Megatron-LM's column-then-row split

When a single layer's weights or activations are too big for one GPU, or when you want to cut the memory of every layer by the same factor, split the matrices themselves. The trick (Shoeybi et al., 2019) is to split so that as little communication as possible is needed. Take the MLP block of a transformer: Y = GeLU(X·A)·B, where X is (tokens × d), A is (d × h) with h = 4d (or 11,008 for a 4,096-wide Llama), and B is (h × d).

  • Split A by columns, A = [A₁ A₂] (each d × h/2), one piece per GPU. Each GPU computes X·Aᵢ, a slice of the hidden features, from the same X. The GeLU is applied elementwise, so each GPU can apply it to its own slice independently: GeLU([XA₁ XA₂]) = [GeLU(XA₁) GeLU(XA₂)]. No communication yet.
  • Split B by rows, B = [B₁; B₂] (each h/2 × d). GPU i multiplies its activation slice by its rows of B, giving a partial output of full size (tokens × d). The true output is the sum of the partials: Y = GeLU(XA₁)B₁ + GeLU(XA₂)B₂. One all-reduce computes it.

Why not split A by rows? Then each GPU would produce a partial sum of the pre-activation, and since GeLU(a + b) ≠ GeLU(a) + GeLU(b) the sum would have to be communicated before the non-linearity, adding a second all-reduce. The lab checks both: the column–row split reproduces the full MLP exactly, and the row split with per-part GeLU does not. Attention splits the same way: heads are independent, so each GPU takes a subset of heads (32 heads over TP = 8 gives 4 per GPU) for the query, key and value projections (a column-parallel split) and the output projection is row-parallel with one all-reduce. Per transformer layer the forward pass therefore needs two all-reduces (one after attention, one after the MLP), and the backward pass needs two more (for the conjugate operations), which is the Megatron-LM count: "two all-reduces in the forward path and two in the backward path".

What tensor parallelism costs, with numbers. The all-reduce carries a full activation tensor, T × d values. For the 7B model with T = 4,096 tokens per micro-batch and d = 4,096 in bf16 that is 4,096 × 4,096 × 2 = 33.6 MB. Four all-reduces per layer (two forward, two backward) with the ring factor 2·7/8 give 4 × 33.6 MB × 1.75 = 235 MB per GPU per layer, and 32 layers make 7.5 GB per GPU per micro-batch, growing with the number of tokens. On 450 GB/s NVLink that is 0.52 ms per layer. The layer's compute per GPU (24·d²·T = 1.65 TFLOP forward, three times that with backward, divided by TP = 8, at 400 TFLOP/s) is about 1.5 ms, so communication is about a third of compute and sits on the critical path (each layer waits for its all-reduce), which is why TP degree is kept small (at most 8, the size of an NVLink domain) and why sequence parallelism and overlap tricks exist. Over a 50 GB/s network the same all-reduces would take 4.7 ms per layer — longer than the compute — so tensor parallelism across nodes loses. The benefits: model state (and, with sequence parallelism, activations) divide by the TP degree: the 112 GB becomes 14 GB per GPU at TP = 8; each GPU's matrices are 8× smaller in one dimension (for Llama-7B's 11,008-wide MLP, 1,376 columns per GPU), still large enough for the tensor cores; and there is no bubble.

4. Pipeline parallelism

Split the model by layers into P consecutive stages on different GPUs (or groups). A single batch pushed through would leave all but one stage idle at any moment, so the batch is cut into M micro-batches that flow through the stages like items on an assembly line: while stage 2 processes micro-batch 1, stage 1 can already start micro-batch 2. Only the activations at stage boundaries move (and their gradients backward), point to point: for the 7B model with 4,096 tokens that is one 33.6 MB tensor per boundary per micro-batch each way, tiny next to tensor parallelism's 7.5 GB, so pipeline stages can be on different servers over the network.

The bubble. At the start of the step the later stages have nothing to do until the first micro-batch reaches them; at the end the early stages are idle while the last micro-batches drain. Measure time in units where one micro-batch's forward through one stage is 1 (its backward is about 2). The ideal time is M × 3 units of work per stage; the actual schedule takes (M + P − 1) × 3, because the pipeline needs P − 1 extra slots to fill and drain. The fraction of time wasted is

bubble fraction = (P − 1) / (M + P − 1)

P = 4 stages with M = 8 micro-batches: 3/11 = 27.3% idle. With M = 32: 3/35 = 8.6%. The GPipe paper found the bubble "negligible when M ≥ 4 × K" (K = stages); the trade-off is that smaller micro-batches make smaller matrices (less efficient kernels) and more micro-batches in flight need more activation memory. The lab's schedule simulator reproduces these numbers exactly (33 time units for P = 4, M = 8, of which 24 are useful).

GPipe versus 1F1B. GPipe (Huang et al., 2018) runs all M forward micro-batches and then all M backward ones. It needs every stage to keep the activations of all M micro-batches until their backward passes come, so activation memory grows with M — a problem, because a small bubble needs large M. The 1F1B schedule (from PipeDream; called PipeDream-Flush in Narayanan et al.) has each stage do a warm-up of forward passes (P − s on stage s) and then alternate one forward and one backward, so backward passes start as soon as possible and each micro-batch's activations are freed early. The total time and the bubble are identical to GPipe's (33 units either way in the lab); what changes is memory: peak stored micro-batches per stage is [4, 3, 2, 1] for 1F1B against [8, 8, 8, 8] for GPipe, bounded by P rather than M (and for M = 32: still [4, 3, 2, 1] against 32 everywhere). GPipe also supports re-materialisation (recomputing activations in backward, gpu9) to cut memory further. Interleaved schedules (Narayanan et al., 2021) give each GPU v non-adjacent chunks of layers (for instance layers 1–4 and 9–12), reducing the bubble by a factor v to (P − 1)/(v·M) at the price of v times more point-to-point traffic; the paper reports up to 10% higher throughput. All these schedules are synchronous: gradients from all micro-batches are accumulated and one optimiser step is taken at the end (a "pipeline flush"), so the maths is exactly that of the full batch. Asynchronous schemes that avoid the flush (PipeDream's weight stashing) introduce stale weights and are rarely used for LLMs.

Stage balance. The stages must take equal time or the slowest sets the pace. Layers are identical in a transformer, but the first stage also holds the embedding and the last the output head and loss (for a 128K vocabulary the output layer is large), so those stages are given fewer transformer layers in practice.

5. Combining them: 3D parallelism

The three parallelisms multiply: world size = tensor degree (t) × pipeline degree (p) × data degree (d). The rules for assigning them follow from the costs above. Tensor parallelism is the chattiest and sits on the critical path, so t is at most the number of GPUs in an NVLink domain (8 in a standard server). Pipeline parallelism sends little, so it crosses servers over the network; use as few stages as memory allows because each adds bubble. Data parallelism (with ZeRO-style sharding if memory is tight) takes the rest; its once-per-step all-reduce tolerates the slowest links, and the global batch caps it (d × micro-batch × accumulation must stay near the critical batch). Narayanan et al. (2021), whose composition of the three they call PTD-P, trained models up to a trillion parameters on 3,072 A100 GPUs at 502 petaFLOP/s aggregate, 163 teraFLOP/s per GPU or 52% of peak; Meta's Llama 3 405B used tensor parallelism 8, pipeline parallelism 16, context parallelism for long sequences and data parallelism 64 (8,192 GPUs) or 128 (16,384 GPUs), at 430 and 400 teraFLOP/s per GPU (43% and 41% MFU); with 131,072-token sequences it added context parallelism 16 and dropped data parallelism to 8, at 38% MFU.

A worked plan for the 7B model. On one 8-GPU server the simplest choice is FSDP (ZeRO-3) over all 8: 14 GB of state per GPU, leaving ~60 GB for activations, with each GPU processing its own slice of the batch; TP or PP is unnecessary because the model is small. On 64 GPUs (8 servers): FSDP over 64, or hybrid sharding (shard within each server, replicate across servers) to keep the gathers on NVLink: at 9,500 tokens per second per GPU the cluster processes 610,000 tokens per second, so 2 trillion tokens take about 38 days; 2.4 days would need about 1,000 GPUs. A 7B model rarely needs TP; its d = 4,096 makes TP's communication a third of compute (section 3), which is why teams use pure FSDP until models reach tens of billions of parameters. For the 70B model on 64 A100s see the drill.

Other axes. Sequence/context parallelism splits long sequences across GPUs (with ring attention for million-token contexts, gpu7); sequence parallelism (Korthikanti et al.) shards the layer-norm and dropout regions that tensor parallelism replicates, turning each all-reduce into a reduce-scatter and an all-gather of the same total volume and dividing those activations by t; expert parallelism places the experts of a mixture-of-experts model on different GPUs, with all-to-all token routing (gpu8).

6. Using it in PyTorch

# launch:  torchrun --nproc_per_node=8 train.py
import torch, torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data.distributed import DistributedSampler

dist.init_process_group("nccl")                          # one process per GPU; NCCL does the collectives
rank, local = dist.get_rank(), int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local)
model = DDP(model.to(local), device_ids=[local])          # all-reduces gradients in 25 MB buckets during backward
sampler = DistributedSampler(dataset, shuffle=True)       # each rank gets a distinct shard
for epoch in range(epochs):
    sampler.set_epoch(epoch)                              # different shuffle each epoch, same on all ranks
    for i, batch in enumerate(loader):
        sync = (i + 1) % accum == 0                       # accumulate without communicating, sync on the last micro-batch
        with (nullcontext() if sync else model.no_sync()):
            (model(batch).loss / accum).backward()
        if sync: opt.step(); opt.zero_grad(set_to_none=True)
# models too large for one GPU: torch.distributed.fsdp.fully_shard (FSDP2) or FullyShardedDataParallel

Tensor and pipeline parallelism are supplied by libraries (Megatron-LM, DeepSpeed, PyTorch's torch.distributed.tensor.parallel and pipelining APIs, TorchTitan) that own the process-group layout: for example a 3D device mesh of shape (data, pipeline, tensor) in which each GPU belongs to one group per dimension.

7. Efficiency: MFU, overlap and what limits it

Model FLOPs utilisation (MFU, gpu3) is achieved useful FLOP/s divided by the hardware's peak. Reported figures are a useful sanity band: Megatron-LM's 2019 baseline on one V100 sustained 39 teraFLOP/s (30% of peak), and its 8.3B model on 512 GPUs sustained 15.1 petaFLOP/s, 76% scaling efficiency compared with that single-GPU baseline; the 2021 trillion-parameter run reached 52% of peak on A100s; Llama 3 405B reached 38–43%. A well-tuned run is in the 35–55% range. What eats the rest: communication that is not hidden (exposed communication), the pipeline bubble, small matrices, activation recomputation, data loading, kernel launch overheads, and stragglers. Practical levers: overlap (DDP buckets, FSDP prefetch), larger micro-batches, fused kernels (gpu6), and interleaved pipelines. When MFU is low, profile before changing the layout (gpu11): look for GPU idle gaps around collectives.

Why the ring all-reduce is bandwidth-optimal, and where the latency goes

To sum a tensor of n bytes across N GPUs, every GPU must at least send out the parts of its data that others need and receive the summed result, about (N − 1)/N × n bytes each way for the reduce phase and the same for the broadcast phase: 2(N − 1)/N × n in total. A ring achieves exactly that lower bound: split the tensor into N chunks, do N − 1 reduce-scatter steps and N − 1 all-gather steps, each sending one n/N chunk. Its cost model is T ≈ 2(N − 1)·α + 2(N − 1)/N · n/β (latency α per step, bandwidth β): for large messages the bandwidth term dominates and is nearly independent of N, which is why data parallelism scales; for small messages on many GPUs the 2(N − 1) latency terms dominate, so NCCL switches to tree algorithms (about 2 log₂ N steps) and, across servers, to hierarchical schemes that reduce-scatter inside each server over NVLink first so the network carries only 1/8 of the data per GPU (gpu8). Ring is why the gradient all-reduce of a 7B model on 8 GPUs costs 24.5 GB of traffic per GPU, and why halving it needs a fundamentally different lever (compression, lower precision gradients, or in-network reduction).

Sequence parallelism and activation memory under tensor parallelism

Tensor parallelism divides weights by t but, as originally described, leaves several activations replicated on every GPU of the group: the input to each block, the layer norms, the dropout masks and the residual stream, since they are not the output of a split matrix. Korthikanti et al. (2022) shard exactly those regions along the sequence dimension ("sequence parallelism"): each GPU normalises and applies dropout to s/t of the tokens, an all-gather reassembles the full activation before each column-parallel matmul, and a reduce-scatter replaces the all-reduce after each row-parallel matmul. An all-reduce equals a reduce-scatter followed by an all-gather, so the communication volume is unchanged; the activation memory of those regions divides by t. Combined with selective recomputation this cut activation memory about five-fold for a few percent extra compute and took a 530B-parameter model from 42.1% to 54.2% MFU (gpu9). For our 7B example the 18 GB of activations per 4,096-token sequence become about 2.3 GB per GPU at t = 8.

Batch size, critical batch and what data parallelism does to optimisation

Adding data-parallel replicas increases the global batch, and beyond the critical batch size (which grows during training as the loss falls and the gradient noise shrinks) more samples per step no longer reduce the number of steps needed, so extra GPUs stop paying off and can hurt final quality without retuning. Recipes therefore raise the batch during training: Llama 3 405B started with 4M tokens per step, doubled to 8M (with 8,192-token sequences) after 252M tokens and to 16M after 2.87 trillion, reporting a stable run with few loss spikes. The learning rate scales with the batch (linearly for SGD and roughly by the square root for Adam as a starting point, dl5) with warmup. When the token budget or the critical batch caps data parallelism, the remaining GPUs must be used by model parallelism (tensor, pipeline, context), which is why very large runs need 3D or 4D parallelism even if the model would fit under FSDP.

Correctness pitfalls that only appear in parallel runs

Random number streams. Dropout masks in data-parallel replicas should differ across ranks (each has its own data) but must be identical across the tensor-parallel ranks that hold shards of the same activation, otherwise the shards of a replicated tensor disagree. Megatron keeps separate RNG states for the tensor-parallel and data-parallel regions. Loss normalisation. With variable-length sequences the loss must be normalised by the total number of tokens across all ranks and micro-batches, not averaged per rank, or short-sequence ranks get too much weight (dl1). Gradient clipping must use the global norm across all parameter shards (an all-reduce of squared norms), not a per-rank norm. Determinism. Reduction order in floating point changes between runs, and bf16 reductions are lossy, so bitwise reproducibility across different parallel layouts is not expected; the right test is that the loss curves agree within noise and that the first-step gradients agree to numerical tolerance. Uneven data. If ranks receive different numbers of batches (a non-divisible dataset) the ranks with data wait forever at a collective for the rank without: a deadlock, cured by drop_last or joining.

Pipeline refinements: zero-bubble, DualPipe and where the bubble really goes

A backward pass has two parts: the gradient with respect to the layer's input (B, which the previous stage waits for) and the gradient with respect to its weights (W, which nobody waits for). Zero-bubble pipeline schedules (Qi et al., 2023) exploit that: they schedule the W parts late, into the slots that would otherwise be idle, and can reach a bubble near zero at the cost of more complex bookkeeping and memory. DeepSeek-V3's DualPipe feeds micro-batches from both ends of the pipeline and overlaps forward and backward computation with communication (including expert all-to-all), to hide most of the pipeline and MoE communication. These are refinements of the same accounting: the bubble is idle time from dependencies, and the fixes reorder independent work into it.

Low-bandwidth training: communicate less

When the interconnect is slow (across data centres, or consumer networks) the once-per-step all-reduce can be relaxed. Local SGD lets each replica take H optimiser steps on its own data and then average the weights; DiLoCo (Douillard et al., 2023) uses an inner AdamW for the H steps and an outer optimiser (Nesterov momentum) on the averaged weight differences, reporting that it matches fully synchronous training with far less communication. Gradient compression (PowerSGD low-rank approximations, 1-bit and top-k schemes with error feedback) shrinks the volume at some risk to convergence. These are worth knowing as answers to "what if the network is 100× slower", and worth distrusting until validated on your own workload: standard synchronous training with overlap is the default at datacentre scale.

Fault tolerance in numbers: the Young–Daly interval

With a checkpoint that stalls training for C seconds and a mean time between failures M for the whole job, checkpointing every τ seconds wastes about C/τ (checkpoint overhead) plus τ/(2M) (average work lost per failure, half an interval). Minimising gives τ* = √(2·C·M) and a waste of about 2·√(C/(2M)). Llama 3's 54-day snapshot had 419 unexpected interruptions, so M ≈ 54 × 24 × 3,600 / 419 ≈ 11,100 s (3.1 hours); with C = 60 s, τ* ≈ 1,150 s (about 19 minutes) and the waste is about 5.2% + 5.2% = 10.4%, which is consistent with Meta's report of more than 90% effective training time even with automated recovery. Two consequences: the failure rate scales with the number of components, so M shrinks as the cluster grows and checkpoint cost C must shrink with it (asynchronous, sharded checkpoints that copy state to CPU memory and write in the background, gpu9), and restart time (re-provisioning, reloading, re-warming) adds to the loss and is why automated node replacement and fast checkpoint reload matter as much as checkpoint frequency.

The public cases

Megatron-LM (2019). Shoeybi et al. at NVIDIA implemented intra-layer model parallelism "with the insertion of a few communication operations in native PyTorch", requiring no new compiler. Their baseline is a 1.2-billion-parameter model on a single V100 32GB GPU that "sustains 39 TeraFLOPs", 30% of that GPU's peak. Scaling the model to 8.3 billion parameters on 512 GPUs with 8-way model parallelism (and 64-way data parallelism), they "achieve up to 15.1 PetaFLOPs per second sustained over the entire application", a "76% scaling efficiency compared to the single GPU case"; the 8.3B-parameter model on 8 GPUs alone achieved 77% of linear scaling. The trained models set state of the art on WikiText103, LAMBADA and RACE, and the paper reports that scaling BERT beyond a size required moving the layer normalisation inside the residual block (an observation that became the pre-norm story of dl4).

ZeRO (2019). Rajbhandari et al. at Microsoft showed that basic data parallelism "runs out of memory for models with more than 1.4B parameters on current generation of GPUs with 32 GB memory", analysed the 16 bytes per parameter, and introduced the three stages with their claimed reductions: stage 1, 4×; stage 2, 8× with the same communication as data parallelism; stage 3, linear in the data-parallel degree N_d (64× on 64 GPUs) for a 50% increase in communication. Their implementation trained "models of over 100B parameter with super-linear speedup on 400 GPUs, achieving throughput of 15 Petaflops", an 8× increase in model size and 10× in performance over the state of the art at the time, and they argue ZeRO can scale to a trillion parameters on 1,024 GPUs. This is the basis of DeepSpeed and PyTorch FSDP.

GPipe (2018). Huang et al. at Google introduced micro-batch pipelining with re-materialisation as a general library. Their bubble analysis says the idle fraction is (K − 1)/(M + K − 1) and that they found the overhead "negligible when M ≥ 4 × K". They scaled a 557-million-parameter AmoebaNet image classifier to 84.4% ImageNet top-1 accuracy, and a Transformer to 6 billion parameters for a multilingual translation model, with a reported 3.5× speed-up when a Transformer was partitioned across four times more accelerators.

Composition at scale (2021). Narayanan et al. combined the three (PTD-P) on up to 3,072 A100 GPUs. Table 1 of their paper shows weak scaling of GPT models from about a billion parameters on tens of GPUs to one trillion parameters on 3,072, with achieved throughput of 135–163 teraFLOP/s per GPU (43–52% of peak) and 502 petaFLOP/s aggregate for the largest run. They report their interleaved schedule improving throughput by as much as 10%, an effective bisection bandwidth of 892 GB/s for pipeline-parallel and 13 TB/s for data-parallel communication in the trillion-parameter run, and that the choice of degrees (tensor parallelism up to the node size, pipeline across nodes) mattered more than any single optimisation.

Llama 3 (2024). Meta's report gives the most complete public account of operating such a run. Llama 3 405B pre-training used up to 16,384 H100 GPUs, and Table 4 of the paper lists the configurations: 8,192 GPUs with TP 8, PP 16 and DP 64 (430 TFLOP/s per GPU, 43% MFU); 16,384 GPUs with DP 128 (400 TFLOP/s, 41%); and for long-context training 16,384 GPUs with context parallelism 16 and DP 8 (380 TFLOP/s, 38%). During a 54-day snapshot there were "a total of 466 job interruptions", 47 planned and 419 unexpected; "approximately 78% of the unexpected interruptions are attributed to confirmed hardware issues" and GPU issues were the largest category at 58.7% of all unexpected ones. Despite this they "achieved higher than 90% effective training time" through automated recovery and cluster maintenance, and they describe checkpoint writes as bursty (each GPU's state 1 MB to 4 GB) and the work of minimising GPU pause time during checkpointing.

Failure modes and how they show up

Collective hangs. If one rank crashes, runs out of memory, or takes a different code path (for example, a data-dependent branch that skips a layer on one rank), the other ranks wait forever at the next collective, and the job appears frozen with GPUs at 100% utilisation (spinning in NCCL). Set collective timeouts (NCCL's watchdog), log which rank and which collective, use a flight recorder for the last collectives on each rank, and keep code paths identical across ranks.

Stragglers. A synchronous step waits for the slowest GPU, so one thermally throttled GPU, a degraded NVLink or a NIC with errors slows the entire cluster. Symptoms: throughput lower than the sum of the parts, wide spread in per-rank step times. Monitor per-rank step and communication times and compare against nccl-tests baselines (gpu8); pull the slow node.

Silent data corruption. Rarely, a GPU computes a wrong result without any error (Llama 3's report lists it among hardware issues). Symptoms: an unexplained loss spike or NaN, a gradient norm that differs across data-parallel ranks after an all-reduce (it should be identical). Defences: cross-rank consistency checks of loss and norms, checksums of weights across replicas, and the ability to roll back to a known-good checkpoint.

Uneven memory. Pipeline stages near the front hold more activations under 1F1B (up to P micro-batches), the first and last stages hold the embedding and output head, and long-sequence batches spike memory on one rank; one rank's OOM kills the job. Measure per-rank peak memory, balance layer assignment, and cap sequence lengths.

Divergence between layouts. A multi-GPU run whose loss differs from the single-GPU run at the same global batch: check batch and learning-rate arithmetic, initial-weight identity, sampler shuffling and drop_last, BatchNorm synchronisation, loss normalisation and RNG handling (deep section).

Network misconfiguration. NCCL silently falling back from InfiniBand/NVLink to sockets or PCIe (wrong interface, missing GPUDirect), producing bandwidth an order of magnitude too low. Check NCCL_DEBUG=INFO for the transports chosen and run nccl-tests before every large run.

What to monitor

Per step: loss, gradient norm (identical across data-parallel ranks after the all-reduce), learning rate, tokens per second, MFU. Per rank: step time, time in collectives (exposed communication), peak memory, GPU temperature and clocks, ECC and NVLink error counters. Cluster: job restarts, time lost to failures and recovery (effective training time), checkpoint duration and success, and data-loader stalls. Alert on a rank whose step time exceeds the median by a few percent for several steps.

Goal: verify on small arrays the three ideas behind the parallelisms, and reproduce the lesson's schedule and memory arithmetic. The script (a) checks that averaging four data-parallel workers' gradients equals the full-batch gradient, (b) reproduces a Megatron-style MLP split (column-parallel then row-parallel) and shows why splitting the first matrix by rows fails, (c) simulates GPipe and 1F1B pipeline schedules with dependencies and reports total time, bubble fraction and peak stored micro-batches per stage, and (d) prints per-GPU memory and per-step communication for a 7B model. NumPy only, Python 3.12, about a second.

import numpy as np
rng = np.random.default_rng(0)

# ---- 1. data parallelism: average the workers' gradients = the full-batch gradient
X = rng.normal(size=(64, 5)); y = rng.normal(size=64); w = rng.normal(size=5)
grad = lambda Xb, yb: 2 * Xb.T @ (Xb @ w - yb) / len(yb)                       # gradient of the mean squared error
full = grad(X, y)
workers = [grad(X[i::4], y[i::4]) for i in range(4)]                            # 4 workers, 16 examples each
print("data parallel: mean of 4 worker gradients equals the full-batch gradient:", np.allclose(np.mean(workers, axis=0), full))

# ---- 2. tensor parallelism: MLP Y = gelu(X A) B, A split by columns, B split by rows, ONE all-reduce
gelu = lambda z: 0.5 * z * (1 + np.tanh(np.sqrt(2 / np.pi) * (z + 0.044715 * z ** 3)))
X = rng.normal(size=(8, 16)); A = rng.normal(size=(16, 32)); B = rng.normal(size=(32, 16))
full = gelu(X @ A) @ B
A1, A2 = A[:, :16], A[:, 16:]; B1, B2 = B[:16], B[16:]                          # GPU 0 holds (A1, B1), GPU 1 holds (A2, B2)
partial0 = gelu(X @ A1) @ B1; partial1 = gelu(X @ A2) @ B2                       # each GPU works alone: no communication yet
print("tensor parallel: partial0 + partial1 (the all-reduce) equals the full MLP:", np.allclose(partial0 + partial1, full))
Ar1, Ar2 = A[:8], A[8:]                                                          # the WRONG split of A (by rows) needs the sum BEFORE gelu
wrong = gelu(X[:, :8] @ Ar1) + gelu(X[:, 8:] @ Ar2)
print("splitting A by rows and applying gelu to each part is not equivalent:", not np.allclose(wrong, gelu(X @ A)))

# ---- 3. pipeline parallelism: schedule simulation (forward 1 unit, backward 2 units per micro-batch per stage)
def simulate(P, M, policy):
    ops = []                                                                     # per-stage op order
    for s in range(P):
        if policy == "gpipe": ops.append([("F", m) for m in range(M)] + [("B", m) for m in range(M)])
        else:                                                                    # 1F1B: warm-up forwards, then alternate B/F, then drain
            warm = min(P - s, M); seq = [("F", m) for m in range(warm)]; f, b = warm, 0
            while b < M:
                seq.append(("B", b)); b += 1
                if f < M: seq.append(("F", f)); f += 1
            ops.append(seq)
    done, free, idx, inflight, peak = {}, [0] * P, [0] * P, [0] * P, [0] * P
    while any(idx[s] < len(ops[s]) for s in range(P)):
        best = None
        for s in range(P):
            if idx[s] >= len(ops[s]): continue
            kind, m = ops[s][idx[s]]
            dep = done.get(("F", s - 1, m), 0) if kind == "F" and s > 0 else (done.get(("B", s + 1, m), 0) if kind == "B" and s < P - 1 else done.get(("F", s, m), 0) if kind == "B" else 0)
            if kind == "F" and s > 0 and ("F", s - 1, m) not in done: continue
            if kind == "B" and s < P - 1 and ("B", s + 1, m) not in done: continue
            if kind == "B" and ("F", s, m) not in done: continue
            start = max(free[s], dep)
            if best is None or start < best[0]: best = (start, s, kind, m)
        start, s, kind, m = best; dur = 1 if kind == "F" else 2
        done[(kind, s, m)] = start + dur; free[s] = start + dur; idx[s] += 1
        inflight[s] += 1 if kind == "F" else -1; peak[s] = max(peak[s], inflight[s])
    total = max(free); busy = M * 3
    return total, 1 - busy / total, peak
for P, M in [(4, 8), (4, 32)]:
    for pol in ("gpipe", "1f1b"):
        total, bubble, peak = simulate(P, M, pol)
        print(f"pipeline P={P} M={M:2d} {pol:5}: total time {total:3d} units, bubble {bubble:5.1%} (formula {(P - 1) / (M + P - 1):5.1%}), peak micro-batches stored per stage {peak}")

# ---- 4. memory per GPU for a 7B model (mixed-precision Adam: 2 + 2 + 4 + 4 + 4 = 16 bytes/param), 8 GPUs
N = 7e9; GB = 1e9
print("\nmodel state per GPU, 7B parameters, 8 GPUs (activations excluded):")
for name, per in [("plain data parallel (DDP)", 16 * N), ("ZeRO-1 (shard optimiser, 12 B)", (4 + 12 / 8) * N), ("ZeRO-2 (+ gradients)", (2 + 14 / 8) * N),
                  ("ZeRO-3 / FSDP (+ parameters)", 16 * N / 8), ("tensor parallel, TP=8", 16 * N / 8), ("pipeline parallel, PP=8", 16 * N / 8)]:
    print(f"  {name:32} {per / GB:6.1f} GB")
# ---- 5. communication per training step for the same model (bf16 gradients/activations)
h, s_tok, L = 4096, 4096, 32
ring = lambda n, p: 2 * (p - 1) / p * n
print("\nbytes moved per GPU per step (ring factor included):")
print(f"  data parallel all-reduce of 14 GB gradients, 8 GPUs: {ring(2 * N, 8) / GB:5.1f} GB   (independent of tokens per step)")
act = s_tok * h * 2                                                              # one activation tensor for a 4,096-token micro-batch
print(f"  tensor parallel: 4 all-reduces x 32 layers of {act / 1e6:.1f} MB, TP=8: {4 * L * ring(act, 8) / GB:5.1f} GB per 4,096 tokens (grows with tokens)")
print(f"  pipeline parallel: one {act / 1e6:.1f} MB activation forward + one gradient backward per boundary per micro-batch: {2 * act / 1e6:.0f} MB")

What to look for.

  1. Data parallel: the mean of the four worker gradients equals the full-batch gradient (True): the reason averaging keeps replicas identical.
  2. Tensor parallel: partial0 + partial1 equals the full MLP output; splitting A by rows and applying the GeLU to each part is not equivalent because GeLU(a + b) ≠ GeLU(a) + GeLU(b).
  3. Pipeline: for P = 4, M = 8 both schedules take 33 time units with a 27.3% bubble matching (P − 1)/(M + P − 1); for M = 32, 105 units and 8.6%. The last column is the point of 1F1B: GPipe stores 8 (or 32) micro-batches on every stage, 1F1B stores [4, 3, 2, 1] regardless of M.
  4. Memory table: 112 GB for DDP, 38.5 / 26.2 / 14.0 GB for ZeRO-1/-2/-3, 14 GB for TP = 8 or PP = 8 (model state only). Change N to 13e9 or 70e9 and see when each scheme fits an 80 GB card.
  5. Communication: 24.5 GB per GPU for the gradient all-reduce (independent of tokens), 7.5 GB for tensor parallelism per 4,096-token micro-batch (grows with tokens), 67 MB per pipeline boundary per micro-batch.

Work it out — the bubble and a plan for 70B

Pipeline parallelism across 4 stages with 8 micro-batches: compute the bubble fraction, then for 32 micro-batches. Then sketch a parallelism plan for a 70B model on 64 A100-80GB GPUs (8 per node).

Answer

Bubble fraction = (stages − 1) / (micro-batches + stages − 1). With 8 micro-batches: 3/11 = 27% of GPU time idle while the pipeline fills and drains. With 32: 3/35 = 8.6%. More micro-batches shrink the bubble but each is smaller (less efficient kernels) and, under GPipe, activation memory grows with them; 1F1B keeps stored micro-batches at about the number of stages, and interleaved schedules cut the bubble further at the cost of more communication.

70B on 64 A100-80GB. State is 16 × 70B = 1,120 GB, so it must be sharded; there are two reasonable answers and a good response compares them with numbers.

  • Option A: FSDP (ZeRO-3) over all 64. State per GPU 1,120/64 = 17.5 GB plus activations. Communication per GPU per step: parameters gathered in forward and again in backward, gradients reduce-scattered: about 3 × 140 GB = 420 GB, roughly 8 s if all of it crossed a 50 GB/s network (less with hybrid sharding that keeps gathers inside a node). Compute per GPU for 16K tokens: 6 · 70×10⁹ · 16,384 ≈ 6.9×10¹⁵ FLOPs, about 55 s at 40% of the A100's 312 TFLOP/s, so the gathers can hide behind compute given enough tokens per GPU. Simple, and viable at this scale.
  • Option B: 3D parallelism. Tensor parallel = 8 within each node (activation all-reduces stay on NVLink), pipeline parallel = 4 across node groups (only activations cross the network) with at least 32 micro-batches to keep the bubble near 9%, data parallel = 2 with ZeRO-1. More moving parts, but it keeps the network traffic small and is how a run scales to thousands of GPUs, as in Llama 3 (TP 8, PP 16, DP 64–128).

In both: bf16 with fp32 master weights, activation checkpointing, a global batch in the low millions of tokens with warmup and cosine decay, and — because on 64 GPUs something fails about weekly — checkpoints every ~20–30 minutes with automatic resume and a loss-spike rollback. Finish with what you would measure: MFU (target 35–45%), exposed communication, per-rank step-time spread, and peak memory per rank.

Cost the communication

A 7B model is trained with tensor parallelism 8 inside a server (NVLink 450 GB/s each way) and data parallelism across 16 servers (network 50 GB/s each way). Micro-batch 4,096 tokens, hidden size 4,096, 32 layers, bf16. Estimate the tensor-parallel traffic per micro-batch and the gradient all-reduce time, and say which one you would worry about.

Answer

Tensor parallel: each all-reduce carries T·d·2 bytes = 4,096 × 4,096 × 2 = 33.6 MB; 4 per layer (2 forward + 2 backward) × 32 layers = 128 of them; ring factor 2 × 7/8 = 1.75, so each GPU sends 128 × 33.6 MB × 1.75 = 7.5 GB per micro-batch, or 16.7 ms at 450 GB/s. The layer compute is about 1.5 ms per layer (fwd + bwd, TP = 8) or about 50 ms for 32 layers, so communication is roughly a third of compute and on the critical path: worth optimising (sequence parallelism does not reduce volume but frees activation memory; overlapping chunks of the matmul with communication helps), and it must never cross the network (it would take 150 ms).

Data parallel: each TP rank holds 1/8 of the model, so its gradient shard is 14 GB / 8 = 1.75 GB; the all-reduce across 16 replicas over the network moves 2 × 15/16 × 1.75 GB = 3.3 GB per GPU, about 66 ms at 50 GB/s — once per optimiser step, and overlapped with backward. With a step of many micro-batches (several seconds of compute), that is a couple of percent.

Which to worry about? Tensor-parallel communication: it is a large, unavoidable fraction of every layer's time and sits on the critical path, whereas the data-parallel all-reduce is once per step and hidden behind backward. That is exactly the asymmetry that puts TP on the fast link and DP on the slow one.
