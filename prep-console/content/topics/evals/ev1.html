A team builds a support assistant for an online shop. In the demo it is wonderful: it answers questions about delivery times, explains the returns policy and drafts polite replies. They launch. In week two a customer complains that the bot promised a refund on a final-sale item. An engineer adds a sentence to the system prompt: "Never promise refunds on final-sale items." She tries the complaining customer's question again, the bot now refuses correctly, and the fix ships.

A week later, refund requests on ordinary items start getting refused too. Support tickets go up. Nobody connects it to the prompt change, because the engineer tested the one case she was fixing, and it worked. Meanwhile the model provider releases a new snapshot of the model behind the same name, and answers get longer and chattier. A product manager wants to move to a smaller model that costs a fifth as much, and nobody can say whether it is worse. Every meeting about quality turns into people trading screenshots of good and bad answers.

This team does not have a bug. It has no way to know whether its product works, and no way to know whether it still works next week. That is the problem evaluation solves. An eval is a repeatable measurement of the system's behaviour on a defined set of cases, and the practice of building, running and trusting evals is most of what separates an AI product from an AI demo. Many experienced practitioners say that teams whose LLM products stall almost always share one root cause: they never built a way to measure them.

This lesson is the foundation for the whole track. It defines what an eval is, made of tasks, trials and graders. It explains why LLM features need them more than ordinary software needs unit tests, and the eval-driven development loop that turns real failures into tests. It describes the four layers of the eval pyramid, from free deterministic checks to expensive online experiments, and the difference between capability and regression suites. It shows the arithmetic of pass@k against pass^k, and catalogues what goes wrong without evals. Later topics take each layer apart: golden sets (ev2), metrics (ev3), LLM judges (ev4), human labelling (ev5), retrieval-augmented generation or RAG (ev6), statistics (ev7), online tests (ev8), safety (ev9), synthetic and training data (ev10, ev11) and running all of it in continuous integration (CI) and production (ev12).

Think of evals as two familiar things at once: a test suite and an instrument panel. Like a test suite, an eval is a set of cases you run before every change so you find out what broke before users do. Like an instrument panel in a cockpit, it gives you readings, numbers with known precision, that you watch over time to see whether you are climbing or descending. You need both because an LLM feature is part software, part measurement problem.

The analogy breaks in two useful places. First, a unit test is deterministic: the same input gives the same output, and the test either passes or fails. An LLM can answer the same question differently on two runs, so a single run of a single case tells you little; you run cases several times and talk about pass rates. Second, a unit test checks against a specification someone wrote down. For most LLM behaviour ("is this reply helpful and faithful to the policy?") there was no specification until you wrote the eval. Writing the eval is writing the spec, which is why it forces decisions nobody had made: should the bot apologise? may it guess a delivery date? when should it hand over to a human?

The vocabulary

A few words recur through the track. A task (or case) is one test: an input, such as a customer message plus account context, and the criteria for success. A trial is one attempt at a task; because outputs vary, you often run several. A grader scores one aspect of a trial's output: a piece of code ("is it valid JSON?"), a language model following a rubric ("does the reply follow the refund policy?"), or a person. A trace (or transcript) is the full record of a trial: the prompt, the model's output, any tool calls and retrieved documents. A suite is a collection of tasks with a shared purpose, and the harness is the code that runs a suite end to end and adds up the scores.

The big picture: a pyramid of checks

There is no single way to grade an LLM output. There is a stack of methods that trade cost against fidelity, the eval pyramid:

At the base are assertions: ordinary code that checks crisp properties, such as "the output parses as JSON", "every claim cites a document ID", "no internal order IDs appear in a customer-facing reply". They cost nothing and run in milliseconds, so they run on every change and even on every production response. Above them are model-graded checks, where a strong LLM reads the output with a rubric and judges things code cannot, like faithfulness or tone. These cost a fraction of a cent to a few cents per case and need to be checked against people. Above that is human review: domain experts labelling a sample. It is slow and expensive, and it is the reference that the judges are calibrated against. At the top is online measurement: A/B tests and signals from real users, such as thumbs-down votes, edits and escalations. This measures the outcome you actually care about, but it takes days or weeks and exposes real users to the change.

The working rule is simple. Every requirement should be checked at the lowest layer that can check it reliably, and each layer exists partly to keep the one below it honest. Humans validate the judge, and online results validate the offline suite.

The loop

Evals are not a phase at the end. They are the inner loop of building the feature. You look at real outputs, name what goes wrong, turn the important failures into cases, change the prompt or the retrieval or the model, re-run the suite to see what improved and what regressed, ship behind a gate, and harvest new failures from production. That loop is eval-driven development, and most of the body of this lesson is about running it well.

If you stop reading here, keep this picture: a feature is "working" only relative to a suite of real cases with trustworthy graders, measured with known precision, and re-measured every time anything changes.

1. What an eval is made of

Take one case from the shop's support assistant and walk it through. The task is a customer message, "I bought the blue jacket on 2 March, it doesn't fit, can I send it back?", plus context: the order record says the jacket was not final-sale and was delivered 20 days ago, and the policy says returns are accepted within 30 days. The success criteria are: the reply says yes, a return is possible; it states the deadline correctly (10 days left); it does not invent a fee; it links the returns page; it is under 120 words.

A trial runs the full system on that input: the prompt is assembled, documents are retrieved, the model generates a reply. The trace records all of it. Then the graders run. Some are code: the length check, a regex for the returns URL, a check that no string matching the internal order-ID pattern appears. One is a model: an LLM judge reads the reply, the order record and the policy, and answers "Does the reply correctly state that a return is allowed and give the correct deadline? Answer PASS or FAIL with a one-line reason." Each grader produces a score; the task passes if all required graders pass.

The suite is a few hundred such tasks covering returns, deliveries, payment problems, complaints, abusive messages and questions the bot should hand to a human. The harness runs the suite, often several trials per task, writes every trace and score to storage, and produces a report: overall pass rate with a confidence interval, pass rate per category, and the list of tasks that changed status since the last run. That report is what a decision is made on.

Notice what each part protects against. Multiple trials protect against luck. Multiple graders per task let a reply fail for different reasons, and the report shows which reason. Storing traces lets you read failures instead of guessing at them. Grouping by category stops a big improvement on easy questions from hiding a collapse on hard ones.

2. Why LLM software needs this more than ordinary software

Ordinary software has unit tests, and most teams consider them sufficient. Three properties of LLM features make them insufficient here.

Non-determinism. With a sampling temperature above zero, the same input produces different outputs on different runs. Even at temperature zero, many hosted models are not perfectly repeatable, because batching and floating-point arithmetic on GPUs can change which token wins a near-tie. So "I tried it and it worked" is one draw from a distribution. If a case passes 80% of the time, trying it once has a one-in-five chance of showing a failure that is not typical, and a four-in-five chance of hiding one that is.

No specification. A function that adds two numbers has a spec. "Answer customer questions helpfully and according to policy" does not, until somebody writes down what helpful and according to policy mean for hundreds of concrete situations. Those concrete situations, with their criteria, are the eval. Until they exist, quality is whatever the last person to edit the prompt thought it was.

Action at a distance. In ordinary code, a change to the refund function rarely breaks the delivery-time function. In an LLM feature, every behaviour flows through the same prompt and the same model. The sentence "never promise refunds on final-sale items" changes the model's whole disposition towards refunds, and can affect cases that have nothing to do with final sale. Worse, many changes do not come from your code at all. The provider updates the model. The retrieval index is rebuilt with new documents. A teammate edits a tool description. Each of these can shift behaviour across the whole surface, and the only way to see the shift is to measure the whole surface.

The prerequisite lm14 covered how to measure an LLM honestly. This track starts from the observation that measurement is not a one-off study. It is the daily engineering practice of the team, the way testing is for ordinary software.

3. Eval-driven development: the loop

Eval-driven development borrows its shape from test-driven development (TDD), where you write a failing test for a behaviour first and then write code until it passes. In eval-driven development you write a case, or a whole suite, for the behaviour you want, then change the system until the pass rate is where you need it, without breaking other cases. The differences from TDD matter. The checks are statistical. Some graders are models that must themselves be validated. And the cases come from reading real outputs rather than from a spec written in advance.

Step 1: look at traces. Pull 100-200 real conversations, or realistic ones from dogfooding (using your own product internally) and beta users, and read them. Most teams skip this, and it is the highest-value hour in the whole process. Seeing the inputs real people send is the only way to find out what the system is actually being asked to do.

Step 2: error analysis. For each trace that looks wrong, write one sentence about what went wrong, in your own words: "told customer refund takes 3 days, policy says 5-7", "answered in English to a French message", "asked for order number that was already in the message". This free-form note-taking is sometimes called open coding, a term borrowed from qualitative research. When you have 30-50 notes, group them into a handful of failure modes and count them. Here is what that table looked like for the shop, over 150 traces of which 41 had a problem (illustrative numbers):

Failure modeCountShare of failuresSeverity
Wrong policy detail (deadline, fee, eligibility)1434%High: money and trust
Didn't use information already in the message or order922%Medium: annoying
Should have escalated to a human, didn't717%High
Wrong language or tone615%Low-medium
Formatting (broken links, wall of text)512%Low

The point of counting is to replace opinions with a priority order. The vivid complaint that started the fire (a refund promised on a final-sale item) is one instance of the top row. Fixing that row properly, perhaps by retrieving the exact policy clause rather than paraphrasing it in the prompt, is worth more than any single patch.

Step 3: write cases. Each important failure mode becomes several tasks: the traces you found, plus variations a domain expert adds (the same question about a different product category, a borderline date). Each gets graders. "Wrong policy detail" needs a grader that knows the right answer, either an expected value checked by code ("deadline mentioned is 10 days") or a judge given the policy text. "Should have escalated" is checkable by code if the system has an explicit escalate action.

Step 4: change the system. Edit the prompt, fix retrieval, add a tool, try a different model.

Step 5: run the whole suite and compare to the stored baseline. You want three things from the comparison: did the targeted failure mode improve, did anything else get worse, and is the difference bigger than run-to-run noise? (lm14 showed how to compare two systems on the same items using only the cases where they disagree. ev7 goes deeper into the statistics.) If something regressed, you go back to step 4 before shipping.

Step 6: ship and monitor. The change goes out behind a gate (ae7): the suite must pass before release, and production is sampled and graded continuously (ae3). New failures from production go back to step 1. Over months, the suite becomes a record of every way the product has failed, and the reason it does not fail that way again.

4. Layer one: assertions

An assertion is a deterministic check written in ordinary code. It is the cheapest, fastest and most reliable grader there is, so the first question for any requirement is "can a program check this?" Surprisingly often, it can:

import json, re

def check_reply(reply: str, case: dict) -> dict:
    results = {}
    results["length_ok"] = len(reply.split()) <= 120
    results["no_internal_ids"] = not re.search(r"\bORD-\d{8}\b", reply)
    results["links_returns_page"] = "shop.example/returns" in reply
    if case.get("expect_escalation"):
        results["escalated"] = "[ESCALATE]" in reply
    if case.get("expected_deadline_days") is not None:
        results["deadline_correct"] = f"{case['expected_deadline_days']} days" in reply
    return results

Structured output makes far more requirements assertable. If the model returns JSON with an action field ("answer", "escalate", "refuse") and a cited_doc_ids list, then "escalated when it should" and "cited a policy document" become exact checks. This is one strong reason to design LLM features with structured output (ae4) even when the user eventually sees prose.

Assertions have two limits. They are brittle to valid variation: the deadline check above fails a reply that says "you have until 22 March", which is correct. And they cannot judge meaning: a reply can contain the right URL and still give wrong advice. When an assertion keeps failing good answers, loosen it or move that requirement up a layer. A grader that fails correct outputs teaches the team to ignore the eval, which is worse than having no grader.

Because assertions are free, they can also run on every production response as online guardrails. An assertion that fires on a live reply can block or rewrite it before the user sees it, and the firing rate becomes a monitored metric.

5. Layer two: model-graded checks

Many requirements need reading comprehension: is the reply faithful to the retrieved policy? Does it answer what was asked? Is the tone appropriate for an angry customer? For these, teams use LLM-as-judge: a strong model is given the input, the output, a rubric (written criteria for what good looks like) and often a reference answer, and asked for a verdict.

The judge's appeal is scale. A human expert might label 30-60 support replies an hour. A judge can grade thousands in minutes for a few dollars, so it can run on the full suite on every candidate release. Its weakness is that it is another model, with its own errors and biases: preferring longer answers, preferring whichever answer comes first in a comparison, being fooled on questions it could not answer itself. lm14 introduced these biases. ev4 is entirely about designing judges and correcting them.

The rule at this layer is that a judge is an instrument that must be calibrated. Before you trust it on a criterion, you measure its agreement with human labels on a sample from your own task. You re-measure whenever the judge model, its prompt or the traffic changes. A judge that agrees with your experts 90% of the time on "policy correct" is a superb tool. The same judge on "tone appropriate for a bereaved customer" may agree 65% of the time, and should not gate anything.

Prefer narrow, binary judge questions ("Does the reply state the correct return deadline given this policy? PASS/FAIL") over broad 1-10 scales ("Rate the quality"). Narrow questions are easier to validate, easier for the judge to get right, and produce failures you can act on. "Quality 6/10" tells you nothing about what to fix.

6. Layer three: human review

People remain the reference for open-ended quality, because "good" is ultimately defined by what users and domain experts consider good. Human review serves three purposes, and it pays to be clear which one you are doing.

The first is building the golden set. Experts write or approve the expected outputs and verdicts that graders compare against (ev2). The second is calibrating the judges. Experts label a sample, and you measure judge-human agreement (ev4, ev5). The third is measuring quality directly on things no automated grader handles well yet: a weekly sample of production conversations, labelled against the rubric, gives an unbiased estimate of real quality.

Human labels are only as good as the guidelines and the labellers. Two experts who disagree 30% of the time on whether a reply is acceptable are telling you the rubric is ambiguous. That disagreement also sets a ceiling: no judge can sensibly be expected to agree with "the humans" better than the humans agree with each other. ev5 covers the measurement of that agreement (Cohen's kappa, Krippendorff's alpha) and how to run labelling as an operation.

7. Layer four: online measurement

Everything below this layer is a proxy. The outcome the business cares about happens in production: did the customer's problem get solved without a human? Did they come back? Did they edit the draft before sending it, or throw it away? Online measurement captures this in two ways. There are A/B tests, where users are randomly split between the old and new version and outcomes are compared (ml16, math7). And there are implicit signals monitored continuously: thumbs-down rate, regeneration rate, edit distance between draft and sent message, escalation rate, abandonment.

Online measurement is the most faithful layer and the most expensive. A test needs enough traffic to detect a meaningful difference, often thousands of conversations per arm. It takes days or weeks. And the users in the treatment arm are exposed to a version that might be worse. So the offline layers act as a filter: a change has to pass the offline suite before it earns a slot in an online test. Online results in turn are the check on the offline suite. If versions that win offline keep losing or tying online, the offline suite is measuring the wrong thing, and ev8 is about diagnosing that.

8. The economics of the pyramid, worked

To see why the shape matters, put rough numbers on one release of the support assistant, evaluated on a 600-case suite with 3 trials per case, so 1,800 outputs to grade. The prices below are illustrative assumptions, not quotes. Plug in your own; the ratios are what matter.

The arithmetic for the judge row: 2,000 input tokens at $3 per million is $0.006, and 150 output tokens at $15 per million is $0.00225, so one call costs about $0.00825. Three criteria on 1,800 outputs is 5,400 calls, about $45. Humans labelling the same 1,800 outputs at 45 an hour would take 40 hours, about $2,400 and a week of calendar time. That is roughly fifty times the judge's cost, and you cannot do it on every pull request. So the pattern is: assertions on everything, always; the judge on the full suite per release; humans on a few hundred items a week, chosen to calibrate the judge and to sample production; online tests for changes that matter.

This is also why the pyramid is a pyramid, not a column. If you find yourself needing humans to grade a criterion every release, ask whether a validated judge could take it over. If the judge is grading something a regex could check, move it down. Every check that moves down a layer gets cheaper, faster and more repeatable.

9. Capability evals and regression evals

Suites have two different jobs, and mixing them causes confusion. A capability eval asks "what can the system do well?" It deliberately contains hard tasks the system fails today: the multi-item return with a gift card, the angry customer writing in Portuguese. Its pass rate starts low, perhaps 30%, and rising scores are the measure of progress. A regression eval asks "does the system still do everything it used to?" It contains tasks the system handles, and its pass rate should sit close to 100%. A drop is an alarm.

The gates differ accordingly. A release is blocked when the regression suite drops beyond its noise (ae7 covers setting those thresholds). A release is not blocked because a capability eval failed to improve. When a capability task becomes reliably solved, it graduates into the regression suite, so that the progress you made is protected. Anthropic's engineering guidance describes exactly this flow: capability evals are "a hill to climb", and solved tasks become a regression suite that runs continuously.

A capability eval eventually saturates: the system passes nearly every solvable task, and the eval stops telling versions apart. Near saturation, large real improvements show up as tiny score changes, because only the hardest few tasks are left. The response is to add harder tasks, usually drawn from today's production failures. Public benchmarks go through the same cycle. Anthropic notes that SWE-bench Verified, a coding benchmark, went from frontier scores around 40% to over 80% within about a year, which is why newer, harder benchmarks keep appearing.

10. Trials, pass@k and pass^k

Because one trial is one draw, suites usually run several trials per task. That raises a question: with three trials, what does "the task passed" mean? There are two common answers, and they describe different products.

pass@k is the probability that at least one of k trials succeeds. It fits situations where a person or a verifier can pick the good attempt: a code assistant that proposes several fixes and runs the tests on each. pass^k (read "pass hat k" or "pass to the k") is the probability that all k trials succeed. It fits situations where every run must work: an agent acting on a customer's account does not get to try three times and keep the best.

Worked, for a task where each trial independently succeeds with probability p = 0.75:

  • pass@1 = 0.75.
  • pass@3 = 1 − (1 − 0.75)³ = 1 − 0.25³ = 1 − 0.015625 = 0.984. Three tries almost always contain a success.
  • pass^3 = 0.75³ = 0.422. Three tries in a row all succeed less than half the time.

Reporting pass@k for a product that needs pass^k is one of the commonest ways teams fool themselves. The arithmetic also explains why multi-step agents feel unreliable. If each step must succeed and each succeeds 95% of the time, a 10-step task succeeds 0.9510 ≈ 60% of the time. (The next track, on agentic systems, builds on this.)

The formulas above assume you know p. In practice you estimate it from a handful of trials per task. ev3 shows the unbiased estimator of pass@k from n samples, introduced in the paper that launched the HumanEval coding benchmark.

11. What goes wrong without evals

It helps to name the failure patterns. They are recognisable in almost every team that ships on manual spot checks.

Whack-a-mole. Each complaint gets a prompt patch tested on that one complaint. Each patch shifts behaviour elsewhere. Quality oscillates and the prompt grows into a list of special cases nobody dares remove. Worked: the final-sale patch fixed the 6 cases like the complaint. Run against a 400-case suite, it also flipped 9 ordinary refund cases from pass to fail. Without the suite, the team sees +6 and ships. With it, they see +6 −9 and look for a better fix, such as retrieving the item's final-sale flag and letting the policy clause decide.

Silent upstream change. A hosted model gets updated, an embedding model is swapped, the document index is rebuilt. Nothing in the repository changed, so nothing was tested. ae3 described the GPT-4 behaviour-drift study, where the same model name answered differently between March and June 2023. A suite run on a schedule against production detects this. A suite that only runs on pull requests does not.

Stuck on an expensive model. A cheaper or faster model might be good enough, but without an eval nobody can show it is not worse on the cases that matter. The team pays the premium indefinitely, or switches on faith and finds out from customers.

Decision by anecdote. Two engineers each have a screenshot. A suite with a confidence interval ends the argument, or shows that the difference is too small to measure, which is also an answer.

The plateau. Early prompt work gives quick wins. Then progress stalls, because the team cannot tell which of several ideas helped, and some "improvements" were actually regressions in disguise. The Rechat case in Hamel Husain's widely cited write-up follows this arc: early success, then a plateau with recurring failure modes, broken by building a systematic evaluation process with unit-test style assertions, logged traces reviewed by people and LLM critics, and eventually A/B tests.

Liability. When a model's output is consequential, someone is responsible for it. ae1 described the 2024 Canadian tribunal ruling that held an airline responsible for what its website chatbot told a customer about bereavement fares. Evals do not remove risk. They are how you know which risks you are running.

12. Starting from nothing

The most common objection is that building evals is a large project. It does not need to be. Anthropic's guidance is that "20-50 simple tasks drawn from real failures is a great start". Early on, changes are big (fixing retrieval might move the pass rate 20 points), and big differences are visible with small samples. The statistics of how small (ev2, ev7) say that with 50 cases at around 80% pass rate, a 95% confidence interval is about ±11 points, so you can see a 25-point jump but not a 3-point one. That is fine at the start.

A practical first week looks like this. Day one: log full traces, then read 100-200 of them. Day two: error analysis, open coding and counting. Days three and four: write 30-50 cases for the top failure modes, with assertions where possible and one narrow judge question where not; label 50 outputs yourself and check the judge agrees. Day five: run a baseline, three trials per case, and record it. From then on, every change is measured against that baseline, and the suite grows by a few cases every time production shows a new failure.

A useful test of whether a case is good, from the same guidance: "a good task is one where two domain experts would independently reach the same pass/fail verdict." If experts would argue about it, the case measures the grader's mood, not the system.

The eval is the specification

Writing a rubric forces product decisions. Should the assistant volunteer a discount code to an angry customer? Should it guess a delivery date when tracking is stale, or say it doesn't know? Each of these, left unwritten, gets decided by the model's defaults and the prompt author's mood. Writing a case with a criterion makes the decision explicit, reviewable and testable. Senior engineers treat eval cases the way they treat API contracts: changes go through review, and disagreements about a case are disagreements about the product, to be settled by the product owner, not by whoever edits the YAML file.

Construct validity: are you measuring the thing?

Psychometrics, the science of measuring abilities and attitudes, distinguishes reliability (does the measurement give the same answer twice?) from validity (does it measure what it claims to?). An eval can be perfectly reliable and invalid: a deterministic check that answers contain the word "sorry" reliably measures apologising, not empathy. Validity is established the way lm14 described for judges: agreement with experts on the same outputs, and correlation with online outcomes. A senior candidate asked "how do you know your eval is good?" should describe both, and should mention auditing passes as well as failures, because invalid graders hide in the passes.

Goodhart's law and eval overfitting

"When a measure becomes a target, it ceases to be a good measure." A team that tunes a prompt against the same 200 cases for three months will find phrasings that pass those cases for idiosyncratic reasons, much like a model overfitting a training set. The score rises, and real quality rises less. The defences mirror machine learning practice (ml9). Keep a held-out set that is consulted rarely, for release decisions only. Rotate fresh production cases in. Prefer fixes that address a failure mode's cause, such as retrieving the policy, over fixes that address the case's wording. Be suspicious when the dev set improves and the held-out set doesn't move.

Graders make two kinds of error

A grader can fail a good output (a false fail) or pass a bad one (a false pass). The costs differ. False fails waste engineering time and erode trust in the eval, until people start ignoring red results. False passes let regressions ship. Measuring both rates against human labels, not just overall agreement, tells you which way a grader leans. A grader with 90% agreement that achieves it by passing almost everything is useless as a gate on a suite where 90% of outputs are good. This is the same precision/recall thinking as ml7, applied to the grader as a classifier of outputs.

Outcomes beat transcripts, but you need both

For systems that take actions, the most trustworthy grader inspects the outcome: the database row, the file on disk, the test result. Models routinely claim success they did not achieve, so grading the final message rewards confident wording. But outcome-only grading misses things that matter. An agent can reach the right state by a dangerous path (deleting and recreating a record), take 40 steps where 6 would do, or skip a required confirmation. So action-taking systems are graded on outcome first, with trajectory checks for safety rules and efficiency on top.

How much evaluation is enough?

Evaluation has a cost, and the right amount scales with consequence and churn. A feature whose errors are cheap and immediately visible to the user, like a brainstorming helper, needs a smoke suite and logging. A feature that gives policy or medical or financial answers, sees heavy traffic, depends on a third-party model, or is changed weekly, needs the full pyramid. The useful framing for an interview is expected cost. If a regression reaching production would cost more than building and running the suite that would have caught it, and with any meaningful traffic it usually does, the suite pays for itself.

Evals for non-deterministic systems are statistical claims

"Version B passes 84% versus A's 81%" is a claim about two distributions estimated from a finite sample of cases and trials. There are two sources of noise: which cases happened to be in the suite, and which outputs the sampler happened to draw. Running more trials per case shrinks the second but not the first. lm14 and rs8 introduced standard errors and paired comparisons; ev7 makes this rigorous, including how many cases you need to see a 2-point difference. At this stage the essential habit is to never report a pass rate without an interval, and never call a difference real without checking it exceeds run-to-run noise.

The public case: Anthropic's "Demystifying evals for AI agents" (January 2026)

Anthropic's engineering post is a first-party account of how evaluation is practised across real agent deployments, and it lines up closely with this lesson. It defines the same building blocks: tasks, trials, graders, transcripts and outcomes. The outcome is the state of the environment at the end; in their example, an agent saying "your flight has been booked" does not count, only a reservation in the database does. It sorts graders into code-based ("fast, cheap, objective, reproducible") but brittle to valid variation; model-based, flexible but non-deterministic and needing calibration against humans; and human, the gold standard but slow and expensive. It separates capability evals, which start low, from regression evals, which should hold near 100%, and describes solved capability tasks graduating into regression suites.

The customer examples show the pyramid forming over time. Descript framed its evals around three questions, "don't break things, do what I asked, and do it well". It moved from manual grading to LLM graders periodically calibrated by humans, and now runs separate suites for quality benchmarking and for regressions. Bolt built an eval system in about three months combining static analysis, browser agents that exercise generated apps, and LLM judges for instruction following. Claude Code started from employee and user feedback, then added evals for concision, file edits and over-engineering. The post also makes the saturation point concrete: SWE-bench Verified scores went from roughly 40% to over 80% in about a year.

Characteristic failure modes

The suite nobody looks at. A suite runs in CI, goes red for flaky reasons, and the team learns to click "re-run" until it passes. The fix is to make the suite trustworthy. Measure its run-to-run noise and set thresholds above it (ae7). Remove or repair graders with high false-fail rates. Make each red result link straight to the failing traces.

The suite that stopped representing traffic. Built at launch from beta users, never refreshed. Six months later, users ask about a new product line the suite has no cases for, and quality there is unknown. Symptom: offline scores climb while support tickets do too. Fix: a standing process that samples recent production into the suite, stratified by intent (ev2, ev12).

The judge nobody validated. A 1-10 "quality" score from an LLM, never compared with human labels, gates releases. It rewards length, so answers grow longer every release and users complain. Symptom: judge scores rise while thumbs-down rate rises too. Fix: narrow binary criteria, measured against human labels, with length controlled (ev4).

Testing only the diff. Engineers run the five cases related to their change. Regressions appear in unrelated categories. Fix: the full regression suite is cheap enough with assertions and a judge; run it on every candidate.

Metrics and tooling

The eval report every team ends up with shows: pass rate per suite with a confidence interval; pass rate per category or slice; a diff list of cases that flipped since the baseline, linking to traces; grader health, meaning judge-human agreement on the latest calibration sample; and cost and latency per case. Open-source harnesses provide most of this. OpenAI's evals repository was an early framework and registry of evals, and its README now also points to evals configured directly in the OpenAI dashboard. Inspect, from the UK AI Security Institute, structures an eval as a dataset, a solver (anything from a single model call to a multi-turn agent with tools) and scorers, and ships a log viewer. promptfoo is a command-line tool for test cases with assertion types such as contains, llm-rubric and similar, used in CI and for red-teaming. The tools change quickly. The concepts in this track are what carry over.

Who owns the evals

In teams that do this well, the people who own the product's quality own the eval cases and rubrics, often a product manager or domain expert, while engineers own the harness and the graders' implementation. When a case is disputed, it is a product question. When a grader is wrong, it is a bug. Making that division explicit avoids the common failure where engineers quietly edit expected answers to make a release pass.

Goal: build a minimal eval harness with assertions, run two prompt "versions" against it with several trials, and see pass rate, per-category results, pass@k and pass^k. Python 3.12, standard library only.

  1. Create ev1_lab.py. Define a stub "model": def model(version, case, rng) that returns a reply string. For version "A", make it include the correct deadline with probability 0.80 and escalate correctly with probability 0.70. For "B" (your "prompt fix"), make it 0.90 on deadlines but 0.60 on escalation. Use random.Random(seed) so runs are repeatable.
  2. Write 40 cases as dicts: 25 in category "returns" with expected_deadline_days, and 15 in "escalation" with expect_escalation=True.
  3. Write check_reply(reply, case) using plain string checks, like the assertion function in the body.
  4. Run each version with 5 trials per case. Record pass/fail per trial. Print: overall pass rate, pass rate per category, and for each case the pass@3 and pass^3 computed from its observed per-trial rate p as 1-(1-p)**3 and p**3; then print the averages over cases.
  5. Print a "diff": cases whose majority verdict flipped between A and B.

What to look for. B should look better overall on a suite dominated by returns cases, and worse on escalation. That is the whack-a-mole pattern, visible only because results are broken down by category. Average pass@3 will be close to 1 for both versions while pass^3 is far lower: the same data tells two stories. Change the seed and re-run. The overall difference between A and B moves by a few points from seed alone, a preview of why ev7 insists on intervals. Finally, set 2 of the 40 cases to have a wrong expected deadline and watch both versions "fail" them every time. A case that every version fails is often a grader bug, not a model bug.

Diagnose: the prompt fix that made things worse

Your support assistant's team fixed a complaint by adding "Never promise refunds on final-sale items" to the system prompt. Over the next two weeks, refund-related support tickets rose 18%, but the engineer insists the fix works: she re-ran the complaining customer's message ten times and it refused correctly every time. You have 3,000 logged traces from before the change and 3,000 from after, and no eval suite. What do you do?

Answer

First, establish what changed, using the traces you have. Sample 150 refund-related traces from before and 150 from after, and label each yourself as correct or incorrect against the policy, writing a one-line note on every incorrect one. Count the failure modes in each period. The likely finding is a new mode after the change: refusals of refunds on ordinary items, because the instruction shifted the model's whole stance on refunds. That turns "tickets went up" into "the refusal rate on eligible refunds went from about 2% to about 15%", a measurable regression with examples.

Second, build the suite that would have caught it. Turn those traces into cases: eligible refunds that must be accepted, final-sale items that must be refused, and borderline ones (partially final-sale orders, items past the deadline). Use structured output if possible, an action field of accept, refuse or escalate, so the core check is an exact assertion. Add a judge only for the explanation's correctness, validated on 50 of your own labels.

Third, fix the cause rather than the wording. The model should not infer final-sale status from a rule in the prompt. Retrieve the item's final-sale flag from the order system and give it, with the exact policy clause, as context. Run both the patched prompt and the new design against the suite, with 3 trials per case, and compare per category. Ship the version that fixes the complaint without regressing eligible refunds, behind a canary that watches refund-ticket rate.

Finally, explain to the engineer why ten re-runs of one message proved nothing about the other 2,999 kinds of message. The fix worked on its case. Nobody measured the rest of the surface.
