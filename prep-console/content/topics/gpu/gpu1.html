A team rents eight H100 GPUs to fine-tune a model. The datasheet promises close to 1,000 trillion floating-point operations per second (TFLOP/s) per GPU for 16-bit maths, so they work out that one epoch should take about four hours. It takes eleven. Someone opens nvidia-smi and sees "GPU-Util 100%", which makes it more confusing: the GPU says it is fully busy, yet it is doing less than half the work the arithmetic promised. A profiler then shows something stranger still. The big matrix multiplications — nearly all of the model's arithmetic — take only about half of each training step. The rest goes on normalisation layers, activation functions, dropout, a softmax, and dozens of tiny operations that each finish in a few microseconds but leave the GPU waiting in between. Operations with a thousandth of the arithmetic take a tenth of the time.

None of this is a bug. It is exactly what you would predict if you knew how a GPU is built. A GPU is not a very fast CPU. It is a different kind of machine, designed around a trade: give up making any single calculation quick, in exchange for doing an enormous number of calculations at the same time. It has a special unit that makes matrix multiplication far cheaper than any other kind of arithmetic, and a memory system that is fast by ordinary standards but slow compared with its own arithmetic. Once you understand those three facts, the eleven-hour epoch explains itself, and so do most of the questions an interviewer will ask about ML performance: why batch size matters, why LLM decoding is slow, why FlashAttention helps, why someone padded a vocabulary to a multiple of 64 and got a 25% speed-up.

This lesson builds that picture from the ground up. We start with why GPUs exist and how they differ from CPUs, then open the chip: the streaming multiprocessors that do the work, the warps of 32 threads they run, the tensor cores that do matrix maths, and the hierarchy of memories from registers to HBM. We then see how a GPU hides the time it spends waiting for memory, and use real numbers from the H100 to classify operations as compute-bound, memory-bound or overhead-bound. Finally we compare GPU generations from A100 to Blackwell and Rubin, look at how shapes decide efficiency, and see how large training fleets measure and lose utilisation in practice. Every later topic in this track — the roofline model, CUDA kernels, FlashAttention, multi-GPU training, inference performance — builds on this one.

Two ways to spend a billion transistors

Think of a CPU as a small team of expert chefs and a GPU as a factory kitchen with thousands of line cooks. Each expert chef can cook any dish, improvise when an ingredient is missing, and plan ahead by guessing what the next order will be. That makes one complicated order come out fast. The factory kitchen's line cooks each know only simple steps and are slower individually, but give them ten thousand identical plates to prepare and they finish long before the experts. They also never stand idle: when one cook is waiting for the oven, a supervisor points them at another plate that is ready.

In hardware terms, a CPU core devotes most of its area to making one stream of instructions run quickly: large caches so data is usually close by, branch prediction so it can guess which way an if will go, and out-of-order execution so it can run later instructions while an earlier one waits. A server CPU might have 32 to 128 such cores. A GPU devotes its area to many simple arithmetic units and to storage that holds the state of tens of thousands of threads at once. A thread here is one independent sequence of instructions working on its own piece of data — for example, "compute output element number 4,711". The GPU gives up speed per thread, and wins on throughput: the total amount of work completed per second.

The analogy breaks in one important way: a factory's line cooks can each do a different simple step. A GPU's cooks work in squads of 32 — a warp — that must all perform the same instruction at the same moment, each on their own data. That is perfect when every cook is chopping onions and wasteful when the recipe says "if the onion is red, do X, otherwise do Y".

The big picture in four moves

1. The CPU drives, the GPU does the heavy lifting. Your Python program runs on the CPU, called the host. When PyTorch executes y = x @ w on a GPU tensor, it asks the GPU (the device) to run a kernel — a function compiled for the GPU — across thousands of threads. The CPU queues the kernel and carries on; the GPU executes it asynchronously.

2. The work runs on streaming multiprocessors. A GPU is built from many copies of one unit, the streaming multiprocessor (SM). An H100 has 132. The kernel's threads are divided into groups called thread blocks, and each block is placed on one SM. Inside, threads run in warps of 32.

3. Matrix multiplication has its own hardware. Each SM contains tensor cores, which multiply small matrices in one instruction. They provide about 15 times more arithmetic than the ordinary units on an H100 — so matmuls are cheap, and everything else is comparatively expensive.

4. Data lives far away. The GPU's main memory, HBM (high-bandwidth memory), holds the model's weights and activations. It is very fast by CPU standards — 3.35 terabytes per second on an H100 — but the arithmetic is faster still, and each access takes hundreds of cycles. The GPU copes by always having other threads ready to run while some wait.

If you remember only one sentence: a GPU is a throughput machine with cheap matrix arithmetic and comparatively expensive memory access, which hides waiting by running a huge amount of parallel work. The rest of the lesson makes each part of that sentence precise.

1. Host, device and kernels: how work reaches the GPU

A GPU does nothing on its own. The CPU (the host) runs your program and, whenever an operation involves GPU tensors, it enqueues work for the GPU (the device). In PyTorch, torch.matmul(a, b) on CUDA tensors does not compute anything on the CPU; it picks a suitable GPU function — a kernel, often from NVIDIA's cuBLAS matrix library — and launches it: it tells the GPU to run that function with, say, 1,024 thread blocks of 256 threads each. CUDA is NVIDIA's platform for this: a compiler, a runtime library and extensions to C++ for writing kernels (we write one in gpu5).

Launches are asynchronous. The CPU puts the kernel on a queue (a stream) and returns immediately, so Python can race ahead and enqueue the next operations while the GPU is still busy. That is why timing GPU code with time.time() gives nonsense unless you call torch.cuda.synchronize() first. Each launch costs a few microseconds of CPU and driver time. For a large matmul that is irrelevant; for an operation on a tensor with a few thousand elements it can be the entire cost, which we will call being overhead-bound.

The GPU connects to the host through PCIe, the standard expansion bus: a Gen5 x16 slot moves about 64 GB/s in each direction. Compare that with the GPU's own memory at 3.35 TB/s — fifty times faster. Copying data between CPU and GPU on every step is therefore a classic mistake; the model, optimiser state and activations live on the GPU, and only input batches (and occasional checkpoints) cross PCIe. Multiple GPUs in a server talk to each other over NVLink, a direct link much faster than PCIe (900 GB/s per H100) — the subject of gpu8.

2. Inside the streaming multiprocessor

An SM is the GPU's unit of replication: design one, then copy it across the chip. The full Hopper die (GH100) has 144 SMs; the H100 SXM product (SXM is NVIDIA's socketed module form, mounted on a server board with NVLink, as opposed to a PCIe plug-in card) enables 132 (the rest are disabled to improve manufacturing yield), the H100 PCIe card 114. When a kernel launches, a hardware scheduler distributes its thread blocks among SMs; each block runs on one SM from start to finish, and an SM can host several blocks at once if it has room.

Each H100 SM is divided into four identical sub-partitions (sometimes called processing blocks). Each sub-partition has:

  • a warp scheduler that picks, every cycle, one warp whose next instruction is ready and issues that instruction;
  • 32 FP32 arithmetic lanes — NVIDIA's CUDA cores — plus integer units, FP64 units (64-bit double precision, used in scientific computing) and special-function units for things like exponentials;
  • one tensor core for matrix arithmetic;
  • a quarter of the SM's register file — 64 KB per sub-partition, 256 KB per SM (65,536 32-bit registers).

Shared by the four sub-partitions is a block of on-chip SRAM (static RAM: fast, small memory built into the chip itself) of 256 KB that serves as both L1 cache and shared memory; up to 228 KB of it can be configured as shared memory. Add it up for an H100: 132 SMs × 128 FP32 lanes = 16,896 lanes; 132 × 256 KB ≈ 33 MB of registers; and 132 × 4 = 528 tensor cores. The register file alone is larger than many CPUs' entire cache.

3. Threads, warps and SIMT

When you write a CUDA kernel, you write the code for one thread — "load element i of x, multiply by 2, store element i of y" — and launch it across as many threads as there are elements. Each thread has its own registers and its own index i. The hardware, however, does not issue instructions one thread at a time. It groups each run of 32 consecutive threads in a block into a warp, and a warp scheduler issues one instruction for all 32 threads at once, each applying it to its own registers. NVIDIA calls this SIMT: single instruction, multiple threads.

SIMT is cheap — one instruction fetch and decode drives 32 lanes of arithmetic — which is part of how a GPU fits so much compute on a chip. The cost appears with branches. Suppose a kernel does:

if (x[i] > 0) { y[i] = expensive_a(x[i]); }   // 100 cycles
else          { y[i] = expensive_b(x[i]); }   // 100 cycles

If, within a warp, 20 threads have positive values and 12 do not, the warp cannot do both at once. It runs expensive_a with the 12 "else" threads switched off (masked), then expensive_b with the 20 "if" threads masked. That takes 200 cycles instead of 100; the lanes are only 50% useful. This is divergence. It only matters within a warp: if warp 0 is all-positive and warp 1 all-negative, each runs one path and nothing is wasted. ML kernels mostly avoid the problem because every element gets the same treatment, but it shows up in code with data-dependent control flow — for example, variable-length sequences handled with per-thread loops, or sparse data.

A block of threads is a multiple of warps: a block of 256 threads is 8 warps. Threads in the same block can cooperate — share data through shared memory and wait for each other at a barrier (__syncthreads() in CUDA) — which is what lets a block load a tile of a matrix once and have all its threads reuse it. Threads in different blocks cannot synchronise within a kernel, which is what lets the hardware run blocks in any order on any SM.

4. How a GPU hides latency

Here is the core trick. A load from HBM takes several hundred clock cycles to return — at about 1.8 GHz, a few hundred nanoseconds. A CPU fights this with big caches and by executing other instructions out of order. A GPU instead keeps many warps resident on each SM at once — up to 64 warps (2,048 threads) on an H100 SM — with all their registers held in the huge register file, so switching from one warp to another costs nothing. Every cycle, each of the four warp schedulers looks at its warps, finds one whose next instruction has its operands ready, and issues it. A warp that is waiting for memory simply isn't picked.

How much parallel work is "enough"? Little's Law from sc1 answers it: the amount of work in flight equals throughput times latency. To keep an H100's HBM streaming at 3.35 TB/s when each load takes roughly 600 ns to return, the chip needs 3.35 × 1012 B/s × 600 × 10-9 s ≈ 2 MB of loads outstanding at every moment. Spread over 132 SMs that is about 15 KB per SM. If each thread loads 16 bytes at a time (a 128-bit load, the widest), one warp instruction brings in 512 bytes, so each SM needs about 30 warp-loads in flight at all times — for example, 30 warps each with one outstanding load, or 8 warps each with four independent loads issued before any result is used. A kernel with too few threads, or whose threads wait for each load before issuing the next, cannot reach the bandwidth the datasheet promises. The same calculation for a B200 at 8 TB/s gives about 4.8 MB in flight: each generation needs more parallelism to stay busy.

The number of resident warps is limited by resources. The SM's 65,536 registers are divided among resident threads: at 32 registers per thread, all 2,048 threads fit; at 128 registers per thread, only 512 threads (16 warps) fit. Shared memory is divided among resident blocks in the same way. The fraction of the maximum warps that are resident is called occupancy. Higher occupancy gives the scheduler more choice, but it is only one way to hide latency — we return to this in the deep section.

5. The memory hierarchy with numbers

Data flows from HBM through L2 into each SM's L1/shared memory and registers. Every level is roughly an order of magnitude smaller and faster than the one below. For an H100 SXM:

HBM deserves a word, because it is the memory you "run out of". It is ordinary DRAM (the same technology as a PC's memory) built as stacks of thin dies placed on the same package as the GPU and joined to it by a very wide interface — 1,024 wires per stack, five or six stacks per GPU. Width, not clock speed, is where the bandwidth comes from. The cost is that capacity and bandwidth are fixed when the chip is built and that each stack is expensive; that is why GPU memory is measured in tens of gigabytes while a CPU server can hold terabytes.

Shared memory is unusual: it is an on-chip scratchpad that the programmer controls explicitly, rather than a cache the hardware manages. A kernel loads a tile of data from HBM into shared memory once, synchronises, and then every thread in the block reads it many times at on-chip speed. It is divided into 32 banks; if the 32 threads of a warp hit 32 different banks, the access completes at once, while several threads hitting different addresses in the same bank must be served one after another — a bank conflict. Tiling with shared memory is how matmul kernels turn HBM-speed data into tensor-core-speed maths; gpu5 builds one.

L2 catches reuse that happens across SMs — for example, many thread blocks reading the same weight tile. At 50 MB it can hold a surprising amount: a whole 4,096 × 4,096 BF16 weight matrix is 32 MB. Kernels sometimes order their work so that blocks running at the same time touch the same data while it is still in L2.

6. Tensor cores: why matrix multiplication is special

An ordinary FP32 lane does one fused multiply-add (FMA) per cycle: d = a × b + c, counted as 2 floating-point operations (FLOPs). A tensor core instead takes small matrix tiles and computes D = A × B + C in one operation — on Hopper, the hardware processes the equivalent of hundreds of FMAs per tensor core per cycle for 16-bit inputs. The result is a lopsided chip. On an H100 SXM, from NVIDIA's datasheet:

Operation typePeak (dense)
FP32 on CUDA cores (element-wise, reductions, softmax…)67 TFLOP/s
TF32 on tensor cores (a reduced-precision stand-in for FP32)~494 TFLOP/s
BF16 / FP16 on tensor cores~989 TFLOP/s
FP8 on tensor cores~1,979 TFLOP/s

The datasheet itself prints twice these numbers (1,979 TFLOP/s for BF16, 3,958 for FP8) with a footnote: "with sparsity". That refers to 2:4 structured sparsity, a mode in which two of every four weights are zero and the tensor core skips them. Almost no training and little inference uses it, so the dense figure — half the headline — is the one to plan with. Always check which one a number is.

The consequence: anything expressible as a matrix multiplication — linear layers, the Q·KT and attention-weights·V products in attention, convolutions (which libraries rewrite as matmuls) — runs on hardware roughly 15 times faster than everything else. Operations that are not matmuls, such as LayerNorm, softmax, the GELU activation function, dropout and residual additions, run on the FP32 lanes. They have few FLOPs, but, as we will see, their real cost is not FLOPs at all. The number formats (TF32, BF16, FP8, FP4) are the subject of gpu4; for now, BF16 is the 16-bit format used for most training.

7. Compute-bound, memory-bound, overhead-bound: a worked example

Every operation's time is set by whichever of three things runs out first: arithmetic, memory bandwidth, or the fixed cost of launching it. Let's compute all three for operations in a transformer layer, on an H100, with a batch of T = 8,192 tokens and hidden size D = 8,192, in BF16 (2 bytes per number).

A matmul, [T, D] × [D, D] — a linear layer. FLOPs: each of the T × D outputs is a dot product of length D, costing D multiplies and D adds, so 2 × T × D × D = 2 × 8,1923 ≈ 1.10 × 1012 FLOPs. Bytes: read the input (T × D × 2 = 134 MB), read the weights (134 MB), write the output (134 MB): about 403 MB. Time for arithmetic at 989 TFLOP/s: 1.10 × 1012 / 989 × 1012 ≈ 1.11 ms. Time for memory at 3.35 TB/s: 403 MB / 3.35 TB/s ≈ 0.12 ms. Arithmetic takes nine times longer, so this matmul is compute-bound: the tensor cores are the bottleneck, which is where you want to be.

A LayerNorm on the same [T, D] tensor. For each element it computes a mean and variance contribution, subtracts, divides and scales — call it about 8 FLOPs per element, 8 × 67 million ≈ 0.54 GFLOPs. These run on the FP32 lanes at 67 TFLOP/s: about 8 µs. Bytes: read 134 MB, write 134 MB: 268 MB, which takes 80 µs. The memory takes ten times longer than the arithmetic: memory-bound. The LayerNorm has 1/2,000 of the matmul's FLOPs but takes 1/14 of its time.

A tiny addition on an [8, D] tensor — say a bias added to a small batch. Arithmetic and memory both take well under a microsecond, but launching a kernel costs a few microseconds of CPU, driver and GPU scheduling time. It is overhead-bound: the GPU spends most of the time waiting for the CPU to tell it what to do next. A model built from thousands of such small operations — common in inference with small batches — can leave a powerful GPU idle most of the time.

The dividing line between compute-bound and memory-bound is the ridge point: peak FLOP/s divided by bandwidth. For the H100 in BF16 it is 989 × 1012 / 3.35 × 1012 ≈ 295 FLOPs per byte. An operation's arithmetic intensity is its FLOPs divided by bytes moved: the matmul has 1.1 × 1012 / 403 × 106 ≈ 2,700 FLOP/byte (above the ridge, compute-bound); the LayerNorm about 2 FLOP/byte (far below it). gpu2 turns this into the full roofline model. The practical lessons are already visible: to go faster, compute-bound work needs better tensor-core use; memory-bound work needs fewer bytes moved — by fusing operations so intermediate results never go back to HBM (gpu6, gpu7), or by using smaller number formats (gpu4); overhead-bound work needs fewer, bigger launches (CUDA graphs, compilation, bigger batches).

8. Shapes: tiles, waves and the 25% vocabulary trick

A matmul library does not compute one output element per thread. It splits the output matrix into tiles — for example 128 × 128 or 256 × 128 elements — and assigns each tile to a thread block, which loops over the shared dimension, loading slices of the inputs into shared memory and feeding them to the tensor cores. Two things follow.

Tile quantization. If a dimension is not a multiple of the tile size, the last tile in each row or column is mostly padding, but costs as much as a full one. Tensor cores also have alignment rules: NVIDIA's performance guide recommends that, for FP16/BF16 on A100 and H100, matrix dimensions be multiples of 64 elements (8 at the very least), and for FP8/INT8 multiples of 128 bytes. Misaligned shapes may force a slower kernel entirely.

Wave quantization. The tiles are distributed across SMs in "waves": with 108 SMs, the first 108 tiles run together, then the next 108, and so on. NVIDIA's guide gives a measured example on an A100 (108 SMs): a matmul with M = 2,304, K = 4,096 and 256 × 128 tiles has 9 tiles per column; at N = 1,536 there are 12 tiles per row, 9 × 12 = 108 tiles — one full wave. At N = 1,544, just 8 columns wider, there are 13 tiles per row and 117 tiles: one full wave plus a second wave with only 9 of 108 SMs busy. The duration roughly doubles for 0.5% more work.

The best-known real case is small but instructive. In February 2023, Andrej Karpathy reported that the most dramatic optimisation to nanoGPT so far — about a 25% speed-up — was to increase the vocabulary size from GPT-2's 50,257 to 50,304, the nearest multiple of 64. The model now computes logits for 47 tokens that never occur, which is wasted arithmetic, but the output-layer matmul (hidden size × 50,304) can now use a well-aligned tensor-core kernel with much higher efficiency. nanoGPT's code still carries the comment "padded up to nearest multiple of 64 for efficiency". The same thinking explains why model designers choose hidden sizes like 4,096 and 8,192, head dimensions of 64 or 128, and MLP widths that are multiples of 256.

Three trends matter. First, compute has outgrown bandwidth: from A100 to B200, dense BF16 grew about 7× while bandwidth grew about 4×, so the ridge point rose and more operations became memory-bound. Second, the extra FLOPs increasingly come from smaller formats: each generation doubles throughput by halving bits (FP8 on Hopper, FP4 on Blackwell), so using those formats well is part of using the hardware well. Third, the unit of computation is growing beyond one GPU: a B200 is two dies joined by a 10 TB/s link and presented as one GPU, and a GB200 NVL72 rack joins 72 GPUs with 130 TB/s of NVLink bandwidth. Rubin (in production in 2026) is notable for rebalancing: HBM4 at about 22 TB/s nearly triples bandwidth, bringing the BF16 ridge point back down. The H200 is the purest example of the bandwidth story: identical compute to the H100, 43% more bandwidth and 76% more memory, and it is markedly faster at LLM decoding for exactly that reason.

Occupancy versus instruction-level parallelism

The simple story says "more warps hide more latency". The full story is that the SM needs enough independent memory operations in flight, and there are two ways to get them. One is thread-level parallelism: many warps, each with one outstanding load. The other is instruction-level parallelism (ILP): fewer warps, each issuing several independent loads before it needs any of the results. Vasily Volkov's well-known 2010 talk "Better performance at lower occupancy" showed matmul and fast Fourier transform (FFT) kernels running faster at low occupancy because each thread did more work from registers. Registers are the fastest storage on the chip; a thread that holds an 8 × 8 tile of the output in registers reuses each loaded input value eight times. That is why the best matmul kernels use close to the 255-register limit per thread and run only a few warps per scheduler. Occupancy is a symptom to check when a kernel is latency-bound, not a target to maximise.

Asynchronous data movement on Hopper: TMA and warp specialisation

On older GPUs, the same threads that did maths also issued loads, computed addresses and waited. Hopper added the Tensor Memory Accelerator (TMA), a hardware copy engine in each SM: one thread describes a multi-dimensional tile ("rows 256-383, columns 0-63 of this matrix") and TMA fetches it from HBM into shared memory asynchronously, computing addresses and handling boundaries itself. Hopper also introduced warpgroup matrix instructions (wgmma), in which four warps (128 threads) issue one large asynchronous matrix multiply that reads its operands straight from shared memory. Together these enable warp specialisation: "producer" warps only issue TMA copies into a ring of shared-memory buffers, while "consumer" warps only issue tensor-core instructions on buffers that are ready. Loading tile k+1 overlaps with computing on tile k. This pipelining is how CUTLASS (NVIDIA's open-source C++ library of matmul kernels) and FlashAttention-3 reach 70-80% of peak on H100, and it is why those kernels are architecture-specific.

Thread block clusters and distributed shared memory

Before Hopper, thread blocks could only share data through L2 or HBM. Hopper groups SMs into GPU processing clusters and lets a kernel launch clusters of thread blocks (up to 8 portably, 16 by opt-in on H100 and B200) that are guaranteed to run at the same time on neighbouring SMs. Blocks in a cluster can read and write each other's shared memory directly — distributed shared memory — and TMA can multicast one tile from HBM into several SMs' shared memory at once. For a matmul, two blocks that need the same slice of B can fetch it once instead of twice, cutting L2 and HBM traffic.

Blackwell: two dies, tensor memory and FP4

A B200 contains 208 billion transistors across two dies, each as large as the lithography machine can print, joined by a 10 TB/s die-to-die link so software sees one GPU. Its fifth-generation tensor cores are driven differently: a single thread can issue a matrix instruction (the tcgen05 family) for the whole SM, and accumulators live in a new dedicated on-SM tensor memory (256 KB per SM) instead of the register file, freeing registers for other work such as the softmax in attention. The tensor cores add FP6 and FP4, with micro-scaling: every small block of values (16 for NVIDIA's NVFP4, 32 for the Open Compute Project's MX microscaling formats) carries its own scale factor, which is what makes 4-bit numbers usable (gpu4 explains the formats). The Blackwell Ultra variant (B300) raises FP4 throughput by about 1.5× and memory to 288 GB but cuts FP64 almost entirely — a sign of which customers now pay for the chips.

Sustained clocks, power and "peak"

Peak FLOP/s assume the chip runs its tensor cores at full boost clock. In practice a dense matmul drives an H100 to its 700 W power limit and the GPU lowers its clock to stay within it, so even a perfect GEMM (general matrix multiply) on an H100 typically sustains around 70-80% of the datasheet dense peak. Temperature matters too: Meta observed a 1-2% daily variation in Llama 3 training throughput that tracked the time of day. When comparing hardware, use measured GEMM throughput at your shapes and formats, not the datasheet.

MFU and HFU

Model FLOPs utilisation (MFU) is the FLOPs the model mathematically needs per second (for a dense transformer, about 6 × parameters × tokens per second in training — gpu3 derives this) divided by peak FLOP/s. Hardware FLOPs utilisation (HFU) also counts FLOPs the hardware performs that the model does not strictly need, such as recomputing activations during activation checkpointing (gpu9). MFU is the honest comparison between systems because recomputation does not count as progress. For large dense-transformer training on H100s, roughly 35-55% MFU is typical; Meta reported 38-43% for Llama 3 405B on 8,192-16,384 GPUs.

The interview framing

For any "why is this slow?" or "how fast could this be?" question, reason in three quantities: how many FLOPs, and on which units (tensor cores or not); how many bytes must move to and from HBM (and across links between GPUs); and whether there is enough parallel work to fill every SM and cover memory latency. Compute the time each would take at peak, take the largest, and you have both a lower bound and the name of the bottleneck. That habit carries through every later topic in this track.

Measuring utilisation honestly

The first production lesson is that the most visible number is the least useful. nvidia-smi's "GPU-Util" is the percentage of time in the sample window during which any kernel was running. A kernel that occupies a single SM counts as 100%. NVIDIA's Data Center GPU Manager (DCGM), which most clusters export to Prometheus, provides better profiling metrics: SM activity (the fraction of time SMs had at least one warp resident, averaged over all SMs), SM occupancy, tensor-pipe activity (how busy the tensor cores were) and DRAM activity (how busy HBM was). A healthy large-model training job shows high tensor-pipe activity; an inference server doing small-batch decoding shows high DRAM activity and low tensor activity — exactly what the arithmetic predicts.

At the job level, teams track MFU from the model's FLOPs and the measured step time. A worked example: a 7-billion-parameter model trains on 8 H100s at 3,200 tokens per second per GPU. Model FLOPs per GPU per second = 6 × 7 × 109 × 3,200 ≈ 1.34 × 1014, against a dense peak of 989 × 1012: MFU ≈ 14%. That is low enough to go looking for gaps — data loading, small micro-batches, unfused operations — before buying more GPUs.

Characteristic failure modes and their symptoms

Starved GPU. The GPU waits for the CPU: data loading, tokenisation or Python overhead between kernels. Symptom: gaps between kernels on the profiler's timeline, low SM activity, and a CPU core at 100%. Fixes: more data-loader workers, pinned memory and asynchronous copies, CUDA graphs or compilation to reduce launch overhead (gpu6, gpu11).

Memory-bound tail. Tensor cores sit idle while normalisation, activation and attention-softmax kernels stream data. Symptom: many short kernels near peak memory bandwidth. Fixes: fused kernels, FlashAttention, torch.compile.

Bad shapes. Odd hidden sizes, vocabulary sizes, or per-GPU batch sizes that produce partial waves. Symptom: matmul kernels far below peak in Nsight Compute. Fixes: pad dimensions to multiples of 64 or 128, choose batch sizes that fill all SMs.

Throttling. Clocks drop when a GPU hits its power or temperature limit. Symptom: one GPU in a server consistently slower, with nvidia-smi -q -d PERFORMANCE reporting power or thermal slowdown. In synchronous data-parallel training, one slow GPU slows every GPU, because all wait for it at each gradient synchronisation.

Hardware faults. At scale, GPUs fail routinely. The Linux driver reports them as numbered Xid errors in the kernel log (for example, uncorrectable ECC errors — errors that the memory's error-correcting codes detected but could not repair or a GPU "falling off the bus"). Meta's Llama 3 paper gives the best public data: in a 54-day snapshot of training on up to 16,384 H100s there were 466 job interruptions, 419 of them unexpected. Of those, 148 (30.1%) were faulty GPUs and 72 (17.2%) were HBM3 memory failures — together almost half — and about 78% of unexpected interruptions were attributed to confirmed or suspected hardware. That is roughly one interruption every three hours. The engineering response is not "buy better GPUs" but to checkpoint frequently, detect and drain failing nodes automatically, and restart fast; Meta reported over 90% effective training time despite the failures.

Power at data-centre scale. The same paper describes a less obvious problem: when thousands of GPUs start or finish a synchronised step together, the site's power draw swings by tens of megawatts in an instant, stressing the power grid. Checkpoints and collective-communication waits cause the same swings. It is a reminder that a GPU cluster behaves as one machine, physically as well as logically.

Knobs people actually turn

Mixed precision: train in BF16 on tensor cores rather than FP32 on CUDA cores (roughly a 15× difference in peak), and on Hopper or Blackwell consider FP8. For FP32 code, PyTorch's torch.set_float32_matmul_precision("high") lets matmuls use TF32 tensor cores. Batch and shape choices that fill all SMs. Fusion and compilation to cut memory traffic and launches. And hardware choice matched to the bottleneck: bandwidth-heavy decoding favours H200 or B200 over H100; very large mixture-of-experts models favour NVL72-class NVLink domains (gpu12).

Goal: predict, with nothing but datasheet numbers, whether an operation is compute-bound, memory-bound or overhead-bound on four GPU generations — the calculation this whole track keeps coming back to. No GPU needed; this machine has none, so everything here is arithmetic that runs on Python 3.12 with the standard library.

  1. Save this as gpu_budget.py and run python gpu_budget.py.
GPUS = {  # name: (dense BF16 tensor TFLOP/s, plain FP32 TFLOP/s, HBM TB/s)
    "A100 80GB": (312, 19.5, 2.04),
    "H100 SXM":  (989, 67, 3.35),
    "H200":      (989, 67, 4.8),
    "B200":      (2250, 75, 8.0),
}
T, D = 8192, 8192                     # tokens x hidden size, BF16 = 2 bytes
OPS = {  # name: (FLOPs, bytes moved, runs on tensor cores?)
    "matmul [T,D]x[D,D]": (2 * T * D * D, 3 * T * D * 2, True),
    "layernorm [T,D]":    (8 * T * D,     2 * T * D * 2, False),
    "tiny add [8,D]":     (8 * D,         3 * 8 * D * 2, False),
}
LAUNCH_US = 5                          # rough per-kernel launch + sync overhead

for gpu, (tc, fp32, bw) in GPUS.items():
    print(f"\n{gpu}: ridge point = {tc / bw:.0f} FLOP/byte")
    for name, (flops, nbytes, tensor) in OPS.items():
        t_c = flops / ((tc if tensor else fp32) * 1e12) * 1e6   # microseconds
        t_m = nbytes / (bw * 1e12) * 1e6
        work = max(t_c, t_m)
        bound = "overhead" if LAUNCH_US > work else ("compute" if t_c > t_m else "memory")
        print(f"  {name:20s} compute {t_c:8.1f} us  memory {t_m:7.1f} us"
              f"  -> ~{work + LAUNCH_US:7.1f} us  {bound}-bound")

LATENCY_NS = 600                       # rough HBM load latency
for gpu, (_, _, bw) in GPUS.items():
    print(f"{gpu}: {bw * 1e12 * LATENCY_NS * 1e-9 / 1e6:.1f} MB must be in flight")

What to look for. On the H100 the matmul takes about 1,112 µs of arithmetic against 120 µs of memory (compute-bound), while the LayerNorm needs 8 µs of arithmetic but 80 µs of memory (memory-bound) — 1/2,000 of the FLOPs, 1/14 of the time. The tiny add is all overhead on every GPU. Moving from H100 to H200 leaves the matmul unchanged but speeds the LayerNorm by about 30%: bandwidth, not compute, is what the H200 adds. The last lines show the Little's Law result: an H100 needs about 2 MB of loads in flight to saturate HBM, a B200 nearly 5 MB.

Try: set T = 16 (a small inference batch) and watch the matmul become memory-bound — its intensity drops to about 16 FLOP/byte. Then set LAUNCH_US = 20 to model a slow Python loop and see how many operations become overhead-bound.

Work it out

A 70-billion-parameter model in BF16 generates one token for one user on an H100 (pretend the weights fit in memory; they don't, at 140 GB). (a) How long does it take just to read the weights from HBM? (b) How long does the arithmetic take at peak? (c) What does the ratio tell you, and what would change on an H200 or B200?

Answer

(a) Weights: 70 × 109 parameters × 2 bytes = 140 GB. Every weight is used once per generated token, so all 140 GB must stream from HBM. At 3.35 TB/s: 140 / 3,350 s ≈ 42 ms.

(b) Generating one token costs about 2 FLOPs per parameter (one multiply and one add per weight): 2 × 70 × 109 = 1.4 × 1011 FLOPs. At 989 × 1012 FLOP/s: ≈ 0.14 ms.

(c) Reading the weights takes about 300 times longer than the arithmetic: single-sequence decoding is entirely memory-bandwidth-bound, using well under 1% of the tensor cores. Its arithmetic intensity is 1.4 × 1011 FLOPs / 1.4 × 1011 bytes = 1 FLOP/byte against a ridge point of 295. On an H200 the time falls to 140 / 4,800 ≈ 29 ms; on a B200 to about 17.5 ms — speed-ups that track bandwidth exactly, while their extra FLOPs do nothing. Every major inference optimisation follows: batching many sequences so each weight read serves many tokens (intensity rises roughly with batch size), quantising weights to FP8 or 4-bit so there are fewer bytes, speculative decoding so each weight read checks several tokens, and choosing high-bandwidth GPUs for decode-heavy serving (gpu10 makes this a full model).
