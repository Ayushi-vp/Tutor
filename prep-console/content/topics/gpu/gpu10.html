A company is about to launch an assistant built on a 70-billion-parameter model. Product wants the first words of an answer on screen within a second and text streaming at least as fast as people read. Finance wants to know how many GPUs to reserve and what each million tokens will cost. Engineering has a week before launch and no time to benchmark every configuration. The questions sound like they need experiments, but most of them can be answered in an afternoon with the arithmetic from this track: FLOPs for the prompt, bytes for each generated token, memory for the KV cache.

The answers are often surprising to people who haven't done the arithmetic. A single user on four H100s gets about 60 tokens per second — and 32 users on the same four GPUs still get about 52 each, because each decode step reads the same weights whatever the batch. The limit on concurrency is usually not compute at all but memory for the KV cache. A single 30,000-token prompt can freeze every other user's answer for two seconds. And at the scale of a large provider, the economics are dominated by batch size: DeepSeek published that its V3/R1 service produced about 14,800 output tokens per second per 8-GPU node while each user saw only 20-22 tokens per second, and reported a theoretical cost-profit margin of 545%.

This lesson builds a quantitative model of LLM serving that predicts these numbers. It defines the metrics users and operators care about — time to first token, time per output token, throughput, goodput — then models prefill as compute-bound and decode as memory-bound, sweeps the batch size to show the throughput-latency curve and the KV-cache ceiling, quantifies tensor parallelism, quantisation and speculative decoding, and explains prefill-decode interference and its fixes. The mechanisms themselves (continuous batching, PagedAttention, prefix caching) are covered in lm13; here the goal is to predict their effect with numbers, and to check the model against published production data.

The kitchen and the conveyor belt

Think of a restaurant where every dish is made in two stages. First the chef reads the whole order and preps everything at once — a big burst of work, done fast because it can use every burner (prefill). Then courses come out one at a time, each needing a trip to a walk-in pantry to fetch every ingredient in the restaurant, whether the course uses them or not (decode — every step reads all the weights). The pantry trip takes the same time whether you're plating one table's course or forty tables' courses, so a smart kitchen plates many tables' next course on each trip. Diners each wait a little longer per course, but the kitchen serves far more people. The catch: every table's order history must stay on the counter (the KV cache), and the counter has limited space.

The analogy's limit: in a real GPU the "pantry trip" is streaming tens of gigabytes of weights from HBM, and the counter space is the same memory that holds the weights.

Why the goals pull against each other

Users and operators want different things from the same GPUs. A user wants a short wait for the first word (TTFT) and a steady stream afterwards — people read at roughly 4-8 tokens per second, so anything above about 20 tokens per second feels instant, while a chat that pauses mid-sentence feels broken. An operator wants each GPU to produce as many tokens per second as possible, because that sets the cost per token. The two meet in the batch size. Serving one user at a time gives the fastest stream and wastes nearly all of the GPU's compute; packing hundreds of users into each step makes tokens cheap and each user's stream slower; admitting every new prompt immediately helps TTFT but stalls everyone already streaming. Every serving technique in this lesson — batching policies, parallelism, quantisation, speculative decoding, chunked prefill, disaggregation — is a way of moving along or shifting this trade-off, and the arithmetic below tells you by how much.

Two simple models predict most of it

Prefill is compute-bound. A 2,000-token prompt through a 70B model is 2 × 70 × 109 × 2,000 = 2.8 × 1014 FLOPs; four H100s delivering about half their 989 TFLOP/s peak do it in about 0.14 s. Decode is memory-bound. Each step must read every weight — 140 GB in BF16, 35 GB per GPU on four GPUs — which at about 80% of 3.35 TB/s takes about 13 ms, plus communication, however few tokens are being generated. Notice that neither number depends much on the other: prefill cares about FLOPs, decode about bytes, which is why the two phases are increasingly run and tuned separately. Everything else in this lesson refines these two lines: adding the KV cache to decode's bytes, adding batch size, adding parallelism and queueing.

1. The metrics

  • TTFT (time to first token): from request arrival to the first output token — queueing plus prefill. Users perceive it as responsiveness.
  • TPOT (time per output token) or ITL (inter-token latency): the gap between successive tokens once streaming starts — essentially one decode step. It sets reading speed: 50 ms per token is 20 tokens per second, comfortably faster than reading.
  • End-to-end latency: TTFT + (output tokens − 1) × TPOT. For a 500-token answer at 25 ms per token, 12.5 s after the first token.
  • Throughput: total tokens per second across all users on a replica or fleet — what determines cost.
  • Goodput: throughput counting only requests that met their latency targets. A server can raise throughput by batching so aggressively that most requests miss their target; goodput exposes that.

Targets are set on percentiles (p50, p95, p99) under realistic load, because users notice the slow tail, not the average.

2. Modelling prefill

Prefill runs the whole prompt through the model in one pass: 2N FLOPs per prompt token for the weights, plus the attention term (4·L·T·d per token for context T, gpu3), which matters for long prompts. With thousands of tokens per matmul, it is compute-bound and reaches perhaps 40-70% of peak:

prefill time ≈ 2 · N · prompt_tokens / (GPUs · peak FLOP/s · efficiency)

For Llama 3 70B on four H100s at 50% efficiency: 2,000 tokens take about 142 ms; 32,000 tokens take about 2.3 s, and more once attention's quadratic term is added. Real systems report similar efficiency: Pope et al. (Google) reached 76% MFU processing input tokens for PaLM 540B at large batch. The main lever beyond hardware is not doing the work: prefix caching reuses the KV cache of repeated prefixes (system prompts, documents in a conversation, earlier turns), so only the new tokens are prefilled. DeepSeek reported that 56.3% of its input tokens over a day hit its on-disk KV cache.

3. Modelling a decode step

Each decode step generates one token for every sequence in the batch. It must read all weights once, and each sequence's entire KV cache:

bytes per GPU per step = weight bytes / TP  +  Σ(context lengths) × KV bytes per token / TP
step time ≈ bytes per GPU / (bandwidth × efficiency)  +  communication
compute check: 2 · N · batch / (GPUs · peak · efficiency)  — must stay smaller

Llama 3 70B in BF16 has KV of 2 × 80 layers × 8 KV heads × 128 × 2 bytes = 320 KiB per token. With tensor parallelism across four H100s, each GPU holds 35 GB of weights. At batch 1: 35 GB at 80% of 3.35 TB/s ≈ 13 ms, plus about 160 all-reduces (two per layer) at roughly 20 µs each ≈ 3 ms: about 16 ms per token, about 61 tokens per second. The arithmetic is 0.14 TFLOPs, about 0.07 ms per GPU — the GPUs spend over 99% of the step waiting for memory. (Pope et al.'s PaLM 540B figure of 29 ms per token with int8 weights on TPUs is the same regime.)

4. The batch-size curve and the KV ceiling

Three limits end the free lunch. KV reads grow with batch × context and are never shared, so step time rises (by batch 128 the KV bytes equal the weight bytes). KV memory: 80 GB × 4 GPUs at 90% utilisation, minus 140 GB of weights, leaves about 148 GB for cache — about 150 sequences of 3,000 tokens. Compute: at batch 150 the step's matmuls need only about 5 ms, so compute-bound is far away; with shorter contexts or FP8 KV, much larger batches fit and compute becomes the limit around a few hundred sequences. Which limit binds first depends on context length, which is why agent and document workloads with long contexts are so much more expensive to serve than short chats.

5. Tensor parallelism: buying latency

Tensor parallelism divides the weight and KV bytes each GPU reads per step. For the 70B model at batch 1: on 4 GPUs, 35 GB per GPU, about 16 ms per token; on 8 GPUs, 17.5 GB per GPU — about 6.5 ms of memory time plus the same ~3 ms of all-reduces, about 10 ms per token, 100 tokens per second. Doubling the GPUs bought 1.6× lower latency, not 2×, because communication and fixed overheads don't shrink. Meanwhile, throughput per GPU usually falls: an 8-GPU replica must run a bigger batch to match two 4-GPU replicas. The rule: use the smallest TP degree that fits the weights plus enough KV cache for the target batch, and raise it only when the latency target demands. (With FP8 weights, 70 GB, the same model fits on 2 H100s with modest KV room, halving GPUs per replica at a cost in latency and batch size.)

6. Quantisation as a serving lever

Every byte removed from a decode step is time saved (gpu2, gpu4). FP8 or int8 weights halve the weight bytes: on four H100s, the batch-1 step's memory time falls from 13 to 6.5 ms, and 70 GB is freed for KV cache, raising the maximum batch from about 150 to about 220 sequences of 3,000 tokens. FP8 KV cache halves KV bytes, doubling concurrency again and halving the KV part of each step. 4-bit weights go further for bandwidth-bound small-batch serving. Prefill, being compute-bound, speeds up only if the arithmetic itself moves to FP8 or FP4, not merely the storage. Each change needs quality validation on the product's own evaluations.

7. Speculative decoding, quantified

Decode is memory-bound, so verifying several tokens in one pass costs about the same as generating one. Speculative decoding exploits this: a cheap draft (a small model, extra prediction heads, or n-gram lookup) proposes γ tokens; the target model processes all γ + 1 positions in one forward pass and accepts the longest prefix consistent with its own distribution, plus one token of its own. The output distribution is exactly the target's. If each draft token is accepted independently with probability α, the expected number of tokens per target pass is a geometric sum:

E[tokens per target pass] = 1 + α + α² + … + α^γ = (1 − α^(γ+1)) / (1 − α)
α = 0.8, γ = 4:  (1 − 0.8^5) / 0.2 = 3.36
α = 0.6, γ = 4:  (1 − 0.6^5) / 0.4 = 2.31

The wall-clock speed-up is lower: if a draft pass costs c of a target decode step and verification costs slightly more than one step, the speed-up is roughly E / (1 + γ·c). With c = 0.05, 3.36 / 1.2 ≈ 2.8×. Published gains span that range: PyTorch's gpt-fast saw about 2× for CodeLlama-34B with a 7B draft on code and 1.3× for Llama-7B with TinyLlama (gpu2); DeepSeek-V3's multi-token-prediction head had its second-token prediction accepted 85-90% of the time, giving about 1.8× more tokens per second. The gains shrink as batch grows: at large batches the target step is closer to compute-bound, so verifying tokens that are then rejected costs real FLOPs.

8. Scheduling: prefill-decode interference

Continuous batching (lm13) adds new requests to the running batch at any step. When a new request's prefill runs in the same step as everyone's decode, every decoding user waits for it. A 32,000-token prompt on four H100s is about 2.3 s of prefill: every active user's stream pauses for 2.3 seconds mid-answer, and p99 inter-token latency explodes.

Chunked prefill limits the tokens processed per step (for example 512-2,048) and splits long prompts into chunks that ride along with decode steps. Each step's time is bounded, so inter-token latency stays predictable, and the decode steps' spare compute is used productively by the prefill chunk. Sarathi-Serve, which introduced "stall-free batching" on this principle, reported 2.6× higher serving capacity under latency targets for Mistral-7B on one A100, 3.7× for Yi-34B on two, and up to 5.6× for Falcon-180B. Disaggregation puts prefill and decode on different GPU pools: prefill nodes run compute-bound batches of prompts; decode nodes run large memory-bound batches; the KV cache is transferred between them over the network. DistServe reported serving up to 7.4× more requests (or 12.6× tighter latency targets) within SLOs than the systems it compared against. The cost is the KV transfer and operating two pools.

9. A real system: DeepSeek's V3/R1 service

In February 2025 DeepSeek published an overview of its production inference system for DeepSeek-V3 and R1 (671B total, 37B active parameters, MoE), and it reads like a worked example of this lesson. Prefill and decode are disaggregated. Prefill runs with expert parallelism across 32 GPUs (4 nodes), each GPU holding 9 routed experts; decode runs with expert parallelism across 144 GPUs (18 nodes), 2 routed experts per GPU — a much wider spread, because decode needs huge batches so each expert sees enough tokens per step to be efficient. Matmuls and expert dispatch use FP8, attention (MLA) and the combine step BF16. Over one day: 608 billion input tokens, of which 342 billion (56.3%) hit the on-disk KV cache and skipped prefill; 168 billion output tokens; average per-user output speed 20-22 tokens per second; average KV length per output token 4,989 tokens. Each H800 node delivered about 73,700 input tokens per second in prefill (including cache hits) or about 14,800 output tokens per second in decode.

The economics follow. At DeepSeek's stated $2 per GPU-hour, a decode node costs $16 per hour and produces about 14,800 × 3,600 ≈ 53 million output tokens: roughly $0.30 per million output tokens. The service averaged 226.75 nodes over the day (peak 278), $87,072 in daily cost, against $562,027 of theoretical revenue at R1 prices — the 545% cost-profit margin they reported, before discounts and free usage. Note the per-user speed: 20-22 tokens per second is modest, the visible price of running decode at very large batch to amortise weight and expert reads — exactly the throughput-latency trade-off of section 4.

Queueing: why TTFT explodes before the GPUs are "full"

TTFT includes waiting in the queue, and queues follow the behaviour from sc1: as utilisation approaches 100%, waiting time grows like 1/(1 − utilisation). A replica whose prefill capacity is 10 requests per second is comfortable at 5 per second and miserable at 9.5, even though it is "only" 95% busy — especially with bursty arrivals and a wide spread of prompt lengths, where one long prompt holds up many short ones. Capacity plans therefore target peak utilisation well below 100% (often 60-80%) for the latency-critical phase, and admission control or priority queues protect interactive traffic from batch jobs sharing the same fleet.

MoE inference: bytes follow the experts you touch

For a mixture-of-experts model, FLOPs per token follow the active parameters, but the bytes read per decode step depend on how many distinct experts the batch touches. At batch 1 a token reads only its few experts — cheap. At batch 1,000 with 256 experts and 8 chosen per token, nearly every expert is touched each step, so nearly all expert weights are read, yet each expert processes only about 1,000 × 8 / 256 ≈ 31 tokens — an intensity of about 31 FLOP/byte for its matmul, well below the ridge. To make experts efficient, the batch per expert must grow, which means enormous global batches and experts spread across many GPUs (expert parallelism) with all-to-all communication each layer (gpu8). DeepSeek's EP144 decode configuration is this reasoning in production, and large NVLink domains such as NVL72 exist partly to make it cheaper.

Attention at long context

Decode attention's bytes are the KV cache, and its intensity is the GQA group size (gpu2), so at long context it dominates the step: at 32,000 tokens, one sequence of Llama 3 70B reads 10.5 GB of KV per step — more than a quarter of what the weights cost per GPU on 4 GPUs, for a single user. Techniques that shrink KV bytes — FP8 KV, grouped or latent attention (MLA), sliding-window layers, KV eviction and compression — are therefore as important for long-context serving as weight quantisation is for short contexts, and Flash-Decoding-style split-KV kernels (gpu7) are needed to keep the GPU busy when the batch is small.

Operating points: the same hardware, different products

One deployment can be tuned for very different products. A coding assistant with strict latency targets might run a 70B model at batch 16 on eight GPUs with speculative decoding — perhaps 100 tokens per second per user and a high cost per token. A batch summarisation service with no latency target runs the same model at the KV-limited batch on four GPUs with FP8 weights and KV — each request slow, tokens several times cheaper. Providers often price these as separate tiers (interactive versus batch APIs at a discount), which is the throughput-latency curve of section 4 turned into a price list.

Where the simple model is wrong

The roofline model gives lower bounds. Real engines lose time to scheduling on the CPU between steps (mitigated by CUDA graphs and asynchronous scheduling, gpu6), to kernels that run below bandwidth at small shapes, to padding and fragmentation, to sampling and detokenisation, and to all-reduce latency that the bandwidth term underestimates. Databricks' measurements of MBU (gpu2) show it typically between 50% and 80% and falling as tensor parallelism rises. A good practice is to calibrate the model: measure the step time at two batch sizes, fit the fixed and per-sequence costs, and then use the fitted model for planning rather than the datasheet.

Offloading and cache hierarchies

KV caches don't have to live only in HBM. Systems keep hot prefixes in GPU memory, warm ones in host memory, and cold ones on local NVMe or distributed storage — DeepSeek's "on-disk KV cache" served over half of its input tokens — and load them back instead of recomputing prefill. Whether loading beats recomputing depends on arithmetic: loading costs bytes ÷ link bandwidth (PCIe, network, disk), recomputing costs 2N FLOPs per token on the GPU. For a 70B model, recomputing one token costs 1.4 × 1011 FLOPs (about 0.07 µs on four H100s at half peak), while loading its 320 KiB over a 50 GB/s link takes about 6.5 µs — so per token, recomputing is faster than loading over the network; but recomputation competes with other requests for GPU compute, while loading uses otherwise idle links. Real systems weigh both, and prefix caches pay off most when prefixes are long and heavily reused.

Metrics that matter in production

Serving dashboards track TTFT and ITL percentiles (p50, p95, p99), end-to-end latency, output tokens per second per replica and per GPU, queue length and queueing time, number of running and waiting sequences, KV-cache utilisation, preemption counts, prefix-cache hit rate, and prompt and output length distributions. The last two matter because they explain most changes in the others: a product change that lengthens system prompts or adds retrieved documents shifts load from decode to prefill and shrinks the KV-limited batch, and it shows up first as rising TTFT and cache utilisation.

Failure modes and their signatures

KV-cache exhaustion. When the cache fills, engines such as vLLM preempt sequences — evicting their cache and recomputing it later — or stop admitting new requests. Symptoms: cache utilisation pinned near 100%, preemption counters rising, and sporadic very slow requests. Fixes: FP8 KV, lower maximum concurrency, capping context length, or more replicas.

Prefill storms. A burst of long prompts (a batch job, a new document feature) spikes TTFT for everyone and, without chunked prefill, ITL for everyone mid-stream. Fixes: chunked prefill with a sensible token budget, separate pools or priority for batch traffic, disaggregation at larger scale.

Latency cliffs at specific batch sizes. CUDA graphs captured only for some batch sizes, so others pad up or run uncaptured (gpu6); or tile and wave quantization in matmuls (gpu1).

Slow autoscaling. Starting a replica means provisioning a GPU node and loading tens to hundreds of gigabytes of weights and compiling kernels — minutes, not seconds. Capacity must be provisioned ahead of predictable peaks, with headroom for unpredictable ones.

Load testing honestly

Benchmarks that send identical short prompts at a fixed rate overstate capacity. Realistic load tests replay production-like distributions of prompt and output lengths, prefix-sharing patterns and arrival burstiness, measure percentiles rather than averages, and report goodput at the latency targets — the open-loop, coordinated-omission-aware methodology of sc16 applied to LLMs. Tools such as vLLM's serving benchmark and NVIDIA's GenAI-Perf generate such load. The output of a load test is a curve of goodput versus request rate, and the planning number is the rate at which p95 targets are still met, not the rate at which the server starts returning errors.

Turning the model into a plan

Record the configuration with every measurement — model version, quantisation, engine version, TP degree, batch limits, GPU type — because each of them moves the numbers by tens of percent.

A production capacity plan combines: traffic forecast (peak requests per second, token distributions, cache-hit rates), targets (p95 TTFT, p95 ITL), the calibrated per-replica model (prefill capacity, decode step time versus batch, KV limit), and operational headroom (failures, deploys, bursts). It yields replicas per region and GPUs per replica, and a cost per million tokens that product and finance can use (gpu12). DeepSeek's published figures are a useful sanity check for any such plan: at very large batch, output tokens can cost well under a dollar per million on H800-class hardware; at low batch and strict latency, costs are an order of magnitude higher.

Work it out

Answer

KV read per step: 64 × 2,048 × 320 KiB ≈ 43 GB in total, about 10.7 GB per GPU.

Bytes per GPU per step: 35 + 10.7 ≈ 45.7 GB → at 80% of 3.35 TB/s ≈ 17 ms, plus about 3 ms of all-reduces ≈ 20 ms per step.

Per user: about 50 tokens/s. Aggregate: 64 × 50 ≈ 3,200 tokens/s — about 50 times the batch-1 throughput for about 25% more latency per token.

Compute check: 2 × 70 × 109 × 64 ≈ 9 × 1012 FLOPs per step, about 2.2 × 1012 per GPU → about 4.5 ms at 50% of peak, well below 17 ms: still memory-bound.

Doubling throughput within 40 ms: batch 128 would need 21.5 GB of KV per GPU — 56.5 GB per step, about 21 ms + 3 ms ≈ 24 ms — and the total 86 GB of KV fits in the ~148 GB free, so simply raising the batch gives about 5,300 tokens/s at about 42 tokens/s per user. To go further, FP8 KV halves the KV bytes (more sequences and shorter steps), and FP8 weights halve the 35 GB per GPU — together allowing roughly 250+ sequences within the 40 ms target. Speculative decoding would help per-user latency more than throughput at these batch sizes.
