An inference team serves a 70-billion-parameter model on H100s. Latency is too high, so they propose three fixes: upgrade to B200s, which have more than twice the FLOPs; rewrite the attention kernel; or quantise the weights to 4 bits. Each costs weeks. Someone else asks a better question first: what is this workload actually waiting for? For a chatbot generating answers one token at a time, it turns out to be waiting for memory — reading 140 GB of weights for every token — while the arithmetic units sit more than 99% idle. That single observation ranks the options immediately. Quantising the weights cuts the bytes by four and should help a lot. The B200 helps, but because its memory is 2.4× faster, not because of its FLOPs. Rewriting attention helps only if attention is where the bytes are.

Now flip the workload: the same team fine-tunes the model on long documents. Here thousands of tokens pass through each weight matrix at once, the arithmetic units are the bottleneck, and 4-bit weights do almost nothing for speed, while FP8 arithmetic nearly doubles it. Same model, same hardware, opposite advice. Engineers who don't know which situation they are in waste months optimising the wrong thing.

The roofline model is the tool that tells you which situation you're in. It needs only two numbers about an operation — how many floating-point operations it does and how many bytes it moves — and two numbers about the chip — peak FLOP/s and memory bandwidth. From them it gives an upper bound on speed, names the bottleneck, and shows which optimisations can possibly help. It is the single most useful model in ML performance work and the one interviewers lean on most: "why is decoding memory-bound?", "why does batching help?", "why did quantisation make it faster but not twice as fast?".

This lesson teaches you to count FLOPs and bytes for real operations, to draw and read the roofline, to derive why a matmul's intensity is roughly its batch size and why decode attention's is the GQA group size, and to place every piece of a transformer on the chart. We then walk through a real, public optimisation — PyTorch's gpt-fast, which took Llama-7B decoding on an A100 from 25 to over 200 tokens per second — explaining each step with the roofline, and finish with the limits of the model and how it is used in production.

The loading dock and the assembly line

Picture a factory with a loading dock and an assembly line. Crates of parts arrive at the dock at a fixed rate — say 100 crates an hour. The assembly line can do a fixed amount of work per hour. Whether the factory is limited by the dock or the line depends on one thing: how much work each crate enables. If each crate holds one bolt that takes a second to fit, the line sits idle waiting for crates; the dock is the bottleneck. If each crate holds a kit that takes an hour to assemble, crates pile up; the line is the bottleneck. Between the two there is a break-even amount of work per crate at which both are exactly busy.

A GPU is that factory. The loading dock is memory bandwidth — how many bytes per second HBM can deliver to the SMs (3.35 TB/s on an H100). The assembly line is peak compute — how many floating-point operations per second the tensor cores can do (about 989 trillion in BF16, dense). "Work per crate" is arithmetic intensity:

arithmetic intensity = FLOPs performed / bytes moved to and from memory

The break-even point is the ridge point: peak FLOP/s ÷ bandwidth = 989 × 1012 / 3.35 × 1012 ≈ 295 FLOP/byte for an H100. An operation doing fewer than 295 FLOPs per byte it moves will leave tensor cores idle waiting for data — it is memory-bound. One doing more will leave memory idle waiting for arithmetic — it is compute-bound.

Where the analogy breaks: a real factory's crates can be reused only once, but a GPU can keep data on chip and reuse it many times — which is exactly how good kernels raise their intensity. Intensity is not fixed by the problem; it depends on how cleverly the work is organised.

The roofline picture

The whole model is one line of algebra:

attainable FLOP/s = min( peak FLOP/s,  intensity × bandwidth )

Plotted with intensity on the horizontal axis and FLOP/s on the vertical, both on logarithmic scales, it looks like a roof: a rising slope on the left, where speed is intensity × bandwidth, and a flat top on the right, where speed is peak compute. The two meet at the ridge point.

Reading the chart gives you the whole method. Find the operation's intensity on the x-axis; go up to the roof; that height is the best FLOP/s it can reach. If you are on the slope, making arithmetic faster does nothing — you need to move right (more FLOPs per byte) or raise the slope (more bandwidth). If you are on the flat top, moving right does nothing — you need a higher roof (faster arithmetic, such as FP8) or less work. The rest of this lesson is about computing intensities correctly and knowing which moves are available.

1. Counting FLOPs

A FLOP is one floating-point addition or multiplication. Counting them for ML operations needs only a few rules.

Matrix multiplication. Multiplying an m × k matrix by a k × n matrix produces m × n outputs, each a dot product of length k: k multiplies and k − 1 adds, which we round to 2k. Total: 2·m·k·n FLOPs. This rule is the workhorse; learn it cold. A [1, 8,192] × [8,192, 8,192] matrix-vector product is 2 × 8,1922 ≈ 134 million FLOPs; an [8,192, 8,192] × [8,192, 8,192] matmul is 2 × 8,1923 ≈ 1.1 trillion.

Element-wise operations — add, multiply, GELU, dropout — do a small constant number of FLOPs per element: one for an add, perhaps 10-20 for a GELU using a tanh approximation. Reductions and normalisations such as softmax and LayerNorm do a handful per element too: softmax computes a maximum, subtracts it, exponentiates, sums and divides, around 5 per element. Precision here is rarely important, because these operations are almost never limited by FLOPs — as we'll see, the bytes decide their speed.

Two cautions. Some sources count a multiply-add as one operation ("MACs"); in this track one multiply-add is 2 FLOPs, matching how NVIDIA quotes peak TFLOP/s. And the FLOPs that matter for the roofline are those executed on the unit you're comparing against: matmuls run on tensor cores, everything else on the CUDA cores, which on an H100 have a roof about 15 times lower (67 TFLOP/s in FP32).

2. Counting bytes

For the roofline we count the minimum traffic to HBM: every input read once, every output written once. That is what an ideal kernel achieves, because it keeps anything it reuses on chip. Real kernels can move more (if tiles don't fit on chip and data is re-read) or occasionally less (if a small operand stays in the 50 MB L2 cache between kernels), but the minimum is the right starting point.

Bytes depend on the number format: 4 bytes per element for FP32, 2 for BF16 or FP16, 1 for FP8 or int8, half a byte for 4-bit formats. For a BF16 matmul of m × k by k × n, the minimum traffic is 2·(m·k + k·n + m·n) bytes — read both inputs, write the output.

The pattern is stark. Everything that is not a matrix multiplication sits between 0.1 and 5 FLOP/byte — two or three orders of magnitude below the H100's ridge at 295. Only matrix-matrix products with large dimensions reach the compute-bound region, and they do so because each loaded element takes part in many multiplications: in an n × n matmul, each input element is used n times.

A worked check: a GELU on a [8,192, 8,192] BF16 tensor (67 million elements) moves 4 × 67 M = 268 MB. At 3.35 TB/s that takes at least 80 µs. Its 940 million FLOPs would take 14 µs even on the FP32 lanes. So its roofline time is 80 µs, and a well-written GELU kernel runs in perhaps 90 µs. No kernel trick can do much better — except not reading and writing the tensor at all, by computing GELU inside the matmul that produced it. That is kernel fusion, and it is the entire reason compilers like torch.compile and tools like Triton exist (gpu6).

4. The roofline, precisely

With intensity I, peak compute P and bandwidth W, the best achievable rate is min(P, I × W), and the best achievable time for an operation with F FLOPs and Q bytes is:

time ≥ max( F / P ,  Q / W )

These are the same statement: whichever resource takes longer sets the time. The ridge point I* = P / W is where F/P = Q/W. Notice two things about the H100 numbers. First, the memory slope is so shallow relative to the roof that an operation at intensity 10 reaches only 33.5 TFLOP/s — 3% of peak. Second, there is not just one roof. Each precision and unit has its own: FP32 on CUDA cores 67 TFLOP/s, TF32 on tensor cores about 494, BF16 about 989, FP8 about 1,979. The ridge point moves with the roof: for FP8 compute, it is 1,979 / 3.35 ≈ 590 FLOP/byte. Using a faster format raises the ceiling but also means you need more reuse to reach it.

The same arithmetic applies to every GPU. The ridge point was about 153 on the A100, is about 295 on the H100, about 206 on the H200 (same compute, 4.8 TB/s), and about 281 on the B200 (2.25 PFLOP/s, 8 TB/s). A lower ridge point means more operations are compute-bound — the H200 is the "memory-bound workloads" edition of the H100.

5. Batch size and the matmul: the free-lunch zone

The most important derivation in LLM performance: a batch of B token vectors, each of width d, multiplied by a d × f weight matrix. FLOPs are 2·B·d·f. Bytes are 2·B·d (activations in) + 2·d·f (weights) + 2·B·f (activations out). When B is much smaller than d and f — as in decoding, where B is the number of sequences, maybe 1 to 256, and d and f are several thousand — the weight term dominates the bytes:

intensity = 2·B·d·f / (2·B·d + 2·d·f + 2·B·f)  ≈  2·B·d·f / 2·d·f  =  B

Intensity is roughly the batch size. One sequence reads each 2-byte weight to do 2 FLOPs: 1 FLOP/byte. Sixty-four sequences read each weight once and use it 64 times: 64 FLOP/byte. The weight read is shared by the whole batch; the activations are tiny by comparison. On an H100, the weight matmuls cross the ridge at roughly B ≈ 300.

Concretely, take the MLP up-projection of a 70B-class model: d = 8,192, f = 28,672, weights 470 MB in BF16. From the roofline:

From batch 1 to 256 the step time barely moves — 140 µs to 146 µs — because it is set by reading 470 MB of weights, and the extra arithmetic is hidden inside that time. Throughput rises 256-fold for nothing. This is the free-lunch zone, and it is why every LLM server batches requests together (continuous batching, lm13). Past the ridge the lunch ends: at B = 1,024 the step takes 3.3 times longer, and cost per token only falls from 0.57 to 0.47 µs.

The same formula explains why prefill and training are compute-bound: a prompt of 2,000 tokens through the same matrix is B = 2,000 rows, intensity around 1,500, well above the ridge. "Prefill of 300 tokens" and "decode batch of 300 sequences" have identical intensity for the weight matmuls — both are 300 rows through the weights.

6. Decode attention: the part batching can't fix

Attention during decoding is different, because its "weights" are the KV cache (lm5): the key and value vectors of every earlier token in this sequence. Nothing is shared between sequences, so batching doesn't amortise anything.

Count one KV head over a context of L tokens with head dimension dh, in BF16. Reading K and V costs 2 × L × dh × 2 bytes = 4·L·dh bytes. With grouped-query attention (GQA), g query heads share that KV head — Llama 3 70B has 64 query heads and 8 KV heads, so g = 8. Each query head computes its scores against all L keys (2·L·dh FLOPs) and a weighted sum of all L values (another 2·L·dh): 4·L·dh FLOPs per query head, 4·g·L·dh for the group. Intensity = 4·g·L·dh / 4·L·dh = g. With g = 8, decode attention runs at 8 FLOP/byte — permanently memory-bound, whatever the batch size and context length.

And the bytes are large. Llama 3 70B has 80 layers, 8 KV heads and dh = 128, so each token's cache is 2 (K and V) × 80 × 8 × 128 × 2 bytes ≈ 0.33 MB. A sequence with 8,000 tokens of context carries 2.6 GB of cache, all read at every decode step. A batch of 64 such sequences reads about 170 GB of KV per step — more than the 140 GB of weights. At long context, attention, not the weight matmuls, dominates decode time.

7. A full decode step, end to end

Put the pieces together for a realistic serving setup: a 70B model in BF16 on eight H100s using tensor parallelism (each GPU holds an eighth of every weight matrix — dl9 and gpu10 cover this), 32 concurrent sequences with 4,096 tokens of context each.

  • Weight bytes per GPU per step: 140 GB / 8 = 17.5 GB.
  • KV bytes per GPU per step: 32 × 4,096 tokens × 0.33 MB = 43 GB across the system, 5.4 GB per GPU.
  • Memory time: (17.5 + 5.4) GB / 3.35 TB/s ≈ 6.8 ms.
  • FLOPs per GPU: weights 2 × 70 × 109 × 32 / 8 ≈ 0.56 TFLOP; attention 4 × 8 query heads per KV head × 4,096 × 128 × 80 layers × 8 KV heads × 32 sequences / 8 GPUs ≈ 0.04 TFLOP. At 989 TFLOP/s: about 0.6 ms.

The step is memory-bound by more than 10×: the roofline minimum is about 6.8 ms per step, so at best 32 / 0.0068 ≈ 4,700 tokens per second across the server, or about 147 tokens per second per user, before communication and overhead (which gpu10 adds). The breakdown also tells you what to do next: weights are three-quarters of the bytes, so FP8 or 4-bit weights are the biggest lever; KV is the rest and grows with batch and context, so KV quantisation matters more as traffic grows; faster FLOPs are irrelevant here.

8. The moves: how each optimisation shifts you on the chart

Every performance technique in this track is one of a few moves on the roofline.

  • Batching raises intensity for anything with shared weights (move right).
  • Fusion removes intermediate reads and writes: a fused matmul + bias + GELU does the same FLOPs but skips 2 passes over the activation (move right).
  • On-chip reuse / tiling — FlashAttention, tiled matmuls — keeps data in shared memory so each HBM byte serves more FLOPs (move right).
  • Weight or KV quantisation halves or quarters the bytes (move right) without changing the arithmetic format.
  • Lower-precision arithmetic (FP8, FP4) raises the roof and the ridge; it helps only operations already near or above the ridge.
  • More bandwidth (H200, B200, Rubin) steepens the slope, speeding every memory-bound operation proportionally.

9. A real case: gpt-fast, step by step

In late 2023 the PyTorch team published "GPT, Fast": a from-scratch Llama-7B decoder in under 1,000 lines of plain PyTorch, benchmarked at batch size 1 on an A100-80GB (power-limited to 330 W). Every step is a roofline argument.

Start: 25.5 tokens/s. The first version was overhead-bound: the trace showed the GPU idle between hundreds of tiny kernel launches while single-threaded Python decided what to do next. It sat far below the roofline entirely.

torch.compile with CUDA graphs and a static KV cache: 107 tokens/s. Compiling the decode step into one captured graph removed the launch gaps (gpu6). Now check against the roofline: 7 billion parameters × 2 bytes = 14 GB read per token; 14 GB × 107 tokens/s ≈ 1.5 TB/s, against the A100's roughly 2 TB/s. The team called this model bandwidth utilisation (MBU) of about 72% — close to what even a plain memory copy achieves. The conclusion: at batch 1 there is at most 10-20% left from better kernels. To go faster, change the bytes.

int8 weight-only quantisation: 157 tokens/s. Weights stored in 8 bits, converted to BF16 inside the fused kernel: half the bytes, about 50% faster. A revealing detail: without torch.compile, the int8 version was slower than FP16, because the dequantisation ran as a separate kernel that wrote the BF16 weights back to memory — adding bytes instead of removing them.

int4 with GPTQ: 202 tokens/s. A quarter of the bytes, with per-32-element scale factors and GPTQ — a method that uses sample data to choose rounded weights that minimise the layer's output error (lm12) — to protect accuracy, and hand-written fused int4 kernels.

Speculative decoding: up to 244.7 tokens/s combined. This one changes the problem: a small draft model proposes several tokens and the large model checks them all in one pass, which is a batch of several rows through the weights — more FLOPs per weight read (move right). The gains depended on how often the draft was right: about 2× for CodeLlama-34B with a 7B draft on code, 1.3× for Llama-7B with TinyLlama.

Tensor parallelism: splitting each matrix across GPUs adds their bandwidths together, which is why Llama-70B reached 80 tokens/s on several GPUs. From 25 to over 240 tokens/s — nearly 10× — with no new hardware, each step chosen by asking which ceiling was nearest.

Realistic ceilings and the "speed of light"

The datasheet roofs are theoretical. A well-tuned large BF16 GEMM on an H100 typically sustains around 70-80% of the dense peak, because clocks fall under the 700 W power limit and pipelines have start-up and tail costs. Memory-bound kernels top out at roughly 80-90% of HBM bandwidth; gpt-fast noted that "even just copying memory struggles to break 85%". Performance engineers therefore draw an empirical roofline from measured peak GEMM and memory-copy throughput, and judge a kernel against that. NVIDIA's Nsight Compute presents this as "speed of light" percentages — how close a kernel is to the compute and memory ceilings — and can draw the roofline chart with the kernel plotted on it. A kernel at 20% of both ceilings has a problem the roofline can't see: latency, launch overhead or too little parallelism.

Hierarchical rooflines

Every memory level has its own bandwidth: HBM at 3.35 TB/s, L2 several times higher, shared memory tens of TB/s summed across SMs. A kernel therefore has a separate intensity for each level — FLOPs per byte of HBM traffic, per byte of L2 traffic, per byte of shared-memory traffic — and a separate slope. A tiled matmul may be far above the ridge relative to HBM yet close to the shared-memory limit, which is why kernel authors care about bank conflicts and register reuse. FlashAttention (gpu7) is the canonical example: standard attention writes the N × N score matrix to HBM and reads it back several times, which puts it on the HBM slope. FlashAttention computes the same result tile by tile in shared memory, never storing the matrix, cutting HBM traffic by a large factor. The FLOPs even rise slightly (it recomputes some values), but HBM intensity rises far more, and the kernel moves up to the compute roof.

The sum of rooflines is not a roofline

A transformer layer is a sequence of kernels. Unless operations overlap, the step's time is the sum of each kernel's max(F/P, Q/W), not the max of the summed FLOPs and bytes. This is why adding a memory-bound LayerNorm to a compute-bound matmul costs the LayerNorm's full memory time even though "the step is compute-bound overall". It is also why fusion is so effective: fusing a memory-bound operation into a compute-bound one lets its bytes hide under the matmul's arithmetic, turning a sum into a max.

Caches can put you above the HBM roof

The HBM slope assumes every byte comes from HBM. If a small tensor — a bias, a small weight matrix, a KV block used by many query tiles — is still in the 50 MB L2 cache from a previous kernel, the effective bandwidth is higher and the measured point lands above the HBM line. That is fine, not a measurement error; it means the relevant roof is L2. Conversely, a kernel with poor locality that re-reads the same data from HBM moves more than the minimum and lands below the ideal.

Latency- and overhead-bound regions below the roof

The roofline assumes enough parallel work to keep the machine busy. A matmul with B = 1 and a small d may launch only a few dozen thread blocks for 132 SMs; it is neither bandwidth- nor compute-bound but parallelism-bound. Kernels lasting a few microseconds are dominated by launch overhead. Both sit well below the roof, and the fixes — CUDA graphs, fusing many tiny ops, split-K matmuls that spread one small matmul over more SMs — are different from the roofline moves. Always compare measured time with the roofline bound: a large gap means you are in one of these regimes.

Rooflines for communication

The same idea governs multi-GPU work (gpu8). Replace HBM bandwidth with link bandwidth and bytes read with bytes sent: the "communication intensity" is FLOPs of local work per byte communicated, and the ridge is peak FLOP/s divided by link bandwidth — for an H100 sending over NVLink at 450 GB/s in each direction (NVIDIA's 900 GB/s figure counts both directions) about 2,200 FLOP/byte, and over a 400 Gb/s (50 GB/s) InfiniBand link about 20,000. With tensor parallelism across T GPUs, each layer's matmuls give each GPU roughly 2·B·d·f/T FLOPs, while the all-reduce of the output sends on the order of B·d elements; intensity scales like f/T. That is why tensor parallelism stays within a server's NVLink domain and why data parallelism, which communicates once per step, can span the slower network.

Energy has a roofline too

Moving a byte from HBM costs far more energy than a multiply-add on data already in registers — an order of magnitude or more. So memory-bound workloads are not only slow but energy-inefficient, and techniques that cut bytes (fusion, quantisation, on-chip reuse) also cut power. At data-centre scale, where power is the binding constraint on how many GPUs can be installed, this is increasingly the argument that decides architecture choices.

How teams use the roofline day to day

The roofline is used less as a chart and more as a habit: before optimising anything, compute its bound. A typical workflow in an inference team: profile a decode step, list the kernels with their times, compute each kernel's minimum bytes and FLOPs, and compare measured time with max(F/P, Q/W). Kernels far below their bound are candidates for better implementation; kernels at their bound are candidates only for fewer bytes (fusion, quantisation) or removal. The model-level summaries are MFU for compute-bound work (training, prefill) and MBU for memory-bound work (decode). Databricks' inference guide, for example, reports MBU for Llama-2-70B across batch sizes and tensor-parallel degrees and shows it falling as more GPUs are added — a sign that communication and overhead, not bandwidth, start to dominate.

Choosing the serving batch size

Serving frameworks such as vLLM expose a maximum number of concurrent sequences (for vLLM, max_num_seqs) and a token budget per step. The roofline tells you where to set them. While the weight matmuls are memory-bound, raising concurrency adds throughput almost for free, limited by KV-cache memory and by the growing KV bytes per step. Past the ridge, extra concurrency adds latency with little throughput. The right setting is where throughput is still rising but per-token latency (inter-token latency, ITL) still meets its target. Prefill complicates this: a long prompt entering the batch is compute-bound and can stall everyone's decoding for tens of milliseconds, which is why servers split long prefills into chunks mixed with decode steps (chunked prefill, lm13).

Characteristic surprises the roofline explains

"We upgraded A100 → H100 and decode got only 1.6× faster, not 3×." Decode is memory-bound; bandwidth rose from 2.0 to 3.35 TB/s, a ratio of 1.64. The 3× FLOPs increase is irrelevant to it. Training throughput, which is compute-bound, did improve by around 2-3×.

"We quantised to int4 and prefill got no faster — or slower." Prefill is compute-bound, and weight-only int4 still computes in BF16 after dequantising; the extra dequantisation work can even slow it. Only decode, which is memory-bound, benefits. If prefill speed matters, you need FP8 or FP4 arithmetic, which raises the roof.

"Throughput stopped scaling with batch size at 64, not 300." KV-cache reads grow with batch × context and are never shared. At long contexts they overtake the weight bytes, and the combined intensity stops rising. The fix is on the KV side: FP8 KV cache, prefix sharing, or a model with fewer KV heads.

"The kernel is at 30% of peak bandwidth and 2% of peak FLOPs." It is below both roofs, so it is overhead- or parallelism-bound. Look at the grid size (does it fill all SMs?), the kernel duration (a few microseconds?) and the timeline gaps. This is where CUDA graphs and fusion earn their keep.

Tools

Nsight Compute reports a kernel's achieved FLOP/s and bandwidth, its speed-of-light percentages and a roofline chart. The PyTorch profiler shows per-kernel times you can compare with hand-computed bounds, and torch.utils.flop_counter.FlopCounterMode counts FLOPs for a model's forward and backward passes. For planning, a spreadsheet or a 20-line script with FLOPs, bytes, peak and bandwidth — like the lab below — answers most questions before any code is written.

Goal: reproduce the free-lunch zone and the effect of weight quantisation from nothing but the roofline formula. Pure Python 3.12, no GPU needed (this machine has none).

  1. Save and run as roofline.py:
PEAK, BW = 989e12, 3.35e12            # H100 SXM: dense BF16 FLOP/s, HBM bytes/s
RIDGE = PEAK / BW

def matmul(m, k, n, bytes_per=2, weight_bytes=None):
    """[m,k] x [k,n]: FLOPs and minimum HBM bytes."""
    wb = bytes_per if weight_bytes is None else weight_bytes
    flops = 2 * m * k * n
    nbytes = m * k * bytes_per + k * n * wb + m * n * bytes_per
    return flops, nbytes

print(f"ridge point: {RIDGE:.0f} FLOP/byte")
d, f = 8192, 28672                     # 70B-class hidden size and MLP width
for B in [1, 8, 64, 256, 1024, 4096]:
    for label, wb in [("bf16 weights", 2), ("int4 weights", 0.5)]:
        fl, by = matmul(B, d, f, weight_bytes=wb)
        ai = fl / by
        t = max(fl / PEAK, by / BW) * 1e6
        print(f"B={B:5d} {label}: intensity {ai:7.1f}  "
              f"{min(PEAK, ai * BW) / 1e12:5.0f} TFLOP/s  {t:8.1f} us  "
              f"{'compute' if ai > RIDGE else 'memory'}-bound")

What to look for. With BF16 weights the step time stays near 140 µs from B = 1 to B = 256 while intensity climbs from 1 to 246: that is the free-lunch zone. At B = 1,024 it crosses the ridge and time grows with B. With int4 weights the small-batch time drops to about 35 µs (4× fewer bytes), but from B = 256 onwards both formats take the same time — quantising weights does nothing once compute-bound.

Try: change PEAK, BW to the H200 (989e12, 4.8e12) and see only the memory-bound rows speed up; then to a B200 (2.25e15, 8e12) and find the new crossover batch.

Work it out

For a 70B model decoding on H100s with BF16 weights, at what batch size do the weight matmuls become compute-bound? What changes with 4-bit weights (BF16 compute), and why does long context spoil the picture?

Answer

BF16 weights: intensity ≈ B FLOP/byte (2 FLOPs per 2-byte weight per sequence). The H100 ridge is about 295, so the weight matmuls become compute-bound at around B ≈ 300 sequences. Below that, adding sequences costs almost no extra time per step.

4-bit weights: 0.5 bytes per weight, so intensity ≈ 2·B / 0.5 = 4B. Compute-bound at B ≈ 75. Below that, decode runs up to 4× faster than BF16 at the same batch because it reads a quarter of the bytes — the main reason weight-only quantisation is standard for serving. Above it, both formats are equally fast, because the maths is still done in BF16.

Long context: each sequence also reads its own KV cache every step, at intensity ≈ the GQA group size (8 for Llama 3 70B) no matter the batch. At about 0.33 MB per token, an 8,000-token sequence carries 2.6 GB of cache; a batch of 64 reads about 170 GB of KV per step — more than the 140 GB of weights. The combined intensity stops rising with batch, and decode stays memory-bound regardless. The levers become KV-cache quantisation (FP8 halves it), fewer or compressed KV heads (GQA, MLA), sliding-window attention in some layers, prefix sharing between requests, and higher-bandwidth GPUs.
