An engineer has a new layer: a normalisation followed by a custom gating function and a quantised matrix multiplication. Written as five PyTorch operations it works, but the profiler shows each operation reading and writing the full activation tensor, and the layer runs at 15% of what the roofline says is possible. torch.compile fuses some of it but not the quantised matmul. The only way forward is to write a GPU kernel — or to understand kernels well enough to judge whether it is worth it, or to read the one a colleague wrote. An interviewer who asks "how would you write a fast matrix multiplication on a GPU?" or "what is memory coalescing?" is testing exactly this understanding.

Programming a GPU looks strange at first. You don't write a loop over the data. You write what one thread does to one element, and ask the GPU to run that code on a million threads at once. The code is short; the performance is subtle. The same few lines of C++ can run at 1% or 90% of the chip's peak depending on how neighbouring threads touch memory, whether data is reused from on-chip storage, and whether the hardware's rules about memory banks and warps are respected. Simon Boehm's well-known write-up shows a single-precision matrix multiplication going from 309 GFLOP/s to 21,779 GFLOP/s on the same GPU — a 70-fold speed-up with the same arithmetic — purely by reorganising how threads use memory.

This lesson teaches CUDA, NVIDIA's programming model, from the ground up. We write a vector addition and the host code that launches it; learn how threads find their data from grid, block and thread indices; meet the memory spaces from the programmer's point of view; and then work through the two ideas behind almost every fast kernel — coalesced global memory access and reuse through shared memory — on matrix multiplication, finishing with bank conflicts and the path to cuBLAS-level performance. The goal is not that you write CUDA every week; most ML engineers rarely do. It is that when a kernel is slow, you can say why.

The exam-hall model

Imagine a huge exam taken by a million students. Every student gets the same instruction sheet (the kernel), and the sheet says "answer question number your seat number". Students are grouped into classes (thread blocks) of up to 1,024; each class sits in one room (an SM), and a room may hold several classes at once. Each room has a whiteboard that only that room's students can see (shared memory), and a class can pause until everyone has finished writing on it (a barrier). There is also a central library everyone can use (global memory), but walking there takes a long time. Each student also has a notepad of their own (registers). The whole exam — all the classes — is the grid.

The analogy captures the rules: all students follow the same sheet but work on different data; classes don't talk to each other during the exam; students within a class cooperate through the whiteboard; the library is slow, so a good class sends a few students to fetch the books everyone needs once, puts them on the whiteboard, and shares. Where it breaks: the students in a GPU class move in squads of 32 (warps) that read the same line of the sheet at the same moment, and the library is fastest when a squad asks for 32 books that sit next to each other on one shelf.

What "CUDA" actually is

CUDA is NVIDIA's whole platform: the nvcc compiler that turns C++ with a few extensions into GPU machine code, a runtime library for allocating memory and launching kernels, a driver, and libraries built on top (cuBLAS for linear algebra, cuDNN for neural-network primitives, NCCL for communication). PyTorch uses all of these under the hood. AMD's equivalent is ROCm, whose HIP language is nearly a copy of CUDA C++, and higher-level tools such as Triton (gpu6) generate kernels for both. The concepts in this lesson — grids, blocks, warps, shared memory, coalescing — carry over to all of them.

The two rules that matter most

Coalescing: when the 32 threads of a warp read 32 adjacent addresses, the hardware serves them all with a few wide memory transactions. When they read scattered addresses, it needs up to 32 transactions to deliver the same useful data, and bandwidth is wasted. So data is arranged, and threads are assigned, so that neighbouring threads touch neighbouring memory.

Reuse through shared memory (and registers): global memory is slow and, as gpu2 showed, bandwidth usually sets the speed. If many threads in a block need the same values, load them from global memory once into shared memory, synchronise, and let every thread read them from there. The number of times each loaded value is reused is exactly the factor by which arithmetic intensity rises.

Matrix multiplication is the classic teaching example because it needs both rules and rewards them dramatically: every output element needs a whole row of A and a whole column of B, so a careless kernel reads each input thousands of times, while a careful one reads it a handful of times.

1. A first kernel: adding two vectors

A complete CUDA program has two parts: device code that runs on the GPU, and host code that runs on the CPU, allocates GPU memory, copies data and launches the kernel. CUDA C++ is C++ with a few extensions. Here is vector addition, c = a + b, for n elements:

__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // this thread's element
    if (i < n)                                        // the last block may be partly empty
        c[i] = a[i] + b[i];
}

int main() {
    int n = 1 << 20;                                  // about a million elements
    size_t bytes = n * sizeof(float);
    float *a, *b, *c;                                 // device pointers
    cudaMalloc(&a, bytes); cudaMalloc(&b, bytes); cudaMalloc(&c, bytes);
    // ... cudaMemcpy(a, host_a, bytes, cudaMemcpyHostToDevice); same for b ...
    int threads = 256;
    int blocks = (n + threads - 1) / threads;        // round up: 4,096 blocks
    add<<<blocks, threads>>>(a, b, c, n);             // launch: grid of blocks
    cudaDeviceSynchronize();                         // wait for the GPU to finish
    // ... cudaMemcpy(host_c, c, bytes, cudaMemcpyDeviceToHost); cudaFree ...
}

Walk through it. __global__ marks add as a kernel: callable from the host, executed by every thread on the device. The triple-angle-bracket syntax <<<blocks, threads>>> launches it with 4,096 blocks of 256 threads — 1,048,576 threads, one per element. Inside the kernel, three built-in variables tell each thread where it is: blockIdx.x (which block, 0-4,095), blockDim.x (threads per block, 256) and threadIdx.x (which thread within the block, 0-255). Thread 5 of block 3 computes i = 3 × 256 + 5 = 773 and adds element 773. The if (i < n) guard matters when n isn't a multiple of 256: the last block then has threads with no element to process, and without the guard they would write past the end of the array.

Blocks and threads can be one-, two- or three-dimensional (dim3 gives x, y and z), which is convenient for images and matrices: a 2D block of 32 × 32 threads has threadIdx.x and threadIdx.y. The launch is asynchronous: the CPU returns immediately, which is why cudaDeviceSynchronize() (or a later blocking copy) is needed before using the result. Errors in a launch are also reported asynchronously — a bad memory access shows up at the next synchronising call, not at the line that caused it.

An alternative pattern, the grid-stride loop, launches a fixed number of threads (say, a few blocks per SM) and lets each process several elements: for (int i = idx; i < n; i += blockDim.x * gridDim.x). It handles any n with the same launch and amortises per-thread setup.

2. Choosing the launch configuration

Two numbers must be chosen for every launch. Threads per block should be a multiple of 32, because the hardware runs whole warps — a block of 100 threads occupies 4 warps and wastes 28 lanes. The limit is 1,024. Common choices are 128 or 256: large enough to give the scheduler several warps, small enough that several blocks fit on each SM and that barriers inside a block don't make many threads wait. Number of blocks should comfortably exceed the number of SMs (132 on an H100) — ideally many times over — so that every SM is busy and fast SMs can pick up more blocks while slow ones finish.

How many blocks actually run on an SM at once depends on resources. An H100 SM holds at most 2,048 threads, 32 blocks, 65,536 registers and 228 KB of shared memory. A kernel using 64 registers per thread in blocks of 256 needs 16,384 registers per block, so at most 4 blocks (1,024 threads, 50% occupancy) fit. Adding a 64 KB shared-memory tile per block also limits it to 3 blocks. The compiler reports register use (nvcc --resource-usage), and Nsight Compute reports achieved occupancy; gpu1 explained why occupancy is a means, not a goal.

4. Coalescing: how a warp talks to memory

The memory system does not fetch single floats. It moves data in 32-byte sectors (four sectors make a 128-byte cache line). When a warp executes a load, the hardware looks at the 32 addresses and fetches every sector that any of them touches. If the 32 threads read 32 consecutive floats — 128 bytes starting at an aligned address — that is exactly 4 sectors, and every fetched byte is used. That is a coalesced access.

Now suppose the 32 threads each read one element from a column of a row-major 4,096 × 4,096 FP32 matrix: consecutive threads' addresses are 4,096 × 4 = 16,384 bytes apart. Each lands in a different sector, so the warp fetches 32 sectors, 1,024 bytes, to use 128. Seven-eighths of the bandwidth is wasted. The rule for kernel design follows: map consecutive threadIdx.x values to consecutive addresses — for a row-major matrix, to consecutive columns.

A real measurement: in Simon Boehm's matmul series on an RTX A6000, the first naive kernel mapped threadIdx.x to rows of the output, so threads in a warp walked down columns. Achieved memory throughput was about 15 GB/s. Swapping the mapping so threadIdx.x followed columns — the only change — raised it to about 110 GB/s and the speed from 309 to 1,987 GFLOP/s, 6.4 times faster.

5. The naive matrix multiplication

C = A × B for N × N FP32 matrices, one thread per output element, with the coalesced mapping:

__global__ void matmul_naive(const float* A, const float* B, float* C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;   // consecutive threads -> consecutive columns
    if (row < N && col < N) {
        float acc = 0.f;
        for (int k = 0; k < N; ++k)
            acc += A[row * N + k] * B[k * N + col];     // two global loads per multiply-add
        C[row * N + col] = acc;
    }
}
// launch: dim3 block(32, 32); dim3 grid((N + 31) / 32, (N + 31) / 32);

Within a warp (32 threads with the same row and consecutive col), the loads of B[k * N + col] are coalesced, and all 32 threads read the same A[row * N + k] — a single broadcast. Correct, but count the traffic. Each thread loads 2N values to do N multiply-adds (2N FLOPs). Ignoring caches, the whole kernel loads 2N3 floats: for N = 4,096, about 550 GB, to do 1.37 × 1011 FLOPs. Arithmetic intensity: 0.25 FLOP/byte. The minimum traffic — read A and B once, write C once — is 3 × 4,0962 × 4 bytes ≈ 200 MB. The naive kernel moves nearly 3,000 times the necessary data. Caches absorb some of it, which is why it isn't 3,000 times slower than optimal, but it is still far below the chip's capabilities.

6. Tiling through shared memory

The fix is reuse. Split the computation into T × T tiles (T = 32 here). A block of 32 × 32 threads computes one 32 × 32 tile of C. It walks along the shared dimension in steps of T: at each step, the block cooperatively loads a T × T tile of A and a T × T tile of B into shared memory — one element per thread, coalesced — waits until all are loaded, and then each thread does T multiply-adds reading only from shared memory.

#define T 32
__global__ void matmul_tiled(const float* A, const float* B, float* C, int N) {
    __shared__ float As[T][T], Bs[T][T];
    int ty = threadIdx.y, tx = threadIdx.x;
    int row = blockIdx.y * T + ty, col = blockIdx.x * T + tx;
    float acc = 0.f;
    for (int t = 0; t < N; t += T) {
        As[ty][tx] = (row < N && t + tx < N) ? A[row * N + t + tx] : 0.f;   // coalesced
        Bs[ty][tx] = (col < N && t + ty < N) ? B[(t + ty) * N + col] : 0.f; // coalesced
        __syncthreads();                         // 1: tiles fully loaded before anyone reads
        for (int k = 0; k < T; ++k)
            acc += As[ty][k] * Bs[k][tx];        // T multiply-adds from shared memory
        __syncthreads();                         // 2: everyone done before tiles are overwritten
    }
    if (row < N && col < N) C[row * N + col] = acc;
}

Count again. Each element of A is now loaded once per block-column of C that needs it — N/T times instead of N times — and likewise for B. Global traffic falls by a factor of T: for N = 4,096 and T = 32, from about 550 GB to 17 GB, and intensity rises from 0.25 to 8 FLOP/byte. The lab reproduces these numbers.

The two __syncthreads() calls are what make it correct. The first guarantees that every thread has written its element of As and Bs before any thread starts reading the tile; without it, a warp that runs ahead would read elements another warp hasn't loaded yet. The second guarantees that every thread has finished reading the current tiles before the next iteration overwrites them; without it, a fast warp would load tile t + 1 on top of data a slow warp is still using. Both bugs produce wrong answers only sometimes, depending on timing — the worst kind.

7. Bank conflicts

Shared memory is fast only if the warp's accesses spread across its 32 banks. Successive 4-byte words go to successive banks: word w lives in bank w mod 32. Each bank serves one word per cycle. If the 32 threads of a warp read 32 words in 32 different banks, the access takes one step. If several threads read the same word, it is broadcast — no problem. If several threads read different words in the same bank, those accesses are serialised: an n-way conflict takes n steps.

In the tiled kernel above, As[ty][k] is the same word for all 32 threads of a warp (they share ty) — a broadcast — and Bs[k][tx] is 32 consecutive words — 32 different banks. No conflicts. But a common variant, such as a transpose or a kernel that reads a tile by columns, has thread t read tile[t][0]. In a float tile[32][32], row t starts at word 32t, so every thread's word is 32t, and 32t mod 32 = 0: all 32 threads hit bank 0 — a 32-way conflict, 32 times slower. The standard fix is padding: declare tile[32][33]. Now row t starts at word 33t, and 33t mod 32 = t, so the 32 threads hit 32 different banks. One wasted column buys a 32-fold speed-up of that access. High-performance libraries use swizzling instead — storing element (r, c) at column c XOR r — which spreads accesses across banks without wasting space or breaking alignment.

Read it as a sequence of bottlenecks. The shared-memory kernel (3) barely beats the coalesced one, because it just moved the problem: each multiply-add now does two shared-memory reads, and shared-memory bandwidth, though high, is the new limit. Register tiling (4 and 5) attacks that: a thread computing an 8 × 8 block of outputs loads 8 values of A and 8 of B from shared memory into registers and does 64 multiply-adds with them — each shared-memory read is reused 8 times from registers, the fastest storage there is. That one idea took it from 13% to 69%. Vectorised 128-bit loads cut the number of load instructions fourfold. Autotuning and warp-tiling polish the last steps.

Modern libraries add two things that section of the write-up didn't use. Double buffering with asynchronous copies — cp.async on Ampere, the Tensor Memory Accelerator on Hopper — loads the next tile while the tensor cores work on the current one, hiding memory latency without needing many warps. And tensor-core instructions replace the scalar inner loop: on an H100, a BF16 matmul through tensor cores reaches roughly 15 times the FP32 rate of the best CUDA-core kernel. That is why production matmuls come from cuBLAS, CUTLASS or compiler-generated Triton kernels rather than hand-written loops — but every one of them is built from the ideas in this table.

9. Calling a kernel from PyTorch, and timing it

You don't need a separate C++ project to try a kernel. PyTorch's torch.utils.cpp_extension.load_inline compiles CUDA source given as a Python string and exposes it as a function taking tensors. Timing must respect asynchrony:

start, end = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
for _ in range(3): my_kernel(a, b)          # warm-up: compilation, allocation, clocks
start.record()
for _ in range(20): my_kernel(a, b)
end.record(); torch.cuda.synchronize()
ms = start.elapsed_time(end) / 20
tflops = 2 * N**3 / (ms / 1e3) / 1e12

Compare the result with torch.matmul (cuBLAS) on the same inputs, check correctness with torch.testing.assert_close using tolerances suited to the format, and test sizes that aren't multiples of the tile size.

Warp-level primitives and reductions

Many ML kernels are reductions — the sum in a softmax's denominator, the mean and variance in LayerNorm. The naive approach has threads add into one location with atomic operations, which serialise. The standard pattern is hierarchical: each thread sums its own elements in a register; the 32 threads of a warp then combine their values with warp shuffle instructions (__shfl_down_sync), which let threads read each other's registers directly without shared memory — five steps (16, 8, 4, 2, 1) combine 32 values; each warp's result goes into shared memory, and one warp reduces those. This does a row reduction of thousands of values in a few microseconds with no atomics, and it is the skeleton of every fused softmax and normalisation kernel.

Asynchronous copies and pipelining

In the section 6 kernel, threads load a tile, wait, compute, wait — memory and arithmetic alternate instead of overlapping. Ampere's cp.async instruction lets a thread start a copy from global to shared memory and continue working; the kernel keeps two or more buffers, issuing loads for tile k + 1 (or k + 2) before computing on tile k, and waits only for the buffer it is about to use. Hopper's Tensor Memory Accelerator goes further: one thread issues a single instruction describing a whole 2D tile, the TMA unit generates the addresses and handles out-of-bounds elements, and a hardware barrier signals when the data has arrived. Combined with warp specialisation — producer warps that only issue TMA loads, consumer warps that only compute — this is how Hopper kernels keep tensor cores busy with few warps.

Programming tensor cores

Tensor cores are driven by warp-level (or larger) matrix instructions rather than per-thread arithmetic. CUDA exposes them at several levels: the wmma API (a warp loads 16 × 16 fragments and issues a multiply-accumulate), the PTX mma.sync instructions used by most Ampere kernels, Hopper's asynchronous wgmma in which a warpgroup of 128 threads multiplies operands read straight from shared memory, and Blackwell's tcgen05 instructions with accumulators in tensor memory. Each generation changed the data layouts the instructions expect in registers and shared memory, and getting those layouts right — with swizzles that avoid bank conflicts — is the hardest part. NVIDIA's CUTLASS library and its CuTe layout algebra exist to express these layouts compositionally; FlashAttention-2 and -3 are built on them.

Register pressure, spills and launch bounds

More work per thread (register tiling) means more registers per thread. Past the per-thread limit, or past the point where too few warps fit on an SM, performance drops: either the compiler spills to slow local memory or occupancy collapses. The __launch_bounds__(threads, minBlocks) annotation tells the compiler the block size and the minimum number of resident blocks you want, so it limits register use accordingly. Tuning tile sizes is largely a search for the point where reuse is high but registers still fit — which is why autotuning (trying many configurations per GPU and shape, as Triton and CUTLASS profilers do) is standard.

Streams, pinned memory and CUDA graphs

Kernels and copies issued to the same stream run in order; different streams may overlap. To overlap a host-to-device copy with computation, the host buffer must be pinned (page-locked) memory — PyTorch's pin_memory=True in the DataLoader and tensor.to("cuda", non_blocking=True) — because the GPU's copy engine reads it directly without the CPU's involvement. For workloads made of many small kernels, CUDA graphs record a whole sequence of launches once and replay it with a single call, removing per-launch CPU overhead; this is what torch.compile(mode="reduce-overhead") uses, and what took gpt-fast from overhead-bound to bandwidth-bound in gpu2.

Atomics

When many threads must update the same location — a histogram, a global sum, scattering gradients for an embedding lookup — CUDA provides atomic operations (atomicAdd and friends) that perform read-modify-write indivisibly. They are correct but serialise on contention: 10,000 threads adding into one float wait in line. The usual pattern is to reduce locally first (per warp with shuffles, then per block in shared memory) and issue one atomic per block. Floating-point atomics also finish in an unpredictable order, which makes results non-deterministic in the last bits — one reason PyTorch's deterministic mode avoids some kernels.

Divergence and predication in practice

Branches inside a warp serialise, but short ones are cheap: the compiler often turns small if-statements into predicated instructions that every thread executes, with results discarded where the condition is false. The costly case is long divergent paths or loops whose trip count differs per thread — for example, processing variable-length sequences one per thread. The usual remedy is to reorganise work so that a warp handles one sequence cooperatively, or to sort or bucket work by size so neighbouring threads do similar amounts.

When writing a kernel is worth it

In ML teams, custom kernels are the exception. The usual escalation is: use library operations; add torch.compile to fuse element-wise work; write a Triton kernel for a fused operation the compiler misses (gpu6); and only then CUDA or CUTLASS, for control Triton doesn't provide or the last 10-20% of a kernel that dominates cost. The decision is driven by the roofline: compute the kernel's bound, measure its time, and estimate what fraction of the whole step the gap represents. A kernel that is 3× from its bound but 2% of step time is not worth a week.

Public examples of when it was worth it: FlashAttention (gpu7) — attention was the dominant memory cost and no library fused it; Andrej Karpathy's llm.c, which trains GPT-2 in plain C and CUDA and documents a progression of hand-written kernels for layernorm, attention, softmax and the fused classifier; and the many fused quantised-matmul kernels (for int4 and FP8 weights) that serving systems needed before libraries caught up.

Failure modes and how to see them

Illegal memory access. A kernel indexes past an array's end, often in the last partial block when a bounds check is missing. Because errors are reported asynchronously, the Python traceback points at an unrelated later operation. Set CUDA_LAUNCH_BLOCKING=1 to make launches synchronous so the error surfaces at the real call, and run compute-sanitizer (its default memcheck tool) to get the exact thread and address.

Races. Missing __syncthreads(), or non-atomic updates to the same global address from many threads. Results vary between runs or GPUs. compute-sanitizer --tool racecheck detects shared-memory hazards; --tool synccheck detects invalid barrier use, such as a barrier inside a branch that not all threads of the block reach, which can hang the kernel.

Slow for no obvious reason. Nsight Compute's source view shows, per line, memory transactions per request (a coalescing check: ideal is 4 sectors per warp-wide FP32 load), shared-memory bank conflicts, register spills and the stall reason for each warp (waiting on memory, on a barrier, on a math pipe). Most kernel problems are visible in the first two metrics.

Architecture mismatch. A kernel compiled only for one architecture (say sm_80) will fail or fall back to just-in-time compilation from PTX (NVIDIA's intermediate assembly) on another; one using Hopper-only instructions won't run on an A100. Build for every architecture you deploy (for example -gencode flags for sm_80, sm_90 and sm_100), and test each.

Testing kernels

Compare against a trusted reference (a PyTorch composition in FP32) with tolerances appropriate to the format — BF16 results legitimately differ from FP32 in the third significant digit. Test awkward sizes (1, 31, 33, primes, sizes just above tile multiples), non-contiguous or transposed inputs, and the largest sizes you'll use (integer overflow in index arithmetic appears above 231 elements; use 64-bit indices when tensors can be that big). Keep a benchmark in CI so a later change can't silently make it slower, and record the GPU model, driver and CUDA version with every result, because performance numbers are only comparable on identical stacks.

Goal: reproduce, with arithmetic alone, the three numbers that decide a matmul kernel's speed: sectors per warp load (coalescing), global traffic (tiling) and bank conflicts (padding). This machine has no NVIDIA GPU, so no CUDA is run here; the script is pure Python 3.12.

def sectors(addresses, sector=32):        # a warp's loads are served in 32-byte sectors
    return len({a // sector for a in addresses})

print("column read:", sectors(col), "sectors")

def traffic(N, T=None, b=4):               # global reads, ignoring caches
    return 2 * N**3 * b if T is None else 2 * N**3 // T * b

def conflict(words, banks=32):             # worst number of distinct words in one bank
    per = {}
    for w in words: per.setdefault(w % banks, set()).add(w)
    return max(len(s) for s in per.values())
for width in (32, 33):                     # float tile[32][width]; warp reads column 0

What to look for. A row read needs 4 sectors (128 bytes, all useful); a column read needs 32 sectors (1,024 bytes for 128 useful). The naive kernel moves about 550 GB at 0.25 FLOP/byte; T = 32 cuts it to 17 GB at 8 FLOP/byte; the lesson's point is that each tile step multiplies intensity. Reading a column of a [32][32] tile is a 32-way conflict; padding to [32][33] makes it conflict-free.

Work it out

For an FP32 matmul with N = 4,096, estimate the global-memory reads (ignoring caches) for the naive kernel and for the tiled kernel with T = 32. Compute the arithmetic intensity of each and compare with an FP32 roofline (about 67 TFLOP/s and 3.35 TB/s on an H100 without tensor cores). What would you change next, and why?

Answer

FLOPs = 2N3 = 2 × 4,0963 ≈ 1.37 × 1011.

Naive: two 4-byte loads per multiply-add → 2N3 loads × 4 bytes ≈ 550 GB. Intensity = 1.37 × 1011 / 5.5 × 1011 = 0.25 FLOP/byte → at most 0.25 × 3.35 TB/s ≈ 0.84 TFLOP/s, about 0.16 s. In reality L1 and L2 absorb much of this traffic, so measured performance is better, but still far from peak.

Tiled (T = 32): traffic falls 32× to about 17 GB. Intensity ≈ 8 FLOP/byte → up to about 27 TFLOP/s from HBM's point of view, now within reach of the 67 TFLOP/s FP32 roof. But the kernel now does two shared-memory reads per multiply-add, so shared-memory bandwidth becomes the limit — which is why the textbook tiled kernel reached only 12.8% of cuBLAS in Boehm's measurements.

Next: register tiling — each thread computes an 8 × 8 block of outputs, so every shared-memory value is reused 8 times from registers (in Boehm's series this took 12.8% to 68.7% of cuBLAS); then vectorised loads, double-buffered asynchronous copies, and, above all, tensor cores, which raise the roof about 15× in BF16. In practice you would call cuBLAS for a plain matmul and write custom code only for a fused variant.
