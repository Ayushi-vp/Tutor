A research team writes a new transformer variant in PyTorch. Every line is simple — a normalisation, a rotation of the query and key vectors, a gated activation, a few residual additions — and the model trains correctly. It also trains at half the speed of a well-known model of the same size. The profiler explains why: each training step launches about 2,000 GPU kernels, most of them lasting a few microseconds. The large matrix multiplications are fast, but between them the GPU reads a tensor from memory, does one addition, writes it back, reads it again, multiplies it, writes it back, and repeats. For long stretches it also sits idle, waiting for Python to decide which kernel to launch next.

They could rewrite every block as a hand-written CUDA kernel. Instead, they add one line — model = torch.compile(model) — and training becomes about 40% faster. That number is not unusual: when the PyTorch team released PyTorch 2.0, they benchmarked 163 open-source models and found torch.compile worked on 93% of them and trained 43% faster on average on an A100 (51% with mixed precision). Where does that speed come from, when the arithmetic hasn't changed at all?

The answer is kernel fusion: combining chains of operations into single kernels so intermediate results never make the round trip to HBM. It is the practical consequence of gpu2's roofline — memory-bound operations are limited by bytes, so the way to speed them up is to stop moving the bytes. This lesson explains fusion from first principles, then the three tools that deliver it: torch.compile, which captures a model's operations and generates fused kernels automatically; Triton, a Python-embedded language in which you can write your own fused kernels at the level of blocks rather than threads; and CUDA graphs, which remove the CPU's launch overhead. We will also cover how they fail — graph breaks, recompilation storms, compile time, numerical differences — because in production those failures matter as much as the speed-ups.

The kitchen that puts everything away

Imagine a cook preparing a sauce in five steps: chop, fry, add stock, reduce, season. A strangely strict kitchen requires that after every step the cook puts the pan back in the walk-in fridge down the corridor, and fetches it again for the next step. The cooking takes a minute per step; the walking takes five. A sensible cook keeps the pan on the stove for all five steps and only puts the finished sauce away. Same recipe, same cooking, a fraction of the time.

Eager PyTorch is the strict kitchen. Each operation is a separate kernel; each kernel reads its inputs from HBM (the walk-in fridge) and writes its output back, because the next operation is a different kernel that can only find its input there. For a matrix multiplication, the walk is negligible compared with the cooking. For an element-wise operation — add, multiply, GELU — the cooking is a few FLOPs per element and the walk is everything. A fused kernel is the sensible cook: it reads the input once, does all the operations on values held in registers, and writes the final result once.

Why not fuse everything into one kernel?

If fusion is so good, why not write each layer — or the whole model — as a single kernel? Three reasons. First, different operations want different shapes of parallelism: a matmul wants to tile its output across all SMs, while a row-wise normalisation wants one program per row; one kernel has to choose one launch shape. Second, some operations need the complete result of the previous one before they can start, and blocks of a single kernel cannot wait for each other (gpu5). Third, hand-writing a fused kernel for every model variant is expensive, fragile and hard to maintain. So in practice fusion happens in the places it pays most — chains of memory-bound operations, reductions with their neighbours, matmul epilogues — and is automated wherever possible. (At the extreme, researchers have built "megakernels" that run an entire small model's decode step as one persistent kernel; they are fast and very specialised.)

Three tools, three problems

torch.compile addresses the traffic automatically: it watches your model's Python code run, builds a graph of the PyTorch operations, decides which ones to fuse, and generates new kernels for the fused groups. Triton is the language those generated kernels are written in, and one you can use yourself when the compiler doesn't produce what you need: you write in Python, describing operations on whole blocks of data, and the Triton compiler handles the thread-level details you met in gpu5. CUDA graphs address a different cost — the CPU time to launch each kernel — by recording a sequence of launches once and replaying it with one call.

A quick number to anchor it: five element-wise operations applied in sequence to a 4,096 × 4,096 BF16 tensor (33.5 MB) on an H100 move 335 MB unfused — about 100 µs at 3.35 TB/s, plus five launches — and 67 MB fused, about 20 µs plus one launch. Roughly 125 µs versus 25 µs, from the same arithmetic.

1. Anatomy of an eager operation

When Python executes y = torch.relu(x * w + b) * scale on GPU tensors, PyTorch does the following for each of the four operations: the Python interpreter calls into PyTorch's C++ dispatcher; the dispatcher checks types, devices and autograd, allocates an output tensor from the caching allocator, records what the backward pass will need, and selects a kernel; the CUDA runtime enqueues the launch. That host-side path costs a few microseconds per operation. The GPU then runs the kernel: read the inputs from HBM, compute, write the output to HBM.

For the expression above on an 8,192 × 4,096 BF16 tensor (67 MB): four kernels, each reading one or two tensors and writing one — roughly 8 full passes, 540 MB, about 160 µs at 3.35 TB/s, plus four launches. Fused: read x once (the vectors w and b are small, or broadcast), write y once — 134 MB, about 40 µs. In training, the backward pass has its own chain of element-wise kernels, and autograd saves intermediate tensors for it, so unfused code also uses more memory.

Two kinds of waste are mixed together here, and the tools attack them separately. Memory traffic (the extra passes over HBM) is removed by fusion. Launch and dispatch overhead (the microseconds of CPU work per operation) is removed by fusion (fewer operations) and by CUDA graphs (no per-kernel CPU work at all). Which dominates depends on tensor size: for large tensors, traffic; for small ones — a decode step with batch size 1 — overhead.

2. What can be fused

Fusion works when one kernel can compute its output piece by piece without waiting for results from elsewhere in the tensor. Four patterns cover most ML code:

  • Element-wise chains ("vertical" fusion): each output element depends only on the input element at the same position — add, multiply, activation functions, dropout, casts. Any chain of these fuses trivially.
  • Reductions with their neighbours: RMSNorm, LayerNorm, softmax and cross-entropy each reduce along a row (a sum or a max) and then apply element-wise work using the result. One program per row can load the row, reduce it in registers or shared memory, and apply the rest — one read, one write.
  • Matmul epilogues and prologues: a matmul produces its output tile by tile; bias addition, an activation, a residual addition, scaling or quantisation can be applied to each tile in registers before it is written (epilogue fusion). Similarly, a cheap transformation of the input (dequantising int4 weights, applying a norm's scale) can happen as tiles are loaded (prologue).
  • Horizontal fusion: several independent small operations — for example, the same optimiser update applied to hundreds of parameter tensors — launched as one kernel. PyTorch's "foreach" and "fused" AdamW implementations do this.

What doesn't fuse easily is work whose next step needs the whole result of the previous one: two consecutive matmuls (the second needs complete rows of the first's output), or a reduction along one axis followed by work along another. These sometimes yield to algorithmic cleverness — FlashAttention (gpu7) fuses the two matmuls and the softmax of attention by restructuring the softmax so it can be computed incrementally — but a general-purpose compiler won't find such rewrites by itself.

3. How torch.compile works

torch.compile is a pipeline of three components, each solving one problem.

TorchDynamo — capture. Python code is compiled to bytecode before it runs. Dynamo hooks into CPython's frame evaluation (a documented interpreter extension point) and, when a compiled function is called, symbolically runs its bytecode: PyTorch operations become nodes in an FX graph (PyTorch's graph representation), while ordinary Python — loops over layers, attribute lookups, arithmetic on constants — is executed away, so the graph contains only tensor work. Alongside the graph it records guards: the assumptions it relied on, such as "x has shape [8, 4,096] and dtype bfloat16" or "self.training is True". On later calls the guards are checked first; if they pass, the compiled code runs directly. When Dynamo meets something it can't trace — a call into an unsupported library, .item() turning a tensor into a Python number that then controls an if, printing a tensor — it inserts a graph break: it compiles the graph so far, runs the problematic code in normal Python, and starts a new graph after it.

AOTAutograd — the backward pass. In eager mode, autograd builds the backward computation as the forward runs. AOTAutograd instead traces the forward and backward together ahead of time, producing a joint graph that can be optimised as a whole — for example, choosing which intermediate tensors to save for the backward pass and which to recompute cheaply (recomputing an element-wise result can be faster than saving and re-reading it). It also decomposes PyTorch's roughly 2,000 operators into a much smaller set of primitive ones (about 250 in the PrimTorch set), so the back end only needs to handle those.

TorchInductor — code generation. Inductor lowers each primitive to a loop-level description ("for each output element i, compute …") and its scheduler fuses nodes whose loops line up, so that intermediates live in registers. Each fused group becomes a Triton kernel on GPUs (C++/OpenMP on CPUs). Matmuls and convolutions usually go to cuBLAS/cuDNN, or, in max-autotune mode, to Triton matmul templates that are benchmarked against cuBLAS and can carry fused epilogues.

4. Using torch.compile, and what goes wrong

model = torch.compile(model)                              # default: fusion, moderate compile time
model = torch.compile(model, mode="reduce-overhead")      # + CUDA graphs: small batches, inference
model = torch.compile(model, mode="max-autotune")         # + kernel autotuning: long compile, best speed
model = torch.compile(model, fullgraph=True)              # make any graph break an error

The first call to a compiled function is slow — tens of seconds to minutes for a large model — because it traces and generates kernels. Subsequent calls with matching guards run the compiled code. Three problems account for most disappointing results.

Graph breaks. Common causes: .item(), .tolist() or print on tensors; data-dependent Python control flow (if x.sum() > 0:); calls into NumPy or other libraries on tensor data; some custom autograd functions or C extensions. Each break limits fusion across it and adds overhead; a break inside a transformer block, repeated 32 times, can erase most of the gain. Find them with TORCH_LOGS="graph_breaks" or torch._dynamo.explain(model)(inputs). Fix by moving logging and checks outside the compiled region, replacing Python conditionals with tensor operations (torch.where), or using torch.cond for true control flow.

Recompilation. Every guard failure triggers a recompile. The usual trigger is shape: with variable sequence lengths, each new length fails the shape guard. PyTorch first specialises on the exact shape; on seeing a second value it recompiles a dynamic-shape version that treats the dimension as a symbol. After a limit (8 recompiles per function by default) it gives up and runs that function eagerly. TORCH_LOGS="recompiles" shows each recompile and the failing guard. The remedies are marking dimensions dynamic up front (torch._dynamo.mark_dynamic or dynamic=True), and padding or bucketing inputs to a few fixed sizes.

Compile time. Minutes of compilation matter for iteration speed and for server start-up. Inductor caches compiled kernels on disk (reused across runs with the same code and shapes), and "regional compilation" — compiling one transformer block and reusing it for all identical layers — cuts compile time for deep models.

5. CUDA graphs: removing launch overhead

Even perfectly fused code launches dozens of kernels per layer, and each launch costs CPU time. When kernels are long (training with large batches), the CPU runs ahead and the GPU never waits. When kernels are short — a decode step for one sequence, where each kernel lasts a few microseconds — the GPU finishes each kernel before the CPU has launched the next, and it sits idle. That is the overhead-bound regime from gpu1.

A CUDA graph is created by capturing a stream: you run the sequence once in capture mode, CUDA records every kernel and its arguments instead of (or as well as) executing them, and afterwards you replay the whole recording with one call. Because the recording contains fixed kernel arguments — including memory addresses — replays must use the same shapes and the same buffers: inputs are copied into static tensors before each replay, and outputs appear in static tensors. PyTorch exposes this as torch.cuda.CUDAGraph and applies it automatically in mode="reduce-overhead".

The effect on overhead-bound workloads is large. In the gpt-fast case study from gpu2, compiling Llama-7B's decode step with CUDA graphs and a static KV cache took it from 25.5 to 107 tokens per second on an A100 — the whole gain came from removing CPU overhead and fusing kernels, after which the model was bandwidth-bound. Inference servers use CUDA graphs universally for decoding: vLLM captures graphs for a list of batch sizes at start-up and pads each decode batch up to the nearest captured size; because attention over variable-length sequences isn't always graph-safe, it captures "piecewise" graphs covering everything between attention calls, or full graphs when the attention back end supports it.

6. Triton: writing fused kernels in Python

When the compiler doesn't fuse what you need, you write a kernel. Triton, created by Philippe Tillet and developed at OpenAI, lets you do that in Python with a different mental model from CUDA. In CUDA (gpu5) you write the code for one thread and arrange threads, shared memory and synchronisation yourself. In Triton you write the code for one program — an instance of the kernel identified by tl.program_id — that operates on whole blocks of data: load a block of values into what behaves like a small array, compute on it with NumPy-like operations, store it. The compiler decides how many threads implement each program, lays out memory accesses for coalescing, uses shared memory where it helps, and — for tl.dot — emits tensor-core instructions.

A fused row-wise softmax shows the style, including a reduction:

import triton, triton.language as tl

@triton.jit
def softmax_kernel(x_ptr, y_ptr, n_cols, stride, BLOCK: tl.constexpr):
    row = tl.program_id(0)                        # one program per row
    cols = tl.arange(0, BLOCK)                    # BLOCK ≥ n_cols, a power of two
    mask = cols < n_cols                          # ragged edge of the row
    x = tl.load(x_ptr + row * stride + cols, mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)                     # reduction in registers
    num = tl.exp(x.to(tl.float32))
    y = num / tl.sum(num, axis=0)                 # second reduction, same row
    tl.store(y_ptr + row * stride + cols, y, mask=mask)   # one read, one write

# launch: one program per row
# softmax_kernel[(n_rows,)](x, y, n_cols, x.stride(0), BLOCK=triton.next_power_of_2(n_cols))

The eager equivalent — max, subtract, exp, sum, divide — is several kernels and several passes over the tensor; this is one pass in, one pass out. Triton's official tutorial benchmarks this exact kernel against PyTorch's eager softmax and shows it running close to the memory-bandwidth limit. Performance knobs are exposed as parameters rather than code: block sizes, num_warps (how many warps implement each program) and num_stages (how deep the compiler pipelines asynchronous loads in loops), and the @triton.autotune decorator benchmarks a list of configurations per input shape and caches the winner.

Triton's reach is the reason it matters: it is what TorchInductor generates, it runs on NVIDIA and AMD GPUs, and many production kernels — FlashAttention implementations, fused MoE layers, quantised matmuls in serving systems, and training kernels such as those in LinkedIn's Liger Kernel library — are written in it.

7. A worked example: one transformer layer

How much does fusion buy in a real layer? Take a Llama-3-8B-sized layer (d = 4,096, MLP width 14,336, 8 KV heads) processing 8,192 tokens in BF16 on an H100, and look at its non-matmul, non-attention work. Typical eager implementations do: two RMSNorms (each about five kernels and seven passes over the activation), two residual additions, rotary position embedding on queries and keys (slices, negations, concatenation, multiplies and an add — around six kernels, ten passes), and the SwiGLU product silu(gate) × up. Counting bytes at 3.35 TB/s plus 5 µs per launch (the lab does this):

2 × residual add130 µs, 2 kernels40 µs, folded into the norms

The layer's matmuls take about 5.2 ms at 70% of peak, so fusion improves this layer by about 13% — useful, not dramatic, because at 8,192 tokens the layer is dominated by compute-bound matmuls. Now shrink the batch to a decode step of a few sequences: the matmuls become memory-bound and short, the element-wise kernels become tiny, and launch overhead dominates — which is where fusion plus CUDA graphs gives several-fold gains, as gpt-fast showed. Published results fall between these poles: PyTorch 2.0's 43% average across 163 models (21% in FP32, 51% with mixed precision, where matmuls are faster and the memory-bound share is larger); and Liger Kernel's fused Triton kernels for RMSNorm, RoPE, SwiGLU and cross-entropy, which LinkedIn reports raise Llama 3 8B training throughput by about 20% and cut memory by about 60% on 8 A100s — the memory saving coming mostly from never materialising the full logits tensor (gpu3).

How Inductor chooses fusions

After decomposition, every operation is a node with a loop nest over its output and a body saying how each element is computed from inputs. Inductor's scheduler then greedily merges nodes that can share a loop — same iteration space, or a reduction and the element-wise work around it along the same axis — scoring candidate fusions by the memory traffic they save, and refusing ones that would recompute expensive work many times or combine incompatible loop structures. Reductions get special treatment: a row reduction followed by a broadcast back over the row (normalisation, softmax) becomes one "persistent" kernel if the row fits in a block, or a looped kernel if it doesn't. Inductor also plans memory, reusing buffers whose lifetimes don't overlap, and chooses what autograd saves: sometimes recomputing a cheap element-wise result in the backward pass is faster than writing and re-reading it, and its min-cut-based partitioner makes that choice automatically.

Inside the Triton compiler

A Triton function is parsed into Triton IR, a representation of block-level operations. The compiler then assigns each block a layout — how its elements are distributed across threads and registers — choosing layouts that make loads coalesced and that match the operand formats tensor-core instructions expect, inserting conversions (through shared memory) where layouts must change. Loops that load tiles are software-pipelined to num_stages depth, issuing asynchronous copies (cp.async or TMA) several iterations ahead. The result is lowered to LLVM IR and then to PTX, NVIDIA's intermediate assembly, or to AMD's equivalent. This is why the same Python source can be competitive on different GPU generations — and also why brand-new hardware features (Blackwell's tensor memory, for example) need compiler support before Triton code benefits from them.

Guards, dynamic shapes and symbolic reasoning

Dynamic-shape compilation replaces concrete sizes with symbols and reasons about them: if the code reshapes [B, S, 4096] to [B·S, 4096], the compiler tracks B·S symbolically and records guards such as "S > 1" or "S is divisible by 8" when the generated code depends on them. Specialising on exact sizes produces the best kernels but recompiles for every new size; fully dynamic kernels avoid recompiles but can't exploit known sizes (for example, choosing a block size that exactly divides a dimension). Practical systems take the middle path: dynamic batch and sequence dimensions, static hidden sizes, and padding to multiples of 8, 16 or 64 so the dynamic kernels still meet tensor-core alignment.

Ahead-of-time compilation for deployment

Just-in-time compilation is awkward for servers: start-up time, compile-time memory spikes, and the risk of a recompile under load. torch.export captures a whole model into a single graph with explicitly declared dynamic dimensions (graph breaks are errors), and AOTInductor compiles that into a shared library that can be loaded without Python. Similar deployment paths exist outside PyTorch — TensorRT and TensorRT-LLM build optimised engines ahead of time for fixed ranges of shapes. The trade-off is flexibility: every shape and code path must be known at build time.

Megakernels: the far end of fusion

Even with CUDA graphs, a decode step is a sequence of separate kernels, and between two kernels the GPU drains: the last blocks of one kernel finish while most SMs sit idle, and the next kernel's loads only start after it launches. Hazy Research's 2025 "Look Ma, No Bubbles" work removed those gaps for Llama 3.2 1B by fusing the entire forward pass into one persistent "megakernel": each SM runs an interpreter that pulls small tasks (a slice of a matmul, a piece of attention) from a schedule, with fine-grained counters in global memory standing in for kernel boundaries, and loads for the next task starting while the current one computes. On an H100 they reported using about 78% of memory bandwidth and beating vLLM and SGLang by over 1.5× in batch-1 latency. The approach shows how much time the gaps between kernels cost in latency-critical decoding — and, because the kernel is specific to one model and GPU, why it remains a specialist technique rather than a default.

Fusion and numerics

Fused kernels often keep intermediates in FP32 registers where eager code rounded them to BF16 in memory, and they may sum in a different order. Results therefore differ slightly — usually for the better in accuracy, but enough to break exact-equality tests and occasionally to change which token wins at temperature 0 (gpu4). When a compiled model diverges meaningfully from eager, PyTorch's accuracy minifier (TORCHDYNAMO_REPRO_AFTER="aot" with an accuracy check level) shrinks the model to the smallest graph that reproduces the difference, which isolates whether a specific fusion or a real bug is responsible.

Rolling out torch.compile safely

Teams adopting torch.compile in training typically compile the model (or each repeated block), run a few hundred steps side by side with eager to compare loss curves, profile to confirm the speed-up comes from where expected, and check the logs for graph breaks and recompiles. For long training runs, compile time is negligible; the concern is correctness and stability across a months-long job, including after checkpoint restarts (compiled caches may need to be rebuilt, adding minutes to each restart unless cached on shared storage).

In serving, the concerns are latency and memory. A first request that triggers a compile can take seconds or minutes, so servers compile and capture everything at start-up for a fixed list of batch sizes and token budgets and never compile on the request path. Recompilation storms — variable prompt lengths each failing a shape guard — show up as sporadic multi-second latency spikes at p99 and as "recompile limit reached" warnings, after which affected functions silently run eagerly and slower. CUDA graphs cost memory: each captured size keeps its own static buffers, which competes with KV-cache space, so servers limit how many sizes they capture.

Symptoms and what they mean

Compiled model is no faster. Either the model is dominated by large matmuls (check with the profiler: if 80% of GPU time is GEMMs at good efficiency, there is little for fusion to do), or graph breaks left the hot path eager (check graph_breaks logs), or the step is bound by data loading or communication.

Speed-up disappears after some steps. Recompiles hit the limit and fell back to eager — typically from varying shapes or from a Python value (a step counter, a flag) that the code reads inside the compiled region and Dynamo guards on.

Out of memory only when compiled. CUDA graph pools, autotuning benchmarks at compile time, or different saved-activation choices. Compare memory snapshots between modes; mode="default" avoids CUDA-graph pools.

Results differ from eager. Expect last-bit differences; use tolerances. Investigate larger differences with the accuracy minifier, and check for code with side effects inside the compiled region (in-place updates of Python state), which compiled code may not reproduce.

Observability for compiled models

Treat compilation as part of the system you monitor. Log compile time per run and per restart, the number of graphs and graph breaks, and recompile counts (PyTorch keeps counters in torch._dynamo.utils.counters, and tlparse turns structured compile logs into a browsable report of every graph, guard and generated kernel). Alert when recompiles appear after warm-up in a server, since they mean some input shape escaped the buckets. Keep the generated kernels (TORCH_LOGS="output_code") for the hot path, so a regression after a PyTorch upgrade can be traced to a specific changed kernel.

When to write the kernel yourself

The decision rule from gpu5 applies: profile, compute each hot kernel's roofline bound, and write Triton only where a specific memory-bound pattern is both large and unfused. Good candidates are losses over large vocabularies (never materialise the logits), fused normalisation with quantisation for an FP8 matmul, custom attention masks or positional schemes, MoE routing and permutation, and dequantise-and-multiply for unusual weight formats. Keep the eager version as the reference implementation and test the kernel against it across shapes, dtypes and edge cases, just as with CUDA.

Goal: estimate what fusion saves in one transformer layer by counting passes over memory and kernel launches. This machine has no NVIDIA GPU, so this is the calculation rather than a benchmark; it runs on plain Python 3.12.

T, d, dff = 8192, 4096, 14336          # tokens, hidden size, MLP width (Llama-3-8B)
BW, LAUNCH_US = 3.35e12, 5             # H100 HBM bytes/s, per-kernel overhead

# (name, elements per pass, eager kernels, eager passes, fused kernels, fused passes)
OPS = [
    ("2x RMSNorm",       2 * T * d,      10, 7, 2, 2),
    ("2x residual add",  2 * T * d,       2, 3, 0, 1),   # folded into the next norm
    ("RoPE on q and k",  T * (d + 1024),  6, 10, 1, 2),
    ("SwiGLU silu(g)*u", T * dff,         2, 5, 1, 3),
]
tot_e = tot_f = 0.0
for name, n, ke, pe, kf, pf in OPS:
    te = n * 2 * pe / BW * 1e6 + ke * LAUNCH_US        # BF16 = 2 bytes
    tf = n * 2 * pf / BW * 1e6 + kf * LAUNCH_US
    tot_e, tot_f = tot_e + te, tot_f + tf
    print(f"{name:18s} eager {te:6.0f} us ({ke:2d} kernels)  fused {tf:5.0f} us")
mm = 2 * T * (2 * d * d + 2 * d * 1024 + 3 * d * dff) / (989e12 * 0.7) * 1e6
print(f"element-wise {tot_e:.0f} -> {tot_f:.0f} us; matmuls {mm:.0f} us; "
      f"layer {(mm + tot_e) / (mm + tot_f):.2f}x faster")

What to look for. Element-wise work drops from about 1,100 µs to about 400 µs, but the layer only improves about 1.13× because the matmuls (about 5,160 µs) dominate at 8,192 tokens. Now set T = 64: the passes shrink 128-fold but the launch costs don't, so the eager column is mostly launch overhead and the fused/eager ratio grows — the small-batch regime where fusion and CUDA graphs give their biggest wins. Try setting LAUNCH_US = 0 to see how much of the gain at small T was overhead rather than bytes.

Estimate the time unfused (five kernels) and fused (one kernel), including about 5 µs of launch overhead per kernel. Then redo it for a 1 × 4,096 tensor, as in single-sequence decoding. What does each case tell you about which tool to reach for?

Answer

Large tensor. Size: 4,0962 × 2 bytes ≈ 33.5 MB. Unfused, each kernel reads and writes it: 67 MB × 5 = 335 MB → about 100 µs of traffic, plus 5 × 5 µs = 25 µs of launches → about 125 µs. Fused: one read and one write, 67 MB → about 20 µs + 5 µs → about 25 µs. About 5× faster, and the intermediate tensors never need to exist, saving memory too. Here fusion (torch.compile or a Triton kernel) is the tool; CUDA graphs would save only the 20 µs of extra launches.

Tiny tensor. Size: 4,096 × 2 bytes = 8 KB. Traffic is a few nanoseconds per pass — irrelevant. Unfused: 5 launches ≈ 25 µs, fused: one launch ≈ 5 µs, and with a CUDA graph covering the whole decode step, the per-kernel CPU cost almost disappears. Here the problem is entirely overhead: fusion helps by reducing the number of launches, and CUDA graphs help most. This is why decode-heavy inference uses mode="reduce-overhead" or equivalent graph capture, while training with large batches mostly benefits from fusion itself.
