An engineer wants to fully fine-tune a 13-billion-parameter model on a server with eight 80 GB H100s — 640 GB of GPU memory in total, five times the 26 GB the weights occupy. The job crashes at the first optimiser step with "CUDA out of memory". The reason is gpu3's arithmetic: mixed-precision training with Adam keeps about 16 bytes per parameter — weights, gradients, a 32-bit master copy and two 32-bit optimiser moments — so the model state is 208 GB. Plain data parallelism, the default way to use several GPUs, gives every GPU a complete copy of all 208 GB. Eight GPUs hold eight identical copies of the optimiser state, and none of them can hold one.

At frontier scale the problem is starker. Llama 3 405B's model state is about 6.5 TB; no single GPU or server comes close. Yet the total memory of the cluster is enormous. The insight behind ZeRO (Zero Redundancy Optimizer, from Microsoft's DeepSpeed team in 2019) is that the redundancy is unnecessary: each GPU only needs its own slice of the optimiser state to do its part of the update, and it only needs a layer's full parameters for the brief moment that layer is computing. Store everything in shards, gather what is needed just in time, and the 208 GB becomes 26 GB per GPU on eight GPUs. PyTorch's FSDP (Fully Sharded Data Parallel) is the same idea built into PyTorch, and it is now the default way to train models from a few billion parameters upwards.

Model state is only half the story. The forward pass also saves activations for the backward pass, and they grow with sequence length and batch size: 28 GB per 4,096-token sequence for that 13B model. Activation checkpointing trades compute for this memory by recomputing activations instead of storing them.

This lesson builds these techniques up step by step: what fills GPU memory during training, how ZeRO's three stages remove redundancy and what each costs in communication, how FSDP runs a layer (gather, compute, free, prefetch), hybrid sharding, checkpointing and selective recomputation, and offloading. We finish with how to choose a layout — including a rule of thumb for when FSDP's communication stops hiding behind compute — and with how memory problems are debugged in practice.

Eight students and one very expensive textbook

A class of eight students must each work through every chapter of an enormous textbook, and each must also keep detailed notes on the book. Buying every student a full copy, and having each keep notes on every chapter, is the plain data-parallel approach: simple, but eight times the paper. The ZeRO approach: each student owns one-eighth of the book and keeps the notes only for their own chapters. When the class reaches chapter 5, its owner photocopies it for everyone; they all work through it; then they throw the copies away and move on. At the end, each student updates the notes for their own chapters using what everyone learned. Everyone still reads every chapter; nobody stores more than their share. The cost is the photocopying — which is why it must happen while everyone is still busy with the previous chapter.

Where the analogy breaks: in training, "reading the chapter" is a layer's forward and backward pass, the photocopying is an all-gather over NVLink or the network, and the whole class moves through the book once forwards and once backwards every step.

What gets sharded, stage by stage

The three stages remove redundancy in order of size. ZeRO-1 shards the optimiser state — the FP32 master weights and Adam moments, 12 of the 16 bytes — so each GPU keeps only the slice it will update. ZeRO-2 also shards the gradients, because each GPU only needs the summed gradients for its own slice. ZeRO-3 also shards the BF16 parameters, gathering each layer's parameters from all GPUs just before the layer runs and freeing them afterwards. With N GPUs, stage 3 brings model state from 16 bytes per parameter down to about 16/N. Activation checkpointing attacks the other half of memory: instead of saving every intermediate result of the forward pass, it saves a few and recomputes the rest when the backward pass needs them, trading roughly one extra forward pass for a large cut in activation memory.

A first calculation

Put numbers on the 13B example from the introduction. Plain data parallelism: 208 GB of model state on each of the eight GPUs — no chance. ZeRO-1 shards the 156 GB of optimiser state (12 bytes per parameter) eight ways, leaving 26 GB of BF16 weights, 26 GB of gradients and 19.5 GB of optimiser state per GPU: 71.5 GB before any activations — still too much. ZeRO-2 also shards gradients: 26 + 3.25 + 19.5 ≈ 49 GB. ZeRO-3 shards everything: 26 GB. Then add activations — 28.5 GB for one 4,096-token sequence, or about 2.4 GB with checkpointing — and the job fits comfortably with ZeRO-3 plus checkpointing. Every number in that paragraph comes from multiplying parameter counts by bytes, which is why memory planning is done on paper before any job is launched.

1. What fills GPU memory during training

From gpu3, a training step needs, per GPU:

  • Model state, proportional to parameters Ψ: BF16 parameters (2Ψ bytes), BF16 gradients (2Ψ), FP32 master weights (4Ψ) and two FP32 Adam moments (8Ψ) — 16Ψ in total.
  • Activations, proportional to tokens: roughly 34·s·b·h bytes per layer with FlashAttention, for sequence length s, micro-batch b and hidden size h.
  • Logits at the output: s × b × vocabulary values, often in FP32, plus their gradient.
  • Temporary buffers: communication buffers, workspace for matmul and attention kernels, gathered parameters in FSDP.
  • Fragmentation: memory the caching allocator has reserved but can't use for the next request because it is split into pieces too small.

The techniques in this lesson address the first two, which are the large ones. Model state is independent of batch size and sequence length; activations are independent of how many GPUs share the model. That is why the fixes are different: sharding for model state, recomputation (and splitting sequences) for activations.

2. The redundancy in data parallelism

In plain data parallelism (DP), each of N GPUs holds the full model, processes its own micro-batch, and after the backward pass all-reduces the gradients so every GPU has the same summed gradient; then each GPU runs the same optimiser step on the same numbers and gets the same new weights. N GPUs perform N identical optimiser steps on N identical copies of 16Ψ bytes. Only the forward and backward passes, which process different data, genuinely need to happen on every GPU. Everything else is redundant — that is the observation ZeRO turns into savings.

3. ZeRO-1 and ZeRO-2: shard the update

Divide the parameters into N equal slices; GPU i "owns" slice i. With ZeRO-1, GPU i keeps the FP32 master weights and Adam moments only for slice i (12Ψ/N bytes), but still keeps full BF16 parameters and gradients. A step goes:

  1. Forward and backward on the local micro-batch with the full BF16 parameters, producing full local gradients.
  2. Reduce-scatter the gradients: GPU i receives the sum over all GPUs of slice i's gradients.
  3. GPU i runs Adam on slice i only, updating its FP32 master weights and moments.
  4. All-gather the updated BF16 parameters so every GPU again has the full model.

Reduce-scatter plus all-gather is exactly what an all-reduce does internally (gpu8), so ZeRO-1 moves the same bytes as plain DP while cutting memory to 4Ψ + 12Ψ/N. ZeRO-2 notices that after step 2 each GPU only needs slice i of the gradients, so gradients for other slices can be freed as soon as they have been reduce-scattered — in practice bucket by bucket during the backward pass. Memory falls to 2Ψ + 14Ψ/N, still with the same communication. For the ZeRO paper's example of 7.5B parameters on 64 GPUs: 120 GB for DP, 31.4 GB for ZeRO-1, 16.6 GB for ZeRO-2.

4. ZeRO-3 and FSDP: shard the parameters too

ZeRO-3 also shards the BF16 parameters: GPU i permanently holds only slice i of every parameter tensor. Model state per GPU becomes 16Ψ/N — 1.9 GB in the example. But a layer can't run with a slice of its weights, so the full parameters of each layer are assembled just in time:

  1. Forward, layer by layer: all-gather layer ℓ's parameters from all GPUs; run its forward pass; free the gathered parameters (keeping only the local shard).
  2. Backward, layer by layer in reverse: all-gather layer ℓ's parameters again; compute its gradients; reduce-scatter the gradients so each GPU keeps the summed gradient for its own slice; free the gathered parameters and full gradients.
  3. Optimiser step: each GPU updates its own slice, with no further communication — the parameters are already in sharded form for the next step.

Communication per step: two all-gathers of all parameters plus one reduce-scatter of all gradients, about 3 × 2Ψ bytes per GPU in BF16, compared with about 2 × 2Ψ for DP's all-reduce — 1.5 times the traffic. And it happens layer by layer, on the critical path of every layer, unless it is overlapped.

PyTorch's FSDP implements this. You wrap the model in units — typically one per transformer block — and each unit's parameters are flattened and sharded. The newer FSDP2 API (fully_shard) shards each parameter individually as a DTensor (a distributed tensor that knows how it is split across GPUs), which composes more cleanly with tensor parallelism, FP8 and checkpointing:

from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy
mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
for block in model.layers:                 # one FSDP unit per transformer block
    fully_shard(block, mp_policy=mp)
fully_shard(model, mp_policy=mp)           # the rest: embeddings, final norm, head
optim = torch.optim.AdamW(model.parameters(), lr=3e-4)   # states are sharded too

Prefetching is what makes this fast: while layer ℓ computes, FSDP issues the all-gather for layer ℓ+1 on a separate communication stream, so its parameters are ready when needed. In the backward pass it prefetches layer ℓ−1 while computing layer ℓ and overlaps reduce-scatters too. Only about two layers' full parameters are ever materialised at once. The option to not reshard after forward keeps each layer's gathered parameters until its backward pass, skipping the second all-gather — back to ZeRO-2's communication at the cost of holding full parameters (useful when memory allows, and for pipeline stages that run several micro-batches).

Wrapping granularity matters. One unit per transformer block is the norm. A single unit around the whole model would gather everything at once, defeating the purpose; units that are too small mean many tiny collectives with high latency. Embeddings and the output layer are often their own units because at a 128K vocabulary they are the largest single tensors.

5. Hybrid sharding: keep the gathers on fast links

If the shard group spans the whole cluster, every layer's all-gather crosses the network. Hybrid sharded data parallelism (HSDP) shards within a group — usually the 8 GPUs of a node, on NVLink — and replicates across groups, with one gradient all-reduce across groups per step. The per-layer traffic stays on NVLink; the network carries the same once-per-step gradient reduction as plain DP.

The group must be large enough to hold the model state. A worked example for a 70B model, 16 × 70 × 109 = 1.12 TB of state: sharded over 8 GPUs it is 140 GB per GPU — doesn't fit on 80 GB. Over 32 GPUs (four nodes) it is 35 GB, which fits with room for activations, but now the shard group spans the network. The usual answer for models of this size is to add tensor parallelism inside the node (each GPU holds 1/8 of each layer), and shard the remaining state across nodes with FSDP: with TP = 8 and FSDP over 16 nodes, each GPU holds 1.12 TB / 128 ≈ 8.8 GB of state. This is the 2D layout TorchTitan uses for Llama 3.1 70B, and adding pipeline parallelism gives the 3D layout used for 405B.

6. Activation memory and checkpointing

Activations are saved in the forward pass because the backward pass needs them: the weight gradient of a linear layer is Xᵀ·dY, which needs the layer's input X, and differentiating normalisation, activation functions and attention needs their inputs (gpu3). They are proportional to tokens per GPU and to the number of layers, and independent of data-parallel sharding: FSDP does nothing for them.

Activation checkpointing (also called gradient checkpointing) keeps only each transformer block's input during the forward pass and discards everything else inside the block. When the backward pass reaches a block, it re-runs that block's forward pass from the saved input to regenerate its activations, then does the block's backward pass and discards them again.

The numbers: per layer, stored activations fall from about 34·s·b·h bytes to the block input, 2·s·b·h bytes in BF16 — about 17 times less — plus one block's full activations during its recomputation. For the 13B model (h = 5,120, 40 layers) at s = 4,096, b = 1: 28.5 GB without checkpointing; with it, 40 × 42 MB ≈ 1.7 GB of saved inputs plus 0.7 GB for the block being recomputed, about 2.4 GB. The cost is one more forward pass: forward is roughly a third of forward plus backward (2N versus 4N FLOPs per token), so the step does about 33% more compute. Chen et al.'s 2016 paper showed the general version: checkpointing every √n layers of an n-layer network brings activation memory to O(√n) for the same one-extra-forward cost.

Selective recomputation is more economical. Not all activations cost the same to recompute: the attention core (scores, softmax, dropout) takes a lot of memory but few FLOPs, while the big matmuls are the reverse. Korthikanti et al. at NVIDIA recompute only the cheap, memory-hungry parts and, combined with sequence parallelism (splitting the activations of normalisation and dropout along the sequence across tensor-parallel GPUs, which tensor parallelism alone leaves replicated), cut activation memory about five-fold while reducing the recomputation overhead by over 90%. Training a 530B-parameter model on 2,240 A100s, that raised MFU from 42.1% with full recomputation to 54.2%. With FlashAttention, which already recomputes attention internally, the same principle continues: recompute cheap element-wise operations (norms, activations) and keep the matmul inputs.

7. Offloading: using CPU memory and NVMe

A server's CPU memory is often 1-2 TB — more than all its GPUs combined — and NVMe drives hold tens of terabytes. ZeRO-Offload keeps the optimiser state in CPU memory and runs the Adam step on the CPU; gradients go down over PCIe and updated parameters come back up. ZeRO-Infinity also offloads parameters and can use NVMe. Activation offloading moves saved activations to CPU memory during the forward pass and back for the backward pass. The constraint is bandwidth: PCIe Gen5 moves about 64 GB/s each way, against 3.35 TB/s of HBM, and a CPU Adam step over billions of parameters takes seconds. Offloading shines when GPUs are scarce — ZeRO-Offload's paper trained 13B-parameter models on a single V100 — and for fine-tuning big models on one node; for large-scale pre-training, sharding over more GPUs is almost always the faster use of money.

8. A worked plan: fine-tuning a 13B model on one node

Eight 80 GB H100s, full fine-tuning with AdamW, sequence length 4,096, micro-batch 1 per GPU, BF16 with FlashAttention (the lab computes these):

  • Plain DP: 16 × 13B = 208 GB per GPU. Impossible.
  • ZeRO-2: 2Ψ + 14Ψ/8 = 26 + 22.8 = 48.8 GB per GPU of state, plus 28.5 GB of activations without checkpointing: 77 GB — too close to 80 GB once buffers and fragmentation are added.
  • FSDP (ZeRO-3) over the 8 GPUs: 26 GB of state per GPU. Plus 28.5 GB of activations: about 55 GB — fits. With checkpointing: about 28 GB, leaving room to raise the micro-batch to 4, which improves matmul efficiency and more than pays for the recomputation.
  • Communication: about 3 × 26 GB = 78 GB sent per GPU per step, all over NVLink at 450 GB/s — about 0.2 s. Compute per GPU per step at micro-batch 4: 6 × 13 × 109 × 16,384 tokens ≈ 1.3 × 1015 FLOPs, about 2.6 s at 50% of peak (plus a third with checkpointing). Communication hides comfortably.

The same arithmetic, scaled up, produces the layouts of published runs. Meta's Llama 3 405B used tensor parallelism of 8 within each server, pipeline parallelism of 16, context parallelism for long sequences, and FSDP-style sharded data parallelism across the rest; TorchTitan, PyTorch's reference trainer, reports that composing FSDP2 with tensor and pipeline parallelism and Float8 training gave speed-ups of 65% for Llama 3.1 8B on 128 GPUs, and a further 12.6% (70B, 256 GPUs, 2D) and 30% (405B, 512 GPUs, 3D) over their baselines on H100s.

When FSDP's communication hides: tokens per GPU

For a layer with P parameters, FSDP moves about 3 × 2P bytes per GPU per step (two all-gathers and a reduce-scatter in BF16), while each GPU computes 6·P·T FLOPs for its T tokens per step. The ratio — FLOPs per communicated byte — is simply T, the tokens per GPU per step. To hide communication, that ratio must exceed the delivered FLOP rate divided by the link's bandwidth (the communication roofline of gpu2 and gpu8). For an H100 running at 50% of peak, about 500 TFLOP/s: over NVLink at 450 GB/s, T must exceed about 1,100 tokens; over a 400 Gb/s network at 50 GB/s, about 10,000 tokens. A 4,096-token micro-batch per GPU hides easily within a node and not across nodes — which is the quantitative reason for hybrid sharding, and for adding tensor or pipeline parallelism when a fixed global batch spread over thousands of GPUs leaves each with too few tokens.

Composing sharding with other parallelisms

Real large-scale layouts are products of dimensions: TP × CP × PP × DP GPUs. Each GPU holds 1/TP of each layer's weights (tensor parallelism), 1/PP of the layers (pipeline), and within its data-parallel group a 1/DP shard of the remaining state (FSDP). Communication sits on the matching links: TP all-reduces on NVLink every layer, CP exchanges of keys and values within the node or rack, PP point-to-point sends across nodes, and FSDP gathers across the DP group once per layer per step. FSDP2's per-parameter DTensor sharding exists precisely so a tensor can be sharded along one dimension for TP and along another for FSDP at the same time. Choosing the degrees is a search: TP no larger than the NVLink domain, PP as small as memory allows (bubbles cost throughput), DP as large as the global batch permits.

Checkpointing and recomputation, optimally

Which activations to keep is an optimisation problem: minimise recomputation FLOPs subject to a memory budget. Frameworks offer points on the curve — full per-block checkpointing, selective recomputation of attention or MLP internals, checkpointing every k-th block, or offloading some saved tensors to CPU memory. PyTorch's compiler can make the choice automatically: its min-cut partitioner decides which forward values to save and which to recompute in the backward graph, favouring recomputation of cheap element-wise operations, and a memory-budget setting lets you trade further towards memory. The best configuration depends on sequence length (longer sequences make activations dominate), model width (wider models make matmul recomputation more expensive) and whether memory saved can buy a larger micro-batch.

Reducing the 16 bytes themselves

Sharding divides model state; other techniques shrink it. 8-bit optimiser states (bitsandbytes' 8-bit Adam) store the moments in 8 bits with block-wise scales, cutting 8 bytes to about 2; Adafactor stores factored second-moment estimates, one row vector and one column vector per matrix, instead of a full matrix; keeping master weights out entirely is possible with stochastic rounding (gpu4). ZeRO++ reduced communication rather than memory, with quantised all-gathers of weights and hierarchical partitioning that keeps a secondary copy of parameters within each node. Each of these trades some risk to convergence or accuracy for memory or bandwidth, and needs validation against the standard recipe.

Pipeline parallelism and memory

Pipeline parallelism divides the layers among stages, so each GPU holds only its stage's model state — the most direct way to cut memory for very deep models — but it has an activation cost that surprises people. To keep all stages busy, a schedule such as 1F1B (one forward, one backward) has several micro-batches in flight at once, and the first stage must hold the saved activations of up to as many micro-batches as there are stages until their backward passes arrive. So pipeline stages near the start need more activation memory than those near the end, and deeper pipelines need more micro-batches in flight. Checkpointing is commonly combined with pipelining for exactly this reason, and interleaved schedules trade more communication for smaller bubbles and more even memory.

The allocator and fragmentation

FSDP allocates and frees each layer's gathered parameters and gradients every step, in patterns that fragment memory: a request for a 500 MB buffer can fail with several gigabytes free in scattered pieces. PyTorch's caching allocator reports "allocated" (in use by tensors) and "reserved" (held from the driver, including cached free blocks); a large gap in an out-of-memory message is the fragmentation signature. Setting PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True lets the allocator grow segments in place instead of carving new fixed blocks, which removes most of it. FSDP also rate-limits how far ahead it prefetches, because unbounded prefetching would materialise many layers at once and defeat the sharding.

Planning memory before launch

Experienced teams don't discover memory limits by trial and error on a 1,000-GPU allocation. They compute a budget per GPU — model state after sharding, activations for the planned micro-batch and sequence length with the chosen recomputation policy, logits, communication buffers, and a 10-20% margin — then validate on a small number of GPUs with the same per-GPU shapes, since per-GPU memory depends on the shard size, not the total GPU count, once the layout is fixed. The lab's planner is the minimal version of this.

Debugging out-of-memory errors

When a job runs out of memory, the fastest path is a memory snapshot: torch.cuda.memory._record_memory_history() before the step, torch.cuda.memory._dump_snapshot("snap.pickle") after, and the viewer at pytorch.org/memory_viz shows every live allocation over time with the Python stack that made it. Typical culprits, in rough order of frequency: activations without checkpointing at a new, longer sequence length; the full logits tensor at a large vocabulary; an attention call silently falling back to a non-flash kernel (quadratic memory, gpu7); an FSDP unit that is too large (for example the whole model accidentally wrapped as one); gathered parameters kept alive by a stray reference; and fragmentation, visible as reserved memory far above allocated.

Initialisation and checkpoint I/O

Two practical traps come from forgetting that no single process should ever hold the full model. Initialisation: if every rank builds the full model on the CPU and then shards it, a node with eight ranks needs eight copies of the model in host memory — 1.1 TB for a 70B model in FP16 — and the host runs out of memory before training starts. The fix is to create the model on PyTorch's "meta" device (structure without storage) and materialise only each rank's shard, or to load weights shard by shard from a distributed checkpoint. Checkpoints: gathering the full state onto rank 0 to save it is slow and can itself run out of memory. Distributed checkpointing (torch.distributed.checkpoint, DeepSpeed's sharded format) has every rank write its shard in parallel, with metadata that allows reloading onto a different number of GPUs. At scale, saves are made asynchronous — copy shards to host memory, keep training, write in the background — because with failures every few hours (gpu1, gpu8), checkpoint frequency directly sets how much work each failure costs.

Fine-tuning versus pre-training

Most teams meet these tools in fine-tuning rather than pre-training, and the trade-offs differ. Fine-tuning runs are short, GPUs are few, and memory is the binding constraint, so ZeRO-3 with checkpointing, CPU offload of optimiser state, or parameter-efficient methods (LoRA, lm11) that avoid most of the 16 bytes are all reasonable. Pre-training runs for weeks on thousands of GPUs, so throughput dominates, and layouts are tuned to keep communication hidden even at the cost of more memory.

Performance symptoms of a memory layout

Throughput drops when you scale out at a fixed global batch. Tokens per GPU fell below the level where FSDP's gathers hide; add hybrid sharding, TP or PP, or increase the batch if convergence allows. Throughput is fine but MFU is low with checkpointing on. The 33% recomputation is being counted as waste — check HFU versus MFU (gpu3) and consider selective recomputation, or use the freed memory for a larger micro-batch. Periodic slow steps. Synchronous checkpoint writes, or allocator defragmentation (cudaMalloc/cudaFree calls visible in the profile) — expandable segments and asynchronous checkpointing fix both.

Goal: build the memory planner teams use before launching a job, check it against the ZeRO paper's numbers, and size a 13B fine-tune on one node. Pure Python 3.12; no GPU needed.

def model_state(psi, n, stage):              # bytes per GPU, mixed-precision Adam
    return {0: 16 * psi,
            1: 4 * psi + 12 * psi / n,
            2: 2 * psi + 14 * psi / n,
            3: 16 * psi / n}[stage]

def activations(s, b, h, layers, ckpt):       # BF16, FlashAttention (gpu3)
    full = 34 * s * b * h                     # per layer, everything saved
    return full * layers if not ckpt else 2 * s * b * h * layers + full

print("ZeRO paper: 7.5B parameters on 64 GPUs")
for st in range(4):
    print(f"  stage {st}: {model_state(7.5e9, 64, st) / 1e9:6.1f} GB")

psi, n, s, b, h, L = 13e9, 8, 4096, 1, 5120, 40
for ckpt in (False, True):
    ms, act = model_state(psi, n, 3), activations(s, b, h, L, ckpt)
    print(f"13B FSDP/8, checkpointing={ckpt}: state {ms / 1e9:.1f} + "
          f"activations {act / 1e9:.1f} = {(ms + act) / 1e9:.1f} GB of 80")
print(f"bytes sent per GPU per step: DP ~{4 * psi / 1e9:.0f} GB, FSDP ~{6 * psi / 1e9:.0f} GB")

What to look for. The four stages print 120, 31.4, 16.6 and 1.9 GB — matching the ZeRO paper, which confirms the formulas. The 13B fine-tune needs about 54.5 GB per GPU without checkpointing and 28.4 GB with it. FSDP sends about 78 GB per GPU per step against 52 GB for plain DP: the 1.5× cost.

Work it out

Full fine-tuning of a 13B model (40 layers, hidden size 5,120) on one node of 8 × 80 GB GPUs, sequence length 4,096, micro-batch 1 per GPU, BF16 with FlashAttention. (a) Can plain data parallelism work? (b) Memory per GPU for model state with FSDP? (c) Activation memory per GPU without and with per-layer checkpointing (use about 34·s·h bytes per layer without, 2·s·h with)? (d) Now the same model must be trained on 64 GPUs across 8 nodes with a global batch of 64 sequences. How would you lay it out?

Answer

(a) 16 × 13 × 109 = 208 GB of model state per GPU — impossible on 80 GB.

(b) Sharded over 8: 208 / 8 = 26 GB per GPU, plus a transient copy of about two layers' gathered parameters (about 0.6 GB each in BF16 — small).

(c) Without checkpointing: 34 × 4,096 × 5,120 ≈ 713 MB per layer × 40 = 28.5 GB. With per-layer checkpointing: 2 × 4,096 × 5,120 ≈ 42 MB per layer × 40 ≈ 1.7 GB, plus one layer's full activations (0.7 GB) during recomputation ≈ 2.4 GB. Total without checkpointing ≈ 26 + 28.5 + buffers ≈ 60 GB — fits, but with the logits (4,096 × vocabulary in FP32) and fragmentation it is tight; with checkpointing ≈ 30 GB, leaving room for a micro-batch of 4.

(d) One sequence per GPU is 4,096 tokens per GPU per step — enough to hide FSDP over NVLink (threshold about 1,100) but not over the network (about 10,000). So use hybrid sharding: shard the 208 GB within each node (26 GB per GPU, as above), replicate across the 8 nodes, and all-reduce gradients across nodes once per step: each GPU owns a 26 GB / 8 = 3.25 GB slice of the BF16 gradients and all-reduces it with its counterparts in the other 7 nodes, sending 2 × 7/8 × 3.25 ≈ 5.7 GB — about 115 ms at 50 GB/s, largely overlapped with the backward pass. Full sharding across all 64 GPUs would save memory (3.3 GB of state per GPU) that isn't needed, at the price of every layer's gathers crossing the slow network.
