A company has fine-tuned three open-weight models and wants every internal team, and later its customers, to call them through one API. The first version is a single GPU server running one model behind a load balancer. On launch day the support-chat team sends short questions, the legal team pastes 80-page contracts, and a data team kicks off a script that summarises two million tickets overnight. By 10 am the chat users see answers freeze mid-sentence for several seconds. By noon the legal team's requests time out after 60 seconds in a queue. The batch script, meanwhile, is getting excellent throughput, because it is using most of the GPU.

Nothing here is a bug in the model. It is a capacity and scheduling problem with three unusual features. First, the unit of work is not "a request" but tokens, and requests differ in size by a factor of a thousand. Second, the hardware is very expensive, roughly a few dollars per GPU per hour, and an idle GPU burns money just as fast as a busy one, so the platform must keep GPUs full. Third, keeping GPUs full means putting many users' work into the same forward pass, which means one user's request directly slows everyone else's in the same batch. Done badly, you get either a fleet that is cheap and unfair or one that is fair and ruinously expensive.

An interviewer asking you to "design a multi-tenant LLM inference platform" wants to see whether you can turn tokens per second into GPUs with real arithmetic, explain why the KV cache rather than the weights limits how many users fit, and design scheduling that is fair in the currency that matters. Strong answers also know what vLLM, the most widely used open-source engine, changed and why.

This lesson walks the interview in order: requirements with latency, quality, cost and safety targets; estimates by hand (weights, KV cache per token, decode step time, GPUs from compute and from bandwidth, the time-to-first-token budget); the API and data model; the architecture; then deep dives on continuous batching with paged KV memory, multi-tenant scheduling, the prefill/decode interference problem and multi-LoRA serving. It ends with the evaluation plan, failure modes, the PagedAttention paper as the real-world case, and a capacity-planner script you can run.

What "serving a model" means

Training produces a file of weights once. Serving is everything after: a request arrives with text, a GPU turns it into more text, and the reply streams back. A serving platform is the gateway, schedulers, GPU workers and bookkeeping that do this for many callers at once. A multi-tenant platform serves many separate customers (tenants) from one shared pool of hardware, which is cheaper than a pool each but means one tenant's load can hurt another, the noisy neighbour problem.

Every request runs in two phases, and almost every design decision follows from how different they are. In prefill, the model reads the whole prompt in one forward pass. All prompt tokens are processed in parallel, so the GPU does large matrix multiplications and its arithmetic units are the bottleneck: prefill is compute-bound. Prefill ends by producing the first output token. In decode, the model produces one token per forward pass, and each pass needs the token before it. A single sequence's decode step does very little arithmetic, but it must read every weight of the model from the GPU's memory to do it. Decode is memory-bandwidth-bound: the time is set by how many bytes must be read per step, not by how many multiplications are done.

To avoid recomputing the past at every step, the model stores, for every earlier token, a key vector and a value vector in each layer (the KV cache, taught in lm5). The cache grows by one entry per token per sequence. Weights are a fixed cost per GPU; the KV cache is a variable cost per active conversation, and it is what decides how many conversations fit at once.

The mental model: a bus, not a taxi

Think of a decode step as a bus that must drive the full route (read all weights) every time it moves one stop (one token). Driving the route with one passenger costs almost the same as driving it with a hundred, because the cost is the driving, not the passengers. So the platform's job is to put as many sequences as possible on each step: that is batching, and it is the whole economics of serving. The analogy breaks in two places. Each passenger brings luggage (their KV cache) that also has to be carried, so the bus slows down as it fills. And the bus has a fixed luggage hold (GPU memory), so the hold, not the seats, usually limits how many passengers board.

The two numbers users feel are time to first token (TTFT: queueing plus prefill plus network, the "is it broken?" number) and time per output token (TPOT, also called inter-token latency: how fast text streams once it starts). Throughput, total tokens per second across everyone, is what the operator pays for. Batching trades the two: a fuller batch raises throughput and lowers each stream's speed.

The picture above is the design in one glance. A gateway authenticates the tenant and enforces quotas measured in tokens. A router picks the model pool (and replica, preferring one that already holds this tenant's adapter or prompt prefix). A scheduler per pool queues requests fairly between tenants and admits them into a running batch only when there is memory for them. The engine on each replica runs continuous batching over a paged KV cache. Tokens stream back to the client and are counted as they go, so billing is right even when a client disconnects halfway. A control plane stores model versions, keeps weights cached near the GPUs and scales replica counts. A reader who stops here has the correct picture; the rest of the lesson is the arithmetic and the mechanisms behind each box.

1 · Requirements

Functional. One HTTP API, compatible with the widely used chat-completions request shape so existing client libraries work, in front of several self-hosted open-weight models: a large 70-billion-parameter model for hard tasks and a small 8-billion-parameter model for cheap, fast ones. Responses can stream token by token. Each tenant has API keys, per-model quotas and a priority tier. Tenants can upload LoRA adapters (small add-on weight matrices that specialise a base model, covered in lm11) and call "base model + my adapter". Every request is metered in input, cached and output tokens for billing. Out of scope, said aloud: training and fine-tuning jobs, the evaluation harness for tenants' own prompts, and the model-weights registry beyond "we can fetch version X".

Latency targets. For the 70B model: p95 time to first token under 1 second for prompts up to 4,000 tokens, and at least 30 output tokens per second per stream at p95 (faster than people read, which is about 5-8 tokens per second, but fast enough that code and lists appear promptly). For the 8B model: p95 TTFT under 400 ms. Long prompts above 32,000 tokens get a looser target that scales with length, stated in the documentation.

Quality target. Any change to how a model is served (quantisation, a new engine version, speculative decoding) must keep the model's score on a fixed internal evaluation suite within 1 point of the reference BF16 deployment, and greedy outputs on a regression set must match unless the change is expected to alter them. Serving is not allowed to silently make the model worse.

Cost target. GPU utilisation is the cost lever, so the target is stated as cost per million tokens served (blended input and output) and as average KV-cache utilisation above 60% at peak. The business may also want a "batch" tier: requests that can wait up to 24 hours, sold cheaper, used to fill troughs.

Safety and isolation targets. No tenant can see another tenant's prompts, outputs, adapters or usage, including through side channels such as cache timing. Prompts and outputs are not logged by default; when a tenant opts in, logs carry the tenant ID and a retention period. A per-tenant content-filter hook can run on inputs and outputs. Availability 99.9% per model per month (about 43 minutes of downtime).

The clarifying questions that change the design. "What is the input-to-output token ratio?" decides whether you are compute-bound (long prompts, retrieval-heavy traffic) or bandwidth-bound (short prompts, long answers). "Is the latency target on first token or on completion?" decides whether streaming solves the problem. "How bursty is traffic, and is there deferrable work?" decides how much headroom you buy versus how much you fill with batch jobs.

2 · Back-of-envelope estimates

Load. Assume 10 million requests per day. The average is 10,000,000 ÷ 86,400 ≈ 116 requests per second; with a peak-to-average ratio of 3, peak is about 350 requests per second. Average prompt is 1,500 tokens (system prompt, conversation history and retrieved context add up quickly) and average answer is 300 tokens. The router sends 30% of traffic to the 70B model (105 requests/s at peak) and 70% to the 8B model (245 requests/s).

Hardware. NVIDIA H100 SXM: 80 GB of HBM memory, 3.35 TB/s of memory bandwidth, and 989 TFLOPS of dense BF16 compute (NVIDIA's datasheet quotes 1,979 with structured sparsity; dense is half). Assume a cloud price of $3 per GPU-hour for round numbers. Two efficiency assumptions keep the maths honest: a well-tuned engine achieves about 70% of peak bandwidth in decode (model bandwidth utilisation, MBU) and about 50% of peak FLOPs in prefill (model FLOPs utilisation, MFU).

Weights. 70 billion parameters × 2 bytes (BF16) = 140 GB. That does not fit on one 80 GB GPU, so the 70B model runs with tensor parallelism across 4 GPUs (each layer's matrices split four ways; each GPU holds 35 GB of weights and the four exchange partial results every layer). Four GPUs give 320 GB; reserve 10% for activations, CUDA graphs and fragmentation, leaving 288 GB, of which 140 GB is weights and 148 GB is free for KV cache. The 8B model is 16 GB on one GPU, leaving 80 × 0.9 − 16 = 56 GB for KV cache.

KV cache per token. The formula is 2 (one key and one value) × layers × KV heads × head dimension × bytes per value. A Llama-3-70B-shaped model has 80 layers, 8 KV heads (grouped-query attention) and head dimension 128: 2 × 80 × 8 × 128 × 2 = 327,680 bytes = 320 KiB per token. The 8B shape (32 layers, 8 KV heads, 128): 2 × 32 × 8 × 128 × 2 = 131,072 bytes = 128 KiB per token. While a sequence decodes, its context averages the prompt plus half the answer: 1,500 + 150 = 1,650 tokens. So one active 70B sequence holds 1,650 × 320 KiB ≈ 0.54 GB, and 148 ÷ 0.54 ≈ 270 sequences fit per replica if memory is used perfectly. Without grouped-query attention (64 KV heads instead of 8), the same sequence would need 4.3 GB and only 34 would fit: GQA is an 8× change in serving economics.

Decode step time. Each decode step reads all weights once plus every active sequence's KV cache. With a batch of 128 sequences on a 70B replica: 140 GB + 128 × 0.54 GB = 140 + 69 = 209 GB per step. Four GPUs read 4 × 3.35 = 13.4 TB/s at peak, 9.4 TB/s at 70% MBU, so a step takes 209 ÷ 9,380 ≈ 22 ms. Check compute: the step does 2 × 70 × 109 × 128 = 17.9 TFLOP, and four GPUs at 50% MFU deliver 1,978 TFLOPS, so the arithmetic takes 9 ms, less than the 22 ms of memory reading. The step is bandwidth-bound. Every sequence gets one token per 22 ms, which is 45 tokens/s per stream (meets the 30 tokens/s target), and the replica produces 128 ÷ 0.022 ≈ 5,700 output tokens/s.

Why does batching help so much? At batch 1 the step reads 140.5 GB to make one token; at batch 128 it reads 209 GB to make 128 tokens. Weight reads are shared by the whole batch, so cost per token falls about 85-fold. The limit arrives from two sides. Memory: each sequence adds 0.54 GB, so the batch cannot pass about 270. Compute: decode does about 2 FLOPs per parameter per token while reading 2 bytes per parameter shared across the batch, so its arithmetic intensity is roughly the batch size in FLOPs per byte. An H100's ridge point (peak FLOPs ÷ peak bandwidth) is 989 ÷ 3.35 ≈ 295 FLOPs per byte, so somewhere around a batch of a few hundred decode becomes compute-bound, and beyond that, bigger batches only slow everyone down.

GPUs for the 70B pool: two bounds. Compute: prefill processes 105 × 1,500 = 157,500 tokens/s at 2 × 70 × 109 FLOPs each = 22,050 TFLOP/s. Decode adds 105 × 300 = 31,500 tokens/s × 140 GFLOP = 4,410 TFLOP/s. Total 26,460 TFLOP/s ÷ (989 × 0.5) ≈ 53.5 GPUs. Bandwidth: decode needs 31,500 tokens/s ÷ 5,700 per replica ≈ 5.5 replicas ≈ 22 GPUs. The two kinds of work can overlap on the same GPUs (prefill uses the arithmetic units that decode leaves idle, which is exactly what chunked prefill exploits), so the fleet needs the larger bound, 53.5, not the sum. Add 30% headroom for bursts, failed nodes and rolling deploys: 70 GPUs, rounded up to whole 4-GPU replicas: 18 replicas, 72 GPUs.

The surprise to say out loud: prefill dominates. With a 5:1 input-to-output ratio, the fleet is sized by compute for reading prompts, not by bandwidth for writing answers. That points straight at the highest-value optimisation: prefix caching. If half of each prompt is a system prompt or document that was already processed, prefill compute halves and the compute bound falls from 53.5 to about 29 GPUs.

GPUs for the 8B pool. Prefill: 245 × 1,500 = 367,500 tokens/s × 16 GFLOP = 5,880 TFLOP/s; decode: 73,500 tokens/s × 16 GFLOP = 1,176 TFLOP/s; total 7,056 ÷ 494.5 ≈ 14.3 GPUs by compute. Bandwidth: at batch 128, a step reads 16 + 128 × 0.22 = 44 GB, which at 3.35 × 0.7 = 2.35 TB/s is about 19 ms, so one GPU makes about 6,800 tokens/s and decode needs about 11 GPUs. The larger bound with 30% headroom gives 19 GPUs. Fleet total: 72 + 19 = 91 H100s, about 91 × $3 × 730 hours ≈ $200,000 per month provisioned for peak. Monthly tokens served: 10 million requests × 1,800 tokens × 30 days = 540 billion, so the blended cost is about $0.37 per million tokens before any optimisation. That number is what you compare against buying the same tokens from an API provider.

The TTFT budget. Prefill of a 1,500-token prompt on a 70B replica is 1,500 × 140 GFLOP = 210 TFLOP ÷ 1,978 TFLOPS ≈ 106 ms. A 30,000-token contract takes about 2.1 seconds of prefill on its own, which is why long prompts need special handling. The figure below lays out the full first-token budget.

3 · API

Keep the public API boring and compatible, so tenants can point existing client libraries at it:

POST /v1/chat/completions
  Authorization: Bearer <tenant API key>
  Idempotency-Key: <uuid>              # optional; safe retries before any token is sent
  {model: "big-70b" | "small-8b", adapter?: "acme-support-v3",
   messages: [...], max_tokens: 512, temperature: 0.2,
   stream: true, priority?: "interactive" | "batch"}
  -> 200 text/event-stream: data: {delta: "..."} ... data: {usage: {input, cached, output}}
  -> 429 {error: "tenant_token_rate"}, Retry-After: 3
  -> 400 {error: "context_length_exceeded", limit: 32768}

POST /v1/batches        {input_file_id, model, completion_window: "24h"}  # deferrable tier
GET  /v1/models          # models and adapters this key may use
GET  /v1/usage?from=&to=  # tokens and cost per model, per day

Three details carry weight. max_tokens is required (or defaulted) because the scheduler needs an upper bound on how much KV memory a request might grow to. Streaming uses server-sent events (SSE), an HTTP response that stays open and delivers events as they are produced; the final event carries the usage counts so the client and the bill agree. And 429 responses come with Retry-After, so well-behaved clients back off instead of hammering the gateway.

4 · Data model

The durable state is small. tenants (id, plan, priority weight, per-model token quotas per minute and per day, data-retention setting). api_keys (hash of the key, tenant, scopes, created and revoked times; never store the key itself). models (id, version, weight location, quantisation, tensor-parallel degree, maximum context). adapters (id, owning tenant, base model, rank, storage path, checksum). usage_events: one append-only row per request with tenant, model, adapter, input/cached/output tokens, TTFT, total time and status, written to a log (Kafka, taught in in1) and aggregated hourly into billing tables.

The interesting state is in memory and is deliberately not durable: each replica's KV block tables, its prefix-cache index, the set of adapters currently loaded, and each scheduler's per-tenant queues and fair-share counters. If a replica dies, this state is lost and the in-flight streams fail; the design accepts that, because rebuilding a KV cache costs one prefill and persisting it would cost far more.

5 · High-level design

Walk one request through the architecture figure. The gateway terminates TLS, hashes the API key and looks it up (cached for a minute), estimates the request's input tokens with the model's tokenizer, and takes that many tokens from the tenant's input-token bucket; output tokens are charged against a second bucket as they are generated. If either bucket is empty, it returns 429 immediately. It also enforces limits such as maximum context length and runs the tenant's optional input content filter.

The router maps model and adapter to a pool and chooses a replica. A naive choice is "least loaded", but a smarter one is cache-aware: hash the first few hundred tokens (usually the system prompt) and prefer the replica that served the same prefix recently, so its prefix cache already holds those KV blocks; likewise prefer a replica that already has the requested adapter loaded. It falls back to least-loaded when the preferred replica is busy, because affinity is an optimisation, never a reason to queue.

Each pool has a scheduler, which can be a separate service or the engine's own scheduler extended with tenant awareness. It keeps one queue per tenant per priority class, picks the next request by weighted fair queueing in tokens (section 7), and admits it into the engine only when enough KV blocks are free for its prompt plus a reserve for growth.

The engine on each replica (vLLM is the reference open-source example) runs the loop that matters: every iteration it assembles a batch from all running sequences, adds prefill chunks for newly admitted ones, runs one forward pass across the GPUs of the replica, appends one token to each decoding sequence, streams those tokens out, and frees the KV blocks of sequences that finished. Section 6 explains this loop and its memory manager.

The streamer forwards tokens to the client as SSE and counts them. Metering happens here, at the point tokens leave, so a client that disconnects after 200 tokens is billed for 200, and the engine is told to cancel the sequence immediately so it stops consuming GPU time. The control plane holds the model registry, pre-stages weights on each node's local NVMe disks so a restart does not pull 140 GB from object storage, and runs the autoscaler (section 9).

6 · Deep dive: continuous batching and paged KV memory

Start with the naive engine. Static batching collects, say, 32 requests, runs them together until every one has finished, then takes the next 32. Two things go wrong. A request that wanted 20 tokens finishes early, but its slot sits empty until the longest request (maybe 1,000 tokens) is done, so most of the batch is idle most of the time. And a request that arrives just after the batch started waits for the entire batch, so TTFT includes someone else's whole generation. The Orca paper (OSDI 2022) fixed this with iteration-level scheduling, now called continuous batching: scheduling decisions happen every decode step. When a sequence emits its end token it leaves the batch at once and a waiting request takes its place in the next step. Slots stay full; new requests start within a step or two. Orca reported 36.9× higher throughput than NVIDIA's FasterTransformer at the same latency on a 175B model.

Continuous batching moves the bottleneck to memory. Each admitted sequence needs room for its KV cache to grow, and earlier engines allocated that room as one contiguous slab per request, sized for the maximum length it might reach (prompt plus max_tokens, or the model's whole context window). Three kinds of waste follow. Reservation: space set aside for tokens that will be generated later sits empty now. Internal fragmentation: a request that stops at 40 tokens when it reserved 2,048 never uses the rest. External fragmentation: slabs of different sizes leave gaps between them that no new request fits into. The vLLM paper profiled such systems and found that only 20.4% to 38.2% of KV-cache memory actually held token state. Since the KV cache decides the batch size, and the batch size decides throughput, wasted KV memory is directly wasted money.

PagedAttention borrows the operating system's answer to the same problem, virtual memory. The KV cache is split into blocks of a fixed number of tokens (vLLM's default is 16). A sequence's cache is a list of blocks that can live anywhere in GPU memory; a per-sequence block table maps "logical block 0, 1, 2…" to physical block numbers, the way a page table maps virtual pages to physical frames. A new block is allocated only when the previous one is full, so the only waste is the unfilled tail of each sequence's last block, at most 15 tokens. The attention kernel is rewritten to follow the block table instead of assuming contiguous memory. vLLM measured 96.3% KV utilisation and 2-4× higher throughput than FasterTransformer and Orca at the same latency.

Blocks also make sharing cheap. If two sequences begin with the same tokens, their block tables can point at the same physical blocks, with a reference count, and a block is copied only if one sequence needs to write into it (copy-on-write). That is how a platform reuses one tenant's 2,000-token system prompt across thousands of requests (prefix caching), how parallel sampling (n answers to one prompt) shares the prompt, and how beam search shares common history; the paper measured 37.6-55.2% memory saved by sharing in beam search on one dataset.

What happens when blocks run out mid-generation, because more sequences grew longer than expected? The engine must preempt: pick a sequence (vLLM picks the most recently admitted), free its blocks, and later either copy them back from CPU memory where they were swapped, or recompute them by running prefill again over prompt plus generated tokens. Either way that user's stream stalls. Preemption is the KV-memory equivalent of swapping on a laptop, and a busy pool that preempts often has the same symptom: everything gets slow at once. The scheduler's admission rule (section 7) exists to keep it rare.

7 · Deep dive: multi-tenant scheduling

Fairness needs a unit, and requests are the wrong one. A tenant sending 100 requests per minute of 50 tokens costs 5,000 prefill tokens; a tenant sending 100 requests of 50,000 tokens costs a thousand times more. So every limit is in tokens, at two layers.

At the gateway: token buckets. A token bucket (from sc12) holds up to B units and refills at R units per second; a request takes units from it or is refused. Each tenant gets one bucket for input tokens per minute and one for output tokens per minute, per model. Input tokens are charged on arrival (the gateway tokenises the prompt). Output tokens are unknown in advance, so the gateway charges max_tokens provisionally and refunds the unused part when the stream ends. Buckets live in a shared store (a Redis cluster, from in3) keyed by tenant and model, because the gateway runs as many instances.

In front of the engine: weighted fair queueing. Quotas stop a tenant exceeding its plan, but within quota, a burst from one tenant can still crowd everyone else's queue. The scheduler therefore keeps a queue per tenant and a counter of service received, measured in tokens processed (prefill tokens plus output tokens), divided by the tenant's weight. When a batch slot opens, it admits the head request of the tenant with the lowest weighted service so far. A tenant with weight 2 gets twice the token throughput of one with weight 1 when both are busy; when one is idle, the other can use everything. This is the same idea as deficit round robin in network routers, applied to tokens.

A short worked trace. Tenants A (weight 1), B (weight 1) and C (weight 2) all have queues. Counters start at zero. The scheduler admits A's 1,000-token request (A: 1,000), then B's 200-token request (B: 200), then C's 3,000-token request (C: 3,000 ÷ 2 = 1,500). Next it admits from B (lowest, 200), then B again until B's counter passes A's. A tenant flooding the queue does not gain share; it just lengthens its own queue. A tenant that has been idle re-enters with its counter set to the current minimum, so it cannot hoard credit and then burst.

Admission control. Before admitting a request, check that its prompt's blocks plus a growth reserve fit in free KV memory. Reserving the full max_tokens is safe but wastes memory (the problem paging solved); reserving nothing invites preemption. A good compromise reserves the expected output length for this tenant and model (tracked as a running average) and keeps a small pool-wide reserve for growth. If a request cannot be admitted within its tenant's queueing budget (say 300 ms for interactive), reject it with 429 and a retry hint rather than letting it wait 60 seconds and time out. A fast, honest rejection lets clients retry elsewhere or back off; a slow timeout wastes everyone's time and still fails.

Priority classes. Interactive traffic, batch traffic and internal evaluation jobs get separate classes. Batch requests are admitted only when interactive queues are empty and KV utilisation is below a threshold, and they are first to be preempted. This is how the platform sells off-peak capacity cheaply without hurting the paying interactive tier: the night-time trough fills with batch work and the fleet's average utilisation rises.

8 · Deep dive: long prompts, chunked prefill and disaggregation

Prefill and decode share each forward pass in a continuous-batching engine. Suppose 128 sequences are streaming at 22 ms per step, and a 30,000-token prompt is admitted. If its prefill runs as one piece, that step takes about 2.1 seconds, and all 128 users see their text freeze for two seconds. This is the classic cause of bad p99 inter-token latency.

Chunked prefill splits the long prompt into chunks of, say, 512 tokens and adds one chunk per step to the decode batch. Each step now does 128 decode tokens plus 512 prefill tokens. Recall that decode left most of the arithmetic units idle (9 ms of compute in a 22 ms step); a 512-token chunk costs 512 × 140 GFLOP ÷ 1,978 TFLOPS ≈ 36 ms of compute, so the step grows to roughly 40-45 ms instead of 2,100 ms. Streams slow down modestly for about 59 steps instead of freezing for two seconds, and the long prompt's TTFT rises from 2.1 s to about 2.5 s. The chunk size is the knob: larger chunks finish prefill sooner, smaller chunks protect inter-token latency. Sarathi-Serve (OSDI 2024) formalised this as stall-free batching and reported up to 2.6× more serving capacity under latency targets on Mistral-7B.

Disaggregation goes further: run prefill on one pool of GPUs and decode on another, and move each request's KV cache from the prefill machine to a decode machine when prefill finishes. The phases then stop interfering entirely, and each pool can be sized and even built from different hardware: compute-heavy for prefill, bandwidth- and memory-heavy for decode. DistServe (OSDI 2024) reported serving up to 7.4× more requests within both TTFT and TPOT targets. The cost is the transfer: a 1,500-token prompt on the 70B shape has 1,500 × 320 KiB ≈ 490 MB of KV cache, which takes about 10 ms over a 400 Gbit/s network link and much longer over ordinary datacentre Ethernet. Disaggregation also adds a second scheduler and a new failure mode (transfer stalls). Start with chunked prefill; reach for disaggregation when long prompts and strict per-token targets coexist at a scale where the separate pools are each large enough to run efficiently.

9 · Deep dive: many adapters, autoscaling and cold starts

Multi-LoRA serving. If 500 tenants each fine-tune the 8B model with LoRA, deploying 500 copies would need 500 GPUs mostly idle. Instead, serve one base model per replica and apply each request's adapter on the fly. A LoRA adapter of rank 16 on an 8B model is tens of megabytes, so hundreds fit in CPU memory and dozens on the GPU. Requests for different adapters can share one batch: the base model's matrix multiply runs once for the whole batch, and a small extra kernel applies each sequence's own low-rank update. S-LoRA showed serving thousands of adapters with up to 4× the throughput of naive approaches by paging adapter weights in the same unified memory pool as the KV cache. The router helps by preferring replicas that already hold the adapter, so loads from CPU memory stay rare.

Autoscaling signals. GPU utilisation is a useless signal for an inference engine: it reads near 100% whenever a kernel is running, whether the batch holds two sequences or two hundred. Scale on what tracks user pain and capacity: queue wait time, TTFT p95 and KV-cache utilisation. A sensible rule: add replicas when queue wait exceeds 200 ms or KV utilisation stays above 80% for two minutes; remove them when KV utilisation stays below 40% for twenty minutes.

Cold starts. A new 70B replica must get four GPUs scheduled, pull a container image of several gigabytes, load 140 GB of weights and warm up (compile CUDA graphs, run a test generation). From object storage at about 1-2 GB/s per node, loading alone is 70-140 seconds; from local NVMe it is much faster, which is why the control plane pre-stages weights on every eligible node. Even optimised, scale-out takes a minute or more, while traffic spikes arrive in seconds. So autoscaling recovers cost over hours; it does not defend latency over seconds. The latency defences are headroom (the 30% in the estimate), admission control, priority shedding (batch first) and a fallback route that sends overflow from the 70B pool to the 8B pool for tenants who allowed it.

10 · Evaluation plan

Performance. Record a day of production request shapes (prompt length, output length, tenant, arrival time; not content) and replay them against a staging pool at increasing request rates. For each rate, measure TTFT and TPOT distributions and goodput: the requests per second that meet both targets. Plot goodput against offered load; the knee of that curve is the replica's real capacity, and it is the number the capacity plan uses, not the vendor's peak tokens per second. Re-run this benchmark for every engine upgrade, quantisation change or scheduler change, because each one moves the knee.

Quality. Serving changes can change outputs: FP8 weights, a quantised KV cache, a new attention kernel or a tokenizer bug in the gateway. Gate every change on an evaluation suite run through the full serving path (not offline with a different stack): task accuracy on a fixed benchmark set, exact-match of greedy outputs on a regression set, and a handful of long-context retrieval checks, because KV-cache quantisation errors show up first at long contexts. The requirement says within 1 point; enforce it in the deployment pipeline (ae7 covers CI evaluation).

Fairness and isolation. Load-test with an adversarial mix: one tenant floods long prompts while others send normal traffic, and assert that the others' TTFT p95 stays within target. Test the prefix-cache side channel by measuring whether one tenant can detect another's cached prefix by timing; with tenant-scoped cache keys it must not.

11 · Failure modes and trade-offs

A GPU or node failure kills every stream on that replica. Clients receive an error event; the gateway retries automatically only if no token was sent yet (otherwise the client would get duplicated text), and the router marks the replica unhealthy. A wedged engine (stuck CUDA context, deadlocked scheduler) can still answer HTTP, so the readiness probe must run a real one-token generation with a timeout. A KV-memory storm, many long generations at once, causes preemption cascades; the symptoms are rising preemption counts and p99 inter-token latency while averages look fine. A bad deploy (new engine version, new quantisation) goes out as a canary to a few percent of replicas, with automatic rollback on error rate, latency or evaluation regressions.

The trade-offs to volunteer: batch size trades throughput against per-stream speed, so expose it as tiers rather than one setting. Quantisation trades memory and cost against a small, measured quality change. Prefix sharing across tenants trades cost against isolation. Headroom trades money against tail latency. And self-hosting at all is a trade: at $0.37 per million tokens with good utilisation it beats most API prices, but at 20% average utilisation the same fleet costs nearly twice as much per token, so self-hosting pays only with sustained load or requirements (data residency, custom models) an API cannot meet.

Why the ridge point decides your batch size

A GPU has a peak arithmetic rate and a peak memory rate; their ratio is the ridge point (for an H100, 989 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOPs per byte, from gpu2). A decode step for batch B reads every weight once (2 bytes each in BF16) and does 2 FLOPs per weight per sequence, so its intensity is about B FLOPs per byte, ignoring KV reads. Below B ≈ 295 decode is memory-bound and adding sequences is nearly free; above it, compute-bound and each added sequence slows the step proportionally. KV reads lower the effective intensity because they are not shared across the batch: each sequence's cache is read only for that sequence. With long contexts, KV traffic can exceed weight traffic, and then batching stops helping much earlier. This is why long-context workloads gain so much from KV quantisation and from grouped-query attention: they shrink exactly the bytes that batching cannot amortise.

Tensor parallelism is not free

Splitting the 70B model over 4 GPUs gives 4× the memory bandwidth per step, which is why the decode step is fast. But every layer ends with an all-reduce (from gpu8) in which the four GPUs exchange partial results; with 80 layers that is 160 small collective operations per decode step. Over NVLink inside one server these cost microseconds each, adding a few milliseconds per step; across servers over InfiniBand they would cost far more. That is why tensor parallelism stays inside a server (up to 8 GPUs) and models too big for one server add pipeline parallelism (different layers on different servers) instead. Choosing TP=4 rather than TP=8 for a 70B BF16 model is a deliberate trade: TP=8 doubles bandwidth per replica and halves per-token latency but doubles the all-reduce overhead share and halves the number of replicas, so you choose by the per-stream speed target.

FP8 changes the plan, not just the cost

Serving the 70B model in FP8 (1 byte per weight) halves weights to 70 GB. It could then run on 2 GPUs with about 74 GB of KV space (2 × 72 GB usable − 70), or on 4 GPUs with 218 GB of KV space. On H100 the FP8 tensor cores also double peak compute, which matters because this workload is compute-bound by prefill. The fleet might fall from 72 to under 40 GPUs. The cost is a quality change that is usually small for weights quantised carefully with calibration (lm12), but must be measured on your suite, especially on long-context and reasoning tasks. KV-cache quantisation to FP8 is a separate decision with a separate risk: errors accumulate across thousands of cached positions.

Speculative decoding is a per-tier decision

A small draft model (or extra prediction heads on the big model) proposes k tokens; the big model scores all k in one forward pass, accepts the longest prefix consistent with its own distribution via a rejection-sampling rule, and adds one token of its own. Leviathan et al. proved the output distribution is unchanged and measured 2-3× latency improvement on T5-XXL. The extra cost is the draft model plus verifying tokens that get rejected. At small batch sizes the GPU is idle on compute, so this cost is hidden and latency improves. At large batch sizes the engine is near the compute bound, rejected drafts are pure waste, and total throughput can fall. Acceptance rates are high for predictable text (code, structured output, low temperature) and low for creative sampling. So enable it for the low-latency interactive tier, and measure goodput with it on and off for each model and traffic class.

Prefix caching as a scheduling problem

A prefix cache only helps if requests sharing a prefix land on the replica that holds it. Random load balancing across 18 replicas gives each prefix about a 1-in-18 chance of a hit. Cache-aware routing hashes the prefix to a preferred replica (consistent hashing, from in2, so adding replicas moves few prefixes) and overrides the preference when that replica's queue is long. The cache itself is evicted by least-recently-used blocks, but blocks referenced by running sequences cannot be evicted. A useful senior observation: a prefix cache turns system-prompt design into a cost lever. Putting the stable part of the prompt first and the variable part (user message, retrieved documents) last maximises shared prefix length. Providers price cached input tokens at a fraction of uncached ones for the same reason.

Fair queueing interacts with batching

Pure weighted fair queueing assumes the server processes one job at a time; an LLM engine processes hundreds at once, and admitting a request commits memory for its whole lifetime. So the fair-share counter should charge a request its expected token cost at admission and correct it at completion, otherwise a tenant whose requests generate long answers is under-charged while they run. Another subtlety: fairness in tokens is not fairness in latency. A tenant with tiny prompts can be treated fairly in tokens and still suffer high TTFT if the batch is full of long prompts from others. That is why chunked prefill and per-class queueing budgets sit alongside fair queueing rather than being replaced by it.

Choosing between preemption by swap and by recompute

When KV memory runs out, a victim sequence's blocks are either copied to CPU memory over PCIe and copied back later (swap), or discarded and rebuilt by re-running prefill over its tokens (recompute). Swap costs PCIe bandwidth proportional to the cache size; recompute costs GPU compute proportional to the token count. The vLLM paper found recompute cheaper with small blocks (many small PCIe transfers are inefficient) and the two comparable at block sizes 16-64. For a compute-bound fleet like the one sized above, recompute steals scarce FLOPs from prefill, so swap may be the better default; this is the kind of decision you justify from your own bound rather than reciting a default.

What it looks like when it goes wrong

The long-prompt freeze. Symptom: p99 inter-token latency spikes to seconds while p50 is unchanged, correlated with the arrival of large prompts from one or two tenants. Cause: prefill without chunking, or a chunk size set too large. Fix: enable chunked prefill, cap per-tenant concurrent prefill tokens, and route very long prompts to a dedicated long-context pool with its own targets.

Preemption cascades. Symptom: throughput drops while GPU utilisation stays high, preemption counters climb, and latency rises for everyone at once. Cause: the scheduler admitted more sequences than the KV cache can hold when they grow, typically after a traffic mix change toward longer answers. Fix: tighten the growth reserve, lower the maximum number of running sequences, and alert on preemptions per minute rather than waiting for latency alarms.

Silent quality regressions. An engine upgrade changed a default (sampling, tokenizer handling of special tokens, KV-cache data type) and outputs subtly degraded; nobody noticed for a week because latency and error dashboards were green. Fix: run the evaluation suite through the production serving path on every deploy, and keep a small continuous canary that sends fixed prompts and checks outputs.

Thundering herd after an outage. A replica pool recovers and every client's retry lands at once, refilling the queue and causing a second outage. Fix: jittered exponential backoff in the client libraries you ship, Retry-After headers, and admission control that rejects quickly rather than queueing.

Metrics and dashboards

Per model and per tenant: TTFT and TPOT at p50, p95 and p99; queue wait time; admitted, rejected (429) and cancelled requests; tokens per second in, cached and out. Per replica: running and waiting sequences, KV-cache utilisation, preemptions, prefix-cache hit rate, adapter loads, batch size distribution, and decode step time. vLLM exposes most of these as Prometheus metrics (in6 covers the monitoring system). The capacity dashboard combines KV utilisation and queue wait, because those two predict an SLO breach minutes before TTFT does.

Knobs people tune

Maximum running sequences per replica (caps batch size), maximum tokens per step (caps how much prefill is mixed in, which is the chunk size), KV block size (vLLM defaults to 16; larger blocks waste more and share less), the fraction of GPU memory given to the engine, tensor-parallel degree, and the scheduler's per-class queueing budgets. Each changes the throughput-latency curve, so tune with the replayed-trace benchmark, never by eye.

The real case: vLLM and PagedAttention

Kwon and colleagues at UC Berkeley built vLLM after measuring how existing engines used GPU memory. Their profile of a 13-billion-parameter model on a 40 GB A100 showed about 65% of memory going to weights (26 GB) and about 30% to the KV cache. For OPT-13B they computed the cache at 800 KB per token (2 × 5,120 hidden size × 40 layers × 2 bytes), so a single 2,048-token request could need 1.6 GB, and "only a few tens of requests" fit at all. Worse, the systems they compared against used only 20.4-38.2% of the KV memory for actual token state; the rest was reserved, fragmented or padded. PagedAttention, block-level allocation with a per-sequence block table and copy-on-write sharing, raised utilisation to 96.3%. The SOSP 2023 paper reports 2-4× higher throughput than FasterTransformer and Orca at the same latency, more gain for longer sequences and larger models, and a default block size of 16 tokens chosen because smaller blocks underuse the GPU and larger ones fragment. The lesson for an interview: the throughput win came from memory management, not from faster maths, which is the same conclusion the capacity estimate reached by hand.

Goal: reproduce this lesson's capacity estimate in code and see which bound, compute or memory bandwidth, sizes each pool. The script models a replica's decode step as max(bytes read ÷ effective bandwidth, FLOPs ÷ effective compute), finds the largest batch that fits in KV memory and still gives each stream 30 tokens/s, and then sizes the fleet for a given request rate. """GPU capacity planner for an LLM serving pool. Python 3.12, stdlib only.
Estimates weights and KV memory, decode step time, the largest batch that
meets a per-stream speed target, and how many GPUs a token load needs."""
from dataclasses import dataclass

GB = 1e9

@dataclass
class Model:
    name: str
    params: float          # parameters
    layers: int
    kv_heads: int
    head_dim: int
    w_bytes: float = 2     # bytes per weight (2 = BF16, 1 = FP8)
    kv_bytes: float = 2    # bytes per cached K or V value

    def kv_per_token(self):  # K and V, every layer, every KV head
        return 2 * self.layers * self.kv_heads * self.head_dim * self.kv_bytes

@dataclass
class GPU:
    name: str
    mem: float = 80 * GB
    bw: float = 3.35e12      # HBM bytes/s (H100 SXM)
    flops: float = 989e12    # dense BF16 FLOP/s
    usd_hour: float = 3.0    # assumption: on-demand price per GPU-hour

def plan(m, g, tp, prompt, output, rps, min_tok_s=30, mbu=0.7, mfu=0.5, overhead=0.10):
    weights = m.params * m.w_bytes
    kv_space = tp * g.mem * (1 - overhead) - weights
    ctx = prompt + output / 2                     # average context while decoding
    kv_seq = ctx * m.kv_per_token()
    bw, fl = tp * g.bw, tp * g.flops
    best = None
    for batch in range(1, 1025):
        if batch * kv_seq > kv_space:
            break                                  # out of KV memory
        read = weights + batch * kv_seq            # bytes read per decode step
        step = max(read / (bw * mbu), 2 * m.params * batch / (fl * mfu))
        if 1 / step < min_tok_s:
            break                                  # streams would be too slow
        best = (batch, step)
    batch, step = best
    decode_tok_s = rps * output
    prefill_flop = rps * prompt * 2 * m.params
    decode_flop = decode_tok_s * 2 * m.params
    gpus_compute = (prefill_flop + decode_flop) / (g.flops * mfu)
    gpus_bw = decode_tok_s / (batch / step) * tp
    need = max(gpus_compute, gpus_bw) * 1.3        # 30% headroom
    replicas = -(-need // tp)
    print(f"--- {m.name} on {tp}x {g.name}")
    print(f"weights {weights/GB:.0f} GB | KV {m.kv_per_token()/1024:.0f} KiB/token,"
          f" {kv_seq/GB:.2f} GB per sequence | KV space {kv_space/GB:.0f} GB")
    print(f"max batch at >= {min_tok_s} tok/s/stream: {batch}, step {step*1e3:.1f} ms,"
          f" {batch/step:,.0f} tok/s per replica")
    print(f"load: {rps*prompt:,.0f} prefill tok/s + {decode_tok_s:,.0f} decode tok/s")
    print(f"GPUs by compute {gpus_compute:.1f}, by bandwidth {gpus_bw:.1f}"
          f" -> {int(replicas)} replicas = {int(replicas*tp)} GPUs with headroom")
    ttft = prompt * 2 * m.params / (fl * mfu)
    print(f"prefill of one {prompt}-token prompt ~ {ttft*1e3:.0f} ms;"
          f" cost ${replicas*tp*g.usd_hour*730:,.0f}/month")
    return int(replicas * tp)

h100 = GPU("H100")
big = Model("70B (Llama-3-70B shape)", 70e9, 80, 8, 128)
small = Model("8B (Llama-3-8B shape)", 8e9, 32, 8, 128)
total = plan(big, h100, tp=4, prompt=1500, output=300, rps=105)
total += plan(small, h100, tp=1, prompt=1500, output=300, rps=245)
print(f"=== fleet: {total} GPUs")
# Experiments: set prompt=750 (50% prefix-cache hits), w_bytes=1 (FP8 weights),
# or min_tok_s=60, and watch which bound -- compute or bandwidth -- moves.

What to look for. The maximum batch is limited by the speed target, not memory, at these context lengths, and decode needs far fewer GPUs than prefill. That is the whole argument for prefix caching and chunked prefill in one printout. If you raise prompt to 8,000, memory becomes the limit: KV per sequence grows to about 2.6 GB and the batch collapses.

Work it out

You are serving Llama-3-8B in BF16 on a single A100-80GB. The model has 32 layers, 8 key-value heads, and a head dimension of 128 (it uses grouped-query attention).

Compute (a) the memory the weights take, (b) the KV cache cost per token, and (c) roughly how many concurrent 8,000-token conversations fit. Then say what you would change first if the answer is too low.

Answer

(a) Weights. 8 billion parameters × 2 bytes = 16 GB. That leaves about 64 GB, minus a few GB for activations and framework overhead — call it 60 GB usable for KV cache.

(b) KV cache per token. The formula is 2 × layers × kv_heads × head_dim × bytes. The leading 2 is for K and V separately. So 2 × 32 × 8 × 128 × 2 = 131,072 bytes = 128 KiB per token.

(c) Concurrency. 8,000 tokens × 128 KiB ≈ 1 GB per conversation. 60 GB ÷ 1 GB ≈ 60 concurrent conversations per GPU, assuming paged allocation; with contiguous reservation for a 32k maximum context, only about 14 would fit.

What to change. In order of impact per unit of effort: quantise the KV cache to 8 bits (halves it to 64 KiB/token, doubling concurrency, after checking long-context quality); enable prefix caching if tenants share a system prompt; quantise the weights to 4 bits to free another 12 GB; only then add GPUs.

The thing worth noticing: grouped-query attention is already doing enormous work here. With full multi-head attention this model would have 32 KV heads instead of 8, so the cache would be 512 KiB per token — 4 GB per conversation and only 15 concurrent users. GQA is a 4× change in the economics of serving.

Diagnose it

The 70B pool meets its TTFT target all morning. At 14:00 a tenant starts a nightly-style job through the interactive API: 2,000 requests per minute of 20,000-token documents, each asking for a 100-token summary. Within five minutes other tenants' p99 inter-token latency goes from 40 ms to 1.8 s and p95 TTFT from 0.6 s to 7 s. GPU utilisation shows 100% throughout. Explain what is happening and what you change, in order.

Answer

What is happening. The new load is almost pure prefill: 2,000 ÷ 60 ≈ 33 requests/s × 20,000 tokens = 667,000 prompt tokens/s × 140 GFLOP ≈ 93 PFLOP/s, about 190 H100s at 50% MFU, more than double the whole pool. Every step that includes one of these prefills (without chunking) takes seconds, freezing every stream on that replica: that is the 1.8 s inter-token latency. The queue fills behind them: that is the 7 s TTFT. GPU utilisation says 100% because it was 100% before too; it carries no information here.

What to change, in order. (1) Immediately, the tenant's input-token bucket should have stopped this: 667,000 tokens/s is far above any interactive plan. If it did not, the quota is set in requests, not tokens; fix that. (2) Move this kind of job to the batch tier (24-hour window, admitted only into spare capacity, preempted first). (3) Turn on chunked prefill so a single long prompt can never freeze a replica, and cap concurrent prefill tokens per tenant. (4) Only then consider capacity: if long-document summarisation is a real product, it deserves a separate pool, possibly an FP8 or smaller model, sized from its own token rate.
