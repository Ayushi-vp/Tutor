A company has shipped LLM features quickly. There is a customer-support assistant built on retrieval, a coding helper inside the developer tools, a contract summariser for the legal team, three agents that file tickets and update records, and about 140 smaller features that rewrite, classify, extract and draft. Thirty teams built them, and each built its own way of knowing whether they work: one has a spreadsheet of 50 test prompts, one prints prompts and responses to application logs, one asks a model to grade outputs with a prompt nobody has checked against humans, and several have nothing at all.

Then the things that always happen, happen. The model provider ships a new version and the support assistant starts refusing refund questions; nobody notices for nine days because the only signal is a slowly rising escalation rate. A prompt change that "obviously improves tone" breaks the JSON format for one of the agents, and it writes malformed tickets for an afternoon. The legal team asks which contracts' text went to which model and where those prompts are stored, and nobody can answer, because prompts are in application logs in four systems with four retention policies. Finance asks why the LLM bill doubled; the answer is a retry loop in one agent, visible only after someone reads raw logs for a day.

Each of these is an observability or evaluation failure, and each team fixing it alone means thirty partial fixes. The senior design question is: build the shared platform. Every LLM call in the company is traced in a standard format; quality is measured before release (offline evals against golden sets, gated in CI) and after release (online monitoring of sampled production traffic, judged by validated LLM judges and humans); regressions raise alerts that link to example traces; cost is attributed to features and releases; and personal data is handled deliberately. The Evals track (ev1 to ev12) teaches the methods. This case is about the system that runs them for everyone: its data model, its numbers, its components, its failure modes and its trade-offs.

The lesson follows the interview: requirements including quality, latency, cost and privacy targets; estimates by hand for trace volume, storage, judging cost and eval cost per release; the API and data model, built on the OpenTelemetry GenAI conventions; the architecture; deep dives on the trace data model for LLM and agent calls, golden sets versus production sampling, the judge service and its agreement with humans, regression gates, and drift alerts; then PII, failure modes, Zheng et al.'s measurements of LLM judges as the real case, and a lab that builds a tiny eval harness with Cohen's kappa and a regression gate.

The problem in one sentence

Give every team a cheap, standard way to see what each LLM request did (which models, tools and documents, how long, how many tokens, at what cost), to measure whether outputs are good, before release and continuously after it, and to be told quickly and specifically when something gets worse, without turning the platform into an uncontrolled copy of every user's data.

The mental model: a hospital's records, lab and alarms

Think of a hospital. Every patient visit produces a structured chart, with each test and treatment recorded in a standard format with its time and result, not a free-text diary: those are the traces. The hospital's laboratory runs standard tests on samples, with calibrated instruments that are themselves checked against reference samples: those are the evaluators, including LLM judges that must be calibrated against human graders. Before a new treatment protocol is adopted it goes through a trial against the current one on comparable patients: the offline eval and regression gate. Monitors on the ward raise alarms when vital signs cross thresholds chosen so that nurses are not woken by noise: online monitoring and alerts. And medical records are confidential, access is logged, and retention is regulated: PII handling.

The analogy breaks in one useful place. A blood test's chemistry does not change from month to month; an LLM judge is itself a model that can be swapped or updated by its provider, so the instruments drift as well as the patients. The platform must measure its own measuring devices continuously.

Three kinds of evaluator, two places to run them

An evaluator is anything that produces a verdict on an output. Deterministic checks are code: is the JSON valid, does the answer cite a retrieved document, is it under the length limit, did the agent call the confirmation tool before the refund tool. They are cheap, exact and should be used wherever a property can be checked mechanically. Model-graded evaluators (LLM judges) apply a rubric to open-ended qualities such as groundedness, helpfulness or tone; they scale but must be validated. Human reviewers are the most expensive and the ground truth against which the others are calibrated. Each evaluator can run in two places: offline, on a fixed dataset before a release, where the question is "is the new version at least as good as the old?", and online, on sampled production traffic after release, where the question is "is the live system still good on what users ask today?". A platform's leverage comes from using the same versioned evaluators in both places, so an offline gate and an online alert speak the same language.

A reader who stops here has the shape: a standard trace format with privacy controls at the entry point, separate storage for cheap metadata and sensitive content, shared and versioned evaluators used both offline and online, gates that decide releases, monitors that watch production, and a loop that turns failures into tests.

1 · Requirements

Functional. An SDK and auto-instrumentation that trace every model, retrieval, tool and agent step in the OpenTelemetry GenAI format; ingestion, storage, search and a trace viewer; cost attribution per feature, team and release; datasets (golden sets, regression sets, production samples) with versions and labels; an evaluator registry (deterministic checks, LLM judges with rubrics, human review forms); an offline eval runner callable from CI; regression gates; online evaluators over sampled production traffic; metrics, dashboards and alerts per feature and release; human review queues; and privacy controls. Out of scope, said aloud: serving the models (hd1), the agents themselves (hd7) and model training.

Quality targets for the platform itself. Judges used for gating validated against human labels per criterion with kappa at least 0.6 and re-validated on any judge change; a daily canary set re-judged with alerts on movement; eval results reproducible from their recorded versions.

Latency and freshness targets. The SDK adds under 1 ms to a request (export is asynchronous and batched); spans searchable within 60 seconds at p95; online judge verdicts within 15 minutes; alert evaluation every 5 minutes; a trace fetched by ID in under 1 second, attribute search over a day in under 5 seconds.

Cost targets. Platform cost a small fraction of the LLM bill it observes; evaluation spend budgeted per feature and visible to its team.

Privacy and safety targets. No message content stored unless the feature opted in with a data classification; PII redacted before storage, with measured recall; user identifiers pseudonymised; content retention 30 days by default; access to content logged and limited to the owning team and approved reviewers; erasure requests completed across traces and derived datasets within the legally required time.

Clarifying questions. "How many features and requests per day, and how many are agents?" "Are prompts and outputs allowed to leave the product's region or account?" "Do teams use one model provider or several, and do we already run OpenTelemetry?" "Who reviews outputs today, and at what cost?"

2 · Back-of-envelope estimates

Traffic. 150 features handle 20 million user requests a day in total, about 230 a second on average and about 700 at peak. Chat-style features produce 3 or 4 spans per request (root, retrieval, model call, guardrail); agents produce 10 to 30 (several model calls and tool calls per run). The average is about 6 spans per request: 120 million spans a day, about 1,400 a second on average and 4,000 at peak. This is modest next to classic distributed tracing (in12 sized 2 million spans a second); what is unusual is the size of the content.

Metadata. Span metadata (names, IDs, timings, model, token counts, finish reasons, tool names, feature and release IDs, status) is about 1 KB per span: 120 GB a day, about 30 GB compressed in a columnar store. Kept 13 months for trends: about 12 TB. This is cheap enough to keep every span; sampling metadata would lose rare errors and make cost attribution wrong.

Content. Prompts are large. A support request with retrieved passages might send 3,000 input tokens (about 12 KB of text) and receive 400 output tokens (1.6 KB), and does this three times: about 40 KB of content per request, 800 GB a day. Much of it repeats: system prompts and tool definitions are identical across requests, so storing them once by hash and referencing them roughly halves the volume. After compression, about 100 GB a day to object storage. With 30-day retention for all content and 90 days for a 10% sample, about 3.6 TB held. Content is where both cost and privacy risk live, which is why it is separated from metadata from the first hop.

Online judging. Judging 1% of requests at random is 200,000 judge calls a day. With about 4,000 input tokens (the request, the output and the rubric) and 150 output tokens per call, that is 800 million input and 30 million output tokens a day. At an assumed price for a small judge model of $0.50 per million input tokens and $2 per million output, about $460 a day, $14,000 a month; at an assumed price six times higher for a strong judge, about $83,000 a month. The design choice follows: a cheaper judge validated per criterion for the broad sample, a stronger judge (or humans) for targeted and disputed cases, and sample sizes set per feature by the precision each needs, not a flat 1%.

Offline eval cost per release. A feature's full suite: 2,000 golden items, 3 samples each to average out sampling temperature (ev7), and 3 rubric criteria judged per output. System calls: 6,000 × 4,000 input tokens = 24 million input and 6,000 × 500 = 3 million output tokens. Judge calls: 18,000 × 3,000 = 54 million input and 18,000 × 200 = 3.6 million output tokens. At an assumed $3 per million input and $15 per million output tokens: $72 + $45 + $162 + $54 ≈ $330 per run. If 150 features each ran it twice a week, that is $100,000 a week, more than $5 million a year, before pairwise comparisons in both orders. Hence tiering (recorded smoke tests on every pull request cost nothing in model calls), judge-verdict caching (unchanged outputs are not re-judged; if 70% of outputs are identical between releases, judge cost falls by 70%) and running full suites only on release candidates.

Human review. Validating judges needs about 200-400 human labels per criterion per quarter. At 150 features × 2 gated criteria × 300 labels = 90,000 labels a quarter, and an assumed $1.50 per label for trained reviewers, about $135,000 a quarter, plus targeted review queues. Human labels are the most expensive and the most valuable data the platform holds.

The insight to say out loud. Tracing volume is easy; content size, judge tokens and human labels are the real costs, and each is controlled by sampling and caching decisions the platform makes on teams' behalf.

5 · Data model

Spans (columnar store, partitioned by day and feature): trace ID, span ID, parent ID, name, kind, start, duration, status, error type, and GenAI attributes: gen_ai.operation.name (chat, embeddings, retrieval, execute_tool, invoke_agent and others), gen_ai.provider.name, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, gen_ai.usage.cache_read.input_tokens, gen_ai.response.finish_reasons, gen_ai.conversation.id, gen_ai.tool.name, gen_ai.tool.call.id; plus platform attributes: feature, team, release ID, user pseudonym, computed cost. Content (object storage): per span, references to redacted input and output messages, with shared blobs (system prompts, tool definitions) stored once by hash. Evaluations: as in the API, plus the judge model and prompt version. Datasets: name, version, items (input, expected behaviour or reference, slice tags, provenance such as "from trace X, reviewed by Y"), label history. Evaluators: name, type, rubric, judge model, version, validation results (agreement, kappa, sensitivity, specificity by slice, date). Runs: release, dataset version, evaluator versions, per-item outputs and verdicts, gate result. Releases: the manifest of model, prompt, tool, index and guardrail versions.

The attribute that makes everything else work is the release ID on every root span: it is how production metrics are grouped by release, how a regression is tied to a change, and how offline and online results for the same release are compared.

6 · High-level design

Ingestion. Features use the SDK (thin wrappers over OpenTelemetry instrumentation for the model clients and agent frameworks the company uses), which exports spans asynchronously over OTLP to a local collector. The collector runs the redaction processors (PII detection on opt-in content, attribute allow-lists, pseudonymisation of user IDs), splits content from metadata, computes cost from token counts and a versioned price table, and writes both to Kafka. Consumers write metadata to the columnar trace store and content to object storage. A metrics pipeline derives per-feature, per-release time series (request counts, errors, finish-reason rates, tokens, cost, latency) for the metrics system (in6).

Online evaluation. A sampler reads completed traces and selects them: a stratified random sample per feature and slice for measurement, and a targeted stream (negative feedback, retries, errors, low-confidence verdicts, new embedding clusters, unusually long or expensive traces) for discovery. Selected traces go to the evaluator workers: deterministic checks (format validity, citation presence), then LLM judges via the shared judge service, which owns judge prompts, model versions, rate limits, retries and a verdict cache. Results go to the evaluations store and the metrics system; alert rules run on them. A review queue routes targeted and disputed traces to human reviewers, whose verdicts are stored as evaluations too.

Offline evaluation. The dataset service stores versioned golden and regression sets, including items promoted from production after review (with redaction and consent rules). The eval runner, invoked from CI, executes a release candidate on a dataset (or replays recorded responses for smoke suites), calls the judge service, compares with the baseline and applies the gate. Results are stored per item so that a failing gate links straight to the items that flipped.

7 · Deep dive: the trace data model for LLM and agent calls

A trace is a tree of spans sharing a trace ID; each span records one operation with its parent, timing, attributes and status (in12). The OpenTelemetry GenAI conventions, maintained in their own repository and still marked Development when checked on 8 October 2026, name the operations and attributes for LLM work. An inference span is named {gen_ai.operation.name} {gen_ai.request.model}, for example chat model-x, with span kind CLIENT; agent spans are named invoke_agent {gen_ai.agent.name}; tool spans execute_tool {gen_ai.tool.name}; retrieval spans retrieval {gen_ai.data_source.id}. Message content attributes (gen_ai.input.messages, gen_ai.output.messages, gen_ai.system_instructions, gen_ai.tool.definitions) are Opt-In, and the conventions say instrumentations should not capture such content by default; they also describe uploading content to external storage and recording a reference, which is exactly the metadata/content split this design uses.

Design decisions in the model. Cost is computed at ingestion from token counts and a versioned price table, never by the SDK, so price changes do not require redeploying 150 services and historical cost can be recomputed. Retries are recorded as attributes or child spans of the logical operation, because the conventions say a span should cover the logical operation including automatic retries, and dashboards must count both the operation and its retries. Streaming responses record time to first token as well as total duration. Conversation ID links multi-turn sessions so that evaluations of "the conversation" have something to attach to. And platform attributes (feature, team, release) are added by the SDK from configuration, not by developers by hand, or they will be missing exactly when needed.

Cardinality. Span attributes can be high-cardinality (trace IDs, user pseudonyms, tool call IDs) because spans are stored as rows; metric labels cannot (in6). The metrics derived from spans use only low-cardinality labels: feature, release, model, operation, finish reason, error type. Per-user questions are answered by querying the trace store, not the metrics system.

8 · Deep dive: golden sets versus production sampling

The platform holds three kinds of evaluation data, each answering a different question. A golden set is curated and labelled, sampled from real traffic and stratified by slice (ev2), versioned, and frozen for comparisons: release N and release N+1 are judged on exactly the same items, so differences come from the release. It answers "did known behaviour regress?". A regression set collects specific past failures, each promoted from a production trace after review, with must-pass status for the severe ones. A production sample is drawn continuously from current traffic and answers "how good is the system on what users ask now?", including kinds of requests the golden set has never seen.

Production sampling has two jobs that must not be confused. Measurement needs a random sample, stratified by feature and slice so small slices get enough items, with each item's sampling weight recorded so estimates can be reweighted to traffic. Discovery needs a targeted sample that over-selects risky traces: thumbs down, regenerations, escalations, errors and retries, low-confidence or disagreeing judge verdicts, inputs far from any training or golden cluster in embedding space, unusually long agent runs. Targeted samples find failures many times faster than random ones, but their pass rates say nothing about overall quality, so the two streams are labelled with their sampler and never averaged together.

The loop between them is the platform's main source of improvement: reviewers look at targeted samples, confirmed failures are written up as golden or regression items with expected behaviour, the next release is gated on them, and the production sampler confirms the fix. Promotion from production to a dataset is also where privacy bites: items must be redacted (or synthesised to preserve the failure without the personal data), their provenance recorded, and they must be reachable by erasure requests.

9 · Deep dive: the judge service and its agreement with humans

An LLM judge is an instrument, and the judge service treats it like one: each judge is a versioned bundle of model, prompt, rubric and parser, with a validation record. Validation means labelling a few hundred items per criterion with trained humans, running the judge on the same items, and computing agreement statistics per slice (ev4, ev5). Raw agreement is (268 + 84) / 400 = 0.88. But two raters who pass 75% and 71% of items would agree by chance on 0.75 × 0.71 + 0.25 × 0.29 = 0.605 of them, so Cohen's kappa = (0.88 − 0.605) / (1 − 0.605) = 0.70, conventionally "substantial" agreement. The judge's sensitivity (share of human passes it passes) is 268 / 284 = 0.94; its specificity (share of human fails it fails) is 84 / 116 = 0.72. The judge is lenient: it misses 28% of the answers humans consider ungrounded. Two consequences follow. As an estimator of the pass rate it can be corrected: true rate ≈ (observed + specificity − 1) / (sensitivity + specificity − 1) = (0.75 + 0.724 − 1) / (0.944 + 0.724 − 1) ≈ 0.71, matching the humans. As a detector of individual failures it is weak, so it should not be the only evaluator on a must-pass safety criterion.

The ceiling is human agreement with humans: if two trained reviewers agree only 80% of the time on a criterion, no judge can be expected to agree 95% with either. Zheng et al. measured exactly this: on MT-bench, GPT-4 as a pairwise judge agreed with expert humans 85% of the time when ties were excluded, against 81% between humans; with ties included, 66% against 63%. A judge "as good as a human" is a judge as inconsistent as humans are, which is why criteria are made narrow and binary where possible.

Bias controls built into the service. Pairwise comparisons always run in both orders, and inconsistent verdicts count as ties (Zheng et al. found GPT-4 consistent under swapping only 65% of the time). Length is recorded alongside verdicts so verbosity bias can be checked. The judge model comes from a different family than the system under test where possible, to limit self-preference. Reference answers are supplied for questions the judge could not answer itself. A canary set of a few hundred fixed outputs is re-judged daily; if its scores move, the judge changed (a provider update, a prompt edit), and dashboards annotate the change instead of reporting a product regression.

Caching and cost. Verdicts are cached by a key of (input hash, output hash, rubric version, judge version). Between two releases most outputs on a golden set are often identical (deterministic decoding or unchanged prompts for most slices), and none of those need re-judging. The cache also makes re-runs reproducible: the same key returns the same verdict, removing judge sampling noise from comparisons of unchanged items.

10 · Deep dive: regression gates and drift alerts

The gate. A release candidate passes only if (1) every must-pass item passes, (2) a paired non-inferiority test on the aggregate shows it is not worse than the baseline by more than a margin, (3) each gated slice stays above its floor, and (4) cost and latency stay within budget (ae7, ev12). Work the aggregate test. On 2,000 golden items the baseline passes 84.0% and the candidate 83.2%. The candidate newly fails 70 items and newly passes 54; all others agree. The paired difference is (54 − 70) / 2,000 = −0.8 points. Its standard error is √(b + c − (b − c)² / n) / n with b = 70, c = 54: √(124 − 0.128) / 2,000 ≈ 0.56 points, so the 95% interval is −0.8 ± 1.96 × 0.56 = −1.9 to +0.3 points. With a non-inferiority margin of 1 point, the gate asks whether the lower bound is above −1. It is not, so the gate blocks: the data cannot rule out a 1.9-point regression. The team can look at the 70 newly failing items (often concentrated in one slice), or add samples and items to narrow the interval if they believe the drop is noise.

Two refinements matter in practice. Gates must be calibrated against A/A runs (the same release evaluated twice), because sampling temperature and judge noise produce differences even with no change; a gate that blocks A/A runs 20% of the time trains teams to ignore it. And checking many slices multiplies false alarms (ev7), so only a few slices are declared gating in advance, with a correction for multiple comparisons, and the rest are reported as diagnostics.

Drift alerts. In production, judged pass rate per feature is a proportion estimated from a daily sample. At 85% with 2,000 judged items a day the standard error is √(0.85 × 0.15 / 2,000) ≈ 0.8 points, so a three-sigma daily alert fires on drops of about 2.4 points; with 500 items it would take about 4.8. Smaller, sustained drifts are caught by smoothing over days with an EWMA chart (ev12). Input drift is watched separately: the share of traffic in each topic cluster, language and length band (ae3), because a quality drop with a shifted mix may be the traffic, not the system. Every alert names the feature, slice and release, shows the trend with intervals, and links to example failing traces, because an alert without examples starts an investigation from zero.

11 · Evaluation plan for the platform itself

A platform for measuring quality must measure itself. Offline: judge validation per criterion (kappa, sensitivity, specificity per slice) on fresh human labels each quarter; redaction recall and precision on a labelled sample of real traces; gate calibration by A/A runs. Online: time from a seeded regression (a deliberately broken canary release in a test feature) to alert; share of production incidents first detected by the platform rather than by users; ingestion lag and span loss rate (compare SDK-side counters with stored counts). Adoption: share of LLM features traced, gated and monitored; teams' use of dashboards; time to answer "what changed?" in incident reviews. Guardrails: SDK overhead on request latency, platform cost as a share of the LLM bill, access-control violations (zero), erasure requests completed within the deadline.

The trade-offs to name: content capture (debuggability) against privacy and cost; judge strength against cost; sampling depth against alert speed; centralised standards against teams' freedom to use the tools they like (the OpenTelemetry format is the compromise: standard data, any backend); strict gates against shipping speed; and build versus buy, since many vendors offer LLM observability on top of the same conventions, while the organisational parts (datasets, validated judges, gates, review) remain the company's own work.

Metadata and content are different products

Span metadata is small, low-risk and valuable forever: it drives dashboards, cost reports and incident timelines. Content is large, sensitive and valuable briefly: for debugging this week's incident and for promoting failures into datasets. Treating them as one stream forces the worst of both: either content inherits metadata's 13-month retention and broad access, or metadata inherits content's short retention and tight access. Splitting them at the collector, with separate stores, retention, access and encryption keys, is the single most important architectural decision in this platform, and it is why the OpenTelemetry conventions describe recording content references instead of content itself.

Evaluating conversations and agent runs, not just responses

Most evaluators judge one output, but users experience a conversation or a task. An agent can make five reasonable-looking calls and still fail the task; a chat can answer each turn well and never resolve the issue. The platform supports evaluations attached at three levels: the span (was this answer grounded?), the trace (did this run achieve its goal, did it respect required checks?) and the conversation (was the user's problem solved across turns?). Trace-level evaluators read the whole span tree, which is why tool call IDs and conversation IDs must be recorded consistently (ag12, ag14).

Judges with different jobs need different validation

A judge used to estimate an aggregate pass rate can be lenient if its error rates are known and stable, because the aggregate can be corrected. A judge used as a gate on individual must-pass items needs high specificity on that criterion (it must catch failures). A judge used to choose which traces humans review needs good ranking (failures scored lower than passes) more than calibration. The validation report should state which uses a judge is approved for, and the service should refuse to use it outside them.

Criteria drift and why rubrics are living documents

Shankar et al. observed that people refine their evaluation criteria as they grade outputs: they discover what "good" means by looking. A rubric written before seeing outputs is a first draft. The platform supports this by letting reviewers flag rubric ambiguities while labelling, versioning rubrics, and re-validating judges after each rubric revision; scores across rubric versions are not compared directly.

Online evaluation can change the system it measures

If a judge's verdicts feed back into the product (for example by blocking low-scoring answers or choosing between candidates), the judge becomes part of the system and its biases become product behaviour; developers may also start optimising prompts against the judge rather than against users. Keep at least one measurement that the product does not optimise against, such as human review of a random sample or a holdout judge, so the platform can detect when the optimised metric and real quality diverge.

Multi-tenancy in the judge service

Thirty teams share one judge service and its model-provider rate limits. Without controls, one team's full-suite run of 18,000 judge calls on a release day starves every other team's online judging, and production alerts go blind exactly when releases are happening. The service therefore separates traffic classes (online measurement first, release gates second, exploratory runs last), gives each team a token budget and a concurrency quota, and degrades online sampling gracefully (lower rates, never zero for gated features) rather than failing. Spend per team is reported next to quality, which turns "judge everything" into a visible trade-off.

Datasets leak too

Golden sets are only useful while they are unseen by what they evaluate. Items promoted from production can end up in few-shot examples in a prompt, in a retrieval index, or in fine-tuning data, after which the system scores well on them for the wrong reason. The dataset service tracks where each item has been used, fingerprints items so the training and indexing pipelines can exclude them, and keeps a held-out portion that is never shown to developers, used only for release decisions (ev2).

Sampling decisions at the edge

Classic tracing samples to save storage; here metadata is kept in full, but content capture and judging are sampled. Deciding at the SDK (head sampling) is cheap but cannot select on outcome; deciding after the trace completes (tail sampling) can keep every trace with an error or a thumbs-down but requires buffering content briefly. A common compromise is to keep all content for a short window (hours to days) in a restricted buffer, let the targeted sampler choose from it once outcomes and feedback are known, and expire the rest.

How it fails in practice

The provider update nobody announced. A model provider updates the model behind an alias; the support assistant's refusal rate on refund questions rises from 2% to 9%. Because finish reasons and a lightweight refusal classifier run on span metadata for every request, the refusal-rate metric for that feature and slice alerts within minutes, the dashboard shows gen_ai.response.model changing at the same moment, and the team pins the previous version. Without the response-model attribute, the cause would have taken days to find.

The judge that got kinder. The judge service's model is upgraded; every feature's groundedness score rises 3 points overnight. Teams celebrate until the canary set shows the same 3-point rise on unchanged outputs. The platform annotates the change on all dashboards and re-baselines gates; the lesson is that judge versions are releases too, gated by their own validation.

The prompts in the logs. A team logs full prompts with their application logger "temporarily" for debugging, bypassing the SDK and its redaction. The logs flow to a general logging system with broad access and 13-month retention. A data-protection review finds customer contract text there. The platform's answers are making the SDK the easiest way to debug (a trace viewer with content for the owning team) and scanning general logs for content patterns.

The retry storm in the bill. An agent's tool starts returning a transient error; the agent retries the whole plan, each time re-sending a 20,000-token context. Tokens per task rise tenfold for that feature. A cost-per-task alert from span metadata (input tokens per trace) catches it within the hour; a per-feature daily budget alarm is the backstop.

Metrics and dashboards

Per feature and release: requests, errors and finish-reason mix, refusal rate, latency percentiles and time to first token, tokens and cost per request and per task, judged quality per criterion with intervals, user feedback rates, safety flags. Platform health: ingestion lag, span loss, redaction recall, judge canary scores, judge latency and spend, review queue backlog, gate pass rates and A/A flake rates.

Knobs people tune

Random and targeted sample rates per feature; content capture and retention per data class; judge model per criterion; samples per golden item; gate margins and slice floors; alert thresholds and smoothing; verdict-cache scope; review queue routing rules.

The real case: Zheng et al. and the OpenTelemetry GenAI conventions

Zheng et al.'s "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena" (NeurIPS 2023 Datasets and Benchmarks track) is the reference measurement of LLM judges. Using about 3,000 controlled expert votes on MT-bench, a multi-turn question set, and about 3,000 crowdsourced votes from Chatbot Arena, they found that GPT-4 as a judge agreed with human experts 85% of the time when ties were excluded, higher than the 81% agreement between humans, and 66% against 63% with ties included. They also documented the biases a platform must control: position bias (GPT-4 gave consistent verdicts when the answer order was swapped only 65% of the time), verbosity bias, self-enhancement, and limited ability to grade maths and reasoning questions the judge cannot solve, with mitigations such as swapping positions and reference-guided grading. The lesson for a platform is double: judges can be good enough to scale evaluation, and only measurement against humans on your own task tells you whether yours is.

The OpenTelemetry GenAI semantic conventions supply the other half: a shared vocabulary for what to record. As checked on 8 October 2026 they live in their own repository with Development status, define inference spans named by operation and model with provider, model, token-usage (including cache reads and reasoning tokens) and finish-reason attributes, agent and tool spans, opt-in content attributes with guidance to upload content externally and record references, and a gen_ai.evaluation.result event for linking evaluation verdicts to the spans they judge. A platform built on them can change storage backends or vendors without re-instrumenting 150 features, which is the strongest argument for adopting a standard that is still evolving.

Goal: build a tiny eval harness: measure a judge against human labels (agreement, Cohen's kappa, sensitivity, specificity, corrected pass rate), then run a paired regression gate with a bootstrap interval and a non-inferiority margin. Python 3.12, standard library only.

  1. Save as eval_gate.py and run python eval_gate.py.
  2. In the judge block, compare raw agreement with kappa, and the judge's pass rate with the human pass rate and the corrected estimate.
  3. In the gate block, read the paired difference, the bootstrap 95% interval and the decision. Then set CANDIDATE_DROP to 0.0 and run several seeds: a gate tuned too tightly will sometimes block an unchanged release, which is the flakiness A/A runs measure.
  4. Set N_ITEMS to 6,000 and see the interval narrow; the same true difference can pass or block depending on suite size.
  5. Make the judge stricter (raise JUDGE_SPEC, lower JUDGE_SENS) and see kappa and the correction change.
"""Judge-vs-human agreement and a paired non-inferiority gate. Python 3.12, stdlib only."""
import random, statistics

rng = random.Random(42)
# ---- 1) validate a judge against human labels ----
N_LABELLED, HUMAN_PASS = 400, 0.71
JUDGE_SENS, JUDGE_SPEC = 0.94, 0.72         # judge passes 94% of human passes, fails 72% of fails
human = [rng.random() < HUMAN_PASS for _ in range(N_LABELLED)]
judge = [(rng.random() < JUDGE_SENS) if h else (rng.random() > JUDGE_SPEC) for h in human]
a = sum(h and j for h, j in zip(human, judge)); d = sum(not h and not j for h, j in zip(human, judge))
po = (a + d) / N_LABELLED
pj, ph = sum(judge) / N_LABELLED, sum(human) / N_LABELLED
pe = pj * ph + (1 - pj) * (1 - ph)
kappa = (po - pe) / (1 - pe)
sens = a / sum(human); spec = d / (N_LABELLED - sum(human))
corrected = (pj + spec - 1) / (sens + spec - 1)
print(f"agreement {po:.3f}  chance {pe:.3f}  kappa {kappa:.3f}")
print(f"sensitivity {sens:.3f}  specificity {spec:.3f}")
print(f"pass rate: judge {pj:.3f}  human {ph:.3f}  judge corrected {corrected:.3f}")

# ---- 2) paired regression gate ----
N_ITEMS, BASE_PASS, CANDIDATE_DROP, MARGIN = 2_000, 0.84, 0.008, 0.01
difficulty = [rng.random() for _ in range(N_ITEMS)]          # shared per item -> pairing helps
base = [dv < BASE_PASS for dv in difficulty]
cand = [dv < BASE_PASS - CANDIDATE_DROP if rng.random() < 0.9 else rng.random() < BASE_PASS
        for dv in difficulty]                                # mostly same items, some churn
diffs = [int(c) - int(b) for b, c in zip(base, cand)]
mean_diff = sum(diffs) / N_ITEMS
boot = []
for _ in range(2_000):                                       # paired bootstrap: resample items
    s = [diffs[rng.randrange(N_ITEMS)] for _ in range(N_ITEMS)]
    boot.append(sum(s) / N_ITEMS)
boot.sort()
lo, hi = boot[int(0.025 * len(boot))], boot[int(0.975 * len(boot))]
newly_fail = sum(1 for x in diffs if x == -1); newly_pass = sum(1 for x in diffs if x == 1)
print(f"\nbaseline {sum(base) / N_ITEMS:.3f}  candidate {sum(cand) / N_ITEMS:.3f}")
print(f"newly fail {newly_fail}  newly pass {newly_pass}  diff {mean_diff * 100:+.2f} pts")
print(f"95% paired bootstrap interval [{lo * 100:+.2f}, {hi * 100:+.2f}] pts, margin -{MARGIN * 100:.1f}")
print("GATE:", "PASS (non-inferior)" if lo > -MARGIN else "BLOCK (cannot rule out a regression larger than the margin)")

What to look for: kappa near 0.7 with raw agreement near 0.88; a judge pass rate a few points above the human rate and a corrected estimate close to the human rate; and a gate decision driven by the lower end of the interval, not by the point estimate. Re-running with different seeds shows how much the gate's verdict depends on noise when the true difference sits close to the margin.

Work it out

Your platform will judge production traffic for 40 features. Each feature wants its judged pass rate (around 90%) estimated daily to within ±1.5 points (95% interval). Judge calls average 3,500 input and 120 output tokens. Assume a validated small judge at $0.50 per million input tokens and $2 per million output tokens. (a) How many judged items per feature per day? (b) What does that cost per month for all features? (c) Three features also need a safety criterion judged by a strong model at six times the price on every sampled item. What does that add?

Answer

(a) The 95% half-width is 1.96 × √(p(1 − p)/n). Setting 1.96 × √(0.09/n) = 0.015 gives √(0.09/n) = 0.00765, so n = 0.09 / 0.0000586 ≈ 1,540 items a day per feature (round up to 1,600 to allow for slices and failures). If features have small slices that each need this precision, the slices, not the feature, set the sample size.

(b) 40 × 1,600 = 64,000 judge calls a day. Input: 64,000 × 3,500 = 224 million tokens × $0.50 per million = $112. Output: 64,000 × 120 = 7.7 million × $2 per million = $15. About $127 a day, about $3,800 a month. Cheap compared with human review; the real constraint is that the judge must be validated on each feature's criteria.

(c) 3 features × 1,600 = 4,800 calls a day at six times the price: per call, the small judge costs 3,500 × $0.50/10⁶ + 120 × $2/10⁶ = $0.00199, so the strong judge costs about $0.0119; × 4,800 ≈ $57 a day, about $1,700 a month. Worth it for a safety criterion where specificity matters; and the verdict cache avoids paying twice when the same output is judged offline and online.

Diagnose it

On Tuesday, the judged groundedness score drops 4 points for 12 of 40 features at once. Nothing was deployed in those features. User thumbs-down rates are flat. Ingestion lag is normal. What is your investigation order, and what would you change in the platform afterwards?

Answer

Suspect the instrument first. A simultaneous drop across many unrelated features with flat user signals points at something they share: the judge (model alias updated by the provider, judge prompt or rubric edited, parser change), the sampler (a change that shifted which traces are judged) or a shared component they all use (a retrieval index or model behind the features). Check the daily canary set: if unchanged outputs scored 4 points lower on Tuesday, the judge changed. Check judge version and gen_ai.response.model on judge spans. Check sampler configuration and the slice mix of judged items.

Then the shared dependency. If the canary is stable, look for a common upstream: the 12 features may share a retrieval index or a model version that changed (visible in their spans' response model or index version). Compare their release manifests and span attributes before and after.

Afterwards: pin judge model versions explicitly rather than aliases; gate judge changes on re-validation and the canary set; annotate dashboards automatically when any judge, rubric or sampler version changes; and add an alert on the canary set itself, so the platform reports "the judge moved" before twelve teams start investigating their own features.
