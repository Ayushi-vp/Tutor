A company has 400 applications that call language models. The support assistant uses one provider's large model; the code-review bot uses another provider; the document summariser runs on the company's own open-weight model cluster; a hundred small features (classify this ticket, draft this reply, extract these fields) use whatever their authors tried first. Every team holds its own API keys, writes its own retry loop, and finds out what it spent when finance forwards the invoice.

Then the predictable week arrives. On Monday, one provider has a two-hour partial outage; the twelve teams that wrote fallback code survive, the others page their on-call engineers. On Tuesday, a batch job written by an intern sends 40,000 requests in ten minutes, exhausts the company's shared rate limit with that provider, and the customer-facing support assistant starts returning errors because it shares the same organisation quota. On Wednesday, the security team discovers that customer email addresses and order numbers have been sent to a provider that the legal team never approved for personal data. On Thursday, finance asks why the bill went up 40% and which team caused it; nobody can say. On Friday, a provider announces a model retirement, and 60 applications must change a hard-coded model name.

Each of these is the same missing piece: a gateway, one service that every model call goes through, which knows who is calling, what they are allowed to send where, how much they may spend, which providers are healthy and how much capacity remains with each. The senior design question is to build it: a single API in front of many providers that routes by cost, quality and latency; falls back on failure without charging anyone twice; enforces per-tenant rate limits and budgets in tokens and dollars; caches what is safe to cache; redacts personal data and runs generic guardrails in the path; and meters and audits everything, while adding only tens of milliseconds to calls that already take seconds.

The lesson follows the interview: requirements with latency, cost and safety targets; estimates by hand for traffic, tokens, cost, concurrency and the gateway's own overhead; the API; the high-level design; deep dives on routing and fallback, token-bucket budgets, and caching (exact and semantic, with the wrong-answer maths); the evaluation plan; failure modes; and what changes at ten times the scale. The real case is LiteLLM, an open-source gateway whose documentation shows how these ideas are configured in practice, alongside a provider's own published rate-limit rules.

What a gateway does

An LLM gateway is a service that sits between applications and model providers. Applications send it requests in one format, with one kind of credential; the gateway decides which provider and model will serve each request, sends it, streams the answer back, and records what happened. The providers might be external APIs, cloud-hosted versions of the same models, or the company's own self-hosted inference platform (the one designed in hd1). From an application's point of view there is one endpoint and a handful of model names; from finance's point of view there is one bill broken down by team; from security's point of view there is one place where data rules are enforced.

The mental model: an airline booking desk in front of many airlines

Think of a corporate travel desk. Employees do not book flights with airlines directly. They tell the desk where they need to go and when; the desk knows company policy (economy for flights under six hours, approved airlines only for certain countries), each department's travel budget, which airlines are on strike today, and which fares are cheapest for the quality required. When a flight is cancelled, the desk rebooks on another airline, and the department is charged once, for the trip it took, not for both tickets. At the end of the month the desk produces one report of who spent what.

The gateway is that desk. Routing is choosing the airline and fare class. Fallback is rebooking on cancellation. Rate limits and budgets are each department's allowance. Data-class rules are "approved airlines only for this destination". Caching is noticing that someone already asked the identical question this morning. Metering and audit are the monthly report and the record of every booking.

The analogy breaks in two useful places. First, a flight is either booked or not, while an LLM response is produced over seconds, token by token, and reaches the user while it is still being generated; once half an answer has been shown, you cannot quietly swap in another provider's answer. Second, airlines are interchangeable for getting from A to B, but models are not interchangeable for answering a question: a cheaper model is a different product whose quality must be measured, not assumed.

Three things that make it different from an ordinary API gateway

First, the unit is the token, not the request. A token is the piece of text a model reads and writes, roughly three quarters of an English word. Cost, provider limits and load are all proportional to tokens, and the number of output tokens is not known until the response is finished. Rate limiting, budgets and cost accounting must therefore estimate before and reconcile after.

Second, responses stream. Most LLM APIs send output with server-sent events (SSE), a long-lived HTTP response that delivers tokens as they are generated, so users see the answer forming. A single request can hold a connection for 30 seconds, which changes how many connections the gateway must hold open, and it limits when a failure can be hidden by switching providers.

Third, the backends differ in quality, not just speed. Two web servers behind a load balancer return the same page. Two models return different answers. Every routing rule, fallback and cache is a choice about which answer the user gets, so the gateway is connected to the evaluation platform (hd12) the way a load balancer never needs to be.

A reader who stops here has the shape: a stateless fleet that authenticates, applies policy, admits by tokens, checks caches, redacts, routes and streams, with shared state for limits and caches, an asynchronous metering pipeline, and quality decisions that are measured rather than assumed.

1 · Requirements

Functional. One API for chat-style generation, embeddings and batch jobs, in a single request format, with streaming. Model aliases (stable names such as chat-default or extract-small) that the gateway maps to a provider and a pinned model version, so a provider's retirement is one configuration change. Routing by policy, cost, latency and health; fallback across deployments and providers; per-tenant API keys, rate limits in tokens per minute, and dollar budgets per period, arranged in a hierarchy (organisation, team, application, end user). Exact caching and opt-in semantic caching. PII redaction and data-class routing. Generic input and output guardrails. Metering of every attempt, chargeback per team, an audit log, and traces in the evaluation platform's format. Out of scope, said aloud: serving the models (hd1), agent orchestration and tool execution (hd7), and application-specific permission checks (au12).

Latency targets. Gateway overhead before the first upstream byte at most 15 ms at p50 and 50 ms at p99 (the 99th percentile: one request in a hundred is slower). Streaming adds no buffering beyond the output-guardrail window. Cache hits served in under 30 ms.

Availability. 99.95% for the gateway itself, measured as requests that get either a model answer or a correct, deliberate error (a 429 for an exhausted budget is a correct answer). Effective availability of answers should exceed any single provider's, which is the point of fallback.

Cost targets. Gateway infrastructure under 1% of the model spend it carries. Metered cost within 1% of provider invoices each month. No tenant charged twice for one logical request.

Safety and compliance targets. No request of a confidential or regulated data class reaches a provider not approved for that class: zero tolerance, fail closed. PII redaction recall at least 98% on the labelled test set for formatted identifiers. Every call auditable: who, which application, which model, which data class, when, at what cost.

Quality targets. Any routing policy, alias change or cache threshold change passes the same offline evaluation gate as a model change (hd12), and the semantic-cache false-hit rate stays below each application's declared limit.

Clarifying questions. "Is this internal (teams are tenants) or external (we resell to customers)?" "Which providers and regions are approved for which data classes?" "Do applications need streaming, tool calls and structured output through the gateway?" "Is there a self-hosted platform we must prefer for cost or privacy?" "Who owns the decision that a cheaper model is good enough?"

2 · Back-of-envelope estimates

Traffic. 400 applications send 20 million requests a day: about 230 a second on average and, with a daytime peak three times the average, about 700 a second. A typical request carries 2,500 input tokens (system prompt, conversation, retrieved passages) and produces 350 output tokens. That is 50 billion input and 7 billion output tokens a day.

Cost without routing. Assume a large model priced at $3 per million input tokens and $15 per million output tokens (illustrative round numbers, not any one provider's list). One request costs 2,500 × $3/10⁶ + 350 × $15/10⁶ = $0.0075 + $0.00525 = $0.01275. Twenty million a day is about $255,000 a day, $7.6 million a month.

Cost with routing. Assume a small model at a tenth of the price: $0.001275 per request. If evaluation shows that 70% of requests are answered acceptably by the small model, the blended cost is 0.3 × $0.01275 + 0.7 × $0.001275 = $0.0047 per request, about $94,000 a day, $2.8 million a month, a 63% saving. Provider prompt caching cuts the input side further: if 60% of input tokens are a repeated system prompt read from the provider's cache at a tenth of the input price, input cost falls by about half. These two levers dwarf everything else the gateway does for cost, which tells you where the design effort belongs.

Concurrency. Little's law (concurrent requests = arrival rate × time in system) with 700 requests a second and an average streamed duration of 8 seconds gives about 5,600 open streams at peak, each with a client connection and an upstream connection. An asynchronous gateway process holds thousands of idle-ish connections cheaply; with a conservative 1,000 streams per 4-vCPU pod, 6 pods carry the peak, and spreading across three availability zones with room to lose one gives about 12 pods. The gateway's compute cost is a rounding error next to the model bill; its connection count and its p99 overhead are the real constraints.

Shared-state operations. Each request does about four operations on the shared in-memory store: bucket reservation, bucket refund, budget check and exact-cache lookup. At peak that is about 2,800 operations a second, trivial for one Redis shard (which handles tens of thousands), but a round trip of about 1 ms each, so they must be pipelined or overlapped to stay inside the overhead budget.

Semantic cache. Only requests an application has marked cacheable are eligible: single-turn, low-temperature, no tools, no user-specific context. Suppose 30% of traffic, 6 million requests a day. Each needs one embedding (a vector of, say, 768 numbers) and a nearest-neighbour search. Keeping 24 hours of entries at 768 dimensions in 16-bit floats is 6 million × 768 × 2 bytes ≈ 9 GB of vectors, plus the stored answers: a modest vector index, partitioned by tenant. Embedding 70 requests a second on average is a fraction of one small GPU or a CPU pool.

Metering and audit. One event per attempt and per delivered response, about 1 KB each with tenant, alias, resolved model, tokens by type, cost, latency, status and data class: roughly 25 million events and 25 GB a day before compression. Kept 13 months for chargeback and audit in a columnar store, this is a few terabytes. Prompt and response content is not stored by the gateway by default; it goes to the evaluation platform's content store under that platform's opt-in and redaction rules (hd12).

The insight to say out loud. The gateway is a small, cheap service sitting in front of a very expensive one. Its value is measured in percentage points of a multi-million-dollar bill and in outages avoided; its risk is that it is on every request path, so its overhead and its availability matter more than its own cost.

3 · The request path and its latency budget

Walk one request. A support application sends a chat request with its key. The gateway resolves the key to a tenant from a local cache refreshed every few seconds (1 ms), loads the tenant's policy (data class "internal", allowed providers A, B and self-hosted; alias chat-default routes to the small model unless the router escalates). It counts input tokens and reserves tokens in the tenant's bucket and cost against its budget in one pipelined round trip (4 ms at p99). It hashes the normalised request and checks the exact cache (2 ms, miss). Because the application handles customer messages, the PII redactor replaces an email address and an order number with placeholders (12 ms at p99 for 2,500 tokens on CPU with a small named-entity model). The application is not semantic-cache eligible, so only the input guardrail runs, a small classifier that scores prompt injection and policy violations (25 ms at p99 on a shared GPU pool). The router picks provider A's small model on its healthiest deployment, the adapter translates the request into A's format and sends it over a pooled connection. About 49 ms have passed. Provider A's first token arrives 400 ms later. As tokens stream, the output guardrail checks them in windows of about one sentence, holding back roughly 150 ms of text so it can stop the stream before a violating sentence reaches the user. When the stream ends, the gateway refunds unused reserved tokens, restores placeholders to real values in the text the user sees (the restore happens per chunk, as tokens pass), emits a metering event, and closes the trace span.

Three choices matter. Applications name aliases, so changing the model behind an alias is a gateway change gated by evaluation, not 60 code changes. The final event reports the resolved model and attempts, so applications and the evaluation platform know what actually answered. And budget exhaustion is a distinct error from rate limiting: a 429 means "wait and retry", a budget error means "retrying will not help until someone raises the budget", the same distinction Anthropic's API draws between its rate-limit 429 (with a retry-after header) and its spend-cap response (without one).

5 · Data model

Configuration (a versioned store, cached in every node): tenants in a hierarchy with keys, data class, rate limits per model class in input and output tokens per minute, budgets per period, allowed providers and regions; aliases mapping to an ordered list of deployments with weights, fallbacks and routing policy; deployments with provider, model version, region, contracted limits and health thresholds; a price table versioned by date, so historical cost can be recomputed. Hot state (in-memory store): token buckets per tenant and per provider deployment, budget counters, circuit-breaker state, the exact cache. Semantic cache: per-tenant vector partitions with entries (embedding, normalised prompt hash, answer, model version, prompt version, knowledge version, created time). Ledger (append-only, columnar): one row per attempt (request ID, attempt number, deployment, tokens by type, provider cost, outcome) and one per delivered response (tenant chain, alias, resolved model, charged cost, cache status, latency, data class). Audit log: who changed which configuration when, and the per-call ledger rows, retained per policy.

6 · High-level design

The request path is the stateless fleet of the primer diagram, behind a regional load balancer. Each node holds configuration in memory (pushed on change, so a routing change takes effect in seconds without a deploy), a connection pool per upstream deployment, local circuit breakers and latency statistics, and short-lived leases of token budget. Upstream adapters translate the gateway's request format to each provider's (message shapes, tool-call formats, streaming event types, error codes) and back; features that only one provider has, such as explicit prompt-cache breakpoints, pass through in a provider-specific extension field rather than being forced into the common format. Side services on the path are kept few and fast: the PII detector and the guardrail classifiers run as separate scaled services so a slow model there does not block the gateway's event loop, and the embedding service feeds the semantic cache. Off the path: metering events go to Kafka, then to the ledger, the budget aggregator, dashboards and the audit store; spans go to the evaluation and observability platform (hd12); a reconciler compares the ledger with providers' usage exports daily; and a control plane holds configuration, its change history and approvals (an alias change requires a passing evaluation run).

7 · Deep dive: routing and fallback

Routing is three decisions. The first is which model class a request needs: the large model or the small one. Policies range from static (the application chose an alias that always means the small model) through rules (requests tagged "extraction" with short inputs go small) to a learned router, a small classifier that reads the request and predicts whether the small model's answer will be acceptable, with a threshold that trades cost for quality. RouteLLM trained such routers on human preference data and reported cost reductions of more than 2× in some settings without lowering quality; FrugalGPT studied cascades, where a cheap model answers first and a scorer decides whether to escalate, at the price of extra latency on escalated requests. The second decision is which provider serves that class, from those the tenant's data class allows. The third is which deployment (region, endpoint, self-hosted pool) is healthiest right now.

Health-aware selection. Each node tracks, per deployment, an exponentially weighted moving average of time to first token and error rate, and in-flight requests. Weights shift away from deployments whose latency rises; a circuit breaker (ld4) opens after a burst of failures, sending no traffic for a cool-down, then lets a few probes through. LiteLLM's router shows the same moving parts as configuration: routing strategies (simple shuffle by weight, the default; latency-based; least-busy; cost-based; usage-based, which its docs advise against in production because of the extra latency of tracking usage in Redis), and cooldowns that by default remove a deployment after 3 failures for 5 seconds.

Fallback, and the rule that makes it safe. A request may be sent again elsewhere only before its first token has been sent to the client. Before that point, a failure (connection error, 5xx, 429 from the provider, a time-to-first-token timeout) is invisible to the user, and the gateway can try the next deployment in the alias's list. After that point, the user has seen part of an answer; another model would produce a different continuation, so the gateway ends the stream with an error event that includes partial usage, and the application decides whether to retry the whole request.

Not double-billing. There are two different bills. The company's bill from providers includes every attempt that reached a provider: a first attempt that timed out at 3 seconds may still have been processed and billed. The tenant's internal charge should cover one logical request. The design keeps them apart. Each logical request carries an idempotency key (from the client header, or generated). Each attempt is a ledger row with its own usage, taken from the provider's response or, for abandoned attempts, estimated and later corrected from the provider's usage export. The tenant is charged for the attempt that produced the delivered answer; the others are booked as failover waste, a platform cost with its own dashboard. When the gateway gives up on an attempt it closes the upstream connection, which for streaming requests generally stops generation, so waste is mostly input processing rather than a full answer. And if the client itself retries with the same idempotency key, the gateway returns the stored completed response (for non-streaming calls, kept for ten minutes) or attaches the client to the in-flight stream, rather than starting again.

Retry budgets. Retries are limited to about 10% of each deployment's normal traffic over a sliding window. Without a budget, an outage multiplies load: every failing request becomes three or four, connection pools fill, and healthy traffic times out too. With one, once the budget is spent, requests fail fast to the next deployment or with a clear error.

Failover capacity is a contract, not a hope. Work the numbers. Provider A carries 60% of traffic. At the 700-request peak with 2,500 input tokens, that is 420 requests and 1.05 million input tokens a second: 63 million input tokens a minute. Provider B is contracted at 80 million input tokens a minute and normally carries its own 40% share, 42 million, leaving 38 million of headroom. Only about 60% of A's traffic can move. If the gateway sends it all, B starts returning 429s to everyone, including the tenants that were already on B. So the design decides in advance: interactive priority tiers fail over first, batch traffic is deferred (it was going to batch endpoints anyway), some applications degrade to the self-hosted model, and the remainder receive a 503 with retry-after. The gateway enforces B's limits with its own per-deployment token buckets, so it, not B, decides who waits.

Hedging for the tail. A hedged request sends a second copy to another deployment if the first has not produced a token by the p95 delay, and uses whichever answers first, cancelling the other. It cuts tail latency but pays for two prefills on the hedged fraction. At a p95 trigger, about 5% of requests are hedged, raising input cost by up to 5%; worthwhile for short, cheap interactive calls such as autocomplete, not for 20,000-token prompts.

8 · Deep dive: token buckets and budgets per tenant

A token bucket holds up to a capacity of tokens and is refilled at a steady rate; a request is admitted if the bucket holds enough and removes what it uses. It allows bursts up to the capacity while holding the long-run rate to the refill rate. Anthropic's API documents that its own rate limits use exactly this algorithm, with capacity continuously replenished rather than reset each minute, and that limits are in requests, input tokens and output tokens per minute. The gateway applies the same idea one level down: per tenant, per model class.

The problem: output is unknown at admission. When a request arrives, its input tokens can be counted (or estimated from its length), but its output tokens are not known until it finishes. Reserving max_tokens is safe but wasteful: applications set it high, and a 4,000-token reservation for a 400-token answer cuts usable throughput tenfold. The gateway reserves input plus an estimate of output, taken as the smaller of max_tokens and 1.5 times the application's recent p99 output length, then reconciles when the response finishes: unused reservation is refunded; overshoot is charged afterwards, letting the bucket go briefly negative so the next request waits. LiteLLM's budget enforcement does the same with money: it estimates a request's maximum cost and rejects it if that reservation would exceed the budget.

A worked trace. The support tenant has a limit of 600,000 tokens per minute: a refill rate of 10,000 tokens a second, with a capacity of 100,000 (ten seconds of burst).

The retry-after value is the deficit divided by the refill rate: 3,000 / 10,000 per second = 0.3 seconds. A well-behaved client waits exactly that long; the remaining requests trickle in at the refill rate. The burst was absorbed up to the capacity and then smoothed, and the interactive tenant on the same provider was never affected, because its bucket is separate and the provider-level bucket in the gateway had headroom.

The hierarchy. Limits nest: an organisation has a total, divided among teams, divided among applications, with optional per-end-user limits for applications that serve the public (so one abusive user cannot spend the application's whole allowance). A request must pass every level. Above token rates sit dollar budgets per period: soft alerts at 80%, a hard stop at 100% for tenants that asked for one, and an override path for incidents. Cost is computed from tokens by type (uncached input, cache writes, cache reads, output) and the versioned price table, so the budget reflects provider discounts such as prompt caching.

Distributed enforcement. Twelve gateway nodes share each tenant's bucket. The simple design keeps buckets in a sharded in-memory store and updates each with a single atomic script (read the level and last refill time, add refill for the elapsed time, check, subtract, write back), so two nodes cannot both spend the same tokens. At 2,800 operations a second this is easy, but it puts a round trip on every request. Two refinements: pipeline the bucket and budget operations into one round trip, and for hot tenants use leases, where a node takes a slice (say 5% of capacity) and admits locally until it is half spent. The overshoot is bounded by nodes × lease: 12 × 5,000 tokens = 60,000 tokens, a little over six seconds of this tenant's refill, an acceptable error for a rate limit and not for a hard legal budget, so hard budgets use small leases. If the store becomes unreachable, nodes fall back to local buckets at capacity divided by the number of nodes, failing open for rate limits rather than blocking all traffic.

Priority and the provider's own buckets. The gateway also keeps one bucket per provider deployment, sized slightly below the contracted limit, because the provider's limits are organisation-wide and the gateway is the only component that sees the total. Admission checks both the tenant bucket and the deployment bucket. When the deployment bucket is short, interactive requests are admitted before batch ones (a strict priority between two queues, with a small guaranteed share for batch so it is never starved forever), and latency-tolerant work is moved to the provider's batch endpoints, where Anthropic, for example, charges 50% less and completes within 24 hours.

9 · Deep dive: caching, exact and semantic

Three caches, different owners. Provider prompt caching reuses the processed form of a repeated prompt prefix inside the provider (or inside the self-hosted engine's prefix cache, hd1): the answer is still computed fresh, so it cannot be wrong, and it cuts input cost and time to first token. The gateway helps it by keeping requests with the same prefix on the same deployment (cache affinity) and by placing stable content first. Exact response caching in the gateway returns a stored answer for a byte-identical request. Semantic caching returns a stored answer for a request that merely means something similar. Only the last can return a wrong answer to a different question, which is what this deep dive is about.

The exact cache key. A hash of: tenant; resolved model and pinned version; every parameter (temperature, max tokens, tools and their schemas, response format, stop sequences); the full normalised message list including the system prompt; and versions of anything the prompt was built from (knowledge-base or index version). Only requests the application marked cacheable, with low temperature, are eligible. Including the tenant prevents one tenant's answers being served to another and closes a timing side channel (a fast response would reveal that another tenant asked the same thing). With the key complete, an exact hit is as correct as the original answer was. Hit rates are modest, a few per cent on interactive traffic and more on repetitive batch jobs (re-running a classifier over unchanged documents), and that is fine: every hit is free and safe.

The semantic cache and its bet. A semantic cache embeds the new prompt, finds the nearest stored prompt by cosine similarity (how closely two embedding vectors point the same way, from −1 to 1), and if it exceeds a threshold returns the stored answer. LiteLLM supports Redis, Valkey and Qdrant semantic caches configured with a similarity_threshold (its examples use 0.8) and an embedding model, scoped by key by default. The problem is that embedding similarity measures topic, not answer-equivalence: "how do I cancel my order" and "how do I cancel my subscription" are close neighbours with different answers. Every semantic hit is a bet. Call a hit whose answer is wrong for the new question a false hit.

The break-even rule. A hit saves the call cost c (plus some latency). A false hit costs the harm of a wrong answer h: a confused user, a support contact, a wrong action. With false-hit rate p, a hit is worth it when c > p × h, so the break-even false-hit rate is p* = c / h. Measure p by sampling hits, running the new question through the model and judging whether the cached answer is acceptable for it. Suppose an FAQ (frequently asked questions) application on the small model, where a call costs $0.0013 and a wrong answer is estimated at $0.05 (a share of users who contact support):

ThresholdSemantic hit rateFalse-hit ratePays? (p* = 2.6%)
0.979%0.5%Yes
0.9515%1.2%Yes
0.9224%4%No
0.9030%7%No

(The hit and false-hit rates are illustrative of the shape such a measurement takes; each application must measure its own.) At 0.95, per million eligible requests, 150,000 hits save about $195 and cost 1,800 wrong answers × $0.05 = $90: a modest net gain. At 0.90 the extra hits are net losses. Now take a large-model application where a call costs $0.0128 but a wrong answer about a refund policy is estimated at $5 (a complaint, a goodwill credit): p* = 0.26%, below even the strictest row. Semantic caching is wrong for it at any threshold.

Making it safe enough. Semantic caching is opt-in per application, with a declared cost of a wrong answer and a threshold chosen from a measured curve. Eligibility is narrow: single-turn, no user-specific context (an answer that mentions the user's own order must never be shared), no tools, low temperature. Entries are partitioned by tenant and keyed additionally by model, prompt and knowledge versions, so a policy change invalidates them; entries expire within hours to days. Some teams add a cheap verifier (a small model asked "does this cached answer answer this question?") on hits between two thresholds, trading a little cost for a lower false-hit rate. And the eligible fraction bounds the prize: 30% eligible traffic × (exact 6% + semantic 15%) ≈ 6% of all requests, about $170,000 a month at the blended price, real money but a fraction of what routing and prompt caching deliver.

10 · PII redaction and data-class routing in the path

Every tenant has a data class: public, internal, confidential or regulated. Each provider deployment is approved for some classes and regions (for example under a contract with zero data retention). The router's candidate list is filtered by class before any other consideration, and the filter fails closed: if no approved deployment is healthy, the request fails rather than going elsewhere.

For tenants whose class requires it, the redactor replaces personal data with typed placeholders before the request leaves: pattern detectors for formatted identifiers (emails, phone numbers, card numbers, national IDs) plus a named-entity model for names and addresses. "Refund order 88123 for jane@example.com" becomes "Refund order [ORDER_1] for [EMAIL_1]". The mapping lives in the request's memory only; as response tokens stream back, placeholders are replaced with the real values before they reach the user. This reversible redaction fails in known ways: the model may rewrite a placeholder ("[EMAIL 1]"), split it across stream chunks (the restorer must buffer a partial placeholder), or need the real value to do the task (a name's spelling). Detector recall is never perfect, which is why the class filter, not redaction alone, is the main protection for regulated data.

11 · Evaluation plan

Offline. For the router: each application's golden set (hd12) run through both model classes, judged by validated evaluators, giving a curve of quality against share routed small; the threshold is chosen per application where quality is non-inferior to all-large within the application's margin. For aliases: any change of the model behind an alias passes the same paired regression gate as a prompt change. For the semantic cache: hit and false-hit rates per threshold on a labelled sample of real request pairs. For redaction: recall and precision on a labelled set of real prompts per data type.

Online. Routing policies are A/B tested with the request (or the conversation) as the unit: primary metric cost per request; guardrail metrics judged quality on a sample, thumbs-down rate, retry and regenerate rates, and escalation rate, per application and slice. Semantic-cache rollouts are A/B tested too, because a false hit's harm shows up in downstream behaviour (re-asks, contacts) the offline label may miss.

Guardrail metrics for the gateway itself. Overhead p50 and p99; availability of answers versus each provider's; fallback success rate and failover waste as a share of spend; ledger versus invoice difference (target under 1%); duplicate charges per million requests (target zero); 429 rate per tenant (too high means limits are wrong); data-class violations (target zero, alert on one); redaction recall on a weekly fresh sample.

13 · What changes at 10× scale

At 200 million requests a day (7,000 a second at peak, about 56,000 open streams), the fleet grows to about 100 pods and the design changes in three places. Cells: the gateway is split into regional cells, each with its own fleet, store and connection pools, and tenants are assigned to cells, so one bad cell does not take down everyone and buckets stay local. Leases everywhere: per-request round trips to a shared store become the bottleneck, so nodes admit from leases and the store sees lease renewals, with overshoot bounded and reported. Capacity as a portfolio: the model bill is now large enough to buy reserved or provisioned throughput from providers and to run a larger self-hosted share (hd1), and the router becomes a capacity planner, filling committed capacity first (it is paid for whether used or not) and spilling to on-demand. Metering moves from one Kafka topic to a partitioned stream with pre-aggregation, and the reconciler runs hourly.

Streaming through a gateway is a protocol, not a pipe

A naive gateway reads the provider's stream and writes it to the client. A correct one must also count tokens as they pass (for metering if the stream is cut), run the output guardrail on windows of text, restore PII placeholders that may straddle chunk boundaries, translate one provider's event types into the common format (tool-call deltas are the hardest, because providers split arguments differently), and apply backpressure: if the client reads slowly, the gateway must not buffer an unbounded amount of a fast provider's output in memory. Each of these holds back a little text, and they must share one buffer rather than each adding its own delay. When the client disconnects, the gateway must cancel the upstream immediately, or the company pays for answers nobody reads.

Output guardrails on a stream

A classifier that judges a complete answer cannot run until the answer is finished, which defeats streaming. The usual compromise checks text in windows (a sentence or about 50 tokens) and holds back one window, so a violating sentence can be stopped before it is shown; the user sees text about 150 ms behind generation. The weakness is context: a harmful instruction can be spread over several innocent-looking windows. So streaming checks are a first line, and high-risk applications either run a full-answer check before showing anything (accepting the latency) or add a post-hoc check that retracts and reports. The decision is per application, which is why guardrail configuration hangs off the alias and tenant, not the gateway globally.

Learned routers drift when their models change

A router learns the gap between two specific models: which requests the small one fails. When either model is upgraded, the gap moves. A new small model that is better at extraction makes the router too conservative (sending work to the large model unnecessarily); a new large model makes nothing change in cost but the comparison baseline moves. The router is therefore versioned with the pair of models it was trained on, re-evaluated on every alias change, and monitored online by the share of traffic it escalates and by quality on each side of its decision. A sudden change in the escalation share is the cheapest early signal that something upstream changed.

Cache affinity versus load balancing

Provider-side and self-hosted prefix caches only help if requests sharing a prefix land where the prefix is cached. Pure load balancing spreads them evenly and destroys hit rates; pure affinity (hash the prefix to one deployment) creates hot spots when one application's prompt dominates. The middle path is bounded-load consistent hashing: route by prefix hash to a preferred deployment unless it is above, say, 1.25 times the average load, then spill to the next. For a self-hosted engine (hd1) this can halve time to first token for long shared system prompts; for external providers whose caching is per organisation and model, affinity matters less, but placing stable content first in the prompt still does.

Fail-open and fail-closed is a table, not a setting

Every check in the path needs an explicit answer to "what if this dependency is down?". Rate limiting fails open to local approximations, because rejecting all traffic is worse than brief overuse. Hard dollar budgets fail closed for external customers and open for internal teams. Data-class routing and redaction for regulated tenants fail closed. Input guardrails fail open for internal tools and closed for consumer products. Writing this table down per tenant tier, and testing it by deliberately failing each dependency in a staging cell, is what separates a gateway that degrades gracefully from one that turns a guardrail-service blip into a company-wide outage.

Metering correctness is an accounting problem

Metering events are produced asynchronously, can be lost or duplicated in transit, and arrive out of order. The ledger therefore keys rows by (request ID, attempt number), makes writes idempotent, and computes budgets from the ledger rather than from a counter that might double-count a replayed event. The real-time budget counter in the in-memory store is an approximation for admission; the ledger is the truth, reconciled daily against providers' usage exports. A persistent gap between the two (for example 3% more spend at a provider than in the ledger) usually means attempts that bypass the gateway, abandoned requests not recorded, or a price-table error, and each has a different fix.

Multi-provider tool calling is the leakiest abstraction

A common format for plain chat is easy; tools are not. Providers differ in how tool schemas are declared, whether several tool calls may be returned at once, how arguments stream, and how results are passed back. An application that relies on parallel tool calls from one provider can break silently when fallback sends it to a provider that serialises them. The defence is to declare per alias which capabilities it guarantees (tools, parallel tools, structured output, image input) and to allow fallback only to deployments with the same capability set, verified by contract tests that run every adapter against recorded conversations.

How it fails in practice

The failover that took down the healthy provider. Provider A starts returning errors at peak. Every gateway node opens its breaker within seconds and sends A's traffic to B. B's organisation-wide token limit is exceeded within a minute; B returns 429 to everything, including the interactive tenants that always ran on B. The fix was twofold: per-deployment token buckets in the gateway, sized below B's contract, so the gateway rather than B decides who gets the headroom; and priority tiers, so interactive traffic fails over and batch traffic waits.

The cache that quoted last month's policy. A support application had semantic caching on; the refund window changed from 30 to 14 days. For two days, users asking about refunds received cached answers quoting 30 days. The cache key had the model and prompt versions but not the knowledge-base version. Now every entry carries the index version, and publishing a policy document flushes the affected tenant's partition.

The leaked key. An application's gateway key was committed to a public repository and used to run thousands of large-model requests overnight. The hard daily budget stopped spend at the application's limit; without the gateway, the provider key would have run until the organisation's spend cap. Keys are now scoped per application and environment, and an anomaly alert fires on spend per hour above five times the trailing average.

The silent version change. An alias pointed at a provider's floating model name; the provider moved the name to a new version, and an extraction application's field accuracy dropped by 4 points. The response's reported model changed at the same moment, visible in the ledger. Aliases now point only at pinned versions, and a resolved-model change on any alias triggers an alert.

What to monitor

Per deployment: request rate, error rate by type, 429s from the provider, time to first token and total latency percentiles, breaker state, tokens per minute against contract. Per tenant: tokens and cost against limits and budgets, 429s and budget rejections, cache hit rates, fallback share. Gateway health: overhead per step at p50 and p99, open streams per node, event-loop lag, side-service timeouts. Money: spend by team, failover waste, ledger-to-invoice gap. Safety: data-class rejections, redaction counts by type, guardrail block rates.

Knobs people tune

Routing weights and router thresholds per application; time-to-first-token timeouts per priority; retry budget share; breaker failure count and cool-down; bucket capacity and refill per tenant; output-estimate multiplier; lease size; semantic-cache threshold and expiry time per application; guardrail window size; priority shares between interactive and batch.

The real case: LiteLLM and a provider's own limits

LiteLLM is an open-source gateway (a proxy server and a Python router) whose documentation, checked on 8 October 2026, maps closely onto this design. Its router offers routing strategies by name: simple-shuffle (the default, weighted random honouring per-deployment rpm and tpm), latency-based, least-busy, cost-based and usage-based routing, the last of which the docs advise against in production because tracking usage in Redis adds latency. Failing deployments are put into cooldown: by default after 3 allowed failures, for 5 seconds, triggered by 429s, by failure rates above 50% in the current minute, and by some client errors. Budgets are set with max_budget and budget_duration on keys, teams, users and end customers, with token and request rate limits alongside, and the docs describe budget reservation, estimating a request's maximum cost before sending it and rejecting it if the reservation would exceed the budget. Semantic caches on Redis, Valkey or Qdrant take a similarity_threshold (0.8 in the examples) and an embedding model, scoped by key unless configured otherwise. What the documentation cannot give you is the threshold for your application or the failover headroom for your providers: those are measurements and contracts.

The other half of the case is a provider's published rules, because the gateway must fit inside them. Anthropic's rate-limit documentation states that its API uses the token bucket algorithm, with capacity continuously replenished rather than reset at intervals; that limits are measured in requests, input tokens and output tokens per minute per model class; that for most models cache-read input tokens do not count toward the input-token limit; and that exceeding a limit returns 429 with a retry-after header, while hitting a spend cap returns a 429 without one. A gateway that mirrors these units and signals, and that keeps its own buckets slightly inside them, never surprises the applications behind it.

Goal: simulate a gateway's admission and routing for three tenants and two providers: token buckets with reservation and refund, a router with circuit breakers, an outage on provider A, fallback before first token, and a ledger that separates the tenant's charge from failover waste. Then compute the semantic-cache break-even for two applications. Python 3.12, standard library only.

  1. Save as gateway_sim.py and run python gateway_sim.py.
  2. Read the per-tenant table: admitted, rejected with 429, and charged dollars. The batch tenant is rejected most because its bursts exceed its bucket.
  3. Read the provider table: during the outage window A's breaker opens and B carries the load; waste is A's spend on failed attempts. Charged plus waste should equal total provider spend.
  4. Set B_LIMIT_TPS lower (for example 60,000) and re-run: fallbacks start failing with 503 because B's deployment bucket is empty, the failover-capacity problem from the lesson.
  5. In the cache block, change the cost of a wrong answer and see which thresholds pay.
"""LLM gateway simulator: token buckets, breakers, fallback, ledger. Python 3.12, stdlib only."""
import random
from dataclasses import dataclass, field

rng = random.Random(7)
PRICE = {"A": (3.0, 15.0), "B": (3.5, 14.0)}     # $ per million input, output tokens (assumed)
B_LIMIT_TPS = 150_000                           # provider B deployment bucket refill, tokens/s
SECONDS, OUTAGE = 120, (40, 70)                 # provider A fails between these seconds

@dataclass
class Bucket:
    cap: float; rate: float; level: float = None; t: float = 0.0
    def __post_init__(self): self.level = self.cap
    def take(self, now, n):
        self.level = min(self.cap, self.level + (now - self.t) * self.rate); self.t = now
        if self.level >= n: self.level -= n; return 0.0
        return (n - self.level) / self.rate        # retry-after seconds
    def refund(self, n): self.level = min(self.cap, self.level + n)

@dataclass
class Breaker:
    fails: int = 0; open_until: float = -1
    def ok(self, now): return now >= self.open_until
    def record(self, now, success):
        self.fails = 0 if success else self.fails + 1
        if self.fails >= 3: self.open_until, self.fails = now + 5, 0   # 3 fails -> 5 s cooldown

tenants = {  # name: (rate tokens/s, capacity, requests/s, input tokens, p99 output)
    "support": (40_000, 200_000, 8, 2_500, 400),
    "coding":  (60_000, 300_000, 6, 6_000, 700),
    "batch":   (30_000, 60_000, 10, 4_000, 300)}
tb = {n: Bucket(cap, rate) for n, (rate, cap, *_ ) in tenants.items()}
dep = {"A": Bucket(400_000, 200_000), "B": Bucket(B_LIMIT_TPS * 2, B_LIMIT_TPS)}
brk = {"A": Breaker(), "B": Breaker()}
stats = {n: {"ok": 0, "429": 0, "503": 0, "charged": 0.0} for n in tenants}
spend = {"A": 0.0, "B": 0.0}; waste = 0.0

def cost(p, i, o): return (i * PRICE[p][0] + o * PRICE[p][1]) / 1e6

for step in range(SECONDS * 10):                 # 100 ms ticks
    now = step / 10
    for name, (_, _, rps, inp, p99) in tenants.items():
        for _ in range(sum(rng.random() < rps / 100 for _ in range(10))):
            est = inp + int(1.5 * p99)
            if tb[name].take(now, est) > 0: stats[name]["429"] += 1; continue
            out = int(rng.expovariate(1 / (p99 / 3)))
            delivered = False
            for p in ("A", "B"):                  # fallback order; only before first token
                if not brk[p].ok(now) or dep[p].take(now, est) > 0: continue
                fails = p == "A" and OUTAGE[0] <= now < OUTAGE[1] and rng.random() < 0.8
                if fails:                         # input was processed, then error: waste
                    w = cost(p, inp, 0); spend[p] += w; waste += w
                    brk[p].record(now, False); dep[p].refund(est - inp); continue
                c = cost(p, inp, out); spend[p] += c; stats[name]["charged"] += c
                brk[p].record(now, True); dep[p].refund(max(0, est - inp - out))
                delivered = True; break
            tb[name].refund(max(0, est - inp - out) if delivered else est)
            stats[name]["ok" if delivered else "503"] += 1

print(f"{'tenant':8} {'ok':>6} {'429':>6} {'503':>6} {'charged $':>10}")
for n, s in stats.items(): print(f"{n:8} {s['ok']:6} {s['429']:6} {s['503']:6} {s['charged']:10.2f}")
charged = sum(s["charged"] for s in stats.values())
print(f"\nprovider spend A ${spend['A']:.2f}  B ${spend['B']:.2f}  total ${sum(spend.values()):.2f}")
print(f"charged to tenants ${charged:.2f} + failover waste ${waste:.2f} = ${charged + waste:.2f}")

print("\nSemantic cache break-even (p* = call cost / wrong-answer cost)")
curve = [(0.97, 0.09, 0.005), (0.95, 0.15, 0.012), (0.92, 0.24, 0.04), (0.90, 0.30, 0.07)]
for app, call, wrong in [("faq-small", 0.0013, 0.05), ("refund-large", 0.0128, 5.0)]:
    print(f"{app}: p* = {call / wrong:.2%}")
    for th, hit, fh in curve:
        net = 1e6 * hit * (call - fh * wrong)
        print(f"  threshold {th}: hits {hit:.0%}, false hits {fh:.1%}, net per 1M eligible ${net:,.0f}")

What to look for: 429s concentrated on the bursty tenant while the others are unaffected; during the outage, A's breaker cycling open and closed (each probe that fails adds waste) while B carries the traffic; charged plus waste exactly equal to total provider spend, which is the no-double-billing invariant; and in the cache block, a positive net only for the FAQ application at the two strictest thresholds.

Work it out

Your gateway carries 700 requests a second at peak, averaging 2,500 input tokens. Provider A carries 60% and B 40%. B's contract allows 80 million input tokens a minute. Provider A goes down. (a) How many input tokens a minute does A's traffic need? (b) How much of it can B absorb? (c) Interactive traffic is 55% of A's share and batch 45%. What do you do with each?

Answer

(a) A carries 0.6 × 700 = 420 requests a second × 2,500 = 1.05 million input tokens a second, 63 million a minute.

(b) B already carries 0.4 × 700 × 2,500 × 60 = 42 million a minute (if its traffic shape matches), leaving 38 million of headroom; keep about 10% in reserve for bursts, so about 34 million, roughly 54% of A's traffic. The point is that headroom, not B's total limit, decides.

(c) Interactive traffic is 0.55 × 63 = 35 million a minute, which just about fits the 34 million of usable headroom: fail it over, with the per-deployment bucket on B enforcing the limit so that any excess gets a 503 with retry-after rather than pushing B into 429s for everyone. Batch traffic (28 million a minute) goes to a queue or the providers' batch endpoints and is retried when A recovers; where some applications can use the self-hosted model, route them there. Afterwards, negotiate failover headroom into B's contract, or move enough steady traffic to the self-hosted platform that the remaining A share fits.

Diagnose it

Finance reports that provider B's invoice for last month is 6% higher than the gateway ledger says the company spent at B. Nothing else looks wrong. What are the likely causes, in what order do you check them, and what do you change?

Answer

Check traffic that bypasses the gateway first. Compare B's usage export by API key with the gateway's keys: an old provider key still used directly by a team or a script is the most common cause, and the fix is to revoke direct keys. Then abandoned attempts. If the ledger records only delivered responses, or records abandoned attempts at an estimated zero cost, the input processed before timeouts and cancellations is missing; compare the gap's timing with failover and timeout events. Then pricing. Check the price table version against the invoice line items: a price change, a cache-write premium or a long-context surcharge not in the table produces a steady percentage gap. Then lost events. Compare request counts in B's export with ledger attempt counts per hour; gaps clustered in time point to a metering pipeline outage. Afterwards: reconcile daily rather than monthly, alert on a gap above 1%, record every attempt with usage from the provider's response or usage export, and make the ledger's write path idempotent so replays cannot hide losses.
