A developer is writing a function to total a customer's invoices. They type def total_for_customer(invoices, customer):, press Enter, and pause for half a second to think. In that half second, grey text appears below the cursor: a three-line loop that filters invoices by customer and sums their totals using the Invoice.total() method defined in another file. They press Tab and move on. If the suggestion had arrived a second later, they would already have been typing and it would have been discarded. If it had used an amount field that does not exist, they would have accepted it, run the code, hit an error and lost more time than they saved.

That moment is the whole product: an inline code assistant predicts what the developer is about to type and offers it as ghost text. It looks simple, and it hides an unusually tight set of constraints. The latency budget is a few hundred milliseconds end to end, including the network. The request rate is enormous, because every pause in typing is a potential request. The context that decides quality is scattered across the current file, the code after the cursor, other open files and the rest of the repository, and only a small slice fits in the prompt. The code is the customer's intellectual property and sometimes contains secrets. And measuring whether it helps is genuinely hard: an accepted suggestion can still be wrong.

Interviewers ask this design because it is the opposite of a chat product. A chat answer can take seconds and use a large model on a long prompt; completion must be fast, small and context-rich, and its evaluation must connect telemetry to developer productivity. A strong answer budgets the latency in milliseconds, explains how the prompt is assembled, and knows what GitHub's published research found about measuring it.

This lesson follows the interview: requirements with latency, quality, cost and safety targets; estimates (request rate after debouncing and cancellation, token volumes, GPUs, a keystroke-to-suggestion budget); the API and data model; the architecture; deep dives on triggering and latency, context building, the model and serving, and post-processing and safety; the evaluation plan; failure modes; GitHub Copilot's research as the real case; and a lab that simulates debouncing and packs a prompt under a token budget.

What inline completion does

An editor plugin watches the developer type. When they pause, it builds a prompt from the code around the cursor, sends it to a language model trained on code, and shows the model's continuation as greyed-out ghost text at the cursor. Tab accepts it; typing anything else dismisses it. The model sees the prefix (code before the cursor) and, if it was trained for fill-in-the-middle, the suffix (code after the cursor), plus extra context such as snippets from other files. Its output is short: a line or a small block.

Three properties make this a distinctive system. It is latency-bound: a suggestion is only useful if it arrives before the developer resumes typing. It is high-request-rate, low-token: hundreds of thousands of developers each generate a request every few seconds of active typing, each asking for tens of output tokens, the opposite shape from a chat product with few requests and long answers. And it is context-bound: the model's skill matters, but whether it knows this repository's function names and types matters more, and that knowledge must be packed into a prompt of a couple of thousand tokens.

The mental model: a pair programmer reading over your shoulder

Imagine an expert sitting beside you who can see your screen, glances at the other files you have open, and occasionally whispers the next line. To be useful they must whisper quickly (before you type it yourself), whisper only when they are fairly sure (wrong whispers break your concentration), and know your codebase's names (generic advice is not enough). The analogy breaks in an important place: the human remembers what you did yesterday and has read the whole repository; the model sees only what fits in this one prompt, so everything it "knows" about your code must be chosen and sent with each request.

Follow one request through the figure. The developer stops typing. After a 75 ms quiet period the plugin decides this position is worth a suggestion, gathers the 40 lines above the cursor, the 15 lines below it, two short snippets from other open files that look similar, and the signature of a class the code is using, and sends them as one request of about 2,000 tokens. The gateway in the nearest region sends it to the model replica that served this developer's previous request, which already holds most of this prompt in its cache, so it only processes the few hundred tokens that changed. The model writes about 15 tokens, stopping at the end of the line. A post-processor checks the text, and the plugin draws it in grey. The developer presses Tab. Telemetry records that a suggestion of 38 characters was shown after 260 ms and accepted, and, ten minutes later, whether those 38 characters are still in the file.

Compare that with a chat assistant answering a question about the same code. The chat request is rare (a few per hour per developer), can take two seconds to start and twenty to finish, uses the largest model available, and is judged by whether the answer is right. The completion request is constant, must finish before the next keystroke, uses a small model, and is judged statistically over millions of suggestions. Most of the design follows from that contrast.

The rest of the lesson puts numbers on each box. Keep three questions in mind throughout: how fast must it be, what goes into the prompt, and how do we know it helps?

1 · Requirements

Functional. Inline suggestions in the major editors (VS Code, JetBrains IDEs, Neovim) for the common languages. Single-line suggestions by default, multi-line where a block is expected (after a function signature, a comment, an opening brace). Tab accepts, Escape or continued typing dismisses; partial acceptance (word by word) is supported. Enterprise administrators can exclude files or repositories from being sent as context and can enable a filter that blocks suggestions matching public code. Out of scope, said aloud: chat, multi-file edits and autonomous agents, which use larger models with looser latency.

Latency targets. From the moment typing pauses to ghost text on screen: p50 under 300 ms, p90 under 500 ms, measured in the client. Server-side time to complete a single-line suggestion: p50 under 120 ms.

Quality targets. Online: acceptance rate and characters accepted per active hour at or above the current production model, persistence of accepted code at 10 minutes (unchanged or mostly unchanged) at or above production. Offline: on a held-out repository benchmark, exact-match and edit-similarity at or above production before any experiment.

Cost target. Serving cost per developer per month a small fraction of the seat price; the estimates below put it at a few dollars.

Safety and privacy targets. No customer code is retained or used for training without opt-in; prompts travel encrypted to regional endpoints; secrets detected in output are never shown; excluded files are never sent; suggestions matching public code beyond a length threshold are blocked when the filter is on.

Clarifying questions. "How many developers, and how concentrated are their hours?" "Self-hosted model or a provider's API?" (latency and cost differ). "Do enterprise customers require a single region?" "What editors?" (the client is a large part of the design).

2 · Back-of-envelope estimates

Requests. 200,000 active developers, each actively editing about 3 hours a day. If a completion opportunity arises every 4 seconds of active typing, that is 3 × 3,600 ÷ 4 = 2,700 opportunities per developer per day. Debouncing suppresses about 40% (the developer is still typing), and of the requests sent, cancellation kills about 25% before the server finishes: 2,700 × 0.6 × 0.75 ≈ 1,215 model calls per developer per day, 243 million per day. Developers are spread across time zones, but working hours overlap: if the busiest hour carries 15% of the day's calls, peak is 243M × 0.15 ÷ 3,600 ≈ 10,000 requests per second.

Tokens. A prompt of about 2,000 tokens (1,200 of prefix, 300 of suffix, 500 of snippets from other files) and an average output of about 40 tokens (many single-line suggestions of 10-20 tokens, some multi-line). Per second at peak: 20 million prompt tokens and 400,000 output tokens. Per day: 486 billion prompt tokens and 9.7 billion output tokens. The prompt-to-output ratio of 50:1 says that prefill dominates the cost.

GPUs, naively. A 7-billion-parameter code model costs 2 × 7 × 109 = 14 GFLOPs per token. Prefill at peak: 20M × 14 GFLOP = 2.8 × 1017 FLOPs per second. An H100 running FP8 has about 1,979 dense TFLOPS (NVIDIA quotes twice that with sparsity); at 50% utilisation, about 990 TFLOPS. So prefill alone would need 2.8 × 1017 ÷ 9.9 × 1014 ≈ 283 GPUs.

GPUs, with session-affine prefix caching. Between two consecutive requests from the same developer, the prompt barely changes: a few new characters near the cursor. Everything before the edit point is identical. If the router sends a developer's requests to the same replica and the engine keeps their prompt's KV cache (hd1), only the tokens after the edit point need prefill: say 300 instead of 2,000. Prefill compute falls to 10,000 × 300 × 14 GFLOP = 4.2 × 1016 per second, about 42 GPUs. (Ordering matters: put stable context, like snippets from other files, before the frequently changing prefix tail so the cached prefix is long.)

Decode. 400,000 output tokens per second. Weights in FP8 are 7 GB; the KV cache for a Llama-like 7B shape (32 layers, 8 KV heads of dimension 128, FP8) is 2 × 32 × 8 × 128 × 1 byte = 64 KiB per token, so a 2,000-token context is about 131 MB. A batch of 64 reads 7 GB + 64 × 0.131 GB ≈ 15.4 GB per decode step; at 70% of 3.35 TB/s (2.35 TB/s) a step takes about 6.6 ms, giving each stream about 150 tokens per second and each GPU about 9,700 tokens per second. Decode therefore needs about 400,000 ÷ 9,700 ≈ 41 GPUs. Prefill and decode share GPUs only partly at these tight latencies, so plan about 42 + 41 = 83 GPUs, plus 30% headroom and multiple regions: about 110 GPUs.

Cost. 110 GPUs × $3 per hour × 730 hours ≈ $241,000 per month, about $1.20 per developer per month. If instead the product calls a provider's API at, say, $0.15 per million input tokens and $0.60 per million output tokens: 486B × 0.15 + 9.7B × 0.60 per day ≈ $72,900 + $5,800 ≈ $78,700 per day, $2.4 million per month, $12 per developer. Unless the provider also gives cached-prefix discounts, self-hosting with session affinity is about ten times cheaper at this scale, which is why prompt structure and caching are central to the design rather than an optimisation.

3 · The latency budget

Notice what is not in the budget: a large model. A 70B model's decode step on one replica is three to four times slower per token, so 18 tokens would take 300+ ms on their own. That is the arithmetic behind "small model, rich context".

4 · API

POST /v1/completions          (HTTP/2, one long-lived connection per editor)
  {session_id, request_id, language, path,
   prefix, suffix, snippets: [{path, text, score}],
   max_tokens: 64, mode: "line" | "block", temperature: 0.0}
  -> stream: {request_id, delta: "..."} ... {done, stop_reason, filtered?: "secret" | "public_code"}
POST /v1/cancel               {request_id}              # or reset the HTTP/2 stream
POST /v1/telemetry            [{request_id, event: shown | accepted | partial | rejected,
                                chars, latency_ms, persisted_30s?, persisted_600s?}]

The session_id drives routing affinity. Cancellation is explicit: when the developer types again, the client resets the stream and the server stops decoding that sequence immediately, freeing its batch slot. The Language Server Protocol, which editors already use for completions, has the same idea of cancelling a request in flight. Telemetry carries events and sizes, not code.

5 · Data model

Durable state is small and mostly about measurement: a telemetry event store (request ID, session, model version, latency, shown, accepted, characters, persistence at 30, 120, 300 and 600 seconds) aggregated into daily metrics by language, editor and model; per-organisation settings (content exclusion patterns, public-code filter on or off, data retention); model registry entries. There is deliberately no store of prompts or completions for enterprise customers. Runtime state lives in replicas: the KV caches of recent sessions and the session-to-replica map in the router, both disposable.

6 · High-level design

The client decides when to trigger, assembles the prompt, sends it and renders the result. A regional gateway close to the developer authenticates the token (cached), applies per-user rate limits, and routes by session ID using consistent hashing (in2) to a model replica, overriding affinity only if that replica is overloaded. Each replica runs an inference engine with continuous batching and a prefix cache (hd1), configured for latency: small batches, short maximum outputs, stop sequences. Tokens stream back through a post-processor that trims, de-duplicates against the suffix, checks for secrets and, if enabled, checks the public-code index. Telemetry flows asynchronously to the metrics pipeline. Several regions run the same stack; a developer is pinned to the nearest healthy one.

7 · Deep dive: triggering, debounce and cancellation

When to trigger. Not every pause deserves a suggestion. The client skips positions in the middle of a word, inside strings and comments where suggestions are rarely useful (unless the comment describes code to write), and right after the developer dismissed a suggestion at the same position. It may run a tiny local model or heuristic to predict whether a suggestion would be accepted here, and skip unlikely positions entirely; this saves server cost and reduces distraction.

Debounce. A request is sent only after a quiet period with no keystroke. The lab simulates a ten-minute session of 2,839 keystrokes typed in bursts: with no debounce, every keystroke sends a request (2,839), and 2,061 of them are cancelled because the developer typed again while the server was working. A 75 ms debounce sends 1,607 and shows 499; 300 ms sends 397 and shows 210, but every suggestion waits 300 ms longer. The right setting balances server load against perceived latency and is tuned per typing speed in practice.

Cancellation. When the developer types while a request is in flight, the suggestion is stale. The client aborts the stream and the server frees the sequence's batch slot at the next step. Without server-side cancellation the GPU would finish generating suggestions nobody will see; at the cancellation rates above, that would waste a large share of decode capacity.

Typing through. If the developer types characters that match the start of the shown suggestion, the client keeps showing the remainder instead of requesting a new one. This "consume as you type" behaviour makes a suggestion useful even when the developer does not press Tab, and avoids a burst of requests.

8 · Deep dive: building the context

The prompt has a budget of perhaps 2,000 tokens, and the candidate context is much larger: the current file (often thousands of tokens), other open files, the repository. Context assembly is a ranking and packing problem, done on the client, where the files are.

The pieces, in priority order. (1) The nearest prefix: the 20-50 lines before the cursor, without which nothing works. (2) The suffix: the lines after the cursor, so the model knows what comes next and does not re-generate it; this requires a model trained for fill-in-the-middle, whose prompt format is <PRE> prefix <SUF> suffix <MID> with the model generating the middle. (3) Metadata: file path and language, which shift the model's expectations (a path under tests/ predicts test code). (4) Neighbouring snippets: windows of lines from other open files, ranked by similarity to the code near the cursor. GitHub described this "neighboring tabs" approach and noted that a low bar for including matches worked best. A simple, fast similarity is the Jaccard similarity of the token sets of the two snippets. (5) Definitions: through the language server (the editor's per-language background process that knows types and definitions), fetch the signatures of functions and classes used near the cursor, such as class Invoice with its fields, which removes the most common kind of error, invented names. (6) The far prefix: imports and earlier code in the file, which matter less per token.

Packing. Each piece is scored and greedily added in priority order while it fits. The lab packs a toy prompt: at 80 tokens only the prefix fits; at 160 the suffix and the most similar snippet (from billing/models.py, which defines Invoice.total()) join; at 400 more snippets come in, including an irrelevant one from web/views.py, showing why a similarity threshold and ranking matter even when there is room. Ordering inside the prompt matters for caching too: snippets and older prefix change rarely and go first; the near prefix changes every keystroke and goes last, so the cached prefix is as long as possible.

Repository retrieval. For code that relates to files that are not open, the client (or a server-side index built for the repository) can retrieve similar code or definitions from the whole repository, the RAG pattern of hd2 at small scale. RepoCoder showed iterative retrieval (retrieve, generate a draft, retrieve again using the draft) improves repository-level completion. The constraint is latency: retrieval must finish within the budget, so it uses a local index or precomputed results, never a slow remote search on the critical path.

9 · Deep dive: the model and serving

Model choice. A code model in the few-billion-parameter range, trained on permissively licensed code with the fill-in-the-middle objective, fine-tuned on completion-shaped data (realistic prefixes, suffixes and neighbouring snippets). Bavarian et al. showed FIM can be learned without hurting left-to-right ability, so there is no reason to skip it. Smaller models can be distilled from larger ones (rs6 covers distillation) to recover quality.

Decoding. Greedy or very low temperature: there is one suggestion slot, so the most likely completion is wanted, and determinism makes debugging possible. Stop rules end generation early: at the end of the line in single-line mode, and when indentation returns to the starting level in block mode. Speculative decoding fits this workload unusually well: code is predictable, so a draft model's tokens are often accepted, and batches are kept small for latency, so there is spare compute to verify drafts.

Serving for latency. Batches are small (tens, not hundreds) to keep per-token time around 5 ms. Session-affine routing plus the engine's prefix cache provides the large prefill saving estimated above. Replicas run in several regions so the network round trip stays near 40 ms. Because cancellations are frequent, the engine must free cancelled sequences at the next step. Autoscaling follows the working day per region, with warm pools ahead of each region's morning.

10 · Deep dive: post-processing and safety

The raw model output is checked before display. Trimming: cut at the end of the line or block; if the suggestion ends by repeating the first line of the suffix, drop the overlap. Validity: reject suggestions with unbalanced brackets or quotes relative to the surrounding code, or that are only whitespace or a copy of the previous line. Secrets: scan for patterns of keys and tokens (cloud credentials, private keys) and drop matching suggestions, because a model trained on public code has seen leaked secrets, and a prompt may contain the customer's own. Public code matching: when the organisation enables it, compare suggestions above a length threshold against an index of public code (for example, hashes of normalised token windows) and block matches, which addresses licence concerns. Insecure patterns: a lightweight check can flag obviously dangerous constructs (SQL built by string concatenation, disabled certificate verification), though deep security review belongs elsewhere.

Privacy is mostly an architectural decision: process prompts in memory, do not log them, keep enterprise traffic out of training, honour content exclusions in the client before anything is sent, and send telemetry about events rather than code (ae5). These choices also constrain debugging: without logged prompts, quality investigations rely on opt-in data and offline benchmarks.

11 · Deep dive: measuring persistence

Acceptance alone cannot tell a good suggestion from one that was accepted and then fixed. Persistence closes the gap: after a suggestion is accepted, the plugin remembers the inserted text and its location, and at fixed delays (30 seconds, 2, 5 and 10 minutes, the intervals GitHub's study used) checks whether that text is still present. "Unchanged" means an exact match; "mostly unchanged" means an edit distance under a threshold (GitHub used a Levenshtein distance under 33% of the length). The check must follow the text as the developer edits around it, so it tracks the region rather than a fixed line number. Only the outcome (persisted or not, and the edit fraction) is sent as telemetry, never the code itself. Aggregated, persistence answers the question acceptance cannot: of the code we wrote for developers, how much did they keep?

11 · Evaluation plan

Offline benchmark. Build tasks from real repositories not in the training set: choose cursor positions in recent commits, rebuild the prompt exactly as the client would (same prefix, suffix and neighbouring-snippet logic), and compare the model's completion with what the developer actually wrote. Metrics: exact match, edit similarity, and for repositories with tests, whether the completed code passes them (pass@1, from Codex's HumanEval methodology, applied to fill-in-the-middle tasks). Slice by language and completion length. Measure latency on production hardware alongside, because a quality gain that costs 50 ms may lose online.

Online metrics. Acceptance rate (accepted ÷ shown), shown rate (shown ÷ opportunities), characters accepted per active hour, persistence (accepted code still present unchanged, or mostly unchanged, after 30 seconds to 10 minutes), and client-measured latency. GitHub's study defined these and found acceptance rate correlated best with developers' perceived productivity; volume and persistence guard against gaming it.

Experiments. Every model, prompt or client change runs as an A/B test by developer (in10), with guardrails on latency and persistence. Occasionally, to justify the product rather than a change, run a controlled study of task completion, as GitHub did (section on the real case).

12 · Failure modes and trade-offs

Latency regression: a model or region problem pushes p90 above 500 ms; acceptance falls because suggestions arrive late. Alert on client-side latency per region. Cache-affinity loss: a router change spreads sessions randomly; GPU load jumps several-fold with no change in traffic. Context bugs: a client update stops sending the suffix for one language; the model starts duplicating code that already exists below the cursor; detect through per-language acceptance and the post-processor's overlap-trim rate. Over-filtering: a secret detector flags common strings and the shown rate drops.

The trade-offs: model size against latency and cost; debounce against server load; prompt size against prefill cost and the chance of including distracting context; single-line against multi-line (value per suggestion against review cost and error rate); and privacy against debuggability.

Why fill-in-the-middle costs nothing

FIM training moves a random middle span of each training document to the end, wrapped in sentinel tokens, so the model learns to generate it after seeing prefix and suffix. One might expect this to hurt ordinary left-to-right generation, since some training examples are reordered. Bavarian et al. found that training with a large fraction of FIM-transformed data left left-to-right performance essentially unchanged, which they called "FIM-for-free". The practical consequence: every code completion model should be trained with FIM, and the serving prompt must use exactly the sentinel format and ordering (prefix-suffix-middle or suffix-prefix-middle) the model was trained with; a mismatch silently degrades quality.

Token healing and the cursor boundary

The cursor often sits in the middle of what will become one token: the developer typed pri, and the model's tokenizer would normally encode print as a single token. If the prompt ends with the token pri, the model must continue from an unusual token boundary it rarely saw in training, and quality drops. Assistants handle this by backing the prompt up to the last complete token boundary and constraining the first generated token to begin with the removed characters, sometimes called token healing. It is a small detail with a measurable effect on single-token-boundary suggestions.

Caching across keystrokes

Beyond the server's prefix cache, the client can cache: if the developer types characters that match the shown suggestion, keep it; if they delete back to a position seen recently, reuse the suggestion made there. Server-side, an exact-match cache keyed by a hash of the full prompt helps for repeated positions. These caches change the request-rate estimate materially and should be measured, since every avoided request is avoided GPU time and latency.

Choosing the debounce and the trigger model together

Debounce is a blunt tool: it delays every suggestion equally. A trigger model, a small classifier on the client predicting whether a suggestion here would be accepted (from features such as the character before the cursor, the language, the time since the last keystroke and recent acceptance history), lets the system send requests eagerly where acceptance is likely and skip where it is not. GitHub's productivity paper defines "shown rate" and "eagerness" for exactly this layer. The combined effect is lower server load and higher acceptance, but it must be tuned against coverage: a trigger model that is too conservative raises acceptance rate by showing less, the classic way the metric is gamed.

Offline-online gaps

Exact match against what the developer wrote is a harsh metric: many correct suggestions differ from the developer's version by a variable name or ordering. Edit similarity is softer but rewards near-misses that may not compile. Execution-based metrics are the most faithful but need tests, which most real positions lack. And none captures the interaction: a suggestion that is 80% right may still be accepted and fixed, saving time. This is why offline benchmarks filter candidates and online experiments decide, the same split as in recommendation systems.

Why a smaller model with better context can win: a worked comparison

Suppose a 7B model accepts at 27% with the standard context, and a 34B model accepts at 31% with the same context. The 34B model decodes about 4× slower per token, so its single-line suggestion takes roughly 350 ms of decode instead of 90, and the client's p50 rises from 270 to about 530 ms. In the lab's typing simulation, raising server time from 180 to 400 ms cuts the number of suggestions shown before the developer resumes typing by a large fraction, and fewer shown suggestions means fewer accepted characters even at a higher acceptance rate. Meanwhile, adding definitions of nearby symbols to the 7B model's context (a client change, no extra GPU) might raise its acceptance from 27% to 30%. The comparison that matters is accepted characters per active hour at production latency, and on that metric context improvements usually beat model size for inline completion.

Latency percentiles compound

The p50 budget adds medians, but a slow suggestion is usually slow because several stages were slow at once: a cold cache, a busy replica, a long prompt, a congested network path. Tail latency in a multi-stage path is worse than any single stage suggests. Practical defences: hedge requests when the first replica has not produced a token within a deadline (send to a second replica and take whichever answers first), cap prompt length so prefill time has a hard ceiling, and give up client-side when the deadline passes, because a late suggestion is worse than none: it appears as the developer types and must be dismissed.

Personalisation without training on customer code

Organisations want suggestions that use their internal libraries. Options in increasing cost and risk: better retrieval of the organisation's code at prompt time (no training, respects permissions if retrieval respects them); a per-organisation fine-tune on its repositories (better fluency with internal APIs, but a separate model to serve and a data-governance decision); and a per-organisation LoRA adapter on a shared base model, served with multi-adapter batching (hd1). Retrieval is the default because it updates instantly when code changes and never puts private code into model weights.

How it fails in practice

The slow region. A capacity shortfall in one region raises queueing; p90 latency goes from 400 to 900 ms. Acceptance rate in that region falls by a third, but no error is ever raised. Client-side latency percentiles per region, with automatic failover to the next-nearest region when queues grow, are the fix.

The broken suffix. An editor update changes how the plugin reads text after the cursor in notebooks; prompts arrive without a suffix and the model writes code that already exists below. Detection: per-editor and per-language acceptance dashboards and the rate at which post-processing trims suffix overlap.

The repetition loop. In files with highly repetitive structure (long lists, generated tables), the model proposes the previous line again and again. Repetition checks in post-processing and stop rules catch most cases.

Metric gaming. A change to the trigger heuristic raises acceptance rate by suppressing suggestions in hard positions. Characters accepted per hour and shown rate reveal it.

Follow-the-sun capacity. Developer traffic follows working hours: Asia-Pacific regions peak first, then Europe, then the Americas. Each region's fleet is sized for its own peak plus failover from a neighbour, and capacity is shifted between regions on a daily schedule. A region that runs short at its morning peak is the most common cause of the slow-region incident above; scaling must start before the peak, not in response to it, because GPU replicas take minutes to come up.

What to monitor

Client latency percentiles per region, editor and language; shown, accepted and cancelled rates; characters accepted per active hour; persistence at 30 seconds and 10 minutes; post-processing filter rates (secrets, public code, suffix overlap); GPU prefix-cache hit rate and session-affinity rate; tokens per second per replica.

The real case: GitHub Copilot's published research

GitHub has published unusually detailed evidence about measuring and improving inline completion. Ziegler and colleagues' 2022 study, "Productivity Assessment of Neural Code Completion", emailed 17,420 users of the Copilot technical preview and matched 2,047 survey responses to four weeks of usage telemetry. They compared many usage measures (shown rate, acceptance rate, persistence of accepted code after 30 to 600 seconds, characters accepted per hour) against developers' self-reported productivity, and found that "acceptance rate of shown suggestions is a better predictor of perceived productivity than the alternative measures" (correlation 0.24 with aggregate productivity). In their data Copilot's acceptance rate was 27%. The authors also caution that acceptance rate suits coarse-grained monitoring and that human factors leave much variance unexplained. Peng and colleagues' 2023 controlled experiment recruited 95 professional developers through a freelancing platform to implement an HTTP server in JavaScript: among those who completed, the group with Copilot took 71.17 minutes on average against 160.89 minutes for the control group, 55.8% faster (95% confidence interval 21-89%), and participants underestimated the gain, guessing 35%. On the context side, GitHub's engineering blog described the prompt-assembly pipeline (select snippets from the current file and other sources, prioritise, filter, assemble) and reported that neighbouring tabs increased acceptance by 5% relative and fill-in-the-middle by 10% relative. The interview lessons: context is a measurable lever; acceptance rate is a sound monitor but needs companion metrics; and the strongest claims come from controlled experiments, not telemetry alone.

"""Two pieces of an inline code assistant. Python 3.12, stdlib only.
1) Debounce + cancellation: how many model calls a typing session really makes.
2) Context packing: fill a token budget with prefix, suffix and the most similar
   snippets from other open files (Jaccard similarity, as in 'neighboring tabs')."""
import random, re

# ---------- 1. debounce and cancellation ----------
rng = random.Random(3)
def typing_session(seconds=600):
    """Keystroke times: bursts of fast typing separated by thinking pauses."""
    t, keys = 0.0, []
    while t < seconds:
        for _ in range(rng.randint(3, 25)):          # a burst of keystrokes
            t += rng.expovariate(1 / 0.12)           # ~120 ms between keys
            keys.append(t)
        t += rng.expovariate(1 / 1.5)                # pause ~1.5 s
    return keys

def simulate(keys, debounce, server_ms=180):
    sent = cancelled = shown = 0
    for i, k in enumerate(keys):
        nxt = keys[i + 1] if i + 1 < len(keys) else float("inf")
        if nxt - k < debounce:                       # user typed again: never sent
            continue
        sent += 1
        if nxt - k < debounce + server_ms / 1000:    # typed again while in flight
            cancelled += 1
        else:
            shown += 1
    return sent, cancelled, shown

Work it out

Your assistant serves 20,000 developers. Each triggers a completion request roughly every 4 seconds of active typing, for about 3 hours of active editing a day. Debouncing suppresses 40% of triggers; cancellation kills another 25% of what remains before the model starts. Each surviving request costs 400 input tokens and 30 output tokens.

(a) What is the peak QPS if 60% of developers are active in the same 8-hour window? (b) What is the daily token bill at $0.15/M input and $0.60/M output? (c) Where would you attack the cost?

Answer

(a) Raw triggers per developer per day: 3 hours × 3,600 ÷ 4 = 2,700. After debounce (× 0.6) and cancellation (× 0.75): 2,700 × 0.45 = 1,215 model calls per developer per day. Across 20,000 developers that is 24.3M calls/day. Concentrated in an 8-hour window, the average rate is 24.3M ÷ 28,800 ≈ 840 rps, and with intra-day peaking call it about 1,500 rps. This is a high-QPS, low-token workload, the opposite shape to a chat product, which is why it wants small models and many replicas rather than large models and big batches.

(b) Input: 24.3M × 400 = 9.72B tokens → $1,458. Output: 24.3M × 30 = 729M tokens → $437. About $1,895/day, $57k/month, or $2.85 per developer per month.

(c) Input is 77% of the bill, and consecutive prompts from one developer are nearly identical, so the biggest lever is prefix caching with session affinity (self-hosted) or a provider's cached-input pricing: if 80% of input tokens are cache hits at a tenth of the price, input cost falls by about 70%. Next, a trigger model that skips positions where suggestions are rarely accepted cuts calls without hurting value. Then client caching when the developer types through a suggestion. Shrinking the prompt is last, because context is what makes suggestions good.

Diagnose it

A Monday release of the editor plugin is followed by acceptance rate falling from 28% to 22% for Python in JetBrains IDEs only. Latency is unchanged, and other editors and languages are flat. How do you find the cause?

Answer

Narrow it with the slice. One editor, one language, unchanged latency and model: the server is almost certainly fine, and the client's context or rendering is not. Compare post-processing statistics for that slice before and after: a jump in suffix-overlap trimming means the suffix is missing from prompts (the model rewrites code that exists below the cursor); a drop in shown rate means triggering changed; a jump in partial acceptances or in rejections immediately after display may mean rendering or indentation problems.

Reproduce. Use an internal build with prompt logging (on internal code only) to compare prompts from the old and new plugin at identical cursor positions. Typical culprits: the plugin reads the document through a new API that returns text up to the cursor only, tabs versus spaces handling, or a change in how notebook cells are concatenated.

Prevent it. Add a client-side contract test that builds prompts from fixture files in each supported editor and compares them with golden prompts, and stage plugin releases by percentage with the acceptance-rate slice as an automatic rollback guardrail.
