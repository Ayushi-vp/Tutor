A payments company has a fraud model in production, written by a data scientist two years ago. Its best feature is "number of disputes on this card so far". In the training notebook it was computed with a SQL query over the disputes table; in production, an engineer re-implemented it in the scoring service from a counter the payments service maintains. The model's offline AUC was 0.97. In production it performs like a model with an AUC around 0.7, and nobody can explain why. A second team building a merchant-risk model has written its own version of the same feature, slightly differently. A third team wants it for a credit model but cannot find where it lives.

The investigation, when it finally happens, finds two separate bugs and one structural problem. The training query counted disputes as of the day the notebook ran, so a fraudulent payment from March was trained with disputes filed about it in April, information the model can never have at decision time. The production counter skipped disputes from one card network, so its values were systematically lower than in training. And the structural problem: there was no single definition of the feature, so every model had its own, each wrong in its own way.

A feature store exists to make that story impossible: one definition of each feature, computed by one pipeline into two stores (one with full history for training, one with the latest values for serving), training data built with point-in-time correct joins, and monitoring that compares what serving saw with what training used. Around it, a training platform makes models reproducible and their deployment routine. Interviewers ask this design to test whether you understand time in data: event time versus availability time, as-of joins, streaming windows, backfills, and the subtle ways skew and leakage enter.

This lesson follows the interview: requirements with correctness, latency, freshness, cost and governance targets; estimates for online store size and QPS, streaming write rates, offline history and training-set generation; the API and data model; the architecture; deep dives on feature definitions, point-in-time joins, the online store, streaming features and backfills, monitoring, and the training platform; the evaluation plan; failure modes; Uber's Michelangelo as the real case; and a lab that shows a leaky join inflate AUC from 0.66 to 0.98.

What a feature store does

A feature is a value a model uses as input, describing an entity such as a user, a card, a merchant or an item: "payments on this card in the last hour", "this restaurant's average preparation time over the last seven days". Features are computed from raw data (event logs, database tables) by code. A feature store manages that code and its outputs. Feature definitions are written once, as code or declarative configuration, and registered with owners and descriptions so others can find and reuse them. Pipelines materialise them, computing values and writing them to two places: an offline store, columnar storage in the data warehouse or lake that keeps every historical value with timestamps, and an online store, a fast key-value store that keeps only the latest value per entity and answers lookups in a few milliseconds.

Two read paths follow. Training asks: "for each of these 500 million labelled events, give me each feature's value as it was at that event's moment", answered from the offline store by a point-in-time join. Serving asks: "for this user and this merchant, give me their features now", answered from the online store. Because both stores are filled from the same definition by the same pipelines, the values agree, which is the whole point.

The mental model: a ledger and a scoreboard

Think of a sports league. The scoreboard shows each team's current points, updated the moment a match ends, and anyone can glance at it instantly: that is the online store. The ledger records every match result with its date, so you can reconstruct any team's points on any past day: that is the offline store. A betting analyst studying "teams that were top of the table on the morning of a match" must read the ledger as of that morning; reading today's scoreboard would leak the results of matches that had not happened yet. A feature store keeps the scoreboard and the ledger in step and makes it easy to read the ledger as of any moment. The analogy breaks in one place: in a league, a result is known the moment the match ends, while a feature value appears only after a pipeline processes it, minutes or hours later, and that delay must be respected too.

A training platform builds on this: pipelines that generate a point-in-time training set, train, evaluate and register a model with everything needed to reproduce it, then deploy it to serving where it reads features from the online store. A reader who stops here has the right picture; the rest is the arithmetic and the time-handling details where systems actually break.

1 · Requirements

Functional. Data scientists define features in code (a source, an entity key, a transformation, a schedule or a stream, a TTL) and register them with owners and descriptions. The platform materialises them to the offline and online stores, serves online lookups to model services, generates point-in-time correct training sets for a given label table, backfills history for new features, and lets users search and reuse features. The training platform runs pipelines (dataset generation, training, evaluation), tracks experiments, registers models with lineage and promotes them through stages to serving. Out of scope, said aloud: the model-serving runtime itself and the labelling tools.

Correctness targets. Training sets are point-in-time correct by construction (no feature value later than the label's timestamp minus the feature's availability delay). Online values for an entity match the offline recomputation for the same time on at least 99.9% of sampled lookups per feature, or an alert fires.

Latency and freshness targets. Online lookups p99 under 10 ms for up to five entity records per request. Streaming features fresh within 30 seconds at p99; batch features as configured (hourly or daily), with alerts when a materialisation is late.

Cost targets. Online storage sized for the entities actually served (TTL expires inactive entities); offline history retained per feature as needed for training windows, not forever by default.

Governance targets. Every feature has an owner, lineage to its sources, and a sensitivity tag; access to personal-data features is controlled; deletion requests propagate to both stores within the legally required time.

Clarifying questions. "How many models and teams, and how much feature reuse?" "Which models need online features and at what latency?" "How fresh must the freshest features be?" "Is there an existing warehouse and stream processor we must build on?"

2 · Back-of-envelope estimates

Scale. 200 models in production across 30 teams; 15,000 registered features over five entity types; the largest entity is 100 million users with about 150 features each, then 5 million merchants (or items) with about 80 features.

Online store size. Users: 100M × 150 × 8 bytes = 120 GB of values. Per-entity overhead (key, record header, serialisation, a version and timestamp per feature group) of about 100 bytes adds 10 GB. Merchants: 5M × 80 × 8 = 3.2 GB. Total about 133 GB; with three replicas about 400 GB. That fits in the memory of a small cluster, or on SSD-backed key-value nodes with a memory cache. Capacity is not the constraint; read rate and tail latency are.

Online read rate. Peak 50,000 predictions per second across models, each reading about four entity records (a user, a merchant, a device, a card): 200,000 key reads per second. Records are read in one parallel round trip, so a prediction's feature latency is the slowest of four reads. If one node handles about 25,000 reads per second comfortably at low tail latency, that is 8 nodes for reads, so with three replicas the cluster is sized at 9-12 nodes, set by read rate.

Streaming writes. 300,000 raw events per second (payments, logins, clicks) feed streaming features. Aggregating within short windows (each entity's counters updated once per second at most, rather than once per event) reduces online writes to about 60,000 per second, each a small update to one entity record. Each update is also appended to the offline log of feature values: 60,000 × 86,400 ≈ 5.2 billion feature-value rows per day, about 100 bytes each compressed, about 520 GB per day.

Offline history. Batch features are snapshotted daily: 100M users × 150 × 8 bytes = 120 GB per day uncompressed, about 30 GB in a compressed columnar format. A year of daily snapshots is about 11 TB, plus the streaming value log (about 190 TB a year at 520 GB a day, typically kept for 90 days, about 47 TB). Storage in a data lake is cheap; the cost to watch is the compute of joins over it.

Training-set generation. A fraud model's label table has 1 billion transactions over 90 days, and the model uses 300 features from five feature views. The point-in-time join scans the label table and the relevant feature history, sorted by entity and time: about 1B rows × 300 features × 4 bytes = 1.2 TB of output, a few hours on a medium Spark cluster. That is the job the platform must make routine, incremental (reuse yesterday's work) and correct.

The insight to say out loud. The online store is small and the offline store is large, but the hard engineering is neither size: it is making the two agree, in time, which is a correctness problem.

4 · API

# definition (registered from code)
FeatureView(name="card_velocity", entity="card_id",
            source=Stream("payments"), ttl="2h",
            features=[Count("payments", window="10m"), Sum("amount", window="1h"),
                      CountDistinct("merchant_id", window="1h")],
            owner="risk-team", tags=["pii:none"])

# serving
get_online_features(features=["card_velocity:*", "merchant_profile:risk_score"],
                    entities={"card_id": "c_91", "merchant_id": "m_7"})
  -> {"card_velocity:count_payments_10m": 3, ..., "merchant_profile:risk_score": 0.12}

# training
get_historical_features(labels=table("fraud_labels"),     # entity ids + event_timestamp
                        features=[...], as_of="availability")  -> training table
materialize(view, start, end)    # batch recompute or backfill

The key property is that serving and training reference features by the same names, which resolve to the same definitions, so a model's feature list works unchanged in both paths. The training call takes a label table with timestamps and returns one row per label with every feature as of that timestamp.

5 · Data model

Registry: feature views (entity, source, transformation code reference, schedule or stream, TTL, owner, tags, version), entities (name, key type), models (which features they use, by version). Online store: key = (feature view, entity ID); value = the latest values of that view's features plus each value's event time and the time it was written. Offline store: per feature view, a table of (entity ID, event time, availability time, feature values), partitioned by date, sorted by entity and time within partitions. Logs of served values: (request ID, model, entity, timestamp, feature values) sampled for skew checks and optionally complete for log-and-train models. Training platform: datasets (label table reference, feature list and versions, as-of mode, snapshot location), runs (code version, config, metrics), registered models (artefact, lineage, stage).

Two timestamps per value is the detail that matters. Event time is when the underlying thing happened (the payment at 10:00:03). Availability time is when the value became readable by serving (10:00:05 for a streaming feature, 02:00 the next night for a daily batch job). Training must use availability time to be honest about what serving could have known.

6 · High-level design

Feature definitions live in a repository, reviewed like code, and are registered on merge. The orchestrator schedules batch materialisation jobs (Spark or warehouse SQL) that read sources, compute values for each entity, write a snapshot to the offline store and bulk-load the latest values to the online store. Streaming jobs (Flink, or Samza at Uber) consume the event log, maintain windowed aggregates per entity, update the online store and append each update to the offline value log. Model services call the online serving API through an SDK that maps feature names to keys, reads records in parallel, applies on-demand transformations and returns a vector. The training platform calls the historical API to build datasets, trains on a compute cluster (GPUs where needed, dl9), evaluates, registers the model with lineage and promotes it via deployment gates. A monitoring service tracks freshness, data quality and online/offline skew.

7 · Deep dive: one definition, three ways to compute

Features fall into three kinds by how fresh they must be. Batch features change slowly (a restaurant's average preparation time over seven days, an account's age, a user's lifetime spend) and are recomputed on a schedule from the data lake. Streaming features change quickly (payments on this card in the last ten minutes, the average preparation time over the last hour) and are maintained by a stream processor. On-demand features depend on the request itself (the distance between the delivery address and the restaurant, the hour of day in the user's time zone) and are computed at request time, possibly combining stored values with request data. Uber's delivery-time model in Michelangelo used all three: request features, a seven-day batch average and a one-hour near-real-time average.

The rule that prevents skew is that each feature has one definition that every path executes. For batch features, the same job writes the offline snapshot and the online bulk load, so the values are identical by construction (Michelangelo says its batch system "guarantees that the same data and batch pipeline is used for both training and serving"). For streaming features, the streaming job writes online and logs the same values offline. For on-demand features, the transformation code is a registered function that the serving SDK calls at request time and the training pipeline calls on historical request data. What must never happen is a second implementation in a different language "for performance" without a parity test.

8 · Deep dive: point-in-time correct training data

A training example is a moment: a payment at 14:02 on 3 March, labelled fraud weeks later. The model will be used at the moment of a payment, with features as they are then. So each training row must contain each feature's value as it was available at 14:02 on 3 March. The operation is an as-of join: for each label row, find, for each feature view, the row for the same entity with the largest availability time at or before the label's timestamp; if that row is older than the view's TTL, treat the feature as missing (the same rule serving applies when a value has expired).

The leak in numbers. The lab builds 13,672 synthetic transactions with 98 frauds. A feature "disputes filed so far" joined naively (today's value) scores an AUC of 0.975 as a fraud predictor; joined as-of the transaction time it scores 0.657. Only 3% of rows differ between the two joins, yet that 3% includes almost every fraud, because the disputes caused by the frauds are exactly the leaked information. A model trained on the naive join would learn to rely on a signal it never has in production.

Doing it at scale. For a billion label rows and several feature views, the join is a distributed sort-merge: partition labels and feature rows by entity ID, sort each partition by time, and walk both sorted lists together, carrying the latest feature row seen so far for each entity. Warehouses and Spark offer as-of joins directly; Feast and similar tools implement this pattern. Optimisations: prune feature history to the label table's time range plus the TTL, and reuse previously generated training sets incrementally when only new labels were added.

Event time versus availability time. If a daily batch job computes "spend over the last 7 days as of 23:59 on 2 March" but the value lands in the online store at 02:00 on 3 March, a 01:30 prediction on 3 March still saw the 1 March value. Training with event time would use the 2 March value for that example, a small but systematic leak. Storing availability time and joining on it makes training see exactly what serving saw.

9 · Deep dive: the online store

Layout. One record per (feature view, entity), holding all that view's features: a model needing five views for four entities makes at most a handful of reads, issued in parallel. The drill below works through why one key per feature fails (reads, memory overhead, inconsistent partial updates). Group views by access pattern: features always read together belong in the same record.

Writes. Batch jobs bulk-load whole snapshots, ideally by writing new records with a version and switching readers atomically, so a model never reads a half-loaded mix of yesterday and today. Streaming jobs update individual records at high rates; the store must handle 60,000 small writes a second alongside 200,000 reads, which favours key-value stores built for that mix (Redis-like memory stores, or Cassandra/DynamoDB-style stores from in2; Michelangelo used Cassandra).

Freshness and TTL. Each value carries its event and write times; the SDK applies the view's TTL and returns "missing" (with the same default the training data used) when a value is too old. Freshness is monitored per view: the age of the newest written value and lag between event time and write time.

Hot keys and caching. A few entities (a large merchant, a popular item) are read far more than others. A process-local cache with a short expiry in the serving SDK, for small entity types, removes most of those reads; the drill's merchant set is 0.5 GB, small enough to cache entirely.

10 · Deep dive: streaming features and backfills

A streaming feature such as "payments on this card in the last 10 minutes" is a windowed aggregate maintained by a stream processor (sc18). Two subtleties decide correctness. Events arrive late and out of order (a mobile client was offline), so windows are defined on event time and the processor uses watermarks, its estimate of how far event time has progressed, to decide when to finalise a window, with a policy for events later than that. And the processor can restart, so updates must be idempotent or use exactly-once state, or counts will drift.

A new streaming feature has no history: it has been computed only since it launched. To train on it, run a backfill: replay months of raw events from the data lake through the same aggregation logic in batch mode, producing the feature's historical values with event and availability times (availability set to event time plus the typical streaming delay). Michelangelo described exactly this, a tool to "backfill" near-real-time features by running a batch job against historical logs to avoid a cold start. The key requirement is that the backfill runs the same logic as the streaming job; frameworks that compile one definition to both a streaming and a batch execution make this tractable, while hand-written duplicates drift.

11 · Deep dive: monitoring data and skew

Data quality. Every materialisation is validated before it is published: schema (types, required fields), null rates, value ranges and distributions compared with recent history. Google's data validation work (Breck et al.) describes this schema-and-anomaly approach for catching broken upstream tables before models consume them. A failed check blocks the online load and alerts the owner, keeping yesterday's values in place.

Freshness. Per view: time since the last successful batch load, and streaming lag. A stale view silently serves old values while the model assumes they are current, so freshness alerts are as important as error alerts.

Online/offline skew. Sample a fraction of served lookups and log the values the model actually received, with timestamps. Offline, recompute those features for the same entities and times through the training path, and compare: share of exact matches, mean absolute difference, null-rate differences, per feature. A mismatch spike points to a broken pipeline, a defaulting bug or a backfill that diverged from the live logic. This is the dashed loop in the architecture figure.

Drift. Compare each feature's serving distribution with its distribution in the model's training set; large drift does not always mean a bug (the world changed) but it tells model owners to evaluate and perhaps retrain.

12 · Deep dive: the training platform

Pipelines. A training pipeline is a graph of steps: build the training set (historical features for a label table), validate it, train, evaluate on held-out time ranges, compare with the production model, register. An orchestrator runs it on a schedule (continuous training) or on demand, retrying failed steps and caching unchanged ones.

Reproducibility. The registry stores, with each model, the dataset definition (label table version, feature view versions, as-of mode) or an immutable snapshot of the dataset, the code commit, the container image, hyperparameters and seeds, and the evaluation results. A model can be rebuilt, compared and audited; rolling back restores a known artefact. This is what turns "the model from last spring" from folklore into a lookup.

Deployment gates. A newly trained model is promoted only if it beats the production model on agreed offline metrics by a margin, passes fairness and calibration checks, and shows no feature unavailable online (every feature it uses must exist in the online store for the serving entities). Then shadow scoring, then an A/B test or a staged rollout, as in ae7 and in10.

Compute. Most tabular models (gradient-boosted trees) train on CPUs in minutes to hours; deep models need GPU scheduling (dl9). The platform provides quotas per team and a queue, and records cost per training run so teams see what retraining frequency costs.

13 · Evaluation plan

The platform is evaluated by whether it is correct, fast and used. Correctness: an automated point-in-time test suite (synthetic entities with known histories, asserting that historical retrieval returns exactly the expected as-of values, including TTL and availability-delay edge cases); online/offline parity at or above 99.9% per feature on sampled lookups; backfill parity tests comparing backfilled values with values the live streaming job produced for an overlapping period. Performance: online p99 latency per feature view and per client; materialisation lateness; training-set generation time per billion rows. Value: number of features reused by more than one model, time from feature idea to production model, and, for important models, the offline-to-online gap (the difference between offline and A/B-measured gains should shrink once point-in-time correctness is enforced).

14 · Failure modes and trade-offs

Leaky training data from a hand-written join that bypassed the platform; detected by large offline-online gaps; prevented by making the platform's historical API the easy path. Stale online features after a failed batch load or a stuck stream; detected by freshness alerts; mitigated by TTLs so models see "missing" rather than very old values. Divergent backfills, where backfill code differs from the live streaming code; detected by overlap parity tests. Upstream schema changes that break pipelines or, worse, silently change meanings; caught by validation. Hot keys in the online store; caches and replicas.

The trade-offs: freshness against cost (streaming everything is expensive), flexibility against consistency (letting teams write custom serving code is fast and breeds skew), retention against cost and privacy, a central platform team against teams' autonomy, and buy against build: open-source frameworks such as Feast provide the definition and retrieval layers on top of existing stores, while the hard organisational work (definitions, ownership, monitoring) remains yours.

Why availability time is the honest clock

Event-time joins are the textbook answer, and they are still subtly wrong for serving-oriented training. Serving reads whatever is in the online store at prediction time; that store holds values written after processing delays. If the training join uses event time, it gives every example values slightly fresher than serving ever had, and the model learns to rely on freshness it will not get, a leak whose size depends on the pipeline delay. For a daily batch feature, that delay is up to a day; for fraud signals that change hourly, it matters. Recording the write (availability) time on every value and joining on it removes the leak; when that is not possible for historical data, add a conservative delay to event time.

Log-and-train versus compute-and-join

There are two ways to get training features. Log-and-train records the exact features served with each prediction and trains on the logs (hd3 used this). It is skew-free by construction, but a new feature has no logged history and must wait or be backfilled, and only predictions that were actually made have features (no counterfactual rows). Compute-and-join builds features for any label table from history using point-in-time joins; it supports new features and new label definitions immediately but depends on the definitions and backfills being right. Mature platforms do both: log served features for parity checks and for models that need exactness, and use point-in-time joins for exploration and new features.

Windows, sketches and the cost of exact aggregates

A "distinct merchants in the last hour" feature needs the set of merchants seen per card per window, which is memory-hungry at scale. Sketches such as HyperLogLog (in9) give approximate distinct counts in a few hundred bytes per entity; sliding windows are approximated with fixed buckets (60 one-minute buckets for an hour). These approximations must be identical in the streaming path and the backfill path, which is another reason to compile one definition to both rather than writing two implementations. An approximate feature computed the same way everywhere is far better than an exact one computed two ways.

Entity resolution and keys

Features are only as good as their keys. A user may have several device IDs, an email change, a merged account; a merchant may have several store IDs. If the payments stream keys a feature by one identifier and serving looks it up by another, the lookup returns nothing and the model sees a default value, silently. Key mappings belong in the registry as first-class entities with documented resolution rules, and serving should track lookup miss rates per view, because a rising miss rate is usually a key problem, not a data problem.

Feature reuse and its hidden coupling

Reuse is the economic argument for a feature store, and it creates coupling Sculley et al. warned about: a feature's owner changes its definition to improve their model and silently changes every other model that consumed it. The defence is versioning: a feature view's definition is immutable once published, changes create a new version, consumers pin versions, and the registry knows which models use which versions, so an owner can see the blast radius before deprecating one. Undeclared consumers (someone reading the online store directly) defeat this, which is why direct store access is closed and all reads go through the SDK.

Training-set generation as an incremental computation

Regenerating a 90-day training set every day repeats 89 days of identical work. Partitioning the label table by day and caching each day's joined output (keyed by label partition and the feature-view versions used) lets daily retraining compute only the new day, unless a feature definition changed. The cache key is the reproducibility record: if any input version changes, the partition is recomputed. This turns a multi-hour job into minutes and makes daily continuous training affordable.

How it fails in practice

The 0.97 that was really 0.7. The opening story is the canonical failure: a hand-written training query read current values instead of as-of values. Symptoms: a large and persistent gap between offline metrics and online A/B results, and features with suspiciously high importance. The fix is routing every training set through the platform's historical API and rejecting registrations whose datasets did not come from it.

The silent default. A streaming job stopped for a region after a configuration change; the online store's values expired by TTL, and the SDK returned the default value, zero, which the model had seen in training only for brand-new cards. Every card in that region looked new, and fraud scores shifted. Freshness alerts per view and per region, plus monitoring of default-value rates, catch this in minutes.

The backfill that disagreed. A data scientist backfilled a new streaming feature with a SQL query that handled late events differently from the Flink job. Offline the feature looked strong; in production its values were systematically lower. An overlap parity test (compare backfilled and live values for the same week) would have caught it before training.

The half-loaded snapshot. A batch bulk load failed midway; half the users had today's values and half yesterday's, and a model combining features from two views saw inconsistent pairs. Versioned loads with an atomic switch prevent it.

What to monitor

Per feature view: materialisation success and lateness, streaming lag, online p50/p99 latency, lookup miss and default rates, null rates and distribution checks, online/offline parity rates. Per model: features used and their versions, training-set generation time, offline-online metric gap after launch. Platform: storage growth, cost per view, number of consumers per feature.

The real case: Uber's Michelangelo

Uber's 2017 post "Meet Michelangelo" by Mike Del Balso and Jeremy Hermann describes the internal machine learning platform that made the feature store a standard idea. Its data management was split into offline pipelines, feeding batch training and prediction from an HDFS data lake via Spark and Hive, and online pipelines feeding low-latency predictions from Cassandra. Online features came two ways: batch precompute, bulk-loading historical features from HDFS into Cassandra "every few hours or once a day", which "guarantees that the same data and batch pipeline is used for both training and serving"; and near-real-time compute, publishing metrics to Kafka and running Samza streaming jobs whose aggregates are written to Cassandra for serving and "logged back to HDFS for future training jobs", with a tool to backfill these features from historical logs to avoid a cold start. The shared Feature Store held about 10,000 features at the time, calculated and updated daily, and a Scala-based domain-specific language ensured the same feature selection and transformations at training and prediction time. Serving latency was typically p95 under 5 ms for models without Cassandra features and under 10 ms with them, and the busiest models served more than 250,000 predictions per second. The UberEATS delivery-time model used request features, a seven-day average preparation time from the batch path and a one-hour average from the near-real-time path. The interview lessons are the ones this lesson builds on: one pipeline for both paths, streaming values logged back for training, backfills for new features, and a transformation layer shared between training and serving.

Goal: see a point-in-time leak with your own eyes. The script builds synthetic transactions and a feature, "disputes filed so far" on the user, whose value increases when a dispute is filed 5-40 days after a fraudulent transaction (and an hour later still, when the batch pipeline lands it). It then builds training rows two ways, a naive join that reads each user's latest value and an as-of join that reads the value available at the transaction time, and measures how well the feature predicts fraud under each. Python 3.12, standard library only; runs in under a second.

  1. Save as pit_join.py and run python pit_join.py.
  2. Compare the two AUC values. The naive one is what a leaky notebook would report; the as-of one is what the model can achieve in production.
  3. Read the share of rows that differ between the joins: small, yet enough to transform the metric, because the leaked rows are concentrated on the frauds.
  4. Set PIPELINE_DELAY to 0 and to several days and see how much the availability delay matters for this feature (little here, because disputes come weeks later; much more for fast-changing features).
  5. Change the dispute delay from 5-40 days to 0-1 days: the naive AUC barely moves. However soon the dispute is filed, it is still filed after the transaction, so only the as-of join removes the leak; speed of the future does not make it the past.
"""Point-in-time correctness: build training rows with a naive 'latest value' join
and with an as-of join, and see the leak. Python 3.12, stdlib only."""
import bisect, random
from collections import defaultdict

rng = random.Random(11)
DAY = 86_400
users = [f"u{i}" for i in range(3_000)]
risky = {u for u in users if rng.random() < 0.05}           # a hidden trait

# 1) Label events: transactions over 60 days; risky users commit fraud more often.
txns = []                                                   # (user, ts, is_fraud)
for u in users:
    for _ in range(rng.randint(1, 8)):
        ts = rng.uniform(0, 60 * DAY)
        p = 0.08 if u in risky else 0.004
        txns.append((u, ts, rng.random() < p))

# 2) Feature history: 'disputes filed so far' (lifetime count). A dispute is filed
#    5-40 days AFTER a fraudulent transaction. Feature rows carry the time the value
#    changed (event_ts) and the time the pipeline made it available (avail_ts).
history = defaultdict(list)                                 # user -> [(avail_ts, value)]
for u, ts, fraud in txns:
    if fraud:
        filed = ts + rng.uniform(5, 40) * DAY
        history[u].append(filed)
# risky users also had some disputes before the window (real, legitimate signal)
for u in risky:
    for _ in range(rng.randint(0, 2)):
        history[u].append(-rng.uniform(1, 300) * DAY)
PIPELINE_DELAY = 3600                                       # batch job lands an hour later
feature = {}
for u, times in history.items():
    times.sort()
    feature[u] = ([t + PIPELINE_DELAY for t in times], list(range(1, len(times) + 1)))

def value_latest(u):                                         # what a naive join reads today
    return feature[u][1][-1] if u in feature else 0

def value_as_of(u, ts):                                      # point-in-time (as-of) join
    if u not in feature:
        return 0
    avail, vals = feature[u]
    i = bisect.bisect_right(avail, ts)                       # last value available at ts
    return vals[i - 1] if i else 0

def auc(scores, labels):                                     # rank-based AUC with ties
    pairs = sorted(zip(scores, labels))
    rank, i, pos_rank_sum = 1, 0, 0.0
    while i < len(pairs):
        j = i
        while j < len(pairs) and pairs[j][0] == pairs[i][0]:
            j += 1
        avg = (rank + rank + (j - i) - 1) / 2
        pos_rank_sum += avg * sum(l for _, l in pairs[i:j])
        rank += j - i; i = j
    P = sum(labels); N = len(labels) - P
    return (pos_rank_sum - P * (P + 1) / 2) / (P * N)

labels = [int(f) for _, _, f in txns]
naive = [value_latest(u) for u, _, _ in txns]
pit = [value_as_of(u, ts) for u, ts, _ in txns]
print(f"{len(txns):,} transactions, {sum(labels)} fraud")
print(f"AUC of 'disputes so far' with naive latest-value join: {auc(naive, labels):.3f}")
print(f"AUC of 'disputes so far' with point-in-time join:      {auc(pit, labels):.3f}")
leaked = sum(1 for a, b in zip(naive, pit) if a != b)
print(f"rows where the naive join used a value from the future: {leaked:,} ({leaked/len(txns):.0%})")
# At serving time the model only ever sees as-of values, so the honest estimate is the PIT one.

Expected output: about 13,700 transactions and about 100 frauds; naive-join AUC about 0.97; as-of AUC about 0.66; about 3% of rows read a future value. The as-of join is implemented with bisect over each entity's sorted availability times, which is the same logic a distributed as-of join runs per entity partition.

Work it out

You are designing the online store for a fraud model: 40M users, 120 features per user averaging 8 bytes each, plus 30 merchant features across 2M merchants. Peak 12,000 predictions/s, each needing one user and one merchant. Latency budget for feature fetch: 15 ms at p99.

(a) How much memory? (b) What is the read pattern and QPS? (c) A colleague suggests one Redis key per feature for flexibility. Evaluate.

Answer

(a) Memory. Users: 40M × 120 × 8 = 38.4 GB of raw values. Merchants: 2M × 30 × 8 = 0.48 GB. Add key overhead and serialisation — Redis costs roughly 50–100 bytes per key beyond the value — so with one key per entity the overhead is 40M × ~80 B ≈ 3.2 GB. Call it ~45 GB, which needs a small cluster (3–6 nodes) for headroom and replication, not a single instance. Worth stating: this comfortably fits in memory, so the design is bounded by operations, not capacity.

(b) Read pattern. One user read plus one merchant read per prediction = 24,000 reads/s, issued as two parallel round trips so the latency is max of the two, not the sum. At ~1 ms per Redis round trip within a datacentre, you spend ~1–2 ms of the 15 ms budget, leaving plenty for deserialisation and the model. The merchant working set is tiny (0.5 GB) and heavily skewed toward popular merchants, so a process-local LRU cache in front of it removes most merchant reads entirely.

(c) One key per feature — evaluate. It sounds flexible and it is a serious mistake at this scale:

  • Reads explode. 150 keys per prediction instead of 2 → 1.8M reads/s rather than 24,000. Even pipelined, the per-key overhead and the cross-slot behaviour in a Redis cluster make p99 latency unpredictable, and a single slow shard now delays every prediction rather than one.
  • Memory nearly doubles. 40M × 120 = 4.8 billion keys at ~80 B of overhead each is hundreds of gigabytes of pure overhead, dwarfing the 38 GB of actual data.
  • Atomicity is lost. With one blob per entity the 120 features are written together and are mutually consistent. With 120 keys, a prediction can read a mix of pre- and post-update values — a skew bug that is nearly impossible to reproduce.

The right design: one key per entity holding a serialised struct of all its features, grouped by access pattern rather than by producer. If different models genuinely need disjoint feature subsets, split into a small number of column-family-style blobs (say "profile", "velocity", "risk") — two or three reads, not 150. And the flexibility the colleague wants is real but belongs at the definition layer: adding a feature should be a schema change to the blob, handled by versioning the serialisation, not a new key per feature.

Diagnose it

A team's new churn model uses a feature "support tickets in the last 30 days". Offline AUC is 0.88; in a two-week A/B test, the model is no better than the old one (offline 0.80). The feature comes from a daily batch job that runs at 03:00 and reads the ticket system's export, which lands at about 01:00. Labels are "churned within 30 days of the prediction date", and training rows were built with an as-of join on event time. Where could the gap come from?

Answer

Availability delay. The job computes the feature as of midnight, but its value is only available in the online store after about 03:30. Predictions made between midnight and 03:30 used the previous day's value; training (joined on event time) used the fresher one. For a daily feature that is a modest leak, worth fixing by joining on availability time.

Label leakage through the feature. More likely: customers who decide to leave often open "cancel my account" tickets. If the label window starts at the prediction date and the training join (or the export) includes tickets created later that day or backdated by the ticket system's export, the feature contains the beginning of the churn itself. Check the ticket export's timestamps (creation time versus last-updated time; exports often use last-updated) and compare the feature's offline distribution for churners with values logged at serving.

Skew. Compare served values (logged in the A/B test) with offline recomputation for the same users and dates. If the online values are systematically lower, the online load may be missing tickets from one channel. The cure in every case is the same discipline: availability-time joins, event timestamps that mean creation, and parity checks before trusting an offline gain.
