Picture a growing AI product. Every time a user sends a prompt, five different teams want to know about it. Billing needs the token counts. The evaluation team wants to sample conversations to score answer quality. Trust and safety wants to scan for abuse. The data platform wants everything in a warehouse for analysis. And the product team wants a live dashboard of requests per minute. The first version of this is always the same: the API server, after answering the user, makes five calls — one to each team's service.

It goes wrong within weeks. The safety service has a slow afternoon, and because the API server waits on it, user-facing latency climbs. The billing service is down for a deploy, and those calls are simply lost: customers get free tokens. The evaluation team realises their scoring had a bug for three days and wants to re-score that traffic, but nobody kept it. A sixth team arrives and the API server needs yet another code change. Every producer is wired to every consumer, every failure leaks across the wires, and the data disappears the moment it has been delivered.

What the system needs is one place to write each event once, durably, in order, and let any number of readers consume it at their own pace — including readers who show up next month and want to start from the beginning of last week. That place is a distributed log, and Apache Kafka is the design everyone means when they say "message queue" in a large-scale system design interview. LinkedIn built it in 2010–2011 for exactly this kind of problem: activity events and operational metrics that many systems, online and offline, needed to read.

This lesson designs it from scratch in interview order. You will scope the requirements, estimate throughput and storage by hand, define a small API and the on-disk data model, and draw the architecture. Then come the deep dives interviewers push on: how partitions and keys decide ordering and parallelism, how offsets and consumer groups work, how replication with the in-sync replica set and the high watermark keeps acknowledged data safe, and what "exactly once" really means. We finish with failure modes, the original Kafka paper's measurements, and a small Python lab you can run.

The idea that makes Kafka different

A traditional message queue works like a to-do list on a shared whiteboard. A worker takes a task, does it, and wipes it off. The broker — the server in the middle — remembers which messages are waiting, which are being worked on, and which are done, for every single message. One message, one consumer, then it is gone.

Kafka works like a ship's logbook. Entries are only ever added at the end, numbered in order, and never erased because someone has read them. Anyone may read the logbook. Each reader keeps their own bookmark — "I've read up to entry 4,812" — and the logbook does not care where anyone's bookmark is. A new reader can start from the first page; a reader who misread something can flip back. Old pages are torn out only when the logbook gets too thick (after, say, seven days), regardless of who has read them.

That is the whole trick: the broker stores, the consumer bookmarks. Because the broker keeps no per-message, per-consumer delivery state, adding a tenth reader costs it almost nothing, and the data stays available for replay.

Where the analogy breaks: one logbook would be a bottleneck, so Kafka splits each stream into many logbooks — partitions — on different machines, and keeps copies of each on several machines so a fire in one cabin loses nothing. Those two ideas, partitioning and replication, are where nearly all the interesting design lives.

The vocabulary, in the order you need it

A record (or message) is one event: an optional key (for example a user ID), a value (the payload bytes, often JSON or a compact binary format), a timestamp and optional headers. A topic is a named stream of records, like llm-calls or orders. A producer is any program that writes records; a consumer is any program that reads them. A broker is one Kafka server; a cluster has several.

A topic is divided into partitions. Each partition is an independent, ordered, append-only log stored on one broker (plus copies). Every record in a partition gets an offset: its position number, starting at 0 and going up by one per record, never reused. The producer chooses the partition, normally by hashing the key, so every record with the same key lands in the same partition — and therefore stays in order relative to the others with that key. Ordering is guaranteed within a partition and nowhere else. That one sentence answers half the follow-up questions in this interview.

A consumer group is a set of consumers that share the work of reading a topic. Each partition is assigned to exactly one consumer in the group at a time, so the group as a whole reads every record once, and the number of partitions caps how many consumers can be busy. A different group — billing versus evaluation, say — reads the same records completely independently with its own offsets.

Finally, the replication factor is how many copies of each partition exist. One copy is the leader, which takes all writes; the others are followers, which copy the leader. Followers that are caught up form the in-sync replica set (ISR). Durability is defined against the ISR, and that subtlety will matter a great deal in the deep dive.

The mental model to carry into the interview

Kafka is best described as a distributed, replicated, partitioned commit log. A database already has a log like this internally — the write-ahead log, where every change is appended before it is applied, and which replicas copy to stay in sync. Kafka takes that internal structure and offers it as a product. Once you see it that way, the design choices stop looking arbitrary: appends are sequential and therefore fast; immutable records are easy to copy and cache; and because consumers track their own position, the broker never has to remember who has seen what. Everything else in this lesson — keys, consumer groups, the in-sync replica set, transactions — is a consequence of taking that log and spreading it over many machines safely.

1 · Requirements

Functional. Producers publish records to named topics. Consumers subscribe to topics and read records at their own pace. Several independent applications can read the same topic. A consumer can rewind to an earlier position and reprocess. Records are retained for a configurable period (days) or until a size limit, whether or not they have been read. Records with the same key are delivered in the order they were written.

Non-functional. High throughput: around a million records per second at peak. Low latency: a few milliseconds to publish, tens of milliseconds from publish to consume. Durability: once the system acknowledges a write, it must not be lost, even if a broker dies. Availability: a single broker failure should cost seconds of disruption, not data and not hours. Horizontal scalability: more brokers, more throughput.

Out of scope, said aloud: stream processing (joins and windows — that is Flink or Kafka Streams running on top of the log), schema management, connectors to databases, and cross-region replication (we will mention it at the end).

The clarifying question that changes the design: "What ordering do you need?" If the answer is "every record in the topic in one global order", the honest answer is that this means one partition, one writer path and one reader per group — no parallelism. Almost always the real need is per-entity ordering: all events for one user, one order, one conversation in sequence. That is what keys and partitions give you, and it drives the entire partitioning scheme. The second question is about delivery: "Is a duplicate worse than a loss, or the other way round?" Billing can tolerate a duplicate if it deduplicates by request ID, but cannot tolerate a loss; a live dashboard tolerates both.

2 · Back-of-envelope estimates

Use the AI-product scenario: every LLM call produces one event. Assume 400,000 records per second on average and 1,000,000 at peak across all topics, an average record of 1 KB (1,000 bytes, after compression), replication factor 3, 7 days of retention, and 3 consumer groups reading everything.

Daily volume. 400,000 × 86,400 seconds = 34.56 billion records per day, about 35 billion. At 1 KB each that is 34.56 TB of new data per day before replication.

Ingest bandwidth at peak. 1,000,000 × 1 KB = 1 GB/s arriving from producers. Each byte is written to the leader and copied to two followers, so the cluster writes 3 GB/s to disk and moves 2 GB/s between brokers for replication.

Egress at peak. Three consumer groups each read everything: 3 × 1 GB/s = 3 GB/s out to consumers. Total outbound from brokers is 3 GB/s to consumers plus 2 GB/s to followers = 5 GB/s.

Storage. Retention is driven by the average rate: 400 MB/s × 604,800 seconds (7 days) = 241.9 TB per copy, and × 3 copies = about 726 TB. This number, not throughput, will decide the broker count.

Partitions. Partition count must satisfy two things. Throughput per partition is rarely the limit — a partition can take tens of MB/s. The real limit is consumers: suppose the billing consumer does real work (parses, aggregates, writes to a database) at 5,000 records per second per instance. Peak 1,000,000 ÷ 5,000 = 200 consumer instances needed, and since each partition feeds one consumer in a group, the topic needs at least 200 partitions. Partitions can be added but never removed, and adding them remaps keys, so add about 20% headroom: 240 partitions.

Brokers. Suppose each broker has 12 disks of 8 TB (96 TB raw) and we keep disks at most 60% full so there is room to move partitions when a broker dies: 57.6 TB usable each. 726 ÷ 57.6 = 12.6, so at least 13 brokers for storage. Check the network: spread over 16 brokers, each broker sends (2 + 3) ÷ 16 = 0.31 GB/s, about 2.5 Gbit/s, which is a fraction of a 25 Gbit/s network card, and writes 3 ÷ 16 = 0.19 GB/s to disk. So storage drives the size. Choose 16 brokers: one can fail and the other 15 hold 726 ÷ 15 = 48 TB each, half full. With 240 partitions × 3 replicas = 720 replicas, each broker holds 45 replicas and leads 15 partitions.

The insight to say out loud. Retention, not traffic, drives the cluster size. If we kept only 12 hours on brokers and moved older segments to object storage (tiered storage, covered in the deep section), local storage drops to 400 MB/s × 43,200 s × 3 = 52 TB, and the cluster could be sized by throughput instead — perhaps 6 brokers.

Memory. A consumer that is caught up reads records written seconds ago, which are still in the operating system's page cache. A consumer one hour behind reads 400 MB/s × 3,600 s = 1.44 TB of older data; spread across 16 leaders that is 90 GB each, more than a typical broker's spare memory. So a lagging consumer turns into disk reads — the most common cause of a "Kafka got slow" incident.

Coordination traffic. If every group commits its offsets every 5 seconds per partition: 240 partitions × 3 groups ÷ 5 s = 144 commits per second. Negligible.

3 · API

The interface is small, and it is worth writing down because it makes the "consumer tracks position" idea concrete:

produce(topic, key, value, headers) -> (partition, offset)
    # acks setting decides when this returns

fetch(topic, partition, from_offset, max_bytes) -> [records], high_watermark
    # pull, not push: the consumer asks for "from offset X"

commit(group, {partition: offset})      # "I have processed everything below offset"
committed(group, partition) -> offset    # where to resume after a restart

join_group(group, member_id, topics) -> assigned partitions
heartbeat(group, member_id)              # "I'm alive"; missing heartbeats trigger reassignment

Two design decisions hide here. First, consumption is pull-based: consumers ask for data from an offset, rather than the broker pushing. Pull lets each consumer go at its own speed, batch naturally (fetch up to 1 MB at a time), and rewind trivially — the 2011 paper notes that rewinding "is much easier to support in the pull model than the push model". Second, produce returns an offset, which is a natural unique ID for the record: (topic, partition, offset) identifies it forever.

4 · Data model: segments, indexes and batches

On a broker, each partition replica is a directory. Inside, the log is a series of segment files, each named after the first offset it contains: 00000000000000000000.log, 00000000000004812345.log, and so on. Producers' records are appended to the newest, active segment. When it reaches 1 GiB (the default segment.bytes) or a time limit, it is closed and a new one starts. Closed segments never change, which makes them trivial to replicate, cache, delete and upload elsewhere. Retention is just deleting whole old segment files — 7 days by default (retention.ms = 604,800,000) — which is far cheaper than deleting individual messages.

Next to each segment sit two small index files. The offset index maps an offset to a byte position in the segment, but sparsely: one entry roughly every 4 KB of log (index.interval.bytes = 4096). To serve "fetch from offset 4,812,900", the broker picks the segment by name (a binary search over file names), binary-searches the offset index for the nearest entry below 4,812,900, seeks to that byte position and scans forward a few kilobytes. The time index does the same for timestamps, which is how "rewind to yesterday 09:00" works.

Records travel and are stored in record batches: a header with the base offset, the leader epoch (explained below), a checksum (CRC) to detect corruption, the producer ID, producer epoch and base sequence number (used for deduplication), followed by the compressed records. The broker stores the batch exactly as the producer sent it. That one decision is what makes zero-copy serving possible later.

Consumer offsets are themselves stored in Kafka: an internal topic named __consumer_offsets (50 partitions by default), keyed by (group, topic, partition), with log compaction so only the latest committed offset per key is kept. The system eats its own cooking: a commit is just a produce.

5 · High-level architecture

Walk the picture from left to right. Producers fetch cluster metadata once (which broker leads which partition), batch records per partition for a few milliseconds (linger.ms defaults to 5 ms since Kafka 4.0, with batches up to 16 KB by default), compress the batch, and send it straight to the leader of that partition. There is no central router in the data path.

Brokers hold partition replicas. Leadership is spread so every broker leads roughly the same number of partitions. Each follower runs a loop that fetches new records from its leader — using the same fetch request a consumer uses — and appends them to its own log.

The controller holds the metadata: topics, partitions, which brokers hold replicas, who leads, and which replicas are in sync. It notices broker failures and elects new leaders. In modern Kafka this is a small quorum of controller nodes running the Raft consensus algorithm (called KRaft); originally Kafka delegated this to an external ZooKeeper cluster, and Kafka 4.0 removed ZooKeeper support entirely. (Raft gets its own treatment in in8; for now, it is a protocol that lets three or five nodes agree on an ordered log of metadata changes as long as a majority are alive.)

Consumers join a group, receive a set of partitions, fetch from each partition's leader starting at the group's committed offset, process records, and periodically commit new offsets to __consumer_offsets. A group coordinator — one of the brokers, chosen by hashing the group name onto a partition of __consumer_offsets — tracks membership through heartbeats and reassigns partitions when members come and go.

6 · Deep dive: partitions, keys and ordering

The default partitioner hashes the key with the murmur2 hash and takes the result modulo the partition count: partition = murmur2(key) mod 240. Records without a key are spread by a "sticky" partitioner that fills a batch for one partition, then switches, which gives good batching. Because the same key always maps to the same partition (as long as the count does not change), all records for user 42 are appended in one log in the order the producer sent them, and a consumer reads them in that order.

The partition is therefore the unit of three things at once: ordering (only within it), parallelism (one consumer per partition per group), and placement (one leader broker handles all of its writes). Every partitioning decision trades among them. More partitions give more parallelism, but each costs open files, memory buffers, replication fetches and leader-election work, and increases end-to-end latency slightly because batches fill more slowly.

The key choice is a domain question. Key by conversation ID when the order of turns in a conversation matters. Key by tenant when a consumer maintains per-tenant state. Key by request ID — effectively random — when order doesn't matter and you want perfectly even spread. The danger is skew: if one tenant produces 35% of all traffic and you key by tenant, 35% of all records go to one partition and one consumer, no matter how many partitions exist. The drill below works through exactly this.

Changing the partition count changes mod 240 to mod 300, so most keys move to a different partition. Records for user 42 written before the change sit in partition 17; records after it go to partition 133. A consumer group reading both partitions in parallel might process a new event for user 42 before an old one. That is why partition count is planned up front and why keyed topics are rarely resized casually.

7 · Deep dive: offsets, consumer groups and rebalancing

Within a group, assignment is the contract "each partition has exactly one owner". With 240 partitions and 200 consumers, 40 consumers own two partitions and 160 own one. With 300 consumers, 60 sit idle. Different groups never interact: billing's offsets and evaluation's offsets are separate rows in __consumer_offsets.

The committed offset means "this group has finished everything below this number in this partition". Consumer lag — the number to watch — is the partition's log end offset minus the committed offset. If billing's committed offset on partition 7 is 4,800,000 and the log ends at 4,812,000, billing is 12,000 records behind on that partition; at 5,000 records per second of processing that is 2.4 seconds of lag.

When the group changes — a consumer crashes, a new one is deployed, a consumer stops heartbeating because it is stuck — partitions must move. This is a rebalance. The original protocol was "stop the world": every member gave up all partitions, the group agreed on a new assignment, and everyone restarted, so one flapping consumer paused the whole group. Kafka then added cooperative incremental rebalancing, where only the partitions that need to move are revoked. Since Kafka 4.0, a new protocol (KIP-848, where KIP stands for Kafka Improvement Proposal, the project's numbered design documents) is generally available in which the broker-side coordinator computes the assignment itself and moves partitions incrementally, with no global synchronization barrier.

A subtle point interviewers like: a consumer that takes too long to process one batch — longer than max.poll.interval.ms, five minutes by default — is considered dead and its partitions are reassigned, even though its process is alive. When it finishes and tries to commit, the commit is rejected because it no longer owns the partition. Long per-record work (like an LLM call that can take a minute) needs smaller batches or a different consumption model.

8 · Deep dive: replication, the ISR and the high watermark

This is the part that separates strong answers. Each partition has a leader and, with replication factor 3, two followers. Each replica has a log end offset (LEO): the offset the next appended record would get. Followers fetch from the leader continuously; when a follower's fetch shows it has caught up to the leader's LEO, it counts as in sync. A follower that has not caught up for replica.lag.time.max.ms (30 seconds by default) is removed from the ISR, and added back when it catches up.

The high watermark (HW) is the smallest LEO among the ISR members: the highest point that every in-sync replica has. Records below the HW are committed — they would survive the loss of the leader — and consumers are only allowed to read below the HW. That rule is what stops a consumer from reading a record that might vanish in a failover.

A worked trace. The leader has LEO 106 after appending a batch of offsets 102–105. Follower F1 has fetched up to 106, but F2 is slow and has only 102. The ISR is {leader, F1, F2}, so HW = min(106, 106, 102) = 102. A producer using acks=all is waiting: its batch is acknowledged only when the HW passes 105. If F2 catches up, HW becomes 106 and the producer gets its acknowledgement. If F2 stays behind for 30 seconds, it is dropped from the ISR; the ISR is now {leader, F1}, HW jumps to 106, and the producer is acknowledged with two copies.

Now the producer's choice of acks:

The subtlety to volunteer. In the trace, if F1 also fell behind and was removed, the ISR would be {leader} alone, and acks=all would be acknowledged by one machine — no better than acks=1, and nobody would notice. The fix is min.insync.replicas: with it set to 2, the leader refuses acks=all writes with a NotEnoughReplicas error whenever the ISR is smaller than 2. The standard production setting is replication factor 3, min.insync.replicas 2, acks=all: one broker can be down (for a crash or a rolling restart) and writes still succeed with two durable copies; if two are down, writes fail loudly instead of silently weakening. Note the default min.insync.replicas is 1, so you must set it.

Why not a majority quorum like Raft for the data itself? The Kafka design documentation makes the comparison directly: to tolerate one failure, a majority quorum needs three replicas and waits for one follower's acknowledgement, and the ISR approach needs only two replicas, also waiting for one acknowledgement. The ISR model lets any in-sync replica become leader, so with f+1 replicas it tolerates f failures without losing committed records. The price is that the ISR membership itself must be agreed safely, which is the controller's job.

Leader failover, traced. The leader dies with LEO 110 and HW 106; records 106–109 were appended but not yet acknowledged. The controller picks a new leader from the ISR — say F1, whose LEO is 108 — and increments the partition's leader epoch, a counter of leadership terms. F1's records 106–107 become committed once the other replicas copy them. Records 108–109 existed only on the old leader; they were never acknowledged, so the producer will retry them. When the old leader comes back, it asks the new leader where epoch N ended (offset 108), truncates its own log at 108, and fetches from there. Leader epochs exist so this truncation is exact: earlier versions used the high watermark for it and could, in rare double-failure sequences, end up with replicas that disagreed.

9 · Deep dive: delivery semantics and exactly-once

On the consumer side, delivery semantics come down to the order of two actions: processing a record and committing its offset.

  • At-most-once: commit, then process. A crash after the commit but before processing skips those records. Acceptable for a live dashboard; rarely what you want.
  • At-least-once: process, then commit. A crash after processing but before the commit means the next owner of the partition starts from the old commit and reprocesses. This is the default and the right default.
  • Exactly-once: the effect of each record happens once even though delivery may repeat.

Take a concrete crash. A billing consumer commits every 100 records. It processes offsets 900 to 950 and crashes before committing 1,000. The replacement starts at the last commit, 900, so offsets 900–950 are processed twice — 51 duplicate billing increments. The lab reproduces exactly this. The 2011 Kafka paper already said it plainly: Kafka "only guarantees at-least-once delivery", and applications that care about duplicates "must add its own de-duplication logic".

Duplicates can also come from the producer. A producer sends a batch, the leader appends it, and the acknowledgement is lost on the network. The producer retries and, without protection, the batch is appended twice. The idempotent producer (default since Kafka 3.0) fixes this: the broker assigns each producer a producer ID, the producer numbers its batches per partition with a sequence number, and the broker remembers the last few sequence numbers per producer per partition. A retried batch with a sequence it has already written is acknowledged without being appended again. The same mechanism keeps ordering correct with up to five requests in flight: an out-of-order sequence is rejected and retried.

Transactions handle the consume-process-produce loop. Suppose a job reads from llm-calls, computes per-tenant cost, and writes to tenant-costs. To be exactly-once, the output records and the input offsets must commit together. The producer is configured with a transactional.id; a transaction coordinator (a broker) records the transaction's state in an internal topic; the producer writes output records to any partitions, then sends the consumed offsets to the coordinator as part of the same transaction, then commits. The coordinator writes a commit marker into every partition involved. Consumers configured with isolation.level=read_committed only return records from committed transactions, so an aborted attempt's output is invisible. If the job crashes mid-transaction, the restarted instance with the same transactional.id aborts the old transaction and resumes from the last committed offsets.

Where it stops. If the consumer instead writes to PostgreSQL or calls a payment API, Kafka's transaction cannot include that write. The pattern then is at-least-once delivery plus an idempotent effect: store the source (partition, offset) or the event's own unique ID with a unique constraint in the same database transaction as the business change, or upsert by a natural key. Say this explicitly; candidates who claim Kafka gives end-to-end exactly-once into any system have misunderstood the guarantee.

10 · Failure modes and trade-offs

A broker dies. The controller notices its session lapse, elects new leaders from the ISR for every partition it led, and publishes new metadata. Clients get "not leader" errors, refresh metadata and continue. Disruption is seconds. Replication factor 3 with min ISR 2 keeps accepting writes.

The whole ISR is lost. Then there is a choice: stay unavailable until an in-sync replica returns, or promote an out-of-sync replica and lose acknowledged records. This is called unclean leader election, it is off by default, and it is the consistency-versus-availability trade-off from the CAP discussion made concrete. Name a business owner for it: for billing, stay down; for click analytics, maybe accept the loss.

A consumer is slow or stuck. Lag grows. If it exceeds max.poll.interval.ms on one batch, it is kicked from the group and its partitions move, possibly to another consumer that also gets stuck on the same record — a poison message. Kafka does not provide per-record retries; you build a retry topic and a dead-letter topic with a bounded attempt count.

A hot partition. One key dominates. Symptoms: one partition's lag grows while others are flat; one broker's network is hot. Fixes trade ordering for spread.

Disk fills. Retention is time-based but traffic spiked; brokers hit full disks and stop. Monitor free disk and set size-based retention as a backstop.

The trade-offs to state in the close: per-partition ordering in exchange for parallelism; at-least-once plus idempotent consumers instead of a costly global exactly-once; durability (acks=all, min ISR 2) in exchange for one extra replication round trip of latency; and long retention in exchange for storage, which tiered storage makes cheaper.

11 · Close

Summarise in four sentences. The broker stores an immutable, partitioned, replicated log and keeps no per-consumer state. Keys pick partitions, partitions give per-key order and cap group parallelism. Acknowledged writes survive because of acks=all with min.insync.replicas and the high-watermark rule. Delivery is at-least-once with idempotent consumers, and exactly-once applies within Kafka-to-Kafka pipelines via idempotent producers and transactions.

Why sequential I/O, the page cache and zero-copy matter together

Kafka's speed comes from three choices that only work as a set. First, every write is an append to the end of a file. Disks — spinning or solid-state — are far faster at long sequential writes than at scattered small ones, because a spinning disk avoids seeks and an SSD avoids the write amplification of partial-page updates. Second, Kafka keeps no cache of its own. It writes into the operating system's page cache and lets the kernel flush to disk in the background; recent data, which is what caught-up consumers want, is served from memory. Because the broker's heap stays small, garbage-collection pauses stay small too. Third, when a consumer fetches, the broker uses the sendfile system call to move bytes from the page cache to the network socket inside the kernel. The 2011 paper counts the alternative as four data copies and two system calls; sendfile "typically avoids 2 of the copies and 1 system call". That is only possible because the broker stores the producer's batch byte-for-byte and never rewrites it. If you add per-message transformation in the broker, you lose zero-copy. (Encrypting connections with TLS also costs it, because data must pass through user space to be encrypted.)

Kafka does not fsync each message, and that is deliberate

By default, Kafka acknowledges a write once it is in the page cache of the ISR members, not once it is forced to physical disk; flush.messages defaults to effectively infinite. Durability comes from having the data in the memory of several machines in different failure domains, on the bet that they won't all lose power in the same few seconds before the kernel flushes. This is a real trade-off: a correlated power failure across a whole rack could lose recently acknowledged data. Spreading replicas across racks or availability zones (rack-aware replica placement) is what makes the bet safe. If an interviewer asks "is acks=all durable?", the precise answer is "durable against independent machine failures, with replicas spread across failure domains".

Partition count is close to irreversible

You can add partitions but not remove them, and adding them changes the key mapping, breaking per-key ordering across the change. So over-provision modestly at creation, guided by the consumer-parallelism calculation. Do not over-provision wildly: every partition replica holds open file handles (three files per segment), memory buffers on producers and consumers, and a replication fetch stream; and a broker failure requires electing a new leader for each partition it led. Thousands of partitions per broker are fine; hundreds of thousands per cluster were painful under ZooKeeper, which is part of why KRaft was built — controller failover no longer requires reloading all metadata from an external store.

Log compaction turns a topic into a table

Time-based retention deletes old segments. Compaction is different: a background cleaner rewrites old segments keeping only the latest record for each key. A record with a key and a null value is a tombstone meaning "delete this key", and tombstones themselves are removed after a retention period. A compacted topic is therefore a complete, replayable snapshot of current state: a new service can read it from offset 0 and rebuild a cache or a search index. __consumer_offsets is compacted this way. This is also how change data capture works — a database's row changes streamed into a compacted topic keyed by primary key — and it is the mechanism underneath event-sourcing designs on Kafka.

Tiered storage decouples retention from broker count

The estimate showed retention drove broker count: 726 TB needs 13+ brokers even though throughput needs far fewer. Tiered storage keeps only recent segments on local disks and uploads closed segments to object storage (S3 or similar). Fetches for old offsets are served by the broker reading from object storage. The cost model flips: local disk holds hours, object storage holds weeks cheaply, and a broker failure moves far less data. The trade-off is that replaying old data now depends on an external service with higher latency — fine for backfills, poor for a consumer trying to catch up quickly from a long outage.

Know when Kafka is the wrong tool

Kafka's consumer groups are a poor fit for task queues where each message is an independent job of variable duration. One slow job blocks everything behind it in its partition (head-of-line blocking); you cannot have more workers than partitions; per-message retry with delay, priority or expiry is not built in. Traditional brokers (RabbitMQ) and managed queues (Amazon SQS) track each message's state and fit those workloads, at the cost of replay and multi-reader fan-out. Kafka itself added share groups in the 4.x line for this case: records are handed to consumers individually with a time-limited acquisition lock (30 seconds by default), acknowledged one by one, counted per delivery attempt so poison records can be rejected, and a share group can have more consumers than partitions. Volunteering "here's when I wouldn't use Kafka" is more convincing than advocating for it.

The controller is the coordination-service design, reused

Something must decide which broker leads each partition, maintain the ISR lists, and fence a broker that was declared dead but is still running. Kafka originally used ZooKeeper: brokers registered ephemeral nodes that vanished when their session expired, and the paper describes consumers using ZooKeeper watches to trigger rebalances. KRaft moves this into a Raft quorum of controllers that stores metadata as its own log, which brokers replicate. The leader epoch on each partition plays the role of a fencing token: a deposed leader's writes carry an old epoch and are rejected. If an interviewer asks you to "design the metadata layer", say it is the coordination service from in8 and reuse it rather than inventing a second mechanism.

Multi-region

A single Kafka cluster stretched across distant regions would put cross-region latency into every acks=all write. The usual design is one cluster per region with asynchronous replication between them (MirrorMaker 2 or a vendor's cluster linking). Consumers failing over to another region need their offsets translated, because the same record has different offsets in the two clusters. Asynchronous replication means a regional failure can lose the last seconds of data — the same recovery-point trade-off (RPO, recovery point objective: how much recent data you can afford to lose) as any asynchronous database replica.

The real case: the 2011 Kafka paper and the 2014 benchmark

Kafka's original paper, "Kafka: a Distributed Messaging System for Log Processing" by Jay Kreps, Neha Narkhede and Jun Rao (NetDB 2011), describes the system LinkedIn built for activity and operational data. At the time it already handled "hundreds of gigabytes of data and close to a billion messages per day", with end-to-end latency for the pipeline into Hadoop of "about 10 seconds on average". Its core decisions are the ones in this lesson: each partition is a set of segment files of roughly equal size (the paper's example is 1 GB); brokers keep no record of what consumers have read, and delete data by a time-based rule, "typically 7 days"; consumers pull from an offset and can rewind; consumer groups divide partitions among their members; and delivery is at-least-once.

The paper's experiment compared Kafka with ActiveMQ and RabbitMQ on two machines (8 cores, 16 GB of memory, 6 disks in RAID 10, a 1 Gbit link). A single producer published 10 million 200-byte messages. Kafka averaged 50,000 messages per second with a batch size of 1 and 400,000 with a batch size of 50 — at batch 50, one producer almost saturated the 1 Gbit link. Kafka's per-message storage overhead was 9 bytes versus 144 bytes for ActiveMQ. On the consumer side Kafka averaged 22,000 messages per second, more than four times the others. The authors are candid that part of the producer advantage came from not waiting for acknowledgements at all — the 2011 system had no replication — and they list replication as future work. That is a useful interview point: the early numbers were for an acks=0-style system, and replication was added later.

Three years later, Jay Kreps published a benchmark of replicated Kafka on three commodity machines (six-core 2.5 GHz Xeon, six 7,200 RPM SATA drives, 32 GB of memory, 1 Gbit Ethernet), producing 100-byte records to a 6-partition topic. A single producer thread achieved 821,557 records/s with no replication, 786,980 records/s with 3× asynchronous replication, and 421,823 records/s with 3× synchronous replication (the leader waiting for the full ISR — today's acks=all). Three producers with 3× asynchronous replication reached 2,024,032 records/s. A single consumer read 940,521 records/s and three consumers 2,615,968 records/s; end-to-end latency was 2 ms median, 3 ms at the 99th percentile and 14 ms at the 99.9th. Read the synchronous number carefully: waiting for followers roughly halved single-producer throughput in that setup, which is the latency-for-durability trade-off the acks table describes, and it is why producers batch and pipeline several requests.

What goes wrong in practice

Under-replicated partitions. The single most important broker metric is the count of partitions whose ISR is smaller than their replica set. It rises when a broker is slow (a failing disk, a long garbage-collection pause, a saturated network) or down. A sustained non-zero value means you are one failure away from either data loss (if min ISR is 1) or write unavailability (if min ISR is 2).

Lagging consumers that slow everyone. A consumer reading hours-old data forces disk reads that compete with the sequential writes of every other partition on that broker, and evicts hot data from the page cache, so producer latency rises for unrelated topics. Watch disk read rates alongside consumer lag; consider tiered storage or a separate cluster for backfills.

Rebalance storms. Consumers that exceed the poll interval, crash-loop, or are deployed one by one trigger repeated rebalances. Under the classic protocol every rebalance pauses the group. Symptoms are lag sawtooths and frequent "partitions revoked" logs. Fixes: smaller batches, the cooperative or KIP-848 protocol, static group membership so restarts don't trigger reassignment.

Retry storms from producers. When a broker is struggling, producers time out and retry, adding load. Producer delivery timeouts, bounded retries with backoff, and broker quotas per client keep one misbehaving client from hurting the rest.

What to monitor. Under-replicated and offline partitions; ISR shrink and expand rates; produce and fetch request latency (99th percentile); bytes in and out per broker; consumer lag per group and per partition; disk usage and disk read rate; controller elections; rebalance frequency per group. The per-partition lag view is the one that catches key skew.

Goal: see four ideas from this lesson in a toy partitioned log: key hashing preserves per-key order, a consumer group can't use more consumers than partitions, process-then-commit duplicates records after a crash, and an idempotent producer removes retry duplicates. Python 3.12, standard library only, runs in under a second.

"""A toy partitioned log: key hashing, consumer groups, crash-redelivery and
idempotent producers. Python 3.12 stdlib only."""
import random, zlib
from collections import Counter, defaultdict

P = 6                                    # partitions in the topic
log = [[] for _ in range(P)]             # each partition is an append-only list
seen_seq = {}                            # broker side: (producer_id, partition) -> last sequence

def partition_for(key):                  # Kafka uses murmur2; any stable hash shows the idea
    return zlib.crc32(key.encode()) % P

def produce(pid, seq, key, value, idempotent):
    p = partition_for(key)
    if idempotent and seen_seq.get((pid, p), -1) >= seq:
        return p, None                   # duplicate retry: broker drops it, returns old offset
    seen_seq[(pid, p)] = seq
    log[p].append((key, value))
    return p, len(log[p]) - 1            # the offset is just the position in the list

def run_producer(idempotent, retry_rate=0.05, n=10_000):
    for part in log: part.clear()
    seen_seq.clear()
    rng = random.Random(7)
    for seq in range(n):
        key = f"user-{rng.randrange(500)}"
        produce("p1", seq, key, seq, idempotent)
        if rng.random() < retry_rate:    # ack lost on the way back -> producer resends
            produce("p1", seq, key, seq, idempotent)
    return sum(len(x) for x in log)

print("records written, plain producer:     ", run_producer(False))
print("records written, idempotent producer:", run_producer(True))

# 1. Per-key order holds because one key always lands in one partition.
ok = all(
    [v for k, v in part if k == key] == sorted(v for k, v in part if k == key)
    for part in log for key in {k for k, _ in part})
print("per-key order preserved:", ok, "| partition sizes:", [len(x) for x in log])

# 2. A consumer group: each partition goes to exactly one member.
for members in (4, 6, 8):
    owned = defaultdict(list)
    for p in range(P):
        owned[p % members].append(p)
    idle = members - len(owned)
    print(f"{members} consumers -> busiest owns {max(map(len, owned.values()))} partitions, idle: {idle}")

# 3. At-least-once: process, then commit every 100 records; crash mid-way.
committed, processed = 0, Counter()
part = log[0]
for off in range(len(part)):
    processed[off] += 1
    if off == 950:                       # crash after processing 950, before the next commit
        break
    if (off + 1) % 100 == 0:
        committed = off + 1
for off in range(committed, len(part)):  # restart from the last committed offset
    processed[off] += 1
dups = sum(1 for c in processed.values() if c > 1)
print(f"restart from offset {committed}: {dups} records processed twice")
sink = {off for off in processed}        # idempotent sink keyed by (partition, offset)
print("rows in idempotent sink:", len(sink), "== partition length:", len(part))

Run it: save as log_lab.py and run python log_lab.py.

What to look for.

  1. The plain producer writes about 10,480 records for 10,000 sends: each simulated lost acknowledgement (5%) caused a resend that was appended again. The idempotent producer writes exactly 10,000, because the broker side recognises the repeated sequence number.
  2. "per-key order preserved: True" — within each partition, a key's values appear in increasing order, because one key always hashes to one partition. Partition sizes are uneven even with 500 keys; with one hot key they would be wildly uneven.
  3. Eight consumers on six partitions leave two idle. That is the consumer-group ceiling.
  4. The crash after offset 950 with commits every 100 records replays offsets 900–950: 51 duplicates. The set-based "sink" keyed by offset ends up with exactly one row per record — the idempotent-consumer pattern.

Try next: make one key 35% of traffic and print partition sizes; change P from 6 to 8 halfway through production and check whether per-key order still holds when a consumer reads two partitions.

Work it out

A topic has 12 partitions and a consumer group of 4 consumers. Throughput is 60,000 messages/s. Each consumer processes 6,000 messages/s per thread. Messages are keyed by customer_id, and one enterprise customer generates 35% of all traffic.

(a) Can this group keep up? (b) You add 8 more consumers. What happens? (c) What is actually wrong, and what do you do?

Answer

(a) Total group capacity is 4 × 6,000 = 24,000 messages/s against 60,000 arriving. Lag grows by 36,000 messages/s — the group falls behind immediately and without bound.

(b) Adding 8 consumers (total 12). Partitions are assigned one per consumer within a group, so 12 consumers each own exactly 1 partition. Nominal capacity is now 12 × 6,000 = 72,000/s, which looks sufficient. Going beyond 12 would be pointless: a 13th consumer gets zero partitions and sits idle, because partition count is the hard ceiling on group parallelism.

But the group still does not keep up, and this is the real question.

(c) The skew. The enterprise customer is 35% of 60,000 = 21,000 messages/s, and because partitioning is hash(customer_id) mod 12, every one of those messages lands on one partition. That partition's consumer must process 21,000/s against a capacity of 6,000/s, so it falls behind by 15,000 messages/s while the other eleven consumers share the remaining 39,000/s — about 3,500/s each, roughly 60% busy.

Adding consumers cannot help. The partition is already owned by exactly one consumer, and that is a guarantee, not a tunable — it is what preserves per-key ordering.

The options, and the trade-off each carries:

  • Change the key to a composite such as customer_id + hash(order_id) mod 8, spreading the hot customer across 8 partitions. Throughput problem solved — but you have given up ordering within that customer. Acceptable if the consumer's work is order-independent (say, independent enrichment); unacceptable if it is applying a sequence of state changes to one account.
  • Give the large customer their own topic with its own partition count and consumer group. Ordering is preserved, noisy-neighbour isolation is better, and it is operationally honest for a genuinely outsized tenant. The cost is per-tenant topology to manage.
  • Make the consumer faster — batch downstream writes, parallelise within the partition while preserving order by sub-key (for example by order ID), or move work off the hot path. Often the cheapest real fix, and it changes nothing about the topology.
  • More partitions overall does not fix it. 100 partitions still hash that one customer ID to exactly one of them.

The lesson to state: in a partitioned log, consumer parallelism is bounded by partition count, and per-partition throughput is bounded by key distribution. A capacity plan based on totals will look fine and fail in production, because the constraint is the hottest key, not the average. This is the same skew failure as the celebrity in a feed and the viral link in a URL shortener.

Estimate it

Your team wants to keep 30 days of LLM-call events (average 150 MB/s after compression, replication factor 3) on Kafka so the evaluation team can replay a month. Brokers have 48 TB usable each at 60% fill. How many brokers does that need, and what would you propose instead?

Answer

Per copy: 150 MB/s × 2,592,000 s (30 days) = 388.8 TB. Times 3 replicas = 1,166 TB. At 48 TB per broker that is 1,166 ÷ 48 ≈ 24.3, so 25 brokers purely for storage, while throughput (150 MB/s in, 450 MB/s of disk writes) would fit on 3–4. You'd be paying for ~20 brokers to hold cold data.

Propose tiered storage: keep 24 hours locally (150 MB/s × 86,400 s × 3 = 38.9 TB, one broker's worth spread across a small cluster) and move closed segments to object storage, which keeps one durable copy internally replicated by the storage service at a fraction of the cost. Or have a sink write the topic to object storage as Parquet files for the eval team to query directly, and keep Kafka retention at a few days. Either way, state the trade-off: replays of old data are slower and depend on the object store.
