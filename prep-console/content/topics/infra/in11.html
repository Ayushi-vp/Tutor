Type "how to" into a search box and before you reach the next word, a list appears: "how to tie a tie", "how to screenshot on mac", "how to boil an egg". It saves typing, but more importantly it steers people toward queries that work, catches spelling mistakes before they happen, and makes the product feel fast and knowing. Search engines, e-commerce sites, social networks, maps, code editors and AI chat boxes all have one.

The constraints are severe. A suggestion is only useful if it appears before the user types the next character; Facebook's engineers put it bluntly when they built theirs: spending more than 100 milliseconds "will cause the typeahead to 'stutter'", and "late answers are wrong answers". Every keystroke from every user is a request, so the request rate is several times the search rate — hundreds of thousands per second for a large product. The candidates come from billions of past queries, and the best ones change with news, seasons and fashions. And because suggestions look like the product's own recommendations, a single offensive, defamatory or dangerous completion is a public embarrassment.

The naive approaches fail in instructive ways. Running SELECT … WHERE query LIKE 'how to%' ORDER BY count DESC LIMIT 10 on every keystroke scans millions of rows for short prefixes. A plain trie finds the prefix instantly but then has to examine every completion beneath it to rank them — and the shortest, most common prefixes have the most completions. Updating counts on every search makes the index a write-hot mess. Each fix is a standard system-design idea: precompute, cache, separate the slow-changing bulk from the fast-changing edge, and push work to the client.

It is also a favourite interview question because it rewards a specific habit: noticing that the request path and the data-update path have completely different requirements. Requests are enormous in number, tiny, latency-critical and read-only. Updates are large, infrequent and tolerant of delay. A design that serves both from the same mutable structure struggles at both; a design that rebuilds a read-only structure offline and serves it from memory is simple at both.

This lesson designs typeahead in interview order: requirements, estimates, API, data model, architecture, then deep dives into tries with top-k caching, building the index from logs, trending queries, serving and scaling, client behaviour and caching, personalisation, and safety. It ends with Facebook's 2010 typeahead and a lab that measures the difference precomputed top-k makes.

The mental model: a dictionary with sticky notes

Imagine a huge printed dictionary of every query anyone has ever searched, sorted alphabetically, with a count next to each. To suggest completions for "how to", you could open it at "how to" and read every entry from "how to a…" to "how to z…", then pick the ten with the biggest counts. That's correct but slow — there may be millions of entries under "how to". Now imagine that, once a night, an assistant goes through the dictionary and puts a sticky note at the start of every section and subsection — "h", "ho", "how", "how ", "how t", "how to" — listing the ten most popular entries in that section. When someone types "how to", you flip to that section and read the sticky note. The answer takes the same time whether the section has ten entries or ten million.

That is the core of typeahead: a trie (a tree where each path from the root spells a prefix) with the top-k completions precomputed at every node. The nightly assistant is an offline build from query logs; the sticky notes are what the servers read at request time. Where the analogy breaks: a dictionary doesn't change during the day, but the world does — a breaking news event can make a brand-new query the most popular one within minutes — so real systems add a fast lane for trending queries. And the dictionary is the same for everyone, while users expect their own recent searches to appear first.

One search, keystroke by keystroke

Follow a user typing "how to tie" at a normal pace. They type "h": the client waits about 100 ms, sees no new keystroke, and asks for suggestions for "h" — but the CDN already has that response from someone else a few seconds ago, so it returns in 10 ms without reaching a server. They type "o" and "w" quickly; the request for "ho" is never sent because "w" arrived within the debounce window. "how" goes out, misses the CDN (three-character prefixes may or may not be cached), and reaches a suggestion server, which walks h → o → w in its in-memory index and reads the ten stored completions in a few microseconds; the whole round trip is perhaps 40 ms. They type " t": the client already holds the top 20 for "how", filters them to those starting with "how t", and shows them instantly while asking the server for the full "how t" list in the background. By the time they've typed "how to tie", "how to tie a tie" has been on screen for several keystrokes. Of maybe ten keystrokes, three or four became requests and only one or two reached a server.

1 · Requirements

Functional. As the user types into the search box, show up to 10 suggestions completing the current text, ranked by likely usefulness. Suggestions come from popular past queries in the user's language and region, plus the user's own recent searches. Reflect trending queries within minutes. Never show blocked content. Support removal of a suggestion within minutes when legally or ethically required.

Non-functional. Latency: suggestions visible within about 100 ms of a keystroke, so the server's share is single-digit milliseconds at the 99th percentile. Very high request volume with strong skew toward short prefixes. Highly available — if typeahead is down, search still works, so it degrades gracefully, but it should be rare. Freshness: the bulk can be a day old; trends within minutes.

Clarifying questions. "What are we completing — search queries, or entities like people, products or places?" (Facebook's typeahead returns people, pages, groups and apps, which changes the index.) "How many languages and scripts?" "Is personalisation expected?" "Is typo tolerance needed?" "Any regulatory constraints on suggestions (defamation, elections, minors)?"

2 · Back-of-envelope estimates

Scenario: 100 million daily active users, each making about 10 searches a day.

Request rate. An average query is around 20 characters, but with debouncing (send only after about 100 ms without a keystroke) and client-side reuse, a search triggers perhaps 6 suggestion requests. 100M × 10 × 6 = 6 billion requests/day = 6 × 109 ÷ 86,400 ≈ 69,000/s on average, and about 200,000/s at a 3× peak. Without debouncing, sending all 20 keystrokes, it would be over three times higher.

Prefix skew and caching. Requests are dominated by short prefixes: every search starts with one character, then two. One- and two-character prefixes in one language are only 26 + 676 = 702 distinct keys (for lowercase Latin letters), and their suggestions are the same for every user in a locale, so a CDN or a front-end cache with a 1-minute expiry absorbs them almost entirely. If short prefixes are, say, 40–50% of requests, that halves server load.

Index size. From a month of logs, perhaps 1 billion distinct queries — most typed once. Keep candidates searched by at least, say, 20 distinct users: perhaps 20 million suggestions, averaging 25 bytes: 500 MB of strings. The trie has roughly one node per distinct prefix; with shared prefixes, perhaps 5–10 nodes per suggestion, so 100–200 million nodes. Storing 10 suggestion IDs (4 bytes each) at every node: 40 bytes × 150M ≈ 6 GB, plus node structure. Limiting stored prefixes to, say, 20 characters (longer prefixes have few completions, which can be computed on the fly) cuts nodes further. Order of magnitude: a few GB to ~10 GB per language — fits in memory on one server.

Servers. A lookup is a few microseconds of CPU plus request overhead; a server handles perhaps 20,000–50,000 requests per second including networking and serialisation. 200,000/s peak minus 50% served by caches = 100,000/s → about 4–5 servers per region, deployed as 8–10 for redundancy, each holding a full replica of the index.

Build pipeline. 1 billion searches/day logged at ~100 bytes = 100 GB/day. A daily batch job aggregates a 30-day window with decay — a few TB scanned — and builds the index: an hour or so on a modest cluster. The trending stream processes about 11,600 searches/s on average (1B ÷ 86,400).

3 · API

GET /v1/suggest?q=how%20to%20t&locale=en-GB&limit=10
    Cache-Control: public, max-age=60        # only when q is short and not personalised
-> {"q": "how to t", "suggestions": [
      {"text": "how to tie a tie", "type": "query"},
      {"text": "how to take a screenshot", "type": "query"}, ...],
    "index_version": "2026-10-02T04"}

Personal history is merged on the client, so the request carries no user identity for public suggestions and the response is cacheable. When personalisation must happen server-side (for entities such as friends), the request is authenticated and the response marked private. The index_version helps debugging ("why did this suggestion appear?") and client-side cache invalidation.

4 · Data model

  • query_counts (offline): (normalised query, locale, day) → searches, distinct users, click-through after selection. Built daily from logs.
  • suggestions: suggestion ID → display text, locale, score, type, flags. The candidate set after thresholds and filters.
  • prefix index (served, in memory): a trie over normalised suggestion text, each node holding the top-k suggestion IDs by score — or an equivalent hash map from prefix to top-k list for prefixes up to a maximum length. Facebook's later Unicorn system describes this second form: typeahead index servers hold posting lists "for every name prefix up to a predefined character limit".
  • trending index: a small prefix map of currently rising queries, rebuilt every minute.
  • overrides: blocked strings and patterns, removal requests, pinned suggestions — checked on every request.

5 · High-level architecture

Client: debounces keystrokes, cancels outdated requests, caches responses per prefix, filters cached lists locally as the user types further, and merges the user's own history. Edge: a CDN or front-end cache stores responses for short, unpersonalised prefixes for a minute. Suggestion servers: stateless except for the in-memory indexes; each request walks to the prefix node, reads the top 20 candidates, merges trending candidates, applies the override list, re-ranks with light context and returns 10. Index builder: a batch job aggregates logs, applies decay and filters, builds the index file and publishes it; servers load the new version alongside the old and switch atomically. Trending job: a streaming job counts recent queries and compares them with their baseline to find risers, after safety filtering.

6 · Deep dive: tries and top-k caching

A trie stores strings by their characters: the root has a child for each first character, each of those has a child for each second character, and so on, so every path from the root spells a prefix and all strings sharing a prefix share a subtree. Insert "how", "how to", "hot dog": they share the nodes h → o, then branch at w versus t. Finding the node for a prefix of length L takes L steps, regardless of how many strings are stored.

But typeahead needs the best completions, not just the node. The completions are every terminal node in the subtree, and a short prefix's subtree is enormous. The lab builds a trie of 49,093 queries (304,660 nodes) and compares two ways of answering prefixes of 1–3 characters: scanning the subtree and taking the top 10 averaged about 5.6 milliseconds per request; reading a top-10 list precomputed at the node averaged about 1.5 microseconds — over 3,000 times faster, with identical answers. With 20 million suggestions instead of 49,000 the scan gets proportionally worse, while the cached read doesn't change at all.

Building the lists is a single bottom-up pass: a node's top-k is the k best among its own count (if a query ends there) and the top-k lists of its children. That's what the lab's build_top does. Because every node's list is drawn only from its children's lists, the build costs O(nodes × k log k), not O(nodes × subtree size).

Memory is the price: k suggestion IDs per node. Two refinements keep it in check. Store IDs (4 bytes) rather than strings, with the strings in a separate table. And compress the trie: chains of nodes with a single child (common in long queries) collapse into one node labelled with a string — a radix tree — cutting node counts by several times. Alternatively, flatten the structure into a hash map from prefix to top-k list, stored only for prefixes up to a length limit; beyond that, suggestions can be computed by scanning the (now small) set of strings sharing the limited prefix.

Ranking needn't be raw counts: the score can combine frequency with time decay, the click-through rate of the suggestion when shown, query success (did people who chose it click a result?) and freshness. Because scores are computed offline, the ranking model can be as sophisticated as the build budget allows, while serving stays a lookup.

7 · Deep dive: building the index from logs

The offline pipeline runs hourly or daily. Normalise each logged query: Unicode normalisation, lower-casing, trimming and collapsing whitespace, optionally removing accents for matching while keeping the display form. Aggregate over a window — say 30 days — with time decay, for example weight = 0.5(age in days ÷ 7), so a query searched heavily last week counts more than one searched heavily two months ago. Count distinct users as well as searches (an HLL per query works, as in in9), and drop candidates below a threshold of distinct users, so neither a single user's private searches nor a bot hammering one query can become a public suggestion. Filter: blocklists, classifiers for hate, sexual content, violence, personal data, spam patterns and policy-sensitive topics. Score and keep the top candidates. Build the trie or prefix table with top-k lists, serialise it, and publish it with a version number.

Servers download the new version, load it into memory next to the current one, run a few sanity checks (size, a sample of known prefixes returning results), then switch a pointer so new requests use it, and free the old one. A bad build — a filter bug that let through offensive suggestions, or an empty index — must be caught by those checks or rolled back in minutes, which is why every response carries the index version.

8 · Deep dive: trending queries

A daily rebuild misses the earthquake, the surprise election result or the product launch that happened an hour ago. The fast path is a streaming job over the query log. It counts queries per minute in a count-min sketch with a heap of heavy hitters (in9), and compares each candidate's recent rate with its baseline from the main index: a query searched 5,000 times in the last 10 minutes that normally gets 50 a day is trending; one searched 5,000 times that normally gets 700,000 a day is not. Candidates pass the same safety filters — fast-moving news is exactly where harmful suggestions appear — plus a minimum distinct-user count, then go into a small trending prefix map rebuilt every minute and pushed to servers. At request time, the server merges the trending candidates for the prefix with the main list, boosting them by how strongly they're rising. Trending entries expire automatically when their rate falls back.

9 · Deep dive: serving, replication and sharding

If the index fits in one server's memory — a few GB per language usually does — replicate it everywhere. Every server can answer every request alone: no fan-out, no waiting for the slowest of several shards, no coordination. Scaling is adding identical servers behind a load balancer; regions each get their own replicas close to users, which matters because network round trip is most of the 100 ms budget.

When the index doesn't fit — many languages and entity types, or very long-tail candidates — shard it. Sharding by first letter is the classic mistake: 's' starts far more queries than 'x', so shards are unevenly loaded, and a hot prefix overloads one shard. Shard instead by prefix ranges sized by traffic and memory (computed from the logs at build time), with boundaries at prefix granularity so any one prefix's subtree and top-k list live on exactly one shard; a request still touches only one shard. A thin routing layer maps prefixes to shards. Replicate each shard for availability and to spread hot ranges.

Facebook's design had a different shape because its results weren't only queries: a stateless aggregator fanned each request out to several leaf services — a global service for pages and applications (identical for every user, so cached in memcached) and a graph service searching the user's own neighbourhood of friends and connections — and merged their results. Fan-out is the price of mixing personal and global sources on the server.

10 · Deep dive: the client, caching and personalisation

The fastest request is the one never sent. Debounce: wait until the user has paused for about 100 ms before sending; a fast typist's intermediate keystrokes never become requests. Cancel an in-flight request when a new keystroke arrives, and ignore responses for stale prefixes, so a slow response for "ho" can't overwrite the list for "how t". Reuse: once the client has the top 20 for "how", typing "how t" can be answered instantly by filtering those 20 locally, sending a request only if too few remain. Bootstrap: Facebook's typeahead, the moment the user focused the search box, fetched "all of the user's friends, pages, groups, applications, and upcoming events" into the browser cache, so the most personal results appeared without any request at all.

Edge caching works because short prefixes are both the most requested and the least personal: the top suggestions for "a" in en-GB are the same for everyone. Cache responses for prefixes up to two or three characters at the CDN with a short expiry (a minute), keyed by prefix and locale. That can remove a large fraction of all server traffic (the drill works out 69% for one distribution).

Personalisation without destroying caching: fetch the global top 20 (cacheable), and blend in the user's own recent queries matching the prefix — tens of items, kept on the device — then re-rank with context such as the page the user is on. Only results that inherently depend on the user (their friends, their files) need server-side personal indexes, and those are small per user.

11 · Deep dive: safety and quality

Suggestions are content the product appears to recommend, so they get the strictest filtering of any search feature. Layers: offline blocklists and classifiers before a candidate enters the index; a minimum number of distinct users per suggestion so private or targeted strings never surface; bot and abuse detection so coordinated campaigns can't push a phrase (people have tried to manipulate autocomplete for marketing and defamation); a serving-time override list for urgent removals, checked on every request and updated in seconds; special handling for sensitive categories (names of private individuals, medical, elections) where many products show no suggestions at all; and monitoring of what's shown — sampled audits, user "report this suggestion" feedback and alerting on new suggestions for high-traffic prefixes.

12 · Sizing the index, worked

Take 20 million suggestions averaging 25 characters, top-k with k = 10. A plain trie has one node per distinct prefix. If suggestions shared nothing, that would be 20M × 25 = 500 million nodes; shared prefixes cut it, and in the lab six nodes per query was typical, so call it 120 million nodes. Each node needs its children (a small map, say 40 bytes on average in a compact implementation), its own count (4 bytes) and its top-10 list of 4-byte IDs (40 bytes): roughly 84 bytes × 120M ≈ 10 GB. Collapse single-child chains into a radix tree and the node count typically falls several-fold, to perhaps 3 GB. Alternatively, store top-k lists only for prefixes up to 12 characters, where most traffic is, and answer longer prefixes by scanning the few strings under them. Add 500 MB for the suggestion strings. A few gigabytes per language fits in memory on a commodity server, which is why replication is usually the right serving model. Had the estimate come out at 200 GB, you would shard by traffic-balanced prefix ranges instead.

13 · Failure modes and trade-offs

A bad index build (empty, corrupted or unfiltered): sanity checks before switching, canary servers first, instant rollback to the previous version. Trending path abuse: a bot network pushes a phrase; distinct-user thresholds and bot filtering before candidates are eligible. Latency spikes: garbage collection or index loading on a server; load the new index in the background, keep request handling allocation-light, hedge requests to a second replica after a few milliseconds. CDN serving stale or wrong-locale results: include locale in the cache key and keep expiry short. Typeahead outage: the search box must still work; the client hides suggestions after a timeout rather than blocking typing.

The trade-offs to state in the close: memory for latency (top-k at every node); freshness for simplicity (batch index plus a small trending path); cacheability for personalisation (global fetch, client-side blending); replication for simplicity until the index doesn't fit; and coverage for safety (no suggestions is better than a harmful one).

Scoring beyond frequency

Counting how often a query was typed is a starting point; better systems learn from what happens after a suggestion is shown. If "how to tie a tie" is suggested a million times for "how to t" and selected 200,000 times, its selection rate is 20%; a less frequent but more often selected suggestion should rise. Success after selection — the user clicked a result and didn't immediately rephrase — is a stronger signal still. Because these signals are computed offline from logs, scores can come from a learned ranking model over features (frequency, decay, selection rate, success rate, length, freshness, locale) without affecting serving latency. One caution: suggestions shape what users type, so frequency and selection data are partly caused by past suggestions — a feedback loop that can lock in early winners. Holding out a small amount of exploration (occasionally showing a lower-ranked candidate) keeps the data informative.

Fuzzy matching and the cost of typos

A noticeable share of queries contain typos, and a pure prefix trie returns nothing for "hwo to". Two families of fixes. Log-mined corrections: users who typed "hwo to" and then corrected to "how to" teach the system a mapping, applied before lookup; cheap and accurate for common errors. Fuzzy trie search: walk the trie allowing up to one or two edits (a substitution, insertion or deletion each costs one), which visits many more nodes — the number grows roughly with the alphabet size times the prefix length for each allowed edit — so it's used only when exact matches are scarce and limited to short edit distances. Phonetic or keyboard-adjacency models help in specific domains (names, mobile typing).

Languages, scripts and normalisation

Many languages don't fit the "lowercase a–z" model. Chinese and Japanese input goes through an input method editor, so the "prefix" may be phonetic input converted to characters; Korean syllables are composed from parts as the user types; Arabic and Hebrew are right-to-left; Turkish has dotted and dotless i that lower-case differently; accents may or may not matter to users. The index is built per locale with locale-specific normalisation, and the 702-key cache trick for short prefixes becomes thousands of keys for scripts with large alphabets — still cacheable, but less dramatically.

Entity typeahead versus query typeahead

Completing queries ranks strings by global popularity. Completing entities — people, pages, products, files — ranks objects by relevance to this user, often through the social graph or their own data, which is why Facebook's typeahead fanned out to a graph service searching "the user's neighborhood of the graph" alongside a global service. Facebook's later Unicorn system generalised this into an inverted index over the social graph, with typeahead served from posting lists for every name prefix up to a character limit and results ranked by social proximity. In an interview, ask which kind is wanted; it changes the index from a shared trie to a combination of per-user and global retrieval with a merge and rank step.

Compact index formats

Pointer-based tries waste memory on object headers and pointers. Production systems serialise the index into compact, read-only formats that load quickly and are shared between processes. A finite-state transducer, as used in Lucene's suggester, shares both prefixes and suffixes of the stored strings and can attach weights, often shrinking a dictionary several-fold compared with a trie. A sorted array of prefix strings with offsets into a top-k table is another simple option: binary search for the prefix, read its list. Because the index is rebuilt offline and never modified in place, read-only formats like these are a natural fit, and loading a new version is a memory-map of a file rather than millions of allocations — which also makes atomic swaps fast.

Suggestions in AI products

Prompt boxes in AI assistants increasingly offer completions: starter tasks, saved prompts, or model-generated continuations. Precomputed candidates (popular task starters, the user's own history) fit this lesson's design directly. Model-generated completions don't fit a 100 ms per-keystroke budget unless the model is small and fast, and they move safety review from the offline build to serving time — every generated suggestion needs the same filters, at request latency. A common compromise is precomputed suggestions for short prefixes and a generated completion only after the user pauses, displayed as lighter "ghost text" they can accept.

The real case: Facebook's typeahead (2010)

In May 2010 Keith Adams described how Facebook built a search box where "high quality results would appear as the user typed", for what was then 400 million users. The goals were explicit: the new typeahead "can't be slower than the existing typeahead for finding your friends, so every millisecond delay matters", and because pressing Enter auto-selected the first result, relevance had to be near-perfect.

The design follows a request through seven steps that map onto this lesson. Bootstrapping: as soon as the user focuses the search box, the browser fetches all of the user's friends, pages, groups, applications and upcoming events into its cache, so they can be found "immediately without sending another request". AJAX request: only if the browser cache doesn't have enough results does it send the query string plus the IDs already shown. Aggregator: a stateless Thrift service, with no index of its own, at the root of a tree of search services; it delegates to leaf services in parallel and merges. Leaf services: each searches its own index for prefix matches and ranks on a few specific features — a global service indexing all pages and applications, ranked by signals identical for every user, so "we can save latency by storing recent results in a memcached-based query cache"; and a graph service searching the user's neighbourhood of a graph with "400 million active users, and many billions of connections". Merging: the aggregator ranks the combined results with a model. Fetching and validating: the web tier fetches display data (names, pictures, mutual friends) from memcache and MySQL and performs privacy checks. Display: results are rendered and added to the browser cache for similar subsequent queries.

Launch engineering mirrors the A/B testing lesson (in10): the team "dark-tested by changing the old typeahead to send a query on every keystroke", discovering network limitations that changed the architecture before real users depended on it, and ran A/B tests on the number of results, the placement of "See More Results", picture sizes and how to show mutual friends. One finding: although employees were heavy keyboard users, most users preferred the mouse, which shifted design priorities. The post's summary of the trade-off is the line to remember: a "trilemma among performance, recall, and relevance", with performance first, because "spending more than 100 msec to retrieve a result will cause the typeahead to 'stutter'" — "late answers are wrong answers".

Notice what the design avoided: no ranking work in the browser beyond filtering, no per-keystroke database queries, and no single service that knew about every kind of result. Each leaf could be optimised for its data — the global index cached because it was the same for everyone, the graph index personal because friends are — and the aggregator kept the merge in one place. The same split between a cacheable global source and a personal source reappears in every modern typeahead, including the client-side blending recommended in this lesson.

What goes wrong, and what to watch

Server latency percentiles (p50, p99) and end-to-end time to suggestions measured in clients. Cache hit rates at client, CDN and server. Zero-result rate by prefix length — a jump means a bad index build or a normalisation bug. Selection rate (how often a shown suggestion is chosen) — a drop after an index swap means ranking regressed. Index build health: size, candidate count, filter hit counts, version deployed per server. Safety signals: reports per million impressions, new suggestions on high-traffic prefixes, override-list size and time to apply a removal.

Goal: build a trie from a skewed query log, precompute the top 10 completions at every node bottom-up, and compare answering prefixes by scanning subtrees versus reading the cached lists. Python 3.12, standard library only, about 6 seconds (mostly the slow scanning path).

"""Typeahead: a trie of past queries with top-k suggestions cached at every
node, versus searching the subtree on every keystroke. Python 3.12 stdlib only."""
import heapq, random, string, time
from collections import Counter

rng = random.Random(3)
def fake_query():                                   # short multi-word queries
    words = ["".join(rng.choices(string.ascii_lowercase[:12], k=rng.randint(2, 6)))
             for _ in range(rng.randint(1, 3))]
    return " ".join(words)
vocab = [fake_query() for _ in range(60_000)]
weights = [1 / (i + 1) ** 0.9 for i in range(len(vocab))]   # skewed popularity
log = Counter(rng.choices(vocab, weights, k=600_000))        # query -> count

class Node:
    __slots__ = ("kids", "count", "top")
    def __init__(self): self.kids, self.count, self.top = {}, 0, []

K = 10
root = Node()
for q, c in log.items():                            # 1. insert every query with its count
    n = root
    for ch in q: n = n.kids.setdefault(ch, Node())
    n.count = c

def build_top(n, prefix):                           # 2. bottom-up: merge children's top-k
    cands = [(n.count, prefix)] if n.count else []
    for ch, kid in n.kids.items():
        cands += build_top(kid, prefix + ch)
    n.top = heapq.nlargest(K, cands)
    return n.top
build_top(root, "")

def walk(prefix):
    n = root
    for ch in prefix:
        n = n.kids.get(ch)
        if n is None: return None
    return n

def suggest_cached(prefix):                         # O(len(prefix)): read the cache
    n = walk(prefix)
    return [q for _, q in n.top] if n else []

def suggest_scan(prefix):                           # O(subtree): collect and sort
    n = walk(prefix)
    if n is None: return []
    out, stack = [], [(n, prefix)]
    while stack:
        node, p = stack.pop()
        if node.count: out.append((node.count, p))
        stack.extend((kid, p + ch) for ch, kid in node.kids.items())
    return [q for _, q in heapq.nlargest(K, out)]

def count_nodes(n): return 1 + sum(count_nodes(k) for k in n.kids.values())
total_nodes = count_nodes(root)
print(f"{len(log):,} distinct queries -> trie with {total_nodes:,} nodes, "
      f"caching up to {K} suggestions per node")

prefixes = [q[:rng.randint(1, 3)] for q in rng.choices(list(log), k=500)]
for fn in (suggest_scan, suggest_cached):
    t = time.perf_counter()
    for p in prefixes: fn(p)
    per = (time.perf_counter() - t) / len(prefixes) * 1e6
    print(f"{fn.__name__:15}: {per:9.1f} microseconds per keystroke")
assert all(suggest_scan(p) == suggest_cached(p) for p in prefixes[:200])
print("same answers:", True)
print("top for 'a':", suggest_cached("a")[:5])

Run it: save as typeahead_lab.py and run python typeahead_lab.py.

What to look for.

  1. About 49,000 distinct queries produce a trie of about 305,000 nodes — roughly six nodes per query even with shared prefixes. That ratio is what makes per-node lists the memory cost to plan for.
  2. Scanning a 1–3 character prefix's subtree costs about 5,600 microseconds per keystroke; reading the precomputed list costs about 1.5 microseconds — over 3,000 times faster, with the same answers (the script asserts this).
  3. The scan's cost grows with the number of stored queries; the cached read doesn't. At 20 million suggestions the scan would be hundreds of times slower still, on the most frequent requests.

Try next: add time decay — give each query a random age in days and score it count × 0.5age/7 before building; then implement an insert that updates the top-k lists along one path (only the nodes on the inserted query's path can change) and compare it with a full rebuild.

Work it out

Your typeahead serves 400,000 requests/s. The suggestion corpus is 40M queries. Measurements show the prefix-length distribution is: 1 char 22%, 2 chars 26%, 3 chars 21%, 4 chars 14%, 5+ chars 17%. Each trie server holds the full index in 6 GB of RAM and handles 25,000 requests/s.

(a) How many servers, and what does edge caching change? (b) A prefix like a has 8M completions in its subtree. What is the lookup cost with and without precomputed top-k? (c) The product wants personalised suggestions. How do you do it without exploding the design?

Answer

(a) Fleet size. 400,000 ÷ 25,000 = 16 servers at full utilisation, so 24–32 with headroom and redundancy. Each holds the full 6 GB index, so this is pure replication — no sharding, no fan-out, no scatter-gather tail latency. Scaling is adding machines.

Now the edge cache. Prefixes of 1 and 2 characters are 48% of all requests, and for a given locale their answers are identical for every user — there are only about 26 + 676 = 702 such prefixes. Caching those at the CDN with a short expiry removes nearly half the traffic before it reaches your servers. Add 3-character prefixes (another 21%, about 17,600 distinct keys, still trivial to cache) and you've removed 69% of requests.

Remaining load: 400,000 × 0.31 = 124,000/s, needing 5 servers at full utilisation (7–8 with headroom) rather than 16. A two-thirds reduction in fleet from caching about 18,000 keys, and it works precisely because short prefixes are both the most requested and the least personalised. The general principle: the skew that makes a workload dangerous is often the same skew that makes it cacheable.

(b) The cost of a.

Without precomputed top-k: walk one edge to the a node, then traverse its entire subtree — 8 million nodes — collecting terminal entries, then heap them by score for the top 10. Even at 100M node visits per second that's about 80 ms for the traversal alone. Completely outside the budget, and it's the most common request: the system would be slowest exactly where it is busiest.

With precomputed top-k: walk one edge and read a stored list of 10 entries — a pointer dereference and a memory read, well under a microsecond. Cost is O(prefix length), so a 1-character prefix becomes the cheapest request rather than the most expensive.

The memory price: 10 IDs of 4 bytes at every node adds 40 bytes per node. Over tens of millions of nodes that's a few hundred megabytes to a couple of gigabytes — affordable next to a five-orders-of-magnitude latency improvement on the hottest path. This is the trade that makes the whole design work.

(c) Personalisation without exploding it. The wrong answer is a per-user index: tens of millions of users × any index is impossible, and it would also destroy the edge cache that's removing 69% of your traffic.

The right structure is a global fetch plus a local re-rank:

  • Fetch the global top 20 for the prefix — still cacheable at the edge, identical for everyone in a locale.
  • Blend in the user's own recent queries matching that prefix. These are few (tens of items) and can live on the client: zero server cost and no privacy exposure.
  • Apply light contextual re-ranking (locale, current page or session) over the candidates and return 10.

The expensive, high-volume part stays global and cached; the personal part is small, per user, and computed where the data already is. Two details: over-fetching 20 for a 10-item response gives room to drop blocked suggestions without returning a short list, and client-side personalisation preserves the edge-cache hit rate — a server-side personalised response would be uncacheable and would take you straight back to 16+ servers.

Diagnose it

An hour after a new daily index is deployed, the zero-result rate for 4–6 character prefixes jumps from 3% to 21%, while 1–3 character prefixes look normal. Selection rate drops. What do you suspect, and what do you do?

Answer

Short prefixes look normal because they're mostly served from the CDN and client caches, still holding yesterday's responses — the problem is in the new index, visible first where requests reach the servers. Likely causes: a normalisation change in the build that differs from the one used at serving time (for example, the build stripped accents or changed whitespace handling but servers didn't), so many typed prefixes no longer match index paths; a filter misconfiguration that removed far more candidates than usual; or a truncated build (a failed partition in the aggregation job). Immediately roll back to the previous index version (every server keeps it), then compare the two builds' candidate counts and filter-hit counts, and replay a sample of logged prefixes against both. Add a pre-switch check that replays a few thousand real prefixes and blocks the deploy if the zero-result rate rises beyond a threshold.
