A customer reports that checkout "sometimes takes ten seconds". The checkout page calls an API gateway, which calls the order service, which calls inventory, pricing, the payment service (which calls a fraud model and a card network), the loyalty service and a shipping-quote service; several of those talk to databases and caches, and one publishes to a queue. Every team's dashboards are green. Average latencies look fine. Logs exist on fifty machines, each with its own timestamps and no common key. Somewhere in that graph, one in a few hundred requests waits nine seconds for something, and nobody can see which.

Metrics (in6) say that something is slow, aggregated over many requests. Logs say what one process did. Neither shows one request's whole journey: which services it touched, in what order, which calls ran in parallel, and where its time went. That is what a distributed trace is, and Google's Dapper paper describes exactly this motivation: a web search touches thousands of machines across many services, and an engineer looking at overall latency "may know there is a problem, but may not be able to guess which service is at fault".

Building tracing raises its own system design problem, and that problem is the subject of this lesson. Every service must pass context along on every call, in every language, through every queue and thread pool, or traces fall apart. Recording every request would produce terabytes a day and slow applications down, so the system must sample — and the choice of when to decide what to keep determines which problems you can debug. Spans arrive at the backend from thousands of machines, out of order and at different times, and must be assembled into traces. And the storage must answer two different questions: "show me trace 4bf92f…", and "find me slow checkout traces with errors in the last hour".

This lesson builds the tracing backend in interview order: requirements; estimates done by hand (spans per second, bytes per span, storage per day under different sampling, collector memory); the API and data model (spans, context and the W3C traceparent header, decoded by hand); the high-level design and the path of one span; then three deep dives — context propagation, head versus tail sampling, and storage and query. sc13 and sc14 introduced traces from the user's side; in6 owns time-series storage; ae1 and hd7 show tracing an LLM application. Here we design the system behind them. The real case is the Dapper paper, with the W3C and OpenTelemetry specifications and Jaeger's architecture; the lab builds a tiny tracer that propagates traceparent across three fake services and compares head and tail sampling on simulated traffic.

The mental model: a parcel with a tracking number

Think of a parcel sent across the country. At the first depot it gets a tracking number. Every depot, van and sorting machine that handles it records a scan: "arrived at Leeds hub 09:14, left 09:52". Some scans happen in parallel — the parcel is weighed while its label is printed. Each scan says which earlier step led to it. Later, anyone can type the tracking number and see the whole journey as a timeline, and the company can also search: "all parcels delayed more than a day at Leeds last week".

In tracing, the tracking number is the trace id, created when the request enters the system. Each scan is a span: one timed unit of work — handling an HTTP request, calling another service, running a query — with its own span id, the id of the span that caused it (its parent), a name, a start and end time, and attributes such as the HTTP route or the database table. The label that travels with the parcel is the trace context, carried in a header (traceparent) on every call so the next service knows which trace it is part of and which span called it. The tracking website is the tracing backend: collectors that receive spans, storage that keeps them, and a query service with a waterfall view.

Where the analogy breaks: a parcel company scans every parcel, while a tracing system usually records only a sample of requests, because there are billions. And a depot's clock is the company's clock, while each server's clock is its own — so two spans' timestamps from different machines can disagree by milliseconds.

A trace as a picture

The standard view of one trace is a waterfall: time runs left to right, each span is a bar, children are indented under their parents. Parallel calls appear as overlapping bars; sequential ones as a staircase. The longest chain of dependent spans — the critical path — is where shaving time would actually shorten the request. Reading a waterfall is the skill this whole system exists to support.

The pieces of a tracing system

Four parts, which the rest of the lesson builds in order. Instrumentation: libraries in each process that create spans and propagate context (OpenTelemetry SDKs — software development kits, one per language — and auto-instrumentation for common frameworks, which wraps HTTP servers, clients and database drivers so spans appear without any application code). Collection: agents and collectors that receive finished spans, batch them, sample them and forward them. Storage: a store that can return all spans of a trace by id, and indexes that let you search. Query and analysis: an API and UI for waterfalls, search, service dependency graphs, and metrics derived from spans.

1 · Requirements

Functional. (1) Applications in many languages produce spans with minimal code, through libraries. (2) Context propagates across HTTP, gRPC, message queues and async work using a standard format. (3) Fetch a full trace by trace id and show it as a waterfall. (4) Search traces by service, operation, time range, duration and attributes (status=error, customer.tier=gold). (5) Derive a service dependency graph and per-operation latency and error metrics from spans. (6) Configurable sampling, including keeping all errors and slow requests. Out of scope, said aloud: logs and metrics storage (in6), profiling, and alerting (spans feed metrics, which feed alerts).

Non-functional. Low overhead on applications — the hard constraint; teams switch tracing off if it costs measurable latency. Never block the application: if the backend is down, spans are dropped, requests are not slowed. Ingest hundreds of thousands to millions of spans per second. Traces searchable within seconds to a minute of the request. Retention of days to weeks. Loss of some spans is acceptable; loss of the application's availability is not. Sensitive data must not leak into spans.

Clarifying questions. How many requests per second, and how many services does a typical request touch? What retention? Must every error be captured, or is a sample enough? Are there regulated data (payments, health) that must not appear in spans? Self-hosted (Jaeger, Tempo) or a vendor? These decide the sampling strategy and the storage engine.

2 · Back-of-envelope estimates

Assume 100,000 requests per second at peak entering the system, an average of 20 spans per request (a dozen services plus database and cache calls), and 500 bytes per span on the wire (ids, name, timestamps, a dozen attributes; Dapper reported 426 bytes per span on average), retention of 14 days.

Unsampled volume. 100,000 × 20 = 2 million spans per second. × 500 B = 1 GB/s = 8 Gbit/s. Per day: 1 GB × 86,400 = 86 TB. Fourteen days: 1.2 PB. Nobody stores this; it is the number that justifies sampling.

Head sampling at 1%. 20,000 spans per second, 10 MB/s, 864 GB per day, 12 TB for 14 days before compression. Span data compresses well (repeated service names, attribute keys and similar values) — assume 5× — so about 2.4 TB, then times the store's replication (3×): about 7 TB of disk. Ordinary.

Tail sampling. Suppose policy keeps a 1% baseline, all traces with errors (0.5% of requests) and the slowest 1%: about 2.5% of traces, so 50,000 spans per second, 25 MB/s, 2.2 TB per day. Storage is modest. The cost is upstream: the collector tier must receive all 2 million spans per second (1 GB/s of ingress) and hold each trace until its decision. With a 30-second decision wait — the default in OpenTelemetry's tail-sampling processor — that is 2,000,000 × 30 × 500 B = 30 GB of span data in memory at any moment, and two to three times that in object overhead: 60-90 GB across the tier, about 20 collectors of 4-8 GB each.

Application overhead. Dapper measured 204 ns to create and destroy a root span and 176 ns for a non-root span on a 2.2 GHz server. For a request with 20 spans that is about 4 µs — negligible next to a request of tens of milliseconds. Serialisation and export cost more, which is why exports are batched and asynchronous; Dapper's collection daemon used under 0.3% of one core and less than 0.01% of network traffic.

Index size. At 1% head sampling, 1,000 traces per second are kept. If each trace adds 10 index entries (service, operation, duration bucket, a few tags) at 100 bytes each, that is 1 MB/s, 86 GB a day — small next to the spans, but it is the part that must be fast to query.

3 · The API

Three interfaces: the propagation format between services, the export protocol from applications, and the query API.

Propagation (W3C Trace Context, on every outgoing request):
  traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
  tracestate:  vendorA=t61rcWkgMzE,vendorB=opaque-value       (optional, up to 32 entries)

Export (OTLP over gRPC or HTTP, batched, async):
  POST /v1/traces   ExportTraceServiceRequest{resource_spans: [{resource: {service.name, host, version},
                                                                spans: [ ... ]}]}

Query:
  GET /api/traces/{trace_id}                                  → all spans of one trace
  GET /api/traces?service=checkout&operation=POST%20/pay&minDuration=2s
                 &tags={"error":"true"}&start=…&end=…&limit=20  → matching trace summaries
  GET /api/dependencies?start=…&end=…                        → service call graph with counts

The traceparent header, decoded by hand. Take 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 (the example in the W3C Recommendation). Split on dashes: four fields. Version 00 — the only version defined so far; a receiver seeing a higher version still tries to parse the next fields in this format. Trace id 4bf92f3577b34da6a3ce929d0e0e4736 — 32 hex characters, 16 bytes; every span of the request carries it. Parent id 00f067aa0ba902b7 — 16 hex characters, 8 bytes: the span id of the span that made this call. Trace flags 01 — one byte, of which only the lowest bit is defined: 1 means the caller sampled (recorded) this trace. An id of all zeros is invalid, and a receiver must ignore the header and start a new trace. The 16-byte random trace id makes collisions negligible across the trillions of traces a large system creates in a year.

What the receiving service does: it starts a SERVER span with the same trace id, a fresh random 8-byte span id — say b7ad6b7169203331 — and parent 00f067aa0ba902b7. When it calls the next service, it creates a CLIENT span (span id e457b5a2e4d86bd1, parent b7ad6b7169203331) and sends traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-e457b5a2e4d86bd1-01. The trace id never changes; the parent id field always names the immediate caller's span; the sampled flag is passed through so every service makes the same decision.

4 · The data model

Span {
  trace_id        bytes[16]
  span_id         bytes[8]
  parent_span_id  bytes[8]          -- empty for the root span
  name            "POST /checkout" | "SELECT orders" | "chat gpt-x"
  kind            SERVER | CLIENT | PRODUCER | CONSUMER | INTERNAL
  start_time_ns, end_time_ns
  attributes      {http.route: "/checkout", http.response.status_code: 200, db.system: "postgresql", ...}
  events          [{time, name: "exception", attributes: {exception.type, exception.message}}]
  links           [{trace_id, span_id}]   -- causal links that are not parent/child (batches, fan-in)
  status          UNSET | OK | ERROR
}
Resource { service.name: "payment", service.version: "2.14.1", host.name, deployment.environment }

The resource describes the process that produced the spans and is sent once per batch, not per span — a simple saving. Kind lets the backend pair a CLIENT span with the SERVER span on the other side of the same call (to compute network time and correct clock skew) and build the service graph. Links handle cases a tree cannot: a batch consumer that processes messages from 50 different traces links to each, instead of pretending to be the child of one.

In storage, spans are grouped by trace id. Jaeger's Cassandra schema, for example, keeps a traces table partitioned by trace id plus separate index tables (by service name, by service and operation, by duration, by tag) that map search criteria and time buckets to trace ids — the two-query problem made concrete.

5 · High-level design and the path of one span

(1) A request reaches the gateway with no traceparent. The SDK's sampler makes a head decision — say keep 1%, decided by the trace id's bits so it is reproducible — and starts the root span. (2) Every outgoing call carries traceparent with the sampled flag; downstream services honour it (a "parent-based" sampler), so a trace is recorded everywhere or nowhere. (3) When a span ends, the SDK puts it in an in-memory queue; a background exporter sends batches (say every 5 seconds or 512 spans) over OTLP to a local agent on the same node. If the queue is full, new spans are dropped and a counter increments — the application is never blocked. (4) The agent adds host and container metadata and forwards to the gateway collectors. (5) If tail sampling is used, the gateway tier routes each span by hashing its trace id to one sampling collector, which buffers the trace and decides when it is complete. (6) Kept spans go to Kafka, partitioned by trace id. (7) Ingesters consume from Kafka and write spans to the trace store and index entries to the search index. (8) The query service serves trace-by-id and search, and a stream job reads the same Kafka topic to compute the service dependency graph and RED metrics (rate, errors, duration) per operation.

6 · Deep dive A: context propagation

Inside a process. The SDK keeps the "current span" in a context object attached to the current thread or, in async runtimes, the current task (Python's contextvars, Java's thread-locals plus context wrappers for executors, Go's explicit context.Context argument). Starting a span makes it current; starting a child reads the current span as parent. The classic breakage is handing work to a thread pool or callback without carrying the context: the work starts a new, disconnected trace. Instrumentation libraries wrap executors and async primitives to carry it automatically; Dapper's paper reports that a few dozen applications at Google still needed manual propagation for unusual control flow.

Across processes. On an outgoing call, the SDK injects the context into the carrier — HTTP headers for HTTP and gRPC (as metadata), message headers for Kafka or AMQP. On the receiving side it extracts it and starts a SERVER or CONSUMER span with that parent. A standard format matters because the call may cross languages, proxies and vendors: the W3C traceparent header is understood by OpenTelemetry SDKs, load balancers and cloud services, and tracestate carries vendor-specific extras (up to 32 entries) without breaking the shared fields. Proxies and gateways must forward these headers; a proxy that strips unknown headers silently splits traces.

Queues and batches. A message published now may be consumed in a second or a day, possibly in a batch with messages from other requests. The producer injects context into the message headers and records a PRODUCER span; the consumer creates a CONSUMER span that either continues the trace (one message per processing) or carries links to each message's producer span (batch processing). Links keep traces honest: the batch job is not "part of" 50 different requests, but each request can show that its message was processed by it.

Baggage. Sometimes services need request-scoped values that the trace context does not carry — a tenant id, a feature-flag cohort. The W3C baggage header propagates such key-value pairs to every downstream service. It is sent on every call, so it must stay small, and it must never carry secrets, because it leaves your network on any call to a third party unless stripped at the edge.

Clock skew. Each span's timestamps come from the host that recorded it. A CLIENT span on host A (start 10.000 s, end 10.050 s) and the SERVER span for the same call on host B (start 9.998 s, end 10.040 s by B's clock) cannot both be right: the server cannot start before the client sent. Viewers estimate B's offset from the pair (here B is at least 2 ms behind) and shift B's spans for display. Durations within one host are trustworthy; cross-host gaps of a few milliseconds are not, and the parent link, not the timestamp, is the source of truth for causality.

7 · Deep dive B: head versus tail sampling

Head sampling. The decision is made when the root span starts, before anything is known about the request, and propagated in the sampled flag. OpenTelemetry's ratio-based sampler computes it from the trace id — keep the trace if its id, read as a number, falls below the ratio times the maximum — so any service seeing the same trace id would reach the same decision even without the flag. Downstream services use a parent-based sampler: record if and only if the parent was sampled. Strengths: unsampled requests cost almost nothing anywhere (spans are not even exported), the volume leaving applications is cut at the source, and every kept trace is complete. Weakness: the decision is blind. If 0.1% of requests fail and you keep 1%, you keep one failing trace in a thousand failing requests; a bug that happens once an hour is captured once in 100 hours on average. Dapper reported that for high-volume services, sampling as low as 1/1024 still gave enough data for most analyses, because a pattern that matters appears thousands of times; its adaptive sampler targeted a number of traces per unit time instead of a fixed probability, so low-traffic services sampled more.

Tail sampling. The decision is made after the trace is complete, using what happened in it. Every service records and exports every span (or a generous head sample). A gateway tier routes spans by trace id — the OpenTelemetry load-balancing exporter does this with consistent hashing — so all spans of a trace reach the same sampling collector. That collector holds each trace in memory for a decision wait (30 seconds by default in OpenTelemetry's tail-sampling processor), then evaluates policies: keep if any span has status ERROR; keep if the root's duration exceeds 2 seconds; keep traces for VIP tenants; otherwise keep 1% at random; and rate-limit the total. Policies available in that processor include latency, status code, probabilistic, string and numeric attribute, rate limiting, span count and composite.

Head sampling worked. A customer reports one failed payment at 14:03. Errors on that path occur at 0.05% of 2,000 requests per second, one per second. At 1% head sampling, the chance that this customer's trace was kept is 1%. You will find other failing traces (about 36 per hour are kept), which is often enough to diagnose a systematic bug, but not this customer's specific request.

Tail sampling worked. With all errors kept, the customer's trace is there. The cost: all 2 million spans per second go to the sampling tier; it buffers 30 GB of span data; if one trace's spans arrive over more than 30 seconds (a slow batch step), the later spans arrive after the decision and are dropped or kept separately by a cached decision; and if traffic spikes so that more traces are in flight than the configured num_traces (50,000 by default in the processor), the oldest are evicted before they are evaluated — at 100,000 traces per second and a 30-second wait you need room for 3 million, so the default would be far too small.

The hybrid most teams run. Head-sample at a rate that caps application and network overhead (say 10-25%), export every span with an error regardless of the head decision (so the collector can upgrade those traces), and tail-sample inside that stream. Record the sampling probability on every kept trace, so analyses can re-weight: a trace kept at 1% stands for 100 requests, one kept because it errored stands for itself.

8 · Deep dive C: storage and query

Two access patterns. Lookup by trace id — someone pastes an id from a log line, an error page or an exemplar on a metrics chart (in6) — must return every span of that trace, quickly. Search — "slow checkout traces with errors for gold customers in the last hour" — must scan many traces by service, operation, time, duration and attributes and return a list of trace ids with summaries.

Lookup by id. Store spans in a key-value or wide-column store partitioned by trace id (in2): all spans of a trace are one partition, read in one request. Writes are append-only and high-volume; reads are rare and by key — the shape Cassandra-style stores handle well. Dapper wrote each trace as a single Bigtable row with one column per span, which exploited Bigtable's sparse rows for traces of arbitrary size. Since trace ids are random, partitions spread evenly across nodes. Retention is enforced by time-to-live on rows, or by dropping whole daily tables, which is much cheaper than deleting rows.

Search with index tables. In a key-value store, search needs explicitly maintained indexes: for each kept trace, the ingester writes entries such as (service, time bucket) → trace id; (service, operation, time bucket) → trace id; (service, duration, time bucket) → trace id; (service, tag key=value, time bucket) → trace id. A query reads the most selective index range and intersects the results, then fetches summaries. This is fast for the indexed fields and impossible for anything not indexed; every indexed tag multiplies write volume, so tag indexing is limited to an allow-list.

Search with a columnar store. The alternative stores spans in a columnar database (ClickHouse is common for this; db12 explains columnar storage) with columns for service, name, duration, status and a map of attributes, sorted by service and time. A query filters on columns and scans compressed data very fast, so any attribute is searchable without pre-declared indexes, at the cost of more CPU per query. Lookup by trace id then needs either a secondary structure (a skip index or a separate small table from trace id to time range) or scanning a time window. Many modern backends take a third path: write spans as large compressed blocks to object storage, keep a small index from trace id to block (often with Bloom filters), and search by scanning blocks in parallel — cheapest storage, slower search.

Assembly and late spans. Spans of one trace arrive from many hosts over seconds to minutes (batched exporters flush every few seconds; a slow downstream may finish long after the root). The store does not need complete traces — it appends spans to the trace's partition as they come — but anything that computes per-trace results (tail sampling, trace-level metrics, "root duration" indexes) must decide when a trace is "complete enough", usually by a quiet period after the last span. Dapper reported a median of under 15 seconds from application to central repository, with a long tail: its 98th percentile was under two minutes about 75% of the time and could grow to hours.

Derived data. The same span stream yields cheap, unsampled-quality aggregates if computed before sampling: request rate, error rate and latency histograms per service and operation, and a service dependency graph from CLIENT→SERVER pairs. Computing them in the collector before tail sampling gives accurate metrics from 100% of spans while storing only a few percent of traces — the most useful single optimisation in a tracing pipeline.

9 · Failure modes and trade-offs

Broken propagation. A proxy strips headers or a thread pool loses context: traces split into fragments, each looking like a separate request. Detect by counting traces whose root span is a SERVER span with a remote caller (an orphan) and by checking that SERVER spans have parents for internal callers.

Backend overload. If collectors fall behind, SDK queues fill and spans are dropped at the source — the right failure, but it should be visible: export failure and drop counters per service. Kafka in front of storage absorbs storage slowness; without it, an Elasticsearch or Cassandra hiccup turns into collector back-pressure and drops.

Cardinality and cost blow-ups. One team adds a span per cache lookup, or puts a user id into span names: span count or index size jumps overnight. Enforce per-service span budgets, keep high-cardinality values in attributes, not names, and alert on volume per service.

Sensitive data. SQL statements with literal values, URLs with tokens, prompts with personal data end up in attributes. Dapper stored RPC method names but no payloads, with application annotations as an explicit opt-in. Scrub in the collector (attribute processors that hash or remove known keys), and default content capture to off.

Trade-offs to close on. Head (cheap, unbiased, blind) versus tail (targeted, expensive, stateful). Key-value plus index tables (fast lookups, limited search) versus columnar (flexible search, more CPU) versus object storage blocks (cheapest, slowest). Collection latency versus batching efficiency. Detail (more spans) versus cost. And always: tracing must fail open — dropping spans is acceptable, slowing requests is not.

Why sampling by trace id keeps traces whole

If each service flipped its own coin, a trace touching 20 services would almost never be recorded completely. Two mechanisms prevent this. Propagating the decision in the sampled flag makes downstream services follow the root. And computing the decision deterministically from the trace id means that even a component that never saw the flag — Dapper's second-round sampling in its collectors, for example — reaches the same answer: Dapper hashed the trace id to a number between 0 and 1 and kept the span only if it fell below the collection coefficient, so whole traces were kept or dropped together. Changing one coefficient adjusted the global write rate.

Adaptive and rate-based sampling

A fixed probability over-samples busy services and under-samples quiet ones: 1% of 50,000 requests per second is 500 traces per second, 1% of 2 per second is one trace every 50 seconds. Dapper moved toward an adaptive scheme parameterised by a desired number of sampled traces per unit time, and recorded the probability actually used with each trace. Jaeger offers remote sampling, where SDKs poll the backend for per-service and per-operation probabilities, including adaptive ones computed from observed traffic. The essential detail is recording the probability with each trace, or every count computed from traces will be wrong.

Exemplars: the bridge between metrics and traces

A latency histogram on a dashboard tells you the p99 jumped; it cannot tell you which request. Exemplars attach a sample trace id to a histogram bucket at write time, so a click on the spike opens a real trace from that bucket (in6). This only works if the trace was kept, which is an argument for tail sampling slow requests, or for at least keeping traces whose ids were recorded as exemplars.

Span metrics before sampling

Request rates, error rates and latency distributions computed from spans are exact only if computed before sampling. Putting a span-to-metrics processor in the collector tier, ahead of the tail sampler, gives per-operation RED metrics from 100% of traffic while storing perhaps 2% of traces. The metrics flow to the time-series system; traces remain the drill-down. This also means the cost of 100% export buys you something even for traces you discard.

Tracing LLM and agent workloads

An LLM request is a short trace with very different span costs: a 30 ms retrieval, a 2-second model call, a tool call that waits on an external API. Useful attributes are not HTTP routes but model name, token counts, time to first token, cache hits and finish reasons; OpenTelemetry's GenAI conventions (marked as in development) name them, for example gen_ai.operation.name, gen_ai.request.model, gen_ai.usage.input_tokens and gen_ai.usage.output_tokens. Agents break assumptions: one task can run for minutes and produce hundreds of spans, sub-agents may run in parallel, and the interesting outcome (did the task succeed? did the user approve?) is known only at the end or later. Tail-sample on outcome and cost rather than latency, link spans from asynchronous sub-tasks instead of nesting them, and keep prompt and completion text out of spans by default, storing it — when enabled — in a separate, access-controlled store referenced by span id.

Trace ids everywhere else

A trace is only useful if people can get to it. Write the current trace id into every log line (most logging libraries can add it automatically from the active context), return it in a response header on errors so support staff can paste it, and attach it as an exemplar to metrics. Then the three signals join on one key: an alert on a metric leads to an exemplar trace, the trace's slow span leads to that service's logs for the same trace id. The catch is sampling: a log line can carry the id of a trace that head sampling dropped. Either keep traces whose ids were surfaced (tail sampling can treat "logged an error" as a keep policy), or make the UI say clearly that the trace was not sampled rather than showing an empty page.

Out-of-band collection, and why

Dapper deliberately did not send trace data back to callers inside RPC responses. Its paper gives two reasons: many responses are small (often under ten kilobytes) while traces can have thousands of spans, so in-band data would dwarf application data and change the network behaviour being measured; and in-band schemes assume perfect nesting, while much middleware returns before all of its own backends have finished. Writing spans to local logs (or a local agent) and collecting them separately keeps tracing's footprint off the request path — the same principle as the SDK's drop-if-full queue.

The real case: Dapper, and the standards that followed

Google's Dapper paper (Sigelman, Barroso, Burrows, Stephenson, Plakal, Beaver, Jaspan and Shanbhag, 2010) reports two years of running tracing across Google's production fleet, and most of today's tracing design comes from it. Traces are trees of spans; each span records its name, span id and parent id, and all spans of a trace share a trace id — all probabilistically unique 64-bit integers in Dapper (W3C later standardised a 128-bit trace id). Instrumentation was confined to a small set of libraries — the RPC framework, threading and control-flow code — under 1,000 lines of C++ and 800 lines of Java, which gave near-universal coverage without developers' involvement. Spans were written to local log files, pulled by a daemon on every machine, and written to regional Bigtable repositories, one row per trace and one column per span.

The paper's numbers are still the reference for overhead and scale: 204 ns to create and destroy a root span and 176 ns for other spans; about 9 ns for an annotation on an unsampled span and 40 ns on a sampled one; the collection daemon below 0.3% of one core; 426 bytes per span on average and less than 0.01% of network traffic; more than 1 TB of sampled trace data per day, with users wanting two weeks of retention; and a median collection latency under 15 seconds. On sampling, it found that tracing every request in a web-search cluster had a noticeable latency cost, that the cost was within measurement error at rates below 1/16, and that 1/1024 still gave enough data for high-volume services; it added a second, trace-id-based sampling stage in collection to control repository write load.

The open-source lineage made this a standard. Twitter's Zipkin implemented the Dapper model with pluggable transports and storage; Uber's Jaeger followed, and Jaeger v2 is now itself a distribution of the OpenTelemetry Collector, with roles for collector, query and an ingester that reads from Kafka, and storage backends including Cassandra, Elasticsearch, OpenSearch, ClickHouse and Badger. The W3C Trace Context Recommendation (2021) fixed the propagation format so that traces survive crossing vendors and clouds, and OpenTelemetry unified the SDKs, the OTLP wire protocol and the collector, whose tail-sampling processor makes the trade-offs in this lesson concrete configuration.

Failure modes you will see

Orphan spans everywhere after a proxy upgrade. The new proxy version strips unknown headers; every trace splits at that hop. Detection: a spike in root spans for internal services. Fix: forward traceparent, tracestate and baggage explicitly.

Tail sampler out of memory during an incident. Error traffic doubles traffic volume (retries), traces take longer (timeouts), so more traces are in flight for longer; the sampler evicts before evaluating — exactly when you need the traces. Size for incident traffic, cap per-trace span counts, and shorten the decision wait under pressure.

Search is slow but lookups are fast. Index tables were not written for a tag people now filter on, or the columnar store's sort key does not match the common filter. Revisit which attributes are indexed, from query logs.

Missing spans from short-lived jobs. A batch job or serverless function exits before its exporter flushes. Flush on shutdown, and give functions a synchronous flush at the end of each invocation.

What to monitor in the tracing system itself

Spans received, dropped (SDK queue full, collector refused) and exported per service; collector queue sizes and memory; tail-sampler traces in flight, evictions before decision, and decisions per policy; Kafka lag for ingesters; end-to-end latency from span end to searchable; storage write errors; orphan-span rate; and span volume per service against its budget.

Goal: build a tiny tracer that propagates a W3C traceparent through three fake services and prints the trace tree, then simulate head and tail sampling on 100,000 synthetic traces and see what each keeps. Python 3.12 standard library.

"""Mini tracer: traceparent propagation across 3 'services', a trace tree, head vs tail sampling."""
import contextvars, os, random, time

SPANS = []                                            # stands in for the exporter
current = contextvars.ContextVar("current", default=None)

class Span:
    def __init__(self, name, trace_id, parent_id, sampled):
        self.name, self.trace_id, self.parent_id, self.sampled = name, trace_id, parent_id, sampled
        self.span_id = os.urandom(8).hex()
        self.start = time.perf_counter(); self.end = None; self.error = False
    def __enter__(self):
        self.token = current.set(self); return self
    def __exit__(self, exc_type, *_):
        self.end = time.perf_counter(); self.error = exc_type is not None
        current.reset(self.token)
        if self.sampled: SPANS.append(self)
        return False
    def traceparent(self):                            # what goes on the wire
        return f"00-{self.trace_id}-{self.span_id}-{'01' if self.sampled else '00'}"

def start_span(name, headers=None):
    parent = current.get()
    if parent:                                        # in-process child
        return Span(name, parent.trace_id, parent.span_id, parent.sampled)
    if headers and "traceparent" in headers:          # extract from the incoming request
        ver, tid, pid, flags = headers["traceparent"].split("-")
        return Span(name, tid, pid, int(flags, 16) & 1 == 1)
    tid = os.urandom(16).hex()                        # new root: head decision from the trace id
    return Span(name, tid, None, int(tid[:8], 16) / 0xFFFFFFFF < HEAD_RATE)

# --- three fake services calling each other over 'HTTP' (a dict of headers) -------------
def remote(service, headers):                         # a fresh Context = a separate process
    return contextvars.Context().run(service, headers)

def inventory(headers):
    with start_span("inventory: reserve", headers): time.sleep(0.01)

def payment(headers):
    with start_span("payment: charge", headers):
        with start_span("payment: card network"): time.sleep(0.03)

def checkout():
    with start_span("checkout: POST /order") as root:
        with start_span("checkout: call inventory") as c:
            remote(inventory, {"traceparent": c.traceparent()})
        with start_span("checkout: call payment") as c:
            remote(payment, {"traceparent": c.traceparent()})
        print("root traceparent:", root.traceparent())

HEAD_RATE = 1.0
checkout()
by_parent = {}
for s in SPANS: by_parent.setdefault(s.parent_id, []).append(s)
def show(parent_id, depth=0):
    for s in sorted(by_parent.get(parent_id, []), key=lambda s: s.start):
        print("  " * depth + f"{s.name:<28} {1000 * (s.end - s.start):6.1f} ms  span={s.span_id}")
        show(s.span_id, depth + 1)
show(None)

# --- head vs tail on 100k synthetic traces: 0.1% errors, 1% slow ---------------------------
random.seed(3)
traces = [{"error": random.random() < 0.001, "ms": random.lognormvariate(4, 0.5) * (8 if random.random() < 0.01 else 1)}
          for _ in range(100_000)]
head = [t for t in traces if random.random() < 0.01]
tail = [t for t in traces if t["error"] or t["ms"] > 500 or random.random() < 0.01]
for name, kept in (("head 1%", head), ("tail err+slow+1%", tail)):
    print(f"{name:>17}: kept {len(kept):5} traces, errors {sum(t['error'] for t in kept):3} "
          f"of {sum(t['error'] for t in traces)}, slow(>500ms) {sum(t['ms'] > 500 for t in kept):4} "
          f"of {sum(t['ms'] > 500 for t in traces)}")
  1. Run it. The tree should show checkout: POST /order at the top, the two CLIENT call spans beneath it, each service's SERVER span beneath its call, and the card-network span under payment: charge — even though the services ran in a fresh context and received only a header string. That is propagation.
  2. Break it on purpose: replace with start_span("checkout: call payment") as c: with c = start_span("checkout: call payment") (and dedent the next line). The CLIENT span is never ended or exported, so payment's whole subtree vanishes from the printed tree — its parent is missing. Real HTTP client wrappers that forget to end their span cause exactly this.
  3. Set HEAD_RATE = 0.0: nothing is exported, and the printed flags end in -00. Every downstream service follows the root's decision.
  4. Read the sampling comparison: head sampling keeps about 1,000 traces but only around 1% of the ~100 errors and slow traces; tail sampling keeps all of them for a few hundred more traces. Then count what tail sampling had to receive: all 100,000.
Estimate it

Your platform serves 40,000 requests per second at peak, each producing 35 spans of about 400 bytes. Leadership wants "every error trace kept" (errors are 0.2% of requests) plus a 2% baseline, 7 days of retention, and the tracing bill under control. (a) What does the collector tier receive? (b) How much is stored per day and in total? (c) How much memory do tail samplers need with a 20-second decision wait? (d) What would you change if that memory is too much?

Answer

(a) 40,000 × 35 = 1.4 million spans per second; × 400 B = 560 MB/s (about 4.5 Gbit/s) into the collector tier, because tail sampling needs every span.

(b) Kept traces: 0.2% errors + 2% baseline ≈ 2.2% (the overlap is negligible). 1.4M × 2.2% ≈ 30,800 spans/s × 400 B ≈ 12.3 MB/s ≈ 1.06 TB per day; 7 days ≈ 7.4 TB raw, roughly 1.5 TB at 5× compression, ×3 replication ≈ 4.5 TB on disk.

(c) In flight: 1.4M spans/s × 20 s = 28 million spans × 400 B = 11.2 GB of span data, so roughly 22-34 GB of memory with object overhead, spread over the sampler tier (for example 8 instances of 4 GB). The trace capacity setting must cover 40,000 traces/s × 20 s = 800,000 traces, plus headroom for incident traffic.

(d) Head-sample first, keeping errors: SDKs sample 20% at the head but always export spans of traces that end in error (or export error spans unconditionally and let the collector upgrade them). The tail tier then receives about 20% plus errors — around 115 MB/s and 5-7 GB of memory — while every error still arrives. Also compute RED metrics in the collector before sampling, so dashboards stay exact. Mention the remaining gap: an error recorded only in a downstream service of a head-dropped trace arrives as a partial trace, which is still more useful than none.

Diagnose it

After moving a service to an async framework, its traces in the UI show the incoming request span with no children, and dozens of new single-span "traces" appear for its database calls. What is wrong?

Answer

Context is lost inside the process. The database calls run in tasks or callbacks that do not inherit the current span, so each starts a new root span with a new trace id. The fix is in-process propagation: use the framework's OpenTelemetry instrumentation (which carries context across awaits and executors), or pass the context explicitly when scheduling work (Python contextvars are copied into new asyncio tasks automatically, but not into thread pools without wrapping; Go needs ctx passed down; Java needs context-wrapping executors). Detect it in future by alerting on root spans whose kind is CLIENT (a database call should never be a root) — they mean propagation broke.
