A company runs 2,000 servers and 400 services. Each service team has its own spreadsheet of which machines run their code. Deploys are a script that copies binaries to a list of hosts. When a machine dies at night, someone is paged to move its services by hand. Average CPU utilisation is 15%, because every team over-provisions its own machines for its own peak. A new team waits three weeks for hardware. And when the company wants to run large ML training jobs on its GPU machines, nobody can tell which GPUs are free.

A container orchestrator solves this by turning the fleet into one pool. Teams stop saying "run this on hosts 17-23" and start saying "keep three copies of this container running, each needing 2 CPUs and 4 GB of memory, spread across zones". The system decides where they go, starts them, watches them, restarts them when they crash, moves them when machines fail, and packs many teams' work onto the same machines so utilisation rises. Google's Borg paper puts the stakes plainly: increasing utilisation by a few percentage points can save millions of dollars, and segregating its production and batch work into separate clusters would have needed 20-30% more machines in the median cell.

Designing one is a control-plane problem. The data plane — the containers serving traffic — must keep running no matter what. The control plane — the brain that stores what should exist, decides placement and reacts to failure — must be consistent (two schedulers must not both place the same work), available enough to make changes, and fast enough to place thousands of containers a minute across thousands of machines. It must detect dead machines without mistaking a network glitch for a mass failure. And it must be built so that its own failure does not take the data plane down with it.

This lesson designs the control plane of a mini Kubernetes in interview order: requirements; estimates (nodes, pods, heartbeat and pod-churn write rates into the store, scheduler throughput, state size); the API and the object model; the high-level design; then three deep dives — the declarative desired-state model and reconciliation loops, the scheduler's filter-then-score pass worked on four nodes with real numbers (and bin-packing versus spreading), and failure detection, leader election and what happens to running workloads when the control plane is down. sc15 and os13 introduced containers, Kubernetes objects and the kernel features underneath; in8 owns etcd and Raft. Here we design what sits between them. The real cases are Google's Borg paper and the "Borg, Omega, and Kubernetes" retrospective, with the Kubernetes scheduler and node documentation; the lab is a toy scheduler with filter and score, plus a reconcile loop that heals a killed pod.

The mental model: a thermostat, not a remote control

A remote control sends commands: "turn on", "volume up". If the TV misses the signal, nothing happens, and nobody notices. A thermostat works differently: you set the desired temperature, and it keeps measuring the room and turning the heating on or off until the room matches — forever. If someone opens a window, it compensates. If the thermostat reboots, it simply measures again and continues. You never tell it what to do; you tell it what you want.

An orchestrator is a building full of thermostats. You write down desired state — "3 replicas of web:v2, each requesting 2 CPU and 4 GiB" — as an object in a database. Separate controllers, each a thermostat for one kind of thing, keep comparing desired state with actual state and act to close the gap: one makes sure the right number of pods exist; the scheduler assigns each new pod to a machine; the agent on each machine (the kubelet in Kubernetes, the Borglet in Borg) makes sure the containers assigned to its machine are running; another controller notices machines that have gone quiet. None of them commands another. They all read and write objects through one API server, which stores them in a small, strongly consistent store (etcd, in8).

The analogy breaks in two useful places. A room has one temperature; a cluster has thousands of interacting objects, so controllers must cope with conflicts (two writers changing the same object), and they do so with version numbers on every object. And a thermostat can measure the room directly; a controller sees the world only through reports from agents on machines, which arrive late or not at all — so "the machine stopped reporting" is not the same as "the machine is dead".

Control plane and data plane

The most important split in the design is between the control plane (API server, store, scheduler, controllers) and the data plane (node agents, container runtimes and the containers themselves, plus the network rules that route traffic to them). The control plane decides; the data plane does. A good design lets the data plane run on its last instructions when the control plane is unavailable — what AWS calls static stability, and what Borg described as tasks continuing to run even if all Borgmaster replicas fail. Keep asking, at each step of the design, "what happens to running containers if this part is down?"

The vocabulary in the order you need it

A pod is the unit of scheduling: one or more containers that share a network address and run together on one node. A node is a machine with an agent. Each container declares requests (what it needs, used for placement) and limits (caps enforced by cgroups on the node, os13). A Deployment declares "N replicas of this pod template", a ReplicaSet maintains exactly N, and a Service gives the replicas one stable address. Every object has a spec (desired state, written by users) and a status (actual state, written by the system).

1 · Requirements

Functional. (1) Users declare workloads: a container image, replica count, resource requests and limits, placement constraints (zones, labels, GPU type), and update strategy. (2) The system places each replica on a suitable node and starts it. (3) It keeps the declared number running: restarts crashed containers, replaces pods on failed nodes. (4) Rolling updates and rollbacks. (5) Scaling up and down on request. (6) Priorities: high-priority work can preempt low-priority work. (7) Expose status: what is running where, and why something is pending. Out of scope, said aloud: container networking internals (net10 and sc15), storage volumes, autoscaling policy, and multi-cluster federation.

Non-functional. Static stability: running workloads must not depend on the control plane being up. Correctness: never run two copies of something declared as one, never place more on a node than its allocatable resources (by requests). Scale: thousands of nodes and around a hundred thousand pods per cluster. Scheduling throughput: at least tens of pods per second sustained, with bursts during deploys. Failure detection within about a minute, replacement within minutes, without overreacting to network partitions. Control-plane availability high enough that deploys and recovery work (Borg reported 99.99% for its master).

Clarifying questions. How big are clusters, and is one cluster per region acceptable? Mixed workloads (latency-sensitive services and batch jobs on the same machines)? GPUs and large training jobs? Multi-tenant (several teams with quotas) or single-team? How quickly must a dead node's work be replaced?

2 · Back-of-envelope estimates

Size for the envelope Kubernetes documents as supported for one cluster: 5,000 nodes, no more than 110 pods per node, and 150,000 pods in total. (Borg's median cell was about 10,000 machines, with some much larger.)

Heartbeat writes. Each node renews a heartbeat lease every 10 seconds: 5,000 ÷ 10 = 500 writes per second to the store, just to say "still alive". This is why heartbeats are a tiny separate Lease object rather than an update to the large Node object — each write is replicated through Raft to every etcd member.

Pod churn. Suppose 1% of pods are replaced per minute on average (deploys, batch jobs finishing, autoscaling): 1,500 new pods per minute = 25 per second, with deploy bursts of 10× (250 per second). Each pod lifecycle is roughly 5-10 writes (create, bind, several status updates, delete): 25 × 8 ≈ 200 writes per second average, about 2,000 in bursts.

Total store load. About 700-1,000 writes per second steady, a few thousand in bursts. A well-provisioned etcd cluster on fast disks handles thousands of small writes per second; each write needs a Raft round and an fsync on a majority, so disk latency is the limit. Reads are mostly served by the API servers' in-memory watch caches, not etcd.

State size. A pod object with its spec and status is a few kilobytes; call it 5 KB. 150,000 × 5 KB = 750 MB for pods, plus nodes, services, endpoints, config maps and events: on the order of 1-2 GB. etcd's default storage quota is 2 GiB and 8 GiB is its suggested maximum, and a single request is limited to 1.5 MiB. The control-plane store must stay small — the reason large blobs and logs never go into it.

Scheduler throughput. 25 pods per second steady and 250 in bursts. Evaluating 5,000 nodes per pod at, say, 1 µs per filter-and-score is 5 ms per pod — 200 pods per second on one thread, borderline for bursts. Scoring only a sample of feasible nodes (Kubernetes' default falls toward 10% at 5,000 nodes) cuts that by ten; parallelising filters across cores cuts it further.

Watch fan-out. 5,000 kubelets each watch their own pods; controllers watch everything of their type. A pod update fans out to every watcher of that object type, which is why API servers keep a watch cache and send each change once to many watchers from memory.

3 · The API

One uniform, resource-oriented API over versioned objects. Every object type supports the same verbs, which is what lets dozens of controllers and tools share it.

POST   /apis/apps/v1/namespaces/shop/deployments           {spec: {replicas: 3, template: {...}}}
GET    /api/v1/namespaces/shop/pods?labelSelector=app=web
GET    /api/v1/pods?fieldSelector=spec.nodeName=node-17&watch=true&resourceVersion=88123
       → stream of {type: ADDED|MODIFIED|DELETED, object: {...}}
PUT    /api/v1/namespaces/shop/pods/web-7f9c/status          (kubelet reports status)
POST   /api/v1/namespaces/shop/pods/web-7f9c/binding         {target: {kind: Node, name: node-17}}  (scheduler)
PUT    /apis/coordination.k8s.io/v1/namespaces/kube-node-lease/leases/node-17   (heartbeat)

Watch is the key verb. A client lists objects, notes the resourceVersion (a cluster-wide, monotonically increasing version from the store), then watches from that version and receives every subsequent change in order. If the connection drops, it resumes from the last version it saw; if that version is too old, it lists again. Controllers are built on list-then-watch plus a local cache.

Optimistic concurrency. Every write carries the object's resourceVersion as read; the API server rejects the write with a conflict if the object changed meanwhile, and the writer re-reads and retries. No locks, and two controllers can never silently overwrite each other's changes.

5 · High-level design and the path of one deployment

Follow kubectl apply of a 3-replica Deployment. (1) The API server authenticates, authorises, runs admission checks (quota, defaults, policy), and stores the Deployment in etcd. (2) The Deployment controller, watching Deployments, sees a new one with no ReplicaSet and creates one. (3) The ReplicaSet controller sees desired 3, actual 0, and creates three Pod objects with empty nodeName. (4) The scheduler, watching for unscheduled pods, takes each from its queue, filters and scores nodes, and writes a binding: nodeName: node-17. (5) The kubelet on node-17, watching for pods assigned to its node, sees the new pod, pulls the image, creates the containers with the requested cgroup limits through the container runtime, runs readiness probes, and writes status Running and Ready. (6) The endpoints controller adds the pod's IP to the Service's endpoints; network proxies on every node update their routing. No component called another: each reacted to an object changing.

6 · Deep dive A: desired state and reconciliation loops

Imperative versus declarative. An imperative system executes commands: "start a container on node 17". If the command is lost, nothing happens; if it runs twice, two containers start; if the node dies later, nothing notices. A declarative system stores the goal: "3 replicas". Borg's paper lists this as a core availability technique: declarative desired-state representations and idempotent mutating operations, so a failed client can harmlessly resubmit any forgotten requests.

The loop. Every controller has the same skeleton:

loop forever:
    desired = read spec of objects I own            # from my local cache, fed by watch
    actual  = observe what exists                   # other objects, or the node itself
    diff    = desired - actual
    for each difference: take one corrective action through the API
    wait for a change notification, or a periodic resync timeout

Level-triggered, not edge-triggered. An edge-triggered controller acts on events: "pod deleted → create one". If it misses the event (crashed, disconnected), the pod is never replaced. A level-triggered controller acts on the state: "there should be 3, there are 2 → create one". Events are only a hint to look now; a periodic resync re-checks everything anyway. This makes controllers robust to restarts, missed watch events, and duplicate notifications — the property that lets a cluster heal itself without a coordinator.

A trace of healing. t = 0: ReplicaSet wants 3; pods a, b, c are Running. t = 1 s: the container in pod b crashes; the kubelet on its node restarts it locally (restart policy Always) with exponential back-off — the control plane is not involved. t = 60 s: the node hosting pod c loses power. Its lease stops renewing. t ≈ 110 s: after the 50-second grace period, the node controller marks the node not ready and adds the unreachable taint. t ≈ 410 s: pod c's 300-second toleration of that taint expires; the node controller evicts it (marks it for deletion). The ReplicaSet controller now sees 2 live pods, desired 3, and creates pod d. The scheduler binds d to a healthy node; its kubelet starts it. Nobody issued a command; four independent loops each closed their own gap.

Conflicts and idempotency. Two controllers may act on the same object, or one controller may restart mid-action. Optimistic concurrency (resource versions) prevents lost updates; deterministic naming and owner references prevent duplicates (a ReplicaSet that crashed after creating a pod sees it on restart, owned by itself, and does not create another). Controllers must also be careful with "expectations": after creating a pod, the controller's cache may not show it for a moment, and naive code would create another. Kubernetes' ReplicaSet controller records how many creations it expects to observe and waits for them before acting again.

7 · Deep dive B: the scheduler — filter, score, bind

Two passes. For each pending pod, the scheduler runs filters (feasibility checks: does this node have enough unrequested CPU and memory? does it match the pod's node selector and affinity? does the pod tolerate the node's taints? is the required port free? is the GPU type right?) and then scores the nodes that passed (how good is this placement?), picking the highest score. It then writes a binding. Borg's paper describes the same two phases: feasibility checking finds machines that meet the task's constraints and have enough available resources (including resources held by lower-priority tasks that could be evicted), and scoring determines the goodness of each feasible machine.

A worked pass on four nodes. The pod requests 2 CPU and 4 GiB and has no GPU toleration. Allocatable and already-requested resources (requests, not usage):

NodeAllocatableRequestedFreeNotes
N18 CPU, 32 GiB7 CPU, 10 GiB1 CPU, 22 GiB
N216 CPU, 64 GiB4 CPU, 16 GiB12 CPU, 48 GiB
N38 CPU, 16 GiB2 CPU, 10 GiB6 CPU, 6 GiB
N432 CPU, 128 GiB8 CPU, 32 GiB24 CPU, 96 GiBtaint gpu=true:NoSchedule

Filter. N1 has 1 free CPU < 2 requested: out. N4 has room but carries a taint the pod does not tolerate: out (keeping expensive GPU machines for GPU work). N2 and N3 pass.

Score with "least allocated" (Kubernetes' default for its resource-fit plugin): for each resource, the fraction left free after placing the pod, times 100, averaged. N2: CPU (16 − 6) ÷ 16 = 62.5; memory (64 − 20) ÷ 64 = 68.75; score 65.6. N3: CPU (8 − 4) ÷ 8 = 50; memory (16 − 14) ÷ 16 = 12.5; score 31.3. N2 wins — the policy spreads work onto the emptier node.

Score with "most allocated" (the bin-packing strategy): the fraction used after placement. N2: 37.5 and 31.25 → 34.4. N3: 50 and 87.5 → 68.8. N3 wins — the policy fills the fuller node and leaves N2's large free space for a big pod or for the autoscaler to reclaim.

Balance. Look at N3 after placement under bin-packing: 4 CPU free but only 2 GiB of memory. Any future pod needing 3 GiB cannot use those 4 CPUs — they are stranded. A balanced-allocation score penalises placements that make one resource's utilisation run far ahead of another's: with CPU at 50% and memory at 87.5%, N3's imbalance is large; N2's 37.5% and 31.25% are close. Kubernetes adds such a score to the resource-fit score; Borg's current scoring model was a hybrid aimed specifically at reducing stranded resources, which it reports gave about 3-5% better packing efficiency than best fit.

Bin-packing versus spreading, as a decision. Spreading keeps every node partly empty: bursts have room, one node failure takes out few replicas of each service, noisy neighbours are rarer. Bin-packing leaves some nodes empty: the cluster autoscaler can remove them (direct cost savings), and large pods (a 30-CPU job) can still find a whole free node. Borg's experience is the best evidence available: its original spreading-style scoring (a variant of E-PVM, which minimises the change in a combined cost) left headroom but fragmented capacity, especially for large tasks; best fit packed tightly but penalised any misestimate of requirements, hurting bursty services and batch jobs; the hybrid that minimised stranded resources did better than either. A useful interview answer: spread latency-sensitive services across failure domains with a spreading constraint, bin-pack batch work, and let priorities decide who yields.

Preemption. If no node passes the filters, the scheduler looks for nodes where evicting lower-priority pods would make room, picks the one that disrupts least, evicts those pods (they go back to pending through their controllers) and places the pod. Borg did the same — preempting from lowest to highest priority until the task fit and requeuing the victims rather than migrating them.

Scaling the scheduler. Evaluating every node for every pod does not scale. Kubernetes stops filtering once it has found enough feasible nodes: by default it scores a percentage that falls linearly from 50% at 100 nodes to 10% at 5,000 nodes, never below 5% and never fewer than 100 nodes, starting each search where the last one stopped so all nodes get a turn. Borg used three tricks: score caching (keep scores until a machine or task changes), equivalence classes (the tasks of one job usually have identical requirements, so compute feasibility and scores once per class), and relaxed randomisation (examine machines in random order until enough feasible ones are found). Its paper reports that scheduling a cell's entire workload from scratch typically took a few hundred seconds, and did not finish after more than three days with these techniques disabled.

Binding without races. The scheduler decides from its cache, which may be slightly stale. It "assumes" the pod onto the node in its cache immediately (so the next decision sees the reduced capacity), writes the binding asynchronously, and if the write fails, forgets the assumption and requeues. The kubelet runs a final admission check and rejects a pod that does not fit — the safety net if two schedulers or a stale cache ever double-book a node.

8 · Deep dive C: failure detection, leader election, and a dead control plane

Heartbeats. The kubelet renews a small Lease object for its node every 10 seconds, and also reports the node's status. The node controller watches leases. If a node's lease has not been renewed within the grace period (50 seconds by default in current Kubernetes), it sets the node's Ready condition to Unknown and adds the node.kubernetes.io/unreachable taint (or not-ready if the node reported itself unhealthy). Pods by default tolerate those taints for 300 seconds; when that expires, they are evicted and their controllers create replacements. Borg used polling in the other direction: the Borgmaster polled each Borglet every few seconds, which let the master control the communication rate and avoid recovery storms; a machine that missed several polls was marked down and its tasks rescheduled.

Why not faster? Because silence is ambiguous. A node behind a failed switch is still running its pods; replacing them creates duplicates — harmless for stateless web servers, dangerous for anything that must be single (a stateful database member, a job with external side effects). When communication returns, Borg told the Borglet to kill the tasks that had already been rescheduled; Kubernetes has the kubelet delete pods that the API says were evicted. Duplicates during the gap are the cost of faster replacement, and the 300-second default is a per-workload knob (tolerationSeconds) precisely so stateless services can opt into faster failover.

Rate-limited eviction. The control plane cannot tell many failed nodes from a partition between itself and many healthy nodes. Kubernetes evicts pods from at most 0.1 nodes per second by default, and when more than 55% of nodes in a zone are unhealthy it treats the zone as partitioned and slows down further (or stops in small clusters). Borg's paper lists the same rule: rate-limit finding new places for tasks from machines that become unreachable, because large-scale failure and network partition look the same.

Leader election. The scheduler and the controller manager each run as several replicas for availability, but two active schedulers would double-book nodes and two ReplicaSet controllers would create twice the pods. So exactly one replica acts at a time, chosen by a lease in the store: the leader renews the lease; others retry periodically and take over if it expires. Kubernetes' defaults are a 15-second lease duration, a 10-second renew deadline (a leader that cannot renew within 10 seconds stops acting, leaving a margin before others may take over at 15) and a 2-second retry period. The underlying guarantee comes from etcd's Raft (in8): lease updates are linearisable, so two replicas cannot both believe they hold it — with the usual caveat that a paused leader might act briefly after losing it, which resource-version checks on writes catch. Borg's master was itself five replicas with a Paxos-based store and an elected master; failover typically took about 10 seconds, up to a minute in a big cell while in-memory state was rebuilt. The API servers, by contrast, are stateless and all active behind a load balancer.

What runs when the control plane is down. Walk the components. etcd loses quorum: the API server cannot write (and, for consistent reads, cannot read). API server down: nothing can be changed or observed. Scheduler down: new pods stay pending. Controller manager down: no scaling, no replacement, no rollouts, no node-failure handling. In every case, the data plane continues: kubelets keep running the pods they already have, restart crashed containers locally, and report status when they can reconnect; the network rules on each node keep routing to the endpoints they last knew. Running workloads are unaffected unless something fails during the outage — a node dying then is not handled until the control plane returns. This is the static-stability property, and it shapes design choices elsewhere: workloads should not call the API on their request path, node agents must cache their assignments, and the control plane must be upgraded and restarted freely without user-visible impact.

9 · Failure modes and trade-offs

etcd as the bottleneck. Too many objects, large objects (big config maps), or event spam push etcd toward its size quota and slow every write; when the quota is hit, writes fail cluster-wide. Keep objects small, rate-limit events, compact and defragment regularly, and run etcd on dedicated fast disks.

Thundering herds. After an API server restart, every kubelet and controller re-lists everything at once. Watch caches, client back-off with jitter, and priority and fairness rules on the API server keep the restart from becoming an outage.

Requests that lie. The scheduler trusts requests. Pods that request little and use a lot crowd their nodes (CPU throttling, out-of-memory kills); pods that request a lot and use little waste capacity. Measure the gap and right-size requests; reclaim unused reservations for low-priority work, as Borg did.

Correlated placement. Spreading by score alone may still put all replicas of a service in one zone. Use explicit topology spread constraints or anti-affinity for anything that must survive a zone failure.

Trade-offs to close on. Declarative and eventually consistent (robust, self-healing, harder to reason about timing) versus imperative (simple, fragile). One central scheduler (simple, globally informed, a throughput ceiling) versus several optimistic schedulers (scales, needs conflict handling). Spreading versus packing. Fast failure detection (less downtime, more false positives and duplicates) versus slow (fewer mistakes, longer outages). Big clusters (better packing — Borg measured the cost of splitting) versus many small ones (smaller blast radius, simpler upgrades).

Gang scheduling and GPUs for distributed training

A data-parallel training job with 64 workers (dl9, gpu8) is useless until all 64 run, because every step waits for an all-reduce across all of them. A pod-at-a-time scheduler happily places 40 of them and leaves 24 pending, holding 40 GPUs idle indefinitely; two such jobs each half-placed can deadlock, each waiting for GPUs the other holds. Gang scheduling places a group all at once or not at all. The usual architecture adds a job-level layer: a queue with per-team quotas admits a whole job only when capacity for all its workers exists (otherwise it waits without holding anything), and a gang-aware scheduling step reserves all the nodes together. Placement is topology-aware: 8 workers per 8-GPU node so they share NVLink, and nodes in the same network block so cross-node collectives stay fast. Failure is also group-level: if one worker's node dies, the whole job restarts from its last checkpoint, so checkpoint frequency trades lost work against checkpoint overhead. Large jobs waiting for a gang leave GPUs idle; backfilling with small preemptible jobs, and preempting them when the gang can start, recovers that capacity.

Resource reclamation and overcommit

Requests are reservations, and services reserve for rare peaks. Borg estimated each task's real usage every few seconds (its "reservation", from fine-grained usage plus a safety margin) and let lower-priority batch work use the difference between limits and reservations; production tasks were scheduled against limits and never relied on reclaimed resources. About 20% of the workload in a median cell ran in reclaimed resources. When Google tested more aggressive safety margins on a live cell for a week, reservations moved closer to usage and out-of-memory events rose slightly — and the team chose a medium setting. The same knob exists in any orchestrator: Kubernetes' quality-of-service classes (guaranteed, burstable, best-effort) decide which pods are killed first when a node runs short.

Why one API and labels

The Borg-Omega-Kubernetes retrospective describes how Borg grew many special-purpose APIs and clients, and how Kubernetes instead put every piece of state behind one uniform, versioned object API with list, watch and optimistic concurrency, so that new controllers could be added without changing the core. Labels — arbitrary key-value tags with selectors — replaced fixed groupings: a Service selects pods by label, a ReplicaSet counts pods by label, an operator can temporarily remove a pod from a Service by changing its label to debug it while the ReplicaSet starts a replacement. Composability came from those two choices.

Shared-state schedulers: the Omega idea

A single scheduler is a throughput ceiling and a bottleneck for specialised policies (batch, ML, services each want different logic). Google's Omega explored giving several schedulers a shared view of cluster state and letting each commit placements optimistically, with conflicts detected at commit time and retried. Kubernetes supports multiple schedulers through a field on the pod naming its scheduler; the kubelet's final admission check and resource-version conflicts protect against double-booking. The cost is wasted work on conflicts when clusters are nearly full.

Cluster size: one big pool versus many small ones

Borg's evaluation used "compaction" — how small a cell could be and still fit its workload — to compare policies, and showed that splitting workloads into separate cells costs machines: separating production and non-production work needed 20-30% more machines in the median cell, because production jobs reserve for spikes they rarely hit and batch work fills the gaps. The counter-pressure is blast radius and operability: a control-plane bug, a bad upgrade or an etcd problem affects the whole cluster. Many organisations settle on large clusters per region with strict isolation between namespaces, plus a few separate clusters for regulated or very risky workloads.

Testing the control plane

Borg kept periodic checkpoints of its master's state and a simulator (Fauxmaster) that ran the production scheduler code against them, which let the team debug failures and evaluate policy changes on real workloads offline. The general lesson: the scheduler and controllers are deterministic functions of state, so record the state and replay it. Policy changes (a new scoring weight) should be evaluated by replaying real snapshots and comparing outcomes — packing efficiency, pending time, preemptions — before rollout. A scoring change that looks better on average can still starve one class of pods, so compare pending-time distributions per priority, not just the mean.

The real case: Borg, and what Kubernetes kept

Google's Borg paper (Verma, Pedrosa, Korupolu, Oppenheimer, Tune and Wilkes, EuroSys 2015) describes the cluster manager that ran most of Google's workloads. A cell — median about 10,000 machines — has one logically centralised controller, the Borgmaster, and an agent, the Borglet, on each machine. The Borgmaster is replicated five times, with state kept in memory and in a Paxos-based store on the replicas' disks; one elected master serves as both the Paxos leader and the state mutator, and failover typically takes about 10 seconds. It reports 99.99% availability for the Borgmaster in practice, from replication, admission control and deliberately simple dependencies. The scheduler is a separate process that scans pending tasks by priority and assigns them with feasibility checking and scoring, made scalable by score caching, equivalence classes and relaxed randomisation. A busy Borgmaster used 10-14 CPU cores and up to 50 GiB of RAM, and several cells had arrival rates above 10,000 tasks per minute.

The availability design is the part every interview should borrow: tasks keep running when the master or their own Borglet goes down; mutations are declarative and idempotent; rescheduling from unreachable machines is rate-limited; task-machine pairings that crash are avoided. And the utilisation results justify building such a system at all: segregating production and batch work would cost 20-30% more machines in the median cell, and resource reclamation let about 20% of the workload run in capacity that would otherwise sit reserved and idle.

The "Borg, Omega, and Kubernetes" retrospective (Burns, Grant, Oppenheimer, Brewer and Wilkes, ACM Queue 2016) explains what changed in Kubernetes: everything goes through one API server over a consistent store; controllers are independent reconciliation loops rather than one monolithic master; labels replace fixed job/task groupings; and pods give each group of containers its own IP address. The Kubernetes documentation encodes the operational numbers this lesson used: lease heartbeats every 10 seconds, a 50-second grace period, 300-second default tolerations, eviction at 0.1 nodes per second, a 55% unhealthy-zone threshold, and a supported envelope of 5,000 nodes and 150,000 pods.

Failure modes you will see

Pods stuck Pending. The scheduler's events say why: insufficient CPU, no node matches affinity, untolerated taint. Usually requests are too large or constraints too strict; sometimes the cluster is genuinely full and the autoscaler is slow.

Mass eviction after a network blip. A short partition between the control plane and a rack exceeds the grace period; nodes are tainted; if tolerations are short, pods are evicted and recreated elsewhere while the originals still run. Zone-aware rate limits and sensible tolerations are the guard.

etcd quota exceeded. Writes fail cluster-wide with "database space exceeded". Compaction and defragmentation, and finding the object type that grew (often events or a misbehaving controller writing large objects).

Controller hot loops. Two controllers fighting over a field (each "correcting" the other) generate endless writes. Watch for objects with rapidly increasing resource versions.

What to monitor

API server request latency and error rate by verb; etcd write latency (fsync), database size and leader changes; scheduler queue length, scheduling latency and attempts per pod; pending pods by reason; node Ready counts and lease ages; eviction counts; controller work-queue depth and retries; and for the data plane, container restarts and out-of-memory kills per node.

Goal: build a toy scheduler that filters and scores the four nodes from the lesson under two policies, then a reconcile loop that keeps three replicas running while a chaos function kills pods and a node. Python 3.12 standard library.

"""Toy orchestrator: filter + score scheduling, and a level-triggered reconcile loop that heals."""
import itertools, random

NODES = {   # name: allocatable, requested, taints
    "N1": {"cpu": 8,  "mem": 32,  "req_cpu": 7, "req_mem": 10, "taints": set(), "up": True},
    "N2": {"cpu": 16, "mem": 64,  "req_cpu": 4, "req_mem": 16, "taints": set(), "up": True},
    "N3": {"cpu": 8,  "mem": 16,  "req_cpu": 2, "req_mem": 10, "taints": set(), "up": True},
    "N4": {"cpu": 32, "mem": 128, "req_cpu": 8, "req_mem": 32, "taints": {"gpu"}, "up": True},
}

def feasible(node, pod):
    if not node["up"]: return "node down"
    if node["cpu"] - node["req_cpu"] < pod["cpu"]: return "insufficient cpu"
    if node["mem"] - node["req_mem"] < pod["mem"]: return "insufficient memory"
    if node["taints"] - pod["tolerations"]: return f"untolerated taint {node['taints'] - pod['tolerations']}"
    return None

def score(node, pod, policy):
    cpu_used = (node["req_cpu"] + pod["cpu"]) / node["cpu"]
    mem_used = (node["req_mem"] + pod["mem"]) / node["mem"]
    if policy == "least":  return 100 * ((1 - cpu_used) + (1 - mem_used)) / 2
    if policy == "most":   return 100 * (cpu_used + mem_used) / 2
    raise ValueError(policy)

def schedule(pod, policy, verbose=False):
    best = None
    for name, node in NODES.items():
        why = feasible(node, pod)
        if why:
            if verbose: print(f"  {name}: filtered ({why})")
            continue
        s = score(node, pod, policy)
        if verbose: print(f"  {name}: score {s:.1f}")
        if best is None or s > best[1]: best = (name, s)
    return best[0] if best else None

POD = {"cpu": 2, "mem": 4, "tolerations": set()}
for policy in ("least", "most"):
    print(f"policy={policy}"); print("  -> bind to", schedule(POD, policy, verbose=True))

# --- reconcile loop ------------------------------------------------------------------------
desired, pods, ids = 3, {}, itertools.count(1)          # pods: id -> node

def bind(pod_id, node):
    pods[pod_id] = node; NODES[node]["req_cpu"] += POD["cpu"]; NODES[node]["req_mem"] += POD["mem"]

def unbind(pod_id):
    node = pods.pop(pod_id); NODES[node]["req_cpu"] -= POD["cpu"]; NODES[node]["req_mem"] -= POD["mem"]

def reconcile():                                        # level-triggered: look at state, not events
    for pid, node in list(pods.items()):                # evict pods on nodes marked down
        if not NODES[node]["up"]: unbind(pid); print(f"    evicted pod-{pid} from dead {node}")
    while len(pods) < desired:
        node = schedule(POD, "least")
        if node is None: print("    pending: no feasible node"); break
        pid = next(ids); bind(pid, node); print(f"    created pod-{pid} on {node}")
    while len(pods) > desired:
        unbind(max(pods)); print("    scaled down")

random.seed(4)
for tick in range(6):
    print(f"tick {tick}: running {sorted(pods.items())}")
    if tick == 2: victim = random.choice(list(pods)); unbind(victim); print(f"  chaos: killed pod-{victim}")
    if tick == 4: dead = pods[min(pods)]; NODES[dead]["up"] = False; print(f"  chaos: node {dead} lost")
    reconcile()
  1. Run it. The first block should filter N1 (insufficient CPU) and N4 (untolerated taint) and print 65.6 for N2 and 31.2 for N3 under least, choosing N2; under most it prints 34.4 and 68.8 and chooses N3 — the lesson's worked numbers.
  2. Watch the reconcile ticks: three pods are created at tick 0; at tick 2 one is killed and the next reconcile recreates it; at tick 4 a node is marked down and its pods are evicted and replaced elsewhere. No step was told "replace pod X"; each tick just compared 3 with what existed.
  3. Add "gpu" to POD["tolerations"] and rerun: N4 now passes the filter and wins under least because it is the emptiest — which is exactly why GPU nodes carry taints.
  4. Change reconcile's scheduling policy to "most" and see the replicas pile onto one node — then ask what a single node failure would do to that service, and why real systems add spreading constraints.
Work it out

You are designing the control plane for a 3,000-node cluster with 90,000 pods. Kubelets renew a lease every 10 seconds; each pod lifecycle generates about 8 writes; 2% of pods turn over per minute normally and 15% per minute during a fleet-wide deploy. etcd on your hardware sustains about 4,000 small writes per second at acceptable latency. (a) Is the steady state safe? (b) Is the deploy safe? (c) What would you change?

Answer

(a) Heartbeats: 3,000 ÷ 10 = 300 writes/s. Pod churn: 2% × 90,000 = 1,800 pods per minute = 30 per second × 8 = 240 writes/s. Total about 540 writes per second — 14% of capacity. Safe.

(b) Deploy: 15% × 90,000 = 13,500 pods per minute = 225 per second × 8 = 1,800 writes/s, plus 300 for heartbeats = 2,100 writes per second — over half of capacity, before events, endpoint updates (each new pod changes its Service's endpoints, which fan out) and controller retries. Endpoint updates for a large Service can multiply this; it is the kind of burst that pushes etcd latency up, which slows every controller, which causes retries — a feedback loop.

(c) Pace the rollout: Deployments roll in waves bounded by maxSurge and maxUnavailable, so limit how many services deploy concurrently (for example a fleet-wide deploy over 30 minutes instead of 6). Use sliced endpoint objects so a pod change rewrites one small slice, not a list of thousands. Rate-limit events or store them outside the main etcd. Give the API server priority-and-fairness limits so heartbeats and system controllers are never starved by deploy traffic. And measure: etcd fsync latency and the API server's request latency are the leading indicators.

Diagnose it

During a 4-minute network partition between the control plane and one of three zones, the zone's 900 nodes stop renewing leases. After the partition heals, you find hundreds of services briefly ran twice as many replicas, and a stateful queue consumer processed some messages twice. What happened, and what do you change?

Answer

After the 50-second grace period, the node controller marked the zone's nodes unreachable and tainted them. A third of the cluster being unhealthy is below the 55% zone threshold for the whole cluster but the entire zone was unhealthy, so the zone-level rate limits applied — yet pods whose tolerations were short (someone had set tolerationSeconds: 30 for fast failover) were evicted within the 4 minutes, and their controllers created replacements in the other zones, while the originals were still running in the partitioned zone, serving whoever could reach them. When the partition healed, the kubelets learned their pods had been deleted and stopped them — but in the meantime, two copies of the queue consumer ran. Changes: keep short tolerations only for stateless services; give singletons default or longer tolerations, and protect them with real fencing (a lease or lock with fencing tokens, in8) so a second copy cannot act even if it runs; check that zone-unhealthy thresholds suit a three-zone layout; and alert on mass taints so humans see a partition as a partition.
