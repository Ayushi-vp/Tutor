A startup's orders table has an auto-increment primary key, and for three years that is fine. Then the database is sharded into eight shards to keep up with growth, and on the first day two different orders are both number 1,048,577 — one on shard 2, one on shard 5. The payment provider, which uses the order number as its reference, rejects the second charge as a duplicate. The quick fix is a central "next order number" table that every shard calls; within a month it is the slowest query in the system, and when its database fails over, nobody can place an order for four minutes. The next fix is UUIDs — 128 random bits, no coordination — and the orders table's insert latency climbs steadily as the table grows, because every new row lands on a random page of a 200 GB index that no longer fits in memory.

Every system that splits data across machines meets this problem, usually by surprise. An identifier seems trivial, but it has to satisfy several requirements that pull against each other. It must be unique across every machine that creates records, without asking each other. It is often expected to be ordered by creation time, so "newest first" is a cheap index scan and pagination by ID works. It should be small, because it is copied into every index and every foreign key. It must be generated at whatever rate the system writes, with no single point of failure. And it has consequences for the storage engine that are easy to miss: the order in which IDs arrive decides whether inserts are cheap appends or random writes, and whether a distributed database spreads them or piles them onto one server.

This lesson designs an ID generator as an interviewer expects: requirements and the arithmetic that sizes each format; the API; the catalogue of approaches — auto-increment, ticket servers and range allocation, UUIDv4, UUIDv7 and ULID, Snowflake — with their trade-offs; then deep dives into Snowflake's bit layout worked by hand, assigning worker ids safely, clocks that skew or go backwards, and how IDs affect index locality. The real sources are Twitter's Snowflake repository, Flickr's ticket servers, RFC 9562 (the 2024 UUID standard that introduced UUIDv7) and Spanner's guidance on hotspots. The lab builds a Snowflake encoder and decoder, survives a backwards clock, and measures random versus time-ordered keys in a B-tree.

The mental model: number plates

Think about how a country issues vehicle number plates without one central office stamping every plate in sequence. One common scheme encodes a region, a period and a serial: each regional office issues plates with its own region code, the period changes on a schedule, and within a region and period the office just counts up. Two offices never clash because their region codes differ; one office never clashes with itself because its counter only goes up; and plates are roughly in order of registration because the period comes first. No office ever calls another.

A Snowflake ID is exactly this: timestamp (the period, to the millisecond), worker id (the region office), sequence (the serial within the millisecond). A UUIDv7 replaces the worker id and sequence with enough random bits that two generators are vanishingly unlikely to pick the same value. A UUIDv4 drops the timestamp entirely: pure randomness, unique by probability, in no order. A ticket server or range allocation is the central office again, but handing each regional office a whole book of plates at a time so it rarely has to call.

The analogy breaks in two places worth knowing. Plates are issued by people with calendars; ID generators rely on machine clocks, which drift and occasionally jump backwards — and a backwards clock can make an office reissue a plate. And plates are not stored in a tree that cares about their order, but IDs are: databases keep primary keys in B-trees, and the order in which new IDs arrive decides whether inserts touch one page or every page.

The one question that picks the design

Ask: where does uniqueness come from? There are only three answers. From a single counter (auto-increment, ticket server, allocated ranges): guaranteed and dense, but every generator depends on it, at least occasionally. From partitioning the space (Snowflake's worker bits, odd and even ticket servers): guaranteed without runtime coordination, but the partitions must be assigned correctly, once. From randomness (UUIDv4, the random part of UUIDv7 and ULID): needs no assignment at all, but needs enough bits that collisions are negligible — which is why random IDs are 128 bits, not 64. Every scheme in this lesson is one of these, or a combination.

The second question is what reads the ID? If only the database reads it, size and index behaviour dominate. If people read it (support tickets, URLs), length and readability matter, and so does what it reveals. If other systems sort or paginate by it, its ordering guarantees become part of an API contract that is very hard to change later. IDs outlive almost every other design decision — they end up in logs, partner systems, customers' spreadsheets — so the format is worth five deliberate minutes in an interview and in real life.

1 · Requirements

Functional. Return a new ID on request (singly or in batches); IDs are never repeated, ever. Optionally: decode an ID into its parts (time, origin) for debugging.

Non-functional — and these are the real design inputs. Uniqueness: absolute, across all generators, across restarts and failovers. Ordering: none, roughly time-ordered (k-sorted within some bound), or strictly increasing? Size: must it fit a 64-bit integer column (many databases, languages and APIs prefer it), or is 128 bits acceptable? Is it shown to humans (short, readable)? Throughput: IDs per second at peak, per process and in total. Latency and availability: may generation involve a network call, and may it ever block? Unguessability: is it a problem if someone can predict the next ID? Information leakage: is it acceptable to reveal creation time or volume?

Clarifying questions. What are the IDs for — database primary keys, events in a log, public references in URLs? What database stores them, and is it single-node or range-partitioned? Do clients ever sort or paginate by ID? Must IDs be generated offline (mobile clients creating records before syncing)? How many generators, and do they autoscale? The answers decide between a counter, Snowflake and a UUID.

2 · Back-of-envelope estimates

Assume 2 million IDs per second at peak across 3 regions, running for decades, with up to 1,000 generating processes.

Snowflake capacity. 12 sequence bits give 212 = 4,096 IDs per millisecond per worker, i.e. 4.1 million per second per worker — one worker could serve the whole peak. 10 worker bits give 210 = 1,024 workers. 41 timestamp bits give 241 ms = 2,199,023,255,552 ms ÷ (1,000 × 86,400 × 365.25) ≈ 69.7 years; from Twitter's epoch in November 2010, the range runs out in July 2080. A custom epoch exists to spend those years on the future rather than on 1970-2010.

UUIDv4 collision risk. 122 random bits. By the birthday bound, the probability of any collision among n IDs is about n² / 2123. For a trillion IDs (1012): 1024 ÷ 1.06 × 1037 ≈ 9 × 10−14. Collisions become likely only around 261 ≈ 2.3 × 1018 IDs. With good randomness, uniqueness is not the concern; size and ordering are.

Why random IDs need 128 bits. The same maths on 64 random bits: a billion IDs (109) gives 1018 ÷ 265 ≈ 1018 ÷ 3.7 × 1019 ≈ 2.7% collision probability. That is unacceptable, and it is why 64-bit IDs need structure (worker and sequence bits) rather than randomness.

Index size. A table of 10 billion rows: an 8-byte key is 80 GB of raw key data per index; a 16-byte UUID is 160 GB. In InnoDB every secondary index stores the primary key, so a table with 4 secondary indexes carries the key 5 times: 400 GB versus 800 GB of key bytes. Text UUIDs (36 characters) would be 1.8 TB. The ID's size multiplies through the schema.

Central allocator load. If every ID came from one database counter, 2 million transactions per second would be needed — impossible for one primary. With range allocation in blocks of 10,000, the counter sees 2,000,000 ÷ 10,000 = 200 allocations per second, trivial. Block size trades allocator load against how many IDs a crash wastes.

3 · The API and where the generator lives

As a library (preferred: no network hop, no dependency on the write path):
  gen = IdGenerator(region=1, worker=lease.worker_id)
  id  = gen.next_id()                 → 2108890285471109125
  ids = gen.next_ids(500)             → batch
  IdGenerator.decode(id)              → {time: 2026-10-10T12:00:00Z, region: 3, worker: 17, seq: 5}

As a service (when clients cannot be trusted with worker ids, or for non-JVM/Go/Python clients):
  POST /v1/ids?count=100              → {ids: [...]}   (batch to amortise the round trip)

A library embedded in each application process is the usual answer for Snowflake and UUIDs: generating an ID is a few hundred nanoseconds of local work, and no outage elsewhere can stop inserts. A service is justified when generators need assignment that you do not want every application to handle (worker ids, ranges), or when many languages must produce identical formats; it should hand out batches so the network round trip is amortised, and it must itself be highly available — which usually means several instances, each with its own worker id or range, behind a load balancer.

4 · The options, from most central to least

Single auto-increment. One database's counter. Unique, dense, strictly ordered, 64-bit. A bottleneck and single point of failure for every insert in a sharded system, and it reveals volume.

Partitioned auto-increment. Give each of N databases a different starting offset and a step of N (MySQL's auto_increment_offset and auto_increment_increment): with N = 2, one produces odd numbers and the other even. Unique without coordination, but adding a database later means changing the step everywhere, and ordering across databases is only approximate.

Ticket server. A database whose only job is issuing numbers. Flickr's 2010 post describes it: a MySQL table Tickets64 with an auto-increment 64-bit id and a unique stub column; to get an id, run REPLACE INTO Tickets64 (stub) VALUES ('a') then SELECT LAST_INSERT_ID(). REPLACE deletes and re-inserts the single row, so the table stays one row while the counter advances. Two ticket servers with step 2 and offsets 1 and 2 give odd and even ids, so either can fail. The post rejects GUIDs (globally unique identifiers, Microsoft's name for UUIDs) because they are big and index badly in MySQL, and notes the two servers drift — a few hundred thousand more odd-numbered objects than even — which harms nobody.

Range allocation. Each app server takes a block from a counter (one row, UPDATE counters SET next = next + 10000 WHERE name = 'orders' RETURNING next) and hands IDs out from memory. Central load falls by the block size; double-buffering (fetch the next block at 50% of the current) hides latency and short outages. IDs are increasing per server but interleaved across servers, and a crash leaves gaps. cd1 used this for short URLs.

UUIDv4. 122 random bits plus fixed version and variant bits. No coordination, generated anywhere (including offline clients), unguessable if the random source is cryptographic. 128 bits, and random order.

UUIDv7 and ULID. A 48-bit Unix millisecond timestamp first, randomness after: no coordination, sortable by creation time, still 128 bits. Detailed in deep dive A.

Snowflake. 64 bits, time-ordered, no runtime coordination — at the price of assigning worker ids and depending on clocks. Detailed in deep dives B and C.

5 · High-level design

For the 2-million-per-second, three-region system: a Snowflake-style library in every application process; a worker-id allocator backed by a coordination service (etcd or ZooKeeper, in8) in each region that leases ids to processes; time synchronisation configured to slew; a decode tool for operators; and, for public identifiers, a separate public id (random or encrypted) mapped to the internal one. Bit budget: 41 bits timestamp, 2 bits region (4 regions), 8 bits worker within region (256 processes per region), 12 bits sequence. Per region, 256 workers × 4.1 million per second is a billion IDs per second of headroom. The critical path for an ID is local: read the clock, compare with the last timestamp, increment the sequence, shift and OR — no network, no disk.

6 · Deep dive A: UUIDv4, UUIDv7 and ULID

UUIDv4. RFC 9562 (published in 2024, replacing RFC 4122) defines a version 4 UUID as 122 random bits with 4 bits of version (0100) and 2 bits of variant (10) in fixed positions. Written as 36 characters of hex and hyphens, e.g. 9f1c…-…-4…-a…-… — the 4 after the second hyphen is the version. Its strengths: anyone can generate one, anywhere, with no state, and a cryptographic random source makes it unguessable. Its weakness is order: consecutive UUIDv4s land anywhere in the key space.

UUIDv7. The RFC's layout: 48 bits unix_ts_ms (milliseconds since 1970), 4 version bits (0111), 12 bits rand_a, 2 variant bits, 62 bits rand_b. Because the timestamp is in the most significant bits, sorting UUIDv7s as bytes or as strings sorts them by creation millisecond. Within one millisecond, the random bits decide order — unless the generator makes them monotonic. The RFC describes three methods for that: a dedicated counter in rand_a (and possibly part of rand_b) incremented for each UUID within the same millisecond; monotonic random, treating the random bits as a counter seeded randomly and incremented by a random amount; and increased clock precision, using up to 12 bits of sub-millisecond time in rand_a. Python's uuid.uuid7(), added in 3.14, documents a 48-bit timestamp with a 42-bit counter for monotonicity within a millisecond. The RFC also notes the reason v7 exists: non-time-ordered UUIDs have poor database index locality, and time-ordered ones can make an order-of-magnitude difference in real-world performance.

ULID. A community specification predating UUIDv7 with the same idea: 48-bit millisecond timestamp, 80 random bits, written as 26 characters of Crockford base32 (which omits I, L, O and U to avoid misreading) so it is shorter than a UUID's 36 characters and sorts correctly as a string. Within the same millisecond, a monotonic ULID generator increments the random part by one; if that overflows, generation fails. UUIDv7 is now the standard choice for new systems, mainly because databases and libraries understand UUIDs natively; ULID's advantage is its compact, readable text form.

What time-ordered UUIDs cost. They reveal creation time to the millisecond to anyone who sees them. They are still 128 bits. And because they are time-ordered, they bring back the hotspot problem in range-partitioned databases (deep dive D). The usual guidance: UUIDv7 for internal primary keys in single-node or hash-partitioned databases; UUIDv4 for keys in range-partitioned databases and for anything public where timing should not leak.

7 · Deep dive B: Snowflake, worked by hand

The layout. Twitter built Snowflake in 2010 when moving from MySQL to Cassandra, which has no sequence facility. Its README lists the requirements: at least 10,000 IDs per second per process, uncoordinated generation for availability, roughly time-ordered — "k-sorted", promising within 1 second and aiming for tens of milliseconds — directly sortable, and under 64 bits. The solution: 41 bits of millisecond time with a custom epoch (69 years), 10 bits of configured machine id (1,024 machines), 12 bits of sequence (4,096 per millisecond per machine, with protection against rolling over within one millisecond). The code splits the machine id into 5 datacenter bits and 5 worker bits and uses the epoch 1288834974657 (4 November 2010). The top bit stays 0 so the value is a positive signed 64-bit integer, which matters in languages without unsigned types.

Encode by hand. Generate an ID at 2026-10-10 12:00:00.000 UTC on datacenter 3, worker 17, as the sixth ID in that millisecond (sequence 5).

  1. Unix time in milliseconds: 1,791,633,600,000.
  2. Subtract the epoch: 1,791,633,600,000 − 1,288,834,974,657 = 502,798,625,343 ms (a 39-bit number, comfortably within 41).
  3. Shift left 22 bits (the 5 + 5 + 12 bits below it): 502,798,625,343 × 4,194,304 = 2,108,890,285,470,646,272.
  4. Datacenter 3 shifted left 17: 393,216. Worker 17 shifted left 12: 69,632. Sequence: 5.
  5. OR them together (here, a sum, since the fields do not overlap): 2,108,890,285,470,646,272 + 393,216 + 69,632 + 5 = 2,108,890,285,471,109,125, hex 0x1D44488A8FC71005.

Decode by hand. Shift right 22: 502,798,625,343, add the epoch: 1,791,633,600,000 ms = 2026-10-10 12:00:00 UTC. (id >> 17) & 31 = 3, (id >> 12) & 31 = 17, id & 4095 = 5. Decoding is why Snowflake IDs are so useful operationally: any ID in a log tells you when and where it was created.

The generation loop. Per worker: read the clock in milliseconds. If it equals the last timestamp used, increment the sequence; if the sequence wraps to 0 (4,096 IDs already issued this millisecond), spin until the clock moves to the next millisecond. If the clock is ahead of the last timestamp, reset the sequence to 0. If the clock is behind the last timestamp, the clock has gone backwards — deep dive C. Then record the timestamp and assemble the ID. All of it is under a lock (or per-thread generators with different worker ids), and takes a few hundred nanoseconds.

Changing the bit budget. The 41/10/12 split is a choice. A system with many short-lived generators (serverless functions, autoscaling pods) wants more worker bits and needs fewer sequence bits: 41/14/8 gives 16,384 workers at 256 IDs per millisecond each. A system needing a longer lifetime can use seconds instead of milliseconds for the timestamp (which Sonyflake, a Go variant, does with 10 ms units). Whatever the split, document it, because every decoder depends on it.

8 · Deep dive C: worker ids and clocks

Assigning worker ids. Snowflake's uniqueness rests entirely on one invariant: no two live generators share a worker id. Three ways to maintain it. Static configuration: each host's id in its config file — fine for a few dozen long-lived hosts, dangerous when an image or config is cloned. A coordination service lease (in8): at start-up, the process claims a free id by creating an ephemeral node such as /id-workers/17 in ZooKeeper or a key with a lease in etcd; the node disappears when the process's session expires, returning the id to the pool. Stable platform identity: a Kubernetes StatefulSet gives pods ordinals 0, 1, 2… that are stable and unique within the set, which can map directly to worker ids. With leases, the dangerous case is a process that pauses (a long garbage-collection pause, a VM migration) longer than its lease: the coordination service hands id 17 to a new process, then the old one wakes up and keeps generating. Two generators now share an id and will produce duplicates whenever they hit the same millisecond and sequence. The defence is fencing: the generator checks its lease is still valid before issuing (cheaply, by tracking the lease's expiry locally with a safety margin) and stops issuing once it cannot be sure.

Clock skew between workers. Two workers whose clocks differ by 5 ms produce IDs whose order across workers is wrong by up to 5 ms. This is acceptable — it is what "k-sorted" means — as long as nothing relies on a total order. Keep skew small with time synchronisation (NTP to milliseconds; PTP to microseconds where needed) and monitor each host's offset.

The clock going backwards. A worker's own clock can move backwards: NTP corrects a fast clock by stepping it back, an operator sets the time, a VM resumes from a snapshot, a leap second is handled by repeating a second. If a worker generated IDs at millisecond 1,002, then the clock steps back to 998, it would generate IDs for 998-1,002 again with the sequence starting from 0 — and duplicate IDs it already issued. Twitter's implementation refuses: it logs "clock is moving backwards" and throws an error, rejecting requests until the clock passes the last timestamp. Practical variants, from gentlest to strictest:

  • Small step (a few ms): keep using the last timestamp. Treat now = last, keep incrementing the sequence; when it is exhausted, wait. IDs stay unique and monotonic; their embedded time runs a few milliseconds ahead of the wall clock until it catches up. This is a logical clock (sc9) built from the physical one.
  • Larger step: refuse, or switch identity. Stop issuing (callers retry on another instance), or claim a spare worker id from the allocator and continue — a different worker id cannot collide with the old one's IDs.
  • Prevent it. Configure the time daemon to slew (adjust the clock's rate gradually) rather than step, and handle leap seconds by smearing them over hours, as large cloud providers' time services do.

Restarts. The last timestamp lives in memory. If a worker crashes and restarts within the same millisecond range — or after a clock step backwards — it could reissue. Defences: on start, wait until the clock is past the start time plus a small margin; persist a high-water mark every second and refuse to issue below it; or take a fresh worker id on every start, which leases make easy.

9 · Deep dive D: how the ID shapes the index

B-trees on one node. A primary key index is a B+ tree (db5): keys sorted across fixed-size pages (16 KB in InnoDB, 8 KB in PostgreSQL). Where a new key goes depends only on its value. Increasing keys (auto-increment, Snowflake, UUIDv7) always go to the rightmost leaf page; that page and its few ancestors stay in memory, and when it fills, the engine starts a new page rather than splitting a full one in half (InnoDB detects sequential inserts and fills pages nearly full). Random keys (UUIDv4) go to a random leaf: every insert touches a different page, so the set of pages that must be in memory is the whole index. Once the index is larger than the buffer pool, a large fraction of inserts read a page from disk first, and full pages split 50/50, leaving the index fragmented and roughly a third larger than necessary. In InnoDB, where the table itself is the clustered primary-key index (db10), random keys scatter the table's rows too, and every secondary index carries the 16-byte key. This is the effect RFC 9562 cites when it says time-ordered UUIDs can improve real-world performance by an order of magnitude or more, and the reason Flickr rejected GUIDs. The lab shows the direction on SQLite: inserting 200,000 random UUIDs took about three times as long as 200,000 time-ordered ones on the same machine.

Range-partitioned distributed databases: the opposite. Spanner, CockroachDB, HBase, Bigtable and similar systems split the key space into contiguous ranges, each served by one node. With increasing keys, every new row has the largest key so far and falls into the last range: one node takes all inserts — a hotspot — until it splits, after which the new last range is hot. Spanner's documentation names monotonically increasing keys, such as timestamps, as a common cause of hotspots, and recommends UUIDv4 keys, bit-reversed sequences (Spanner offers a bit-reversed sequence that reverses a counter's bits so consecutive values land far apart), hashing the key into a shard prefix, or putting a non-monotonic column first. So the same Snowflake ID that is ideal for MySQL is a poor raw key for Spanner. The common resolution: keep the time-ordered ID as the logical identifier (for sorting, pagination and debugging), and store it under a physical key that spreads writes — the ID with its bits reversed, or prefixed with a hash of itself.

Hash-partitioned stores. Systems that place data by hash of the key (Cassandra, DynamoDB's partition key, Redis Cluster) spread writes regardless of the ID's order, so any ID works for spreading; time-ordered IDs still help within a partition if they are used as the sort key, since "newest first" becomes a range scan.

10 · Failure modes and trade-offs

Duplicate IDs are the failure that matters, and they come from a short list: two live generators with one worker id (cloned config, a lease reused after a pause without fencing); a clock stepping backwards with code that trusts it; a restart that reissues timestamps; sequence overflow that wraps instead of waiting; or, for random IDs, a broken random source (cloned VMs with identical entropy state, a non-cryptographic generator seeded with the time). A unique constraint in the database turns a duplicate into a failed insert instead of corrupted data — keep it as a backstop. Allocator outages affect only ticket servers and range allocation; double-buffered blocks ride through them. Running out is a calendar event: 41 bits of milliseconds end 69.7 years after the epoch, and a 10-bit worker space ends when the 1,025th concurrent generator starts.

Trade-offs to close on. 64 versus 128 bits (index size versus coordination-free randomness); ordered versus random (B-tree locality versus range-partition hotspots and information leakage); library versus service (no network hop versus central control); and coordination once (worker ids) versus coordination per block (ranges) versus none (UUIDs).

Public IDs versus internal IDs

An ID that appears in URLs, emails and API responses has different requirements from a primary key. Sequential and time-ordered IDs leak volume and timing (a competitor can sign up twice a day apart and subtract) and invite enumeration (try /orders/1001, /orders/1002…). Authorisation on every lookup is mandatory regardless, but many systems also separate the two: an internal 64-bit key for joins and indexes, and a public identifier that is random (a UUIDv4 or a random base62 string) stored in a unique column, or a reversible encryption of the internal key with a secret (a keyed permutation such as a small block cipher over 64 bits, the same idea cd1 used to scramble short codes). The second avoids a lookup table but makes the key a long-lived secret.

Generating IDs on clients and offline

Mobile apps and collaborative editors often create records before they can reach a server — a note written on a plane. Client-generated IDs must be unique without any assignment, which rules out Snowflake worker ids and ranges and leaves random IDs: UUIDv4, or UUIDv7 if creation order is useful. Since clients are untrusted, the server must treat a client-supplied ID as a proposal: enforce uniqueness with a constraint, scope it to the user (so one user cannot claim another's ID), and be ready to remap on conflict. Client-generated IDs also make retries idempotent for free: resending the same create with the same ID cannot create two records.

Monotonicity within a process versus across processes

Within one generator, monotonicity is easy: hold the last value and never go below it. Across processes, it is only as good as the clocks, and that limit is fundamental, not an implementation flaw. Applications sometimes quietly assume total order — "fetch everything with id > last_seen" as a change feed — and then miss rows: a row with a slightly smaller ID, from a worker with a slightly slow clock, commits after the reader advanced past it. Either read with a safety lag ("id > last_seen − 5 seconds' worth", de-duplicating), or use a real sequence from the database's log (a commit sequence number or change data capture), which is ordered by commit, not by creation.

Database sequences that scale

Databases offer middle grounds between a single counter and an external generator. PostgreSQL sequences can cache values per session (CACHE 100), which is range allocation inside the database: fewer contended updates, with gaps on restart. Distributed SQL databases provide unique-ID functions that combine a timestamp with a node identifier (Snowflake-like) so inserts need no coordination, and bit-reversed sequences that keep integer keys while avoiding range hotspots. Knowing these exist often removes the need for a separate ID service.

Sortable text encodings

If IDs are stored or compared as strings — in object storage keys, filenames, or text columns — the encoding must preserve order. Fixed-width hexadecimal and Crockford base32 (ULID's 26 characters) sort the same as the underlying number, provided every ID has the same width. Base64 does not sort correctly in plain byte order because its alphabet is not in ASCII order, and variable-width decimal sorts "10" before "9". Pick an order-preserving, fixed-width encoding, or keep the binary form for sorting.

Migrating from one ID scheme to another

Changing ID formats in a live system is common (auto-increment to Snowflake when sharding, UUIDv4 to UUIDv7 for locality) and is mostly about keeping old and new IDs from colliding and keeping consumers working. Snowflake and UUID spaces are disjoint from small auto-increment values by construction (a Snowflake ID from 2026 is around 2 × 1018), so both can coexist in one 64-bit column during the transition. Changing a column from 64-bit to 128-bit, or from integer to UUID, is an expand-and-contract migration (db14): add the new column, backfill, dual-write, move readers, then drop the old. Consumers that parsed IDs as 32-bit integers or JavaScript numbers (which lose precision above 253, a real problem for Snowflake IDs in browsers — Twitter's API returns them as strings too for this reason) must be found before the switch, not after.

When you actually need a total order

Some systems need IDs in a strict global order: a ledger where entry n+1 must be after entry n, an event log consumed as a sequence. No coordination-free scheme provides that; it needs a single sequencer (one leader assigning numbers, made fault-tolerant by consensus — the exchange case cd15 is built on one) or a database's own commit order. Recognise that requirement in the interview and say so, rather than claiming Snowflake gives it.

The real cases: Snowflake and Flickr's ticket servers

Twitter's Snowflake (2010) is the reference design, and its repository records the reasoning as well as the code. The motivation: moving from MySQL to Cassandra, which has no sequential ID facility. The requirements: at least 10,000 IDs per second per process with a 2 ms response, generation without coordination between machines, IDs that are roughly time-ordered (k-sorted, promising within 1 s and aiming for tens of milliseconds) and directly sortable, and under 64 bits because many otherwise reasonable solutions needed 128. The layout: 41 bits of milliseconds with a custom epoch giving 69 years, 10 bits of configured machine id for up to 1,024 machines, 12 bits of sequence rolling over every 4,096 per machine with protection against rollover in the same millisecond. On clocks, the README is explicit: use NTP, and if the clock runs backwards Snowflake refuses to generate IDs until a time after the last one it used — better still, run NTP in a mode that does not move the clock backwards. The Scala IdWorker shows the epoch (1288834974657) and the 5/5 split of the machine bits. The service was a Thrift server; Twitter archived the project, and Snowflake-style generators are now usually embedded libraries.

Flickr's ticket servers (2010, in production since 2006) are the opposite philosophy: keep a counter, make it cheap and redundant. Two MySQL servers each hold a one-row table and hand out 64-bit ids via REPLACE INTO and LAST_INSERT_ID(), one on odd numbers and one on even. Flickr chose this because uploads ran at over 60 photos a second — too many for a single central table with sharded data — and because GUIDs were big and indexed badly in MySQL, where Flickr kept indexes in memory. The post's honest footnote is a good interview line: the two servers drift, so there are a few hundred thousand more odd ids than even, and it hurts no one. Uniqueness mattered; perfect balance and strict order did not.

Failure modes you will see

Duplicate key errors in bursts. Symptom: occasional unique-constraint violations on insert, clustered in time. Cause: decode the duplicates — same worker id and timestamp means two generators shared an id or a clock stepped back. Detection: alert on any duplicate-key error on ID columns; log worker id leases with timestamps. Fix: fencing on lease loss, slewing time sync, refuse on large backward steps.

Insert latency growing with table size. Symptom: p99 insert latency on a large table rises month by month. Cause: random primary keys and an index that has outgrown memory. Detection: buffer-pool hit rate and page splits per second. Fix: time-ordered keys for new tables; for existing ones, migrate or add a time-ordered surrogate key.

One hot node in a distributed database. Symptom: one range server at 100% CPU while others idle, all on inserts. Cause: monotonically increasing keys in a range-partitioned store. Fix: bit-reversed or hash-prefixed physical keys.

Worker id exhaustion. Symptom: new pods fail to start during a scale-out. Cause: more concurrent generators than worker ids, or leases not released by crashed processes. Fix: shorter leases, more worker bits, or fewer generator processes (one per host rather than per thread).

What to monitor

Clock offset per host against the time source, and any backward step events; IDs refused due to clock moves; worker id leases held, free and expiring; sequence exhaustion waits per second (a sign one worker is overloaded); duplicate-key errors on ID columns; for range allocation, allocator latency and remaining IDs in each server's current block; and for storage, page splits and buffer-pool misses on primary key indexes.

Goal: build a Snowflake encoder and decoder, reproduce the worked example, show uniqueness under threads and safe handling of a backwards clock, build a UUIDv7 by hand, and measure random versus time-ordered keys in a B-tree. Python 3.12 standard library, about 15 seconds.

"""Snowflake IDs: encode, decode, survive a backwards clock; then UUIDv7 by hand and index locality."""
import os, sqlite3, tempfile, threading, time, uuid

EPOCH = 1288834974657                     # Twitter's custom epoch (ms), 2010-11-04

class Snowflake:
    def __init__(self, dc, worker, clock=lambda: time.time_ns() // 1_000_000):
        assert 0 <= dc < 32 and 0 <= worker < 32
        self.dc, self.worker, self.clock = dc, worker, clock
        self.last, self.seq, self.lock = -1, 0, threading.Lock()

    def next_id(self):
        with self.lock:
            now = self.clock()
            if now < self.last:                               # clock went backwards
                if self.last - now > 5:                       # big jump: refuse, like Snowflake
                    raise RuntimeError(f"clock moved back {self.last - now} ms")
                now = self.last                               # small jump: keep using last ms
            if now == self.last:
                self.seq = (self.seq + 1) & 0xFFF
                if self.seq == 0:                             # 4,096 used this ms: wait
                    while (now := self.clock()) <= self.last: pass
            else:
                self.seq = 0
            self.last = now
            return ((now - EPOCH) << 22) | (self.dc << 17) | (self.worker << 12) | self.seq

def decode(i):
    return {"ms": (i >> 22) + EPOCH, "dc": (i >> 17) & 31, "worker": (i >> 12) & 31, "seq": i & 4095}

def uuid7():                                                  # 3.12 lacks uuid.uuid7 (3.14 has it)
    ms = time.time_ns() // 1_000_000
    b = bytearray(ms.to_bytes(6, "big") + os.urandom(10))
    b[6] = 0x70 | (b[6] & 0x0F)                              # version 7
    b[8] = 0x80 | (b[8] & 0x3F)                              # variant 10
    return uuid.UUID(bytes=bytes(b))

Budget the bits

A serverless platform runs up to 20,000 concurrent function instances, each needing to generate IDs, at most 50 per millisecond per instance. IDs must fit a signed 64-bit integer and last at least 30 years from a 2026 epoch. Instances live minutes. Design the bit layout and the worker id assignment.

Answer

Worker bits: 20,000 instances need 15 bits (32,768). Sequence: 50 per ms needs 6 bits (64). Timestamp: 30 years in ms is 30 × 365.25 × 86,400,000 ≈ 9.5 × 1011 ≈ 240, so 40 bits gives about 34.8 years. Total 40 + 15 + 6 = 61, plus the sign bit = 62, leaving 2 spare bits — add them to the timestamp (42 bits, about 139 years) or to the sequence. Worker ids: instances live minutes, so static assignment is impossible; lease from a coordination service with a lease shorter than the instance lifetime and renewed while running, fence on renewal failure, and, because a pause can outlive a lease, have each instance check its lease's local expiry before every batch. Alternatively, avoid worker ids entirely with UUIDv7 if 128 bits is acceptable.

Diagnose it

A payments table in MySQL with a UUIDv4 primary key has grown to 1.5 billion rows. Insert p99 latency rose from 4 ms to 60 ms over six months, the buffer pool hit rate fell from 99.9% to 97%, and the table is 40% larger than the raw data. What is happening and what do you do?

Answer

Random keys put each insert on a random leaf page of the clustered index. While the index fit in the buffer pool, that cost little; now it does not, so many inserts must read a page from disk first (the hit rate drop), and full pages split in half, leaving the tree fragmented (the 40% bloat). Every secondary index carries the 16-byte key, amplifying both. Fixes: for new rows, switch to a time-ordered key (UUIDv7, same type and size, so the column need not change) — inserts move to the right edge and the hot set shrinks to recent pages; rebuild the table during a maintenance window to remove fragmentation; or add an auto-increment or Snowflake surrogate as the clustered key and keep the UUID as a unique secondary column for external references. Verify by watching page splits per second and the buffer pool hit rate after the change.
