Imagine you run the shopping cart for a large online store in 2004. It is the week before Christmas. Tens of millions of people are adding items, and every one of those clicks must be saved, because a customer who adds a gift and later finds it gone may not come back. Your cart lives in a big relational database on a powerful primary server with a replica. On the busiest evening a disk controller on the primary fails. Failover takes several minutes, and during those minutes every "Add to cart" returns an error. Amazon's engineers described exactly this priority in the Dynamo paper: customers must be able to add items "even if disks are failing, network routes are flapping, or data centers are being destroyed by tornados".

Two things are wrong with the single-primary design. First, it cannot grow past one machine's write capacity and disk. Second, and worse, every write depends on one specific machine being up and reachable, so any failure of that machine is a failure of the feature. Making the primary bigger fixes neither.

The alternative is to spread keys over hundreds of ordinary machines, keep several copies of each key, and let any of the copies accept a write, so there is no single machine whose failure stops writes. That buys enormous scale and availability, but it raises hard questions. How does a client know which machines hold a key, when machines join and leave all the time? If two copies accepted different writes while the network was split, which one is right? How do copies that missed updates catch up? How do you delete something when one copy is offline?

This lesson designs that store in interview order — requirements, hand-worked estimates, API, data model and architecture — then goes deep on the four hard parts interviewers push on: consistent hashing with virtual nodes, quorums and why R + W > N works, vector clocks and conflict resolution, and anti-entropy with Merkle trees. It ends with the storage engine on each node, failure modes, what Amazon reported from running Dynamo, and how DynamoDB later chose a different path.

Two questions define the design

A key-value store has the smallest possible interface: put(key, value) and get(key). No joins, no queries across keys, no multi-key transactions. That restriction is not a weakness to apologise for; it is what makes the design scale, because every operation touches one key, and one key can be placed and copied independently of every other key. With more data than one machine can hold, two questions remain:

  1. Which machines hold this key? That is partitioning.
  2. What happens when those machines are down, slow or disagree? That is replication and consistency.

An analogy: a library with no head librarian

Picture a library whose books are spread over many branches, with three copies of every book in three different branches. There is no central catalogue desk. Instead, every branch has the same simple rule for working out which branches hold a given title — say, from the first letters of its title — so anyone can compute where to go. To update a book (add an erratum), you send the change to its three branches and consider it done once two confirm. To read it, you ask two branches and take the newer edition. Because any two of three branches overlap, you always reach at least one branch with the latest erratum.

When a branch closes for a week, a neighbouring branch keeps the errata on its behalf with a sticky note — "deliver to Elm Street when it reopens". At night, branches compare short summaries of their shelves and copy whatever the other one is missing. And if two people add different errata to the same book at the same time at different branches, the library keeps both and asks the next reader to merge them, rather than throwing one away.

Where the analogy breaks: real machines fail in the middle of an operation, messages arrive late or twice, and clocks on different machines disagree, so "the newer edition" is not always obvious. Most of the design is about exactly those edge cases.

The big picture in four moves

Move 1 — place keys with a hash ring. Hash every node's name to several points on a circle, and hash every key to a point too. A key belongs to the first node clockwise from it. Adding a node takes over only the arcs just before its points; nothing else moves.

Move 2 — copy each key to N nodes. The first N distinct nodes clockwise form the key's preference list. Any of them can coordinate a request; there is no leader.

Move 3 — wait for only some of them. A write succeeds after W acknowledgements, a read after R responses. If R + W > N, every read overlaps the latest completed write. Lower values buy speed and availability at the cost of staleness.

Move 4 — let copies disagree, then converge. Disagreement is inevitable when any copy can accept writes. The system records enough history (vector clocks) to know whether two versions conflict, keeps both if they do, and runs background repair so copies converge. The central mental model: every hard question here is "what do you do when replicas disagree?" The design does not prevent disagreement; it defines when you notice it, who resolves it, and what the caller is promised meanwhile.

1 · Requirements

Functional. get(key) and put(key, value), plus delete(key). Values are opaque bytes up to, say, 400 KB (DynamoDB's item limit is a useful anchor). Optional per-key time-to-live. The caller can choose consistency per request.

Non-functional. Always writable: a put should succeed as long as some replicas are reachable, even during a network partition. Single-digit-millisecond median latency and a strict tail target — Amazon's services stated their storage requirements at the 99.9th percentile because, as the Dynamo paper argues, averages hide the experience of the customers with the most history, often the most valuable ones. Horizontal scale to hundreds of terabytes by adding nodes, with no downtime when nodes join or leave. Survive the loss of a node, a rack or an availability zone (a separate data centre within a cloud region) without data loss.

Out of scope, said aloud: joins, secondary indexes, range scans across partitions and multi-key transactions. Point out that this restricted interface is what buys the scale.

The clarifying question that decides the design: "Can we ever refuse a write?" If not — the shopping-cart answer — you must let copies on both sides of a network split accept writes and deal with conflicts later. If some writes must never conflict (a username claim, a balance), they need a different, consensus-based path. Make the interviewer own that product decision, and note that it can differ per operation.

2 · Back-of-envelope estimates

Scenario: a session and feature store behind an AI product. 100 TB of logical data, average value 2 KB, 500,000 reads/s and 100,000 writes/s at peak, replication factor N = 3 across three availability zones, and R = W = 2.

Key count. 100 TB ÷ 2 KB = 100 × 1012 ÷ 2 × 103 = 5 × 1010, 50 billion keys.

Stored bytes. 100 TB × 3 = 300 TB on disk before overheads.

Node count. Each node has 4 TB of NVMe SSD. An LSM engine needs free space for compaction (merging files temporarily needs room for both input and output), so plan to fill only half: 2 TB of data per node. 300 ÷ 2 = 150 nodes, 50 per zone.

Per-node request load. Every write goes to all 3 replicas (W only decides how many the coordinator waits for): 100,000 × 3 = 300,000 replica writes/s ÷ 150 = 2,000 writes/s per node. Each read contacts R = 2 replicas (in practice, one full read plus one digest — a hash of the value): 500,000 × 2 = 1,000,000 ÷ 150 ≈ 6,700 reads/s per node. Both are comfortable for an SSD-backed LSM engine.

Bandwidth. Writes: 100,000 × 2 KB = 200 MB/s of client data, × 3 replicas = 600 MB/s across the cluster, 4 MB/s per node. Reads: 500,000 × 2 KB = 1 GB/s returned to clients. Small per node.

Memory for Bloom filters. Each node holds 50 billion × 3 ÷ 150 = 1 billion keys. A Bloom filter with about 10 bits per key gives roughly a 1% false-positive rate: 10 × 109 bits = 1.25 GB per node. That fits in memory, which matters because the filters are consulted on every read.

Recovery time, the number that justifies virtual nodes. When a node dies, its 2 TB must be re-copied to restore three replicas. With one ring position per node, its ranges are shared with only a couple of neighbours, so one or two nodes stream 2 TB; at a throttled 100 MB/s that is 2 × 1012 ÷ 108 = 20,000 s, about 5.6 hours of reduced redundancy. With virtual nodes the ranges are spread over all 149 survivors, each sending about 13 GB at the same 100 MB/s: about 134 seconds, if the network allows. Say this number; it is the most convincing argument for vnodes.

3 · API

get(key, consistency=QUORUM)          -> [(value, context)]   # may return several siblings
put(key, value, context, consistency=QUORUM) -> ok
delete(key, context)                  -> ok                   # writes a tombstone

Two details make this an honest API for a leaderless store. get can return a list of values: if the store holds concurrent versions it cannot order, it returns all of them. And every value comes with an opaque context — in Dynamo, the vector clock — which the client passes back on its next put. That tells the store which versions the client had seen when it wrote, so the store knows the new write supersedes them. A client that reads two siblings, merges them and writes back with the context has resolved the conflict.

4 · Data model

Logically each record is key → (value, vector clock, timestamp, optional TTL, tombstone flag). Physically, each node stores the key ranges it owns in a log-structured merge tree, described in the storage-engine dive. The ring itself — the list of tokens (ring positions) and which node owns each — is small metadata every node keeps in memory: with 150 nodes and 16 tokens each, 2,400 entries. Membership and token ownership spread by gossip, so every node can compute any key's preference list locally, and a client library can route requests directly to a replica without an extra hop.

5 · High-level architecture

There are no special nodes. Each node runs the same software with four parts: a request coordinator that handles client requests for any key, computes the preference list and fans out to replicas; a membership and failure detector fed by gossip; a storage engine; and background repair (hint delivery and Merkle-tree comparison). A client sends a request either to a load balancer, which picks any node, or — with a ring-aware client library — straight to a replica of the key, which saves a hop. The Dynamo paper measured this: client-driven coordination cut 99.9th-percentile read latency from 68.9 ms to 30.4 ms and average read latency from 3.9 ms to 1.55 ms.

A put for cart:42 with N = 3, W = 2 goes like this. The coordinator computes the preference list [B, C, A]. It generates the new version's vector clock, writes locally if it is a replica, and sends the write to the others. As soon as two replicas (itself included) have written to their commit logs, it replies success. The third replica's write completes in the background; if it fails, repair fixes it later. A get with R = 2 sends to the replicas, waits for two, and if their versions differ, returns the newest — or all concurrent ones — and asynchronously writes the newest back to the stale replica (read repair).

6 · Deep dive: consistent hashing and virtual nodes

Start with why hash(key) mod N fails. With 10 nodes, a key with hash 1,234,567 lives on node 1,234,567 mod 10 = 7. Add an 11th node and it lives on 1,234,567 mod 11 = 4. For nearly every key the remainder changes, so roughly 10/11 of all data — 90.9% — must move. The lab measured 90.7% on 100,000 keys. Moving 90 TB to add one node is not an operation; it is an outage.

Consistent hashing hashes both nodes and keys into the same large space, say 0 to 264 − 1, imagined as a circle. A key belongs to the first node clockwise from its point. When an 11th node joins, it lands at some points and takes over only the keys between each of its points and the previous node's point. Every other key stays where it was. The expected fraction that moves is 1/11 ≈ 9.1%; the lab measured 9.3%.

With one point per node, though, the arcs are uneven. Ten random points on a circle make some gaps two or three times the average. In the lab, ten nodes with one point each gave the busiest node 2.26 times the average load. Virtual nodes fix this: each physical node takes many points (tokens), so it owns many small arcs scattered around the circle, and the sums average out — 16 tokens gave 1.33, 256 tokens 1.11. Two more benefits follow. When a node fails, its many small arcs are inherited by many different successors, so the extra load spreads instead of doubling one neighbour's. And capacity can be weighted: a machine with twice the disk takes twice the tokens.

The preference list for a key is the first N distinct physical nodes clockwise, skipping extra tokens of a node already chosen. Production systems also skip nodes in the same rack or zone so the N copies land in different failure domains — Cassandra's NetworkTopologyStrategy, for example, walks the ring choosing replicas in distinct racks.

The Dynamo paper describes an evolution worth knowing. Its first strategy gave each node T random tokens, which made adding a node expensive: the new node had to scan and pull data from many nodes for its random ranges. The final strategy split the ring into Q equal fixed-size partitions and assigned Q/S of them to each of S nodes; data moves as whole partitions, which can be shipped as files, and the ring metadata shrinks. Cassandra followed a similar path in spirit, moving its default from 256 random tokens to 16 tokens chosen by an allocation algorithm aware of the replication factor (its current cassandra.yaml sets num_tokens: 16 and allocate_tokens_for_local_replication_factor: 3). The lesson: more tokens give better balance but cost metadata, repair work and streaming overhead, and a smart allocator gets good balance with few tokens.

7 · Deep dive: quorums and why R + W > N overlaps

With N = 3 replicas, a write that waited for W = 2 acknowledgements is on at least 2 of the 3. A read that waits for R = 2 responses hears from 2 of the 3. Two subsets of size 2 drawn from a set of 3 must share at least one member — there are only 3 to go around. That shared replica has the latest acknowledged write, and the coordinator returns the newest version it sees. In general, if R + W > N, any read set and any write set intersect. It is a counting argument, not a protocol.

N, W, RBehaviourTolerates
3, 2, 2Quorum: reads see the latest completed write1 replica down for reads and writes
3, 3, 1Fast reads; any replica down blocks writes0 down for writes
3, 1, 3Fast, always-available writes; reads need every replica0 down for reads
3, 1, 1Fastest and most available; stale reads common2 down, but data may be lost

Latency follows from the same choice. A quorum operation is as slow as the W-th or R-th fastest replica. With N = 3 and R = 2, one slow replica (a garbage-collection pause, a compaction burst) doesn't hurt; with R = 3 it does. That is why the Dynamo paper notes request latency is "limited by the slowest of the R or W replicas", and why (3,2,2) is the common choice: one replica can be slow or down without affecting either latency or availability.

What R + W > N does not give. It concerns completed writes. A write that reached one replica and then failed may still be read by some readers and not others. Two concurrent writes can reach different overlapping sets and both "succeed". A read concurrent with a write can see the new value and a later read the old one if they hit different replicas. So quorum reads are not linearizable. Get that sentence right in an interview; it is the most common senior-level probe on this design.

Sloppy quorums and hinted handoff. Dynamo deliberately weakened the rule further to stay writable. If B is down, the coordinator sends B's copy of cart:42 to the next healthy node clockwise, D, with a hint saying "this belongs to B". D's acknowledgement counts toward W. D keeps hinted writes in a separate local store and periodically tries to deliver them; once B is back and accepts them, D deletes its copy. The paper notes that with W = 1, "a write request is only rejected if all nodes in the system are unavailable". The price: a later read from the preferred nodes [B, C, A] may not include D, so the overlap guarantee is broken until the hint is delivered. Cassandra keeps hints for up to three hours by default (max_hint_window: 3h); a node down longer than that needs a full repair.

8 · Deep dive: versions, vector clocks and conflicts

Because several nodes can coordinate writes to the same key, two writes can happen without either knowing about the other — for example, during a network split, or simply two clients writing at the same moment through different coordinators. The store needs to tell two situations apart: B came after A (B was written by someone who had seen A, so B replaces A) and A and B are concurrent (neither saw the other, so throwing either away loses information).

Wall-clock timestamps cannot tell these apart. Clocks on different machines drift by milliseconds or more, so a write that happened later can carry an earlier timestamp. And even with perfect clocks, "later" is not "had seen": two writes 1 ms apart from two devices are still concurrent.

A vector clock is a list of (node, counter) pairs attached to each version. Trace the Dynamo paper's own example. A client writes a new cart; node Sx coordinates and the version gets clock [(Sx, 1)]. The client updates it again through Sx: [(Sx, 2)]. That version replicates. Now two clients, each having read [(Sx, 2)], update it at the same time — one through node Sy, giving [(Sx, 2), (Sy, 1)], and one through node Sz, giving [(Sx, 2), (Sz, 1)].

The comparison rule: version A descends from B if every counter in A is greater than or equal to the matching counter in B. [(Sx, 2), (Sy, 1)] descends from [(Sx, 2)], so the old version can be discarded. But compare the two new ones: the first has Sy = 1 where the second has 0, and the second has Sz = 1 where the first has 0. Neither descends from the other: they are concurrent, and the store keeps both as siblings. The lab's compare function prints exactly "CONCURRENT" for this pair.

The next client to read gets both siblings plus a context that summarises both clocks. For a shopping cart, the application merges by taking the union of items — the paper's design choice that "add to cart" must never be lost — and writes back with the merged context, producing [(Sx, 3), (Sy, 1), (Sz, 1)] if Sx coordinates. That version descends from both siblings, and the conflict is gone. The known cost of union merging is that a deleted item can reappear if the delete happened on one sibling and the other sibling still has it.

Vector clocks can grow if many different nodes coordinate writes to one key. Dynamo truncated them: when a clock reaches a threshold of about 10 pairs, the oldest pair (by a stored timestamp) is dropped. That can occasionally make a descendant look concurrent, creating an unnecessary sibling — a safe failure, since nothing is lost — and the paper reports the problem "has not surfaced in production".

The alternatives, compared:

  • Last-write-wins (LWW): keep the version with the highest timestamp. Cheap, needs no client merging, and is Cassandra's model at the column level. It is correct for values that are overwritten wholesale and idempotent, such as a cached profile. For anything accumulated concurrently it silently drops writes.
  • Siblings plus application merge: Dynamo and Riak's model. Correct, but every client must handle a list of values.
  • CRDTs (conflict-free replicated data types): counters, sets and maps whose merge is mathematically guaranteed to converge regardless of order, so the store can merge siblings itself. A grow-only counter keeps one count per node and sums them; an observed-remove set tags each add with a unique ID so a remove only cancels adds it has seen.

The Dynamo paper shows conflicts are rare in practice: profiling the shopping-cart service for 24 hours, 99.94% of requests saw exactly one version, 0.00057% saw two, 0.00047% three and 0.00009% four. The authors add that divergent versions came mainly from concurrent writers — "usually triggered by busy robots (automated client programs)" — rather than from failures.

9 · Deep dive: anti-entropy and Merkle trees

Replicas drift: a write reached only W of N, a node missed writes while down longer than the hint window, a disk lost a file. Three mechanisms converge them, from fastest to most thorough. Hinted handoff replays writes held for a returning node. Read repair fixes keys that happen to be read: when the coordinator sees replicas disagree, it writes the newest version to the stale ones. Hot keys converge quickly; keys nobody reads never do. So the backstop is full anti-entropy: replicas periodically compare everything they share.

Comparing 2 TB key by key would mean shipping 2 TB. A Merkle tree avoids that. Each replica builds, for each key range it owns, a tree of hashes: leaves hash small sub-ranges of keys and values, each parent hashes its children, and the root summarises the whole range. Two replicas exchange roots. If the roots match, the whole range is identical — one hash compared. If not, they compare the two children, descend only into branches whose hashes differ, and end at the few leaves that differ, then exchange only those keys. With a tree of depth 15 over a range (about 32,000 leaves), finding one differing leaf takes about 15 levels of comparisons — two hashes per level — rather than streaming every key. Dynamo keeps a Merkle tree per key range a node hosts; Cassandra builds them during its repair operation.

The catch is that adding or removing a node changes ranges and forces trees to be rebuilt, which is another reason Dynamo moved to fixed-size partitions: a partition's tree stays valid as it moves between nodes.

10 · Deep dive: membership, gossip and failure detection

Every node needs the same view of the ring, but there is no central registry by design. Gossip does the job: every second, each node picks a random peer and they exchange their membership tables (node, tokens, status, a heartbeat counter), each keeping the newer entry for every node. Information spreads like a rumour, reaching all n nodes in about log2(n) rounds — around 8 rounds for 150 nodes — with constant work per node per round. Dynamo used gossip for membership and token ownership, plus a few seed nodes every node knows, so a new node can find the cluster and partitions don't persist for logical reasons.

Deciding that a node is down is local and probabilistic. Cassandra uses a phi accrual failure detector: instead of "no heartbeat for 5 s means dead", each node tracks the usual gap between heartbeats from each peer and computes a suspicion level phi from how unusual the current silence is. A threshold on phi adapts to slow networks without causing false alarms on fast ones. Being marked down only affects routing (stop sending it requests, start writing hints); it does not remove the node from the ring. Permanent removal is an explicit operator action, because confusing a long pause with a permanent loss would trigger a huge, unnecessary data movement.

11 · Deep dive: the storage engine on each node

Each node is a single-machine key-value store optimised for writes, using a log-structured merge tree (LSM tree) — the engine Cassandra borrowed from Google's Bigtable. A write is appended to the commit log (sequential, for crash recovery) and inserted into the memtable, a sorted in-memory structure. When the memtable reaches a size limit, it is written out in key order as an immutable SSTable file, and the commit log segment can be discarded. Writes therefore never update a file in place, which is why write throughput is high.

A read must check the memtable and then potentially every SSTable that might hold the key, newest first. Two structures keep that cheap: a Bloom filter per SSTable answers "definitely not here" for most files (about 1% false positives at 10 bits per key, the 1.25 GB per node estimated above), and a sparse index per SSTable jumps to the right block. Compaction merges SSTables in the background, keeping only the newest version of each key and dropping expired tombstones. Its strategies trade write cost against read cost: size-tiered compaction merges similar-sized files (cheap writes, more files per read, and a merge can temporarily need as much free disk again as its inputs — hence the 50% fill target in the estimate); levelled compaction keeps files in levels with non-overlapping key ranges (one file per level per read, but each byte is rewritten many times).

Deletes are tombstones. A delete is written as a marker with a timestamp and replicated like any write. It must survive until every replica has it; otherwise a replica that missed the delete will, during repair, look like it has data the others lack and copy the old value back. Cassandra keeps tombstones for a grace period (gc_grace_seconds, 10 days by default) and requires repair to run within that window. A node that has been down longer than the grace period must be wiped and rebuilt rather than rejoined.

12 · Failure modes and trade-offs

One node down. With (3,2,2), reads and writes still meet their quorums; hints accumulate for the down node. A zone down. One replica per zone means every key still has two replicas; the same applies. A network partition between zones. On the side with two replicas of a key, quorum operations succeed; on the side with one, strict quorums fail — unless sloppy quorums let it write to substitutes, in which case both sides accept writes and siblings appear afterwards. That is CAP made concrete, and the choice is per request: a shopping cart write uses sloppy W = 1, a payment-related key uses strict quorums or a different store.

A slow node. It hurts only operations that must wait for it. Coordinators can send reads to the fastest replicas first, or send an extra request after a short delay ("speculative retry") and take whichever answers first.

A hot key. The design spreads keys, not load within a key. Add a cache, read from all N replicas with R = 1 where staleness is fine, or split the key.

Compaction or repair storms. Background work competes with foreground requests for disk. Dynamo built an admission controller that gave background tasks time slices based on how close foreground latency was to its target (for example, the 99th-percentile database read latency over the last 60 seconds compared to a 50 ms threshold).

The trade-offs to state in the close: availability during partitions in exchange for conflicts the application must merge; tunable per-request consistency in exchange for complexity in every client; linear scale-out in exchange for losing joins, secondary indexes and multi-key transactions.

Quorum is not linearizability, precisely

Linearizability means every operation appears to happen at a single instant between its call and its return, so once any read returns a value, every later read returns that value or a newer one. Strict quorums fail this in at least three ways. A write that times out after reaching one replica is neither committed nor cleanly rolled back: some quorum reads will include that replica and return the value, others won't, so the value flickers in and out. A reader can see the new value from a quorum that includes a fast replica, and a second reader shortly after can hit two replicas that haven't received it yet. And sloppy quorums break the overlap entirely. Cassandra can make reads monotonic by doing a blocking read repair — writing the newest value to a quorum before returning — and offers "lightweight transactions" that run a Paxos round for compare-and-set, at roughly four round trips. The senior answer is: quorums give "read your latest completed write, usually"; if you need a register you can build locks or unique constraints on, you need consensus.

DynamoDB chose a leader per partition

The managed DynamoDB service, described in a 2022 USENIX ATC paper, kept Dynamo's partitioning and multi-zone replication but replaced leaderless quorums with a leader per partition. Each partition's replicas form a replication group that elects a leader with Multi-Paxos and holds leadership with a lease. Only the leader serves writes and strongly consistent reads; a write is acknowledged "once a quorum of peers persists the log record to their local write-ahead logs"; any replica can serve eventually consistent reads. A new leader won't serve until the old leader's lease expires, which prevents two leaders from both accepting writes. This removes siblings and client-side merging entirely, at the cost of a brief write unavailability for a partition during leader failover. The paper reports that during the 66-hour Prime Day 2021 event, Amazon systems made trillions of API calls to DynamoDB, peaking at 89.2 million requests per second, with single-digit-millisecond latency. Knowing this distinction shows you understand that "Dynamo-style" and "DynamoDB" are different consistency designs.

Hinted handoff can hide a durability gap

With sloppy W = 2, a write may be acknowledged by one preferred replica and one substitute holding a hint. If the preferred replica then fails permanently before the hint is delivered, only the substitute has the data, and it stores hints in a side table that normal reads don't consult. Dynamo also offered a write-buffering optimisation where writes sat in memory and were flushed by a writer thread; it cut 99.9th-percentile latency by a factor of 5 at peak with a buffer of only a thousand objects, and to limit the risk the coordinator asked one of the N replicas to perform a durable write. These are deliberate trades of durability for latency, and in an interview you should name them as such rather than presenting the store as unconditionally durable.

Rack and zone awareness change the ring walk

Placing replicas on the next N distinct nodes is not enough if two of them share a rack or zone. Real systems annotate each node with its rack and zone and walk the ring choosing nodes in distinct failure domains, falling back only when there aren't enough. With three zones and N = 3, each key gets one replica per zone, so a zone outage leaves two. Reads can then prefer the local zone's replica (lower latency, no cross-zone data-transfer charges) and count it toward R, while writes still need one remote acknowledgement for W = 2, which is exactly the latency you pay for zone-level durability.

Tombstone lifetime couples correctness to operations

The grace period must exceed the longest time a replica could be unaware of a delete. That couples your delete semantics to your operational practice: if full repair runs weekly, the grace period must be longer than a week plus slack; if a node is down longer than the grace period, it must be rebuilt, never simply restarted. Delete-heavy patterns — queues implemented on top of the store, for example — accumulate tombstones that every read must skip until compaction drops them, and Cassandra will fail a query that scans too many tombstones. This is why "don't build a queue on Cassandra" is standard advice, and why time-to-live data is best grouped so whole SSTables expire together.

Secondary indexes break the model

The whole design rests on knowing which node owns a key. An index on another attribute either lives locally on each node — so a query must scatter to all 150 nodes and wait for the slowest — or is a separate, globally partitioned table keyed by the indexed attribute, updated asynchronously and therefore briefly inconsistent with the base data. DynamoDB's global secondary indexes are the second kind and are eventually consistent. If the interviewer adds "and search by email", say which of these you pick and what it costs.

Know when you don't need this

A single PostgreSQL primary with replicas handles tens of thousands of writes per second and several terabytes, with transactions, joins and indexes, run by one engineer. A leaderless store costs all of those and requires clients that handle siblings. Reach for it when the write rate or data size genuinely exceeds one machine, when writes must survive the loss of any machine or zone without a failover pause, or when the access pattern is purely by key. Saying this unprompted is a strong senior signal.

The real case: Amazon's Dynamo paper (SOSP 2007)

DeCandia and colleagues' paper describes the store behind several core services of Amazon's e-commerce platform, including the shopping cart. It is unusually frank about requirements: services stated their latency targets at the 99.9th percentile — the paper's example service must respond within 300 ms for 99.9% of requests at a peak of 500 requests per second — and the store had to stay writable through failures. In the holiday season before publication, the shopping-cart service "served tens of millions requests that resulted in well over 3 million checkouts in a single day", and the session-state service "handled hundreds of thousands of concurrently active sessions".

The production numbers map onto this lesson. "The common (N,R,W) configuration used by several instances of Dynamo is (3,2,2)", typically on "a couple hundred nodes". Average read and write latencies were a few milliseconds, while 99.9th-percentile latencies were "around 200 ms", an order of magnitude higher, driven by load variability, object sizes and locality — the reason tail latency, not average, sets the design. Write buffering lowered 99.9th-percentile latency by a factor of 5. Client-driven coordination (routing straight to a replica) cut 99.9th-percentile read latency from 68.9 ms to 30.4 ms. Conflicts were rare: 99.94% of shopping-cart requests saw one version in a 24-hour profile. And over two years, applications "received successful responses (without timing out) for 99.9995% of its requests and no data loss event has occurred to date".

The paper's load-balancing analysis is also instructive. It measured the "imbalance ratio" (nodes whose load deviates more than 15% from average) and found it as high as 20% at low load, falling as load rose — because at high load the many popular keys spread evenly, while at low load a few active keys dominate. And it explains the switch from random tokens to equal-sized partitions: bootstrapping a node under random tokens took almost a day during busy periods, because streaming had to run at low priority to protect foreground traffic.

The lesson Amazon drew later is in the DynamoDB paper: application developers found managing siblings and N/R/W hard, so the service moved to leader-based replication with simple strongly or eventually consistent reads. Both papers are worth reading side by side.

What goes wrong in practice

Zombie data after a long outage — the tombstone problem above; the fix is process (rebuild, don't rejoin) plus alerts on node downtime. Hint overload — a node down for hours causes many peers to store and later replay hints all at once, a burst that can overload it as it comes back; hint delivery is throttled for this reason (Cassandra defaults to 1,024 KiB/s per delivery thread). Compaction falling behind — write bursts create SSTables faster than compaction merges them, reads touch more files, and tail latency climbs with no change in request rate. Clock skew with LWW — a node with a clock minutes ahead wins every conflict and its writes cannot be overwritten until real time catches up; run NTP (Network Time Protocol, which keeps machine clocks in sync) and alert on skew. Large partitions or hot keys — one key or wide row on three nodes saturates them while the rest of the cluster idles.

What to monitor: per-node read and write latency at p99 and p99.9; pending compactions and SSTables per read; hints stored and delivered; repair progress and the time since the last full repair per range; tombstones scanned per read; dropped messages; disk usage against the 50% compaction headroom; clock skew; and the per-key or per-partition request rate to catch hot keys. Jepsen-style fault-injection testing — partitioning the network and checking the claimed consistency — is how teams find the anomalies quorums allow.

Goal: measure four claims from this lesson: virtual nodes even out load, consistent hashing moves about 1/(n+1) of keys while mod-N moves most, R + W > N avoids stale reads, and vector clocks detect concurrent writes. Python 3.12, standard library only, about two seconds.

"""Consistent hashing with virtual nodes, quorum reads/writes, vector clocks.
Python 3.12 stdlib only."""
import bisect, hashlib, random, statistics

def h(s):                                   # 64-bit position on the ring
    return int.from_bytes(hashlib.md5(s.encode()).digest()[:8], "big")

class Ring:
    def __init__(self, nodes, vnodes):
        self.points = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vnodes))
        self.keys = [p for p, _ in self.points]
    def preference_list(self, key, n=3):    # first n DISTINCT nodes clockwise
        i, out = bisect.bisect(self.keys, h(key)), []
        while len(out) < n:
            node = self.points[i % len(self.points)][1]
            if node not in out: out.append(node)
            i += 1
        return out

keys = [f"user:{i}" for i in range(100_000)]
nodes = [f"n{i}" for i in range(10)]

# 1. Load spread: max/mean keys per node for 1, 16 and 256 virtual nodes.
for v in (1, 16, 256):
    ring = Ring(nodes, v)
    load = {n: 0 for n in nodes}
    for k in keys: load[ring.preference_list(k, 1)[0]] += 1
    print(f"vnodes={v:3}: max/mean load = {max(load.values()) / statistics.mean(load.values()):.2f}")

# 2. Adding an 11th node: how many keys change owner?
before, after = Ring(nodes, 256), Ring(nodes + ["n10"], 256)
moved = sum(before.preference_list(k, 1) != after.preference_list(k, 1) for k in keys)
modn = sum(h(k) % 10 != h(k) % 11 for k in keys)
print(f"ring: {moved / len(keys):.1%} of keys move | hash mod N: {modn / len(keys):.1%} move")

# 3. Quorums: each write reaches W of N=3 replicas (others stay stale for a while).
def stale_read_rate(R, W, trials=20_000):
    rng, stale = random.Random(1), 0
    for _ in range(trials):
        version = [1, 1, 1]                 # every replica holds v1
        for i in rng.sample(range(3), W):   # write v2 lands on W replicas only
            version[i] = 2
        seen = max(version[i] for i in rng.sample(range(3), R))
        stale += seen < 2
    return stale / trials
for R, W in [(1, 1), (1, 2), (2, 2), (1, 3)]:
    print(f"N=3 R={R} W={W} (R+W>N: {R + W > 3}) -> stale reads {stale_read_rate(R, W):.1%}")

# 4. Vector clocks: does one version descend from the other, or are they concurrent?
def compare(a, b):
    ks = a.keys() | b.keys()
    le = all(a.get(k, 0) <= b.get(k, 0) for k in ks)
    ge = all(a.get(k, 0) >= b.get(k, 0) for k in ks)
    return "equal" if le and ge else "a before b" if le else "b before a" if ge else "CONCURRENT"
print(compare({"Sx": 2}, {"Sx": 2, "Sy": 1}))           # b descends from a
print(compare({"Sx": 2, "Sy": 1}, {"Sx": 2, "Sz": 1}))  # siblings: app must merge

Run it: save as kv_lab.py and run python kv_lab.py.

What to look for.

  1. Load spread: max/mean of about 2.26 with one token per node, 1.33 with 16 and 1.11 with 256. With one token, the busiest node does more than twice its share.
  2. Adding an 11th node moves about 9.3% of keys on the ring (the theory says 1/11 = 9.1%) but 90.7% with hash mod N.
  3. Stale-read rates: about 67% for W=1, R=1 and 33% for W=2, R=1, but 0% whenever R + W > N. These are worst cases, because the simulation does no repair between the write and the read; in a real cluster the third replica usually catches up within milliseconds, so the stale window is short but real.
  4. The vector-clock comparison reports "a before b" for a version and its descendant, and "CONCURRENT" for two updates of the same base made through different coordinators.

Try next: remove one node from the ring and measure which nodes absorb its keys with 1 versus 256 tokens (you should see one neighbour versus nearly everyone); then extend stale_read_rate with a sloppy quorum that writes to a substitute instead of a down replica, and watch R + W > N stop protecting you.

Work it out

A cluster runs N=3, W=2, R=2 across three availability zones, one replica per zone, with strict (not sloppy) quorums. A network partition isolates zone C from zones A and B for 90 seconds. Clients in each zone can reach only the replicas on their side of the partition.

(a) What happens to writes from a client in zone A? In zone C? (b) What happens after the partition heals? (c) The team proposes W=1, R=1 "for latency". Evaluate.

Answer

(a) During the partition. A client in zone A can reach A and B, which is 2 replicas — W=2 is satisfiable, so writes succeed and reads with R=2 succeed. A client in zone C can reach only C — W=2 cannot be met, so writes fail and R=2 reads fail too.

This is the CAP trade-off in concrete form: the majority side stays available, the minority side becomes unavailable, and the system has chosen consistency over availability for zone C's clients. It is a consequence of the quorum arithmetic: choosing W=2 with N=3 and strict quorums is choosing to sacrifice the minority side. With sloppy quorums, C could have written to substitutes on its side — but here C's side has no other nodes, so even that would fail.

(b) After healing. Zone C's replica is 90 seconds stale for every key written during the partition. Three mechanisms converge it, at different speeds:

  • Hinted handoff — coordinators in A and B stored hints for the C replica of each key they wrote. On reconnection those hints replay, usually within seconds. This is the fast path.
  • Read repair — any read that includes C notices the older version and writes the newer value back. This fixes hot keys quickly and cold keys never.
  • Merkle-tree anti-entropy — a scheduled comparison of hash trees streams only the differing ranges. This is the backstop that catches whatever hints and reads missed, which is why hints are an optimisation rather than a correctness requirement.

No data is lost and no conflict arises, because the minority side never accepted a write. Had W=1 been configured, both sides would have accepted writes to the same key, producing siblings to merge.

(c) Evaluating W=1, R=1. Latency improves — you wait for the fastest replica rather than the second fastest, which at p99 is a real win. But R+W = 2 is not greater than N = 3, so read and write sets need not intersect:

  • Stale reads are routine. Write to A, read immediately from B, get the old value; a user changes a setting and sees it revert. The lab's worst case was 67% stale before repair.
  • Both sides of a partition accept writes, so you now need conflict resolution — and if that is last-write-wins on unsynchronised clocks, one write is silently discarded.
  • An acknowledged write can be lost. W=1 means one replica confirmed it; if that node dies before replicating, the write is gone.

The response to give: not "no", but "per operation". W=1/R=1 is right for high-volume, loss-tolerant, self-correcting data — telemetry, view counts, cache-like values. Quorum is right for anything a user would notice reverting. Since N, R and W are chosen per request, route each kind of traffic accordingly — and measure what the quorum path actually costs before trading correctness for a latency number nobody has measured.

Estimate it

A 60-node cluster (20 per zone, N=3) holds 90 TB of replicated data evenly. One node's disk dies permanently. Each surviving node can stream at most 80 MB/s for recovery without hurting foreground latency. How long until full redundancy is restored with (a) one token per node, (b) 16 well-allocated tokens per node?

Answer

The dead node held 90 TB ÷ 60 = 1.5 TB. (a) With one token per node, its ranges are replicated on its two ring neighbours (zone-aware placement keeps them in other zones), so at best two nodes stream: 1.5 TB ÷ (2 × 80 MB/s) = 1.5 × 1012 ÷ 1.6 × 108 ≈ 9,400 s, about 2.6 hours, assuming the replacement can absorb 160 MB/s. (b) With 16 tokens, the node's 16 ranges have replicas spread across up to 32 different peers, so roughly 30 nodes can each send about 50 GB: 50 × 109 ÷ 8 × 107 ≈ 625 s, about 10 minutes — if the data is re-replicated to many nodes rather than one replacement. If a single new node must receive it all, its own ingest (say 500 MB/s) is the limit: 1.5 TB ÷ 0.5 GB/s = 3,000 s, 50 minutes. State the bottleneck explicitly: it moves from the senders to the receiver, which is why some systems re-replicate to many nodes first and rebalance onto the replacement later.
