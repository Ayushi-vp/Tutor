A social app's home page shows a user's name, photo, friend count and the last few posts of each friend. Rendering one page touches a few hundred small pieces of data, and the app serves millions of pages a minute. Every piece lives in a relational database, and the database is fast — a well-indexed lookup takes a millisecond or two — but a few hundred lookups per page times millions of pages is hundreds of millions of queries a second. No database cluster of reasonable size serves that, and the same few thousand celebrity profiles are read over and over.

So the team puts memory in front of the database. A cache server holds recently read values in RAM and answers in well under a millisecond. Most reads now never touch the database. Then the trouble starts, and it is not the trouble anyone expected. A deploy restarts all cache servers at once and the database, suddenly receiving every read, falls over and stays down, because a down database cannot refill the cache. A popular post's cache entry expires and ten thousand requests all miss in the same instant. A user edits their bio, and for the next hour some friends see the old one because a slow request wrote the old value back after the edit. A celebrity's profile key gets so many reads that the one server holding it melts, taking thousands of unrelated keys with it.

A cache at scale is not "a hash map with more memory". It is a distributed system with its own sharding, replication, eviction, failure handling and — the part that surprises people — consistency problems. Facebook's "Scaling Memcache" paper, the case study at the end, describes a deployment that processes billions of requests per second and is mostly about exactly these problems.

This lesson designs a distributed cache in interview order: requirements, hand-worked estimates, API and data model, architecture, then deep dives into sharding and replication, eviction and TTLs, hot keys, stampedes, and keeping the cache consistent with the database. It closes with failure handling, Facebook's measured results, and a lab that reproduces a stampede and fixes it.

The mental model: a desk in front of an archive

Think of a researcher working in a huge archive. The archive (the database) has everything, carefully filed and authoritative, but every retrieval means walking to the stacks: slow. So the researcher keeps a desk (the cache) with copies of the documents they use most. Most of the time the answer is already on the desk. When it isn't, they walk to the stacks, read the original, and put a copy on the desk. The desk is small, so when it is full they clear off whatever they haven't touched for longest. If an original in the archive is corrected, the copy on the desk is now wrong, so the archivist sends a note: "throw away your copy of file 42". And copies on the desk are dated, so anything older than a day gets thrown away regardless.

Each sentence of that story is a design decision. Most answers come from the desk: the hit rate. Walking to the stacks and making a copy: cache-aside filling on a miss. Clearing off the least recently touched copy: LRU eviction. The archivist's note: invalidation. Throwing away old copies: a TTL (time to live).

Where the analogy breaks is scale. In a real system there are thousands of researchers sharing hundreds of desks, the same document is wanted by ten thousand people at once, notes from the archivist arrive late or out of order, and a desk can vanish without warning. A distributed cache is the set of rules that keeps that crowd fast and mostly correct.

The big picture

Why one big cache server isn't enough

A single cache machine is limited in three ways at once. Its memory caps how much of the working set fits — a few hundred gigabytes at most, while a large product's hot data can be terabytes. Its network card and CPU cap throughput — a few hundred thousand to a million small operations per second — while a large product needs tens or hundreds of millions. And it is a single point of failure: when it restarts, every read becomes a miss. So the cache is split across many machines, each holding a slice of the keys, and the client decides which machine to ask by hashing the key. That split is what makes it a distributed cache, and it brings the distributed-systems questions with it: what happens when a machine joins or dies, when one slice is far busier than the rest, and when copies of the same value on different machines or in different regions disagree with the database.

The design has four layers of decisions. Where does a key live? Keys are spread across many cache nodes by hashing, so the cluster's memory and throughput add up. What stays in memory? Memory is limited, so an eviction policy picks what to drop, and TTLs expire entries that may be stale. How do reads and writes interact with the database? The usual pattern is cache-aside with delete-on-write. What happens under stress? Hot keys, stampedes, node failures and cold restarts — the cases that turn a performance optimisation into an outage. The rest of the lesson takes those in turn, always measuring the result the way the database feels it: in misses per second.

1 · Requirements

Functional. get, set with a TTL, delete, and batched multi-get (a page needs dozens of keys at once). Optionally atomic increments for counters. Values are small — typically under a few KB, with a hard cap around 1 MB.

Non-functional. Sub-millisecond latency inside a data centre at the median and a few milliseconds at the 99th percentile. Millions of operations per second, scaling by adding nodes. High hit rate on the working set. Graceful behaviour when nodes fail: the database must never see a sudden flood. Bounded staleness: after a write, readers should see the new value within seconds at most.

The clarifying questions. First: "Is this a cache or a data store?" If the data exists only in this system (sessions, rate-limit counters, a queue), losing a node loses data, and you need replication and persistence; if every value can be rebuilt from the database, losing a node only costs misses. Second: "How stale may a read be?" A friend count can be a minute old; a permission check cannot be stale at all and probably shouldn't be cached. Third: "What is the read-to-write ratio?" Caching pays when each value is read many times per write.

2 · Back-of-envelope estimates

Scenario: the cache in front of an AI product's user, profile and feature data. 2,000,000 reads/s at peak, 500 million distinct keys requested over a day, average value 1 KB, target hit rate 95%.

Database load is set by the miss rate. 5% of 2,000,000 = 100,000 reads/s reach the database. If the hit rate falls to 90%, that becomes 200,000/s — double — even though "90%" sounds almost as good as "95%". If the cache tier vanishes entirely, the database sees 2,000,000/s, 20 times its normal load. Put this in front of the interviewer early: it is the number that decides every failure-handling choice later.

Memory. Each item costs its value plus its key plus per-item metadata (pointers, expiry, flags — around 50 bytes in memcached or Redis), and memory allocators waste some space to fragmentation. Say 1,000 + 50 + 50 = 1,100 bytes per item. All 500 million items: 500 × 106 × 1,100 B = 550 GB. Add 25% for fragmentation and headroom: about 690 GB.

But do we need all of it? Access is skewed. In the lab, a workload where key i is requested with weight 1/(i+1) (a Zipf distribution, typical of real traffic) gave a 50% hit rate with a cache holding just 1% of keys, 66% at 5% and 79% at 20%. Real workloads vary, so measure — but caching the hot fraction often gets most of the benefit. Suppose measurement shows 30% of keys give 95%: that is about 210 GB.

Nodes. With 64 GB of usable cache memory per node, 690 GB needs 11 nodes, and 210 GB needs 4. Throughput: 2,000,000 reads/s ÷ 11 nodes ≈ 182,000 ops/s per node, which a single memcached or Redis node handles (Redis is mostly single-threaded per instance, so run several instances per machine to use all cores). Network: 2,000,000 × 1 KB = 2 GB/s = 16 Gbit/s total, about 1.5 Gbit/s per node — fine on 25 Gbit/s cards. Plan for one or two node failures without losing too much hit rate: about 14 nodes.

The cost of losing one node. With 14 nodes, a dead node takes 1/14 of keys with it. Those keys miss until refilled: 2,000,000 × 1/14 ≈ 143,000 reads/s extra to the database, more than doubling its 100,000/s load. That is why the failure-handling dive matters even for a "simple" cache.

The hot-key ceiling. A single key can only be served by its one node: roughly 200,000–1,000,000 small operations per second depending on the server. A key above that needs special handling regardless of cluster size.

3 · API

get(key)                          -> value | miss
get_multi([k1, k2, ...])          -> {k: value}     # one round trip per node, fanned out
set(key, value, ttl_s)            -> ok
delete(key)                       -> ok
incr(key, n)                      -> new value       # atomic counter
lease_get(key)                    -> value | (miss, lease_token) | wait
lease_set(key, value, token, ttl) -> ok | rejected   # rejected if the token was invalidated

The last two are the senior addition, from Facebook's design, and we'll build up to why they exist. Everything is keyed by a string the application constructs, such as user:42:profile:v3. Putting a version number in the key (v3) is a cheap, powerful trick: when the format of a value changes, bump the version and old entries are simply never read again.

4 · Data model inside a node

Each node is an in-memory hash table from key to item, where an item holds the value, its expiry time, flags and links for the eviction structure. Memcached stores items in a slab allocator: memory is divided into classes of fixed-size chunks (the Facebook paper describes classes starting at 64 bytes and growing by a factor of 1.07 up to 1 MB), each item goes in the smallest chunk that fits, and each class keeps its own LRU list. Fixed-size chunks avoid fragmentation, but if the mix of value sizes shifts, one class can be starved while another has spare memory, so Facebook added an allocator that moves memory between classes based on eviction rates. Redis stores richer types (strings, hashes, sorted sets, lists) and uses a general allocator. Expired items are removed lazily when touched and by a background sweep.

5 · High-level architecture

Three pieces. Cache nodes are dumb on purpose: in memcached, servers do not talk to each other at all. A client library or proxy holds the intelligence: it maps keys to nodes, batches multi-gets, applies timeouts, and routes around failures. Facebook runs a proxy called mcrouter on each web server for routing, pools and failover; Redis Cluster puts the routing knowledge in "smart clients" that cache which node owns each hash slot. An invalidation pipeline deletes keys when the database changes.

A read: the application asks the client library for 24 keys (the Facebook paper reports an average of 24 keys per batched request). The library hashes each key to a node, sends one request per node in parallel, gathers the results, and returns hits plus a list of misses. For each miss the application reads the database and sets the value with a TTL. A write: the application writes the database, then deletes the affected keys. At scale, deletes come from a daemon that tails the database's commit log, so they cannot be forgotten if an app server crashes between the write and the delete.

6 · Deep dive: sharding and replication

Keys must spread over nodes so memory and throughput add up. Two schemes dominate. Consistent hashing (from in2) places nodes on a hash ring with virtual nodes; a key goes to the next node clockwise; adding a node moves about 1/(n+1) of keys. Fixed hash slots are what Redis Cluster uses: slot = CRC16(key) mod 16384, and each primary node owns a set of slots. Moving data means moving slots one at a time. During a move, a client asking the old owner for a key that has already moved gets an ASK redirect for that one request; once the move completes, it gets MOVED and updates its slot map. Slots make ownership explicit and rebalancing incremental. Redis also supports hash tags: only the part of a key inside braces is hashed, so {user:42}:profile and {user:42}:settings share a slot and can be used together in one multi-key command.

Whatever the scheme, remember what a moved key means for a cache: a miss. Adding a 15th node to 14 moves about 1/15 of keys, so for a while 2,000,000 × 1/15 ≈ 133,000 extra reads per second hit the database. Grow the cluster during quiet hours, or warm the new node first.

Replication answers two needs. Read capacity: a key fetched by many clients at once, or a small set of keys read very often, can be copied to several nodes and reads spread across them. Facebook replicates within a pool when the application fetches many keys together, the whole set fits on one or two servers, and the request rate is more than one server can handle; its example is a server holding 100 items that handles 500,000 requests per second, each request asking for 100 keys — splitting the keys over two servers would double the request count without halving the per-request work, while replicating doubles capacity. And availability: Redis primaries have replicas that take over on failure. Redis replication is asynchronous — the primary does not wait for replicas unless a client calls WAIT — so a failover can lose the last writes and replicas can serve slightly stale data. For a pure cache that is acceptable; for Redis as a data store it is the risk you must name.

7 · Deep dive: eviction and TTLs

When memory fills, something must go. LRU (least recently used) evicts the entry untouched for the longest time, betting that recent use predicts future use. Exact LRU keeps every item in a doubly linked list and moves it to the front on each access — the lab's OrderedDict does exactly this. That costs two pointers per item and a list update on every read, which under heavy multi-threaded load becomes a contention point. Redis instead approximates LRU: on each eviction it samples a few keys (maxmemory-samples, default 5) and evicts the oldest of the sample. Its documentation explains the reason plainly: a true LRU "costs more memory". With 5 samples the approximation is close to true LRU on realistic workloads, and raising the sample count makes it closer at more CPU cost.

LFU (least frequently used) evicts the entry with the fewest recent accesses. It protects consistently popular keys from being flushed by a one-off scan — a batch job reading a million keys once each pushes every popular item out of an LRU cache, but barely affects an LFU one. Pure frequency counts never forget, so a key that was popular last month stays forever; Redis's LFU keeps a small logarithmic counter per key that decays over time. Redis offers both, for all keys (allkeys-lru, allkeys-lfu) or only for keys with a TTL (volatile-*), plus noeviction, which rejects writes when memory is full — the right setting when Redis holds data you can't lose, and the wrong one for a cache.

TTLs do a different job from eviction: they bound how stale an entry can be, whether or not memory is tight. Choose them per key family from how stale the data may be: seconds for counters, minutes for profiles, hours for rarely changing configuration. Two refinements matter. Jitter: entries created together (a warm-up, a batch load) with the same TTL expire together and stampede the database together, so add a random ±10–20%. And short TTLs for short-lived items: Facebook found a family of keys with short useful lives sat in memory until they reached the end of the LRU list; giving them short expirations and a separate structure that evicts expired items promptly cut that family's share of the pool from 6% to 0.3% without affecting the hit rate.

Pools are the other lever. Different key families have different sizes, churn and miss costs, and in one shared LRU a high-churn family evicts low-churn keys that are expensive to recompute. Facebook splits servers into pools: a default "wildcard" pool, a small pool for frequently accessed keys whose misses are cheap, a large pool for infrequently accessed keys whose misses are expensive.

8 · Deep dive: hot keys

Skew is why caches work, and its extreme is the cache's weak spot. A key at 400,000 requests per second hashes to one node. If that node handles 200,000 ops/s, it saturates: its queue grows, its latency climbs, and every other key on it — 1/14 of the cache — gets slow too. Adding nodes changes nothing; the key still lives on one of them. The fixes, from most to least effective:

  • An in-process cache on each app server with a 1–5 second TTL. With 300 app servers and a 2-second TTL, the shared tier sees at most 300 ÷ 2 = 150 requests per second for that key instead of 400,000. The cost is up to 2 seconds of extra staleness for that key, which is almost always fine for read-mostly hot data.
  • Key replication: store the value under key#0 … key#9 on different nodes and read a random one. Load spreads 10 ways; a write or invalidation must now touch 10 keys.
  • Serve it from a CDN if it is public — a viral post's image or text shouldn't reach your data centre at all.
  • Bounded-load hashing: a variant of consistent hashing that caps any node at a factor (say 1.25×) above average by spilling excess keys to the next node; it helps balance many warm keys, though not one key hotter than any single node.

Finding hot keys is half the battle. Sample requests in the client or proxy and count per key, alert on per-node CPU and network skew (one node at 90% while the rest sit at 30% is the signature), and keep a list of known-hot keys that the client caches locally.

9 · Deep dive: stampedes

A stampede (or thundering herd) is the cache's most famous failure. Take a key read 2,000 times per second whose database query takes 200 ms. When its TTL expires, every request in the next 200 ms misses: 2,000 × 0.2 = 400 identical database queries, all computing the same value. For an expensive query (an aggregation, a recommendation, an LLM call) that can saturate the database on its own, and every app thread waiting adds latency. The lab reproduces exactly 400 database calls.

Four defences, often combined:

  • Leases (a lock per key at the cache). On a miss, the cache gives the first client a lease token and tells subsequent clients to wait briefly. Facebook's servers hand out a token for a key at most once every 10 seconds; other requests get "wait a short amount of time and retry", and by then the lease holder has usually filled the key "within a few milliseconds". In the lab: 1 database call instead of 400. The cost is a few milliseconds of extra latency for the waiting requests.
  • Request coalescing (single-flight) inside each app server: concurrent requests for the same missing key share one database call. It cuts the herd from 400 to one per app server — with 300 servers still up to 300 — so it complements leases rather than replacing them.
  • Serve stale while refreshing. Keep the expired value for a short grace period; the lease holder refreshes while everyone else gets the slightly old value with no wait. Facebook does a version of this: a deleted value is kept briefly in a side structure and can be returned, marked stale, to clients that accept it.
  • Probabilistic early refresh (XFetch). Each request, while the value is still fresh, refreshes it early with a probability that rises as expiry approaches and with how long the recomputation takes. The rule from Vattani et al.: refresh if now − δ·β·ln(rand()) ≥ expiry, where δ is the recompute time and β ≥ 1 tunes eagerness. Because ln(rand()) is negative, the left side is now plus a random positive amount, usually small and occasionally large, so with high request rates exactly one request almost always refreshes shortly before expiry and nobody ever misses. The lab shows 2 database calls in 2 minutes and zero waiting requests.

And separately, TTL jitter prevents the mass-expiry version of the problem, where thousands of different keys filled at the same moment expire together.

10 · Deep dive: keeping the cache consistent with the database

Why delete on write instead of update? Two writers can interleave. Writer A sets the price to 10 in the database; writer B sets it to 12 in the database and the cache; then A's cache update, delayed by a garbage-collection pause, sets the cache to 10. The database says 12, the cache says 10, until the TTL expires. Deletes are idempotent and order-insensitive: whatever order they arrive in, the result is "no entry", and the next read fills from the database. Facebook's paper states this choice directly: "we choose to delete cached data instead of updating it because deletes are idempotent".

Delete-on-write still has a race, the stale set. Reader R misses on the price, reads 10 from the database, then pauses. Writer W updates the price to 12 and deletes the key. R wakes up and sets the cache to 10. The stale value now lives for the full TTL. Leases close this: R's miss gave it a lease token; W's delete invalidated the token; R's set with the old token is rejected. It works like load-link/store-conditional in CPUs — a write succeeds only if nothing touched the location since you read it.

At scale, deletes come from the database's commit log rather than from application code, because an app server can crash between committing and deleting. Facebook's mcsqueal daemons read each database's committed statements, extract the keys to invalidate, batch the deletes and broadcast them to every cache cluster in the region. Because the deletes are derived from a durable log, lost or misrouted ones can be replayed. Across regions, a user who just wrote in one region may read from a replica database in another region that hasn't received the write yet; Facebook's remote markers flag such keys so that, until replication catches up, a miss on them goes to the primary region's database instead of the stale local replica.

The honest summary: a look-aside cache gives eventual consistency with a small stale window, made smaller by delete-on-write, leases and log-driven invalidation, and bounded by TTLs as the last line of defence. Data that must never be stale — permissions, balances — should be read from the source of truth or cached with explicit versioning.

11 · Failure modes and trade-offs

One node dies. Its keys all miss. Rehashing them onto the remaining nodes sounds natural but is dangerous: hot keys land on healthy nodes and can overload them, cascading the failure, and the moved keys all miss at once. Facebook's answer is Gutter: about 1% of cache servers kept as a spare pool. When a client gets no response from a server, it retries against Gutter; on a Gutter miss it reads the database and fills Gutter with a short TTL. Gutter entries aren't invalidated by normal deletes, so the short TTL is what bounds their staleness.

The whole tier restarts or a new cluster comes up empty. The database receives the full read load. Defences: rolling restarts one node at a time; keeping cache contents in memory that survives a process restart (Facebook moved memcached's data into System V shared memory so software upgrades keep the cache warm, after finding that a server takes a few hours to reach 90% of its peak hit rate and upgrading a set of servers could otherwise take over 12 hours); and cold-cluster warmup, where a new cluster's clients fill misses from a warm cluster's cache rather than from the database until the hit rate stabilises.

Incast and fan-out. A request for 100 keys spread over 100 nodes gets 100 replies at once, which can overflow switch buffers and drop packets. Clients cap outstanding requests with a sliding window that grows on success and shrinks when requests go unanswered.

The trade-offs to state in the close: memory spent against misses saved; staleness accepted for speed; simplicity of dumb servers against intelligence in clients and proxies; and the uncomfortable fact that a cache at scale becomes an availability dependency, which must be engineered as one.

Hit rate is not linear in memory, so measure the curve

Doubling cache memory does not double the hit rate; with skewed access, the first few percent of keys bring most of the hits and each extra gigabyte brings less. The lab's Zipf workload gave 50% at 1% of keys, 66% at 5% and 79% at 20%. The useful tool is a miss-ratio curve: hit rate (or misses per second) plotted against cache size, measured from a sample of real traffic replayed through simulated caches of different sizes. With it, sizing becomes an economic question — the cost of the next 100 GB of RAM against the database capacity its extra hits save — instead of a guess. It also reveals when a workload has a "cliff", where the working set just fails to fit and the hit rate collapses with a small reduction in memory, which is exactly what happens when one node is lost.

Memcached versus Redis is a real design choice

Memcached is a multi-threaded, pure cache: simple values, no persistence, no replication, servers that never talk to each other. That makes it predictable and easy to scale for look-aside caching; Facebook raised its peak get rate by moving to fine-grained locking, so one process uses all cores. Redis is single-threaded per instance for command execution (it can use extra threads for network I/O), and offers rich data structures — sorted sets for leaderboards, hashes for objects, streams, atomic scripts — plus replication and optional persistence. Those features tempt teams into using it as a database. The senior answer: use memcached-style caching when the database is the source of truth; use Redis when you need its data structures or atomic operations; and if Redis is the source of truth, treat it as a database with durability requirements, not a cache.

Negative caching

A miss for a key that doesn't exist in the database ("user 9999999 has no profile") is just as expensive as a real miss, and nothing fills the cache, so the next request misses again. Attackers exploit this by requesting random non-existent IDs. Cache the absence too — store a sentinel "not found" value with a short TTL — or put a Bloom filter of existing keys in front of the database so impossible keys are rejected without a query.

Multi-get fan-out and tail latency

A page that fetches 100 keys from 50 nodes waits for the slowest of 50 responses. If each node has a 1% chance of a 10 ms hiccup, the chance at least one of 50 hiccups is 1 − 0.9950 ≈ 39.5%, so the page's tail latency is dominated by rare slow nodes. Three mitigations: co-locate keys fetched together on the same node with hash tags, which reduces fan-out; replicate small, hot, often-batched key sets so each request goes to fewer, less-loaded servers; and send a duplicate request to a replica if the first hasn't answered within the 95th-percentile latency (a hedged request).

Consistency with the database's replication

If the cache is filled from a database replica that lags the primary, a read right after a write can miss, read the old value from the lagging replica, and put it in the cache — after the invalidation has already happened. The stale value then lives for the full TTL. Fixes: fill from the primary for a short time after a write to that key (Facebook's remote markers serve this purpose across regions), delay invalidations until replication catches up, or include a version or timestamp in cached values and reject fills older than the last known write.

Caching in AI systems

The same principles apply to new kinds of cached values. An exact-match cache of LLM responses keyed by a hash of (model, system prompt version, parameters, normalised prompt) is a classic look-aside cache with an expensive miss — seconds of GPU time — so stampede protection matters even more. Semantic caches, which reuse an answer when a new prompt's embedding is close to an old one, trade correctness for hit rate: two questions can be close in embedding space and need different answers. And the KV cache (key-value cache) inside a model server, which stores attention keys and values for a prompt prefix so it isn't recomputed, is a cache with LRU eviction, hot prefixes (a shared system prompt) and memory pressure — the same vocabulary at a different layer.

The real case: Scaling Memcache at Facebook (NSDI 2013)

Nishtala and colleagues describe how Facebook turned open-source memcached into a caching layer that processes billions of requests per second and stores trillions of items. Memcache sits as a "demand-filled look-aside cache" in front of MySQL: web servers read from memcache, fill it on misses, and delete keys after writes.

Leases. The paper introduced leases for both stale sets and thundering herds. Servers return a lease token for a given key at most once every 10 seconds; other requesters are told to wait and retry. For a set of keys particularly susceptible to thundering herds, measured for a week, leases cut the peak database query rate from 17,000 per second to 1,300 per second — and since databases are provisioned for peak load, that is a direct capacity saving.

Gutter. Machines that fail are not instantly removed from the routing configuration — that can take a few minutes — so Facebook keeps a Gutter pool of about 1% of a cluster's memcached servers. Clients that get no response retry against Gutter. The paper reports that this reduced client-visible failures by 99% and converted 10%–25% of failures into hits each day; when a memcached server fails entirely, Gutter hit rates "generally exceed 35% in under 4 minutes and often approach 50%". The paper explicitly rejects rehashing failed keys among remaining servers because "a single key can account for 20% of a server's requests".

The network. Clients send gets over UDP to cut overhead and sets and deletes over TCP through mcrouter for reliability. Under peak load, clients observed 0.25% of gets discarded, about 80% of them due to late or dropped packets; clients treat those as misses but skip filling the cache afterwards, to avoid adding load to a possibly overloaded server or network. A sliding window limits outstanding requests to avoid incast congestion.

Invalidation. mcsqueal daemons on every database extract deletes from committed SQL statements and broadcast them; the paper notes only 4% of all deletes issued actually invalidate a cached item, which is why deletes are batched through routers rather than sent directly from each database to every cache server.

Operations. A memcached server reaches 90% of its peak hit rate within a few hours, so upgrading a set of servers could take over 12 hours of carefully managed database load; storing cache data in shared memory that survives a restart solved it. Short expirations for short-lived key families cut one family's share of memory from 6% to 0.3%.

What makes the paper worth reading in full is that almost none of it is about making memcached faster. It is about protecting the database from the cache's failure modes and keeping stale data bounded — the deep dives of this lesson, measured in production.

What goes wrong, and what to watch

Mass expiry after a warm-up or bulk load, creating a sawtooth of database load every TTL period — fix with jitter. A hot key saturating one node — watch per-node CPU and network skew. Memory pressure from a new key family evicting valuable keys — watch evictions per second per pool and the age of evicted items (if items are evicted minutes after being written, the cache is too small for its working set). Big values (a 1 MB list cached as one key) causing latency spikes for everything else on that node — watch value-size distribution. Client misconfiguration after a topology change, where some clients hash with the old node list and others with the new, splitting keys and doubling misses.

Metrics: misses per second reaching the database (the number that matters), hit rate per key family, evictions and evicted-item age, p99 latency per node, per-node ops and bytes for skew, connection counts, replication lag and failover events for Redis, and database load attributable to cache misses. Alert on miss-rate jumps, not hit-rate dips: a 5-point hit-rate drop can mean double the database load.

Goal: build an LRU cache with TTLs, see how hit rate grows with cache size under skewed traffic, and reproduce a cache stampede, then stop it with a lease and with probabilistic early refresh. Python 3.12, standard library only, about one second.

"""An LRU cache with TTL, hit rate under a skewed workload, and a cache stampede
with and without a lease / probabilistic early refresh. Python 3.12 stdlib only."""
import math, random
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.cap, self.d = capacity, OrderedDict()      # key -> (value, expires_at)
    def get(self, key, now):
        item = self.d.get(key)
        if item is None or item[1] <= now:              # missing or expired
            self.d.pop(key, None)
            return None
        self.d.move_to_end(key)                         # mark most recently used
        return item[0]
    def set(self, key, value, now, ttl):
        self.d[key] = (value, now + ttl)
        self.d.move_to_end(key)
        if len(self.d) > self.cap:
            self.d.popitem(last=False)                  # evict least recently used

# 1. Hit rate vs cache size for a Zipf-like workload over 100,000 keys.
rng = random.Random(42)
N_KEYS = 100_000
weights = [1 / (i + 1) for i in range(N_KEYS)]          # key i is requested ~ 1/(i+1)
stream = rng.choices(range(N_KEYS), weights, k=300_000)
for frac in (0.01, 0.05, 0.20):
    c, hits = LRUCache(int(N_KEYS * frac)), 0
    for t, k in enumerate(stream):
        if c.get(k, t) is not None: hits += 1
        else: c.set(k, "v", t, ttl=10**9)
    print(f"cache = {frac:4.0%} of keys -> hit rate {hits / len(stream):.1%}")

# 2. Stampede: a hot key gets 2 requests per ms; a DB refill takes 200 ms; TTL 60 s.
def simulate(mode, ms=120_000, rate=2, fetch_ms=200, ttl=60_000, beta=1.0):
    expires, db_calls, refill_done, waits = ttl, 0, None, 0
    for now in range(ms):
        if refill_done is not None and now >= refill_done:
            expires, refill_done = now + ttl, None      # value written back
        for _ in range(rate):
            fresh = now < expires
            if mode == "xfetch" and fresh and refill_done is None:
                # refresh early with probability rising as expiry nears (XFetch)
                if now - fetch_ms * beta * math.log(rng.random()) >= expires:
                    db_calls, refill_done = db_calls + 1, now + fetch_ms
                continue
            if fresh: continue
            if mode == "naive":
                db_calls += 1                           # every miss goes to the DB
                if refill_done is None: refill_done = now + fetch_ms
            elif refill_done is None:                   # lease: first miss refills,
                db_calls, refill_done = db_calls + 1, now + fetch_ms
            else:
                waits += 1                              # others wait briefly and retry
    return db_calls, waits
for mode in ("naive", "lease", "xfetch"):
    calls, waits = simulate(mode)
    print(f"{mode:6}: DB calls in 2 minutes = {calls:4}, requests told to wait = {waits}")

Run it: save as cache_lab.py and run python cache_lab.py.

What to look for.

  1. Hit rate rises quickly then flattens: about 50% with the cache holding 1% of keys, 66% at 5% and 79% at 20%. Skew is why small caches work; the flattening is why "just add memory" stops paying.
  2. The naive stampede makes 400 database calls in two minutes, all inside one 200 ms window after the TTL expires: 2 requests per millisecond for 200 ms.
  3. The lease makes 1 call and tells 399 requests to wait; in a real system they retry a few milliseconds later and hit.
  4. XFetch makes 2 calls (one early refresh before each expiry inside the 2-minute window) and nobody waits or misses.

Work it out

A product page service does 800,000 reads/s with a 96% cache hit rate across 8 cache shards. The database sustains 60,000 reads/s before latency degrades. Cache TTL is 300 seconds, set uniformly when an entry is created. A deploy restarts the entire cache tier at 14:00.

(a) What is normal database load? (b) What happens at 14:00? (c) Suppose instead the tier survives, but a product goes viral at 400,000 requests/s for one key. What happens, and what do you do?

Answer

(a) 4% of 800,000 = 32,000 reads/s to the database, about half its capacity. The hit rate can fall to about 92.5% (7.5% of 800,000 = 60,000) before the database is in trouble — a 3.5-point drop, which shows how sensitive the database is to the miss rate.

(b) The restart. The cache is empty, so the hit rate is 0% and all 800,000 reads/s hit the database — 13× its capacity. It queues, latency climbs, connections run out, timeouts begin. Clients retry, adding more load. Because requests now time out before returning, the cache cannot refill either: the system cannot recover on its own, which is what makes a cold cache an outage rather than a slowdown.

Even once restored, the uniform 300-second TTL means everything filled in the recovery minute expires together five minutes later, producing a second wave. The uniform TTL turned a one-off incident into a recurring one.

What should have been in place, in order of importance:

  • Admission control on the database. Cap concurrent queries so it serves, say, 55,000/s and rejects the rest quickly. Service degrades — some requests fail fast — but the database stays up, and the requests that succeed refill the cache, so the system heals.
  • Rolling restart with warm-up. Never restart the whole tier. Restart one shard at a time: 1/8 of traffic misses fully (100,000/s) and the other 7/8 at 4% (28,000/s), so the database sees about 128,000/s — still more than double its capacity, so combine with admission control, warm the shard from a peer or from persisted memory before it takes traffic, or restart during low traffic.
  • TTL jitter — 300 seconds ± 20% — so expiry is spread instead of synchronised. A one-line change that removes an entire class of incident.
  • Persistence or a warm standby (memory that survives the process restart, as Facebook did with shared memory) so a restarted node comes back populated.

(c) The viral key. 400,000 requests/s for one key all hash to one shard. That shard must serve 400,000/s against a per-node capacity of perhaps 125,000/s, so it saturates — and because it also holds 1/8 of all other keys, those slow down too. One key has degraded 12.5% of the entire cache. Adding shards does not help: the key still hashes to exactly one of them.

The fixes, in order of how fast you can apply them:

  • Local in-process cache with a 1–5 second TTL. Each app server caches this key itself, so the shared tier sees one request per server per TTL instead of 400,000/s. With 200 app servers and a 2-second TTL, that is 100 requests/s reaching the shard. By far the most effective fix, and it needs no topology change.
  • Key replication — store the value under key#0 through key#9 and have clients read a random one. Traffic spreads across up to 10 shards. Invalidation now means deleting 10 keys.
  • Promote to the CDN or edge if the content is public. A key at 400,000/s should probably not be reaching your infrastructure at all.

The connecting observation: (b) and (c) are the same lesson from opposite directions. Sizing by aggregate hit rate and aggregate capacity hides both failures — one is about what happens when the cache is absent, the other about what happens when load is skewed. Neither appears in a spreadsheet of averages, and both are the normal way cache tiers fail.

Diagnose it

After a schema change, users report that edited profiles sometimes show the old bio for exactly 10 minutes (the TTL), then fix themselves. Writes go to the primary database and then delete the cache key; cache misses are filled from a read replica that lags the primary by up to 2 seconds. What is happening, and how do you fix it?

Answer

A stale set via replication lag. Sequence: the user writes the new bio to the primary; the app deletes the key; a reader immediately misses, reads the replica, which hasn't received the write yet, and fills the cache with the old bio. The delete already happened, so nothing removes the stale value until the 10-minute TTL expires — exactly the symptom.

Fixes, any of which works: fill from the primary for a short window after a write to that key (a "recently written" marker, like Facebook's remote markers); send a second, delayed delete a few seconds after the write (longer than worst-case replication lag); use leases so the fill started before the delete is rejected (this only helps if the miss happened before the delete); or store a version number in the row and cache, and reject fills older than the latest version recorded at write time. The schema change probably made the window visible by slowing replication — check replica lag around the incidents.
