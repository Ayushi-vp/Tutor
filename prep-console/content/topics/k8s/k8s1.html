In 2012 a small team ships a Python web service. On the developer's laptop it works. On the test server it crashes, because that server has an older OpenSSL library. On the production machines it works for a week, until an operations engineer installs a monitoring agent that upgrades a shared library, and two other services on the same machines break. Each new machine takes a day to set up by hand from a wiki page that is never quite current. Nobody can say with confidence what is installed where.

The obvious fix was the virtual machine: give every service its own complete computer, with its own operating system, built from a saved disk image. That solved "works on my machine", but at a cost. Each VM boots a full kernel and init system, which takes tens of seconds. Each carries its own kernel, page cache and system daemons in memory, often a few hundred megabytes before the application does anything. A disk image is gigabytes. Packing twenty small services onto one server meant twenty copies of an operating system.

Linux had, by then, quietly gained the pieces of a lighter answer. Namespaces could give a process its own view of process IDs, mounts and network. Control groups could cap what it used. What was missing was a convenient way to package the files a program needs and start it inside those features with one command. In 2013 Docker supplied that: an image format, a build tool and docker run. A service now shipped with exactly its own libraries, started in under a second, and used only the memory its process used.

A decade later this is the default way software is deployed, and Kubernetes runs nearly everything on top of it. Yet many engineers who use containers every day hold the wrong model: they think of a container as a small VM. That model fails them exactly when it matters, when a container is slow to stop, will not start on a new server, leaks zombie processes, or must run code nobody trusts.

This lesson builds the correct model. It starts from what a plain process shares with everything else on a machine, shows how a VM and a container each separate workloads and what each costs, opens up an image to see what is really in it, follows the chain of programs from the docker command down to the system calls, and then traces docker run step by step with real values. It ends with where the model matters in production: architectures, PID 1, logs, and running code you do not trust.

A process with blinkers, a budget and a suitcase

Picture a normal program running on a Linux server. It can see every other process with ps. It sees the whole file system, so it uses whatever version of Python or OpenSSL is installed at /usr/lib. It shares the machine's network interfaces and ports with everyone. It can use as much memory and CPU as it can grab. That openness is what made the 2012 story above so painful: everything on the machine was entangled with everything else.

A container is the same kind of program with three things added:

  • Blinkers: namespaces. The kernel gives it its own view of process IDs (it sees itself as process 1 and nothing else), mounts, network interfaces, host name and, optionally, user IDs. Nothing is copied or emulated; the kernel filters what it shows.
  • A budget: a cgroup. The kernel counts the CPU, memory and number of processes the program and its children use, and enforces limits: throttling CPU above a quota, killing the process if memory exceeds a cap.
  • A suitcase: an image. A packaged set of files — its own /usr/lib, its own Python, its own configuration — that becomes its root file system, plus a small config that says which command to run.

A virtual machine does something quite different. A hypervisor — software such as KVM or Hyper-V that runs virtual computers — gives the VM virtual CPUs, virtual memory and virtual devices. Inside, a whole operating system boots: its own kernel, its own init system, its own daemons, and finally the application. The VM is not a process with blinkers; it is a separate computer that happens to be made of software.

Where the analogy breaks

Blinkers do not change the horse. A process in a container makes system calls straight into the same host kernel as every other container. If the kernel has a bug that a system call can trigger, a process in any container can trigger it. The VM's boundary is narrower: a guest can only talk to the hypervisor through virtual devices and a handful of hardware-assisted transitions. That one difference explains most of the trade-off: containers are cheaper and faster, VMs isolate more strongly.

The big picture in four moves

  1. An image is built once and stored in a registry. It is a list of file archives (layers) plus a config, each named by a SHA-256 digest of its bytes.
  2. On a host, a chain of programs — docker → dockerd → containerd → a shim → runc — pulls the image, unpacks it and prepares a bundle: a root directory plus a JSON description of the process to run.
  3. runc asks the kernel for new namespaces, places the process in a cgroup, switches its root to the unpacked image, drops privileges and executes the program. Then runc exits.
  4. What is left is a normal process tree on the host, limited and blinkered. Kubernetes runs exactly the same thing, except that its node agent, the kubelet, talks to containerd directly.

Everything else in this lesson fills in those four moves.

1. What a plain process shares

Start from what a container takes away. A process is a running program: the kernel gives it an address space (its own memory), a set of open file descriptors and a numeric process ID (PID). To do anything outside its own memory — read a file, open a socket, start another program — it makes a system call, a controlled jump into the kernel (os1). The kernel is the one piece of software shared by every process on the machine.

Without containers, every process on a host sees the same global resources:

  • the same process table: ps aux lists every process, and a process with enough privilege can signal any of them;
  • the same file system tree: /usr/lib/libssl.so.3 is the same file for everyone, which is how one package upgrade broke two services in the opening story;
  • the same network stack: one set of interfaces and IP addresses, one port 8080 that only one process can bind;
  • the same host name, the same user IDs, the same shared-memory and message-queue namespace;
  • and no limit on CPU or memory except the machine's size.

There are two classic ways to separate workloads. One builds a second machine in software — the virtual machine. The other keeps one machine but gives each process its own copy of those global resources and a budget — the container. Look at each in turn.

2. How a virtual machine separates workloads

A virtual machine is a computer implemented by a hypervisor. Modern CPUs have hardware virtualisation (Intel VT-x, AMD-V, Arm's virtualisation extensions): a mode in which a guest operating system runs its own kernel directly on the CPU at near-native speed, but certain sensitive actions — touching a device, changing page tables in certain ways, some privileged instructions — trap out to the hypervisor, which emulates them. Memory is virtualised a second time: the guest thinks it owns physical addresses 0 to 4 GiB, and the hardware translates those to wherever the host actually placed them.

Two families of hypervisor exist. A type 1 hypervisor runs directly on the hardware (VMware ESXi, Xen, Hyper-V). A type 2 runs as a program on a normal operating system (VirtualBox). Linux's KVM is in between: a kernel module that turns the Linux kernel itself into a hypervisor, with a user-space program (QEMU, or a minimal one like Firecracker) supplying the virtual devices. Every major cloud's VMs run on KVM-derived or similar hypervisors.

What a VM costs, concretely:

  • Boot time. The guest runs firmware, a bootloader, its kernel and an init system before the application starts: typically 10-60 seconds for a general-purpose cloud VM. Firecracker, which strips the device model down to a handful of virtio devices, boots a minimal Linux guest in under 125 ms.
  • Memory. Each guest has its own kernel, page cache, and daemons. A general-purpose VM easily spends a few hundred megabytes before the app; Firecracker's own overhead is under 5 MiB per VM, but the guest kernel still needs memory on top.
  • Disk. A VM image is a whole disk: partition table, boot files, a full distribution, usually gigabytes.

What a VM buys: a narrow boundary. A guest process that wants to attack the host must first compromise its own guest kernel, then escape through the hypervisor's small interface. That is why public clouds put customers in VMs, not just in containers.

3. How a container separates workloads

A container keeps one kernel and removes the sharing listed in section 1, piece by piece. os13 covers each kernel feature in depth; here is how they combine into "a container", in the order a runtime applies them.

  1. New namespaces. The runtime creates the process with the clone() system call and flags such as CLONE_NEWPID, CLONE_NEWNS (mounts), CLONE_NEWNET, CLONE_NEWUTS (host name), CLONE_NEWIPC and optionally CLONE_NEWUSER and CLONE_NEWCGROUP. The new process sees itself as PID 1, an empty network stack with only a loopback interface, and a private copy of the mount table.
  2. A cgroup. The runtime creates a directory in the cgroup v2 tree (for example /sys/fs/cgroup/system.slice/docker-<id>.scope/), writes limits into files such as memory.max, cpu.max and pids.max, and writes the process's PID into cgroup.procs. From then on the process and all its children are counted and limited.
  3. A root file system. The image layers, already unpacked on disk, are stacked with OverlayFS under a fresh writable directory. Inside the new mount namespace the runtime mounts that overlay, mounts fresh /proc, /dev and /sys, then calls pivot_root to make the overlay the process's / and detaches the old root. The process can no longer name any host file that was not explicitly mounted in.
  4. Less privilege. It drops Linux capabilities down to a short default list (Docker keeps 14, such as CAP_CHOWN and CAP_NET_BIND_SERVICE, and drops e.g. CAP_SYS_ADMIN), sets no_new_privs, installs a seccomp filter that blocks dangerous system calls, applies an AppArmor or SELinux profile if configured, and switches to the configured user.
  5. Exec. Finally it calls execve() on the program named in the image config. The runtime's own code is replaced by the application. From the kernel's point of view, the result is just a process in some namespaces and a cgroup.

That is the most important sentence in this lesson: there is no "container" object in the Linux kernel. The kernel knows processes, namespaces and cgroups. "Container" is the name user-space tools give to one particular combination, and the container ID is a label the runtime invented. You can see this on any Docker host: ps -ef shows the nginx processes of every container, with ordinary host PIDs, and cat /proc/<pid>/cgroup shows which container's cgroup each belongs to.

What a container costs: almost nothing beyond the process itself. Creating namespaces and a cgroup takes milliseconds. There is no second kernel, no boot, no daemons. Memory is just the processes' own memory, and identical image files are shared on disk and in the page cache between all containers that use them. A server that held twenty VMs can often hold hundreds of containers.

What a container gives up: a narrow boundary. Every container talks to the full host kernel through roughly 300-400 system calls. seccomp and capabilities shrink that surface, but a kernel vulnerability reachable through an allowed system call is a way out. Section 9 returns to this.

4. What is inside an image

"Image" sounds like a disk image. It is not. The OCI image format — published by the Open Container Initiative, the industry body Docker and others formed in 2015 so that images and runtimes would interoperate — defines an image as a handful of JSON documents and archives, each stored as a blob (a file) named by its digest: sha256: followed by the SHA-256 hash of its exact bytes.

  • A layer is a tar archive (usually gzip- or zstd-compressed) of the files one build step added or changed. Deleted files are recorded as special "whiteout" entries. k8s2 is all about layers.
  • The config is a JSON document: the CPU architecture and OS, the default command (Entrypoint, Cmd), environment variables, working directory, user, exposed ports, labels, the build history, and the list of diff_ids — digests of each layer's uncompressed tar, used to verify the unpacked content.
  • The manifest is a JSON document that ties it together: the config's digest and size, and the ordered list of layer digests (of the compressed bytes, as stored in the registry) and sizes.
  • An image index (Docker calls its older equivalent a "manifest list") lists several manifests, one per platform such as linux/amd64 or linux/arm64. A tag like nginx:1.27 usually points at an index, so the same name works on an Intel server and an Arm laptop.

Here is the shape of the manifest for one platform of an nginx image (digests shortened, sizes rounded from a real pull; they change with every release):

{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "digest": "sha256:9bea9f2796e2…", "size": 8582
  },
  "layers": [
    { "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:af302e5c37e9…", "size": 28227259 },
    { "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:207b812743af…", "size": 43944212 },
    … five more small layers …
  ]
}

The first layer, about 28 MB compressed, is the Debian base; the second is nginx and its libraries; the rest are small configuration files and the entrypoint scripts. The config would show "Entrypoint": ["/docker-entrypoint.sh"], "Cmd": ["nginx", "-g", "daemon off;"], "ExposedPorts": {"80/tcp": {}} and "StopSignal": "SIGQUIT".

Two properties follow from naming everything by digest. Content is verifiable: after downloading a blob, the client hashes it and rejects it if the hash differs. And content is shareable: if two images use the same Debian layer, it has the same digest, so it is downloaded and stored once. Note what is absent: no kernel, no bootloader, no partition table. An image is a user space and an instruction for what to run in it.

5. The runtime stack: from docker to runc

Several programs sit between you and the kernel, and interviewers like to ask why. The OCI runtime specification defines the lowest level. A runtime receives a bundle: a directory containing rootfs/ (the root file system) and config.json (the process to run, its arguments, environment, user, the namespaces to create, the mounts, cgroup limits, capabilities and seccomp profile). The spec defines a lifecycle with states creating, created, running and stopped, and operations create, start, kill, delete and state.

runc is the reference implementation. It reads config.json, makes the system calls from section 3, and leaves the process waiting just before execve ("created"); runc start lets it exec ("running"). Then runc itself exits. It is a tool, not a daemon. Alternatives implement the same spec: crun (written in C, faster and smaller), runsc (gVisor's sandbox), and Kata Containers' runtime (a lightweight VM per pod).

Above runc, something must manage images, keep track of containers and survive restarts. That is containerd, a daemon that stores image content, unpacks layers into snapshots (prepared directories, usually overlay-based), creates bundles and starts containers. For each container it launches a shim, containerd-shim-runc-v2. The shim calls runc, then stays alive as the container process's parent: it holds the process's standard input and output, waits for it to exit and records the exit code. Because of the shim, containerd (and dockerd) can be restarted or upgraded while containers keep running.

Above containerd sits dockerd, the Docker daemon. It adds what developers want: docker build (via BuildKit), networks, volumes, port publishing, Compose support, and the Docker Engine API, a REST API on a Unix socket (/var/run/docker.sock) that the docker CLI calls. Since Docker Engine 29 (November 2025), fresh installations also store images in containerd's image store by default rather than Docker's older storage drivers.

Kubernetes uses a different front door. Its node agent, the kubelet, speaks the Container Runtime Interface (CRI), a gRPC API with calls like RunPodSandbox, PullImage, CreateContainer and StartContainer. containerd implements the CRI through a built-in plugin, and CRI-O is a runtime built only for it. Docker never implemented the CRI, which is the story told in the prod section.

6. docker run, step by step

Now trace one command on a fresh Linux host running Docker Engine with the containerd image store and cgroup v2:

docker run -d --name web -p 8080:80 --memory 256m --cpus 0.5 nginx:1.27
  1. CLI to daemon. The CLI calls the Engine API on /var/run/docker.sock: create a container with this config; if the daemon replies that the image is missing, the CLI asks it to pull, then creates, then starts.
  2. Resolve the name. nginx:1.27 is short for docker.io/library/nginx:1.27: registry Docker Hub, repository library/nginx (official images live under library/), tag 1.27.
  3. Authenticate. Docker Hub's registry (registry-1.docker.io) answers the first request with 401 and a WWW-Authenticate header naming a token service. The client fetches an anonymous bearer token for repository:library/nginx:pull and retries. (Anonymous pulls are rate-limited, a classic CI failure.)
  4. Fetch the index. GET /v2/library/nginx/manifests/1.27 with an Accept header listing OCI and Docker index and manifest types. The registry returns the index; the client picks the entry whose platform is linux/amd64 (on this host) and notes its manifest digest.
  5. Fetch the manifest and config by digest: GET /v2/library/nginx/manifests/sha256:…, then GET /v2/library/nginx/blobs/sha256:9bea… for the config.
  6. Fetch the layers, several in parallel, from /v2/library/nginx/blobs/<digest> (the registry often redirects to a CDN). Each blob's SHA-256 is checked as it streams in; a mismatch aborts the pull. Layers already present locally, by digest, are skipped — on a host that already has a Debian-based image, the 28 MB base layer is not downloaded again.
  7. Unpack. containerd decompresses each layer into a snapshot directory, in order, each one a child of the previous, and checks each uncompressed tar against the config's diff_ids.
  8. Create the container. A new snapshot — empty, writable — is prepared on top of the image's top layer. The overlay mount that will become the root looks like lowerdir=L7:L6:…:L1, upperdir=<new>, workdir=….
  9. Build the runtime config. dockerd merges the image config with the flags into an OCI config.json: args = ["/docker-entrypoint.sh", "nginx", "-g", "daemon off;"] (entrypoint followed by cmd), environment from the image, namespaces pid, ipc, uts, mount, network, cgroup, the default capability list and seccomp profile, mounts for /proc, /dev, /sys and Docker-generated /etc/hosts, /etc/hostname and /etc/resolv.conf, and resources memory.limit = 268435456 (256 × 1,048,576) and CPU quota 50,000 µs per 100,000 µs period (--cpus 0.5).
  10. Network. Docker's bridge driver creates a veth pair — two virtual Ethernet interfaces joined like a cable. One end is attached to the docker0 bridge on the host; the other is moved into the container's network namespace and renamed eth0, with an address from the bridge's subnet, say 172.17.0.2/16, and a default route via 172.17.0.1. For -p 8080:80, Docker adds NAT rules so traffic to the host's port 8080 is rewritten to 172.17.0.2:80. k8s4 traces this packet by packet.
  11. Start. containerd starts a shim; the shim runs runc create. runc clones a child in the new namespaces, creates the cgroup /sys/fs/cgroup/system.slice/docker-<id>.scope/ and writes memory.max = 268435456 and cpu.max = 50000 100000, mounts the overlay and pivots root, mounts /proc and friends, drops capabilities, sets no_new_privs, installs seccomp, and waits. runc start releases it: the child calls execve("/docker-entrypoint.sh", …).
  12. Running. runc exits. The entrypoint script prints a few configuration lines, then execs nginx, which replaces the shell as PID 1 in the container (host PID, say, 41237). nginx forks its worker processes. The CLI prints the container ID and returns, because of -d.

A second docker run of the same image skips steps 3-7 entirely and completes in well under a second. That asymmetry drives a lot of production engineering: image size, layer ordering, pre-pulling and registry mirrors all exist to make step 6 cheaper (k8s2, k8s3, k8s14).

7. PID 1 and stopping a container

The first process in a PID namespace is PID 1, and Linux treats it specially in two ways (os2). First, the kernel does not apply default signal actions to it: a normal process that receives SIGTERM with no handler dies, but PID 1 with no handler simply ignores it. Second, orphaned processes in the namespace are re-parented to PID 1, which must wait() for them or they remain as zombies.

docker stop sends the image's stop signal (SIGTERM unless the image sets STOPSIGNAL, as nginx does with SIGQUIT for a graceful drain) and waits 10 seconds by default, then sends SIGKILL, which cannot be ignored. Kubernetes does the same with a 30-second default grace period. Three common mistakes turn this into a slow, unclean stop:

  • Shell form. A Dockerfile line CMD python app.py (shell form) runs /bin/sh -c "python app.py". The shell is PID 1, Python is its child, and most shells do not forward SIGTERM. Exec form, CMD ["python", "app.py"], makes Python PID 1.
  • No handler. A program that never installs a SIGTERM handler is not stopped by it when it is PID 1. Python, for example, installs no SIGTERM handler by default; as PID 1 it ignores the signal.
  • No reaping. An app that spawns subprocesses and does not wait for grandchildren accumulates zombies. docker run --init (or tini as the entrypoint) inserts a tiny init that forwards signals and reaps.

Every one of these shows up as "docker stop takes 10 seconds" or "pods take 30 seconds to terminate and drop requests", and every one is explained only by the container-is-a-process model.

8. Architectures and operating systems

Because a container uses the host kernel, two compatibility rules follow, and both surprise people with the VM model in their heads.

The CPU architecture must match. Binaries in an image are machine code. An image built on an Apple-silicon Mac for linux/arm64 contains Arm instructions; an x86-64 server's kernel refuses to execute them with exec format error. Multi-platform images solve this with an index (section 4); build them with docker buildx build --platform linux/amd64,linux/arm64. Emulation through QEMU registered with the kernel's binfmt_misc feature can run foreign binaries, but slowly, which is fine for a build and painful in production.

The distribution does not need to match. An Alpine image runs on an Ubuntu host, because a distribution is mostly user-space files, and the Linux system-call interface is kept stable across kernel versions. The kernel version still matters at the edges: a program that needs a newer system call, a kernel module, or a particular cgroup feature works on one host and fails on another.

The operating system must match. Linux containers need a Linux kernel. Docker Desktop on macOS and Windows therefore runs a small Linux VM (on Windows, usually through WSL 2) and runs your containers inside it; the docker CLI on your desktop talks to dockerd inside the VM. Windows containers exist too, sharing a Windows kernel, and they cannot run Linux images.

9. How strong is the boundary?

The honest answer is "strong enough for code you trust, not for code you do not". Within one team's services, isolation protects against accidents: a bug in one service cannot read another's files or exhaust the node's memory. Against an attacker who controls the code, the boundary is the kernel's system-call interface, hardened by seccomp, capabilities, a non-root user and security modules. That has failed in practice through kernel bugs and runtime bugs (os13 describes two runc escapes).

So the industry layers sandboxes under the container interface rather than giving it up. gVisor implements most Linux system calls in a user-space kernel written in Go, so the container's calls go to gVisor and only a small, filtered set reaches the host. Kata Containers and Firecracker put each pod or function in a microVM with its own kernel, and still present an OCI runtime to containerd. Kubernetes lets a pod pick one through a RuntimeClass: runtimeClassName: gvisor in the pod spec, and the kubelet asks containerd to use the matching handler. The image, the API and the tooling stay the same; only the boundary changes.

Why the shim exists, and live restore

Early Docker made dockerd the parent of every container process, so upgrading or crashing the daemon killed every container on the host. The shim design breaks that link. containerd starts one containerd-shim-runc-v2 per container (or per pod in Kubernetes), and the shim becomes a subreaper — a process that adopts orphans in its subtree — so the container's PID 1 is its child. The shim keeps the container's stdio pipes or log files open and records the exit status. containerd talks to shims over a local socket and can reconnect after a restart. Docker's live-restore setting extends the same idea to dockerd. The trade-off is one small extra process per container, a few megabytes each, which is why the v2 shim can serve all containers of one Kubernetes pod.

Rootless containers and user namespaces

By default dockerd runs as root and container UID 0 is host UID 0, held back by dropped capabilities and seccomp. A user namespace maps container UIDs to a range of unprivileged host UIDs: root inside might be UID 100000 outside, with no power over host files. Rootless Docker and Podman run the whole daemon and runtime as an ordinary user this way; networking then goes through a user-space network stack (slirp4netns or pasta), which is slower, and some features such as binding ports below 1024 need extra configuration. Kubernetes added user-namespace support for pods (hostUsers: false), which became beta and on by default in 1.33 and needs a recent kernel and runtime. The security gain is large — a container escape lands as a nobody — and it is the main structural improvement to container isolation in years.

The CRI pod sandbox

A Kubernetes pod is several containers sharing one network namespace (and optionally IPC and PID). The CRI models this explicitly: RunPodSandbox creates the shared environment first, and containers are then created "into" it. In containerd the sandbox has traditionally been a tiny "pause" container whose only job is to hold the namespaces open while app containers come and go; it sleeps forever and reaps zombies. That is why crictl ps -a or ctr -n k8s.io containers ls on a node shows a pause container per pod. VM-based runtimes map the sandbox to a microVM instead, which is why the CRI calls it a sandbox rather than a container.

Snapshotters and lazy loading

containerd separates content (compressed blobs) from snapshots (unpacked file trees) through pluggable snapshotters: overlayfs by default, plus native, btrfs, zfs and devmapper. Because unpacking is a separate step, a snapshotter can change how it happens. Lazy-loading snapshotters — stargz/eStargz and AWS's SOCI (Seekable OCI) — use an index of file offsets within the compressed layer so they can mount the image almost immediately and fetch each file from the registry with an HTTP range request the first time it is read. Studies of container start-up found that most of an image is never read at start, so this cuts start time for large images dramatically, at the price of first-access latency and a dependency on the registry being reachable while the app runs.

What the kernel can and cannot tell you

Because "container" is a user-space idea, kernel-level tools need help to report on it. top shows host PIDs; the OOM killer logs a process name and a cgroup path; eBPF-based profilers see cgroup IDs. Mapping these back to containers and pods means reading /proc/PID/cgroup and asking the runtime which container owns that cgroup, which is what cAdvisor (built into the kubelet) and node agents do. The same gap explains why free and /proc/meminfo inside a container report the host's memory: those files are not namespaced, so the right numbers come from the cgroup files (os13).

Multi-architecture images in practice

With Arm servers (AWS Graviton, Ampere) now common and developers on Apple silicon, multi-platform images are the norm. BuildKit builds each platform either natively on matching builders or under QEMU emulation; compiled languages can cross-compile instead, which is much faster than emulating a compiler. The resulting index lists one manifest per platform, and pulling clients choose. Failure modes are subtle: a base image that lacks an arm64 variant, a native Python wheel with no arm64 build that then compiles from source for ten minutes, or a CI cache keyed without the platform that hands an amd64 layer to an arm64 build.

The case: Kubernetes removes dockershim (deprecated 1.20, removed 1.24)

When Kubernetes started, Docker was the only practical runtime, and the kubelet had Docker-specific code built in. As containerd and CRI-O matured, Kubernetes defined the CRI so any runtime could plug in. Docker never implemented it, so the project kept an adapter called dockershim inside the kubelet, translating CRI calls into Docker Engine API calls — which dockerd then translated into containerd calls. In December 2020 the Kubernetes blog post "Don't Panic: Kubernetes and Docker" announced that dockershim was deprecated in 1.20; it was removed in 1.24 (May 2022).

The technical point the post made is the one this lesson builds: images built with Docker are OCI images, and containerd and CRI-O run them unchanged, so for most users nothing changed. What did break were things that assumed the Docker daemon on nodes: CI systems that ran builds by mounting /var/run/docker.sock into pods ("Docker-out-of-Docker"), monitoring and security agents that queried the Docker API or parsed Docker's JSON log files, and runbooks that used docker ps on a node. The fixes were to build images with daemonless builders (BuildKit in rootless mode, Kaniko, Buildah), switch agents to the CRI or containerd, and use crictl for node debugging. The lesson for engineers: depend on the open interfaces (OCI images, CRI), not on one implementation's socket.

Characteristic failure modes

  • exec format error on start. Image built for the wrong CPU architecture. Check with docker image inspect --format '{{.Architecture}}'; publish multi-platform images.
  • Stops take exactly 10 s (Docker) or 30 s (Kubernetes). PID 1 ignores SIGTERM: shell-form CMD, no handler, or a wrapper script without exec. Fix with exec form, a handler, or --init/tini.
  • Disk full on the host. The json-file log driver keeps logs forever by default (max-size defaults to unlimited); chatty containers fill /var/lib/docker. Set max-size/max-file or use the local driver; on Kubernetes the kubelet rotates container logs (containerLogMaxSize, 10 MiB by default). Unused images and stopped containers pile up too: docker system df, then prune.
  • Zombie build-up. An app that shells out without reaping, as PID 1, fills the PID table until pids.max stops new forks. Add an init.
  • Pull failures. Docker Hub's anonymous rate limits, a private registry needing credentials, or a deleted tag. Use authenticated pulls, a mirror or pull-through cache, and pin digests (k8s5).
  • Memory looks wrong inside. free shows the host's memory; programs that size caches from it get OOM-killed by the cgroup. Read limits from /sys/fs/cgroup/memory.max; modern JVMs, Go and .NET do (Go's GOMAXPROCS respects CPU limits since Go 1.25).

What to look at on a host

Map a container to kernel objects: docker inspect -f '{{.State.Pid}}' web gives the host PID; ls -l /proc/<pid>/ns shows its namespaces; cat /proc/<pid>/cgroup its cgroup; that cgroup's memory.current, memory.events and cpu.stat (look at nr_throttled) show usage, OOM kills and throttling. nsenter -t <pid> -n ss -tlnp runs a host tool inside the container's network namespace, useful when the image has no shell. On Kubernetes nodes the same work is done with crictl ps, crictl inspect and crictl logs.

Knobs worth knowing

Log driver and rotation; --init; --stop-timeout and image STOPSIGNAL; default runtime (runc vs crun) and extra runtimes for sandboxes; live-restore on Docker hosts so daemon upgrades do not stop containers; the cgroup driver (systemd is recommended with cgroup v2 and is what the kubelet and runtime must agree on).

  4. Build an OCI image layout by hand (runs here). Save as oci_by_hand.py: 
    import gzip, hashlib, io, json, pathlib, tarfile
out = pathlib.Path("oci-demo"); blobs = out / "blobs" / "sha256"
blobs.mkdir(parents=True, exist_ok=True)
def put(data):
    d = hashlib.sha256(data).hexdigest(); (blobs / d).write_bytes(data)
    return "sha256:" + d, len(data)
buf = io.BytesIO()
with tarfile.open(fileobj=buf, mode="w") as tar:
    body = b"print('hello from a layer')\n"
    info = tarfile.TarInfo("app/hello.py"); info.size = len(body); info.mtime = 0
    tar.addfile(info, io.BytesIO(body))
raw = buf.getvalue()
diff_id = "sha256:" + hashlib.sha256(raw).hexdigest()   # uncompressed
layer, lsize = put(gzip.compress(raw, mtime=0))          # compressed
config = {"architecture": "amd64", "os": "linux",
          "config": {"Cmd": ["python3", "/app/hello.py"]},
          "rootfs": {"type": "layers", "diff_ids": [diff_id]}}
cfg, csize = put(json.dumps(config).encode())
manifest = {"schemaVersion": 2, "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {"mediaType": "application/vnd.oci.image.config.v1+json", "digest": cfg, "size": csize},
  "layers": [{"mediaType": "application/vnd.oci.image.layer.v1.tar+gzip", "digest": layer, "size": lsize}]}
m, msize = put(json.dumps(manifest).encode())
(out / "oci-layout").write_text('{"imageLayoutVersion": "1.0.0"}')
(out / "index.json").write_text(json.dumps({"schemaVersion": 2, "manifests": [
  {"mediaType": "application/vnd.oci.image.manifest.v1+json", "digest": m, "size": msize}]}, indent=2))
print("diff_id", diff_id, "\nlayer  ", layer, "\nconfig ", cfg, "\nmanifest", m)
    Run it twice: the digests are identical, because the bytes are (mtime fixed at 0). Change one character of body and every digest up the chain changes. That is content addressing. With Docker installed, skopeo inspect oci:oci-demo reads this directory as an image.
Diagnose: the deploy that takes 30 seconds per pod

A team moves a Python Flask service from VMs to Kubernetes. Every rolling deploy takes several minutes, and during it users see a burst of connection errors. Pod events show each old pod in Terminating for exactly 30 seconds. The Dockerfile ends with CMD gunicorn -w 4 app:app. What is happening, and what do you change?

Answer

The CMD is in shell form, so the container's PID 1 is /bin/sh -c "gunicorn …", and gunicorn is its child. When Kubernetes deletes a pod it sends SIGTERM to PID 1. The shell, as PID 1, has no default action for SIGTERM and does not forward it, so gunicorn never hears it. After the 30-second grace period the kubelet sends SIGKILL to everything, which cuts off in-flight requests — those are the errors. Meanwhile each old pod holds its slot for 30 s, so the rollout crawls.

Fix: use exec form, CMD ["gunicorn", "-w", "4", "app:app"], so gunicorn is PID 1 and receives SIGTERM; gunicorn treats it as a graceful shutdown, finishing in-flight requests. If the image needs a wrapper script, end it with exec gunicorn …. Add a short preStop sleep so the pod leaves the Service endpoints before shutdown begins (sc15), and set terminationGracePeriodSeconds above the longest request. Verify by watching a deploy: pods should terminate in a few seconds with no errors.

Estimate: VMs or containers for 200 small services

A platform runs 200 internal services, each needing about 150 MB of memory and a fraction of a core. Compare the memory cost of one VM per service against containers on shared hosts.

Answer

With a VM each, assume roughly 300 MB per guest for its kernel, page cache and system daemons on top of 150 MB of app: 200 × 450 MB ≈ 90 GB, two-thirds of it overhead, plus 200 boot sequences on every rollout and 200 operating systems to patch. With containers, the overhead per service is a shim of a few megabytes and shared image layers: 200 × ~155 MB ≈ 31 GB. Containers save roughly 60 GB and start in seconds. The VM option only wins if the services are mutually untrusted, in which case microVMs (tens of megabytes each) are the middle ground.
