Every pod in Kubernetes makes two promises about resources and gets two different kinds of behaviour in return, and the gap between what people expect and what actually happens is one of the richest sources of production surprises.

A latency-sensitive API has a CPU limit of one core and uses, on average, 0.4 cores. Its p99 latency is three times what it was on VMs. Nothing is overloaded; the dashboards show plenty of idle CPU on the node. The cause is a scheduling mechanism in the Linux kernel that pauses the container for most of every 100-millisecond window as soon as its threads have spent their quota, which a multi-threaded server can do in a fraction of the window. A training job with a 32 GiB memory limit, whose tensors take 20 GiB, is killed at a random step with OOMKilled; the missing memory turns out to be data-loader workers and shared memory, which the kernel counts but the training code never sees. A cluster at 25% average utilisation cannot schedule a new pod, because what the scheduler adds up is requests, not usage, and the requests were copied from a template years ago. And in 2019 Grafana Labs lost writes to its hosted Prometheus service for 26 minutes when a new priority scheme let a freshly created workload evict production pods, whose replacements in turn evicted more production pods.

All of these come from a small set of rules: how requests feed the scheduler; how requests and limits are turned into cgroup settings on the node; how CPU throttling is computed; what happens when memory runs out inside one container versus across a whole node; and how the quality-of-service class, priorities and placement rules decide who wins when there is not enough to go round.

This lesson goes through those rules with real numbers. It starts with what a node offers (allocatable), then requests and limits and the exact cgroup files they become, works through CPU throttling with the CFS quota arithmetic, separates OOM kills from evictions, derives QoS classes and their OOM scores, and then turns to placement: node and pod affinity, topology spread, taints and tolerations, and priority with preemption.

Restaurant bookings, a meter and a bouncer

Think of a node as a restaurant. A request is a booking: "a table for four". The host seats parties by bookings, not by how much they will eat: a restaurant with every table booked is full, even if half the diners only order coffee. That is the scheduler: it fits pods onto nodes by adding up requests against the node's allocatable capacity.

Once seated, two different rules apply to the two main resources.

  • CPU is a meter on a shared kitchen. Booked tables get priority on the kitchen's time in proportion to their booking (cpu.weight); when the kitchen is quiet, anyone can order more. A CPU limit is a meter that cuts a table off once it has used its allowance for the current 100-millisecond window, until the next window starts (throttling). Nobody is thrown out; they just wait.
  • Memory is the size of the table. You cannot borrow a bit of someone else's table for a moment and give it back. A table that tries to spread beyond its memory limit has a diner thrown out on the spot (the kernel's OOM killer). And if the whole restaurant runs out of room, the manager asks some parties to leave (eviction), starting with those who booked nothing or are using far more than they booked.

How seriously a pod is protected follows from how it booked, its QoS class: Guaranteed (booked exactly what it will use, limits equal requests), Burstable (booked something, may use more), BestEffort (booked nothing). And who is seated first when tables are short, even at the cost of moving others out, is decided by priority.

Placement is a separate question from size

Resources answer "does this pod fit on that node?". A second family of rules answers "is this pod allowed on that node, and which allowed node is best?". Nodes carry labels (zone, instance type, GPU model) and can carry taints, which repel any pod that does not explicitly tolerate them, like a "staff only" sign. Pods can require or prefer nodes by label (node affinity), require or prefer to be near or far from other pods (pod affinity and anti-affinity), and ask to be spread evenly across zones or nodes (topology spread). The scheduler applies all of these as filters and scores alongside the resource check. In the restaurant, these are the seating rules: the private room is only for parties who asked for it, two rival families must not sit together, and the regulars want one table on each floor.

Where the analogy breaks: a restaurant's meter would be measured per table per hour; the CPU meter runs per 100-millisecond window and counts every thread at once, so a party of eight diners can use a whole window's allowance in an eighth of the time and then sit idle for the rest. That arithmetic, not average usage, is what drives latency.

1. What a node offers: allocatable

A node's capacity is its hardware as the kubelet sees it: CPUs, memory, ephemeral storage, the number of pods it allows (110 by default), and extended resources such as GPUs (k8s14). Not all of it is offered to pods. The kubelet subtracts:

  • kube-reserved: CPU and memory for Kubernetes' own node daemons, the kubelet and container runtime;
  • system-reserved: for the operating system (systemd, sshd, the kernel's own usage);
  • the hard eviction threshold: memory the kubelet keeps free so it can act before the kernel runs out (memory.available<100Mi by default on Linux).

What remains is allocatable, and it is all the scheduler will ever hand out. A worked example for a node with 4 vCPUs and 16 GiB, with reservations of the kind managed node images set (the exact values vary by provider and node size):

2. Requests, limits and units

Each container may set, per resource, a request (what it needs and what is reserved for it) and a limit (the most it may use). CPU is measured in cores or millicores: 500m is half a CPU's time, 2 is two. Memory is in bytes with binary suffixes: 512Mi is 512 × 220 bytes (beware 512M, which is decimal and about 5% smaller). A pod's request is the sum of its containers' requests (plus init-container rules and any pod overhead).

resources:
  requests: { cpu: 500m, memory: 1Gi }
  limits:   { cpu: "1",  memory: 1Gi }

If a limit is set and the request is not, the request defaults to the limit. Namespaces can impose defaults and bounds with a LimitRange, and total budgets with a ResourceQuota.

The scheduler uses requests only. Its NodeResourcesFit filter (k8s6) admits a pod to a node if, for every resource, the sum of requests of pods already there plus this pod's request is at most allocatable. Actual usage plays no part. Two corollaries: requests far above usage waste money (nodes are "full" of reservations), and requests far below usage overpack nodes, so pods fight over real CPU and memory and node-level pressure follows.

The kubelet builds a cgroup hierarchy under /sys/fs/cgroup/kubepods.slice/, with a sub-tree per QoS class (Guaranteed pods directly under it, then kubepods-burstable.slice and kubepods-besteffort.slice), a cgroup per pod and one per container. For each container (os13 explains the files):

The CPU request travels a slightly odd path. The kubelet still computes cgroup v1-style shares — millicores × 1024 / 1000, so 500m gives 512 — and the OCI runtime converts shares to the cgroup v2 cpu.weight (range 1 to 10,000, default 100). For years that conversion was linear and mapped a full CPU request (1024 shares) to a weight of only 39, below the default 100 that host services get, quietly de-prioritising pods. Since January 2026 runc 1.3.2 and crun 1.23 use a new formula that passes through (2 → 1), (1024 → 100) and (262144 → 10000): a 1-CPU request now gets weight about 100, 500m about 59, 250m about 35. Weight only matters when CPUs are contended: an idle node lets any container run as much as its limit allows.

4. CPU throttling, worked

The CPU limit is enforced by CFS bandwidth control (os3): a group may consume at most quota microseconds of CPU time per period (100,000 µs by default), summed across all its threads on all CPUs. When the quota is used up, every thread in the group is throttled — not scheduled — until the next period starts.

Case 1: one thread, limit 500m (cpu.max = 50000 100000). A request needs 120 ms of CPU. Period 1: it runs for 50 ms, quota exhausted, throttled for 50 ms. Period 2: another 50 ms, throttled 50 ms. Period 3: the last 20 ms. Finished at 200 + 20 = 220 ms of wall time instead of 120 ms. Throttling added 100 ms.

Case 2: four threads, limit 1 CPU (100000 100000), on a node with idle cores. A request fans out to four worker threads, each needing 40 ms of CPU (160 ms total). Unthrottled, they would all finish in 40 ms of wall time on four cores. With the limit:

  1. 0-25 ms: four threads run in parallel, consuming 4 × 25 = 100 ms of quota. Each has 15 ms of work left.
  2. 25-100 ms: quota exhausted; the whole container is throttled for 75 ms.
  3. 100-115 ms: new period, quota refilled; the four threads finish their remaining 15 ms each (60 ms of quota).

The request completes at 115 ms instead of 40 ms. The container's average CPU over the surrounding second might be 0.4 cores, which is why dashboards of average usage never show the problem. The evidence is in the cgroup's cpu.stat: nr_periods, nr_throttled (periods in which the group was throttled) and throttled_usec; in Prometheus, cAdvisor's container_cpu_cfs_throttled_periods_total divided by container_cpu_cfs_periods_total gives the fraction of throttled periods, and anything above a few percent on a latency-sensitive service deserves a look.

What teams do about it: set CPU requests accurately from load tests (they buy weight under contention), and leave CPU limits off or generous for latency-sensitive services, relying on requests and namespace quotas for fairness; or keep limits but size thread pools, GOMAXPROCS and worker counts to the limit so the process cannot burst far beyond it (Go 1.25+, recent JVMs and .NET read the limit automatically, k8s3). Batch work, where throughput matters more than latency, tolerates throttling well.

5. Memory: OOM kills and evictions

Memory has two different failure paths, and confusing them wastes hours.

Container over its own limit: OOMKilled. memory.max caps everything the cgroup charges: anonymous memory (heaps), page cache from files the container read or wrote, tmpfs and /dev/shm (including memory-backed emptyDirs), and some kernel memory. When usage approaches the limit, the kernel first reclaims what it can (clean page cache) within the cgroup. If that is not enough, the kernel's OOM killer kills a process inside the cgroup — typically the largest. The container exits with code 137 (128 + 9, SIGKILL), its last state shows reason: OOMKilled, and the kubelet restarts it per its restart policy; repeated kills become CrashLoopBackOff (k8s13). The pod stays on the node. Nothing above the container was short of memory.

Node short of memory: eviction. If the node as a whole runs low — because pods use more than they requested (allowed when limits are above requests, or absent) — the kubelet watches memory.available and, when it falls below the eviction threshold, evicts pods to reclaim memory. It ranks candidates by: first, whether the pod's usage exceeds its request; then by PriorityClass; then by how far usage exceeds the request. Evicted pods are terminated, marked Failed with reason: Evicted, and replaced by their controllers on other nodes. The node gets the MemoryPressure condition and a NoSchedule taint until it recovers. (Disk and inode pressure work the same way with nodefs and imagefs signals; the kubelet first tries garbage-collecting images and dead containers.)

And if memory vanishes faster than the kubelet's polling, the kernel's node-wide OOM killer acts first. It scores processes by memory use plus oom_score_adj, which the kubelet sets by QoS class:

QoS classoom_score_adj
Guaranteed−997 (almost never chosen)
Burstablemin(max(2, 1000 − 1000 × memoryRequest / nodeMemoryCapacity), 999)

For a Burstable container requesting 1 GiB on a 16 GiB node: 1000 − 1000 × 1/16 = 937.5, so about 937. Requesting 8 GiB: 500. The bigger the request relative to the node, the more protected the container — the kernel's version of "you booked it, you keep it". The kubelet and runtime themselves run at −999, so they survive.

A practical rule follows: for memory, set the request equal to the limit for anything important. The pod then cannot use more than it reserved (so it cannot push the node into pressure), it is first in line for protection under eviction, and its OOM behaviour is predictable. If CPU requests also equal limits, the pod is Guaranteed.

6. QoS classes

The class is computed from the spec and written to status.qosClass; you cannot set it directly.

  • Guaranteed: every container (sidecars and init containers included) has CPU and memory limits, and requests equal to them.
  • BestEffort: no container has any CPU or memory request or limit.
  • Burstable: everything else, including "memory request = limit but no CPU limit".

Besides eviction and OOM order, the class decides the cgroup sub-tree, and with the kubelet's static CPU manager policy, Guaranteed pods requesting whole CPUs (for example cpu: "4") get exclusive cores pinned to them via cpusets, removing interference from other pods — used for latency-critical, NUMA-sensitive and some inference workloads.

7. Changing resources without restarting

Historically, changing a pod's requests or limits meant replacing the pod. In-place resize, stable since 1.35, lets you patch a running pod's CPU and memory through its resize subresource (kubectl patch pod web --subresource resize -p '{"spec":{"containers":[{"name":"web","resources":{"requests":{"cpu":"800m"},"limits":{"cpu":"800m"}}}]}}'). The kubelet checks the node can fit the new requests, updates the cgroup files and reports progress in pod conditions (PodResizePending if the node lacks room, PodResizeInProgress while applying). Each container's resizePolicy says per resource whether a change needs a restart: CPU is usually NotRequired; memory is often RestartContainer, because many runtimes (a JVM with a fixed heap) cannot use more memory without restarting, and shrinking a limit below current usage is unsafe. Vertical autoscaling (k8s11) builds on this.

8. Placement: node selectors and node affinity

Resources decide whether a pod fits on a node; placement rules decide whether it is allowed or preferred there. All work through labels on nodes — set by the cloud (topology.kubernetes.io/zone=us-east-1b, node.kubernetes.io/instance-type=g6.xlarge), by node pools or by you.

  • nodeSelector: a simple map of required labels: nodeSelector: {disktype: ssd}.
  • Node affinity: expressive rules with operators (In, NotIn, Exists, Gt…). requiredDuringSchedulingIgnoredDuringExecution is a hard filter; preferredDuringSchedulingIgnoredDuringExecution adds weighted score. "IgnoredDuringExecution" means a running pod is not moved if labels change later.
affinity:
  nodeAffinity:

    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 50
      preference: { matchExpressions: [ { key: karpenter.sh/capacity-type, operator: In, values: [spot] } ] }

9. Placement relative to other pods: affinity, anti-affinity and topology spread

Pod affinity places a pod near pods with certain labels ("same node as the cache"); pod anti-affinity keeps it away ("not on a node that already runs a replica of me"). Both take a topologyKey that defines "near": kubernetes.io/hostname for the node, topology.kubernetes.io/zone for the zone. Hard anti-affinity per node with ten replicas needs ten nodes, and inter-pod affinity is expensive for the scheduler to evaluate in big clusters.

Topology spread constraints are the more flexible tool for spreading replicas. A constraint says: among pods matching this selector, the difference in count between the most and least populated domains of this topology may be at most maxSkew.

topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector: { matchLabels: { app: api } }

A worked placement: three zones currently hold api replicas 2, 2, 1. The next replica may only go to zone c (2, 2, 2): putting it in a or b would make 3, 2, 1, a skew of 2. The one after may go anywhere (3, 2, 2 has skew 1). If zone c has no room, DoNotSchedule keeps the pod Pending rather than unbalancing (and may trigger the cluster autoscaler to add a node there, k8s11); ScheduleAnyway turns the rule into a scoring preference. Spreading across zones is what lets a service survive a zone outage with capacity left.

10. Taints and tolerations

Affinity is the pod choosing nodes. A taint is the node refusing pods: a key, an optional value, and an effect.

  • NoSchedule: new pods without a matching toleration are not scheduled here.
  • PreferNoSchedule: the scheduler avoids the node if it can.
  • NoExecute: also evicts running pods that do not tolerate it, optionally after tolerationSeconds.

A pod's toleration matches a taint (by key, value or Exists, and effect) and permits the pod onto that node; it does not attract it. Uses:

  • Dedicated pools: GPU nodes tainted nvidia.com/gpu=present:NoSchedule keep ordinary pods off expensive hardware; GPU pods tolerate it and request nvidia.com/gpu, which only those nodes advertise (k8s14).
  • Control-plane isolation: control-plane nodes carry node-role.kubernetes.io/control-plane:NoSchedule.
  • Node problems: the node lifecycle controller adds node.kubernetes.io/not-ready and unreachable with NoExecute (k8s6), and the kubelet's pressure conditions become NoSchedule taints. Every pod gets default tolerations of 300 seconds for not-ready and unreachable, which is the five-minute eviction delay; a latency-critical service can tolerate them for 30 seconds instead to be rescheduled sooner.
  • Spot capacity: autoscalers often taint spot nodes so only interruption-tolerant workloads land there.

11. Priority and preemption

A PriorityClass is a cluster object with a name and an integer value; pods reference it with priorityClassName. Two built-ins, system-cluster-critical and system-node-critical, have very high values and protect components like CoreDNS and CNI pods. One class may be marked globalDefault, applied to pods that name none; without one, pods get priority 0.

Priority does two things. The scheduling queue orders pending pods by priority, so important pods are considered first. And when a pod cannot be scheduled, the scheduler's PostFilter step tries preemption: find a node where evicting some lower-priority pods would let this pod fit, choose victims to minimise disruption (lowest priority first, respecting PodDisruptionBudgets if possible, though not guaranteed), evict them gracefully, and nominate the node for the pending pod. The victims' controllers recreate them, and they schedule wherever there is room — or preempt something of even lower priority. A pod with preemptionPolicy: Never is prioritised in the queue but never evicts others; useful for important batch work that should wait rather than disrupt.

Priority is powerful and dangerous in exactly one way: it creates chains. The prod section shows a chain running through a production service.

12. Right-sizing requests, worked

Requests should come from measurement, not templates. Take a service with 20 replicas, each requesting cpu: 2 and memory: 4Gi, copied from another team. A week of per-container metrics shows CPU usage with a median of 0.25 cores, a 95th percentile of 0.6 and short peaks of 1.4; memory working set steady at 900 MiB with a maximum of 1.3 GiB during a nightly report. A reasonable sizing: CPU request 0.6 (covering the p95, so the pod gets its share under contention) and no CPU limit, or a limit of 2 to cap runaway loops; memory request and limit 1.75Gi (the maximum plus about a third for headroom and growth), keeping memory predictable. Per replica, reserved CPU falls from 2 to 0.6 cores and memory from 4 to 1.75 GiB. Across 20 replicas that releases 28 cores and 45 GiB of reservations — roughly three or four nodes of the size in section 1 — which the node autoscaler can then remove (k8s11).

Three cautions. Measure over a period that includes the real peaks (month-end, the nightly job); a quiet week gives requests that fail on a busy one. Re-check after changes in traffic or code; the Vertical Pod Autoscaler in recommendation mode does this continuously. And roll changes out like any other change: lowering a memory limit below a rare peak turns a healthy service into one that is OOM-killed once a month, which is much harder to diagnose than paying for a little headroom.

Why limits above requests are an overcommit, and when that is fine

The sum of limits on a node may exceed its capacity; only requests must fit. That is deliberate overcommitment: most services spend most of their time below their peaks, so letting them burst into each other's unused headroom raises utilisation. For CPU the downside is graceful (contention shares CPU by weight). For memory it is not: if several Burstable pods burst at once, the node runs out, and the kubelet evicts or the kernel kills. Mature platforms therefore treat CPU and memory differently: generous or no CPU limits with accurate requests, and memory requests equal to limits for anything stateful or latency-critical, allowing memory overcommit only for tolerant workloads such as batch and development namespaces.

The non-linearity of the new weight formula

The 2026 shares-to-weight conversion is a quadratic in log space, chosen so that the minimum, default and maximum values line up between cgroup v1 and v2. A side effect is that weights are no longer proportional to requests: 512 shares map to about 59 and 1024 to about 100, a ratio of 0.59 rather than 0.5. Under full contention, a 500m pod therefore gets slightly more than half of what a 1-CPU pod gets. Kubernetes' guarantee that a container can use at least its request still holds in practice because nodes are packed by requests and requests sum to no more than allocatable; the change matters most for small requests (100m now maps to weight 17 instead of 4) and for pods competing with system services.

Memory accounting surprises

The cgroup charges page cache to the cgroup that first touched the page. A container that streams a 50 GB dataset through reads can fill its limit with cache; normally the kernel reclaims clean cache before OOM-killing, but dirty pages waiting for slow storage, or cache pinned by memory-mapping, can tip it over. Shared memory (/dev/shm, used by PyTorch data loaders) is charged too and cannot be reclaimed while files exist. memory.stat breaks the total into anon, file, shmem, kernel and more, and is the first file to read after an unexplained OOM kill. The kubelet's memory.available signal and the container_memory_working_set_bytes metric exclude inactive file cache, which is why they differ from memory.current.

Burst, quota periods and the 'CFS throttling bug'

For several years, Linux kernels throttled containers more than their quota required, because quota assigned to per-CPU run queues in slices was not returned promptly and expired; containers using far less than their limit were still throttled. The fix landed in Linux 5.4 (and was backported widely), and much of the folk wisdom "never set CPU limits" dates from that era. Even on fixed kernels the arithmetic of section 4 remains: parallelism inside one period burns quota fast. cgroup v2's cpu.max.burst lets a group accumulate unused quota up to a bound and spend it later, which smooths bursty services; Kubernetes does not expose it per container as of this writing, so it is set at the node or runtime level if at all.

Scheduler scoring and bin packing

The default scoring plugin prefers less allocated nodes (spreading load), which leaves fragmented free space across many nodes. For cost-sensitive clusters, the NodeResourcesFit plugin can score with MostAllocated or a RequestedToCapacityRatio curve to pack pods tightly, so autoscalers can remove empty nodes (k8s11). The cost of tight packing is less headroom for bursts and for rollouts' surge pods. Schedulers also do not move pods after placement: the descheduler project evicts pods that violate current policies or sit on underused nodes, so they can be rescheduled better, with PodDisruptionBudgets limiting the churn.

Requests as a contract with the autoscalers

Requests are read by more than the scheduler. The Horizontal Pod Autoscaler's CPU utilisation is usage divided by request, so an inflated request makes a busy service look idle and suppresses scaling; the Cluster Autoscaler and Karpenter add nodes based on the requests of pending pods; the Vertical Pod Autoscaler's whole job is to correct requests. A wrong request therefore misleads three control loops at once (k8s11), which is why right-sizing is a first-class platform task rather than a tidy-up.

Dynamic resource allocation

Requests and limits handle CPU, memory and simple counted devices. Devices with structure — GPUs that can be partitioned, network cards with attributes, accelerators that must be allocated together — use Dynamic Resource Allocation (DRA): ResourceClaims that pods reference, DeviceClasses with selectors on device attributes, and drivers that publish ResourceSlices describing each node's devices; the scheduler allocates matching devices as part of placement. k8s14 returns to it for GPUs.

Pod overhead and sandboxed runtimes

Pods that run under a sandboxed runtime such as Kata Containers or gVisor (k8s1) consume resources beyond their containers: a guest kernel, a VMM process, a user-space kernel. A RuntimeClass can declare this pod overhead (for example 128 MiB and 250m CPU), and the scheduler and kubelet add it to the pod's requests and cgroup limits automatically, so nodes are not overpacked by an invisible cost. It is a small field with a large effect on clusters that mix sandboxed and ordinary pods.

The case: Grafana Labs' pod-priority outage (July 2019)

Grafana Labs ran Cortex, a horizontally scalable Prometheus service, on Kubernetes. Cortex's ingesters are stateful, holding recent samples in memory, replicated three ways with quorum writes. Zero-downtime upgrades needed an extra ingester temporarily, so the team introduced priorities to let a new ingester preempt smaller stateless pods. On 18 July they deployed four PriorityClasses — critical, high, medium, low — with medium as the global default, high intended for ingesters and critical for monitoring. The production Cortex clusters had not yet been updated to give their ingesters high, so they had priority 0.

The next day an engineer created a new dedicated Cortex cluster for a large customer, without the new priorities in its configuration, so its pods got the default, medium. The Kubernetes cluster lacked room for it. The new ingesters, at medium, outranked the existing production ingesters at 0, so the scheduler preempted a production ingester. That ingester's ReplicaSet created a replacement — which, being new and naming no class, also got medium, and preempted another production ingester. The chain continued until all production ingesters had been preempted. With many ingesters leaving the hash ring at once, Cortex could not reach write quorum and writes failed. Alerts paged within four minutes; the team scaled up the cluster, ingesters flushed and rescheduled, and the outage lasted 26 minutes in total, including recovery of reverse proxies overloaded by a tenfold retry storm. No data was lost: ingesters flushed to long-term storage and clients' write-ahead logs replayed.

The mechanisms are all from this lesson: a globalDefault higher than existing pods; preemption choosing victims by priority; controllers recreating victims at the default priority; capacity short enough that preemption was the only path. The defences: never introduce a default above existing workloads' priority (or set the default to 0 and opt workloads in); roll out priorities to critical workloads before enabling preemption for others; use preemptionPolicy: Never for pods that should wait; keep headroom; and protect stateful sets with PodDisruptionBudgets, remembering that preemption honours them only on a best-effort basis.

Failure modes and symptoms

  • Latency spikes with low average CPU: CFS throttling. Check throttled periods; remove or raise CPU limits.
  • OOMKilled (exit 137): container over its own memory limit; read memory.stat, look for cache, shm, workers.
  • Evicted pods, node MemoryPressure: Burstable/BestEffort pods using far beyond requests; raise requests or make memory requests equal limits.
  • Pending: "Insufficient cpu" on an idle-looking cluster: requests, not usage, fill nodes. Right-size requests (VPA recommendations, k8s11).
  • Pending: "had untolerated taint": missing toleration, or toleration without the matching resource request or affinity.
  • Pods piled into one zone: no topology spread; a zone outage takes most replicas.
  • Unexpected preemptions: a priority class higher than you thought; check events for Preempted.

What to measure

Per workload: requests versus actual usage (CPU and working-set memory) over a week, throttled-period ratio, OOM kill count, restarts. Per node and cluster: allocatable versus requested versus used (the gap between requested and used is money), eviction counts, pending pods by reason, and preemption events. Tools: kubectl describe node, kubectl top, kube-state-metrics, cAdvisor metrics and the cgroup files themselves.

    if all(not c.get("req") and not c.get("lim") for c in containers): return "BestEffort"
    ok = all(c.get("lim", {}).get(r) is not None and c.get("req", c.get("lim", {})).get(r) == c["lim"][r]
             for c in containers for r in ("cpu", "mem"))
    return "Guaranteed" if ok else "Burstable"
def oom_adj(cls, mem_req, node_mem):
    return {"Guaranteed": -997, "BestEffort": 1000}.get(cls) or min(max(2, int(1000 - 1000 * mem_req / node_mem)), 999)
def weight(millicores):                      # kubelet shares -> new runtime formula
    shares = max(2, millicores * 1024 // 1000); L = math.log2(shares)
    return math.ceil(10 ** (L * L / 612 + 125 * L / 612 - 7 / 34))
def wall_ms(work_ms_per_thread, threads, limit_cpu, period=100):
    quota, left, t = limit_cpu * period, [work_ms_per_thread] * threads, 0.0
    while any(left):
        running = [i for i, w in enumerate(left) if w > 0]
        burn = min(quota / len(running), min(left[i] for i in running), period)
        for i in running: left[i] -= burn
        t += burn
        if any(left) and burn * len(running) >= quota - 1e-9: t = math.ceil(t / period) * period
    return round(t, 1)

Diagnose: p99 tripled after moving to Kubernetes

A Java service moved from VMs (8 vCPUs each) to Kubernetes with requests: {cpu: "1", memory: 4Gi}, limits: {cpu: "2", memory: 4Gi}, 12 replicas on 32-core nodes. Average CPU per pod is 0.7 cores; p50 latency is unchanged, but p99 rose from 120 ms to 380 ms. The JVM's thread pools were configured on the VMs with 64 request threads and ParallelGC. What is going on, how do you prove it, and what do you change?

Answer

CFS throttling. The limit gives each container 200 ms of CPU per 100 ms period. With 64 request threads and parallel GC threads, a burst of concurrent requests or a GC cycle can spend 200 ms of CPU in a few milliseconds of wall time across many of the node's 32 cores; the whole container is then frozen until the period ends. Average usage (0.7 cores) stays low, p50 requests rarely coincide with a burst, but tail requests do and wait up to tens of milliseconds per period, sometimes over several periods. GC pauses also stretch when GC threads are throttled.

Prove it: container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total for these pods (expect well above 10%), or cat /sys/fs/cgroup/cpu.stat inside a pod during load; correlate throttled seconds with p99 spikes. Also check what the JVM thinks it has: a modern JVM sizes GC threads from the CPU limit (2), but the hand-configured 64-thread pool ignores it.

Change: remove the CPU limit (or raise it well above the burst) and keep an accurate request — perhaps 1.5 CPUs from load tests — so scheduling and weight stay fair; size request threads to the real concurrency the CPU can serve; let GC threads follow the container's CPU count. Memory stays request = limit at 4Gi so the pod remains well protected (with no CPU limit it becomes Burstable, which is fine for eviction ranking as long as memory usage stays within request). Verify that throttled periods drop near zero and p99 returns toward 120 ms; watch node-level CPU contention, since unlimited pods now share by weight.
