A team's first Kubernetes service is five YAML files applied with kubectl apply -f from a laptop. Six months later they run twelve services in three environments. Each service has a Deployment, a Service, a ConfigMap, an HPA, a PodDisruptionBudget, an HTTPRoute and a ServiceAccount, and each environment needs slightly different replicas, resources, hostnames and image tags. Someone copies the staging directory to make production and edits it by hand. A fix to the readiness probe is made in staging and forgotten in production. A colleague scales a Deployment with kubectl scale during an incident and nobody remembers to put it back. A deploy is run from a laptop with an uncommitted change. Nobody can say for certain what is running in production or who changed it.

Three families of tools address this, at different levels. Helm turns manifests into parameterised templates packaged as versioned charts, installs them as releases with history and rollback, and is how most third-party software (databases, ingress controllers, monitoring stacks) is distributed. Kustomize, built into kubectl, keeps one plain set of manifests and applies declared patches to produce each environment's variant, without any templating. And GitOps — with agents such as Argo CD and Flux — changes who applies the manifests: instead of people or CI pushing to the cluster, an agent in the cluster pulls the desired state from Git, applies it, and keeps putting it back whenever the cluster drifts.

Each brings its own mechanics and its own sharp edges: template whitespace that silently produces wrong YAML; a rollback that does not roll back a database; config changes that never restart pods; an autoscaler and a GitOps agent fighting over the same field; and the uncomfortable fact that the components rendering your manifests can read a great deal. In 2022 a vulnerability in Argo CD's Helm rendering let any user who could create an Application read files outside their repository, including other applications' decrypted secrets.

This lesson renders a Helm chart by hand, line by line, follows a release through upgrade and rollback and what Helm 4 changed, builds Kustomize overlays, and then sets up the GitOps loop with Argo CD and Flux, including promotion, rollback, secrets and the failure modes that matter in production.

Forms, tracing paper and a librarian

Three analogies, one per tool. Helm is a form with blanks. The chart's templates are a standard contract with blanks for the name, the number of copies, the image; the values file fills the blanks; the result is a completed contract (a manifest) that Kubernetes understands. Helm also keeps a filed copy of every contract it has submitted for each installation, so it can resubmit an older one to undo a change.

Kustomize is tracing paper. You keep one clean drawing (the base: complete, valid manifests). For production you lay a sheet of tracing paper over it and draw only the differences — more replicas here, a bigger memory limit there, a different image tag. The final picture is the base with the overlay on top. Nothing in the base has blanks; you can read it as it is.

GitOps is a librarian with a catalogue. The catalogue (Git) says exactly which books should be on which shelves. The librarian (Argo CD or Flux) walks the shelves continuously, puts back anything missing, removes anything that should not be there, and re-shelves books that someone moved. If you want a change, you change the catalogue — through review — and the librarian makes the shelves match.

Why not just a script?

Before adopting any of this, teams often write a shell script that substitutes variables into YAML with sed or envsubst and pipes the result to kubectl apply. It works for a while, and its failure modes explain what the real tools add. A script has no memory of what it applied last time, so a resource removed from the files is never deleted from the cluster (Helm releases and GitOps pruning track that). It has no idea about Kubernetes structure, so replacing a value inside a list or merging two maps becomes fragile string manipulation (Kustomize's strategic merge and Helm's values merging understand the shapes). It cannot roll back to "what was running before" without someone reconstructing the inputs (Helm revisions and Git history record them). And it runs wherever it is run from, with whatever credentials that place has, so the cluster's state depends on whose laptop last ran it (GitOps moves the applying into the cluster). Each tool in this lesson is, in part, the hard-won answer to one of those problems.

The tools compose. Helm and Kustomize decide what the manifests are; GitOps decides how and when they reach the cluster. Argo CD and Flux both render Helm charts and Kustomize overlays as part of their loop.

Where the analogies break: a form, a tracing and a catalogue all describe the cluster's objects, not its data. Re-submitting an old contract, reverting an overlay or rolling back a catalogue entry restores manifests; it does not restore a database schema that the newer version migrated, or files a job wrote. Delivery tools manage desired state; data needs its own plan (swe9's expand-contract migrations, k8s9's snapshots and backups).

1. What packaging has to do

Look at what differs between environments for one service and what stays the same. The same: the container port, probes, labels and selectors, the Service, the security context, the shape of the HPA. Different: the image tag (dev runs today's build, production last week's), replicas and resources, hostnames on the HTTPRoute, a few configuration values, sometimes extra objects (a PodDisruptionBudget only in production). A packaging tool must let you express "the same, except…" without copying, make the result reviewable as ordinary manifests, and, ideally, make config changes roll pods. Helm and Kustomize take opposite approaches to the "except".

2. A Helm chart's anatomy

web/
  Chart.yaml          # apiVersion: v2, name: web, version: 1.4.0 (chart), appVersion: "2.7.1" (app)
  values.yaml         # defaults
  values.schema.json  # optional JSON Schema for values
  templates/
    _helpers.tpl      # named templates (not rendered on their own)
    deployment.yaml
    service.yaml
    configmap.yaml
    hpa.yaml
    NOTES.txt         # printed after install
  charts/             # dependencies (subcharts), declared in Chart.yaml

The chart's version is the package's version; appVersion is the version of the software inside, often used as the default image tag. Charts are distributed as .tgz archives in HTTP chart repositories or, increasingly, as OCI artefacts in the same registries as images (helm push web-1.4.0.tgz oci://ghcr.io/myorg/charts), where they can be signed like images (k8s5).

3. Rendering a template by hand

Templates use Go's text/template language extended with the Sprig function library. Here are the relevant pieces of the chart:

# values.yaml
replicaCount: 2
image:
  repository: ghcr.io/myorg/web
  tag: ""               # empty: fall back to appVersion
resources:
  requests: { cpu: 250m, memory: 256Mi }
config:
  LOG_LEVEL: info

# templates/_helpers.tpl
{{- define "web.fullname" -}}
{{- printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" -}}
{{- end -}}
{{- define "web.labels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}

# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "web.fullname" . }}
  labels:
    {{- include "web.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      {{- include "web.labels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "web.labels" . | nindent 8 }}
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
      - name: web
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
        {{- with .Values.resources }}
        resources:
          {{- toYaml . | nindent 10 }}
        {{- end }}

Now install it for production:

helm upgrade --install shop ./web -n prod -f values-prod.yaml --set image.tag=2.7.2

with values-prod.yaml containing replicaCount: 6 and resources: {requests: {cpu: "1", memory: 1Gi}, limits: {memory: 1Gi}}. Render it step by step.

  1. Merge values, later sources overriding earlier ones: the chart's values.yaml, then each -f file in order, then --set. Maps are merged key by key; lists and scalars are replaced. Result: replicaCount: 6; image.repository: ghcr.io/myorg/web (from defaults), image.tag: 2.7.2 (from --set); resources is a map, so it is merged: requests from the prod file replaces the default requests map key by key (cpu: "1", memory: 1Gi), and limits is added; config.LOG_LEVEL: info from defaults.
  2. Build the context (the "dot"): .Values (merged values), .Release (Name: shop, Namespace: prod, Revision, IsUpgrade), .Chart (from Chart.yaml), .Capabilities (the cluster's Kubernetes version and APIs) and .Template.
  3. {{ include "web.fullname" . }} runs the named template with the same context: printf "%s-%s" gives shop-web; trunc 63 keeps it within the 63-character limit for names; trimSuffix "-" removes a trailing dash that truncation might leave. Output: shop-web.
  4. Whitespace. {{- trims all whitespace (including the newline) to its left, -}} to its right. In labels: followed by {{- include "web.labels" . | nindent 4 }}, the {{- eats the newline after labels:; nindent 4 then adds a newline and indents every line of the helper's output by four spaces. Result: the two label lines appear correctly nested under labels:. Using indent instead of nindent, or forgetting the dash, produces lines at the wrong depth — sometimes invalid YAML, sometimes valid YAML with the labels attached to the wrong key, which is worse.
  5. {{ .Values.replicaCount }} prints 6.
  6. The image: .Values.image.tag | default .Chart.AppVersion — default returns its argument if the piped value is empty; the tag is 2.7.2, so the line is image: "ghcr.io/myorg/web:2.7.2". (In production you would set a digest; k8s5.)
  7. {{- with .Values.resources }} sets the dot to the resources map and renders its body only if the map is non-empty. toYaml . serialises the map at column zero; nindent 10 places it under resources:.
  8. The checksum annotation renders the ConfigMap template itself to a string and takes its SHA-256. If config.LOG_LEVEL changes, the ConfigMap's rendered text changes, the hash changes, the pod template changes, and the Deployment rolls out new pods (k8s9). If nothing changes, the hash is identical and nothing rolls.

The rendered result (from helm template shop ./web -f values-prod.yaml --set image.tag=2.7.2):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-web
  labels:
    app.kubernetes.io/name: web
    app.kubernetes.io/instance: shop
spec:
  replicas: 6
  selector:
    matchLabels:
      app.kubernetes.io/name: web
      app.kubernetes.io/instance: shop
  template:
    metadata:
      labels:
        app.kubernetes.io/name: web
        app.kubernetes.io/instance: shop
      annotations:
        checksum/config: 6f1c0b4e…   # sha256 of the rendered ConfigMap
    spec:
      containers:
      - name: web
        image: "ghcr.io/myorg/web:2.7.2"
        resources:
          limits:
            memory: 1Gi
          requests:
            cpu: "1"
            memory: 1Gi

Note toYaml sorted the keys alphabetically (limits before requests) and kept "1" quoted because it came from YAML as a string. Two classic template pitfalls come from types: --set converts true, numbers and null to typed values (use --set-string for literal strings), and large integers can be rendered in scientific notation if they pass through floating point. helm template plus a linter (helm lint, or validating the output with kubeconform) catches most of these before the cluster does.

4. Releases, upgrades and rollback

A release is one installation of a chart under a name in a namespace (shop in prod). Every install, upgrade or rollback creates a new revision, stored by default as a Secret in the release's namespace named sh.helm.release.v1.shop.v3, labelled owner=helm, containing the chart, the merged values and the rendered manifest (gzipped and base64-encoded). helm history shop lists the revisions with their status (deployed, superseded, failed, pending-upgrade); helm get values and helm get manifest read them back. Because the record is a Secret, it is subject to the 1 MiB object limit — very large charts can hit it.

On upgrade, Helm renders the new manifests and works out what to change. Helm 3 did this with a three-way merge: the old manifest from the last revision, the new manifest, and the live object, so that changes made in the cluster by others (an HPA's replica count, for example) are preserved unless the chart changes the same field. Helm 4, released in November 2025, switched new releases to Kubernetes server-side apply (k8s6): the API server merges the chart's fields and records Helm as their field manager, so a field owned by another manager produces an explicit conflict instead of a silent overwrite. Releases created by Helm 3 keep their original method when upgraded with Helm 4. Helm 3's final feature release is scheduled for September 2026, with security fixes through February 2027.

helm rollback shop 2 re-applies revision 2's manifests as a new revision (say, revision 5). It restores objects, not data. Two more gaps: Helm installs CRDs from a chart's crds/ directory on first install but never upgrades or deletes them, so CRD changes need their own process; and hooks — templates annotated helm.sh/hook: pre-upgrade and similar, typically Jobs for database migrations — run at defined points but are not themselves rolled back. A failed or interrupted upgrade can leave a release in pending-upgrade, blocking further operations with "another operation is in progress" until it is rolled back.

5. Kustomize: bases, overlays and generators

Kustomize takes the opposite approach: no templates. A kustomization.yaml lists resources and transformations, and kubectl kustomize (or kubectl apply -k) builds the result.

base/
  kustomization.yaml     # resources: [deployment.yaml, service.yaml, hpa.yaml]
  deployment.yaml        # a complete, valid Deployment (replicas omitted, image web:latest)
overlays/prod/
  kustomization.yaml
  resources-patch.yaml

# overlays/prod/kustomization.yaml
resources: [../../base]
namespace: prod
labels:
- pairs: { env: prod }
  includeSelectors: false
images:
- name: ghcr.io/myorg/web
  newTag: "2.7.2"
patches:
- path: resources-patch.yaml
configMapGenerator:
- name: web-config
  literals: [LOG_LEVEL=info]

# overlays/prod/resources-patch.yaml   (strategic merge patch)
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  template:
    spec:
      containers:
      - name: web                  # merged by container name
        resources:
          requests: { cpu: "1", memory: 1Gi }
          limits: { memory: 1Gi }

Building the prod overlay: Kustomize loads the base resources, sets metadata.namespace: prod on every object, adds the env: prod label, rewrites any image named ghcr.io/myorg/web to tag 2.7.2, and applies the patch with strategic merge semantics — Kubernetes-aware merging in which the containers list is merged by each container's name, so only web's resources change. (JSON 6902 patches with explicit op/path are available for precise edits.) The configMapGenerator creates a ConfigMap named web-config-<hash>, where the suffix is derived from a hash of its contents, and rewrites every reference to web-config in the Deployment to the hashed name. Change LOG_LEVEL and the name changes, so the pod template changes and pods roll — the same effect as Helm's checksum annotation, with old ConfigMaps left for rollbacks until pruned.

The appeal is that every file is ordinary YAML you can read, validate and diff; the limits are that anything not expressible as a patch or transformer — loops, conditionals, computed values — has no place, by design.

6. GitOps: the pull model

Helm and Kustomize decide what the manifests are. Something still has to apply them. Pushing from CI (helm upgrade in a pipeline) works but has two weaknesses: CI needs credentials that can change production, and nothing notices or corrects changes made outside the pipeline. GitOps, summarised by the OpenGitOps principles, fixes both: desired state is declarative, versioned and immutable (in Git), pulled automatically by agents, and continuously reconciled. It is the Kubernetes controller pattern (k8s6) applied one level up, with Git as the spec.

Argo CD has three main components. The repo-server clones repositories and renders manifests — plain YAML, Kustomize, Helm (via helm template) or plugins — caching results by commit. The application controller watches live objects in each destination cluster, compares them with the rendered desired state (normalising defaults so that fields the API server fills in do not count as drift), reports each Application as Synced or OutOfSync and Healthy, Progressing or Degraded, and performs syncs. The API server and UI serve users and CI. An Application declares it all:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: web-prod, namespace: argocd }
spec:
  project: shop
  source:
    repoURL: https://github.com/myorg/shop-config
    targetRevision: main
    path: web/overlays/prod
  destination: { server: https://kubernetes.default.svc, namespace: prod }
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions: [ServerSideApply=true]

With automated, a merge to main is noticed (by polling, every few minutes by default, or immediately via a webhook), rendered, diffed and applied. prune: true deletes live objects that disappeared from Git; selfHeal: true re-applies Git when someone changes the cluster by hand. Ordering within a sync uses sync waves (an annotation; lower waves are applied first and must become healthy before the next) and hooks (PreSync Jobs for migrations). AppProjects restrict which repositories, clusters and namespaces an Application may use — a security boundary that matters in the prod section. ApplicationSets generate Applications from patterns, such as one per directory or per cluster.

Flux takes the same approach with a toolkit of controllers: source-controller fetches GitRepository, OCIRepository and HelmRepository sources into artefacts; kustomize-controller applies Kustomization objects (Flux's resource, which builds a Kustomize directory and applies it with server-side apply, with pruning and health checks); helm-controller reconciles HelmRelease objects using the Helm libraries, so releases keep Helm's history; and image-automation controllers can commit new image tags back to Git. Argo CD is known for its UI and multi-cluster application view; Flux for composability and a Kubernetes-native, CLI-first design. Both are CNCF graduated projects.

7. Promotion, rollback and secrets in GitOps

A typical flow for one service:

  1. CI builds the image once, pushes it, signs it and records its digest (k8s5).
  2. CI opens a pull request (or commits directly, for dev) changing the image in overlays/dev to the new digest. Merge → Argo CD syncs dev.
  3. After dev checks pass, an automated pull request makes the same change in overlays/staging, then overlays/prod-eu, then overlays/prod-us, each gated on checks and, for production, approval. Only the version moves; environment differences stay in their overlays.
  4. Rollback is git revert of the promotion commit; the agent applies the previous digest. The Deployment performs an ordinary rolling update back (k8s7).

Secrets need care because Git must not hold plaintext. The common choices are SOPS (files encrypted with keys in a KMS, decrypted by the agent at render time — Flux supports it natively, Argo CD through plugins), Sealed Secrets (encrypted with a public key; only the controller in the cluster can decrypt into a Secret), or the External Secrets Operator, where Git holds an ExternalSecret that references a path in Vault or a cloud secret manager and the operator creates the Secret (k8s9). The last keeps secret material out of the GitOps pipeline entirely.

And one field needs special handling: replicas. If an HPA manages a Deployment, a replicas value in Git makes the agent reset it on every sync. Omit replicas from the manifest (the API server keeps the live value), or configure the tool to ignore it; with server-side apply, the HPA's controller owns the field and conflicts are visible.

8. A change, from commit to production, with times

Follow one change through a GitOps setup to see where time goes and where it can go wrong. At 10:00 a developer merges a fix to the application repository. CI builds, tests, scans and signs the image in about eight minutes, and at 10:08 opens a pull request in the configuration repository changing overlays/dev to the new digest; it is auto-merged because dev requires no review. Argo CD learns of the commit by webhook within seconds (without a webhook it polls, every three minutes by default), renders the overlay, sees the Deployment's pod template differ, and syncs at 10:09. The Deployment rolls out (k8s7) and is healthy by 10:11; Argo CD marks the Application Synced and Healthy. Automated checks run against dev, and at 10:20 a promotion pull request for staging opens; after the staging checks, a production pull request opens for one region, needs one approval, and is merged at 11:05. Production regions then follow one at a time.

Every step is visible and reversible: the commits say what changed and who approved it, the Application's history shows when each environment synced, and rollback at any stage is a revert. Two practical points come out of the timeline. Configure webhooks from the Git host to the GitOps agent, or "merged" and "deployed" can be minutes apart and confuse everyone. And keep promotion automated but gated: the value of GitOps is not speed alone but that the fast path and the safe path are the same path.

9. Laying out the configuration repository

Two layouts are common. A separate config repository holds the manifests or values for many services and environments; application repositories only build images, and CI opens pull requests against the config repository. This keeps deploy history in one place and lets platform teams review environment-wide changes. Keeping manifests next to the application code (a deploy/ directory) keeps a service self-contained, but then the deploy record is spread across repositories and an image build and its rollout are entangled in one commit. Whichever you choose, avoid one Git branch per environment: merging between long-lived environment branches drifts, conflicts and hides what is actually different; directories per environment (Kustomize overlays, values files) on one main branch make the differences explicit and diffable.

Templates versus overlays is a trade-off in where complexity lives

Templating puts complexity in the chart: every configurable field is a values key, and popular charts grow hundreds of keys, conditionals and helper functions until reading the template is harder than reading the output. Overlays put complexity in the variants: the base stays readable, but a large organisation can end up with deep chains of overlays whose combined effect is only visible after a build. Both converge on the same discipline: review the rendered output, not just the inputs. Tools that diff rendered manifests between the current and proposed commit in a pull request (Argo CD's diff, flux diff, helm diff) make the effect of a change visible where it is reviewed.

Server-side apply and field ownership

Server-side apply records, for every field of every object, which field manager last set it: Helm, Argo CD, the HPA controller, a human with kubectl. Applying a manifest that sets a field owned by another manager is a conflict; the applier must either drop the field or force ownership. This makes previously silent fights visible — GitOps versus HPA over replicas, a mutating webhook versus a chart over an injected sidecar — and makes "remove a field from Git" safe: with SSA, fields no longer in the applied configuration are removed if the manager owned them. The cost is learning to read managedFields and deciding deliberately which manager owns what.

Ordering, dependencies and CRDs

Kubernetes has no global transaction: a sync applies many objects, and some depend on others. A custom resource cannot be created before its CRD is established; a namespace must exist before objects in it; a migration Job should run before the new Deployment. Helm orders installs by kind with a built-in list and supports hooks and weights; Argo CD uses sync waves and phases; Flux uses dependsOn between Kustomizations and health checks. CRDs are the persistent pain point: they are cluster-scoped, shared by every release that uses them, and deleting one deletes every instance of it, so most platforms manage CRDs separately from the applications that use them, with conservative upgrade and no automatic pruning.

Multi-cluster and the app-of-apps pattern

With dozens of clusters, someone has to create the Argo CD Applications themselves. The app-of-apps pattern stores Application manifests in Git and has one root Application sync them; ApplicationSets generate Applications from generators (a list of clusters registered in Argo CD, directories in a repository, pull requests for preview environments). The same Git change can then fan out to every cluster in waves — one region first — which turns cluster-wide changes (a new admission policy, a CNI upgrade) into ordinary reviewed commits with a staged rollout, precisely the discipline whose absence caused the Reddit outage in sc15.

Charts are supply-chain inputs too

A third-party Helm chart is code that runs with your deployer's permissions: its templates decide which ClusterRoles, webhooks and privileged DaemonSets get created, and its hooks run Jobs at install time. Pulling latest of a popular chart from a public repository is the same risk as pulling an unpinned image (k8s5). Treat charts accordingly: pin chart versions (and, for OCI charts, digests), mirror them into an internal registry, verify provenance or signatures where publishers provide them, render and review the output of every upgrade — especially RBAC and admission-webhook changes — and scan rendered manifests with policy tools before they reach the cluster. The same applies to Kustomize remote bases referenced by URL.

Progressive delivery inside GitOps

GitOps decides what version should run; it does not, by itself, roll it out cautiously. Argo Rollouts and Flagger replace the Deployment's simple rolling update with canary or blue-green steps gated on metrics (swe9): a Rollout object in Git describes the steps (5% for five minutes, analysis, 25%…), and the controller shifts traffic through a service mesh or Gateway API weights (k8s8), aborting and scaling back the canary if the analysis fails. Git still holds the desired version; the rollout controller decides how fast reality catches up, and an aborted rollout leaves the cluster on the old version while Git says new — a deliberate, visible divergence for a human to resolve.

Rendering in CI versus rendering in the agent

Two schools exist for where manifests are rendered. In the first, the GitOps agent renders Helm charts and Kustomize overlays itself from source (Argo CD's repo-server, Flux's controllers). It keeps the repository small and declarative, but the exact manifests applied are only visible in the agent, and the renderer becomes a privileged component with access to many repositories — the risk the prod case illustrates. In the second, CI renders the final manifests and commits them (the "rendered manifests" pattern) to a branch or repository that the agent applies verbatim. Every change to what runs in the cluster is then a reviewable diff of plain YAML, and the agent no longer needs to execute templates or plugins, at the cost of more generated files in Git and a CI step that must stay in sync with tool versions. Teams with strict review requirements or many third-party charts increasingly prefer the second.

The case: Argo CD's Helm path traversal (CVE-2022-24348)

In February 2022 Argo CD published security advisory GHSA-63qx-x74g-jcr7, crediting Moshe Zioni of Apiiro with the discovery. Argo CD lets users create Applications whose source is a Helm chart, optionally with a list of values files. The repo-server renders such charts by running helm template with those values files on its own file system, where it keeps clones of every repository it serves. The advisory states that all versions were vulnerable to a path-traversal bug allowing arbitrary values files to be passed to Helm, and that while fixing it, the Argo CD team found that chart packages could also contain values files that were symbolic links pointing outside the repository root. A user allowed to create or update Applications, who knew or could guess the path of a YAML file on the repo-server, could therefore make a chart consume it as values and read data they had no right to — and because helm template's verbose error messages were returned to the user, they could enumerate files. The impact was especially critical where plugins such as git-crypt or SOPS decrypted secret value files to disk before rendering: other applications' secrets sat on the same disk. Fixed versions were 2.3.0, 2.2.4 and 2.1.9; there was no workaround.

The lesson connects to k8s9's subPath escape: a privileged component following paths and symlinks supplied by less-trusted users. For delivery systems specifically: the renderer runs other people's charts, plugins and Kustomize remote bases, so treat it as a sandbox boundary — restrict which repositories each team may use through AppProjects, avoid decrypting secrets to a shared file system (prefer External Secrets, where plaintext never passes through the GitOps pipeline), keep the agent patched, and limit what the agent's own credentials can do in each cluster.

Failure modes in production

  • "another operation (install/upgrade/rollback) is in progress": a Helm release stuck in pending-* after an interrupted upgrade. Roll back to the last deployed revision.
  • Immutable field changed: a chart change to a Deployment's selector or a StatefulSet's volumeClaimTemplates is rejected; requires delete-and-recreate or a new resource name.
  • Config changed, pods didn't: no checksum annotation or hashed ConfigMap name.
  • Sync loop / constant OutOfSync: fields defaulted or mutated by controllers and webhooks (replicas, injected sidecars, caBundles) not ignored or not owned via SSA.
  • Prune deletes too much: a refactor that moves resources between Applications deletes them in one and creates them in the other, briefly or with data loss for PVCs. Use prune-protection annotations on stateful resources.
  • Hotfix reverted: self-heal undoes an emergency kubectl change. Have a documented "pause sync" procedure and make the fix in Git.
  • CRD drift: chart upgrades that need newer CRDs fail because Helm does not upgrade them.

What to measure

Per Application: sync status, health, last sync time and duration, sync failures. For the pipeline: lead time from merge to synced in each environment, deployment frequency, change failure rate and time to restore (the DORA measures), drift events per week (a high number means people work around Git), and the age of the oldest unpromoted change between environments.

Ownership and access

Decide who may change what in the configuration repository with the same care as cluster RBAC, because in GitOps the repository is the access path to production. Code owners per directory, required reviews for production overlays, signed commits where your tooling supports them, and branch protection on the main branch translate organisational responsibility into enforceable rules, and the GitOps agent's AppProjects make sure a team's Applications can only deploy to that team's namespaces.

  4. Values precedence and config hashing (runs here). Save as values.py: 
    import copy, hashlib, json
def merge(base, over):                       # Helm-style: maps merge, others replace
    out = copy.deepcopy(base)
    for k, v in over.items():
        out[k] = merge(out[k], v) if isinstance(v, dict) and isinstance(out.get(k), dict) else copy.deepcopy(v)
    return out
def set_path(vals, dotted, value):           # --set a.b.c=value
    d = vals
    *parents, leaf = dotted.split(".")
    for p in parents: d = d.setdefault(p, {})
    d[leaf] = value
defaults = {"replicaCount": 2, "image": {"repository": "ghcr.io/myorg/web", "tag": ""},
            "resources": {"requests": {"cpu": "250m", "memory": "256Mi"}}, "config": {"LOG_LEVEL": "info"}}
prod = {"replicaCount": 6, "resources": {"requests": {"cpu": "1", "memory": "1Gi"}, "limits": {"memory": "1Gi"}}}
vals = merge(defaults, prod); set_path(vals, "image.tag", "2.7.2")
print(json.dumps(vals, indent=1))
def config_hash(cfg):                         # stand-in for checksum/config or a Kustomize suffix
    return hashlib.sha256(json.dumps(cfg, sort_keys=True).encode()).hexdigest()[:10]
print("checksum/config:", config_hash(vals["config"]))
vals["config"]["LOG_LEVEL"] = "debug"
print("after change:    ", config_hash(vals["config"]), "-> pod template changes -> rollout")
    Expect replicaCount 6, the repository from defaults, tag 2.7.2, requests replaced by the prod values with limits added, and two different hashes. (Real Kustomize uses its own hash encoding; the principle is the same.)
Diagnose: the deployment that keeps undoing itself

A team moved a service to Argo CD with automated sync, prune and self-heal. Since then: (1) every few minutes the Deployment's replicas drop from around 12 to 3 and climb back, and users see brief latency spikes; (2) a ConfigMap change merged an hour ago is visible in the cluster, but the pods still log with the old level; (3) during last night's incident an engineer raised a memory limit with kubectl edit, and it reverted within three minutes, causing OOM kills to resume. The manifests are plain YAML in a Kustomize overlay with replicas: 3, a ConfigMap web-config referenced by envFrom, and an HPA. Explain each symptom and fix them.

Answer

(1) The HPA scales to ~12, Argo CD sees replicas: 3 in Git, reports OutOfSync and self-heal applies 3; the HPA scales up again. Fix: remove replicas from the overlay (or add ignoreDifferences for /spec/replicas), and use server-side apply so the HPA owns the field. (2) The ConfigMap object changed, but the pods read it through envFrom, which is evaluated only at container start, and the pod template did not change, so no rollout happened. Fix: replace the plain ConfigMap with a configMapGenerator so its name carries a content hash and references update, causing a rollout on every config change (or add a checksum annotation if using Helm). (3) Self-heal did exactly its job: the live object differed from Git. Fix the process, not the tool: the emergency change should be a commit (fast-tracked review), or the runbook should include pausing automated sync for that Application (disable self-heal or the automated policy temporarily) and re-enabling it after the fix lands in Git. Raise the memory limit in the overlay now, so the incident fix is permanent. Add alerts on repeated self-heal events, which reveal both automation fights and people working around Git.
