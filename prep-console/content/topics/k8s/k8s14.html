An ML team moves its work onto the company's Kubernetes platform. Within a month, every lesson in this track shows up again, amplified by the price of a GPU. A data scientist's notebook pod holds an 80 GB H100 for a week while using it a few minutes a day. Two distributed training jobs each grab half the free GPUs and wait forever for the other half. A new LLM endpoint takes nine minutes to serve its first request after a scale-up, because a fresh GPU node must boot, pull a 9 GB serving image, download 16 GB of weights and load them into GPU memory. The autoscaler, configured on GPU utilisation, never scales: the GPUs read "98% utilised" while requests queue. And a training job that has run for eleven hours is OOM-killed by the container's memory limit — not GPU memory, host memory, eaten by data-loader workers.

None of these failures needs new Kubernetes concepts. They need the existing ones applied to hardware that is scarce, expensive, slow to provision and shaped differently from CPUs. A GPU is an integer resource that cannot be overcommitted. It reaches a container through a driver, a runtime hook and a device plugin rather than a cgroup. It can be split in software or in hardware, with very different isolation. Training jobs need all their workers at once. Serving replicas carry gigabytes of state that must be loaded before they help. And the most-quoted GPU metric does not mean what people think (gpu1).

This lesson connects the Kubernetes mechanics of k8s1-k8s13 to ML workloads. It starts with how a GPU gets into a container and how the scheduler accounts for it, then sharing GPUs with time-slicing, MPS and MIG, and the newer Dynamic Resource Allocation. It covers training — gang scheduling and quota queues with Kueue — then serving: cold starts worked out with real image and model sizes, keeping weights out of images, KServe's two deployment modes, and autoscaling inference on signals that track load (lm13's queues and KV-cache). It closes with Ray on Kubernetes and with OpenAI's account of running training clusters of 7,500 nodes.

Specialist ovens in a shared kitchen

Picture a commercial kitchen. Most work uses the ordinary hobs and counters, which are shared flexibly: a cook can use a bit more counter space when nobody else needs it (CPU and memory, k8s10). But a few stations have a specialist oven that costs as much as the rest of the kitchen put together. Ovens are booked whole — you cannot book half an oven — and the booking sheet only counts ovens, not how hot each one is running.

  • Getting an oven needs three things on that station: the oven's own wiring (the GPU driver on the node), an adapter that lets a cook's equipment plug into it (the NVIDIA Container Toolkit), and a sign on the station listing how many ovens it has (the device plugin, which tells the kubelet "this node has 8 nvidia.com/gpu"). The GPU Operator is the contractor who installs and maintains all three.
  • Sharing an oven: you can let several cooks take turns (time-slicing), let them use it at once and hope they don't clash (MPS), or install fixed internal walls so it becomes several smaller, isolated ovens (MIG).
  • Banquets (distributed training) need all their ovens at the same moment; booking half and waiting for the rest wastes the half. A maître d' with a reservation book (Kueue) only seats a banquet when all its ovens are free.
  • Restaurants (model serving) must preheat: a new oven is useless until it is installed, the right equipment is fetched and the dish is prepared. Keeping some ovens warm, and the ingredients nearby, is what makes service fast.

Three workload shapes, three sets of rules

ML on Kubernetes is really three workload shapes with different needs. Interactive work (notebooks, experiments) holds resources for long periods while using them in bursts; it needs cheap, shareable GPUs and automatic clean-up. Training runs for hours or days on many GPUs at once; it needs all of them together, fast interconnect between them, fair sharing between teams, and protection from interruption or the ability to resume after it. Serving runs indefinitely with traffic that rises and falls; it needs fast start-up, autoscaling on the right signal and isolation from noisy neighbours. Most of the mistakes in the opening story come from applying one shape's rules to another — serving-style Deployments for training, training-style whole-GPU allocations for notebooks, CPU-style autoscaling for inference.

Where the analogy breaks: an oven's heat is a fair measure of its work, but a GPU's "utilisation" number is not. It reports the fraction of time any kernel was running, so a GPU doing light work continuously looks as busy as one running flat out (gpu1). Decisions about capacity need better signals, from the serving engine or from finer-grained GPU counters.

1. How a GPU reaches a container

Containers get CPU and memory through cgroups (k8s10). A GPU is different: it is a PCIe device driven by a kernel driver, used by applications through user-space libraries (libcuda, NVML) that must match the driver version. Four pieces make it work on Kubernetes:

  1. The driver on the host creates device files (/dev/nvidia0 … /dev/nvidia7, /dev/nvidiactl, /dev/nvidia-uvm) and loads the kernel modules.
  2. The NVIDIA Container Toolkit integrates with containerd or CRI-O so that, when a container is created with certain GPUs assigned, the runtime adds those device files and bind-mounts the matching driver libraries and utilities into the container (today usually through the Container Device Interface, CDI, a standard for describing such device injections). The image therefore does not contain the driver — only CUDA user-space libraries that must be compatible with it.
  3. The device plugin runs as a DaemonSet and talks to the kubelet's device plugin API over a Unix socket: it registers the resource name nvidia.com/gpu, streams the list of healthy devices (ListAndWatch), and, when the kubelet starts a container that was allocated GPUs, answers Allocate with what the runtime must inject for those specific device IDs. The kubelet adds the count to the node's capacity and allocatable, so kubectl describe node shows nvidia.com/gpu: 8.
  4. The GPU Operator installs and manages these as Kubernetes components: the driver (as a container), toolkit, device plugin, GPU feature discovery (which labels nodes with nvidia.com/gpu.product=NVIDIA-H100-80GB-HBM3, memory, count and MIG capability), the DCGM exporter (metrics and health) and the MIG manager — all reconciled from one custom resource, so versions stay consistent across nodes.

A pod asks for GPUs as an extended resource:

resources:
  limits:
    nvidia.com/gpu: 1        # whole GPUs; requests, if set, must equal limits
    cpu: "8"
    memory: 64Gi
nodeSelector:
  nvidia.com/gpu.product: NVIDIA-H100-80GB-HBM3
tolerations:
- { key: nvidia.com/gpu, operator: Exists, effect: NoSchedule }

The rules from the Kubernetes docs: GPUs are specified in limits; requests default to the limit and must equal it if given; you cannot specify requests without limits; and the quantity is an integer. The scheduler counts GPUs exactly like CPU against allocatable (k8s6), but there is no overcommit and no sharing: a pod that gets one GPU has it exclusively, whether it uses it fully or not. The node selector picks a GPU model; the toleration lets the pod onto GPU nodes that are tainted to keep everything else off (k8s10). Many managed platforms add the taint to GPU node pools and the toleration to GPU-requesting pods automatically.

2. Sharing a GPU: time-slicing, MPS and MIG

Whole-GPU allocation wastes money for small workloads: a 7B-parameter model in 4-bit weights, a notebook, a small embedding service might need 10 GB and a fraction of the compute of an 80 GB H100. There are three ways to share, configured at the node level and surfaced to pods as resources.

Time-slicing is a device-plugin setting: "advertise each GPU as 4". A node with 8 GPUs then shows nvidia.com/gpu: 32, and up to four pods share each GPU by time. Nothing stops one of them from allocating all 80 GB, crashing the others with out-of-memory errors, so it suits development, notebooks and light inference where tenants trust each other. MPS lets kernels from several processes run at the same time rather than in turns, improving throughput for many small kernels, with partial isolation.

MIG (Multi-Instance GPU) splits a supported GPU in hardware. An H100 80GB can be partitioned, for example, into seven 1g.10gb instances (each one-seventh of the compute with 10 GB), or into mixes such as 3g.40gb + 2g.20gb + 1g.10gb; each instance has its own memory, cache and SMs, so a fault or memory exhaustion in one does not affect the others. With the device plugin's mixed strategy, each profile is its own resource, and a pod asks for nvidia.com/mig-1g.10gb: 1. The MIG manager applies a node's partition layout from a label. The trade-off is rigidity: slice sizes are fixed per GPU model, re-partitioning requires draining the GPU, and a workload that needs 15 GB must take a 20 GB slice.

3. Dynamic Resource Allocation

Counting identical devices works for "one GPU". It struggles with "a GPU with at least 40 GB of memory and compute capability 9.0, on the same NVLink domain as another", or "a 2g.20gb MIG slice created on demand". Dynamic Resource Allocation (DRA), which the Kubernetes documentation lists as stable since 1.35, replaces counted resources with claims. A driver publishes ResourceSlices describing each node's devices and their attributes; administrators define DeviceClasses; a pod references a ResourceClaim (or a template that creates one per pod) whose requests select devices with CEL expressions on attributes:

apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata: { name: big-gpu }
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          selectors:
          - cel: { expression: "device.capacity['gpu.nvidia.com'].memory.compareTo(quantity('40Gi')) >= 0" }

The scheduler allocates matching devices as part of placement, and the driver prepares them on the node. DRA is how structured sharing, partitioning on demand and device topology are being brought into the scheduler rather than bolted on beside it; NVIDIA publishes a DRA driver for GPUs. For most clusters today, the device-plugin resources above remain the common path, and DRA is worth adopting where its selection power is needed.

4. Training: gang scheduling and quota queues

A distributed data-parallel training job — say 4 nodes × 8 GPUs with PyTorch's distributed launcher, or an MPI job — only makes progress when every worker is running, because each step synchronises gradients across all of them. Kubernetes' default scheduler places one pod at a time (k8s6), and that creates a classic deadlock. Worked example: a cluster has 16 free GPUs on two 8-GPU nodes. Job A and job B are each 4 pods × 4 GPUs (16 GPUs). Their pods are created at the same moment and interleave in the scheduling queue: A-0 and B-0 land on node 1, A-1 and B-1 on node 2. All 16 GPUs are now allocated; A-2, A-3, B-2 and B-3 are Pending. Neither job can start, and neither will release its GPUs — they are waiting on each other forever, while the GPUs sit idle and bill.

The fix is gang scheduling: admit all of a job's pods, or none. The most common way in Kubernetes is Kueue, a SIG Scheduling project that works with standard Jobs, JobSets, Kubeflow training jobs, RayJobs and more:

  • Jobs are created suspended (spec.suspend: true, k8s7) and placed in a LocalQueue for their namespace, pointing at a ClusterQueue that holds quota per ResourceFlavor (for example 64 H100s and 32 L4s).
  • Kueue admits a job only when its whole request fits in the queue's available quota, then unsuspends it, so all its pods are created together and fit. In the example, A is admitted (16 GPUs), B waits in the queue, and A runs.
  • ClusterQueues in a cohort can borrow each other's unused quota and reclaim it by preemption, so a research team can use idle production-reserved GPUs at night and give them back in the morning; fair sharing balances usage across teams over time.

Alternatives include the scheduler's coscheduling plugin (pods labelled into a PodGroup with a minimum member count), and batch schedulers such as Volcano. Placement also matters: workers that exchange gradients every step should sit on nodes with fast interconnect between them, so training platforms add topology labels (rack, network block) and topology-aware scheduling, and multi-node jobs often use JobSet or LeaderWorkerSet to manage groups of pods as one unit. Finally, long jobs must survive disruption: checkpoint regularly to object storage (k8s9), protect running jobs from consolidation and drains (karpenter.sh/do-not-disrupt, k8s11), and make restarts resume from the last checkpoint.

5. Serving: where a cold start goes

A model server replica is not ready until it has the model in GPU memory, so its start-up is much longer than a web service's. Work through a new replica of an 8B-parameter LLM served with vLLM, scheduled when no GPU node has room:

The image size is real: the vllm/vllm-openai image on Docker Hub is about 8.7 GB compressed for amd64, and even a minimal pytorch/pytorch CUDA runtime image is about 3.3 GB (the devel variant, with compilers, about 14 GB). A 70B model in BF16 is about 140 GB of weights, which changes "seconds" into "minutes" at any realistic bandwidth. The table shows where to attack:

  • Keep weights out of the image. Images change rarely, weights often; baking them together makes every model update a huge push and every pull a huge download. Store weights in object storage or a model registry (ae8) and fetch them at start.
  • Cache weights per node, not per pod. Download once to node-local NVMe (a DaemonSet or init container populating a hostPath or local volume), or a shared read-many volume (k8s9), so the second replica on a node starts from local disk. Image volumes (stable since 1.36) mount an OCI image or artefact read-only into a pod: package weights as an OCI artefact, store it in your registry next to the serving image, and let the node's image cache and pull machinery (and signing, k8s5) handle it.
  • Pre-pull serving images into GPU node images, or with a DaemonSet, and use lazy-loading snapshotters for the remainder (k8s1).
  • Keep warm capacity: placeholder pods on GPU nodes (k8s11's overprovisioning) or a minimum replica count, so scale-up lands on a ready node.
  • Use startup probes sized to the real load time, so the liveness probe does not kill a replica that is still loading (k8s13), and readiness that passes only when the model is loaded.

6. KServe: InferenceService and its two modes

KServe is a Kubernetes-native model-serving platform. You describe the model, not the Deployment:

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata: { name: summariser }
spec:
  predictor:
    minReplicas: 1
    maxReplicas: 8
    model:
      modelFormat: { name: huggingface }
      storageUri: s3://models/summariser/v7
      resources:
        limits: { nvidia.com/gpu: 1, cpu: "8", memory: 48Gi }

KServe picks a serving runtime for the model format (for LLMs typically vLLM-based), runs a storage initializer that downloads storageUri into the pod before the server starts, and creates the routing. It supports canary rollouts between model versions and, for LLMs, an LLMInferenceService resource with features such as disaggregated prefill and decode. It has two deployment modes:

  • Standard mode (previously called raw deployment) creates ordinary Deployments and Services, scaled by an HPA or KEDA. KServe's documentation recommends it for most production scenarios and especially for LLM serving: predictable scaling, standard networking, no extra dependencies.
  • Knative mode runs the predictor as a Knative Service. Knative's autoscaler scales on request concurrency: with a target of, say, 4 concurrent requests per replica and 37 requests in flight, it wants ceil(37 ÷ 4) = 10 replicas. It can scale to zero after a period without traffic; the next request is held by Knative's activator, which triggers scale-from-zero and forwards the request once a replica is ready. That is ideal for many rarely used models on shared GPUs, and a cold start of the length worked above for the unlucky first caller.

7. Autoscaling inference on the right signal

For CPU services, CPU utilisation is a usable proxy for load. For GPU inference, the obvious analogue — GPU utilisation — is misleading. The commonly exported DCGM utilisation metric (DCGM_FI_DEV_GPU_UTIL) measures the fraction of time in the sample period that at least one kernel was executing (gpu1). An LLM server doing continuous batching runs decode kernels almost constantly, so it reads close to 100% at modest load and stays there as load doubles; meanwhile the real limits — KV-cache memory and batch slots (lm13) — determine when requests start to queue.

Better signals come from the serving engine itself. vLLM, for example, exports Prometheus metrics for requests running and requests waiting, and KV-cache usage. A KEDA ScaledObject (k8s11) on waiting requests:

triggers:
- type: prometheus
  metadata:
    serverAddress: http://prometheus.monitoring:9090
    query: sum(vllm:num_requests_waiting{model_name="summariser"})
    threshold: "4"          # target: about 4 waiting requests per replica

Worked: 3 replicas, 26 requests waiting → the HPA KEDA manages computes ceil(26 ÷ 4) = 7 replicas; as the queue drains, the scale-down window holds capacity before releasing it. Pair this with: a scale-down stabilization window of many minutes (replicas are slow to start, so flapping is expensive); a minReplicas that covers baseline traffic; warm GPU capacity for the first scale-up step; and a router that spreads requests well — long-lived connections and very uneven request sizes defeat per-connection balancing (k8s8), which is why inference-aware gateways route by queue length or prefix-cache affinity.

8. Ray on Kubernetes with KubeRay

Ray is a Python framework for distributed computing — data processing (Ray Data), training (Ray Train), tuning and serving (Ray Serve) — with its own scheduler for tasks and actors inside a cluster of processes. KubeRay is the operator that runs Ray clusters on Kubernetes:

  • RayCluster: a head pod (cluster control, the Global Control Service) and one or more worker groups, each a pod template with resources — for example a CPU group for preprocessing and a GPU group for training — with min and max replicas.
  • RayJob: submits a job to a RayCluster (creating one if needed) and can tear it down when the job finishes; works with Kueue for gang admission.
  • RayService: runs Ray Serve applications with zero-downtime upgrades of the underlying cluster.

Scaling is layered exactly as in k8s11: when Ray tasks or actors need more resources than the cluster has, the Ray autoscaler asks KubeRay for more worker pods; pending worker pods make Karpenter or the Cluster Autoscaler add GPU nodes. Ray suits workloads that are naturally Python-level graphs of tasks — a pipeline that reads data, tokenises on CPUs and embeds on GPUs, or hyperparameter search over hundreds of trials — that would be clumsy as many separate Kubernetes Jobs.

9. Observing GPU workloads

Because the headline utilisation number misleads (section 7), GPU observability needs a few more signals. The DCGM exporter publishes per-GPU metrics labelled with the pod that holds the GPU, so they join cleanly with Kubernetes data. Device-level fields include memory in use (DCGM_FI_DEV_FB_USED), temperature, power and clock throttling, and XID error counts (DCGM_FI_DEV_XID_ERRORS) for health. The profiling fields are the ones that describe how busy the GPU really is: DCGM_FI_PROF_SM_ACTIVE (the fraction of time streaming multiprocessors have work), DCGM_FI_PROF_SM_OCCUPANCY (how full they are), DCGM_FI_PROF_PIPE_TENSOR_ACTIVE (tensor-core use) and DCGM_FI_PROF_DRAM_ACTIVE (memory-bandwidth use). A training job that shows 99% utilisation but 30% tensor activity and high DRAM activity is memory-bound (gpu1); an inference server with low SM activity and a growing request queue is limited elsewhere — the CPU, the network or the batch configuration.

Join these with the application's own metrics — step time and tokens per second for training, waiting requests, time to first token and time per output token for serving (lm13) — and with Kubernetes data: pods per GPU node, pending GPU pods, Kueue admission and wait times, and cold-start durations. The questions a platform team must answer every week are "which teams hold GPUs they are not using?", "which jobs wait longest and why?" and "how long does a new replica take to serve?"; each needs at least one metric from each of the three layers.

GPU health is a first-class scheduling concern

At fleet scale, GPUs fail in ways CPUs rarely do: uncorrectable memory errors, a GPU "falling off the bus", NVLink errors, thermal throttling. The driver reports many of them as XID errors in the kernel log; DCGM exposes health checks and counters. A failed GPU on an 8-GPU node can stall a 512-GPU training job, so platforms automate detection and response: the device plugin marks unhealthy devices so they are no longer allocatable; node health agents read XIDs and DCGM diagnostics and taint or cordon the node; active tests run when a node joins (and periodically) before the taint that keeps workloads off is removed; and remediation resets GPUs, reboots or replaces the VM. OpenAI's case below describes exactly this split between passive and active checks.

Topology and interconnect

Within a node, GPUs connected by NVLink and NVSwitch exchange data an order of magnitude faster than over PCIe; across nodes, training traffic uses high-bandwidth fabrics such as InfiniBand or RoCE with RDMA, often through dedicated network interfaces attached to pods (SR-IOV, multi-network). Kubernetes' kubelet has a Topology Manager that aligns CPUs, memory and devices on the same NUMA node for a pod, and schedulers and Kueue can use node labels for network topology to keep a job's workers in the same block. For an 8-GPU pod the question is mostly solved by taking the whole node; for jobs spanning many nodes, placement within the network topology can change step time noticeably, which is why large training clusters are scheduled with topology awareness rather than as a flat pool.

The economics of idle GPUs

A GPU's hourly price is roughly that of dozens of CPU cores, so the waste patterns of k8s10 — inflated requests, idle reservations — cost an order of magnitude more. Common leaks: notebooks holding whole GPUs for days (cull idle notebooks, or give them time-sliced or MIG slices); inference replicas sized for peak all day (autoscale on queue depth with warm minimums rather than fixed fleets); training jobs that crash at hour ten and restart from zero (checkpoint); and GPUs blocked by deadlocked partial gangs (Kueue). Spot GPUs cut prices substantially for checkpointed training and for inference with enough replicas to absorb interruptions. The metric to watch is not "GPU utilisation" but allocated-versus-busy GPU hours per team, from Kueue and DCGM together.

Multi-node inference

Models too large for one node's GPUs (hundreds of billions of parameters) are served across several nodes with tensor and pipeline parallelism. Each replica is then a group of pods that must start together, share a leader for coordination and be replaced together: LeaderWorkerSet provides that unit, with gang-like semantics for groups and rolling updates of whole groups. Autoscaling then adds or removes whole groups, each costing a large multi-node allocation, which makes warm capacity and accurate queue-based signals even more important.

Batch inference as a cheaper path

Not every model call needs an online endpoint. Scoring a table of a million rows overnight, embedding a document corpus or running evaluation suites are throughput problems, not latency problems (ae8). On Kubernetes they fit Indexed Jobs or RayJobs (k8s7) admitted through Kueue, running at large batch sizes on spot or borrowed GPUs, with checkpointed progress per shard. Moving work from always-on endpoints to scheduled batch jobs is often the single largest cost reduction available to an ML platform, because it turns idle reserved capacity into fully used, interruptible capacity.

Driver and CUDA compatibility

The driver lives on the node; CUDA libraries live in images. NVIDIA's compatibility rules let newer drivers run images built against older CUDA versions, and within a major CUDA version, images built for a newer minor version can often run on an older driver with limitations. Practically: pin a driver branch per node pool, test images against it in CI, and upgrade drivers through the GPU Operator node by node (it drains GPU pods first). A mismatch shows up as "CUDA driver version is insufficient for CUDA runtime version" at start-up — an error that is about the node, not the image.

Inference routing that understands models

Generic load balancing treats every request as equal, but LLM requests differ by orders of magnitude in prompt and output length, and replicas differ in what they have cached. Model-aware routing — for example the Gateway API Inference Extension, which lets a Gateway pick an endpoint using signals such as each replica's queue length and KV-cache usage, or routing that prefers the replica already holding a conversation's prefix in its cache (lm13's prefix caching) — reduces tail latency and wasted recomputation, and it changes autoscaling too, because a fleet with balanced queues saturates evenly rather than one replica at a time. It is the inference-specific answer to the per-connection balancing problem of k8s8, and it is moving quickly, so check what your Gateway implementation and serving engine support before designing around a specific feature.

The case: OpenAI, "Scaling Kubernetes to 7,500 nodes" (January 2021)

OpenAI described how it ran Kubernetes clusters of up to 7,500 nodes for research workloads behind models such as GPT-3, CLIP and DALL·E, following an earlier post about 2,500 nodes. Its workload is unusual for Kubernetes and typical of large-scale ML: a pod usually takes a whole node, so the scheduler is rarely bin-packing; large jobs span many nodes and communicate with MPI, over SSH between pods' IPs rather than through Services; and a failing worker can force the whole job to restart from a checkpoint, so reliability of every node matters more than load balancing.

The post maps onto this track almost section by section. Networking: Flannel's overlay could not keep up at that scale, so they moved to the cloud's native pod networking with routable pod IPs (k8s8), and used iptables mangle rules with an exporter to account for internet-bound versus internal traffic. Control plane: API servers and etcd on dedicated nodes, with events stored in a separate etcd cluster to protect the main one, and attention to the load from watches and EndpointSlices (k8s6). Monitoring: Prometheus hit memory and crash problems with their metric volume and needed tuning. Health checks: passive checks continuously watching network, disk and GPU errors (including XIDs) to cordon or drain bad nodes, and active GPU tests at boot and periodically, with nodes kept tainted until they pass — the "GPU health is a scheduling concern" pattern above. Quotas: a team-resource-manager that applied team taints so nodes were reserved per team, with tolerations on that team's pods (k8s10). Autoscaling: CPU and GPU "balloon" Deployments of low-priority pods kept the cluster autoscaler from removing idle capacity, the overprovisioning pattern of k8s11. Gang scheduling: they adopted the scheduler's Coscheduling plugin so jobs' pods start together.

The lesson is not that every ML platform should run 7,500-node clusters, but that ML on Kubernetes works by applying ordinary Kubernetes mechanisms deliberately — taints, priorities, gang admission, overprovisioning, health-driven cordoning — to scarce, failure-prone hardware, and by simplifying where the workload allows (one pod per node, no service mesh for training).

Failure modes on GPU platforms

  • Pending: Insufficient nvidia.com/gpu: no free GPUs, or the device plugin is not running on new nodes (allocatable shows 0); check the GPU Operator's pods on the node.
  • "CUDA driver version is insufficient" or no CUDA-capable device: driver/image mismatch, or the pod did not request a GPU and therefore received none.
  • Partial gangs holding GPUs: training without Kueue or coscheduling.
  • Time-sliced tenants crashing each other with out-of-memory errors: move to MIG or dedicated GPUs.
  • Slow scale-up, then latency SLO breach: cold starts dominated by node provisioning, image pull and weight download.
  • Host OOM kills in training: data-loader workers and /dev/shm (k8s10, k8s13).
  • Silent GPU degradation: XID errors, throttling or ECC errors slowing a whole job; watch DCGM and step time.

What to measure

GPUs allocated versus busy per team (Kueue admission plus DCGM), queue wait time for training jobs, preemptions and restarts, cold-start time from pod creation to Ready for serving replicas, waiting requests and time to first token per model (lm13), and node health events.

Capacity planning for GPUs

Because GPU nodes are slow and sometimes impossible to obtain on demand, capacity is planned rather than purely autoscaled: reserved or committed capacity for steady serving and scheduled training, on-demand for daily peaks, spot for interruptible batch work, and a forecast reviewed monthly against queue wait times. Treat "GPU unavailable in this zone" as a normal event the platform handles — by falling back to other zones, instance types or queues — rather than as an outage.

def place(jobs, nodes, gang):
    free = dict(nodes); placed = {j: 0 for j, _, _ in jobs}
    if gang:                                       # admit whole jobs only
        for name, pods, gpus in jobs:
            fits, trial = 0, dict(free)
            for _ in range(pods):
                n = next((k for k, v in trial.items() if v >= gpus), None)
                if n is None: break
                trial[n] -= gpus; fits += 1
            if fits == pods: free, placed[name] = trial, pods
    else:                                          # one pod at a time, interleaved
        for i in range(max(p for _, p, _ in jobs)):
            for name, pods, gpus in jobs:
                if i < pods:
                    n = next((k for k, v in free.items() if v >= gpus), None)
                    if n: free[n] -= gpus; placed[name] += 1
    return {j: f"{placed[j]}/{p} pods" for j, p, _ in jobs}

Design: a GPU platform for a 40-person ML team

The team has 32 H100 GPUs (four 8-GPU nodes) on a managed Kubernetes cluster, plus the option of on-demand and spot GPU nodes from the cloud. Workloads: about ten notebooks, nightly fine-tuning jobs of 8-16 GPUs, and three production LLM endpoints (an 8B model with steady traffic, a 70B model with business-hours traffic, and an internal summariser used a few times a day). Today everything runs as plain Deployments and Jobs requesting whole GPUs; GPUs are 30% busy on average, the 70B endpoint breaches its p95 latency every morning, and fine-tuning jobs sometimes deadlock. Propose a design.

Answer

Nodes and sharing. Label and taint GPU node pools; install the GPU Operator. Partition one H100 node with MIG (for example 7 × 1g.10gb per GPU) for notebooks and the small summariser, which removes whole GPUs held by idle notebooks; cull idle notebooks after a few hours.

Training. Install Kueue with ClusterQueues per flavour (on-demand H100, spot H100) and LocalQueues per project; submit fine-tuning as suspended Jobs or JobSets so they are admitted whole (no more deadlocks); let them borrow idle inference capacity at night through a cohort, with preemption when serving needs it back; checkpoint every N steps to object storage so spot interruptions and preemptions cost minutes, not hours; annotate running jobs do-not-disrupt against consolidation.

Serving. KServe in Standard mode with vLLM. Scale the 8B and 70B endpoints with KEDA on num_requests_waiting per replica, long scale-down windows, and minimum replicas covering baseline; for the 70B endpoint, add a scheduled scale-up before the morning ramp and keep one warm GPU node via low-priority placeholder pods. Remove the cold-start path: weights as OCI artefacts mounted with image volumes or cached on node NVMe, serving images pre-pulled, startup probes sized to load time. Run the summariser in Knative mode with scale-to-zero on a MIG slice, accepting a cold start for occasional users.

Measure. GPU hours allocated versus busy per team, queue wait for training, cold-start time per endpoint, waiting requests and time to first token. Expected outcome: higher useful utilisation from MIG and borrowing, no gang deadlocks, and the 70B morning breach removed by pre-scaling and warm capacity rather than by permanently over-provisioning.
