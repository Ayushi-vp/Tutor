A team's Python service lives in a Dockerfile that someone wrote on their first day with containers. It starts FROM python:3.12, copies the whole repository, runs pip install -r requirements.txt, and sets a command. It works. Then the costs start to show.

Every pull request takes nine minutes in CI, six of them reinstalling the same 80 dependencies, even when the change is a typo in a log message. The image is 1.6 GB; pushing it from CI takes a minute, and when the cluster scales out at 9 a.m., each new node spends forty seconds pulling it before the service can start. A security scanner reports 400 known vulnerabilities, most in packages like compilers and image libraries that the running service never uses. And one day an engineer notices that an old .env file with a database password was copied in by COPY . ., removed two lines later with RUN rm .env, and is still sitting in the published image for anyone to extract.

None of these problems is about the application. They all come from not knowing how a Dockerfile turns into an image: that each step produces a layer that only ever adds; that layers are stacked by a union file system at run time; that the builder reuses a step only if everything before it is unchanged; and that a build can have several stages, only one of which ships.

This lesson works through those mechanisms in order. It starts with what a single build step produces, then how OverlayFS combines layers when a container runs, then why deletion never shrinks an image. It then opens up the build cache and traces exactly which steps rerun when one line of code changes, introduces BuildKit's graph model and its mounts, and finishes with multi-stage builds and how to keep the cache alive on throwaway CI machines. By the end, each of the four problems above has an obvious fix, and you can predict a build's behaviour before you run it.

Transparent sheets on a projector

Think of an old overhead projector and a stack of transparent sheets. The bottom sheet has a map printed on it. The next sheet adds roads. The next adds town names. The projected image is what you see looking down through the whole stack. If you want to "remove" a town from the picture, you cannot scratch it off the lower sheet, because that sheet is shared and locked. You can only add a new sheet on top with a white patch covering it. The town is invisible on screen, but the lower sheet still has it, and anyone handed the stack can lift the patch.

An image works the same way. Each build step that touches files produces a new sheet — a layer — that records only what that step changed. When a container starts, the layers are stacked in order and the container sees the merged result through a union file system called OverlayFS. A fresh, empty, writable sheet goes on top for the container's own changes. Deleting a file from a lower layer means adding a "whiteout" patch on a higher one.

The build side: a recipe with memoised steps

Building is like following a recipe where you keep the result of every step in the fridge. Next time, if the first five steps of the recipe and their ingredients are unchanged, you take step five's result out of the fridge and continue from there. The moment one step differs — a new ingredient, a changed instruction — that step and every step after it must be done fresh, because each depends on the result before it. That is the build cache, and its "everything after the first change reruns" rule is the reason the order of lines in a Dockerfile matters so much.

Several kitchens, one dish

Finally, a build can use several kitchens. A multi-stage build prepares ingredients in a messy workshop full of tools (a builder stage with compilers), then carries only the finished parts into a clean, small kitchen (the final stage). Only the final kitchen ships. The tools never leave the workshop.

The four mechanisms, in one paragraph each

Everything in this lesson follows from four facts. Layers only add: a build step records what it changed, never what an earlier step "really" contained, so nothing can be removed from a published image after the fact. Lookup is top-down: when a container reads a path, the highest layer holding that path wins, and a whiteout counts as "not here". The cache is a chain: a step is reused only if every step before it was reused and its own inputs match. And stages are independent: a build may run many stages, but an image is assembled only from the one you ship. If you can say these four sentences and explain each with an example, you understand Docker images better than most people who use them daily.

Where the analogies break: a sheet is not a picture but a tar file of whole files, so changing one byte of a 100 MB file puts all 100 MB in a new layer; and the cache does not compare results, only inputs, so it happily serves a stale result when something outside the Dockerfile — a package repository — has changed.

1. From a Dockerfile to an image

A Dockerfile is a list of instructions. Take this small one for a Flask app:

FROM python:3.12-slim
WORKDIR /app
ENV PYTHONUNBUFFERED=1
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER 10001
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]

The instructions fall into two kinds. File-system instructions — RUN, COPY and ADD — change files and each produce a new layer. Metadata instructions — ENV, WORKDIR, USER, EXPOSE, LABEL, CMD, ENTRYPOINT — only edit the image config (the JSON document from k8s1) and add no layer. (WORKDIR creates the directory if it is missing, which BuildKit records cheaply.) FROM picks the starting point: the base image's layers and config.

So this image is the base's layers plus three new ones: the copied requirements.txt (a few hundred bytes), the installed packages (say 40 MB), and the application source. docker history shows one row per instruction, with 0B for metadata-only ones:

2. How one build step becomes a layer

For a RUN step the builder does exactly what docker run does, with one twist. It mounts the file system produced so far (all earlier layers) as read-only lower directories, puts an empty writable upper directory on top, and runs the command inside a container. When the command exits, everything the command changed is sitting in that upper directory. The builder turns the upper directory into a changeset:

  • A file that was added or modified is stored in full. There are no binary diffs: change one byte of a 100 MB file and the new layer carries the whole 100 MB file again.
  • A file that was deleted is stored as a whiteout: an empty entry named .wh.<name> in the same directory. When layers are stacked, the whiteout hides the file from lower layers.
  • A directory that was deleted and recreated is marked opaque with an entry named .wh..wh..opq, meaning "ignore this directory's contents in all lower layers".
  • Changed permissions or ownership also count as a modification, so RUN chown -R app /app on a 500 MB directory copies all 500 MB into a new layer. (COPY --chown=app sets ownership as the files arrive instead.)

The changeset is written as a tar archive, compressed (gzip by default; zstd is supported), and hashed. The hash of the compressed bytes is the layer's digest in the manifest; the hash of the uncompressed tar is its diff_id in the config (k8s1). COPY and ADD work the same way, except the "command" is placing files from the build context.

3. How layers are combined at run time

When a container starts, its root file system is an OverlayFS mount. The lowerdir option lists the unpacked image layers from top to bottom, separated by colons; upperdir is the container's empty writable directory; workdir is a scratch directory OverlayFS needs for atomic operations; and the mount point shows the merged view. os13 introduced the rules; here they are with consequences.

  • Lookup. To open /etc/app.conf, the kernel checks the upper directory, then each lower directory from the top down, and uses the first copy it finds. A whiteout in a higher layer stops the search: the file "does not exist". Lookups are cached in the kernel's directory-entry cache, so the number of layers costs almost nothing after the first access.
  • Reads of a file that is only in a lower layer go straight to that layer's file. All containers from the same image share those files, on disk and in the page cache: a hundred containers from one image read libpython3.12.so from one cached copy.
  • The first write to a lower file triggers copy-up: the whole file is copied to the upper directory, then the write is applied there. For small config files that is invisible. For a 2 GB SQLite database baked into the image, the first one-byte write copies 2 GB, blocks the writer while it does, and doubles the disk used.
  • Deletes of a lower file create a whiteout in the upper directory, so the merged view hides it.
  • Renaming a directory that lives in a lower layer either fails with EXDEV ("cross-device link"), which careful programs handle by copying, or, with the redirect_dir feature enabled, is recorded as a redirect. Some old tools break on this, a niche but real source of surprises.

The practical rule follows directly: anything a container writes heavily — databases, caches, uploads, logs written to files — belongs on a volume, which is a plain directory or block device mounted into the container that bypasses the overlay completely (k8s4, k8s9). The writable layer is for small, disposable changes.

4. Why deleting never shrinks an image

Put sections 2 and 3 together and the bloated-image trap becomes obvious. Consider:

RUN curl -fsSLo /tmp/sdk.tar.gz https://example.com/sdk-1.4.tar.gz   # layer A: +300 MB
RUN tar -xzf /tmp/sdk.tar.gz -C /opt                                  # layer B: +700 MB
RUN /opt/sdk/build-tool --out /usr/local/bin/tool                     # layer C: +20 MB
RUN rm -rf /tmp/sdk.tar.gz /opt/sdk                                   # layer D: whiteouts, ~0 MB

The merged view at the end contains only the 20 MB tool. The image contains layers A, B, C and D: about 1,020 MB, every byte of which is downloaded by every pull. Layer D did nothing but add two whiteout entries.

There are three fixes, in order of preference:

  1. Do it in another stage and copy only the result into the final stage (section 7). Nothing from the builder's layers reaches the image.
  2. Do it in one RUN step: RUN curl … && tar … && build-tool … && rm -rf /tmp/sdk.tar.gz /opt/sdk. The upper directory at the end of that step only contains the tool, so the layer is 20 MB. The cost is caching granularity: any change reruns the whole chain.
  3. Use a mount so the large files never enter the file system the layer is made from: a cache mount for downloads, a bind mount from another stage, or a secret mount for credentials (section 6).

The same mechanism leaks secrets. COPY . . that sweeps in .env or id_rsa, followed by RUN rm .env, ships the secret inside a layer. Anyone with pull access can run docker save, unpack the tar, and read each layer. The prod section has the numbers on how often this happens in public images.

5. The build cache, precisely

Building from scratch every time would be slow, so the builder stores the result of every step and reuses it when it can. The rule, from the Docker documentation, is that the builder walks the instructions in order and, for each one, looks for a cached result whose cache key matches. If none matches, the cache is invalidated and that step and all subsequent steps run again. The key is built from:

  • the parent: the cache key of the previous step (so a miss propagates to everything after it);
  • the instruction text: for RUN, the exact command string. The builder does not look at what the command would do; RUN apt-get update with the same text is a hit forever;
  • for COPY and ADD, a checksum of the files being copied: their contents and metadata such as permissions. The docs state explicitly that modification time is not part of it, so touch does not bust the cache, but any content change, mode change, or file added to or removed from the copied set does;
  • build arguments (ARG) whose values are used by the step, and the base image's digest for FROM;
  • but not the contents of secret mounts: changing a secret's value does not invalidate the cache (its ID and mount path do count).

Now trace a one-line change through two versions of a Dockerfile. The app has 80 dependencies; installing them takes 180 s; copying source takes 1 s.

StepVersion A (copy everything first)After editing app.pyVersion B (manifest first)After editing app.py
1FROM python:3.12-slimCACHEDFROM python:3.12-slimCACHED
2WORKDIR /appCACHEDWORKDIR /appCACHED
3COPY . .MISS (app.py changed)COPY requirements.txt .CACHED (file unchanged)

Same files, same commands, different order: version A rebuilds in about three minutes, version B in about a second. The general principle is to order steps from least to most frequently changing: base image, system packages, language dependencies (keyed on the lock file only), then source code.

Two more details make or break this in practice. First, the build context — the directory sent to the builder — includes everything not excluded by .dockerignore. Without one, COPY . . includes .git/, whose contents change on every commit, plus local virtual environments, caches and test output; the COPY misses even when no source file changed, and secrets like .env get swept in. A good .dockerignore lists .git, .venv, __pycache__, *.pyc, .env, node_modules, build outputs and test reports.

Second, because RUN is keyed on text only, a cached step can be stale. RUN apt-get update && apt-get install -y curl stays cached with whatever versions existed the day it first ran, including ones with known vulnerabilities. Teams rebuild on a schedule with docker build --pull --no-cache (fresh base image, no cache) or pin versions so the text changes when they want an update. And apt-get update must share a RUN with install: on its own line it is cached forever, and a later install line runs against an old package index.

6. BuildKit: builds as a graph

BuildKit has been Docker's default builder since Docker Engine 23.0 (2023). Instead of executing instructions one by one, it converts the Dockerfile into a graph of operations, where each node is a step and edges are "needs the output of". That changes three things.

Parallelism and pruning. Stages that do not depend on each other run concurrently, and stages the requested target does not need are skipped entirely. A Dockerfile with test, lint and prod stages builds only prod's dependencies when you build the default target.

Content-based cache. Cache keys are computed from the inputs as in section 5, and results are stored by content, so they can be exported to and imported from remote storage (section 8).

RUN mounts. A RUN step can mount things that are available while it runs and never become part of the layer:

# syntax=docker/dockerfile:1
# pip's download cache survives between builds but is not in the image
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# a private index token, available only to this step, never stored
RUN --mount=type=secret,id=pip_token \
    PIP_INDEX_URL="https://__token__:$(cat /run/secrets/pip_token)@pypi.example.com/simple" \
    pip install -r requirements.txt

# use source files without copying them into a layer
RUN --mount=type=bind,target=/src,source=. \
    make -C /src dist OUT=/out

The secret is supplied at build time with docker build --secret id=pip_token,src=token.txt .. Compare that with ARG PIP_TOKEN: build arguments used in RUN steps appear in the image history (docker history --no-trunc), which is why secrets must never go through ARG or ENV. One gotcha with cache mounts for apt: Debian-based images ship a docker-clean configuration that deletes downloaded packages after each install, so an apt cache mount stays empty unless that file is removed, as Docker's docs show.

7. Multi-stage builds

A multi-stage build has several FROM lines. Each starts a new stage with its own base; stages can be named with AS; a later stage can copy files out of an earlier one with COPY --from=<stage>; and only the last stage (or the one named with --target) becomes the image. Here is the Flask app rebuilt that way, for a dependency list that includes a package with a C extension that must be compiled:

# syntax=docker/dockerfile:1
FROM python:3.12 AS builder                 # full image: gcc, headers, ~1.1 GB unpacked
RUN python -m venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

FROM python:3.12-slim AS runtime            # ~132 MB unpacked, no compiler
RUN useradd --uid 10001 --no-create-home app
COPY --from=builder /opt/venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
WORKDIR /app
COPY . .
USER app
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]

The numbers: python:3.12 (amd64) is 411 MB compressed and about 1,132 MB unpacked; python:3.12-slim is 46 MB compressed and about 132 MB unpacked. The single-stage image built on the full base would be well over 1.2 GB; the multi-stage one is about 190 MB, and it contains no compiler for an attacker to use and far fewer packages for a scanner to flag. k8s3 takes the same app further down, to distroless.

The trick that makes copying a virtual environment work is that both stages use the same Python version at the same path (/usr/local/bin/python3.12 in both official images), so the venv's interpreter links and compiled extensions stay valid. Copying a venv between different base images (Debian to Alpine, which uses a different C library) breaks it.

Multi-stage builds are also how one Dockerfile serves several purposes. A test stage can extend the builder with test dependencies and run the suite; docker build --target test . builds just that, and BuildKit skips the runtime stage. A debug stage can add a shell and tools on top of the runtime stage for troubleshooting. Stages can even copy from external images: COPY --from=ghcr.io/astral-sh/uv:0.8 /uv /bin/uv pulls a single binary out of another image without inheriting anything else.

8. Keeping the cache in CI

All of the above assumes the cache from the previous build is still on the machine. On a developer laptop it is. On CI, runners are often fresh virtual machines for every job, so every build starts cold and the careful ordering buys nothing. BuildKit solves this by exporting cache to external storage and importing it next time:

docker buildx build \
  --cache-from type=registry,ref=registry.example.com/app:buildcache \
  --cache-to   type=registry,ref=registry.example.com/app:buildcache,mode=max \
  -t registry.example.com/app:1.8.3 --push .

The registry backend stores cache as a special image; there are also backends for GitHub Actions' cache service (type=gha), S3, Azure Blob and a local directory. The mode matters for multi-stage builds. With mode=min, the default, only the layers of the final image are exported, so the expensive builder stage — exactly the one you want cached — is missing next time. mode=max exports every step of every stage, at the cost of more upload and storage.

A build on a fresh runner then imports the cache metadata, finds that steps 1-4 have matching keys, downloads only the layers it needs (or none, if they are only needed as parents), and runs from the first real change. A typical result is that a nine-minute cold build becomes a one-minute warm one, which is worth more to a team than almost any other CI optimisation.

9. Reading an image's layers yourself

You do not have to guess what a build produced. docker history --no-trunc <image> lists each step with its size, and the zero-byte rows confirm which instructions only touched the config. docker save <image> -o img.tar writes the image as an OCI layout: unpack it and you find index.json, the manifest and config as JSON blobs, and one tar per layer under blobs/sha256/; tar -tvf on a layer shows exactly which files it adds, and entries named .wh.* are its deletions. Tools such as dive present the same information interactively, with the bytes each layer wastes on files later overwritten or deleted. Two minutes with these tools on your own images usually finds the biggest win: a forgotten build cache, a test fixture, a duplicated directory from a late chown, or a credential that should never have been there.

Cache keys and layer digests are different things

The build cache is keyed on inputs: parent key, instruction, file checksums. The image is identified by outputs: the digest of each layer's bytes. These come apart because a tar file records modification times, owners and ordering, and because commands like pip install write timestamps, compiled bytecode and sometimes random values into files. Rebuild the same commit on a clean machine and you get layers with identical content but different digests, so registries store them twice, nodes pull them again, and nobody can check that a published image really came from a given commit. Reproducible builds close the gap: BuildKit honours SOURCE_DATE_EPOCH for the config's timestamps and, with rewrite-timestamp=true on the image exporter, clamps file times inside layers; pinned base digests and locked dependencies remove the remaining variation. k8s3 and k8s5 build on this.

COPY --link and rebasing

Normally a layer's changeset is computed against its parent, so a new base image forces every later layer to be rebuilt and re-pushed even when the copied files are identical. COPY --link creates the layer independently of what is below it — the files are placed into an empty directory and the layer is simply stacked. BuildKit can then reuse it when the base changes, and with the right exporter settings a registry can reuse the blob without re-uploading it. The cost is that --link cannot follow symlinks in the destination path or rely on files from earlier layers, which is why it is opt-in. It is most valuable for the final "copy the app" steps on top of frequently patched base images.

Why squashing usually loses

Collapsing an image into a single layer looks attractive: no hidden deleted files, one blob. But it destroys sharing: the base OS layer that a hundred services and every node already have is now embedded in each service's unique blob, so every pull downloads it again, and every code change produces a new full-size blob. The right fix for hidden files is to not create them (stages, single-RUN cleanups, mounts), keeping a small number of well-ordered layers whose lower ones change rarely.

Layer depth and overlay limits

OverlayFS has a practical limit on how many lower directories one mount can stack, because the mount options must fit in a single page and lookups walk the stack. Docker refuses images that are too deep with a "max depth exceeded" error, a limit in the low hundreds of layers. Ordinary images never approach it; it bites generated images (one layer per file) and long chains of images built on images built on images. Distroless images show the other side: over forty small layers is perfectly normal and costs nothing measurable at run time.

ADD, remote sources and pinning

ADD does more than COPY: it extracts local tar archives automatically, and it can fetch a URL or a Git repository. Those extras are why style guides prefer COPY unless you need them: an archive silently expanding is surprising, and a remote download is a supply-chain input whose content can change while the instruction text stays the same. For remote sources, the builder downloads the content to compute the cache checksum, so a changed file does invalidate the step. Better still, pin it: ADD --checksum=sha256:<hash> https://…/tool.tar.gz /tmp/ makes the build fail if the bytes ever differ, which turns "the URL changed under us" from a mystery into an error. The same thinking applies to FROM: a tag can move, a digest cannot (k8s5).

Compression choices

Layers are gzip-compressed by default. zstd (--output type=image,compression=zstd) decompresses several times faster at similar ratios, which shortens the unpack phase that often dominates cold starts on big images, and is supported by containerd and recent registries. eStargz and SOCI (k8s1) change the layout so files can be fetched individually. The constraint is the consumers: old runtimes cannot read zstd, so multi-platform or multi-compression outputs are sometimes published side by side.

Build context size and remote builders

The builder needs the context before it can compute COPY checksums. On a remote builder (a BuildKit pod in a cluster or a cloud build service) a 2 GB context of datasets and model weights is uploaded on every build. BuildKit transfers only the files that steps actually reference and keeps a session cache, but a tight .dockerignore remains the cheapest optimisation, and large artefacts such as model weights usually belong outside the image entirely (k8s14).

The case: secrets left in image layers (RWTH Aachen, ASIA CCS 2023)

Dahlmanns and colleagues downloaded and examined 337,171 images from Docker Hub and from 8,076 private registries reachable on the internet, and searched every layer for secrets. About 8.5% of images contained at least one secret, mostly private keys and API tokens; they found 52,107 valid private keys and 3,158 distinct API secrets across 28,621 images. Active scanning then found 275,269 hosts on the internet using leaked private keys for TLS or SSH authentication. Most leaks were in images from single users, consistent with accidents rather than intent.

The mechanisms are exactly the ones in this lesson: COPY . . sweeping .env files, SSH keys and certificates into a layer because there was no .dockerignore; a key copied in to fetch private dependencies and deleted in a later step, leaving it in the earlier layer; tokens passed with ARG or ENV and recorded in the config history. The fixes are mechanical: a .dockerignore that excludes secrets by default, RUN --mount=type=secret for build-time credentials, multi-stage builds so build-time files never reach the final image, secret scanning of images in CI (Trivy and similar tools scan layers, not just the final view), and — once a secret has been pushed — revoking it, since deleting the tag does not un-publish copies already pulled.

Characteristic failure modes

  • Every build reinstalls dependencies. Volatile COPY too early, missing .dockerignore, or a cold CI runner without cache import. BuildKit's progress output shows which step first lacks CACHED.
  • Images keep growing. Downloads, package caches (/var/lib/apt/lists, ~/.cache/pip) or build tools left in layers; chown -R duplicating directories. docker history and tools like dive show bytes per layer and the files each layer adds or hides.
  • Stale or vulnerable packages despite rebuilds. Cached apt-get/apk steps and an old local base image. Rebuild on a schedule with --pull --no-cache.
  • Slow first write or disk spikes. Copy-up of large image files; move them to volumes.
  • Build works locally, fails in CI. The local build used a cached step whose command no longer works (an upstream URL moved), or the context differs because of .dockerignore or files that exist only locally.

Knobs people actually turn

The builder: a shared remote BuildKit (a long-lived builder pod or service) keeps a warm local cache across CI jobs and is often simpler than exporting cache on every run. Cache garbage collection: BuildKit prunes its cache by size and age (docker buildx prune, builder GC policy); too small a budget silently evicts the expensive steps. Cache scope: in CI, key the cache by branch with a fallback to the main branch's cache so feature branches start warm. Base-image refresh: a scheduled no-cache rebuild picks up security patches, paired with automated pull requests that bump pinned base digests. Context hygiene: a .dockerignore reviewed like code, and a CI check that fails if the build context exceeds a size budget.

What to measure

Build duration and per-step cache hit rate in CI; final image size compressed (what nodes pull) and unpacked; number and size of layers that change per release (only the top ones should); and pull time on a fresh node. Budget the image like any other resource: a 200 MB increase is a cold-start regression and should be visible in review.

    import hashlib

        print(f"  {'CACHED' if hit else 'RUN   '} {instr:42} {t:4}s")
    print("  total", total, "s")

Fix: a 1.4 GB image that rebuilds for eight minutes

A data-science team's inference service has this Dockerfile, no .dockerignore, and CI on ephemeral runners:

FROM python:3.12
COPY . /app
WORKDIR /app
RUN apt-get update
RUN apt-get install -y build-essential libgomp1
RUN pip install -r requirements.txt
RUN rm -rf /root/.cache/pip
CMD python serve.py

Builds take eight minutes on every commit and the image is 1.4 GB. List what is wrong and write the improved build.

Answer

Problems, in order of impact: (1) COPY . /app comes first, so every source change — and every commit, since .git is in the context — invalidates everything after it, including the dependency install. (2) CI runners are fresh, so even a perfect order gets no cache without --cache-from/--cache-to. (3) apt-get update is a separate, permanently cached step, so installs run against a stale index. (4) build-essential (compilers, about 250 MB) ships in the runtime image. (5) rm -rf /root/.cache/pip in its own step frees nothing; the cache is already in the previous layer. (6) Shell-form CMD makes /bin/sh PID 1, so the server never sees SIGTERM (k8s1).

# syntax=docker/dockerfile:1
FROM python:3.12 AS builder
RUN python -m venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

FROM python:3.12-slim
RUN apt-get update && apt-get install -y --no-install-recommends libgomp1 \
 && rm -rf /var/lib/apt/lists/*
COPY --from=builder /opt/venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
WORKDIR /app
COPY . .
USER 10001
CMD ["python", "serve.py"]

Add a .dockerignore (.git, .venv, __pycache__, .env, data and notebooks), and build in CI with a registry cache in mode=max so the builder stage is cached too. Expect code-only commits to rebuild in under a minute (one COPY plus push of a small top layer) and the image to drop to the slim base plus the virtual environment, a few hundred megabytes depending on the ML libraries. The full builder image (gcc, headers) never leaves CI.
