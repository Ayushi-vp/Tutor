The previous lesson explained how images are built. This one is about writing Dockerfiles that produce images you would want running in production, and the stakes are concrete.

A 1.1 GB image is not just untidy. When a cluster adds a node at 9 a.m., that node must download and unpack every byte before the first pod can start, and a single service can turn a 20-second scale-up into a two-minute one. The same image contains a full compiler toolchain, image-processing libraries, a shell, curl, a package manager and hundreds of other packages. A vulnerability scanner flags several hundred known issues in it, and the security team cannot tell which ones matter, so they all become tickets. If an attacker finds a remote-code-execution bug in the app, they find a root shell, curl to fetch their tools, and apt-get to install more.

Other problems are quieter. The image runs as root because nobody wrote USER. It stops slowly because its command is in shell form. Two builds of the same commit, a week apart, produce different images because python:3.12-slim moved and pip install picked up a new minor version of a library, so a bug appears in production that nobody can reproduce from the source tree. And when the cluster's security policy starts requiring non-root containers, half the services fail to start with a cryptic message about non-numeric users.

None of this needs exotic tools. It needs a handful of decisions made deliberately: which base image, which user, which stages, which pins, which signals. This lesson takes a real Python web service and walks it from a naive 1.1 GB image to about 85 MB, one measured step at a time, explaining what each step removes and what it costs. It then covers running as non-root properly, signals and health, debugging images with no shell, and finally reproducibility: how to make the same commit produce the same digest, which is the foundation for the supply-chain checks in k8s5.

Packing for a trip

Think of an image as a suitcase for a trip where you pay for every gram, and where anything in it can be stolen and used against you. A naive Dockerfile packs the whole wardrobe "just in case": a full operating system with compilers, editors and network tools. A good one packs what the trip needs: the runtime, the app, its libraries, certificates, and nothing else. The extra weight costs you every time the suitcase is carried (every pull), and every extra item is something a thief could use.

Four decisions do most of the work:

  1. The base. The base image is usually 90% or more of the size. Full Debian-based images include compilers; slim variants do not; distroless images keep only the runtime and drop even the shell.
  2. The stages. Anything needed to build but not to run — compilers, headers, caches, source of dependencies — lives in a builder stage and never ships (k8s2).
  3. The user and the signals. The process runs as a numeric non-root user and is PID 1 in exec form, so it can be restricted by policy and stopped cleanly (k8s1).
  4. The pins. Base image by digest, dependencies by exact version and hash, and time removed from the output, so a build can be repeated and verified.

What "good" means, in measurable terms

It helps to turn "a good Dockerfile" into numbers you can check in CI, because otherwise every review becomes a debate about taste. A reasonable set for a web service:

  • Size: compressed image size, which is what every node downloads. For a Python web service, under about 100 MB is easy; over 500 MB needs a reason (an ML framework is a reason; a compiler is not).
  • Build time on a code-only change: seconds, not minutes, because only the top layer should rebuild (k8s2).
  • Identity: the process runs as a numeric UID other than 0, which you can confirm with docker image inspect -f '{{.Config.User}}'.
  • Stop time: docker stop returns in well under the 10-second timeout, proving PID 1 handles SIGTERM.
  • Contents: the number of OS packages and known vulnerabilities reported by a scanner, and no secrets found by a secret scanner.
  • Repeatability: the base image and dependencies are pinned, and rebuilding the same commit gives the same digest.

The rest of the lesson is about moving each of these numbers in the right direction, and knowing when to stop.

Where the suitcase analogy breaks: size is not the only goal. Smaller can be slower to build (Alpine compiling native packages), harder to debug (no shell), or a different runtime (musl instead of glibc, a different Python minor version in distroless). Each step below says what it costs, so you can stop at the right one for your service.

1. The starting point, measured

Our service is a small Flask app served by gunicorn. Its requirements.txt pins flask==3.1.2 and gunicorn==23.0.0, which pull in Werkzeug, Jinja2, MarkupSafe, itsdangerous, click and blinker. Installed, those packages take about 8 MB. Here is the Dockerfile most people write first:

FROM python:3.12
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
EXPOSE 8000
CMD gunicorn -b 0.0.0.0:8000 app:app

Sizes for the bases come from the registries (amd64, October 2026): python:3.12 is 411 MB compressed across 7 layers and 1,132 MB unpacked. With the app, its dependencies and pip's download cache, the image is about 1,140 MB unpacked. Every node that runs it downloads 411 MB first. It contains gcc, make, the headers for dozens of libraries, ImageMagick's libraries, git, curl, wget, an SSH client and a full shell environment — none of which the app uses at run time. It runs as root. Its CMD is shell form, so /bin/sh is PID 1.

We will fix it in five moves and measure each.

2. Move one: pick the right base

The Docker Official Python image comes in several variants. The default tag (python:3.12, currently on Debian 13 "trixie") is built on Debian's buildpack-deps image, which deliberately includes compilers and development headers so that pip install of almost anything works. Slim (python:3.12-slim) is a minimal Debian with just what Python needs to run. Alpine (python:3.12-alpine) is built on Alpine Linux.

For our app, nothing needs compiling: every dependency has a pure-Python wheel or a prebuilt binary wheel for glibc. So the first move is one word:

FROM python:3.12-slim

Image size: 132 + 8 ≈ 140 MB unpacked, about 49 MB compressed. That is 88% smaller and roughly eight times faster to pull. The vulnerability count drops by a similar factor, because most flagged packages were the build tools.

Why not Alpine at 57 MB? Alpine uses musl instead of glibc as its C library. Python packages with native code publish prebuilt binary wheels per platform: manylinux wheels for glibc and musllinux wheels for musl. Most popular packages now publish both, but many smaller or older ones only publish manylinux, and on Alpine pip then compiles them from source, which needs gcc and headers installed and can take minutes. musl also differs at run time: its DNS resolver historically did not fall back to TCP for large responses (fixed in musl 1.2.4, Alpine 3.18), and its memory allocator is slower for some multi-threaded workloads. For Python services, slim is the safer default; Alpine is excellent for static Go binaries and simple tools.

3. Move two: multi-stage, only when something must be built

Suppose the app later adds a dependency with a C extension that has no wheel for our platform. On slim there is no compiler, so pip install fails. The wrong fix is to apt-get install build-essential in the runtime image (about 250 MB more, back toward where we started). The right fix is the multi-stage pattern from k8s2:

# syntax=docker/dockerfile:1
FROM python:3.12-slim AS builder
RUN apt-get update && apt-get install -y --no-install-recommends gcc libc6-dev \
 && rm -rf /var/lib/apt/lists/*
RUN python -m venv /opt/venv
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    /opt/venv/bin/pip install -r requirements.txt

FROM python:3.12-slim
COPY --from=builder /opt/venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
WORKDIR /app
COPY . .
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]

A measured surprise: for our dependency set, this image is bigger than the single-stage slim image, about 153 MB. The venv is 21 MB, and 13 MB of that is the copy of pip that python -m venv installs inside it, which the runtime never needs. The lesson: multi-stage pays off when the builder holds something heavy (compilers, headers, downloaded sources, caches); when it does not, it only adds tooling. Two ways to drop pip from the venv: create it with python -m venv --without-pip /opt/venv and install with pip --python /opt/venv/bin/python install … from the system pip (pip 22.3+), or use uv, which installs into a venv without putting itself there. Either gets the venv to about 8 MB and the image back to about 140 MB, now with a compiler available only at build time.

4. Move three: distroless

A distroless image, from Google's GoogleContainerTools project, keeps only what a runtime needs: for python3, the interpreter and standard library, glibc, OpenSSL, CA certificates and time-zone data. There is no shell, no package manager, no ls. Current distroless images are built from Debian 13 packages, and the Python in python3-debian13 is Debian's Python, which is 3.13. (The older python3-debian12 carries 3.11.) There is no distroless image with Python 3.12, so this move is also a Python upgrade, or a reason to stop at slim.

The second subtlety is paths. A venv records the absolute path of the interpreter that created it. The official Python images install Python at /usr/local/bin/python; distroless has it at /usr/bin/python. Copy a venv built in python:3.13-slim into distroless and its bin/python link points at a path that does not exist. Distroless's own example solves this with a symlink in the builder so the venv is created against /usr/bin/python:

# syntax=docker/dockerfile:1
FROM python:3.13-slim-trixie AS build
RUN ln -s /usr/local/bin/python /usr/bin/python \
 && /usr/bin/python -m venv /venv
COPY requirements.txt .
RUN /venv/bin/pip install --disable-pip-version-check --no-cache-dir -r requirements.txt

FROM gcr.io/distroless/python3-debian13:nonroot
COPY --from=build /venv /venv
COPY --chown=65532:65532 . /app
WORKDIR /app
ENTRYPOINT ["/venv/bin/python3", "-m", "gunicorn", "-b", "0.0.0.0:8000", "app:app"]

Size: 62 + 21 ≈ 83 MB unpacked, about 30 MB compressed (drop pip from the venv and it is about 70 MB). The :nonroot tag sets the default user to UID 65532, so the container runs unprivileged. The entrypoint must be exec form: there is no shell to interpret a shell-form command. Compared with slim, we removed about 60 MB and, more importantly, the shell, apt, perl and the rest of the base system's user-space tools, which is where most scanner findings and most attacker conveniences live.

Distroless costs you the ability to docker exec … sh. Section 7 shows how to debug without it.

5. Move four: the user, the files and the port

By default a container runs as whatever USER the image config says, and if nothing says, that is UID 0, root. Without a user namespace, container root is host root held back only by dropped capabilities and seccomp (os13). Running as an ordinary user removes a whole class of escalation paths. Doing it properly involves four details.

  1. Use a numeric UID. Kubernetes can enforce runAsNonRoot: true in a pod's securityContext. The kubelet checks the image's configured user before starting the container. If the image says USER app, the kubelet cannot know whether app is UID 0 inside the image's /etc/passwd, so it refuses to start the container, with an error saying the image has a non-numeric user and it cannot verify the user is non-root. USER 10001 (or 10001:10001) avoids this. A UID above 10000 also avoids colliding with system users on the host if a volume is shared.
  2. Own only what must be written. Files copied into the image are owned by root unless you say otherwise. If the app writes to /app/cache, create that directory owned by the app user; use COPY --chown=10001:10001 rather than a later RUN chown -R, which duplicates every file into a new layer (k8s2). Better still, keep the image read-only and write to a mounted volume or emptyDir.
  3. Listen above 1024. Binding ports below 1024 traditionally requires root or CAP_NET_BIND_SERVICE. The app listens on 8000; a Kubernetes Service or Docker's -p 80:8000 maps the public port.
  4. Make the root file system read-only when the app allows it: docker run --read-only --tmpfs /tmp, or readOnlyRootFilesystem: true in Kubernetes with an emptyDir mounted at /tmp. An attacker cannot drop files into the image's directories, and accidental writes to the writable layer (k8s2's copy-up costs) become visible errors.

The Kubernetes side, for reference (k8s10 returns to security contexts):

securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }

6. Move five: signals, health and runtime settings

k8s1 explained why PID 1 matters. In Dockerfile terms:

  • Write ENTRYPOINT and CMD in exec form, as JSON arrays. Shell form (CMD gunicorn …) runs /bin/sh -c, which becomes PID 1 and does not forward SIGTERM; in distroless it fails outright because there is no /bin/sh.
  • If you need a startup script, end it with exec "$@" or exec gunicorn … so the server replaces the shell.
  • If the app spawns child processes and does not reap them, add a tiny init (tini, or docker run --init; in Kubernetes, shareProcessNamespace makes the pause container reap). Gunicorn manages its own workers and does not need one.
  • ENTRYPOINT vs CMD: the entrypoint is the program, CMD its default arguments. docker run image --workers 8 replaces CMD; in Kubernetes, command replaces ENTRYPOINT and args replaces CMD.

The Dockerfile HEALTHCHECK instruction makes plain Docker mark a container unhealthy when a command fails, but Kubernetes ignores it; it uses liveness, readiness and startup probes defined in the pod (sc15, k8s13). For Python, two environment variables are standard: PYTHONUNBUFFERED=1 so log lines appear immediately rather than sitting in a buffer when the process is killed, and PYTHONDONTWRITEBYTECODE=1 so the app does not try to write .pyc files into a read-only image at run time. Size worker counts from the container's CPU limit, not the node's core count (os13).

7. Debugging images that have no shell

The objection to distroless is "how do I look inside?" Three answers. First, design for it: logs to stdout, metrics, and a status endpoint answer most questions without a shell. Second, in Kubernetes, ephemeral containers attach a temporary container with a tools image to a running pod:

kubectl debug -it pod/web-7d9f -c debugger --image=busybox:1.37 --target=web
# inside: ps shows the app's processes; its files are at /proc/1/root/app

--target joins the app container's process namespace, so you can see and signal its processes and read its file system through /proc/<pid>/root. Third, distroless publishes :debug tags of every image, with a BusyBox shell, for use in development or a one-off copy of a pod (kubectl debug --copy-to with --set-image). On a node, nsenter into the process's namespaces works for any image (k8s1).

8. Pin everything

"It built yesterday" is not good enough for production. A Dockerfile has several inputs that move unless you pin them:

  • The base image. python:3.12-slim is a tag, and the publisher rebuilds it whenever Debian or Python ships fixes — often several times a month. Pin the digest: FROM python:3.12-slim@sha256:<digest>. The tag part becomes documentation; the digest decides. Then let a bot (Renovate, Dependabot) open pull requests that bump the digest, so you get patches on purpose, tested by CI.
  • Language dependencies. Pin exact versions of the whole dependency tree in a lock file (pip-compile, uv lock, Poetry), ideally with hashes and pip install --require-hashes, so a compromised or re-uploaded package fails the build instead of entering it.
  • OS packages. apt-get install curl gets whatever version is current. Pin versions where it matters, or install from a dated snapshot of the Debian archive.
  • Tools. The # syntax=docker/dockerfile:1 line picks the Dockerfile frontend version; pin it to a minor version if you need stability. Pin binaries copied from other images (COPY --from=ghcr.io/astral-sh/uv:0.8.17, or better, by digest).

9. Reproducible builds

Pinning makes the inputs stable. A reproducible build goes further: the same inputs produce bit-for-bit identical outputs, and therefore the same image digest, on any machine at any time. Two things normally prevent that, as k8s2 noted: time (the image config's created fields, and file modification times inside every layer) and nondeterminism in tools (file ordering, embedded paths, random seeds).

BuildKit's tools for this:

  • SOURCE_DATE_EPOCH, a Unix timestamp passed as a build argument or picked up from the environment by Buildx (0.10+). BuildKit uses it for the created timestamp in the image config and its history entries, and for the image index's created annotation. Set it to the commit time: SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct).
  • rewrite-timestamp=true on the image exporter (BuildKit 0.13+) clamps file modification times inside layers to that value: --output type=image,name=…,push=true,rewrite-timestamp=true.
  • Tool flags for the rest: pip install --no-compile or deterministic bytecode (SOURCE_DATE_EPOCH also makes Python's compileall use hash-based .pyc files), sorted file lists, no embedded build paths.

Why bother? Because a reproducible image can be verified: a second, independent builder rebuilds from the same commit and checks that the digests match, which proves the published image came from that source and nothing was injected in CI. That is a requirement at the highest levels of supply-chain frameworks like SLSA (k8s5). There are smaller wins too: unchanged layers keep the same digest across rebuilds, so registries and nodes do not store or pull them again.

10. The finished Dockerfile, annotated

# syntax=docker/dockerfile:1
# --- build stage: has a compiler, never ships ---
FROM python:3.13-slim-trixie@sha256:<digest> AS build
RUN apt-get update \
 && apt-get install -y --no-install-recommends gcc libc6-dev \
 && rm -rf /var/lib/apt/lists/* \
 && ln -s /usr/local/bin/python /usr/bin/python \
 && /usr/bin/python -m venv --without-pip /venv
COPY requirements.lock .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip --python /venv/bin/python install --require-hashes --no-compile -r requirements.lock

# --- runtime stage: interpreter + venv + app ---
FROM gcr.io/distroless/python3-debian13:nonroot@sha256:<digest>
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
COPY --from=build /venv /venv
COPY --chown=65532:65532 app/ /app/
WORKDIR /app
USER 65532:65532
EXPOSE 8000
ENTRYPOINT ["/venv/bin/python3", "-m", "gunicorn", "-b", "0.0.0.0:8000", "app:app"]

Every decision in it maps to a section above: two stages so the compiler stays behind; digests on both bases; a hashed lock file; a venv without pip; a numeric non-root user; exec-form entrypoint; no shell to fall back on. With a .dockerignore and the cache settings from k8s2, it builds in seconds on a code change and produces an image of roughly 70 MB.

11. A review checklist, with the reason for each item

When reviewing someone else's Dockerfile, walk it top to bottom with a handful of questions, each tied to a mechanism from this lesson or the last. Is the base the smallest that works, and is it pinned by digest? The base dominates size, vulnerability count and reproducibility. Does anything that is only needed to build — compilers, headers, package caches, source of dependencies — reach the final stage? If so, it belongs in a builder stage. Are dependency manifests copied and installed before the source code? Otherwise every code change reinstalls everything. Is there a .dockerignore, and does it exclude .git, local environments and secrets? Do any secrets pass through ARG, ENV or a COPY? They must use secret mounts instead. Is USER numeric and non-zero, and can the app run with a read-only root file system? Are CMD and ENTRYPOINT in exec form, and does the program handle SIGTERM? Are package installs and cleanups in the same RUN? And finally, could two people build this commit and get the same digest?

Most of these can be automated: a linter catches shell form, unpinned bases and missing cleanups; a scanner catches secrets and known vulnerabilities; a CI job can compare image size against a budget and fail the build when it grows. What remains for the human reviewer is judgement — whether a dependency is needed at all, whether a smaller base fits this workload, whether the trade-off between debuggability and attack surface is right for this service. The review is quicker and kinder when it cites the reason, not just the rule: "this COPY . . before the install means every code change reinstalls 80 packages" persuades where "move this line" does not.

What scanners count, and why the number misleads

Image scanners such as Trivy or Grype read the package database inside the image (dpkg's status file, Alpine's apk database, Python's installed-package metadata) and match package versions against vulnerability databases. They therefore report every vulnerable package present, whether or not anything loads it. That is why moving from python:3.12 to slim can drop findings by an order of magnitude without changing the app, and why distroless images, which have very few packages, report so few. It also explains two blind spots: a binary copied in without package metadata (a static Go tool from another stage) is invisible unless the scanner inspects binaries, and Alpine packages are tracked in a different advisory database than Debian's, so counts are not comparable across bases. Reachability analysis and VEX (Vulnerability Exploitability eXchange) statements, which record "this CVE is present but not exploitable here", are the mature way to triage what remains.

Why distroless has no shell, and what that does to an attack

Most real exploitation chains after initial code execution are "living off the land": spawn /bin/sh, use curl or wget to fetch a second stage, chmod +x it, run it. In a distroless image with a read-only root file system and a non-root user, every step fails: there is no shell to spawn, no downloader, no writable executable location. An attacker with a Python-level code execution can still do damage in-process, so this is defence in depth rather than prevention, but it turns many commodity exploits into crashes. This is also why the debug variants and ephemeral containers exist: the shell is something you bring temporarily, not something the image carries.

Static binaries and scratch

For languages that compile to static binaries (Go with CGO_ENABLED=0, Rust with the musl target), the final stage can be FROM scratch, an empty image, or distroless/static at about 3 MB, which adds CA certificates, /etc/passwd entries for nonroot, and time-zone data. Those three are what a bare scratch image most often lacks: TLS connections fail with certificate errors, user lookups fail, and time zones silently become UTC. A dynamically linked binary in scratch fails with a confusing "no such file or directory", because the missing file is the dynamic loader, not the binary.

User namespaces versus non-root images

A non-root image protects you even on hosts without user namespaces. User namespaces (k8s1 deep) protect you even when an image insists on root, by mapping container UID 0 to an unprivileged host UID. They are complementary: the image author controls one, the platform the other. File ownership is the friction point: with user namespaces, volumes must be mounted with ID-mapped mounts so the container's UID 0 can write its files; with a fixed non-root UID, volumes need fsGroup or matching ownership. Platforms that mandate both get the strongest boundary.

Base image freshness as a metric

A pinned digest is only safe if it is updated. Mature platforms track the age of the base image in every running workload and alert past a threshold (for example 30 days), automate digest bumps through pull requests with tests, and rebuild all images when a critical base vulnerability lands. The counter-intuitive result is that teams who pin strictly patch faster than teams who float tags, because updates are visible, reviewable and automated instead of accidental side effects of an unrelated rebuild.

Labels and provenance metadata

Images can carry labels, and the OCI image spec defines standard annotation keys such as org.opencontainers.image.source (the repository URL), org.opencontainers.image.revision (the commit) and org.opencontainers.image.version. They cost nothing and answer the first question in every incident — "what code is this?" — directly from the running image. Registries such as GitHub's use the source label to link packages to repositories. They are not a security control, since anyone can write any label, which is why signed provenance attestations exist (k8s5); labels are for humans and tooling, attestations are for verification.

Language-specific traps

JVM images should rely on container awareness (on by default since JDK 10) and set -XX:MaxRAMPercentage rather than -Xmx from the node size. Node.js images should run node directly, not npm start, which adds a process layer that swallows signals. Python images should avoid leaving pip, setuptools and wheel in the runtime venv when they are not needed, and should not compile bytecode at import time into a read-only file system. Each of these is the same lesson — know what PID 1 is, what is installed, and what writes where — applied to a runtime.

Measuring before and after

Every move in this lesson should be checked with numbers rather than assumed: compressed size from the registry (what nodes pull), unpacked size, the count of OS packages and known vulnerabilities, cold-pull time on a fresh node, and container start time to readiness. Keep them in the pull request that changes the Dockerfile. It turns "distroless is better" into "this change removed 58 MB, 140 packages and 31 known CVEs, and cut cold start by 9 seconds", which is both a better engineering record and a better interview story.

The case: Google's distroless Python example

The distroless project's own python3-requirements example is worth reading line by line, because it encodes several of this lesson's points in eleven lines. It builds in python:3.13-slim-trixie — matching Debian 13 and Python 3.13, the same release and version as the python3-debian13 runtime. It installs gcc and libc6-dev only in the build stage, with --no-install-recommends. It creates a symlink from /usr/bin/python to /usr/local/bin/python before creating the venv, with a comment explaining that the runtime image has Python at /usr/bin/python, so the venv must record that path. It installs requirements in a separate stage (build-venv) so that layer is rebuilt only when requirements.txt changes. And it ends with an exec-form ENTRYPOINT that calls the venv's interpreter directly. Teams that copy only the last line and skip the symlink get a container that exits immediately with "no such file or directory" for /venv/bin/python3 — the venv's interpreter link points at a path that does not exist in distroless.

Failure modes you will meet

  • "container has runAsNonRoot and image has non-numeric user": the image uses a user name. Use a numeric USER or set runAsUser.
  • Permission denied at start after moving to non-root: the app writes to a directory owned by root (a cache, uploads, a PID file). Create it with the right owner via COPY --chown or mount an emptyDir.
  • Exits immediately with "no such file or directory" in distroless or scratch: a shell-form command, a script with a #!/bin/sh line, a venv pointing at the wrong interpreter path, or a dynamically linked binary without its loader.
  • TLS errors in a tiny image: missing CA certificates (scratch), or a base whose certificate bundle is years old because the digest was pinned and never updated.
  • Alpine builds take ten minutes: pip compiling native packages without musllinux wheels. Use slim, or a builder stage with wheels cached.
  • Intermittent DNS failures on old Alpine: musl before 1.2.4 did not retry over TCP for truncated responses, which bit services resolving names with many records. Upgrade the base.

Rolling out a base change safely

Switching a fleet from full to slim, or from slim to distroless, is a production change, not a cosmetic one. Things that existed only by accident disappear: a shell that an init script used, curl called by a health check, a time-zone database, locale data that changed string sorting, a CA bundle path. Roll the new base out like any other release: build both images in CI for a while, run the integration suite against the new one, canary it (swe9), and compare error rates and latency before switching everything.

Guardrails that keep Dockerfiles good

Lint every Dockerfile in CI with hadolint (it flags unpinned bases, shell-form commands, apt-get without cleanup, missing USER, ADD for local files and more). Scan images for vulnerabilities and secrets before push. Fail the build if the compressed size grows beyond a budget. Enforce at deploy time with Kubernetes Pod Security Admission at the restricted level, which rejects pods that run as root, allow privilege escalation or keep capabilities. Measure pull time on fresh nodes and base-image age across the fleet. These checks catch regressions that review misses, because nobody notices a 300 MB layer in a diff.

issues, seen_install, seen_copy_all, user = [], False, False, None
for i, l in enumerate(lines, 1):
    op, _, rest = l.partition(" "); op = op.upper()
    if op == "FROM" and "@sha256:" not in rest:
        issues.append(f"{i}: base not pinned by digest: {rest}")
    if op == "FROM" and re.search(r":latest\b|^[^:@ ]+(\s|$)", rest):
        issues.append(f"{i}: floating tag (latest or none)")
    if op in ("CMD", "ENTRYPOINT") and not rest.startswith("["):
        issues.append(f"{i}: shell-form {op}: PID 1 will be /bin/sh")
    if op == "RUN" and re.fullmatch(r"apt-get update\s*", rest):
        issues.append(f"{i}: apt-get update in its own RUN is cached forever")
    if op == "COPY" and re.match(r"(--\S+\s+)*\.\s", rest) and not seen_install:
        seen_copy_all = True
    if op == "RUN" and "install" in rest and seen_copy_all:
        issues.append(f"{i}: dependency install after COPY . . : any code change reruns it")
    if op == "RUN" and "install" in rest:
        seen_install = True
    if op in ("ARG", "ENV") and re.search(r"(?i)(token|secret|password|key)\b", rest):
        issues.append(f"{i}: possible secret in {op}: visible in image history")
    if op == "USER":
        user = rest.split(":")[0]
if user is None or user in ("0", "root"):
    issues.append("no non-root USER")
elif not user.isdigit():
    issues.append(f"USER {user} is not numeric: runAsNonRoot cannot verify it")
print(json.dumps(issues, indent=1) if issues else "clean")
    Expect five or six issues on the naive file and none (or only the digest warning if you left <digest> placeholders) on the final one. Real projects use hadolint; this shows what it checks and why.
Review: a Dockerfile in a pull request

A colleague opens a pull request with this Dockerfile for a new internal API. The platform runs Kubernetes with the restricted Pod Security Standard. Review it: what will fail, what is risky, and what would you ask them to change?

FROM python:3.12-alpine
ARG PYPI_TOKEN
ENV PIP_INDEX_URL=https://__token__:${PYPI_TOKEN}@pypi.internal/simple
RUN apk add --no-cache gcc musl-dev libffi-dev
COPY . /srv
RUN pip install -r /srv/requirements.txt
RUN adduser -D api
USER api
HEALTHCHECK CMD wget -qO- localhost:8080/health || exit 1
CMD cd /srv && uvicorn main:app --host 0.0.0.0 --port 8080
Answer

Will fail: USER api is a name, so a pod with runAsNonRoot: true (required by the restricted standard) is rejected because the kubelet cannot verify it. Security: the private index token is in ENV, so it is in the image config and visible to anyone who can pull the image, forever; it must move to RUN --mount=type=secret and the existing token must be revoked. The compiler and headers ship in the runtime image. Behaviour: shell-form CMD makes /bin/sh PID 1, so SIGTERM never reaches uvicorn and every rollout waits the full grace period. HEALTHCHECK is ignored by Kubernetes; they need readiness and liveness probes in the manifest. Build: COPY . /srv before pip install reruns the install on every change, and with no .dockerignore it may copy .env files. Alpine plus gcc suggests dependencies without musllinux wheels, which will compile slowly.

Ask for: a python:3.12-slim base pinned by digest; a builder stage with the secret mount and compiler that creates a venv; a runtime stage copying the venv; COPY --chown=10001:10001 of the source after the dependency layer; USER 10001; exec-form CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"] with WORKDIR /srv; probes in the Deployment; and a .dockerignore.
