A developer containerises a web API and a Postgres database on a laptop. The API cannot connect: it is configured for localhost:5432, which worked when both ran directly on the laptop. They try 172.17.0.2, which works until the database container is recreated and gets a different address. They publish the database port with -p 5432:5432 to "make it reachable", which works — and also makes the database reachable from the coffee shop's Wi-Fi, because the laptop's firewall never sees the traffic. They restart everything the next morning and all the data is gone.

In production the problems look different but come from the same place. A team runs containers on cloud VMs with ufw blocking everything except SSH, and later discovers their Redis was open to the internet for months because published container ports bypass ufw. Another team sees HTTPS calls from containers hang on one cloud while working on another, which turns out to be a packet-size mismatch between the VM network and the container bridge. A third finds their database running ten times slower in a container than outside it, because the data was being written into the container's writable layer.

Every one of these is explained by a few mechanisms that Docker sets up quietly: a network namespace per container joined to the host by a virtual cable and a virtual switch; address translation rules that rewrite packets on their way in and out; an embedded DNS server that only some networks get; and three kinds of mounts that put data outside the container's disposable layer.

This lesson builds those mechanisms from the bottom. It starts with how a single container gets an IP address, follows a packet to a published port and back with every rewrite shown, explains container-to-container naming, compares the network drivers, then turns to storage — bind mounts, volumes and tmpfs — and finishes by putting a three-service application together in Docker Compose. Kubernetes networking (k8s8) and storage (k8s9) build directly on these ideas, so the time spent here pays off twice.

Flats, a corridor switch and a front desk

Picture a building of flats. Each flat (a container) has its own phone line with its own internal number (a private IP address such as 172.17.0.2); nobody outside the building can dial it directly. All the lines run to a switchboard in the corridor (a bridge, docker0), so flats can call each other. The building has one public phone number (the host's IP). When someone outside calls the public number and asks for extension 8080, the front desk (the host's NAT rules) has a note: "extension 8080 goes to flat 2, port 80". It connects the call and remembers it, so the reply goes back through the same desk. When a flat calls out, the desk makes the call from the building's public number, so the world never sees the private ones.

That is almost exactly how Docker's default networking works:

  • Each container gets a network namespace (os13): its own interfaces, routes, firewall rules and ports. Its localhost is its own.
  • A veth pair — two virtual network interfaces wired back to back — links the namespace to the host. One end is eth0 inside the container; the other is plugged into the docker0 bridge on the host.
  • NAT rules in the host's firewall rewrite addresses: outgoing traffic leaves as the host's IP (masquerade), and incoming traffic to a published port is redirected to the right container (DNAT).
  • On networks you create yourself, an embedded DNS server lets containers find each other by name instead of by address.

Notice what the picture does not contain: no virtual network card emulated in software, no second operating system's network stack, no tunnel. Every box is an ordinary kernel object — a namespace, an interface, a bridge, a firewall rule — that you can list with standard Linux tools. That is why container networking is fast, and why debugging it is mostly a matter of knowing which object to look at.

Storage, in the same picture

The container's own files live in its writable layer, which is slow for heavy writes (copy-up, k8s2) and deleted with the container. To keep data, or to share it with the host, you mount something into the container at a path: a host directory (a bind mount), a Docker-managed directory (a named volume), or a piece of memory (tmpfs). In the flats analogy, that is a storage unit outside the flat, reached through a door in the wall: if the flat is demolished and rebuilt, the storage unit is still there.

And Compose ties it together

Docker Compose describes a multi-container application in one YAML file: which images, which networks, which volumes, which ports, in which order to start. docker compose up turns that description into exactly the namespaces, bridges, NAT rules and mounts described above. Where the analogy breaks: NAT and bridges cost almost nothing per packet, unlike a human front desk, but they do change addresses — and anything that depends on seeing the original address or on the host firewall's view of traffic has to account for that.

1. One container's network, built by hand

When Docker starts a container on the default bridge network, it does the following, which you could reproduce with the ip command:

  1. Create a new network namespace. Inside it there is only a loopback interface, lo, which is down.
  2. Create a veth pair, for example vethab12cd and its peer. A frame sent into one end comes out of the other, like a cable.
  3. Move the peer into the container's namespace and rename it eth0. Leave the other end in the host namespace and attach it to the bridge docker0.
  4. Assign eth0 an address from the bridge's subnet. Docker's IP address manager (IPAM) picks the next free one: on a default install the subnet is usually 172.17.0.0/16, the bridge itself has 172.17.0.1, and the first container gets 172.17.0.2.
  5. Add a default route inside the container: default via 172.17.0.1 dev eth0. Bring up lo and eth0.
  6. Write /etc/resolv.conf, /etc/hosts and /etc/hostname for the container (k8s1's bind-mounted files).

A Linux bridge is a software switch in the kernel. It learns which MAC address is behind which attached interface and forwards Ethernet frames between them, so two containers on docker0 talk to each other directly at layer 2, never leaving the host. The bridge also has an IP address (172.17.0.1), which makes the host a router for the containers: packets for anywhere else go to the bridge, and the host decides what to do with them.

2. Getting out: masquerade

Container addresses like 172.17.0.2 are private; nothing on the internet can route back to them. So when a container connects out, the host rewrites the source address. The host must have IP forwarding enabled (Docker turns it on), and Docker adds a rule to the nat table's POSTROUTING chain that says, in effect, "packets from 172.17.0.0/16 leaving by any interface other than docker0: MASQUERADE". Masquerade is source NAT to whatever address the outgoing interface has.

Trace a container fetching a web page:

WhereSourceDestinationWhat happened
Leaves container eth0172.17.0.2:4031293.184.215.14:443Normal connect()
Leaves host eth0198.51.100.10:4031293.184.215.14:443MASQUERADE; conntrack records the mapping

The bookkeeping is done by conntrack, the kernel's connection-tracking table. NAT rules are consulted only for the first packet of a flow; conntrack records the translation and applies it, in both directions, to every later packet. (If the source port is already in use on the host, the kernel picks a different one and records that too.) You can see these entries with conntrack -L.

3. Getting in: a published port, packet by packet

Now the reverse. The container runs nginx on port 80 and was started with -p 8080:80. A client at 203.0.113.5 connects to 198.51.100.10:8080. Docker has added a DNAT rule (destination NAT) to its DOCKER chain in the nat table: TCP to port 8080 on any local address, not arriving from docker0, has its destination changed to 172.17.0.2:80. It has also added a rule to its filter chains to accept forwarded traffic to 172.17.0.2:80 on docker0.

  1. SYN arrives at the host's eth0: 203.0.113.5:51000 → 198.51.100.10:8080.
  2. PREROUTING (nat). Before any routing decision, the packet passes Docker's DOCKER chain, which matches port 8080 and rewrites the destination: now 203.0.113.5:51000 → 172.17.0.2:80. conntrack creates an entry recording both versions.
  3. Routing. The destination is no longer a local address but one on the docker0 subnet, so the kernel will forward the packet rather than deliver it to a local socket. This is the key fact: the packet never passes through the INPUT chain.
  4. FORWARD (filter). The packet passes DOCKER-USER (empty unless an administrator added rules), then Docker's forwarding chains, which accept it because the port is published.
  5. Delivery. Out of docker0, through the veth pair, into the container's eth0. nginx's listening socket on port 80 accepts it. Note that nginx sees the client's real address 203.0.113.5.
  6. Reply. nginx answers 172.17.0.2:80 → 203.0.113.5:51000. On the way out of the host, conntrack recognises the flow and rewrites the source back to 198.51.100.10:8080, so the client sees a reply from the address it called.

Two consequences matter in practice. First, published ports bypass the host firewall's INPUT rules. Tools like ufw and many hand-written firewalls filter INPUT, because that is where traffic for the host's own services goes. Container traffic goes through FORWARD instead, where Docker's rules accept it. Docker's documentation says plainly that Docker and ufw are incompatible in this way. Second, by default -p 8080:80 publishes on all host addresses (0.0.0.0 and [::]), and Docker's docs call that "insecure by default". Write -p 127.0.0.1:8080:80 when only the host itself should connect, and put filtering for container traffic in the DOCKER-USER chain, which Docker creates, evaluates first and never modifies.

Two more details. Traffic from the host to its own published port (curl localhost:8080) does not come in through PREROUTING on eth0, so Docker also handles it — historically with a small user-space forwarder, docker-proxy, which is still enabled by default for cases NAT cannot cover. And Docker 28.0 tightened a long-standing gap: in older releases, hosts on the same local network segment could reach ports published only to the Docker host's localhost; from 28.0 that is blocked by default.

4. Names: the embedded DNS server

Container IPs change whenever a container is recreated, so applications should use names. Here the default bridge is a trap: containers on docker0 get the host's DNS settings and no way to resolve each other's names (except the legacy --link flag). On a user-defined network (docker network create appnet), Docker provides an embedded DNS server. Inside each container, /etc/resolv.conf says nameserver 127.0.0.11, and Docker intercepts queries to that address in the container's namespace:

  • A query for another container's name or network alias on the same network is answered with its current IP, for example db → 172.18.0.3.
  • Anything else is forwarded to the host's upstream resolvers.

User-defined networks also isolate: containers on appnet cannot reach containers on another user-defined network unless connected to both. The default bridge connects every container that did not ask for a network, which is why Docker's docs recommend user-defined networks for anything real. Each one gets its own bridge (br-<id>) and subnet (often 172.18.0.0/16, 172.19.0.0/16 and so on).

5. The other network drivers

The bridge driver is the default, but Docker has others, each a different trade-off between isolation, performance and reach.

Host networking deserves a note because Kubernetes uses it too (hostNetwork: true): the container shares the host's interfaces and port space, so there is no NAT, no veth hop and no port mapping, and also no isolation. It is the choice for network plugins, node monitoring agents and occasionally extreme-throughput services. Kubernetes networking (k8s8) replaces Docker's bridge-plus-NAT model with a flat one in which every pod has a routable IP; the veth pair per pod survives, the per-host NAT for incoming traffic does not.

6. Container to container, and across networks

Put the pieces together and trace the Compose-style case: an api container (172.18.0.4) calls a db container (172.18.0.3) on the same user-defined network appnet, whose bridge is br-7a1c with gateway 172.18.0.1.

  1. The app resolves db: its resolver sends a query to 127.0.0.11, Docker's embedded DNS server answers 172.18.0.3.
  2. The kernel in api's namespace sees that 172.18.0.3 is on the directly connected subnet of eth0, so it sends an ARP request ("who has 172.18.0.3?") out of eth0. The frame crosses the veth pair to the bridge, which floods it to its ports; db's eth0 answers with its MAC address.
  3. The SYN goes from api's eth0, through its veth, across the bridge (which has now learned which port leads to which MAC), through db's veth, to db's eth0. No NAT, no published port, no routing through the host's IP stack beyond the bridge's forwarding (bridged traffic can still be filtered by iptables when the br_netfilter module is loaded, which Docker relies on for isolation rules).
  4. Postgres sees the real source address 172.18.0.4, so its access rules can match on the network's subnet.

Two containers on different user-defined networks cannot talk at all: Docker installs isolation rules that drop traffic between its bridges. To let a container reach both, connect it to both networks (docker network connect); it then gets an interface and an address on each. This is how a reverse proxy can sit on a "frontend" network with published ports and also on a "backend" network with the databases, while the databases have no route to the outside at all — a small-scale version of the network segmentation that Kubernetes NetworkPolicy provides (k8s8).

The default bridge has one more legacy knob: inter-container communication (icc) can be disabled daemon-wide, so containers on docker0 cannot reach each other except through published ports. User-defined networks make that unnecessary, because isolation is the default between them and sharing is explicit.

7. Storage: three kinds of mounts

Everything a container writes to its own file system goes to its writable layer: slowed by copy-up, tied to that container, deleted with it (k8s2). Data that must persist, be shared, or be written heavily goes into a mount instead. All three kinds bypass OverlayFS entirely, so I/O runs at the speed of the underlying file system.

Bind mounts map an existing host path: -v ~/code/api:/src or --mount type=bind,src=…,dst=/src. The container sees the host's files, with the host's ownership and permissions, and anything the image had at /src is hidden while the mount is in place. They are perfect for development (edit on the host, the container reloads) and for host resources like /var/run/docker.sock (dangerous: whoever has the socket controls Docker, which means root on the host). Their weakness is that they depend on the host's directory layout and user IDs; a container running as UID 10001 writing into a directory owned by your laptop user gets "permission denied". On Docker Desktop, bind mounts cross the VM boundary and are slower; on Windows with WSL 2, keep source inside the Linux file system for speed.

Named volumes are created and managed by Docker: -v pgdata:/var/lib/postgresql/data. By default they are directories under /var/lib/docker/volumes/pgdata/_data, owned by Docker, independent of any container. Two behaviours set them apart. If a new, empty volume is mounted at a path where the image has files, Docker copies the image's files into the volume first, so a database image's default configuration or ownership is preserved. And volume drivers can put the data elsewhere — NFS, cloud block storage — without changing the container. Volumes survive docker rm and docker compose down, and are deleted only by docker volume rm or docker compose down -v.

tmpfs mounts (--tmpfs /tmp:size=64m) are backed by memory and vanish when the container stops. They are ideal for scratch files and for secrets you do not want on disk, and they are the usual companion to a read-only root file system (k8s3). Their contents count toward the container's memory limit.

A worked comparison: Postgres writing 2 GB of data. In the writable layer, every write goes through OverlayFS, the first write to each preexisting file copies it up, and removing the container loses everything. In a named volume, writes go straight to the host's ext4 or XFS at native speed, and the data survives upgrades of the Postgres container. That is the difference between the "ten times slower" team in the opening and a normal one.

8. Docker Compose: the whole app in one file

Running three containers with the right networks, volumes, environment and ordering by hand is tedious and error-prone. Docker Compose describes it declaratively in a Compose file (compose.yaml), following the open Compose Specification, and the docker compose command creates, updates and removes it. (The old top-level version: key is obsolete and ignored.)

services:
  api:
    build: .
    ports: ["127.0.0.1:8000:8000"]          # host-only
    environment:
      DATABASE_URL: postgresql://app:app@db:5432/app
      REDIS_URL: redis://cache:6379/0
    depends_on:
      db:    { condition: service_healthy }
      cache: { condition: service_started }
  db:
    image: postgres:17
    environment: { POSTGRES_USER: app, POSTGRES_PASSWORD: app, POSTGRES_DB: app }
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      retries: 10
  cache:
    image: redis:8
volumes:
  pgdata: {}

What docker compose up does with this, in terms of everything above, for a project directory named shop:

  1. Creates a user-defined bridge network shop_default (for example 172.18.0.0/16) and a named volume shop_pgdata. The project name prefixes everything, so two projects on one host do not collide.
  2. Builds the api image from the Dockerfile in . and pulls postgres:17 and redis:8.
  3. Starts db and cache first, because api depends on them. Each joins shop_default with its service name as a DNS alias. db mounts shop_pgdata; because the volume is new and empty, Docker copies the image's files at that path into it first.
  4. Runs db's healthcheck every 5 s until pg_isready succeeds, marking the container healthy. Only then starts api, because its dependency on db has condition: service_healthy; for cache it only waits for the container to start.
  5. Starts api with the environment shown. When it connects to db:5432, its resolver asks 127.0.0.11, which answers with db's current IP on shop_default. Port 8000 is published on 127.0.0.1 only, via the DNAT path from section 3.

Three Compose features are worth knowing beyond the basics. Healthchecks with depends_on conditions give a safe start order — but they only cover start-up, so apps should still retry connections, because a database can restart later. Profiles mark optional services (an admin UI, a load generator) that start only when asked for with --profile. And docker compose watch syncs source changes into running containers or rebuilds them, for a fast development loop without bind-mount permission problems. docker compose down removes containers and the network but keeps named volumes; down -v removes those too.

Compose is a single-host tool. It is the right tool for development, tests in CI and small deployments; it has no scheduler across machines, no self-healing beyond restart policies, and no rolling updates. Those are what Kubernetes adds, and its concepts map closely: services become Deployments, service names become Service DNS names, named volumes become PersistentVolumeClaims, healthchecks become probes.

9. A worked debugging session: no internet from a container

Put the mechanisms to work on a common report: "pip install works on the host but times out inside the container." Check in the order the packet travels. Inside the container, ip route should show a default route via the bridge gateway (172.17.0.1); cat /etc/resolv.conf shows which resolver it uses. ping -c1 1.1.1.1 tests routing without DNS; getent hosts pypi.org tests DNS without HTTP. If IP works but names do not, the host's resolver is a local stub the container cannot reach (deep section), or a corporate DNS is unreachable from the bridge. If nothing leaves at all, look on the host: is IP forwarding on (sysctl net.ipv4.ip_forward must be 1)? Does iptables -t nat -L POSTROUTING -n -v show the masquerade rule for 172.17.0.0/16, and do its counters increase when you retry? Has a firewall tool flushed Docker's rules (restarting Docker recreates them)? Does the bridge subnet overlap a VPN route, sending replies the wrong way? If small requests work and large downloads stall, it is the MTU. Each check isolates one stage — routing, NAT, DNS, packet size — and in practice the answer appears within five commands.

How the embedded DNS server is wired

The address 127.0.0.11 is inside each container's own namespace, so it cannot be a single server on the host. Docker installs NAT rules inside the container's network namespace that redirect UDP and TCP port 53 traffic for 127.0.0.11 to a random port where dockerd's resolver listens through a socket it opened inside that namespace. The resolver answers names it knows from the network's service registry and forwards the rest to the upstream servers taken from the host's configuration. Two practical consequences: if the host's /etc/resolv.conf points at a local stub such as systemd-resolved's 127.0.0.53, Docker cannot forward to that loopback from a container and substitutes the real upstreams or public defaults; and DNS failures inside containers are often dockerd problems rather than network ones.

Hairpin NAT and the userland proxy

When a container connects to the host's public IP on a published port — common when the app is configured with a public URL — the packet goes out of the container, gets DNATed back to a container on the same bridge, and the reply would go directly between the two containers, bypassing the translation and confusing TCP. This is hairpin NAT. Docker handles it either with the user-space docker-proxy or by enabling hairpin mode on bridge ports plus an extra masquerade rule. Disabling the userland proxy ("userland-proxy": false) removes a process per published port and preserves client addresses in more cases, but depends on kernel features like route_localnet for localhost access. It is a good example of how much plumbing hides behind -p.

MTU and encapsulation

The bridge driver defaults to an MTU of 1500 bytes. Many cloud networks and VPN tunnels carry less (1460 on some clouds, around 1400 or lower over tunnels), and overlay networks subtract another 50 bytes of VXLAN header. If a container sends a 1500-byte packet that will not fit, the network should return an ICMP "fragmentation needed" message so the sender lowers its segment size (path MTU discovery). When those messages are filtered, large packets vanish silently: DNS and TCP handshakes work, then the first large response — often a TLS certificate chain — stalls. The fix is to set the bridge or overlay MTU explicitly to match the path.

Volume ownership and the first-mount copy

The copy-into-empty-volume behaviour also copies ownership and permissions, which is why official database images "just work" with a fresh named volume even when they run as a non-root user. Bind mounts do not do this, so the same image on a bind-mounted host directory fails with permission errors unless the directory's owner matches the container's UID. Rootless Docker and user namespaces add another mapping layer: a file owned by UID 999 in the container is owned by a large sub-UID on the host. In Kubernetes the equivalent problems are solved with fsGroup and volume ownership changes (k8s9).

Restart policies: the single-host version of self-healing

Docker can restart a container when it exits, according to its restart policy: no (the default), on-failure[:max-retries] (only after a non-zero exit), always, or unless-stopped (like always, but not after you stopped it manually). Between restarts Docker waits an increasing delay, starting at 100 ms and doubling each time, which prevents a crashing container from spinning the CPU; the delay resets once a container has run successfully for a while. This is the same back-off idea as Kubernetes' CrashLoopBackOff (k8s13), without the rest of Kubernetes: no rescheduling to another machine if the host dies, no replacement of a container that hangs without exiting, and no health-based restart (a Docker HEALTHCHECK marks a container unhealthy but does not restart it on its own). Compose exposes the same policies with restart:.

IPv6

Default bridge networks are IPv4-only unless IPv6 is enabled on the network (docker network create --ipv6, with a subnet or an address pool). Two behaviours surprise people. Published ports listen on [::] as well as 0.0.0.0, so on an IPv4-only network an IPv6 client connection is accepted and relayed by docker-proxy, and the container sees the proxy's address rather than the client's. And with IPv6 enabled, containers can get globally routable addresses that need no NAT at all — so the firewall, not address translation, is what keeps them private. In both cases the right mental model is the one from section 3: follow the packet through the stages and ask which rule it meets.

nftables and the future of the firewall rules

Docker historically programs iptables. Modern distributions implement the iptables commands on top of nftables, the newer kernel packet-filtering framework, and Docker Engine 29 added experimental native nftables support. The concepts in this lesson — a nat stage that DNATs published ports before routing, a forward stage with a user-controlled hook evaluated first, masquerade for outbound traffic, conntrack underneath — stay the same; the chain names and commands differ, so scripts that grep for DOCKER-USER need revisiting on hosts that switch.

The case: published ports and host firewalls

Docker's own documentation on packet filtering states that when you publish a container's ports with Docker on a host using ufw, the container's traffic is diverted before it reaches ufw's rules, so ufw cannot be used to block it; its port-publishing page adds that publishing is "insecure by default" because ports bind to all addresses. The mechanism is section 3's routing step: after DNAT in PREROUTING, packets to a published port are forwarded, not delivered locally, so they traverse FORWARD (where Docker accepts them) and never INPUT (where ufw filters). For years this produced a steady stream of exposed services: teams ran Redis, Elasticsearch, MongoDB or Postgres in containers with -p 6379:6379 "so the app can reach it", believed ufw's default-deny protected them, and found the service open to the internet, often after it had been scanned and abused. Docker 28.0 additionally closed a related gap in which machines on the same LAN segment could reach ports published only on the host's localhost.

The lessons generalise. Do not publish ports that only other containers need: put them on a user-defined network and let them talk by name. Bind host-only ports to 127.0.0.1. Put any filtering for container traffic in DOCKER-USER, matching on the original port with conntrack. Scan your own hosts from outside. And in production prefer an orchestrator whose networking model and policies (Kubernetes NetworkPolicy, cloud security groups) are designed for this.

Failure modes and their symptoms

  • "Connection refused" to a published port: the app listens on 127.0.0.1 inside the container, which is the container's own loopback. Make it listen on 0.0.0.0.
  • Containers can't resolve each other: they are on the default bridge. Use a user-defined network or Compose.
  • App can't reach a service on the host via localhost: different namespace. Use host.docker.internal with host-gateway, or the bridge gateway IP.
  • Subnet clash: Docker picks 172.17.0.0/16 and friends, which can collide with a corporate VPN or VPC range; hosts in that range become unreachable from containers. Set default-address-pools in the daemon config.
  • HTTPS hangs, DNS works: MTU mismatch (deep section).
  • Data loss after compose down: data in the writable layer instead of a volume, or down -v.
  • Permission denied on a bind mount: host directory ownership does not match the container's UID.
  • conntrack table full ("nf_conntrack: table full, dropping packet" in the kernel log) on hosts with many short connections through NAT; raise nf_conntrack_max or reduce NAT.

Knobs worth setting on every Docker host

In /etc/docker/daemon.json: default-address-pools to keep container subnets away from your VPC and VPN ranges; mtu if the underlying network is smaller than 1500; "ip": "127.0.0.1" to change the default bind address for published ports, so a forgotten -p exposes nothing; log rotation (k8s1); and live-restore so daemon upgrades keep containers running. In Compose files: bind published ports to 127.0.0.1 unless they are meant to be public, separate frontend and backend networks, and give every stateful service a named volume.

Tools for looking

docker network inspect (subnets, attached containers and their IPs), docker port, iptables -t nat -L DOCKER -n -v (packet counters per rule show whether traffic matched), conntrack -L, nsenter -t <pid> -n ss -tlnp to see what a container is listening on from the host, and tcpdump -i docker0 to watch packets on the bridge. docker volume inspect shows where a volume's data lives.

def inbound(src, dst):
    if (src, dst) in conntrack: return conntrack[(src, dst)]
    new = (src, DNAT.get(dst, dst)); conntrack[(src, dst)] = new
    conntrack[("reply",) + (new[1], new[0])] = (dst, src)   # how replies are un-NATed
    return new
def outbound(src, dst):
    key = ("reply", src, dst)
    if key in conntrack: return conntrack[key]                # reply to a DNATed flow
    if src[0].startswith(BRIDGE_NET): return ((HOST, src[1]), dst)   # MASQUERADE
    return (src, dst)
c = ("203.0.113.5", 51000)
print("SYN    ", c, "->", ("198.51.100.10", 8080), "becomes", inbound(c, ("198.51.100.10", 8080)))
print("SYN-ACK", ("172.17.0.2", 80), "->", c, "becomes", outbound(("172.17.0.2", 80), c))
print("egress ", ("172.17.0.2", 40312), "->", ("93.184.215.14", 443), "becomes",
      outbound(("172.17.0.2", 40312), ("93.184.215.14", 443)))

Diagnose: the Redis that was open to the internet

A small company runs its app on one cloud VM with Docker. ufw is set to deny incoming traffic except SSH (22) and HTTPS (443). The app and Redis run as separate containers on the default bridge, started with docker run -d -p 6379:6379 redis:8 and docker run -d -p 443:8443 --link redis app:4.2. A security scan reports Redis reachable from the internet on port 6379. The team insists the firewall blocks it. Explain what happened and fix it properly.

Answer

Publishing 6379 made Docker add a DNAT rule in the nat table's PREROUTING path and an accept rule in its forwarding chains, binding on all addresses. Packets to VM-IP:6379 are rewritten to Redis's container IP before routing, so they are forwarded through FORWARD and Docker's chains and never pass INPUT, where ufw's deny rules live. ufw never sees them; Docker's documentation describes exactly this incompatibility.

Fix: Redis does not need to be published at all — only the app talks to it. Create a user-defined network (docker network create appnet), run Redis on it with no -p, run the app on it and connect to redis:6379 by name (dropping the legacy --link). Keep only the app's 443 published. Add Redis authentication anyway, as defence in depth. If some container port must be published but restricted, bind it to 127.0.0.1 or add rules to DOCKER-USER matching --ctorigdstport. Verify by scanning the VM's public IP from outside, and check iptables -t nat -L DOCKER -n shows no rule for 6379. Then rotate any data Redis held, since it may have been read or modified.
