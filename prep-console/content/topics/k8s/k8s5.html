On 29 March 2024 a Microsoft engineer investigating why SSH logins on a Debian test machine were half a second slower than expected found a backdoor in xz, a compression library present in almost every Linux system. Over two years, an attacker had become a trusted maintainer of the project and slipped obfuscated code into release tarballs of versions 5.6.0 and 5.6.1. Under specific conditions it would let the holder of a particular private key run code on any machine running an affected SSH server. It was caught before reaching most stable distributions, mostly by luck. It was assigned CVE-2024-3094.

For anyone running containers, the next questions were urgent and very concrete. Which of our images contain liblzma 5.6.0 or 5.6.1? Which of those are running, on which clusters? Were any of them built from base images we did not control? Can we be sure that the image running in production is the one our CI built, and not something pushed under the same tag? Teams that could answer in minutes had invested in the unglamorous machinery of this lesson. Teams that could not spent days pulling and unpacking images by hand.

And the story did not end in 2024. In August 2025 researchers at Binarly reported that Docker Hub still served images containing the backdoored library: Debian images from the affected window, kept for archival reasons, and at least 35 images built on top of them. A registry, it turns out, remembers everything, and a tag or base image you chose years ago can quietly keep shipping something nobody would choose today.

This lesson is about the path an image takes from a build to a running pod, and how to make every step of it trustworthy. It starts with how registries store and serve images, and the crucial difference between a tag and a digest. It covers tagging strategies, vulnerability scanning and what its numbers do and do not mean, and software bills of materials. It then traces keyless signing with cosign step by step, explains provenance and the SLSA levels, and ends with enforcing all of it at deployment time in Kubernetes.

A warehouse with labels and fingerprints

Picture a warehouse that stores sealed boxes. Every box is filed under its fingerprint: a code computed from its exact contents. Change one screw inside and the fingerprint changes. The warehouse also has shelf labels: sticky notes like "lamp, model 2" or "latest lamp", each pointing at a fingerprint. Anyone with permission can move a sticky note to a different box at any time.

A container registry is that warehouse. The fingerprints are digests (sha256:…), and the boxes are manifests, configs and layers (k8s1). The sticky notes are tags (1.4.2, latest). Ordering by fingerprint always gets you the same box and lets you check it on arrival. Ordering by label gets you whatever the label points at today.

Trusting the boxes takes three more things, each with a physical counterpart:

  • A packing list inside each box saying what parts it contains: the SBOM (software bill of materials).
  • An inspector who compares the packing list against a list of known-faulty parts: the vulnerability scanner.
  • A tamper-evident seal from the factory saying "we packed this exact box, here is our ID": a signature, plus a provenance record saying which production line built it from which parts.

Finally, a gatekeeper at the loading dock (an admission controller in Kubernetes) refuses any box ordered by label instead of fingerprint, any box without the factory's seal, or any box whose packing list contains a recalled part.

Four questions, four mechanisms

It helps to see the whole lesson as answers to four questions a careful operator asks about any image before running it.

Is this the content I think it is? Answered by the digest. If the manifest's hash matches the digest in my deployment, and every blob's hash matches the digest the manifest names, nothing has changed in transit or at rest. This check is automatic and free; it only requires that I refer to images by digest.

What is inside it? Answered by the SBOM, and judged by the scanner. The SBOM is a fact about the image that never changes; the scan is an opinion that changes every day as new vulnerabilities are disclosed. Keeping them separate is what makes continuous rescanning cheap.

Who vouches for it? Answered by the signature, bound to an identity I chose to trust — ideally an automated build identity rather than a person's laptop.

How was it made? Answered by provenance: which source, which commit, which build system, which inputs. With provenance I can check that the release came from my main branch through my CI, not from a developer's machine that happened to have push credentials.

The registry stores the image and all four kinds of evidence side by side, linked by the digest. Admission control asks the four questions automatically on every deploy. If any answer is missing or wrong, the image does not run.

Where the analogy breaks: unlike a physical seal, a digital signature can be checked by anyone, anywhere, without trusting the delivery driver; and unlike a warehouse, a registry never forgets — old boxes and labels stay available until someone deletes them, which is exactly how stale, vulnerable images stay in use.

1. How a registry stores and serves images

A registry is an HTTP server implementing the OCI Distribution Specification. Images live in repositories — named collections such as library/python on Docker Hub or myorg/api on GitHub Container Registry (ghcr.io). Within a repository, everything is a blob addressed by digest, plus a set of tags. The core API is small:

GET  /v2/<name>/manifests/<tag-or-digest>    # index or manifest JSON
GET  /v2/<name>/blobs/<digest>               # config or layer bytes
GET  /v2/<name>/tags/list                     # all tags
POST /v2/<name>/blobs/uploads/  … PUT ?digest=sha256:…   # push a blob
PUT  /v2/<name>/manifests/<tag>               # push a manifest, set a tag
GET  /v2/<name>/referrers/<digest>            # artefacts that point at a digest (OCI 1.1)

A push uploads every blob the registry does not already have (it checks with a HEAD request by digest first, which is why pushing a new version usually uploads only the top layer), then uploads the manifest with a PUT to a tag. The registry computes the manifest's digest and moves the tag to point at it. A pull runs the other way, as traced in k8s1: resolve the tag to an index or manifest, choose the platform, fetch blobs by digest and verify each one's hash.

Common registries: Docker Hub (the default for unqualified names like nginx), GitHub Container Registry, the clouds' registries (Amazon ECR, Google Artifact Registry, Azure Container Registry), and self-hosted ones such as Harbor. Two operational facts matter early. Docker Hub rate-limits pulls — currently 100 per six hours per IPv4 address (or IPv6 /64) for anonymous users and 200 for authenticated free users — so CI fleets and clusters behind one NAT address hit limits quickly; mirrors and authenticated pulls avoid it. And registries keep everything until deleted: old tags, old digests, abandoned images. Retention policies and garbage collection are something you configure, not something you get.

2. Tags versus digests, worked

A tag is a mutable pointer. A digest is the SHA-256 hash of a manifest's (or index's) exact bytes, so it cannot point at anything else without changing. You can see the difference with two pulls of the same tag a few weeks apart:

$ docker buildx imagetools inspect python:3.12-slim | head -3
Name:      docker.io/library/python:3.12-slim
MediaType: application/vnd.oci.image.index.v1+json
Digest:    sha256:4c7a…      # in September

$ docker buildx imagetools inspect python:3.12-slim | head -3
Digest:    sha256:9e12…      # in October: same tag, new Debian security fixes

The official Python image's tags are rebuilt whenever Python, Debian or the image's own scripts change, which can be several times a month. Nothing is wrong with that; it is how security fixes reach you. But it means a Dockerfile saying FROM python:3.12-slim builds against different bytes on different days, and a Kubernetes manifest saying image: myorg/api:1.4.2 runs whatever 1.4.2 points at when each node pulls it.

Three references, three behaviours:

ReferenceMeaningKubernetes default pull policyRisk
myorg/api or myorg/api:latestWhatever was pushed lastAlwaysUnknown content; no rollback target
myorg/api:1.4.2What 1.4.2 points at nowIfNotPresentNodes with an old copy keep it; re-pushes diverge
myorg/api@sha256:9e12…Exactly this manifestIfNotPresentNone from the reference; updates are explicit

The middle row is the subtle one. With IfNotPresent, a node that already has an image stored under myorg/api:1.4.2 does not ask the registry again. If someone re-pushed 1.4.2 with a hotfix, new nodes run the hotfix and old nodes run the original, under the same name. Digests remove the ambiguity: image: myorg/api:1.4.2@sha256:9e12… is valid syntax, keeps the readable tag for humans, and makes the digest authoritative.

A good tagging strategy for your own images therefore has three parts. CI tags every build with the commit SHA (api:3f9c2e1), which is unique and traceable. Releases also get a semantic version (api:1.4.2), and the registry is configured with immutable tags (ECR, Artifact Registry, Harbor and others support this) so a version cannot be re-pointed. Deployments reference the digest, filled in by CI or the GitOps tool (k8s12). latest is avoided entirely, or used only as a convenience for humans pulling by hand.

3. Vulnerability scanning, and how to read the result

An image scanner (Trivy, Grype, Docker Scout, the registries' built-in scanners) unpacks the layers and builds an inventory: OS packages from /var/lib/dpkg/status or /lib/apk/db/installed, language packages from Python's site-packages metadata, package-lock.json, go.sum, JAR manifests and so on. It then looks up each package and version in vulnerability databases — the distribution's own security trackers, GitHub's advisory database, the NVD — and reports matches as CVEs with a severity and, when one exists, the fixed version.

A typical report on the naive image from k8s3 might list 300+ findings; on slim, a few dozen; on distroless, a handful. Reading it well means asking four questions of each finding:

  1. Is there a fix? Many base-image CVEs are "won't fix" or "no fix yet" in the distribution. Those cannot be patched by rebuilding; they can only be removed by removing the package.
  2. How severe, and is it exploited? Severity (CVSS) is a starting point; inclusion in CISA's Known Exploited Vulnerabilities list matters more.
  3. Is it reachable? A vulnerability in an image-processing library the app never loads is real but not urgent. A vulnerability in the TLS library the app uses on every request is urgent.
  4. Who owns it? Base-image findings are fixed by rebuilding on a newer base digest; application-dependency findings by bumping the lock file.

Findings judged not applicable are recorded as VEX statements (Vulnerability Exploitability eXchange — "product X is not affected by CVE Y, because…") so scanners can suppress them consistently. And scanning is not a one-off: an image that was clean at build time accumulates CVEs as new ones are disclosed, so running images must be rescanned continuously. That is where SBOMs come in.

4. SBOMs: the packing list

A software bill of materials (SBOM) is a machine-readable inventory of every component in an artefact: name, version, supplier, a package URL (pkg:deb/debian/liblzma5@5.6.1-1?arch=amd64), often hashes and licences. Two formats dominate: SPDX (a Linux Foundation standard, also an ISO standard) and CycloneDX (an OWASP standard). BuildKit can generate one during the build and attach it to the image:

docker buildx build --sbom=true --provenance=mode=max \
  -t ghcr.io/myorg/api:1.4.2 --push .
docker buildx imagetools inspect ghcr.io/myorg/api:1.4.2 --format '{{ json .SBOM }}'

Tools like Syft generate SBOMs from existing images too. The point is what you do with them. Store every image's SBOM in a central index as part of CI. When the xz announcement lands, the question "which images contain liblzma5 5.6.0 or 5.6.1?" becomes a query over that index, answered in seconds, rather than a crawl that pulls and unpacks thousands of images. Join the answer with deployment data (which digests are running where) and you have the list of workloads to patch. Continuous rescanning works the same way: rerun the vulnerability match against stored SBOMs every time the advisory databases update, without touching the images.

5. Signing with cosign, step by step

Digests tell you an image has not changed since someone recorded the digest. They do not tell you who recorded it. A signature binds an identity to a digest. The Sigstore project provides the most widely used tooling: cosign for signing and verifying, Fulcio as a certificate authority, and Rekor as a public transparency log. Its distinctive mode is keyless signing, which removes the hardest part of signing — keeping a private key safe for years.

Here is the flow when a GitHub Actions release workflow runs cosign sign ghcr.io/myorg/api@sha256:9e12…:

  1. Identity. The job asks GitHub for an OIDC token (OpenID Connect: a signed JSON Web Token describing who the caller is). For a workflow, the token says, in effect, "repository myorg/api, workflow .github/workflows/release.yml, ref refs/tags/v1.4.2, issued by https://token.actions.githubusercontent.com". cosign generates a fresh key pair in memory.
  2. Certificate request. cosign sends the public key and the token to Fulcio, proving it holds the private key by signing a challenge.
  3. Short-lived certificate. Fulcio verifies the token against GitHub's published keys and issues an X.509 certificate valid for about ten minutes. The certificate embeds the identity (the workflow's URL as the subject) and the issuer.
  4. Sign. cosign signs a small payload naming the image digest, sha256:9e12…. Note it signs the digest, never a tag; the Sigstore docs stress this because a tag could later point elsewhere.
  5. Log. cosign uploads the signature and certificate to Rekor, an append-only transparency log.
  6. Proof. Rekor returns a signed timestamp and an inclusion proof. This is what makes an expired certificate still useful: the log proves the signature was created during the certificate's ten-minute validity.
  7. Store. The signature, certificate and log proof are packaged as a Sigstore bundle and attached to the image in the registry as an OCI referrer — an artefact whose manifest names the image's digest as its subject, discoverable through the referrers API (older cosign versions stored a tag named sha256-<digest>.sig instead).
  8. Forget. The private key is discarded.

Verification is where most of the security lives, and where most mistakes are made:

cosign verify ghcr.io/myorg/api@sha256:9e12… \
  --certificate-identity "https://github.com/myorg/api/.github/workflows/release.yml@refs/tags/v1.4.2" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

The verifier fetches the referrers for that digest, checks the certificate chains to Sigstore's root of trust (distributed through a signed TUF repository), checks the Rekor inclusion proof and that the signing time falls inside the certificate's validity, checks the signature over the digest, and — crucially — checks that the certificate's identity and issuer match the expected values. (Pattern flags such as --certificate-identity-regexp allow, say, any tag of that workflow.) Skipping the identity check is the classic mistake: anyone in the world can get a valid Sigstore signature for any image they can push to, so "has a valid signature" proves nothing on its own.

Keyless is not the only option. cosign also signs with long-lived keys, including keys held in a cloud KMS or HSM, which suits air-gapped environments. Notation (the Notary Project) is an alternative signing tool built around X.509 certificates; registries and admission tools increasingly support both.

6. Provenance and SLSA

A signature says "the release workflow of myorg/api signed this digest". Provenance says how the image was built: source repository and commit, the build platform and workflow, the build parameters, the resolved inputs such as base-image digests. BuildKit generates provenance in the SLSA format (--provenance=mode=max includes the full build definition); GitHub's artifact attestations and the SLSA GitHub generator produce signed provenance for workflows. Provenance is stored as another referrer, usually as a signed in-toto attestation.

SLSA (Supply-chain Levels for Software Artifacts, pronounced "salsa"; current specification v1.2) organises this into incremental levels on its build track:

LevelRequirementProtects against
Build L0Nothing—
Build L1A consistent build process that produces provenance describing how the artefact was builtMistakes, such as releasing from a commit that is not in the repository
Build L2Provenance generated and signed by a hosted build platform; consumers verify itTampering after the build
Build L3A hardened platform: builds isolated from each other, signing material inaccessible to build stepsTampering during the build by insider threats, stolen credentials or other tenants

SLSA v1.2 also has a source track, with levels for how the source repository is protected (branch protection, reviews, history retention). The practical reading for an engineer: L1 is cheap and immediately useful (you can trace any image to a commit); L2 is what you get from a managed CI that signs attestations for you; L3 is about the build platform's isolation and is mostly a property of the CI service you choose. Reproducible builds (k8s3) go further still, letting a second party rebuild and compare digests.

7. Enforcing it at deploy time

None of the above matters if anything can still be deployed. In Kubernetes the enforcement point is admission control: before the API server stores a pod (or a Deployment that will create pods), validating admission webhooks can inspect it and reject it (k8s6 explains where this sits). Policy engines provide ready-made rules:

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-api-images }
spec:
  rules:
  - name: signed-by-release-workflow
    match: { any: [ { resources: { kinds: [Pod] } } ] }
    verifyImages:
    - imageReferences: ["ghcr.io/myorg/*"]
      failureAction: Enforce      # Audit while rolling out
      mutateDigest: true          # rewrite tags to digests at admission
      verifyDigest: true
      attestors:
      - entries:
        - keyless:
            subject: "https://github.com/myorg/*/.github/workflows/release.yml@*"
            issuer: "https://token.actions.githubusercontent.com"
            rekor: { url: https://rekor.sigstore.dev }

(Kyverno's docs show this ClusterPolicy form with failureAction on each verifyImages entry; newer Kyverno releases also offer a dedicated ImageValidatingPolicy type for the same job.) This rule makes the API server reject any pod using a ghcr.io/myorg/ image that is not signed by a release workflow in that organisation, and rewrites tag references to the verified digest so every node runs exactly the signed bytes. Similar rules can require attestations (an SBOM exists; provenance names the expected repository; the last scan has no critical known-exploited CVEs) and restrict images to approved registries. The Sigstore policy-controller and Ratify are alternatives with the same idea. Two operational cautions: run new policies in audit mode first, since a rejected pod during an incident is its own outage; and make sure the policy engine is highly available and its failure mode is decided deliberately (fail closed is safer, fail open is more available).

8. The whole pipeline in one CI job

Here is how the pieces fit in a single GitHub Actions release job, described step by step rather than as a full workflow file. The job declares permissions: id-token: write (so it can request an OIDC token for keyless signing), packages: write (to push to GitHub Container Registry) and contents: read. It checks out the tagged commit and sets SOURCE_DATE_EPOCH from the commit time (k8s3). It builds with docker/build-push-action, passing sbom: true and provenance: mode=max, pushing to ghcr.io/myorg/api with the commit SHA and version as tags; the action outputs the pushed digest, and every later step uses that digest, never the tag. A scanner step runs against ghcr.io/myorg/api@<digest> and fails the job on fixable critical or known-exploited vulnerabilities. Then sigstore/cosign-installer installs cosign, and cosign sign --yes ghcr.io/myorg/api@<digest> signs keylessly with the job's identity, which is the workflow path and tag. Finally the job opens a pull request in the configuration repository that sets the new digest for the first environment (k8s12).

Notice what is not in the job: no long-lived signing key, no registry password beyond the job's own short-lived token, and no cluster credentials — deployment happens by the cluster pulling, and admission (section 7) verifies that the digest was signed by exactly this workflow. If an attacker steals a developer's laptop, they can push code for review but cannot produce an image that passes admission; if they compromise the CI system, every signature they make appears in the public transparency log under the workflow identity, where monitoring can catch it.

Why transparency logs matter more than signatures

A signature proves possession of a key. A transparency log proves that a signing event happened publicly. Because Rekor is append-only and its entries are chained in a Merkle tree, a signature cannot be quietly created and later removed, and monitors can watch the log for any signing event involving your identities. If an attacker steals a CI token and signs a malicious image as your release workflow, that signature appears in the log, where a monitor that alerts on "signatures for our identity not matching a CI run we know about" catches it. Certificate Transparency did the same for TLS certificates: the cryptography was never the weak point; undetected misuse was.

The referrers model and artefact sprawl

Before OCI 1.1 there was no standard way to attach a signature or SBOM to an image, so cosign used tag naming conventions (sha256-<digest>.sig, .att, .sbom). The 1.1 specification added a subject field to manifests and the referrers API, so any artefact can declare "I am about digest X" and clients can list them. That cleans up the repository but creates new operational questions: garbage collection must not delete an image's signatures while keeping the image (or vice versa), replication to mirrors must copy referrers along with images, and air-gapped transfers must include them. Registry support has become broad, but a mirror that silently drops referrers turns every image unsigned at the edge.

Dependency confusion and typosquatting reach images too

Images are built from packages, and package ecosystems have their own supply-chain attacks. In dependency confusion, a build that resolves an internal package name against a public index can be tricked into installing an attacker's public package of the same name with a higher version. Typosquatting publishes look-alike names. Inside a Dockerfile both show up as an ordinary pip install layer. The defences are the ones from k8s3 — lock files with hashes, a single configured index or an internal proxy with allow-lists — plus SBOM review for unexpected new components between releases.

Mirrors, pull-through caches and trust

Large fleets rarely pull from public registries directly. A pull-through cache (Harbor, the clouds' registries, or containerd's mirror configuration) fetches each image once and serves it locally, which avoids rate limits, cuts cold-start time and keeps working when the upstream is down. Mirrors change the trust question: you now trust the mirror to serve the same bytes. Digest pinning makes that safe automatically, because the client verifies every blob's hash regardless of where it came from; with tags, a compromised mirror could serve anything. This is one more reason the digest, not the tag, is the unit of trust.

Base images as a dependency you must manage

Most teams treat the FROM line as a constant. It is the largest dependency in the image — usually more code than the application and all its libraries combined — and the one that accumulates CVEs fastest. Managing it like a dependency means: a small set of approved base images, owned by a platform team, rebuilt on a schedule and when upstream fixes land, published to an internal registry with their own signatures and SBOMs; application Dockerfiles pinned to those digests; and automated pull requests that bump the digest in every service when a new base is published. The result is that a base-image fix reaches every service through the normal review-and-deploy path in days, with a clear record of which services have taken it, instead of whenever each team happens to rebuild.

What signatures cannot do

The xz backdoor was in the official upstream release, built and signed by the legitimate pipeline. Every signature and provenance check would have passed. Supply-chain controls prove an artefact came through the expected path; they cannot judge whether the source itself is malicious. Defences against that live elsewhere: minimising dependencies, reviewing updates to critical ones, reproducible builds that let distributions rebuild from source rather than trusting release tarballs (the xz payload hid in tarball-only build files), behavioural monitoring at run time, and the ability to find and replace a component everywhere quickly when it is exposed — which brings us back to SBOMs.

Attestations beyond SBOM and provenance

The in-toto attestation format that carries provenance can carry any signed claim about a digest: a vulnerability scan result with its timestamp, a test report, a code-review attestation, a VEX statement. Policy engines can then require combinations — "signed by the release workflow, with provenance from this repository, and a scan less than 24 hours old with no critical known-exploited findings". The design principle is that every claim is bound to the digest and signed by the system that made it, so the decision at admission is a pure function of verifiable evidence rather than of trust in whichever pipeline happened to push the image. The cost is operational: attestations must be generated, stored as referrers, replicated to mirrors and kept fresh, and a policy that demands a recent scan will block deployments when the scanner is down — so decide in advance whether that policy fails open or closed.

The case: xz in Docker Hub images, seventeen months later

CVE-2024-3094 was disclosed on 29 March 2024: xz/liblzma 5.6.0 and 5.6.1 contained an obfuscated backdoor that, when loaded into an OpenSSH server through distribution patches linking it with libsystemd, could let the holder of a specific key execute commands. Distributions reverted within days, and the affected versions had mostly reached only development and testing branches such as Debian unstable and testing, Fedora Rawhide and some rolling releases.

In August 2025 Binarly reported that Docker Hub still served images containing the backdoored library. They found official Debian images from the affected window and at least 35 further images built on top of them — a partial scan, by their own account. Debian's maintainers chose to keep their dated images available as historical artefacts, arguing that exploitation is unlikely in a container because it requires sshd installed and running, network access to it, and the attacker's specific private key. That reasoning is sound for most containers; the broader lesson is about how registries and builds behave. Old tags remain pullable indefinitely. Images built FROM a dated or testing-branch base inherit its contents and keep them until rebuilt. And scanners only flag such images if someone scans them after the advisory was published.

The controls from this lesson map one-to-one onto the failure: base images chosen from stable, maintained tags and pinned by digest with automated updates; regular rebuilds so fixes propagate; SBOMs stored centrally and rescanned against new advisories, which turns "do we run liblzma 5.6.1 anywhere?" into a query; and admission policy that blocks images with known-exploited critical CVEs. Teams that had those in place in March 2024 answered the question the same morning.

Failure modes in production

  • ImagePullBackOff from rate limits (toomanyrequests) when a cluster behind one NAT address scales out from Docker Hub. Mirror images or authenticate pulls.
  • Fleet divergence: a re-pushed tag with IfNotPresent leaves nodes running different images. Pin digests; enable tag immutability.
  • Policy outage: a new verification policy in Enforce mode, or an unavailable policy webhook, blocks all deployments, including the fix for an incident. Roll out in Audit, keep break-glass procedures, monitor the webhook.
  • Signatures missing at the edge: a mirror or replication job that copies images but not referrers.
  • Scanner fatigue: thousands of unfixable base-image findings drown real ones. Shrink bases, use VEX, gate on known-exploited and fixable findings.
  • Registry storage growth: every CI build pushes; without retention rules, storage and cost grow forever and old vulnerable images remain deployable.

Incident response with images

When an advisory lands, the playbook is: query the SBOM index for the component and versions; join with the inventory of running digests per cluster and namespace; triage by exposure (internet-facing first) and exploitability; rebuild affected images on a fixed base, which with digest pinning is a reviewed pull request per service; deploy through the normal pipeline; and add a temporary admission rule that blocks the vulnerable versions so nothing old is redeployed by accident. Afterwards, delete or quarantine the vulnerable digests in your registries, so a rollback cannot resurrect them.

What to measure

Percentage of running workloads referenced by digest and passing signature verification; age of base images in production; time from a critical advisory to "all affected images identified" and to "all patched"; registry pull error rate and cache hit rate for mirrors; number of policy denials (audit mode first) by reason.

Rolling out supply-chain controls without stopping delivery

Introduce the controls in the order that gives value earliest and blocks least: first generate SBOMs and provenance for every build (no gates, just data); then sign images in CI; then run admission policies in audit mode and fix what they report, team by team; then enforce for new namespaces and finally for all. Publish a dashboard of compliance per team so progress is visible, and keep a documented, logged exception path for emergencies, because a policy that cannot be bypassed during an incident will be disabled entirely the first time it gets in the way.
