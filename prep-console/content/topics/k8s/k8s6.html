sc15 introduced Kubernetes as a set of control loops and walked through what happens when you create a Deployment, at the level of "the scheduler picks a node, the kubelet starts the containers". That is enough to use Kubernetes. It is not enough to operate it, debug it, or answer the follow-up questions in a platform-engineering interview.

Consider the situations that come up in practice. A pod has been Pending for ten minutes: is the scheduler failing to place it, or did it place it on a node whose kubelet is not responding? Every kubectl command takes eight seconds: is it the API server, etcd, an admission webhook, or a misbehaving controller flooding the API with requests? A node vanished an hour ago but its pods still show as Running: who was supposed to notice, and when? A security team wants every new pod checked against a policy: where in the request path can that happen, and what happens if the policy service is down? A team's custom controller takes down the API server by listing every pod in a 5,000-node cluster every second: what should it have done instead?

Each of these has a precise answer once you know what each component does, what it reads and writes, and how they find out about each other's work. The surprising part is how few interactions there are. Kubernetes has a handful of components, and almost all of them do just one thing: read and write objects through one API server and watch for changes. The design is deliberate, and Google's paper on Borg, Omega and Kubernetes explains the decade of experience behind it.

This lesson opens each component in turn. It starts with objects and the API they live behind, follows a write through the API server's pipeline into etcd, explains watches and informers (the mechanism everything else depends on), then the controllers, the scheduler, the kubelet and kube-proxy. It ends by tracing kubectl apply of a Deployment all the way to running containers, with every hop named, and by looking at how the control plane fails and how you would notice.

A newsroom with one shared board

Picture a newsroom with one big shared board and a strict editor guarding it. Nobody phones anybody. The chief writes on the board: "three reporters cover the election". The desk editor, who watches the board for anything about coverage, notices and pins up three assignment cards with no names on them. The scheduler, who watches for unassigned cards, writes a reporter's name on each, choosing people who are free and spreading them across districts. Each reporter watches the board for cards with their own name, picks theirs up, goes out, and writes progress notes back on the card. If a reporter falls ill and stops checking in, the desk editor notices only two active cards where three are wanted, and pins up another.

That is Kubernetes. The board is the API server, backed by etcd, which keeps the board's contents safe even if a wall falls down. The editor guarding the board checks who you are, whether you may write that, and whether what you wrote is well formed (authentication, authorisation, admission). The desk editors are controllers. The person writing names on cards is the scheduler. The reporters are kubelets, one per node. Nobody calls anybody: everyone reads the board, writes the board and watches the board.

Three ideas carry the whole design, and the rest of the lesson unpacks them:

  1. State, not commands. Users declare desired state in objects; components observe state and act. Nothing sends "start container X" to a node.
  2. One gateway. All state lives behind the API server, which enforces identity, permissions, validation and policy for every change.
  3. Watch, then reconcile. Every component learns about changes by watching the API server, and each one runs a loop that makes the part of the world it owns match the board.

Who writes what

One more way to hold the picture is to ask, for each piece of an object, who is allowed to write it. You (or your CI, or a GitOps tool) write the spec of top-level objects such as Deployments and Services. Controllers write the spec of the objects they create — the Deployment controller writes ReplicaSets, the ReplicaSet controller writes pods — and the status of the objects they own. The scheduler writes exactly one field, a pod's node assignment. The kubelet writes pod status and its node's status and lease. kube-proxy writes nothing to the API at all; it only reads, and writes packet rules into its node's kernel. When something is wrong, this division tells you where to look: a field that has the wrong value was written by one particular component, and a field that never changes belongs to a component that is not running or cannot see the change.

Where the analogy breaks: a real board has no latency, but watches deliver changes over the network with small delays, so components always act on a slightly old picture. Kubernetes is built to tolerate that: every action is re-checked against the latest state, and conflicting writes are rejected rather than silently applied.

1. Objects and the API they live behind

Everything in Kubernetes is an object of some kind: Pod, Deployment, Service, Node, Lease. Every object has three parts. Metadata is the same for all kinds: name, namespace, a unique UID, labels, annotations, owner references, and a resourceVersion. Spec is the desired state, written by a user or a higher-level controller. Status is the observed state, written only by the component responsible for that kind. The Borg-Omega-Kubernetes paper calls this uniform shape one of Kubernetes' key decisions: generic tools work across every kind, and the split between spec and status is what controllers reconcile.

Objects are exposed as REST resources organised into API groups and versions. Pods are in the core group, version v1, at /api/v1/namespaces/default/pods/web-7d9f; Deployments are in the apps group at /apis/apps/v1/namespaces/default/deployments/web. Every resource supports the same verbs: get, list, watch, create, update, patch, delete. Custom resource definitions add new kinds with the same machinery, which is how operators extend the cluster.

kubectl is just an HTTP client for this API. Running kubectl get pods -v=8 prints the requests: GET https://10.0.0.1:6443/api/v1/namespaces/default/pods?limit=500, and the JSON that comes back.

2. The API server's write path

The kube-apiserver is a stateless HTTP server, usually run as several replicas behind a load balancer. Every request passes the same pipeline:

  1. Authentication establishes who is calling: a client certificate (common for components and kubeadm admins), a bearer token (service-account tokens, which pods get automatically), or an OIDC token from a corporate identity provider. Failure: 401 Unauthorized.
  2. Authorisation decides whether that identity may perform this verb on this resource in this namespace. Almost every cluster uses RBAC: Roles list allowed verbs on resources, RoleBindings grant them to users, groups or service accounts; ClusterRoles and ClusterRoleBindings do the same cluster-wide. Nodes use a special Node authoriser that limits each kubelet to objects related to its own pods. Failure: 403 Forbidden.
  3. Mutating admission. Admission controllers are plugins that run after authorisation and before storage, in two phases. Mutating ones may change the object: setting defaults (the default service account, the default StorageClass), adding a sidecar container (a service mesh's injector, implemented as a mutating webhook), or rewriting image tags to digests (k8s5).
  4. Schema validation checks the object against the kind's schema: required fields, types, immutable fields not changed. Failure: 422 Unprocessable Entity.
  5. Validating admission may only accept or reject: Pod Security Admission enforcing the baseline or restricted profiles, ResourceQuota, policy engines via webhooks, and ValidatingAdmissionPolicy rules written in the CEL expression language and evaluated inside the API server (GA since 1.30). If any controller in either phase rejects the request, the whole request fails.
  6. Storage. The object is serialised (protobuf for built-in kinds) and written to etcd under a key such as /registry/deployments/default/web. etcd assigns a new revision, which becomes the object's resourceVersion. The API server returns the stored object, and its watch machinery notifies everyone watching that kind.

Two properties of this path matter later. Writes are optimistically concurrent: an update carrying an old resourceVersion fails with 409 Conflict instead of overwriting someone else's change, and the client must re-read and retry. And admission webhooks are in the critical path of every matching write: a slow or unavailable webhook slows or blocks writes, governed by its timeoutSeconds and failurePolicy (Fail or Ignore).

How kubectl apply fits: the default, client-side apply computes a patch from your file, the live object and a last-applied-configuration annotation. Server-side apply (kubectl apply --server-side, stable since 1.22) sends your declared fields to the API server, which merges them and records in managedFields which manager owns each field, so two tools that set different fields of the same object do not fight, and genuine conflicts are reported.

3. etcd: the store, and its limits

in8 covers etcd as a design: a Raft-replicated key-value store, usually three or five members, where a write is committed once a majority has it in their logs. For Kubernetes, four practical facts matter.

  • Only the API server talks to it. Components never read etcd directly, so the API server can change storage formats, encrypt Secrets at rest, and enforce semantics in one place.
  • Every write is a consensus round. Each create, update and status change costs a Raft commit, which includes an fsync on a majority of members. etcd's latency is therefore bounded by disk latency, and etcd on slow or shared disks is the most common cause of a slow control plane.
  • It is small by design. A single request is limited to about 1.5 MiB by default, so a ConfigMap or Secret cannot exceed roughly 1 MiB; the database has a storage quota (2 GiB by default, commonly raised to 8 GiB) after which it refuses writes until compacted and defragmented. Old revisions are compacted periodically by the API server.
  • Losing quorum stops change, not pods. With two of three members down, etcd refuses writes and linearizable reads; the API server cannot update anything; but kubelets keep running existing containers. Backups (snapshots) of etcd are the cluster's disaster-recovery story.

4. Watches and informers: how everyone finds out

If every component polled the API server for changes, a cluster with 50 controllers and 1,000 kubelets would melt it. Instead, Kubernetes clients use list-and-watch:

  1. LIST the resource once, getting every object and the collection's resourceVersion, say 48211.
  2. WATCH from that version: GET /api/v1/pods?watch=1&resourceVersion=48211. The connection stays open, and the API server streams one event per change: {"type":"ADDED","object":{…}}, MODIFIED, DELETED, plus periodic BOOKMARK events that advance the client's resourceVersion without data.
  3. If the connection drops, re-watch from the last version seen. If that version is too old (history compacted), the server answers 410 Gone and the client relists.

The API server does not open an etcd watch per client. It keeps a watch cache per resource — the recent history and current state in memory — fed by one etcd watch, and serves all client watches (and many lists) from it. That is what makes thousands of watchers affordable.

On the client side, the client-go library wraps this into an informer: it lists and watches one resource, keeps a local in-memory cache (indexed, for example, by namespace or node name), and calls handlers on add, update and delete. Controllers do not do work inside those handlers. They push the object's key (namespace/name) onto a work queue that deduplicates keys and rate-limits retries, and worker goroutines pop keys and reconcile: read the current object from the cache, compare spec with observed state, act, and write status. This pattern is called level-triggered: the controller looks at the current level of the world, not at the sequence of events. If it misses events, crashes or restarts, it simply reconciles the current state and ends up correct — the robustness the Borg paper credits to "action based on observation rather than a state diagram".

The kube-controller-manager is one binary running dozens of built-in controllers, each a reconcile loop for some kinds. The ones you meet most:

Ownership is recorded in owner references: each pod's metadata names its ReplicaSet as owner, and each ReplicaSet names its Deployment. Delete the Deployment and the garbage collector deletes the ReplicaSets, then the pods. Ownership is loose on purpose: a ReplicaSet adopts any pod matching its label selector that has no owner, and removing a label from a misbehaving pod orphans it from its Service and its ReplicaSet, which creates a replacement while you debug the original in place — a trick the Borg paper describes explicitly.

To avoid two copies of a controller fighting, the controller manager and scheduler run with leader election: replicas compete to hold a Lease object in kube-system, renewing it every couple of seconds; only the holder acts, and if it stops renewing, another replica takes over within about 15 seconds by default. In clouds, a separate cloud-controller-manager runs the cloud-specific loops: provisioning load balancers for type: LoadBalancer Services, labelling nodes with their zone, and deleting Node objects whose VMs are gone.

6. The scheduler

The kube-scheduler watches for pods with no spec.nodeName, places them in a priority queue, and for each one runs a scheduling cycle (serially, one pod at a time) followed by a binding cycle (which can run concurrently). Its logic is a pipeline of plugins at extension points; the main ones:

  1. PreFilter / Filter remove nodes that cannot run the pod. NodeResourcesFit: the sum of requests of pods already on the node plus this pod's requests must fit the node's allocatable CPU, memory and other resources — requests, not actual usage (k8s10). TaintToleration: the pod must tolerate the node's taints. NodeAffinity, PodTopologySpread, InterPodAffinity, NodePorts, volume plugins.
  2. PostFilter runs if no node passed: the default is preemption, which looks for lower-priority pods whose eviction would make room.
  3. Score ranks the feasible nodes 0-100 per plugin, weighted: balanced or least-allocated resource use, topology spreading, affinity preferences, ImageLocality (nodes that already have the image). For big clusters the scheduler only scores a sample of feasible nodes (percentageOfNodesToScore, adaptive by default) to keep each cycle fast.
  4. Reserve / Permit tentatively assign the node in the scheduler's own cache, so the next pod in the queue sees those resources as taken.
  5. Bind writes a Binding to the API server, which sets spec.nodeName. That write is all the scheduler does to the world.

When a pod cannot be placed, the scheduler records a FailedScheduling event that lists, per filter, how many nodes it rejected: 0/12 nodes are available: 3 node(s) had untolerated taint {dedicated: gpu}, 9 Insufficient memory. That message is the first thing to read for any Pending pod (k8s13). The pod goes back to the queue and is retried when something changes that might help, such as a node being added or a pod deleted.

7. The kubelet: from pod object to processes

The kubelet runs on every node as a systemd service, not as a pod (it has to exist before pods can). It watches the API server for pods whose spec.nodeName is its own node, and for each one a pod worker drives the container runtime through the CRI (k8s1):

  1. Admit the pod: check it fits the node's allocatable resources and passes node-level checks.
  2. Prepare: create the pod's cgroup under the kubepods hierarchy, according to its QoS class (k8s10); mount volumes (ConfigMaps, Secrets, persistent volumes via CSI, k8s9); fetch image pull secrets.
  3. RunPodSandbox: containerd creates the pod's shared namespaces with a pause container and calls the CNI plugin (Container Network Interface) with ADD, which creates the veth pair, assigns the pod IP and sets up routes (k8s8).
  4. For each init container, in order, then each app container: PullImage per the pull policy, CreateContainer with the command, environment, mounts, security context and resource limits translated into cgroup settings, then StartContainer. (Native sidecars, init containers with restartPolicy: Always, start in order and keep running.)
  5. Probe: run startup, then liveness and readiness probes on schedule.
  6. Report: patch the pod's status — phase, conditions (PodScheduled, Initialized, ContainersReady, Ready), container states, restart counts, pod IP.

The kubelet keeps reconciling: if a container exits, it restarts it according to restartPolicy with exponential back-off (10 s, 20 s, 40 s… capped at five minutes — the CrashLoopBackOff state, k8s13). It learns about container state changes by periodically relisting containers from the runtime (the pod lifecycle event generator, PLEG) or, where enabled, from CRI events. It also enforces node-level health: it evicts pods when memory or disk runs low (node-pressure eviction), and it heartbeats.

Heartbeats. Each kubelet renews a Lease object named after its node in the kube-node-lease namespace every 10 seconds, and updates the heavier Node status when something changes or periodically. The node lifecycle controller checks every 5 seconds; if a node's lease has not been renewed for the node-monitor-grace-period (50 seconds by default in current releases; older releases used 40 seconds), it sets the node's Ready condition to Unknown and adds the taint node.kubernetes.io/unreachable:NoExecute. Pods get a default toleration of 300 seconds for that taint, so about five minutes later they are evicted and their controllers replace them elsewhere.

8. kube-proxy

kube-proxy runs on each node (usually as a DaemonSet) and implements Services. It watches Services and EndpointSlices and programs the node's packet rules — iptables, IPVS or, more recently, nftables — so that a connection to a Service's virtual IP is DNATed to one of the ready pod IPs, much as Docker DNATs a published port (k8s4). It is not on the data path as a process; the kernel does the forwarding. Several CNI plugins (Cilium, for example) replace kube-proxy with their own eBPF programs. k8s8 traces a Service connection through these rules.

9. The whole trace: kubectl apply to a running container

Now put it together. A three-node cluster; you apply:

apiVersion: apps/v1
kind: Deployment
metadata: { name: web, namespace: shop }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        resources: { requests: { cpu: 100m, memory: 64Mi } }
        readinessProbe: { httpGet: { path: /, port: 80 } }
  1. kubectl reads the file, fetches the live object (none exists), and sends a create (client-side apply). The API server authenticates the user's OIDC token, RBAC allows create deployments in shop, mutating admission adds defaults (strategy RollingUpdate with 25% maxSurge and maxUnavailable, imagePullPolicy: IfNotPresent because the tag is not latest, terminationGracePeriodSeconds: 30), validation passes, Pod Security Admission checks the template, and the object is stored as /registry/deployments/shop/web at resourceVersion 90112. kubectl prints deployment.apps/web created, typically within tens of milliseconds.
  2. The Deployment controller's informer receives ADDED. Its worker reconciles shop/web: no ReplicaSet matches the template, so it hashes the pod template (say 7d9f6c8b5) and creates ReplicaSet web-7d9f6c8b5 with replicas 3 and an owner reference to the Deployment.
  3. The ReplicaSet controller sees a ReplicaSet wanting 3 pods with 0 matching, and creates three pods, web-7d9f6c8b5-x2k4q and two siblings, each with the template's labels plus pod-template-hash, an owner reference, and no node. It records that it expects three creations, so a slow watch does not make it create six.
  4. The scheduler receives three unscheduled pods. For each: all three nodes pass filtering (100m CPU and 64 MiB fit everywhere); scoring prefers spreading pods of the same ReplicaSet and nodes with lower allocation; pod 1 goes to node-a, pod 2 to node-b, pod 3 to node-c. Each binding sets spec.nodeName.
  5. Each kubelet sees one pod bound to its node. On node-a: admit; create cgroup kubepods-burstable-pod<uid>.slice; RunPodSandbox, where the CNI plugin gives the pod 10.244.1.17; PullImage nginx:1.27 (cold node: a few seconds); CreateContainer, StartContainer; the readiness probe gets 200 from http://10.244.1.17:80/; status patched to Running, Ready=True.
  6. The Deployment controller sees the ReplicaSet's ready count reach 3 and updates the Deployment's status (availableReplicas: 3), which kubectl rollout status was waiting for. If a Service selects app: web, the EndpointSlice controller adds the three ready pod IPs and every node's kube-proxy programs them.

kubectl get events -n shop --sort-by=.metadata.creationTimestamp shows the same story in the components' own words: ScalingReplicaSet from the deployment controller, SuccessfulCreate from the replicaset controller, Scheduled from the scheduler, then Pulling, Pulled, Created, Started from each kubelet.

Why choreography instead of a workflow engine

A central orchestrator — one program that executes "create ReplicaSet, then create pods, then wait for scheduling, then…" — is easier to read but brittle: if it crashes mid-way, someone must know where it was; if the world changes under it (a node dies during step 3), its plan is wrong. Kubernetes instead composes many small, independent loops, each owning one transition and each idempotent. A crash loses nothing because there is no in-flight plan, only state in the API. New behaviour is added by adding a loop (an operator) rather than editing a central workflow. The cost is that the emergent behaviour can be hard to trace — which is why events, conditions and owner references exist, and why "which controller should have acted, and what did it see?" is the core debugging question.

Optimistic concurrency and the 'expectations' trick

Because components act on cached, slightly stale views, two hazards appear: lost updates and duplicate actions. resourceVersion handles the first: any update based on an old version fails with a conflict, and the controller re-reads and retries. The second is subtler: a ReplicaSet controller creates three pods, but its cache has not yet seen them, so on its next reconcile it still counts zero and would create three more. The controller therefore records expectations — "I expect to see three creations for this key" — and skips reconciling that key until the cache catches up or a timeout passes. Writing your own controller without this pattern is a classic source of runaway pod creation.

API Priority and Fairness

The API server has finite concurrency. Without protection, one runaway client — a controller listing all pods every second, a script hammering secrets — can starve kubelets and controllers. API Priority and Fairness (stable since 1.29) classifies each request by FlowSchema into a priority level with its own share of concurrency, and within a level fair-queues requests by flow (for example per user), so a noisy flow waits in its own queue instead of blocking everyone. System components get reserved, high-priority levels; leader-election traffic is exempt from queuing. Metrics such as apiserver_flowcontrol_rejected_requests_total show who is being throttled, which is often the quickest way to find the noisy client.

Scaling limits and where they come from

The project's tested limits are around 5,000 nodes, 150,000 pods and 110 pods per node by default. The binding constraints are not CPU on the control plane but the volume of watched state and writes: every pod status change is an etcd write and a watch event delivered to every interested client; every endpoint change fans out to every node's kube-proxy. EndpointSlices replaced the single Endpoints object per Service for exactly this reason: with one object listing 5,000 pod IPs, any change re-sent the whole list to every node. Large clusters run etcd on dedicated fast disks, separate the events resource into its own etcd, tune watch-cache sizes, and prefer more smaller clusters over one enormous one.

Static pods and how the control plane bootstraps itself

There is a chicken-and-egg problem: the API server runs as a pod, but pods are created through the API server. kubeadm-style clusters solve it with static pods: manifests the kubelet reads from a local directory (/etc/kubernetes/manifests) and runs directly, without the API server. The kubelet then creates read-only "mirror pod" objects so they are visible in kubectl get pods -n kube-system. That is how etcd, the API server, controller manager and scheduler start on control-plane nodes. Managed services (EKS, GKE, AKS) hide the control plane entirely, which removes this concern but also removes access to etcd and the control-plane logs except through the provider's tooling.

What the kubelet does without the API server

If the API server becomes unreachable, the kubelet keeps running what it already has, restarts crashed containers per their restart policy, and keeps running probes, but it cannot report status, learn about new pods, or be told to delete old ones. When connectivity returns, it reconciles against the API: pods deleted in the meantime are stopped. This "headless" robustness is why a control-plane outage is an outage of change rather than of service — provided nothing in the data path depends on the API server, such as an application that calls the Kubernetes API on every request, or a service mesh control plane that cannot push configuration.

Custom resources and operators use the same machinery

A CustomResourceDefinition adds a new kind to the API server — say PostgresCluster — with its own schema, validation and versioning, stored in etcd like any built-in object. An operator is simply a controller for that kind: it watches PostgresCluster objects through informers, and reconciles by creating StatefulSets, Services, Secrets and backup Jobs, writing progress to the custom resource's status. Nothing about the control plane changes; the API server, admission, RBAC, watches and garbage collection all apply. That uniformity is why Kubernetes became a platform for building platforms, and also why a badly written operator — one that lists instead of watching, or updates status in a tight loop — can load the API server as heavily as any built-in controller.

The case: "Borg, Omega, and Kubernetes" (ACM Queue, 2016)

Brendan Burns, Brian Grant, David Oppenheimer, Eric Brewer and John Wilkes wrote down what Google learned from three container-management systems over a decade, and much of this lesson's architecture is a direct answer to it. Borg, the first, ran both services and batch work on shared machines and accumulated an ecosystem of add-on tools with idiosyncratic APIs. Omega, an offspring of Borg, stored cluster state in a centralised Paxos-based store that control-plane components accessed directly with optimistic concurrency, letting the Borgmaster's monolith be broken into peers. Kubernetes kept Omega's shared store with watching components but put a REST API server in front of it that "applies higher-level versioning, validation, semantics, and policy" for a wider range of clients — the "don't expose raw state" lesson.

The paper's "things to avoid" read like a design rationale for features you use daily. Don't make the container system manage port numbers: in Borg all containers on a machine shared its IP, so each got assigned ports, which broke DNS, URLs and ordinary tools; Kubernetes gives each pod its own IP so applications use well-known ports. Don't just number containers: give them labels: Borg's numbered task vectors caused holes, rigid restarts and names decoded with regular expressions; Kubernetes groups pods with labels and selectors. Be careful with ownership: Borg tasks were permanently tied to their job; Kubernetes controllers select pods by label, which allows adopting and orphaning — remove a label to pull a misbehaving pod out of a Service while its controller replaces it. And the paper describes the control loops as choreography — "achieving a desired emergent behavior by combining the effects of separate, autonomous entities that collaborate" — chosen deliberately over a centralised orchestration system that "tends to become brittle and rigid over time".

Reading the paper is the best preparation for "why is Kubernetes designed this way?" questions, because the answers are lessons from production rather than taste.

How the control plane fails, and what you see

  • etcd slow or out of quorum: every write slow or failing, etcdserver: request timed out, leader elections in etcd logs; watch for WAL fsync and backend commit latency above tens of milliseconds and mvcc: database space exceeded.
  • Admission webhook down with failurePolicy: Fail: all matching writes rejected with failed calling webhook, including the deploy that would fix it. Exempt kube-system, set short timeouts, run webhooks highly available.
  • API server overload: high latency, 429s from API Priority and Fairness; usually a client doing large LISTs or a watch storm after an API server restart (every client relists at once).
  • Scheduler or controller manager not leading: pods stay Pending with no events; Deployments do not progress; check the leader Lease's renew time.
  • Kubelet unhealthy: node NotReady; pods bound there stay Pending or keep stale status; after the grace period plus 300 s, pods are evicted.
  • Certificate expiry: kubeadm clusters' component certificates expire after a year unless renewed (upgrades renew them); expired certificates stop components talking to the API server.

What to watch

API server request latency and error rate by verb and resource; in-flight and rejected requests; webhook latency; etcd leader changes, fsync latency, database size; scheduler pending pods and scheduling latency; controller work-queue depth and age; node Ready status and lease renewal age. Back up etcd on a schedule and test restores — a cluster whose etcd cannot be restored has no disaster recovery, whatever its replication.

Diagnose: pods Pending for twenty minutes, no events

After a control-plane node was replaced during maintenance, new pods in every namespace stay Pending. kubectl describe pod shows no events at all, not even FailedScheduling. Existing pods are fine, and kubectl apply works. Deployments created after the maintenance show ReplicaSets and pods, so controllers are working. Where is the problem and how do you confirm it?

Answer

The chain is: API server accepted the Deployment (apply works), the Deployment and ReplicaSet controllers acted (ReplicaSets and pods exist), so the break is at the next hop. A pod with no node and no FailedScheduling event has not been looked at by any scheduler: if the scheduler had tried and failed, it would have recorded an event explaining why. So the kube-scheduler is not running, or no replica holds leadership, or the pods name a schedulerName nobody serves.

Confirm: kubectl get pods -n kube-system -l component=kube-scheduler (on kubeadm clusters the scheduler is a static pod — was its manifest restored on the new node?); kubectl get lease kube-scheduler -n kube-system -o yaml and check renewTime is recent and holderIdentity names a live instance; read the scheduler's logs for certificate or connection errors (a replaced node with a wrong kubeconfig or expired certificate cannot talk to the API server); check spec.schedulerName of a stuck pod. Fix the scheduler's manifest or credentials; pods schedule within seconds as the queue is processed. Afterwards, add an alert on the scheduler lease's renew age and on pending pods older than a few minutes.
