Kubernetes never runs "a container" on its own. You describe a workload — "keep ten copies of this web server running", "run this migration once", "run this agent on every machine", "run three database members that each keep their own disk" — and a controller turns that description into pods, keeps them in shape, and changes them when you change the description. Choosing the wrong kind of workload, or not knowing how the right one behaves, is behind a surprising number of incidents.

Some examples. A team deploys a new version on Friday afternoon; it cannot pull its image, and the Deployment sits half-rolled for an hour, with five broken pods and eight old ones, while everyone assumes Kubernetes "will roll back". A rollout of a busy API produces a burst of 502 errors every time, even though every new pod passes its readiness check. A Postgres cluster run as a Deployment loses data when two pods mount the same volume. A nightly CronJob that usually takes 50 minutes occasionally takes 70 and starts a second copy, which double-charges customers. A batch job over 200 data shards fails because one shard has bad input, and retries the whole thing six times.

Each of these is a predictable consequence of how a particular controller works: how a Deployment counts available pods and how far it lets the count fall; what happens at the old pod's end of a rollout; what a StatefulSet promises about identity and storage and what it does not; how Jobs and CronJobs retry and overlap.

This lesson starts with the pod itself — what is shared inside it, its lifecycle, init containers and sidecars — then the ReplicaSet that keeps a count, and the Deployment that rolls between versions, traced step by step with real numbers, including a rollout that gets stuck and the rollback that fixes it. Then it covers StatefulSets, DaemonSets, Jobs and CronJobs, each with the mechanism that decides its behaviour, and ends with how to choose between them.

Crews, a roster and a shift manager

Think of a delivery company. The smallest thing it schedules is not a person but a crew: a driver and, sometimes, a helper who ride in the same van, share its radio and its storage, and are always dispatched together. In Kubernetes that crew is a Pod: one or more containers that share a network identity and volumes and are always placed on the same node.

Different kinds of work need different managers:

  • A Deployment is the manager of the general delivery fleet: "keep ten vans on the road". Any van is as good as any other. When the vans are upgraded, the manager adds a few new vans, retires a few old ones, and repeats, never letting the fleet fall below a safe number. Underneath, it uses a ReplicaSet per van model, a simple roster that only knows "there should be ten of these".
  • A StatefulSet manages named routes: "route 0, route 1, route 2", each with its own locker of parcels. If route 1's van breaks down, its replacement is also called route 1 and gets the same locker.
  • A DaemonSet puts exactly one maintenance person at every depot, including new depots as they open.
  • A Job is a one-off task: "deliver these 200 parcels, 20 vans at a time, and tell me when it's done". A CronJob is a recurring one: "every night at 2 a.m."

The one loop they all share

Every workload controller is the same shape of loop from k8s6, applied to a different question. Each one reads its object's spec (how many, which template, which ordering), counts the pods it owns by label and owner reference, and creates or deletes pods to close the gap, writing what it observed into the object's status. What differs is the policy wrapped around that loop: the Deployment's policy is "move between templates without dropping below a floor or rising above a ceiling"; the StatefulSet's is "one at a time, in order, each with its own name and disk"; the DaemonSet's is "one per eligible node"; the Job's is "until enough have succeeded, retrying failures within a budget"; the CronJob's is "create a Job at each scheduled time". When a workload misbehaves, ask which policy is in play and what the controller currently observes — kubectl describe on the controller object shows both, and its events say what it last did.

Where the analogy breaks: a broken van can be repaired and sent out again, but a pod is never repaired or moved. If its node fails, the pod is gone, and its manager creates a new pod — with a new name (except under a StatefulSet) and a new IP address — somewhere else. That disposability is the single most important property to design around: any state that matters must live outside the pod, in a volume or a database.

1. The Pod: what is shared, and its lifecycle

A Pod is the smallest unit Kubernetes schedules: a set of containers that the kubelet runs together on one node, inside one pod sandbox (k8s6). Inside a pod, containers share:

  • The network namespace: one IP address, one port space. Containers reach each other on localhost, and two containers in one pod cannot both listen on port 8080.
  • Volumes declared in the pod spec, which each container can mount at its own path, such as an emptyDir scratch directory both write to.
  • Optionally the process namespace (shareProcessNamespace: true), so containers see each other's processes.

Each container still has its own image, root file system, resource limits and restart count. A pod's restartPolicy (Always, the default and the only one Deployments allow; OnFailure; or Never) tells the kubelet what to do when a container exits; restarts happen in place on the same node with back-off, and the pod keeps its name and IP.

A pod's life is summarised by its phase:

PhaseMeaning
PendingAccepted, but not all containers running: waiting to be scheduled, pulling images, or running init containers
RunningBound to a node, all containers created, at least one running (or restarting)
SucceededAll containers exited with code 0 and will not restart (Jobs)
FailedAll containers terminated, at least one with failure, and will not restart
UnknownThe node stopped reporting; the state cannot be read

Phase is coarse. The detail is in conditions (PodScheduled, Initialized, ContainersReady, Ready) and in each container's state: Waiting with a reason such as ContainerCreating, ImagePullBackOff or CrashLoopBackOff; Running; or Terminated with an exit code and reason such as OOMKilled. A pod can be Running but not Ready — up, but failing its readiness probe and therefore receiving no Service traffic. k8s13 is about reading these.

Termination is the half of the lifecycle that causes most rollout errors. When a pod is deleted, two things start in parallel: the kubelet runs any preStop hook and then sends SIGTERM to each container's PID 1; and the endpoint controllers remove the pod from Services, a change that takes a moment to reach every node's kube-proxy and any external load balancer. After terminationGracePeriodSeconds (30 by default), remaining processes get SIGKILL. sc15 gives the standard recipe (a short preStop sleep, drain on SIGTERM, grace period long enough), and the drill at the end shows what happens without it.

2. Init containers and native sidecars

Init containers are listed in spec.initContainers and run one at a time, in order, each to successful completion, before any app container starts. They are for setup that must finish first: waiting until a dependency's DNS name resolves, running a schema migration, downloading a model or configuration into a shared emptyDir, fixing file permissions on a volume. If one fails, the kubelet restarts it per the pod's restart policy; the pod stays Pending with status Init:CrashLoopBackOff or Init:1/2.

A sidecar is a helper container that runs alongside the main one for its whole life: a service-mesh proxy, a log shipper, a credential refresher. For years sidecars were just extra app containers, which caused ordering bugs: the app could start before its proxy was ready, and a Job's pod never finished because the sidecar kept running after the main container exited. Native sidecars (stable since 1.33) fix this: declare the sidecar in initContainers with restartPolicy: Always. It starts in init order (the next init container or the app waits until it has started, or passed its startup probe), keeps running beside the app, is restarted if it exits, does not block a Job from completing, and is shut down after the app containers on termination.

spec:
  initContainers:
  - name: migrate                     # runs once, must succeed
    image: myorg/api:1.4.2
    command: ["python", "-m", "api.migrate"]
  - name: log-shipper                 # native sidecar
    image: fluent/fluent-bit:4.0
    restartPolicy: Always
  containers:
  - name: api
    image: myorg/api:1.4.2

3. ReplicaSets: keeping a count

A ReplicaSet has three fields that matter: replicas, a label selector and a pod template. Its controller reconciles one number: count the pods that match the selector and are not being deleted; if there are fewer than replicas, create pods from the template; if more, delete some (preferring pods that are not yet ready, on nodes with more replicas, or newer). That is all it does. It does not know about versions or rollouts, and it never updates existing pods when you change its template; only new pods use the new template.

Membership is by label, and ownership is recorded in owner references (k8s6). A pod that matches the selector and has no owner is adopted; a pod whose labels are edited so it no longer matches is released, and the ReplicaSet creates a replacement. You rarely create ReplicaSets yourself. They are the building block that Deployments use.

4. Deployments: rolling between versions

A Deployment manages ReplicaSets. Each distinct pod template gets its own ReplicaSet, named with a hash of the template (web-7d9f6c8b5), and its pods carry the label pod-template-hash=7d9f6c8b5 so the ReplicaSets' selectors do not overlap. When you change anything in the template — the image, an environment variable, a resource request, even an annotation inside the template — the hash changes, a new ReplicaSet is created, and the Deployment controller moves replicas from the old ReplicaSet to the new one. Changes outside the template, such as replicas, do not create a new ReplicaSet.

The default strategy is RollingUpdate, paced by two settings:

  • maxSurge: how many pods may exist above the desired count during the rollout. A percentage is rounded up.
  • maxUnavailable: how many pods may be unavailable below the desired count. A percentage is rounded down.

Both default to 25%. A pod counts as available when it has been ready for at least minReadySeconds (0 by default). The controller's two rules on each reconcile are: never let the total number of pods exceed replicas + maxSurge; and when scaling the old ReplicaSet down, never let available pods drop below replicas − maxUnavailable. The other strategy, Recreate, deletes all old pods before creating any new ones, which causes downtime but guarantees two versions never run together — sometimes required for schema or protocol changes.

5. A rolling update, step by step

Take the example the Kubernetes documentation uses: 10 replicas, maxSurge: 3, maxUnavailable: 2 (the same numbers the 25% defaults produce for 10 replicas: 2.5 rounded up is 3, rounded down is 2). So the controller may run at most 13 pods and must keep at least 8 available. You run kubectl set image deployment/web nginx=nginx:1.28. Assume each new pod takes about 20 seconds to become ready.

StepOld RS (ready)New RS (ready)TotalAvailableWhat the controller did
010 (10)0 (0)1010Template changed; new ReplicaSet created at 0
18 (8)3 (0)118New up by 3 (10 → 13 allowed); old down by 13 − 8 − 3 unready new = 2
28 (8)3 (3)1111New pods passed readiness (~20 s later)
35 (5)5 (3)108New up by 2 (11 → 13); old down by 13 − 8 − 2 = 3

50 (0)10 (8)108After 3 more ready: new up by 2; old down by 3

Three variations are worth knowing. With maxSurge: 25%, maxUnavailable: 0 (popular for latency-sensitive services), the old ReplicaSet is never scaled down until new pods are ready, so capacity never drops, but the rollout needs room for the extra pods — on a full cluster it waits for the autoscaler (k8s11). With maxSurge: 0, maxUnavailable: 1, no extra pods are created at all: one old pod is removed, its replacement started, and so on, which suits clusters with no spare room or workloads holding exclusive resources such as GPUs. And if you scale the Deployment in the middle of a rollout, the controller uses proportional scaling: extra replicas are split across the old and new ReplicaSets in proportion to their sizes, rather than all going to one.

6. When a rollout gets stuck, and rolling back

The documentation continues its example with an image that cannot be pulled (nginx:sometag). Follow the rules: the new ReplicaSet is scaled to 3 (surge) and then to 5, the old one down to 8. But the new pods never become ready — they sit in ImagePullBackOff — so available pods stay at 8, the floor, and the controller cannot scale the old ReplicaSet down further or the new one up further without breaking a limit. The rollout is stuck at old 8 / new 5, with 13 pods and 8 serving. The service keeps working at 80% capacity, which is exactly what maxUnavailable promised.

Kubernetes does not roll back on its own. After progressDeadlineSeconds (600 by default) without progress, the Deployment's Progressing condition becomes False with reason ProgressDeadlineExceeded; kubectl rollout status exits with an error, which a CD pipeline can act on. Rolling back is a command:

kubectl rollout history deployment/web          # revisions 1, 2, 3 …
kubectl rollout undo deployment/web             # back to the previous template
kubectl rollout undo deployment/web --to-revision=2

Undo copies an old ReplicaSet's template back into the Deployment, which is just another template change: the old ReplicaSet becomes the "new" one and a normal rolling update runs back to it. This works because the Deployment keeps old ReplicaSets, scaled to zero, up to revisionHistoryLimit (10 by default). In GitOps setups (k8s12), the rollback should be a Git revert instead, so the repository and the cluster agree.

Rollouts can also be paused (kubectl rollout pause) to batch several template changes into one rollout, and resumed. And the readiness probe is the quality gate of the whole process: if it passes while the app is not really ready (a probe that only checks that the process is up), the rollout proceeds happily into a broken state.

7. StatefulSets: identity and storage

Some workloads cannot be interchangeable. A three-member etcd or ZooKeeper ensemble needs each member to have a stable identity its peers recognise; a Kafka broker owns specific partitions on its own disk; a Postgres replica must reattach to its own data after a restart. A StatefulSet provides three guarantees for each pod:

  1. A stable name with an ordinal: db-0, db-1, db-2. If db-1 is deleted or its node dies, its replacement is also db-1.
  2. A stable network identity through a headless Service (a Service with clusterIP: None, named in the StatefulSet's serviceName): DNS resolves db-1.db.prod.svc.cluster.local to whatever IP db-1 currently has.
  3. Stable storage: for each entry in volumeClaimTemplates, the controller creates a PersistentVolumeClaim per pod (data-db-0, data-db-1…). A replacement db-1 reattaches data-db-1. Scaling down does not delete claims by default; persistentVolumeClaimRetentionPolicy (stable since 1.32) can delete them on scale-down or deletion.

And it adds ordering. With the default podManagementPolicy: OrderedReady, pods are created one at a time from 0 upwards, each waiting until the previous is running and ready, and deleted in reverse order. Rolling updates go from the highest ordinal down, one pod at a time by default. rollingUpdate.partition: N updates only ordinals ≥ N, which lets you canary a new version on db-2 before touching db-0; rollingUpdate.maxUnavailable (beta since 1.35) allows updating several pods at once. podManagementPolicy: Parallel drops the ordering for workloads that do not need it.

What a StatefulSet does not do is understand the application. It does not replicate data, decide which member is primary, wait for replication to catch up before restarting the next pod, or take backups. That is why databases on Kubernetes are almost always run by an operator — a controller that encodes the database's operational knowledge and drives the StatefulSet (or pods directly) safely. k8s9 covers the volumes underneath.

8. DaemonSets: one per node

A DaemonSet ensures that every node — or every node matching a nodeSelector or affinity, and whose taints the pod tolerates — runs exactly one copy of a pod. When a node joins, the DaemonSet controller creates a pod for it (the default scheduler places it, with node affinity pinning it to that node); when a node leaves, the pod goes with it. Typical DaemonSets: the CNI plugin, kube-proxy, log collectors (Fluent Bit), metrics agents (node-exporter), CSI node drivers, and GPU device plugins (k8s14). Because they often need to run everywhere, including on tainted control-plane or GPU nodes, DaemonSet pods usually carry broad tolerations, and they are created with tolerations for node-condition taints such as not-ready so they can run on a node before it is fully healthy (the network plugin is what makes it healthy). Updates use RollingUpdate with maxUnavailable: 1 by default, node by node; maxSurge can be set to start the new pod on a node before stopping the old one, for agents that must never be absent.

9. Jobs: work that finishes

A Job runs pods until a number of them succeed. The key fields:

  • completions (default 1): how many pods must exit successfully.
  • parallelism (default 1): how many may run at once.
  • completionMode: Indexed: each pod gets an index 0…completions−1 in the JOB_COMPLETION_INDEX environment variable and its hostname, so pod 17 processes shard 17. Without it, pods are interchangeable and must coordinate work themselves, for example through a queue.
  • backoffLimit (default 6): how many pod failures are tolerated before the whole Job is marked Failed. Failed pods are retried with exponential back-off (10 s, 20 s, 40 s…, capped at six minutes). Pods must use restartPolicy: OnFailure or Never.
  • activeDeadlineSeconds: a hard cap on the Job's duration, after which running pods are terminated and the Job fails.
  • ttlSecondsAfterFinished: delete the Job and its pods some time after it finishes, so completed Jobs do not accumulate.

Three newer policies make Jobs much better for real batch work. podFailurePolicy matches a pod failure by container exit code or pod condition and decides: FailJob immediately (exit code 42 means "bad input", retrying is pointless), Ignore (the pod was evicted or preempted; don't count it against backoffLimit), or Count. backoffLimitPerIndex (stable since 1.33) gives each index its own retry budget in an Indexed Job, so one bad shard fails alone instead of exhausting the whole Job's retries; the failed indexes are listed in the status. successPolicy declares an Indexed Job successful when specific indexes or a number of them succeed — for example when only the leader's success matters in a distributed training run.

apiVersion: batch/v1
kind: Job
metadata: { name: features-20261004 }
spec:
  completionMode: Indexed
  completions: 200
  parallelism: 20
  backoffLimitPerIndex: 2
  maxFailedIndexes: 5
  podFailurePolicy:
    rules:
    - action: FailIndex
      onExitCodes: { containerName: worker, operator: In, values: [42] }
    - action: Ignore
      onPodConditions: [ { type: DisruptionTarget } ]
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: myorg/features:3.1
        args: ["--shard=$(JOB_COMPLETION_INDEX)", "--of=200"]

Trace a run: 20 pods start with indexes 0-19. As each succeeds, the controller starts the next index, keeping 20 running. Index 57 exits with code 42 (its input file is corrupt): the rule marks index 57 failed immediately, without retries. Index 103's node is drained for maintenance: its pod gets the DisruptionTarget condition, the failure is ignored, and the index is simply run again. Index 140 fails twice with a transient error and succeeds on the third attempt — within its per-index limit of 2 retries. At the end, 199 indexes succeeded and one failed; since that is within maxFailedIndexes: 5, the controller marks the Job Failed only after every index has been attempted, and lists index 57 in status.failedIndexes, so a rerun can target just that shard.

10. CronJobs: work on a schedule

A CronJob creates a Job from its jobTemplate on a cron schedule ("0 2 * * *" for 02:00 every day), in the controller manager's time zone unless timeZone names one (for example Europe/London). Its controller checks every 10 seconds. Four settings decide its behaviour at the edges:

  • concurrencyPolicy: Allow (default) starts the next run even if the previous one is still going; Forbid skips it; Replace stops the old run and starts the new one.
  • startingDeadlineSeconds: how late a run may still start after its scheduled time (if the controller was down, or a Forbid policy delayed it). If the controller finds more than 100 missed schedules to consider, it does not start the Job and logs "too many missed start times", which is why setting this field matters for frequent schedules.
  • successfulJobsHistoryLimit (3) and failedJobsHistoryLimit (1): how many finished Jobs to keep.
  • suspend: pause future runs without deleting the CronJob.

CronJobs create a Job at roughly the scheduled time, and in rare cases (controller restarts, clock issues) a run can be missed or doubled. Jobs they start should therefore be idempotent: processing "yesterday's partition" rather than "everything since the last run", and using unique keys so a second run does not double-count.

Bare pods — created directly, with no controller — are for experiments only: nothing recreates them if they or their node die.

How the Deployment controller decides, in code terms

Each reconcile of a Deployment does roughly this: find all ReplicaSets it owns; identify the one whose template hash matches the current template (create it if missing); if the Deployment is paused, only scale; otherwise run the strategy. For RollingUpdate, "reconcile new" scales the new ReplicaSet up to at most replicas + maxSurge − (pods in all other ReplicaSets), and "reconcile old" first deletes unhealthy old pods (which reduces capacity at no cost), then scales old ReplicaSets down by at most allPods − minAvailable − newUnavailable. The controller writes those scale changes to the ReplicaSets and returns; the ReplicaSet controllers create and delete the pods; the next reconcile happens when pod readiness changes. This split — Deployment computes target sizes, ReplicaSets enforce them — is the decoupling the Borg paper describes: a higher-level controller adjusts a number and lets a lower-level one implement it, just as the autoscaler adjusts a Deployment's replicas without knowing how pods are created.

Which pods get deleted on scale-down

When a ReplicaSet must remove pods, the order is deliberate: pods not yet assigned to a node first, then pending before running, not-ready before ready, pods on nodes with more replicas of the same ReplicaSet (to keep spread), pods that have been ready for less time, pods with more restarts, newer pods before older. Two knobs let you influence it: the controller.kubernetes.io/pod-deletion-cost annotation (lower cost deleted first), which an autoscaler or the application can set to remove the least-loaded or least-valuable replicas; and, for StatefulSets, the strict highest-ordinal-first rule.

Readiness gates and rollout safety

Readiness is the signal every rollout waits on, so making it meaningful is the main lever on rollout safety. A readiness probe should fail until the pod can really serve: model weights loaded, caches warmed, connections to dependencies established. minReadySeconds adds a soak time so a pod that crashes 15 seconds after start does not count as available. Pod readiness gates let an external controller add its own condition — for example a cloud load balancer controller marking a pod ready only once the load balancer's health checks see it — which prevents rollouts from outpacing external routing. And progressive-delivery tools (Argo Rollouts, Flagger) replace the Deployment's blind rolling update with metric-gated steps (swe9's canary analysis).

StatefulSet failure semantics: why it waits

If a node running db-1 becomes unreachable, the StatefulSet controller does not create a new db-1 elsewhere as soon as the pod is marked for deletion, because the old one might still be running on the partitioned node and writing to the same volume. It waits until the old pod object is really gone, which, for an unreachable node, means the kubelet confirms or someone force-deletes it. This "at most one" guarantee protects data at the cost of availability, and it is why a StatefulSet pod on a dead node can stay Terminating until an operator intervenes (or until the non-graceful node shutdown feature, with an out-of-service taint, lets volumes be detached safely). Force-deleting such a pod while the node may still be alive is how split-brain happens.

Job tracking with finalizers and large-scale batch

Early Job controllers counted finished pods by looking at pods that still existed, so if pods were garbage-collected before being counted, Jobs miscounted. The controller now adds a finalizer to each pod it creates and removes it only after recording the pod's outcome in the Job's status, which makes tracking exact even for Jobs with thousands of pods. For very large or multi-tenant batch systems, Jobs are usually combined with queueing: Kueue holds Jobs suspended (spec.suspend: true) until quota is available and then admits them as a whole, which matters for all-or-nothing workloads such as distributed training where starting half the pods wastes GPUs (k8s14).

Version skew during rollouts

Every strategy except Recreate runs two versions simultaneously, and Kubernetes cannot know whether they are compatible. During the table above, requests may hit 1.27 and 1.28 alternately; a user's session may bounce between them; old and new pods share a database. Schema changes must follow expand-contract (swe9), APIs must accept both old and new message shapes, and caches must tolerate entries written by either version. Rolling back reverses the same skew, so "can the old version read what the new one wrote?" is a question every release must answer.

The case: the Kubernetes documentation's stuck rollout

The Kubernetes Deployments page walks through exactly the failure in body section 6, with real output, and it is worth reading as a case study because the behaviour surprises many teams. A Deployment of 10 nginx replicas with maxSurge=3 and maxUnavailable=2 is updated to an image tag that cannot be resolved from inside the cluster. kubectl get rs then shows the old ReplicaSet at 8 desired, 8 current, 8 ready, and the new one at 5 desired, 5 current, 0 ready: the controller scaled up as far as the surge allowed and down as far as the availability floor allowed, and stopped. The page then scales the Deployment from 10 to 15 mid-rollout to show proportional scaling: the 5 extra replicas are split 3 to the old ReplicaSet and 2 to the new one in proportion to their sizes, rather than all going to the broken new version.

The page's notes are the operational lessons. "Kubernetes takes no action on a stalled Deployment other than to report a status condition with reason: ProgressDeadlineExceeded"; higher-level orchestrators can act on it, for example by rolling back. Pausing a rollout suspends the deadline. Setting revisionHistoryLimit to 0 removes the ability to roll back. In practice this means: your CD pipeline must run kubectl rollout status --timeout (or watch the condition) and decide what to do; progressive-delivery tools automate the rollback; and alerting on ProgressDeadlineExceeded catches stuck rollouts that nobody is watching — common on Friday afternoons.

Failure modes by workload

  • Deployment rollout 502s: termination races (no preStop, app exits on SIGTERM immediately) or readiness that passes too early. Fix shutdown; tighten readiness; consider minReadySeconds.
  • Rollout blocked on a full cluster with maxUnavailable: 0: surge pods stay Pending until the cluster autoscaler adds a node. Budget headroom or allow some unavailability.
  • Node drain stuck: a PodDisruptionBudget with minAvailable equal to replicas (or a single-replica Deployment with maxUnavailable: 0 PDB) blocks evictions forever. PDBs must allow at least one disruption.
  • StatefulSet pod stuck Terminating on an unreachable node: by design (deep section). Recover the node, or use the out-of-service taint workflow; do not force-delete blindly.
  • CronJob overlaps or missed runs: default Allow policy with long runs; no startingDeadlineSeconds after controller downtime; non-idempotent jobs.
  • Job retries exhausting the budget on deterministic errors: add podFailurePolicy rules for non-retriable exit codes; use per-index limits.
  • Thousands of finished Jobs and pods slowing the API: set ttlSecondsAfterFinished and CronJob history limits.

Knobs

maxSurge/maxUnavailable (speed versus spare capacity), minReadySeconds (soak time), progressDeadlineSeconds (how soon a stuck rollout is reported), revisionHistoryLimit (rollback depth versus clutter), terminationGracePeriodSeconds and preStop (clean exits), StatefulSet partition (canary by ordinal), Job parallelism (throughput versus cluster pressure) and CronJob concurrencyPolicy.

What to watch

Deployment conditions (Progressing, Available) and the gap between replicas, updatedReplicas and availableReplicas; StatefulSet currentRevision versus updateRevision; DaemonSet numberMisscheduled and numberUnavailable; Job failed counts, failedIndexes and duration; CronJob lastSuccessfulTime (alert if too old — a silent CronJob is a classic unnoticed failure). kube-state-metrics exposes all of these to Prometheus.

    import math
def rollout(replicas=10, surge="25%", unavail="25%", ready_per_step=None):
    pct = lambda v, up: (math.ceil if up else math.floor)(replicas * int(v[:-1]) / 100) if isinstance(v, str) else v
    max_surge, max_unavail = pct(surge, True), pct(unavail, False)
    max_total, min_avail = replicas + max_surge, replicas - max_unavail
    old, new, new_ready, step = replicas, 0, 0, 0
    print(f"maxSurge={max_surge} maxUnavailable={max_unavail}: total<={max_total}, available>={min_avail}")
    while not (old == 0 and new_ready == replicas):
        new_up = min(max_total - (old + new), replicas - new)
        new += max(new_up, 0)
        scale_down = (old + new) - min_avail - (new - new_ready)
        old -= max(min(scale_down, old), 0)
        print(f"step {step}: old={old:2} new={new:2} (ready {new_ready:2}) total={old+new:2} available={old+new_ready:2}")
        new_ready = new if ready_per_step is None else min(new, new_ready + ready_per_step)
        step += 1
        if step > 30: print("stuck"); break

Diagnose: 502s during every rollout

An API runs as a Deployment of 12 replicas (maxSurge: 25%, maxUnavailable: 0) behind a cloud load balancer via an Ingress. Readiness checks /healthz, which returns 200 as soon as the process starts. During each deploy, error rates spike to 3% for about a minute, almost all 502s and connection resets, and recover once the rollout finishes. New pods log no errors. Explain the likely causes and the fix, and how you would verify it.

Answer

Two independent problems, one on each end of a pod's life. Exit side: when an old pod is deleted, the kubelet sends SIGTERM at the same moment the pod is removed from endpoints; the load balancer, Ingress controller and every node's kube-proxy take a few seconds to stop routing to it. If the app exits on SIGTERM (or is killed because its PID 1 ignores it until SIGKILL — k8s1), requests already in flight and those routed in the propagation window get resets and 502s. Start side: /healthz passes before the app can serve (connection pools, caches, JIT warm-up), so the rollout counts pods as available — and the load balancer sends them traffic — too early; with maxUnavailable: 0 capacity is fine on paper, but the new pods time out under load.

Fix: add lifecycle.preStop: sleep 10 (or the built-in sleep action) so endpoint removal propagates before shutdown begins; make the app drain on SIGTERM — stop accepting, finish in-flight requests, then exit; set terminationGracePeriodSeconds to cover the sleep plus the longest request; ensure exec-form entrypoint so the signal arrives. Make readiness meaningful (a /ready that checks warm-up and dependencies) and add minReadySeconds: 10; for cloud load balancers that route directly to pod IPs, use the controller's readiness gate. Verify by deploying in a load test and comparing error rate during rollout before and after; watch per-pod request counts drop to zero before each pod exits.
