A checkout service calls a payments service. In Kubernetes both are sets of pods that come and go: a rollout replaces every payments pod with new ones on different nodes with different IP addresses; the autoscaler adds three more at lunch and removes them at two; a node dies and its pods reappear elsewhere. Yet checkout simply connects to http://payments and it works, every time, without anyone updating a configuration file. How?

The answer involves more moving parts than most engineers realise. A DNS server inside the cluster turns payments into a virtual IP address that belongs to no machine. A controller keeps a list of which payments pods are ready. An agent on every node turns that list into kernel rules that rewrite the destination of each new connection to one of those pods. A network plugin makes sure a packet addressed to a pod on another node gets there. And none of that helps a customer on the internet, who needs yet another layer — a load balancer, an ingress controller or a gateway — to get into the cluster at all.

When one of these parts misbehaves, the symptoms are confusing. DNS lookups that take five seconds. A gRPC service where one pod is at 90% CPU and the rest idle. Client IP addresses that all look like node IPs. Connection errors for a few seconds after every rollout. A NetworkPolicy that "doesn't work". An ingress controller that turns out to be the easiest way into the whole cluster: in March 2025, the IngressNightmare vulnerabilities in ingress-nginx, the controller in front of roughly half of all clusters, let any pod in a cluster run code inside the controller and read every Secret.

This lesson builds the picture from the bottom. It starts with the network model and how CNI plugins give pods addresses and connectivity, then Services and EndpointSlices, then follows one connection through kube-proxy's rules packet by packet. It covers CoreDNS and its most common trap, the other Service types and traffic policies, NetworkPolicy, and finally getting traffic into the cluster with Ingress and its successor, the Gateway API.

A switchboard with extension numbers

Imagine a large company where employees change desks constantly. Calling a person's desk phone directly is hopeless: the number is wrong by the afternoon. So the company publishes department extensions: dial 4100 for Payments and you reach someone in Payments, whoever is at a desk today. A directory maps names to extensions ("Payments → 4100"). And on every floor there is a small automatic switch that, the moment you dial 4100, rewrites the call to the desk number of one available Payments person, picking a different one each time.

Kubernetes Services work the same way:

  • Each pod has its own IP address, like a desk phone, and the network model guarantees any pod can call any other pod directly. A CNI plugin wires up the desks.
  • A Service is the department extension: a stable virtual IP (the ClusterIP) and name for a group of pods selected by labels.
  • CoreDNS is the directory: payments.shop.svc.cluster.local → 10.96.120.15.
  • The EndpointSlice controller keeps the list of who is at a desk and ready.
  • kube-proxy is the switch on every floor: it programs each node's kernel so a connection to the ClusterIP is rewritten to one ready pod's IP.

Three kinds of address, three meanings

Much confusion in Kubernetes networking comes from mixing up three address ranges that look alike but behave completely differently. A node IP (say 192.168.0.11) belongs to a machine's real network interface; the underlying network knows how to reach it. A pod IP (say 10.244.1.23) belongs to a pod's eth0 inside its network namespace; it is real in the sense that packets are addressed to it and arrive at it, but whether the underlying network knows about it depends on the CNI plugin. A ClusterIP (say 10.96.120.15) belongs to nothing at all: no interface has it, nothing answers ARP for it, and you cannot ping it in iptables mode. It exists only as a pattern in each node's packet rules, which rewrite it to a pod IP before the packet goes anywhere. When something fails, the first question is which of the three addresses the client was using, because each fails in its own way.

Getting in from outside is a separate layer: a NodePort or LoadBalancer Service opens a door at the edge of the cluster, and an Ingress or Gateway controller — a reverse proxy running as pods — routes HTTP requests by hostname and path to Services. Policies about who may talk to whom are expressed as NetworkPolicy and enforced by the CNI plugin.

Where the analogy breaks: the floor switch makes its choice once per connection, not per request. A client that opens one long-lived connection and sends a million requests over it talks to the same pod the whole time. That single fact explains most "load balancing doesn't work" complaints in Kubernetes.

1. The network model, and who implements it

Kubernetes states the rules and leaves the implementation to a plugin. The rules:

  1. Every pod gets its own IP address. Containers in a pod share it and reach each other on localhost (k8s7).
  2. Every pod can reach every other pod, on any node, using that IP, without NAT: the receiving pod sees the sender's real pod IP.
  3. Agents on a node (the kubelet, for probes) can reach all pods on that node.

Compare Docker's model from k8s4, where containers sit behind per-host NAT and are reached through published host ports. The Borg-Omega-Kubernetes paper explains why Kubernetes rejected that: in Borg all containers shared their machine's IP, so ports had to be allocated by the scheduler, which broke DNS, URLs and ordinary tools. An IP per pod lets every application use its normal well-known port.

The address plan has three separate ranges: the node network (say 192.168.0.0/16), the pod CIDR (say 10.244.0.0/16, split per node: node-a gets 10.244.1.0/24, node-b 10.244.3.0/24), and the Service CIDR (say 10.96.0.0/12) from which ClusterIPs are allocated.

The CNI (Container Network Interface) is the contract between the container runtime and network plugins. When the kubelet creates a pod sandbox (k8s6), containerd invokes the configured plugin binary with the command ADD, the sandbox's network namespace path and a JSON configuration. The plugin creates a veth pair, moves one end into the pod namespace as eth0, assigns an IP from the node's range (through an IPAM plugin), adds routes, and returns the result. On deletion it is called with DEL. How a packet then crosses between nodes is the plugin's design choice:

ApproachHow pod packets cross nodesExamplesTrade-off
OverlayEncapsulated in UDP (VXLAN) or IP-in-IP between node IPsFlannel VXLAN, Calico IPIP/VXLANWorks on any network; ~50 bytes overhead per packet, lower MTU

A worked crossing with an overlay: pod 10.244.2.9 on node-b (192.168.0.12) sends to pod 10.244.1.17 on node-a (192.168.0.11). The packet leaves the pod's veth; node-b's routing table says 10.244.1.0/24 is reached through the flannel.1 VXLAN device; the kernel wraps the whole packet in a UDP datagram from 192.168.0.12 to 192.168.0.11 port 8472; node-a's VXLAN device unwraps it and routes the inner packet, still from 10.244.2.9, to the target pod's veth. No address was translated: rule 2 holds.

2. Services and EndpointSlices

A Service is an object with a selector and ports:

apiVersion: v1
kind: Service
metadata: { name: payments, namespace: shop }
spec:
  selector: { app: payments }
  ports:
  - name: http
    port: 80            # the Service's port
    targetPort: 8080    # the container's port

On creation, the API server allocates a ClusterIP from the Service CIDR, say 10.96.120.15. The EndpointSlice controller watches Services and pods; for each Service it maintains one or more EndpointSlice objects (up to 100 endpoints each by default) listing every pod that matches the selector: its IP, the target port, its node and zone, and conditions — ready, serving, terminating. A pod that fails its readiness probe stays in the slice with ready: false, and kube-proxy stops sending new connections to it; a pod being deleted is marked terminating.

$ kubectl get endpointslices -n shop -l kubernetes.io/service-name=payments
NAME             ADDRESSTYPE   PORTS   ENDPOINTS                            AGE
payments-x7q2c   IPv4          8080    10.244.1.17,10.244.1.23,10.244.3.4   4d

Slices replaced the older single Endpoints object per Service because, for a Service with thousands of pods, every single pod change re-sent the whole list to every node (k8s6). With slices, a change re-sends only one slice of up to 100 entries.

3. kube-proxy: one connection, traced through the rules

kube-proxy runs on every node, watches Services and EndpointSlices, and writes kernel packet rules. It has three modes on Linux: iptables (the default), nftables (the newer kernel framework, generally available since 1.33 and recommended by the docs as the replacement for the others), and IPVS (a kernel load balancer with hash tables, deprecated since 1.35, disabled by default from 1.40 and to be removed in 1.43). Some CNIs (Cilium) replace kube-proxy entirely with eBPF. The iptables mode shows the mechanism most plainly, so trace a connection through it.

For our Service with three ready endpoints, kube-proxy generates rules like these (from iptables-save -t nat, chain hashes shortened):

-A KUBE-SERVICES -d 10.96.120.15/32 -p tcp --dport 80 -j KUBE-SVC-PAYM
-A KUBE-SVC-PAYM ! -s 10.244.0.0/16 -d 10.96.120.15/32 -p tcp --dport 80 -j KUBE-MARK-MASQ
-A KUBE-SVC-PAYM -m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-AAAA
-A KUBE-SVC-PAYM -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-BBBB
-A KUBE-SVC-PAYM -j KUBE-SEP-CCCC
-A KUBE-SEP-AAAA -p tcp -j DNAT --to-destination 10.244.1.17:8080
-A KUBE-SEP-BBBB -p tcp -j DNAT --to-destination 10.244.1.23:8080
-A KUBE-SEP-CCCC -p tcp -j DNAT --to-destination 10.244.3.4:8080

Now the client pod 10.244.2.9 on node-b connects to 10.96.120.15:80:

  1. SYN leaves the pod: 10.244.2.9:51122 → 10.96.120.15:80. It crosses the veth into node-b's root network namespace.
  2. PREROUTING, nat table: the jump to KUBE-SERVICES matches the ClusterIP and port, so the packet enters KUBE-SVC-PAYM. The source is inside the pod CIDR, so the masquerade-mark rule does not apply.
  3. Random choice: the first rule matches with probability 1/3. Suppose it does not. The second matches with probability 1/2 of what is left — 1/3 overall. Suppose it does: jump to KUBE-SEP-BBBB. (The third rule catches the remaining 1/3.) Each endpoint gets an equal share of new connections.
  4. DNAT: the destination becomes 10.244.1.23:8080. conntrack records the original and translated tuples.
  5. Routing: 10.244.1.0/24 lives on node-a, so the CNI carries the packet there (VXLAN in our example). The payments pod sees a SYN from 10.244.2.9 — the client's real address — to its own 8080.
  6. Reply: 10.244.1.23:8080 → 10.244.2.9:51122 travels back to node-b, where conntrack recognises the flow and rewrites the source to 10.96.120.15:80 before delivering it to the client, which therefore sees an answer from the address it called.
  7. Every later packet of this connection skips the rule walk: conntrack applies the same translation. The choice was made once.

Three consequences follow from "the decision is per connection, made by random choice, remembered by conntrack". Balance is statistical and per connection: a client using HTTP/1.1 keep-alive or gRPC over HTTP/2 sends all its requests to one pod. Removing a pod does not move existing connections: kube-proxy updates the rules for new connections, but conntrack entries for open ones still point at the old pod, so the pod must drain gracefully (k8s7). Rule count grows with Services and endpoints: iptables evaluates its Service matches as a list, so very large clusters (tens of thousands of Services) saw slow rule updates and per-packet cost, which is what IPVS and now nftables, with hash-based lookups, address.

Two more rules in the real output explain edge cases. The KUBE-MARK-MASQ rule marks packets to the ClusterIP from outside the pod CIDR (a process on the node itself, or a NodePort client) so they are source-NATed on the way out; otherwise the reply from the pod would go straight back to the original sender, bypassing the un-DNAT. And a hairpin case — a pod connecting to its own Service and being DNATed to itself — is also masqueraded so the reply returns through the bridge correctly.

4. DNS: CoreDNS, search domains and ndots

CoreDNS runs as a Deployment (two replicas by default in kubeadm clusters) behind a Service, conventionally kube-dns at a fixed ClusterIP such as 10.96.0.10. Its kubernetes plugin watches Services and EndpointSlices and answers:

  • payments.shop.svc.cluster.local → A record 10.96.120.15 (the ClusterIP);
  • for a headless Service, one A record per ready pod, and for StatefulSet pods db-0.db.shop.svc.cluster.local → that pod's IP (k8s7);
  • SRV records for named ports: _http._tcp.payments.shop.svc.cluster.local;
  • anything outside cluster.local is forwarded to upstream resolvers.

The kubelet writes each pod's /etc/resolv.conf (for the default dnsPolicy: ClusterFirst):

nameserver 10.96.0.10
search shop.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

The search list lets a pod in shop say just payments, or payments.other for another namespace. The ndots:5 option says: if a name has fewer than five dots, try it with each search suffix first, and only then as written. That is right for cluster names (payments has zero dots and should get shop.svc.cluster.local appended) and wasteful for external ones. Trace a pod in shop calling api.stripe.com (two dots):

#QueryResult
1-2api.stripe.com.shop.svc.cluster.local (A, AAAA)NXDOMAIN
3-4api.stripe.com.svc.cluster.local (A, AAAA)NXDOMAIN
5-6api.stripe.com.cluster.local (A, AAAA)NXDOMAIN
7-8api.stripe.com.<node search domain, e.g. ec2.internal>NXDOMAIN (if the node has one)
9-10api.stripe.com (A, AAAA)Answer

Up to ten queries for one lookup, each a round trip to CoreDNS and, for the misses, sometimes to upstream. Under load this shows up as DNS latency in every outbound call and as CoreDNS CPU. Fixes, from cheapest: write external names fully qualified with a trailing dot (api.stripe.com.), which skips the search list; lower ndots for chatty workloads through the pod's dnsConfig (options: [{name: ndots, value: "2"}]); enable CoreDNS's caching and autopath; and run NodeLocal DNSCache, a DaemonSet that answers from a cache on each node, which also sidesteps a class of conntrack races on UDP that historically caused occasional 5-second DNS timeouts.

5. The other Service types and traffic policies

NodePort extends a ClusterIP Service by opening the same port (from 30000-32767 by default) on every node; kube-proxy DNATs traffic arriving at <any node IP>:31080 to an endpoint. LoadBalancer extends NodePort: the cloud-controller-manager (or a load-balancer controller) provisions an external load balancer that forwards to the NodePorts on every node, or, with modern cloud controllers, directly to pod IPs. ExternalName is only a DNS CNAME to an outside name. A headless Service skips the virtual IP entirely.

For external traffic the externalTrafficPolicy decides a trade-off. With Cluster (default), a node that receives traffic for the Service may forward it to a pod on any node; to make the reply come back through it, it source-NATs the packet to its own IP, so the pod sees a node IP instead of the client's, and some requests take an extra hop. With Local, a node forwards only to endpoints on itself and does not SNAT: client IPs are preserved and there is no extra hop, and nodes without a local endpoint fail the load balancer's health check (on a dedicated healthCheckNodePort) so they receive nothing. The cost is imbalance: a node with one pod and a node with five each get half the traffic if the load balancer spreads evenly across nodes.

Inside the cluster, internalTrafficPolicy: Local restricts a Service's in-cluster traffic to endpoints on the same node (useful for node-local agents), and the trafficDistribution field expresses a softer preference: PreferSameZone keeps traffic within the client's zone when that zone has endpoints, which saves cross-zone data-transfer charges and latency, and PreferSameNode prefers the client's own node first.

6. NetworkPolicy

By default every pod can reach every pod. A NetworkPolicy narrows that. It selects pods in its namespace with a podSelector and lists allowed ingress sources and/or egress destinations by pod selector, namespace selector, IP block and port. The semantics are the part people get wrong:

  • A pod selected by no policy allows all traffic.
  • Once a pod is selected by any policy that covers a direction (ingress or egress), only traffic allowed by some policy in that direction is permitted. Policies only add allowances; there is no "deny" rule.
  • Replies to allowed connections are allowed automatically (enforcement is stateful).
  • Enforcement is done by the CNI plugin. If the plugin does not implement NetworkPolicy, the objects are accepted and ignored.
# 1. default deny all ingress and egress in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: shop }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# 2. payments accepts only checkout, on 8080; everyone may use DNS
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: payments-in, namespace: shop }
spec:
  podSelector: { matchLabels: { app: payments } }
  ingress:
  - from: [ { podSelector: { matchLabels: { app: checkout } } } ]
    ports: [ { port: 8080 } ]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: shop }
spec:
  podSelector: {}
  egress:
  - to: [ { namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } },
            podSelector: { matchLabels: { k8s-app: kube-dns } } } ]
    ports: [ { port: 53, protocol: UDP }, { port: 53, protocol: TCP } ]

With these three, checkout still cannot reach payments: checkout's egress is denied by policy 1 and nothing allows it. A fourth policy allowing checkout's egress to payments on 8080 completes the path — the classic "I allowed ingress but it still doesn't work" lesson. Policies match the pod's port (8080), not the Service port (80), because enforcement sees packets after kube-proxy's DNAT.

7. Getting in: Ingress and the Gateway API

A LoadBalancer Service per application gets expensive and gives only layer-4 routing. HTTP services usually share one entry point that routes by hostname and path: an Ingress controller or Gateway implementation, which is a reverse proxy (NGINX, Envoy, HAProxy, a cloud load balancer) configured from Kubernetes objects and itself exposed with a LoadBalancer Service.

Ingress is the original API: one object lists hosts, paths, backend Services and TLS secrets. Its API is frozen. Everything beyond basic routing — rewrites, timeouts, canary weights, rate limits — lives in controller-specific annotations, so Ingress objects are not portable, and one object mixes what the platform team cares about (addresses, certificates) with what the app team cares about (paths).

The Gateway API is its successor, developed by SIG Network, with a role-oriented design:

  • GatewayClass (cluster-scoped, owned by the infrastructure provider): names an implementation, like a StorageClass names a storage provider.
  • Gateway (owned by the platform team): an actual entry point with listeners — port 443, hostnames *.example.com, TLS certificates — and rules about which namespaces may attach routes.
  • HTTPRoute, GRPCRoute and others (owned by application teams): match hosts, paths, headers and methods, and send to one or more backend Services with weights, plus redirects, rewrites, header changes and timeouts.
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: api, namespace: shop }
spec:
  parentRefs: [ { name: public, namespace: infra } ]
  hostnames: ["api.example.com"]
  rules:
  - matches: [ { path: { type: PathPrefix, value: /v1 } } ]
    backendRefs:
    - { name: api-v1, port: 80, weight: 90 }
    - { name: api-v2, port: 80, weight: 10 }   # a canary, in the standard API

Gateway API implementations (Envoy Gateway, Istio, Cilium, NGINX Gateway Fabric, the major clouds' controllers and others) report conformance against the standard, so routes move between implementations. Many implementations send traffic directly to pod IPs from EndpointSlices rather than through the ClusterIP, which allows per-request load balancing — the fix for the gRPC imbalance above.

8. A request from the internet, end to end

Put the layers together for one HTTPS request from a phone to https://api.example.com/v1/orders in a cloud cluster with a Gateway implementation. DNS outside the cluster resolves api.example.com to the public address of a cloud load balancer, created for the Gateway's LoadBalancer Service by the cloud controller. The load balancer forwards the TCP connection either to a NodePort on some node (where kube-proxy DNATs it to a Gateway pod) or, with a controller that targets pods directly, straight to a Gateway pod's IP. The Gateway pod — an Envoy or NGINX process — terminates TLS with the certificate named by the Gateway's listener, then matches the request against attached HTTPRoutes: hostname api.example.com, path prefix /v1. The matching rule names backends api-v1 (weight 90) and api-v2 (weight 10). Backend selection usually happens in the proxy itself: it watches the backends' EndpointSlices and picks a ready pod per request, so it opens a connection to, say, 10.244.3.4:8080 directly, across the CNI's pod network. The pod receives the request from the Gateway pod's IP, with the original client address carried in X-Forwarded-For (or preserved at the TCP level with externalTrafficPolicy: Local and proxy protocol). If api then calls payments, that connection follows the ClusterIP path traced in section 3, with DNS through CoreDNS.

Every hop is a place where the request can fail and a component whose status you can read: the cloud load balancer's target health, the Gateway's and route's status conditions, the proxy's access log, the EndpointSlice's ready endpoints, the pod's own logs. Debugging external traffic is walking that list in order (k8s13).

Connection draining and the endpoint-propagation race

When a pod is deleted, the kubelet starts its shutdown and the EndpointSlice controller marks it terminating at about the same time. The change then fans out: every node's kube-proxy rewrites its rules, the Gateway implementation updates its upstreams, and an external load balancer deregisters the target after its own health checks or API calls — which can take from under a second to tens of seconds. Requests routed during that window to a pod that has already exited fail. The fix is on the pod side (preStop sleep plus graceful drain, k8s7), and the platform side has added help: EndpointSlices keep terminating endpoints with serving status so proxies can let in-flight requests finish, and kube-proxy can fall back to terminating-but-serving endpoints when a node has no ready ones, avoiding black holes during rollouts with externalTrafficPolicy: Local.

conntrack as a scaling limit

Every connection through a Service, and every UDP DNS exchange, occupies a conntrack entry on the client's node. Nodes with many short-lived connections — a busy API gateway, a pod making thousands of outbound calls per second without keep-alive — can fill the table (nf_conntrack_max), at which point the kernel drops new connections and logs "table full". UDP entries linger for their timeout even after the exchange is done. Remedies: connection reuse (keep-alive, pooling), raising the table size with memory in mind, NodeLocal DNSCache (which uses TCP upstream and avoids per-query conntrack entries through the Service), and eBPF dataplanes that handle Service translation without conntrack for some paths.

eBPF dataplanes replacing kube-proxy

Cilium and similar plugins attach eBPF programs at the socket and network-device layers. For Service traffic, a socket-level program can translate the ClusterIP to a pod IP at connect() time, so packets leave the pod already addressed to the pod, with no per-packet NAT and no conntrack entry for the translation. Lookups use hash maps rather than rule lists, so cost does not grow with the number of Services, and policy, Services and flow visibility share one dataplane. The trade-offs are kernel version requirements, a more complex component in the critical path, and debugging that needs plugin-specific tools instead of iptables-save.

Why the Gateway API exists, beyond features

Ingress's real problem was not missing features but where they lived. With features in annotations, a cluster's routing semantics depended on which controller read them, two controllers could interpret the same object differently, and annotations offered no validation, no status and no access control: anyone who could edit an Ingress could set any annotation — including, in ingress-nginx, snippets that injected raw NGINX configuration (another source of CVEs). The Gateway API makes routing features typed API fields with defined semantics, conformance tests and status conditions, splits ownership across resources so RBAC can match organisational roles, and adds explicit cross-namespace permission (ReferenceGrant). Its scope has grown beyond HTTP: GRPCRoute is standard, and Gateway API v1.6 graduated TCPRoute and UDPRoute to the standard channel. The GAMMA initiative applies the same route types to service-mesh (east-west) traffic.

Session affinity, and why it rarely helps

A Service can set sessionAffinity: ClientIP, which makes kube-proxy send all connections from one client IP to the same endpoint for a timeout (three hours by default). It sounds like a fix for stateful sessions, but it keys on the source IP seen by kube-proxy: behind a NAT gateway, a load balancer that SNATs, or an Ingress proxy, thousands of real users share one IP and land on one pod, which defeats balancing; and when that pod goes away, the affinity breaks anyway. Sessions that matter belong in a shared store (sc1), and request-level stickiness, where genuinely needed, belongs in the Gateway or proxy, which can use cookies or headers rather than addresses.

IP address planning

Pod and Service ranges are chosen at cluster creation and are painful to change. With cloud-native addressing, every pod consumes a VPC address: a 2,000-node cluster at 30 pods per node needs 60,000 addresses, plus headroom for surges during rollouts, which can exhaust subnets and block scaling with obscure "insufficient IP" errors. Overlays avoid that but add encapsulation and break direct reachability from outside. Dual-stack (IPv4 plus IPv6) and IPv6-only clusters remove scarcity but require every component and dependency to support IPv6. These decisions are made once, early, and are worth more design attention than they usually get.

Service meshes, briefly

A service mesh (Istio, Linkerd, Cilium's mesh) adds a proxy to the data path of in-cluster traffic — a sidecar per pod, or a per-node proxy in "ambient" designs — so that every connection can be encrypted with mutual TLS, retried, load-balanced per request and observed, without changing application code. It solves problems from this lesson (per-request balancing for gRPC, identity-based policy beyond IP-based NetworkPolicy) at the price of extra latency, resources and an important new control plane to operate. Many clusters get most of the benefit from a Gateway for north-south traffic plus NetworkPolicy and good client libraries for east-west, and adopt a mesh only when they need mutual TLS everywhere or fine-grained traffic control.

The case: IngressNightmare and the retirement of ingress-nginx

ingress-nginx was the most common Ingress controller, maintained by a small group of volunteers. Like many controllers, it ran a validating admission webhook (k8s6) so that bad Ingress objects would be rejected before reaching the proxy. To validate, the webhook built an NGINX configuration from the submitted object, wrote it to disk and ran nginx -t on it. In March 2025 Wiz Research disclosed a set of vulnerabilities, the worst being CVE-2025-1974 (CVSS 9.8): the webhook was reachable over the pod network without authentication, and crafted configuration made nginx -t load attacker-controlled code. Code running in the controller inherited its service account, which by design could read Secrets in all namespaces — every TLS key, database password and token in the cluster. Wiz estimated about 43% of cloud environments were vulnerable and found over 6,500 clusters exposing the webhook to the public internet. Patched releases (1.12.1 and 1.11.5) and mitigations (disabling the webhook temporarily, restricting access to it) followed.

In November 2025 Kubernetes SIG Network and the Security Response Committee announced that ingress-nginx would be retired in March 2026: no further releases, bug fixes or security patches, with existing deployments continuing to work and users urged to migrate — preferably to a Gateway API implementation. The post cited the difficulty of sustaining a project with best-effort maintenance and features (like configuration snippets) that are hard to secure.

Lessons for engineers: the component that terminates internet traffic is also one of the most privileged in the cluster, so treat it like one — minimal RBAC (scope Secret access to the namespaces it serves), NetworkPolicy so only the API server can reach its webhooks, no arbitrary-configuration features enabled for untrusted teams, fast patching, and an inventory of which clusters run which controller version. And depending on a critical open-source component means tracking its health, not just its version.

Failure modes and symptoms

  • Service has no endpoints: selector does not match pod labels, or no pod is ready. kubectl get endpointslices -l kubernetes.io/service-name=x; connections are refused or time out.
  • Uneven load: long-lived connections (gRPC, keep-alive) pinned by per-connection balancing.
  • DNS latency or 5-second timeouts: ndots expansion, CoreDNS saturation, conntrack races. Scale CoreDNS, NodeLocal DNSCache, trailing-dot names.
  • Client IP lost: externalTrafficPolicy: Cluster SNAT; use Local or proxy protocol / X-Forwarded-For from the Gateway.
  • Errors during rollouts: endpoint-propagation race without preStop and drain.
  • NetworkPolicy "not working": CNI does not enforce it, or egress (including DNS) was not allowed.
  • Cross-node traffic fails, same-node works: overlay blocked by a firewall (VXLAN UDP 8472, IPIP protocol 4, BGP 179) or MTU mismatch with encapsulation (k8s4).
  • Pods cannot be created: no IPs: node pod CIDR or VPC subnet exhausted.

Tools

kubectl get svc,endpointslices; kubectl run a debug pod with nslookup/dig and curl; iptables-save -t nat | grep <svc> or nft list ruleset on a node; conntrack -L -d <clusterIP>; CNI-specific tools (Cilium's Hubble for flow logs); CoreDNS metrics (request rate, latency, NXDOMAIN rate); Gateway and HTTPRoute status conditions, which say whether a route was accepted and why not.

    import random, collections
def pick(endpoints):
    n = len(endpoints)
    for i, ep in enumerate(endpoints[:-1]):           # iptables: probability 1/(n-i)
        if random.random() < 1 / (n - i):
            return ep
    return endpoints[-1]
eps = ["10.244.1.17", "10.244.1.23", "10.244.3.4"]
print(collections.Counter(pick(eps) for _ in range(30_000)))
def queries(name, ns="shop", ndots=5, extra=("ec2.internal",)):
    search = [f"{ns}.svc.cluster.local", "svc.cluster.local", "cluster.local", *extra]
    if name.endswith("."): return [name]
    tries = [f"{name}.{s}" for s in search] if name.count(".") < ndots else []
    return tries + [name] if tries else [name] + [f"{name}.{s}" for s in search]
for n in ["payments", "api.stripe.com", "api.stripe.com.", "a.b.c.d.e.f"]:
    q = queries(n); print(f"{n:18} {len(q)*2:2} queries (A+AAAA) first: {q[0]}")
    Expect roughly 10,000 per endpoint, and 10 queries for api.stripe.com (5 names × A and AAAA) against 2 for the trailing-dot form. (For payments the first try succeeds, so only 2 are actually sent.)
Diagnose: checkout times out calling payments after a security change

A platform team rolls out NetworkPolicies to the shop namespace: a default-deny for ingress and egress, and a policy allowing ingress to app=payments pods from app=checkout pods on port 80, "because the Service listens on 80". Immediately, checkout's calls to http://payments fail. First the error is "could not resolve host", and after someone adds a DNS egress allow, it becomes a connect timeout. Explain both errors and give the correct set of policies.

Answer

Error 1: the default-deny covers egress, so checkout's DNS queries to CoreDNS in kube-system are dropped: no name resolution. Error 2: two mistakes remain. Checkout's egress to payments is still denied — the payments ingress policy allows the traffic at the receiving end, but checkout is also selected by the default-deny egress policy, and nothing allows its egress. And the port is wrong: kube-proxy DNATs 10.96.x.x:80 to the pod's targetPort (8080) before policy is enforced, so policies must name the pod port, not the Service port.

Correct set: (1) default deny ingress and egress for podSelector: {}; (2) allow egress from all pods to CoreDNS pods (k8s-app: kube-dns in kube-system) on UDP and TCP 53; (3) on payments, allow ingress from app: checkout on port 8080; (4) on checkout, allow egress to app: payments on port 8080. Plus whatever else each app really needs (payments' egress to its database and to the payment provider, ideally by IP block or through an egress gateway). Verify with kubectl exec into checkout: nslookup payments, then curl -m 3 http://payments. Before rolling policies out cluster-wide, use the CNI's flow logs (Hubble, Calico flow logs) in audit mode to see what would be denied.
