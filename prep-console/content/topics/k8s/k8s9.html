The container images from k8s2 and k8s3 are deliberately the same in every environment: the image that passed tests in staging is the image that runs in production. But production needs different settings — a different database host, a bigger connection pool, a real payment-provider key instead of a test one — and it needs data that outlives any single container: the database's files, uploaded documents, model checkpoints. Kubernetes separates these concerns into objects that live beside the pod: ConfigMaps and Secrets for configuration and credentials, and volumes for files, from scratch space to durable disks.

They are easy to start using and easy to get wrong. A team changes a ConfigMap and waits for the app to pick up the new setting; it never does, because the value was injected as an environment variable. Another team stores their database password in a Secret and assumes it is encrypted; it sits in plain text in etcd and in every etcd backup. A third team's StatefulSet pod stays Pending forever after a node replacement: its disk lives in one availability zone and the only node with room is in another. A data scientist deletes a PVC to "clean up" and discovers that this also deleted the cloud disk with three weeks of training checkpoints. And in 2018 the Kubernetes security team had to fix a vulnerability in which a container could use a symbolic link inside its own volume to mount the host's entire file system.

Underneath, these objects are mechanisms you have already met: files placed into a pod by the kubelet, bind mounts like Docker's (k8s4), controllers that reconcile claims against real storage (k8s6). This lesson follows them in order: how configuration reaches a container and how — and whether — it changes; what a Secret actually protects and how to make it protect more; the volume types and what each costs; and then persistent storage end to end, from a claim through a StorageClass and a CSI driver to a disk attached, formatted and mounted inside a container, traced step by step. It ends with the vulnerability that showed how much trust the mount path carries.

Notes on the fridge, a locked drawer and a storage unit

Think of a pod as a rented flat that might be swapped for an identical flat at any moment. Three kinds of things must follow the tenant from flat to flat.

  • Notes on the fridge — instructions anybody in the flat may read: "the bins go out on Tuesday". That is a ConfigMap: non-secret settings, delivered either read aloud once at move-in (environment variables) or pinned to the fridge, where the landlord can swap the note later (a mounted file).
  • A locked drawer for the door codes and bank cards. That is a Secret. The catch: by default the drawer's lock is a sticker saying "locked" (base64 encoding); the real protection comes from who has the key to the building's records (RBAC), whether the records office encrypts its files (encryption at rest), and whether the codes are kept somewhere better altogether (an external secret manager).
  • A storage unit that is not part of any flat, rented by name. That is a PersistentVolumeClaim: whichever flat the tenant moves to, the same unit is connected to it. The unit itself is a PersistentVolume, and the company that builds units on demand, to a specification, is the StorageClass and its CSI driver.

There are also things that belong to the flat and are thrown away with it: a scratch table for the current job (emptyDir), and, dangerously, a door straight into the building's plant room (hostPath).

Two questions for any piece of data

Before choosing an object or volume type, ask two questions about the data. First, how long must it live? Until the container restarts (the writable layer — almost never what you want), until the pod is replaced (emptyDir), for as long as the configuration is in force (ConfigMap, Secret), or independently of any pod (a PersistentVolumeClaim, or a database or object store outside the cluster). Second, who may read it, and how bad is a leak? Settings that would be harmless on a public web page go in a ConfigMap; anything that grants access to something — a password, an API token, a private key — goes in a Secret or, better, an external secret manager. Most mistakes in this lesson come from answering one of these questions by accident: a database whose files lived as long as its container, a password whose readers were "anyone who can list ConfigMaps", or checkpoints whose lifetime was tied to a claim someone tidied up.

Where the analogy breaks: the storage unit is not reachable from everywhere. Most cloud disks live in one availability zone and can be attached to one machine at a time, so "follow the tenant" really means "the tenant may only move to flats in the same district" — a constraint the scheduler must respect, and the source of many stuck pods.

1. ConfigMaps: configuration as an object

A ConfigMap is a namespaced object holding key-value data — either short strings or whole files — up to 1 MiB in total (the etcd request limit, k8s6). It has data for UTF-8 strings and binaryData for base64-encoded binary.

apiVersion: v1
kind: ConfigMap
metadata: { name: api-config, namespace: shop }
data:
  LOG_LEVEL: info
  POOL_SIZE: "20"
  config.yaml: |
    timeouts: { db_ms: 800, payments_ms: 2500 }
    features: { new_checkout: false }

A pod consumes it in one of three ways, and the choice decides what happens on change:

  • Environment variables, one key at a time (env[].valueFrom.configMapKeyRef) or all keys (envFrom). The kubelet reads the values when it creates the container. They never change for the life of that container.
  • Files in a volume: a configMap volume makes each key a file (/etc/app/LOG_LEVEL, /etc/app/config.yaml). These are updated when the ConfigMap changes — eventually.
  • Command-line arguments built from environment variables ($(POOL_SIZE) in args), which inherit the env-var behaviour.

How a mounted ConfigMap is updated. The kubelet keeps a local cache of ConfigMaps used by its pods, fed by a watch by default. On each periodic sync of a pod (every minute by default, or sooner when something triggers it), it checks whether mounted ConfigMaps are fresh and, if not, rewrites the files. It does that atomically. The volume directory looks like this:

/etc/app/
  ..2026_10_04_09_15_02.481516/    # real directory with the current files
      LOG_LEVEL
      config.yaml
  ..data -> ..2026_10_04_09_15_02.481516
  LOG_LEVEL   -> ..data/LOG_LEVEL
  config.yaml -> ..data/config.yaml

To update, the kubelet writes the new files into a new timestamped directory, then atomically renames a new symlink over ..data (a rename is atomic on Linux), then removes the old directory. A reader opening config.yaml sees either the complete old file or the complete new one, never a mixture. The delay between editing the ConfigMap and the file changing is the sync period plus cache propagation: usually within a minute or two. Two exceptions: a key mounted with subPath is a plain bind mount of one file, not part of the symlink scheme, and never updates; and an immutable ConfigMap (immutable: true) cannot change at all — which lets the kubelet stop watching it, a real saving in big clusters.

Even when the file changes, the application must notice: watch the file (inotify on the ..data symlink's directory), reload on a signal, or re-read on each use. Many teams prefer a simpler, auditable rule: configuration changes cause a rollout. A pod-template annotation containing a hash of the ConfigMap (Helm's checksum/config pattern, k8s12) changes when the ConfigMap changes, so the Deployment rolls out new pods that read the new values at start, with the usual readiness gating and rollback.

2. Secrets: what they protect, and what they don't

A Secret looks like a ConfigMap and is consumed the same ways, with a type (Opaque, kubernetes.io/tls, kubernetes.io/dockerconfigjson for image pull credentials, and others) and values that are base64-encoded in the API:

$ printf 'hunter2' | base64
aHVudGVyMg==
$ kubectl get secret db -o jsonpath='{.data.password}' | base64 -d
hunter2

Base64 is an encoding for binary data, not encryption; anyone who can read the object can read the value. What Kubernetes does add for Secrets:

  • Secret volumes on nodes are backed by tmpfs, so values are not written to the node's disk, and the kubelet only fetches Secrets for pods on its node (the Node authoriser enforces this).
  • kubectl describe shows sizes, not values; RBAC can grant ConfigMap access without Secret access.
  • Encryption at rest is available, but off until configured.

Without encryption at rest, etcd holds the value in plain text: etcdctl get /registry/secrets/shop/db on a control-plane node shows hunter2 inside the stored object, and so does every etcd backup file. Encryption at rest is configured with an EncryptionConfiguration passed to the API server, listing providers in order: the first encrypts new writes, all are tried for reads. aescbc, aesgcm and secretbox use a key stored in that configuration file on the control-plane nodes, which protects backups but not someone with the node's disk. The KMS v2 provider uses envelope encryption: each object is encrypted with a data-encryption key, and that key is itself encrypted by a key-encryption key held in an external KMS (a cloud KMS or HSM) that never leaves it. After enabling encryption, existing Secrets must be rewritten (kubectl get secrets -A -o json | kubectl replace -f -) to be encrypted, and stored values then begin with a prefix such as k8s:enc:kms:v2:.

The bigger risks are usually not etcd but access paths. RBAC get, list or watch on Secrets in a namespace reveals all of them (list returns values too). Anyone who can create pods in a namespace can mount any Secret in it, so pod-creation rights are Secret-read rights. Environment variables leak into crash dumps, debug endpoints and child processes; files are easier to protect and rotate. Mature setups therefore keep the source of truth outside Kubernetes — Vault or a cloud secret manager — and either sync it into Secrets with the External Secrets Operator or mount it directly with the Secrets Store CSI driver, with rotation handled by the external system. Service-account credentials have improved the same way: pods now get short-lived, audience-bound projected service-account tokens that the kubelet refreshes, instead of long-lived token Secrets.

3. Volumes: the menu

A pod declares volumes; each container mounts some of them with volumeMounts at a path. The kubelet prepares every volume before starting containers (k8s6). The common types:

emptyDir deserves a worked number. A pod with resources.limits.ephemeral-storage: 2Gi writes a 3 GB temporary file into an emptyDir: the kubelet's periodic usage check (container writable layers, logs and emptyDirs all count) sees the pod over its limit and evicts it. With medium: Memory, the same 3 GB counts toward the container's memory instead, and with a 2 GiB memory limit the kernel OOM-kills it (k8s10). Scratch is never free.

hostPath mounts a node path into the pod. With /, /var/run/containerd/containerd.sock or /etc, a container owns the node. That is why the Pod Security Standards' baseline profile forbids hostPath, and why node agents that need it run as DaemonSets in tightly controlled namespaces.

4. Information about the pod itself: downward API and projected tokens

Applications often need facts that only exist once the pod is running: their own pod name for logs, their namespace, the node they landed on, their memory limit to size a cache. The downward API exposes these, either as environment variables (valueFrom.fieldRef: {fieldPath: metadata.name}, or resourceFieldRef: {resource: limits.memory}) or as files in a downwardAPI volume, where labels and annotations are also updated when they change. A worked example: a Python worker reads MEMORY_LIMIT, injected from limits.memory as 2147483648 bytes, and sizes its in-memory cache at 40% of it, about 820 MB, instead of guessing from the node's 64 GB — the container-awareness lesson from k8s3 applied without any cgroup parsing.

The same mechanism delivers the pod's identity. Every pod runs as a service account, and by default the kubelet mounts a projected volume at /var/run/secrets/kubernetes.io/serviceaccount/ combining three sources: a short-lived token requested from the API server's TokenRequest API, bound to this pod and an audience and refreshed by the kubelet before it expires; the cluster's CA certificate; and the namespace name. Client libraries read these files to call the API server. The token is a JSON Web Token naming the service account and pod; because it expires and is invalidated when the pod is deleted, a stolen copy is far less useful than the old long-lived token Secrets. Pods that never call the API should set automountServiceAccountToken: false, removing one credential an attacker could otherwise use. Projected tokens with other audiences are also how workloads authenticate to cloud providers (IRSA on AWS, Workload Identity on GKE) without any static cloud keys in Secrets.

5. PersistentVolumes, claims and classes

Durable storage is split into two objects so that applications ask for storage without knowing where it comes from:

  • A PersistentVolumeClaim (PVC), namespaced, is the request: "20 GiB, ReadWriteOnce, class gp3".
  • A PersistentVolume (PV), cluster-scoped, is a real piece of storage: "AWS EBS volume vol-0abc, 20 GiB, zone us-east-1b". It is bound one-to-one to a claim.
  • A StorageClass, cluster-scoped, is a recipe for making PVs on demand: a provisioner (a CSI driver name), parameters (disk type, IOPS, encryption), a reclaimPolicy, a volumeBindingMode and allowVolumeExpansion. One StorageClass can be marked default, used by claims that name none.

The access modes describe concurrency, and they are about nodes, not pods: ReadWriteOnce (RWO, mounted read-write by a single node; several pods on that node may share it), ReadOnlyMany (ROX), ReadWriteMany (RWX, needs a shared file system such as NFS or a cloud file service), and ReadWriteOncePod (RWOP, a single pod in the whole cluster, for databases that must never have two writers). Block disks (EBS, Persistent Disk, Azure Disk) are RWO.

The reclaim policy says what happens to the PV when its claim is deleted. Delete, the default for dynamically provisioned volumes, deletes the PV and the cloud disk. Retain keeps both; the PV becomes Released and must be cleaned up or re-bound by an administrator. For anything precious, use a Retain class and snapshots.

Binding. A controller in the controller manager matches claims to PVs: for a claim, it looks for an available PV of the same class with sufficient capacity and compatible access modes, choosing the smallest that fits; if none exists and the class has a provisioner, it requests dynamic provisioning. The volumeBindingMode decides when. With Immediate, binding and provisioning happen as soon as the claim is created. With WaitForFirstConsumer, they wait until a pod using the claim has been scheduled, so the scheduler's choice of node — with all its resource, affinity and taint constraints — decides the disk's zone, rather than a disk created in a random zone deciding where the pod must go.

6. Dynamic provisioning, traced end to end

CSI (Container Storage Interface) is the standard between Kubernetes and storage drivers. A CSI driver has a controller part (a Deployment with Kubernetes-maintained sidecars: external-provisioner, external-attacher, external-resizer, external-snapshotter) that talks to the storage system's API, and a node part (a DaemonSet) that does mounts on each node, called by the kubelet over a Unix socket. Now trace a StatefulSet pod db-0 with a 20 GiB claim data-db-0 of class gp3 (provisioner ebs.csi.aws.com, WaitForFirstConsumer) in a cluster spanning three zones.

  1. Schedule first. The StatefulSet controller creates db-0 and the claim. Because of WaitForFirstConsumer, the claim stays Pending. The scheduler's volume-binding plugin considers it while filtering nodes (a new disk can be made in any zone the class allows) and picks node-7 in us-east-1b, recording it on the claim as the annotation volume.kubernetes.io/selected-node: node-7.
  2. Provision. The external-provisioner sidecar sees a claim for its driver with a selected node, and calls the driver's CreateVolume with capacity 20 GiB, the class parameters (type: gp3) and an accessibility requirement of zone us-east-1b. The driver calls the EC2 API; a new volume vol-0abc appears.
  3. Bind. The provisioner creates a PV pvc-5e1f… with the volume handle vol-0abc, node affinity for us-east-1b, the class's reclaim policy, and a reference to the claim; the binder marks both Bound.
  4. Request attachment. The attach-detach controller in the controller manager sees a pod on node-7 using a PV that is not attached there, and creates a VolumeAttachment object (driver, PV, node).
  5. Attach. The external-attacher sidecar calls ControllerPublishVolume; the driver calls the EC2 AttachVolume API; the disk appears on node-7 as a block device such as /dev/nvme2n1. The VolumeAttachment's status becomes attached: true.
  6. Stage. The kubelet on node-7 calls the node plugin's NodeStageVolume: since the disk is blank, the plugin formats it (ext4 by default, or the class's fsType) and mounts it at a per-volume global path under /var/lib/kubelet/plugins/kubernetes.io/csi/…/globalmount.
  7. Publish. NodePublishVolume bind-mounts that global path into the pod's own volume directory, /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~csi/pvc-5e1f…/mount. If the pod has an fsGroup, the kubelet adjusts ownership so the non-root container can write (with fsGroupChangePolicy: OnRootMismatch, only if the top directory is wrong, avoiding a slow recursive walk on a big volume).
  8. Mount into the container. When the kubelet creates the container through the CRI, it passes that directory as a mount; containerd bind-mounts it at /var/lib/data inside the container's mount namespace. Postgres writes go straight to ext4 on the EBS device, bypassing OverlayFS (k8s4).

When db-0 is later rescheduled, the claim and PV already exist, so steps 2-3 are skipped. The PV's node affinity restricts the new db-0 to nodes in us-east-1b; the old node unpublishes, unstages and the disk is detached (or force-detached after a failure, see deep) before it is attached to the new node. If no node in us-east-1b has room, the pod stays Pending with a volume node affinity conflict message — the zone constraint from the primer.

Expansion works the same way in reverse direction of size only: if the class sets allowVolumeExpansion: true, editing the claim's request from 20Gi to 50Gi makes the external-resizer call ControllerExpandVolume and the kubelet grow the file system, usually online. Volumes cannot shrink. Snapshots use VolumeSnapshot objects and a VolumeSnapshotClass; a new claim can name a snapshot as its dataSource to restore.

7. Matching storage to the workload, with numbers

A claim's size is easy to choose; its performance is where surprises live. Cloud block volumes have performance attributes separate from capacity. On AWS, for example, a gp3 volume provides a baseline of 3,000 IOPS and 125 MiB/s whatever its size, with more purchasable; other volume types scale performance with size. Work through a Postgres example: the database does about 2,500 random 8 KiB writes per second at peak (WAL plus data pages), plus checkpoint bursts. 2,500 IOPS fits under the 3,000 baseline with little headroom, and checkpoints will push it over, at which point I/O latency climbs from around a millisecond to many, and every transaction slows. Provisioning extra IOPS, spreading WAL onto its own volume, or tuning checkpoints is a capacity decision just like CPU and memory — and it is invisible in Kubernetes unless you graph the disk's own metrics.

A rough decision guide follows from everything above. Data that must outlive pods and is written by one instance at a time — databases, queues, search indexes — goes on RWO block volumes through a StatefulSet, with a Retain class and snapshots. Data shared read-mostly by many pods — datasets, model weights, static assets — goes to object storage or a ROX/RWX file system, often with a node-local cache. Scratch data that can be recomputed goes in emptyDir or generic ephemeral volumes, sized with limits. And anything that must survive a region loss goes, in the end, to replicated object storage with backups. Choosing by these properties first, and only then by product, avoids most storage incidents.

Why mounting is a security boundary

Every volume mount is performed by privileged code on the host — the kubelet and the container runtime — on paths that the container may partly control. A container can write files and symlinks into an emptyDir or a PVC; if host-side code later follows those symlinks while resolving a mount source, the container has steered a privileged operation. That is the shape of the subPath vulnerability in the prod section, and of later issues in the same family. The defences are generic: resolve paths relative to a directory file descriptor without following symlinks out of it, validate and then use the same pinned file descriptor (avoiding time-of-check to time-of-use races), and keep containers non-root with read-only root file systems so they have less ability to plant traps.

Attach, detach and the dead-node problem

RWO block devices must be attached to exactly one node. When a node dies, its pods' disks remain attached in the cloud's view, and the kubelet that would unmount them is gone. The attach-detach controller will not attach the disk elsewhere while a VolumeAttachment for the old node exists and the old pod might be running, because two machines writing the same ext4 file system corrupts it. Historically this produced long stalls (a "Multi-Attach error" and a six-minute force-detach timeout). The non-graceful node shutdown feature makes the decision explicit: an operator or automation that knows the node is really down applies the node.kubernetes.io/out-of-service taint, the pods are deleted, and volumes are force-detached immediately. Cloud-provider node deletion achieves the same thing when the VM is gone.

Secret delivery and the API server's load

Every pod that mounts Secrets and ConfigMaps makes the kubelet watch those objects. A cluster with 100,000 pods, each mounting a few objects, means hundreds of thousands of watches. Marking unchanging ConfigMaps and Secrets immutable lets the kubelet drop the watch after the first read, which is a measurable reduction in API-server load in large clusters, and also protects against accidental edits; changing configuration then means creating a new object (often with a hash in its name, as Kustomize's generators do, k8s12) and rolling pods over to it.

Local persistent volumes and the trade-off of speed

Network block storage adds latency (single-digit milliseconds per I/O on general-purpose cloud disks) and has per-volume IOPS and throughput caps. Instance-local NVMe is an order of magnitude faster but disappears if the node does. local PersistentVolumes expose such disks with node affinity, so a pod is bound to the node holding its data. That suits replicated systems that tolerate losing a member — Cassandra, Kafka, Elasticsearch, or a Postgres replica set run by an operator — where a lost node means re-replicating from peers rather than restoring from backup. The trade-off is explicit: performance in exchange for the application, not the platform, owning durability.

Snapshots are not backups

A CSI VolumeSnapshot is usually implemented by the storage system itself — an EBS snapshot, a Ceph snapshot — and is fast and space-efficient. But it is crash-consistent at best (like pulling the power cord: the database must recover on restore), it lives in the same cloud account and often the same region as the original, and it is deleted if someone with enough permissions deletes it. A backup that survives a compromised account or a region failure must be copied elsewhere, ideally with immutability (object lock), and for databases an application-level backup (a base backup plus write-ahead log archiving for Postgres) gives point-in-time recovery that a disk snapshot cannot. Velero and similar tools back up both Kubernetes objects and volume data; whichever you use, the only backup that counts is one whose restore has been tested.

Consistency of shared file systems

RWX volumes look like ordinary directories, but network file systems relax POSIX semantics: NFS caches attributes and may show stale metadata for seconds; file locks behave differently; rename atomicity and fsync durability depend on the server. Applications that work on a local disk can corrupt data or slow to a crawl on a shared one — SQLite on NFS is the classic example. Object storage accessed through a file-system adapter (a CSI driver mounting a bucket) is weaker still: no in-place updates, eventual listing in some systems, high per-operation latency. Choose RWX only for workloads designed for it, such as read-mostly shared datasets or append-only outputs.

CSI drivers are privileged infrastructure

A CSI node plugin runs as a privileged DaemonSet with access to the host's devices and mount namespace, and its controller holds cloud credentials that can create, attach and delete disks. That makes CSI drivers part of the cluster's trusted computing base, like the CNI plugin and the kubelet: they must be patched promptly, their service accounts and cloud roles scoped tightly (a driver that can delete every disk in the account is a large blast radius), and upgrades rolled out node by node, because a broken node plugin prevents any new pod with volumes from starting on that node. The same applies to secret-store CSI drivers, which hold credentials to the external secret manager.

The case: the subPath symlink escape (CVE-2017-1002101)

In March 2018 Kubernetes disclosed CVE-2017-1002101, and the Kubernetes blog later explained it in detail. subPath lets a container mount one subdirectory or file of a volume. To set it up, the kubelet joined the volume's host directory with the subPath and handed the result to the container runtime as a bind-mount source. The blog shows the attack in two containers of one pod sharing an emptyDir. An init container runs ln -s / /mnt/data/symlink-door, creating a symlink inside the volume that points at /. The main container mounts the same volume with subPath: symlink-door. When the kubelet resolved that path on the host, it followed the symlink — to the host's root directory — and the runtime bind-mounted the host's whole file system into the container. From there the container could read other pods' volumes, Secrets on tmpfs, and credentials on the node.

The fix was harder than it looks, and the blog walks through the designs the security team rejected. Simply resolving symlinks and checking the result is inside the volume fails, because the container can swap the path between the check and the mount (a time-of-check-to-time-of-use race). The adopted approach resolves the path component by component relative to the volume without following symlinks outside it, holds the result open as a file descriptor so it cannot change, and bind-mounts from that pinned descriptor. Some functional regressions followed the first patch and were fixed in later releases.

The lessons reach beyond subPath: mount setup is privileged host code operating on container-controlled paths; features like hostPath, subPath and writable shared volumes widen what a compromised container can influence; and the Pod Security Standards, non-root users, read-only root file systems and minimal volume types shrink it.

Failure modes and their symptoms

  • Config change not applied: env vars, subPath mounts, or an app that never re-reads its files. Roll out on config change.
  • Secret exposure: etcd backups without encryption at rest; broad RBAC (list secrets); values in env vars printed by debug pages.
  • Pod Pending: "volume node affinity conflict" or "didn't find available persistent volumes to bind": zonal disk and no capacity in that zone, or Immediate binding put the disk in the wrong zone.
  • ContainerCreating with "Multi-Attach error": RWO disk still attached to an old or dead node.
  • Slow pod start on big volumes: recursive fsGroup ownership changes; use OnRootMismatch.
  • Evictions for ephemeral storage: emptyDir or logs over limit, or node disk pressure.
  • Accidental data loss: PVC deleted with a Delete reclaim policy; StatefulSet PVC retention policy set to delete on scale-down.
  • Volume full: no alert on PV usage; expansion disabled in the class.

What to monitor and tune

Kubelet volume stats (kubelet_volume_stats_used_bytes versus capacity) with alerts at 80%; CSI operation latency and errors (provisioning, attach); PVCs stuck Pending; VolumeAttachments not attached; disk IOPS and throughput against the volume type's caps; snapshot success and age; and, for Secrets, audit logs of reads and the encryption status of etcd. Knobs: default StorageClass with WaitForFirstConsumer and expansion enabled; a separate Retain class for precious data; ConfigMap/Secret immutability; projected tokens with short expiry.

Restores are the real test

Schedule a restore drill: pick a production database's latest snapshot or backup, restore it into a fresh claim in a staging namespace, start the application against it and check the data. Measure how long it takes, from decision to serving, because that number is your real recovery time, not the one in the design document. Teams that run this quarterly find expired credentials, missing permissions, snapshots in the wrong region and restore procedures that only one person knows, while it is still cheap to find them. Write the measured time and every surprise into the runbook straight after the drill.

Diagnose: the database that won't come back after a node upgrade

A three-zone EKS cluster runs Postgres as a single-replica StatefulSet with a 200 GiB gp3 claim. During a node-group upgrade, the old node in us-east-1a is drained and terminated. The new pg-0 pod stays Pending for 40 minutes. kubectl describe pod pg-0 shows: 0/9 nodes are available: 3 Insufficient memory, 6 node(s) had volume node affinity conflict. The new node group has three nodes per zone. What happened, how do you restore service now, and what do you change?

Answer

The PV is an EBS volume in us-east-1a, so its node affinity allows only us-east-1a nodes. The six nodes in 1b and 1c are rejected for "volume node affinity conflict". The three 1a nodes are rejected for insufficient memory: Postgres requests a lot of memory and the new 1a nodes are already filled by pods that were rescheduled there first during the drain. The scheduler cannot move the disk, and nothing evicts other pods for it unless it has a higher priority.

Restore now: free capacity in us-east-1a — scale up the node group in that zone (or let the cluster autoscaler do it; if it has not, check that the 1a node group can scale and that the autoscaler understands the volume's zone), or evict lower-priority pods from a 1a node. Then pg-0 schedules, the attach and mount steps run, and Postgres recovers from its disk.

Change: give critical stateful pods a higher PriorityClass so they can preempt (k8s10); keep headroom per zone, or use node groups per zone so the autoscaler can add capacity where the volume lives; upgrade nodes zone by zone with surge capacity; and, for a database, run replicas across zones with an operator so losing a zone's node means failover rather than waiting for one disk. Use a WaitForFirstConsumer, Retain StorageClass with snapshots for the data.
