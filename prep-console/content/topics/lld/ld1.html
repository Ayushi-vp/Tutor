Picture a service that turns a user id into a profile by calling a database that takes 20 milliseconds per query. The same few thousand active users ask for their profiles again and again, so the service answers the same question thousands of times a minute, paying 20 milliseconds each time. The obvious fix is to remember answers in a dict. A week later the process has been killed for running out of memory, because the dict remembered every user who ever logged in and never forgot any of them.

What you actually want is a store that remembers a limited number of answers and, when it is full, forgets the one least likely to be needed again. You cannot know the future, but programs have a strong habit: what was used a moment ago is likely to be used again soon. That habit is called temporal locality, and it suggests a simple rule. When you must forget something, forget the entry that was used longest ago. That rule is least recently used, or LRU, and a bounded store that follows it is an LRU cache.

The rule is easy to say and surprisingly easy to implement slowly. Finding "the entry used longest ago" naively means scanning every entry, so each insertion into a full cache costs time proportional to the cache size. A cache of a million entries that scans a million entries per insert is slower than the database it was meant to protect. The interview question exists because the fast version needs two data structures working together, and the way they cooperate (one finds things, the other orders them) is a pattern you will reuse in half of the later machine-coding cases.

That is why LRU is the standard opener of a machine-coding round. In 45 minutes the interviewer watches whether you clarify before typing, pick a clean interface, reach the right structure by reasoning rather than recall, keep the two structures consistent, test the edge cases where implementations usually break, and discuss what changes when the cache must be thread-safe, expire entries, or hold values of very different sizes.

This lesson follows the round in order. It starts with the questions to ask, names the pieces and their responsibilities, sketches the interface, then builds the cache in stages: a correct but slow dict-with-timestamps version, a version built on a Python list, the ten-line OrderedDict version, and finally the hash map plus doubly linked list that the round is really about, traced pointer by pointer. Then come the full tested solution, the edge cases, the extensions an interviewer asks for, complexity, and why Redis and Caffeine do not use exact LRU at all.

Start here: what a machine-coding round marks

A machine-coding round is not a harder algorithm puzzle. You are asked to build a small, working component, the kind of class a colleague would import, in about 45 minutes, while talking. The interviewer is marking roughly four things: whether you pin down the requirements before you type, whether your interface and decomposition are clean, whether the code is correct on the cases that usually break, and how well you discuss the extensions you will not have time to build. A dense, clever, uncommented solution that you cannot explain scores worse than plain code with a clear invariant and three good tests.

The analogy: a desk with limited space

Think of a desk that holds eight folders. Every time you use a folder you put it on top of the pile. When a ninth folder arrives and the desk is full, you take the one at the bottom of the pile, the one you have not touched for longest, and put it back in the filing cabinet. The pile is the recency order; the bottom of the pile is the eviction candidate. That is LRU exactly.

The analogy breaks in one useful place. On a real desk, finding a particular folder in the pile means looking through it, and pulling it out of the middle means lifting the folders above it. A computer has the same two problems. Finding a key in an ordered sequence is slow unless you also have an index, and removing from the middle of an array is slow because everything after it shifts. The design you are about to learn solves each problem with a separate structure.

Two structures, two jobs

A hash map (Python's dict) answers "where is the entry for this key?" in O(1) on average. O(1), read "order one" or "constant time", means the cost does not grow with the number of entries; O(n) means it grows in proportion to the number of entries n. The dict cannot tell you which entry is least recently used, because it does not keep access order.

A doubly linked list answers "what is the order of use?" Each node holds one entry and two pointers, prev and next, to its neighbours. Removing a node you are already holding takes four pointer changes, no matter how long the list is, and adding a node at the front takes four more. What a list cannot do is find a node by key without walking it.

Put them together and each covers the other's weakness. The dict maps every key to its node in the list. To read a key: the dict finds the node in O(1), you unlink it in O(1) and re-link it at the front in O(1). To evict: the node at the back of the list is the least recently used, so you unlink it in O(1) and delete its key from the dict in O(1). Every operation is a constant number of steps.

Sentinels: the detail that signals experience

A sentinel node is a permanent dummy node that holds no data. This design uses two, a head and a tail, created once in the constructor and never removed. Because they are always there, every real node always has a node before it and a node after it, so the code that unlinks or inserts a node never has to ask "is the list empty?" or "is this the first node?". Without sentinels each of those questions becomes an if with its own chance of a bug. With them, unlinking is one line and inserting at the front is three.

The questions to ask before typing

Spend the first few minutes asking, because the answers change the code. What should a miss return: -1, None, or raise? Can None be stored as a value? Is capacity counted in entries or bytes? Must it be thread-safe? Should entries expire after a time? Does reading a key count as "use" (in LRU it does)? Interviewers often answer "keep it simple, single-threaded, entries, return None", and then bring the others back as extensions later; asking shows you know they exist.

The shape of the answer

A reader who stops here has the right picture: a dict from key to node, a doubly linked list in recency order bounded by two sentinels, get as "find, unlink, push to front", and put as "update in place if present, otherwise evict the node before the tail if full, then insert at the front". The rest of the lesson builds that up in stages, proves it with tests, and explains what real systems do differently.

1 · Clarify the requirements

Write the agreed requirements as a short comment at the top of your file, so both you and the interviewer can point at them later. A typical agreed list looks like this. The cache has a fixed positive capacity counted in entries. get(key) returns the value if present and marks the entry as most recently used; otherwise it returns a default. put(key, value) inserts or updates and marks the entry most recently used; if inserting a new key would exceed capacity, it first evicts the least recently used entry. Both operations must be O(1). Single-threaded for now. Values may be None.

Two of those answers deserve a sentence each because they change code. "Values may be None" means None cannot also be the miss signal, so you need either a default argument, a private sentinel object, or an exception. "O(1)" rules out everything that scans, which is exactly where the naive versions will fail. Non-functional requirements matter too: say that you will add a check for capacity zero or negative, and that you will keep statistics (hits, misses, evictions) because a cache without a hit rate cannot be tuned.

2 · Entities and responsibilities

Even a small problem rewards naming the pieces before writing them. There are three. The node holds one entry: its key, its value, and its two neighbour pointers. It has no behaviour; it is a record. The recency list owns ordering: it can unlink a node it is given and push a node to the front, and it knows which node is last. The cache owns the policy: it holds the dict and the list, decides when to evict, and keeps the two consistent. Separating "how to move a node" (two tiny private methods) from "when to move it" (the public methods) keeps every public method short enough to read in one glance, which is what the interviewer checks.

The invariant, the condition that must hold between any two public calls, is worth saying out loud and writing as a comment: the dict and the list contain exactly the same nodes; the node for key k is map[k]; and their count never exceeds capacity. Every bug in this problem is a path that breaks one of those three statements.

3 · The interface

The public surface is deliberately tiny: a constructor taking capacity, get(key, default=None), put(key, value), plus __len__ and __contains__ so it behaves like a Python container. Note one design decision: __contains__ does not refresh recency. A membership test is a peek, and if peeking counted as use, diagnostic code that checks for keys would change what gets evicted. Say this decision out loud; it shows you thought about what "use" means.

Making the class generic, LRUCache[K, V], costs nothing at runtime and documents that keys must be hashable and values can be anything. Type hints are optional in an interview but read as care.

4 · Stage one: a dict with timestamps

Always start with something correct, even if slow, and say its complexity. The simplest correct cache stores, for each key, the value and the time of last use, using a counter that increases on every operation so ties cannot happen.

class NaiveLRU:
    def __init__(self, capacity):
        self.capacity, self.data, self.clock = capacity, {}, 0   # key -> [value, last_used]

    def get(self, key, default=None):
        if key not in self.data:
            return default
        self.clock += 1
        self.data[key][1] = self.clock
        return self.data[key][0]

    def put(self, key, value):
        self.clock += 1
        if key not in self.data and len(self.data) == self.capacity:
            oldest = min(self.data, key=lambda k: self.data[k][1])   # O(n) scan
            del self.data[oldest]
        self.data[key] = [value, self.clock]

This is correct. get is O(1). But every put of a new key into a full cache runs min over all n entries, which is O(n). With n = 100,000 and an eviction on most inserts, that is 100,000 comparisons per insert. The fix is not to compute the order on demand but to maintain it as you go, so the oldest entry is always at a known position.

5 · Stage two: a dict plus a Python list in recency order

Keep a list of keys with the least recently used at index 0. A miss on eviction is now cheap: keys.pop(0) names the victim. But "mark as used" means finding the key in the list and moving it to the end: keys.remove(key) searches linearly, and both remove and pop(0) shift every later element one place left, because a Python list is a contiguous array. Both are O(n). We have moved the cost from eviction to every access, which is worse.

This stage teaches the real requirement. We need a sequence where (a) we can reach any element directly, without searching, and (b) removing an element from the middle does not shift anything. A dict gives (a) if it points at the element. A linked list gives (b), because removing a node only changes its neighbours' pointers. That is the whole design, derived rather than remembered, and narrating that derivation is worth more marks than the final code.

6 · Stage three: OrderedDict, the honest ten-line answer

Python already ships the structure. collections.OrderedDict is a dict that remembers order and maintains it with an internal doubly linked list, and it exposes the two operations we need in O(1): move_to_end(key) and popitem(last=False), which removes the first (oldest) item.

from collections import OrderedDict

class OrderedDictLRU:
    def __init__(self, capacity):
        self.capacity, self.od = capacity, OrderedDict()

    def get(self, key, default=None):
        if key not in self.od:
            return default
        self.od.move_to_end(key)                 # mark as most recent
        return self.od[key]

    def put(self, key, value):
        if key in self.od:
            self.od.move_to_end(key)
        self.od[key] = value
        if len(self.od) > self.capacity:
            self.od.popitem(last=False)          # evict least recent

In production Python this is the version to write, and it is faster than a hand-written node class because OrderedDict is implemented in C: on this machine with Python 3.12, a hit through this class took about 0.1 microseconds against about 0.3 for the node-based class below. Say that in the interview, then say "I'll implement the underlying structure, since I assume that's what you want to see." Most interviewers will say yes; a few will accept this version and move straight to extensions, so it is worth knowing both.

A plain dict is ordered too since Python 3.7, but it keeps insertion order and has no move_to_end. You can emulate a refresh with value = d.pop(key); d[key] = value, and evict with del d[next(iter(d))]. It works, and knowing it shows fluency, but it leans on details that are easy to get wrong under pressure.

7 · Stage four: the hash map plus doubly linked list

Now the version the round is about. Define the node with __slots__, which tells Python to store the four attributes in fixed slots instead of a per-instance dict. That saves memory per node and catches typos, because assigning an attribute not in the slots raises an error.

The constructor creates the two sentinels and links them to each other: head.next = tail and tail.prev = head. An empty cache is a list with only sentinels. Two private helpers do all the pointer work. _unlink(n) makes n's neighbours point at each other, which removes n from the chain: n.prev.next, n.next.prev = n.next, n.prev. _push_front(n) places n between the head and the current first node: set n's own pointers first, then make the old first node point back at n, then make the head point forward at n.

Order matters in _push_front. If you write self._head.next = n first, you have lost the only reference to the old first node, and the next line, which should set the old first node's prev, now sets n.prev instead. The safe habit is: set the new node's pointers first (they reference nodes that do not change yet), then update the neighbours.

With the helpers in place the public methods are short. get looks the key up in the dict; on a miss it returns the default; on a hit it unlinks the node, pushes it to the front and returns the value. put has two paths and their order is the most tested detail in this problem. First, if the key exists, overwrite the value, move the node to the front, and return: the number of entries does not change, so nothing may be evicted. Only then, on the new-key path, check whether the cache is full; if it is, the victim is tail.prev, so unlink it and delete map[victim.key]. Finally create the node, store it in the dict and push it to the front.

Here is a trace with capacity 2, writing the list from most to least recent:

Notice the fourth row. Eviction starts from the list, so the code holds a node, not a key. To remove the matching dict entry it needs the key, which is why every node stores its key even though the dict already knows it. Forgetting that leaves the evicted key in the dict pointing at an orphaned node, and the next get for it "hits" a node that is no longer in the list.

8 · The full solution

The complete file below is what you would aim to have on screen at the end of the round, plus the test functions you would write if time allows. It adds a few things beyond the core: statistics, delete, a keys_mru_first helper used by the tests, and an invariant checker that walks the list and confirms each back-pointer and each dict entry. It also contains the thread-safe and sharded wrappers discussed in the extensions. It runs on Python 3.12 with only the standard library; every test passes, including a 20,000-operation fuzz test and an eight-thread stress test.

"""LRU cache with O(1) get and put: hash map + doubly linked list with sentinels.
Python 3.12, standard library only. Run: python lru.py"""
from __future__ import annotations

import random
import threading
from collections import OrderedDict
from typing import Generic, Hashable, TypeVar

K = TypeVar("K", bound=Hashable)
V = TypeVar("V")
_MISSING = object()          # miss marker, so None can be a legitimate value


class _Node:
    __slots__ = ("key", "value", "prev", "next")

    def __init__(self, key=None, value=None):
        self.key, self.value = key, value
        self.prev: _Node | None = None
        self.next: _Node | None = None


class LRUCache(Generic[K, V]):
    """Most-recently used node sits right after head; least-recently used right before tail."""

    def __init__(self, capacity: int) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self.capacity = capacity
        self._map: dict[K, _Node] = {}
        self._head, self._tail = _Node(), _Node()          # sentinels, never removed
        self._head.next, self._tail.prev = self._tail, self._head
        self.hits = self.misses = self.evictions = 0

    # --- the two pointer primitives everything else is built from ---
    def _unlink(self, n: _Node) -> None:
        n.prev.next, n.next.prev = n.next, n.prev

    def _push_front(self, n: _Node) -> None:
        n.prev, n.next = self._head, self._head.next
        self._head.next.prev = n
        self._head.next = n

    # --- public API ---
    def get(self, key: K, default=None):
        n = self._map.get(key)
        if n is None:
            self.misses += 1
            return default
        self.hits += 1
        self._unlink(n)
        self._push_front(n)                                 # a read refreshes recency
        return n.value

    def put(self, key: K, value: V) -> None:
        n = self._map.get(key)
        if n is not None:                                   # update path: never evicts
            n.value = value
            self._unlink(n)
            self._push_front(n)
            return
        if len(self._map) == self.capacity:                 # insert path: make room first
            lru = self._tail.prev
            self._unlink(lru)
            del self._map[lru.key]                          # why the node stores its key
            self.evictions += 1
        n = _Node(key, value)
        self._map[key] = n
        self._push_front(n)

    def delete(self, key: K) -> bool:
        n = self._map.pop(key, None)
        if n is None:
            return False
        self._unlink(n)
        return True

    def __len__(self) -> int:
        return len(self._map)

    def __contains__(self, key: K) -> bool:                 # peek: does NOT refresh recency
        return key in self._map

    def keys_mru_first(self) -> list[K]:
        out, n = [], self._head.next
        while n is not self._tail:
            out.append(n.key)
            n = n.next
        return out

    def check_invariants(self) -> None:
        """len(map) == nodes between sentinels <= capacity, and prev/next agree."""
        count, n = 0, self._head
        while n.next is not self._tail:
            assert n.next.prev is n, "broken back-pointer"
            n = n.next
            count += 1
            assert self._map[n.key] is n, "map and list disagree"
        assert count == len(self._map) <= self.capacity


class ThreadSafeLRU(LRUCache[K, V]):
    """One lock around both structures. get() needs it too: it rewires the list."""

    def __init__(self, capacity: int) -> None:
        super().__init__(capacity)
        self._lock = threading.Lock()

    def get(self, key, default=None):
        with self._lock:
            return super().get(key, default)

    def put(self, key, value) -> None:
        with self._lock:
            super().put(key, value)

    def delete(self, key) -> bool:
        with self._lock:
            return super().delete(key)


class ShardedLRU:
    """N independent locked caches chosen by hash(key) % N: less contention, approximate global LRU."""

    def __init__(self, capacity: int, shards: int = 8) -> None:
        per = max(1, capacity // shards)
        self._shards = [ThreadSafeLRU(per) for _ in range(shards)]

    def _shard(self, key) -> ThreadSafeLRU:
        return self._shards[hash(key) % len(self._shards)]

    def get(self, key, default=None):
        return self._shard(key).get(key, default)

    def put(self, key, value) -> None:
        self._shard(key).put(key, value)

    def __len__(self) -> int:
        return sum(len(s) for s in self._shards)


# ---------------------------------------------------------------- tests
def test_basic_eviction() -> None:
    c = LRUCache[int, str](2)
    c.put(1, "a"); c.put(2, "b")
    assert c.get(1) == "a"                 # 1 becomes MRU, so 2 is now LRU
    c.put(3, "c")                          # evicts 2
    assert 2 not in c and c.get(1) == "a" and c.get(3) == "c"
    assert c.keys_mru_first() == [3, 1]


def test_update_does_not_evict() -> None:
    c = LRUCache[int, str](2)
    c.put(1, "a"); c.put(2, "b"); c.put(1, "z")
    assert c.get(2) == "b" and c.get(1) == "z" and c.evictions == 0


def test_none_value_and_capacity_one() -> None:
    c = LRUCache[str, object](1)
    c.put("x", None)
    assert c.get("x", _MISSING) is None    # a stored None is a hit, not a miss
    c.put("y", 1)
    assert c.get("x", _MISSING) is _MISSING and len(c) == 1
    try:
        LRUCache(0)
    except ValueError:
        pass
    else:
        raise AssertionError("capacity 0 accepted")


def test_fuzz_against_ordereddict(ops: int = 20_000) -> None:
    rng = random.Random(7)
    for cap in (1, 2, 3, 8):
        c, ref = LRUCache[int, int](cap), OrderedDict()
        for _ in range(ops // 4):
            k = rng.randrange(cap * 3)
            if rng.random() < 0.5:
                got = c.get(k, _MISSING)
                if k in ref:
                    ref.move_to_end(k)
                    assert got == ref[k]
                else:
                    assert got is _MISSING
            else:
                c.put(k, k * 10)
                ref[k] = k * 10
                ref.move_to_end(k)
                if len(ref) > cap:
                    ref.popitem(last=False)
            assert c.keys_mru_first() == list(reversed(ref))
        c.check_invariants()


def test_threads(workers: int = 8, ops: int = 5_000) -> None:
    for cache in (ThreadSafeLRU[int, int](64), ShardedLRU(64, shards=8)):
        def worker(seed: int) -> None:
            rng = random.Random(seed)
            for _ in range(ops):
                k = rng.randrange(200)
                v = cache.get(k)
                assert v is None or v == k * 2
                cache.put(k, k * 2)
        ts = [threading.Thread(target=worker, args=(i,)) for i in range(workers)]
        for t in ts: t.start()
        for t in ts: t.join()
        assert len(cache) <= 64
        if isinstance(cache, ThreadSafeLRU):
            cache.check_invariants()


if __name__ == "__main__":
    for t in (test_basic_eviction, test_update_does_not_evict, test_none_value_and_capacity_one,
              test_fuzz_against_ordereddict, test_threads):
        t()
        print("ok ", t.__name__)

Two choices in that file deserve a word. The miss marker in the tests is a private _MISSING = object(): a fresh object that can never equal any stored value, so None remains a storable value. And the thread-safe class wraps the base methods instead of putting locks inside the core class, so the single-threaded class stays free of locking overhead and can be tested on its own.

9 · Edge cases

Walk through these aloud before the interviewer asks, because each is where some implementation breaks. Capacity zero or negative: decide. Rejecting it in the constructor with ValueError is cleanest; a cache that silently stores nothing hides configuration mistakes. Capacity one: every new key evicts the previous one, and the victim is the only node, so tail.prev is also head.next; sentinels make this case need no special code, which is a good thing to point out. Updating an existing key in a full cache must not evict. Storing None: if allowed, the miss signal cannot be None. get on a missing key must change nothing, including recency. Unhashable keys such as lists raise TypeError from the dict; let them, because guessing a conversion would silently merge different keys.

A subtler case is a key whose hash or equality is unusual: 1, 1.0 and True are equal and have the same hash in Python, so they are the same key. functools.lru_cache has a typed=True option for exactly this reason. Mentioning it is a small, cheap signal of depth.

10 · Testing: invariants and a reference

Pointer code fails in ways that unit tests with three operations rarely reveal. The strongest test is a fuzz test: generate thousands of random get and put calls on a small key space (so hits, misses, updates and evictions all happen often), apply each to your cache and to a trusted reference, here an OrderedDict driven the same way, and compare the entire recency order after every step. Comparing the whole order, not just return values, matters: a broken back-pointer corrupts the order many steps before it changes a value you return, and comparing order pinpoints the operation that caused it.

Run the fuzz test at capacities 1, 2, 3 and a larger one. Capacity 1 and 2 hit the boundary conditions constantly; a large capacity rarely evicts. Pair it with check_invariants, which walks from the head checking that every node's next.prev is itself, that each node is the one the dict holds for its key, and that the count equals the dict's size and is within capacity. Calling it at the end of each fuzz run catches pointer errors that the order comparison could miss, such as a dangling back-pointer that forward iteration never follows.

11 · Extensions the interviewer will ask for

Thread safety. Add one lock and hold it for the whole of get, put and delete. People are often surprised that get needs it: it rewrites pointers, so two concurrent gets can each read a neighbour the other is about to change and leave the list with a node whose next and prev disagree. Python's global interpreter lock (the GIL, a lock in CPython that lets only one thread run Python bytecode at a time) does not save you, because unlinking is several bytecodes and a thread switch can happen between them. If one lock becomes a bottleneck, shard: keep N independent locked caches and pick one with hash(key) % N. Contention falls roughly N-fold, at the cost that recency is now per shard: one shard may evict a fairly recent key while another holds an older one.

Time to live. Store an expiry timestamp in each node, taken from time.monotonic() (a clock that never goes backwards, unlike wall time). On get, an expired node is removed and reported as a miss. Expired nodes still occupy capacity until someone touches them, so when evicting prefer expired entries, or run a sweep that removes a bounded number per tick.

Capacity in bytes. Track a size per entry and a total. After inserting, evict from the tail in a loop until the total fits. Reject values larger than the budget up front; otherwise the loop empties the cache and still overflows.

LFU. Least frequently used needs a map from frequency to a doubly linked list of nodes with that frequency, plus a minimum-frequency pointer. The LFU answer below walks through it among the interview questions; it is a common second half of this round.

Compute on miss. Wrap the cache in a get_or_compute(key, fn). In a threaded server, avoid running fn while holding the lock (it may be slow), and avoid many threads computing the same key at once, which is the single-flight pattern discussed in the production section.

12 · Complexity

get and put are O(1): one dict operation and a constant number of pointer writes. The dict's O(1) is amortised: occasionally a dict grows and rehashes all entries, so one insert is expensive, but averaged over many inserts the cost per insert is constant. Memory is O(capacity). In concrete terms, on Python 3.12 with integer keys, measured with tracemalloc, the node-based cache used about 148 bytes per entry against about 137 for OrderedDict and 84 for a plain dict: each entry pays for a dict slot, a 64-byte node object and the key itself. That overhead is one reason production caches written in lower-level languages pack these fields tightly, and why Redis chose not to keep a full linked list at all.

Why exact LRU is a weak policy on real traffic

LRU assumes the recent past predicts the near future. That holds for many workloads, but it fails badly on a scan: a batch job, a backup or a crawler that reads a large set of keys once each. Every key it reads becomes most recently used, and each one pushes a genuinely hot entry off the tail. After the scan the cache is full of keys that will never be read again, and the hot set must be refetched from the backend. The cache did the worst possible thing at the moment it mattered. This is not hypothetical: database buffer pools, CDN caches and operating system page caches all add protection against it.

The classic protection is segmented LRU. New entries go into a small probationary segment; only an entry that is accessed a second time is promoted to the protected segment. A scan fills the probation area and evicts itself, while the protected hot set survives. Linux's page cache uses a related idea with active and inactive lists, and MySQL's InnoDB buffer pool inserts newly read pages at a midpoint of its LRU list rather than at the head, so a full table scan cannot flush the whole pool.

Frequency matters as much as recency: TinyLFU and W-TinyLFU

LFU keeps hit counts and evicts the least popular entry. It resists scans, because a key read once has a count of one, but pure LFU never forgets: a key that was hugely popular yesterday stays cached forever, and keeping an exact counter per key, including keys not in the cache, costs memory. TinyLFU fixes both. It keeps approximate frequencies for all recently seen keys in a compact count-min sketch (a small table of counters indexed by several hash functions; the estimate for a key is the minimum of its counters), and periodically halves every counter so popularity decays. It is used as an admission filter: when the cache is full and a new key arrives, compare the new key's estimated frequency with the eviction victim's; admit the newcomer only if it is more popular. A scan's keys all have frequency one, so they are rejected at the door.

W-TinyLFU, used by Java's Caffeine library, adds a small "window" LRU of about one percent of capacity in front, so a brand-new key that is about to become popular gets a short chance to build up frequency before facing the filter. Caffeine's published benchmarks show it beating LRU on hit rate across database, search and web traces, often by a wide margin on scan-heavy ones. You do not need to implement it in an interview; you need to explain why it beats LRU in two sentences.

Approximating LRU: CLOCK and Redis sampling

Exact LRU has a cost beyond memory: every read is a write to shared structure. On a busy multi-threaded server that means every get takes a lock and dirties cache lines that other cores also read. CLOCK avoids it. Entries sit in a circular array, each with one reference bit. A read only sets the bit, which is cheap and does not reorder anything. To evict, a "hand" sweeps around the circle: if an entry's bit is set, clear it and move on (a second chance); if it is clear, evict it. Entries that are read often keep getting their bit set and survive; entries untouched for a full revolution go. Operating systems have used CLOCK variants for page replacement for decades because of this.

Redis takes a different shortcut. It stores a small last-access timestamp in each key's object header and, when it must evict, samples a few random keys (five by default, set by maxmemory-samples) and evicts the one idle longest. Since Redis 3.0 it also keeps a pool of good candidates across evictions, which brings the result close to true LRU; the Redis documentation says that with ten samples the approximation is very close to theoretical LRU, and that the reason for not implementing true LRU is that it costs more memory. Redis also offers an LFU mode that stores a logarithmic, decaying counter in the same header field. The lesson for an interview: exact LRU is a teaching device; real systems trade a little accuracy for less memory and less write traffic.

What the GIL does and does not protect

In CPython, the global interpreter lock lets one thread execute bytecode at a time, so individual operations such as a single dict assignment are effectively atomic. That tempts people to skip the lock. But _unlink is a tuple assignment that compiles to several loads and stores, and a thread switch can occur between them. Two threads moving neighbouring nodes can interleave so that A's next points to C while C's prev still points to B, which is now detached. Later traversal loops forever or loses entries. The pure-Python fallback of functools.lru_cache in CPython's source takes an RLock for exactly this reason, with a comment that the linked-list updates are not thread-safe. On the free-threaded build available from Python 3.13, where there is no GIL, the need for explicit locking is even more direct.

Sharding and what it costs

Sharding into N caches divides contention because two threads only compete when their keys hash to the same shard. The costs are worth naming. Recency becomes local: the cache evicts the oldest entry of one shard, not the oldest overall. Capacity becomes fragmented: if keys are unevenly distributed, one shard evicts while another has free space. And global operations such as "clear" or "size" now visit every shard. These are usually acceptable, and they generalise: whenever a single lock protects a structure with no cross-key invariant, splitting by key is the first scaling move.

Memory per entry and why it matters at scale

The measured 148 bytes per entry on Python 3.12 breaks down into a dict slot plus hash table spare capacity, a 64-byte node with four slots, and the key object. For a million small entries that is about 150 MB of overhead before counting values. In C or Rust the same structure might be 32 to 48 bytes per entry. This is why language matters for caches and why designs like Redis's, which store a 24-bit access clock in an existing header instead of two 8-byte pointers per key, are attractive at hundreds of millions of keys.

Caching function results: lru_cache's sharp edges

functools.lru_cache builds its key from the call arguments, so arguments must be hashable, and calls whose arguments are equal but of different types (1 versus 1.0) are usually treated as the same call unless typed=True (the docs note some types, such as int and str, may be cached separately anyway). Applied to a method, the cache holds a reference to self in every key, which keeps every instance alive as long as the cache lives; the Python documentation warns about this and suggests caching at module level or using cached_property for per-instance values. And the cache returns the same object to every caller: if a cached function returns a list and one caller appends to it, every later caller sees the change. Return immutable values (tuples, frozen dataclasses) from cached functions.

How caches fail in production

The most common failure is not a bug in the eviction code but a low hit rate nobody measured. A cache with a 5 percent hit rate adds memory, latency for the lookup and invalidation complexity, and saves almost nothing. Always export hits, misses and evictions as counters, compute the hit rate on a dashboard, and look at the eviction rate alongside it: a high eviction rate with a low hit rate usually means the cache is too small for the working set, while a low eviction rate with a low hit rate means the keys are not being reused at all, and no size will help.

The second is the cache stampede, also called thundering herd. A popular key expires or is evicted, and hundreds of concurrent requests miss at once and all call the backend. The backend slows down, requests time out, clients retry, and the load grows. The standard fixes are single-flight (the first miss stores an in-progress marker such as a concurrent.futures.Future under the key; later misses wait on it instead of recomputing), early refresh (recompute a hot key shortly before it expires, with a little random jitter so many keys do not refresh at the same instant), and serving the stale value while one request refreshes it.

The third is unbounded growth, the problem this lesson opened with: an @lru_cache(maxsize=None) or a module-level dict used as a cache. It looks fine in tests and runs out of memory after a week in production. A bounded cache is the fix, and a byte budget is better than an entry count when value sizes vary.

Correctness failures: stale and shared data

A cache returns what was true when the entry was stored. If the underlying data changes, readers see the old value until the entry is evicted or expires. For a profile name that is harmless; for a permission check it is a security bug (a revoked user keeps access until the entry ages out). Decide per key type how stale data may be, and either delete the entry on write (invalidation) or set a short TTL. A related bug is returning a mutable cached object: one request mutates it and every other request sees the mutation. Copy on the way out or cache immutable values.

Metrics and knobs

Track hit rate, eviction rate, size in entries and bytes, and the latency of the miss path, because the miss path is what users feel when the cache is cold, for example right after a deploy restarts every process. Redis exposes keyspace_hits, keyspace_misses and evicted_keys in INFO stats; an in-process cache should expose the same three counters. The knobs are size, policy and TTL. Size is tuned by plotting hit rate against capacity, often from a replay of logged keys: the curve flattens once the working set fits, and memory beyond that point is wasted. Redis adds maxmemory-policy (for example allkeys-lru, allkeys-lfu or volatile-ttl) and maxmemory-samples.

Cold starts and deploys

An in-process cache is empty after every restart. If a fleet of 50 instances deploys at once, the backend suddenly sees 50 caches' worth of misses. Rolling deploys spread this out; some systems warm the cache from a snapshot or from a shared cache tier before taking traffic. Measuring the miss path's latency and the backend's headroom tells you whether a simultaneous restart is survivable.

The real case: why Redis approximates LRU

Redis is the most widely deployed cache in the industry, and its key-eviction documentation is an unusually honest design note. When memory reaches maxmemory, Redis evicts according to the configured policy, and its LRU is approximate: it samples maxmemory-samples keys (default five) and evicts the one idle longest, and since 3.0 it keeps a pool of good candidates between evictions. The documentation states that true LRU was not implemented because it costs more memory, shows plots comparing the approximation with theoretical LRU, notes that ten samples come very close, and adds that under power-law access patterns, where a few keys get most of the traffic, the difference is minimal. It also offers LFU policies with a logarithmic counter controlled by lfu-log-factor and decayed over time by lfu-decay-time. The design choice is the senior lesson of this case: the interview structure (exact order, two pointers per key) is correct and teaches the right reasoning, but a system holding hundreds of millions of keys chooses an approximation whose memory cost is a few bits per key, and measures hit rate to show the approximation is good enough.

Work it out

Trace this implementation with capacity 2 and explain what is wrong with it:

def put(self, k, v):
    if len(self.map) == self.cap:
        lru = self.tail.prev
        self._unlink(lru); del self.map[lru.key]
    if k in self.map:
        n = self.map[k]; n.value = v
        self._unlink(n); self._push_front(n); return
    n = _Node(k, v)
    self.map[k] = n; self._push_front(n)

Run: put(1,'a'), put(2,'b'), put(2,'z'), then get(1). What is returned, and what should be?

Answer

The bug: the eviction check runs before the update check. The two blocks are in the wrong order, so updating an existing key in a full cache evicts something.

CallWhat happensState (MRU first)
put(1,'a')size 0, not full; key new; insert1
put(2,'b')size 1, not full; key new; insert2, 1
put(2,'z')size is 2, so it evicts tail.prev, which is key 1, an unrelated live entry; then finds key 2 and updates it2
get(1)key 1 is gone: miss2

Returns the miss value. Should return 'a'. An update does not change the number of entries, so it must never evict; this version threw away a live entry and left the cache holding one item when it should hold two.

Now try put(1,'a'), put(2,'b'), put(1,'z'), get(2). Here the victim is key 1, the very key being updated, so the code evicts it and re-inserts it fresh, and get(2) correctly returns 'b'. The answer is right by luck, yet an eviction happened that should not have. A test that only checks return values passes; a test that also checks the eviction counter, or the fuzz test comparing full order, fails. That is why the full solution counts evictions.

The fix is to handle the update path first and return, then check capacity only on the new-key path. The lesson to say in the interview is that every mutating path must preserve the invariant "the map and the list hold the same nodes, never more than capacity". Write the invariant before the method and this class of bug becomes visible while you type; an invariant check in the tests finds it on the first run.
