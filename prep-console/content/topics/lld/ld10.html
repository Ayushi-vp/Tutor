A vending machine at a railway station takes a customer's two one-euro coins for a bottle of water priced at 1.35, drops the bottle, and then discovers it has no five-cent coins to give 65 cents change. The customer walks away 65 cents short and complains to the station. The next week another machine's spiral catches a packet of crisps halfway; the software, having counted the sale when the motor turned, keeps the money and decrements the stock for an item still hanging in the window. Neither bug is in an algorithm. Both are about the order in which a machine does things, and about which step cannot be undone.

The vending machine is the classic interview question for the State pattern. A machine is always in one of a few states (waiting for money, holding money, dispensing, out of service), and the same button means something different in each. Pressing "select" with no money should say "insert money"; with enough money it should start a sale; while dispensing it must be ignored. Candidates either write one enormous method with nested conditionals on the state, which grows a branch for every combination, or they model each state as an object that knows which actions it allows. The second is what the round is testing.

Underneath the pattern sit three questions that separate strong answers. Is the money exact, and does every coin reconcile? Can the machine make change from the coins it actually has, which is a harder problem than the textbook greedy algorithm suggests? And where is the commit point, the one irreversible step, around which every check must be arranged? The same questions, with banknotes and bank accounts, describe an ATM: authenticate, check the notes, authorise the debit, dispense, and undo the debit if the notes never come out.

Interviewers often ask for the ATM as a follow-up, or instead of the vending machine, because it adds a second party (the bank) and a distributed failure (the connection drops between debit and dispense). Both reward the same habit: list what can fail, decide what is irreversible, and put every check before it and a compensating action after it.

The question is also a good test of restraint. It is easy to add classes for coins, buttons, displays and motors; the strong answer models only what the rules depend on: states, held coins, the coin bank, slots, and the injected hardware functions whose results the software must react to.

This lesson follows the round: clarify the requirements, write the state-by-action table, build a naive switch-based machine and watch it fail, then build the correct design in stages (states as classes, held coins, exact bounded change, validate-then-commit, jam handling, reconciliation), then the ATM, the full tested solution, edge cases, extensions such as card payments, complexity, and the change-making facts that make greedy wrong in practice.

State machines, and why this one is a good example

A finite-state machine has a fixed set of states and rules saying which events are allowed in each state and which state follows. A vending machine is a textbook example because its states are visible from outside. Idle: no money inserted; only inserting a coin does anything. Has money: coins inserted; the customer may insert more, select an item, or cancel. Dispensing: the motor is running; every button must be ignored or rejected until it finishes. Out of service: the operator has disabled sales; nothing is accepted. The useful habit is to draw a table with states as rows and actions as columns and fill in every cell before coding, because each empty cell is a question you have not answered.

The State pattern in one paragraph

The State pattern turns each state into a class. All state classes share an interface with one method per action: insert, select, cancel. The machine (called the context) holds a reference to its current state object and forwards every action to it: machine.select("A1") becomes self.state.select(self, "A1"). Each state implements the actions it allows, and may replace the machine's state with another, which is a transition. The base class implements every action by raising an "invalid action" error, so a state rejects everything it does not explicitly allow. Adding a state means adding a class; adding an action means adding a method to the base and overriding it where it is legal.

Money, coins and change

Money is kept as integer cents, never floating-point numbers, for the same reason as in the earlier cases: decimal fractions are not exact in binary. Coins are kept as a multiset, a count per denomination, which Python's collections.Counter provides: Counter({100: 4, 50: 2}) is four euro coins and two 50-cent coins, and adding or subtracting Counters adds or removes coins. Giving change means choosing coins from the machine's bank that add up to the amount owed. The textbook method is greedy: take the largest coin that fits, repeat. For everyday currencies with unlimited coins that gives the fewest coins. A real machine does not have unlimited coins, and that is where greedy breaks, as the body shows.

Beyond vending machines

The State pattern appears wherever an object's behaviour depends on where it is in a lifecycle: a network connection (connecting, open, closing, closed), an order (placed, paid, shipped, returned), a document in review (draft, submitted, approved, published), a media player (stopped, playing, paused). In each, the same request means different things in different states, and the same design applies: draw the state-by-action table, reject by default, and keep each state's rules together. Learning it on a vending machine, where the states are visible and the stakes are a few coins, makes it easy to recognise in larger systems.

The analogy, and where it breaks

Think of a shop assistant who will not hand over your purchase until they have counted your money, checked the shelf and opened the till to make sure they can give change. If they cannot, they hand your own coins back. That is validate-then-commit. The analogy breaks at the jam: a human assistant can pick up a dropped item and hand it over; a machine whose spiral catches the item cannot, so it must detect the failure with a sensor and give the money back.

1 · Clarify the requirements

Ask which coins and notes are accepted, whether card payment exists, whether a customer may insert more money after selecting, what happens when an item is out of stock (refund or choose again), what happens when change cannot be made, whether the machine can detect a failed dispense, how many coins of each kind it holds and whether it recycles inserted coins as change, whether the operator can take it out of service, and what reporting the operator needs. For the ATM: authentication rules, withdrawal limits, note denominations, and what happens on communication failures.

A typical agreed scope: coins of 5, 10, 20, 50, 100 and 200 cents; select after inserting; out of stock lets the customer choose again; impossible change refuses the sale and returns the inserted coins; a drop sensor reports success or jam; inserted coins may be used as change; an operator out-of-service mode. Invariants: the customer either receives the item and exact change, or gets back exactly the coins inserted; cash in the machine equals the starting float plus revenue; stock never goes negative.

3 · Stage one: the naive switch

def select(self, code):
    if self.state == "idle":
        print("insert money")
    elif self.state == "has_money":
        item = self.items[code]
        if self.balance >= item.price:
            self.dispense(item)
            self.give_change(self.balance - item.price)   # may fail AFTER dispensing
            self.balance = 0
            self.state = "idle"
    elif self.state == "dispensing":
        pass                                              # silently ignored
    # out_of_service: forgotten, falls through and does nothing

Its faults are typical. Change is attempted after dispensing, so an impossible change short-changes the customer. The balance is a single number, so a cancel cannot return the customer's actual coins and the machine cannot use them as change. Illegal actions are handled inconsistently: printed, silently ignored, or forgotten. A forgotten state falls through and does nothing. And every action method repeats the same chain of conditions, so adding "card payment" means editing every method.

4 · Stage two: states as classes

The base State class defines insert, select and cancel, each raising InvalidAction with the state's name. Idle overrides only insert: accept the coin and switch to HasMoney. HasMoney overrides all three. Dispensing and OutOfService override nothing, so every action is rejected. The machine's public methods are one line each, forwarding to the current state, and the operator's set_out_of_service refuses to switch off while a customer's coins are held, which would otherwise strand them. Notice how little code each state needs; that is the State pattern working.

5 · Stage three: held coins

Inserted coins go into machine.inserted, a Counter separate from the coin bank. Rejected denominations (a 3-cent token, a foreign coin) raise and are physically returned at once. Cancel returns the contents of inserted: the customer gets back exactly the coins they put in, which is what people expect and what keeps the bank's contents unchanged by aborted sales. Only when a sale commits are the inserted coins added to the bank.

6 · Stage four: exact change from a limited supply

The change owed is the inserted total minus the price. The coins available are the bank plus the inserted coins, since a machine that recycles coins can hand back one of yours. Greedy, take the largest coin that fits, is fast and often right, but with a limited supply it can fail even for euro coins: to make 60 cents from one 50-cent and three 20-cent coins, greedy takes the 50 and then cannot make 10, while three 20s work. The textbook statement that greedy is optimal for canonical coin systems assumes an unlimited supply of each coin; a machine never has that.

exact_change(amount, stock) solves the bounded problem with dynamic programming. It keeps a dictionary from each reachable amount to the fewest-coin multiset that reaches it, starting with {0: no coins}. It then considers the available coins one physical coin at a time; for each, it tries adding it to every amount reached so far (iterating from high to low so a coin is used at most once) and keeps the result if it reaches a new amount, or the same amount with fewer coins. At the end it returns the multiset for the target amount, or None if the amount is unreachable. The cost is the number of coins times the number of reachable amounts, tiny for a vending machine: a few hundred coins and amounts up to a few hundred cents.

The solver also handles non-canonical systems, where greedy gives more coins than needed even with unlimited supply. The change-making article's example is US coins without nickels: 40 cents from 25, 10 and 1 is seven coins greedily (25, 10, five 1s) and four optimally (four 10s); the test checks both.

A worked trace of the change solver

Make 60 cents from one 50 and three 20s. The table of reachable amounts starts as {0: nothing}. Processing the 50 first (largest denominations first, to find few-coin answers early): from 0 add 50, giving {0, 50}. First 20: from 50 add 20 is 70, too much; from 0 add 20 gives 20; table {0, 20, 50}. Second 20: from 50 is 70 (too much), from 20 gives 40 (two coins), from 0 gives 20 (already reached with one coin, no better); table {0, 20, 40, 50}. Third 20: from 50 is 70, from 40 gives 60 with three 20s, from 20 gives 40 (no better), from 0 gives 20 (no better); table {0, 20, 40, 50, 60}. The answer for 60 is three 20s. Greedy, by contrast, commits to the 50 in its first step and never reconsiders, which is exactly why it fails. Iterating from the highest reached amount downwards is what stops one physical coin being used twice within the same pass, the same trick as in the classic 0/1 knapsack.

7 · Stage five: validate, then commit

HasMoney.select runs every check before anything irreversible. Is the slot present, stocked and not jammed? If not, raise OutOfStock and stay in HasMoney with the coins held, so the customer can choose something else. Is the inserted total at least the price? If not, raise InsufficientFunds with the shortfall. Can exact change be made from bank plus inserted coins? If not, refund and return to Idle with the message "cannot make change". Only when all three pass does the machine enter Dispensing and call _commit. The drill's first scenario is the second test: no 5-cent coins, two euros for a 1.35 item, 65 cents of change impossible, so the sale is refused, the same two euro coins come back, stock and revenue are untouched.

8 · Stage six: the jam path and reconciliation

_commit runs the motor through an injected function that returns whether the drop sensor saw the item fall. If it did not, the sale never happened: the inserted coins are refunded, stock and revenue do not change, and the slot is marked jammed so later selections treat it as out of stock until an engineer clears it. If it did, the machine adds the inserted coins to its bank, removes the change coins, clears the held coins, decrements stock, adds the price to revenue, returns to Idle, and checks the invariant: the value of the coin bank equals the starting float plus revenue, and no coin count is negative. A test runs 40 sales of a 70-cent bar paid with one euro each against a bank of 20 coins each of 50, 20 and 10 cents: the first 20 sales give 20 + 10 cents change, after which the 10-cent coins are gone, and the remaining 20 attempts are refused and refunded rather than short-changed. Revenue is 14.00 and cash reconciles after every sale.

9 · Stage seven: the ATM

The ATM has the same shape with one more party. Its states are idle, card inserted and authenticated, small enough for an enum with guard checks rather than classes, which is itself a design point: use the State pattern when states are many and rich, not by reflex. enter_pin asks the bank to verify; three failures retain the card and return to idle. withdraw(amount) follows an order chosen so that each failure after money moves has a compensating action. First, check that the amount can be made from the notes in the cassettes, using the same bounded solver as the vending machine; if not, refuse before contacting the bank at all. Second, ask the bank to authorise the debit, which either declines or returns a transaction id. Third, dispense. If the dispenser reports that the notes did not leave the machine, send a reversal for that transaction id so the account is restored, and report the failure. Only after a successful dispense are the notes removed from the cassettes.

Two details are visible only in a trace. The bank does not change until step 4, so if the drop sensor had reported a jam at step 3, nothing would need undoing except handing back the held euro. And the reconciliation runs at the very end, after every field has been updated, so it checks the final state rather than an intermediate one.

11 · Testing a state machine

State machines are tested through their transitions and their invariants. For transitions, walk the state-by-action table: every reject cell gets a test that the action raises (the illegal-actions test covers the idle row and out of service), and every allowed cell gets a test of the resulting state and side effects. For outcomes, test each way a sale can end: success with change, refused for change with the same coins back, out of stock with coins still held, insufficient funds, and a jam with a refund and a blocked slot. For invariants, assert inside the code (cash reconciles after every sale) and drive many operations through it (40 sales until change runs out). Inject the motor so a test can force a jam deterministically, and inject the ATM's dispenser and bank for the same reason. A machine whose hardware is behind functions is a machine you can test on a laptop, which is how real embedded teams work before anything touches metal.

12 · Talking through the design

A strong summary in the round: "The machine is a state machine, and since most actions are illegal in most states, I give the base state a raising default and each state overrides only what it allows. Money is cents; inserted coins are held apart so a refund returns the same coins and the bank only changes on a committed sale. The only interesting cell is select while holding money: I check stock, then funds, then exact change from bank plus inserted coins using a bounded solver, because greedy fails on a limited supply. Dispensing is the commit point: the drop sensor decides between finishing the sale and refunding. After each sale I assert cash equals float plus revenue. The ATM follows the same rule with a bank in the loop: check the notes, authorise, dispense, reverse on failure."

13 · The full solution

The file below contains the change solvers, the vending machine with its five state classes, and the ATM with a fake bank, plus eight tests: the happy path, refusal when change is impossible, greedy versus exact on a limited supply, using inserted coins as change, illegal actions and cancel, the jam path, reconciliation over 40 sales, and the ATM's PIN, debit and reversal. Python 3.12, standard library only.

"""Vending machine with the State pattern, exact change from a LIMITED coin supply,
validate-then-commit dispensing with a jam sensor, and a small ATM that authorises, dispenses
and reverses. Python 3.12, standard library only. Run: python vending.py"""
from __future__ import annotations

import itertools
from collections import Counter
from dataclasses import dataclass, field
from typing import Callable


# ------------------------------------------------------------------ change from a limited supply
def greedy_change(amount: int, stock: Counter) -> Counter | None:
    """Largest coin first. Optimal for canonical systems with UNLIMITED coins; can fail here."""
    out = Counter()
    for d in sorted(stock, reverse=True):
        take = min(stock[d], amount // d)
        if take:
            out[d] = take
            amount -= take * d
    return out if amount == 0 else None


def exact_change(amount: int, stock: Counter) -> Counter | None:
    """Fewest coins making `amount` from the coins actually available (bounded change-making).
    Dynamic programming over reachable amounts, one coin at a time: O(coins x amount)."""
    if amount == 0:
        return Counter()
    best: dict[int, Counter] = {0: Counter()}            # amount -> fewest-coin multiset
    for d in sorted(stock, reverse=True):
        for _ in range(stock[d]):
            for a, used in sorted(best.items(), reverse=True):
                b = a + d
                if b <= amount and (b not in best or sum(best[b].values()) > sum(used.values()) + 1):
                    best[b] = used + Counter({d: 1})
    return best.get(amount)


# ------------------------------------------------------------------ vending machine
class InvalidAction(Exception): ...
class OutOfStock(Exception): ...
class InsufficientFunds(Exception): ...
class CannotMakeChange(Exception): ...


@dataclass
class Slot:
    code: str
    name: str
    price: int                   # cents
    count: int
    jammed: bool = False


@dataclass(frozen=True)
class Result:
    item: str | None
    change: tuple[tuple[int, int], ...]   # (denomination, count)
    message: str


class State:
    """Default: every action is illegal. A state overrides only what it allows."""
    name = "?"

    def insert(self, m: "VendingMachine", coin: int) -> None:
        raise InvalidAction(f"cannot insert in {self.name}")

    def select(self, m: "VendingMachine", code: str) -> Result:
        raise InvalidAction(f"cannot select in {self.name}")

    def cancel(self, m: "VendingMachine") -> Result:
        raise InvalidAction(f"nothing to cancel in {self.name}")


class Idle(State):
    name = "idle"

    def insert(self, m, coin):
        m._accept(coin)
        m.state = HasMoney()


class HasMoney(State):
    name = "has_money"

    def insert(self, m, coin):
        m._accept(coin)

    def cancel(self, m):
        return m._refund("cancelled")

    def select(self, m, code):
        slot = m.slots.get(code)
        if slot is None or slot.count == 0 or slot.jammed:
            raise OutOfStock(code)                        # money stays in; customer may choose again
        paid = sum(d * n for d, n in m.inserted.items())
        if paid < slot.price:
            raise InsufficientFunds(f"need {slot.price - paid} more")
        pool = m.bank + m.inserted                         # inserted coins can be given as change
        change = exact_change(paid - slot.price, pool)
        if change is None:
            return m._refund("cannot make change")        # refuse BEFORE the irreversible step
        m.state = Dispensing()
        return m._commit(slot, change)


class Dispensing(State):
    name = "dispensing"                                   # transient: every action is rejected


class OutOfService(State):
    name = "out_of_service"


class VendingMachine:
    def __init__(self, slots: list[Slot], bank: Counter, accepted: set[int],
                 motor: Callable[[str], bool] = lambda code: True) -> None:
        self.slots = {s.code: s for s in slots}
        self.bank, self.accepted, self.motor = Counter(bank), accepted, motor
        self.inserted: Counter = Counter()
        self.state: State = Idle()
        self.revenue = 0
        self._float = sum(d * n for d, n in self.bank.items())

    # public API: delegate to the current state
    def insert(self, coin: int) -> None:
        self.state.insert(self, coin)

    def select(self, code: str) -> Result:
        return self.state.select(self, code)

    def cancel(self) -> Result:
        return self.state.cancel(self)

    def set_out_of_service(self, on: bool) -> None:
        if on and self.inserted:
            raise InvalidAction("refund the customer first")
        self.state = OutOfService() if on else Idle()

    # helpers used by states
    def _accept(self, coin: int) -> None:
        if coin not in self.accepted:
            raise InvalidAction(f"coin {coin} rejected")  # physically returned at once
        self.inserted[coin] += 1

    def _refund(self, why: str) -> Result:
        coins = tuple(sorted(self.inserted.items(), reverse=True))   # the same coins back
        self.inserted.clear()
        self.state = Idle()
        return Result(None, coins, why)

    def _commit(self, slot: Slot, change: Counter) -> Result:
        paid = Counter(self.inserted)
        if not self.motor(slot.code):                     # sensor saw nothing drop
            slot.jammed = True
            return self._refund(f"{slot.code} jammed")
        self.bank += paid
        self.bank -= change
        self.inserted.clear()
        slot.count -= 1
        self.revenue += slot.price
        self.state = Idle()
        self._check()
        return Result(slot.name, tuple(sorted(change.items(), reverse=True)), "enjoy")

    def _check(self) -> None:
        cash = sum(d * n for d, n in self.bank.items())
        assert cash == self._float + self.revenue, "cash does not reconcile"
        assert all(n >= 0 for n in self.bank.values())


# ------------------------------------------------------------------ ATM
class Declined(Exception): ...


@dataclass
class FakeBank:
    balances: dict[str, int]
    pins: dict[str, str]
    log: list[str] = field(default_factory=list)
    _ids: itertools.count = field(default_factory=lambda: itertools.count(1))

    def verify(self, card: str, pin: str) -> bool:
        return self.pins.get(card) == pin

    def authorise_debit(self, card: str, amount: int) -> str:
        if self.balances[card] < amount:
            raise Declined("insufficient funds")
        self.balances[card] -= amount
        txn = f"T{next(self._ids)}"
        self.log.append(f"debit {txn} {card} {amount}")
        return txn

    def reverse(self, txn: str, card: str, amount: int) -> None:
        self.balances[card] += amount
        self.log.append(f"reverse {txn} {card} {amount}")


class ATM:
    """IDLE -> CARD -> AUTHENTICATED -> (withdraw)* -> IDLE. Three wrong PINs retain the card."""

    def __init__(self, bank: FakeBank, cassettes: Counter,
                 dispenser: Callable[[Counter], bool] = lambda notes: True) -> None:
        self.bank, self.cassettes, self.dispenser = bank, Counter(cassettes), dispenser
        self.state, self.card, self.tries = "IDLE", None, 0
        self.retained: list[str] = []

    def insert_card(self, card: str) -> None:
        if self.state != "IDLE":
            raise InvalidAction("card already inserted")
        self.state, self.card, self.tries = "CARD", card, 0

    def enter_pin(self, pin: str) -> bool:
        if self.state != "CARD":
            raise InvalidAction("no card waiting for a PIN")
        if self.bank.verify(self.card, pin):
            self.state = "AUTHENTICATED"
            return True
        self.tries += 1
        if self.tries == 3:
            self.retained.append(self.card)
            self.state, self.card = "IDLE", None
        return False

    def withdraw(self, amount: int) -> Counter:
        if self.state != "AUTHENTICATED":
            raise InvalidAction("not authenticated")
        notes = exact_change(amount, self.cassettes)
        if notes is None:                                  # check BEFORE touching the account
            raise CannotMakeChange(f"cannot dispense {amount} from the notes loaded")
        txn = self.bank.authorise_debit(self.card, amount)
        if not self.dispenser(notes):                      # notes did not leave the machine
            self.bank.reverse(txn, self.card, amount)
            raise RuntimeError("dispense failed; debit reversed")
        self.cassettes -= notes
        return notes

    def eject(self) -> str:
        card, self.state, self.card = self.card, "IDLE", None
        return card


# ---------------------------------------------------------------- tests
EURO = {200, 100, 50, 20, 10, 5}                           # cents; machine takes no 1c/2c


def machine(**kw) -> VendingMachine:
    slots = [Slot("A1", "water", 135, 5), Slot("B2", "crisps", 85, 1), Slot("C3", "gum", 60, 3)]
    return VendingMachine(slots, Counter({100: 4, 50: 2, 20: 1, 10: 3}), EURO, **kw)


def test_happy_path_with_change() -> None:
    m = machine()
    m.insert(100)
    r = m.select("C3")                                     # gum 60c, 40c change
    assert r.item == "gum" and r.change == ((20, 1), (10, 2))
    assert isinstance(m.state, Idle) and m.slots["C3"].count == 2


def test_cannot_make_change_refunds_before_dispensing() -> None:
    m = machine()                                          # no 5c coins, so 65c is impossible
    m.insert(100); m.insert(100)
    r = m.select("A1")
    assert r.item is None and r.message == "cannot make change"
    assert r.change == ((100, 2),) and m.slots["A1"].count == 5 and m.revenue == 0


def test_greedy_fails_on_limited_supply_exact_succeeds() -> None:
    stock = Counter({50: 1, 20: 3})                        # canonical coins, limited supply
    assert greedy_change(60, stock) is None               # takes 50, then stuck at 10
    assert exact_change(60, stock) == Counter({20: 3})
    assert greedy_change(40, Counter({25: 5, 10: 5, 1: 10})) == Counter({25: 1, 10: 1, 1: 5})
    assert exact_change(40, Counter({25: 5, 10: 5, 1: 10})) == Counter({10: 4})   # non-canonical


def test_uses_inserted_coins_as_change() -> None:
    m = VendingMachine([Slot("C3", "gum", 60, 3)], Counter({50: 1}), EURO)
    for c in (20, 20, 20, 20):
        m.insert(c)                                        # 80c; 20c change exists only in coins just inserted
    r = m.select("C3")
    assert r.item == "gum" and r.change == ((20, 1),)


def test_illegal_actions_and_cancel() -> None:
    m = machine()
    for bad in (lambda: m.select("A1"), lambda: m.cancel()):
        try:
            bad()
        except InvalidAction:
            pass
        else:
            raise AssertionError("illegal action allowed in idle")
    try:
        m.insert(3)
    except InvalidAction:
        pass
    m.insert(50); m.insert(20)
    assert m.cancel().change == ((50, 1), (20, 1))
    m.set_out_of_service(True)
    try:
        m.insert(100)
    except InvalidAction:
        pass


def test_jam_refunds_and_blocks_slot() -> None:
    m = machine(motor=lambda code: code != "C3")
    m.insert(50); m.insert(10)
    r = m.select("C3")
    assert r.item is None and "jammed" in r.message and r.change == ((50, 1), (10, 1))
    m.insert(50); m.insert(10)
    try:
        m.select("C3")
    except OutOfStock:
        pass
    assert m.slots["C3"].count == 3 and m.revenue == 0


def test_reconciliation_over_many_sales() -> None:
    m = VendingMachine([Slot("X", "bar", 70, 100)], Counter({50: 20, 20: 20, 10: 20}), EURO)
    sold = refused = 0
    for _ in range(40):
        m.insert(100)
        r = m.select("X")
        if r.item:
            sold += 1
            assert sum(d * n for d, n in r.change) == 30
        else:
            refused += 1                                   # change ran out: refuse, never short-change
    assert (sold, refused) == (20, 20) and m.revenue == 1_400   # 20 x (20c + 10c) used every 10c coin
    assert m.bank[10] == 0 and m.bank[100] == 20


def test_atm_pin_debit_and_reversal() -> None:
    bank = FakeBank({"card1": 50_000}, {"card1": "1234"})
    atm = ATM(bank, Counter({5_000: 2, 2_000: 10, 1_000: 10}))
    atm.insert_card("card1")
    assert not atm.enter_pin("0000") and atm.enter_pin("1234")
    notes = atm.withdraw(13_000)
    assert notes == Counter({5_000: 2, 2_000: 1, 1_000: 1}) and bank.balances["card1"] == 37_000
    try:
        atm.withdraw(500)                                  # no 5.00 notes: refuse before debiting
    except CannotMakeChange:
        assert bank.balances["card1"] == 37_000
    atm.dispenser = lambda notes: False
    try:
        atm.withdraw(2_000)
    except RuntimeError:
        assert bank.balances["card1"] == 37_000 and bank.log[-1].startswith("reverse")
    atm.eject()
    atm.insert_card("card1")
    for _ in range(3):
        atm.enter_pin("9999")
    assert atm.retained == ["card1"] and atm.state == "IDLE"

14 · Edge cases

A coin inserted while dispensing: rejected (physically returned). Selecting an out-of-stock item: coins stay held and the customer can choose again or cancel. Exact payment: zero change is always possible. Overpayment far beyond the price (inserting 20 euros for a 1-euro item): may make change impossible; set a maximum accepted credit. Taking the machine out of service with coins held: refused until the customer is refunded. Power failure mid-sale: on restart, the machine must know whether a sale committed; persist the held coins and a "dispensing" marker before running the motor, and resolve on boot using the drop sensor's record. ATM card left in the slot: most ATMs retain it after a timeout. ATM amount not a multiple of the smallest note: refused by the note check before any debit.

15 · Extensions the interviewer will ask for

Card payments: a state for awaiting authorisation; authorise the price, dispense, then capture after the drop sensor confirms, or void on jam. Change strategy: prefer handing out coins that are plentiful, so scarce small coins last, by weighting the dynamic program's objective. Exact-change-only mode: when the bank cannot cover likely change, light the sign and accept only exact amounts. Inventory and telemetry: report low stock and low coins to the operator, an Observer on sales. Promotions: a pricing strategy injected into the machine. ATM deposits, balance enquiries and daily limits: more states and a limit check before authorisation.

16 · Complexity

Each action is O(1) apart from change-making. The bounded change solver is O(C × A) for C coins available and A reachable amounts up to the change owed, a few thousand operations for realistic machines. The ATM's note solver is the same with notes. Memory is O(denominations + slots), plus the solver's table of reachable amounts.

Canonical coin systems and why limited supply changes everything

A coin system is canonical if greedy always gives the fewest coins for every amount, given unlimited coins. Euro, sterling and US coins are canonical; it is possible to test any system for canonicity in polynomial time, and a system such as 25, 10 and 1 (US coins without the nickel) is not: 40 cents greedily is 25 + 10 + 1 + 1 + 1 + 1 + 1, seven coins, while four 10s is optimal. The vending machine adds a constraint the canonicity theory ignores: each denomination has a finite count. With limited coins, greedy can fail to find any answer at all, not just the best one, as the 60-cent example shows (one 50 and three 20s). The fix is to solve the bounded problem, which is a small knapsack-style dynamic program. Saying "greedy is fine for euro coins with unlimited supply, but the machine's supply is limited, so I need the exact solver" is precisely the senior distinction.

The commit point, generalised

Many operations combine reversible steps (checks, reservations, held coins) with one irreversible step (the item drops, cash leaves the ATM, an email is sent, a missile is launched). The design rule is to perform every check and every reversible preparation before the irreversible step, make that step the commit point, and plan a compensating action for each failure that can happen after it. The vending machine's compensation is a refund; the ATM's is a reversal; a payment system's is a refund or a void. Listing the steps of an operation and marking which are irreversible is a five-minute exercise that prevents a whole family of bugs, and it is the reasoning interviewers are probing with "what if the change cannot be made?".

Persisting state across power failures

A real machine can lose power between running the motor and recording the sale. On restart it must know what happened. The standard technique is a write-ahead record: before running the motor, persist "dispensing slot C3 with these held coins"; after the drop sensor confirms, persist "sale complete". On boot, a record of dispensing without completion is resolved by checking the sensor's latch or, failing that, by refunding and flagging the slot for inspection. This is the same idea as a database's write-ahead log, and it is why the state machine must be explicit: you cannot persist and recover a state that exists only implicitly in the control flow of a function.

Distributed failure in the ATM

The ATM's hardest failure is not a jam but a lost message. If the authorisation request reaches the bank and the debit is recorded, but the response never reaches the ATM, the ATM does not know whether the account was debited. It must not dispense on a guess. It reports the outcome as unknown, and a reconciliation process at the bank matches debits against dispense confirmations by transaction id, reversing any debit without a matching dispense. Banks run such reconciliation continuously. The software lesson is that every message carries a unique id, every operation can be matched to its outcome later, and the system is designed to be correct after reconciliation even when individual messages are lost.

One controller, one thread

A vending machine's events, coins dropping through the validator, buttons pressed, the drop sensor firing, arrive from hardware interrupts at unpredictable times. The robust structure is the same as the elevator's: a single control loop owns the state and processes events from a queue one at a time. A coin that arrives while the machine is dispensing is then simply an event handled by the Dispensing state, which rejects it, rather than a race between two threads updating the held coins. Embedded controllers are usually written exactly this way, and the State pattern fits it naturally, since "handle this event in the current state" is the loop's only job.

Coins, fraud and validation

Coin validators measure weight, diameter and metal properties to accept genuine coins and reject slugs and foreign coins. Two software consequences follow. Credit is given only for coins the validator accepted, and the routing gate sends rejected coins straight to the return tray, so insert raising on an unknown denomination mirrors the hardware. And the machine should never pay out more than it can account for: the reconciliation invariant is also a fraud detector, because a manipulated validator that credits coins it did not keep would make counted cash fall short of recorded revenue.

When the State pattern is overkill

The ATM in the solution uses a string state and guard checks rather than classes, because it has three states and each action is legal in exactly one. The State pattern pays when states are numerous and each changes the meaning of many actions; it costs a class per state and indirection that makes a small machine harder to read. A useful test: if the conditionals on the state start repeating across several methods, extract states into classes. Interviewers appreciate hearing that you chose the pattern for the vending machine and deliberately did not for the ATM, with the reason.

How real machines fail

Vending machine operators see the same failure classes the design addresses. Change runs out, usually of one small denomination, so machines refuse sales or switch to exact-change-only mode; telemetry that reports coin levels lets operators refill before it happens. Products jam on the spiral, which drop sensors detect, turning a "stolen money" complaint into an automatic refund. Coin validators reject worn or foreign coins, which must be returned immediately rather than credited. Card readers time out mid-transaction, which is why card flows authorise first and capture after the drop. And power failures mid-sale require the persisted state discussed in the deep section.

ATM failures are similar in shape and higher in stakes. Note jams in the dispenser, partially dispensed bundles (some notes out, some retained), cassettes running out of a denomination, communication failures with the bank, and card retention. Each has a defined response: a reversal for undispensed amounts, a partial reversal for partial dispenses, refusing amounts that cannot be made from the cassettes, and reconciliation for communication failures.

Customer-facing behaviour

Every refusal is a customer experience. "Cannot make change" should say so and return the coins at once, not after a timeout; "out of stock" should keep the credit so the customer can choose again; a jam should refund automatically and show a message, because the customer cannot see the sensor. Logging each refusal reason, as the measurements below suggest, is how operators learn which of these is costing them sales.

Remote management

Modern machines report sales, stock, coin levels and faults over a network, which changes operations from fixed refill routes to demand-driven ones: a technician visits the machines that are low on stock or change, or have jammed slots, rather than every machine on a schedule. The software needed is small (an event stream of sales and faults from the controller) but it depends on the controller having explicit states and outcomes to report, which is another argument for modelling them as first-class objects rather than as implicit control flow.

What to measure

For vending: sales and refusals by reason (out of stock, insufficient funds, cannot make change), jams per slot, coin levels per denomination, and reconciliation differences between counted cash and recorded revenue at each collection, which should be zero. For ATMs: dispense failures and reversals, unresolved transactions awaiting reconciliation, cassette levels, retained cards, and the time each terminal spends out of service.

Operations

Prices and products change on refill, so prices should be data loaded by the operator rather than code. Coin floats are tuned per site: a station machine needs many 5- and 10-cent coins, an office machine where most items cost exactly a euro needs few. Firmware updates must preserve the persisted state format, or a machine that loses power during an update may forget a sale in progress.

The real case: the change-making problem

The change-making problem, as summarised in the standard references, is the mathematical core of both machines. Its key facts are exactly the ones this lesson depends on. The greedy method, taking the largest coin not larger than the remaining amount, is optimal for some coin systems, called canonical, and not for others; the article's example is making 40 US cents without nickels from 25, 10 and 1, where greedy chooses seven coins and the optimum is four. Whether a coin system is canonical can be tested in polynomial time, and the general problem is solved by dynamic programming over amounts. The vending machine adds a limit on how many of each coin exist, which the canonical-system result does not cover, so even euro coins can defeat greedy, and the bounded dynamic program in this lesson is the practical answer. Knowing where the textbook result stops applying is the real point of the case.

Work it out

A machine's coin bank holds 4 × 1.00, 2 × 0.50, 1 × 0.20, 3 × 0.10 and no 0.05 coins. A customer inserts 2.00 (two 1.00 coins) and selects an item priced 1.35.

(a) Can it make change? (b) A second customer inserts 1.00 and selects an item priced 0.85. What happens? (c) A third customer inserts 1.00 for an item priced 0.40, and the bank has only one 0.50, three 0.20 and nothing smaller. What does greedy do, and what should the machine do? (d) What should the design do about all this?

Answer

(a) First customer. Change owed is 200 − 135 = 65 cents. Every coin the machine holds, including the two euros just inserted, is a multiple of 10 cents, and there are no 5-cent coins, so 65 cents is impossible. The machine must refuse the sale before dispensing and return the same two euro coins. This is the solution's second test.

(b) Second customer. Change owed is 15 cents. Again impossible without a 5-cent coin: refuse and refund. The machine can now sell nothing whose change ends in 5, and from the customer's point of view it is broken.

(c) Third customer. Change owed is 60 cents from one 50 and three 20s. Greedy takes the 50, leaving 10, with no 10-cent coin: greedy says impossible. But three 20s make 60. Euro coins are canonical, yet greedy fails here because the supply is limited; the bounded solver finds 20 + 20 + 20, and the sale goes ahead. A machine using greedy would refuse a sale it could have made.

(d) The design. Check change before the commit point and refund if it is impossible; never dispense and then discover the problem. Use the exact bounded solver, not greedy. Keep the inserted coins available as change (in (a), the customer's own coins are part of the pool, though they do not help here). Light "exact change only" when the bank cannot cover the change for likely prices, and report coin levels so the operator refills 5- and 10-cent coins before the machine starts refusing sales. A cheap operational improvement: when giving change, prefer larger coins where possible so small ones last longer.
