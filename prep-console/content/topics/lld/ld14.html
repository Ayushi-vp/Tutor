A user spends an hour editing a long document, pastes a block in the wrong place, and presses undo. The editor removes one character of the paste. They press undo forty more times. The paste is gone, but so is the sentence they typed just before it, and pressing redo does nothing because they typed a space by accident in between. Or worse: they open a 200 MB log file and the editor freezes for a minute, then crashes out of memory. Both experiences come from design decisions inside the editor, not from the user.

The text editor with undo and redo is a classic machine-coding round because it is a pure test of modelling actions. Every change to the document must be representable as something that can be performed, reversed and performed again, consistently, in any order the user chooses. That is the Command pattern, and this problem is its textbook application. Undo and redo then become two stacks and a handful of rules, and the interesting questions are the rules: what a delete must remember, why a new edit throws away the redo history, how keystrokes are grouped so undo feels natural, how a replace-all of 300 matches becomes a single step, and where the cursor should land.

Underneath sits a second question that strong candidates raise and interviewers love: how is the document itself stored? A Python string makes every insertion copy everything after it. An array of lines is what many editors start with, and Microsoft's VS Code team documented exactly why they abandoned it: one user could not open a 35 MB file with 13.7 million lines because the per-line objects needed about 600 MB of memory. They moved to a piece table, an old idea from early word processors in which the original text is never copied and every edit is a small record pointing into two buffers. The same property that saves memory also makes undo cheap.

The round rewards reasoning about invariants. After any sequence of edits, undos and redos, undoing everything must return the original text exactly, and redoing everything must return the final text exactly. A test that does thousands of random operations and checks those two facts catches almost every bug in an undo system.

It is also a problem that rewards small, careful classes over clever ones. The commands are a few lines each; the subtlety is in the rules connecting them, and in testing those rules against the one property users care about: undo must give back exactly what they had.

This lesson follows the round: clarify the requirements, find the entities, draw the commands and stacks, try snapshots first and see why they fail, then build the design in stages (commands for insert and delete, the two stacks and their rules, coalescing, composite commands, cursor restoration, a history limit), then the piece table underneath, a full trace of the drill's sequence, testing, edge cases, extensions such as undo trees, collaboration and persistent history, complexity, and the VS Code write-up that motivates the data structure.

Actions as objects

The key idea is to stop thinking of an edit as something that happens and start thinking of it as a thing: an object that knows how to apply itself to the document and how to reverse itself. "Insert 'abc' at position 10" is such an object; applying it inserts the text, reversing it deletes three characters at position 10. "Delete 6 characters at position 5" is another; applying it removes them, and reversing it puts them back, which means it must remember what they were. This is the Command pattern. Once edits are objects, history is just a list of objects, and undo and redo are operations on that list.

Two stacks

The editor keeps an undo stack of commands it has executed, most recent on top, and a redo stack of commands it has undone. A new edit executes a command and pushes it on the undo stack. Undo pops the top command, reverses it and pushes it on the redo stack. Redo pops the top of the redo stack, executes it again and pushes it back on the undo stack. One more rule completes the system: a new edit clears the redo stack. After you undo three steps and type something new, the three undone steps no longer describe a possible future of this document, because they were computed against text that has now changed.

Why the Command pattern generalises

Undo is the famous use of commands, but treating actions as objects pays off in many other places, and mentioning them shows range. A macro recorder is a list of commands replayed later. A collaborative editor sends commands over the network. A database's write-ahead log is a sequence of commands that can be replayed after a crash. A job queue holds commands to be executed by workers. Photo editors, spreadsheets, CAD tools and game engines all use the same structure for history. Once actions are objects, they can be stored, sent, inspected, grouped, reversed and replayed, which a function call that just happens cannot.

How undo looks to the user

From the user's side, a good undo system has three properties. It is predictable: each press removes about one "thing I did", such as a word, a paste or a replace-all. It is exact: undoing everything returns precisely the text they started with. And it is reversible: redo restores what undo removed, until they start a new edit. Every rule in this lesson exists to deliver one of these three properties.

The analogy, and where it breaks

Think of a careful accountant's journal. Every change to the books is written as an entry that says exactly what was done, so it can be reversed by a matching entry. To go back a day, you reverse the day's entries in reverse order. The analogy fits commands well and breaks on redo: accountants never "redo" a reversed entry later after making new ones, because the books have moved on, which is precisely why an editor clears its redo stack on a new edit.

Where the document lives

Commands need a document to act on. The simplest is a Python string, but strings are immutable: inserting a character in the middle of a 10 MB string builds a new 10 MB string. A piece table avoids copying entirely. It keeps the file's original text in one buffer that is never changed, appends everything the user types to a second, add buffer, and describes the document as a list of pieces, each saying "take this many characters from that buffer starting here". Inserting text appends it to the add buffer and splits one piece into three; deleting text shortens or removes pieces. Neither ever moves existing text.

What the round expects

A command interface with execute and undo; insert and delete commands, with delete capturing its text; an editor with two stacks and the redo-clearing rule; coalesced typing; a composite command for replace-all; cursor restoration; and tests. Raising the document representation, and ideally implementing a simple piece table, is what separates a strong answer.

1 · Clarify the requirements

Ask which operations exist (type at the cursor, delete or backspace, delete a selection, paste, replace-all, move the cursor), what one undo step should cover (a keystroke, a word, a paste), whether redo must survive new edits, whether undo history is unlimited or bounded, whether it must survive closing the file, how large files get, and whether several people edit the same document at once.

A typical agreed scope: a single-user editor core with a cursor; type, backspace, delete a range and replace-all; undo and redo with typing grouped by word, a new edit clearing redo, multi-edit operations as one step, and the cursor restored; a configurable history limit; documents up to hundreds of megabytes; no persistence or collaboration in the code. The invariants to state: undoing every step from any point returns the original text exactly; redoing every step after that returns the latest text exactly; undo and redo never change text outside what the command describes.

2 · Entities and responsibilities

PieceTable owns the text: insert, delete (returning what it removed), length and full text. The Command interface has execute(doc) and undo(doc); Insert, Delete and Composite implement it. A Step pairs a command with the cursor positions before and after it. The Editor owns the document, the cursor, both stacks, the history limit and the coalescing state, and exposes the user actions. Separating the command objects from the editor means commands know nothing about cursors or stacks; they only know how to change a document and change it back.

3 · Stage one: snapshots

class SnapshotEditor:
    def __init__(self, text=""):
        self.text, self.undo_stack, self.redo_stack = text, [], []

    def edit(self, new_text):
        self.undo_stack.append(self.text)         # copy of the whole document
        self.text, self.redo_stack = new_text, []

    def undo(self):
        self.redo_stack.append(self.text)
        self.text = self.undo_stack.pop()

Snapshots (the Memento pattern) are correct and pleasantly simple: every state is stored whole, so undo and redo just swap strings. The cost is memory proportional to document size times history length. A 10 MB document with 1,000 edits is 10 GB of history, and every keystroke copies the document. It also loses information: a snapshot does not say what changed, so the editor cannot group keystrokes, show what an undo will do, or replay edits on another copy. Snapshots remain useful in a supporting role, for example a checkpoint every few hundred commands to speed up restoring very old states.

4 · Stage two: insert and delete commands

Insert(pos, text) executes by inserting text at pos and undoes by deleting len(text) characters at pos. Delete(pos, length) executes by deleting and, crucially, storing the text it removed in removed; it undoes by inserting removed back at pos. A delete command is therefore not fully defined until it has executed once, which is fine because commands are always executed before they reach the undo stack. Both commands are tiny dataclasses. Their correctness rests on one assumption: undo is applied to exactly the document the command left behind. The stack discipline guarantees that, since only the most recent command can be undone.

5 · Stage three: the two stacks and their rules

The editor's private _run(cmd, cursor_after) executes a command, pushes a Step with the cursor before and after, trims the history to max_history by dropping the oldest step, clears the redo stack, and moves the cursor. undo() pops a step, calls cmd.undo, pushes the step on the redo stack and restores cursor_before. redo() pops from redo, calls cmd.execute again, pushes back on undo and sets cursor_after. Re-executing a delete recaptures the removed text, which is the same text because the document is in the same state as the first time.

Why does redo re-execute the command rather than restore a stored result? Because the command already contains everything needed, and re-executing keeps one code path for "apply this edit", which is tested every time the user edits. It also keeps the delete's captured text honest: when redo runs, the delete records the removed text again from the current document, which matches because the stack discipline guarantees the document is in the same state it was in the first time. If it ever did not match, the round-trip test would catch it immediately.

6 · Stage four: coalescing typing

Typing "hello world" one key at a time would push eleven commands. Instead, type asks _run to merge when possible: if the top of the undo stack is an insert, the new insert starts exactly where that one ended, no other action intervened, and the new text does not begin with a space or newline, the new characters are appended to the existing command's text and its cursor_after is updated, with no new step. Anything else (moving the cursor, deleting, undoing) sets a flag that prevents the next keystroke from merging. The result is undo by words: "hello world" becomes two steps, "hello" and " world", which the test checks. Real editors also break the run after a pause of a second or so; the solution leaves time out to stay deterministic, but it is a one-line extension with an injected clock.

7 · Stage five: composite commands and replace-all

Replace-all finds every match, then builds a delete and an insert for each. Two details matter. The commands are created from the last match to the first, so each edit only changes text after the positions still to be processed; working front to back, the first replacement of "cat" with "tiger" would shift every later match by two characters and the stored positions would be wrong. And the whole list is wrapped in a Composite, which executes its parts in order and undoes them in reverse order, so it is one undo step. The test replaces three occurrences of "cat" with "dog", undoes once to restore all three, and redoes once to reapply them. The same composite serves paste-over-selection (a delete plus an insert) and automatic formatting.

8 · Stage six: the piece table

The document is a PieceTable. Construction stores the original text without copying and creates one piece covering it. To insert at position p, the table finds the piece containing p and the offset inside it, appends the new text to the add buffer, and either places a new piece before or after that piece or splits it into left, new and right pieces. As an optimisation, typing that continues at the end of the most recent add-buffer piece just extends that piece, so typing a paragraph creates one piece, not hundreds. To delete a range, it walks the pieces, keeps those outside the range, trims those that overlap it, and collects the removed text so the delete command can store it. The text of the document is the concatenation of each piece's slice of its buffer.

The solution keeps pieces in a Python list, so locating a position is O(number of pieces). That is fine for an interview and for documents edited lightly; production editors keep pieces in a balanced tree whose nodes cache the total length (and line-break count) of their subtrees, so finding a position or a line number is O(log pieces). VS Code calls its version a piece tree: a piece table kept in a red-black tree, optimised for line lookups.

What goes into a command

A command should contain exactly what is needed to apply and reverse it, and nothing that can go stale. Positions and text, yes; references to the document object, no, because the command is applied to whatever document the editor passes in, which keeps commands reusable for replay on another copy or over the network. Cursor positions belong in the history step, not the command, because the same command can be part of different user gestures. Derived data such as line numbers should not be stored, because they change as other edits happen. Keeping commands minimal and pure also makes them easy to serialise for persistent undo or crash recovery: a command is a small record of plain values.

9 · A trace of the drill

0startHello world[][]
1delete 6 characters at 5Hello[Del(5, " world")][]
2type " there" at 5 (six keys, one coalesced step)Hello there[Del, Ins(5, " there")][]
3undoHello[Del][Ins]
4undoHello world[][Ins, Del]
5type "!" at 11Hello world![Ins(11, "!")][] (cleared)

Step 2's six keystrokes coalesce: the first, a space, starts a new step (a space breaks a run, but it can begin one), and "t", "h", "e", "r", "e" each continue exactly where the previous insert ended. After step 3 the cursor is back at 5, the position before the typing. Step 6 does nothing: the redo entries described edits to "Hello world" and were discarded at step 5. Re-applying Ins(5, " there") to "Hello world!" would give "Hello there world!", a document the user never had.

10 · Testing undo systems

The most powerful test is a round-trip property. The solution's random test performs 400 random actions (moving and typing, backspacing, replace-all with random strings including the empty string), then undoes until nothing is left, checking the document equals the original exactly, then redoes until nothing is left, checking it equals the final text exactly. Any command that fails to restore precisely what it changed, any wrong ordering inside a composite, any cursor-dependent mistake, breaks one of those two equalities. The piece table gets its own property test against a plain Python string as the reference: 3,000 random inserts and deletes, comparing length after every operation, every deleted substring, and the final text, plus a check that the original buffer was never copied. Named tests then pin the behaviours users notice: the drill's sequence, word-level coalescing, replace-all as one step, and the history limit.

11 · Talking through the design

"Every edit is a command with execute and undo. Delete records what it removed. The editor has two stacks: a new edit pushes and clears redo, undo moves a command to redo and reverses it, redo moves it back. Typing coalesces into word-sized steps; replace-all is a composite applied back to front so positions stay valid, and undone in reverse. Each step records the cursor before and after. History is bounded. The document is a piece table: the original text is never copied, typed text goes to an append-only buffer, and the document is a list of pieces, which in production becomes a balanced tree, as VS Code did when its array of lines ran out of memory on a 35 MB file. I test with a round trip: random edits, undo everything back to the original, redo everything back to the final text."

12 · The full solution

The file below contains the piece table, the three commands, the editor and six tests. Python 3.12, standard library only.

"""Text editor core: a piece table for the document, edits as Command objects with undo/redo
stacks, typing coalesced into one undo step, composite commands for multi-edit operations,
cursor restoration and a bounded history. Python 3.12, standard library only.
Run: python editor.py"""
from __future__ import annotations

import random
from dataclasses import dataclass, field
from typing import Protocol


# ------------------------------------------------------------------ piece table
@dataclass
class Piece:
    buf: str           # "orig" or "add"
    start: int
    length: int


class PieceTable:
    """The original text is never copied or modified; inserted text is appended to an add
    buffer; the document is a list of pieces pointing into the two buffers."""

    def __init__(self, text: str = "") -> None:
        self.orig, self.add = text, []                # add buffer as a list of chunks
        self._add_len = 0
        self.pieces: list[Piece] = [Piece("orig", 0, len(text))] if text else []
        self.length = len(text)

    def _buf(self, p: Piece) -> str:
        return self.orig if p.buf == "orig" else self._add_text()

    def _add_text(self) -> str:
        if len(self.add) > 1:                         # join lazily, keep one string
            self.add = ["".join(self.add)]
        return self.add[0] if self.add else ""

    def _locate(self, pos: int) -> tuple[int, int]:
        """(piece index, offset inside it) for document position pos."""
        for i, p in enumerate(self.pieces):
            if pos <= p.length:
                return i, pos
            pos -= p.length
        return len(self.pieces), 0

    def insert(self, pos: int, text: str) -> None:
        if not 0 <= pos <= self.length:
            raise IndexError(pos)
        if not text:
            return
        new = Piece("add", self._add_len, len(text))
        self.add.append(text)
        self._add_len += len(text)
        i, off = self._locate(pos)
        if i < len(self.pieces):
            p = self.pieces[i]
            if off == 0:
                self.pieces.insert(i, new)
            elif off == p.length:
                # extend the previous add-piece in place when typing continues at its end
                if p.buf == "add" and p.start + p.length == new.start:
                    p.length += new.length
                else:
                    self.pieces.insert(i + 1, new)
            else:
                left, right = Piece(p.buf, p.start, off), Piece(p.buf, p.start + off, p.length - off)
                self.pieces[i:i + 1] = [left, new, right]
        else:
            last = self.pieces[-1] if self.pieces else None
            if last and last.buf == "add" and last.start + last.length == new.start:
                last.length += new.length
            else:
                self.pieces.append(new)
        self.length += len(text)

    def delete(self, pos: int, n: int) -> str:
        if n < 0 or pos < 0 or pos + n > self.length:
            raise IndexError((pos, n))
        removed, out, cur = [], [], 0
        for p in self.pieces:
            a, b = cur, cur + p.length                # piece covers [a, b)
            cur = b
            lo, hi = max(a, pos), min(b, pos + n)
            if lo >= hi:
                out.append(p)
                continue
            s = self._buf(p)
            removed.append(s[p.start + lo - a: p.start + hi - a])
            if lo > a:
                out.append(Piece(p.buf, p.start, lo - a))
            if hi < b:
                out.append(Piece(p.buf, p.start + hi - a, b - hi))
        self.pieces = out
        self.length -= n
        return "".join(removed)

    def text(self) -> str:
        return "".join(self._buf(p)[p.start:p.start + p.length] for p in self.pieces)


# ------------------------------------------------------------------ commands
class Command(Protocol):
    def execute(self, doc: PieceTable) -> None: ...
    def undo(self, doc: PieceTable) -> None: ...


@dataclass
class Insert:
    pos: int
    text: str

    def execute(self, doc: PieceTable) -> None:
        doc.insert(self.pos, self.text)

    def undo(self, doc: PieceTable) -> None:
        doc.delete(self.pos, len(self.text))


@dataclass
class Delete:
    pos: int
    length: int
    removed: str = ""                                 # captured when executed

    def execute(self, doc: PieceTable) -> None:
        self.removed = doc.delete(self.pos, self.length)

    def undo(self, doc: PieceTable) -> None:
        doc.insert(self.pos, self.removed)


@dataclass
class Composite:
    """Several edits as one undo step (replace-all, paste-over-selection, auto-format)."""
    parts: list = field(default_factory=list)

    def execute(self, doc: PieceTable) -> None:
        for c in self.parts:
            c.execute(doc)

    def undo(self, doc: PieceTable) -> None:
        for c in reversed(self.parts):                # undo in reverse order
            c.undo(doc)


# ------------------------------------------------------------------ editor
@dataclass
class Step:
    cmd: object
    cursor_before: int
    cursor_after: int


class Editor:
    def __init__(self, text: str = "", max_history: int = 1_000) -> None:
        self.doc = PieceTable(text)
        self.cursor = 0
        self.undo_stack: list[Step] = []
        self.redo_stack: list[Step] = []
        self.max_history = max_history
        self._coalesce = True                         # broken by cursor moves, deletes, undo

    def _run(self, cmd, cursor_after: int, merge_ok: bool = False) -> None:
        before = self.cursor
        if (merge_ok and self._coalesce and self.undo_stack
                and isinstance(self.undo_stack[-1].cmd, Insert) and isinstance(cmd, Insert)):
            top = self.undo_stack[-1]
            if top.cmd.pos + len(top.cmd.text) == cmd.pos and not cmd.text.startswith((" ", "\n")):
                cmd.execute(self.doc)
                top.cmd.text += cmd.text
                top.cursor_after = cursor_after
                self.cursor = cursor_after
                self.redo_stack.clear()
                return
        cmd.execute(self.doc)
        self.undo_stack.append(Step(cmd, before, cursor_after))
        if len(self.undo_stack) > self.max_history:
            self.undo_stack.pop(0)                    # forget the oldest step
        self.redo_stack.clear()                       # a new edit ends the redo branch
        self.cursor = cursor_after
        self._coalesce = True

    # user actions
    def move(self, pos: int) -> None:
        self.cursor = max(0, min(pos, self.doc.length))
        self._coalesce = False

    def type(self, text: str) -> None:
        self._run(Insert(self.cursor, text), self.cursor + len(text), merge_ok=True)

    def backspace(self, n: int = 1) -> None:
        n = min(n, self.cursor)
        if n:
            self._run(Delete(self.cursor - n, n), self.cursor - n)
            self._coalesce = False

    def delete_range(self, pos: int, n: int) -> None:
        self._run(Delete(pos, n), pos)
        self._coalesce = False

    def replace_all(self, old: str, new: str) -> int:
        text = self.doc.text()
        hits, i = [], text.find(old)
        while i != -1 and old:
            hits.append(i)
            i = text.find(old, i + len(old))
        if not hits:
            return 0
        parts = []
        for pos in reversed(hits):                    # back to front: earlier offsets stay valid
            parts += [Delete(pos, len(old)), Insert(pos, new)]
        self._run(Composite(parts), min(self.cursor, len(text) + len(hits) * (len(new) - len(old))))
        self._coalesce = False
        return len(hits)

    def undo(self) -> bool:
        if not self.undo_stack:
            return False
        step = self.undo_stack.pop()
        step.cmd.undo(self.doc)
        self.redo_stack.append(step)
        self.cursor = step.cursor_before
        self._coalesce = False
        return True

    def redo(self) -> bool:
        if not self.redo_stack:
            return False
        step = self.redo_stack.pop()
        step.cmd.execute(self.doc)
        self.undo_stack.append(step)
        self.cursor = step.cursor_after
        self._coalesce = False
        return True

    @property
    def text(self) -> str:
        return self.doc.text()


# ---------------------------------------------------------------- tests
def test_piece_table_matches_string_reference() -> None:
    rng = random.Random(5)
    original = "The quick brown fox jumps over the lazy dog. " * 20
    pt, ref = PieceTable(original), original
    for _ in range(3_000):
        if rng.random() < 0.6 or not ref:
            pos = rng.randrange(len(ref) + 1)
            s = rng.choice(["a", "XY", "hello ", "\n", "zz"])
            pt.insert(pos, s)
            ref = ref[:pos] + s + ref[pos:]
        else:
            pos = rng.randrange(len(ref))
            n = rng.randrange(1, min(8, len(ref) - pos) + 1)
            got = pt.delete(pos, n)
            assert got == ref[pos:pos + n]
            ref = ref[:pos] + ref[pos + n:]
        assert pt.length == len(ref)
    assert pt.text() == ref and pt.orig is original               # original never copied


def test_drill_trace() -> None:
    e = Editor("Hello world")
    e.delete_range(5, 6)                                          # remove " world"
    assert e.text == "Hello"
    e.move(5)
    for ch in " there":
        e.type(ch)
    assert e.text == "Hello there" and len(e.undo_stack) == 2     # six keystrokes, one step
    e.undo()
    assert e.text == "Hello" and e.cursor == 5
    e.undo()
    assert e.text == "Hello world" and len(e.redo_stack) == 2
    e.move(11)
    e.type("!")
    assert e.redo_stack == [] and e.redo() is False and e.text == "Hello world!"


def test_typing_coalesces_into_words() -> None:
    e = Editor()
    for ch in "hello world":
        e.type(ch)
    assert len(e.undo_stack) == 2                                 # "hello", " world"
    e.undo()
    assert e.text == "hello" and e.cursor == 5
    e.move(0)
    e.type("X")                                                   # cursor moved: new step
    assert len(e.undo_stack) == 2 and e.text == "Xhello"


def test_replace_all_is_one_undo_step() -> None:
    e = Editor("a cat sat on a cat mat with a cat")
    assert e.replace_all("cat", "dog") == 3
    assert e.text == "a dog sat on a dog mat with a dog"
    e.undo()
    assert e.text == "a cat sat on a cat mat with a cat"
    e.redo()
    assert e.text.count("dog") == 3


def test_undo_redo_round_trip_random() -> None:
    rng = random.Random(9)
    e = Editor("seed text")
    history = [e.text]
    for _ in range(400):
        r = rng.random()
        if r < 0.5:
            e.move(rng.randrange(len(e.text) + 1))
            e.type(rng.choice(["a", "bc", " d", "\n"]))
        elif r < 0.8 and e.cursor > 0:
            e.backspace(rng.randint(1, 3))
        else:
            e.replace_all(rng.choice(["a", "b"]), rng.choice(["Q", "RR", ""]))
        history.append(e.text)
    final = e.text
    while e.undo():
        pass
    assert e.text == "seed text"
    while e.redo():
        pass
    assert e.text == final


def test_history_is_bounded() -> None:
    e = Editor(max_history=10)
    for i in range(50):
        e.move(e.doc.length)
        e.type(f" w{i}")
    assert len(e.undo_stack) == 10
    while e.undo():
        pass
    assert e.text.startswith(" w0") and e.text.count(" w") == 40  # only the last 10 undone


if __name__ == "__main__":
    for t in (test_piece_table_matches_string_reference, test_drill_trace, test_typing_coalesces_into_words,
              test_replace_all_is_one_undo_step, test_undo_redo_round_trip_random, test_history_is_bounded):
        t()
        print("ok ", t.__name__)

13 · Edge cases

Undo or redo with an empty stack: return false, change nothing. Backspace at position 0: nothing to delete, no step recorded. Replace-all with no matches: no step recorded, so undo does not consume an empty action. Replace-all where the replacement contains the search text ("a" with "aa"): matches are found once on the original text, so the operation terminates. Empty search string: rejected or a no-op, never an infinite loop. History limit reached: the oldest steps are forgotten; undo stops at the oldest remaining one. Cursor beyond the end after an undo: clamp to the document length. Unicode: positions should count user-perceived characters consistently; Python strings index code points, which differs from what an editor shows for combined emoji or accents.

14 · Extensions the interviewer will ask for

Undo tree: keep the discarded redo branch as a sibling, so the user can navigate every state ever reached, as Vim's undo tree allows. Persistent undo: append commands to a sidecar file and rebuild the stacks on reopen if the file is unchanged. Selection-aware commands: record selection ranges as well as the cursor. Multiple cursors: one composite per keystroke, with edits applied back to front. Collaborative editing: undo becomes "invert my operation, transformed against everything since", using operational transformation or CRDTs. Large files: a piece tree with cached line counts, lazy loading, and avoiding a full-text materialisation for display.

15 · Complexity

Undo and redo cost one command's undo or execute. With the list-based piece table, insert and delete are O(pieces) to locate plus O(pieces) to rebuild the list on delete; with a balanced piece tree both are O(log pieces). Coalescing keeps the number of steps and pieces proportional to editing actions, not keystrokes. Memory: the original text once, the add buffer (everything typed, never shrinking), the piece list, and the history, which holds positions and only the deleted text. Materialising the full text is O(document size) and should be avoided on every keystroke in a real editor; renderers ask the buffer only for the visible lines, which a piece tree with cached line counts answers in logarithmic time.

Why a piece table, and why VS Code built a tree

The VS Code team's 2018 write-up explains the trade-off precisely. Their original buffer was an array of lines: simple, fast to look up by line number, and fine for typical files. But each line was an object of about 40 to 60 bytes, so a 35 MB file with 13.7 million lines used around 600 MB, about twenty times the file size, and building the array meant splitting the whole file into line strings, which slowed opening. A piece table stores just the text plus a few pieces, so memory is close to the file size. Its weakness is lookup by line number, which an editor does constantly (rendering, diagnostics, go to line). VS Code solved it by keeping pieces in a red-black tree whose nodes store the length and line-break count of their left subtree, so both "which piece holds offset X" and "which piece holds line N" are logarithmic. They called it a piece tree and shipped it in version 1.21 in March 2018. The post also describes engineering details that matter at scale, such as avoiding concatenating file chunks into one giant string.

Gap buffers and ropes

Two other structures are worth knowing. A gap buffer is one array with an empty gap at the cursor; typing fills the gap in O(1), and moving the cursor moves text across the gap, cheap for small moves and expensive for jumps across a large file. It is simple and well suited to one cursor; Emacs uses it. A rope is a balanced tree of string fragments: insert and delete anywhere are O(log n), concatenation is cheap, and fragments can be shared between versions, which suits very large documents and persistent (versioned) data. A piece table, especially as a tree, combines the rope's logarithmic edits with the property that original text never moves.

Undo as inverse operations versus restored states

The command approach stores inverse operations. An alternative, natural with immutable structures, stores versions: because piece tables never change their buffers, an earlier document version is fully described by an earlier piece list, so "undo" can restore that list. Persistent tree structures share unchanged subtrees between versions, making each version cost O(log n) memory. Both approaches are valid; commands are lighter and say what happened (useful for coalescing and collaboration), versions are simpler to make correct. Many editors mix them: commands for history, periodic checkpoints for fast navigation.

Grouping rules shape the user experience

What counts as one undo step is a product decision with surprising impact. Too fine (per keystroke) and undo is tedious; too coarse (per editing session) and undo throws away work the user wanted to keep. Common rules break a typing run at whitespace and punctuation, at cursor movement or selection changes, at a change of operation type (typing then deleting), after a pause, and around commands such as paste or replace-all that form their own step. Some editors let extensions open an explicit transaction so a multi-step automated change, such as a refactoring, becomes one undoable unit; that is exactly the composite command.

Selections and multiple cursors

Real editors restore not only the cursor but the selection, and many support several cursors at once. Both fit the command design with small extensions. A step records the selection ranges before and after, not just one position. Typing with five cursors produces five inserts per keystroke, wrapped in one composite and applied from the last cursor to the first, exactly like replace-all, so earlier insertions do not shift the positions of later ones. Coalescing then works per composite: five parallel runs of typing become one undo step. The pattern generalises: any operation that touches many positions is a composite applied back to front.

The add buffer only grows

A piece table never removes text from its add buffer, even when the user deletes what they typed, because undo may need it again and pieces may still point at it. Over a long session the add buffer accumulates every character ever typed or pasted. For normal editing that is small, a few megabytes even for heavy days, but a session that repeatedly pastes large blocks can grow it substantially. Editors handle this by compacting on save (write the current document as the new original and start a fresh add buffer, discarding history or keeping it as commands against the new original), or by bounding history so that unreachable text can be released.

Undo in collaborative editors

With several people editing, a global undo stack is wrong: pressing undo should revert my last edit, not my colleague's, and my edit's position may have moved because of theirs. Collaborative editors treat undo as generating a new operation: the inverse of my earlier operation, transformed against all operations that happened since, using operational transformation, or expressed directly in a CRDT's operations. That is considerably harder than single-user undo and a good place to show judgement: name the problem, explain why the simple stack fails, and point to the established techniques.

How editors fail

The visible failures are about trust. Undo that does not restore exactly the previous text, even once, makes users afraid to use it; the round-trip property test is the defence. Undo that removes too much (a whole paste plus the typing before it) or too little (one character) annoys users daily and is tuned through grouping rules. Cursors that jump to the wrong place after undo are a common complaint, fixed by recording cursor and selection with each step.

The invisible failures are about resources. History that grows without limit during a long session, especially with large pastes or replace-alls on big files, can exhaust memory; bounded history and storing only deltas address it. Buffers that copy text on every edit make typing lag on large files. And opening very large files can fail outright, as VS Code's line array did, when the representation's per-line or per-character overhead multiplies the file size.

Autosave and crash recovery

Users expect not to lose work when an editor crashes. The command log is the natural recovery mechanism: append each command (or each coalesced step) to a journal file as it happens, and on restart, if the journal is newer than the saved file, replay it onto the original. Because commands are small, journalling costs little I/O. The same journal can provide persistent undo across sessions. The subtle part is consistency: the journal must be tied to a specific version of the file (by size, timestamp or hash), or replaying it onto a file changed by another program corrupts the text.

Large-file mode

Even with a piece table, some features scale with document size: syntax highlighting, search indexes, minimaps, word wrap. Editors detect very large files and switch them off or make them lazy, processing only the visible region. The text buffer's job is to make that possible by answering "give me lines 1,000,000 to 1,000,050" quickly without materialising the whole text, which is what VS Code's piece tree with cached line-break counts provides.

What to measure

Keystroke-to-render latency (typing must feel instant, so a few milliseconds is the budget), memory per megabyte of document, time to open large files, history memory, and crash reports involving large files. Editors also collect anonymous counts of undo and redo usage to tune grouping: many presses of undo in a row suggest steps are too small, and frequent redo right after undo suggests they are too large.

Knobs

Each of these has a sensible default that most users never change, and an escape hatch for the few who edit unusually large files or work in unusually long sessions. History depth or byte budget, the coalescing rules and pause threshold, checkpoint frequency for long histories, and thresholds at which the editor switches to a large-file mode (disabling expensive features such as full syntax analysis).

The real case: VS Code's text buffer reimplementation

In March 2018 the VS Code team published how and why they replaced the text buffer behind the editor. The original implementation, unchanged since the Monaco project began, used an array of lines: typing modified a line in place, and inserting a line spliced a new object into the array. It worked for typical documents, but reports of out-of-memory crashes kept arriving; one user could not open a 35 MB file because it had 13.7 million lines, each stored as an object of roughly 40 to 60 bytes, so the array took about 600 MB, around twenty times the file. Splitting the file into line strings also made opening slow. After reviewing data structures that need less metadata, they chose the piece table (original buffer, added buffer, list of nodes) and, to keep line lookups fast, organised the pieces in a red-black tree with each node caching its left subtree's length and line-break count, which they nicknamed the piece tree. It shipped in VS Code 1.21. For this interview problem the case shows two things: the document representation is a real design decision with measured consequences, and the piece table, introduced here as the store under undo, is what a widely used editor actually runs.

Goal: run the editor, then break, measure and extend it. Python 3.12, standard library only.

  1. Save the full solution as editor.py and run it. Six tests print ok, including the round-trip property over 400 random actions.
  2. Break it. Build replace-all's commands from the first match to the last instead of last to first. The replace-all test or the round-trip test fails, because earlier replacements shift later positions.
  3. Break it again. Remove self.redo_stack.clear() from _run. Replay the drill and redo after typing "!": the document becomes text the user never had.
  4. Measure it. Load a 10 MB string, then time 10,000 single-character inserts at random positions with a plain string (s = s[:i] + c + s[i:]) and with the piece table. Then do the same inserts all at the end, and count pieces in each case.
  5. Extend it. Add a pause-based coalescing rule: inject a clock and break a typing run if more than one second passed since the last keystroke.
  6. Extend it again. Turn the redo branch into an undo tree: when a new edit happens with a non-empty redo stack, keep that stack as a sibling branch, and add a command to switch branches.

After every change, the round-trip test must still pass: undo everything gives the original, redo everything gives the final text. If a change makes it fail only occasionally, print the random seed and the failing action sequence, then shrink the sequence by hand until the bug is obvious; that is how undo bugs are usually found.

Work it out

A document contains Hello world. The user performs: (1) delete the 6 characters starting at position 5 (" world"), (2) type " there" at position 5, (3) undo, (4) undo, (5) type "!" at the end, (6) redo.

(a) Trace the document and both stacks after each step. (b) What does the redo in step 6 do, and why? (c) What memory does the history hold, compared with snapshots?

Answer

(a) The trace. U is the undo stack, R the redo stack, top last.

StepDocumentUR
startHello world[][]
1 · deleteHello[Del(5, " world")][]

Step 2 does not merge with step 1: coalescing joins consecutive inserts, and a delete followed by an insert are different operations. Within step 2 the six keystrokes do coalesce into one Ins(5, " there"), because each continues where the previous ended. The full solution's test replays this sequence exactly.

(b) The redo does nothing, because step 5 cleared the redo stack. That is correct: after two undos, the two redo entries described edits to Hello world. Typing "!" created a new future from that state. Re-applying Ins(5, " there") to Hello world! would give Hello there world!, which the user never had and would not expect. Keeping the old branch is possible, as an undo tree, but it is a separate feature with its own interface.

(c) Memory. The history holds one small command: an insert of one character at position 11, a few dozen bytes. Before step 5 it held a delete with its six removed characters and an insert with six characters. Snapshots would have stored the whole document per step: tiny here, but for a 10 MB file every keystroke would cost 10 MB, and a thousand edits 10 GB. Commands store only what changed, which is why every real editor uses them, sometimes with an occasional snapshot as a checkpoint.
