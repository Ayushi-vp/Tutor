A service ingests events from a message stream on one thread and writes them to a database on four worker threads. Someone connects them with a plain Python list and a lock: the reader appends, the workers pop. When the database slows down, the list grows to millions of events and the process runs out of memory. Someone adds a size check and a time.sleep(0.01) loop for when the list is full or empty: memory is fine now, but idle workers burn CPU polling, every handoff waits up to ten milliseconds, and once in a while a worker crashes with "pop from empty list" even though it had just checked the list was not empty.

The structure they needed is a bounded blocking queue: producers call put, which waits while the queue is full; consumers call get, which waits while it is empty; and waiting means sleeping until another thread changes the state, not polling. It is the most widely used concurrency building block there is, behind thread pools, logging pipelines, web servers' request queues, batchers and data loaders, and Python ships one as queue.Queue.

Implementing it is a standard machine-coding question because it is small enough to write in twenty minutes and subtle enough that most first attempts are wrong in ways that pass simple tests. The tools are a lock and condition variables. The traps are two classic bugs: checking the condition with if instead of while, and using one condition variable for both producers and consumers with notify(). The first crashes consumers occasionally; the second freezes every thread occasionally. Both depend on the exact order in which threads happen to run, which is why the interviewer will ask you to trace an interleaving step by step.

It is also the cleanest place to learn to reason about interleavings. Two threads and three lines each already allow dozens of orders; the habit of asking "what if the other thread runs right here?" at every line is what the rest of this family of cases builds on.

This lesson's solution follows the same design as CPython's own queue.Queue: one mutex shared by two conditions, waits in loops, deadline arithmetic for timeouts. It also runs both broken versions under a stress test that switches threads as often as possible, and both fail on every run: the first with IndexError, the second with all eight threads asleep.

The lesson follows the round: clarify the requirements, name the pieces, draw the structure, write the naive version and trace its failures, then build the correct queue in stages (mutual exclusion, waiting with condition variables, the while loop, two conditions and notify, timeouts, close for shutdown), trace the two bad interleavings line by line and show why the fixes work, stress-test it, and cover fairness, edge cases, extensions such as priorities and asyncio, complexity, and the CPython source.

Producers, consumers and a buffer between them

The producer-consumer pattern connects threads that create work (producers) to threads that process it (consumers) through a queue. The queue decouples them: producers do not wait for a particular consumer, and consumers do not need to know where work came from. A bounded queue has a capacity. When it is full, producers must wait, which slows them to the consumers' pace; this is backpressure, and it is what keeps memory and latency bounded when consumers fall behind. When the queue is empty, consumers must wait until something arrives.

Waiting without polling: condition variables

"Wait until the queue is not empty" could be written as a loop that checks, sleeps briefly, and checks again. That wastes CPU when idle and adds latency to every handoff. A condition variable does better. It is attached to a lock, and offers three operations. wait(): atomically release the lock and go to sleep; when woken, reacquire the lock before returning. notify(): wake one waiting thread. notify_all(): wake every waiting thread. The atomic release-and-sleep is essential: if a thread released the lock and then went to sleep as two separate steps, a notify arriving between them would be lost and the thread could sleep forever.

The pattern for using one is always the same. Take the lock. While the thing you need is not true, wait. Do your work. Notify any thread whose condition you may have made true. Release the lock. The thing you need is called the predicate: "the queue has an item", "the queue has a free slot".

Where blocking queues appear

Once you can recognise the pattern, it is everywhere. A thread pool is a blocking queue of tasks with worker threads as consumers. A web server's accept loop hands connections to handler threads through one. Logging frameworks put records on one for a background writer. Data loaders for model training fill one with batches while the GPU consumes them, so the GPU never waits for disk. Pipelines of stages (download, parse, enrich, store) connect each pair of stages with one, so a slow stage applies backpressure upstream instead of being flooded. In every case the queue's bound is a deliberate choice about how much work may be in flight.

The analogy, and where it breaks

Think of a sushi conveyor with space for four plates between a chef and the diners. If the conveyor is full, the chef waits in a "waiting for space" area; if it is empty, diners wait in a "waiting for food" area. When a diner takes a plate, they tap one chef on the shoulder; when the chef adds a plate, they tap one diner. Two separate waiting areas mean a tap always reaches someone who can act on it. The analogy breaks on timing: a tapped person does not act instantly. Before they reach the conveyor, someone who was not waiting at all may walk up and take the plate, which is exactly why a woken thread must look again before acting.

1 · Clarify the requirements

Ask how many producers and consumers there are, whether the queue must be bounded and at what capacity, whether put and get should block, fail immediately, or wait with a timeout, what order items come out in (FIFO, priority), whether fairness among waiting threads matters, how the queue is shut down and what happens to queued items then, and whether it is used from threads, processes or asyncio tasks.

A typical agreed scope: many producers and many consumers in one process using threads; FIFO; fixed capacity; blocking put and get with optional timeouts raising Full or Empty; a close that rejects new puts and lets consumers drain remaining items before get starts raising Closed. Invariants: the number of items is always between zero and the capacity; every item put is returned by exactly one get; no thread waits while the operation it is waiting for is possible and no other thread is going to wake it.

2 · The pieces

The state is a deque of items, a capacity, and a closed flag. A single Lock protects all three. Two Condition objects are created on that same lock: not_full, where producers wait, and not_empty, where consumers wait. Because both conditions share one lock, holding either condition means holding the lock, and the state can be checked and changed consistently. CPython's queue.Queue has exactly this structure (plus a third condition, all_tasks_done, for its join feature).

3 · Stage one: a naive queue and the polling trap

class PollingQueue:
    def __init__(self, cap):
        self.cap, self.items, self.lock = cap, [], threading.Lock()

    def put(self, x):
        while True:
            with self.lock:
                if len(self.items) < self.cap:
                    self.items.append(x)
                    return
            time.sleep(0.001)            # full: poll again soon

    def get(self):
        while True:
            with self.lock:
                if self.items:
                    return self.items.pop(0)
            time.sleep(0.001)

This one is correct, because each check and its action happen under the lock, but it is poor engineering. Idle consumers wake a thousand times a second each to find nothing; every handoff waits up to the polling interval; list.pop(0) is O(n). The tempting "optimisation" is to move the check outside the lock, or to sleep less, and the first breaks correctness while the second burns more CPU. Condition variables replace the polling with sleeping until something actually changes.

4 · Stage two: condition variables, and the while loop

The correct get takes the lock through the condition (with self._not_empty:), then waits while the queue is empty, then pops, then notifies a producer:

def get(self):
    with self._not_empty:                      # holds the shared lock
        while not self._items:                 # re-check after every wakeup
            self._not_empty.wait()             # release lock, sleep, reacquire
        item = self._items.popleft()
        self._not_full.notify()                # one slot freed: wake one producer
        return item

The while is not style; it is correctness. When wait() returns, the thread has been notified and has reacquired the lock, but those are two separate moments. Between them, any other thread may have acquired the lock and changed the queue. Python's documentation for condition objects states this directly: the while loop checking the condition is necessary because wait() can return after an arbitrarily long time, and the condition that prompted the notify may no longer hold. Some threading systems also allow spurious wakeups, returns from wait with no notify at all, which the loop handles for free. The solution uses wait_for(predicate, timeout), which is the same loop written by the standard library.

5 · The bad interleaving: if instead of while

Replace while with if and run two consumers, C1 and C2, and one producer P against an empty queue. Here is one interleaving, line by line.

StepC1PC2Queue
1acquires lock; if not items: true[]
2wait(): releases lock, sleeps[]
3acquires lock; appends x[x]
4woken, now waiting to reacquire the locknot_empty.notify()[x]
5releases lock(just arrived) acquires lock first[x]
6if not items: false; pops x; releases[]
7reacquires lock; skips the check (it was an if)[]
8popleft() on empty deque: IndexError[]

Step 5 is called barging: C2 was not waiting, so it competed for the lock on equal terms with the just-woken C1 and won. Nothing about this is exotic; it is simply one of the legal orders. With while, step 7 re-checks, finds the queue empty, and waits again; C1 gets the next item instead. The solution's IfNotWhileQueue contains exactly this bug, and under a stress test with four producers, four consumers and the interpreter's thread switch interval set as small as possible, every one of three runs ended with consumers raising IndexError.

6 · Stage three: two conditions, and the stall with one

Why two condition variables? Consider the tempting simplification: one condition for everyone, with notify() after every put and get. Capacity 1, producers P1 and P2, consumers C1 and C2. Trace one interleaving:

StepEventQueueWaiting on the one condition
1C1 and C2 call get: empty, both wait[]C1, C2
2P1 puts a; notify wakes C1[a]C2
3P1 puts b: full, waits; P2 puts c: full, waits[a]C2, P1, P2
4C1 gets a; notify wakes the longest waiter, C2[]P1, P2
5C1 calls get again: empty, waits[]P1, P2, C1
6C2 runs: empty, waits again (its notify was wasted)[]P1, P2, C1, C2

All four threads are waiting. The queue is empty and two producers have items ready, but every thread is asleep and nobody will ever call notify again. The wakeup at step 4 went to a thread of the wrong kind. This is a lost wakeup: a notification consumed by a thread that cannot use it. With two conditions, step 4's notify would go to not_full, where only producers wait, so it would have woken P1. The solution's OneConditionQueue has this bug, and under stress all eight threads were stuck in every run. The alternative fix, notify_all() on the single condition, is correct (everyone wakes and re-checks in a while loop) but wakes every waiter on every operation, which wastes work as thread counts grow.

Why not check the size first?

A common shortcut is if q.qsize() < capacity: q.put(x) outside any lock, to avoid blocking. It is a check-then-act race: between the check and the put, other producers can fill the queue, so the put blocks anyway, or, in a hand-written queue without internal checks, overfills it. The standard library's documentation warns that qsize() > 0 does not guarantee that a following get() will not block, nor does qsize() < maxsize guarantee that put() will not block. The correct non-blocking operation is a single atomic attempt, put_nowait or a zero timeout, which checks and acts under the lock.

7 · Stage four: put, get and notify, correctly

The correct put mirrors get: take the lock through not_full, wait while the queue is full (or until closed), append, then not_empty.notify(). Each put creates exactly one item, so it can enable exactly one get; waking one consumer is enough, and because consumers re-check, waking one that loses the race is harmless (someone else got the item, and that someone will notify in turn when needed). Each get frees exactly one slot and wakes one producer. The notify happens while holding the lock, which is required by Python and harmless: the woken thread cannot proceed until the notifier releases the lock at the end of its with block.

Order inside the critical section does not matter for correctness, but clarity does: change the state first, then notify, as the solution does. Because the notifier still holds the lock, the woken thread cannot observe the state until the notifier leaves its with block, so "notify then append" would also be correct, merely confusing to read. What must never happen is changing the state without holding the lock, or notifying a condition that is not built on the lock that protects the state.

8 · Stage five: timeouts

A timeout means "wait at most this long for the predicate". Waiting once with the timeout is wrong, because the thread may be woken early by a notify that another thread wins, and then it should wait again for the remaining time, not the full timeout again. CPython's Queue.put computes an end time and, in its while loop, waits for endtime - now, raising Full when the remaining time reaches zero. Condition.wait_for(predicate, timeout) implements exactly that loop and returns the predicate's final value, which the solution uses: if it returns false, raise Full or Empty.

9 · Stage six: close and shutdown

Threads blocked in get must be released when the program shuts down, without losing queued work. close() takes the lock, sets closed, and calls notify_all() on both conditions, because now every waiter's situation has changed. The predicates include the flag: producers wait while "not closed and full", then raise Closed if closed; consumers wait while "empty and not closed", then, if items remain, keep taking them; only when the queue is empty and closed does get raise Closed. Consumers therefore drain everything that was accepted and then exit cleanly, which the test checks: a consumer blocked on an empty queue receives the one item, then Closed, and a later put is rejected. Python 3.13 added the same capability to the standard library as Queue.shutdown() with a ShutDown exception.

Choosing the capacity

Capacity is a design parameter, not a safety margin. Too small and producers block on every short burst even though consumers would catch up a moment later, so throughput drops. Too large and the queue hides a slow consumer until it holds minutes of work, so latency for every item grows and memory with it; in the extreme, a huge queue behaves like an unbounded one. Little's law gives the link: the average number of items waiting equals the arrival rate times the average wait, so a queue of 1,000 items fed at 100 items per second means each item waits about ten seconds. Start from the burst you want to absorb and the latency you can tolerate, and measure blocked-producer time to see whether the choice is right.

10 · The full solution

The file below contains the correct queue, the two broken variants, a stress harness and five tests. The stress tests set sys.setswitchinterval(1e-6) so the interpreter switches threads as often as possible, which makes races far more likely to show up. Python 3.12, standard library only; it takes about ten seconds, mostly the broken variants hitting their time limits.

"""Bounded blocking queue: one lock, two condition variables (not_full, not_empty), waits in
while loops, timeouts, and close() for shutdown. Plus the two classic broken versions, run
under stress so their failures are visible. Python 3.12, standard library only.
Run: python blocking_queue.py"""
from __future__ import annotations

import collections
import sys
import threading
import time
from typing import Generic, TypeVar

T = TypeVar("T")


class Full(Exception): ...
class Empty(Exception): ...
class Closed(Exception): ...


class BoundedQueue(Generic[T]):
    """Invariant (under the lock): 0 <= len(items) <= capacity.
    put waits while full; get waits while empty; every wait sits in a while loop."""

    def __init__(self, capacity: int) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self.capacity = capacity
        self._items: collections.deque[T] = collections.deque()
        self._lock = threading.Lock()
        self._not_full = threading.Condition(self._lock)     # producers wait here
        self._not_empty = threading.Condition(self._lock)    # consumers wait here
        self._closed = False

    def put(self, item: T, timeout: float | None = None) -> None:
        with self._not_full:
            if not self._not_full.wait_for(
                    lambda: self._closed or len(self._items) < self.capacity, timeout):
                raise Full(f"still full after {timeout}s")
            if self._closed:
                raise Closed("queue closed")
            self._items.append(item)
            self._not_empty.notify()                         # wake ONE consumer: one new item

    def get(self, timeout: float | None = None) -> T:
        with self._not_empty:
            if not self._not_empty.wait_for(lambda: self._items or self._closed, timeout):
                raise Empty(f"still empty after {timeout}s")
            if not self._items:                              # closed and drained
                raise Closed("queue closed and empty")
            item = self._items.popleft()
            self._not_full.notify()                          # wake ONE producer: one free slot
            return item

    def close(self) -> None:
        """No more puts; consumers drain what is left, then get() raises Closed."""
        with self._lock:
            self._closed = True
            self._not_full.notify_all()                      # everyone must re-check
            self._not_empty.notify_all()

    def qsize(self) -> int:
        with self._lock:
            return len(self._items)


# ------------------------------------------------------------------ two broken versions
class IfNotWhileQueue(BoundedQueue):
    """BUG: get() checks emptiness with `if`. A woken consumer can find the item already taken."""

    def get(self, timeout=None):
        with self._not_empty:
            if not self._items:
                self._not_empty.wait()
            item = self._items.popleft()                     # IndexError if someone barged in
            self._not_full.notify()
            return item


class OneConditionQueue(BoundedQueue):
    """BUG: producers and consumers share ONE condition and use notify(). A consumer's notify
    can wake another consumer instead of a producer; eventually everyone is waiting."""

    def __init__(self, capacity: int) -> None:
        super().__init__(capacity)
        self._cv = threading.Condition(self._lock)

    def put(self, item, timeout=None):
        with self._cv:
            while len(self._items) >= self.capacity:
                self._cv.wait()
            self._items.append(item)
            self._cv.notify()

    def get(self, timeout=None):
        with self._cv:
            while not self._items:
                self._cv.wait()
            item = self._items.popleft()
            self._cv.notify()
            return item


# ------------------------------------------------------------------ stress harness
def stress(q: BoundedQueue, producers: int, consumers: int, per_producer: int,
           limit: float = 3.0) -> dict:
    received: list = []
    errors: list[str] = []
    max_seen = [0]
    lock = threading.Lock()

    def produce(p: int) -> None:
        for k in range(per_producer):
            q.put((p, k))
            with lock:
                max_seen[0] = max(max_seen[0], len(q._items))   # racy peek, only for reporting

    def consume() -> None:
        try:
            while True:
                item = q.get()
                with lock:
                    received.append(item)
        except Closed:
            pass
        except Exception as e:                               # what the broken versions do
            with lock:
                errors.append(type(e).__name__)

    ps = [threading.Thread(target=produce, args=(p,), daemon=True) for p in range(producers)]
    cs = [threading.Thread(target=consume, daemon=True) for _ in range(consumers)]
    for t in ps + cs:
        t.start()
    deadline = time.time() + limit
    for t in ps:
        t.join(max(0.0, deadline - time.time()))
    stuck_producers = sum(t.is_alive() for t in ps)
    if not stuck_producers:
        q.close()                                            # let consumers drain and exit
    for t in cs:
        t.join(max(0.0, deadline - time.time()))
    return {"received": received, "errors": errors, "max": max_seen[0],
            "stuck": stuck_producers + sum(t.is_alive() for t in cs)}


# ---------------------------------------------------------------- tests
def test_correct_queue_under_stress() -> None:
    sys.setswitchinterval(1e-6)                              # switch threads as often as possible
    for cap in (1, 3, 64):
        q = BoundedQueue(cap)
        r = stress(q, producers=4, consumers=4, per_producer=2_000)
        assert r["stuck"] == 0 and not r["errors"]
        assert sorted(r["received"]) == sorted((p, k) for p in range(4) for k in range(2_000))
        assert r["max"] <= cap
    sys.setswitchinterval(0.005)


def test_if_not_while_breaks() -> None:
    sys.setswitchinterval(1e-6)
    failures = [stress(IfNotWhileQueue(2), 4, 4, 2_000, limit=2.0) for _ in range(3)]
    sys.setswitchinterval(0.005)
    bad = [r for r in failures if r["errors"] or r["stuck"]]
    print(f"    if-instead-of-while: {len(bad)}/3 runs failed; errors seen: "
          f"{sorted({e for r in failures for e in r['errors']})}")
    assert bad


def test_one_condition_with_notify_stalls() -> None:
    sys.setswitchinterval(1e-6)
    runs = [stress(OneConditionQueue(1), 4, 4, 2_000, limit=2.0) for _ in range(3)]
    sys.setswitchinterval(0.005)
    print(f"    one shared condition + notify(): threads stuck per run {[r['stuck'] for r in runs]}")
    assert any(r["stuck"] for r in runs)


def test_timeouts_and_close() -> None:
    q = BoundedQueue[int](1)
    t0 = time.perf_counter()
    try:
        q.get(timeout=0.05)
    except Empty:
        assert time.perf_counter() - t0 >= 0.04
    q.put(1)
    try:
        q.put(2, timeout=0.05)
    except Full:
        pass
    results: list = []

    def consumer() -> None:
        try:
            while True:
                results.append(q.get())
        except Closed:
            results.append("closed")
    th = threading.Thread(target=consumer)
    th.start()
    time.sleep(0.05)
    q.close()
    th.join(1)
    assert results == [1, "closed"] and not th.is_alive()
    try:
        q.put(3)
    except Closed:
        pass
    else:
        raise AssertionError("put after close accepted")


def test_blocked_producer_wakes_when_space_frees() -> None:
    q = BoundedQueue[str](1)
    q.put("a")
    done = threading.Event()

    def producer() -> None:
        q.put("b")                                           # blocks: queue is full
        done.set()
    th = threading.Thread(target=producer)
    th.start()
    assert not done.wait(0.1)                                # still blocked
    assert q.get() == "a"                                    # frees a slot, notifies not_full
    assert done.wait(1) and q.get() == "b"
    th.join()


if __name__ == "__main__":
    for t in (test_correct_queue_under_stress, test_if_not_while_breaks,
              test_one_condition_with_notify_stalls, test_timeouts_and_close,
              test_blocked_producer_wakes_when_space_frees):
        t()
        print("ok ", t.__name__)

11 · Testing concurrent code

Concurrency bugs depend on timing, so tests must make bad timings likely and detect their consequences. Three techniques do most of the work here. Shrink the thread switch interval so threads interleave at fine granularity. Run many threads doing many operations (four producers and four consumers moving 8,000 items). And check properties that any correct run must satisfy: every item received exactly once (compare sorted lists), the size never exceeds capacity, no thread errors, no thread still alive after a generous time limit (a join timeout turns a hang into a failed assertion instead of a frozen test suite). The same harness run against the broken variants proves the tests can detect the bugs, which is as important as passing: a stress test that never fails on a known-broken queue tests nothing. Small deterministic tests then pin specific behaviours: a timeout raises after roughly the right time, a blocked producer wakes when a slot frees, close drains and then rejects.

12 · Talking through the design

"One lock protects the deque. Two conditions share it: producers wait on not_full, consumers on not_empty. Every wait is in a while loop, because a woken thread has to reacquire the lock and someone may have changed the queue first; with an if, a barging consumer makes the woken one pop from an empty deque. Two conditions because each put enables exactly one get and vice versa, so notify() reaches a thread that can act; with one shared condition a get's notify can wake another consumer and every thread can end up waiting. Timeouts are wait_for with a deadline. Close sets a flag and notify_all on both conditions; consumers drain, then get raises Closed. It is the same structure as CPython's queue.Queue."

13 · Edge cases

Capacity zero or negative: rejected (CPython treats maxsize <= 0 as unbounded; decide and document). Timeout zero: behaves as a non-blocking attempt. Negative timeout: CPython raises ValueError. Exceptions while holding the lock: the with block releases it. Putting None: allowed; never use None as a sentinel inside the queue if users can put None (use close, or a private sentinel object). qsize: only a snapshot; by the time the caller acts on it, it may be wrong, as the standard library's documentation warns. Interrupts: a KeyboardInterrupt in a waiting thread propagates out of wait with the lock reacquired and released by the with block.

14 · Extensions the interviewer will ask for

Task tracking: CPython's task_done() and join(), a counter of unfinished tasks and a third condition notified when it reaches zero. Priorities: a heap with (priority, sequence, item). Batch operations: get up to n items in one lock acquisition to cut overhead. Fair ordering: a FIFO of per-waiter events. Multiprocessing: a queue between processes needs serialisation and a pipe or shared memory (multiprocessing.Queue). asyncio: asyncio.Queue with futures instead of conditions. Metrics: time producers spent blocked (backpressure) and consumers spent idle, which tell you which side to scale.

15 · Complexity

put and get are O(1) apart from waiting: one deque operation and one notify. Memory is O(capacity). Under contention, throughput is bounded by the single lock, since every operation takes it; at very high rates the remedies are batching, several queues (sharding), or lock-free structures in lower-level languages. Each wakeup costs a context switch, which is why waking only one thread per state change matters. With notify_all on a shared condition and n waiting threads, each operation can trigger n wakeups of which n − 1 find nothing to do, so the cost of an operation grows with the number of threads; with two conditions and notify it stays constant.

Mesa versus Hoare semantics

Condition variables come in two flavours. Under Hoare semantics, notify hands the lock directly to the woken thread, which runs immediately with the condition guaranteed true; an if would be enough. Under Mesa semantics, used by Python, Java, POSIX threads and almost every real system, notify only makes the waiter runnable; it must compete for the lock, and by the time it runs the condition may be false again. Mesa semantics are cheaper to implement and allow barging, which improves throughput, at the price of the while loop. Knowing the names explains why the loop is not paranoia: it is the contract.

Fairness and barging

CPython's Condition keeps its waiters in a deque and notify(n) releases the first n, so waiters are woken in the order they started waiting. But a woken waiter still has to acquire the lock, and a thread that arrives at that moment, never having waited, can acquire it first. That is barging, and it is what made the if-bug trace possible. Barging is allowed because it is faster: handing the lock to a specific sleeping thread forces a context switch, while letting a running thread take it avoids one. The cost is that a thread can, in principle, be overtaken repeatedly. CPython's queue module says plainly in a comment that fairness is not part of the API contract. Java's ArrayBlockingQueue offers an optional fairness policy that grants access in FIFO order, documented as reducing throughput. If strict FIFO service matters, give each waiter its own event in a queue and signal them in order.

Why notify inside the lock

Python requires the lock to be held when calling notify, and Java's equivalent likewise. Holding it guarantees there is no window between changing the state and signalling: a consumer cannot check "empty", be preempted, miss the producer's notify, and then wait forever, because the consumer's check and its wait are atomic with respect to the lock, and the producer's change and notify happen inside the same lock. This is the lost-wakeup problem that condition variables were designed to prevent, and it is also why the release-and-sleep inside wait() must be a single atomic operation.

Semaphores as an alternative

The classic textbook solution uses two counting semaphores, "empty slots" starting at capacity and "full slots" starting at zero, plus a mutex for the buffer. A producer acquires an empty slot, locks, appends, unlocks, releases a full slot; a consumer does the reverse. It is elegant and correct, and Python's threading.Semaphore supports it. Condition variables are more flexible, because predicates can be arbitrary (closed flags, priorities, batch sizes), which is why production queues, including CPython's, use them. The semaphore version is a good way to show you know both and why one is chosen.

Spurious wakeups

POSIX threads, the threading interface beneath most Unix systems, explicitly allow a waiting thread to return from a condition wait without any notify, a spurious wakeup. Allowing it lets implementations be simpler and faster on multiprocessor hardware, at the cost of requiring every caller to re-check. Java's documentation says the same about its conditions. Python's own condition implementation does not produce spurious wakeups in practice, but the while loop is required anyway for the barging reason in the body, so the rule is the same everywhere: a wait is a hint that the state may have changed, never a guarantee that it did.

Contention and batching

Every put and get takes the same lock, so at high rates threads spend more time waiting for the lock than doing work, and each handoff may cost a context switch, several microseconds. Two remedies are common. Batching: a consumer that takes up to n items per lock acquisition, or a producer that puts a list, divides the locking cost by n. Sharding: several queues with producers spread across them (by hash or round robin) and consumers each owning one or stealing from others, as work-stealing thread pools do. Both trade strict global FIFO order for throughput, which is usually acceptable.

Ring buffers for one producer and one consumer

When exactly one thread produces and exactly one consumes, a bounded queue can avoid locks entirely: a fixed-size array used as a ring, a head index written only by the consumer and a tail index written only by the producer. Each side reads the other's index to know whether the ring is full or empty, using atomic loads and stores with the right memory ordering. Audio pipelines, network drivers and trading systems use such single-producer single-consumer rings because they cost nanoseconds per item. Blocking still needs a way to sleep when the ring is empty, typically a brief spin followed by an operating system wait. In Python the interpreter's overheads dwarf these savings, so the condition-variable design is the right one; the ring is worth knowing for the interview's "how would you make it faster in C++ or Rust?" follow-up.

The GIL does not make this safe

In CPython, the global interpreter lock lets one thread run Python bytecode at a time, which tempts people to think simple operations are safe without locks. Individual deque operations are indeed atomic, but the queue's correctness depends on multi-step sequences, check then act, which the interpreter can interrupt between any two bytecodes. The broken variants in the solution fail on CPython with the GIL, which is the most direct proof. On the free-threaded build available from Python 3.13, more interleavings are possible, not fewer.

How blocking queues fail in production

The classic failure is the unbounded queue: a producer faster than its consumers fills memory until the process is killed, and latency grows long before that because every item waits behind millions of others. Bound every queue between threads or services, and decide what happens when it is full: block (backpressure, as here), reject (fast failure, as in the batching case), or drop with a counter (as in the logging case).

The second is shutdown hangs: consumer threads blocked forever in get when the program tries to exit, or daemon consumers killed mid-item. A close or shutdown that wakes everyone and lets consumers drain fixes both.

The third is rare crashes and freezes from the bugs in this lesson, often in hand-written queues inside larger components (a custom connection pool, a scheduler's wait list). They appear under load, disappear when logging is added (which changes timing), and are found by stress tests and code review against the two rules: while, not if; one condition per kind of waiter or notify_all.

Choosing the full-queue policy

Blocking is right inside one process when producers can afford to wait, such as a file reader feeding parsers. It is wrong at a service boundary, where a blocked request handler holds a connection, memory and often a client's patience; there, rejecting immediately with a retry hint (as in the batching case) or shedding load is better. Dropping is right for data whose loss is acceptable and counted, such as logs or metrics samples. Many systems combine them: block for a short timeout, then reject. Whatever the policy, it should be explicit in the code and visible in metrics, because the full-queue path is where the system's behaviour under stress is decided.

What to measure

Most of these signals are cheap to collect inside the queue itself, with counters updated under the lock it already holds. Queue depth over time, the fraction of time producers spend blocked in put (backpressure, a sign consumers are the bottleneck), the fraction of time consumers spend idle in get (producers are the bottleneck), item age when dequeued (queueing latency), and the number of threads waiting on each condition. A queue that is always full means add consumers; always empty means add producers or fewer consumers.

Knobs

Capacity (larger absorbs bursts but adds latency and memory; Little's law relates them), number of consumers, timeouts on put and get, and the full-queue policy. Size capacity from burst size and acceptable latency, not as "big enough to never block", which defeats backpressure. Revisit it when traffic patterns change: a capacity tuned for steady load can be far too small for a nightly batch burst, and the blocked-producer metric is what tells you.

The real case: CPython's queue.Queue

The standard library's Lib/queue.py is a compact, production-quality version of this lesson's design and worth reading in full. The constructor creates one threading.Lock as self.mutex and three conditions sharing it: not_empty, notified whenever an item is added so a waiting get can proceed; not_full, notified whenever an item is removed so a waiting put can proceed; and all_tasks_done, notified when the count of unfinished tasks drops to zero, for join(). put waits on not_full in a while self._qsize() >= self.maxsize loop, with deadline arithmetic for timeouts that raises Full when time runs out, then appends, increments the unfinished-task count and calls self.not_empty.notify(). get waits on not_empty in a while not self._qsize() loop, raising Empty on timeout, then removes an item and calls self.not_full.notify(). The module also contains a comment on its simpler queue noting that while the pure-Python version happens to provide fairness, fairness is not part of the API contract. The documentation adds that qsize() is approximate and that 3.13 introduced shutdown and the ShutDown exception. Every rule in this lesson, one lock, two conditions, while loops, notify one per state change, deadline-based timeouts, is visible in those few dozen lines.

Goal: run the queue and its broken twins, then break, measure and extend. Python 3.12, standard library only.

  1. Save the full solution as blocking_queue.py and run it. The correct queue passes the stress test at capacities 1, 3 and 64; the two broken variants fail, and the output shows how (IndexError for if-not-while, eight stuck threads for one shared condition).
  2. Break it. Put the default switch interval back (remove the setswitchinterval calls) and run the broken variants again. How often do they fail now? This is why such bugs survive casual testing.
  3. Fix it two ways. Make OneConditionQueue correct by replacing notify() with notify_all(). It passes; now time it against the two-condition queue with 16 producers and 16 consumers.
  4. Measure it. Count, with a wrapper around wait, how many times consumers wake up and find nothing to do, for notify() with two conditions versus notify_all() with one.
  5. Extend it. Add task_done() and join() with a third condition, as CPython does, and a get_batch(n, timeout) that returns up to n items in one lock acquisition.
  6. Extend it again. Implement the semaphore version (two semaphores and a mutex) and run it through the same stress harness.

Each change is judged by the harness: exactly-once delivery, size within capacity, no errors, no stuck threads. Run each experiment several times, because a single passing run of a concurrent test proves very little. Record the failure rate across, say, twenty runs; a fix that lowers it without reaching zero is not a fix.

Work it out

A colleague's bounded queue uses one threading.Condition for everything:

def put(self, x):
    with self.cv:
        if len(self.items) == self.cap:
            self.cv.wait()
        self.items.append(x)
        self.cv.notify()

def get(self):
    with self.cv:
        if not self.items:
            self.cv.wait()
        x = self.items.popleft()
        self.cv.notify()
        return x

(a) Find every bug. (b) For each, give an interleaving that triggers it. (c) Write the fix and explain why it works.

Answer

(a) Three bugs. Both waits use if instead of while (two bugs, one in each method), and producers and consumers share one condition with notify().

(b) Interleavings.

get with if: C1 finds the queue empty and waits. P appends x and notifies; C1 is woken but must reacquire the lock. C2, arriving fresh, takes the lock, sees x, removes it. C1 reacquires, skips the check and pops from an empty deque: IndexError.

put with if: capacity 1, queue full. P1 and P2 both wait. C takes the item and notifies, waking P1. Before P1 reacquires the lock, P3 (arriving fresh) appends, filling the queue. P1 reacquires, skips the check and appends anyway: the queue now holds 2 items with capacity 1, and the bound, the whole point of the class, is broken silently.

One condition with notify: capacity 1, both consumers waiting on an empty queue. P1 puts a and wakes C1; P1 tries to put b and waits (full); P2 tries to put c and waits. C1 takes a and notifies; the notify wakes C2 (the longest waiter), not a producer. C1 calls get again and waits; C2 finds the queue empty and waits. Four threads waiting, two producers with items, nobody left to notify: everything stops.

(c) The fix. Two conditions on one lock, waits in while loops:

self.lock = threading.Lock()
self.not_full = threading.Condition(self.lock)
self.not_empty = threading.Condition(self.lock)

def put(self, x):
    with self.not_full:
        while len(self.items) == self.cap:
            self.not_full.wait()
        self.items.append(x)
        self.not_empty.notify()

def get(self):
    with self.not_empty:
        while not self.items:
            self.not_empty.wait()
        x = self.items.popleft()
        self.not_full.notify()
        return x

Why it works. The while loops make every thread re-check its predicate after reacquiring the lock, so no thread acts on a state that changed while it was waking up; barging can delay a thread but never make it act wrongly. The two conditions make every notify reach a thread that can use it: a get's notify can only wake a producer and a put's only a consumer, and each operation enables exactly one opposite operation, so one notify suffices. Holding the shared lock while checking, changing and notifying means no notify can fall between a thread's check and its wait. The solution's stress test shows the difference empirically: the broken versions failed in every run; the fixed one never did.
