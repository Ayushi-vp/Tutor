A web service connects to its database for every request. At low traffic nobody notices that each request spends 30 milliseconds opening a connection before running a 2-millisecond query. During a launch, traffic grows twentyfold; the database spends more time accepting and authenticating connections than answering queries, hits its connection limit, and starts refusing new ones. The service falls over, and the database graphs show it nearly idle in terms of actual queries.

A connection pool fixes this by keeping a small number of connections open and lending them out: a request borrows one, runs its queries, and returns it for the next request. Every serious database client has one: SQLAlchemy's QueuePool in Python, HikariCP in Java, the pools inside most drivers, and server-side poolers such as PgBouncer when there are too many application processes.

The pool is a perfect machine-coding question for concurrency because it is a shared, scarce resource with a messy lifecycle. Connections are expensive to create, so creating them must not happen under the pool's lock. They are limited, so the pool must never create more than its bound, even when twenty threads ask at the same instant. They go stale, because servers close idle connections, restart and fail over, so they must be checked before reuse. They carry state, so a returned connection must be reset before someone else gets it. And callers make mistakes: they forget to return connections on error paths, or return one twice.

Each of those has a bad interleaving worth tracing. The most instructive is the over-creation race: check that there is room, then open a connection, then count it. In this lesson's test a pool written that way, with a limit of 5, handed out 20 connections to 20 simultaneous callers. The fix, reserving the slot under the lock before opening the connection outside it, is the central idea of the lesson, and it generalises to any "check capacity, then do slow work" situation.

The lesson follows the round: clarify the requirements, name the states a connection can be in, draw the pool, write a naive version and trace its failures, then build the correct pool in stages (reservation, waiting with a timeout, validation on checkout, reset on return, discarding and overflow, leak and double-release detection, FIFO versus LIFO), test it against a fake database server under contention and across a simulated restart, and compare each decision with SQLAlchemy's documented pool.

Why connections are expensive

A database connection is a TCP connection plus a protocol session. Opening one costs a network round trip for the TCP handshake, often more for TLS encryption, then authentication and session setup on the server, which may start a process or allocate memory per connection. That can take from a few milliseconds on a local network to hundreds over long distances, often far more than the query itself. Servers also cap concurrent connections (PostgreSQL's default max_connections is 100), because each one costs memory. Reusing connections removes the setup cost from every request and keeps the number the server sees small and stable.

The life of a pooled connection

A connection in a pool is always in one of a few states. Being opened: a slot is reserved and the handshake is in progress. Idle: open and waiting in the pool. Checked out: lent to a caller. Discarded: closed and removed, because it was broken, too old, or an extra overflow connection that is no longer needed. The pool's job is to move connections between these states safely and to keep one number honest: the total it is responsible for, which must never exceed its limit.

Waiting for a connection

When every connection is in use and the pool is at its limit, a caller must wait. Waiting uses a condition variable, exactly as in the blocking-queue case: hold the pool's lock, and while there is no idle connection and no free slot, wait; when a connection is returned or a slot frees up, notify. Unlike a queue, the wait needs a deadline: a caller should get an error after, say, 30 seconds rather than hang forever when the database is overloaded. SQLAlchemy calls this pool_timeout and defaults it to 30 seconds.

The analogy, and where it breaks

Think of a library with five copies of a popular textbook. Students borrow a copy, use it and return it; the librarian keeps a count of copies on loan. If all five are out, students queue. The librarian may order up to ten extra copies during exam week, and sends those extras back when they are returned. Before lending a copy, the librarian checks it is not falling apart; when a copy comes back, they remove any notes left in it. The analogy breaks at ordering: a librarian who has decided to order a copy writes it in the ledger first, but software that checks "fewer than five?" and then spends ten milliseconds opening a connection before writing anything down lets twenty requests each decide to order one.

1 · Clarify the requirements

Ask what is being pooled (database connections, HTTP clients, model-server sessions), how expensive creating one is, how many the server allows, the base size and whether bursts may exceed it, how long callers may wait, whether connections go stale (server idle timeouts, restarts, failover), what state connections carry between uses (transactions, session settings), whether connections should be created up front or lazily, and how callers will use the pool (threads, async tasks, forked processes).

A typical agreed scope: a thread-safe pool of database connections; base size and maximum overflow; lazy creation; acquire with a timeout that raises; validation on checkout by age and by ping; rollback on return; broken and overflow connections closed on return; a context manager; detection of double returns and long-held connections. Invariants: the total of opening, checked-out and idle connections never exceeds size plus overflow; a connection is never checked out by two callers at once; every capacity change wakes a waiter if one exists.

2 · The pieces

The pool's state is a deque of idle connections, a dict of checked-out connection ids with the time each was taken, and an integer _total counting every connection the pool is responsible for, including those being opened. One condition variable (with its lock) guards all of it. The solution adds a FakeServer that counts open connections, records the peak, can enforce a connection limit, takes a configurable time to connect, and can "restart", which makes every existing connection dead, so the tests can check bounds and recovery without a real database.

3 · Stage one: a naive pool and the over-creation race

def acquire(self):
    with self.lock:
        if self.idle:
            return self.idle.pop()
        room = self.total < self.limit         # check
    if not room:
        raise PoolTimeout("full")
    conn = self.connect()                     # slow: 10 ms, no lock held
    with self.lock:
        self.total += 1                       # act, too late
    return conn

The author carefully kept the slow connect() outside the lock, which is right, but split the check from the increment, which is wrong. Here is the interleaving with a limit of 5 and twenty threads arriving together:

StepThread 1Threads 2–20total
1lock; no idle; 0 < 5: room; unlock0
2connect() begins (10 ms)each: lock; no idle; 0 < 5: room; unlock0
3still connectingeach: connect() begins0
4lock; total += 1each in turn: lock; total += 11 … 20

Every thread checked the count while it was still 0, because no thread had incremented it yet: the increment only happens after the slow connect. Twenty connections are opened against a limit of 5. In the solution's test, with a 10-millisecond connect delay, the racy pool handed out exactly that: 20 connections, and the fake server's peak was 20. Against a real database with a limit, the excess connections fail with "too many connections"; against one without, the application quietly uses four times the connections it was configured for.

4 · Stage two: reservation, and why it works

The correct acquire makes the decision and the count one step: under the lock, if no idle connection exists and _total is below the limit, it increments _total immediately and records that it must create a connection. Only then does it release the lock and open the connection. The count now includes connections being opened, so a second thread arriving one microsecond later sees 1, not 0, and the twenty-first thread sees 20... except it cannot, because the fifth reservation brought the total to the limit and every later thread waits. If opening fails (the server is down or rejects the connection), the reservation is given back: _total is decremented and a waiter notified, so a failure does not permanently shrink the pool. The solution's contention test drives 20 threads through 100 queries each against a pool of 5 with a 2-millisecond connect delay: the server's peak was 5 and the pool created exactly 5 connections.

Why not simply hold the lock during connect()? It would also be correct, but every other thread, including those returning connections, would be blocked for the duration of a connect. One slow connection attempt (a database failing over, a DNS lookup timing out) would freeze the entire pool. Reservation keeps the critical section to a few instructions.

5 · Stage three: waiting with a deadline

When there is no idle connection and no free slot, acquire waits on the condition variable in a loop, recomputing the time left until a single deadline computed at the start. If the wait times out and the condition still does not hold, it raises PoolTimeout. The loop matters for the reasons from the blocking-queue case: a woken thread must re-check, because another thread may have taken the connection first. The test holds both connections of a size-2 pool and checks that a third acquire with a 0.1-second timeout raises after about 0.1 seconds.

6 · Stage four: validation on checkout

An idle connection may be dead: the server restarted, failed over to a standby, or closed it after an idle timeout (MySQL's default is eight hours, as SQLAlchemy's documentation notes), or a firewall silently dropped it. Using it fails the caller's first query. The pool validates connections when it hands them out, outside the lock since validation can do I/O. Two checks are standard. Recycle by age: a connection older than the configured age is closed and replaced, which SQLAlchemy calls pool_recycle and describes as the optimistic approach. Pre-ping: a cheap round trip (a driver ping, or SELECT 1) on every checkout, SQLAlchemy's pool_pre_ping, the pessimistic approach. A connection that fails either check is discarded (closed, slot released, a waiter notified) and the loop tries again, creating a fresh connection if needed, so the caller never sees the dead one. The restart test checks out a connection, returns it, restarts the fake server, and checks that the next checkout returns a different, working connection, with one discard recorded.

7 · Stage five: return, reset, discard and overflow

release first removes the connection from the checked-out set under the lock; if it was not there, this is a double release (or a connection from another pool) and it raises, because otherwise the same connection could end up in the idle deque twice and be handed to two callers at once. Then, outside the lock, it resets the connection: if a transaction is open, it rolls back, releasing locks and discarding uncommitted changes. If the reset fails because the connection is dead, the connection is discarded. Otherwise, under the lock: if the total exceeds the base size, this is an overflow connection that was opened during a burst, so it is closed; else it goes back to the idle deque and one waiter is notified.

Every path that frees capacity notifies a waiter, and in the solution all discard paths go through one helper, _forget, so none can forget. That matters: here is the lost-wakeup trace that results if the discard path only decrements the count.

8 · Stage six: leaks, double release and the context manager

The commonest real bug is a connection that is never returned: a request handler raises between acquire and release. After as many such errors as the pool's size, every acquire times out. The defence is structural: callers use with pool.connection() as c:, whose finally block returns the connection whatever happens; the test raises inside the block and checks the connection came back. Detection complements it: the pool records when each connection was checked out, and leaks(older_than) lists those held too long, which a monitoring thread can log with the checkout's stack trace. Double release is rejected using the same checked-out map.

9 · Stage seven: FIFO or LIFO

Which idle connection should the pool hand out? FIFO (the one idle longest) spreads use across all connections in rotation, so all of them stay warm. LIFO (the one returned most recently) keeps reusing a few, leaving the rest idle; under light load the spares sit long enough for the server's idle timeout to close them, and pre-ping replaces them when traffic returns. SQLAlchemy's documentation describes exactly this trade-off for its pool_use_lifo flag. The test fills a pool of four, then runs twelve sequential checkouts: FIFO touches all four connections, LIFO only one.

10 · The full solution

The file below contains the fake server, the pool, the racy pool and seven tests. Python 3.12, standard library only; it runs in a couple of seconds.

"""Connection pool: bounded size plus overflow, reserve-then-create outside the lock,
acquire with timeout on a condition variable, validation on checkout (recycle by age,
pre-ping), reset on return, broken and overflow connections discarded, double-release
detection, a context manager against leaks, and FIFO or LIFO reuse.
Python 3.12, standard library only (a fake database stands in for the server).
Run: python connpool.py"""
from __future__ import annotations

import collections
import contextlib
import itertools
import threading
import time
from typing import Callable, Iterator


# ------------------------------------------------------------------ a fake database server
class TooManyConnections(Exception): ...
class Disconnected(Exception): ...


class FakeServer:
    def __init__(self, max_connections: int = 100, connect_delay: float = 0.0) -> None:
        self.max_connections, self.connect_delay = max_connections, connect_delay
        self.open = 0
        self.peak = 0
        self.generation = 0                                   # bumps on restart
        self._lock = threading.Lock()
        self._ids = itertools.count(1)

    def connect(self) -> "FakeConnection":
        time.sleep(self.connect_delay)                        # handshakes take time
        with self._lock:
            if self.open >= self.max_connections:
                raise TooManyConnections(f"server limit {self.max_connections}")
            self.open += 1
            self.peak = max(self.peak, self.open)
            return FakeConnection(self, next(self._ids), self.generation)

    def restart(self) -> None:
        with self._lock:
            self.generation += 1                              # every existing socket is now dead
            self.open = 0


class FakeConnection:
    def __init__(self, server: FakeServer, cid: int, generation: int) -> None:
        self.server, self.id, self.gen = server, cid, generation
        self.created = time.monotonic()
        self.in_transaction = False
        self.closed = False

    def _check(self) -> None:
        if self.closed or self.gen != self.server.generation:
            raise Disconnected(f"connection {self.id} is dead")

    def execute(self, sql: str) -> str:
        self._check()
        if sql.upper().startswith("BEGIN"):
            self.in_transaction = True
        return f"ok:{sql}"

    def ping(self) -> bool:
        try:
            self._check()
            return True
        except Disconnected:
            return False

    def rollback(self) -> None:
        self._check()
        self.in_transaction = False

    def close(self) -> None:
        if not self.closed:
            self.closed = True
            if self.gen == self.server.generation:
                with self.server._lock:
                    self.server.open -= 1


# ------------------------------------------------------------------ the pool
class PoolTimeout(Exception): ...


class ConnectionPool:
    def __init__(self, connect: Callable[[], FakeConnection], size: int = 5, max_overflow: int = 0,
                 timeout: float = 30.0, recycle: float | None = None, pre_ping: bool = True,
                 lifo: bool = False) -> None:
        self._connect, self.size, self.max_overflow = connect, size, max_overflow
        self.timeout, self.recycle, self.pre_ping, self.lifo = timeout, recycle, pre_ping, lifo
        self._idle: collections.deque[FakeConnection] = collections.deque()
        self._out: dict[int, float] = {}                      # checked-out id -> since
        self._total = 0                                        # idle + out + being created
        self._cv = threading.Condition()
        self.created = self.discarded = 0

    @property
    def limit(self) -> int:
        return self.size + self.max_overflow

    def _valid(self, c: FakeConnection) -> bool:
        if self.recycle is not None and time.monotonic() - c.created > self.recycle:
            return False
        return c.ping() if self.pre_ping else True

    def _forget(self, c: FakeConnection | None) -> None:
        """Give a slot back (call WITHOUT the lock held: close may do I/O)."""
        if c is not None:
            c.close()
        with self._cv:
            self._total -= 1
            self.discarded += c is not None
            self._cv.notify()                                 # capacity changed: wake a waiter

    def acquire(self, timeout: float | None = None) -> FakeConnection:
        deadline = time.monotonic() + (self.timeout if timeout is None else timeout)
        while True:
            with self._cv:
                while not self._idle and self._total >= self.limit:
                    left = deadline - time.monotonic()
                    if left <= 0 or not self._cv.wait(left):
                        if not self._idle and self._total >= self.limit:
                            raise PoolTimeout(f"no connection within the timeout ({self.limit} in use)")
                if self._idle:
                    c = self._idle.pop() if self.lifo else self._idle.popleft()
                    create = False
                else:
                    self._total += 1                          # RESERVE the slot under the lock
                    c, create = None, True
            if create:                                        # slow I/O outside the lock
                try:
                    c = self._connect()
                except BaseException:
                    self._forget(None)                        # un-reserve, wake a waiter
                    raise
                with self._cv:
                    self.created += 1
            elif not self._valid(c):                          # stale: replace transparently
                self._forget(c)
                continue
            with self._cv:
                self._out[c.id] = time.monotonic()
            return c

    def release(self, c: FakeConnection) -> None:
        with self._cv:
            if self._out.pop(c.id, None) is None:
                raise RuntimeError(f"connection {c.id} released twice or not from this pool")
        try:
            if c.in_transaction:
                c.rollback()                                  # reset: never hand over open state
        except Disconnected:
            self._forget(c)
            return
        with self._cv:
            if self._total > self.size:                       # an overflow connection: shrink
                overflow = True
            else:
                self._idle.append(c)
                self._cv.notify()
                return
        if overflow:
            self._forget(c)

    @contextlib.contextmanager
    def connection(self, timeout: float | None = None) -> Iterator[FakeConnection]:
        c = self.acquire(timeout)
        try:
            yield c
        finally:
            self.release(c)                                   # even if the body raised

    def leaks(self, older_than: float) -> list[int]:
        now = time.monotonic()
        with self._cv:
            return [cid for cid, since in self._out.items() if now - since > older_than]

    def dispose(self) -> None:
        with self._cv:
            idle, self._idle = list(self._idle), collections.deque()
        for c in idle:
            self._forget(c)


class RacyPool(ConnectionPool):
    """BUG: checks the count, then creates, then increments; two threads both pass the check."""

    def acquire(self, timeout=None):
        with self._cv:
            if self._idle:
                c = self._idle.popleft()
                self._out[c.id] = time.monotonic()
                return c
            room = self._total < self.limit                   # check ...
        if not room:
            raise PoolTimeout("full")
        c = self._connect()                                   # ... act, unprotected
        with self._cv:
            self._total += 1
            self._out[c.id] = time.monotonic()
        return c


# ---------------------------------------------------------------- tests
def hammer(pool: ConnectionPool, threads: int = 20, ops: int = 100) -> list[str]:
    errors: list[str] = []
    start = threading.Barrier(threads)

    def worker() -> None:
        start.wait()
        for _ in range(ops):
            try:
                with pool.connection(timeout=5) as c:
                    c.execute("SELECT 1")
            except Exception as e:
                errors.append(type(e).__name__)
    ts = [threading.Thread(target=worker) for _ in range(threads)]
    for t in ts: t.start()
    for t in ts: t.join(30)
    return errors


def test_bounded_under_contention() -> None:
    server = FakeServer(max_connections=1_000, connect_delay=0.002)
    pool = ConnectionPool(server.connect, size=5, max_overflow=0)
    assert hammer(pool) == []
    assert server.peak <= 5 and pool.created <= 5
    print(f"    20 threads x 100 queries through 5 connections: peak {server.peak}, created {pool.created}")


def test_racy_creation_overshoots() -> None:
    server = FakeServer(max_connections=1_000, connect_delay=0.01)
    pool = RacyPool(server.connect, size=5, max_overflow=0)
    got, start = [], threading.Barrier(20)

    def grab() -> None:
        start.wait()
        try:
            got.append(pool.acquire())
        except PoolTimeout:
            pass
    ts = [threading.Thread(target=grab) for _ in range(20)]
    for t in ts: t.start()
    for t in ts: t.join()
    print(f"    racy pool, limit 5: {len(got)} connections handed out, server peak {server.peak}")
    assert len(got) > 5


def test_restart_is_survived_with_pre_ping() -> None:
    server = FakeServer()
    pool = ConnectionPool(server.connect, size=3)
    with pool.connection() as c:
        first = c.id
    server.restart()                                          # the idle connection is now dead
    with pool.connection() as c:
        assert c.execute("SELECT 1") == "ok:SELECT 1" and c.id != first
    assert pool.discarded == 1


def test_recycle_and_overflow_and_reset() -> None:
    server = FakeServer()
    pool = ConnectionPool(server.connect, size=1, max_overflow=2, recycle=0.05)
    a, b, c = pool.acquire(), pool.acquire(), pool.acquire()  # 1 pooled + 2 overflow
    a.execute("BEGIN")
    for x in (a, b, c):
        pool.release(x)
    assert len(pool._idle) == 1 and server.open == 1          # overflow closed on return
    assert not pool._idle[0].in_transaction                   # rolled back on return
    time.sleep(0.06)
    d = pool.acquire()                                        # too old: recycled
    assert d.id not in (a.id, b.id, c.id)
    pool.release(d)


def test_timeout_leak_and_double_release() -> None:
    server = FakeServer()
    pool = ConnectionPool(server.connect, size=2)
    leaked = pool.acquire()
    held = pool.acquire()
    t0 = time.monotonic()
    try:
        pool.acquire(timeout=0.1)
    except PoolTimeout:
        assert time.monotonic() - t0 >= 0.09
    time.sleep(0.02)
    assert set(pool.leaks(older_than=0.01)) == {leaked.id, held.id}
    pool.release(held)
    try:
        pool.release(held)
    except RuntimeError:
        pass
    else:
        raise AssertionError("double release accepted")
    try:
        with pool.connection() as c:
            raise ValueError("bug in the request handler")
    except ValueError:
        pass
    assert len(pool._idle) == 1                               # returned despite the exception


def test_waiter_wakes_when_a_broken_connection_is_discarded() -> None:
    server = FakeServer()
    pool = ConnectionPool(server.connect, size=1)
    c = pool.acquire()
    got = []
    t = threading.Thread(target=lambda: got.append(pool.acquire(timeout=2)))
    t.start()
    time.sleep(0.05)
    c.execute("BEGIN")
    server.restart()                                          # rollback on return will fail
    pool.release(c)                                           # discarded: must still wake the waiter
    t.join(1)
    assert got and got[0].ping()


def test_lifo_keeps_spares_idle() -> None:
    server = FakeServer()
    for lifo in (False, True):
        pool = ConnectionPool(server.connect, size=4, lifo=lifo)
        conns = [pool.acquire() for _ in range(4)]
        for c in conns:
            pool.release(c)
        used = set()
        for _ in range(12):                                   # light, sequential load
            with pool.connection() as c:
                used.add(c.id)
        assert len(used) == (1 if lifo else 4)
        pool.dispose()

11 · Testing a pool

Three kinds of test cover it. A contention test drives many threads through the pool simultaneously, released together by a barrier, and checks the bound from the server's point of view (peak open connections), not just the pool's own counters. A demonstration test runs the racy pool through the same burst to prove the test can detect over-creation; with a 10-millisecond connect delay it saw all 20 threads get a connection against a limit of 5. Scenario tests then pin each lifecycle rule: dead connections replaced after a restart, overflow connections closed on return, transactions rolled back, recycling by age, timeouts, leak reports, double-release rejection, the context manager returning connections on exceptions, a waiter woken when a broken connection is discarded, and LIFO's reuse pattern. The fake server is what makes all of this fast and deterministic: no database, and a restart is one method call.

12 · Talking through the design

"The pool tracks a total that includes connections being opened, so under the lock acquire either takes an idle connection or reserves a slot by incrementing the total, then opens the connection outside the lock; on failure it un-reserves and notifies. Without reservation, twenty simultaneous callers all see room and open twenty connections against a limit of five; I've reproduced that. If there's no idle connection and no room, it waits on the condition with a deadline and raises a timeout. On checkout it validates: recycle by age and pre-ping, discarding dead ones transparently. On return it rejects double releases, rolls back open transactions, closes broken and overflow connections, and every capacity change notifies, or a waiter can sleep through a freed slot. Callers use a context manager so errors can't leak connections. SQLAlchemy's QueuePool makes the same choices: pool_size 5, max_overflow 10, pool_timeout 30, pre-ping and recycle, rollback on return, LIFO optional."

13 · Edge cases

Size zero: SQLAlchemy treats pool_size 0 as no limit; decide and document. Connect hangs: give the connect call its own timeout, or a reserved slot is held indefinitely. Server rejects connections (limit reached): the reservation is released and the error propagates; consider backing off. Pool disposed while connections are out: close idle ones now and checked-out ones when returned. Connection used after release: the caller still holds a reference; wrapping connections in a proxy that refuses use after release catches it. Threads and asyncio mixed: use an async pool for coroutines; a thread pool's blocking waits would stall the event loop. Forking: never share pooled connections with a child process.

14 · Extensions the interviewer will ask for

Minimum idle and pre-warming: keep a few connections open ahead of demand to avoid cold-start latency. Background health checks that ping idle connections periodically instead of at every checkout. Fair queuing for waiters. Per-tenant or per-endpoint pools as bulkheads. Metrics: in use, idle, waiting, wait time, creation rate, discard reasons. Async pools for asyncio drivers. Server-side pooling with PgBouncer when hundreds of application processes would otherwise each hold their own pool.

15 · Complexity

acquire and release are O(1) apart from waiting and I/O: deque and dict operations under a short critical section. Validation costs one round trip per checkout with pre-ping, or nothing with recycling alone. Memory is O(size + overflow) connections, each costing memory on both client and server. Throughput is bounded by the number of connections times the queries per second each can serve; the lock is never held during I/O, so it is not the bottleneck.

Reservation as a general pattern

"Check that there is capacity, then do slow work, then record it" appears far beyond connection pools: allocating seats, rate-limit tokens, disk quota, GPU memory for a batch, worker slots in a scheduler. The race is always the same, decisions made from a counter that has not yet been updated, and the fix is always the same: update the counter as part of the check, under the lock (or with an atomic compare-and-set), do the slow work afterwards, and roll the reservation back if the work fails. Databases use the same idea when they insert a placeholder row with a unique constraint before doing expensive work. Recognising "this is a reservation problem" is worth saying explicitly in an interview.

Pessimistic versus optimistic validation

Pre-ping on every checkout costs one round trip per request but guarantees the connection was alive a moment ago. Recycling by age costs nothing per request but only protects against staleness that correlates with age, such as server idle timeouts; it does nothing for a database that restarted five seconds ago. Many deployments combine them, or use pre-ping only after a connection has been idle for some seconds, which is what HikariCP's keepalive and validation settings approximate. And neither eliminates errors entirely: a connection can die between the ping and the query, so applications still need retry logic for idempotent operations.

Sizing the pool

A database can do only so much concurrent work: roughly its CPU cores times a small factor, plus some allowance for queries waiting on disk. Beyond that, more concurrent queries add lock contention and context switching without adding throughput, and latency rises for everyone. HikariCP's pool-sizing guide gives a widely used starting point, active connections ≈ (core count × 2) + effective spindle count, and notes that the result is often surprisingly small. The application's pool should be sized so that the sum across all instances stays near that number; requests beyond it should queue in the application (in the pool's wait queue), where they cost little, rather than in the database, where they cost a lot. Autoscaling multiplies pools, which is why server-side poolers exist.

Fairness and the waiter queue

With one condition variable, notify wakes the longest waiter, but a thread that arrives at that moment can take the returned connection first, and the woken waiter goes back to sleep. Under sustained overload, an unlucky waiter can be overtaken repeatedly and time out while newer requests succeed. Strictly fair pools keep a FIFO of waiters, each with its own event, and hand a returned connection directly to the head waiter, bypassing the idle deque. HikariCP's design notes list direct hand-off among the optimisations of its connection bag. Fairness costs a little throughput and makes tail latency predictable.

Pools across processes and forks

A connection is a socket, and sockets survive fork(): the child process inherits copies of the parent's file descriptors. If both processes then use the same pooled connection, their protocol messages interleave on one socket, and the database sees garbage or answers the wrong process. SQLAlchemy's documentation calls it critical that pooled connections are not shared with a forked process and recommends disposing of the pool in the child, or creating engines after forking. Pre-fork servers (Gunicorn with preload, multiprocessing workers) are where this bites.

How pools fail in production

Pool exhaustion is the classic outage: every connection checked out, every new request waiting, timeouts everywhere. Its causes are leaks (an error path that skips the return), slow queries holding connections for seconds, and transactions left open while the application does something slow, such as calling an external API inside a database transaction. The symptoms are rising wait times and timeouts in the application while the database itself shows few active queries, the tell-tale sign that connections are held but idle. Leak detection with checkout stack traces, statement timeouts on the database, and never doing network calls inside transactions are the standard remedies.

Stale connections are the second: after a database failover or restart, the first request on each pooled connection fails. Pre-ping removes the errors at the cost of a round trip; recycling below the server's idle timeout prevents most idle disconnections. Over-subscription is the third: many instances times large pools exceeding the database's limit, often triggered by autoscaling during a traffic spike, exactly when the database can least afford extra connections.

What to measure

Connections in use, idle and being opened; threads waiting and their wait time (the most direct sign of an undersized pool or a slow database); connection creation and discard rates with reasons (age, failed ping, broken, overflow); checkout duration distribution (long tails mean slow queries or leaks); and on the database side, active versus idle-in-transaction sessions.

Knobs

Base size, overflow, acquire timeout, recycle age (below the server's and any firewall's idle timeouts), pre-ping on or off, FIFO or LIFO, and a statement timeout on the server. Tune size from the database's capacity divided by instances, and acquire timeout from the request's own deadline: there is no point waiting 30 seconds for a connection inside a request that times out after 10.

The real case: SQLAlchemy's QueuePool

SQLAlchemy's pooling documentation describes the production version of this design. Its QueuePool is tuned with four main parameters passed to create_engine: pool_size (default 5, the number of connections kept open), max_overflow (default 10, connections allowed beyond the pool size), pool_timeout (default 30 seconds to wait before giving up on getting a connection) and pool_recycle (default −1, no recycling; the documentation notes that MySQL disconnects connections idle for eight hours by default). No pool pre-creates connections; they are opened on first use. On return, the pool's reset-on-return behaviour calls rollback() so that transactional state, including row and table locks, is removed before reuse. For disconnects it describes two approaches: pessimistic, with pool_pre_ping testing each connection at checkout with a driver ping or SELECT 1; and optimistic, with pool_recycle replacing connections after a set age and invalidation when an error reveals a dead connection. A pool_use_lifo flag switches reuse from FIFO, which cycles through every connection, to LIFO, which lets surplus connections idle so server-side timeouts can close them, recommended together with pre-ping. And the documentation is emphatic that pooled connections must not be shared with a forked process. Each of those features corresponds to a stage in this lesson's pool, which is why reading the SQLAlchemy page after building one is the best way to check the design.

Goal: run the pool against the fake server, then break, measure and extend it. Python 3.12, standard library only.

  1. Save the full solution as connpool.py and run it. Seven tests print ok; note the contention test's peak of 5 and the racy pool's 20 connections against a limit of 5.
  2. Break it. In acquire, move self._total += 1 from the reservation branch to after self._connect(). Run the contention test with connect_delay=0.01: the server's peak climbs above 5.
  3. Break it again. Remove the notify() from _forget. Run the broken-connection test: the waiter times out after two seconds despite the free slot.
  4. Measure it. With 50 threads and 2 ms queries, vary the pool size from 1 to 20 and plot throughput and average wait time. Then set the fake server to slow down as more connections are open (add a delay proportional to open) and find the size beyond which throughput falls.
  5. Extend it. Add a minimum-idle setting with a background thread that keeps at least N idle connections open and pings idle ones every few seconds.
  6. Extend it again. Make the pool fair: keep a FIFO of waiter events and hand returned connections directly to the first waiter.

Judge each change by the server's peak, the absence of timeouts under the stress test, and the scenario tests.

Work it out

A service runs 8 instances, each with a pool of size 10 and max_overflow 10, against a PostgreSQL server with max_connections 100. Each request runs queries for 20 ms in total, and each instance handles up to 400 requests per second at peak. A deploy adds a call to a payment API, taking 300 ms, inside the database transaction.

(a) Before the deploy, how many connections does each instance need at peak, and is the server's limit safe? (b) After the deploy? (c) What do you change?

Answer

(a) Before. By Little's law, connections in use ≈ arrival rate × time each request holds a connection: 400 per second × 0.02 s = 8 connections per instance, within the base size of 10. Across 8 instances: 64 at peak, under the server's 100. In the worst case, if every instance used its overflow, 8 × 20 = 160 would exceed the limit, so the configuration is only safe because traffic stays below overflow levels.

(b) After. Each request now holds its connection for 20 + 300 = 320 ms, because the payment call happens inside the transaction. Needed per instance: 400 × 0.32 = 128 connections. The pool provides at most 20, so 108 requests' worth of demand queue in the pool, waits rise until they hit the pool timeout, and requests fail. The instances try to open their overflow connections, 160 in total, beyond the server's 100, so some opens fail with "too many connections". On the database, the sessions are mostly "idle in transaction", holding locks while waiting for the payment API, which can block other queries. Database CPU looks low, which misleads anyone looking only at it.

(c) The fix. Move the payment call outside the transaction: commit, call the API, then record the result in a new short transaction (with an idempotency key for the payment). Connection hold time returns to about 20 ms and demand to about 8 per instance. Then make the configuration safe even at overflow: size the pools so that instances × (size + overflow) stays below the server's limit with headroom for administration, for example size 8 and overflow 2 (80 total), or put PgBouncer in front of the database. Add a statement timeout and an idle-in-transaction timeout on the server, alert on pool wait time, and set the pool timeout shorter than the request deadline so failing requests release capacity quickly.
