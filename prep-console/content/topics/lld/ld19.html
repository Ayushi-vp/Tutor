A service keeps its routing table in memory: thousands of requests per second read it, and once a minute a background job rewrites part of it. With a plain lock around the table, every request waits for every other request's lookup, even though lookups never interfere with each other. Someone swaps in a read-write lock, which lets lookups proceed together and makes the background job wait until it can have the table alone. Latency drops. Then, under peak traffic, the routing updates stop applying. The update job is waiting for the lock and never gets it: at every instant some request is reading, new requests keep arriving while old ones are still inside, and the count of readers never reaches zero.

A read-write lock grants two kinds of access: shared access for readers, any number at once, and exclusive access for a writer, alone. That part is easy to state and easy to implement. The hard part, and the part interviewers probe, is the policy for what happens when readers and writers are both waiting. Let readers in whenever no writer is active, and writers can starve, as in the opening story. Make new readers wait whenever a writer is waiting, and writers are safe, but a thread that takes a read lock twice can deadlock against a waiting writer. Serve everyone in arrival order, and both problems go away, at some cost in throughput.

Real libraries made different choices and documented the consequences. Go's sync.RWMutex blocks new readers once a writer is waiting and states that this prohibits recursive read locking. Java's ReentrantReadWriteLock offers a default non-fair mode that may postpone threads indefinitely but usually has higher throughput, and a fair mode that uses approximately arrival order; it allows downgrading from write to read but states that upgrading from read to write is not possible. Python offers no read-write lock at all, which is one reason the question is popular in Python interviews.

The round rewards precise reasoning about interleavings: why a writer starves, why a nested read deadlocks, why two upgrading readers deadlock, and why a waiter that gives up on a timeout must wake others. This lesson builds three locks from one condition variable, reproduces each failure with a test, and also records a bug the author introduced and caught while writing the solution: a timeout path that forgot to notify.

It is also the case in this family where the interviewer most often asks "and what does your favourite language do?", because the answer reveals whether you have read the documentation of the tools you use. Go, Java and Python give three different answers, and each is defensible.

The lesson follows the round: clarify the requirements, define the state, build the reader-preferring lock and trace the starvation, build the writer-preferring lock and trace the recursive-read deadlock, build the fair lock, discuss upgrade and downgrade, test everything with an invariant witness and timeouts, and cover when not to use a read-write lock at all.

Two kinds of access

Data shared between threads can be read concurrently without harm, because readers do not change anything. A write, however, must not overlap with any other access: a reader could see half-updated data, and two writers could interleave their changes. A plain mutual-exclusion lock enforces "one thread at a time", which is safe but needlessly strict for readers. A read-write lock enforces a compatibility rule instead: a read lock is compatible with other read locks; a write lock is compatible with nothing.

Already heldRequest readRequest write
NothingGrantGrant
Read locks (any number)Grant (policy permitting)Wait
Write lockWaitWait

"Policy permitting" in the middle cell is where the whole design lives. If a writer is waiting, should a newly arriving reader be granted the lock? The table says it is compatible with the current holders; fairness says it arrived after the writer.

Building one from a condition variable

The state is small: how many readers are inside, and whether a writer is inside. One condition variable (with its lock) guards it. A reader waits while a writer is inside, then increments the count. A writer waits while a writer is inside or any reader is, then sets the flag. Releasing a read lock decrements the count and, if it reaches zero, notifies all waiters, since a writer may now enter. Releasing the write lock clears the flag and notifies all, since many readers may now enter together. Everything else in this lesson is variations on the waiting predicates.

Where read-write locks appear

Read-mostly shared data is common: routing and configuration tables, in-memory indexes, caches refreshed periodically, the list of live cluster members, a model registry that maps names to loaded models. Databases use the same idea under the names shared and exclusive locks, and file systems for byte-range locks. In each case the reads are frequent and independent, and the writes are rare and must see and leave a consistent state, which is exactly the shape a read-write lock is built for.

The analogy, and where it breaks

Think of a museum room with a painting. Any number of visitors can look at once; a restorer needs the room empty. A guard at the door decides who enters. If the guard lets visitors in whenever the restorer is not working, a busy day means the room is never empty and the restorer waits until closing. If the guard stops admitting visitors as soon as the restorer arrives, the room empties and the restoration happens, but a visitor who stepped out to fetch a friend and wants to come back in is now stuck outside while the restorer waits for that same visitor to finish. If the guard keeps a single queue in arrival order, everyone gets a turn. The analogy breaks on scale and speed: guards are slow and polite, threads arrive millions of times a second, and the bookkeeping itself becomes a cost.

1 · Clarify the requirements

Ask about the read-to-write ratio and how long each holds the lock (a read-write lock only pays off when reads dominate and are not trivially short), whether writers must not starve, whether readers must not starve, whether a thread may take the read lock recursively, whether readers need to upgrade to writers, whether timeouts are needed, and whether the lock is used by threads or asyncio tasks.

A typical agreed scope: many readers, few writers; writers must not starve; timeouts on acquisition; context managers; no recursive or upgradable locking unless designed for. Invariants: at most one writer, and never a writer together with readers; readers can overlap; every waiter that can proceed is eventually woken; under the chosen policy, nobody waits forever while the lock keeps being granted to others.

2 · The state and the invariant

All three locks share the same skeleton: a Condition, an integer _readers, a boolean _writer, and policy-specific extra state. The safety invariant is not (_writer and _readers > 0) and "at most one writer", maintained because every change happens under the condition's lock and every acquire waits until the predicate for entering holds. The tests check it from outside with a Witness object that counts threads currently inside as readers or writers and flags any moment where a writer coexists with anyone else.

3 · Stage one: the reader-preferring lock

def acquire_read(self):
    with self._cv:
        while self._writer:                       # only an ACTIVE writer blocks readers
            self._cv.wait()
        self._readers += 1

def release_read(self):
    with self._cv:
        self._readers -= 1
        if self._readers == 0:
            self._cv.notify_all()                 # a writer may now enter

def acquire_write(self):
    with self._cv:
        while self._writer or self._readers:
            self._cv.wait()
        self._writer = True

def release_write(self):
    with self._cv:
        self._writer = False
        self._cv.notify_all()                     # readers may enter together

It is correct, the stress test finds no invariant violations, and it gives readers maximum concurrency. Note the two notifications. A reader leaving matters only when it was the last, because only then can a writer proceed. A writer leaving uses notify_all because every waiting reader may enter at once; waking just one would leave the others asleep until some later event.

4 · The bad interleaving: writer starvation

Trace a writer W against readers that arrive continuously, each holding the lock briefly:

TimeEventActive readersW
0R1, R2 enter2
1W calls acquire_write: readers > 0, waits2waiting
2R3 arrives: no writer active, enters3waiting
3R1 leaves (count 2, no notify)2waiting
4R4 enters3waiting
5R2 leaves, R5 enters, R3 leaves, R6 enters …≥ 1 alwayswaiting forever

Because readers overlap, the count never returns to zero and W is never notified at all (the zero-count notify never fires). This is starvation: the system is making progress, readers are being served, but one thread never is. The solution's test runs eight readers each holding the lock for 10 ms in a loop, then asks for the write lock with a one-second timeout: with the reader-preferring lock the writer times out every time.

5 · Stage two: the writer-preferring lock

Add a counter of waiting writers. A writer increments it before waiting and decrements it once it gets in. A reader now waits while a writer is active or any writer is waiting. Active readers finish, nobody new joins, the count reaches zero, the last reader notifies, and the writer enters. In the same test the writer got in after about 10 ms, one reader hold. This is the rule Go's sync.RWMutex documents: if any goroutine calls Lock while readers hold the lock, concurrent calls to RLock block until the writer has acquired and released it, "to ensure that the lock eventually becomes available to the writer".

Writers now win every contest, so under a steady stream of writers, readers could starve instead. In practice writers are rare in read-write-lock workloads, which is why writer preference is a common default; but it is a trade, not a solution.

6 · The bad interleaving: recursive reads deadlock

Writer preference introduces a deadlock that reader preference did not have. Suppose a function takes the read lock and calls a helper that also takes the read lock, a natural thing in layered code.

StepThread AThread WState
1acquire_read: no writer, none waiting: entersreaders 1
2acquire_write: readers > 0; waiting_writers = 1; waitsreaders 1, waiting 1
3calls helper: acquire_read: a writer is waiting, so waitsreaders 1, waiting 1
4waits for W to finishwaits for A's first read lock to be releaseddeadlock

A waits for W, which waits for A. Neither can proceed. Go's documentation draws the conclusion explicitly: this rule "prohibits recursive read-locking". The fair lock has the same property, because A's second request arrives after W's. The solution's test runs this exact sequence with a 0.3-second timeout on the inner read: the reader-preferring lock lets the nested read through (it ignores waiting writers), while the writer-preferring and fair locks time out, demonstrating the deadlock without hanging the test. The fix is a coding rule: never acquire a read lock while already holding it; structure code so helpers expect the caller to hold the lock, or make the lock re-entrant by tracking which threads hold read locks and letting them through, as Java's re-entrant implementation does at extra cost.

7 · Stage three: the fair lock

The fair lock serves requests in arrival order. Each call to acquire takes a ticket from a counter and joins a queue of (ticket, kind). A reader may enter when its ticket is at the head of the queue and no writer is active; on entering it leaves the queue and notifies all, so if the next ticket is also a reader it can enter immediately and join the active readers. A writer may enter when its ticket is at the head, no writer is active and no readers are active. The effect is that consecutive readers share the lock, but no request overtakes an earlier one. The test checks the key case: R0 holds a read lock, W1 arrives, then R2 arrives. Although R2 is compatible with the current holder, it waits, because W1 arrived first; when R0 releases, W1 runs, then R2. Java's ReentrantReadWriteLock in fair mode describes nearly this behaviour: a thread trying to acquire a fair read lock blocks if the write lock is held or a writer is waiting, and when the lock is released either the longest-waiting writer or a group of readers waiting longer than all writers gets it.

A trace of the fair lock

StepEventQueue (head first)Inside

2W1 takes ticket 1: head, but a reader is inside: waits[1:w]R0
3R2 takes ticket 2: not the head (W1 is): waits[1:w, 2:r]R0
4R3 takes ticket 3: waits[1:w, 2:r, 3:r]R0

Step 3 is the fairness rule at work: R2 was compatible with R0, yet it waited because W1 arrived earlier. Steps 7 and 8 show readers that queued together entering together: each reader that enters notifies, so the next reader in line can join without waiting for a release.

8 · Timeouts and the wakeup they owe

All three locks accept a timeout, implemented with Condition.wait_for. A timeout is not just "give up": the waiter must undo its effect on others. In the fair lock, a request that times out must remove its ticket from the queue and notify, or the request behind it waits forever for a head that will never move. In the writer-preferring lock, a writer that times out must decrement the waiting-writers count and notify, because readers that were blocked only because of it can now enter. The first draft of this lesson's solution decremented the counter in a finally block but did not notify on the timeout path; reviewing every exit path against "who might be sleeping because of me?" found it before a test did. It is the same lost-wakeup pattern as in the queue and pool cases: every state change that can make someone else's predicate true needs a notify.

9 · Upgrading and downgrading

A reader that discovers it needs to write is tempted to upgrade: keep the read lock and acquire the write lock. With one such reader that works in some designs. With two, it deadlocks: each holds a read lock and waits for the reader count to reach zero, which requires the other to release. The solution's test has two threads take read locks, synchronise with a barrier, then both request the write lock with a timeout: both time out. Java's documentation states that upgrading from a read lock to the write lock is not possible, and Go's that an RLock cannot be upgraded. The safe pattern is to release the read lock, acquire the write lock, and then re-check whatever condition prompted the write, because another writer may have changed it in between. (Some libraries offer a single "upgradable read" slot: at most one thread may hold it alongside plain readers, and only it may upgrade, which avoids the two-upgrader deadlock.)

Downgrading is safe: a thread holding the write lock acquires the read lock (permitted because it is the only holder; Java's re-entrant lock allows it), then releases the write lock. It never waits for anyone, so it cannot deadlock, and no other writer can slip in between, so the thread keeps a consistent view while letting other readers in. Java documents this sequence; the simple locks in this lesson would need re-entrancy tracking to support it.

10 · The full solution

The file below contains the three locks, the witness and six tests: invariant under stress for all three, readers sharing, writer starvation, recursive-read deadlock, upgrade deadlock and fair ordering. Python 3.12, standard library only; it takes a few seconds because the starvation and deadlock tests wait for their timeouts.

"""Read-write locks three ways: reader-preferring (writers can starve), writer-preferring
(Go's RWMutex rule: a waiting writer blocks new readers), and fair FIFO (Java's fair mode:
consecutive readers share, writers in arrival order). Plus the recursive-read and upgrade
deadlocks, and an invariant checker. Python 3.12, standard library only.
Run: python rwlock.py"""
from __future__ import annotations

import collections
import contextlib
import itertools
import threading
import time
from typing import Iterator


class LockTimeout(Exception): ...


class _Base:
    def acquire_read(self, timeout: float | None = None) -> None: ...
    def release_read(self) -> None: ...
    def acquire_write(self, timeout: float | None = None) -> None: ...
    def release_write(self) -> None: ...

    @contextlib.contextmanager
    def read_locked(self, timeout: float | None = None) -> Iterator[None]:
        self.acquire_read(timeout)
        try:
            yield
        finally:
            self.release_read()

    @contextlib.contextmanager
    def write_locked(self, timeout: float | None = None) -> Iterator[None]:
        self.acquire_write(timeout)
        try:
            yield
        finally:
            self.release_write()

    def _wait(self, cv: threading.Condition, pred, timeout: float | None) -> None:
        if not cv.wait_for(pred, timeout):
            raise LockTimeout("lock not acquired in time")


class ReaderPreferringRWLock(_Base):
    """Readers enter whenever no writer is ACTIVE. Simple, maximal read concurrency,
    and a continuous stream of overlapping readers starves writers forever."""

    def __init__(self) -> None:
        self._cv = threading.Condition()
        self._readers = 0
        self._writer = False

    def acquire_read(self, timeout=None):
        with self._cv:
            self._wait(self._cv, lambda: not self._writer, timeout)
            self._readers += 1

    def release_read(self):
        with self._cv:
            self._readers -= 1
            if self._readers == 0:
                self._cv.notify_all()

    def acquire_write(self, timeout=None):
        with self._cv:
            self._wait(self._cv, lambda: not self._writer and self._readers == 0, timeout)
            self._writer = True

    def release_write(self):
        with self._cv:
            self._writer = False
            self._cv.notify_all()


class WriterPreferringRWLock(ReaderPreferringRWLock):
    """A WAITING writer blocks new readers (Go's sync.RWMutex rule), so writers cannot starve.
    Consequence: a thread that already holds a read lock and asks for another can deadlock."""

    def __init__(self) -> None:
        super().__init__()
        self._waiting_writers = 0

    def acquire_read(self, timeout=None):
        with self._cv:
            self._wait(self._cv, lambda: not self._writer and self._waiting_writers == 0, timeout)
            self._readers += 1

    def acquire_write(self, timeout=None):
        with self._cv:
            self._waiting_writers += 1
            try:
                self._wait(self._cv, lambda: not self._writer and self._readers == 0, timeout)
            except LockTimeout:
                self._waiting_writers -= 1
                self._cv.notify_all()                     # readers we were blocking may proceed
                raise
            self._waiting_writers -= 1
            self._writer = True

    def release_write(self):
        with self._cv:
            self._writer = False
            self._cv.notify_all()


class FairRWLock(_Base):
    """Arrival order: each request takes a ticket. A reader may enter when every earlier
    ticket is a reader that has already entered; a writer when it is first and the lock is free.
    Consecutive readers therefore share; nobody overtakes an earlier writer."""

    def __init__(self) -> None:
        self._cv = threading.Condition()
        self._queue: collections.deque[tuple[int, str]] = collections.deque()
        self._tickets = itertools.count()
        self._readers = 0
        self._writer = False

    def _head_is(self, ticket: int) -> bool:
        return bool(self._queue) and self._queue[0][0] == ticket

    def acquire_read(self, timeout=None):
        with self._cv:
            t = next(self._tickets)
            self._queue.append((t, "r"))
            try:
                self._wait(self._cv, lambda: not self._writer and self._head_is(t), timeout)
            except LockTimeout:
                self._queue.remove((t, "r"))
                self._cv.notify_all()
                raise
            self._queue.popleft()
            self._readers += 1
            self._cv.notify_all()                         # let the next reader in line join us

    def release_read(self):
        with self._cv:
            self._readers -= 1
            if self._readers == 0:
                self._cv.notify_all()

    def acquire_write(self, timeout=None):
        with self._cv:
            t = next(self._tickets)
            self._queue.append((t, "w"))
            try:
                self._wait(self._cv, lambda: not self._writer and self._readers == 0
                           and self._head_is(t), timeout)
            except LockTimeout:
                self._queue.remove((t, "w"))
                self._cv.notify_all()
                raise
            self._queue.popleft()
            self._writer = True

    def release_write(self):
        with self._cv:
            self._writer = False
            self._cv.notify_all()


# ---------------------------------------------------------------- instrumentation
class Witness:
    """Counts who is inside; flags any moment with a writer plus anyone else."""

    def __init__(self) -> None:
        self._lock = threading.Lock()
        self.readers = self.writers = 0
        self.max_readers = 0
        self.violations = 0

    def enter(self, kind: str) -> None:
        with self._lock:
            if kind == "r":
                self.readers += 1
                self.max_readers = max(self.max_readers, self.readers)
            else:
                self.writers += 1
            if self.writers > 1 or (self.writers and self.readers):
                self.violations += 1

    def leave(self, kind: str) -> None:
        with self._lock:
            if kind == "r":
                self.readers -= 1
            else:
                self.writers -= 1


# ---------------------------------------------------------------- tests
VARIANTS = (ReaderPreferringRWLock, WriterPreferringRWLock, FairRWLock)


def test_mutual_exclusion_under_stress() -> None:
    for cls in VARIANTS:
        lock, w = cls(), Witness()
        stop = time.monotonic() + 0.6

        def reader() -> None:
            while time.monotonic() < stop:
                with lock.read_locked(timeout=5):
                    w.enter("r"); time.sleep(0.0005); w.leave("r")

        def writer() -> None:
            while time.monotonic() < stop:
                with lock.write_locked(timeout=5):
                    w.enter("w"); time.sleep(0.0005); w.leave("w")
                time.sleep(0.002)
        ts = [threading.Thread(target=reader) for _ in range(6)] + [threading.Thread(target=writer) for _ in range(2)]
        for t in ts: t.start()
        for t in ts: t.join(10)
        assert w.violations == 0 and w.max_readers > 1, (cls.__name__, w.violations, w.max_readers)


def test_readers_share() -> None:
    lock = FairRWLock()
    t0 = time.perf_counter()

    def r() -> None:
        with lock.read_locked():
            time.sleep(0.1)
    ts = [threading.Thread(target=r) for _ in range(4)]
    for t in ts: t.start()
    for t in ts: t.join()
    assert time.perf_counter() - t0 < 0.25                # 4 x 100 ms overlapped


def writer_wait_under_reader_stream(cls) -> float:
    """8 readers keep the lock continuously read-held (their holds overlap); how long until a writer gets in?"""
    lock = cls()
    stop = threading.Event()

    def reader() -> None:
        while not stop.is_set():
            with lock.read_locked():
                time.sleep(0.01)
    rs = [threading.Thread(target=reader) for _ in range(8)]
    for t in rs: t.start()
    time.sleep(0.05)
    t0 = time.perf_counter()
    try:
        with lock.write_locked(timeout=1.0):
            waited = time.perf_counter() - t0
    except LockTimeout:
        waited = float("inf")
    stop.set()
    for t in rs: t.join()
    return waited


def test_reader_preference_starves_writers() -> None:
    waits = {cls.__name__: writer_wait_under_reader_stream(cls) for cls in VARIANTS}
    print("    writer wait with 8 readers streaming: "
          + ", ".join(f"{k} {'timed out (1 s)' if v == float('inf') else f'{v*1000:.0f} ms'}" for k, v in waits.items()))
    assert waits["ReaderPreferringRWLock"] == float("inf")
    assert waits["WriterPreferringRWLock"] < 0.2 and waits["FairRWLock"] < 0.2


def test_recursive_read_deadlocks_when_writer_waits() -> None:
    for cls, expect_deadlock in ((ReaderPreferringRWLock, False), (WriterPreferringRWLock, True), (FairRWLock, True)):
        lock = cls()
        outcome = []
        writer_waiting = threading.Event()

        def nested_reader() -> None:
            with lock.read_locked():
                writer_waiting.wait(1)
                time.sleep(0.05)                          # the writer is now queued
                try:
                    with lock.read_locked(timeout=0.3):   # re-entrant read
                        outcome.append("ok")
                except LockTimeout:
                    outcome.append("deadlock")

        def writer() -> None:
            writer_waiting.set()
            try:
                with lock.write_locked(timeout=2):
                    pass
            except LockTimeout:
                pass
        a = threading.Thread(target=nested_reader); b = threading.Thread(target=writer)
        a.start(); time.sleep(0.02); b.start()
        a.join(3); b.join(3)
        assert outcome == (["deadlock"] if expect_deadlock else ["ok"]), (cls.__name__, outcome)


def test_upgrade_deadlock() -> None:
    lock = WriterPreferringRWLock()
    results, both_reading = [], threading.Barrier(2)

    def upgrader(name: str) -> None:
        lock.acquire_read()
        both_reading.wait()
        try:
            lock.acquire_write(timeout=0.3)               # needs readers == 0, including the other one
            results.append(f"{name} upgraded")
            lock.release_write()
        except LockTimeout:
            results.append(f"{name} stuck")
        lock.release_read()
    ts = [threading.Thread(target=upgrader, args=(n,)) for n in "AB"]
    for t in ts: t.start()
    for t in ts: t.join(3)
    assert sorted(results) == ["A stuck", "B stuck"]


def test_fair_order_reader_does_not_overtake_writer() -> None:
    lock, order = FairRWLock(), []
    lock.acquire_read()                                   # R0 holds the lock

    def w() -> None:
        with lock.write_locked():
            order.append("W1")

    def r() -> None:
        with lock.read_locked():
            order.append("R2")
    tw = threading.Thread(target=w); tw.start(); time.sleep(0.05)
    tr = threading.Thread(target=r); tr.start(); time.sleep(0.05)
    assert order == []                                    # R2 waits behind W1 although only readers hold the lock
    lock.release_read()
    tw.join(1); tr.join(1)
    assert order == ["W1", "R2"]


if __name__ == "__main__":
    for t in (test_mutual_exclusion_under_stress, test_readers_share, test_reader_preference_starves_writers,
              test_recursive_read_deadlocks_when_writer_waits, test_upgrade_deadlock,
              test_fair_order_reader_does_not_overtake_writer):
        t()
        print("ok ", t.__name__)

11 · Testing locks

A lock's tests fall into two groups. Safety tests check that the invariant holds under heavy, random contention: six readers and two writers loop for 0.6 seconds, each recording entry and exit in the witness, and the test asserts zero violations and that readers did overlap (a lock that serialises everything would pass the first check trivially). Liveness tests check that waiting ends when it should and reproduce the failure modes: starvation as a timeout under reader preference and a short wait under the other policies; deadlocks as timeouts on a nested read or a double upgrade, which turns a would-be hang into a fast, deterministic failure. Ordering tests use small sleeps to establish arrival order and assert who entered first. Every acquire in a test takes a timeout, so no bug can freeze the test suite.

12 · Talking through the design

"State is active readers and an active-writer flag under one condition. Readers wait while a writer is active; writers wait while anyone is inside. Release-read notifies all when the count hits zero; release-write notifies all because many readers may enter. That's reader preference, and overlapping readers starve writers forever; I reproduced it. Writer preference counts waiting writers and blocks new readers while any wait, which ends starvation but deadlocks recursive reads, as Go documents. A fair lock gives tickets in arrival order so consecutive readers share and nobody overtakes. Never upgrade: two upgraders deadlock; release, take the write lock, re-check. Every timeout path must notify, or its waiters' neighbours sleep through a free lock. And often the better design is an immutable snapshot swapped atomically, with no lock for readers at all."

13 · Edge cases

Release without acquire: the counts go negative; real implementations raise. Releasing another thread's write lock: track the owner and refuse. Exceptions inside the critical section: context managers release the lock. Recursive write locks: deadlock in these simple locks; re-entrant locks count the depth per owner. Thousands of readers: notify_all on writer release wakes them all, which is correct and briefly expensive. Timeout of zero: a try-lock. Lock used across asyncio tasks: a threading lock blocks the event loop; use an asyncio-aware design.

14 · Extensions the interviewer will ask for

Re-entrancy: track per-thread read and write counts so a holder can re-acquire. Upgradable read lock: one designated upgrader at a time. Phase-fair policy: alternate between a batch of all waiting readers and one writer, bounding both sides' waits. Try-lock and lock statistics: wait times, hold times, readers' concurrency. Sharded read-write locks: per-CPU reader counters so readers do not contend on one counter, at the cost of writers checking all shards. Async version with asyncio primitives.

15 · Complexity

Each acquire and release is O(1) for the reader- and writer-preferring locks. The fair lock's head check is O(1) and its timeout removal O(waiters). Notify_all on writer release wakes every waiter, O(waiters) context switches. Throughput is limited by the single condition lock that every reader and writer touches, which is why highly read-heavy systems move to sharded counters, seqlocks or copy-on-write. Measure before choosing: for many Python workloads a plain lock with short critical sections is simpler and just as fast, and the read-write lock earns its complexity only when readers hold the lock long enough, or wait inside it, for overlap to matter.

The three classical readers-writers problems

The textbook literature names the policies by number. The first readers-writers problem asks that no reader wait unless a writer already has the lock: reader preference, with writer starvation. The second asks that once a writer is waiting, no new reader start: writer preference, with reader starvation possible under a steady supply of writers. The third asks that no thread starve: fairness, usually by arrival order. Knowing that these are three different specifications, not three implementations of one, is the senior framing: the interviewer is asking which property you want and what you give up for it.

Why reader preference never even notifies the writer

It is worth noticing exactly how the starvation happens in the reader-preferring code. The writer waits for the predicate "no readers and no writer". Notifications happen when the reader count reaches zero or a writer releases. Under overlapping readers, neither event occurs, so the writer is not even woken to re-check; it sleeps until its timeout. A lock that notified on every reader exit would wake the writer often, only for it to find readers still inside and go back to sleep, wasting work and changing nothing. Starvation is a property of the predicate and the arrival pattern, not of how often anyone is woken.

The GIL and real parallelism

In CPython's default build only one thread executes Python bytecode at a time, so readers holding a read lock do not compute in parallel; they overlap only when they block (on I/O, sleeping) or run C code that releases the GIL. The read-write lock still matters for correctness and for overlapping waits, but its performance benefit is smaller than in Java, Go or C++. On the free-threaded build introduced in Python 3.13, readers truly run in parallel, and contention on the lock's own condition variable becomes the limiting factor.

Contention on the reader count

Every reader increments and decrements the same counter under the same lock. On many cores, that shared counter's cache line moves between processors on every read lock acquisition, which can make a read-write lock slower than a plain lock for short critical sections. High-performance implementations spread the reader count across per-CPU or per-thread slots (sometimes called big-reader locks or sharded reader counts); readers touch only their own slot, and writers must visit every slot, making writes slower and reads much cheaper. It is the same trade as everywhere in this family: optimise the frequent operation at the expense of the rare one.

Alternatives that avoid read locks entirely

Two patterns often beat read-write locks. Copy-on-write snapshots: the data is immutable; a writer builds a new version and replaces a single reference; readers take the reference and use that version without locking, possibly finishing on an old version while a new one exists. Writers serialise among themselves with an ordinary lock. In Python, assigning a reference is atomic, so a configuration object or routing table can be swapped this way trivially. The Linux kernel's read-copy-update (RCU) applies the same idea with careful rules for when old versions can be freed. Seqlocks: readers read a version counter before and after reading the data and retry if it changed; writers never wait for readers. Both make reads nearly free and push complexity onto writers, the right trade when reads vastly outnumber writes.

Why the fair lock cannot starve anyone

The fair lock's liveness argument is short and worth giving in an interview. Every request gets a ticket and joins the back of the queue. The head of the queue enters as soon as the lock's state allows it: a reader when no writer is inside, a writer when nobody is inside. Inside, every holder eventually releases (assuming critical sections finish). So the head eventually enters, the next request becomes the head, and by induction every request reaches the head after finitely many others ahead of it have been served. No later arrival can enter before it, because entry requires being the head. Starvation-freedom follows from FIFO order plus finite critical sections, the same argument that makes a ticket lock fair.

The cost of re-entrancy

Re-entrant read locks fix the recursive-read deadlock by letting a thread that already holds a read lock enter again regardless of waiting writers. To know that, the lock must track which threads hold read locks and how many times each, typically in a per-thread counter (Java keeps a thread-local hold count, with a cached fast path for the first reader). Every acquire and release then pays for a lookup and an update in that structure, and fairness weakens, because a re-entering reader overtakes queued writers. That is why Go chose not to support it and to document the prohibition instead: simpler and faster, with the burden on the programmer.

Lock ordering still applies

A read-write lock is still a lock for deadlock purposes. If thread A holds the read side of lock X and wants lock Y, while thread B holds Y and wants the write side of X, they deadlock exactly as with plain locks. The lock-ordering discipline from the scheduler case, and the next case's money transfers, applies to read-write locks too: acquire multiple locks in one global order regardless of whether each acquisition is a read or a write.

How read-write locks fail in production

The characteristic failures are liveness failures, not corrupted data. Writer starvation under read-heavy load shows up as updates that apply late or never: configuration changes that take minutes to apply under peak traffic, caches that never refresh, a background job's lock wait time growing with traffic. Recursive-read deadlocks show up as an entire service freezing when a write happens to arrive while some request is inside a nested read, typically rare, under load, and impossible to reproduce on a developer's laptop. Upgrade deadlocks look similar. All three are easier to prevent by design than to debug: choose a writer-preferring or fair lock, forbid recursive acquisition and upgrades by convention or by assertion, and add acquisition timeouts that log loudly.

The second class is performance disappointment: a read-write lock introduced to speed up reads that makes things slower, because critical sections are microseconds long and the lock's own bookkeeping dominates, or because every reader contends on one counter. Benchmarks with realistic thread counts and hold times decide, and the answer is often a plain lock or a copy-on-write snapshot.

The database version: shared and exclusive locks

Relational databases implement the same idea at the row and table level, where it matters even more because transactions hold locks for longer than most in-memory critical sections. A shared lock (taken by SELECT ... FOR SHARE in PostgreSQL) admits other shared lockers and blocks writers; an exclusive lock (SELECT ... FOR UPDATE, or any UPDATE) admits nobody. The same failure modes appear: two transactions that each hold a shared lock on a row and then try to update it deadlock exactly like two upgrading readers, which databases detect and resolve by aborting one transaction with a deadlock error. Application code that reads with FOR SHARE and later updates the same row is the database-level form of the upgrade trap.

What to measure

Wait time to acquire, separately for readers and writers, with high percentiles (starvation appears in the tail of writer waits); hold times; the number of concurrent readers (if it is usually one, the read-write lock is buying nothing); and timeouts. A thread dump during a freeze, showing threads blocked in acquire_read while one holds a read lock, identifies the recursive-read deadlock immediately.

Knobs

The policy (reader-preferring, writer-preferring, fair), timeouts, and whether to use the lock at all versus snapshots. Some libraries expose fairness as a constructor flag, as Java does, so the choice can be changed and measured without rewriting callers.

The real cases: Go's RWMutex and Java's ReentrantReadWriteLock

Two widely used standard libraries document opposite resolutions of the trade-offs in this lesson, and each documentation reads like an answer to an interview question. Go's sync.RWMutex says the lock can be held by an arbitrary number of readers or a single writer, and that if any goroutine calls Lock while the lock is held by readers, concurrent calls to RLock will block until the writer has acquired and released it, to ensure that the lock eventually becomes available to the writer. It then states the consequence: this prohibits recursive read-locking; and it adds that an RLock cannot be upgraded into a Lock, nor a Lock downgraded into an RLock. Java's ReentrantReadWriteLock offers two modes. In the default non-fair mode the order of entry is unspecified, and a continuously contended lock may indefinitely postpone one or more readers or writers but will normally have higher throughput than a fair lock. In fair mode, threads contend using an approximately arrival-order policy: on release, either the longest-waiting writer gets the write lock or, if a group of readers has waited longer than all waiting writers, that group gets the read lock, and a thread trying to acquire a fair read lock blocks if a writer is waiting. It is re-entrant, so a thread holding the write lock may also acquire the read lock, which enables downgrading; and the documentation states that upgrading from a read lock to the write lock is not possible. The three locks in this lesson's solution reproduce, in miniature, the behaviours both documents describe, including the deadlock Go warns about.

Goal: run the three locks, then break, measure and extend them. Python 3.12, standard library only.

  1. Save the full solution as rwlock.py and run it. Six tests print ok; the starvation test prints the writer's wait under each policy (a timeout for reader preference, about 10 ms for the others).
  2. Break it. In WriterPreferringRWLock.acquire_write, remove the notify_all() on the timeout path. Write a test where a writer with a short timeout gives up while readers are blocked behind it; those readers now wait until something unrelated wakes them.
  3. Break it again. Change release_write to call notify() instead of notify_all(). With five readers waiting on a writer, how many enter when it releases?
  4. Measure it. Compare throughput of a plain threading.Lock with each read-write lock for hold times of 1 µs, 100 µs and 10 ms (simulate with sleep), 8 readers and 1 writer. Where does the read-write lock start to pay?
  5. Extend it. Make the fair lock re-entrant for readers: track read-holding threads and let them bypass the queue. Check that the recursive-read test now succeeds, and think about what that does to fairness.
  6. Extend it again. Replace the lock in a toy routing-table service with a copy-on-write snapshot and compare reader latency under frequent writes.

For every change, rerun the stress test several times; it is the guard that the invariant still holds. Predict each result before running it, especially the timing experiments, and explain any surprise before moving on to the next change. Keep every acquire in the tests bounded by a timeout.

Work it out

A configuration store uses a read-write lock. Request handlers read configuration under the read lock; inside, some of them call a helper, feature_enabled(), which also takes the read lock. An admin thread updates configuration under the write lock a few times a day. The team switches from a reader-preferring lock to Go-style writer preference to fix slow updates.

(a) Why were updates slow before? (b) What can happen after the switch? (c) Give two fixes and the trade-offs.

Answer

(a) Before: writer starvation. With reader preference, a reader may enter whenever no writer is active. Under steady traffic, request handlers' read holds overlap, so the reader count rarely or never reaches zero, and the admin thread waits until traffic dips, minutes during peak hours. This lesson's test shows the extreme case: eight streaming readers kept a writer out for the full one-second timeout.

(b) After: an occasional total freeze. With writer preference, once the admin thread is waiting, new read requests block. Consider handler H holding the read lock and about to call feature_enabled(). The admin thread calls acquire_write: readers are active, so it waits and blocks new readers. H's helper calls acquire_read: a writer is waiting, so it blocks. The admin thread waits for H's outer read lock; H waits for the admin thread. Deadlock. Every other request handler now also blocks on acquire_read behind the waiting writer, so the whole service stops. It happens only when an update coincides with a nested read, a few times a day under load, which makes it look random. Go's documentation warns exactly about this: blocking readers for a waiting writer prohibits recursive read locking.

(c) Fixes. First, remove the recursion: make feature_enabled() an internal function that assumes the caller holds the lock, and a separate public wrapper that takes it; keep writer preference. Cheap and keeps updates fast, but relies on discipline; add an assertion that a thread never re-acquires (track holders in a debug mode). Second, and better for this workload, remove the lock from the read path: store configuration as an immutable object; the admin thread builds a new one and swaps the reference; handlers read the reference once per request and use that snapshot, never locking. Reads become free and can never deadlock or starve updates; the costs are that a request may run with the previous configuration for its duration, and that updates must build a complete new object. A third option, a re-entrant fair lock that lets threads already holding a read lock re-enter, works but adds per-thread bookkeeping and weakens fairness.
