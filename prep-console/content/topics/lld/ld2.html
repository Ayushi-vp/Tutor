A small company exposes an API. One customer writes a script with a bug: it retries every failure immediately, in a loop, from forty machines. Within a minute that one customer is sending 30,000 requests a second. The database behind the API saturates, every other customer's requests start timing out, and the company's status page goes red, not because the system was too small for its real users but because nothing stopped one caller from taking all of it.

A rate limiter is the component that would have stopped it. Before doing any work, the server asks the limiter "may this caller do this now?", and the limiter answers yes or no based on how much that caller has done recently. A no is cheap: the server returns an error immediately, and well-behaved clients slow down. The runaway script gets errors; everyone else carries on.

Rate limiters exist for three different reasons, and an interviewer will notice whether you ask which one applies. Protection: stop any single caller from overloading a shared service. Here the limiter must be fast and cheap, and approximate is fine. Fairness: share limited capacity between tenants so a noisy one cannot starve the others. Monetisation: a paid plan allows more than a free one, so the limit is part of the product, must be enforced accurately and must be explainable to the customer. The same algorithms serve all three, but the purpose decides how exact the count must be and what happens when the limiter itself breaks.

The coding question looks small: write a class with a method allow(). It earns its place in interviews because the obvious first version has a subtle bug, the correct versions differ in ways that matter (bursts, memory, exactness), testing anything time-based is a skill of its own, and the follow-ups lead straight into concurrency and distributed systems: what happens with many threads, with many servers, when the shared store is down.

This lesson follows the round. It clarifies requirements, names the parts and their interface, then builds four algorithms in order of sophistication: a fixed-window counter and its boundary bug, the exact sliding-window log, the sliding-window counter that Cloudflare uses, and the token bucket that AWS API Gateway and Stripe use. Then it makes the limiter per-key and thread-safe, covers edge cases and the extensions an interviewer will ask for, takes it across many servers with Redis, and ends with the response headers that make a limiter friendly to its clients.

The question that picks the algorithm

Before any code, ask: "are bursts acceptable?" Suppose a client has been quiet for an hour and then sends 50 requests in one second. Is that fine? For a public API used by humans and scripts, usually yes: real traffic is bursty (a page load fires ten requests at once), and punishing that makes the API feel broken. For a downstream system that falls over under spikes, such as a legacy database or a payment processor with a strict contract, no. The answer chooses between two families. Algorithms that allow controlled bursts (the token bucket) and algorithms that enforce a smooth rate (sliding windows, the leaky bucket).

The token bucket, the mental model to carry

Picture a bucket that holds at most 10 tokens. A tap drips tokens into it at 2 per second; when the bucket is full, extra drips overflow and are lost. Each request must take one token out. If there is a token, the request proceeds; if the bucket is empty, the request is rejected (or told when to come back). Two numbers describe it completely. The refill rate (2 per second) sets the long-run sustained throughput: over a long time, nobody can average more than 2 requests per second. The capacity (10) sets the largest burst: a client who has been idle can spend up to 10 tokens at once. Those are independent knobs, which is exactly what most APIs want to say: "100 per minute on average, but never more than 10 at once".

Lazy refill: no background thread

A beginner's instinct is a timer that adds tokens to every bucket every second. With a million clients that is a million updates a second for buckets nobody is using. The standard trick is to compute refill lazily. Store two numbers per bucket: how many tokens it had, and when that was. When a request arrives, compute the elapsed time, add elapsed × rate, cap at capacity, then decide. An idle bucket costs nothing, and the answer is exactly what the timer would have produced. The same idea, storing a timestamp and computing state on demand, recurs in TTL caches and timeouts later in this family.

Windows, the other family

A fixed window counts requests per calendar minute and resets at each minute boundary. It is the first thing anyone writes, and it has a bug the interviewer is waiting for you to find: the boundary. A sliding-window log fixes the bug exactly by remembering every request's time. A sliding-window counter fixes it approximately with only two counters. The body builds all three so you can see each problem cause the next design.

Rejecting is a feature, not a failure

Beginners sometimes treat a rejection as the limiter failing. It is the opposite: a fast, cheap rejection with a clear "try again in 0.5 seconds" is the service working as designed. The alternative to rejecting excess load is not serving it; it is serving everyone slowly, then timing out, which wastes the work already done and makes clients retry even harder. A limiter turns an overload that would hurt everyone into an error that affects only the caller who exceeded its budget, and tells that caller exactly how to recover.

Where the analogy breaks

A real bucket holds whole objects; a token bucket holds a real number, so after 0.3 seconds at 2 per second it holds 0.6 of a token. That is fine and in fact necessary: rounding refills to whole tokens would lose fractions on every request and slowly undercount. Requests can also cost more than one token, which lets one bucket limit by work done (bytes, database rows, LLM tokens) rather than by request count.

What the round expects you to produce

A Limiter interface with one method, try_acquire(cost), returning a small result: allowed or not, how much is left, and when to retry. Two or more implementations behind it. A per-key front end so each API key gets its own limiter. Tests that use a fake clock. And a clear spoken plan for the distributed version. The body walks through each piece in that order.

1 · Clarify the requirements

Ask, and write down the answers. What is limited, and per what key: per API key, per user, per IP address, per endpoint? What is the limit, and over what window: 100 per minute, 10 per second? Are bursts acceptable, and how large? Does every request cost the same, or do some cost more? Single process or many servers? Must it be thread-safe? What should a rejected caller receive: an error now, or a wait? How exact must it be: is 1 percent over the limit acceptable for a few seconds? What happens if the limiter's own storage fails?

A typical agreed scope for the coding part: per-key limits, in-process, thread-safe, a configurable algorithm, requests may carry a cost, reject immediately with a retry hint. The distributed version is discussed, not coded. Say the non-functional targets aloud as well: the check must be O(1) per request and must not allocate unbounded memory per key, because a limiter that is slower than the request it guards, or that grows forever, has failed at its job.

2 · Entities and responsibilities

Four pieces. A Limiter is one rate-limit state machine for one key: given a cost, it decides. A Decision is the immutable answer: allowed, remaining, retry-after. A clock is a function returning the current time in seconds; injecting it is what makes everything testable. A KeyedRateLimiter owns the map from key to limiter, creates limiters on first use, makes each decision atomic under concurrency, and forgets idle keys. Keeping the algorithm (Limiter) separate from the bookkeeping (KeyedRateLimiter) means you can swap algorithms without touching the concurrency code, and test each algorithm single-threaded.

3 · The interface

Python's typing.Protocol describes the interface by shape: any class with a matching try_acquire method satisfies it, with no inheritance needed. The Decision is a frozen dataclass, an immutable record, so callers cannot accidentally modify a result they were handed. Returning a Decision rather than a bare boolean pays off immediately: the HTTP layer needs retry_after for its header, and dashboards want remaining.

4 · Stage one: a fixed-window counter

The simplest limiter. Divide time into windows of, say, 60 seconds, numbered by floor(now / 60). Keep the current window's number and a count. On each request, if the window number changed, reset the count to zero; then allow if count + cost <= limit. It is O(1) in time and memory, easy to make atomic, and maps directly onto Redis's INCR plus EXPIRE.

class FixedWindow:
    def __init__(self, limit, window, clock):
        self.limit, self.window, self.clock = limit, window, clock
        self.window_id, self.count = None, 0

    def try_acquire(self, cost=1):
        now = self.clock()
        wid = math.floor(now / self.window)
        if wid != self.window_id:
            self.window_id, self.count = wid, 0
        if self.count + cost <= self.limit:
            self.count += cost
            return Decision(True, self.limit - self.count, 0.0)
        return Decision(False, self.limit - self.count, (wid + 1) * self.window - now)

Now find the bug. Limit 100 per 60 seconds. A client sends 100 requests at t = 59.9, all allowed because window 0 has room. At t = 60.1, a new window starts and the count resets; the client sends 100 more, all allowed. That is 200 requests in 0.2 seconds, twice the limit, and the limiter never broke its own rule. The test test_fixed_window_boundary_burst in the full solution demonstrates exactly this. For protection against overload that may be tolerable, since the long-run average is still bounded; for a contract that says "never more than 100 in any 60 seconds" it is wrong.

5 · Stage two: the sliding-window log, exact but costly

To enforce "no more than N in any trailing window", remember when each accepted request happened. Keep a deque of timestamps. On each request, pop timestamps from the left while they are older than now - window; then allow if the deque's length plus the cost is within the limit, and append the current time once per unit of cost. The answer is exact: the deque is literally the list of accepted requests in the last 60 seconds.

The retry hint is exact too. If the deque is full, the request can succeed once enough of the oldest entries slide out; for cost 1 that is when the oldest timestamp turns window seconds old, so retry_after = log[0] + window - now. In the boundary scenario above, after 100 requests at 59.9 seconds, a request at 60.1 is rejected with a retry of 59.8 seconds. The cost is memory: one float per accepted request per key. A limit of 10,000 per hour for a million keys is billions of floats. That is why the log is used for low limits or audit-grade enforcement, not for everything.

6 · Stage three: the sliding-window counter, O(1) and nearly exact

Keep only two counters per key: the count in the current fixed window and the count in the previous one. To estimate how many requests fell in the trailing window, assume the previous window's requests were spread evenly. If you are elapsed seconds into the current window, the trailing window still covers window - elapsed seconds of the previous one, so estimate prev × (window - elapsed) / window + curr. When a new window begins, the current count becomes the previous one; if two or more windows passed with no traffic, both reset to zero. This is the code's _roll method.

Cloudflare's write-up gives a worked example, reproduced as a test in the full solution: 42 requests in the previous minute, 18 so far in this one, 15 seconds in. The estimate is 42 × 0.75 + 18 = 49.5. With a limit of 50, one more request would push it over. The estimate is wrong only when the previous window's traffic was bunched at one end; Cloudflare measured it across 400 million requests from 270,000 sources and found 0.003 percent of decisions wrong, with the estimated rate on average 6 percent from the real one. That is the trade the industry usually takes: constant memory, two integers per key, and an error that is small and bounded.

7 · Stage four: the token bucket

The token bucket is the most common answer and the one to have fluent. State: tokens (a float) and last (the time of the last update). Start full, so a new client may burst immediately. On each request: compute elapsed = now - last, add elapsed × rate, cap at capacity, set last = now. If tokens >= cost, subtract and allow; otherwise reject with retry_after = (cost - tokens) / rate, the time until enough tokens will have dripped in. Two guard rails: clamp elapsed at zero, so a clock that misbehaves never refills backwards; and reject a cost greater than capacity up front, because such a request can never succeed and would otherwise get a misleading retry hint forever.

Trace it with rate 2 per second and capacity 10. A client idle for 30 seconds would earn 60 tokens, but the cap holds it at 10. It sends 15 requests at once: 10 succeed; the 11th sees 0 tokens and gets a retry hint of 0.5 seconds. After another 2.5 seconds, 5 tokens have dripped in, and 5 more succeed. These exact numbers are the first test in the full solution.

A leaky bucket is the mirror image: requests go into a queue and leave it at a fixed rate, so the output is smooth even when the input is bursty. Used as a meter (reject when the queue would overflow) it makes the same decisions as a token bucket; used as a queue it adds delay instead of rejecting. Choose it when the thing downstream cannot take a burst at all, such as an SMS gateway with a strict per-second contract.

8 · Per-key limiting and thread safety

Real limiters hold one state per key. KeyedRateLimiter keeps a dict from key to a tuple of the limiter, a lock, and a last-seen time. The race to prevent is the classic check-then-act: two threads both read "one token left", both decide "allow", and both subtract. The fix is to hold that key's lock around the whole try_acquire, making check and update a single step. A separate short lock guards the dict itself while creating a new entry, so two threads seeing a new key at the same moment do not create two limiters, one of which would be lost.

Why a lock per key rather than one lock for everything? Because unrelated tenants should not wait for each other. This is the sharding idea from the LRU case taken to its limit: one lock per key. The stress test in the solution starts 16 threads behind a threading.Barrier (so they all start at the same moment) and makes 800 attempts against a bucket of 100 tokens that effectively never refills; exactly 100 must be granted, and they are.

Keys must also be forgotten. Every IP address that ever touched the service would otherwise stay in the dict forever. sweep() deletes keys whose last-seen time is older than an idle TTL. This is safe for a token bucket because a key idle long enough has a full bucket, which is exactly what a freshly created limiter has, so forgetting it changes no decision.

9 · The full solution

The file below contains all four algorithms, the keyed front end, a header helper and seven tests, including the Cloudflare example, the boundary burst and the 16-thread stress test. It runs on Python 3.12 with the standard library; all tests pass. Notice that the tests never sleep: they construct a FakeClock, pass it in, and move it forward.

"""Rate limiters: fixed window, sliding-window log, sliding-window counter, token bucket,
plus a per-key, thread-safe front end. Python 3.12, standard library only.
Run: python ratelimit.py"""
from __future__ import annotations

import math
import threading
import time
from collections import deque
from dataclasses import dataclass
from typing import Callable, Protocol

Clock = Callable[[], float]


@dataclass(frozen=True)
class Decision:
    allowed: bool
    remaining: int          # whole requests still allowed right now
    retry_after: float      # seconds until a rejected request could succeed (0 if allowed)


class Limiter(Protocol):
    def try_acquire(self, cost: int = 1) -> Decision: ...


class FixedWindow:
    """One counter per window of `window` seconds. Simple; allows 2x limit across a boundary."""

    def __init__(self, limit: int, window: float, clock: Clock) -> None:
        self.limit, self.window, self.clock = limit, window, clock
        self.window_id, self.count = None, 0

    def try_acquire(self, cost: int = 1) -> Decision:
        now = self.clock()
        wid = math.floor(now / self.window)
        if wid != self.window_id:                       # a new window: reset the counter
            self.window_id, self.count = wid, 0
        if self.count + cost <= self.limit:
            self.count += cost
            return Decision(True, self.limit - self.count, 0.0)
        return Decision(False, self.limit - self.count, (wid + 1) * self.window - now)


class SlidingWindowLog:
    """Exact: keep the timestamp of every accepted request in the trailing window. O(limit) memory."""

    def __init__(self, limit: int, window: float, clock: Clock) -> None:
        self.limit, self.window, self.clock = limit, window, clock
        self.log: deque[float] = deque()

    def try_acquire(self, cost: int = 1) -> Decision:
        now = self.clock()
        while self.log and self.log[0] <= now - self.window:   # drop entries that slid out
            self.log.popleft()
        if len(self.log) + cost <= self.limit:
            self.log.extend([now] * cost)
            return Decision(True, self.limit - len(self.log), 0.0)
        # the oldest needed entry must slide out before `cost` slots are free
        needed = len(self.log) + cost - self.limit
        return Decision(False, self.limit - len(self.log), self.log[needed - 1] + self.window - now)


class SlidingWindowCounter:
    """Two fixed-window counters; estimate = current + previous * (unexpired share of previous)."""

    def __init__(self, limit: int, window: float, clock: Clock) -> None:
        self.limit, self.window, self.clock = limit, window, clock
        self.window_id, self.curr, self.prev = None, 0, 0

    def _roll(self, now: float) -> float:
        wid = math.floor(now / self.window)
        if self.window_id is None or wid > self.window_id + 1:
            self.prev, self.curr = 0, 0                     # idle for 2+ windows
        elif wid == self.window_id + 1:
            self.prev, self.curr = self.curr, 0
        self.window_id = wid
        elapsed = now - wid * self.window
        return self.prev * (self.window - elapsed) / self.window + self.curr

    def try_acquire(self, cost: int = 1) -> Decision:
        now = self.clock()
        estimate = self._roll(now)
        if estimate + cost <= self.limit:
            self.curr += cost
            return Decision(True, int(self.limit - estimate - cost), 0.0)
        return Decision(False, max(0, int(self.limit - estimate)), self.window / max(self.limit, 1))


class TokenBucket:
    """Refill `rate` tokens/second up to `capacity`; each request spends `cost` tokens.
    Refill is computed lazily from elapsed time: no background thread."""

    def __init__(self, rate: float, capacity: float, clock: Clock) -> None:
        if rate <= 0 or capacity <= 0:
            raise ValueError("rate and capacity must be positive")
        self.rate, self.capacity, self.clock = rate, capacity, clock
        self.tokens, self.last = capacity, clock()          # start full: allow an initial burst

    def _refill(self, now: float) -> None:
        elapsed = max(0.0, now - self.last)                  # never refill backwards
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last = now

    def try_acquire(self, cost: int = 1) -> Decision:
        if cost > self.capacity:
            raise ValueError("cost exceeds bucket capacity: can never succeed")
        now = self.clock()
        self._refill(now)
        if self.tokens >= cost:
            self.tokens -= cost
            return Decision(True, int(self.tokens), 0.0)
        return Decision(False, int(self.tokens), (cost - self.tokens) / self.rate)


class KeyedRateLimiter:
    """One limiter per key (API key, user, IP), created on first use, dropped when idle.
    A lock per key keeps check-and-update atomic; a short global lock guards the dict."""

    def __init__(self, factory: Callable[[], Limiter], clock: Clock, idle_ttl: float = 600.0) -> None:
        self.factory, self.clock, self.idle_ttl = factory, clock, idle_ttl
        self._entries: dict[str, tuple[Limiter, threading.Lock, list[float]]] = {}
        self._dict_lock = threading.Lock()

    def try_acquire(self, key: str, cost: int = 1) -> Decision:
        with self._dict_lock:
            entry = self._entries.get(key)
            if entry is None:
                entry = self._entries[key] = (self.factory(), threading.Lock(), [0.0])
        limiter, lock, last_seen = entry
        with lock:                                          # check-and-update as one step
            last_seen[0] = self.clock()
            return limiter.try_acquire(cost)

    def sweep(self) -> int:
        """Forget keys idle longer than idle_ttl (a full token bucket is the same as no bucket)."""
        cutoff = self.clock() - self.idle_ttl
        with self._dict_lock:
            stale = [k for k, (_, _, seen) in self._entries.items() if seen[0] < cutoff]
            for k in stale:
                del self._entries[k]
        return len(stale)


def headers(policy: str, limit: int, window: int, d: Decision) -> dict[str, str]:
    """Response headers in the style of the IETF RateLimit draft, plus Retry-After on 429."""
    h = {"RateLimit-Policy": f'"{policy}";q={limit};w={window}',
         "RateLimit": f'"{policy}";r={d.remaining};t={math.ceil(d.retry_after)}'}
    if not d.allowed:
        h["Retry-After"] = str(max(1, math.ceil(d.retry_after)))
    return h


# ---------------------------------------------------------------- tests
class FakeClock:
    def __init__(self, t: float = 0.0) -> None:
        self.t = t

    def __call__(self) -> float:
        return self.t

    def advance(self, dt: float) -> None:
        self.t += dt


def test_token_bucket_burst_then_refill() -> None:
    clk = FakeClock()
    tb = TokenBucket(rate=2, capacity=10, clock=clk)
    clk.advance(30)                                         # idle: still capped at 10, not 60
    results = [tb.try_acquire().allowed for _ in range(15)]
    assert results.count(True) == 10
    d = tb.try_acquire()
    assert not d.allowed and math.isclose(d.retry_after, 0.5)
    clk.advance(2.5)                                        # 5 more tokens
    assert sum(tb.try_acquire().allowed for _ in range(6)) == 5


def test_fixed_window_boundary_burst() -> None:
    clk = FakeClock(59.9)
    fw = FixedWindow(limit=100, window=60, clock=clk)
    a = sum(fw.try_acquire().allowed for _ in range(100))
    clk.advance(0.2)                                        # t = 60.1, a new window
    b = sum(fw.try_acquire().allowed for _ in range(100))
    assert a + b == 200                                     # 2x the limit in 0.2 seconds


def test_sliding_log_is_exact() -> None:
    clk = FakeClock(59.9)
    log = SlidingWindowLog(limit=100, window=60, clock=clk)
    assert sum(log.try_acquire().allowed for _ in range(100)) == 100
    clk.advance(0.2)
    d = log.try_acquire()
    assert not d.allowed and math.isclose(d.retry_after, 59.8)


def test_sliding_counter_matches_cloudflare_example() -> None:
    # Cloudflare's post: 42 requests in the previous minute, 18 so far, 15 s into this minute
    clk = FakeClock(0)
    sw = SlidingWindowCounter(limit=1000, window=60, clock=clk)   # generous while filling
    for _ in range(42):
        sw.try_acquire()
    clk.t = 60
    for _ in range(18):
        sw.try_acquire()
    clk.t = 75
    sw.limit = 50                                           # now apply the real limit
    assert math.isclose(sw._roll(clk()), 42 * 0.75 + 18)   # 49.5
    assert sw.try_acquire().allowed is False                # 49.5 + 1 > 50


def test_keyed_limiter_threads_never_overspend() -> None:
    clk = FakeClock()
    rl = KeyedRateLimiter(lambda: TokenBucket(rate=1e-9, capacity=100, clock=clk), clk)
    allowed = [0]
    count_lock = threading.Lock()
    start = threading.Barrier(16)

    def hammer() -> None:
        start.wait()
        for _ in range(50):
            if rl.try_acquire("tenant-1").allowed:
                with count_lock:
                    allowed[0] += 1
    ts = [threading.Thread(target=hammer) for _ in range(16)]
    for t in ts: t.start()
    for t in ts: t.join()
    assert allowed[0] == 100, allowed[0]                    # 800 attempts, exactly capacity granted


def test_idle_keys_are_swept_and_headers() -> None:
    clk = FakeClock()
    rl = KeyedRateLimiter(lambda: TokenBucket(rate=1, capacity=5, clock=clk), clk, idle_ttl=60)
    for k in ("a", "b", "c"):
        rl.try_acquire(k)
    clk.advance(61)
    rl.try_acquire("a")
    assert rl.sweep() == 2 and set(rl._entries) == {"a"}
    tb = TokenBucket(rate=1, capacity=1, clock=clk)
    tb.try_acquire()
    h = headers("default", 1, 1, tb.try_acquire())
    assert h["Retry-After"] == "1" and h["RateLimit"] == '"default";r=0;t=1'


def test_real_clock_smoke() -> None:
    tb = TokenBucket(rate=1000, capacity=5, clock=time.monotonic)
    assert sum(tb.try_acquire().allowed for _ in range(5)) == 5


if __name__ == "__main__":
    for t in (test_token_bucket_burst_then_refill, test_fixed_window_boundary_burst,
              test_sliding_log_is_exact, test_sliding_counter_matches_cloudflare_example,
              test_keyed_limiter_threads_never_overspend, test_idle_keys_are_swept_and_headers,
              test_real_clock_smoke):
        t()
        print("ok ", t.__name__)

10 · Edge cases

Go through these aloud. Clock going backwards: wall-clock time is adjusted by time synchronisation (NTP, the network time protocol) and can jump; use time.monotonic() and clamp elapsed at zero anyway. Cost greater than capacity: reject with a clear error. Very low rates such as 1 per hour: the retry hint is up to 3,600 seconds and the float arithmetic is fine. Very high rates such as 100,000 per second: refill per request is tiny, and float precision is still ample, but the lock becomes the bottleneck long before the arithmetic does. Fractional tokens: keep them; rounding down on each refill loses tokens systematically. First request: decide whether a new bucket starts full (allow an initial burst, the usual choice) or empty. Zero or negative configuration: reject in the constructor. Key cardinality: a flood of spoofed or rotating keys can grow the dict; sweep it and cap its size.

11 · Testing time-based code

Tests that call time.sleep are slow and flaky: a loaded CI machine sleeps longer than asked, and the refill you expected has become two refills. Inject the clock instead. FakeClock is three lines: it stores a float, returns it when called, and has advance(dt). A refill test then reads like a specification: advance 2.5 seconds, expect exactly 5 more successes. The same technique, a controllable collaborator passed in rather than reached for, is dependency injection from the SWE track, and it recurs in every time-based case later in this family.

12 · Taking it distributed

With twenty application servers behind a load balancer, twenty in-process limiters each allow the full limit, so a client spread across them gets twenty times its quota. The state must be shared. The usual store is Redis, an in-memory key-value server. The naive version reads the bucket, computes in the application, and writes it back, and it races exactly like the threads did: two servers read "one token", both allow. The fix is to run the whole read-decide-write inside Redis as a Lua script; Redis executes a script to completion without running any other command in between, so it is atomic. A sketch of the script:

-- KEYS[1] = bucket key; ARGV = rate, capacity, cost
local t = redis.call('TIME')                       -- Redis's clock, not the app server's
local now = tonumber(t[1]) + tonumber(t[2]) / 1e6
local b = redis.call('HMGET', KEYS[1], 'tokens', 'last')
local rate, cap, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local tokens = tonumber(b[1]) or cap
local last = tonumber(b[2]) or now
tokens = math.min(cap, tokens + math.max(0, now - last) * rate)
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'last', now)
redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate) * 2)  -- idle keys vanish
return {allowed and 1 or 0, tostring(tokens)}

Three details earn credit. Using Redis's TIME inside the script gives every server one clock, so servers whose clocks disagree cannot mint or destroy tokens. The EXPIRE does the idle sweep for free. And the script is the same algorithm as the Python class, which is the point: the algorithm does not change when it goes distributed; only where the state lives and how updates are made atomic.

13 · Extensions the interviewer will ask for

Cost-based limits: pass a cost per request (bytes, rows, LLM tokens). Multiple limits: a per-second and a per-day limit together; check both and only spend from either if both allow, or the per-second bucket is drained by requests the daily one rejects. Hierarchies: per IP for anonymous callers, per API key, and per (key, endpoint class) for expensive endpoints; check the cheapest and most specific first and stop at the first rejection. Waiting instead of rejecting: return the retry hint and let the caller sleep, or offer an acquire(timeout) that blocks, which turns the limiter into a pacer for outbound calls to someone else's API. Concurrency limits: "at most 20 requests in flight" is a different control, a counting semaphore incremented on start and decremented on finish, and Stripe runs it alongside its rate limiter.

15 · Complexity

Fixed window, sliding-window counter and token bucket are O(1) time and O(1) memory per key: two or three numbers. The sliding-window log is O(1) amortised time per request (each timestamp is appended once and popped once) but O(limit) memory per key. The keyed front end adds one dict lookup and one lock acquisition per request, and O(active keys) memory, bounded by the idle sweep.

GCRA: the token bucket in one number

The generic cell rate algorithm (GCRA), from telecom traffic shaping, enforces exactly the token bucket's policy while storing a single value per key: the theoretical arrival time (TAT), the time at which the next request would arrive if the client sent at exactly the allowed rate. Let the emission interval be T = 1 / rate and the burst tolerance τ = T × (capacity - 1). A request at time now is allowed if TAT - now <= τ; if so, set TAT = max(TAT, now) + T. Intuitively, TAT runs ahead of real time by one interval per recent request, and the bucket is "empty" when it has run ahead by more than the burst allows. One number per key means a smaller, simpler atomic update, which is why the redis-cell module implements GCRA. Being able to derive it from the token bucket is a strong senior signal.

Why the sliding-window counter's error is small in practice

The estimate is wrong only when the previous window's requests were unevenly distributed and the current total is close to the limit. Clients far below the limit are never affected, and clients far above it are rejected either way. Only the narrow band near the threshold sees errors, and an error there means allowing or rejecting a request that was within a few percent of the line. Cloudflare's numbers (0.003 percent wrong decisions, and the few false negatives were clients less than 15 percent over the threshold) reflect exactly that. When exactness matters more than memory, for example a billing quota, use the log or a per-second sub-window counter.

Leasing tokens to remove the network hop

A Redis round trip inside the datacentre costs perhaps half a millisecond to a millisecond, and the limiter is on every request. At high request rates that is a real share of the latency budget and a real load on Redis. The standard mitigation is a lease: each server takes a block of, say, 100 tokens from the shared bucket in one call, and spends them from a local in-process bucket. Only one request in a hundred touches Redis. The cost is accuracy: in the worst case each of N servers holds an unspent lease, so a client can briefly exceed the limit by up to N times the lease size, and tokens leased to an idle server are temporarily unavailable to busy ones. Size the lease against both: small enough that the overshoot is acceptable, large enough that Redis traffic falls meaningfully. Returning unspent tokens on graceful shutdown limits the waste.

Fail open, fail closed, and the backstop

When Redis is unreachable, the limiter cannot know the shared state. Failing open (allow everything) keeps the product working but removes protection at the moment the system is already in trouble, since the cause of a Redis outage is often overload. Failing closed (reject everything) protects the backend but turns a limiter outage into a full outage. Mature designs fail open to a local backstop: each server enforces a conservative in-process limit, such as the global limit divided by the number of servers, so protection degrades rather than disappears, and an alert fires. For a monetisation quota the answer flips toward failing closed or using a cached allowance, because giving the paid product away is a business failure. The point to make in the interview is that the answer depends on the purpose you clarified at the start.

Clocks, skew and monotonicity

Every algorithm here depends on elapsed time. Inside one process, use a monotonic clock: time.time() reports wall-clock time, which the operating system adjusts, sometimes backwards, when synchronising with a time server, and a backwards jump makes elapsed negative. Across servers, the problem is skew: two machines' clocks differ by milliseconds or more, and if server A refills using its clock and server B using its own, tokens appear or disappear. Using one authority (Redis's TIME in the script) removes the disagreement. This is a general lesson for distributed design: when several machines must agree about time, pick one clock, or design so that agreement is not needed.

Fairness, priorities and the noisy neighbour

A per-key limiter stops one key from exceeding its own budget, but it does not by itself keep the total within the system's capacity: 10,000 tenants each within their limit can still overload the backend. Two further controls handle that. A global limiter or concurrency cap bounds the total. And load shedding, as Stripe describes, rejects low-priority work first when the fleet is busy, for example by reserving a fraction of capacity for critical endpoints such as creating charges and shedding non-critical ones such as listing them. Weighted fair queuing goes further and gives each tenant a share of capacity proportional to a weight, which is how multi-tenant inference platforms share GPUs between customers.

Cost-based limiting for AI products

LLM APIs limit by tokens per minute as well as requests per minute, because one request with a 100,000-token prompt costs far more than one with 200. The cost is not fully known in advance: output length depends on the model. The usual approach is to charge the bucket an estimate up front (prompt tokens plus the requested maximum output) and reconcile when the response completes, refunding unused tokens. That means a bucket can briefly hold less than zero after reconciliation, and you must decide whether a negative balance blocks the next request until it recovers, which is the fair choice, or is forgiven.

How rate limiters fail in production

The first failure mode is the limiter becoming the outage. Every request touches it, so a slow Redis, a hot key (one huge tenant whose bucket all servers hammer) or a lock held too long adds latency to everything. Watch the limiter's own latency percentiles and its error rate as first-class metrics. Hot keys are handled with leases or by splitting one tenant's budget across several sub-keys that are summed approximately.

The second is retry storms. A client that receives 429 and immediately retries makes the problem worse; thousands of such clients turn a brief overload into a sustained one. The server's part of the fix is a precise Retry-After (the token bucket knows exactly when the next token arrives) and quota headers on every response, so clients can pace themselves before they are rejected. The client's part, covered in the resilient-client case later in this family, is exponential backoff with jitter.

The third is misattributed keys. Limiting by IP address punishes everyone behind one corporate proxy or carrier network address translation, where thousands of phones share a single public IP, and is trivially bypassed by attackers who rotate addresses. Limiting by API key is precise for authenticated traffic. Most systems combine them: per-key limits for authenticated callers, generous per-IP limits plus other abuse signals for anonymous ones.

What to measure

Per limit: requests allowed and rejected, broken down by key class or tier, and the top rejected keys. A sudden rise in rejections for many keys at once usually means a misconfiguration or a bad deploy of a client library, not abuse. A single key with a high rejection rate is a runaway client, and a short message to that customer is often the best fix. Also measure the limiter's decision latency, its store's latency and error rate, and, for leased designs, how often leases are refreshed and how many tokens expire unspent.

Knobs and how they are tuned

Rate and capacity are set from observed traffic: take the distribution of per-key request rates and set the limit well above the normal heavy user, so that only genuine runaways are throttled. Capacity is set from real burst sizes, for example the number of requests a client library fires at startup. Limits per endpoint class reflect cost: a search or export endpoint gets a much smaller budget than a cheap read. All of this is configuration, ideally per tier and changeable without a deploy.

Rolling out a new limit safely

Turning on a new or stricter limit is a production change with real blast radius: set it too low and you reject paying customers' legitimate traffic. The standard practice is a shadow mode (also called dry run): the limiter makes its decision and records it in metrics and logs, but the request proceeds regardless. After a few days of real traffic you can see exactly which keys would have been rejected and how often, contact the customers who would be affected, and adjust limits before enforcing. Stripe's post gives the same advice: dark launch each limiter to watch the traffic it would block, and put limiters behind feature flags (kill switches) so a human can turn one off quickly if it starts rejecting the wrong traffic. Once enforcing, change limits gradually and watch the rejection rate per tier; a step change in rejections right after a limit change is a configuration mistake until proven otherwise.

The real case: a token bucket in AWS API Gateway

Amazon API Gateway's documentation describes its throttling in exactly this lesson's terms. It "throttles requests to your API using the token bucket algorithm, where a token counts for a request", examining a steady-state rate and a burst, and returns 429 Too Many Requests when both are exceeded. The burst is described as the maximum bucket size. The default account-level quota per Region is 10,000 requests per second with a burst capacity provided by the token bucket of 5,000 requests. Limits apply in a hierarchy: per-client or per-method limits in a usage plan first, then per-method limits for a stage, then the account level, then AWS's Regional limits. The documentation also warns that throttles are applied on a best-effort basis and should be treated as targets rather than guaranteed ceilings, which is the distributed-accuracy trade-off from the deep section stated plainly by a vendor. Stripe's engineering post describes the same algorithm from the inside: a token bucket per user held in Redis, alongside a concurrency limiter and two load shedders, with the request-rate limiter rejecting millions of requests a month, mostly from scripts that had gotten out of hand.

Work it out

A sliding-window-counter limiter allows 100 requests per minute. At 12:00:45 a client asks for permission. The 11:59–12:00 window recorded 90 requests; the 12:00–12:01 window so far has 42.

(a) Is the request allowed? (b) A fixed-window limiter with the same limit: what is the worst burst a client can achieve, and when? (c) Your token bucket has rate 2/s, capacity 10. A client idle for 30 seconds sends 15 requests instantly. How many succeed, and how long until the 15th?

Answer

(a) The estimate weights the previous window by the fraction of it still inside the trailing 60 seconds. At 45 seconds into the current minute, 15 seconds (25 percent) of the previous window remains in view. Estimated count = 42 + 90 × 0.25 = 42 + 22.5 = 64.5. Adding this request gives 65.5, below 100, so it is allowed.

Name the approximation: this assumes the 90 requests were spread evenly through the previous minute. If they all came in its last 15 seconds, the true trailing count is 132 and the request should be denied. The error is bounded and rare in practice (Cloudflare measured 0.003 percent of decisions), which is why the algorithm is the standard compromise, but present it as an estimate.

(b) Fixed window worst case: 200 requests in a fraction of a second: 100 at 11:59:59.9 and 100 at 12:00:00.1. Each window respects its own limit; the client gets twice the intended rate across the boundary. That is the whole reason sliding windows exist.

(c) Token bucket. Thirty idle seconds would add 60 tokens, but the capacity caps it at 10. The burst of 15 gets 10 immediately; the other 5 must wait for refill at 2 per second, one every 0.5 seconds: 0.5, 1.0, 1.5, 2.0 and 2.5 seconds for the 15th, assuming the client retries at the hinted times.

The design point: capacity and rate are independent controls. If a 10-request burst is too generous, lower the capacity without touching the sustained rate; if sustained throughput is too low, raise the rate without changing burst tolerance. A window algorithm folds both into one number and cannot express "100 per minute sustained but never more than 10 at once", which is what most APIs actually want.
