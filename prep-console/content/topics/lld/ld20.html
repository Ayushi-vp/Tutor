A fintech start-up's ledger service moves money between customer accounts. The first version updates balances without locks, and the nightly reconciliation finds that the sum of all balances no longer matches the money held at the bank: a few cents here, a few euros there, more on busy days. Someone adds a lock to each account and has each transfer lock the source, then the destination. Reconciliation is clean for a week. Then, at the monthly payroll run, the service freezes. Two employees were paying each other back at the same moment, Alice to Bob and Bob to Alice; each transfer took its first lock and waited for the second, which the other transfer held. Every later request that touched either account queued behind them, and the service stopped.

The money-transfer problem is the canonical deadlock question because it is so small. Two accounts, two locks, two threads, and the obvious code is wrong in two different ways: without locks it loses updates, and with locks taken in the natural order it deadlocks. The fix is one line, take the locks in a global order, usually by account id, and the interviewer wants to hear why that line works, not just that it does.

The answer has a formal shape worth knowing. A deadlock requires four conditions at once: resources are exclusive, threads hold resources while waiting for others, resources cannot be taken away, and the waits form a cycle. Lock ordering breaks the cycle; try-lock with backoff breaks hold-and-wait; databases break no-preemption by aborting one transaction. Each real system picks one of these, and knowing which one a system uses explains how it fails.

Databases face the same problem with row locks, and PostgreSQL's documentation uses almost exactly this example: two transactions updating account rows 11111 and 22222 in opposite orders. PostgreSQL detects the cycle and aborts one transaction, and the documentation's advice is the same as this lesson's: acquire locks on multiple objects in a consistent order. That makes the interview question directly practical.

It is also unforgiving in the way money is: a bug that loses one cent in a million transfers is invisible in testing and costly in an audit, so the tests here check exact conservation over tens of thousands of concurrent transfers rather than a handful of examples.

This lesson, the last in the machine-coding family, follows the round: clarify the requirements, define the invariant, show the lost update and the deadlock with line-by-line traces and deterministic reproductions, fix them with lock ordering and prove it, add try-lock with backoff as an alternative and discuss livelock, handle self-transfers, insufficient funds and retried requests, and connect to how databases detect deadlocks with wait-for graphs and how transfers work across shards.

What a transfer must guarantee

A transfer moves an amount from one account to another. Three properties must hold whatever other transfers run at the same time. Atomicity: the debit and the credit happen together or not at all, so no observer ever sees money that has left one account but not arrived in the other. Conservation: the total of all balances never changes, because transfers only move money; this is the invariant to test. No overdraft: the source must have enough at the moment of the debit, which means the funds check must happen inside the same critical section as the debit. Amounts are integer cents, as in the expense-sharing case, so the arithmetic is exact.

Lost updates

Without locks, the statement src.balance -= amount is three steps: read the balance, compute the new value, write it back. If two threads run it on the same account at once, both can read the same old balance, and the second write overwrites the first. One debit disappears, and money is created; the mirror case on a credit destroys money. Python's global interpreter lock does not prevent this, because the interpreter can switch threads between the read and the write. The solution's unsynchronised bank, run with eight threads making random transfers among four accounts that start with 400.00 in total, ended with totals such as 388.90, 430.62 and 376.79.

Deadlock, and the four conditions

Adding a lock per account fixes lost updates but introduces deadlock: a set of threads each holding a resource and waiting for a resource held by another in the set. It requires four conditions simultaneously, often called the Coffman conditions. Mutual exclusion: a lock can be held by one thread at a time. Hold and wait: a thread holds one lock while waiting for another. No preemption: a lock cannot be taken from its holder. Circular wait: there is a cycle of threads each waiting for the next. Break any one and deadlock is impossible.

Why this question closes the family

Earlier cases in this family each used one concurrency tool: a lock around an LRU cache, conditions in a blocking queue, a lock making submit and shutdown atomic, a reservation in a connection pool, a policy for readers and writers, sorted locks in a scheduler. Money transfer puts the hardest property, deadlock freedom across several locks, at the centre, and asks for a proof rather than a test. It is where interviewers check whether a candidate can reason about all interleavings, not just run a few.

The analogy, and where it breaks

Two people meet in a corridor only wide enough for one, each needing to pass the other, and each politely waits for the other to back off first: nobody moves. Lock ordering is a traffic rule such as "whoever is heading north backs off": with a rule everyone applies the same way, the stand-off cannot happen. Try-lock with backoff is "if blocked, step back and try again after a random pause"; without the randomness both step back and forward in sync forever, which is livelock. The analogy breaks on visibility: people can see the deadlock and talk; threads cannot, which is why the prevention must be built into the rule every thread follows.

1 · Clarify the requirements

Ask how many accounts and how many concurrent transfers, whether a transfer may overdraw, whether transfers to the same account are allowed, whether a transfer can involve more than two accounts (fees), whether requests can be retried after a timeout, whether balances live in memory or in a database, and whether accounts are spread across machines.

A typical agreed scope: in-memory accounts with integer-cent balances; concurrent transfers from many threads; no overdraft (insufficient funds raises); self-transfers are no-ops; transfers carry an optional id so retries are not applied twice; everything in one process. Invariants: the total of all balances never changes; no balance is ever negative; every transfer either applies completely or not at all; the system never deadlocks.

2 · The data and the invariant

An Account has an id, a balance in cents and its own lock. A Bank holds accounts in a dict and exposes transfer and total. The conservation invariant, total() == initial total, is checked by tests after heavy concurrent use; it is the single most powerful assertion here, because a lost update in either direction changes it. Per-account locks rather than one global lock allow transfers between unrelated accounts to proceed in parallel.

3 · The bad interleaving: lost update

Without locks, trace two transfers out of account A (balance 100) at once: T1 sends 30 to B, T2 sends 50 to C.

The solution's UnsafeBank separates the read and the write explicitly so the window is visible, and with the interpreter's switch interval reduced to a microsecond, every run of eight threads making 5,000 transfers each changed the total.

4 · The bad interleaving: deadlock

Give each account a lock and lock source then destination:

def transfer(self, src_id, dst_id, amount):
    src, dst = self.accounts[src_id], self.accounts[dst_id]
    with src.lock:
        with dst.lock:                 # argument order: depends on the direction
            self._move(src, dst, amount)
StepT1: transfer(A → B)T2: transfer(B → A)
1acquires A's lock
2acquires B's lock
3tries B's lock: held by T2, waits
4waitingtries A's lock: held by T1, waits
5waits foreverwaits forever

All four conditions hold: the locks are exclusive, each thread holds one while waiting for the other, nothing takes a lock away, and the waits form the cycle T1 → T2 → T1. The window is tiny, the gap between the two acquisitions, so casual testing rarely hits it; the solution's test makes it certain by pausing each thread at a barrier just after its first lock, so both hold one before either tries the second. With a 0.5-second timeout on the second acquisition, the naive bank reports "waited for account 1 while holding 0" and "waited for account 0 while holding 1". Sometimes one thread times out first, releases its lock, and the other then completes, which is exactly how timeout-based recovery and database victim selection work: one participant is sacrificed so the other can proceed.

5 · The fix: global lock order, and why it works

first, second = (src, dst) if src.id < dst.id else (dst, src)
with first.lock:
    with second.lock:
        self._move(src, dst, amount)        # funds check and both updates, all locked

Every transfer locks the account with the lower id first, regardless of direction. A to B and B to A both start by locking A. Whichever gets A proceeds to B and completes; the other waits for A while holding nothing, so it blocks no one.

The general argument is short. Suppose there were a deadlock cycle T1 → T2 → … → Tk → T1, each thread waiting for a lock held by the next. Under the ordering rule, a thread only ever waits for a lock with a higher id than every lock it already holds. T1 waits for a lock L2 held by T2, so L2 is higher than T1's held lock L1. T2 holds L2 and waits for L3 held by T3, so L3 > L2. Following the cycle, each lock is higher than the last, until Tk waits for a lock held by T1, which must be higher than everything before it, including L1 itself. A lock cannot be higher than itself, so the cycle is impossible. Circular wait is broken, and with it, deadlock. The same argument works for any number of locks per operation and any number of threads, which is why the meeting scheduler sorted calendar names and why a transfer with a fee to a third account simply sorts three ids.

6 · Funds, self-transfers and the order of checks

_move checks the source balance and performs both updates while both locks are held. Checking funds before acquiring the locks would reintroduce a check-then-act race: two transfers could both see sufficient funds and both debit. A transfer from an account to itself is handled before locking: with Python's non-re-entrant Lock, locking the same account as both first and second would make the thread wait for itself forever, the smallest possible deadlock. The solution treats it as a no-op; rejecting it with an error is equally valid. Non-positive amounts are rejected, since a negative amount would reverse the transfer's direction and bypass the funds check.

7 · Idempotent retries

A client that times out waiting for a response does not know whether the transfer happened, and will retry. Applying the retry would move the money twice. The solution accepts an optional transfer id; inside the account locks, after moving the money, it records the id; a later call with the same id returns immediately. Recording the id inside the same critical section as the money movement matters: if it were recorded afterwards, a retry arriving in between would apply the transfer again. In a database, the id would be a unique column in a transfers table inserted in the same transaction as the balance updates, the idempotency-key pattern from the resilient-client and expense-sharing cases.

8 · Alternative: try-lock with backoff

Lock ordering prevents circular wait. An alternative attacks hold-and-wait instead: take the first lock, then try the second without waiting (lock.acquire(blocking=False)); if that fails, release the first, sleep a short random time, and start again. A thread never waits while holding a lock, so deadlock is impossible. The cost is wasted work and the risk of livelock: two threads that repeatedly take their first lock, fail to get the second, release and retry in lockstep, making no progress though neither is blocked. Randomised backoff that grows with each attempt (jitter, as in the resilient-client case) breaks the symmetry. The solution's test forces the conflict on the first round; both threads back off, one wins on a retry, and the retry counter shows at least one retry. Try-lock is useful when a global order is impossible to define (locks discovered dynamically) or when a thread must not block.

9 · Detection instead of prevention: wait-for graphs

Databases take a third approach because they cannot control the order in which arbitrary SQL statements lock rows. They let transactions wait, and after a delay build the wait-for graph (an edge from each waiting transaction to the one holding the lock it needs) and search for cycles. If one exists, they abort one transaction, the victim, releasing its locks so the others proceed; the application receives a deadlock error and should retry. The solution includes a tiny find_cycle over such a graph, tested on a two-node cycle, an acyclic chain and a three-node cycle with a fourth thread waiting into it. PostgreSQL waits deadlock_timeout, one second by default, before running this check, because the check is relatively expensive and most lock waits end on their own.

What the GIL does not protect

It is tempting to believe that CPython's global interpreter lock makes simple statements on shared integers safe. It guarantees only that one bytecode runs at a time; balance -= amount compiles to several bytecodes (load, subtract, store), and the interpreter may switch threads between them. The unsafe bank's results show it plainly. On the free-threaded build available since Python 3.13, threads truly run in parallel and such races become more frequent, not less. Every shared read-modify-write needs a lock or an atomic primitive.

11 · The full solution

The file below contains the unsafe bank, the naive-lock bank, the ordered bank, the try-lock bank, the cycle finder and seven tests. Python 3.12, standard library only; it runs in a few seconds.

"""Deadlock-free money transfer: per-account locks acquired in a global order, balance checks
inside the locks, conservation of money as the invariant, idempotent transfer ids, plus the
broken versions (no locks: lost updates; locks in argument order: deadlock), a try-lock with
backoff alternative, and wait-for-graph cycle detection. Python 3.12, standard library only.
Run: python transfers.py"""
from __future__ import annotations

import random
import sys
import threading
import time
from dataclasses import dataclass, field
from typing import Callable


class InsufficientFunds(Exception): ...


@dataclass(eq=False)
class Account:
    id: int
    balance: int                                          # integer cents
    lock: threading.Lock = field(default_factory=threading.Lock, repr=False)


class Bank:
    def __init__(self, n: int, opening: int = 10_000, hook: Callable[[], None] | None = None) -> None:
        self.accounts = {i: Account(i, opening) for i in range(n)}
        self.hook = hook or (lambda: None)                # tests pause here between the two locks
        self._done: dict[str, int] = {}                   # transfer id -> amount (idempotency)
        self._done_lock = threading.Lock()

    def total(self) -> int:
        return sum(a.balance for a in self.accounts.values())

    def _move(self, src: Account, dst: Account, amount: int) -> None:
        if src.balance < amount:
            raise InsufficientFunds(f"account {src.id} has {src.balance}, needs {amount}")
        src.balance -= amount
        dst.balance += amount

    def transfer(self, src_id: int, dst_id: int, amount: int, transfer_id: str | None = None) -> None:
        raise NotImplementedError


class UnsafeBank(Bank):
    """BUG: no locks. Concurrent `balance -= x` updates overwrite each other."""

    def transfer(self, src_id, dst_id, amount, transfer_id=None):
        src, dst = self.accounts[src_id], self.accounts[dst_id]
        if src.balance >= amount:
            b = src.balance                                # read ...
            self.hook()
            src.balance = b - amount                       # ... write: another update may be lost
            c = dst.balance
            dst.balance = c + amount


class NaiveLockBank(Bank):
    """BUG: locks taken in argument order. A->B and B->A at once deadlock."""

    def transfer(self, src_id, dst_id, amount, transfer_id=None, timeout: float = -1):
        src, dst = self.accounts[src_id], self.accounts[dst_id]
        if not src.lock.acquire(timeout=timeout):
            raise TimeoutError("first lock")
        try:
            self.hook()
            if not dst.lock.acquire(timeout=timeout):
                raise TimeoutError(f"waited for account {dst.id} while holding {src.id}")
            try:
                self._move(src, dst, amount)
            finally:
                dst.lock.release()
        finally:
            src.lock.release()


class OrderedLockBank(Bank):
    """FIX: always lock the lower account id first. A cycle of waits is impossible."""

    def transfer(self, src_id, dst_id, amount, transfer_id=None):
        if amount <= 0:
            raise ValueError("amount must be positive")
        if src_id == dst_id:
            return                                         # one lock, nothing to move; avoids self-deadlock
        if transfer_id is not None:
            with self._done_lock:
                if transfer_id in self._done:
                    return                                 # retried request: already applied
        src, dst = self.accounts[src_id], self.accounts[dst_id]
        first, second = (src, dst) if src.id < dst.id else (dst, src)
        with first.lock:
            self.hook()
            with second.lock:
                self._move(src, dst, amount)
                if transfer_id is not None:
                    with self._done_lock:
                        self._done[transfer_id] = amount


class TryLockBank(Bank):
    """ALTERNATIVE: never wait while holding a lock. Take the first, TRY the second; on failure
    release everything, back off a random time, retry. No deadlock; livelock is possible but
    jittered backoff makes it unlikely."""

    def __init__(self, *a, **kw) -> None:
        super().__init__(*a, **kw)
        self.retries = 0
        self._retries_lock = threading.Lock()

    def transfer(self, src_id, dst_id, amount, transfer_id=None):
        src, dst = self.accounts[src_id], self.accounts[dst_id]
        attempt = 0
        while True:
            with src.lock:
                self.hook()
                if dst.lock.acquire(blocking=False):
                    try:
                        self._move(src, dst, amount)
                        return
                    finally:
                        dst.lock.release()
            with self._retries_lock:
                self.retries += 1
            attempt += 1
            time.sleep(random.uniform(0, 0.001 * min(2 ** attempt, 64)))   # jittered backoff


def find_cycle(wait_for: dict[str, str]) -> list[str] | None:
    """Wait-for graph: thread -> thread it waits on. A cycle is a deadlock (what databases detect)."""
    for start in wait_for:
        seen, node = [], start
        while node in wait_for and node not in seen:
            seen.append(node)
            node = wait_for[node]
        if node in seen:
            return seen[seen.index(node):]
    return None


# ---------------------------------------------------------------- tests
def opposite_transfers(bank: Bank, **kw) -> list[str]:
    """T1 moves 0->1 while T2 moves 1->0; both pause after their FIRST lock until both hold one."""
    both = threading.Barrier(2)
    results: list[str] = []
    bank.hook = lambda: both.wait(timeout=1)

    def go(a: int, b: int) -> None:
        try:
            bank.transfer(a, b, 100, **kw)
            results.append("done")
        except TimeoutError as e:
            results.append(f"timeout: {e}")
    ts = [threading.Thread(target=go, args=p) for p in ((0, 1), (1, 0))]
    for t in ts: t.start()
    for t in ts: t.join(5)
    return results


def test_unsafe_bank_loses_money() -> None:
    sys.setswitchinterval(1e-6)
    bank = UnsafeBank(4)
    before = bank.total()

    def worker(seed: int) -> None:
        rng = random.Random(seed)
        for _ in range(5_000):
            a, b = rng.sample(range(4), 2)
            bank.transfer(a, b, rng.randint(1, 50))
    ts = [threading.Thread(target=worker, args=(i,)) for i in range(8)]
    for t in ts: t.start()
    for t in ts: t.join()
    sys.setswitchinterval(0.005)
    print(f"    unsafe bank: total before {before}, after {bank.total()} (money created or destroyed)")
    assert bank.total() != before


def test_naive_lock_order_deadlocks() -> None:
    results = opposite_transfers(NaiveLockBank(2), timeout=0.5)
    print(f"    naive lock order: {results}")
    # Both threads hold one lock and wait for the other: a deadlock. The timeout is the only way
    # out; whichever gives up first releases its lock, and the other may then finish (like a
    # database aborting one victim).
    assert any(r.startswith("timeout: waited for account") for r in results), results


def test_ordered_locks_complete_the_same_scenario() -> None:
    bank = OrderedLockBank(2)
    reached = []
    # with ordering, both threads want account 0 FIRST, so only one can hold a lock at the pause;
    # a barrier would wait forever here, so just record arrival and continue
    bank.hook = lambda: reached.append(1)
    ts = [threading.Thread(target=bank.transfer, args=p + (100,)) for p in ((0, 1), (1, 0))]
    for t in ts: t.start()
    for t in ts: t.join(2)
    assert all(not t.is_alive() for t in ts) and bank.total() == 20_000 and len(reached) == 2
    assert bank.accounts[0].balance == bank.accounts[1].balance == 10_000


def test_ordered_bank_stress_conserves_money() -> None:
    sys.setswitchinterval(1e-6)
    bank = OrderedLockBank(10, opening=1_000)
    rejected = [0]
    rej_lock = threading.Lock()

    def worker(seed: int) -> None:
        rng = random.Random(seed)
        for _ in range(3_000):
            a, b = rng.randrange(10), rng.randrange(10)
            try:
                bank.transfer(a, b, rng.randint(1, 300))
            except InsufficientFunds:
                with rej_lock:
                    rejected[0] += 1
    ts = [threading.Thread(target=worker, args=(i,)) for i in range(8)]
    for t in ts: t.start()
    for t in ts: t.join(30)
    sys.setswitchinterval(0.005)
    assert all(not t.is_alive() for t in ts)
    assert bank.total() == 10_000 and min(a.balance for a in bank.accounts.values()) >= 0
    print(f"    ordered bank: 24,000 random transfers, total conserved, {rejected[0]} rejected for funds")


def test_try_lock_with_backoff_avoids_deadlock() -> None:
    bank = TryLockBank(2)
    both = threading.Barrier(2)
    first_round = [True]

    def hook() -> None:
        if first_round[0]:
            try:
                both.wait(timeout=0.5)                    # force the conflict once
            except threading.BrokenBarrierError:
                pass
    bank.hook = hook
    ts = [threading.Thread(target=bank.transfer, args=p + (100,)) for p in ((0, 1), (1, 0))]
    for t in ts: t.start()
    time.sleep(0.05); first_round[0] = False
    for t in ts: t.join(3)
    assert all(not t.is_alive() for t in ts) and bank.total() == 20_000 and bank.retries >= 1


def test_funds_self_transfer_and_idempotency() -> None:
    bank = OrderedLockBank(2, opening=500)
    try:
        bank.transfer(0, 1, 600)
    except InsufficientFunds:
        pass
    bank.transfer(0, 0, 100)                               # no-op, and no self-deadlock
    bank.transfer(0, 1, 200, transfer_id="tx-42")
    bank.transfer(0, 1, 200, transfer_id="tx-42")          # client retry
    assert (bank.accounts[0].balance, bank.accounts[1].balance) == (300, 700)


def test_wait_for_graph() -> None:
    assert find_cycle({"T1": "T2", "T2": "T1"}) == ["T1", "T2"]
    assert find_cycle({"T1": "T2", "T2": "T3"}) is None
    assert find_cycle({"T1": "T2", "T2": "T3", "T3": "T1", "T4": "T1"}) == ["T1", "T2", "T3"]

12 · Testing for conservation and deadlock

The stress test is the backbone: eight threads each make 3,000 random transfers among ten accounts with random amounts, under the smallest thread switch interval, then the test checks that the total is still exactly 10,000 cents times the number of accounts, that no balance is negative, and that every thread finished within its join timeout. Few accounts maximise collisions; random amounts exercise the insufficient-funds path (about 2,400 to 2,600 rejections per run). The deterministic tests then pin the two famous failures: a barrier after the first lock makes the naive deadlock certain, and the same scenario completes under ordering. The unsafe bank's test proves the stress harness can detect lost updates. Unit tests cover the remaining rules one at a time: insufficient funds, self-transfer, idempotent retry and cycle detection.

13 · Talking through the design

"Each account has a lock. A transfer locks both accounts, checks funds and moves the money inside the locks, so it's atomic and can't overdraw; without locks, read-modify-write loses updates and the total drifts. Locking source then destination deadlocks when A→B and B→A run together: each holds one lock and waits for the other. I lock the lower account id first; then every wait goes from a lower held lock to a higher wanted lock, so a cycle is impossible. Self-transfers are handled before locking, because a non-re-entrant lock taken twice deadlocks with itself. Transfer ids make retries idempotent. Try-lock with jittered backoff is the alternative when an order can't be defined; it can livelock without jitter. Databases detect cycles in the wait-for graph and abort a victim, and PostgreSQL's docs recommend consistent lock order for exactly this transfer case."

14 · Edge cases

Same account: no-op or error, never two acquisitions. Unknown account ids: fail before locking. Negative or zero amounts: rejected. Overflow: Python integers do not overflow, but a database column might; validate limits. Accounts created or closed during transfers: closing must take the account's lock and fail transfers that arrive afterwards. Exceptions inside the critical section: with blocks release locks; make sure partial updates cannot happen (the funds check comes before any update). Ids that are not comparable (strings and numbers mixed): define the order on a canonical key.

15 · Extensions the interviewer will ask for

Batch transfers involving many accounts: sort and deduplicate all ids, lock in order. Ledger entries: append debit and credit records inside the critical section for audit and reconciliation. Persistence: one database transaction per transfer, rows locked in id order (SELECT ... FOR UPDATE ORDER BY id), retry on deadlock errors. Sharded accounts: sagas or two-phase commit with idempotent steps. Hot accounts (a merchant receiving thousands of payments a second): one lock becomes a bottleneck; split the balance into sub-accounts or apply credits asynchronously from a queue. Read-only queries such as total balance: lock all accounts in order, or read from a consistent snapshot.

16 · Complexity

Each transfer is O(1): two lock acquisitions in order, a comparison and two updates. Throughput scales with the number of distinct account pairs in flight; transfers touching the same account serialise on its lock. Lock ordering adds a single comparison. Try-lock adds retries proportional to contention. Cycle detection over a wait-for graph is linear in the number of waiting transactions. The cheapest of all these costs is the ordering comparison, a single integer comparison per transfer, which is why lock ordering is the first tool to reach for: it buys deadlock freedom for essentially nothing, as long as every code path that takes two account locks goes through the same helper.

The four conditions as a design checklist

The Coffman conditions turn deadlock from folklore into a checklist. For any component that takes more than one lock, ask which condition you will break. Breaking mutual exclusion means making the resource shareable, for example immutable data or lock-free structures; it is rarely possible for balances. Breaking hold and wait means acquiring everything at once or nothing (try-lock with release, or a single lock covering all needed resources). Breaking no preemption means being able to take a lock away, which in practice means aborting and rolling back the holder, as databases do. Breaking circular wait means a global order. Lock ordering is the most common choice in application code because it costs one comparison and needs no rollback machinery.

When a global order is hard

Ordering requires knowing all the locks an operation needs before taking the first one, and a stable, total order over them. Both can fail. An operation may discover which locks it needs only after reading data under an earlier lock (follow a pointer, then lock what it points to). Locks may live in different subsystems with no shared ordering key. In those cases the options are: release and restart in order once the full set is known (optimistic: read without locks, compute the set, lock in order, then re-validate what was read); try-lock with backoff; or a coarser lock that covers the whole operation. Lock hierarchies in large systems, such as the Linux kernel's documented lock ordering rules and its runtime validator, exist because maintaining a global order across thousands of locks is itself an engineering discipline.

Livelock and starvation in the alternatives

Try-lock removes deadlock but not all liveness problems. Two threads backing off for identical fixed delays can collide forever (livelock); randomised exponential backoff makes the probability of repeated collisions shrink quickly. Even with lock ordering, a thread can starve if locks are not fair: a transfer waiting for a hot account's lock may be overtaken repeatedly by others. Python's Lock makes no fairness guarantee. In practice, contention on one account is rare enough that this does not matter, and when it does (a hot merchant account), the fix is architectural: reduce contention rather than queue more fairly.

The dining philosophers

The textbook ancestor of this problem is Dijkstra's dining philosophers: five philosophers around a table, one fork between each pair, each needing both neighbouring forks to eat. If each picks up the left fork first, all can hold one fork and wait forever for the right one, a five-way circular wait. The classic resource-ordering solution numbers the forks and has every philosopher pick up the lower-numbered fork first, which makes one philosopher reach to the right first and breaks the cycle. Account transfers are the two-philosopher version, and the solution is identical; mentioning the connection shows the interviewer you recognise the general problem behind the specific question.

Optimistic alternatives for balances

Locks are pessimistic: they assume conflict and prevent it. An optimistic design lets transfers proceed without locks and detects conflicts at commit. Each account carries a version number; a transfer reads both accounts and versions, computes new balances, and commits only if both versions are unchanged, otherwise it retries. In SQL this is a conditional update such as UPDATE accounts SET balance = balance - 100, version = version + 1 WHERE id = 7 AND version = 41 with a check that one row changed, applied to both accounts in one transaction. Optimistic concurrency avoids lock waits and deadlocks entirely, at the cost of retries under contention, so it suits workloads where two transfers rarely touch the same account at once.

How databases do it

A relational database locks rows as UPDATE statements touch them, in whatever order the application issues the statements, so it cannot rely on a global order. PostgreSQL's documentation walks through the transfer case: transaction one updates account 11111, transaction two updates 22222 and then tries 11111 and waits, transaction one then tries 22222 and waits, a deadlock. PostgreSQL waits deadlock_timeout (one second by default) before checking, because most lock waits resolve on their own and the check is relatively expensive, then aborts one transaction; which one is hard to predict and should not be relied upon. Its guidance is the application-level fix: acquire locks on multiple objects in a consistent order, and make the first lock on an object the most restrictive mode that will be needed (to avoid the upgrade trap from the read-write lock case). Applications should still catch deadlock errors and retry the whole transaction, with idempotency to make the retry safe.

Transfers across shards

When accounts live on different database shards or services, no single lock manager sees both rows, and distributed locking is slow and fragile. The common patterns are a saga: debit the source with a pending marker, credit the destination, then mark complete, with compensating actions (refund the debit) if a later step fails; and two-phase commit, where a coordinator asks both shards to prepare and then commit. Both rely on idempotent steps keyed by a transfer id, because retries are certain. Both relax atomicity in time: for a moment the money is in neither account's available balance, which is acceptable if the ledger records the pending state explicitly. The deadlock lesson still applies inside each shard.

How transfer systems fail in production

Deadlocks in production rarely look like a dramatic freeze; in databases they appear as a steady trickle of "deadlock detected" errors that rise with traffic, each causing a failed request or a retry. The cause is almost always two code paths touching the same rows in different orders: a transfer that updates the source first, and a reversal that updates the destination first; or a batch job that walks accounts in one order while online traffic uses another. Logging the lock-wait graph that the database reports, and fixing the code paths to lock in id order, makes them disappear. In-memory systems without detection fail harder: threads hang, request queues fill, health checks time out, and the process is restarted, losing the evidence unless thread dumps are captured.

Lost updates are quieter and worse: no error at all, just balances that do not reconcile. They come from read-modify-write cycles outside a lock or transaction, often an ORM loading an object, changing a field in application code and saving it back while another request did the same. The defences are atomic updates in SQL (UPDATE ... SET balance = balance - 100 WHERE id = ... AND balance >= 100, checking the row count), row locks, or optimistic versioning, plus a reconciliation job that recomputes totals and alerts on any difference.

Hot accounts

Lock ordering makes transfers correct; it does not make a single busy account fast. A marketplace's settlement account or a popular merchant may receive thousands of credits a second, all serialising on one lock or one database row, and lock waits rather than deadlocks become the problem. Common remedies split the account into several sub-accounts (credits go to a random one; the true balance is their sum), apply credits asynchronously by appending ledger entries and folding them into the balance in batches, or treat credits as commutative increments that need no read of the current balance. Debits still need a consistent view, which is why such systems often allow credits to be eventually consistent but keep debits strictly locked.

What to measure

Deadlock errors and transaction retries per minute, lock wait time by table, the longest-held locks, the conservation check from reconciliation (should always be exact), duplicate transfer ids rejected (a measure of client retries), and for hot accounts, lock contention on individual rows.

Knobs

None of these replaces correct lock ordering; they bound the damage when something still goes wrong, and they make failures visible quickly instead of hours later, when the evidence of what went wrong is still fresh in the logs and the thread dumps you captured. Lock acquisition timeouts (application side) and deadlock_timeout and lock_timeout (database side), retry limits with jittered backoff for deadlock errors, and the granularity of locking (row, account group, or a sub-account split for hot accounts).

The real case: PostgreSQL's deadlock documentation

PostgreSQL's chapter on explicit locking contains a section on deadlocks that reads like this lesson's drill. It defines a deadlock as two or more transactions each holding locks that the other wants, notes that PostgreSQL automatically detects deadlock situations and resolves them by aborting one of the transactions involved, and warns that which transaction is aborted is difficult to predict and should not be relied upon. It then shows that deadlocks can arise from row-level locks alone: the first transaction runs UPDATE accounts SET balance = balance + 100.00 WHERE acctnum = 11111; the second updates account 22222 and then tries 11111, and waits; the first then tries to update 22222 and waits for the second, a deadlock, which PostgreSQL detects by aborting one. The documentation's conclusion is the one this lesson proves: the best defence against deadlocks is generally to avoid them by being certain that all applications using a database acquire locks on multiple objects in a consistent order, and in the example, if both transactions had updated the rows in the same order, no deadlock would have occurred. The server configuration chapter adds the detection mechanics: deadlock_timeout, the time to wait on a lock before checking for a deadlock, defaults to one second because the check is relatively expensive. Prevention by ordering in the application, detection with a victim in the database, and retries with idempotency on top: the same three layers apply whether the accounts are Python objects or table rows.

Work it out

A payments service has this transfer code, called from many threads:

def transfer(src, dst, amount):
    if src.balance < amount:
        raise InsufficientFunds()
    with src.lock:
        with dst.lock:
            src.balance -= amount
            dst.balance += amount

(a) Find every bug. (b) Give an interleaving for each. (c) Write the corrected code and explain why it is deadlock-free.

Answer

(a) Three bugs. The funds check happens before the locks (check-then-act race, allows overdraft). Locks are taken in argument order (deadlock on opposite transfers). A transfer from an account to itself takes the same non-re-entrant lock twice (self-deadlock).

(b) Interleavings.

Overdraft: account A holds 100. T1 (A → B, 80) checks 100 ≥ 80: passes. T2 (A → C, 80) checks 100 ≥ 80: passes. T1 locks A and B, debits A to 20, releases. T2 locks A and C, debits A to −60. The check was true when made and false when acted on.

Deadlock: T1 runs transfer(A, B), T2 runs transfer(B, A). T1 locks A; T2 locks B; T1 waits for B; T2 waits for A. Neither proceeds; every later transfer touching A or B queues behind them.

Self-deadlock: transfer(A, A, 10) locks A, then tries to lock A again. Python's Lock is not re-entrant, so the thread waits for itself forever.

(c) The fix.

def transfer(src, dst, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")
    if src is dst:
        return                                   # or raise; never lock twice
    first, second = (src, dst) if src.id < dst.id else (dst, src)
    with first.lock:
        with second.lock:
            if src.balance < amount:             # check inside the locks
                raise InsufficientFunds()
            src.balance -= amount
            dst.balance += amount

Why it is deadlock-free. Every thread acquires account locks in increasing id order. A thread therefore only waits for a lock with a higher id than any lock it holds. A cycle of waiting threads would require some thread to wait for a lock lower than one it holds, which never happens, so circular wait, one of the four necessary conditions for deadlock, cannot occur. Moving the funds check inside the locks makes check and debit atomic, so overdraft is impossible; handling the same-account case before locking removes the self-deadlock. A stress test checking that the total of all balances is unchanged after thousands of concurrent random transfers, with join timeouts, confirms both properties empirically.
