The interviewer opens with: "Every agent framework is a loop around a model call. Build that loop. You have a model that can request tools, a few tools, and 45 minutes. Make it robust." It sounds small, and the first version is: call the model, if it wants a tool, run it, append the result, repeat. Then the questions start. What if the model calls a tool that does not exist? What if it passes a number where the tool expects a string? What if the tool raises, or hangs for two minutes? What if the model asks for three tools at once — do you run them one after another? What if it calls the same search forty times? What stops a run from costing fifty dollars? How would you debug a run that went wrong last Tuesday? How do you test any of this without paying for model calls?

These questions are the job. In production, the loop is where agents fail: an unvalidated argument that deletes the wrong record, a tool exception that ends a twenty-step task at step nineteen, an unbounded loop that burns a budget overnight, a hanging tool that blocks a user for minutes, a result split across messages that confuses the model. AI-engineer loops increasingly include exactly this round because it tests whether you have built one: the code is not hard, but the right decisions — feed errors back, validate before executing, bound four different resources, keep results paired and ordered, make everything testable — only come from having seen it break.

This lesson builds the loop in the order an interview flows. It starts with the message shapes a tool-calling model uses (Anthropic's documented format: tool_use blocks with ids, tool_result blocks with matching ids and an is_error flag), then the entities and their responsibilities, then a naive loop and everything wrong with it. It adds, in stages, a tool registry with JSON-schema validation, errors fed back to the model, parallel execution with per-tool timeouts, four budgets, a repeated-call guard and a trace. The full solution is a single runnable Python 3.12 file with thirteen tests, including a barrier test that proves calls really run in parallel and a stress test with eight threads sharing one agent. The lesson closes with edge cases, the extensions interviewers ask for (human approval, async, streaming, persistence) and complexity.

The analogy: a manager, a phone and a team of specialists

Picture a manager who cannot do anything themselves but can phone specialists: a weather desk, a calculator, a records clerk. A request comes in. The manager thinks, then writes instructions on numbered slips: "slip 1: weather desk, city Paris"; "slip 2: records clerk, customer 4471". An assistant takes the slips, checks each is filled in properly (a weather slip with no city goes straight back with "missing city"), phones the specialists — all at once, not one after another — and staples each answer to its slip. If a specialist does not answer within a minute, the slip comes back marked "no answer". The manager reads the stapled answers and either writes more slips or writes the final reply. A supervisor watches the clock and the phone bill and stops the whole thing if either runs too high.

The model is the manager. The slips are tool_use blocks, each with an id. The assistant is the harness — the code you are writing. Checking the slip is schema validation. Phoning everyone at once is parallel execution. "No answer" is a timeout. Stapling answers to slips is the tool_result with a matching tool_use_id. The supervisor is the budget. And the assistant's notebook of who was called, when and what came back is the trace.

Where the analogy breaks: a human manager learns from a returned slip that says "missing city" and fixes it; a model does too, but only if the message is precise. And a human assistant can hang up on a specialist who talks too long; a Python thread cannot be forcibly stopped — the harness can stop waiting, but the work continues in the background.

The message format

Tool-calling APIs differ in detail but share a shape. In Anthropic's Messages API, which this solution mirrors, you send the conversation plus a list of tools, each with a name, a description and an input_schema (a JSON Schema object). When the model wants tools, its response has stop_reason equal to "tool_use" and its content includes one or more tool_use blocks, each with an id, the tool name and an input object. You append that assistant message unchanged, run the tools, and send back a user message whose content is a list of tool_result blocks, each carrying the tool_use_id it answers, the result as content, and is_error: true if the tool failed. The documentation is specific on two points this lesson relies on: a failed tool should be returned with is_error rather than dropped, and all results for one turn belong in a single user message.

What the round expects

A ToolRegistry with a decorator to register tools; a validator for a sensible subset of JSON Schema; an Agent.run loop with a clear stop status; parallel tool execution with per-tool timeouts; errors returned as results; budgets for steps, tokens, time and tool calls; a trace; a fake model and an injected clock for tests; and a confident explanation of what you would add for production (approval, persistence, streaming, async).

1 · Clarify the requirements

Ask what the model interface is (does it return content blocks and a stop reason, as Anthropic's API does?), whether the model can request several tools in one turn, whether tools are I/O-bound (network, database) or CPU-bound, whether any tools have side effects, what limits matter (latency for an interactive user, cost for a batch job), whether runs must survive a process restart, and whether the loop will be shared by many concurrent requests.

A typical agreed scope: synchronous run(user_text) → RunResult; tools are Python functions with JSON-schema inputs; the model may request parallel calls; tools are mostly I/O-bound so threads are fine; budgets on steps, tokens, wall time and tool calls; every failure the model could fix is fed back to it; a trace of every call; tests with a fake model, no network. Out of scope: streaming, human approval, persistence — but have an answer for each.

2 · Entities and responsibilities

Tool: an immutable record of name, description, input schema, function and timeout. ToolRegistry: registers tools (rejecting duplicate names and non-object schemas), looks them up, and renders the tool specs sent to the model — in a stable, sorted order, because provider prompt caches key on an exact prefix and tools come first. validate: a function that checks a value against a schema and raises SchemaError with a path like $.tags[1]. ModelResponse: content blocks, stop reason, token usage. Model: any callable taking messages and tool specs and returning a ModelResponse — the seam that lets a fake replace the real API. Budget: four limits. Agent: owns the loop, the thread pool, the repeated-call counter and the trace, and returns a RunResult with a status, final text, the full transcript, steps, tokens and trace.

3 · Stage one: the naive loop, and what is wrong with it

def run(model, tools, user_text):
    messages = [{"role": "user", "content": user_text}]
    while True:
        resp = model(messages, tools)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return resp.content[0]["text"]
        for call in [b for b in resp.content if b["type"] == "tool_use"]:
            out = TOOLS[call["name"]](**call["input"])          # KeyError, TypeError, hangs…
            messages.append({"role": "user", "content": [
                {"type": "tool_result", "tool_use_id": call["id"], "content": str(out)}]})

Count the problems. while True has no bound: a model that keeps calling tools runs forever. An unknown tool name raises KeyError and kills the run. Bad arguments raise TypeError inside the tool, or worse, are accepted and do the wrong thing. A tool exception kills the run. A hanging tool hangs the run. Parallel calls run one after another, so three 2-second lookups take 6 seconds. Each result goes in its own user message, which the provider's documentation warns against. A huge result (a 5 MB file) goes straight into the context. Nothing records what happened. And the only way to test it is with a real model. Each stage below fixes a group of these.

4 · Stage two: the registry and validation

Tools are registered with a decorator that records the schema next to the function. The registry refuses duplicate names (two tools named search would make the model's choice ambiguous) and schemas that are not objects (tool inputs are always objects of named arguments). specs() returns the tool list sorted by name, because the list is part of every request's prefix and a changing order would defeat prompt caching on every call.

Before running any call, validate its input against the schema. A full JSON Schema implementation is large; an interview needs the subset tool schemas actually use: type (object, array, string, integer, number, boolean, null), enum, minimum/maximum, minLength/maxLength, items, properties, required and additionalProperties: false. Two details show care. First, Python's bool is a subclass of int, so isinstance(True, int) is true; an integer field must explicitly reject booleans, and the test checks that {"k": true} fails with "expected integer". Second, errors carry a path — $.tags[1]: 'c' is not one of ['a', 'b'] — because the message is for the model, and the model can only fix what it can locate.

5 · Stage three: errors are results, not exceptions

Every way a call can fail becomes a tool_result with is_error: true: an unknown tool ("unknown tool 'get_wether'; available tools: add, get_weather" — listing the real names lets the model correct a typo), invalid input ("invalid input: $.city: expected string, got int"), an exception inside the tool ("ConnectionError: upstream reset" — type and message, not a traceback full of file paths) and a timeout. The loop continues, and the model decides: retry with fixed input, try another tool, or explain. The test test_validation_error_is_fed_back_and_model_recovers scripts a model that first passes city=5, then — in a turn written as a function of the messages — asserts it was shown exactly that error, and corrects the call. What still raises: bugs in the harness itself, and running out of scripted turns in the fake model, which is a test failure.

6 · Stage four: parallel calls with per-tool timeouts

When a response contains several tool_use blocks, they are independent by the model's own judgement, so run them concurrently. The implementation has two phases. First, for each call, look up the tool, check the repeat guard and validate; valid calls are submitted to a ThreadPoolExecutor immediately, and the submission time is recorded. Second, walk the calls in order and collect each future with result(timeout=remaining), where remaining is the tool's timeout minus the time already elapsed since submission. Measuring from submission matters: if you gave each future its full timeout while waiting in order, a slow first call would extend the waiting time of every later one.

Results are appended in call order, each with its tool_use_id, all in one user message. The test proves both properties. Three calls to a wait tool meet at a threading.Barrier(3, timeout=2), which only releases when all three threads are inside it at once — so if the harness ran them one by one, the first would time out at the barrier. They then finish in reverse order (sleeps of 60, 30 and 0 ms), and the test asserts the results still come back as w0, w1, w2. Threads suit I/O-bound tools (HTTP calls, database queries), which release Python's global interpreter lock while waiting; CPU-bound tools would need a process pool.

A timeout stops the waiting, not the work. Python cannot kill a thread; the timed-out function keeps running and occupies a pool worker until it returns. The test with a 0.05-second timeout on a 0.5-second tool asserts the run finishes in under 0.4 seconds — the harness moved on — but the worker is busy for the rest of the half second. That is why real tools need their own timeouts on network and subprocess calls, and why side-effecting tools need idempotency: a "timed out" payment may have gone through.

7 · Stage five: four budgets

Each budget protects against a different failure, so each is separate. Steps (model calls) stop infinite loops. Tokens, summed from each response's input and output counts, bound cost — and cost per step grows as the transcript grows, so a 10-step run is not 10× a 1-step run. Wall time bounds latency; it reads an injected clock so tests can make a model call "take" 40 seconds without waiting. Tool calls bound side effects and external costs (a paid search API), and are checked before executing a turn's calls so a turn is never half-executed.

Budgets are checked at the top of each step, before spending more, and the result's status says which one ended the run: final, max_steps, token_budget, deadline or tool_budget. Worked through the tests: with a 1,000-token budget and 600 tokens per model call, the first call leaves 600 used (under budget, so step 2 runs), the second brings it to 1,200, and the check before step 3 stops the run — two model calls, status token_budget. With a 100-second deadline and 40 seconds per call, steps 1-3 start at 0, 40 and 80 seconds; step 4 would start at 120, so the run stops after 3.

8 · Stage six: the repeated-call guard, truncation and the trace

The commonest real agent failure is calling the same tool with the same input repeatedly because the result did not contain what the model hoped for. The agent counts identical calls by a canonical key — the tool name plus its input serialised with sorted keys, so {"a":1,"b":2} and {"b":2,"a":1} match — and after max_repeats returns an error: "this exact call was already made 2 times with the same input; use the earlier result or change approach". It costs nothing and breaks the loop at its most typical point.

Results longer than max_result_chars are cut with a marker saying how much was removed, so one huge tool output cannot fill the context window; a production version would summarise or store the full output and return a handle.

The trace records, per step, the model call (stop reason, tokens, milliseconds) and each tool call (name, id, success, milliseconds), then the stop status. It is the agent's flight recorder: when a run misbehaves, the trace shows whether the model asked for the wrong tool, a tool failed, or a budget ran out.

9 · The full solution

Thirteen tests: the happy path and the exact message shape; validation errors fed back and corrected; unknown tools and extra properties; exceptions and timeouts as results; the barrier test for parallelism and order; each of the four budgets; the repeat guard; truncation; the validator and registry rules; and a stress test in which eight threads share one agent and run 400 conversations of five parallel calls each, checking every answer. Python 3.12, standard library only; it runs in about a second.

"""A tool-calling agent loop: a tool registry with JSON-schema validation, the model -> tool -> result
loop against a fake model, budgets (steps, tokens, wall time, tool calls), parallel tool calls with
per-tool timeouts, errors fed back to the model, a repeated-call guard and a trace log.
Python 3.12, standard library only.  Run: python agent_loop.py"""
from __future__ import annotations

import json
import threading
import time
from collections import Counter
from concurrent.futures import ThreadPoolExecutor, TimeoutError as FutureTimeout
from dataclasses import dataclass, field
from typing import Any, Callable


# ---------------------------------------------------------------- JSON Schema (a useful subset)
class SchemaError(ValueError):
    pass


_PY_TYPES = {"object": dict, "array": list, "string": str, "boolean": bool, "null": type(None)}


def validate(value: Any, schema: dict, path: str = "$") -> None:
    """Raise SchemaError with a path-qualified message if value does not match schema.
    Supports type, enum, minimum/maximum, minLength/maxLength, items, properties,
    required and additionalProperties: false."""
    t = schema.get("type")
    if t == "integer":
        ok = isinstance(value, int) and not isinstance(value, bool)
    elif t == "number":
        ok = isinstance(value, (int, float)) and not isinstance(value, bool)
    elif t is not None:
        ok = isinstance(value, _PY_TYPES[t])
    else:
        ok = True
    if not ok:
        raise SchemaError(f"{path}: expected {t}, got {type(value).__name__}")
    if "enum" in schema and value not in schema["enum"]:
        raise SchemaError(f"{path}: {value!r} is not one of {schema['enum']}")
    if t in ("integer", "number"):
        if "minimum" in schema and value < schema["minimum"]:
            raise SchemaError(f"{path}: {value} is below minimum {schema['minimum']}")
        if "maximum" in schema and value > schema["maximum"]:
            raise SchemaError(f"{path}: {value} is above maximum {schema['maximum']}")
    if t == "string":
        if len(value) < schema.get("minLength", 0):
            raise SchemaError(f"{path}: shorter than {schema['minLength']} characters")
        if "maxLength" in schema and len(value) > schema["maxLength"]:
            raise SchemaError(f"{path}: longer than {schema['maxLength']} characters")
    if t == "array" and "items" in schema:
        for i, item in enumerate(value):
            validate(item, schema["items"], f"{path}[{i}]")
    if t == "object":
        props = schema.get("properties", {})
        for name in schema.get("required", []):
            if name not in value:
                raise SchemaError(f"{path}: missing required property {name!r}")
        for name, item in value.items():
            if name in props:
                validate(item, props[name], f"{path}.{name}")
            elif schema.get("additionalProperties", True) is False:
                raise SchemaError(f"{path}: unexpected property {name!r}")


# ---------------------------------------------------------------- tools
@dataclass(frozen=True)
class Tool:
    name: str
    description: str
    input_schema: dict
    fn: Callable[..., Any]
    timeout_s: float = 5.0


class ToolRegistry:
    def __init__(self) -> None:
        self._tools: dict[str, Tool] = {}

    def register(self, name: str, description: str, input_schema: dict,
                 timeout_s: float = 5.0) -> Callable:
        if name in self._tools:
            raise ValueError(f"tool {name!r} already registered")
        if input_schema.get("type") != "object":
            raise ValueError("a tool's input_schema must describe an object")

        def deco(fn: Callable[..., Any]) -> Callable[..., Any]:
            self._tools[name] = Tool(name, description, input_schema, fn, timeout_s)
            return fn
        return deco

    def get(self, name: str) -> Tool | None:
        return self._tools.get(name)

    def specs(self) -> list[dict]:
        # Sorted, so the tool list is byte-identical every call (prompt caches key on the prefix).
        return [{"name": t.name, "description": t.description, "input_schema": t.input_schema}
                for t in sorted(self._tools.values(), key=lambda t: t.name)]


# ---------------------------------------------------------------- model interface
@dataclass
class ModelResponse:
    content: list[dict]                 # text and tool_use blocks
    stop_reason: str                    # "tool_use" or "end_turn"
    input_tokens: int = 0
    output_tokens: int = 0


Model = Callable[[list[dict], list[dict]], ModelResponse]


class FakeModel:
    """Plays back scripted turns. A turn is a ModelResponse or a function(messages) -> ModelResponse,
    so a test can make the 'model' react to the tool results it was given."""

    def __init__(self, turns: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.turns, self.seen = list(turns), []

    def __call__(self, messages: list[dict], tools: list[dict]) -> ModelResponse:
        self.seen.append(json.loads(json.dumps(messages)))          # snapshot what it was shown
        if not self.turns:
            raise AssertionError("fake model ran out of scripted turns")
        turn = self.turns.pop(0)
        return turn(messages) if callable(turn) else turn


def tool_use(id_: str, name: str, **inp: Any) -> dict:
    return {"type": "tool_use", "id": id_, "name": name, "input": inp}


def text(s: str) -> dict:
    return {"type": "text", "text": s}


# ---------------------------------------------------------------- the loop
@dataclass
class Budget:
    max_steps: int = 10                 # model calls
    max_tokens: int = 100_000           # input + output, summed over calls
    max_seconds: float = 120.0          # wall time for the whole run
    max_tool_calls: int = 50


@dataclass
class RunResult:
    status: str                         # final | max_steps | token_budget | deadline | tool_budget
    text: str | None
    messages: list[dict]
    steps: int
    tokens: int
    trace: list[dict] = field(default_factory=list)


class Agent:
    def __init__(self, model: Model, registry: ToolRegistry, budget: Budget | None = None,
                 clock: Callable[[], float] = time.monotonic, max_workers: int = 8,
                 max_result_chars: int = 4000, max_repeats: int = 2) -> None:
        self.model, self.registry = model, registry
        self.budget = budget or Budget()
        self.clock = clock
        self.pool = ThreadPoolExecutor(max_workers=max_workers, thread_name_prefix="tool")
        self.max_result_chars, self.max_repeats = max_result_chars, max_repeats

    def run(self, user_text: str) -> RunResult:
        messages: list[dict] = [{"role": "user", "content": [text(user_text)]}]
        trace: list[dict] = []
        tokens = tool_calls = 0
        seen_calls: Counter[str] = Counter()
        start = self.clock()

        def stop(status: str, step: int, final: str | None = None) -> RunResult:
            trace.append({"step": step, "event": "stop", "status": status})
            return RunResult(status, final, messages, step, tokens, trace)

        for step in range(1, self.budget.max_steps + 1):
            if self.clock() - start > self.budget.max_seconds:
                return stop("deadline", step - 1)
            if tokens >= self.budget.max_tokens:
                return stop("token_budget", step - 1)

            t0 = time.perf_counter()
            resp = self.model(messages, self.registry.specs())
            tokens += resp.input_tokens + resp.output_tokens
            trace.append({"step": step, "event": "model", "stop_reason": resp.stop_reason,
                          "tokens": resp.input_tokens + resp.output_tokens,
                          "ms": round((time.perf_counter() - t0) * 1000, 2)})
            messages.append({"role": "assistant", "content": resp.content})

            calls = [b for b in resp.content if b["type"] == "tool_use"]
            if resp.stop_reason != "tool_use" or not calls:
                final = "".join(b["text"] for b in resp.content if b["type"] == "text")
                return stop("final", step, final)

            if tool_calls + len(calls) > self.budget.max_tool_calls:
                return stop("tool_budget", step)
            tool_calls += len(calls)

            results = self._execute(calls, seen_calls, trace, step)
            # Every tool_use gets exactly one tool_result, in one user message, in call order.
            messages.append({"role": "user", "content": results})
        return stop("max_steps", self.budget.max_steps)

    # ---- tool execution: validate, then run all calls concurrently, each with its own timeout
    def _execute(self, calls: list[dict], seen: Counter, trace: list[dict], step: int) -> list[dict]:
        pending: list[tuple[dict, Tool | None, Any, str | None, float]] = []
        for call in calls:
            key = call["name"] + json.dumps(call["input"], sort_keys=True)
            seen[key] += 1
            tool = self.registry.get(call["name"])
            error = None
            if tool is None:
                names = ", ".join(t["name"] for t in self.registry.specs())
                error = f"unknown tool {call['name']!r}; available tools: {names}"
            elif seen[key] > self.max_repeats:
                error = (f"this exact call was already made {seen[key] - 1} times with the same input; "
                         "use the earlier result or change approach")
            else:
                try:
                    validate(call["input"], tool.input_schema)
                except SchemaError as e:
                    error = f"invalid input: {e}"
            future = None if error else self.pool.submit(tool.fn, **call["input"])
            pending.append((call, tool, future, error, time.monotonic()))

        results = []
        for call, tool, future, error, submitted in pending:
            out = None
            if future is not None:
                remaining = tool.timeout_s - (time.monotonic() - submitted)
                try:
                    out = future.result(timeout=max(0.0, remaining))
                except FutureTimeout:
                    error = f"tool {tool.name!r} timed out after {tool.timeout_s}s"
                except Exception as e:                       # the tool's bug becomes a message
                    error = f"{type(e).__name__}: {e}"
            if error is not None:
                body, is_error = error, True
            else:
                body = out if isinstance(out, str) else json.dumps(out, sort_keys=True, default=str)
                if len(body) > self.max_result_chars:
                    body = body[: self.max_result_chars] + f"... [truncated {len(body) - self.max_result_chars} chars]"
                is_error = False
            trace.append({"step": step, "event": "tool", "name": call["name"], "id": call["id"],
                          "ok": not is_error, "ms": round((time.monotonic() - submitted) * 1000, 2)})
            results.append({"type": "tool_result", "tool_use_id": call["id"],
                            "content": body, "is_error": is_error})
        return results


# ---------------------------------------------------------------- tests
def make_registry() -> ToolRegistry:
    reg = ToolRegistry()

    @reg.register("get_weather", "Current temperature in Celsius for a city.",
                  {"type": "object", "properties": {"city": {"type": "string", "minLength": 1}},
                   "required": ["city"], "additionalProperties": False})
    def get_weather(city: str) -> dict:
        return {"city": city, "temp_c": {"Paris": 18, "Oslo": 4}.get(city, 21)}

    @reg.register("add", "Add two integers.",
                  {"type": "object", "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}},
                   "required": ["a", "b"], "additionalProperties": False})
    def add(a: int, b: int) -> int:
        return a + b

    return reg


def last_results(messages: list[dict]) -> list[dict]:
    return messages[-1]["content"]


def test_happy_path_and_message_shape() -> None:
    model = FakeModel([
        ModelResponse([text("Let me check."), tool_use("t1", "get_weather", city="Paris")], "tool_use", 50, 10),
        lambda msgs: ModelResponse([text(f"It is {json.loads(last_results(msgs)[0]['content'])['temp_c']} C.")],
                                   "end_turn", 80, 8),
    ])
    r = Agent(model, make_registry()).run("Weather in Paris?")
    assert r.status == "final" and r.text == "It is 18 C." and r.steps == 2 and r.tokens == 148
    res = model.seen[1][-1]["content"][0]
    assert res == {"type": "tool_result", "tool_use_id": "t1", "content": '{"city": "Paris", "temp_c": 18}',
                   "is_error": False}
    assert [e["event"] for e in r.trace] == ["model", "tool", "model", "stop"]


def test_validation_error_is_fed_back_and_model_recovers() -> None:
    def second(msgs):
        res = last_results(msgs)[0]
        assert res["is_error"] and "$.city: expected string, got int" in res["content"]
        return ModelResponse([tool_use("t2", "get_weather", city="Oslo")], "tool_use")
    model = FakeModel([ModelResponse([tool_use("t1", "get_weather", city=5)], "tool_use"), second,
                       ModelResponse([text("4 C in Oslo.")], "end_turn")])
    r = Agent(model, make_registry()).run("Weather in Oslo?")
    assert r.status == "final" and r.steps == 3
    assert [e["ok"] for e in r.trace if e["event"] == "tool"] == [False, True]


def test_unknown_tool_and_extra_property() -> None:
    model = FakeModel([
        ModelResponse([tool_use("a", "get_wether", city="Paris"),
                       tool_use("b", "add", a=1, b=2, c=3)], "tool_use"),
        ModelResponse([text("done")], "end_turn"),
    ])
    r = Agent(model, make_registry()).run("x")
    res = model.seen[1][-1]["content"]
    assert "unknown tool 'get_wether'; available tools: add, get_weather" in res[0]["content"]
    assert "unexpected property 'c'" in res[1]["content"] and all(x["is_error"] for x in res)
    assert r.status == "final"


def test_tool_exception_and_timeout_become_errors() -> None:
    reg = make_registry()

    @reg.register("flaky", "Always raises.", {"type": "object", "properties": {}})
    def flaky() -> str:
        raise ConnectionError("upstream reset")

    @reg.register("slow", "Takes too long.", {"type": "object", "properties": {}}, timeout_s=0.05)
    def slow() -> str:
        time.sleep(0.5)
        return "late"

    model = FakeModel([ModelResponse([tool_use("f", "flaky"), tool_use("s", "slow"),
                                      tool_use("g", "add", a=2, b=2)], "tool_use"),
                       ModelResponse([text("ok")], "end_turn")])
    t0 = time.monotonic()
    r = Agent(model, reg).run("x")

def test_parallel_calls_run_concurrently_and_keep_call_order() -> None:

def test_schema_validator_and_registry_rules() -> None:
    s = {"type": "object", "required": ["tags"], "properties": {
        "tags": {"type": "array", "items": {"type": "string", "enum": ["a", "b"]}},
        "k": {"type": "integer", "minimum": 1, "maximum": 5}}}
    validate({"tags": ["a", "b"], "k": 3}, s)
    for bad, msg in [({"tags": ["a", "c"]}, "$.tags[1]: 'c' is not one of"), ({}, "missing required"),
                     ({"tags": [], "k": 9}, "above maximum"), ({"tags": [], "k": True}, "expected integer")]:
        try:
            validate(bad, s)
        except SchemaError as e:
            assert msg in str(e), (msg, str(e))
        else:
            raise AssertionError(f"accepted {bad}")
    reg = make_registry()
    for args in [("add", "dup", {"type": "object"}), ("x", "not an object", {"type": "string"})]:
        try:
            reg.register(*args)
        except ValueError:
            pass
        else:
            raise AssertionError("bad registration accepted")
    assert [t["name"] for t in reg.specs()] == ["add", "get_weather"]


def test_stress_one_agent_shared_by_threads() -> None:
    class EchoModel:                    # stateless: answers from the messages it is shown
        def __call__(self, messages, tools):
            last = messages[-1]["content"]
            if last[0]["type"] == "text":                       # first turn: fan out 5 adds
                n = int(last[0]["text"])
                return ModelResponse([tool_use(f"{n}-{i}", "add", a=n, b=i) for i in range(5)], "tool_use")
            total = sum(int(r["content"]) for r in last)
            return ModelResponse([text(str(total))], "end_turn")
    agent, out, errors = Agent(EchoModel(), make_registry(), max_workers=16), {}, []

    def worker(k: int) -> None:
        try:
            for n in range(k * 50, k * 50 + 50):
                out[n] = agent.run(str(n)).text
        except Exception as e:          # pragma: no cover
            errors.append(e)
    ts = [threading.Thread(target=worker, args=(k,)) for k in range(8)]
    for t in ts: t.start()
    for t in ts: t.join()
    assert not errors and len(out) == 400
    assert all(out[n] == str(5 * n + 10) for n in out)    # sum of n+i for i in 0..4

10 · Edge cases

A response with tool_use blocks but stop reason end_turn (or the reverse): trust the blocks you can act on and the documented stop reason together; the solution treats "no tool calls or not tool_use" as final. Truncated tool input: if the model hit its output limit mid-call (stop reason max_tokens), the input may be incomplete JSON or a valid-looking partial object; do not execute it — re-request with more room. Duplicate tool_use ids in one turn: reject the turn rather than answering one id twice. Tool returns non-JSON-serialisable data: json.dumps(default=str) keeps the loop alive. A tool that never returns: the harness moves on, but the worker is lost until it does; bound tool I/O. Empty final text: a model may end its turn with no text; return an empty string and let the caller decide. Budgets exhausted mid-turn: the tool-call budget is checked before executing any of a turn's calls, so the transcript never contains a tool_use without its result unless the run stopped deliberately.

11 · Extensions the interviewer will ask for

Human approval: tag tools with a risk level; for risky calls, pause, persist the transcript and pending calls, and resume with the real result or a "denied by user" error result. Persistence and resumption: all state already lives in messages plus the budget counters, so checkpoint them after each step and a crashed run can resume from the last checkpoint. Streaming: stream the model's text to the user and accumulate tool_use input fragments; validate the complete input before running. Async: the same loop with asyncio.gather or a TaskGroup and asyncio.wait_for per tool; cancellation actually stops coroutines. Retries: wrap the model call in ld4's resilient client; retry idempotent tools on transient errors before reporting failure. Context management: when tokens per step grow, drop or summarise old tool results (ag5). Serial tools: mark tools that must not run concurrently and execute them one at a time.

12 · Complexity

Per step: one model call, plus O(k) work to dispatch k tool calls and validation linear in the size of each input. With a pool of w workers, a turn's wall time is about the slowest call when k ≤ w, and roughly ⌈k / w⌉ × the typical call time beyond that. The transcript grows by the size of each turn's content and results, so the tokens sent per model call grow linearly with steps and total tokens quadratically — the reason token budgets and context trimming matter more than step limits. Memory: O(transcript) per run plus the trace.

Errors are prompts

An error result is text the model reads and acts on, so it deserves the same care as a prompt. Good error messages say what failed, where, and what would succeed: "$.date: expected format YYYY-MM-DD, got '10/10/2026'"; "unknown tool 'search_web'; available tools: web_search, fetch_page"; "rate limited by the search API; retry after 20 seconds or use cached_search". Bad ones say "error" or dump a stack trace, and the model either repeats the call or gives up. Anthropic's tool-use guidance makes the same point from the provider side: return the error with is_error set and an informative message, and the model will typically try a different approach. In evaluation, the share of tool errors followed by a successful corrected call is a useful metric of error-message quality.

Validation layers: provider, harness, tool

There are three places to check arguments. Providers increasingly offer strict tool use — Anthropic's API accepts strict: true on a tool definition, constraining generation so the input matches the schema exactly. The harness validates against the registered schema, which catches anything the provider did not enforce and works for any provider. And the tool itself validates business rules no schema expresses (this customer exists; this amount is within the user's limit). Each layer catches different mistakes. With streamed tool input, partial JSON must be parsed strictly and validated after the block completes, because a lenient parser can return a silently truncated object.

Parallelism changes what the model does

Models make parallel calls when they judge actions independent, and harnesses influence that judgement. If results for one turn are returned across several messages, the transcript looks as if the calls were sequential, and the model learns from its own history to stop parallelising; if a failed call's result is dropped, the model may assume it succeeded. When some tools must not run concurrently (two writes to the same file), either serialise them in the harness or tell the API to allow at most one call per turn (Anthropic's disable_parallel_tool_use option on tool_choice). Parallel execution also changes failure semantics: if call 2 fails and call 3 succeeds, the model sees both outcomes and must reason about a partial success, which is one more reason for precise messages.

Why the loop must be append-only

The harness appends the model's response exactly as returned, including any reasoning or thinking blocks, and never rewrites earlier turns. Two reasons. Prompt caching matches on an unchanged prefix, so editing an early message invalidates the cache for everything after it, multiplying cost. And some current models bind reasoning blocks to the conversation that produced them, rejecting or ignoring them if earlier history was edited. Context management (dropping old tool results) is therefore done deliberately, rarely, and with the provider's supported mechanisms, not by mutating the list casually inside the loop.

Threads, processes or async

Threads are right for this round: tools are typically network calls, which release the global interpreter lock while waiting, and the code stays simple. Their limitation — no cancellation — matters when tools can hang. Processes allow killing a stuck tool and suit CPU-bound or untrusted code (a code-execution tool should run in a sandboxed subprocess or container, never in the harness's own process). Asyncio gives cheap concurrency for thousands of in-flight calls and real cancellation, at the cost of requiring every tool to be async or wrapped with asyncio.to_thread. Naming the trade-off and why you chose threads is worth more in the interview than the choice itself. A useful closing sentence: the orchestration logic does not change between the three, only the executor does, which is why the solution keeps execution inside one method.

Budgets as product decisions

Budget values come from the product, not the code. An interactive assistant might allow 8 steps and 30 seconds; a nightly research agent 100 steps and an hour; a coding agent a token budget sized to its cost per task. The harness should make hitting a budget a graceful outcome — return what is known, say what was not finished — and the trace should record which budget bound, so that limits can be tuned from data: if 20% of runs hit the step limit with correct partial answers, the limit may be too tight; if most of them were looping, the guard or the prompt needs work.

How agent loops fail in production

Runaway loops. A model repeatedly calls a search tool with slight variations, each returning nothing useful, until the step budget ends the run. Detection: steps per run and repeated-call counts in the trace. Fix: the repeat guard, better tool results ("no results; try a broader query"), and prompts that tell the model when to stop.

Silent wrong actions. A model passes a customer id as a string with a leading space; the tool, without validation, looks up nothing and creates a new record. Detection: tool-level business validation failures and audit of side effects. Fix: schema validation in the harness plus semantic validation in the tool.

Hung runs. One tool's upstream stops responding; without timeouts, runs hang until the user gives up and the worker pool fills. Detection: tool latency percentiles and pool saturation. Fix: per-tool timeouts in the harness and real I/O timeouts inside tools.

Cost blow-ups. A tool starts returning much larger results (an API added fields), every subsequent step carries them, and token use per run triples. Detection: tokens per step in the trace, alerting on drift. Fix: result truncation or projection, and context trimming.

Provider drift. A model upgrade changes how often the model calls tools in parallel or how it escapes strings in tool inputs; a harness that string-matched serialised inputs instead of parsing them breaks. Detection: tool error rates by model version. Fix: always parse inputs as JSON, validate, and run the agent's evaluation suite on every model change.

Mismatched results. A harness bug returns results in completion order without ids, or drops a failed one; the model attributes results to the wrong calls. Detection: hard to see in outputs, obvious in the trace. Fix: always pair by tool_use_id, include every call's result.

What to measure

Per run: status (final versus each budget), steps, tokens, wall time, tool calls, error results and repeat refusals. Per tool: call rate, error rate by error type, latency percentiles, timeouts, result size. Per model call: input and output tokens, cache hit tokens if the provider reports them. Then the quality signals from evaluation (ag12): task success, and how often an error result is followed by a successful correction.

Knobs

Pool size (at least the largest expected parallel fan-out times concurrent runs, bounded by downstream limits); per-tool timeouts (from each tool's p99 latency plus margin); the four budgets (from product requirements and observed distributions); max_repeats (2-3); max_result_chars (sized against the context budget per step); and whether parallel calls are allowed at all for side-effecting tools.

The real reference: the provider's documented contract

The message shapes in this solution follow Anthropic's tool-use documentation: tools defined with name, description and input_schema; a response with stop_reason "tool_use" containing tool_use blocks with id, name and input; results sent back as tool_result blocks with tool_use_id, content and optional is_error; parallel tool use on by default, with all results for a turn returned in a single user message; and strict: true available on a tool definition to guarantee schema-valid inputs. The official SDKs also provide a tool runner that drives this loop for you; writing it by hand, as in this round, is what you do when you need control the runner does not give, and it is the best way to understand what any runner or framework is doing underneath.

Design it

Your team's support agent has three tools: lookup_order(order_id), refund(order_id, amount_cents) and send_email(to, body). Interactive users wait at most 20 seconds. Last week the agent refunded one order twice and emailed a customer an empty body. Which parts of this lesson's loop would have prevented each, and what else do you add?

Answer

Double refund. Likely a timeout or retry: the first refund call timed out from the harness's point of view, the model saw an error and called refund again, but the first call had completed. Fixes: give refund an idempotency key derived from the tool_use id (or from order id + amount) and pass it to the payments API so a repeat is deduplicated; make refund check existing refunds before acting; tag it as requiring approval above a threshold; and have the repeat guard refuse identical refund calls after one. Empty email. Validation: the schema should require body with minLength (say 20) and to with a format check, and the tool should apply business validation (no placeholder text). Latency. A 20-second wall-time budget with per-tool timeouts (lookup 3 s, refund 8 s, email 5 s), and lookups for several orders run in parallel. Add tracing so every refund can be tied to the run, step and model decision that caused it.

Diagnose it

After a harness refactor, the agent's tool calls per run dropped by 40% and task success fell, though no single error appears. In traces, turns that used to contain three parallel lookups now contain one lookup each. What changed?

Answer

The refactor probably changed how results are returned: sending each tool_result in its own user message (or interleaving text between them) instead of all results for a turn in one message. The model, seeing a history in which its parallel calls appear to have been answered one by one, stops making parallel calls; each lookup now takes its own step, steps run out sooner or latency budgets bind, and success falls. Confirm by diffing the message structure in traces before and after. Fix: return every result for a turn in a single user message, in call order, and add a test asserting that structure.
