A customer-support assistant answers 2 million questions a month, and the finance team notices that a third of them are some version of "how do I reset my password", "where is my order" or "what is your refund policy". Each costs a model call: a few cents and two seconds. Someone proposes a cache. An exact-match cache helps a little — the identical string "How do I reset my password?" comes up often — but "how can I reset my password", "reset password how", and "I forgot my password" all miss. So the team adds a semantic cache: embed each question, and if a stored question is close enough, return its answer. The hit rate jumps. Two weeks later, a customer who wrote "do not cancel my order" receives "Your order has been cancelled — you'll get a refund in 5 days", because the cache matched it to "cancel my order". Another customer, of a different company using the same platform, receives an answer that mentions a competitor's internal discount code.

A semantic cache is one of the most common optimisations proposed for LLM applications and one of the most commonly misbuilt. The mechanism is simple: an embedding, a similarity threshold, a dictionary. The design decisions are what an interviewer probes. Where does the exact match go? What must be in the key besides the question? How do you pick the threshold, and what is the error rate it implies? How do entries expire, and what bounds memory? How do you keep tenants apart? How do you even know when the cache gave a wrong answer? And when is a semantic cache simply the wrong tool?

This lesson builds one in the order a machine-coding round flows: requirements, the entities, a naive version, then in stages an exact-key fast path, semantic matching with a deterministic toy embedder (so tests are reproducible), partitioning by tenant, model and parameters, TTL and LRU eviction, metrics including false hits, and a threshold sweep over labelled pairs that makes the core trade-off concrete. The full solution is a runnable Python 3.12 file with nine tests including a concurrent stress test. The sweep is the lesson's centre: with this embedder, the paraphrase "What is your refund policy?" / "What's your refund policy?" scores 0.787 while "capital of Australia" / "capital of Austria" scores 0.829 — no threshold separates them.

The analogy: a help desk with a binder of past answers

A help desk keeps a binder of questions it has answered, each with the answer written out. When a new question arrives, the clerk first checks the index for that exact question — if it is there, copy the answer. If not, the clerk skims the binder for a question that "sounds the same" and, if one is close enough, copies that answer instead of researching from scratch. The binder has a separate section for each client company, so one company's answers are never given to another. Each page has a "valid until" date, after which it is torn out. And the binder has a fixed number of pages: when it is full, the page nobody has looked at for the longest is removed.

The exact index is the exact-key fast path. "Sounds the same" is embedding similarity above a threshold. The sections are namespaces by tenant (and, in practice, by model and settings, since a different expert might answer differently). "Valid until" is the TTL. Removing the least-read page is LRU eviction.

The analogy breaks exactly where the danger is. A human clerk reading "do not cancel my order" notices the "not". An embedding compresses a sentence into a few hundred numbers, and small words that flip the meaning can barely move it. The clerk's "sounds the same" is judgement; the cache's is a number compared with a threshold, and the number is wrong sometimes. The design must assume that and measure it.

Where it sits in an LLM application

A request to an LLM application passes several places where reuse is possible, and the semantic cache is only one. Before the model call, the provider's prompt cache can make a repeated long prefix cheap without changing the answer. An exact response cache can return a stored answer for a byte-identical request. The semantic cache sits after those, catching paraphrases. After it comes the model call, and the result flows back to be stored. Placing the semantic layer last among the caches means it handles only what the safe layers could not, which keeps its error rate confined to the traffic that needs it.

What the round expects

A class with get and put; an exact fast path; cosine similarity over unit vectors with a threshold; namespaces that include the tenant and everything that changes the answer; TTL with an injected clock; an LRU bound per namespace; thread safety with the slow embedding call outside the lock; metrics including false hits; a deterministic embedder for tests; and — the part that distinguishes strong candidates — a clear statement of the false-hit risk, how to measure it and how the threshold trades it against hit rate.

1 · Clarify the requirements

Ask: what traffic is this for — repeated FAQ-like questions, or long personalised prompts? Is the deployment multi-tenant? Which model and parameters vary between requests? How stale may an answer be? How large may the cache grow? What is the cost of a wrong answer (a support FAQ versus a refund decision)? Is there an embedding model available, and what does it cost per call? Is the cache in-process or shared between servers?

A typical agreed scope: an in-process cache (a shared store is an extension); get(tenant, prompt, model, **params) and put(...); exact-match fast path; semantic match by cosine similarity over embeddings with a configurable threshold; per-tenant isolation and partitioning by model and parameters; TTL; an LRU size bound per namespace; metrics for exact hits, semantic hits, misses, false hits, evictions and expirations; thread-safe; and a deterministic embedder for tests. Non-functional: a lookup should cost one embedding plus a scan; exact hits should cost microseconds.

2 · Entities and the interface

embed(text) -> Vector                       # unit-length; ToyEmbedder in tests, a real model in prod
SemanticCache(embed, threshold, ttl_s, max_entries, clock)
  .get(tenant, prompt, model, **params) -> Lookup(response, kind, similarity, matched_prompt)
  .put(tenant, prompt, response, model, **params)
  .report_false_hit(tenant, matched_prompt, model, **params)
  .invalidate_tenant(tenant) -> int
  .metrics -> Metrics(exact_hits, semantic_hits, misses, false_hits, evictions, expirations)

Internally: a dict from namespace — the pair (tenant, partition key) — to an OrderedDict mapping exact key to Entry (prompt, response, vector, expiry, hit count). The OrderedDict doubles as the LRU list: move_to_end on access, popitem(last=False) to evict, both O(1) — the same trick as ld1's honest ten-line LRU. One lock protects the structure; the embedder is injected so tests can use a deterministic one, and the clock is injected so TTL tests do not sleep.

3 · Stage one: the naive version

cache = []                                  # list of (vector, prompt, response)
def get(prompt):
    v = embed(prompt)
    best = max(cache, key=lambda e: cosine(v, e[0]), default=None)
    if best and cosine(v, best[0]) > 0.8:
        return best[2]
def put(prompt, response):
    cache.append((embed(prompt), prompt, response))

It works in a demo and has every production problem. It embeds even identical repeats. It shares answers across tenants and across models. It never expires anything, so last quarter's price is served forever. It grows without bound. It has no metrics, so nobody knows the hit rate or how often it is wrong. Its threshold of 0.8 was chosen by feel. It is not thread-safe. And it re-embeds on every put even when the prompt is already cached. The stages fix these in order of risk.

4 · Stage two: the exact-key fast path

Before any embedding, hash the normalised prompt and look it up. Normalisation is deliberately conservative: lower-case and collapse whitespace, nothing else. " what IS your refund policy?" and "What is your refund policy?" share a key. Stripping punctuation, digits or stop words would make more strings collide, but an exact hit is trusted completely — it skips the similarity check — so every normalisation step must be one that can never change meaning. Removing digits would merge "refund order 1234" with "refund order 5678"; removing stop words would merge "cancel" with "do not cancel". Fuzziness belongs in the semantic step, where it is measured.

The fast path is cheap (a SHA-256 of a short string and a dict lookup, microseconds), it avoids the embedding call entirely, and it can never be a false hit. In real traffic a large share of repeats are byte-identical — retries, programmatic callers, popular canned questions — so it often carries a substantial fraction of all hits by itself.

5 · Stage three: semantic matching

The embedder. Tests need an embedder that is deterministic and free. The solution's ToyEmbedder uses feature hashing: each word (weight 1) and each character trigram of each word (weight 0.5, so spelling variants overlap) is hashed with BLAKE2 — not Python's built-in hash(), which is randomised per process — into one of 512 positions, with the hash's top bit choosing the sign so collisions tend to cancel rather than accumulate; the vector is then scaled to unit length. It captures word overlap and typos, not meaning, which is precisely what makes it a good teacher: it fails the same way real embedders sometimes do, only more visibly.

Cosine similarity. For unit-length vectors, cosine similarity is just the dot product: 1.0 for identical direction, around 0 for unrelated. The lookup embeds the prompt (outside the lock, see below), scans the namespace, keeps the best similarity, and returns a semantic hit if it is at least the threshold. Worked from the solution's labelled pairs: "How can I reset my password?" against the cached "How do I reset my password?" scores 0.863; the typo "how do i reset my pasword" scores 0.882 (trigrams rescue the misspelling); "How do I change my email address?" scores 0.508. At a threshold of 0.85 the first two hit and the third misses.

Embedding outside the lock. Embedding is the slow step — in production a network call to an embedding model, several milliseconds. If get held the lock while embedding, every concurrent lookup would queue behind it. So get checks the exact key under the lock, releases it, embeds, then re-acquires the lock to scan. The cache may change in between (an entry may be added or evicted); for a cache that is harmless — at worst a lookup misses an entry added a millisecond earlier.

6 · Stage four: namespaces — tenants, models, parameters

A response depends on more than the prompt. The namespace is the pair (tenant, partition key), where the partition key is the model plus a sorted JSON of the parameters that change the answer: "small-model" + '{"temperature": 0}'. Lookups and inserts touch only their own namespace, so a different model, a different temperature, or a different tenant can never be served another's answer — not even on an exact match. The test test_tenants_are_isolated stores "What is our discount code?" with the answer "ACME-SECRET-20" for tenant acme and checks that tenant globex, asking the identical question, misses. In a real system the partition key also includes the system prompt or template version (a new prompt template makes old answers stale), the tool set, and for retrieval-augmented answers, the version of the documents retrieved.

invalidate_tenant drops every namespace for a tenant at once — what you call when a tenant updates its policies, or on an incident.

7 · Stage five: TTL and LRU

TTL. Each entry stores expires_at = clock() + ttl_s. Expiry is enforced lazily: _alive checks an entry whenever a lookup meets it, and deletes it if expired. Inserts also sweep the namespace for expired entries before LRU eviction, so the size bound is spent on live entries. The test sets a 60-second TTL with a fake clock: at 59.9 seconds the entry hits; at exactly 60.0 it is gone and an expiration is counted.

LRU. Each namespace holds at most max_entries. Every hit moves the entry to the end of the OrderedDict; when an insert makes the namespace too large, popitem(last=False) removes the front — the least recently used. The test inserts alpha, beta, gamma into a namespace of three, reads alpha (making it most recent), inserts delta, and checks that beta — not alpha — was evicted. A per-namespace bound also stops one tenant's traffic from evicting another's entries, a fairness property worth stating.

8 · Stage six: metrics, false hits and the threshold sweep

What to count. Exact hits, semantic hits and misses give the hit rate. Evictions and expirations show whether the size and TTL are right. And false hits — semantic hits whose answer was wrong — are the only measure of whether the cache is safe. They cannot be detected at lookup time (if the cache could tell, it would not have returned the answer), so they arrive later: a user's thumbs-down, a support escalation, a sampled LLM judge comparing the new question with the matched question and answer, or shadow traffic that calls the model anyway for a sample of semantic hits and compares. report_false_hit counts the event and removes the offending entry so it cannot mislead again. The test shows the canonical failure: with a threshold of 0.7, "Do not cancel my order" matches "Cancel my order" (similarity 0.811) and returns "Your order is cancelled."

The sweep. The solution labels twelve pairs: six with the same intent (paraphrases, a typo, extra punctuation) and six near-misses (a negation, Sunday versus Saturday, two order numbers, Australia versus Austria, French versus German, and an unrelated question). The threshold is a dial between hit rate and false hits, chosen per product from a sweep like this on real, labelled traffic.

9 · The full solution

Running the file prints the sweep and the similarity of every labelled pair, then nine tests: the exact fast path, semantic hit and miss, tenant isolation and invalidation, partitioning by model and parameters, TTL with a fake clock, LRU order, false-hit feedback, the monotone sweep, and eight threads doing 1,600 concurrent gets and puts across three tenants. Python 3.12, standard library only.

"""A semantic cache for LLM responses: a deterministic toy embedder, an exact-key fast path, a
cosine-similarity threshold, TTL and LRU eviction, per-tenant namespaces, partitioning by model
and parameters, and hit / false-hit metrics with a threshold sweep.
Python 3.12, standard library only.  Run: python semantic_cache.py"""
from __future__ import annotations

import hashlib
import json
import math
import re
import threading
import time
from collections import OrderedDict
from dataclasses import dataclass, field
from typing import Callable

Vector = list[float]


# ---------------------------------------------------------------- a deterministic toy embedder
class ToyEmbedder:
    """Feature hashing of words and character trigrams into `dim` buckets, L2-normalised.
    Deterministic across runs and machines (blake2b, not Python's salted hash()). It captures
    word overlap and spelling variants, NOT meaning: 'cancel my order' and 'do not cancel my
    order' look very similar to it, which is exactly the false-hit risk a real cache must face."""

    def __init__(self, dim: int = 512) -> None:
        self.dim = dim

    def _features(self, text: str) -> list[tuple[str, float]]:
        words = re.findall(r"[a-z0-9']+", text.lower())
        feats = [(f"w:{w}", 1.0) for w in words]
        for w in words:
            padded = f"#{w}#"
            feats += [(f"c:{padded[i:i + 3]}", 0.5) for i in range(len(padded) - 2)]
        return feats

    def __call__(self, text: str) -> Vector:
        v = [0.0] * self.dim
        for feat, weight in self._features(text):
            h = int.from_bytes(hashlib.blake2b(feat.encode(), digest_size=8).digest(), "big")
            v[h % self.dim] += weight if (h >> 63) & 1 else -weight     # signed hashing
        norm = math.sqrt(sum(x * x for x in v)) or 1.0
        return [x / norm for x in v]


def cosine(a: Vector, b: Vector) -> float:          # both unit length: dot product = cosine
    return sum(x * y for x, y in zip(a, b))


def normalise(prompt: str) -> str:
    """Conservative normalisation for the exact key: case and whitespace only."""
    return " ".join(prompt.lower().split())


# ---------------------------------------------------------------- the cache
@dataclass
class Entry:
    prompt: str
    response: str
    vector: Vector
    expires_at: float
    hits: int = 0


@dataclass
class Lookup:
    response: str | None
    kind: str                       # "exact" | "semantic" | "miss"
    similarity: float = 0.0
    matched_prompt: str | None = None


@dataclass
class Metrics:
    exact_hits: int = 0
    semantic_hits: int = 0
    misses: int = 0
    false_hits: int = 0             # semantic hits later reported wrong
    evictions: int = 0
    expirations: int = 0

    @property
    def hit_rate(self) -> float:
        total = self.exact_hits + self.semantic_hits + self.misses
        return (self.exact_hits + self.semantic_hits) / total if total else 0.0


class SemanticCache:
    def __init__(self, embed: Callable[[str], Vector], threshold: float = 0.9, ttl_s: float = 3600.0,
                 max_entries: int = 1000, clock: Callable[[], float] = time.monotonic) -> None:
        if not 0.0 < threshold <= 1.0:
            raise ValueError("threshold must be in (0, 1]")
        self.embed, self.threshold, self.ttl_s = embed, threshold, ttl_s
        self.max_entries, self.clock = max_entries, clock
        # namespace = (tenant, partition); partition = model + parameters that change the answer
        self._spaces: dict[tuple[str, str], OrderedDict[str, Entry]] = {}
        self._lock = threading.Lock()
        self.metrics = Metrics()

    @staticmethod
    def partition(model: str, **params: object) -> str:
        return model + json.dumps(params, sort_keys=True)

    @staticmethod
    def _key(prompt: str) -> str:
        return hashlib.sha256(normalise(prompt).encode()).hexdigest()

    def get(self, tenant: str, prompt: str, model: str, **params: object) -> Lookup:
        ns, key = (tenant, self.partition(model, **params)), self._key(prompt)
        vec = None
        with self._lock:
            space = self._spaces.get(ns)
            if space is not None:
                e = space.get(key)
                if e is not None and self._alive(space, key, e):            # 1. exact fast path
                    space.move_to_end(key)
                    e.hits += 1
                    self.metrics.exact_hits += 1
                    return Lookup(e.response, "exact", 1.0, e.prompt)
        vec = self.embed(prompt)                    # embed outside the lock: it is the slow part
        with self._lock:
            space = self._spaces.get(ns)
            best_key, best_sim = None, -1.0
            if space is not None:
                for k, e in list(space.items()):                            # 2. semantic scan
                    if not self._alive(space, k, e):
                        continue
                    sim = cosine(vec, e.vector)
                    if sim > best_sim:
                        best_key, best_sim = k, sim
            if best_key is not None and best_sim >= self.threshold:
                e = space[best_key]
                space.move_to_end(best_key)
                e.hits += 1
                self.metrics.semantic_hits += 1
                return Lookup(e.response, "semantic", best_sim, e.prompt)
            self.metrics.misses += 1
            return Lookup(None, "miss", max(best_sim, 0.0))

    def put(self, tenant: str, prompt: str, response: str, model: str, **params: object) -> None:
        ns, key = (tenant, self.partition(model, **params)), self._key(prompt)
        vec = self.embed(prompt)
        with self._lock:
            space = self._spaces.setdefault(ns, OrderedDict())
            space[key] = Entry(prompt, response, vec, self.clock() + self.ttl_s)
            space.move_to_end(key)
            self._evict(space)

    def report_false_hit(self, tenant: str, matched_prompt: str, model: str, **params: object) -> None:
        """Feedback (a user said the answer was wrong, or a judge disagreed): count it and drop the entry."""
        ns = (tenant, self.partition(model, **params))
        with self._lock:
            self.metrics.false_hits += 1
            space = self._spaces.get(ns)
            if space is not None:
                space.pop(self._key(matched_prompt), None)

    def invalidate_tenant(self, tenant: str) -> int:
        with self._lock:
            doomed = [ns for ns in self._spaces if ns[0] == tenant]
            n = sum(len(self._spaces[ns]) for ns in doomed)
            for ns in doomed:
                del self._spaces[ns]
            return n

    def size(self, tenant: str | None = None) -> int:
        with self._lock:
            return sum(len(s) for ns, s in self._spaces.items() if tenant is None or ns[0] == tenant)

    # ---- internals (lock held)
    def _alive(self, space: OrderedDict, key: str, e: Entry) -> bool:
        if e.expires_at <= self.clock():
            del space[key]
            self.metrics.expirations += 1
            return False
        return True

    def _evict(self, space: OrderedDict) -> None:
        now = self.clock()
        for k in [k for k, e in space.items() if e.expires_at <= now]:      # expired first
            del space[k]
            self.metrics.expirations += 1
        while len(space) > self.max_entries:                               # then least recently used
            space.popitem(last=False)
            self.metrics.evictions += 1


# ---------------------------------------------------------------- tests
class FakeClock:
    def __init__(self) -> None:
        self.t = 0.0

    def __call__(self) -> float:
        return self.t


EMB = ToyEmbedder()

# (query, cached prompt, same intent?) — labelled pairs for the threshold sweep
PAIRS = [
    ("How do I reset my password?", "how do i reset my password", True),
    ("How can I reset my password?", "How do I reset my password?", True),
    ("how do i reset my pasword", "How do I reset my password?", True),
    ("What is your refund policy?", "What's your refund policy?", True),
    ("Where is my order?", "where is my order??", True),
    ("Cancel my order", "Please cancel my order", True),
    ("Cancel my order", "Do not cancel my order", False),
    ("Is the store open on Sunday?", "Is the store open on Saturday?", False),
    ("Refund for order 1234", "Refund for order 5678", False),
    ("What is the capital of Australia?", "What is the capital of Austria?", False),
    ("How do I reset my password?", "How do I change my email address?", False),
    ("Translate 'hello' to French", "Translate 'hello' to German", False),
]


def test_exact_fast_path_ignores_case_and_spacing() -> None:
    c = SemanticCache(EMB)
    c.put("acme", "What is your refund policy?", "30 days.", "m1")
    r = c.get("acme", "  what IS your   refund policy?", "m1")
    assert (r.kind, r.response, r.similarity) == ("exact", "30 days.", 1.0)


def test_semantic_hit_and_miss() -> None:
    c = SemanticCache(EMB, threshold=0.85)
    c.put("acme", "How do I reset my password?", "Use the reset link.", "m1")
    hit = c.get("acme", "How can I reset my password?", "m1")
    miss = c.get("acme", "How do I change my email address?", "m1")
    assert hit.kind == "semantic" and hit.response == "Use the reset link." and hit.similarity >= 0.85
    assert miss.kind == "miss" and miss.response is None
    assert (c.metrics.semantic_hits, c.metrics.misses) == (1, 1)


def test_tenants_are_isolated() -> None:
    c = SemanticCache(EMB)
    c.put("acme", "What is our discount code?", "ACME-SECRET-20", "m1")
    assert c.get("globex", "What is our discount code?", "m1").kind == "miss"   # not even exact
    assert c.get("acme", "What is our discount code?", "m1").kind == "exact"
    assert c.invalidate_tenant("acme") == 1 and c.size() == 0


def test_model_and_parameters_partition_the_cache() -> None:
    c = SemanticCache(EMB)
    c.put("acme", "Summarise this policy", "Short summary", "small-model", temperature=0)
    assert c.get("acme", "Summarise this policy", "large-model", temperature=0).kind == "miss"
    assert c.get("acme", "Summarise this policy", "small-model", temperature=0.7).kind == "miss"
    assert c.get("acme", "Summarise this policy", "small-model", temperature=0).kind == "exact"


def test_ttl_expiry() -> None:
    clock = FakeClock()
    c = SemanticCache(EMB, ttl_s=60, clock=clock)
    c.put("acme", "Opening hours?", "9 to 5", "m1")
    clock.t = 59.9
    assert c.get("acme", "Opening hours?", "m1").kind == "exact"
    clock.t = 60.0
    assert c.get("acme", "Opening hours?", "m1").kind == "miss" and c.metrics.expirations == 1
    assert c.size() == 0


def test_lru_eviction_respects_recency() -> None:
    c = SemanticCache(EMB, max_entries=3, threshold=0.99)
    for p in ["alpha question", "beta question", "gamma question"]:
        c.put("t", p, p.upper(), "m1")
    c.get("t", "alpha question", "m1")                    # alpha is now most recent
    c.put("t", "delta question", "DELTA", "m1")           # evicts beta, the least recent
    assert c.get("t", "beta question", "m1").kind == "miss"
    assert all(c.get("t", p, "m1").kind == "exact" for p in ["alpha question", "gamma question", "delta question"])
    assert c.metrics.evictions == 1 and c.size("t") == 3


def test_false_hit_feedback_drops_the_entry() -> None:
    c = SemanticCache(EMB, threshold=0.7)
    c.put("t", "Cancel my order", "Your order is cancelled.", "m1")
    r = c.get("t", "Do not cancel my order", "m1")
    assert r.kind == "semantic"                           # the toy embedder cannot see negation
    c.report_false_hit("t", r.matched_prompt, "m1")
    assert c.metrics.false_hits == 1 and c.get("t", "Do not cancel my order", "m1").kind == "miss"


def sweep(thresholds: list[float]) -> list[tuple[float, int, int, int]]:
    """For each threshold: (threshold, true hits, false hits, missed same-intent pairs)."""
    rows = []
    for th in thresholds:
        tp = fp = fn = 0
        for query, cached, same in PAIRS:
            sim = cosine(EMB(query), EMB(cached))
            if normalise(query) == normalise(cached):
                sim = 1.0
            if sim >= th:
                tp += same
                fp += not same
            else:
                fn += same
        rows.append((th, tp, fp, fn))
    return rows


def test_threshold_sweep_trades_hits_for_false_hits() -> None:
    rows = sweep([0.5, 0.6, 0.7, 0.8, 0.9, 0.95])
    tps, fps = [r[1] for r in rows], [r[2] for r in rows]
    assert tps == sorted(tps, reverse=True) and fps == sorted(fps, reverse=True)   # both fall as threshold rises
    assert fps[0] > 0 and fps[-1] == 0                                         # low threshold: false hits
    assert tps[-1] >= 1                                                         # high: still some hits


def test_concurrent_gets_and_puts() -> None:
    c, errors = SemanticCache(EMB, max_entries=50), []

10 · Edge cases

Empty or whitespace prompt: the embedder returns a zero vector scaled by 1, similarity 0 to everything; reject it at the API. Two entries tie for best similarity: the first scanned wins; deterministic but arbitrary — prefer the most recent or the most hit. Updating an answer: put with the same normalised prompt overwrites the entry and resets its TTL. Threshold of exactly 1.0: semantic matching degenerates to vector equality — useful as an off switch. Responses that should never be cached: errors, refusals, answers containing user-specific data, and streamed responses that were cut off; the caller decides, and the cache should expose a way to skip storage. Embedding failures: if the embedding call fails, fall through to the model rather than failing the request — the cache is an optimisation, never a dependency.

11 · Extensions the interviewer will ask for

A verification step for borderline matches (say 0.80-0.90): a rule check that numbers, dates and named entities in both prompts match, or a small model asked "do these two questions have the same answer?". Shared storage: Redis or a vector database holding vectors and responses, with TTL and per-tenant filters as store features — RedisVL's SemanticCache, for example, stores prompt-response pairs with a cosine distance threshold, an optional TTL refreshed on hits, and filterable fields to scope entries by user or account. An ANN (approximate nearest-neighbour) index per namespace once entries exceed tens of thousands (ld3). Adaptive thresholds per namespace, tuned from that namespace's false-hit feedback. Caching at a different level: cache retrieval results or tool outputs instead of final answers, where staleness and personalisation are easier to reason about. Warming: pre-populate with curated FAQ (frequently asked question) pairs reviewed by a human, which makes the cache's answers trustworthy by construction.

12 · Complexity

Exact lookup: O(p) to normalise and hash a prompt of length p, O(1) dictionary access. Semantic lookup: one embedding call plus O(n·d) to scan n entries of dimension d — 512 here, 768-3,072 for real models; at 10,000 entries of 768 dimensions that is 7.7 million multiply-adds, a few milliseconds in vectorised code and much more in pure Python. Insert: one embedding, O(1) dictionary work, plus an O(n) expired-entry sweep (amortisable by sweeping only occasionally). Memory: O(n·d) floats per namespace — 10,000 entries × 768 dimensions × 4 bytes ≈ 31 MB as float32, or roughly double that as Python floats in lists.

Semantic caching versus prompt caching

Two different features share the word "cache". Provider prompt caching reuses the computation for an identical prefix of a request — a long system prompt, a document, conversation history — so repeated prefixes are processed far more cheaply and quickly, while the model still generates a fresh answer. It has no correctness risk: the answer is computed for this exact request. A semantic cache skips the model entirely and returns an answer generated for a different request. The first is almost always worth turning on; the second is a product decision with an error rate. In interviews, propose prompt caching first for long shared prefixes, an exact response cache second, and a semantic cache only for high-repeat, low-risk traffic.

Why embeddings confuse near-misses

Embedding models are trained so that texts about the same thing land close together. "What is the capital of Australia?" and "What is the capital of Austria?" are about the same thing — a capital city question with a similar country name — so they should be close by the model's training objective, even though their answers differ completely. Negation is similar: "cancel" and "do not cancel" share their topic, and a single function word moves a sentence embedding only a little. This is not a bug in a particular model; it is a mismatch between what similarity measures (topic, phrasing) and what a cache needs (same answer). Cross-encoders or small models that compare two questions directly are better at "same answer?" but cost a model call per comparison, which is why they appear only as verification for borderline matches.

Hit rate is distribution-dependent

The value of a semantic cache depends on how concentrated traffic is. If a few hundred intents cover most questions (a narrow support bot), hit rates can be high. If prompts are long, contain user data, or include conversation history (a general assistant), almost nothing repeats closely enough, and the cache mostly adds an embedding call per request. Before building one, measure on logged traffic: embed a sample, cluster or nearest-neighbour it at candidate thresholds, and estimate the hit rate and the false-hit rate from a labelled subset. That analysis is often enough to decide not to build it.

Caching multi-turn conversations

In a chat, the meaning of "and how much does it cost?" depends on the previous turns. Caching on the last message alone would answer with whatever "how much does it cost" meant in another conversation. Options: cache only first turns (often the bulk of FAQ-like traffic); embed a condensed version of the conversation (a rewritten standalone question, at the cost of a model call to rewrite); or include a hash of the relevant context in the partition key, which makes hits rare. This is one more reason semantic caches suit narrow, first-turn traffic.

Choosing and changing the embedder

The embedder determines everything the threshold means. A threshold tuned at 0.9 for one model is meaningless for another, because each model spreads its vectors differently; some place unrelated sentences around 0.2, others around 0.6. So the embedder's name and version belong in the partition key, and changing it means a new namespace (or re-embedding every entry) and a new sweep. Smaller embedding models are cheaper and faster per lookup, which matters because every miss pays for an embedding; larger ones separate near-misses somewhat better. The pragmatic choice is the cheapest model whose sweep on your labelled pairs gives an acceptable false-hit rate at a useful hit rate — measured, not assumed from a leaderboard.

Security and privacy

A cache is a store of past outputs, so it inherits every data-protection obligation of those outputs: tenant isolation (a cross-tenant leak through a cache is a data breach), deletion requests (a user's data must be removable from cached answers), and poisoning — if users can influence what is stored (by asking crafted questions whose answers are then served to others), an attacker can plant content. Scope by tenant and, where answers contain user data, by user; store only responses from trusted generations; and keep an audit trail of what was served from cache.

How semantic caches fail in production

Confident wrong answers. Symptom: complaints that the assistant answered a different question, clustered around negations, numbers or named entities. Cause: threshold too low for the embedder and domain. Detection: false-hit rate from feedback and sampled judging, broken down by similarity band. Fix: raise the threshold, add verification in the borderline band, or exclude intents with numbers and entities.

Cross-tenant leaks. Symptom: one customer sees another's data. Cause: missing tenant scope on some code path (often a background warm-up job that stored without a tenant). Fix: make tenant a required argument with no default, test isolation, and alert on any namespace without a tenant.

Stale answers after a change. Symptom: the bot quotes last month's price. Cause: TTL too long, or no invalidation when the source changed. Fix: shorter TTLs for volatile intents, and invalidation (per tenant or per document) wired to content updates.

Cache that costs more than it saves. Symptom: latency and spend rose after launch. Cause: low hit rate, so most requests pay for an embedding and a search on top of the model call. Detection: hit rate and added latency per request. Fix: keep the exact cache, drop or narrow the semantic layer.

Embedder upgrade, silent drift. Symptom: false hits jump after an infrastructure change nobody connected to the cache. Cause: the embedding model was upgraded and old vectors were compared with new ones at the old threshold. Fix: embedder version in the partition key and a fresh sweep before switching.

Model upgrade, old answers. Symptom: after switching models, answers are inconsistent in style or quality. Cause: model not in the partition key, so the new model's traffic is served the old model's answers. Fix: include the model and prompt template version in the namespace.

What to measure

Exact, semantic and overall hit rates per tenant and per intent; false-hit rate overall and by similarity band; latency added by embedding and search on misses; cost saved (hits × model cost) minus cost added (lookups × embedding cost); evictions and expirations; namespace sizes; and the similarity distribution of hits, which shifts when traffic or the embedder changes.

Knobs

Threshold (per namespace if possible); TTL (per intent class: short for prices and stock, long for how-to answers); max entries per namespace; which requests are eligible (first turn only, no user data, no tools); verification band; and whether semantic matching is on at all for a given tenant.

The real references

GPTCache, an open-source semantic cache from Zilliz, structures the problem into the same modules as this solution — an embedding generator, cache storage, a vector store, a cache manager with eviction policies such as LRU and FIFO, and a similarity evaluator — and its README states the core risk directly: a semantic cache can produce false positives on hits and false negatives on misses, with hit ratio, latency and recall as the metrics to tune. RedisVL's SemanticCache shows the production shape: a threshold expressed as cosine distance (0 identical, 2 opposite, so a distance threshold of 0.1 corresponds to a similarity of 0.9), optional TTL refreshed on every hit, and filterable fields to scope entries by user or account — the namespaces of this lesson.

Decide it

Three teams ask for a semantic cache: (a) a public FAQ bot for a bank's opening hours, branch locations and card replacement process; (b) a coding assistant inside an IDE whose prompts include the open file; (c) a multi-tenant HR assistant answering policy questions from each company's handbook. For each: build it or not, and with what key, TTL and threshold policy?

Answer

(a) Yes. Narrow, repetitive, mostly public answers. Namespace by model and template version; exact path first; threshold from a sweep on labelled logs, likely conservative, with verification for numbers (branch numbers, dates); TTL hours to a day, with invalidation when opening hours change; exclude anything mentioning the user's account. (b) No semantic cache. Prompts contain the file, so nearly every prompt is unique, and a wrong reused completion is costly. Use provider prompt caching for the shared prefix (system prompt, repository context) and perhaps an exact cache for identical requests. (c) Yes, with care. Namespace by tenant (mandatory), handbook version and model; TTL tied to handbook updates (invalidate the tenant's namespace on upload); threshold conservative because policies differ by small details (number of leave days); verification on numbers; never cache answers that used employee-specific data.

Diagnose it

After a semantic cache launched, overall hit rate is 41% and the team is happy, but CSAT (customer satisfaction score) for cached answers is 12 points lower than for uncached ones. Exact hits are 30% of all lookups, semantic hits 11%. What do you look at, and what do you change?

Answer

Split CSAT by hit type: exact hits cannot be false, so if they are fine, the drop comes from the 11% semantic hits — meaning a substantial fraction of semantic hits are wrong. Plot satisfaction (or sampled judge verdicts) by similarity band: false hits usually concentrate just above the threshold. Inspect low-rated semantic hits for patterns (numbers, negations, entities, multi-turn follow-ups). Then: raise the threshold until the borderline band is gone, or add verification in that band; exclude follow-up turns and intents with numbers; and keep reporting false hits to remove bad entries. Expect hit rate to drop a few points — mostly semantic hits that were doing harm — while the exact path keeps most of the savings.
