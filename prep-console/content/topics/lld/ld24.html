A travel assistant works beautifully in testing, where conversations are five turns long. In production, a user plans a two-week trip over an evening: forty turns, a dozen tool calls to flight and hotel search returning long lists, and a pasted itinerary. On turn 31 the request fails with "prompt is too long". The quick fix — drop the oldest messages until it fits — makes turn 32 fail differently: the oldest message dropped was the assistant's flight-search call, but its results stayed, and the API rejects a tool result whose call is missing. The next fix drops whole messages from the start until the error goes away, and that removes the system prompt: the assistant stops following its formatting rules and its safety instructions halfway through the evening. Meanwhile every turn costs more than the last, because every turn resends the whole history.

Every chat product and every agent needs a component that decides what goes into the context window on each call. It sounds like a list truncation, and machine-coding rounds for AI-engineer roles use it precisely because the naive version breaks in instructive ways. The constraints interact: the budget must be measured in the model's tokens, not characters; the reply needs room; the system prompt must never be dropped; tool calls and their results are inseparable; dropped history can be summarised, but summarising badly is expensive and destroys prompt caching; and the result must be deterministic so it can be tested and cached.

This lesson builds that component in stages: requirements, the entities (messages, a pluggable tokenizer, units), a naive truncation and its failures, then the correct design — pinned messages, units that keep tool calls with their results, keeping the longest suffix that fits, an explicit error when nothing fits, and an incremental summary with its own budget that trims its oldest details first. A worked example fits a nine-message travel conversation into 80 and 70 tokens by hand. The full solution is a runnable Python 3.12 file with eleven tests, including a property test that checks five invariants on 300 random conversations.

The analogy: packing a suitcase with a weight limit

You are flying with a 20 kg limit and a pile of things to take. Some items are non-negotiable — passport, medication — so they go in first and their weight comes off the top. Some things only make sense together — a camera and its charger, a suit and its shoes — so you pack both or neither. You leave space for souvenirs on the way back. Then you add the rest in order of how recently you will need them, until the next item would break the limit. What does not fit, you leave at home, perhaps with a note listing what you left so you can buy replacements.

The suitcase is the context window, the weight limit is the token budget, and the scale is the tokenizer — the wrong scale (counting items instead of weighing them) gets you stopped at the airport. The passport is the system prompt and other pinned messages. The camera-and-charger pair is a unit: an assistant message that called tools plus the tool results answering it. The souvenir space is the output reserve. "Most recently needed first" is keeping the suffix of the conversation. The note is the summary.

The analogy breaks in two places worth knowing. Suitcase items are packed in any order, but messages must stay in conversational order. And a suitcase is packed once, while a conversation is repacked every turn — so the packing should change as little as possible between turns, both to save summarisation calls and because model providers cache the unchanged beginning of a request.

Three budgets inside one number

It helps to see the limit as three separate claims on the same space. The reply claims its share first, because a request with no room to answer is useless. The fixed context — system prompt, tool definitions, pinned facts — claims its share next, because it defines who the assistant is on every turn. Only what is left — the remainder — is the history budget, and that is the only part this component negotiates. A surprising amount of trouble in production comes from forgetting one of the first two: a long tool list that silently eats a fifth of the window, or a maximum output length raised without anyone shrinking the history.

What the round expects

A Message type with roles and tool ids; a tokenizer interface with two implementations; a ConversationMemory with add (which rejects broken tool sequences) and build (which returns the window); grouping into units; the suffix-that-fits algorithm; pinned messages; an output reserve and per-message overhead; a clear failure when nothing fits; optional incremental summarisation with a capped summary; and deterministic tests, ideally including a property test. Strong candidates also explain the interaction with prompt caching.

1 · Clarify the requirements

Ask: what is the model's context limit, and does output share it? How much output must be reserved? Which tokenizer — is there an exact counter, or must we estimate? What message roles exist, and can the assistant call several tools at once? Are there messages that must never be dropped (system prompt, user preferences)? Is summarisation available, at what cost and latency? Does the provider cache prompts (which rewards a stable prefix)? Must the output be deterministic for tests and caching?

Agreed scope: roles system, user, assistant and tool; assistant messages may carry several tool-call ids, each answered by one tool message; a pluggable tokenizer; per-message overhead; an output reserve; pinned messages; keep the longest suffix of whole units that fits; optional incremental summarisation with a summary budget; raise if the newest unit cannot fit; deterministic. Out of scope: retrieval of old messages from long-term storage (an extension).

2 · Entities and the interface

Tokenizer (Protocol): count(text) -> int        WordTokenizer, CharTokenizer (≈ 4 chars/token)

The tokenizer is a Protocol — any object with a count method works — so tests use a deterministic word counter while production passes the model's real counter. Message is frozen, so built windows can be compared and cached safely. The summariser is a plain function (previous_summary, newly_dropped) → new_summary, so tests inject a deterministic stub and production wraps a model call.

3 · Stage one: naive truncation, and how it breaks

def build(messages, budget):
    while sum(count(m.content) for m in messages) > budget:
        messages = messages[1:]                 # drop the oldest
    return messages

Four failures, each from the opening story. It drops the system prompt first, since it is the oldest message. It splits tool exchanges: dropping an assistant message that called tools while keeping its results produces an orphaned result. It counts only content, ignoring per-message overhead (role markers and separators that every chat format adds), and leaves no room for the reply, so requests near the limit fail. And it uses whatever counter was handy, so its idea of the budget is not the model's. It is also quadratic — re-summing the list after every drop — though that is the least of its problems.

4 · Stage two: validating structure on the way in

Correct output is easier if broken input is impossible. add enforces three rules: there is at most one system message; a tool message must answer a call that is still open — made by the most recent assistant message with calls and not yet answered; and no other message may arrive while calls are open, because providers expect the results immediately after the call. The test test_add_rejects_broken_tool_sequences checks a result for an unknown id, an unknown role, and a user message interrupting an open call. With these rules, every assistant call is followed directly by its results, which is what makes grouping simple.

5 · Stage three: units

Group messages into units: walk the history, skip the system and pinned messages, start a new unit at every user or assistant message, and append each tool message to the current unit (which add guarantees is the assistant message that made the call). An assistant message with two tool calls plus the two results is therefore a single unit of three messages. Every other message is a unit of one. Dropping and keeping now happen in whole units, so orphans cannot occur by construction — and the property test checks that over thousands of random builds anyway.

6 · Stage four: the longest suffix that fits

Compute the space: available = budget − output reserve − cost(system and pinned messages), where a message's cost is its token count plus the per-message overhead (4 here). Then walk the units from newest to oldest, adding each unit's cost while it fits; the first unit that would overflow — and everything older — is dropped. Keeping a suffix rather than choosing "important" messages keeps the conversation coherent: there are no gaps where an answer refers to a question that is no longer there.

Worked by hand. The test conversation, with the word tokenizer and 4 tokens of overhead per message, costs: system "You are a travel assistant. Be brief." 13; units: "I want to visit Lisbon in May with my partner." 15; "Great choice. How many days?" 11; "Five days, mid budget, we love food and museums." 16; the tool unit — "Let me check the weather." 10 + "Lisbon May: 22C, mostly sunny." 12 + "Porto May: 19C, some rain." 12 — 34; "Lisbon will be warm and sunny; Porto cooler with rain." 16; "Book a food tour for day two please." 13.

With a budget of 80: available = 80 − 13 = 67. From the newest: 13 (total 13), 16 (29), the tool unit 34 (63 ≤ 67, kept), the next unit costs 16 and 63 + 16 = 79 > 67, so stop. The window is the system prompt, the tool unit, the assistant's weather answer and the latest request: 76 tokens, 3 units kept, 3 dropped. With a budget of 70: available = 57; 13 + 16 = 29, then 29 + 34 = 63 > 57, so the tool unit and everything older go: the system prompt plus the last two units, 42 tokens. Notice that at 70 the assistant's message about the weather survives while the results it was based on do not — a reason to add a summary. At 95 and 105 the window grows to 4 and 5 units.

When nothing fits. If even the newest unit exceeds the available space, there is no valid window: build raises BudgetTooSmall with the sizes, rather than sending a truncated message or an orphaned result. The caller decides — ask the user to shorten, chunk a large paste, summarise a large tool result before adding it, or switch to a larger-context model.

7 · Stage five: pinned messages and the output reserve

The system prompt and any message marked pinned — for example "Remember: my partner is vegetarian" — are counted first and always included, placed after the system prompt in their original order, so they survive any amount of history being dropped. The test pins a preference among twenty messages in a 60-token budget and checks it is second in every window. The output reserve comes off the top: with a 120-token budget, reserving 40 for the reply visibly shortens the window (test_reserve_for_output_shrinks_the_window). In production the reserve is at least the request's maximum output tokens, plus a margin for estimation error when the tokenizer is approximate.

8 · Stage six: incremental summaries

Dropping history loses information; a summary keeps some of it. The design that works across many turns is incremental: the memory keeps a running summary and a count of units already folded into it. When a build must drop units, it passes the previous summary and only the newly dropped units to the summariser, stores the result, advances the count, and never considers those units again. The summary is placed after the pinned messages as a user message labelled "[Summary of earlier conversation]", and it has its own summary budget, reserved from the available space as soon as summarisation begins.

Three details make it robust. Stable prefix: once folded, units never reappear verbatim and the summary changes only when new units are folded in, so between folds the start of the context is byte-identical — what prompt caching rewards. Bounded calls: the summariser runs only when something new is dropped; a second build with nothing new makes no call (the test checks the call count is unchanged). Capped, newest-preserving: if the summariser's output exceeds its budget, the memory trims it — dropping the oldest words first, because summaries append newer material at the end and recent context matters more. Traced with an 80-token budget, a 20-token summary budget and eight short exchanges: builds 1-4 fit without dropping (25, 43, 61, 79 tokens); at build 5 the window overflows, five units are folded into the summary and the window is 71 tokens; from then on each new turn folds the oldest two units, the summary's oldest notes are trimmed ("Topic0" disappears, "Topic5" appears), and every window stays at 74 tokens or less.

9 · Stage seven: testing with invariants

Hand-written examples catch the cases you thought of. The property test generates 300 random conversations — random message lengths, random tool calls with one to three results each, occasional pinned messages, word or character tokenizer, budgets from 40 to 200, output reserve on or off, summarisation on or off — and after every added message checks five invariants: the window fits within budget minus reserve; the system prompt is first; there are no orphaned tool messages; the non-pinned, non-summary messages are a suffix of the conversation in the original order; and building again returns exactly the same window. Any violation pinpoints a seed and a turn to replay.

10 · The full solution

Eleven tests, Python 3.12, standard library only, about a second.

"""Token-budgeted conversation memory: fit a chat history into a token budget with a pluggable
tokenizer, pin the system prompt (and other pinned messages), keep an assistant tool call and its
tool results together as one unit, drop or summarise the oldest units, summarise incrementally so
the kept prefix stays stable, and test it all deterministically.
Python 3.12, standard library only.  Run: python memory.py"""
from __future__ import annotations

import math
import random
import re
from dataclasses import dataclass, field
from typing import Callable, Protocol


# ---------------------------------------------------------------- tokenizers (pluggable)
class Tokenizer(Protocol):
    def count(self, text: str) -> int: ...


class WordTokenizer:
    """Words and punctuation marks each count as one token. Deterministic, good enough for tests."""
    _pat = re.compile(r"\w+|[^\w\s]")

    def count(self, text: str) -> int:
        return len(self._pat.findall(text))


class CharTokenizer:
    """The common rule of thumb: about four characters per token."""

    def count(self, text: str) -> int:
        return math.ceil(len(text) / 4)


# ---------------------------------------------------------------- messages
@dataclass(frozen=True)
class Message:
    role: str                                   # system | user | assistant | tool
    content: str
    tool_call_ids: tuple[str, ...] = ()         # on an assistant message that calls tools
    tool_call_id: str | None = None             # on a tool result
    pinned: bool = False                        # never dropped or summarised


class BudgetTooSmall(ValueError):
    pass


@dataclass
class BuildStats:
    tokens: int
    kept_units: int
    dropped_units: int
    summarised: bool


Summariser = Callable[[str, list[Message]], str]   # (previous summary, newly dropped) -> new summary


class ConversationMemory:
    def __init__(self, budget: int, tokenizer: Tokenizer, reserve_output: int = 0,
                 per_message_overhead: int = 4, summariser: Summariser | None = None,
                 summary_budget: int = 0) -> None:
        if summariser is not None and summary_budget <= 0:
            raise ValueError("a summariser needs a positive summary_budget")
        self.budget, self.tok, self.reserve = budget, tokenizer, reserve_output
        self.overhead, self.summariser, self.summary_budget = per_message_overhead, summariser, summary_budget
        self.messages: list[Message] = []
        self._summary = ""
        self._summarised_units = 0              # units [0, n) are folded into the summary for good
        self.summariser_calls = 0
        self.last_stats: BuildStats | None = None

    # ---- input
    def add(self, m: Message) -> None:
        if m.role not in ("system", "user", "assistant", "tool"):
            raise ValueError(f"unknown role {m.role!r}")
        if m.role == "system" and any(x.role == "system" for x in self.messages):
            raise ValueError("only one system message")
        if m.role == "tool":
            # a tool result must answer a call made by the most recent assistant message with calls
            open_calls = self._open_calls()
            if m.tool_call_id not in open_calls:
                raise ValueError(f"tool result {m.tool_call_id!r} does not answer an open tool call")
        elif self._open_calls():
            raise ValueError(f"tool calls {sorted(self._open_calls())} still need results")
        self.messages.append(m)

    def _open_calls(self) -> set[str]:
        for i in range(len(self.messages) - 1, -1, -1):
            m = self.messages[i]
            if m.role == "assistant" and m.tool_call_ids:
                answered = {x.tool_call_id for x in self.messages[i + 1:] if x.role == "tool"}
                return set(m.tool_call_ids) - answered
            if m.role != "tool":
                return set()
        return set()

    # ---- structure
    def cost(self, m: Message) -> int:
        return self.tok.count(m.content) + self.overhead

    def _units(self) -> list[list[Message]]:
        """Non-pinned, non-system messages grouped so that an assistant message with tool calls
        and all its tool results form one unit. Other messages are units on their own."""
        units: list[list[Message]] = []
        for m in self.messages:
            if m.role == "system" or m.pinned:
                continue
            if m.role == "tool":
                units[-1].append(m)                 # add() guarantees the call precedes it
            else:
                units.append([m])
        return units

    # ---- output
    def build(self) -> list[Message]:
        system = [m for m in self.messages if m.role == "system"]
        pinned = [m for m in self.messages if m.pinned and m.role != "system"]
        fixed = sum(self.cost(m) for m in system + pinned)
        avail = self.budget - self.reserve - fixed
        units = self._units()[self._summarised_units:]
        if not units:
            self.last_stats = BuildStats(fixed, 0, 0, bool(self._summary))
            return system + pinned + self._summary_msgs()
        unit_cost = [sum(self.cost(m) for m in u) for u in units]

        def suffix_that_fits(space: int) -> int:
            """Index of the first unit kept when keeping the longest suffix that fits in space."""
            start, used = len(units), 0
            while start > 0 and used + unit_cost[start - 1] <= space:
                start -= 1
                used += unit_cost[start]
            return start

        summary_space = self.summary_budget + self.overhead if (self.summariser or self._summary) else 0
        start = suffix_that_fits(avail - (summary_space if self._summary else 0))
        if start > 0 and self.summariser is not None and not self._summary:
            start = suffix_that_fits(avail - summary_space)      # dropping now: make room for a summary
        if start == len(units):
            raise BudgetTooSmall(f"the newest unit needs {unit_cost[-1]} tokens; "
                                 f"only {avail - (summary_space if self.summariser else 0)} available")
        if start > 0 and self.summariser is not None:
            dropped = [m for u in units[:start] for m in u]
            self._summary = self._cap(self.summariser(self._summary, dropped))
            self.summariser_calls += 1
            self._summarised_units += start
            units, dropped_now, start = units[start:], start, 0
        else:
            dropped_now = start
        kept = [m for u in units[start:] for m in u]
        out = system + pinned + self._summary_msgs() + kept
        self.last_stats = BuildStats(sum(self.cost(m) for m in out), len(units) - start, dropped_now,
                                     bool(self._summary))
        assert self.last_stats.tokens <= self.budget - self.reserve
        return out

    def _summary_msgs(self) -> list[Message]:
        return [Message("user", f"[Summary of earlier conversation] {self._summary}")] if self._summary else []

    def _cap(self, text: str) -> str:
        """Trim a summary to its budget (counting the prefix). Drop the OLDEST words first: the
        summariser appends newer material at the end, and recent context matters more."""
        prefix = "[Summary of earlier conversation] "
        words = text.split()
        while words and self.tok.count(prefix + " ".join(words)) > self.summary_budget:
            words.pop(0)
        return " ".join(words)


# ---------------------------------------------------------------- tests
WT = WordTokenizer()


def stub_summariser(previous: str, dropped: list[Message]) -> str:
    """Deterministic stand-in for a model: keeps the first three words of each dropped user message."""
    notes = [" ".join(m.content.split()[:3]) for m in dropped if m.role == "user"]
    return "; ".join(x for x in [previous] + notes if x)


def convo(mem: ConversationMemory) -> ConversationMemory:
    mem.add(Message("system", "You are a travel assistant. Be brief."))
    mem.add(Message("user", "I want to visit Lisbon in May with my partner."))
    mem.add(Message("assistant", "Great choice. How many days?"))
    mem.add(Message("user", "Five days, mid budget, we love food and museums."))
    mem.add(Message("assistant", "Let me check the weather.", tool_call_ids=("c1", "c2")))
    mem.add(Message("tool", "Lisbon May: 22C, mostly sunny.", tool_call_id="c1"))
    mem.add(Message("tool", "Porto May: 19C, some rain.", tool_call_id="c2"))
    mem.add(Message("assistant", "Lisbon will be warm and sunny; Porto cooler with rain."))
    mem.add(Message("user", "Book a food tour for day two please."))
    return mem


def no_orphans(msgs: list[Message]) -> bool:
    calls = {c for m in msgs if m.role == "assistant" for c in m.tool_call_ids}
    results = {m.tool_call_id for m in msgs if m.role == "tool"}
    return calls == results


def test_everything_fits() -> None:
    mem = convo(ConversationMemory(1000, WT))
    assert mem.build() == mem.messages and mem.last_stats.dropped_units == 0


def test_drops_oldest_units_and_keeps_the_latest() -> None:
    mem = convo(ConversationMemory(70, WT))
    out = mem.build()
    assert out[0].role == "system" and out[-1].content == "Book a food tour for day two please."
    assert mem.last_stats.tokens <= 70 and mem.last_stats.dropped_units > 0
    assert out[1:] == mem.messages[len(mem.messages) - len(out) + 1:]       # a suffix, in order


def test_tool_call_and_results_stay_together() -> None:
    for budget in range(30, 140):
        mem = convo(ConversationMemory(budget, WT))
        try:
            out = mem.build()
        except BudgetTooSmall:
            continue
        assert no_orphans(out), budget
        has_call = any(m.tool_call_ids for m in out)
        assert has_call == any(m.role == "tool" for m in out)


def test_system_and_pinned_messages_are_never_dropped() -> None:
    mem = ConversationMemory(60, WT)
    mem.add(Message("system", "You are a travel assistant."))
    mem.add(Message("user", "Remember: my partner is vegetarian.", pinned=True))
    for i in range(10):
        mem.add(Message("user", f"Question number {i} about something long enough to matter here."))
        mem.add(Message("assistant", f"Answer number {i}."))
    out = mem.build()
    assert out[0].role == "system" and out[1].content.startswith("Remember")
    assert out[-1].content == "Answer number 9." and mem.last_stats.tokens <= 60


def test_reserve_for_output_shrinks_the_window() -> None:
    a = convo(ConversationMemory(120, WT)).build()
    b = convo(ConversationMemory(120, WT, reserve_output=40)).build()
    assert len(b) < len(a)


def test_summary_replaces_dropped_units_incrementally() -> None:
    mem = ConversationMemory(80, WT, summariser=stub_summariser, summary_budget=20)
    mem.add(Message("system", "Be brief."))
    outs = []
    for i in range(8):
        mem.add(Message("user", f"Topic{i} details here please and thanks."))
        mem.add(Message("assistant", f"Noted topic{i}."))
        outs.append(mem.build())
        assert mem.last_stats.tokens <= 80
    last = outs[-1]
    assert last[1].content.startswith("[Summary of earlier conversation]")
    assert "Topic5" in last[1].content and "Topic0" not in last[1].content   # oldest detail trimmed first
    assert mem.summariser_calls < 8                     # not called on every build
    calls = mem.summariser_calls
    mem.build()
    assert mem.summariser_calls == calls                # nothing new dropped: no new call
    # once folded into the summary, a unit never reappears verbatim
    assert not any(m.content.startswith("Topic0") for m in last[2:])


def test_summary_is_capped_to_its_budget() -> None:
    long_summary = lambda prev, dropped: "word " * 500
    mem = ConversationMemory(60, WT, summariser=long_summary, summary_budget=15)
    mem.add(Message("system", "Be brief."))
    for i in range(10):
        mem.add(Message("user", f"Message {i} with several words in it to use tokens."))
    out = mem.build()
    assert WT.count(out[1].content) <= 15 and mem.last_stats.tokens <= 60

    b = convo(ConversationMemory(105, CharTokenizer())).build()    # ~4 chars/token: 7 fit
    assert (len(a), len(b)) == (8, 7) and no_orphans(a) and no_orphans(b)


def test_budget_too_small_for_the_newest_unit() -> None:

        mem.build()
    except BudgetTooSmall as e:

def test_add_rejects_broken_tool_sequences() -> None:

    mem.add(Message("user", "hi"))

def test_property_random_conversations() -> None:
    rng = random.Random(7)
    for trial in range(300):
        summarise = rng.random() < 0.5
        mem = ConversationMemory(rng.randint(40, 200), rng.choice([WT, CharTokenizer()]),
                                 reserve_output=rng.choice([0, 10]),
                                 summariser=stub_summariser if summarise else None,
                                 summary_budget=15 if summarise else 0)
        mem.add(Message("system", "System prompt " * rng.randint(1, 4)))
        n_call = 0
        for _ in range(rng.randint(1, 25)):
            r = rng.random()
            words = " ".join(rng.choice(["alpha", "beta", "gamma", "delta"]) for _ in range(rng.randint(1, 12)))
            if r < 0.15:
                ids = tuple(f"c{n_call + k}" for k in range(rng.randint(1, 3)))
                n_call += len(ids)
                mem.add(Message("assistant", words, tool_call_ids=ids))
                for cid in ids:
                    mem.add(Message("tool", words, tool_call_id=cid))
            else:
                mem.add(Message(rng.choice(["user", "assistant"]), words, pinned=rng.random() < 0.05))
            try:
                out = mem.build()
            except BudgetTooSmall:
                continue
            assert out[0].role == "system"
            assert no_orphans(out)
            assert mem.last_stats.tokens <= mem.budget - mem.reserve
            body = [m for m in out if m.role != "system" and not m.pinned and not m.content.startswith("[Summary")]
            nonpinned = [m for m in mem.messages if m.role != "system" and not m.pinned]
            assert body == nonpinned[len(nonpinned) - len(body):]           # always a suffix, in order
            assert out == mem.build()                                       # deterministic, idempotent

11 · Edge cases

No messages yet: the window is just the system prompt and pinned messages. A pinned set larger than the budget: available space is negative and the newest unit cannot fit, so BudgetTooSmall — pinned content must itself be budgeted. A huge tool result: one 50,000-token search result makes its whole unit unaffordable; truncate or summarise tool results before adding them, keeping the full output elsewhere. Pending tool calls at build time: the solution's add rejects other messages while calls are open, but a build in the middle of executing tools would send a call without results; build only between complete exchanges. Summariser failure: fall back to plain dropping for that build rather than failing the request. Tokenizer mismatch: when the counter is an estimate, keep a safety margin, and on a "prompt too long" error from the API, shrink the budget and rebuild.

12 · Extensions the interviewer will ask for

Hysteresis: when overflowing, drop down to a low-water mark (say 60% of the budget) so several turns fit before the next fold, cutting summariser calls and keeping the prefix stable longer. Clearing old tool results instead of whole turns: tool outputs are usually most of the tokens, and replacing an old result's content with "[result cleared]" keeps the structure and the reasoning while freeing space — the approach provider-side context editing takes. Retrieval memory: store all messages and extracted facts outside the window and retrieve the relevant ones per turn. Exact counting: call the provider's token-counting endpoint for the final check before sending, with the heuristic for planning. Per-role budgets: cap the share of the window tool results may take. Server-side compaction: some APIs can summarise the history themselves when it nears a threshold, which moves this logic to the provider.

13 · Complexity

add is O(k) to find open calls, where k is the distance back to the last assistant message with calls (small). build is O(n) to group and cost n messages, plus O(u) to scan u units for the suffix — linear per call, so O(n) per turn and O(n²) over a conversation if every turn rebuilds from scratch; caching per-message costs (they never change) makes the per-turn cost a cheap sum. Summarisation calls are bounded by the number of fold events, and the summary's size is bounded by its budget. Memory: O(n) for the full history.

Why the prefix must stay stable

Providers cache the computation for a request's prefix: tools first, then the system prompt, then the messages in order. When the next request begins with the same bytes, the cached part is far cheaper and faster to process. A memory design that rewrites early content every turn — re-summarising everything, reordering, renumbering — breaks the prefix at its first change and pays full price for everything after it, on every turn. The design here changes the prefix only at fold events: system and pinned messages never change, the summary changes only when units are folded in, and kept messages are appended in order. Hysteresis makes fold events rarer still. On a long agent run, the difference between a stable and an unstable prefix can be most of the input cost.

Summaries lose information, and errors compound

A summary is a lossy compression written by a model. Details it drops are gone for good under incremental summarisation, and mistakes it makes are carried into every later summary. Mitigations: pin facts that must survive (the user's constraints, decisions made, identifiers); ask the summariser for a structured summary (goals, decisions, open questions, key facts with values) rather than prose; evaluate summaries by whether later turns that needed old information still get it right; and for precise data, keep it in external storage and retrieve it rather than trusting the summary.

Long contexts are not free even when they fit

Models with very large context windows make it tempting to send everything. Three costs remain. Price scales with input tokens on every turn, so a long history makes each turn expensive. Latency grows with input length, mostly in time to first token. And quality can fall: models attend less reliably to information buried in the middle of long contexts, and irrelevant history distracts. A budget well below the maximum, chosen per product, is often better on all three axes; the memory component is where that choice is enforced.

Tool results dominate agent contexts

In agents, a single file read, search result or API response can be thousands of tokens, while the reasoning around it is short. Dropping whole old turns throws away the reasoning along with the bulky result. Clearing just the content of old tool results — keeping the call, the result's id and a placeholder — preserves the structure the API requires and the model's chain of decisions while reclaiming most of the space. Anthropic's context-engineering guidance describes this kind of tool-result clearing as one of the safest forms of compaction, and its API offers context editing that clears old tool results server-side.

Choosing what to pin automatically

Asking users to mark messages as pinned does not scale; most never will. Production systems detect standing instructions ("always answer in Spanish", "I'm allergic to nuts", "use metric units") and decisions ("we chose the 9:40 flight") and lift them into a pinned profile or a structured memory block that is rendered after the system prompt. Detection can be a cheap classifier or a model call run when a turn is added, off the critical path. The profile then has its own budget and its own update rules (a later "actually, imperial is fine" replaces the earlier entry), which keeps the history free to be dropped or summarised without losing what the user expects the assistant to remember. Getting this wrong is visible to users in a way most memory failures are not, because forgetting a stated preference feels like not listening.

Measuring memory quality

Unit tests prove the window is well-formed; they cannot prove it contains what the model needs. For that, build long-session evaluations: scripted conversations of 30-100 turns where late questions depend on early facts ("what was the budget I mentioned?", "which hotel did we rule out and why?"). Run them with different budgets, summarisation settings and pinning rules, and score whether answers use the early information correctly. This turns the knobs in this lesson — budget, summary budget, hysteresis — into measured trade-offs between cost and recall, rather than guesses.

Determinism is a feature

Given the same messages, the same budget and the same tokenizer, build returns the same window — the property test checks it. Determinism makes the memory testable, makes prompt caching effective, and makes bugs reproducible: a failing conversation can be replayed exactly. It rules out tempting heuristics such as random sampling of history or time-based decisions inside build; anything that varies (a summary) is computed once and stored.

How conversation memory fails in production

"Prompt is too long" errors on long sessions. Cause: an estimating tokenizer undercounting (code and non-English text) or ignoring overhead and tool definitions. Detection: API rejections by session length. Fix: exact counting for the final check, a safety margin, and rebuild with a smaller budget on rejection.

Rejected histories after trimming. Cause: a tool result kept without its call. Detection: API validation errors mentioning tool ids. Fix: unit-based dropping and structural validation on add.

Assistant forgets its rules mid-conversation. Cause: the system prompt was dropped or summarised. Fix: pin it, and test that it is first in every window.

Assistant forgets user constraints. Cause: a constraint stated early was summarised away. Fix: detect and pin standing instructions, or extract them to a profile that is always included.

Costs rising per turn and low cache hits. Cause: an unstable prefix — re-summarising every turn, timestamps or counters injected early in the context. Detection: cached input tokens per request near zero. Fix: incremental summaries, hysteresis, nothing volatile before the history.

Summaries drift. Symptom: late in long sessions the assistant contradicts earlier decisions. Cause: compounding summary errors. Fix: structured summaries with explicit decisions and facts, and pinning.

Mismatch between estimate and bill. Symptom: per-session token counts in your logs disagree with the provider's usage reports. Cause: logging the estimator's count rather than the API's reported usage. Fix: log the usage the API returns on every response, and compare it with the estimate to tune the safety margin from real data rather than intuition.

What to measure

Input tokens per turn and their growth over a session; cached input tokens per turn; units dropped and summariser calls per session; summary length; BudgetTooSmall occurrences; API rejections for length or structure; and quality on long sessions, measured by evaluations that ask about information from early turns.

Two of these deserve dashboards rather than logs: input tokens per turn plotted against turn number (a straight line rising without bound means the memory is not trimming; a sawtooth means folding is working), and cached input tokens as a share of input (a sudden drop after a deploy points straight at a prefix change).

Knobs

Total budget (well below the model's maximum, per product); output reserve; per-message overhead estimate; summary budget; low-water mark for hysteresis; maximum size of a single tool result before it is truncated or summarised on add; which messages are pinned automatically.

Work it out

A model has a 32,000-token context shared by input and output. Your system prompt and tool definitions take 2,500 tokens; the user pinned a 200-token preference; replies may be up to 4,000 tokens; you keep a 10% safety margin because you estimate tokens at four characters each; the summary budget is 1,000. Each turn adds about 600 tokens, and every fifth turn calls a tool that returns about 3,000 tokens. How much history fits, and after roughly how many turns does the first fold happen?

Answer

Usable input: 32,000 − 4,000 reply = 28,000, minus the 10% margin (2,800) = 25,200; minus fixed parts 2,500 + 200 = 22,500 for history. Once folding starts, reserve 1,000 for the summary: 21,500. Five turns cost 5 × 600 + 3,000 = 6,000 tokens, so 22,500 holds about 3.75 five-turn blocks: the first fold happens at turn 20 (3 blocks = 15 turns = 18,000 tokens; turns 16-18 add 1,800 more to 19,800; turn 19 adds 600 more to 20,400; the tool turn 20 adds 3,600 and overflows). After that, each new turn folds the oldest unit(s); with hysteresis to 60% (13,500), the fold drops about 9,000 tokens at once and the next fold is about 13-15 turns later.

Diagnose it

An agent's per-turn input cost doubled after a refactor, though windows look the same size. The API reports cached input tokens near zero on every turn, where they used to be most of the input. What changed?

Answer

The prefix is no longer stable. Likely culprits: the summary is now regenerated from the whole history every turn (so its text changes every turn), something volatile was added early in the context (a timestamp, a turn counter, a random request id in the system prompt), pinned messages are re-ordered (for example sorted by a dict whose order changed), or tool definitions are serialised in a non-deterministic order. Diff two consecutive requests byte by byte to find the first difference. Fix by making everything before the recent history deterministic and unchanged between folds: incremental summaries, no volatile values in the system prompt, stable ordering of tools and pinned messages.
