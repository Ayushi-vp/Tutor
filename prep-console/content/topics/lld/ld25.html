The team is about to switch the support assistant from one model to a cheaper one. Someone runs the eval: 200 questions, a loop that calls the model and checks the answer. It takes forty minutes because calls run one at a time. Halfway through a second run the laptop sleeps, and the run starts again from zero. The third run hits the provider's rate limit after parallelising, and 31 questions fail with HTTP 429; the script scores them as wrong, and the new model "loses" by 6 points. Rerun the next morning: the new model "wins" by 2. The decision gets made on whichever run someone believed, and nobody can say how big a difference would actually matter.

Every model change, prompt change and retrieval tweak in an AI product should go through an evaluation harness, and building its runner is a natural machine-coding round for AI-engineer roles: it combines concurrency, rate limiting, retries, durable state and statistics in one small system. The model and the scorers are the easy part. The interviewer is listening for the engineering around them: does the pool respect a shared rate limit? Are transient errors retried and permanent ones not? Are errors kept out of the quality score? Does a crash lose an hour of paid calls, or resume? Can a changed dataset ever reuse stale results? And does the report say how uncertain each number is?

This lesson builds the runner in stages: requirements; entities (examples, a model callable, scorers, a token bucket, a results store, the runner, the report); a naive loop and everything wrong with it; then concurrency with a worker pool and a shared token bucket; retries with jittered backoff and error classification; resumable runs via an append-only JSONL store keyed by a hash of the run's configuration; and a report with Wilson intervals for pass/fail scores, a seeded bootstrap for judge scores, and per-slice breakdowns. The worked example scores 100 questions: 80% on the regex scorer with a 95% interval of 71.1%-86.7%, 85% on the judge scorer with 79.0%-90.3%, and a slice that shows every failure sits in "long" questions. The full solution is a runnable Python 3.12 file with eight tests, including a crash-and-resume test and a 16-worker stress test.

The analogy: marking a stack of exam papers with a team

A head examiner has 1,000 exam papers to mark and a team of markers. Each marker takes the next paper from the pile, marks it against the answer key — some questions by exact answer, some by "the key word appears", essays by a rubric — and writes the result on a register. The exam board's office can only process so many queries a minute, so markers queue at a single phone line when they need to check something. If a query fails because the line is busy, they wait a little and try again; if the paper itself is illegible, they write "unmarkable" rather than a zero. At the end of each paper, the mark goes on the register in ink, so if the building is evacuated at paper 600, marking resumes at 601 tomorrow — unless the answer key changed overnight, in which case the old marks are not reused. Finally the head examiner reports the average with a margin of error, and the average for each section.

The markers are the worker pool; the phone line is the shared rate limiter; the answer key and rubric are the scorers; "try again after a wait" is a retry with backoff; "unmarkable" is an error recorded separately; the inked register is the append-only results store; "unless the answer key changed" is the run key; the margin of error is the confidence interval; section averages are slices.

The analogy breaks in a way that matters: the papers here are not fixed. A model's answer can vary between calls, and the "exam" is a sample of the questions users will actually ask. The margin of error is not a formality; it is the difference between "the new model is better" and "we cannot tell yet".

Where the runner sits

The runner is the middle of a loop that every AI team runs repeatedly: curate a dataset (ev2), run candidates through it, compare, ship or iterate, and add new failure cases from production back into the dataset. Because it runs on every prompt edit and every model upgrade, its properties compound: a runner that takes an hour and loses work on a crash gets run less often; one whose numbers carry no uncertainty gets over-trusted. Fast, resumable and honest is what makes the whole loop work.

What the round expects

An Example type; a model as a callable; scorer classes behind one interface; a runner with run(dataset) that uses a pool, a shared rate limiter and retries; durable per-example results with resumption; a report with means, intervals, error counts and slices; and tests with a fake model, including a crash-and-resume test. Strong answers explain why errors are not zeros, why the run key hashes the configuration, and why the Wilson interval beats the textbook formula.

1 · Clarify the requirements

Ask: how big are datasets (hundreds or hundreds of thousands)? What is the provider's rate limit and typical latency? Which scorers are needed — exact answers, patterns, open-ended grading? Is the judge another model call (with its own rate limit)? Must runs survive crashes and be resumable? How will results be compared between models — is a confidence interval expected? Are examples grouped (several questions per document)? Should the same configuration give identical results?

Agreed scope: datasets up to tens of thousands; a model callable; exact-match, regex and judge scorers; a configurable worker pool with a shared token bucket; up to four attempts for transient errors with full-jitter backoff, no retries for permanent ones; a JSONL results file with a run key for resumption; a report with means, 95% intervals (Wilson for binary, bootstrap for continuous), error counts, retries, median latency and per-slice means; deterministic given a seed. Out of scope: distributed execution and dashboards (extensions).

2 · Entities and the interface

Example(id, input, expected, tags)                          # frozen
Model = Callable[[str], str]                                # raises TransientError or another exception
Scorer: name, binary, __call__(example, output) -> float    # ExactMatch, RegexMatch, JudgeScorer
TokenBucket(rate, burst).acquire()                          # shared by all workers
ResultStore(path, run_key).done / .save(record)             # append-only JSONL, reload on start
run_key(model_name, params, scorers, dataset) -> str        # hash of everything that changes results
EvalRunner(model, model_name, scorers, store, RunConfig).run(dataset) -> list[record]
report(records, scorers, seed) -> dict                      # metrics with ci95, errors, slices

Each piece has one job, and the seams make testing easy: the model is a plain function (a fake in tests), the sleep function is injected (a list's append in the retry test, so backoff is recorded instead of waited), and the store takes a file path (a temporary directory in tests).

3 · Stage one: the naive loop

correct = 0
for ex in dataset:
    out = model(ex.input)                 # one at a time; any exception kills the run
    correct += out.strip() == ex.expected
print(correct / len(dataset))             # no interval, no slices, nothing saved

It is serial, so 1,000 two-second calls take 33 minutes. One rate-limit error ends the run. If you wrap it in try/except and count failures as wrong, an outage looks like a quality drop. Nothing is saved, so a crash at example 900 costs 900 paid calls. The exact-string check is too strict for real outputs. And the single number has no uncertainty, so a reader cannot tell whether 0.78 versus 0.80 means anything. Each stage below fixes one of these.

4 · Stage two: scorers

All scorers share one interface: a name, a binary flag (which decides the interval method), and a call returning a score in [0, 1]. ExactMatch normalises both strings (lower-case, strip punctuation, collapse whitespace) and compares. RegexMatch takes a pattern with an {expected} placeholder, inserted with re.escape so an expected answer containing regex characters is matched literally; the solution uses \b{expected}\b, which accepts "The answer is Paris." but rejects "Parisian food". JudgeScorer wraps a judge function returning a 1-5 rating and maps it to (rating − 1) / 4 — in production a model call with a rubric, in tests a deterministic stub that gives 5 if the expected answer appears and 2 otherwise. A scorer that raises does not crash the run: the record is marked scorer_error, because a bug in grading is not the model's failure and should be visible as such.

The worked example shows why several scorers matter. The fake model answers "The answer is Paris." when right and "London." when wrong (every fifth question). Exact match scores 0% — every answer has extra words. The regex scores 80%. The judge scores 85%: 80 answers at 1.0 and 20 at 0.25.

5 · Stage three: a worker pool and a shared rate limit

Model calls are slow and I/O-bound, so a thread pool runs many at once. The question is how many. By Little's law, requests in flight = throughput × latency: at a provider limit of 50 requests per second and 2 seconds per call, 100 calls in flight saturate the limit, and more workers only produce 429 errors. Sizing the pool is not enough on its own, though — when calls get faster, a fixed pool exceeds the rate — so every worker also takes a token from one shared token bucket before each attempt, including retries. The bucket refills at rate tokens per second up to burst; a worker that finds it empty computes how long until the next token, releases the lock, and sleeps (sleeping while holding the lock would block every other worker). The concurrency test runs 40 calls with 6 workers at 100 per second and a burst of 1: peak concurrency never exceeds 6, and the run takes at least 0.39 seconds, as the rate dictates.

6 · Stage four: retries and error classification

Errors fall into two kinds. Transient ones — rate limited, overloaded, timed out — may succeed later, so the worker retries: up to max_attempts (4), each retry after a full-jitter wait, uniform between zero and base × 2attempt − 1 (50, 100, 200 ms), so workers that failed together do not retry together (ld4). The random generator is seeded per example (Random(f"{seed}:{id}")), so the waits are reproducible run to run. Permanent ones — an invalid request, an input that is too long — will fail identically, so the worker records them after one attempt. The retry test scripts all three cases: question 1 fails twice then succeeds (status ok, 3 attempts), question 2 always fails transiently (error after 4 attempts), question 3 raises a permanent error (error after 1 attempt); exactly 2 + 3 backoff sleeps were requested, each within its cap.

Errors are then kept out of the quality metrics. The report shows errors: 2 and computes exact match over the 3 scored examples, stating n = 3. Counting the errors as wrong would make a rate-limit storm look like a worse model.

7 · Stage five: resumable runs

Append, flush, fsync. When an example finishes — model called, scorers run — its record is serialised to one JSON line, appended to results.jsonl under a lock, flushed and fsynced so it survives a crash or power loss. Results are only written once complete, so there is never a half-scored record to reuse.

The run key. Every line carries a run_key: a hash of the model name, its parameters (temperature, prompt template version), the scorer names, and a hash of the whole dataset's content. On start, the store reads the file and keeps only lines whose key matches. Change the model, a parameter, the scorers, or one example, and the key changes, so nothing stale is reused — the test checks all four changes produce different keys. Different runs can share one file safely.

Reload, skip, continue. run skips every example whose id is already in the store. If the process crashed mid-write, the last line is incomplete JSON; the loader skips lines that do not parse (the torn-line test writes half a record and checks it is ignored). A fatal error inside the run — a KeyboardInterrupt, a bug — sets a stop flag so idle workers start nothing new, cancels queued work and re-raises, leaving everything finished on disk. The crash test runs 60 examples with a model that dies on its 25th call: 24 results survive; the rerun, with a different worker count, calls the model exactly 36 times; and its results equal those of an uninterrupted run.

8 · Stage six: the report and its intervals

Binary scores: Wilson. For a pass/fail scorer with s successes out of n, the textbook interval p ± 1.96·√(p(1−p)/n) misbehaves at small n and extreme p: at 8 of 10 it gives 55%-105%, at 10 of 10 an interval of zero width. The Wilson interval fixes both. With z = 1.96: centre = (p + z²/2n) / (1 + z²/n) and half-width = z·√(p(1−p)/n + z²/4n²) / (1 + z²/n). Worked for the regex scorer, 80 of 100: z²/n = 0.038416, so centre = (0.8 + 0.019208) / 1.038416 = 0.7889; half-width = 1.96 × √(0.0016 + 0.000096) / 1.038416 = 1.96 × 0.04118 / 1.038416 = 0.0777; interval 71.1%-86.7%, exactly what the test asserts. For comparison: 8 of 10 gives 49.0%-94.3%, 800 of 1,000 gives 77.4%-82.4%. To halve the width you need four times the examples.

Continuous scores: bootstrap. Judge scores take values like 0.25 and 1.0, so the solution resamples the 100 scores with replacement 2,000 times (seeded), computes each resample's mean, and takes the 2.5th and 97.5th percentiles: the judge's 85% has an interval of 79.0%-90.3%. The seed makes the report reproducible.

Slices. Each example carries tags; the report computes each metric per tag. In the worked example every question tagged "long" (40 of them) contains all 20 failures: regex 50% on long questions, 100% on short ones. A single 80% hides that entirely, and slices are usually where the actionable finding lives.

What else. Counts of errors, scorer errors and retried examples, and median latency. A comparison between two models should use paired differences on the same examples, which the record format supports directly (join two runs' records by id).

9 · The full solution

Eight tests: scorers; the end-to-end report including the exact Wilson bounds and slice values; retries and error classification with recorded backoff; crash and resume against an uninterrupted run; cache-key invalidation; rate limit and concurrency; torn-line recovery; and 500 examples on 16 workers with every id written exactly once. Python 3.12, standard library only, a few seconds (most of it fsync).

"""An evaluation-harness runner: a dataset, a pluggable model, scorers (exact match, regex, an LLM-judge
stub), a worker pool with a shared rate limiter, retries with backoff, resumable runs backed by a
JSONL results cache keyed by the run configuration, and a report with confidence intervals
(Wilson for pass/fail scores, a seeded bootstrap for continuous ones) and per-slice breakdowns.
Python 3.12, standard library only.  Run: python eval_runner.py"""
from __future__ import annotations

import hashlib
import json
import math
import os
import random
import re
import statistics
import tempfile
import threading
import time
from concurrent.futures import ThreadPoolExecutor
from dataclasses import asdict, dataclass, field
from typing import Callable, Protocol


# ---------------------------------------------------------------- data
@dataclass(frozen=True)
class Example:
    id: str
    input: str
    expected: str
    tags: tuple[str, ...] = ()


class TransientError(Exception):
    """Rate limited, overloaded, timed out: worth retrying."""


Model = Callable[[str], str]


# ---------------------------------------------------------------- scorers
class Scorer(Protocol):
    name: str
    binary: bool

    def __call__(self, ex: Example, output: str) -> float: ...


def _norm(s: str) -> str:
    return " ".join(re.sub(r"[^\w\s]", "", s.lower()).split())


@dataclass
class ExactMatch:
    name: str = "exact"
    binary: bool = True

    def __call__(self, ex: Example, output: str) -> float:
        return float(_norm(output) == _norm(ex.expected))


@dataclass
class RegexMatch:
    pattern: str
    name: str = "regex"
    binary: bool = True

    def __call__(self, ex: Example, output: str) -> float:
        return float(re.search(self.pattern.format(expected=re.escape(ex.expected)), output) is not None)


@dataclass
class JudgeScorer:
    """An LLM-as-judge scorer. `judge` returns a 1-5 rating; the scorer maps it to [0, 1].
    In tests the judge is a deterministic stub; in production it is a model call with a rubric."""
    judge: Callable[[str, str, str], int]
    name: str = "judge"
    binary: bool = False

    def __call__(self, ex: Example, output: str) -> float:
        rating = self.judge(ex.input, ex.expected, output)
        if not 1 <= rating <= 5:
            raise ValueError(f"judge returned {rating}, expected 1-5")
        return (rating - 1) / 4


# ---------------------------------------------------------------- rate limiting
class TokenBucket:
    """Shared by all workers: at most `rate` calls per second on average, bursts up to `burst`."""

    def __init__(self, rate: float, burst: int = 1, clock=time.monotonic, sleep=time.sleep) -> None:
        self.rate, self.burst, self.clock, self.sleep = rate, burst, clock, sleep
        self.tokens, self.last = float(burst), clock()
        self.lock = threading.Lock()

    def acquire(self) -> None:
        while True:
            with self.lock:
                now = self.clock()
                self.tokens = min(self.burst, self.tokens + (now - self.last) * self.rate)
                self.last = now
                if self.tokens >= 1:
                    self.tokens -= 1
                    return
                wait = (1 - self.tokens) / self.rate
            self.sleep(wait)                              # sleep outside the lock


# ---------------------------------------------------------------- results cache (resumability)
class ResultStore:
    """Append-only JSONL file of finished examples for one run key. Safe for many threads;
    a crash loses at most the line being written, which is ignored on reload."""

    def __init__(self, path: str, run_key: str) -> None:
        self.path, self.run_key, self.lock = path, run_key, threading.Lock()
        self.done: dict[str, dict] = {}
        if os.path.exists(path):
            with open(path, encoding="utf-8") as f:
                for line in f:
                    try:
                        rec = json.loads(line)
                    except json.JSONDecodeError:
                        continue                          # torn final line after a crash
                    if rec.get("run_key") == run_key:
                        self.done[rec["id"]] = rec

    def save(self, rec: dict) -> None:
        rec = {**rec, "run_key": self.run_key}
        line = json.dumps(rec, sort_keys=True) + "\n"
        with self.lock:
            with open(self.path, "a", encoding="utf-8") as f:
                f.write(line)
                f.flush()
                os.fsync(f.fileno())
            self.done[rec["id"]] = rec


def run_key(model_name: str, model_params: dict, scorers: list, dataset: list[Example]) -> str:
    """Anything that changes results changes the key, so stale results are never reused."""
    blob = json.dumps({"model": model_name, "params": model_params,
                       "scorers": [s.name for s in scorers],
                       "data": hashlib.sha256(json.dumps([asdict(e) for e in dataset]).encode()).hexdigest()},
                      sort_keys=True)
    return hashlib.sha256(blob.encode()).hexdigest()[:16]


# ---------------------------------------------------------------- the runner
@dataclass
class RunConfig:
    workers: int = 8
    rate_per_s: float = 50.0
    burst: int = 5
    max_attempts: int = 4
    backoff_base_s: float = 0.05
    seed: int = 0


class EvalRunner:
    def __init__(self, model: Model, model_name: str, scorers: list, store: ResultStore,
                 cfg: RunConfig | None = None, sleep=time.sleep) -> None:
        self.model, self.model_name, self.scorers, self.store = model, model_name, scorers, store
        self.cfg = cfg or RunConfig()
        self.sleep = sleep
        self.bucket = TokenBucket(self.cfg.rate_per_s, self.cfg.burst, sleep=sleep)
        self.model_calls = 0
        self._calls_lock = threading.Lock()
        self._stop = threading.Event()                    # set by a fatal error: start no new work

    def run(self, dataset: list[Example]) -> list[dict]:
        todo = [ex for ex in dataset if ex.id not in self.store.done]
        pool = ThreadPoolExecutor(self.cfg.workers, thread_name_prefix="eval")
        try:
            for fut in [pool.submit(self._one, ex) for ex in todo]:
                fut.result()                              # re-raises a fatal error from a worker
        except BaseException:
            pool.shutdown(wait=True, cancel_futures=True) # stop promptly; finished work is on disk
            raise
        pool.shutdown(wait=True)
        return [self.store.done[ex.id] for ex in dataset]

    def _one(self, ex: Example) -> None:
        if self._stop.is_set():
            return
        try:
            self._run_example(ex)
        except BaseException:
            self._stop.set()
            raise

    def _run_example(self, ex: Example) -> None:
        rng = random.Random(f"{self.cfg.seed}:{ex.id}")   # deterministic jitter per example
        t0, attempts, output, error = time.perf_counter(), 0, None, None
        while attempts < self.cfg.max_attempts:
            attempts += 1
            self.bucket.acquire()
            with self._calls_lock:
                self.model_calls += 1
            try:
                output = self.model(ex.input)
                break
            except TransientError as e:
                error = f"TransientError: {e}"
                if attempts < self.cfg.max_attempts:
                    cap = self.cfg.backoff_base_s * 2 ** (attempts - 1)
                    self.sleep(rng.uniform(0, cap))           # full jitter
            except Exception as e:                        # a permanent failure: do not retry
                error = f"{type(e).__name__}: {e}"
                break
        rec = {"id": ex.id, "tags": list(ex.tags), "attempts": attempts,
               "latency_s": round(time.perf_counter() - t0, 4)}
        if output is None:
            rec.update(status="error", error=error, scores={})
        else:
            scores, serr = {}, None
            for s in self.scorers:
                try:
                    scores[s.name] = s(ex, output)
                except Exception as e:                    # a scorer bug is not the model's failure
                    serr = f"{s.name}: {type(e).__name__}: {e}"
            rec.update(status="ok" if serr is None else "scorer_error", output=output,
                       scores=scores, error=serr)
        self.store.save(rec)


# ---------------------------------------------------------------- statistics and the report
def wilson(successes: int, n: int, z: float = 1.96) -> tuple[float, float]:
    if n == 0:
        return (0.0, 1.0)
    p = successes / n
    denom = 1 + z * z / n
    centre = (p + z * z / (2 * n)) / denom
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / denom
    return (max(0.0, centre - half), min(1.0, centre + half))


def bootstrap_ci(values: list[float], seed: int = 0, iters: int = 2000, alpha: float = 0.05) -> tuple[float, float]:
    if not values:
        return (0.0, 1.0)
    rng, n = random.Random(seed), len(values)
    means = sorted(sum(rng.choices(values, k=n)) / n for _ in range(iters))
    return (means[int(alpha / 2 * iters)], means[int((1 - alpha / 2) * iters) - 1])


def report(results: list[dict], scorers: list, seed: int = 0) -> dict:
    ok = [r for r in results if r["status"] == "ok"]
    out = {"n": len(results), "scored": len(ok),
           "errors": sum(r["status"] == "error" for r in results),
           "scorer_errors": sum(r["status"] == "scorer_error" for r in results),
           "retried": sum(r["attempts"] > 1 for r in results), "metrics": {}, "slices": {}}
    lat = sorted(r["latency_s"] for r in results)
    out["latency_p50_s"] = lat[len(lat) // 2] if lat else 0.0
    for s in scorers:
        vals = [r["scores"][s.name] for r in ok]
        mean = sum(vals) / len(vals) if vals else 0.0
        ci = wilson(round(sum(vals)), len(vals)) if s.binary else bootstrap_ci(vals, seed)
        out["metrics"][s.name] = {"mean": round(mean, 4), "ci95": (round(ci[0], 4), round(ci[1], 4)), "n": len(vals)}
    for tag in sorted({t for r in ok for t in r["tags"]}):
        rows = [r for r in ok if tag in r["tags"]]
        out["slices"][tag] = {s.name: round(sum(r["scores"][s.name] for r in rows) / len(rows), 4)
                              for s in scorers} | {"n": len(rows)}
    return out


# ---------------------------------------------------------------- tests
def make_dataset(n: int = 100) -> list[Example]:
    caps = ["Paris", "Rome", "Madrid", "Berlin", "Lisbon"]
    return [Example(f"ex{i:03d}", f"Q{i}: capital #{i % 5}?", caps[i % 5],
                    ("geo", "long" if i % 5 in (0, 1) else "short")) for i in range(n)]


def fake_model(fail_every: int = 5) -> Model:
    """Correct except on every fail_every-th question, where it answers 'London'."""
    caps = ["Paris", "Rome", "Madrid", "Berlin", "Lisbon"]

    def model(prompt: str) -> str:
        i = int(prompt[1:prompt.index(":")])
        return "London." if i % fail_every == 0 else f"The answer is {caps[i % 5]}."
    return model


def stub_judge(question: str, expected: str, output: str) -> int:
    return 5 if expected.lower() in output.lower() else 2


def store(tmp: str, key: str = "k") -> ResultStore:
    return ResultStore(os.path.join(tmp, "results.jsonl"), key)


SCORERS = [ExactMatch(), RegexMatch(r"\b{expected}\b"), JudgeScorer(stub_judge)]


def test_scorers() -> None:
    ex = Example("a", "q", "Paris")
    assert ExactMatch()(ex, " paris! ") == 1.0 and ExactMatch()(ex, "It is Paris") == 0.0
    assert RegexMatch(r"\b{expected}\b")(ex, "It is Paris.") == 1.0
    assert RegexMatch(r"\b{expected}\b")(ex, "Parisian food") == 0.0
    assert JudgeScorer(stub_judge)(ex, "Paris") == 1.0 and JudgeScorer(stub_judge)(ex, "Rome") == 0.25


def test_end_to_end_report_and_intervals() -> None:
    with tempfile.TemporaryDirectory() as tmp:
        data = make_dataset(100)
        runner = EvalRunner(fake_model(5), "fake", SCORERS, store(tmp), RunConfig(workers=8, rate_per_s=1e6, burst=100))
        rep = report(runner.run(data), SCORERS)
    m = rep["metrics"]
    assert m["exact"]["mean"] == 0.0                      # 'The answer is Paris.' is not an exact match
    assert m["regex"]["mean"] == 0.8 and m["regex"]["ci95"] == (0.7112, 0.8666)   # Wilson, n = 100
    assert m["judge"]["mean"] == 0.85                     # 80 x 1.0 + 20 x 0.25
    lo, hi = m["judge"]["ci95"]
    assert lo < 0.85 < hi and hi - lo < 0.15
    assert rep["slices"]["long"] == {"exact": 0.0, "regex": 0.5, "judge": 0.625, "n": 40}   # every failure is here
    assert rep["slices"]["short"]["regex"] == 1.0 and rep["slices"]["short"]["n"] == 60


def test_retries_transient_then_records_permanent_errors() -> None:
    calls: dict[str, int] = {}
    lock = threading.Lock()

    def flaky(prompt: str) -> str:
        with lock:
            calls[prompt] = calls.get(prompt, 0) + 1
            n = calls[prompt]
        if prompt.startswith("Q1:") and n < 3:
            raise TransientError("overloaded")           # succeeds on the 3rd attempt
        if prompt.startswith("Q2:"):
            raise TransientError("always overloaded")    # exhausts retries
        if prompt.startswith("Q3:"):
            raise ValueError("prompt too long")          # permanent: no retry
        return "Paris"
    with tempfile.TemporaryDirectory() as tmp:
        slept: list[float] = []
        r = EvalRunner(flaky, "f", [ExactMatch()], store(tmp), RunConfig(workers=2, rate_per_s=1e6, burst=10),
                       sleep=slept.append)
        res = {x["id"]: x for x in r.run(make_dataset(5))}
    assert res["ex001"]["status"] == "ok" and res["ex001"]["attempts"] == 3
    assert res["ex002"]["status"] == "error" and res["ex002"]["attempts"] == 4
    assert res["ex003"]["status"] == "error" and res["ex003"]["attempts"] == 1
    assert len(slept) == 2 + 3 and all(0 <= s <= 0.05 * 4 for s in slept)
    rep = report(list(res.values()), [ExactMatch()])
    assert rep["errors"] == 2 and rep["metrics"]["exact"]["n"] == 3           # errors are not zeros


def test_resume_after_crash_reuses_finished_work() -> None:
    data = make_dataset(60)

    class Crash(BaseException):                          # not an Exception: kills the run like Ctrl-C
        pass
    seen: list[str] = []

    def crashing(prompt: str) -> str:
        seen.append(prompt)
        if len(seen) == 25:
            raise Crash()
        return fake_model()(prompt)
    with tempfile.TemporaryDirectory() as tmp:
        key = run_key("fake", {"t": 0}, SCORERS, data)
        try:
            EvalRunner(crashing, "fake", SCORERS, store(tmp, key), RunConfig(workers=1, rate_per_s=1e6)).run(data)
        except Crash:
            pass
        st = store(tmp, key)
        assert len(st.done) == 24                         # finished work survived
        r2 = EvalRunner(fake_model(), "fake", SCORERS, st, RunConfig(workers=4, rate_per_s=1e6, burst=20))
        resumed = r2.run(data)
        assert r2.model_calls == 36                       # only the unfinished examples were called
        with tempfile.TemporaryDirectory() as tmp2:
            clean = EvalRunner(fake_model(), "fake", SCORERS, store(tmp2, key),
                               RunConfig(workers=4, rate_per_s=1e6, burst=20)).run(data)
        strip = lambda rows: [{k: v for k, v in x.items() if k != "latency_s"} for x in rows]
        assert strip(resumed) == strip(clean)             # same results as an uninterrupted run
        assert report(resumed, SCORERS) ["metrics"] == report(clean, SCORERS)["metrics"]

def test_rate_limit_and_concurrency() -> None:
    in_flight, peak, lock = [0], [0], threading.Lock()

    def slow(prompt: str) -> str:
        with lock:
            in_flight[0] += 1
            peak[0] = max(peak[0], in_flight[0])
        time.sleep(0.02)
        with lock:
            in_flight[0] -= 1
        return "Paris"
    with tempfile.TemporaryDirectory() as tmp:
        t0 = time.monotonic()
        EvalRunner(slow, "s", [ExactMatch()], store(tmp), RunConfig(workers=6, rate_per_s=100, burst=1)).run(make_dataset(40))
        elapsed = time.monotonic() - t0
    assert peak[0] <= 6 and peak[0] >= 2                  # pool size caps concurrency
    assert elapsed >= 0.38                                # 40 calls at 100/s with burst 1: >= ~0.39 s

10 · Edge cases

Duplicate example ids: the store keys by id, so a duplicate would be skipped as already done; validate ids are unique before running. Empty dataset or all errors: means over zero scored examples are undefined; the report returns n = 0 and the widest interval, and the caller should treat it as a failed run. Judge returns out-of-range ratings: the scorer raises and the record is a scorer error, visible in the report. Rate limit headers: real providers send Retry-After; honour it instead of the formula when present. Very slow examples: add a per-call timeout so one stuck call cannot hold a worker forever. Disk full: an append failure must stop the run loudly; silently continuing would lose results that appear to have been saved.

11 · Extensions the interviewer will ask for

Paired comparison of two runs: join by id, compute per-example differences, report the mean difference with a bootstrap interval and win/loss/tie counts. Cache model outputs separately from scores, so a new scorer re-scores without re-calling the model. Clustered intervals when examples come in groups (bootstrap over groups). Multiple samples per example at non-zero temperature, to reduce variance and measure consistency (pass@k). Async with asyncio.Semaphore and an async token bucket for thousands of concurrent calls. Distributed runs: shard examples across machines with a shared rate limiter (cd12) and a shared result store. Cost tracking per example from usage fields, and a budget that stops the run. Batch APIs for large, non-urgent runs at lower cost.

12 · Complexity

Wall time ≈ max(n × latency / workers, n / rate) plus retries, so the run is bounded by whichever of concurrency or rate limit binds. Each example does O(attempts) model calls, O(scorers) scoring, and one append with an fsync — the fsync (milliseconds on many disks) can dominate for fast fake models, which is why the stress test is the slowest. Reloading the store is O(file size). The report is O(n × scorers) plus O(B × n) for B bootstrap resamples per continuous metric. Memory is O(n) records.

Five statistical habits that change decisions

Anthropic's 2024 write-up on the statistics of model evaluations, with Evan Miller's accompanying paper, makes five recommendations that map directly onto this runner. Report a standard error (or interval) with every score, via the central limit theorem. Cluster standard errors when questions come in related groups, because correlated questions carry less information than their count suggests. Reduce variance within questions — for example by sampling several answers per question when using chain-of-thought — so the score reflects the model rather than one lucky sample. Analyse paired differences when comparing two models on the same questions, so per-question difficulty cancels. And use power analysis before running, to know how many questions are needed to detect the difference you care about. The runner's record format (one line per example per run, with id and tags) is exactly what all five need.

Power: how many examples are enough

For two unpaired proportions near p, detecting a difference δ with 95% confidence and 80% power needs about n ≈ 2 × (1.96 + 0.84)² × p(1 − p) / δ² examples per model. At p = 0.8: δ = 10 points needs about 250; δ = 5 points about 1,000; δ = 2 points about 6,300. Paired designs on the same examples need fewer, often several times fewer when the two models agree on most examples, because only disagreements carry information. This arithmetic, done before building a dataset, prevents the most common eval mistake: declaring a winner from a difference smaller than the noise.

Judges need their own evaluation

A judge scorer is a model making errors of its own: preferences for longer answers, for its own model family's style, for the first of two options in pairwise comparisons, and sensitivity to rubric wording. Before trusting a judge metric, measure its agreement with human labels on a sample (ev4), keep that sample as a regression test for the judge, and fix its version, prompt and temperature in the run key so judge changes invalidate cached scores. When the judge and a deterministic scorer disagree, the disagreements are the most informative examples to read.

Determinism and what "the same run" means

Reproducibility has layers. The runner's own randomness (jitter, bootstrap) is seeded. Scorers are pure functions. The model may not be: even at temperature 0, providers do not always guarantee identical outputs, because batching and numerical details vary. So "resume gives the same results" is guaranteed for the runner's logic and for stored outputs, not for fresh model calls; record the model version and timestamp per result, and treat an eval as a sample whose uncertainty the intervals describe. Separating output caching from scoring also makes a re-score fully deterministic: the outputs are fixed, only the scorer runs.

Slices can reverse the headline

Aggregate scores can mislead when slices have different sizes. Suppose model B beats model A on both short and long questions, but B's run happened to include more long (harder) questions because some short ones errored: B's overall average can still come out lower. This is Simpson's paradox, and it is one more reason to compare models on exactly the same examples, with errors handled the same way, and to read per-slice tables before the headline. Slices also guide what to fix: a 50% score on "long" questions with 100% on "short" points at context handling or truncation, not at the model's knowledge.

Contamination and dataset hygiene

An eval measures what it was meant to only if the model has not seen the answers. Public benchmarks leak into training data; internal datasets leak into prompts when engineers paste failing examples as few-shot demonstrations. Keep a held-out set that is never used in prompts or tuning, version datasets (their hash is already in the run key), and rotate in fresh examples from recent production traffic. A sudden jump on an old dataset with no jump on fresh examples is the signature of contamination, not progress.

Rate limits are shared resources

Provider limits apply per organisation or API key, not per process. An eval run that saturates the limit can starve the production service using the same key — a self-inflicted outage during an experiment. Use a separate key or workspace for evals, set the runner's rate below the limit with headroom for production, and prefer batch interfaces for large offline runs. If several eval jobs run at once, they need a shared limiter (a Redis-backed token bucket, cd12), not one bucket each.

How eval runners fail in practice

Decisions made on noise. Symptom: model choices flip between runs. Cause: small datasets and no intervals; differences of a few points on 100-200 examples. Fix: intervals on every metric, paired comparisons, and power analysis to size the dataset.

Outages scored as regressions. Symptom: a candidate model's score drops during a provider incident. Cause: errors counted as zeros. Fix: separate error accounting; rerun or exclude errors, and alert when the error rate exceeds a threshold so the run is flagged as unreliable.

Stale results reused. Symptom: a "new" run shows identical numbers to the last. Cause: a cache keyed by example id only, not by configuration. Fix: a run key that hashes model, parameters, prompt version, scorers and dataset.

Production starved by an eval. Symptom: users see rate-limit errors while an eval runs. Cause: eval and production share an API key and the eval saturates it. Fix: separate keys, a runner rate below the limit, batch APIs.

Lost runs. Symptom: a long run dies at 90% and starts over. Cause: results held in memory. Fix: append-and-fsync per example, resumable by run key.

Judge drift. Symptom: judge scores shift after an unrelated change. Cause: the judge model or prompt changed without invalidating cached scores. Fix: include the judge's version and prompt in the run key; keep a human-labelled sample to monitor judge agreement.

Silent truncation. Symptom: scores fall on long inputs only. Cause: the runner or the model client truncates long prompts to a maximum length without saying so. Fix: record input token counts per example and fail, rather than truncate, when an input exceeds the limit.

What to measure about the runner itself

Throughput (examples per minute) against the configured rate; error and retry rates by error type; time spent waiting on the rate limiter versus calling the model; cost per run; and the fraction of examples reused from cache on resumed runs. For the results: every metric with its interval and n, error counts, per-slice tables, and for comparisons the paired difference with its interval.

Knobs

Workers (≈ rate × latency, with headroom); rate and burst (below the provider limit, leaving room for production traffic); max attempts and backoff base; bootstrap iterations (2,000 is plenty for a 95% interval); which tags to slice by; and whether to fsync per record (safest) or per batch (faster, loses at most a batch on crash).

Plan it

You must decide whether a new model is better than the current one on a support-answer benchmark. Current accuracy is about 80%. The product cares about a 3-point improvement. Calls take 4 seconds, the eval key's limit is 30 requests per second, and the judge is a second model call per example with the same latency. How many examples, how many workers, and how long will the run take?

Answer

Unpaired, n ≈ 2 × (1.96 + 0.84)² × 0.8 × 0.2 / 0.03² = 2 × 7.84 × 0.16 / 0.0009 ≈ 2,790 per model. Paired on the same examples needs fewer — perhaps 1,000-1,500 if the models agree on most items — so plan 1,500 examples, run both models on all of them, and analyse paired differences. Calls: 1,500 examples × 2 models × 2 calls (answer + judge) = 6,000 calls. Rate-bound time: 6,000 ÷ 30 = 200 seconds. Workers: rate × latency = 30 × 4 = 120 in flight to reach the limit; use about 120 workers with the shared token bucket. Expect 4-5 minutes with retries. Keep the eval on its own key so production is not starved.

Diagnose it

A nightly eval shows the production model's accuracy falling from 84% to 79% overnight, with no model or prompt change. The report says n = 812 of 1,000 examples scored. What do you check first?

Answer

188 examples were not scored: check the error counts and types. If the runner counted errors in the denominator or the errors are not random — for example, long inputs timing out more under provider load — the scored subset is biased toward easier or harder examples, and the 5-point drop may be selection, not quality. Compare per-slice scores and the error distribution across slices, and compare the 812 scored examples with the same examples in yesterday's run (a paired comparison on the intersection). Then rerun the errored examples. If the drop persists on a complete, paired comparison, look for silent changes: a provider model update behind the same name, a judge change, or a dataset change (the run key would reveal that).
