A support chatbot calls a hosted language model for every reply. On a normal day the call takes two seconds and works. One afternoon the provider is overloaded: a third of calls return an "overloaded" error, the rest take twenty seconds. The chatbot's code retries every failure immediately, three times. Within minutes it is sending more than twice its normal traffic to a provider that was already failing, every reply takes a minute, the web servers run out of worker threads waiting on slow calls, and the chatbot's own health checks start failing. A partial problem at the provider has become a total outage at the customer, caused largely by the customer's own retry loop.

A model API is a network call to a shared, heavily loaded service, and it fails in more ways than most dependencies. Rate limits are routine at any real volume. Overload errors come in bursts. Latency is large and extremely variable, because it depends on how many tokens the model writes. Streaming responses can fail halfway through. And every call costs money, so a retry of a call that actually succeeded may charge twice.

The resilient client is the small layer between your application and the provider that handles all of this deliberately. It decides which errors are worth retrying, how long to wait, when to stop retrying entirely because the provider is clearly unhealthy, when to give up because the caller's time has run out, which alternative model to use instead, and what to do when a stream breaks after the user has already seen half an answer.

This is a favourite machine-coding round for AI-engineer roles because each piece is simple and the interactions are subtle. The textbook circuit breaker that opens after five consecutive failures does not open under a sustained 40 percent error rate. Retries that look harmless per request triple the load on a dying service. Jitter, which sounds like a refinement, is the part that prevents synchronised retry waves. Interviewers probe exactly these points.

The lesson follows the round: the requirements to clarify, the entities and their interface, then a build in stages. It starts with the naive retry loop and shows why it amplifies failure, then adds error classification, backoff with full jitter, a deadline, a client-wide retry budget, a sliding-window circuit breaker with a half-open state, provider fallback, idempotency keys and the streaming commit point. It ends with the full tested solution, edge cases, extensions, complexity, and how resilience4j and the Google SRE book handle the same problems in production.

Two kinds of failure, two tools

Failures come in two shapes, and the design is easiest to understand once you separate them. Transient, uncorrelated failures are one-off: a dropped connection, a single overloaded server behind a load balancer, a momentary rate limit. Trying again shortly afterwards usually works, so the tool is a retry. Sustained, correlated failures affect everyone at once: the provider is overloaded or down for minutes. Retrying makes them worse, because every client retries at once and the provider receives more traffic exactly when it can handle less. The tool for these is a circuit breaker, which notices that failures are frequent and stops sending calls for a while, failing fast instead. Retries handle the first kind; the breaker handles the second; most of the subtlety is in making sure the first does not make the second worse.

The circuit breaker, by analogy

The name comes from household wiring. When too much current flows, a breaker trips and cuts the circuit, protecting the wiring from burning. You then reset it once the fault is fixed. A software circuit breaker sits in front of a dependency and watches recent calls. In the closed state calls flow normally. When the recent failure rate crosses a threshold, it trips to open: calls fail immediately with no network traffic, which protects both your service (no threads stuck waiting) and the dependency (no load while it recovers). After a waiting period it moves to half-open and lets a few probe calls through. If they succeed, it closes; if one fails, it opens again for another wait.

Backoff and jitter

Backoff means waiting before a retry, and waiting longer after each failure: 0.5 seconds, then 1, then 2, up to a cap. That is exponential backoff, and it gives a struggling service room to recover. But if a thousand clients all fail at the same instant (because the service hiccupped for everyone), they all compute the same 0.5 seconds and all retry together, then all fail together and all wait 1 second, and so on: synchronised waves. Jitter adds randomness. With full jitter each client waits a random time between zero and the backoff value, so the thousand retries spread across the interval instead of landing together. AWS's analysis found that jitter of this kind dramatically reduces the total work clients and servers do.

Idempotency: is a retry safe at all?

An operation is idempotent if doing it twice has the same effect as doing it once. Reading is idempotent; charging a card is not. A model completion is mostly harmless to repeat, but it costs money, and if the model's output triggers actions (sending an email via a tool call) a duplicate is real damage. The trouble is that a timeout does not tell you whether the server did the work. The standard answer is an idempotency key: a unique id generated once per logical request and sent with every attempt, so the server can recognise a repeat and return the first result instead of doing the work again.

Fallback and the commit point

When the preferred provider is failing, a fallback sends the request to an alternative: the same model in another region, a different provider, or a smaller model. For a normal request this is transparent. For a streamed response, it is transparent only until the first chunk reaches the user. After that commit point, switching would splice the start of one model's answer onto another's, so the client must report a partial response and let the application decide.

1 · Clarify the requirements

Ask what the caller's latency budget is (an interactive chat reply and a nightly batch job tolerate very different waits), whether responses are streamed, which providers or models are acceptable as fallbacks and in what order, whether requests have side effects that must not be duplicated, how much extra cost retries may add, and whether the client is shared by many threads. Ask also what the provider's errors look like: which status codes mean overload, whether it sends Retry-After, and whether its SDK already retries.

A typical agreed scope: a synchronous complete call with an overall deadline, an ordered list of providers, transparent retry of transient failures, no retry of client errors, a circuit breaker per provider, idempotency keys, and a streaming variant that may fall back only before the first chunk. Thread-safe, because one client object is shared by a web server's workers. Non-functional targets to state: never exceed the caller's deadline; under a total provider outage, add no more than about 10 percent extra load; fail fast (no network call) when a provider is known to be down.

2 · Entities and responsibilities

Six pieces, each with one job. A Provider bundles a callable that performs one attempt, its maximum context length, and its own breaker. The error classes carry the status and any Retry-After value, and is_retryable decides policy in one place. The RetryPolicy knows the attempt cap and computes backoff waits. The RetryBudget is shared across all requests and limits retries as a fraction of traffic. The CircuitBreaker tracks one provider's health and gates its calls. The ResilientClient orchestrates: it owns the deadline, the idempotency key, the loop over providers and attempts, and the logging that explains what happened. A Clock abstraction provides now and sleep, so tests can replace it with a fake whose sleep simply advances time.

3 · Stage one: the naive retry loop, and why it hurts

def complete(request):
    for attempt in range(3):
        try:
            return provider.call(request)
        except Exception:
            time.sleep(2 ** attempt)        # 1, 2, 4 seconds
    raise RuntimeError("failed")

It retries everything, including a malformed request that will fail identically three times. It has no jitter, so every client that failed together retries together. It ignores Retry-After. It has no deadline, so a caller with two seconds left may wait seven. It never stops calling a provider that is down, so every request pays the full timeout and backoff before failing. And it multiplies load. Suppose 500 requests per second and a provider failing 40 percent of calls. The first attempts are 500; 200 fail and retry; 80 of those fail and retry again. The provider now receives 780 requests per second instead of 500, more than half as much again, while it is already failing. That is retry amplification, and it is how a partial degradation becomes an outage.

4 · Classify errors first

Before deciding how to retry, decide whether to. The solution puts that decision in one function. Network errors and timeouts (status 0 and 408), 5xx server errors, 529 overloaded and 503 unavailable are transient: retry. 429 rate limits are usually transient, and the server says when to come back. But not always: Anthropic's error documentation notes that a 429 caused by reaching a spend cap has no retry-after header and keeps failing until access resumes, so the solution retries 429 only when Retry-After is present. 400, 401, 403 and 404 mean the request or credentials are wrong; retrying cannot help, so they are raised to the caller at once. A context-length error is a 400 with a twist: the same model will never accept the prompt, but a model with a larger window might, so it triggers fallback rather than either retry or failure.

5 · Stage two: backoff with full jitter, Retry-After and a deadline

The retry wait for attempt a (counting from zero) is a uniform random number between 0 and min(cap, base × 2^a): with base 0.5 seconds, up to 0.5, then up to 1, then up to 2, capped at 8. That is full jitter, which AWS's simulations found uses the least total work among the jitter strategies they compared. If the error carries Retry-After, the client waits exactly that long instead: the server knows its own recovery schedule better than a formula does.

The deadline is computed once as an absolute time. Each attempt's timeout is the smaller of the per-attempt limit and the time remaining, and before any backoff sleep the client checks whether the sleep would end past the deadline; if so it raises DeadlineExceeded at once rather than sleeping uselessly. The test test_deadline_stops_retries gives a 30-second deadline and a Retry-After of 50: the client fails immediately without sleeping.

6 · Stage three: a client-wide retry budget

A per-request attempt cap is necessary but not sufficient. During a full outage, every request uses all its attempts, and with a cap of three the provider sees three times normal traffic. Google's SRE book describes the fix used there: alongside a per-request budget of up to three attempts, a per-client retry budget that only allows a retry while retries are below 10 percent of requests. The solution implements it as a token bucket, the structure from the rate-limiter case: each first attempt deposits 0.1 tokens (up to a cap of 10), and each retry must spend one whole token. In normal operation, when failures are rare, the bucket stays full and every transient failure can be retried. In a broad outage, the bucket drains within a few dozen failures, and from then on only about one request in ten gets a retry.

The test drives 1,000 requests at a provider that always fails, with three attempts allowed. Without a budget the provider receives 3,000 attempts. With the budget it receives 1,109: the 1,000 first attempts, the initial 10 banked tokens, and about one retry per ten requests. The amplification falls from 3 to about 1.1, and it does so automatically, with no one having to notice the outage.

7 · Stage four: the circuit breaker

The textbook breaker counts consecutive failures and opens after, say, five. It looks right and does not work at volume. With independent failures at 40 percent, the probability that a given five calls all fail is 0.45, about 1 percent, and every success resets the count, so the breaker can stay closed through a long, heavy degradation. The solution uses what production libraries use: a count-based sliding window, a deque holding the last N outcomes (failed or not). After each recorded outcome, if at least min_calls outcomes are in the window and the failure fraction is at or above the threshold, the breaker opens.

The test test_breaker_opens_on_rate_not_streak feeds the pattern fail, ok, fail, ok, ok twice: 40 percent failures and never two in a row. After nine calls the breaker stays closed because the minimum is ten; on the tenth it opens. The minimum matters at low volume: one failure out of two calls is a 50 percent rate, and without a minimum the breaker would trip on noise.

While open, acquire() raises CircuitOpen immediately, and the client moves to the next provider without any network call. After open_for seconds the next acquire() moves the breaker to half-open and admits up to half_open_calls probes at a time; a further caller is rejected until a probe finishes. If every probe succeeds the breaker closes and clears its window; if any probe fails it opens again with a fresh timer. Limiting concurrent probes is important: without it, the moment the wait ends every queued request rushes the recovering provider, trips the breaker again, and the system oscillates.

What counts as a failure is a design decision worth saying aloud: only outcomes that reflect the provider's health. The client records a 400 as a success for breaker purposes, because a bug in your prompt-building code should not open the circuit and cut every user off from a healthy provider.

Breaker state is shared by every thread using the client, so acquire and record each hold a lock while they read and change state. The check "is it open, and has the wait elapsed?" followed by the change to half-open is a check-then-act sequence; without the lock two threads could both make the transition and both count themselves as the only probe.

8 · Stage five: fallback and context routing

The client walks its providers in order. For each, it first checks whether the request's token count fits the provider's context; if not it skips it, logging why. Then it tries up to the attempt cap, moving on when the breaker is open, when attempts or retry budget are exhausted, or when the error is a context-length error. A client error is raised immediately, since another provider would reject the same malformed request. Only when every provider is exhausted does it raise AllProvidersFailed with the last error.

In test_fallback_and_context_routing, a small-context model is skipped for a 50,000-token request, the primary fails once and (with a breaker configured to open on the first failure) opens, and the backup serves the request. On the next request the primary is skipped instantly with "circuit open", which is the point of the breaker: no thread waits on a provider known to be down.

9 · Idempotency keys

The key is generated once, before the loop, unless the caller supplied one, and passed to every attempt and every provider. The first test checks that three attempts carried one key. Generating it inside the loop is a classic bug: each retry then looks like a new request to the server, and if the first attempt actually succeeded but its response was lost, the work is done twice. Note that a key only deduplicates within one provider; falling back to another provider genuinely does the work again, which is acceptable for a completion but not for a side effect.

10 · Streaming and the commit point

Streaming changes the contract. The client opens the stream and reads the first chunk inside the error-handling block; any failure up to there can go to the next provider exactly as before. Once the first chunk is yielded to the caller, the request is committed. If the stream later fails, the client raises PartialResponse rather than retrying, because the caller already holds text from this model. Anthropic's documentation makes the same point from the provider side: with server-sent events (SSE), an error can arrive after the API has already returned a 200 response, and such errors do not follow the usual status-code handling. The test makes the first provider fail before any output and the second fail after two chunks; the caller receives both chunks and then a partial-response error. For streaming, replace the single per-attempt timeout with two: a time-to-first-token timeout, the best early signal of an unhealthy call, and an idle timeout between chunks, so a long but steadily flowing answer is never cut off.

11 · Testing without the network or the clock

Resilience code is notoriously hard to test against a real provider: you cannot make it fail on demand, and real backoff makes tests slow. Two test doubles solve both problems. A scripted provider is a function that pops the next outcome from a list, either an exception to raise or a value to return, so a test states the exact failure sequence it wants: "529, then 503, then success". A fake clock implements now and sleep, where sleep records the requested duration and advances the fake time. Tests then assert on behaviour precisely: how many attempts were made, which keys they carried, how long the client chose to sleep, and in what state the breaker ended. Every test in the solution runs in microseconds, is deterministic (the retry policy takes a seeded random generator), and never touches the network. This is dependency injection paying for itself, and saying so in the interview signals that you have tested this kind of code before.

12 · The full solution

The file below implements everything above with ten tests, including the 40-percent breaker test, the retry-budget amplification test, the streaming commit-point test and an eight-thread breaker test. Python 3.12, standard library only; all tests pass in well under a second because the fake clock's sleep only advances a number.

"""A resilient LLM client: error classification, retries with full jitter, a retry budget,
a sliding-window circuit breaker, deadlines, idempotency keys and provider fallback,
including the streaming 'commit point'. Python 3.12, standard library only.
Run: python resilient.py"""
from __future__ import annotations

import random
import threading
import uuid
from collections import deque
from dataclasses import dataclass, field
from enum import Enum
from typing import Callable, Iterator


# ------------------------------------------------------------------ errors
class ProviderError(Exception):
    """Raised by a provider call. `status` mirrors the HTTP status (0 = network/timeout)."""

    def __init__(self, status: int, msg: str = "", retry_after: float | None = None) -> None:
        super().__init__(f"{status} {msg}")
        self.status, self.retry_after = status, retry_after


class ContextTooLong(ProviderError):
    """The prompt does not fit this model: never retry, but a larger-context fallback may work."""

    def __init__(self) -> None:
        super().__init__(400, "context length exceeded")


class CircuitOpen(Exception): ...
class DeadlineExceeded(Exception): ...
class PartialResponse(Exception):
    """A stream failed after tokens reached the caller: cannot silently retry or switch."""


class AllProvidersFailed(Exception): ...


RETRYABLE = {0, 408, 429, 500, 502, 503, 504, 529}      # network, timeout, rate limit, server, overloaded


def is_retryable(e: ProviderError) -> bool:
    # A 429 without Retry-After from a spend cap keeps failing; real clients inspect the error
    # type. Here: retry 429 only when the server tells us when.
    if e.status == 429:
        return e.retry_after is not None
    return e.status in RETRYABLE


# ------------------------------------------------------------------ clock
class Clock:
    """Real time by default; tests replace it with a fake whose sleep just advances time."""

    def now(self) -> float:
        import time
        return time.monotonic()

    def sleep(self, s: float) -> None:
        import time
        time.sleep(s)


# ------------------------------------------------------------------ circuit breaker
class State(Enum):
    CLOSED, OPEN, HALF_OPEN = "closed", "open", "half_open"


class CircuitBreaker:
    """Count-based sliding window of the last `window` outcomes (like resilience4j's default).
    Opens when failure rate >= threshold once `min_calls` are recorded; after `open_for` seconds
    lets `half_open_calls` probes through; all succeed -> CLOSED, any fails -> OPEN again."""

    def __init__(self, clock: Clock, window: int = 20, min_calls: int = 10,
                 threshold: float = 0.5, open_for: float = 30.0, half_open_calls: int = 2) -> None:
        self.clock, self.window, self.min_calls = clock, window, min_calls
        self.threshold, self.open_for, self.half_open_calls = threshold, open_for, half_open_calls
        self.state = State.CLOSED
        self.outcomes: deque[bool] = deque(maxlen=window)   # True = failure
        self.opened_at = 0.0
        self.probes_in_flight = self.probe_successes = 0
        self._lock = threading.Lock()

    def acquire(self) -> None:
        """Call before each attempt. Raises CircuitOpen to fail fast."""
        with self._lock:
            if self.state is State.OPEN:
                if self.clock.now() - self.opened_at < self.open_for:
                    raise CircuitOpen()
                self.state, self.probes_in_flight, self.probe_successes = State.HALF_OPEN, 0, 0
            if self.state is State.HALF_OPEN:
                if self.probes_in_flight >= self.half_open_calls:
                    raise CircuitOpen()                   # only a few probes at a time
                self.probes_in_flight += 1

    def record(self, failed: bool) -> None:
        with self._lock:
            if self.state is State.HALF_OPEN:
                if failed:
                    self._open()
                else:
                    self.probe_successes += 1
                    if self.probe_successes >= self.half_open_calls:
                        self.state = State.CLOSED
                        self.outcomes.clear()
                return
            if self.state is State.OPEN:                   # late result from before opening
                return
            self.outcomes.append(failed)
            n = len(self.outcomes)
            if n >= self.min_calls and sum(self.outcomes) / n >= self.threshold:
                self._open()

    def _open(self) -> None:
        self.state, self.opened_at = State.OPEN, self.clock.now()


# ------------------------------------------------------------------ retry policy
class RetryBudget:
    """Client-wide: each first attempt deposits `ratio` tokens (capped); each retry spends one.
    Under a total outage retries fall to about `ratio` of traffic instead of multiplying it."""

    def __init__(self, ratio: float = 0.1, cap: float = 10.0) -> None:
        self.ratio, self.cap, self.tokens = ratio, cap, cap
        self._lock = threading.Lock()

    def on_request(self) -> None:
        with self._lock:
            self.tokens = min(self.cap, self.tokens + self.ratio)

    def try_spend(self) -> bool:
        with self._lock:
            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False


@dataclass
class RetryPolicy:
    max_attempts: int = 3
    base: float = 0.5
    cap: float = 8.0
    rng: random.Random = field(default_factory=random.Random)

    def backoff(self, attempt: int, retry_after: float | None) -> float:
        if retry_after is not None:                       # the server knows best
            return retry_after
        return self.rng.uniform(0, min(self.cap, self.base * 2 ** attempt))   # full jitter


# ------------------------------------------------------------------ providers and client
@dataclass
class Provider:
    name: str
    call: Callable[[dict, float, str], object]            # (request, timeout, idem_key) -> response
    breaker: CircuitBreaker
    max_context: int = 200_000


class ResilientClient:
    def __init__(self, providers: list[Provider], clock: Clock, policy: RetryPolicy | None = None,
                 budget: RetryBudget | None = None, attempt_timeout: float = 60.0) -> None:
        self.providers, self.clock = providers, clock
        self.policy, self.budget = policy or RetryPolicy(), budget or RetryBudget()
        self.attempt_timeout = attempt_timeout
        self.log: list[str] = []

    def complete(self, request: dict, deadline_s: float = 120.0) -> object:
        deadline = self.clock.now() + deadline_s
        idem_key = request.get("idempotency_key") or str(uuid.uuid4())   # same key on every retry
        self.budget.on_request()
        last: Exception | None = None
        for p in self.providers:
            if request.get("tokens", 0) > p.max_context:
                self.log.append(f"{p.name}: skip, context too small")
                continue
            for attempt in range(self.policy.max_attempts):
                remaining = deadline - self.clock.now()
                if remaining <= 0:
                    raise DeadlineExceeded(f"after {self.log}")
                try:
                    p.breaker.acquire()
                except CircuitOpen as e:
                    self.log.append(f"{p.name}: circuit open")
                    last = e
                    break                                  # next provider
                try:
                    resp = p.call(request, min(self.attempt_timeout, remaining), idem_key)
                except ProviderError as e:
                    # client errors say nothing about provider health
                    p.breaker.record(failed=is_retryable(e))
                    last = e
                    self.log.append(f"{p.name}#{attempt}: {e}")
                    if isinstance(e, ContextTooLong):
                        break                              # a bigger model might fit
                    if not is_retryable(e):
                        raise                              # 400/401/403: our bug, not theirs
                    if attempt + 1 == self.policy.max_attempts or not self.budget.try_spend():
                        break                              # out of attempts or budget: fall back
                    wait = self.policy.backoff(attempt, e.retry_after)
                    if self.clock.now() + wait >= deadline:
                        raise DeadlineExceeded(f"after {self.log}")
                    self.clock.sleep(wait)
                    continue
                p.breaker.record(failed=False)
                self.log.append(f"{p.name}#{attempt}: ok")
                return resp
        raise AllProvidersFailed(str(last))

    def stream(self, request: dict, deadline_s: float = 120.0) -> Iterator[str]:
        """Retry/fallback is allowed only until the first chunk is yielded (the commit point)."""
        for p in self.providers:
            try:
                p.breaker.acquire()
            except CircuitOpen:
                continue
            try:
                it = iter(p.call(request, self.attempt_timeout, request.get("idempotency_key", "")))
                first = next(it)                           # failures before here are retryable
            except ProviderError as e:
                p.breaker.record(failed=is_retryable(e))
                if not is_retryable(e):
                    raise
                continue
            p.breaker.record(failed=False)
            yield first                                    # committed: the caller has output now
            try:
                yield from it
            except ProviderError as e:
                raise PartialResponse(f"{p.name} failed mid-stream: {e}") from e
            return
        raise AllProvidersFailed("no provider produced a first chunk")


# ------------------------------------------------------------------ tests
class FakeClock(Clock):
    def __init__(self) -> None:
        self.t, self.slept = 0.0, []

    def now(self) -> float:
        return self.t

    def sleep(self, s: float) -> None:
        self.slept.append(s)
        self.t += s


def scripted(outcomes: list, keys: list | None = None):
    """A fake provider: each call pops the next outcome (an exception to raise or a value)."""
    def call(req, timeout, key):
        if keys is not None:
            keys.append(key)
        o = outcomes.pop(0)
        if isinstance(o, Exception):
            raise o
        return o
    return call


def mk(clock, name, outcomes, keys=None, **kw):
    return Provider(name, scripted(outcomes, keys), CircuitBreaker(clock, **kw))


def test_transient_error_retried_with_same_key() -> None:
    clk, keys = FakeClock(), []
    c = ResilientClient([mk(clk, "a", [ProviderError(529), ProviderError(503), "hi"], keys)], clk,
                        RetryPolicy(rng=random.Random(1)))
    assert c.complete({}) == "hi"
    assert len(keys) == 3 and len(set(keys)) == 1          # one logical request, one key
    assert len(clk.slept) == 2 and all(0 <= s <= 1.0 for s in clk.slept)


def test_client_errors_are_never_retried() -> None:
    clk = FakeClock()
    c = ResilientClient([mk(clk, "a", [ProviderError(400, "bad json"), "unused"])], clk)
    try:
        c.complete({})
    except ProviderError as e:
        assert e.status == 400 and clk.slept == []
    else:
        raise AssertionError("400 was retried or swallowed")


def test_retry_after_is_obeyed() -> None:
    clk = FakeClock()
    c = ResilientClient([mk(clk, "a", [ProviderError(429, retry_after=7.0), "ok"])], clk)
    assert c.complete({}) == "ok" and clk.slept == [7.0]


def test_breaker_opens_on_rate_not_streak() -> None:
    clk = FakeClock()
    br = CircuitBreaker(clk, window=20, min_calls=10, threshold=0.4, open_for=30, half_open_calls=2)
    pattern = [True, False, True, False, False] * 2        # 40% failures, never 2 in a row
    for f in pattern[:9]:
        br.acquire(); br.record(f)
    assert br.state is State.CLOSED                        # 9 calls < min_calls
    br.acquire(); br.record(pattern[9])
    assert br.state is State.OPEN
    try:
        br.acquire()
    except CircuitOpen:
        pass
    else:
        raise AssertionError("open breaker let a call through")
    clk.t += 30
    br.acquire(); br.acquire()                             # two probes allowed
    try:
        br.acquire()
    except CircuitOpen:
        pass                                               # a third concurrent probe is not
    br.record(False); br.record(False)
    assert br.state is State.CLOSED


def test_half_open_failure_reopens() -> None:
    clk = FakeClock()
    br = CircuitBreaker(clk, window=4, min_calls=4, threshold=0.5, open_for=10, half_open_calls=1)
    for _ in range(4):
        br.acquire(); br.record(True)
    clk.t += 10
    br.acquire(); br.record(True)
    assert br.state is State.OPEN and br.opened_at == 10


def test_fallback_and_context_routing() -> None:
    clk = FakeClock()
    small = mk(clk, "small", [], min_calls=1, threshold=1.0)
    small.max_context = 8_000
    primary = mk(clk, "primary", [ProviderError(503)] * 3, min_calls=1, threshold=1.0)
    backup = mk(clk, "backup", ["from backup", "again"])
    c = ResilientClient([small, primary, backup], clk, RetryPolicy(rng=random.Random(2)))
    assert c.complete({"tokens": 50_000}) == "from backup"
    assert c.log[0] == "small: skip, context too small"
    assert primary.breaker.state is State.OPEN             # opened by the first failure
    assert c.complete({"tokens": 50_000}) == "again"       # primary skipped fast
    assert "primary: circuit open" in c.log


def test_retry_budget_caps_amplification() -> None:

def test_stream_commit_point() -> None:
    clk = FakeClock()

    def broken_after_two(req, timeout, key):
        yield "Hel"
        yield "lo"

        yield  # pragma: no cover

def test_breaker_thread_safety() -> None:
    clk = FakeClock()
    br = CircuitBreaker(clk, window=1000, min_calls=10**9)
    def worker():
        for i in range(2_000):
            br.acquire(); br.record(i % 3 == 0)
    ts = [threading.Thread(target=worker) for _ in range(8)]
    for t in ts: t.start()
    for t in ts: t.join()
    assert len(br.outcomes) == 1000 and br.state is State.CLOSED

13 · Edge cases

Retry-After in HTTP-date form rather than seconds: parse both. Retry-After longer than the deadline: fail or fall back now. Negative or zero deadlines: fail before calling. Late results: a call that started before the breaker opened may finish after; the breaker ignores outcomes recorded while open. All providers' breakers open: fail fast with a clear error rather than looping. SDK retries underneath: Anthropic's SDK retries transient failures twice by default, honouring retry-after; with your own three attempts on top, one request can become nine calls, so set the SDK's max_retries to zero when you own the policy. Cancellation: if the caller abandons the request (the user closed the tab), stop retrying. Exceptions that are not provider errors, such as a bug raising TypeError: let them propagate; do not retry your own bugs.

14 · Extensions the interviewer will ask for

Hedged requests: if the first attempt has not answered by the 95th-percentile latency, send a second copy to another replica and take whichever answers first; it cuts tail latency at a few percent extra cost, and only suits idempotent requests. Slow-call detection: count calls slower than a threshold as failures, as resilience4j's slow-call rate does, so a provider that answers every call in 60 seconds also trips the breaker. Per-model breakers: key breakers by provider and model, since one overloaded model should not cut off another. Async: the same design with asyncio.sleep and asyncio.wait_for, and an asyncio.Lock. Metrics: emit attempts, retries, budget exhaustion, breaker transitions and which fallback tier served each request. Cost limits: refuse to retry a request whose accumulated cost already exceeds a ceiling.

15 · Complexity

Each attempt does O(1) work in the client besides the call itself: a classification, a budget update, and a breaker update that appends to a bounded deque and sums at most N booleans (O(N) as written; keep a running failure count to make it O(1), as resilience4j's subtract-on-evict window does). Total attempts per request are bounded by providers × max_attempts, and globally by the retry budget. Memory is O(window) per breaker and O(1) for the budget.

The arithmetic of retry amplification

With failure probability p per attempt and up to A attempts, the expected attempts per request are 1 + p + p² + ... + pA-1. At p = 0.4 and A = 3 that is 1.56; at p = 0.9 it is 2.71; at p = 1 it is A. The amplification is worst exactly when the provider is most broken. Layering makes it multiplicative: if an API gateway retries three times, your service retries three times and the SDK retries three times, a single user action can produce 27 calls to a dead backend. The Google SRE book's chapter on cascading failures describes this pattern and recommends retrying at only one layer, a per-request cap, and a server-wide retry budget; its overload chapter gives the per-client 10 percent ratio. The retry budget is the only mechanism whose cost stays flat as p rises toward 1, which is why it is the strongest single answer to "how do you stop retries making outages worse?".

Full, equal and decorrelated jitter

AWS's architecture blog compared three jitter strategies in simulation with many competing clients. Full jitter sleeps a uniform random time between 0 and the exponential backoff. Equal jitter keeps half the backoff and randomises the other half, preventing very short sleeps. Decorrelated jitter grows the maximum based on the previous random sleep. Their conclusion: equal jitter was the loser, doing slightly more work and taking much longer; between full and decorrelated the choice is less clear, with full jitter using less work but slightly more time. All of them substantially reduce work compared with un-jittered backoff. The interview-ready summary: use full jitter by default, know that the alternatives exist, and know that the big win is having jitter at all.

How production breakers keep the window cheap

Resilience4j offers a count-based window (the last N calls) and a time-based window (the calls in the last N seconds). Its count-based window is a circular array of N measurements with a running total: when a new outcome arrives, the oldest is subtracted from the total and replaced, so reading the failure rate is O(1) regardless of window size. The time-based window keeps N per-second buckets with partial aggregates and does the same subtract-on-evict per bucket, which keeps memory bounded even at very high call rates. Its defaults are worth knowing as a reference point: open at a 50 percent failure rate, a window of 100 calls, a minimum of 100 calls before the rate is computed, a 60-second wait in the open state, and 10 permitted calls in half-open. It also has a slow-call threshold (a call slower than 60 seconds by default counts as slow) and special states for disabling the breaker or forcing it open, which are the operational kill switches.

Choosing thresholds

The threshold, window and wait trade false alarms against reaction time. A small window and low minimum react fast but trip on noise at low traffic; a large window is stable but slow to notice a sudden outage. A short open period probes often, adding load to a recovering service; a long one keeps users on the fallback longer than necessary. Set them from data: the provider's normal error rate (a threshold well above it), your traffic volume (a window that fills in seconds, not minutes), and the provider's typical incident shape. For low-traffic clients, a time-based window with a sensible minimum avoids the "two calls, one failed, 50 percent" problem.

Fallback quality is a product decision

Falling back from a large model to a smaller one keeps the service up but changes the answers. The fallback must be evaluated on the same test set as the primary, its prompts may need adapting, and the product may need to say that responses are degraded. Watch the share of traffic served by each tier: if the primary's breaker is quietly open for hours, users are getting the cheaper model and nobody may notice except through slowly worse feedback. A fallback that is never exercised also rots: exercise it regularly, for example with a small share of live traffic or scheduled tests, so it works on the day it is needed.

Bulkheads: containing the blast radius

A ship's hull is divided into watertight compartments, bulkheads, so one breach floods one compartment rather than the whole ship. In software a bulkhead is a separate, bounded pool of resources (threads, connections, or an asyncio semaphore) reserved for one dependency. If model calls may use at most 32 concurrent slots, then even when the provider hangs and every call waits for its full timeout, only those 32 slots are stuck and the rest of the service (health checks, database reads, other features) keeps working. The breaker reacts after failures accumulate; the bulkhead limits the damage before the breaker has enough data to open. A request that cannot get a slot can fail fast, queue briefly, or go straight to a fallback. Combined with deadlines, bulkheads are what turn "the model provider is slow" from an outage into a degraded feature.

Retries and the rest of the stack

The client is one layer among several. Load balancers retry connection failures; API gateways may retry; SDKs retry; application code retries. Decide which layer owns the policy and turn the others off or down. Propagate the deadline downstream (many RPC systems send it as a header) so that a server can stop working on a request whose caller has already given up. And make sure the provider can deduplicate: an idempotency key is useless if the server ignores it.

How these clients fail in production

The most common failure is the one this lesson opened with: retry storms. Signs are request rates to the provider rising while the user-facing request rate is flat, and error rates climbing together across all instances. The fixes are the budget, jitter and the breaker, and the evidence that they work is a dashboard showing attempts per logical request staying near 1.0 to 1.1 during an incident.

The second is thread or connection exhaustion. Model calls are slow, so a web server with 64 worker threads can have all 64 waiting on a slow provider, and then nothing else, including health checks, gets served. Deadlines, an open breaker failing fast, and bulkheads (a separate, bounded pool of workers or connections for model calls, so they cannot starve everything else) prevent it.

The third is flapping: the breaker opens, the wait ends, all traffic rushes in, the provider fails again, the breaker opens. Limited half-open probes, a gradual ramp after closing and jittered open durations across instances calm it.

The fourth is silent fallback: the breaker for the primary model stays open for hours because of a misconfigured threshold or an expired key returning 401s that are wrongly counted as failures, and all users get the fallback. Alert on time spent open and on the share of traffic served by each tier.

What to measure

Per provider and model: attempts, successes, failures by class (rate limit, overload, server, timeout, client error), latency percentiles including time to first token, breaker state and transitions, retry budget level and how often it is exhausted, and fallback tier per request. Per logical request: total attempts and total latency, so you can see amplification and deadline misses. Log the provider's request id with every failure; Anthropic's API, for example, returns a request-id header on every response for support investigations.

Knobs

Attempt cap (usually 2 or 3 including the first), backoff base and cap, retry budget ratio (10 percent is the published Google figure), breaker threshold, window, minimum calls, open duration and half-open probes, per-attempt timeout, time-to-first-token and idle timeouts for streams, and the fallback order. Keep them in configuration, per provider, changeable without a deploy, and put each mechanism behind a switch so an operator can disable a misbehaving breaker during an incident.

The real case: resilience4j and Google's retry budgets

Resilience4j, a widely used Java fault-tolerance library, documents its circuit breaker as a finite state machine with three normal states, CLOSED, OPEN and HALF_OPEN, plus three special ones, METRICS_ONLY, DISABLED and FORCED_OPEN. It aggregates call outcomes in either a count-based sliding window (the last N calls) or a time-based one (the last N seconds), opens when the failure rate or the slow-call rate reaches its threshold, and will not compute a rate until a minimum number of calls has been recorded; its documentation gives the example that with a minimum of 10, nine failures out of nine calls will not open the breaker. Its defaults are a 50 percent failure-rate threshold, a 100-call window, a minimum of 100 calls, 60 seconds in the open state and 10 permitted calls when half-open. Google's SRE book supplies the retry side: in its chapter on handling overload it describes a per-request retry budget of up to three attempts and a per-client budget that allows retries only while they are below 10 percent of requests, explaining that if a request has already failed three times the whole datacentre is probably overloaded and retrying will not help. The interview solution in this lesson is a direct, small-scale implementation of both documents, and the drill's arithmetic shows why each exists.

Goal: run the full solution, then break it, measure it and extend it. Python 3.12, standard library only.

  1. Save the full solution as resilient.py and run it. Ten tests print ok instantly, although they simulate many minutes of backoff, because the fake clock's sleep only advances a number.
  2. Measure amplification. In a short script, send 1,000 requests at a provider that always fails, with and without a retry budget (pass RetryBudget(ratio=1e9, cap=1e9) for "no budget"). You should see about 1,109 attempts with the budget and 3,000 without.
  3. Break the breaker. Replace the sliding-window rule in record with a consecutive-failure counter that opens after 5. Run the 40 percent pattern from the breaker test for 1,000 calls with a seeded random generator and count how often it opens compared with the window version.
  4. Break idempotency. Move idem_key = ... inside the attempt loop and watch the first test fail: three attempts now carry three different keys.
  5. Extend it. Add a slow-call rule: if a call takes longer than a threshold (measure with the clock before and after), record it as a failure. Write a test with a fake provider that advances the fake clock by 90 seconds per call.
  6. Extend it again. Add hedging: if the first attempt has not returned within a threshold, start a second attempt on the next provider in a thread and return whichever finishes first.

Each exercise is judged the same way: by a test with a scripted provider and the fake clock, never by calling a real API.

Work it out

Your service makes 500 LLM calls per second. The provider starts returning 503 for 40 percent of requests. Your client tries each request up to four times (one call plus three retries) with exponential backoff of 1, 2 and 4 seconds and no jitter, and the circuit breaker opens after 5 consecutive failures.

(a) What load does the provider now see? (b) Does the breaker open? (c) What do you change?

Answer

(a) Load amplification. Of 500 first attempts, 200 fail and retry; of those, 40 percent fail again, so 80 second retries; then 32 third retries. Total = 500 + 200 + 80 + 32 = 812 requests per second, 1.62 times normal. And because there is no jitter, the retries arrive in synchronised waves 1, 3 and 7 seconds after each failure burst, so the instantaneous peaks are far worse than the average. A provider failing 40 percent of requests has been handed 60 percent more work, in bursts. That is how a partial degradation becomes a full outage.

(b) Does the breaker open? Almost certainly not, and this is the important part. With independent 40 percent failures, the chance that five given calls in a row all fail is 0.45, about 1 percent, and every success resets the counter. A consecutive-failure breaker can sit closed through a sustained 40 percent error rate, precisely the situation it was installed for. It passes code review and does nothing in production.

(c) The changes, in order of impact:

  • A failure-rate breaker over a sliding window with a minimum number of calls, opening at, say, 25 to 50 percent. This alone makes the breaker work here.
  • A retry budget of about 10 percent of requests. Amplification falls from 1.62 to at most about 1.1, and it self-limits as things get worse instead of growing.
  • Full jitter, so retries spread across each backoff interval instead of arriving as waves. Same average, far lower peaks.
  • Fewer attempts. Only 6.4 percent of requests (0.43) reach the fourth attempt; dropping to three attempts in total removes the least useful retries.
  • Obey Retry-After when the provider sends it, and fall back to another provider once the breaker opens, so users still get answers.

The lesson to say aloud: retries handle independent, transient failures; the breaker and the budget handle correlated, sustained ones. Without the second pair, the first makes outages worse.
