A team serves an embedding model behind an HTTP endpoint. Each request carries one sentence; the server runs the model on it and returns a vector. On a modern GPU one call takes about 10 milliseconds whether it embeds one sentence or thirty-two, because most of the time goes into reading the model's weights from memory, and that cost is paid once per call however many inputs ride along. At 50 requests per second the server keeps up. At 300 it does not: the GPU is "busy" every millisecond, but almost all of that is the same weights being read over and over for one sentence at a time. Throughput is capped at about 100 calls per second, and the queue grows.

The fix is batching: hold incoming requests for a moment, run them through the model together, and hand each caller its own slice of the output. Thirty-two sentences per 10-millisecond call is 3,200 per second from the same GPU. Every serious model server does this, from NVIDIA's Triton, which calls it dynamic batching, to LLM servers such as vLLM, which take it further with continuous batching.

Batching introduces its own problems, and they are concurrency problems. Callers arrive independently and each must get back exactly its own result. The first request into an empty batch must not wait forever for companions that never come, nor should a steady trickle keep postponing it. When load exceeds what the device can do, the queue must not grow without limit. A caller who gives up should not have its request computed anyway. One malformed input must not fail thirty-one others. And during a deploy, the server must finish what it accepted without taking more.

Getting batching right is also a cost question. GPUs are expensive, and a server that batches poorly needs several times as many of them for the same traffic, so the difference between a naive and a careful batcher shows up directly in the infrastructure bill.

That makes this a classic machine-coding round for AI infrastructure roles. There is no model to write: the "model" is a function that takes a list and returns a list. Everything interesting is in the queue, the timer, the futures, the error paths and the arithmetic that says whether the design can keep up.

This lesson follows the round: the questions to ask, the entities, a naive version and its bugs, then the correct batcher built in stages (futures, dual triggers keyed to the oldest request, bounded queue, deadlines and cancellation, overlapping batches, poison isolation, shutdown), the full tested solution with a discrete-event simulator, edge cases, the extensions an interviewer will ask for (length bucketing, priorities, continuous batching), complexity, and how Triton's dynamic batcher configures the same ideas.

Why batching helps

A neural network forward pass multiplies inputs by large weight matrices. For small batches, the bottleneck is not arithmetic but memory bandwidth: the weights must stream from the GPU's memory into its compute units for every call. Reading 1 GB of weights takes the same time whether the input is one row or thirty-two, and the arithmetic for thirty-two rows still fits in that time. So up to a point, batch time is nearly flat in batch size, and throughput grows almost linearly with it. Beyond that point the GPU becomes compute-bound and batch time starts to grow. The lesson treats batch time as fixed, which is accurate for the region where batching pays.

The shape of the solution

Callers do not see batches. A caller calls await batcher.submit(item) and gets back its result. Inside, submit creates a future, an object representing a result that does not exist yet, puts the item and the future in a queue, and awaits the future. A single background loop, the assembler, takes items off the queue and groups them into a batch, calls the model with the list of items, and then sets each future's result from the corresponding position in the returned list. Each awaiting caller wakes with its own answer. That is the whole mechanism; the rest of the lesson is about getting its timing and failure behaviour right.

Futures, more concretely

A future has three possible states: pending, done with a result, or done with an exception (cancellation is a special exception). Exactly one party resolves it, exactly once; any number of parties can await it. Awaiting a pending future suspends the awaiting coroutine without blocking the thread, so thousands of callers can wait at once at almost no cost. That property is what lets one assembler and a handful of execution tasks serve thousands of concurrent callers on a single thread. The cost of the pattern is discipline: every future the batcher creates must be resolved on every path, including errors, shutdown and timeouts, or its caller waits forever.

The analogy: a shuttle bus

An airport shuttle seats 32. If the driver leaves only when the bus is full, the first passenger at 3 a.m. waits for hours. If the driver leaves on a fixed schedule regardless of passengers, buses run nearly empty at night and passengers queue at the kerb during the rush. A sensible rule is both: leave when full, or when the first passenger on board has waited ten minutes, whichever comes first. Note the "first passenger": if the timer restarted whenever someone new boarded, a steady trickle of passengers would keep the bus parked forever. The analogy breaks in a useful place. At rush hour, a bus returning from the terminal finds a crowd already waiting, so it fills instantly and the ten-minute rule never matters. That is exactly what happens in a loaded batcher: requests pile up while the previous batch runs, and the timer only matters at low traffic.

Capacity is arithmetic

One more idea frames everything. If a batch of up to B items takes S seconds and one batch runs at a time, the server can complete at most B / S requests per second: 32 / 0.04 = 800 per second for a 40 ms call. If requests arrive faster than that, the queue grows forever, whatever the triggers are. Batching raises this ceiling; it does not remove it. Little's law adds the other half: in a stable system the average number of requests inside equals the arrival rate times the average time each spends inside. At 2,000 requests per second and 50 ms per request, about 100 requests are in the system at any moment. Those two facts let you size queues and replicas before writing code, and the drill uses both.

1 · Clarify the requirements

Ask about the model call: does it take a list and return a list in the same order, how long does it take as a function of batch size, what is the largest batch it accepts, and can it report per-item errors? Ask about traffic: requests per second, burstiness, and whether inputs vary in size (token length, image size). Ask about latency: the target for typical and tail requests, and whether callers have their own timeouts. Ask about overload: should excess requests be rejected or queued, and how long may a queue wait be? And about operations: does the server need graceful shutdown for deploys, and are there priorities?

A typical agreed scope: an async submit returning the caller's own result; batches of at most B items; no request waits more than T for companions; a bounded queue that rejects immediately when full; per-request deadlines; cancelled requests not computed; a failing item must not fail others; graceful shutdown. Non-functional requirements to state: never lose a request silently (every future resolved), and know the maximum sustainable throughput before deploying.

2 · Entities and responsibilities

A request record holds the item, its future, when it was enqueued and its deadline. The Batcher owns the bounded queue, the assembler loop, a semaphore limiting in-flight batches, the set of running batch tasks and simple statistics. The batch function is injected: an async callable from a list of items to a list of results (or exception objects) in the same order. Two exception types carry the policy outcomes: Overloaded when the queue is full or the batcher is shutting down, and Expired when a request's deadline passed in the queue.

3 · Stage one: a naive batcher and its bugs

async def loop(self):
    while True:
        batch = []
        deadline = time.monotonic() + self.max_wait          # bug 1: timer from now, not oldest
        while len(batch) < self.max_batch and time.monotonic() < deadline:
            try:
                batch.append(self.q.get_nowait())
            except asyncio.QueueEmpty:
                await asyncio.sleep(0.001)                    # bug 2: busy polling
        if batch:
            results = await self.fn([i for i, f in batch])    # bug 3: blocks the next assembly
            for (i, f), r in zip(batch, results):             # bug 4: exception fails everyone,
                f.set_result(r)                               #        futures left unresolved

Walk through what goes wrong. The timer starts when the loop wakes, not when the oldest request arrived, so a request that arrived just after a flush waits a full extra window. The loop polls every millisecond even when the server is idle, burning CPU. It awaits the model call before collecting the next batch, so assembly and execution never overlap and the device sits idle between batches. If fn raises, the exception escapes the loop, the loop dies, and every queued future is never resolved: every caller hangs until its own timeout, and every future caller hangs too. And with an unbounded asyncio.Queue(), overload means unbounded memory and latency. Each of these is fixed by one stage below.

4 · Stage two: futures and a blocking first get

submit creates the future with loop.create_future(), wraps the item, the future, the current monotonic time and the deadline into a record, and puts it on the queue. The assembler starts each batch with await self.q.get(), which sleeps until there is work: no polling, no CPU when idle, and the batch clock starts from a real request. A detail worth knowing: when a caller's await req.fut is cancelled (for example because the HTTP client disconnected), asyncio cancels the future itself, so the assembler can detect abandoned requests with fut.done().

5 · Stage three: the dual trigger, keyed to the oldest

After taking the first request, the assembler computes flush_at = first.enqueued + max_wait: the oldest request's arrival plus the maximum delay. It then keeps adding requests until the batch is full or flush_at passes. Each additional request is taken in one of two ways. If one is already waiting in the queue, take it immediately with get_nowait(). Only if the queue is empty, wait for the next arrival with asyncio.wait_for(self.q.get(), flush_at - now), which either returns the next request or raises TimeoutError when the oldest request's time is up.

The order of those two checks matters, and the full solution's own first draft got it wrong. That draft checked the deadline first and stopped as soon as flush_at had passed. Under backlog, the oldest queued request has always waited longer than max_wait by the time the assembler reaches it, so every batch was flushed with a single item. The throughput test caught it: batch sizes went 16, 16, 1, 1, 1, ... and 210 of 320 requests expired. The fix is the rule above: anything already queued is free to take, so take it, and consult the deadline only when deciding whether to wait for more. This is a good story to tell in an interview, because it shows the test caught a bug that reading the code did not.

6 · Stage four: a bounded queue, deadlines and cancellation

The queue is created with maxsize, and submit uses put_nowait, which raises QueueFull instead of waiting. The batcher converts that into Overloaded, which an HTTP layer maps to status 503 with a Retry-After header. Rejecting in a microsecond is better for the caller than accepting and answering in ninety seconds, and far better for the server, which otherwise spends its device time on requests whose callers have gone.

Each request carries a deadline, from a timeout argument. When the assembler takes a request, it checks two things: if the future is already done, the caller cancelled, so the request is dropped; if the deadline has passed, the future gets an Expired exception and the request is dropped. The executor checks fut.done() once more just before calling the model, catching cancellations that happened while the batch was assembling. Under overload, this is what stops the server from entering a state where it only ever computes answers nobody is waiting for.

7 · Stage five: overlapping batches with a semaphore

Instead of awaiting the model call, the assembler acquires a slot from asyncio.Semaphore(max_inflight), starts the batch as a separate task, and immediately begins assembling the next batch. The task releases the slot when it finishes, in a finally block so that a failure cannot leak a slot. With max_inflight = 1 assembly still overlaps execution; with 2 or 3, several batches can be on the device at once if it has headroom, or spread across replicas. When all slots are taken the assembler waits at acquire, stops draining the queue, the queue fills, and submit starts rejecting: backpressure flows from the device to the callers with no extra code.

8 · Stage six: per-item errors and poison isolation

The batch function may return an exception object in a result position, meaning that item failed; the executor sets that future's exception and the others' results. If the whole call raises, the executor does not fail everyone. It splits the batch in half and calls each half separately, recursively, until a failing half has one item, whose future gets the exception. Every other item succeeds. With one poison item in a batch of 8, that is the original call plus up to six more (two per level for three levels), as the test checks. The executor also verifies that the function returned as many results as items, because a length mismatch would silently give callers each other's answers, the worst bug a batcher can have.

9 · Stage seven: graceful shutdown

close() sets a flag so new submit calls raise Overloaded, puts a None sentinel on the queue, waits for the assembler to flush whatever was queued before the sentinel and exit, then waits for all in-flight batch tasks. Anything still in the queue afterwards gets an explicit error. The test submits ten requests, closes immediately, and checks that all ten completed and that a later submit is refused.

10 · Testing concurrent code without flakiness

Asynchronous code with timers is easy to test badly: assertions on exact timings fail on a busy machine, and tests that only check happy paths miss the hanging-future bugs that matter. The tests here follow three rules. First, assert on structure where possible: the batch sizes recorded in stats.batches, which items reached the model (the fake model records each list it receives), which futures hold which exceptions. Second, when timing is the property, assert generous bounds: the lone request must wait at least most of max_wait and well under ten times it, which holds even with Windows' coarse timer. Third, measure completion time with a done callback rather than after an await placed later in the test; the first version of the oldest-deadline test awaited the first request only after submitting all the others, and so measured the test's own loop instead of the batcher. Above all, use the injected batch function: a fake model that sleeps, records its inputs and can be told to fail on a particular item makes every failure path reproducible in milliseconds. For capacity questions, the discrete-event simulator replaces real time entirely, so a 30-second run at 2,000 requests per second takes a fraction of a second and gives the same answer every time.

11 · The full solution

The file below contains the batcher, a discrete-event simulator of the same policy, eight asyncio tests and a simulated version of the drill. Python 3.12, standard library only; the asyncio tests take a few seconds of real time because they use real sleeps of tens of milliseconds, with tolerances loose enough for Windows timer resolution.

"""A dynamic-batching inference queue (asyncio): size and time triggers keyed to the OLDEST
request, a bounded queue that rejects fast, per-request deadlines, cancellation, overlapping
batches, poison-item isolation and graceful shutdown. Plus a discrete-event simulator for
sizing. Python 3.12, standard library only. Run: python batcher.py"""
from __future__ import annotations

import asyncio
import heapq
import random
import time
from dataclasses import dataclass, field
from typing import Any, Awaitable, Callable

BatchFn = Callable[[list[Any]], Awaitable[list[Any]]]   # results (or Exception objects) in order


class Overloaded(Exception):
    """Queue full: reject now (HTTP 503 + Retry-After) instead of queueing work nobody will wait for."""


class Expired(Exception):
    """The request's own deadline passed while it waited in the queue."""


@dataclass
class _Req:
    item: Any
    fut: asyncio.Future
    enqueued: float
    deadline: float


@dataclass
class Stats:
    batches: list[int] = field(default_factory=list)
    rejected: int = 0
    expired: int = 0


class Batcher:
    def __init__(self, fn: BatchFn, max_batch: int = 32, max_wait: float = 0.02,
                 max_queue: int = 1_000, max_inflight: int = 2) -> None:
        self.fn, self.max_batch, self.max_wait = fn, max_batch, max_wait
        self.q: asyncio.Queue[_Req] = asyncio.Queue(maxsize=max_queue)
        self.slots = asyncio.Semaphore(max_inflight)    # batches allowed on the device at once
        self.stats = Stats()
        self._closing = False
        self._inflight: set[asyncio.Task] = set()
        self._loop_task = asyncio.create_task(self._run())

    async def submit(self, item: Any, timeout: float = 5.0) -> Any:
        if self._closing:
            raise Overloaded("shutting down")
        now = time.monotonic()
        req = _Req(item, asyncio.get_running_loop().create_future(), now, now + timeout)
        try:
            self.q.put_nowait(req)                       # never block the caller on a full queue
        except asyncio.QueueFull:
            self.stats.rejected += 1
            raise Overloaded("queue full") from None
        return await req.fut                             # cancelling this cancels req.fut too

    def _usable(self, r: _Req, now: float) -> bool:
        if r.fut.done():                                 # caller gave up (cancelled)
            return False
        if now >= r.deadline:
            self.stats.expired += 1
            r.fut.set_exception(Expired())
            return False
        return True

    async def _run(self) -> None:
        while True:
            first = await self.q.get()                   # sleep until there is work
            if first is None:
                break
            if not self._usable(first, time.monotonic()):
                continue
            batch = [first]
            flush_at = first.enqueued + self.max_wait    # the OLDEST request sets the clock
            stop = False
            while len(batch) < self.max_batch:
                try:
                    r = self.q.get_nowait()              # already waiting: always take it
                except asyncio.QueueEmpty:
                    left = flush_at - time.monotonic()
                    if left <= 0:
                        break                            # oldest is due and nothing else is queued
                    try:
                        r = await asyncio.wait_for(self.q.get(), left)
                    except TimeoutError:
                        break
                if r is None:
                    stop = True
                    break
                if self._usable(r, time.monotonic()):
                    batch.append(r)
            await self.slots.acquire()                   # backpressure from the device
            t = asyncio.create_task(self._execute(batch))
            self._inflight.add(t)
            t.add_done_callback(self._inflight.discard)
            if stop:
                break

    async def _execute(self, batch: list[_Req]) -> None:
        try:
            live = [r for r in batch if not r.fut.done()]
            if live:
                self.stats.batches.append(len(live))
                await self._call(live)
        finally:
            self.slots.release()

    async def _call(self, reqs: list[_Req]) -> None:
        """Run the batch; if the whole call fails, bisect to isolate the poison item(s)."""
        try:
            results = await self.fn([r.item for r in reqs])
            if len(results) != len(reqs):
                raise RuntimeError(f"batch fn returned {len(results)} results for {len(reqs)} items")
        except Exception as e:
            if len(reqs) == 1:
                if not reqs[0].fut.done():
                    reqs[0].fut.set_exception(e)
                return
            mid = len(reqs) // 2
            await self._call(reqs[:mid])
            await self._call(reqs[mid:])
            return
        for r, res in zip(reqs, results):                # every future resolved on every path
            if r.fut.done():
                continue
            if isinstance(res, Exception):
                r.fut.set_exception(res)
            else:
                r.fut.set_result(res)

    async def close(self) -> None:
        """Stop accepting, flush what is queued, wait for in-flight batches."""
        self._closing = True
        await self.q.put(None)                           # sentinel: assemble the last batch, then stop
        await self._loop_task
        if self._inflight:
            await asyncio.gather(*self._inflight)
        while not self.q.empty():                        # anything still queued after the sentinel
            r = self.q.get_nowait()
            if r is not None and not r.fut.done():
                r.fut.set_exception(Overloaded("shut down"))


# ---------------------------------------------------------------- discrete-event simulator
def simulate(rate: float, max_batch: int, max_wait: float, service: float,
             inflight: int = 1, seconds: float = 30.0, seed: int = 1) -> dict[str, float]:
    """Poisson arrivals into the same policy; returns mean batch size, mean latency, throughput."""
    rng = random.Random(seed)
    t, arrivals = 0.0, []
    while t < seconds:
        t += rng.expovariate(rate)
        arrivals.append(t)
    free = [0.0] * inflight                               # when each device slot frees up
    i, sizes, lat, done_at = 0, [], [], 0.0
    while i < len(arrivals):
        slot_free = heapq.heappop(free)
        oldest = arrivals[i]
        start = max(oldest, slot_free)
        # flush when full or when the oldest has waited max_wait, but never before a slot frees
        j = i
        while j < len(arrivals) and j - i < max_batch and arrivals[j] <= max(start, oldest + max_wait):
            j += 1
        if j - i == max_batch:
            flush = max(slot_free, arrivals[j - 1])
        else:
            flush = max(slot_free, oldest + max_wait)
            while j < len(arrivals) and j - i < max_batch and arrivals[j] <= flush:
                j += 1
        end = flush + service
        sizes.append(j - i)
        lat += [end - a for a in arrivals[i:j]]
        heapq.heappush(free, end)
        done_at = max(done_at, end)
        i = j
    return {"mean_batch": sum(sizes) / len(sizes), "mean_latency_ms": 1000 * sum(lat) / len(lat),
            "p99_latency_ms": 1000 * sorted(lat)[int(0.99 * len(lat))],
            "throughput": len(arrivals) / done_at}


# ---------------------------------------------------------------- tests
def fake_model(delay: float, seen: list | None = None, poison: str | None = None) -> BatchFn:
    async def fn(items: list[Any]) -> list[Any]:
        if seen is not None:
            seen.append(list(items))
        if poison is not None and poison in items:
            raise ValueError("bad input in batch")
        await asyncio.sleep(delay)
        return [f"out:{x}" for x in items]
    return fn


async def test_size_trigger() -> None:
    b = Batcher(fake_model(0.01), max_batch=8, max_wait=1.0)
    t0 = time.monotonic()
    out = await asyncio.gather(*(b.submit(i) for i in range(8)))
    assert out == [f"out:{i}" for i in range(8)] and b.stats.batches == [8]
    assert time.monotonic() - t0 < 0.5                   # did not wait for the 1 s timer
    await b.close()


async def test_time_trigger_lone_request() -> None:
    b = Batcher(fake_model(0.0), max_batch=32, max_wait=0.05)
    t0 = time.monotonic()
    assert await b.submit("x") == "out:x"
    waited = time.monotonic() - t0
    assert 0.04 <= waited < 0.3 and b.stats.batches == [1], waited
    await b.close()


async def test_deadline_belongs_to_oldest() -> None:
    b = Batcher(fake_model(0.0), max_batch=100, max_wait=0.06)
    t0 = time.monotonic()
    first = asyncio.create_task(b.submit("first"))
    done_at: list[float] = []
    first.add_done_callback(lambda _: done_at.append(time.monotonic()))
    others = []
    for k in range(10):                                  # a trickle that never fills the batch
        await asyncio.sleep(0.02)
        others.append(asyncio.create_task(b.submit(k)))
    await first
    waited = done_at[0] - t0
    assert waited < 0.15, waited                         # bounded by max_wait, not by the trickle
    await asyncio.gather(*others)
    await b.close()


async def test_bounded_queue_rejects_fast() -> None:
    b = Batcher(fake_model(0.2), max_batch=4, max_wait=0.0, max_queue=8, max_inflight=1)
    tasks = [asyncio.create_task(b.submit(i)) for i in range(40)]
    res = await asyncio.gather(*tasks, return_exceptions=True)
    rejected = sum(isinstance(r, Overloaded) for r in res)
    assert rejected > 0 and b.stats.rejected == rejected
    assert all(r == f"out:{i}" for i, r in enumerate(res) if not isinstance(r, Exception))
    await b.close()


async def test_poison_item_isolated() -> None:
    seen: list = []
    b = Batcher(fake_model(0.0, seen, poison="bad"), max_batch=8, max_wait=0.5)
    res = await asyncio.gather(*(b.submit(x) for x in ["a", "b", "bad", "c", "d", "e", "f", "g"]),
                               return_exceptions=True)
    assert isinstance(res[2], ValueError)
    assert [r for k, r in enumerate(res) if k != 2] == [f"out:{x}" for x in "abcdefg"]
    assert len(seen) <= 1 + 2 * 3                         # bisection: O(log n) extra calls per poison
    await b.close()


async def test_cancelled_and_expired_are_skipped() -> None:
    seen: list = []
    b = Batcher(fake_model(0.0, seen), max_batch=8, max_wait=0.1)
    gone = asyncio.create_task(b.submit("gone"))
    stale = asyncio.create_task(b.submit("stale", timeout=0.0))
    live = asyncio.create_task(b.submit("live"))
    await asyncio.sleep(0)
    gone.cancel()
    assert await live == "out:live"
    try:
        await stale
    except Expired:
        pass
    assert all("gone" not in s and "stale" not in s for s in seen) and b.stats.expired == 1
    await b.close()


async def test_overlap_raises_throughput() -> None:
    async def run(inflight: int) -> float:
        b = Batcher(fake_model(0.05), max_batch=16, max_wait=0.01, max_inflight=inflight)
        t0 = time.monotonic()
        await asyncio.gather(*(b.submit(i) for i in range(320)))
        await b.close()
        return 320 / (time.monotonic() - t0)
    one, three = await run(1), await run(3)
    print(f"    throughput with 1 batch in flight {one:.0f}/s, with 3 {three:.0f}/s")
    assert three > 1.8 * one


async def test_graceful_close_drains() -> None:
    b = Batcher(fake_model(0.02), max_batch=4, max_wait=0.05)
    tasks = [asyncio.create_task(b.submit(i)) for i in range(10)]
    await asyncio.sleep(0)
    await b.close()
    assert [t.result() for t in tasks] == [f"out:{i}" for i in range(10)]

        pass


def test_simulated_drill() -> None:
    for rate in (100, 2_000):
        for inflight in (1, 2):
            s = simulate(rate, max_batch=32, max_wait=0.02, service=0.04, inflight=inflight)
            print(f"    {rate:>5}/s inflight={inflight}: batch {s['mean_batch']:.1f}, "
                  f"mean {s['mean_latency_ms']:.0f} ms, p99 {s['p99_latency_ms']:.0f} ms, "

12 · Sizing it: what the simulator says

The simulator replays Poisson arrivals through the same policy in simulated time, with a 40 ms model call regardless of batch size, a maximum batch of 32 and a 20 ms maximum wait. At 100 requests per second with one slot, mean batch size is about 4.1 and mean latency about 60 ms (p99 about 80 ms): batches are bigger than the 2 requests that arrive in 20 ms, because requests also accumulate while the previous batch runs. At 2,000 requests per second with one slot, capacity is 32 / 0.04 = 800 per second, the queue grows without bound, and mean latency over a 30-second run passes 22 seconds. Two slots give 1,600 per second, still short. Three slots give 2,400 per second of capacity, and latency settles at about 48 ms mean and 59 ms p99 with full batches. That is the conversation the interviewer wants: the triggers set latency at low load, and only capacity, measured as batch size over batch time per slot, decides whether high load is survivable.

13 · Edge cases

max_wait of zero: the batcher still batches whatever is already queued, which is Triton's default behaviour. A batch function that returns the wrong number of results: treated as a failure, never zipped silently. A request whose timeout is zero: expires at dequeue. Cancellation during execution: the result is computed but the future is already done, so setting it is skipped. Exceptions thrown by the assembler itself: must not kill the loop silently; in production wrap the loop body and log. Clock: use time.monotonic. Very slow batch function: deadlines expire queued requests, and a per-batch timeout should fail the batch rather than hold a slot forever.

14 · Extensions the interviewer will ask for

Length bucketing: separate queues per input-length range, or sort a window of queued requests by length, so short inputs are not padded to long ones; cap batches by total tokens. Priorities: one queue per level, fill from the highest first, with anti-starvation. Continuous batching for LLM generation: schedule at every decoding step so finished sequences leave and new ones join, as Orca and vLLM do. Multiple models or devices: one batcher per model and device, behind a router. Metrics: batch size histogram, queue depth, wait time, rejections, expirations. Adaptive delay: tune max_wait from observed load, shrinking it when batches fill anyway.

15 · Complexity

Each request costs O(1) work in the batcher: one put, one get, one future resolution. A batch costs O(B) to assemble and resolve. Bisection on failure costs O(log B) extra calls per poison item. Memory is bounded by max_queue plus max_inflight × max_batch requests. Throughput is bounded by max_inflight × max_batch / batch_time, and latency at low load by max_wait + batch_time.

Why a delay often buys nothing

It is tempting to think a longer delay always means bigger batches and more throughput. That is only true when the device would otherwise be idle. Under steady load with one slot, requests pile up in the queue during each 40 ms batch, so the next batch is already sizeable when the slot frees; the oldest waiting request has usually waited longer than any reasonable delay, so the delay is never what decides the flush. The simulator shows it: at 100 requests per second, a 20 ms delay and no delay both give about 60 ms mean latency and batches of about 4. A delay helps in a narrow band: when the device is idle, traffic is moderate, and the model's batch time really is flat, waiting a little lets a few more requests share the next call. Triton's tuning guide reflects this: enable dynamic batching with no delay first, measure, and only then try increasing the delay while latency stays within budget.

Queueing theory in three sentences

Utilisation is arrival rate divided by capacity; as it approaches 1, waiting time grows sharply, roughly in proportion to 1 / (1 - utilisation) for simple queues, which is why a server at 95 percent utilisation has far worse tail latency than one at 70 percent. Little's law (L = λW) turns a latency target into a queue bound: at 2,000 requests per second and an acceptable 100 ms wait, about 200 queued requests is the most that makes sense, and anything beyond is guaranteed to be late. Batching complicates the picture because capacity itself grows with batch size up to the maximum, which is what makes batchers stable over a wide load range and then fall off a cliff at B / S.

Continuous batching for generation

The batcher in this lesson runs each batch to completion, which is right for fixed-cost calls such as embeddings, classifiers or rerankers. Text generation is different: each request produces a different number of tokens, so a static batch is held hostage by its longest member, and requests that finish early leave their slots idle. Orca, published at OSDI 2022, introduced iteration-level scheduling: the server makes a scheduling decision at every decoding step, removing finished sequences and admitting waiting ones, so the batch stays full. vLLM combines this with paged management of the attention key-value cache, so admitting a request depends on free memory rather than a fixed batch size. The front end of such servers still needs everything here: a bounded queue, deadlines, cancellation, priorities and admission control.

Ordering and fairness

A single FIFO queue with one assembler serves requests in arrival order, which is fair and predictable. Overlapping batches break strict ordering of completions (a small later batch can finish before a large earlier one), which is fine for independent requests but matters for streams that expect ordered responses; Triton has a preserve_ordering option for that case. Bisection also reorders work: the items in a failing batch are retried after later batches may have started. When fairness across tenants matters, one FIFO is not enough: a single tenant flooding the queue fills every batch. Per-tenant queues drained round-robin, or a cap on each tenant's share of a batch, restore fairness at the cost of slightly smaller batches.

Padding and length bucketing

Models consume rectangular tensors, so a batch of inputs with lengths 10, 12 and 2,000 is padded to 2,000 each, and the two short inputs cost as much as the long one. For transformer models the attention cost grows with the square of length, so the waste can be worse than linear. Bucketing groups inputs of similar length: separate queues for, say, under 128, under 512 and under 2,048 tokens, each with its own batch cap measured in total tokens and its own timer. The cost is fairness and complexity: a rarely used bucket has small batches, and requests may wait longer for a bucket to fill, which is why each bucket keeps its own oldest-request deadline.

Choosing the maximum batch size

The maximum batch is bounded from above by device memory (activations grow with batch size) and by the shape of the batch-time curve: while the model is memory-bound, batch time is nearly flat and bigger batches are free throughput; once it becomes compute-bound, batch time grows roughly in proportion and bigger batches only add latency. Measure the curve once, batch sizes 1, 2, 4 and so on, and pick the knee. A bigger maximum also raises worst-case latency, because a full batch takes the longest, and raises the cost of a poison item, because bisection has more levels. Triton's advice to avoid preferred batch sizes for most models fits this picture: unless one size is specially optimised, any size up to the knee is fine.

The asyncio details that bite

A few behaviours of asyncio are easy to get wrong. asyncio.wait_for on a queue get either returns an item or raises TimeoutError (an alias of asyncio.TimeoutError since Python 3.11); cancellation of the inner get is handled for you. A task created with create_task and not referenced anywhere can be garbage-collected while running, which is why the batcher keeps in-flight tasks in a set and removes them in a done callback. Exceptions in a task that nobody awaits are only logged when the task is garbage-collected, so the assembler should never let exceptions escape silently. And everything here runs on one thread, so the batcher's own data structures need no locks; the model call must be truly asynchronous (or run in an executor), or it blocks the whole event loop and every caller with it.

How batchers fail in production

The most common failure is running past capacity without noticing. Arrivals creep above batch size over batch time, the queue grows, latency rises for everyone, and the first alert is a flood of client timeouts. The leading indicators are queue depth and queue wait time rising while batch sizes sit at the maximum: the batcher is doing all it can. Fix with more replicas or slots, and in the meantime let the bounded queue shed load rather than letting everything become slow.

The second is hanging callers: a code path that does not resolve a future. A batch function that raises in an unexpected way, a length mismatch handled by zip (which silently truncates), or an assembler that dies on an exception leaves callers waiting until their own timeouts. Count futures created and resolved; the difference should be the number in flight, never growing.

The third is padding waste, visible as GPU utilisation that is high while throughput is low. Mixed input lengths in the same batch spend compute on padding. Bucketing by length, or limiting batches by total tokens, is the fix.

The fourth is head-of-line blocking by slow or huge requests: one enormous input makes its whole batch slow, delaying every small request that shared it. Separate queues by size class, cap input size, and give large requests their own path.

Autoscaling on the right signal

Replicas are the long-term answer to capacity, and autoscaling decides how many to run. Scaling on device utilisation is misleading for batchers: a GPU running batches of one can look 90 percent busy while delivering a fraction of its throughput, and a GPU running full batches looks the same. Better signals are queue depth or time spent queued per request, and the ratio of arrival rate to measured capacity. Scale out before the queue grows, because new replicas take time to start and load a model, often tens of seconds or minutes; during that time the bounded queue and fast rejection are what keep the service usable.

What to measure

Batch size distribution, queue depth and time spent queued, model call time by batch size, end-to-end latency percentiles, rejections and expirations per second, and device utilisation. Two derived numbers matter most: capacity (max batch over measured batch time, times slots) compared with the arrival rate, and the share of requests that expire in the queue, which should be essentially zero in healthy operation.

Knobs

Maximum batch size (bounded by device memory and the batch-time curve), maximum delay, queue bound, per-request timeout, number of in-flight batches or model instances per device, and length buckets. Tune them with a load generator replaying realistic traffic, not single requests: measure throughput and latency at increasing load until latency leaves the budget, as Triton's tuning process describes.

The real case: Triton's dynamic batcher

NVIDIA's Triton Inference Server documents its dynamic batcher with exactly this lesson's knobs. By default, enabling dynamic_batching creates batches as large as possible up to the model's maximum batch size and does not delay to form them. The max_queue_delay_microseconds setting allows a request to be delayed for a limited time so others can join; if a new arrival lets a maximum (or preferred) size batch form during the delay, the batch is sent immediately, and when the delay expires the batch is sent as is. A preferred_batch_size can be set but, the documentation says, should not be for most models, only when a particular size performs significantly better. priority_levels create separate queues so higher-priority requests bypass lower ones, with in-order processing within a level. Queue policies set a max_queue_size and per-request timeouts, with an action to reject or defer requests that wait too long. The recommended tuning process is to start with the defaults, measure latency and throughput with its performance analyser, and only then increase the maximum batch size or add a delay while latency stays within budget. Each of those settings has a counterpart in the hundred-line batcher in this lesson, which is the point of building it: after writing one, the production configuration reads as a list of decisions you already understand.

  2. Break it. In the assembler, restore the first-draft order: check flush_at first and stop if it has passed, before trying get_nowait(). Run the overlap test and print b.stats.batches: batches collapse to size 1 under backlog and requests expire.

Work it out

A batching server has max_batch = 32 and max_wait = 20 ms. The batched model call takes 40 ms regardless of batch size (from 1 to 32 items), and one batch runs at a time. Requests arrive at random (Poisson).

(a) At 100 requests per second, what is the average batch size and latency? (b) At 2,000 per second? (c) What do you change so 2,000 per second is served within about 60 ms at p99?

Answer

(a) 100 per second. The tempting answer is "2 requests arrive in 20 ms, so batches of 2". But requests also arrive during each 40 ms batch: about 4 of them. By the time the device is free, the oldest has usually waited more than 20 ms, so the batcher flushes immediately with whatever has accumulated. The simulator gives a mean batch of about 4.1 and mean latency of about 60 ms (roughly 20 ms queued plus 40 ms on the device), p99 about 80 ms. Capacity is 800 per second, so utilisation is about 12 percent and everything is stable. Setting max_wait to 0 gives about the same numbers, because the queue, not the timer, is forming the batches.

(b) 2,000 per second. 32 requests arrive in 16 ms, so the size trigger fires and every batch is full. But one slot completes at most 32 / 0.04 = 800 requests per second. Arrivals exceed capacity by 1,200 per second, so the queue grows by 1,200 every second, without bound. In a 30-second simulation, mean latency exceeded 22 seconds. No trigger setting can fix this, because batches are already full: this is a capacity problem, not a tuning problem. With a bounded queue, the batcher would instead reject the excess immediately, which at least keeps accepted requests fast.

(c) The fix. Add capacity. Two concurrent slots (or replicas) give 1,600 per second, still short. Three give 2,400, utilisation about 83 percent, and the simulator shows full batches with about 48 ms mean and 59 ms p99. On real hardware, check whether one device really runs three batches concurrently without slowing each (often it does not, and you need three devices or a larger batch with a longer batch time). Keep the bounded queue and deadlines as protection for when traffic exceeds 2,400. Size the queue with Little's law: at 2,000 per second, a 50 ms queueing allowance means about 100 queued requests is the useful maximum.

The lesson to say aloud: triggers decide latency at low load; batch size over batch time, per slot, decides whether you survive high load; and the bounded queue decides how you fail when you do not.
