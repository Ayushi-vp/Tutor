A city garage installs a new system. It has three floors, spots of three sizes, a few spots with electric chargers, two entrances and a pay station. In its first week two problems appear. On a busy Saturday morning, two cars at the two entrances are both sent to spot F2-C7; the second driver finds it taken and blocks the ramp. And the availability sign at the entrance says floor 2 has 14 free compact spots when it has none, because a counter is decremented on entry but, in one code path, never incremented on exit. Neither bug is exotic. Both come from how the objects were modelled: who owns the state of a spot, and how many places store the same fact.

The parking lot is the most famous object-oriented design question, and it has lasted because it tests exactly that skill. There is no clever algorithm to discover; everybody can produce something that parks a car. The difference between candidates is in the modelling: which things are objects with identity and a lifecycle, which are plain values, where behaviour lives, which parts deserve an interface because they will genuinely vary, and how the design behaves when two things happen at once.

Candidates fail it in two opposite ways. Some under-engineer: one class with a dictionary and a long park method full of if-statements for every vehicle type and every pricing rule. It works and demonstrates nothing. Others over-engineer: abstract factories, a vehicle class hierarchy with no behaviour, an interface for every noun, and no working code after forty minutes. Interviewers see the second failure more often than the first, because it feels like "good design" from the inside.

The target is in between: concrete classes for real things, behaviour placed with the data it changes, an interface only where a second implementation is real (here, spot allocation and pricing), and a clear answer to the question every strong interviewer asks next: what happens when two cars arrive at once?

It is also a good proxy for everyday work. Most business software is exactly this shape: a handful of entities with lifecycles, rules about money and time, policies that change every quarter, and a few places where two requests can collide. Modelling a garage cleanly is practice for modelling orders, bookings, subscriptions and inventory.

This lesson follows the round: the questions to ask, the entities and value objects, a class diagram, a naive version and its bugs, then the correct version built in stages (spots that own their state, an allocation strategy, an itemised fee policy, tickets with a lifecycle, idempotent exit, derived availability), the race and its fix in memory and in SQL, edge cases, extensions such as reservations and many entrances, complexity, and the PostgreSQL documentation that explains why the database version of the fix works.

What the round is really marking

Object-oriented design, at its core, is deciding where knowledge and behaviour live. A good model has objects that correspond to things in the domain, each responsible for keeping its own data consistent, and small, clear relationships between them. The interviewer listens for that reasoning out loud: "a spot knows whether it is occupied, so a spot should be the one that decides whether it can be taken"; "pricing rules change every season, so pricing should be a separate object the lot is given". Code that follows from sentences like these is easy to read and to change, which is what the round is really testing.

Entities and value objects

Two kinds of objects appear in almost every domain model. An entity has an identity that persists while its attributes change. A ticket is issued at 8:00, paid at 10:05, and is the same ticket throughout; two tickets with identical times are still different tickets. A spot is the same spot whether free or occupied. A value object has no identity; it is defined entirely by its values. A fee line "3 hours at 300 cents" is equal to any other line with the same label and amount, and nothing about it ever changes. Value objects should be immutable (in Python, a @dataclass(frozen=True)), which makes them safe to share, compare and use as dictionary keys. Mixing the two up causes real bugs: a mutable "money" object shared between two receipts, changed in one, silently changes the other.

Behaviour lives with the state it changes

The most common modelling mistake is the anaemic domain model: classes that are only bags of fields with getters and setters, while all the logic sits in a service class that reaches in and changes them. In this problem it looks like a Spot with a public occupied_by field that any code can overwrite. Then nothing stops two pieces of code from overwriting each other, which is exactly the double-assignment bug from the opening story. The alternative is to give the spot a method, try_occupy(plate), that checks and changes its state as one step and refuses if the spot is taken. Now the rule "a spot holds at most one car" is enforced in one place, by the object that owns the data.

Strategies, only where variation is real

The Strategy pattern means: when a piece of behaviour has several interchangeable versions, define one interface for it, write each version as its own class, and pass the chosen one in. Two parts of a parking lot vary for business reasons. How a spot is chosen (smallest that fits, nearest the exit, chargers first for electric vehicles, reserved spots excluded) and how a stay is priced (hourly with a daily cap, a flat rate for event nights, weekend discounts). Both deserve a strategy. Almost nothing else does. The test is concrete: if you cannot name a second implementation someone would plausibly want, do not create the interface.

Where the analogy of "real-world objects" breaks

Textbooks say objects model real-world things, and that is a helpful start, but software objects model the rules of the domain, not its physical parts. A real garage has walls, ramps and barriers; none needs a class, because no rule depends on them. A ticket in software may never exist on paper (a licence-plate camera can stand in for it), yet it must be an entity because rules hang on it: when the stay started, whether it has been paid. Model what the rules talk about.

1 · Clarify the requirements

Ask before modelling, because each answer adds or removes a class. How many floors, and which spot sizes? Which vehicle types, and which spots can each use (can a motorcycle take a compact spot; can a car take a large one)? Are there electric-vehicle chargers, and do electric vehicles get priority for them? How many entrances and exits, and can they operate at the same time? How is a stay priced: grace period, hourly rates per size, daily caps, special rates? How does the driver pay, and is there a lost-ticket rule? Are there reservations or monthly passes? Is there a display of free spots per floor?

A typical agreed scope for the coding part: multiple floors; three sizes (motorcycle, compact, large), with a vehicle fitting any spot at least its size; some compact spots with chargers, preferred by electric vehicles; several entrances running concurrently; a ticket issued at entry; payment at exit with itemised fees: 30 minutes free, then every started hour at a size-dependent rate, capped at 25.00 per 24 hours; an availability display per floor and size. Reservations, passes and payment processing are extensions. State the invariants: no spot ever holds two vehicles; a vehicle has at most one active ticket; every paid ticket's spot is free.

2 · Entities, values and responsibilities

Walk through the nouns in the requirements and decide what each is. Vehicle: plate, size, electric or not. It has no lifecycle in this system, so it is a value object. Size: an ordered enum, IntEnum with MOTORCYCLE = 1, COMPACT = 2, LARGE = 3, so "fits" is simply spot.size >= vehicle.size. Spot: an entity with id, floor, size, charger flag and the one piece of mutable state that matters, which plate holds it; it owns the rules for taking and releasing itself. Ticket: an entity with a lifecycle, active then paid, holding entry and exit times and, once paid, its receipt. FeeLine and Receipt: value objects. Allocator and FeePolicy: strategies. ParkingLot: the coordinator that holds spots and tickets, enforces "one active ticket per plate", and uses the strategies. Floors do not need a class: a floor number on each spot is enough until a rule needs floor behaviour.

3 · Stage one: a naive version and its bugs

class ParkingLot:
    def park(self, vehicle):
        for floor in self.floors:
            for spot in floor.spots:
                if spot.occupied_by is None and spot.type == vehicle.type:
                    spot.occupied_by = vehicle
                    floor.free_count -= 1
                    t = Ticket(vehicle.plate, spot.id, datetime.now())
                    self.tickets[vehicle.plate] = t
                    return t
        return None

    def unpark(self, plate):
        t = self.tickets[plate]
        spot = self.find_spot(t.spot_id)
        spot.occupied_by = None
        return (datetime.now() - t.entry_time).seconds / 3600 * 2.5

It parks cars, and the drill takes it apart in detail. In brief: the check occupied_by is None and the write occupied_by = vehicle are separate steps, so two entrances can assign the same spot. free_count is decremented on entry and never incremented on exit, so the display drifts. A motorcycle cannot use a compact spot because types must match exactly. Tickets are keyed by plate, so a second visit overwrites the first ticket's history. The fee uses timedelta.seconds, which ignores whole days (a 25-hour stay is charged as 1 hour), uses floating-point money, and has no grace period or cap. return None on a full lot pushes error handling onto every caller. And the clock is hard-coded, so no test can check a fee without waiting.

4 · Stage two: spots that own their state

The fix for the worst bug starts with moving behaviour. A Spot keeps its plate private and offers try_occupy(plate) and release(plate). try_occupy takes the spot's own lock, checks that the spot is free, sets the plate, and returns True, or returns False if someone else already holds it. That is a compare-and-set: "set the plate, but only if it is still empty", done atomically. release checks that the caller's plate is the one holding the spot, so a bug elsewhere cannot free somebody else's spot. A spot also answers fits(vehicle) with the size comparison. Every rule about a spot is now in the spot.

5 · Stage three: the allocation strategy

The allocator's job is to rank candidate spots for a vehicle; it does not take them. SmallestFitNearest.candidates filters to free spots that fit, then sorts by a key of four parts: for an electric vehicle, spots with chargers first; then smaller sizes first, so a motorcycle takes a motorcycle spot and leaves compact spots for cars and large spots for vans; then lower floors; then spot id for a stable, predictable order. Separating ranking from taking is deliberate: ranking reads state without locks and may be slightly out of date by the time the lot acts on it, which is fine, because the lot then tries try_occupy on each candidate in order and simply moves on when one has been taken in the meantime.

A second allocator is easy to imagine, which is what justifies the interface: "nearest to the exit" for short stays, "spread across floors" to balance ramp traffic, or one that skips spots held by reservations. The lot does not change when one is swapped in.

6 · Stage four: an itemised fee policy

HourlyWithCap.charge(vehicle, entry, exit) returns a tuple of fee lines. If the stay is within the 30-minute grace period, one zero line says so. Otherwise it counts whole 24-hour days, each charged at the daily cap, then takes the remaining time, rounds it up to started hours, and charges each at the vehicle size's hourly rate: 150 cents for motorcycles, 300 for compact, 500 for large. If those hours cost more than the cap, it adds a negative "daily cap applied" line that brings them down to the cap. Amounts are integer cents throughout, because floating-point numbers cannot represent most decimal fractions exactly.

Worked examples, each a test: 25 minutes costs 0 (grace). 2 hours 10 minutes is 3 started hours at 300 cents, 900. 10 hours would be 3,000 cents, so the lines are "10 h x 300c (compact)" and "daily cap applied" at minus 500, total 2,500. 30 hours is one full day at the cap plus 6 started hours at 300: 2,500 + 1,800 = 4,300. Note the subtle choice inside: the grace period only applies to whole stays under 30 minutes, not as a discount on longer ones. That is a business rule; say it aloud and ask, because tariffs differ.

Durations are computed with timedelta division (d // timedelta(days=1), rest / timedelta(hours=1)), never with timedelta.seconds, which holds only the seconds part after whole days. That attribute is the source of a classic bug where a stay of one day and one hour is billed as one hour.

7 · Stage five: tickets, park and unpark

park(vehicle) first reserves the plate under the lot's lock, so the same car cannot enter twice, even from two entrances at once. It then asks the allocator for candidates and calls try_occupy on each in turn. On the first success it creates a ticket with an id from a counter and the entry time from an injected clock, records it, and returns it. If no candidate can be taken it raises LotFull, a named exception the entrance can turn into a "full" sign, and releases the plate reservation in a cleanup block so a failed attempt never leaves the plate stuck.

unpark(ticket_id, vehicle) checks that the ticket exists and belongs to that plate, and then handles a detail that matters in practice: a driver may tap the pay button twice, or the barrier may retry after a network error. If the ticket is already paid, it returns the stored receipt and does nothing else. Otherwise it sets the exit time, asks the fee policy for lines, stores the receipt, marks the ticket paid, frees the plate for future visits, and releases the spot. Paying the same ticket twice therefore charges once and frees the spot once: unpark is idempotent.

8 · The race, traced, and two fixes

Here is the naive interleaving with one compact spot left and cars at two entrances, A and B, each handled by its own thread.

StepEntrance AEntrance BSpot F2-C7
1reads occupied_by is None: truefree
2reads occupied_by is None: truefree
3writes occupied_by = car A, issues ticketcar A
4writes occupied_by = car B, issues ticketcar B (A's claim silently lost)

Both drivers have tickets for F2-C7. The system believes car B is there. When car A's driver later pays, the naive unpark frees the spot, while car B is still in it. With per-spot compare-and-set, step 4 becomes try_occupy taking the spot's lock, seeing car A's plate, and returning False; entrance B moves to the next candidate or reports the lot full. The stress test in the full solution starts sixteen threads at once with a barrier against a lot with five compact spots: exactly five tickets are issued, all for distinct spots, and eleven cars are told the lot is full.

In a real deployment the spots live in a database, and the same idea becomes a conditional update: UPDATE spots SET plate = ? WHERE id = ? AND plate IS NULL, followed by checking the number of rows changed. If it is one, this entrance won; if zero, someone else did. The full solution includes a SQLite version and a test where eight threads race for one spot and exactly one wins. In PostgreSQL the reason it works is spelled out in the isolation documentation: under the default Read Committed level, a second transaction updating a row that a first has just updated waits for the first to commit, then re-evaluates its WHERE clause against the new version; plate IS NULL is now false, so it updates nothing.

9 · Availability without a second source of truth

availability() loops over the spots and counts free ones per floor and size. With a few thousand spots that costs microseconds, and it can never disagree with the spots because it is computed from them. If the display is polled so often that the loop matters, cache the counts, but update them inside the same lock or database transaction as the spot change, and run a periodic job that recomputes from spots and alerts if the cache ever differs. A counter maintained separately, as in the naive version, is a second source of truth, and second sources of truth drift.

10 · The full solution

The file below is the complete design with five tests: allocation rules, the 16-thread race, itemised fees, idempotent exit, and the SQLite conditional-update race. Python 3.12, standard library only. It also contains a small trap worth knowing: in Python's sqlite3, using a connection as a context manager commits or rolls back the transaction but does not close the connection; the first version of this test failed on Windows because the database file was still open when the test tried to delete it.

"""Parking lot: entities with behaviour, a pluggable allocation strategy, an itemised fee policy,
race-free spot assignment in memory (per-spot compare-and-set) and in SQL (conditional UPDATE).
Python 3.12, standard library only. Run: python parking.py"""
from __future__ import annotations

import itertools
import math
import sqlite3
import threading
from dataclasses import dataclass, field
from datetime import datetime, timedelta
from enum import Enum, IntEnum
from typing import Callable, Protocol


# ------------------------------------------------------------------ value objects
class Size(IntEnum):                     # ordered: a vehicle fits any spot at least its size
    MOTORCYCLE = 1
    COMPACT = 2
    LARGE = 3


@dataclass(frozen=True)
class Vehicle:
    plate: str
    size: Size
    electric: bool = False


@dataclass(frozen=True)
class FeeLine:
    label: str
    cents: int


@dataclass(frozen=True)
class Receipt:
    ticket_id: int
    plate: str
    lines: tuple[FeeLine, ...]

    @property
    def total_cents(self) -> int:
        return sum(l.cents for l in self.lines)


# ------------------------------------------------------------------ entities
class Spot:
    """Owns its own state transition, so 'is it free?' and 'take it' are one atomic step."""

    def __init__(self, spot_id: str, floor: int, size: Size, charger: bool = False) -> None:
        self.id, self.floor, self.size, self.charger = spot_id, floor, size, charger
        self._plate: str | None = None
        self._lock = threading.Lock()

    def fits(self, v: Vehicle) -> bool:
        return self.size >= v.size

    @property
    def free(self) -> bool:
        return self._plate is None

    def try_occupy(self, plate: str) -> bool:
        with self._lock:                                  # compare-and-set: only if still free
            if self._plate is not None:
                return False
            self._plate = plate
            return True

    def release(self, plate: str) -> None:
        with self._lock:
            if self._plate != plate:
                raise ValueError(f"spot {self.id} is not held by {plate}")
            self._plate = None


class TicketStatus(Enum):
    ACTIVE = "active"
    PAID = "paid"


@dataclass
class Ticket:
    id: int
    plate: str
    spot_id: str
    entry: datetime
    exit: datetime | None = None
    status: TicketStatus = TicketStatus.ACTIVE
    receipt: Receipt | None = None


# ------------------------------------------------------------------ strategies
class Allocator(Protocol):
    def candidates(self, spots: list[Spot], v: Vehicle) -> list[Spot]: ...


class SmallestFitNearest:
    """EVs try charger spots first; then the smallest spot that fits (saves large spots for
    large vehicles); then the lowest floor."""

    def candidates(self, spots: list[Spot], v: Vehicle) -> list[Spot]:
        ok = [s for s in spots if s.free and s.fits(v)]
        return sorted(ok, key=lambda s: (not (v.electric and s.charger), s.size, s.floor, s.id))


class FeePolicy(Protocol):
    def charge(self, v: Vehicle, entry: datetime, exit: datetime) -> tuple[FeeLine, ...]: ...


@dataclass(frozen=True)
class HourlyWithCap:
    """Grace period free; otherwise every started hour at the size's rate, capped per 24 h."""
    hourly_cents: dict[Size, int] = field(default_factory=lambda: {
        Size.MOTORCYCLE: 150, Size.COMPACT: 300, Size.LARGE: 500})
    daily_cap_cents: int = 2_500
    grace: timedelta = timedelta(minutes=30)

    def charge(self, v: Vehicle, entry: datetime, exit: datetime) -> tuple[FeeLine, ...]:
        if exit < entry:
            raise ValueError("exit before entry")
        d = exit - entry
        if d <= self.grace:
            return (FeeLine(f"grace period ({int(d.total_seconds() // 60)} min)", 0),)
        lines, days = [], d // timedelta(days=1)
        if days:
            lines.append(FeeLine(f"{days} full day(s) at daily cap", days * self.daily_cap_cents))
        rest = d - days * timedelta(days=1)
        hours = math.ceil(rest / timedelta(hours=1))
        if hours:
            raw = hours * self.hourly_cents[v.size]
            lines.append(FeeLine(f"{hours} h x {self.hourly_cents[v.size]}c ({v.size.name.lower()})", raw))
            if raw > self.daily_cap_cents:
                lines.append(FeeLine("daily cap applied", self.daily_cap_cents - raw))
        return tuple(lines)


# ------------------------------------------------------------------ the lot
class LotFull(Exception): ...
class AlreadyParked(Exception): ...


class ParkingLot:
    def __init__(self, spots: list[Spot], allocator: Allocator, fees: FeePolicy,
                 clock: Callable[[], datetime] = datetime.now) -> None:
        self.spots = spots
        self.by_id = {s.id: s for s in spots}
        self.allocator, self.fees, self.clock = allocator, fees, clock
        self.tickets: dict[int, Ticket] = {}
        self.active_by_plate: dict[str, int] = {}
        self._ids = itertools.count(1)
        self._lock = threading.Lock()                     # guards the ticket maps only

    def park(self, v: Vehicle) -> Ticket:
        with self._lock:
            if v.plate in self.active_by_plate:
                raise AlreadyParked(v.plate)
            self.active_by_plate[v.plate] = 0             # reserve the plate while we look
        try:
            for spot in self.allocator.candidates(self.spots, v):
                if spot.try_occupy(v.plate):              # lost the race? try the next one
                    with self._lock:
                        t = Ticket(next(self._ids), v.plate, spot.id, self.clock())
                        self.tickets[t.id] = t
                        self.active_by_plate[v.plate] = t.id
                    return t
            raise LotFull(f"no {v.size.name.lower()} spot")
        except BaseException:
            with self._lock:
                if self.active_by_plate.get(v.plate) == 0:
                    del self.active_by_plate[v.plate]
            raise

    def unpark(self, ticket_id: int, v: Vehicle) -> Receipt:
        with self._lock:
            t = self.tickets.get(ticket_id)
            if t is None or t.plate != v.plate:
                raise KeyError("unknown ticket for this vehicle")
            if t.status is TicketStatus.PAID:             # idempotent: the same receipt again
                return t.receipt
            t.exit = self.clock()
            t.receipt = Receipt(t.id, t.plate, self.fees.charge(v, t.entry, t.exit))
            t.status = TicketStatus.PAID
            del self.active_by_plate[t.plate]
        self.by_id[t.spot_id].release(t.plate)
        return t.receipt

    def availability(self) -> dict[int, dict[str, int]]:
        """Derived on read from spot state: no second counter to drift."""
        out: dict[int, dict[str, int]] = {}
        for s in self.spots:
            if s.free:
                floor = out.setdefault(s.floor, {})
                floor[s.size.name] = floor.get(s.size.name, 0) + 1
        return out


# ------------------------------------------------------------------ the same rule in SQL
class SqlSpots:
    """Persistence-layer version of try_occupy: UPDATE ... WHERE plate IS NULL, check rowcount."""

    def __init__(self, path: str, n: int) -> None:
        self.path = path
        db = sqlite3.connect(path)
        try:                                              # 'with conn' commits but does not close
            with db:
                db.execute("DROP TABLE IF EXISTS spots")
                db.execute("CREATE TABLE spots (id INTEGER PRIMARY KEY, plate TEXT)")
                db.executemany("INSERT INTO spots (id, plate) VALUES (?, NULL)",
                               [(i,) for i in range(n)])
        finally:
            db.close()

    def try_occupy(self, spot_id: int, plate: str) -> bool:
        db = sqlite3.connect(self.path, timeout=10, isolation_level=None)
        try:
            cur = db.execute("UPDATE spots SET plate = ? WHERE id = ? AND plate IS NULL",
                             (plate, spot_id))
            return cur.rowcount == 1                      # 0 rows: someone else got it first
        finally:
            db.close()


# ---------------------------------------------------------------- tests
class FakeClock:
    def __init__(self) -> None:
        self.now = datetime(2026, 10, 2, 8, 0)

    def __call__(self) -> datetime:
        return self.now


def build(floors: int = 2, per_floor: dict[Size, int] | None = None, chargers: int = 1,
          clock=None) -> ParkingLot:
    per_floor = per_floor or {Size.MOTORCYCLE: 2, Size.COMPACT: 3, Size.LARGE: 1}
    spots = []
    for f in range(floors):
        for size, n in per_floor.items():
            for k in range(n):
                spots.append(Spot(f"F{f}-{size.name[0]}{k}", f, size,
                                  charger=(size is Size.COMPACT and k < chargers)))
    return ParkingLot(spots, SmallestFitNearest(), HourlyWithCap(), clock or datetime.now)


def test_allocation_rules() -> None:
    lot = build()
    m = lot.park(Vehicle("M1", Size.MOTORCYCLE))
    assert lot.by_id[m.spot_id].size is Size.MOTORCYCLE            # smallest fit
    ev = lot.park(Vehicle("EV1", Size.COMPACT, electric=True))
    assert lot.by_id[ev.spot_id].charger                           # EV prefers a charger
    big = [lot.park(Vehicle(f"L{i}", Size.LARGE)) for i in range(2)]
    try:
        lot.park(Vehicle("L9", Size.LARGE))
    except LotFull:
        pass
    else:
        raise AssertionError("third large vehicle parked in a smaller spot")
    assert {lot.by_id[t.spot_id].floor for t in big} == {0, 1}


def test_no_double_assignment_under_threads() -> None:
    lot = build(floors=1, per_floor={Size.COMPACT: 5}, chargers=0)
    wins, losses = [], []
    start = threading.Barrier(16)

    def car(i: int) -> None:
        start.wait()
        try:
            wins.append(lot.park(Vehicle(f"C{i}", Size.COMPACT)))
        except LotFull:
            losses.append(i)
    ts = [threading.Thread(target=car, args=(i,)) for i in range(16)]
    for t in ts: t.start()
    for t in ts: t.join()
    assert len(wins) == 5 and len(losses) == 11
    assert len({t.spot_id for t in wins}) == 5                   # five distinct spots
    assert lot.availability() == {}


def test_fees_itemised() -> None:
    p, car = HourlyWithCap(), Vehicle("X", Size.COMPACT)
    t0 = datetime(2026, 10, 2, 8, 0)
    def total(**kw) -> int:
        return sum(l.cents for l in p.charge(car, t0, t0 + timedelta(**kw)))
    assert total(minutes=25) == 0                                 # grace
    assert total(hours=2, minutes=10) == 900                      # 3 started hours x 300
    assert total(hours=10) == 2_500                               # 3,000 capped at 2,500
    assert total(hours=30) == 2_500 + 1_800                       # 1 day cap + 6 h
    lines = p.charge(car, t0, t0 + timedelta(hours=10))
    assert [l.label for l in lines] == ["10 h x 300c (compact)", "daily cap applied"]


def test_unpark_idempotent_and_frees_spot() -> None:
    clk = FakeClock()
    lot = build(clock=clk)
    car = Vehicle("AB12", Size.COMPACT)
    t = lot.park(car)
    try:
        lot.park(car)
    except AlreadyParked:
        pass
    clk.now += timedelta(hours=1, minutes=5)
    r1 = lot.unpark(t.id, car)
    r2 = lot.unpark(t.id, car)
    assert r1 is r2 and r1.total_cents == 600
    assert lot.by_id[t.spot_id].free
    lot.park(car)                                                 # can park again after paying


def test_sql_conditional_update_race() -> None:
    import os, tempfile
    tmp = os.path.join(tempfile.mkdtemp(), "spots.db")
    store = SqlSpots(tmp, n=1)
    winners = []
    start = threading.Barrier(8)

    def car(i: int) -> None:
        start.wait()
        if store.try_occupy(0, f"P{i}"):
            winners.append(i)
    ts = [threading.Thread(target=car, args=(i,)) for i in range(8)]
    for t in ts: t.start()
    for t in ts: t.join()
    os.remove(tmp)
    assert len(winners) == 1, winners


if __name__ == "__main__":
    for t in (test_allocation_rules, test_no_double_assignment_under_threads, test_fees_itemised,
              test_unpark_idempotent_and_frees_spot, test_sql_conditional_update_race):
        t()
        print("ok ", t.__name__)

11 · Talking through the design

In the round, narration matters as much as code. A strong walkthrough sounds like this: "I'll start from the invariants: one car per spot, one active ticket per car, and fees fixed once paid. Spot owns occupancy, so it gets try_occupy. Ticket owns the stay's lifecycle. Allocation and pricing change for business reasons, so they're strategies passed in; I can name a second implementation of each. Vehicles are values with an ordered size, no hierarchy, because they have no behaviour of their own. The lot coordinates and holds the only lock that spans objects, the plate-to-ticket map. The one place two threads can collide is taking a spot, so that's a compare-and-set, and in a database a conditional update." Every sentence links a design choice to a requirement, which is precisely what the interviewer is scoring.

12 · Edge cases

The same car entering twice (a cloned plate, or a camera misread): refuse the second entry and flag it. A ticket for a different plate presented at exit: refuse. Exit time before entry time because of a clock change: the fee policy raises; use a time source that cannot jump, or record both times from the same server. Stays crossing midnight or a daylight-saving change: compute durations from timezone-aware or UTC timestamps, not local wall-clock times, or a 2-hour stay on the night clocks go back is billed as 3 hours. A full lot for one size but not others: a motorcycle can still park in a compact spot; a van cannot. Lost ticket: charge a fixed lost-ticket fee or the maximum, looked up by plate. Partial failure: if the ticket is created but the barrier never opens, the spot must be released after a timeout.

13 · Extensions the interviewer will ask for

Reservations: an entity with a time window and states (held, checked in, expired, cancelled); the allocator excludes spots held for an overlapping window; expire no-shows. Monthly passes: a different fee policy chosen per vehicle. EV charging: a separate charging session per ticket with metered kilowatt-hours, adding its own fee lines. Display boards: subscribers notified when availability changes, the Observer pattern, or simply polling the derived counts. Many entrances against a central database: conditional updates, or SELECT ... FOR UPDATE SKIP LOCKED so entrances grab different free rows without waiting on each other. Multiple sites: each lot is an object; nothing is a singleton, so this costs nothing.

14 · Complexity

Allocation as written is O(S log S) for S spots (filter and sort); with thousands of spots that is negligible. For very large lots, keep per-floor, per-size free lists (a set of free spot ids) so finding a candidate is O(1), and update them atomically with the spot state. try_occupy and release are O(1). Fees are O(1) per ticket. Memory is O(S + T) for spots and tickets; archive paid tickets to keep T bounded.

Aggregates and where locks belong

Domain-driven design has a name for "a group of objects that must stay consistent together, changed only through one root": an aggregate. The question of where to put locks is the question of where aggregate boundaries are. In this design the invariant "a spot holds at most one plate" involves only the spot, so the spot is its own consistency boundary and gets its own lock; entrances working on different spots never wait for each other. The invariant "a plate has at most one active ticket" spans tickets, so the lot's ticket maps get a lock. A design that puts one lock around everything is correct but serialises every entrance; one with no locks is fast and wrong. Choosing boundaries from invariants is the reasoning interviewers want to hear.

Optimistic versus pessimistic concurrency

Compare-and-set and conditional updates are optimistic: proceed without holding a lock while deciding, and detect at the moment of writing whether someone else got there first, then retry with another candidate. They shine when conflicts are rare, which is true for a lot with many free spots and few entrances. Pessimistic concurrency takes a lock before reading, for example SELECT ... FOR UPDATE on a candidate row, so nobody else can change it until the transaction ends. It wastes less work when conflicts are common, at the cost of waiting. PostgreSQL's SKIP LOCKED option combines them nicely for queues and pools: each entrance locks the first free row that nobody else has locked, skipping rows other transactions hold, so entrances never queue behind each other.

The Read Committed re-check, and when it is not enough

The conditional update is safe because the database re-checks the WHERE clause after waiting for a conflicting writer. That protects a single-row decision. It does not protect decisions spread across several rows read earlier: if an entrance reads "floor 2 has 3 free spots" in one statement and then, based on that, decides to send a van there, another transaction can fill those spots in between. Either make every decision a single conditional write, or use a stricter isolation level such as Serializable, where PostgreSQL detects such anomalies and aborts one transaction, which the application must retry.

Time is a dependency

The lot receives its clock as an argument, defaulting to datetime.now. That small choice makes every fee test instant and exact: the test sets the fake clock to 8:00, parks, moves it forward 65 minutes, unparks, and asserts 600 cents. It also forces a decision about which clock: a server's local wall clock jumps at daylight-saving changes and can be corrected by time synchronisation, so production systems record UTC timestamps and convert to local time only for display. Billing that uses local time will, once a year, charge a stay that crossed the autumn change for an hour that did not exist.

Value objects and equality in Python

A frozen dataclass gets __eq__ and __hash__ generated from its fields, so two FeeLine("3 h", 900) objects compare equal and can be dictionary keys or set members, which is exactly value semantics. Assigning to a field raises FrozenInstanceError, so a receipt handed to the payment terminal cannot be altered by a later bug. Entities are the opposite: a Ticket is a regular (mutable) dataclass, and if you ever need tickets in sets you should compare them by id only, since two tickets with equal fields are still different tickets. Python's default __eq__ for ordinary classes compares identity, which is the right default for entities that are not dataclasses. Getting this right is cheap, and it removes a whole class of bugs where a shared mutable "value" changes under someone's feet.

Testing a domain model

A good object model is easy to test because each rule lives in one place. The allocation test does not need a fee policy; the fee test does not need a lot at all, only HourlyWithCap.charge and two datetimes; the exit test injects a fake clock. Tests follow the invariants written under the state diagram: a spot never holds two plates (the thread test), a plate never has two active tickets (the double-entry check), a paid ticket is never charged again (the idempotency test), and the sum of fee lines is the total (each fee example). When a rule changes, one test changes. When the model is anaemic, by contrast, every test must build the whole lot and drive it through a service, and a pricing change breaks tests about allocation. Test effort is a useful smell detector for design quality.

When inheritance is right

The lesson argues against a Car, Truck, Motorcycle hierarchy, but inheritance is not wrong in general. It earns its place when subtypes genuinely behave differently behind one interface: a ValetTicket whose fee policy and exit flow differ, or spot types with different occupation rules (a charger spot that must start a charging session). The test is behavioural, not taxonomic: if the subclasses would only differ in a constant, use data; if they override methods with different logic, a hierarchy or composition with strategies may fit. Prefer composition first, because it lets behaviours combine (an electric, reserved, large spot) without a subclass for every combination.

How parking systems fail in practice

Real garage systems fail at the boundaries between software and the physical world more than in their object models. A licence-plate camera misreads a plate at entry and reads it correctly at exit, so the exit cannot find the ticket; systems handle this with fuzzy matching and a human override at the barrier. A barrier opens but the car reverses out, leaving a ticket active and a spot marked occupied with no car; a timeout that releases unconfirmed spots, or a sensor per spot, reconciles it. Network partitions between an entrance and the central database must not stop the barrier: entrances usually fall back to issuing tickets offline and reconciling later, accepting a small risk of over-filling.

The software failures are the ones this lesson's design prevents: double assignment from check-then-act races, availability displays drifting from a separately maintained counter, double charging when a payment is retried, and billing errors from date arithmetic (the timedelta.seconds bug, daylight-saving transitions, floating-point money).

What to measure

Occupancy per floor and size over time (for pricing decisions and capacity planning), entry-to-spot time, failed or retried assignments (a rising rate means contention or stale candidate lists), differences found by the availability reconciliation job (should be zero), unpaid tickets older than a threshold, and revenue per day reconciled against the payment processor's records. Each discrepancy count is a cheap, early bug detector.

Knobs and operations

Tariffs change often, so the fee policy should be data-driven: rates, grace period and caps loaded from configuration with an effective date, so a price change is a configuration release rather than a code change, and old tickets are billed at the tariff in force when they entered if that is the rule. Allocation policies are tuned to traffic: spreading cars across floors reduces ramp congestion at peak, while filling lower floors first shortens walks off-peak. Keep both strategies swappable at runtime, which the injected-strategy design already allows.

Tariff changes and versioned rules

Prices change, and a garage open all night always has cars that entered under the old tariff. Decide and document which tariff applies: the one in force at entry (common, and easy to explain to customers) or a split charge across the change. Implement tariffs as versioned data with effective dates, chosen by the fee policy from the ticket's entry time, and keep old versions forever so any past receipt can be recomputed exactly during a dispute. The same idea, versioned rules selected by an event's timestamp, recurs in tax systems, insurance pricing and feature flags.

The real case: PostgreSQL's isolation rules

The most important production fact in this lesson is how a database behaves when two transactions race for the same row, and the PostgreSQL documentation states it precisely. Read Committed is PostgreSQL's default isolation level. In it, UPDATE commands find target rows that were committed as of the command's start, but such a row may already have been updated by a concurrent transaction by the time it is found. In that case the would-be updater waits for the first transaction to commit or roll back. If the first commits, the second re-evaluates its WHERE clause against the updated version of the row, and proceeds only if the row still matches. For UPDATE spots SET plate = 'B' WHERE id = 7 AND plate IS NULL, the first entrance's commit sets the plate, the re-check fails for the second, and its update affects zero rows. The application reads that row count and tries the next spot. No explicit lock, no lost update, and no change to the object model: the database simply performs the compare-and-set that Spot.try_occupy performs in memory. The documentation also describes where Read Committed is not enough, for decisions involving several rows read earlier, which is why stricter levels exist and why the design keeps each decision to a single conditional write.

Work it out

Review this allocation code. Find at least five distinct problems and say how you would fix each.

class ParkingLot:
    def park(self, vehicle):
        for floor in self.floors:
            for spot in floor.spots:
                if spot.occupied_by is None and spot.type == vehicle.type:
                    spot.occupied_by = vehicle
                    floor.free_count -= 1
                    t = Ticket(vehicle.plate, spot.id, datetime.now())
                    self.tickets[vehicle.plate] = t
                    return t
        return None

    def unpark(self, plate):
        t = self.tickets[plate]
        spot = self.find_spot(t.spot_id)
        spot.occupied_by = None
        fee = (datetime.now() - t.entry_time).seconds / 3600 * 2.5
        return fee
Answer

In the order a reviewer should raise them:

1 · A check-then-act race. Two entrances can both see occupied_by is None and both assign; the second overwrites the first, and both drivers hold tickets for one spot. Fix: move the transition into the spot as try_occupy(plate), an atomic compare-and-set under the spot's lock, and continue to the next candidate when it returns False. In a database, a conditional update with a row-count check.

2 · free_count is a second source of truth and is never restored. park decrements it; unpark never increments it, so the display drifts towards "full" all day. Fix: derive availability from spot state, or update the count inside the same atomic step as the spot and reconcile periodically.

3 · The fee is wrong in three ways. timedelta.seconds is only the seconds part after whole days, so a 25-hour stay bills as 1 hour. Money is a float, so totals drift by fractions of a cent. And there is no grace period, rounding to started hours or daily cap. Fix: compute with timedelta division, integer cents, and an injected fee policy that returns itemised lines.

4 · Exact type matching wastes capacity. A motorcycle cannot use an empty compact spot, so motorcycles are turned away from a half-empty lot. Fix: ordered sizes and spot.size >= vehicle.size, with an allocator that prefers the smallest fitting spot.

5 · Tickets keyed by plate. A second visit overwrites the first ticket, losing history, and a car can enter twice without being noticed. Fix: tickets keyed by their own id, plus a separate "active ticket by plate" map that refuses a second active ticket.

6 · No idempotency and no ownership check on exit. Calling unpark twice charges twice; and nothing checks that the spot is still held by this car before freeing it. Fix: a ticket state machine (active, paid) that returns the stored receipt on repeat, and release(plate) that refuses if another plate holds the spot.

7 · Untestable time and silent failure. datetime.now() is hard-coded, so fees cannot be tested without waiting, and return None on a full lot forces every caller to remember to check. Fix: inject a clock; raise a named LotFull exception.

The theme to say aloud: almost every bug comes from state being changed by code that does not own it. Moving each rule into the object that owns the data (spot occupancy into Spot, ticket lifecycle into Ticket, pricing into a policy) fixes most of the list at once.
