Two companies serve the same open model on the same GPUs. One pays three times as much per million tokens as the other, and its users still complain that answers start slowly at busy times. Nothing about the model differs; the difference is entirely in how requests are scheduled, how GPU memory is managed, whether repeated prompt prefixes are reused, and whether generation is accelerated with speculation. Serving engineering is where an LLM's cost is decided, and for most companies running models at scale it is a larger lever than any change to the model itself.

The underlying reason is the shape of LLM inference, set out in lm5 and gpu10. Generating a token is a memory-bound step that reads all the model's weights to do very little arithmetic, so a GPU serving one request at a time is mostly idle. The cure is to process many requests together, but requests arrive at random times, have prompts of very different lengths and generate answers of unpredictable length, and each one needs a KV cache that grows as it generates. Naive batching wastes most of the GPU; naive memory management wastes most of the memory. The techniques in this lesson, all developed between 2022 and 2024 and now standard in serving engines, recover that waste.

For an AI engineer this matters whether you run models yourself or buy them through an API: it explains the latency numbers you see, the price differences between input, cached-input and output tokens, why long contexts cost more, and what to ask of a serving platform. In interviews it shows up as system-design questions ("design an LLM serving system") and as quick calculations (the speed-up of speculative decoding for a given acceptance rate).

There is a useful mental shift here. Training engineers think in FLOPs, because training is compute-bound. Serving engineers think in bytes and slots: bytes of weights and cache read per step, and how many request slots are doing useful work at each step. Almost every serving optimisation either reduces bytes per useful token or increases the number of useful tokens per step, and keeping that frame in mind makes new techniques easy to place.

This lesson defines the metrics (time to first token, time per output token, throughput, goodput), then walks through the levers: continuous batching, paged KV-cache memory, prefix caching, chunked prefill and disaggregation, and speculative decoding with its exact acceptance rule and expected-speed-up formula worked by hand. The public case is vLLM's PagedAttention paper. The lab simulates batching policies, memory allocation and speculative sampling in NumPy.

Three numbers

Serving performance comes down to three numbers. Time to first token (TTFT) is how long a user waits before the answer starts streaming: queueing plus prefill, the parallel pass over the prompt. Time per output token (TPOT, or inter-token latency) is the gap between streamed tokens: one decode step. Throughput is the total number of tokens the deployment produces per second across all users, which, divided into the hourly GPU price, gives the cost per token. A user feels the first two; the finance team feels the third. They trade off: making the batch bigger raises throughput but lengthens each decode step, so each user's tokens arrive more slowly. Serving is therefore usually framed as "maximise throughput subject to latency targets", for example p95 TTFT under one second and p95 TPOT under 50 ms. Throughput counting only requests that met their targets is called goodput.

An analogy: a restaurant kitchen

A kitchen with one chef cooking one order at a time from start to finish wastes the oven, the stove and the chef's hands most of the time. A good kitchen works on many orders at once. Static batching is a kitchen that takes eight orders, cooks them together, and seats no new customers until all eight are served, even if seven were salads and one was a slow roast. Continuous batching seats a new customer the moment any order goes out. Paged memory is having flexible counter space handed out a tray at a time instead of reserving a full table's worth for every order in case it turns into a banquet. Prefix caching is preparing the sauce once for every order that starts with it. Speculative decoding is a junior cook preparing the next few steps of a dish in advance, with the head chef checking them all at a glance and redoing only the first one that is wrong. The analogy is imperfect in one way: in a GPU the "checking at a glance" is nearly free only because the head chef's real bottleneck is fetching ingredients (reading weights from memory), not cooking.

Numbers for one GPU

To make this concrete: Llama 3 8B in bf16 on one H100 can generate roughly 200 tokens per second for a single user, because each step reads its 16 GB of weights in about 5 ms. Serving a hundred users at once, the same GPU produces several thousand tokens per second in total, while each user sees perhaps 40-60 tokens per second. The gap between those two numbers, single-user speed versus total throughput, is the territory of this lesson, and closing it without breaking per-user latency is what serving engines do.

The levers, in one list

Everything in this lesson attacks one of four wastes. Idle slots: fixed by continuous batching. Wasted memory: fixed by paged KV allocation (and quantised caches, lm12), which lets more requests share the GPU. Repeated work: fixed by prefix caching. Under-used arithmetic during decode: exploited by speculative decoding, which turns spare compute into fewer sequential steps. Chunked prefill and disaggregation address a fifth problem, interference between compute-heavy prefill and latency-sensitive decode.

1. The anatomy of a request

A request arrives and waits in a queue until the scheduler admits it. Prefill runs the whole prompt through the model in one pass, which is compute-bound because thousands of tokens share each weight read; for a 7B model and a 2,000-token prompt that is about 2 × 7 × 10⁹ × 2,000 = 2.8 × 10¹³ FLOPs, roughly 50 ms on an H100 at half its peak. Prefill writes the prompt's KV cache and produces the first token. Then decode runs one step per output token: each step reads all the weights and the request's growing cache to compute one new token. For a 7B model at batch 1 that is about 13.5 GB per step, about 4-5 ms on an H100, or 200-250 tokens per second for that one user. TTFT is queueing plus prefill; TPOT is one decode step; total time is TTFT plus output length times TPOT.

2. Why batching is the main lever

At batch 1, a decode step reads 13.5 GB to do about 13.5 GFLOP of arithmetic, about 1 FLOP per byte, while an H100 can do several hundred FLOPs per byte of bandwidth (gpu2). The GPU's arithmetic units are almost entirely idle. With 32 sequences in the batch, the same weight read serves 32 tokens; step time rises only modestly (each sequence adds its own KV-cache read), so throughput rises nearly 32-fold. This continues until one of four limits binds: KV-cache memory (no room for more sequences, lm5), KV reads dominating step time, the step becoming compute-bound, or the step exceeding the latency target. Every technique below is about reaching a larger effective batch, or making better use of each step.

3. Static batching and its waste

The simplest scheme collects B requests, runs them together until all finish, then takes the next B. Two wastes follow. Requests generate different numbers of tokens, so slots whose requests finished sit idle until the longest request in the batch is done, and output lengths in chat traffic vary by orders of magnitude. And a newly arrived request must wait for the whole current batch to finish before it even starts, inflating TTFT. In the lab's simulation of 400 requests with log-normal output lengths (median about 150 tokens, a long tail up to 2,000) on 8 slots, static batching produced 3.13 tokens per step: on average, fewer than half the slots were doing useful work.

4. Continuous batching

Orca (Yu et al., OSDI 2022) introduced iteration-level scheduling, now usually called continuous batching. The scheduler re-forms the batch at every decode step: a request that emitted its end token leaves immediately, and a waiting request is admitted into the free slot (its prefill can run in the same step or a chunked prefill can be mixed in, section 7). Slots are therefore busy nearly all the time and short requests return as soon as they are done. In the lab, the same 400 requests took 10,144 steps instead of 25,051: 7.73 tokens per step against 3.13, 2.5× the throughput, and the mean completion time fell from step 14,169 to step 5,339. Continuous batching requires kernels that handle a batch whose sequences are at different positions with different cache lengths, and a scheduler that knows how much KV memory each admitted request will need, which leads directly to paged memory.

5. Paged KV-cache memory

Each request needs a KV cache that grows by one token per step, up to an unknown final length. Systems before 2023 typically allocated each request a contiguous region large enough for its maximum possible length (say 2,048 tokens), because tensors were easiest to handle contiguously. Most of that reservation was never used, and freed regions of different sizes fragmented memory. Kwon et al. profiled existing systems and found that only 20.4% to 38.2% of KV-cache memory held actual token states. The lab reproduces the effect: 400 requests with realistic prompt and output lengths use 373,403 token slots but a 2,048-token reservation per request sets aside 819,200, 45.6% utilised.

PagedAttention borrows the operating system's answer: virtual memory with pages. The KV cache of each sequence is split into fixed-size blocks of tokens (vLLM's default is 16 tokens), allocated from a pool only when the sequence reaches them, and placed anywhere in GPU memory. A per-sequence block table maps logical block numbers to physical blocks, and the attention kernel follows the table when reading keys and values. Waste is at most one partially filled block per sequence: the lab's paged allocation uses 376,416 slots for 373,403 tokens, 99.2% utilisation. More sequences fit in the same memory, so batches grow and throughput rises. Blocks also enable sharing: several sequences can point to the same physical blocks for a shared prefix, with copy-on-write when they diverge, which saves up to 55% memory for parallel sampling and beam search in the paper's experiments.

6. Prefix caching

Many requests start with the same tokens: a 2,000-token system prompt, a set of few-shot examples, a document that users ask several questions about, or the full history of a conversation resent on each turn. The KV cache of those tokens is identical every time (it depends only on the tokens and their positions), so recomputing it is pure waste. Prefix caching keeps the KV blocks of recently seen prefixes, indexed by a hash of their tokens, and when a new request's beginning matches, links its block table to the cached blocks and prefills only the new suffix. Worked: 100 requests, each a 2,000-token shared prompt plus a 200-token question. Without caching, prefill processes 100 × 2,200 = 220,000 tokens; with caching, 2,000 once plus 100 × 200 = 22,000: 90% less prefill compute and a much lower TTFT for every request after the first. The cache competes for memory with running sequences, so engines evict least-recently-used prefixes under pressure. API providers expose the same mechanism as discounted "cached input" pricing.

7. Chunked prefill and prefill-decode interference

Prefill and decode have opposite characters. A long prompt's prefill is a large, compute-bound burst; decode steps are small, memory-bound and latency-sensitive. In a continuously batched server, admitting a 30,000-token prompt can occupy the GPU for a second, and every other user's next token waits behind it: a TPOT spike. Chunked prefill splits the prompt into chunks (for example 512-2,048 tokens) and processes one chunk per step alongside the ongoing decode tokens of other requests, so each step mixes some compute-heavy prefill work with memory-bound decode work, using both resources and keeping step times bounded. The long request's TTFT rises slightly; everyone else's latency becomes predictable. Disaggregated serving goes further: dedicated prefill GPUs and decode GPUs, each configured for its bottleneck, with the KV cache transferred between them over fast interconnect (gpu10 discusses the trade-offs).

8. Speculative decoding: the idea

Decode is sequential: token t + 1 cannot be computed until token t is known. But a decode step on a large model is memory-bound, so the target model could score several positions in one forward pass for almost the same cost as one, if only it knew which tokens to score. Speculative decoding supplies guesses. A small, fast draft model (for example a 1B model from the same family as a 70B target, sharing its tokeniser) generates γ tokens autoregressively, which is cheap. The target model then runs one forward pass over the prompt plus those γ draft tokens and obtains its own probability distribution at every one of those positions (lm2: a causal forward pass produces predictions at all positions in parallel). A verification rule decides how many draft tokens to keep. If several are kept, the target has produced several tokens for the cost of about one step.

9. The acceptance rule, and why outputs do not change

Let p be the target's distribution at a position and q the draft's. The draft sampled token x from q. Accept it with probability min(1, p(x)/q(x)). If it is rejected, sample a replacement from the residual distribution max(0, p − q), normalised, and discard all later draft tokens. If all γ are accepted, sample one more token from the target's distribution at the next position, which the verification pass computed anyway. The rule is a form of rejection sampling: the probability of emitting x is q(x)·min(1, p(x)/q(x)) plus the probability of rejection times the residual's share for x, which works out to exactly p(x). So the emitted text is distributed exactly as if the target model had sampled alone. The lab checks this with p = [0.40, 0.25, 0.15, 0.10, 0.06, 0.04] and q = [0.30, 0.35, 0.10, 0.15, 0.05, 0.05]: over 200,000 trials the emitted distribution is [0.399, 0.250, 0.151, 0.100, 0.059, 0.040]. The acceptance probability per token is Σ min(p, q) = 0.84, matching the simulated 0.84. With greedy decoding the rule simplifies to: keep draft tokens while they match the target's argmax.

10. Expected speed-up, worked

If each draft token is accepted independently with probability α, a round produces 1 + (number of accepted tokens before the first rejection, capped at γ) tokens. Its expectation is

E[tokens per target pass] = (1 − α^(γ+1)) / (1 − α)

Worked: α = 0.8, γ = 4: (1 − 0.8⁵)/(1 − 0.8) = (1 − 0.32768)/0.2 = 3.36 tokens per target forward pass. The round also costs γ draft steps; if one draft step costs c = 5% of a target step, a round costs 1 + 4 × 0.05 = 1.2 target-step equivalents, so the speed-up is 3.36/1.2 = 2.8× (Leviathan et al.'s walltime-improvement formula, which assumes the verification pass costs about one normal step, true when decode is memory-bound). The lab's table shows the trade-offs: at α = 0.6, γ = 4 gives 1.92× and γ = 8 only 1.77× (drafts are wasted); at α = 0.9, γ = 8 gives 4.38×. Choose γ from the measured acceptance rate. The lab also simulates whole rounds at α = 0.8, γ = 4 and gets 3.36 tokens per pass, matching the formula.

11. Speculation variants

The draft need not be a separate model. Medusa adds several extra output heads to the target model itself, each predicting a token further ahead, and verifies their candidate continuations with a tree-structured attention pass; its authors report over 2.2× speed-up without a separate draft model. Related methods draft from a lightweight head on the target's hidden states, or from n-gram lookup in the prompt (effective when outputs copy from inputs, as in code editing or retrieval-augmented answers). All share the verify-in-parallel structure; they differ in where guesses come from and how much they cost.

12. Putting it together: sizing a deployment

A worked example ties the levers together. A chat service runs Llama 3 8B in bf16 on one 80 GB H100: weights 16.1 GB, leaving about 56 GB for KV cache at 90% utilisation. Conversations average 3,000 tokens of context; at 128 KiB per token (lm5) each holds 0.37 GiB, so about 140 can be active at once with paged allocation, against about 52 if each reserved 8,192 tokens contiguously. A decode step at batch 140 reads 16.1 GB of weights plus about 55 GB of cache: about 21 ms at 3.35 TB/s, about 47 tokens per second per user and about 6,600 tokens per second in total. If the latency target were 15 ms per token, the batch would have to be capped near 80. Prefix caching of the 1,500-token system prompt removes half the prefill for every request. An 8-bit KV cache would double concurrency or halve KV read time. This back-of-the-envelope model, built from lm5's formula and this lesson's levers, is what serving teams use before load testing confirms it.

13. Choosing a serving engine and configuration

In practice teams rarely implement these techniques themselves; they pick an engine (vLLM, SGLang, TensorRT-LLM, Text Generation Inference and others) and configure it. The decisions that matter are the ones this lesson explains: maximum number of concurrent sequences and maximum batched tokens per step (the throughput-latency dial), KV-cache memory fraction and cache data type, block size, whether prefix caching and chunked prefill are on and with what chunk size, tensor-parallel degree, quantisation of weights, and whether to enable speculative decoding and with which draft. Defaults are tuned for benchmarks, not for your traffic. A good process is to replay a sample of real traffic at increasing load, record TTFT, TPOT and goodput at each setting, and choose the configuration that meets latency targets at the lowest cost per token. Re-run it when the model, the hardware or the traffic mix changes.

14. Streaming and perceived latency

Users perceive latency differently from the metrics. Streaming tokens as they are generated makes a 10-second answer feel responsive if the first token arrives in 300 ms and tokens then flow faster than reading speed (roughly 5-10 tokens per second is comfortable to read). This is why TTFT targets are usually strict and TPOT targets are set relative to reading speed rather than as fast as possible. For non-streaming uses, such as an agent calling the model as a tool (lm16) or a batch job, total request latency or pure throughput is what matters, and the configuration should change accordingly: batch jobs can run at very large batch sizes and accept long per-token times for the lowest cost.

15. What to measure

Track TTFT and TPOT as distributions (p50, p95, p99), not averages; throughput and goodput; queue length and wait time; KV-cache utilisation and the number of preemptions (requests paused or recomputed because memory ran out); prefix-cache hit rate; speculative acceptance rate and accepted tokens per step if speculation is on; and tokens per second per GPU for cost. Load-test with realistic distributions of prompt and output lengths: results with fixed lengths are misleading because the waste continuous batching and paging remove comes precisely from variation.

Why verification is nearly free

A decode step at small batch reads all weights for one token per sequence. Verifying γ + 1 positions per sequence reads the same weights once and does γ + 1 times the arithmetic. As long as the step stays memory-bound, the extra arithmetic fits in the idle compute, so the step takes about the same time. Attention to the KV cache adds a little, and the draft tokens' own keys and values are appended to the cache (rejected ones are rolled back). The argument fails at large batch: with 128 sequences each verifying 5 positions, the step processes 640 tokens, approaching the compute-bound regime where extra positions cost proportionally more. That is the precise sense in which speculative decoding trades spare compute for fewer sequential steps.

Acceptance rate as a distance between models

The acceptance probability for one token, Σ min(p(x), q(x)), equals 1 minus the total variation distance between the target and draft distributions: identical distributions accept everything, disjoint ones nothing. So α measures how well the draft imitates the target on your traffic, which depends on domain (drafts do well on predictable text such as code boilerplate), on temperature (higher temperatures flatten both distributions in ways that may reduce overlap), and on how the draft was trained. Distilling the draft on the target's own outputs is the standard way to raise α. Measured acceptance rates are what decide γ and whether speculation is worth enabling.

Scheduling policies and fairness

A continuous-batching scheduler decides at every step which waiting requests to admit and, under memory pressure, which running ones to pause. First-come-first-served is simple but lets one huge request block many small ones; shortest-job-first lowers average latency but output lengths are unknown in advance (systems predict them, or use prompt length as a proxy); priority classes protect interactive traffic from batch jobs. Preemption can swap a paused request's KV blocks to CPU memory (costs PCIe bandwidth) or discard them and recompute later (costs prefill compute); vLLM supports both. These policies are where tail latency is won or lost under load.

Prefix caching across replicas

A prefix cache only helps if the request lands on the replica that holds the prefix. With many replicas behind a load balancer, random routing scatters conversations and destroys hit rates. Cache-aware routing hashes the prefix (or the conversation ID) to choose a replica, trading some load balance for hits; more elaborate systems maintain a global index of cached prefixes. The same consideration applies to API providers' prompt caching: hits depend on requests sharing an exact token prefix, so applications should put static content (instructions, tools, documents) first and variable content last.

Multi-model and multi-adapter serving

Serving many fine-tuned variants multiplies the memory problem unless they share a base. With LoRA adapters (lm11), one base model plus many small adapters can be served in one continuous batch, each request applying its own adapter through batched low-rank kernels; adapters are cached on the GPU and loaded on demand. This is how platforms host thousands of customer fine-tunes economically. The same paging ideas apply to adapter weights, which are swapped like KV blocks.

Little's law for LLM servers

Queueing theory gives a useful sanity check. Little's law says the average number of requests in a system equals the arrival rate times the average time each spends in it. If requests arrive at 10 per second and each takes 8 seconds (prefill plus a 300-token answer at about 25 ms per token), about 80 requests are in flight on average, so the server needs KV memory and batch capacity for about 80 concurrent sequences, plus headroom for bursts. If it has room for only 50, queues grow without bound until requests time out. Combining this with lm5's KV arithmetic gives a quick capacity estimate before any load test: concurrency needed = arrival rate × request duration, and memory needed = concurrency × KV bytes per sequence.

The economics in one formula

Cost per output token ≈ (GPU cost per second) / (tokens per second). Tokens per second ≈ batch size / step time, and step time ≈ (weight bytes + Σ KV bytes of the batch) / bandwidth at small to moderate batch. So the levers act on clear terms: quantised weights shrink weight bytes; GQA and quantised caches shrink KV bytes; paging and prefix sharing let the batch grow within memory; continuous batching keeps the batch full; speculation divides the number of steps. Writing this out, with real numbers, is the most useful thing to do before buying hardware or choosing a provider.

The public case: vLLM and PagedAttention (Kwon et al., SOSP 2023)

In 2023, a team at UC Berkeley noticed that LLM serving throughput was limited not by compute but by how many requests fit in memory at once, and that existing systems were wasting most of that memory. Profiling showed only 20.4% to 38.2% of KV-cache memory in existing systems held actual token states; the rest was lost to reservations for maximum sequence length, internal fragmentation and external fragmentation. Their answer, PagedAttention, applied the classic operating-system idea of paging: store each sequence's KV cache in fixed-size blocks that need not be contiguous, allocate them on demand, map them through block tables, and share identical blocks between sequences with copy-on-write. They built vLLM around it, with continuous batching and a scheduler that preempts by swapping or recomputation.

The reported results: near-zero waste in KV-cache memory; flexible sharing of KV cache within and across requests, saving up to 55% of memory for parallel sampling and beam search; and 2-4× higher throughput than FasterTransformer and Orca at the same level of latency, with larger gains for longer sequences, larger models and more complex decoding algorithms. vLLM was released as open source and became one of the most widely used serving engines, and paged KV memory became standard across serving systems. Speculative decoding followed a parallel path from research to production: Leviathan et al. reported 2-3× on T5-XXL with identical outputs and Chen et al. 2-2.5× on Chinchilla 70B, and both draft-model and head-based speculation are now options in common engines.

Failure modes in production

Latency spikes from long prompts. A few very long prompts stall decode for everyone. Enable chunked prefill or separate long-context traffic.

Preemption storms. Under bursty load the KV pool runs out, sequences are swapped or recomputed repeatedly, and throughput collapses. Cap concurrency, quantise the cache, add capacity, and alert on preemption rate.

Low prefix-cache hit rate. Variable content (timestamps, user names) placed before static instructions breaks prefix matching; random routing scatters conversations. Reorder prompts and use cache-aware routing.

Speculation that slows things down. Enabled at high batch or with a poorly matched draft, it adds work without enough accepted tokens. Monitor acceptance rate and compare TPOT with speculation on and off at production load.

Benchmarks that lie. Load tests with fixed prompt and output lengths hide the variation that batching and paging exploit and mislead capacity planning. Replay real traffic distributions.

Batch (offline) inference

Not all inference is interactive. Classifying a million documents, generating synthetic training data or running an evaluation suite has no per-token latency target, only a deadline and a budget. These jobs should run at the largest batch sizes the KV memory allows, with prefix caching for shared instructions, and on cheaper or pre-emptible capacity. Providers offer discounted batch APIs for exactly this reason: they can schedule the work into idle capacity at high batch sizes. Separating offline work from interactive traffic protects interactive latency and lowers the cost of both.

Why this case matters for engineers who do not run GPUs

Even teams that only call hosted APIs feel these mechanisms. Prices per token reflect them (output tokens cost more than input tokens because they occupy decode slots; cached input tokens cost less because prefill is skipped), rate limits reflect KV capacity, and latency rises at busy times because batches grow. Structuring prompts so that static content comes first (to hit provider prompt caches), keeping outputs no longer than needed, and streaming responses are the application-level counterparts of the serving techniques described here.

What to monitor

TTFT and TPOT percentiles, throughput and goodput, queue depth, KV utilisation, preemptions, prefix-cache hit rate, speculative acceptance rate, and cost per million tokens. Alert on percentiles and preemptions, not averages.

Goal: verify that speculative sampling reproduces the target distribution, tabulate the expected speed-up for different acceptance rates and draft lengths, simulate static versus continuous batching on realistic output lengths, compare contiguous and paged KV allocation, and compute prefix-cache savings. NumPy only, a few seconds.

import numpy as np
rng = np.random.default_rng(0)

# ---- 1. speculative sampling keeps the target distribution exactly
p = np.array([0.40, 0.25, 0.15, 0.10, 0.06, 0.04])     # target model's next-token distribution
q = np.array([0.30, 0.35, 0.10, 0.15, 0.05, 0.05])     # cheaper draft model's distribution
accept_rate = np.minimum(p, q).sum()
def spec_step():
    x = rng.choice(6, p=q)                                   # draft proposes x
    if rng.random() < min(1, p[x] / q[x]): return x, True    # accept with prob min(1, p/q)
    r = np.maximum(p - q, 0); return rng.choice(6, p=r / r.sum()), False   # else resample from the residual
draws = [spec_step() for _ in range(200_000)]
emp = np.bincount([d[0] for d in draws], minlength=6) / len(draws)
print("target p        ", p, "\nemitted (spec.)  ", emp.round(3), "\nacceptance: formula sum(min(p,q)) =", round(accept_rate, 3),
      " simulated =", round(np.mean([d[1] for d in draws]), 3))

# ---- 2. expected tokens per target forward pass and the speed-up, as a function of acceptance rate
def tokens_per_pass(a, g): return (1 - a ** (g + 1)) / (1 - a)
def speedup(a, g, c): return tokens_per_pass(a, g) / (g * c + 1)   # c = draft cost relative to the target
print("\n alpha  gamma  tokens/target pass  speed-up (draft cost c=0.05)")
for a in (0.6, 0.8, 0.9):
    for g in (2, 4, 8):
        print(f"  {a:.1f}    {g}        {tokens_per_pass(a, g):5.2f}               {speedup(a, g, 0.05):4.2f}x")
a, g = 0.8, 4                                                # check by simulating whole speculation rounds
sim = [min(rng.geometric(1 - a) - 1, g) + 1 for _ in range(100_000)]   # accepted drafts (capped at g) + 1 target token
print(f"simulated tokens/pass at alpha=0.8, gamma=4: {np.mean(sim):.2f} (formula {tokens_per_pass(a, g):.2f})")

# ---- 3. static versus continuous batching (one decode step per time unit, 8 slots)
lengths = np.clip(rng.lognormal(5.0, 0.8, 400).astype(int), 10, 2000)   # output tokens per request
def static(lengths, B=8):
    t, lat = 0, []
    for i in range(0, len(lengths), B):
        batch = lengths[i:i + B]; t += batch.max(); lat += [t] * len(batch)   # everyone waits for the longest
    return t, np.mean(lat)
def continuous(lengths, B=8):
    queue, slots, t, lat = list(lengths), [], 0, []
    while queue or slots:
        while queue and len(slots) < B: slots.append(queue.pop(0))
        t += 1; slots = [s - 1 for s in slots]
        lat += [t] * sum(s == 0 for s in slots); slots = [s for s in slots if s > 0]
    return t, np.mean(lat)
ts, ls = static(lengths); tc, lc = continuous(lengths)
print(f"\n{len(lengths)} requests, {lengths.sum():,} output tokens, 8 slots")
print(f"static batching:     {ts:7,} steps -> {lengths.sum()/ts:.2f} tokens/step, mean completion step {ls:,.0f}")
print(f"continuous batching: {tc:7,} steps -> {lengths.sum()/tc:.2f} tokens/step, mean completion step {lc:,.0f}")

# ---- 4. KV-cache memory: reserve the maximum length up front versus paged blocks of 16 tokens
prompt = rng.integers(50, 1500, 400); total = prompt + lengths
reserved_contig = 2048 * len(total)
paged = (np.ceil(total / 16) * 16).sum()
print(f"\nKV slots actually used {total.sum():,}; contiguous max-length reservation {reserved_contig:,} "
      f"({total.sum()/reserved_contig:.1%} utilised); paged {paged:,.0f} ({total.sum()/paged:.1%} utilised)")

# ---- 5. prefix caching: a shared 2,000-token system prompt across 100 requests with 200-token questions
shared, own, n = 2000, 200, 100
print(f"prefill tokens without prefix cache {n*(shared+own):,}; with cache {shared + n*own:,} "
      f"({1 - (shared + n*own)/(n*(shared+own)):.0%} less prefill)")

Compute — is speculative decoding worth it here?

A 70B target model's decode step takes 30 ms at batch 1. A 1B draft takes 2 ms per token. Measured acceptance rate on your traffic is 0.7. Should you use γ = 3 or γ = 6, and what latency per token should you expect?

Answer

c = 2/30 = 0.067. γ = 3: tokens per pass = (1 − 0.7⁴)/0.3 = (1 − 0.2401)/0.3 = 2.53; round cost = 30 + 3 × 2 = 36 ms; 36/2.53 = 14.2 ms per token (2.1× faster than 30 ms). γ = 6: (1 − 0.7⁷)/0.3 = (1 − 0.0824)/0.3 = 3.06; round cost 30 + 12 = 42 ms; 42/3.06 = 13.7 ms per token (2.2×). γ = 6 is marginally better; γ = 4 or 5 is probably near the optimum, so measure around there. Caveats: at higher batch the verification pass gets more expensive and the gain shrinks, and acceptance varies by traffic type, so monitor it.

Diagnose — throughput is fine, users are not

After moving to a new serving engine, tokens per second per GPU doubled, but users complain that answers sometimes freeze for a second mid-stream. What do you check?

Answer

Mid-stream freezes are step-time spikes, which averages and throughput hide. Check the TPOT p99 and the step-time distribution. Likely causes: long prompts being prefilled in one piece (enable chunked prefill, tune the chunk size, or route long prompts to separate replicas); KV memory exhaustion causing preemption (look at preemption counts; lower the maximum batch, quantise the cache); and a maximum batch size set for throughput rather than the latency target (cap it). Re-run the load test with realistic prompt lengths and judge it by goodput at the latency target, not raw throughput.
