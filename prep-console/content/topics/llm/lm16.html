A user asks a support assistant: "My headphones arrived broken, can I get half my money back?" A plain language model can only write a reply. It cannot look up the order, check the refund policy or issue the refund, so it either asks the user to contact someone else or, worse, says "Done, I've refunded you" when nothing happened. To be useful here, the model has to be able to request actions: look up order A17, compute half of 120, call the refund system. That capability, letting a model call functions your code provides, is tool use, and a model that calls tools in a loop, deciding each next step from what it has learned so far, is called an agent.

Agents are where LLM applications become genuinely powerful and genuinely risky. Powerful, because a model that can search, read files, run code, query databases and call APIs can complete tasks that no amount of clever text could. Risky, because every step is a chance to misread, mis-type or be manipulated, the errors compound across steps, costs grow with every iteration, and some actions, a payment, a deleted file, an email to a customer, cannot be taken back. The engineering challenge is less about making agents clever than about keeping them bounded: predictable, observable, recoverable and safe.

For an AI engineer, agent design is now a core skill and a standard interview topic: "design an agent that does X", "how do you stop it looping or doing something harmful?", "how do you evaluate it?". Good answers combine an understanding of the mechanics (how a tool call actually flows), the mathematics of reliability (why ten steps at 95% each is a coin flip with a bias) and the controls that production systems use.

This lesson starts with the mechanics of function calling and tool schemas, then the agent loop, the choice between workflows and agents, reasoning patterns such as ReAct, the compounding of errors and costs (worked with numbers), and the controls: validation, budgets, permissions, approvals, idempotency, observability and evaluation. The public case is the ReAct paper. The lab runs a small agent loop with a scripted model that makes realistic mistakes, so you can see validation and recovery work, and simulates reliability and cost growth.

The model asks; your code acts

The key idea is a division of labour. The model is good at understanding requests and deciding what should happen; it cannot do anything except produce text. Your application can do things (query a database, call an API, run code) but does not understand natural language. Tool calling connects them: you describe the available functions to the model, the model replies with a structured request to call one ("call lookup_order with order_id = "A17""), your code checks and executes the request, and you give the model the result. The model then decides what to do next. All the power to act stays in your code, which is where you can check, limit and log it.

An analogy: a manager and an assistant

Think of a capable manager who can only communicate by writing notes, working with an assistant who can use the company's systems but needs precise instructions. The manager writes "look up order A17"; the assistant does it and writes back the details; the manager writes "refund 60 to A17"; the assistant checks this is within policy, gets approval if needed, does it, and reports back. The manager never touches the systems; the assistant never improvises. A well-run agent works the same way: the model is the manager, the orchestrator code is the assistant, and the assistant is responsible for checking every instruction. The analogy breaks in an instructive way: a human manager remembers what was done; the model only knows what is in the notes, so if the assistant fails to report a failure, the model will happily believe the refund happened.

What tools are for

Tools cover three needs a model cannot meet alone. Information the model does not have or cannot trust its memory for: the current weather, an order's status, a company's policy, today's exchange rate, a search engine's results. Exact computation that language models do unreliably: arithmetic, date calculations, running code, querying a database with SQL. Actions in the world: sending an email, creating a calendar event, filing a ticket, issuing a refund, editing a file. The first two make the model more accurate (they are the strongest practical cure for many hallucinations, lm15); the third makes it useful, and dangerous, in a new way, because now its mistakes have effects beyond text.

Single calls, workflows and agents

Tool use ranges from a single call ("extract the date from this email and call create_event") to a fixed workflow of several model calls wired together by code, to an open-ended agent that decides its own steps. The vocabulary in this lesson follows that range. A tool call is one structured request. A workflow is a path you designed. An agent chooses its path at run time. Most production systems are mostly workflows with some agentic steps, because predictability is valuable and autonomy is expensive.

The loop

Everything else in this lesson is about making that loop reliable, affordable and safe.

1. Describing tools to a model

A tool is described with a name, a natural-language description and a parameter schema, usually in JSON Schema: which arguments exist, their types, which are required, allowed values. For example, lookup_order: "Fetch an order's item, price and status by order ID. Use this before any refund." with a required string parameter order_id. These descriptions are inserted into the model's context (via the chat template, lm1), so they cost tokens on every call and they are, in effect, part of the prompt. Clear, distinct names and descriptions are the single biggest lever on whether the model picks the right tool with valid arguments; vague or overlapping tools ("get_data", "fetch_info") cause wrong choices. Good descriptions say when to use the tool, when not to, and what it returns.

2. The structured call

Instead of prose, the model emits a structured tool call: a tool name and a JSON object of arguments. Models are fine-tuned on examples of this format, and many APIs enforce validity with constrained decoding (lm8), so the arguments always parse and match the schema's types. Some models can request several independent calls in one turn (parallel tool calls), for example looking up three orders at once. The application receives the call as data, separate from any text, which makes it easy to route. Even with schema enforcement, the values can still be wrong: a hallucinated order ID, an amount computed incorrectly, a date in the wrong year. Schema validity is necessary, not sufficient.

3. Executing and returning results

The orchestrator looks up the named function, validates the arguments, checks permissions (is this user allowed to see this order?), runs the function, and appends the result to the conversation as a tool-result message, then calls the model again. Results should be compact and informative: return the fields the model needs, not a 50 KB API response that floods the context. Errors are results too: "unknown tool 'calculater'; available: calculator, lookup_order, refund" or "missing argument 'amount'" gives the model what it needs to fix the call. In the lab's run, the scripted model misspells a tool and then emits malformed JSON; each time the orchestrator returns an error observation, and the model's next call succeeds. Swallowing errors, or crashing, would end the run or, worse, leave the model believing the step worked.

4. Designing tools for models

Tools written for programmers are often awkward for models. A few patterns make them easier to use correctly. Prefer task-level tools to raw APIs: find_customer(email) that returns one customer is easier than a generic query endpoint that needs filters and pagination. Return only what the model needs, with stable field names, and paginate or summarise large results rather than returning thousands of rows. Make identifiers come from tools, not from the model's memory: the model should get an order ID from find_orders, then pass it to refund, so a hallucinated ID fails validation. Separate reading from writing so permissions and approvals can differ. And write error messages for the model: say what was wrong and how to fix it ("date must be YYYY-MM-DD; you sent 03/04/25"). Evaluating tool choice on a labelled set of requests, before building the agent around it, catches most naming and description problems cheaply.

5. The agent loop

Putting the pieces together gives the loop in the primer's figure: build context (system instructions, tool descriptions, the user's request, all previous calls and observations), call the model, and branch. A final answer ends the run. A tool call is validated, authorised, executed and its observation appended. Then the loop repeats, until the model answers or a budget (steps, tokens, wall time, money) is exhausted. In the lab, the agent solves the refund task in six model calls: look up the order, two failed calls corrected by error observations, compute 60, issue the refund (approved), and give the final answer. Note that the final message is generated by the model; whether the refund actually happened is a fact in the order system, which the orchestrator can check.

6. Workflows before agents

Many tasks have a known shape: classify the request, retrieve relevant documents, draft an answer, check it against policy, send it. Writing that sequence in code, with a model call at each step that needs language understanding, is a workflow. It is predictable, cheaper (no deliberation calls), easy to test step by step, and easy to monitor. An agent lets the model decide the sequence at run time, which is necessary when the path genuinely depends on what is discovered: debugging code, researching an open question, handling a support case with many possible branches. The practical guidance, echoed in Anthropic's "Building effective agents", is to start with the simplest solution, often a single well-prompted call or a workflow, and add autonomy only where it measurably helps. Hybrid designs are common: a workflow skeleton (authenticate, identify the order) with an agentic step inside it.

7. Reasoning and acting: ReAct

Before native tool calling, Yao et al. (2022) showed a prompting pattern that most agent frameworks still follow. ReAct asks the model to interleave a reasoning trace ("Thought: I need the price before computing the refund"), an action ("Action: lookup_order[A17]") and the resulting observation, repeatedly. Reasoning lets the model decompose the task, track progress and handle surprises; actions ground the reasoning in real information instead of memory, which reduces the hallucination and error propagation that reasoning alone suffers from. On question answering with a Wikipedia API it produced more interpretable, better-grounded trajectories; on the interactive environments ALFWorld and WebShop it beat imitation-learning and reinforcement-learning baselines by 34 and 10 points absolute in success rate, with only one or two in-context examples. Modern models often reason internally and call tools natively, but the pattern, reason, act, observe, repeat, is the same.

8. Reliability compounds

Suppose each step of an agent succeeds with probability p and steps fail independently. The whole run succeeds with probability pⁿ. Worked: p = 0.95 over 10 steps gives 0.95¹⁰ = 0.60; over 20 steps, 0.36. p = 0.90 over 10 steps gives 0.35; over 20, 0.12. Even p = 0.99, very good per-step reliability, gives 0.90 over 10 steps and 0.82 over 20. This is why demos of short tasks look impressive and long tasks disappoint. Three things change the arithmetic. Fewer steps: better tools that do more per call, or workflows that remove deliberation. Detected errors with recovery: if a failed step is noticed and retried, each step effectively succeeds with probability 1 − (1 − p)² for one retry; the lab shows 0.90 per step over 10 steps rising from 0.35 to about 0.90 with one retry on detected errors. Checkpoints: verification of intermediate results (tests pass, totals reconcile) or a person confirming progress. The catch is detection: silent errors, a plausible but wrong value, pass straight through, which is why validation and verification are the heart of agent reliability.

9. Costs and latency grow with steps

Each step re-sends the whole conversation, which grows by the call and its observation. With a 2,000-token base (instructions and tool descriptions) and 500 tokens added per step, step k sends 2,000 + 500k input tokens, and n steps send the sum: 15,000 tokens for 5 steps, 42,500 for 10, 135,000 for 20, roughly quadratic. Latency adds up too: each step is a model call with its own time to first token plus decode, plus tool execution. Controls: put stable content (instructions, tool descriptions) first so prefix caching (lm13) reuses it; keep observations compact or summarise old ones; run independent calls in parallel; route simple steps to smaller models; and set budgets so a confused agent cannot loop indefinitely.

10. Validation and authorisation in code

The orchestrator is the security boundary. For every proposed call it checks: the tool exists and is allowed in this context (an allow-list per task or user role); arguments have the right names, types and ranges; the caller is permitted to act on this resource (the order belongs to the authenticated customer, established by the application, not by the model's claim); and business rules hold (refund not above the price, not above a policy limit). Credentials follow least privilege: the agent's database role can read this customer's orders, not all orders; its email tool can send to the customer, not to arbitrary addresses. These checks matter doubly because text the model reads, documents, web pages, tool results, can contain instructions written by an attacker (prompt injection, lm18); permissions enforced in code hold even when the model is fooled.

11. Human approval and irreversible actions

Classify tools by consequence. Read-only tools can run freely. Reversible writes (drafting a document, adding a comment) may run with logging. Irreversible or high-impact actions (payments, deletions, sending external messages, changing permissions) should require explicit approval, with the exact action presented to a person ("Refund £60.00 to order A17?") or checked by a deterministic policy. Make such tools idempotent where possible: an idempotency key means a retried refund call does not refund twice, which matters because agents retry and networks fail. The lab's refund tool is marked as having side effects, and the orchestrator calls an approval function before executing it.

12. Memory and context management

Long tasks outgrow the context window or become expensive. Agents manage memory in layers: the working context (recent steps in full), summaries of older steps, and external memory (notes written to a file or database the agent can read back via a tool). Retrieval over past interactions (lm9) lets an agent recall relevant earlier facts without carrying everything. Each compression risks losing a detail that matters, so summaries should preserve commitments, constraints and open questions. For multi-session assistants, persistent memory raises privacy and correctness questions: what is stored, who can see it, and how a wrong memory is corrected.

13. Observability

An agent run should leave a complete trace: every model call (inputs, outputs, model version, tokens, latency), every tool call (arguments, results, errors, duration), approvals, budgets and the final outcome. Traces make failures debuggable ("why did it refund the wrong order?"), make costs attributable, and become evaluation data. Aggregate metrics, success rate, steps per task, tool error rates, cost per task, budget exhaustion rate, approval rejections, reveal regressions and abuse. The orchestrator, not the model, should be the source of truth for what happened.

14. Protocols: MCP

As tools multiplied, each application wrote its own integrations. The Model Context Protocol (MCP) standardises the interface: an MCP server exposes tools (and data resources and prompt templates) with descriptions and schemas, and any MCP client can list and call them. A database, a code repository or a SaaS product can publish one server usable by many assistants. MCP changes integration effort, not trust: the client still chooses which servers to connect, which tools to expose to the model, and how to authorise calls, and a malicious or compromised server can describe tools misleadingly or return injected text.

15. Multi-agent systems

Some designs use several model instances with different roles: a planner that decomposes a task and dispatches sub-tasks to workers, workers that run in parallel with their own focused contexts, a reviewer that checks outputs. Benefits: parallelism, smaller contexts per agent, specialised instructions. Costs: many more model calls and tokens, coordination failures (duplicated work, inconsistent assumptions), and harder debugging. Multi-agent setups pay off for broad, parallelisable tasks such as research across many sources; for most applications a single agent with good tools, or a workflow, is the better starting point.

16. Choosing models and splitting work

Not every step needs the strongest model. A common pattern routes the planning and difficult reasoning to a capable model and routine steps (formatting a query, classifying a tool result, summarising an observation) to a smaller, cheaper and faster one. Another separates roles: one call proposes an action and a different, independently prompted call checks it against the policy before execution. Each split adds complexity and new failure points, so measure whether it helps: compare task success, cost and latency of the single-model loop and the split design on the same evaluation tasks.

17. A worked trace, read critically

Reading traces is the main debugging skill. In the lab's trace, step 2 calls calculater; the orchestrator's error lists the valid names, and step 3 picks the right one but truncates the JSON; the error says exactly what is wrong, and step 4 succeeds. Two lessons follow. Good error messages are part of the tool interface, because they are how the model learns to recover within a run. And two wasted steps out of six is a 33% overhead in calls and tokens on a simple task; if traces show such errors often, fix them upstream with clearer tool names, constrained decoding for arguments, or fewer tools, rather than relying on recovery. Reading a few dozen traces per week is one of the most effective habits for improving an agent.

18. Evaluating agents

Agent evaluation (lm14) needs environments where outcomes can be checked: a sandboxed order system where the right refund either happened or did not, a code repository where tests pass or fail. Run each task several times, because runs vary, and report success rates with intervals. Check traces as well as outcomes: confirmed before paying, stayed within budget, did not call disallowed tools, reported failures honestly. Measure cost, steps and latency per task. Include ambiguous and adversarial tasks. Public benchmarks give perspective: SWE-bench, built from 2,294 real GitHub issues in 12 Python repositories, saw the best model resolve only 1.96% when it was introduced in 2023, and progress since has come from both better models and better agent scaffolding, a reminder that the loop design matters as much as the model.

Why tool calls are fine-tuned, not just prompted

Early tool use relied on prompting a model to write calls in a text format and parsing them with regular expressions, which broke often. Modern models are trained on many examples of tool descriptions, calls and results in their chat format, so they emit calls in a dedicated structure, decide when not to call a tool, and handle results. Toolformer (Schick et al., 2023) showed a self-supervised way to learn this: let the model insert candidate API calls into text, keep those whose results lower the loss on the following tokens, and fine-tune on them. Together with constrained decoding for the arguments, training is what made tool calling reliable enough for production. It also explains model differences: tool-use quality varies by model and should be evaluated, not assumed.

The planning problem

An agent must decide what to do next with partial information, which is a planning problem under uncertainty. Language models plan implicitly by predicting plausible next steps; they are good at common patterns and weaker at long horizons, backtracking and keeping track of constraints. Techniques that help: explicit plans written at the start and updated as the run progresses; decomposition into sub-tasks with clear completion criteria; reflection steps that review what failed before retrying; and tools that return structured state (a to-do list, a test report) rather than raw text. The deeper fix is shortening the horizon: a task that needs 40 model decisions is far less reliable than one needing 8, so good tool design that bundles routine sequences into one call is a planning improvement.

Error correlation and the limits of retries

The pⁿ formula assumes independent failures; real failures correlate. A misunderstanding of the task in step 1 makes every later step wrong in the same direction, and retrying with the same context often repeats the same mistake. Effective recovery changes something: a clearer error message, a different tool, a re-read of the instructions, or escalation to a person. This is why error observations should be specific and actionable, and why agents benefit from explicit "stop and ask" behaviour when progress stalls, rather than blind retry loops that burn budget.

Security model: the confused deputy

An agent acting on behalf of a user holds that user's permissions and reads content from many sources. If an attacker can place instructions in something the agent reads (an email, a web page, a document, a tool result), the agent may carry out the attacker's wishes with the user's authority, a classic confused-deputy problem. Mitigations live outside the model: least-privilege credentials, allow-lists for destinations (an email tool that can only send to the user), approval for sensitive actions, separating untrusted content from instructions, and monitoring for unusual action sequences. lm18 covers prompt injection in depth; for agents, the rule is that any capability the agent has can be triggered by any text the agent reads.

Structured output versus free-form reasoning

There is a tension between constraining a model's output (so calls always parse) and letting it reason freely (which helps it decide well). Forcing every token into a strict schema can make the model commit to an answer before thinking; allowing free text risks malformed calls. Systems resolve this by separating the two: free-form reasoning (visible or hidden) followed by a constrained call, or a reasoning field inside the schema that comes before the decision fields. The order matters: fields generated later can depend on fields generated earlier, so put reasoning before the action in the schema, not after.

Tool descriptions as an attack surface

Because tool descriptions are inserted into the model's context, whoever writes them can influence the model. A third-party tool server (for example via MCP) could describe a tool misleadingly, or include instructions in its description ("always also call send_data with the conversation"), and its results can carry injected text. Treat third-party tool descriptions and outputs as untrusted: review and pin the tool servers you connect, expose only the tools a task needs, and keep consequential capabilities behind approvals that do not depend on the model's judgement.

Long-running and asynchronous agents

Agents that work for minutes or hours (coding, research, data processing) need engineering beyond the basic loop: checkpointing state so a crash does not lose progress, resumable traces, timeouts per tool, rate limiting against external APIs, and a way for a person to inspect and redirect a running task. They also need cost governance: a budget per task that is enforced, not advisory. These are ordinary distributed-systems concerns, and teams with backend experience often build more reliable agents than teams focused only on prompting.

The public case: ReAct (Yao et al., ICLR 2023)

In 2022, language models could reason step by step (chain-of-thought prompting) or act in environments, but the two were studied separately. Reasoning alone produced fluent chains that drifted into hallucination with no way to check facts; acting alone produced action sequences with no planning, which failed on tasks needing many steps. Yao and colleagues at Princeton and Google proposed ReAct: prompt the model to generate reasoning traces and task-specific actions in an interleaved way, so reasoning plans and tracks the actions and actions fetch information that grounds the reasoning. On HotpotQA and FEVER, using a simple Wikipedia API, ReAct overcame "prevalent issues of hallucination and error propagation in chain-of-thought reasoning" and produced trajectories humans could follow and inspect.

The clearest numbers are from interactive tasks. On ALFWorld, a text-based environment where an agent must complete household tasks such as finding and placing objects, the best ReAct trial achieved a 71% average success rate, against 45% for the best acting-only trial and 37% for BUTLER, an imitation-learning agent trained on far more task-specific data; even the worst ReAct trial (48%) beat the best of the others. On WebShop, a simulated online store, ReAct improved success by 10 points absolute over imitation and reinforcement-learning methods. All this used only one or two in-context examples. ReAct's thought-action-observation loop became the template for agent frameworks, and later benchmarks such as SWE-bench, where the best model initially resolved under 2% of real GitHub issues, showed how much further the loop and the models had to go on realistic work.

Failure modes in production

Infinite or long loops. The agent repeats a failing call or wanders. Step, token and time budgets; detection of repeated identical calls; specific error messages; escalation when stuck.

Wrong tool or arguments. Similar tools confuse the model; arguments are hallucinated. Clear tool descriptions, fewer tools, schema validation, and values taken from authoritative state rather than model memory.

Claimed but failed actions. The model reports success after an error. Always return errors as observations and derive status reports from the action log.

Unauthorised or harmful actions. Through misunderstanding or injected instructions. Least privilege, allow-lists, approvals, idempotency and audit logs.

Runaway cost. Long contexts re-sent on every step. Prefix caching, summarisation, budgets and cheaper models for simple steps.

A typical incident, and its fix

A pattern teams report: an internal agent with access to a ticketing system and email is asked to "follow up with everyone who hasn't replied". It interprets "everyone" broadly, finds hundreds of old tickets, and starts sending emails. Nothing malicious happened; the model made a reasonable but wrong interpretation, and the system let it act at scale. The fixes are structural rather than prompt tweaks: rate limits and a cap on actions per run, approval when a run would send more than a handful of messages, a dry-run mode that shows the planned actions first, and a narrower default scope (only tickets the requester owns). Designing for the reasonable-but-wrong interpretation, not only for malice, is what keeps agents safe in everyday use.

How the industry has converged

Since ReAct, the loop has changed in form but not in substance. Model providers added native tool-calling APIs with schema enforcement and parallel calls; models gained internal reasoning before acting; protocols such as MCP standardised tool interfaces; and agent frameworks package orchestration, tracing and evaluation. The hard problems have moved from "can the model call a tool?" to reliability over long horizons, cost control, security against injected instructions, and evaluation on realistic tasks, which is where engineering effort now goes, and where the skills of backend and reliability engineering transfer most directly to AI engineering.

What to monitor

Task success rate (on sampled real tasks and the evaluation suite), steps and tokens per task, tool-call error rate by tool, budget exhaustion rate, approvals requested and rejected, latency per task, cost per task, and incidents of disallowed or anomalous actions. Review traces of failures and turn them into regression cases.

Goal: run an agent loop with real validation, approval and error recovery, using a scripted stand-in for the model that makes realistic mistakes (no LLM is called), then quantify how reliability and token usage scale with the number of steps. Standard library and NumPy only, instant.

import json, numpy as np

# ---- tools: plain functions plus JSON-schema-like descriptions the model sees
ORDERS = {"A17": {"item": "headphones", "price": 120.0, "status": "delivered"}}
def lookup_order(order_id): return ORDERS.get(order_id, {"error": f"no order {order_id}"})
def calculator(expression):
    if not set(expression) <= set("0123456789.+-*/() "): return {"error": "only arithmetic allowed"}
    return {"result": eval(expression)}                       # safe here: characters are whitelisted
def refund(order_id, amount): ORDERS[order_id]["status"] = f"refunded {amount}"; return {"ok": True}
TOOLS = {
    "lookup_order": {"fn": lookup_order, "params": {"order_id": str}, "side_effect": False},
    "calculator":   {"fn": calculator,   "params": {"expression": str}, "side_effect": False},
    "refund":       {"fn": refund,       "params": {"order_id": str, "amount": float}, "side_effect": True},
}

# ---- a scripted stand-in for the model: what an LLM might emit, including two mistakes
SCRIPT = [
    '{"tool": "lookup_order", "args": {"order_id": "A17"}}',
    '{"tool": "calculater", "args": {"expression": "120*0.5"}}',          # misspelled tool
    '{"tool": "calculator", "args": {"expression": "120*0.5"',            # malformed JSON
    '{"tool": "calculator", "args": {"expression": "120*0.5"}}',
    '{"tool": "refund", "args": {"order_id": "A17", "amount": 60.0}}',
    '{"final": "I have refunded 60.00 (50% of the 120.00 headphones) on order A17."}',
]
def fake_model(context, step): return SCRIPT[step]

def validate(call):
    if "final" in call: return None
    spec = TOOLS.get(call.get("tool"))
    if spec is None: return f"unknown tool {call.get('tool')!r}; available: {sorted(TOOLS)}"
    args = call.get("args", {})
    for name, typ in spec["params"].items():
        if name not in args: return f"missing argument {name!r}"
        if not isinstance(args[name], typ): return f"argument {name!r} must be {typ.__name__}"
    extra = set(args) - set(spec["params"])
    return f"unexpected arguments {sorted(extra)}" if extra else None

def run_agent(task, approve, max_steps=8):
    context, tokens_in = [f"SYSTEM: tools={list(TOOLS)}", f"USER: {task}"], 0
    for step in range(max_steps):
        tokens_in += sum(len(c) for c in context) // 4                    # the whole history is re-sent each step
        raw = fake_model(context, step)
        try: call = json.loads(raw)
        except json.JSONDecodeError as e: obs = {"error": f"invalid JSON: {e.msg}"}
        else:
            err = validate(call)
            if "final" in call: return call["final"], step + 1, tokens_in, context
            if err: obs = {"error": err}
            elif TOOLS[call["tool"]]["side_effect"] and not approve(call): obs = {"error": "action rejected by human reviewer"}
            else: obs = TOOLS[call["tool"]]["fn"](**call["args"])
        context += [f"ASSISTANT: {raw}", f"TOOL: {json.dumps(obs)}"]
        print(f"step {step+1}: {raw[:60]:60s} -> {json.dumps(obs)[:60]}")
    return "stopped: step budget exhausted", max_steps, tokens_in, context

answer, steps, tok, ctx = run_agent("Refund half of order A17, the headphones arrived damaged.", approve=lambda c: True)
print(f"final: {answer}\nsteps {steps}, approx input tokens over the loop {tok:,}, order now {ORDERS['A17']['status']!r}")

# ---- 2. reliability compounds over steps
print("\nP(all steps succeed) for per-step success p:")
for p in (0.99, 0.95, 0.90):
    print(f"  p={p}: " + ", ".join(f"{n} steps {p**n:.2f}" for n in (5, 10, 20)))
rng = np.random.default_rng(0)
p, n, retries = 0.90, 10, 1
ok = (rng.random((100_000, n, retries + 1)) < p).any(axis=2).all(axis=1)   # each step may be retried once after a detected error
print(f"  p=0.90, 10 steps, one retry when an error is detected: {ok.mean():.2f} (vs {p**n:.2f} without)")

# ---- 3. context growth: input tokens are quadratic in the number of steps without caching
base, per_step = 2000, 500
for n in (5, 10, 20):
    total = sum(base + per_step * k for k in range(n))
    print(f"{n:2d} steps: {total:,} input tokens in total (last step alone {base + per_step*(n-1):,})")

Employees want an assistant that can reset passwords, unlock accounts, check laptop warranty status and open tickets. Sketch the tools, controls and evaluation.

Answer

Tools: get_user (read: the requester's own profile, identity from single sign-on, not from the chat), get_warranty (read), open_ticket (low-risk write), unlock_account and reset_password (consequential).

Structure: a workflow skeleton that authenticates the employee and scopes every tool to their own account; an agentic step inside it to understand the request and choose tools.

Controls: schema validation of every call; allow-list per role (employees can only act on themselves; helpdesk staff more widely); unlock and reset require a second factor confirmation sent by the system, not text the model writes; idempotency keys; step budget of about 8 and a cost cap; all actions logged; untrusted text (ticket descriptions, emails) treated as data.

Evaluation: sandboxed directory with scripted scenarios (forgotten password, locked account, warranty question, ambiguous request, request to reset someone else's password, injected instructions in a ticket); several runs each; check end state, confirmations, refusals and cost; regression cases from every incident.

Compute — how many steps can we afford?

Your agent's per-step success rate is 0.97 and your product needs 80% task success. How many steps can a task take? If a verifier catches 70% of step errors and allows one retry, what changes?

Answer

Without recovery: 0.97ⁿ ≥ 0.8 → n ≤ ln 0.8/ln 0.97 = 0.223/0.0305 ≈ 7 steps.

With a verifier catching 70% of errors and one retry: a step fails only if it fails and the error is missed (0.03 × 0.3 = 0.009), or it fails, is caught and the retry also fails (0.03 × 0.7 × 0.03 = 0.00063). Per-step success ≈ 1 − 0.0096 = 0.9904. Now 0.9904ⁿ ≥ 0.8 → n ≤ 0.223/0.00965 ≈ 23 steps. Detection is worth more than a slightly better model: it roughly triples the affordable task length here.
