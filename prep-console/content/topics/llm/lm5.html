A team launches an internal assistant on one 80 GB GPU running a 7-billion-parameter model. The weights take 13.5 GB, so they expect plenty of room. In testing, with a handful of users and short questions, it is fast. Then they let employees paste whole documents and keep long conversations going, and the service starts rejecting requests at around two dozen concurrent users, with latency climbing steeply before it does. The GPU's compute is mostly idle. What has filled the memory is not the model; it is a data structure that grows with every token every user has typed or received.

That structure is the KV cache. To generate text, a model produces one token at a time, and each new token's attention must look at the keys and values of every previous token in every layer. Recomputing them at every step would be hopelessly slow, so the serving engine keeps them in GPU memory. For that 7B model it is half a mebibyte per token per conversation; a 4,096-token conversation holds 2 GiB, and 27 of them fill the GPU. Reading that cache at every step is also what makes each generated token slow once the batch is large.

The cache is why "how many users can one GPU serve?" and "how long a context can we offer?" are memory questions rather than compute questions, why serving engines manage memory like operating systems, and why model architects changed attention itself. Multi-query attention and grouped-query attention, now used by most open models, exist almost entirely to shrink this cache.

This lesson builds the cache from the attention you already know, separates the prefill and decode phases, derives the bytes-per-token formula and works it for 7B and 70B models, shows why the cache limits batch size and dominates decode time, and then explains MQA and GQA, how an existing model is converted to GQA, and what the published results were. The lab computes cache sizes for real models and verifies in NumPy that cached decoding gives exactly the same result as recomputing everything.

Generation is a loop

A language model predicts the next token from all the tokens so far. To write a reply, it runs that prediction, appends the chosen token, and runs it again, one token per step, until it emits an end token. This is autoregressive generation. Each step, the new token needs attention over all earlier tokens: its query must be compared with every earlier token's key, and it must take a weighted sum of every earlier token's value, in every layer.

What can be reused

Here is the key observation. Because of the causal mask (lm2), token 5's key and value in layer 1 depend only on tokens 1 to 5. When token 6, 7 or 700 is generated later, token 5's key and value in layer 1 are exactly the same as they were. The same holds in every layer, since each layer's input for token 5 also depends only on tokens 1 to 5. So instead of recomputing all earlier keys and values at each step, the model can compute each token's keys and values once and store them. That store is the KV cache: for every layer, a growing list of key vectors and value vectors, one entry per token so far.

An analogy: a meeting with minutes

Picture a long meeting where each new speaker needs to respond to everything said so far. Without minutes, every speaker would have to ask everyone to repeat their previous points. With minutes, each point is written down once, in a compact form, and every later speaker simply reads the whole document. The minutes make speaking cheap but have their own cost: the document grows with every contribution, and reading the whole of it before each new speech takes longer and longer. The KV cache is exactly this: it turns recomputation into storage and reading, and its size and reading time grow with the conversation.

Two phases

A request therefore runs in two phases. In prefill, the model processes the whole prompt in one parallel forward pass, computing and storing keys and values for every prompt token in every layer, and produces the first output token. In decode, it generates one token per step: compute the new token's query, key and value in each layer, append the key and value to the cache, attend over the whole cache, and move on. Prefill is a big parallel computation; decode is a long series of small ones, each of which must read the model's weights and the sequence's whole cache from GPU memory.

How big is "big"?

Each cached entry is small, two vectors of 128 numbers per KV head per layer, but there are a lot of them. For Llama 2 7B, every token of every conversation costs half a mebibyte of cache; a 4,096-token conversation costs 2 GiB, about one seventh of the model's own weights. A GPU serving dozens of such conversations at once holds more cache than model. The body of this lesson derives the formula and shows how architecture changes (multi-query and grouped-query attention) cut the per-token figure by 4 to 64 times.

Hold on to two facts: the cache costs memory proportional to (tokens so far) × (layers) × (key and value heads) × (head size), for every sequence being served; and every decode step reads all of it.

1. Generation without a cache

Start with the naive loop. To generate token t + 1, run the full model on tokens 1 … t and read the last position's logits. Every step recomputes every earlier token's hidden states in every layer, including their keys and values. Generating T tokens after a short prompt costs about 1 + 2 + … + T = T(T + 1)/2 token-passes through the model, so cost grows with the square of the output length: 500,500 token-passes for 1,000 generated tokens, against 1,000 if each token were processed once. Since a forward pass costs about 2N FLOPs per token for an N-parameter model (lm3), a 7B model generating 1,000 tokens would spend about 7 × 10¹⁵ FLOPs on recomputation alone.

2. Why past keys and values can be reused

The causal mask guarantees that token i's representation in layer 1 depends only on tokens 1 … i. Layer 2's input for token i is layer 1's output for token i, which therefore also depends only on tokens 1 … i; by induction, token i's hidden state at every layer, and so its key k = h W_K and value v = h W_V, are fixed the moment token i is known. With RoPE (lm4), the key is rotated by token i's own position, which is also fixed. Nothing that happens later can change them. The new token's query, however, is new at every step, and its attention weights over the past must be computed fresh, because they depend on that query.

3. Generation with a cache, step by step

With a cache, each decode step does this in every layer:

  1. Take the new token's hidden state h (one vector), compute its query q = hW_Q, key k = hW_K and value v = hW_V, and apply RoPE to q and k at the token's position.
  2. Append k and v to this layer's cache, which now holds t entries.
  3. Compute scores of q against all t cached keys (a 1 × t vector), scale, softmax, and take the weighted sum of the t cached values.
  4. Project with W_O, add to the residual stream, run the MLP, and pass the new token's vector to the next layer.

Every matrix multiplication now involves one token instead of t, so the weight arithmetic per step is about 2N FLOPs regardless of position, and attention is O(t) instead of O(t²). The lab checks that this incremental procedure gives exactly the same outputs as recomputing the whole sequence with the causal mask, to floating-point precision. During prefill, the same cache is filled for all prompt tokens at once by an ordinary causal forward pass, which is why prefill can process thousands of tokens in about the time decode takes for a handful.

4. How big is the cache?

For each token, each layer stores one key vector and one value vector per KV head, each of length d_head, in some number format. So

KV bytes per token = 2 × n_layers × n_kv_heads × d_head × bytes_per_element

Multiply by the number of tokens in a sequence (prompt plus generated so far) for one sequence, and by the number of sequences being served at once for the whole batch. In standard multi-head attention, n_kv_heads equals the number of query heads, and n_kv_heads × d_head = d_model, so the formula is also 2 × n_layers × d_model × bytes: two numbers per layer per model dimension per token.

Worked: Llama 2 7B. 32 layers, 32 heads, d_head = 128, fp16 (2 bytes): 2 × 32 × 32 × 128 × 2 = 524,288 bytes = 512 KiB per token. A 4,096-token conversation: 512 KiB × 4,096 = 2 GiB. A batch of 32 such conversations: 64 GiB, nearly five times the 13.5 GB of weights. The parameter count (6.74 billion) is fixed; the cache scales with users × context.

Worked: Llama 2 70B. 80 layers, 64 query heads but only 8 KV heads (grouped-query attention, section 8), d_head = 128: 2 × 80 × 8 × 128 × 2 = 327,680 bytes = 320 KiB per token, 1.25 GiB per 4,096-token sequence. Had it used standard multi-head attention with 64 KV heads: 2 × 80 × 64 × 128 × 2 = 2,621,440 bytes = 2.5 MiB per token, 10 GiB per sequence, 320 GiB for 32 sequences, more than eight 80 GB GPUs could hold alongside the 138 GB of weights. That factor of eight is why GQA exists.

5. The cache sets the batch size

Serving throughput comes from batching: processing many users' decode steps together so each read of the weights is shared (gpu10). The cache decides how big that batch can be. On one 80 GB H100, keeping 10% headroom for activations and fragmentation, Llama 2 7B leaves 72 − 13.5 = 58.5 GB for cache: at 2 GiB per 4,096-token sequence, 27 sequences. Llama 3 8B, with a quarter of the cache per token thanks to GQA, leaves 55.9 GB and fits 104 sequences, nearly four times as many despite being a slightly larger model. The same arithmetic in the GPU track gives about 150 sequences of 3,000 tokens for Llama 3 70B on four H100s. When requests' contexts vary, an engine that reserves the maximum context per request wastes most of this memory; paged allocation (lm13) reserves memory in small blocks as the cache actually grows.

6. The cache sets the decode speed

Each decode step must read every weight once (shared by the batch) and every active sequence's entire cache (not shared). Reading from GPU memory at about 3.35 TB/s on an H100, Llama 2 7B's 13.5 GB of weights take about 4.0 ms per step. A full batch of 27 sequences of 4,096 tokens adds 27 × 2 GiB = 58 GB of cache reads, about 17 ms. So at long context and high batch, cache reads, not weight reads, dominate the time per generated token. The arithmetic per byte of cache is tiny: each cached key is used for one dot product with one query per query head sharing it, so attention during decode does roughly as many FLOPs as bytes it reads, times the number of query heads per KV head. That ratio, the group size, is exactly what GQA raises.

7. Multi-query attention

Shazeer's 2019 paper "Fast Transformer Decoding: One Write-Head is All You Need" made the bandwidth argument explicitly: incremental decoding is limited by the memory bandwidth needed to reload the keys and values, so make them smaller. In multi-query attention (MQA), all query heads share a single key head and a single value head. Each head still has its own query projection, so heads can still look for different things; they just search the same keys and read the same values. The cache shrinks by a factor equal to the number of heads: a 64-head 70B-shape model would need 40 KiB per token instead of 2.5 MiB. Decode becomes much faster. The costs are some loss of quality, since the model has far less capacity in its keys and values, and reports of less stable training; and in tensor-parallel serving, where heads are split across GPUs, the single KV head must be copied to every GPU.

8. Grouped-query attention

Ainslie et al. (2023) proposed the middle ground. In grouped-query attention (GQA), the H query heads are divided into G groups, and each group shares one key head and one value head. G = H is ordinary multi-head attention; G = 1 is MQA. With G = 8, a model with 64 query heads has 8 query heads per KV head and a cache 8 times smaller than MHA. In code, GQA is a small change: the key and value projections produce G heads instead of H, and each KV head is repeated (or indexed) to serve the query heads in its group before the usual attention computation.

The GQA paper also answered a practical question: what if you already have a trained MHA model? They uptrained it: build each group's key projection by mean-pooling the key projection matrices of the heads in that group (and likewise for values), then continue pretraining for a small fraction of the original compute. With 5% of T5-XXL's pretraining compute, the converted GQA-8 model averaged 47.1 across their summarisation, translation and question-answering benchmarks, against 47.2 for the original multi-head model and 46.6 for an MQA conversion, while its inference time per sample was 0.28 s against 1.51 s for multi-head and 0.24 s for MQA. GQA keeps nearly all of the quality and nearly all of the speed.

9. GQA in parameter and FLOP terms

GQA also shrinks the key and value projection matrices: in Llama 3 8B, W_K and W_V are 4,096 × 1,024 rather than 4,096 × 4,096, so attention has 42 million weights per layer instead of 67 million (lm3 counted this). Model designers usually spend the saved parameters elsewhere; the Llama 2 authors, comparing MHA, MQA and GQA at 30B, enlarged the MLP to keep total parameters equal. The arithmetic of attention itself hardly changes: each query head still computes scores against every cached position. What changes is bytes: the cache is smaller, and each cached key is read once and used by every query head in its group, which raises attention's arithmetic intensity during decode by the group size and moves it towards the compute-bound regime.

10. One request, traced with numbers

Put the pieces together for one request to Llama 3 8B on an H100: a 2,000-token prompt (a document plus a question) and a 300-token answer, served alone. Prefill processes 2,000 tokens in one pass: about 2 × 8 × 10⁹ × 2,000 = 32 × 10¹² FLOPs for the weights. An H100 SXM's dense bf16 peak is about 989 TFLOP/s, so at a realistic 50-60% of peak this is about 55-65 ms, plus attention. During that pass the cache for all 2,000 tokens is written: 2,000 × 128 KiB = 250 MiB. The first output token appears after prefill (plus any queueing): that is the time to first token.

Decode then runs 300 steps. Each step reads the 16.1 GB of weights (about 4.8 ms at 3.35 TB/s) and the cache, which grows from 250 MiB to about 288 MiB (well under 0.1 ms to read), so each step takes roughly 5 ms and the user sees about 200 tokens per second; 300 tokens take about 1.5 s. Now serve 64 such requests together. Prefill work scales with the number of prompts, and decode steps still read the weights once (shared) but now also read 64 caches of about 280 MiB each, roughly 18 GB per step, about 5.4 ms. Each step now takes about 10 ms, so every user sees about 100 tokens per second, but the GPU produces about 6,400 tokens per second in total, about 32 times the single-user throughput. With an MHA model of the same shape, those 64 caches would be four times larger, about 72 GB, more than the roughly 56 GB left after the weights, so the batch would not even fit; at the batch that does fit, each step would spend about four times as long reading cache per request. This is the trade-off the whole lesson revolves around: batching amortises weight reads, the cache does not amortise, and GQA shrinks the part that does not amortise.

11. Choosing the number of KV heads

For a model designer, the number of KV heads is a dial between quality and serving cost. The considerations are the ones this lesson has built up. Fewer KV heads mean a smaller cache, more concurrent users and faster long-context decode, but less capacity in the keys and values. The number should usually be at least the tensor-parallel degree you expect to serve with, so every GPU holds distinct heads rather than copies; 8 matches the common 8-GPU node. Very long-context models benefit most, because their cache dominates; short-context, low-concurrency deployments benefit least. In practice most open models from 2024 onwards use 8 KV heads at sizes from 8B to 70B and beyond, and some use even more aggressive schemes such as MLA or sliding-window layers. When choosing a model to deploy, look up its layer count, KV head count and head dimension before anything else: those three numbers, multiplied by your expected context and concurrency, tell you whether it will fit.

12. Other ways to shrink or manage the cache

Several further techniques attack the same memory, and you should know what each one trades. Cache quantisation stores keys and values in 8-bit (or lower) formats instead of 16-bit, halving the bytes with a small accuracy cost; it is a configuration option in common serving engines. Sliding-window attention in some layers keeps only the most recent w tokens' keys and values, capping the cache for those layers. Paged allocation and prefix sharing do not shrink the cache per token but stop memory being wasted on reserved-but-unused space and on duplicate copies of shared prompts (lm13). Offloading moves rarely used parts of the cache to CPU memory. And multi-head latent attention changes the architecture again, caching a compressed latent per token (deep section).

Arithmetic intensity of decode attention

During decode, for one KV head with g query heads in its group and a cache of t tokens, attention reads 2·t·d_head numbers (keys and values) and performs about 4·t·d_head·g FLOPs (scores and weighted sum for each query head). Its arithmetic intensity is therefore about g FLOPs per number read, or g/2 FLOPs per byte in fp16. For MHA (g = 1) that is 0.5 FLOP per byte, hopelessly memory-bound on a GPU whose ridge point (gpu2) is hundreds of FLOPs per byte. GQA-8 raises it to 4, MQA with 64 heads to 32: still memory-bound, but with proportionally fewer bytes per unit of useful work. Unlike weight reads, cache reads cannot be amortised by batching, because each sequence's cache is used only by that sequence. This is why, at long context, decode throughput stops improving with batch size: more sequences mean more cache bytes per step, linearly.

Multi-head latent attention

DeepSeek-V2 introduced MLA. Rather than reducing the number of KV heads, it projects each token's hidden state down to a compressed latent vector of a few hundred dimensions, caches only that latent (plus a small decoupled rotary key component, because RoPE's position-dependent rotation would otherwise prevent a key trick described next), and reconstructs full per-head keys and values with up-projection matrices. At inference the up-projections can be absorbed into the query and output projections, so attention can be computed directly against the latents. The result is a cache smaller than GQA's while keeping per-head key diversity. The cost is implementation complexity and extra matrix multiplications, a good trade when decode is limited by bytes rather than FLOPs.

Why sharing keys and values costs so little quality

Empirically, the key and value projections of different heads in a trained MHA model are fairly redundant, which is why mean-pooling them is a good starting point. Intuitively, the query projection decides what each head looks for, and that remains per-head; the keys only need to expose enough features for the queries to discriminate positions, and the values enough content to be useful. A shared key space with 8 × 128 dimensions is still large. MQA's single 128-dimensional key space is more restrictive, which matches the measured gap. The Llama 2 ablation at 30B parameters found GQA comparable to MHA on most evaluations and better than MQA on average, after compensating the parameter loss with a wider MLP.

Tensor parallelism and the number of KV heads

When a model is split across GPUs by heads, each GPU holds a slice of query heads and the matching KV heads, and keeps the cache for those heads only. If there are fewer KV heads than GPUs, as with MQA on 8 GPUs, every GPU must hold a copy of the shared head and its cache, so the cache per GPU is no smaller than with GQA-8. The Llama 2 paper notes this explicitly: on an 8-GPU node, MQA's cache would either be duplicated (making it equal to GQA's) or sharded across the batch dimension, which complicates serving. Matching the number of KV heads to the typical tensor-parallel degree is one reason 8 became the common choice.

Prefill, chunked prefill and the cache

Prefill writes the cache for the whole prompt in one pass; for a 32K-token prompt that is a large, compute-bound operation that can stall the decode steps of other users sharing the GPU. Serving engines split long prompts into chunks and interleave them with decode steps (chunked prefill), and some systems run prefill and decode on separate GPU pools and transfer the cache between them (disaggregated serving, gpu10). Both depend on the cache being a well-defined, transferable object, which is also what makes prefix caching possible: if two requests share their first 2,000 tokens, the cache for those tokens is identical and can be computed once and shared (lm13).

Verifying a cache implementation

Cache bugs are subtle because the model still produces fluent text. Typical ones: applying RoPE to cached keys at the wrong position (for instance, the position within the current chunk rather than within the sequence), forgetting to apply it to the new key before appending, appending before computing attention so the token attends to itself twice, or reusing a cache slot from a previous request in a batched engine. The reliable test is the one in the lab: for a fixed input, compare the logits of cached incremental decoding with a full non-cached forward pass at every position, to a tight tolerance. Run it for multiple batch sizes and for prompts that cross any chunk or page boundary the engine uses.

Cache eviction and long conversations

When memory runs out, an engine must pause some sequences: either drop their cache and recompute it later from the tokens (cheap to store, costs prefill compute) or copy it to CPU memory (costs PCIe bandwidth). Research methods instead evict individual tokens from the cache, keeping the ones attention uses most plus the first few "attention sink" tokens (lm2), which bounds memory for streaming but loses exact recall of evicted content. For products, the simpler and more predictable lever is conversation management: summarising or truncating old turns so the cache stays within budget.

The public case: grouped-query attention (Ainslie et al., Google, 2023) and its adoption in Llama 2

The GQA paper begins from MQA's problem: it "drastically speeds up decoder inference" but "can lead to quality degradation", and it may not be desirable to train a separate model just for faster inference. The authors made two contributions. First, an uptraining recipe: convert an existing multi-head checkpoint by mean-pooling the key and value projection heads within each group, then continue pretraining with 5% of the original compute. Second, grouped-query attention itself, with an intermediate number of KV heads. On T5-XXL, measured on a TPU with input length 2,048 and output length 32, the multi-head model took 1.51 s per sample and averaged 47.2 across seven summarisation, translation and question-answering datasets; the uptrained MQA model took 0.24 s and averaged 46.6; the uptrained GQA-8 model took 0.28 s and averaged 47.1. Their timing plots show cost growing only slowly as groups are added, so 8 groups buys back most of MHA's quality for little speed.

Meta adopted it within weeks. The Llama 2 paper (July 2023) states that the 34B and 70B models use GQA "to improve inference scalability", and its appendix compares MHA, MQA and GQA variants of a 30B model trained on 150B tokens, widening the MLP to keep parameter counts equal: GQA performed comparably to MHA on most tasks and better than MQA on average. It also gives the serving rationale: the largest models are hosted on 8 A100s with tensor parallelism, where MQA's single KV head cannot be sharded across heads. Llama 3 then used GQA with 8 KV heads at every size, which is why Llama 3 8B's cache is a quarter of Llama 2 7B's per token.

Failure modes in production

Out-of-memory under load, not at startup. The model loads fine; failures appear when concurrency or context grows. Symptoms: rising preemption or eviction counts in the serving engine, then errors or latency spikes. Fix by sizing the cache explicitly (maximum concurrent tokens), using paged allocation, capping context, or moving to a GQA model.

Latency that grows with conversation length. Time per output token creeps up over a long chat because each step reads a longer cache. Expected behaviour, but it surprises teams who benchmarked with short prompts. Benchmark at realistic context lengths.

Mis-sized capacity plans. Planning with parameter counts alone ("7B fits easily") ignores that 32 users with 4K contexts need 64 GiB of cache on an MHA model. Every capacity estimate should include the bytes-per-token formula times expected concurrent tokens.

Quality changes from cache quantisation. 8-bit caches are usually safe, but some models and long-context tasks degrade; evaluate on long-input tasks before enabling it.

What it means for cost

Because throughput comes from batching and the cache limits the batch, the cache feeds directly into cost per token. Doubling the average context of your traffic roughly halves the number of concurrent sequences a GPU can hold and lengthens each decode step, so cost per output token rises even though the model is unchanged. This is why providers price long-context requests higher, why prompt caching discounts exist (a reused prefix's cache is computed once), and why product decisions such as how much conversation history to resend each turn show up on the GPU bill. When comparing two candidate models for a long-document product, compare their KV bytes per token as carefully as their parameter counts: a model with a quarter of the cache per token can serve several times more users on the same hardware.

What to monitor

KV-cache utilisation (fraction of cache blocks in use), number of running and waiting sequences, preemptions, time to first token and time per output token by context-length bucket, and tokens per second per GPU. Engines such as vLLM expose these as metrics; dashboards that show cache utilisation next to latency make capacity problems obvious before they become outages.

import numpy as np

# ---- 1. KV-cache size calculator
def kv_bytes_per_token(layers, kv_heads, head_dim, bytes_per=2):
    return 2 * layers * kv_heads * head_dim * bytes_per            # 2 = one key + one value
models = {                     # layers, query heads, kv heads, head dim, params (B)
    "Llama 2 7B (MHA)":      (32, 32, 32, 128, 6.74),
    "Llama 3 8B (GQA-8)":    (32, 32, 8, 128, 8.03),
    "Llama 2 70B (GQA-8)":   (80, 64, 8, 128, 69.0),
    "70B if it were MHA":    (80, 64, 64, 128, 69.0),
    "70B if it were MQA":    (80, 64, 1, 128, 69.0),
}
print(f"{'model':22s} {'per token':>10s} {'4K-token seq':>13s} {'32 x 4K':>9s}")
for name, (L, hq, hkv, hd, p) in models.items():
    b = kv_bytes_per_token(L, hkv, hd)
    print(f"{name:22s} {b/1024:8.0f} KiB {b*4096/2**30:10.2f} GiB {32*b*4096/2**30:7.1f} GiB")

# ---- 2. how many sequences fit, and what a decode step must read (one H100: 80 GB, 3.35 TB/s)
hbm, bw = 80e9, 3.35e12
for name in ("Llama 2 7B (MHA)", "Llama 3 8B (GQA-8)"):
    L, hq, hkv, hd, p = models[name]
    weights = p * 1e9 * 2; free = 0.9 * hbm - weights; b = kv_bytes_per_token(L, hkv, hd)
    n_seq = int(free // (b * 4096))
    t_w, t_kv = weights / bw, n_seq * 4096 * b / bw
    print(f"\n{name}: weights {weights/1e9:.1f} GB, free for cache {free/1e9:.1f} GB -> {n_seq} sequences of 4,096 tokens")
    print(f"  one decode step reads weights {t_w*1e3:.1f} ms + KV cache {t_kv*1e3:.1f} ms at full batch")

# ---- 3. incremental decoding with a KV cache gives exactly the same outputs as recomputing everything
rng = np.random.default_rng(0)
d, hq, hkv, n = 32, 8, 2, 10; hd = d // hq; group = hq // hkv
Wq = rng.normal(0, d ** -0.5, (d, hq * hd)); Wk = rng.normal(0, d ** -0.5, (d, hkv * hd)); Wv = rng.normal(0, d ** -0.5, (d, hkv * hd))
def softmax(z): z = z - z.max(-1, keepdims=True); e = np.exp(z); return e / e.sum(-1, keepdims=True)
def gqa_full(X):                                                     # all positions at once, causal
    T = len(X); q = (X @ Wq).reshape(T, hq, hd); k = (X @ Wk).reshape(T, hkv, hd); v = (X @ Wv).reshape(T, hkv, hd)
    k, v = np.repeat(k, group, axis=1), np.repeat(v, group, axis=1)  # each KV head serves `group` query heads
    s = np.einsum("thd,shd->hts", q, k) / np.sqrt(hd)
    s = np.where(np.triu(np.ones((T, T), bool), 1), -np.inf, s)
    return np.einsum("hts,shd->thd", softmax(s), v).reshape(T, d)
X = rng.normal(size=(n, d)); full = gqa_full(X)
K_cache, V_cache, outs = [], [], []
for t in range(n):                                                   # one token per step, cache grows by one row
    x = X[t]
    K_cache.append((x @ Wk).reshape(hkv, hd)); V_cache.append((x @ Wv).reshape(hkv, hd))
    q = (x @ Wq).reshape(hq, hd)
    K = np.repeat(np.stack(K_cache), group, axis=1); V = np.repeat(np.stack(V_cache), group, axis=1)
    w = softmax(np.einsum("hd,shd->hs", q, K) / np.sqrt(hd))
    outs.append(np.einsum("hs,shd->hd", w, V).reshape(d))
print("\ncached decoding == full recompute:", np.allclose(np.stack(outs), full),
      f"| cache holds {len(K_cache)} x {hkv} KV heads x {hd} dims (MHA would hold {hq} heads)")

# ---- 5. converting MHA heads to GQA by mean-pooling (the GQA paper's uptraining start point)
Wk_mha = rng.normal(size=(d, hq, hd))
Wk_gqa = Wk_mha.reshape(d, hkv, group, hd).mean(axis=2)
print("MHA key projection", Wk_mha.shape, "-> GQA key projection", Wk_gqa.shape, "(mean of each group of", group, "heads)")

Estimate — how many users fit?

You serve Llama 3 70B (80 layers, 64 query heads, 8 KV heads, head dimension 128) in bf16 on one node of 8 × 80 GB GPUs with tensor parallelism. Average conversations are 6,000 tokens. How many can be served concurrently, and what would the number be if the model used MHA?

Answer

Memory available: 8 × 80 = 640 GB; at 90% usable, 576 GB. Weights: about 70.6B × 2 bytes ≈ 141 GB. Free for cache ≈ 435 GB (ignoring activation overhead, which is small at decode).

Cache per conversation: 2 × 80 × 8 × 128 × 2 = 327,680 bytes = 320 KiB per token; × 6,000 = 1.97 GB.

Concurrency: 435 ÷ 1.97 ≈ 220 conversations.

With MHA (64 KV heads): 2.5 MiB per token, 15.7 GB per conversation, about 27 conversations: eight times fewer. Each decode step would also read eight times more cache bytes, so it would be slower at the same batch.

Caveats to mention: conversations vary in length, so paged allocation matters; the latency target may cap the batch below the memory limit, because each step reads all active caches (220 × 1.97 GB ≈ 433 GB, about 16 ms per step at 8 × 3.35 TB/s aggregate on top of the weights); and an 8-bit cache would double capacity.

Diagnose — the assistant that slows down over time

Users report that a chat assistant's answers stream quickly at the start of a conversation but noticeably slower after an hour of back-and-forth. GPU compute utilisation is low. What is happening and what are your options?

Answer

Each decode step reads the whole conversation's KV cache, so time per output token grows linearly with conversation length; after an hour the context may be tens of thousands of tokens, making cache reads dominate each step. Low compute utilisation confirms the step is memory-bound. As the caches of long conversations grow, the server can also batch fewer users, so per-user throughput falls further, and it may be evicting and recomputing caches. Options: summarise or truncate older turns to bound the context; enable prefix caching so the system prompt is shared; quantise the cache to 8-bit; serve a GQA model or one with sliding-window layers; and check engine metrics for preemptions, which add recomputation stalls.
