Every classifier with more than two classes, and every language model ever trained, ends with the same two operations: a softmax that turns the final layer's raw scores into a probability for each class, and a cross-entropy loss that measures how much probability went to the right answer. A language model predicting the next token chooses among tens or hundreds of thousands of tokens at every position of every sequence, so these two lines of code run trillions of times during training. Get them slightly wrong and nothing else matters: the model trains on NaN, or on padding, or on a gradient with the wrong scale.

That is why "implement softmax and cross-entropy with the gradient" is one of the most common ML coding questions for deep-learning and LLM roles. It looks like a one-liner, and the one-liner is wrong. np.exp(z) / np.exp(z).sum() returns NaN for logits in the hundreds (in float16, for a logit of 12). Taking the log of a computed probability returns minus infinity when the probability underflows. Forgetting to exclude padding makes the model learn to predict padding. Dividing by the batch size instead of the number of real tokens makes the loss depend on how much padding happened to be in the batch. And the gradient, which interviewers expect you to derive on the whiteboard, is one of the most elegant results in the field: predicted probabilities minus the target.

At LLM scale a new problem appears. The logits for one training batch are a matrix of tokens by vocabulary. With 32,768 tokens and a 256,000-token vocabulary that is 8.4 billion numbers, 33.5 GB in float32, larger than the rest of a small model's activations combined. The 2024 Cut Cross-Entropy paper measured the loss computation of Gemma 2 2B using 24 GB and reduced it to 1 MB by never storing the logits. The trick is the same online log-sum-exp that makes FlashAttention work, and this lesson's drill implements it in NumPy. The same online update reappears in attention (mc16) and in KV-cached generation (mc18), so understanding it here pays off three times.

The lesson builds everything from one row of three logits worked by hand: the exponentials, the probabilities, the loss computed two ways, the gradient, and the same with label smoothing. Then it writes the naive version (and shows it crash), the stable vectorised version with ignore_index and label smoothing, a central-difference gradient check, and an exact comparison with PyTorch's CrossEntropyLoss. It closes with the softmax Jacobian, temperature, z-loss, and the memory arithmetic that drives fused loss kernels in LLM training.

A classifier's last layer produces one number per class, called a logit. Logits are scores, not probabilities: they can be negative, larger than one, and they do not add up to anything in particular. A dog-cat-bird classifier might output [2, 1, 0], meaning "dog is most likely, then cat, then bird", without saying how likely. Softmax turns scores into probabilities in two moves: exponentiate each score (which makes everything positive and stretches the gaps, so a score one higher becomes about 2.7 times larger), then divide by the total so they sum to 1. For [2, 1, 0] that gives roughly 67% dog, 24% cat and 9% bird.

The name is apt. A "hard max" would put 100% on the largest score; softmax is a soft version that keeps some probability on the others, more when the scores are close and less when one dominates. Adding the same number to every logit does not change the result (it multiplies every exponential by the same factor, which cancels in the division), so only the differences between logits matter. That one fact is the key to the stable implementation.

Cross-entropy scores the probabilities. If the true answer was "dog", the loss is −log(0.67) = 0.41; had the model said 99% dog, the loss would be 0.01; had it said 1% dog, the loss would be 4.6. Only the probability given to the right class matters, and confident mistakes are punished hard. Averaged over a batch, cross-entropy is the negative log-likelihood of the labels, the same principle as mc2's binary cross-entropy, which is the two-class special case.

Training needs the gradient, how the loss changes as each logit changes. Here the maths is unusually kind: the gradient for each logit is just the predicted probability minus the target. For the dog example, the dog logit's gradient is 0.665 − 1 = −0.335 (push it up), the cat logit's is 0.245 and the bird logit's 0.090 (push them down, in proportion to the probability they wrongly took). No exponentials, no division, just a subtraction.

The same machinery runs inside a language model at every position: the logits are scores for every token in the vocabulary, softmax turns them into a next-token distribution, and the loss is minus the log-probability of the token that actually came next. The loss averaged over a text, exponentiated, is the model's perplexity, roughly "how many tokens was the model choosing between, on average". A model guessing uniformly over a 50,000-token vocabulary has perplexity 50,000; a good model on ordinary text is in the single or low double digits.

Where the simple picture breaks: computers store numbers with limited range. e¹⁰⁰⁰ does not fit in any floating-point format, and the probability of a very unlikely class can be too small to store at all, becoming exactly zero, whose logarithm is minus infinity. A correct implementation never computes either. And at the scale of a language model, the problem is not one row of three logits but billions of logits per batch, which changes how the computation must be organised.

1. The problem as it is usually asked

"Implement softmax and the cross-entropy loss with its gradient, in NumPy, for a batch of logits of shape (N, C) and integer targets of shape (N,). Support an ignore index for padding and label smoothing." Clarify: mean or sum reduction? Is the gradient wanted with respect to the logits only (yes, usually)? Targets as integers or probabilities? Which dtype? Then outline: stable log-softmax by max subtraction, loss as a weighted sum of log-probabilities, gradient as softmax minus the target distribution divided by the count of kept rows, then a gradient check and a reference comparison.

2. The maths in plain words

For one row, the softmax probability of class i is its exponential divided by the sum of all the row's exponentials. The loss is minus the log of the true class's probability. Take the log of the softmax formula and the division becomes a subtraction: log-probability of class i equals its logit minus the log of the sum of exponentials. That last quantity, "the log of the sum of the exponentials", appears so often it has a name, log-sum-exp, and a standard stable recipe: pull out the largest logit m, so logsumexp(z) = m + log Σ e^(zᵢ − m). Every exponent is now zero or negative, so the sum is between 1 and C, and its log is between 0 and log C: perfectly safe.

So the whole computation is: find the row maximum, subtract it, exponentiate, sum, take the log, add the maximum back to get log-sum-exp, subtract from the logits to get log-probabilities. The loss for a row is minus the log-probability of the target. The probabilities, if needed, are the exponentials of the log-probabilities, which are all at most 0 and therefore safe to exponentiate.

For the gradient, think about what nudging one logit does. Raising the true class's logit raises its probability, lowering the loss, at a rate equal to the probability still missing, 1 − p_true. Raising another class's logit steals probability from the true class, raising the loss, at a rate equal to that class's probability. Put together: the gradient is p − onehot. With label smoothing, the target is a spread-out distribution q instead of a one-hot, and the gradient is p − q.

3. The equations

softmax:      pᵢ = e^(zᵢ) / Σⱼ e^(zⱼ)
logsumexp:    LSE(z) = m + log Σⱼ e^(zⱼ − m),   m = maxⱼ zⱼ
log-softmax:  log pᵢ = zᵢ − LSE(z)
loss (row):   ℓ = −Σᵢ qᵢ log pᵢ                       q = onehot(y), or (1 − ε)·onehot(y) + ε/C
              = LSE(z) − z_y                          when q is one-hot
batch loss:   L = (1/n_kept) Σ_{rows with y ≠ ignore} ℓ
gradient:     ∂L/∂z = (p − q) / n_kept   for kept rows,   0 for ignored rows

softmax Jacobian:  ∂pᵢ/∂zⱼ = pᵢ(δᵢⱼ − pⱼ)
chain rule:        ∂ℓ/∂zⱼ = −Σᵢ (qᵢ/pᵢ)·pᵢ(δᵢⱼ − pⱼ) = −qⱼ + pⱼ Σᵢ qᵢ = pⱼ − qⱼ

The last line is worth saying in an interview: the 1/pᵢ from the derivative of the log cancels the pᵢ in the softmax Jacobian, and Σᵢ qᵢ = 1 finishes the job. That cancellation is why fused "softmax cross-entropy" functions exist: backpropagating through a separate softmax would multiply by a full C × C Jacobian per row and divide by probabilities that may be tiny, while the fused gradient is one subtraction.

4. A worked example by hand

One row, logits z = [2, 1, 0], target class 0.

  • Exponentials. e² = 7.389, e¹ = 2.718, e⁰ = 1; sum 11.107.
  • Probabilities. 7.389/11.107 = 0.6652, 2.718/11.107 = 0.2447, 1/11.107 = 0.0900. They sum to 1.
  • Loss, directly. −log 0.6652 = 0.4076.
  • Loss, stably. m = 2; shifted logits [0, −1, −2]; exponentials [1, 0.3679, 0.1353], sum 1.5032; LSE = 2 + log 1.5032 = 2 + 0.4076 = 2.4076; loss = LSE − z₀ = 2.4076 − 2 = 0.4076. Same answer, no large numbers anywhere.
  • Gradient. p − onehot = [0.6652 − 1, 0.2447, 0.0900] = [−0.3348, 0.2447, 0.0900]. It sums to zero.
  • With label smoothing ε = 0.1. The target becomes q = 0.9 × [1, 0, 0] + 0.1/3 = [0.9333, 0.0333, 0.0333]. Loss = −(0.9333 log 0.6652 + 0.0333 log 0.2447 + 0.0333 log 0.0900) = 0.9333 × 0.4076 + 0.0333 × (1.4076 + 2.4076) = 0.3804 + 0.1272 = 0.5076. Gradient p − q = [−0.2681, 0.2114, 0.0567]: a gentler push on the true class and a slightly smaller push down on the others.

Two things to notice. Even a perfect model cannot reach zero loss under label smoothing, because the target itself is not one-hot; the minimum loss equals the entropy of q. And the smoothed gradient on the true class becomes zero when p₀ = 0.9333, not when p₀ = 1, which is precisely what stops the logits from growing without bound. The first solution block asserts every number above.

import math
import time
import numpy as np

# The hand-worked example: one row of three logits, target class 0.
z_hand = np.array([2.0, 1.0, 0.0])
e = np.exp(z_hand)                                        # 7.389, 2.718, 1.000
assert np.allclose(e, [7.389056, 2.718282, 1.0])
p_hand = e / e.sum()                                      # sum 11.107
assert np.allclose(p_hand, [0.665241, 0.244728, 0.090031], atol=1e-6)
loss_hand = -np.log(p_hand[0])
assert np.isclose(loss_hand, 0.407606, atol=1e-6)
lse = 2 + np.log(1 + np.exp(-1) + np.exp(-2))             # log-sum-exp with the max (2) factored out
assert np.isclose(lse - z_hand[0], loss_hand)             # loss = logsumexp - z_target
grad_hand = p_hand - np.array([1.0, 0.0, 0.0])            # softmax - one-hot
assert np.allclose(grad_hand, [-0.334759, 0.244728, 0.090031], atol=1e-6)

# Label smoothing 0.1 over 3 classes: target q = 0.9·onehot + 0.1/3.
q = np.full(3, 0.1 / 3); q[0] += 0.9
assert np.allclose(q, [0.933333, 0.033333, 0.033333], atol=1e-6)
loss_ls = -(q * np.log(p_hand)).sum()
assert np.isclose(loss_ls, 0.507606, atol=1e-6)
assert np.allclose(p_hand - q, [-0.268093, 0.211395, 0.056698], atol=1e-6)

5. The naive implementation

The textbook formula, row by row and class by class, with math.exp, a sum, a division and a log:

def cross_entropy_naive(logits, targets):
    """Row by row, class by class, straight from the textbook formula (unstable on purpose)."""
    N, C = len(logits), len(logits[0])
    total, grads = 0.0, []
    for i in range(N):
        exps = [math.exp(logits[i][j]) for j in range(C)]   # overflows beyond about 709
        Z = sum(exps)
        probs = [x / Z for x in exps]
        total += -math.log(probs[targets[i]])
        grads.append([(probs[j] - (1.0 if j == targets[i] else 0.0)) / N for j in range(C)])
    return total / N, grads

On tame logits it is correct, and the test uses it to check the vectorised version. On logits of 1,000 it raises OverflowError immediately (Python's math.exp refuses to return infinity); the same formula in NumPy returns inf/inf = NaN with only a warning, which is worse because training continues on garbage. It is also slow: on 512 rows of 2,000 classes it took about 600 ms.

6. The vectorised, stable version

def log_softmax(z):
    z = z - z.max(axis=-1, keepdims=True)                 # shift: exp can no longer overflow
    return z - np.log(np.exp(z).sum(axis=-1, keepdims=True))

def softmax(z):
    return np.exp(log_softmax(z))

def cross_entropy(logits, targets, ignore_index=-100, label_smoothing=0.0):
    """Mean cross-entropy over rows whose target is not ignore_index.
    Returns (loss, dlogits) with dlogits the gradient of the loss w.r.t. logits."""
    N, C = logits.shape
    logp = log_softmax(logits)
    keep = targets != ignore_index
    t = np.where(keep, targets, 0)                         # placeholder index for ignored rows
    q = np.full((N, C), label_smoothing / C)               # target distribution per row
    q[np.arange(N), t] += 1.0 - label_smoothing
    q[~keep] = 0.0
    n = max(int(keep.sum()), 1)
    loss = -(q * logp).sum() / n
    dlogits = (np.exp(logp) * keep[:, None] - q) / n       # softmax(z) - q for kept rows, 0 otherwise
    return loss, dlogits

log_softmax. Subtract the row maximum (keepdims=True keeps the shape (N, 1) so it broadcasts back over the row), then subtract the log of the row sum of exponentials. The result is the log-probabilities, all at most 0. softmax is simply its exponential.

The target distribution. q starts as ε/C everywhere and gets 1 − ε added at each row's target, which is the label-smoothing target (with ε = 0 it is a one-hot). Rows whose target is ignore_index are given a placeholder index 0 so the indexing works, then their entire row of q is set to zero.

The loss. −(q * logp).sum() / n, where n is the number of kept rows (at least 1, to avoid dividing by zero on an all-padding batch). Ignored rows have q = 0, so they contribute nothing to the sum.

The gradient. (softmax · keep − q) / n: for kept rows, probabilities minus target; for ignored rows, zero minus zero. This is the exact derivative of the loss as written, including the 1/n, which the gradient check confirms.

The vectorised version took about 46 ms on the same 512 × 2,000 batch, 13 times faster than the loops. Most of its time goes into allocating and filling the dense (N, C) target matrix; a production version would avoid materialising q by using LSE(z) − z_y for the one-hot part and ε·(LSE(z) − mean(z)) for the smoothing part, which is how fused kernels compute it.

7. Testing it

The test block checks: the vectorised function reproduces the hand-worked loss and gradient, with and without smoothing; shifting logits by 1,000 changes nothing and raises no floating-point error, while the naive version overflows and the literal NumPy formula gives NaN; float16 exp(12) is infinite while the stable log-softmax of float16 logits [12, 10, 0] is finite; naive and vectorised agree on random logits; a central-difference gradient check on a 6 × 5 batch with smoothing and one padding row matches to 10⁻⁸, the padding row's gradient is exactly zero and every row's gradient sums to zero; PyTorch's CrossEntropyLoss(ignore_index=-100, label_smoothing=0.1) gives the same loss and gradient to 10⁻¹²; and uniform logits over 50 classes give perplexity exactly 50.

rng = np.random.default_rng(0)

loss, g = cross_entropy(z_hand[None], np.array([0]), label_smoothing=0.1)
assert np.isclose(loss, loss_ls) and np.allclose(g[0], p_hand - q)

# float16 overflows exp() at about 11.1: a logit of 12 is enough without the shift.
with np.errstate(over="ignore"):

# 3. Naive and vectorised agree on tame logits.

_, g = cross_entropy(z, t, label_smoothing=0.1)
eps, num = 1e-6, np.zeros_like(z)
for i in range(6):
    for j in range(5):
        zp, zm = z.copy(), z.copy(); zp[i, j] += eps; zm[i, j] -= eps
        num[i, j] = (cross_entropy(zp, t, label_smoothing=0.1)[0] - cross_entropy(zm, t, label_smoothing=0.1)[0]) / (2 * eps)

Matching PyTorch to twelve decimals with both features switched on is a strong test, because it pins down three conventions at once: how smoothing distributes ε (uniformly over all C classes, including the true one, which is PyTorch's documented behaviour), that ignored rows are excluded from the denominator, and that the gradient includes the 1/n of the mean.

8. Numerical stability traps

Trap 1: exponent overflow. The largest finite exponent is about 709.8 in float64, 88.7 in float32 and 11.1 in float16. Logits beyond these are common in float16 (anything above 11) and appear in float32 when training diverges. Always subtract the maximum.

Trap 2: log of an underflowed probability. Even with the shift, a very unlikely class's probability can underflow to 0 (in float32, anything below about 10⁻⁴⁵). If you compute log(softmax(z)) you get −inf for it; if that class is the target, the loss is infinite. Computing log-softmax as z − LSE(z) gives a finite, exact log-probability however small the probability.

Trap 3: fully masked rows. Attention and some loss masks set disallowed positions to −inf. If every entry of a row is −inf, the maximum is −inf, and z − m computes −inf − (−inf) = NaN. Use a large negative finite number (such as the dtype's minimum) for masks, or skip fully masked rows explicitly.

Trap 4: the wrong denominator. Dividing by the batch size instead of the number of kept rows makes the loss, and the gradient scale, depend on the amount of padding, so batches with more padding train more slowly. For gradient accumulation over several micro-batches, divide by the total number of kept tokens across all of them, not by each micro-batch's count, or tokens in short micro-batches are over-weighted.

Trap 5: low-precision accumulation. Summing 256,000 exponentials in float16 or bfloat16 loses precision badly (bfloat16 has only 8 significant bits). Mixed-precision training computes log-softmax and the loss in float32 even when the logits arrive in bfloat16.

Trap 6: integer targets of the wrong type. Targets that arrive as floats (1.0 instead of 1) or as a one-hot matrix when integers are expected produce shape errors at best and silent misuse at worst; PyTorch's CrossEntropyLoss accepts both class indices and probabilities, with different semantics. Check dtypes at the boundary. A one-line assertion on the target dtype and range costs nothing and catches the whole class of bug.

The online update, by hand

The drill's chunked loss rests on one update rule, and it is worth doing once on the hand example. Split the logits [2, 1, 0] into two chunks in an awkward order: first [0], then [2, 1]. After the first chunk, the running maximum is m = 0 and the running sum is s = e^(0 − 0) = 1. The second chunk's maximum is 2, larger than the old m, so the new maximum is 2 and the old sum, measured relative to 0, must be rescaled to be relative to 2: 1 × e^(0 − 2) = 0.1353. Then add the second chunk's terms relative to the new maximum: e^(2 − 2) + e^(1 − 2) = 1 + 0.3679. The running sum is now 0.1353 + 1.3679 = 1.5032, exactly the sum computed in one pass earlier, and LSE = 2 + log 1.5032 = 2.4076. The target logit, 2, was picked up when its chunk went by, so the loss is 2.4076 − 2 = 0.4076, as before. The rescaling step is the whole trick: it lets each chunk be processed and discarded, keeping only two numbers per row.

The binary case, and soft targets

Softmax over two logits [z, 0] gives e^z/(e^z + 1) = σ(z) for the first class: the sigmoid of mc2 is a two-class softmax with one logit pinned at zero. The two-class cross-entropy is then LSE([z, 0]) − z_y, which for y = 0 is log(1 + e^z) − z = softplus(−z) and for y = 1 is softplus(z), the same stable formula as mc2's bce_with_logits (with the classes labelled the other way round). So nothing in this lesson is new mathematics relative to logistic regression; it is the same idea with C outputs. The other generalisation is soft targets. In knowledge distillation, the target for each row is a teacher model's probability distribution rather than a one-hot vector, and the loss is the cross-entropy between the teacher's distribution and the student's, −Σ q_teacher log p_student. The function above already supports it: pass the teacher's probabilities as q, and the gradient is still p − q. When the teacher is confident the loss behaves like ordinary training; when it spreads probability over several plausible answers, the student learns those relative preferences too, which is what makes distillation work better than training on the teacher's argmax labels.

9. Edge cases worth naming

A batch in which every row is ignored has no loss to compute; the code divides by max(n, 1) and returns 0 with a zero gradient, which is the safe choice, though logging it is wise because it usually means a data bug. A single class (C = 1) makes softmax identically 1 and the loss identically 0, a degenerate setup worth rejecting. Targets outside [0, C) that are not the ignore index should raise an error rather than index out of bounds or wrap around (negative indices in NumPy silently count from the end). Very large C with small N is the LLM case and calls for chunking. And soft targets from a teacher model (distillation) replace q entirely; the same code works if q is passed in directly, and the gradient remains p − q.

10. Complexity

Forward and backward are O(N·C) time: a few passes over the logits for the maximum, the exponentials, the sums and the subtraction. Memory is O(N·C) for the logits, the log-probabilities and the gradient, which is the real constraint at scale. The logits themselves come from a matrix product of hidden states (N, d) with an output matrix (d, C), which costs O(N·d·C) and dominates the compute; for a 4,096-dimensional model with a 256k vocabulary, that is about a billion multiply-adds per token, often more than a transformer layer. Chunking over the vocabulary keeps time the same (plus a recomputation in the backward pass) and cuts the memory from N·C to N·chunk.

11. Talking through the design

In the interview: write softmax and the loss, then immediately the max-shift and log-softmax as z − LSE(z); derive the gradient through the Jacobian to p − y; add ignore_index with the correct denominator and label smoothing as a target distribution; test with a gradient check and against PyTorch. Then raise the scale question yourself: the logits matrix for a large vocabulary, and the chunked online log-sum-exp that avoids it.

The online log-sum-exp, and why FlashAttention needs it

The drill computes the loss over the vocabulary in chunks without ever holding all the logits. The key is that log-sum-exp can be updated incrementally. Keep a running maximum m and a running sum s = Σ e^(z − m) over the logits seen so far. When a new chunk arrives with maximum m', the new maximum is max(m, m'), the old sum must be rescaled by e^(m − m_new) (because it was measured relative to the old maximum), and the new chunk's terms are added relative to m_new. At the end, LSE = m + log s. This is exactly the "online softmax" of Milakov and Gimelshein, and it is the inner loop of FlashAttention (mc16 and mc18 meet it again), which applies it to rows of the attention matrix so that the full sequence-by-sequence score matrix is never stored.

Memory arithmetic for LLM losses

The logits for a batch are tokens × vocabulary. A 32,768-token batch with a 256,000-token vocabulary is 8.4 × 10⁹ logits: 33.5 GB in float32, 16.8 GB in bfloat16, and the backward pass needs a gradient of the same size. The Cut Cross-Entropy paper reports that the cross-entropy layer is responsible for up to 90% of the memory footprint of modern LLM training in its setting, and that for Gemma 2 2B its method reduces the loss computation's memory from 24 GB to 1 MB and the classifier head's training memory from 28 GB to 1 GB, enabling batch sizes 1.5 to 10 times larger without slowing training. The approach is the drill's, implemented as fused GPU kernels: compute logits for a block of vocabulary in fast on-chip memory, update the running log-sum-exp, gather the target logit, and in the backward pass recompute the block and form the gradient on the fly. It also skips gradient entries whose softmax probability is below numerical precision, which are most of them.

Token-level versus sequence-level averaging

"The mean over kept rows" hides a modelling choice once rows are tokens grouped into sequences. Averaging over all target tokens in the batch (token-level) gives every token equal weight, so long sequences dominate. Averaging each sequence's tokens first and then averaging sequences (sequence-level) gives every sequence equal weight, so a short answer counts as much as a long one. Supervised fine-tuning recipes differ on this, and switching between them changes what the model learns to prioritise. Under gradient accumulation, the token-level mean must be normalised by the total token count across all micro-batches, which a naive per-micro-batch mean gets wrong; several popular training libraries shipped exactly that bug and fixed it in 2024. Whichever convention you choose, state it, and test it with batches of very different lengths.

Temperature

Dividing logits by a temperature T before softmax rescales all differences: T > 1 flattens the distribution (more random sampling), T < 1 sharpens it, and T → 0 approaches the argmax. In distillation, both teacher and student logits are divided by the same T (often 2-4) so the student learns from the teacher's relative preferences among wrong answers, the "dark knowledge"; the loss is then multiplied by T² to keep gradient magnitudes comparable. mc20 uses temperature for decoding. The gradient of the tempered loss with respect to the original logits is (p_T − q)/T.

Label smoothing in more depth

Müller, Kornblith and Hinton showed that label smoothing makes the penultimate-layer representations of each class cluster tightly and equidistantly, which improves calibration and often accuracy, but erases information about which wrong classes are similar, which is why teachers trained with label smoothing make worse distillation teachers. In practice ε = 0.1 is the common default for image classification and machine translation; LLM pre-training usually uses none, because the next-token targets are already inherently uncertain.

z-loss and logit soft-capping

Softmax is invariant to adding a constant, so nothing in the cross-entropy loss stops all logits from drifting upward together. In low-precision training that drift costs precision and can trigger instabilities. A z-loss adds λ·LSE(z)² (PaLM used λ = 10⁻⁴) to keep the normaliser near 1; logit soft-capping (used in Gemma 2) passes logits through c·tanh(z/c) so they cannot exceed ±c. Neither changes which token is predicted; both are cheap stability insurance in large runs.

Sampled and hierarchical softmax

Before chunked exact losses were practical, large-vocabulary models approximated the normaliser: sampled softmax computes the loss over the target plus a random sample of negatives with an importance correction; hierarchical softmax arranges the vocabulary in a tree so each token's probability is a product of a few binary decisions, O(log C) per token. Both are still used in recommendation and retrieval with millions of items, where even chunked exact softmax over the full catalogue is too expensive. The in-batch-negatives contrastive loss of embedding models (mc22's dense retrieval) is a sampled softmax in disguise.

Class weights and focal loss

Two common modifications change how much each row counts. Class weights multiply each row's loss by a weight for its target class (PyTorch's weight argument), and the mean then divides by the sum of the weights of the kept rows rather than their count; rare classes get larger weights so their gradients are not drowned out. Focal loss, introduced for dense object detection, multiplies each row's loss by (1 − p_y)^γ, so examples the model already gets right with high confidence contribute almost nothing and training concentrates on the hard ones; γ = 2 is the usual choice. Both change the gradient from p − q to a reweighted version, so a gradient check is the quickest way to confirm a hand-written implementation.

Where this code runs

The output layer and loss of every classifier and language model, the attention weights inside every transformer (softmax over keys), knowledge distillation, contrastive embedding training, and decoding (softmax with temperature before sampling). In LLM training the loss is usually a fused kernel (PyTorch's built-in, Liger-Kernel's fused linear cross-entropy, or Cut Cross-Entropy) rather than separate softmax and log operations.

Failure modes and symptoms

NaN loss. Usually an unshifted exponential, a log of a zero probability, a fully masked row with −inf, or an exploding logit in low precision. Detection: assert finiteness; log the maximum absolute logit and the log-sum-exp per step. Fix the computation first, then the cause of growing logits.

Loss that depends on padding. Symptom: the loss curve has a sawtooth that tracks batch composition, or long-sequence batches train differently. Cause: the mean divides by the batch size or the total sequence length rather than the number of target tokens. Fix the denominator, especially under gradient accumulation.

Out-of-memory at the loss. Symptom: the model runs fine with a small vocabulary or short sequences and dies at the final layer with a large one. Cause: the full logits matrix and its gradient. Fix: chunked or fused cross-entropy, or a smaller micro-batch for the head. Measure the peak at the head separately from the rest of the model, because it scales with vocabulary size times tokens per micro-batch while the rest scales with model width and depth, and the two call for different fixes.

Learning the padding token. Symptom: generations end early or emit padding tokens. Cause: padding positions were not given the ignore index. Fix: set their targets to −100 (or your framework's ignore value) when building batches, and test that a batch of pure padding yields zero gradient.

Overconfident outputs. A classifier that outputs 0.999 for everything it gets wrong is miscalibrated, often from long training without smoothing. Measure calibration; consider label smoothing or post-hoc temperature scaling (fitting one temperature on validation data).

A cost estimate

For a 7-billion-parameter model with hidden size 4,096 and a 128,000-token vocabulary, the output projection is 4,096 × 128,000 ≈ 0.5 billion parameters, and computing logits costs about 0.5 billion multiply-adds per token, roughly 7% of the model's total forward compute. The logits for a 16,384-token micro-batch are 2.1 billion numbers, 4.2 GB in bfloat16 plus as much again for the gradient: a large share of an 80 GB GPU once activations are included. Chunking the head over the vocabulary in, say, 8 pieces cuts that peak to about 1 GB at the cost of recomputing the logits in the backward pass, a few per cent of total step time.

Silent precision loss in the head. Symptom: validation loss plateaus slightly higher in bfloat16 than in float32 runs of the same model. Cause: log-softmax or the loss computed in bfloat16, whose 8 significant bits cannot resolve small differences between large log-sum-exp values. Fix: upcast the logits to float32 inside the loss (fused kernels do this).

What to monitor

Training and validation loss in nats per token (and perplexity), the number of target tokens per step (to catch denominator and padding bugs), the maximum logit and log-sum-exp (to catch drift), the fraction of steps with non-finite values, and peak memory at the loss layer.

The reference for this problem

PyTorch's documentation for torch.nn.CrossEntropyLoss is the official specification this lesson's implementation matches. Its signature shows ignore_index=-100 and label_smoothing=0.0 as defaults; it states that the input "is expected to contain the unnormalized logits for each class"; it defines the per-example loss as the negative log of the softmax probability of the target, multiplied by an indicator that the target is not ignore_index, and the 'mean' reduction as the sum of those losses divided by the sum of the (weights of the) non-ignored targets, which is the denominator rule this lesson emphasises. It describes label_smoothing as "a float in [0.0, 1.0]" with which "the targets become a mixture of the original ground truth and a uniform distribution", the uniform part covering all classes. The solution's tests compare against CrossEntropyLoss(ignore_index=-100, label_smoothing=0.1) and agree to 10⁻¹² in both loss and gradient. The second reference, Wijmans and colleagues' "Cut Your Losses in Large-Vocabulary Language Models" (arXiv 2411.09009), supplies the memory figures for the chunked loss.

Goal: run the solution, then vary it, break it and time it. Python 3.12 with NumPy; PyTorch only for the optional cross-check.

  1. Run the four blocks as one script. All assertions pass and it prints the hand-example probabilities and losses and the timing.
  2. Vary the inputs. Work the loss and gradient by hand for logits [3, 1, 1] with target 1, then with ε = 0.2. Check both with cross_entropy.
  3. Break the stability. Remove the max subtraction from log_softmax and feed logits of 100, 500 and 1,000 in float64, then logits of 10, 12 and 20 in float16. Record where each first produces inf or NaN.
  4. Break the denominator. Change n to N (the batch size) and rerun the PyTorch comparison with two padding rows. By what factor is the loss off, and which test catches it?
  5. Break the mask. Set one row of logits entirely to -np.inf and run log_softmax. Then use np.finfo(float).min instead and compare.
  6. Time and scale it. Time cross_entropy on 4,096 × 50,000 logits, then the drill's chunked version with chunk sizes 1,000, 5,000 and 25,000, and record peak memory for each.

What to look for: float16 fails an order of magnitude earlier than float64 without the shift; the wrong denominator scales the loss by kept/total rows; an all −inf row gives NaN while a large finite negative does not; and the chunked loss trades a little time for a large drop in peak memory. Check that every variant still matches the unchunked loss to many decimals.

Work it out

You have final hidden states h of shape (N, d) and an output matrix W of shape (d, V) with V in the hundreds of thousands. Compute the mean cross-entropy without ever holding the full (N, V) logits. Process the vocabulary in chunks.

Answer

Keep, per row, a running maximum m and a running sum s = Σ e^(z − m). When a new chunk arrives with a larger maximum, rescale the old sum by e^(m_old − m_new) before adding the chunk. Pick out each row's target logit when its chunk passes by. At the end, logsumexp = m + log s and the loss is logsumexp − z_target.

def chunked_cross_entropy(h, W, targets, chunk=1000):
    N, V = len(h), W.shape[1]
    m = np.full(N, -np.inf)             # running max of the logits seen so far
    s = np.zeros(N)                     # running sum of exp(logit - m)
    z_t = np.zeros(N)                   # logit of each row's target
    for start in range(0, V, chunk):
        z = h @ W[:, start:start + chunk]                  # (N, chunk): the only logits in memory
        m_new = np.maximum(m, z.max(1))
        s = s * np.exp(m - m_new) + np.exp(z - m_new[:, None]).sum(1)
        m = m_new
        hit = (targets >= start) & (targets < start + chunk)
        z_t[hit] = z[hit, targets[hit] - start]
    return float(np.mean(m + np.log(s) - z_t))

h = rng.normal(size=(8, 16)); W = rng.normal(size=(16, 5000)); tg = rng.integers(0, 5000, 8)
full, _ = cross_entropy(h @ W, tg)
assert np.isclose(chunked_cross_entropy(h, W, tg, chunk=777), full)

Peak memory drops from N·V to N·chunk. The backward pass recomputes each chunk's logits and forms softmax − onehot chunk by chunk using the saved logsumexp, accumulating ∂W and ∂h, trading a second matrix multiply for tens of gigabytes. The rescaling step is word for word the online softmax inside FlashAttention.
