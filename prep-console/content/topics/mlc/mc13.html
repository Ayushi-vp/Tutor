In mc11 you wrote a backward pass by hand: seven lines of matrix calculus for a two-layer network, each derived on paper and checked numerically. That works for a two-layer network. It does not work for a transformer with dozens of layer types, residual connections, attention masks and a loss you are still experimenting with. Every time the model changes, someone would have to re-derive and re-check the backward pass. Autograd engines remove that burden: you write only the forward computation, and the engine works out every gradient automatically and exactly. PyTorch's loss.backward() is one; JAX's grad is another. They are the reason a researcher can try a new architecture in an afternoon.

"Build a tiny autograd engine" is a popular interview question because it is small enough to finish in an hour and deep enough to show whether you really understand backpropagation. The core is about a hundred lines, as Andrej Karpathy's teaching engine micrograd demonstrates, and almost every line hides a classic bug. If a value is used twice and its backward function assigns instead of adding, its gradient is wrong. If the backward functions run in the wrong order, some of them use gradients that are not finished yet. If the graph is sorted recursively, a long chain of operations crashes with a recursion error. And if the engine is extended to arrays, every broadcast in the forward pass needs a matching sum in the backward pass, which is where most hand-rolled tensor engines go wrong.

Building one also makes framework behaviour obvious that otherwise seems arbitrary: why you call zero_grad, why modifying a tensor in place sometimes raises an error, why frameworks provide fused operations like cross-entropy instead of letting you compose it from exp and log, and why the backward pass costs about twice the forward pass.

The lesson works one small expression by hand, a function in which one input is used twice, so its gradient has to be accumulated from two paths. Then it builds a scalar Value class with an iterative topological sort, checks it against the exact numbers printed in micrograd's README, against finite differences and on a 5,000-step chain. Then it rebuilds the engine over NumPy arrays, with matrix-multiply and broadcasting-aware backward rules, and checks a two-layer network's gradients against PyTorch to twelve decimal places. The drill adds a fused cross-entropy operation and shows the composed version producing NaN on logits where the fused one is exact.

The payoff goes beyond interviews. Once you have built the engine, reading a framework's autograd error messages, deciding where to detach a tensor, writing a custom operation for a fused kernel, or explaining why a training run's memory grows each step all become questions about a mechanism you have implemented yourself, not about a black box.

Think of a calculation as a little factory line. Raw inputs enter, each machine does one simple thing (add two numbers, multiply them, apply a ReLU), and the final product is the loss. Now suppose the final product comes out one unit too heavy and you want to know how much each raw input is to blame. You could walk backwards along the line: the last machine knows exactly how its output depends on its inputs (that is its local derivative), so it can split the blame between them; each of those machines splits its share further, and so on back to the raw inputs. That backwards walk is backpropagation, and an autograd engine is a factory line that writes down, as it runs, which machine fed which, so the walk can be done automatically.

The engine needs three ingredients. First, a wrapper object for every number, called Value here, that holds the number, a slot for its gradient (starting at zero), and references to the values it was made from. Second, a small function attached to every result, its backward closure, that knows the local derivatives of the operation that made it and pushes gradient to its inputs. For multiplication out = a·b, the closure adds b × out.grad to a's gradient and a × out.grad to b's. Third, a backward() method on the final result that visits every node in the right order and calls its closure.

A tiny numeric example shows the chain rule doing the work. Suppose y = 3x and L = y², with x = 2. Forward: y = 6, L = 36. The squaring machine knows its local derivative is 2y = 12, so it tells y "each unit you increase raises L by 12". The tripling machine knows its local derivative is 3, so it passes back 12 × 3 = 36 to x. Check directly: L = 9x², so dL/dx = 18x = 36. No formula for dL/dx was ever written down; two local derivatives were multiplied in the right order. An autograd engine does nothing more than this, systematically, for every number in the program.

"The right order" is the subtle part. A value's gradient is complete only when every operation that used it has passed its share back, so the engine must process the graph from the output toward the inputs, never visiting a node before all the nodes that consumed it. Sorting the graph so that every node comes after its inputs (a topological order) and then walking that list backwards does exactly this. And because a value can feed several operations, each closure must add to its inputs' gradients rather than overwrite them.

Where the factory picture breaks: real engines do not wrap individual numbers, they wrap whole arrays, so one "machine" is an entire matrix multiplication with a matrix-shaped backward rule. The algorithm is the same; the bookkeeping for shapes, especially broadcasting, is new, and the second half of the lesson builds it.

1. The problem as it is usually asked

"Implement a minimal reverse-mode autograd engine: a Value class supporting +, ×, power, ReLU (and maybe tanh), with backward() that fills .grad for every value. Use it to train a tiny network." Follow-ups usually extend it to tensors. Clarify: scalars only, or arrays? Which operations? Should it support values used more than once (yes, always)? Does it need higher-order gradients (usually not)? Then outline: the node class with data, grad, parents and a backward closure; one method per operation; a topological sort; a gradient check and a reference comparison.

2. The maths in plain words

The chain rule says: if L depends on y and y depends on x, then dL/dx = dL/dy × dy/dx. If x influences L through several paths (through y₁ and through y₂), the contributions add: dL/dx = dL/dy₁ × dy₁/dx + dL/dy₂ × dy₂/dx. That is the whole theory. Reverse mode organises the computation so that each dL/dy is computed once and reused: process nodes from the output backwards, and when a node's dL/d(node) is complete, push dL/d(node) × d(node)/d(input) into each input's running total.

Each operation therefore needs only its local derivatives, evaluated at the forward values. Addition passes the gradient through unchanged to both inputs. Multiplication sends each input the other input times the upstream gradient. A power xᵏ sends k·x^(k−1) times the gradient. ReLU sends the gradient through if its input was positive and zero otherwise. tanh sends 1 − tanh² times the gradient. Subtraction and division need no new rules: a − b = a + (−1)·b and a/b = a·b⁻¹, built from the existing operations, and the engine differentiates them correctly by composition.

3. The equations

node rules (upstream gradient ḡ = out.grad; each line is "+=", never "=")
out = a + b      a.grad += ḡ                 b.grad += ḡ
out = a · b      a.grad += b · ḡ             b.grad += a · ḡ
out = a^k        a.grad += k · a^(k−1) · ḡ
out = relu(a)    a.grad += [a > 0] · ḡ
out = tanh(a)    a.grad += (1 − out²) · ḡ

backward():  order = topological_sort(output)      # every node after its inputs
             output.grad = 1
             for node in reversed(order): node._backward()

array versions (shapes in brackets)
C = A @ B        A.grad += C.grad @ Bᵀ   [n,k]      B.grad += Aᵀ @ C.grad   [k,m]
out = A + b      A.grad += unbroadcast(ḡ, A.shape)  b.grad += unbroadcast(ḡ, b.shape)
s = A.sum(axis)  A.grad += broadcast of ḡ back to A.shape (re-inserting the summed axis)

The array rules are the scalar rules applied element-wise, plus two shape rules. A matrix product's backward is two matrix products, the ones mc11 derived by hand. And any operation that broadcast an input in the forward pass (adding a bias of shape (4,) to a (3, 4) matrix, say) used each input element several times, so in the backward pass those uses' gradients are summed: that is unbroadcast, the array version of +=.

4. A worked example by hand

Take f = (a·b + c)·a with a = 2, b = −3, c = 10. Name the intermediate results: d = a·b, e = d + c, f = e·a.

  • Forward. d = −6, e = 4, f = 8.
  • Topological order. One valid order is a, b, d, c, e, f: each node after its inputs. Reversed: f, e, c, d, b, a.
  • Seed. f.grad = 1.
  • f's closure (f = e·a): e.grad += a·1 = 2; a.grad += e·1 = 4.
  • e's closure (e = d + c): d.grad += 2; c.grad += 2.
  • c is a leaf; nothing to push.
  • d's closure (d = a·b): a.grad += b·2 = −6, so a's gradient is now 4 − 6 = −2; b.grad += a·2 = 4.
  • Result. df/da = −2, df/db = 4, df/dc = 2.

Check by algebra: f = a²b + ac, so df/da = 2ab + c = −12 + 10 = −2, df/db = a² = 4, df/dc = a = 2. Notice two things. a's gradient came from two places and only the sum is right; with assignment instead of addition, a's gradient would be 4 or −6 depending on which closure ran last. And d's closure had to run after e's, because it needed d's completed gradient; reverse topological order guarantees that. The first block does exactly this calculation with plain Python numbers.

import math
import time
import numpy as np

# The hand-worked example: f = (a·b + c)·a with a = 2, b = -3, c = 10. Note that a is used twice.
a, b, c = 2.0, -3.0, 10.0
d = a * b            # -6
e = d + c            # 4
f = e * a            # 8
assert (d, e, f) == (-6.0, 4.0, 8.0)
# Backward, in reverse topological order, accumulating into a from both of its uses:
f_grad = 1.0
e_grad = a * f_grad              # f = e·a  -> df/de = a = 2
a_grad = e * f_grad              # ... and df/da (direct use) = e = 4
d_grad = 1.0 * e_grad            # e = d + c -> 2
c_grad = 1.0 * e_grad            # 2
a_grad += b * d_grad             # d = a·b -> += -3·2 = -6, so a_grad = -2
b_grad = a * d_grad              # 4
assert (a_grad, b_grad, c_grad) == (-2.0, 4.0, 2.0)
# Analytic check: f = a²b + ac, so df/da = 2ab + c = -2, df/db = a² = 4, df/dc = a = 2.
assert (2 * a * b + c, a * a, a) == (a_grad, b_grad, c_grad)

5. The scalar engine

class Value:
    """A scalar that records how it was made, so gradients can flow back through it."""

    def __init__(self, data, _children=(), _op=""):
        self.data, self.grad = float(data), 0.0
        self._backward = lambda: None
        self._prev, self._op = tuple(_children), _op

    def __add__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data + other.data, (self, other), "+")
        def _backward():
            self.grad += out.grad                       # += : a node may feed several others
            other.grad += out.grad
        out._backward = _backward
        return out

    def __mul__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data * other.data, (self, other), "*")
        def _backward():
            self.grad += other.data * out.grad
            other.grad += self.data * out.grad
        out._backward = _backward
        return out

    def __pow__(self, k):
        assert isinstance(k, (int, float)), "only constant powers"
        out = Value(self.data ** k, (self,), f"**{k}")
        def _backward():
            self.grad += k * self.data ** (k - 1) * out.grad
        out._backward = _backward
        return out

    def relu(self):
        out = Value(max(self.data, 0.0), (self,), "relu")
        def _backward():
            self.grad += (out.data > 0) * out.grad
        out._backward = _backward
        return out

    def tanh(self):
        t = math.tanh(self.data)
        out = Value(t, (self,), "tanh")
        def _backward():
            self.grad += (1 - t * t) * out.grad
        out._backward = _backward
        return out

    def backward(self):
        # Iterative depth-first topological sort: no recursion limit on deep graphs.
        topo, seen, stack = [], set(), [(self, False)]
        while stack:
            node, done = stack.pop()
            if done:
                topo.append(node); continue
            if id(node) in seen:
                continue
            seen.add(id(node))
            stack.append((node, True))
            stack.extend((ch, False) for ch in node._prev if id(ch) not in seen)
        self.grad = 1.0
        for node in reversed(topo):                     # every node after all of its consumers
            node._backward()

    __radd__ = __add__
    __rmul__ = __mul__
    def __neg__(self): return self * -1
    def __sub__(self, other): return self + (-other)
    def __rsub__(self, other): return other + (-self)
    def __truediv__(self, other): return self * other ** -1
    def __rtruediv__(self, other): return other * self ** -1

Each operation computes its result, creates a new Value with the operands as parents, and attaches a closure. The closure captures self, other and out, so when it runs later it can read the forward values and out.grad. Constants are wrapped in Value on the fly so x * 3 works, and __radd__/__rmul__ make 3 * x work too.

The derived operations (negation, subtraction, division) are defined in terms of the primitives, so they need no backward rules of their own. Division by other ** -1 means the power rule supplies the derivative −1/b² automatically.

The topological sort is an iterative depth-first search with an explicit stack of (node, done) pairs. When a node is first popped it is marked visited and pushed back with done = True, followed by its unvisited children; when it is popped with done = True, all its descendants have been appended, so it is appended after them. The result lists every node after its inputs. micrograd uses the same depth-first search written recursively, which is clearer but limited by Python's default recursion limit of 1,000 frames; the test builds a 5,000-step chain to show the iterative version copes.

backward seeds the output's gradient with 1 and calls the closures in reverse order. Visited nodes are tracked by id, so the engine does not depend on Value being hashable by value.

6. The tensor engine

The scalar engine is a teaching tool: it creates one Python object per number and one closure call per arithmetic operation. Real engines make one node per array operation. The Tensor class below is the same design over NumPy arrays.

def unbroadcast(grad, shape):
    """Sum a gradient back down to the shape of an input that was broadcast in the forward pass."""
    while grad.ndim > len(shape):                       # axes broadcasting prepended
        grad = grad.sum(axis=0)
    for axis, size in enumerate(shape):
        if size == 1 and grad.shape[axis] != 1:         # axes broadcasting stretched
            grad = grad.sum(axis=axis, keepdims=True)
    return grad

class Tensor:
    """The same engine over NumPy arrays: one node per array operation instead of per scalar."""

    def __init__(self, data, _children=(), _op=""):
        self.data = np.asarray(data, dtype=float)
        self.grad = np.zeros_like(self.data)
        self._backward = lambda: None
        self._prev, self._op = tuple(_children), _op

    @staticmethod
    def _wrap(x):
        return x if isinstance(x, Tensor) else Tensor(x)

    def __add__(self, other):
        other = Tensor._wrap(other)
        out = Tensor(self.data + other.data, (self, other), "+")
        def _backward():
            self.grad += unbroadcast(out.grad, self.data.shape)
            other.grad += unbroadcast(out.grad, other.data.shape)
        out._backward = _backward
        return out

    def __mul__(self, other):
        other = Tensor._wrap(other)
        out = Tensor(self.data * other.data, (self, other), "*")
        def _backward():
            self.grad += unbroadcast(other.data * out.grad, self.data.shape)
            other.grad += unbroadcast(self.data * out.grad, other.data.shape)
        out._backward = _backward
        return out

    def __matmul__(self, other):
        out = Tensor(self.data @ other.data, (self, other), "@")
        def _backward():
            self.grad += out.grad @ other.data.T          # (N, out) @ (out, in)
            other.grad += self.data.T @ out.grad          # (in, N) @ (N, out)
        out._backward = _backward
        return out

    def relu(self):
        out = Tensor(np.maximum(self.data, 0), (self,), "relu")
        def _backward():
            self.grad += (self.data > 0) * out.grad
        out._backward = _backward
        return out

    def exp(self):
        out = Tensor(np.exp(self.data), (self,), "exp")
        def _backward():
            self.grad += out.data * out.grad
        out._backward = _backward
        return out

    def log(self):
        out = Tensor(np.log(self.data), (self,), "log")
        def _backward():
            self.grad += out.grad / self.data
        out._backward = _backward
        return out

    def sum(self, axis=None, keepdims=False):
        out = Tensor(self.data.sum(axis=axis, keepdims=keepdims), (self,), "sum")
        def _backward():
            g = out.grad
            if axis is not None and not keepdims:
                g = np.expand_dims(g, axis)               # put the summed axis back
            self.grad += np.broadcast_to(g, self.data.shape)
        out._backward = _backward
        return out

    def backward(self):
        topo, seen, stack = [], set(), [(self, False)]
        while stack:
            node, done = stack.pop()
            if done:
                topo.append(node); continue
            if id(node) in seen:
                continue
            seen.add(id(node))
            stack.append((node, True))
            stack.extend((ch, False) for ch in node._prev if id(ch) not in seen)
        self.grad = np.ones_like(self.data)
        for node in reversed(topo):
            node._backward()

    __radd__ = __add__
    __rmul__ = __mul__
    def __neg__(self): return self * -1.0
    def __sub__(self, other): return self + (-Tensor._wrap(other))

Gradients are arrays of the same shape as the data, initialised to zeros.

Matrix multiply. For C = A @ B, the closure adds C.grad @ Bᵀ to A's gradient and Aᵀ @ C.grad to B's: the linear-layer rules from mc11, now attached to an operation instead of written into a model.

Broadcasting. + and * may broadcast, so their closures pass each gradient through unbroadcast, which sums over any leading axes broadcasting added and over any axes where the input had size 1 but the output did not. A bias of shape (4,) added to a (16, 4) matrix therefore receives the column sums of the upstream gradient, which is the db = Σ dz rule of mc11, derived automatically.

Reductions. sum(axis, keepdims)'s backward re-inserts the summed axis (if it was dropped) and broadcasts the upstream gradient back to the input's shape: every input element contributed once to the sum, so each receives the sum's gradient.

exp and log use their own outputs and inputs: d exp(x) = exp(x), d log(x) = 1/x. With these, log-softmax and cross-entropy can be composed, which the tests do, and which the drill shows is numerically fragile.

Training with the engine

Once gradients are automatic, a training loop has the same four steps for any model, and writing them out makes the engine's responsibilities clear. First, zero every parameter's gradient, because backward accumulates. Second, run the forward pass from the parameters and a batch of data to a scalar loss; this records the graph. Third, call loss.backward(), which fills every parameter's .grad. Fourth, update each parameter's data in place (for plain gradient descent, p.data -= lr * p.grad), outside the graph, so the update itself is not recorded. The graph from this step is then discarded, and the next step records a new one. With the tensor engine and the two-layer network from the tests, those four steps are a dozen lines, and changing the architecture (adding a layer, a residual connection, a different loss) changes only the forward pass. That separation, write the forward pass and get the backward pass free, is the whole value of autograd, and it is exactly the workflow of optimizer.zero_grad(), loss.backward() and optimizer.step() in PyTorch.

How the same expression looks in PyTorch

Every line of the hand example has a PyTorch twin. a = torch.tensor(2.0, requires_grad=True) creates a leaf that records operations, like Value(2.0). f = (a * b + c) * a builds the same graph, with nodes whose grad_fn attributes (MulBackward0, AddBackward0) play the role of the closures. f.backward() runs the same reverse topological sweep, and a.grad is −2. Differences are about scale and safety rather than the algorithm: PyTorch's nodes operate on tensors, its backward functions are compiled kernels, intermediate results are freed after use, and only leaves with requires_grad=True keep a .grad by default (intermediate nodes' gradients are discarded unless you call retain_grad()), which saves memory that this lesson's engine spends freely.

7. Testing it

The tests, in order. The scalar engine reproduces the hand example, including a's accumulated −2. It reproduces, to four decimal places, the example in micrograd's README, a deliberately convoluted expression using addition, multiplication, powers, negation, in-place +=, ReLU and division, for which the README states g = 24.7041, dg/da = 138.8338 and dg/db = 645.5773. Finite differences on a function with tanh, division and a reused input agree to 10⁻⁸. A 5,000-step multiplication chain backpropagates without a recursion error and gives the exact derivative 1.0001^5000. The tensor engine computes a two-layer network's composed cross-entropy loss and all four parameter gradients identically to PyTorch's autograd, to 10⁻¹². The scalar and tensor engines agree on a ReLU layer's weight gradient. Finally, the timing: one forward and backward pass of an 8-unit ReLU layer on 256 rows took 230 ms with scalar nodes and 0.62 ms with array nodes, a factor of 371.

def h(xv, yv):
    x, y = Value(xv), Value(yv)
    out = (x * y + x.tanh()) / (y * y + 1) + x * x
    return out, x, y
out, x, y = h(0.7, -1.3); out.backward()
eps = 1e-6
num_x = (h(0.7 + eps, -1.3)[0].data - h(0.7 - eps, -1.3)[0].data) / (2 * eps)

# 5. The tensor engine on a two-layer MLP with a composed cross-entropy, against PyTorch.
rng = np.random.default_rng(0)
Xn, yn = rng.normal(size=(16, 3)), rng.integers(0, 4, 16)
W1n, b1n, W2n, b2n = rng.normal(size=(3, 8)) * 0.5, np.zeros(8), rng.normal(size=(8, 4)) * 0.5, np.zeros(4)
onehot = np.eye(4)[yn]
def tensor_loss(W1, b1, W2, b2):
    z = (Tensor(Xn) @ W1 + b1).relu() @ W2 + b2                         # (16, 4) logits
    logp = z - z.exp().sum(axis=1, keepdims=True).log()                  # log-softmax, composed
    return -(logp * onehot).sum() * (1 / len(yn))
P = [Tensor(t.copy()) for t in (W1n, b1n, W2n, b2n)]
L = tensor_loss(*P); L.backward()
try:
    import torch
    T = [torch.tensor(t, requires_grad=True) for t in (W1n, b1n, W2n, b2n)]
    zt = torch.relu(torch.tensor(Xn) @ T[0] + T[1]) @ T[2] + T[3]
    lt = torch.nn.functional.cross_entropy(zt, torch.tensor(yn)); lt.backward()
    assert np.isclose(L.data, lt.item(), atol=1e-12)
    assert all(np.allclose(p.grad, t.grad.numpy(), atol=1e-12) for p, t in zip(P, T))
except ImportError:
    pass

The README test deserves a comment. Matching someone else's published numbers for an expression you did not design is a much stronger test than your own examples, because it exercises operator combinations you might not think of: right-hand operators (1 + c), in-place addition rebinding a name to a new node (c += ...), and a value (b + a) appearing inside ReLU while its parts appear elsewhere.

8. Numerical and practical traps

Trap 1: assignment instead of accumulation. self.grad = ... in a closure is correct only if the node has a single consumer. The hand example and the README example both fail with it.

Trap 2: wrong traversal order. Running closures in creation order, or breadth-first from the output without a full topological sort, can run a node's closure before all its consumers have contributed. The bug appears only in graphs with shared nodes, which is why simple tests miss it.

Trap 3: recursion depth. A recursive topological sort fails beyond about 1,000 levels. Unrolled loops (an RNN over 2,000 steps, a long chain of scalar operations) reach that quickly. Use an explicit stack.

Trap 4: not zeroing gradients. Calling backward() twice without resetting .grad adds the second gradient to the first. In a training loop, zero the leaves' gradients before each backward pass.

Trap 5: shape mistakes in broadcasting. Without unbroadcast, a bias's gradient has the batch's shape and the update either fails or, with in-place NumPy broadcasting, silently adds the wrong thing.

Trap 6: composed operations that overflow. The tensor engine's composed log-softmax computes exp(z) directly, so logits of 1,000 overflow to infinity and the loss becomes NaN. The drill adds a fused cross-entropy op that subtracts the maximum first, the same fix as mc10, which is why frameworks fuse it.

Trap 7: ReLU at exactly zero. The engine uses [x > 0], so a zero input gets gradient 0, the same convention as PyTorch. Finite differences at that point disagree, as in mc11; it is a kink, not a bug.

Debugging an autograd engine

When an engine gives a wrong gradient, three tools find the cause quickly. First, test each operation alone: build the smallest expression that uses it, with non-trivial values (avoid 0 and 1, which hide multiplication mistakes), and compare with a finite difference. A wrong local derivative shows up immediately. Second, test reuse: an expression where one input appears in two places, such as the hand example, catches assignment-instead-of-accumulation and ordering bugs that single-use expressions never reveal. Third, print the topological order for a small graph and check by eye that every node appears after all of its inputs. For the tensor engine, add a fourth: test every operation with inputs that broadcast in each possible way (a scalar, a row, a column, a full matrix), because the unbroadcast logic is where shape bugs live. With those tests in place, a new operation can be added with confidence in minutes.

9. Edge cases worth naming

Calling backward on a node that does not depend on some leaf leaves that leaf's gradient at zero, which is correct. A value used as both inputs of one operation (x * x) receives two contributions from a single closure, x.grad += x·ḡ twice, giving 2x, which is why even a single operation must use +=. Python's sum() starts from the integer 0, so summing Values works only because __radd__ handles 0 + Value; the tests pass an explicit Value(0.0) start for clarity. Non-scalar outputs need an explicit seed gradient: Tensor.backward seeds with ones, which computes the gradient of the sum of the outputs.

10. Complexity

The forward pass records one node per operation; the backward pass visits each node once and does work proportional to its local derivative computation, so backward costs a small constant multiple of forward: O(V + E) for V nodes and E edges, plus the arithmetic. Memory is O(V) nodes plus every forward value a closure needs, which is why frameworks free saved tensors as soon as their backward has run. The scalar engine's constant factor is huge (a Python object and a closure call per number); the tensor engine's is one NumPy call per array operation, which is why it was 371 times faster here and why real frameworks go further and fuse many operations into one kernel.

11. Talking through the design

In the interview: describe the node (data, grad, parents, closure); write add, mul and one non-linearity with +=; explain the topological sort and why reverse order; seed with 1; show the reused-variable example; then gradient-check and compare with a reference. Close by naming the two invariants every closure must respect, accumulate with += and give each input a gradient of its own shape, because those are the two lines interviewers most often probe with follow-up questions about reuse and broadcasting. If asked to scale it, move to arrays, matrix-multiply rules and unbroadcast; if asked about frameworks, mention saved tensors, version counters, fused ops and graph compilation.

Reverse mode, forward mode and why training uses reverse

Automatic differentiation comes in two directions. Forward mode carries, alongside each value, its derivative with respect to one chosen input direction; one forward pass yields the derivative of every output along that direction (a Jacobian-vector product). Reverse mode, implemented here, records the graph and sweeps backward from one output, yielding that output's derivative with respect to every input in one pass (a vector-Jacobian product). A training loss is one scalar depending on millions or billions of parameters, so reverse mode gets the whole gradient for a few times the cost of the forward pass, where forward mode would need one pass per parameter. Baydin and colleagues' survey lays out both and their costs, and explains why automatic differentiation is neither symbolic differentiation (which manipulates formulas and can blow up in size) nor numerical differentiation (which approximates with finite differences and suffers rounding).

Define-by-run versus graph capture

micrograd and PyTorch's eager mode build the graph as the code runs ("define-by-run"), so Python control flow (loops, conditionals, early exits) just works: the graph is whatever actually executed. The cost is per-operation overhead and no global view for optimisation. Graph-capture systems (JAX's tracing, torch.compile, older static-graph TensorFlow) record the operations once, then optimise the whole graph: fusing element-wise operations into single kernels, planning memory, eliminating redundant work. The autograd logic is the same; what changes is when the graph is known and how much optimisation is possible.

Saved tensors, memory and in-place safety

Every closure in this lesson keeps references to the values it needs: the multiplication's closure keeps both operands, exp keeps its output, log its input. Those references are why training memory is dominated by activations, and why PyTorch frees a node's saved tensors as soon as its backward has run (unless asked to retain the graph). They also create a correctness hazard: if a saved array is modified in place after the forward pass, backward silently uses the modified value. PyTorch attaches a version counter to every tensor, increments it on in-place operations, and checks it when backward unpacks a saved tensor, raising an error rather than returning a wrong gradient. Activation checkpointing (mc11) deliberately drops some saved tensors and recomputes them inside backward.

Higher-order gradients

If the backward closures were themselves built from engine operations (instead of raw floats and NumPy), backward would record a graph of its own, and calling backward on a gradient would give second derivatives. That is how frameworks compute Hessian-vector products (useful for second-order optimisers and some meta-learning) and gradient penalties (used in some GAN and regularisation methods). It costs memory, because the backward graph must be kept, which is why it is opt-in (create_graph=True in PyTorch).

Custom functions: the contract

Frameworks let you add an operation with a hand-written forward and backward (torch.autograd.Function in PyTorch, custom_vjp in JAX). The contract is exactly this lesson's: in forward, compute the output and save what backward needs; in backward, receive the output's gradient and return each input's gradient, shaped like the input, accounting for broadcasting. Fused attention, fused normalisation, chunked cross-entropy and quantisation-aware straight-through estimators are all written this way and verified with torch.autograd.gradcheck, a finite-difference check in float64 on small inputs.

Stop-gradient and detaching

Sometimes you want a value in the forward pass but no gradient through it. Examples: the target network's predictions in reinforcement learning, an exponential-moving-average teacher in self-supervised learning, a carried hidden state when truncating backpropagation through time, and the straight-through estimator, which uses a non-differentiable rounding in the forward pass but pretends it is the identity in the backward pass (common in quantisation-aware training). In engine terms, detaching creates a new leaf with the same data and no parents, so backward stops there. In the scalar engine that is Value(x.data); the straight-through estimator is x + Value(round(x.data) − x.data), whose forward value is the rounded number and whose gradient with respect to x is 1. Knowing how to cut or reroute the graph deliberately is as important as knowing how to build it.

The micrograd lineage

micrograd's README points to a newer single-file "microgpt" that trains a GPT-2-like transformer in dependency-free Python on an improved engine that stores local gradients at forward time instead of per-operation backward closures. Storing the local derivative (a number per edge) rather than a closure is a classic implementation choice, closer to how tape-based autodiff systems work: the backward sweep becomes a loop that multiplies stored local derivatives into accumulated gradients, with no function call per node. It makes the scalar engine faster without changing the algorithm.

Where autograd runs

Every deep-learning training run, of course, but also anywhere a gradient of a program is useful: differentiable simulators and renderers, sensitivity analysis in scientific computing, adversarial-example generation, prompt and embedding optimisation, and probing which input tokens most affect an LLM's output (gradient-based attribution). In all of them the engine is a framework's, and the engineer's job is to write forward code that the engine differentiates correctly and efficiently, and occasionally to add custom operations.

Failure modes and symptoms

Gradients that grow every step. The optimiser diverges even with a tiny learning rate. Cause: gradients not zeroed between backward calls, so they accumulate across steps. Fix: zero before each backward; check that the gradient norm of the first two steps is similar.

"Trying to backward through the graph a second time". Calling backward twice on the same graph after its saved tensors were freed. Usually a bug where part of the previous step's graph is reused (a hidden state carried across batches without detaching). Detach carried state, or retain the graph deliberately.

In-place modification errors. PyTorch complains that a variable needed for gradient computation has been modified. Cause: an in-place operation (x += ..., relu_) on a tensor saved for backward. Fix: use the out-of-place version.

Slow eager loops. A model written as many tiny operations (a Python loop over sequence positions or over individual heads) spends most of its time in per-node overhead rather than arithmetic, the scalar-engine problem at a larger scale. Fix: express the work as fewer, larger array operations, or compile the graph so small operations are fused.

Memory growing over time. A training loop that appends the loss tensor (not its value) to a list keeps every step's whole graph alive. Fix: store loss.item() or a detached copy.

Parameters that never learn. Some weights keep their initial values for the whole run. Cause: they are not connected to the loss (a layer computed but not used, a branch skipped by a condition, or a detach in the wrong place), so backward never reaches them and their gradients stay zero or None. Fix: after the first backward pass, list every parameter whose gradient is None or exactly zero and check each one is supposed to be unused.

Silent wrong gradients in custom ops. A custom backward with a broadcasting or transpose mistake trains, badly. Fix: gradcheck every custom op in float64 on small, non-square shapes with broadcasting, and compare against a composed reference implementation.

Gradients of inputs, not just parameters

Autograd can differentiate the loss, or any output, with respect to inputs as easily as with respect to weights. That is used in production for saliency and attribution (which input tokens or pixels most affect a prediction), for adversarial testing (nudge an input in the gradient's direction to find failures), and for optimising continuous prompts or embeddings while the model's weights stay frozen. The mechanics are this lesson's: mark the input as requiring gradient, run forward, backward from the output of interest, read the input's gradient. The usual caveats apply: raw gradients are noisy and saturate, so attribution methods average them (integrated gradients) or combine them with activations.

What to monitor

Gradient norms per parameter group (and their ratio to weight norms), memory per step (to catch retained graphs), the fraction of parameters with zero or None gradients (to catch disconnected parts of the model, such as a layer accidentally left out of the forward pass), and, for custom operations, gradcheck tests in CI.

A cost estimate

The scalar engine's 230 ms for 256 × 3 × 8 multiply-adds and ReLUs is about 35 microseconds per scalar operation including graph bookkeeping. A 7-billion-parameter transformer's forward pass for one token is about 14 billion floating-point operations; at that rate a scalar engine would need about five days per token. The tensor engine's per-operation overhead is per array, so its cost is dominated by the arithmetic itself, and a GPU framework with fused kernels runs the same token in milliseconds. The algorithm is identical in all three; the granularity of a node is what changes.

The reference for this problem

Andrej Karpathy's micrograd is the reference implementation this lesson follows. Its README describes it as "a tiny Autograd engine" that "implements backpropagation (reverse-mode autodiff) over a dynamically built DAG and a small neural networks library on top of it with a PyTorch-like API", both tiny "with about 100 and 50 lines of code respectively", and notes that "the DAG only operates over scalar values, so e.g. we chop up each neuron into all of its individual tiny adds and multiplies". Its engine accumulates gradients with += in every backward closure, sorts the graph with a depth-first topological sort, seeds the output with gradient 1 and runs closures in reversed order, exactly the design implemented here (with the recursion replaced by an explicit stack). The README's example prints 24.7041 for the forward value and 138.8338 and 645.5773 for the two gradients; this lesson's tests reproduce all three. Its demo trains a two-layer MLP with two 16-node hidden layers as a binary classifier on the moons dataset.

Goal: run the solution, then vary it, break it and time it. Python 3.12 with NumPy; PyTorch only for the optional cross-check.

  1. Run the four blocks as one script. All assertions pass and it prints the README values and the scalar-versus-tensor timing.
  2. Vary the inputs. Work f = (a + b)·(a − c) with a = 3, b = 1, c = 2 by hand: forward values, topological order, every gradient. Check with Value.
  3. Break the accumulation. Change += to = in __mul__'s closure and rerun the hand example and the README example. Which numbers change, and why does x * x now give the wrong derivative?
  4. Break the order. Replace the topological sort with a breadth-first traversal from the output and rerun the README test. Then make the sort recursive and run the 5,000-step chain.
  5. Extend it. Add exp, log and sigmoid to Value, train a tiny logistic regression with it, and compare the gradients with mc2's formula.
  6. Time it. Time the scalar and tensor engines on layers of width 8, 32 and 128.

What to look for: assignment breaks every example with a reused value, the breadth-first order breaks the README example but not simple chains, the recursive sort raises RecursionError, and the scalar engine's time grows with the number of scalar operations while the tensor engine's barely changes. Keep the broken variants: Run each one at least twice with different random inputs. a gradient-check test suite should fail on every one of them, which is a good way to test the tests.

Work it out

The tensor engine's composed cross-entropy (exp, sum, log, multiply by one-hot) overflows on large logits. Add a fused cross-entropy operation to the engine: a single node whose forward uses the stable log-sum-exp and whose backward is (softmax − onehot)/N. Show the composed version fails at logits of 1,000 and the fused one does not.

Answer

The fused node computes the loss from max-shifted logits, saves the log-probabilities, and in its closure forms exp(logp) − onehot, divides by N and multiplies by the upstream gradient. It is one node instead of five, its backward needs no division by small probabilities, and it never exponentiates a large number.

def cross_entropy(logits, targets):
    """A fused op: forward with log-sum-exp, backward (softmax - onehot) / N in one node."""
    z = logits.data - logits.data.max(axis=1, keepdims=True)
    logp = z - np.log(np.exp(z).sum(axis=1, keepdims=True))
    N = len(targets)
    out = Tensor(-logp[np.arange(N), targets].mean(), (logits,), "cross_entropy")
    def _backward():
        g = np.exp(logp); g[np.arange(N), targets] -= 1
        logits.grad += g / N * out.grad
    out._backward = _backward
    return out

big = Tensor(np.array([[1000.0, 1001.0, 1002.0]]))
with np.errstate(over="ignore", invalid="ignore"):
    composed = -((big - big.exp().sum(axis=1, keepdims=True).log()) * np.eye(3)[[0]]).sum()
assert not np.isfinite(composed.data)                    # exp(1000) overflows: inf - inf = nan
fused = cross_entropy(big, np.array([0]))
fused.backward()
assert np.isclose(fused.data, np.log(1 + np.exp(-1) + np.exp(-2)) + 2)
assert np.allclose(big.grad.sum(), 0) and np.isfinite(big.grad).all()

The composed version computes exp(1000) = inf, then log(inf) = inf and 1000 − inf = −inf, and multiplying by the zeros of the one-hot gives 0 × −inf = NaN. The fused op returns the exact loss, log(1 + e⁻¹ + e⁻²) + 2, and a finite gradient that sums to zero. This is precisely why frameworks ship cross_entropy as one operation rather than asking users to compose it.
