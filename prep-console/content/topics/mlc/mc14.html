A photo on a phone has about twelve million pixels, each with three colour values. If the first layer of a vision model were an ordinary fully connected layer with even a thousand outputs, it would need 36 billion weights, and it would have to learn separately that a cat's ear looks the same in the top-left corner as in the bottom-right. Convolutional layers solve both problems with one idea: use a small filter, say 3×3 pixels, and slide the same filter over every position of the image. The layer has only as many weights as the filter, and whatever it learns to detect, it detects everywhere. That idea powered the deep-learning revolution in vision, from AlexNet in 2012 to the ResNets and EfficientNets in production today, and it survives in modern vision transformers, whose first layer is a convolution in disguise.

In an ML coding round, "implement a 2-D convolution and max pooling in NumPy" tests three skills at once. Shape bookkeeping: batches, channels, height and width, padding and stride, and the output-size formula that ties them together (get it wrong and you are in good company: the AlexNet paper's stated 224×224 input does not fit its own first layer, while 227×227 does). Vectorisation: the readable implementation is four nested loops, which took 655 ms on a small batch in this lesson's test; rewriting it as a single matrix multiply, the trick called im2col, took 5 ms. And the backward pass: once a convolution is a matrix multiply, its gradients follow from mc11's linear-layer rule plus one new operation that adds gradients back to the pixels they came from.

There are traps that interviewers enjoy. Deep-learning "convolution" does not flip the kernel. im2col copies each pixel several times over (seven times for AlexNet's first layer), which is why GPU libraries avoid materialising it. Max pooling padded with zeros returns values that were never in the data. And the parameter savings of depthwise-separable convolutions do not always translate into speed.

The lesson starts from the sliding-window picture, gives the equations with shapes, and works a 4×4 example by hand: every output value, the im2col matrix, the stride-2 version and the pooled map. It then writes the loop version, the im2col version, the col2im backward pass, and tests them against each other, against PyTorch's conv2d and autograd to twelve decimal places, against finite differences, and against the AlexNet shapes from Stanford's CS231n notes. The drill builds a depthwise-separable convolution and counts its savings.

The same skills transfer directly to language and multimodal models. A vision-language model's image encoder starts with a patch-embedding convolution; audio models such as Whisper start with 1-D convolutions over spectrogram frames; and the habit of deriving an operation's output shape, writing a loop reference, vectorising it and checking the backward pass against a framework is the workflow for any custom layer you will ever write.

Picture a small square stencil, say 3×3 cells, laid over the top-left corner of an image. Multiply each of the nine pixel values under the stencil by the number written in the matching stencil cell, add the nine products, and write the result in the top-left cell of a new, smaller image. Slide the stencil one pixel right and repeat; at the end of the row, move down a pixel and start again. The new image, the feature map, shows how strongly each part of the original matches the pattern encoded in the stencil. A stencil with negative numbers on the left and positive on the right lights up at vertical edges; one with a bright centre and dark surround lights up at spots. In a convolutional network the stencil values are learned, and a layer has many stencils, called filters or kernels, each producing its own feature map.

A colour image has three channels (red, green, blue), so each filter is really a small block, 3×3×3, and the dot product runs over all channels at once. The next layer's input is the stack of feature maps, so its filters are 3×3×(number of maps). Two settings control the sliding. Stride is how far the stencil moves each time: stride 2 skips every other position and halves the output size. Padding adds a border of extra values (usually zeros) so that the stencil can be centred on edge pixels; with the right padding, the output has the same size as the input.

Counting makes the efficiency concrete. A 3×3 filter over a 3-channel image has 27 weights, plus a bias, whether the image is 32×32 or 4,000×3,000 pixels. A layer of 64 such filters has 1,792 parameters. A fully connected layer mapping a 224×224×3 image to just 64 outputs would need 9.6 million. The convolution does many more multiply-adds than its parameter count suggests, because each weight is reused at every position, which is exactly the property that makes it efficient on hardware built for repeated multiply-adds.

Two properties make convolution powerful. Parameter sharing: the same filter weights are used at every position, so a layer's size does not depend on the image size, and a pattern learned in one place is recognised everywhere. Locality: each output depends only on a small receptive field, matching the fact that nearby pixels are related. Stacking layers grows the receptive field, so deeper layers see larger regions and can respond to larger structures.

Max pooling is the other building block: slide a window (usually 2×2 with stride 2) and keep only the largest value in each. It halves the height and width, keeping the strongest responses and discarding exact positions, which makes the network a little less sensitive to small shifts. It has no weights.

Where the stencil picture breaks: real implementations do not slide anything. Sliding is a loop, and loops are slow. The fast way rearranges the image so that every stencil position becomes a column of a big matrix, and then every filter at every position is a single matrix multiplication, the operation hardware is best at. That rearrangement, im2col, is the core of this problem.

1. The problem as it is usually asked

"Implement conv2d(x, w, b, stride, pad) and maxpool2d in NumPy for batched, multi-channel input. Start with loops, then vectorise. Bonus: the backward pass." Clarify: the layout (NCHW, batch first, as in PyTorch), whether 'convolution' means cross-correlation (yes), padding mode (zeros), whether dilation or groups are needed (usually not), and the input sizes (to sanity-check memory). Then outline: the output-size formula, a loop reference, im2col plus one matrix product, col2im for the backward pass, and tests including a framework comparison.

2. The maths in plain words

Each output value is a dot product between one filter and one receptive field. For output position (i, j) with stride S, the field starts at row i·S and column j·S of the padded input and spans the filter's height and width across all input channels. Multiply element by element, sum, add the filter's bias. Doing this for every image in the batch, every filter, and every output position fills an output array of shape (N, F, OH, OW).

The number of positions along a dimension is how many times a window of size F fits into the padded length W + 2P when moving S at a time: one at the start, plus one more for every full stride that still fits, which is (W + 2P − F)/S + 1. If the division is not exact, the last few pixels are never covered; libraries floor the division and ignore them, which is legal but usually a sign of a mis-sized network.

im2col rearranges the problem. Collect every receptive field of one image, flatten each into a column of length C·KH·KW, and stack the columns side by side: a matrix of shape (C·KH·KW, OH·OW). Flatten each filter into a row of the same length: a matrix of shape (F, C·KH·KW). Then the product of the filter matrix and the column matrix is (F, OH·OW): every filter's dot product with every field, which is the whole convolution, ready to be reshaped to (F, OH, OW).

3. The equations

output size:   OH = (H + 2P − KH)/S + 1,   OW = (W + 2P − KW)/S + 1

convolution (cross-correlation), x padded:
out[n, f, i, j] = b[f] + Σ_c Σ_u Σ_v  w[f, c, u, v] · x[n, c, i·S + u, j·S + v]

im2col:        cols[n] has shape (C·KH·KW, OH·OW)      column p = flattened field at output position p
               W_row = w.reshape(F, C·KH·KW)
               out[n] = W_row @ cols[n] + b              shape (F, OH·OW), then reshape to (F, OH, OW)

backward (upstream dout[n] of shape (F, OH·OW)):
               dW_row = Σ_n dout[n] @ cols[n]ᵀ           → reshape to (F, C, KH, KW)
               db     = Σ_n Σ_p dout[n][:, p]
               dcols[n] = W_rowᵀ @ dout[n]               shape (C·KH·KW, OH·OW)
               dx = col2im(dcols)                        add each entry back to the pixel it came from

max pooling:   out[n, c, i, j] = max over the k×k window at (i·S, j·S);  gradient goes to the argmax

The backward lines are mc11's linear-layer rules with the column matrix playing the role of the input: dW = dout·inputᵀ, dinput = Wᵀ·dout. The single new idea is col2im. In the forward pass, a pixel was copied into several columns (one per receptive field containing it), so in the backward pass its gradient is the sum of the gradients of all those copies. col2im performs exactly that scatter-add.

4. A worked example by hand

One image, one channel, 4×4, and a 2×2 filter that compares each pixel with its lower-right neighbour:

x = [[1, 2, 0, 1],        kernel = [[1,  0],
     [0, 1, 3, 1],                  [0, −1]]
     [2, 1, 0, 2],
     [1, 0, 1, 3]]
  • Output size. (4 − 2 + 0)/1 + 1 = 3 in each direction, so 3×3.
  • First output. The top-left 2×2 field is [[1, 2], [0, 1]]; the dot product with the kernel is 1·1 + 2·0 + 0·0 + 1·(−1) = 0.
  • All outputs. Because the kernel is 1 at the top-left and −1 at the bottom-right, each output is x[i, j] − x[i+1, j+1]: row 0 is 1 − 1, 2 − 3, 0 − 1 = 0, −1, −1; row 1 is 0 − 1, 1 − 0, 3 − 2 = −1, 1, 1; row 2 is 2 − 0, 1 − 1, 0 − 3 = 2, 0, −3.
  • im2col. Flatten each of the 9 fields into a column of 4: the first column is [1, 2, 0, 1], the second (one pixel right) [2, 0, 1, 3], and so on, giving a 4×9 matrix. The flattened kernel is the row [1, 0, 0, −1]; multiplying it by the 4×9 matrix gives the 9 outputs above in one product.
  • Stride 2. (4 − 2)/2 + 1 = 2 positions per direction, at rows and columns 0 and 2: the outputs [[0, −1], [2, −3]], a subsample of the stride-1 map.
  • Max pooling 2×2, stride 2. The four blocks are {1, 2, 0, 1}, {0, 1, 3, 1}, {2, 1, 1, 0}, {0, 2, 1, 3}, with maxima [[2, 3], [2, 3]].

Notice how many columns each pixel appears in at stride 1: the corner pixels belong to one field each, edge pixels to two, and the four central pixels to four. Those counts are both the duplication factor of im2col and the number of gradient contributions col2im must add for each pixel.

import time
import numpy as np

# The hand-worked example: a 4x4 single-channel image and a 2x2 "diagonal difference" kernel.
X_hand = np.array([[1, 2, 0, 1],
                   [0, 1, 3, 1],
                   [2, 1, 0, 2],
                   [1, 0, 1, 3]], dtype=float)
K_hand = np.array([[1, 0],
                   [0, -1]], dtype=float)
# Output size (W - F + 2P)/S + 1 = (4 - 2 + 0)/1 + 1 = 3.
out = np.array([[(X_hand[i:i + 2, j:j + 2] * K_hand).sum() for j in range(3)] for i in range(3)])
assert out.tolist() == [[0, -1, -1], [-1, 1, 1], [2, 0, -3]]          # x[i, j] - x[i+1, j+1]
# im2col: each 2x2 patch becomes a column of 4 numbers; 9 positions -> a 4 x 9 matrix.
cols = np.array([X_hand[i:i + 2, j:j + 2].ravel() for i in range(3) for j in range(3)]).T
assert cols.shape == (4, 9) and cols[:, 0].tolist() == [1, 2, 0, 1]
assert (K_hand.ravel() @ cols).reshape(3, 3).tolist() == out.tolist()   # one matrix product
# Stride 2: only positions (0,0), (0,2), (2,0), (2,2) -> a 2x2 output.
assert out[::2, ::2].tolist() == [[0, -1], [2, -3]]
# 2x2 max pooling with stride 2 keeps the largest value of each block.
pooled = X_hand.reshape(2, 2, 2, 2).max(axis=(1, 3))
assert pooled.tolist() == [[2, 3], [2, 3]]

5. The naive implementation

Four nested loops over images, filters, output rows and output columns, each computing one dot product of a field with a filter; and the same pattern for max pooling.

def out_size(n, k, stride, pad):
    return (n + 2 * pad - k) // stride + 1

def conv2d_loops(x, w, b, stride=1, pad=0):
    """x (N, C, H, W), w (F, C, KH, KW), b (F,) -> (N, F, OH, OW). Readable, slow."""
    N, C, H, W = x.shape
    F, _, KH, KW = w.shape
    xp = np.pad(x, ((0, 0), (0, 0), (pad, pad), (pad, pad)))
    OH, OW = out_size(H, KH, stride, pad), out_size(W, KW, stride, pad)
    out = np.zeros((N, F, OH, OW))
    for n in range(N):
        for f in range(F):
            for i in range(OH):
                for j in range(OW):
                    patch = xp[n, :, i * stride:i * stride + KH, j * stride:j * stride + KW]
                    out[n, f, i, j] = (patch * w[f]).sum() + b[f]
    return out

def maxpool2d_loops(x, k=2, stride=2):
    N, C, H, W = x.shape
    OH, OW = (H - k) // stride + 1, (W - k) // stride + 1
    out = np.empty((N, C, OH, OW))
    for n in range(N):
        for c in range(C):
            for i in range(OH):
                for j in range(OW):
                    out[n, c, i, j] = x[n, c, i * stride:i * stride + k, j * stride:j * stride + k].max()
    return out

This is the reference implementation: easy to read, easy to get right, and directly checkable against the formula. It is also slow. The inner work, an element-wise product and sum over C·KH·KW numbers, is vectorised, but the loops run N·F·OH·OW times in Python; for a batch of 4 images with 8 channels at 32×32 and 16 filters of 3×3 that is 65,536 iterations, 655 ms in the test.

6. The vectorised version: im2col, col2im and pooling

def im2col(x, KH, KW, stride, pad):
    """Unfold every receptive field into a column: (N, C*KH*KW, OH*OW)."""
    N, C, H, W = x.shape
    xp = np.pad(x, ((0, 0), (0, 0), (pad, pad), (pad, pad)))
    OH, OW = out_size(H, KH, stride, pad), out_size(W, KW, stride, pad)
    cols = np.empty((N, C, KH, KW, OH, OW), dtype=x.dtype)
    for ki in range(KH):                      # loop over the small kernel, never over the image
        for kj in range(KW):
            cols[:, :, ki, kj] = xp[:, :, ki:ki + stride * OH:stride, kj:kj + stride * OW:stride]
    return cols.reshape(N, C * KH * KW, OH * OW), OH, OW

def col2im(cols, x_shape, KH, KW, stride, pad):
    """The adjoint of im2col: scatter-add every column entry back to the pixel it came from."""
    N, C, H, W = x_shape
    OH, OW = out_size(H, KH, stride, pad), out_size(W, KW, stride, pad)
    cols = cols.reshape(N, C, KH, KW, OH, OW)
    xp = np.zeros((N, C, H + 2 * pad, W + 2 * pad), dtype=cols.dtype)
    for ki in range(KH):
        for kj in range(KW):
            xp[:, :, ki:ki + stride * OH:stride, kj:kj + stride * OW:stride] += cols[:, :, ki, kj]
    return xp[:, :, pad:pad + H, pad:pad + W]

def conv2d(x, w, b, stride=1, pad=0):
    F, C, KH, KW = w.shape
    cols, OH, OW = im2col(x, KH, KW, stride, pad)
    out = w.reshape(F, -1) @ cols + b[:, None]          # (F, CKK) @ (N, CKK, P) -> (N, F, P)
    return out.reshape(x.shape[0], F, OH, OW)

def conv2d_backward(dout, x, w, stride=1, pad=0):
    """Gradients of sum(dout * conv2d(x, w, b)) with respect to x, w and b."""
    F, C, KH, KW = w.shape
    cols, OH, OW = im2col(x, KH, KW, stride, pad)                     # (N, CKK, P)
    d = dout.reshape(x.shape[0], F, OH * OW)                           # (N, F, P)
    dw = np.einsum("nfp,nkp->fk", d, cols).reshape(w.shape)            # sum over images and positions
    db = d.sum(axis=(0, 2))
    dcols = w.reshape(F, -1).T @ d                                     # (CKK, F) @ (N, F, P)
    dx = col2im(dcols, x.shape, KH, KW, stride, pad)
    return dx, dw, db

def maxpool2d(x, k=2, stride=2):
    N, C, H, W = x.shape
    OH, OW = (H - k) // stride + 1, (W - k) // stride + 1
    out = np.full((N, C, OH, OW), -np.inf)
    for i in range(k):
        for j in range(k):
            out = np.maximum(out, x[:, :, i:i + stride * OH:stride, j:j + stride * OW:stride])
    return out

im2col without looping over the image. The function loops only over the kernel's KH × KW offsets, never over output positions. For a fixed offset (ki, kj), the pixels that offset sees at every output position form a strided slice of the padded input, xp[:, :, ki : ki + S·OH : S, kj : kj + S·OW : S], which has shape (N, C, OH, OW) and is copied into one slot of a (N, C, KH, KW, OH, OW) array. Reshaping that array to (N, C·KH·KW, OH·OW) gives the column matrix. For a 3×3 kernel that is nine slice copies, regardless of the image size.

The convolution. w.reshape(F, -1) @ cols multiplies the (F, CKK) filter matrix by each image's (CKK, P) columns; NumPy broadcasts the matrix product over the batch, giving (N, F, P). Adding b[:, None] broadcasts the bias over positions, and a reshape gives (N, F, OH, OW).

The backward pass. conv2d_backward recomputes the columns, then: dw is an einsum that multiplies each image's output gradient by its columns' transpose and sums over images and positions; db sums the output gradient over images and positions; dcols is the filter matrix's transpose times the output gradient; and col2im undoes the unfolding.

col2im. It mirrors im2col's loop over kernel offsets, but instead of copying a strided slice out of the input, it adds the corresponding slice of the column gradients into a zero array of the padded input's shape, then crops the padding away. Using += on overlapping slices is what sums the contributions of a pixel that appeared in several fields. Gradients that land in the padding are discarded, correctly, because padding is not a parameter or an input.

Max pooling uses the same strided-slice trick: for each of the k × k offsets, take the slice and keep the running element-wise maximum, starting from −∞.

A worked backward pass

Take the hand example and suppose the upstream gradient is all ones, so the loss is simply the sum of the nine outputs. Then the gradient for the kernel weight at position (u, v) is the sum of the input pixels that weight touched across all nine positions: for the top-left weight, the top-left 3×3 block of the image, 1 + 2 + 0 + 0 + 1 + 3 + 2 + 1 + 0 = 10; for the bottom-right weight, the bottom-right 3×3 block, 1 + 3 + 1 + 1 + 0 + 2 + 0 + 1 + 3 = 12. In matrix form that is dW_row = dout · colsᵀ: a row of nine ones times the 9×4 transpose of the column matrix, which sums each row of the column matrix. The gradient for each input pixel is the kernel weights it met, summed over the fields it belongs to: the top-left pixel met only the weight 1, so its gradient is 1; the bottom-right pixel met only −1; a centre pixel met all four weights once each, 1 + 0 + 0 − 1 = 0. Working one case like this by hand is the fastest way to convince yourself that col2im with += is right before trusting the framework comparison.

7. Testing it

The tests check: the vectorised functions reproduce the hand example at stride 1 and 2 and the pooled map; the im2col convolution equals the four-loop one for four combinations of stride and padding on a non-square 9×7 input with 3 channels, and vectorised pooling equals the pooling loops; PyTorch's conv2d with stride 2 and padding 1 gives the same output to 10⁻¹², and its autograd gives the same gradients for the input, the weights and the bias as conv2d_backward, also to 10⁻¹²; central differences on selected input and weight entries, including a corner pixel and the far corner, agree with the analytic gradients to 10⁻⁷; the AlexNet shapes come out as CS231n states (55×55 outputs, a 363 × 3,025 column matrix, 7.1 times as many numbers as the image, and 224 not fitting evenly); zero-padded max pooling returns 0 for an all-negative input; and a 1×1 identity kernel and a vertical-edge kernel behave as expected. Finally, the timing.

rng = np.random.default_rng(0)

assert conv2d(xh, kh, np.zeros(1), stride=2)[0, 0].tolist() == [[0, -1], [2, -3]]
assert maxpool2d(xh)[0, 0].tolist() == [[2, 3], [2, 3]]

# 3. Reference: PyTorch's conv2d and max_pool2d, and its autograd for the backward pass.

    yt = Fn.conv2d(xt, wt, bt, stride=2, padding=1)

Testing the backward pass on an input whose size and padding make some receptive fields overlap the border is deliberate: border pixels belong to fewer fields than interior ones, and padding positions receive gradients that must be thrown away. A col2im that forgets to crop the padding, or uses assignment instead of addition, fails exactly at those positions.

8. Numerical and practical traps

Trap 1: flipped kernels. Signal-processing convolution flips the kernel; deep-learning layers do not. If you use scipy.signal.convolve2d as a reference, flip the kernel first or use its correlation function, or your "reference" disagrees with every framework.

Trap 2: sizes that do not fit. When (W + 2P − F) is not divisible by S, flooring silently drops the last rows and columns. Assert divisibility for layers you design, and remember AlexNet's 224 versus 227.

Trap 3: im2col memory. The column matrix is about KH·KW/S² times larger than the input. For a 3×3 convolution at stride 1 on a batch of 64 images of 224×224 with 64 channels, the input is 205 million numbers and the column matrix 1.85 billion, 7.4 GB in float32. Process the batch in chunks, or use an implicit approach.

Trap 4: padding value for pooling. Pad max pooling with −∞ (and average pooling with zeros but divide only by the count of real pixels, or document that padding counts).

Trap 5: col2im with assignment. Writing xp[...] = cols[...] instead of += keeps only the last field's gradient for each pixel. The test against PyTorch's autograd fails at every interior pixel.

Trap 6: accumulation precision. A convolution's dot products sum C·KH·KW terms (thousands in deep layers). In float16, accumulation must happen in float32, which tensor-core kernels do; a hand-written float16 accumulation drifts.

Trap 7: layout mismatches. Passing NHWC images (height, width, channels last, as most image libraries load them) to NCHW code produces garbage of the right size. Transpose explicitly at the boundary and assert the channel dimension.

9. Edge cases worth naming

A 1×1 convolution is a matrix multiply over channels at every pixel, and im2col reduces to a reshape; the identity-kernel test exercises it. A kernel as large as the input (with no padding) gives a 1×1 output, a fully connected layer over the whole image. Stride larger than the kernel skips pixels entirely; those pixels get zero gradient, which is correct. A batch of one and a single channel must work without special cases. Even kernel sizes have no centre, so "same" padding needs one more pixel on one side than the other; frameworks differ on which side, a common source of off-by-one differences when porting models.

Batch size zero, which can happen at the end of a data loader, should return an empty output of the right shape rather than crash; NumPy's matrix product handles it, but explicit loops and reshapes with -1 sometimes do not. Very large images can make even one image's column matrix too big, so chunking over output rows, not just over the batch, is the general fallback.

10. Complexity

A convolution costs N·F·OH·OW·C·KH·KW multiply-adds; im2col does not change that, it only changes how fast the arithmetic runs, by handing it to an optimised matrix multiply. Memory for im2col is N·C·KH·KW·OH·OW numbers, against N·C·H·W for the input. The backward pass costs about twice the forward (one product for the weight gradient, one for the column gradient) plus the col2im scatter, which is linear in the column matrix's size. Max pooling costs O(N·C·OH·OW·k²) comparisons. For AlexNet's first layer, the forward pass is 55 × 55 × 96 × 363 ≈ 105 million multiply-adds per image; for a 3×3, 64 → 128-channel layer on a 56×56 map, about 231 million.

11. Talking through the design

In the interview: write the output-size formula and check it on an example; write the loop version as the reference; explain im2col with shapes and its memory cost; reshape filters and multiply; then the backward pass as a linear layer plus col2im with +=; then max pooling with −∞ padding and argmax gradient routing. Test against loops, against a framework and with an impulse or identity kernel. If asked about production, mention implicit GEMM, Winograd, layouts and depthwise convolutions' memory-bound behaviour.

A good habit to show: before writing any code, compute the output shape, the parameter count and the multiply-add count for the interviewer's example on the whiteboard. It catches stride and padding mistakes before they become bugs, and it demonstrates the arithmetic fluency that convolution questions are really probing.

Why parameter sharing matters so much

CS231n's AlexNet arithmetic makes the case in two numbers. The first layer's output has 55 × 55 × 96 = 290,400 neurons, each looking at an 11 × 11 × 3 field, so without sharing it would need 290,400 × 364 = 105,705,600 parameters. With one set of weights per filter, it needs 96 × 363 = 34,848 weights plus 96 biases, 34,944 in total, three thousand times fewer. Sharing encodes a prior, translation equivariance: shifting the input shifts the feature map by the same amount. That prior is right for natural images, which is why convolutional networks learned from far less data than fully connected ones, and why removing it (as vision transformers do after the first layer) requires much more data or augmentation to compensate.

How libraries avoid im2col's memory

NVIDIA's cuDNN paper describes lowering convolution to matrix multiplication without materialising the column matrix: the GPU computes tiles of the product, and each thread block builds just the piece of the column matrix it needs in fast on-chip memory, discards it, and moves on (implicit GEMM). Winograd's minimal filtering algorithms compute, for example, a 2×2 output tile of a 3×3 convolution with 16 multiplications instead of 36, at the cost of extra additions and some numerical error, which is why it is used for 3×3 layers in inference. FFT-based convolution turns the operation into element-wise multiplication in the frequency domain and pays off for large kernels. Libraries benchmark the options per layer and per shape and cache the winner.

Max pooling's gradient and its alternatives

The gradient of a max with respect to its inputs is 1 for the winner and 0 for the rest, so max pooling routes each output's gradient to one input position, the argmax; ties are broken by convention (usually the first). Average pooling spreads the gradient evenly. Many modern architectures replace pooling with strided convolutions (learned downsampling) and end with global average pooling over the whole map, which makes the network accept any input size and has no parameters.

Dilated and transposed convolutions

A dilated convolution spaces the kernel's taps apart (a 3×3 kernel with dilation 2 covers a 5×5 area with 9 weights), enlarging the receptive field without more parameters or downsampling; it is used in segmentation and in audio models such as WaveNet. In im2col it only changes which pixels each column gathers. A transposed convolution (often misnamed "deconvolution") is the backward pass of a convolution with respect to its input used as a forward operation: col2im applied to Wᵀ·x. It upsamples, which is why decoders in segmentation and generative models use it. Dumoulin and Visin's guide gives the output-size formulas for every combination.

Depthwise-separable and grouped convolutions

A grouped convolution splits the input channels into g groups and convolves each separately, dividing parameters and multiply-adds by g. Depthwise convolution is the extreme, one group per channel; followed by a 1×1 "pointwise" convolution that mixes channels, it forms the depthwise-separable block of MobileNets, whose cost relative to a standard convolution is about 1/F + 1/K². The drill computes the case of 64 → 128 channels with 3×3 kernels on a 56×56 map: 73,728 parameters and 231 million multiply-adds for the standard layer against 8,768 and 27.5 million, about 8.4 times fewer. The memory-bound caveat in the myths explains why measured speed-ups are smaller.

Receptive fields grow with depth

One 3×3 convolution sees a 3×3 patch. Stack two and each output of the second depends on a 5×5 patch of the input; three give 7×7. Each additional 3×3 layer adds 2 pixels of reach, and each stride-2 layer doubles the reach of everything after it. That is why VGG-style networks replaced large kernels with stacks of 3×3 ones: two 3×3 layers cover the same 5×5 area as one 5×5 layer with 18 weights per channel pair instead of 25, and with a non-linearity in between. The theoretical receptive field of a deep network's final layer usually covers the whole image; the effective receptive field, where outputs are actually sensitive, is much smaller and concentrated near the centre, which is one motivation for adding attention to convolutional backbones.

Convolution in the transformer era

Vision transformers split an image into 16×16 patches and project each to an embedding: a convolution with kernel and stride 16, whose im2col is a pure reshape because patches do not overlap. Convolutional stems (a few small convolutions before the transformer) often train more stably than that single large-stride convolution. In language models, short 1-D convolutions appear in some efficient architectures and in audio front-ends, such as the two 1-D convolutions at the start of Whisper's encoder. The im2col idea carries over directly to one dimension.

Where convolutions run

Image classification, detection and segmentation backbones (ResNet, EfficientNet, ConvNeXt), on-device vision with depthwise-separable networks, video and medical imaging with 3-D convolutions, audio front-ends, the patch embeddings of vision transformers and multimodal LLMs, and the U-Nets inside diffusion models. In all of them the convolution is a library call, and the engineering concerns are memory, layout, precision and the occasional custom variant that needs its own forward and backward.

Failure modes and symptoms

Shape errors deep in a network. A layer's output size is one pixel off what the next layer expects, often from a stride that does not divide evenly or "same" padding with an even kernel. Fix: compute sizes with the formula at design time and assert them in code. A one-line shape assertion after each block costs nothing at run time.

Out-of-memory in a convolution. A custom or fallback implementation materialises im2col for a large batch. Fix: chunk the batch, use the framework's optimised kernel, or use channels-last layout so the library can pick an implicit algorithm.

Disappointing speed-ups. A model redesigned with depthwise-separable convolutions has a third of the operations but runs only slightly faster on a GPU. Cause: memory-bound depthwise layers. Measure wall-clock time per layer, not FLOPs. Profile with the batch size and resolution you will actually serve, because memory-bound and compute-bound layers swap places as those change.

Non-reproducible results. GPU convolution algorithms chosen by benchmarking may differ between runs, and some backward algorithms use non-deterministic atomic additions. Set the framework's deterministic flags when bit-exact reproducibility matters, at some cost in speed.

Ported weights that perform badly. Weights moved between frameworks give poor accuracy because of a flipped kernel, a different channel order (RGB versus BGR), a different layout, or different padding conventions. Run an impulse image through both and compare.

Silent downsampling mismatches. A segmentation model's output is a few pixels smaller than its label map because a stride-2 layer floored an odd size, and the training code crops or resizes the labels to match, shifting every label by a fraction of a pixel. Accuracy suffers slightly and nobody notices. Use input sizes divisible by the network's total stride (32 for most backbones), or pad inputs to the next multiple and crop the outputs back.

Border artefacts. Zero padding tells the network where the image edge is, and some models learn to rely on it, producing worse predictions near borders or when images are tiled for high-resolution inference. Reflection padding, overlapping tiles with the borders discarded, or training on random crops reduce the effect.

What to monitor and tune

Per-layer time and memory (profilers show which convolutions dominate), the algorithms the library selected, utilisation of tensor cores (alignment of channel counts to multiples of 8 or 16 matters), and activation memory, which for high-resolution inputs dominates training memory and motivates activation checkpointing.

A cost estimate

A ResNet-50 forward pass on a 224×224 image is about 4 billion multiply-adds, almost all in convolutions. On a GPU sustaining 100 trillion tensor-core operations per second at good utilisation, that is tens of microseconds per image of arithmetic, which is why batching thousands of images per second is feasible. A NumPy im2col implementation running at a few billion operations per second on a CPU would take a second or two per image, and the four-loop version, at the hundred-fold slowdown measured here, minutes.

The reference for this problem

Stanford's CS231n notes on convolutional networks are the reference for the formulas and numbers used here. They give the output size as (W − F + 2P)/S + 1, with the example that a 7×7 input and a 3×3 filter give a 5×5 output at stride 1 and 3×3 at stride 2. They work through Krizhevsky and colleagues' 2012 architecture: inputs of 227×227×3, a first layer with F = 11, S = 4 and P = 0, so (227 − 11)/4 + 1 = 55 and an output of 55×55×96, and note that the paper's stated 224×224 cannot be right because (224 − 11)/4 + 1 is not an integer. They count 290,400 neurons with 364 parameters each, 105,705,600 without sharing, against 34,944 with it. And they describe im2col for exactly this layer: 11×11×3 blocks stretched into columns of 363, at 3,025 locations, an X_col of size 363 × 3,025, filters stretched into a W_row of 96 × 363, and the convolution as one matrix multiply giving 96 × 3,025, with the caveat that "it can use a lot of memory, since some values in the input volume are replicated multiple times in X_col". This lesson's tests reproduce those shapes.

Goal: run the solution, then vary it, break it and time it. Python 3.12 with NumPy; PyTorch only for the optional cross-checks.

  1. Run the four blocks as one script. All assertions pass and it prints the AlexNet column-matrix shape, its duplication factor and the loop-versus-im2col timing.
  2. Vary the inputs. Use the kernel [[0, 1], [−1, 0]] on the hand image. Predict the 3×3 output by hand (which neighbours does it compare?), then check. Repeat with padding 1 and work out the new output size first.
  3. Break it. Change += to = in col2im and rerun the PyTorch gradient comparison; then remove the final crop. Find which pixels' gradients are wrong in each case.
  4. Break the pooling. Pad an all-negative feature map with zeros before pooling and compare with −∞ padding.
  5. Measure memory. For a batch of 32 images of 3×224×224 and a 3×3 convolution with 64 filters, compute the size of the column matrix in megabytes before running anything, then confirm with cols.nbytes.
  6. Time it. Time the loop and im2col versions for kernel sizes 1, 3 and 7 and for strides 1 and 2.

What to look for: assignment in col2im breaks every pixel that belongs to more than one field while corners still pass; the uncropped version fails on shape; zero padding returns 0 for an all-negative input; the column matrix for that batch is several hundred megabytes; and im2col's advantage grows with kernel size. Note the memory figure next to each timing, because the faster method is also the hungrier one.

Work it out

Implement a depthwise-separable convolution using your conv2d, and compare its parameter count and multiply-adds with a standard 3×3 convolution from 64 to 128 channels on a 56×56 feature map.

Answer

Depthwise: each input channel gets its own K×K filter (C filters of one channel each). Pointwise: a 1×1 convolution mixes channels to produce F outputs.

def depthwise_separable(x, w_dw, w_pw, b_pw, pad=1):
    """w_dw (C, 1, K, K) one filter per channel; w_pw (F, C, 1, 1) mixes channels."""
    per_channel = [conv2d(x[:, c:c + 1], w_dw[c:c + 1], np.zeros(1), 1, pad) for c in range(x.shape[1])]
    return conv2d(np.concatenate(per_channel, axis=1), w_pw, b_pw)

C, F, K, S = 64, 128, 3, 56
std_params = F * C * K * K                     # 73,728
sep_params = C * K * K + F * C                 # 576 + 8,192 = 8,768
std_macs, sep_macs = std_params * S * S, sep_params * S * S
assert (std_params, sep_params) == (73_728, 8_768)
assert round(std_macs / 1e6) == 231 and round(sep_macs / 1e6, 1) == 27.5   # ~8.4x cheaper

xs2 = rng.normal(size=(1, 4, 8, 8))
y = depthwise_separable(xs2, rng.normal(size=(4, 1, 3, 3)), rng.normal(size=(6, 4, 1, 1)), np.zeros(6))
assert y.shape == (1, 6, 8, 8)

The ratio is 1/F + 1/K² = 1/128 + 1/9 ≈ 0.12, so about 8.4× fewer parameters and multiply-adds. The catch: depthwise convolutions have low arithmetic intensity, so on a GPU they are often memory-bound and the wall-clock speed-up is far smaller than the operation count suggests, a useful point to raise unprompted.
