When a chatbot answers a question, it produces its reply one token at a time: compute a probability for every possible next token, pick one, append it, and repeat. A 500-token answer is 500 passes through the model. Done naively, each pass reprocesses the entire conversation so far, so the 500th token costs 500 times as much as the first, and the whole answer costs about 125,000 token-forwards instead of 500. Every production LLM server avoids that waste with a KV cache: it stores the keys and values that each attention layer computed for earlier tokens and reuses them, so each new token needs only its own computation. In this lesson's small test, generating 20 tokens after a 6-token prompt took 310 token-forwards without a cache and 25 with one.

"Implement a small GPT and add KV-cached generation" is one of the most common LLM coding questions, because it tests whether you understand how the pieces of a decoder fit together (embeddings, positions, pre-norm blocks, causal attention, weight-tied output) and whether you can reason about state across steps. The cache is where the subtle bugs live: the new token's position must be the current length, not zero; the causal mask during chunked prefill must account for tokens already cached; each layer needs its own cache; and the cached output must match the uncached one exactly, which is the test interviewers want to see.

The cache is also the heart of LLM serving economics. A Llama-3-8B-sized model needs 128 KiB of cache per token in bf16, 1 GiB for one 8,000-token conversation. The number of conversations a GPU can serve at once, and therefore the cost per token, is set largely by how much cache fits. That is why grouped-query attention (which shrinks the cache four- to eight-fold), paged cache allocation, cache quantisation and prefix sharing are central topics for anyone deploying LLMs, and why interviewers follow the coding question with memory arithmetic.

It is also a rare interview problem where the clean solution and the production solution share the same core: the forty lines of cached attention written here are, line for line, the logic inside every serving engine, wrapped in better memory management.

The lesson builds a tiny GPT in NumPy, works one cached decode step by hand on the three-token example from mc16, writes a naive single-head decode with list caches and the full multi-layer cached generator, and tests that the cache changes nothing but speed: identical greedy outputs, each step equal to the last row of a full pass, chunked prefill equal to single prefill. It also shows why appending to the cache by concatenation is quadratic, and the drill computes cache sizes for a real model configuration.

By the end you should be able to sketch, from memory, the decoder's forward pass, the two-phase generation loop, the exact condition each new query uses to decide which cached keys it may see, and the one-line formula for cache memory, and to explain to a product manager why the number of simultaneous users a GPU can serve depends mostly on that formula.

A GPT-style model is a stack of identical blocks on top of a lookup table. The lookup table, the token embedding, turns each token ID into a vector of d numbers; a second table adds a vector for each position (or, in modern models, positions enter through RoPE, mc17). The resulting sequence of vectors, the residual stream, flows through the blocks. Each block does two things, each as a small detour that adds its result back to the stream: causal self-attention (mc16), where each position gathers information from earlier positions, and a feed-forward network applied to each position separately. Before each detour the stream is normalised (pre-norm). At the end, a final normalisation and a projection onto the vocabulary give, for every position, a score for every possible next token. With weight tying, that projection is the embedding table itself, transposed: the score for token j is the dot product of the final vector with token j's embedding.

Training uses all positions at once: position t's logits are trained to predict token t + 1, and the causal mask makes sure position t cannot peek at it. Generation is different: you have a prompt, you want one new token, then another. The simple way is to run the whole model on the prompt, take the last position's logits, pick a token, append it, and run the whole model again on the longer sequence. Every pass recomputes every earlier position, even though, because of the causal mask, nothing about those positions has changed.

The KV cache removes that waste. Inside every attention layer, each position produces a query, a key and a value; later positions look back at earlier keys and values, and earlier positions never look forward. So once a token's key and value have been computed for a layer, they are final. Store them. To generate the next token, run only the new token through the network: at each layer, compute its query, key and value, append the key and value to that layer's cache, and let its query attend over the whole cache. Everything else in the block (the projections, the feed-forward network) works on one vector instead of the whole sequence.

A useful way to see why this is exact: think of the causal mask as a rule that information only flows forward in time. Token 5's key and value at layer 3 are computed from tokens 1 to 5 only. When token 6 arrives, nothing about tokens 1 to 5 changes, so recomputing their keys and values would produce the same numbers again. The cache simply refuses to compute the same numbers twice. This is also why the cache only works for causal (decoder) attention; a bidirectional encoder's representation of token 5 does depend on token 6.

Generation therefore has two phases. Prefill processes the prompt in one parallel pass, exactly like training, and fills the cache. Decode then loops: one token in, one set of logits out, cache one longer. Prefill is a big burst of matrix-matrix work; decode is a long series of small matrix-vector steps that mainly read weights and cache from memory. Where the picture needs care: the new token must be given its true position, both for the positional embedding and for the mask, and the cache costs memory proportional to layers × heads × tokens, which becomes the limiting resource of an LLM server.

1. The problem as it is usually asked

"Implement a small GPT forward pass in NumPy (embeddings, pre-norm blocks with causal multi-head attention and an MLP, weight-tied output), then a generate function, first naive, then with a KV cache. Show the cache gives the same output." Clarify: greedy decoding is fine for testing (mc20 covers sampling); learned absolute positions or RoPE; one sequence or a batch (one, to keep it short); and whether the cache may grow by concatenation (acceptable in an interview if you say what production does instead). Outline: the model, naive generation, prefill plus decode with per-layer caches and position offsets, and equivalence tests.

2. The maths in plain words

The forward pass, for a sequence of T tokens: look up token embeddings (T × d), add position embeddings for positions start..start+T−1, and for each layer add the attention branch's output and then the MLP branch's output to the stream. Attention splits Q, K, V into heads, scores queries against keys with the causal rule, and mixes values. The final logits are the normalised stream times the transposed embedding matrix.

With a cache, the attention layer receives the new tokens' queries, keys and values and the cached keys and values of everything before them. It appends the new keys and values to the cache, and each new query attends over the full cache. The causal rule needs one adjustment: if S keys are now available and T new tokens were just added, new token t sits at absolute position S − T + t, and may see keys 0 through S − T + t. For a single decode token (T = 1) that is every key, so no masking is needed; for chunked prefill (T > 1) the new tokens must still not see each other's futures.

3. The equations

forward(ids, start):
  x = E[ids] + P[start : start + T]                         (T, d)
  for each layer ℓ:
      x = x + Attn_ℓ(Norm(x), cache_ℓ)                      pre-norm residual
      x = x + W2_ℓ · GELU(W1_ℓ · Norm(x))
  logits = Norm(x) · Eᵀ                                     weight tying, (T, vocab)

Attn with cache (per head):
  q, k, v = split(x · W_qkv)                                 new tokens only
  K = [K_cache; k],  V = [V_cache; v]                        S = len(K) keys
  allowed[t, j] = (j ≤ S − T + t)                            absolute-position causal rule
  out = softmax(qKᵀ/√d_k masked) · V

generate(prompt, n):
  logits = forward(prompt, caches, start = 0)                prefill
  repeat n times:  tok = argmax(logits[−1]);  append tok
                   logits = forward([tok], caches, start = len − 1)   decode

work for n new tokens after a p-token prompt:
  no cache:   Σ_{L=p}^{p+n−1} L token-forwards                p = 6, n = 20 → 310
  cache:      p + (n − 1)                                     → 25

cache memory: 2 × layers × kv_heads × head_dim × tokens × bytes

4. A worked example by hand

Reuse mc16's three tokens, x₁ = [1, 0], x₂ = [0, 1], x₃ = [1, 1], with one head, d_k = 2 and identity projections, so each token's query, key and value equal its vector.

  • Prefill tokens 1 and 2. The cache now holds keys [1, 0], [0, 1] and the same values. (Their attention outputs were computed during prefill: [1, 0] and [0.330, 0.670], as in mc16.)
  • Decode token 3. Compute its query, key and value, all [1, 1]. Append key and value: the cache has three entries.
  • Scores. Query [1, 1] against keys [1, 0], [0, 1], [1, 1]: dot products 1, 1, 2; divided by √2: 0.707, 0.707, 1.414. No mask is needed: a single new token may see all cached keys and itself.
  • Weights. Softmax gives [0.248, 0.248, 0.504], exactly row 3 of mc16's full causal pass.
  • Output. 0.248·[1, 0] + 0.248·[0, 1] + 0.504·[1, 1] = [0.752, 0.752], identical to the full pass.

The decode step did one query's worth of work instead of three, and reproduced the full result exactly, because keys and values 1 and 2 were already final. Now the work count for the test's generation: a 6-token prompt and 20 new tokens. Without a cache, generating the k-th new token re-runs the model on 5 + k tokens, so the total is 6 + 7 + … + 25 = (6 + 25) × 20/2 = 310 token-forwards. With a cache, prefill processes 6 tokens and each of the next 19 decode steps processes one; the 20th token is read from the last step's logits without another pass: 25. The first solution block asserts all of this.

import math
import time
import numpy as np

# The hand-worked example: mc16's three tokens, Q = K = V = X, one head, d_k = 2.
X3 = np.array([[1.0, 0.0], [0.0, 1.0], [1.0, 1.0]])
# Prefill tokens 1 and 2: the cache stores their keys and values.
K_cache, V_cache = X3[:2].copy(), X3[:2].copy()
# Decode step for token 3: its query meets the cached keys plus its own key.
q3 = X3[2]
K = np.vstack([K_cache, X3[2]]); V = np.vstack([V_cache, X3[2]])
s = K @ q3 / math.sqrt(2)                                   # [0.707, 0.707, 1.414]
w = np.exp(s - s.max()); w /= w.sum()
assert np.allclose(w, [0.2483, 0.2483, 0.5035], atol=1e-4)  # the same row as the full causal pass
assert np.allclose(w @ V, [0.7517, 0.7517], atol=1e-4)

# Work saved: generating 20 tokens after a 6-token prompt.
no_cache = sum(range(6, 26))               # every step re-runs the whole sequence: 6 + 7 + ... + 25
with_cache = 6 + 19                        # prefill 6, then one token per decode step (the last token needs no step)
assert (no_cache, with_cache) == (310, 25)

5. The naive implementation: one head, list caches, explicit loops

The simplest possible cached decode step, for one head: append the new key and value to Python lists, compute the new query's scores against every cached key with loops, softmax them, and take the weighted sum of cached values.

def decode_step_naive(q, k_new, v_new, k_list, v_list):
    """One head, one new token: append to Python-list caches, then attend with explicit loops."""
    k_list.append(k_new); v_list.append(v_new)
    d = len(q)
    scores = [sum(qi * ki for qi, ki in zip(q, k)) / math.sqrt(d) for k in k_list]
    m = max(scores); e = [math.exp(x - m) for x in scores]; tot = sum(e)
    return [sum(e[j] / tot * v_list[j][c] for j in range(len(v_list))) for c in range(len(v_new))]

It shows the whole idea in ten lines and is easy to verify by eye. The test runs it position by position over a prompt for one head of the real model's first layer and checks the outputs equal that head's full causal attention. Its cost per step is linear in the cache length but entirely interpreted; the model below does the same with arrays for every head and layer at once.

6. The vectorised model and cached generation

def softmax(z):
    z = z - z.max(-1, keepdims=True); e = np.exp(z)
    return e / e.sum(-1, keepdims=True)

def rms_norm(x, g, eps=1e-6):
    return g * x / np.sqrt((x * x).mean(-1, keepdims=True) + eps)

def gelu(x):
    return 0.5 * x * (1 + np.tanh(np.sqrt(2 / np.pi) * (x + 0.044715 * x ** 3)))

class TinyGPT:
    def __init__(self, vocab, d=32, n_heads=4, n_layers=2, max_T=64, seed=0):
        rng = np.random.default_rng(seed)
        init = lambda *shape: rng.normal(0, 0.1, shape)
        self.h, self.dk = n_heads, d // n_heads
        self.tok, self.pos = init(vocab, d), init(max_T, d)
        self.layers = [dict(g1=np.ones(d), Wqkv=init(d, 3 * d), Wo=init(d, d),
                            g2=np.ones(d), W1=init(d, 4 * d), W2=init(4 * d, d)) for _ in range(n_layers)]
        self.g_final = np.ones(d)
        self.tokens_processed = 0

    def attn(self, L, x, cache):
        T, D = x.shape
        q, k, v = np.split(x @ L["Wqkv"], 3, axis=-1)
        heads = lambda t: t.reshape(T, self.h, self.dk).transpose(1, 0, 2)      # (h, T, dk)
        q, k, v = heads(q), heads(k), heads(v)
        if cache is not None:
            if "k" in cache:                                   # append to what earlier steps stored
                k = np.concatenate([cache["k"], k], axis=1)
                v = np.concatenate([cache["v"], v], axis=1)
            cache["k"], cache["v"] = k, v
        S = k.shape[1]                                         # keys available: past + new
        scores = q @ k.transpose(0, 2, 1) / np.sqrt(self.dk)   # (h, T, S)
        # new query t sits at absolute position S - T + t and may see keys 0 .. S - T + t
        allowed = np.arange(S)[None, :] <= (S - T + np.arange(T))[:, None]
        scores = np.where(allowed, scores, -np.inf)            # every row keeps at least itself
        return (softmax(scores) @ v).transpose(1, 0, 2).reshape(T, D) @ L["Wo"]

    def forward(self, ids, caches=None, start=0):
        self.tokens_processed += len(ids)
        x = self.tok[ids] + self.pos[start:start + len(ids)]
        for i, L in enumerate(self.layers):
            x = x + self.attn(L, rms_norm(x, L["g1"]), None if caches is None else caches[i])   # pre-norm
            x = x + gelu(rms_norm(x, L["g2"]) @ L["W1"]) @ L["W2"]
        return rms_norm(x, self.g_final) @ self.tok.T          # weight tying: logits (T, vocab)

    def generate(self, prompt, n_new, use_cache=True):
        ids = list(prompt)
        if not use_cache:
            for _ in range(n_new):                             # recompute everything every step
                ids.append(int(self.forward(np.array(ids))[-1].argmax()))
            return ids
        caches = [{} for _ in self.layers]
        logits = self.forward(np.array(ids), caches)           # prefill: the whole prompt at once
        for step in range(n_new):
            ids.append(int(logits[-1].argmax()))
            if step < n_new - 1:                               # decode: one new token per step
                logits = self.forward(np.array(ids[-1:]), caches, start=len(ids) - 1)
        return ids

Structure. TinyGPT holds a token table, a learned position table, and per layer a fused Q/K/V projection (Wqkv, d × 3d, as in nanoGPT's c_attn), an output projection, two RMSNorm gains and the MLP's two matrices. The final RMSNorm feeds logits computed with self.tok.T: weight tying.

attn with a cache. The cache for a layer is a dictionary holding k and v of shape (h, S, d_k). New keys and values are concatenated after the cached ones and stored back. The causal rule uses absolute positions: allowed[t, j] = j ≤ S − T + t. For a decode step (T = 1) it allows every key; for a full forward without a cache (S = T) it is the usual lower triangle; for chunked prefill it is a lower triangle shifted right by the number of cached tokens.

forward takes a start offset so position embeddings match each token's absolute position, and a list of per-layer caches (or None). It counts processed tokens, which the tests use to confirm the 310-versus-25 arithmetic.

generate has both modes. Without a cache it re-runs the growing sequence each step. With one, it prefills the prompt, then for each new token appends the argmax of the last logits and runs a one-token forward at start = len(ids) − 1, skipping the pass after the final token.

Cache memory, worked

The formula is short enough to do in your head: two tensors (keys and values) per layer, each holding KV heads × head dimension numbers per token, at the cache's precision. For the Llama-3-8B shape that is 2 × 32 × 8 × 128 = 65,536 numbers per token, 131,072 bytes in bf16, 128 KiB. Multiply by context length for one conversation and by the number of concurrent conversations for a server. Three things change the answer by large factors: the number of KV heads (GQA's 4× here), the precision (an 8-bit cache halves it), and whether some layers use a sliding window, whose cache stops growing at the window size. Weights, by contrast, are fixed: 16 GB for 8 billion bf16 parameters regardless of traffic. On a busy server the cache, not the model, is what runs out.

Batching generation

The class here generates one sequence at a time. Real servers generate many at once, and that changes three things. Prompts have different lengths, so either they are left-padded to a common length (each sequence then needs its own positions, starting at its first real token, and a padding mask over keys), or the server stores sequences raggedly with per-sequence caches and offsets, which paged caches make natural. Sequences finish at different times, so finished ones are removed and new ones inserted between steps (continuous batching). And the decode step becomes a small batched matrix multiply, (batch, d) times (d, ·), which reuses each weight read across all sequences, the main reason batching raises throughput so much. None of this changes the per-sequence logic tested here; it changes the bookkeeping around it.

Choosing the next token

The generator uses argmax (greedy decoding) because it is deterministic, which makes the cached-versus-uncached test exact. Real systems usually sample from the softmax of the last logits with a temperature, top-k or top-p filter (mc20). The cache is unaffected by the choice: it depends only on which tokens were appended, not on how they were chosen. For testing sampled generation, fix the random seed and draw from identical logits in both paths.

7. Testing it

The tests check: the naive list-cache step reproduces the hand example; greedy generation of 20 tokens is identical with and without the cache, and the processed-token counts are 310 and 25; feeding tokens one at a time through the cache gives, at every step, logits equal to the last row of a full forward pass on the whole sequence, and the first layer's cache grows by one entry per step; a prompt prefilled in two chunks (4 then 2 tokens) gives the same final logits as one prefill; the naive one-head loop equals the model's first-layer, first-head causal attention over the prompt; weight tying holds; growing a cache by concatenation is far slower than writing into a preallocated buffer (573 ms against 1.9 ms for 1,500 appends); and cached generation of 40 tokens is faster in wall time.

rng = np.random.default_rng(0)

# 1. The naive list cache reproduces the hand-worked decode step.
kl, vl = [list(X3[0]), list(X3[1])], [list(X3[0]), list(X3[1])]
assert np.allclose(decode_step_naive(list(X3[2]), list(X3[2]), list(X3[2]), kl, vl), [0.7517, 0.7517], atol=1e-4)

# 2. Cached generation equals recomputing everything; and it processes far fewer tokens.
model = TinyGPT(vocab=50)
prompt = [3, 14, 15, 9, 2, 6]
model.tokens_processed = 0; slow = model.generate(prompt, 20, use_cache=False); n_slow = model.tokens_processed
model.tokens_processed = 0; fast = model.generate(prompt, 20); n_fast = model.tokens_processed
assert slow == fast and (n_slow, n_fast) == (310, 25)

# 3. Step by step: each cached decode step reproduces the last row of a full forward pass.
ids = list(prompt)
caches = [{} for _ in model.layers]
model.forward(np.array(ids), caches)
for tok in [7, 1, 8]:
    ids.append(tok)
    step_logits = model.forward(np.array([tok]), caches, start=len(ids) - 1)[-1]
    assert np.allclose(step_logits, model.forward(np.array(ids))[-1])
assert caches[0]["k"].shape == (model.h, len(ids), model.dk)     # the cache grows by one per step

# 4. Chunked prefill (prompt in two pieces) matches a single prefill.
c1 = [{} for _ in model.layers]
model.forward(np.array(prompt[:4]), c1)
assert np.allclose(model.forward(np.array(prompt[4:]), c1, start=4)[-1], model.forward(np.array(prompt))[-1])

# 5. The naive per-head decode step equals the model's attention for one head of the first layer.
L = model.layers[0]
xin = rms_norm(model.tok[np.array(prompt)] + model.pos[:len(prompt)], L["g1"])
qkv = xin @ L["Wqkv"]; d = qkv.shape[1] // 3
q, k, v = qkv[:, :d], qkv[:, d:2 * d], qkv[:, 2 * d:]
head = slice(0, model.dk)
kl, vl, outs = [], [], []
for t in range(len(prompt)):
    outs.append(decode_step_naive(list(q[t, head]), list(k[t, head]), list(v[t, head]), kl, vl))
full_scores = q[:, head] @ k[:, head].T / np.sqrt(model.dk)
full_scores = np.where(np.tril(np.ones((6, 6), bool)), full_scores, -np.inf)
assert np.allclose(outs, softmax(full_scores) @ v[:, head])

# 6. Weight tying: the output layer is the token embedding matrix transposed.
h_last = rng.normal(size=32)
assert np.allclose(rms_norm(h_last, model.g_final) @ model.tok.T, model.tok @ rms_norm(h_last, model.g_final))

# 7. Concatenating onto the cache every step copies it every step; a preallocated buffer does not.
steps, hd = 1500, (4, 64)
t0 = time.perf_counter()
cache = np.zeros((hd[0], 0, hd[1]))
for _ in range(steps):
    cache = np.concatenate([cache, np.ones((hd[0], 1, hd[1]))], axis=1)
t_concat = time.perf_counter() - t0
t0 = time.perf_counter()
buf = np.zeros((hd[0], steps, hd[1]))
for t in range(steps):
    buf[:, t] = 1.0
t_prealloc = time.perf_counter() - t0
assert np.array_equal(cache, buf) and t_concat > 3 * t_prealloc

# 8. Wall time: cached vs uncached generation of 40 tokens.
t0 = time.perf_counter(); model.generate(prompt, 40, use_cache=False); t_slow = time.perf_counter() - t0
t0 = time.perf_counter(); model.generate(prompt, 40); t_fast = time.perf_counter() - t0
if __name__ == "__main__":
    print(f"tokens processed for 20 new: no cache {n_slow}, cache {n_fast}")
    print(f"cache growth over 1,500 steps: concatenate {t_concat*1e3:.0f} ms, preallocated {t_prealloc*1e3:.1f} ms")
    print(f"generate 40: no cache {t_slow*1e3:.0f} ms, cache {t_fast*1e3:.0f} ms ({t_slow/t_fast:.1f}x)")

The step-by-step comparison is the strongest test, because it isolates each decode step: any error in the position offset, the mask or the cache update shows up at the first step where it matters, with a precise location, instead of as a different token somewhere in a long generation. Comparing generated tokens alone can miss small logit errors that happen not to change the argmax.

The wall-time saving in the test, 2.4 times for 40 tokens, is far smaller than the 12-fold reduction in token-forwards, and the gap is instructive. TinyGPT is tiny (d = 32, two layers), so each forward pass is dominated by Python and NumPy call overhead, which is roughly the same whether the pass processes one token or forty. The cached path also concatenates arrays every step. In a real model, each forward pass is dominated by the arithmetic and memory traffic of large matrices, which scale with the number of tokens processed, so the measured speed-up approaches the token-forward ratio for long generations. Measuring both the operation count and the wall time, and explaining the difference, is the habit that makes performance claims trustworthy.

8. Numerical and practical traps

Trap 1: the position offset. The new token's positional embedding (or RoPE angle) must use its absolute position. Using 0 makes every new token look like the start of the text; using an off-by-one makes distances wrong by one. The step-by-step test catches both.

Trap 2: the chunk mask. When several new tokens are processed at once against a cache, the mask must be the shifted triangle, not the plain one (which would hide all cached keys from the first new tokens) and not "allow all" (which would let them see each other's futures). The chunked-prefill test checks it.

Trap 3: one cache for all layers. Each layer has its own keys and values. Sharing one dictionary across layers overwrites them, and outputs diverge immediately.

Trap 4: quadratic cache growth. np.concatenate allocates a new array and copies the old cache every step, so total copying is O(T²). For a tiny model it is invisible; for long generations it dominates. Preallocate to the maximum length and write in place, or allocate in blocks (paging).

Trap 5: −∞ masks. Safe here because every query can at least see itself; with left padding a padded position's row can be fully masked, and −∞ then gives NaN (mc16). Use a finite value or skip padded rows.

Trap 6: precision drift. A bfloat16 cache and a float32 reference will disagree slightly and the disagreement grows along the sequence; that is expected. In float64 or float32 the cached and uncached paths should agree to rounding error, and any larger difference is a bug.

9. Edge cases worth naming

Generating past the position table's length fails with learned absolute positions (the model has no embedding for position 1,025 in GPT-2); RoPE models instead degrade gradually (mc17). A prompt of length one has a one-token prefill. Generating zero new tokens should return the prompt unchanged, which the step-skipping logic handles. A batch of prompts with different lengths needs either left padding with per-sequence positions and masks, or a ragged representation, which is what paged caches make convenient. And stopping conditions (an end-of-sequence token, a maximum length) belong in the loop, before the next forward pass, so no wasted step is run.

10. Complexity

For a model with L layers and width d, a forward pass over T tokens costs about L·(12·T·d² + 2·T²·d) multiply-adds (projections and MLP, plus attention). Generating n tokens after a prompt of p without a cache sums that over every length from p to p + n − 1, roughly O(L·n·(p + n)·d²) for the dense parts. With a cache, prefill costs one pass over p tokens and each decode step L·(12·d² + 2·S·d) for a cache of length S, so the dense work is linear in n and only the attention over the cache grows with length. Cache memory is 2·L·h_kv·d_k numbers per token. For GPT-2 small in float32 (L = 12, d = 768, no GQA) that is 2 × 12 × 768 × 4 bytes = 72 KiB per token.

11. Talking through the design

In the interview: write the block (pre-norm, causal attention, MLP), weight-tied logits, and naive generation; explain why keys and values of earlier tokens never change; add per-layer caches, prefill, decode with the position offset, and the absolute-position mask; then test cached against uncached at every step. Follow with cost: the 310-versus-25 count, cache memory per token, and the memory-bound nature of decoding that leads to batching, GQA and paged caches.

A strong closing move is to state the invariant your tests enforce, in one sentence: for every step, the cached path's logits equal the last row of an uncached forward pass over the same tokens. Every optimisation a serving system adds, from paging to prefix sharing to speculative verification, is judged against that invariant, so naming it shows you know how such systems are kept correct as they get faster.

Why decoding is memory-bound

During a decode step, each weight matrix is multiplied by a single vector: two floating-point operations per weight read. A GPU can perform hundreds of operations in the time it reads one weight from high-bandwidth memory, so for a single sequence it spends most of its time waiting for memory. Pope and colleagues' analysis of transformer inference makes this quantitative and shows the same is true of the KV cache at long context: every step reads the whole cache. The standard remedies all follow from it. Batching many sequences per step reuses each weight read across the batch. Quantising weights and caches reduces the bytes read. Multi-query and grouped-query attention cut the cache's bytes. Speculative decoding verifies several draft tokens in one step, turning matrix-vector work into small matrix-matrix work.

Continuous batching and paged caches

Requests arrive and finish at different times with different lengths. Static batching waits for a whole batch to finish, wasting slots on finished requests. Continuous batching inserts new requests and removes finished ones at every decode step, keeping the batch full. That only works if each request's cache can grow independently without copying, which is what PagedAttention provides: the cache is stored in fixed-size blocks (for example 16 tokens), each request has a block table mapping logical positions to physical blocks, and attention kernels read through the table. Kwon and colleagues report that this nearly eliminates memory waste from fragmentation and over-reservation and allows sharing blocks between requests with a common prefix, improving throughput by two to four times over earlier systems.

Prefix caching

Many requests share long prefixes: a system prompt, a few-shot template, a document asked about repeatedly. Their KV caches for the shared prefix are identical, so a server can compute them once and reuse the blocks for every request that starts the same way, skipping that part of prefill entirely. The correctness argument is the one this lesson tests: keys and values at a position depend only on tokens up to that position. The engineering problem is lookup (hashing token blocks) and eviction.

Speculative decoding

A small draft model proposes k tokens; the large model processes all k in one forward pass with the cache (a chunked step, like the test's two-piece prefill) and accepts the longest prefix consistent with its own distribution, using a rejection-sampling rule that keeps the output distribution exactly the large model's. When the draft is often right, several tokens are produced per expensive step. The chunked-prefill mask from this lesson is exactly what verification needs.

Weight tying, initialisation and scale

nanoGPT ties wte.weight to lm_head.weight, initialises weights with standard deviation 0.02, and scales the residual output projections by 1/√(2·n_layer), following GPT-2, so that the residual stream's variance does not grow with depth. With tying, the logit for token j is the dot product of the final hidden state with token j's input embedding, which encourages tokens used in similar contexts to have similar embeddings. For a 50,257-token vocabulary and d = 768 the tied matrix is 38.6 million parameters, almost a third of GPT-2 small; for a 70-billion-parameter model with a 128,000-token vocabulary and d = 8,192 it is about 1 billion, small enough that many large models untie the output layer for flexibility.

GQA in the cache code

With grouped-query attention, the Q/K/V projection produces h query heads but only h_kv key and value heads, and only the h_kv heads are cached. In the attention step, each group of h/h_kv query heads attends to its shared key/value head; in NumPy that is a reshape of the queries to (h_kv, h/h_kv, T, d_k) against keys of shape (h_kv, 1, S, d_k), which broadcasting expands without copying. Nothing else in prefill, decode or the position logic changes, which is why converting a model's serving code to GQA is mostly a matter of shapes, and why the cache shrinks by exactly h/h_kv.

Cache compression at long context

At very long contexts the cache dominates memory even with GQA. Options in use: quantising cached keys and values to 8 or 4 bits (keys often need per-channel scales because of outlier dimensions), sliding-window attention in some layers so their cache holds only the last few thousand tokens, keeping a few initial "sink" tokens plus a recent window for streaming (mc16's attention sinks), and evicting tokens that recent queries rarely attend to. Each saves memory at some risk to quality, measured with long-context retrieval tests rather than perplexity alone.

Sliding-window layers

Some models restrict attention in some or all layers to the most recent W tokens (for example 4,096). For those layers the cache becomes a ring buffer of W entries: each new key and value overwrites the oldest, positions keep counting up (RoPE uses the true position), and the mask allows only keys within the window. Memory per sequence for those layers stops growing at W tokens, which is why mixing sliding-window and full-attention layers is a popular way to support long contexts cheaply. The chunked-prefill and decode logic in this lesson carries over, with the window added to the allowed-key condition.

Where this runs

Every LLM serving stack (vLLM, TensorRT-LLM, SGLang, Hugging Face TGI, llama.cpp) implements exactly this structure: a prefill pass that fills a per-layer KV cache, and decode steps that append to it. The differences are in how the cache is stored (paged blocks, quantised), how requests are batched (continuously), and how kernels read the cache efficiently.

Failure modes and symptoms

Cached and uncached outputs disagree. Usually a position offset, a mask bug in chunked prefill, or a shared cache across layers. The step-by-step comparison localises it to the first bad step.

Out-of-memory under load. The server works for one user and fails at 50 concurrent long conversations. Cache memory scales with total tokens in flight. Cap concurrent tokens, use paged allocation with admission control, quantise the cache, or move to a GQA model. Plot cache utilisation against request volume to see the cliff before users do.

Latency spikes when long prompts arrive. A large prefill monopolises the GPU and every in-flight decode stalls. Chunked prefill interleaves pieces of the long prompt with decode steps; disaggregated serving runs prefill on separate hardware.

Throughput far below expectations. Batch size one, memory-bound decode. Enable continuous batching; check the GPU's memory bandwidth utilisation rather than its FLOP utilisation. A decode-heavy workload at 30% of peak FLOPs can still be saturating memory bandwidth.

Quality drops on long chats. The conversation exceeds the trained context, a sliding window evicts important early tokens, or cache quantisation is too aggressive. Evaluate long-context tasks at realistic lengths with the production cache settings.

Non-determinism across batch sizes. The same prompt gives slightly different outputs when served alone and in a busy batch. Batched kernels sum in different orders, and with bf16 the small differences can change an argmax several hundred tokens in. This is usually acceptable but surprises teams that compare transcripts; when exact reproducibility matters, fix the batch composition or use deterministic kernels, and compare log-probabilities rather than text.

Prefix-cache false sharing. Two requests share a cached prefix that is not actually identical (a different system prompt version, a different tokenizer normalisation), producing subtly wrong outputs for one of them. Key prefix caches on exact token IDs and model version, never on raw text. Log the hit rate too.

What to monitor

Time to first token and time per output token (separately, as percentiles), tokens in flight and cache memory utilisation, prefix-cache hit rate, batch size per decode step, and occasional cached-versus-uncached spot checks on fixed prompts to catch numerical regressions after kernel or configuration changes.

A cost estimate

A Llama-3-8B-sized model in bf16 has about 16 GB of weights. On an 80 GB GPU that leaves roughly 40 GB for the cache after activations and overheads. At 128 KiB per token (32 layers, 8 KV heads, head dimension 128), that is about 300,000 cached tokens: 37 conversations of 8,192 tokens, or 150 of 2,000. Each decode step must read the 16 GB of weights once for the whole batch plus every active conversation's cache; at about 3 TB/s of memory bandwidth, reading the weights alone takes roughly 5 ms, so a single conversation gets at most about 200 tokens per second while a batch of 37 shares that same weight read. That arithmetic is why batch size, set by cache memory, sets serving cost.

The reference for this problem

Karpathy's nanoGPT model.py is the reference implementation this lesson's model follows. Its blocks are pre-norm, x = x + self.attn(self.ln_1(x)) then the MLP branch likewise; attention uses a fused c_attn projection to 3 × n_embd split into q, k, v, and PyTorch's scaled_dot_product_attention with is_causal=True; the token embedding and output head share weights (self.transformer.wte.weight = self.lm_head.weight, commented as weight tying); and the default configuration is GPT-2 small: block_size = 1024, vocab_size = 50304 ("GPT-2 vocab_size of 50257, padded up to nearest multiple of 64 for efficiency"), 12 layers, 12 heads and 768 dimensions. Its initialisation uses standard deviation 0.02, with residual projections scaled by 0.02/√(2·n_layer). This lesson's TinyGPT keeps that structure at toy size, uses RMSNorm without biases, and adds the per-layer KV cache whose correctness the tests establish.

Goal: run the solution, then vary it, break it and time it. Python 3.12 with NumPy only.

  1. Run the four blocks as one script. All assertions pass and it prints the token-forward counts, the concatenation-versus-preallocation timing and the generation timing.
  2. Vary the inputs. Count by hand the token-forwards for a 10-token prompt and 50 new tokens with and without a cache, then confirm with tokens_processed.
  3. Break the offset. Call the decode step with start=0 and rerun the step-by-step test. At which step does it fail? Then use start=len(ids) (off by one).
  4. Break the mask. In attn, replace the absolute-position mask with a plain lower triangle of size T and rerun the chunked-prefill test; then with "allow everything".
  5. Break the cache. Pass the same dictionary to every layer and compare generations.
  6. Improve it. Replace concatenation with a preallocated (h, max_T, d_k) buffer and a length counter per layer, and time generation of 60 tokens before and after.
  7. Measure it. Print the cache's total bytes after generation and compare it with the formula 2 × layers × heads × head dimension × tokens × 8 bytes for float64.

What to look for: the offset bugs fail on the first decode step, the plain triangle hides cached keys from the second chunk, "allow everything" leaks the future within the chunk, the shared cache diverges at once, and preallocation removes the quadratic copying while leaving outputs bit-identical. Rerun the step-by-step test after every change (and the generation-equality test); it is the safety net that makes such optimisations safe.

Work it out

Write a function for the KV-cache size and use it for Llama-3-8B (32 layers, 8 KV heads, head dimension 128, bf16). How much cache does one 8,192-token conversation need, and how many such conversations fit in the 40 GB left on an 80 GB GPU after the weights? What if the model used 32 KV heads (no GQA)?

Answer 
def kv_cache_bytes(layers, kv_heads, head_dim, tokens, bytes_per_value=2):
    return 2 * layers * kv_heads * head_dim * tokens * bytes_per_value      # 2 = keys and values

per_token = kv_cache_bytes(32, 8, 128, 1)
per_conv = kv_cache_bytes(32, 8, 128, 8192)
assert per_token == 131_072                        # 128 KiB per token
assert per_conv == 1024 ** 3                       # exactly 1 GiB per 8k-token conversation
assert int(40e9 // per_conv) == 37                 # ~37 concurrent 8k conversations
assert kv_cache_bytes(32, 32, 128, 8192) == 4 * per_conv    # without GQA: 4 GiB each, ~9 fit

128 KiB per token, 1 GiB per 8k conversation, so about 37 concurrent conversations in 40 GB. Without GQA (32 KV heads) each conversation needs 4 GiB and only 9 fit. GQA's 4× reduction translates directly into 4× more concurrent users, and into faster decoding, because at long context the cache is read every step just like the weights.
