A bank's fraud team gets 50,000 card transactions a minute and can afford to put 200 of them in front of a human reviewer. They do not need a yes/no verdict for each transaction; they need a number between 0 and 1 for each one, a probability of fraud, so they can sort, pick the top 200, and also tell finance "we expect about 31 frauds in this batch". Linear regression from mc1 cannot give them that: a weighted sum can be −4 or 17, and neither is a probability. Logistic regression takes the same weighted sum and squeezes it through an S-shaped curve into the range 0 to 1, and it is trained so that those numbers behave like honest probabilities.

That makes it the most-asked classical implementation in ML coding rounds, and the questions are predictable. Can you write the sigmoid? Can you write the loss? Can you derive the gradient on the whiteboard? And then the one that separates candidates: what happens when your code meets a logit of 40? The textbook formulas, typed literally, compute log(1 − 1.0), get minus infinity, and from that moment every number in the training run is NaN ("not a number"). The fraud model trained fine for months and then, on the day one merchant's transactions became extremely predictable, the nightly job died. That bug is in a large fraction of hand-written logistic regressions, and interviewers know it.

This round tests three things at once. The maths: the cross-entropy loss and its famously clean p − y gradient. The numerics: computing the sigmoid and the loss so that no number ever overflows or hits log(0). And the engineering: a vectorised implementation, a stopping rule, and tests you can trust, including a check against PyTorch's own fused loss.

The lesson builds it from zero. It explains the sigmoid, probabilities, odds and the loss in plain words, then derives the equations, then does one full gradient step by hand on four points with every number shown. Then it writes the naive loop version, the vectorised version with a stable sigmoid and a logits-based loss, and a test suite: the hand step, the overflow cliffs at z ≈ 37 in float64 and z ≈ 17 in float32, a finite-difference gradient check, the loop matching the vectorised code to ten decimals, and PyTorch's BCEWithLogitsLoss agreeing on loss and gradient. It finishes with separable data, Newton's method, complexity, the multi-class extension and what breaks at the scale of billions of clicks.

Think of logistic regression as two machines bolted together. The first is the linear model you already built in mc1: multiply each feature by a weight, add them up, add a constant. Its output is called the logit, written z, and it can be any real number. Large positive means "strongly yes", large negative "strongly no", zero "can't tell". The second machine is the sigmoid, σ(z) = 1 / (1 + e^−z), which turns any logit into a probability: σ(0) = 0.5, σ(2) = 0.88, σ(−2) = 0.12, σ(10) = 0.99995. It is smooth, always increasing, and never quite reaches 0 or 1.

Why this particular squashing function? Because the logit has a meaning. If p is the probability of yes, then p / (1 − p) is the odds (0.8 probability is 4-to-1 odds), and the logarithm of the odds, the log-odds, is exactly z. So logistic regression assumes that each feature adds a fixed amount to the log-odds. A weight of 0.7 means "one more unit of this feature multiplies the odds of yes by e^0.7 ≈ 2". That is a strong, simple, readable assumption, and it is why the model is so popular in banking, medicine and advertising.

Training needs a way to score the probabilities. The natural score is: how much probability did the model give to what actually happened? If a transaction was fraud and the model said 0.9, good; if it said 0.01, terrible. Taking the negative logarithm of that probability turns it into a penalty that is 0 for a perfect prediction and grows without limit as the model becomes confidently wrong: −log(0.9) = 0.105, −log(0.01) = 4.6. Averaged over examples, this is binary cross-entropy, also called log-loss. Minimising it is the same as maximising the probability of the observed labels, which is maximum likelihood, the principle you met in ml6.

The rest of the round is mechanics you already know from mc1. The loss has a gradient; gradient descent walks downhill; the gradient turns out to be almost identical to linear regression's, with the prediction replaced by a probability: average of (p − y) times the feature. And there is one new thing to be careful about: the computer's numbers are finite. e^710 is too big for a 64-bit float and becomes infinity (overflow), and σ(37) is so close to 1 that it rounds to exactly 1.0, after which log(1 − p) is log(0). The professional implementation is arranged so that neither ever happens.

Where the "two machines" picture breaks: the boundary between yes and no, where p = 0.5, is where z = 0, which is a straight line (or flat plane) in feature space. Logistic regression can only draw straight boundaries unless you add curved features yourself. And if a straight boundary separates the classes perfectly, the second machine's confidence can grow for ever, a quirk the lesson treats in detail.

1. The problem as it is usually asked

"Implement binary logistic regression trained with gradient descent: fit, predict_proba, predict. No scikit-learn." The questions worth asking first: are the labels 0/1 or −1/+1 (it changes the formulas)? Is there class imbalance? Should there be an L2 penalty? How large is the data, and is it sparse? Do they want probabilities or just labels? Then state the plan: logits, stable sigmoid, loss from logits, the p − y gradient, a stopping rule, and tests including a gradient check.

2. The maths in plain words

For one example with features x and label y (1 for yes, 0 for no) the model computes the logit z = w·x + b, then the probability p = σ(z). The loss for that example is "minus the log of the probability you gave the truth": −log p if y = 1, −log(1 − p) if y = 0. The usual trick writes both cases in one line, −[y log p + (1 − y) log(1 − p)]: when y = 1 the second term vanishes, when y = 0 the first does.

Now the gradient, in words. Nudge the logit z up a little. For a positive example, p rises and the loss −log p falls; for a negative one, p rises and the loss −log(1 − p) rises. Work through the derivative and every complication cancels: the derivative of the loss with respect to the logit is exactly p − y. If the truth is 1 and the model said 0.3, the gradient is −0.7: push the logit up, strongly. If the truth is 0 and the model said 0.3, it is +0.3: push it down, gently. The size of the push is the size of the mistake in probability terms. Then, because z = w·x + b, the weight for feature j receives that push multiplied by x_j, exactly as in linear regression.

3. The equations

The derivation that interviewers ask for is three lines. The sigmoid has the convenient derivative σ'(z) = σ(z)(1 − σ(z)) = p(1 − p). For one example:

ℓ      = −[ y log p + (1 − y) log(1 − p) ]
∂ℓ/∂p  = −y/p + (1 − y)/(1 − p)  =  (p − y) / (p(1 − p))
∂ℓ/∂z  = ∂ℓ/∂p · p(1 − p)          =  p − y            the p(1 − p) cancels

Averaging over n examples and applying the chain rule through z = Xw + b, with X of shape (n, d):

L      = (1/n) Σ ℓᵢ
∂L/∂w  = (1/n) Xᵀ(p − y)          shape (d,)
∂L/∂b  = (1/n) Σ (pᵢ − yᵢ)        scalar
with L2:  ∂L/∂w += λw

Notice the pattern: this is mc1's gradient with the prediction replaced by a probability (and no factor 2, because there is no square). That is not a coincidence. Both are generalised linear models whose loss is the negative log-likelihood of an exponential-family distribution with its natural link (Gaussian with identity for mc1, Bernoulli with the logit here), and for every such pairing the gradient with respect to the linear score is "prediction minus target". Softmax regression and Poisson regression have the same form.

There is no closed form this time: setting Xᵀ(σ(Xw + b) − y) = 0 gives equations with w inside a sigmoid, which cannot be rearranged into a linear system. That is why we iterate. The good news is that the loss is convex in w: its Hessian Xᵀ diag(p(1 − p)) X / n is positive semi-definite because every p(1 − p) is positive. So gradient descent cannot get trapped in a bad local minimum; any minimum it finds is the global one.

4. A worked example by hand

Four examples with one feature: x = [1, 2, 3, 4], labels y = [0, 1, 0, 1]. No threshold on x separates them perfectly, so a finite optimum exists. Start from w = 0, b = 0, learning rate 0.5.

  • Forward. Every logit is 0, so every probability is σ(0) = 0.5. Each example's loss is −log 0.5 = 0.693, so the mean loss is ln 2 = 0.6931. This is the loss of a model that knows nothing, a useful landmark: any trained model scoring above 0.693 on balanced data is worse than a coin.
  • Error signal. p − y = [0.5, −0.5, 0.5, −0.5].
  • Weight gradient. (1/4)·(0.5·1 − 0.5·2 + 0.5·3 − 0.5·4) = (1/4)·(0.5 − 1 + 1.5 − 2) = −0.25.
  • Intercept gradient. (1/4)·(0.5 − 0.5 + 0.5 − 0.5) = 0. The model already predicts the base rate (half the labels are 1, every p is 0.5), so the intercept has nothing to fix.
  • Step. w = 0 − 0.5·(−0.25) = 0.125, b = 0.
  • New forward. Logits [0.125, 0.25, 0.375, 0.5], probabilities [0.531, 0.562, 0.593, 0.622]. Per-example losses: −log(1 − 0.531) = 0.758, −log 0.562 = 0.576, −log(1 − 0.593) = 0.898, −log 0.622 = 0.474. Mean: 0.6764, down from 0.6931.

The model learned the only thing these four points really say: larger x is slightly more likely to be positive (two of the larger values are positive, but so is one small one). The first block asserts every number above.

Keep going and the trace shows how the two parameters cooperate. After the first step b has no reason to move, but as soon as w is positive, every probability is above 0.5 while only half the labels are 1, so the predictions are too high on average, the intercept's gradient becomes positive, and b starts falling to compensate.

The solution's tests assert this converged answer too.

import time
import numpy as np

# The hand-worked example: four points, one feature, labels that no threshold separates.
x_hand = np.array([1.0, 2.0, 3.0, 4.0])
y_hand = np.array([0.0, 1.0, 0.0, 1.0])

# Start at w = b = 0: every probability is 0.5 and the loss is ln 2.
p0 = 1 / (1 + np.exp(-(0.0 * x_hand + 0.0)))
assert np.allclose(p0, 0.5)
loss0 = -np.mean(y_hand * np.log(p0) + (1 - y_hand) * np.log(1 - p0))
assert np.isclose(loss0, np.log(2))                      # 0.6931

# Gradient: mean of (p - y) * x and mean of (p - y).
gw = np.mean((p0 - y_hand) * x_hand)                     # (0.5 - 1 + 1.5 - 2) / 4
gb = np.mean(p0 - y_hand)
assert np.isclose(gw, -0.25) and np.isclose(gb, 0.0)
w1, b1 = 0 - 0.5 * gw, 0 - 0.5 * gb                      # lr = 0.5
assert np.isclose(w1, 0.125) and b1 == 0.0
z1 = w1 * x_hand + b1                                    # [0.125, 0.25, 0.375, 0.5]
p1 = 1 / (1 + np.exp(-z1))
loss1 = -np.mean(y_hand * np.log(p1) + (1 - y_hand) * np.log(1 - p1))
assert np.allclose(p1, [0.53121, 0.56218, 0.59267, 0.62246], atol=1e-5)
assert np.isclose(loss1, 0.67643, atol=1e-5)             # down from 0.69315

5. The naive loop implementation

The literal translation loops over steps, examples and features, and uses math.exp for the sigmoid. It is correct on friendly data, and it is a good way to make sure you understand each symbol, but it has two problems: it is slow, and math.exp(-z) raises OverflowError for z below about −709, which is a crash rather than a warning.

import math

def fit_naive(X, y, lr=0.5, steps=200):
    """Logistic regression by batch gradient descent, written as plain Python loops."""
    n, d = len(X), len(X[0])
    w, b = [0.0] * d, 0.0
    for _ in range(steps):
        gw, gb = [0.0] * d, 0.0
        for i in range(n):
            z = b + sum(w[j] * X[i][j] for j in range(d))
            p = 1 / (1 + math.exp(-z))                 # overflows for z below about -709
            for j in range(d):
                gw[j] += (p - y[i]) * X[i][j] / n
            gb += (p - y[i]) / n
        w = [w[j] - lr * gw[j] for j in range(d)]
        b -= lr * gb
    return np.array(w), b

6. The vectorised, stable version

Two helper functions carry all of the numerical care.

The stable sigmoid. 1/(1 + e^−z) is safe when z ≥ 0 (then e^−z ≤ 1). For z < 0, multiply top and bottom by eᶻ to get the algebraically identical eᶻ/(1 + eᶻ), which is safe because eᶻ < 1. Choosing the branch by the sign of z means the code only ever exponentiates numbers that are zero or negative, so nothing overflows. Very negative z gives e^z underflowing gracefully to 0, which is the correct limit.

The loss from logits. Substitute p = σ(z) into the loss and simplify. Since log σ(z) = −log(1 + e^−z) and log(1 − σ(z)) = −log(1 + eᶻ), the per-example loss becomes log(1 + eᶻ) − y·z. The first term is called softplus, and NumPy computes it without overflow as np.logaddexp(0, z): logaddexp(a, b) returns max(a, b) + log(1 + e^−|a − b|), so the exponent is never positive. The model never forms a probability on the way to the loss at all, which is the whole point.

def sigmoid(z):
    """1 / (1 + e^-z) without overflow: never exponentiate a large positive number."""
    z = np.asarray(z, float)
    out = np.empty_like(z)
    pos = z >= 0
    out[pos] = 1 / (1 + np.exp(-z[pos]))
    ez = np.exp(z[~pos])                               # z < 0, so e^z is in (0, 1)
    out[~pos] = ez / (1 + ez)
    return out

def bce_with_logits(z, y):
    """Mean of -[y log p + (1 - y) log(1 - p)], computed from logits as softplus(z) - y z."""
    return np.mean(np.logaddexp(0, z) - y * z)

class LogisticRegression:
    def __init__(self, lr=0.5, l2=0.0, max_iter=20_000, tol=1e-7):
        self.lr, self.l2, self.max_iter, self.tol = lr, l2, max_iter, tol

    def fit(self, X, y):
        X, y = np.asarray(X, float), np.asarray(y, float)
        n, d = X.shape
        self.w, self.b = np.zeros(d), 0.0
        self.history = []
        for self.n_iter in range(1, self.max_iter + 1):
            z = X @ self.w + self.b                         # (n,) logits
            err = sigmoid(z) - y                            # (n,) p - y
            gw = X.T @ err / n + self.l2 * self.w           # (d,)
            gb = err.mean()
            self.w -= self.lr * gw
            self.b -= self.lr * gb
            if self.n_iter % 100 == 0:
                self.history.append(bce_with_logits(z, y))
            if np.sqrt(gw @ gw + gb * gb) < self.tol:
                break
        return self

    def decision_function(self, X):
        return np.asarray(X, float) @ self.w + self.b

    def predict_proba(self, X):
        return sigmoid(self.decision_function(X))

    def predict(self, X, threshold=0.5):
        return (self.predict_proba(X) >= threshold).astype(int)

The training loop computes logits once, the error p − y once, and the gradient as one matrix-vector product X.T @ err / n of shape (d,). It stops when the gradient's length falls below a tolerance. On 400 examples it converged in 1,178 steps; 200 steps took about 100 ms as loops and 10 ms vectorised here, and the ratio grows with n and d (mc1 measured 75 times on 20,000 × 20).

7. Numerical stability traps, with numbers

Trap 1: log of exactly zero. In float64, 1 + e^−37 is 1 plus 8.5 × 10⁻¹⁷, which is smaller than half the gap between 1.0 and the next representable number (1.1 × 10⁻¹⁶), so it rounds to exactly 1.0 and σ(37) = 1.0. A negative example with that logit then has loss −log(1 − 1.0) = −log(0) = inf, and the mean over the batch is inf. The test builds logits [−1000, −40, 0, 40, 1000] and confirms the naive loss is infinite at 40 while logaddexp(0, z) gives the true values: 0, 4.2 × 10⁻¹⁸, 0.693, 40 and 1000.

Trap 2: float32 hits the cliff much earlier. Float32 has about 7 significant digits, so 1 + e^−17 already rounds to 1, and σ(17) = 1.0. Logits of 17 are common in deep networks, which is why every framework offers a fused "with logits" loss and why mixed-precision training computes losses in float32 or higher.

Trap 3: overflow in the sigmoid itself. np.exp(1000) is inf with a RuntimeWarning, and math.exp(1000) raises an exception. NumPy's result 1/(1 + inf) = 0 happens to be right, but warnings in a training loop are noise that hides real problems, and other expressions (e^z / (1 + e^z) for large z) give inf/inf = NaN. The two-branch sigmoid avoids all of it.

Trap 4: clipping instead of fixing. A common patch is np.clip(p, 1e-15, 1 − 1e-15) before the log. It keeps the loss finite, but inside the clipped region the loss is flat, so the gradient is zero and a confidently wrong example stops teaching the model anything. PyTorch's plain BCELoss clamps its log outputs at −100 for exactly this reason and documents the trade-off; its BCEWithLogitsLoss is the stable alternative.

Trap 5: unscaled features. As in mc1, a feature measured in large units inflates the curvature and caps the safe learning rate. Logistic regression's Hessian is bounded by XᵀX/(4n) (because p(1 − p) ≤ 1/4), so standardising features gives a safe learning rate of a few units; the 0.5 used here is comfortably inside it, and the test asserts the loss never increases.

8. Testing it

The fourth block is the test suite. It checks the class reproduces the hand step (w = 0.125 after one iteration). It demonstrates the stability traps above. On 400 synthetic examples drawn from a known model (w = [2, −3], b = 0.5, with labels sampled from the true probabilities) it checks that the vectorised fit matches the naive loop to 10⁻¹⁰ after 200 steps, that the converged weights land near the truth ([1.94, −2.71], b = 0.88: noisy labels mean you recover the truth only approximately), and that training accuracy exceeds 80%. It runs a central finite-difference gradient check (error below 10⁻⁸). And if PyTorch is installed it computes the same loss and gradient with autograd through binary_cross_entropy_with_logits, which must agree to 10⁻¹².

Why test against labels sampled from known probabilities, rather than labels from a hard threshold? Because hard-threshold labels are separable, and on separable data the true answer is "infinitely large weights" (next section): your test would chase a moving target. Sampling labels from the model makes a finite optimum exist and gives you a ground truth to aim at.

9. Separable data: the weights that never stop

Take four points x = [−2, −1, 1, 2] with labels [0, 0, 1, 1]. The boundary x = 0 separates them perfectly. Any w > 0 classifies all four correctly, and doubling w makes every probability more extreme and the loss smaller. The loss approaches zero but never reaches it, so there is no minimum, and gradient descent keeps going: in the test, |w| was 3.4 after 100 steps, 5.6 after 1,000 and 7.8 after 10,000, growing roughly with the logarithm of the step count. In practice this shows up as training accuracy of exactly 100%, overconfident probabilities, and weights that keep changing between runs. The fix is an L2 penalty λ‖w‖²/2, which adds λw to the gradient and makes the loss bowl rise again at large w: with λ = 0.1 the same data converges to w ≈ 1.46. In real data, sudden separability usually means a leaked feature (one that encodes the label), which is worth checking before reaching for regularisation.

10. Debugging a logistic regression that will not learn

When the loss sits at 0.693 and refuses to move, or moves the wrong way, a short checklist finds the cause in minutes. First, compare against the landmarks: on data with positive rate π, a model that predicts π for everyone scores −[π log π + (1 − π) log(1 − π)] (0.693 for balanced data, 0.056 for a 1% positive rate). If your loss is above that, the model is worse than predicting the base rate, which almost always means a sign error in the update (w += lr·g instead of −=) or labels encoded as −1/+1 fed into a 0/1 formula. Second, run the finite-difference check from section 8 at a random point; a transposed X or a missing /n shows up immediately as a mismatch. Third, check the scale: print the largest absolute logit and the largest feature value. Logits in the thousands mean unscaled features or a learning rate far too large. Fourth, check the data: a label column that is all zeros after a bad join, or features that are all NaN because of a missing-value encoding, produce perfectly "correct" code that learns nothing. Finally, overfit a tiny subset (eight examples) on purpose: a working implementation drives their loss toward zero, and one that cannot has a bug, not a data problem.

11. Complexity

Each gradient step is O(nd): one product Xw and one Xᵀ(p − y), plus O(n) exponentials. Memory beyond the data is O(n + d) for the logits and gradient. The number of steps depends on conditioning, as in mc1, and here also on how close the data is to separable: near-separable data has a very flat valley along the direction that scales up w, and convergence slows. Newton's method (the drill) costs O(nd²) to form the Hessian and O(d³) to solve it per step, but needs only 6-10 steps; it wins for d up to a few thousand and loses badly beyond. For sparse data with millions of features, each SGD step costs O(non-zeros in the batch), which is why large click-prediction systems use it.

12. Talking through it in the interview

A clean presentation: model and shapes; loss and why it is cross-entropy; the three-line gradient derivation ending in p − y; the stable sigmoid and the logits-based loss, with the cliff at 37; the vectorised loop with a tolerance; then tests (hand step, gradient check, a reference). If asked "what could go wrong", go to separability and imbalance. If asked "how would you speed it up", go to Newton for small d and SGD for large n. Each of these is a short paragraph you can now say from memory.

Why the gradient is p − y: the exponential-family view

The Bernoulli distribution can be written as P(y) = exp(y·z − log(1 + eᶻ)), where z is the log-odds. That is the exponential-family form exp(y·θ − A(θ)) with natural parameter θ = z and log-partition function A(z) = softplus(z). Two facts about every exponential family then give the whole lesson: the derivative of A is the mean, so A'(z) = σ(z) = p, which is why the gradient of the negative log-likelihood A(z) − yz is p − y; and the second derivative of A is the variance, p(1 − p), which is why the Hessian has those weights. It also explains why the stable loss is softplus(z) − yz: it is literally the negative log of the Bernoulli density.

Newton's method and IRLS

Gradient descent uses only the slope; Newton's method also uses the curvature. Near the optimum the loss looks like a quadratic bowl with Hessian H = Xᵀ diag(p(1 − p)) X / n, and Newton jumps straight to that bowl's bottom: w ← w − H⁻¹g. Once close, the number of correct digits roughly doubles each step, so 6-10 steps suffice where gradient descent needed over a thousand. Rearranged, each step is a weighted least-squares problem with weights p(1 − p) and a "working response" z + (y − p)/(p(1 − p)), hence the name iteratively reweighted least squares. Two cautions: on separable data some p(1 − p) go to zero and H becomes singular (a tiny ridge term fixes it, as in the drill), and far from the optimum a full Newton step can overshoot, so production solvers add a line search or a trust region.

Why L-BFGS is the default in libraries

L-BFGS approximates H⁻¹ from the last few (typically 10) gradient differences, so each step costs O(nd) like gradient descent but converges in tens to hundreds of steps like a quasi-Newton method. It needs no learning rate (a line search picks the step), handles thousands to millions of dense features, and is the default for scikit-learn's logistic regression. For sparse, very large data, SGD variants with per-coordinate learning rates (AdaGrad, FTRL-Proximal) win because they process one mini-batch at a time and give rare features larger steps.

Calibration and the intercept after downsampling

A well-specified, converged logistic regression is calibrated on its training distribution: among examples it scores at 0.3, about 30% are positive. That property is what made it the workhorse of advertising and credit scoring. It breaks predictably when you downsample negatives to speed training: if you keep a fraction r of negatives, the model's odds are inflated by 1/r, and the fix is to add log r to every logit (or equivalently to the intercept) at serving time. Regularisation also pulls probabilities toward the base rate, a small calibration cost; if exact probabilities matter, check a reliability diagram on held-out data.

Multinomial (softmax) regression

With K classes, compute K logits z = XW + b with W of shape (d, K), convert them with softmax p_k = e^{z_k} / Σ_j e^{z_j}, and use categorical cross-entropy. The gradient has the same form, Xᵀ(P − Y)/n with Y one-hot, and the stable loss uses log-sum-exp: logsumexp(z) − z_true, computed by subtracting the row maximum before exponentiating. Binary logistic regression is the K = 2 case with one class's logit pinned to zero; mc10 builds the stable softmax and its gradient in full.

Class weights versus resampling, exactly

With a 1:300 imbalance there are two standard fixes, and they are closer than they look. Weighting each positive's loss by 300 (PyTorch's pos_weight) multiplies its contribution to the gradient by 300, so the optimiser treats the data as if each positive appeared 300 times. Downsampling negatives to one in 300 achieves a similar balance by throwing data away, which makes each epoch 300 times cheaper but noisier. Both shift the model's probabilities: weighting inflates the odds by the weight, downsampling inflates them by 1/r. Both are therefore corrected the same way, by subtracting the log of the factor from the logits, if you need calibrated probabilities. If you only need a ranking (top 200 transactions for review), neither correction matters, because adding a constant to every logit does not change the order. Saying which of the two goals the product has is the senior part of the answer.

L1 regularisation and sparse models

Replacing the L2 penalty with λ‖w‖₁ pushes many weights to exactly zero, which is valuable when there are millions of hashed features and the model must fit in memory on a serving box. The L1 term has no derivative at zero, so plain gradient descent cannot handle it; the standard tools are proximal methods, which take a gradient step on the log-loss and then apply soft thresholding (the same operator as mc1's lasso drill), and FTRL-Proximal, the online algorithm Google described for ad-click prediction, which combines per-coordinate learning rates with an L1 term so that rare features stay exactly zero until they have earned a weight.

Interpreting coefficients honestly

A coefficient is a change in log-odds per unit of the feature, holding the others fixed; e^w is the odds ratio. Three things undermine that reading: correlated features share credit unpredictably (as with collinearity in mc1), the "holding others fixed" may be impossible in the real world, and L2 shrinkage biases every coefficient toward zero. Standardise features if you want to compare magnitudes, and treat coefficients as associations, not causes.

Where it runs

Logistic regression is still a production model in credit scoring (where regulators want a reason for every decision), click and conversion prediction (often on top of learned or hashed features), medical risk scores, spam and abuse filters, and as the calibration layer on top of larger models (Platt scaling is a one-feature logistic regression on a model's score). It is also the baseline every new classifier should beat.

Failure modes and symptoms

The NaN day. Symptom: a stable nightly job suddenly reports a NaN loss, and the model artefact is full of NaN. Cause: a naive loss met an extreme logit, often after a new, highly predictive feature or a data bug (a label leaked into a feature). Detection: assert finite loss and gradient every step, and log the maximum absolute logit. Prevention: compute the loss from logits, always.

Silent separation. Symptom: training accuracy 100%, validation fine at first, then probabilities of 0.99999 everywhere and terrible log-loss on new data. Cause: perfect separation, often from a leaked feature such as "refund issued" in a churn model. Detection: monitor the weight norm and the share of predictions above 0.999. Fix: remove the leak, then regularise.

Miscalibration after resampling. Symptom: the fraud model predicts a 12% fraud rate when the real one is 0.4%. Cause: training on downsampled negatives without correcting the intercept. Fix: add log r to the logits, then verify with a reliability plot.

Drift. A model trained in one month sees new merchants, new devices, new fraud patterns. The weights are fixed; the input distribution is not. Monitor per-feature distributions and the average predicted probability against the observed rate, and retrain on a schedule or when they diverge.

What to monitor

Four numbers catch most problems before users do. The training and validation log-loss against the base-rate landmark (a model that drifts toward 0.693 on balanced data is forgetting). The mean predicted probability against the observed positive rate, per day and per segment, which is the cheapest calibration check there is. The distribution of logits, especially the share beyond ±10, which rises before separation or NaN problems appear. And the weight norm across retrains: a model whose weights double from one week to the next has found a leak or a broken feature. Each is a single line of logging and a threshold alert.

Knobs people tune

The L2 strength (by cross-validated log-loss, on a log grid), the class or sample weights for imbalance, the decision threshold (chosen from costs or a precision target, after training), and the solver (L-BFGS for dense, SGD/FTRL for very large sparse data). Feature work matters more than any of these: standardisation, sensible transforms (log of counts), and hand-made interactions, since the model cannot invent curved boundaries itself.

The reference for this problem

PyTorch's documentation for BCEWithLogitsLoss is the official statement of this lesson's central engineering point. It says the loss "combines a Sigmoid layer and the BCELoss in one single class" and that this version "is more numerically stable than using a plain Sigmoid followed by a BCELoss as, by combining the operations into one layer, we take advantage of the log-sum-exp trick for numerical stability". The companion BCELoss page documents the alternative's workaround: it "clamps its log function outputs to be greater than or equal to −100", so the loss stays finite, which is Trap 4 above in the library's own words. The same page gives the standard recipe for imbalance: with 100 positive and 300 negative examples, set pos_weight to 300/100 = 3, and "the loss would act as if the dataset contains 3 × 100 = 300 positive examples". Work it out

Gradient descent above needs over a thousand iterations. Implement Newton's method (IRLS) for the same model and show it reaches the same solution in a handful of steps. What does each step cost?

Answer

Append a column of ones so the intercept is just another weight. The gradient is Xᵀ(p − y)/n; the Hessian is Xᵀ·diag(p(1 − p))·X / n. Each Newton step solves H·Δ = g and subtracts Δ. A tiny ridge term keeps H invertible if the data are separable.

def fit_newton(X, y, l2=1e-8, max_iter=50):
    Xb = np.hstack([X, np.ones((len(X), 1))])
    w = np.zeros(Xb.shape[1])
    for it in range(1, max_iter + 1):
        p = sigmoid(Xb @ w)
        g = Xb.T @ (p - y) / len(y) + l2 * w
        H = (Xb * (p * (1 - p))[:, None]).T @ Xb / len(y) + l2 * np.eye(len(w))
        step = np.linalg.solve(H, g)
        w -= step
        if np.abs(step).max() < 1e-12:
            break
    return w[:-1], w[-1], it

w_n, b_n, iters = fit_newton(X, y)
assert iters <= 12                                            # quadratic convergence
assert np.allclose(w_n, m.w, atol=1e-4) and abs(b_n - m.b) < 1e-4   # same optimum as GD

Each step costs O(nd²) to build the Hessian plus O(d³) to solve it, against O(nd) for a gradient step. With d = 10 that is a bargain; with d = 10⁶ sparse features it is impossible, which is why large-scale systems use L-BFGS or SGD.
