A language model does not write text. At each step it produces a score for every token in its vocabulary, and something else, the decoding strategy, decides which token to emit. The same model can produce crisp, correct answers or bland repetition or incoherent rambling depending only on that decision. Ask a chat model for a story with the wrong settings and it will loop on "I'm sorry, I'm sorry"; ask it for a JSON object with sampling at high temperature and it will occasionally emit a stray comma that breaks your parser. Decoding is the cheapest lever an AI engineer has over output quality: no retraining, just a few lines of code between the logits and the user.

It is also where a lot of misunderstanding lives. Teams raise temperature to fix factual errors (it makes them worse), use beam search for chat (it makes replies bland), or compare models evaluated with different sampling settings and draw conclusions about the models. Knowing exactly what each knob does to the distribution, with numbers, is what lets you make these calls quickly and defend them.

That is why "implement temperature, top-k, top-p and beam search" appears in LLM coding interviews, usually with follow-ups that test judgement. Why does greedy decoding sometimes miss the most likely sentence? (In this lesson's example it settles for probability 0.21 when 0.38 is available.) Why does top-p adapt where top-k does not? Why do beam scores need a length penalty and log-probabilities? And why did Holtzman and colleagues find that beam search, the "best" search, produces the worst open-ended text?

The implementation details matter too. Temperature zero must be special-cased rather than divided by. The top-p cut needs a precise rule (keep tokens while the mass before them is below p, so the top token always survives). Sorting a 128,000-token vocabulary for every row of every step is expensive, and a top-k prefilter with argpartition removes most of that cost without changing the result. Beam search must sum log-probabilities, because multiplying hundreds of probabilities underflows to exactly zero.

This lesson works the four strategies by hand on a four-token distribution, then implements an inverse-CDF sampler with a loop and an exhaustive best-sequence search as references, the vectorised sampler with temperature, top-k and top-p, a batched top-p for many rows, and beam search with length normalisation. The tests check the hand numbers, sampled frequencies, the greedy trap against beam and exhaustive search, the length bias, the underflow trap and the prefilter's equivalence. The drill adds min-p sampling.

Picture the model at one step of writing: it has just produced "The cat sat on the", and its output is a list of probabilities, one per token in its vocabulary: " mat" 0.5, " floor" 0.3, " sofa" 0.15, " moon" 0.05, and tiny amounts for the other hundred thousand tokens. Decoding answers one question: which token comes next?

The simplest answer is greedy: always take the most likely token, " mat". It is deterministic and often good for short factual answers, but over a long text it tends to repeat itself and, as the lesson shows, it can walk into a dead end: a token that looks best now can lead only to weak continuations.

The opposite answer is sampling: roll a weighted die, so " mat" comes up half the time, " floor" 30% of the time, and so on. That gives varied, natural-sounding text, but every so often the die lands in the long tail of very unlikely tokens, and one bad token can derail everything after it. Three knobs shape the die. Temperature sharpens or flattens it: below 1 the likely tokens become more likely (at 0.5, " mat" rises to 68.5%), above 1 the distribution evens out. Top-k removes all but the k most likely faces. Top-p, or nucleus sampling, removes all but the smallest set of faces whose probabilities add up to p, so the number of faces kept adapts to how confident the model is.

An everyday analogy for the three knobs: temperature is how adventurous the writer feels, top-k is a rule like "only ever consider your five favourite words", and top-p is "only consider the words that together make up 90% of your instinct". The first changes how strongly preferences are held, the other two change which options are on the table at all, and top-p's table grows when the writer is unsure and shrinks when they are certain.

Beam search takes a different approach: instead of choosing one token at a time, it keeps a handful of partial sentences, the most probable few seen so far, extends each by its best next tokens, and keeps the best few extensions. It explores alternatives that greedy would discard, so it finds higher-probability sentences, which suits tasks with one correct output, such as translation or extraction. Its cost is that every hypothesis needs its own forward pass and KV cache, so a beam of four costs about four times as much as greedy decoding.

Where the "most probable is best" intuition breaks: for open-ended writing, the most probable text is often not the best text. Human writing regularly uses less likely, more informative words; the highest-probability continuation tends to be generic and repetitive. That is why chat models sample with moderate temperature and top-p, and reserve greedy and beam search for tasks where there is a right answer.

1. The problem as it is usually asked

"Given a function that returns next-token logits, implement greedy decoding, sampling with temperature, top-k and top-p, and beam search." Clarify: is the input logits or probabilities (logits, usually); how should temperature 0 behave (as greedy); are top-k and top-p combined (yes, top-k first, as Hugging Face does); does beam search need length normalisation and end-of-sequence handling (yes); is batching needed. Then outline: a single sample_next with the three knobs, a batched top-p, beam search over log-probabilities, and tests with known distributions.

2. The maths in plain words

Temperature. Divide each logit by T, then softmax. Because probabilities are exponentials of logits, dividing logits by T raises each probability to the power 1/T before renormalising. T = 0.5 squares them (the gaps widen), T = 2 takes square roots (the gaps shrink).

Top-k. Find the k-th largest logit and set every smaller logit to −∞, so their probability becomes 0; softmax renormalises the rest. Ties at the k-th value all survive, which is a harmless detail worth knowing.

Top-p. Sort the probabilities in decreasing order and add them up. Keep tokens until the running total reaches p; keep that last token too, since it is the one that brings the total to p. Equivalently, keep each token whose probability mass before it in sorted order is below p; that rule always keeps the most likely token. Renormalise the kept probabilities and sample.

Beam search. Keep a list of up to b hypotheses, each a partial sequence with a score equal to the sum of the log-probabilities of its tokens. At each step, extend every live hypothesis by its best b next tokens, pool the extensions, move any that ended with the end-of-sequence token to a finished list, and keep the best b of the rest. At the end, choose the finished hypothesis with the best length-normalised score.

3. The equations

temperature:   p_T(i) = exp(z_i / T) / Σ_j exp(z_j / T)  ∝ p(i)^(1/T);    T = 0 → argmax
top-k:         keep i if z_i ≥ z_(k) (the k-th largest);  renormalise
top-p:         sort p descending: p_(1) ≥ p_(2) ≥ …;  keep (j) while Σ_{m<j} p_(m) < p;  renormalise
sampling:      draw u ~ Uniform[0, 1); return the first i with cumsum(p)_i > u

beam search:   score(y_1..y_t) = Σ_{s≤t} log p(y_s | y_<s)
               keep the b best hypotheses at every step; finished ones leave the beam
               final choice: argmax score(Y) / lp(Y),   lp(Y) = ((5 + |Y|) / 6)^α     (GNMT)

Two remarks. The log-sum form of the beam score is not a nicety: multiplying 400 probabilities of 0.01 gives 10⁻⁸⁰⁰, which underflows to exactly 0 in float64, and every hypothesis would tie (the test shows it). And the length penalty changes which hypothesis wins, not just its score: without it, every extra token adds a negative log-probability, so shorter outputs always look better.

4. A worked example by hand

Take next-token probabilities [0.5, 0.3, 0.15, 0.05] (logits are their logarithms).

  • Temperature 0.5. Square and renormalise: 0.25, 0.09, 0.0225, 0.0025, sum 0.365, giving [0.685, 0.247, 0.062, 0.007]. The top token went from 50% to 68.5%; the last from 5% to under 1%.
  • Temperature 2. Square roots: 0.707, 0.548, 0.387, 0.224, sum 1.866, giving [0.379, 0.294, 0.208, 0.120]. The distribution is much flatter.
  • Top-k = 2. Keep 0.5 and 0.3; renormalise by 0.8: [0.625, 0.375, 0, 0].
  • Top-p = 0.75. Cumulative sums 0.5, 0.8, 0.95, 1.0. The mass before token 0 is 0 and before token 1 is 0.5, both below 0.75; before token 2 it is 0.8, not below. Keep tokens 0 and 1: the same [0.625, 0.375].
  • Top-p = 0.9. The mass before token 2 is 0.8 < 0.9, so it is kept; before token 3 it is 0.95. Keep three tokens.

Now the beam-search example. A toy model starts at BOS. Its first step offers A with 0.6 and B with 0.4. After A, the best options are X or Y at 0.35 each, or stopping (EOS) at 0.3; after B, X has 0.95. After X, the model always stops.

  • Greedy takes A (0.6), then X (0.35, the first of the tied pair), then EOS (1.0): probability 0.6 × 0.35 = 0.21.
  • Beam width 2 keeps both A (log 0.6) and B (log 0.4) after step one. Step two extends A to A-X, A-Y (log 0.21 each) and A-EOS (0.18, finished), and B to B-X (log 0.38) and B-EOS (0.02, finished). The best two live hypotheses are B-X (0.38) and A-X (0.21). Step three ends both with EOS. The best finished sequence is BOS-B-X-EOS with probability 0.4 × 0.95 = 0.38.

Greedy lost because it judged A by its first step alone. Beam search kept B alive one step longer and found that its continuation was far stronger. The first block asserts these numbers.

import itertools
import math
import time
import numpy as np

# The hand-worked example: four tokens with probabilities 0.5, 0.3, 0.15, 0.05.
p = np.array([0.5, 0.3, 0.15, 0.05])
logits = np.log(p)
# Temperature divides the logits, so p_T ∝ p^(1/T).
p_half = p ** 2 / (p ** 2).sum()                        # T = 0.5 sharpens
p_two = p ** 0.5 / (p ** 0.5).sum()                     # T = 2 flattens
assert np.allclose(p_half, [0.6849, 0.2466, 0.0616, 0.0068], atol=1e-4)
assert np.allclose(p_two, [0.3790, 0.2936, 0.2076, 0.1199], atol=1e-4)
# Top-k = 2 keeps tokens 0 and 1 and renormalises: 0.5/0.8, 0.3/0.8.
assert np.allclose(np.r_[p[:2] / p[:2].sum(), 0, 0], [0.625, 0.375, 0, 0])
# Top-p = 0.75: cumulative 0.5, 0.8, ... -> the smallest prefix reaching 0.75 is {0, 1}.
assert np.searchsorted(np.cumsum(p), 0.75) == 1
# Top-p = 0.9 needs three tokens (0.5 + 0.3 + 0.15 = 0.95 >= 0.9).
assert np.searchsorted(np.cumsum(p), 0.9) == 2
# Greedy versus beam on a two-step model: A (0.6) then best 0.35 = 0.21; B (0.4) then 0.95 = 0.38.
assert math.isclose(0.6 * 0.35, 0.21) and math.isclose(0.4 * 0.95, 0.38)

5. The naive implementations

Two references, written for clarity rather than speed. sample_naive draws by walking the cumulative probabilities until they pass a uniform number u, the inverse-CDF method that every sampler implements underneath. best_sequence_exhaustive scores every possible sequence up to a maximum length and returns the most probable one that ends with EOS: correct by construction, and exponential in length, which is exactly why beam search exists.

def sample_naive(probs, u):
    """Inverse-CDF sampling with a loop: walk the cumulative sum until it passes u in [0, 1)."""
    total = 0.0
    for i, pi in enumerate(probs):
        total += pi
        if u < total:
            return i
    return len(probs) - 1                               # guard against rounding at the very end

def best_sequence_exhaustive(next_logprobs, bos, eos, vocab, max_len):
    """Score every sequence up to max_len tokens; the true highest-probability completed sequence."""
    best, best_lp = None, -np.inf
    for L in range(1, max_len + 1):
        for body in itertools.product(range(vocab), repeat=L):
            seq, lp = [bos], 0.0
            for tok in body:
                lp += next_logprobs(seq)[tok]; seq = seq + [tok]
                if tok == eos:
                    break
            if seq[-1] == eos and len(seq) == L + 1 and lp > best_lp:
                best, best_lp = seq, lp
    return best, best_lp

Exhaustive search over a vocabulary of 6 and lengths up to 3 enumerates 6 + 36 + 216 sequences; over a real vocabulary of 100,000 and a sentence of 20 tokens it would be 10¹⁰⁰. It is useful only as ground truth on toy models, which is how the tests use it.

6. The vectorised implementations

def sample_next(logits, temperature=1.0, top_k=0, top_p=1.0, rng=None):
    logits = np.asarray(logits, float)
    if temperature == 0:
        return int(logits.argmax())                          # greedy
    z = logits / temperature
    if top_k:
        kth = np.sort(z)[-top_k]
        z = np.where(z < kth, -np.inf, z)                     # keep the k largest (ties at the edge survive)
    p = np.exp(z - z.max()); p /= p.sum()
    if top_p < 1.0:
        order = np.argsort(-p)
        cum = np.cumsum(p[order])
        keep = order[:np.searchsorted(cum, top_p) + 1]        # smallest prefix with mass >= top_p
        mask = np.zeros(len(p), bool); mask[keep] = True
        p = np.where(mask, p, 0.0); p /= p.sum()
    rng = rng or np.random.default_rng()
    return int(rng.choice(len(p), p=p))

def filtered_probs_batch(logits, temperature=1.0, top_p=1.0):
    """Temperature + top-p for a whole batch (B, V) at once: sort each row, cut, scatter back."""
    z = np.asarray(logits, float) / temperature
    p = np.exp(z - z.max(-1, keepdims=True)); p /= p.sum(-1, keepdims=True)
    order = np.argsort(-p, axis=-1)
    sp = np.take_along_axis(p, order, -1)
    cum = np.cumsum(sp, -1)
    keep_sorted = (cum - sp) < top_p                          # keep while the mass before it is < top_p
    keep = np.zeros_like(keep_sorted)
    np.put_along_axis(keep, order, keep_sorted, -1)
    p = np.where(keep, p, 0.0)
    return p / p.sum(-1, keepdims=True)

def beam_search(next_logprobs, bos, eos, beam=3, max_len=10, alpha=0.6):
    """next_logprobs(seq) -> log-probabilities over the vocabulary for the next token."""
    live, finished = [([bos], 0.0)], []
    for _ in range(max_len):
        candidates = []
        for seq, score in live:
            lp = next_logprobs(seq)
            for tok in np.argsort(-lp)[:beam]:               # only the top `beam` extensions can survive
                candidates.append((seq + [int(tok)], score + float(lp[tok])))
        candidates.sort(key=lambda c: -c[1])
        live = []
        for seq, score in candidates:
            if seq[-1] == eos:
                finished.append((seq, score))
            elif len(live) < beam:
                live.append((seq, score))
        if not live:
            break
    finished += live                                          # unfinished beams at max_len still count
    length_penalty = lambda c: ((5 + len(c[0])) / 6) ** alpha
    return max(finished, key=lambda c: c[1] / length_penalty(c))

sample_next handles one row: greedy for T = 0; temperature by division; top-k by masking every logit below the k-th largest to −∞; a stable softmax; top-p by sorting, taking cumulative sums, and keeping the prefix found with searchsorted (the index of the first cumulative sum reaching p, plus one); then a draw with rng.choice, which uses the same inverse-CDF idea as the naive version.

filtered_probs_batch applies temperature and top-p to every row of a (B, V) matrix at once: softmax per row, argsort each row descending, gather the sorted probabilities, compute cumulative sums, mark entries whose preceding mass is below p, and scatter the marks back to vocabulary order with put_along_axis. That is the shape of the operation inside a serving engine, which samples for every sequence in the batch at each decode step.

beam_search keeps live hypotheses as (sequence, summed log-probability). For each, it takes the top b next tokens (no other extension can enter the next beam), pools and sorts the candidates, moves EOS-terminated ones to finished, and keeps the best b others. Unfinished hypotheses at the length limit are added to the finished pool. Without that line, a search that never produces an end token would return nothing; with it, the best partial output is still available, which is the behaviour users expect when a maximum length is reached. The winner maximises score divided by the GNMT length penalty ((5 + |Y|)/6)^α; α = 0 disables it.

Drawing the samples for a batch

Filtering gives a probability matrix; the draw itself is also vectorisable. For each row, take one uniform number u in [0, 1), compute the row's cumulative sums, and pick the first index whose cumulative sum exceeds u: (np.cumsum(P, -1) > u[:, None]).argmax(-1). That is the inverse-CDF method of the naive sampler, done for all rows at once, and the test confirms the loop and searchsorted agree draw for draw on shared uniforms. Two cautions: rounding can leave a row's final cumulative sum a hair below 1, so a uniform very close to 1 must still map to the last non-zero token (clip the index or renormalise first); and each row needs its own uniform, ideally from a per-request generator, so that one user's output does not depend on another's.

Repetition penalties, worked

Serving APIs usually offer penalties that act on the logits before temperature and truncation. A frequency penalty subtracts a constant times the number of times a token has already appeared; a presence penalty subtracts a constant once if it has appeared at all. With logits [2.0, 1.0, 0.5] and token 0 already used twice, a frequency penalty of 0.5 lowers its logit to 1.0, tying it with token 1, so its probability falls from 0.63 to 0.38. The multiplicative "repetition penalty" of the CTRL paper divides positive logits (and multiplies negative ones) by a factor such as 1.2. Penalties reduce loops but also discourage legitimate repetition (a variable name in code, a person's name in a story), so they are tuned per use case and usually left off for code. They are applied before temperature and truncation, so a penalised token can also fall out of the top-k or nucleus entirely, which makes their effect larger than the logit change alone suggests.

Choosing settings per task

A working rule of thumb, to be validated on your own data. Deterministic, factual or structured tasks (classification by prompt, extraction, SQL, tool arguments, short factual answers): temperature 0 or near it, with constrained decoding where a schema exists. Code generation: low temperature (0 to 0.3) for a single answer, higher (0.6 to 0.8) when generating several candidates to test and rank. Conversational answers: temperature around 0.7 with top-p 0.9 to 0.95, or min-p around 0.05 to 0.1. Creative writing: higher temperature with min-p to keep the tail in check. Translation and speech recognition: beam search with a small width (4 to 5) and a tuned length penalty. These are starting points; the right values depend on the model, because models differ in how peaked their distributions are, and a setting copied from one model to another can behave quite differently.

Decoding for evaluation

Benchmark numbers depend on decoding as much as on the model. The same model can score several points apart with greedy decoding versus sampling at temperature 0.7, and the "pass@k" metric for code generation is defined in terms of k sampled attempts. A fair comparison fixes the decoding settings, reports them, and when sampling, repeats with several seeds and reports the spread. Self-consistency, majority voting over several sampled answers, is itself a decoding strategy that trades extra samples for accuracy on reasoning tasks.

7. Testing it

The tests check: temperature 0 and top-k = 1 always return the argmax; 20,000 samples with top-p = 0.75 contain only tokens 0 and 1, with token 0 about 62.5% of the time; 20,000 samples at T = 0.5 match the hand-computed distribution to within 1.5 percentage points; the loop sampler gives exactly the same draws as searchsorted on the cumulative sums for 1,000 shared uniforms; the batched top-p keeps two tokens for the hand row, three for the uniform row and one for the confident row; entropy rises with temperature; greedy returns the 0.21 sequence while beam width 2 returns the 0.38 one, and exhaustive search confirms 0.38 is optimal; beam width 1 equals greedy; raw beam scores choose stopping immediately (0.5) over a longer answer (0.451), while α = 1 chooses the longer one; the product of 400 probabilities underflows while the log sum does not; and, on 128 peaked rows of 32,000 logits, a top-64 prefilter finds exactly the same nuclei as sorting everything.

def entropy(T):
    q = np.exp(logits / T); q /= q.sum()
    return -(q * np.log(q)).sum()
assert entropy(0.5) < entropy(1.0) < entropy(2.0)

# 5. A model where greedy is a trap: 'A' looks best (0.6) but every continuation after it is weak.
BOS, A, B, X, Y, EOS = range(6)
table = {(BOS,): {A: 0.6, B: 0.4}, (BOS, A): {X: 0.35, Y: 0.35, EOS: 0.3}, (BOS, B): {X: 0.95, EOS: 0.05}}
def next_logprobs(seq):
    dist = table.get(tuple(seq), {EOS: 1.0})
    lp = np.full(6, -1e9)
    for tok, prob in dist.items():
        lp[tok] = np.log(prob)
    return lp
greedy = [BOS]
while greedy[-1] != EOS and len(greedy) < 5:
    greedy.append(int(next_logprobs(greedy).argmax()))
best_seq, best_score = beam_search(next_logprobs, BOS, EOS, beam=2, alpha=0.0)

assert best_seq == [BOS, B, X, EOS]                           # 0.38 beats greedy's 0.6 * 0.35 = 0.21
# Reference: exhaustive search over every sequence agrees on the optimum.
ex_seq, ex_lp = best_sequence_exhaustive(next_logprobs, BOS, EOS, 6, 3)
assert ex_seq == best_seq and np.isclose(ex_lp, best_score)

# 6. Beam width 1 is greedy; without length normalisation beam search prefers short outputs.

def lp_short(seq):

Testing a random sampler needs statistical tolerance: with 20,000 draws, a frequency of 0.625 has a standard error of about 0.0034, so a tolerance of 0.015 is more than four standard errors, which makes a false failure vanishingly rare while still catching any real bug (a wrong renormalisation changes the frequency by far more). Fixing the generator's seed makes the test deterministic as well.

8. Numerical and practical traps

Trap 1: temperature zero. Dividing by zero gives inf and NaN. Special-case T = 0 as argmax, and clamp tiny temperatures if the API allows them.

Trap 2: the top-p boundary. Keeping tokens while cumulative mass is ≤ p (instead of the mass before them being < p) can drop the token that crosses the threshold, and when p is smaller than the top token's probability it keeps nothing at all. The "mass before" rule always keeps at least the top token.

Trap 3: products of probabilities. Underflow, as shown. Sum log-probabilities, and compute them with a stable log-softmax (mc10).

Trap 4: order of filters. Applying temperature after top-p changes which tokens are in the nucleus; applying top-k after top-p is different from before. Libraries apply temperature, then top-k, then top-p; document whatever order you use.

Trap 5: sorting the whole vocabulary. A full sort of 128,000 logits per sequence per step is a noticeable cost at high throughput. Prefilter the top few hundred with argpartition, compute their true probabilities with the full log-sum-exp, and sort only those; the test confirms identical nuclei whenever the nucleus fits in the prefilter. (Renormalising within the prefilter before applying top-p would change the nucleus, which is a subtle bug.)

Trap 6: randomness per sequence. In a batch, each sequence needs its own random draws; reusing one uniform for every row correlates outputs across users.

9. Edge cases worth naming

Top-k larger than the vocabulary should keep everything; top-k of 0 conventionally means "off". Top-p of 1.0 keeps everything, but cumulative sums in float32 may end at 0.99999994, so the boundary logic must not drop the last token because of rounding; the "mass before" rule handles it. Logits containing −∞ (masked tokens, constrained decoding) are fine for softmax as long as at least one token is finite. Beam search with all hypotheses finished early stops before the length limit. A beam width larger than the number of possible continuations simply keeps fewer hypotheses, which the code handles because it slices at most b candidates per hypothesis. And an EOS token that is never produced leaves only unfinished hypotheses, which the code still ranks rather than returning nothing.

10. Complexity

Greedy is O(V) per step (an argmax). Sampling with top-k is O(V) with argpartition; top-p with a full sort is O(V log V), or O(V + K log K) with a K-candidate prefilter. Beam search with width b costs b model evaluations per step (batched as one forward pass of b sequences with b caches) plus O(b·V) to select candidates, and b times the KV-cache memory. In the test on 128 rows of 32,000 logits, per-row sorting took 212 ms, the batched sort 293 ms (the sort dominates either way on a CPU) and the top-64 prefilter 87 ms.

11. Talking through the design

In the interview: start with greedy and sampling; write temperature as division of logits with the p^(1/T) interpretation; write top-k and top-p with the precise boundary rule; then beam search over summed log-probabilities with EOS handling and a length penalty; then test with fixed distributions and the greedy-trap example. Finish with judgement: which tasks want which strategy, why beam search degenerates on open-ended text, and how decoding interacts with batching, caches and constrained output.

If the interviewer asks you to extend the code, the natural next steps are a batched sampler (filter all rows, then one inverse-CDF draw per row), a repetition penalty applied to the logits before temperature, constrained decoding through a mask, and beam search that batches its hypotheses into a single forward pass with per-hypothesis caches. Each is a small change to the functions here, and naming them shows you see decoding as part of a serving system rather than a standalone function.

Why high-probability text degenerates

Holtzman and colleagues' key observation is that natural text is not the most probable text under the model. Their Figure 2 shows the per-token probabilities of human text varying widely and often dipping low, while beam search text stays in a narrow, high-probability band and falls into repetition. Repetition is self-reinforcing: once a phrase has appeared, the model assigns higher probability to it appearing again, so maximising probability locks into loops. Their Figure 1 shows beam search (size 32) on GPT-2 Large repeating a phrase, and pure sampling producing incoherent text from the unreliable tail. Nucleus sampling cuts the tail dynamically, keeping the "nucleus" that they note ranges between one and a thousand candidates depending on the step, and they compare it with top-k = 40 and with top-k = 40 at temperature 0.7.

Length normalisation and its alternatives

Google's neural machine translation system (Wu et al., 2016) divides the log-probability by lp(Y) = (5 + |Y|)^α / (5 + 1)^α, with α around 0.6 to 0.7 tuned on development data, and adds a coverage penalty that favours translations attending to every source word. Simpler variants divide by length (α = 1) or add a per-token bonus. The point is the same: beam search optimises a score that, unnormalised, prefers short outputs, and translation quality improves when that bias is removed. Exact search with very large beams (Stahlberg and Byrne) famously finds that the single most probable translation under many models is the empty one, the extreme form of this bias.

Combining filters, and min-p

Practical samplers chain operations: repetition penalties on logits, temperature, top-k, then top-p or min-p. Min-p (the drill) keeps tokens with probability at least a fraction of the top token's probability, so its threshold scales with the model's confidence: one token survives when the top is 0.9 and the rest small, all survive when the top five are near 0.2. At high temperatures, where the flattened tail can hold enough mass to fill a top-p nucleus with junk, min-p still rejects tokens far below the top one, which is why it has become popular for creative sampling.

Constrained decoding

For structured outputs (JSON matching a schema, a function call, a regular expression), constrained decoding sets the logits of every token that would make the output invalid to −∞ before sampling. A grammar compiled into a state machine tells, at each step, which tokens are allowed; the decoder intersects that set with the model's distribution. The result always parses, and the model's preferences decide only among valid continuations. The mask is applied before temperature and truncation, using the same masking machinery as top-k.

One subtlety: masking changes the distribution the model would have chosen from, and if the grammar forces an unlikely token early, the rest of the output can suffer, because the model is now continuing text it would not have written. Good schemas leave the model room (allowing whitespace, ordering fields the way the model naturally writes them), and some systems let the model think in free text first and then produce the constrained output.

Temperature as a calibration knob

Temperature also has a statistical reading: a model's probabilities may be over- or under-confident, and dividing logits by a single fitted temperature (temperature scaling) is the standard post-hoc calibration method for classifiers. For generation it is usually treated as a creativity dial rather than fitted, but the same mathematics applies: T changes the entropy of every step's distribution without changing the ranking of tokens, which is why top-k with T is equivalent to top-k without it in which tokens are kept, but not in how often each is chosen.

Best-of-n and other sequence-level strategies

Several strategies work at the level of whole outputs instead of tokens. Best-of-n samples n completions and keeps the one a scorer prefers (a reward model, a test suite for code, or the model's own log-probability); self-consistency samples n reasoning chains and returns the most common final answer. Both cost n times the generation and often beat a single greedy answer by a wide margin on reasoning and coding tasks, which is why sampling diversity matters even when the user sees only one output. Locally typical sampling is another token-level alternative: it keeps tokens whose surprisal is close to the distribution's entropy, avoiding both the bland most-likely tokens and the incoherent tail.

Speculative decoding

Decoding is memory-bound (mc18), so a cheap draft model proposing several tokens, verified by the large model in one batched forward pass, can produce multiple tokens per expensive step. Leviathan and colleagues' acceptance rule, accept a drafted token with probability min(1, p_large/p_draft) and otherwise resample from the normalised positive part of p_large − p_draft, guarantees the output is distributed exactly as if sampled from the large model alone. It composes with temperature and top-p, applied consistently to both models' distributions.

Where decoding runs

In every generation call: the API's temperature, top_p, top_k and max_tokens parameters map directly onto this lesson's code, applied per sequence at every decode step inside the serving engine, after the logits and before the token is appended to the KV cache. Beam search runs mainly in translation, speech recognition and some extraction systems; chat and code assistants sample.

Failure modes and symptoms

Loops and repetition. Greedy or near-zero temperature on open-ended prompts, or a model that has slipped into a repetitive pattern. Fixes: sampling with top-p or min-p, frequency or presence penalties, n-gram blocking. Measure the repetition rate before and after any change. It is cheap to compute.

Incoherent or off-topic output. Temperature too high or no truncation, so tail tokens get sampled. Lower the temperature or tighten top-p; check for a bug that applies temperature twice. Also check that the logits are not being divided by temperature both in the client library and on the server.

Invalid structured output. Sampling produced JSON that does not parse. Use greedy decoding or constrained decoding for structured fields, and validate with a schema before use.

Truncated beam outputs. Translations that stop early or drop clauses: no or weak length normalisation. Tune α on held-out data.

Inconsistent evaluations. Benchmark scores vary between runs because evaluation used sampling. Evaluate with greedy decoding, or report the mean and spread over several seeds. A two-point difference between models evaluated once each at temperature 0.7 may be nothing but sampling noise.

Sampling throughput bottleneck. At very high batch sizes with large vocabularies, the sort for top-p shows up in profiles. Use a candidate prefilter or fused sampling kernels.

Safety filters bypassed by sampling. A model refuses a harmful request under greedy decoding but occasionally complies when sampled at high temperature, because the compliant continuation has small but non-zero probability. Safety evaluations should sample many times at the production settings, not test a single greedy output, and output-side classifiers should not assume the decoding is deterministic.

Parameter drift between environments. A prompt tested in a playground at temperature 0.7 is deployed with the API default of 1.0, or a client library silently applies its own top-p, and output quality changes. Make decoding parameters explicit in every call and log them with each request. Include them in the cache key for any cached responses, too.

What to monitor

Per-request decoding parameters (so quality changes can be traced to configuration), output length distribution, repetition rate (fraction of outputs with repeated n-grams), structured-output parse failure rate, and, for evaluation, the decoding settings next to every reported score.

A cost estimate

For a 128,000-token vocabulary, a softmax and full sort per sequence per step is about 128,000 × log₂(128,000) ≈ 2.2 million comparisons, against roughly 14 billion floating-point operations for the model's forward pass on one token for a 7-billion-parameter model: negligible per token, but at a batch of 256 sequences it is half a billion comparisons per step on the host or in a separate kernel, which is why serving engines fuse sampling on the GPU and prefilter candidates. Beam search with width 4 multiplies the forward-pass work and the KV cache by 4 for the same output length.

The reference for this problem

Holtzman, Buys, Du, Forbes and Choi's "The Curious Case of Neural Text Degeneration" (arXiv 1904.09751) is the reference for this lesson's view of decoding. It reports that "maximization-based decoding methods such as beam search lead to degeneration: output text that is bland, incoherent, or gets stuck in repetitive loops", illustrated with GPT-2 Large and beam size 32, and proposes Nucleus Sampling, defining the top-p vocabulary as the smallest set of tokens whose cumulative probability reaches p, so that "the size of the sampling set will adjust dynamically based on the shape of the probability distribution at each time step". Its experiments compare greedy decoding, beam search with b = 16, pure sampling, temperature 0.9, top-k = 40 and 640, top-k = 40 with temperature 0.7, and nucleus sampling with p = 0.95, using measures such as Self-BLEU and perplexity against human text. This lesson's batched top-p uses exactly that smallest-set definition, implemented as "keep while the mass before the token is below p".

Work it out

Implement min-p sampling: keep only tokens whose probability is at least min_p times the top token's probability. Show how the kept set adapts between a confident and an uncertain distribution, compared with top-k = 3.

Answer 
def min_p_filter(logits, min_p=0.1, temperature=1.0):
    z = np.asarray(logits, float) / temperature
    p = np.exp(z - z.max()); p /= p.sum()
    keep = p >= min_p * p.max()
    p = np.where(keep, p, 0.0)
    return p / p.sum()

confident = np.log(np.array([0.90, 0.04, 0.03, 0.02, 0.01]))
uncertain = np.log(np.array([0.22, 0.21, 0.20, 0.19, 0.18]))
assert (min_p_filter(confident) > 0).sum() == 1             # only the obvious token survives
assert (min_p_filter(uncertain) > 0).sum() == 5             # every plausible option survives
# top-k = 3 keeps three either way: two junk tokens when confident, drops two good ones when unsure

Min-p's threshold is relative to the model's own confidence, so the candidate set shrinks to one when the model is sure and stays wide when it is not. Top-k keeps a fixed count regardless. Top-p also adapts, but at high temperature it admits a long tail of junk because the tail's cumulative mass grows; min-p's rule keeps rejecting tokens far below the top one, which is why it holds up better for creative high-temperature sampling.
