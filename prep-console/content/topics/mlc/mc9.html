A bank's fraud model gives every card transaction a score between 0 and 1. The product manager asks a simple question: is the new model better than the old one? The answer is a number, and which number you choose, and how you compute it, decides which model ships. Accuracy says both models are 99.9% accurate, because 999 of every 1,000 transactions are legitimate and both models say "legitimate" to nearly everything. ROC-AUC says the new model scores 0.95 against 0.93. Average precision says 0.41 against 0.28, a much bigger gap. And the review team, who can look at 500 flagged transactions a day, wants to know how many real frauds will be among those 500. Each number answers a different question, and an engineer who cannot compute and explain them cannot be trusted to evaluate a model.

That is why "implement F1, ROC-AUC and average precision from scratch" is a common ML coding question, and also an evaluation question in disguise. The formulas look easy, and each hides a bug that ships regularly. ROC-AUC computed by sorting and summing ranks gives a different answer every time the data is shuffled if there are tied scores: in this lesson's test, 0.730 and 0.736 for the same data, against a correct 0.732. Average precision computed with trapezoids differs from the definition most libraries use. Precision with no predicted positives divides by zero. And a model whose scores were saved as float32 probabilities can have its AUC collapse from 0.85 to 0.50, because almost every confident score rounds to exactly 1.0 and the ranking information is gone.

Interviewers also listen for judgement. When would you report AUC and when average precision? What does an AUC of 0.8 mean, in words a product manager would understand? Why is precision at the review team's capacity worth more than either? How would you compute AUC on ten billion rows? These come up in every evaluation discussion, including evaluations of LLM-based classifiers and retrieval systems. When an LLM is used as a judge or a classifier, its outputs are turned into scores and labels and evaluated with exactly these metrics, so the same traps apply there: ties from coarse scores (a judge that outputs only 1 to 5 produces enormous tie groups) and conventions that differ between evaluation scripts.

This lesson builds all three metrics on one six-example dataset by hand, including a tie: the confusion matrix and F1 at a threshold, AUC three ways (counting pairs, summing ranks, adding trapezoids) all landing on 11/18, and average precision step by step to 0.7. It then writes the naive versions (pairwise loops and per-threshold recounts), the vectorised versions (mid-ranks, one sort and two cumulative sums), tests them against each other on deliberately tied data, demonstrates the tie and float32 traps, and closes with ranking metrics (nDCG and MRR) in the drill.

Start with one threshold. A classifier gives each example a score; pick a cut-off, say 0.5, and call everything above it positive. Comparing those calls with the truth sorts every example into one of four boxes: a true positive (flagged and really positive), a false positive (flagged but negative), a false negative (missed positive) and a true negative. These four counts, the confusion matrix, are the raw material of every threshold-based metric.

Two ratios matter most. Precision asks: of the items I flagged, how many were right? Recall asks: of the items I should have flagged, how many did I catch? They pull against each other. Lower the threshold and you catch more positives (recall up) but flag more negatives too (precision down). F1 combines them with a harmonic mean, 2PR/(P + R), which is high only when both are high: precision 1.0 with recall 0.1 gives F1 of only 0.18.

A single threshold hides a lot, so the next step is to look at all thresholds at once. Slide the threshold from above the highest score down to below the lowest. At each position, compute the true-positive rate (recall) and the false-positive rate (the fraction of negatives wrongly flagged). Plotting one against the other traces the ROC curve, from (0, 0) where nothing is flagged to (1, 1) where everything is. A perfect model climbs straight up to (0, 1) before moving right; a random one follows the diagonal. The area under the ROC curve, ROC-AUC, condenses it into one number, and that number has a beautiful meaning: it is the probability that a randomly chosen positive gets a higher score than a randomly chosen negative.

A helpful way to feel what AUC measures is a tournament. Pair every positive with every negative and let them play one game each, which the higher score wins (a tie is a draw worth half a point to each). AUC is the positives' share of all the points. A model with AUC 0.611 wins about 61% of these head-to-heads. Notice what the tournament ignores: how far apart the scores are (0.9 beats 0.2 by the same one point as 0.71 beats 0.70), how many positives there are relative to negatives, and where any threshold sits. That is both its strength, one clean number about ranking quality, and its weakness, because the product only ever experiences one threshold and one class mix.

The precision-recall curve plots precision against recall across the same thresholds, and average precision summarises it: walk down the ranked list, and every time recall increases, add the current precision times the size of the increase. It answers "how clean is the top of my ranked list, on average, as I collect the positives?", which is what a review team or a search user experiences.

Where these summaries break: AUC treats all thresholds as equally important, though you will only ever operate at one; it ignores the base rate, so it can look excellent on a problem where every useful threshold still produces mostly false alarms; and neither AUC nor AP says anything about whether the scores are calibrated probabilities. Choosing the metric is part of the job.

1. The problem as it is usually asked

"Implement precision, recall, F1, ROC-AUC and average precision from scratch, given true labels and predicted scores." Clarify: binary labels 0/1? How should ties in scores be handled (they must be, but say so)? What should precision return when nothing is predicted positive? Should AP match scikit-learn's definition? How large is the data? Then outline: confusion counts and threshold metrics, rank-based AUC with mid-ranks, curves from one sort and cumulative sums, AP as a step sum, and tests against the pairwise definition.

2. The maths in plain words

At a threshold, everything is counting. Across all thresholds, the trick is to notice that the only thresholds that matter are the distinct score values: between two consecutive distinct scores, every threshold flags exactly the same examples. So sort the examples by score from highest to lowest and walk down the list. Each time you pass a distinct score, everything above is "flagged", and the counts of positives and negatives seen so far are the true and false positives at that threshold. Running totals, cumulative sums, give all of them at once.

AUC has three equivalent definitions, and seeing why they agree is the heart of this problem. The pair definition: over all (positive, negative) pairs, the fraction where the positive scores higher, with ties counting half. The geometric definition: the area under the ROC curve. The rank definition: rank all scores from lowest (rank 1) to highest; the sum of the positives' ranks, minus the smallest value that sum could possibly take, divided by the number of pairs. Why does the rank sum count pairs? A positive's rank is one plus the number of examples below it. Summed over positives, that counts every (positive, example below it) pair, including positive-positive pairs, which contribute exactly P(P + 1)/2 however the scores fall. Subtract that, and what remains is the number of (positive, negative-below-it) pairs. That count is the Mann-Whitney U statistic. With ties, a tied pair should count half, and giving tied values the average of their ranks does exactly that.

3. The equations

precision = TP / (TP + FP)        recall = TPR = TP / (TP + FN)        FPR = FP / (FP + TN)
F1        = 2 · precision · recall / (precision + recall)

AUC (pairs) = [ Σ_{i∈pos} Σ_{j∈neg} ( 1[sᵢ > sⱼ] + ½·1[sᵢ = sⱼ] ) ] / (P · N)
AUC (ranks) = ( Σ_{i∈pos} rankᵢ − P(P + 1)/2 ) / (P · N)         ties get mid-ranks
AUC (area)  = Σ_k (FPR_k − FPR_{k−1}) · (TPR_k + TPR_{k−1}) / 2   one point per distinct threshold

AP          = Σ_n (R_n − R_{n−1}) · P_n                           R_0 = 0, distinct thresholds n

Three conventions are worth stating explicitly because libraries differ on them. Precision when nothing is flagged is 0/0; scikit-learn reports 0 by default with a warning (its zero_division parameter), and the solution returns 0. AUC with only one class present is undefined, and the solution raises an error rather than returning 0.5. And AP here is the step sum, which scikit-learn's documentation describes as not interpolated, "different from computing the area under the precision-recall curve with the trapezoidal rule, which uses linear interpolation and can be too optimistic".

4. A worked example by hand

Six examples, sorted by score: (0.9, +), (0.8, −), (0.7, +), (0.7, −), (0.4, +), (0.2, −). Three positives, three negatives, and one tie at 0.7 between a positive and a negative.

At threshold 0.5. Flagged: 0.9, 0.8, 0.7, 0.7. TP = 2 (0.9 and the positive 0.7), FP = 2, FN = 1 (0.4), TN = 1 (0.2). Precision 2/4 = 0.5, recall 2/3 = 0.667, F1 2 × 0.5 × 0.667/(0.5 + 0.667) = 0.571 (exactly 4/7).

AUC by pairs. Nine positive-negative pairs. Positive 0.9 beats 0.8, 0.7 and 0.2: 3. Positive 0.7 loses to 0.8, ties the negative 0.7 (½) and beats 0.2: 1.5. Positive 0.4 beats only 0.2: 1. Total 5.5, so AUC = 5.5/9 = 11/18 = 0.611.

AUC by ranks. Ranked from lowest: 0.2 → 1, 0.4 → 2, the two 0.7s share positions 3 and 4 so each gets 3.5, 0.8 → 5, 0.9 → 6. The positives' ranks are 6, 3.5 and 2, summing to 11.5. Subtract P(P + 1)/2 = 6 to get 5.5, the same count as the pairs; divide by 9. Had the tie been broken by input order, the positive 0.7 would get rank 3 or 4 and the AUC would be 5/9 or 6/9 depending on how the data happened to be stored.

AUC by area. Walk down the distinct thresholds, recording (FPR, TPR): start (0, 0); after 0.9, (0, 1/3); after 0.8, (1/3, 1/3); after both 0.7s together, (2/3, 2/3); after 0.4, (2/3, 1); after 0.2, (1, 1). Trapezoids: 1/3 × 1/3 = 1/9, then 1/3 × (1/3 + 2/3)/2 = 1/6, then 1/3 × 1 = 1/3, and two vertical moves with zero width. Total 2/18 + 3/18 + 6/18 = 11/18. The tie produced one diagonal segment, from (1/3, 1/3) to (2/3, 2/3), whose trapezoid counts that tied pair as exactly half: the geometric version of "ties count half".

Average precision. At each distinct threshold, record (recall, precision): 0.9 gives (1/3, 1/1 = 1.0); 0.8 gives (1/3, 1/2 = 0.5); 0.7 gives (2/3, 2/4 = 0.5); 0.4 gives (3/3 = 1, 3/5 = 0.6); 0.2 gives (1, 3/6 = 0.5). AP adds precision times the increase in recall: 1/3 × 1.0 + 0 × 0.5 + 1/3 × 0.5 + 1/3 × 0.6 + 0 × 0.5 = 0.333 + 0.167 + 0.2 = 0.7. Only thresholds where recall increases contribute, which is why AP is sometimes described as "the average of the precision values at the ranks where each positive is found" (with ties grouped).

The first block asserts every number.

import time
import numpy as np

# The hand-worked example: six scored examples, three positive, with one tie across classes.
y_hand = np.array([1, 0, 1, 0, 1, 0])
s_hand = np.array([0.9, 0.8, 0.7, 0.7, 0.4, 0.2])

pred = (s_hand >= 0.5).astype(int)                      # threshold 0.5
tp = int(((pred == 1) & (y_hand == 1)).sum()); fp = int(((pred == 1) & (y_hand == 0)).sum())
fn = int(((pred == 0) & (y_hand == 1)).sum()); tn = int(((pred == 0) & (y_hand == 0)).sum())
assert (tp, fp, fn, tn) == (2, 2, 1, 1)
precision, recall = tp / (tp + fp), tp / (tp + fn)
assert precision == 0.5 and np.isclose(recall, 2 / 3)
assert np.isclose(2 * precision * recall / (precision + recall), 4 / 7)   # F1 = 0.571

# AUC by counting pairs: 9 (positive, negative) pairs, ties count half.
wins = sum((p > n) + 0.5 * (p == n) for p in s_hand[y_hand == 1] for n in s_hand[y_hand == 0])
assert wins == 5.5 and np.isclose(wins / 9, 11 / 18)                     # 0.611

# The ROC curve and its trapezoids give the same area.
roc_pts = [(0, 0), (0, 1 / 3), (1 / 3, 1 / 3), (2 / 3, 2 / 3), (2 / 3, 1), (1, 1)]
area = sum((x1 - x0) * (y0 + y1) / 2 for (x0, y0), (x1, y1) in zip(roc_pts, roc_pts[1:]))
assert np.isclose(area, 11 / 18)

# Average precision: Σ (recall step) × precision, one step per distinct threshold.
steps = [(1 / 3, 1.0), (0, 0.5), (1 / 3, 0.5), (1 / 3, 0.6), (0, 0.5)]   # thresholds .9 .8 .7 .4 .2
assert np.isclose(sum(dr * p for dr, p in steps), 0.7)

5. The naive implementations

The definitions translate directly into loops: AUC by comparing every positive with every negative (O(P·N)), and the curves by recounting TP and FP from scratch at every distinct threshold (O(n) thresholds times an O(n) count, so O(n²)).

def auc_pairs_naive(y, s):
    """The definition: compare every positive with every negative. O(P · N)."""
    pos = [si for yi, si in zip(y, s) if yi == 1]
    neg = [si for yi, si in zip(y, s) if yi == 0]
    total = 0.0
    for p in pos:
        for n in neg:
            total += 1.0 if p > n else 0.5 if p == n else 0.0
    return total / (len(pos) * len(neg))

def curves_naive(y, s):
    """Recount the confusion matrix at every distinct threshold. O(n²)."""
    P = sum(y); N = len(y) - P
    fpr, tpr, prec, rec = [0.0], [0.0], [], []
    for t in sorted(set(s), reverse=True):
        tp = sum(1 for yi, si in zip(y, s) if si >= t and yi == 1)
        fp = sum(1 for yi, si in zip(y, s) if si >= t and yi == 0)
        fpr.append(fp / N); tpr.append(tp / P)
        prec.append(tp / (tp + fp)); rec.append(tp / P)
    ap = sum((r1 - r0) * p for r0, r1, p in zip([0.0] + rec[:-1], rec, prec))
    return np.array(fpr), np.array(tpr), ap

They are correct, including ties, because they follow the definitions literally, and that makes them the reference for testing. They are slow: for 3,000 examples the pairwise AUC took 211 ms in the test, and it grows with the square of the data; at a million examples with balanced classes it would be 2.5 × 10¹¹ comparisons.

6. The vectorised versions

def confusion(y_true, y_pred):
    y, p = np.asarray(y_true), np.asarray(y_pred)
    tp = int(((p == 1) & (y == 1)).sum()); fp = int(((p == 1) & (y == 0)).sum())
    fn = int(((p == 0) & (y == 1)).sum()); tn = int(((p == 0) & (y == 0)).sum())
    return tp, fp, fn, tn

def precision_recall_f1(y_true, y_pred):
    tp, fp, fn, _ = confusion(y_true, y_pred)
    p = tp / (tp + fp) if tp + fp else 0.0          # convention: no predicted positives -> 0
    r = tp / (tp + fn) if tp + fn else 0.0
    f1 = 2 * p * r / (p + r) if p + r else 0.0
    return p, r, f1

def average_ranks(s):
    """1-based ranks; tied values share the mean of the ranks they span."""
    order = np.argsort(s, kind="mergesort")
    ranks = np.empty(len(s))
    ranks[order] = np.arange(1, len(s) + 1)
    _, first, counts = np.unique(s[order], return_index=True, return_counts=True)
    tied = counts > 1
    for f, c in zip(first[tied], counts[tied]):
        ranks[order[f:f + c]] = f + (c + 1) / 2
    return ranks

def roc_auc(y_true, scores):
    """P(random positive outscores random negative), ties count half: the Mann-Whitney U."""
    y, s = np.asarray(y_true), np.asarray(scores, float)
    n_pos, n_neg = int(y.sum()), int(len(y) - y.sum())
    if n_pos == 0 or n_neg == 0:
        raise ValueError("ROC-AUC is undefined with a single class")
    return (average_ranks(s)[y == 1].sum() - n_pos * (n_pos + 1) / 2) / (n_pos * n_neg)

def _sorted_counts(y_true, scores):
    y, s = np.asarray(y_true), np.asarray(scores, float)
    o = np.argsort(-s, kind="mergesort")
    y, s = y[o], s[o]
    last = np.r_[np.diff(s) != 0, True]             # one point per distinct threshold
    return np.cumsum(y)[last], np.cumsum(1 - y)[last]

def roc_curve(y_true, scores):
    tps, fps = _sorted_counts(y_true, scores)
    return np.r_[0, fps / fps[-1]], np.r_[0, tps / tps[-1]]     # (fpr, tpr)

def average_precision(y_true, scores):
    tps, fps = _sorted_counts(y_true, scores)
    precision, recall = tps / (tps + fps), tps / tps[-1]
    return float(np.sum(np.diff(np.r_[0, recall]) * precision))

Mid-ranks. average_ranks sorts once with a stable sort, assigns ordinal ranks 1..n, then uses np.unique(..., return_index=True, return_counts=True) on the sorted values to find each run of equal values: its starting position f and length c. The run occupies ranks f + 1 to f + c, whose average is f + (c + 1)/2, and every member gets that. The loop runs only over tied runs.

Rank AUC. roc_auc sums the positives' mid-ranks, subtracts P(P + 1)/2 and divides by P·N, refusing single-class input.

Curves. _sorted_counts sorts by descending score, takes cumulative sums of the labels (true positives so far) and of one minus the labels (false positives so far), and keeps only the positions where the next score differs (np.diff(s) != 0, plus the last position). That keeps one point per distinct threshold, so a run of ties becomes a single step. roc_curve divides by the totals and prepends (0, 0); average_precision computes precision and recall at each kept point and sums Δrecall × precision.

Threshold metrics. confusion counts the four boxes with boolean masks, and precision_recall_f1 applies the zero-division convention explicitly. On 3,000 examples the rank-based AUC took 0.77 ms against 211 ms for the pairwise loop, a factor of 274, and the gap grows quadratically.

7. Testing it

The test block checks: the vectorised functions reproduce every hand number (precision, recall, F1, AUC 11/18, the six ROC points, AP 0.7); on 300 examples with scores rounded to one decimal place (so ties are everywhere), the rank AUC equals the pairwise definition, equals the trapezoidal area under the vectorised ROC curve, and the curves and AP equal the naive per-threshold recount; shuffling the input leaves AUC and AP unchanged, while an AUC with ordinal ranks changes (0.730 versus 0.736, against the correct 0.732); AUC is unchanged by a monotone transform of the scores; random scores give AUC near 0.5 and AP near the positive rate; and the float32 saturation trap.

# 1. The vectorised functions reproduce every hand-worked number.
assert np.allclose(precision_recall_f1(y_hand, (s_hand >= 0.5).astype(int)), (0.5, 2 / 3, 4 / 7))
assert np.isclose(roc_auc(y_hand, s_hand), 11 / 18)
fpr, tpr = roc_curve(y_hand, s_hand)
assert np.allclose(fpr, [0, 0, 1 / 3, 2 / 3, 2 / 3, 1]) and np.allclose(tpr, [0, 1 / 3, 1 / 3, 2 / 3, 1, 1])
assert np.isclose(average_precision(y_hand, s_hand), 0.7)

# 2. Against the definitions on data with many ties.
rng = np.random.default_rng(0)
y = rng.integers(0, 2, 300)
s = np.round(y * 0.3 + rng.random(300), 1)            # rounding creates many ties on purpose
assert np.isclose(roc_auc(y, s), auc_pairs_naive(y.tolist(), s.tolist()))
fpr, tpr = roc_curve(y, s)
assert np.isclose(roc_auc(y, s), np.trapezoid(tpr, fpr))     # rank formula = trapezoidal area
nf, nt, nap = curves_naive(y.tolist(), s.tolist())
assert np.allclose(fpr, nf) and np.allclose(tpr, nt) and np.isclose(average_precision(y, s), nap)

# 3. Ties: shuffling the input order changes nothing (a sort-based AUC without tie handling would).
perm = rng.permutation(300)
assert np.isclose(roc_auc(y[perm], s[perm]), roc_auc(y, s))
assert np.isclose(average_precision(y[perm], s[perm]), average_precision(y, s))
def auc_ignoring_ties(y, s):                                  # common bug: ordinal ranks
    r = np.empty(len(s)); r[np.argsort(s, kind="stable")] = np.arange(1, len(s) + 1)
    P = y.sum(); return (r[y == 1].sum() - P * (P + 1) / 2) / (P * (len(y) - P))
assert abs(auc_ignoring_ties(y, s) - auc_ignoring_ties(y[perm], s[perm])) > 1e-3

# 4. Invariants: AUC ignores monotone transforms of the score; AP's floor is the positive rate.
assert np.isclose(roc_auc(y, np.exp(5 * s)), roc_auc(y, s))
yr, sr = rng.integers(0, 2, 20000), rng.random(20000)
assert abs(roc_auc(yr, sr) - 0.5) < 0.02 and abs(average_precision(yr, sr) - yr.mean()) < 0.02

# 5. Precision trap: confident probabilities saturate in float32 and collapse into ties.
z = 20 + rng.normal(size=5000) + 1.5 * (yb := rng.integers(0, 2, 5000))   # very confident logits
p32 = (1 / (1 + np.exp(-z))).astype(np.float32)
auc_logits, auc_p32 = roc_auc(yb, z), roc_auc(yb, p32)
assert (p32 == 1.0).mean() > 0.99                            # almost every score is exactly 1.0
assert auc_logits > 0.8 and abs(auc_p32 - 0.5) < 0.02         # ranking information destroyed

The tie-heavy test data is the most important design choice in the suite. With continuous random scores, ties almost never occur, and an implementation that ignores them passes every test and then fails in production on rounded or saturated scores. Rounding to one decimal place makes ties the common case.

Precision at a capacity, from the same cumulative sums

The review team in the opening story can look at 500 transactions a day. The metric they care about is precision at 500: of the top 500 scores, how many are fraud? The cumulative sums already contain it. After sorting by descending score, cumsum(y)[499] is the number of positives in the top 500, so precision@500 is that divided by 500, and recall@500 divides it by the total number of positives instead. For a threshold-based view, search the per-threshold arrays for the lowest threshold whose precision is still at least some target, or the highest recall reachable while keeping the daily flag count under a limit. All of these are a single pass over arrays you have already built, so there is no reason to report only AUC when the operating question can be answered directly. (When the 500th and 501st scores tie, precision@500 depends on which one is "in"; report the tie-group boundary or break ties by a documented rule.)

Multi-class: macro, micro and weighted averages

With more than two classes, precision, recall and F1 are computed per class, treating that class as positive and all others as negative, and then averaged. The macro average is the plain mean over classes, so a rare class counts as much as a common one; it is the right choice when every class matters equally (rare intents in a support-ticket router). The micro average pools all the TP, FP and FN counts first and computes one precision and recall from the totals; for single-label multi-class problems micro-precision, micro-recall and micro-F1 all equal accuracy, which surprises people in interviews. The weighted average weights each class's score by its number of true examples, which sits between the two. For AUC, the common choices are one-versus-rest AUC per class, macro-averaged, or Hand and Till's pairwise multi-class AUC. Whichever you choose, write it next to the number; "F1 = 0.81" for a ten-class problem means three different things under the three averages.

Edge cases worth naming

A score vector with every value equal gives one ROC segment from (0, 0) to (1, 1) and an AUC of exactly 0.5, the right answer for an uninformative model. A dataset where every positive outscores every negative gives AUC 1.0 and AP 1.0; reversing the scores gives AUC 0.0, which usually means the labels or the score direction are flipped rather than that the model is anti-informative. NaN scores must be rejected or handled explicitly, because NaN sorts unpredictably and compares unequal to itself, which breaks the distinct-threshold mask. Sample weights generalise everything by replacing counts with sums of weights in the cumulative sums and pair counts. And labels given as booleans or strings should be mapped to 0/1 with an explicit positive class before any of this runs.

8. Numerical and practical traps

Trap 1: ties broken by input order. Ordinal ranks, per-example curve points, or an unstable sort make the metric depend on how the data was stored. Use mid-ranks and one point per distinct threshold.

Trap 2: saturated probabilities. In the test, 5,000 examples with very confident logits around 20 (positives about 1.5 higher) had a logit AUC of 0.852. Converted to float32 probabilities, over 99% of scores were exactly 1.0, every pair among them tied, and the AUC was 0.501. The sigmoid is monotone, so computing ranking metrics from logits loses nothing and avoids the problem entirely. The same saturation happens when scores are rounded for storage or display (two decimal places is a common culprit).

Trap 3: division by zero. Precision with no predicted positives, recall with no actual positives, F1 when both are zero, and AUC with a single class. Decide and document each convention; never let NaN propagate silently into an average across slices.

Trap 4: averaging across groups. The mean of per-slice AUCs is not the AUC of the pooled data, and per-slice AUCs on tiny slices are very noisy. Report sizes alongside slice metrics, and use confidence intervals.

Trap 5: label and score alignment. Sorting scores without carrying the labels along, or joining predictions to labels on the wrong key, gives a plausible but meaningless number. The pair-based test on a small sample catches it.

Trap 6: positive-class convention. If the positive class is encoded as 0 or as a string, a library default (pos_label=1) silently evaluates the other class, which turns an AUC of 0.8 into 0.2. Check that a strong model gives AUC above 0.5.

9. Complexity

Threshold metrics are O(n). Rank-based AUC, the curves and AP are each one sort, O(n log n), plus linear passes; memory is O(n). The pairwise definition is O(P·N) and the per-threshold recount O(n²), fine for tests and hopeless at scale. For data that does not fit in memory, histogram the scores per class into fine bins on each shard, add the histograms, and compute AUC and AP from bin counts in O(bins); it is exact if the bins are the score's own precision, and the per-bin ties are handled by the half-count rule.

10. Talking through the design

In the interview: confusion counts and the three threshold metrics with the zero-division rule; AUC's probabilistic meaning; the rank formula with mid-ranks and why subtracting P(P + 1)/2 works; curves from a descending sort and cumulative sums with one point per distinct score; AP as a step sum and how it differs from trapezoidal PR-AUC; tests against the pairwise definition on tie-heavy data. Then the judgement: which metric for which problem, why PR beats ROC for rare positives, and why logits beat stored probabilities.

AUC as a statistic: Wilcoxon, Mann-Whitney and DeLong

The equivalence between AUC and the probability that a random positive outranks a random negative is not a coincidence of formulas; it is the Mann-Whitney U statistic (equivalently the Wilcoxon rank-sum test), and Fawcett's review cites Hanley and McNeil (1982) for it. That connection gives you statistics for free. The U statistic has a known variance, and DeLong, DeLong and Clarke-Pearson's 1988 method estimates the variance of an AUC, and the covariance between two models' AUCs on the same data, from per-example "placement values" (for each positive, the fraction of negatives below it, and vice versa). That yields confidence intervals and a paired test for "is model B's AUC really higher than model A's?" without bootstrapping. Bootstrapping, stratified by class, is the simpler general alternative and works for AP and F1 too. A useful rule of thumb from the U-statistic variance: with only 50 positives, an AUC around 0.8 carries a standard error of a few hundredths, so differences of 0.01 between models on such a set are noise, however many negatives there are.

Gini, KS and other rewrites of the same ranking

Credit-risk teams often report the Gini coefficient, which is 2·AUC − 1; Fawcett notes the relation as Gini + 1 = 2 × AUC. The Kolmogorov-Smirnov statistic is the maximum vertical gap between the ROC curve and the diagonal (the largest TPR − FPR over thresholds). All three summarise the same ranking. Knowing that saves confusion when a finance team says "Gini 0.6" and an ML team says "AUC 0.8": they agree.

Why ROC curves flatter rare-positive problems

The false-positive rate divides false positives by all negatives. If negatives outnumber positives 1,000 to 1, a threshold with 90% recall and a 1% false-positive rate flags 0.9 frauds and 10 legitimate transactions per 1,000 transactions: precision 8%. The ROC point (0.01, 0.9) looks superb; the review team sees 11 alarms for every real fraud. ROC curves are invariant to the class ratio (a feature when you want a property of the scorer alone), while precision depends on it (a feature when you want to know what users will experience). Saito and Rehmsmeier's study is the standard citation for preferring PR plots on imbalanced data.

Interpolated AP, mAP and the many definitions

Information retrieval and object detection use variants. The 11-point interpolated AP (older TREC and PASCAL VOC up to 2010) averages, at recall levels 0, 0.1, …, 1, the maximum precision achieved at any recall at least that high. "All-point" interpolation does the same at every recall level where recall changes, which makes the PR curve monotonically decreasing before summing; COCO's mAP averages 101-point interpolated AP over IoU thresholds and classes (mc23 builds the IoU part). Interpolation always gives an AP at least as high as the step sum. None is wrong; mixing them is. A model's "mAP" is meaningless without the definition.

Choosing the operating point

Summary metrics compare models; a deployed classifier runs at one threshold. Choose it from the costs: with false-positive cost c_FP and false-negative cost c_FN and calibrated probabilities, flag when p > c_FP / (c_FP + c_FN). Without calibration, choose it on validation data to meet a constraint: the threshold whose precision is at least 30%, or whose number of flags per day matches the review team's capacity. The cumulative sums used for the curves give every threshold's metrics at once, so this search is free.

Calibration is a separate axis

None of AUC, AP or F1 says whether a score of 0.3 means a 30% chance. Two models with identical rankings, and therefore identical AUC and AP, can have very different calibration, for example one producing well-spread probabilities and the other squashing everything between 0.45 and 0.55. When probabilities are consumed (expected-cost decisions, risk scores shown to users, combining models), measure calibration directly: log-loss or the Brier score (mean squared difference between probability and label) on held-out data, plus a reliability diagram that bins predictions and compares the mean prediction in each bin with the observed positive rate. A model can be improved in calibration (Platt scaling, isotonic regression) without changing its ranking at all, which is why ranking metrics and calibration metrics should both appear in an evaluation report.

Ranking metrics: MRR and nDCG

When the output is a ranked list per query (search, retrieval for RAG, recommendations), per-query ranking metrics replace AUC. Mean reciprocal rank averages 1/(rank of the first relevant item), which suits tasks with one right answer. nDCG handles graded relevance: each item contributes its gain (often 2^rel − 1) discounted by 1/log₂(rank + 1), and the total is divided by the best achievable, computed from all judged items for the query. The drill implements both and shows the classic bug, normalising by an ideal built only from the returned items.

Where these metrics run

Model selection and A/B readouts for every classifier; monitoring dashboards (daily AUC and precision at the operating threshold on labelled feedback); fairness audits by slice; evaluation of LLM-based classifiers and judges against human labels; and retrieval evaluation for search and RAG systems with recall@k, MRR and nDCG. Because the same few numbers decide launches, small implementation differences become arguments between teams.

Failure modes and symptoms

Metric disagreement between teams. Two dashboards show different AUCs for the same model. Causes: tie handling, a different AP definition, sample weights, or one team scoring stored rounded probabilities. Fix: one shared, tested implementation, and the definition written next to every number. A tiny shared test set with hand-computed answers, like this lesson's six examples, settles such disputes in minutes.

AUC collapse after a storage change. A pipeline starts writing scores as float32 or rounded to two decimals, and AUC drops sharply for no modelling reason. Detection: the fraction of tied scores jumps. Fix: store logits or float64.

Great offline AUC, poor online precision. The offline set had a different class ratio from production (balanced sampling for labelling, say). AUC is ratio-invariant, precision is not. Evaluate precision on data with the production ratio, or reweight.

Delayed labels. Fraud labels arrive weeks later, so yesterday's metrics are computed on the few cases already labelled, which are not a random sample. Report label coverage alongside metrics and recompute when labels mature.

Slice noise. A small segment's AUC swings from 0.71 to 0.83 day to day and triggers alerts. With 40 positives, the confidence interval is wide. Add intervals and minimum sample sizes to alerts.

Threshold drift. The threshold was chosen to give 30% precision last quarter; the score distribution has since shifted, so the same threshold now flags twice as many transactions at lower precision, while AUC is unchanged because the ranking is as good as ever. Monitor the flag volume and precision at the deployed threshold, not only threshold-free metrics, and re-derive the threshold from fresh validation data when they move.

A worked operating-point example

Suppose a day brings 1,000,000 transactions, 1,000 of them fraudulent, and the chosen threshold has recall 0.9 and a false-positive rate of 1%. The model catches 900 frauds and flags 0.01 × 999,000 = 9,990 legitimate transactions, so the review team faces 10,890 alerts, of which 8.3% are real. On a ROC plot that operating point, (0.01, 0.9), sits near the top-left corner and looks excellent. On a precision-recall plot it sits at precision 0.083, which is what the team will actually live with. Moving the threshold to a false-positive rate of 0.1% might cut recall to 0.7 but give 700 real frauds among 1,699 alerts, 41% precision, which may well be the better product. Writing this arithmetic out is the most persuasive thing you can do in an evaluation review.

What to monitor

At the operating threshold: precision, recall and the volume of flags per day. Across thresholds: AUC and AP with bootstrap intervals, by slice. For the scores themselves: the fraction of tied values, the distribution of scores (drift), and calibration if probabilities are consumed. For ranking systems: recall@k and nDCG@k per query type.

The reference for this problem

Tom Fawcett's "An introduction to ROC analysis" (Pattern Recognition Letters 27, 2006, pages 861-874) is the standard reference for the ROC part of this lesson. It gives the efficient algorithm for building the curve by sorting the scores, and it singles out "sequences of equally scored instances": with four negatives and six positives tied, the curve could follow an "optimistic" or a "pessimistic" path depending on how the sort orders them, and the correct "expected" curve is the diagonal segment, exactly the one-point-per-distinct-score rule used here. It states that "the AUC of a classifier is equivalent to the probability that the classifier will rank a randomly chosen positive instance higher than a randomly chosen negative instance", that this "is equivalent to the Wilcoxon test of ranks", and that Gini + 1 = 2 × AUC. Its Algorithm 2 computes the area as a sum of trapezoids, "rather than rectangles in order to average the effect between points", the geometric form of counting ties as half. For average precision, scikit-learn's documentation defines AP = Σₙ (Rₙ − Rₙ₋₁)Pₙ and notes the implementation "is not interpolated and is different from computing the area under the precision-recall curve with the trapezoidal rule, which uses linear interpolation and can be too optimistic".

Work it out

Implement nDCG@k (graded relevance) and MRR for a set of ranked result lists. Use the gain 2^rel − 1 and the discount 1/log₂(rank + 1).

Answer 
def dcg_at_k(rels, k):
    rels = np.asarray(rels, float)[:k]
    return float(np.sum((2 ** rels - 1) / np.log2(np.arange(2, len(rels) + 2))))

def ndcg_at_k(rels, k, all_rels=None):
    """rels: relevance of the returned items in ranked order.
    all_rels: relevance of every judged item for the query (defaults to rels)."""
    ideal = dcg_at_k(sorted(all_rels if all_rels is not None else rels, reverse=True), k)
    return dcg_at_k(rels, k) / ideal if ideal > 0 else 0.0

def mrr(ranked_lists):
    return float(np.mean([next((1 / (i + 1) for i, rel in enumerate(l) if rel > 0), 0.0)
                          for l in ranked_lists]))

assert ndcg_at_k([3, 2, 1, 0], 4) == 1.0                      # already ideal
assert ndcg_at_k([0, 1, 2, 3], 4) < ndcg_at_k([3, 0, 1, 2], 4) < 1.0
# a relevant document the system never returned still lowers the score
assert ndcg_at_k([1, 0], 2, all_rels=[1, 3]) < ndcg_at_k([1, 0], 2)
assert np.isclose(mrr([[0, 1, 0], [1, 0], [0, 0, 0]]), (1 / 2 + 1 + 0) / 3)

The subtle point is the ideal ranking: it must be built from all judged relevant documents for the query, not only the ones the system returned; otherwise a system that returns one mediocre document and nothing else scores a perfect 1.0. MRR rewards only the first relevant item, which suits question answering; nDCG rewards the whole ordering, which suits search and recommendations.
