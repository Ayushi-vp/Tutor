Imagine you are asked to write the software that lets a browser in Mumbai load a page from a server in Virginia. The bits have to leave your laptop as radio waves, turn into light in an undersea fibre, cross equipment owned by a dozen different companies, survive being corrupted or lost along the way, find the one machine out of billions that has the page, reach the one program on that machine that serves it, and arrive in a form the browser can understand. If every web browser had to handle all of that itself, including the details of every kind of cable and radio, no one could ever write a browser. And every time someone invented a faster kind of Wi-Fi, every program on earth would need rewriting.

Networking avoids this by splitting the job into layers. Each layer solves exactly one part of the problem and offers a simple service to the layer above it, while relying on the layer below. The browser only has to say "send this request to that server"; it never learns whether the bits went over copper, fibre or radio. The Wi-Fi chip only has to get a chunk of bytes to the next device across the room; it never learns that those bytes are a web page.

This matters to you as an engineer for three practical reasons. First, the layers are the vocabulary of the field: interviewers and colleagues say "an L4 load balancer", "that's an L7 concern" or "it's failing at the TCP layer" and expect you to know exactly what that implies. Second, the layer a device works at decides what it can see and do: a box that only reads layer 4 cannot route requests by URL. Third, and most important day to day, the layers are a debugging map. When "the service is down", checking one layer at a time from the bottom up turns a vague panic into a short, ordered checklist.

This lesson builds that map from scratch. You will learn what a protocol and a header are, walk through the five layers that matter in practice and the kind of address each uses, watch a request get wrapped layer by layer and then travel hop by hop across routers, compare the seven-layer OSI model with the four-layer TCP/IP model the internet actually uses, place real devices on the layers, and finish with a layer-by-layer debugging method you can use tomorrow. It is the foundation for every other topic in this track, so it takes its time.

Two ideas first: protocol and header

A protocol is an agreed set of rules and message formats that two parties follow so they can understand each other. "Say hello, state your request, wait for a reply, say goodbye" is a protocol for a phone call. Computers need the same thing, written down precisely enough that two programs built by strangers on different continents interoperate.

Most network protocols work by putting a header in front of the data they carry. A header is a small block of bookkeeping bytes: who this is from, who it is for, how long it is, what kind of data follows. The data behind the header is called the payload. The key trick of layering is that one layer's entire message, header and all, becomes the next layer's payload.

The analogy: sending a parcel through a company post room

You write a letter to a colleague at another company's office in another city. You write it in a language you both understand (that is the application layer). You put it in an internal envelope marked with your colleague's name and department, so that once it reaches their building it goes to the right desk (the transport layer, and the department is like a port). The post room puts that in a postal envelope with the street address of their building (the network layer, and the street address is like an IP address). The postal service hands the parcel from depot to depot; each van only knows how to get it to the next depot, and the van's own delivery slip is thrown away and replaced at every depot (the data link layer, and the slip is like a MAC address). The vans and roads themselves are the physical layer.

Notice what each party does not need to know. The van driver never opens the envelope. The post room never reads the letter. Your colleague never learns which roads the vans took. That independence is exactly what layering buys.

The analogy breaks in two places worth remembering. Real networks lose and reorder "parcels" all the time, and one layer (usually TCP) has the job of noticing and resending. And real "depots" (routers) decide the next hop for every single packet independently, in microseconds, so two packets of the same conversation can take different routes.

The five layers you actually use

From the bottom up, with the kind of address each one uses:

  • Layer 1, physical: turns bits into signals (voltage on copper, light pulses in fibre, radio waves) and back. No addresses; it just moves bits between two directly connected devices.
  • Layer 2, data link: moves a chunk of bytes, called a frame, from one device to the next device on the same local network, using MAC addresses, which are 48-bit hardware addresses such as 3c:22:fb:0a:11:01. Ethernet and Wi-Fi live here.
  • Layer 3, network: moves a packet from the original sender to the final destination across many networks, using IP addresses such as 203.0.113.9. The Internet Protocol (IP) and routers live here.
  • Layer 4, transport: delivers data to the right program on the destination host, using port numbers (443 is the conventional port for HTTPS, 5432 for PostgreSQL). TCP (reliable, ordered) and UDP (minimal, no guarantees) live here.
  • Layer 7, application: the conversation the programs actually care about, such as HTTP for the web, DNS for looking up names, SSH for remote shells. Addresses here are names and URLs, like https://example.com/index.html.

Why is the top one numbered 7 and not 5? Because the numbers come from the seven-layer OSI model, which has two extra layers (5 and 6) that in practice got folded into the application. You will see the full mapping in the body.

The big picture in one diagram

When your browser sends a request, each layer wraps what it received from above with its own header. This is called encapsulation. The receiver does the reverse, decapsulation: each layer reads and removes its own header and hands the rest upward.

If you stop reading here, keep this picture: each layer solves one problem, uses one kind of address, and wraps the layer above. Everything else in networking hangs off it.

1. What each layer promises, and what it does not

A layer is defined by the service it offers upward, so it is worth being precise about each promise.

Physical (L1) promises to move a stream of bits between two devices that are directly connected by a cable or share a radio channel. It does not know where a message starts or ends, and it makes no promise that the bits arrive uncorrupted. Problems here look like a cable that is unplugged, a damaged fibre, or Wi-Fi interference.

Data link (L2) promises to move a frame (a bounded chunk of bytes with a start and an end) to another device on the same local network, and to detect corruption on that one link. It detects corruption with a checksum: the sender computes a small number from the frame's bytes (Ethernet uses a 32-bit value called the Frame Check Sequence, or FCS) and appends it; the receiver recomputes it and throws the frame away if it does not match. Every network interface has a MAC address (MAC stands for Media Access Control), and a frame carries a source and a destination MAC. The crucial limitation is local: a MAC address means something only on one link or one local network. Ethernet (wired) and Wi-Fi (the 802.11 family of standards from the IEEE, the engineering standards body) are the two link layers you meet daily.

Network (L3) promises to try to move a packet from any host to any other host on the internet, across as many intermediate networks as needed. It is "best effort": packets can be lost, duplicated, delayed or delivered out of order, and IP will not notice or fix any of that. Every host has an IP address, either 32-bit IPv4 (203.0.113.9) or 128-bit IPv6 (2001:db8::9). IP addresses are hierarchical, grouped into ranges that belong to networks, which is what lets routers forward towards them without knowing every host individually (addressing, subnets and routing get their own topic, net3). A companion protocol, ICMP (Internet Control Message Protocol), carries layer-3 error and control messages such as "destination unreachable"; ping uses it.

Transport (L4) promises to deliver data between two specific programs, not just two hosts. It does this with ports: 16-bit numbers from 0 to 65535. A server program listens on a well-known port (443 for HTTPS), and the client's operating system picks a temporary ephemeral port for its end (on Linux, from 32768 to 60999 by default). The pair of IP addresses plus the pair of ports identifies one conversation. There are two classic transport protocols. TCP (Transmission Control Protocol) sets up a connection, numbers every byte, resends anything lost and hands the application an ordered, reliable stream; its details are net4. UDP (User Datagram Protocol) adds only ports and a checksum and sends independent messages called datagrams with no guarantees; it is used where speed matters more than perfection, and as a foundation for newer protocols like QUIC (net5).

Application (L7) is everything the programs actually say to each other: an HTTP request and response (net7), a DNS query (net6), an SSH session. This layer carries meaning; all the layers below just carry bytes.

The pattern to notice is that each layer adds exactly one new capability: L1 moves bits, L2 adds frames and local delivery, L3 adds global addressing and routing, L4 adds programs and (with TCP) reliability, L7 adds meaning. That is why the same few layers show up in every design and every outage.

2. Encapsulation, step by step, with real sizes

Let us trace your browser sending GET /index.html to a server at 203.0.113.9, port 443. (Real HTTPS would first encrypt the request with TLS, the protocol that encrypts a connection and proves the server's identity, covered in net9. We will ignore encryption for this trace; it just turns the data into unreadable bytes of about the same size.)

  1. Application. The browser produces the HTTP request, say 400 bytes of text. It hands those bytes to the operating system through a socket, the programming interface for "a network connection" (sockets are net13).
  2. Transport. The kernel's TCP code puts a 20-byte TCP header in front: source port 51514 (ephemeral), destination port 443, a sequence number saying which bytes these are, and a checksum. The result, 420 bytes, is a TCP segment.
  3. Network. The IP code puts a 20-byte IPv4 header in front: source IP (your laptop, 198.51.100.7 in this trace), destination IP 203.0.113.9, a protocol field saying "the payload is TCP", and a TTL (Time To Live) of 64. The result, 440 bytes, is an IP packet.
  4. Data link. The network card's driver puts a 14-byte Ethernet header in front (destination MAC, source MAC, and a type field saying "the payload is IPv4") and a 4-byte FCS checksum after. The result, 458 bytes, is a frame.
  5. Physical. The card turns the frame into signals on the wire or in the air.

On arrival, each layer reads its own header, uses the "what is my payload" field (Ethernet's type, IP's protocol number, TCP's destination port) to decide who gets the rest, strips the header, and passes the payload up. This is why the design works: each layer only ever parses its own header, and a small "next protocol" field tells it which code to hand the payload to.

Two numbers follow directly from this and come up constantly. The MTU (Maximum Transmission Unit) is the largest packet a link carries in one frame; for standard Ethernet it is 1,500 bytes. Subtract 20 bytes of IP header and 20 of TCP header and you get the MSS (Maximum Segment Size) of 1,460 bytes, the most application data one ordinary TCP packet can carry. Header overhead therefore costs about 4 percent on full-size packets but can dominate on small ones: a 50-byte message sent alone carries 58 bytes of Ethernet, IP and TCP overhead.

3. Inside one local network: switches, MAC addresses and ARP

Start with the smallest case: two machines plugged into the same switch, for example an office network. A switch is a layer-2 device with many ports. It keeps a table of which MAC address lives behind which port. It builds that table by learning: whenever a frame arrives on port 3 with source MAC 3c:…:01, it notes "3c:…:01 is on port 3". When a frame arrives for a destination it already knows, it sends it out of only that port. When it does not know the destination yet, it floods the frame out of every port and lets the right machine pick it up. The switch never looks at IP addresses; it only reads the Ethernet header.

That leaves a puzzle. Programs talk in IP addresses, but a frame needs a destination MAC. How does a host that wants to send to 192.168.1.30 learn which MAC address that is? It uses ARP (Address Resolution Protocol). The host sends a broadcast frame, addressed to the special MAC ff:ff:ff:ff:ff:ff that every device on the local network receives, asking "who has 192.168.1.30? tell 192.168.1.20". The owner answers directly with its MAC, and the asker stores the answer in its ARP cache for a few minutes so it does not have to ask again. (IPv6 does the same job with a protocol called Neighbor Discovery.) You can see your ARP cache with ip neigh on Linux or arp -a on Windows and macOS.

ARP is the glue between layers 2 and 3, and it has a sharp edge: it only works on the local network, because broadcasts do not cross routers. That leads to the most important rule in this lesson.

4. Leaving the local network: routers and hop-by-hop delivery

Before sending any packet, a host asks one question: is the destination on my own local network? It answers it using its own IP address and its subnet mask, which together describe which range of addresses is "local" (net3 explains how). If the destination is local, the host ARPs for the destination's MAC and sends the frame straight to it. If the destination is not local, the host sends the frame to its default gateway, the router configured for its network, and it ARPs for the router's MAC address, not the server's. Your laptop never learns, and never needs, the MAC address of a server in another country.

A router is a layer-3 device connecting two or more networks. When a frame arrives, the router checks the FCS, strips the Ethernet header and trailer, and reads the IP header. It then does three things:

  • It decrements the TTL by one. If the TTL reaches zero, it discards the packet and sends an ICMP "time exceeded" message back to the sender. TTL exists so that a packet caught in a routing loop dies instead of circling forever.
  • It looks up the destination IP in its routing table, a list of address ranges and the next hop for each, and picks the most specific match.
  • It builds a brand-new frame for the outgoing link: source MAC is the router's own outgoing interface, destination MAC is the next router (found with ARP, or already cached), and a fresh FCS. For IPv4 it also recomputes the IP header checksum, because the TTL changed.

This is the single fact interviewers probe most in this topic: MAC addresses are hop-by-hop, IP addresses are end-to-end. It also explains how traceroute works. It sends packets with TTL 1, then 2, then 3, and so on. The first router decrements TTL 1 to 0 and replies "time exceeded", revealing itself; the second router does the same for TTL 2; and so on until the destination answers. The tool is just a clever abuse of the loop-prevention counter.

A real path from a home to a big website has 10 to 20 routers. Your home router is also usually doing NAT (Network Address Translation): it rewrites your private source address such as 192.168.1.20 into its single public address on the way out, and back on the way in, which is how a whole household shares one public IPv4 address. NAT is the main exception to "IP addresses stay end to end", and net3 covers it in detail.

5. The two models: OSI and TCP/IP

You now have the five working layers. Two formal models describe them, and interviews use both.

The OSI model (Open Systems Interconnection), published by ISO in 1984, has seven layers. It was designed alongside a full set of OSI protocols meant to replace the early internet's; those protocols mostly lost the market, but the model's numbering stuck. The TCP/IP model, written down in RFC 1122 in 1989 (RFCs are the numbered documents that define internet standards), describes what the internet actually runs, in four layers: link, internet, transport and application. Some textbooks split its link layer in two and call it a five-layer model, which is the version this lesson has been using.

What happened to layers 5 and 6? Session (L5) was meant to manage long-lived dialogues: opening, checkpointing and resuming them. Presentation (L6) was meant to handle data representation: character encoding, compression and encryption. On the internet those jobs are done inside the application protocol or by libraries the application calls. HTTP handles its own compression; JSON and Protocol Buffers (a compact binary format from Google) are encodings chosen by the application; TLS does encryption as a library sitting between TCP and HTTP. That is why TLS is variously called "layer 5", "layer 6" or "part of layer 7": the honest answer in an interview is "it sits between transport and application and does not fit the model cleanly".

6. Devices and what each can see

A useful way to classify any network device is by the highest layer whose header it reads, because that decides what information it can act on.

Two consequences come up in design interviews. First, an L4 load balancer (a device that spreads connections over servers, covered in net10) forwards whole TCP connections by address and port, which makes it fast and protocol-agnostic but blind to requests: it cannot send /api to one pool and /images to another. Second, an L7 proxy can do exactly that, but for HTTPS it must terminate TLS, meaning it holds the certificate, decrypts the traffic, reads it, and usually re-encrypts it to the backend. That costs CPU and makes the proxy a place where plaintext exists, which is a security decision, not just a performance one.

Firewalls follow the same logic. A stateful firewall, like a cloud security group (the per-server firewall rules that cloud providers such as AWS attach to each machine), remembers connections it has allowed out so it can let the replies back in; a stateless one judges each packet alone. Most cloud firewalls drop disallowed packets silently rather than rejecting them, which is why a missing firewall rule shows up as a timeout rather than an error. That brings us to debugging.

7. Using the layers to debug

The layers give you an order in which to check things. Each layer depends on all the layers below it, so the lowest failing layer is the real problem and everything above it is a symptom. Work bottom-up and prove each layer before moving on.

Name resolution appears before TCP in that list even though DNS is an application-layer protocol, because you must turn a name into an IP address before you can open a connection to it. DNS itself is net6; for now it is enough to know that it is the internet's directory from names to IP addresses and that a surprising fraction of "network outages" are DNS problems.

Two TCP failure messages deserve special attention because they point in opposite directions. Connection refused means your connection request reached the host and the host's kernel replied with a TCP RST (reset), meaning "nothing is listening on that port". The network is fine; the service is down, listening on a different port, or bound only to 127.0.0.1 (localhost) so it only accepts local connections. Connection timed out means your request got no answer at all. The client retried a few times and gave up, which on Linux takes roughly two minutes by default (the exact figure depends on kernel version). Something dropped the packets silently: a firewall or security group, a wrong route, a wrong IP address from stale DNS, or a host that is off. You look at the service for the first and at the network path for the second.

curl -v is worth knowing well because it walks up the layers for you and prints each step: resolving the name, "Connected to … port 443", the TLS handshake, then the HTTP request and response. The first line that goes wrong tells you the layer.

Layering is a design principle, not a law

Layering works because each layer hides its implementation behind a narrow interface. The price is that information useful to one layer is hidden in another. The classic example is wireless: TCP treats packet loss as a sign of congestion and slows down, but on Wi-Fi a lot of loss is radio interference, so TCP backs off when it did not need to. RFC 3439's section "Layering Considered Harmful" makes the general case: strict layering can duplicate functions (checksums and retransmission at several layers) and hide the information needed to optimise. Senior engineers treat the model as a tool for reasoning, and deliberately cross layers when the payoff is worth it, for example a load balancer that reads layer-7 health checks to make layer-4 routing decisions.

The narrow waist: why IP is the centre of the hourglass

Draw every protocol as a shape and you get an hourglass: many link technologies at the bottom (Ethernet, Wi-Fi, 5G, fibre), many applications at the top, and exactly one protocol in the middle, IP. This "narrow waist" is why the internet could absorb forty years of new hardware and new applications. A new link technology only needs to carry IP packets, and a new application only needs to use IP; neither needs the other. It is also why changing the waist is so slow: moving from IPv4 to IPv6 has taken decades, because every device at the waist has to learn it.

The end-to-end argument

Saltzer, Reed and Clark's paper argues that a function like reliable delivery can only be completely implemented at the endpoints, because only they know what "correct" means; the network can at most help as a performance optimisation. The concrete consequence: TCP's 16-bit checksum and Ethernet's per-link FCS do not guarantee your data is intact. A frame can be corrupted inside a router's memory after one link's check and before the next link's new checksum is computed; a proxy that terminates and re-sends the TCP connection computes a fresh checksum over whatever bytes it holds; and a 16-bit checksum misses some multi-bit errors. That is why storage and replication systems add their own strong end-to-end checksums (for example a hash of each object or block verified on read) instead of trusting the transport.

Layer violations and ossification

In theory, routers read only up to layer 3. In practice, the internet is full of middleboxes: NATs that rewrite L3 and L4 headers, firewalls and load balancers that parse L4 and L7, and "optimisers" that modify TCP. Each one encodes assumptions about what TCP headers look like, and silently drops or strips anything unfamiliar. The result is ossification: it became nearly impossible to deploy changes to TCP, because some fraction of paths would break. QUIC (net5) is partly a response. It runs over UDP, which middleboxes pass without inspection, and encrypts almost all of its own transport headers, so middleboxes cannot come to depend on them. It is a deliberate choice to make the transport layer invisible to the network.

Tunnels, overlays and the MTU tax

A tunnel carries one packet as the payload of another: a VPN wraps your packets in encrypted outer packets, and cloud networks and Kubernetes (the container platform covered in sc15) often use overlays such as VXLAN, which wraps a whole Ethernet frame inside UDP (port 4789) and adds 50 bytes of outer Ethernet, IP, UDP and VXLAN headers. Layering makes this possible, since a packet does not care what carries it, but every added header comes out of the MTU. If the physical MTU is 1,500, the inner packets must be at most 1,450 bytes. Senders learn the limit through Path MTU Discovery: packets are sent with a "don't fragment" flag, and a router that cannot forward one without splitting it drops it and sends back an ICMP "fragmentation needed" message with the size that fits. If a firewall blocks that ICMP message, the sender never learns, and full-size packets vanish without trace. This PMTUD black hole is a classic cross-layer failure: a layer-3 control message blocked by an overzealous security rule breaks layer-7 transfers.

Where latency really comes from

Every packet's delay has four parts. Propagation is distance over the speed of light in fibre, roughly two-thirds of the speed in vacuum, about 200 km per millisecond: New York to London is about 5,600 km, so at least 28 ms one way and 56 ms round trip before any equipment is involved. Transmission is size over bandwidth: 1,500 bytes take 12 microseconds at 1 Gbps but 1.2 ms at 10 Mbps. Queueing is time spent waiting in buffers behind other packets and grows sharply as a link approaches saturation. Processing is time in routers, kernels and applications. You cannot speed up light, so the only levers on propagation are moving closer (cloud regions near users, and CDNs, content delivery networks that serve copies of content from servers close to users, net12) or doing fewer round trips (connection reuse, faster handshakes); queueing and processing are where tuning and capacity planning pay off.

Checksums and responsibilities at each layer

It is instructive to list who checks what. Ethernet's FCS protects one link and is recomputed at every hop. The IPv4 header checksum protects only the IP header and is also recomputed at every hop because TTL changes; IPv6 dropped it entirely, reasoning that link and transport checks already exist and that per-hop recomputation wasted router effort. TCP and UDP checksums cover their header, payload and a "pseudo-header" of the IP addresses, end to end between the two transport endpoints. Each layer protects exactly its own scope, which is the layering idea applied to integrity.

Failure modes by layer, and how they look

In production the symptom almost always appears at the top ("requests are failing", "the page is slow") while the cause can be at any layer. Knowing the characteristic signature of each layer shortens incidents dramatically.

  • L1-L2: a bad cable, optic or network card shows up as rising interface error counters (CRC errors, meaning frames whose FCS checksum did not match, and drops) and as retransmissions at the TCP layer on that host only. In the cloud you rarely see this layer directly; the provider handles it, and you see it indirectly as a single unhealthy instance.
  • L3: missing routes, misconfigured subnets or overlapping address ranges (two VPCs, or Virtual Private Clouds, the private networks a cloud account gets, using the same 10.0.0.0/16 cannot be peered) show up as timeouts from specific sources to specific destinations. Routing changes on the internet, announced between networks with BGP (Border Gateway Protocol, the protocol networks use to tell each other which address ranges they can reach), can make whole services disappear.
  • Firewalls and security groups (L3-L4): silently dropped packets, so timeouts, never refusals. The first question in any new "cannot connect" incident should be "was a rule changed?".
  • MTU: connections open and small requests work, but large responses, file uploads or TLS handshakes with big certificate chains hang. Common after adding a VPN, a service mesh (a proxy placed beside every service to handle its traffic) or an overlay network.
  • DNS: failures to resolve, or resolving to an old IP after a migration because of caching. Often looks like "some clients work, some don't".
  • TLS: expired certificates, missing intermediate certificates, or name mismatches after moving a service behind a new hostname. These are sudden, total and at a predictable time (expiry dates are known in advance).
  • L7: HTTP 5xx errors from overloaded or broken backends, and 502 or 504 errors generated by a proxy that cannot reach or wait long enough for its backend.

Observability: seeing each layer

Interface counters (ip -s link, or the cloud provider's instance network metrics) cover layers 1-2. Flow logs, such as AWS VPC Flow Logs, record which connections were accepted or rejected by security rules and are the fastest way to prove a firewall drop in the cloud, where you cannot run a capture on the provider's network. tcpdump or Wireshark on the hosts at each end shows exactly which packets arrive and leave: if the server sees the client's connection attempts but never replies, the fault is on the server; if it replies but the client never sees the reply, it is the return path. mtr combines ping and traceroute to show loss and latency per hop over time. At the top, load balancer and proxy access logs record status codes and timings per request, and TCP retransmission counters (nstat, ss -ti) reveal a lossy path even when requests eventually succeed.

The knobs people actually tune

MTU on interfaces and tunnels (lower it inside overlays, or enable jumbo frames of about 9,000 bytes inside a data centre network that supports them); MSS clamping, where a router rewrites the MSS value that TCP advertises during connection setup so both ends send smaller segments through a tunnel; firewall rules to reject rather than drop on internal networks, so misconfigurations fail fast with "refused" instead of hanging; connection timeouts in clients, which should be seconds for internal calls rather than the operating system's default of around two minutes; and DNS cache lifetimes before planned migrations.

War story: Facebook, October 2021

On 4 October 2021, from about 15:40 UTC, Facebook, Instagram and WhatsApp vanished from the internet for roughly five and a half hours. A maintenance command inadvertently took down Facebook's backbone, and its edge routers then withdrew the BGP announcements for the address ranges containing Facebook's own DNS servers. To the rest of the world, the symptom was at the application layer: every lookup for facebook.com failed, and public DNS resolvers saw many times their normal query volume as clients retried. The cause was two layers down, at L3 routing. Recovery was slowed because internal tools and even physical access systems depended on the same network and DNS that were down. The lessons are layer lessons: diagnose symptoms downward, and never let the tools you need to fix a layer depend on that same layer.

War story pattern: the hanging VPN

A team moves a service behind a new VPN or service mesh. Health checks pass and small API calls work, but large downloads stall forever. Captures show full-size packets leaving the sender and never arriving, and no ICMP "fragmentation needed" coming back because a security rule blocks all ICMP. The fix is to allow that ICMP type, lower the MTU on the tunnel interface, or clamp the MSS, and the lesson is that "block all ICMP" is not a harmless hardening step.

Twenty minutes, on your own laptop. Linux, macOS or WSL commands first; Windows PowerShell equivalents where they differ. You will see every layer's address for yourself and watch encapsulation in a real capture.

  1. Find your L2 and L3 addresses. Run ip addr (Linux), ifconfig (macOS) or ipconfig /all (Windows). Find your active interface. Note its MAC ("link/ether", "ether" or "Physical Address") and its IPv4 address. What it proves: one interface has one address per layer.
  2. Find your default gateway. ip route (look for default via …), netstat -rn on macOS, or route print on Windows. Look for: the router's IP. This is where every non-local packet goes.
  3. See ARP's work. ip neigh or arp -a. Look for: your gateway's IP with a MAC next to it. That MAC is what your laptop writes as the destination on every frame bound for the internet. There will be no entry for any website, because you never need a remote host's MAC.
  4. Watch TTL at work. traceroute -n example.com (Linux/macOS; install with your package manager if missing) or tracert -d example.com (Windows). Look for: hop 1 is your gateway, then your provider's routers, with rising round-trip times. Rows of * * * are routers that do not answer, not failures.
  5. Walk up the layers in one command. curl -v https://example.com -o /dev/null (on Windows use curl.exe -v https://example.com -o NUL). Look for, in order: the name being resolved to an IP ("Trying …"), the TCP connection ("Connected to … port 443"), the TLS handshake lines, then the HTTP request (> GET /) and response status (< HTTP/2 200 or similar).
  6. See refused versus timed out. Run nc -vz 127.0.0.1 5999, a port where nothing listens: it fails immediately with "refused". Then nc -vz -w 5 10.255.255.1 80, an address that usually goes nowhere: it waits and times out. On Windows use Test-NetConnection 127.0.0.1 -Port 5999 and Test-NetConnection 10.255.255.1 -Port 80. What it proves: refused is fast because a host answered; timeout is slow because nothing did.
  7. Capture encapsulation. Install Wireshark (all platforms) and start a capture on your active interface with the display filter tcp.port == 443, then load any website. Click one packet. Look for: the details pane lists "Ethernet II", then "Internet Protocol Version 4", then "Transmission Control Protocol", then "Transport Layer Security", nested exactly like the diagram in the primer. If you see nothing, your browser may be using HTTP/3, which runs over UDP instead of TCP (net8); switch the filter to udp.port == 443 to see it. Expand the Ethernet row and compare the destination MAC with your gateway's MAC from step 3; expand the IP row and find the TTL. On Linux without a GUI, sudo tcpdump -i any -nn -e -c 5 tcp port 443 shows the same (the -e flag prints MAC addresses).

Stretch: capture while running ping 8.8.8.8 and filter on icmp. Notice that there is no TCP or UDP header at all: ICMP rides directly on IP, which is why ping says nothing about whether any port is open.

Walk the layers

A service reports "connection refused" when calling db.internal:5432. Another reports "connection timed out" to the same host. A third gets "could not translate host name". For each, which layer is failing and what would you check?

Answer
  • "Could not translate host name": name resolution (DNS) failed, so no connection was ever attempted. Check dig db.internal from that host, the resolver configuration in /etc/resolv.conf (including search domains, the suffixes the resolver appends to short names), and whether the record exists in the DNS that host actually uses, for example a private zone that is not attached to this VPC.
  • "Connection refused": layer 3 worked and the host answered, replying with a TCP RST because nothing listens on 5432. The database process may be down, listening on another port, or bound only to 127.0.0.1 so it refuses remote connections; less often, a firewall is configured to actively reject. Check ss -ltnp on the server for a listener on 0.0.0.0:5432 or the right interface, and the database's listen-address setting.
  • "Connection timed out": the connection attempt got no answer at all, so packets are being silently dropped: a security group or firewall rule, no route between the subnets, DNS pointing to a dead or old IP, or the host is down. Check the security group and network ACL rules (a network ACL, or access control list, is a stateless firewall applied to a whole subnet), flow logs for REJECT entries, traceroute or mtr towards the host, and tcpdump -nn port 5432 on the server to see whether connection attempts arrive at all.

The refused-versus-timeout distinction is a classic interview probe: refused means something answered; timed out means nothing did. Note also the order: DNS failed first for the third service, so looking at ports would have been wasted effort.

Estimate the overhead

A fleet of sensors each sends one 100-byte reading per second to a collector, one reading per packet, over TCP and IPv4 on Ethernet. What fraction of the bytes on the wire is useful data? What changes if each sensor batches 14 readings per packet?

Answer

Add up each layer. TCP header 20 bytes, IPv4 header 20, Ethernet header 14 and FCS 4: 58 bytes of headers. Ethernet also sends 20 bytes on the wire that are not part of the frame at all: an 8-byte preamble (a fixed bit pattern that lets the receiver's clock lock on) and a 12-byte inter-frame gap (enforced silence between frames).

CasePayloadOn the wireUseful
1 reading per packet100 B100 + 58 + 20 = 178 B56%
14 readings per packet1,400 B1,400 + 58 + 20 = 1,478 B95%

Batching nearly doubles the efficiency, and it also cuts the number of packets 14-fold, which matters more than bytes for routers and kernels, whose cost is mostly per packet. In reality it is worse for the unbatched case: TCP's acknowledgements from the collector add return packets, and TLS adds about 22 more bytes per encrypted record. The general lesson: overhead is fixed per packet, so small messages are expensive, which is why protocols batch, and why the 1,460-byte MSS is the sweet spot.
