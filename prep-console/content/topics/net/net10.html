A single server can only handle so much. When a service outgrows one machine, you run several copies, and suddenly you need something to decide which copy each request goes to. That something also needs to notice when a copy dies and stop sending it traffic, let you deploy new versions without dropping requests, terminate TLS in one place, and protect the servers from abusive or merely slow clients. That something is a load balancer, usually built from a reverse proxy.

Proxies sit on nearly every request you will ever serve: a CDN edge, a cloud load balancer, an ingress controller, a service-mesh sidecar, an API gateway, often several of them in a row. Because every request passes through them, their behaviour becomes your application's behaviour, whether you configured it or not. A proxy's timeout decides when a slow request becomes a 504. Its idle timeout, set against your server's, decides whether you see random 502s. Its buffering decides whether an LLM's streamed tokens appear one by one or all at the end. Its retries decide whether a timeout becomes a duplicate payment. Its health check decides whether a database hiccup takes down one server or all of them.

There is also a proxy facing the other way. A forward proxy sits between your clients and the outside world: the corporate proxy your laptop uses, or the egress proxy through which your services call third-party APIs. It controls and records what leaves your network.

This lesson builds from the idea of a proxy to the practice of load balancing: the two directions of proxying, the difference between layer-4 and layer-7 balancing, the algorithms for choosing a backend and when each wins, health checks and draining, how the real client's address survives the trip, and the timeouts, buffering and retries that account for so many production incidents. It connects directly to the system design interviews in which "put a load balancer in front" is only the start of the answer.

A proxy is a middleman that makes its own connections

A proxy receives a request from one side and makes its own request to the other side, passing the answer back. The two sides each talk only to the proxy. That position lets it inspect, change, route, cache, block or record traffic. What distinguishes the two main kinds is whom the proxy works for.

The analogy: a restaurant host

A load balancer is like the host at a busy restaurant. Guests do not walk to a table themselves; the host greets them at the door (the single public address), checks which waiters are available and not overwhelmed (health and load), and seats each party with one of them (routing). When a waiter goes on break, the host stops seating guests in their section but lets current diners finish (draining). A sophisticated host looks at each party and seats large groups with the experienced waiter (layer-7 routing on request details); a simple one just rotates through sections in order (round robin).

Where the analogy breaks: a restaurant host never makes guests wait while they go into the kitchen themselves, but a layer-7 proxy does exactly that. It opens its own separate connection to the server, so every timeout, buffer and retry it has becomes part of your request's path.

Why every service needs one

Three reasons, each worth saying in an interview. Scale: one address for clients, many servers behind it, and you add servers without clients noticing. Availability: when a server dies, the balancer stops sending it traffic, so the service survives. Change: you can deploy new versions, drain old ones and shift traffic gradually, all behind a stable address. On top of those, the reverse proxy doing the balancing is the natural place for TLS termination (net9), request routing, rate limiting, compression, caching and a web application firewall (net14), which is why it is almost always there even for a single server.

A request's path, concretely

A request to https://api.example.com/orders in a typical cloud setup: DNS returns the load balancer's address; the client's TCP and TLS handshakes complete with the balancer, not the application; the balancer reads Host and path, picks one of the healthy instances of the orders service, and forwards the request over a connection it already has open to that instance, adding X-Forwarded-For and X-Forwarded-Proto; the response comes back the same way. The application never sees the client's TCP connection at all.

The key questions any load balancer answers

  • At which layer does it decide? Per TCP connection using addresses and ports (L4), or per HTTP request using host, path and headers (L7).
  • How does it choose? Round robin, least busy, random pairs, or a hash that keeps related requests together.
  • How does it know a server is healthy? Probes on an interval, and watching real failures.
  • How does it change servers safely? Draining before removal, gradual ramp-up after adding.
  • What does it change about the request? Source address, headers, timeouts, buffering, retries.

The body answers them in that order.

1. L4 and L7: what happens to the connection

An L4 load balancer works with TCP or UDP connections and never parses the application protocol. When a new connection arrives, it picks a backend and from then on forwards that connection's packets to it. There are three common ways to do the forwarding. In NAT mode, it rewrites the destination address to the backend's (like the DNAT in net3) and replies return through it. In a full TCP proxy mode it terminates the client's TCP connection and opens a second one to the backend, relaying bytes between them. In direct server return (DSR), it forwards the incoming packets but the backend replies straight to the client, which suits download-heavy traffic because the heavy direction bypasses the balancer. L4 is fast, cheap, works for any TCP or UDP protocol (databases, MQTT, gRPC, raw TLS), and can pass TLS through untouched. Its limit: it decides once per connection and knows nothing about requests.

An L7 load balancer is a reverse proxy that speaks HTTP. It terminates the client's connection (and usually TLS), parses each request, chooses a backend per request, and sends it over its own, separate connection from a pool it keeps to each backend:

Because the L7 proxy owns both connections, it can route by host, path or header (/api/ to one service, /static/ to another), retry a failed request on a different backend, reuse warm backend connections so backends never pay handshakes, and absorb slow clients: it reads a slow upload fully before forwarding it, so the application server's worker is busy for milliseconds rather than minutes. The costs are CPU for parsing and TLS, and the fact that it must terminate TLS to see anything.

Real deployments stack them: an anycast or DNS layer chooses a region (net12), an L4 tier spreads connections across a fleet of L7 proxies, and the L7 proxies route requests to services, which may themselves have mesh sidecars doing L7 balancing between services.

2. Choosing a backend: the algorithms

  • Round robin: each new connection or request goes to the next backend in turn. Simple and fair when requests are similar and servers identical.
  • Weighted round robin: backends get shares proportional to weights, for mixed server sizes or for sending 5% of traffic to a canary.
  • Least connections: pick the backend with the fewest open connections. Better when connections last different amounts of time.
  • Least outstanding requests: pick the backend with the fewest requests currently in progress. The right default for HTTP when request durations vary a lot.
  • Power of two choices (P2C): pick two backends at random, send to the less loaded. Explained in the deep section; the default in Envoy's least-request balancer.
  • Hashing: hash some key, such as the client IP, a user ID, a cookie or a URL, to choose the backend, so the same key always lands on the same backend. Used for caches and affinity; consistent hashing (below) keeps the mapping stable as backends change.

A worked example shows why the choice matters. Three backends, each able to process 4 requests at once. Requests arrive in a repeating pattern: one 10-second report, then two 50 ms page loads. With round robin, every third request goes to backend A, and every one of those happens to be a report, so A fills up with reports and queues, while B and C sit nearly idle serving quick pages. Least outstanding requests notices that A has 4 requests in progress and B has 0, and sends new work to B and C until A frees up. The difference in tail latency can be enormous. The same logic is why LLM inference gateways balance on queue depth: one request can take 100 ms and the next 60 seconds.

3. Consistent hashing

Suppose each backend caches data for the keys it serves. With plain hashing, backend = hash(key) mod N. Add a fourth backend, and N changes from 3 to 4: about three-quarters of all keys now map to a different backend, and every cache is suddenly cold. Consistent hashing fixes this:

Each backend is placed at many points on the ring (virtual nodes, often 100 or more per backend) so that each owns many small arcs rather than one big one, which evens out the load. Production systems add a load bound: if the chosen backend is already above, say, 125% of the average load, the key spills to the next one clockwise ("consistent hashing with bounded loads"), so a hot key cannot melt one server. Consistent hashing is used by L4 fleets to keep connections stable (Maglev), by caches and CDNs, and increasingly by LLM gateways to route requests sharing a prompt prefix to the server that already holds it.

Sticky sessions are a cruder form of affinity: the balancer sets a cookie naming the backend, or hashes the client IP, so a user keeps hitting the same server. They are sometimes necessary for legacy apps that keep sessions in memory, but they make load uneven and lose state whenever that server restarts. Prefer shared session stores or stateless tokens, and treat affinity as an optimisation.

4. Health checks

An active health check is a probe the balancer sends to each backend on an interval, such as GET /healthz expecting 200. Thresholds prevent flapping: a backend is marked unhealthy after several consecutive failures and healthy again after several successes. Put numbers on it: with AWS Application Load Balancer defaults (30-second interval, 5-second timeout, unhealthy after 2 failures, healthy after 5 successes), a crashed backend may keep receiving traffic for up to about a minute, and a recovered one waits over two minutes to return. Shorter intervals detect faster but multiply probe traffic across big fleets.

A passive health check, or outlier detection, watches real traffic instead: if a backend returns five 5xx errors in a row, or its error rate stands out from its peers, eject it for a while. Passive checks react in seconds and catch problems probes miss; the two are combined.

What the health endpoint checks is a design decision. Kubernetes distinguishes liveness (is the process alive, or should it be restarted?) from readiness (should it receive traffic right now?). A readiness check should test what this instance controls: it has finished starting, loaded its model or cache, and is not overloaded. It should not fail just because a shared dependency like the database is slow, because then every instance fails at once. Balancers anticipate that failure: when all targets are unhealthy, an AWS ALB fails open and sends traffic to all of them, and Envoy ignores health status once fewer than 50% of hosts are healthy (its panic threshold). Both bet that a total failure is more likely a bad health check than a truly dead fleet.

5. Draining and deploys

Removing a backend abruptly fails every request in progress on it. Connection draining (AWS calls it the deregistration delay, 300 seconds by default) stops new requests to the backend while letting in-flight requests finish, up to a limit. A clean shutdown sequence for an instance is: fail readiness or deregister; wait until the balancer has stopped sending new requests (at least one health-check interval, plus any propagation delay in service discovery); let in-flight requests finish; close idle keep-alive connections, or for HTTP/2 send GOAWAY; then exit. Kubernetes handles part of this with a pre-stop hook and a termination grace period, and a common bug is exiting immediately on SIGTERM before endpoints have been updated everywhere.

New instances need the opposite care. Many runtimes are slow when cold (JIT compilation, empty caches, lazy model loading), so a new instance that receives its full share immediately gives terrible latency. Balancers offer slow start: ramp a new backend's share up over a minute or two.

6. Who is the client? Addresses and schemes behind proxies

An L7 proxy opens its own connection to the backend, so the backend sees the proxy's IP address as the source. The original client's address is passed in a header. The traditional one is X-Forwarded-For: each proxy appends the address it received the request from, giving a list like X-Forwarded-For: 203.0.113.7, 198.51.100.20. The standard Forwarded header carries the same information in a structured form. X-Forwarded-Proto: https tells the backend the original request was HTTPS, so it builds correct redirect URLs and marks cookies Secure; without it, apps behind TLS-terminating proxies generate http:// links and redirect loops.

The security rule: a client can send its own X-Forwarded-For header with any value, and proxies append to it rather than replace it. So the leftmost entries are untrustworthy. The real client is the address added by your outermost trusted proxy: count trusted proxies from the right. Frameworks have a setting for this (Express's trust proxy, Django and Flask proxy-fix middleware), and getting it wrong breaks rate limiting, geolocation and audit logs, or lets attackers spoof their IP.

An L4 balancer cannot add headers, because it does not parse HTTP. It either preserves the client's source address (NAT and DSR modes can) or prepends a PROXY protocol header, a single line such as PROXY TCP4 203.0.113.7 10.0.1.5 51514 443, at the start of the TCP stream, which the backend must be configured to expect.

7. Timeouts and keep-alives across hops

Every hop in a chain like client → CDN → load balancer → proxy → application → database has its own timeouts: how long to wait to connect, how long to wait for a response, and how long to keep an idle connection open. Two rules keep them consistent.

Request timeouts should shrink as you go deeper. If the load balancer gives up after 30 seconds but the application waits 60 seconds for the database, the balancer returns 504 while the application keeps working for another 30 seconds on a response nobody will receive, and if the client retries, the work doubles. Each layer's deadline should be shorter than its caller's, ideally with the remaining deadline propagated downstream.

Idle timeouts should grow as you go deeper. A backend must keep idle keep-alive connections open longer than the proxy in front of it, so the proxy always closes them first. If the backend closes first, the proxy can send a request on a connection at the exact moment it is being closed, receive a reset, and return a 502 that never appears in the application's logs (the race from net4). AWS documents exactly this for its load balancers; the fix is typically a backend idle timeout a few seconds longer than the balancer's (60 seconds by default for an Application Load Balancer; 350 seconds for a Network Load Balancer's TCP flows).

Long-running work, such as report exports or batch inference, should not hold an HTTP request open past these limits at all: accept the job, return 202 Accepted with a job ID, and let the client poll or receive a callback.

8. Buffering, limits and streaming

Reverse proxies usually buffer: they read the whole upstream response (up to some size) as fast as the backend can send it, freeing the backend's worker, then feed it to the client at the client's pace. They also read request bodies before forwarding. That protects application servers from slow clients, including deliberate slowloris attacks that trickle bytes to hold connections open. But buffering breaks streaming. A server-sent events endpoint or an LLM API streaming tokens will appear frozen, then dump everything at the end, because the proxy is holding the stream. The fix is to disable buffering for those routes (in nginx, proxy_buffering off or the X-Accel-Buffering: no response header), avoid response compression that waits for large blocks, and raise idle timeouts or send periodic heartbeat comments, since a model may think for tens of seconds before the first token.

Proxies also enforce limits that surface as mysterious errors: nginx rejects request bodies over 1 MB by default with a 413 error (client_max_body_size), and header size limits produce 400 or 431 errors when cookies grow too big.

9. Forward proxies in production

Forward proxies are not only a corporate IT thing. Many production platforms route all outbound traffic from services through an egress proxy. It enforces an allow-list of external destinations, which limits where stolen credentials or a compromised service can send data. It gives partners a small set of stable source IPs to allow-list. It centralises outbound credentials and TLS settings for third-party APIs. And it defends against SSRF (server-side request forgery), where an attacker tricks a service into fetching an internal URL such as the cloud metadata endpoint 169.254.169.254. For HTTPS destinations, clients use the CONNECT method to ask the proxy for a tunnel; TLS then runs end to end through it, so the proxy sees the destination host and port but not the content, unless it performs TLS inspection (net9).

Why power of two choices works

With many load balancers, each tracking only the requests it sent, "least connections" has a herding problem: every balancer sees the same backend as currently least loaded and sends its next request there, so that backend is flooded, then all switch to the next. Pure random choice avoids herding but occasionally piles requests onto an unlucky backend; with n backends the busiest one's excess load grows roughly like log n / log log n. Mitzenmacher's analysis showed that sampling just two random backends and picking the less loaded drops that to about log log n, an exponential improvement, while needing only local, slightly stale information. It is cheap, robust to staleness and works with any load signal (outstanding requests, latency, queue depth), which is why Envoy, Linkerd and many L4 fleets use it.

Keeping the load balancer itself available

A load balancer is itself a single point of failure unless it is a fleet. Large L4 fleets announce the same virtual IP from many machines using BGP; routers spread packets across them with ECMP (net3), and a machine that fails simply stops announcing. The catch: after the fleet changes, packets of an existing connection may hash to a different balancer machine, which must forward them to the same backend as before. Google's Maglev solves this with a consistent hashing scheme designed for minimal disruption plus a local connection-tracking table; GitHub's GLB Director uses a stateless two-tier design so any director can forward any packet correctly. For smaller setups, pairs of balancers share a floating IP with a protocol like VRRP, or you use a managed cloud balancer that hides all of this.

Retries, budgets and hedging at the proxy

Proxies are an attractive place to retry because they see failures first and can pick a different backend. They are also where retry storms start. When backends are overloaded, each failed request retried twice triples the offered load, exactly when capacity is lowest; with retries at the client, the gateway and the mesh, attempts multiply. Good proxy retry policy: retry only idempotent requests or ones with idempotency keys (net7); retry only on failures that mean "never processed" (connection refused, reset before response, 503 from a draining instance), not on timeouts of heavy work; use one or two attempts with jittered backoff; and enforce a retry budget such as "retries may add at most 20% to traffic", after which failures pass through. A related technique, hedging, sends a second copy of a slow idempotent request to another backend after, say, the p95 latency, and takes whichever answers first, trading a little extra load for much better tail latency.

Zone awareness and the cost of crossing zones

Cloud regions have several availability zones, and traffic between zones adds latency (typically under 2 ms) and usually costs money per gigabyte. A balancer that spreads every request evenly across all zones sends two-thirds of traffic cross-zone in a three-zone setup. Zone-aware routing prefers backends in the caller's zone while enough healthy capacity exists there, spilling over only when needed. The trade-off is resilience and balance: if one zone has fewer healthy backends, strict locality overloads them. Most meshes implement a middle ground that keeps traffic local unless the local zone falls below a capacity threshold.

Load balancing without a balancer: client-side and DNS

A central balancer is not the only design. In client-side load balancing, each client gets the list of backend addresses from service discovery (DNS returning all instances, or a registry) and chooses itself, with its own health tracking. gRPC supports this natively, and it removes a hop and a bottleneck, at the cost of logic in every client and slower reaction to changes. At the other extreme, DNS-based balancing (net6) spreads clients across regions or data centres with coarse, cached decisions. Large systems use all three: DNS or anycast to pick a region, a central L4 and L7 tier at the edge, and client-side or mesh balancing between internal services.

Dynamic configuration and its risks

Modern proxies are configured by control planes rather than static files: Envoy receives routes, clusters and endpoints through its xDS APIs, and Kubernetes ingress controllers regenerate configuration as services change. That enables instant endpoint updates and gradual traffic shifts, but it also means a bad configuration reaches every proxy within seconds. Proxy and CDN configuration pushes are a leading cause of large outages (the Fastly incident in net2 was triggered by a customer configuration change). The defences are the same as for code: validation before push, staged rollout to a fraction of proxies, automatic rollback on error-rate increases, and the ability to fall back to last known good configuration.

Other characteristic failures

  • Health check cascades: a readiness check that queries the database fails on every instance during a database slowdown; the balancer either fails open (sending traffic to instances that cannot serve it) or returns 503 for everything, turning a partial degradation into a total outage.
  • Uneven load: long-lived HTTP/2, gRPC or WebSocket connections through L4 balancing pin traffic to a few backends (net8); round robin with heterogeneous requests overloads unlucky servers.
  • Cold-start storms: after a deploy or scale-out, new instances receive full traffic before warming up and their latency spikes; enable slow start.
  • Retry amplification: an overloaded service gets several times its normal load because proxies and clients retry timeouts; look for request counts at backends far exceeding client request counts.
  • Frozen streams: server-sent events or LLM token streams arrive all at once because a proxy buffers responses.
  • Spoofed client IPs: rate limiting keyed on the leftmost X-Forwarded-For entry is trivially bypassed.

War story pattern: the health check that took everything down

A team adds a database query to its service's readiness endpoint "to be safe". Months later the database has a slow patch lasting two minutes. Every instance's health check times out, the load balancer marks the whole fleet unhealthy, and because this balancer is configured not to fail open, it returns 503 for all traffic, including the large share of requests that did not need the database at all, such as cached pages and static content. The database recovers in two minutes; the service takes several more, because instances must pass five consecutive checks to return. The fix is a readiness check that only covers the instance itself, plus alerts on dependency health and graceful degradation in the code.

Knobs

Algorithm per route; health check path, interval, timeout and thresholds; outlier detection settings; deregistration delay and slow start; connect, request and idle timeouts per hop; retry policy and budget; maximum connections and pending requests per backend (a form of circuit breaking); buffering and body size limits per route; trusted proxy settings in applications; and zone-aware routing thresholds.

        self.send_response(200)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers(); self.wfile.write(body)
    def log_message(self, *a): pass
http.server.ThreadingHTTPServer(("0.0.0.0", port), H).serve_forever()

Add proxy_next_upstream off; to the location, restart nginx, and repeat: one backend, one 504 after two seconds.

Diagnose it

A Node.js API behind an AWS Application Load Balancer (idle timeout 60 s) returns occasional 502s, about 0.1% of requests, more during quiet periods, never visible in the application's own logs. Node's server.keepAliveTimeout is the default 5 s. Also, rate limiting by client IP seems to limit everyone at once. Explain both.

Answer
  • 502s: the ALB reuses idle backend connections for up to 60 s, but Node closes idle keep-alive connections after 5 s. When the ALB sends a request on a connection at the moment Node closes it, the request hits a closed socket and gets a reset, the ALB returns 502, and the application never saw the request, hence nothing in its logs. It happens more in quiet periods because connections sit idle long enough to hit 5 s.
  • Fix: make the backend's idle timeout longer than the balancer's: server.keepAliveTimeout = 65000 and server.headersTimeout = 66000 (Node requires headersTimeout to exceed keepAliveTimeout).
  • Rate limiting: the app sees the ALB's IP as the source for every request, so all clients share one bucket. Use the client IP from X-Forwarded-For, taking the entry added by the ALB (the rightmost address not belonging to your own infrastructure), not the leftmost, which a client can forge. In Express, configure trust proxy with the correct number of hops.
Design it

You are putting a gateway in front of 20 GPU servers that run an LLM with streaming responses. Prompts range from 100 to 100,000 tokens and outputs from 10 to 4,000 tokens. Many requests from the same conversation share a long prefix. What load balancing, health checking and proxy settings would you choose?

Answer
  • Layer and protocol: an L7 gateway terminating TLS and HTTP/2, doing authentication and per-tenant rate limits.
  • Algorithm: not round robin, since request cost varies by three orders of magnitude. Use least outstanding requests, or better, a queue-aware policy using each server's reported queue length and KV-cache memory, with power of two choices to avoid herding across gateway replicas.
  • Affinity: route requests from the same conversation (or with the same prompt prefix hash) with consistent hashing, so the server that already cached the prefix can reuse it, with a load bound that spills to another server when the preferred one is saturated.
  • Streaming: disable response buffering and compression-that-buffers on these routes; long idle timeouts plus heartbeat comments, since time to first token can be tens of seconds for long prompts.
  • Retries: retry only if the request failed before any bytes were streamed, on a different server, with a strict budget; never retry mid-stream.
  • Health: readiness means "model loaded and queue below a limit"; passive outlier detection ejects servers returning errors; drain on deploy by stopping new requests and letting streams finish, with a generous deregistration delay.
  • Scaling signal: queue length or pending tokens, not CPU.
