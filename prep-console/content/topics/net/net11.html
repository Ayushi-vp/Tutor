HTTP has a built-in limitation: the client always speaks first. A browser asks, the server answers, and then the server has no way to say anything until it is asked again. That is fine for loading pages, and useless for a chat message that should appear the instant a friend sends it, a live sports score, a collaborator's cursor moving in a shared document, a stock price, a delivery driver's position on a map, or an AI model's answer appearing word by word as it is generated.

Engineers have invented a whole family of techniques to let the server push. Some are clever reuses of ordinary HTTP: asking over and over (polling), or asking and having the server deliberately wait before answering (long polling), or answering with a response that never ends (Server-Sent Events). Some switch the connection to a different protocol entirely (WebSockets). Some are built for service-to-service traffic (gRPC streaming), and some for audio and video between people, where every millisecond counts and a late packet is worthless (WebRTC).

Picking among them is a common interview question, and the right answer depends on direction (does only the server push, or do both sides talk?), latency needs, message rate, the clients (browsers, mobile apps, other services), and the infrastructure in between. The bigger challenge comes after picking. A normal web request lasts milliseconds and leaves no trace on the server; a real-time connection lasts hours, pins a user to one particular server, must survive deploys and network changes, and must reach users who are connected to other servers. Discord, Slack and WhatsApp each hold millions of such connections, and their engineering blogs are largely about the consequences.

This lesson explains each technique on the wire, compares them, and then covers what it takes to run persistent connections at scale: fan-out across servers, delivery guarantees and resumption, heartbeats, backpressure, deploys and reconnection storms, and security at the handshake.

The problem in one sentence

The server has news for a client, but in HTTP only the client can start a conversation. Every technique is a different answer to "how does the news get there, and how fast?"

The analogy: waiting for a parcel

  • Short polling is phoning the depot every ten minutes to ask "is my parcel here?" Mostly the answer is no, and when it arrives you only find out at your next call.
  • Long polling is phoning and asking them to stay on the line until it arrives, then calling back immediately after they tell you.
  • Server-Sent Events is subscribing to a text-message alert service: one sign-up, and they message you whenever something happens. You can't reply on that channel.
  • WebSockets is keeping an open phone line to the depot all day. Either side can speak at any time.
  • WebRTC is a walkie-talkie directly between you and a friend, set up with the depot's help, for when you need to hear each other instantly.

Where the analogy breaks: an open "phone line" costs the server very little while idle, only memory, which is why one machine can hold hundreds of thousands of them; the real costs come when messages must be copied to many listeners.

The techniques on a timeline

A concrete example: an AI chat app

A typical AI assistant web app uses several of these at once. The user's message goes up as an ordinary POST. The model's answer streams back as Server-Sent Events, token by token, on the response to that request. If the app shows other users' activity, such as a shared workspace where colleagues' edits and presence appear live, that runs over a WebSocket. A voice mode sends microphone audio and receives speech with WebRTC, or with a WebSocket carrying audio chunks when latency needs are looser. And the backend's calls to internal services, such as retrieval or tool execution, may use gRPC streams. Each choice follows from direction, latency and who the client is.

What changes when connections stay open

With ordinary requests, a server can be restarted, scaled or replaced at any time, because no client is attached to it for more than a moment. A persistent connection attaches a client to one server for minutes or hours. That single change is the source of most of the engineering in the second half of this lesson: getting a message to the right server, surviving disconnections without losing messages, keeping idle connections alive, and deploying without a storm of reconnects.

A first rule for choosing

Ask two questions. Does data need to flow from client to server frequently and fast, or mostly from server to client? And how quickly must updates arrive? Server-to-client only: SSE, or polling if updates are infrequent. Both directions with low latency: WebSockets. Service-to-service streams: gRPC. Live audio and video between people: WebRTC. The body explains why.

1. Short polling

The client requests GET /notifications?since=1042 every N seconds. Each request is an ordinary, stateless HTTP request: any server can answer it, responses can be cached, and it works through every proxy. The costs are latency (an event waits up to N seconds) and waste. Put numbers on it: one million clients polling every 5 seconds is 200,000 requests per second, each with a few hundred bytes of headers and a database or cache lookup, and if events are rare, almost all return nothing. Shorter intervals cut latency and multiply cost. For dashboards refreshed every 30 seconds, or job status pages, polling is often exactly right; use ETag and 304 responses (net7) to make empty polls cheap.

2. Long polling

The client sends a request, and if there is nothing new the server does not answer immediately; it holds the request open until an event arrives or a timeout (commonly 20 to 60 seconds, kept below proxy idle timeouts) passes. Then it responds, and the client immediately sends the next request. Delivery is near-instant, and it needs nothing but plain HTTP, which is why early web chat and many older APIs used it. Its costs: one full request-response per batch of messages, careful handling of events that happen between the response and the next request (the client must send its last seen id so nothing is missed), and many open requests on the server, which ties up a thread each on thread-per-request servers.

3. Server-Sent Events

With Server-Sent Events (SSE), the client makes one request and the server sends back a response with Content-Type: text/event-stream that never ends. It writes events into it as they happen, in a simple text format:

id: 1043
event: token
data: {"text": "Hello"}

id: 1044
event: token
data: {"text": " world"}

: heartbeat comment, ignored by the client

retry: 5000

Each event is a few field: value lines ended by a blank line. data is the payload (multiple data lines are joined with newlines), event an optional type, id an identifier, and retry tells the client how many milliseconds to wait before reconnecting. Lines starting with a colon are comments, used as heartbeats.

In browsers, the EventSource API does the work: new EventSource("/events") opens the stream, parses events, and, crucially, reconnects automatically if the connection drops, sending a Last-Event-ID header with the last id it received so the server can resume from there. Because SSE is ordinary HTTP, it works through proxies, uses normal cookies and authentication, and over HTTP/2 many SSE streams share one connection. Its limits: server-to-client only (clients send data with separate requests), text only, and under HTTP/1.1 browsers allow only about six connections per domain across all tabs, so several open SSE streams can starve other requests.

SSE is the standard way to stream LLM output. Provider APIs such as OpenAI's and Anthropic's stream generated tokens as server-sent events, which is why proxy buffering (net10) matters so much for AI applications.

4. WebSockets: the handshake

A WebSocket (RFC 6455) turns an HTTP connection into a two-way channel for messages. It begins as an HTTP/1.1 request asking to switch protocols:

After the 101 Switching Protocols response, HTTP is over for that connection. Data now travels in frames: a small header with a final-fragment flag, an opcode (text, binary, close, ping or pong), a length, and the payload. Frames from browser to server are masked with a random 4-byte key, an obscure but important defence against confused proxies caching attacker-controlled bytes. Unlike TCP's byte stream, WebSockets preserve message boundaries: one send() is one message. Ping and pong frames serve as heartbeats, and a close frame with a status code (1000 for normal closure, 1001 when a server is going away) ends the connection cleanly.

What WebSockets do not give you is just as important: no automatic reconnection, no message acknowledgements or replay, no backpressure signal to the application, no built-in authentication beyond what happened in the handshake, and no request-response correlation. Applications build these on top, often with a small protocol of their own (message types, ids, acks), or use a library or managed service that provides them. WebSockets can also run over HTTP/2 and HTTP/3 (RFC 8441 and RFC 9220) using an extended CONNECT method, though HTTP/1.1 upgrades remain the most common.

5. gRPC streaming

Between services, the usual tool is gRPC (net8), which besides ordinary request-response calls supports three streaming shapes, defined in the service's Protocol Buffers file: server streaming (one request, a stream of responses, such as a feed of updates), client streaming (a stream of requests, one response, such as uploading a series of events), and bidirectional streaming, where both sides send streams independently. Each call is an HTTP/2 stream, so it gets HTTP/2's flow control, deadlines, cancellation and typed messages for free. Browsers cannot speak native gRPC because they do not expose HTTP/2 framing and trailers to JavaScript, so front ends use gRPC-Web through a proxy, or SSE and WebSockets.

6. WebRTC: real-time media between peers

For live audio and video, even a WebSocket through a server adds latency and server bandwidth, and TCP's retransmissions make late packets arrive when they are already useless (net5). WebRTC sends media, and optionally data, directly between peers over UDP, encrypted, with codecs that adapt to available bandwidth and hide small losses.

Step by step: the peers exchange session descriptions (codecs, encryption fingerprints) through a signalling channel you provide, typically a WebSocket to your server. Each gathers candidates, the addresses it might be reachable at: its local address, its public address and port as seen by a STUN server (net3's NAT mapping, discovered from outside), and a relayed address on a TURN server. ICE then tests candidate pairs, direct ones first. If both NATs allow it, packets sent simultaneously from each side "punch holes" and a direct path works; otherwise traffic goes through TURN. Media is encrypted with DTLS-SRTP. For group calls, a full mesh (everyone sends to everyone) collapses beyond a handful of people, so calls go through an SFU (selective forwarding unit), a server that receives each participant's streams once and forwards them to the others, choosing quality per receiver.

WebTransport is the newest option: a browser API over HTTP/3 (net5, net8) that gives a web app multiple independent streams and unreliable datagrams on one QUIC connection, suitable for games and media that want some data reliable and some disposable, with no head-of-line blocking between streams.

8. Scaling persistent connections: fan-out

With request-response, any server can answer any request. With persistent connections, each user is attached to one specific server, and a message for them must reach that server. In a chat room whose members are connected to 20 different gateway servers, one message must be delivered by 20 servers to their local members. The standard design:

Each gateway subscribes to a pub/sub channel per room its connected users belong to (Redis pub/sub, NATS, or a Kafka-based bus for larger systems), and unsubscribes when the last one leaves. For one-to-one messages, a registry mapping each user to their current gateway lets you route directly rather than broadcast. An alternative is to route all members of a room to the same gateway with consistent hashing (net10), which avoids cross-server traffic but makes very large rooms and rebalancing harder.

9. Backpressure and slow consumers

A push server can produce messages faster than some clients can receive them: a user on a weak mobile signal, a browser tab in the background, or a client whose event loop is busy. The kernel send buffer fills, then the server's own per-connection queue starts growing. With thousands of such clients, memory runs out. Every push system therefore needs a policy per connection: a maximum queue size, and what to do when it is reached. For state that supersedes itself, such as prices, positions or presence, conflate: keep only the newest update per item. For low-value messages such as typing indicators, drop them. For important messages, disconnect the slow client and let it resume from its last sequence number once it can keep up. What you must never do is let the queue grow without bound.

10. Reliability: sequence numbers, heartbeats and reconnects

Delivery. Connections drop constantly: phones switch networks, laptops sleep, servers deploy. Anything pushed while a client is disconnected, or in flight when it drops, is lost unless you design for it. The robust pattern: assign each message a per-conversation sequence number, persist it before pushing, have clients track the last number they processed, and on reconnect ask for everything after it. Clients deduplicate by sequence number, so at-least-once delivery becomes effectively exactly-once processing. SSE has this built in through id and Last-Event-ID; with WebSockets you implement it.

Heartbeats. NATs, load balancers and proxies drop idle connections silently after 30 to 350 seconds (net3, net10), and TCP alone takes hours to notice a dead peer (net4). Send a ping or a comment line every 20 to 30 seconds, and treat two missed heartbeats as a dead connection.

Reconnection. When a gateway restarts, all of its clients reconnect. If they all do so immediately, the new servers receive tens of thousands of TLS handshakes and authentication calls in the same second, a thundering herd that can take them down and cause another round of reconnects. Clients must reconnect with exponential backoff and jitter: wait a random time up to a growing maximum, for example up to 1 s, then up to 2 s, 4 s, capped at 30 s or so.

Capacity of a connection server

An idle WebSocket or SSE connection on an event-driven server (Node.js, Go, Netty, Erlang/Elixir, Python asyncio) costs a file descriptor, kernel socket buffers and some application memory, commonly a few kilobytes to a few tens of kilobytes including TLS state, and no thread or CPU while idle. So one machine can hold hundreds of thousands of connections, and well-tuned systems report millions. The limits you hit first are usually file-descriptor limits (raise ulimit -n and fs.file-max), memory for per-connection buffers under load, ephemeral ports on load balancers or proxies connecting onwards (net4), and CPU during reconnection storms, when TLS handshakes dominate. Thread-per-connection servers, by contrast, run out of memory and scheduler capacity at a few thousand connections, which is why real-time servers are almost always event-driven (net13).

Load balancing long-lived connections

Load balancers must allow the HTTP upgrade (most L7 balancers do), keep idle timeouts above the heartbeat interval, and balance on something better than round robin, since connections accumulate: least-connections is the usual choice. Balance only happens at connect time, so imbalance builds up. After a scale-out, new servers receive only new connections; after a rolling deploy, clients from restarted servers pile onto whichever servers were up. Operators cap connections per server so the balancer skips full ones, and periodically shed a small fraction of connections from overloaded servers, with a "please reconnect" message, so clients spread out again.

Graceful deploys for stateful connections

A connection server cannot be drained by waiting for requests to finish, because its connections never finish. The standard procedure: stop accepting new connections (fail readiness, net10); then, over several minutes, send clients a reconnect instruction in small, jittered batches (a close frame with code 1001 "going away", an SSE event, or HTTP/2 GOAWAY); clients reconnect to other servers and resume by sequence number; finally exit. Spreading the close over minutes turns what would be a spike of reconnects into a gentle migration. Some systems go further and hand connection state to a new process on the same machine to avoid disconnecting at all, but most accept reconnection and make it cheap.

Presence and delivery semantics

"Who is online" sounds simple and is inherently approximate: a user whose phone lost signal still looks connected until heartbeats time out, and a user connected on three devices must count once. Presence is usually tracked with expiring entries refreshed by heartbeats, and published as eventually consistent updates, with rate limiting because in a large group a single user's flapping connection can generate a storm of presence events. Message delivery should be designed as at-least-once with idempotent client handling, and important messages acknowledged by the client, while typing indicators and cursor positions are best-effort and can be dropped or conflated.

Mobile realities

Mobile operating systems suspend background apps and close their sockets to save battery, so a phone cannot rely on holding a WebSocket open. Real-time apps combine an open connection while the app is in the foreground with platform push notifications (Apple Push Notification service, Firebase Cloud Messaging) when it is not; the notification wakes the app or informs the user, and the app then syncs from the last sequence number. Frequent network changes on mobile also make connection migration valuable, one reason HTTP/3 and QUIC-based transports appeal for mobile real-time features.

Why SSE is having a revival

For years WebSockets were the default for anything real-time, and SSE was a footnote. Two things changed. HTTP/2 removed SSE's biggest practical limit, the six-connections-per-domain cap, because many streams share one connection. And LLM APIs made one-directional streaming the most common real-time pattern in new applications, where SSE's plain-HTTP nature means it works with existing API gateways, authentication, logging and CDNs without special handling. The lesson for design interviews: pick the simplest mechanism that matches the data flow, not the most powerful one.

Security at the handshake

Browsers attach cookies to WebSocket handshakes, including cross-site ones, but a WebSocket is not subject to CORS (net7). So a malicious page can open a WebSocket to your server as the logged-in user, cross-site WebSocket hijacking, unless the server checks the Origin header against an allow-list. Browsers also cannot add custom headers such as Authorization to the WebSocket handshake, so token-based apps pass a short-lived token in the URL query or authenticate with the first message, taking care that URLs with tokens are not logged. Authorisation must be checked per subscription ("may this user join room 7?"), not just at connect, and long-lived connections need a way to handle token expiry. Message rate limits per connection prevent one client from flooding a room.

Characteristic failures

  • Reconnect storms: a deploy or network blip disconnects hundreds of thousands of clients that all reconnect at once; TLS handshake CPU and auth-service load spike, new servers fail health checks, and the cycle repeats. Fix with jittered exponential backoff in clients, gradual draining, capacity headroom, and fast token validation (such as signed tokens verified locally).
  • Silent disconnections: users stop receiving messages without errors because a NAT or proxy dropped an idle connection and neither side noticed. Fix with heartbeats shorter than the smallest idle timeout on the path.
  • Lost messages: messages sent during a reconnect gap never arrive, because the design pushed directly without persistence or sequence numbers.
  • Buffered streams: SSE or LLM token streams arrive all at once because of proxy buffering or compression; fix per route (net10).
  • Memory blow-ups from slow consumers: a few clients on poor networks accumulate megabytes of unsent messages each; cap buffers, conflate, or disconnect.
  • Uneven load: some gateway servers at 90% while others idle after deploys or scale-outs; rebalance by shedding connections.
  • Pub/sub bottlenecks: a single Redis instance handling every room's messages saturates; shard channels across instances or move to a partitioned bus.

What real systems report

Discord's engineering team has described scaling Elixir-based gateway and session services to millions of concurrent users, including the work needed to make fan-out to very large guilds efficient; Slack has described its channel servers and gateway servers, which route messages to the right edge servers holding each user's connection. Both designs follow the pattern in this lesson: persistent connections at a gateway tier, routing by channel or user through a backbone, and clients that resume from where they left off.

A debugging order

When users report missing or late real-time updates: first check whether the message was persisted and published (store and pub/sub metrics); then whether the right gateway received it (subscription state, registry lookups); then whether the connection was actually open at that moment (connection logs, close codes, heartbeat failures); and finally whether the client processed it (client logs, last acknowledged sequence number). Stamping each message with an id and a creation timestamp that travels all the way to the client makes this traceable. Most lost-message bugs turn out to be a disconnect that went unnoticed because heartbeats were missing, or a push that bypassed the persisted log.

Observability

Track connected clients per server and in total, connection open and close rates with close codes (a spike in 1006, abnormal closure without a close frame, means network-level drops), reconnects per minute, message publish and delivery rates, end-to-end delivery latency (stamp messages at creation and measure at the client), per-connection send-buffer sizes, heartbeat failures, and pub/sub lag. Browser DevTools shows WebSocket frames in the Network tab (select the connection, then Messages), and EventStream for SSE.

Knobs

Heartbeat interval; load balancer and proxy idle timeouts; maximum connections per server; per-connection send buffer and message rate limits; reconnect backoff parameters and jitter in clients; drain duration and batch size on deploy; pub/sub partitioning; SSE retry value; and buffering settings on every proxy in the path.

  1. An SSE server. Save as sse.py and run python sse.py: 
    import http.server, time
PAGE = b"""<script>
const es = new EventSource('/events');
es.addEventListener('token', e => document.body.append(e.data + ' '));
es.onerror = () => document.body.append(' [reconnecting] ');
</script>"""
class H(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path != "/events":
            self.send_response(200); self.send_header("Content-Type", "text/html")
            self.end_headers(); self.wfile.write(PAGE); return
        start = int(self.headers.get("Last-Event-ID", 0)) + 1
        print("stream starting at", start, flush=True)
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.send_header("Cache-Control", "no-cache")
        self.end_headers()
        for i in range(start, start + 5):
            self.wfile.write(f"id: {i}\nevent: token\ndata: word{i}\n\n".encode())
            self.wfile.flush(); time.sleep(1)
        self.wfile.write(b"retry: 2000\n\n")
http.server.ThreadingHTTPServer(("127.0.0.1", 8000), H).serve_forever()

Look for: words continuing from word6, word11 and so on, and in the server terminal "stream starting at 6", "11": the browser sent Last-Event-ID automatically, and the server resumed. In DevTools' Network tab, the events request has an EventStream tab listing each event.

Choose and scale

(a) Choose a transport for: a dashboard showing order counts updated every 30 s; streaming an LLM's answer token by token; a collaborative whiteboard; a stock ticker for 500,000 concurrent web users. (b) The whiteboard runs on 20 WebSocket servers. Two collaborators on the same board are connected to different servers. How does a stroke from one reach the other, and what happens when a server is redeployed?

Answer

(a) Dashboard: polling every 30 s (or SSE): simple, cacheable, stateless. LLM tokens: SSE: one-directional, plain HTTP, reconnect support; make sure proxies do not buffer. Whiteboard: WebSockets: frequent bidirectional low-latency messages. Ticker for 500,000 users: SSE or WebSockets through a fan-out tier (or a managed real-time service); updates are server to client only, so SSE is sufficient and simpler, with conflation of updates per symbol for slow clients.

(b)

  • Each server subscribes to a pub/sub channel per active board (for example board:123) when its first client for that board connects. A stroke arriving on server A is persisted, appended to the board's operation log with a sequence number, and published to board:123; server B receives it and pushes it to its local clients.
  • Alternatively, route all clients of one board to the same server with consistent hashing on the board id: less pub/sub traffic, but hot boards and rebalancing get harder.
  • Redeploy: the server stops accepting new connections and closes existing ones gradually (or sends a "reconnect" message); clients reconnect with jittered backoff to other servers, send their last seen sequence number, and the server replays missed operations from the log. Without the sequence numbers and log, strokes sent during the reconnection would be lost silently.
Estimate it

A notification feature must reach 2 million concurrently online users. Compare short polling every 10 seconds with SSE plus a heartbeat every 25 seconds: requests or messages per second at the servers, and the number of servers needed for connections if one server holds 100,000 SSE connections.

Answer

Polling: 2,000,000 / 10 s = 200,000 requests per second, around the clock, each a full HTTP request with headers, authentication and a lookup, even when there is nothing new; average notification latency about 5 seconds.

SSE: 2,000,000 open connections / 100,000 per server = 20 servers, plus headroom (say 30). Heartbeats: 2,000,000 / 25 s = 80,000 tiny messages per second spread across them, no authentication or database work per heartbeat. Notifications arrive in milliseconds. The costs move elsewhere: holding state per connection, fan-out infrastructure to reach the right server, and handling reconnect storms (2 million reconnects after a bad deploy is 2 million TLS handshakes, which is why jitter and gradual draining matter).

If notifications are rare and a few seconds of delay is acceptable, a longer polling interval (60 s) with cheap 304 responses can still be the simpler choice; the numbers are what let you argue it either way.
