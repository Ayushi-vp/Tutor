Everything in this track so far has been about what travels on the wire. This lesson is about the other end: what happens inside a server process that has to talk to thousands of clients, and inside a client process that has to talk to databases and APIs efficiently. That is where networking meets the code you write every day, and where many performance and reliability problems actually live.

Consider some situations you will meet. A Python web service handles 50 requests per second comfortably, then falls over at 60, while its CPU sits at 20%, because every worker thread is waiting on a slow downstream call. An asynchronous server handling thousands of WebSocket clients freezes for everyone whenever one handler parses a large file. A service scaled from 5 to 40 instances brings the database down, not with queries, but with connections. A containerised service works perfectly inside the container and refuses every connection from outside. A long-running service dies at 3 a.m. with "Too many open files".

Each of these is explained by three ideas. First, what a socket is to the operating system: a file descriptor with kernel buffers and queues behind it, created and managed with a handful of system calls. Second, the I/O model: how a program waits for many sockets at once, from one thread per connection, through event loops built on epoll, to modern completion APIs and virtual threads. Third, connection management: because connections are expensive to create (net4, net9), programs keep pools of them, and sizing and maintaining those pools is a skill interviewers test directly.

This lesson builds each idea from the system calls up, with runnable Python, and ends with the production failure modes and the numbers you need to reason about capacity.

A socket is a file descriptor with buffers behind it

When a program wants to use the network, it asks the operating system for a socket. The kernel creates the internal structures for a network endpoint and gives the program back a small integer, a file descriptor, the same kind of handle it gets for an open file. The program then uses system calls on that descriptor: connect it somewhere, write bytes into it, read bytes out of it, close it.

Behind each connected socket, the kernel keeps two buffers. The receive buffer holds bytes that have arrived from the network but that the program has not read yet. The send buffer holds bytes the program has written but that TCP has not yet had acknowledged by the other side. That is why send() usually returns instantly (it only copies into the send buffer), and why recv() sometimes returns data immediately and sometimes has to wait.

The analogy: a switchboard with mailboxes

Think of a hotel switchboard. The hotel's published number is the listening socket: calls to it do not go to a guest directly. The switchboard answers each incoming call and connects it to its own line (accept() returns a new socket per connection). Each line has an in-tray and an out-tray (the receive and send buffers), so messages can arrive while the guest is busy. The question this lesson keeps asking is: how many staff do you need to watch all those in-trays? One per line (a thread per connection), or one attentive operator who watches a board of lights and only picks up lines that are flashing (an event loop)?

The analogy breaks in scale: a real server may have a hundred thousand "lines" open, almost all silent at any moment, which is exactly why the second approach wins.

The life of a server socket

What this looks like from your code

Most of the time you never call these system calls yourself: a web framework, a database driver or an HTTP client library does it for you. But their behaviour follows directly from what is underneath. A framework's "worker count" is how many requests it can wait on at once. An "async" framework is an event loop over non-blocking sockets. A database driver's "pool size" is how many sockets to the database it keeps open. When a service is slow while its CPU is idle, the answer is almost always that its threads, coroutines or pooled connections are all busy waiting on something, and the tools in this lesson are how you find out what.

Three things to take away before the details

First, most of the networking work happens in the kernel; your program's job is to move bytes in and out of buffers promptly. Second, the hard question for a server is how to wait on many sockets at once without wasting threads. Third, creating a connection is expensive, so well-behaved clients reuse them through pools. The body takes each in turn.

1. The system calls, one by one

A TCP server makes four calls to get going, then loops:

import socket
srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)   # 1. create a TCP endpoint
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("0.0.0.0", 8000))                                # 2. attach to address and port
srv.listen(128)                                            # 3. accept connections, backlog 128
while True:
    conn, addr = srv.accept()                              # 4. next completed connection
    data = conn.recv(4096)                                 #    read up to 4096 bytes
    conn.sendall(b"HTTP/1.0 200 OK\r\n\r\nhello\n")        #    write (looping until all sent)
    conn.close()
  • socket() creates the endpoint. AF_INET means IPv4 (AF_INET6 for IPv6) and SOCK_STREAM means TCP (SOCK_DGRAM would be UDP).
  • bind() attaches it to a local address and port. The address matters: 127.0.0.1 accepts connections only from the same machine (or the same container), while 0.0.0.0 accepts on every network interface. A service bound to 127.0.0.1 inside a Docker container is unreachable from the host, the most common "works in the container, refused from outside" bug.
  • listen(backlog) turns it into a listening socket. The kernel now completes TCP handshakes on its own and queues finished connections in the accept queue, up to the backlog (further capped by the system setting net.core.somaxconn).
  • accept() removes the next connection from that queue and returns a new socket for it, plus the client's address. The listening socket carries on listening.

A client needs only two: socket() and connect((host, port)), during which the kernel chooses an ephemeral port and performs the handshake (net4). Two more details bite everyone once. send() may accept only part of the data and return how many bytes it took, so use sendall() or loop; and recv(4096) returns whatever has arrived, from 1 byte up to 4096, or an empty result when the peer has closed, so reading a whole message means looping and framing (net4's byte stream lab).

Two socket options are worth knowing by name. SO_REUSEADDR lets a restarted server bind its port even though connections from its previous run linger in TIME_WAIT; without it, restarts fail with "Address already in use" for up to a minute. SO_REUSEPORT lets several processes bind the same port and has the kernel spread incoming connections across them, a simple way to use all cores.

Every socket costs a file descriptor, and processes have a limit, often 1,024 by default on Linux for the soft limit. A server holding 50,000 connections needs that raised (ulimit -n, systemd's LimitNOFILE, or the container runtime's settings); otherwise it fails with "Too many open files".

2. The core problem: waiting on many sockets

The loop above handles one client at a time: while recv() waits for a slow client, every other client waits too. Calls like recv() and accept() are blocking: they pause the calling thread until something happens. A server with many clients must somehow wait on all of them at once. There are four broad answers.

3. Answer one: a thread (or process) per connection

Give each connection its own thread, which can block freely. The code stays simple and linear, which is why classic servers such as early Apache and many Java servlet containers worked this way. The cost appears at scale. Each operating-system thread reserves a stack (8 MB of virtual memory by default on Linux, though only the pages actually used consume RAM, typically tens to hundreds of kilobytes), kernel scheduling structures, and CPU time for context switches whenever the scheduler moves between threads. At ten thousand mostly idle connections, you have ten thousand threads, most asleep, with heavy memory use and scheduler overhead. That was the famous C10K problem of the late 1990s: how to serve ten thousand concurrent clients on one machine. Thread pools (a fixed number of threads serving a queue of connections) cap the cost but cap concurrency too: with 50 threads, the 51st slow client waits.

4. Answer two: non-blocking sockets and an event loop

Put every socket into non-blocking mode, so a read with no data returns immediately with an error (EAGAIN) instead of waiting. Then ask the kernel a single question: "which of these sockets are ready to read or write right now?" and handle only those. A loop that does this forever is an event loop, and it lets one thread serve thousands of connections.

How the kernel answers "which sockets are ready?" matters. The original APIs, select and poll, take the full list of descriptors on every call and scan it, so each call costs time proportional to the number of connections, even if only two are active. epoll on Linux and kqueue on BSD and macOS fix this: the program registers each socket once, the kernel maintains a ready list as data arrives, and each wait returns only the ready sockets. Cost now scales with activity, not with the number of connections. This is the engine inside nginx, Node.js, Redis, HAProxy, Netty, and Python's asyncio.

Writing raw event loops with callbacks is error-prone, so modern languages hide it behind async/await. An async def function is a coroutine: when it reaches await reader.read() and no data is ready, it suspends, the loop registers interest in that socket, and other coroutines run; when data arrives, the loop resumes it. The code reads like blocking code but behaves like an event loop.

The price is one strict rule: never block the loop. A call to time.sleep(), a synchronous HTTP library such as requests, a classic database driver, or a few hundred milliseconds of CPU work (parsing a big JSON document, running a model) stops the only thread, and every connection on that loop freezes. Blocking and CPU-heavy work must go to a thread or process pool (asyncio.to_thread, run_in_executor), and I/O should use async libraries (httpx, asyncpg).

5. Answer three: completion-based I/O

Readiness APIs tell you "this socket can be read now"; you then make the read call. Completion-based APIs let you say "read into this buffer and tell me when you're done". Windows has had this for decades as IOCP (I/O completion ports). Linux added io_uring in 2019 (kernel 5.1): the program and kernel share two ring buffers, one where the program queues requests and one where the kernel posts results, so many operations can be submitted and reaped with few or even no system calls. It also covers file I/O, which epoll cannot make asynchronous. It shines when operation rates are very high, as in storage engines, databases and proxies, and is gradually being adopted by runtimes, though its complexity and a history of security bugs mean some platforms restrict it.

6. Answer four: green threads and virtual threads

What if you could have the simple, blocking-style code of thread-per-connection with the efficiency of an event loop? That is what green threads offer: lightweight threads managed by the language runtime, costing a few kilobytes each, multiplexed onto a small number of OS threads. When one blocks on a socket, the runtime parks it, registers the socket with epoll, and runs another. Go's goroutines have worked this way since the language's start, Erlang and Elixir processes similarly, and Java added virtual threads in Java 21 (2023). A Go server can simply start a goroutine per connection and hold hundreds of thousands. Python's closest equivalent is asyncio, which requires explicit async and await.

7. Using all the cores

One event loop runs on one core. To use a 16-core machine, run one loop per core: multiple processes each with its own loop (nginx workers, gunicorn or uvicorn with several workers), or a runtime that spreads tasks across a pool of OS threads (Go, Rust's Tokio, Netty). New connections are spread across loops with SO_REUSEPORT or a single acceptor that hands sockets to workers. In Python, the global interpreter lock limits CPU parallelism within a process, so the standard pattern is several processes, each running an asyncio loop.

8. Connection pools

On the client side, the most important habit is reuse. Opening a connection costs a TCP handshake, often a TLS handshake (net9), sometimes authentication (a database login), and slow start before throughput ramps up (net4). On the server side it can cost a lot of memory: each PostgreSQL connection is a separate server process using several megabytes. So clients keep a connection pool: a set of open connections that requests borrow and return.

Sizing starts with Little's law, which says that in a steady system the average number of items in progress equals the arrival rate times the time each spends: at 500 queries per second, each holding a connection for 10 ms, on average 5 connections are busy. Add headroom for bursts and variance, perhaps two to four times, and you get a pool of 10 to 20. Then check the other side: the database can only execute about as many queries in parallel as it has cores (plus some for I/O waits). Past that, more connections do not add throughput; they add lock contention, memory and context switching, and latency rises. The HikariCP project's widely quoted rule of thumb is roughly twice the database's core count for the total number of active connections. The trap is multiplication: 40 application instances with a pool of 20 each is 800 connections, far beyond a database whose default max_connections in PostgreSQL is 100. The fix is smaller pools per instance or a server-side pooler such as PgBouncer, which lets thousands of client connections share a few dozen real database connections.

Maintenance matters as much as size. Connections go stale: a NAT or load balancer drops them after an idle timeout (net3, net10), the database fails over, a firewall resets them. Pools protect themselves by validating connections before use or in the background, by retiring connections after a maximum lifetime shorter than any idle timeout on the path (which also makes clients follow DNS changes and rebalance), and by TCP keepalive. Callers need a checkout timeout, so that when the pool is exhausted they fail fast with a clear error instead of queuing indefinitely. And code must always return connections, including on error paths, which in Python means with blocks or async with; a leaked connection per error slowly drains the pool until everything hangs.

HTTP clients pool too: a requests.Session or an httpx.Client keeps connections to each host alive and reuses them. Creating a new client per request, a very common mistake with LLM and other third-party API clients, throws that away and pays DNS, TCP and TLS on every call.

Backpressure at the socket level

When a client reads slowly, TCP flow control (net4) fills the server's send buffer for that socket, and a non-blocking write then returns EAGAIN, or an async write stops completing. Correct code treats that as a signal to slow down: in asyncio, await writer.drain() suspends the producer until the buffer has room. Incorrect code keeps appending to an application-level queue, which grows without bound: a handful of slow clients can then exhaust a server's memory. The same principle chains through proxies, which stop reading from upstream when their downstream buffers are full, pushing the slowdown back to the origin. Designing push servers (net11) is largely about choosing what to do when this backpressure hits: wait, conflate, drop or disconnect.

Accept queues and connection storms

The kernel completes handshakes into a listening socket's accept queue, whose length is the minimum of the application's backlog argument and net.core.somaxconn (4096 by default on modern Linux). If the application's accept loop falls behind, for example because the event loop is busy with CPU work, the queue fills and new connection attempts are dropped, which clients experience as connect timeouts. You can see it in ss -ltn, where a listening socket's Recv-Q approaching its Send-Q means the queue is nearly full, and in the kernel's ListenOverflows counter. Connection storms, such as all clients reconnecting after a restart, are exactly when this happens, and TLS handshakes make each new connection CPU-expensive. Larger backlogs, SO_REUSEPORT with several acceptors, and client-side jittered reconnection are the defences.

Edge-triggered versus level-triggered notification

epoll can notify in two modes. Level-triggered, the default, reports a socket as readable as long as data remains in its buffer, so a handler that reads only part of the data will be told again. Edge-triggered reports only when the state changes, that is, when new data arrives, so a handler must keep reading until it gets EAGAIN, or leftover data may sit unnoticed forever. Edge-triggered mode reduces redundant wake-ups in very busy servers and is used by high-performance proxies; level-triggered is more forgiving. The difference is a classic source of subtle hangs in hand-written event loops, and a good interview probe of real understanding.

Zero-copy and kernel bypass

A static file server that reads a file into user memory and then writes it to a socket copies every byte twice across the user-kernel boundary. sendfile() tells the kernel to move bytes from a file directly to a socket, and splice() does similar work between pipes and sockets, which is why nginx serves static files so efficiently. Encryption complicates this, since TLS happens in user space, but kernel TLS (kTLS) moves record encryption into the kernel or even the network card so zero-copy works for HTTPS too. At the extreme, systems such as DPDK and XDP bypass or pre-empt the kernel's network stack for packet processing at tens of millions of packets per second, used in load balancers and DDoS mitigation rather than application servers.

Unix domain sockets and same-host traffic

Processes on the same machine, such as an application and its sidecar proxy, or an application and a local database or cache, can talk over Unix domain sockets, addressed by a file path such as /var/run/postgresql/.s.PGSQL.5432. They skip TCP and IP processing entirely, so they have lower latency and higher throughput than loopback TCP, and their access can be controlled with file permissions. Many databases, Docker's API and service-mesh sidecars use them. They also allow passing file descriptors between processes, a trick used for zero-downtime restarts where a new process inherits the old one's listening socket.

Server-side poolers and their trade-offs

PgBouncer and similar poolers (RDS Proxy, pgcat, ProxySQL for MySQL) sit between applications and the database. In session mode, each client connection gets a dedicated server connection for its whole life, which mostly just caps the count. In transaction mode, a server connection is lent only for the duration of a transaction, so thousands of clients share a few dozen connections, which is what serverless and heavily scaled deployments need. The cost is that anything relying on session state across transactions, such as SET commands, session advisory locks, temporary tables and LISTEN, breaks or needs special handling, and older versions could not support server-side prepared statements in this mode. Knowing which mode you are in explains many "works locally, fails in production" database bugs.

Characteristic failures

  • Thread or worker exhaustion: a synchronous service with 32 workers and a downstream that slows from 50 ms to 2 s can serve only 16 requests per second; the rest queue, and the service looks down while its CPU is idle. Fixes: timeouts on downstream calls, async I/O, more workers, and circuit breakers (sc12).
  • Blocked event loops: an async service's p99 latency spikes whenever a large payload is parsed or a blocking library is called; all connections on that loop pause. Detect with event-loop lag metrics or asyncio debug mode; fix by offloading.
  • Pool exhaustion: requests hang waiting for a database connection because slow queries or leaked connections hold them all. Without checkout timeouts this looks like mysterious latency; with them, it becomes clear errors. Watch pool wait time and active count.
  • Connection explosions: autoscaling application instances multiplies pool sizes until the database hits max_connections and rejects new connections, or spends its memory on idle connections. Serverless functions, each opening its own connection, are notorious for this.
  • Stale connections after failover: after a database or load balancer fails over, pooled connections to the old address fail one by one, producing a burst of errors. Validation, maximum lifetimes and retry-once on connection errors smooth it out.
  • Descriptor limits and leaks: "Too many open files" at high load (limit too low) or after days of uptime (leak, visible as growing CLOSE_WAIT counts).
  • Accept queue overflow: connect timeouts during bursts or restarts while the service seems healthy.

War story pattern: the scale-out that took down the database

A team moves a Python API to Kubernetes with horizontal autoscaling. Each pod runs 4 gunicorn workers, each with a SQLAlchemy pool of 10 plus 10 overflow connections. At a traffic peak the autoscaler goes from 6 to 30 pods, and the theoretical connection count jumps from 480 to 2,400 against a PostgreSQL instance with max_connections set to 500. New pods fail their readiness checks because they cannot connect, the autoscaler adds more pods in response to rising latency, and the database spends its memory on connection processes. The fix is structural: a PgBouncer tier in transaction mode between the pods and the database, pool sizes per worker reduced to a handful, and a pool budget written down as "total connections = pods × workers × pool size" and checked against the database whenever autoscaling limits change.

Observability

Useful signals: open file descriptors per process (/proc/PID/fd) against the limit; socket counts by state (ss -s, ss -tan state close-wait); listen queue depth and overflow counters; event-loop lag (the delay between when a timer should fire and when it does); pool metrics (size, in use, idle, wait count and wait time, timeouts); and database-side connection counts by client. Most pool libraries and frameworks export these; make sure they are on dashboards before you need them.

Knobs

File descriptor limits; listen backlog and somaxconn; SO_REUSEPORT and worker count per core; socket buffer sizes for high-bandwidth connections; TCP keepalive and user timeouts on long-lived connections; pool size, overflow, checkout timeout, validation and maximum lifetime; server-side pooler mode and size; and downstream timeouts, which decide how long threads, coroutines and connections can be held by a single slow call.

Twenty minutes with Python 3.8+ (any OS; the ss step needs Linux or WSL). You will see what blocking the event loop does, and measure how pool size affects throughput.

  4. Pool sizing experiment. Save as pool.py: it simulates a database that can run 8 queries in parallel and slows down, with some contention, when given more: 
    import asyncio, time, statistics
CORES, QUERY = 8, 0.02
async def run(pool_size, requests=400, timeout=2.0):
    pool, active, lat, failed = asyncio.Semaphore(pool_size), 0, [], 0
    async def query():
        nonlocal active
        active += 1
        slowdown = max(1, active / CORES) * (1 + 0.02 * max(0, active - CORES))
        await asyncio.sleep(QUERY * slowdown)
        active -= 1
    async def request():
        nonlocal failed
        t0 = time.perf_counter()
        try:
            await asyncio.wait_for(pool.acquire(), timeout)   # checkout timeout
        except asyncio.TimeoutError:
            failed += 1; return
        try: await query()
        finally: pool.release()
        lat.append(time.perf_counter() - t0)
    t0 = time.perf_counter()
    await asyncio.gather(*(request() for _ in range(requests)))
    el = time.perf_counter() - t0
    print(f"pool={pool_size:4d} ok={len(lat):3d} failed={failed:3d} "
          f"throughput={len(lat)/el:5.0f}/s p50={statistics.median(lat)*1000:5.0f} ms")
for size in (2, 8, 16, 64, 256):
    asyncio.run(run(size))
    Look for: a tiny pool fails requests at the checkout timeout; throughput peaks somewhere around one to two times the database's "cores"; and very large pools are slower, with higher latency, because the database spends its time on contention. Exact numbers vary with your OS's timer precision, but the shape, rise then fall, is the lesson.
  5. Inspect listening sockets (Linux/WSL): ss -ltnp. Look for: your server on 127.0.0.1:9000, with Recv-Q (current accept queue) and Send-Q (its limit). Restart the server bound to 0.0.0.0 and see the local address change: that is the difference between "only this machine" and "every interface".
Write and analyse

(a) Write a minimal asyncio TCP echo server that handles many clients concurrently. (b) Why can it handle 10,000 idle clients on one thread? (c) What happens to the other clients if one handler calls time.sleep(2)?

Answer 
import asyncio

async def handle(reader: asyncio.StreamReader, writer: asyncio.StreamWriter):
    try:
        while data := await reader.readline():   # b"" when the client closes
            writer.write(data)
            await writer.drain()                  # respect backpressure
    finally:
        writer.close()
        await writer.wait_closed()

async def main():
    server = await asyncio.start_server(handle, "0.0.0.0", 9000)
    async with server:
        await server.serve_forever()

asyncio.run(main())

(b) Each idle client is just a socket registered with epoll plus a suspended coroutine (a few kilobytes), not a thread with its own stack. The event loop asks the kernel which sockets are ready and resumes only those coroutines, so idle connections cost almost nothing (raise the file-descriptor limit, though).

(c) time.sleep blocks the only thread: the event loop cannot run, so every client stalls for 2 s. Use await asyncio.sleep(2), or for blocking library calls and CPU work, await asyncio.to_thread(fn) or a process pool. Detect it with asyncio's debug mode, which warns about callbacks slower than 100 ms.

Size it

An API runs 12 instances, each handling up to 300 requests per second at peak. Each request makes two database queries averaging 8 ms each, and holds its connection only during the queries. The PostgreSQL server has 16 cores and max_connections = 200. Size the per-instance pool and decide whether you need a pooler.

Answer

Per instance, connection hold time per request is about 2 × 8 ms = 16 ms, so by Little's law the average busy connections are 300/s × 0.016 s ≈ 4.8. With headroom for bursts and variance (×2 to ×3), a pool of about 10 to 15 per instance.

Across the fleet: average busy connections ≈ 12 × 4.8 ≈ 58, and the pool maximum is 12 × 15 = 180, which fits under max_connections = 200 but leaves little room for admin tools, migrations and other services. The database with 16 cores runs efficiently at roughly 32 or so active queries; 58 average active is already beyond that, so at peak queries will queue inside the database. That suggests optimising the queries or adding read replicas matters more than bigger pools. If the fleet autoscales beyond 12 instances, the pool budget breaks; putting PgBouncer in transaction mode in front, with a server-side pool of about 40, caps real connections regardless of instance count and is the robust choice.
