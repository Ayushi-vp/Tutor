Sooner or later every engineer gets the message: "the service is slow", "it times out sometimes", "it works from my laptop but not from production", "the upload hangs at 99%". Network problems are frustrating because the symptom appears far from the cause, and because many components are involved: resolvers, load balancers, proxies, NATs, firewalls, TLS, the kernel's TCP stack, connection pools, and the application. It is tempting to guess, restart things, or blame "the network". Engineers who are good at this do something different: they narrow the problem down systematically, with measurements, until only one explanation fits.

This final lesson of the track pulls everything together into that skill. You already know the pieces: how DNS resolves (net6), how TCP behaves under loss and distance (net4), how TLS fails (net9), how proxies generate 502s and 504s (net10), how NAT and firewalls drop idle or unexpected traffic (net3, net14), and how pools and event loops behave (net13). Debugging is the art of asking the right question in the right order, choosing the tool that answers it, and knowing what a healthy answer looks like.

The second half is performance: the small amount of arithmetic that explains most network speed problems. Why a download between continents crawls on a fast link. Why 1% packet loss matters so much. Why a request that is fast in one region is slow in another. Why a VPN makes large requests hang while small ones work. These are standard interview questions, and each has a numerical answer.

This lesson covers a debugging method, how to split latency into phases, the performance fundamentals of RTT, bandwidth-delay product, loss and MTU, the command-line toolkit organised by the question each tool answers, how to debug inside containers and Kubernetes, and how to approach the hardest case: intermittent failures.

The method in one line

Scope it, then go layer by layer from the client's point of view, comparing a working case with a failing one, and measure instead of guessing. Everything else in this lesson is detail on that sentence.

The analogy: a doctor's diagnosis

A good doctor does not start by prescribing. They take a history (when did it start, what changed, who else is affected), examine systematically from the most basic vital signs upward, run the test that best separates the likely causes, and compare against what "normal" looks like. Network debugging is the same: scoping is the history, the layer-by-layer checks are the examination, a packet capture is the blood test, and baselines are "normal". Where the analogy breaks: you can usually reproduce a network problem on demand and test a hypothesis in seconds, so you should, rather than reasoning at length.

The decision path

Three habits that save hours

Reproduce from the right place. A request from your laptop takes a different path, resolver and set of firewall rules from a request made inside a production pod. Get a shell where the failing client runs, or as close to it as possible, before drawing conclusions.

Change one thing at a time, and write it down. Under pressure it is tempting to restart services, flush caches and tweak timeouts all at once. If the problem then disappears, you have learned nothing and it will return. Keep a running log of what you checked, what you saw and what you changed, with timestamps; it becomes the incident timeline for free.

Prefer tests that split the hypotheses in half. "Does it fail with the VPN off?" or "does it fail against a pod IP instead of the Service name?" each rule out half of the possible causes in one step. A good debugger is always asking which single test would eliminate the most explanations.

Before any tool: scope

Five questions narrow most problems before a single command runs. Who is affected: one user, one region, one client version, everyone? What exactly fails: every request, some requests, only large ones, only new connections? Since when, to the minute? What changed around then: deploys, configuration, DNS, certificates, firewall rules, provider incidents? And from where can you reproduce it? A problem that affects only one availability zone, starting at 14:02, right after a security-group change, has usually solved itself before you open a terminal.

Scoping also tells you who to involve and how urgent it is: a problem for one user on hotel Wi-Fi is a support ticket; a problem for every user in one region since a change ten minutes ago is an incident with an obvious first action, rolling that change back.

Then compare: a request that works against one that fails, a healthy host against a sick one, today against yesterday's baseline. Differences are evidence; similarities rule things out.

1. Step by step with the right tool

Each step of the decision path has a tool that answers exactly its question, and a way of reading the answer.

Name resolution. dig +short api.example.com shows what the resolver returns; dig @8.8.8.8 api.example.com compares another resolver; dig +trace walks the delegation from the root (net6). But programs do not use dig; they use the system's resolver library, which also reads /etc/hosts and applies search domains. getent hosts api.example.com on Linux follows the same path most programs do, so when dig and the application disagree, getent usually explains why.

Reachability of the port. nc -vz host 443 (or Test-NetConnection host -Port 443 in PowerShell) attempts a TCP connection and reports success, "connection refused" or a timeout. Recall net1's distinction: refused means a host answered with a reset, so check whether the service is running and what address it is bound to (ss -ltnp on the server); timed out means nothing answered, so look at security groups, network ACLs, routes and whether the address is right. Flow logs show whether a firewall rejected the connection.

TLS. openssl s_client -connect host:443 -servername host shows the certificate chain the server actually sends, its dates and names, the negotiated protocol and the verification result (net9). Always pass -servername, or you may test the wrong certificate on a server that hosts several.

HTTP. curl -v https://host/path shows the request, the status line and the response headers. The first question for any 5xx is which component generated it: the server and via headers, the error page's style and the proxy's logs usually tell you whether a CDN, load balancer or the application answered (net10).

The wire. When the tools above disagree or the symptom is ambiguous, capture packets. sudo tcpdump -i any -nn host 10.0.1.5 and port 5432 -w cap.pcap records the conversation with one database, and Wireshark decodes it, flagging retransmissions, duplicate ACKs, zero windows and resets automatically. Captures answer the questions nothing else can: did the SYN arrive? Did the server answer? Who sent the reset? Did data stop in one direction?

2. Where does the time go?

For slowness, the most productive first step is splitting a request into phases. curl reports cumulative times at each milestone:

curl -s -o /dev/null https://api.example.com/v1/items -w \
 'dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}  total %{time_total}\n'

Subtract consecutive values to get each phase: TCP handshake = tcp − dns, TLS handshake = tls − tcp, server time plus one round trip = ttfb − tls, transfer = total − ttfb. Browsers show the same phases in DevTools' timing tab, and real-user monitoring collects them from every visitor (net2).

Interpreting the phases uses what you know about round trips. The TCP handshake phase should be about one RTT to the server; TLS 1.3 about one more. If they are each 200 ms, the user is far away or the path is poor, and the fix is proximity (a CDN edge or a nearer region) or fewer handshakes (connection reuse). If handshakes are small but time to first byte is large, the server or something behind it is slow: now switch to application tracing and logs. If DNS is large, look at resolvers; exactly five seconds means a lost query and a retry. If transfer dominates, the response is large relative to throughput, which the next sections explain.

3. Latency and bandwidth are different things

Latency is how long a bit takes to get there and back (RTT); bandwidth is how many bits per second the path can carry. They are independent: a satellite link can have high bandwidth and terrible latency; a local connection can have low latency and modest bandwidth. Small requests, such as API calls and page loads, are dominated by latency, because they consist of a few round trips each carrying little data. Large transfers are dominated by throughput, but only after TCP has ramped up, and throughput depends on latency too, as the next section shows. The practical rule: to make small things faster, remove round trips or shorten them; to make big things faster, make sure enough data is in flight.

A few reference numbers help intuition: within one data centre or availability zone, RTTs are well under a millisecond; between zones in a region, about 1 to 2 ms; across a continent, 30 to 80 ms; between continents, 100 to 300 ms. Light in fibre covers about 200 km per millisecond, so there is a hard floor on every long-distance RTT (net1).

4. The bandwidth-delay product

TCP can only have one window of unacknowledged data in flight per round trip (net4), so a single connection's throughput is at most window ÷ RTT. The bandwidth-delay product (BDP), bandwidth × RTT, is the window needed to keep a path full. Worked examples:

Modern Linux grows windows automatically (window scaling plus buffer autotuning) up to limits set by net.ipv4.tcp_rmem and tcp_wmem, so a healthy connection on a clean path reaches much higher throughput than the last column. When it does not, the window is being capped: window scaling disabled or stripped by a middlebox, buffer maximums too small, or an application that sets SO_RCVBUF explicitly, which switches off autotuning. ss -ti on a live connection shows the numbers: rtt, cwnd, rcv_space, the window scale factors (wscale) and the delivery rate.

5. Loss and its cost

On long paths, loss is usually the limit, not windows. Every loss makes TCP's congestion control reduce its sending window (net4), and a lost final segment may wait for a retransmission timeout of at least 200 ms on Linux. The Mathis approximation says a loss-based TCP connection achieves roughly MSS ÷ (RTT × √loss). On a 100 ms path, 1% loss gives about 1,460 × 8 ÷ (0.1 × 0.1) ≈ 1.2 Mbit/s, and 0.01% loss about 12 Mbit/s: a hundredfold drop in loss gives only a tenfold rise in throughput, and both are far below a gigabit. For short requests the same losses show up as tail latency: a request that normally takes 20 ms sometimes takes 220 ms or more.

Where to see loss: retransmission counters (nstat -az TcpRetransSegs, ss -ti showing retrans), Wireshark's retransmission flags, and mtr for loss along a path. Where it comes from in practice: congested links, overflowing queues in middleboxes or on hosts, cloud per-instance packet-rate limits, and full connection-tracking tables. Its opposite, bufferbloat, is equally real: oversized buffers that avoid loss by queueing, so latency climbs to hundreds of milliseconds under load while loss stays near zero.

6. MTU problems

Every link has a maximum packet size, its MTU: 1,500 bytes on standard Ethernet, up to 9,001 bytes (jumbo frames) inside an AWS VPC, but traffic through an internet gateway, a VPN or between regions without a transit gateway is limited to 1,500. Tunnels, VPNs and overlay networks add headers, so the usable MTU inside them is smaller (VXLAN adds 50 bytes, net1). When a packet is too big for a link and marked "don't fragment", the router drops it and should send back an ICMP "fragmentation needed" (IPv6: "packet too big") message, so the sender can shrink its packets: that is Path MTU Discovery. If a firewall blocks those ICMP messages, the sender never learns, and full-size packets vanish: a PMTU black hole. The signature is unmistakable once you know it: connections open, small requests work, but large responses, uploads or TLS handshakes with big certificate chains hang and eventually time out.

To test by hand, ping with the don't-fragment flag and a payload that makes a 1,500-byte packet (1,472 bytes of data plus 20 bytes of IP header plus 8 of ICMP): ping -M do -s 1472 host on Linux, ping -D -s 1472 host on macOS, ping -f -l 1472 host on Windows. If that fails with "message too long" or silence while smaller sizes succeed, reduce the size until it works; that is the path MTU. Fixes: allow ICMP type 3 code 4 (and ICMPv6 type 2) through firewalls, clamp the TCP MSS on the tunnel so both ends send smaller segments, or lower the interface MTU.

8. Debugging inside containers and Kubernetes

Every container and pod has its own network namespace: its own interfaces, routing table, DNS configuration and, in Kubernetes, its own NetworkPolicies. So "it works from my laptop" and even "it works from the node" say little about what the pod sees. Debug from inside: kubectl exec -it pod -- sh if the image has tools, or attach an ephemeral debug container with a toolbox image, such as kubectl debug -it pod --image=nicolaka/netshoot --target=app, which shares the pod's network namespace. From there, check DNS against the cluster resolver (watch for ndots expansion, net6), curl the Service name and then a pod IP directly (if the IP works and the name does not, look at the Service's selector and kubectl get endpoints), and test whether a NetworkPolicy blocks the path. Kubernetes adds its own failure modes: Services with no ready endpoints, readiness probes failing, kube-proxy or eBPF data-plane rules out of sync, and connection-tracking races.

Intermittent problems: correlate, then capture

The hardest network problems affect a small fraction of requests. The approach that works is statistical before it is technical: slice failures by every dimension you have, such as backend instance, availability zone, client host or version, time of day, request size, connection age, protocol version and source network, and look for the dimension where failures concentrate. Common fingerprints: one bad instance behind a load balancer (failures concentrate on one target), one zone with a faulty path (failures by zone), requests above a size threshold (MTU), connections idle longer than a NAT or balancer timeout (failures on first use after quiet periods, net3, net10), overloaded DNS (exact five-second delays), pool connections that died (errors on first query after a failover), and ECMP hashing onto a bad link, which looks random per request but is consistent per connection 4-tuple, so a retry on a new connection succeeds (net3). Only after narrowing does a packet capture become efficient, taken on both sides of the suspect hop.

The USE method for network resources

Brendan Gregg's USE method is a checklist: for every resource, check utilisation (how busy), saturation (how much work is queued) and errors. Applied to networking: interface utilisation against bandwidth and packet-rate limits (cloud instances have both, and small-packet workloads hit packets per second first); saturation as queue lengths, socket backlogs, drops and TCP retransmissions; errors as interface errors, conntrack "table full" messages, ICMP unreachables and resets. Doing this for NICs, NAT gateways, load balancers, conntrack tables, file descriptors and connection pools turns "the network is slow" into a short list of saturated resources.

eBPF observability

eBPF lets small verified programs run inside the Linux kernel at events such as TCP state changes, retransmissions, packet drops and socket calls, aggregating results cheaply. The bcc tools collection includes tcpretrans (every retransmission, with addresses and state), tcplife (every connection's duration and bytes, with process names), tcpconnect and tcpaccept, and tools that report the kernel's drop reasons. In Kubernetes, network plugins built on eBPF, such as Cilium with Hubble, show per-flow visibility including which policy dropped a packet. These answer many questions that previously needed full captures, with overhead low enough for production, and they attribute traffic to processes and pods rather than just addresses.

Connection tracking and cloud limits

Stateful components everywhere keep per-connection state: Linux's conntrack table (used by NAT, Docker and Kubernetes kube-proxy in iptables mode), cloud security groups, NAT gateways and load balancers. All have limits. When Linux's table fills, the kernel logs "nf_conntrack: table full, dropping packet" and new connections fail silently; cloud providers impose per-instance limits on tracked connections and packets per second, surfacing as allowance-exceeded metrics rather than errors. High connection churn, long timeouts for idle flows and UDP-heavy workloads fill these tables. Mitigations are raising limits, shortening timeouts for short-lived flows, reducing churn with connection reuse, and, for specific high-volume flows, disabling tracking where the design allows.

Baselines turn debugging into comparison

Most debugging time is spent establishing what "normal" is. Teams that record baselines, such as RTT distributions between zones and regions, throughput per instance type, typical retransmission rates, DNS resolution times and per-phase request latency percentiles, answer "is this abnormal?" in seconds. Synthetic probes that continuously measure key paths (client regions to edge, edge to origin, service to database) provide both the baseline and early warning. Baselines also feed capacity and placement decisions: knowing that a cross-region round trip is 70 ms tells you immediately that a chatty service calling a database in another region will be slow.

Reproducing network conditions on purpose

Many network bugs only appear under conditions that developers never see locally: 150 ms of latency, 2% loss, a 1,400-byte MTU, a connection dropped mid-request. Linux's tc netem can add delay, jitter, loss, duplication and reordering to any interface; browser DevTools can throttle latency and bandwidth; and fault-injection features in proxies and service meshes can add delays or abort a percentage of requests between services. Testing timeouts, retries and streaming code against these conditions before production is far cheaper than discovering their behaviour during an incident, and the lab uses exactly this technique.

Latency is a distribution

Averages hide the problems users feel. A page that makes 50 requests will almost certainly include at least one request at the p98 of your latency distribution, so tail latency is the user experience. Network effects concentrate in the tail: retransmission timeouts, DNS retries, cold connections paying handshakes, queueing behind large responses, and garbage collection pauses on either end. Measure and alert on p95 and p99 per phase, compare tails across hosts and zones, and treat a rising tail with a flat average as an early sign of loss or saturation.

Worked incident: the upload that stalls at 99%

Users behind a new corporate VPN report that uploading files larger than about 1 MB to an internal service stalls near completion and times out, while browsing works. Scoping shows it affects only VPN users and only large uploads, starting the day the VPN was rolled out. The decision path passes steps 1 to 4 (names resolve, ports open, TLS works, small requests return 200). A capture on the client shows the TCP connection established, data flowing, then repeated retransmissions of 1,448-byte segments with no acknowledgements; a capture on the server shows none of those segments arriving. ping -M do -s 1472 through the VPN fails and -s 1400 succeeds: the tunnel's MTU is smaller than 1,500, and a firewall blocks the ICMP messages that would tell the client. Enabling MSS clamping on the VPN gateway fixes it within minutes. Total investigation time was short because the method went straight from scope ("large, VPN-only, since rollout") to the MTU hypothesis to a decisive test.

Worked incident: the slow region

After launching in Asia, users there see page loads three times slower than in the US. Real-user timings split by phase show DNS normal, TCP and TLS phases around 200 ms each, and time to first byte around 400 ms: the handshakes and requests are travelling to the US origin. The CDN had been configured only for static assets, so HTML and API calls went direct. Routing HTML and API traffic through the CDN (terminating TLS at Asian edges and forwarding over warm connections) and caching public API responses briefly cut the handshake phases to about 10 ms and time to first byte to about 220 ms (net12). The measurement took minutes; the diagnosis followed directly from the phase breakdown.

Knobs you will reach for

Timeouts (connect, read and idle) at every hop; keep-alive and connection reuse; socket buffer maximums and congestion control on long-haul senders; MTU and MSS clamping on tunnels; ICMP rules that allow Path MTU Discovery; conntrack limits and timeouts; resolver settings and node-local DNS caches; and synthetic probes and baselines that make "is this normal?" answerable.

Twenty-five minutes on Linux or WSL (some steps also work on macOS). You will add artificial latency and loss to your own machine and watch throughput, timings and TCP internals respond, then find a path MTU. Clean up with the commands given.

  1. Baseline. Install iperf3. In one terminal run iperf3 -s; in another, iperf3 -c 127.0.0.1 -t 5. Look for: tens of Gbit/s on loopback: no distance, no loss.
  2. Add distance. sudo tc qdisc add dev lo root netem delay 50ms (100 ms RTT, since both directions cross loopback). Run ping -c 3 127.0.0.1 to confirm about 100 ms, then iperf3 -c 127.0.0.1 -t 10. Look for: throughput ramping up over the first seconds (slow start) and settling far below the baseline. Now cap the window: iperf3 -c 127.0.0.1 -t 10 -w 64K. Look for: a few Mbit/s, in the region of 64 KB ÷ 0.1 s ≈ 5 Mbit/s (Linux adjusts requested buffer sizes, so expect roughly 5 to 10): the bandwidth-delay product limit, as the table predicts.
  3. Add loss. sudo tc qdisc change dev lo root netem delay 50ms loss 1% and run iperf3 -c 127.0.0.1 -t 10 again. Look for: a large further drop, and in the iperf3 output the Retr column counting retransmissions. While it runs, ss -ti dst 127.0.0.1 shows cwnd staying small and retrans climbing.
  4. Timings under distance. Still with the delay, start python3 -m http.server 8000 and run curl -s -o /dev/null http://127.0.0.1:8000/ -w 'tcp %{time_connect} ttfb %{time_starttransfer} total %{time_total}\n'. Look for: about 0.1 s to connect (one RTT) and about 0.2 s to first byte (one more RTT for the request): phases are multiples of RTT.
  5. Clean up: sudo tc qdisc del dev lo root. Rerun ping to confirm the delay is gone.
  6. Find your path MTU. ping -M do -s 1472 -c 2 8.8.8.8 (macOS: ping -D -s 1472 -c 2 8.8.8.8; Windows: ping -f -l 1472 8.8.8.8). Look for: replies if your path carries 1,500-byte packets. If you are on a VPN, try again with it on: you will probably need a smaller size such as 1,400, and "message too long" or silence at 1,472 shows the tunnel's overhead.
  7. Read a path. mtr -rwc 20 1.1.1.1 (install mtr). Look for: the destination's loss column (should be 0%), and any middle hops showing loss that does not continue to later hops: ICMP rate limiting, not real loss.
  8. Capture a timeout. sudo tcpdump -i any -nn host 10.255.255.1 in one terminal and curl --connect-timeout 20 http://10.255.255.1/ in another. Look for: the same SYN sent again and again with no reply: at one-second intervals at first on recent kernels, then with doubling gaps (older kernels double from the start: 1 s, 2 s, 4 s, 8 s). That retry pattern is the signature of a silently dropped connection.
Diagnose from the data

A client in Singapore downloads large files from a server in Frankfurt (RTT 160 ms) over a 1 Gbps path, but gets only about 3 Mbps. ss -ti shows no retransmissions and a receive window stuck around 64 KB. Separately, after a VPN was introduced, some HTTPS requests to an internal service hang forever while others work; small API responses succeed, large ones never finish. Explain both and the fixes.

Answer

Download: throughput ≤ window ÷ RTT = 64 KB ÷ 0.16 s ≈ 400 KB/s ≈ 3.3 Mbps, exactly what is observed. The BDP is 1 Gbps × 0.16 s = 20 MB, so the window must be about 300 times larger. With no loss, the cause is a window cap: window scaling disabled (often by a middlebox stripping the option) or small socket buffers (the net.ipv4.tcp_rmem maximum, or the application setting SO_RCVBUF explicitly, which disables autotuning). Fix: enable window scaling, raise buffer maximums, let autotuning work; otherwise use parallel streams.

VPN hangs: a classic PMTU black hole. The VPN encapsulation reduces the effective MTU below 1,500; small packets fit, but full-size packets carrying large responses (or big TLS certificate chains) exceed it and are dropped. Path MTU Discovery would fix it, but the ICMP "fragmentation needed" messages are blocked, so the sender never learns and keeps retransmitting the same large packets. Confirm with ping -M do -s 1472 host failing versus smaller sizes succeeding, and tcpdump showing repeated retransmissions of full-sized segments. Fix: allow ICMP type 3 code 4, enable TCP MSS clamping on the VPN gateway, or lower the interface MTU.

Triage it

At 14:05 an on-call engineer sees p99 latency for the checkout API jump from 300 ms to 5.3 s, while p50 is unchanged and error rates are flat. Nothing was deployed. Where do you look first, and why?

Answer

A tail jump to almost exactly 5 seconds above normal, with a flat median and no errors, is the fingerprint of occasional lost DNS queries being retried after the resolver's 5-second timeout (net6). First, split the slow requests' time by phase (tracing spans or client DNS timing): if DNS dominates the slow ones, check the resolver (CoreDNS or the VPC resolver) for saturation, drops or rate limiting starting at 14:05, and check whether traffic or query volume rose (ndots expansion multiplies it). If DNS is normal, the next candidates for a clean +5 s are client retry timers with a 5-second timeout, or connection attempts to a dead backend that time out and retry elsewhere; slicing the slow requests by backend instance and zone distinguishes those. Mitigate with node-local DNS caching, lower ndots, fully qualified names, and connection reuse so fewer lookups happen at all.
