You type example.com into a browser in Bengaluru, press Enter, and a moment later a page appears. In that moment your laptop has consulted several caches, asked a chain of servers around the world where "example.com" lives, opened a connection to a machine it has never met, checked that machine's cryptographic identity, asked for a page, and then asked for dozens more files the page needed, all while a whole fleet of machines on the other side decided who should answer.

When this goes well nobody thinks about it. When it goes badly, the complaints are vague: "the site is slow in Australia", "it works on my laptop but not on the office Wi-Fi", "some users get a certificate error", "the page is blank for three seconds". Each of those is really a statement about one specific step in this chain. An engineer who knows the chain can say which step, why, and what to do about it. One who does not is reduced to guessing.

That is why "what happens when you type a URL and press Enter?" is one of the most common interview questions in software engineering. It has no single right depth. The interviewer lets you give the overview, then points at a step ("tell me more about DNS", "how does the certificate check work?", "why is it slow from far away?") and keeps drilling. A strong answer shows the whole map, puts a latency cost on each step, and knows what real systems do to make each step cheaper.

This lesson is that map. Many of the steps have their own full topic later in this track, so here each gets a working explanation, enough to follow the whole journey, with a pointer to where it is taught in depth. You will first learn the unit of cost, the round trip, then walk the journey in order: parsing the URL, checking caches, finding the address with DNS, opening a TCP connection, securing it with TLS, sending the HTTP request, what happens on the server side, and how the browser turns the response into pixels. It ends with a worked time budget and the main techniques the web uses to shrink it.

The unit of cost: the round trip

A round trip is the time for a message to travel from your machine to another one and for a reply to come back. It is usually written RTT (round-trip time). It is set mostly by distance, because signals in fibre travel at roughly 200 km per millisecond (net1): a server in the same city might be 5 ms away, one across India 40 ms, one in the United States from India 200 to 250 ms.

Most steps in loading a page are ask-and-wait exchanges: the browser sends something and cannot continue until the answer arrives. So the most useful first estimate of load time is number of round trips × RTT. Bandwidth, the number of bits per second the link carries, matters much less for ordinary web pages, because the individual messages are small. This one idea explains most of web performance.

The short version, with an analogy

Imagine phoning a company you have never called. First you look up its number in a directory (DNS: turn the name into an IP address). You dial and wait for someone to pick up and say hello (TCP handshake: open a connection). You check they really are the company, and agree a code language so eavesdroppers learn nothing (TLS handshake: verify identity, set up encryption). You ask your question and wait for the answer (HTTP request and response). The answer says "you will also need forms A, B and C", so you ask for those too (subresources), and finally you assemble everything into something usable (rendering).

The analogy breaks in one useful way: phone calls wait for a person, but most of this waiting is pure distance. Even if the server answers instantly, each exchange still takes a full RTT.

The first four round trips, drawn

If the resolver has the answer cached and is close, DNS shrinks to a few milliseconds. If the browser already has an open connection to this server, TCP and TLS disappear entirely. A second visit to a site can therefore cost one round trip, or zero if the browser's cache already holds the page. That gap between cold and warm is the heart of web performance.

How the web makes this faster

Almost every performance technique you will hear about falls into two buckets. Fewer round trips: caching (answer locally), connection reuse (skip handshakes), TLS 1.3 and HTTP/3 (combine handshakes), and flattening chains of dependent requests. Shorter round trips: CDNs (content delivery networks) that answer from a server in your city rather than one on another continent. Keep those two buckets in mind as you read the details.

The body below walks the journey in the same order as the diagram, then adds the two phases the diagram leaves out: what happens inside the company's network after the request arrives, and how the browser turns the HTML into a page, which is where most of the remaining time goes.

1. Parsing the input

First the browser decides whether you typed a URL or a search. example.com looks like a hostname, so it becomes a URL; best pizza goes to the search engine. A URL (Uniform Resource Locator) has up to six parts. In https://shop.example.com:8443/cart?id=7#total:

  • Scheme https: which protocol to use. If you typed none, the browser assumes one.
  • Host shop.example.com: the name DNS will turn into an address.
  • Port 8443: usually omitted, in which case it defaults to 443 for https and 80 for http.
  • Path /cart and query ?id=7: sent to the server to say which resource you want.
  • Fragment #total: never sent to the server; the browser uses it to scroll or for client-side routing.

Next comes HSTS (HTTP Strict Transport Security). If this site is on the preload list built into the browser, or it previously sent a Strict-Transport-Security header that the browser remembered, the browser rewrites http:// to https:// right here, before sending anything. Without HSTS, a plain http:// request would go out unencrypted and rely on the server redirecting to HTTPS, and anyone on the network (say, a malicious café Wi-Fi) could intercept that first request. HSTS removes the window.

2. Checking caches before touching the network

The cheapest request is the one never sent. The browser checks, in order:

  • A service worker: a script the site may have installed in your browser on an earlier visit, which intercepts that site's requests and can answer them itself, for example from an offline copy.
  • The HTTP cache: stored responses from earlier visits. If a response came with a header such as Cache-Control: max-age=3600 and is less than an hour old, it is "fresh" and used without any request. If it is stale, the browser can send a cheap conditional request ("send it only if it changed since this version") and get back a tiny 304 Not Modified. HTTP caching rules are net7.
  • For Back and Forward navigation, the back/forward cache keeps the entire previous page in memory and restores it instantly.

For a typical top-level navigation to an HTML page, the HTML itself is usually not cached for long (sites want you to see fresh content), so we continue to the network. But the page's images, scripts and styles often are, which matters a lot later.

3. DNS: turning the name into an IP address

Routers only understand IP addresses (net1), so the browser must turn example.com into one. That is the job of DNS, the Domain Name System, a worldwide distributed directory (net6 covers it fully). The lookup passes through several caches, each checked before the next:

  1. The browser's own DNS cache.
  2. The operating system's stub resolver, a small DNS client with its own cache, which also reads the local hosts file (/etc/hosts, or C:\Windows\System32\drivers\etc\hosts) where you can hard-code names.
  3. A recursive resolver: a DNS server that does the actual lookup work for many users and caches results. It is usually provided by your ISP or company network, or is a public one such as 1.1.1.1 or 8.8.8.8.

If the recursive resolver has no cached answer, it walks the DNS hierarchy from the top:

A root server knows which servers handle each top-level domain (TLD) such as .com, .org or .in. The TLD servers know which authoritative name servers hold each domain's records. The authoritative server returns the actual answer: an A record (an IPv4 address) and, if asked, an AAAA record (an IPv6 address). Every answer carries a TTL in seconds, which says how long it may be cached. Be careful: this DNS TTL is a completely different thing from the IP header's TTL hop counter in net1; they only share a name.

Big sites add one more twist. Their authoritative DNS is often run by a CDN, which returns the address of an edge server near the resolver, so users in Mumbai and users in Paris get different answers for the same name. Other CDNs give every user the same address and let the network route them to the nearest location, a technique called anycast (net12).

Cost: a cached answer takes microseconds to a few milliseconds; a resolver cache miss adds one or more round trips to distant authoritative servers, occasionally hundreds of milliseconds. Unencrypted DNS is also visible to anyone on the network path; DoH (DNS over HTTPS) and DNS over TLS encrypt it.

4. Choosing an address and opening a TCP connection

DNS often returns several addresses, possibly both IPv4 and IPv6. Browsers use Happy Eyeballs (RFC 8305): start a connection attempt on the preferred address, usually IPv6, and if it has not succeeded within about 250 ms, start an IPv4 attempt in parallel and keep whichever connects first. That avoids long hangs on networks where one address family is quietly broken.

Before opening a new connection, the browser checks its connection pool: does it already have an open, idle connection to this same scheme, host and port (together called the origin)? If so, it reuses it and skips the next two steps entirely. This is one of the biggest wins on the web.

If not, the operating system opens a TCP connection (net4). It picks an ephemeral port for the client end, then does the three-way handshake: the client sends a SYN ("I want to connect; my byte numbering starts here"), the server replies SYN-ACK ("fine; here is mine"), and the client replies ACK. Under the hood, the packets travel exactly as in net1: the laptop sees that 203.0.113.9 is not on its local network, ARPs for its default gateway's MAC address if that is not cached, and sends the frames to the router. The handshake costs one round trip before any data flows (the client's ACK can carry the first data, so the next step starts immediately).

5. TLS: proving identity and setting up encryption

For HTTPS, the browser now runs a TLS handshake (Transport Layer Security; the full story is net9). TLS has two jobs. First, authentication: prove that this server really is example.com and not an impostor on the network. Second, encryption: agree secret keys that only the two ends know, so everything after is unreadable and tamper-proof to anyone in between.

In TLS 1.3, the current version, it goes like this:

  1. The client sends a ClientHello: the encryption methods it supports, its half of a key exchange (a key share), and the hostname it wants in a field called SNI (Server Name Indication), because one server IP often hosts many sites and needs to know which certificate to present. It also lists the HTTP versions it speaks, using ALPN (Application-Layer Protocol Negotiation), for example "h2, http/1.1".
  2. The server replies with its key share, its certificate, a signature proving it holds the certificate's private key, the chosen ALPN protocol, and a Finished message. A certificate is a document binding a public key to a hostname, signed by a certificate authority the browser already trusts.
  3. The browser checks that the certificate is valid, unexpired, issued for example.com, and chains up to a trusted authority. Both sides combine the key shares into the same secret keys, and the client sends its own Finished.

Cost: one round trip for TLS 1.3. The older TLS 1.2 needed two, so upgrading servers to TLS 1.3 removed a whole round trip from every new connection. On a repeat visit, session resumption lets the client skip the certificate work, and with 0-RTT it can even send the request inside its first message, at the price of a replay risk discussed in the deep section.

HTTP/3 changes this step. It runs over QUIC (net5), a transport built on UDP that has TLS 1.3 built into its own handshake, so the transport and encryption handshakes happen together in a single round trip instead of two. Browsers learn that a site supports HTTP/3 from a response header or a DNS record, so typically the first connection uses TCP and later ones switch to QUIC.

6. The HTTP request and response

Now the browser sends the actual HTTP request (net7 covers HTTP in depth):

GET / HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 ...
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=4f2a...

The first line has the method (GET, meaning "fetch"), the path and the version. Then come headers: the Host header names the site, because many sites share an IP; Accept-Encoding says the browser can decompress gzip and Brotli; Cookie carries any small pieces of state the site stored in the browser earlier, such as a login session. With HTTP/2 and HTTP/3 the same information is sent in a compact binary form, and many requests share one connection at once (net8).

The server answers with a status code (200 OK, 301 redirect, 404 not found, 500 server error), response headers such as Content-Type: text/html, Content-Encoding: br and caching rules, then the body. The time from sending the request to receiving the first byte of the response is called TTFB (time to first byte); it is one round trip plus however long the server takes to think.

7. The server side

From the outside, "the server" is one IP address. Inside a real company, the request passes through a chain of components, each with a job:

  • CDN edge: a server of a content delivery network in a city near the user. The browser's TCP and TLS handshakes actually happened with this machine, over a short RTT. If the edge has the response cached, it answers immediately. If not, it forwards the request to the site's own origin servers, over long-lived connections it keeps open.
  • Layer-4 load balancer: spreads incoming TCP connections across a pool of proxies using only addresses and ports (net10).
  • Layer-7 proxy or API gateway: terminates TLS (decrypts), reads the HTTP request, and routes it by host and path, for example /api/ to one service and everything else to another. It may also enforce rate limits and authentication.
  • Application server: your code. It may read a cache (such as Redis), query a database, or call other internal services, each a network call with its own latency.

The response flows back the same way, usually compressed (gzip or Brotli shrink HTML and JSON by 70 to 90 percent), and the edge may store a copy for the next user.

8. The browser turns bytes into a page

The HTML arrives, and the second half of the load begins. The browser:

  1. Parses the HTML into the DOM (Document Object Model), a tree of elements. It does this as bytes stream in, not after the whole file arrives.
  2. Discovers subresources: stylesheets, scripts, fonts, images. A background preload scanner skims ahead in the HTML to start these downloads early. Each goes through the same steps (cache, DNS, connection, request), but usually reuses the connection and DNS answer already obtained for the same origin.
  3. Builds the CSSOM from all the CSS. The browser will not draw anything until the CSS it knows about has arrived, because drawing unstyled content and then restyling it would flash. That makes CSS render-blocking.
  4. Runs JavaScript. A plain <script src> tag pauses HTML parsing until the script downloads and runs, because the script might change the document. Scripts marked defer or async do not block parsing.
  5. Computes layout (the size and position of every element), paints pixels, and composites layers onto the screen.

The page is slowest when resources form chains: the HTML references a script, which when it runs fetches an API, whose response names an image. Each link in the chain is at least one more round trip that could not start until the previous one finished. Performance work is mostly about finding and shortening these chains.

The CDN column assumes the page itself is not cacheable, so the edge still has to ask the origin; if it is cacheable, TTFB drops to about 40 ms. And all of this is only the first byte of HTML. A typical page then needs its render-blocking CSS and scripts, each at least one more round trip, and large files take several round trips because a new TCP connection starts slowly (slow start: it may send only about 10 packets, roughly 14 KB, before waiting for acknowledgements, then doubles each round trip; net4). So real first loads on distant connections run to one or two seconds even when every server is fast.

Connection reuse and coalescing

Browsers keep idle connections open per origin for a while, and HTTP/2 and HTTP/3 multiplex many requests over one connection, so a page with 80 resources from one origin needs one handshake rather than 80. HTTP/2 also allows connection coalescing: if static.example.com resolves to the same IP as www.example.com and the certificate on the existing connection covers both names, the browser reuses that connection for both. This is why consolidating assets onto fewer origins, the opposite of the old HTTP/1.1 advice to "shard" across many hostnames, is now faster. For backend engineers the same lesson applies to API clients: create one HTTP client object and reuse it, because a new client per request pays DNS, TCP and TLS every time, which for a call to an LLM API across an ocean can add hundreds of milliseconds per request.

0-RTT and replay

With TLS 1.3 resumption (or QUIC), a client that has connected before can send its first request along with the ClientHello, using keys derived from the previous session, so the request costs zero extra handshake round trips. The catch is that an attacker who records that first flight can resend it, and the server cannot tell the copy from the original, because no fresh exchange has happened yet. So 0-RTT data must only carry requests that are safe to repeat (idempotent, like a GET that does not change state). Servers and CDNs typically accept 0-RTT only for such requests and may add replay caches.

TCP slow start and the "14 KB rule"

A fresh TCP connection does not know how much the path can carry, so it starts with an initial congestion window of 10 segments (RFC 6928), about 14 KB, and grows it each round trip that goes well (net4 explains the mechanism). The practical consequence: the first 14 KB of the HTML response arrive in the first round trip, the next 28 KB in the second, and so on. If the first 14 KB contain the critical CSS and the top of the page, the browser can start rendering one round trip earlier. It also explains why a CDN's pre-warmed connections to the origin matter: they are already past slow start.

Resource hints and Early Hints

Because chains of dependent requests dominate, browsers accept hints that let pages start work before it is discovered. <link rel="preconnect" href="https://api.example.com"> does DNS, TCP and TLS for an origin the page will need, in parallel with other work. dns-prefetch does only the DNS part. <link rel="preload"> fetches a specific critical file (a font, a hero image) early. The HTTP 103 Early Hints status (RFC 8297) lets a server or CDN send those hints before the final response, while the application is still thinking, so the browser uses the server's think time to warm up connections and fetch assets.

Privacy along the path

Each step leaks something unless protected. Plain DNS reveals every hostname to the network and to the resolver; DoH and DNS over TLS encrypt the query. The TLS ClientHello carries the hostname in the SNI field in plaintext; Encrypted Client Hello, published as RFC 9849 in 2026, encrypts it using a public key the site advertises in DNS. The destination IP address cannot be hidden, although on large CDNs one IP serves thousands of sites. Enterprises that filter traffic by reading DNS and SNI lose that visibility, which is an active tension between privacy and network control.

Happy Eyeballs, in more detail

RFC 8305 recommends asking for AAAA and A records in parallel, waiting up to about 50 ms for the AAAA answer if the A answer comes first, then trying addresses in an interleaved order, starting a new attempt every 250 ms or so while earlier ones are still pending. The first connection to complete wins and the others are cancelled. The mechanism turns "IPv6 is broken on this hotel Wi-Fi" from a 20-second hang into a quarter-second delay, and it explains puzzles such as a server seeing clients connect over IPv4 even though both sides support IPv6.

API clients are the same journey without the rendering

A backend service calling another service, or a Python script calling an LLM provider, makes exactly the same steps 3 to 7: DNS, TCP, TLS, HTTP, server-side chain. The differences are in what you control: you choose DNS caching behaviour (some runtimes cache DNS forever, which breaks failovers; others never cache), connection pool sizes, timeouts for each phase, and HTTP version. Many "the API is slow" investigations end at "we were creating a new connection per request" or "our connect timeout was the operating system default of two minutes".

How each step fails in production

  • DNS: a record changed but clients still use the old address because resolvers and runtimes cache it for its TTL, or longer if they ignore TTLs. Before a migration, teams lower the TTL (say from 3,600 to 60 seconds) a day in advance. Resolver outages make everything fail at once with "could not resolve host", even though every server is healthy.
  • TCP connect: firewalls silently drop packets and clients hang until a timeout; a server's queue of pending connections overflows under load and new connections are dropped; clients that open a new connection per request run out of ephemeral ports.
  • TLS: expired certificates are the classic self-inflicted outage, sudden and total at a predictable minute. Others include a server sending an incomplete certificate chain (works in browsers that cache intermediates, fails in API clients) and hostnames not covered by the certificate after a DNS change.
  • Server side: a slow database query or downstream service raises TTFB; proxies return 502 Bad Gateway when the backend is unreachable and 504 Gateway Timeout when it is too slow; a CDN misconfiguration can cache the wrong thing.
  • Browser: a third-party script (analytics, ads, chat widget) that is render-blocking or slow delays the whole page, and if its origin is down the page can hang.

Seeing where the time goes

In the browser, the DevTools Network panel shows each request's timing split into queueing, DNS lookup, initial connection, SSL (TLS), waiting (TTFB) and content download, and the waterfall view makes dependency chains visible. For real users, the Navigation Timing and Resource Timing APIs expose the same phases in JavaScript; real-user monitoring (RUM) tools collect them from every visitor and let you slice by country, network type and device. Google's Core Web Vitals summarise the user experience: Largest Contentful Paint (good is 2.5 s or less), Interaction to Next Paint (200 ms or less) and Cumulative Layout Shift (0.1 or less), each measured at the 75th percentile of page loads. On the server, the Server-Timing response header can expose backend phases to the browser's tools, and CDN dashboards report cache hit ratio and origin latency. From the command line, curl -w prints DNS, connect, TLS and TTFB times for one request, which the lab uses.

War story: when the CDN is the single point of failure

On 8 June 2021, one Fastly customer pushed a valid configuration change that triggered a latent bug introduced in a software deployment on 12 May. Within a minute, about 85 percent of Fastly's network was returning errors, and major news sites, government sites and shops went down together. Fastly detected it within a minute and recovered 95 percent of the network within 49 minutes. In terms of this lesson: DNS, TCP and TLS all succeeded, because they terminated at healthy edge machines; the failure was in step 7, the edge's own request processing, so users saw HTTP 503 errors rather than connection failures. The lessons teams drew were multi-CDN setups for critical sites and a clear plan for bypassing the CDN in an emergency.

War story pattern: caching the private page

A recurring class of incident is a CDN or proxy caching a personalised page (an account page, a basket) and serving it to other users, because the response lacked Cache-Control: private or the cache key ignored the session cookie. It usually happens during an emergency configuration change, for example turning on aggressive caching to survive a traffic spike. Step 2's caching rules and step 7's edge are the same mechanism seen from both ends, and a bug in either leaks data.

Knobs worth knowing

DNS TTLs (short before migrations, longer for stability); enabling TLS 1.3 and HTTP/3 at the edge; keep-alive and idle timeouts on load balancers, which must be longer than the backend's to avoid the proxy reusing a connection the backend just closed; connection pool sizes and per-phase timeouts in API clients; Cache-Control headers per response type; and preconnect hints for critical third-party origins.

Fifteen minutes. You will time every step of a real page load, watch DNS walk the hierarchy, and see the TLS handshake's choices. Linux, macOS or WSL shown; on Windows PowerShell use curl.exe (not the curl alias) and install dig via WSL or use Resolve-DnsName.

  1. Time each phase with curl. Run: 
    curl -s -o /dev/null https://www.wikipedia.org \
  -w 'dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}  total %{time_total}\n'
    The numbers are cumulative seconds since the start. Look for: the gap between dns and tcp is roughly one RTT (the TCP handshake); the gap between tcp and tls is roughly one RTT for TLS 1.3; the gap from tls to ttfb is one RTT plus server time. Run it twice: the second dns figure usually shrinks because the answer is now cached by your resolver.
  2. Compare near and far. Repeat step 1 for a site hosted far from you (for example a small university site on another continent) and one served by a big CDN. Look for: the CDN-served site's TCP and TLS gaps are a few milliseconds; the distant one's are tens or hundreds. That difference is RTT, not bandwidth.
  3. Walk DNS yourself. dig +trace www.wikipedia.org. Look for: the first block lists root servers (a.root-servers.net and friends), the next lists the .org servers, then Wikipedia's authoritative servers, and finally the answer. That is the diagram's steps 2 to 4, done by your own machine instead of a resolver.
  4. See caching and TTL. Run dig www.wikipedia.org twice, ten seconds apart, and compare the number in the second column of the answer. Look for: it counts down: that is the remaining cache lifetime at your resolver.
  5. Inspect the TLS handshake. openssl s_client -connect www.wikipedia.org:443 -servername www.wikipedia.org -alpn h2,http/1.1 </dev/null. Look for: the certificate chain (subject and issuer lines), "Protocol: TLSv1.3", and "ALPN protocol: h2", meaning the server agreed to HTTP/2. The -servername flag is the SNI.
  6. Watch a full page in DevTools. Open a new private window, open DevTools (F12), go to the Network tab, tick "Disable cache", and load a news site. Hover the Waterfall bar of the first request. Look for: DNS Lookup, Initial connection, SSL, Waiting for server response (TTFB) and Content Download. Then look at the waterfall's shape: requests that start only after an earlier one finishes are dependency chains. Right-click a column header and enable "Protocol" to see which requests used h2 or h3.

Stretch: in DevTools, set network throttling to "Slow 4G" and reload. The page slows far more than the drop in bandwidth alone would suggest, because throttling also adds round-trip latency, and the page is made of round trips.

Diagnose: slow in Australia

An interviewer asks: "The page takes 3 seconds to load for users in Australia but 400 ms in the US. The origin is in us-east-1 (Virginia). Walk me through why, using the URL walk-through, and what you would do."

Answer
  • Round trips dominate. Sydney to US East is about 200 ms RTT. A cold visit pays DNS (possibly a round trip to authoritative servers far away), TCP (1 RTT), TLS (1 RTT, or 2 with TLS 1.2), then the HTML request (1 RTT plus server time): close to 1 second before the first byte. Then the page's render-blocking CSS and scripts, fonts and API calls each add round trips, often in chains, and larger files need extra round trips because new connections start slowly (TCP slow start). Three seconds is entirely plausible with a perfectly fast server.
  • Measure first. Look at real-user timing data sliced by country, or run a synthetic test from Sydney, and read the waterfall to confirm where the time goes: handshakes, TTFB, or dependency chains.
  • Fixes, in order of impact:
    • Put a CDN in front. TCP and TLS then terminate at a Sydney edge about 10 ms away; static assets are served from its cache; dynamic requests travel over the edge's warm, long-lived connections to the origin, paying one long round trip instead of three or four.
    • Enable TLS 1.3 and HTTP/3 at the edge to remove handshake round trips, with resumption for repeat visitors.
    • Shorten the critical path: inline critical CSS, defer scripts, preconnect to API and font origins, and remove waterfalls where an API call waits for JavaScript that waits for CSS.
    • Cache API responses at the edge where they are not personalised; if heavy dynamic traffic remains, add a read replica or deploy the application in an Asia-Pacific region.
Estimate: a chatty page

A single-page app loads like this on a fresh visit: HTML (15 KB), then one JavaScript bundle (300 KB compressed) referenced by the HTML, which when it runs calls /api/me, and only after that returns calls /api/feed. All on one origin, RTT 80 ms, TLS 1.3, each API call takes 40 ms of server time. Ignoring rendering and DNS, how long until the feed data arrives, and what is the single biggest improvement?

Answer

Count round trips in order. TCP 80 ms, TLS 80 ms, HTML request 80 ms: 240 ms. The 300 KB bundle on the same, still-young connection: slow start sends about 14 KB, then 28, 56, 112, 224 KB in successive round trips, so roughly five round trips, 400 ms, bringing us to 640 ms. /api/me: 80 + 40 = 120 ms, reaching 760 ms. /api/feed: another 120 ms, reaching about 880 ms, before any rendering or JavaScript execution time.

The biggest improvement is breaking the chain: have the server include the user and feed data in the initial HTML (server-side rendering or an inline data blob), which removes both API round trips and lets the page show content without waiting for the bundle. Next best: fetch /api/me and /api/feed in parallel if the second does not truly depend on the first, and split the bundle so the critical part is small.
