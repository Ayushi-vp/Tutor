IP, the layer below TCP, makes only one promise: it will try to deliver each packet. In practice packets get dropped when a router's queue is full, corrupted by a noisy link, duplicated by a confused device, or delivered out of order because they took different paths. Now imagine writing a database client, a web browser or a file-sync tool directly on top of that. Every one of them would need code to number its data, notice gaps, ask for resends, put things back in order, and avoid sending faster than the other side or the network can take. Every one would get it subtly wrong.

TCP, the Transmission Control Protocol, is that code, written once and built into every operating system. It gives programs a simple illusion: a reliable pipe of bytes between two programs, where whatever goes in one end comes out the other, complete and in order. Almost everything you use runs on it: HTTP/1.1 and HTTP/2, database protocols, SSH, message brokers, gRPC.

So why study its internals rather than just trust the illusion? Because the illusion leaks, and the leaks show up as exactly the problems backend engineers get paged for. A new connection is slow for its first few round trips, so a service that opens a connection per request is slow and eventually runs out of ports. A tiny amount of packet loss can multiply tail latency. A connection can silently die in a NAT while both ends think it is alive. A load balancer can return 502 errors because two idle timeouts are set in the wrong order. Small writes can mysteriously take 40 ms each. Every one of these is explained by a specific TCP mechanism.

This lesson builds the mechanisms one at a time: the byte-stream model and the connection's identity, the header, the handshake, sequence numbers and acknowledgements, how loss is detected and repaired, flow control, congestion control and what they mean for throughput, the small-write problem, closing and TIME_WAIT, head-of-line blocking, and keepalive. The deep, production and lab sections then connect each one to real failures and to tools you can use to see them.

The promise: a reliable byte stream

A program using TCP opens a connection to another program and gets a socket, a handle it can write bytes to and read bytes from. TCP promises that the bytes read at one end are exactly the bytes written at the other, in the same order, with nothing missing or duplicated, or else the connection reports an error. It works in both directions at once.

Note what it does not promise: it is a stream of bytes, not of messages. If you write "HELLO" and then "WORLD", the other side might read "HELLOWORLD" in one go, or "HEL" then "LOWORLD". Programs on top of TCP must mark where their messages start and end themselves.

The analogy: posting a book one numbered page at a time

You want to send a friend a whole book, but the postal service only takes single pages and sometimes loses or shuffles them. So you number every page. Your friend reassembles them in order and regularly posts back a note saying "I have everything up to page 57". If a note stops advancing, you resend the page they are missing. Your friend also tells you how much desk space they have left, so you do not bury them (flow control). And you notice that when you send too many pages at once, more of them get lost at a crowded sorting office, so you start with a few and send more only while things go well (congestion control). Before the first page, you exchange a short "ready? ready!" (the handshake), and at the end, "that's all from me" (closing).

The analogy breaks in one important way: TCP numbers bytes, not pages, so the notes say "I have every byte up to byte 57,000".

The life of a connection, drawn

Six mechanisms, one sentence each

  • Handshake: SYN, SYN-ACK, ACK agree to talk and exchange starting byte numbers; one round trip.
  • Sequence numbers and ACKs: every byte is numbered, and the receiver keeps reporting the next byte it expects.
  • Retransmission: data not acknowledged in time, or clearly missing, is sent again.
  • Flow control: the receiver advertises how much free buffer it has; the sender stays within it.
  • Congestion control: the sender starts cautiously, speeds up while things go well and backs off on loss.
  • Teardown: each side sends FIN when it is done; a RST aborts instantly.

All of this lives in the operating system kernel, not in your program. Your code calls connect(), send(), recv() and close(); the kernel runs the state machine, keeps the buffers, sets the timers and decides when to send each segment. That is why so many TCP problems are fixed with socket options and kernel settings rather than application logic.

With those six in mind, every behaviour in the rest of the lesson is a detail of one of them.

1. Identity: sockets, ports and the 4-tuple

A server program listens on a port, say 443, using a listening socket. When a client connects, its operating system picks an ephemeral port for the client end (Linux uses 32768 to 60999 by default, about 28,000 ports). The connection is then identified by its 4-tuple: client IP, client port, server IP, server port. Every incoming segment is matched to its connection by this 4-tuple, which is why one server port can serve millions of connections (they differ in client IP and port), and why a single client can only have about 28,000 simultaneous connections to one server IP and port (they differ only in client port).

Because TCP is a byte stream, applications must do their own framing. HTTP/1.1 uses a blank line to end headers and a Content-Length header (or chunked encoding) to mark the body's end; many binary protocols put a 4-byte length in front of each message. A common beginner bug is to call recv() once and assume it returned one complete message. It returns whatever bytes have arrived, which may be part of a message or several messages.

2. The TCP header

Each segment carries a header of at least 20 bytes. The fields that matter for understanding behaviour:

FieldSizeWhat it is for
Source and destination port16 bits eachwhich programs
Sequence number32 bitsnumber of the first data byte in this segment
Acknowledgement number32 bitsnext byte expected from the other side (valid if ACK flag set)
FlagsbitsSYN (open), ACK, FIN (done sending), RST (abort), PSH (deliver now)
Window16 bitsfree receive buffer, in bytes (scaled, see flow control)
Checksum16 bitsdetects corruption of header and data
Options0-40 bytesMSS, window scale, SACK, timestamps, negotiated in the handshake

In packet captures, flags are abbreviated: [S] is SYN, [S.] is SYN-ACK (the dot means ACK), [.] is a plain ACK, [P.] is data with PSH and ACK, [F.] is FIN, [R] is RST.

3. The three-way handshake, and the queues behind it

Each side picks a random initial sequence number (ISN). The client sends a SYN carrying its ISN (1000 in the diagram) and its options, such as its MSS and whether it supports window scaling and SACK. The server replies with a SYN-ACK carrying its own ISN (5000) and ack=1001, meaning "I got your SYN; your data starts at 1001". The client replies with an ACK, ack=5001. Why three messages and not two? Each side must know the other received its ISN. After two messages the client knows the server has its number, but the server does not yet know the client has the server's number; the third message confirms it. Random ISNs make it hard for an off-path attacker to inject forged segments, and make it unlikely that delayed packets from an old connection fit the new one.

Inside the server's kernel there are two queues per listening socket. A half-open connection (SYN received, SYN-ACK sent, final ACK not yet received) sits in the SYN queue. Once the ACK arrives it moves to the accept queue (the backlog), where it waits for the application to call accept(). If the application is too slow and the accept queue fills, the kernel starts dropping new SYNs or final ACKs, and clients see slow connects or timeouts even though the server looks healthy. A SYN flood attack fills the SYN queue with half-open connections from spoofed addresses; the defence is SYN cookies, where the server encodes the connection's details into the sequence number of its SYN-ACK instead of storing them, and reconstructs them when (if) the final ACK arrives. Linux enables SYN cookies automatically when the queue overflows.

Cost: one round trip before any data. Combined with TLS on top (one more round trip for TLS 1.3, net9), this is why new connections are expensive and why connection reuse matters so much (net2).

4. Sequence numbers, ACKs and retransmission

After the handshake, each segment's sequence number says where its bytes belong in the stream, and each ACK says "I have every byte before this number". ACKs are cumulative: ack=7801 acknowledges everything up to 7800 at once, so one lost ACK is harmless as long as a later one arrives.

How does the sender know data was lost? Two ways.

Timeout. The sender keeps measuring round-trip times and computes a retransmission timeout (RTO): roughly the smoothed RTT plus four times its variation, with a minimum. The standard initial RTO before any measurement is 1 second, and Linux never goes below 200 ms. If the oldest unacknowledged segment is not acknowledged within the RTO, it is resent and the RTO doubles for the next attempt (exponential backoff). Timeouts are slow, especially in a data centre where the real RTT might be 0.1 ms but the minimum RTO is 200 ms, 2,000 times longer.

Duplicate ACKs. When a segment goes missing but later ones arrive, the receiver cannot advance its cumulative ACK, so each later segment triggers another ACK with the same number, a duplicate ACK. Three duplicates strongly suggest a loss rather than mere reordering, so the sender immediately resends the missing segment: fast retransmit. With the SACK (selective acknowledgement) option, the receiver also lists the byte ranges it has beyond the gap, so the sender resends only what is actually missing.

Note what the receiver's kernel does meanwhile: it holds bytes 3000 to 5999 in its buffer but cannot hand them to the application, because the application must read the stream in order and byte 2000 is missing. That waiting is head-of-line blocking, and section 9 returns to it.

5. Flow control: protecting the receiver

The receiver's kernel holds incoming data in a receive buffer until the application reads it. Every segment the receiver sends carries a receive window (rwnd): how many more bytes it can currently accept. The sender must never have more unacknowledged bytes in flight than that. If the application stops reading, the buffer fills, the window shrinks to zero, and the sender pauses, periodically probing until the window reopens. In a packet capture a "zero window" is therefore a signal that the receiving application is slow, not the network.

The window field is only 16 bits, so without help it caps at 65,535 bytes. That is far too small for fast, long paths, because of the bandwidth-delay product (BDP): to keep a path full you need bandwidth × RTT bytes in flight. For 1 Gbit/s and 100 ms that is 125,000,000 bytes/s × 0.1 s = 12.5 MB. The window scaling option, agreed in the handshake, multiplies the window field by a power of two (up to 214), allowing windows up to about 1 GB. Linux also auto-tunes buffer sizes per connection. If a middlebox strips the window scale option from the SYN, connections silently fall back to 64 KB windows and long-distance transfers crawl, a classic mystery.

6. Congestion control: protecting the network

Flow control stops the sender overwhelming the receiver, but not the routers in between. In 1986 the early internet suffered congestion collapse: senders retransmitted into already-full queues, making them fuller, and useful throughput between some sites dropped by a factor of about a thousand. The fix, added to TCP by Van Jacobson, is that each sender limits itself with a congestion window (cwnd), its own estimate of how much the network can take. The sender may have at most min(cwnd, rwnd) bytes unacknowledged.

Nobody tells the sender the right cwnd; it discovers it by probing:

  • Slow start. A new connection starts with an initial window of 10 segments (about 14 KB, standardised in RFC 6928). Every ACK increases cwnd by the amount acknowledged, which in effect doubles it every round trip: 10, 20, 40, 80 segments. Despite its name, this is fast growth, but it starts small.
  • Congestion avoidance. Once cwnd reaches the slow start threshold (ssthresh), growth becomes additive: roughly one extra segment per round trip.
  • Reacting to loss. Loss is taken as the sign of congestion. After fast retransmit, the classic algorithm halves cwnd and continues (fast recovery). After a timeout, it assumes things are badly wrong: ssthresh becomes half the window and cwnd drops to a small value, restarting slow start.

This rule, grow by one per round trip and halve on loss, is called AIMD (additive increase, multiplicative decrease). It is what makes many connections sharing a bottleneck converge towards fair shares. Plotted over time, it gives the famous sawtooth:

Real stacks use refinements. CUBIC, the default on Linux and Windows, grows the window along a cubic curve based on time since the last loss, which recovers quickly on fast long-distance paths while staying loss-based. BBR, from Google, takes a different approach: it continuously estimates the bottleneck bandwidth and the minimum RTT and paces its sending to match them, instead of pushing until something breaks. The deep section compares them.

7. What this means for throughput and latency

Put flow and congestion control together and you get the most useful formula in this lesson: a single connection can deliver at most one window per round trip, so

throughput ≤ min(cwnd, rwnd) / RTT

Three worked consequences. A connection limited to a 64 KB window over a 100 ms path gets at most 65,535 × 8 / 0.1 ≈ 5.2 Mbit/s, even on a 10 Gbit/s link. A brand-new connection sending a 200 KB response needs about four round trips (14 + 28 + 56 + 112 KB), so 400 ms at 100 ms RTT, regardless of bandwidth. And loss keeps cwnd small: the well-known approximation by Mathis and colleagues says loss-based TCP achieves about MSS / (RTT × √p) for loss rate p, so 1% loss on a 100 ms path limits a connection to roughly 1,460 × 8 / (0.1 × 0.1) ≈ 1.2 Mbit/s. That is why lossy long-distance links hurt so much, and why bulk transfer tools open several connections in parallel.

8. Small writes: Nagle and delayed ACKs

Two old optimisations interact badly. Nagle's algorithm, on the sender, says: if there is unacknowledged data in flight, do not send a new small segment; wait until the ACK arrives or a full segment's worth accumulates. It prevents programs that write one byte at a time (early terminals) from flooding the network with 41-byte packets. Delayed ACK, on the receiver, says: do not acknowledge immediately; wait briefly (up to about 40 ms on Linux) in case there is data to send back that the ACK can ride along with.

Now take a client that writes a request as two small pieces, a header then a body. The header goes out. The body is small and the header is unacknowledged, so Nagle holds the body. The server has received only half a request, so it has nothing to reply with and delays its ACK. Both wait until the delayed-ACK timer fires, about 40 ms later. Every request pays 40 ms for nothing. The standard fixes: write each complete message in one call, and set the TCP_NODELAY socket option, which turns Nagle off. Most HTTP clients, database drivers and RPC frameworks set it by default.

9. Closing: FIN, RST, TIME_WAIT and CLOSE_WAIT

A TCP connection is two independent byte streams, one per direction, and each is closed separately. When a side has nothing more to send, it sends a FIN; the other side ACKs it and may keep sending (a half-close) until it too sends a FIN. Usually this is four segments, as in the lifecycle diagram, sometimes three when the second FIN rides on the ACK. A RST instead aborts immediately and discards buffered data; it is sent for segments to unknown connections (a closed port gives "connection refused"), when a process dies with unread data, or by middleboxes killing idle connections.

Along the way each socket passes through named states you will see in ss or netstat. Two matter in practice:

  • TIME_WAIT: the side that sent the first FIN, after the exchange completes, waits for twice the maximum segment lifetime (MSL). Linux hard-codes this at 60 seconds. It exists for two reasons: if its final ACK was lost, the peer will resend its FIN and this side must still be able to answer; and it prevents a new connection with the same 4-tuple from receiving delayed segments of the old one. The cost is that the 4-tuple, and so for a client the ephemeral port to that destination, stays reserved for 60 seconds.
  • CLOSE_WAIT: the peer sent FIN, the kernel acknowledged it, and now it is waiting for the local application to call close(). Sockets stuck here are an application bug, a leaked connection.

The TIME_WAIT arithmetic is worth doing once. A client opening and closing 3,000 connections per second to one server, closing first each time, keeps 3,000 × 60 = 180,000 sockets in TIME_WAIT, each needing a distinct ephemeral port to that destination, but only about 28,000 exist. New connections fail with "Cannot assign requested address". The fix is not to fight TIME_WAIT but to stop opening a connection per request: use a connection pool with keep-alive.

10. Head-of-line blocking

Because TCP delivers a single ordered stream, a lost segment stops delivery of all later bytes until the retransmission arrives, as in the fast-retransmit diagram. For one file download that is fine. But HTTP/2 (net8) sends many independent requests over one TCP connection, interleaved, and TCP does not know they are independent: a single lost packet belonging to an image stalls a JSON response that arrived intact behind it. On networks with noticeable loss this can make HTTP/2 slower than HTTP/1.1 with several connections. It is the main reason QUIC (net5) implements its own streams on top of UDP, so each stream is ordered separately.

11. Keepalive and detecting a dead peer

If a peer's machine loses power or its network path dies, it sends nothing, not even a RST. What happens next depends on whether your side is sending. If the connection is idle, TCP sends nothing and notices nothing, indefinitely. If you are sending, unacknowledged data is retransmitted with exponential backoff, and Linux's default (tcp_retries2 = 15) gives up after about 924 seconds, roughly 15 minutes.

TCP keepalive is an optional probe on idle connections. On Linux it defaults to the first probe after 2 hours of idleness, then 9 probes 75 seconds apart before declaring the connection dead. Those defaults are far longer than the idle timeouts of the NATs, firewalls and load balancers in between (350 seconds for an AWS NAT gateway, 60 seconds by default for an AWS Application Load Balancer), which silently drop the connection. So long-lived connections, such as database pools, message consumers and WebSockets, need tuned keepalive intervals, a TCP_USER_TIMEOUT to bound how long sent data may stay unacknowledged, or, best, application-level heartbeats.

Retransmission timeouts and tail latency in data centres

Inside a data centre RTTs are tens to hundreds of microseconds, but Linux's minimum RTO is 200 ms. So any loss that cannot be repaired by fast retransmit, because there were not three later segments to generate duplicate ACKs, turns a sub-millisecond request into a 200 ms one. This happens most for the last segments of a response (nothing follows them) and for small responses of one or two segments. The p99 latency of a service is therefore often dominated by rare timeouts, not by average speed. Modern Linux mitigates this with tail loss probes, which resend the last segment after about two RTTs of silence to provoke a SACK revealing the loss, and RACK, which detects loss by timing (a segment is lost if one sent later was acknowledged and enough time has passed) rather than by counting duplicate ACKs. A related pathology is incast: a request fans out to many servers that all answer at once into one switch port, overflowing its buffer and causing synchronised timeouts.

Bufferbloat, BBR and ECN

Loss-based algorithms like CUBIC only back off when a router drops packets, which happens when its buffer is full. Routers with large buffers therefore fill up with queued packets first, adding tens or hundreds of milliseconds of delay for everyone sharing the link: bufferbloat. BBR avoids this by modelling the path: it tracks the highest delivery rate seen recently (the bottleneck bandwidth) and the lowest RTT seen (the propagation delay), paces packets at the bandwidth, and keeps roughly one BDP in flight, periodically probing for more bandwidth and draining queues to re-measure the minimum RTT. It keeps throughput high on lossy long-distance paths, where CUBIC mistakes random loss for congestion. Its early versions could be unfair to CUBIC flows and caused extra loss in shallow buffers; later versions react to loss and ECN as well. ECN (Explicit Congestion Notification) lets routers mark packets as "congestion experienced" instead of dropping them, and the receiver echoes the mark to the sender, which slows down without losing data; data-centre variants such as DCTCP react in proportion to the fraction of marked packets to keep queues tiny.

TCP Fast Open and why the handshake is hard to shorten

TCP Fast Open lets a client that has connected before send data in its SYN, using a cookie from the earlier connection, saving a round trip. It works, but deployment stalled: some middleboxes drop SYNs carrying data or unknown options, so clients had to detect and fall back, and the saving applied only to repeat connections. It is a textbook case of the ossification described in net1, and one reason the industry moved to QUIC, where the transport runs in user space over UDP and can evolve without middlebox permission.

Accept queues, SO_REUSEPORT and connection storms

A listening socket's accept queue is bounded by the application's backlog argument and the system-wide net.core.somaxconn. When a service restarts, or when clients reconnect en masse after an outage, thousands of SYNs arrive together, the queue overflows and connects time out, which makes clients retry and amplifies the storm. Mitigations are larger backlogs, jittered client reconnection with exponential backoff, and SO_REUSEPORT, which lets several processes or threads each open their own listening socket on the same port with separate queues, with the kernel spreading new connections across them by hashing the 4-tuple.

Slow start after idle, and warm connections

By default Linux resets a connection's congestion window after it has been idle for about one RTO, on the theory that network conditions may have changed. For servers holding long-lived connections that send bursts, such as HTTP/2 connections to browsers or connections between a CDN edge and an origin, this throws away the "warmth" that made connection reuse valuable, so each burst restarts slow start. Many operators disable tcp_slow_start_after_idle on such servers. It is a good example of a default designed for the general internet being wrong for a specific workload.

Why ISNs and RSTs are security-relevant

If an attacker can guess a connection's 4-tuple and the current sequence number, they can inject data or reset the connection without being on the path. Randomised ISNs, per-connection sequence offsets and the requirement that a RST's sequence number be exactly the expected one (answering near-misses with a "challenge ACK") make this impractical, but long-lived, predictable connections, such as BGP sessions between routers, historically needed extra authentication for this reason.

Characteristic failures and their fingerprints

  • Ephemeral port exhaustion: "Cannot assign requested address" (EADDRNOTAVAIL) on connect, with tens of thousands of sockets in TIME_WAIT towards one destination (ss -tan state time-wait | wc -l). Cause: a connection per request. Fix: pooling and keep-alive.
  • CLOSE_WAIT leak: CLOSE_WAIT count grows steadily until the process hits its file-descriptor limit ("Too many open files"). Cause: code paths that never close sockets. Fix the code; restarting only resets the clock.
  • Accept queue overflow: clients see slow or failed connects under load while the server's CPU looks fine. ss -ltn shows the listening socket's Recv-Q (current queue) near its Send-Q (the limit); nstat -az TcpExtListenOverflows TcpExtListenDrops counts the drops. Fix: faster accept loops, bigger backlog, more workers.
  • Idle-timeout mismatches: intermittent resets or 502s after quiet periods, from a NAT, firewall or load balancer dropping idle connections before the endpoints do. AWS documents that if the backend closes idle connections before its Application Load Balancer (default 60 s idle timeout), the balancer may send a request on a connection the backend just closed and return 502. A notorious instance is Node.js's default server keepAliveTimeout of 5 seconds behind a 60-second balancer. Fix: backend idle timeout longer than the balancer's.
  • Retransmissions and loss: rising p99 latency with normal averages; nstat retransmission counters (TcpRetransSegs) and per-socket retrans in ss -ti climb. Look for a bad link, an overloaded middlebox, or incast.
  • 40 ms stalls: request latency clustering at about 40 ms above expected, typically a client writing messages in pieces without TCP_NODELAY.
  • Zero windows: in captures, the receiver advertises window 0 and the sender probes; the receiving application is not reading fast enough, often a slow consumer or a blocked event loop.

Tools

ss is the Swiss army knife: ss -s for a summary by state, ss -tan for all connections, and ss -ti for per-connection internals including rtt, cwnd, retrans, rcv_space and the congestion algorithm. nstat shows system-wide TCP counters. tcpdump and Wireshark show the actual segments; Wireshark's "TCP analysis" flags retransmissions, duplicate ACKs, zero windows and out-of-order segments automatically, and its stream graphs plot sequence numbers over time, which makes slow start and stalls visible. Load balancer metrics such as backend connection errors and target resets, and NAT gateway metrics such as idle timeouts, surface the middlebox side.

Knobs, and when to touch them

Per socket: TCP_NODELAY for request/response protocols; keepalive idle, interval and count (TCP_KEEPIDLE, TCP_KEEPINTVL, TCP_KEEPCNT) below middlebox timeouts; TCP_USER_TIMEOUT to bound dead-peer detection. System-wide on Linux: net.ipv4.ip_local_port_range, net.core.somaxconn, tcp_rmem/tcp_wmem maxima for high-BDP paths, tcp_congestion_control (for example bbr on internet-facing servers), and tcp_slow_start_after_idle. Leave tcp_tw_reuse at its default unless you understand it (it is safe only for outgoing connections), and never look for tcp_tw_recycle, which broke clients behind NAT and was removed from Linux in version 4.12. The most effective "knob" is almost always in the application: reuse connections, set timeouts, and write whole messages.

War story pattern: the 502s every few minutes

A team moves a Node.js API behind an AWS Application Load Balancer. Under steady traffic everything is fine, but a small percentage of requests fail with 502 during quieter periods, with no errors in the application logs. The balancer keeps idle backend connections for up to 60 seconds; Node closes them after 5. Occasionally the balancer picks a connection at the exact moment Node's FIN is in flight, sends a request, gets a RST, and returns 502. The application never saw the request, so its logs are clean. Raising server.keepAliveTimeout (and headersTimeout) above 60 seconds makes the errors disappear. The same shape recurs with any pair of proxies whose idle timeouts are in the wrong order.

Twenty minutes on Linux, macOS or WSL (the ss commands are Linux/WSL only). You will watch a handshake and teardown, see a RST, prove TCP is a byte stream, and read a live connection's congestion window.

  1. Watch a whole connection. In terminal 1 start a server: python3 -m http.server 8000. In terminal 2 start a capture: sudo tcpdump -i lo -nn 'tcp port 8000' (on macOS use -i lo0). In terminal 3: curl -s localhost:8000 > /dev/null. Look for: [S], [S.], [.] (the handshake), [P.] segments carrying the request and response with seq and ack numbers, then [F.] segments closing each direction. Check that each ACK number equals the previous segment's sequence number plus its length.
  2. See a reset. With the capture still running, change it to port 8001 and run curl localhost:8001. Look for: [S] answered immediately by [R.]: "connection refused" is a reset.
  3. See TIME_WAIT. Right after step 1, run ss -tan state time-wait | grep 8000. Look for: a socket in TIME_WAIT on whichever side closed first. Run it again after a minute: it is gone.
  4. Prove it is a byte stream. Save as stream.py and run python3 stream.py: 
    import socket, threading, time
srv = socket.socket(); srv.bind(("127.0.0.1", 9009)); srv.listen()
def serve():
    conn, _ = srv.accept(); time.sleep(0.5)      # let several sends pile up
    while (data := conn.recv(4096)):
        print("recv got", len(data), "bytes:", data[:40])
threading.Thread(target=serve).start()
c = socket.create_connection(("127.0.0.1", 9009))
for msg in [b"HELLO", b"WORLD", b"x" * 10000]:
    c.sendall(msg)
c.close()
    Look for: fewer recv results than sends: "HELLOWORLD" arrives glued together with the start of the large message, and the large one may be split. Message boundaries do not exist in TCP.
  5. Read congestion control live. Start a large download in the background: curl -s -o /dev/null https://speed.cloudflare.com/__down?bytes=500000000 &, then run ss -ti dst speed.cloudflare.com a few times (or ss -ti | grep -A1 ':443'). Look for: cubic or bbr (the algorithm), rtt: (smoothed RTT and variation), cwnd: (growing between runs), retrans:, and delivery_rate. Divide cwnd × 1,448 bytes by the RTT and compare with the delivery rate; they should be in the same ballpark. Stop it with kill %1.
  6. Count states system-wide. ss -s and nstat -az | grep -Ei 'retrans|listenover'. Look for: totals by state and the retransmission and listen-overflow counters you would watch in production.

Stretch: open the step 1 capture in Wireshark (tcpdump -w out.pcap), then use Statistics → TCP Stream Graphs → Stevens on the download from step 5 to see slow start as a steepening curve of sequence numbers.

Diagnose it

A Python service calls an internal HTTP API about 3,000 times per second using requests.get(url) (no session). After a few minutes of peak traffic, calls start failing with "Cannot assign requested address". ss -s shows about 28,000 sockets in TIME_WAIT. Explain and fix.

Answer
  • requests.get without a Session opens a new TCP connection per call and closes it afterwards. The client closes first, so each closed connection sits in TIME_WAIT for 60 seconds on the client.
  • Every connection to the same destination IP and port needs a unique local ephemeral port, and Linux's default range (32768 to 60999) gives about 28,000. At 3,000 connections per second × 60 s, 180,000 would be needed, so the range is exhausted and connect() fails with EADDRNOTAVAIL, "Cannot assign requested address".
  • Fix: reuse connections. Use a requests.Session() (or an httpx client) with a connection pool sized to the concurrency, and HTTP keep-alive; ideally HTTP/2 to multiplex. This also removes a TCP handshake (and a TLS handshake, if HTTPS) from every call, cutting latency and CPU on both sides.
  • Secondary mitigations, not the real fix: widen net.ipv4.ip_local_port_range, enable net.ipv4.tcp_tw_reuse for outgoing connections, or spread load over more destination IPs. Do not set SO_LINGER to zero to skip TIME_WAIT: it replaces clean closes with resets and loses the protection.
Estimate it

You must copy a 10 GB model checkpoint from Mumbai to Frankfurt (RTT 120 ms) over a 10 Gbit/s link, using one TCP connection. The receiver's maximum receive buffer is 6 MB. Roughly how long will it take, and what would you change?

Answer

One connection delivers at most one window per round trip. With a 6 MB window: 6 MB / 0.12 s = 50 MB/s, about 400 Mbit/s, only 4% of the link. 10 GB / 50 MB/s = 200 s, just over three minutes, and more if any loss shrinks the congestion window below 6 MB.

To fill the link you need a window of at least the bandwidth-delay product: 10 Gbit/s = 1.25 GB/s, × 0.12 s = 150 MB. Options: raise the maximum socket buffers (tcp_rmem/tcp_wmem maximum) on both ends so auto-tuning can reach that size; use several parallel connections (as tools like aws s3 cp and gsutil do by splitting the file), so each needs a smaller window and one loss only slows one stream; and consider BBR on the sender, since any loss on a 120 ms path hurts loss-based algorithms badly. With 16 parallel streams of 6 MB windows you would already reach about 6.4 Gbit/s, around 13 seconds for the data.
