In net4 you saw how much work TCP does: a handshake before any data, numbering every byte, retransmitting losses, and delivering everything strictly in order. For a file download or a database query that is exactly what you want. But imagine you are on a video call. A packet carrying 20 milliseconds of your friend's voice goes missing. TCP would stop delivering everything that came after it until the lost packet is retransmitted and arrives, perhaps 150 ms later. By then that sound is useless: the conversation has moved on, and you have heard a freeze instead of a tiny glitch. For the call, skipping the lost packet is better than waiting for it.

That is the case for UDP, the User Datagram Protocol: the transport that does almost nothing, and so lets the application decide what to do about loss and timing. DNS lookups, voice and video, online games and telemetry all use it.

There is a second, bigger reason to learn UDP today. TCP's design has limits that became painful on the modern web: it needs a handshake round trip before encryption can even start; a single lost packet stalls every request sharing a connection; a phone switching from Wi-Fi to mobile data breaks every connection; and TCP lives inside operating-system kernels and is inspected by countless middleboxes, so improving it takes a decade. Engineers at Google, and then the IETF, responded by building a new transport, QUIC, on top of UDP. It is now what HTTP/3 runs on, carrying a large share of all web traffic from browsers to the big CDNs and platforms.

So this lesson has two halves. First UDP itself: what it provides, where it is the right tool, and the problems you take on when you use it, including why it is the favourite tool of denial-of-service attackers. Then QUIC: how it rebuilds reliability, encryption and multiplexing in user space on UDP, how its handshake saves round trips, how its independent streams remove head-of-line blocking, how connections survive network changes, and what it costs to run in production.

UDP: a postcard, not a phone call

TCP is like a phone call: you connect first, then talk in a continuous stream, and the line takes care of making sure every word arrives in order. UDP is like sending postcards. Each one is a self-contained datagram with an address on it. There is no setup, you can send one immediately, and each arrives whole or not at all. But some may be lost, some may arrive in a different order from the one you sent them in, occasionally one arrives twice, and the post office will not tell you about any of it.

That is almost literally the whole protocol. UDP's header is 8 bytes: source port, destination port, length and checksum. Compared with TCP's 20-plus bytes and its state machine, UDP adds only one thing to IP: ports, so the datagram reaches the right program. Everything else, if you need it, is your job.

Two properties make UDP genuinely useful rather than just primitive. It preserves message boundaries: one send is one datagram is one receive, so no framing is needed. And nothing ever waits: a lost datagram does not delay the ones after it, because there is no ordering to preserve.

QUIC: reliability rebuilt on postcards

Because UDP does so little, you can build a whole new transport on top of it without asking operating systems or network equipment for permission. QUIC does exactly that: it numbers its packets, acknowledges them, retransmits what is lost and controls congestion, like TCP, but it runs as a library inside the application, has TLS 1.3 encryption built in, and carries many independent streams in one connection.

The payoffs, each explained in the body: a new connection with encryption in one round trip instead of two (and zero on repeat visits), a lost packet only delays the stream it belongs to, connections survive changing networks, and the protocol can be improved by shipping a new library rather than new operating systems.

Where you meet them today

Every DNS lookup your laptop makes is almost certainly a UDP datagram. Every video call in a browser or app sends its audio and video over UDP. When you load a page from Google, YouTube, Meta or a site behind a large CDN in a modern browser, the requests very likely travel over QUIC. And the database connections, internal APIs and SSH sessions you work with daily are still TCP. All three coexist, and a single page load can use all of them.

How to choose, in one sentence each

Use TCP when you need a reliable byte stream and the standard tools, which is most of the time. Use QUIC (usually via HTTP/3) when latency on real-world networks matters, especially mobile and long-distance. Use raw UDP when late data is worthless, you need multicast, or you are building a transport yourself, and then accept that you own loss, pacing and security.

1. The UDP datagram, and what "no guarantees" means

A UDP datagram is an 8-byte header plus payload, inside one IP packet:

FieldSizeMeaning
Source port16 bitswhere replies should go (optional in theory)
Destination port16 bitswhich program receives it, e.g. 53 for DNS
Length16 bitsheader plus payload, in bytes
Checksum16 bitsdetects corruption; optional in IPv4, mandatory in IPv6

A program opens a UDP socket, and every sendto() call produces exactly one datagram; every recvfrom() returns exactly one datagram, whole, together with the sender's address and port. There is no connection: the same socket can talk to many peers, and a server simply answers whoever sent the last datagram.

What can go wrong, concretely, is everything IP allows. A datagram can be lost (a full router queue drops it, or the receiver's socket buffer is full and the kernel drops it on arrival), reordered (two datagrams take different paths), duplicated (rare, from misbehaving equipment), or corrupted (and then dropped by the checksum). The sender is told about none of it.

2. When UDP is the right tool

  • Tiny request/response exchanges. A DNS query and its answer each fit in one datagram. Over TCP, a lookup would cost a handshake plus the exchange, and servers would hold state for billions of short connections. Over UDP it is one round trip, and if the answer does not come back, the client simply asks again after a timeout.
  • Real-time media. Voice and video calls send small packets every 10 to 20 ms, usually in the RTP format, which adds timestamps and sequence numbers. The receiver uses a jitter buffer (a small delay, perhaps 30 to 100 ms, that smooths out variation in arrival times), plays packets in order, and conceals any that are missing. Retransmitting would arrive too late to play.
  • Games and state updates. A player's position is sent 20 to 60 times per second; each update replaces the previous one, so a lost update is best forgotten.
  • Telemetry and discovery. Metrics agents (StatsD) fire-and-forget counters where occasional loss is acceptable; local service discovery uses broadcast or multicast (one datagram to a group of listeners), which only UDP supports.
  • Building a new transport. QUIC, the WireGuard VPN and media protocols like WebRTC's data channels use UDP as a thin, universally allowed wrapper, and do their own reliability and congestion control on top.

3. The problems you inherit

Choosing UDP means taking on, yourself, the jobs TCP was doing:

  • Loss, reordering and duplicates. Put a sequence number in every message so the receiver can detect gaps, discard duplicates and stale data, and decide whether to request a resend.
  • Congestion control and pacing. Nothing stops a UDP sender from transmitting faster than the path can carry. If it does, routers drop the excess, including other people's TCP packets, whose senders politely back off while yours keeps going. Well-behaved UDP applications measure loss and delay and adjust their rate, and send at a steady pace rather than in bursts.
  • Size. Keep datagrams below the path MTU. The header allows about 64 KB, but a datagram bigger than the link's MTU is split into IP fragments; losing any fragment loses the whole datagram, and many firewalls drop fragments entirely. Safe sizes are about 1,200 bytes: QUIC requires paths to carry at least 1,200-byte datagrams, and DNS now recommends a 1,232-byte limit.
  • NAT and firewalls. A NAT (net3) creates a mapping when you send, but because there is no FIN to say a UDP "conversation" is over, it expires mappings after inactivity, often within 30 seconds to a few minutes. Long-lived UDP flows send keepalives more often than that.
  • Receive buffer overflows. If the application does not read fast enough, the kernel drops arriving datagrams when the socket buffer is full, and counts them (netstat -su shows "receive buffer errors"). With TCP the sender would have been slowed by flow control; with UDP data just disappears.

4. Spoofing and amplification

TCP's handshake proves the client can receive packets at its claimed address; a forged source address never sees the SYN-ACK, so the connection cannot proceed. UDP has no such proof. Anyone can send a datagram with a spoofed source address, and the server will send its reply to whoever owns that address. Combine that with a service whose reply is much bigger than the request, and you get a reflection and amplification attack:

In February 2018 GitHub was hit by 1.35 Tbit/s of traffic reflected from misconfigured memcached servers on UDP port 11211; the production section tells that story. Any protocol you design on UDP must avoid being an amplifier, typically by never sending more to an unverified address than it received from it. QUIC builds that rule in.

5. QUIC's building blocks

QUIC was developed at Google from 2012 and standardised by the IETF in 2021 as RFC 9000 (the transport), RFC 9001 (how TLS secures it), RFC 9002 (loss detection and congestion control) and RFC 9114 (HTTP/3). Its vocabulary:

  • A connection is between a client and a server, identified by connection IDs chosen by each side, not by IP addresses and ports.
  • Each UDP datagram carries one or more QUIC packets, each with a packet number that only ever increases.
  • Each packet carries frames: STREAM frames with application data, ACK frames acknowledging received packet numbers, CRYPTO frames carrying the TLS handshake, and control frames for flow control and connection management.
  • A stream is an independent, ordered byte sequence within the connection, like a lightweight TCP connection. Either side can open many; HTTP/3 uses one per request.

Almost everything after the first few bytes of each packet is encrypted, including the packet number and all frames. An observer on the network sees UDP ports, a few flag bits and the connection ID, and nothing else.

6. The handshake: one round trip, sometimes zero

With TCP and TLS 1.3 (net2), the client waits one round trip for the TCP handshake and another for the TLS handshake before it can send its request, so the response arrives after three round trips. QUIC carries the TLS 1.3 handshake messages inside its own first packets, so connection setup and key agreement happen together:

In detail: the client's first datagram contains an Initial packet carrying the TLS ClientHello, padded to at least 1,200 bytes (which, as we will see, is an anti-amplification measure). The server replies with its own Initial and Handshake packets carrying the ServerHello, certificate and Finished, and can already send application data. The client finishes the handshake and sends its request in the same flight. For a returning client, TLS 1.3 session resumption lets it derive keys for 0-RTT data and include the request in its very first flight. As with TLS 0-RTT over TCP, that early data can be replayed by an attacker, so it is only safe for idempotent requests (net2).

7. Streams without head-of-line blocking

Recall from net4 that TCP delivers one ordered byte stream per connection, so when HTTP/2 multiplexes requests over TCP, one lost packet blocks all of them. QUIC keeps order per stream. Each STREAM frame says which stream it belongs to and at which byte offset, so the receiver reassembles each stream independently:

This mattered enough that HTTP/3 also needed a new header compression scheme. HTTP/2's HPACK relies on all header blocks arriving in order across the connection; HTTP/3's QPACK is designed so that a stream's headers can usually be decoded without waiting for other streams.

8. Reliability and congestion control, rebuilt

QUIC acknowledges packets, not bytes. ACK frames list ranges of received packet numbers (like TCP's SACK, but with many more ranges) and report how long the receiver delayed the ACK, so RTT is measured accurately. Because packet numbers never repeat, when data is lost its frames are placed into a new packet with a new number. That removes a long-standing TCP ambiguity, where an ACK for a retransmitted segment could refer to either the original or the retransmission, confusing RTT measurement. Loss is detected when a later packet has been acknowledged and either enough packets or enough time have passed, similar to Linux TCP's RACK method (net4). Congestion control follows the same principles as TCP, starting cautiously and backing off on loss, and implementations ship CUBIC or BBR; because it is a library, changing algorithm is a software update. Flow control exists at two levels, per stream and per connection, so one greedy stream cannot use all the receiver's buffer.

9. Connection migration

A TCP connection is its 4-tuple; if the client's address changes, the server sees packets from an unknown tuple and the connection is dead. When a phone walks out of Wi-Fi range onto mobile data, every TCP connection breaks and every app reconnects, paying the handshakes again. QUIC packets carry a connection ID, so a server receiving packets from a new address with a known connection ID recognises the connection. It validates the new path (sending a challenge that the client must echo, so an attacker cannot redirect traffic to a victim) and continues. Clients switch to fresh connection IDs when migrating so observers cannot link the old and new paths.

11. Discovering and falling back

A browser cannot know in advance whether a site speaks HTTP/3 or whether the network lets UDP through. Usually the first visit uses HTTP/2 over TCP, and the response carries an Alt-Svc header such as h3=":443"; ma=86400, meaning "HTTP/3 is available on UDP port 443, remember this for a day". Newer sites also publish an HTTPS DNS record that advertises HTTP/3 before the first connection. Browsers then try QUIC, often racing it against TCP, and fall back silently if UDP is blocked, as it is on some corporate networks. Any service offering HTTP/3 must therefore keep offering HTTP/2 over TCP.

Anti-amplification and address validation

A QUIC server receiving a first packet cannot yet know whether the source address is genuine, so it could be used as a reflector. RFC 9000 therefore limits a server to sending at most three times the number of bytes it has received from an address until that address is validated, which happens when the client proves it received the server's packets. The client's first datagram must be padded to at least 1,200 bytes, which both gives the server a budget for its certificate-heavy reply and ensures the path supports QUIC's minimum datagram size. Under attack, a server can go further and send a Retry packet containing a token the client must echo, proving its address before the server does any expensive cryptography, the same idea as TCP SYN cookies.

Load balancing QUIC

Layer-4 load balancers traditionally hash the 4-tuple to pick a backend. With migration, the tuple changes mid-connection, so a tuple hash would send the migrated connection to the wrong server, which knows nothing about it. The solution is to route on the connection ID: servers issue connection IDs that encode which backend they belong to (optionally encrypted so outsiders cannot learn the mapping), and the balancer decodes it. The IETF's QUIC-LB work standardises such schemes. Stateless balancers that cannot do this simply lose migration; stateful ones must track connection IDs. Either way, UDP port 443 must be open through every firewall and security group on the path.

The CPU cost and how it is being closed

Kernel TCP benefits from decades of optimisation and hardware offloads: the network card segments large sends and coalesces received packets, and encryption can be offloaded too. A user-space QUIC stack originally made one system call per packet and encrypted each packet in software, costing noticeably more CPU per byte. The gap is being closed by UDP GSO and GRO, which let one system call send or receive a batch of datagrams that the kernel or card splits and merges; by sendmmsg/recvmmsg for batching; by pacing in the kernel; and by careful memory handling. For most services the remaining overhead is acceptable; for bulk transfer inside data centres, kernel TCP usually remains cheaper.

Visibility: the price of encryption

Operators used to debug TCP performance from passive captures: sequence numbers, retransmissions and RTT are all visible in the headers. QUIC hides packet numbers and ACKs, deliberately. What remains visible is the UDP header, the connection ID, and one optional spin bit that flips once per round trip so on-path observers can estimate RTT if the endpoints choose to allow it. Debugging therefore moves to the endpoints, which can emit qlog event logs (packets sent, lost, acknowledged, congestion window changes) to be viewed in tools such as qvis, or export TLS keys so Wireshark can decrypt a capture on a test machine.

Unreliable data inside QUIC, and WebTransport

Some applications want QUIC's encryption, congestion control and NAT friendliness but also want to send some data unreliably, such as game state or media frames. RFC 9221 adds a DATAGRAM frame: unreliable, unordered messages carried inside the encrypted, congestion-controlled connection. Browsers expose this, together with multiple streams, through the WebTransport API over HTTP/3, giving web apps a UDP-like option for the first time, alongside WebRTC (net11).

Versions, GREASE and keeping the protocol flexible

QUIC's designers expected middleboxes to try to parse whatever was left visible, so they defended even those few bits. Every packet with a long header carries a version number, and a client and server can negotiate versions; QUIC version 2 (RFC 9369) exists largely to prove that negotiation keeps working in practice. Endpoints also grease the protocol: they send random values in reserved fields and occasionally use reserved version numbers, so any middlebox that assumed those values were fixed breaks immediately in testing rather than years later in production. It is the same lesson as TCP's ossification, applied pre-emptively: a field that never varies will eventually be treated as a constant by someone.

Why not just fix TCP?

Many of QUIC's ideas were tried in TCP: Fast Open for faster handshakes, multipath TCP for migration, bigger initial windows. Each was slowed by two facts. TCP lives in operating-system kernels, so improvements reach users only as fast as phones and servers upgrade their OS, which takes years. And middleboxes that parse TCP headers drop or mangle unfamiliar options, so new features fail on some fraction of paths. Running over UDP in user space, with encrypted headers, makes QUIC deployable by updating an app or a library, and keeps middleboxes from freezing it. It is an architectural lesson: put the parts you want to evolve where you control them.

Failure modes you will meet

  • UDP blocked or throttled. Some enterprise firewalls block UDP 443 or rate-limit UDP generally. Clients fall back to TCP, so nothing breaks outright, but you lose the latency benefits for those users, and connection attempts that race QUIC and TCP waste a little work. Track the share of requests on HTTP/3 versus HTTP/2 by network to see it.
  • Missing firewall rules for QUIC. A team enables HTTP/3 on its load balancer but the security group or network ACL only allows TCP 443. Clients try QUIC, time out and fall back, adding delay to the first connection. The fix is simple once noticed: allow UDP 443 end to end.
  • Silent UDP drops at the receiver. A metrics collector or DNS server under load drops datagrams because its socket receive buffer is full. Nothing errors; data just goes missing. Watch RcvbufErrors in netstat -su or nstat, raise net.core.rmem_max and the socket buffer, and add more reader threads.
  • NAT timeouts on UDP flows. VoIP calls lose audio in one direction after a pause, or a game client stops receiving updates, because a NAT mapping expired. Send keepalives every 15 to 25 seconds on long-lived UDP flows.
  • Fragmentation. Large DNS responses (for example with DNSSEC signatures) fragment, fragments are dropped by a firewall, and lookups time out for some domains only. DNS Flag Day 2020 moved the ecosystem to a 1,232-byte default EDNS buffer, with truncation and fallback to TCP for anything bigger.
  • CPU increase after enabling HTTP/3. Edge servers use more CPU per request than with TCP; capacity plans must account for it until GSO/GRO and batching are enabled.

War story: 1.35 Tbit/s from memcached

On 28 February 2018 at 17:21 UTC, GitHub was hit by one of the largest DDoS attacks recorded at the time: 1.35 Tbit/s and about 127 million packets per second. The traffic came from memcached servers, a caching system that some operators had left listening on UDP port 11211 on the public internet. Attackers sent them small requests with GitHub's addresses as the spoofed source, and memcached replied with responses up to 51,000 times larger. GitHub's site was fully unavailable for about five minutes and intermittently for four more. It recovered by withdrawing its BGP announcements from its transit providers and routing through its DDoS mitigation provider, which filtered the UDP 11211 traffic at the edge of its network. The lessons were aimed at the whole ecosystem: never expose UDP services that answer unauthenticated requests with large replies, networks should drop packets with forged source addresses, and critical sites need a mitigation provider on standby.

Observability and tools

For UDP: ss -uan lists UDP sockets and their queues; netstat -su and nstat give datagram and error counters; tcpdump shows datagrams in full because UDP itself is not encrypted. For QUIC: browser DevTools show the protocol per request (h3); Chrome's chrome://net-export captures detailed connection logs; servers and libraries can write qlog; Wireshark can decode QUIC if you give it the TLS keys through the SSLKEYLOGFILE environment variable. At the load balancer, watch HTTP/3 request share, handshake failures and fallback rates.

Knobs

Socket receive and send buffer sizes (net.core.rmem_max, SO_RCVBUF) for high-rate UDP; UDP GSO/GRO enablement in the QUIC library; congestion control choice in the QUIC stack; the Alt-Svc max-age (how long clients remember HTTP/3 support); QUIC idle timeout and keepalive intervals relative to NAT timeouts; and whether to accept 0-RTT, and for which request types.

Choose and justify

Pick TCP, UDP or QUIC for each and justify: (a) a multiplayer game's position updates at 30 Hz; (b) the same game's in-game purchases; (c) a mobile app's API, used heavily on flaky cellular networks; (d) a service-mesh call between pods in one data centre; (e) bulk nightly backup transfer of 2 TB between regions.

Answer
  • (a) UDP, with a light custom protocol: each update supersedes the previous one, so retransmitting a stale position only adds delay. Add sequence numbers to drop out-of-order packets, interpolate over losses, pace sending and send NAT keepalives.
  • (b) Reliable delivery: TCP (HTTPS) or a reliable QUIC stream. Purchases must arrive exactly once and be confirmed by the server; use idempotency keys so a retried request does not charge twice.
  • (c) QUIC / HTTP/3: fewer handshake round trips, 0-RTT resumption for idempotent calls, no head-of-line blocking under loss, and connection migration when the phone changes network all matter on mobile. Keep HTTP/2 over TCP as the fallback for networks that block UDP.
  • (d) TCP (HTTP/2 or gRPC): RTT and loss inside a data centre are tiny, so QUIC's advantages are small, while kernel TCP is cheaper on CPU and well supported by meshes, proxies and tooling.
  • (e) TCP, tuned: large windows or several parallel streams to fill a high bandwidth-delay path (net4), BBR on long lossy paths, or a purpose-built transfer tool. UDP-based bulk tools exist, but they must implement their own congestion control to avoid harming other traffic.
Diagnose: missing metrics

Your team sends application metrics as UDP datagrams (StatsD style) to a collector. During traffic peaks, dashboards show counts dropping by 20% even though request logs show traffic rising. No errors are logged anywhere. What is happening, how do you confirm it, and what would you change?

Answer

At peak, datagrams arrive faster than the collector reads them, its socket receive buffer fills, and the kernel drops the excess on arrival. UDP has no flow control, so senders are never told, and no application logs an error. Confirm on the collector host with netstat -su or nstat -az UdpRcvbufErrors: the counter rises during peaks. Also check for loss on the path if the collector is remote (NIC and switch drop counters). Fixes, in order: increase the socket receive buffer (SO_RCVBUF, capped by net.core.rmem_max) to absorb bursts; add reader threads or processes with SO_REUSEPORT so reading keeps up; reduce datagram count by aggregating on the sender (a local agent that pre-aggregates per host is the standard pattern); and for metrics that must not be lost, such as billing counters, switch to a reliable transport or a push to a queue. Accept that UDP metrics are "best effort" and label dashboards accordingly.
