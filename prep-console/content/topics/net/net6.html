Every connection your code makes starts with a name: api.stripe.com, db.internal, my-service.default.svc.cluster.local. Before a single TCP packet can be sent, that name has to become an IP address. The system that does this, DNS, is so reliable most of the time that engineers forget it exists, which is exactly why it is behind so many outages. There is a well-worn joke among operations engineers, "it's always DNS", and a haiku that ends "it was DNS".

Consider three real situations. A team migrates its database to a new host, updates the DNS record, and half of its services keep talking to the old host for an hour, because the record had a long TTL and some clients never re-resolve. A company's DNS provider is hit by a denial-of-service attack, and its website becomes unreachable worldwide even though every one of its servers is perfectly healthy. A Kubernetes cluster's DNS pods are overloaded, and random requests across dozens of services stall for exactly five seconds. None of these is a bug in application code; each is a DNS mechanism behaving exactly as designed.

DNS is also a tool you actively use. It is how CDNs send each user to a nearby server, how multi-region services fail over, how you prove to a certificate authority or an email provider that you own a domain, how services find each other inside a cluster, and one of the first places a security reviewer looks.

net2 walked through a lookup once. This lesson goes inside it: how the namespace is organised into zones and delegated, what stub and recursive resolvers do, how caching and TTLs really work (including caching of "does not exist"), the record types you will meet, how DNS is used to steer traffic, what goes over the wire, how DNSSEC and encrypted DNS protect it, and how DNS behaves inside Kubernetes. The production section then catalogues how it fails.

The problem: names for people, numbers for routers

Routers forward by IP address, but people and configuration files use names, and addresses change: servers move, CDNs pick different edges for different users, failover switches regions. DNS (the Domain Name System) is the directory that turns a name into its current address, and into other kinds of information such as which servers accept a domain's email.

The analogy: a directory of directories

No single directory could hold every name on the internet and handle every lookup. So DNS works like asking for a phone number through a chain of receptionists. The main switchboard (the root) does not know your friend's number, but it knows who handles every country code. The ".com" desk does not know it either, but it knows who handles "example.com". Example.com's own receptionist (its authoritative server) finally gives the number. Your company has one assistant (the recursive resolver) who makes these calls for everyone and writes answers on a notepad, crossing them out after a set time (the TTL), so most questions are answered from the notepad without any calls.

Where the analogy breaks: the notepad is shared by millions of people, so a wrong entry, or a stale one, affects all of them until it expires; and the chain of receptionists is enormous but mostly idle, because the notepads answer nearly everything.

The tree of names

Why DNS is fast despite the tree

Walking root, TLD and authoritative servers for every lookup would be slow and would melt the root servers. It almost never happens. Your browser and operating system cache answers; your recursive resolver caches answers for everyone who uses it, including the referrals for com and other TLDs, which it needs to fetch only once a day or so. A popular name is usually answered from the resolver's memory in a millisecond or two. The tree is the source of truth; the caches do the work.

What a record looks like

Every piece of DNS data is a resource record with a name, a TTL in seconds, a type and a value. This is what dig prints:

api.example.com.   300   IN   A       203.0.113.10
www.example.com.   3600  IN   CNAME   example.cdn-provider.net.
example.com.       86400 IN   MX      10 mail.example.com.

Read the first line as: "the name api.example.com has an IPv4 address (A record) of 203.0.113.10, and you may cache this for 300 seconds". The IN means the internet class, which is the only one you will use. The second line is an alias (CNAME): "www is really that CDN name; look that up instead". The third names the mail server. Those three types, plus a handful more in the body, cover almost everything you will touch.

If you remember one operational fact from this lesson: a DNS change reaches a client only when every cache between them has let the old answer expire. Everything about DNS migrations follows from that.

1. Zones and delegation

The namespace is one big tree, but it is managed in pieces called zones. The root zone contains, for each top-level domain (TLD) such as com or in, a set of NS records naming the servers responsible for it. The com zone, run by its registry, contains NS records for every registered .com domain. The example.com zone, run by whoever owns the domain (often through a DNS provider such as Route 53 or Cloudflare), contains the actual records for www, api and so on. Handing a subtree to other servers is called delegation, and it is always done by NS records in the parent zone.

One chicken-and-egg problem: if example.com's name servers are ns1.example.com and ns2.example.com, a resolver cannot look up their addresses without already asking them. So the parent zone also publishes their addresses, called glue records, alongside the delegation.

When you "register a domain", you pay a registrar, which tells the TLD registry which name servers to list in the parent zone for your domain. When you "move DNS to a new provider", you change those NS records at the registrar. Because the parent's NS records have long TTLs, often two days for .com, that particular change genuinely does take a day or two to reach every resolver, which is where the folklore about slow "propagation" comes from.

Every zone also has an SOA (Start of Authority) record at its top, the zone apex, carrying administrative data: a serial number that secondary servers use to notice changes, and the TTL for caching negative answers.

2. Resolvers: stub and recursive

Two kinds of client software take part in every lookup.

The stub resolver is a small piece of the operating system or C library. On Linux its configuration lives in /etc/resolv.conf: which recursive resolvers to ask (up to three nameserver lines), which search domains to try for short names, and options such as ndots, timeout (5 seconds by default) and attempts (2 by default). The stub sends one query and waits for one final answer. It does not walk the tree.

The recursive resolver does the real work for many clients: your ISP's resolver, your company's, your cloud provider's (such as the one at the VPC base address plus two in AWS), or a public one like 1.1.1.1 or 8.8.8.8. On a cache miss it starts from the root (every resolver ships with a root hints list of the 13 root server names, a.root-servers.net to m.root-servers.net, each actually served from many sites worldwide by anycast), follows referrals down to the authoritative server, and caches everything it learns along the way: the final answer, the NS records and glue for com and example.com, for their TTLs. A busy resolver therefore rarely needs to talk to the root at all, and usually goes straight to the authoritative servers of the domain being asked about.

Between the application and the stub there may be further caches: the browser's DNS cache, a language runtime's own cache (the JVM, for example, has its own lookup cache), and a local caching daemon such as systemd-resolved. Each layer is another place an old answer can linger.

3. Caching and TTLs, precisely

When a resolver receives a record with TTL 300, it may answer from cache for up to 300 seconds, counting down; clients asking later get the remaining TTL, which is why dig run twice shows a decreasing number. After expiry the next query triggers a fresh lookup. That is the whole mechanism: DNS is pull, never push. Nobody tells caches that a record changed.

The consequence for changes is precise. If a record's TTL is T and you change it at time 0, a resolver that fetched it just before time 0 may keep serving the old value until almost time T. So the worst case for everyone to see the change is one old TTL, plus any client that ignores TTLs.

Resolvers also cache "no". If a name does not exist, the authoritative server answers NXDOMAIN and includes the zone's SOA record; the resolver caches the negative answer for the smaller of the SOA's own TTL and its "minimum" field (RFC 2308). This negative caching protects authoritative servers from floods of queries for missing names, but it means a record created shortly after someone asked for it may stay invisible to them for that period.

Choosing TTLs is a trade-off. Short TTLs (30 to 60 seconds) make failover and migration fast, but every cache miss costs a lookup (tens of milliseconds, sometimes more), authoritative servers get more queries, and if your DNS provider goes down, clients lose your records within a minute. Long TTLs (hours) are cheap and ride out short provider outages, but lock in mistakes. A common pattern: long TTLs on stable records (MX, NS, verification TXT records), 60 to 300 seconds on records you may need to move.

The CNAME rule deserves a sentence of explanation because it trips everyone up. A CNAME says "this name is that other name, for every record type". That is why DNS providers invented ALIAS-style records: the provider's server resolves the target itself and answers with plain A and AAAA records at the apex.

5. On the wire

A DNS message is small and binary: a header with a 16-bit transaction ID and flags, then the question (name and type), then answer, authority and additional sections. Queries normally go over UDP port 53: one datagram out, one back, no handshake (net5). The client matches the reply to its question by the transaction ID and its own source port, retries after a timeout if nothing comes back, and moves on to the next configured resolver if that fails too.

Classic DNS limited UDP answers to 512 bytes. EDNS(0) lets the client advertise a bigger buffer, and since DNS Flag Day 2020 the recommended size is 1,232 bytes, chosen so answers fit in one packet without IP fragmentation on almost any path. If an answer is larger, the server sets the truncated (TC) flag and the client repeats the query over TCP port 53. Zone transfers between primary and secondary authoritative servers also use TCP.

Two response codes you must recognise: NXDOMAIN, "the name does not exist", and SERVFAIL, "I could not get a valid answer", which means something is broken upstream (unreachable or misconfigured authoritative servers, or a DNSSEC validation failure), not that the name is missing. A third outcome, an answer with no records of the requested type (NOERROR with an empty answer, sometimes called NODATA), means the name exists but has no, say, AAAA record.

6. Steering traffic with DNS

Because an authoritative server can answer each query however it likes, DNS is a powerful traffic control tool:

  • Round-robin: return several A records, possibly in rotating order. Clients spread out roughly. No health awareness.
  • Weighted: return endpoint A for 90% of queries and B for 10%, for gradual migrations or canary releases.
  • Latency- or geo-based: answer with the region or edge nearest to the querying resolver. The server only sees the resolver's address, so providers use the EDNS Client Subnet extension, where the resolver passes along a truncated form of the client's address, to pick better.
  • Health-checked failover: the DNS provider probes endpoints and stops returning unhealthy ones.

All of these are limited by caching: a decision stays in effect for a TTL, and a client that picked a dead address keeps trying it. So the standard architecture is DNS for coarse, global decisions (which region, which CDN edge), and load balancers for fine-grained, per-request decisions inside a region (net10).

7. Security: poisoning, DNSSEC and encrypted DNS

Classic DNS has no authentication: a resolver accepts the first reply whose transaction ID and port match its question. Cache poisoning exploits this. An attacker triggers a lookup and floods the resolver with forged replies guessing the ID; if one is accepted, the resolver caches the attacker's address and serves it to every user. In 2008 Dan Kaminsky showed how to make this fast: query random nonexistent names like x123.example.com so each attempt is a fresh cache miss, and include forged referrals that hijack the whole domain. The immediate defence was randomising the query's source port as well as its ID, multiplying the guessing space by tens of thousands.

The complete defence is DNSSEC. Each zone signs its records with its own key and publishes the signatures. The parent zone publishes a DS record, a hash of the child's key, and signs that; so a validating resolver can follow a chain of trust from the root's key, which it has built in, down to the answer, and reject anything forged. DNSSEC provides authenticity and integrity, not confidentiality, and it adds real operational risk: an expired signature, a key rotation mistake, or a DS record left at the parent after disabling signing makes the whole domain fail to resolve (SERVFAIL) for users of validating resolvers.

Privacy is a separate problem: classic DNS queries travel in plaintext, so anyone on the path, and the resolver operator, sees every name you look up. DNS over TLS (DoT, port 853), DNS over HTTPS (DoH, port 443) and DNS over QUIC (DoQ) encrypt the hop between the client and its resolver. Browsers and operating systems increasingly enable DoH by default. Note that they protect only that hop: the resolver still sees your queries, and resolvers talk to authoritative servers mostly in plaintext.

8. DNS inside Kubernetes

In a Kubernetes cluster, a DNS server (usually CoreDNS) answers names for Services, such as payments.prod.svc.cluster.local, and forwards everything else to upstream resolvers. Each pod gets a resolv.conf like this:

nameserver 10.96.0.10
search prod.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

The ndots:5 option says: if a name has fewer than five dots, first try it with each search domain appended. That lets code say just payments or payments.prod. But it means a lookup of api.stripe.com (two dots) is tried as api.stripe.com.prod.svc.cluster.local, then api.stripe.com.svc.cluster.local, then api.stripe.com.cluster.local, and only then as itself, each failing with NXDOMAIN first, and each for both A and AAAA. One logical lookup becomes eight queries. At scale this multiplies CoreDNS load and adds latency to every external call. Fixes: write external names fully qualified with a trailing dot (api.stripe.com.), lower ndots in the pod's dnsConfig, and run a node-local DNS cache so repeated lookups never leave the node.

Why "it's always DNS": failure amplification

DNS sits at the start of every connection, so a DNS problem is instantly a problem for everything. Three properties amplify it. First, a lost UDP query is only retried after the stub's timeout, 5 seconds by default in glibc, so small packet loss turns into multi-second latency spikes that look like application slowness. Second, when a resolver is slow, clients retry and applications retry on top, multiplying load on an already struggling resolver. Third, caches hide problems until TTLs expire, so a broken change can appear fine for minutes and then fail everywhere at once, far from the moment of the change. Mature teams therefore treat DNS changes like code deploys: reviewed, staged, monitored from many locations, and easy to roll back.

The DNSSEC chain of trust and its sharp edges

A signed zone has a key-signing key (KSK), whose hash the parent publishes as a DS record, and a zone-signing key (ZSK) that signs the records, itself signed by the KSK. Validation follows DS → KSK → ZSK → signature → record, from the root down. The operational hazards come from the cached pieces you do not control. The DS record lives in the parent zone with the parent's TTL: Slack learned in September 2021 that the .com zone tells resolvers to cache DS records for 24 hours, so after they turned signing off, validating resolvers kept expecting signatures and returned SERVFAIL. Negative answers need signed proofs of non-existence (NSEC or NSEC3 records), and a provider bug in how those proofs described wildcard records made some resolvers cache "no A record" answers for Slack. The general lesson is that DNSSEC changes are a multi-day, multi-party procedure with a rollback plan that accounts for every TTL involved.

Resolver location, Client Subnet and privacy

Geo-steering assumes the resolver is near the user, which was true when everyone used their ISP's resolver. Public resolvers and encrypted DNS break that assumption: a user in Chennai using a resolver instance in Singapore may be sent to a Singapore edge. EDNS Client Subnet fixes steering by passing the first 24 bits of the client's IPv4 address to the authoritative server, but it leaks location information and fragments resolver caches (one cached answer per subnet instead of one per name). Some large public resolvers therefore send it only to providers that need it, and anycast-based CDNs sidestep the issue by routing on the client's own packets instead of DNS answers.

Client behaviour matters as much as TTLs

What actually determines failover speed is what clients do. Browsers re-resolve often. Many server-side HTTP clients keep connections in a pool for minutes or hours and never look up the name again while a connection stays open, so a DNS change affects only new connections. The JVM caches successful lookups for 30 seconds by default, but forever when a security manager is installed, and some older libraries cache for the process lifetime. Connection pools to databases behave similarly. For DNS-based failover to work, clients need bounded connection lifetimes (for example, recycle pooled connections every few minutes) and sane DNS caching, and failover procedures should expect a long tail of stragglers on the old address.

Split-horizon and private zones

Organisations often serve different answers inside and outside their network: api.example.com resolves to a private load balancer for employees and servers, and to a public edge for everyone else. Clouds implement this with private hosted zones attached to specific VPCs. It is convenient and reduces exposure, but it is a classic source of "works for me" confusion: the same name gives different answers depending on which resolver you ask, so debugging must always start by asking "which resolver did this client use, and what did it return?"

DNS as a data-exfiltration and command channel

Because DNS queries are allowed out of almost every network and are forwarded by resolvers to whichever authoritative server owns a domain, attackers encode data in query names (c2VjcmV0.attacker.example) to smuggle it out, or receive instructions in TXT answers. Defences are forcing all DNS through monitored resolvers, blocking direct outbound port 53 and unknown DoH endpoints, and looking for unusual query volumes and long random-looking labels. This is also why enterprises are wary of browsers doing DoH to external resolvers: it bypasses their monitoring.

How DNS takes production down

  • Provider outage or DDoS. On 21 October 2016, a botnet of hacked cameras and routers (Mirai) flooded Dyn, a major managed DNS provider, and sites whose domains used only Dyn, including Twitter, GitHub, Netflix and Reddit, became unreachable for parts of the day in waves, while their servers were fine. Users whose resolvers had cached records kept working until the TTLs ran out. The lesson most teams took: critical domains need a second authoritative provider.
  • Bad changes. A typo in a record, a deleted record, an accidental TTL of 0, or a zone file pushed with the wrong serial. Because of caching, the blast radius grows as TTLs expire, so the incident may start well after the change.
  • DNSSEC mistakes. Expired signatures or broken DS records produce SERVFAIL for users behind validating resolvers only, a confusing partial outage. Slack's September 2021 rollout caused about 24 hours of intermittent failures for under 1% of users, mostly behind corporate resolvers and Google Public DNS.
  • Expired domains and certificates. A forgotten domain renewal takes everything down at once; registrars' reminder emails go to a departed employee. Put expiry dates in monitoring.
  • Resolver overload and 5-second stalls. CoreDNS pods or a VPC resolver hitting limits (AWS's VPC resolver has a per-network-interface packet rate limit) drop queries; clients see exact 5-second delays from the stub's retry timeout. Node-local caches and lower ndots are the standard fixes.
  • Stale addresses after migrations. Clients keep connecting to an old IP for long after the TTL because of connection pools or runtime caches. Keep the old endpoint alive and watch its traffic.
  • Dangling records. CNAMEs left pointing at deleted cloud resources enable subdomain takeover; security teams scan for them.

A debugging order that works

When a name misbehaves, ask these in order. What does the authoritative server say right now (dig @ns1.provider.example api.example.com)? What does the resolver this client actually uses say, and with what remaining TTL? What does the client itself see, including any hosts-file entry, runtime cache or search-domain expansion (getent hosts api.example.com on Linux uses the same path as most programs)? And is the client even resolving, or reusing an old connection? The answer is almost always a difference between two of those four views.

Observability

Monitor resolution of your key names from many networks and regions (synthetic checks), and alert on SERVFAIL rates and latency. On resolvers and CoreDNS, track query rate, cache hit ratio, response codes, upstream latency and dropped queries. On clients, DNS lookup time is visible in HTTP client metrics and traces if you instrument it, and in browsers through the Navigation and Resource Timing APIs (net2). Keep zone changes in version control (for example Terraform or OctoDNS), with review and an audit trail, because "what changed?" is the first question in every DNS incident.

Knobs

TTLs per record; SOA negative-caching TTL; a second authoritative provider; health checks and routing policies on the DNS provider; ndots, search domains, timeout, attempts and single-request-reopen in resolv.conf or pod dnsConfig; node-local DNS caches in Kubernetes; runtime DNS cache settings (such as the JVM's networkaddress.cache.ttl); and maximum connection lifetimes in pools so clients eventually follow DNS changes.

Fifteen minutes with dig (Linux, macOS, WSL; on Windows PowerShell, Resolve-DnsName works for most steps). You will read a response, walk the tree, watch caching and negative caching, and do a lookup over HTTPS.

  1. Read a full response. dig www.wikipedia.org. Look for: the status: field in the header (NOERROR), the flags (rd ra mean recursion desired and available), the ANSWER section (probably a CNAME then A records), the TTL column, and at the bottom SERVER: (which resolver answered) and Query time:.
  2. Watch caching. Run dig +noall +answer www.wikipedia.org twice, ten seconds apart. Look for: the TTL counting down by about ten, and a much lower query time on the second run: the resolver answered from cache.
  3. Walk the tree yourself. dig +trace api.github.com. Look for: root servers answering first with NS records for com., then .com servers answering with GitHub's name servers, then GitHub's servers giving the answer. This is exactly what a recursive resolver does on a cache miss.
  4. Look at other record types. dig +short NS github.com, dig +short MX gmail.com, dig +short TXT google.com, dig +short CAA google.com, dig +short HTTPS cloudflare.com. Look for: delegation, mail servers with priorities, verification and SPF strings, the certificate authorities allowed to issue, and HTTP/3 advertised in DNS (alpn="h3,h2").
  5. See a negative answer. dig no-such-name-12345.example.com. Look for: status: NXDOMAIN and an SOA record in the AUTHORITY section: its last number and its TTL set how long resolvers will cache "does not exist".
  6. Reverse lookup. dig -x 8.8.8.8 +short. Look for: dns.google., served from a PTR record under 8.8.8.8.in-addr.arpa.
  7. Compare resolvers. dig @1.1.1.1 +short www.netflix.com and dig @8.8.8.8 +short www.netflix.com. Look for: possibly different addresses: the answer depends on who asks and from where.
  8. DNS over HTTPS with curl. curl -s -H 'accept: application/dns-json' 'https://cloudflare-dns.com/dns-query?name=example.com&type=A'. Look for: a JSON answer with the same data, fetched over an encrypted HTTPS connection that an on-path observer cannot read.
  9. Your own stub configuration. cat /etc/resolv.conf (Linux/WSL) or scutil --dns (macOS) or Get-DnsClientServerAddress (Windows). Look for: which resolver your machine uses and any search domains; this is the first thing to check when "DNS works for me but not for them".
Plan a migration

You are moving api.example.com from an old load balancer (A record 203.0.113.10, TTL 86400) to a new one in another region, with no downtime. Internal Java services and external customers both call it. Write the plan.

Answer
  1. Two days ahead: lower the TTL on api.example.com from 86400 to 60. Wait at least 24 hours (the old TTL) so every cache has picked up the short TTL.
  2. Prepare: bring the new load balancer up and verify it end to end by testing with a hosts-file override or curl --resolve api.example.com:443:<new IP>, including TLS certificates for the name.
  3. Shift gradually if the provider supports it: weighted records sending 10%, then 50%, then 100% to the new endpoint, watching error rates and latency at each step. Otherwise switch the record in one change.
  4. Keep the old endpoint serving and watch its traffic. It will not drop to zero at 60 seconds: long-lived connection pools, JVM or library DNS caches and customers with odd resolvers keep using it. For internal Java services, check the DNS cache TTL setting and bound connection lifetimes, or restart them in a rolling fashion to pick up the change.
  5. Decommission only when old traffic has been near zero for a while (hours to days), then remove the old load balancer, and only then raise the TTL back to something like 300 to 3600.
  6. Rollback plan: during the window, switching the record back takes effect within about a minute, because the TTL is 60.
Diagnose: the five-second stalls

After a traffic increase, several services in a Kubernetes cluster show p99 latency spikes of almost exactly 5 seconds on calls to external APIs. Internal service-to-service calls are mostly fine. What is going on, and what do you check and change?

Answer

An exact 5 seconds is the fingerprint of the stub resolver's default timeout: some DNS queries get no answer and are retried after 5 s. External names are hit hardest because of ndots:5: each lookup of api.partner.com becomes up to eight queries through the search domains, multiplying the chance that one is dropped, and the load on CoreDNS grew with traffic.

Check CoreDNS pods' CPU, query rate and error metrics and whether they are being throttled; check the upstream resolver's limits (cloud resolvers rate-limit per interface); and check for dropped UDP packets (conntrack table and the known race when A and AAAA queries share a socket). Fix by: using fully qualified external names with a trailing dot or setting ndots:2 in the pod dnsConfig; deploying node-local DNS caching so most lookups never cross the network; scaling CoreDNS; adding single-request-reopen or reducing the timeout in the pod DNS options; and making HTTP clients reuse connections so they resolve far less often.
