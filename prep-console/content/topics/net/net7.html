By the time a request reaches your service, DNS, TCP and TLS have done their jobs, and what arrives is an HTTP message. Almost every API you build or call, every web page, every webhook and every call to an LLM provider is HTTP. The protocol looks simple, a verb, a path, some headers, a body, and that simplicity hides a lot of precise meaning that systems all along the path depend on.

Consider what goes wrong when that meaning is misunderstood. A mobile app retries a timed-out "place order" request and the customer is charged twice, because the request was a POST with no idempotency key. A CDN serves one user's account page to thousands of strangers, because the page was marked as cacheable. A deploy goes out and half the users see a broken page for a day, because the HTML was cached with a long max-age and pointed at old JavaScript. A front-end team spends a week fighting "CORS errors" that curl never shows. A load balancer returns 502s and nobody knows whether to blame the balancer or the service. Each of these is a misunderstanding of HTTP semantics, not of networking.

"Semantics" means the meaning of messages, independent of how they are carried. HTTP/1.1 sends text over TCP, HTTP/2 sends binary frames over TCP, HTTP/3 sends frames over QUIC (net8 compares them), but a GET, a 304 or a Cache-Control header means exactly the same in all three. Learn the meaning once and it applies everywhere.

This lesson covers the parts that matter in interviews and in production: the anatomy of a message, methods and the crucial ideas of safety and idempotency, status codes and what each tells a client to do, the headers you will meet most, caching and revalidation, conditional requests for safe concurrent updates, cookies and sessions, and the browser's same-origin policy and CORS. Along the way it points out the security and caching mistakes each feature invites.

A request and a response

HTTP is a request-response protocol. A client sends a request naming a resource (the thing a URL identifies, like an order or an image) and a method (what to do with it); the server sends back a response with a status code (how it went). Both can carry headers, lines of metadata, and a body. In HTTP/1.1 they are literally lines of text:

Four ideas that carry most of the meaning

Methods have promises. GET promises not to change anything (it is safe). PUT and DELETE promise that doing them twice is the same as doing them once (they are idempotent). POST promises neither. Those promises decide what browsers, proxies and client libraries may retry or cache automatically.

Status codes tell the client what to do next. 2xx: done. 3xx: look elsewhere or use your copy. 4xx: you made a mistake, do not just repeat it. 5xx: we failed, maybe try later.

Responses can be reused. A response can say "you may keep and reuse me for 60 seconds" (Cache-Control: max-age=60). Browsers and CDNs then answer from their copy without asking the server, which is the biggest performance lever on the web.

The browser keeps sites apart. A page from one site cannot read responses from another site unless that site explicitly allows it (CORS), and browsers carry small pieces of state per site (cookies), with rules about when to send them.

A worked example: one image, three visits

A browser requests /logo.png. The first time, it has nothing stored, so it sends a GET and receives 200 OK with the image, Cache-Control: max-age=3600 and ETag: "v7". It stores the image. Ten minutes later the page needs the logo again: the stored copy is only 600 seconds old, still fresh, so the browser uses it without sending anything. Two hours later the copy is stale, so the browser sends GET /logo.png with If-None-Match: "v7". The logo has not changed, so the server answers 304 Not Modified with no body, and the browser reuses its copy for another hour. Three visits, one download. Section 5 of the body draws this as a flow.

The analogy, and where it breaks

HTTP is like ordering at a counter by writing slips. The slip says what you want (method and resource) and carries notes (headers: "I prefer JSON", "here is my membership card"). The clerk hands back a result with a stamp (status code) and notes of their own ("this answer is good for an hour"). Where it breaks: there are many clerks in a chain between you and the kitchen (proxies, CDNs, load balancers), and each of them reads the notes and may answer on the kitchen's behalf. HTTP's precise rules exist largely so that those intermediaries do the right thing.

1. Methods, safety and idempotency

MethodMeaningSafeIdempotent
GETfetch a representation of the resourceyesyes
HEADlike GET but headers onlyyesyes
OPTIONSask what is allowed (used by CORS preflight)yesyes
PUTstore this representation at this URL (create or replace)noyes
DELETEremove the resourcenoyes
POSTprocess this body (create a child resource, run an action)nono
PATCHapply these partial changesnonot by default

A safe method is one the client does not intend to change anything. That is why browsers prefetch links with GET, crawlers follow them, and caches store their responses; it is also why an endpoint like GET /delete?id=5 is a disaster waiting for a crawler.

An idempotent method is one where sending the request twice leaves the server in the same state as sending it once. PUT /users/7 with a full profile: repeat it and the profile is the same. DELETE /orders/9: repeat it and the order is equally gone (the second response may be 404, but the state is the same). POST /orders: repeat it and you have two orders.

Why this matters so much: networks fail in the middle. A client sends a request, the connection drops, and the client cannot know whether the server processed it. For idempotent methods the answer is easy, just retry, and HTTP clients, proxies and load balancers do so automatically. For POST, a blind retry might duplicate the action, so they do not. The standard fix is an idempotency key: the client generates a unique ID for each logical operation and sends it in a header (Stripe popularised Idempotency-Key, and the IETF is standardising it). The server stores the key with the result of the first successful attempt and, if the same key arrives again, returns the stored result instead of acting again.

PATCH is not idempotent by default because a patch can be relative ("add 1 to the quantity"); a patch that sets absolute values happens to be idempotent, but clients cannot assume it.

Three distinctions come up in interviews. 401 versus 403: "who are you?" versus "you may not". 301/302 versus 308/307: the older pair historically allowed clients to change a POST into a GET when following the redirect; 307 and 308 guarantee the method and body are kept. 502 versus 503 versus 504: all typically generated by a proxy or load balancer rather than your code; 502 says the upstream misbehaved or the connection broke (for example the idle-timeout race in net4), 503 says there was nobody healthy to send to or the server is shedding load, and 504 says the upstream took too long. Knowing which component emitted the error is the first step in debugging it.

3. Headers you will meet constantly

Header names are case-insensitive (HTTP/2 and HTTP/3 send them in lowercase). Grouped by job:

  • Describing the body: Content-Type (application/json; charset=utf-8), Content-Length (bytes), Content-Encoding (gzip, br).
  • Content negotiation: the client says what it can accept (Accept, Accept-Encoding, Accept-Language) and the server picks a representation.
  • Identity and credentials: Authorization: Bearer <token>, Cookie, and in responses WWW-Authenticate (with 401) and Set-Cookie.
  • Routing and proxies: Host (which site, since many share an IP), X-Forwarded-For or the standard Forwarded (original client IP; trust it only when set by your own proxies, net3), X-Request-ID or traceparent for tracing.
  • Caching and conditions: Cache-Control, ETag, Last-Modified, If-None-Match, If-Match, Vary, Age.
  • Flow control for clients: Retry-After, Location.
  • Security: Strict-Transport-Security (HSTS, net2), Content-Security-Policy, X-Content-Type-Options: nosniff, and the CORS headers in section 7.

4. Caching: freshness

A cache stores responses and reuses them for later requests. There are two kinds: the browser's private cache, used by one user, and shared caches, such as CDNs and reverse proxies, used by many users. The response's Cache-Control header governs both:

  • max-age=N: the response is fresh for N seconds and may be reused without asking the server. s-maxage=N overrides it for shared caches only.
  • no-cache: may be stored, but must be revalidated with the server before every reuse. (Despite its name, it does not mean "do not cache".)
  • no-store: must not be stored anywhere. For sensitive responses.
  • private: only the browser may store it, never a shared cache. public: shared caches may store it even if it would otherwise not be cacheable (for example, a response to an authenticated request).
  • immutable: the content will never change at this URL, so do not even revalidate when the user reloads.
  • stale-while-revalidate=N: after expiry, a cache may serve the stale copy for up to N more seconds while fetching a fresh one in the background, hiding revalidation latency.

If a response has no explicit freshness information, caches may guess a heuristic lifetime, commonly 10% of the time since its Last-Modified date, which is a frequent source of "why is this cached?" surprises. Be explicit.

A cache must also know when two requests can share a response. The cache key is normally the method and the URL. If the response depends on a request header, say the server returns Brotli to clients that accept it and plain text to others, the server must list that header in Vary (Vary: Accept-Encoding) so caches keep one copy per value. Forget Vary and a CDN serves the Brotli copy to a client that cannot decode it, or the French page to everyone. Over-use Vary (for example Vary: Cookie or Vary: User-Agent) and the cache holds thousands of near-duplicate copies with almost no hits.

5. Caching: revalidation and the 304

When a stored response becomes stale, the cache does not have to download it again. It asks the server whether its copy is still good, using a validator the server sent with the original response:

There are two validators. An ETag is an opaque version string, such as a hash of the content (ETag: "v7"); the client revalidates with If-None-Match: "v7". Last-Modified is a timestamp; the client revalidates with If-Modified-Since. If nothing changed, the server replies 304 Not Modified with no body, and the cache refreshes its copy's freshness. The saving is bandwidth and server work, but not the round trip.

The standard pattern for web assets combines both ideas. Build tools give static files content-hashed names (app.3f9a1.js); since a change produces a new URL, the file can be cached "forever": Cache-Control: public, max-age=31536000, immutable. The HTML page that references them is served with no-cache and an ETag, so every visit revalidates it cheaply and picks up new asset names immediately after a deploy.

6. Conditional requests for safe updates

The same validators solve a completely different problem: two people editing the same thing. Alice and Bob both GET document 12 (ETag "v7"). Alice saves first with PUT /docs/12 and If-Match: "v7"; the version matches, so the server applies it and the ETag becomes "v8". Bob then saves with If-Match: "v7"; the current version is "v8", so the server refuses with 412 Precondition Failed instead of silently overwriting Alice's work. Bob's client re-reads, merges or asks him, and retries. This is optimistic concurrency control built into HTTP: no locks, just a check at write time. A server can insist that clients use it by answering unconditional writes with 428 Precondition Required.

7. Cookies and sessions

HTTP itself is stateless: each request stands alone. Cookies add state. A server sends Set-Cookie: session=abc123; ...attributes, the browser stores it, and on later requests to that site it sends Cookie: session=abc123. A login session is usually just a random session ID in a cookie, mapped to the user on the server, or a signed token.

The attributes are where the security lives:

  • Secure: only send over HTTPS, so it cannot be sniffed on the network.
  • HttpOnly: JavaScript cannot read it, so a script injected by XSS (cross-site scripting) cannot steal the session.
  • SameSite=Strict | Lax | None: whether the browser attaches the cookie to requests that another site triggers. This is the main defence against CSRF (cross-site request forgery), where evil.example contains a hidden form that posts to your bank, and the browser would otherwise helpfully attach your bank cookie. Strict sends it only for requests initiated from the same site; Lax also allows top-level navigations such as following a link, but not cross-site POSTs, images or scripts; None always sends it and requires Secure. Chromium-based browsers treat cookies with no SameSite attribute as Lax.
  • Domain and Path: which hosts and paths receive it. Setting Domain=example.com sends it to every subdomain, which widens exposure; the __Host- name prefix forces a cookie to be host-only, Secure and Path=/.
  • Max-Age or Expires: lifetime; without them it is a session cookie deleted when the browser closes.

Keep cookies small: browsers limit each to about 4 KB, and every cookie for a domain is sent on every request to it, including image requests, adding bytes to every round trip.

8. The same-origin policy and CORS

An origin is the triple of scheme, host and port: https://app.example.com and https://api.example.com are different origins, as are http:// and https:// versions of the same host. The browser's same-origin policy says a script loaded by one origin may send requests to another origin but may not read the responses. Without it, any web page you visit could use your logged-in cookies to read your email from your webmail's API.

Legitimate sites often need cross-origin reads, for example a front end on app.example.com calling an API on api.example.com. CORS (Cross-Origin Resource Sharing) lets the API opt in with response headers. For a simple request (GET, HEAD or POST with only basic headers and a form or plain-text content type), the browser just sends it with an Origin header, and lets the script read the response only if it carries Access-Control-Allow-Origin matching that origin. For anything else, including JSON bodies and Authorization headers, which covers most API calls, the browser first sends a preflight:

For requests with credentials (cookies or HTTP authentication), the rules tighten: the server must name the exact origin (the wildcard * is refused) and add Access-Control-Allow-Credentials: true. Servers typically check the request's Origin against an allow-list, echo it back when it matches, and add Vary: Origin so a cache does not serve one origin's CORS headers to another.

Keep in mind what CORS is and is not. It is a browser feature that relaxes the same-origin policy. It does not stop curl, a server, or an attacker's script from calling your API; it only controls whether a web page running in a user's browser may read the answer. Your API still needs authentication and authorisation.

Idempotency keys done properly

An idempotency key only works if storing the key and performing the side effect are atomic, or at least ordered carefully. The robust design: on receipt, insert the key into a table with a unique constraint and status "in progress"; if the insert fails because the key exists, return the stored response if complete, or 409 if still in progress; perform the operation in the same database transaction that records the result against the key, or, when the side effect is external (charging a card through a payment provider), pass the same key downstream so the provider deduplicates too. Keys should expire after a retention window (Stripe keeps them for at least 24 hours), and a request that reuses a key with a different body should be rejected rather than silently answered with the old result. This is the HTTP face of the distributed-systems problem that sc11 covers in depth.

Cache keys, deception and poisoning

Shared caches are a common source of serious incidents because they multiply one mistake across all users. Web cache deception exploits a mismatch between how the cache and the origin interpret a URL: a CDN rule says "cache anything ending in .css", the application routes /account/settings.css to the account page (ignoring the suffix), and the CDN stores a logged-in user's page for anyone to fetch. Cache poisoning is the reverse: an attacker finds a request header that changes the response but is not part of the cache key (an unkeyed header, such as X-Forwarded-Host used to build absolute URLs), sends a request with a malicious value, and the poisoned response is cached and served to everyone. Defences are to make the origin the single source of truth for cacheability (personalised responses marked private or no-store, and CDNs configured to respect it), never cache responses that set cookies, make routing strict about paths, and avoid using unkeyed headers to generate content.

Content negotiation versus separate URLs

HTTP lets one URL return different representations depending on Accept, Accept-Language and Accept-Encoding. Compression negotiation works well because it is universal and caches handle Vary: Accept-Encoding specially. Language and format negotiation work less well in practice: they fragment caches, make links ambiguous (which language does a shared link show?), and are invisible to users. Many APIs therefore put the version and format in the URL or a dedicated header, and sites put the language in the path, reserving negotiation for compression and image formats.

Retries across layers

A single user click may pass through a browser, a CDN, a load balancer, a service mesh sidecar and an HTTP client library, and each may retry on failure. If each retries three times, one failing request can become 35 = 243 attempts at the bottom layer, turning a small outage into a self-inflicted overload (a retry storm). The HTTP semantics give the tools to control it: only idempotent requests are retried by intermediaries, 429 and 503 carry Retry-After, and well-designed systems retry at one layer with exponential backoff and jitter, with budgets that cap retries as a fraction of traffic (sc12 covers resilience patterns).

Partial responses and HEAD

Two less glamorous features matter for large objects such as model weights, datasets and video. A Range: bytes=1000000-1999999 request asks for part of a resource, and a server that supports it answers 206 Partial Content with just those bytes. Download tools use ranges to resume interrupted transfers and to fetch one file in parallel pieces over several connections (the fix for a single connection's window limit from net4); video players use them to seek. Combined with If-Range and an ETag, a client resumes only if the file has not changed in the meantime. HEAD returns the headers of a GET without the body, so a client can check size, type and ETag before committing to a download.

Security headers as a layered defence

Beyond cookies and CORS, a handful of response headers harden browsers' handling of your pages. Content-Security-Policy restricts where scripts, styles and frames may come from, and with nonces or hashes can block injected inline scripts, the most effective XSS mitigation after output encoding. X-Content-Type-Options: nosniff stops browsers guessing a response's type, closing attacks where an uploaded file is interpreted as a script. Referrer-Policy limits how much of the current URL leaks to other sites. Cross-origin isolation headers (COOP and COEP) are needed to unlock powerful features such as shared memory, because they guarantee the page cannot be mixed with other origins' data. None of these replaces correct code, but each turns a class of bugs from exploitable into harmless.

Characteristic failures

  • Duplicate side effects from retries. Mobile clients on flaky networks, load balancers retrying on connection resets, and users double-clicking all produce repeated POSTs. Symptoms: duplicate orders, double charges, duplicate emails. Fix with idempotency keys end to end.
  • Private data in shared caches. On 25 December 2015, during a denial-of-service attack, Valve changed the caching configuration of its Steam store's CDN to cope with the load; personalised store pages were cached and served to other users. Between 11:50 and 13:20 Pacific time, pages for about 34,000 users, some showing billing addresses, partial card digits, email addresses and purchase history, may have been seen by others. The lesson: cacheability must be decided by the origin per response, and emergency cache rules are exactly where these mistakes happen.
  • Stale front ends after deploys. HTML cached with a long max-age keeps referencing old bundles, or new HTML references bundles not yet uploaded to the CDN. Fix with hashed asset names, short-lived HTML and deploying assets before HTML.
  • CORS breakage. After moving an API to a new subdomain, the front end fails with CORS errors while curl works. Usually the allow-list lacks the new origin, the preflight is blocked by authentication middleware, or a credentialed request receives *. Browser DevTools' console and network tab show the preflight and the missing header.
  • Misattributed 5xx. 502 and 504 come from proxies; teams look in application logs and find nothing. Check which component generated the response (load balancer logs usually record whether the target responded) before debugging the application.
  • Cache fragmentation. A CDN hit ratio collapses after someone adds Vary: User-Agent or a per-user query parameter; origin load jumps. Watch hit ratio as a key metric.

Observability

Log method, path template (not raw path, to keep cardinality low), status code, latency, response size, cache status and request ID for every request at the edge and in services. Track rates of 4xx and 5xx separately, and break 5xx down by code and by emitting component. At the CDN, track hit ratio, origin request rate and bytes served from cache. In browsers, the Network panel shows each response's headers, whether it came from memory or disk cache, and CORS preflights. The Age response header shows how long a shared cache has held a response, and many CDNs add a cache-status header (for example cf-cache-status or x-cache) saying HIT or MISS.

A debugging order for 'the API returns the wrong thing'

First establish which component produced the response: look at server, via, age and cache-status headers, and compare with the origin's own logs. If the response came from a cache, ask why it was cacheable and what the cache key was. If it came from a proxy (a 502 or 504 with a proxy's error page), look at that proxy's logs and upstream health. Only if it came from your application does the application's code become the suspect. Reproducing with curl -v and the exact headers the client sent (cookies, Accept-Encoding, Origin) usually settles it in minutes.

Knobs

Cache-Control per response type; CDN rules for what to cache and which headers and cookies form the cache key; CORS allow-lists and preflight max-age; cookie attributes on every Set-Cookie; retry policies in clients and proxies (which methods, how many times, with what backoff); idempotency key retention; and default security headers set centrally at the edge.

Fifteen minutes with curl and a browser. You will read raw messages, trigger status codes, watch a 304, set cookies and see CORS enforced by a browser but not by curl. On Windows PowerShell use curl.exe.

  1. Read a raw exchange. curl -v https://httpbin.org/get -o /dev/null. Look for: lines starting with > (your request line and headers) and < (the status line and response headers). Note Host, User-Agent, Accept, content-type and access-control-allow-origin.
  2. Status codes on demand. curl -s -o /dev/null -w '%{http_code}\n' https://httpbin.org/status/503, then /status/429 and /status/404. Then curl -si 'https://httpbin.org/redirect-to?url=/get&status_code=308' | head -5. Look for: the codes and, for the redirect, a location header. Add -L to follow it.
  3. Revalidation with an ETag. curl -si https://httpbin.org/etag/v7 | head -8 shows etag: v7. Now send it back: curl -si -H 'If-None-Match: "v7"' https://httpbin.org/etag/v7 | head -3. Look for: 304 and no body: "your copy is still good". Try a different tag and you get 200 with a body.
  4. Caching headers of a real site. curl -sI https://www.wikipedia.org | grep -Ei 'cache-control|age|etag|vary|x-cache'. Then pick a static asset from any site's page source (a .js or .css file) and do the same. Look for: short or no-cache policies on HTML, long max-age or immutable on hashed assets, an age header and HIT or MISS from the CDN.
  5. Cookies. curl -si 'https://httpbin.org/cookies/set?session=abc123' | grep -i set-cookie. Then use a cookie jar: curl -s -c jar.txt -b jar.txt -L 'https://httpbin.org/cookies/set?session=abc123' followed by curl -s -b jar.txt https://httpbin.org/cookies. Look for: the server setting a cookie and curl sending it back on the next request, which is all a browser session is.
  6. CORS is a browser rule. Open https://example.com in a browser, open the DevTools console and run fetch('https://httpbin.org/get').then(r => r.json()).then(console.log): it works, because httpbin sends Access-Control-Allow-Origin. Now run fetch('https://www.wikipedia.org/').then(r => r.text()).then(console.log). Look for: a CORS error in the console, and in the Network tab, the request itself was sent and got a response; the browser just refused to let the page read it. Now run curl -s https://www.wikipedia.org/ | head -3: curl reads it fine. That difference is the whole point of CORS.
  7. Trigger a preflight. In the same console: fetch('https://httpbin.org/anything', {method: 'PUT', headers: {'Content-Type': 'application/json'}, body: '{}'}). Look for: in the Network tab, an OPTIONS request before the PUT, with Access-Control-Request-Method and Access-Control-Request-Headers.
Design the headers

A product catalogue site has: (1) the HTML shell of a single-page app, (2) hashed JavaScript and CSS bundles, (3) GET /api/products/42, the same for everyone and updated a few times a day, (4) GET /api/me/cart, per user, (5) POST /api/orders. Everything goes through a CDN. Give the caching (and any other) headers for each, and explain.

Answer
  1. HTML shell: Cache-Control: no-cache with an ETag. Every load revalidates cheaply (304 when unchanged) and picks up new bundle names right after a deploy. A very short s-maxage (say 60) lets the CDN absorb load if needed.
  2. Hashed bundles: Cache-Control: public, max-age=31536000, immutable. The hash in the file name changes whenever the content does, so these can be cached for a year by browsers and the CDN. Deploy them before the HTML that references them.
  3. Product API: Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=600 plus an ETag. Browsers reuse it for a minute, the CDN for five minutes, and after that can serve it while refreshing in the background. When prices change, purge the CDN URL or accept up to five minutes of staleness. If it varies by language, add Vary: Accept-Language or better, put the language in the URL.
  4. Cart: Cache-Control: private, no-store (or private, no-cache if you want browser revalidation). It must never be stored by the CDN; also make sure the CDN is configured not to cache responses to requests carrying the session cookie.
  5. Orders: POST responses are not cached by default; send Cache-Control: no-store anyway. Require an Idempotency-Key header so retries after timeouts do not create duplicate orders, and return 201 Created with a Location header.

Cookies for the session: HttpOnly; Secure; SameSite=Lax; Path=/, ideally with a __Host- prefix. If the API is on a different origin from the page, configure CORS with an explicit allow-list, credentials allowed, and Vary: Origin.

Diagnose: the double charge

Customers occasionally get charged twice. Logs show two POST /api/payments requests with identical bodies about 30 seconds apart, both returning 200. The app uses a mobile HTTP client with automatic retries, and there is a load balancer with a 30-second timeout in front of the payments service. Explain and fix.

Answer

The payment call sometimes takes longer than 30 seconds (a slow downstream card processor). The load balancer times out and returns 504 to the client while the service keeps processing and eventually succeeds. The client, seeing a 504, retries the POST, which is not idempotent, so the service charges again. Two successful charges, two 200s in the service's logs, and one confused customer.

Fix: the client generates an idempotency key per payment attempt and reuses it on every retry; the service records the key atomically with the charge and returns the stored result for duplicates, and passes the same key to the card processor. Also: make clients retry POSTs only when they carry an idempotency key; align timeouts so the load balancer's is longer than the service's own deadline for the downstream call; and consider making long payments asynchronous (return 202 Accepted and let the client poll), so no request sits open for 30 seconds.
