In net7 you learned what an HTTP message means. This lesson is about how it is carried, and why that changed twice in a decade. The answer is a story about the modern web outgrowing its protocol.

HTTP/1.1 was standardised in 1997, when a web page was an HTML file and a few images. Today a typical page makes 50 to 100 requests for scripts, styles, fonts, images and API data, and a mobile app may fire dozens of API calls on launch. HTTP/1.1 can only have one request in flight on a connection at a time, so browsers opened about six connections per host and developers invented a whole toolkit of hacks, such as spreading assets across many hostnames and gluing images into sprite sheets, just to get more requests moving in parallel. Each extra connection paid its own TCP and TLS handshake and its own slow start (net4).

HTTP/2, published in 2015 and grown from Google's SPDY experiment, fixed that by letting many requests share one connection at the same time. Then its own limit surfaced: all those requests shared one TCP byte stream, so on lossy mobile networks a single dropped packet froze every request at once. HTTP/3, published in 2022, moved HTTP onto QUIC (net5) to remove that last bottleneck.

For an engineer this is not history trivia. The version in use changes how load balancers must be configured (a gRPC service can end up sending all its traffic to one pod), which performance hacks help or hurt, how large downloads behave through proxies, which attacks your edge must defend against, and how you debug a slow request. Interviewers ask about it because it tests whether you understand the layers underneath, and not just the API on top.

This lesson walks through each version's wire format and connection model, the three kinds of head-of-line blocking and which version fixes which, header compression, how versions are negotiated hop by hop, and the operational consequences for proxies, gRPC and security.

Same letter, different envelopes and roads

Think of an HTTP request as a letter. Its meaning, what you are asking for, is the same whichever way you send it. HTTP/1.1 sends letters one at a time down a single-lane road: the next letter cannot leave until the reply to the previous one has come back. To go faster you hire more roads (connections), each of which costs time to set up. HTTP/2 cuts every letter into numbered strips, interleaves strips from many letters on one road, and reassembles them at the other end, so dozens of letters travel at once. But the road is still a single lane that must deliver strips in exact order, so if one strip is lost, everything behind it waits. HTTP/3 gives each letter its own lane on a new kind of road (QUIC), so a lost strip only delays its own letter.

Where the analogy breaks: the "roads" are not free to build. Each new connection costs round trips for handshakes and starts slowly while TCP probes the network, which is why "just open more connections" was never a good answer.

A short history

By the late 2000s, page load times were dominated by round trips rather than bandwidth, and Google began experimenting with a replacement wire format called SPDY, deployed between Chrome and Google's servers from 2009. Its core ideas, binary framing, multiplexed streams and header compression, became HTTP/2 in 2015. Google's next experiment, running HTTP over its own UDP-based transport, became QUIC and HTTP/3, standardised in 2021 and 2022. Each step was driven by measurements of real users, which is also how you should decide whether a change helps your own traffic.

What that looks like in time

How your code sees it

Mostly, it does not. Browsers negotiate the best version automatically. HTTP client libraries do too, if enabled: Python's httpx needs http2=True, Go's standard client uses HTTP/2 automatically over TLS, and gRPC always uses HTTP/2. What your code does control is connection reuse. A client object created once and reused keeps its HTTP/2 connection open and multiplexes all calls over it; a client created per request throws that away and pays a new handshake every time, under any version.

If you remember one thing: every version sends the same HTTP messages, and each new version exists to remove a kind of waiting that the previous one imposed.

1. HTTP/1.1: text, keep-alive and one request at a time

An HTTP/1.1 message is text: a request line, header lines, a blank line, then the body, exactly as drawn in net7. Because TCP is a byte stream, the receiver must know where each message ends. For bodies it uses either a Content-Length header or chunked transfer encoding, where the body is sent as a series of chunks each prefixed with its size, ending with a zero-size chunk, used when the length is not known in advance (for example, a streamed response).

HTTP/1.0 opened a new TCP connection for every request. HTTP/1.1 made persistent connections (keep-alive) the default: after a response, the connection stays open and the next request reuses it, saving the TCP and TLS handshakes and keeping the congestion window warm. But reuse is sequential. The client sends a request, waits for the whole response, then sends the next.

HTTP/1.1 did define pipelining, sending several requests without waiting, but the responses must come back in the same order as the requests, because nothing in an HTTP/1.1 response says which request it answers. If the first response is slow (a big image, or a slow database query), all the responses queued behind it wait, even if they are ready. This is head-of-line blocking at the application level. Combined with buggy proxies, it made pipelining so unreliable that browsers never enabled it.

So browsers parallelise by opening multiple connections, about six per host. That in turn produced the HTTP/1.1 performance toolkit: domain sharding (serving assets from img1.example.com, img2.example.com to get six connections to each), sprite sheets (many small images glued into one file), concatenating all scripts into one bundle, and inlining small resources into the HTML. All of them work around the one-request-per-connection limit, and all of them have costs: more DNS lookups and handshakes, worse caching, and more bytes when only part of a bundle is needed.

A final HTTP/1.1 cost is headers. They are sent as uncompressed text on every request, and they are highly repetitive: the same cookies, user agent and accept headers, often 500 bytes to over 1 KB per request. For a page making 80 requests, that is tens of kilobytes of repeated headers on a mobile uplink.

2. HTTP/2: frames and streams

HTTP/2 keeps HTTP's meaning and changes the encoding completely. Every message is split into frames: small binary units, each with a 9-byte header that gives its length, its type and the ID of the stream it belongs to. A stream is one request/response exchange. The frame types you need to know:

  • HEADERS: opens a stream and carries the compressed request or response headers.
  • DATA: carries a piece of a body.
  • SETTINGS: each side announces its limits, such as the maximum number of concurrent streams (often 100 or more) and initial flow-control window sizes.
  • WINDOW_UPDATE: grants the peer permission to send more bytes (flow control, below).
  • RST_STREAM: cancels one stream without closing the connection, for example when the user navigates away.
  • GOAWAY: tells the peer the connection is closing and which streams were processed, for graceful shutdown.
  • PING: measures round-trip time and keeps idle connections alive.

The consequences follow directly. A browser needs only one connection per origin, so one handshake and one congestion window that warms up and stays warm. Slow responses do not block fast ones. And the HTTP/1.1 hacks become counterproductive: sharding across hostnames now adds connections, handshakes and cold congestion windows, and splits the header compression context.

HTTP/2 also added flow control per stream on top of TCP's. Each stream and the whole connection have a window, 65,535 bytes by default, that the receiver enlarges with WINDOW_UPDATE frames as it consumes data. The point is fairness inside the connection: without it, one huge download could fill the receiver's buffers and starve every other stream. The side effect is a second place throughput can be capped, as the drill shows.

Two HTTP/2 features did not survive contact with reality. Prioritisation let clients describe a tree of dependencies between streams ("send the CSS before the images"), but implementations were inconsistent; it was replaced by a much simpler Priority header with an urgency level (RFC 9218), also used by HTTP/3. Server push let servers send resources before they were requested, but servers could not know what the browser already had cached; Chrome removed it in 2022, and the modern replacement is the 103 Early Hints response plus preload hints (net2).

3. Header compression: HPACK

HTTP/2 compresses headers with HPACK. Both ends keep a static table of 61 common header fields and values (such as :method: GET and accept-encoding: gzip, deflate) and a dynamic table, per connection, of headers recently sent. A header already in a table is sent as a small index number; a new one is sent literally (with Huffman coding to shrink the text) and optionally added to the dynamic table for next time. On the second request to a site, a 700-byte header block with a big cookie can shrink to a few dozen bytes. HTTP/2 also turns the request line into pseudo-headers (:method, :path, :scheme, :authority) and requires header names in lowercase.

HPACK was designed to avoid the compression side-channel attacks (such as CRIME) that hit general-purpose compression of headers: it does not let attacker-controlled data be compressed together with secrets in a way that leaks them through the output length, and sensitive values can be marked never to enter the dynamic table.

4. The remaining problem: TCP head-of-line blocking

HTTP/2's streams are independent only at the HTTP layer. Underneath, all frames of all streams travel in one TCP byte stream. If the packet carrying a DATA frame for stream 1 is lost, TCP holds back every byte after it, including complete frames for streams 3 and 5, until the retransmission arrives (net4 showed the mechanism). On a clean wired connection that happens rarely. On a mobile network with 1 to 2% loss, it happens constantly, and measurements found HTTP/2 could be slower than HTTP/1.1, whose six independent connections meant a loss stalled only one of them. There are therefore three kinds of head-of-line blocking to keep apart: HTTP/1.1's response ordering (fixed by HTTP/2), TCP's byte ordering (fixed by HTTP/3), and, within a single stream, data still arriving in order (inherent in any ordered stream).

5. HTTP/3: HTTP over QUIC

HTTP/3 maps each request/response onto its own QUIC stream (net5). QUIC delivers each stream's bytes in order but treats streams independently, so a lost packet delays only the streams whose data it carried. HTTP/3's own frames are simpler than HTTP/2's because QUIC already provides streams, flow control and connection management: it mostly needs HEADERS and DATA frames per request stream, plus a control stream for settings.

Header compression had to be redesigned. HPACK's dynamic table depends on header blocks being processed in the exact order they were sent; over independent QUIC streams, a stream would have to wait for an earlier stream's table update, reintroducing head-of-line blocking. QPACK sends dynamic table updates on separate, dedicated streams and lets the encoder choose, per header block, whether to refer to entries the decoder may not have yet (and risk waiting) or to avoid them.

HTTP/3 also inherits QUIC's benefits: a combined transport and TLS handshake (one round trip, or zero with resumption), connection migration when a phone changes networks, and encrypted transport headers. And it inherits QUIC's costs: more CPU per byte, UDP that some networks block, and less passive visibility.

6. Negotiation, hop by hop

A client does not choose a version once for the whole path; each hop negotiates separately.

  • HTTP/2 over TLS is negotiated inside the TLS handshake with ALPN: the ClientHello lists h2 and http/1.1, and the server picks one in its reply, at no extra cost.
  • HTTP/2 without TLS (h2c) is not supported by browsers; it is used internally, for example by gRPC, with the client simply assuming the server speaks HTTP/2 ("prior knowledge").
  • HTTP/3 uses a different transport, so it cannot be negotiated within a TCP connection. The server advertises it with Alt-Svc: h3=":443" in a response, or with an HTTPS DNS record, and the client tries QUIC on subsequent connections, keeping TCP as a fallback.

7. A worked comparison

Take a page that needs 60 resources from one origin, a user 80 ms away, and assume each response is small. Under HTTP/1.1 with six connections, the browser pays six TCP and TLS handshakes (in parallel, about 160 ms with TLS 1.3), then each connection fetches about ten resources one after another: roughly ten round trips, 800 ms, plus the handshakes, close to a second before everything arrives, with six congestion windows each warming up separately. Under HTTP/2 on one connection, it pays one handshake, then requests all 60 at once; responses stream back as fast as the single connection's congestion window allows, typically two or three round trips once the window has grown: a few hundred milliseconds. Now add 2% packet loss. HTTP/1.1's six connections each suffer occasional stalls, but a stall freezes only a sixth of the page. HTTP/2's single connection stalls entirely on every loss, and each loss also halves its one congestion window. That is the case where HTTP/2 can lose to HTTP/1.1 and where HTTP/3 wins clearly, since QUIC's loss affects only some streams, while its congestion control behaves like TCP's.

8. What to change when you upgrade

Turning on HTTP/2 or HTTP/3 at the edge is a configuration change, but a few related changes capture the benefit. Remove domain sharding and serve assets from as few origins as practical, or at least from origins that can share a connection through coalescing. Revisit bundling: split code by route or by how often it changes, so a deploy invalidates less. Replace server push, if any, with preload and Early Hints. Check that proxies raise HTTP/2 flow-control windows and allow enough concurrent streams. Move gRPC and HTTP/2 service traffic onto layer-7 balancing. And measure real users by protocol before and after, because the effect depends on your users' networks.

This hop-by-hop independence is why most of the benefit can be captured at the edge alone: the long, lossy client-to-edge hop gets HTTP/3, while the short, clean edge-to-origin hop can use HTTP/2 or even HTTP/1.1 over pooled, warm connections without users noticing.

Long-lived connections change load balancing and deploys

With HTTP/1.1, clients open and close connections often, so even a naive L4 balancer spreads load over time. With HTTP/2 and gRPC, a client opens one connection and keeps it for hours. Three consequences follow. Load concentrates: a few heavy clients pin a few backends. Scaling out does not help immediately: new pods get no traffic until clients reconnect. And deploys are uneven: draining a pod means its clients reconnect in a burst elsewhere. The fixes are L7 proxies or service meshes that balance per request; client-side load balancing, where the gRPC client resolves all backend addresses and keeps connections to each; and servers that cap connection age or send GOAWAY periodically so clients re-spread. Kubernetes' default Service (an L4 mechanism) is the classic trap: gRPC traffic to a Deployment ends up on one pod.

Flow control as a hidden throughput cap

HTTP/2's per-stream and per-connection windows default to 65,535 bytes. A single stream can therefore have at most that much unacknowledged at the HTTP/2 layer, however large TCP's window is. At 100 ms RTT that caps a stream at about 5 Mbit/s, the same bandwidth-delay arithmetic as net4, one layer up. Browsers and good servers raise the windows immediately through SETTINGS and WINDOW_UPDATE, but proxies and internal clients with defaults can silently throttle large downloads, model-weight transfers or streaming responses. When a big transfer is slow over HTTP/2 but fine over HTTP/1.1, check the initial window settings first.

Stream-level attacks: Rapid Reset and friends

Multiplexing makes each connection far more powerful, and attackers noticed. In the Rapid Reset attack (CVE-2023-44487), which began in late August 2023 and was disclosed in October, clients opened streams with HEADERS and immediately cancelled them with RST_STREAM. Reset streams do not count against the concurrent-stream limit, so a single connection could generate an unbounded request rate while the server had already begun routing each request. Cloudflare saw peaks just above 201 million requests per second from a botnet of about 20,000 machines. Mitigations tracked the ratio of resets to completed requests per connection and closed abusive connections. In 2024 a related family of "CONTINUATION flood" bugs abused unbounded header continuation frames. The lesson for operators: protocol-level limits (streams per connection, resets per second, header sizes, connection lifetime) are as important as request-level rate limits, and edge software must be patched promptly.

Request smuggling and protocol downgrades

HTTP/1.1 has two ways to delimit a body, Content-Length and Transfer-Encoding: chunked, and historically servers disagreed on what to do when both, or malformed variants, appear. If a front-end proxy and a backend disagree about where a request ends, an attacker can append a hidden second request that the backend attaches to the next user's request on the same pooled connection, leading to cache poisoning or session hijacking. HTTP/2's frames carry explicit lengths, removing the ambiguity, but edges that accept HTTP/2 and forward HTTP/1.1 must translate carefully; flaws in that translation ("H2.CL" and "H2.TE" smuggling) reintroduce the bug. Using HTTP/2 end to end, rejecting ambiguous requests and keeping parsers strict are the durable fixes.

Connection coalescing and 421

HTTP/2 and HTTP/3 clients reuse a connection for another hostname if it resolves to the same IP and the connection's certificate covers that name (for example a wildcard or multi-name certificate). This saves handshakes but can surprise operators: requests for b.example.com arrive on a connection originally opened for a.example.com, perhaps at a server not configured for b. Servers answer such requests with 421 Misdirected Request, which tells the client to open a fresh connection. It shows up when certificates are shared more broadly than the routing configuration behind them.

What gRPC takes from HTTP/2

gRPC maps each call to an HTTP/2 stream: the method is the path (/package.Service/Method), messages are length-prefixed Protocol Buffers in DATA frames, and the call's final status travels in trailers, headers sent after the body, which HTTP/1.1 infrastructure rarely supports. Streaming calls are simply long-lived streams with many messages in each direction. This is why gRPC requires HTTP/2 end to end, why browsers need a translation layer (gRPC-Web), and why every HTTP/2 operational issue above, from load balancing to flow-control windows, applies directly to gRPC services.

Characteristic problems

  • gRPC hot-spotting: one pod at 90% CPU while others idle, after scaling out. Cause: long-lived HTTP/2 connections through an L4 balancer or Kubernetes Service. Fix: L7 proxy or mesh, client-side balancing, or maximum connection age on the server.
  • Slow large transfers through a proxy: fine over HTTP/1.1, capped over HTTP/2. Cause: small HTTP/2 flow-control windows. Fix: raise initial stream and connection windows.
  • Concurrency limits: requests queue on the client while the network is idle, because the server's SETTINGS_MAX_CONCURRENT_STREAMS (often 100) is reached on the single connection. Clients that need more concurrency must open more connections.
  • Pages slower after enabling HTTP/2 on lossy networks: the single connection amplifies loss. HTTP/3 at the edge is the remedy for mobile-heavy audiences.
  • Legacy hacks left in place: domain sharding, huge bundles and inlined assets from the HTTP/1.1 era now hurt; audit them when upgrading.
  • Protocol attacks: Rapid Reset and CONTINUATION floods exhausted servers that had no per-connection stream abuse limits; patched software and edge protections are essential.
  • Translation bugs: request smuggling at an HTTP/2-to-HTTP/1.1 boundary, header-size limits that differ between versions, and trailers dropped by intermediaries that break gRPC status reporting.

War story: Rapid Reset, August to October 2023

Starting on 25 August 2023, Cloudflare, Google and AWS saw floods of HTTP/2 requests far larger than any before: Cloudflare recorded a peak just above 201 million requests per second, nearly three times its previous record, from only about 20,000 machines. The attackers used a legitimate protocol feature, stream cancellation, at an illegitimate rate. At Cloudflare, about 1% of requests were affected initially, with peaks around 12% during the worst waves, before new connection-level defences closed abusive connections and brought impact to effectively zero. The vendors coordinated a disclosure on 10 October 2023, and every major HTTP/2 implementation shipped patches. It is a reminder that multiplexing moves work that used to be spread over many connections onto one, and so moves the need for limits there too.

A debugging order

For a performance or error problem that might be version-related: first find out which version each hop negotiated (browser DevTools, curl -w '%{http_version}', proxy logs). Then reproduce with the version forced (--http1.1, --http2, --http3) to see whether the problem follows the version. If it does, look at the version's specific limits: flow-control windows and concurrent streams for HTTP/2, UDP reachability and CPU for HTTP/3, connection counts for HTTP/1.1.

Observability

Record the negotiated protocol per request in edge and proxy logs (most CDNs and proxies expose it, and browsers show it in DevTools' Protocol column), so you can compare latency and error rates by version. Track connections, streams per connection, resets and GOAWAYs at proxies. For gRPC, track per-pod request rate to spot pinning. curl -w '%{http_version}' shows what a single request negotiated; nghttp -v and Wireshark (with TLS keys) show individual HTTP/2 frames.

Knobs

Maximum concurrent streams; initial stream and connection window sizes; maximum header list size; idle and maximum connection age; reset-rate limits per connection; enabling HTTP/3 and the Alt-Svc lifetime; and the upstream protocol each proxy uses towards origins (HTTP/2 where the origin supports it, especially for gRPC).

Diagnose it

After moving an internal gRPC service to Kubernetes with 6 replicas behind a standard ClusterIP Service, one pod runs at 95% CPU and the others at 5%. Scaling to 12 replicas changes nothing. Explain and fix.

Answer

A ClusterIP Service balances at layer 4: it picks a pod when a TCP connection is opened. gRPC clients open one long-lived HTTP/2 connection and multiplex every call over it, so all calls from a client go to the pod chosen at connect time. With few clients (or one big one), a single pod gets nearly everything, and new replicas receive no traffic because no new connections are opened.

Fixes: use a layer-7 proxy or service mesh (Envoy, Linkerd, Istio) that terminates HTTP/2 and balances each call; or use client-side load balancing, with a headless Service so DNS returns every pod IP and the gRPC client's round-robin policy keeps a connection to each; and set a maximum connection age on the server (gRPC's MAX_CONNECTION_AGE) so clients periodically reconnect and re-spread after scaling or deploys.

Estimate it

A service downloads a 2 GB file from an object store through an HTTP/2 proxy. RTT between them is 50 ms. The proxy uses HTTP/2's default initial stream window of 65,535 bytes and does not enlarge it. Roughly how long does the download take, and what is the fix?

Answer

At most one window can be in flight per round trip on the stream: 65,535 bytes / 0.05 s ≈ 1.3 MB/s, about 10 Mbit/s, no matter how fast the network or how large TCP's window. 2 GB / 1.3 MB/s ≈ 1,500 s, about 25 minutes. Over HTTP/1.1 the same path might run hundreds of times faster, limited only by TCP. The fix is to raise the HTTP/2 initial stream and connection window sizes on the proxy and client (to several megabytes, ideally near the bandwidth-delay product), or to split the download into parallel range requests on several streams.
