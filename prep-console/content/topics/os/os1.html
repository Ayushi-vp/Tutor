Imagine a computer with no operating system. Your program is loaded at address zero and owns the whole machine. It talks to the disk by writing magic numbers into the disk controller's registers, waits for the network card by checking a status bit in a loop, and decides by itself where in memory to keep its data. Now try to run two programs at once. Both believe they own address zero. Both write to the disk controller at the same moment and corrupt each other's requests. One has a bug that writes over the other's memory. And if one enters an infinite loop, nothing can ever take the CPU back: the only fix is the power switch.

That is roughly how early computers and simple embedded devices worked, and it is why every general-purpose computer now runs an operating system (OS). The OS sits between programs and hardware and solves three problems at once. It gives programs simpler things to work with than raw hardware: a file instead of disk sectors, a socket instead of a network card. It shares the hardware among many programs so each seems to have its own CPU and memory. And it protects programs from each other and the machine from all of them, so a bug in your browser cannot read your password manager's memory or wipe the disk.

The third job is the hardest, because protection cannot be a polite agreement between programs; a buggy or malicious program would simply ignore it. It needs help from the CPU itself. This lesson is about that help and how the OS uses it: the two CPU modes, the controlled doorways a program uses to ask the kernel for anything, the timer that lets the kernel take the CPU back, and the context switch that lets many programs share one CPU. Interviewers ask about these constantly, from campus rounds ("what is a system call?") to senior loops ("why is this service spending 40% of its time in the kernel?").

By the end you will be able to trace a write() call from your code into the kernel and back, explain what a context switch saves and why it is expensive, and read strace and vmstat output to see these mechanisms in a real program.

The OS as a building manager

Think of a large office building. Tenants (programs) rent offices and do their own work inside them, and most of the time the building does not interfere. But tenants cannot wire their own electricity, open the lift machinery or walk into another tenant's office. When they need something only the building controls, they go to the front desk and ask: "please deliver this parcel", "please give me another room". The front desk staff (the kernel) have master keys, check every request against the rules, do the work and report back. A guard also walks the floors on a fixed schedule (the timer) so that no tenant can lock everyone else out of a shared meeting room forever.

The analogy breaks in one useful place: the front-desk staff do not have their own separate bodies. When a program asks the kernel for something, it is the program's own thread of execution that switches into a privileged state and runs kernel code, then switches back. The kernel is less a separate worker and more a set of rooms that any tenant can be escorted into through one guarded door.

Two modes, enforced by the CPU

Every modern CPU has at least two privilege modes. In user mode, the mode applications run in, some instructions are forbidden (changing memory mappings, disabling interrupts, talking directly to devices) and memory marked as kernel-only cannot be touched. Trying either raises an exception, which hands control to the kernel, and the kernel usually kills the offending process. In kernel mode, everything is allowed. On x86 these are called ring 3 and ring 0; on ARM they are exception levels EL0 and EL1. The kernel is the part of the OS that runs in kernel mode; the rest of the "operating system" (the shell, system services, libraries) is ordinary user-mode programs.

Three doors into the kernel

If user code can never execute privileged instructions, how does anything get done? There are exactly three ways for the CPU to move from user mode into kernel mode, and each one makes the CPU jump to an address the kernel chose at boot time, never to an address the program picks:

  • System calls. The program deliberately asks for a service: open a file, read from a socket, start a process. It does this with a special trap instruction.
  • Exceptions. The instruction just executed needs the kernel's attention: it divided by zero, touched memory that is not mapped, or tried a privileged instruction. Some exceptions are fixed silently (a page that just needs loading from disk, os8); others end with the process being killed.
  • Interrupts. A device needs attention: the network card has received a packet, the disk has finished a read, or the timer has fired. Interrupts arrive at any moment, regardless of what the program is doing.

The timer interrupt is the quiet hero. Because the kernel programs the timer before handing the CPU to a program, the kernel is guaranteed to get control back within a few milliseconds, even if the program loops forever. At that point it can choose to run a different program, saving the first one's state so it can resume later. That swap is a context switch, and doing it fast and often is how one CPU runs hundreds of programs that each believe they have it to themselves.

Hold on to this picture: programs run directly on the CPU at full speed in user mode, and the kernel steps in only through these three doors. The textbook Operating Systems: Three Easy Pieces (OSTEP) calls this limited direct execution: direct because programs are not interpreted or slowed down, limited because the hardware stops them at the boundaries. The body of the lesson walks through each door in detail.

1. The three jobs, made concrete

It helps to see each job of the OS as a promise to programs.

Abstraction. A program calls open("notes.txt") and then read(). It never learns which disk sectors hold the file, whether the disk is an SSD or a network volume, or that part of the file was already in memory. Likewise a process (a running program, os2) sees its own private memory starting at the same addresses every time, and a thread (one sequence of execution inside a process) behaves as if it had the CPU to itself. These abstractions are what make programs portable: the same binary runs on very different hardware.

Resource management. There might be 8 CPU cores and 400 threads that want to run. The scheduler (os3) decides who runs where and for how long. Memory is limited, so the OS decides which pages stay in RAM and which go to disk (os8). Disks and network cards have queues of requests that the OS orders and batches. The goals compete: fairness, high throughput, low latency for interactive work.

Protection and isolation. A process cannot read another process's memory unless both agree to share it (os12). A program cannot reprogram the disk controller to read files it has no permission for. One process crashing does not take others down. All of this rests on two hardware features: the privilege modes from the primer, and the memory-management unit that translates every address a program uses through tables only the kernel can edit (os7).

2. Why "privileged instruction" is the key idea

Consider what a program would need to do to break isolation. To read another process's memory, it would have to change the address-translation tables. To monopolise the CPU, it would disable interrupts so the timer could never fire. To read a file it has no permission for, it would talk to the disk controller directly. The CPU designers made exactly these operations privileged instructions, executable only in kernel mode. So the security argument becomes short: user code cannot do anything dangerous directly, so it must ask the kernel, and the kernel checks every request. Everything else follows from that.

The mode itself is a bit of state inside the CPU (on x86 the "current privilege level" in the code segment register; on ARM64 the current exception level). Each page of memory also carries a "user or supervisor" bit in its page-table entry. So the CPU checks two things on every instruction: is this instruction allowed in the current mode, and is this memory address allowed in the current mode. Both checks happen in hardware on every access, which is why they cost essentially nothing.

3. The three doors and the table behind them

At boot, while it still runs with full privilege, the kernel fills in tables that tell the CPU where to jump for each kind of event. On x86 the main one is the interrupt descriptor table (IDT), with entries for each exception number (14 is a page fault, 0 is divide error) and each hardware interrupt vector. The fast syscall instruction uses a separate CPU register that holds the system-call entry address. ARM64 has a single vector table pointed to by a system register. Changing any of these requires kernel mode, so once they are set, user code can enter the kernel only at the entry points the kernel wrote.

On entry, the CPU switches to kernel mode, saves the minimum it needs (the user instruction pointer and flags), and jumps. The kernel's entry code then saves the rest of the user registers and switches from the user stack to a kernel stack, a small per-thread stack in kernel memory (16 KB on x86-64 Linux). The kernel never trusts the user stack, because user code controls it. When the kernel is done, it restores the registers and executes a return instruction that drops back to user mode at the saved address.

4. A system call, step by step

Let's trace the simplest useful system call, writing three bytes to standard output, on Linux on x86-64. In C it is write(1, "hi\n", 3); Python's os.write(1, b"hi\n") ends in the same place.

  1. The libc wrapper. write() is an ordinary function in libc, the C standard library. It places the system call number for write, which is 1 on x86-64, in register rax, and the arguments in rdi (fd = 1), rsi (address of the buffer) and rdx (length = 3). Up to six arguments travel in registers this way.
  2. The trap. It executes the syscall instruction. The CPU saves the user instruction pointer in rcx and the flags in r11, switches to ring 0 and jumps to the address the kernel stored at boot (Linux names this code entry_SYSCALL_64).
  3. Entry. The kernel switches to this thread's kernel stack and pushes all user registers into a structure called pt_regs, so it can restore them exactly later.
  4. Dispatch. It uses rax as an index into the system call table, an array of function pointers, and calls entry 1, the kernel's write handler. A number past the end of the table returns -ENOSYS.
  5. Validation and work. The handler looks up file descriptor 1 in the process's table of open files. If it is not open, it fails with -EBADF. It checks that the buffer address really lies in user memory (never trusting a pointer from user space, since a malicious program could pass a kernel address) and copies the bytes in with copy_from_user, which also copes safely with unmapped pages. Then it calls the write function of whatever is behind fd 1: a terminal driver, a pipe, a file system.
  6. Return. The result, 3 bytes written, goes into rax. The kernel restores the user registers and executes sysret, which switches back to ring 3 and continues at the instruction after syscall.
  7. Error convention. Back in libc, the wrapper checks rax. Linux returns errors as small negative numbers (−9 for EBADF). The wrapper turns that into the familiar C convention: store 9 in the per-thread variable errno and return −1. Python then raises OSError: [Errno 9] Bad file descriptor.

Two details deserve emphasis. First, the program cannot choose where in the kernel it lands, only which numbered service it wants. Second, the kernel treats every argument as hostile until checked. Many historic kernel vulnerabilities are exactly a missing check on a pointer or length passed in from user space.

What if the call has to wait, for example read() on a socket with no data yet? Then the kernel marks the thread as blocked, records what it is waiting for, and calls the scheduler to run something else. When the data arrives (signalled by a network interrupt), the thread is marked runnable again and eventually resumes inside the kernel, finishes the read and returns. This is where system calls and context switches meet: a blocking call is a system call that causes a context switch.

5. What system calls cost, and the vDSO shortcut

A bare system call that does almost nothing (such as getppid()) takes roughly 50 to 100 nanoseconds on a modern x86 CPU without security mitigations, and a few hundred with some of the post-2018 mitigations enabled. That sounds tiny, but a normal function call costs about a nanosecond, so a syscall is 50 to 300 times as expensive before any useful work. Programs that make millions of tiny syscalls feel it.

This is why I/O libraries buffer. Python's print() writes into a user-space buffer; when stdout is a file or pipe, the buffer is flushed with one write() per 8 KB or so, but when stdout is a terminal it is flushed at every newline so you see output promptly. The same loop of 100,000 prints can make 100,000 write calls to a terminal but only a few dozen to a file. The lab measures exactly this.

Some calls are made so often, and only read data, that Linux removes the kernel entry entirely. The kernel maps a tiny shared library, the vDSO (virtual dynamic shared object), into every process. Its clock_gettime() and gettimeofday() read a page of time data the kernel keeps updated plus the CPU's timestamp counter, all from user mode, in about 20 nanoseconds. libc calls the vDSO version automatically. The catch, which bites in production, is that it only works when the clock hardware can be read from user mode; on some virtual machines it cannot, and every clock read silently becomes a real syscall (see Production).

6. The timer interrupt and preemption

Suppose a program runs while True: pass. It never makes a system call and never faults. How does the OS ever run anything else? Before switching to any user thread, the kernel makes sure the CPU's local timer will fire an interrupt soon. Historically this was a fixed tick, set by the kernel configuration constant HZ (commonly 250 or 1000 times per second on Linux, so every 4 ms or 1 ms). Modern Linux kernels are "tickless" when idle and can schedule the next timer interrupt precisely for when the scheduler next needs to look.

When the timer fires, the CPU stops the loop mid-instruction-stream, enters kernel mode through the interrupt door, and runs the timer handler. The handler charges the elapsed time to the running thread and asks the scheduler whether this thread has used its fair share while others wait. If so, the kernel sets a "need to reschedule" flag and, on the way back out of the interrupt, performs a context switch instead of returning to the loop. Taking the CPU away like this is preemption. Systems that instead wait for programs to yield voluntarily (classic Mac OS, Windows 3.1, early cooperative schedulers) let one misbehaving program freeze the whole machine.

7. The context switch, in detail

A context is everything the CPU needs to resume a thread exactly where it left off: the general-purpose registers, the instruction pointer, the stack pointer, the flags, floating-point and vector registers, and (for a process) which page table is in use. Here is a switch from thread A of process P to thread B of process Q, triggered by a timer interrupt:

  1. A is running in user mode. The timer interrupt arrives; the CPU enters kernel mode on A's kernel stack, and the entry code saves A's user registers there.
  2. The scheduler decides B should run next.
  3. The switch routine (__switch_to in Linux, preceded by switch_mm) saves A's kernel-side registers and stack pointer into A's thread structure, loads B's kernel stack pointer and registers, and, because Q is a different process, loads Q's page table into the CPU (the CR3 register on x86). Floating-point and vector state is saved and restored as needed.
  4. The CPU is now running on B's kernel stack, at the point where B last entered the kernel. It unwinds back out to user mode using B's saved user registers, and B continues as if nothing happened.

What it costs. The direct cost (entering the kernel, the scheduler decision, saving and loading registers, switching page tables) is typically around 1 to 3 microseconds on current hardware. The indirect cost is often larger: B's data is not in the CPU caches, and the TLB, the CPU's cache of address translations (os7), may have been flushed or filled with A's entries. Modern CPUs tag TLB entries with an address-space identifier (PCID on x86, ASID on ARM) so a switch need not flush everything, but B still starts cold. A thread that is switched out every 100 microseconds can spend a large fraction of its time just warming up again.

Thread switch versus process switch. Switching between two threads of the same process skips the page-table change, so the TLB entries stay valid and it is somewhat cheaper. That is one reason threads are lighter than processes (os2).

Voluntary versus involuntary. Linux counts both for every task. A voluntary switch happens when the thread blocks (waiting for I/O, a lock, a sleep); an involuntary one happens when it is preempted while it still wanted to run. Lots of involuntary switches mean CPU contention: more runnable threads than cores. Lots of voluntary ones mean the thread waits a lot. You can read both counters in /proc/<pid>/status.

8. How kernels are organised

Where should a device driver or a file system live? Two schools of thought:

A monolithic kernel puts the scheduler, memory manager, file systems, network stack and all device drivers into kernel mode, in one shared address space. Subsystems call each other with ordinary function calls, which is fast. The price is that all of that code is trusted: a bug in an obscure USB driver can corrupt the memory of the network stack or crash the whole machine. Linux is monolithic, though loadable kernel modules let drivers be added and removed at runtime (lsmod lists them), which gives flexibility without changing the trust model.

A microkernel keeps only the essentials in kernel mode: address spaces, threads, scheduling and a fast message-passing mechanism. Drivers and file systems run as ordinary user-mode server processes. A crashed driver can be restarted without a reboot, and the trusted kernel is small; seL4 is small enough to have a machine-checked proof that it is correct. The price is that reading a file now involves messages between several processes, each crossing the user/kernel boundary. QNX (used in cars and industrial systems), MINIX 3 and seL4 are microkernels.

Real systems blur the line. Windows NT and Apple's XNU are usually called hybrid kernels: microkernel-inspired structure, but most services run in kernel mode for speed. Linux, meanwhile, moves some work out: file systems in user space through FUSE, user-space drivers through VFIO, and safe, verified mini-programs loaded into the kernel through eBPF (os14).

9. Putting it together: one second in the life of a CPU

On a busy Linux server, one core in one second might handle a few thousand timer and device interrupts, tens of thousands of system calls, a few thousand context switches and a few hundred page faults, while spending most of its time running user code directly. vmstat 1 shows this live: the in column is interrupts per second, cs is context switches per second, and us/sy split CPU time between user and kernel mode. When sy is large, the program is spending its time in the doors rather than in its own code, and the next step is to find out which door and why.

Meltdown, KPTI and why kernel entry got more expensive

Until 2018, Linux mapped the whole kernel into every process's page table, marked supervisor-only. That made kernel entry cheap: no page-table switch was needed. The Meltdown vulnerability showed that on many Intel CPUs, user code could speculatively read those supervisor-only pages before the permission check took effect, and recover the values through cache timing. The fix, kernel page-table isolation (KPTI), gives each process two page tables: a user one that contains only a tiny trampoline of kernel code, and a full one used inside the kernel. Every syscall, interrupt and exception now switches page tables twice. With the PCID feature the TLB does not have to be flushed each time, but the overhead is still real, and it scales with the rate of kernel entries: workloads doing hundreds of thousands of syscalls per second per CPU slowed by a few percent to well over ten percent, while compute-bound code barely noticed. Newer CPUs that are not vulnerable skip KPTI, which is why the same benchmark can differ across hardware generations.

Why kernel developers are obsessed with avoiding syscalls

Since each crossing has a fixed cost, many modern interfaces exist purely to cross less often. The vDSO removes the crossing for clock reads. readv/writev and sendmmsg batch several buffers or messages into one call. epoll returns many ready sockets per call (os11). io_uring, added in Linux 5.1, goes further: the program places requests in a ring buffer shared with the kernel and reads completions from another ring, so with polling enabled a busy server can do I/O with almost no syscalls at all. At the extreme, kernel-bypass frameworks such as DPDK map the network card directly into a user process and poll it, giving up the kernel's protection and sharing in exchange for millions of packets per second per core.

Interrupts are split into top and bottom halves

An interrupt handler runs while the CPU has stopped whatever it was doing, often with further interrupts on that CPU masked, so it must be short. Linux splits device handling into a fast "top half" that acknowledges the device and queues work, and deferred "bottom halves" (softirqs, tasklets and workqueues) that do the rest with interrupts enabled. Network receive processing, for example, mostly runs as a softirq. When softirq work piles up it is handed to per-CPU kernel threads named ksoftirqd/N, which is why a busy network server can show ksoftirqd using a full core in top, and why the si column in top exists.

Kernel preemption and real-time Linux

The timer can preempt user code at any instruction, but kernel code is a different matter: if the kernel is in the middle of updating a shared structure, switching away could leave it inconsistent. Early Linux kernels were not preemptible at all while in kernel mode, so a long system call could delay a high-priority task by milliseconds. Modern kernels can be configured to preempt kernel code except inside critical sections (spinlocks, os4). The PREEMPT_RT patch set, merged into mainline in Linux 6.12 after about twenty years of out-of-tree development, goes further by turning most spinlocks into sleeping locks and running interrupt handlers in threads, so worst-case latency becomes predictable for audio, robotics and industrial control, at some cost in throughput.

Virtualisation adds a third level

Under a hypervisor, the guest kernel believes it runs in kernel mode, but the hardware has a still more privileged mode for the hypervisor (Intel VMX root mode, ARM EL2). Certain guest operations, such as touching some devices or control registers, cause a VM exit into the hypervisor, the virtual-machine equivalent of a trap, which costs on the order of a microsecond or more. Much of the history of virtualisation performance, from paravirtual drivers to hardware nested page tables, is about reducing the number of VM exits, in the same way that syscall design is about reducing kernel entries.

Signals turn the boundary inside out

System calls let user code call the kernel; signals (os12) are the kernel calling user code. When a signal is pending for a thread, the kernel, just before returning to user mode, rewrites the saved user context so that the thread "returns" into its signal handler instead, with a special frame on the user stack that makes the handler return into the rt_sigreturn system call, which restores the original context. This is also why a system call interrupted by a signal can fail with EINTR: the kernel had to unwind it to deliver the signal, and the program must retry or the library must restart it.

Reading the user/system split

The first number to look at on a struggling host is how CPU time divides between user mode and kernel mode: us and sy in vmstat 1 or top, and %usr and %sys per process in pidstat -u 1. A healthy application server is usually dominated by user time. A system time share above roughly 20-30% is worth explaining. The usual causes are excessive small syscalls (unbuffered logging, reading a socket a byte at a time, polling loops), heavy lock contention (the futex syscall), memory churn (frequent mmap/munmap or page faults, os8-os9), and network packet processing (shows as si, softirq time).

Finding which syscalls

strace -c -f -p <pid> attaches to a process and prints a table of syscall counts, errors and time. It is invaluable but dangerous in production: it uses ptrace, which stops the traced thread at every syscall entry and exit, and can slow a syscall-heavy process by 10x or more. Prefer low-overhead tools: perf trace -s -p <pid>, or eBPF tools such as syscount from the bcc collection, which count in the kernel without stopping the process (os14). A syscall that returns errors at a high rate is a classic finding: a program calling open() on a list of paths that mostly do not exist (ENOENT) or retrying non-blocking reads that return EAGAIN in a busy loop.

Context-switch storms

vmstat's cs column and pidstat -w (which splits cswch/s, voluntary, from nvcswch/s, involuntary) reveal switching problems. A service with thousands of threads all waking for each request, or a thread pool far larger than the core count, can produce hundreds of thousands of switches per second, burning CPU in the scheduler and destroying cache locality. High involuntary switching with a long run queue (r column above the number of cores) means CPU saturation; high voluntary switching usually means threads handing work to each other through queues and locks. Fixes include right-sizing pools, batching handoffs, and pinning latency-critical threads to dedicated cores.

Real incident: the clock that became a syscall

Several public reports (including Brendan Gregg's account of a Netflix Cassandra investigation and the Packagecloud and Heap engineering blogs) describe the same surprise on Xen-based EC2 instances: the default xen clock source could not be read through the vDSO, so every clock_gettime() and gettimeofday(), which databases and JVMs call constantly for timestamps and metrics, became a full system call and, underneath, a hypervisor interaction. Flame graphs showed significant CPU in kernel time functions. Switching the clock source to tsc (via /sys/devices/system/clocksource/clocksource0/current_clocksource, where the hardware supports it reliably) restored the vDSO fast path and cut CPU usage noticeably. The lesson generalises: a "free" operation can become expensive when an environment change moves it across the kernel boundary.

Mitigations and kernel versions

Because CPU-vulnerability mitigations change the cost of every kernel entry, a kernel upgrade, a microcode update or a move to new instance types can shift syscall-heavy services by several percent. /sys/devices/system/cpu/vulnerabilities/ shows which mitigations are active. Benchmark before and after such changes rather than assuming hardware is the only variable, and never disable mitigations on shared or multi-tenant machines to win back performance.

Containers do not change any of this

A container is ordinary processes on the host kernel (os13), so every syscall from inside a container is a normal syscall into the shared kernel. There is no extra layer to cross, which is why containers are so much lighter than virtual machines, and also why a kernel bug reachable by a syscall is reachable from every container on the host. Sandboxes such as gVisor intercept syscalls in a user-space kernel precisely to shrink that shared surface, and pay for it in syscall overhead.

The voluntary_ctxt_switches count is small for this CPU-bound script; try adding time.sleep(0.001) inside a loop of 1,000 and watch it climb by about 1,000, one voluntary switch per sleep.

Diagnose: a logging change doubles CPU

A team switches their Python service's logging from a buffered file handler to writing each log line directly with os.write() on an unbuffered file descriptor "so that logs are never lost on a crash". The service logs about 40,000 lines per second per process. After the change, CPU usage per process rises from 35% to 60%, and top shows the extra time as sy, not us. Explain what happened in terms of this lesson, estimate whether the numbers are plausible, and propose a fix that keeps most of the durability benefit.

Answer

Mechanism. Before the change, log lines were collected in a user-space buffer and written with one write() system call per several kilobytes, perhaps a few hundred syscalls per second. After the change every line is its own write(): 40,000 kernel entries per second per process. Each crossing pays the fixed entry and exit cost, and each write also takes the file's lock, updates the inode's timestamps and size, and copies into the page cache (os10). That work is kernel time, so it appears as sy.

Plausibility. 25% of a core is 250 ms per second. Divided by 40,000 writes, that is about 6 µs per write. A bare syscall is well under a microsecond, but a file write through the file system, with locking, accounting and page-cache work and mitigation overheads, plausibly costs a few microseconds. So the numbers fit.

Confirming. perf trace -s -p <pid> or strace -c on a short sample would show write dominating syscall counts at roughly the log rate.

Fix. Note first that the change did not even achieve its goal fully: write() only puts data in the kernel's page cache, which survives a process crash but not a power loss (that needs fsync, os10). Since the process-crash case is what they care about, a middle ground works: buffer in memory and flush on a short interval (say every 100 ms) or every N lines, flush on clean shutdown and in the crash handler, and accept losing at most 100 ms of logs on a hard kill. Alternatively, log to stdout and let the container runtime or a local agent handle batching. Either way the syscall rate drops by two or three orders of magnitude.
