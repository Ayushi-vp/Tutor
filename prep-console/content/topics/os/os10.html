A disk, whether a spinning platter or an SSD, offers one primitive: read or write block number N, where a block is a few kilobytes. It has no idea what a file is, what a directory is, who owns what, or which blocks belong together. Yet you expect ~/projects/report.md to exist by name, to grow when you append to it, to be readable only by you, to survive a reboot, and above all to still be intact if the power fails while you are saving it. The file system provides all of that on top of numbered blocks.

Doing it is harder than it looks. Saving a file changes several separate structures on disk: the data itself, the record of which blocks are in use, the file's size and block list, and maybe a directory entry. The disk writes them one at a time, and a crash can happen between any two, leaving a file pointing at garbage or blocks lost forever. Disks are also slow compared with memory, so the kernel keeps file data in RAM and writes it back later, which makes everything fast and introduces the question every database engineer has to answer precisely: when exactly is my data safe?

These questions show up in real incidents constantly. A disk shows full but you cannot find the files. A service stalls for seconds whenever another process writes a big file. A configuration file is empty after a power cut. A database loses data after a disk error that it thought it had handled. Each one makes sense once you know about inodes, link counts, the page cache, write-back and fsync.

Interviewers ask "what is an inode?", "hard link versus soft link?", "what is journaling?" in OS rounds, and "how would you make this write durable?" or "why is the disk full?" in senior and SRE rounds. This lesson goes from file descriptors to inodes and directories, through crash consistency and journaling, ext4 and XFS, the VFS layer and the page cache, to fsync and the patterns that make data actually safe.

A library: catalogue cards and shelf locations

Picture an old library. The books' pages are spread across shelves wherever there was space (the disk's blocks). For each book there is one catalogue card recording its size, owner, borrowing rules, when it was last changed, and which shelf positions hold its pages, in order. That card is the inode. The card does not carry the book's title. Titles live in separate index drawers, the directories, where each entry says "title → card number". A book can be listed under two titles in different drawers (a hard link); a drawer entry can also say "see the entry for this other title" (a symbolic link). And the library keeps a list of free shelf positions and free cards.

To read a book by its full name, say /home/ana/notes.txt, a librarian starts at the root drawer, finds "home", follows it to the drawer for home, finds "ana", then "notes.txt", and finally gets a card number, which leads to the shelves. That walk is path resolution.

The analogy breaks in two important ways. First, the "librarian" keeps photocopies of recently used cards and pages on a desk in RAM (the page cache) and writes changes back to the shelves later, which is fast but means the shelves may lag behind. Second, the library can be hit by a power cut in the middle of shelving a book, after updating the free list but before updating the card. Keeping cards, drawers and free lists consistent despite that is the job of journaling.

The life of one write, in brief

Follow a single write() of 4 KiB to the end of notes.txt. The kernel finds the open file's inode through the file descriptor, copies your bytes into a page of the page cache (allocating one if needed), marks it dirty, updates the size in the in-memory inode, and returns. Your program carries on, perhaps a few microseconds later. Nothing has touched the disk. Some seconds later a kernel flusher thread notices the dirty page, the file system chooses where on disk the new block goes, writes the data, and records the new size and block location through its journal. Only then is the change on stable storage. Everything interesting about file systems in production lives in the gap between "write returned" and "it is on disk", and in what happens if the power fails inside that gap.

What a file system promises

It helps to name the promises explicitly, because applications often assume more than they get. Naming: a file can be found again by its path. Isolation and permissions: other users cannot read or change it unless allowed. Consistency after a crash: the file system's own structures (directories, inodes, free-space maps) will be valid after an unclean shutdown. Durability: data reaches stable storage, but by default only eventually; to know that a specific write is durable, the application must ask with fsync. Most data-loss bugs come from treating the third promise as if it were the fourth.

1. From a file descriptor to the file: three tables

When a process calls open("notes.txt", O_RDWR), three kernel structures are involved:

  1. The process's file-descriptor table: a small array per process. The returned integer (say 3) is an index into it. 0, 1 and 2 are stdin, stdout and stderr by convention.
  2. An open file description (Linux's struct file): created by each open(), holding the current offset, the access mode and flags such as O_APPEND or O_NONBLOCK.
  3. The file's in-memory inode: one per file, shared by everyone who has it open, holding metadata and the map of where the data is.

This structure explains several everyday behaviours. Shell redirection works because the child's fd 1 is pointed at a new description before exec (os2). O_APPEND lives in the description, so every write through it atomically seeks to the end first, which is how many processes can safely append to one log. And closing a descriptor only drops one reference; the description and inode live on while anyone else uses them.

2. Inside an inode: where the data is

An inode holds the file's type (regular file, directory, symlink, device, socket, pipe), permissions, owner and group, size, link count, three timestamps (atime last access, mtime last content change, ctime last inode change) and the map from file offsets to disk blocks. stat notes.txt prints all of it.

The classic Unix map (ext2 and ext3) is a multi-level index. The inode has 15 block pointers: 12 direct pointers to data blocks, then one single indirect pointer to a block full of pointers, one double indirect (a block of pointers to pointer blocks) and one triple indirect. With 4 KiB blocks and 4-byte block numbers, a pointer block holds 1,024 pointers:

direct:           12 blocks              =      48 KiB
single indirect:  1,024 blocks           =       4 MiB
double indirect:  1,024² blocks          =       4 GiB
triple indirect:  1,024³ blocks          =       4 TiB
maximum file size ≈ 4 TiB (ext3 limits it further to 2 TiB)

Small files, the vast majority, need only direct pointers and no extra reads; big files pay one to three extra block reads to find their data, usually cached. The weakness is that a 1 GiB file needs 262,144 pointers, even if its blocks are contiguous. Modern file systems (ext4, XFS, Btrfs, NTFS) use extents instead: "starting at block 9000, 3 blocks", "starting at block 15220, 2 blocks". A single ext4 extent covers up to 32,768 blocks (128 MiB), and an inode holds four extents directly, with an extent tree for files with more. A large contiguous file needs a handful of extents instead of thousands of pointers.

3. Directories, path resolution and links

A directory is a file whose contents are entries mapping names to inode numbers, plus . (itself) and .. (its parent). Small directories can be a simple list; large ones need an index, and ext4 uses a hashed B-tree (htree) so that a lookup in a directory of a million files is a few block reads rather than a scan.

Path resolution walks the path one component at a time. For /home/ana/notes.txt: start at the root inode (number 2 on ext4), read its directory data and find home → inode 130; check that the process has execute (search) permission on /; read inode 130's directory and find ana → 812; read 812 and find notes.txt → 4410. Each step could cost disk reads, so the kernel caches recent lookups in the dentry cache, making repeated path lookups pure memory operations. Mount points and symbolic links are handled during the walk.

A hard link (ln notes.txt copy.txt) adds another directory entry with the same inode number and increments the inode's link count. Both names are equally "the" file. A symbolic link (ln -s notes.txt alias.txt) is a separate tiny file of type symlink whose content is the path notes.txt; opening it makes the kernel resolve that path instead. Symlinks can cross file systems and point at directories; they can also dangle.

Deleting is unlinking. rm calls unlink(), which removes one directory entry and decrements the link count. The inode and its blocks are freed only when the link count is zero and no process holds the file open. Until then, the file exists without a name. That is a deliberate feature (programs can create a temporary file and unlink it immediately so it vanishes automatically when they exit) and a classic production trap (see Production).

4. Allocation and layout

The file system must track free inodes and free blocks, typically with bitmaps (one bit per block or inode). ext4 divides the disk into block groups (128 MiB each with 4 KiB blocks), each with its own bitmaps, inode table and data blocks, and tries to place a file's inode and data in the same group and files of one directory near each other, so related reads are close together. That was crucial on spinning disks, where a seek cost milliseconds, and still helps SSDs by keeping I/O large and sequential.

Modern file systems also use delayed allocation: when an application writes, the data goes to the page cache without choosing disk blocks; blocks are allocated only when write-back happens, by which time the file system knows how big the file is and can choose one large contiguous extent. That reduces fragmentation, and it is also why a crash shortly after writing can leave a newly created file empty (deep section).

5. Crash consistency: why one write is several writes

Appending one 4 KiB block to a file requires three on-disk updates: mark the block used in the bitmap, update the inode (new size and the pointer or extent), and write the data block. The disk performs them one at a time, in an order the kernel and the disk's own scheduler choose. If power fails after some but not all:

Written before the crashResult
Data onlyData is lost, but the file system is consistent (as if the write never happened)
Inode onlyInode points to a block that holds old garbage, and the bitmap says it is free: it may be given to another file
Bitmap onlyBlock marked used but referenced by nothing: a space leak
Inode + bitmapMetadata consistent, but the file contains garbage where the new data should be
Inode + dataFile looks right, but the bitmap says the block is free: a future file may overwrite it
Bitmap + dataBlock used and filled but no inode refers to it: a leak

The traditional fix is fsck: after an unclean shutdown, scan every inode, directory and bitmap and make them agree. It works, but takes time proportional to the size of the file system, minutes to hours for multi-terabyte disks, during which the machine cannot mount the volume.

6. Journaling: write the plan first

Journaling borrows the database's write-ahead log (sc4). A reserved area of the disk, the journal, records each update before it is applied in place:

  1. Journal write: write a transaction-begin record and the new versions of every block the update will change (bitmap, inode, maybe directory) into the journal.
  2. Journal commit: once those are safely on disk, write a small commit record. The update is now durable: whatever happens next, it can be completed.
  3. Checkpoint: write the blocks to their real locations. This can happen lazily, batching many transactions.
  4. Free: mark the transaction's journal space as reusable.

Recovery after a crash reads the journal: committed transactions are replayed (writing the logged blocks to their homes again is harmless if it was already done, because the blocks are whole new versions), and transactions without a commit record are discarded. Either way, the file system ends up in a state that existed before or after each update, never in between.

What about the data? Journaling data too would write every byte twice. ext4 offers three modes:

ext4 modeJournaledOrderingAfter a crash
data=journalData and metadataEverything through the journalStrongest; all writes doubled
data=ordered (default)Metadata onlyA file's data blocks are written before the metadata transaction that refers to them commitsFiles never point at garbage, but unsynced data can be missing
data=writebackMetadata onlyNoneRecently extended files may contain stale data from previously freed blocks

Ordered mode removes the "inode points to garbage" cases from the crash table at almost no cost: write the data block first, then journal the metadata. XFS gives similar guarantees through its own metadata journal plus careful ordering, including not exposing unwritten extents.

7. ext4 and XFS in brief

ext4 (2008) extends ext3 with extents, delayed allocation, a checksummed journal, htree directories and nanosecond timestamps. Its inode tables are created when the file system is made, by default one inode per 16 KiB of space, which can run out on volumes of tiny files. It is the default on Debian and Ubuntu and a safe general choice. XFS (from SGI, 1990s) splits the volume into allocation groups that operate largely independently, so many threads can allocate in parallel; uses B+trees for free space, extents and directories; allocates inodes dynamically; and handles very large files and file systems well. It is the default on Red Hat Enterprise Linux. It cannot be shrunk. Btrfs and ZFS are copy-on-write file systems with checksums, snapshots and built-in volume management (deep section).

8. The VFS: one interface, many file systems

Linux supports dozens of file systems: ext4, XFS, Btrfs, NFS (remote), tmpfs (in RAM), procfs and sysfs (kernel data shown as files), FUSE (user-space implementations), overlayfs (container image layers, os13). Programs use the same open, read, write, stat on all of them because of the virtual file system layer. The VFS defines four common objects: the superblock (one mounted file system), the inode (one file), the dentry (one name in a directory, cached) and the file (one open file description). Each file system supplies tables of functions (inode_operations, file_operations and so on) that the VFS calls. When you read() from /proc/meminfo, the VFS calls procfs's read function, which generates the text on the spot; nothing is on a disk.

9. The page cache, write-back and fsync

Ordinary file I/O goes through the page cache (os8). A read() copies from cached pages, reading from disk only on a miss (with readahead for sequential access). A write() copies into cache pages, marks them dirty and returns immediately, typically in microseconds. Memory-mapped files use the same pages directly.

Dirty pages reach the disk through write-back, done by kernel flusher threads when:

  • a page has been dirty longer than vm.dirty_expire_centisecs (3,000, so 30 seconds, by default; flushers wake every 5 seconds to check);
  • dirty memory exceeds vm.dirty_background_ratio (10% of available memory by default) or dirty_background_bytes, which starts background write-back;
  • memory is needed (reclaim must clean dirty pages before reusing them);
  • or an application asks with fsync, fdatasync or sync.

If dirty memory reaches vm.dirty_ratio (20% by default), processes that write are throttled: their write() calls sleep until write-back catches up, so a fast writer cannot fill all of RAM with unwritten data.

What fsync guarantees. fsync(fd) blocks until the file's dirty data and its metadata (size, block map) have been written to the device and the device has been told to flush its volatile write cache. fdatasync skips metadata not needed to read the data back (such as mtime), saving a journal write. Neither makes the file's name durable: a newly created file also needs an fsync on its directory. Opening with O_SYNC or O_DSYNC makes every write behave like write plus fsync or fdatasync. O_DIRECT bypasses the page cache entirely (the application manages its own cache, as many databases do) but still needs fsync for durability of metadata and the device cache.

The atomic replace pattern. To update config.json so that readers and crashes only ever see the old or the new version:

fd = open("config.json.tmp", O_WRONLY|O_CREAT|O_TRUNC)
write(fd, new_contents)
fsync(fd)                          # new data is durable
close(fd)
rename("config.json.tmp", "config.json")   # atomic switch of the name
dfd = open(".", O_RDONLY|O_DIRECTORY)
fsync(dfd)                         # the rename itself is durable

Each step has a reason. Writing elsewhere means readers never see a partial file. The first fsync ensures the name will never point to a file whose data did not make it. rename() within a file system is atomic: at every moment the name refers to the old inode or the new one. The directory fsync makes the switch survive a crash.

Delayed allocation and the zero-length file problem

In 2009, users of the newly released ext4 found that after a crash, configuration files of desktop applications were often empty. The applications updated files by truncating and rewriting them, or by writing a temporary file and renaming it without fsync. Under ext3's ordered mode, data happened to be flushed within about five seconds, before the metadata commit, so this mostly worked. ext4's delayed allocation postponed choosing blocks, and therefore writing data, for up to 30-60 seconds, while the rename was journaled within seconds, so a crash left the new name pointing at an inode with no data. The applications were relying on behaviour POSIX never promised; ext4 added heuristics (flushing data on rename-over and truncate-then-write patterns, controlled by auto_da_alloc) to protect them anyway. The episode is the classic illustration that crash consistency is a contract between application and file system, and that the only portable contract is explicit fsync.

Write-back errors and fsyncgate

When write-back of a dirty page fails (a disk error, a thin-provisioned volume out of space, a network file server down), there is no write() call in progress to report it to. Linux records the error on the file's address space and reports it to a later fsync. In 2018, PostgreSQL developers discovered that older kernels reported such an error only to the first caller to check and then cleared it, and, worse, marked the failed pages clean, so the data was gone from the cache too. PostgreSQL's checkpointer retried fsync, got success, and believed its data was durable. Linux 4.13 introduced per-description error sequence counters (errseq_t) so every file description open at the time sees the error; PostgreSQL's February 2019 releases changed fsync failure to a panic followed by recovery from the WAL. The broader lesson: after a failed fsync, the state of the data since the last successful fsync is unknown, and retrying proves nothing.

Disk caches, barriers and FUA

Drives have their own volatile write caches. A drive may report a write complete when it is only in that cache, and may reorder cached writes. Journaling depends on order (journal blocks, then commit record, then checkpoint), so file systems issue cache flush commands at the critical points and use FUA (force unit access) writes for the commit record so it is written through to stable media. fsync ends with a flush. Drives with power-loss protection (common in enterprise SSDs) can complete flushes quickly because their cache is safe; consumer drives without it pay the full cost, and some cheap or misconfigured drives historically lied about flushes, which no file system can defend against. Virtualised and networked block devices add more layers that must honour flushes.

Copy-on-write and log-structured file systems

Btrfs and ZFS never overwrite live blocks. A change writes new copies of the modified data and of every metadata block on the path up to the root of the tree, then atomically switches the root pointer. Before the switch, the old tree is complete; after it, the new one is, so no journal is needed for consistency. The same structure gives instant snapshots (keep an old root and its blocks), end-to-end checksums that detect silent corruption, and send/receive replication. The costs: small random overwrites (database pages, VM images) fragment files and amplify writes, which is why databases on Btrfs often disable copy-on-write for their files (chattr +C) and ZFS users tune record sizes. Log-structured file systems (LFS, and F2FS designed for flash) take the idea further by writing everything sequentially into a log and cleaning old segments in the background, a design that suits SSDs' preference for large sequential writes.

SSDs underneath

Flash memory cannot overwrite in place: it erases in large blocks (hundreds of kilobytes to megabytes) and writes in pages. SSDs hide this with a flash translation layer that remaps logical blocks, writing updates to fresh locations and garbage-collecting old ones, which is itself a log-structured design. That layer works better when it knows which blocks are free: TRIM (discard) commands from the file system tell the drive that deleted blocks need not be preserved, improving write performance and wear. Linux offers continuous discard (mount -o discard) or periodic fstrim (a weekly systemd timer on most distributions), the latter usually preferred for performance.

"Disk full" mysteries

When df says full and du disagrees, check in order: deleted-but-open files (lsof +L1, or find /proc/*/fd -lname '*(deleted)'; the classic case is a log deleted by a cleanup script while the service keeps writing, fixed by signalling it to reopen logs or using copytruncate in logrotate); files hidden under a mount point (unmount, or bind-mount the parent elsewhere to look underneath); the reserved blocks (ext4 keeps 5% for root by default; tune2fs -m changes it on data volumes); and on Btrfs or ZFS, snapshots holding old blocks. A different "full": No space left on device with free space means inode exhaustion (df -i), usually from millions of tiny files such as session files, mail spools, cache entries or container layers on ext4.

Write stalls and dirty-page tuning

A service that writes logs or files steadily can see sudden latency spikes when another process writes a large file: dirty memory crosses dirty_ratio and every writer on the machine is throttled, or a big burst of write-back saturates the disk and reads queue behind it. With RAM measured in hundreds of gigabytes, the default ratios (10% and 20%) allow tens of gigabytes of dirty data, which takes a long time to flush. Common tuning sets absolute limits instead (vm.dirty_background_bytes of a few hundred MB, vm.dirty_bytes of a few GB) so write-back starts earlier and stays smoother. Watch Dirty and Writeback in /proc/meminfo, per-device latency with iostat -x (os14), and I/O pressure in /proc/pressure/io. Put bulk writers in cgroups with I/O limits (io.max) so they cannot starve latency-sensitive neighbours.

fsync cost and how databases manage it

An fsync on a consumer NVMe drive without power-loss protection can take a millisecond or more; on cloud network block storage, a few milliseconds; on spinning disks, tens. Anything that fsyncs per operation (a naive key-value store, SQLite in its default journal mode, a message queue configured for per-message durability) is bounded by that latency. Databases amortise it with group commit: many transactions' log records are written and fsynced together, so one flush makes a whole batch durable. When choosing storage for a database, measure fsync latency directly (for example with fio --fsync=1 or pg_test_fsync) rather than trusting throughput numbers, and check whether the device has power-loss protection.

When storage fails

I/O errors appear in the kernel log (dmesg: "Buffer I/O error", "blk_update_request: I/O error"). When ext4 detects metadata corruption it reacts according to its errors= mount option, commonly remounting the file system read-only to prevent further damage, which applications experience as sudden EROFS errors. XFS shuts the file system down on serious metadata errors. Treat these as hardware or storage-layer incidents: fail over, replace the volume, then run fsck or xfs_repair on an unmounted copy if needed. Applications should treat EIO from fsync as data loss, as fsyncgate showed.

Small but useful knobs

Updating atime on every read turns reads into writes; Linux defaults to relatime (update atime only if older than mtime or a day old), and noatime removes it entirely for data volumes. Choose XFS or ext4 with an inode ratio suited to the file-size distribution (mkfs.ext4 -i) for volumes of many small files. For databases using O_DIRECT, align I/O to the device's block size. And when running many containers, remember that overlayfs layers live on the host file system, so image churn can exhaust inodes and space on /var/lib/docker or /var/lib/containerd long before the application's own volumes.

Explore inodes, links and deleted-but-open files, then measure what fsync costs. Linux or WSL (macOS works for most steps).

  1. Inodes and links: 
    mkdir fslab && cd fslab
echo "hello" > a.txt
ln a.txt hard.txt          # hard link
ln -s a.txt soft.txt       # symbolic link
ls -li                     # first column: inode numbers; third: link counts
stat a.txt
rm a.txt; cat hard.txt; cat soft.txt
  2. Deleted but open: 
    python3 -c "import time; f=open('big.log','w'); f.write('x'*50_000_000); f.flush(); time.sleep(120)" &
sleep 1; df -h . ; rm big.log ; df -h .
ls -l /proc/$!/fd | grep deleted
kill $!; sleep 1; df -h .
  3. The cost of durability, in Python: 
    import os, time
fd = os.open("t.bin", os.O_WRONLY | os.O_CREAT | os.O_TRUNC)
for sync in (False, True):
    t = time.perf_counter()
    for i in range(500):
        os.write(fd, b"x" * 4096)
        if sync: os.fsync(fd)
    print("fsync" if sync else "no fsync", (time.perf_counter() - t) / 500 * 1e6, "µs per write")

What to look for. In step 1, a.txt and hard.txt share an inode number and show a link count of 2; soft.txt has its own inode and is shown as soft.txt -> a.txt. After removing a.txt, hard.txt still prints "hello" (the inode survives with one link) while cat soft.txt fails: the path it contains no longer exists. In step 2, df does not drop after rm, and /proc/PID/fd shows the file as "(deleted)"; space is released only when the process exits. In step 3, writes without fsync take a few microseconds (a copy into the page cache), while each fsync'd write takes from tens of microseconds to several milliseconds depending on the device, often 100 times slower or more. On WSL the numbers reflect the virtual disk, so they may differ from native Linux.

Design and diagnose: a message log that must not lose acknowledged messages

You are writing a single-node message queue. Producers send messages; the server appends each to a log file and replies "ack"; consumers read from the log. Requirement: once a producer receives an ack, the message must survive a power failure. Load is 20,000 messages per second of about 1 KB each, and the server's NVMe drive (no power-loss protection) takes about 1 ms per fsync. A first version acknowledges after write() returns. (a) Explain why it violates the requirement. (b) Why can't you simply fsync after every message? (c) Design the durable write path. (d) The log is rotated by renaming the current file and creating a new one; what else must be fsynced?

Answer

(a) write() only copies the message into the page cache and returns. The kernel writes it to disk up to about 30 seconds later. A power failure in that window loses messages that were already acknowledged. Even a clean crash of the kernel loses them. The ack must wait for stable storage.

(b) With 1 ms per fsync and one fsync per message, a single writer thread can make at most about 1,000 messages durable per second, 20 times short of the load. Parallel fsyncs on the same file do not help much, because they all wait for the same device flush.

(c) Group commit. Have producer requests append to the file (or to an in-memory buffer written in large chunks) without waiting, and run one flusher loop: take everything written so far, call fdatasync (size changes need the metadata, which fdatasync includes; mtime does not), then acknowledge every message covered by that sync. At 20,000 messages per second with roughly 1 ms flushes, each fsync covers about 20 messages (about 20 KB), so throughput is met and each message waits on average about one flush interval, around 1-2 ms, before its ack. Preallocating the log file (fallocate) reduces metadata changes on each sync. If latency must be lower, the options are storage with power-loss protection (fast flushes) or replication to another machine before acking, which trades disk durability for network latency.

(d) Rotation. Creating a new log file and renaming the old one are directory changes. After creating the new file, fsync the directory, or after a crash the new file (and messages acknowledged in it) might not have a name. Renaming the old file also needs a directory fsync to be durable. And fsync the old file one last time before closing it so its tail is durable. The general rule: fsync data before acknowledging, and fsync the directory whenever durability depends on a name existing.
