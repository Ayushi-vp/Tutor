A web server answers a request: it receives bytes from a network card, maybe reads a file from an SSD, and sends bytes back. Each of those devices works on its own schedule, millions of times slower or faster than the CPU's view of time. The network card might deliver a packet now, or in three seconds. The SSD takes 80 microseconds, an eternity of 300,000 CPU cycles. The kernel has to coordinate all of this: tell devices what to do, find out when they are done, move the data to the right place, and wake the right thread, without wasting CPU waiting and without drowning in overhead when events arrive millions of times per second.

How a program asks for I/O shapes everything about its architecture. A thread per connection that simply blocks is easy to write but costs memory and context switches at scale. An event loop with non-blocking sockets and epoll handles tens of thousands of connections on one thread, as net13 showed, but stalls if anything blocks. io_uring promises asynchronous everything with almost no system calls, and comes with security concerns. Underneath, interrupts and DMA decide how much CPU a gigabyte of traffic costs.

Interviewers ask about this layer in two ways. Classic OS questions: "polling versus interrupts", "what is DMA", "blocking versus non-blocking versus asynchronous I/O", "how does epoll differ from select". Systems questions: "why is your event loop stalling", "why can't epoll make file reads asynchronous", "what is io_uring and why is it fast", "how would you find where this I/O latency comes from".

This lesson starts at the hardware (registers, polling, interrupts, DMA and descriptor rings), moves through the block layer and I/O schedulers, lays out the five I/O models, opens up select, poll and epoll to show why their costs differ, and finishes with io_uring and how to diagnose I/O problems in production. It builds on the socket-level view in net13 and the page cache from os8 and os10.

A restaurant kitchen and its waiters

Think of the CPU as a waiter and the devices as kitchen stations. The waiter could stand at the grill asking "is it ready yet?" every few seconds: that is polling, simple and quick to notice when the food is ready, but the waiter serves nobody else while standing there. Or the grill could ring a bell when an order is ready, and the waiter comes when called: that is an interrupt, efficient when orders are occasional, but if the bell rings every two seconds the waiter does nothing but run back and forth. And instead of carrying every plate personally, the waiter can leave a list of orders on a board and let kitchen porters carry dishes directly to tables, checking back only when a batch is finished: that is DMA with a descriptor ring.

Programs face the same choice one level up. A thread can wait at the counter for its one order (blocking I/O). It can keep asking "ready yet?" (non-blocking I/O with retries). It can ask a manager "tell me which of my 10,000 orders are ready" (I/O multiplexing: select, poll, epoll). Or it can hand over the orders and be told when the food has been delivered to the table (asynchronous I/O: io_uring).

The analogy breaks on speed ratios, which are extreme. An SSD read takes around 100 microseconds; a CPU does hundreds of thousands of operations in that time. A 100 Gb/s network card can deliver over 8 million small packets per second; at that rate even a microsecond of overhead per packet consumes eight cores. Every design in this lesson is about keeping that per-event overhead small.

Two numbers that drive every design

Two quantities explain most I/O design decisions. The first is latency per operation: how long one read or one packet takes from request to completion, from tens of nanoseconds for a cached page to roughly 10-100 µs for an NVMe SSD, around 10 ms for a spinning disk, and milliseconds or more across a network. The second is overhead per operation: the CPU time spent on bookkeeping around each I/O, such as a system call (os1), an interrupt, a context switch to wake a thread, a copy between buffers. When devices were slow, overhead hardly mattered; a 10 ms disk read dwarfed a 5 µs system call. Today devices are fast enough that overhead is often the larger cost, so modern interfaces are all about doing more per kernel crossing: batching requests, polling instead of interrupting when busy, and handing completions back through shared memory. Keep asking "what is the overhead per operation here, and how is it amortised?" as you read.

1. Talking to a device: registers

Every device presents a few registers: a status register (busy, ready, error), a command register (what to do), and data or address registers. The CPU reaches them in one of two ways. x86 has special in/out instructions for a separate I/O port space, now used only by legacy devices. Almost everything else uses memory-mapped I/O (MMIO): the device's registers appear at physical addresses, and ordinary load and store instructions to those addresses go to the device instead of RAM. The kernel maps those addresses uncached, so every access really reaches the device. Because only the kernel maps them (os7), user programs cannot touch devices directly, which is what makes drivers part of the kernel's protection boundary (os1).

2. Polling versus interrupts

To read a disk block the simple way, a driver writes the command and block number into the device's registers, then waits for completion. Waiting by polling means looping on the status register until "ready" appears. If the device takes 100 µs, the CPU wastes 100 µs. Waiting by interrupt means the driver puts the requesting thread to sleep and the CPU runs something else; when the device finishes, it raises an interrupt, the handler runs (os1), notes the completion and wakes the thread.

Which is better depends on timing. An interrupt costs a fixed amount, roughly a microsecond or more including the handler, the context disruption and the eventual wake-up. For slow, infrequent events (a keypress, a disk read on a mostly idle machine) interrupts are clearly better. For very fast devices or very frequent events, the fixed cost dominates: an NVMe read that completes in 10 µs might spend a noticeable share of that on interrupt handling, and a network card receiving millions of packets per second would bury the CPU in interrupts. That is why modern drivers are hybrid: interrupt when idle, poll when busy. Two related techniques: interrupt coalescing, where the device waits until several completions accumulate or a few microseconds pass before interrupting (tunable on network cards with ethtool -C), and Linux's NAPI, where the first packet's interrupt switches the driver into polling mode until the receive ring is empty.

3. DMA and descriptor rings

Moving data byte by byte through registers (programmed I/O) would cost the CPU one instruction per word, impossible at gigabytes per second. With direct memory access, the device itself reads or writes main memory. The driver's job becomes bookkeeping: tell the device which memory to use, and find out when it is done.

Fast devices do this with descriptor rings: circular arrays in memory, shared between driver and device, each entry describing one buffer (physical address and length) plus status flags. For a network card receiving packets:

  1. The driver allocates, say, 1,024 packet buffers and writes their addresses into the receive ring, then tells the card (by writing a "tail" register) that those entries are available.
  2. Each arriving packet is DMA'd by the card into the next available buffer; the card writes the packet length into the descriptor and sets its "done" flag.
  3. The card raises an interrupt (or the driver is already polling). The driver walks the ring from where it left off, hands each completed buffer to the network stack, puts fresh buffers in those slots, and advances the tail register.

Storage works the same way. An NVMe SSD uses submission queues and completion queues in host memory: the driver writes a command (read 8 blocks at LBA 1,234,567 into these pages) into a submission queue and rings a doorbell register; the drive executes it, DMAs the data, posts an entry to the completion queue and interrupts. NVMe allows up to 65,535 queue pairs, so Linux gives each CPU its own, and CPUs never contend with each other to issue I/O. Keep this picture in mind: io_uring, later in the lesson, applies exactly this design to the boundary between programs and the kernel.

4. The block layer and I/O schedulers

Between file systems and storage drivers sits the block layer. A file system submits requests ("read these sectors into these pages"); the block layer may merge adjacent requests into one larger one, schedule them, apply cgroup I/O limits (os13) and accounting, and dispatch them to the driver. Since Linux 5.0 the block layer is fully multi-queue (blk-mq): per-CPU software queues map onto however many hardware queues the device has.

On spinning disks, ordering mattered enormously: a seek costs several milliseconds, so serving requests in disk order rather than arrival order (the "elevator" algorithm) multiplied throughput. Modern Linux offers a few schedulers, set per device in /sys/block/<dev>/queue/scheduler:

SchedulerIdeaTypical use

For NVMe the answer is usually none: there is no seek to optimise, the drive schedules internally across its flash channels, and the most valuable thing the kernel can do is stay out of the way.

5. The five ways a program can wait

Every input operation has two phases: waiting for data to be ready (a packet to arrive, a disk block to be read) and copying it from the kernel into the program's buffer. Richard Stevens' classic Unix Network Programming classifies I/O models by how a program experiences those phases:

ModelWaiting for dataCopyingExample
BlockingThread sleeps in the callInside the same callread() on a blocking socket
Non-blockingCall returns EAGAIN; program retriesInside the successful callO_NONBLOCK + retry loop
MultiplexingThread sleeps in select/poll/epoll for many fdsSeparate read on each ready fdNginx, Redis, asyncio, Node.js
Signal-drivenKernel sends SIGIO when readySeparate readRare today
AsynchronousProgram submits and continuesDone by the kernel; program told on completionio_uring, Windows IOCP

The first four are readiness-based: the kernel tells you when you can do the operation, and you then do it yourself. The last is completion-based: the kernel tells you when it has done it. net13 traced how servers use each; here we look inside the kernel to see why their costs differ.

6. Inside select and poll

select(nfds, readfds, writefds, exceptfds, timeout) takes bitmaps of descriptor numbers. On every call, the kernel copies the bitmaps in, and for each descriptor up to nfds: checks whether it is ready, and if not, adds the calling thread to that descriptor's wait queue (the list the kernel wakes when that socket gets data). If none is ready, the thread sleeps; when any wakes it, the kernel scans all descriptors again, removes the thread from every wait queue, writes back the bitmaps, and returns. The program then scans the bitmaps to find which are set. poll() replaces the fixed-size bitmaps with an array of {fd, events, revents} structures, removing select's limit of descriptor numbers below FD_SETSIZE (1,024), but does the same work.

So every call costs O(n) in the number of watched descriptors, regardless of how many are active. A server with 10,000 connections, of which 10 are active at any moment, does 10,000 checks to find 10. That was the heart of the C10K problem (net13).

7. Inside epoll

epoll separates the two jobs that select repeats on every call. epoll_create1() makes an epoll instance, itself a file descriptor, holding an interest list (a red-black tree of registered descriptors) and a ready list. epoll_ctl(ADD, fd, events) registers a descriptor once: the kernel inserts it into the tree and attaches a small callback to the descriptor's wait queue. From then on:

  1. When data arrives on the socket, the network stack wakes the socket's wait queue as usual, which runs epoll's callback.
  2. The callback appends that descriptor to the epoll instance's ready list (if not already there) and wakes any thread sleeping in epoll_wait.
  3. epoll_wait() copies up to maxevents entries from the ready list to the program and returns. If the list is empty, it sleeps.

Level- versus edge-triggered. In the default level-triggered mode, a descriptor that remains readable stays on the ready list and is reported on every epoll_wait. With EPOLLET (edge-triggered), it is reported only when new data arrives; if the program reads half the data and waits again, it will not hear about this descriptor until more data comes, and the remaining bytes sit unread. Edge-triggered code must therefore use non-blocking descriptors and read (or write) until EAGAIN. net13 discusses when each fits; two more flags matter for multithreaded servers. EPOLLONESHOT disables a descriptor after one event until it is re-armed, so two threads never handle the same connection at once. EPOLLEXCLUSIVE (Linux 4.5) wakes only one of several epoll instances waiting on the same descriptor, avoiding the thundering herd (os5) on a shared listening socket.

macOS and the BSDs have kqueue, which plays the same role as epoll and also covers timers, signals, process exits and file changes in one interface. Windows takes the completion route with I/O completion ports.

8. The hole in readiness: regular files

Readiness APIs work for sockets, pipes and terminals, whose "not ready" state can last forever. Regular files are different: the kernel considers them always ready, because a disk read completes in bounded time. So epoll reports a file descriptor as readable immediately, and the following read() still blocks the thread while the disk fetches uncached data, freezing the entire event loop for 100 µs to tens of milliseconds. This is why libuv (Node.js) uses a thread pool for file system calls, why Python's asyncio offers run_in_executor and asyncio.to_thread for file work, and why nginx has thread pools for file reads. The older Linux AIO interface (io_submit) offered asynchronous file I/O, but only reliably with O_DIRECT, and it could still block in surprising places, so it saw little use outside databases. That gap is a major reason io_uring was created.

9. io_uring: I/O through shared rings

io_uring, added in Linux 5.1 (2019) by Jens Axboe, gives programs the same structure NVMe gives drivers. Setting up an instance with io_uring_setup() creates two ring buffers in memory shared between the program and the kernel:

  • A submission queue (SQ): the program writes submission queue entries (SQEs), each describing one operation: opcode (read, write, accept, connect, send, recv, openat, fsync, timeout, and dozens more), file descriptor, buffer address, length, offset, and a 64-bit user_data tag to match results.
  • A completion queue (CQ): the kernel writes completion queue entries (CQEs), each with the user_data tag and a result (bytes transferred or a negative error).

The flow: the program fills several SQEs, advances the SQ tail, and calls io_uring_enter() once to submit them all (optionally also waiting for some number of completions). The kernel executes each operation, completing it inline if it can (data already in the page cache, a socket with data waiting) or handing it to internal async workers or poll-based retry if it would block, and posts CQEs. The program reads CQEs straight from shared memory and advances the CQ head; no system call is needed to collect results.

Where the speed comes from: batching (one kernel entry for many operations, which matters more since Meltdown mitigations made each entry dearer, os1); completion semantics (one step does the wait and the copy, instead of epoll_wait followed by read); uniformity (files, sockets, timers and file-system operations all asynchronous through one interface); and optional modes that remove more overhead. SQPOLL runs a kernel thread that polls the submission ring, so a busy program submits work just by writing to memory. Registered files and buffers pre-register descriptors and pin memory once, avoiding per-operation lookups and page pinning. Linked SQEs chain operations (read then write, with a timeout) so they run in order without returning to user space. Most programs use it through liburing or runtime support (Rust's tokio-uring and glommio, Java's Netty incubator transport, databases such as ScyllaDB and TigerBeetle, and io_uring use for some file operations in libuv, and an optional io_uring method in PostgreSQL 18's new asynchronous I/O).

The caveat is security. io_uring exposes a large, fast-moving kernel surface that bypasses some of the usual syscall-filtering points. In 2023 Google reported that most of the kernel exploits submitted to its kernel bug bounty in the previous year targeted io_uring, and it disabled or restricted io_uring on ChromeOS, Android apps and its production servers; Docker's default seccomp profile blocks the io_uring system calls too. A sysctl (kernel.io_uring_disabled, Linux 6.6) lets administrators turn it off or limit it to a group.

Receive livelock and why polling came back

In 1996, Mogul and Ramakrishnan showed that interrupt-driven kernels collapse under packet floods: each packet's interrupt preempts whatever is processing earlier packets, so at high enough rates the CPU spends all its time acknowledging packets it never finishes processing, and useful throughput falls to zero while the CPU is 100% busy. The fix is to bound the work done in interrupt context and switch to polling under load, processing a budget of packets per poll and dropping excess input early. Linux's NAPI (2001) implements exactly this: the first packet's interrupt disables further receive interrupts on that queue and schedules a poll in softirq context; the poll processes up to a budget (64 packets per device by default) per round and only re-enables interrupts when the ring is empty. Busy polling (SO_BUSY_POLL) lets a latency-sensitive socket reader spin on the device queue directly for a few microseconds, trading CPU for lower latency.

Spreading interrupts and packet processing across CPUs

A single queue and a single interrupt would serialise all network processing on one CPU. Modern cards have many receive queues and use receive-side scaling (RSS): a hash of each packet's addresses and ports picks the queue, so all packets of one connection land on the same queue and CPU (preserving order and cache locality) while different connections spread out. Each queue has its own interrupt (MSI-X), which can be pinned to a CPU via /proc/irq/<n>/smp_affinity, usually managed by irqbalance. Software equivalents (RPS, RFS) do the spreading in the kernel for cards with fewer queues, and RFS steers packets to the CPU where the consuming thread runs. Getting this wrong shows up as one CPU at 100% in softirq (si in top) while others idle.

Avoiding copies: zero-copy paths

A classic file-serving path copies data twice: disk to page cache by DMA, page cache to a user buffer by read(), user buffer to socket buffer by write(), then DMA to the card. sendfile() lets the kernel send page-cache pages to a socket directly, skipping the user-space copies, which is how nginx and Kafka serve static data efficiently. splice() moves data between a pipe and another descriptor by passing page references. MSG_ZEROCOPY lets send() transmit from user pages without copying, notifying the program via the error queue when the pages can be reused; it pays off only for large sends because of the bookkeeping. kTLS moves TLS encryption into the kernel (or the card) so even encrypted traffic can use sendfile. io_uring adds registered buffers and zero-copy send and receive paths for the same reasons.

Polled storage I/O

NVMe devices can complete reads in under 10 µs, comparable to the cost of an interrupt plus a context switch to wake the waiting thread. For such devices Linux supports polled I/O: the submitting thread (or an io_uring instance created with IORING_SETUP_IOPOLL) spins on the completion queue instead of sleeping, so completions are noticed within nanoseconds. It burns a core per polling context, so it is used where latency or IOPS per core matter more than CPU efficiency, such as storage engines and benchmarks; SPDK takes the extreme route of a user-space NVMe driver that polls with no kernel involvement at all.

Who wakes whom: the cost of a wake-up

Even with perfect devices, a blocking read on an idle thread involves a chain of hand-offs: the interrupt handler records completion, the kernel marks the sleeping thread runnable, the scheduler eventually runs it on some CPU (maybe a different one, with cold caches), and only then does the program see its data. Each step adds microseconds of latency and jitter, and at high rates the wake-ups themselves become a large share of CPU. That is the deeper reason event loops and io_uring batch completions, why NAPI and polled I/O spin while busy, and why latency-critical systems pin the consuming thread to the CPU that handles the device's interrupts.

Why asynchronous file I/O took so long on Linux

File I/O can block in many places beyond the device: page-cache misses, metadata reads to find the blocks, journal waits, memory allocation, locks inside the file system. Making all of those asynchronous inside the kernel is a huge change, which is why Linux AIO only worked for O_DIRECT on some file systems and quietly blocked otherwise. io_uring took a pragmatic approach: try the operation non-blockingly inline, and if it would block, hand it to a pool of kernel worker threads (io-wq) that perform it synchronously, so the program never blocks. Later versions reduced the use of workers by adding non-blocking paths in file systems and block layers. The design shows a recurring systems pattern: when you cannot make an operation asynchronous at the bottom, move the blocking onto threads you control.

Looking at interrupts

/proc/interrupts shows, per CPU, how many interrupts each device line has raised; watching it with watch -d reveals which CPUs handle network and storage interrupts. mpstat -P ALL 1 and top (press 1) show per-CPU %irq and %soft. A single CPU saturated with softirq work while others idle means interrupts and packet processing are not spread: check that the card has multiple queues (ethtool -l), that RSS is enabled, and that irqbalance or manual affinity distributes queue interrupts. ksoftirqd/N running hot means softirq work has overflowed into its fallback thread on CPU N. For latency-critical applications, a common pattern is to keep interrupts off the cores running the application's threads (or deliberately on the same core, to keep data cache-hot); measure both.

Storage latency, queue depth and utilisation

iostat -x 1 is the first tool: per device, r/s and w/s (IOPS), rkB/s and wkB/s (throughput), r_await and w_await (average latency including time queued), aqu-sz (average number of requests in flight) and %util. %util is misleading for SSDs and NVMe: it measures the share of time at least one request was in flight, so a device that can serve 64 requests in parallel can show 100% while far from saturated; use latency and IOPS against the device's specification instead. For distributions, the eBPF tools biolatency (histogram of block I/O latency) and biosnoop (each I/O with process, size and latency) show tail behaviour and who causes it. Cloud block volumes add their own limits: provisioned IOPS and throughput caps and burst credits, which produce sudden latency cliffs when exhausted.

Event-loop stalls

In epoll-based servers (Node.js, Python asyncio, Netty, Redis), the canonical I/O incident is a blocked loop: one handler does a synchronous file read, a DNS lookup, a CPU-heavy parse or a blocking database call, and every other connection on that loop waits. Measure event-loop lag (schedule a timer and measure how late it fires; Node's monitorEventLoopDelay, asyncio's debug mode which logs callbacks slower than 100 ms). Fixes: move blocking work to thread pools or io_uring, split CPU work into worker processes, and make sure file access in the request path is either cached in memory or asynchronous. Redis, single-threaded by design, documents its own version: avoid slow commands (KEYS, large SMEMBERS) that block all clients.

Choosing an I/O model

For most services the choice is about developer time, not microseconds. A thread or virtual thread per request with blocking calls is simplest and fine up to thousands of concurrent requests. An event loop (epoll via your runtime) is the standard for tens of thousands of mostly idle connections. io_uring pays off for storage-heavy engines, very high request rates per core, or when file I/O must be asynchronous; check that your kernel, container runtime's seccomp profile and security policy allow it before depending on it. Whatever the model, bound concurrency to what the devices can usefully absorb: more in-flight I/O than the device's internal parallelism only adds queueing latency.

Writes that look like reads

A frequent surprise: read latency spikes on a database volume every few seconds, and the cause is writes. Large write-back bursts from the page cache (os10), journal commits or an SSD's internal garbage collection occupy the device and reads queue behind them. Signs are periodic w/s bursts aligned with r_await spikes. Remedies: smoother write-back (lower dirty thresholds), separating write-heavy data (logs, WAL) onto another device, I/O cgroup limits on bulk writers, and leaving free space on SSDs so garbage collection has room.

Measure why epoll scales and select/poll do not. Linux or WSL, Python 3.

  1. Save as mux.py: 
    import os, select, time, resource
soft, hard = resource.getrlimit(resource.RLIMIT_NOFILE)
resource.setrlimit(resource.RLIMIT_NOFILE, (min(hard, 20000), hard))

def bench(n, rounds=200):
    pipes = [os.pipe() for _ in range(n)]
    reads = [r for r, w in pipes]
    os.write(pipes[-1][1], b"x")              # exactly one ready fd
    p = select.poll()
    for r in reads: p.register(r, select.POLLIN)
    ep = select.epoll()
    for r in reads: ep.register(r, select.EPOLLIN)
    t = time.perf_counter()
    for _ in range(rounds): assert len(p.poll(0)) == 1
    t_poll = (time.perf_counter() - t) / rounds * 1e6
    t = time.perf_counter()
    for _ in range(rounds): assert len(ep.poll(0)) == 1
    t_ep = (time.perf_counter() - t) / rounds * 1e6
    print(f"{n:6} fds: poll {t_poll:8.1f} µs/call   epoll {t_ep:6.1f} µs/call")
    ep.close()
    for r, w in pipes: os.close(r); os.close(w)

for n in (10, 100, 1000, 5000):
    bench(n)
  2. Run python3 mux.py. If it fails with "Too many open files", run ulimit -n 20000 first (each pipe uses two descriptors).
  3. Edge versus level: in a Python shell, create a pipe, register its read end with select.EPOLLIN | select.EPOLLET, write 10 bytes, call ep.poll(0) twice; then read 5 bytes and poll again; then write 1 more byte and poll.

What to look for. With one ready descriptor in every case, poll's time per call grows roughly in proportion to the number of descriptors (the kernel checks every one and Python builds the full list), from a few microseconds at 10 to hundreds at 5,000, while epoll stays nearly flat, since it only returns the ready list. That flat line is why event-driven servers can hold tens of thousands of idle connections. In step 3, edge-triggered epoll reports the pipe on the first poll after the write but not on the second, and not after the partial read, even though 5 bytes are still waiting; only the new write produces another event. That is the "must drain until EAGAIN" rule in action.

Diagnose: the API that freezes when the log disk is slow

A Python asyncio API service handles about 3,000 requests per second on one event loop per process. Every request appends an audit line to a local file with a plain open(...).write() call inside the coroutine. Normally p99 latency is 15 ms. Several times a day, p99 jumps to 2-3 seconds for a minute, across all endpoints, including health checks; CPU drops during these periods. The incidents coincide with a nightly-style log compression job that runs at random times on the same disk, and iostat then shows w_await on that disk above 500 ms. Explain the mechanism, why epoll does not prevent it, and fix it.

Answer

Mechanism. The audit write is a synchronous file operation executed on the event-loop thread. Usually it is fast: write() copies into the page cache and returns in microseconds (os10). But when the compression job floods the disk with writes, dirty memory rises past the dirty limits and the kernel throttles writers: write() calls block until write-back catches up, and with w_await above 500 ms that can mean hundreds of milliseconds per call. Opening the file each time can also block on metadata and journal waits. While the loop thread is blocked, no other coroutine runs: health checks, other endpoints and already-arrived responses all wait. CPU drops because the only thread is asleep in the kernel.

Why epoll does not help. asyncio's event loop uses epoll to know when sockets are ready. File descriptors for regular files are always reported ready, and asyncio does not route ordinary file writes through the selector at all; a write() to a file is just a blocking system call made directly by the coroutine. Readiness-based multiplexing has no way to make it non-blocking.

Fix. Take file I/O off the loop. Simplest: push audit lines onto an asyncio.Queue (bounded) and have one background writer thread (or asyncio.to_thread worker) drain it, keeping the file open and writing in batches; if the queue fills because the disk is slow, decide explicitly whether to drop lines (count them) or apply backpressure. Alternatively log to stdout and let the platform's agent handle files, or use an io_uring-based async file library. Separately, isolate the compression job: run it under an I/O cgroup limit (io.max) or with ionice -c3, and consider lower dirty-memory thresholds so writers are not throttled in large bursts. Add an event-loop-lag metric and alert so the next blocking call is caught before users notice.
