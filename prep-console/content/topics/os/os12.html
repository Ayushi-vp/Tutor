The isolation that os2 and os7 work so hard to provide has a cost: processes cannot simply share variables. Yet real systems are made of cooperating processes everywhere you look. A shell pipeline chains grep, sort and uniq. Chrome splits each tab into a renderer process that talks to the browser process thousands of times a second. PostgreSQL's backends share one buffer pool of gigabytes. A PyTorch training job's data-loader workers hand decoded batches to the main process. Nginx's master process tells its workers to reload configuration. docker on the command line talks to the Docker daemon. Kubernetes tells your container to shut down. Each uses a different inter-process communication (IPC) mechanism, chosen for different reasons.

Choosing badly causes real incidents. A pipeline hangs because a process forgot to close a pipe end. A server dies silently when a client disconnects, killed by a signal nobody handled. A machine-learning job crashes with "Bus error" only inside Docker. A service takes 30 seconds to stop on every deploy and drops requests when it finally does. A shared-memory design corrupts data because two processes wrote without a lock, or deadlocks because one crashed while holding it.

Interviewers ask "what IPC mechanisms do you know and when would you use each?", "how does a pipe work?", "what is a signal?" and "what is async-signal-safe?" in OS rounds, and design questions in senior rounds: "how would two processes on one machine exchange large data with low latency?", "how do you implement graceful shutdown?".

This lesson covers the mechanisms one by one (pipes and FIFOs, Unix domain sockets, message queues, shared memory, signals), how each works inside the kernel, what each costs, and how to choose, then the production failures each one is known for.

Ways to talk between rooms

Picture processes as people in separate, soundproof rooms of one building (the machine). They cannot hear or see each other. The building (the kernel) offers several ways to communicate:

  • A pneumatic tube from one room to another: whatever one side pushes in comes out the other side in order. That is a pipe: one direction, a stream of bytes, with a limited capacity in the tube.
  • A telephone line between two rooms, which either side can dial by a number listed in the lobby: two-way conversation, and the caller can even hand over a key to a room through it. That is a Unix domain socket.
  • A mailbox where people drop separate letters, possibly marked urgent: each letter arrives whole. That is a message queue.
  • A shared whiteboard visible from both rooms through a window: no need to send anything, but two people writing at once make a mess unless they agree on turns. That is shared memory, plus the synchronization from os4.
  • A doorbell with a few distinct rings: it carries no message beyond "ring number 15", it interrupts whatever you were doing, and if it rings twice while you are answering the first, you may only notice once. That is a signal.

Where the analogy breaks: everything except shared memory actually passes through the kernel, which copies the data from the sender's memory into a kernel buffer and then into the receiver's memory. Those copies are what make these mechanisms safe and simple, and also what limits their speed for large volumes. Shared memory removes the copies and with them the safety.

Four questions before choosing

Almost every IPC decision comes down to four questions. Are the processes related? A parent can hand its children inherited descriptors (pipes, anonymous shared mappings); strangers need something with a name (a FIFO, a socket path, a named shared-memory object) or a broker. Which direction, and what shape? One-way streaming suits a pipe; request and response suits a socket; discrete prioritised messages suit a queue; a big data set both sides read suits shared memory. How much data, how often? At kilobytes per request, two kernel copies are invisible; at gigabytes per second, they cost whole cores. What happens when one side dies? With pipes and sockets the kernel tells the survivor (end-of-file, EPIPE, connection reset); with shared memory nobody tells you anything, and a lock held by the dead process stays held. Most production problems with IPC trace back to an unasked fourth question.

One more distinction runs through the lesson: data versus notification. Pipes, sockets and queues carry data and notify at the same time, because a blocked reader wakes when bytes arrive. Shared memory carries data but notifies nobody, and signals notify but carry no data. Designs that use shared memory therefore always pair it with some notification channel, and designs that use signals pair them with some data channel, such as a configuration file to reread on SIGHUP.

1. Pipes

pipe(fds) creates a kernel buffer and returns two file descriptors: fds[0] for reading and fds[1] for writing. Data written to one end comes out of the other, in order, as a byte stream with no message boundaries. On its own a pipe is useless; its power comes from fork (os2), which copies descriptors into the child, so parent and child share both ends and each closes the end it does not use.

import os
r, w = os.pipe()
if os.fork() == 0:                # child: the writer
    os.close(r)
    os.write(w, b"hello from child\n")
    os._exit(0)
os.close(w)                       # parent: the reader; close its copy of w!
print(os.read(r, 100))            # b'hello from child\n'
print(os.read(r, 100))            # b'' : every writer has closed, so EOF
os.wait()

The rules of a pipe follow from its buffer, 64 KiB by default on Linux (16 pages; adjustable up to /proc/sys/fs/pipe-max-size, 1 MiB by default, with fcntl(F_SETPIPE_SZ)):

  • Full buffer: write() blocks until the reader drains space. This is natural backpressure: a fast producer piped into a slow consumer is slowed down automatically (os5).
  • Empty buffer: read() blocks until data arrives, unless every write end in every process has been closed, in which case it returns 0, end-of-file. Forgetting to close one copy of the write end (in the reader itself, or in a child that inherited it) means EOF never comes and the reader hangs forever.
  • No readers: if every read end is closed, write() raises SIGPIPE in the writer, which kills it by default; if SIGPIPE is ignored, the write fails with EPIPE. That is how yes | head -1 ends: head exits after one line, and yes dies on its next write.
  • Atomicity: a write of at most PIPE_BUF bytes (4,096 on Linux) is atomic: it will not be interleaved with other writers' data. Larger writes from several processes can interleave. That is why many processes can safely write short lines to one shared pipe or log, but not large records.

A named pipe or FIFO (mkfifo /tmp/feed) is a pipe with an entry in the file system. Unrelated processes open it by name, one for reading and one for writing; data still flows through a kernel buffer, never through the disk. Opening one end blocks until the other end is opened too, a frequent source of "my script hangs at open".

2. Unix domain sockets

Unix domain sockets (AF_UNIX) use the socket API from net13 between processes on the same machine. A server binds to a path such as /run/myapp.sock (or, on Linux, an abstract name that exists only in the kernel, written with a leading zero byte), listens and accepts; clients connect to the path. Compared with pipes they are bidirectional, can be connected to by unrelated processes, and come in three types: SOCK_STREAM (a byte stream, like TCP), SOCK_DGRAM (messages with boundaries preserved, and on Unix sockets, unlike UDP, reliable and ordered) and SOCK_SEQPACKET (connection-oriented messages).

They have three abilities TCP lacks, which explain why so much local infrastructure uses them:

  • Permission control by the file system. A socket file's owner and mode decide who can connect. The Docker daemon listens on /var/run/docker.sock, owned by root and the docker group; anyone who can write to it can control containers, which is effectively root access (production section).
  • Peer credentials. getsockopt(SO_PEERCRED) returns the connecting process's PID, user ID and group ID, verified by the kernel. PostgreSQL's peer authentication and systemd's services use this to know who is calling without passwords.
  • Passing file descriptors. With sendmsg() and an SCM_RIGHTS control message, a process can send open file descriptors; the kernel installs new descriptors in the receiver pointing to the same open file descriptions (os10). The receiver gets access to a file, socket or pipe it could not have opened itself.

Because they skip the network stack entirely (no TCP handshake, sequence numbers, checksums, congestion control or routing), Unix sockets have noticeably lower latency and CPU cost than TCP over loopback; benchmarks typically show tens of percent or more better throughput for small messages. Databases, X11 and Wayland, D-Bus, container runtimes (containerd, the kubelet's CRI socket) and local proxies use them.

3. Message queues

A message queue is a kernel-held list of discrete messages. POSIX queues (mq_open("/jobs", ...), mq_send, mq_receive) give each message a priority, deliver the highest-priority oldest message first, block senders when the queue is full and receivers when it is empty, and appear under /dev/mqueue. On Linux a queue descriptor works with select/epoll, and mq_notify can signal a process when a message arrives. Default limits are small (10 messages of 8 KiB per queue unless raised through /proc/sys/fs/mqueue/). System V message queues (msgget, msgsnd) are the older interface, with typed messages.

Their value over a pipe is that message boundaries are preserved: two 100-byte messages arrive as two 100-byte messages, never as one 200-byte read or a 150 + 50 split, so no framing protocol is needed. In practice they are less common than Unix datagram sockets, which offer the same boundary preservation plus credentials and descriptor passing, and than user-space brokers when messages must survive restarts. Note the difference from distributed message queues such as Kafka or SQS: kernel queues are local, in memory, and vanish on reboot.

4. Shared memory

Every mechanism so far copies data twice: from the sender into a kernel buffer, then from the kernel buffer into the receiver. For a few kilobytes that is negligible; for gigabytes per second it consumes cores. Shared memory removes the copies by mapping the same physical pages into both processes' address spaces (os7): a store by one process is visible to a load by the other, with the kernel not involved at all after setup. Three common ways to set it up on Linux:

  • Anonymous shared mapping before fork: mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0), then fork; parent and child share it. Note MAP_SHARED: a private mapping would be copy-on-write (os9).
  • POSIX shared memory: shm_open("/frames", O_CREAT|O_RDWR, 0600) creates a named object, really a file in the /dev/shm tmpfs; size it with ftruncate and map it with mmap(MAP_SHARED) in each process. It persists until shm_unlink. Python's multiprocessing.shared_memory wraps this.
  • memfd: memfd_create() makes an anonymous in-memory file with no name; pass its descriptor over a Unix socket and the receiver maps it. It disappears when the last reference closes, so nothing leaks, and seals can make it immutable before sharing.

Synchronizing across processes. Everything in os4 applies, because two processes sharing memory are like two threads sharing memory. A pthread mutex or condition variable placed in the shared region works across processes if initialised with the PTHREAD_PROCESS_SHARED attribute; it is a futex on the shared page, and futexes work on shared mappings. POSIX named semaphores (sem_open) and C11 atomics in the region also work. Two extra hazards: a process can crash while holding a lock, leaving it locked forever (robust mutexes, PTHREAD_MUTEX_ROBUST, report EOWNERDEAD to the next locker so it can repair the data), and memory ordering must be handled exactly as between threads, with acquire and release when publishing data.

PostgreSQL's shared buffers, Chrome's compositor buffers, PyTorch tensors passed between DataLoader workers and the main process, and audio servers' ring buffers all use shared memory, each with its own synchronization protocol on top.

5. Signals

A signal is a small, numbered, asynchronous notification sent to a process (or a specific thread). Sources: the kernel (SIGSEGV for a bad memory access, SIGPIPE for writing to a closed pipe, SIGCHLD when a child exits), the terminal (SIGINT on Ctrl+C, SIGTSTP on Ctrl+Z), and other processes via kill(pid, sig), subject to permission (same user, or privileged). Each signal has a default action:

SignalNumber (x86 Linux)Typical sourceDefault actionCatchable?

How delivery works. Sending a signal sets a bit in the target's pending set; it does not run anything immediately. Each thread has a signal mask of blocked signals, which stay pending until unblocked. When the target thread next returns from the kernel to user mode (after a system call, an interrupt, or being scheduled), the kernel checks for pending, unblocked signals and delivers one: either performs the default action, ignores it, or arranges for the thread to run the program's handler, by building a frame on the user stack so the thread "returns" into the handler and, when the handler returns, into a sigreturn system call that restores the interrupted state (os1's deep section). If the thread was blocked in a slow system call, the call is interrupted and either restarted automatically (with SA_RESTART) or fails with EINTR.

Standard signals are not queued. Pending is a bit, not a counter. If three children exit while SIGCHLD is already pending, the parent's handler may run once, so a handler must loop with waitpid(-1, WNOHANG) until no more children are reaped (os2). Real-time signals (SIGRTMIN to SIGRTMAX) are queued and can carry a value, but are rarely used directly.

Handlers are dangerous. A handler can run between any two instructions of the main program, including in the middle of malloc while it holds the allocator lock or halfway through updating a linked list. If the handler calls malloc, printf or almost any library function, it can deadlock or corrupt state. POSIX lists the async-signal-safe functions callable from handlers (write, read, _exit, kill, sigaction and a few dozen more). The robust patterns all reduce the handler to almost nothing:

  • Set a volatile sig_atomic_t flag that the main loop checks.
  • The self-pipe trick: the handler writes one byte to a pipe that the event loop watches with epoll, turning the signal into an ordinary readable event.
  • signalfd (Linux): block the signals, then read them as data from a file descriptor in the event loop; no handler at all.
  • In multithreaded programs: block signals in all threads and dedicate one thread to sigwait().

Higher-level runtimes do this for you. CPython's C-level handler only records that a signal arrived; your Python handler runs later, in the main thread, between bytecodes. asyncio's loop.add_signal_handler uses a self-pipe; Go delivers signals on a channel.

A common combination is a Unix socket for control (connect, authenticate, pass a memfd, exchange small commands) plus shared memory for bulk data, plus an eventfd or futex for "new data is ready" notifications. That is the structure of Wayland compositors, Chrome's GPU process channels, many high-frequency trading feeds and some inference servers.

Passing descriptors: socket activation and zero-downtime restarts

Descriptor passing enables patterns that would otherwise be impossible. With systemd socket activation, systemd creates and binds a service's listening socket at boot, before the service starts, and passes it to the service as an inherited descriptor (fd 3 onwards, announced in LISTEN_FDS). Connections arriving before the service is ready wait in the socket's accept queue instead of being refused, services can be started on demand, and the socket survives service restarts. Zero-downtime reloads work similarly: nginx re-executes its binary while keeping listening sockets inherited across exec, and proxies such as HAProxy and Envoy hand listening sockets from the old process to the new one over a Unix socket with SCM_RIGHTS, so no connection is ever refused. Because each passed descriptor shares the same open file description, the new process accepts from the very same kernel queue.

eventfd and futexes as doorbells

Shared-memory designs need a way to wake a sleeping consumer without spinning. An eventfd is a descriptor holding a 64-bit counter: write adds to it, read returns and resets it (or decrements by one in semaphore mode), and it is readable in epoll when non-zero, so it slots into event loops. Between threads and processes that share memory, a futex word inside the shared region does the same job with less overhead (os4). A well-designed shared-memory ring only rings the doorbell when the consumer has said it is going to sleep, avoiding a system call per message in the busy case.

Android's Binder and D-Bus

Operating systems often build a higher-level IPC system on top of these primitives. D-Bus, used on Linux desktops and by systemd, is a message bus over Unix sockets with typed method calls, signals (events, not Unix signals) and a central broker that handles naming and access policy. Android's Binder is a kernel driver for object-oriented remote procedure calls between apps and system services: a transaction copies data once, directly from the sender into a buffer mapped by the receiver, carries the caller's identity for permission checks, can pass file descriptors and object references, and integrates with thread pools and priority inheritance. Nearly every Android API call, from opening the camera to showing a notification, is a Binder transaction.

Signals and threads: why they mix badly

Signal dispositions (handlers) are per process, but masks and delivery are per thread, and a process-directed signal goes to an arbitrary thread that does not block it. Libraries that start background threads therefore change where signals land, and a handler can run on a thread holding a lock the handler needs. Combined with async-signal-safety, this is why robust multithreaded programs block all asynchronous signals in every thread at startup (masks are inherited by new threads) and consume them in one dedicated place: a sigwait thread or a signalfd in the event loop. Synchronous signals such as SIGSEGV and SIGFPE still go to the faulting thread, which is what lets runtimes such as the JVM implement null checks and safepoints with deliberate faults on guard pages.

IPC across containers

Containers (os13) isolate IPC as well as files and networks. Each container normally gets its own IPC namespace, which separates System V objects and POSIX message queues, and its own /dev/shm, so two containers cannot see each other's shared memory or queues by name. Each also has its own network namespace, so localhost in one container is not localhost in another, except for containers in one Kubernetes pod, which share a network namespace and can talk over loopback. Unix sockets are files, so they cross container boundaries wherever a directory is shared: a socket in a volume mounted into two containers is how sidecars such as service-mesh proxies, log agents and the kubelet's container-runtime socket communicate. Pods can opt into a shared IPC namespace for shared memory between their containers, and docker run --ipc=container:<name> does the same for two containers.

Copies, splice and vmsplice

Pipes copy data in and out, but Linux can move data between descriptors without user-space copies. splice() moves pages between a pipe and a file or socket by passing page references inside the kernel, and vmsplice() maps user pages into a pipe. tee() duplicates pipe contents without consuming them. Tools such as high-throughput log shippers and proxies use these to forward data between sockets and files with minimal CPU. They are subtle (the user must not modify pages given to vmsplice until consumed), which is why most programs use sendfile (os11) or plain copies.

SIGPIPE: the silent killer

A C or Go-cgo server that writes to a client which has already disconnected receives SIGPIPE, whose default action kills the whole server, with no log line. Servers therefore ignore SIGPIPE at startup (signal(SIGPIPE, SIG_IGN)) or pass MSG_NOSIGNAL to send(), and handle the resulting EPIPE error per connection. Python ignores SIGPIPE at interpreter startup, so the same situation raises BrokenPipeError; that is why python script.py | head prints a traceback about a broken pipe when head exits early. The usual fix in command-line tools is to catch it and exit quietly, or restore the default disposition so the tool dies like other Unix filters.

/dev/shm in containers

POSIX shared memory lives in /dev/shm, a tmpfs. Docker gives each container its own /dev/shm of only 64 MB by default. Anything that moves large data through shared memory then fails inside containers but works on the host: PyTorch DataLoader workers (which share batch tensors through shared memory) crash with "Bus error" or "unable to write to file", Chrome and Electron renderers crash, and PostgreSQL's parallel queries fail to allocate dynamic shared memory. Fixes: docker run --shm-size=8g, in Kubernetes a emptyDir volume with medium: Memory and a sizeLimit mounted at /dev/shm, or --ipc=host where isolation allows. Remember that tmpfs pages count against the container's memory limit (os9).

Graceful shutdown under orchestration

When Kubernetes deletes a pod, the kubelet sends SIGTERM to the container's PID 1, waits terminationGracePeriodSeconds (30 seconds by default), then sends SIGKILL. Meanwhile, endpoints are removed from load balancers asynchronously, so new requests may still arrive for a few seconds after SIGTERM. A well-behaved service: catches SIGTERM; starts failing its readiness probe; keeps serving for a short drain period (often implemented as a preStop sleep of 5-10 seconds) so in-flight routing updates catch up; stops accepting new connections; finishes in-flight requests within a deadline; flushes buffers; and exits. Common failures: the application is not PID 1 and never receives SIGTERM (a shell entrypoint without exec, os2); the handler exits immediately, dropping in-flight requests; or shutdown takes longer than the grace period and is cut off by SIGKILL.

The Docker socket is root

Mounting /var/run/docker.sock into a container (common for CI agents and monitoring tools) gives that container full control of the Docker daemon, which runs as root: it can start a privileged container with the host's root file system mounted and take over the machine. Unix-socket permissions are the only gate, so membership of the docker group is equivalent to root. Safer alternatives are rootless runtimes, socket proxies that allow only specific API calls, and build tools that do not need a daemon.

Leaks and stale endpoints

IPC objects can outlive their processes. A server that crashes leaves its Unix socket file behind, and the next start fails with "Address already in use" until the stale file is removed (servers commonly unlink the path before bind, carefully, or use abstract names, which vanish with the socket). POSIX shared memory and message queues persist in /dev/shm and /dev/mqueue until unlinked; System V segments, queues and semaphores persist until removed with ipcrm (list them with ipcs). Python's multiprocessing.shared_memory warns about "leaked shared_memory objects" at shutdown for this reason. Leaked segments consume RAM (tmpfs is memory) and count against limits.

Pipe hangs

Two classic hangs come from pipe rules. A reader waiting for EOF that never arrives, because some process still holds a write end (often a child that inherited it, which is one reason to use O_CLOEXEC/close_fds=True, the default in Python's subprocess). And the two-pipe deadlock from os6: a parent writes a large input to a child's stdin while the child, which writes output as it goes, blocks on its full stdout pipe that the parent is not reading. subprocess.run(..., input=...) and communicate() avoid it by reading and writing concurrently.

Compare copying through a pipe with shared memory, and handle SIGTERM gracefully. Linux, WSL or macOS with Python 3.8+.

  1. Save as ipc.py: 
    import os, time, signal
from multiprocessing import shared_memory

N = 200 * 1024 * 1024                         # 200 MB payload
data = os.urandom(1024) * (N // 1024)

# 1. through a pipe: copied into and out of the kernel
r, w = os.pipe()
t = time.perf_counter()
if os.fork() == 0:
    os.close(r); mv = memoryview(data)
    for i in range(0, N, 1 << 20): os.write(w, mv[i:i + (1 << 20)])
    os._exit(0)
os.close(w); got = 0
while chunk := os.read(r, 1 << 20): got += len(chunk)
os.wait()
print(f"pipe:          {got / (time.perf_counter() - t) / 1e9:.2f} GB/s")

# 2. shared memory: child writes in place, parent reads it directly
shm = shared_memory.SharedMemory(create=True, size=N)
t = time.perf_counter()
if os.fork() == 0:
    shm.buf[:N] = data; os._exit(0)
os.wait()
print(f"shared memory: {N / (time.perf_counter() - t) / 1e9:.2f} GB/s (one copy, by the writer)")
print("same bytes:", bytes(shm.buf[:16]) == data[:16])
shm.close(); shm.unlink()

# 3. graceful SIGTERM
stop = False
def on_term(sig, frame):
    global stop; stop = True                  # just set a flag
signal.signal(signal.SIGTERM, on_term)
print("pid", os.getpid(), "- run: kill", os.getpid())
while not stop: time.sleep(0.2)
print("got SIGTERM: finishing in-flight work, flushing, exiting 0")
  2. Run python3 ipc.py, and when it prints its PID, run kill <pid> from another terminal. Then try kill -9 <pid> on a second run.
  3. Pipe behaviour: yes | head -1; echo "exit codes: ${PIPESTATUS[@]}".

What to look for. The pipe moves data at a few GB/s: every byte is copied from the child into the kernel buffer and from there into the parent, in 64 KiB pipe-sized gulps with a context switch whenever the buffer fills or empties. Shared memory is typically several times faster, since the only cost is the writer's own copy into the mapped pages (plus first-touch page faults), and the reader sees the bytes with no transfer at all. With plain kill (SIGTERM), the program prints its shutdown message and exits cleanly; with kill -9, it dies instantly with no message, since SIGKILL cannot be caught. In step 3, PIPESTATUS shows 141 0: yes was killed by SIGPIPE (128 + 13) as soon as head exited.

Design: a local inference sidecar

A Python web service (8 worker processes) calls a GPU inference server running as a separate process on the same machine. Each request sends a 2 MB preprocessed tensor and receives a 4 KB result; the target is 2,000 requests per second with p99 under 20 ms. The first version uses HTTP over TCP to localhost with JSON-encoded tensors and reaches only 300 requests per second with high CPU in both processes. Design a better IPC scheme, estimate its data rates, and describe how you would handle a crash of either side and a graceful restart of the inference server.

Answer

Why the first version is slow. JSON-encoding 2 MB tensors inflates them several times and costs heavy CPU to encode and parse; HTTP over loopback TCP adds the network stack, and every byte is copied at least twice through the kernel. At 2,000 requests/s the raw payload is 4 GB/s before any encoding overhead, which a copy-and-encode design cannot sustain on a few cores.

Design. Separate control from data. Control: each web worker connects to the inference server over a Unix domain socket (lower overhead than TCP, permission-protected, and the server can check the caller with SO_PEERCRED). Data: at connection setup, the server creates a memfd shared-memory region per worker, for example a ring of 16 slots of 2 MB plus a header each (about 32 MB per worker, 256 MB total), and passes it with SCM_RIGHTS; both sides map it. A request: the worker writes the tensor in raw binary directly into a free slot (one 2 MB copy, or zero if preprocessing writes straight into the slot), then sends a tiny message on the socket: "slot 5, length, request id". The server reads the slot in place (or DMAs from it to the GPU, ideally from pinned memory), writes the 4 KB result into the slot's result area, and replies "slot 5 done" on the socket. Messages of a few bytes over a Unix socket cost a few microseconds; the socket also acts as the notification mechanism, so no extra eventfd is needed.

Rates. Data crosses memory once per request: 2,000 × 2 MB = 4 GB/s of writer-side memcpy, spread across 8 workers (about 0.5 GB/s each, a small fraction of one core each). Control traffic is about 4,000 small messages per second, negligible. Latency added by IPC is tens of microseconds, leaving the 20 ms budget to the model.

Failures. If the inference server crashes, workers see EOF or ECONNRESET on their sockets, fail in-flight requests (or retry against a restarted server), and reconnect, receiving new memfds; the old memory is freed automatically when the last mapping closes, so nothing leaks. If a worker crashes, the server sees its socket close and reclaims that worker's slots. Slot ownership is tracked by the protocol on the socket (never by locks inside shared memory), so a crash cannot leave a lock held. Graceful restart: the server handles SIGTERM by stopping acceptance of new requests, telling connected workers to pause (a control message), finishing in-flight slots, and exiting; the new server can be started first and listen on a new socket path (or receive the listening socket via descriptor passing) so workers reconnect without a gap. Size /dev/shm is irrelevant here because memfd does not use it, which avoids the container shared-memory limit.
