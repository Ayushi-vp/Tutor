Run docker run -it ubuntu bash and inside you appear to be on a different machine: your shell is PID 1, the host name is a random hex string, ls / shows a fresh Ubuntu file system, ip addr shows a single interface with an unfamiliar address, and you are root. Yet on the host, ps aux shows that same bash as an ordinary process with a PID in the thousands. There is no second kernel and no virtual hardware. Everything that makes it feel like a separate machine comes from a handful of kernel features applied to a normal process.

Understanding those features is what separates using containers from operating them. Why does a container with a 2 GB limit get killed when free inside it shows 200 GB available? Why does a Go service in Kubernetes get throttled although its CPU graph looks fine? Why can a container that mounts the Docker socket take over the host? Why does a container escape vulnerability in the kernel or runc affect every container on the machine? Why can rootless Podman run containers without being root at all? Each answer is one of four mechanisms: namespaces, cgroups, capabilities and seccomp.

These questions come up in infrastructure, platform, SRE and senior backend interviews ("what is a container, really?", "namespaces versus cgroups", "how do Kubernetes limits work under the hood?", "how would you run untrusted code safely?") and in incident reviews. The Kubernetes lesson (sc15) covered containers from the orchestration side; this lesson opens the kernel side.

We will take each mechanism in turn: the eight namespaces and how a container's view is assembled, the overlay file system for images, cgroups v2 and its controllers, capabilities, seccomp filters and security modules, then how they combine, where the boundary is weak, and what stronger sandboxes add.

Serviced apartments in one building

Imagine a building of serviced apartments, all sharing one foundation, one electrical system and one front desk (the kernel). Each tenant's apartment is set up so that it feels like a whole house. Four separate things make that work:

  • Walls and curtains decide what each tenant can see: their own rooms, their own door number, their own mailbox. That is namespaces, controlling visibility of processes, files, network, host name and user IDs.
  • Meters and fuses decide how much each apartment can draw: electricity, water, heating, with a breaker that trips if a tenant exceeds their allowance. That is cgroups, controlling CPU, memory, I/O and process count.
  • Keys: even a tenant who is "in charge" of their apartment gets only some keys, not the building's master key. That is capabilities, splitting root's powers so a process gets only what it needs.
  • A list of requests the front desk will accept from each apartment: they will deliver parcels but will not let a tenant rewire the building. That is seccomp, filtering which system calls a process may make.

The analogy shows the key weakness too. All tenants share one foundation and one front desk. If the front desk has a flaw that lets a cleverly worded request open any door, every apartment is exposed. In computing terms, all containers share one kernel, so a kernel bug reachable through a permitted system call can break isolation for everyone. Virtual machines are more like separate houses on separate foundations.

Who puts the layers together

No single kernel feature called "container" exists. A stack of user-space software assembles one from the pieces. At the bottom, a low-level runtime such as runc or crun reads a configuration file (the OCI runtime specification: which namespaces, which mounts, which cgroup limits, which capabilities, which seccomp profile) and makes the system calls. Above it, containerd or CRI-O pulls images, unpacks layers and manages container lifecycles; Docker and Podman add the familiar command line; and in a cluster, the kubelet translates pod specs into those configurations through the container runtime interface (CRI). Every Dockerfile option and pod field that touches security or resources (USER, --memory, securityContext, resources.limits) eventually becomes one of a few dozen kernel settings described in this lesson.

That also tells you where to look when something is wrong. If a container cannot see a file, think mount namespace and volumes. If it cannot reach a service, think network namespace and routing. If it is killed or slow, think cgroups. If a call fails with EPERM even as root, think capabilities, seccomp or the security module. Matching the symptom to the mechanism is most of the debugging, and the rest of this lesson gives you the details of each mechanism so you can do that matching quickly.

1. A container is a process with new namespaces

os2 showed that Linux creates every task with clone(), and that flags decide what the new task shares with its parent. A set of extra flags, CLONE_NEWNS, CLONE_NEWPID, CLONE_NEWNET, CLONE_NEWUTS, CLONE_NEWIPC, CLONE_NEWUSER, CLONE_NEWCGROUP and CLONE_NEWTIME (the last applies on the next fork), creates the child in new namespaces instead of its parent's. Three system calls manage them: clone() creates a process in new namespaces, unshare() moves the calling process into new ones, and setns() joins an existing namespace given a file descriptor for it. Every process's namespaces are visible as links in /proc/<pid>/ns/; two processes are in the same namespace exactly when the links point to the same inode number:

$ ls -l /proc/self/ns/
... cgroup -> 'cgroup:[4026531835]'
... mnt    -> 'mnt:[4026531841]'
... net    -> 'net:[4026531840]'
... pid    -> 'pid:[4026531836]'
... uts    -> 'uts:[4026531838]'   (also ipc, user, time)

Container runtimes such as runc and crun are, at their core, programs that call these system calls in the right order, set up the file system, cgroups and security settings, and then exec the container's entrypoint.

PID namespaces nest: a process has a PID in its own namespace and in every ancestor namespace. The container's shell may be PID 1 inside and PID 48213 on the host. The PID 1 inside inherits init's duties (os2): orphans in the namespace are reparented to it, signals with default actions are ignored unless it installs handlers, and when it exits the kernel kills every other process in the namespace.

Network namespaces start empty except for a down loopback interface. To connect one, the runtime (or a CNI plugin in Kubernetes) creates a veth pair, two virtual interfaces joined like the ends of a cable, moves one end into the container's namespace (renamed eth0) and attaches the other to a bridge or routing setup on the host, then configures addresses, routes and NAT. Each namespace has its own port space, which is why ten containers can all listen on port 80. A Kubernetes pod is a group of containers sharing one network namespace, so they reach each other over localhost.

Mount namespaces give the container its own mount table, and the runtime uses pivot_root to make the image's file system the root, so the host's files simply are not in its tree, except paths deliberately bind-mounted in (volumes).

User namespaces are the most powerful and subtle. They map ranges of user and group IDs: container UID 0 might map to host UID 100000, container UID 1000 to host 101000. Inside, the process is root with all capabilities, but only over resources owned by its user namespace (its own mount, network and other namespaces); toward the host it is an unprivileged user. That is what makes rootless containers (Podman, rootless Docker, and Kubernetes pods with hostUsers: false) possible.

You can build a rough container with one command on Linux or WSL:

$ sudo unshare --uts --ipc --net --pid --fork --mount-proc bash
# hostname sandbox; hostname        → sandbox (host unchanged)
# ps aux                            → only bash (PID 1) and ps
# ip link                           → only lo, and it is DOWN

3. The file system: image layers and OverlayFS

A container image is a stack of layers, each a tarball of files added or changed by one build step. Rather than copy them into one directory per container, runtimes stack them with OverlayFS: the image layers are read-only lower directories, each container gets a writable upper directory, and the merged view shows upper on top of lowers. Reading a file finds the topmost copy. Writing to a file from a lower layer triggers copy-up: the whole file is copied into the upper directory first, then modified. Deleting a lower file creates a whiteout marker in upper. So a hundred containers from one image share one copy of its files on disk and in the page cache (os10), and each container's changes cost only what it writes. Copy-up of large files on first write and the build-up of upper directories are the usual performance and disk-space surprises; databases and other write-heavy data belong in volumes, which bypass the overlay.

4. cgroups v2: limiting and accounting

Control groups organise processes into a tree, mounted at /sys/fs/cgroup, and attach controllers that account for and limit resources of everything in a subtree. cgroups v2, the unified hierarchy, is the default on current distributions and Kubernetes; v1 had a separate tree per controller, which made combined policies such as "throttle I/O caused by memory write-back of this group" impossible. Each cgroup is a directory; its interface is files:

ControllerKey filesMeaning
cpucpu.weight, cpu.maxRelative share under contention (default 100); hard quota per period (os3)
memorymemory.min, memory.low, memory.high, memory.maxProtected minimum; soft protection; throttle-and-reclaim threshold; hard limit with OOM kill (os9)
ioio.weight, io.maxRelative I/O share; bandwidth or IOPS caps per device
pidspids.maxMaximum number of tasks (processes and threads)

Each group also exposes accounting: cpu.stat (usage and throttling counts), memory.current and memory.stat (anonymous, file cache, kernel memory), memory.events (how often high and max were hit, OOM kills), io.stat, and pressure stall information (cpu.pressure, memory.pressure, io.pressure). Doing it by hand takes a few commands:

$ sudo mkdir /sys/fs/cgroup/demo
$ echo "50000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max     # half a CPU
$ echo 100M | sudo tee /sys/fs/cgroup/demo/memory.max
$ echo 64   | sudo tee /sys/fs/cgroup/demo/pids.max
$ echo $$   | sudo tee /sys/fs/cgroup/demo/cgroup.procs           # move this shell in
$ python3 -c "x = bytearray(300_000_000)"                            # → Killed
$ cat /sys/fs/cgroup/demo/memory.events                              # oom_kill 1

How Kubernetes uses it. The kubelet arranges a tree: kubepods.slice for all pods, split by quality-of-service class, then one cgroup per pod and per container. A container's CPU request becomes cpu.weight (proportional to millicores), so CPU is shared by request when the node is busy; a CPU limit becomes cpu.max, with the throttling behaviour from os3; a memory limit becomes memory.max, and exceeding it produces OOMKilled. systemd does the same for services on any Linux host: every unit is a cgroup, and CPUWeight=, MemoryMax=, TasksMax= in a unit file write these files.

5. Capabilities: root in pieces

Traditional Unix had two classes of process: root (UID 0), which bypasses every permission check, and everyone else. That is far too coarse: a web server that only needs to bind port 443 should not also be able to load kernel modules. Linux splits root's power into about forty capabilities. A few important ones:

CapabilityAllows
CAP_NET_BIND_SERVICEBinding to ports below 1024
CAP_NET_ADMINConfiguring interfaces, routes, firewall rules
CAP_NET_RAWRaw sockets (ping, packet crafting)
CAP_DAC_OVERRIDEBypassing file read/write/execute permission checks
CAP_CHOWN, CAP_SETUID, CAP_SETGIDChanging file owners; changing process user and group IDs
CAP_SYS_PTRACETracing and inspecting other processes' memory
CAP_SYS_MODULELoading kernel modules
CAP_SYS_ADMINMounting, many namespace and admin operations: so broad it is nearly root

Each thread has several capability sets: effective (checked by the kernel right now), permitted (the most it may enable), bounding (a ceiling that can only shrink, inherited by children) and others governing what survives execve. Executables can carry file capabilities (setcap cap_net_bind_service=+ep ./server), giving one binary one privilege without running it as root. And the no_new_privs flag ensures that nothing a process execs (setuid binaries, file capabilities) can ever gain more privilege than it has, which container runtimes set.

Docker's default keeps 14 relatively low-risk capabilities (CHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, SETGID, SETUID, SETPCAP, NET_BIND_SERVICE, NET_RAW, SYS_CHROOT, MKNOD, AUDIT_WRITE, SETFCAP) and drops the rest, so root in a default container cannot, for example, load modules, change the network configuration of the host or mount file systems. --privileged gives all capabilities back and more (see below). Kubernetes' "restricted" Pod Security Standard requires dropping all capabilities (adding back at most NET_BIND_SERVICE) and running as non-root.

6. seccomp: filtering system calls

Capabilities control privileged operations; they do nothing about the hundreds of unprivileged system calls every process may make, each of which is kernel code an attacker might find a bug in. seccomp (secure computing mode) closes that gap. A process installs a filter, a small program in classic BPF, that the kernel runs on every system call the process makes, looking at the call number and arguments and returning an action:

  • ALLOW: proceed normally.
  • ERRNO: fail the call with a chosen error (often EPERM), without running it.
  • KILL_PROCESS / KILL_THREAD, TRAP (send SIGSYS), LOG, or USER_NOTIF (ask a supervisor process to decide, used by some sandboxes).

Filters are inherited by children and can only be added to, never removed, so a sandboxed process cannot escape its filter. The original 2005 "strict" mode allowed only read, write, exit and sigreturn; the filter mode (seccomp-bpf, 2012) made it practical. Docker's and containerd's default profile allows the few hundred calls ordinary programs need and blocks several dozen dangerous or rarely needed ones, such as kexec_load (load a new kernel), init_module, keyctl and add_key (a historically buggy keyring interface), bpf, userfaultfd, mount without CAP_SYS_ADMIN, and the io_uring calls (os11). Kubernetes uses it when a pod sets seccompProfile: RuntimeDefault, which the restricted Pod Security Standard requires. Chrome's renderers, Android apps, systemd services (SystemCallFilter=) and OpenSSH's pre-authentication process use seccomp too.

7. Security modules and how it all combines

Linux Security Modules add mandatory access control on top: AppArmor (Ubuntu, Debian, SUSE) confines programs with path-based profiles, and SELinux (Red Hat, Android) labels every process and file and enforces a policy over the labels. Docker applies an AppArmor profile docker-default on Ubuntu; on Red Hat systems each container gets a unique SELinux category so that even two root containers cannot touch each other's files.

A container launch, then, applies all of it in a specific order: create namespaces; set up the overlay root, mounts and pivot_root; join the cgroup and apply limits; configure networking; drop capabilities and set no_new_privs; apply the LSM profile; install the seccomp filter (last, because setting things up needs calls the filter will block); switch to the container's user; and exec the entrypoint. --privileged skips most of this: all capabilities, no seccomp filter, no AppArmor confinement, and access to all host devices, which together make it nearly equivalent to running on the host as root.

For running other people's code (serverless functions, CI jobs from public repositories, notebooks from strangers, AI agents executing generated code), the shared kernel is too large a surface, and platforms add gVisor (Google Cloud Run's first generation, GKE Sandbox) or microVMs (AWS Lambda and Fargate on Firecracker, Kata Containers).

User namespaces: a security tool and an attack surface

User namespaces let unprivileged users become "root" over their own namespaces, which is exactly what rootless containers need. The catch is that a lot of kernel code that was written assuming only real root could reach it (file-system mounting code, netfilter configuration, many namespace-specific paths) becomes reachable by any local user who creates a user namespace with its own mount or network namespace. A long series of privilege-escalation bugs used this path, including CVE-2022-0185 in file-system context parsing. Distributions responded differently: some disabled unprivileged user namespaces by default for years (Debian historically, via a sysctl), and Ubuntu 23.10 and 24.04 restrict them with AppArmor so that only programs with a profile allowing it can create them. Container runtimes' default seccomp profiles also block unshare and clone with namespace flags inside containers. The trade-off is real: user namespaces make containers safer by removing host root, while making the kernel's exposed surface larger.

Escapes through the runtime

The runtime that sets up a container briefly runs on the host with full privileges, inside and around the container's namespaces, and bugs there are serious. In CVE-2019-5736, a malicious container image could overwrite the host's runc binary: when runc executed inside the container (for docker exec), the container could open /proc/self/exe, which pointed to the host binary, and write to it after runc exited, gaining code execution as root on the next runc invocation. The fix made runc execute from a sealed, read-only memfd copy of itself. In CVE-2024-21626 ("Leaky Vessels"), runc leaked a file descriptor referring to a host directory into the container process; setting the container's working directory to /proc/self/fd/7 gave the container a foothold in the host file system. Both show why runtimes must be patched as promptly as kernels, and why the setup phase is as security-critical as the steady state.

Memory accounting subtleties in cgroups

A cgroup's memory.current includes more than processes' heaps: page cache for files the group read or wrote, tmpfs files (including /dev/shm, os12), kernel memory such as socket buffers, dentries and inodes created on its behalf. That is why a container that only streams files through can hit its limit: its page cache counts until reclaimed. Reclaim within the group usually frees cache before any OOM kill, but a burst of dirty pages that cannot be written back fast enough, or memory pinned by the kernel, can still trigger OOMKilled with a modest heap. Page-cache pages are charged to the first group that touches them, so a shared file read first by one container is charged to it even when others use it. memory.stat breaks usage into anon, file, kernel, sock, shmem and more, and is the first file to read when a limit is hit unexpectedly.

Why /proc lies inside containers

Most of /proc and /sys reflects the whole machine, because the corresponding kernel data is not namespaced: /proc/meminfo, /proc/cpuinfo, /proc/stat, /proc/loadavg and sysconf(_SC_NPROCESSORS_ONLN) (unless a cpuset restricts CPUs). Programs that size themselves from these values in a container limited by cgroup quotas over-commit: a JVM sizing its heap as a quarter of 256 GB, a Go program running 64 scheduler threads under a 2-CPU quota (heavy throttling, os3), a Python process pool with 64 workers. Fixes are container-aware runtimes (modern JVMs; Go 1.25 made GOMAXPROCS respect CPU limits by default; libraries such as automaxprocs before that), explicit configuration from the downward API in Kubernetes, and LXCFS, a FUSE file system that serves cgroup-aware versions of those /proc files to containers.

Network namespace plumbing

A container's packets take a longer path than a host process's: from the container's eth0 across the veth pair into the host namespace, through a bridge or routing, through netfilter rules for NAT and Kubernetes service load balancing, and out of the physical interface. Each hop costs CPU, and the netfilter rules installed by kube-proxy in iptables mode grow linearly with the number of services, which is why large clusters moved to IPVS mode or eBPF-based data planes (Cilium), which replace rule lists with hash-table lookups attached to the interfaces. Pods with hostNetwork: true skip all of it by staying in the host's network namespace, trading isolation for performance and port conflicts.

Reading a container's cgroup when something goes wrong

Find the container's cgroup (cat /proc/<pid>/cgroup on the host gives the path under /sys/fs/cgroup; inside a container with a cgroup namespace it shows /) and read the files directly. For kills: memory.events (max and oom_kill counts) and memory.stat (what kind of memory). For slowness: cpu.stat (nr_throttled, throttled_usec, os3), memory.pressure and io.pressure (PSI shows whether the group is stalling on memory reclaim or I/O, often the hidden cause of latency under a memory limit set too tight), and io.stat. For fork failures: pids.current versus pids.max (os2). These files are the ground truth behind every container metric your monitoring system shows.

Hardening defaults that matter most

In rough order of value for typical services: run as a non-root user (USER in the Dockerfile, runAsNonRoot: true); never run privileged and never mount /var/run/docker.sock or sensitive host paths (os12); drop all capabilities and add back only what is needed (capabilities: drop: ["ALL"]); set allowPrivilegeEscalation: false (which sets no_new_privs); use seccompProfile: RuntimeDefault; make the root file system read-only and mount writable volumes only where needed; and enforce these with Pod Security Admission or a policy engine. Where available, enable user namespaces for pods (hostUsers: false) so container root maps to an unprivileged host user. Keep kernels and runtimes (runc, containerd, CRI-O) patched, since they are the boundary.

Debugging inside namespaces

Minimal images often lack shells and tools. From the host, nsenter -t <pid> -n runs host tools such as ss, tcpdump and ip inside the container's network namespace only, keeping the host's file system and binaries, which is often the most useful combination. nsenter -t <pid> -a joins all namespaces. In Kubernetes, kubectl debug -it <pod> --image=busybox --target=<container> adds an ephemeral container sharing the target's process namespace, and kubectl debug node/<name> gives a privileged shell on the node. Tools like perf and eBPF profilers (os14) run on the host and see container processes directly, since they are host processes; only symbol resolution needs access to the container's file system (/proc/<pid>/root).

Noisy neighbours that cgroups do not stop

cgroups divide CPU time, memory, block I/O and tasks, but not everything that is shared. Last-level CPU cache and memory bandwidth are shared by all cores (Intel RDT can partition them on supporting hardware); the kernel's own locks, page allocator and network softirq processing are shared; inodes, file descriptors (system-wide limits), conntrack table entries and ephemeral ports are node-wide. A pod opening millions of connections can exhaust the node's conntrack table and break networking for everyone; a pod creating millions of tiny files can exhaust inodes on the node's container storage (os10). Monitoring at node level, not just per pod, is necessary for these.

Version and configuration drift

Behaviour differs between cgroup v1 and v2 hosts (file names, memory accounting, PSI availability), between kernels (EEVDF since 6.6, os3; time namespaces since 5.6), between runtimes (runc versus crun versus gVisor's runsc), and between seccomp profile versions (a new runtime release may start blocking a call your application uses, surfacing as unexpected EPERM). When a container behaves differently on two nodes, compare kernel version, cgroup version (stat -fc %T /sys/fs/cgroup prints cgroup2fs for v2), runtime and profile first.

Build a container from kernel primitives and watch a cgroup kill a process. Linux or WSL 2 with root (sudo); WSL 2 on recent Windows uses cgroups v2.

  1. Namespaces with unshare: 
    sudo unshare --uts --ipc --net --pid --fork --mount-proc bash
hostname sandbox && hostname     # new host name, host unaffected
echo $$                           # 1: this shell is PID 1
ps aux                            # only processes in this PID namespace
ip link                           # only a DOWN loopback interface
readlink /proc/self/ns/pid /proc/self/ns/net
exit
    Compare the readlink output with the same command run outside.
  2. A memory-limited cgroup (as root; if memory.max does not appear in the new directory, first run echo "+memory +pids +cpu" > /sys/fs/cgroup/cgroup.subtree_control to enable those controllers for children): 
    cd /sys/fs/cgroup && mkdir demo && cd demo
echo 100M > memory.max; echo 0 > memory.swap.max; echo 32 > pids.max
echo $$ > cgroup.procs            # move this shell into the cgroup
python3 -c "b = bytearray(50_000_000); print('50 MB ok')"
python3 -c "b = bytearray(300_000_000); print('300 MB ok')"
cat memory.events memory.peak
python3 -c "import os; [os.fork() or __import__('time').sleep(30) for _ in range(40)]"
  3. Capabilities: grep Cap /proc/self/status, then capsh --decode=<CapEff value> as a normal user and as root, and (if Docker is installed) inside docker run --rm alpine grep Cap /proc/self/status.
  4. Clean up: open a new shell, echo <demo shell PID> > /sys/fs/cgroup/cgroup.procs or exit it, then rmdir /sys/fs/cgroup/demo.

What to look for. In step 1 the shell is PID 1, sees only its own processes, has only a loopback interface, and its namespace links show different inode numbers from the host's: a container without an image. In step 2, the 50 MB allocation succeeds and the 300 MB one is "Killed": memory.events shows oom_kill 1 and memory.peak is about 100 MB, the limit. The fork loop fails with BlockingIOError: [Errno 11] once the cgroup reaches 32 tasks: the pids controller at work (os2). In step 3, a normal user's effective set is empty, root's decodes to every capability, and a default Docker container's is a much shorter list (the 14 defaults).

Review: a pod spec for running user-submitted code

Your team is launching a feature that runs short Python scripts written by customers (data transformations) inside the company's Kubernetes cluster. A first draft creates one pod per job with this container spec: image python:3.12, securityContext: {privileged: true} "because some scripts needed to install system packages", no resource limits "to keep scripts fast", the job's input data mounted from a host path, and the cluster's default service-account token mounted. Review it as a security and reliability reviewer: list the risks in terms of this lesson's mechanisms and propose a design.

Answer

Risks. (1) privileged: true gives all capabilities (including CAP_SYS_ADMIN and CAP_SYS_MODULE), no seccomp filter, no AppArmor confinement and access to host devices: a customer script can mount the host's disk, load a kernel module or otherwise take over the node, and with it every other tenant's pods on that node. (2) Even unprivileged, root in a container shares the host kernel; untrusted code calling obscure system calls is exactly the scenario where a kernel bug becomes an escape. (3) No limits: a script can allocate all node memory (OOM-killing other pods, os9), burn every CPU, fork-bomb the node's PID space (os2) or fill the disk; the only cgroup protection left is whatever the QoS class gives. (4) A hostPath mount gives direct access to the node's file system, and if writable, to other jobs' data or system files. (5) The service-account token lets the script call the Kubernetes API with the pod's permissions, possibly listing secrets or creating pods. (6) No network restrictions: scripts can reach internal services and the cloud metadata endpoint, which can hand out node credentials.

Design. Treat customer code as hostile. Run jobs in a sandboxed runtime, gVisor (runtimeClassName: gvisor) or Kata/Firecracker microVMs, on a dedicated node pool with taints so only these jobs land there. In the pod: run as a non-root user, allowPrivilegeEscalation: false, drop all capabilities, seccompProfile: RuntimeDefault (gVisor adds its own), read-only root file system with a small emptyDir for scratch, and hostUsers: false if supported. Set requests and limits for CPU and memory, a pod PID limit and ephemeral-storage limits, plus a hard job timeout (activeDeadlineSeconds). Do not mount host paths; deliver input through an object-store download with short-lived, job-scoped credentials. Disable the service-account token (automountServiceAccountToken: false). Apply a NetworkPolicy denying all egress except the object store, and block the metadata endpoint. Preinstall common packages in a curated image instead of allowing system package installation. Finally, enforce all of this with an admission policy so a later change cannot quietly reintroduce privileged.
