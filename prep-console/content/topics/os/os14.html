It is 3 a.m. and the alert says p99 latency for the checkout service has tripled. You log in to one of the hosts. What now? The tempting move is to open whatever tool you happen to know, see a number that looks big, decide that must be the cause, and start changing things. Experienced engineers have a name for that: the "streetlight effect", looking for your keys under the streetlight because that is where the light is. It wastes the critical first hour and often makes things worse.

Linux gives you remarkable visibility. Every topic in this track has counters exposed through /proc and /sys: context switches (os1), process states (os2), run queues and throttling (os3), lock contention via futex calls (os4), page faults and reclaim (os8), allocator and OOM events (os9), dirty pages and fsync (os10), device latency and interrupts (os11), cgroup pressure (os13). Tools such as vmstat, iostat, perf and eBPF read and correlate them. The skill is knowing which question to ask first, what each number really means, and how to get from "the host is slow" to "this lock in this function, caused by this change" in minutes.

This is a favourite area for senior, SRE and infrastructure interviews: "a server is slow, walk me through it", "what does load average mean?", "how does strace work and why not use it in production?", "how would you find where CPU time goes in a Python service?", "what is eBPF?". Strong answers show a method, not a list of commands.

This lesson starts with methods (the USE method and the 60-second checklist), teaches you to read the standard tools correctly, including the classic misreadings, then goes deeper with strace, perf and flame graphs, on-CPU versus off-CPU analysis, and eBPF, before turning to how teams make the next incident easy to diagnose.

A doctor's method, not a box of instruments

A good doctor seeing a patient who "feels unwell" does not order an MRI first. They take the vital signs (temperature, pulse, blood pressure, oxygen), ask a few targeted questions, and only then order the specific test that the vitals point to. The order matters because each step narrows the search and keeps you from chasing whatever happens to look abnormal on an expensive scan.

Performance debugging works the same way. The vital signs are a handful of numbers per resource; the targeted tests are tracing and profiling tools. Two methods structure the first step:

  • The USE method (Brendan Gregg): for every resource, check utilisation (how busy), saturation (how much work is queued waiting for it) and errors. Resources are the physical ones (CPUs, memory, disks, network interfaces) and the software ones (thread pools, connection pools, locks, file descriptors).
  • The RED method for services: rate of requests, errors, and duration (latency distribution). RED tells you a service is unhappy; USE tells you which resource underneath is the problem.

Two kinds of measurement

The tools fall into two families. Counters and sampling are cheap: the kernel keeps running totals (CPU time per state, bytes per disk, context switches) and tools like vmstat print the change each second; profilers interrupt each CPU 99 times a second and record what is running. Tracing records individual events: every system call, every disk request, every scheduler switch. Tracing tells you exactly what happened but can cost a lot if events are frequent, so the art is to start with counters, narrow down to a resource and a process, and only then trace, with filters, for a short time. eBPF changed the economics of that last step by summarising events inside the kernel.

Questions before tools

Before running anything, it pays to pin down the symptom, because the right first tool depends on it. Is the problem throughput (we cannot handle the load) or latency (each request is slow), and is the latency in the median or only the tail? Is it on every host or only some, and did it start at a particular moment? What changed around then: a deploy, a configuration change, a traffic shift, a kernel update, a noisy neighbour? A latency problem on one host since 14:05 suggests a local resource or a co-located job; a gradual fleet-wide throughput decline suggests a code or data change. Brendan Gregg's "problem statement" questions, and the habit of writing the answers down at the start of an incident, prevent a large share of wasted effort.

The rest of the lesson follows that funnel: the 60-second checklist with counters, reading each tool's output correctly, then tracing and profiling tools for the deep dive.

1. The first 60 seconds

Netflix's performance team published a checklist for the first minute on a misbehaving Linux host. Each command is cheap and available almost everywhere (most come from the procps and sysstat packages):

uptime                 # load averages: rising, falling, stable?
dmesg -T | tail        # OOM kills, I/O errors, hung tasks, TCP drops
vmstat 1               # run queue, blocked, memory, swap, I/O, CPU split
mpstat -P ALL 1        # per-CPU: one hot CPU? softirq? steal?
pidstat 1              # which processes use CPU (also -d disk, -r memory, -w switches)
iostat -xz 1           # per-device IOPS, throughput, latency, queue depth
free -m                # memory, buffers/cache, available
sar -n DEV 1           # network throughput per interface
sar -n TCP,ETCP 1      # TCP connections per second, retransmits
top                    # overview; check it agrees with the above

The point is breadth: in about a minute you have touched every resource in the USE grid and usually know which one to investigate.

2. Load average, read correctly

uptime prints three load averages, over 1, 5 and 15 minutes. On Linux, load counts tasks that are runnable (running or waiting in a run queue, os3) plus tasks in uninterruptible sleep (state D, usually waiting on disk or network file systems, os2), exponentially smoothed. Comparing the 1-minute value to the 15-minute value tells you the trend: 12.1, 6.3, 2.0 means the problem started within the last few minutes. Comparing to the core count tells you magnitude, with the caveat that D-state tasks inflate it without using CPU. Linux includes them deliberately, as a measure of demand on the whole system rather than the CPUs alone, but it means load is a prompt to look further, never a diagnosis.

3. vmstat: one line per second for the whole machine

Read it column group by column group. r (runnable tasks) is 14-15; on an 8-core machine that means about 7 tasks waiting for a CPU at any moment: CPU saturation. b (blocked in uninterruptible sleep) is 0, so it is not storage. free is low, but cache is large, which is normal (os8); si and so (swap in and out, in KB/s) are 0, so no memory pressure. bi/bo (blocks in/out) are small. in and cs (interrupts and context switches per second) are moderate. CPU: us 88%, sy 10%, almost no idle, no iowait (wa), no steal (st). Conclusion: a CPU-bound host with more runnable work than cores; next, find which process (pidstat) and which code (perf). The first line of vmstat output shows averages since boot; ignore it.

Inside containers, also check the cgroup's throttling counters (os3, os13): a container can be starved while the host looks idle.

5. Processes and threads: pidstat and top

pidstat 1 prints per-process CPU split into user and system each second, unlike top's rolling snapshot, which makes trends visible. Its other modes complete the picture: -d for disk read/write per process, -r for memory and page faults (majflt/s is the important one, os8), -w for voluntary and involuntary context switches (os1, os3), and -t for per-thread figures. In top, press 1 for per-CPU lines, H for threads, P/M to sort by CPU or memory; read RES (resident memory, including shared pages), not VIRT (address space, os7), and note processes in state D.

6. Memory: available, pressure and faults

free -m's available column (from MemAvailable in /proc/meminfo) estimates how much memory can be used without swapping, counting reclaimable cache; "free" is meaningless on Linux because the kernel deliberately fills spare RAM with cache. Real memory trouble shows as saturation: swap activity (si/so), major faults (sar -B, pidstat -r), direct reclaim (allocstall in /proc/vmstat), and PSI: cat /proc/pressure/memory gives the share of time some or all tasks were stalled on memory over 10, 60 and 300 seconds. Errors are OOM kills, found in dmesg or the cgroup's memory.events (os9).

7. Disks: iostat

Device   r/s    w/s   rkB/s   wkB/s  r_await w_await aqu-sz  %util
nvme0n1  4210   120   67360   1920     0.21    0.40   0.92   61.0
sdb        85    310    1360  39680    12.40   48.70  16.80  100.0

The NVMe drive does 4,210 reads per second at 0.21 ms average with less than one request queued: healthy, and the 61% %util is meaningless for a device that serves many requests in parallel (os11). The sdb device is in trouble: a write latency of 48.7 ms, an average queue of 16.8 requests and 100% busy, consistent with a spinning disk or a throttled cloud volume being flooded with writes. The questions then are who is writing (pidstat -d, iotop, biosnoop) and whether reads are suffering behind them (os10's write-back stalls). -x gives extended columns and -z hides idle devices.

8. Network: throughput, drops and retransmits

sar -n DEV 1 shows packets and kilobytes per second per interface; compare with the link speed for utilisation. Saturation and errors live elsewhere: ip -s link (errors, drops), nstat or sar -n ETCP 1 (TCP retransmits per second, which net-track topics explain as the main sign of loss or congestion), ss -s (socket counts by state) and ss -tin (per-connection details such as RTT, congestion window and retransmits). Accept-queue overflows (ListenOverflows in nstat) mean an application is not accepting connections fast enough (net13).

9. strace: every system call, at a price

Once you know which process, strace shows what it is asking the kernel to do:

strace -c -f -p 4321          # summary table: calls, errors, time, per syscall (Ctrl+C to stop)
strace -f -T -e trace=network,openat -p 4321   # selected calls with time spent in each
strace -f -tt -o trace.txt ./app               # full timestamped trace of a new process

It answers questions like "which config file is it failing to open?" (openat returning ENOENT), "what is it waiting on?" (a read on fd 7 that takes 3 seconds; ls -l /proc/4321/fd/7 shows it is a socket to the database), and "why is system time high?" (300,000 futex calls per second: lock contention, os4). The price: strace uses ptrace, so the kernel stops the traced thread at every system-call entry and exit and switches to strace to decode it. A process making 100,000 calls per second can slow by an order of magnitude or more. In production, prefer perf trace -s -p PID or the eBPF tools in section 12, which count in the kernel without stopping the process.

10. perf: sampling profiles and flame graphs

perf is the Linux profiler, built on the kernel's perf_events subsystem. Its most used mode is sampling:

perf top                                   # live view of the hottest functions, system-wide
perf record -F 99 -g -p 4321 -- sleep 30   # sample stacks 99 times/s per CPU for 30 s
perf report --stdio                        # text report, hottest stacks first
perf script | stackcollapse-perf.pl | flamegraph.pl > cpu.svg   # flame graph

On each sample (a timer interrupt, os1), the kernel records the running process, the instruction pointer and, with -g, the call stack. 99 Hz rather than 100 avoids sampling in lockstep with periodic activity. Thirty seconds on 8 CPUs gives about 24,000 samples, enough to find anything using more than a percent of CPU. The overhead at this rate is small, a fraction of a percent.

Two practical obstacles cause most broken profiles. Stack walking: the cheap method follows the chain of frame pointers, which compilers often omit for speed (-fomit-frame-pointer), producing truncated stacks; Fedora (38+) and Ubuntu (24.04+) now build their packages with frame pointers for this reason, and --call-graph dwarf or Intel's LBR are alternatives. Symbols: stripped binaries show raw addresses, and JIT-compiled code (Java, Node.js, .NET) has no symbols on disk unless the runtime writes a /tmp/perf-<pid>.map file. Interpreted languages show the interpreter's C functions rather than your code, which is why language-aware profilers exist: py-spy for Python (reads the interpreter's memory from outside, no restart needed), async-profiler for the JVM, and the runtimes' built-in profilers (Go's pprof). Python 3.12+ can also emit perf map entries with -X perf.

perf stat counts instead of sampling: perf stat -p 4321 -- sleep 10 reports cycles, instructions, IPC, branch misses, context switches, page faults and CPU migrations, and -e selects specific hardware events such as cache or TLB misses (os7).

11. On-CPU versus off-CPU

A CPU profile only sees threads that are running. A request that takes 200 ms might spend 5 ms on CPU and 195 ms waiting: for a lock (os4), a disk read (os11), a downstream service, or a CPU (run-queue delay or throttling, os3). Off-CPU analysis records, every time a thread is switched out, the stack where it blocked and, when it runs again, how long it was off-CPU. Aggregated into an off-CPU flame graph (bcc's offcputime), it shows where waiting time goes. Together, on-CPU and off-CPU views account for all of a thread's time. For quick checks without tooling, thread dumps work too: a few py-spy dump, jstack or gdb -batch -ex "thread apply all bt" snapshots a few seconds apart reveal where threads are consistently stuck.

12. eBPF: safe programs inside the kernel

eBPF lets you load small programs into the running kernel and attach them to events: kprobes (entry or return of almost any kernel function), tracepoints (stable, named events such as block:block_rq_complete or sched:sched_switch), uprobes (functions in user programs and libraries), perf events and network hooks. Before loading, the kernel's verifier checks that the program always terminates, only reads memory it is allowed to, and stays within size limits, so a tracing program cannot crash or hang the kernel. Programs store results in maps (hash tables, arrays, histograms) in kernel memory, and user space reads only the summaries. Instead of shipping a million events to user space and counting them there, the kernel increments a histogram bucket per event, which is why eBPF tools can run in production.

The bcc collection has ready-made tools for most questions in this track:

13. Putting it together: a worked investigation

Symptom: an API's p99 latency doubled at 14:05; average CPU looks normal. uptime: load 3.1, 2.8, 1.2 on 16 cores: rising but not alarming. dmesg: nothing. vmstat: r around 2, b around 0, no swapping, us 25%, sy 5%. mpstat: all CPUs similar. iostat: the data volume's r_await jumped from 0.3 ms to 9 ms, with w/s up tenfold since 14:05. pidstat -d: a newly deployed log-compaction job is writing 400 MB/s. Hypothesis: the job's writes saturate the volume (a cloud disk with a throughput cap), and the API's reads queue behind them. Confirm with biolatency -D (read latency distribution bimodal since 14:05) and biosnoop (large writes from the job). Fix: rate-limit the job with a cgroup io.max or move it to another volume (os13); verify that r_await and p99 return to baseline. Total time: about ten minutes, with no guessing.

Why sampling works, and when it misleads

A sampling profiler is a statistical estimate: with N samples, a function that truly uses a fraction p of CPU appears in about pN of them, with relative error shrinking as 1/√(pN). At 99 Hz on 8 CPUs for 30 seconds, a function using 1% of CPU appears in about 240 samples, an estimate within roughly ±13%: good enough to rank hotspots. Sampling misleads in specific ways: very short-lived processes may never be sampled (use execsnoop); periodic work aligned with the sampling frequency is over- or under-counted (hence 99 rather than 100 Hz); and a sample attributes time to whatever instruction is retiring, which with out-of-order execution can be a few instructions after the one that stalled (skid), so line-level attribution needs care or precise events (PEBS on Intel).

Instructions per cycle and top-down analysis

Knowing where CPU goes leaves the question why that code is slow. Hardware counters answer it. perf stat reports instructions per cycle (IPC): modern cores can retire four or more instructions per cycle, so an IPC of 0.3 on a hot loop means the core is mostly stalled, typically on cache misses (each DRAM access costs about 100 ns, hundreds of cycles); an IPC near 3 means the code is running efficiently and only doing less work will help. Intel's top-down microarchitecture analysis (perf stat --topdown, or toplev) splits pipeline slots into front-end bound (instruction fetch, often large code or i-cache/iTLB misses), bad speculation (branch mispredictions), back-end bound (memory or execution units) and retiring (useful work). The category tells you whether to fix data layout, branches, code size or the algorithm.

Continuous profiling

Profiling during an incident has a flaw: you see the problem but not the baseline. Google described Google-Wide Profiling in 2010, sampling stacks across the whole fleet at low frequency continuously; today eBPF-based open-source profilers (Parca, Grafana Pyroscope, the OpenTelemetry eBPF profiler donated by Elastic) do the same for any Linux host, with overhead around 1% or less. With weeks of profiles stored, you can diff flame graphs before and after a deploy, find which functions grew the fleet's CPU bill, and see what was running during an incident that is already over. Teams that adopt it often find several percent of fleet CPU in surprising places (logging, serialisation, regular-expression compilation) within days.

Why eBPF is safe enough for production, and its limits

The verifier walks every possible path of a program before loading it: it rejects unbounded loops (bounded loops are allowed since 5.3), out-of-bounds memory access, uninitialised reads and calls to non-permitted helpers. Programs run to completion without sleeping in most contexts, and the kernel can attach and detach them atomically. The remaining costs are real but bounded: each probe adds tens to hundreds of nanoseconds to the event it instruments, so attaching to a function called millions of times per second (every malloc, every packet) is noticeable; kprobes on internal kernel functions can break across kernel versions since those functions are not a stable interface (tracepoints are); and uprobes trap into the kernel on each hit, costing around a microsecond. Choosing the cheapest stable event that answers the question is part of the craft.

Tracing distributed requests

Host tools stop at the machine boundary. When a request crosses many services, the slow part may be three hops away, and every host involved can look healthy. Distributed tracing (OpenTelemetry, with backends such as Jaeger or Tempo) propagates a trace ID through each call and records timed spans, so a single slow request can be broken down service by service. The two views complement each other: tracing tells you which service and which operation is slow; the tools in this lesson tell you why on that service's host, whether CPU, a lock, the disk or the scheduler.

Debugging after the fact: core dumps and kernel evidence

Some problems leave only remains. A crashed process can leave a core dump, a snapshot of its memory and registers that gdb or coredumpctl debug can examine as if the process had just stopped; enable it with ulimit -c unlimited or, on systemd hosts, systemd-coredump, which stores and compresses dumps and lists them with coredumpctl list. Containers complicate this, since the core pattern is set host-wide. The kernel's own evidence lives in its log: OOM-kill reports with a memory table (os9), "task blocked for more than 120 seconds" from the hung-task detector with the stuck stack (os2), soft-lockup warnings when a CPU is stuck in kernel code, and I/O errors. For kernel crashes, kdump boots a small capture kernel to save the crashed kernel's memory for analysis with the crash tool.

Mistakes that waste incidents

The recurring ones: tuning before measuring (raising a thread pool, adding replicas, changing GC settings because they worked last time); trusting averages (average latency hides the tail, average CPU hides one saturated core or bursts of throttling); reading %util on SSDs and %iowait as saturation; reading "free memory" instead of "available"; running heavy tracing (strace on a busy process, tcpdump without filters, debug logging) on an already struggling host, turning a slowdown into an outage; and looking only at the application's host while the cause is a dependency, a noisy neighbour, or the hypervisor (steal time).

Containers and Kubernetes

Host tools see container processes directly, because they are host processes (os13), but numbers need care. A container's CPU and memory are bounded by its cgroup, not the host, so check cpu.stat throttling and memory.events along with host metrics. Tools run inside a container may report host-wide figures from /proc. Profiling requires privileges: perf and eBPF need CAP_PERFMON/CAP_BPF or root, and kernel.perf_event_paranoid (2 by default upstream; some distributions set it higher) restricts unprivileged use, so the usual approach is to profile from the node (a privileged debug pod or DaemonSet) and resolve symbols through /proc/<pid>/root. Language profilers that attach from outside (py-spy, async-profiler) need CAP_SYS_PTRACE in the same PID namespace, which kubectl debug --target can provide.

Make the next incident easy

Most of the time saved in incidents is earned beforehand. Export USE metrics per host and per cgroup (CPU and throttling, memory and PSI, disk latency and queue, network errors and retransmits) and RED metrics per service, with percentiles, not just averages. Run a continuous profiler. Build with frame pointers and keep debug symbols in a symbol server so profiles and core dumps resolve. Preinstall sysstat, perf, bpftrace and bcc tools on hosts or in a debug image, and enable sysstat's collector so sar can answer "what was the disk doing at 03:12 last night?". Keep a runbook with the 60-second checklist and the questions for each resource. Record kernel, runtime and configuration versions, since "what changed?" is the most productive question in any incident.

A real-world pattern: the slow DNS lookup that looked like CPU

A frequently reported pattern in Kubernetes: intermittent 5-second latency spikes on outbound requests, with no CPU or network saturation. CPU profiles show nothing; off-CPU analysis or strace -T shows threads blocked in getaddrinfo or poll on a DNS socket for exactly five seconds, the resolver's default timeout. The cause was a race in the kernel's connection tracking when two UDP DNS queries (A and AAAA) from one socket were sent simultaneously through NAT, causing one to be dropped; the client waited out the timeout and retried. Weave Works and others documented it publicly in 2018, and fixes ranged from resolver options (single-request-reopen) to node-local DNS caches. The lesson for method: latency without CPU is waiting; find what is waited on, and suspicious round numbers (exactly 5 s, 1 s, 200 ms) usually point to a timeout or retry somewhere.

Practise the checklist on load you create yourself, then profile it. Linux or WSL 2; install tools with sudo apt install sysstat linux-tools-common linux-tools-$(uname -r) (on WSL, perf may need the WSL kernel's tools package) and pip install py-spy.

  1. Save as load.py and start it in one terminal with python3 load.py: 
    import hashlib, os, threading, time
def cpu():                                     # CPU hog: hashing
    while True: hashlib.sha256(os.urandom(4096)).digest()
def disk():                                    # disk writer with fsync
    with open("junk.bin", "wb") as f:
        while True:
            if f.tell() > 256 << 20: f.seek(0)  # cap the file at 256 MB
            f.write(os.urandom(1 << 20)); f.flush(); os.fsync(f.fileno())
def sleepy():                                  # off-CPU waiting
    while True: time.sleep(0.01)
for fn in (cpu, cpu, disk, sleepy): threading.Thread(target=fn, daemon=True).start()
print("pid", os.getpid()); time.sleep(600)
  2. In another terminal, run the checklist for about ten seconds each: uptime; vmstat 1 5; mpstat -P ALL 1 3; pidstat -u -d -w -p <pid> 1 5; iostat -xz 1 3; free -m.
  3. Profile it: sudo py-spy top --pid <pid>, then sudo py-spy record -o load.svg --pid <pid> --duration 15 and open the SVG in a browser. Optionally sudo perf top -p <pid>.
  4. Count its system calls cheaply versus with strace: sudo perf trace -s -p <pid> -- sleep 5, then sudo strace -c -f -p <pid> for 5 seconds (Ctrl+C).
  5. Delete junk.bin when done.

What to look for. vmstat shows r around 1-2 (two hashing threads, but the GIL lets only about one run Python at a time, py8), noticeable bo from the writer, and some wa. iostat shows steady writes with latency dominated by the fsyncs. pidstat -w shows many voluntary context switches (sleeps and fsync waits) for the process. py-spy's flame graph puts most CPU in cpu/sha256/urandom, some in disk/write, and almost nothing in sleepy, although that thread exists all the time: it is off-CPU, which is the point of section 11 (py-spy's --idle flag shows it). perf trace -s summarises system calls with little slowdown, while strace's summary arrives with a visible drop in the process's throughput.

Diagnose: half a fleet is slow after a routine change

After a Tuesday maintenance window, 50% of the hosts running a Java pricing service show p99 latency of 300 ms instead of 80 ms; the other half are fine. All hosts run the same container image and receive the same traffic share. The maintenance included a kernel update on some hosts and a move of some hosts to a new instance type. On a slow host: load 6.2 on 16 vCPUs, vmstat shows r ≈ 6, us 35%, sy 18%, st 9%; on a fast host: us 30%, sy 6%, st 0%. Describe your investigation step by step and what each finding would mean, then give the most likely causes and how you would confirm and fix them.

Answer

Frame it. Same image and traffic, half the hosts slow: the difference is the host, not the code. First establish which hosts are slow and correlate with the two changes: are the slow ones the new kernel, the new instance type, or both? That single correlation usually halves the search.

Read the vitals. Compared with a fast host, the slow one has more system time (18% versus 6%) and steal (9% versus 0%). Run queue 6 on 16 vCPUs is not CPU saturation by itself. Steal means the hypervisor is not giving these vCPUs their time: an oversubscribed or burstable instance type, or noisy neighbours. Higher sy means more kernel work per request: more or costlier system calls, page faults or locking.

Dig into sy. Compare system-call profiles on a slow and a fast host with perf trace -s or syscount. If the counts are similar but each call costs more, suspect kernel entry cost: a new kernel or microcode enabling extra CPU-vulnerability mitigations (check /sys/devices/system/cpu/vulnerabilities/, os1), or a clock source change. Check cat /sys/devices/system/clocksource/clocksource0/current_clocksource: if the new instance type uses a clock source that cannot be read through the vDSO (os1's EC2 story), every System.nanoTime() and currentTimeMillis(), which Java services call constantly for metrics and timeouts, becomes a real system call. A perf flame graph would show time in clock_gettime kernel paths. If instead futex calls jumped, look at lock contention changes; if page faults rose, compare transparent huge page settings between kernels (os7).

Dig into steal. Steal of 9% directly delays threads; check the instance type's CPU model and whether it is a burstable class out of credits, and compare perf stat IPC across hosts in case the new type has a slower CPU or smaller caches.

Confirm and fix. The most likely combination: the new instance type has a different clock source (and possibly steal from oversubscription), and/or the new kernel enables more expensive mitigations. Confirm by moving one slow host's clock source to tsc if the platform supports it reliably (or setting it in the image), and measuring sy and p99; and by comparing the same kernel on both instance types. Fix by standardising the clock source and instance type, rolling back or reconfiguring the kernel if mitigations are the cause (never by disabling mitigations on shared hardware without a security review), and adding st, sy and clock-source checks to the host health dashboard so the next mixed rollout is caught in canary.
