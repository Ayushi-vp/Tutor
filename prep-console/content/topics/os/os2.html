You type python train.py into a terminal. A moment later there are two new things on your machine: a Python interpreter running your script, and, behind the scenes, a record inside the kernel that tracks everything about it: which memory it owns, which files it has open, how much CPU it has used, who started it. When the script starts a data-loader with eight worker processes, eight more such records appear. When you press Ctrl+C, the kernel uses those records to deliver the interrupt, tear everything down and tell your shell how the program ended.

Most engineers live happily without thinking about this until something goes wrong in a way that only makes sense in terms of processes. A container takes the full 10 seconds to stop every time you deploy. A server slowly fills up with entries marked <defunct>. A machine with free memory refuses to start any new program with "Resource temporarily unavailable". A Python program that uses both threads and multiprocessing hangs forever, but only on Linux. Each of these is a lifecycle bug: something about how processes are created, how they end, or how threads and processes interact.

Interviewers love this area for the same reason. "What is the difference between a process and a thread?" is one of the most common OS questions in any loop, and "what is a zombie?" and "explain fork and exec" follow close behind. A senior candidate is expected to go further: explain why fork and exec are separate, why containers need an init process, and why forking a multithreaded program is dangerous.

This lesson builds the picture from the bottom up: what a process is to the kernel, the states it moves through, how fork, exec and wait create and reap processes, what zombies and orphans really are, and how threads fit in, including how Linux implements both with a single mechanism.

A recipe versus a kitchen in use

A program is like a recipe in a book: a fixed set of instructions and ingredients, sitting on a shelf. A process is a kitchen actively cooking that recipe: a bench with ingredients laid out, pans on the stove, a cook partway through step 7, and a note of which step comes next. You can have three kitchens cooking the same recipe at once, each at a different step with its own mess. The threads are the cooks. A kitchen can have one cook or several; all cooks in one kitchen share the bench and the ingredients (and can bump into each other), while each cook keeps their own place in the recipe.

The analogy is useful but breaks in one place: kitchens in different processes are walled off completely. A cook in one kitchen cannot even see the next kitchen's bench, because the kernel gives each process its own address space, its own private view of memory (os7 explains the mechanism).

What the kernel keeps for each process

For each process the kernel keeps a record called the process control block (PCB). On Linux it is a structure named task_struct, a few kilobytes containing or pointing to: the process ID (PID) and parent's PID; the state (running, sleeping, and so on); the saved registers for when it is not on a CPU; the memory map; the table of open file descriptors (small integers like 0, 1, 2 for stdin, stdout and stderr); the user and group it runs as; signal handlers; and scheduling data such as priority and CPU time used. When the kernel context-switches (os1), it is saving into and loading from these records.

The life of a process in four calls

On Unix-like systems, almost every process is born and dies through four system calls:

  • fork(): make a copy of me. The new child process is nearly identical to its parent, including memory contents and open files.
  • exec(): replace my program with another one. Same process, same PID, new code.
  • exit(): I'm done, here is my exit status (0 for success).
  • wait(): parent says "tell me when a child finishes and how".

When you type ls, your shell forks; the child execs /bin/ls; ls prints and exits; and the shell, which was waiting, collects the exit status and shows the next prompt. Every process on the system descends this way from PID 1, the init process (systemd on most Linux distributions), forming a tree you can see with pstree.

One more piece of vocabulary: processes talk to each other and to the kernel through signals, small numbered notifications such as SIGINT (Ctrl+C), SIGTERM (please shut down), SIGKILL (die now, cannot be caught) and SIGCHLD (one of your children has changed state). os12 covers them fully; here you only need to know that they exist and that the kernel delivers them using the information in the PCB.

The rest of the lesson fills in each arrow: what fork really copies, why a dead process lingers as a zombie, and where threads fit in.

1. What is inside a process's address space

When the kernel runs a program, it builds a fresh address space with a standard layout. From low addresses to high on Linux x86-64:

  • Text: the program's machine code, mapped read-only and executable from the executable file.
  • Data and BSS: global and static variables, initialised (data) and zero-initialised (BSS, which takes no space in the file).
  • Heap: memory handed out by malloc or the language runtime, growing upwards (os9 covers how).
  • Memory-mapped region: shared libraries such as libc, memory-mapped files and large allocations, placed by mmap.
  • Stack: function call frames and local variables for the main thread, growing downwards from near the top of the user address range (8 MB limit by default, ulimit -s).
  • Above that, the kernel's half of the address space, inaccessible from user mode.

You can see a real one with cat /proc/self/maps: each line is a region with its address range, permissions (r-xp for code, rw-p for data) and the file it came from. Each process has its own such map, which is why two processes can both use address 0x55d4a0000000 for completely different data.

3. States, and the two kinds of sleep

The textbook three states are ready, running and blocked. Linux's ps shows a few more letters, and two of them matter in production. S is interruptible sleep: waiting for something (a socket read, a timer, a lock) but willing to wake up early to handle a signal. Most idle processes are in S. D is uninterruptible sleep: waiting for something the kernel does not want to abandon halfway, classically a disk read or an NFS request. A D-state task ignores signals, including SIGKILL, until the operation completes, which is why a hung network mount produces processes nobody can kill. Linux also counts D-state tasks in the load average, so a stuck storage device can drive load to 50 on an idle CPU. T is stopped (Ctrl+Z, or a debugger), and Z is zombie, covered below.

4. fork(): one call, two returns

fork() is the strangest-looking system call in Unix because it returns twice. Here is the classic pattern in Python, which maps directly onto the C calls:

import os
print("before fork, pid", os.getpid())
pid = os.fork()
if pid == 0:
    # child: fork returned 0
    print("child", os.getpid(), "parent is", os.getppid())
    os._exit(7)                     # exit status 7
else:
    # parent: fork returned the child's PID
    done, status = os.waitpid(pid, 0)
    print("parent saw child", done, "exit code", os.waitstatus_to_exitcode(status))

Possible output:

before fork, pid 4100
child 4101 parent is 4100
parent saw child 4101 exit code 7

What happened inside the kernel: it allocated a new task_struct and PID 4101, copied the parent's PCB fields, duplicated the file descriptor table (both now point to the same open files, sharing file offsets), and gave the child a copy of the address space. The child's saved registers are the parent's with one change: the return-value register holds 0. Both processes then return from the same fork() call, one with 0 and one with 4101, and the if sends them down different paths.

Copying the address space sounds expensive, and for a 10 GB process it would be. Linux avoids it with copy-on-write (COW): instead of copying pages, it copies the page tables and marks every writable page read-only in both processes. When either one writes to a page, the CPU faults, and the kernel copies just that page and makes it writable again (os9 covers the mechanism). A child that calls exec immediately copies almost nothing. Forking still costs something proportional to the parent's size, because the page tables themselves are copied: roughly milliseconds for a process with tens of gigabytes mapped.

5. exec(): same process, new program

execve(path, argv, envp) (the underlying call; execl, execvp and Python's os.execv are wrappers) discards the current address space and loads a new program into it. The PID stays the same, the parent stays the same, and open file descriptors stay open unless they were marked close-on-exec (O_CLOEXEC, which Python sets by default on files it opens). Signal handlers are reset to defaults, because the handler code no longer exists. If exec succeeds it never returns; there is nothing left to return to.

Why split creating a process (fork) from choosing its program (exec)? Because the gap between them is where the child customises itself using ordinary code. Here is what a shell does for ls -l > out.txt:

  1. Shell calls fork(). Now there are two shells.
  2. The child opens out.txt (getting, say, fd 3), calls dup2(3, 1) to make fd 1 (stdout) point to the file, and closes fd 3.
  3. The child calls execve("/bin/ls", ["ls", "-l"], env). ls starts with stdout already pointing at the file and writes to fd 1 as usual, never knowing it was redirected.
  4. The parent shell calls waitpid(child), gets the exit status, stores it in $? and prints the prompt.

A pipeline ls | wc -l is the same idea: the shell creates a pipe (os12), forks twice, and each child uses dup2 to connect its stdout or stdin to one end before exec. No program in the pipeline knows about the others. Windows chose the other design, a single CreateProcess call with many parameters; POSIX later added posix_spawn for the same reason, and both are faster for huge parents because nothing is copied.

6. Exit, wait and zombies

A process ends by calling exit(status) (or returning from main, or being killed by a signal). The kernel then releases nearly everything: memory, open files (closing sockets and pipes), threads. But it cannot throw away the whole record yet, because the parent may want to know how the child ended: exit code 0, exit code 1, or killed by signal 9. So the kernel keeps a tiny remnant, PID plus exit status plus resource usage, marks it state Z, and sends the parent a SIGCHLD signal. That remnant is a zombie.

When the parent calls wait() or waitpid(), the kernel hands over the status and deletes the remnant. This is called reaping. If the parent never waits, the zombie stays forever, holding its PID. A few zombies are harmless. Thousands are a problem: PIDs are a finite resource (/proc/sys/kernel/pid_max, often 4,194,304 on modern systems but 32,768 on some), and per-user or per-container process limits run out sooner.

Parents that create many children reap them in one of three ways: wait in a loop, install a SIGCHLD handler that calls waitpid(-1, WNOHANG) repeatedly until no more children are finished, or set SIGCHLD to be ignored, which tells Linux to reap children automatically.

7. Orphans and who adopts them

What if the parent dies first? The child is now an orphan. The kernel immediately reparents it, normally to PID 1, the init process, whose job description includes calling wait for anything it adopts. If some closer ancestor has declared itself a subreaper (prctl(PR_SET_CHILD_SUBREAPER), used by systemd user managers and container runtimes), the orphan goes there instead. Orphaning is often deliberate: classic Unix daemons fork, and the parent exits immediately so that the child is no longer attached to the shell that started it.

This is exactly why containers need care. Inside a container's PID namespace (os13), your application is often PID 1, so every orphan in the container is reparented to it. A Python web server is not written to reap random children, so zombies from, say, a shell script it ran accumulate. PID 1 also gets special signal treatment: the kernel does not apply default signal actions to it, so a SIGTERM that would kill a normal process is simply ignored unless the program installed a handler. The result is the familiar "docker stop takes exactly 10 seconds": SIGTERM ignored, timeout, SIGKILL. The fix is a tiny init such as tini (docker run --init) that reaps zombies and forwards signals, or making sure the application handles both duties.

8. Threads: several cooks in one kitchen

A thread is one sequence of execution inside a process. All threads of a process share its address space (code, globals, heap, mapped files), its file descriptors, its current directory, its user ID and its signal handlers. Each thread has its own registers and instruction pointer, its own stack (Linux reserves 8 MB of address space by default for each thread's stack, but only pages actually touched use RAM), its own signal mask, and its own thread-local storage, where per-thread variables such as errno live.

Why have threads at all, when you could fork processes? Because sharing is cheap: two threads can work on the same in-memory data structure with no copying and no IPC. Creating a thread is also cheaper than creating a process (typically tens of microseconds versus hundreds for a fork-and-exec), and switching between threads of the same process skips the page-table switch (os1). The price is that nothing protects threads from each other. A wild pointer in one thread corrupts data the others use; an unhandled crash in one kills them all; and every piece of shared mutable data needs synchronization (os4).

9. How Linux implements threads: everything is a task

Linux does not have separate kernel objects for processes and threads. It has tasks, each with its own task_struct, and one system call to create them: clone(). Flags decide what the new task shares with its creator:

clone flagSharesfork()pthread_create()
CLONE_VMAddress spaceno (COW copy)yes
CLONE_FILESFile descriptor tableno (copy)yes
CLONE_FSCurrent directory, umasknoyes
CLONE_SIGHANDSignal handlersnoyes
CLONE_THREADThread group (same PID to users)noyes

So a "process" in Linux is a thread group: a set of tasks sharing a thread group ID (TGID). getpid() returns the TGID, which is the same in every thread, and gettid() returns each task's own ID. ps -eLf shows one line per thread with an LWP (light-weight process) column for the thread ID, and /proc/<pid>/task/ has one directory per thread. The same clone flags, with additions such as CLONE_NEWPID and CLONE_NEWNET, create containers (os13).

This is a one-to-one threading model: every user thread is a kernel task that the scheduler sees directly. Language runtimes add their own layers on top. Go runs many goroutines on a few OS threads (M:N), switching between them in user space for a few hundred nanoseconds when one blocks; Java's virtual threads and Python's asyncio tasks are similar ideas. These cheap user-level tasks make it practical to have a million concurrent units of work, which a million kernel threads would not be.

10. Choosing processes or threads

Real systems pick based on what they value. PostgreSQL forks a process per client connection, so a crash in one backend cannot corrupt another's memory (shared state lives in an explicit shared-memory segment). Chrome runs each site in its own renderer process so a compromised page cannot read another site's data. Nginx runs a handful of single-threaded worker processes, each with an event loop. Java application servers and most Go services are one process with many threads, sharing caches and connection pools cheaply. CPython adds a twist: because of the global interpreter lock (py8), threads do not run Python bytecode in parallel, so CPU-bound Python uses multiple processes (multiprocessing, Gunicorn workers) while I/O-bound Python can use threads or asyncio (py9).

fork in a multithreaded process is a trap

When a thread in a multithreaded process calls fork(), the child gets a copy of the entire address space but only one thread: the caller. Every other thread vanishes mid-step, and any lock they held at that instant is copied in its locked state. If another thread was inside malloc holding the allocator lock, the child's first malloc deadlocks forever. POSIX therefore restricts the child of a multithreaded parent to async-signal-safe functions until it calls exec. The problem is not academic: Python's multiprocessing used fork by default on Linux for years, and programs that had already started threads (often invisibly, inside a library such as a logging handler, gRPC or a BLAS thread pool) would occasionally hang in their children. Python 3.12 started warning when fork is used in a multithreaded process, and Python 3.14 changed the Linux default start method to forkserver, which forks children from a clean single-threaded server process started early.

Why fork is increasingly criticised

Beyond threads, fork has costs that grow with the parent: copying page tables for a 100 GB process takes a long pause, COW makes memory accounting unpredictable (the system must decide whether to allow a fork that could in theory double memory, os9), and the child inherits everything by default, including file descriptors and locks the programmer forgot about. A 2019 Microsoft Research paper, "A fork() in the road", argued fork should be deprecated for these reasons. Alternatives exist: vfork() suspends the parent and lets the child borrow its address space until exec (fast but fragile), posix_spawn() creates and execs in one call (glibc implements it with clone and CLONE_VM | CLONE_VFORK), and Linux 5.x added clone3() plus pidfds, file descriptors that refer to a process, which avoid races where a PID is reused between looking it up and signalling it.

PID reuse races

PIDs are recycled once freed. A supervisor that reads a PID from a file and later sends it a signal can hit a different process if the original died and its PID was reused. Zombies actually protect against this while they exist, since the PID is held until reaping. pidfds solve it properly: pidfd_open(pid) returns a descriptor bound to that exact process, pidfd_send_signal targets it, and the descriptor becomes readable when the process exits, so it can be used with epoll (os11).

Kernel threads

Some tasks have no user-space part at all. Kernel threads, shown in ps with names in square brackets such as [kworker/2:1], [ksoftirqd/0] and [kswapd0], run only kernel code: deferred interrupt work, flushing dirty pages, reclaiming memory. They are children of kthreadd (PID 2). Recognising them helps when top shows kswapd0 busy (memory pressure, os8) or ksoftirqd busy (heavy network interrupt load, os1).

Process groups, sessions and the terminal

Shell job control relies on two more groupings. A process group is the set of processes in one pipeline, so Ctrl+C can send SIGINT to all of cat log | grep x | wc at once. A session groups the process groups started from one terminal login. When the terminal closes, the kernel sends SIGHUP to the session's foreground jobs, which is why long jobs die when an SSH connection drops unless started with nohup, setsid, tmux or as a systemd service. Daemons call setsid() to start a new session with no controlling terminal.

Preforking and shared read-only memory

Copy-on-write makes a useful trick possible: load something large once, then fork many workers that all read it. Gunicorn with --preload, uWSGI and many model servers do this so that a 4 GB model is in RAM once rather than once per worker. The sharing lasts only while nobody writes to the pages. In CPython, merely touching an object updates its reference count, which is a write, so the pages holding object headers get copied one by one as workers run, and memory slowly climbs towards one copy per worker. gc.freeze() before forking moves existing objects out of the garbage collector's reach so its scans do not dirty them, and keeping bulk data in NumPy arrays or memory-mapped files (whose data pages are not touched by reference counting) keeps it shared. Measure with the Pss (proportional set size) figure in /proc/<pid>/smaps_rollup, which splits shared pages fairly between the processes using them.

The cost of a thread is mostly its stack and its scheduling

A thread's kernel cost is a task_struct and a 16 KB kernel stack; its user-space stack reserves virtual address space (8 MB default) but consumes RAM only for pages touched, often tens of kilobytes. So 10,000 threads might use a few hundred megabytes, which is survivable. The bigger cost is scheduling: if many of them are runnable, context switches and cache churn dominate. That is why M:N runtimes and event loops exist, and why a thread pool sized to the core count for CPU work, larger for blocking I/O work, is the standard design.

Zombie build-up

Symptom: ps shows many entries with state Z and <defunct>, all with the same parent. Find them with ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/'; the PPID column names the culprit. Common causes are a long-running service that shells out with subprocess.Popen and never calls wait() or communicate(), a custom process supervisor with a buggy SIGCHLD handler that reaps only one child per signal (signals are not queued, so several children exiting together produce one SIGCHLD; the handler must loop with WNOHANG), and container entrypoints that are not init-aware. Killing the zombies does nothing; fix or restart the parent.

The 10-second container stop

If every deploy waits exactly the stop timeout, PID 1 in the container is ignoring SIGTERM. Usually the entrypoint is a shell script that runs the app as a child (sh -c "python app.py"): the shell is PID 1, does not forward the signal, and the app never hears it. Fixes: use the exec form in the Dockerfile (CMD ["python", "app.py"]) or exec python app.py in the script so the app replaces the shell, add --init/tini, and make the app handle SIGTERM by finishing in-flight requests and exiting. Kubernetes behaves the same way with terminationGracePeriodSeconds (sc15).

Running out of PIDs or threads

"fork: Resource temporarily unavailable" (EAGAIN) or Java's "unable to create native thread" with free memory points at a process-count limit. Check, in order: the user's limit (ulimit -u; it counts threads), the cgroup's pids.max (systemd units default to a TasksMax, and container runtimes and Kubernetes can set PID limits), and kernel.pid_max and kernel.threads-max. Then find the leak: ps -eLf | wc -l for total threads, ps -eo nlwp,pid,cmd --sort=-nlwp | head for the processes with the most threads. Thread leaks in pools created per request are a classic cause, as are fork bombs; the pids cgroup controller exists precisely to contain them.

D-state hangs and phantom load

A process in state D that never leaves it is waiting on the kernel, usually storage: an NFS server that went away, a failing disk, a stuck block device. It cannot be killed, and each one adds 1 to the load average, so dashboards show "load 40" on an idle machine. cat /proc/<pid>/stack (as root) shows the kernel function it is stuck in, and echo w > /proc/sysrq-trigger dumps all blocked tasks to the kernel log. The fix is at the storage layer; for NFS, mount options such as soft or timeo trade hang-forever for I/O errors.

Fork latency in large-memory services

Services that fork for snapshots (Redis BGSAVE, some databases, Python preforking servers that load a big model before forking workers) pay a pause proportional to the page tables. Redis exposes latest_fork_usec in INFO; values of hundreds of milliseconds on large instances are common on some virtualisation platforms. Afterwards, COW copying makes memory grow with write rate, and transparent huge pages magnify it. Teams mitigate with headroom, by disabling transparent huge pages, by snapshotting from replicas, or by using preforking deliberately: loading read-only data before forking lets dozens of workers share one copy, as long as nothing writes to those pages (in CPython, reference-count updates do write, which is why gc.freeze() exists).

Watch fork, zombies and orphans happen. Use Linux or WSL with Python 3; keep a second terminal open for ps.

  1. Save as life.py: 
    import os, sys, time
mode = sys.argv[1]
pid = os.fork()
if pid == 0:
    if mode == "zombie":
        os._exit(3)                       # child dies at once
    time.sleep(30)                        # orphan mode: child outlives parent
    os._exit(0)
print("parent", os.getpid(), "child", pid)
if mode == "zombie":
    time.sleep(20)                        # do NOT wait yet: child is a zombie
    _, st = os.waitpid(pid, 0)
    print("reaped, exit code", os.waitstatus_to_exitcode(st))
    time.sleep(10)
else:
    sys.exit(0)                           # parent leaves; child is orphaned
  2. Run python3 life.py zombie & and within 20 seconds run ps -o pid,ppid,stat,cmd --ppid $! (or ps -eo pid,ppid,stat,cmd | grep defunct).
  3. Wait for "reaped" and run the same ps again.
  4. Run python3 life.py orphan, note the child PID it prints, then run ps -o pid,ppid,stat,cmd -p <child> a few times.
  5. Optional: ls /proc/$$/task in your shell, then start python3 -c "import threading,time; [threading.Thread(target=time.sleep,args=(60,)).start() for _ in range(5)]" & and run ls /proc/$!/task.

What to look for. In step 2 the child shows state Z and [python3] <defunct>: it has exited, but its entry stays because the parent has not waited. After the parent reaps it, the entry is gone and the parent printed exit code 3, the status the zombie was holding. In step 4 the child's PPID is no longer the parent's PID: it is 1, or, on systems with a user-session subreaper (systemd user manager, some WSL setups), that subreaper's PID. In step 5 the Python process has six entries under task/, the main thread plus five, each a separate kernel task sharing one PID.

Diagnose: the job runner that slowly breaks the node

A team runs a Python job-runner service in a container. For each job it calls subprocess.Popen(["bash", "-c", job_cmd]), streams the job's output to a log for a while, and moves on to the next job when the output closes; it keeps the Popen objects in a list that is never cleared. Jobs often start background helpers with &. After about a week, new jobs fail with BlockingIOError: [Errno 11] Resource temporarily unavailable, the node has plenty of free memory, and ps inside the container shows thousands of <defunct> entries. Restarting the container fixes it for another week. Explain all of this and propose fixes.

Answer

Two sources of zombies. First, the runner's own children: when a job's bash exits, it becomes a zombie until the runner calls wait(). Reading until the output closes does not reap it. Because the Popen objects are kept in a list forever, Python's own cleanup (which polls finished children when new Popen objects are created, but only ones no longer referenced) never reaps them either. Second, the background helpers: when a job's bash exits, its & children become orphans. Inside the container, the runner itself is PID 1, so every orphan is reparented to it, and when those helpers exit they become the runner's zombies too. The runner never waits for children it did not know it had.

Why the error and not memory. Each zombie holds a PID. The container has a PID limit (the cgroup pids.max, set by the runtime or Kubernetes), and zombies count against it. When the count reaches the limit, fork() inside Popen fails with EAGAIN, which Python reports as BlockingIOError: [Errno 11]. Memory is irrelevant: zombies use almost none. Restarting kills PID 1, which destroys the whole PID namespace and every zombie with it.

Confirm. ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/' | wc -l compared with cat /sys/fs/cgroup/pids.max and pids.current; the PPID of the zombies will be 1, the runner.

Fix. Reap the runner's own children: call proc.wait() (or communicate()) after the output closes, with a timeout, and drop references to finished jobs. Run the container with an init (docker run --init, or tini as the entrypoint, or shareProcessNamespace/an init in Kubernetes) so orphaned helpers are reaped by a process designed for it, and so SIGTERM is forwarded. Better still, run each job in its own process group (start_new_session=True) and kill the group when the job ends, so background helpers do not outlive their job. Add an alert on pids.current approaching pids.max.
