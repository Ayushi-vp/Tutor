Two threads of a web server each handle a purchase and each run the same line: stock = stock - 1. Stock was 1. Both threads read 1, both compute 0, both write 0, and both tell their customers the purchase succeeded. You have sold one item twice, and if you run the same test a thousand times it might only happen once. This is a race condition, and the swe12 lesson traced it line by line. Its fix is familiar: put a lock around the code that touches stock.

But that fix hides a puzzle. A lock is itself a piece of shared state that two threads try to change at the same moment. How can a lock be built without already having a lock? If you try to write one with an ordinary variable (wait until locked is 0, then set it to 1), you have the same race as the stock counter, one level down. The answer involves the hardware: special atomic instructions, memory barriers, and an operating-system mechanism that lets waiting threads sleep without missing their wake-up call.

This is the layer interviewers probe in OS rounds. "Mutex versus semaphore" and "what is a spinlock" are standard campus questions; "how is a mutex implemented on Linux", "why must a condition-variable wait be in a while loop" and "why does this service stop scaling beyond 8 threads" are senior questions. Getting them right requires knowing what happens below the lock() call.

The lesson goes from the problem to the tools: what a correct lock must guarantee, why software-only solutions such as Peterson's algorithm break on real CPUs, the atomic instructions hardware provides, spinlocks, how Linux mutexes combine user-space atomics with the futex system call, semaphores, condition variables, monitors, and finally what all of this costs when many threads contend.

The single-key bathroom

A café has one bathroom and one key on a hook. To use the bathroom you take the key; while you have it, nobody else can get in; when you leave you hang it back. The bathroom is a critical section, a piece of code that must not be run by two threads at once because it touches shared data, and the key is a lock that gives mutual exclusion. Everything in this lesson is a variation on this idea: how to make taking the key a single indivisible act, what to do while waiting for it (stand at the door checking, or sit down and ask to be called), and how to wait for things other than the key, such as "wait until the coffee is ready".

The analogy breaks in an important way. In the café, taking the key is obviously one action: two people cannot both grab it. In a computer, "check if the lock is free, then take it" is at least two steps, a read and a write, and another CPU can slip in between them. Making those steps indivisible requires hardware help.

Why "check then take" fails

Here is the naive lock, and the interleaving that breaks it:

while (locked == 1) { }   // wait until free
locked = 1;              // take it

Thread A: reads locked == 0, leaves loop
Thread B: reads locked == 0, leaves loop      <- before A writes
Thread A: locked = 1, enters critical section
Thread B: locked = 1, enters critical section  <- both inside

Any lock built from separate reads and writes has some interleaving like this. The cure is an atomic instruction: a single CPU instruction that reads a memory location and writes it in one step that no other CPU can interleave with. With an atomic "set to 1 and tell me the old value", a thread that gets back 0 knows it is the one that took the lock.

Two ways to wait

Once a thread finds the lock taken, it can spin: keep retrying in a tight loop (a spinlock). That is fast if the lock is released within a few hundred nanoseconds, and wasteful if not. Or it can sleep: ask the kernel to take it off the CPU and wake it when the lock is released (a mutex). Sleeping wastes no CPU but costs a system call and two context switches (os1), several microseconds. Real locks combine both.

Waiting for a condition, not just a lock

Locks solve "only one at a time". Many problems are instead "wait until something is true": a consumer waiting until a queue is non-empty, a worker waiting until a job arrives. Two tools handle this. A semaphore is a counter that threads decrement (blocking at zero) and increment (waking a waiter). A condition variable is a waiting room attached to a lock: a thread holding the lock can say "release the lock and sleep until someone signals me", atomically. Wrap shared data, its lock and its condition variables in one object that locks automatically, and you have a monitor.

1. The race, at instruction level

On x86-64, counter++ on a shared integer compiles to something like three instructions: load the value into a register, add one, store it back. Two threads, counter = 5:

StepThread AThread Bcounter in memory
1load → reg = 55
2load → reg = 55
3add → reg = 65
4add → reg = 65
5store 66
6store 66 (should be 7)

The interleaving can come from two CPUs running truly in parallel or from one CPU being preempted (os3) between the load and the store. Both are possible on every modern machine, which is why "it works on my laptop" means nothing for concurrent code.

2. What a correct solution must guarantee

The textbook "critical-section problem" asks for three properties. Mutual exclusion: at most one thread inside at a time. Progress: if no thread is inside and some want to enter, one of them must get in; the decision cannot be postponed forever. Bounded waiting: once a thread asks to enter, only a bounded number of others may enter before it, so nobody starves. In practice we add two engineering requirements: don't waste CPU, and perform well with many CPUs.

One early solution, used by single-CPU kernels, was to disable interrupts during the critical section: no timer interrupt means no preemption, so nothing else can run. It cannot work for user programs (disabling interrupts is privileged, os1, and a program could simply never re-enable them) and it does nothing on a multiprocessor, where other CPUs keep running. Kernels still disable interrupts locally for very short sections that interrupt handlers also touch, always combined with a spinlock for other CPUs.

3. Peterson's algorithm, and why it fails on real CPUs

In 1981 Gary Peterson published a famously short software-only lock for two threads, using only ordinary reads and writes:

bool flag[2] = {false, false};   // flag[i]: thread i wants in
int  turn;                        // whose turn it is to wait

void lock(int i) {                // i is 0 or 1
    int j = 1 - i;
    flag[i] = true;               // I want in
    turn = j;                     // but you go first if you also want in
    while (flag[j] && turn == j) { }   // wait while you want in and it's your turn
}
void unlock(int i) { flag[i] = false; }

Why it works: if both threads want in, both set their flags and then both write turn. Whichever wrote turn last has given priority away, so it waits, and the other enters. If only one wants in, the other's flag is false and it enters at once (progress). And a waiting thread enters after at most one entry by the other (bounded waiting).

The proof assumes that memory operations happen in program order and that every CPU sees writes in the same order, a model called sequential consistency. Real hardware does not provide it. An x86 CPU puts each store into a per-core store buffer and lets later loads proceed before the store reaches the cache. So thread 0 can write flag[0] = true into its buffer, then read flag[1] from cache as false; thread 1 does the same; both enter. Compilers may also reorder or cache these plain accesses. The algorithm works again only with a full memory barrier (fence) between the writes and the read, or with sequentially consistent atomics. The lesson for interviews: Peterson's algorithm shows how to reason about mutual exclusion, and its failure shows why real locks are built on hardware atomic instructions with explicit ordering.

4. The atomic instructions hardware provides

Every modern CPU offers read-modify-write instructions that are atomic across all CPUs. The CPU achieves this by taking exclusive ownership of the cache line for the duration of the instruction, using the cache-coherence protocol, so no other CPU can read or write that line in between.

  • Test-and-set: write 1, return the old value. (x86's xchg with memory is atomic and does this.)
  • Compare-and-swap (CAS): "if the location still holds expected, write new and report success; otherwise report failure and the current value". x86 lock cmpxchg; ARM uses load-linked/store-conditional pairs (ldxr/stxr) or, on newer chips, a cas instruction.
  • Fetch-and-add: add to a location and return the old value (x86 lock xadd). Ideal for counters.

These are exposed in languages as atomics: C11's atomic_fetch_add, C++'s std::atomic, Java's AtomicInteger, Go's sync/atomic. An uncontended atomic operation costs a few to about 20 nanoseconds; when many CPUs hammer the same location, each operation has to pull the cache line from another core, which can cost 50-100+ nanoseconds and serialises everyone.

5. Spinlocks

With test-and-set, a lock is three lines:

void spin_lock(atomic_int *l)   { while (atomic_exchange(l, 1) == 1) { /* spin */ } }
void spin_unlock(atomic_int *l) { atomic_store(l, 0); }

The thread that gets back 0 owns the lock; everyone else loops. This is correct (the exchange is atomic) but has two practical problems. First, every failed attempt is a write, so waiting CPUs fight over the cache line and slow down the lock holder's release. The standard fix is test-and-test-and-set: spin on a plain read (which can be served from each CPU's own cache) and only attempt the atomic exchange when the lock looks free; also add a CPU pause hint in the loop. Second, it is unfair: whichever CPU happens to win the race gets the lock, and an unlucky thread can wait indefinitely. A ticket lock fixes fairness like a deli counter: each arriving thread takes a ticket with fetch-and-add, then waits until a "now serving" counter equals its ticket; unlock increments "now serving".

When is spinning right? When the critical section is very short, the holder is guaranteed to be running on another CPU, and sleeping is either impossible or more expensive than the wait. That describes the inside of the kernel: interrupt handlers cannot sleep, and many kernel critical sections are tens of nanoseconds. Linux kernel spinlocks also disable preemption while held, so the holder cannot be switched out. In user space, a spinning thread has no such guarantee: if the holder is preempted, the spinner burns its entire time slice. On a single-CPU machine, spinning is pointless, since the holder cannot run while you spin.

6. Sleeping locks and the futex

A mutex should cost almost nothing when uncontended (the common case) and sleep when contended. Early Unix mutexes made a system call for every lock and unlock, which is wasteful when nobody else wants the lock. Linux solved this in 2002 with the futex ("fast user-space mutex"), a system call with two main operations on an integer in the program's own memory:

  • FUTEX_WAIT(addr, expected): "if *addr still equals expected, put me to sleep on addr". The kernel checks the value and queues the thread atomically, so a wake-up between the program's check and its sleep cannot be missed.
  • FUTEX_WAKE(addr, n): wake up to n threads sleeping on addr.

Ulrich Drepper's paper "Futexes Are Tricky" gives the classic mutex built on it, with three states: 0 = unlocked, 1 = locked with no waiters, 2 = locked and maybe waiters.

lock:
    c = CAS(&m, 0, 1)                 // fast path: 0 -> 1, no syscall
    if c == 0: return
    if c != 2: c = exchange(&m, 2)    // mark "there are waiters"
    while c != 0:
        futex_wait(&m, 2)             // sleep while it is still 2
        c = exchange(&m, 2)
unlock:
    if fetch_sub(&m, 1) != 1:         // was 2: someone may be waiting
        m = 0
        futex_wake(&m, 1)             // only now pay for a syscall

glibc's pthread_mutex_t, Java's monitors when contended, Go's sync.Mutex parking, Python's threading.Lock and the GIL itself all bottom out in futexes on Linux. Most implementations also spin briefly before sleeping (adaptive mutexes), betting that a lock held by a running thread will be released within a microsecond or so.

7. Semaphores

Edsger Dijkstra introduced the semaphore in the 1960s: an integer with two atomic operations, originally P and V after Dutch words, now usually wait/acquire and post/signal/release. wait decrements the count, blocking while it is zero; post increments it and wakes one waiter. Three common uses:

  • As a lock (initial count 1, a "binary semaphore"): wait to enter, post to leave.
  • To bound concurrency (initial count N): at most N threads hold a "unit" at once, such as N database connections or N concurrent downloads. Python's threading.BoundedSemaphore(10) and asyncio's Semaphore are used exactly like this.
  • As a signal (initial count 0): one thread waits until another posts, for example "wait until the worker has finished initialising".

The important difference from a mutex is ownership. A mutex is locked and unlocked by the same thread, and the system can check that (error-checking mutexes), support recursion, and apply priority inheritance (os3) because it knows who holds it. A semaphore has no owner; any thread can post, which is what makes it useful for signalling and also what makes misuse undetectable. POSIX provides sem_wait/sem_post, built on futexes too.

8. Condition variables

Suppose a consumer must wait until a shared queue is non-empty. Spinning on while queue.empty() wastes CPU. Sleeping with a plain futex risks a lost wake-up: the consumer checks (empty), the producer adds an item and signals (nobody is asleep yet), then the consumer goes to sleep forever. A condition variable solves this by being tied to a mutex. The rules:

  1. The waiter takes the mutex, then checks the condition.
  2. While the condition is false it calls wait(cv, mutex), which atomically releases the mutex and puts the thread to sleep, so no signal can slip in between. When woken, wait reacquires the mutex before returning.
  3. The signaller takes the same mutex, changes the state, and calls signal (wake one waiter) or broadcast (wake all), then releases the mutex.
import threading
items, lock = [], threading.Lock()
nonempty = threading.Condition(lock)

def consumer():
    with nonempty:                    # take the mutex
        while not items:              # WHILE, not if
            nonempty.wait()           # release + sleep, reacquire on wake
        return items.pop(0)

def producer(x):
    with nonempty:
        items.append(x)
        nonempty.notify()             # wake one waiter

Why while and not if? Two reasons. POSIX and Java allow spurious wake-ups, returns from wait without any signal, because it simplifies implementations on some platforms. More importantly, every common library uses Mesa semantics (named after the Xerox Mesa language): signal merely makes the waiter runnable. Between the signal and the waiter reacquiring the mutex, a third thread can grab the mutex and take the item. Under the original Hoare semantics, the signaller handed the mutex directly to the waiter, so the condition was guaranteed true, but that requires extra context switches and nobody implements it. With Mesa semantics, the condition is a hint, and the loop rechecks it.

Signal or broadcast? Signal wakes one waiter, which is enough when any waiter can use the change and the change only helps one (one item added). Broadcast wakes all, needed when the change may let several proceed or when different waiters wait for different conditions on the same variable. Broadcast is always correct but can cause a thundering herd, many threads waking only to find nothing to do and go back to sleep. os5 uses condition variables to build a bounded producer-consumer buffer and shows the bug that a single condition variable with signal can cause.

9. Monitors

Locks and condition variables are easy to misuse: forget to lock before touching data, forget to unlock on an error path. A monitor, proposed by Hoare and Brinch Hansen in the early 1970s, makes synchronisation a property of the object. All the shared data is private to the monitor; every operation automatically takes the monitor's lock on entry and releases it on exit; and condition variables inside it let operations wait. Java is the best-known example: every object has an intrinsic lock and one condition queue, synchronized methods take the lock, and wait()/notify()/notifyAll() are the condition operations (with Mesa semantics, so the same while loop applies). C#'s lock and Monitor, and a Python class that takes self._lock in every method with a Condition, are monitors by convention.

10. What synchronisation costs

OperationRough cost on a modern x86 server
Uncontended atomic or mutex lock+unlock~10-25 ns
Cache line moving between cores (contended atomic)~50-100 ns; more across sockets
Contended mutex handoff via futex (sleep and wake)several µs, including two context switches
Spinning while holder is preemptedup to a whole time slice (milliseconds)

The lesson in that table is that locks are not slow; contention is. A lock taken a million times a second by one thread is cheap. The same lock wanted by 32 threads becomes a queue: only one thread makes progress, the rest sleep and wake, and throughput stops scaling (Amdahl's law: the serialised fraction caps the speed-up). The remedies, in roughly the order to try them: hold locks for less time (do the slow work outside), split one lock into many (per-bucket locks in a hash map, per-CPU counters), use reader-writer locks when reads dominate (os5), and redesign to share less (message passing, per-thread state).

Memory ordering is part of every lock

CPUs reorder memory operations (store buffers, out-of-order loads) and compilers reorder code, as long as a single thread cannot observe the difference. Locks must stop this at their boundaries: taking a lock has acquire semantics (no read or write after it may move before it) and releasing has release semantics (no read or write before it may move after it). Together they guarantee that everything the previous holder wrote inside the critical section is visible to the next holder. On x86, locked instructions are full barriers and ordinary stores already have release semantics, so the costs are low; on ARM, which reorders more aggressively, acquire and release map to dedicated instructions (ldar, stlr). This is why the advice "use a lock or a proper atomic, never a plain flag" is not pedantry: code that "works" on x86 can break on ARM servers and Apple silicon. swe12 covers the language-level memory models.

Scalable spinlocks: MCS and Linux's qspinlock

With a ticket lock, all waiters spin on the same "now serving" word, so every release invalidates that cache line in every waiting CPU, and the release takes longer the more waiters there are. The MCS lock (Mellor-Crummey and Scott, 1991) gives each waiter its own queue node and has it spin on a flag in its own node; the releaser writes only the next waiter's flag, so each handoff touches one remote cache line regardless of how many wait. Linux's default spinlock since 4.2, the qspinlock, packs an MCS-style queue into a 32-bit word, spinning normally when uncontended and queueing when contended. The general idea, have each waiter spin on its own cache line, also shows up in user-space locks and in Java's AbstractQueuedSynchronizer.

Adaptive spinning and lock handoff policy

Whether to spin or sleep depends on whether the holder is running. Linux kernel mutexes do optimistic spinning: a waiter spins as long as the lock owner is currently running on another CPU, and sleeps as soon as the owner is not. User-space glibc offers PTHREAD_MUTEX_ADAPTIVE_NP with a bounded spin. A second policy choice is fairness. If an unlocking thread immediately tries to lock again, it often wins against the sleeping waiter, which still has to be woken and scheduled; that maximises throughput but can starve waiters. Strict FIFO handoff is fair but makes every handoff pay a context switch, causing lock convoys where throughput collapses to one handoff per wake-up latency. Many implementations compromise: allow barging, but switch to handoff mode after a waiter has waited too long (Go's sync.Mutex starvation mode after 1 ms is a documented example).

Read-mostly data: reader-writer locks, seqlocks and RCU

When reads vastly outnumber writes, mutual exclusion among readers is wasteful. Reader-writer locks (os5) allow many readers or one writer, but every reader still writes to the lock's counter, so on many cores the counter's cache line becomes the bottleneck. Two kernel techniques avoid reader writes entirely. A seqlock has the writer increment a sequence number before and after its update; readers read the number, read the data, read the number again, and retry if it changed or was odd. Readers never block the writer, which suits small data such as the kernel's clock. RCU (read-copy-update) lets readers proceed with no locks or atomic writes at all: writers make a new copy, publish it with a single pointer update, and free the old copy only after a grace period in which every CPU has passed through a point where it cannot hold an old reference. RCU is used throughout Linux (routing tables, file-descriptor tables, module lists) and has user-space versions (liburcu).

Lock-free structures and their traps

A lock-free stack pushes with CAS on the head pointer, retrying if another thread changed it. Such structures guarantee that some thread always makes progress, even if others are preempted, which matters in real-time and signal-handler contexts. They are notoriously subtle. The ABA problem: a thread reads head = A, is preempted; others pop A, pop B, push A back; the CAS sees A and succeeds, linking to the freed B. Fixes are tagged pointers (a counter alongside the pointer, checked with double-width CAS) or safe memory reclamation such as hazard pointers or epochs. And lock-free code still contends on the same cache line, so it is not automatically faster than a well-sharded locked design.

Kernel locking rules that explain user-visible bugs

Inside the kernel, code holding a spinlock must not sleep (the CPU cannot be given up while others spin on you), and data shared with interrupt handlers needs spin_lock_irqsave so an interrupt on the same CPU cannot try to take a lock its own CPU already holds, which would deadlock instantly. Linux's lockdep validator records the order in which every class of lock is taken and warns about any cycle the first time it could occur, rather than waiting for the deadlock to happen. The same idea (a global lock order, checked by tools) is the main defence against deadlocks in user space too (os6).

Recognising contention

Symptoms of lock contention: throughput that stops rising (or falls) as threads or cores are added; CPU that is either low with idle threads (they are sleeping on locks) or high in system time (futex calls) or high in user time with a spin function on top of the profile; and tail latency that grows with load. The tools: perf trace -s -p <pid> or strace -c -f on a short sample to count futex calls; off-CPU flame graphs (bcc's offcputime) showing the stacks where threads block; perf lock contention on recent kernels for both kernel and user locks; Java thread dumps (jstack) showing many threads BLOCKED on the same monitor with the owner's stack; Go's mutex and block profiles in pprof; and py-spy dump for Python threads.

Common culprits

A global lock around a cache or connection pool that every request takes; a logging library that serialises all threads on one file handle; the memory allocator (older glibc versions with many threads and few arenas, one reason services switch to jemalloc or tcmalloc, which use per-thread caches); a synchronised singleton such as a random-number generator or date formatter; and metrics counters incremented by every request on one shared atomic. The fixes follow the cost table: move slow work (I/O, serialisation, logging) out of the critical section, shard (striped locks, per-CPU or per-thread counters summed on read), use read-mostly structures, and avoid locks on the hot path entirely where possible.

False sharing

A classic performance bug with no lock in sight: an array of per-thread counters, each thread incrementing only its own slot. It looks embarrassingly parallel, but eight 8-byte counters fit in one 64-byte cache line, so every increment steals the line from the other cores, and the program can get slower as threads are added. perf c2c finds cache lines with heavy cross-core modification. The fix is to pad or align each thread's data to its own cache line (alignas(64) in C/C++, @Contended in Java, used in the JDK's own LongAdder). The LMAX Disruptor, a well-known low-latency Java queue, owes much of its speed to careful padding of its sequence counters.

Hangs: deadlock, lost wake-ups and stuck owners

A process whose threads are all asleep on futexes with no CPU use is usually deadlocked (os6) or waiting for a wake-up that was lost. Thread dumps give the lock graph: who holds what, who waits for what. Lost wake-ups come from waiting on a condition outside the mutex or with if instead of while; they show up as rare hangs under load. A third hang: a thread that died or was cancelled while holding a lock. POSIX robust mutexes (PTHREAD_MUTEX_ROBUST) report EOWNERDEAD to the next locker for locks in shared memory between processes, so the survivor can repair the data.

Python specifics

In CPython with the GIL, only one thread runs Python bytecode at a time (py8), so contention for the GIL itself looks like a lock problem: CPU-bound threads plus I/O threads produce poor latency for the I/O threads. Your own threading.Lock objects are still needed, since the GIL does not make compound operations atomic. In the free-threaded build (officially supported from 3.14), threads really run in parallel and the costs in this lesson apply directly, including contention on reference counts of shared objects, which the runtime mitigates with biased and deferred reference counting.

See a race, fix it three ways, and compare costs. Use Linux, WSL or macOS with gcc or clang.

  1. Save as race.c: 
    #include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
#include <string.h>
#define N 10000000
volatile long plain = 0; long locked = 0; atomic_long at = 0;
atomic_int spin = 0; long spun = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
const char *mode;
void *work(void *_) {
    for (long i = 0; i < N; i++) {
        if (!strcmp(mode, "plain"))  plain++;
        else if (!strcmp(mode, "mutex")) { pthread_mutex_lock(&m); locked++; pthread_mutex_unlock(&m); }
        else if (!strcmp(mode, "atomic")) atomic_fetch_add(&at, 1);
        else { while (atomic_exchange(&spin, 1)) ; spun++; atomic_store(&spin, 0); }
    }
    return 0;
}
int main(int argc, char **argv) {
    mode = argv[1]; pthread_t t[4];
    for (int i = 0; i < 4; i++) pthread_create(&t[i], 0, work, 0);
    for (int i = 0; i < 4; i++) pthread_join(t[i], 0);
    printf("%s: %ld (expected %d)\n", mode, plain + locked + at + spun, 4 * N);
}
  2. Build and time each mode: gcc -O2 -pthread race.c -o race, then for m in plain atomic spin mutex; do /usr/bin/time -f "%e s, %S sys" ./race $m; done (on macOS use time ./race $m).
  3. Count futex calls in the mutex run: strace -f -c -e trace=futex ./race mutex.

What to look for. plain prints a total well below 40,000,000 and different each run: lost updates from the load-add-store race. The other three print exactly 40,000,000. atomic is usually fastest, since each increment is one locked instruction, though still much slower per operation than a single-threaded loop because the cache line bounces between cores. spin and mutex are slower still; the mutex run shows some system time and many futex calls (contended handoffs entering the kernel), while the spin run shows almost no system time but burns user CPU waiting. Try changing the thread count to 1: every correct version becomes fast, which is the point of the lesson: the cost is contention, not the lock.

Review: the job queue that sometimes hangs

A teammate wrote this worker pool in Python. Under load tests it occasionally hangs with all workers asleep and items still in the queue; at other times a worker crashes with IndexError: pop from empty list. Find every bug, explain the interleaving behind each symptom, and fix it.

jobs = []
lock = threading.Lock()
cv = threading.Condition(lock)

def submit(job):
    jobs.append(job)
    with cv:
        cv.notify()

def worker():
    while True:
        if not jobs:
            with cv:
                cv.wait()
        with lock:
            job = jobs.pop(0)
        run(job)
Answer

Bug 1: lost wake-up (the hang). The worker checks if not jobs without holding the lock, then takes the lock and waits. Interleaving: the worker sees an empty list; before it reaches cv.wait(), submit appends a job and calls notify(), which wakes nobody because no one is waiting yet; the worker then waits and sleeps forever with a job in the queue. If every worker hits this, the pool hangs. The check and the wait must happen under the same lock, so that the notify cannot slip between them.

Bug 2: if instead of while (the IndexError). When a worker wakes from wait(), it assumes a job is there. But with Mesa semantics another worker that was not waiting can grab the lock first and pop the job, or the wake-up can be spurious; the woken worker then pops from an empty list. The condition must be rechecked in a loop after every wake-up.

Bug 3: the append is outside the lock. jobs.append in submit modifies shared state without the lock. In CPython the GIL happens to make a single list append atomic, but the code relies on that accident, breaks on a free-threaded build, and is the reason bug 1 is possible at all: state changes and notifications must both happen under the mutex.

Fix:

def submit(job):
    with cv:
        jobs.append(job)
        cv.notify()

def worker():
    while True:
        with cv:
            while not jobs:
                cv.wait()
            job = jobs.pop(0)
        run(job)                     # run outside the lock

Running the job outside the lock keeps the critical section short so workers do not serialise on it. In real code use queue.Queue, which implements exactly this pattern (plus a bound and timeouts), and use collections.deque rather than list.pop(0), which is O(n).
