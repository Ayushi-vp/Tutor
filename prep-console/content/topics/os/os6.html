At 2 a.m. a payment service stops responding. CPU is near zero, memory is fine, the process is alive, and every health check times out. A thread dump shows two hundred threads, all asleep, all waiting for something. Nothing is broken in the usual sense: no exception, no crash, no error log. The service has simply stopped, and it will stay stopped until someone restarts it. This is a deadlock: a group of threads each waiting for a resource that another member of the group holds, so none can ever move.

The dining philosophers in os5 showed the smallest version. Real ones are rarely so tidy. The resources can be locks, but just as often they are database rows, connections in a pool, threads in a thread pool, slots in a queue, or the buffer of a pipe. A transfer from account A to B running at the same moment as one from B to A. A web request holding a database connection while it waits for a second connection from a pool that is empty because every other request is doing the same. A parent process waiting to read its child's output while the child waits for the parent to read its errors.

Deadlock is one of the oldest topics in operating systems, and interviews treat it as core material. Expect "what are the four necessary conditions?", "what is the difference between prevention and avoidance?" and a Banker's algorithm table to work through by hand in campus and SDE rounds; expect "how would you find and fix a deadlock in this service?" and "how do databases deal with deadlocks?" in senior ones.

This lesson defines deadlock precisely, gives the four conditions and the graphs used to reason about it, then works through the four strategies in turn: prevent it by design, avoid it with the Banker's algorithm (fully worked), detect and recover, or deliberately ignore it. It ends with the deadlocks that actually take down production systems and how to diagnose them.

The gridlocked intersection

Picture a small crossroads with four cars, one approaching from each direction, each wanting to turn left. Each car pulls into the intersection and occupies one quarter of it. To finish its turn, each car needs the quarter in front of it, which the next car occupies. No car can reverse, and no car will give up its quarter. Traffic stops until a police officer makes one car back out. Every ingredient of deadlock is there:

  • Mutual exclusion: a quarter of the road can hold only one car.
  • Hold and wait: each car keeps the space it has while waiting for the next.
  • No preemption: nobody can lift a car out of the way.
  • Circular wait: car 1 waits for car 2, which waits for car 3, which waits for car 4, which waits for car 1.

These are the Coffman conditions, published in 1971. A deadlock needs all four at the same time, which is the most useful fact in this lesson: remove any one and deadlock becomes impossible. Traffic engineers do exactly that. A "do not block the box" rule attacks hold and wait (don't enter unless you can get all the way through); a traffic light attacks circular wait (only some directions move at once).

Drawing it: who holds what, who wants what

To reason about deadlock precisely, draw a resource-allocation graph. Processes (or threads) are circles; resources are boxes, with a dot for each identical instance. An arrow from a process to a resource is a request ("I am waiting for this"); an arrow from a resource instance to a process is an assignment ("this is held by that process").

When every resource has a single instance (a specific mutex, a specific database row), a cycle in this graph is a deadlock. When a resource has several interchangeable instances (three printers, a pool of ten connections), a cycle is a warning but not proof: some other process outside the cycle may release an instance and break it. Section 6 handles that case.

Notice what is not required. Nobody has to be doing anything wrong in isolation: each car followed reasonable rules, and each thread in a deadlock is running correct code. Deadlock is a property of how their requests interleave, which is why it so often escapes testing and appears only under production load.

Four strategies

There are four ways to deal with deadlock, and every real system uses one or a mix. Prevent it by designing so that one of the four conditions can never hold. Avoid it by checking each request against what processes might still ask for, and refusing requests that could lead to trouble. Detect it after it happens and recover by aborting or rolling back a victim. Or ignore it, on the grounds that it is rare and the cure costs more than the disease. The rest of the lesson takes these in turn.

1. The precise definition

A set of processes is deadlocked when every process in the set is waiting for an event that only another process in the set can cause. The event is usually the release of a resource. Two consequences follow. A deadlock never resolves on its own, unlike slowness or contention. And it involves a set: one thread waiting forever for a lock that a crashed thread never released is a bug, but not a deadlock in this sense.

It helps to distinguish two neighbours. In livelock, threads are not blocked; they keep reacting to each other (both back off, both retry, both back off) without progress. In starvation, the system makes progress but one thread is always passed over. Both are liveness failures, but the fixes differ: deadlock needs the cycle broken, livelock needs randomness or asymmetry, starvation needs fairness.

2. Prevention: break one of the four conditions

Prevention means designing the system so that one of the Coffman conditions can never hold. Take each in turn:

Mutual exclusion. Make resources shareable so nobody has to wait. Read-only data needs no lock; immutable snapshots published by pointer swap (os5) let readers share freely; lock-free data structures avoid exclusive holding altogether. But many resources are inherently exclusive (a printer mid-job, a row being updated), so this condition can only be removed in places.

Hold and wait. Require a process to request everything it needs at once, and grant all or nothing. A transaction that declares the rows it will touch and locks them together cannot hold some while waiting for others. Alternatively, a process may only request resources when it holds none, releasing everything before asking again. Both work, but they hurt utilisation (resources are held longer than needed) and require knowing the full set in advance, and a process that needs many popular resources may starve waiting for all of them to be free at once.

No preemption. Allow resources to be taken away. If a process holding some resources requests one that is unavailable, it releases everything it holds and starts over later. The trylock pattern does this voluntarily: try the second lock; if it fails, release the first, back off for a random time, and retry. This works for resources whose state can be saved and restored, such as CPU registers and memory pages (which the OS preempts all the time), but not for a half-printed page or a half-written file, and it risks livelock without random back-off.

Circular wait. Impose a global order on resources and require every process to acquire them in increasing order. A cycle would need some process to hold a higher-numbered resource while waiting for a lower-numbered one, which the rule forbids. This is the most practical prevention technique by far: it costs nothing at runtime and only needs discipline. The order can be anything consistent: account IDs for a transfer, memory addresses of the lock objects, or a documented hierarchy ("always take the connection lock before the session lock"). The Linux kernel documents lock orders for its subsystems and checks them automatically with lockdep (see Deep).

def transfer(a, b, amount):
    first, second = (a, b) if a.id < b.id else (b, a)   # global order by id
    with first.lock:
        with second.lock:
            a.balance -= amount
            b.balance += amount

A transfer from 7 to 3 and one from 3 to 7 both lock account 3 first, so one simply waits for the other; the circular wait from the primer's figure can never form.

3. Avoidance: stay in safe states

Avoidance takes a different approach: allow all four conditions, but look at each request and only grant it if the system can still guarantee that every process will finish. This needs extra information: each process must declare in advance the maximum number of each resource type it might ever hold.

A state is safe if there is at least one order of processes, a safe sequence, in which each process's remaining maximum need can be satisfied by the currently available resources plus everything released by the processes before it in the order. If such an order exists, the system can always avoid deadlock by running processes in that order if necessary. If not, the state is unsafe: deadlock is not certain (processes may never ask for their maximum), but it can no longer be ruled out. Every deadlocked state is unsafe; not every unsafe state is deadlocked.

4. The Banker's algorithm, worked in full

Dijkstra's Banker's algorithm (named for a banker who never lends so much cash that it could not meet all customers' credit lines in some order) implements avoidance for several resource types. With n processes and m resource types it keeps:

  • Available[m]: free instances of each type.
  • Max[n][m]: each process's declared maximum.
  • Allocation[n][m]: what each process holds now.
  • Need[n][m] = Max − Allocation: what each may still request.

Safety algorithm. Set Work = Available and mark all processes unfinished. Repeatedly find an unfinished process whose Need ≤ Work (component by component); pretend it runs to completion and releases its allocation (Work += Allocation), and mark it finished. If all processes get marked, the state is safe and the order you marked them in is a safe sequence.

Request algorithm. When process i requests vector R: if R exceeds Need[i], it is an error (it lied about its maximum); if R exceeds Available, it must wait. Otherwise, pretend to grant it (Available −= R, Allocation[i] += R, Need[i] −= R) and run the safety algorithm. Safe: grant it. Unsafe: undo the pretence and make the process wait.

Here is the textbook example. Three resource types with totals A = 10, B = 5, C = 7, and five processes:

ProcessAllocation (A B C)Max (A B C)Need (A B C)
P00 1 07 5 37 4 3
P12 0 03 2 21 2 2
P23 0 29 0 26 0 0
P32 1 12 2 20 1 1
P40 0 24 3 34 3 1

Total allocated is (7, 2, 5), so Available = (10, 5, 7) − (7, 2, 5) = (3, 3, 2).

Is it safe? Scan for a process whose need fits in Work = (3, 3, 2):

  1. P0 needs (7, 4, 3): no. P1 needs (1, 2, 2): yes. P1 finishes and returns (2, 0, 0): Work = (5, 3, 2).
  2. P0 (7, 4, 3): no (A). P2 (6, 0, 0): no (A). P3 (0, 1, 1): yes. Returns (2, 1, 1): Work = (7, 4, 3).
  3. P0 (7, 4, 3): yes. Returns (0, 1, 0): Work = (7, 5, 3).
  4. P2 (6, 0, 0): yes. Returns (3, 0, 2): Work = (10, 5, 5).
  5. P4 (4, 3, 1): yes. Returns (0, 0, 2): Work = (10, 5, 7), everything back.

All five finish, so the state is safe with safe sequence ⟨P1, P3, P0, P2, P4⟩. (Other safe sequences exist, such as ⟨P1, P3, P4, P2, P0⟩; one is enough.)

P1 requests (1, 0, 2). It is within P1's need (1, 2, 2) and within Available (3, 3, 2). Pretend: Available = (2, 3, 0), P1's allocation (3, 0, 2), need (0, 2, 0). Safety check from Work = (2, 3, 0): P1's need (0, 2, 0) fits; it returns (3, 0, 2), giving (5, 3, 2), which is the same Work as step 1 above, so the rest of the sequence completes exactly as before. Safe: grant.

Next, P4 requests (3, 3, 0). Within its need, but Available is now (2, 3, 0) and A is short: P4 waits (no safety check needed).

Next, P0 requests (0, 2, 0). Within need (7, 4, 3) and within Available (2, 3, 0). Pretend: Available = (2, 1, 0), P0 need (7, 2, 3). Safety: P0 needs 7 A: no. P1 needs (0, 2, 0): only 1 B available: no. P2 needs 6 A: no. P3 needs (0, 1, 1): no C available: no. P4 needs (4, 3, 1): no. Nobody can finish, so the state would be unsafe. Deny; P0 waits even though the resources physically exist. That is avoidance being cautious.

Cost. The safety check is O(m × n²) in the simple form, run on every request. Combined with the need to know maximum demands in advance, that is why general-purpose kernels do not use it. Its ideas live on in admission control: a cluster scheduler that only starts a job when its declared CPU and memory requests fit, or a connection broker that refuses a session whose declared needs could exhaust the pool.

5. Detection with single-instance resources: the wait-for graph

Detection lets processes request freely and checks for deadlock afterwards, periodically or when something has waited suspiciously long. If each resource has one instance, collapse the resource-allocation graph into a wait-for graph: an edge P → Q whenever P waits for a resource Q holds. A deadlock exists exactly when this graph has a cycle, and a depth-first search finds one in time proportional to the number of nodes plus edges. Databases maintain this graph for row and table locks; Java's ThreadMXBean.findDeadlockedThreads() and the JVM's thread-dump deadlock report do the same for monitors and java.util.concurrent locks.

6. Detection with multiple instances

With several instances per type, use a Banker-like algorithm, but with each process's current outstanding request instead of its maximum need (nobody declares a maximum in this scheme). Set Work = Available; mark any process holding nothing as finished; repeatedly find an unfinished process whose current request fits in Work, assume it will get what it asked for, finish and release its allocation, and add that to Work. Any process left unmarked at the end is deadlocked. The assumption that a satisfiable process will finish is optimistic: if it later requests more, the next detection run will catch any new deadlock.

How often to run it? Running detection on every blocked request finds deadlocks immediately and identifies the request that closed the cycle, but costs CPU on every wait. Running it periodically, or only when a wait exceeds a threshold, is cheaper but lets deadlocked processes sit idle longer. PostgreSQL takes the second approach: a backend that has waited on a lock for deadlock_timeout (1 second by default) runs the check; most waits end sooner and never pay for it.

7. Recovery

Once a deadlock is found, something has to give.

Abort processes. Kill every process in the cycle (simple, expensive), or kill them one at a time, rerunning detection after each, until the cycle is gone. Which victim? Choose by cost: how much work it has done, how much it holds, how much it still needs, how many processes would have to be rolled back, its priority, and whether it is interactive. Databases typically abort the transaction that is cheapest to undo (InnoDB uses the number of rows inserted, updated or deleted).

Preempt resources and roll back. Take resources from a victim and give them to others. The victim must be rolled back to a safe earlier state, its last checkpoint or, simplest, its start. Transactions make this natural: aborting undoes their changes and the client retries.

Avoid starving the victim. If the same process is always cheapest, it may be chosen forever. Include the number of times a process has been rolled back in the cost, or use age-based schemes where the oldest participant always survives.

8. The ostrich algorithm

Linux and Windows do not detect or prevent deadlocks among user processes' locks, pipes or semaphores. If your threads deadlock, the kernel just sees sleeping threads. This is a reasoned choice, nicknamed the ostrich algorithm: deadlocks among user resources are application bugs, prevention would restrict programs too much, avoidance needs information programs do not have, and detection over every lock in the system would cost too much for a rare event. The kernel does protect itself: it uses lock ordering internally, validates it with lockdep in debug builds, and its hung-task detector logs tasks stuck in uninterruptible sleep for more than 120 seconds by default.

Lock-order validation: lockdep

Waiting for a deadlock to happen in testing is a poor strategy, because the bad interleaving may be rare. Linux's lockdep instead learns the order in which classes of locks are taken (all inode locks are one class, for example) and builds a graph of "A was held while B was acquired". The first time any code path would add an edge that closes a cycle, lockdep prints a report with both stacks, even if the two paths never actually ran concurrently. It also checks rules such as taking a lock in interrupt context that is elsewhere taken with interrupts enabled. The same idea exists in user space: ThreadSanitizer's deadlock detector for C/C++ and Go, and lock-order checks in Abseil's Mutex, which record lock acquisition orders at runtime and flag potential inversions.

Timestamp schemes: wait-die and wound-wait

Distributed databases often cannot afford global cycle detection, so they prevent cycles by fixing the direction of waiting with transaction timestamps (older = smaller). In wait-die (non-preemptive), an older transaction requesting a lock held by a younger one waits; a younger one requesting from an older one "dies" (aborts) and restarts later with its original timestamp. In wound-wait (preemptive), an older requester "wounds" (aborts) the younger holder; a younger requester waits. Either way, waits only ever go in one direction of age, so no cycle can form, and because a restarted transaction keeps its timestamp, it eventually becomes the oldest and cannot starve. Google Spanner uses wound-wait for read-write transactions. The trade-off is unnecessary aborts: some conflicts that would never have deadlocked still cause a restart.

Distributed deadlock and why timeouts dominate

When the cycle spans machines (service A holds a lock and calls service B, which waits on a lock held by a request in A), no single node sees the whole wait-for graph. Algorithms exist to detect distributed cycles (edge-chasing algorithms send probe messages along wait-for edges and declare deadlock if a probe returns to its sender), but they are complex and false positives appear when the graph changes while probes are in flight. In practice, distributed systems use timeouts and leases: every remote wait has a deadline, locks held by a crashed or slow client expire (sc9 covers leases and fencing tokens), and the caller retries with back-off. Timeouts cannot tell a deadlock from a slow peer, which is why they must be paired with prevention (consistent ordering of cross-service calls, avoiding holding locks across remote calls).

Communication deadlocks

Not every deadlock involves reusable resources like locks. In a communication deadlock, processes wait for messages that will never come: two processes each blocked in recv() waiting for the other to speak first, or a request-response protocol where both sides wait for a request. Bounded buffers turn ordinary data flow into deadlock risks too: two processes each writing to the other through a pipe, both pipes full, both blocked in write(). Go's runtime detects the case where every goroutine is blocked and aborts with "all goroutines are asleep - deadlock!", but cannot detect a partial deadlock while any goroutine (a timer, a network poller) is still runnable.

Deadlocks the kernel must avoid in itself: memory reclaim

A subtle kernel example shows that "resources" include memory. A file system holds a lock on an inode and needs to allocate memory. Memory is short, so the allocator tries to free some by writing dirty pages back to disk, and those pages may belong to the same file system, whose write-back path needs the inode lock the allocating thread already holds. That is a deadlock through the memory allocator. Linux prevents it with allocation flags (GFP_NOFS, GFP_NOIO, and the scoped memalloc_nofs_save()) that tell reclaim not to call back into file-system or block-I/O code from inside such sections. The general lesson for application code is the same: any call that may block on a resource (allocation, logging, metrics, a callback) is a potential edge in the wait-for graph.

Deadlock-freedom by construction in modern languages

Some designs make whole classes of deadlock impossible. Actor systems (Erlang, Akka) have no shared locks; each actor processes one message at a time, though two actors synchronously waiting on each other's replies still deadlock, which is why they favour asynchronous messages. Software transactional memory (Clojure, Haskell's STM) runs transactions optimistically and retries on conflict, trading deadlock for possible livelock under heavy contention. Rust's type system does not prevent deadlocks (they are safe in Rust's definition), but libraries can encode lock ordering in types so that acquiring locks out of order fails to compile. The common thread: removing a Coffman condition structurally is more reliable than avoiding it by care.

Recognising a deadlock

The signature is a process that is alive, uses almost no CPU, and makes no progress: requests time out, queues grow, health checks fail, but there are no errors. Contrast with overload (high CPU or long queues but still progress) and with livelock (high CPU, no progress). Confirm with stacks. On the JVM, jstack <pid> prints "Found one Java-level deadlock" with the cycle spelled out. For C/C++/Rust, gdb -p <pid> -batch -ex "thread apply all bt" shows each thread blocked in pthread_mutex_lock or futex and which code path took which lock. Python: py-spy dump --pid <pid> or faulthandler.dump_traceback_later. Go: send SIGQUIT for all goroutine stacks, or use the /debug/pprof/goroutine?debug=2 endpoint.

Database deadlocks

Databases report them instead of hanging. PostgreSQL raises ERROR: deadlock detected with the two processes, the locks and the statements in the server log; MySQL's SHOW ENGINE INNODB STATUS keeps the latest detected deadlock with both transactions' locks, and innodb_print_all_deadlocks logs every one. A few deadlocks per day under heavy contention are normal and should simply be retried by the application (wrap transactions in a retry loop for deadlock and serialization errors). A rising rate means a design problem: transactions that update the same rows in different orders (sort keys before batch updates), long transactions holding locks across user think time or remote calls, or missing indexes that make UPDATEs lock far more rows than intended. sc5 covers isolation levels, which change which locks are taken.

Resource-pool deadlocks

The most common production deadlocks have no explicit lock. Thread-pool starvation: an executor with 16 threads runs tasks that submit subtasks to the same executor and block on their futures; under load, all 16 threads are parents waiting, and the subtasks never run. Connection-pool deadlock: each request takes a database connection, then calls a helper that takes a second connection from the same pool of 20; with 20 concurrent requests each holding one and waiting for another, the pool is empty forever. Nested remote calls: service A's worker calls service B, which synchronously calls back into A, whose workers are all busy waiting on B. The fixes are the same shape: never hold a pooled resource while waiting for another from the same pool, use separate pools per stage, size pools with nesting in mind, and set checkout timeouts so the failure becomes an error rather than a hang.

Pipes and subprocesses

A frequent "my script hangs" report: a program runs a child with stdout=PIPE, stderr=PIPE and reads stdout to the end, or calls wait() before reading. As soon as the child writes more than the pipe buffer (64 KiB on Linux) to the pipe nobody is reading, the child blocks, and the parent waits forever for it. Python's documentation warns about exactly this; communicate() reads both pipes concurrently. The same pattern bites shell pipelines with named pipes and programs that talk to a child interactively over stdin and stdout.

Defensive defaults

Practical hygiene that prevents most incidents: document and enforce a lock order for any code that takes more than one lock; keep critical sections free of I/O, remote calls and callbacks into unknown code (a callback may take locks you cannot see); put timeouts on every lock acquisition, pool checkout and remote call in server code so a deadlock surfaces as an error with a stack trace; and add an internal watchdog that dumps all thread stacks if no request has completed for N seconds, so the evidence exists when someone gets paged.

    def is_safe(avail, alloc, need):
    work, done, order = list(avail), [False] * len(alloc), []
    progress = True
    while progress:
        progress = False
        for i in range(len(alloc)):
            if not done[i] and all(n <= w for n, w in zip(need[i], work)):
                work = [w + a for w, a in zip(work, alloc[i])]
                done[i], progress = True, True
                order.append(f"P{i}")
    return all(done), order

def request(i, req, avail, alloc, need):
    if any(r > n for r, n in zip(req, need[i])): return "error: exceeds max"
    if any(r > a for r, a in zip(req, avail)):   return "wait: not available"
    a2 = [x - r for x, r in zip(avail, req)]
    al2 = [list(row) for row in alloc]; nd2 = [list(row) for row in need]
    al2[i] = [x + r for x, r in zip(al2[i], req)]; nd2[i] = [x - r for x, r in zip(nd2[i], req)]

    if not ok: return "wait: would be unsafe"
    avail[:], alloc[i], need[i] = a2, al2[i], nd2[i]

Diagnose: the checkout service that freezes at peak

An e-commerce checkout service runs with a request thread pool of 50 and a database connection pool of 50. During flash sales it periodically freezes: CPU drops to 2%, all 50 request threads are busy, the database shows only 50 idle connections (no queries running), and the service recovers only after a restart. A thread dump shows most threads blocked in pool.getConnection(). The checkout handler takes a connection to reserve inventory, then calls applyCoupon(), a shared library function that takes its own connection to read coupon rules. Explain the deadlock in terms of the four conditions, say why it only happens at peak, and give two fixes and one safeguard.

Answer

The cycle. Each request holds one connection (from reserving inventory) and waits for a second (inside applyCoupon). At peak, 50 requests run concurrently; each has taken its first connection, so the pool of 50 is empty, and every request now waits for a connection that only another waiting request could release. Mapping to the conditions: mutual exclusion (a connection serves one request at a time), hold and wait (the first connection is held while waiting for the second), no preemption (the pool cannot take a connection back), and circular wait (every holder waits on the pool, which only other holders can replenish). The database shows idle connections because they are checked out but their owners are blocked inside the application.

Why only at peak. With fewer than 50 concurrent checkouts, some connections are always free for the second checkout, so every request completes. The deadlock needs as many concurrent first checkouts as the pool size, which only a flash sale produces. Classic hold-and-wait bugs hide until load reaches the pool size.

Fix 1: remove hold and wait. Pass the request's existing connection into applyCoupon (or have it use the transaction's connection through a context), so each request needs exactly one connection. This is the real fix, and also makes the coupon read part of the same transaction.

Fix 2: separate the pools. If the coupon read must use its own connection, give it a separate small pool (or cache coupon rules in memory), so the two stages cannot exhaust each other. Sizing the main pool larger than the thread pool also breaks the cycle (with 51 connections and 50 threads, someone can always get a second), but it is fragile if thread counts change.

Safeguard. Set a checkout timeout on the pool (for example 2 seconds) so a future deadlock turns into errors with stack traces, and alert on pool wait time and on "threads blocked in getConnection while connections are idle in the database".
