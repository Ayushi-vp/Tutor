Run the same program twice, side by side, and print the address of a global variable in each. On Linux with address randomisation turned off, both print the same number, say 0x555555558010. Both processes write different values to "the same" address, and neither sees the other's value. Meanwhile your machine has, say, 16 GB of RAM, and a hundred processes that each believe they own a huge, private, neatly laid-out stretch of memory starting at the same addresses. None of them knows where in the physical RAM chips its data actually lives, and none can reach anyone else's data even by accident.

That illusion is the work of address translation. Every memory access a program makes, every load, store and instruction fetch, billions per second, uses a virtual address that the CPU translates into a physical address on the fly, using tables the kernel maintains. Without it, programs would have to be compiled for specific RAM locations, a stray pointer in any program could corrupt any other program or the kernel, and memory would fragment into unusable gaps as programs started and stopped.

Translation is also where a surprising amount of real-world performance is won or lost. A database whose working set exceeds what the CPU's translation cache can cover can lose 10-30% of its throughput to page walks; huge pages can win it back or, misconfigured, cause latency spikes. Virtual machines pay more for every translation miss. And interviewers love the topic: "what is a page table?", "translate this address", "why multi-level?", "what is the TLB?" are standard OS questions, and the effective-access-time calculation is a favourite exam problem.

This lesson builds translation up the way history did: simple relocation with base and bounds, segmentation, then paging; what is in a page-table entry; why page tables are trees and how the hardware walks one; the TLB that makes it fast; huge pages; and what it all means for systems you run.

Apartment numbers and a building directory

Imagine every tenant in a city is told their flat is "Flat 1, Floor 1" in their own private building. Mail addressed by tenants uses these private addresses. A city directory, one per tenant, says "this tenant's Floor 1, Flat 1 is actually 47 Elm Street, unit 12". The postal service looks up each letter in the sender's directory and delivers to the real location. Tenants never see real addresses, so they cannot send anything to another tenant's flat, and the city can move a tenant's belongings to a different building simply by updating the directory.

In the computer, the private addresses are virtual addresses, the real locations are physical addresses, the directory is the page table, and the postal service is the memory-management unit (MMU), hardware inside the CPU that translates every address. The kernel writes the directories; user programs cannot touch them (os1).

The analogy breaks on scale and speed. The directory is not consulted once per letter but on every memory access, billions of times per second, so it must be organised cleverly and cached aggressively. That is most of what this lesson is about.

Pages: translating in blocks, not bytes

Keeping a directory entry for every single byte would make the directory larger than memory. Instead, memory is translated in fixed-size blocks called pages, 4 KiB (4,096 bytes) by default on x86-64 and most ARM systems. Physical memory is divided into frames of the same size. Any virtual page can be placed in any free frame. An address then splits into two parts: the high bits say which page (the virtual page number, VPN), and the low 12 bits (since 212 = 4,096) say where within the page (the offset). Translation replaces the page number with a frame number and keeps the offset.

Who does what: hardware versus kernel

The work is split cleanly. The kernel decides policy: which virtual pages a process may have, which frame each one goes in, what permissions it gets, and it writes all of that into the page tables, which live in ordinary memory. The hardware does the per-access work: on every load, store and instruction fetch, the MMU translates the address using those tables, checks the permission bits and, if anything is wrong or missing, raises a page fault so the kernel can decide what to do. The kernel is not involved in normal translations at all, which is the only way translation can happen billions of times per second. When the kernel switches processes, it simply tells the MMU where the new process's tables are.

Three things to carry forward. First, isolation is automatic: a process can only reach frames its page table points to. Second, sharing is cheap: map the same frame into two page tables (shared libraries, os12's shared memory). Third, pages that are never touched need no frame at all, which os8 and os9 exploit for lazy allocation, swapping and copy-on-write.

1. Before paging: base and bounds

The simplest hardware translation uses two registers per running process: a base and a bound (limit). Every address the program uses is checked against the bound, then added to the base. Suppose a process is loaded at physical 32 KiB (base = 32,768) with 16 KiB of memory (bound = 16,384):

  • Virtual 1,000 → 1,000 < 16,384, so physical 32,768 + 1,000 = 33,768.
  • Virtual 15,000 → physical 47,768.
  • Virtual 20,000 → exceeds the bound → exception; the kernel kills the process. This is the ancestor of the "segmentation fault".

This gives relocation (the program can live anywhere) and protection (it cannot reach outside its range), and it is fast: one comparison and one addition. The kernel just reloads the two registers on each context switch. But each process needs one contiguous block of physical memory sized for its whole address space, including the unused gap between heap and stack. As processes start and exit, free memory breaks into holes between allocations, and eventually a new process cannot fit anywhere even though enough total memory is free. That is external fragmentation, and fixing it means moving processes around (compaction), which is slow.

2. Segmentation

Segmentation generalises base and bounds to several regions per process, called segments: typically code, heap and stack, each with its own base, limit and permissions (code read-only and executable, stack growing downwards). The top bits of an address, or the instruction type, select the segment. Now the gap between heap and stack costs nothing, and code segments can be shared between processes running the same program, marked read-only.

But each segment still needs contiguous physical memory, so external fragmentation remains, and growing a segment may require moving it. Segmentation survives mostly in vocabulary: a segmentation fault (SIGSEGV) is still what Linux delivers for an invalid memory access, decades after x86-64 stopped enforcing segment limits in 64-bit mode.

3. Paging: the address split

Paging gets rid of contiguity by using fixed-size units. Take a 32-bit address space with 4 KiB pages: the low 12 bits are the offset, and the high 20 bits are the virtual page number, so there are 220 (about a million) virtual pages. Translate the virtual address 0x00403A7C:

  1. Split: VPN = 0x00403 (the top 20 bits), offset = 0xA7C (the low 12 bits).
  2. Look up entry 0x403 in the page table. Say it holds frame number 0x1F2 and is marked present, user-accessible and writable.
  3. Check permissions against the access (a user-mode write, here): allowed.
  4. Physical address = frame number followed by the offset = 0x1F2A7C.

The offset is copied unchanged because pages and frames are the same size: byte 0xA7C of the page is byte 0xA7C of the frame. Any page can go in any free frame, so allocation is trivial (keep a list of free frames) and there is no external fragmentation. The cost is internal fragmentation (a 10 KiB region occupies three pages, wasting 2 KiB in the last), plus the page table itself and the time to consult it.

4. What a page-table entry holds

Each page-table entry (PTE) is 8 bytes on x86-64. Besides the frame number, it carries bits the hardware checks or sets on every access:

BitMeaningUsed for
PresentThe page is in a frame right nowIf clear, any access raises a page fault (os8)
WritableWrites allowedRead-only code and data; copy-on-write (os9)
User/SupervisorUser mode may access itHiding kernel memory from programs (os1)
AccessedSet by hardware on any accessApproximating LRU when choosing pages to evict (os8)
DirtySet by hardware on a writeKnowing which pages must be written back before reuse
No-execute (NX)Instruction fetches forbiddenNon-executable stacks and heaps
GlobalSame in every address spaceKernel mappings that survive TLB flushes

A violation (writing a read-only page, user code touching a supervisor page, executing an NX page, touching a non-present page) raises a page fault. The kernel's handler decides whether it is legitimate (load the page, copy it for copy-on-write, grow the stack) or an error (send SIGSEGV). That one mechanism underlies much of os8 and os9.

5. Why page tables are trees

A flat table indexed by VPN must have an entry for every possible virtual page, used or not. For 32-bit addresses: 220 entries × 4 bytes = 4 MiB per process, already uncomfortable with hundreds of processes. For 64-bit x86 with 48-bit virtual addresses: 236 entries × 8 bytes = 512 GiB per process. Impossible. Yet a typical process uses only a few small islands of its address space (code near the bottom, heap above it, libraries and stack near the top).

The solution is a multi-level page table, a tree. Split the VPN into several indexes. The top-level table has entries pointing to second-level tables, which point to third-level tables, and so on; only the bottom level holds frame numbers. If a whole region is unused, its upper-level entry is simply marked not present, and none of the tables below it exist.

x86-64 with 4 KiB pages uses four levels. Each table is exactly one 4 KiB page holding 512 eight-byte entries, so each level consumes 9 bits of the address (29 = 512): 9 + 9 + 9 + 9 + 12 = 48 bits. Linux calls the levels PGD, PUD, PMD and PTE (with a P4D level that only exists in 5-level mode); Intel calls them PML4, PDPT, PD and PT.

How much does a real process need? A process with 1 GiB of memory mapped contiguously needs 262,144 last-level entries (1 GiB / 4 KiB), filling 512 last-level tables of 4 KiB each, 2 MiB, plus one L2 table, one L3 and one L4: just over 2 MiB, about 0.2% of the mapped memory. You can see the total for the whole system in /proc/meminfo as PageTables.

Newer Intel and AMD server CPUs support 5-level paging (57-bit virtual addresses, 128 PiB), which Linux enables on hardware that has it, for machines with more than 64 TiB of physical memory or applications that need huge virtual spaces. The cost is one more level per walk.

6. The TLB: making translation fast

Done naively, every memory access would need four extra memory reads to walk the tree, making programs several times slower. The fix is the translation lookaside buffer (TLB), a small cache inside the CPU that holds recent VPN → frame translations together with their permission bits. On every access the MMU checks the TLB first, in parallel with starting the cache lookup. A hit costs essentially nothing. A miss triggers a page walk: on x86 and ARM, dedicated hardware reads the four levels (usually finding them in the L1 or L2 cache) and refills the TLB. Only if the walk finds a non-present or forbidding entry does the kernel get involved, through a page fault.

Modern x86 cores have a two-level TLB: an L1 data TLB of roughly 64-96 entries and a shared L2 TLB of roughly 1,500-3,000 entries (exact sizes vary by generation), plus separate instruction TLBs and smaller arrays for huge pages. The number that matters is TLB reach: entries × page size. With 2,048 entries of 4 KiB, reach is 8 MiB. A program whose hot data fits in 8 MiB rarely misses; a database scanning a 50 GB buffer pool, or a JVM chasing pointers across a 64 GB heap, misses constantly.

The classic exam calculation, effective access time: with a TLB lookup of 1 ns, a memory access of 100 ns, a 4-level walk that goes to memory each time and a 99% hit rate:

hit:  1 + 100                 = 101 ns
miss: 1 + 4 × 100 + 100       = 501 ns
EAT = 0.99 × 101 + 0.01 × 501 = 99.99 + 5.01 = 105 ns

So 1% misses cost about 5% extra; 5% misses (EAT ≈ 121 ns) cost over 20%. Real hardware does better than this worst case, because page-table entries are cached and page-walk caches remember upper-level entries so most walks only read one or two levels, but the shape of the trade-off is right: hit rate is everything.

7. The TLB and context switches

When the kernel switches to another process, it loads the new process's top-level table address into CR3 (os1). Old TLB entries now describe the wrong address space. Older CPUs simply flushed the TLB on every CR3 write, so each switch was followed by a burst of misses. Modern CPUs tag entries with an address-space identifier, PCID on x86 and ASID on ARM, so entries from several recent processes can coexist and only matching ones are used. Kernel mappings, identical in every process, are marked global so they survive switches (except when KPTI is active, os1). Switching between threads of the same process does not change CR3 at all, one reason thread switches are cheaper.

The TLB also complicates changing mappings. If the kernel unmaps or changes a page on one CPU, other CPUs may still have the old translation cached. The kernel must send an inter-processor interrupt to each CPU that might be using that address space, telling it to invalidate the entry, a TLB shootdown. Shootdowns cost microseconds and scale with CPU count, which is why frequent munmap or mprotect calls in heavily threaded programs show up in profiles.

8. Huge pages

The tree offers a shortcut: an entry at level 2 can point directly to a 2 MiB physical region instead of to a level-1 table, and an entry at level 3 can map a 1 GiB region. These are huge pages. One 2 MiB page covers what 512 small pages would, using one TLB entry and no level-1 table. TLB reach jumps from megabytes to gigabytes, and page-table memory drops by about 512 times for that region.

The costs: memory is now allocated in 2 MiB chunks (more internal fragmentation for small or sparse regions), the kernel must find 2 MiB of contiguous, aligned physical memory, which becomes hard on a long-running fragmented machine and may require compaction (moving pages around), and copy-on-write or swapping operates on 2 MiB at a time unless the huge page is split. Linux offers two mechanisms. hugetlbfs reserves explicit huge pages (vm.nr_hugepages) that applications request deliberately, as databases and DPDK do. Transparent huge pages (THP) let the kernel back ordinary anonymous memory with 2 MiB pages automatically, either everywhere (always) or only where the application asks with madvise(MADV_HUGEPAGE) (madvise mode); a background thread, khugepaged, collapses small pages into huge ones. The production section covers when THP helps and when it hurts.

9. The full layout, with the kernel on top

On x86-64 Linux with 48-bit addresses, the lower half of the address space (up to 0x00007fffffffffff, 128 TiB) belongs to the user process and the upper half (from 0xffff800000000000) to the kernel; addresses in the huge gap between are non-canonical and fault if used. Every process's page tables contain the same kernel mappings in the upper half, marked supervisor-only, which is what lets a system call run kernel code without switching page tables (KPTI aside). Within the user half, ASLR (address space layout randomisation) places the executable, heap, libraries and stack at random offsets on each run, so an attacker cannot hard-code addresses. Turn it off for one run with setarch -R ./program and the addresses become repeatable, as in this lesson's opening.

Translation in virtual machines: the two-dimensional walk

Inside a VM there are two translations: the guest's page tables map guest-virtual to guest-physical addresses, and the hypervisor maps guest-physical to host-physical. Early hypervisors maintained shadow page tables combining both, trapping every guest page-table update, which was slow. Modern CPUs do nested paging in hardware (Intel EPT, AMD NPT). The catch is the miss cost: each of the guest's four page-table reads is itself a guest-physical address that must be translated through the host's four-level table, and so is the final address. The worst-case walk is (4 + 1) × (4 + 1) − 1 = 24 memory references instead of 4. TLB misses therefore hurt much more inside VMs, which is why huge pages on both guest and host give larger wins for virtualised databases, and why page-walk caches have grown.

Inverted and hashed page tables

Some architectures took a different route to small tables. An inverted page table has one entry per physical frame (not per virtual page), recording which process and virtual page occupy it, so its size depends on RAM, not address-space size. Translation then needs a search, done with a hash table keyed by (process, VPN); IBM POWER used hashed page tables of this kind. The drawbacks are slower misses, awkward sharing (one frame mapped by two processes needs two entries in a structure with one slot per frame) and complex hardware. The radix-tree design won on x86 and ARM, and newer POWER CPUs added radix-tree support too.

Protection keys and memory tagging

Changing page permissions with mprotect requires a system call, page-table edits and TLB shootdowns. Intel memory protection keys (PKU) add a 4-bit key to each PTE and a per-thread register (PKRU) that says which keys are readable or writable; a thread can flip access to a whole group of pages with one unprivileged instruction, in tens of cycles. Databases and JITs use this to make data writable only during brief windows. ARM's memory tagging extension (MTE) goes further, storing a 4-bit tag per 16 bytes of memory and in the top bits of pointers, and faulting when they mismatch, which catches use-after-free and buffer overflows in hardware; Android uses it on supporting devices.

What the kernel does with the accessed and dirty bits

The hardware sets the accessed bit on any access and the dirty bit on any write, without kernel involvement. The kernel periodically clears accessed bits and checks later which were set again, a cheap way to estimate which pages are in active use, which page replacement relies on (os8). Clearing the bits requires flushing those TLB entries, otherwise the CPU would keep using the cached translation without setting the bit again. The dirty bit tells the kernel whether an evicted file-backed page must be written back to disk or can simply be dropped, which halves the I/O for clean pages. Linux's multi-generational LRU (since 6.1) scans these bits in page-table order for efficiency.

Why 4 KiB, and the move to bigger base pages

The 4 KiB page dates from the 1980s, when memories were measured in megabytes and wasting half a page per region mattered. Page size is a trade-off: larger pages mean fewer TLB misses, smaller page tables and fewer page faults when touching memory sequentially, but more internal fragmentation, coarser copy-on-write and more I/O when a page is swapped or read from a file. x86 is stuck with 4 KiB as its base size for compatibility, adding huge pages on top. ARM64 lets the operating system choose a 4 KiB, 16 KiB or 64 KiB base "granule": Apple's macOS on Apple silicon uses 16 KiB pages, and some Linux distributions for ARM servers ship 64 KiB-page kernels for big-memory workloads. Software that hard-codes 4,096 instead of asking the system (sysconf(_SC_PAGESIZE), os.sysconf("SC_PAGE_SIZE")) breaks on such systems, a real portability bug that affected allocators and databases during the move to ARM servers.

IOMMUs: translation for devices

Devices that read and write memory directly (DMA, os11) originally used physical addresses, so a buggy or malicious device, or a device passed through to a VM, could scribble anywhere. An IOMMU (Intel VT-d, AMD-Vi) gives devices their own page tables, translating device addresses to physical ones with permission checks, exactly as the MMU does for CPUs. It is what makes safe device passthrough to virtual machines and protection against malicious Thunderbolt devices possible, and it has its own TLB (the IOTLB) with the same miss and invalidation costs.

TLB misses as a hidden tax

Large-memory services (databases, caches, JVMs and Go programs with big heaps, graph and analytics engines) can spend a significant share of cycles on page walks without any single hot function in the profile. Measure it: perf stat -e dTLB-loads,dTLB-load-misses,iTLB-load-misses -p <pid> sleep 10, or on recent Intel parts the dtlb_load_misses.walk_active event, which counts cycles spent walking. If walk cycles are more than a few percent of total cycles, huge pages are worth trying. Large binaries with lots of code (big C++ servers) can suffer from instruction-TLB misses too, which is why some companies remap their hot code onto huge pages at startup.

Transparent huge pages: friend or foe

THP in always mode can speed up memory-heavy applications with no code changes, but has known failure modes. When the kernel cannot find a free 2 MiB region, a page fault may stall while it compacts memory synchronously (direct compaction), producing latency spikes of milliseconds or more. Sparse access patterns waste memory: touching one byte in each of a thousand 2 MiB regions consumes 2 GB instead of 4 MB. And a fork followed by writes copies 2 MiB per touched huge page (os2's Redis case). That is why Redis warns at startup when THP is set to always, MongoDB historically advised disabling it (newer versions on recent kernels recommend enabling it), and Oracle and PostgreSQL recommend explicit huge pages instead. A common compromise is madvise mode (applications opt in) with defrag set so faults do not compact synchronously. Watch AnonHugePages in /proc/meminfo, the thp_* and compact_stall counters in /proc/vmstat, and tail latency when changing these.

Page-table memory with many processes

Page tables are per process, so a large region shared by many processes is described many times. PostgreSQL is the textbook case: each client connection is a backend process that maps the shared buffer pool. With a 64 GB pool and 4 KiB pages, a backend that has touched the whole pool needs about 128 MB of page tables; 500 such backends could need 64 GB of page tables, as much as the pool itself. Symptoms are a huge PageTables value in /proc/meminfo and unexplained memory pressure. Configuring huge pages (huge_pages = on with vm.nr_hugepages sized to the shared memory) cuts that by 512 times; using a connection pooler to reduce backend count helps too.

Reading a segfault message

When a process dies with SIGSEGV, the kernel log often has a line like app[1234]: segfault at 0 ip 000055d4a1b2c3d4 sp 00007ffc... error 4 in app[55d4a1b00000+5000]. "at 0" is the faulting address: a NULL dereference. "ip" is the instruction that faulted; subtracting the mapping base shown at the end gives an offset you can look up with addr2line. The error code is a bit field from the page-fault exception: bit 0 set means the page was present (a permission violation rather than a missing page), bit 1 means a write, bit 2 means user mode, bit 4 means an instruction fetch. So error 4 is a user-mode read of an unmapped page, 6 a user-mode write to an unmapped page, 7 a user-mode write to a present but read-only page.

Virtual size is not memory use

Tools show several numbers per process. VSZ or VIRT is the total size of all mappings, which can be enormous (a Go or Java process reserving a big address range, ASAN reserving terabytes of shadow memory) without using any RAM. RSS is the memory actually resident in frames, counting shared pages fully in every process that maps them; PSS (in /proc/<pid>/smaps_rollup) divides shared pages among their users and is the fairer number for summing across processes. Alerting on VSZ is a classic false alarm; os9 covers what RSS does and does not include.

Find the TLB's reach on your own CPU by timing memory accesses as the number of pages touched grows. Linux, WSL or macOS with gcc or clang.

  1. Save as tlb.c: 
    #include <stdio.h>
#include <stdlib.h>
#include <time.h>
#define PAGE 4096
int main(void) {
    long sizes[] = {16, 64, 256, 1024, 2048, 4096, 16384, 65536, 262144};
    for (int s = 0; s < 9; s++) {
        long pages = sizes[s];
        char *buf = malloc(pages * PAGE);
        long *order = malloc(pages * sizeof(long));
        for (long i = 0; i < pages; i++) { buf[i * PAGE] = 1; order[i] = i; }
        for (long i = pages - 1; i > 0; i--) {            /* shuffle page order */
            long j = rand() % (i + 1), t = order[i]; order[i] = order[j]; order[j] = t;
        }
        long reps = 20000000 / pages + 1, sum = 0;
        struct timespec a, b; clock_gettime(CLOCK_MONOTONIC, &a);
        for (long r = 0; r < reps; r++)
            for (long i = 0; i < pages; i++) sum += buf[order[i] * PAGE];
        clock_gettime(CLOCK_MONOTONIC, &b);
        double ns = ((b.tv_sec - a.tv_sec) * 1e9 + (b.tv_nsec - a.tv_nsec)) / (reps * pages);
        printf("%7ld pages (%7ld KiB): %5.2f ns/access  [%ld]\n", pages, pages * 4, ns, sum % 7);
        free(buf); free(order);
    }
}
  2. Build and run: gcc -O2 tlb.c -o tlb && ./tlb.
  3. Optional on Linux: perf stat -e dTLB-load-misses ./tlb, and compare grep -E "PageTables|AnonHugePages" /proc/meminfo before and during a big run.

What to look for. Each access touches a different page in random order, one byte per page, so the data itself is tiny but every access needs a translation. With 16-64 pages, time per access is low (a few nanoseconds, everything hits the L1 TLB). It steps up once the page count passes the L1 TLB's size (around 64-100 pages), again once it passes the L2 TLB (around 1,500-3,000 pages on most x86 parts), and grows further at hundreds of thousands of pages, where page-table entries themselves stop fitting in the caches. Those steps are the TLB reach, measured. Note that cache misses also grow with the number of distinct lines touched, so not every bit of the slowdown is TLB; the perf counter confirms which part is.

Estimate and tune: the in-memory graph service

A graph service keeps a 48 GB adjacency structure in memory and answers queries by following pointers between nodes scattered across that memory. It runs as one process with 32 threads on a 64-core x86 server with 4 KiB pages and THP disabled. Profiling shows no dominant function, but perf stat reports that about 30% of cycles are spent in page walks. (a) Estimate the page-table size and compare the TLB reach with the working set. (b) Explain why walks are so expensive here. (c) Propose changes and say what you would measure.

Answer

(a) Sizes. 48 GB / 4 KiB ≈ 12.6 million pages, each needing an 8-byte last-level entry: about 96 MB of page tables (plus a little for upper levels). The L2 TLB holds on the order of 2,000 entries, a reach of about 8 MB. The working set is 48 GB, roughly 6,000 times the TLB reach, so practically every pointer hop to a random node misses the TLB.

(b) Why walks are expensive. Each miss walks four levels. The upper levels are few and stay cached, but the 96 MB of last-level page-table entries is far bigger than the CPU's last-level cache, so the final level of the walk often misses the cache and goes to DRAM, about 100 ns, before the data access itself, which also goes to DRAM. Pointer chasing makes it worse because each access depends on the previous one, so the CPU cannot overlap them. So a large share of each hop is spent on translation.

(c) Changes. Back the structure with 2 MiB huge pages: either THP in madvise mode with madvise(MADV_HUGEPAGE) on the arena (and allocate it early, before memory fragments), or explicit hugetlbfs pages reserved at boot. With 2 MiB pages: 48 GB / 2 MiB = 24,576 pages, 192 KB of page tables (fits comfortably in cache), and the TLB's 2 MiB entries (typically about a thousand of them in the shared TLB on recent Intel parts, fewer on older ones) reach gigabytes rather than megabytes. Walks become rare and short. 1 GiB pages would shrink this further if the allocator can use them, at the cost of reserving memory at boot. Also consider the NUMA placement of the arena (os3) and improving locality, for example by laying nodes out in BFS order so neighbours share pages.

Measure before and after: page-walk cycles as a share of total, dTLB miss rate, query throughput and p99 latency, AnonHugePages or HugePages_* in /proc/meminfo to confirm the memory really is huge-page backed, and compaction stalls if using THP.
