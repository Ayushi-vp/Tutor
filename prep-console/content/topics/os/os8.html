Open a large photo editor. Its executable and libraries are hundreds of megabytes on disk, but it is ready in a couple of seconds, long before that much could be read. Leave it in the background for a day while you run a compile and a browser with fifty tabs, and when you switch back it hesitates for a moment, the disk light flickers, and then it is fine. Behind both experiences is the same idea: the operating system does not keep a program's whole memory in RAM. It loads pages when they are first used and quietly moves unused ones out when memory is needed elsewhere.

This idea, virtual memory in its fullest sense, is what lets the sum of all programs' memory exceed physical RAM, lets programs start quickly, and lets the kernel use spare RAM to cache files. It also creates some of the worst performance cliffs in computing. When programs collectively need more memory than exists, the system starts thrashing: every process waits for pages that were just thrown out to make room for another process's pages. The machine is "busy" at 100% disk and almost no useful work. Anyone who has watched a laptop freeze while swapping, or a Kubernetes node go unresponsive for minutes before pods get killed, has seen it.

The topic is a staple of OS exams and interviews. Expect to trace FIFO, LRU and optimal replacement on a reference string, explain Belady's anomaly, describe what happens on a page fault, and compute effective access time with faults. Senior interviews ask what thrashing looks like on a real server, why swap is or is not a good idea, and why a service stalls under memory pressure with plenty of CPU.

This lesson covers demand paging and the page fault step by step, the cost of faults, the replacement algorithms with worked traces, Belady's anomaly, working sets and thrashing, and how Linux actually reclaims memory, then what to watch and tune in production.

A small desk and a big library

You are writing a report at a small desk (RAM) in a large library (disk). The desk holds only a dozen books. You don't carry every book you might need to the desk at the start; you fetch each one the first time you need it, which takes a walk to the shelves (a page fault). When the desk is full and you need another book, you must return one to the shelves first (replacement). Which one? Ideally one you won't need again soon. Return the dictionary you open every five minutes, and you'll be walking back for it immediately.

Now imagine three people sharing that desk, each needing ten books at once. Every time one fetches a book, another's book has to go back, which that person needs next. All three spend their time walking to the shelves and nobody writes anything. That is thrashing. The only fixes are a bigger desk or fewer people at it; walking faster barely helps.

The analogy breaks in two places. The "walk" is extremely long relative to normal work: reading a page from an SSD takes about 100 microseconds, a thousand times longer than a memory access, and from a spinning disk about 10 milliseconds, a hundred thousand times longer. And the computer cannot ask the program which pages it will need next; it can only guess from the past.

The mechanism in one picture

os7 showed that each page-table entry has a present bit. Demand paging uses it as a switch. A page that is not in RAM has present = 0, and the kernel remembers separately where its contents live: in the program file, in another file, in swap, or nowhere yet (fresh memory to be zero-filled). Touching it causes a page fault; the kernel brings it in, sets present = 1 and lets the program continue as if nothing happened.

Where an absent page actually lives

"Not present" can mean several different things, and the kernel's handling, and the cost, depends on which. A page of program code or of a memory-mapped file lives in that file on disk, and may also still be sitting in the kernel's page cache from an earlier read, in which case it can be mapped without any I/O. A page of heap or stack that has never been touched lives nowhere yet: the kernel hands over a zero-filled frame. A heap page that was evicted earlier lives in swap, a disk area reserved for anonymous memory, and must be read back. Keeping these cases in mind explains most of what follows: why first-touch faults are cheap, why re-reading a file is fast the second time, and why a system with no swap still has to evict something when memory is full.

Two questions drive the rest of the lesson: when RAM is full, which page do we throw out (replacement), and what happens when no choice is good because the programs simply need more memory than there is (thrashing)?

1. Demand paging from program start

When you run a program, execve (os2) does not read the executable into memory. It creates regions (Linux calls them VMAs, virtual memory areas) describing the address space: "addresses X to Y are the program's code, backed by this file at this offset, read and execute", "the heap starts here, anonymous, read and write", and so on. Page-table entries start out not present. The first instruction fetch faults; the kernel maps the page of code (reading it from disk, or from the page cache if the file was recently used); execution continues and faults on the next new page, and so on. A program that only uses a fraction of its code and data only ever loads that fraction.

The same applies to memory a program allocates. malloc(1 GB) succeeds instantly and uses almost no RAM: it creates an anonymous region. Each page is given a frame, filled with zeros, only when first written (os9). This is why a process's virtual size can be enormous while its resident size is small.

2. The page fault, step by step

  1. Trap. The MMU finds the entry not present (or the access forbidden) and raises a page-fault exception. The CPU records the faulting address (in the CR2 register on x86) and an error code saying whether it was a read or write, user or kernel, present or not.
  2. Find the region. The kernel looks up which VMA contains the address. None? The access is invalid: send SIGSEGV. Region exists but forbids the access (writing a read-only region)? Also SIGSEGV, unless it is a copy-on-write case (os9).
  3. Get a frame. Take one from the free list. If free memory is short, reclaim: choose a victim page using the replacement policy. If the victim is dirty, it must be written out first (to its file or to swap); its owner's page-table entry is set to not present and its TLB entry invalidated (os7).
  4. Fill the frame. Fresh anonymous memory: zero it. A file page: if it is already in the page cache (the kernel's cache of file contents), just map it, a minor fault. Otherwise issue a disk read, put the process to sleep, and run something else until the I/O completes: a major fault. A swapped-out page: read it back from swap, also major.
  5. Update the page table with the frame number and present = 1.
  6. Return from the exception. The CPU re-executes the instruction that faulted, which now succeeds.

Linux also does fault-around and readahead: when it faults in a file page, it maps neighbouring pages that are already cached and reads ahead sequential file data, betting on spatial locality so that the next accesses do not fault.

3. What faults cost: effective access time

Let p be the probability that an access causes a major fault. With a memory access time of 100 ns and a fault service time of 8 ms (a spinning disk plus overheads, the classic textbook figure):

EAT = (1 − p) × 100 ns + p × 8,000,000 ns ≈ 100 + 7,999,900 × p  ns

p = 1/1,000      →  EAT ≈ 8,100 ns      (81× slower than RAM)
p = 1/800,000    →  EAT ≈ 110 ns        (10% slower)

To keep the slowdown under 10%, fewer than one access in 800,000 may fault to disk. Even on an SSD (around 100 µs per fault), one fault per 10,000 accesses would roughly double the average access time. The lesson: page replacement does not need to be clever on average; it needs to make major faults extremely rare, which only works if the hot data fits in memory.

4. Where evicted pages go

Evicting a page means different things depending on what is in it:

Page typeIf cleanIf dirtyNext access
File-backed (code, mmapped files, page cache)Simply drop itWrite back to the file firstRe-read from the file
Anonymous (heap, stack)(zero pages: drop)Write to swapRead back from swap

So clean file pages are cheapest to evict: no I/O at all. Without swap configured, anonymous pages can never be evicted, so all reclaim pressure falls on file pages, including the code of running programs. Programs then fault their own code back in constantly, which is why "no swap" does not mean "no thrashing".

5. Replacement algorithms on a reference string

To compare algorithms, use a reference string (the sequence of pages accessed) and count faults for a given number of frames. Take 1 2 3 1 4 1 5 2 1 4 with 3 frames.

OPT (optimal, Belady's MIN). Evict the page whose next use is furthest in the future (or never). It is provably optimal, but needs the future, so it is only a yardstick.

FIFO. Evict the page that arrived first. Simple, with a queue, but blind to use: a page used constantly is evicted just because it is old.

LRU (least recently used). Evict the page unused for the longest time. It uses the recent past to predict the near future, which works because of locality: programs tend to reuse what they used recently.

6. Belady's anomaly

Intuition says more frames means fewer faults. For FIFO, not always. On 1 2 3 4 1 2 5 1 2 3 4 5, FIFO has 9 faults with 3 frames and 10 with 4. With four frames, FIFO's queue happens to line up so that it evicts each page just before it is needed again. LRU and OPT cannot show this anomaly, because they are stack algorithms: the set of pages they would hold with n frames is always a subset of the set with n + 1 frames, so an extra frame can only turn a miss into a hit. That property is one more reason real systems approximate LRU rather than use FIFO.

7. Approximating LRU: the Clock algorithm

Exact LRU would require recording a timestamp or moving a page to the front of a list on every memory access. Hardware does not do that, and software could not keep up. What hardware does provide is the accessed bit in each page-table entry, set automatically on any access (os7). The Clock (second-chance) algorithm uses just that bit. Arrange the frames in a circle with a "hand". To pick a victim:

  1. Look at the page under the hand.
  2. If its accessed bit is 1, it was used recently: clear the bit (give it a second chance) and move the hand on.
  3. If its accessed bit is 0, it has not been used since the hand last passed: evict it, put the new page in that frame, and advance the hand.

The enhanced Clock also looks at the dirty bit and prefers, in order: not accessed and clean (free to evict), not accessed and dirty (schedule a write-back, evict later), accessed and clean, accessed and dirty. Evicting clean pages first avoids I/O on the critical path. On the textbook string from section 5, simple Clock gets 14 faults, between FIFO's 15 and LRU's 12, about what you would expect from a one-bit approximation.

8. Locality, working sets and thrashing

Programs do not touch memory uniformly. In any short window they concentrate on a small set of pages: the current function's code, the stack, the data structures being worked on. Peter Denning formalised this in 1968 as the working set: the set of distinct pages a process referenced in the last Δ time (or Δ references). As long as each process's working set fits in its frames, faults are rare, occurring mainly when the program moves to a new phase.

Thrashing is what happens when the working sets of all running processes add up to more than physical memory. Each process faults, evicting a page another process needs right away, which then faults, and so on. Processes spend their time blocked on disk; CPU utilisation falls. A historic disaster made it worse: schedulers of the 1960s saw low CPU utilisation and admitted more processes to raise it, which shrank everyone's frames further and deepened the collapse.

The cures all reduce demand relative to memory. The working-set model only runs a process if its working set fits; otherwise it is suspended (swapped out entirely) until there is room. The page-fault-frequency approach watches each process's fault rate: above an upper threshold it gets more frames (or, if none are available, a process is suspended); below a lower threshold it gives frames back. Modern systems add memory limits per group of processes (cgroups, os13), and, as a last resort, kill a process (os9's OOM killer).

9. How Linux reclaims memory

Linux does not use textbook Clock directly. For each NUMA node and memory cgroup, it tracks file pages and anonymous pages separately. The classic design keeps two lists for each: an inactive list of candidates for eviction and an active list of pages that have proved themselves by being accessed again. New pages start on the inactive list; a second access promotes them; reclaim scans from the old end of the inactive list, evicting pages whose accessed bit is clear and giving referenced pages another chance; and pages are demoted from active to inactive to keep the lists balanced. Since Linux 6.1, the multi-generational LRU (MGLRU) replaces the two lists with several age generations and finds accessed bits by scanning page tables in bulk, which cut reclaim CPU cost and improved decisions on many workloads.

When reclaim happens is governed by watermarks on free memory per zone. Below the low watermark, the background thread kswapd wakes and reclaims until free memory reaches the high watermark. If allocations outpace it and free memory falls to the min watermark, the allocating process must reclaim itself before it can continue, direct reclaim, which shows up as latency. How the kernel balances evicting file pages versus swapping anonymous ones is biased by vm.swappiness (default 60; 0 strongly prefers file pages, up to 200 for fast swap like zram) and adjusted by feedback about refaults, pages that were evicted and then needed again soon, a sign that list was being cut too deeply.

Why LRU is not always right: scans and frequency

LRU's weakness is a large one-time scan. A backup reading a 100 GB file once, or a query scanning a big table, touches every page exactly once; under pure LRU each newly read page is "most recent", so the scan flushes the genuinely hot data out of memory, and then the scan's pages are never used again. Solutions separate pages that have been used once from those used repeatedly. Linux's inactive list does this: a page needs a second access to be promoted to active, so a single scan cycles through the inactive list without disturbing the active set. Database buffer pools use similar tricks: PostgreSQL uses small ring buffers for large sequential scans so they do not evict shared buffers; MySQL's InnoDB inserts new pages at the midpoint of its LRU list. Research algorithms such as 2Q, ARC (adaptive replacement cache, which balances recency and frequency and was used in ZFS) and CLOCK-Pro formalise the same idea.

Stack algorithms and why Belady's anomaly cannot hit LRU

An algorithm has the inclusion property if, for every reference string, the pages it keeps with n frames are always a subset of those it keeps with n + 1 frames. LRU has it: with n frames it holds the n most recently used pages, which are among the n + 1 most recently used. OPT has it too. Any algorithm with the property, called a stack algorithm, can never fault more with more frames, because every hit with n frames is also a hit with n + 1. FIFO lacks it because its contents depend on arrival order, which changes with the number of frames. This analysis (Mattson et al., 1970) also gives a practical tool: from one pass over a trace, a stack algorithm's fault count for every memory size can be computed at once, which is how cache-sizing tools build miss-ratio curves.

Major faults are I/O, so I/O scheduling matters

A major fault is a small random read, and under memory pressure many processes issue them at once. On spinning disks each costs a seek; random 4 KiB reads at 100-200 per second can make a thrashing machine take minutes to respond to a keypress. On SSDs and NVMe the raw cost is much lower, so modern systems degrade more gracefully, but writing dirty anonymous pages to swap adds write traffic, and swap readahead (reading neighbouring swap slots) helps only when swapped pages are related. Compressed in-memory swap changes the economics: zram stores swapped pages compressed in RAM (often 2-3:1), so a "swap-in" costs a decompression of a few microseconds instead of I/O; Android, ChromeOS and Fedora use it by default. zswap is a compressed cache in front of a real swap device.

User-space fault handling: userfaultfd

Linux lets a process handle page faults for a region itself. With userfaultfd, faults on registered pages are reported to a user-space thread through a file descriptor; that thread fetches the data from anywhere (another machine's memory, a snapshot, a compressed store) and installs the page. This powers post-copy live migration of virtual machines (the VM starts running on the new host before its memory arrives; pages are pulled over the network on first touch), fast VM and container snapshot restore (Firecracker), and some garbage collectors. It is demand paging with the backing store replaced by your own code.

Telling the kernel what you know: madvise

Replacement and readahead are guesses; applications can improve them. madvise(MADV_SEQUENTIAL) on a mapping says "I will read this once, in order", so the kernel reads ahead aggressively and drops pages soon after use; MADV_RANDOM disables readahead, which wastes I/O for random lookups into a big mapped index; MADV_WILLNEED starts reading pages in before they are touched; MADV_DONTNEED and MADV_FREE tell the kernel that anonymous pages can be discarded (memory allocators use these to return freed memory, os9). Databases and search engines that memory-map large files tune these hints, and choosing wrongly shows up as either wasted disk bandwidth or extra major faults.

Memory cgroups change the unit of reclaim

On a shared host, global LRU would let one container's scan evict another container's hot pages. Memory cgroups (os13) keep separate LRU lists per group, so a group that exceeds its memory.high is throttled and reclaimed first, and one that hits memory.max reclaims from itself and, failing that, has a process OOM-killed inside the group. memory.low and memory.min protect a group's working set from reclaim caused by others. This turns thrashing from a machine-wide collapse into a per-workload problem, which is what made dense container packing workable.

Recognising memory pressure

"Free" memory near zero is normal on Linux, because the kernel fills spare RAM with page cache; look at MemAvailable in /proc/meminfo (an estimate of how much could be freed without swapping) instead. Signs of real pressure: vmstat 1 showing non-zero si/so (swap in and out per second) persistently; a rising major-fault rate (sar -B shows majflt/s, and per process ps -o maj_flt or pidstat -r); pgscan and pgsteal counters climbing in /proc/vmstat, especially allocstall and pgscan_direct (direct reclaim); kswapd using significant CPU; and PSI. Pressure stall information (/proc/pressure/memory, and memory.pressure per cgroup) reports the share of time in which some tasks (some) or all non-idle tasks (full) were stalled waiting for memory. A sustained full avg10 above a few percent means the workload is losing real time to reclaim.

The thrashing node

A classic Kubernetes incident: a node with swap off gets close to full because pods have generous or missing limits. The kernel cannot swap anonymous memory, so it evicts page cache, including the executable code of every process, which then refaults from disk. The node's disk read rate soars, load average climbs into the hundreds (tasks in D state waiting on I/O count, os2), SSH takes minutes, the kubelet itself stalls and the node goes NotReady. The kernel OOM killer does not fire because reclaim is technically still making progress. Fixes: accurate memory requests and limits so pods hit their own cgroup limit early; kubelet eviction thresholds (memory.available) and system-reserved/kube-reserved so the node keeps headroom; and PSI-based user-space OOM handling (systemd-oomd, Meta's oomd) that kills on sustained pressure rather than on total failure. Kubernetes long required swap to be off; newer versions support it as an opt-in, which with limits can absorb cold memory more gracefully.

Swap: tune it, don't fear it

On servers, a modest amount of swap (or zram) lets the kernel move genuinely cold anonymous memory (startup data, leaked-but-never-touched allocations) out of the way and keep more page cache, and gives a gradual warning slope instead of a cliff. What you must avoid is the hot working set being swapped. Use vm.swappiness to bias reclaim (lower values protect anonymous memory; for latency-critical services, 1-10 is common), and protect critical processes: mlockall() or cgroup memory.min/memory.low so their memory is not reclaimed. Garbage-collected runtimes need special care because a collection touches the whole heap: Elasticsearch documents bootstrap.memory_lock and recommends disabling swap for its JVM, and the general advice is to size heaps well below physical memory.

Latency from the page cache

Even without swap, page-cache eviction causes latency surprises: a service whose data files are memory-mapped or read through the page cache is fast while its working set is cached and suddenly slow after a big batch job, backup or log rotation evicts it. Symptoms are a burst of major faults or disk reads at the start of the day or after a deploy. Remedies include warming caches on startup, isolating batch jobs in cgroups with memory limits (so their page cache is reclaimed within their own group), using O_DIRECT or posix_fadvise(POSIX_FADV_DONTNEED) for one-pass streams, and reserving memory for the hot set with memory.low.

Direct reclaim and compaction stalls

When kswapd cannot keep up with allocation bursts, processes enter direct reclaim and stall, sometimes for tens to hundreds of milliseconds; a request that needs a high-order (multi-page) allocation may also trigger synchronous compaction. Tail latency spikes with no CPU explanation and rising allocstall or compact_stall counters are the signature. Raising vm.watermark_scale_factor (and, carefully, vm.min_free_kbytes) makes kswapd start earlier and keep more headroom; reducing large allocations and THP's synchronous defragmentation (os7) removes compaction stalls.

    frames, faults = [], 0

def lru(refs, n):
    frames, faults = [], 0            # least recently used at the front
    for p in refs:
        if p in frames: frames.remove(p)
        else:
            faults += 1
            if len(frames) == n: frames.pop(0)
        frames.append(p)
    return faults

def opt(refs, n):
    frames, faults = [], 0
    for i, p in enumerate(refs):
        if p in frames: continue
        faults += 1
        if len(frames) < n: frames.append(p); continue
        future = refs[i + 1:]
        victim = max(frames, key=lambda q: future.index(q) if q in future else 10**9)
        frames[frames.index(victim)] = p
    return faults

Diagnose: the nightly slowdown

A search service runs on 64 GB machines. Its index files (40 GB) are memory-mapped, and its JVM heap is 12 GB. Swap is 8 GB with default swappiness. Every night at 02:00 a backup job reads 200 GB of data files sequentially and sends them to object storage. From about 02:10 until mid-morning, p99 latency is three times higher than usual; CPU is normal. Overnight graphs show disk reads on the index volume jumping from near zero to thousands per second after 02:00, and a few hundred MB of swap in use by morning. Explain the mechanism and propose fixes.

Answer

Mechanism. The index is served from the page cache through memory mapping: queries are fast only while the hot parts of those 40 GB stay resident. The backup reads 200 GB of other files once, and every page it reads enters the page cache, which is shared machine-wide. Memory is full, so reclaim must evict something for each new backup page. The backup's pages are new and recently used, while some index pages have not been touched in the last few minutes, so index pages get evicted (a second access promotes pages to the active list, but less frequently used index pages sit on the inactive list and go first). After the backup, queries touch evicted index pages and take major faults: random reads on the index volume, the disk-read spike in the graphs, and latency triples. The cache only refills as queries happen to touch each page, which takes hours for the colder parts of the index, hence the slow recovery into the morning. The few hundred MB of swap are cold JVM heap or other anonymous pages swapped out as part of the same pressure; harmless unless the GC touches them, in which case they add GC pauses.

Confirm. sar -B or pidstat -r for major faults on the search process after 02:00; vmtouch or fincore on the index files before and after the backup to see how much is resident; /proc/pressure/memory during the backup.

Fixes. Stop the backup from polluting the cache: run it in its own cgroup with a memory.max or memory.high of a few GB, so its page cache is reclaimed within its own group; or have it read with O_DIRECT or call posix_fadvise(..., POSIX_FADV_DONTNEED) after each chunk. Protect the service: put it in a cgroup with memory.low set to cover the hot index plus heap, so reclaim prefers other memory. Lower swappiness for this host and lock the JVM heap (or disable swap for that cgroup) so GC never touches swapped pages. Optionally warm critical index files after the backup (vmtouch -t). Measure p99 and major faults the next night to confirm.
