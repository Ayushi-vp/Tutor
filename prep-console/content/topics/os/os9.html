A service's memory graph climbs during the day, as expected, and then stays at the peak all night although traffic has dropped to almost nothing. A Python worker processes a large file, deletes every reference to the data, calls the garbage collector, and still reports 3 GB resident. A Java container with a 2.5 GB heap keeps getting killed for exceeding its 4 GB limit although the heap never fills. A machine with plenty of "free" memory refuses to start a process; another, with none, happily lets a program allocate 100 GB. And sometimes, in the middle of the night, the kernel picks a perfectly healthy database and kills it.

All of these are consequences of how memory is allocated, which happens at two levels. The kernel hands out memory to processes in page-sized pieces, lazily and often optimistically. Inside each process, an allocator (malloc in C, and the runtimes of Python, Java and Go built on similar ideas) carves those pages into objects of every size and decides when, if ever, to give pages back. Between them sit copy-on-write, which makes fork cheap and memory accounting confusing, and the OOM killer, the last resort when promises cannot be kept.

Interviews probe this from both ends. Classic questions: "what happens when you call malloc?", "what is fragmentation?", "explain copy-on-write", "how does the buddy system work?". Senior questions: "why does this service's memory never come down?", "why was this container OOMKilled?", "what is overcommit and should we disable it?", "design an allocator for this workload".

This lesson follows memory from the kernel to your objects and back: brk and mmap, overcommit, how malloc works inside (free lists, size classes, arenas), fragmentation and why freed memory stays, the kernel's own buddy and slab allocators, copy-on-write in detail, and the OOM killer, then how to diagnose memory growth in production.

Wholesale and retail

Think of memory allocation as two shops. The kernel is a wholesaler: it sells memory only in large, page-aligned lots (4 KiB at the smallest, usually much more), and each purchase is a system call, which is relatively slow. The allocator inside your process is a retailer: it buys wholesale lots and sells them to your code in any size you like, 24 bytes here, 3 KiB there, quickly, with no system call. When you return an item (free), the retailer puts it back on its own shelves for the next customer; it rarely sends anything back to the wholesaler. That one fact explains most "my memory never goes down" mysteries.

The analogy breaks in a helpful way. The wholesaler does not even deliver the goods when you buy them. Buying a lot only reserves addresses; the kernel puts real memory behind each page the first time you touch it (os8's demand paging). So a process can "own" 10 GB of address space while using 100 MB of RAM.

Three ideas to hold on to

Lazy, optimistic allocation. The kernel reserves address space instantly and backs it with frames only when touched. By default Linux even promises more than it has (overcommit), which works because most programs never touch everything they allocate: a thread reserves an 8 MB stack and uses 40 KB of it; a runtime reserves a large range to keep its heap contiguous. The catch is that a promise is not a guarantee, and the bill can arrive at an awkward moment, during an ordinary memory write rather than during the allocation call.

Copy-on-write. When memory is duplicated, by fork or by mapping a file privately, the kernel shares the pages read-only and copies a page only when someone writes to it. It makes process creation cheap and lets many processes share one copy of a program's code and unchanged data. It also makes the question "how much memory does this process use?" surprisingly hard to answer, because a page may belong to several processes at once.

The OOM killer. If the promises come due and reclaim (os8) cannot free enough, the kernel has no failed system call to report the problem through, so it kills a process instead. Which process dies is a policy decision you can influence, and in containers the decision is made per group of processes against the group's own limit.

What each layer costs

The layers differ hugely in speed. A small malloc served from a per-thread cache costs around 10-20 nanoseconds. One that has to take a lock and search the allocator's free lists costs more. One that needs fresh memory from the kernel costs a system call (os1) plus, later, one page fault per 4 KiB page touched, each with the kernel zeroing a page. That is why allocators buy from the kernel in big pieces and hoard what they get, and why the patterns in this lesson, keeping memory rather than returning it, are deliberate trade-offs of memory for speed rather than bugs.

1. Getting memory from the kernel: brk and mmap

A process's classic heap sits just above its data segment, and its top is called the program break. brk (or the older sbrk(increment)) moves the break up to grow the heap or down to shrink it. Simple, but the heap must be contiguous, so it can only shrink from the top.

mmap is the general tool: map a region of a given length anywhere in the address space, either anonymous (zero-filled memory with no file) or backed by a file, and either private or shared. munmap removes it. Allocators use anonymous mmap for large blocks and for whole arenas, because each mapping can be released independently.

Neither call allocates physical memory. Both create or extend a virtual region (a VMA, os8) and return. The first read of an untouched anonymous page maps the shared zero page, a single read-only page of zeros; the first write faults again and gets a private zeroed frame. You can watch this: malloc(1 GB) returns in microseconds, and the process's RSS (resident set size) only grows as you write to the memory, about 262,144 minor faults for the whole gigabyte.

2. Overcommit: promising more than you have

If the kernel only reserves address space, how much should it let processes reserve? Linux's answer is set by vm.overcommit_memory:

ModeBehaviourConsequence
0 (default, heuristic)Refuse only requests obviously larger than RAM plus swapMost allocations succeed; shortage shows up later as OOM kills
1 (always)Never refuseUseful for sparse workloads; maximum OOM risk
2 (strict)Refuse once committed memory would exceed CommitLimit = swap + RAM × overcommit_ratio/100 (ratio defaults to 50)malloc can fail with NULL; OOM kills become rare

Why overcommit at all? Because programs reserve far more than they use: thread stacks reserve 8 MB each but touch kilobytes; runtimes reserve large address ranges; and fork of a 20 GB process would need another 20 GB of commitment under strict accounting, even if the child immediately calls exec. /proc/meminfo shows Committed_AS (total promised) and CommitLimit; on a typical desktop, Committed_AS exceeds physical RAM comfortably.

3. Inside malloc: blocks, headers and free lists

An allocator must answer two questions fast: where is a free block of at least n bytes, and how big was the block being freed? The basic design: every block (glibc calls them chunks) carries a small header with its size, and free chunks are linked into free lists. In glibc on 64-bit systems the size field takes 8 bytes and chunks are multiples of 16 bytes, so malloc(24) gets a 32-byte chunk; malloc(1) also gets 32, the minimum. That rounding is internal fragmentation.

Two operations keep the heap usable:

  • Splitting: to serve a 100-byte request from a free 1,000-byte chunk, cut off what is needed and put the remainder back on a free list.
  • Coalescing: when a chunk is freed and its neighbour is also free, merge them into one larger free chunk, so the heap does not degrade into tiny pieces. The header (and, for free chunks, a footer) lets the allocator find neighbours' sizes in constant time.

Which free block to pick? First fit takes the first big-enough block (fast, but small fragments pile up at the front); best fit takes the smallest big-enough block (less waste per request, but leaves tiny unusable slivers and needs searching); next fit continues from where the last search ended. Real allocators avoid searching altogether by keeping separate lists per size range, called bins or size classes, so a request goes straight to the list that can serve it.

4. glibc malloc in practice

glibc's allocator (ptmalloc) layers several mechanisms:

  1. tcache: a small per-thread cache of recently freed chunks per size (up to 7 per size, for chunks up to about 1 KiB), checked first with no locking at all.
  2. Bins: per-arena free lists for small sizes (exact sizes), large sizes (ranges, sorted), plus an "unsorted" list where freed chunks wait briefly so they can be reused immediately or coalesced.
  3. The top chunk: the free space at the end of the heap, split to serve requests no bin can; when it is exhausted the heap grows with brk, and when it grows large enough after frees (128 KiB by default, M_TRIM_THRESHOLD) the heap is trimmed back.
  4. Direct mmap for big requests: at or above the mmap threshold (128 KiB by default, raised dynamically up to 32 MiB as the program frees large blocks), the chunk gets its own mapping, and free unmaps it at once.
  5. Arenas: to reduce lock contention, threads are spread over multiple arenas, each with its own lock and heap; on 64-bit systems glibc allows up to 8 × (number of cores) arenas by default. MALLOC_ARENA_MAX caps this.

Here is a short trace on a fresh 64-bit process:

p = malloc(24)       # tcache/bins empty → split 32 bytes from the top chunk
q = malloc(5000)     # split 5,008 bytes from the top chunk
r = malloc(200000)   # ≥ 128 KiB → separate mmap of ~200 KiB (page-rounded)
free(p)              # 32-byte chunk → this thread's tcache
s = malloc(20)       # also a 32-byte chunk → served straight from tcache (s == p)
free(r)              # munmap: those pages go back to the kernel immediately
free(q)              # 5,008-byte chunk → unsorted bin; may coalesce with top

5. Fragmentation, and why memory does not come back

Suppose a program allocates 10,000 objects of 1 KiB (about 10 MB of heap) and then frees every other one. Now about 5 MB of the heap is free, in 5,000 holes of 1 KiB each, each sandwiched between live objects. A 2 KiB request cannot use any of them, so the heap grows. And the heap cannot be trimmed, because trimming only works from the top, where a live object sits. This is external fragmentation within the heap, and it is the main reason a long-running process's RSS stays near its historical peak.

Allocators fight this in several ways. Size classes keep like-sized objects together so holes are reusable by the next object of that size. Allocators can release whole free pages in the middle of the heap with madvise(MADV_DONTNEED) or MADV_FREE, which keeps the address range but drops the frames (glibc does this in malloc_trim(); jemalloc and tcmalloc do it routinely with decay timers). And programs can avoid the pattern by allocating long-lived and short-lived objects from different pools or arenas, so short-lived ones can be released wholesale.

6. Multithreaded allocators

A single heap with one lock would serialise every allocation in a 64-thread server (os4's contention problem). Modern allocators are designed around thread caches: each thread keeps free objects per size class and serves most requests from them without any locks, exchanging batches with a central pool only when its cache runs empty or overflows. jemalloc (FreeBSD's allocator, used by Redis and many large services), tcmalloc (Google's, with per-CPU caches using restartable sequences) and mimalloc (Microsoft's, with per-page free lists) all follow this pattern, and also organise memory into page-sized runs dedicated to one size class, which bounds fragmentation. The trade-off is memory held idle in caches per thread, and glibc's per-thread arenas, in particular, can multiply fragmentation in programs with hundreds of threads. Swapping allocators usually needs no code change: LD_PRELOAD=libjemalloc.so.

7. How the kernel allocates its own memory: buddy and slab

The kernel manages physical frames with the buddy allocator. Free memory is kept in blocks of 2order contiguous pages, from order 0 (4 KiB) to order 10 (4 MiB), with a free list per order. Worked example: a request for order 1 (8 KiB) when only an order-3 block (32 KiB, pages 0-7) is free:

  1. Split the order-3 block into two order-2 buddies: pages 0-3 and 4-7. Put 4-7 on the order-2 list.
  2. Split pages 0-3 into order-1 buddies: 0-1 and 2-3. Put 2-3 on the order-1 list.
  3. Return pages 0-1.

When pages 0-1 are freed, the allocator checks their buddy (2-3, found by flipping one bit of the block's page number). If it is free, they merge into 0-3, whose buddy 4-7 is also free, so they merge back into 0-7. Merging only equal-size buddies keeps it fast and limits fragmentation, though a long-running system still ends up with few high-order blocks free; /proc/buddyinfo shows the count per order, and compaction migrates pages to rebuild large blocks (needed for huge pages, os7).

On top of the buddy allocator sits the slab layer (SLUB on modern Linux). The kernel allocates millions of identical small objects (inodes, directory entries, socket buffers, task structures). A slab cache takes pages from the buddy allocator and divides them into slots of one object type, with per-CPU free lists for lock-free fast paths. kmalloc uses general caches of common sizes. slabtop shows which caches hold the most memory, the place to look when "used" memory is high but no process owns it (the dentry and inode caches after scanning millions of files are a common, reclaimable example).

8. Copy-on-write in detail

os2 introduced copy-on-write for fork. Here is the mechanism page by page:

  1. At fork, the kernel copies the parent's page tables for the child. For every private writable page, it clears the writable bit in both page tables and increments the frame's share count. Both processes now map the same frames, read-only.
  2. Reads by either process proceed normally: no fault, no copy.
  3. A write by, say, the child faults (writable bit clear). The kernel checks the region: it is supposed to be writable, so this is copy-on-write, not an error. If the frame is still shared, it allocates a new frame, copies the 4 KiB, maps the copy writable in the child, and decrements the original's share count. If the frame is no longer shared (the other process already copied or exited), it simply sets the writable bit again, no copy needed.
  4. The faulting instruction restarts and succeeds.

The same mechanism serves private file mappings (MAP_PRIVATE): a program's data segment is mapped from the executable copy-on-write, so every running instance shares the file's pages until it modifies a global variable. Copy-on-write is also why memory accounting after fork is confusing: both processes report the shared pages in their RSS, which is why PSS (os2, os7) exists.

9. When memory runs out: the OOM killer

When an allocation needs a frame and reclaim (os8) cannot free one after repeated attempts, the kernel invokes the OOM killer (out of memory). It cannot fail the allocation, because the "allocation" is often a page fault in the middle of some instruction, with no system call to return an error from. So it frees memory the only way left: by killing a process.

Choosing the victim. For each eligible process, the kernel computes a badness score: roughly the process's memory footprint (resident memory plus swap entries plus page-table pages) as a share of the memory available, scaled to 0-1000, plus the process's oom_score_adj (-1000 to +1000). The highest score dies with SIGKILL. -1000 means never kill (sshd and critical daemons often set it); /proc/<pid>/oom_score shows the current score. The kernel log records the event: "Out of memory: Killed process 4321 (java) total-vm:..., anon-rss:..., oom_score_adj:0".

In cgroups. Containers usually die from a cgroup limit rather than global exhaustion. When a cgroup reaches memory.max, the kernel first reclaims within the group (including its page cache); if that fails, it OOM-kills a process inside the group only. Kubernetes reports this as OOMKilled with exit code 137 (128 + signal 9). memory.high, set below max, throttles and reclaims a group before it reaches the hard limit, and memory.oom.group kills all processes in the group together, which suits services where a partial kill leaves a broken half.

How tcache and freed chunks become security bugs

Allocators keep their bookkeeping inside the freed memory itself: a free chunk's first bytes hold the pointer to the next free chunk. A use-after-free bug writes into such a chunk after free, overwriting that pointer, and a later malloc can be tricked into returning an attacker-chosen address, the root of many heap exploits. A double free puts the same chunk on a free list twice, so two later allocations overlap. glibc has added hardening over the years: checks for obvious double frees in tcache, "safe-linking" (since 2.32) that mangles free-list pointers with address bits so forged pointers fail alignment checks, and integrity checks on chunk sizes. Tools find these bugs before attackers do: AddressSanitizer replaces the allocator with one that keeps freed memory poisoned in quarantine and checks every access; production allocators such as Scudo (Android) and hardened_malloc trade some speed for randomisation and isolation.

Per-CPU caches and restartable sequences

Per-thread caches waste memory in programs with thousands of threads, most of them idle, each holding its own stash. tcmalloc's newer design uses per-CPU caches instead: a thread allocates from the cache of whichever CPU it is running on. The danger is being preempted or migrated halfway through updating that cache. Linux's restartable sequences (rseq) solve this: the thread registers a critical region, and if the kernel preempts or migrates it inside the region, it restarts the thread at an abort handler instead of resuming mid-update. The result is lock-free, atomic-free per-CPU operations with memory bounded by core count rather than thread count.

Arena allocation and region-based memory

When many objects share a lifetime, such as everything allocated while handling one request or compiling one function, freeing them individually is wasted work. An arena (region, bump allocator) allocates by bumping a pointer through a large block and frees everything at once by resetting the pointer. It is extremely fast and has zero fragmentation within its lifetime. Compilers, game engines (per-frame arenas), protobuf's arena option, and Postgres's memory contexts use it; Go and Java's young generation achieve a similar effect with bump allocation plus a copying collector.

Kernel same-page merging and memory deduplication

KSM (kernel same-page merging) scans memory regions that applications mark with madvise(MADV_MERGEABLE), finds pages with identical contents, and merges them into one copy-on-write page. It is useful for hosts running many similar VMs, where guest kernels and libraries are identical, saving substantial memory at the cost of scanning CPU. It has a security side effect: writing to a merged page takes longer (the copy), which leaks whether another process had an identical page, a timing side channel that led cloud providers to disable cross-tenant merging.

Garbage-collected runtimes sit on the same layers

Java, Go, .NET and JavaScript engines do not call malloc for each object. They reserve large regions with mmap and allocate objects inside them by bumping a pointer in a thread-local buffer, which is even faster than a thread-cached malloc. Freeing is done by the garbage collector in bulk. The kernel-facing behaviour is the same, though: the runtime decides when to hand memory back (the JVM's -XX:SoftMaxHeapSize and periodic uncommit in G1 and ZGC, Go's background scavenger returning pages with MADV_DONTNEED or MADV_FREE), and until it does, the pages count as resident. With MADV_FREE, freed pages stay counted in RSS until the kernel actually needs them, which is why Go programs once appeared to "leak" on Linux: RSS stayed high although the memory was reclaimable. Go 1.16 switched its default back to MADV_DONTNEED for clearer accounting.

NUMA placement: first touch

On multi-socket machines (os3), the kernel's default policy places a page on the NUMA node of the CPU that first touches it, not the one that allocated it. A program that initialises a big array from one thread puts all of it on one node, and then threads on the other socket access it remotely at higher latency and lower bandwidth. Solutions: initialise data in parallel from the threads that will use it, set policies with numactl --interleave=all or mbind, or let automatic NUMA balancing migrate pages towards their users (it samples accesses by temporarily unmapping pages, at some CPU cost). Databases often recommend interleaving their buffer pools.

Leak, fragmentation or cache?

"Memory keeps growing" has three common explanations, and the fix depends on which. A leak: live objects accumulate (unbounded caches, lists that are appended to forever, listeners never removed); heap profilers (heaptrack, jemalloc's profiling, tracemalloc in Python (py8), heap dumps in Java) show the growing call site. Fragmentation or allocator retention: live data is stable but RSS is not; compare the allocator's own statistics (malloc_info/malloc_stats in glibc, stats.allocated versus stats.resident in jemalloc) with RSS, and if "allocated" is flat while "resident" climbs, it is the allocator holding free memory. Cache: page cache or slab growth that is reclaimable under pressure; it appears in buff/cache or in a container's memory.stat as file, not in the process's anonymous RSS. /proc/<pid>/smaps_rollup breaks a process's memory into anonymous, file-backed, shared and swapped.

The glibc arena problem

Multithreaded programs on glibc, especially JVMs with many native threads and Python or Ruby servers with threads, can see native memory balloon because each of up to 8 × cores arenas fragments independently, and freed memory in one arena cannot serve another thread's requests. Two widely used mitigations: set MALLOC_ARENA_MAX=2 (or 4) in the environment, trading some contention for much lower fragmentation, or switch to jemalloc or tcmalloc with LD_PRELOAD. Many teams report RSS drops of tens of percent from either change; measure throughput too, since fewer arenas can increase lock contention.

OOMKilled containers

When a pod shows OOMKilled (exit 137), first establish whether it was the container's own limit or node pressure (the kubelet evicting pods shows up differently, as an eviction event). Then account for everything the cgroup counts: anonymous memory of every process in the container, page cache from files it read or wrote (reclaimable, but counted until reclaimed), kernel memory such as socket buffers, and tmpfs files (an emptyDir with medium: Memory lives in RAM). For JVMs, the heap is only part: metaspace, threads, code cache, direct buffers and native allocations need headroom; modern JVMs size the heap from the container limit (-XX:MaxRAMPercentage), and leaving 25% or more for non-heap use is common practice. Go programs can set GOMEMLIMIT so the GC works harder before the limit. Watch memory.events (high, max, oom, oom_kill counters) to see how close a container runs to its limit before it dies.

Protecting what matters from the OOM killer

On hosts that run a mix of workloads, set oom_score_adj so that the right thing dies: negative for critical daemons (systemd sets OOMScoreAdjust= per unit; Kubernetes assigns -997 to Guaranteed pods and up to 1000 to BestEffort pods), positive for batch work that can be retried. Because the kernel OOM killer acts late, after the system may have thrashed for minutes (os8), production fleets increasingly run user-space killers (systemd-oomd, oomd, earlyoom) that kill based on sustained memory pressure (PSI) or free-memory thresholds, which keeps the machine responsive.

Allocation in hot paths

Allocation is cheap but not free, roughly tens of nanoseconds for a cached small allocation, and much more when it falls through to locking, page faults or system calls. Latency-critical code (trading systems, packet processing, game loops, inference servers) avoids allocating in steady state: preallocate buffers, reuse objects through pools, use arenas per request. Profilers show the cost under names like malloc, _int_malloc, page_fault and clear_page (the kernel zeroing new pages). A burst of first-touch faults after startup or a big allocation also explains why a service is slow for its first few seconds; pre-touching memory (MAP_POPULATE, -XX:+AlwaysPreTouch in the JVM) moves that cost to startup.

Watch lazy allocation, copy-on-write and memory accounting in a real process. Linux or WSL with Python 3.

  1. Save as mem.py: 
    import mmap, os, time

def rss():
    with open(f"/proc/{os.getpid()}/status") as f:
        return next(l.split()[1] for l in f if l.startswith("VmRSS")) + " kB"

def roll(pid):
    out = {}
    with open(f"/proc/{pid}/smaps_rollup") as f:
        for l in f:
            k = l.split(":")[0]
            if k in ("Rss", "Pss", "Shared_Clean", "Shared_Dirty", "Private_Dirty"):
                out[k] = l.split()[1] + " kB"
    return out

size = 512 * 1024 * 1024
m = mmap.mmap(-1, size, flags=mmap.MAP_PRIVATE)   # private anonymous, untouched
print("after mmap:   ", rss())
for i in range(0, size // 2, 4096): m[i] = 1   # touch the first half
print("touched half: ", rss())

pid = os.fork()
if pid == 0:
    time.sleep(1)                           # shared with parent, copy-on-write
    print("child before:", roll(os.getpid()))
    for i in range(0, size // 4, 4096): m[i] = 2   # write a quarter
    print("child after: ", roll(os.getpid()))
    os._exit(0)
os.waitpid(pid, 0)
  2. Run python3 mem.py.
  3. Look at the system-wide numbers: grep -E "Committed_AS|CommitLimit|AnonPages|PageTables" /proc/meminfo and cat /proc/sys/vm/overcommit_memory.

What to look for. After mmap of 512 MiB, RSS barely moves: only address space was reserved. Touching half adds about 262,144 kB (256 MiB) to RSS, page by page (the extra beyond that is the interpreter). In the child before writing, its touched pages are shared with the parent: Shared_Dirty is around 256 MiB, and Pss is about half of Rss because each shared page is split between two processes. After the child writes a quarter of the mapping (the first 128 MiB, all inside the touched half), about 131,072 kB moves from shared to Private_Dirty: copy-on-write copied exactly the pages written, no more. Committed_AS is usually larger than physical RAM on a desktop, which is overcommit in action.

Diagnose: the API whose memory never comes down

A C++ API server (glibc malloc, 96 worker threads on a 24-core machine) handles bursty traffic. Each request builds a response of 50-500 KB in many small allocations, plus a few long-lived entries added to an in-memory cache (bounded at 1 GB). Daily RSS climbs from 2 GB at start to 9 GB at peak and stays at 9 GB overnight. Heap profiling shows live allocations of about 1.8 GB at peak and 1.3 GB at night. The container limit is 10 GB, and twice last month the process was OOMKilled during a traffic spike. Explain the gap between live memory and RSS, why it does not come down, and what you would change.

Answer

The gap. Live data is under 2 GB but RSS is 9 GB, so about 7 GB is memory the allocator holds but the program is not using: allocator retention and fragmentation, not a leak (the profiler would show growing live allocations for a leak). Three mechanisms combine. First, glibc arenas: 96 threads on 24 cores can use up to 8 × 24 = 192 arenas, so threads spread over many independent heaps; each grows to cover its share of the peak, and free memory in one arena cannot serve another. Second, interleaved lifetimes: request objects (short-lived) are allocated next to cache entries (long-lived) in the same heaps; when requests finish, their memory is free but scattered between pinned cache entries, so heaps cannot be trimmed from the top. Third, the dynamic mmap threshold: after the program frees some large blocks, glibc raises the threshold, so later 200-500 KB responses are carved from the heaps instead of using separate mappings that would have been returned on free.

Why it stays. Trimming only releases free memory at the top of each heap, and glibc does not routinely madvise away free pages in the middle. So RSS sits at the historical peak, and each new spike can push it higher if the new peak's allocation pattern does not line up with existing holes, eventually reaching the 10 GB limit: OOMKilled.

Changes. (1) Switch to jemalloc or tcmalloc (via LD_PRELOAD first, to test), which pack objects by size class and return free pages to the kernel with decay timers; or, staying on glibc, set MALLOC_ARENA_MAX=2-4 and call malloc_trim(0) periodically. (2) Separate lifetimes: allocate cache entries from a dedicated pool or arena, and build responses in a per-request arena that is reset when the request ends, so request garbage never fragments the long-lived heap. (3) Make the response buffer a single large allocation (or a reused buffer per thread) rather than many small pieces. (4) Pin the mmap threshold (M_MMAP_THRESHOLD) if large blocks should always be returned. Then measure: allocator stats versus RSS under a replayed day of traffic, peak RSS, latency and throughput, and the cgroup's memory.events.
