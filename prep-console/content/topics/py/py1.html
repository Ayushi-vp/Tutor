Here is a bug that has been written in almost every Python codebase at some point. A service loads a default configuration once at startup and hands it to each request handler:

DEFAULTS = {"retries": 3, "tags": []}

def handle(request):
    cfg = DEFAULTS                  # "take a copy of the defaults"
    cfg["tags"].append(request.user)
    ...

The author believed cfg = DEFAULTS made a copy. It did not. After a thousand requests, DEFAULTS["tags"] holds a thousand user names, every request sees every previous user's tag, and memory creeps upward until somebody restarts the process. Nothing crashed, no exception was raised, and the code looks perfectly reasonable if you think of a variable as a box that holds a value.

The same misunderstanding produces a family of related surprises: a function that "only reads" its argument but somehow changes the caller's list; a default argument that remembers values between calls; a grid built with [[0] * 3] * 3 where setting one cell changes a whole column; an object that goes into a dictionary and can never be found again; an if x is 5 check that works in a test and fails in production. Interviewers love these because they separate people who have memorised Python syntax from people who understand what the interpreter is actually doing.

All of them have one root cause and one fix: a correct mental model of how Python connects names to objects. Once you have it, you can predict the output of any of these puzzles instead of guessing, and you can design APIs that do not hand out shared state by accident.

This lesson builds that model from scratch. It starts with what an object is (identity, type and value), then what a name is and what assignment really does. It separates mutating an object from rebinding a name, sorts the built-in types into mutable and immutable, and uses that to explain argument passing and the mutable-default trap. Then it covers is versus == (and why small-integer caching makes is look like it works), shallow versus deep copies, and finally hashing: the contract that decides which objects can be dict keys and what goes wrong when it is broken. Every snippet was run on CPython 3.12.10 and the outputs shown are the real ones.

Labels, not boxes

In languages like C, a variable is a box: a named piece of memory that holds a value. Writing b = a copies whatever is in box a into box b, and from then on the two boxes are independent.

Python works differently. Every piece of data lives in an object somewhere in memory, and a variable is just a name — a label tied to an object with a piece of string. Writing a = [1, 2, 3] does two things: it creates a list object, and it ties the label a to it. Writing b = a does not create anything. It ties a second label, b, to the same object. There is one list with two labels on it.

a = [1, 2, 3]
b = a            # a second label on the SAME list
b.append(4)
print(a)         # [1, 2, 3, 4]  — a sees the change, because it is the same list
print(a is b)    # True          — "is" asks: same object?

The analogy is a person with a name and a nickname. If you give "Robert" a haircut, "Bob" has had a haircut too, because there is only one person. That is what just happened to the list: we changed it through one name and saw the change through the other.

Two kinds of objects

Some objects can be changed after they are created — lists, dicts, sets and most objects of classes you write. These are mutable. Others can never change: integers, floats, strings, tuples, None. These are immutable. When you seem to change an immutable object, as in s = s + "!", Python actually builds a new string and moves the label s onto it. The old string is untouched.

That distinction is why the label model sometimes feels invisible. With immutable objects, sharing is harmless: nobody can change the shared object, so it behaves exactly as if each name had its own copy. The surprises only happen with mutable objects, where one name can change something another name is looking at.

Two questions you can ask

Because names and objects are separate, "are these the same?" has two meanings. a == b asks whether the two objects have equal values. a is b asks whether the two names point at the very same object. Two lists built separately with the same numbers are equal but are not the same object. In day-to-day code you nearly always want ==; is is for checking against one-of-a-kind objects such as None.

Where the analogy breaks

Labels on objects is a good first picture, but two refinements come later in the lesson. First, the labels do not live on the object: they live in a namespace, a lookup table from names to objects that belongs to a module or to a running function. The object has no idea which names point at it; it only keeps a count of how many references there are. Second, names are not the only things that point at objects. A list's slots, a dict's values and an object's attributes are references too, so a list of lists is a web of arrows. That web is exactly what makes copying subtle, and it is the main thing to keep in mind for the rest of the lesson.

1. Every value is an object with an identity, a type and a value

The Python language reference defines an object as the thing that holds data, and says every object has three properties. Its identity never changes once it is created; you can think of it as the object's address, and the built-in id() returns it as an integer. In CPython — the standard interpreter, written in C, that you download from python.org — id() really is the memory address. Its type decides what operations it supports and also never changes; type() returns it. Its value is the data; for mutable objects the value can change while the identity and type stay the same.

a = [1, 2, 3]
print(type(a))            # <class 'list'>
print(id(a) == id(a))     # True — identity is stable
a.append(4)               # value changed; identity and type did not

Everything is an object: numbers, strings, functions, classes, modules, even None. That has practical consequences you will use constantly. Functions can be stored in a dict and called later (handlers = {"add": lambda a, b: a + b}; handlers["add"](2, 3) returns 5), passed to other functions, and given attributes (f.calls = 3 works). Classes are objects whose type is type; print(type(type)) prints <class 'type'>. Decorators (py4), registries and dependency injection are cheap in Python precisely because functions and classes are ordinary objects.

2. Names, namespaces and binding

A name is an identifier like a or total. Names do not hold data; they are entries in a namespace, a table that maps names to objects. Each module has a global namespace, each function call gets a fresh local namespace, and each class body has one too (py3 covers how Python decides which namespace a name is looked up in).

Attaching a name to an object is called binding. The obvious way to bind is assignment, x = ..., but many statements bind names: def f(): ... binds f to a new function object, class C: ... binds C, import json binds json to the module object, and for item in items rebinds item on every loop iteration.

The rule for assignment is short: evaluate the right-hand side to get an object, then bind the name on the left to that object. Nothing is ever copied. When the right-hand side is just another name, the result is two names bound to one object. Two names for one object is called aliasing. Aliasing is not a bug; it is how Python works everywhere. It only matters when the shared object is mutable and someone changes it.

3. Mutation versus rebinding

This is the single most important distinction in the lesson. There are two completely different things you can do that both look like "changing x":

  • Mutation changes the object that x refers to: x.append(5), x[0] = 9, d["k"] = 1, obj.attr = 2. Every name bound to that object sees the change, because the object itself is different now.
  • Rebinding points the name x at a different object: x = something. The old object is not touched, and other names bound to it still see it exactly as before.

Watch the two in action. Both programs start with y as an alias of x, and both "add 2 to x".

x = [1]; y = x
x = x + [2]        # builds a NEW list [1, 2], then rebinds x to it
print(x, y)        # [1, 2] [1]

x = [1]; y = x
x += [2]           # extends the EXISTING list in place
print(x, y)        # [1, 2] [1, 2]

Why do + and += behave differently? x + [2] calls list.__add__, whose job is to return a new list containing both. x += [2] is augmented assignment: Python first looks for an in-place method, __iadd__, and for lists that method extends the list in place and returns the same list, which is then bound back to x. Immutable types such as str and tuple have no __iadd__, so for them += falls back to + and rebinds:

s = "hi"; t = s
s += "!"
print(s, t)        # hi! hi   — t still refers to the original string

4. Mutable and immutable types

Whether a type is mutable decides whether aliasing can ever bite you. The built-ins sort cleanly:

ImmutableMutable
int, float, complex, boollist
str, bytesbytearray
tuple, frozensetdict, set
None, rangeinstances of ordinary classes

Why make anything immutable? Three reasons. Immutable objects can be shared freely, so Python can reuse them (you will see this with small integers). They can be hashed safely, so they can be dict keys (section 8). And they make programs easier to reason about: if a function receives a tuple, you know it cannot change it behind your back.

One subtlety: immutability is shallow. A tuple fixes which objects its slots point to, but if one of those objects is a list, the list can still change:

t = ([1],)
t[0].append(2)     # allowed: we mutate the list, not the tuple
print(t)           # ([1, 2],)

5. Passing arguments: call by sharing

When you call a function, Python binds each parameter name in the function's new local namespace to the object the caller passed. That is the whole rule, and it has a name: call by sharing (people also say "pass by object reference"). It is neither the "pass by value" of C, which copies the data, nor the "pass by reference" of C++ references, which would let the function rebind the caller's variable.

def add(item, bucket):
    bucket.append(item)      # mutation: the caller's list changes
    bucket = ["new"]         # rebinding: only the local name moves

xs = []
add(1, xs)
print(xs)                    # [1]

Trace it. On entry, the local bucket and the caller's xs point at the same empty list. append mutates it, so it now holds [1]. The assignment then points the local name bucket at a brand-new list; xs in the caller's namespace is a different entry and does not move. When the function returns, the new list has no names left and is freed.

This explains the myth that "ints are passed by value": they are passed the same way, but because an int is immutable the function has no operation available that could change it. n += 1 inside a function only rebinds the local n.

The practical design rule follows directly: a function should either mutate its argument and say so (and conventionally return None, like list.sort()), or leave its argument alone and return a new object (like sorted()). A function that silently mutates an argument it seems only to read is one of the most common sources of aliasing bugs.

6. The mutable default argument trap

Default values are evaluated once, when the def statement runs, and stored on the function object in its __defaults__ attribute. Every call that omits the argument binds the parameter to that same stored object.

def f(x, acc=[]):
    acc.append(x)
    return acc

print(f(1), f(2), f.__defaults__)
# [1, 2] [1, 2] ([1, 2],)

Walk through it. When def runs, one empty list is created and stored in f.__defaults__. f(1) binds acc to it and appends 1. f(2) binds acc to the same list and appends 2. Both calls return that one list, and print formats its arguments only after both calls have run, so both show [1, 2]. The __defaults__ tuple shows the evidence: the default itself has been modified.

The fix is a sentinel default that is immutable, conventionally None, and a fresh object created inside the body on each call:

def f(x, acc=None):
    if acc is None:
        acc = []
    acc.append(x)
    return acc

If None is a meaningful value for the caller to pass, use a private sentinel instead: _MISSING = object() at module level and acc=_MISSING. A fresh object() is equal only to itself, so it can never be confused with real data.

7. Identity versus equality: is and ==

a == b calls a.__eq__(b), a method the type defines to compare values. Lists compare element by element; your own classes compare however you write __eq__ (and, if you write none, by identity). a is b compares identities and cannot be customised; it is effectively id(a) == id(b).

x = [1, 2]; y = [1, 2]
print(x == y, x is y)     # True False

Use is for singletons — types with exactly one instance — and sentinels: if x is None. It is faster than == and it cannot be fooled by a class with a strange __eq__. Use == for everything else.

Now the trap. CPython pre-creates the integers from -5 to 256 when it starts and reuses them, because small numbers are used constantly. So:

p = 256; q = int("256"); print(p is q)          # True  — both are the cached 256
p = 257; q = int("257"); print(p is q, p == q)  # False True — two separate int objects

It gets murkier: when the compiler sees the same constant twice in one block of code, it stores it once. In a script, a = 257; b = 257; print(a is b) prints True. Run the same two assignments as separate statements in the interactive prompt (the REPL, the read-eval-print loop you get by running python with no arguments), where each line is compiled on its own, and you get False. Strings behave similarly: some are automatically interned (kept as one shared copy), others are not — "hello_world" is "".join(["hello", "_world"]) is False even though they are equal. None of this is part of the language; it is how CPython happens to optimise, and it varies by version and context. Since Python 3.8 the compiler warns you when you write it:

x = 1
print(x is 1)
# SyntaxWarning: "is" with 'int' literal. Did you mean "=="?

8. Copying: shallow and deep

Because assignment never copies, you must copy explicitly when you want independence. There are two depths.

A shallow copy creates a new outer container and fills it with references to the same element objects. list(x), x[:], x.copy(), dict(d), d.copy() and copy.copy(x) are all shallow. For a list of numbers that is all you need, since the numbers are immutable. For a list of lists, the inner lists are shared.

A deep copy, copy.deepcopy(x), walks the whole structure and copies every mutable object it finds, recursively.

import copy
orig = [[1, 2], [3, 4]]
sh = copy.copy(orig)
dp = copy.deepcopy(orig)
orig[0].append(99)
print(sh, dp, sh[0] is orig[0], dp[0] is orig[0])
# [[1, 2, 99], [3, 4]] [[1, 2], [3, 4]] True False

How does deepcopy cope with an object that appears twice, or a structure that points back at itself (a tree node whose child has a parent attribute)? It keeps a memo dict mapping id(original) to the copy already made. Before copying any object it checks the memo; if the object was already copied, it reuses that copy. That preserves sharing inside the structure and stops infinite recursion on cycles. In the test run, a deep-copied tree node's child's parent was the new root (r2.children[0].parent is r2 printed True).

The best-known shallow-copy trap does not even call copy. Multiplying a list repeats its references:

grid = [[0] * 3] * 3       # three references to ONE inner list
grid[0][0] = 9
print(grid)                # [[9, 0, 0], [9, 0, 0], [9, 0, 0]]

grid = [[0] * 3 for _ in range(3)]   # the comprehension builds a new list each time
grid[0][0] = 9
print(grid)                # [[9, 0, 0], [0, 0, 0], [0, 0, 0]]

The inner [0] * 3 is fine, because it repeats references to the immutable 0. The outer * 3 repeats references to one mutable list.

9. Hashing and why only some objects can be dict keys

A dict (and a set) is a hash table. To store a key it calls hash(key), which returns an integer, uses that integer to pick a slot in an internal array, and puts the entry there. To look a key up it hashes the key again, goes to the same slot, and confirms the match with == (py2 goes into the table layout and costs). This makes lookups take roughly constant time regardless of size — but it only works if two rules hold. Objects that satisfy them are called hashable:

  1. The hash never changes while the object exists. Otherwise the dict would look in a different slot from where it stored the entry.
  2. Equal objects have equal hashes: if a == b then hash(a) == hash(b). Otherwise a lookup with an equal key would go to the wrong slot.

Rule 1 is why mutable built-ins are unhashable: a list's value can change, so any hash computed from its value could go stale. Tuples are hashable only if everything inside them is:

hash([1, 2])      # TypeError: unhashable type: 'list'
hash(([1],))      # TypeError: unhashable type: 'list'
hash((1, 2)) == hash((1, 2))   # True

For your own classes, the default is a hash based on identity, paired with an identity-based ==. That pair is consistent. But the moment you define __eq__ to compare values, an identity hash would break rule 2, so Python sets __hash__ to None and instances become unhashable:

class P:
    def __init__(self, x): self.x = x
    def __eq__(self, other): return isinstance(other, P) and self.x == other.x

print(P.__hash__)   # None

If you add a __hash__ but base it on a field that can change, you have broken rule 1 and the failure is silent:

class K:
    def __init__(self, x): self.x = x
    def __eq__(self, other): return isinstance(other, K) and self.x == other.x
    def __hash__(self): return hash(self.x)

k = K(1)
d = {k: "v"}
k.x = 2                         # mutate a key that is inside a dict
print(k in d, K(1) in d, K(2) in d, len(d))
# False False False 1

The clean way to get a correct, value-based, hashable class is a frozen dataclass, which generates __eq__ and __hash__ over its fields and forbids assigning to them after creation (py6 covers dataclasses in detail):

from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: int
    y: int

{Point(1, 2): "a"}[Point(1, 2)]   # 'a'

10. References, reference counts and object lifetime

If names only point, when does an object go away? CPython keeps a reference count in every object: the number of references pointing at it, from names, container slots, attributes and the interpreter's own internals. Binding a name adds one; rebinding or deleting the name (del x) removes one. When the count drops to zero the object is freed immediately. del x therefore does not destroy an object; it removes one name, and the object dies only if that was the last reference. Reference cycles (an object that points to itself, directly or through others) never reach zero on their own, which is why CPython also has a cycle-detecting garbage collector; py8 covers both in depth.

sys.getrefcount(x) shows the count, plus one for the temporary reference its own argument creates, so sys.getrefcount([]) prints 1. On 3.12, sys.getrefcount(None) prints a huge constant (4294967295 on the machine used for this lesson) because None is now an immortal object — see the deep dive.

How augmented assignment on a subscript really executes

The puzzle t = ([1],); t[0] += [2] raises TypeError: 'tuple' object does not support item assignment, yet afterwards t is ([1, 2],). The bytecode explains it. dis.dis on Python 3.12 shows the statement compiles to BINARY_SUBSCR (load t[0]), BINARY_OP 13 (+=) (call list.__iadd__, which extends the list in place and returns it), and then STORE_SUBSCR (assign the result back to t[0]). The first two steps succeed, so the list is already mutated; the third fails because tuples have no __setitem__. Augmented assignment always performs that final store, even when __iadd__ returned the same object, because for immutable types the result is a new object that must be stored. The official Programming FAQ documents this exact case.

Constant folding and interning are compile-time decisions

Whether a is b holds for equal immutable values depends on how many objects the interpreter actually created. Small integers from -5 to 256 are preallocated at startup. Beyond that, each compiled code object has a constants table, and the compiler deduplicates equal constants within it; that is why a = 257; b = 257 in one script yields one object while the same two lines typed separately at the REPL yield two. For strings, CPython automatically interns identifiers and many short string constants that look like names, while strings built at runtime (by join, concatenation, reading a file) are not interned. sys.intern(s) returns the canonical interned copy, which is useful when you hold millions of repeated strings such as column names or token labels: each duplicate then costs one pointer rather than a full string, and equality checks between interned strings can short-circuit on identity.

Containers assume identity implies equality

When a list compares elements or in searches a container, CPython first checks x is y and only calls == if that fails. This is a big speed-up and is correct for every sane type — but IEEE-754 NaN ("not a number") is defined as unequal to itself. Hence nan == nan is False, while [nan] == [nan] and nan in [nan] are True when it is the same nan object. In data work this shows up as "dedupe" code that behaves differently depending on whether NaNs were produced by the same operation; pandas and NumPy provide explicit NaN-aware functions (isna, isnan) for exactly this reason.

Immortal objects (Python 3.12+)

PEP 683 (a PEP, Python Enhancement Proposal, is the design document through which language changes are proposed and accepted), implemented in 3.12, gives certain objects — None, True, False, the small integers, and some other interpreter-owned objects — a special reference count value that incrementing and decrementing leave unchanged. Such objects are never freed. The motivation is performance and sharing: these objects are touched by nearly every line of code, and every increment is a write to memory that invalidates CPU cache lines and, with multiple processes forked from one parent, forces copy-on-write of memory pages that would otherwise stay shared. Immortality is also groundwork for a separate GIL per sub-interpreter (PEP 684; the GIL, or Global Interpreter Lock, is the lock that lets only one thread run Python bytecode at a time, covered in py8) and the free-threaded build (PEP 703, experimental in 3.13, officially supported in 3.14 — py8 covers it). The visible consequence is only that sys.getrefcount on those objects returns a large meaningless constant.

Hash randomisation

The hashes of str and bytes are salted with a random value chosen when the interpreter starts, so hash("abc") differs between runs. This was introduced (on by default since Python 3.3) to stop hash-flooding denial-of-service attacks, in which an attacker sends many keys crafted to collide in the same slot, turning each dict insert from constant time into a scan. The consequences: never persist hash() values or use them to shard data across processes (use hashlib instead), and set PYTHONHASHSEED only when you need reproducible iteration order of sets in tests. Integers hash to themselves, with one curiosity: hash(-1) is -2, because the C-level hash function uses -1 to signal an error.

Integer size and the digit limit

Python ints have arbitrary precision: they grow as needed and never overflow. Converting a huge integer to or from a decimal string takes time that grows quadratically with the number of digits, which was a denial-of-service risk for any service parsing numbers from untrusted JSON. Since Python 3.11 (and backported to security releases of earlier versions), int("1" * 5000) raises ValueError: Exceeds the limit (4300 digits) for integer string conversion. sys.set_int_max_str_digits() or PYTHONINTMAXSTRDIGITS changes the limit; hexadecimal and other power-of-two bases are not limited because they convert in linear time.

What sys.getsizeof really measures

Every CPython object starts with a header holding its reference count and a pointer to its type. sys.getsizeof returns the size of that one object only. On 64-bit 3.12, an empty list reports 56 bytes and [1, 2, 3] reports 88 — the header plus an array of three 8-byte pointers — but nothing for the integers themselves. sys.getsizeof([[0] * 1000]) reports 64, ignoring the 1,000-element inner list entirely. To measure a real footprint use tracemalloc (in the standard library) to snapshot allocations before and after building the structure.

Defensive copying and read-only views at API boundaries

A class that stores a list passed to its constructor and returns it from a property has handed the caller a live handle into its internals. Senior code closes these holes: copy mutable inputs on the way in (self._items = list(items)), and on the way out return an immutable form (a tuple, a frozenset) or a read-only view. types.MappingProxyType(d) wraps a dict in a view that raises TypeError on any write but reflects later changes to the underlying dict, which is a zero-copy way to expose internal mappings safely.

Shared mutable state that leaks across requests

The story in the introduction — a module-level default dict "copied" by assignment and then mutated per request — is the most common production form of an aliasing bug. It hides in class attributes too: class Session: headers = {} makes one dict shared by every instance, so a header set on one session appears on all of them. The symptoms are data from one user appearing in another's response, lists that grow without bound, and memory that rises steadily until a restart. Code review heuristics: any module-level or class-level mutable object that is modified after import deserves a comment explaining why it is safe; defaults should be constructed per use (copy.deepcopy(DEFAULTS) or a factory function).

Caches that return shared objects

functools.lru_cache and hand-written memo dicts return the same object on every hit. If a caller mutates the result — sorts a returned list in place, adds a key to a returned config dict — every future caller receives the corrupted value. The bug is intermittent, because it depends on request order, and disappears on restart. Return immutable values from cached functions (tuples, frozen dataclasses, MappingProxyType), or document that callers must copy.

Views versus copies in NumPy and pandas

AI and data code adds a twist: NumPy slicing returns a view, a new array object that shares the same underlying memory buffer, so b = a[:10]; b[0] = 99 changes a, the opposite of slicing a Python list. pandas historically sometimes returned views and sometimes copies, producing the infamous SettingWithCopyWarning; pandas' Copy-on-Write mode (default from pandas 3.0) makes every derived object behave like a copy until it is written. When a notebook "mysteriously" changes an input DataFrame, this is the first place to look. np.shares_memory(a, b) answers the question directly.

Unfindable keys and silent data loss

Objects with a value-based __hash__ over mutable fields cause entries that exist but can never be found. In production that looks like cache hit rates dropping over time, sets that "contain duplicates" (two entries whose keys became equal after insertion), and memory that is never reclaimed. The fix is structural: hash only immutable fields, or key by an immutable identifier. Frozen dataclasses make the mistake impossible to write.

Measuring memory correctly

When a process's memory grows, sys.getsizeof on a big structure will badly under-report. The standard tools are tracemalloc (take a snapshot, run the suspect code, take another, and compare with snapshot.compare_to(old, "lineno") to see which lines allocated the growth), and, for "who is keeping this alive?", gc.get_referrers() or the third-party objgraph package. Growing lists hanging off a module-level default are found this way in minutes.

Deepcopy as a performance problem

copy.deepcopy is written in Python, visits every object, and consults the memo dict for each; on large nested structures it can dominate a request's latency. It also has sharp edges: objects holding locks, open files or sockets cannot be meaningfully copied. Common alternatives are to keep configuration immutable so it never needs copying, to rebuild from a factory function, or to serialise and deserialise (a JSON round-trip is often faster for plain data, although it loses types such as tuples and datetimes).

Checking with tools

Linters catch the most common forms statically. Ruff's rule B006 (from flake8-bugbear) flags mutable default arguments, B008 flags function calls in defaults, RUF012 flags mutable class attributes that are not annotated as ClassVar, and the compiler's own SyntaxWarning flags is against literals. Turning these on in CI eliminates most of this lesson's bugs before review.

Answer

[1, 2, 3, 4] [1, 2, 3] True False — b is another name for the list a refers to; c is a shallow copy taken before the append. a == c is False because a now has four elements.

[[9, 0], [9, 0]] — the outer * 2 repeated a reference to one inner list, so both rows are the same object.

[1, 2] [1, 2] — the default list is created once, when def runs, and shared by every call. Both calls return that same list, and print only formats it after both appends. Fix: acc=None and if acc is None: acc = [].

([1, 2],) — t[0] += [2] loads the list, calls list.__iadd__ (which mutates it in place), and then tries to store the result back into the tuple, which raises TypeError. The mutation had already happened.
