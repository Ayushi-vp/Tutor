A recommendation service has a function get_user(user_id) that returns a user or None if the id is unknown. Eighty call sites use it. Three of them forget the None case and call user.preferences directly. Tests pass, because the test users always exist. In production, a deleted account triggers AttributeError: 'NoneType' object has no attribute 'preferences' in the middle of a batch job at 3 a.m. Elsewhere in the same codebase, a function takes (user_id, order_id), both integers, and a caller passes them in the wrong order; nothing fails, and refunds go to the wrong accounts for a week.

Python's flexibility makes these bugs easy to write and hard to see in review, because nothing in the code says what get_user returns or which integer is which. Type hints fix that. Writing def get_user(user_id: UserId) -> User | None documents the contract, and a static type checker run in CI reads it and flags every one of the three unsafe call sites and the swapped arguments, before any code runs.

Hints have become part of how modern Python is written far beyond bug-catching. Editors use them for completion and safe renames. FastAPI turns a function's hinted parameters into request validation and API documentation; Pydantic turns a hinted class into a parser for untrusted JSON; LLM tool-calling libraries generate the tool's JSON schema from a function's type hints. Interviewers for senior roles expect you to use them fluently and to know their limits: they are not checked at runtime, they can lie about external data, and Any quietly switches them off.

This lesson starts with what hints are and who reads them, then builds the everyday vocabulary: built-in generics, unions, abstract collection types, Literal, TypedDict, NewType. It covers generics (with Python 3.12's syntax), Protocols, narrowing, variance, typing decorators and overloads; then how to run a checker in practice and how to validate data at runtime with Pydantic. It ends with Python 3.14's deferred annotations. Runtime behaviour was verified on CPython 3.12.10; checker messages are shown in the format mypy documents, and version-specific features are marked.

Labels on the parcels

Imagine a warehouse where parcels move between departments. Nobody opens the parcels in transit; everyone just hands them on. Type hints are labels on the parcels: "contains a User, or nothing", "contains a list of prices". The conveyor belt — the Python interpreter — does not read the labels at all; it moves whatever you put on it. But an inspector who walks the floor before the shift starts — the type checker — reads every label and every hand-off instruction, and flags any place where a department expects a User but the label says "User, or nothing" and nobody checks.

def area(w: float, h: float) -> float:
    return w * h

area("ab", 2)       # runs fine and returns 'abab' — the interpreter ignores the labels
# a type checker, run separately, reports something like:
# error: Argument 1 to "area" has incompatible type "str"; expected "float"  [arg-type]

The syntax is small: after a parameter, : type; after the parameter list, -> return type; on a variable, name: type = value. Python stores them in __annotations__ (py3) and otherwise leaves them alone.

Gradual by design

Python's typing is gradual: code without hints is treated as Any — "could be anything, don't check" — so you can add hints to one module at a time and the rest keeps working. That is what made typing adoptable in huge existing codebases such as Instagram's and Dropbox's. The flip side is that Any can creep in and quietly disable checking, so mature projects measure and reduce it.

Two jobs, two tools

Keep two jobs separate in your mind. Static checking answers "is my code consistent with itself?" — do the calls match the signatures, is None handled, are the right ids passed. Runtime validation answers "does this data from outside actually have the shape I claim?" — a JSON body, a config file, an LLM's structured output. Hints serve both, through different tools, and neither replaces the other.

A small example of what it buys

Suppose a colleague changes get_user so that it returns User | None instead of raising for unknown ids. Without hints, nothing tells the eighty callers; the change passes review because the diff only touches one function. With hints and a checker in CI, the same pull request fails with a list of every call site that uses the result without checking for None. The author fixes them in the same change, and the bug that would have appeared at 3 a.m. never ships. That is the core value proposition: types turn a class of runtime surprises into a to-do list at review time, and they make the next person's refactor safe.

Where the parcel analogy breaks: the checker does not just read labels, it also infers them. If you write x = [1, 2] without a hint, the checker labels x as list[int] itself, and hints are mostly needed at function boundaries, where inference cannot see how the function will be called.

1. The basic vocabulary

Since Python 3.9 you annotate collections with the built-in types themselves, and since 3.10 you write unions with |:

def mean(xs: list[float]) -> float: ...
counts: dict[str, int] = {}
point: tuple[int, int] = (3, 4)          # exactly two ints
row: tuple[str, ...] = ("a", "b", "c")   # any number of strs
def find(name: str) -> User | None: ...  # same as Optional[User]

int | None and Optional[int] are the same type; at runtime (int | None) == typing.Optional[int] is True. The name "Optional" was a poor choice — it means "may be None", not "may be omitted" — which is why the | form is preferred.

For parameters, prefer the abstract types from collections.abc that say only what the function needs, so callers can pass any suitable container: Iterable[str] (can be looped once), Sequence[str] (indexable, has length, read-only), Mapping[str, int] (read-only dict-like), Callable[[int, str], bool] (a function taking an int and a str and returning a bool). For return values, be concrete (list[str]), so callers know exactly what they get.

A few special forms appear constantly:

  • Literal["asc", "desc"] restricts a value to specific constants, so sort(order="ascending") is caught.
  • Final marks a name that must not be reassigned; ClassVar marks a class-level attribute (which dataclasses then skip as a field, py6).
  • Any is the escape hatch that disables checking; object accepts anything but allows almost nothing until narrowed.
  • None as a return type means the function returns nothing useful; NoReturn or Never means it never returns at all (always raises or exits).

2. Records: TypedDict, NamedTuple, dataclasses and NewType

JSON-shaped dicts are common, so TypedDict describes a dict with fixed string keys and value types:

from typing import TypedDict

class Movie(TypedDict):
    title: str
    year: int

m: Movie = {"title": "Up", "year": 2009}
m["yeer"]        # checker: TypedDict "Movie" has no key "yeer"

At runtime a TypedDict is only a plain dict: m: Movie = {"title": "Up", "year": "2009"} ran without complaint in the test, and type(m) was dict. It is a static description, useful for data you did not create as objects. For records you construct yourself, dataclasses (py6) or NamedTuple are usually better, because they are real types with attribute access.

NewType solves the swapped-integer bug from the introduction:

from typing import NewType
UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)

def refund(user: UserId, order: OrderId) -> None: ...
refund(OrderId(7), UserId(5))   # checker: Argument 1 has incompatible type "OrderId"; expected "UserId"

For the checker they are distinct types; at runtime UserId(5) is just the integer 5 (type(u) is int), so there is no cost.

3. Generics: connecting types across a signature

Consider def first(xs): return xs[0]. If we annotate it (xs: Sequence[Any]) -> Any, the checker learns nothing about the result. What we mean is "whatever type the elements are, the result has that type". A type variable expresses that. Python 3.12 (PEP 695) added a dedicated syntax:

from collections.abc import Sequence

def first[T](xs: Sequence[T]) -> T:
    return xs[0]

first([3, 4])          # checker infers int
first(["a"])           # checker infers str
print(first.__type_params__)   # (T,) — the type parameter exists at runtime too

On older versions the same thing is T = TypeVar("T") at module level and def first(xs: Sequence[T]) -> T. Type variables can be bounded (def biggest[T: Comparable](...), meaning T must be a subtype of Comparable) or constrained to a fixed set ([T: (int, float)]). Classes can be generic too, and type aliases have their own statement:

class Box[T]:
    def __init__(self, item: T) -> None:
        self.item = item

type Vector = list[float]          # 3.12 type alias statement
print(Vector.__value__)            # list[float]  (a lazily evaluated TypeAliasType)

A checker's reveal_type(expr) prints the type it inferred for an expression; since 3.11 typing.reveal_type also exists at runtime, where it prints the runtime type (Runtime type is 'int') and returns the value, so you can leave it in code while debugging.

4. Protocols: typed duck typing

Python code usually cares what an object can do, not what it inherits from (py6's duck typing). A Protocol describes that directly:

from typing import Protocol

class Sender(Protocol):
    def send(self, to: UserId, msg: str) -> None: ...

def notify(sender: Sender, to: UserId, msg: str) -> None:
    sender.send(to, msg)

class EmailClient:                 # never mentions Sender
    def send(self, to: UserId, msg: str) -> None: ...

notify(EmailClient(), UserId(1), "hi")   # accepted: it has a matching send

Any class with a compatible send method — an email client, an SMS gateway, a test fake with a list of sent messages — is a Sender. That makes Protocols ideal for dependency injection and for typing third-party objects you cannot change. The checker compares full signatures. At runtime, @runtime_checkable allows isinstance(obj, Sender), but it only checks that attributes with those names exist: in the test, a class whose send took no parameters still passed.

5. Narrowing: how the checker follows your logic

A value of type User | None cannot be used as a User until the code has ruled out None. Checkers follow control flow and narrow the type in each branch:

def greeting(user_id: UserId) -> str:
    user = get_user(user_id)        # User | None
    if user is None:
        return "hello, guest"
    return f"hello, {user.name}"    # here the checker knows user is User

def describe(x: int | str) -> str:
    if isinstance(x, int):
        return "int"                # x: int
    elif isinstance(x, str):
        return "str"                # x: str
    else:
        assert_never(x)             # x: Never — proves all cases are handled

Checkers narrow on is None, isinstance, equality with Literal values, truthiness, match statements and in checks against literal collections. When the condition lives in a helper function, annotate its return type as TypeIs[User] (3.13, PEP 742) or TypeGuard[User] so the checker narrows at the call site. At runtime, assert_never(3.0) raises AssertionError: Expected code to be unreachable, but got: 3.0, so it is a runtime safety net as well.

6. Variance: why list[Dog] is not a list[Animal]

Suppose Dog is a subclass of Animal. Should a function declared to take list[Animal] accept a list[Dog]? Intuition says yes; the checker says no, and it is right:

def adopt(pets: list[Animal]) -> None:
    pets.append(Cat())          # perfectly legal for a list[Animal]

dogs: list[Dog] = [Dog()]
adopt(dogs)                     # checker error — otherwise dogs would now contain a Cat

That is invariance: for mutable containers (list, dict, set), list[Dog] and list[Animal] are simply different types. Read-only containers (Sequence, Mapping's values, tuple, frozenset) are covariant: a Sequence[Dog] is a Sequence[Animal], because you can only take Dogs out. Function parameters are contravariant: a callback that accepts any Animal can stand in wherever a callback for Dog is needed. The practical rule is the one from section 1: parameters take the most general read-only abstract type (Sequence[Animal], Mapping[str, float]), which makes them both flexible and correct. With the 3.12 syntax, checkers infer the variance of your own generic classes from how the type parameter is used.

7. Typing callables: decorators and overloads

A decorator (py4) replaces a function with a wrapper. Typed naively as Callable[..., Any], it erases the signature, and the checker stops checking every call to every decorated function. ParamSpec captures the whole parameter list so the wrapper can promise "same parameters, same return type":

from collections.abc import Callable
import functools

def logged[**P, R](func: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        return func(*args, **kwargs)
    return wrapper

Some functions' return types depend on their arguments. @overload declares several signatures for one implementation, and the checker picks the first that matches each call:

from typing import overload, Literal

@overload
def load(path: str, binary: Literal[True]) -> bytes: ...
@overload
def load(path: str, binary: Literal[False] = ...) -> str: ...
def load(path: str, binary: bool = False) -> str | bytes:
    ...                          # the one real implementation

data = load("x.bin", binary=True)    # checker knows: bytes

Two more tools for methods: Self (3.11) as the return type of methods that return their own instance, so fluent APIs keep the subclass type, and @override (3.12, py6) to have the checker confirm a method really overrides something.

8. Running a checker

The main static checkers are mypy, the original reference implementation with a plugin system (Django and Pydantic ship plugins); pyright, Microsoft's fast checker that powers VS Code's Pylance; and a new generation of much faster Rust-based checkers, including Meta's Pyrefly and Astral's ty. They all target the same typing specification but differ in inference details and defaults, so a project should pick one for CI. A typical mypy error reads:

app/users.py:42: error: Item "None" of "User | None" has no attribute "preferences"  [union-attr]

That is the 3 a.m. bug from the introduction, found in CI. Practical configuration:

  • Run the checker in CI and in editors; fail the build on errors.
  • Start lenient globally and strict on new or core modules (mypy's --strict enables flags such as disallowing untyped definitions and implicit Any), using per-module overrides, and tighten over time.
  • Third-party libraries without inline hints need stub files (.pyi files containing only signatures), usually installed as types-* packages from typeshed, the community stub repository; otherwise their values are Any.
  • Silence individual lines with error codes, # type: ignore[union-attr], never a bare # type: ignore, which also hides future, unrelated errors on that line.

9. Runtime validation at the boundaries

Static checking stops at the edge of your program. json.loads returns Any; annotating the result as Movie is a promise the checker takes on trust. Dataclasses do not check either: P(x="oops") for a dataclass with x: int ran without error in the test. The data that most needs checking — HTTP request bodies, configuration, webhook payloads, and structured output from LLMs — is exactly the data static types cannot see.

Pydantic fills this gap by reading the same kind of annotations at runtime to parse and validate:

from pydantic import BaseModel, PositiveInt, ValidationError

class Order(BaseModel):
    id: str
    qty: PositiveInt

Order.model_validate_json('{"id": "A1", "qty": 3}')     # Order(id='A1', qty=3)
Order.model_validate_json('{"id": "A1", "qty": -1}')    # raises ValidationError naming the qty field

The pattern is: validate once at each boundary, converting untrusted data into well-typed objects, and let the core code trust those types, which the static checker then verifies. FastAPI applies it automatically to request parameters and bodies and generates OpenAPI documentation from the same models; LLM libraries use Pydantic models both to generate the JSON schema sent to the model and to validate what comes back (the AI-engineering track's ae4 covers structured output).

10. Typing *args, **kwargs and callbacks

Variadic parameters are annotated with the type of each element, not the container: def total(*nums: float) -> float means every positional argument is a float (inside the function nums is a tuple[float, ...]), and **opts: str means every keyword value is a string. When keyword arguments have different types, Python 3.12's Unpack with a TypedDict (PEP 692) describes them precisely:

from typing import TypedDict, Unpack

class Opts(TypedDict, total=False):   # total=False: every key optional
    timeout: float
    retries: int

def connect(host: str, **kw: Unpack[Opts]) -> None: ...
connect("db", timeout=5)              # OK
connect("db", timeuot=5)              # checker: unexpected keyword argument "timeuot"

That closes py3's "**kwargs swallows typos" hole for typed code. For callbacks, Callable[[str], None] works when the callback takes simple positional arguments, but it cannot express keyword arguments, defaults or overloads. A callback protocol can: a Protocol whose only member is __call__ with the exact signature, such as def __call__(self, event: str, *, retry: bool = False) -> None. Any function or object with a compatible signature, including a lambda, satisfies it.

11. Forward references and deferred annotations

Until Python 3.14, annotations were evaluated when the def or class statement ran. An annotation naming a class defined later in the file therefore failed at definition time — on 3.12, def f(n: Node) before class Node raised NameError: name 'Node' is not defined — so people quoted it as a string, "Node", or added from __future__ import annotations, which stores every annotation as a string ({'n': 'Node', 'return': 'list[Node]'}) and leaves resolution to typing.get_type_hints.

Python 3.14 (PEP 649 and PEP 749) changed the default: annotations are compiled into a small annotate function that runs only when someone asks for them. Definitions are cheaper, forward references work without quotes, and the new annotationlib module can return annotations in three formats: VALUE (evaluate them, as before, raising NameError for undefined names), FORWARDREF (evaluate what it can and return ForwardRef markers for the rest) and STRING (the source text). Code using from __future__ import annotations keeps the old string behaviour. Libraries that introspect annotations — dataclasses, Pydantic, FastAPI — should call annotationlib.get_annotations() rather than reading __annotations__ directly.

How checkers infer and where they differ

Checkers infer the types of local variables from assignments, of containers from their initial contents, and of expressions from the signatures of the functions they call; annotations are needed mainly on function parameters, return types of public functions, and empty containers (names: list[str] = []). Checkers differ in details: pyright infers return types of unannotated functions from their bodies, while mypy by default treats unannotated functions as untyped and does not check their bodies at all unless --check-untyped-defs is set; they narrow slightly differently in complex control flow; and they differ in how they treat the declared versus inferred type of a variable after reassignment. The shared typing specification and its conformance test suite (at typing.python.org) are steadily reducing these differences.

Structural versus nominal typing

Most of Python's type system is nominal: a Dog is an Animal because it inherits from it. Protocols add structural subtyping: a type matches because of its shape. Structural typing fits Python's duck-typed libraries and avoids coupling modules through a shared base class, but it can match accidentally (any class with a close() method is a SupportsClose). Protocol members can include attributes and properties as well as methods, and generic protocols such as Iterable[T] are how the standard library's abstract types are described to checkers.

Recent additions worth recognising

Each release has extended the system. 3.11: Self, LiteralString (a string built only from literals, used to type SQL-injection-safe APIs), variadic generics with TypeVarTuple (tensor shapes), Required/NotRequired for TypedDict keys, and dataclass_transform for dataclass-like libraries. 3.12: the PEP 695 syntax, @override, and Unpack[TypedDict] for typing **kwargs precisely (PEP 692). 3.13: TypeIs (PEP 742), ReadOnly TypedDict items (PEP 705), defaults for type parameters (PEP 696), and @warnings.deprecated (PEP 702), which checkers report at call sites. 3.14: deferred annotations. The typing_extensions package backports new constructs to older Python versions, which is why libraries import from it.

Deferred annotations: what changes for library authors

Under PEP 649/749, a class's __annotations__ is computed on first access by calling __annotate__(format). Accessing it in VALUE format still raises NameError if a referenced name does not exist yet, so code that inspects annotations during class creation, as dataclasses and ORMs do, must be careful about when it asks and in which format; FORWARDREF lets it proceed with markers and resolve later. Metaclasses that read annotations from the class namespace before the class exists must use annotationlib.get_annotate_from_class_namespace. And the long-debated plan to make from __future__ import annotations the default (PEP 563) is abandoned: stringified annotations remain available but are no longer the future.

Typing and performance

Annotations have no effect on how CPython executes code: they are not used for optimisation, and a fully typed program runs at the same speed. (Tools such as mypyc, which compiles type-annotated modules to C extensions, and Cython do use them for speed; mypy itself is compiled with mypyc.) The runtime cost of annotations is limited to evaluating them at definition time, which 3.14's lazy evaluation reduces further, and to libraries that introspect them, such as Pydantic building its validators at import time.

Typing numerical and ML code

Array-heavy code is hard to type precisely because what matters — shapes and dtypes — is not captured by np.ndarray alone. NumPy's numpy.typing.NDArray[np.float32] expresses dtype, and TypeVarTuple (3.11) was designed to express shapes (Array[Batch, Height, Width]), though checker support for shape arithmetic remains limited. Libraries such as jaxtyping add shape annotations checked at runtime in tests. In practice, ML codebases type their interfaces — configuration objects, data loaders, service boundaries — strictly, and accept looser types inside numerical kernels.

Variance inference for PEP 695 generics

With the old TypeVar API you had to declare variance by hand (TypeVar("T_co", covariant=True)), and getting it wrong produced confusing errors or unsound code. Type parameters declared with the 3.12 syntax are inferred: the checker looks at how T is used in the class — only in return positions and read-only attributes means covariant, only in parameters means contravariant, both or in a mutable attribute means invariant. A read-only class Box[T] with a get() -> T method is therefore automatically covariant, and adding a set(self, item: T) method silently makes it invariant, which is exactly the list-versus-Sequence rule applied to your own classes.

Where static types stop helping

Some Python is inherently dynamic: getattr with computed names, objects built with type() at runtime, plugin systems that import by string, and heavily metaprogrammed ORMs. Checkers see Any there, or need plugins and stubs to understand the library's conventions. The honest senior position is that typing is a tool with diminishing returns: type public interfaces and data models thoroughly, keep dynamic tricks contained behind typed facades, and do not contort working code to satisfy a checker when a small, documented cast() or Any at the edge is clearer.

Adopting typing in a large codebase

The proven path, described publicly by Dropbox and Instagram, who typed millions of lines: add the checker to CI in a permissive mode so it passes, make every new module strict, type shared utilities and data models first because every caller benefits, and ratchet: each module that becomes clean gets added to the strict list so it cannot regress. Track the number of errors, type: ignore comments and Any-typed expressions (mypy can produce coverage reports) as metrics. Tools like MonkeyType or pyannotate can infer initial annotations from runtime traces, which are then reviewed.

Validation at every trust boundary

Production incidents from bad data enter through boundaries: an upstream service changes a field from int to string, a config value is missing, an LLM returns malformed JSON or an extra field. The defence is a Pydantic model (or msgspec, attrs with cattrs) at each boundary, with explicit policies for unknown fields (ignore, forbid) and for coercion ("3" to 3 or rejection). Validation errors should be logged with the offending field and counted as a metric, and for LLM outputs, retried with the validation error included in the prompt.

Type-driven frameworks

FastAPI, Typer, SQLModel, Pydantic settings and many LLM tool-calling frameworks derive runtime behaviour from annotations. Consequences in production: changing a hint changes an API's validation or documentation; decorators that erase signatures break these frameworks (py4); and an annotation that cannot be resolved at startup, such as a forward reference to a type imported only under TYPE_CHECKING, fails at import. Python 3.14's deferred annotations make the last issue rarer but frameworks still need resolvable types when they build validators.

Typing and refactoring safety

The day-to-day payoff in a mature typed codebase is refactoring: rename a field, change a function's return type from User to User | None, or split a function, and the checker lists every call site that must change. Reviewers can trust that a green type check means all callers were updated. This is also where Any hurts most: a single Any in a chain silently exempts everything downstream, so refactors "pass" while still broken.

Types as documentation for people and tools

Hints are also the most reliable documentation in a codebase, because unlike comments and docstrings they are checked on every build and cannot drift silently. Code-review tools, IDE navigation and AI coding assistants all read them: a function annotated -> User | None tells a reviewer, an editor and an assistant that callers must handle None, and generated code that forgets is caught by the same CI check. One maintenance hazard is third-party stubs drifting from the library version you actually run; pin types-* packages alongside the libraries they describe and upgrade them together.

Common problems

Circular imports caused by importing modules only for annotations are solved with if TYPE_CHECKING: imports (true only for checkers) plus quoted or deferred annotations. Slow checker runs in big monorepos are solved with the daemon modes (dmypy), incremental caches in CI, or faster checkers. Disagreement between the editor's checker (often pyright via Pylance) and CI's (often mypy) confuses developers; align them or accept one as the source of truth.

Type it

Add precise type hints to these functions so a checker catches misuse:

def group_by(items, key):
    out = {}
    for it in items:
        out.setdefault(key(it), []).append(it)
    return out

def notify(sender, user_id, message):
    sender.send(user_id, message)      # sender: any object with .send(int, str)

def parse_order(raw):                   # raw comes from an HTTP JSON body
    return Order(id=raw["id"], qty=raw["qty"])
Answer 
from collections.abc import Callable, Hashable, Iterable
from typing import NewType, Protocol
from pydantic import BaseModel, PositiveInt

def group_by[T, K: Hashable](items: Iterable[T], key: Callable[[T], K]) -> dict[K, list[T]]:
    out: dict[K, list[T]] = {}
    for it in items:
        out.setdefault(key(it), []).append(it)
    return out

UserId = NewType("UserId", int)

class Sender(Protocol):
    def send(self, user_id: UserId, message: str) -> None: ...

def notify(sender: Sender, user_id: UserId, message: str) -> None:
    sender.send(user_id, message)

class Order(BaseModel):
    id: str
    qty: PositiveInt

def parse_order(raw: bytes) -> Order:
    return Order.model_validate_json(raw)     # raises ValidationError with field details

Points to make: the type parameters T and K tie the input element type to the output's list type and the key function's result to the dict's key type, so group_by(users, lambda u: u.country) is inferred as dict[str, list[User]]; K is bounded by Hashable because it becomes a dict key; items is an Iterable, the most general thing the loop needs; the empty dict needs an annotation because inference cannot see its future contents. Protocol means any sender — email, SMS, a test fake — qualifies without inheriting. NewType stops someone passing an order id where a user id is expected, at zero runtime cost. And for external JSON, static hints are not enough: Pydantic validates at runtime at the boundary, after which the returned Order can be trusted by the checker and by the rest of the code.
