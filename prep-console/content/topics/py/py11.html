A team's nightly feature-generation job used to take twenty minutes. After six months of growth it takes five hours and runs into the morning. An engineer is asked to "make it faster" and spends two days rewriting the string-formatting helper, which they are sure is expensive because it is called everywhere. The job gets 2% faster. A colleague then runs a profiler for ten minutes and finds that 80% of the time is a single line: if customer_id in active_ids, where active_ids is a list of 200,000 ids that grew with the business. Changing it to a set takes one line and the job finishes in twelve minutes.

This story is so common it is almost a cliché, and it contains the three core lessons of performance work. First, measure: human intuition about where time goes is unreliable, and the cost of a profiler run is minutes. Second, the biggest wins are usually structural — algorithms, data structures, I/O patterns — not micro-level tweaks. Third, Python's costs are per operation: anything that multiplies the number of Python-level operations (a quadratic loop, a row-by-row pass over millions of records) is where the time goes, and anything that hands a whole batch to compiled code (a built-in, a set lookup, a NumPy expression) is how you get it back.

For AI engineers this matters constantly. Data preparation, feature pipelines, evaluation harnesses, tokenisation, embedding post-processing and API services all have Python in the hot path, and the difference between a pandas apply and a vectorised column operation, or between N+1 database calls and one bulk query, is often two orders of magnitude. Interviewers probe it with "this code is slow, what would you do?" questions whose best answers start with "I'd measure", then move through a clear ladder of options.

This lesson explains why Python code is slow where it is slow, then covers measuring properly: benchmarking with timeit, function-level profiling with cProfile, line-level profiling, sampling profilers such as py-spy for production, and memory profiling. It then climbs the optimisation ladder — algorithms, doing less work, built-ins, vectorisation, parallelism and compiled extensions — and ends with what the interpreter itself has gained from 3.11 to 3.14. Timings are from CPython 3.12.10 on a laptop, with NumPy 2.5.3 for the vectorised examples.

Why Python is slow per operation

Consider adding two numbers. In C, a + b on two doubles is one machine instruction on values sitting in CPU registers. In Python, a + b means: fetch the next bytecode instruction and dispatch on it; look at the type of a (every value is an object with a header, py1); find the addition implementation for that type; check that b is compatible; read the two raw numbers out of their objects; add them; allocate a new float object for the result; and adjust reference counts. That is dozens of instructions for one addition. Python trades raw speed per operation for flexibility: any variable can hold any type, and everything is an object you can inspect.

The consequence is a simple mental model: the cost of Python code is roughly proportional to the number of Python-level operations it performs. A loop over a million elements doing five operations each costs five million interpreted operations. Built-in functions and libraries written in C escape this cost: sum(xs) performs one Python-level call and then a tight C loop. Measured on a million floats: an explicit loop took 22 ms; sum(xs) took 5.7 ms.

The two rules

Rule one: measure first. Before changing anything, reproduce the slowness with realistic data and find where the time goes with a profiler. It is common to find that 80% or more of the time is in one or two places, and they are rarely the places you would have guessed. Then change one thing and measure again.

Where the time really goes in services

For web services and pipelines that talk to databases and APIs, a third insight matters: most of the wall-clock time is often waiting, not computing. A request that makes twelve sequential database queries of 5 ms each spends 60 ms waiting, no matter how fast the Python between them is. A CPU profiler shows little; distributed tracing, which records how long each downstream call took within a request, shows everything. Performance work in services is therefore as much about I/O patterns (fewer round trips, batching, concurrency, caching) as about Python speed.

Put together, those ideas make performance work a short loop: reproduce the slow case, measure where the time goes, change the biggest cost using the highest rung that applies, verify the result is unchanged and faster, and repeat until the remaining time is spread thinly or dominated by things you cannot change.

Where the "operations" model breaks down: the cost of an operation also depends on memory. Following pointers to objects scattered across memory causes CPU cache misses, which is part of why contiguous arrays (NumPy) are faster than lists of objects even beyond interpretation overhead, and why memory-heavy code can be slow even when it does few operations.

1. Benchmarking small things with timeit

Timing a snippet once with time.time() gives noise, not data: the first run pays for caches warming up, the operating system may schedule something else, and the CPU changes frequency. timeit runs the snippet many times, uses the highest-resolution clock (time.perf_counter), and disables garbage collection during the run by default. Take the minimum of several repeats — the run least disturbed by noise:

import timeit
xs = [random.random() for _ in range(1_000_000)]
t = min(timeit.repeat("sum(xs)", globals=globals(), number=10, repeat=5)) / 10
# 5.7 ms per call on the test machine

# from the command line:
# python -m timeit -s "xs = list(range(10**6))" "sum(xs)"

2. Profiling a whole program with cProfile

timeit answers "how fast is this snippet?"; a profiler answers "where does my program spend its time?". cProfile, in the standard library, is a deterministic profiler: it records every function call and return. Run a script under it with python -m cProfile -s cumulative script.py, or profile a block in code:

import cProfile, pstats
pr = cProfile.Profile()
pr.enable()
dist_py(points[:5000], centres)
pr.disable()
pstats.Stats(pr).sort_stats("cumulative").print_stats(5)
         5002 function calls in 0.178 seconds
   Ordered by: cumulative time
   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.177    0.177    0.178    0.178 p11.py:30(dist_py)
     5000    0.001    0.000    0.001    0.000 {method 'append' of 'list' objects}

How to read it: ncalls is how many times each function was called; tottime is time spent in the function's own code; cumtime includes everything it called. Sort by cumtime to find the expensive top-level operation, by tottime to find where the actual work happens. Here nearly all the time is tottime inside dist_py itself: the arithmetic in its inner loop, which cProfile cannot break down further because it only sees function calls. That is the job of the next tool. For larger programs, the pstats output is easier to explore visually with snakeviz or by converting to a call graph.

cProfile's weakness is overhead: it adds a fixed cost to every call, so code with millions of tiny function calls looks slower under it, and proportionally more so than code with few calls. Treat its absolute numbers as approximate and its ranking as the useful part.

3. Line-level and sampling profilers

line_profiler (third-party) times every line of functions you mark with @profile, run through its kernprof command. It is the tool for "which line of this 40-line function is slow?", and on dist_py it would show the distance line consuming most of the time.

Sampling profilers work differently: many times per second they look at what the program is doing and record the current call stack. Functions that appear in many samples are where the time goes. The overhead is low and does not depend on how many calls you make, so sampling profilers are accurate for tiny-function-heavy code and safe to use in production. The main ones:

  • py-spy attaches to an already running process by its process id, with no code change or restart: py-spy top --pid 1234 shows a live, top-like view; py-spy record -o profile.svg --pid 1234 writes a flame graph; py-spy dump --pid 1234 prints every thread's current stack, invaluable when a service seems hung. --native includes C extension frames, and --gil shows only threads holding the GIL.
  • Scalene separates time spent in Python from time in native code and system calls, and profiles memory and GPU usage alongside CPU.
  • On Linux, Python 3.12+ can expose Python function names to the system profiler perf (python -X perf), so native and Python frames appear together.

4. Memory profiling

Memory use is a performance problem in its own right: running out of RAM kills processes, and allocating and freeing millions of objects costs time. tracemalloc (py8) snapshots allocations by line; memray tracks every allocation including native ones and produces flame graphs of memory; Scalene reports memory per line. The usual fixes are the ones from py2 and py5: stream instead of materialising, use generators, store numbers in arrays rather than lists of objects, and use __slots__ or columnar storage for millions of records.

5. Rung one: algorithms and data structures

Complexity dominates everything else once data is large. The customer-id story is O(n × m) membership testing turned into O(n) by building a set once. Other frequent fixes: deque instead of list.pop(0); heapq.nlargest instead of sorting for a top-k; a dict index instead of repeated searching; bisect on sorted data; and removing hidden quadratic behaviour such as += on strings or list.insert(0, ...) in loops (py2 covers the costs). When a profile shows a single line with enormous time, ask first what its complexity is and how large n has become.

6. Rung two: do less work

The fastest code is code that does not run. Common forms:

  • Hoist invariant work out of loops: compile a regex once, compute a lookup table once, look up a config value once.
  • Cache expensive pure functions with functools.cache or lru_cache (py4); the memoised fib(27) dropped from 33 ms to 7 µs because the exponential recursion became linear.
  • Batch I/O: one query with WHERE id IN (...) instead of N queries, one bulk insert instead of N inserts, one embedding request with 100 texts instead of 100 requests. Round trips, not bytes, are usually the cost.
  • Compute only what is needed: in the drill below, taking the square root after finding the minimum computes 20,000 square roots instead of two million; stop early with generators and next() when you need only the first match.

7. Rung three: built-ins and C-implemented libraries

Built-in functions (sum, min, max, sorted, any, all, map), string methods, str.join, comprehensions, and modules such as collections, itertools, heapq and bisect run their loops in C. Replacing hand-written Python loops with them moves work out of the interpreter. For serialisation, orjson and msgspec are several times faster than the standard json module, which often matters for APIs returning large payloads.

8. Rung four: vectorisation

Vectorisation means expressing a computation as operations on whole arrays, so the per-element loop runs in compiled code. It works because of how the data is stored:

Even a simple reduction shows the effect: summing a million floats took 5.67 ms with the built-in sum over a list and 1.15 ms with np.sum over an array. A list of floats is an array of pointers to separate float objects (py2); processing it means one interpreted operation per element, pointer chasing and a new object per result. A NumPy array is one buffer of raw numbers, and a * b + c runs as a few compiled loops, often with SIMD (single instruction, multiple data) instructions. The same thinking applies to pandas and Polars: operate on whole columns (df["total"] = df["qty"] * df["price"]), use np.where for conditionals, merges instead of per-row lookups, and never iterrows or row-wise apply in a hot path. Broadcasting — NumPy's rule for combining arrays of different shapes — lets you express pairwise computations such as the distances in the drill without any Python loop.

Vectorisation has costs: temporary arrays use memory (the drill's intermediate array is 160 MB), code that is naturally sequential is awkward to express, and for small inputs the fixed overhead of calling into NumPy can exceed the loop it replaces.

9. Rungs five and six: parallelism and compiled code

Once single-core work is efficient, spread it across cores where possible (py9): processes for CPU-bound Python, thread pools for native code that releases the GIL, asyncio or threads for I/O. Parallelism multiplies by at most the number of cores, and less after overheads, which is why it comes after the rungs that can give 100× on one core.

For hot loops that cannot be vectorised — each step depends on the previous one, or there is complex branching per element — compile them. Numba compiles a numeric function decorated with @njit to machine code the first time it is called, often reaching C speed with no other changes, and supports parallel loops. Cython compiles Python-like code with optional C type declarations into an extension module. Rust with PyO3 (built with maturin) gives memory-safe compiled extensions and is behind many modern Python tools (Polars, Pydantic's core, tokenizers, Ruff). All three let you keep a Python API, so callers do not change. PyPy, an alternative Python implementation with a tracing JIT, can run pure-Python code several times faster without changes, but has weaker compatibility with C extensions.

10. Rung seven: micro-optimisations, honestly

There are small, real effects: local variables are faster than globals and attribute lookups, so hot loops sometimes alias sqrt = math.sqrt (measured: 5.11 ms to 4.62 ms over 100,000 calls, about 10%); avoiding repeated attribute access in a loop; using tuple unpacking (for px, py in points) rather than repeated indexing. Since 3.11 the specialising interpreter has already removed much of the gap these tricks used to close. Use them only in proven hot loops, after everything above, and measure each one.

11. A worked session: the story from the introduction

Here is the introduction's job in miniature, run for real. Twenty thousand customer records are filtered against a list of 200,000 active ids, and each match is formatted by a helper, fmt, that the engineer suspected was the bottleneck:

def build(customers, active_ids):
    rows = []
    for c in customers:
        if c["id"] in active_ids:        # active_ids is a list
            rows.append(fmt(c))
    return rows

Profiled with cProfile, sorted by tottime:

   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1   17.687   17.687   17.747   17.747 p11b.py:6(build)
     9931    0.056    0.000    0.056    0.000 p11b.py:5(fmt)
     9931    0.005    0.000    0.005    0.000 {method 'append' of 'list' objects}

Read it the way you would at work. Total 17.7 s. The suspected helper, fmt, was called 9,931 times and took 0.056 s in total — 0.3% of the run. Optimising it perfectly could save at most that (Amdahl's law). Almost all the time is tottime in build itself, meaning its own lines, and the only line in it that can cost this much is the membership test: 20,000 scans of a 200,000-element list, about two billion comparisons in the worst case. Passing set(active_ids) instead brought the run to 15.8 ms with identical output — about 1,100 times faster, from a one-line change, found in minutes.

12. Wall-clock time versus CPU time

Two clocks answer different questions. Wall-clock time (time.perf_counter()) is elapsed real time, including waiting on the network, disk, locks and sleeps. CPU time (time.process_time()) counts only time the process was actually computing. In a test that slept 0.5 s and then summed ten million integers, wall time was 0.64 s and CPU time 0.14 s. A large gap means the program is waiting, and the fix is on the I/O side (batching, concurrency, caching); CPU close to wall time means it is computing, and the ladder's computational rungs apply. cProfile reports wall time by default, so a function that waits on a slow query shows a large cumtime even though no Python is running — another reason to confirm with tracing what kind of time you are looking at.

The specialising adaptive interpreter (3.11+)

PEP 659 made CPython rewrite its own bytecode as it runs. Each instruction that can benefit — attribute loads, global loads, binary operations, calls, subscripts — starts in a generic "adaptive" form that counts executions. After a few runs it inspects the types it sees and replaces itself with a specialised variant: LOAD_ATTR_INSTANCE_VALUE reads an attribute directly from a known object layout, BINARY_OP_ADD_INT adds two ints without generic dispatch, LOAD_GLOBAL_MODULE uses a cached dict version. Each specialised instruction starts with a cheap guard; if the types change it de-optimises back. dis.dis(func, adaptive=True) shows the specialised instructions after warming a function up. The practical consequence: type-stable code (a variable that always holds the same type, objects of one class with attributes set in __init__) runs faster than code that mixes types at the same site.

The JIT and the tail-calling interpreter

3.13 added an experimental JIT compiler based on "copy-and-patch": hot sequences of specialised micro-operations are translated into machine code by stitching together pre-compiled templates, which is fast to compile but does limited optimisation. It is off by default. 3.14 ships it in the official Windows and macOS binaries, still experimental and disabled unless enabled explicitly (via the PYTHON_JIT environment variable in builds that include it). 3.14 also added an opt-in interpreter implementation using tail calls between instruction handlers, which the release notes report as 3-5% faster on the pyperformance suite when built with Clang 19+ on x86-64 and AArch64. These are incremental background gains; they do not change the ladder.

Why vectorised code is fast beyond interpretation

Removing interpreter dispatch is only part of NumPy's advantage. Contiguous memory lets the CPU prefetch data into cache and stream through it; a list of objects scattered across the heap causes cache misses on almost every element. SIMD instructions process 4-16 numbers per instruction. And libraries such as NumPy's linear algebra call tuned BLAS libraries that use every core. That is also why array layout matters: iterating along the contiguous axis is much faster than across it, and float32 halves memory traffic compared with float64, which matters for embeddings.

Profiler overhead and observer effects

Deterministic profilers hook every call and return; with sys.setprofile-style hooks, a program dominated by tiny function calls can run several times slower under cProfile, and the slowdown is uneven, inflating functions with many calls. Since 3.12, sys.monitoring (PEP 669) gives tools a low-overhead event API — tools register only for the events they need, and events can be disabled per code location — which newer profilers, debuggers and coverage tools use. Sampling profilers have negligible overhead but are statistical: short runs give noisy results, and functions that run rarely but slowly can be missed, so record long enough windows.

Benchmarking pitfalls

Common ways benchmarks lie: measuring the first run (cold caches, specialisation not yet happened, imports), including setup in the timed region, benchmarking on toy data that fits in CPU cache while production data does not, CPU frequency scaling and thermal throttling on laptops, and noisy neighbours on shared cloud machines. pyperf mitigates many of these by running multiple worker processes, calibrating, and reporting variance; its system tune command configures a Linux machine for stable measurements. When comparing two versions, look at the distributions, not single numbers.

Memory allocation as a cost

Creating and destroying objects is a large share of Python's cost: every intermediate float, tuple, string slice or temporary list is an allocation, reference-count traffic and eventually a deallocation. Code that reuses buffers, avoids building intermediate lists (generators, sum over a generator expression), and avoids unnecessary copies (slicing copies; memoryview and NumPy views do not) is faster for that reason alone. In NumPy, in-place operations (a *= 2, np.add(a, b, out=a)) avoid allocating new arrays in tight loops.

The cost of a Python function call

On the test machine, evaluating x + y inline cost about 17 ns per iteration while calling a function that returns a + b cost about 42 ns: roughly 25 ns of overhead per call for creating a frame, binding arguments and returning. 3.11 made calls much cheaper by inlining Python-to-Python calls in the interpreter loop (py3), but a call is still many times the cost of the arithmetic inside a tiny function. This is why splitting a hot numeric loop into many small helper functions costs real time, why vectorised libraries that make one call per array win, and why deterministic profilers, which add work to every call, distort such code the most. It is not a reason to avoid functions in ordinary code, where readability matters far more.

BLAS and multithreaded native libraries

Matrix operations in NumPy, SciPy and PyTorch call BLAS (Basic Linear Algebra Subprograms) libraries such as OpenBLAS or Intel MKL, which are hand-tuned and multithreaded. A single A @ B may therefore use every core. This interacts with Python-level parallelism: running eight worker processes that each start a BLAS thread pool sized to all cores oversubscribes the machine and can be slower than one process. Setting OMP_NUM_THREADS, OPENBLAS_NUM_THREADS or MKL_NUM_THREADS (or using threadpoolctl) to divide cores between processes is a standard fix in data pipelines and model-serving containers.

Latency in services: trace first

For request-serving systems, start with distributed tracing (OpenTelemetry) and database query logs, not a CPU profiler. The usual findings: N+1 queries (one query per item in a loop), missing indexes, sequential calls to downstream services that could run concurrently, unbounded result sets, and serialisation of large payloads. Fix those, then profile the Python. p50 and p99 latency behave differently: the median is dominated by typical work, while the tail is often GC pauses, cold caches, lock contention or a blocked event loop (py9).

Continuous profiling

Many teams run a sampling profiler continuously in production (Pyroscope, Datadog's or Google Cloud's profilers, or py-spy triggered on demand) and keep flame graphs over time. When latency regresses after a deploy, comparing the flame graphs before and after points at the change. It also catches slowly growing costs, such as a list scan whose n grows with the customer base, long before they become outages.

Data pipelines and AI workloads

The recurring wins: replace row-by-row pandas code with column operations; read columnar formats (Parquet) and only the needed columns; use Arrow-backed or categorical dtypes for strings; push heavy joins and aggregations into a query engine (DuckDB, Polars' lazy API, the warehouse itself); batch calls to embedding and model APIs; cache expensive, deterministic steps such as tokenisation or embedding of unchanged documents keyed by content hash; and use float32 embeddings. Measure end-to-end throughput, not just a single step.

Upgrading Python as an optimisation

Moving from 3.10 to 3.11 or later typically sped up CPU-bound Python by 10-60% with no code changes, and later releases continued to add smaller improvements. For services with large fleets, that translates directly into fewer machines. It is often the highest return-on-effort performance change available, provided dependencies support the new version and you benchmark before and after.

Containers and CPU limits

Code that inspects os.cpu_count() to size pools sees the host's cores, not the container's CPU quota, so a pod limited to two CPUs may start sixteen workers and be throttled by the kernel, which shows up as latency spikes without high CPU utilisation in dashboards. Python 3.13 added os.process_cpu_count(), which respects CPU affinity, and ThreadPoolExecutor uses it for its default size; for cgroup quotas, configure worker counts explicitly from the deployment's limits.

Regression protection

Performance fixes regress silently unless something checks them. Options: benchmark suites run in CI with thresholds (pytest-benchmark, pyperf, or codspeed), load tests before major releases, and latency and throughput SLOs (service-level objectives) with alerts. A benchmark that fails the build when a hot path gets 20% slower catches the next accidental list-membership test in code review rather than in the nightly job.

War story pattern: the hidden quadratic

A frequently reported incident shape: an operation that was O(n²) in a quantity that used to be small — items in a cart, rows in an import, dependencies in a build graph — becomes slow after growth, often suddenly, because quadratic costs go from negligible to dominant quickly. The profile shows one line with a surprising share of time and a call count proportional to n². The fix is almost always a set, a dict index, or sorting once, which is why "what's the complexity of this loop, and how large can n get?" is the most valuable question in performance review.

About 25 minutes with Python 3.11+ (outputs from CPython 3.12.10 on a laptop; yours will differ). Steps 1-5 use only the standard library; step 6 needs NumPy in a virtual environment.

  1. Benchmark properly. Run python -m timeit -s "xs = [float(i) for i in range(10**6)]" "sum(xs)", then the loop version via -s setup and a multi-line statement (or with timeit.repeat in code). Expect roughly a 4× gap.
  2. Reproduce the table. Time "".join(parts) against a += loop for 100,000 short strings, and list versus set membership for 10,000 lookups. Confirm the ratios are about 20× and 1,000×.
  3. Profile the distance function. Paste dist_py from the drill, generate 20,000 random points and 100 centres, and run it under cProfile sorted by cumulative time. Note that almost all the time is tottime in dist_py itself: the profiler cannot see inside the line.
  4. Climb two rungs without NumPy. Rewrite the inner loop as min((px-cx)*(px-cx) + (py-cy)*(py-cy) for cx, cy in centres), unpacking tuples in the for and taking math.sqrt once after the minimum. On the test machine this went from 0.67 s to 0.26 s for 20,000 points with identical results (checked to 1e-12).
  5. Profile a running process. If you can install py-spy, start a script that loops forever calling dist_py, then from another terminal run py-spy top --pid <pid> and py-spy dump --pid <pid>. On Windows run the terminal as administrator.
  6. Vectorise. With NumPy installed, implement the broadcasting version from the drill and compare against step 4 for 200,000 points (test machine: 2.62 s versus 564 ms). Check np.allclose against the pure-Python result on a sample, and watch memory with Task Manager or top as the (200,000 × 100) intermediate array is created; then process in chunks of 20,000 points and compare peak memory.

Speed it up 
def distances(points, centres):          # points: 200,000 × (x, y); centres: 100
    out = []
    for p in points:
        best = None
        for c in centres:
            d = ((p[0]-c[0])**2 + (p[1]-c[1])**2) ** 0.5
            if best is None or d < best:
                best = d
        out.append(best)
    return out

This takes several seconds (about 0.67 s per 20,000 points measured on 3.12, so roughly 7 s for 200,000). How would you approach it?

Answer

Measure: cProfile shows essentially all the time as tottime inside distances — twenty million inner-loop iterations, each doing tuple indexing, several arithmetic operations that each create a float object, a power operation and a comparison.

Do less work first, even in pure Python: compare squared distances and take the square root once per point after the minimum (monotonic, so the minimum is unchanged), unpack tuples in the loop headers, and let min run the comparison loop. That alone went from 0.67 s to 0.26 s per 20,000 points in testing.

Vectorise with NumPy broadcasting:

import numpy as np
P = np.asarray(points)            # (200000, 2)
C = np.asarray(centres)           # (100, 2)
d2 = ((P[:, None, :] - C[None, :, :]) ** 2).sum(axis=2)   # (200000, 100)
best = np.sqrt(d2.min(axis=1))

This replaces twenty million interpreted iterations with a handful of compiled array operations. Measured for 200,000 points: the original loop takes roughly 7 s, the improved pure-Python version 2.62 s, and the NumPy version 564 ms, with np.allclose confirming identical results. Much of that 564 ms is allocating and filling the temporary arrays. Watch memory: the intermediate is 200,000 × 100 × 8 bytes = 160 MB (the test measured exactly that for d2, plus a larger temporary before sum); process points in chunks if that is too much. For much larger centre sets, change the algorithm instead: a k-d tree (scipy.spatial.cKDTree) answers nearest-neighbour queries in roughly O(log m) each rather than O(m). If NumPy did not fit the problem, Numba's @njit on the original loops would get most of the speed with almost no code changes. And verify each rewrite against the original on a sample before trusting it.
