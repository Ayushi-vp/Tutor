A payments team ships a change to how a restaurant bill is split between friends. The code is short and obviously right: divide the total in cents by the number of people. A reviewer approves it, the manual check with a 1,200-cent bill split four ways looks fine, and it goes out. Three weeks later accounting finds that thousands of bills have been short by a cent or two: 1,000 cents split three ways produced 333 + 333 + 333 = 999. Nothing crashed. The only thing that would have caught it was a test that checked the right property — "the parts always add up to the total" — on the right inputs.

Automated tests are how a team keeps changing code without breaking what already works. In Python they are more important than in statically compiled languages, because many mistakes that a compiler would reject — a wrong argument, a misspelled attribute, a None where a value was expected — only appear when the line runs. A good test suite is the thing that runs those lines before users do. It is also the safety net that makes refactoring, dependency upgrades and Python version upgrades routine rather than frightening.

Writing tests that actually protect you is a skill, and the pitfalls are specific. Tests that mock the wrong name and silently call the real email service. Mocks that accept any arguments and so keep passing after the real API changes. Tests that pass only in one order because they share state. Tests that depend on the clock, the network or a random seed and fail once a week for no visible reason. Interviewers probe exactly these, along with the pytest features that avoid them: fixtures, parametrisation, monkeypatch, autospec and property-based testing.

This lesson uses pytest, the de facto standard test runner in Python. It starts with how pytest discovers and runs tests and what its rewritten assert reports, then covers testing exceptions and floats, parametrisation, fixtures, scopes and conftest.py, and the built-in fixtures. It then turns to test doubles: where to patch, autospec, monkeypatch, and designing code so tests need less patching. It covers time, HTTP, async code and databases, property-based testing with Hypothesis, and how to keep a suite fast and trustworthy. Every example was run with pytest 9.1.1 and Hypothesis 6.168.2 on CPython 3.12.10, and the outputs shown are the real ones. The broader strategy — what to test at which level — is covered in the SWE track's swe5.

A test is a small program that checks another program

At its simplest, a test calls some code with known inputs and checks the result against what you expect. With pytest, that is an ordinary function whose name starts with test_, containing an ordinary assert:

# app/pricing.py
def apply_discount(price: float, percent: float) -> float:
    if not 0 <= percent <= 100:
        raise ValueError(f"percent must be between 0 and 100, got {percent}")
    return round(price * (1 - percent / 100), 2)

# tests/test_pricing.py
from app.pricing import apply_discount

def test_ten_percent_off():
    assert apply_discount(100.0, 10) == 90.0

Running pytest in the project directory finds every file named test_*.py (or *_test.py), collects every function named test_* in them, runs each one, and reports a dot for a pass and an F for a failure. If the assert is false, pytest shows the values involved, not just "AssertionError".

Think of a test suite as a set of tripwires across the paths your code can take. Each one is cheap, and together they tell you immediately when a change sends the program somewhere it should not go. Their value comes from three properties: they are automatic (run on every change, in CI), fast (so people run them), and trustworthy (a failure means a real problem and a pass means real safety).

The shape of a good test

Most tests follow three steps, often called arrange, act, assert: set up the inputs and dependencies, call the code under test once, then check the result or the effect. Keep each test focused on one behaviour and name it after that behaviour (test_rejects_percent_over_100), so a failure's name already tells you what broke.

The hard part: dependencies

Pure functions like apply_discount are easy to test. Real code talks to databases, calls HTTP APIs, reads the clock, sends emails and writes files. A test must control those dependencies, both so it is fast and repeatable and so it can create the situations it wants to check (the API times out; it is 2 p.m. and raining). pytest gives two tools for this: fixtures, which build and clean up the things a test needs, and test doubles — fakes, stubs and mocks — which stand in for real dependencies.

One more habit makes all of this work: run the tests constantly. Locally, run the relevant file after every change (a few seconds), and the whole suite before pushing; in CI, run everything on every pull request. A test that is only run before a release finds bugs weeks after they were written, when the context is gone.

Where the tripwire analogy breaks: a tripwire only goes off when something crosses it. Tests only check the paths and properties someone thought to write down, which is why the bill-splitting bug slipped through a test that used a total divisible by the number of people. Choosing which inputs and properties to check is the real skill, and property-based testing, at the end of the lesson, helps with it.

1. Running tests and reading failures

pytest's discovery rules are simple and configurable: starting from the given paths (or the current directory), it collects files named test_*.py or *_test.py, functions named test_*, and methods named test_* in classes named Test*. The most useful command-line options:

  • -q quieter and -v verbose output; -x stop at the first failure; -s show print output instead of capturing it.
  • -k "discount and not free" selects tests whose names match an expression; -m "not slow" selects by marker.
  • --lf re-runs only the tests that failed last time, and --ff runs them first; pytest remembers failures in a .pytest_cache directory.
  • tests/test_pricing.py::test_ten_percent_off runs one test by its node id.

When an assert fails, pytest shows the values that made it fail. That comes from assertion rewriting: when pytest imports a test module, it rewrites each assert statement so that it records the intermediate values. Here is the real output for the bill-splitting bug:

def split_bill(total_cents: int, people: int) -> list[int]:
    base = total_cents // people
    return [base] * people          # loses the remainder

def test_split_keeps_every_cent():
    assert split_bill(1000, 3) == [334, 333, 333]

# pytest output:
>       assert split_bill(1000, 3) == [334, 333, 333]
E       assert [333, 333, 333] == [334, 333, 333]
E         At index 0 diff: 333 != 334
E         Use -v to get more diff

Rewriting only applies to test modules and conftest.py files (and plugins), so helper functions in your application that use assert give ordinary messages. It is one reason pytest needs no assertEqual-style API.

2. Checking exceptions and floats

To assert that code raises, wrap the call in pytest.raises. The optional match argument is a regular expression checked against the message, so the test fails if the wrong error is raised for the wrong reason:

import pytest

def test_rejects_bad_percent():
    with pytest.raises(ValueError, match="between 0 and 100"):
        apply_discount(10.0, 150)

Floating-point arithmetic is inexact, so 0.1 + 0.2 == 0.3 is False. pytest.approx compares with a relative tolerance (one part in a million by default): assert 0.1 + 0.2 == pytest.approx(0.3) passes. It also works element-wise on lists and dicts of numbers.

3. Parametrisation: one test, many cases

When the same check applies to several inputs, write it once and give pytest a table:

@pytest.mark.parametrize(
    ("price", "percent", "expected"),
    [(100.0, 0, 100.0), (100.0, 100, 0.0), (19.99, 15, 16.99)],
    ids=["no-discount", "free", "odd-cents"],
)
def test_discounts(price, percent, expected):
    assert apply_discount(price, percent) == expected

# pytest -v -k discounts
# tests/test_pricing.py::test_discounts[no-discount] PASSED
# tests/test_pricing.py::test_discounts[free] PASSED
# tests/test_pricing.py::test_discounts[odd-cents] PASSED

Each row becomes an independent test with its own id, so one failing case does not hide the others and the report names exactly which input failed. That is the difference from a for loop inside one test, where the first failure stops the loop. Stacking two parametrize decorators produces every combination of their values.

4. Fixtures: providing what tests need

A fixture is a function decorated with @pytest.fixture. A test that names it as a parameter receives the value it returns or yields. Code before yield is setup; code after it is teardown and runs after the test, even if the test failed — the same pattern as @contextmanager (py7). Fixtures can use other fixtures, which gives a dependency graph that pytest resolves by name:

# tests/conftest.py
import sqlite3, pytest

@pytest.fixture(scope="session")
def engine():
    print("\n[session] start database")
    yield "db-engine"
    print("\n[session] stop database")

@pytest.fixture
def db(tmp_path, engine):
    print(f"\n[function] open connection in {tmp_path.name}")
    conn = sqlite3.connect(tmp_path / "t.db")
    conn.execute("create table users(id integer primary key, email text unique)")
    yield conn
    conn.close()
    print("[function] closed connection")

@pytest.fixture
def make_user(db):
    def _make(email="a@example.com"):
        cur = db.execute("insert into users(email) values (?)", (email,))
        return cur.lastrowid
    return _make
# tests/test_fixtures.py
def test_insert(db, make_user):
    uid = make_user("x@example.com")
    assert db.execute("select email from users where id=?", (uid,)).fetchone() == ("x@example.com",)

def test_unique_email(make_user):
    make_user("dup@example.com")
    with pytest.raises(sqlite3.IntegrityError):
        make_user("dup@example.com")

Run with pytest -s to see the prints, and the lifetimes are visible:

[session] start database
[function] open connection in test_insert0
.[function] closed connection
[function] open connection in test_unique_email0
.[function] closed connection
...
[session] stop database

Three design points. Scope — function (default), class, module, package or session — trades isolation for speed; share expensive, effectively read-only resources widely and keep mutable state per test. Factory fixtures such as make_user return a function, so each test builds exactly the data it needs with readable overrides, instead of depending on one giant pre-built dataset. conftest.py files make their fixtures available to every test in their directory and below without imports, so shared fixtures live near the tests that use them. A fixture with autouse=True applies to every test in scope automatically; use it sparingly, because invisible setup makes tests harder to understand.

5. Built-in fixtures you will use constantly

  • tmp_path: a fresh temporary directory (a pathlib.Path) unique to the test, as in the db fixture above (test_insert0).
  • monkeypatch: temporarily replace attributes (monkeypatch.setattr(module, "name", fake)), dict items and environment variables (monkeypatch.setenv("APP_MODE", "test")), all undone automatically after the test.
  • capsys: capture print output — capsys.readouterr().out == "hello\n".
  • caplog: capture log records — after logging.getLogger("app").warning("disk %d%% full", 91), "91% full" in caplog.text is true.
  • request: information about the requesting test, used inside fixtures for parametrised fixtures and finalizers.

6. Test doubles and where to patch

A test double is anything that stands in for a real dependency. The vocabulary: a stub returns canned answers; a fake is a working simplified implementation (an in-memory repository); a mock records how it was called so the test can assert on the calls. Python's unittest.mock provides Mock and MagicMock objects and mock.patch, which temporarily replaces a name with a mock.

The most common mocking bug comes straight from py1 and py3: names are bindings in namespaces. Consider:

# app/email_client.py
def send_email(to: str, subject: str) -> None:
    raise RuntimeError("would really send an email")

# app/notify.py
from app.email_client import send_email      # notify gets its OWN name bound to the function

def welcome(user):
    send_email(user["email"], "Welcome!")
    return True

The two tests below both ran and passed; the first proves the wrong patch leaves the real function in place:

from unittest import mock

def test_patch_wrong_place():
    with mock.patch("app.email_client.send_email") as fake:
        with pytest.raises(RuntimeError, match="really send"):   # the REAL function ran
            notify.welcome({"email": "a@b.c"})
        assert not fake.called

def test_patch_right_place():
    with mock.patch("app.notify.send_email") as fake:
        assert notify.welcome({"email": "a@b.c"})
    fake.assert_called_once_with("a@b.c", "Welcome!")

The rule, as the unittest.mock documentation puts it: patch where an object is looked up, not where it is defined. If notify had written import app.email_client and called app.email_client.send_email(...), it would look the function up on the defining module at call time, and patching there would work.

7. autospec: mocks that know the real signature

A plain mock accepts anything. That makes tests pass that should fail: if send_email's signature changes, or the code calls it wrongly, a plain mock does not notice.

def test_plain_mock_accepts_nonsense():
    with mock.patch("app.notify.send_email") as fake:
        fake("a", "b", "c", urgent=True)            # wrong signature: silently accepted

def test_autospec_rejects_nonsense():
    with mock.patch("app.notify.send_email", autospec=True) as fake:
        with pytest.raises(TypeError):
            fake("a", "b", "c", urgent=True)        # autospec copies (to, subject)

autospec=True (or mock.create_autospec(obj)) builds a mock with the real object's signature and attributes, so wrong calls and non-existent methods raise. Modern versions of unittest.mock also catch misspelled assertion methods: calling m.assert_called_once_wiht(1) raised AttributeError: 'assert_called_once_wiht' is not a valid assertion. Default to autospec whenever you patch.

8. monkeypatch, time and HTTP

monkeypatch is pytest's simpler alternative to mock.patch for replacing an attribute with your own function or object. Here is a complete test of a function that calls an HTTP API and reads the clock — the two classic sources of flaky tests:

# app/weather.py
import requests
from datetime import datetime

def should_carry_umbrella(city):
    r = requests.get(f"https://api.example.com/forecast?city={city}", timeout=5)
    r.raise_for_status()
    hour = datetime.now().hour
    return r.json()["hourly"][hour]["rain_mm"] > 0.5
# tests/test_weather.py
import app.weather as weather
from datetime import datetime

class FakeResponse:
    def __init__(self, payload): self._payload = payload
    def raise_for_status(self): pass
    def json(self): return self._payload

def test_umbrella_when_rain_at_current_hour(monkeypatch):
    payload = {"hourly": [{"rain_mm": 0.0}] * 24}
    payload["hourly"][14] = {"rain_mm": 3.2}
    calls = []
    def fake_get(url, timeout):
        calls.append((url, timeout))
        return FakeResponse(payload)
    monkeypatch.setattr(weather.requests, "get", fake_get)

    class FixedDatetime(datetime):
        @classmethod
        def now(cls, tz=None): return cls(2026, 9, 27, 14, 5)
    monkeypatch.setattr(weather, "datetime", FixedDatetime)

    assert weather.should_carry_umbrella("Pune") is True
    assert calls == [("https://api.example.com/forecast?city=Pune", 5)]

Notice the details. weather does import requests and calls requests.get, so patching the get attribute on the requests module object that weather uses works. It did from datetime import datetime, so we replace weather.datetime. The fake response is a tiny class, clearer than a configured mock. And the test also checks the request itself — URL and timeout — because a test that only checks the result would pass even if the code stopped sending the timeout.

The test is still more complicated than it should be, which is a signal about the design. If the function took the forecast client and a clock as parameters (or constructor arguments), the test would simply pass fakes, with no patching at all. Designing for testability — injecting dependencies at the edges — is the long-term fix for heavy mocking. For HTTP specifically, libraries such as responses (for requests) and respx (for httpx) intercept requests at the transport layer; for time, time-machine and freezegun freeze the clock globally.

9. Async tests

pytest itself runs only synchronous test functions. A plugin runs async def tests on an event loop: with pytest-asyncio installed, mark the test and await as usual. Both of these passed:

import asyncio, pytest

@pytest.mark.asyncio
async def test_gather():
    assert await asyncio.gather(fetch(1), fetch(2)) == [2, 4]

@pytest.mark.asyncio
async def test_timeout():
    with pytest.raises(TimeoutError):
        async with asyncio.timeout(0.05):
            await slow()                      # sleeps 10 s; the timeout cancels it

Test timeouts with short limits rather than real waits, and make delays in retry logic configurable so tests do not sleep. The anyio plugin offers the same with support for Trio as well.

10. Property-based testing with Hypothesis

Example-based tests check the cases you thought of. The bill-splitting bug slipped through because nobody thought to try a total not divisible by the number of people. Property-based testing flips the approach: you state a property that must hold for every valid input, and a library generates inputs to try to break it.

from hypothesis import given, strategies as st

@given(st.integers(min_value=0, max_value=10**6), st.integers(min_value=1, max_value=50))
def test_split_sums_to_total(total, people):
    assert sum(split_bill(total, people)) == total

The real output:

total = 1, people = 2
>       assert sum(split_bill(total, people)) == total
E       assert 0 == 1
E        +  where 0 = sum([0, 0])
E        +    where [0, 0] = split_bill(1, 2)
E       Failing test case: test_split_sums_to_total(
E           total=1,
E           people=2,
E       )

Hypothesis found an input that broke the property and then shrank it — repeatedly simplifying while the test kept failing — to the smallest counterexample: one cent between two people. The fix (give the remainder, one cent each, to the first total % people people) is now obvious. Hypothesis saves failing examples in a local database and replays them first on the next run, so the bug stays covered. Good properties to look for: round trips (decode(encode(x)) == x), invariants (sums, lengths, sortedness), idempotence (applying twice equals once), equivalence with a slow but obviously correct reference implementation, and "does not crash" on arbitrary input for parsers.

11. Markers, skipping and expected failures

Markers label tests. @pytest.mark.skipif(sys.platform == "win32", reason="POSIX only") skips conditionally; @pytest.mark.xfail(reason="known bug #123", strict=True) records a known failure, and with strict=True an unexpected pass fails the run, so the marker gets removed when the bug is fixed. Custom markers such as @pytest.mark.slow should be registered in configuration (markers = slow: long-running tests in pytest.ini or pyproject.toml) so typos are caught, and then pytest -m "not slow" gives a fast local run. pytest -rsx lists the reasons for skips and xfails in the summary.

How assertion rewriting works

pytest installs an import hook. When a test module (or conftest.py, or a registered plugin module) is imported, pytest parses its source into an abstract syntax tree, rewrites every assert statement into code that evaluates each sub-expression into temporary variables and, on failure, builds a message from them, then compiles the result and caches the bytecode in __pycache__ with a pytest-specific tag. Comparison details come from hooks: pytest has specialised explanations for sequences, dicts, sets, strings (with diffs) and dataclasses, and plugins can add more through pytest_assertrepr_compare. Because it happens at import time, modules imported before pytest's hook is active are not rewritten, which is why helper modules with asserts must be registered with pytest.register_assert_rewrite to get rich messages.

Fixture resolution and teardown order

For each test, pytest computes the closure of all fixtures it needs, including transitive dependencies and autouse fixtures, and orders them so higher-scoped fixtures are created first. A fixture of a given scope can only request fixtures of the same or wider scope (a session fixture cannot use a function-scoped one), which pytest checks and reports as a ScopeMismatch. Teardown runs in the reverse order of setup, and higher-scoped fixtures are torn down only when the last test using them in that scope has finished. Parametrised fixtures (@pytest.fixture(params=[...])) make every dependent test run once per parameter, and pytest reorders tests to minimise how often expensive parametrised fixtures are rebuilt.

Mock internals and their traps

Mock objects create child mocks on attribute access, which is why a plain mock "has" every attribute and every method. MagicMock additionally configures dunder methods (__len__, __iter__, __enter__), so it can stand in for containers and context managers. spec restricts attributes to those of a real object; autospec goes further and recursively applies specs to methods, including their signatures, and for functions checks the call signature. patch.object(target, "attr") patches an attribute on an object you already hold, avoiding string-path mistakes. AsyncMock (3.8+) returns awaitables, and patching an async def function with autospec produces one automatically.

Test isolation and shared state

Hidden coupling between tests comes from module-level state (caches, registries, singletons), environment variables, the current working directory, files outside tmp_path, and database rows left behind. In the demo, two tests sharing a module-level list passed in file order and failed under pytest-randomly with seeds 1 and 2; running with random order routinely, and with pytest-xdist in parallel (-n auto), makes such bugs visible early. pytest-randomly also reseeds random before each test and prints the seed, so a failing order can be reproduced with -p randomly --randomly-seed=N.

Hypothesis strategies and shrinking

Strategies describe input distributions and compose: st.lists(st.integers(), max_size=20), st.builds(User, email=st.emails()), st.from_type(Order) (derived from type hints), and @st.composite for dependent values. Hypothesis deliberately biases generation toward boundary values (0, -1, empty, very large, special floats such as NaN), which is why it finds edge-case bugs quickly. Shrinking works on the underlying choice sequence rather than on the values themselves, so it shrinks complex structures consistently. @settings(max_examples=...) trades thoroughness for speed; @example(...) pins a specific case; stateful testing (RuleBasedStateMachine) generates sequences of operations against an API and a model of it, finding bugs that only appear after particular sequences.

Coverage done right

coverage.py (usually via pytest-cov) records executed lines, and with branch coverage, whether each branch of each condition was taken. Use it to find untested code, especially untested error paths, and to review whether new code came with tests. Do not use a global percentage as a target: it rewards trivial tests and assertion-free calls. Since Python 3.12, coverage.py can use sys.monitoring (PEP 669) for much lower overhead. Mutation testing tools such as mutmut measure test quality more honestly by introducing small bugs and checking whether any test fails.

Plugins and hooks

Almost everything in pytest is implemented as plugins using the pluggy hook system, and your own conftest.py can implement the same hooks. pytest_addoption adds command-line options (for example --run-live to enable tests that call real APIs), pytest_collection_modifyitems can skip or reorder collected tests based on markers and options, and pytest_runtest_makereport can attach extra information to failures, such as the last log lines or a screenshot in browser tests. The ecosystem covers most needs: pytest-xdist (parallelism), pytest-cov (coverage), pytest-randomly (ordering), pytest-timeout (kill hung tests), pytest-asyncio and anyio (async), and pytest-benchmark (performance). Knowing that these are ordinary hook implementations makes it easy to write a small in-house plugin rather than bending tests around a missing feature.

Flaky tests erode trust

A test that fails one run in fifty teaches the team to click "re-run", and eventually real failures are ignored too. The usual causes, in rough order of frequency: timing (real sleeps, fixed timeouts on a busy CI machine, races in concurrent code), order dependence and shared state, external services, the clock and time zones (tests that fail at midnight or on the last day of the month), and unseeded randomness. Track flaky tests explicitly (CI tools and pytest plugins can report them), fix the root cause, and quarantine with a ticket rather than deleting. Retrying failed tests automatically hides real bugs and should be a temporary diagnostic at most.

Keeping the suite fast

A suite that takes 40 minutes is run less often and blocks merges. Techniques: keep most tests at the unit level with no I/O; share expensive resources at session scope with per-test transactions; run in parallel with pytest-xdist (tests must be independent, and each worker needs its own database); mark slow and integration tests and run them in a separate CI stage; and profile the suite itself with pytest --durations=10, which lists the slowest tests and fixtures.

Databases and integration tests

Unit tests with fakes are fast but can miss real behaviour: SQL dialect differences, constraints, transaction isolation, serialisation. Integration tests against a real database engine of the same kind and version as production catch those. testcontainers-python starts a disposable PostgreSQL (or Redis, Kafka) in Docker for the test session; the schema is migrated once, and each test runs in a transaction rolled back at the end, or against a template database cloned per worker.

Testing ML and LLM code

For ML pipelines, test the deterministic parts rigorously — feature transformations, data validation, shape and dtype contracts, serialisation of models and configs — using small fixed datasets and fixed seeds. For model quality, use evaluation suites rather than unit tests: fixed datasets, metrics with thresholds, and comparisons against the current production model. For LLM applications, unit-test prompt assembly, output parsing and tool dispatch with recorded responses (including malformed and adversarial ones), and run model-behaviour evaluations separately; the LLM track's lm14 covers evaluation. Keep any live calls to paid APIs behind a marker so CI stays deterministic and cheap.

Test data that stays readable

As a codebase grows, tests often come to depend on large shared fixtures — "the standard customer", a 200-row seed file — that nobody dares to change, because dozens of tests silently rely on details of them. Factory fixtures and libraries such as factory_boy or polyfactory avoid this: each test builds the minimum data it needs and states the details that matter to it (make_user(country="IN", verified=False)), so a reader can see why the test expects what it expects. For large expected outputs, snapshot (golden-file) tests, such as syrupy, store the approved output and show a diff on change, with an explicit command to accept intentional updates.

CI configuration

Run the suite on every pull request, on the Python versions you support (a matrix including the newest release catches upcoming breakage early), with warnings turned into errors for your own code (filterwarnings = error) so deprecations fail before they become removals. Upload JUnit XML (--junitxml) so CI can show per-test history, and publish coverage reports for review rather than as a gate.

    base, extra = divmod(total_cents, people)
    return [base + 1 if i < extra else base for i in range(people)]

# app/weather.py
import requests
from datetime import datetime

def should_carry_umbrella(city):
    r = requests.get(f"https://api.example.com/forecast?city={city}", timeout=5)
    r.raise_for_status()
    hour = datetime.now().hour
    return r.json()["hourly"][hour]["rain_mm"] > 0.5

Write tests for this function that are fast, deterministic and never touch the network. What would you change in the design, and why?

Answer

Two things make it hard to test: it calls the network through the module-level requests, and it reads the real clock. A test must control both. The test in body section 8 does so with monkeypatch: replace weather.requests.get with a fake that records its arguments and returns a small FakeResponse object, and replace weather.datetime (the name the module actually uses after from datetime import datetime) with a subclass whose now() returns a fixed moment. Assert both the result and the request that was made (URL and timeout=5), and add cases for no rain (False), exactly 0.5 mm (False, because the comparison is strict), and an HTTP error, where the fake's raise_for_status raises requests.HTTPError and the test uses pytest.raises. Parametrise the rain amounts.

The design change: make the dependencies explicit so tests need no patching. For example:

def should_carry_umbrella(city, *, client, now=datetime.now):
    forecast = client.forecast(city)          # returns parsed hourly data
    return forecast[now().hour]["rain_mm"] > 0.5

Tests then pass a fake client with a forecast method and now=lambda: datetime(2026, 9, 27, 14). The HTTP details (URL, timeout, error handling, parsing) move into the client class, which gets its own tests with a transport-level mock such as responses. Each piece becomes trivially testable, the tests stop depending on import details, and the same client can be reused and swapped. Mention also that the current code has an edge case worth a test: if the API returns fewer than 24 hourly entries, [hour] raises IndexError.
