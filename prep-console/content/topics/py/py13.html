Friday afternoon, a routine deploy of an unchanged service fails in production with ImportError: cannot import name 'soft_unicode' from 'markupsafe'. Nobody touched the code. The requirements.txt listed flask and jinja2==2.11.3, and that pinned Jinja2 depended on MarkupSafe with no upper limit. That morning a new MarkupSafe release removed a function the old Jinja2 used, and the fresh Docker build pulled it in. This exact incident hit thousands of projects in February 2022.

Other versions of the same pain: a notebook that works for its author but not for a colleague because they have a different pandas; a test suite that passes locally and fails in CI because the tests imported the source folder instead of the installed package; a Docker image that takes twenty minutes to build because a package without a matching wheel compiles from source; an internal package name that an attacker registered on the public index. None of these are programming bugs. They are problems of environment: which code, at which version, gets loaded when your program says import.

Packaging has a reputation for confusion because Python accumulated many tools over thirty years. The modern picture is much simpler, built on a few standards: pyproject.toml to describe a project, wheels as the installable format, virtual environments for isolation, and lockfiles for reproducibility, with fast tools such as uv on top. An AI engineer meets all of it daily: GPU-specific wheels for PyTorch, conflicting versions between an LLM SDK and an older library, reproducible training environments, and container images that must build quickly.

This lesson starts from the import system — how import finds code — because everything else is about controlling that. It then covers virtual environments, pyproject.toml, how a project becomes a wheel and how installation works (with a real package built and installed along the way), the crucial difference between version ranges and lockfiles, the modern toolchain, compiled wheels, Docker images and supply-chain security. All commands were run on CPython 3.12.10 in throwaway environments, with build, hatchling and uv 0.12.

Where does import find code?

When you write import httpx, Python walks a list of directories, sys.path, in order and takes the first match. That list typically contains the directory of the script you ran, any directories in the PYTHONPATH environment variable, the standard library, and a directory called site-packages, where installed third-party packages live. Every packaging tool ultimately exists to put the right files, at the right versions, into the right site-packages.

One kitchen per recipe book

Imagine several cooks sharing one pantry. One recipe needs a particular brand of flour; another needs a different one; swapping the flour for one cook ruins the other's cake. The fix is to give each project its own pantry. A virtual environment is exactly that: a directory with its own site-packages and a python that uses it. Install packages "into the project" and they go into that pantry, leaving other projects and the operating system's Python untouched.

python -m venv .venv                 # create
.venv\Scripts\activate               # Windows   (macOS/Linux: source .venv/bin/activate)
python -m pip install httpx          # installs into .venv's site-packages
python -c "import sys; print(sys.prefix != sys.base_prefix)"   # True inside a venv

Two habits follow immediately: never type pip install without knowing which Python it belongs to (use python -m pip or a project tool), and never share an environment between projects.

Recipes and shopping receipts

A project describes what it needs in pyproject.toml, the way a recipe says "flour, about 500 g, any plain wheat flour". Those are ranges: httpx>=0.27,<1. When you install, a resolver chooses one exact version of every package — including the packages your dependencies depend on, the transitive dependencies — that satisfies all the ranges at once. A lockfile is the shopping receipt from that resolution: exact versions and file hashes for everything. Libraries publish recipes; applications keep receipts, so every build buys exactly the same ingredients.

Three layers of reproducibility

It helps to see the whole problem as three nested layers, each answering a different question. The virtual environment answers "which packages can this project see?" — only its own. The lockfile answers "exactly which versions and files are they?" — the same ones every time. The container image (or a pinned machine image) answers "on which interpreter, operating system and system libraries?" — the same ones in development, CI and production. Most packaging incidents are a missing layer: packages installed globally, versions resolved fresh at deploy time, or a production operating system that differs from the one the wheels were tested on. The rest of this lesson builds each layer properly.

Where the pantry analogy breaks: a virtual environment does not copy Python itself. It links to an existing interpreter (the "base" Python) and only isolates the installed packages. That is why a venv is tied to one Python version and to the machine it was created on, and why you recreate environments from the lockfile rather than copying the directory around.

1. The import system and sys.path

When Python executes import x, it first checks sys.modules, a dict of every module already imported in this process; if x is there, it simply binds the name (imports run a module's code only once). Otherwise it asks a series of finders, the main one of which searches each directory in sys.path for a package directory x/ (with an __init__.py) or a module file x.py or a compiled extension. The first match is loaded, executed, stored in sys.modules and bound.

The order of sys.path is the source of many surprises. Its first entry is the directory of the script being run — or, for python -c and the interactive prompt, the empty string meaning the current directory. That entry comes before site-packages. So a folder in your current directory named like an installed package wins:

# flat/tinystats/__init__.py contains a stub whose mean() returns "LOCAL COPY"
cd flat
python -c "import tinystats; print(tinystats.mean([1]), tinystats.__file__)"
# LOCAL COPY  ...\flat\tinystats\__init__.py        ← not the installed package
python -c "import sys; print(repr(sys.path[0]))"
# ''

The same mechanism makes a file called random.py, json.py or requests.py in your project break unrelated imports. python -m package.module runs a module with the current directory on the path and correct package context, which is the right way to run code inside a package.

2. Virtual environments

python -m venv .venv creates a directory containing a pyvenv.cfg file (pointing at the base interpreter), a Scripts (Windows) or bin directory with a python that uses the environment, and an empty Lib/site-packages. When that python starts, it sees pyvenv.cfg, sets sys.prefix to the environment, and puts the environment's site-packages on sys.path instead of the system one. "Activating" only puts that Scripts/bin directory first on your shell's PATH for convenience; running .venv/Scripts/python directly works identically.

Rules that avoid most trouble: one environment per project, created inside the project directory and excluded from version control; always install with python -m pip (or uv) so you use the pip belonging to the Python you mean; never install into the system Python — many Linux distributions now enforce this with PEP 668's "externally managed" marker, which makes pip refuse; and treat environments as disposable, rebuilt from the lockfile. For command-line tools you want globally (Ruff, httpie), pipx or uv tool install give each tool its own hidden environment.

3. pyproject.toml: describing a project

Here is a complete, real project file for a small library, tinystats, with a src/ layout (section 6):

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "tinystats"
version = "0.1.0"
description = "Tiny statistics helpers"
requires-python = ">=3.10"
dependencies = ["httpx>=0.27,<1"]
license = "MIT"

[project.optional-dependencies]
plot = ["matplotlib>=3.8"]

[project.scripts]
tinystats = "tinystats.cli:main"

The [build-system] table (PEP 517/518) names the build backend — the tool that knows how to turn this source into installable artefacts — and what must be installed to run it. Swapping hatchling for setuptools, flit, pdm-backend, or maturin (for Rust extensions) changes nothing else. The [project] table (PEP 621) is standard metadata every tool understands: name, version, supported Python versions, runtime dependencies as version ranges, optional dependencies ("extras", installed as tinystats[plot]), and [project.scripts] entry points that become command-line programs. Tool configuration lives in [tool.ruff], [tool.pytest.ini_options], [tool.mypy] and so on, so one file configures the whole project. Development-only dependencies such as pytest go in [dependency-groups] (PEP 735), which are never published as part of the package.

4. Building: sdists and wheels

Running the standard front end python -m build asks the backend for two artefacts:

python -m build
# Successfully built tinystats-0.1.0.tar.gz and tinystats-0.1.0-py3-none-any.whl

The sdist (.tar.gz) is the source plus metadata; installing it requires building it first, which may run code and need compilers. The wheel (.whl) is the built result, and it is just a zip file. Listing this one shows everything an installer needs:

['tinystats/__init__.py', 'tinystats/cli.py', 'tinystats/core.py',
 'tinystats-0.1.0.dist-info/METADATA', 'tinystats-0.1.0.dist-info/WHEEL',
 'tinystats-0.1.0.dist-info/entry_points.txt', 'tinystats-0.1.0.dist-info/RECORD']

# METADATA (excerpt)
Metadata-Version: 2.5
Name: tinystats
Version: 0.1.0
License-Expression: MIT
Requires-Python: >=3.10
Requires-Dist: httpx<1,>=0.27
Provides-Extra: plot
Requires-Dist: matplotlib>=3.8; extra == 'plot'

# entry_points.txt
[console_scripts]
tinystats = tinystats.cli:main

The filename encodes compatibility tags: py3-none-any means any Python 3, no compiled ABI, any platform. A compiled wheel looks like numpy-2.x-cp312-cp312-manylinux_2_17_x86_64.whl: CPython 3.12, its ABI, Linux on x86-64 with glibc 2.17 or newer (section 9). Note also Requires-Dist with an environment marker (extra == 'plot'); markers such as python_version < "3.11" and sys_platform == "win32" let one package declare platform-specific dependencies.

5. Installing: what pip and uv actually do

Installing the wheel into a fresh environment shows the whole flow. The installer reads the wheel's Requires-Dist, resolves compatible versions for httpx and everything httpx needs, downloads wheels, verifies them, unzips each into site-packages, writes a RECORD of installed files (used for uninstalling), and generates a small executable for each console script:

pip install dist/tinystats-0.1.0-py3-none-any.whl
tinystats 1 2 3 4                 # the generated console script
# 2.5
pip list
# anyio 4.15.1, certifi 2026.7.22, h11 0.16.0, httpcore 1.0.9, httpx 0.28.1,
# idna 3.20, pip 25.0.1, tinystats 0.1.0, typing_extensions 4.16.0

One requested dependency brought six others. That is the transitive dependency tree, and it is where version surprises come from: the application declared a range for httpx but said nothing about h11 or certifi.

During development you want code changes to take effect without reinstalling. An editable install (pip install -e ., which uv sync does for your own project by default) installs a small pointer in site-packages to your source directory instead of a copy.

6. The src/ layout

If the package directory sits at the repository root, running pytest or a script from the root puts the root first on sys.path (section 1), so tests import the working copy, not the installed package. They pass even when the wheel is broken — a data file missing from the build, a module excluded by mistake, a dependency not declared. Putting the package in src/tinystats/ means nothing importable sits at the root; tests can only import the package once it is installed (editable in development), so they exercise what users will actually receive. That is why the packaging guide and most modern templates use it.

7. Ranges versus locks

This distinction is the heart of dependency management. A library — code other people install — should declare the broadest ranges it genuinely supports, because it will be installed next to other libraries with their own constraints, and every unnecessary pin is a potential conflict for someone's application. An application — something you deploy — should install from a lockfile: the exact version, source URL and hash of every package in the resolved tree. uv lock on the tinystats project resolved 26 packages (the plot extra and different dependency sets for Python 3.10, 3.11 and 3.12+ included) into uv.lock, with entries like:

[[package]]
name = "anyio"
version = "4.15.1"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "exceptiongroup", marker = "python_full_version < '3.11'" },
    { name = "idna" },
    { name = "typing-extensions", marker = "python_full_version < '3.15'" },
]
wheels = [
    { url = "https://files.pythonhosted.org/.../anyio-4.15.1-py3-none-any.whl",
      hash = "sha256:6152fdbbf9a77fdec97731721bebf7c4c44f7c29b424b0065826173efc7ed101", ... },
]

Installs from the lock are identical every time, and the hashes mean a tampered or substituted file is rejected. Upgrades then become explicit changes: uv lock --upgrade-package httpx, reviewed and tested, usually opened automatically by Renovate or Dependabot. Other tools produce equivalent locks: Poetry's poetry.lock, PDM's pdm.lock, and pip-tools' pip-compile --generate-hashes, which writes a fully pinned requirements.txt. PEP 751 (Final) standardised a tool-neutral lock format, pylock.toml; uv export --format pylock.toml produced one from the same project, and newer pip versions can install from it.

Why is pip freeze > requirements.txt not a lockfile? The pip freeze output from the test environment lists exact versions — but only for this one environment on this platform and Python version, without hashes, without distinguishing what you asked for from what came along, and it even records the local wheel as a file:// path. It is a snapshot, not a reproducible resolution.

8. The modern toolchain

  • uv (Astral, written in Rust) replaces pip, pip-tools, virtualenv, pipx and pyenv-style Python management with one fast tool: uv init, uv add httpx (edits pyproject.toml and the lock), uv sync (makes the environment match the lock), uv run pytest, uv python install 3.14, and uv run script.py for single-file scripts that declare their dependencies in a comment header (PEP 723). Its speed comes from a global cache, parallel downloads and hard-linking files instead of copying.
  • Poetry and PDM are established project managers with their own lock formats; pip plus pip-tools remains a solid minimal combination; conda/mamba/pixi manage non-Python binaries too (CUDA toolkits, GDAL, compilers), which is why scientific and GPU environments often use them.
  • Ruff lints and formats in one very fast tool, replacing flake8, isort, pyupgrade and black in many projects, configured in [tool.ruff].
  • Type checkers (py10) and pytest (py12) run in CI across the supported Python versions.
  • pre-commit runs formatters, linters and checks on staged files before each commit, so problems are fixed before review.

Which should you choose? For a new application or library in 2026, uv is the default recommendation of many teams: one tool, standard pyproject.toml, a universal lockfile and very fast CI. Existing Poetry or pip-tools setups work well and need no migration unless speed or workflow is a problem. Choose conda, mamba or pixi when the environment must include non-Python binaries that are hard to get as wheels, such as specific CUDA toolkits or geospatial libraries. Whatever the tool, the principles are the same: declare ranges, lock exactly, install from the lock, and update deliberately.

9. Compiled packages and platform wheels

Packages with C, C++ or Rust code — NumPy, pandas, PyTorch, Pydantic's core, cryptography — must be compiled for each platform. To spare users a compiler, maintainers build a wheel per combination of Python version, operating system and architecture, usually with cibuildwheel in CI. Linux wheels follow the manylinux standard: built against an old glibc and bundling other shared libraries (via auditwheel), so they run on most distributions; Alpine uses musl libc and needs musllinux wheels. The installer picks the most specific wheel whose tags match; if none match, it falls back to the sdist and tries to compile, which is the classic cause of slow or failing installs on new Python versions and unusual platforms. The stable ABI (abi3; an ABI, application binary interface, is the binary-level contract between compiled code and the interpreter) lets one wheel serve several Python versions for extensions that restrict themselves to it. The free-threaded builds (py8) have their own tags such as cp314t and need their own wheels.

A related convenience: python -m pip install --dry-run --report report.json httpx shows what a resolution would install without changing anything, and uv tree prints the resolved dependency tree, which is the fastest way to answer "why is this package here?" when an unfamiliar transitive dependency appears in a lockfile diff.

10. Security: the supply chain

Installing a package runs other people's code on your machine, and installing an sdist can run arbitrary build code before you ever import it. Threats include typosquatting (reqeusts), compromised maintainer accounts publishing malicious releases, and dependency confusion, where an attacker publishes a public package with the name of your private internal one and a higher version, so an installer configured with both indexes picks theirs. Defences: lockfiles with hashes; index pinning so internal names can only come from the internal index; a vetted mirror or proxy for production; pip-audit or similar scanners against vulnerability databases; minimal dependencies; and, for publishing your own packages, PyPI's trusted publishing, which lets CI upload via short-lived OpenID Connect tokens instead of long-lived API tokens.

11. Version numbers and specifiers

Python versions follow PEP 440, and dependency ranges are written with specifiers. The ones you meet daily, with what the packaging library (the reference implementation installers use) accepted in a test over a set of sample versions:

SpecifierMeaningAccepted from the samples
>=0.27,<1at least 0.27, below 1.00.27.2, 0.99
~=2.31compatible release: >=2.31, ==2.*2.31.5, 2.32.0
~=2.31.0>=2.31.0, ==2.31.*2.31.5
==3.*any 3.x release3.0, 3.2
!=1.5.0,>=1.4exclude one known-bad release1.4, 1.6 and later

Versions compare numerically per segment (1.10 is newer than 1.9) and pre-releases such as 2.0.0rc1 sort before the final release; installers skip pre-releases unless you ask for them or pin one explicitly. Many projects use semantic versioning (MAJOR.MINOR.PATCH, where a major bump signals breaking changes), others use calendar versioning (2026.7.22, as certifi does). Neither is a guarantee, which is why the lock-and-test workflow matters more than the numbering scheme.

12. Single-file scripts with inline dependencies

Not everything is a project. For a one-off script — a data export, an evaluation run — PEP 723 lets the script declare its own requirements in a special comment block, and a runner such as uv run creates a cached, isolated environment for it on the fly:

# /// script
# requires-python = ">=3.11"
# dependencies = ["httpx>=0.27"]
# ///
import httpx, sys
print("httpx", httpx.__version__, "on Python", sys.version.split()[0])

# uv run report.py
# Installed 7 packages in 56ms
# httpx 0.28.1 on Python 3.12.10

The script is self-describing and reproducible to share (add uv lock --script to lock it too), without polluting any other environment or requiring a requirements.txt next to it.

Inside the import system

sys.meta_path holds finders; CPython's default list contains finders for built-in modules, frozen modules and the path-based finder. The path-based finder consults sys.path_hooks to get a finder for each sys.path entry (a directory, or a zip file via zipimport) and caches them in sys.path_importer_cache. A finder returns a module spec describing how to load the module; the loader then creates the module object, inserts it into sys.modules before executing its code (which is how circular imports partially work), and executes it. Packages have a __path__ that sub-imports search. Directories without __init__.py are namespace packages (PEP 420), which can be split across several directories — useful for plugin namespaces, confusing when created by accident. Editable installs are implemented with .pth files or custom finders in site-packages, which is why some tools resolve editable packages differently from regular ones.

Circular imports

When module A imports B at the top and B imports A, the second import finds A already in sys.modules but only partly executed, so names defined later in A do not exist yet, producing ImportError: cannot import name 'x' from partially initialized module. Fixes, in order of preference: move the shared code to a third module both can import; import the module rather than names from it (import a then use a.x at call time); defer the import into the function that needs it; and for type annotations only, use if TYPE_CHECKING: imports (py10).

How resolution works and why it can be slow

Choosing versions that satisfy every constraint is NP-hard in general. pip uses a backtracking resolver (since 20.3): it picks candidate versions, and when it hits a conflict, backtracks and tries older ones, which can take a long time for large trees with loose constraints. uv uses PubGrub, a conflict-driven algorithm that learns from each conflict to prune the search and produces readable explanations of unsolvable constraints. uv's lock is universal: it resolves once for every supported Python version and platform, recording markers (as in the anyio entry), so one lockfile serves Windows developers and Linux production. Metadata is fetched without downloading whole wheels using PEP 658 metadata files and HTTP range requests.

Wheel tags in detail

A wheel filename is {name}-{version}(-{build})?-{python tag}-{abi tag}-{platform tag}.whl. The Python tag (cp312, py3) says which interpreter; the ABI tag (cp312, abi3, none) says which binary interface compiled code expects; the platform tag (manylinux_2_28_aarch64, macosx_11_0_arm64, win_amd64, any) says where it runs. python -m pip debug --verbose lists the tags your interpreter accepts, in priority order. Understanding tags explains most "no matching distribution" errors: the package simply has not published a wheel for that combination yet.

GPU packages: an AI-engineering special case

PyTorch and similar libraries ship different builds for different accelerator stacks (CUDA versions, ROCm, CPU-only). Because standard wheel tags do not describe CUDA versions, these builds are published on separate indexes (https://download.pytorch.org/whl/cu128-style URLs), and projects must direct the installer to the right index per platform, which uv supports through per-package index configuration and markers. The wheels are several gigabytes, which dominates Docker build times and image sizes, so teams cache them aggressively and separate the heavy dependency layer from application code. Work on "wheel variants" aims to let installers select accelerator-specific builds automatically.

Reproducibility beyond Python packages

A lockfile pins Python packages but not the interpreter build, the operating system libraries, the compilers used for sdists, or the CUDA driver. Fully reproducible environments pin those too: a base image by digest, the Python version exactly (uv's .python-version or the image tag), system packages at fixed versions, and for ML, the driver and CUDA toolkit. Conda-based lockfiles (conda-lock, pixi) and Nix go further by pinning native dependencies, at the cost of more complex tooling.

What "installed" means: dist-info and uninstalling

Each installed distribution leaves a name-version.dist-info directory in site-packages containing its METADATA, the RECORD of every file it installed (with hashes), entry_points.txt, INSTALLER (which tool installed it) and optionally direct_url.json for packages installed from a path or URL. importlib.metadata.version("httpx") and importlib.metadata.entry_points() read these at runtime, which is how plugin systems such as pytest's discover installed plugins. Uninstalling removes exactly the files in RECORD. Mixing installers in one environment — conda and pip, or pip and a system package manager — causes trouble precisely because each keeps its own records and may overwrite the other's files.

Docker images for Python services

A good image builds fast and runs small. Structure: a builder stage that copies only pyproject.toml and the lockfile and installs dependencies (uv sync --frozen --no-install-project), so that layer is cached until dependencies change; then copy the source and install the project; then a final stage from a slim base with the same Python version and libc, copying only the environment and the application, running as a non-root user. Set PYTHONUNBUFFERED=1 so logs appear immediately. Prefer Debian-slim over Alpine unless every dependency publishes musllinux wheels. Pin the base image by digest and rebuild regularly to pick up security patches.

Dependency updates as a routine

Teams that update rarely face painful "big bang" upgrades across dozens of breaking changes. Teams that let Renovate or Dependabot open small, frequent update pull requests, each run through the full test suite, keep the lock current with little effort and get security fixes quickly. Group low-risk updates (patch releases of development tools) to reduce noise, and pin a schedule so updates do not land on Friday afternoons.

Private packages and monorepos

Internal libraries are published to a private index (Artifactory, AWS CodeArtifact, Google Artifact Registry, a self-hosted devpi) or consumed directly from Git. Configure installers so internal names resolve only from the private index. In monorepos, uv workspaces let several packages share one lockfile and depend on each other by path, so a change to a shared library is tested against all its consumers in one pull request.

CI speed

Dependency installation is often the slowest part of CI. Cache the installer's download cache keyed by the lockfile hash, use uv (typically an order of magnitude faster than pip for cold installs, more with a warm cache), avoid building sdists by preferring versions with wheels, and install only the dependency groups a job needs (no GPU packages for the linting job).

Notebooks and research code

Data-science and ML work often starts in notebooks with packages installed ad hoc into whatever kernel is running, and months later nobody can reproduce a result. The cheap discipline that fixes most of it: one project directory per piece of work with a pyproject.toml and lockfile, a Jupyter kernel registered from that project's environment, random seeds and data versions recorded alongside results, and the lockfile committed with the notebook. When a model moves to production, the same lock becomes the starting point for the serving image instead of a fresh, untested resolution.

Upgrading the Python version itself

New Python releases arrive every October. Upgrading is usually worthwhile (py11's free speed-ups, security support), but the blockers are compiled dependencies without wheels for the new version and deprecated APIs removed after their warning period. The routine: add the new version to the CI test matrix early, with warnings as errors, watch which dependencies fail, and switch production once the lockfile resolves cleanly with wheels for everything. Python versions receive bug fixes for about two years and security fixes for five, per PEP 602, so plan upgrades before the end-of-life date rather than after.

Incidents and responses

Recurring incident types: an unpinned transitive dependency releases a breaking change (the MarkupSafe story); a package is yanked or deleted from the index and builds fail (lockfiles with a vetted mirror protect against this); a malicious release of a popular package is published for a few hours (hash-pinned locks and delayed adoption help — some teams only accept versions older than a few days); and a new Python version ships before key compiled dependencies publish wheels for it, so upgrades wait. Each has the same lesson: control exactly what gets installed, and change it deliberately.

About 30 minutes on Python 3.10+. Everything happens in a scratch directory with its own virtual environments, so nothing touches your system Python. Outputs are from CPython 3.12.10 with build, hatchling and uv 0.12; versions of downloaded packages will be newer for you.

  2. Create the project. Make tinystats/pyproject.toml as in body section 3, plus src/tinystats/__init__.py (importing mean from .core), src/tinystats/core.py (def mean(xs): xs = list(xs); return sum(xs) / len(xs)) and src/tinystats/cli.py (a main() that prints the mean of sys.argv[1:] as floats).
  3. Build it. In a venv with pip install build, run python -m build. Then inspect the wheel: 
    python -c "import zipfile; z = zipfile.ZipFile('dist/tinystats-0.1.0-py3-none-any.whl'); print(z.namelist()); print(z.read('tinystats-0.1.0.dist-info/METADATA').decode())"

    Find Requires-Dist, the extra and the entry point.

  4. Install and use it. In a second, fresh venv, pip install dist/tinystats-0.1.0-py3-none-any.whl, run tinystats 1 2 3 4 (expect 2.5), and pip list to see the transitive dependencies httpx brought.

  7. Break and fix a circular import. Create a.py with from b import g and def f(): return 1, and b.py with from a import f and def g(): return f(). Run python -c "import a" and read the "partially initialized module" error. Fix it by changing b.py to import a and calling a.f() inside g.
Diagnose it

A deploy on Friday breaks production with ImportError: cannot import name 'soft_unicode' from 'markupsafe'. Nothing in your code changed; your requirements.txt lists flask and jinja2==2.11.3 without other pins. What happened, and how do you prevent it permanently?

Answer

What happened: a transitive dependency moved. Jinja2 2.11 depends on MarkupSafe with only a lower bound; MarkupSafe 2.1.0 (released in February 2022) removed the long-deprecated soft_unicode, which old Jinja2 still imported. The fresh image build resolved the newest MarkupSafe allowed by the ranges, so an unchanged codebase broke. You would confirm it by comparing pip freeze from the last good image and the broken one: only MarkupSafe's version differs.

Immediate fix: pin markupsafe<2.1 (the last working version) or upgrade Jinja2 and Flask to releases that no longer use soft_unicode, redeploy, then investigate calmly.

Permanent fix: keep only direct dependencies, as ranges, in pyproject.toml; generate a lockfile pinning every transitive dependency with hashes (uv lock, or pip-compile --generate-hashes); build images only from the lock (uv sync --frozen or pip install --require-hashes) so the same commit always produces the same environment; and let Renovate or Dependabot propose upgrades as pull requests that run the full test suite. Upgrades then happen on purpose, tested, on a weekday — not by accident during a deploy. Add a CI job that fails if the lockfile is out of date with pyproject.toml (uv lock --check), so nobody forgets to re-lock.
