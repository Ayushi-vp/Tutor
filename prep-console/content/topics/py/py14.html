A team launches an LLM-backed support assistant as a FastAPI service. In testing it is fast. On launch day, response times climb from 800 ms to 30 seconds, and the health check starts failing, so the orchestrator restarts pods, which makes things worse. The cause turns out to be one helper that calls an internal user-profile service with the synchronous requests library from inside an async def endpoint. Each call blocks the event loop for its duration, and with no timeout set, a few slow profile lookups stall every request on the worker, including the health check.

Meanwhile the analytics team's nightly job that computes customer features has started taking four hours. It iterates over a 20-million-row DataFrame with iterrows, and a well-meaning fix, df[df.active]["score"] = 0, silently does nothing, so the model is trained on unfiltered scores for a week.

Both teams wrote correct Python. What they lacked was knowledge of how Python behaves in production: how a web server actually runs your code, what a worker is, why an innocent blocking call can take a service down, what must surround every outbound call, how logs and configuration should work across a hundred containers, and which pandas idioms are thousands of times slower or silently wrong. This lesson is where the earlier topics — concurrency (py9), memory (py8), types and validation (py10), packaging (py13) — meet in running systems.

It starts with how a Python web service runs: the WSGI and ASGI interfaces, servers such as gunicorn and uvicorn, worker processes and the reverse proxy in front. It compares Django, Flask and FastAPI and shows, with real measurements, the def versus async def trap. It then covers the production essentials: configuration validated at startup, structured logging with request ids, timeouts and connection pools, background jobs, health checks and graceful shutdown. The second part turns to data work with pandas: vectorisation, chained assignment and copy-on-write in pandas 3.0, dtypes and memory, missing values and time zones. Examples were run on CPython 3.12.10 with FastAPI 0.141, uvicorn 0.54, Pydantic 2.13 and pandas 3.0.6.

The restaurant model of a web service

Picture a restaurant. The reverse proxy or load balancer is the host at the door: it greets every guest (terminates TLS, the encryption layer covered in net9), turns away troublemakers, and seats people at whichever section has room. The application server is the kitchen manager, and the workers are the cooks. Each cook follows the same recipes (your application code). How many dishes a cook can handle at once depends on the kind of cook: a synchronous cook works on one order from start to finish, even while it sits in the oven; an asynchronous cook starts many orders and moves between them while each is waiting.

Two contracts: WSGI and ASGI

How does a server like gunicorn call your Flask or FastAPI code? Through a standard contract, so any server works with any framework. WSGI (Web Server Gateway Interface, PEP 3333) is the synchronous contract: your application is a function that receives the request and returns the response, and the worker is busy until it returns. ASGI (Asynchronous Server Gateway Interface) is the async contract: your application is a coroutine that receives and sends messages, so one worker can juggle thousands of requests while they wait, and can keep connections open for WebSockets and streamed responses such as LLM tokens.

What production adds

Code that works on a laptop needs a few more things to survive in production. It must get its configuration from the environment and refuse to start if it is wrong. It must log in a form that can be searched across many instances, tagged with a request id. Every call it makes to another service needs a timeout, because in a distributed system something is always slow. Slow work must move to background jobs. And it must report its health and shut down gracefully, because orchestrators restart and move processes constantly. None of this is glamorous, and all of it is what separates a demo from a service.

Following one request

Trace a single request through that picture. A browser sends POST /orders. The load balancer terminates TLS and forwards plain HTTP to one instance. On that instance, the operating system hands the connection to one of the worker processes waiting on the shared socket. The worker parses the request, the framework matches the route, validates the JSON body into a typed object, and calls your handler. Your handler takes a connection from the worker's database pool, runs two queries, calls a pricing service through a pooled HTTP client with a timeout, logs a line tagged with the request id, and returns. The framework serialises the result, the worker writes the response, and the connection returns to the pool. Every production concern in this lesson attaches to one of those steps.

Where the restaurant analogy breaks: cooks in a kitchen share one pantry, but worker processes share nothing. Each has its own copy of the application's memory, caches, loaded ML model and database connections, which is why "add more workers" costs memory and connections, not just CPU.

1. WSGI: the synchronous contract

A complete WSGI application is a callable that takes the request environment (a dict of CGI-style variables plus the request body stream) and a start_response callback, and returns an iterable of bytes:

def app(environ, start_response):
    body = f"hello from {environ['PATH_INFO']}".encode()
    start_response("200 OK", [("Content-Type", "text/plain"),
                              ("Content-Length", str(len(body)))])
    return [body]

# called by a test harness with PATH_INFO="/users":
# 200 OK [('Content-Type', 'text/plain'), ('Content-Length', '17')]
# [b'hello from /users']

Flask and Django (in its classic mode) produce exactly such a callable. The server — gunicorn, uWSGI, mod_wsgi — handles sockets and HTTP parsing, then calls it for each request in a worker. The key property: the worker is occupied until the call returns. If the handler waits two seconds on a database, that worker serves nothing else for two seconds. Concurrency therefore comes from running many workers (processes) or threads.

2. ASGI and the event loop

An ASGI application is async def app(scope, receive, send): it receives events ("request body chunk arrived", "client disconnected") and sends events ("response start", "body chunk"). Because it is a coroutine, a worker running an event loop (uvicorn, Hypercorn, Granian) can have thousands of requests in progress, switching whenever one awaits I/O (py9). ASGI also covers WebSockets and server-sent events, and it is what makes token-by-token streaming of LLM output efficient: an open stream costs a small coroutine rather than a whole worker. FastAPI and Starlette are ASGI frameworks; Django supports ASGI for async views.

3. Servers and workers

gunicorn is a pre-fork process manager. Its master process binds the listening socket, forks N workers that all accept connections from it, monitors them, restarts any that crash or exceed --timeout, and reloads them gracefully on signals. Worker classes determine concurrency inside each process: sync (one request at a time), gthread (a thread pool per worker), or uvicorn.workers.UvicornWorker for ASGI apps (an event loop per worker). uvicorn can also run on its own with --workers. gunicorn's documentation suggests (2 × cores) + 1 sync workers as a starting point; the right number comes from load testing while watching CPU, memory per worker, latency percentiles and database connections. In Kubernetes, many teams instead run one or two workers per container and scale the number of pods.

Useful gunicorn settings: --max-requests with --max-requests-jitter recycles workers after a number of requests, capping slow memory leaks (py8); --preload imports the application in the master before forking so read-only memory is shared copy-on-write (combine with gc.freeze(), py8); --timeout kills workers stuck longer than the limit, a safety net, not a substitute for timeouts in your code.

4. Frameworks: Django, Flask, FastAPI

  • Django: batteries included — ORM with migrations, admin interface, authentication, forms, templating, security middleware. The fastest route to a complete product around a relational database, with strong conventions.
  • Flask: a minimal core (routing, request and response objects, templates) and extensions for everything else. Flexible and easy to understand; you assemble and maintain the stack.
  • FastAPI: built on Starlette (ASGI) and Pydantic. Handler parameters and return types, declared with type hints (py10), drive request parsing, validation, serialisation and automatically generated OpenAPI documentation. Async-first, which makes it the common choice for JSON APIs, LLM backends and model serving.

5. The def versus async def trap, measured

FastAPI runs an endpoint declared with async def directly on the event loop, and one declared with plain def in a thread pool. That design is convenient but produces the most common production bug in FastAPI services. Three endpoints, each waiting one second, hit with ten concurrent requests through uvicorn:

@app.get("/async-sleep")
async def async_sleep():
    await asyncio.sleep(1)       # non-blocking wait
    return {"ok": True}

@app.get("/sync-sleep")
def sync_sleep():
    time.sleep(1)                # blocking, but runs in FastAPI's thread pool
    return {"ok": True}

@app.get("/async-blocking")
async def async_blocking():
    time.sleep(1)                # blocking call ON the event loop
    return {"ok": True}

# measured, 10 concurrent requests each:
# /async-sleep     1.19 s
# /sync-sleep      1.05 s
# /async-blocking 10.04 s

The rule: in async def endpoints use only async libraries (httpx.AsyncClient, asyncpg, async SQLAlchemy, async Redis clients); if an endpoint must call blocking code, declare it with plain def or wrap the call in await asyncio.to_thread(...). Also note the thread pool is finite (40 threads by default in the underlying AnyIO library), so many slow def endpoints can still saturate it.

6. Configuration validated at startup

Configuration belongs in the environment, not in code, so the same image runs in development, staging and production (the twelve-factor principle), and secrets are injected by the platform or a secrets manager. The common failure is reading variables lazily with os.environ.get scattered through the code, so a missing value surfaces as None in the middle of a request. Instead, declare all settings once and validate them when the process starts, for example with pydantic-settings:

from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str          # required
    workers: int = 4
    debug: bool = False

settings = Settings()          # reads DATABASE_URL, WORKERS, DEBUG from the environment

# with WORKERS=8 and DEBUG=true but no DATABASE_URL:
#   1 validation error for Settings
#   database_url  Field required [type=missing, ...]
# with DATABASE_URL set: settings.workers == 8 (an int), settings.debug is True
# with WORKERS=eight:
#   workers  Input should be a valid integer, unable to parse string as an integer

A bad deploy now fails immediately with a precise message, and the rest of the code receives typed values.

7. Logging that works across a fleet

Use the logging module, not print. Each module gets a logger with logging.getLogger(__name__), the application configures handlers and formats exactly once at startup, and libraries never configure logging themselves. In production, emit structured records — JSON with level, logger, message and context — so a log platform can filter and aggregate them. The most valuable piece of context is a request id, generated (or taken from an incoming header) by middleware and stored in a contextvars variable, which is automatically separate per thread and per asyncio task (py9):

import logging, json, contextvars
request_id = contextvars.ContextVar("request_id", default="-")

class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({"level": record.levelname, "logger": record.name,
                           "msg": record.getMessage(), "request_id": request_id.get()})

# after middleware sets request_id to "req-7f3a":
# {"level": "INFO", "logger": "app.orders", "msg": "creating order 1001", "request_id": "req-7f3a"}
# {"level": "WARNING", "logger": "app.orders", "msg": "inventory low for sku-42", "request_id": "req-7f3a"}

Pass the id to downstream services in a header so logs and traces from different services join up (OpenTelemetry does this automatically as trace context). Log exceptions once, where handled, with logger.exception (py7), and keep secrets, tokens and personal data out of logs.

8. Outbound calls: timeouts, pools and retries

Every call to another service can hang, and the defaults will not save you: requests has no default timeout at all. Against a local socket that accepted connections and never replied, requests.get(url, timeout=(3.05, 2)) raised ReadTimeout ... (read timeout=2) after 2.02 s; without a timeout it would have waited forever, holding a worker. The first number is the connect timeout, the second the maximum wait between bytes of the response. httpx defaults to a 5-second timeout, which is better but still worth setting deliberately.

Create one client per process and reuse it — requests.Session or httpx.Client/AsyncClient — so TCP and TLS connections are pooled rather than re-established per call (net13 covers connection pools). Retry only idempotent operations, with exponential backoff and jitter, at one layer (py4). For dependencies that fail for long periods, a circuit breaker stops calling them and fails fast, and a bulkhead (a separate, bounded pool) keeps one slow dependency from consuming all workers. The same logic applies to databases: a connection pool per worker process means total connections are pool size × workers × instances, which must stay within the database's limit; poolers such as PgBouncer help at scale.

9. Background jobs, health checks and shutdown

Work that is slow, retryable or not needed for the response — sending email, generating a report, re-embedding a document — goes to a task queue. The handler enqueues a job (with ids, not large objects) and returns, often 202 Accepted with a job id; worker processes run jobs from a broker such as Redis or RabbitMQ with retries and visibility. Celery is the long-established option; RQ, Dramatiq and arq are simpler; workflow engines such as Temporal handle long multi-step processes. Jobs must be idempotent, because delivery is at-least-once.

Orchestrators need two signals. A liveness check asks "is the process healthy enough to keep running?" and should be cheap and not depend on other services, or a database blip makes every instance restart at once. A readiness check asks "should traffic be sent here now?" and can include loaded models and reachable dependencies. On shutdown the platform sends SIGTERM, waits a grace period (30 s by default in Kubernetes), then SIGKILL. A graceful shutdown stops accepting new work, finishes in-flight requests and the current job, closes pools, and exits; gunicorn and uvicorn implement this for their workers, and the Dockerfile must use the exec form of CMD so the signal reaches Python rather than a shell.

10. pandas in pipelines: speed

pandas stores each column as an array (NumPy or Arrow), so column operations run in compiled code, while row-by-row iteration builds Python objects for every row. Computing quantity × price over 200,000 rows with pandas 3.0.6:

[row["qty"] * row["price"] for _, row in df.iterrows()]   # 6.13 s
df.apply(lambda r: r["qty"] * r["price"], axis=1)          # 1.06 s
[r.qty * r.price for r in df.itertuples()]                 # 0.165 s
df["qty"] * df["price"]                                    # 1.18 ms

That is over 5,000 times between the first and last line. iterrows is slowest because it builds a Series (with an index and a dtype) for every row; apply(axis=1) is a Python loop in disguise (py11). Conditional logic uses np.where or Series.where, lookups use merge or map, and aggregation uses groupby(...).agg(...).

11. pandas in pipelines: correctness

Chained assignment. df[df["qty"] > 5]["price"] = 0 selects rows (producing a new object) and then assigns into that object. Under copy-on-write, the default and only mode in pandas 3.0, it can never modify df: in the test it raised a ChainedAssignmentError warning and changed zero rows. The correct form is a single .loc call, df.loc[df["qty"] > 5, "price"] = 0, which updated 88,906 rows. Copy-on-write also means modifying a subset (sub = df[df.country == "IN"]; sub["qty"] = -1) never changes the original, which makes pipelines predictable (py1 discussed views versus copies).

Missing values and dtypes. A NumPy integer column cannot hold a missing value, so pd.Series([1, 2, None]) silently becomes float64 with nan, and ids like 1234567890123456789 can lose precision as floats. The nullable Int64 dtype keeps integers and uses <NA> for missing values. Decide explicitly how each stage treats missing data, because NaN propagates through arithmetic and is excluded by most aggregations by default.

Memory. Repeated strings are expensive: a 200,000-row country column used 10.2 MB as strings (pandas 3.0's default str dtype, or the old object dtype) and 0.2 MB as category. Read only needed columns (usecols, or columnar Parquet), downcast numeric types, and process large files in chunks or with Polars or DuckDB, which are multi-threaded and can work out of core.

Time zones. Store timestamps in UTC and convert at the edges. Daylight saving produces surprising arithmetic: adding one hour to 01:30 on 29 March 2026 in Europe/Berlin gives 03:30+02:00, because 02:00 to 03:00 does not exist that night. Naive (zone-less) timestamps compared with aware ones raise errors, and mixing them silently in groupbys by date is a classic cause of off-by-one-day reports.

12. Testing a service without its infrastructure

Web services are tested at the HTTP level with a test client that calls the application in-process, no server needed, and with real dependencies replaced through the framework's dependency injection (py12). In FastAPI, app.dependency_overrides swaps a dependency for a fake:

from fastapi import FastAPI, Depends
from fastapi.testclient import TestClient
from pydantic import BaseModel, PositiveInt

app = FastAPI()
class Order(BaseModel):
    sku: str
    qty: PositiveInt
def get_repo():
    raise RuntimeError("real database")
@app.post("/orders", status_code=201)
def create(order: Order, repo=Depends(get_repo)):
    repo.append(order)
    return {"sku": order.sku, "qty": order.qty}

fake = []
app.dependency_overrides[get_repo] = lambda: fake
client = TestClient(app)
client.post("/orders", json={"sku": "A1", "qty": 2})   # 201 {'sku': 'A1', 'qty': 2}, fake now holds 1 order
client.post("/orders", json={"sku": "A1", "qty": 0})   # 422 'Input should be greater than 0' at ['body', 'qty']

The second call shows validation doing its job before any of your code runs: the request never reached the handler. Tests like these cover routing, validation, status codes and serialisation quickly; a smaller set of integration tests then runs against a real database and the real server process.

How FastAPI turns type hints into an API

At startup FastAPI inspects each endpoint's signature (py3, py10): parameters that match path segments become path parameters, simple types become query parameters, Pydantic models become the JSON body, and Depends(...) parameters are resolved through a dependency-injection graph (database sessions, the current user). Pydantic validates incoming data and serialises return values according to the declared response_model, which also filters out fields you did not intend to expose. The same metadata generates the OpenAPI schema and interactive docs. Because behaviour comes from signatures, decorators that erase them (py4) or annotations that cannot be resolved break the API at import time rather than at runtime.

Sizing: Little's law in practice

The number of requests in progress equals arrival rate × time each spends in the system (Little's law). A service receiving 200 requests per second with 250 ms average latency has about 50 requests in flight. With sync workers, you need at least 50 workers or threads across the fleet, plus headroom for latency spikes, because when a dependency slows to 2 s the same traffic needs 400. With async workers, in-flight requests cost little memory, but the downstream pools (database connections, API rate limits) still bound concurrency. This arithmetic explains why a slow dependency without timeouts exhausts a sync service: in-flight requests grow until every worker is waiting.

Process models and memory

Each worker imports the whole application: frameworks, ORM models, and for ML services, model weights. A 2 GB model with eight workers is 16 GB, unless it is loaded before fork with --preload and stays shared copy-on-write (py8 explains why reference counting and GC erode that sharing, and gc.freeze()). For GPU inference, several workers cannot share one GPU's memory safely without a model server. That is why ML serving often uses one process per GPU with dynamic batching (vLLM, Triton), with the Python web tier as a thin, async gateway.

contextvars and request-scoped state

Thread-local storage fails under asyncio, where many requests share one thread. contextvars.ContextVar values belong to a context that asyncio copies into each task when it is created, so setting a request id in middleware makes it visible to everything that request's task calls, and invisible to other requests. Threads started with threading.Thread did not inherit the context before 3.14; 3.14's thread_inherit_context flag makes new threads start with a copy of the caller's context (on by default in the free-threaded build), and asyncio.to_thread copies the current context into the worker thread, whereas loop.run_in_executor does not: in a test, a request id set before the call was visible through to_thread but read as the default through run_in_executor, unless the call is wrapped as contextvars.copy_context().run(fn).

Copy-on-write in pandas 3.0, mechanically

Under copy-on-write, operations that produce a new DataFrame or Series from an existing one may share the underlying arrays instead of copying them, which saves memory and time. pandas tracks references to each array; the first write to an object whose data is shared with another triggers an actual copy of just that data. So derived objects behave like copies while costing like views until written. Chained assignment cannot work in this model because the intermediate object is a temporary whose data would be copied on write, which is why pandas 3.0 turns it into a warning rather than silently doing nothing. The same release made a dedicated string dtype the default for text columns.

Choosing between pandas, Polars and DuckDB

pandas remains the most widely used and best integrated with plotting, statistics and ML libraries. Polars, written in Rust on Arrow memory, is multi-threaded, has a lazy API that optimises the whole query (pushing filters down, selecting only needed columns) and handles larger-than-memory data in streaming mode; it is often several times to an order of magnitude faster on large transformations. DuckDB is an in-process analytical SQL database that queries Parquet, CSV and even pandas or Polars frames directly with a vectorised, parallel engine. A common production pattern is to do heavy joins and aggregations in DuckDB or Polars and hand the smaller result to pandas or scikit-learn.

Threads inside WSGI workers

gunicorn's gthread worker runs a thread pool inside each process, so one process can handle several requests at once while they wait on I/O, sharing that process's memory and pools. Because the GIL is released during socket waits (py8), this gives much of async's concurrency benefit for I/O-heavy Flask or Django apps without rewriting them, at the cost of thread-safety concerns in application code and the GIL's serialisation of any CPU work. A common configuration is a few processes (for CPU parallelism and fault isolation) each with a modest number of threads (for I/O overlap). On the free-threaded build (3.14), threads could also run CPU work in parallel, if every extension in the stack supports it.

Incident pattern: the slow dependency that takes everything down

A dependency slows down; requests waiting on it pile up; worker pools or event loops fill; health checks start failing; the orchestrator restarts instances, which lose their warm caches and connection pools and make things worse. The defences are layered: timeouts on every call, bounded pools and concurrency (bulkheads), circuit breakers that fail fast, liveness checks that do not depend on other services, load shedding (returning 503 early when queues are long), and retry budgets so clients do not multiply the load. The scale track's sc12 covers these resilience patterns in depth.

Observability for Python services

OpenTelemetry has automatic instrumentation for the common frameworks, database drivers and HTTP clients, producing traces with spans for each request and each outbound call, which answers "where did the time go?" across services. Pair traces with structured logs carrying the trace or request id, metrics for request rate, error rate and latency percentiles per endpoint (the RED method), worker and pool saturation, and event-loop lag for async services. Continuous profiling (py11) catches CPU regressions that metrics only hint at.

Capacity and cost for LLM backends

Services that call LLM APIs have unusual profiles: requests last seconds rather than milliseconds, responses are often streamed, and cost is per token. That favours ASGI workers (a streamed response holds a cheap coroutine, not a whole process), strict per-request token and time budgets, semaphores sized to the provider's rate limits (py9), caching of repeated prompts or embeddings, and metrics per endpoint for tokens, cost and time to first token alongside the usual latency and error rates. The AI-engineering track's ae1 and ae2 go into architecture and cost modelling.

Deploying safely

Build one immutable image from the lockfile (py13), promote the same image through environments, run database migrations as a separate step that is backward-compatible with the previous code version (add columns before using them, remove them after), and roll out gradually with automated rollback on error-rate or latency regressions. Readiness probes should only pass once the application, caches and models are loaded, or users hit cold instances during every deploy.

Data pipelines in production

Pipelines fail quietly more often than services fail loudly. Guard them with schema and data-quality checks at the boundaries (column presence and types, null rates, value ranges, row counts versus yesterday), using Pandera, Great Expectations or plain assertions; make each step idempotent and re-runnable for a given date partition; write outputs atomically (to a temporary location, then rename or commit) so consumers never read half-written data; and alert on freshness, not just failures. The ML track's ml14 covers the training/serving skew that follows when the online feature code and the batch pipeline compute features differently.

Security basics every Python service needs

Validate all input with typed models; use parameterised queries or the ORM, never string-formatted SQL; keep dependencies patched from the lockfile; never log or return secrets and stack traces to clients (disable debug modes in production — Flask's and Django's debug pages execute code or leak settings); set request size limits and timeouts at the proxy; and run containers as a non-root user with a read-only file system where possible. Diagnose it

A Flask API on gunicorn with 4 sync workers serves 200 requests/s normally. Every few days, requests start timing out and all 4 workers show as busy, but CPU is near zero. A handler calls a partner API with requests.get(PARTNER_URL). What is happening, and what do you change?

Answer

What is happening: requests has no default timeout. When the partner API hangs — accepts the connection and never responds — each request to that handler blocks a sync worker indefinitely. With only 4 workers, 4 hung calls take the entire service down: every other endpoint queues behind them, and the health check may fail too, triggering restarts. Near-zero CPU confirms the workers are waiting, not working; py-spy dump on a worker would show it stuck in a socket read inside requests. Little's law explains why it only happens sometimes: at 200 requests/s even a few seconds of partner slowness needs far more than 4 workers in flight.

Changes:

  • Always pass a timeout: session.get(url, timeout=(3.05, 5)) (connect, read), using one shared requests.Session per process for connection pooling.
  • Wrap the partner in a circuit breaker with a fallback or a fast 503 when it is failing, so its outage does not consume your capacity.
  • Isolate it: if the call is slow by nature, move it to a background job, or give it its own bounded worker pool (a bulkhead) so it cannot starve other endpoints.
  • Consider an async stack (FastAPI with httpx.AsyncClient) if many requests wait on I/O, since one worker can then hold hundreds of in-flight calls — but the missing timeout is the actual bug, and an async service without timeouts fails the same way.
  • Keep gunicorn's own --timeout as a safety net that kills stuck workers, and add alerts on worker saturation and on the partner's latency and error rate.
