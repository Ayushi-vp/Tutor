Two kinds of questions come up in almost every Python interview. The first is the snippet: "What does this print?" — a loop that removes items from the list it is iterating, a default argument that remembers values, round(2.5), a match statement with a constant in it. The second is "what's new?": "Have you used pattern matching? What are exception groups for? What changed in 3.12? What are t-strings?" Candidates who answer the first kind from memory stumble on the next variation; candidates who can't answer the second sound like they stopped learning Python years ago.

Both kinds matter outside interviews too. The snippet puzzles are distilled production bugs. A configuration loader that writes cfg.get("port") or 8080 silently overrides a deliberate port 0. A report that rounds with round surprises finance with 2.5 becoming 2. A cleanup loop that removes items while iterating skips every second one. A match on HTTP status codes that uses a bare constant name treats every status as OK. And the version features are the tools you are expected to reach for: TaskGroup instead of loose tasks, tomllib instead of a third-party parser, the 3.12 generic syntax, and in 3.14 lazily evaluated annotations and template strings that make safe HTML and SQL construction possible.

This lesson is the capstone of the Python track. Its first half regroups the classic gotchas by the handful of rules that explain them — several taught in earlier topics (py1, py3, py5, py7) — and adds the ones not covered elsewhere: floating point, rounding and division, truthiness, comparisons and datetimes. Its second half is a version-by-version tour from Python 3.8 to 3.14, with working examples of the features you should recognise and use, and a deeper look at pattern matching and t-strings. It ends with how teams manage Python upgrades. The gotchas were run on CPython 3.12.10; features that exist only in 3.13 or 3.14 are shown as documented in the official release notes and PEPs and are labelled with their version.

Six rules behind almost every gotcha

Python's surprising behaviours are not a random list. Nearly all of them follow from six rules, and once you can name the rule, you can predict the output instead of remembering it.

  1. Names are references. Assignment never copies; mutation is visible through every name bound to the object (py1). This explains aliasing, [[0] * 3] * 3, shared class attributes and caches that return shared objects.
  2. Some things are evaluated once. Default arguments are evaluated when def runs; class bodies run once; module code runs once on first import (py3, py6).
  3. Closures look names up late. A function reads an enclosing variable's value when called, not when created (py3).
  4. Floats are binary approximations. Most decimal fractions cannot be stored exactly, so arithmetic and rounding produce surprises (this lesson).
  5. Truthiness conflates "empty" with "missing". 0, "", [] and None are all false in an if (this lesson).
  6. Iteration and mutation don't mix. Iterators are single-pass and track positions, so changing a collection while looping over it goes wrong (py5).

Python keeps changing — on a schedule

Since 2019, CPython releases a new minor version every October (PEP 602). Each gets about two years of bug-fix releases and security fixes until five years after release. So in late 2026, 3.10 through 3.14 are supported (3.10 reaching end of life in October 2026), and 3.15 is due. Each release adds language features and library improvements and removes things that were deprecated two releases earlier.

What "modern Python" means in practice

Knowing the feature list is less important than knowing which features change how you write everyday code. From 3.8 to 3.14 those are: f-strings everywhere (with = for debugging), | for unions and dict merges, match for dispatching on data shapes, dataclasses and typed signatures with the built-in generic syntax, TaskGroup and asyncio.timeout for async code, exception groups for concurrent failures, and, from 3.14, t-strings for safe templating and forward references without quotes. A codebase that uses these reads as current; one full of Optional[List[Dict]], %-formatting and loose create_task calls reads as a decade old.

How to answer a "what does this print?" question

In an interview, narrate the rule, not just the answer: "The default list is created once when def runs, so both calls append to the same list, and it prints [1, 2] [1, 2]. The fix is a None default." That shows the interviewer you can handle the next variation. Then mention how you would catch it in practice — a linter rule or a test — because that is what a senior engineer does with a known trap.

Where the "six rules" framing breaks down: some behaviours are CPython implementation details rather than language rules — small-integer caching that makes is seem to work, or the exact moment a generator's cleanup runs. Name them as implementation details when they come up, and never rely on them.

1. References and evaluation time: the classics, briefly

These were taught in detail earlier; here is the one-line explanation for each, as you would give it in an interview.

def f(x, acc=[]):                  # default evaluated once (py1, py3)
    acc.append(x); return acc
f(1); f(2)                         # [1, 2] — the same list both times

fns = [lambda: i for i in range(3)]
[fn() for fn in fns]               # [2, 2, 2] — closures read i when called (py3)

grid = [[0] * 3] * 3
grid[0][0] = 1                     # [[1, 0, 0], [1, 0, 0], [1, 0, 0]] — one inner list, three times (py1)

t = (1, [2])
t[1] += [3]                        # raises TypeError AND leaves t == (1, [2, 3]) (py1)

Two more in the same family. A mutable class attribute (members = [] in the class body) is shared by every instance (py6). And except SomeError as e: deletes e at the end of the block — after the except in the test, print(e) raised NameError: name 'e' is not defined — because keeping it would create a reference cycle through the traceback's frames (py7, py8).

2. Floating point

Python's float is an IEEE 754 64-bit binary number: 53 bits of precision in base 2. Fractions whose denominator is a power of two (0.5, 0.25, 0.375) are exact; most decimal fractions, like 0.1, are repeating fractions in binary, the way 1/3 is 0.333... in decimal, so they are stored as the nearest representable value.

0.1 + 0.2                  # 0.30000000000000004
0.1 + 0.2 == 0.3           # False
math.isclose(0.1 + 0.2, 0.3)   # True — compare with a tolerance
decimal.Decimal(0.1)       # 0.1000000000000000055511151231257827021181583404541015625 (the float's true value)
decimal.Decimal("0.1") + decimal.Decimal("0.2")   # Decimal('0.3') — exact decimal arithmetic

Python prints floats with the shortest decimal string that converts back to the same binary value, which is why 0.1 displays as 0.1 even though it is not exactly 0.1 — the error only shows when operations accumulate it. Rules of thumb: never compare floats with == after arithmetic; use math.isclose (relative tolerance) or an absolute tolerance appropriate to the domain; for money, use integer minor units (cents) or Decimal constructed from strings, never from floats; for summing many floats accurately, math.fsum.

3. Rounding and integer division

round(x) uses round-half-to-even ("banker's rounding"): round(2.5) is 2 and round(3.5) is 4. Rounding halves always upwards would bias sums and averages upwards; alternating by evenness cancels out. Floating-point representation adds a second layer: round(2.25, 1) is 2.2 (2.25 is exact in binary, so the even rule applies), but round(2.35, 1) is 2.4, because 2.35 is actually stored as slightly more than 2.35. For financial rounding rules, use Decimal.quantize with an explicit rounding mode such as ROUND_HALF_UP.

The // operator is floor division: it rounds towards negative infinity, so -7 // 2 is -4, and % is defined to match (-7 % 2 is 1), keeping (a // b) * b + a % b == a true. int(-3.5) and math.trunc(-3.5) truncate towards zero instead, giving -3. C, Java and JavaScript truncate integer division, so ported code can silently change behaviour for negative numbers.

4. Truthiness, None and defaults

In a boolean context, False, None, numeric zero (0, 0.0), empty strings and empty containers are false; almost everything else is true, including "0", " " and [0]. This makes if items: a clean "non-empty" test, and makes "missing" checks dangerous:

cfg = {"port": 0}
cfg.get("port") or 8080      # 8080 — the deliberate 0 is lost
cfg.get("port", 8080)        # 0    — default only when the key is missing
port = cfg.get("port")
if port is None:              # explicit "missing" test
    port = 8080

Also remember [] == False is False even though not [] is True: truthiness and equality are different questions. When None is itself a meaningful value, use a private sentinel object as the "not provided" marker (py1).

5. Comparisons and chaining

Comparison operators chain: 1 < x < 10 means 1 < x and x < 10, which is convenient. The same rule produces puzzles: False == False in [False] is True, because it means (False == False) and (False in [False]). is compares identity and must not be used for values (py1). Sorting mixed types raises: sorted([3, "a"]) gives TypeError: '<' not supported between instances of 'str' and 'int'. And string sorting is by code point, so sorted(["b", "B", "a"]) is ['B', 'a', 'b']; pass key=str.lower (or str.casefold for full Unicode case folding) for human ordering.

6. Iteration, slicing and strings

Removing from a list while iterating over it skips elements; mutating a dict's size while iterating raises RuntimeError; a generator can be consumed once (py5). Slicing never raises for out-of-range bounds — [1, 2, 3][10:20] is [] — while indexing does (IndexError: list index out of range), so a slice can hide an off-by-one bug that an index would have exposed. str.split() with no argument splits on runs of whitespace and drops empty strings, but split(" ") keeps them: "a b c".split(" ") is ['a', 'b', '', 'c']. str.strip("abc") strips any of those characters, not the substring; for a prefix or suffix use removeprefix/removesuffix (3.9).

7. Datetimes and time zones

A naive datetime has no time zone and means whatever the programmer assumed; an aware one carries a tzinfo. datetime.utcnow() returns a naive value that merely happens to hold UTC time, which then gets treated as local time elsewhere; it is deprecated since 3.12 and emitted a DeprecationWarning in the test. Use datetime.now(datetime.UTC) (the UTC alias is 3.11+; timezone.utc before), store and compute in UTC, convert to local zones with zoneinfo (3.9) only for display, and remember that daylight-saving transitions create non-existent and repeated local times (py14).

10. Structural pattern matching in depth

match (3.10) compares a subject against case patterns in order and runs the first that matches, binding parts of the subject to names as it goes. It is designed for dispatching on the shape of data:

def classify(ev):
    match ev:
        case {"type": "click", "x": int(x), "y": int(y)}:
            return f"click {x},{y}"
        case {"type": "key", "key": "q" | "Q"}:
            return "quit"
        case [first, *rest] if rest:
            return f"batch {first}+{len(rest)}"
        case str() as s:
            return f"text {s}"
        case _:
            return "unknown"

classify({"type": "click", "x": 1, "y": 2, "extra": 9})   # 'click 1,2' — extra keys are ignored
classify({"type": "key", "key": "Q"})                      # 'quit'
classify([1, 2, 3])                                        # 'batch 1+2'
classify("hi")                                             # 'text hi'
classify(3.0)                                              # 'unknown'

Key semantics: mapping patterns match if the listed keys are present and ignore extra keys (use **rest to capture them); sequence patterns match lists and tuples but deliberately not strings; class patterns call isinstance and then read attributes, with positional sub-patterns mapped through the class's __match_args__ (dataclasses define it automatically); int(x) is a class pattern that checks the type and binds. And the trap: a bare name is a capture pattern that matches anything. Compiling a match with case OK: followed by case _: fails with SyntaxError: name capture 'OK' makes remaining patterns unreachable; with no later case it compiles and silently matches everything. Compare against constants with dotted names (HTTPStatus.OK), literals, or a guard.

11. Template strings (3.14)

f-strings are convenient but dangerous for building HTML, SQL or shell commands, because by the time a library sees the result, user input has been merged into the string and cannot be told apart from the trusted parts. PEP 750 adds t-strings: the same syntax with a t prefix, but the result is a string.templatelib.Template, not a str. According to the 3.14 documentation:

# Python 3.14
variety = "Stilton"
template = t"Try some {variety} cheese!"
type(template)      # <class 'string.templatelib.Template'>
list(template)
# ['Try some ', Interpolation('Stilton', 'variety', None, ''), ' cheese!']

Iterating a template yields the literal strings and Interpolation objects, each carrying the evaluated value, the source expression text, and any conversion (!r) and format spec. A processing function can therefore treat the two differently — escape every interpolated value for HTML, turn each into a bound SQL parameter, or quote each for a shell — and then assemble the result. Because a Template is not a str, an API that accepts only templates makes unsafe concatenation a type error rather than a code-review item. The standard library supplies the types; escaping functions come from libraries built on them.

12. Everyday traps not covered elsewhere

Methods that mutate return None. xs = xs.sort() leaves xs as None, because list.sort, list.append, dict.update and random.shuffle change the object in place and return None by convention (py1). The functional counterparts — sorted(xs), xs + [item], {**d, **other} — return new objects. The opposite trap applies to immutable types: name.strip() on its own line does nothing, since strings cannot change; the result must be assigned (name = name.strip()).

Strings are sequences of code points, not characters. "café" typed with a precomposed é has length 4, but the visually identical "café" (e followed by a combining accent) has length 5 and compares unequal; unicodedata.normalize("NFC", ...) makes them equal. An emoji with a skin-tone modifier has length 2 in Python and takes 8 bytes in UTF-8. Case-insensitive comparison needs casefold, not lower: "Straße".lower() == "strasse" is False, while "Straße".casefold() == "strasse" is True. Text from users, files and LLM output should be normalised before comparing, deduplicating or counting length limits.

Dict views are live. k = d.keys() followed by d["b"] = 2 gives list(k) == ['a', 'b']: views reflect later changes (py2). Snapshot with list(d) when you need a fixed set.

Shadowing modules. A file in your project named random.py, email.py, json.py or test.py is found before the standard library's module of the same name, because the script's directory comes first on sys.path (py13), producing baffling AttributeErrors in unrelated imports. Similarly, a variable named list, dict, id or type shadows the built-in for the rest of its scope (py3).

How floats are stored and printed

A 64-bit float has a sign bit, an 11-bit exponent and a 52-bit fraction with an implicit leading 1, giving 53 significant bits — about 15 to 17 significant decimal digits. Every float is exactly a fraction with a power-of-two denominator; (0.1).as_integer_ratio() reveals it as 3602879701896397 / 36028797018963968. Since Python 3.1, repr prints the shortest decimal string that round-trips to the same float, which hides the error until arithmetic accumulates it. Special values follow IEEE 754 too: float("inf"), -0.0 (which equals 0.0 but has a sign), and NaN, which is unequal to itself (py1). math.fsum uses extra precision internally and returns the correctly rounded sum, which matters when adding many values of different magnitudes, a common case in metrics and ML.

Pattern matching implementation details

The compiler turns a match statement into a sequence of type checks, length checks, key lookups and comparisons; there is no special runtime "matcher" object. Class patterns use isinstance and getattr; positional sub-patterns rely on __match_args__, a tuple of attribute names that dataclasses and named tuples generate. Mapping patterns use the mapping's get method for listed keys, so they work with any collections.abc.Mapping. Sequence patterns reject str, bytes and bytearray on purpose, since treating a string as a sequence of characters is rarely what dispatch code wants. Guards are evaluated after bindings, so names bound by a failed guard may still be set, which is why case-bound names should not be relied on outside their block.

How t-strings are evaluated

At runtime a t-string evaluates each interpolated expression eagerly, left to right, exactly like an f-string, but does not call format or str: it stores the values, the source text, the conversion and the format spec. Template exposes strings (the literal parts, always one more than the interpolations), interpolations and values, and supports concatenation with other templates but not with plain strings. This design lets processors apply different policies — HTML escaping, SQL parameter binding, structured logging that keeps values as fields rather than formatting them into the message — while keeping the familiar f-string syntax and its compile-time checking.

Deferred annotations and what they change

Before 3.14, annotations were evaluated when a function or class was defined, costing time at import and failing on forward references (py10). Under PEP 649 and 749, the compiler generates an __annotate__ function and evaluates it only when someone asks for annotations, in one of three formats (values, forward references or strings) via annotationlib. For ordinary code nothing changes except that forward references work without quotes. For frameworks that read annotations — dataclasses, Pydantic, FastAPI, ORMs — the details of when and how they ask matter, which is why their 3.14 support landed with specific releases.

The release cycle and supporting several versions

PEP 602 fixed an annual October release. Each version receives regular bug-fix releases for about two years (extended from 18 months for 3.13 and later) and then source-only security fixes until five years after its first release. Libraries typically support all non-end-of-life versions; the Scientific Python community's SPEC 0 recommends supporting Python versions for three years after release, which is why NumPy and pandas drop old versions sooner. Supporting several versions in one codebase means writing to the oldest syntax you support, using typing_extensions for newer typing constructs, gating library features with sys.version_info >= (3, 12) checks, and testing on every version in CI.

Where CPython is heading

The two big long-term projects are visible in 3.13 and 3.14. The free-threaded build removes the GIL at a small single-thread cost and is officially supported but still opt-in; its success depends on the extension ecosystem publishing compatible wheels. The JIT compiler, experimental and off by default, builds on the specialising interpreter; its gains are modest so far and workload-dependent. Sub-interpreters offer isolated parallelism within one process. None of these change how you write ordinary Python, but they change the answers to "how do I use all my cores?" (py8, py9) over the next few releases.

Why Python strings are code points

Since Python 3, str is a sequence of Unicode code points, and CPython stores each string in the narrowest fixed-width form that fits its largest code point — 1, 2 or 4 bytes per code point (PEP 393) — so indexing is O(1) and len counts code points. What users perceive as one character, a grapheme cluster, can be several code points: a base letter plus combining marks, an emoji plus a skin-tone modifier, or flags made of two regional-indicator symbols. That is why truncating a string at a code-point index can split a visible character, and why UI and database length limits (often in bytes, or in UTF-16 units in JavaScript) disagree with len. Libraries such as regex with \X, or grapheme segmentation packages, handle user-perceived characters when it matters.

Catching gotchas automatically

Most of this lesson's traps can be caught before review. Ruff (or flake8-bugbear) flags mutable default arguments (B006), function definitions in loops that use the loop variable (B023), mutable class attributes without ClassVar (RUF012), bare except (E722), and datetime.utcnow and naive datetimes (the DTZ rules). The compiler itself warns about is with literals, rejects unreachable capture patterns, and since 3.14 warns about return in finally. Type checkers catch None handling and many truthiness bugs. Enabling these in CI is cheap insurance.

Money, measurements and ML metrics

Financial code uses integer minor units or Decimal with explicit quantisation and rounding modes, and rounds once at defined points rather than repeatedly. Scientific and ML code accepts floating point but compares with tolerances (math.isclose, numpy.allclose), sums carefully (math.fsum, pairwise summation in NumPy), and watches for precision loss when using float32 or bfloat16. Evaluation reports that print metrics to many decimal places invite false precision; round for display only.

Upgrading Python in production

Upgrades are routine for teams that treat them as such. Keep the newest Python in the CI matrix from its first release candidate, with deprecation warnings turned into errors for your own code, so incompatibilities surface months early. Use Ruff's pyupgrade rules (UP) to modernise syntax once the oldest supported version allows it — Optional[X] to X | None, List[int] to list[int], old-style formatting to f-strings. Re-resolve the lockfile for the new version to confirm every dependency publishes wheels, benchmark (behaviour such as the 3.14 garbage collector changed within a release series), and roll out gradually. Track end-of-life dates: 3.10 stops receiving security fixes in October 2026, so services still on it need a plan now.

Text normalisation in data and LLM pipelines

Deduplication, search indexes, evaluation metrics and prompt caches all compare strings, and invisible differences — Unicode normalisation forms, non-breaking spaces, different quote characters, trailing whitespace — make equal-looking text compare unequal. Pipelines that ingest documents or model output normalise once at the boundary (NFC or NFKC, whitespace collapsing, casefold where case is irrelevant) and record which normalisation was applied, so that training data, retrieval indexes and evaluation all see text the same way.

Adopting new features responsibly

New syntax is only usable when every environment that runs the code supports it: a library that uses match cannot support Python 3.9, and one that uses def f[T] requires 3.12. Applications that control their runtime can adopt features as soon as they upgrade; libraries lag by the length of their support window. Some features are worth a version bump on their own — TaskGroup and asyncio.timeout make async code markedly safer, and 3.14's t-strings enable safe templating APIs — while others are conveniences that can wait.

Knowing which Python you are actually running

A surprising number of "this feature doesn't work" reports come from code running on a different interpreter than the developer assumed: a system Python in a cron job, an old base image in CI, a notebook kernel pointing at another environment. Log sys.version and sys.executable at service start-up, declare requires-python in pyproject.toml so installers refuse unsupported versions (py13), pin the interpreter in Docker images and .python-version files, and fail fast with a clear message if a script needs newer features (if sys.version_info < (3, 11): sys.exit("needs Python 3.11+")). On 3.13 and later, sys._is_gil_enabled() also tells you whether a free-threaded interpreter is running with the GIL disabled, which matters when diagnosing concurrency behaviour (py8). These checks cost seconds to add and save hours of confusion.

Interview technique for snippet questions

When given a snippet, read it aloud line by line, name the rule at the line where it bites ("the default is evaluated once here"), state the output, and then propose the fix and how you would prevent recurrence (a lint rule, a test, a type). If unsure, say which rule you are applying; interviewers value the reasoning over instant recall, and a clearly reasoned wrong answer is often corrected in one exchange.
