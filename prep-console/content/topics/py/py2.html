A data engineer writes a script to remove duplicate user ids from a list of a million records while keeping the original order. The logic is obviously correct:

out = []
for uid in ids:
    if uid not in out:
        out.append(uid)

On the 1,000-record test file it finishes instantly. On the real file it runs for hours. Nothing is wrong with the logic; the problem is that uid not in out on a list compares uid against every element already collected. The loop does that a million times against a list that grows to a million, which is on the order of half a trillion comparisons. Changing one line — keep a set of seen ids next to the list — makes the whole thing finish in well under a second.

This is the most common kind of performance bug in Python, and it is not about clever algorithms. It comes from not knowing what the built-in containers cost. Python makes every container look equally convenient: in, indexing, append and pop work on nearly everything. Under the hood they are very different machines. A list is an array, so it is fast at the end and slow at the front; a dict is a hash table, so it is fast at finding a key but uses more memory; a deque is fast at both ends but slow in the middle. Picking the wrong one does not raise an error. It just makes your program a thousand times slower once the data is real.

Interviewers probe this constantly, both directly ("what does x in list cost?") and inside coding questions, where using a list as a queue or sorting to find a maximum quietly turns an O(n) solution into O(n²).

This lesson starts by defining big-O notation, then opens up each container in turn: how a list is laid out in memory and why appending is cheap but inserting at the front is not; what a tuple adds; how a hash table works and how CPython's dict and set implement one; and the standard-library structures — deque, heapq, bisect, Counter, defaultdict, OrderedDict — built for the jobs the basic four do badly. It finishes with memory: why a million Python ints take far more space than a million numbers should, and what NumPy does differently. All timings and sizes were measured on CPython 3.12.10, 64-bit Windows.

Cost that grows with size: big-O in one page

We need a way to talk about how expensive an operation is without timing it on every machine. Big-O notation describes how the cost grows as the number of elements, n, grows, ignoring constant factors:

  • O(1), constant: the cost does not depend on n. Reading xs[5] takes the same time for a list of ten items or ten million.
  • O(log n), logarithmic: the cost grows by one step each time n doubles. Binary search over a million sorted items needs about 20 steps.
  • O(n), linear: the cost grows in proportion. Scanning a list twice as long takes twice as long.
  • O(n log n): the cost of a good sort.
  • O(n²), quadratic: usually an O(n) operation inside a loop over n items. Double n and the time quadruples.

One more term: amortised cost is the average per operation over a long run. An operation that is usually trivial but occasionally expensive can still be "amortised O(1)" if the expensive cases are rare enough.

Four containers, four machines

Think of the built-in containers as different ways to organise a filing room.

A list is a row of numbered pigeonholes. Going straight to pigeonhole 500 is instant. Adding a folder at the end of the row is instant as long as there is an empty hole. Inserting one at the front means shuffling every folder one hole to the right. Finding "the folder labelled Smith" means checking holes one by one.

A tuple is the same row of pigeonholes, sealed: you cannot add, remove or swap folders, which makes it safe to share and usable as a label itself.

A dict is a room with a clerk who has a rule for turning any label into a pigeonhole number — that rule is the hash. Asking for "Smith" means computing the number and walking straight there. That is why finding by key is fast no matter how many folders there are, and why the label must never change (py1): if it did, the clerk would compute a different number and look in the wrong place.

A set is the same room with labels but no folders: it answers "do we have Smith?" and nothing more.

The rule of thumb

Ask what your code does most. Iterating in order and indexing by position: list. Fixed record or composite key: tuple. Looking up by key or checking membership: dict or set. Adding and removing at both ends, as in a queue: deque. Repeatedly taking the smallest or largest item: heapq. Keeping things sorted and searching them: bisect. The rest of the lesson explains why each of those is the right machine.

Where the filing-room analogy breaks: pigeonholes in a Python list do not contain the folders, only notes saying where each folder is (py1: containers hold references). That is why a list can mix types, and why a list of a million numbers takes far more memory than a million numbers would.

1. list: a dynamic array of references

In CPython a list object has a small header (its reference count, its type, its length and its capacity) and a pointer to a separate block of memory holding an array of references, one 8-byte pointer per slot on a 64-bit machine. Because the slots are contiguous and equally sized, the address of slot i is just start + 8 × i, which is why xs[i] is O(1) regardless of length.

A plain array has a fixed size, but a list can grow, so it is a dynamic array: it allocates more slots than it currently uses. The number of slots in use is the length; the number allocated is the capacity. When an append finds a free slot, it just writes the pointer and increments the length. When the array is full, CPython allocates a bigger block, copies the pointers across and frees the old block. The CPython 3.12 source computes the new capacity as roughly newsize + newsize/8 + 6, rounded down to a multiple of 4 — about 12.5 percent headroom plus a little. You can watch it happen with sys.getsizeof, which reports the header plus the pointer array:

import sys
lst = []
print(sys.getsizeof(lst))            # 56   (header only, no array yet)
for i in range(40):
    lst.append(i)
    # print whenever the size jumps:
# len=1  size=88  capacity=4
# len=5  size=120 capacity=8
# len=9  size=184 capacity=16
# len=17 size=248 capacity=24
# len=25 size=312 capacity=32
# len=33 size=376 capacity=40

Capacity is (size − 56) / 8. Thirty-three appends caused only six reallocations. Because each reallocation adds room proportional to the current size, the total copying across n appends adds up to a constant multiple of n, so each append is amortised O(1).

The same layout explains the expensive operations. insert(0, x) and pop(0) must move every other pointer one slot, which is O(n). remove(x) and x in lst must search from the start, O(n). Slicing lst[a:b] copies b − a pointers, O(k). lst.sort() is O(n log n). Here is what that means in real time for a million integers:

ids_list = list(range(1_000_000))
ids_set = set(ids_list)
999_999 in ids_list    # measured: about 12.5 ms per check
999_999 in ids_set     # measured: about 0.14 µs per check (including call overhead)

A factor of nearly 100,000. Inside a loop of a million iterations, the list version is the "runs for hours" script from the introduction.

2. Sorting

sorted(iterable) returns a new list; lst.sort() sorts in place and returns None (the "mutate and return None" convention from py1). Both accept key=, a function called once per element to produce the value to compare, and reverse=True. Python's sort is stable: items with equal keys keep their original relative order, which lets you sort by several fields in passes (sort by secondary key, then by primary key):

sorted([("b", 2), ("a", 2), ("c", 1)], key=lambda t: t[1])
# [('c', 1), ('b', 2), ('a', 2)]   — 'b' still precedes 'a' among the 2s

The algorithm is a merge sort that first finds already-sorted stretches ("runs") in the data and then merges them. It was Timsort from Python 2.3; since 3.11 CPython uses the Powersort rule for deciding which runs to merge. Either way it is O(n log n) in general and close to O(n) when the input is already mostly sorted, which is common in real data.

3. tuple: a sealed array

A tuple has the same idea as a list — a header plus an array of references — but the array is allocated inline with the header at exactly the right size, because it can never grow. That makes it a little smaller (sys.getsizeof((1, 2, 3)) is 64 bytes versus 88 for the equivalent list) and slightly cheaper to create. More important than the bytes: a tuple is immutable and therefore hashable if its contents are, so it can be a dict key or set member. That makes tuples the natural representation of composite keys, such as (user_id, date), and of fixed records returned from functions. When positional access becomes unreadable, typing.NamedTuple adds field names while staying a tuple.

4. Hash tables: the idea

We want to find an item by its key without scanning. The trick is to turn the key into a slot number. A hash table is an array of slots; to store a key, compute hash(key) (an integer, py1), reduce it to a slot index, and put the entry there. To look it up later, compute the same index and look in one place.

Two different keys will sometimes produce the same slot; that is a collision. CPython resolves collisions with open addressing: if the slot is taken by a different key, it computes the next slot to try from a fixed probe sequence and keeps going until it finds the key or an empty slot. An empty slot means "not present", which is why the table must always have some empty slots.

The fuller the table, the more collisions and the longer the probes. So the table is resized — to a bigger array, with every entry reinserted — before it gets too full. The fraction in use is the load factor; CPython keeps dicts at most two-thirds full. As with list growth, resizing is proportional to size and happens rarely, so insertion is amortised O(1), and with a low load factor most lookups succeed on the first or second probe.

5. dict: CPython's compact hash table

Here is the actual lookup, step by step, for d["cat"]:

  1. Compute h = hash("cat"), a 64-bit integer.
  2. The table size is a power of two, say 8. Take the low bits: i = h & 7, giving a slot between 0 and 7. Taking low bits is a single fast machine instruction.
  3. Look at slot i. If it is empty, the key is absent: raise KeyError.
  4. If it holds an entry, compare the stored hash with h. If they differ, it cannot be our key. If they match, check stored_key is "cat" or stored_key == "cat". On success, return the value.
  5. Otherwise, compute the next slot with the recurrence from CPython's source, i = (5*i + 1 + perturb) mod size, where perturb starts as the full hash and is shifted right by 5 bits each step. Mixing in the high bits spreads out keys whose low bits collide. Go back to step 3.

Storing the hash in each entry means collisions are usually rejected by comparing two integers, without calling a possibly slow __eq__, and a resize can reinsert everything without recomputing any hashes.

The memory layout is the clever part. Since Python 3.6 a dict holds two arrays. The entries array is dense and stores (hash, key, value) triples in the order they were inserted. The indices array is the actual hash table: a sparse array of small integers, each either "empty" or a position in the entries array. The load-factor slack now costs only one to eight bytes per empty index slot rather than a 24-byte empty entry. And because entries are appended in order, iterating the dict walks the dense array in insertion order — which is why, since 3.7, insertion order is a language guarantee, not a coincidence.

A few behaviours follow from this design. Reassigning an existing key updates its entry in place, so it keeps its original position: d = {"b": 1, "a": 2}; d["c"] = 3; d["b"] = 9 iterates as ['b', 'a', 'c']. Deleting a key marks its entry as a dummy rather than shifting the array, so probe sequences through that slot keep working; the space is only reclaimed at the next resize, and a dict never shrinks just because you delete. Adding or removing keys while iterating would invalidate the walk, so CPython detects it: RuntimeError: dictionary changed size during iteration. Iterate over list(d) if you need to modify.

The views returned by d.keys() and d.items() are live (they reflect later changes) and support set operations: d.keys() & {"a", "z"} gives {'a'}. And because keys are compared by hash and ==, keys that are equal are the same key even if their types differ: {1: "int", 1.0: "float"} evaluates to {1: 'float'}, since 1 == 1.0 and hash(1) == hash(1.0).

6. set and frozenset

A set is a hash table of keys with no values, so membership, add and remove are O(1) on average. Sets use their own table (not the compact dict layout), which is why they are not ordered. They shine at two jobs. The first is fast membership, the fix for the deduplication script: keep seen = set() and test uid not in seen. (If you just need order-preserving deduplication, list(dict.fromkeys(items)) does it in one line, using a dict's keys as an ordered set: list(dict.fromkeys([3, 1, 3, 2, 1])) is [3, 1, 2].) The second is set algebra, where each operation costs time proportional to the sizes involved:

{1, 2, 3} | {3, 4}      # union:        {1, 2, 3, 4}
{1, 2, 3} & {2, 3, 9}   # intersection: {2, 3}
{1, 2, 3} - {1}         # difference:   {2, 3}
{1, 2} ^ {2, 3}         # symmetric difference: {1, 3}

frozenset is the immutable, hashable version, usable as a dict key — for example, a key representing an unordered pair of users.

7. collections.deque: a queue that is fast at both ends

For a first-in, first-out queue you need to add at one end and remove at the other. A list can only do one of those cheaply. collections.deque ("double-ended queue", pronounced "deck") is implemented as a doubly linked list of fixed-size blocks, each holding 64 references. Adding or removing at either end touches only the end block, and allocates or frees a block occasionally, so append, appendleft, pop and popleft are all O(1). The cost is that reaching the middle means walking blocks: dq[i] is O(1) near the ends but O(n) toward the middle.

The difference is dramatic, and grows with n because pop(0) is O(n) per call and therefore O(n²) to drain:

from collections import deque
# drain a queue of n items; measured on 3.12
# n = 10,000:  list.pop(0)   12.3 ms   deque.popleft   1.5 ms
# n = 100,000: list.pop(0) 1488.7 ms   deque.popleft  10.7 ms

Ten times more items made the list version 120 times slower — the signature of O(n²). A deque with maxlen is also a ready-made ring buffer that discards from the opposite end when full: after appending 0 to 4 into deque(maxlen=3) it holds deque([2, 3, 4], maxlen=3), perfect for "the last N events".

8. heapq: always know the smallest item

A heap is a binary tree in which every parent is less than or equal to its children, so the smallest item is always at the root. heapq stores this tree in a plain list with no pointers: the children of index i are at 2i + 1 and 2i + 2. Pushing appends at the end and "sifts up", swapping with the parent while smaller; popping takes the root, moves the last item to the root and "sifts down". Each walk is at most the tree's height, log₂ n, so push and pop are O(log n) and peeking at heap[0] is O(1). heapify(list) builds a heap in O(n).

Two practical patterns. First, heapq is a min-heap only, so for a max-heap push negated priorities. Second, if you push (priority, item) tuples and two priorities tie, Python compares the items, which fails for unorderable items like dicts (TypeError: '<' not supported between instances of 'dict' and 'dict'). The standard fix is (priority, next(counter), item) with counter = itertools.count(), which breaks ties by insertion order. heapq.nlargest(k, iterable) and nsmallest keep a heap of only k items, making "top k of a huge stream" O(n log k) time and O(k) memory: heapq.nlargest(2, [5, 1, 9, 3]) is [9, 5].

9. bisect: binary search on a sorted list

If a list is sorted you can find where a value belongs by binary search: compare with the middle element and discard the half it cannot be in, repeating until one position remains — O(log n). bisect.bisect_left(a, x) returns the leftmost position where x could be inserted keeping order, bisect_right the rightmost: for [1, 3, 5, 7] and x = 5 they return 2 and 3. bisect.insort(a, x) inserts in order. Searching is O(log n), but inserting still shifts elements, so it is O(n) overall. Use bisect for lookup tables (grade boundaries, time-bucketing) and mostly-read sorted data; for heavy inserts into a sorted collection, the third-party sortedcontainers package is the usual answer. Since Python 3.10 the bisect functions accept key=.

10. The dict variants in collections

  • Counter counts hashable items: Counter("mississippi").most_common(2) gives [('i', 4), ('s', 4)]. It supports addition and subtraction of counts.
  • defaultdict(factory) calls factory() to create a value for a missing key, so grouping becomes groups[key].append(item) with no existence check. Beware that merely reading a missing key inserts it.
  • OrderedDict is mostly superseded by ordered dicts, but keeps two useful methods: move_to_end(key) and popitem(last=False), which together implement a least-recently-used (LRU) cache in a few lines. With od built from "abc", od.move_to_end("a") gives order ['b', 'c', 'a'] and popitem(last=False) removes 'b'.
  • ChainMap searches several dicts in order without merging them — command-line overrides over environment settings over defaults. ChainMap({"debug": True}, {"debug": False, "port": 80}) returns True for "debug" and 80 for "port".

11. Memory: why Python containers are big

Every Python object carries a header. An int is 28 bytes for small values, more for big ones (sys.getsizeof(10**100) is 72). A list of a million ints is therefore about 8 MB of pointers plus about 28 MB of int objects (small cached ints aside). An empty dict is 64 bytes and a one-key dict 184. Millions of small dicts or objects add up to gigabytes.

When the data is numeric and homogeneous, store raw values instead of objects. The standard library's array.array('d', ...) stores C doubles contiguously at 8 bytes each. NumPy does the same and adds fast vectorised maths implemented in C, typically several to tens of times smaller and faster than lists of Python numbers. For record-like data, __slots__ classes (py6), NamedTuples, or columnar tools such as pandas, Polars and Arrow remove the per-record dictionary. py11 returns to measuring and fixing these costs.

The probe sequence and why low bits are enough

CPython's hash for small integers is the integer itself, which looks like a terrible hash: hash(5) == 5. The source comments in dictobject.c argue that it is actually good: for a contiguous range of int keys, taking the low bits gives zero collisions, better than random. The weakness appears when keys share low bits (for example all multiples of 65,536). That is handled by the probe recurrence j = (5*j + 1 + perturb) mod 2**i with perturb >>= 5 on each step: the first few probes mix in progressively higher bits of the hash, and once perturb reaches zero the 5*j + 1 recurrence alone visits every slot of a power-of-two table, guaranteeing termination because at least one slot is always empty.

Load factor, growth and the never-shrinking dict

USABLE_FRACTION(n) in the 3.12 source is (2n)/3: a table of 8 index slots holds at most 5 entries before resizing. When it resizes, the new size is based on GROWTH_RATE = used × 3, rounded up to a power of two, so a table roughly doubles or quadruples. Deletions only turn entries into dummies and decrement the used count; the table is compacted only when an insertion triggers a resize. Consequence: a dict used as a cache that once held millions of entries and has since been emptied with del still occupies its peak memory. d.clear() releases the table, and rebuilding with dict(d) creates a right-sized copy.

Key-sharing dictionaries for instances

Most objects store their attributes in a per-instance __dict__. Since Python 3.3 (PEP 412), instances of the same class share a single keys table and each instance stores only its values array, because objects of one class usually have the same attribute names set in the same order in __init__. 3.11 went further and stores those values inline in the object, creating a real dict only if someone asks for __dict__. This is why setting attributes in a consistent order in __init__ is slightly better for memory, and why adding attributes dynamically outside __init__ can make an instance fall back to a private dict.

The list growth pattern and pre-sizing

The 3.12 formula (newsize + (newsize >> 3) + 6) & ~3 gives capacities 0, 4, 8, 16, 24, 32, 40, 52, 64, 76 and so on — about 1.125× per step once large. Growth is deliberately mild to avoid wasting memory, relying on the system allocator to extend blocks in place where possible. Building a list with a comprehension or list(iterable) lets CPython size it once when the length is known, which is faster than repeated appends; [None] * n preallocates when you will fill by index. When a list shrinks below half its capacity, the next resize reallocates smaller.

Sorting internals and key functions

The sort first finds natural runs — maximal ascending or strictly descending stretches, which it reverses — and extends short runs to a minimum length with binary insertion sort. It then merges runs using "galloping" (exponential search) when one run repeatedly wins, which makes merging data with long pre-sorted stretches very cheap. The merge policy decides which adjacent runs to merge; Python 3.11 adopted Munro and Wild's Powersort policy, which is provably near-optimal in the pattern of run lengths. The key= function is evaluated exactly once per element and the results are cached alongside the items, so an expensive key such as a regex extraction costs n calls, not n log n. Sorting also only uses <, so a class needs only __lt__ to be sortable.

Hash-flooding and SipHash

If an attacker can predict hashes, they can post a request with thousands of keys that all collide, forcing every dict insert to probe past all previous colliding keys: O(n²) work for one request. Since Python 3.4 (PEP 456), str and bytes hashes use SipHash, a keyed hash function, with a key chosen randomly at startup (Python 3.11 switched to the faster SipHash-1-3 variant). Without the key, collisions cannot be precomputed. The cost is that string hashes and therefore set iteration order differ from run to run, which occasionally breaks tests that assumed an order.

Thread safety and the free-threaded build

With the GIL (the Global Interpreter Lock, covered in py8, which lets only one thread execute Python bytecode at a time), individual operations on built-in containers implemented as a single C call — append, d[k] = v, deque.popleft — appear atomic. Read-modify-write sequences like d[k] += 1 or "check if key exists, then insert" are several bytecodes and can interleave, losing updates. The free-threaded build (PEP 703; experimental in 3.13, officially supported but still optional in 3.14 per PEP 779) removes the GIL and protects each list and dict with a lightweight per-object lock, so single operations remain safe, but compound ones still need threading.Lock. queue.Queue and collections.deque's append/popleft are the documented thread-safe choices for producer-consumer patterns.

Accidental quadratic behaviour

The characteristic production symptom is a job that is fine in staging and times out in production, with run time growing much faster than data volume: 10× the rows, 100× the time. The usual culprits are membership tests against a list inside a loop, list.pop(0) or insert(0, ...) queues, building strings with += in a loop (each concatenation can copy the whole string; use "".join(parts)), and repeatedly sorting a list to get its maximum. A profiler (py11) points straight at them: the hot line will be a single in, pop or sort with a huge call count or time.

Memory blow-ups from object overhead

Loading a 1 GB CSV into a list of dicts commonly consumes 5-10 GB of RAM, because each row becomes a dict of Python strings and ints, each with its own header and hash table. The fixes, in order of effort: read in chunks and stream instead of materialising; use tuples or __slots__ objects; load into pandas, Polars or Arrow, which store each column as one typed buffer. Measure with tracemalloc rather than sys.getsizeof, which ignores referenced objects (py1).

Caches that never shrink

An unbounded dict used as a cache grows until the process is killed for exceeding its memory limit, and, because dicts do not shrink on delete, even a cache that evicts by deleting keys keeps its peak table size. Use functools.lru_cache(maxsize=...) or an OrderedDict-based LRU with a bound, or a library such as cachetools with TTL (time-to-live) expiry. Watch the process's resident memory (RSS) over days, not minutes: slow leaks from caches are the classic "restarts fix it" bug.

Order-dependent bugs

Code that iterates a set of strings and relies on the order — writing output files, generating ids, choosing the first match — produces different results on each run because of hash randomisation. It passes locally by luck and fails in CI (continuous integration) or differs between replicas. Sort explicitly (sorted(s)) wherever order is observable. The inverse surprise: dicts built from sets inherit the set's arbitrary order.

Choosing structures under concurrency

Worker pools that share a plain list or dict as a work queue lose or duplicate items under load because check-then-act sequences interleave. Use queue.Queue for threads, multiprocessing.Queue for processes, and asyncio.Queue for coroutines (py9). These have blocking get, bounded sizes for backpressure, and correct locking.

A common AI-engineering case: embeddings and vocabularies

Storing a million 768-dimensional embeddings as a list of Python lists of floats costs roughly 24 bytes per float object plus an 8-byte pointer, around 25 GB, and every similarity computation runs in the interpreter one float at a time. The same data as a single NumPy float32 array is about 3 GB and a matrix multiply runs in optimised C. Conversely, a tokenizer's vocabulary (token string to integer id) is exactly what a dict is for: a few hundred thousand keys with O(1) lookups. Knowing which side of that line your data sits on is most of the performance work in data-heavy Python services.

Seeing it

Useful tools: timeit for micro-benchmarks of alternatives; cProfile and py-spy for finding hot lines in real workloads; tracemalloc and memray for memory; and the Python wiki's TimeComplexity page as the reference for what each operation costs. A good habit in code review is to ask, for every loop, "what is the cost of the operations inside it, and how large can n get?"

Afterwards, rewrite the dedupe loop from the introduction with a set and time both versions on 20,000 random ids.

Fix the complexity 
# 1. dedupe while keeping order
out = []
for x in items:                # n = 1,000,000
    if x not in out:
        out.append(x)

# 2. process a work queue
queue = [start]
while queue:
    node = queue.pop(0)
    queue.extend(neighbours(node))

# 3. top 10 scores from 50M records streamed from disk
scores = sorted(read_all(), reverse=True)[:10]
Answer

1. x not in out scans a list, O(n), inside a loop of n, so the whole thing is O(n²) — hundreds of billions of comparisons at a million items. Keep a set for membership next to the output list: seen = set(), and append only when x not in seen, adding it to seen. That is O(n) overall. 3. Sorting 50 million items is O(n log n) time and needs all of them in memory at once. heapq.nlargest(10, stream) keeps only a 10-element heap: O(n log 10) time and O(10) memory, and it consumes a generator that reads the file lazily.
