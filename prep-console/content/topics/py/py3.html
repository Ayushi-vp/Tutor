A developer is wiring up a small dashboard. For each of three data sources they create a button, and each button's click handler should refresh its own source. The code is a tidy loop:

handlers = []
for source in ["sales", "users", "errors"]:
    handlers.append(lambda: refresh(source))

Every button refreshes "errors". Nothing is misspelled and there is no exception. The bug comes from how Python decides what the name source means inside the lambda, and when it looks up its value.

A second developer adds a request counter to a module: count = 0 at the top, and count += 1 inside the handler function. The first request crashes with UnboundLocalError: cannot access local variable 'count' — even though count is right there, one screen up, with a value of zero. A third adds a flag to a widely used function, def connect(host, port, timeout, retries, verify), and six months later a caller swaps the two middle numbers and nobody notices until production retries for five minutes instead of five seconds.

Functions are the first abstraction every Python programmer learns, and these bugs show that "I can write a function" and "I know what a function does" are different things. The rules involved are small — how arguments are matched to parameters, which scope a name belongs to, and what a closure captures — but they are precise, and getting them slightly wrong produces exactly this kind of quiet misbehaviour. They also underpin everything that comes later in this track: decorators (py4) are closures, generators (py5) are suspended function frames, and frameworks like pytest and FastAPI read your function signatures to decide what to pass in.

This lesson starts from what a def statement actually creates, then walks through calling: how Python matches arguments to parameters, defaults, *args and **kwargs, and the / and * markers. Then scope: namespaces, the LEGB lookup order, the compile-time rule behind UnboundLocalError, global and nonlocal, and the special cases of class bodies and comprehensions. Then closures: what a cell is, how state survives after a function returns, and why the loop above breaks. It ends with functions as values — higher-order functions, lambdas and functools.partial. Everything was run on CPython 3.12.10; version-specific behaviour is marked.

A function is an object that holds a recipe

Think of a def statement as writing a recipe card and filing it under a name. Writing the card does not cook anything. Later, each call takes the card, sets out a fresh, empty kitchen counter, puts the ingredients you handed over onto it with labels, follows the steps, hands back the result, and wipes the counter clean.

In Python terms: def runs like any other statement and creates a function object — containing the compiled code, the default values and a reference to the module's global namespace — and binds it to a name (py1: binding). Each call creates a call frame, a fresh record holding that call's local namespace, and binds each parameter (the names in the definition) to the matching argument (the values at the call site). When the function returns, the frame is discarded along with its local names, unless something still refers to them.

def greet(name, greeting="Hello", *, punctuation="!"):
    return f"{greeting}, {name}{punctuation}"

greet("Asha")                     # 'Hello, Asha!'
greet("Asha", "Hi")               # 'Hi, Asha!'
greet("Asha", punctuation=".")    # 'Hello, Asha.'
greet("Asha", "Hi", ".")          # TypeError: greet() takes from 1 to 2 positional arguments but 3 were given

Arguments can be passed by position or by name (keyword arguments). Parameters can have defaults. The bare * in the definition means everything after it must be passed by name, which is why the last call fails.

Which variable does a name mean?

Inside a function, a name could refer to a local variable, a variable of an enclosing function, a module-level variable, or a built-in like len. Python searches in that order — Local, Enclosing, Global, Built-in, "LEGB" — and uses the first match. The twist is that Python decides whether a name is local before the function ever runs: if the function assigns to the name anywhere, it is local everywhere in that function.

Functions that remember

A function defined inside another function can use the outer function's variables — and keeps them alive after the outer function has returned. That combination is a closure:

def make_multiplier(n):
    def multiply(x):
        return x * n        # n belongs to make_multiplier
    return multiply

double = make_multiplier(2)
double(5)                   # 10 — n is still 2, long after make_multiplier returned

This is how Python functions carry configuration and state without a class, and it is the mechanism behind decorators in the next lesson. The one thing to remember now: the closure remembers the variable, not a snapshot of its value, which is the root of the loop bug in the introduction.

Where the recipe analogy breaks: the kitchen counter is not always wiped clean. If a closure still refers to some of the frame's variables, those survive. And unlike a paper recipe, the function object is a live Python object you can inspect, pass around, store in a dict and even attach attributes to.

1. What def creates

Python code is first compiled into bytecode, a compact list of instructions for the interpreter. When the compiler meets a function, it produces a code object for the body. Then, when the module actually runs and reaches the def line, Python executes it: it evaluates the default values, builds a function object that bundles the code object, the defaults, the module's global namespace and any captured variables, and binds the function's name to it.

def f():
    pass

print(f(), f.__name__, type(f.__code__))
# None f <class 'code'>

Three consequences follow. A function with no return (or a bare return) returns None. A def inside an if or inside another function creates a new function object every time that line runs. And defaults are evaluated once, at def time — the mutable-default trap from py1.

2. Matching arguments to parameters

When you call a function, Python must decide which argument goes into which parameter. The algorithm is mechanical, and knowing it explains every argument-related TypeError:

  1. Positional arguments fill positional parameters left to right. If there are more positional arguments than positional parameters, the extras go into *args if the function has it, and otherwise raise "takes N positional arguments but M were given".
  2. Keyword arguments are matched by name. If the named parameter was already filled in step 1, Python raises "got multiple values for argument". If no parameter has that name, it goes into **kwargs if present, and otherwise raises "got an unexpected keyword argument".
  3. Defaults fill any parameters still empty.
  4. Anything still empty raises "missing required argument".
def g(a, b, c=3):
    return (a, b, c)

g(1, c=5, b=2)     # (1, 2, 5)  — a by position, b and c by name
g(1, 2, a=3)       # TypeError: g() got multiple values for argument 'a'
g(1)               # TypeError: g() missing 1 required positional argument: 'b'

2a. Returning values and unpacking them

A function returns exactly one object. "Returning several values" is really returning one tuple: return a, b, c builds the tuple (a, b, c), because commas, not parentheses, make a tuple. The caller can keep the tuple or unpack it into several names in one assignment:

def stats(xs):
    return min(xs), max(xs), sum(xs) / len(xs)

r = stats([3, 1, 2])            # (1, 3, 2.0)  — one tuple
lo, hi, mean = stats([3, 1, 2]) # 1 3 2.0      — unpacked into three names

Unpacking requires the counts to match: a, b = [1, 2, 3] raises ValueError: too many values to unpack (expected 2). A starred name absorbs "the rest" as a list, which is handy for head/tail splits: first, *rest = [10, 20, 30, 40] gives 10 and [20, 30, 40], and *init, last = "abc" gives ['a', 'b'] and 'c'. When a function returns more than three or four values, callers start mixing up positions; return a NamedTuple or dataclass instead so each field has a name.

2b. Docstrings and annotations

Two optional parts of a def are stored on the function object for tools and readers. A string literal as the first statement of the body is the docstring, available as f.__doc__ and shown by help(f) and editors. Annotations after parameters and after -> record intended types:

def area(w: float, h: float = 1.0) -> float:
    """Return the area of a w-by-h rectangle."""
    return w * h

area.__annotations__   # {'w': <class 'float'>, 'h': <class 'float'>, 'return': <class 'float'>}
area("ab", 2)          # 'abab' — annotations are not enforced at runtime

The last line matters: Python itself ignores annotations when calling the function, so a string multiplied by 2 happily returns 'abab'. They are checked by separate tools such as mypy and Pyright, and read by frameworks such as FastAPI and Pydantic. py10 covers type hints properly; for now, read them as documentation that tools can verify.

3. Collecting and unpacking: *args and **kwargs

A parameter written with one star collects every surplus positional argument into a tuple; one with two stars collects every surplus keyword argument into a dict. The names args and kwargs are just convention.

def v(*args, **kwargs):
    return args, kwargs

v(1, 2, x=3)       # ((1, 2), {'x': 3})

At a call site the same symbols do the reverse, unpacking a sequence into positional arguments and a mapping into keyword arguments:

nums = [1, 2, 3]
opts = {"sep": "-"}
print(*nums, **opts)     # same as print(1, 2, 3, sep="-")  → 1-2-3

Put together, def wrapper(*args, **kwargs): return inner(*args, **kwargs) forwards any call unchanged to another function. That one line is the skeleton of nearly every decorator in py4.

4. Positional-only and keyword-only parameters

Two markers in a parameter list restrict how parameters may be passed. Everything after a bare * (or after *args) is keyword-only: callers must use the name (PEP 3102, Python 3.0). Everything before a / is positional-only: callers must not use the name (PEP 570, Python 3.8). The general shape is:

def f(pos_only, /, normal, *, kw_only): ...
def pos(a, b, /, c, *, d):
    return a, b, c, d

pos(1, 2, 3, d=4)          # (1, 2, 3, 4)
pos(1, 2, c=3, d=4)        # (1, 2, 3, 4)
pos(a=1, b=2, c=3, d=4)    # TypeError: pos() got some positional-only arguments passed as keyword arguments: 'a, b'
pos(1, 2, 3, 4)            # TypeError: pos() takes 3 positional arguments but 4 were given

Why would you want either? Keyword-only parameters make call sites self-describing and robust: connect("db", 5432, timeout=5, retries=3) cannot be silently swapped, and you can later add or reorder options without breaking anyone. Positional-only parameters do the opposite job: the parameter name is not part of the public contract, so the author can rename it, and the name never collides with a key a caller passes through **kwargs. Many built-ins are positional-only for that reason; len(obj=[1]) fails.

5. Namespaces and the LEGB rule

Recall from py1 that a namespace maps names to objects. When a function runs there are several namespaces in play: the call's local namespace, the local namespaces of any enclosing functions, the module's global namespace, and the built-in namespace (the builtins module, home of len, print and the exception classes). The region of code in which a binding is visible is its scope. Name lookup searches Local, then Enclosing (innermost first), then Global, then Built-in:

x = "global"
def outer():
    x = "enclosing"
    def inner():
        return x
    return inner()

outer()     # 'enclosing'

Because built-ins come last, a module that defines its own len or a function with a parameter called list shadows the built-in in that scope. Linters warn about this for good reason.

6. Scope is decided at compile time

Here is the rule that produces UnboundLocalError. When the compiler processes a function body, it collects every name the function assigns to — by =, augmented assignment like +=, for targets, import, def, with ... as, except ... as. Those names are local for the whole body, and the compiler emits "load local" instructions for every use of them. There is no runtime fallback to the global.

total = 0
def add(x):
    total += x          # reads local total, which has no value yet
    return total

add(1)
# UnboundLocalError: cannot access local variable 'total' where it is not associated with a value

Walk through it: total += x means "load total, add x, store total". The store makes total local. At runtime the load looks in the local slot, finds it empty, and raises. The global total is never consulted.

Two declarations change the rule for a name. global total says: in this function, total means the module-level variable, and assignments rebind it there. nonlocal n says: n means the variable in the nearest enclosing function, and assignments rebind it there. Note what does not need a declaration: mutating an object through a name (items.append(1), config["k"] = v) is not an assignment to the name, so it works on a global or enclosing object without global or nonlocal (py1: mutation versus rebinding).

Idiomatic code rarely uses global. Module-level mutable state is hard to test and unsafe to share between threads; returning values, passing objects in, or keeping state on an instance are all clearer.

7. The two scope exceptions: class bodies and comprehensions

A class body runs in its own namespace, which becomes the class's attributes. But it is not an enclosing scope for functions defined inside it. A method looking up a bare name skips the class and goes straight to the module:

class C:
    y = 10
    def m(self):
        return y            # NameError: name 'y' is not defined

# write self.y or C.y instead

This is deliberate: methods are called later, from anywhere, and would otherwise depend on class-body variables in confusing ways. The same rule catches comprehensions in class bodies. A comprehension has its own scope, and its expression cannot see class attributes. Only its first (outermost) iterable is evaluated in the class scope:

class D:
    n = 3
    vals = [k for k in range(n)]      # OK: range(n) is evaluated in the class scope → [0, 1, 2]

class E:
    y = 10
    vals = [k * y for k in range(3)]  # NameError: name 'y' is not defined

In ordinary functions, the comprehension's own scope is what stops its loop variable from leaking: after i = 99; [i for i in range(3)], i is still 99. Since Python 3.12 (PEP 709) comprehensions are compiled inline rather than as hidden nested functions, which makes them faster, but the isolation of the loop variable is preserved.

8. Closures and cells

Normally a function's locals live in its frame and vanish when the call returns. But if an inner function references an outer function's variable, that variable must outlive the outer call. The compiler handles it by storing such variables in a cell: a tiny object that holds one reference. Both the outer frame and the inner function point at the same cell. The inner function keeps its cells in __closure__, and its code object lists their names in co_freevars (a free variable is one used in a function but defined in an enclosing one).

def counter():
    n = 0
    def inc():
        nonlocal n
        n += 1
        return n
    return inc

c1 = counter()
c1(); c1()
print(c1(), c1.__code__.co_freevars, c1.__closure__[0].cell_contents)
# 3 ('n',) 3
c2 = counter()
print(c2())      # 1 — a separate call to counter() made a separate cell

Two points to notice. First, nonlocal is required here because n += 1 rebinds n; without it, n would be local to inc and you would get UnboundLocalError. Second, several inner functions defined in the same call share the same cells — a getter and a setter returned together see each other's changes, which is a tiny object with private state.

The bytecode shows the machinery directly. On 3.12, dis of an outer function that creates a closure shows MAKE_CELL for the variable, STORE_DEREF to assign it, and LOAD_CLOSURE plus MAKE_FUNCTION ... (closure) to build the inner function; the inner function uses COPY_FREE_VARS and LOAD_DEREF ("dereference the cell") instead of the ordinary LOAD_FAST.

9. Late binding: the loop trap explained

A closure reads a cell's current contents each time it runs. When closures are created in a loop, they all share the single cell for the loop variable, and by the time any of them runs the loop has finished:

fns = [lambda: i for i in range(3)]
print([f() for f in fns])              # [2, 2, 2]

This is late binding: the name is looked up when the function is called, not when it is created. The dashboard bug in the introduction is exactly this: every handler reads source after the loop ended, when it was "errors".

Two fixes capture the value at creation time. A default argument is evaluated when the lambda is created (section 1), so lambda i=i: i stores the current value in the function's defaults. Or use functools.partial, which stores the argument in the partial object:

fns = [lambda i=i: i for i in range(3)]
print([f() for f in fns])                               # [0, 1, 2]

import functools
fns = [functools.partial(lambda i: i, i) for i in range(3)]
print([f() for f in fns])                               # [0, 1, 2]

The default-argument trick has one downside: the function now accepts an i argument that a caller could override by accident. partial or a small factory function (def make(i): return lambda: i, where each call creates a new cell) avoids that.

10. Functions as values

Because functions are first-class objects (py1), you can pass them to other functions. A function that takes or returns a function is a higher-order function. The everyday examples are sorted(rows, key=...), max(items, key=...), map and filter, and callback registration.

A lambda is an expression that creates a function whose body is one expression. It is the same kind of function object as one made by def, just anonymous: (lambda x: x * x).__name__ is '<lambda>', which is what appears in tracebacks. Use it for short key functions; use def for anything worth naming.

The operator module provides ready-made key functions that are faster and clearer than lambdas for common cases: sorted(rows, key=itemgetter(1)) sorts by the second field, attrgetter("name") by an attribute. functools.partial performs partial application: it fixes some arguments of a function and returns a new callable. cube = functools.partial(pow, exp=3) gives a function where cube(2) returns 8 (using the built-in pow, whose second parameter is called exp).

11. Recursion and its limit

A function may call itself. Each call creates a new frame, and CPython caps the depth of nested Python calls with a recursion limit, 1000 by default (sys.getrecursionlimit()). Exceeding it raises RecursionError: maximum recursion depth exceeded. CPython does not perform tail-call optimisation (reusing the frame when a function's last action is a call), so even tail-recursive code is limited. Recursion is natural for trees of known, modest depth; for arbitrary-depth input, use a loop and an explicit stack (a list you append to and pop from).

How the compiler chooses load instructions

The scope decision is visible in the bytecode. Locals use LOAD_FAST/STORE_FAST, which index directly into an array in the frame — no dictionary lookup at all, which is why local variable access is the fastest in Python. Globals and built-ins use LOAD_GLOBAL, which checks the module dict and then the builtins dict. Cell and free variables use LOAD_DEREF/STORE_DEREF through the cell. Since 3.11, the specialising adaptive interpreter (PEP 659) rewrites LOAD_GLOBAL at runtime into a specialised form that caches the lookup and checks a version number on the dicts, so repeated global lookups are cheap too; the old advice to copy globals into locals for speed now rarely matters.

Cheaper calls since 3.11

Before 3.11, every Python-to-Python call went through the C function that evaluates frames, recursing on the C stack and allocating a frame object on the heap. 3.11 made frames lightweight structs allocated in a contiguous per-thread stack and inlined Python-to-Python calls inside the interpreter loop, so a call no longer consumes C stack. Heap frame objects are only created if someone asks for them (a traceback, sys._getframe, a debugger). Calls still cost tens of nanoseconds — orders of magnitude more than a C function call — so in hot numeric loops vectorisation (py11) still beats factoring code into many tiny functions.

Recursion limits after the 3.11 changes

Because Python calls no longer recurse on the C stack, 3.12 made sys.setrecursionlimit apply to Python code only; recursion through C code (deep repr of nested structures, C extensions calling back into Python) is protected by a separate mechanism. Raising the Python limit is therefore much safer than it used to be, but it is still a smell: a limit of 100,000 frames means 100,000 frames of memory, and a recursion that deep over user-controlled input is a denial-of-service vector. Explicit stacks remain the robust answer.

locals(), exec and PEP 667 (3.13)

In a function, locals() historically returned a dict that was a cached, partially synchronised copy of the fast locals array; writing to it sometimes appeared to work and sometimes did not. PEP 667 in Python 3.13 made it well defined: in functions, generators, coroutines and comprehensions, each locals() call returns a fresh independent snapshot, and exec/eval without an explicit namespace run against such a snapshot, so assignments inside them never create real local variables. Debuggers use frame.f_locals, which is now a write-through proxy. If you need dynamic names, use a dict explicitly.

Comprehension inlining (PEP 709, 3.12)

Until 3.11, each list, dict or set comprehension compiled into a hidden nested function that was created and called on every evaluation. 3.12 inlines the comprehension's bytecode into the containing function, saving the function creation and call (up to about twice as fast for small comprehensions per the PEP), while pushing and popping the iteration variable so it still does not leak. Visible differences are small: tracebacks no longer show a separate <listcomp> frame, and locals() inside a comprehension now includes the enclosing function's variables. Generator expressions are not inlined, since they must suspend (py5).

Signatures as an API: inspect and frameworks

inspect.signature(pos) returns (a, b, /, c, *, d), a structured object listing each parameter's kind, default and annotation. Frameworks build on it: pytest injects fixtures by matching parameter names, FastAPI reads parameter names, defaults and type annotations to decide what comes from the URL path, the query string or the body, and Typer and Click-like tools build command-line interfaces from signatures. This is why renaming a parameter in such code is a behaviour change, and why decorators must preserve signatures with functools.wraps (py4).

Closures, pickling and processes

To send a callable to another process, multiprocessing and most task queues pickle it, and pickle stores functions by module and qualified name, to be re-imported on the other side. Lambdas and nested functions have names like <lambda> or outer.<locals>.inner that cannot be imported, so they fail to pickle. functools.partial of a module-level function pickles fine because it stores the function reference and the arguments. This is a common reason to prefer partial or a small class over a closure in data pipelines (py9).

Closures versus classes

A closure is the smallest possible object: private state (its cells) and exactly one behaviour. It avoids the ceremony of a class for callbacks and factories, and attribute lookups on self are replaced by fast cell loads. The trade-offs are that the state is invisible to debuggers and repr, cannot be reset or inspected without hacks, and cannot be pickled. A rule of thumb that interviewers accept: closure for one behaviour and a little state, class once there are two or more operations or the state needs to be observed.

Callbacks registered in loops

The late-binding bug shows up wherever code builds callbacks in a loop: GUI and dashboard handlers, asyncio loop.call_later calls, retry hooks, route registration, and executor.submit(lambda: work(item)) in thread pools. The symptom is that "every task processed the last item", often only under load, when the loop finishes before the callbacks run. Code review rule: a lambda inside a for loop that references the loop variable is a bug until proven otherwise. executor.submit(work, item) passes the value directly and avoids the closure entirely.

Signatures as contracts in shared code

In a library or a shared internal package, parameter names and order are part of the public API. Making optional parameters keyword-only from the start lets you add, reorder and deprecate them without breaking callers; retrofitting it later is itself a breaking change. The opposite failure is **kwargs swallowing typos: a function that accepts **kwargs and forwards them selectively will silently ignore timeuot=5. Validate unknown keys or avoid catch-all **kwargs in public functions.

Module-level mutable state

Functions that update globals — counters, caches, registries, "current user" variables — are a source of bugs under concurrency (lost updates between threads, py9) and in tests (state leaking from one test to the next, py12). In web services, request-specific data belongs in parameters, in a request object, or in contextvars, which give each thread or asyncio task its own value. Global configuration should be read-only after startup.

Closures that pin memory

A handler registered with an event bus, a cache of partially applied functions, or a long-lived lru_cache-decorated nested function keeps its cells, and those cells keep whatever they reference. In data pipelines it is easy to close over a large DataFrame or model object "just for logging", and the object then lives as long as the callback is registered. Memory profilers show the object held by a cell; the fix is to capture only small values (an id, a length) or to deregister callbacks when done.

Recursion on untrusted input

Recursive parsers and tree walkers (for example over ASTs, abstract syntax trees, the tree form of parsed code) work in tests and crash in production when a user sends a structure nested 5,000 levels deep, producing RecursionError (a 500 error at best). Services that process arbitrary JSON, ASTs or nested configs should either cap depth explicitly or iterate with an explicit stack. The standard library's json module itself raises RecursionError on very deeply nested input, so validate size and depth at the edge.

Notebooks and stale globals

Jupyter notebooks, the everyday tool of data and AI work, run every cell in one shared global namespace. A function defined in cell 3 that reads a global df or model sees whatever value that name has when the function runs, which depends on which cells you ran and in what order, not on the order they appear on screen. The classic result is a notebook that works for its author and fails for everyone who runs it top to bottom, or a training function that silently uses a stale, differently filtered DataFrame. The fix is the same discipline as elsewhere in this lesson: pass data in as parameters instead of reading globals, and regularly use "restart kernel and run all" to prove the notebook works from a clean state.

Answer

(a) UnboundLocalError. (c) It works, but the call site is unreadable and fragile: swapping timeout and retries is silent.
