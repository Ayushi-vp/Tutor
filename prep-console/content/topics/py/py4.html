A team building an inference service wants three things on every endpoint handler: log how long it took, retry twice if the model server resets the connection, and reject callers without a valid API key. The first version does it by hand:

def predict(request):
    if not valid_key(request):
        raise Unauthorized()
    start = time.perf_counter()
    for attempt in range(3):
        try:
            result = model_client.predict(request.body)
            break
        except ConnectionError:
            if attempt == 2:
                raise
    log.info("predict took %.1f ms", (time.perf_counter() - start) * 1000)
    return result

Only one line of that function — the call to model_client.predict — is about predicting. The rest is plumbing, and it is copied into embed, classify, health and eleven other handlers. Six months later the retry logic has four slightly different versions, one handler forgot the key check, and changing the log format means editing fifteen files.

Timing, logging, retrying, caching, authorisation and rate limiting are cross-cutting concerns: behaviour that many unrelated functions need, but that is not part of what any of them does. Python's answer is the decorator: write the plumbing once as a function that wraps other functions, then attach it with one line:

@require_api_key
@timed
@retry(times=3, exceptions=(ConnectionError,))
def predict(request):
    return model_client.predict(request.body)

Decorators are everywhere in real Python: @app.get("/") in FastAPI, @pytest.fixture, @dataclass, @property, @functools.cache, @torch.no_grad(). Interviewers ask candidates to write one from scratch because it tests several things at once: functions as objects, *args/**kwargs forwarding, closures and a clear grasp of when code runs.

This lesson builds a decorator by hand without any special syntax, then shows that @ is only a shorthand. It covers functools.wraps and why frameworks depend on it, decorators that take arguments (the three-level pattern), stacking order, keeping state, registration decorators, decorating methods and async functions, class decorators, the standard library's built-in decorators, and finally how to type-annotate decorators. All code was run on CPython 3.12.10.

The gift-wrapping analogy

Think of a function as a present. A decorator is a gift-wrapping service: you hand it the present, and it hands back a wrapped parcel. From the outside the parcel looks like the same gift and you "open" it the same way, but opening it now involves some extra steps — a card that gets read first, a ribbon that gets untied afterwards. The present inside is untouched.

In code, "wrapping" means writing a new function, the wrapper, that calls the original and does something before, after or around the call. The decorator is the function that builds that wrapper and returns it. Then we rebind the original name to the wrapper, so every caller who uses the name gets the wrapped version without changing a single call site.

import time

def timed(func):                         # takes a function...
    def wrapper(*args, **kwargs):        # ...builds a replacement...
        start = time.perf_counter()
        try:
            return func(*args, **kwargs) # calls the original
        finally:
            print(f"{func.__name__} took {(time.perf_counter() - start) * 1000:.1f} ms")
    return wrapper                       # ...and returns it

def slow_add(a, b):
    time.sleep(0.05)
    return a + b

slow_add = timed(slow_add)               # rebind the name to the wrapper
print(slow_add(2, 3))
# slow_add took 50.6 ms
# 5

Everything in that snippet is from earlier lessons. Functions are objects we can pass to timed (py1). *args, **kwargs let the wrapper accept and forward any arguments (py3). And wrapper is a closure (py3): it remembers func in a cell long after timed has returned.

The @ shorthand

Writing slow_add = timed(slow_add) after every function gets tedious and puts the important information below the function where readers miss it. So Python has syntax for it:

@timed
def slow_add(a, b):
    ...

This means exactly "define slow_add, then rebind it to timed(slow_add)". There is nothing else to it: a decorator is any callable that takes one argument, and the @ line calls it with the new function.

What decorators are for, and what they are not for

Decorators are the right tool when the extra behaviour is the same for many functions and does not depend on what the function does inside: measure it, log it, retry it, cache it, check permissions before it, register it. They are the wrong tool when the extra behaviour needs to reach into the middle of the function, or when a reader must know about it to understand the function's result. A decorator that silently changes arguments or return values makes code hard to follow, because the behaviour is no longer visible where the function is defined. A good test: if you deleted the decorator line, would the function still do its job, just without the plumbing? If yes, a decorator fits.

When things run

The single most useful fact about decorators: the decorator runs once, when the def statement executes — for a module-level function, when the module is imported. The wrapper runs on every call. Keep those two moments separate in your head and most decorator puzzles become easy.

Where the gift analogy breaks: a gift-wrapper cannot replace the present, but a decorator can return anything — the original function unchanged (to register it somewhere), a completely different function, or even a non-function object such as a property. The only rule is that whatever it returns is what the name now means.

1. Decoration happens at definition time

Let us prove the timing claim. This decorator prints when it is applied and returns the function unchanged:

def announce(func):
    print(f"decorating {func.__name__}")
    return func

@announce
def hello():
    print("hello called")

print("after def")
hello()
# decorating hello
# after def
# hello called

"decorating hello" appears before "after def": the decorator ran as part of executing the def. In a real project that means decorators run when import mymodule executes. Expensive work in a decorator (connecting to a database, loading a model) therefore slows down imports and runs even if the function is never called — do that work lazily inside the wrapper instead.

2. Anatomy of a wrapper

A good general-purpose wrapper has four properties. It accepts any arguments (*args, **kwargs) so it works on any function. It forwards them unchanged to the original. It returns the original's return value — forgetting the return is the most common beginner bug and makes every decorated function return None. And it lets exceptions propagate unless handling them is its job; using try/finally for "after" logic ensures that logic runs even when the original raises, while the exception still reaches the caller.

3. functools.wraps: keeping the function's identity

Our hand-written timed has a flaw. After decoration, the name slow_add refers to wrapper, and the function object says so:

import inspect
print(slow_add.__name__, slow_add.__doc__, inspect.signature(slow_add))
# wrapper None (*args, **kwargs)

Every log line, traceback, help() page and documentation generator now says "wrapper". Worse, tools that read the signature (the parameter list) see only (*args, **kwargs). pytest decides which fixtures to inject by reading parameter names, and FastAPI decides which query parameters and body fields an endpoint accepts the same way, so a decorator without this fix can silently break them.

functools.wraps(func) is itself a decorator, applied to the wrapper, that copies the original's __name__, __qualname__, __doc__, __module__ and __annotations__ onto the wrapper, merges its attribute __dict__, and sets wrapper.__wrapped__ = func. inspect.signature follows __wrapped__ to report the real signature:

import functools

def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        ...
        return func(*args, **kwargs)
    return wrapper

@timed
def slow_add(a: int, b: int) -> int:
    """Add slowly."""
    return a + b

print(slow_add.__name__, slow_add.__doc__, inspect.signature(slow_add))
# slow_add Add slowly. (a: int, b: int) -> int
slow_add.__wrapped__      # the original, undecorated function

__wrapped__ is also handy in tests: you can call slow_add.__wrapped__(2, 3) to test the logic without the decoration. Rule: every wrapper you write gets @functools.wraps(func).

4. Decorators that take arguments

A retry decorator needs configuration: how many times, and on which exceptions. The syntax @retry(times=3) looks like it passes arguments to a decorator, but read it literally: the expression after @ is retry(times=3), which is evaluated first, and its result is then used as the decorator. So retry must be a decorator factory: a function that takes the configuration and returns a decorator. That gives three nested levels, each closing over the one outside it:

def retry(times=3, exceptions=(Exception,)):         # level 1: configuration
    def decorator(func):                             # level 2: the function
        @functools.wraps(func)
        def wrapper(*args, **kwargs):                # level 3: each call
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    print(f"attempt {attempt} failed: {e!r}")
                    if attempt == times:
                        raise
        return wrapper
    return decorator

calls = {"n": 0}
@retry(times=3, exceptions=(ConnectionError,))
def flaky():
    calls["n"] += 1
    if calls["n"] < 3:
        raise ConnectionError("reset")
    return "ok"

print(flaky())
# attempt 1 failed: ConnectionError('reset')
# attempt 2 failed: ConnectionError('reset')
# ok

The classic mistake is forgetting the parentheses. @retry passes the function to retry as times, and retry returns the level-2 decorator, which the name is now bound to:

@retry
def oops():
    return 1

oops()
# TypeError: retry.<locals>.decorator() missing 1 required positional argument: 'func'

Well-designed libraries accept both forms. The trick is to make the configuration keyword-only and check whether the function was passed directly:

def retry(func=None, *, times=3):
    if func is None:                                    # used as @retry(times=5)
        return functools.partial(retry, times=times)    # a decorator awaiting func
    @functools.wraps(func)                              # used as @retry
    def wrapper(*args, **kwargs):
        ...
    return wrapper

5. Stacking decorators

Several decorators can be applied to one function. They are applied bottom-up, nearest the def first: @a above @b above def core means core = a(b(core)). At call time the outermost wrapper runs first. Run it and watch:

@a
@b
def core():
    print("core")
    return 1

# at definition:  apply b, apply a
# at call:        a: before, b: before, core, b: after, a: after

Order changes meaning. With @timed above @retry, the timing includes all retry attempts; swap them and each attempt is timed separately. With an authorisation check outside a cache, unauthorised callers are rejected before the cache is consulted; put the cache outside and an unauthorised caller might be served a cached result computed for someone else. When stacking, ask what each layer should see.

6. Decorators with state

Some decorators need memory across calls: a call counter, a cache, a rate limiter's timestamps. There are three places to keep it.

In the closure. Variables created in the decorator (level 2) exist once per decorated function and are shared by all its calls — the rate limiter in the drill keeps a deque of timestamps and a lock this way. Rebinding them needs nonlocal (py3); mutating a container does not.

As an attribute on the wrapper. Functions accept attributes, and this makes the state inspectable from outside:

def count_calls(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        wrapper.calls += 1
        return func(*args, **kwargs)
    wrapper.calls = 0
    return wrapper

@count_calls
def ping(): pass
ping(); ping()
print(ping.calls)      # 2

On an instance of a class. Any object with a __call__ method is callable, so a class can be a decorator: __init__ receives the function and __call__ runs on each call. Use functools.update_wrapper(self, func), the non-decorator form of wraps, to copy the metadata.

class CountCalls:
    def __init__(self, func):
        functools.update_wrapper(self, func)
        self.func = func
        self.calls = 0
    def __call__(self, *args, **kwargs):
        self.calls += 1
        return self.func(*args, **kwargs)

This works on plain functions but breaks on methods, for a reason covered next.

7. Decorating methods

A method is just a function stored on a class. When you access it through an instance, obj.m, Python calls the function's __get__ method, which returns a bound method that automatically passes obj as the first argument, self. An object that controls attribute access through __get__ is called a descriptor; functions are descriptors, and py6 explains the mechanism fully.

A function-based wrapper is a function, so it is a descriptor too: obj.m binds it and self arrives in args, forwarded untouched. That is why function decorators just work on methods:

class Svc2:
    @count_calls
    def m(self):
        return f"m on {type(self).__name__}"

Svc2().m()      # 'm on Svc2'

An instance of CountCalls is not a function and has no __get__, so no binding happens and self is never passed:

class Svc:
    @CountCalls
    def m(self): return "m"

Svc().m()
# TypeError: Svc.m() missing 1 required positional argument: 'self'

Class-based decorators that must work on methods need a __get__ that returns functools.partial(self.__call__, instance), or you can simply prefer function-based decorators.

8. Registration decorators

Not every decorator wraps. A registration decorator records the function somewhere and returns it unchanged, so calls have zero overhead:

HANDLERS = {}

def on(event):
    def register(func):
        HANDLERS[event] = func
        return func                 # unchanged
    return register

@on("signup")
def welcome(user):
    return f"welcome {user}"

HANDLERS["signup"]("asha")          # 'welcome asha'
welcome("ravi")                     # 'welcome ravi' — still a normal function

This is the shape of Flask's @app.route, FastAPI's @app.get, Click's @cli.command, pytest's @pytest.fixture and every plugin system. It relies on definition-time execution: importing the module fills the registry. The corresponding pitfall is a handler module that nothing imports, whose routes silently never exist.

9. Class decorators

The @ syntax also works on a class statement: the decorator receives the new class object and returns a class, usually the same one after adding or modifying methods. @dataclasses.dataclass reads the class's annotations and generates __init__, __repr__ and __eq__ (py6). @functools.total_ordering takes a class that defines __eq__ and one ordering method such as __lt__ and fills in __le__, __gt__ and __ge__:

@functools.total_ordering
class Version:
    def __init__(self, n): self.n = n
    def __eq__(self, other): return self.n == other.n
    def __lt__(self, other): return self.n < other.n

Version(1) <= Version(2), Version(3) >= Version(2)    # (True, True)

10. Decorating async functions

A function defined with async def is a coroutine function: calling it does not run its body but returns a coroutine object, and the body runs when that object is awaited (py9 covers asyncio). A normal wrapper calls the function, gets the coroutine back immediately, and returns it — so anything it does "after" happens before the real work:

@timed_sync
async def work1():
    await asyncio.sleep(0.1)

@timed_async                   # async def wrapper that awaits func(...)
async def work2():
    await asyncio.sleep(0.1)

# measured: sync wrapper reports 0.003 ms, async wrapper reports ~110 ms

The fix is a wrapper that is itself async def and awaits the call inside try/finally. A decorator meant for both kinds can branch on inspect.iscoroutinefunction(func) and return the matching wrapper. Note that a sync wrapper also hides the async nature from introspection: inspect.iscoroutinefunction(work1) returns False, which confuses frameworks that dispatch on it.

11. The standard decorators you should know cold

  • @property turns a method into a computed attribute read without parentheses (circle.area); add @area.setter for assignment. Without a setter, c.area = 5 raises AttributeError: property 'area' of 'Circle' object has no setter.
  • @classmethod passes the class instead of the instance, for alternative constructors: Circle.unit() returning cls(1) also works correctly for subclasses.
  • @staticmethod passes neither; a plain function grouped with the class.
  • @functools.cache (3.9+) and @functools.lru_cache(maxsize=N) perform memoisation: they store results keyed by the arguments, which therefore must be hashable (py1: sq([1]) raises TypeError: unhashable type: 'list'). cache is unbounded; lru_cache evicts the least recently used entry. A memoised Fibonacci computes fib(80) with 81 misses and 78 hits instead of billions of calls; fib.cache_info() reports those numbers.
  • @functools.cached_property computes a value on first access and stores it on the instance, so later accesses are plain attribute reads (the lab shows "computing" printed once).
  • @functools.singledispatch chooses an implementation by the type of the first argument: register handlers with @show.register and a type annotation, and show(3), show([1, 2]), show("s") give int 3, list of 2, object 's'.
  • @contextlib.contextmanager turns a generator into a context manager (py7), and @abc.abstractmethod marks methods subclasses must implement (py6).

12. Putting it together: tracing a decorated handler

Return to the inference handler from the introduction, now written as @require_api_key above @timed above @retry(times=3, exceptions=(ConnectionError,)) above def predict(request). Trace what happens.

At import. Python creates the function object for predict. It then evaluates retry(times=3, exceptions=(ConnectionError,)), gets a decorator, and applies it: call the result R, a wrapper holding the original. Next it applies timed to R, producing T, which holds R. Finally require_api_key is applied to T, producing K, and the name predict is bound to K. Because every layer used functools.wraps, predict.__name__ is still "predict" and inspect.signature(predict) still shows (request), so the web framework registers the right parameter.

A request with a bad key. K runs first, checks the key, and raises Unauthorized. T and R never run, so no timing is logged and the model server is never contacted. That is the reason the key check is outermost.

A request where the model server resets once. K passes the request to T, which starts its timer and calls R. R calls the original; it raises ConnectionError; R logs attempt 1 and loops; the second attempt succeeds and R returns the result. T's finally block logs the elapsed time — including both attempts, because T is outside R — and returns the result through K to the framework.

If the dashboard should instead show the latency of individual model calls, swap @timed and @retry. The function body did not change at all; only the order of the layers did. That separation is exactly what the decorators bought us.

13. A checklist for writing any decorator

  1. Does it need configuration? If yes, write a factory (three levels), and consider supporting use without parentheses.
  2. Decorate the wrapper with @functools.wraps(func).
  3. Accept *args, **kwargs and forward them unchanged.
  4. Return the original's return value.
  5. Put "after" logic in finally if it must run on errors, and let exceptions propagate unless handling them is the point.
  6. If the decorated function might be async def, provide an async wrapper.
  7. Keep state in the closure or on the wrapper, and protect it with a lock if threads can call concurrently.
  8. Do nothing expensive at decoration time.

Typing decorators: ParamSpec and PEP 695

If a decorator is annotated as taking and returning Callable[..., Any], a type checker forgets everything about the decorated function: wrong argument counts and types at call sites are no longer caught, and the return type becomes Any. PEP 612 (Python 3.10) added ParamSpec, a type variable that captures a whole parameter list. With the PEP 695 syntax available since 3.12, a signature-preserving decorator is written:

from collections.abc import Callable

def logged[**P, R](func: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        return func(*args, **kwargs)
    return wrapper

On older versions the same thing is spelled with P = ParamSpec("P") and R = TypeVar("R"). For decorators that inject or remove a leading argument (a request object, a database session), Concatenate[Session, P] describes the difference. Type checkers such as mypy and Pyright then check calls to decorated functions exactly as if they were undecorated.

What wraps does and does not preserve

functools.wraps copies metadata, but the wrapper is still a different object with a different code object. inspect.signature follows __wrapped__, but anything that reads func.__code__ directly (some old tools, profilers keyed by code object) still sees the wrapper. wraps also cannot make a sync wrapper look like a coroutine function; since 3.12, inspect.markcoroutinefunction can mark a sync function that returns awaitables so iscoroutinefunction reports True. Libraries that need perfect transparency — correct behaviour on methods, classmethods, staticmethods and descriptors, plus picklability — use Graham Dumpleton's wrapt, whose design notes document all the edge cases.

lru_cache internals and thread safety

lru_cache is implemented in C as a dict from a key (built from the positional and keyword arguments, with typed=True distinguishing 1 from 1.0) to a node in a circular doubly linked list ordered by recency. A hit moves the node to the front; a miss beyond maxsize evicts the node at the back. The cache's own bookkeeping is thread-safe, but the wrapped function is not locked: if two threads miss on the same key simultaneously, both compute the value, and the second result overwrites the first. For expensive idempotent computations that is acceptable; for side-effecting ones it is not. cache_info() and cache_clear() are exposed on the wrapper for monitoring and tests.

cached_property and the 3.12 lock removal

cached_property is a descriptor that defines only __get__. The first access runs the method and stores the result in the instance's __dict__ under the same name; because instance attributes take priority over non-data descriptors (py6), later accesses never reach the descriptor at all, which is why it is essentially free after the first call. It requires the instance to have a __dict__, so it does not work with __slots__-only classes. Until 3.11 it held an undocumented lock that was per property rather than per instance, causing heavy contention in threaded servers; 3.12 removed the lock, so two threads can now compute the value concurrently and one result wins.

classmethod chaining: added in 3.9, removed in 3.13

Python 3.9 allowed classmethod to wrap other descriptors, so @classmethod stacked on @property seemed to create a class-level property. The interaction with other descriptors was inconsistent, so the feature was deprecated in 3.11 and removed in 3.13; on current versions that stack does not produce a class property. Decorator order with classmethod and staticmethod matters for the same reason: your own wrapper should usually be applied first (listed below them) so it wraps the plain function, and @classmethod goes outermost.

Relaxed decorator grammar (PEP 614)

Until Python 3.9 the expression after @ had to be a dotted name, optionally followed by one call, so @buttons["save"].on_click was a syntax error and people wrote @_ = buttons["save"].on_click style workarounds. PEP 614 allowed any expression. It rarely matters day to day, but it explains why older codebases contain odd helper variables used only as decorators.

Decorators, metaclasses and __init_subclass__

Class decorators, __init_subclass__ and metaclasses can all customise classes. A class decorator runs once, on the class it is written above, after the class is created, and is not inherited. __init_subclass__ (Python 3.6) is a hook on a base class called for every subclass definition, ideal for plugin registration by inheritance. A metaclass controls class creation itself (for example, providing a custom namespace for the class body) and is inherited, but combining two bases with unrelated metaclasses raises a conflict. Prefer the lightest tool that does the job — usually a decorator or __init_subclass__.

Cost of a wrapper

Each layer of decoration adds a Python function call, typically tens of nanoseconds, plus the cost of packing and unpacking *args and **kwargs. That is irrelevant for request handlers and significant for a function called millions of times in a tight loop. Registration decorators and cached_property after its first access cost nothing per call; that is a useful design lever when overhead matters.

Retry decorators that make outages worse

The most dangerous decorator in production is a naive retry. Retrying immediately, with no backoff, turns a struggling dependency into one receiving three times the traffic; retrying at every layer of a call chain multiplies attempts (three layers of three retries is 27 calls); and retrying non-idempotent operations — charging a card, sending an email, appending to a log — duplicates side effects. A production retry decorator uses exponential backoff with jitter (random spread so clients do not retry in lock-step), a maximum total time, a whitelist of transient exception types, and is applied at one layer only. The tenacity library provides this; scale track topic sc12 covers retry budgets.

Unbounded caches as memory leaks

@functools.cache on a function whose arguments come from user input (ids, query strings, prompts) grows forever; the process's memory rises steadily until it is killed. Use lru_cache(maxsize=...) or a time-to-live cache, and watch cache_info(): a low hit rate means the cache is only costing memory. On methods, the class-level cache also pins instances (see the myths), a common leak in services that create a client object per request.

Import-time side effects

Because decorators run at import, a decorator that connects to a database, reads configuration from the network or loads a model makes importing the module slow and fragile — tests that merely import it need the network. Keep decorator bodies cheap and defer work to the first call. The flip side, registration by import, causes "missing route" bugs when a module is never imported; frameworks solve it with explicit router inclusion or entry points.

Observability decorators

Timing, tracing and metrics decorators are a legitimate and common use: OpenTelemetry's instrumentation, prometheus_client's @REQUEST_TIME.time(), and logging decorators that record arguments. Two rules: use functools.wraps so the metric or span name is the real function's name rather than "wrapper", and never log full arguments by default, because they often contain personal data, secrets or huge payloads (prompts, embeddings).

Decorators and frameworks that inspect signatures

FastAPI, pytest and Typer build behaviour from function signatures. A custom decorator that omits wraps, or that changes the parameters (adds an injected argument) without adjusting __signature__, makes FastAPI expose args and kwargs as required query parameters or makes pytest fail to find fixtures. When a framework mysteriously ignores or misreads your parameters after you added a decorator, check inspect.signature on the decorated function first.

Authorisation decorators

Decorators such as @login_required or @requires_role("admin") are a convenient way to attach access checks to handlers, and a dangerous one when they are the only defence: a handler that someone forgets to decorate is open to everyone, and nothing fails loudly. Robust services invert the default — deny unless a route explicitly declares its permission, enforced by middleware or by the router — and add a test that enumerates every registered route and asserts it has a policy. The decorator then declares the policy rather than being the sole enforcement point.

Debugging decorated code

Stack traces through decorated functions show one extra frame per layer, named after the wrapper's code (wrapper) even when wraps is used, because tracebacks read the code object's name. Knowing that each wrapper frame belongs to a decorator makes long traces readable. To bypass decoration in a test or a debugging session, call func.__wrapped__; inspect.unwrap(func) follows the whole chain to the innermost original.

import functools, threading, time
from collections import deque

def rate_limited(calls, per_seconds, clock=time.monotonic):
    def decorator(func):
        stamps = deque()
        lock = threading.Lock()

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            now = clock()
            with lock:
                while stamps and now - stamps[0] >= per_seconds:
                    stamps.popleft()
                if len(stamps) >= calls:
                    raise RuntimeError(f"{func.__name__}: rate limit exceeded")
                stamps.append(now)
            return func(*args, **kwargs)      # call outside the lock
        return wrapper
    return decorator

Points to say out loud: it takes configuration, so it is a three-level factory. functools.wraps keeps the name for the error message and for logs. time.monotonic, not time.time, because the wall clock can jump when the system clock is adjusted. The clock is injectable so tests can simulate time without sleeping. The deque and lock live in the level-2 closure, so each decorated function has its own limit. The lock protects the check-then-append sequence, which would otherwise let two threads both see room for one more call; the real call happens outside the lock so a slow function does not serialise all callers. This is a sliding-window log using O(calls) memory; mention the token bucket as the O(1)-memory alternative that also allows short bursts.
