An analyst needs the number of error events per service per hour from a 40 GB log file, one JSON object per line. The first attempt is what most people write:

lines = open("app.log").readlines()          # read the whole file into a list
events = [json.loads(l) for l in lines]      # parse every line into a dict
errors = [e for e in events if e["level"] == "error"]

The laptop has 16 GB of RAM. readlines() alone needs more than 40 GB, because every line becomes a Python string object with its own header; the list of parsed dicts would need several times more. The process is killed by the operating system before the first filter runs. The frustrating part is that the answer — a few thousand counts — is tiny. The program never needed all the data at once; it only needed to look at each line, update a counter, and move on.

Python has a built-in way to express exactly that: the iterator protocol and its most convenient form, the generator. Rewriting the three lines as generators changes almost nothing visually but changes everything about memory: the program then holds one line at a time and finishes with a few megabytes of RAM. The same idea powers reading database results in chunks, paginating through an API, feeding batches to a model during training, and streaming an LLM's answer to a browser token by token.

Iteration is also where a whole class of silent bugs lives: a generator consumed twice that gives an empty result the second time, items skipped because a list was modified during a loop, groupby producing duplicate groups, a file left open by a half-consumed generator. Interviewers probe these because they reveal whether you understand what a for loop actually does.

This lesson starts by taking a for loop apart into iter(), next() and StopIteration. It then separates iterables from iterators, writes an iterator by hand, and introduces generators as the easy way to write one — including what "suspending a function" means. It builds lazy pipelines, explains comprehensions and generator expressions precisely, tours itertools, and finishes with the advanced generator features — yield from, send, close — and the cleanup rules that matter in production. Code was run on CPython 3.12.10; features newer than 3.8 are marked with their version.

A ticket dispenser, not a pile of tickets

Imagine a deli counter. One way to serve customers is to print a thousand numbered tickets in the morning and hand people the pile — you need space for all of them before anyone is served, and if only thirty customers come, you printed 970 tickets for nothing. The other way is a ticket dispenser: each pull gives you the next number, and the machine only remembers the last number it issued.

A list is the pile of tickets: all values exist in memory at once, and you can count them, index them, and go through them as many times as you like. An iterator is the dispenser: it hands out one value per request, remembers only where it is, and once it has handed out its last ticket it is empty for good. Python's for loop does not care which one it gets; it only needs something that can be asked for "the next value" repeatedly.

What a for loop really does

This loop:

for x in [10, 20, 30]:
    print(x)

is shorthand for:

it = iter([10, 20, 30])       # ask the list for a dispenser (an iterator)
while True:
    try:
        x = next(it)          # pull the next ticket
    except StopIteration:     # the dispenser is empty
        break
    print(x)

Two built-in functions and one exception are the whole mechanism. iter(obj) asks an object for an iterator. next(it) asks the iterator for its next value. When there are no more values, the iterator raises StopIteration, which the loop treats as "done" rather than as an error.

Generators: writing a dispenser the easy way

You can build a dispenser by writing a function that uses yield instead of return:

def countdown(n):
    while n > 0:
        yield n          # hand out n, then pause right here
        n -= 1

for x in countdown(3):
    print(x)             # 3, 2, 1

Calling countdown(3) does not run the loop. It returns a generator, an iterator whose values come from running the function body a bit at a time. Each next() runs the body until it reaches a yield, hands out that value, and freezes the function in place, local variables and all. The next next() unfreezes it and carries on from the line after the yield.

That pause-and-resume behaviour is what makes generators lazy: nothing is computed until someone asks, and only one value exists at a time. Chain several generators together and data flows through them one item at a time, which is how the 40 GB log is processed in constant memory.

Where the ticket analogy breaks: some objects, like lists, are not dispensers themselves but dispenser factories. Every for loop over a list asks it for a brand-new iterator, which is why you can loop over a list twice but not over a generator twice. That distinction — iterable versus iterator — is the first thing the body makes precise.

1. The iterator protocol, precisely

Python defines iteration through two special methods, known together as the iterator protocol:

  • __iter__() returns an iterator. The built-in iter(obj) calls it.
  • __next__() returns the next value, or raises StopIteration when there are no more. The built-in next(it) calls it.

Watch it by hand on a list:

nums = [10, 20, 30]
it = iter(nums)
print(type(it).__name__, next(it), next(it), next(it))   # list_iterator 10 20 30
next(it)                                                   # raises StopIteration

Many built-ins consume iterators exactly like a for loop does: list(), tuple(), sum(), max(), sorted(), "".join(), the in operator, unpacking a, b = pair, and *args at call sites. Any object that implements the protocol works with all of them. next(it, default) returns default instead of raising when the iterator is exhausted, which is the safe way to ask for "the first item, if any".

2. Iterables versus iterators

These two words are easy to blur, and the difference explains the most common iteration bug.

An iterable is any object you can pass to iter(). Containers like lists, tuples, strings, dicts, sets and ranges are iterables whose __iter__ creates a new iterator each time, starting from the beginning. So you can loop over a list as many times as you like, and even run two loops over it at once.

An iterator is the object that actually walks through the values. It has __next__, and its __iter__ simply returns itself. It remembers its position, and once it has raised StopIteration it is exhausted: it will keep raising StopIteration forever. Generators, file objects, and the results of map, filter, zip and enumerate are all iterators.

print(iter(it) is it)               # True  — an iterator is its own iterator
print(iter(nums) is iter(nums))     # False — a list makes a fresh iterator each time

gen = (x * x for x in range(3))
print(list(gen), list(gen))         # [0, 1, 4] []  — second pass is silently empty

Practical consequence: if a function receives an iterable and needs to walk it twice (say, once to compute a mean and once to compute deviations), it must either convert it to a list first or document that it requires a re-iterable container. Passing a generator to such a function gives wrong results with no exception.

3. Writing an iterator class

To see there is no magic, here is an iterator written by hand:

class Countdown:
    def __init__(self, start):
        self.current = start
    def __iter__(self):
        return self                    # it is its own iterator
    def __next__(self):
        if self.current <= 0:
            raise StopIteration
        self.current -= 1
        return self.current + 1

print(list(Countdown(3)))              # [3, 2, 1]

It works, but notice the ceremony: the state (current) must be stored on self, and the logic of "count down, stopping at zero" is split across a method that is called once per value. For anything more complex — nested loops, several phases, a try/finally around a file — writing the state machine by hand gets painful fast. Generators exist to remove exactly this ceremony.

4. Generators: functions that pause

A function whose body contains yield anywhere is a generator function. Calling it does not execute the body; it returns a generator object that wraps a frame for the function (py3: the frame holds local variables and the current position). Let us instrument countdown to watch the frame's life cycle:

import inspect

def countdown(n):
    print("starting")
    while n > 0:
        yield n
        n -= 1
    print("done")

g = countdown(2)
print(type(g).__name__, inspect.getgeneratorstate(g))   # generator GEN_CREATED  (nothing printed yet)
print(next(g))                                           # starting / 2
print(inspect.getgeneratorstate(g))                      # GEN_SUSPENDED
print(next(g))                                           # 1
next(g)                                                  # done / raises StopIteration
print(inspect.getgeneratorstate(g))                      # GEN_CLOSED

Trace it. Creating g printed nothing: the body had not started. The first next ran from the top, printed "starting", reached yield n with n = 2, handed 2 back, and suspended. The frame stayed alive with n = 2 stored in it. The second next resumed after the yield, ran n -= 1, looped, and yielded 1. The third resumed, decremented to 0, left the loop, printed "done" and fell off the end of the function. Falling off the end (or executing return) makes next raise StopIteration, and the generator is closed for good.

The generator did everything the Countdown class did in six fewer lines, with the state held naturally in local variables and the control flow written as a normal loop. That is why hand-written iterator classes are rare in modern Python.

5. Laziness and memory

Because a generator produces values on demand, it holds only its own frame, however many values it will eventually produce. Compare a list comprehension and a generator expression over a million items on 3.12:

import sys
sys.getsizeof([x for x in range(1_000_000)])   # 8448728  — ~8.4 MB of pointers (plus the int objects)
sys.getsizeof((x for x in range(1_000_000)))   # 192      — just the generator object

Laziness has a second benefit: work that is never requested is never done. next(x for x in huge if is_match(x)) stops at the first match. And a third: generators can be infinite. itertools.count() yields 0, 1, 2, ... forever, which is fine as long as the consumer stops.

The costs are the other side of the same coin. A generator can be consumed once, has no len(), cannot be indexed, and raises its errors during iteration rather than when it is created, which can put a traceback far from the code that caused it. Per item, it is often slightly slower than a list comprehension because of the resume/suspend overhead. Use a list when data is small and you need random access or several passes; use a generator when data is large, unbounded, streamed, or likely to be abandoned early.

6. Comprehensions and generator expressions

A comprehension is compact syntax for building a collection from a loop. There are four forms, differing only in brackets:

[x * x for x in range(6) if x % 2 == 0]      # list:   [0, 4, 16]
{w: len(w) for w in ["a", "bb"]}             # dict:   {'a': 1, 'bb': 2}
{c for c in "hello"}                         # set:    the four distinct letters h, e, l, o
(x * x for x in range(10))                   # generator expression: lazy, no brackets of its own

The first three are eager: they run to completion immediately and build the whole collection. The parenthesised form is a generator expression, the lazy version. When a generator expression is the only argument to a function, its parentheses can be dropped: sum(x * x for x in range(10)) gives 285 without ever building a list.

How to read a comprehension with several clauses: the for and if clauses are nested loops written in the same order as the equivalent loop code, left to right, and the expression at the front is what gets collected:

[(i, j) for i in range(2) for j in range(3) if j != i]
# same as:
# for i in range(2):
#     for j in range(3):
#         if j != i:
#             result.append((i, j))
# → [(0, 1), (0, 2), (1, 0), (1, 2)]

Two things are easy to confuse. An if after the for is a filter and has no else. A conditional expression at the front chooses a value for every item: ["even" if x % 2 == 0 else "odd" for x in range(3)] gives ['even', 'odd', 'even']. And when the filter and the value need the same computed result, the walrus operator := (Python 3.8+) assigns inside the expression so it is computed once:

data = ["3", "x", "5"]
[n for s in data if (n := int(s) if s.isdigit() else None) is not None]   # [3, 5]

Readability rule: if a comprehension needs more than two for clauses or a nested conditional, write the loop. Comprehensions have their own scope (py3), so the loop variable does not leak into the surrounding code.

7. Pipelines: generators feeding generators

Because a generator accepts any iterable and is itself an iterable, generators snap together into a pipeline. Here is the 40 GB log problem from the introduction:

import json
from collections import Counter

def read_lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:                # a file object yields one line at a time
            yield line

def parse(lines):
    for line in lines:
        try:
            yield json.loads(line)
        except json.JSONDecodeError:
            continue                  # skip corrupt lines (count them in real code)

def only_errors(events):
    return (e for e in events if e["level"] == "error")

counts = Counter((e["service"], e["ts"][:13])          # "YYYY-MM-DDTHH"
                 for e in only_errors(parse(read_lines("app.log"))))

This is a pull-based pipeline. Counter asks only_errors for an item; only_errors asks parse; parse asks read_lines; read_lines reads one line from the file. The item then travels forward through every stage before the next line is read. Memory is proportional to the number of distinct (service, hour) keys in the Counter, not to the file. Each stage is small, testable with a plain list as input, and reusable.

8. The itertools toolbox

The itertools module provides fast, lazy building blocks written in C. The ones worth knowing by heart, with real outputs:

from itertools import islice, count, chain, groupby, batched, pairwise, accumulate, product

list(islice(count(10, 5), 4))          # [10, 15, 20, 25]   slice any iterator; count() is infinite
list(chain([1, 2], (3, 4)))            # [1, 2, 3, 4]       concatenate iterables lazily
list(batched(range(7), 3))             # [(0, 1, 2), (3, 4, 5), (6,)]   3.12+; strict= in 3.13
list(pairwise([1, 4, 9, 16]))          # [(1, 4), (4, 9), (9, 16)]      3.10+
list(accumulate([1, 2, 3, 4]))         # [1, 3, 6, 10]       running totals
list(product("ab", [0, 1]))            # [('a', 0), ('a', 1), ('b', 0), ('b', 1)]

groupby deserves special care, because it groups only consecutive equal keys:

[(k, list(g)) for k, g in groupby("aabbba")]
# [('a', ['a', 'a']), ('b', ['b', 'b', 'b']), ('a', ['a'])]   — 'a' appears twice
[(k, len(list(g))) for k, g in groupby(sorted("aabbba"))]
# [('a', 3), ('b', 3)]

batched is the everyday tool for sending work to bulk APIs — embed 100 texts per request, insert 1,000 rows per statement. Related built-ins: zip pairs up iterables and stops at the shortest, silently dropping extras; since 3.10, zip(a, b, strict=True) raises ValueError: zip() argument 2 is shorter than argument 1 instead, which catches misaligned data. enumerate adds indexes, and map and filter return lazy iterators in Python 3.

9. yield from: delegating to a sub-generator

A generator often wants to yield everything another iterable produces. yield from sub does that, and also evaluates to the sub-generator's return value (a generator's return x is delivered inside the StopIteration that ends it):

def inner():
    yield 1
    yield 2
    return "inner done"

def outer():
    result = yield from inner()
    print("got", result)
    yield 3

print(list(outer()))
# got inner done
# [1, 2, 3]

For simple flattening, yield from is just a shorter loop. Its deeper job is to make the sub-generator fully transparent: values sent in and exceptions thrown in (next section) pass straight through to it. That property is what let generators act as coroutines before async/await existed, and it is how recursive generators, such as walking a tree, are written cleanly.

10. Two-way generators: send, throw and close

A generator's yield is also an expression that can receive a value. gen.send(value) resumes the generator and makes the paused yield evaluate to value. The generator must first be advanced to its first yield with next() (called "priming"):

def running_avg():
    total = count = 0
    avg = None
    while True:
        x = yield avg        # hand out the current average, receive the next number
        total += x
        count += 1
        avg = total / count

ra = running_avg()
next(ra)                                         # prime: run to the first yield
print(ra.send(10), ra.send(20), ra.send(60))     # 10.0 15.0 30.0

gen.throw(exc) raises an exception at the paused yield, and gen.close() raises GeneratorExit there, so that any finally blocks and with blocks inside the generator run:

def g2():
    try:
        yield 1
        yield 2
    finally:
        print("cleanup")

x = g2()
next(x)       # 1
x.close()     # prints "cleanup"; state is now GEN_CLOSED

In everyday code you will rarely call send or throw yourself — asyncio (py9) replaced generator-based coroutines — but close() and its cleanup guarantee matter whenever a generator holds a file or connection.

11. Iteration pitfalls to recognise instantly

Consuming an iterator twice. The second pass yields nothing and raises nothing. Materialise with list() if you need two passes.

in consumes. it = iter([1, 2, 3, 4]); 3 in it is True, and afterwards list(it) is [4]. The same happens with map objects.

Modifying a list while looping over it. The iterator advances by index, so removals skip elements: looping over [2, 4, 6] and removing evens leaves [4]. Dicts and sets detect size changes and raise RuntimeError: dictionary changed size during iteration. Build a new collection instead.

Raising StopIteration inside a generator. Since 3.7 (PEP 479) it becomes RuntimeError: generator raised StopIteration. End a generator with return.

What a suspended generator actually holds

A generator object owns a frame: the code object, the instruction pointer, the local variables and the value stack. When it yields, the interpreter saves that state inside the generator object and returns to the caller; when resumed, it continues at the next instruction. Since 3.11 generator frames are allocated inside the generator object itself rather than as separate heap objects, making creation cheaper. Everything the frame references stays alive while the generator is suspended — which is exactly why an abandoned generator can hold a file, a lock or a large buffer. inspect.getgeneratorlocals(g) shows the live locals of a suspended generator, a useful debugging aid.

Cleanup semantics and deterministic closing

When a generator is closed — explicitly, by exhaustion, or by garbage collection — Python raises GeneratorExit at the paused yield. The generator must let it propagate (or return); if it yields again instead, close() raises RuntimeError: generator ignored GeneratorExit. In CPython, reference counting usually closes an abandoned generator as soon as the last reference disappears, but in a reference cycle, on PyPy, or when a traceback keeps the frame alive, it can be much later. contextlib.closing(gen) gives a with block that calls close() on exit; for async generators, contextlib.aclosing (3.10+) does the same with aclose().

PEP 479: why StopIteration became RuntimeError

Before 3.7, a bare next(it) inside a generator that hit an exhausted iterator raised StopIteration, which propagated out of the generator and looked exactly like the generator finishing normally. The consumer's loop quietly ended early and data was lost without an error. PEP 479 made any StopIteration escaping a generator's body into a RuntimeError, turning silent truncation into a loud failure. The idiom inside generators is item = next(it, sentinel) and return when the sentinel appears.

Async iteration

The async world has a parallel protocol: __aiter__ and __anext__, consumed with async for, and async generators (an async def containing yield, 3.6+) that can await between yields. They are the natural shape for paginated HTTP APIs, database cursors in async drivers, and LLM token streams. Async comprehensions ([x async for x in agen]) exist too. The asyncio event loop tracks async generators and finalises forgotten ones at shutdown (loop.shutdown_asyncgens(), which asyncio.run calls), which is why their cleanup code can run surprisingly late. py9 covers the event loop.

tee, and why buffering can defeat laziness

itertools.tee(it, n) creates n iterators over one source by keeping a shared buffer of items consumed by some copies but not yet by others. If the copies advance together — a sliding comparison, for instance — the buffer stays small. If one copy is fully consumed before the other starts, the buffer holds the entire stream and you have built a list with extra overhead. The original iterator must also not be used after teeing, since advancing it would bypass the buffer.

Performance: comprehensions, generators and vectorisation

A list comprehension is faster than an equivalent loop with append because it avoids looking up and calling the append method on each iteration; since 3.12 (PEP 709) comprehensions are also inlined rather than executed as a hidden nested function. Generator expressions pay a small resume/suspend cost per item, so for small data a list comprehension is usually faster, while for large data the generator wins by not allocating. For numeric work, neither is competitive with NumPy, which applies an operation to a whole array in C: a sum of squares over ten million floats is typically tens of times faster with NumPy than with a generator expression. Choose generators for streaming and memory, vectorisation for arithmetic throughput.

Generator-based context managers and coroutines

The generator's ability to pause in the middle of a try/finally is what @contextlib.contextmanager exploits: the code before yield is the setup, the yield hands a value to the with block, and close() or throw() resumes it to run the teardown (py7). Historically, send and yield from were the building blocks of asyncio's first coroutines (@asyncio.coroutine, removed in 3.11); async def and await are the dedicated syntax that replaced them, but under the hood a coroutine object still has send and throw.

The legacy sequence protocol

iter() has a fallback that predates __iter__: if an object has no __iter__ but has __getitem__, Python builds an iterator that calls obj[0], obj[1], ... until IndexError is raised. A class with only __getitem__ returning i * 10 below 3 therefore gives list(Seq()) == [0, 10, 20] and supports in. It explains why some old classes are iterable without looking like it, and why isinstance(x, collections.abc.Iterable) can return False for an object that iterates perfectly well — the only reliable test is to call iter(x) and catch TypeError.

Streaming instead of materialising

The biggest production win from this lesson is memory. Jobs that read a whole file, table or API response into a list before processing it have memory proportional to input size, so they fail on the largest customer or the busiest day. Streaming rewrites — iterate the file, use a database server-side cursor (cursor.itersize in psycopg, yield_per in SQLAlchemy), paginate API calls in a generator — keep memory flat. The symptom that you need one is the process being killed by the out-of-memory killer (exit code 137 in containers) only on large inputs.

Batching for bulk APIs

Embedding services, vector databases and warehouses all prefer batches: one request with 100 texts is far cheaper than 100 requests. A generator pipeline with itertools.batched(texts, 100) (or an islice loop on older versions) gives batching without loading everything. Pair it with backpressure — only fetching the next batch when the previous one is sent — and the job's memory is bounded by the batch size.

Token streaming to users

LLM applications stream tokens to the browser so the first words appear in a few hundred milliseconds rather than after the full completion. The server-side shape is a generator (or async generator) that iterates the model client's stream and yields server-sent-event chunks, returned in something like FastAPI's StreamingResponse. The production details: detect client disconnects and cancel the upstream request, put cleanup in finally, flush proxies (some buffer responses unless configured), and record the full text for logging after the stream ends.

The exhausted-iterator bug

A common incident: a function computes a list of records as a generator for memory reasons, then passes it to both a validation step and a write step. Validation consumes it, and the write step writes nothing. Tests pass because they used lists. The fix is to make the contract explicit: accept Iterable and consume once, or accept Sequence and convert at the boundary. Type hints (Iterator[Row] versus list[Row], py10) make the distinction visible in review.

Leaked resources from half-consumed generators

A generator that opens a database cursor or file and is abandoned after the first few items (because the consumer found what it wanted or raised an exception) keeps that resource open until it is collected. Under load this shows up as connection-pool exhaustion or "too many open files". Close generators explicitly, use contextlib.closing, or restructure so the with block lives in the consumer rather than inside the generator.

Training data loaders are iterators too

In model training, PyTorch's DataLoader is an iterable: each for batch in loader creates a fresh iterator, which is why every epoch starts from the beginning (and reshuffles). A map-style Dataset implements __getitem__ and __len__; an IterableDataset implements __iter__, usually as a generator that streams records from files or object storage that do not fit in memory. The classic bug with the latter is that each worker process runs its own copy of the generator, so without sharding by worker id every sample is seen once per worker. Recognising the loader as "just the iterator protocol" makes such bugs much easier to reason about.

Errors surface late

With lazy pipelines, a bad input raises inside the consumer's loop, possibly minutes into a job and far from the function that created the generator. Log enough context in each stage (the line number or record id) to find the offending input, and decide deliberately whether a stage should skip bad records (counting them in a metric) or fail the whole job. Silent skipping without a counter is how data quietly goes missing.

Build it

A 40 GB log file has one JSON event per line. Produce the count of error events per service per hour, without loading the file into memory. Then: the same file also needs the first 100 events after a given timestamp — how do you avoid reading the rest?

Answer 
import json
from collections import Counter
from itertools import islice

def events(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            try:
                yield json.loads(line)
            except json.JSONDecodeError:
                continue                         # count these in real code

def errors(evts):
    return (e for e in evts if e["level"] == "error")

counts = Counter((e["service"], e["ts"][:13]) for e in errors(events("app.log")))  # "YYYY-MM-DDTHH"

Memory is proportional to the number of (service, hour) buckets, not to the file. The Counter is the only accumulated state; every stage is a generator that holds one item at a time, and the file object itself yields one line at a time.

Second part: list(islice((e for e in events(p) if e["ts"] >= t0), 100)). Laziness means reading stops as soon as 100 matches have been produced; the rest of the file is never read. Because we stopped early, the events generator is left suspended inside its with block, so wrap it in contextlib.closing (or let reference counting close it) to release the file promptly. If lines are in timestamp order and this query is frequent, binary-search the file by byte offset — seek to the middle, skip to the next newline, compare timestamps — to avoid scanning the prefix at all.

Trade-off to mention: single-threaded parsing of 40 GB is CPU-bound on json.loads. Split the file by byte ranges across processes (multiprocessing, py9) and merge the Counters, which add together with +, or use a faster parser such as orjson.
