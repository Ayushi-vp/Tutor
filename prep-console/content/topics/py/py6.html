A backend engineer adds a Team class to a service, with members = [] written at the top of the class body because that looked like a sensible default. Every team created afterwards shares one list, so adding someone to the data-science team adds them to every team. Meanwhile a colleague writing a mixin for audit logging calls Base.__init__(self) directly instead of super().__init__(), and a second mixin's initialiser silently never runs, leaving its lock set to None until the first concurrent request crashes. Another teammate defines __eq__ on a value class and suddenly instances cannot go into a set.

None of these developers were bad at object-oriented programming. They brought mental models from Java, C# or C++, where fields are declared per instance, super means the parent, and privacy is enforced. Python's object model looks similar on the surface but is built from a small number of different mechanisms: dictionaries of attributes, a lookup order, descriptors that intercept attribute access, and special methods that the interpreter calls behind your syntax. Knowing those mechanisms is what lets you predict what obj.attr, super(), a + b, len(x) or x == y will actually do.

This matters beyond puzzles. The libraries an AI engineer uses daily are built on these mechanisms: PyTorch's nn.Module intercepts attribute assignment to register parameters, Pydantic and dataclasses generate methods from annotations, SQLAlchemy columns are descriptors, and Enum uses a metaclass. When one of them behaves strangely, the explanation is almost always in this lesson.

The lesson starts with what a class and an instance are, and how Python finds an attribute. It then covers methods and binding, class versus instance attributes, inheritance and overriding, super() and the C3 method resolution order, and the special methods that plug objects into Python's syntax. Next come properties and descriptors — the mechanism under methods, properties and ORMs — then dataclasses, __slots__, abstract base classes versus Protocols, and finally __init_subclass__ and metaclasses. Everything was run on CPython 3.12.10.

Blueprints and houses, with a twist

The usual analogy is that a class is a blueprint and an instance is a house built from it. That is a good start: the class describes behaviour (methods) shared by all instances, and each instance holds its own data (attributes).

The twist in Python is that both the blueprint and the houses are live objects, and each has its own little table of names — a dictionary called __dict__. When you ask a house for something, say house.colour, Python first looks in the house's own table; if it is not there, it looks in the blueprint's table; if not there, in the blueprint's parent blueprints. So a house can "have" things that are really stored on the blueprint and shared with every other house built from it.

class Account:
    bank = "PyBank"                         # stored on the class: shared
    def __init__(self, owner, balance=0):
        self.owner = owner                  # stored on this instance
        self.balance = balance
    def deposit(self, amount):
        self.balance += amount
        return self.balance

a = Account("asha", 100)
print(a.__dict__)      # {'owner': 'asha', 'balance': 100}  — no 'bank' here
print(a.bank)          # PyBank — found on the class

Calling Account("asha", 100) creates a new, empty instance and then runs __init__ with the instance as self, which stores owner and balance in the instance's own table. bank lives only on the class and is found there by the lookup.

Methods are just functions stored on the class

deposit is an ordinary function sitting in the class's table. When you write a.deposit(50), Python finds it on the class and hands back a version with a already filled in as the first argument, self. So a.deposit(50) and Account.deposit(a, 50) do exactly the same thing. There is nothing magic about the name self; it is just the conventional name of the first parameter, and Python never passes it implicitly anywhere except through this lookup.

Special methods: plugging into Python's syntax

Python's syntax and built-ins are implemented by calling methods with double-underscore names, nicknamed dunder methods. len(x) calls x.__len__(), a + b calls a.__add__(b), x == y calls x.__eq__(y), and print(x) uses x.__str__(). Define those methods on your class and your objects work with the built-in syntax. This is why Python code rarely needs interfaces like Comparable or Iterable: an object that has the right methods simply works — the idea called duck typing ("if it quacks like a duck...").

Where the blueprint analogy breaks: a real blueprint cannot be changed after the houses are built, but a Python class can. Adding a method to a class after instances exist makes it available on all of them immediately, because they look it up on the class every time. And a class is itself an object — an instance of type — which is where metaclasses come in at the end of the lesson.

1. Creating an instance: __new__ then __init__

A class statement runs its body like a small module, collects the names it defines into a namespace, and creates a class object from it. Calling the class, Account("asha", 100), performs two steps. First Account.__new__(Account, ...) allocates a new, empty instance (normally inherited from object). Then, if __new__ returned an instance of the class, __init__(instance, "asha", 100) initialises it. __init__ must return None; its job is to set attributes on self.

You almost never override __new__. The exception is subclassing an immutable type, where the value must be decided before the object exists: class Upper(str): def __new__(cls, v): return super().__new__(cls, v.upper()) makes Upper("abc") equal to 'ABC'. __new__ can also return an existing object, which is how a singleton or an instance cache is written, though a module-level instance is usually a simpler singleton.

2. Class attributes and instance attributes

Anything assigned in the class body is a class attribute, stored once on the class. Anything assigned through self is an instance attribute, stored on that one object. Reading looks at the instance first and then the class, so instances share class attributes. Writing through an instance always writes to the instance, creating an attribute that shadows the class one:

b = Account("ravi")
a.bank = "Mine"                         # creates an instance attribute on a only
print(a.bank, b.bank, Account.bank)     # Mine PyBank PyBank

Mutation is different from assignment (py1). self.members.append(x) does not assign self.members; it looks up members — finding the class's list — and mutates it:

class Team:
    members = []                        # ONE list, stored on the class
    def add(self, m):
        self.members.append(m)

t1, t2 = Team(), Team()
t1.add("x")
print(t2.members)                       # ['x'] — shared by every Team

Rule: class attributes for constants and genuinely shared state; per-instance state is created in __init__.

3. Methods and binding

When attribute lookup finds a function on the class, it does not return the plain function. It returns a bound method, a small object that remembers both the function and the instance:

print(type(a.deposit).__name__)              # method
print(a.deposit.__self__ is a)                # True — the remembered instance
print(a.deposit.__func__ is Account.deposit)  # True — the plain function
print(a.deposit(50), Account.deposit(a, 50))  # 150 200

Calling the bound method calls the function with the instance inserted as the first argument. The mechanism that produces bound methods is the descriptor protocol (section 9): functions define a __get__ method, and attribute lookup calls it. @classmethod and @staticmethod (py4) are alternative descriptors that bind the class, or nothing, instead of the instance.

4. Inheritance and overriding

A class can inherit from another: class Dog(Animal). Lookups that fail on Dog continue to Animal. A subclass overrides a method by defining one with the same name, and because lookup always starts from the instance's actual class, code in the base class that calls self.speak() gets the subclass's version:

class Animal:
    def __init__(self, name): self.name = name
    def speak(self): return f"{self.name} makes a sound"
    def describe(self): return f"{type(self).__name__}: {self.speak()}"

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)          # let Animal set up its part
        self.breed = breed
    def speak(self): return f"{self.name} barks"

d = Dog("rex", "lab")
print(d.describe())                     # Dog: rex barks  — Animal's method called Dog's speak
print(isinstance(d, Animal))            # True

super().__init__(name) runs the base class's initialiser so the base can set up its own attributes. Forgetting it is a common bug: the subclass instance then lacks everything the base class's __init__ would have set.

5. Multiple inheritance, the MRO and super()

Python allows several base classes. That raises the question of where to look, and in what order, when a name is not on the class itself. The answer is the method resolution order (MRO), a single list of classes stored as Class.__mro__. For single inheritance it is just the chain of parents. For multiple inheritance Python computes it with C3 linearisation, which guarantees two rules: a class always comes before its own bases, and the left-to-right order of bases in each class statement is preserved.

Consider the "diamond":

class Base:
    def __init__(self, **kw): print("Base"); super().__init__(**kw)
class A(Base):
    def __init__(self, **kw): print("A"); super().__init__(**kw)
class B(Base):
    def __init__(self, **kw): print("B"); super().__init__(**kw)
class C(A, B):
    def __init__(self, **kw): print("C"); super().__init__(**kw)

C()                                   # prints C, A, B, Base
print([k.__name__ for k in C.__mro__])  # ['C', 'A', 'B', 'Base', 'object']

This is the key to understanding super(): it does not mean "my parent". It means "the next class after this one in the MRO of the object I am running on". For a plain A(), super() inside A reaches Base; for a C(), the same line reaches B. That is what makes cooperative multiple inheritance work: if every class calls super() and forwards **kwargs, each class in the hierarchy runs exactly once, in MRO order, even in a diamond.

Break the cooperation and the chain breaks. If A calls Base.__init__(self) directly, C() prints C, A, Base: B.__init__ is skipped, silently. And some hierarchies have no valid order at all:

class X: pass
class Y(X): pass
class Z(X, Y): pass
# TypeError: Cannot create a consistent method resolution order (MRO) for bases X, Y

Z asks for X before Y, but Y must come before its own base X. C3 cannot satisfy both, so Python refuses to create the class.

6. Special methods: making objects feel built-in

Here is a small value class that uses the most important special methods, followed by what each one enables:

class Money:
    def __init__(self, cents, cur="USD"):
        self.cents, self.cur = cents, cur
    def __repr__(self): return f"Money({self.cents!r}, {self.cur!r})"
    def __str__(self):  return f"{self.cents / 100:.2f} {self.cur}"
    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return (self.cents, self.cur) == (other.cents, other.cur)
    def __hash__(self): return hash((self.cents, self.cur))
    def __add__(self, other):
        if isinstance(other, Money) and other.cur == self.cur:
            return Money(self.cents + other.cents, self.cur)
        if other == 0:
            return self
        return NotImplemented
    __radd__ = __add__
    def __bool__(self): return self.cents != 0

Display. __repr__ is the unambiguous, developer-facing form, used by the REPL, by containers ([m] prints [Money(250, 'USD')]) and by {m!r}. __str__ is the friendly form used by print and f"{m}" (2.50 USD). If you write only one, write __repr__; str() falls back to it.

Equality and hashing. __eq__ compares values. Defining it without __hash__ would make instances unhashable (py1), so we hash the same tuple we compare. Returning NotImplemented for unknown types means "I don't know how to compare with that": Python then tries the other operand's method and finally falls back to identity, which is why Money(1) == 1 is simply False instead of an error.

Operators. a + b first tries a.__add__(b). If that returns NotImplemented, Python tries the reflected method on the right operand, b.__radd__(a). Only if both decline does it raise TypeError: unsupported operand type(s) for +: 'Money' and 'str'. Supporting 0 in __radd__ makes sum() work, because sum starts from 0 + first: sum([Money(100), Money(50)]) gives 1.50 USD.

Truthiness. if m: calls __bool__; if absent, Python uses __len__ (zero means false); if both are absent, every object is true. bool(Money(0)) is False.

Containers. Implementing __len__ and __getitem__ is enough to get len(), indexing, slicing (if your __getitem__ passes slices through), iteration and in:

class Deck:
    def __init__(self): self.cards = list(range(52))
    def __len__(self): return len(self.cards)
    def __getitem__(self, i): return self.cards[i]

dk = Deck()
len(dk), dk[0], dk[-1], dk[:3], 51 in dk     # (52, 0, 51, [0, 1, 2], True)

Other families you will meet: __call__ makes instances callable (py4), __enter__/__exit__ make context managers (py7), __iter__/__next__ make iterators (py5), __lt__ and friends define ordering (or use functools.total_ordering), and __getattr__ is called only when normal lookup fails, which is handy for proxies and wrappers.

7. Naming conventions and name mangling

Python has no private keyword. A single leading underscore, self._internal, is a convention meaning "implementation detail, do not use from outside". A double leading underscore, self.__hidden, triggers name mangling: inside the class, the compiler rewrites it to self._Secret__hidden. Its purpose is to prevent a subclass from accidentally overwriting a base class's attribute of the same name, not to hide it:

class Secret:
    def __init__(self):
        self._internal = 1
        self.__hidden = 2

s = Secret()
print(s.__dict__)        # {'_internal': 1, '_Secret__hidden': 2}
s.__hidden               # AttributeError: 'Secret' object has no attribute '__hidden'

8. Properties: attributes with logic

In Java you write getters and setters up front "in case" you later need logic. In Python you expose a plain attribute and switch to a property only when logic is needed, without changing any caller, because the access syntax stays obj.attr:

class Temp:
    def __init__(self, c):
        self.celsius = c                 # goes through the setter below
    @property
    def celsius(self):
        return self._c
    @celsius.setter
    def celsius(self, v):
        if v < -273.15:
            raise ValueError("below absolute zero")
        self._c = v
    @property
    def fahrenheit(self):                # computed, read-only
        return self._c * 9 / 5 + 32

t = Temp(25)
t.fahrenheit          # 77.0
t.celsius = -300      # ValueError: below absolute zero

Notice that even the assignment in __init__ is validated, because it goes through the property. The actual value is stored under a different name, _c, to avoid the property calling itself forever.

9. Descriptors: the mechanism under methods, properties and ORMs

How does t.celsius end up calling a function? Through the descriptor protocol. A descriptor is any object stored as a class attribute that defines __get__, and optionally __set__ or __delete__. When attribute lookup finds such an object on the class, it calls those methods instead of returning the object itself. property is a descriptor; so is every function (its __get__ produces the bound method); so are classmethod and staticmethod.

Writing one yourself makes the idea concrete. This reusable validator can be attached to any number of attributes:

class Positive:
    def __set_name__(self, owner, name):     # called when the class is created (3.6+)
        self.name = "_" + name
    def __get__(self, obj, objtype=None):
        if obj is None:                      # accessed on the class itself
            return self
        return getattr(obj, self.name)
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name[1:]} must be positive, got {value}")
        setattr(obj, self.name, value)

class Order:
    qty = Positive()
    price = Positive()
    def __init__(self, qty, price):
        self.qty = qty                       # calls Positive.__set__
        self.price = price

o = Order(2, 9.5)
print(o.qty, o.__dict__)                     # 2 {'_qty': 2, '_price': 9.5}
Order(0, 1)                                  # ValueError: qty must be positive, got 0

Descriptors come in two kinds, and the difference decides who wins a name clash. A data descriptor defines __set__ (or __delete__) and beats the instance's own dictionary. A non-data descriptor defines only __get__ and loses to an instance attribute of the same name. Put a value into an instance's __dict__ under the name of each kind and you can watch it: the non-data descriptor returns "from instance", the property returns "from property". That gives the full attribute lookup order:

ORMs (object-relational mappers: libraries that map database rows to Python objects) are the famous real-world use: a SQLAlchemy or Django model's columns are descriptors whose __get__ returns the row's value on an instance and a SQL expression on the class, and whose __set__ records the change for the next flush.

10. Dataclasses: classes from field declarations

Most classes that mainly hold data need the same boilerplate: an __init__ that stores each argument, a __repr__, and an __eq__. @dataclass reads the class's annotated fields and generates them:

from dataclasses import dataclass, field

@dataclass
class Point:
    x: float
    y: float = 0.0
    tags: list = field(default_factory=list)   # fresh list per instance

p = Point(1.5)
print(p)                     # Point(x=1.5, y=0.0, tags=[])
print(p == Point(1.5))       # True
print(Point.__hash__)        # None — eq without frozen means unhashable (py1)

Dataclasses protect you from the mutable-default trap: writing items: list = [] raises ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory. The main options:

  • frozen=True forbids assignment after creation (FrozenInstanceError: cannot assign to field 'x') and generates __hash__, so instances can be dict keys. dataclasses.replace(obj, x=9) makes a modified copy.
  • order=True generates <, <= and friends comparing fields as a tuple: sorted([Ver(1, 2), Ver(0, 9), Ver(1, 0)]) gives [Ver(0, 9), Ver(1, 0), Ver(1, 2)].
  • slots=True (3.10+) generates __slots__ (section 11).
  • kw_only=True (3.10+) makes fields keyword-only, which also fixes the classic inheritance error: a base with a defaulted field and a subclass adding a required one raises TypeError: non-default argument 'b' follows default argument; with kw_only=True on the subclass, Child2(b=1) works.
  • __post_init__ runs after the generated __init__, the place for validation (if self.age < 0: raise ValueError) and derived fields.

Dataclasses do not validate types: Point("oops") is accepted. For data arriving from outside the program — HTTP bodies, config files, model outputs — use Pydantic, which parses and validates at runtime. Python 3.13 added copy.replace(), a general version of dataclasses.replace that works on dataclasses, named tuples and any class implementing __replace__.

11. __slots__: fixed attribute storage

By default each instance can hold arbitrary attributes, which requires dictionary-like storage. Declaring __slots__ = ("x", "y") tells Python the instance will only ever have those attributes, so it allocates fixed storage for them — implemented as data descriptors on the class — and no __dict__. Unknown attributes then raise AttributeError: 'PS' object has no attribute 'z', which also catches typos.

How much does it save? Measured with tracemalloc on 3.12, creating 100,000 two-attribute objects cost about 120 bytes per object without slots and 88 bytes with slots, including the integers stored in them. That is a real but modest saving, because since Python 3.11 CPython already stores instance attributes inline and builds a dict only if you ask for __dict__ (on older versions the gap was much larger). Slots matter when you hold millions of small objects; for a few thousand, they are not worth the restrictions.

12. Interfaces: ABCs and Protocols

An abstract base class declares methods subclasses must implement. Instantiating a class that has not implemented them fails immediately:

import abc

class Shape(abc.ABC):
    @abc.abstractmethod
    def area(self): ...

Shape()
# TypeError: Can't instantiate abstract class Shape without an implementation for abstract method 'area'

A Protocol (typing.Protocol, 3.8+) describes the same requirement structurally: any class with a matching area method satisfies it, with no inheritance. Type checkers (py10) verify this statically, and @runtime_checkable allows a shallow isinstance check that only tests the methods exist. A Circle class with an area method is an instance of a runtime-checkable HasArea Protocol but not of the Shape ABC, which it never inherited. Choose a Protocol for "accept anything that can do X", and an ABC when you own a family of classes and want to share code in the base.

13. __init_subclass__ and metaclasses

Sometimes a base class needs to act whenever a subclass is defined — to register plugins, validate that required attributes exist, or add behaviour. __init_subclass__ (3.6+) is a hook on the base class that Python calls for each new subclass, and it can accept keyword arguments from the class statement:

class Plugin:
    registry = {}
    def __init_subclass__(cls, name, **kw):
        super().__init_subclass__(**kw)
        Plugin.registry[name] = cls

class CSV(Plugin, name="csv"): pass
print(Plugin.registry)       # {'csv': <class '__main__.CSV'>}

Underneath, every class is itself an object, an instance of its metaclass. The default metaclass is type: type(Account) is <class 'type'>, and type("Dyn", (), {"hello": lambda self: "hi"}) creates a class at runtime. A custom metaclass (a subclass of type) controls how classes are created. It is the most powerful and most intrusive tool here, and modern Python rarely needs it: class decorators (py4), __init_subclass__ and descriptors with __set_name__ cover almost every use. Saying so, with an example of when a metaclass is still needed (Enum, explained in the deep dive), is the answer interviewers look for.

The real attribute lookup algorithm

object.__getattribute__(obj, name) does the following. It searches type(obj).__mro__ for name in each class's __dict__, remembering the first hit. If that hit has __set__ or __delete__ on its type, it is a data descriptor: return hit.__get__(obj, type(obj)). Otherwise, look in the instance's own storage; if found, return it. Otherwise, if the hit has __get__, return hit.__get__(obj, type(obj)); if it is a plain value, return it. If there was no hit, raise AttributeError — at which point Python calls type(obj).__getattr__(obj, name) if it exists. Note that special methods used by syntax (len, +, with) are looked up on the type, bypassing the instance entirely, so assigning obj.__len__ = ... on an instance has no effect on len(obj).

How C3 merges

For class C(B1, B2), L[C] = [C] + merge(L[B1], L[B2], [B1, B2]). The merge repeatedly picks the first element among the heads of the lists that does not appear in the tail (anything after the head) of any list, appends it to the result and removes it from every list. Worked for the diamond: merge([A, Base, object], [B, Base, object], [A, B]). A is not in any tail, take it. Next heads are Base, B, B; Base appears in the tail of [B, Base, object], so skip it; B qualifies. Then Base, then object. Result: C, A, B, Base, object. If no head ever qualifies, class creation fails, as with Z(X, Y). The algorithm guarantees monotonicity: a class's MRO is consistent with the MROs of all its bases, so subclassing never reorders an existing hierarchy.

Designing cooperative hierarchies

For super() chains to be safe, every class in the chain must call super(), use keyword arguments and forward the ones it does not consume (def __init__(self, *, retries=3, **kw): super().__init__(**kw)), and something at the root must absorb the end of the chain — object.__init__ accepts no extra arguments, so any leftovers there raise TypeError. Mixins should be small, stateless where possible, and listed before the main base class so their methods come earlier in the MRO. When classes you do not control are involved, composition (holding an object rather than inheriting from it) is usually safer than joining their super() chain; the SWE track's swe2 covers composition over inheritance.

__slots__ details

Each name in __slots__ becomes a member descriptor on the class, a data descriptor that reads and writes a fixed offset in the instance. Slots are per class: a subclass that does not declare __slots__ gets a __dict__ again, losing most of the benefit, so every class in a hierarchy must declare them (an empty tuple for classes adding nothing). Instances without __dict__ cannot be weakly referenced unless "__weakref__" is listed. Class attributes cannot share a name with a slot, which is why dataclasses with slots=True create a new class rather than modifying the original, and why default values interact awkwardly with hand-written slots. Pickling works through __getstate__, which since 3.11 has a default implementation for slotted objects.

Instance layout since 3.11

Python 3.11 changed how ordinary instances store attributes: the values are stored in an array inline with the object and share the class's keys table (py2's key-sharing dict), and a real __dict__ is materialised only if code accesses it or the attribute pattern diverges. sys.getsizeof on such an instance reports only 48 bytes on 3.12 because it does not include the values, and asking for obj.__dict__ materialises a real dict (in the lab, about 60 extra traced bytes per object). Practical consequences: set all attributes in __init__ in a consistent order, avoid adding attributes later, and do not touch __dict__ in hot code if memory matters.

Dataclass generation and dataclass_transform

@dataclass builds the source code of __init__ and friends as strings and compiles them with exec at class-creation time, which is why dataclass creation is slightly slow but instance creation is as fast as a hand-written class. Libraries that generate classes the same way — Pydantic, attrs, SQLAlchemy's mapped dataclasses — mark their decorators or base classes with typing.dataclass_transform (PEP 681, 3.11) so type checkers understand the generated __init__. In Python 3.14, annotations are evaluated lazily by default (PEP 649/749), which lets dataclass fields refer to classes defined later in the module without quoting them; py10 and py15 cover the change.

When a metaclass is genuinely needed: Enum

enum.Enum shows what only a metaclass can do. Its metaclass, EnumType, supplies a special namespace for the class body (via __prepare__) that records member definitions in order and rejects duplicates, converts each class attribute into an instance of the class itself, and defines __iter__, __len__ and __contains__ on the metaclass so that for c in Color and len(Color) work on the class. None of that is possible from a decorator or __init_subclass__, which run after the class body has already been executed into an ordinary dict and cannot give the class object itself new behaviour.

typing.override (3.12)

PEP 698 added @typing.override, a decorator that marks a method as intentionally overriding one in a base class. At runtime it only sets an attribute, but type checkers report an error if no base class has a method of that name — catching the bug where a base method is renamed and the subclass's "override" silently becomes an unused new method.

Shared mutable class state

Class-level lists, dicts and sets that are mutated through self are a recurring production bug, especially in web services where one class instance per request is created and all of them share the class attribute. Symptoms are the same as for mutable defaults (py1): data leaking across requests or tenants and memory that only grows. Ruff's RUF012 flags mutable class attributes that are not annotated as ClassVar, which forces the author to state whether sharing is intended.

Broken super() chains in mixin-heavy code

Frameworks such as Django's class-based views and many test-case hierarchies rely on mixins. A single mixin that calls a base class directly, or that swallows **kwargs, silently prevents later classes' setup from running; the failure appears far away, as a missing attribute or an unconfigured lock. When debugging, print type(obj).__mro__ and check each class's method calls super(). Many teams set a rule: at most one "real" base class plus stateless mixins, or prefer composition.

Objects in hot paths and memory budgets

Services that hold millions of small objects in memory — a feature store cache, a graph of entities, parsed log records — can spend most of their RAM on per-object overhead. The progression of fixes is: @dataclass(slots=True) or __slots__ to trim each object; tuples or NamedTuples for read-only records; and for truly large data, columnar storage (NumPy, Arrow, pandas, Polars) where there is no per-record object at all (py2). Measure with tracemalloc or memray on realistic data before and after.

PyTorch modules and attribute interception

AI engineers meet heavy use of this lesson's machinery in torch.nn.Module. Its __setattr__ intercepts assignments such as self.linear = nn.Linear(...) and records sub-modules and parameters in internal dictionaries, and its __getattr__ finds them again. Two classic bugs follow directly: forgetting super().__init__() in a module's __init__ raises AttributeError: cannot assign module before Module.__init__() call, because the internal dictionaries do not exist yet; and storing sub-modules in a plain Python list instead of nn.ModuleList hides their parameters from the optimiser and from .to(device), because __setattr__ only recognises modules assigned directly.

Equality and hashing bugs in caches and sets

Value classes with __eq__ but a hash over mutable fields, or dataclasses that are neither frozen nor hashed deliberately, cause lookups that fail intermittently (py1). In production this looks like a cache whose hit rate decays over time, or deduplication that lets duplicates through. Default to @dataclass(frozen=True) for anything used as a key, and keep identity (a database id) separate from mutable state. A cheap safety net is a unit test that puts two equal instances into a set and asserts its length is one.

Validation at the edges

Dataclasses and plain classes trust their inputs. Bugs appear when a string arrives where an int was expected — from JSON, environment variables or an LLM's structured output — and fails much later in arithmetic. The production pattern is to validate at the boundary with Pydantic models (or attrs validators), convert to internal types once, and let internal code use simple dataclasses. The AI-engineering track's ae4 covers validating structured model output specifically.

Trace the MRO 
class Base:
    def __init__(self, **kw):
        print("Base"); super().__init__(**kw)
class A(Base):
    def __init__(self, **kw):
        print("A"); super().__init__(**kw)
class B(Base):
    def __init__(self, **kw):
        print("B"); super().__init__(**kw)
class C(A, B):
    def __init__(self, **kw):
        print("C"); super().__init__(**kw)

C()
print([k.__name__ for k in C.__mro__])

What is printed? What changes if A.__init__ calls Base.__init__(self) directly instead of super()?

Answer

It prints C, A, B, Base, then the MRO ['C', 'A', 'B', 'Base', 'object']. C3 linearisation puts each class before its bases and keeps A before B as written in class C(A, B). Inside A, super() means the next class in the MRO of the actual object, a C, which is B, not Base. Each initialiser runs exactly once even though the hierarchy is a diamond.

If A calls Base.__init__(self) directly, the chain skips B: the output is C, A, Base, and B.__init__ never runs, silently leaving B's state uninitialised. That is why cooperative multiple inheritance requires every class in the hierarchy to use super() and to accept and forward **kwargs. Base forwarding to object.__init__ is fine only if no keyword arguments are left by then, because object.__init__ accepts none.
