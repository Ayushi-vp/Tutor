A nightly job loads configuration, opens a database connection, processes a batch of records, and closes the connection. One night a record contains a malformed date. The parsing function raises, the exception skips the line that closes the connection, and the connection is never returned to the pool. The job's retry logic runs it again, the same record fails again, another connection leaks, and forty minutes later the database refuses all new connections — taking down the customer-facing API that shares it. The root cause was one bad record; the outage was caused by cleanup that only ran on the happy path.

In another service, a well-meaning developer wrapped a function in try: ... except: return None to "make it robust". The function now returns None for a network timeout, a typo in a variable name, a full disk and a user pressing Ctrl-C, and every caller treats None as "no data". Months of silently missing rows follow before anyone notices.

These are the two halves of error handling. The first is guaranteed cleanup: resources — files, connections, locks, temporary state — must be released however a block of code exits. Python's answer is the with statement and context managers. The second is handling failures honestly: catching the errors you can do something about, letting the rest propagate with enough context to debug, and never turning an error into a plausible-looking value. Python's answer is its exception system: a class hierarchy, try/except/else/finally, chaining, and since 3.11, exception groups for concurrent failures.

This lesson starts with what happens when an exception is raised — how it travels up the call stack and how to read the traceback it leaves. It covers matching exceptions by class, the hierarchy (and why a bare except: is dangerous), the full try statement, raising and chaining well, and the EAFP style. Then it turns to cleanup: the with statement, writing context managers as classes and as generators, and the contextlib toolbox. It ends with exception groups and the error-handling changes in Python 3.14. Code was run on CPython 3.12.10; version-specific behaviour is labelled.

Exceptions: an alarm that travels upward

Think of a company where each manager delegates work to someone below them. When a junior employee hits a problem they cannot deal with, they do not quietly return a blank report; they raise the alarm and pass it to their manager. If that manager knows how to handle this kind of problem, they deal with it; if not, they pass it up again, and so on. If it reaches the chief executive and nobody handled it, the company stops, and the incident report lists everyone the alarm passed through.

That is exactly how Python exceptions work. Functions call functions, forming a call stack. When something goes wrong, code raises an exception object. Python abandons the current function and hands the exception to its caller; if the caller has a matching except clause, the exception is handled there; otherwise the caller is abandoned too, and so on up the stack. This is called propagation. If nothing handles it, the program ends and prints a traceback: the incident report.

def parse_port(s):
    return int(s)                        # raises ValueError for "80a"
def load_config(d):
    return {"port": parse_port(d["port"])}
def main():
    return load_config({"port": "80a"})

try:
    main()
except ValueError as e:
    print("bad config:", e)              # bad config: invalid literal for int() with base 10: '80a'

Cleanup that cannot be skipped

Propagation skips the rest of every abandoned function — including any cleanup lines at the end of them. That is exactly the connection-leak story. Python gives two ways to run code no matter how a block exits: a finally clause, and the with statement, which packages "set up, then always tear down" into a reusable object called a context manager:

with open("config.txt", encoding="utf-8") as f:   # set up: open the file
    data = f.read()                              # use it; may raise
# tear down: the file is closed here, whether or not read() raised

Files, locks, database transactions, network connections and temporary settings are all managed this way.

Handle what you understand; let the rest travel

The guiding principle for everything that follows: catch an exception only where you can do something meaningful about it — retry, fall back, translate it into a clearer error, or report it to a user. Everywhere else, let it propagate, because the traceback it produces is the most useful debugging information you will get. Swallowing an error to "keep going" usually converts a loud, easy bug into a silent, expensive one.

Where the office analogy breaks: in an office the alarm is a message; in Python it is an object with a type, and handlers are chosen by type, including parent types. except LookupError catches both KeyError and IndexError because they are subclasses of it. That makes the class hierarchy of exceptions, covered next, part of how your error handling behaves.

1. Reading a traceback

An unhandled exception prints something like this (paths shortened):

Traceback (most recent call last):
  File "app.py", line 7, in <module>
    main()
  File "app.py", line 5, in main
    return load_config({"port": "80a"})
  File "app.py", line 3, in load_config
    return {"port": parse_port(d["port"])}
  File "app.py", line 1, in parse_port
    return int(s)
           ^^^^^^
ValueError: invalid literal for int() with base 10: '80a'

Read it in two directions. Start at the bottom: the last line is the exception type and message, the actual problem. The lines above it are frames, printed from the outermost call ("most recent call last" means the innermost frame is printed last). Read upward from the bottom to find the first frame in your own code — library frames usually are not where the bug is. Since 3.11, carets (^^^^) underline the exact expression that failed. In code, the same information is available from e.__traceback__; traceback.extract_tb(e.__traceback__) gave frame names ['<module>', 'main', 'load_config', 'parse_port'] in the test run.

2. Catching: try and except

A try block runs code; if an exception is raised inside it (at any depth of calls), Python checks each except clause in order and runs the first whose class matches. Matching uses isinstance, so a clause catches the named class and all its subclasses:

d = {}
try:
    d["missing"]
except LookupError as e:          # KeyError is a subclass of LookupError
    print(repr(e))                # KeyError('missing')

Consequences of class-based matching: order clauses from most specific to most general, because the first match wins and a general clause placed first would shadow the specific ones. Several classes can share a clause with a tuple, except (TimeoutError, ConnectionError):; Python 3.14 (PEP 758) also allows the parentheses to be omitted when there is no as. The name after as is bound only inside the clause and deleted at its end, to avoid keeping the traceback — and every local variable it references — alive.

3. The exception hierarchy

All exceptions are classes arranged in a tree. Knowing its top levels explains which catches are safe:

KeyboardInterrupt (Ctrl-C), SystemExit (raised by sys.exit()) and GeneratorExit (used to close generators, py5) inherit directly from BaseException, not from Exception, precisely so that except Exception does not intercept them. A bare except: catches BaseException and therefore swallows them. Useful families: LookupError for failed indexing; OSError for operating-system failures, with subclasses such as FileNotFoundError, PermissionError, ConnectionError and TimeoutError (which socket.timeout has been an alias of since 3.10); ValueError for "right type, wrong value" (int("80a")) versus TypeError for "wrong type" (len(5)).

4. else and finally: the full try statement

A try can have four parts. Their order of execution for the two main cases, as recorded by a small tracing function:

try:
    ...                  # the protected code
except ValueError:
    ...                  # runs if ValueError was raised
else:
    ...                  # runs only if nothing was raised
finally:
    ...                  # always runs, last

# no exception:   ['try', 'else', 'finally']
# ValueError:     ['try', 'except', 'finally']

Why have else at all? Code in else runs only on success, but is not protected by the except clauses. That keeps the protected region small: if you put the success-path code inside try, an unrelated ValueError from it would be caught by a handler meant for the parsing step.

finally runs on every exit path — including return. In def f(): try: return "try" finally: print(...), the print runs before the value is actually returned. The dangerous case is a return inside finally:

def g():
    try:
        raise ValueError("lost")
    finally:
        return "finally wins"

print(g())    # finally wins — the ValueError vanished without a trace

The return replaced the in-flight exception. Python 3.14 (PEP 765) makes the compiler emit a SyntaxWarning when return, break or continue leaves a finally block. Keep finally for cleanup only.

5. Raising, custom exceptions and chaining

raise SomeError("message") raises an exception; a bare raise inside an except block re-raises the one being handled, keeping its original traceback. For your own code, define a small hierarchy: one base class per library or domain, and subclasses for cases a caller might handle differently. Exceptions are ordinary classes, so they can carry structured data:

class PaymentError(Exception):
    def __init__(self, msg, *, order_id):
        super().__init__(msg)
        self.order_id = order_id

class CardDeclined(PaymentError):
    pass

try:
    raise CardDeclined("insufficient funds", order_id=17)
except PaymentError as e:                 # catches the whole family
    print(type(e).__name__, e, e.order_id)   # CardDeclined insufficient funds 17

When you catch a low-level exception and raise a higher-level one, chain them so the original is not lost. There are three variants, and the attributes they set are visible in code:

  • raise RuntimeError("config broken") from e sets __cause__ to the original. The traceback shows both, joined by "The above exception was the direct cause of the following exception". Use this when deliberately translating an error.
  • Raising inside an except block without from still records the original, in __context__, and the traceback says "During handling of the above exception, another exception occurred" — the wording for an accident in a handler.
  • raise RuntimeError("clean") from None sets __suppress_context__ and hides the original. Use it only when the original is pure noise.

Since 3.11, e.add_note("while parsing line 42 of data.csv") attaches extra context strings, printed under the traceback, without changing the exception's type. It is ideal in loops where the caller should still catch ValueError but the log should say which record failed.

6. EAFP versus LBYL

There are two styles for code that might fail. LBYL, "look before you leap", checks first: if os.path.exists(p): open(p). EAFP, "easier to ask forgiveness than permission", just tries and handles failure: try: open(p) except FileNotFoundError: .... Python generally favours EAFP for two reasons. It avoids a race: the file can be deleted between the check and the open, so LBYL code needs the try anyway. And it avoids double work, because the operation repeats the check internally.

LBYL still wins when failure is the common case, because raising is expensive (measured in section 11: a KeyError miss cost about 0.42 µs versus 0.06 µs for dict.get). "Is this key present?" in a hot loop should use in or .get(); "open this config file that should exist" should use EAFP.

7. The with statement and the context manager protocol

A context manager is any object with two methods. with cm as x: does the following:

  1. Evaluate cm and call cm.__enter__(). Bind its return value to x (it is often cm itself, but a file's __enter__ returns the file, and a lock's returns True).
  2. Run the block.
  3. However the block exits, call cm.__exit__(exc_type, exc_value, traceback). On a normal exit all three are None; if an exception escaped the block, they describe it.
  4. If __exit__ returns a true value, the exception is suppressed and execution continues after the with. Otherwise it keeps propagating.

A class-based context manager that times a block shows every step:

import time

class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self
    def __exit__(self, exc_type, exc, tb):
        self.elapsed = time.perf_counter() - self.start
        print("exit", exc_type.__name__ if exc_type else None)
        return False                     # never suppress

with Timer() as t:
    pass                                 # exit None

with Timer() as t:
    raise KeyError("k")                  # exit KeyError, then the KeyError propagates

Suppression is rarely what you want. A context manager whose __exit__ returns True unconditionally turns with Swallow(): 1/0 into silence. When you really do mean "ignore this specific error", say so explicitly with contextlib.suppress (section 9).

The with statement is really a packaged try/finally (PEP 343 gives the exact expansion). What makes it better than writing try/finally by hand is reuse: the setup and teardown live in one object, tested once, and every call site gets it right automatically.

8. Writing context managers with @contextmanager

Writing a class with two methods is fine, but most context managers are clearer as a generator (py5). @contextlib.contextmanager turns a generator function with exactly one yield into a context manager: the code before yield is __enter__, the yielded value is what as binds, and the code after it is __exit__:

from contextlib import contextmanager

@contextmanager
def tag(name):
    print(f"<{name}>")
    try:
        yield name.upper()
    finally:
        print(f"</{name}>")

with tag("b") as v:
    print("inside", v)
# <b> / inside B / </b>

with tag("i"):
    raise ValueError("boom")
# <i> / </i>, then the ValueError propagates

How does the exception reach the generator? When the block raises, the context manager's __exit__ throws the exception into the generator at the paused yield (py5's gen.throw()). So the try/finally around yield sees it. Without that try/finally, the teardown line would be skipped when the block raises — the most common bug in hand-written context managers. To suppress, catch the exception around the yield and do not re-raise; to let it through, re-raise or simply do not catch it.

A realistic example is a database transaction that commits on success and rolls back on any error:

@contextmanager
def transaction(conn):
    tx = conn.begin()
    try:
        yield tx
    except BaseException:
        tx.rollback()
        raise                          # never swallow
    else:
        tx.commit()

Catching BaseException here is one of the few legitimate uses: we are not handling the error, only cleaning up before re-raising it, and we want to roll back even on KeyboardInterrupt.

9. The contextlib toolbox

  • contextlib.suppress(FileNotFoundError) ignores exactly the listed exceptions in its block: with suppress(FileNotFoundError): os.remove(path) means "delete it if it exists".
  • contextlib.ExitStack() manages a number of context managers known only at runtime. stack.enter_context(open(p)) for each file, stack.callback(fn, *args) for arbitrary cleanup; on exit everything is closed in reverse order. In the test run, three files were open inside the block and all closed after it, and the callback ran.
  • contextlib.closing(obj) calls obj.close() on exit, for objects with a close method but no context manager support (and for generators, py5).
  • contextlib.nullcontext() is a do-nothing context manager, useful when a resource is optional: with (lock if threaded else nullcontext()):.
  • contextlib.redirect_stdout(buf) temporarily sends print output to a buffer; contextlib.chdir(path) (3.11+) temporarily changes the working directory.
  • Async versions exist for asyncio code: async with, __aenter__/__aexit__, @asynccontextmanager and AsyncExitStack (py9).

10. Exception groups and except* (3.11+)

Everything so far assumes one exception at a time. Concurrent code breaks that assumption: if ten tasks run at once and three fail, which error should the caller see? Before 3.11 the answer was "usually the first", and the others were lost. PEP 654 added ExceptionGroup, an exception that contains a list of exceptions, and except*, which handles the members matching a type and lets the rest continue to other clauses:

try:
    raise ExceptionGroup("batch failed",
                         [ValueError("a"), TimeoutError("b"), ValueError("c")])
except* ValueError as eg:
    print("values:", [str(x) for x in eg.exceptions])      # values: ['a', 'c']
except* TimeoutError as eg:
    print("timeouts:", [str(x) for x in eg.exceptions])    # timeouts: ['b']

Both clauses ran, each seeing a sub-group of its matching exceptions. You will mostly meet exception groups from asyncio.TaskGroup (3.11+): if child tasks fail, the group cancels the remaining tasks and raises an ExceptionGroup of the failures. With four jobs where the odd-numbered ones raise, the test run caught ['job 1', 'job 3']. py9 covers TaskGroup in context.

11. What exceptions cost

Since 3.11, CPython uses "zero-cost" exceptions: entering a try block executes no extra instructions, because the compiler records the handler locations in a table that is only consulted when something is raised. Raising is not free: Python creates the exception object, records traceback entries as it unwinds, and searches for handlers. Measured on 3.12 for one million iterations: a try that did not raise, about 30 ms; raise-and-catch, about 375 ms; a missing-key lookup via KeyError, about 419 ms versus 63 ms for dict.get. The practical rule: exceptions for exceptional situations, cheap checks for frequent, expected outcomes.

12. Exceptions or return values?

Not every failure should be an exception. A useful rule: raise when the caller asked for something that could not be done and would otherwise have to check for a special value; return a value when "not found" or "no result" is an ordinary, expected outcome that most callers handle on the spot. The standard library follows this: dict[key] raises KeyError but dict.get(key) returns None; str.index raises but str.find returns -1; re.match returns None when nothing matches, because a non-match is a normal answer to "does this match?". When you do return an "absent" value, make it explicit in the type (User | None, py10) so the checker forces callers to handle it. What to avoid is the ambiguous middle: returning 0, "" or False for errors that are indistinguishable from legitimate results, which is exactly the bug in this lesson's drill. For batch operations where some items fail, a common design is to collect per-item errors (or raise an ExceptionGroup at the end) rather than stopping at the first failure or silently dropping failed items.

How with expands

PEP 343 specifies with EXPR as VAR: BLOCK as roughly: evaluate EXPR to mgr; look up type(mgr).__exit__ and __enter__ on the type, before calling anything; value = enter(mgr); then try: VAR = value; BLOCK, except: if not exit(mgr, *sys.exc_info()): raise, else: exit(mgr, None, None, None). Two details matter. Looking up the methods on the type means patching __exit__ on an instance does nothing. And because __enter__ runs outside the try, a failure in __enter__ skips __exit__, so a context manager acquiring several resources must clean up the ones it already acquired itself — ExitStack's pop_all() idiom exists for exactly this.

Exceptions inside __exit__ and in cleanup

If __exit__ or a finally block raises while another exception is propagating, the new exception replaces it, with the original attached as __context__. The traceback then leads with a secondary failure ("connection already closed") rather than the root cause. Cleanup code should therefore be defensive: guard against half-initialised state (the classic UnboundLocalError when f.close() runs in finally after open failed), and catch-and-log errors from secondary cleanup steps rather than letting them mask the primary error. ExitStack does this correctly by chaining exceptions from multiple exit callbacks.

Tracebacks keep frames alive

An exception's __traceback__ references every frame it passed through, and each frame references its local variables. Storing caught exceptions (in a list of errors, in an attribute, in a closure) therefore keeps potentially large objects alive: a request body, a DataFrame, a model batch. Python mitigates the most common case by implicitly deleting the as name at the end of an except block, which is why e is undefined after the block. If you must keep errors, keep repr(e) or a formatted traceback string, or call traceback.clear_frames(tb). sys.exception() (3.11+) returns the exception currently being handled and is the modern replacement for sys.exc_info()[1].

Zero-cost exceptions in detail

Before 3.11, entering a try pushed a block onto a per-frame stack with a SETUP_FINALLY instruction and popped it on exit, a small cost on every pass. 3.11 removed those instructions: the compiler emits an exception table mapping ranges of bytecode offsets to handler offsets and stack depths, and the interpreter consults it only when unwinding. dis.dis on 3.11+ shows the table at the end of a function's disassembly. This is why wrapping a hot loop's body in try is now effectively free, while raising inside it on most iterations is still costly.

ExceptionGroup semantics

An ExceptionGroup can nest other groups, forming a tree, and carries its own message and traceback. except* T calls eg.split(T), which returns the sub-tree of matching leaves (preserving structure) and the remainder; each clause sees only its match, and whatever remains after all clauses is re-raised as a group. Rules follow from that design: a single try cannot mix except and except*; break, continue and return are not allowed inside except* clauses; and a naked exception raised in the try body is wrapped in a group for matching. BaseExceptionGroup is the variant that can hold KeyboardInterrupt and friends.

Python 3.14 changes to know

Three 3.14 changes touch this lesson. PEP 765 makes return, break and continue that leave a finally block a SyntaxWarning, targeting the swallowed-exception bug. PEP 758 allows except TimeoutError, ConnectionRefusedError: without parentheses when there is no as clause (with as, parentheses are still required). And error messages improved further: 3.14 detects common keyword typos, explains unhashable-type errors with context, and gives a specific message when a synchronous object is used with async with or vice versa. 3.13 had already added coloured tracebacks in the interactive interpreter.

Warnings versus exceptions

The warnings module reports conditions that are not errors — deprecated APIs, suspicious but legal code — without interrupting flow. Warnings are filtered: by default DeprecationWarning is shown only when triggered by code in __main__, and each unique warning is shown once. In tests, python -W error or pytest's filterwarnings = error turns warnings into exceptions so deprecations fail CI (continuous integration) before they become removals. warnings.catch_warnings() is a context manager that temporarily changes filters; in 3.14 it can optionally use context variables so concurrent threads or tasks do not interfere with each other's filters.

Exceptions across threads and processes

An exception raised in a worker thread does not propagate to the thread that started it; it ends that thread and, by default, is printed by threading.excepthook. With concurrent.futures, the exception is stored in the Future and re-raised in the caller when it calls future.result(), so a pool whose results are never collected hides its failures entirely. Exceptions from multiprocessing workers must be pickled to cross the process boundary; custom exceptions whose __init__ requires keyword-only arguments (like PaymentError above) can fail to unpickle unless they implement __reduce__, turning a clear error into a confusing one. py9 revisits this.

Leaked resources on error paths

The connection-pool exhaustion story from the introduction is one of the most common outage patterns. Its signature is a slow ramp: an error rate on some input causes a leak per failure, and the service degrades minutes or hours later, far from the triggering request. Metrics that expose it: pool "in use" count climbing without falling, open file descriptors rising (ls /proc/<pid>/fd | wc -l on Linux), or "too many open files" errors. The fix is structural — every acquire inside a with — and linters (Ruff's SIM115 for open outside with) catch many cases.

Swallowed exceptions and silent data loss

except Exception: pass, except: return None and try/except that logs at debug level all convert failures into missing data. In pipelines the result is jobs that "succeed" while producing fewer rows each day. Production practice: every broad catch either re-raises, returns an explicit error to a caller, or increments a metric and logs at warning or error level with context. Many teams ban bare except via Ruff (E722) and flag except Exception without a re-raise or log (BLE001).

Where to handle: boundaries

Handle exceptions at boundaries: the request handler of a web service (turn it into a 4xx or 5xx response), the loop of a worker (retry, dead-letter, move on), the top of a command-line tool (print a clean message and exit with a non-zero status). Inside the core logic, raise specific exceptions and let them travel. Frameworks help: FastAPI and Flask let you register exception handlers that map domain exceptions such as NotFound to HTTP responses in one place.

Logging exceptions once, with context

logger.exception("...") inside an except block logs at error level with the full traceback. Do it once, where the exception is finally handled, and include identifiers (request id, job id, record key) in the message or structured fields. Logging at every layer produces five copies of the same traceback; logging without the traceback (logger.error(str(e))) loses the most useful information. Error trackers such as Sentry group exceptions by type and traceback, which works best when exception types are specific.

Retries and exception classification

Retry logic depends on knowing which errors are transient. Timeouts, connection resets, HTTP 429 and 503 responses and database serialisation failures usually are; validation errors, 400s and 404s are not. Encode that in the exception hierarchy (a RetryableError base, or checking isinstance(e, (TimeoutError, ConnectionError))) rather than string-matching messages, and retry only idempotent operations. py4 covers retry decorators; the scale track's sc12 covers backoff and retry budgets.

Exit codes for command-line tools and jobs

Schedulers, CI (continuous integration) systems and container orchestrators judge success by a process's exit code. An uncaught exception exits with status 1, and sys.exit(2) raises SystemExit with that code. A batch script that catches everything at the top, prints the error and then ends normally exits with 0, so the scheduler records a success and nobody is alerted. Top-level handlers in tools and jobs should log the error and then exit non-zero.

Cancellation is not an error

In asyncio, cancelling a task raises asyncio.CancelledError inside it, and since 3.8 that class inherits from BaseException, not Exception, precisely so that except Exception in application code does not swallow cancellation and leave zombie tasks running. Code that catches BaseException for cleanup must re-raise it. The same reasoning applies to KeyboardInterrupt in long-running jobs: catch it only to clean up and exit.

Answer
  • The bare except: swallows everything, including KeyboardInterrupt and genuine bugs such as a typo'd name, and conflates "file missing" with "file contains garbage".
  • If open fails, f is never bound, so finally: f.close() raises UnboundLocalError: cannot access local variable 'f' where it is not associated with a value — which replaces the original error. (Verified: calling it with a missing file raises exactly that.)
  • Returning 0 on failure makes a corrupt or missing config indistinguishable from a legitimate zero.
  • No encoding is specified, so decoding depends on the platform's default (a classic Windows versus Linux difference).
class ConfigError(Exception):
    pass

def load(path: str) -> int:
    try:
        with open(path, encoding="utf-8") as f:
            text = f.read()
    except FileNotFoundError as e:
        raise ConfigError(f"config file missing: {path}") from e
    try:
        return int(text.strip())
    except ValueError as e:
        raise ConfigError(f"expected an integer in {path}, got {text[:20]!r}") from e

The with statement guarantees the file is closed on every path and only after it was opened. Each failure becomes a specific, chained ConfigError that keeps the original cause in the traceback. The protected regions are small, so an unrelated error is not misreported. And the policy — whether a missing file means "use a default" — is left to the caller, which knows the context; it does not belong inside load.
