A team deploys a Flask service for looking up user profiles. It starts at 300 MB per worker. Two days later each worker uses 3 GB, the container hits its memory limit, and the operating system kills it with exit code 137. The service restarts, looks healthy, and the cycle repeats. The team's first theory is "a garbage collection problem"; their second is "Python leaks memory"; their third is to schedule nightly restarts. The real cause, found an hour after someone ran a memory profiler, was a module-level dictionary that remembered every user who had ever requested a profile.

Meanwhile, a data team tries to speed up a feature-engineering job by running it on eight threads instead of one. It gets no faster at all. Someone explains "it's the GIL", and the team concludes that Python cannot use more than one core. That is also not quite right: the same job on eight processes is nearly eight times faster, the I/O-heavy download step did benefit from threads, and the NumPy parts of it could have used all cores on threads.

Both teams were missing a working model of the runtime underneath their code: how CPython decides when memory can be freed, what the garbage collector actually does, why the process's memory graph does not come down after a big job, and what the Global Interpreter Lock (GIL) blocks and does not block. These are standard senior-interview topics precisely because they show up as production incidents — memory growth, latency spikes during collection, disappointing parallel speed-ups, and race conditions people assumed the GIL prevented.

The ground is also moving. Python 3.12 made some objects immortal; 3.13 introduced an experimental build without the GIL; 3.14 made that free-threaded build officially supported, added sub-interpreters to the standard library, and shipped — then, in 3.14.5, reverted — a new incremental garbage collector.

This lesson starts with reference counting, the main way CPython frees memory, then shows the one thing it cannot handle — cycles — and how the generational cyclic collector fixes that. It covers the allocator and why resident memory stays high, how "leaks" happen in a garbage-collected language and how to find them with tracemalloc, and weak references. The second half is the GIL: what it is, why it exists, what it means for threads on CPU-bound and I/O-bound work, what it does not protect, and today's options for real parallelism. Measurements were made on CPython 3.12.10 on a 12-core Windows laptop; version differences up to 3.14 are called out explicitly.

Memory: a library with a lending counter

Picture every Python object as a book in a library, with a counter on its cover showing how many people currently have it checked out. Each time a new name, list slot or attribute starts referring to the object, the counter goes up; each time one stops, it goes down. When the counter hits zero, nobody can possibly be using the book, so the librarian puts it back on the shelf immediately. That is reference counting, and it is how CPython frees the vast majority of objects — instantly and predictably, the moment the last reference disappears.

The scheme has one blind spot. Suppose two books are each only checked out by the other: book A's borrower is book B, and B's borrower is A. Nobody in the library can reach either book any more, but both counters are stuck at one. Reference counting will never free them. So once in a while the librarian does an audit: take a group of books, ignore loans that come from other books in the same group, and see which books have no outside borrower at all. Those are garbage. That audit is the cyclic garbage collector.

Leaks: books nobody returns

If the librarian frees everything nobody holds, how can a Python program "leak"? By holding things it no longer needs. A dictionary at module level that stores every request, a cache with no size limit, a list of callbacks that is appended to and never cleared: each keeps its objects checked out forever. No collector can free them, because from its point of view they are in use. Nearly every Python memory leak is this kind.

The GIL: one talking stick

Now the second half. Standard CPython has a Global Interpreter Lock: a single lock that a thread must hold to run Python code. Think of a meeting with one talking stick. Many people (threads) can be in the room, but only the holder may speak (run Python instructions). The stick is passed around frequently, so everyone gets turns, but two people never speak at once.

The crucial detail is that anyone who stops to wait — for a web page to download, a file to be read, a timer, or a long calculation inside a C library that does not touch Python objects — puts the stick down while waiting. So threads work well for programs that spend their time waiting (I/O-bound), and poorly for programs that spend their time computing in Python (CPU-bound), where they just take turns on one core.

Where the analogies break: reference counts are not checked out by people but by references of any kind, including references from inside the interpreter itself (a function call's arguments, a traceback). And the talking stick does not make conversations orderly: a speaker can be interrupted mid-sentence, so two threads that each "read a number, add one, write it back" can still interleave and lose an update. The GIL protects the interpreter's internals, not your program's logic.

1. Reference counting in practice

Every CPython object starts with a header containing its reference count and a pointer to its type (py1). The interpreter increments the count whenever a new reference is created and decrements it when one is dropped. sys.getrefcount(obj) shows the value, always one higher than you expect because passing obj as an argument creates a temporary reference:

import sys
x = []
print(sys.getrefcount(x))   # 2  — the name x, plus the argument
y = x
print(sys.getrefcount(x))   # 3  — y added one
d = {"k": x}
print(sys.getrefcount(x))   # 4  — the dict's value slot added one
del y; d.clear()
print(sys.getrefcount(x))   # 2  — back down

When the count reaches zero the object is destroyed at once: its __del__ method (if any) runs, its memory is released, and the references it held are dropped, which may cascade to free further objects.

class Node:
    def __init__(self, name): self.name = name; self.other = None
    def __del__(self): print(f"freeing {self.name}")

a = Node("a")
del a                 # prints "freeing a" immediately
print("after del a")

This promptness is a real advantage: in CPython, a file object that goes out of scope is closed right away, and memory from a temporary list is reused immediately. The costs are that every reference operation writes to memory (which matters for multi-core caching and for forked processes, section 10) and that the count is shared mutable state, which is the main reason for the GIL (section 7). Some objects are exempt: since 3.12, immortal objects such as None, True and small integers have a fixed count that is never changed (py1).

2. Cycles and the cyclic garbage collector

A reference cycle is a set of objects that refer to each other. They are everywhere in real code: a tree node with a parent pointer and a list of children; a doubly linked list; an object that stores one of its own bound methods as a callback; an exception whose traceback references the frame that holds the exception. When the program drops all outside references to a cycle, every object in it still has a nonzero count, so reference counting never frees it. We can watch this by turning the collector off:

import gc
gc.disable()
a = Node("A"); b = Node("B")
a.other = b; b.other = a          # a cycle
del a, b                          # nothing printed: counts are still 1
print("after del cycle (gc disabled)")
print("collected:", gc.collect()) # prints "freeing A", "freeing B", then a count
gc.enable()

How does the collector find garbage without knowing which objects the program can reach? It only needs to consider container objects — lists, dicts, class instances, anything that can hold references — because only they can form cycles; ints and strings are never tracked (gc.is_tracked([]) is True, gc.is_tracked("s") is False; CPython even untracks dicts and tuples that contain only atomic values). For the set of tracked objects being examined, it:

  1. Copies each object's reference count into a scratch field.
  2. For every reference between two objects in the set, subtracts one from the target's scratch count. What remains counts only references from outside the set: names, the stack, objects not being examined.
  3. Objects with a remaining count above zero are reachable from outside, and so is everything they reference, transitively. Mark them all alive.
  4. Everything not marked alive is unreachable: garbage. Run finalizers (__del__, weakref callbacks), clear the objects' references to break the cycles, and let reference counting free them.

Scanning every object on every collection would be slow for large programs, so the collector is generational. Newly created container objects go into generation 0. gc.get_threshold() on 3.12 returns (700, 10, 10): when allocations minus deallocations of tracked objects exceed 700, generation 0 is collected; survivors move to generation 1, which is collected after every ten generation-0 collections; survivors of that move to generation 2, collected after ten generation-1 collections and only if enough new long-lived objects have accumulated. The bet — true for most programs — is that objects die young. Creating 100,000 two-object cycles in the test run triggered 262 generation-0 collections and no extra full collections.

A collection pauses the thread that triggered it for as long as the scan takes, usually well under a millisecond for generation 0 but potentially tens or hundreds of milliseconds for a full collection over a heap of millions of objects. Those pauses are where the version history gets interesting (deep dive): 3.14.0 tried an incremental design to shorten them, and 3.14.5 reverted it.

3. The allocator and why memory doesn't come back

Python programs allocate enormous numbers of small objects, and the operating system's general-purpose malloc is relatively slow for that. CPython therefore has its own small-object allocator, pymalloc, used for requests up to 512 bytes. It requests large arenas from the OS (1 MiB each on 64-bit builds since 3.10, 256 KiB on 32-bit ones), splits each into 16 KiB pools, and splits each pool into equal-sized blocks for one size class. Freeing an object returns its block to its pool's free list, ready for the next object of that size.

The consequence that confuses dashboards: an arena can be given back to the operating system only when every block in it is free. After a spike — loading a big file, one huge request — most objects are freed, but a few survivors scattered across many arenas keep those arenas alive. Python can reuse the space, so memory does not keep growing, but the process's resident set size (RSS, the physical memory the OS counts against it) stays at roughly its peak. A plateau at the peak is allocator behaviour; unbounded growth is a leak. Large objects (over 512 bytes) go to the system allocator, which has its own, similar fragmentation behaviour.

4. How Python programs leak

A Python "leak" is almost always an object that is still referenced by something the program forgot about. The usual suspects:

  • Growing module-level containers: a dict used as a cache or registry that is added to on every request and never trimmed.
  • Unbounded caches: @functools.cache or lru_cache(maxsize=None) keyed on unbounded input, and lru_cache on methods, which also keeps every self alive (py4).
  • Listeners and callbacks registered with an event bus, signal or long-lived object and never unregistered; each callback keeps its closure's cells, and a bound method keeps its whole instance.
  • Stored exceptions: a traceback references every frame it passed through and every local in them (py7).
  • Class-level mutable attributes used as per-instance storage (py6).
  • Native leaks in C extensions, which Python-level tools cannot see and need a native profiler such as memray.

5. Finding leaks with tracemalloc

tracemalloc hooks CPython's allocators and records, for each allocated block, the source line that allocated it. Take a snapshot, let the suspected leak run, take another, and compare them grouped by line:

import tracemalloc
tracemalloc.start()
_seen = {}
def handle(uid):
    _seen[uid] = str(uid) * 100       # "cache" that never forgets

snap1 = tracemalloc.take_snapshot()
for i in range(10_000):
    handle(i)
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "lineno")[:3]:
    print(stat)
# app.py:5: size=... KiB (+... KiB), count=10000 (+10000), average=... B

Each line of output names a file and line, the total size allocated there and still alive, and how much it grew between snapshots. In a service, expose an endpoint or signal handler that dumps a snapshot, take two an hour apart under real traffic, and the leaking line is usually at the top of the diff. Then ask "what keeps these objects alive?": gc.get_referrers(obj) lists the objects referring to one, and the third-party objgraph draws chains of references back to a module or global. Tracing costs memory and CPU (often 2-4× slowdown in allocation-heavy code), so enable it temporarily or on one canary instance.

6. Weak references

Sometimes you want to refer to an object without keeping it alive — a cache that should forget objects nobody else uses, or an observer list that should drop listeners that have gone away. A weak reference does not increase the reference count:

import weakref
class Big: pass

o = Big()
r = weakref.ref(o)
print(r() is o)          # True — calling the weakref returns the object
del o
print(r())               # None — the object was freed; the weakref noticed

cache = weakref.WeakValueDictionary()
o = Big(); cache["k"] = o
print(len(cache))        # 1
del o
print(len(cache))        # 0 — the entry vanished with the object

WeakKeyDictionary attaches data to objects you do not own without extending their lives, weakref.WeakSet holds observers, and weakref.finalize(obj, fn) registers a cleanup callback that runs when the object is collected — a more reliable alternative to __del__. Not every type supports weak references: ints, strings and tuples do not, and __slots__ classes need "__weakref__" in their slots (py6).

7. The Global Interpreter Lock

Now the second question: why can't threads run Python code in parallel? In standard CPython, a thread must hold the GIL to execute Python bytecode or touch Python objects. There is one GIL per interpreter, so only one thread runs Python code at any instant, even on a 12-core machine.

Why does it exist? Reference counts are updated on nearly every operation (section 1). If two threads could update the same object's count at once, increments would be lost and objects freed while in use — crashes, not just wrong answers. Protecting every count with an atomic instruction or per-object lock costs noticeable single-threaded speed, and CPython's internals and thousands of C extensions were written assuming exclusive access. One global lock made the interpreter simple, single-threaded code fast, and extensions easy to write. That trade was made in the early 1990s when multi-core machines were rare.

A thread gives up the GIL in two situations. It voluntarily releases it around blocking operations: socket and file I/O, time.sleep, waiting on a lock, and inside C code written to release it (NumPy's large array operations, hashlib on big inputs, compression, most of PyTorch's kernels). And it is asked to release it: a waiting thread sets a flag after the switch interval (sys.getswitchinterval(), 0.005 s by default), and the running thread hands over at its next check point.

The measurements on a 12-core laptop, running a pure-Python loop four times:

# CPU-bound (sum of squares, 10M iterations) x4
#   sequential   2.37 s
#   4 threads    2.38 s     ← no gain: the GIL serialises them
#   4 processes  1.00 s     ← real parallelism, minus process start-up
# I/O-bound (time.sleep(0.5)) x4
#   sequential   2.00 s
#   4 threads    0.50 s     ← the waits overlap
# hashlib.sha256 of 50 MB x4 (C code that releases the GIL)
#   sequential   0.10 s
#   4 threads    0.03 s     ← threads parallelise native work

8. What the GIL does not protect

The GIL keeps the interpreter's own data structures consistent. It does not make your multi-step logic atomic, because a thread can lose the GIL between any two bytecodes. Here is a race made visible by inviting a switch between the read and the write:

import threading, time
counter = 0
def work():
    global counter
    for _ in range(1000):
        v = counter          # read
        time.sleep(0)        # a switch can happen here (or anywhere)
        counter = v + 1      # write back

threads = [threading.Thread(target=work) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print("expected 4000, got", counter)    # measured: expected 4000, got 1705

Two threads read the same value, both add one, and both write it back: one increment is lost. Without the sleep(0), a plain counter += 1 loop on 3.12 happened to give the right answer in testing, because since 3.10 CPython only switches threads at certain instruction boundaries — but that is an implementation detail, not a guarantee, and on the free-threaded build the race is immediate. Single operations on built-in containers implemented in C (list.append, dict[k] = v, deque.popleft) are effectively atomic; anything composed of several steps is not. Protect shared state with threading.Lock (with lock: counter += 1 gave exactly 400,000 in the 4×100,000 test) or avoid sharing and pass data through queue.Queue.

Processes (ProcessPoolExecutor, multiprocessing) are the long-standing answer: each process has its own interpreter and GIL. Arguments and results cross between processes by pickling, so they suit tasks where the work is large relative to the data. Native code is usually the best answer for numeric work: one NumPy call does millions of operations in C, often on many cores, with no GIL involved. py9 covers the concurrency APIs in detail; the next two rows are new enough to deserve their own paragraphs.

Sub-interpreters. CPython has long been able to run several isolated interpreters in one process. Python 3.12 (PEP 684) gave each its own GIL, so they can run in parallel, and 3.14 (PEP 734) exposed them in the standard library as concurrent.interpreters, plus concurrent.futures.InterpreterPoolExecutor. They are lighter than processes but share almost nothing by default; the 3.14 release notes list current limitations: slow start-up, high per-interpreter memory, few ways to share data besides memoryview, and many third-party extensions not yet compatible.

The free-threaded build. PEP 703 made the GIL optional in a separately compiled CPython (usually installed as python3.14t). It was experimental in 3.13; 3.14 made it officially supported (PEP 779) and cut the single-threaded overhead to roughly 5-10%. Threads then run Python code truly in parallel on multiple cores. The catches: extensions must be rebuilt and declare compatibility, otherwise importing one re-enables the GIL for the process; and code that relied on the GIL's accidental serialisation will expose races. sys._is_gil_enabled() (3.13+) reports whether the GIL is currently on.

10. Fork, copy-on-write and gc.freeze

Web servers such as gunicorn often load the application once in a parent process and then fork() worker processes. The operating system shares the parent's memory pages with the children through copy-on-write: a page is copied only when someone writes to it. Python writes to objects even when you only read them — every reference taken updates a reference count, and every garbage-collection pass writes to tracked objects' headers — so pages full of long-lived objects gradually get copied into every worker, and memory that should be shared becomes private. Two mitigations: immortal objects (3.12) remove the refcount writes for the most-shared objects, and gc.freeze(), called just before forking, moves every existing object into a permanent generation the collector never scans. The gc documentation recommends gc.disable() early in the parent, gc.freeze() right before fork(), and gc.enable() early in each child.

The 3.14 incremental collector, and its revert

A full collection over a heap of millions of objects can pause a program for a noticeable time, which hurts latency-sensitive services. Python 3.14.0 shipped an incremental collector with only two generations, young and old, which collected the young generation plus an increment of the old generation on each run, cutting maximum pause times by an order of magnitude or more on large heaps; gc.collect(1) meant "do one increment" and threshold2 was ignored. The trade-off was that garbage in the old generation was reclaimed more slowly, and production users reported significant memory pressure. Python 3.14.5 reverted to 3.13's generational collector: three generations again, gc.collect(1) collects the middle generation, and threshold2 is honoured. For interviews and operations, the lesson is that GC behaviour is a tunable engineering trade-off between pause time and memory, and that it can change in a patch release — pin versions and watch memory graphs when upgrading.

Why only containers are tracked, and untracking

Only objects that can contain references can participate in cycles, so only they are tracked by the collector, via a linked list threaded through a small header placed before each tracked object. CPython saves work by untracking objects that provably cannot be part of a cycle: a dict whose keys and values are all atomic (ints, strings, None) is untracked (gc.is_tracked({"a": 1}) is False), and tuples are untracked during a collection if all their elements are untracked. This keeps collections cheaper in data-heavy programs that hold millions of small dicts of plain values.

Finalizers, resurrection and PEP 442

Before Python 3.4, objects in a cycle that defined __del__ could not be collected safely — which finalizer runs first? — so they were parked in gc.garbage forever. PEP 442 made them collectable: the collector runs all finalizers in the unreachable set first, then re-checks reachability, because a finalizer may have "resurrected" an object by storing a reference to it somewhere; resurrected objects are kept, the rest are freed. Finalizer order within a cycle is undefined and each finalizer runs at most once. weakref.finalize avoids most of these subtleties and also runs registered callbacks at interpreter exit.

How the free-threaded build replaces the GIL

PEP 703 needed thread-safe reference counting without making every increment an expensive atomic operation. The answer is biased reference counting: each object records its owning thread, which updates a local count with ordinary instructions, while other threads update a separate shared count atomically; the two are merged when needed. Immortal objects skip counting entirely, and some objects (functions, code objects, module globals) use deferred counting that is reconciled during garbage collection. Lists and dicts get lightweight per-object locks so that single operations stay atomic. Memory allocation switches from pymalloc to Microsoft's thread-safe mimalloc, which the collector also uses to find all objects without a global linked list. The cyclic collector itself briefly stops all threads ("stop the world") while it runs.

Sub-interpreters in more depth

Each interpreter has its own modules, sys state, builtins and, since 3.12, its own GIL; objects are never shared implicitly. In 3.14's concurrent.interpreters, you create an interpreter, run code or call functions in it, and pass data through queues that copy or share only simple immutable values and buffers. The model resembles processes (CSP, "communicating sequential processes", or actors: isolated workers communicating by messages) with lower overhead and without pickling for supported types. Extension modules must opt in to multi-phase initialisation and per-interpreter state to be importable in sub-interpreters, which is the main adoption barrier today.

Latency tuning in practice

Services sensitive to tail latency sometimes tune the collector. Options include raising threshold0 (fewer, larger young collections), calling gc.freeze() after start-up so the application's long-lived objects are never scanned again, disabling automatic collection and calling gc.collect() at quiet moments, or relying on the fact that most garbage is acyclic and freed by refcounting anyway. Instagram's engineering team famously disabled the GC in their Django workers and later moved to gc.freeze(), which they contributed upstream. Any such change needs before-and-after measurement of both latency percentiles and memory, because the cost of not collecting is memory growth from uncollected cycles. gc.callbacks lets you record the duration of each collection as a metric.

The switch interval and convoy effects

Since the "new GIL" of Python 3.2, a thread waiting for the GIL requests it after the switch interval (5 ms by default) and the holder drops it at its next eval-breaker check. A CPU-bound thread can thereby delay an I/O-bound thread's response by up to that interval each time the I/O thread needs the GIL back — the "convoy effect" that makes mixed CPU and I/O workloads on threads show higher latency than expected. Lowering sys.setswitchinterval trades throughput for responsiveness; moving CPU work out of the process is the structural fix.

Memory growth incidents

The canonical incident is a worker whose RSS climbs steadily until it is killed by the OOM (out-of-memory) killer, which in containers shows up as exit code 137 and a restart. The first diagnostic question is shape: a staircase that plateaus is usually allocator behaviour after load spikes; a line that climbs with traffic is a leak. Next, find which objects are growing: a tracemalloc diff between two snapshots taken under real traffic, or memray attached to a canary instance, which also shows native allocations. Expose sizes of suspect caches and registries as metrics so the next occurrence is obvious without profiling. Record the Python version alongside memory graphs too: the 3.14.0-3.14.4 collector change showed that an interpreter upgrade alone can shift a service's memory profile.

Pragmatic mitigations

Worker recycling — gunicorn's max_requests with max_requests_jitter, Celery's worker_max_tasks_per_child — restarts workers after a number of requests or tasks. It caps the damage of slow leaks and fragmentation and is a reasonable safety net, but it hides bugs if used as the fix. For memory-heavy one-off work (building an index, loading a large file), run it in a subprocess that exits afterwards, which returns all its memory to the OS regardless of fragmentation.

Forked workers and shared memory

Pre-fork servers that load large read-only data (a vocabulary, a model's weights in Python objects, a feature table) before forking expect the data to be shared across workers. Refcount and GC writes break that sharing over time, so per-worker memory creeps up towards a full private copy. Use gc.freeze() before forking, keep large read-only data in formats with no per-object headers (NumPy arrays, memory-mapped files, Arrow buffers), or load models once per worker and budget memory accordingly.

Parallelism decisions for AI and data workloads

Most heavy lifting in AI engineering already happens in native code that releases the GIL: PyTorch kernels, tokenizers written in Rust, NumPy and Polars. For such workloads, threads and async I/O are usually enough in the serving path, and a thread pool for pre-processing often scales fine. Pure-Python pre-processing loops (text cleaning, JSON reshaping) are the part that does not scale with threads; move them to processes (PyTorch's DataLoader uses worker processes for exactly this reason), vectorise them, or evaluate the free-threaded build once your dependencies support it.

Race conditions that the GIL used to hide

Codebases that have run for years on threads sometimes contain unprotected shared counters, lazily initialised globals and check-then-set sequences that rarely fail because the GIL makes switches infrequent. They fail under load, after a Python upgrade that changes switching behaviour, or immediately on the free-threaded build. Before enabling free threading, audit shared mutable state, run tests under the free-threaded interpreter, and use thread sanitizers where available; the Python free-threading HOWTO lists known pitfalls.

Observability

Useful signals: process RSS and container memory against limits; gc.get_stats() and collection durations via gc.callbacks; object counts for key types (objgraph.show_growth() in a debug endpoint); and, for GIL contention, py-spy's --gil mode, which samples only threads holding the GIL and shows whether threads are spending their time waiting for it.

Diagnose it

A Flask service's memory grows from 300 MB to 3 GB over two days and is then killed by the OOM killer. CPU is normal. Code includes:

_seen_users = {}

@app.get("/profile/<uid>")
def profile(uid):
    _seen_users[uid] = load_profile(uid)     # "cache"
    return render(_seen_users[uid])

class Report:
    @functools.lru_cache(maxsize=None)
    def rows(self, day): ...

How do you confirm the cause, and fix it?

Answer

Confirm: the memory graph climbs with traffic rather than plateauing, which rules out allocator fragmentation. Take tracemalloc snapshots an hour apart (or attach memray to a canary) and compare top allocations by line; growth attributed to load_profile and to the rows cache confirms it. len(_seen_users) and Report.rows.cache_info() exposed as metrics are even cheaper checks.

Causes: (1) _seen_users is an unbounded module-level dict: every distinct user ever seen stays in memory forever, separately in each worker process. (2) lru_cache(maxsize=None) on a method is unbounded and includes self in every key, so every Report instance and all its rows are kept alive.

Fixes: replace the dict with a bounded cache with expiry (cachetools.TTLCache(maxsize=10_000, ttl=300)), or move shared caching to Redis so it is not duplicated per process. For rows, use a bounded cache keyed on day only, or functools.cached_property if the value is per instance. Add a memory alert, and consider max_requests worker recycling in gunicorn as a safety net — a net, not the fix. Note that this is not the GIL or the garbage collector: every one of these objects is still referenced, so no collector may free it.
