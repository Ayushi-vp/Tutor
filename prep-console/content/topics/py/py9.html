An AI team builds a service that enriches documents: for each incoming document it calls an embedding API, a moderation API and a vector database, then combines the results. Each call takes about 200 ms. Written as ordinary sequential Python, one document takes 600 ms and the service handles fewer than two documents per second per worker, while the CPU sits almost entirely idle. The program is not slow; it is waiting, one call at a time.

A developer rewrites it with async def and sprinkles await in front of every call. Nothing gets faster. Then someone notices that one helper still uses the synchronous requests library, and under load the whole service's latency climbs to seconds, even for the health check. A second developer adds a thread pool for a slow text-cleaning step that is pure Python, and that gets no faster either. A third fixes the first problem by firing all 10,000 API calls at once with asyncio.gather, and the embedding provider starts returning 429 "too many requests" errors.

Each of these is a different misunderstanding of concurrency in Python. Python offers three models — threads, processes and asyncio — and they are good at different things because of the GIL (py8) and because of how each one waits. Choosing the wrong one gives no speed-up; using the right one wrongly (sequential awaits, a blocking call on the event loop, unbounded fan-out, lost exceptions) gives outages. For AI engineers this is daily work: almost every LLM application is dominated by network waits on model APIs, vector stores and databases, and streaming responses and batching requests are concurrency problems.

This lesson starts with the difference between concurrency and parallelism and between I/O-bound and CPU-bound work, which decides the model to use. It covers threads and concurrent.futures, then processes and their pickling and start-method rules. Most of the lesson is asyncio: what a coroutine and a task are, how the event loop runs them, how to get real concurrency with gather and TaskGroup, and the essential production controls — never blocking the loop, timeouts, cancellation, bounded concurrency and queues. It ends with race conditions in both worlds and the changes up to Python 3.14. Measurements are from CPython 3.12.10; the network-socket machinery underneath asyncio is covered in net13.

One cook, many dishes

Imagine a kitchen. A sequential cook puts pasta on to boil and stands watching the pot for ten minutes, then starts the sauce. Most of the cook's time is spent waiting. A concurrent cook puts the pasta on, starts chopping for the sauce while the water heats, checks the oven, and returns to each dish when it needs attention. There is still only one cook, but several dishes are in progress at once, and the meal is ready much sooner. Parallel cooking means hiring more cooks, who genuinely work at the same instant.

That distinction maps directly onto programs:

  • I/O-bound work spends its time waiting for something outside the CPU — a network response, a disk read, a database query. It needs concurrency: something that lets the program start other work while waiting. Threads and asyncio both do this.
  • CPU-bound work spends its time computing. It needs parallelism: more cores working at once. Because of the GIL (py8), Python threads cannot run Python code in parallel, so this needs processes, native code, or the newer options in 3.14.

The three tools

Threads are several cooks sharing one kitchen and, in standard CPython, one knife (the GIL): only one can cut at a time, but while one waits for the oven another can cut. They work with any ordinary library, which makes them the easiest way to overlap a few dozen network calls.

Processes are separate kitchens, each with its own cook and its own knife. They really do work in parallel, but ingredients must be packed up and carried between kitchens (pickling), and setting up a kitchen takes time.

asyncio is the single concurrent cook: one thread runs an event loop that juggles thousands of tasks, each of which says explicitly "I'm waiting now, go do something else" by writing await. It is the most efficient way to wait on many things at once, but it requires every step to cooperate: one task that stands staring at a pot without saying await freezes the whole kitchen.

What each one costs

The three tools also differ in price. An operating-system thread reserves memory for its own stack and is switched by the kernel, so a few hundred threads are fine but tens of thousands are not. A process costs a whole interpreter — tens of megabytes and noticeable start-up time — plus the work of copying data to and from it. An asyncio task is just a small Python object, so a single process can keep tens of thousands of them waiting at once. The trade-off runs the other way for convenience: threads and processes work with any library, while asyncio needs libraries written for it. Most real services end up combining them, for example an asyncio web server that hands CPU-heavy steps to a process pool.

Where the kitchen analogy breaks: real cooks can be interrupted at any moment, and so can threads, which is why shared data needs locks. asyncio tasks can only switch at an await, which makes it easier to reason about which code runs uninterrupted — but not immune to races, as the end of the lesson shows.

1. Threads and concurrent.futures

The threading module creates operating-system threads directly, but most code should use the higher-level concurrent.futures API, which manages a pool of reusable threads (a thread pool) and hands you futures: placeholder objects for results that will arrive later. Here ten simulated 200 ms calls run sequentially and then on a pool:

import time
from concurrent.futures import ThreadPoolExecutor

def fetch(i):
    time.sleep(0.2)          # stands in for a network call; releases the GIL
    return i * 10

# sequential: 2.00 s
with ThreadPoolExecutor(max_workers=10) as pool:
    results = list(pool.map(fetch, range(10)))     # 0.20 s, [0, 10, 20, ...]

The waits overlap because time.sleep, like real socket reads, releases the GIL (py8). pool.map returns results in input order. For more control, pool.submit(fn, *args) returns a Future immediately; future.result(timeout=...) waits for it; as_completed(futures) yields futures as they finish, in completion order, so you can handle fast results first:

from concurrent.futures import as_completed
with ThreadPoolExecutor(max_workers=16) as pool:
    futures = {pool.submit(fetch_url, url): url for url in urls}
    for fut in as_completed(futures):
        url = futures[fut]
        try:
            handle(url, fut.result())
        except Exception as e:
            log.warning("failed %s: %s", url, e)

Two rules. First, an exception raised in a worker is stored in the future and re-raised only when you call result(); in the test, a pool where item 3 raised completed the with block silently, and the error appeared only when the results were collected. Never fire and forget. Second, max_workers is your concurrency limit, and it protects downstream services; the default for threads is min(32, cpu_count + 4). The with block waits for all submitted work on exit. Since 3.14, Executor.map accepts buffersize= to limit how many tasks are submitted ahead of the results you have consumed, so mapping over a huge or infinite iterable no longer submits everything up front.

For producer-consumer designs between threads, queue.Queue is the thread-safe building block: put blocks when a bounded queue (maxsize) is full, giving backpressure, and get blocks until an item is available.

2. Processes

For CPU-bound pure-Python work, ProcessPoolExecutor has the same API but runs each task in a separate process with its own interpreter and GIL. In py8's measurement, four CPU-bound tasks took 2.38 s on threads and 1.00 s on processes. The price is that everything crossing the process boundary — the function, its arguments and its result — is pickled (serialised to bytes) and unpickled on the other side. That has three consequences:

  • The function must be importable by name: module-level functions work; lambdas and nested functions do not. On 3.12, pool.map(lambda x: x, [1]) failed with AttributeError: Can't get local object 'main_sync.<locals>.<lambda>'.
  • Each task costs at least the pickling of its data plus inter-process communication, typically well under a millisecond for small data but significant for large arrays. Tasks must be large enough to amortise it; map(fn, items, chunksize=100) sends items in batches.
  • Large read-only data (a model, a lookup table) should be loaded once per worker with the pool's initializer= argument, not sent with every task.

How child processes are created is the start method. fork copies the parent process instantly (sharing memory copy-on-write, py8) but can deadlock if the parent has threads holding locks at the moment of the fork. spawn starts a fresh interpreter that re-imports your main module, slower but safe; it is the default on Windows and macOS. forkserver forks children from a clean single-threaded helper process; since Python 3.14 it is the default on Linux and other Unix systems except macOS. With spawn and forkserver, the main module is imported in each child, so code that creates the pool must be under if __name__ == "__main__":, or each child would try to create its own pool.

3. asyncio: coroutines

Threads are managed by the operating system, which can switch between them at any moment, and each costs memory for its stack; thousands of threads become expensive. asyncio takes the opposite approach: one thread, and tasks that cooperatively hand control back whenever they would wait.

The building block is the coroutine. A function defined with async def is a coroutine function; calling it runs nothing and returns a coroutine object, a paused computation much like a generator (py5). Inside it, await something means: "suspend me until something is done, and let other work run meanwhile." asyncio.run(main()) creates an event loop, runs the main coroutine to completion, and closes the loop.

import asyncio

async def fetch_a(i):
    await asyncio.sleep(0.2)      # a non-blocking wait: suspends this coroutine
    return i * 10

async def main():
    for i in range(10):
        await fetch_a(i)          # measured: 2.10 s — each await waits before the next starts

asyncio.run(main())

That loop is sequential. await waits for one thing; it does not start anything else. This is the single most common asyncio mistake: code that is async all the way down and exactly as slow as the synchronous version.

4. Tasks, gather and TaskGroup: getting actual concurrency

Concurrency comes from starting several coroutines before waiting for them. A task wraps a coroutine and schedules it on the event loop so it runs independently. Three ways to get there:

results = await asyncio.gather(*(fetch_a(i) for i in range(10)))   # 0.21 s, results in order

async with asyncio.TaskGroup() as tg:                               # 3.11+
    tasks = [tg.create_task(fetch_a(i)) for i in range(1000)]
# 1,000 concurrent 0.2 s waits: 0.21 s total
results = [t.result() for t in tasks]

task = asyncio.create_task(fetch_a(1))   # starts running at the next await
...                                      # do other things
value = await task

gather and TaskGroup differ in how they handle failure, which matters a lot in production. With gather, the first exception propagates to the awaiting code but the other tasks keep running in the background; with return_exceptions=True it instead returns exceptions in place of results: [0, 1, ValueError('task 2 failed'), 3]. TaskGroup implements structured concurrency: the async with block cannot exit until every task in it has finished, and if one task fails, the group cancels the others and raises all failures as an ExceptionGroup (py7). In the test, four tasks where task 2 failed after 20 ms finished in 0.08 s with the others cancelled rather than running for their full second. That makes it impossible to leak background tasks by accident, which is why TaskGroup is the default choice for new code.

One more rule about loose tasks: the event loop keeps only weak references to tasks. A task created with create_task and not stored anywhere can be garbage-collected mid-flight. Keep references (a set, with a done-callback that removes the task) or use a TaskGroup.

5. How the event loop runs all this

The event loop is a scheduler running in one thread. It keeps a queue of tasks that are ready to run and a record of what each suspended task is waiting for. Each iteration:

  1. Run each ready task until it reaches an await on something that is not finished yet (a network read, a timer, another task). The task is suspended there, and the loop records a callback to resume it.
  2. Ask the operating system which sockets are ready, using the platform's efficient readiness API (epoll on Linux, kqueue on macOS, IOCP on Windows; net13 explains these). The wait's timeout is the time until the nearest timer, such as a pending sleep.
  3. For each socket that became readable or writable and each timer that expired, mark the waiting task ready.
  4. Repeat.

Two properties follow. Waiting costs almost nothing: a suspended coroutine is a small object, not a thread with a stack, so tens of thousands of concurrent connections fit in one process. And switching is cooperative: a task runs uninterrupted between two awaits. That is what makes the next section so important.

6. Never block the loop

Anything that takes time without awaiting — time.sleep, requests.get, a synchronous database driver, reading a big file, parsing a large JSON document, a CPU-heavy loop — holds the loop in step 1, and every other task waits. We can measure it with a heartbeat task that expects to wake every 100 ms:

async def heartbeat():
    for _ in range(5):
        t = time.perf_counter()
        await asyncio.sleep(0.1)
        ticks.append(round(time.perf_counter() - t, 2))

# with time.sleep(0.5) called inside another coroutine:
#   heartbeat intervals: [0.56, 0.1, 0.11, 0.11, 0.11]   ← one tick delayed by the blocking call
# with await asyncio.to_thread(time.sleep, 0.5) instead:
#   heartbeat intervals: [0.11, 0.11, 0.11, 0.11, 0.11]

In a web server, that delayed tick is every other user's request. The fixes: use async-native libraries (httpx or aiohttp for HTTP, asyncpg or async SQLAlchemy for databases); wrap unavoidable blocking calls in await asyncio.to_thread(fn, *args) (3.9+), which runs them on a thread pool while the loop continues; and send CPU-heavy work to a process pool with await loop.run_in_executor(process_pool, fn, *args), because a thread would still hold the GIL. asyncio's debug mode (asyncio.run(main(), debug=True) or PYTHONASYNCIODEBUG=1) logs any callback that runs longer than 100 ms, which finds these calls quickly.

7. Timeouts and cancellation

Every network call needs a timeout, or one hung connection holds a task (and whatever it has locked) forever. asyncio.timeout (3.11+) is a context manager: if the block takes longer, it is cancelled and TimeoutError is raised:

try:
    async with asyncio.timeout(0.1):
        await asyncio.sleep(1)
except TimeoutError:
    print("timed out")

Under the hood, timeouts, TaskGroup failure handling and task.cancel() all use cancellation: the loop raises asyncio.CancelledError inside the task at its current await. The task should let it propagate after cleaning up:

async def worker():
    try:
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print("worker: cleaning up after cancel")
        raise                      # re-raise, or cancellation silently fails

t = asyncio.create_task(worker())
await asyncio.sleep(0.01)
t.cancel()                         # prints the cleanup line; awaiting t raises CancelledError

Since 3.8 CancelledError inherits from BaseException, so except Exception does not catch it. Code that swallows it breaks timeouts and TaskGroups in confusing ways. asyncio.shield() protects an inner operation from an outer cancellation when it must finish (such as committing a transaction), and should be used sparingly.

8. Bounding concurrency and backpressure

asyncio makes it easy to start 100,000 operations at once, which is usually a bug: it opens too many sockets, uses memory for every pending response, and floods the downstream service until it rate-limits or falls over. Bound it. A semaphore lets at most N tasks into a section:

sem = asyncio.Semaphore(3)
async def limited(i):
    async with sem:              # at most 3 inside at once
        await asyncio.sleep(0.05)
# 20 tasks via gather: measured peak concurrency 3

For long-running pipelines, a fixed set of worker tasks reading from a bounded asyncio.Queue is often better: it bounds concurrency, and when workers fall behind, await queue.put() blocks the producer — backpressure — instead of letting work pile up in memory. queue.join() waits until every item has been marked done with task_done(); in the test, three workers processed 20 items through a queue of size 10.

queue = asyncio.Queue(maxsize=10)
async def consumer():
    while True:
        item = await queue.get()
        try:
            await process(item)
        finally:
            queue.task_done()

Size the bound from the downstream limit: the API's rate limit or concurrency allowance, the database's connection pool, or the number of GPU batches the model server accepts. And share one HTTP client (one connection pool) across tasks rather than creating one per request.

9. Race conditions in both worlds

Threads can be interrupted between any two bytecodes, so shared mutable state needs threading.Lock (py8 showed a counter losing 2,295 of 4,000 updates). asyncio tasks can only be interrupted at await, so code between awaits is effectively atomic — a real simplification. But a read, an await and a write still interleave:

counter = 0
async def incr():
    global counter
    v = counter
    await asyncio.sleep(0)        # any await is a switch point
    counter = v + 1

await asyncio.gather(*(incr() for _ in range(100)))
print(counter)                    # measured: 1, not 100

All 100 tasks read 0 before any of them wrote. The asyncio fixes are the same ideas as for threads: asyncio.Lock around the check-then-act sequence, or keep the state in one task and send it messages through a queue. Note that asyncio.Lock is not thread-safe and threading.Lock must never be awaited on the loop (acquiring it would block the loop); the two worlds need their own primitives.

10. Mixing sync and async code

Real systems combine both. From async code, call blocking code with asyncio.to_thread or run_in_executor. From synchronous code, run a coroutine with asyncio.run(), which creates a new loop — but it cannot be called from inside a running loop (a common error in notebooks, where Jupyter already runs one; use await directly there). From another thread, submit a coroutine to a running loop with asyncio.run_coroutine_threadsafe(coro, loop), which returns a concurrent.futures.Future. Frameworks hide much of this: FastAPI runs plain def endpoints in a thread pool and async def endpoints on the loop, which is exactly why a blocking call inside an async def endpoint is so damaging.

Coroutines are generators with a different hat

A coroutine object implements send() and throw() like a generator (py5). When a coroutine awaits something that is not ready, the chain of awaits bottoms out in a Future, which yields itself up through every await to the task driving the coroutine. The task registers a callback on that future and returns control to the loop. When the future completes — because the selector reported the socket ready — the callback schedules the task, which calls coro.send(None) to resume the whole chain exactly where it paused. Cancellation is coro.throw(CancelledError()) at that point. This is why an await on an already-completed awaitable does not yield to the loop at all, and why await asyncio.sleep(0) is the idiom for "let other tasks run now".

Eager tasks and task factories (3.12+)

By default, create_task schedules the coroutine to start at the loop's next iteration. Python 3.12 added asyncio.eager_task_factory: with it, a new task starts running synchronously inside create_task until its first real suspension, and if it finishes without ever suspending (for example, a cache hit), no scheduling happens at all. For workloads with many tasks that often complete immediately, this measurably reduces overhead. Since 3.14, create_task passes arbitrary keyword arguments through to the task factory, so custom factories can accept extra metadata.

How asyncio talks to the operating system

On Linux and macOS the default loop uses the selectors module over epoll or kqueue: sockets are non-blocking, the loop registers interest in readability or writability, and the selector call blocks until something is ready or a timer is due (net13 covers readiness-based I/O). On Windows the default is the ProactorEventLoop over IOCP, which is completion-based: the loop submits a read and is told when it has finished. Disk files are not supported by readiness APIs, so asyncio's file-like operations and to_thread use threads for disk I/O. uvloop, a drop-in loop built on libuv, is commonly used in production for 2-4× lower loop overhead.

Thread-pool sizing and the GIL

For I/O-bound threads, the right pool size is set by the downstream resource and by latency: to sustain R requests per second with a latency of L seconds, you need about R × L in flight (Little's law). CPU-bound threads are capped by the GIL, so a large pool only adds contention; py8's convoy effect means a CPU-heavy thread also adds latency to I/O threads sharing the GIL. On the free-threaded build (3.14), thread pools can run pure-Python CPU work in parallel, and ThreadPoolExecutor becomes a viable choice for it — provided every shared structure is properly locked.

Processes: sharing without copying

Pickling large NumPy arrays into every task can dominate run time. multiprocessing.shared_memory.SharedMemory (3.8+) creates a named block of memory that several processes can map; wrap it in a NumPy array with np.ndarray(shape, dtype, buffer=shm.buf) and pass only the name between processes. Memory-mapped files (np.memmap) and Arrow buffers serve the same purpose. Worker initializers that load a model once per process, combined with chunksize batching, usually recover most of the theoretical speed-up.

fork, threads and the 3.14 default

fork() copies only the calling thread into the child, but copies the memory of all threads, including any locks they held. If another thread held, say, the logging module's lock or the allocator's lock at the instant of the fork, the child inherits a lock that nobody will ever release and deadlocks the first time it needs it. That is why 3.12 began emitting a DeprecationWarning when forking a process that has other threads, and why 3.14 switched Linux's default start method to forkserver, where children are forked from a helper process started before the application creates threads. Code that relied on children inheriting module-level state modified at runtime must now pass that state explicitly.

Structured concurrency and its origins

Nathaniel J. Smith's essay "Go statement considered harmful" argued that spawning a background task is like a goto: control flow escapes the scope that created it, so errors can be lost and resources outlive their owners. His Trio library introduced "nurseries", scopes that cannot exit until their child tasks finish, and asyncio adopted the idea as TaskGroup in 3.11 along with asyncio.timeout. The practical rule that follows: every task should have an owner that awaits it, and loose create_task calls should be rare, documented, and supervised.

Introspection in 3.14

Python 3.14 added tooling for the hardest asyncio debugging question — "what is every task waiting on?". python -m asyncio ps PID lists the tasks of a running process with their coroutine stacks and awaiter chains, python -m asyncio pstree PID draws the tree of tasks awaiting each other, and asyncio.capture_call_graph()/print_call_graph() produce the same information from inside the program. These rely on 3.14's safe external debugger interface (PEP 768).

The blocked event loop

The most common asyncio incident is a latency spike across all endpoints of a service caused by one blocking call: a synchronous SDK call, a requests.get in a helper, a large json.loads, a CPU-heavy tokenisation step, or logging to a slow disk. Symptoms: p99 latency jumps for everything, including the health check, while CPU is low. Detection: event-loop lag metrics (a heartbeat measuring its own lateness), asyncio debug mode's slow-callback warnings in staging, and py-spy dump on a stuck process. Fix: async libraries, to_thread, process pools, and linting with rules such as Ruff's ASYNC family, which flags blocking calls in async functions.

Unbounded fan-out

A batch job that does await asyncio.gather(*[call(x) for x in items]) over a million items creates a million coroutines and, as fast as the loop can go, a million requests. The provider returns 429s, the local process runs out of file descriptors ("Too many open files") or memory, and retries amplify the load. Always bound concurrency with a semaphore or worker pool, respect provider rate limits with a token bucket, and use Executor.map(..., buffersize=) (3.14) or a bounded queue so input is not materialised all at once.

Lost exceptions

Background tasks created with create_task and never awaited, thread-pool futures never collected, and gather without handling the first exception all lose errors. The only trace may be a "Task exception was never retrieved" message at garbage collection, if that. Use TaskGroups, collect every future's result, and add a done-callback that logs failures for intentionally detached tasks.

LLM applications: concurrency patterns

Typical AI workloads are almost pure I/O: calls to model APIs, embedding services and vector stores. Good patterns: an async client shared per process; a semaphore sized to the provider's concurrency limit; per-call timeouts plus an overall deadline for the user request; retries with exponential backoff and jitter on 429 and 5xx responses; streaming responses back to users as tokens arrive (py5); and batching (sending 100 texts per embedding request) wherever the API supports it, which usually beats higher concurrency for throughput and cost. Retrieval, tool calls and reranking that do not depend on each other should run concurrently in a TaskGroup rather than one after another.

Process pools in data pipelines

Feature engineering and pre-processing in pure Python are the classic candidates for process pools. Common production problems: pickling a large DataFrame into every task (use shared memory, memory-mapped files, or have workers read their own partition from storage), forgetting the __main__ guard (children re-execute the script), and worker processes silently killed by the OOM killer, which surfaces as BrokenProcessPool. Size the pool below the core count if the machine also runs other services, and set max_tasks_per_child (3.11+) to recycle workers that leak.

Graceful shutdown

Deployments restart processes constantly. A service should stop accepting work on SIGTERM, let in-flight tasks finish within a deadline, cancel the rest, and close pools and clients. asyncio.run cancels remaining tasks on exit; worker loops should treat CancelledError as "finish or checkpoint the current item and stop". Thread pools and process pools should be shut down with shutdown(wait=True, cancel_futures=True) (3.9+), and queue.Queue.shutdown() (3.13+) unblocks threads waiting on a queue.

(1) requests.get is blocking: inside a coroutine it freezes the event loop for the duration of every request, so no other task in the process runs, and because nothing is started concurrently the loop is fully sequential — about 10,000 × latency. Use an async client, run the requests concurrently, and bound the concurrency:

import asyncio, httpx

async def fetch_all(urls, limit=100):
    sem = asyncio.Semaphore(limit)
    async with httpx.AsyncClient(timeout=10) as client:
        async def one(u):
            async with sem:
                r = await client.get(u)
                r.raise_for_status()
                return r.json()
        async with asyncio.TaskGroup() as tg:
            tasks = [tg.create_task(one(u)) for u in urls]
    return [t.result() for t in tasks]

One shared client reuses connections (a connection pool); the semaphore protects the target service and your file descriptors; the timeout stops one hung server from holding a slot forever. Decide the failure policy explicitly: TaskGroup cancels everything on the first error, which suits "all or nothing"; gather(..., return_exceptions=True) suits "take what succeeded". For 10,000 URLs, also consider retries with backoff for transient errors.

(2) Three seconds of pure-Python CPU work on the event loop blocks every other request the server is handling for three seconds. Move it off the loop: await loop.run_in_executor(process_pool, compute_heavy_model, data), with a process pool created once at start-up, because the work is CPU-bound pure Python and a thread would still hold the GIL.
