A hardware shop's support site has 40,000 help articles. A customer types portable solar charger won't charge. Somewhere in those articles is a short troubleshooting page titled "Solar charger not charging: four checks", and also a 3,000-word buying guide that mentions "solar" forty times and "portable" twenty times but never discusses a fault. Which should come first? Obviously the troubleshooting page. Now write a rule a computer can apply in microseconds, across 40,000 articles, that gets it right.

The first rule everyone writes is "count the query words in each document": the buying guide wins by a mile, because it is long and repetitive. The second rule is "weight rare words more": better, but the guide still wins on sheer count. The third rule, which took the field roughly two decades of experiments to settle, is BM25: weight rare words more, let repeated mentions count less and less, and judge counts relative to how long the document is. It is still, in 2026, the default scoring function in Elasticsearch, OpenSearch and Lucene, and the keyword half of nearly every hybrid search and RAG system.

The scoring formula is half the story. The other half is the data structure that makes it fast: you cannot read 40,000 articles per query, let alone 40 billion web pages. The inverted index, a map from each word to the documents containing it, lets a query touch only the few lists it needs. And before either can work, text must be turned into comparable units: is "Charger" the same as "charger"? Is "charging"? Is "e-mail" one term or two?

This lesson builds keyword search from the bottom: analysing text into terms, the inverted index and how it is compressed and updated, TF-IDF, BM25 derived piece by piece and worked by hand for one query and two documents, how engines find the top 10 without scoring every match, fields and phrases, and finally the evidence for where lexical search still beats embeddings, and where it loses. lm9 introduced BM25 as one retriever in a RAG pipeline; here we open it up.

Think of the index at the back of a textbook. You do not read the book to find every mention of "photosynthesis"; you look the word up in the index, which lists the pages where it appears, and go straight there. A search engine's inverted index is the same idea taken to the extreme: for every word in every document, a list of the documents (and positions) where it appears. It is called inverted because the documents map words to positions, and the index inverts that into words mapping to documents.

A query then becomes a few lookups. For solar charger, fetch the list for "solar" and the list for "charger", walk them together, and score each document that appears. Scoring answers "how well does this document match?" using three facts per query word: how often it appears in this document (term frequency), how rare it is across all documents (inverse document frequency), and how long this document is compared with the average. Combine these well and you have BM25.

The analogy breaks in two useful places. A book index is curated by a person who knows that "photosynthesis" and "photosynthetic" belong together and that "plant" in a botany book does not mean "factory". A search engine has only rules: an analyser that lowercases, splits and stems text the same way for documents and queries. Those rules decide what counts as "the same word", and many search bugs are analyser bugs. Second, a book index lists every page equally; a search engine ranks, so it needs a theory of which match is better.

It helps to see the three facts as three questions a sensible librarian would ask about each query word. Does this document mention it, and how much? A page that says "charger" once probably touches on chargers; a page that says it six times is probably about chargers; a page that says it sixty times is probably a catalogue or spam, so the evidence should level off. How surprising is a mention? Nearly every page in a hardware help centre says "device", so a match on "device" tells you almost nothing; only a few say "thermocouple", so a match there is strong evidence. How much room did the document have? Three mentions in a ten-line note mean more than three mentions in a forty-page manual. BM25 is nothing more than a careful, tested way of turning those three answers into one number per document and adding them up across the query's words.

Where does this sit in the funnel from rec1? For search, lexical retrieval is usually the most important candidate source: it pulls the top few hundred or thousand documents for the query in a few milliseconds, and the ranker takes it from there, with the BM25 score itself as one of the ranker's features. For recommendation without a query it plays a smaller role, mainly matching item text against a user's interests or powering "search within" features. Either way the mechanics are the same.

With that picture, the rest of the lesson is detail: how the analyser decides what a term is, how posting lists are stored small and read fast, why BM25's formula has the shape it has, and how the engine avoids scoring every one of the possibly millions of documents that contain at least one query word.

1. Analysis: from text to terms

Before anything can be indexed, text is turned into a sequence of terms, the units that will be matched. The component that does this is the analyser, and in Lucene-based engines (Elasticsearch, OpenSearch, Solr) it has three parts that run in order.

Character filters clean the raw string: strip HTML tags, map "&" to "and", normalise Unicode so that "é" written as one code point and as "e" plus an accent mark become identical. The tokeniser splits the string into tokens. The standard tokeniser follows Unicode word-boundary rules: "Solar charger, 20W (USB-C)" becomes Solar, charger, 20W, USB, C. Notice the decisions hidden in that: the hyphen split "USB-C" in two, which helps a search for "usb" and hurts a search for the exact "USB-C". Token filters then transform tokens: lowercasing (solar), removing stop words, and stemming, which chops suffixes by rule so that "charging" and "charged" both become "charg". A stemmer such as Porter's for English is a set of suffix-stripping rules; it is fast and crude. It conflates some unrelated words ("university" and "universe" both become "univers") and misses some related ones: Porter leaves "charger" whole, because its rule for removing "-er" only fires on longer stems, so "charger" and "charging" do not match under it. Lemmatisation uses a dictionary to map words to their base form ("better" to "good") and is more accurate but slower and language-specific.

The cardinal rule: the same analyser must process documents at index time and queries at search time, or terms stop matching. If documents were stemmed to "charg" and the query term stays "charger", the lookup finds nothing. Engines bind an analyser to each field for this reason. Most analyser bugs come from changing the analysis of one side without reindexing the other.

Two choices deserve care. Stop words ("the", "of", "who") used to be removed to save space. Today they are usually kept: BM25 gives them tiny weights anyway (because they appear everywhere, their IDF is near zero), and removing them breaks queries like "The Who" or "to be or not to be". And identifiers such as model numbers, error codes and SKUs are often damaged by language analysers, so it is common to index the same text twice: once with a language analyser for natural-language matching, once with a keyword or whitespace analyser that keeps "ERR_CONN_RESET" or "WH-1000XM5" intact.

2. The inverted index and its posting lists

After analysis, each document is a bag of terms with counts and positions. The index stores, for each distinct term, a posting list: the IDs of the documents containing it, in increasing order, each with the term frequency (tf, how many times the term occurs in that document) and, if phrase search is needed, the positions. The set of all distinct terms is the dictionary (or term dictionary), stored in a structure that supports fast lookup and prefix search; Lucene uses a compact finite-state transducer for it.

Two properties make posting lists fast. First, they are sorted by document ID, so two lists can be intersected (for AND) or unioned (for OR) in a single forward pass, like merging two sorted arrays, and skip pointers let the engine jump ahead in a long list. Second, they compress very well. Instead of storing document IDs, store the gaps between consecutive IDs: the list 3, 7, 21, 22, 150 becomes 3, 4, 14, 1, 128. Gaps are small numbers, and small numbers can be stored in few bits. With variable-byte encoding, each number uses as many 7-bit groups as it needs: the first four gaps fit in one byte each and 128 needs two, so the list takes 6 bytes instead of 20 as 32-bit integers. Modern engines pack blocks of 128 gaps using the minimum bit width that fits the block, which is even tighter and decodes with vector instructions.

A rough sense of scale: for typical English text, the posting lists for a collection are a fraction of the size of the original text (positions add substantially more), and a common term's list may hold millions of entries while most terms' lists hold a handful. That skew, a few huge lists and a long tail of tiny ones, is a fact the top-k algorithms below exploit.

The document text itself lives elsewhere, in stored fields, read only for the final 10 or 20 results to display titles and snippets. Keeping it out of the posting lists is why a query reads kilobytes, not the collection.

3. Building and updating an index: segments

Posting lists are sorted and compressed, which makes them expensive to edit in place: inserting one document ID in the middle of a compressed block means rewriting the block. Lucene's answer, used by Elasticsearch and OpenSearch, is to never edit. New documents accumulate in an in-memory buffer; periodically the buffer is written out as a new, small, immutable segment, a complete mini-index with its own dictionary and posting lists. A search runs over every segment and merges the results. Deleting a document only sets a bit in a per-segment "deleted documents" bitmap; an update is a delete plus an insert.

This design trades write cost for read cost. Many small segments mean many lookups per query, so a background merge process continuously combines small segments into larger ones, dropping deleted documents as it goes. The moment a buffer is written as a segment and made searchable is a refresh; in Elasticsearch the default refresh interval is one second (for indices that are being searched), which is why it is called near-real-time search: a newly indexed document is typically visible within a second, not instantly. Bulk loads go faster with refresh disabled, because fewer, larger segments are written.

4. TF-IDF: the first good idea

Now scoring. Take the help-article example with a collection of N = 1,000 documents and an average length of 100 terms. The query, after analysis, is three terms: portable, solar, charger. Their document frequencies (n, the number of documents containing each) are: portable 200, solar 20, charger 50.

Two documents are candidates. Document A is a short troubleshooting page, 80 terms long, containing solar twice, charger once and portable once. Document B is a long buying guide, 300 terms long, containing solar 4 times, portable 3 times and charger not at all. A person would rank A first: it matches every query word and is about exactly this.

The first idea is term frequency: more mentions, more relevant. The second is that not all terms are equal: matching "solar", which is in 2% of documents, is much stronger evidence than matching "portable", in 20%. Inverse document frequency captures this. The classic form is idf = ln(N / n): solar ln(1000/20) = ln 50 = 3.91, charger ln(20) = 3.00, portable ln(5) = 1.61. TF-IDF sums tf × idf over the query terms:

  • A: 2 × 3.91 + 1 × 3.00 + 1 × 1.61 = 12.43
  • B: 4 × 3.91 + 0 + 3 × 1.61 = 20.48

TF-IDF ranks the buying guide first, by a wide margin. Two defects cause it. Term frequency grows linearly, so B's fourth "solar" counts as much as A's first, though the fourth mention adds far less evidence that the page is about solar. And there is no notion of length: B has more mentions largely because it has more words. TF-IDF as a family also includes vector-space variants that normalise documents to unit length with cosine similarity, which addresses length crudely, but the linear growth of term frequency remains.

5. BM25, piece by piece

BM25 ("Best Match 25", from Robertson and colleagues' Okapi experiments of the 1990s) keeps the TF-IDF skeleton, a sum over query terms of a rarity weight times a frequency factor, and repairs both defects. For a query q and a document d:

score(q, d) = Σ over terms t in q:  idf(t) × f / (f + K)
    where  f = tf of t in d
           K = k1 × (1 − b + b × len(d) / avgdl)
           idf(t) = ln(1 + (N − n + 0.5) / (n + 0.5))

This is the form Lucene uses since version 8.0. The textbook form multiplies each term's contribution by (k1 + 1); Lucene removed that factor (issue LUCENE-8563) because it is the same constant for every document and so cannot change the ranking. Scores from different versions are therefore not directly comparable, but orders are identical.

Saturation. Look at f / (f + K) with K fixed at 1.0. One mention gives 0.50, two give 0.67, four 0.80, eight 0.89, sixteen 0.94. The factor approaches 1 but never exceeds it: the first mention is worth half the maximum, and each doubling adds less. The parameter k1 sets the speed: small k1 saturates almost immediately (any mention is nearly as good as many); large k1 lets frequency keep mattering for longer. The default is 1.2.

Length normalisation. K is not fixed: it is k1 scaled by how long the document is compared with the average. With b = 0.75 and avgdl = 100, a 50-term document gets K = 1.2 × (0.25 + 0.75 × 0.5) = 0.75; a 100-term document K = 1.2; a 300-term document K = 1.2 × (0.25 + 2.25) = 3.0. A larger K means each mention is worth less: a long document needs more mentions to earn the same factor. The parameter b (0 to 1) sets how much length matters: b = 0 ignores length (K = k1 always), b = 1 fully normalises by it. The default is 0.75.

The IDF is the probabilistic form from Robertson and Spärck Jones, with the "1 +" inside the logarithm added by Lucene so it never goes negative. For our terms: solar ln(1 + 980.5/20.5) = 3.888; charger ln(1 + 950.5/50.5) = 2.987; portable ln(1 + 800.5/200.5) = 1.608. A term in all 1,000 documents gets ln(1 + 1.5/1000.5) ≈ 0.0015, effectively nothing; a term in one document gets about 6.5.

6. The worked example, by hand

Use k1 = 1.2, b = 0.75, N = 1,000, avgdl = 100.

Document A (80 terms): K = 1.2 × (0.25 + 0.75 × 80/100) = 1.2 × 0.85 = 1.02.

  • solar, f = 2: 2 / (2 + 1.02) = 0.662; × 3.888 = 2.575
  • charger, f = 1: 1 / 2.02 = 0.495; × 2.987 = 1.479
  • portable, f = 1: 0.495 × 1.608 = 0.796
  • Total: 4.850

Document B (300 terms): K = 1.2 × (0.25 + 0.75 × 3) = 1.2 × 2.5 = 3.00.

  • solar, f = 4: 4 / 7 = 0.571; × 3.888 = 2.222
  • charger, f = 0: 0
  • portable, f = 3: 3 / 6 = 0.500; × 1.608 = 0.804
  • Total: 3.026

BM25 ranks A first, 4.85 to 3.03, reversing TF-IDF. Read the arithmetic for the reasons. B's four mentions of "solar" earn 2.22, less than A's two mentions (2.58), because B is three times as long as average, so its K is three times larger and each mention is diluted. And A gets 1.48 for "charger" that B cannot earn at all: covering all the query's terms beats repeating some of them, because each term's contribution is capped. (With the textbook (k1 + 1) factor every number above is multiplied by 2.2, giving 10.67 and 6.66; the order is the same.)

7. Query processing: from posting lists to the top 10

A query's terms each have a posting list. The engine must combine them and return the best k documents (k = 10, or 1,000 if this is a candidate source feeding a ranker). There are two classic strategies. Term-at-a-time processes one term's whole list, adding its contributions into an accumulator per document, then the next term's list. Document-at-a-time walks all lists in parallel in document-ID order, so each document's full score is computed in one go and can be compared with a min-heap holding the best k so far. Document-at-a-time uses little memory and is what modern engines use.

The naive version scores every document that contains any query term. For a query with a common word, that can be millions. WAND ("weak AND", Broder and colleagues, 2003) avoids most of that work. For each term, precompute an upper bound: the highest contribution that term can give any document (its IDF times the maximum of the frequency factor). Once the heap holds k documents, its smallest score is the threshold θ a new document must beat. Walking the lists, WAND asks for each candidate document: could the terms it contains possibly add up to more than θ, using their upper bounds? If not, skip it without scoring, and skip ahead in the lists. Rare terms have high bounds and short lists; common terms have low bounds and long lists, so documents that contain only common terms are skipped in bulk.

Block-max WAND refines this by storing an upper bound per block of 128 postings rather than one per list, which is much tighter (a block of postings for short documents with tf = 1 has a lower maximum than the list's global maximum) and lets the engine skip whole blocks. Lucene implements block-max WAND, used when the exact count of matching documents is not needed. That is why Elasticsearch returns hit counts as "10,000+" by default: counting every match exactly would require visiting every match, which defeats the skipping.

The query structure matters too. A plain multi-term query is an OR with scoring: a document matching any term is a candidate, and matching more terms scores more. Users rarely want strict AND for long queries, because one unmatched word would drop a perfect document; a common middle ground is a "minimum should match" rule such as "at least 2 of 3 terms" or "75% of terms".

8. Fields, phrases and proximity

Real documents have fields: title, body, tags, brand, anchor text from links pointing at the page. A match in the title is stronger evidence than one in the body. The naive approach scores each field with BM25 and adds the scores, perhaps with weights. That over-rewards a term appearing in both title and body, because each field saturates separately, so the term gets two nearly-full contributions. BM25F (Robertson, Zaragoza and Taylor) fixes this: multiply each field's term frequency by a field weight (title × 3, say), length-normalise per field, add them into one pseudo-frequency, and saturate once. Elasticsearch's combined_fields query follows this idea; its multi_match with best_fields instead takes the best single field's score.

Phrase queries such as "solar charger" (in quotes) require the terms to be adjacent and in order. They need positions in the posting lists: after finding documents containing both terms, check whether some position of "charger" equals a position of "solar" plus one. A slop parameter allows a few words between them. Positions are costly: they often double or triple the index size, and phrase checks are slower than term lookups. Proximity scoring, a bonus when query terms appear close together even without quotes, is a cheaper signal that many engines add, because "solar ... charger" in one sentence is stronger than the two words five paragraphs apart.

9. Evaluating and tuning lexical retrieval

How do you know the analyser and parameters are good? Build a set of real queries with judged relevant documents (ev6 and rec8 cover labelling and metrics; for now, the metric is the share of queries whose relevant documents appear near the top). Then tune: try k1 from 0.6 to 2.0 and b from 0.3 to 0.9 per field, compare analysers (stemmed versus not, with and without a synonym list) and field weights. Lexical retrieval is cheap to tune because nothing needs to be retrained: a parameter change takes effect immediately (k1 and b apply at query time in Lucene; analysers need a reindex).

Look at failure categories, not just averages: zero-result queries (often analyser or spelling problems), queries where the right document exists but ranks below 10 (often a field-weight or length-normalisation problem), and queries whose words simply are not in the relevant documents (vocabulary mismatch, which no BM25 tuning can fix: that is what synonyms, query expansion and dense retrieval are for, rec5).

10. Filters and structured constraints

Product and job search queries are rarely pure text. A shopper types "running shoes" and ticks "size 42", "under 100 euros" and "in stock". These constraints are not relevance signals to be traded off; a size-41 shoe is simply not an answer. Engines therefore separate queries, which score, from filters, which only include or exclude. In Elasticsearch a bool query has must and should clauses that contribute to the score and filter clauses that do not.

Filters are cheap for two reasons. They do not need scoring, so the engine only checks membership. And they repeat across queries ("in stock" is part of half of all product searches), so engines cache a filter's result as a bitset, one bit per document in a segment, set when the document passes. A 10-million-document segment needs 10 million bits, 1.25 MB, and intersecting the bitset with posting lists is very fast. Numeric ranges such as price use a different structure (Lucene uses block k-d trees, called points) that finds all documents in a range without walking every value.

Filters interact with the funnel in the way rec1 described: apply them inside retrieval whenever possible, so the top 1,000 candidates are all eligible. Lexical retrieval is good at this because the filter and the text match are evaluated in the same pass over posting lists. Approximate vector search is not naturally good at it, which is one of the reasons db15 spends a whole section on filtered vector search, and one reason keyword search remains attractive for heavily filtered catalogues.

11. BM25 as a candidate source and as a feature

In a modern search stack BM25 rarely decides the final order. It plays two other roles. As a candidate source, it retrieves the top 500-2,000 documents for the query, quickly and with high recall for queries whose words appear in the relevant documents. Recall at that depth is what matters, not whether the very best document is first; a learned ranker will reorder them. Tuning a lexical source for this role means looking at recall@1000 rather than nDCG@10, and often using a looser "minimum should match" so that documents matching only some of a long query's words still enter the pool.

As a feature, the ranker receives BM25 scores per field (title, body, brand), the number of query terms matched, whether the full query appears as a phrase, and the proximity of the matches. These are among the strongest features in most search rankers, because they tell the model how literally the document answers the query, something an embedding similarity blurs. Logging these features at serving time is essential: recomputing them later for training data gives slightly different values once the index has changed, which is a form of the training/serving skew that rec9 covers.

12. Where lexical wins, and where it loses

Lexical retrieval matches symbols, not meaning, and that is both its strength and its weakness. It is strong when the query contains rare, specific strings that must appear in the answer: product codes ("WH-1000XM5"), error messages, function names, legal citations, people's and places' names, newly coined words. A term seen in few documents gets a high IDF and pulls exactly those documents up. It needs no training, handles a new document the second it is indexed, works in any domain without adaptation, is cheap, and can explain itself ("matched 'solar' in the title").

It is weak when the relevant document uses different words: "money back" against "refund policy", "laptop won't turn on" against "notebook power failure", a question in Spanish against an answer in English. This vocabulary mismatch is the reason dense retrieval exists. It also cannot tell that a page about "Java the island" is not about "Java the language" except through co-occurring words.

The evidence for "lexical still wins on some queries" is strong. The BEIR benchmark, described in the production section, found that on average across 18 diverse datasets, BM25 beat most neural retrievers trained on a single large dataset, though not the expensive re-ranking approaches. In product search, a large share of queries contain a brand or model number. The practical conclusion is hybrid retrieval, both kinds of retriever with fused results, which is rec5's subject.

Where BM25 comes from

BM25 is not an ad hoc formula; it approximates a probabilistic model. The Robertson–Spärck Jones framework asks: given a document's features, what are the odds it is relevant? Assuming terms are independent and, in the absence of relevance information, that relevant documents are a small fraction of the collection, the log-odds contribution of a term reduces to something close to ln((N − n + 0.5)/(n + 0.5)), the IDF. For term frequency, Robertson modelled occurrences as a mixture of two Poisson distributions (documents "about" the term, where it occurs often, and others, where it occurs incidentally); the exact form is unwieldy, but its shape is a curve that rises and saturates, which f/(f + K) mimics with one parameter. Length normalisation came from the observation that long documents are long either because they are verbose (same content, more words) or because they cover more topics; b interpolates between those two hypotheses. Knowing this helps in interviews: k1 and b are not magic numbers but knobs on modelling assumptions.

Why the IDF needs the "1 +"

The raw Robertson–Spärck Jones IDF, ln((N − n + 0.5)/(n + 0.5)), becomes negative when a term appears in more than half the documents. A negative weight means matching the term lowers the score, which can make a document that matches more query words rank below one that matches fewer. Lucene adds 1 inside the logarithm, ln(1 + (N − n + 0.5)/(n + 0.5)), keeping weights positive and making very common terms count for almost nothing rather than less than nothing.

Statistics are per shard

IDF and average document length are computed from the statistics the engine has at hand, which in a sharded index is the shard (and in Lucene, the set of segments in that shard, including deleted documents not yet merged away). If routing puts all of one customer's documents on one shard, a term common for that customer looks common there and rare elsewhere, and the same document would score differently on different shards. For large, randomly routed shards the differences are negligible. Elasticsearch's dfs_query_then_fetch gathers global statistics in a first round trip for exact scores, at extra latency. Deleted-but-unmerged documents also skew statistics slightly until merges catch up, a known source of score drift after heavy updates.

Document length is stored approximately

To keep the index small, Lucene does not store each document's exact length for scoring; it stores a "norm" in a single byte, an encoding that is exact for short lengths and increasingly approximate for longer ones. Two documents of 1,000 and 1,030 terms can therefore share the same length value. This rarely matters for ranking, but it explains why hand-computed BM25 scores for long documents differ slightly from what the engine reports, a common source of confusion when debugging with the explain API.

Dynamic pruning and its trade-offs

WAND-style pruning is "safe": it returns exactly the same top k as exhaustive scoring, only faster, because it skips only documents proven unable to enter the heap. Its speed depends on the threshold rising quickly: once the heap holds strong documents, most others are skipped. Queries with many common terms and no rare ones prune poorly. Unsafe variants trade a little accuracy for more speed, for example by inflating the threshold. Separately, some systems order posting lists by a static quality score (impact-ordered or score-at-a-time indexes) so the best documents are met first and the search can stop early; web search engines have used tiered indexes, where a small top tier of high-quality documents is searched first and the full index only if needed.

Learned sparse retrieval: lexical machinery, learned weights

An interesting middle ground between BM25 and embeddings keeps the inverted index but learns the term weights with a neural model. Document expansion models such as docT5query generate likely queries for each document and append them to its text before indexing, adding vocabulary the author did not use; in BEIR it averaged 1.6% above BM25. Models such as SPLADE output a weight for every vocabulary term for each document and query, so "refund" can receive weight for a document that only says "money back". These run on ordinary inverted-index engines, keep exact-match strengths, and close part of the vocabulary gap; their cost is a model at indexing time (and for SPLADE, at query time) and larger posting lists.

Relevance is not only text match

A web or product search engine that ranked purely by BM25 would be easy to manipulate (stuff the page with keywords) and blind to quality. Text-match scores therefore become one feature among many for the learned ranker (rec6, rec7): along with static quality signals (link-based scores such as PageRank for the web, ratings and sales for products), freshness, click history and personalisation. BM25's job in a modern stack is mainly candidate generation and a strong feature, not final ordering.

The public case: BEIR and the robustness of BM25

In 2021 Thakur and colleagues released BEIR, a benchmark of 18 publicly available retrieval datasets across 9 task types (question answering, fact checking, argument retrieval, duplicate-question detection, bio-medical and financial search, news, entity retrieval and more), with corpora from 3.6 thousand to 15 million documents. They evaluated ten systems in a zero-shot setting: models trained on one large dataset (mostly MS MARCO, a web question collection) and then tested on the others without further training, which is the situation of most companies adopting an off-the-shelf model.

The findings, measured by nDCG@10 (a ranking metric, rec8), were striking for the time. Compared with BM25's average, the dense retriever DPR scored 47.7% lower, ANCE 7.4% lower and TAS-B, the best dense model, 2.8% lower. The late-interaction model ColBERT was 2.5% higher, document expansion with docT5query 1.6% higher, and BM25 retrieval followed by a cross-encoder re-ranker was 11% higher, the best overall, at a much higher computational cost. The authors' conclusion: "BM25 remains a strong baseline for zero-shot text retrieval", and dense models "can substantially underperform" it outside their training domain.

Two caveats keep the case honest. The paper itself warns of a lexical bias in some datasets: relevance judgements were often made on documents found by lexical systems, so documents only a dense model would retrieve may never have been judged, which understates dense retrieval. And embedding models have improved a great deal since 2021, trained on much broader data; recent general-purpose models report averages above BM25 on BEIR. What has not changed is the shape of the failures: dense models still stumble on exact identifiers and unseen vocabulary, and BM25 still cannot bridge paraphrase. That complementary pattern is why production search runs both.

How lexical search fails in production

Analyser drift. Someone adds a synonym filter or switches the stemmer on the index side without reindexing old documents, or only on the query side. Symptom: zero-result rate jumps for a class of queries. Monitor zero-result and low-result rates per query category after every analyser change, and reindex fully when index-side analysis changes.

Identifier mangling. A standard tokeniser splits "WH-1000XM5" into "wh", "1000xm5"; a search for the full model returns the right product but also many partial matches, or misses it when users type "WH1000XM5". Fix with a dedicated keyword field, normalisation that strips hyphens and spaces from codes, and n-gram fields for partial codes.

Too many small segments. High update rates with a one-second refresh create many tiny segments; query latency rises until merges catch up. Symptoms: p99 latency climbing during heavy indexing. Lengthen the refresh interval for indices that do not need near-real-time visibility, and watch segment counts.

Score drift after mass deletes. Deleting a large share of documents without merges leaves statistics that still count them, so IDF is off until segments merge. Rankings shift subtly; usually harmless, occasionally visible in tests that compare exact scores.

Keyword stuffing and spam. Any pure text-match signal invites manipulation. Sellers repeat brand names in descriptions to appear in other brands' searches. BM25's saturation limits the gain from repetition, but cross-brand stuffing needs explicit detection and quality features in the ranker.

What to monitor and tune

Zero-result rate, result count distribution, click-through on the first page, and reformulation rate (users rephrasing their query immediately), all sliced by query type: navigational ("nike air max 90"), identifier, natural-language question, short head queries versus long-tail queries. Latency percentiles of the search cluster with segment counts and merge activity. For tuning, a labelled query set re-run on every analyser or parameter change, reporting nDCG@10 and recall@100 per slice, because a change that helps natural-language queries often hurts identifier queries.

Diagnose: search got worse after an "improvement"

A documentation site (60,000 pages, Elasticsearch) changed its analyser from "standard" to "english" (which adds English stemming and stop-word removal) to help natural-language questions, and reindexed. A week later, support tickets say searches for configuration keys such as max-connections and keep-alive-timeout return worse results, and the query "is not null check" returns the same pages as "null check". Click-through on the first result fell from 41% to 35% for queries containing a hyphenated key or a negation. Explain the causes and propose a fix.

Answer

Causes. First, the english analyser's stop-word list includes "is" and "not", so "is not null check" becomes "null check": the negation, the word that defines the query, is gone. Second, the standard tokeniser (shared by both analysers) splits max-connections at the hyphen into "max" and "connections", which are common words with low IDF, and the English stemmer then reduces "connections" to "connect", so the key matches every page about connecting. (Underscored keys such as max_connections survive, because Unicode word-break rules keep letters joined by an underscore in one token, which is why only hyphenated keys regressed.) Before the change there was no stemming and no stop-word removal, so the hyphen split hurt less.

Fix. Index the content into multiple fields: body.en with the english analyser (for natural-language questions), body.exact with the standard analyser and no stop-word removal, and an identifiers field built from code blocks and headings with a custom analyser (a whitespace or pattern tokeniser) that keeps tokens like max-connections whole and also emits sub-tokens split on hyphens, underscores and camel case. Query all three with a combined scoring approach (BM25F-style via combined_fields, or a weighted bool query), weighting exact and identifier matches above stemmed matches. Keep stop words in the exact field so negations like "is not" survive.

Verify. Build a labelled set of 200 queries split by type (identifier, natural-language, phrase-like). Report nDCG@10 per type for the old analyser, the english analyser and the multi-field design; ship only if no type regresses. Track first-result click-through per type for two weeks after launch.
