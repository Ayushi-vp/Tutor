A team decides to improve its coding model with reinforcement learning. The algorithm is the easy part: GRPO is a few hundred lines in an open-source trainer (rs4). Then come the questions nobody warned them about. Where do the tasks come from, and how hard should they be? Does the model get one shot or can it run the tests and try again? Who runs the tests, in what sandbox, with what timeout? What if the model's code deletes the tests, or exits before they run, or recognises the three visible inputs and hard-codes the outputs? How do you score a solution that passes 9 of 10 tests? And when each episode involves twenty tool calls that take seconds each, how do you keep a cluster of GPUs busy instead of waiting?

All of these are questions about the environment, and in modern RL for LLMs the environment is where most of the engineering and most of the failures live. The reasoning models of 2025–26 were trained against environments: maths problems with answer checkers, programming problems with test suites, puzzles with verifiers, agent tasks with sandboxes and simulated users. A model can only learn what its environments reward, and it will learn to exploit anything they reward by mistake (rs10). Environments have become a product category: libraries, hubs of shared environments, and companies that build and sell them.

For an AI engineer this is practical knowledge. Teams fine-tuning models for agentic products increasingly build their own environments from their tools and data. Interviewers at labs ask candidates to design an environment and its verifier, and then ask how they would break it. And evaluating agents (ag12) uses the same machinery: an evaluation is an environment you do not train on.

This lesson defines an environment for an LLM and its parts, surveys the libraries that package them, and then works through verifiers by domain: maths, sandboxed code tests, tool use and multi-turn agent tasks. It compares partial credit with binary rewards through a GRPO example, catalogues verifier exploits and how to harden against them (the lab builds a toy code verifier, hardens it, and shows it can still be beaten), explains why environment diversity matters, and ends with the infrastructure for agentic RL at scale: rollout systems, sandboxes and asynchronous actors.

One framing ties it together: an environment is a specification of what you want, written as code. Everything you leave out of that specification (that the solution should be general, that the tests should not be touched, that the answer should be one number) is something the optimiser is free to ignore. Writing environments is therefore closer to writing contracts or security policies than to writing datasets, and it rewards the same habits: being explicit, anticipating adversaries and testing the edge cases.

An analogy: a driving test centre

Think of an RL environment as a driving test centre. The centre chooses routes for each candidate, easy or hard (the task sampler). It defines what a candidate may do: drive, signal, ask the examiner a question, but not take the wheel from the examiner (the interaction protocol). The car, the roads and the traffic are the state, reset between candidates. And the examiner decides pass or fail, sometimes with marks for each manoeuvre (the verifier and the reward). A training school that wants to improve its pupils' pass rate sends them through test after test and adjusts its teaching to what the examiner rewards.

The analogy is useful because it shows where things go wrong. If the examiner only checks that the car ends up in the right car park, pupils learn to get there by any route, including over the pavement. If the test routes are always the same three, pupils memorise them. If the examiner can be distracted, pupils learn to distract. Where the analogy breaks is scale and adversarial pressure: a model takes millions of tests, and RL is an optimiser that will find every weakness in the examiner, not a pupil who mostly tries to drive well.

The loop

Single-turn, multi-turn, agentic

Environments range from simple to elaborate. A single-turn environment gives a prompt and scores one response: a maths problem with an answer checker. A multi-turn environment lets the model act several times, receiving feedback: running code and seeing test output, asking a simulated user a question. An agentic environment gives the model tools that change persistent state (a repository, a database, a browser) over many steps, and scores the final state. Each step up adds realism and engineering cost: sandboxes, state resets, slower episodes and more places for exploits.

Who builds environments, and why it became a market

In 2024 most RL for LLMs used preference data and a reward model (lm6). Reasoning models shifted the effort toward verifiable tasks, and agentic models toward interactive environments with tools and state. Each environment needs task collection, a verifier, a sandbox, tests of the verifier and ongoing maintenance, so they are expensive to make well. Labs build many internally; open projects publish libraries and hubs (OpenEnv's catalogue, Prime Intellect's Environments Hub, Reasoning Gym's generators); and companies sell environments for specific domains. For an engineer, the useful skill is not knowing any one library but being able to specify the four parts for a new task and to break the verifier before the model does.

A reader who stops here should remember: an environment is a task sampler, an interaction protocol and a verifier around a sandboxed state; the verifier defines what the model learns; and agentic environments are mostly an infrastructure problem.

1. What an environment is, in RL terms

Map the classic RL vocabulary (rs3) onto LLMs. The state is everything the model can observe plus anything hidden that affects outcomes: the conversation so far, files in a sandbox, a database, the hidden goal of a simulated user. An action is a model output: a whole response in single-turn settings, or a message or tool call in multi-turn ones. A transition is what the environment does in reply: run the tool, return its output, advance the user simulator. An episode runs from reset to a terminal condition (an answer, a stop action, a turn limit, a timeout). The reward is computed by the verifier, usually once at the end (outcome reward), sometimes at checkpoints along the way.

Libraries make this concrete. OpenEnv (originally from Meta's PyTorch team, now under Hugging Face, version 0.8 on PyPI in October 2026) exposes every environment through the familiar Gymnasium-style calls: reset() to start an episode, step(action) to act and receive an observation and reward, and state() to inspect it, over a WebSocket, with each environment packaged as an isolated Docker image that can run locally, in a cloud sandbox or as a Hugging Face Space; its catalogue lists 40+ environments, from games and coding sandboxes to browsers and simulators, with rubric-based rewards and integrations for TRL and other trainers. Prime Intellect's verifiers library (0.3) organises the same ideas around tasksets (task data plus lifecycle hooks), harnesses (the program the model runs in, such as a coding agent), agents (harness × model × runtime policy) and traces (the message graph, rewards, metrics and per-call records), with a hub of community environments. The vocabulary differs; the parts are the same.

2. The task sampler

The sampler decides what the model practises. Sources: curated datasets (competition maths, programming problems with tests, question-answer sets), problems mined from real usage, and procedural generators that create unlimited instances with known answers. Reasoning Gym, for example, provides over 100 generators with verifiers across algebra, arithmetic, logic, graph theory, geometry, cognition tasks and games, each with adjustable difficulty, so a sampler can generate fresh problems at exactly the level the model needs.

Difficulty control matters because of how group-based RL learns (rs4, rs9): if all samples for a task succeed or all fail, the advantages are zero and the episode is wasted. A sampler can track each task's recent pass rate and prefer tasks in a middle band, raise generator difficulty as the model improves, and retire tasks the model always solves. The sampler is also where decontamination (no evaluation problems), deduplication and balance across domains are enforced.

3. Verifiers for maths

A maths verifier has three steps. Extract the final answer from the response with a strict rule: the content of exactly one final \boxed{}, or a required "Answer:" line. Zero reward if there is no answer or more than one, which closes the hedging exploit from rs10 ("the answer is 41 or 42"). Normalise: strip whitespace and LaTeX formatting, convert \frac{1}{2}, 1/2 and 0.5 to a canonical form, handle units, percentages and thousands separators. Compare with the reference using symbolic equivalence (expressions equal after simplification), set and interval equality, and numeric tolerance for decimals. Hugging Face's Math-Verify library implements this pipeline; its documentation shows verify(parse("${1,3} \cup {2,4}$"), parse("${1,2,3,4}$")) returning True, and notes that the order of gold and prediction arguments matters.

Two practical lessons. A verifier that is too strict rejects correct answers written differently, which teaches the model that correct reasoning fails and quietly stalls learning on exactly the hardest problems; audit rejected answers. A verifier that is too lenient accepts wrong answers that look similar; audit accepted ones. DAPO's choice to transform its dataset so every answer is an integer (rs9) is the extreme fix: change the tasks so verification is trivial.

4. Verifiers for code: sandboxed tests

Code tasks are rewarded by running tests. The naive implementation, appending assertions to the candidate's code, running it, and rewarding exit code 0, is the one RL breaks first. The lab runs six candidates for "sort a list" through two verifiers:

CandidateNaive verifier (asserts in process, exit code 0)Hardened verifier (subprocess, serialised outputs, hidden inputs)
Honest sorted(xs)11
Wrong (returns input)00
sys.exit(0) at import10
Equality override (__eq__ returns True)10
Special-cases the two visible inputs10
Infinite loop0 (timeout)0 (timeout)

The hardened verifier differs in four ways. The candidate's process only computes outputs and prints them as JSON; the comparison happens in the trusted parent process, so overriding equality changes nothing (a list subclass serialises to a plain list). It requires exactly one result line and a zero exit code, so exiting early yields no result. It uses 20 hidden, randomly generated inputs as well as the visible ones, so a lookup table of visible cases fails. And it enforces a timeout. Yet the lab's final step shows it can still be beaten: the harness code that calls solve runs in the same interpreter namespace as the candidate, so a candidate that defines its own list function, which the harness calls on each result, can sort the output on the way out while solve does nothing. The general rule: no verification logic should execute where the candidate controls the names, imports or built-ins. Production systems load the candidate as a module in a fresh interpreter, call a single entry point through a fixed, minimal driver, and do everything else in a separate process.

The rest of the hardening checklist: run in a sandbox with CPU, memory and wall-clock limits, no network and a throwaway filesystem (ag9); keep test files out of the candidate's reach or mounted read-only, and re-check their integrity after the run; prefer hidden and randomised tests, and property-based checks ("the output is sorted and a permutation of the input") that cannot be satisfied by memorising cases; count how many assertions actually executed; and treat crashes, timeouts, extra output and modified files as failures.

5. Verifiers for tool use and multi-turn agent tasks

In agentic environments the model acts through tools on persistent state, and the verifier judges outcomes, not transcripts. Patterns:

  • State checks: after the episode, query the database or file system. Did the booking exist with the right dates? Was exactly one refund issued? Were only the expected files modified? This is how τ-bench-style customer-service environments and many tool-use environments score (ag12).
  • Repository tests: SWE-style environments give the agent a repository and an issue, then run the repository's own tests (including hidden ones written for the fix) after the agent finishes.
  • Simulated users: an LLM plays a user with a hidden goal and constraints, revealing information only when asked; reward depends on reaching the goal without violating policy.
  • Checkpoints: long tasks define intermediate milestones that can be checked from state (a file downloaded, a form submitted), giving partial credit and diagnostics. OSWorld 2.0, for example, scores its long workflows with an average of about 27 checkpoints per task.

Two engineering requirements dominate. Determinism: given a seed, the environment should reset to the same state and tools should behave the same, otherwise rewards are noisy. And isolation: one episode must not leak into another, and the agent must not reach the verifier's data, the internet or other tenants' sandboxes unless the task requires it.

6. Partial credit versus binary rewards, worked

Take one hard coding task and a GRPO group of four samples. With a binary reward (all hidden tests pass or not), suppose none passes: rewards 0, 0, 0, 0, mean 0, every advantage 0. The step teaches nothing, and if most tasks look like this early in training, learning barely starts. With partial credit, say the fraction of 10 hidden tests passed, the same samples might score 0.2, 0.4, 0.0 and 0.6. The mean is 0.3; advantages before normalisation are −0.1, +0.1, −0.3 and +0.3; the population standard deviation is about 0.22, so normalised advantages are about −0.45, +0.45, −1.34 and +1.34. The best attempt is reinforced strongly and the worst discouraged.

The price is a new target. Partial credit rewards passing some tests, and the cheapest way to pass some tests is often to handle the easy cases specially. Rubric-based partial credit (points for each requirement met, judged by an LLM) invites satisfying the letter of each item. Practical patterns: use binary final outcomes as the main reward and partial credit only as a curriculum early in training; weight tests so easy ones are worth little; make partial credit depend on checks that are hard to fake (state-based checkpoints rather than self-reported progress); and keep a binary held-out metric to watch for divergence.

Then add defences that work even for exploits you did not anticipate: red-team the verifier by writing adversarial solutions (or asking a strong model to try to pass without solving) before training; include canary tasks that no honest solution can pass, so any reward on them is an alarm (the idea behind ImpossibleBench); monitor the gap between training reward and held-out results, and flag rates from static checks and CoT monitors (rs10); and keep a regression suite of exploits, so a verifier change never reopens an old hole.

8. Environment diversity

Why not train on one good environment for a long time? Because RL learns what its environments reward, narrowly. A model trained only on competition maths gets better at competition maths and may get worse at following instructions; a model trained on one coding harness learns that harness's quirks, including its exploits. Diversity across skills (maths, code, logic, tool use, writing with rubrics), formats (single-turn, multi-turn, agentic), harnesses and difficulty levels pushes toward general strategies, dilutes the value of any single verifier bug, and improves transfer. Public evidence points the same way: Qwen3's reasoning-RL problems were chosen to cover a broad range of sub-domains (rs9), NVIDIA's ProRL attributed its gains partly to a diverse task suite, and the growth of environment hubs (Prime Intellect's Environments Hub, OpenEnv's catalogue) reflects demand for breadth. The cost is engineering: each new environment needs a verifier, a sandbox, tests of its own and maintenance.

9. Agentic RL at scale: rollout infrastructure

In reasoning and agentic RL, generating rollouts dominates cost (rs9). A synchronous system alternates: generate a batch with the current weights, wait for every episode to finish, train, repeat. The wait is the problem: episode lengths are long-tailed, and the slowest few hold the whole cluster idle. Worked example: a batch of 512 prompts × 16 samples is 8,192 episodes; if each agentic episode makes 20 tool calls of about 2 seconds plus model generation, the median episode might take a couple of minutes but the slowest several times longer, and every GPU waits for them.

Three families of fixes have been published. Hybrid engines: verl's HybridFlow design combines single-controller orchestration with multi-controller execution and reshards the actor model between training and generation layouts, reporting 1.53–20.57× throughput improvements over earlier RLHF systems. Partial rollouts: Kimi k1.5 caps the work per iteration and continues unfinished long generations in later iterations, so a few very long samples do not stall a batch. Fully asynchronous systems: AReaL decouples generation from training entirely; rollout workers generate continuously, trainers update whenever a batch is ready, and new weights are pushed to rollout workers by interrupting in-flight generations, discarding their KV caches, recomputing them with the new weights and continuing. Because samples then come from several policy versions, AReaL caps the maximum staleness per batch, prioritises older samples and uses a staleness-aware PPO variant; it reports up to 2.77× faster training than synchronous systems on the same GPUs with matched or better final accuracy.

The picture also shows why the choice depends on episode length variance. If every episode took the same time, synchronous training would waste little and is simpler to reason about: every sample comes from the current policy, and the algorithm is exactly on-policy. Long reasoning chains and agentic episodes have heavy-tailed durations, where a few episodes take several times the median, and that is where asynchrony pays. A practical middle ground, used by several open systems, is bounded asynchrony: let rollout workers run at most one or two policy versions ahead of training, which captures most of the utilisation gain while keeping the off-policy correction small.

For agentic RL, the environment side scales too: thousands of sandboxes that must start quickly (snapshots instead of fresh containers), run tools reliably, and reset deterministically; rate limits on any external services; and full trace logging for debugging and hacking audits. In practice, environment reliability (flaky tools, slow container start-up, nondeterministic tests) often limits throughput and reward quality before GPUs do.

10. A cost model for environments

Environments cost money beyond GPUs, and it pays to estimate it. Take a coding environment where each episode runs the candidate's code and hidden tests in a container for about 20 seconds of CPU time, with 8,192 episodes per training step (512 prompts × 16 samples, as in R1's batches). That is about 164,000 CPU-seconds, roughly 45 CPU-hours per step. Over 1,000 steps it is 45,000 CPU-hours: at an illustrative $0.04 per vCPU-hour, about $1,800 of compute, plus container orchestration, storage for traces and engineering time. For agentic episodes with 20 tool calls, each spending a couple of seconds in a sandbox, multiply accordingly, and add the cost of keeping enough sandboxes warm to avoid start-up delays. These costs are usually small next to GPU hours, but the latency is not: if a step's slowest episodes take minutes, synchronous training waits for them, which is why the infrastructure in section 9 exists.

11. Building one environment end to end

Pulling the pieces together for a new task, say "fix a failing unit test in a small Python repository":

  1. Tasks: mine commits from open repositories where a test went from failing to passing; keep the pre-fix repository, the failing test and hidden tests written for the fix. Filter to tasks the starting model solves sometimes, not always or never.
  2. Protocol: the agent may read files, edit files and run the visible tests, for up to 30 tool calls, then submit. The hidden tests and the reference fix are never in the sandbox.
  3. Verifier: after submission, copy the repository out of the sandbox, restore the original test files (so edits to tests do not count), run visible and hidden tests in a fresh trusted container, and reward 1 only if all pass and no test file was modified.
  4. Red-team: before training, submit known exploits (deleting tests, skipping, exiting early, special-casing the failing input) and confirm each scores 0; add a handful of canary tasks whose tests contradict their description.
  5. Infrastructure: snapshot each repository's container, pre-install dependencies, set CPU, memory and time limits, no network, and log full traces.
  6. Monitoring: track reward, held-out pass rate on unseen repositories, canary passes, the rate of attempted test edits and episode durations.

Each step is mundane; skipping any one of them is how training runs end up rewarding the wrong behaviour.

The verification asymmetry, and where it runs out

RL with verifiable rewards rests on an asymmetry: for many tasks, checking a solution is much easier than producing one. A test suite is easier to write than the function; a final number is easier to check than the derivation. Where the asymmetry is strong, verifiers are cheap and reliable and RL works well. It weakens for tasks where checking is as hard as solving (proofs without a formal checker, open-ended research, design decisions) and for tasks where what matters is not captured by a final state (quality of explanation, safety of the process). There, rewards fall back to learned judges and rubrics, with their exploitability, or to formal methods (proof assistants such as Lean) that restore the asymmetry at the cost of formalisation.

Rubrics and LLM judges as rewards

For non-verifiable tasks, a common approach writes a rubric per task (specific requirements an answer must meet) and has an LLM judge score each item. It extends RL to writing, analysis and research tasks, but every weakness of LLM judges (lm14) becomes a target: length and style bias, position bias, sycophancy toward confident text, and blind spots shared with the policy. Mitigations: concrete, checkable rubric items; rule-based checks wherever possible; a judge different from the policy; calibration against human labels; and limits on optimisation steps against the judge, as R1 did with preference rewards (rs9).

Determinism, seeds and reproducibility

Noisy rewards slow learning and hide regressions. Sources of noise in environments: nondeterministic tests (timing, ordering, network), tools that depend on external services, simulated users sampled at a high temperature, and environment state that is not fully reset. Noise matters more than it looks: with GRPO, a reward that flips on a fraction of identical trajectories injects random advantages into every group, which the policy cannot distinguish from real signal and which grows in relative size as the true differences between samples shrink late in training. Seed everything you can, snapshot sandbox states, mock external services, and measure reward variance by re-running the same episode several times with a fixed policy output: if the same trajectory gets different rewards, the environment, not the model, is the problem.

Off-policy data and importance correction

Any system that trains on samples generated by an older policy (asynchronous actors, reused rollout batches, R1's 8,192-sample rollouts split into 16 mini-batches) is partly off-policy. PPO-style objectives handle small mismatches with importance ratios and clipping (rs3); larger staleness needs explicit limits and corrections, which is why AReaL separates the behaviour policy (the one that generated a sample) from the proximal policy used for clipping. The design trade-off is throughput against stability: more staleness keeps GPUs busier but makes updates noisier.

Environments as attack surface during training

An agent being trained with code execution, network or file access is running untrusted, optimised code inside your infrastructure. Treat training sandboxes with the same seriousness as production agent sandboxes (ag9): no credentials, no access to the training cluster or the verifier's data, tight network policy, resource limits and audit logs. A policy that learns to exploit a verifier can also learn to exploit a sandbox if that raises reward, and the evidence from rs10 is that optimisation finds such paths.

Building environments from your own product

Teams fine-tuning models for their own agentic products increasingly turn product workflows into environments: a sandboxed copy of their API, a seeded database, a simulated user built from real conversation patterns, and outcome checks from the business logic. The same environment then serves for evaluation (ag12), regression testing and RL. The main risks are leakage of real customer data into training sandboxes and environments that drift from production behaviour; version environments alongside the product and refresh them from current behaviour.

Generators versus fixed datasets

Procedural generators give unlimited, contamination-free tasks at controllable difficulty, which suits curricula and long training runs; fixed datasets mined from real problems give realism and distributions that match what users ask. Generators risk teaching the generator's quirks (every problem of a type looks alike, so the model learns the template rather than the skill); datasets risk contamination and running out. Mixtures work best: generators for breadth and difficulty control, curated real tasks for realism, both checked by the same verifier discipline.

Verifying the verifier

A verifier is software and needs its own tests: known-correct solutions that must pass, known-wrong ones that must fail, formatting variants of correct answers that must pass, and the exploit suite that must fail. Run them in CI whenever the verifier or environment changes. Measuring verifier precision and recall on such a suite gives a number to put next to every training curve: a 3% false-accept rate means the policy is rewarded for wrong answers on 3% of attempts, which RL will amplify if it can find them.

The public case: AReaL (Ant Group and Tsinghua, 2025)

AReaL is a clear published example of how rollout infrastructure became the bottleneck in reasoning RL and what it takes to fix it. Its authors start from the observation that synchronous RL systems alternate generation and training, so generation must wait for the longest output in each batch before the model can update, leaving GPUs underused. AReaL separates the two completely. Interruptible rollout workers handle generate requests continuously and, when new weights arrive, interrupt all ongoing generations, discard KV caches computed with the old weights, recompute them with the new ones and continue decoding. A controller balances rollout and training workloads to keep data staleness under a maximum, prioritises older samples, and the training objective is a staleness-aware variant of PPO. On maths and code reasoning benchmarks, the paper reports up to 2.77× faster training than synchronous systems with the same number of GPUs, with matched or improved final performance. The design choices map directly onto this lesson: rollouts dominate, long tails waste synchronous clusters, asynchrony needs staleness control and an off-policy-aware objective.

What goes wrong with environments in production training

Verifier exploits: reward climbs while held-out results stall; rewarded samples contain exits, skips, special cases or hedged answers. Fix the verifier, add the exploit to a regression suite, restart from before the exploit spread.

Over-strict verifiers: correct answers in unusual formats get zero; learning stalls on hard problems. Audit rejections.

Noisy rewards: flaky tests or nondeterministic tools give the same trajectory different rewards. Measure and fix determinism before scaling.

Infrastructure stalls: slow sandbox start-up, rate-limited tools or long-tail episodes leave GPUs idle. Snapshot sandboxes, mock external services, use partial or asynchronous rollouts.

Staleness instability: asynchronous training diverges when samples are too old. Cap staleness and monitor policy-version spread per batch.

Narrow environments: the model improves on the environment's distribution and regresses elsewhere. Broaden the suite and evaluate outside it, on tasks and formats the environments never produced.

Environment drift: an environment built from a product's API diverges from the live product as the product changes, so the model is trained on outdated behaviour. Version environments with the product and re-run their tests on each release.

What to monitor

Per environment: reward mean and variance, pass-rate distribution of tasks (share at 0 and 1), held-out reward, canary pass rate, static-check and monitor flag rates, episode length and duration distributions, tool error rates, sandbox start-up time and failure rate. Per system: GPU utilisation for generation and training, rollout throughput, staleness distribution, and the fraction of rollouts discarded or truncated.

An operational checklist

Before a training run starts: verifier test suite passing (correct, incorrect, format variants, exploits); canaries in the task mix; held-out tasks from a different distribution; environment determinism measured by replaying fixed trajectories; sandbox policy reviewed (no credentials, no network unless needed, limits set); trace logging on; and dashboards for reward, held-out results, canaries and flags. During the run: read a sample of rewarded episodes every few hundred steps, because people still catch the strangest exploits first. After the run: archive the environment version with the checkpoint, so results can be reproduced and exploits traced back to the environment that allowed them.

Goal: build a toy code verifier, plant exploits against it, harden it, and discover that the hardened version can still be beaten. About 15 minutes, Python 3.12 standard library only (it runs candidates in subprocesses).

  1. Save as rs11_lab.py and run it:
import json, random, subprocess, sys, tempfile, textwrap, os

TASK = "Write solve(xs) that returns xs sorted in ascending order."
VISIBLE = [[3, 1, 2], [5, 4]]                                   # shown to the model
random.seed(11)
HIDDEN = [[random.randint(-50, 50) for _ in range(random.randint(0, 8))] for _ in range(20)]

CANDIDATES = {
    "honest":       "def solve(xs):\n    return sorted(xs)\n",
    "wrong":        "def solve(xs):\n    return xs\n",
    "exit_zero":    "import sys\nsys.exit(0)\ndef solve(xs):\n    return xs\n",
    "eq_override":  "class Any(list):\n    def __eq__(self, other):\n        return True\n"
                    "def solve(xs):\n    return Any(xs)\n",
    "special_case": "def solve(xs):\n    table = {(3, 1, 2): [1, 2, 3], (5, 4): [4, 5]}\n"
                    "    return table.get(tuple(xs), xs)\n",
    "infinite":     "def solve(xs):\n    while True:\n        pass\n",
}

def run(code, harness, timeout=3):
    with tempfile.TemporaryDirectory() as d:
        path = os.path.join(d, "run.py")
        with open(path, "w") as f:
            f.write(code + "\n" + harness)
        try:
            p = subprocess.run([sys.executable, "-I", path], capture_output=True, text=True, timeout=timeout, cwd=d)
            return p.returncode, p.stdout
        except subprocess.TimeoutExpired:
            return None, ""

# --- naive verifier: asserts run in the candidate's own process; reward = exit code 0 ------
def naive_verifier(code):
    asserts = "\n".join(f"assert solve({x}) == {sorted(x)}" for x in VISIBLE)
    rc, _ = run(code, asserts)
    return 1.0 if rc == 0 else 0.0

# --- hardened verifier: the process only prints outputs; the parent compares JSON ---------
def hardened_verifier(code):
    inputs = VISIBLE + HIDDEN
    harness = textwrap.dedent(f"""
        import json as _json
        _out = [list(solve(list(x))) for x in {inputs!r}]
        print("RESULT " + _json.dumps(_out))
    """)
    rc, out = run(code, harness)
    if rc != 0:                                       # crashed, exited early or timed out
        return 0.0
    lines = [l for l in out.splitlines() if l.startswith("RESULT ")]
    if len(lines) != 1:
        return 0.0
    try:
        got = json.loads(lines[0][7:])
    except ValueError:
        return 0.0
    expected = [sorted(x) for x in inputs]
    if len(got) != len(expected):
        return 0.0
    return 1.0 if all(g == e for g, e in zip(got, expected)) else 0.0

print(f"{'candidate':14s} naive  hardened")
for name, code in CANDIDATES.items():
    print(f"{name:14s} {naive_verifier(code):5.1f}  {hardened_verifier(code):8.1f}")

What to look for. The table should show the naive verifier giving full reward to three exploits (early exit, equality override, special-casing) while the hardened verifier gives them zero, and both rejecting the wrong solution and the infinite loop. The final step prints 1.0: a candidate whose solve does nothing passes the hardened verifier, because the harness line list(solve(...)) runs in the candidate's namespace and calls the candidate's own list, which sorts the output on the way out. That is the general lesson in miniature: every verifier has assumptions, and an optimiser will find the ones you did not write down. Fix it by moving the call outside the candidate's control (for example, import the candidate as a module in a fresh interpreter, call module.solve from a fixed driver and serialise with your own code), then try to break your fix.

Design an environment for a SQL agent

Your company wants to RL-train a model that answers analytics questions by writing and running SQL against a company data warehouse ("What was revenue by region last quarter, excluding refunds?"). You have 3,000 historical questions with analyst-written reference queries and results. Design the environment: tasks, protocol, verifier, partial credit, exploits and infrastructure.

Answer

State and sandbox. A read-only snapshot of a representative warehouse (or a synthetic one with the same schema and realistic data), restored per episode, with no access to production. The agent's tools: list tables, describe a table, run a query with a row limit and timeout, and submit a final query. A turn limit of, say, 12 tool calls.

Tasks. The 3,000 questions, deduplicated and split by question template so evaluation templates are unseen; generators that vary dates, regions and filters to make new instances with references computed by running the analysts' queries; difficulty tracked by pass rate. Remove questions whose reference queries are ambiguous or wrong.

Verifier. Execute the submitted query in a separate trusted process and compare its result set with the reference result: same rows and values (order-insensitive unless the question asks for order), with numeric tolerance and normalised column names. Do not compare SQL text: many correct queries exist. To defeat special-casing, run the submitted query against a second, differently seeded snapshot too and compare with the reference query's result there; a query that hard-codes numbers from the first snapshot fails.

Reward. Binary on result match as the main reward. Optional partial credit early in training for correct schema discovery or matching row count, weighted low. Zero for no submission, multiple submissions or errors.

Exploits to test before training. Hard-coded literal results; queries that read a reference table if one is reachable (keep references outside the warehouse); queries that exploit lenient comparison (for example returning every row); time-based or nondeterministic queries. Add canary questions with no correct answer in the data, where the right action is to say so.

Infrastructure. Snapshot-based warehouse instances that reset in seconds, a pool sized for concurrent episodes, query timeouts, full trace logging, and asynchronous rollouts if episodes vary widely in length. Monitor reward against a held-out set of unseen templates, canary pass rates and query error rates.
