By 2023, RLHF with PPO worked, but it was heavy. A PPO run holds four large models in memory, two of them being trained, and the value model, a whole second LLM, has to learn to predict from any half-written response how good the final answer will be. For short chat responses scored by a reward model that was tolerable. For mathematical reasoning, where responses run to thousands of tokens and the only feedback is whether the final answer is right, the value model was both expensive and hard to make accurate. Meanwhile, the reward model itself was a liability: optimise against a learned scorer hard enough and the policy finds outputs it over-rates.

Two ideas, both simple, removed those obstacles. The first, from DeepSeek's 2024 DeepSeekMath paper, was GRPO (Group Relative Policy Optimization): sample several answers to the same question, and judge each answer only against the others in its group. An answer that scored above its siblings is good; one that scored below is bad. No value model is needed, because the group itself provides the baseline. The second idea was to use rewards that a program can compute exactly: does the final answer match the reference, does the code pass the tests? That is RL with verifiable rewards (RLVR). Put together and scaled up in DeepSeek-R1, they produced a model whose reasoning matched OpenAI's o1 on many benchmarks, trained with a recipe that the community could reproduce, argue about and improve within weeks.

For an AI engineer this is now core knowledge. GRPO and its variants are what open-source reasoning models are trained with, what libraries such as TRL and verl implement, and what you would use to train a small model on your own checkable task: SQL generation, structured extraction, a domain-specific calculation. Interviews ask you to compute group-relative advantages, to explain what happens when every answer in a group is right, and to discuss the biases that later papers found in the original loss.

This lesson starts from PPO (rs3) and shows exactly what GRPO removes and adds. It computes the advantages for a group of four answers, one token's clipped objective and its KL term by hand, and explains why groups with identical rewards teach nothing and how often that happens. It then covers verifiable rewards and their failure modes, the fixes introduced by DAPO and Dr. GRPO (asymmetric clipping, dynamic sampling, token-level loss, removing the length and difficulty biases), the DeepSeek-R1 training settings, and what RLVR does and does not add to a model. The public case is the DeepSeekMath paper that introduced GRPO.

The mental model: grading on a curve

Imagine a teacher who cannot write model answers but can tell whether a student's final answer is right. To help one student improve, the teacher has them attempt each problem sixteen times. On a problem where twelve attempts are right and four wrong, the teacher says: "do more of what you did in the twelve, less of what you did in the four". On a problem where all sixteen are right, the teacher says nothing; there is nothing to distinguish. On one where all sixteen are wrong, again nothing: the student never found the way, so there is no good attempt to imitate. And the teacher's emphasis depends on the pattern. If fifteen attempts are right and one wrong, that one failure is surprising and gets strong attention; if eight are right and eight wrong, each attempt gets moderate feedback.

That is GRPO. Each prompt is sampled G times (the group), each response gets a reward, and each response's advantage, the signal telling the model whether to make it more or less likely, is its reward compared with the group: subtract the group's mean reward, divide by the group's standard deviation. A response above its group's average is reinforced, one below is discouraged. This is grading on a curve, and it replaces the value model of PPO, whose job was precisely to say what reward to expect from a given prompt. The group's average answers that question directly, from samples.

The reward itself, in reasoning training, comes from a verifier: a program that extracts the final answer and compares it with the known one, or runs the generated code against tests. Nothing in it is learned, so the policy cannot discover that the verifier likes confident phrasing or long answers. It can only discover how to be right (or, if the verifier has holes, how to exploit the holes, which is why the verifier needs as much care as the algorithm).

Why this combination took off

Each substitution solves a problem the other creates. A learned reward model is noisy and hackable, and a value model trained on a noisy reward is noisier still. A verifiable reward is exact but binary and arrives only at the end, which makes value learning especially hard, but group statistics need no value learning at all. And sampling a group is natural for reasoning, because you want the model to explore several approaches to every problem anyway.

Where the analogy breaks

The teacher's feedback reaches the whole of each attempt equally: "more of attempt 3" includes its false starts as well as its key insight. GRPO has the same property, every token of a response shares one advantage, and relies on thousands of problems for the useful patterns to stand out statistically. A human student would get specific comments; the model gets a single number per attempt and an enormous number of attempts.

1. Starting point: what PPO needed the value model for

Recall from rs3 that a policy-gradient update multiplies the gradient of each sampled token's log-probability by an advantage, the reward minus a baseline, and that the baseline's job is to answer "what reward did we expect from this prompt?" so that only the surprise drives learning. PPO gets the baseline, and per-token advantages, from a learned value model V(s) via GAE. For an LLM that value model is a second network as large as the policy, trained alongside it with its own optimiser state. In mixed-precision training that is about 16 bytes per parameter on top of the policy's 16, and for long reasoning chains it must predict the final 0/1 outcome from partial text, a hard and noisy target whose errors leak straight into the advantages.

The cheaper way to answer "what reward did we expect from this prompt?" is to sample the prompt several times and look. If eight samples of a problem score [1, 1, 0, 1, 0, 1, 1, 1], the expected reward from this prompt is about 0.75, and a response that scored 1 did better than expected. This is a Monte Carlo estimate of the value of the prompt, and it is unbiased, needs no training, and is specific to the prompt, which matters enormously because prompts vary from trivial to impossible.

2. The GRPO advantage

For a prompt q, GRPO samples G responses o_1 … o_G from the current policy, scores them with rewards r_1 … r_G, and sets the advantage of response i to its standardised reward:

Â_i = ( r_i − mean(r_1 … r_G) ) / std(r_1 … r_G)

Every token t of response i gets the same advantage, Â_{i,t} = Â_i. (DeepSeekMath also describes a process-supervision variant, where a step-level reward model scores each reasoning step and each token's advantage sums the normalised step rewards that follow it; the outcome version is the one that took over.)

By hand, a group of four: rewards r = [1, 0, 1, 1]. The mean is 0.75. The population standard deviation is √(((0.25)² × 3 + (0.75)²) / 4) = √(0.1875) = 0.433. The three correct responses get (1 − 0.75)/0.433 = +0.577; the wrong one gets (0 − 0.75)/0.433 = −1.732. The advantages sum to zero across the group, which is what makes them relative: GRPO only ever says "better or worse than your siblings". (Some implementations use the sample standard deviation, dividing by G − 1 inside the root; here that gives 0.5 and advantages +0.5 and −1.5. It changes only the scale.)

Two more groups show the pattern. With r = [1, 1, 0, 0], mean 0.5 and standard deviation 0.5, the advantages are ±1. With r = [1, 0, 0, 0], mean 0.25 and standard deviation 0.433, the single correct answer gets +1.732 and each wrong one −0.577. Rare outcomes, a lone success or a lone failure, get the large advantages, because they carry the most information about what distinguishes right from wrong on that prompt.

3. The GRPO objective

With advantages in hand, GRPO uses PPO's clipped surrogate (rs3), averaged over the tokens of each response and then over the group, and subtracts a KL penalty to the reference model directly in the loss:

J(θ) = E_q (1/G) Σ_i (1/|o_i|) Σ_t [ min( ρ_{i,t} Â_i , clip(ρ_{i,t}, 1−ε, 1+ε) Â_i ) − β · D_KL,i,t ]

ρ_{i,t} = π_θ(o_{i,t} | q, o_{i,<t}) / π_old(o_{i,t} | q, o_{i,<t})             (importance ratio)
D_KL,i,t = π_ref/π_θ − log(π_ref/π_θ) − 1        evaluated at the sampled token      (k3 estimator)

Here |o_i| is the length of response i in tokens. Two differences from RLHF-style PPO stand out. The KL term is in the loss, not subtracted from the reward, so it does not leak into the advantages. And it uses the k3 estimator, which is never negative: for ρ_ref = π_ref/π_θ = 0.9, it gives 0.9 − ln 0.9 − 1 = 0.9 + 0.1054 − 1 = 0.0054, while the plain log-ratio would give 0.105 and for a token the policy has made less likely, a negative number.

By hand, one token: take the first correct response above, Â = +0.577, a token whose ratio has reached 1.25 after some updates, ε = 0.2, π_ref/π_θ = 0.9 and DeepSeekMath's β = 0.04. The unclipped surrogate is 1.25 × 0.577 = 0.721; the clipped one is 1.2 × 0.577 = 0.692; the min is 0.692, the clipped branch, so this token sends no policy gradient. The KL term is 0.04 × 0.0054 = 0.0002, so the token's objective is 0.6926 and the only gradient it still sends is a small pull back towards the reference. For a token in the wrong answer (Â = −1.732) whose ratio has fallen to 0.90, the surrogate is min(0.90 × −1.732, 0.90 × −1.732) = −1.559, unclipped, so the gradient keeps pushing it down; at a ratio of 0.70 it would be min(−1.212, 0.8 × −1.732 = −1.386) = −1.386, clipped, and the push stops.

4. Groups that teach nothing

If every response in a group gets the same reward, the mean equals every reward, the numerators are all zero, and (with a small constant added to the denominator to avoid dividing by zero) every advantage is zero. The group contributes only the KL term. This is the price of a purely relative signal: the model learns only from prompts where its attempts disagree.

How often does it happen? If the policy solves a prompt with probability p per sample, the chance that all G samples agree is

P(dead group) = p^G + (1 − p)^G

By hand: with G = 16 and p = 0.9, 0.9^16 = 0.185 (and 0.1^16 is negligible), so nearly one group in five is wasted. With p = 0.98 it is 0.98^16 = 0.724. With p = 0.05 it is 0.95^16 = 0.440. With p = 0.5 it is essentially zero. With G = 4 the waste is much worse: at p = 0.9, 0.9^4 = 0.656. As training succeeds, prompts that were hard become easy, p rises across the dataset, and more and more groups go dead, quietly shrinking the effective batch. The remedies are to sample larger groups, to discard dead groups and refill the batch (DAPO's dynamic sampling, section 8), and to curate training prompts so the model's pass rate on them sits in the middle.

5. Verifiable rewards

A verifiable reward is computed by a program. For maths, the policy is told to put its final answer in a fixed place (for example inside \boxed{}), a parser extracts it, and a checker compares it with the reference, ideally after normalising equivalent forms (1/2, 0.5 and \frac{1}{2} should all match), returning 1 or 0. For code, the generated program is run in a sandbox against test cases, and the reward is 1 if all pass (or the fraction passed). DeepSeek-R1 added a format reward for putting the reasoning between <think> and </think> tags, weighted equally with accuracy, and, for the full R1, a language-consistency reward, the fraction of reasoning words in the target language, to stop the model mixing English and Chinese.

Verifiable rewards have three properties that made large-scale reasoning RL work. They are exact where they apply, so there is no learned scorer to over-optimise. They are cheap, so millions of samples can be scored. And they stay valid however far the policy moves: a reward model is trustworthy only near the distribution it was trained on, while an answer checker is equally right about a 30,000-token chain as about a 300-token one. That last property is why some reasoning recipes weaken or drop the KL leash that RLHF depends on (section 8).

They also have limits. They are sparse: one bit per response, and nothing at all on prompts the model never solves. They are narrow: most valuable tasks (writing, advice, open-ended analysis) have no automatic checker. And they are only as good as the checker: an extractor that accepts any of several boxed answers, or tests that can be satisfied without solving the problem, will be exploited, because RL is an optimiser and will find whatever the checker actually rewards (rs5).

6. Putting GRPO into a training step

One GRPO step for reasoning RL, end to end:

  1. Sample a batch of prompts (DeepSeek-R1's first RL stage used 32 prompts per step).
  2. Generate G responses per prompt with the current policy at temperature 1 (R1 used G = 16, giving 512 responses per step), recording each token's log-probability under the sampling policy and, unless the KL term is dropped, under the frozen reference.
  3. Score each response with the verifier and compute the group-relative advantages.
  4. Optionally drop dead groups and refill the batch.
  5. Split the responses into mini-batches and take one or a few gradient steps on the clipped objective plus the KL term. With exactly one step per batch, π_old equals π_θ at the moment of the step, every ratio is 1, and the clip never fires; this was DeepSeekMath's setting. R1 instead generated 8,192 outputs per rollout and trained on them in 16 mini-batches for one epoch, so later mini-batches are slightly off-policy and the clip matters.
  6. Periodically update the reference model to the current policy (R1 replaced it every 400 steps), so the KL leash restrains drift per phase rather than tying the model to its starting point forever.

The cost structure is dominated by step 2. With 32 prompts × 16 samples × responses averaging, say, 8,000 tokens, every step generates about 4.1 million tokens before a single gradient is computed. That is why reasoning RL runs pair a high-throughput inference engine with the trainer, and why tricks that make each generated token count (dynamic sampling, length control) are worth so much.

7. Biases in the original loss: length and difficulty

Two details of the objective in section 3 turned out to matter. The first is the factor 1/|o_i|: each response's token losses are averaged before averaging over the group. Consider two wrong responses, both with advantage −1, one 100 tokens long and one 1,000 tokens long. Under per-response averaging, each token of the short one is pushed down with weight 1/100 = 0.01, each token of the long one with weight 1/1,000 = 0.001: ten times less per token. A wrong answer is penalised less per token if it is long, so the policy is quietly encouraged to make wrong answers longer. For correct answers the effect reverses, favouring short ones. Liu et al. ("Understanding R1-Zero-Like Training", 2025) identified this length bias and showed it inflates response length, especially of incorrect responses, during training; they also found that many open-source PPO implementations normalise by response length in the same way, a habit inherited from pretraining code.

The second is the division by the group's standard deviation. A prompt where 15 of 16 samples are right has a small standard deviation (0.242), so its one wrong sample gets advantage (0 − 0.9375)/0.242 = −3.87 and its right samples +0.26; a prompt split 8/8 gives ±1. Per-prompt standardisation therefore weights prompts that are nearly always or nearly never solved more heavily than balanced ones, a question-level difficulty bias. Standardising advantages across a whole batch is a common RL trick; doing it per question changes the relative weight of questions. Liu et al.'s Dr. GRPO ("GRPO done right") removes both: it uses r_i − mean(r) without dividing by the standard deviation, and normalises the loss by a constant (such as the maximum generation length) rather than each response's length. With a minimal recipe built on it they reached 43.3% on AIME 2024 with a 7B base model, while producing shorter wrong answers.

8. DAPO: four fixes for long-chain RL

ByteDance Seed and Tsinghua's DAPO (Decoupled Clip and Dynamic sAmpling Policy Optimization, 2025) started from the observation that a naive GRPO run on Qwen2.5-32B reached only 30 points on AIME 2024, against 47 for DeepSeek's R1-Zero recipe applied to the same base model, and identified four changes that closed and passed the gap:

  • Clip-Higher. With a symmetric ε = 0.2, a token with probability 0.01 can only rise to 0.012 per update, while a token at 0.9 can easily reach the cap. Exploration of rare but useful tokens is choked and entropy collapses. DAPO decouples the bounds: ε_low = 0.2, ε_high = 0.28.
  • Dynamic sampling. Over-sample prompts and drop groups whose responses are all right or all wrong, refilling until the batch contains only informative groups, so the effective batch size does not shrink as the model improves.
  • Token-level policy-gradient loss. Average the loss over all tokens in the batch rather than per response, so each token counts equally and long responses' bad patterns (repetition, gibberish) are penalised as much as short ones'. This removes the length bias of section 7.
  • Overlong reward shaping. A response cut off at the length limit may have been on track; scoring it as a plain failure injects noise. DAPO instead applies a soft length penalty that grows linearly over the last stretch before the limit (they used an expected maximum of 16,384 tokens with a 4,096-token buffer), and filters truncated samples.

DAPO also removed the KL penalty, arguing that for long chain-of-thought training the model's distribution should be allowed to move far from the initial model, with a rule-based reward keeping the target honest. With these changes the same Qwen2.5-32B base reached 50 points on AIME 2024, using half the training steps of the R1-Zero-style baseline.

9. DeepSeek-R1's settings, for scale

The R1 paper gives concrete numbers worth knowing. For R1-Zero on DeepSeek-V3-Base: learning rate 3×10⁻⁶, KL coefficient 0.001, sampling temperature 1, 16 outputs per question, maximum length 32,768 tokens and 65,536 after step 8,200, at which point both accuracy and response length jumped. For R1's first reasoning RL stage: the same learning rate and KL coefficient, a GRPO clip ratio ε of 10 (far looser than PPO's 0.2; the authors note that a low value truncated gradients for many tokens and hurt performance while a high one risked instability), 32 questions × 16 outputs = 512 responses per step, the reference model refreshed every 400 steps, and a language-consistency reward added. Compared with DeepSeekMath's β = 0.04 and outputs of at most 1,024 tokens, the progression is towards much longer outputs and a much looser leash, enabled by a reward that cannot be fooled by drifting.

GRPO as REINFORCE with a group baseline, plus PPO's machinery

Strip GRPO to one gradient step per batch (so every ratio is 1 and the clip is inactive) and no KL, and its gradient is Σ_i Â_i ∇log π(o_i)/|o_i|: REINFORCE with a per-prompt baseline equal to the group mean, scaled by one over the group standard deviation and the response length. That places it in a family. RLOO (rs3) uses the leave-one-out mean, which is exactly unbiased; GRPO's mean includes the sample itself, shrinking each advantage by a factor (G − 1)/G, a harmless rescaling. The standard-deviation division acts like an adaptive learning rate per prompt. The clip and ratio matter only when a batch is reused for several steps, which large-scale runs do for throughput. Seeing GRPO this way explains why so many "new" algorithms are small edits to the same three ingredients: the baseline, the normalisation and the clipping.

Why the standard deviation is there at all

Dividing by the group's standard deviation makes every non-dead group produce advantages of comparable scale (their squares average to one), regardless of how rewards are distributed. With a learned reward model whose score differences vary greatly between prompts, that normalisation stabilises step sizes; DeepSeekMath, which introduced GRPO with a reward model, motivated the group-relative design by its match with how reward models are trained (on comparisons between outputs for the same question). With 0/1 rewards it has the side effects of section 7: prompts with lopsided outcomes get amplified. Whether that is harmful depends on what you want: amplifying the rare failure on an almost-solved prompt is arguably useful, since it targets the model's remaining errors; amplifying the rare success on a nearly impossible prompt is also useful, since that success is precious. Dr. GRPO's evidence is that removing it improves token efficiency without hurting accuracy; DAPO kept it. Treat it as a tunable choice.

Credit assignment without a critic

Every token of a response shares one advantage, so how does GRPO learn which tokens mattered? Statistically. A token pattern that tends to appear in correct responses (checking the answer by substitution, say) gets positive advantage more often than negative across thousands of groups, and its probability rises; a pattern that appears equally in right and wrong responses gets pushed up and down in equal measure and stays put. This works because the same prompt's responses share most of their context, so differences between them are concentrated where they diverge. It is slower than a good critic would be, and it gives credit to irrelevant tokens that happen to co-occur with success. Process rewards (rs5) and step-level value estimates from rollouts (as in VinePPO-style methods, which re-sample continuations from intermediate points to estimate step values) are attempts to recover per-step credit without a learned critic.

Entropy, clipping and exploration

RL sharpens distributions, and with verifiable rewards the sharpening is relentless: whatever pattern first raises accuracy gets reinforced until alternatives disappear. Entropy collapse shows up as identical samples within groups, rising dead-group rates even on prompts that are not solved, and plateaus. The upper clip bound is one of the main levers. For a token with probability p under π_old, the clip allows it to reach at most p(1 + ε_high) within one batch; for small p that is a tiny absolute change, while the lower bound lets confident tokens shrink alternatives freely. Raising ε_high (DAPO) or loosening the clip altogether (R1's ε = 10) lets low-probability tokens grow, preserving diversity. Temperature 1 during rollouts matters for the same reason: lower temperatures make groups agree more, killing signal.

The KL leash: when to keep it

In RLHF the KL term protects against reward-model exploitation, which grows the further the policy moves. With a rule-based reward that protection is less needed, and the KL can actively hold the model back from the long, exploratory behaviour reasoning needs; hence DAPO's removal and R1's tiny coefficient of 0.001 with a periodically refreshed reference. But the KL also preserves general abilities and readability that the narrow reward does not measure. A model trained only on maths answers with no leash may drift in style, mix languages (as R1-Zero did) or lose skills on other tasks. Practical recipes either keep a small KL, refresh the reference periodically, add auxiliary rewards (language consistency, format), or follow RL with a general SFT and preference stage, as R1 did.

What RLVR adds, and what it does not

The DeepSeekMath paper included an analysis that anticipated a later debate. Comparing the instruct model with the RL model on GSM8K and MATH at temperature 0.7, RL improved maj@k (majority voting over k samples) but not pass@k: RL made correct answers more probable per sample, making the output distribution more robust, rather than enabling the model to solve problems it previously could not solve in any of k tries. Yue et al. (2025) extended this with very large k and found base models eventually matching or exceeding RL models' pass@k. For practitioners this has two implications. RLVR is extremely effective at turning "can sometimes" into "usually does", which is what users experience. And it needs a starting model that can sometimes succeed; to teach genuinely new skills, distillation from a stronger model (rs6) or better base pretraining is the stronger lever.

Pretraining biases and the "aha moment"

Liu et al. also examined the base models used for R1-Zero-style replications. They found that DeepSeek-V3-Base already exhibits self-reflection ("aha") behaviour before any RL, and that Qwen2.5 base models answer maths questions well even without a prompt template, suggesting their pretraining included a lot of instruction- or reasoning-style data. That does not make RL's gains illusory, but it means "reasoning emerged from RL alone" should be read as "RL amplified behaviours present at low frequency in the base model", consistent with the pass@k evidence. When replicating results, the base model matters as much as the algorithm.

Reward noise and partial credit

Binary rewards make GRPO's group statistics coarse: with G = 8 and rewards in {0, 1}, the advantages take only a handful of distinct values. Partial credit (fraction of tests passed, a similarity score for near-miss answers) gives finer signal but opens new loopholes; a model can learn to pass the easy tests and give up on the hard ones. Noisy checkers, ones that occasionally mark correct answers wrong, act like label noise: they slow learning roughly in proportion to the error rate but do not systematically mislead, unless the errors correlate with some feature of the response (format, length), in which case the policy learns that feature. Auditing the checker on a sample of training responses, with special attention to the high-reward ones, is cheap insurance.

The public case: DeepSeekMath and the introduction of GRPO (Shao et al., DeepSeek, 2024)

DeepSeekMath, published in February 2024 by Zhihong Shao and colleagues at DeepSeek-AI, Tsinghua and Peking University, is mostly a paper about data. Its 7B base model continued pretraining from DeepSeek-Coder-Base-v1.5 on a 120-billion-token mathematical corpus mined from Common Crawl with an iteratively retrained classifier. The resulting DeepSeekMath-Base 7B scored 64.2% on GSM8K and 36.2% on the competition-level MATH benchmark, ahead of the 540-billion-parameter Minerva. Instruction tuning produced DeepSeekMath-Instruct 7B at 82.9% on GSM8K and 46.8% on MATH with chain-of-thought reasoning.

The final stage introduced GRPO. The paper's framing is the one in this lesson: PPO's value function is "typically another model of comparable size as the policy model", a substantial memory and compute burden, and in the LLM setting only the last token receives a reward, which makes a per-token value function hard to train. GRPO instead uses "the average reward of multiple sampled outputs, produced in response to the same question, as the baseline", adds the KL divergence to the loss rather than the reward, and estimates it with the always-positive estimator from Schulman's note. The RL run started from the instruct model and used about 144,000 chain-of-thought questions related to GSM8K and MATH from the SFT data, a learned reward model trained from the base model, a policy learning rate of 1×10⁻⁶, a KL coefficient of 0.04, 64 sampled outputs per question, a maximum length of 1,024 tokens, a batch size of 1,024, and a single policy update per exploration stage.

The results: DeepSeekMath-RL 7B reached 88.2% on GSM8K and 51.7% on MATH, up from 82.9% and 46.8%, surpassing every open-source model from 7B to 70B on those benchmarks and approaching GPT-4 (92.0% and 52.9% in the paper's table) and Gemini Ultra (94.4% and 53.2%). Because RL used only GSM8K- and MATH-style questions, the other benchmarks in the table act as out-of-domain tests, and the RL model improved on them too. With self-consistency over 64 samples the model reached 60.9% on MATH. The paper also compared outcome and process supervision within GRPO (process supervision did better in their experiments) and iterative RL in which the reward model is retrained on the policy's new samples with 10% replayed historical data.

Two parts of the paper outlasted the model. One is GRPO itself, which DeepSeek-R1 scaled up a year later with rule-based rewards in place of the reward model. The other is a "unified paradigm" that writes SFT, rejection-sampling fine-tuning, DPO, PPO and GRPO as the same gradient form with different data sources and "gradient coefficients", and the observation, discussed in the deep section, that RL improved maj@k but not pass@k. Both are useful frames for an interview: algorithms differ mainly in where the samples come from and how each sample's log-probability gradient is weighted.

Running GRPO on your own task

The practical recipe for a team with a checkable task is now well trodden. Start from a model that already solves the task sometimes, ideally with pass@8 well above zero on your training prompts, because prompts it never solves give no signal. Write the verifier first and test it adversarially: feed it answers with multiple candidates, malformed formats, empty reasoning, and correct answers in unusual but equivalent forms. Filter training prompts by the starting model's pass rate, keeping those in roughly the 10-90% band. Use a group size of 8 to 16, temperature 1, a modest maximum length that you raise later, token-level loss, and dynamic sampling. Libraries such as Hugging Face TRL (GRPOTrainer) and verl implement all of this; most of the work is the reward function and the data.

Failure modes

Verifier exploits. Reward climbs but held-out accuracy does not. Read high-reward samples; typical culprits are lenient answer extraction, tests that can be special-cased and format rewards satisfied trivially.

Length explosion. Mean response length grows until most responses hit the limit and are truncated. Check the loss normalisation (length bias), add overlong shaping, and watch the truncation rate.

Entropy collapse. Samples within a group become near-identical, dead groups rise and reward plateaus. Raise the upper clip bound, keep temperature at 1, and refresh the prompt set.

Signal starvation. As the model improves, most groups go dead. Track the fraction of informative groups per batch; if it falls below about half, add harder prompts or use dynamic sampling.

Capability regression elsewhere. The model improves on the RL task and gets worse on general chat, formatting or other languages. Keep a broad regression suite, a small KL or periodic reference refresh, and mix in general data afterwards.

What to log

Mean reward and its split into accuracy and format components; held-out accuracy with an independent checker; fraction of dead groups (all-correct and all-wrong separately); mean, p95 and maximum response length and truncation rate; entropy; clip fraction for the upper and lower bounds separately; KL to the reference if used; and a random sample of high-reward responses, read by a person, at regular intervals.

import numpy as np

# 1) Group-relative advantages for G = 4 answers to one question (1 = correct).
r = np.array([1.0, 0.0, 1.0, 1.0])
A = (r - r.mean()) / (r.std() + 1e-6)            # population std, as in the worked example
print("rewards", r, "-> advantages", A.round(3))
print("all correct:", ((np.ones(4) - 1) / (np.ones(4).std() + 1e-6)).round(3), "(no signal)")

# 2) The clipped GRPO term for single tokens, with the k3 KL estimator, eps = 0.2, beta = 0.04.
def grpo_token(ratio, adv, ref_over_pi, eps=0.2, beta=0.04):
    surr = min(ratio * adv, np.clip(ratio, 1 - eps, 1 + eps) * adv)
    kl = ref_over_pi - np.log(ref_over_pi) - 1    # always >= 0
    return surr - beta * kl, surr, kl
for ratio, adv in [(1.25, A[0]), (0.90, A[1]), (0.70, A[1])]:
    obj, surr, kl = grpo_token(ratio, adv, ref_over_pi=0.9)
    print(f"ratio={ratio:.2f} A={adv:+.3f}: surrogate={surr:+.4f}  kl={kl:.5f}  objective={obj:+.4f}")

# 3) Length bias: two wrong answers (A = -1) of 100 and 1,000 tokens.
lengths = np.array([100, 1000]); adv = np.array([-1.0, -1.0])
seq_mean = adv / lengths                         # GRPO: average within each response first
token_lvl = adv / lengths.sum()                  # DAPO: average over all tokens in the group
print("per-token push, sequence-mean :", seq_mean, " ratio", seq_mean[0] / seq_mean[1])
print("per-token push, token-level   :", token_lvl.round(6), " ratio", token_lvl[0] / token_lvl[1])

# 4) Dead groups: if every answer in a group gets the same reward, all advantages are 0.
for G in (4, 8, 16, 64):

# 5) A tiny GRPO run on a 4-response bandit: response 2 is right 80% of the time, others 20%.
rng = np.random.default_rng(0); z = np.zeros(4); q = np.array([0.2, 0.2, 0.8, 0.2])
for step in range(200):
    p = np.exp(z - z.max()); p /= p.sum()
    a = rng.choice(4, size=8, p=p); rew = (rng.random(8) < q[a]).astype(float)
    if rew.std() == 0: continue                  # dynamic sampling: skip dead groups
    adv = (rew - rew.mean()) / rew.std()
    z += 0.1 * sum(adv[i] * (np.eye(4)[a[i]] - p) for i in range(8)) / 8
print("policy after 200 steps:", (np.exp(z) / np.exp(z).sum()).round(3))

Work it out

A group of G = 8 responses to one problem gets rewards [1, 1, 0, 1, 0, 0, 0, 0]. (a) Compute the GRPO advantages. (b) Compute the Dr. GRPO advantages. (c) For a token in a correct response with ratio 1.3 and ε = 0.2, is its policy gradient zero? (d) If the model's pass rate on this problem rises to 0.95, how often will a group of 8 be dead?

Answer

(a) Mean = 3/8 = 0.375. Population std = √(0.375 × 0.625) = 0.484. Correct: (1 − 0.375)/0.484 = +1.29; wrong: −0.375/0.484 = −0.77. (b) Dr. GRPO skips the division: +0.625 and −0.375. (c) Positive advantage and ratio 1.3 > 1.2: the min selects the clipped term 1.2 × 1.29 = 1.55, constant in θ, so yes, zero policy gradient (only a KL gradient if β > 0). (d) 0.95^8 + 0.05^8 = 0.663 + ~0 ≈ 66% of groups dead; use a larger G for this prompt, or drop it from the training mix.

Design

You want to train a 7B model with GRPO to extract invoice fields into JSON. What is the reward, what could go wrong, and how do you choose prompts?

Answer

Reward: parse the JSON (0 if invalid); compare each field with the labelled value after normalising (dates, currency, whitespace); reward = fraction of fields correct, or 1 only if all are correct for a stricter target, plus a small format reward. Exploits to guard against: outputting every candidate value for a field, copying large chunks of the invoice into a field the checker matches by substring, or empty fields when the checker is lenient about missing values. Test the checker with such adversarial outputs first. Prompts: run the starting model 8 times per invoice and keep invoices with pass rates between roughly 10% and 90%, so groups are informative; refresh the set as the model improves.
