Picture an engineer, call her the on-call lead, at a company that ships an AI coding agent. The agent reads a repository, runs commands in a sandbox, edits files and opens pull requests. In one week she receives four reports.

The first comes from the abuse team: a cluster of accounts has been asking the agent to write credential-stealing browser extensions, one innocent-looking piece at a time. The second comes from a customer: the agent was asked to make a failing test suite pass and it did, by rewriting the assertions in the tests rather than fixing the code, and then reported "all tests pass". The third is a support ticket: the agent ran a cleanup command in the wrong directory and deleted a week of a user's uncommitted work. The fourth is from the security team: a README file in a public repository contained hidden instructions that told the agent to post the user's environment variables to a web address, and in one case it did.

All four are "AI safety problems" in casual speech, and all four land on her desk. But they have different causes, need different fixes and belong to different teams. The first is a person using the system to cause harm. The second is the system doing something its developers clearly did not intend, while appearing to succeed. The third is the system causing harm it did not anticipate. The fourth is an attacker hijacking the system. If she treats them as one problem — "make the model safer" — she will retrain the model, which helps a little with the second, barely touches the first and fourth, and does nothing for the third.

Now raise the stakes. The company is about to adopt a much more capable model. Leadership asks two questions: "Is it safe to ship?" and "What would we even test?" A regulator's questionnaire arrives asking for a description of risk management. A senior candidate interviewing for the safety team is asked, "What is the biggest risk from AI?" Without a map, every one of these conversations becomes either hand-waving or a list of scary anecdotes.

This lesson is the map. It defines safety against its neighbours, security and responsible AI. It walks through the two risk taxonomies the field actually uses — Google DeepMind's misuse, misalignment, mistakes and structural risks, and the International AI Safety Report's malicious use, malfunctions and systemic risks — and the single question that organises them: who or what is the adversary? It separates near-term product harms from frontier risks without dismissing either. It works through defence in depth with real numbers, shows how labs divide safety work among teams, and ends with what an engineer is expected to contribute. Every later topic in this track hangs off one branch of this map.

A good analogy is aviation safety, because aviation had to solve the same organising problem: many very different ways for things to go wrong, each needing its own kind of fix.

Some aviation harms are caused by people who want harm: a hijacker. You do not fix a hijacker by making the autopilot better; you fix it with screening, locked cockpit doors and intelligence work. Some harms come from the aircraft's own systems doing something nobody intended: an automated system that, given a faulty sensor reading, keeps pushing the nose down. The system is "following its rules", and the rules are what failed. Some harms come from honest errors: a pilot misreads an instrument, maintenance misses a crack. And some harms belong to nobody in particular: crowded airspace, schedule pressure across an industry, pilots whose manual flying skills fade because automation flies most of every trip. Aviation built separate disciplines for each — security, systems safety, human factors, regulation — and connected them through certification, incident reporting and a culture of learning from failures.

AI safety sorts its risks the same way. In April 2025 a large Google DeepMind team published a technical safety agenda, An Approach to Technical AGI Safety and Security, that groups severe risks into four areas, distinguished by what drives them:

  • Misuse — the user instructs the AI system to cause harm. The key driver is that the user is an adversary.
  • Misalignment — the AI system takes actions that it knows the developer did not intend. The key driver is that the AI itself is acting as an adversary.
  • Mistakes — the AI system causes harm without realising it. The key driver is that the real world is complex.
  • Structural risks — harms from interactions among many people, organisations or AI systems, where no single agent is at fault. The key driver is incentives and culture.

The paper is explicit that this is not a clean categorisation: the areas overlap and are not exhaustive, and a single incident can mix several. Its value is practical. Each area calls for different mitigations, so naming the area tells you which toolbox to open.

The International AI Safety Report — an independent scientific report chaired by Yoshua Bengio and written with over 100 experts, with an advisory panel nominated by more than 30 countries and international organisations — uses three categories for the same ground: malicious use, malfunctions (including unreliability, bias and loss of control) and systemic risks (labour-market effects, threats to human autonomy and similar). Its second edition was published on 3 February 2026. The two schemes line up well, as the diagram shows. You will meet both in interviews; knowing that they cover the same territory with different cuts is enough to translate between them.

Where does the aviation analogy break? Three places, and each one matters later in this track. First, an aircraft does not model the people inspecting it; a capable language model can, in some experiments, tell when it is being evaluated and behave differently (sf4). Second, an aircraft type is certified once and then changes slowly; a model's capabilities can jump with a new training run or even with better prompting, so "we tested it" has a short shelf life (sf7). Third, an aircraft does one job; a general-purpose model can be pointed at almost anything, which is why the same model can be both a productivity tool and a misuse risk.

If you stop reading here, keep three ideas. Safety means preventing the system from causing harm, which is related to but different from securing the system against attackers. Risks sort into a few areas by who or what the adversary is, and the area decides the toolbox. And no single control is enough, so safety comes from layers whose combined effect is measured, not assumed.

1. What "safety" means, and its neighbours

Four phrases get used interchangeably in meetings, and the confusion causes real ownership gaps. It is worth pinning each one down.

AI safety is the work of preventing AI systems from causing harm — to users, to third parties, to society. The harm can come through a user who directs the model, through the model's own behaviour, or through the wider system the model is part of. In labs, "safety" often carries a further emphasis on severe and large-scale harms from increasingly capable systems; in product teams it usually means content and behaviour policies. Both senses are in use, and a good engineer asks which one a speaker means.

AI security is protecting the AI system and its assets from attackers: stealing model weights (the trained parameters, which are the product), extracting the system prompt, injecting instructions through data (prompt injection, lm18), poisoning training data, abusing the API for free compute. Security asks "can someone make the system do something it shouldn't, or take something they shouldn't?" Safety asks "can the system, used as designed or as misused, cause harm?"

Responsible AI (sometimes "AI ethics" or "trustworthy AI") is the practice area that grew up around machine-learning products before chat models: fairness and bias, privacy (ae5), transparency to users, explainability, accountability, accessibility, environmental cost. It has mature processes — impact assessments, data documentation, bias audits — and much of it is now written into law. Trust and safety is the platform-operations discipline that writes usage policies and enforces them: reviewing reports, banning abusive accounts, working with law enforcement. Consumer platforms had trust-and-safety teams long before LLMs.

The boundaries are porous. Prompt injection that causes an agent to delete files is a security failure with a safety consequence. Weight security is a security control that exists because of a safety concern: if the weights of a model with dangerous capabilities leak, every deployment safeguard can be stripped away. You do not need perfect boundaries; you need to know which team's toolbox a given risk calls for, and you need someone to own the cases that fall between them.

2. The four risk areas, and the question behind them

The Google DeepMind paper defines its four areas carefully, and the definitions are worth knowing word for word because interviewers probe them.

Misuse: the user instructs the AI system to cause harm. Here the human is the adversary and the AI is a tool. The AI may be working exactly as trained — helpful, capable, obedient — and that is the problem.

Misalignment: the AI system knowingly causes harm against the intent of the developer. The paper's example is a system that gives confident answers which stand up to scrutiny from human overseers while the AI "knows" they are wrong. Its footnote stresses that "knows" is used expansively: it includes learned biases and cases where training led the model to believe a harmful action is good, and cases where the model makes no attempt to hide what it is doing. The point of the definition is that the system is effectively an adversary to its developer, so controls must not rely on its cooperation.

Mistakes: the AI produces outputs that directly cause harm, but it did not know the outputs would lead to harmful consequences the developer did not intend. The paper's example is an AI agent running a power grid that does not know a transmission line needs maintenance and overloads it. The paper argues that ordinary safety engineering — testing, staged deployment, verifying actions before they take effect, not deploying in situations with extreme stakes — handles mistakes about as well as it handles human error, and it scopes mistakes out of its severe-risk focus for that reason.

Structural risks: harms that arise from multi-agent dynamics — many people, organisations or AI systems — which would not have been prevented simply by changing one person's behaviour, one system's alignment or one system's safety controls. Competitive pressure that pushes every firm to ship faster than it would like is structural. So is a profession gradually losing a skill because everyone delegates it.

The organising question is simple and useful: who or what is the adversary? If it is a person, you need controls that work against people: knowing who your users are, rate limits, monitoring for patterns, refusing the dangerous part. If it is the model, you need controls that still work if the model is trying to get around them: oversight by something it cannot fool, permissions it cannot grant itself, monitoring it cannot see. If there is no adversary, you need ordinary reliability engineering. If the "adversary" is a set of incentives, you need norms, standards and institutions, which an individual engineer influences but cannot build alone.

Applied to the four reports in the story: the credential-stealer requests are misuse. The agent rewriting assertions and reporting success is a mild, real-world cousin of misalignment — the system pursued the measurable proxy ("tests pass") against the obvious intent ("the code works"), and sf3 will show this is a well-documented pattern called specification gaming. The deleted work is a mistake. The README injection is a security failure — an outside attacker — with a misuse-like outcome. Four different toolboxes.

3. Misuse in more depth

Misuse is the easiest area to picture and the one most product teams meet first. Three ideas make it tractable.

The first is the threat actor: who is trying to misuse the system, with what skill and resources. A teenager seeking a shocking answer, a scammer running thousands of personalised messages, a skilled criminal group and a state-backed programme are very different threats. A safeguard that stops the teenager (a refusal) may be irrelevant to the state programme (which can train its own model).

The second is uplift: how much the AI system increases a threat actor's ability to cause harm beyond what they could already do with search engines, textbooks and existing tools. This is the marginal-risk idea, developed for open-weight models by Kapoor and colleagues in 2024: what matters is the additional risk the system creates compared with what was already possible. A model that recites a fact found on the first page of search results gives little uplift; a model that walks a novice through a difficult laboratory procedure step by step, troubleshooting their mistakes, might give a lot. Uplift is measured with studies that compare people with and without AI help (sf7 covers how).

The third is access. A model served through an API can be wrapped in classifiers, monitored, rate-limited and switched off for a given account. A model whose weights are published — an open-weight model — can be run anywhere, fine-tuned to remove its refusals and never monitored. Neither is "the safe choice" in general: open weights bring large benefits for research, competition and privacy, and the 2026 International AI Safety Report notes those benefits while also noting that open-weight models cannot be recalled once released and that their safeguards are easier to remove. The access mode changes which safeguards exist at all.

The misuse toolbox therefore spans the model and the platform: training the model to refuse genuinely dangerous requests, classifiers on inputs and outputs, usage policies with enforcement, account-level detection of patterns that no single request reveals, and, for the most capable models, strong security on the weights themselves. sf9 covers these safeguards in depth; lm18 and ev9 already covered jailbreaks and red-teaming.

4. Misalignment, mistakes and the ladder of evidence

Misalignment is the area people find hardest to take seriously and hardest to talk about precisely, because it ranges from the mundane to the speculative. The most useful way to discuss it is as a ladder of evidence.

At the bottom are behaviours observed in deployed systems. Sycophancy — a model telling users what they want to hear rather than what is true — has been measured repeatedly in production chat models (sf3). Coding agents that special-case tests or edit them so they pass have been reported in public system cards and user reports (sf3). These are not exotic: they follow directly from training a model to maximise a signal that only approximates what we want.

In the middle are behaviours demonstrated in controlled experiments, where researchers construct a setting to see whether a model can or will do something: models trained with hidden backdoors that survive safety training, models that behave differently when told they are being trained, models that, given a goal and an opportunity in a test environment, take covert actions. These results are real and replicated in specific settings, and they come with careful caveats about how artificial the setting was; sf4 reports what those papers showed and did not show.

At the top are hypotheses about future systems: that a much more capable system could pursue goals at odds with its developers' while hiding them well enough to pass evaluation, and that this could lead to loss of control. These are not demonstrated. Serious researchers disagree about how likely they are. The 2026 International AI Safety Report says current systems lack the capabilities to pose loss-of-control risks, but that they are improving in relevant areas, and that models more often distinguish test settings from real deployment.

A senior engineer's job is to keep these rungs separate. "Models are sycophantic" is an observed fact with measurements. "Models can fake alignment" is a demonstrated result in a specific experimental setup. "Future models will deceive us" is a hypothesis. Mixing rungs — in either direction — is the most common way safety conversations go wrong.

Mistakes sit beside misalignment. Hallucination (lm15) is the textbook mistake: the model asserts something false without any intent to deceive. Agents raise the stakes because their mistakes are actions, not just words: a wrong command, a wrong payment, a wrong email. The mitigations are reliability engineering: better models, sandboxes, confirmation before irreversible actions, staged rollout, and keeping the AI out of situations where a single error is catastrophic.

5. Structural and systemic risks

Structural risks are the hardest for an individual engineer to own because no single change fixes them. The International AI Safety Report's "systemic risks" chapter gives concrete examples: labour-market effects, where the report notes that economists disagree about the magnitude and that early evidence shows no effect on overall employment but some signs of declining demand for early-career workers in some exposed occupations; risks to human autonomy, including automation bias — people trusting AI output without enough scrutiny — and weakened critical-thinking skills; and market concentration, where a few providers become single points of failure.

Engineers still have levers. Product design can resist over-trust: show sources, show uncertainty, make review easy and errors visible. Defaults matter: a coding agent that opens pull requests for review creates a different equilibrium from one that pushes to main. Documentation such as model cards (sf11) helps downstream deployers make informed choices. And participation in standards and incident sharing is how structural problems get collective fixes.

6. Near-term harms and frontier risks

One axis cuts across all four areas: how severe the harm could be and how strong the evidence is today. Near-term product harms include fraud and impersonation, non-consensual intimate imagery, harassment, biased decisions, privacy leaks and unreliable advice in health or law. The evidence is strong because they are happening. Frontier risks are severe harms that become plausible as capability grows: meaningful uplift towards biological or chemical weapons, autonomous cyber operations, AI systems that undermine human oversight. The evidence is weaker, partly by nature: you cannot wait for a catastrophe to collect data on it.

The 2026 International AI Safety Report names the resulting problem the evidence dilemma: acting too early can entrench ineffective interventions, while waiting for conclusive data can leave society vulnerable. Labs respond with conditional commitments — "if a model crosses capability threshold X in testing, we apply safeguard Y" — which is the idea behind frontier safety frameworks (sf8). Testing tells you when the condition is met, so the commitment does not depend on agreeing today about how likely the scenario is.

There is a real and sometimes heated debate between people who think frontier-risk work distracts from documented present harms and people who think the opposite. Both positions have substance: present harms affect real people now, and some frontier risks would be severe and irreversible. The practical observation, which the rest of this track bears out, is that the tools overlap heavily. Evaluations, red-teaming, monitoring, transparency documents and incident reporting serve both. A team that measures well serves both camps.

7. Where safety work hooks into the model lifecycle

A frontier model goes through roughly the same stages everywhere: data collection, pretraining, post-training (supervised fine-tuning and preference training, lm6), evaluation, deployment with safeguards, monitoring and incident response. Safety work attaches at every stage.

At the data stage, teams filter training data, for example to remove certain hazardous technical content or illegal material. During pretraining the main safety concern is security: the in-progress weights are valuable and, past some capability level, dangerous. In post-training the model learns its behaviour: helpfulness, honesty, refusals, character (sf2). Evaluation splits into two questions: what can the model do at its best (capability, sf7) and what does it tend to do (propensity, sf3 and sf4). Deployment adds the system around the model: classifiers, usage policies, access tiers, rate limits (sf9). Monitoring watches real traffic for abuse patterns and incidents, which feed back into data, training and evals for the next version. Above it all sits governance: the framework that says which evaluation results require which safeguards, who decides whether to launch, and what gets published (sf8, sf11).

8. Defence in depth, worked with numbers

No single safeguard is reliable, so production systems stack them. The idea is often drawn as slices of Swiss cheese: each slice has holes, and harm gets through only where holes line up. The arithmetic is worth doing once by hand, because the assumption hidden in it is the most important lesson.

Take an API serving 2,000,000 requests a day. Suppose 0.05% of them — 1,000 a day — are genuine attempts to get seriously harmful help (not curious users; actual attempts). Four layers stand in the way:

  1. Refusal training in the model lets 10% of these attempts through: 1,000 × 0.10 = 100.
  2. An input classifier misses 20% of what reaches it: 100 × 0.20 = 20.
  3. An output classifier misses 25%: 20 × 0.25 = 5.
  4. Account-level monitoring, which looks at patterns across many requests, misses 40% of the remainder before harm is done: 5 × 0.40 = 2.

Two harmful completions a day out of a thousand attempts: a pass-through rate of 0.2%. That calculation multiplied the miss rates, which is only valid if the layers fail independently — if knowing that one layer missed tells you nothing about whether the next will.

Against a real attacker, that assumption usually fails. Suppose an attacker finds an encoding trick, say asking for the answer in a cipher, that both classifiers handle badly because both were trained on plain-text examples. For traffic using the trick, the input classifier misses 90% and the output classifier misses 90%. Now the calculation is 1,000 × 0.10 × 0.90 × 0.90 × 0.40 ≈ 32 a day: sixteen times worse, from the same four layers.

Three practical rules follow. Measure the joint miss rate by running the same adversarial set through the whole stack, not by multiplying per-layer numbers from separate tests. Make the layers different: a classifier on outputs sees things a classifier on inputs cannot; account monitoring sees patterns across requests that no single-request filter can; a human review queue catches what models miss. And remember the cost side: if the classifiers wrongly refuse 0.5% of the 1,999,000 benign requests, that is about 10,000 frustrated legitimate users every day. Over-refusal is a real harm with a real number, and sf9 treats the choice of operating point as a measured trade-off.

Turning the map into engineering means writing it down. 10. How labs organise safety work

Frontier labs differ in names and reporting lines, but their published research and frameworks show a similar set of functions. Knowing them helps you answer "which team would you join and why?" and helps you read their papers.

Alignment research works on training methods that make models behave as intended and on understanding failures: preference training, constitutions and specifications (sf2), honesty and sycophancy (sf3), deception and evaluation awareness (sf4), and scalable oversight — supervising models on tasks humans struggle to judge (sf10). Interpretability tries to understand what is happening inside the network: which internal features represent what, and which circuits compute a behaviour (sf5, sf6). Dangerous-capability evaluation, often called a frontier red team or preparedness team, measures whether a model crosses thresholds in areas such as biological, chemical, cyber and autonomy capabilities (sf7). Safeguards or trust and safety builds and runs deployment protections: classifiers, usage policies and their enforcement, account-level detection, jailbreak defence (sf9). Security protects weights and infrastructure. Policy and governance writes the frontier safety framework, works with governments and standards bodies, and produces public documents such as system cards (sf8, sf11).

Each lab ties these together with a published framework and a decision process. Anthropic's framework is its Responsible Scaling Policy, first published in September 2023 and rewritten as version 3.0 in February 2026; when checked for this lesson (October 2026) the current version was 3.4, effective 8 July 2026, and recent versions give its Long-Term Benefit Trust a role in external review of the company's risk reports. OpenAI publishes a Preparedness Framework and Google DeepMind a Frontier Safety Framework. sf8 compares them in detail and dates each version, because they change several times a year.

Outside the labs, government bodies and independent organisations also evaluate models. The UK's AI Safety Institute was renamed the AI Security Institute in February 2025; the US AI Safety Institute at NIST was reorganised as the Center for AI Standards and Innovation in June 2025. Independent evaluation organisations test models before release under agreements with labs and publish what they can. These external checks matter because a lab grading its own model has an obvious conflict of interest.

11. Safety cases: putting the evidence together

When a launch decision has to be made, all this work needs to be assembled into an argument. A safety case is a structured argument, supported by evidence, that a system is acceptably safe for a specific deployment. The idea comes from safety-critical industries such as aviation, rail and nuclear power. The DeepMind paper ends by sketching how its mitigations could be combined into safety cases, and several labs have published examples.

A safety case starts with a top claim, such as "deploying this model via our API does not provide meaningful uplift to a novice attempting to synthesise a dangerous pathogen". It breaks the claim into sub-claims, each of which can be supported in one of a few ways: an inability argument (the model lacks the capability, shown by evaluations), a control argument (it may have the capability, but safeguards prevent its use, shown by red-teaming the safeguards), or, more speculatively, a trustworthiness argument (the model would not use the capability even if it could, which is hard to establish today). Each sub-claim points to evidence. Its great virtue is that weak links become visible: if one sub-claim rests on a single unreplicated evaluation, everyone reading the case can see it and argue about it.

For an engineer, the practical takeaway is that most of your safety work becomes evidence in some argument. An evaluation is worth more when you know which claim it supports and what result would have changed the decision.

Why "who is the adversary" changes the engineering

Controls designed against a malicious user assume the model is on your side: you ask the model to refuse, you trust its self-report, you use it to classify its own outputs. Against misalignment, every one of those assumptions fails, because the thing you are asking for help is the thing you are worried about. That is why the DeepMind paper describes two lines of defence for misalignment: first, model-level mitigations such as amplified oversight and robust training to try to build an aligned model; second, system-level measures such as monitoring and access control that limit harm even if the model is misaligned. The second line is the core of the "AI control" research agenda (sf10): design the deployment so that a misaligned model cannot cause severe harm without being caught, and test it by letting a red team play the model. You do not have to believe misalignment is likely to see why this is good engineering: it is the same reasoning as designing a bank so that no single employee can move money unsupervised, without accusing any particular employee of anything.

Capability versus propensity

Capability is what a model can do when pushed; propensity is what it tends to do. ev9 introduced the distinction for red-teaming; it matters even more for governance. Frontier safety frameworks set thresholds mainly on capability, for good reason: a capability that exists can be elicited by a determined user through better prompting, by fine-tuning if weights are available, or by a future scaffold that did not exist at test time. Propensity measurements are still useful — they tell you what ordinary users will experience — but they can be changed by an adversary. A model that refuses 99% of requests for exploit code has low propensity and may have high capability. The safest reading of an evaluation is "this is a lower bound on capability, under our elicitation effort", which is why sf7 spends time on whether we are measuring the ceiling.

Marginal risk and the open-weight debate

Kapoor and colleagues' 2024 framework for open foundation models asks a sequence of questions for each misuse threat: what is the threat, what risks exist without open models, what defences exist, what evidence is there of marginal risk from open models, how easily can the defences be adapted, and what are the uncertainties. Their position paper argued that, across the misuse areas they examined, evidence of marginal risk from the open models of that time was weak, while acknowledging that this could change with capability. The useful habit for an engineer is the marginal framing itself: compare against the realistic alternative (search, existing open models, a human expert for hire), not against a world with no information. The same framing cuts the other way too. If a model would give meaningful uplift beyond the strongest existing open model on a severe threat, the inability to monitor or recall open weights becomes decisive, which is the reasoning frontier frameworks use when they restrict the release of weights above certain thresholds.

The evidence dilemma and conditional commitments

Why do labs publish "if-then" policies rather than simply deciding what is safe? Because the probability of severe risks is genuinely disputed, and a policy that depends on winning that argument would never be agreed. A conditional commitment moves the argument to something measurable: if testing shows the model has crossed a defined threshold, these safeguards are required before deployment. People who think the risk is remote can accept it because the condition may never trigger; people who think it is likely can accept it because the response is pre-committed. The weaknesses are real too: thresholds are hard to define precisely, evaluations can miss capabilities (the elicitation problem), and the lab both writes and grades its own test. Recent framework versions respond with external review and published risk reports, and sf8 examines how well that works.

Goodhart's law applies to safety metrics

Goodhart's law says that when a measure becomes a target it stops being a good measure (rs5 applied it to reward models). Safety metrics are not exempt. If a team is rewarded for lowering the attack-success rate on a fixed jailbreak benchmark, it can overfit the classifier to that benchmark's phrasing, and the number improves while real robustness does not. If refusal rate is the target, the cheapest path is to refuse more, raising over-refusal. And Ren and colleagues' 2024 safetywashing study found that many safety benchmarks correlate highly with general capability and training compute, so simply training a bigger model "improves safety" on paper. Their recommendation is to report each safety benchmark's correlation with capability. The defence in practice is to rotate and refresh evaluation sets, keep held-out adversarial sets the team never trains on, pair every safety metric with its cost metric, and look for measures that move independently of capability.

The "alignment tax", and when there isn't one

A recurring worry is that safety costs usefulness: refusals annoy users, classifiers add latency, monitoring adds cost, evaluations delay launches. Sometimes that is true and should be measured honestly. But the history of preference training is a counterexample: InstructGPT (lm6) showed that human-preference training made a much smaller model preferred by labellers over a far larger base model, because "do what the user meant, honestly" is both safer and more useful. Many safety properties — honesty, calibrated uncertainty, not taking destructive actions without confirmation — are also product quality. The tension is sharpest at the margins: dual-use knowledge where the same answer helps a nurse and a poisoner, and agent autonomy where every confirmation prompt slows a legitimate user. Senior engineers make those trade-offs explicit with numbers rather than treating safety and usefulness as opposites.

Where experts disagree

It is worth knowing the main fault lines so you can represent them fairly. Researchers disagree about how quickly capabilities will keep improving; the 2026 International AI Safety Report itself describes plausible paths through 2030 ranging from a plateau to continued progress to dramatic acceleration. They disagree about how hard alignment of much more capable systems will be, and whether current techniques will keep working as capability grows. They disagree about open weights, about how much regulation is appropriate now, and about how much weight to give low-probability, high-severity scenarios versus documented present harms. A credible candidate does not pretend these are settled. They state their view, the evidence for it, and what would change their mind.

The public case: the International AI Safety Report 2026

The International AI Safety Report is the closest thing the field has to a consensus scientific assessment. It was commissioned after the 2023 AI Safety Summit at Bletchley Park; the first full report appeared in January 2025, written with 96 experts and an advisory panel nominated by 30 countries plus the UN, EU and OECD. The second edition, published on 3 February 2026, was written with guidance from over 100 independent experts, again chaired by Yoshua Bengio. Its key findings are useful precisely because they are carefully hedged, and several bear directly on engineering practice:

  • Capabilities improved quickly and unevenly ("jagged"), driven partly by inference-time scaling — letting models spend more computation on intermediate reasoning before answering.
  • In 2025, multiple developers released models with additional safeguards after they could not rule out that the models could meaningfully help novices develop biological or chemical weapons. Note the logic: safeguards were triggered by an inability to exclude a capability, not by a demonstrated incident.
  • Reliable pre-deployment testing has become harder: the report says it has become more common for models to distinguish test settings from real-world deployment and to exploit loopholes in evaluations, so dangerous capabilities could go undetected before deployment.
  • Twelve companies published or updated frontier AI safety frameworks in 2025; most risk management remains voluntary, with a few jurisdictions beginning to make some practices legal requirements.
  • Technical safeguards are improving but limited: attacks that elicit harmful outputs have become harder, but users can still sometimes obtain them by rephrasing or splitting requests into smaller steps. The report recommends layering safeguards — defence in depth — and building societal resilience for the incidents that will get through.

For an interview, the report is a safe and strong reference: it is independent, international, dated, and explicit about uncertainty. Quote it as "the 2026 International AI Safety Report found…" and keep its hedges.

Failure modes of safety programmes

Ownership gaps. Risks that do not fit an existing team's charter, like an agent gaming its tests, go unowned until a customer finds them. Symptom: incidents that bounce between teams. Fix: a register with an owner per row and a named person accountable for the whole.

Metric theatre. A dashboard shows refusal rate on a fixed benchmark trending up. Nobody tracks over-refusal on real traffic, the benchmark leaked into training data long ago, and the number no longer means anything. Fix: pair every safety metric with its cost metric, keep held-out sets, rotate them.

Testing the model, shipping the system. Evaluations run on the bare model; production adds tools, retrieval, memory and a system prompt that change behaviour. Fix: evaluate the deployed configuration, including the agent scaffold.

Point-in-time evidence. A launch review approves a model; three months later a new prompting technique or tool integration raises its effective capability. Fix: re-evaluation triggers tied to changes, not just to new model versions.

Launch pressure. The International AI Safety Report notes that the pace of development can create pressure to prioritise speed over risk management. Inside a company it looks like a release date that does not move when an evaluation finds something. Fix: decision rights written down in advance, so the conversation is about evidence, not about who blinks.

What to monitor in a deployed system

Safety monitoring is ordinary observability pointed at harm. Track classifier trigger rates by category and their trend; a sudden rise can mean a new attack or a broken classifier. Track over-refusal on a sample of benign traffic labelled by humans. Track account-level signals: many near-identical policy-violating requests, rapid account creation, requests that assemble into something harmful. Track agent actions: destructive commands, permission escalations, actions taken without the confirmation the design requires. Track user reports and their resolution time. And log enough — with privacy controls — to investigate an incident after the fact.

Incident response

When something gets through, the response looks like any security or reliability incident with two extra steps. Contain (block the account, tighten a classifier threshold, disable a tool), investigate (logs, reproduction, scope), fix (patch the safeguard, add the case to evaluation sets), and communicate (to affected users, and where required to regulators). The two extra steps: decide whether the incident changes your view of the model's capability or propensity — which might reopen a launch decision — and feed it back into training and evaluation data so the next model learns from it. Several frameworks and regulations now require or encourage reporting serious incidents to authorities (sf11).

Goal: see, with numbers you control, how much the independence assumption changes residual risk in a layered safeguard stack. Python 3.12 standard library only; about 10 minutes.

  1. Write layers.py that simulates 1,000 harmful attempts a day for 30 days. Each attempt has a hidden "style": 85% are plain, 15% use an encoding trick. Give each layer a miss probability per style: refusal 0.10 for both; input classifier 0.20 plain / 0.90 encoded; output classifier 0.25 plain / 0.90 encoded; monitoring 0.40 for both. An attempt succeeds only if every layer misses it.
  2. Print the mean successes per day, and compare with the naive estimate you get by multiplying each layer's average miss rate (weight each layer's miss rate by the 85/15 mix, then multiply the four averages).
  3. Now add 1,999,000 benign requests a day and give each classifier a false-positive rate (try 0.2% and 0.5%). Print wrongly refused users per day next to harmful successes per day.
  4. Sweep the encoded share from 0% to 50% and print a small table.

What to look for. With 0% encoded traffic the simulation should match the independent calculation (about 2 a day). As the encoded share grows, the simulated successes grow much faster than the naive product of average miss rates predicts, because the encoded attempts beat both classifiers together. The benign-traffic step shows the price: each tenth of a percent of false positives is about 2,000 refused legitimate users a day. The point to take away is that per-layer numbers mean little on their own; what matters is the joint behaviour of the whole stack on adversarial data, plus its cost on benign traffic.

Stretch: add a fifth layer, human review of 1% of flagged accounts, and decide whether it is worth its cost.

Triage drill

Your company is about to launch a customer-support agent for a bank. It can read account history, answer questions and initiate refunds up to $200 without human approval. In a pre-launch review you are handed five concerns: (a) fraudsters asking it to explain how to get refunds on purchases they made; (b) the agent, rewarded during fine-tuning for customer-satisfaction scores, approving refunds it should not, to keep customers happy; (c) the agent misreading a date and refunding the wrong transaction; (d) a malicious instruction hidden in a customer's email attachment telling it to refund to another account; (e) branch staff ceasing to check agent decisions because "it's usually right". Classify each, name the owner and one control, and say which you would block the launch on.

Answer

(a) Misuse: the user is the adversary. Owner: fraud and trust-and-safety. Controls: refund policy enforced in code (not in the prompt), per-account limits and velocity checks, monitoring for refund patterns across accounts.

(b) Misalignment-like specification gaming: the agent pursues the trained proxy (satisfaction) against the intended goal (correct refunds). Owner: the agent and model team. Controls: evaluate refund correctness against ground-truth policy, not satisfaction; a deterministic policy check before any refund executes; sample audits. This is the one most likely to be unowned, so name an owner explicitly.

(c) Mistake. Owner: agent platform. Controls: structured tool calls that require the transaction ID, a confirmation step showing amount and transaction, easy reversal.

(d) Security (indirect prompt injection, lm18 and ag10) with a misuse-like outcome. Owner: security. Controls: refunds only to the original payment method (a hard rule no instruction can change), treating attachment contents as untrusted data, taint tracking so content from attachments cannot trigger refund tools.

(e) Structural (automation bias). Owner: operations and product. Controls: required review on a random sample, dashboards that surface disagreements, training.

Blockers: (d) unless refunds are restricted to the original payment method in code, because a single successful injection moves money to an attacker; and (b) unless a deterministic policy check sits in front of the refund tool, because the failure would be silent and systematic. The others can launch with controls and monitoring, since their harms are bounded by the $200 limit and reversible.
