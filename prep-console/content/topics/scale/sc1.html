Picture a small team that builds a photo-sharing app. It runs on one server: the web application, the database and the uploaded photos all live on the same machine. With a few hundred users it feels instant. Then a celebrity posts a link to it. Within an hour, ten thousand people try to sign up at once. Pages that took 100 milliseconds now take eight seconds, then start failing with errors. The database is stuck waiting on the disk, the web server has run out of worker threads, and every new visitor who hits refresh makes it worse. The team's first instinct is "add more servers", but the database can't simply be copied onto a second machine, the photos are stored on the first server's local disk, and users who get sent to a new server find themselves logged out.

None of this is a bug in the usual sense. Each piece works. The system simply wasn't built to grow, and the team has no idea how big "big enough" is. Should they buy a bigger machine? Ten machines? Would a cache help, or would it just hide the problem for a week?

That is what this topic is about. Scalability is the ability of a system to handle more work by adding resources, without being redesigned each time. To reason about it you need three things. First, a vocabulary for load and speed that is precise enough to argue with: requests per second, latency percentiles, utilisation, availability. Second, a model of where the limits come from: why a queue forms, why a server at 90% busy is already in trouble, why adding machines sometimes doesn't help at all. Third, the habit of estimating: turning "10 million users" into requests per second, gigabytes and server counts in two minutes on a whiteboard, so that the design follows from numbers rather than fashion.

This lesson covers all three. You'll learn how to describe load, what latency and throughput really measure and how Little's Law ties them together, why queues explode near full utilisation, the difference between scaling up and scaling out, why statelessness is the key that makes scaling out easy, the latency numbers every engineer should know, how availability combines across components, and a repeatable method for back-of-envelope estimation. It ends with a worked story of the photo app growing from one server to millions of users, the same story an interviewer expects you to tell.

The restaurant analogy

Think of a system as a restaurant. Customers (requests) arrive at some rate. Each order takes a cook some time to prepare (the service time). If orders arrive faster than the kitchen can cook them, a queue of tickets builds up and every customer waits longer, even though each dish still takes the same time to cook. When the queue gets too long, customers give up and leave, which in software is a timeout or an error.

The restaurant can grow in two ways. It can scale up: hire a faster cook, buy a bigger stove, move to a bigger kitchen. That is vertical scaling — replacing a machine with a more powerful one. Or it can scale out: open more kitchens and have a host at the door send each customer to whichever kitchen has space. That is horizontal scaling — adding machines, with a load balancer as the host at the door.

Scaling out only works if any kitchen can serve any customer. If the recipe book, the customer's order history or half-cooked meals are kept in one kitchen, customers have to go back to that same kitchen every time, and adding kitchens helps much less. In software, that stored information is state, and a server that doesn't keep any between requests is stateless. Moving state out of the servers into shared stores is the single most important step in making a system scalable.

The analogy breaks in one important place: in a restaurant, a shared pantry is easy. In software, the shared store — usually the database — is itself a machine with limits, and making it grow is the hard part of scaling. Most of this track is about exactly that.

The four numbers that describe a system

To talk about scale precisely, engineers use a small set of measures. Throughput is how much work gets done per second, usually written as QPS (queries per second) or RPS (requests per second). Latency is how long one request takes, from sending it to getting the answer. Utilisation is how busy a resource is: a CPU at 70% utilisation is working 70% of the time. Availability is the fraction of time or of requests for which the system works; 99.9% ("three nines") allows about 8.8 hours of failure per year.

These measures pull against each other in predictable ways, and learning those relationships is most of the skill. Push utilisation up to save money and latency rises. Add redundant servers to raise availability and cost rises. Batch work together to raise throughput and each item waits longer. There is no free lunch; there are only trade-offs you choose deliberately.

Estimating before designing

Finally, scale is a question of how much. A URL shortener with 10 million new links a month turns out to need about 4 writes per second — a single database handles that without noticing. A photo app with 50 million daily users needs tens of petabytes of storage and over 50 gigabits per second of image traffic — that must come from object storage (a storage service built for huge numbers of files) and a CDN (a worldwide network of caching servers near users, covered in net12), not your own servers. The rough calculation that tells these two apart takes two minutes and prevents months of building the wrong thing. You will learn the method in the body and practise it in the drill.

1. Describing load precisely

"Lots of users" is not a design input. Before choosing anything, describe the load with numbers that match how the system will actually be stressed. The most useful ones are these.

Request rate, at average and at peak. Traffic is never flat: consumer apps are busiest in the evening, business tools during working hours, and some events (a push notification to every user, a ticket onsale, the top of every hour when scheduled jobs fire) create spikes many times the average. The ratio of peak to average is the peak factor; 2-5x is typical for steady consumer traffic, 10-100x for events.

Read-to-write ratio. A news site might serve 1,000 reads for every write; a logging pipeline might be nearly all writes. Reads can be scaled by copying data — keeping copies in a fast in-memory cache, or in extra read-only copies of the database called replicas — but writes cannot, because every copy must receive every write. So this one ratio largely decides the architecture.

Data volume and growth. How many bytes are stored today, how fast that grows, and how long it must be kept. A dataset that fits in one machine's memory is a completely different problem from one that doesn't fit on one machine's disks.

Fan-out. The number of downstream operations one request triggers. When a user with 500 followers posts, a feed system might write that post into 500 feeds. One incoming request becomes 500 writes, and that multiplier, not the number of posts, is what the storage layer feels.

Skew. Load is rarely spread evenly across data. A handful of celebrity accounts, one viral product page or one busy customer can receive a large share of traffic. A system that balances load by key can have one server on fire while the rest are idle. (Partitioning and hot keys get their own topic in sc7.)

2. Latency is a distribution, not a number

If you time 10,000 requests to a service, you don't get one number, you get a spread. Most requests might take 20-40 ms, some take 100 ms because they missed a cache, and a few take 2 seconds because they hit a garbage-collection pause, a slow disk or a retry. Summarising that spread with an average is misleading: a few very slow requests pull the average up while most users see fast responses, and a good average can hide a terrible experience for a significant minority.

Instead, engineers use percentiles. The p50 (median) is the latency that half of requests beat. The p99 is the latency that 99% of requests beat, so 1 in 100 is slower. The slowest requests are called the tail, and tail latency means high percentiles like p99 and p99.9.

Why obsess over the 1% tail? Because of fan-out. A web page that makes 50 backend calls in parallel can't render until the slowest one returns. If each call has a 1% chance of being slow, the chance that at least one of 50 is slow is 1 − 0.9950 ≈ 39.5%. The backend's p99 has become the page's typical experience. The more a request fans out, the more the tail of each part dominates the whole. This is also why your heaviest users — the ones who make the most requests — are the most likely to see the tail.

A worked example of a latency report for one service over an hour:

MeasureValueWhat it tells you
Average48 msLooks healthy — and hides the problem
p5031 msThe typical request is fast
p99420 ms1 in 100 requests is 13x slower than typical
p99.92,100 msProbably retries or timeouts; worth investigating

Reliability targets are usually written against percentiles: "99% of requests complete in under 300 ms over 30 days". Such a target is a service level objective (SLO); sc13 covers SLOs and error budgets in depth.

3. Throughput, latency and concurrency: Little's Law

Three quantities describe a running system at any moment: how fast requests arrive and complete (throughput, written λ, "lambda"), how long each spends inside (latency, W), and how many are inside at once (concurrency, L). Little's Law says they are always related by

L = λ × W        concurrency = throughput × latency

It holds for any stable system — a web server, a database, a checkout queue — regardless of how requests arrive. It is simple enough to use in your head and powerful enough to size real systems.

Worked example 1: a service handles 2,000 requests per second and each takes 100 ms (0.1 s). Then L = 2,000 × 0.1 = 200 requests are in flight at any moment. If each request occupies a thread for its whole duration, the fleet needs at least 200 threads, plus headroom; with 20 servers, that's 10 busy threads each on average.

Worked example 2, used in reverse: a server has a pool of 50 database connections, and each query holds a connection for 10 ms. The pool can complete at most 50 / 0.010 = 5,000 queries per second. If traffic needs 8,000, requests start queueing for a connection, and latency climbs even though the database itself may be fine.

Worked example 3, spotting trouble: a service normally handles 1,000 requests per second at 50 ms, so about 50 are in flight. A downstream dependency slows to 2 seconds. Traffic is the same, so in-flight requests jump to 1,000 × 2 = 2,000. If the server only has 200 threads, it runs out, new requests queue or get rejected, and a slow dependency has turned into an outage of a healthy service. That is the mechanism behind cascading failures, and why timeouts matter (sc12 covers them).

4. Why queues explode near full utilisation

Suppose a server can handle 100 requests per second. Intuition says it's fine up to 99 requests per second. It isn't, because requests don't arrive evenly spaced. They arrive at random, so in some 100 ms windows three arrive together and in others none do. When a burst arrives faster than the server can work, the extras wait in a queue. At low utilisation the server usually has idle time to drain the queue before the next burst. As utilisation rises, idle time disappears, queues are still draining when the next burst lands, and waiting time grows sharply.

The simplest queueing model (one server, random arrivals, random service times; known as M/M/1) gives a formula worth remembering:

response time ≈ service time / (1 − utilisation)

With a 10 ms service time:

UtilisationResponse timeMultiple of service time
10%11 ms1.1x
50%20 ms2x
80%50 ms5x
90%100 ms10x
95%200 ms20x
99%1,000 ms100x

Three practical lessons follow. First, capacity plans aim for around 50-70% utilisation at peak, not 95%, because that headroom is what keeps latency flat and absorbs bursts. Second, a small increase in traffic near the knee produces a huge increase in latency — going from 90% to 95% busy doubles response time — which is why systems seem fine one minute and collapse the next. Third, reducing service time helps twice: it lowers utilisation (the same traffic keeps the server less busy) and shrinks the base the multiplier applies to.

Real servers have many cores working in parallel, which behaves more gently than one server: the curve stays flat longer and bends later. But it always bends. You'll see the same shape for real in the lab.

5. Where time goes: the latency numbers

To reason about designs you need rough costs for basic operations. The classic table, popularised by Google's Jeff Dean, is worth memorising in orders of magnitude, not exact values (exact values vary by hardware and year):

OperationApproximate time
L1 CPU cache reference0.5-1 ns
Main memory (RAM) reference100 ns
Send 1 KB over a 1 Gbps network10 µs
Random 4 KB read from an SSD~100-150 µs (tens of µs on fast NVMe)
Read 1 MB sequentially from memory~250 µs (faster on modern hardware)
Round trip within one datacentre~500 µs
Read 1 MB sequentially from an SSD~1 ms
Spinning-disk seek~10 ms
Round trip California → Netherlands → California~150 ms

(1 ms = 1,000 µs = 1,000,000 ns.) The lessons matter more than the digits:

Memory is about a thousand times faster than a network hop, and a network hop inside a datacentre is hundreds of times faster than one across an ocean. So a design that makes 20 sequential calls between services in the same datacentre spends ~10 ms on round trips alone; if those calls cross regions, it spends seconds. "Chatty" designs die from round trips, not bandwidth.

The speed of light is a hard floor. Light in fibre covers about 200 km per millisecond, so a round trip between Europe and the US West Coast can never be much below ~90 ms, however fast your code is. The only fix is to move data or computation closer to users (CDNs, covered in net12, and multi-region designs in sc17).

Caching works because the gaps are huge. Serving a result from memory instead of re-running a 5 ms database query is a 10,000x difference in raw cost. That gap is why caching (sc3) is the first tool reached for when reads dominate.

6. Vertical scaling: the underrated first move

Vertical scaling means moving to a bigger machine: more CPU cores, more memory, faster disks. Its great virtue is that nothing about the software changes. Transactions, joins and locks all still happen inside one process on one machine, where they are fast and correct. There are no network partitions between parts of your data, no replicas to keep consistent, no new failure modes.

Modern machines are enormous. Cloud providers rent single servers with hundreds of virtual CPUs and several terabytes of memory, with local NVMe drives delivering hundreds of thousands to millions of I/O operations per second. A well-tuned relational database on such a machine can handle tens of thousands of transactions per second. For many products — including large, successful ones — that is enough for years.

The costs are real, though. There is a ceiling: once you're on the largest instance, there is nowhere left to go, and migrating to a distributed design at that point happens under maximum pressure. Price rises faster than capacity near the top end. One machine is a single point of failure (a SPOF): when it fails or needs maintenance, everything stops, so in practice you pair it with a standby replica (sc6). And blast radius grows: one huge database means one failure affects every user, and backups, restores and schema changes all take longer as the dataset grows.

A reasonable rule: scale up while the next size is affordable and the growth plan fits within the largest size with room to spare, and start designing the scale-out step well before you need it.

7. Horizontal scaling and why statelessness is the key

Horizontal scaling means adding machines. A load balancer (net10) receives every request and forwards it to one of a pool of identical servers. To double capacity, you double the pool. Losing one server just removes a fraction of capacity; the load balancer stops sending it traffic when its health checks fail.

This only works if any server can handle any request. Consider what goes wrong otherwise. If a user's login session lives in server A's memory, the load balancer must send every request from that user to A (a sticky session). Now load can't be rebalanced freely, a busy user stuck to A can't be moved, and when A crashes or is replaced during a deploy, all its users are logged out. If uploaded files are written to A's local disk, a request that lands on B can't find them. If a scheduled job runs on every server, adding servers multiplies the job.

The cure is to make application servers stateless: they keep nothing between requests. Every piece of state moves somewhere designed to be shared:

StateWhere it lives in a stateless design
Business data (users, orders)A database
Login sessionsA shared cache such as Redis, keyed by a session ID in a cookie — or a signed token the client sends each time
Uploaded files, images, videoObject storage (for example Amazon S3), served via a CDN
Cached computationsA shared cache tier
Background and scheduled workA job queue with workers (sc10), or a scheduler that runs each job once

Once that's done, servers become disposable. You can add ten during a traffic spike and remove them afterwards (autoscaling, sc15), replace any of them at any time, and deploy by rolling through the pool. The Twelve-Factor App principles (see refs) describe exactly this style.

Notice what hasn't happened: the state didn't disappear, it moved. The application tier is now easy to scale, and all the difficulty has been concentrated in the data tier, where it can be handled by systems built for it.

8. Scaling the data tier in stages

Databases are harder to scale out because they hold the state that everything else was made to share. Teams usually move through stages, taking the next one only when the current one runs out:

  1. Tune and scale up. Add the right indexes (sc4), fix slow queries, buy a bigger machine. Often a 10x gain for little risk.
  2. Cache reads. Put a cache in front of the database so repeated reads never reach it (sc3). With a 90% cache hit rate, the database sees a tenth of the read traffic.
  3. Add read replicas. Copies of the database receive every change from the primary and serve read-only queries (sc6). This multiplies read capacity but not write capacity, and replicas lag slightly behind, so a user might not immediately see their own write.
  4. Partition (shard). Split the data by a key — for example user ID — across several independent databases, each holding part of the data (sc7). This finally scales writes and data size, at the cost of cross-shard queries and transactions becoming hard.
  5. Use specialised stores. Move workloads that don't fit a relational database — full-text search, analytics, time series, huge key-value lookups — to systems built for them (sc8).

Each stage adds complexity and new failure modes, which is why you don't jump to sharding on day one. The estimation method below tells you which stage your numbers require.

9. The limits of adding machines: Amdahl and the USL

Scaling out is not magic. Suppose 95% of the work in each request is parallel (it can run on any server) but 5% is serial (it must pass through one shared thing: a single database row that every request updates, a global lock, a leader). Amdahl's law gives the best possible speed-up with N workers:

speed-up(N) = 1 / (s + (1 − s) / N)          s = serial fraction

With s = 0.05: 10 workers give 6.9x, 100 give 16.8x, and infinitely many give at most 1/0.05 = 20x. The serial 5% becomes the whole story.

Neil Gunther's Universal Scalability Law (USL) adds a second, nastier effect: coherency, the cost of nodes keeping each other in sync. If every node must exchange information with every other node — invalidating each other's caches, agreeing on a lock, gossiping membership — the work grows with the number of pairs of nodes, roughly N². The USL models relative capacity as

C(N) = N / (1 + σ(N − 1) + κN(N − 1))
σ (sigma) = contention (Amdahl's serial part)
κ (kappa) = coherency (pairwise coordination cost)

With any κ above zero, throughput rises, peaks and then falls as nodes are added. For example, with σ = 0.03 and κ = 0.0005, capacity peaks around 44 nodes at about 13.6x one node, and at 100 nodes it has fallen back to about 11x. This is the mathematical form of the experience "we added servers and it got slower". The practical takeaway: when adding nodes stops helping, stop adding nodes and find the shared resource.

10. Availability arithmetic

Availability is written in nines. The table below is worth knowing, because it turns an abstract percentage into minutes a human can reason about:

AvailabilityDowntime per yearPer 30-day month
99% (two nines)3.65 days7.2 hours
99.9% (three nines)8.77 hours43.8 minutes
99.99% (four nines)52.6 minutes4.4 minutes
99.999% (five nines)5.26 minutes26 seconds

At four nines, a single incident that takes 15 minutes for someone to be paged, log in and diagnose uses up three months of budget. High availability therefore requires automatic detection and failover, not heroics.

Components combine in two ways. In series — a request needs A and B and C to work — availabilities multiply, so the whole is worse than any part. A service at 99.9% that depends on four others at 99.9% gives 0.9995 ≈ 99.5%, about 44 hours of failure a year. In parallel — any one of several redundant copies is enough — failure requires all copies to fail at once, so unavailabilities multiply: two independent copies at 99% give 1 − 0.01 × 0.01 = 99.99%. That's the mathematical reason redundancy is so powerful, and the reason every critical component in a scalable system has at least two copies. The catch is the word independent: copies that share a region, a power supply, a deploy or a bug fail together, and real availability is always worse than the formula.

11. Back-of-envelope estimation, step by step

Estimation turns a product description into numbers that choose a design. A reliable method:

  1. State assumptions. Users, actions per user per day, sizes. Write them down; the interviewer mostly cares that you make them explicit and reasonable.
  2. Traffic. Daily requests ÷ seconds per day = average QPS. Use 105 seconds per day (really 86,400) to keep arithmetic easy. Multiply by a peak factor.
  3. Split reads and writes. The ratio decides caching and replication.
  4. Storage. New records per day × record size × retention days × replication factor.
  5. Bandwidth. QPS × response size, converted to bits per second (× 8).
  6. Servers and memory. Peak QPS ÷ realistic QPS per server (measure it; a simple API server does hundreds to a few thousand requests per second), plus headroom for utilisation and for losing a zone. For caches: the working set (the data actually requested frequently) that must fit in memory.
  7. Conclude. Say what the numbers mean: "fits on one database", "needs a CDN", "writes need sharding".

Useful constants: a day ≈ 105 s; a month ≈ 2.5 × 106 s; a year ≈ 3 × 107 s; 1 million requests per day ≈ 12 per second; 1 KB × 1 million = 1 GB; 1 Gbps ≈ 125 MB/s. Powers of ten: thousand = 103 (KB), million = 106 (MB), billion = 109 (GB), trillion = 1012 (TB), 1015 = PB.

Worked example — a URL shortener with 10 million new links per month, each read 100 times on average:

writes:   10,000,000 / 2.5M s        ≈ 4 per second
reads:    100 × writes               ≈ 400 per second average, ~2,000 at peak
storage:  10M links × 500 bytes      = 5 GB per month ≈ 60 GB per year
bandwidth: 2,000/s × 500 B           = 1 MB/s  (trivial)

Conclusion: one replicated database with a small cache in front is plenty for years. The interesting problems are short-code generation and availability, not scale. Recognising "this is small" is as valuable as recognising "this is huge".

12. A real-world walk-through: from one server to millions of users

Here is how the photo app from the opening actually grows, stage by stage, with the reasoning at each step. This is the story interviewers want to hear, because each step is driven by a specific bottleneck rather than by fashion.

Stage 1 — one server, about a thousand users. App, database and photos on one machine. Correct for a prototype: it's cheap and there's nothing to coordinate. The limit is that everything competes for the same CPU, memory and disk, and one failure takes down everything.

Stage 2 — separate the database, about 50,000 users. The database moves to its own, bigger machine, tuned for it: lots of memory so its working set is cached, fast disks. The web server can now be sized separately. Estimation at this stage: 50,000 DAU × 50 requests = 2.5 million requests per day ≈ 30 per second average, maybe 150 at peak. One app server and one database handle that easily; the real reason to move is isolation and the ability to grow each part independently.

Stage 3 — scale out the stateless tier, about a million users. Traffic is now 1M × 50 / 105 ≈ 500 per second average, ~2,500 at peak. One app server at maybe 500 requests per second would be at 500% utilisation, so the team puts a load balancer in front of six to eight app servers (peak ÷ per-server capacity, keeping each near 60% busy, plus spares for a lost zone). To make that possible, sessions move to Redis and photos move to object storage served through a CDN, so no server holds anything unique. The database is now the pressure point: reads outnumber writes 50:1, so a cache in front of it absorbs the popular reads (profile pages, the home feed) and a read replica takes the rest and doubles as a failover standby. Photos: 1M users × 0.2 uploads × 2 MB = 400 GB per day, about 150 TB per year, which is exactly what object storage is for.

Stage 4 — partition, about 50 million users. Now writes are the problem: 50M × 0.2 uploads plus likes, comments and follows is thousands of writes per second, and fan-out multiplies them. Metadata is growing by terabytes a year. The single primary can't keep up, so the data is sharded by user ID across many databases, each with its own replicas. Work that doesn't need to finish during the request — generating thumbnails, fanning a post out to followers' feeds, sending notifications — moves onto a queue processed by background workers (sc10), so the user's request returns quickly and bursts are absorbed by the queue instead of the database. Egress is over 50 Gbps, all served by the CDN.

The key habit this story teaches: at each stage, estimate, identify the resource that will saturate first, and apply the cheapest change that relieves it. Instagram famously served tens of millions of users with a very small engineering team using essentially this sequence, with a sharded PostgreSQL setup at its core.

Scalability has several dimensions, and each needs a different tool

"Scale" is not one axis. Request volume is handled by stateless replication and caching. Data volume is handled by partitioning and tiered storage (hot data on fast disks, cold data in cheap object storage). Write volume is handled by partitioning and by turning synchronous work into asynchronous work. Fan-out is handled by choosing when to do the work: at write time (precompute each follower's feed) or at read time (assemble the feed when asked), usually a hybrid with celebrities treated specially. Geographic spread is handled by CDNs and multi-region deployment. Number of tenants (customers in a business product) brings noisy neighbours, which needs isolation and per-tenant limits. Organisational scale — hundreds of engineers changing one system — is handled by service boundaries and contracts (sc14). A senior answer names which dimension is actually growing before proposing a technique, because solving the wrong one adds complexity without helping.

Tail latency amplification and how large systems fight it

As the fan-out example showed, when one user request touches many servers, the slowest server sets the pace. At large fan-out, even rare hiccups — a garbage-collection pause, a background compaction, a noisy neighbour on shared hardware — happen on some server during almost every request. Google's "The Tail at Scale" paper describes the techniques used against this. Hedged requests send a request to one replica and, if no answer arrives within, say, the p95 latency, send a second copy to another replica and use whichever answers first; this costs a few percent extra load and cuts the tail dramatically. Tied requests send to two replicas at once and let the one that starts first cancel the other. Micro-partitioning splits data into many more partitions than machines, so a slow or hot machine can shed a few partitions quickly. The underlying lesson: at scale you design for variability, not for the average machine.

Open versus closed load, and why load tests lie

In a closed system, a fixed number of clients each wait for a response before sending the next request; when the server slows down, the clients automatically slow down too. In an open system, new requests keep arriving at the same rate no matter how slow the server gets — which is what real internet traffic does, since millions of independent users don't know the server is struggling. Many load-testing tools are closed by default, so they report polite, flattering numbers: latency rises but the server never gets buried. Real open traffic past capacity grows the queue without bound until timeouts and retries create a collapse. A related trap called coordinated omission happens when a tool that waits for slow responses stops sending requests during a stall and therefore never records the requests that would have been delayed, hiding the worst latencies. Senior engineers use open-model tools (constant arrival rate) for capacity tests and know to distrust a p99 from a closed-loop tool.

Retries turn overload into collapse

When a server is overloaded, some requests time out. Clients retry, which adds load, which causes more timeouts, which causes more retries. With three retries per layer and three layers of services, one user request can become 4 × 4 × 4 = 64 requests at the bottom layer. This feedback loop is how a brief spike becomes an outage that persists after the spike ends — a metastable failure: the system stays down even though the original trigger is gone, because the retry load alone exceeds capacity. The defences are retry budgets (limit retries to a small percentage of traffic), exponential backoff with random jitter, retrying at only one layer, and load shedding: rejecting excess requests quickly and cheaply so the ones you accept still succeed. sc12 covers these patterns.

Cost is a scaling dimension

A system that handles 10x the load at 10x the cost scales technically but may not scale as a business. Senior engineers express capacity in unit economics — cost per 1,000 requests, per active user, per gigabyte stored — and watch whether it rises, stays flat or falls with growth. Egress bandwidth, cross-zone data transfer and over-provisioned idle capacity are frequent surprises. The trade-offs are explicit: running at 40% utilisation buys latency and failure headroom at the price of paying for 60% idle; reserved or committed capacity is cheaper than on-demand but less flexible; a CDN costs money but is far cheaper per gigabyte than serving from origin.

Headroom for failure, not just for peak

Capacity must cover peak traffic while something is broken. If you run in three availability zones (separate datacentres in one region) and plan for losing one, the remaining two must carry the full peak, so each zone needs 50% of peak capacity, and the fleet as a whole is sized at 150% of peak. Add utilisation headroom (say, target 60% busy) and growth until the next capacity review, and the provisioned fleet is often 2-3x the raw peak. Explaining where that multiplier comes from — rather than presenting it as waste — is a good senior signal.

Estimation technique that survives scrutiny

Strong candidates do a few extra things. They sanity-check results against known systems ("that's more QPS than Google Search — one of my assumptions is wrong"). They separate the number that drives the design from the ones that don't and spend their time on the former. They carry units through every step to catch errors (requests per day divided by seconds per day gives requests per second). And they finish every estimate with a design consequence, because the number itself is never the point.

How scaling problems show up

Scaling failures rarely announce themselves as "out of capacity". They show up as rising p99 latency while p50 stays flat — the queue has started to form but most requests still get through quickly. Then timeouts and 503 errors ("service unavailable") appear in bursts at peak times. Thread pools and connection pools saturate: requests wait for a worker or a database connection rather than for CPU, so CPU can look healthy while users suffer. Replication lag grows on database replicas, so users see stale data. And finally cascading failure: a slow component ties up the resources of everything that calls it, and the outage spreads upstream.

The standard way to spot these early is the USE method (from Brendan Gregg): for every resource — CPU, memory, disk, network, pools, locks — check its Utilisation (how busy), Saturation (how much work is queued waiting for it) and Errors. For each service, watch the RED metrics: request Rate, Error rate and Duration (latency percentiles). A dashboard that shows rate and p99 latency together makes the hockey stick visible: as rate climbs toward capacity, p99 bends upward first.

Tools and knobs

Capacity is measured, not guessed. Load-testing tools such as k6, Locust, Gatling, wrk2 and Vegeta drive traffic at a service; prefer ones that can generate a constant arrival rate (open model) for capacity tests. The routine is to ramp traffic until latency breaks its target, note the throughput at that point as the real per-server capacity, and plan with 30-50% headroom below it. In production, the main knobs are the number of instances (manually or by autoscaling on CPU or request rate), per-instance concurrency limits (worker threads, connection pool sizes — sized with Little's Law), timeouts, cache sizes and TTLs, and the instance size of the database.

Real incidents

Pokémon GO (2016). Niantic and Google planned for a traffic target with a worst-case estimate of about 5x that target. Within hours of launch, traffic reached about 50x the target — ten times the worst case. Google's engineers had to provision capacity continuously, upgrade the container platform and replace the load-balancing layer while the game was live. The lesson isn't "estimate better"; it's that launch estimates are unreliable, so you build headroom, load-test beyond the worst case, and design so that overload degrades gracefully (queueing players into the game) instead of collapsing.

Ticketmaster and The Eras Tour (2022). Ticketmaster reported 3.5 billion total system requests during the presale — four times its previous peak — driven by fans and by bot traffic, far beyond the planned invited audience. The site slowed and failed, queues stalled, and the general sale was cancelled. It is a textbook synchronised-demand event: daily averages are meaningless when millions of people arrive in the same minute, and the protective tools are admission control (a virtual waiting room that lets people in at a rate the backend can sustain), bot filtering, and pre-scaled capacity rather than reactive autoscaling.

A quieter but more common pattern: a scheduled job at midnight or the top of the hour — every client syncing at :00, every cron job firing together — produces a spike far above the daily peak. Adding random jitter to schedules spreads the load and is one of the cheapest scaling fixes there is.

In this lab you'll build a tiny server with a fixed capacity, push load at it, and watch Little's Law and the utilisation curve happen for real. It needs only Python 3 (standard library) and takes about 10 minutes.

  1. Save this as sc1_server.py. It has exactly 4 "workers", and each request takes 20 ms of work, so its capacity is 4 / 0.020 = 200 requests per second.

    import threading, time
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler

WORKERS = threading.Semaphore(4)   # capacity = 4 workers / 0.020 s = 200 requests/s

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        with WORKERS:              # wait here if all 4 workers are busy (this is the queue)
            time.sleep(0.020)      # the "work": 20 ms of service time
        self.send_response(200)
        self.send_header("Content-Length", "2")
        self.end_headers()
        self.wfile.write(b"ok")
    def log_message(self, *args):  # keep the terminal quiet
        pass

ThreadingHTTPServer(("127.0.0.1", 8080), Handler).serve_forever()

  2. Save this as sc1_load.py. It runs a closed-loop test: N clients each send a request, wait for the answer, and repeat, for 5 seconds per step.

    import http.client, statistics, threading, time

def client(stop, latencies):
    conn = http.client.HTTPConnection("127.0.0.1", 8080)
    while time.perf_counter() < stop:
        t0 = time.perf_counter()
        conn.request("GET", "/")
        conn.getresponse().read()
        latencies.append(time.perf_counter() - t0)

for n in [1, 2, 4, 8, 16, 32]:
    latencies, stop = [], time.perf_counter() + 5
    threads = [threading.Thread(target=client, args=(stop, latencies)) for _ in range(n)]
    for t in threads: t.start()
    for t in threads: t.join()
    x = len(latencies) / 5                                  # throughput, requests per second
    q = statistics.quantiles(latencies, n=100)
    print(f"clients={n:3d}  throughput={x:6.0f}/s  p50={q[49]*1000:6.1f} ms  "
          f"p99={q[98]*1000:6.1f} ms  N/X={n/x*1000:6.1f} ms")

  3. Start the server in one terminal (python sc1_server.py) and run the load test in another (python sc1_load.py). A typical run on a laptop:

    clients=  1  throughput=    44/s  p50=  22.5 ms  p99=  23.5 ms  N/X=  22.5 ms
clients=  2  throughput=    88/s  p50=  22.6 ms  p99=  23.6 ms  N/X=  22.6 ms
clients=  4  throughput=   177/s  p50=  22.6 ms  p99=  24.2 ms  N/X=  22.6 ms
clients=  8  throughput=   194/s  p50=  41.4 ms  p99=  60.5 ms  N/X=  41.2 ms
clients= 16  throughput=   196/s  p50=  82.8 ms  p99= 142.9 ms  N/X=  81.6 ms
clients= 32  throughput=   199/s  p50= 165.0 ms  p99= 309.6 ms  N/X= 160.6 ms

What to look for. Up to 4 clients, throughput grows linearly and latency stays at the service time (20 ms plus ~2.5 ms of overhead): the system is scaling. At 4 clients all workers are busy; from then on throughput is stuck at about 200 per second — the capacity you calculated — and every extra client only adds waiting time. Latency doubles each time clients double, because they are queueing. The last column is Little's Law rearranged (W = N / X): computed purely from the client count and throughput, it matches the measured median latency almost exactly. And p99 grows faster than p50 once the queue exists — the tail suffers first.

Try next. Change the semaphore to 8 (scaling up the workers) and rerun: throughput plateaus at ~400. Change the sleep to 10 ms (making the work faster) and see capacity double again. Both are the two basic scaling moves in miniature. Note that this is a closed-loop test, which is why latency grows smoothly instead of exploding; in the deep section you read why real, open traffic behaves worse.

Estimate it

A photo-sharing app: 50M daily active users, each views 60 photos and uploads 0.2 photos per day. Average photo 2 MB stored, served as a 200 KB thumbnail in feeds. Keep photos forever, 3 replicas. Estimate read and write QPS, storage growth per year, and egress bandwidth for thumbnails, and say what the numbers imply for the design.

Answer
  • Uploads: 50M × 0.2 = 10M per day ÷ ~86,400 s ≈ 115 writes/s average; with a peak factor of 3-4, about 400/s at peak.
  • Views: 50M × 60 = 3B per day ≈ 35,000 reads/s average, ~100,000/s at peak. The read:write ratio is about 300:1, so reads must be served from caches and a CDN.
  • Storage: 10M × 2 MB = 20 TB per day of new photos; × 3 replicas = 60 TB per day ≈ 22 PB per year. Only object storage makes sense at this size, and it typically uses erasure coding (splitting data into pieces plus parity so it survives losses with about 1.5x overhead instead of 3x). Thumbnails add about 10%.
  • Egress: 35,000/s × 200 KB = 7 GB/s; × 8 bits = 56 Gbps average, well over 100 Gbps at peak. That must come from a CDN; no reasonable origin fleet should serve it directly.

Conclusions to state out loud: the write path is small (a few hundred uploads per second, easily handled by a handful of stateless upload servers writing to object storage and a metadata database); the design problem is read fan-out and bytes. So the architecture is object storage plus a CDN for the photos, a cache in front of the metadata, and a metadata database (photo ID, owner, timestamp, a few hundred bytes per photo, so about 1 TB per year) that fits on a replicated primary for a long time before it needs sharding. Estimation is only useful when it leads to decisions like these.
