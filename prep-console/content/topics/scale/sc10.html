A user clicks "Place order" on a shopping site. In the first version of the code, that one request does everything in sequence: saves the order, charges the card, sends a confirmation email through an email provider, generates a PDF invoice, notifies the warehouse system, updates the search index so the product's stock count is right, credits loyalty points and records an analytics event. On a good day it takes three seconds. On a bad day the email provider is slow, and every checkout takes fifteen seconds; when the warehouse system is down for maintenance, checkouts fail outright, even though the customer doesn't care when the warehouse hears about the order. On Black Friday, traffic triples for an hour, and every one of those downstream systems gets hammered at the same moment as the database.

The fix is to notice that most of that work doesn't need to happen while the customer waits. The order must be saved and paid for before saying "done"; the email can go out ten seconds later, the invoice a minute later, the analytics an hour later. If the checkout just records the order and drops a note — "order 8812 was placed" — into a queue, each of the other jobs can pick up the note and do its part in its own time, at its own pace, retrying if it fails. Checkout becomes fast and reliable, a slow email provider affects only emails, and a traffic spike becomes a backlog that drains over the next few minutes instead of an outage.

That's asynchronous processing, and the tools for it — message queues, publish-subscribe systems and logs like Apache Kafka — are among the most important building blocks in scalable systems. They also bring their own hard problems, which interviewers probe relentlessly. A message may be delivered twice, so the loyalty service credits points twice. Messages may arrive out of order. A malformed message may fail forever and block everything behind it. A queue may grow for hours without anyone noticing, so "successful" orders aren't actually being shipped.

This lesson builds the whole picture: why and when to go asynchronous, the three messaging models (queues, pub/sub and logs) and what each is good for, how Kafka actually works — topics, partitions, offsets, consumer groups, replication — delivery guarantees and why "exactly once" really means idempotent consumers, retries and dead-letter queues, ordering, back-pressure, schemas, and how to publish events reliably from a database. It ends with a full event-driven design for that order pipeline.

The analogy: a restaurant's order rail

In a busy restaurant, the waiter doesn't stand in the kitchen watching each dish being cooked. They write the order on a ticket, clip it to the rail, and go back to serve other tables. Cooks take tickets from the rail when they're ready. If a rush of customers arrives, tickets pile up on the rail and the cooks work through them; nobody is turned away at the door. If one cook goes on break, the others keep taking tickets. The rail is a queue: the waiter is a producer, the cooks are consumers, and each ticket is a message.

Now suppose several stations need to know about each order: the grill, the salad station and the dessert station each need a copy. That's publish-subscribe: one published message, many subscribers. And suppose the restaurant keeps every ticket in a numbered ledger instead of throwing it away, so a new station can read yesterday's orders, and each station keeps a bookmark of how far it has got. That's a log, which is how Kafka works.

The analogy also shows the problems. If a cook takes a ticket, starts cooking, and faints, does someone else notice and redo the dish — possibly producing it twice? If tickets pile up faster than the cooks can work, at what point do you stop seating customers? The analogy breaks in one way: in software, the "rail" is itself a distributed system that can fail, and "did the cook finish?" is a network message that can be lost.

Synchronous versus asynchronous, concretely

The rule for what goes where: if the user needs the result to continue — the payment must be authorised before you can say "order confirmed" — it stays synchronous. If the user doesn't need it right now, or can be told about it later, it can go asynchronous. A useful test: if this step took ten minutes instead of ten milliseconds, would the customer notice at checkout? Saving the order and charging the card stay; everything else becomes a consumer of the OrderPlaced event.

Asynchronous processing buys four things. Latency: the user waits only for the essential work. Burst absorption: a spike becomes a backlog that consumers drain at a sustainable rate, instead of overload (sc1's queueing curve, moved out of the request path). Decoupling: producers and consumers don't need to be up at the same time, can be deployed separately, and don't need to know about each other. Fan-out: one event feeds any number of consumers, and new ones can be added without changing the producer. What it costs is also four things: duplicates, reordering, eventual rather than immediate results, and a new system to operate and monitor. Most of this lesson is about paying those costs safely: making duplicates harmless, keeping the order that matters, and noticing quickly when the work falls behind.

1. Three messaging models

"Messaging" covers three different models, and choosing the right one is the first design decision.

Message queue (point-to-point). Producers send messages to a queue; each message is delivered to one consumer, which processes it and acknowledges it, and then the broker deletes it. Many consumers can read from the same queue, competing for messages, which spreads work across workers — the work queue or competing-consumers pattern. Queues typically offer per-message features: individual acknowledgements, retries with delays, dead-letter queues, priorities, scheduled delivery. Examples: RabbitMQ, Amazon SQS, ActiveMQ, and job-queue libraries like Celery or Sidekiq on top of Redis or RabbitMQ. Use for distributing tasks: "resize this image", "send this email".

Publish-subscribe (pub/sub). Producers publish to a topic, and every subscriber to that topic gets its own copy. The producer doesn't know who's listening. Examples: Amazon SNS, Google Cloud Pub/Sub, RabbitMQ exchanges, Redis pub/sub (which is fire-and-forget: subscribers that aren't connected miss messages). A common AWS pattern is SNS topic → one SQS queue per subscribing service, so each subscriber gets a durable queue of its own. Use for broadcasting events: "order placed" to fulfilment, email and analytics.

Log (stream). Producers append messages to a durable, ordered, partitioned log that's retained for a configured time (days, or forever) regardless of consumption. Consumers read at their own pace and remember their position; nothing is deleted when read. Many independent consumer groups can read the same log, each getting every message, and any of them can rewind and replay. Examples: Apache Kafka, Amazon Kinesis, Apache Pulsar, Redpanda. Use when several systems need the same stream of events, when you need replay (rebuild a search index, reprocess after a bug fix, backfill a new service), for change data capture, and for stream processing.

2. How Kafka works

Kafka is the most widely used log, and its model is worth knowing in detail because interviews go deep on it.

Topics and partitions. A topic (say orders) is split into partitions, each an ordered, append-only log stored on disk. Each message in a partition has an offset: its position, 0, 1, 2… Partitions are the unit of parallelism and of ordering. Order is guaranteed within a partition and not at all across partitions.

Producers and keys. A producer sends a message with an optional key. Kafka hashes the key to choose the partition, so every message with the same key — say order ID 8812 — goes to the same partition and is stored in the order it was sent. Messages without a key are spread across partitions. Choosing the key is the Kafka version of choosing a shard key (sc7): it decides what stays in order together and how evenly load spreads.

Brokers and replication. Partitions are spread over a cluster of servers called brokers. Each partition is replicated to several brokers (the replication factor, typically 3): one replica is the partition's leader, which takes all reads and writes, and the others follow it — single-leader replication exactly as in sc6. Replicas that are fully caught up form the in-sync replica set (ISR). Since Kafka 4.0 (2025), cluster metadata and leader election are managed by Kafka's own Raft-based controller quorum (KRaft) rather than ZooKeeper.

Consumers, groups and offsets. Consumers read partitions sequentially from an offset. A consumer group is a set of consumer instances that share a topic's work: Kafka assigns each partition to exactly one member of the group, and a member may own several partitions. So a group processes partitions in parallel, but there's never more than one active consumer per partition in a group, which is what preserves order. Consumers periodically commit the offset they've processed up to; after a restart, a consumer resumes from its group's last committed offset. Different groups — fulfilment, analytics, search — have independent offsets, so each gets every message at its own pace.

Two consequences follow. Parallelism within a group is capped by the partition count: 12 partitions allow at most 12 busy consumers, and a 13th sits idle. And when members join, leave or crash, the group rebalances: partitions are reassigned, and during a rebalance the affected partitions pause. Kafka 4.0 made a new rebalance protocol generally available that moves partitions incrementally, reducing those pauses; techniques like static membership keep a restarting consumer from triggering a rebalance at all.

Retention and compaction. Messages are kept for a retention period (7 days by default) or up to a size limit, whether or not anyone has read them, which is what makes replay possible. Alternatively a topic can use log compaction, keeping only the latest message for each key — turning the topic into a changelog of current values, useful for rebuilding state ("the latest address for every customer").

Why it's fast. Kafka writes are sequential appends to files, which disks and SSDs handle very efficiently; reads of recent data come from the operating system's page cache; producers and consumers batch messages; and data is sent to consumers with zero-copy transfer from file to network. A modest cluster handles hundreds of thousands to millions of messages per second.

3. Durability: when is a message safe?

A producer's write is only as safe as the acknowledgement it waits for, the same trade-off as synchronous versus asynchronous replication in sc6. With acks=0 the producer doesn't wait at all (fast, can lose messages). With acks=1 it waits for the partition leader to write the message, but if the leader fails before followers copy it, the message is lost. With acks=all it waits until every in-sync replica has the message. The topic setting min.insync.replicas closes the last gap: with replication factor 3 and min.insync.replicas=2, the leader refuses writes if fewer than two replicas are in sync, so every acknowledged message is on at least two brokers. That configuration survives one broker failure with no loss and keeps accepting writes; with two brokers down, writes to affected partitions stop — consistency over availability, per partition.

Producers also retry on errors, and a retry after a lost acknowledgement would store a duplicate. Idempotent producers (on by default in modern Kafka clients) attach a producer ID and sequence number to each message so the broker discards duplicates from retries and keeps order.

Queues have equivalents: SQS stores each message redundantly across multiple servers before acknowledging the send; RabbitMQ's quorum queues replicate messages with Raft (sc9).

4. Delivery semantics: why duplicates are normal

Consider a consumer processing one message. It must do two things: perform the effect (credit points, send an email) and tell the broker it's done (acknowledge, or commit the offset). A crash can happen between them, and which order you choose decides what a crash does.

At-most-once: acknowledge first, then process. A crash after the acknowledgement loses the message — it will never be delivered again. No duplicates, possible loss. Acceptable only where loss is harmless (some metrics).

At-least-once: process first, then acknowledge. A crash after processing but before the acknowledgement means the broker redelivers, and the message is processed again. No loss, possible duplicates. This is the practical default for anything that matters.

Exactly-once delivery — each message delivered and processed exactly one time, guaranteed — can't be achieved in general over an unreliable network. The core problem is the one from sc9: if the acknowledgement is lost, the broker can't tell whether the consumer processed the message or crashed before doing so. It must either redeliver (risking a duplicate) or not (risking loss). What systems achieve is effectively-once processing: the result is as if each message were processed once. Two ways:

  • Idempotent consumers — make processing a duplicate harmless (next section). This works for any broker and any side effect you control.
  • Kafka transactions — for "read from Kafka, process, write to Kafka" pipelines, a transactional producer writes its output messages and the consumer's offset commit in one atomic transaction; consumers reading with isolation.level=read_committed never see output from aborted attempts. This is what "exactly-once semantics" in Kafka and Kafka Streams means. It covers only effects inside Kafka; an email sent from the consumer is outside the transaction.

Duplicates also come from elsewhere: a consumer that's slower than its visibility timeout or poll interval (section 7), a rebalance that moves a partition before its offset was committed, and a producer that retries a send without idempotence. Designing for at-least-once and idempotency covers all of them.

5. Idempotent consumers

An operation is idempotent if doing it several times has the same effect as doing it once. "Set the order status to shipped" is naturally idempotent; "add 10 loyalty points" is not. Making consumers idempotent is the single most important technique in asynchronous systems. The standard methods:

A processed-messages table in the same transaction. Give every message a unique ID (the producer sets it, for example the event ID from the outbox). In the consumer, inside the same database transaction as the effect, insert the ID into a table with a unique constraint:

BEGIN;
INSERT INTO processed_events (event_id) VALUES ('evt-8812-placed')
  ON CONFLICT DO NOTHING;
-- if that inserted 0 rows, this event was already handled: COMMIT and acknowledge
UPDATE users SET points = points + 10 WHERE id = 42;
COMMIT;
-- then acknowledge the message

If the consumer crashes before the commit, both the insert and the update roll back and the redelivered message is processed properly; if it crashes after the commit but before the acknowledgement, the redelivery finds the ID and skips. The dedup record and the effect must commit atomically — if they're in different systems, a crash between them breaks the guarantee. Processed IDs are kept for longer than any redelivery window, then expired.

Natural idempotency. Shape the effect so repetition doesn't matter: upsert the full current state rather than applying a delta ("set stock to 17" rather than "subtract 1"), or write conditionally on a version ("update where version = 5"), ignoring events older than what's stored. This also makes consumers tolerant of reordering.

Idempotency keys for external calls. Payment providers, email services and many APIs accept an idempotency key: send the event ID with the request, and a retried request with the same key returns the original result instead of charging or sending again. Stripe's API is the classic example.

You'll see the effect of duplicates, and of a processed-IDs check, in the lab.

6. Retries, backoff and dead-letter queues

Processing fails for two kinds of reasons. Transient failures — a timeout, a database failover, a rate-limited API — succeed if you try again later. Permanent failures — a malformed message, a reference to a deleted record, a bug — fail every time. A poison message is one that fails permanently.

Retry transient failures with exponential backoff and jitter — wait 1 s, 2 s, 4 s, 8 s, each with some randomness — so a struggling dependency isn't hammered by synchronised retries (sc12 covers this). After a limit (say 5 attempts spread over several minutes), stop retrying and move the message to a dead-letter queue (DLQ). SQS does this automatically with a redrive policy (after maxReceiveCount receives); RabbitMQ with dead-letter exchanges; in Kafka, consumers implement it by publishing failed messages to retry topics (with increasing delays) and finally a dead-letter topic, then committing the offset to move on.

A DLQ is only useful with three things around it: an alert when messages arrive there (each one is unfinished work — an order not shipped), an owner who investigates, and a redrive tool to send messages back to the main queue once the bug is fixed. Distinguish transient from permanent errors in code where you can: retrying a validation error five times just delays the inevitable, while dead-lettering a timeout on the first failure throws away work that would have succeeded.

7. Visibility timeouts, leases and slow consumers

A broker has to know when a consumer has stopped working on a message, so the message can be given to someone else. Each system has a timeout for this, and getting it wrong causes duplicate concurrent processing.

In SQS, receiving a message doesn't delete it; it hides it from other consumers for the visibility timeout (30 seconds by default, up to 12 hours). The consumer must delete the message within that time. If processing takes longer — a large batch, a slow dependency, a 45-second PDF — the message reappears and another consumer starts on it while the first is still working. Set the timeout comfortably above the worst-case processing time, or have the consumer extend it periodically as it works.

In Kafka, a consumer owns its partitions as long as it keeps polling. If it doesn't call poll again within max.poll.interval.ms (5 minutes by default) — because it's stuck processing a huge batch — the group decides it's dead and rebalances its partitions to another member, which resumes from the last committed offset and reprocesses everything since. Keep per-poll work bounded (max.poll.records) and move genuinely long work elsewhere.

8. Ordering

Ordering guarantees are narrow and expensive, so first decide what you actually need. Global order across all messages would force a single partition and a single consumer — no parallelism — and is almost never required. What's usually needed is per-entity order: an order's events (placed, paid, shipped, delivered) must be processed in sequence, while different orders are independent.

Get per-entity order by routing on the entity's key: the Kafka partition key, or the MessageGroupId of an SQS FIFO queue (which delivers messages within a group in order and one at a time; standard SQS queues don't guarantee order). Then protect it from things that silently break it: processing messages from one partition in parallel threads without keying the threads; producer retries without idempotence (a retried message can land after the next one); changing the partition count (keys move to new partitions); and dead-lettering a failed message while later messages for the same key continue, so "shipped" is processed without "paid".

The most robust approach is to make consumers tolerant of disorder: include a version number or sequence in each event, store the last applied version per entity, and ignore events older than what's stored. Then occasional reordering is harmless, and retries and replays are safe.

9. Back-pressure and backlogs

A queue smooths bursts only if consumers are faster than producers on average. If they're not, the backlog grows forever — and because producers see success, nobody notices until customers complain that orders placed hours ago haven't shipped. Little's Law (sc1) makes the cost concrete: a backlog of 360,000 messages drained at 100 per second means every new message waits an hour.

So asynchronous systems need monitoring of consumer lag — preferably as time ("the oldest unprocessed message is 4 minutes old") rather than count, since a count means different things for different topics — and back-pressure: a way to slow producers or shed load when the backlog passes a limit. Options include bounded queues that reject or block new messages, producers that check lag and degrade (delay non-critical events, sample analytics), rate-limited relays in front of consumers, and autoscaling consumers on lag (up to the partition count for Kafka).

The broker's own capacity matters too. An in-memory broker that fills up fails hard, which is exactly what happened to Slack (prod section): their Redis-based job queue filled memory during a slowdown and then couldn't even dequeue. Durable, disk-backed logs like Kafka can hold large backlogs for days, which is why they're often used as the buffer in front of a faster but less forgiving execution layer.

10. Events as a contract: schemas and reliable publishing

Once several teams consume an event, its format is a public API. Changing a field name or type breaks consumers you may not even know about. So events get explicit, versioned schemas (Avro, Protobuf or JSON Schema), usually stored in a schema registry that rejects incompatible changes. The usual rules are backwards-compatible evolution: add optional fields with defaults, never remove or retype fields that consumers use, and create a new event type or topic for breaking changes.

Events also have to be published reliably. The naive code — write the order to the database, then publish OrderPlaced to Kafka — has the dual-write problem from sc8: if the process crashes between the two, or the publish fails, the order exists with no event (fulfilment never hears about it), or, if you publish first, an event exists for an order that rolled back. The fixes:

Transactional outbox. In the same database transaction as the order, insert the event into an outbox table. A separate relay process reads committed outbox rows in order, publishes them to the broker, and marks them published. The event exists if and only if the order committed. The relay may publish a row twice (if it crashes after publishing but before marking), so consumers must be idempotent — which they are anyway.

Change data capture. Publish directly from the database's write-ahead log with a tool like Debezium: every committed change to the outbox (or to business tables) becomes an event in commit order, with no polling.

A related design choice is what an event contains. A thin event ("order 8812 changed") forces consumers to call back to the source for details, coupling them to its API and its availability. A fat event (the full order state at that moment) lets consumers work independently, at the cost of larger messages and more careful schema management. Most event-driven systems prefer events that carry the data consumers need.

11. A real-world walk-through: an event-driven order pipeline

Here's the checkout from the opening, redesigned. Peak load is 500 orders per second; downstream work per order is an email, a PDF invoice, a warehouse notification, a loyalty update, a search-index update and analytics.

The synchronous path. The order service validates the cart, reserves stock with an atomic conditional update, authorises payment with an idempotency key, and in one database transaction writes the order and an OrderPlaced row into the outbox. It returns "order confirmed" in about 300 ms. Nothing else is on the path.

Publishing. A Debezium connector reads the outbox table from the database log and publishes each event to the Kafka topic orders.v1, keyed by order ID, so each order's lifecycle events stay in one partition in order. The topic has 48 partitions (headroom for 48 parallel consumers per group), replication factor 3, min.insync.replicas=2, and 7-day retention. Events follow a versioned Protobuf schema in a schema registry and carry the order's full state, so consumers don't need to call the order service.

Consumers, each an independent group. Notifications sends email and push messages, passing the event ID as the provider's idempotency key. Invoices generates PDFs — slow (up to 45 s) — so it consumes events and enqueues invoice jobs onto an SQS work queue with a 5-minute visibility timeout, processed by a separately scaled worker pool. Fulfilment creates the warehouse shipment, using a processed-events table in its database for idempotency. Loyalty credits points the same way. Search upserts product stock levels with version checks, so replays and reordering are harmless. Analytics streams everything into the warehouse (sc18). None of them knows about the others; adding a fraud-scoring consumer next month requires no change to checkout.

Failure handling. Each consumer retries transient errors with exponential backoff through two retry topics (1-minute and 10-minute delays) and then a dead-letter topic of its own. A dead-letter message pages the owning team, and a small tool shows the message, the error and a "redrive" button. For fulfilment, where order matters, a failed event parks all later events for the same order until it's resolved, while other orders flow.

Capacity and monitoring. At 500 orders per second, each consumer group must sustain at least that; the slowest, fulfilment, processes events one at a time with a 25 ms warehouse API call each, so one instance handles about 40 per second and peak needs 500 ÷ 40 ≈ 13 instances; the team runs 20 for headroom against API latency spikes, autoscaled on lag up to the 48-partition limit. Each group's lag in seconds is on a dashboard with alerts — for example, fulfilment lag above 2 minutes pages, analytics lag above 30 minutes warns. On Black Friday, when traffic triples for an hour, checkout stays fast; the email and analytics lags grow to a few minutes and drain afterwards, which is exactly the trade the design intended.

What changed for the business. The email provider's outage last month delayed receipts by twenty minutes and affected nothing else; warehouse maintenance windows no longer block sales; and a bug in loyalty points was fixed by replaying seven days of events into a corrected consumer. Those three sentences are the value of asynchronous design, and they're a good way to close an interview answer.

The log as the backbone of data systems

Jay Kreps, one of Kafka's creators, argued that an ordered, replicated log is the unifying abstraction behind databases, replication and data integration: a database's write-ahead log is a log of changes, replication streams that log (sc6), and consensus agrees on a log (sc9). Kafka makes that log a shared, durable service. The architectural consequence is powerful: if every important change is an event in a retained log, then caches, search indexes, warehouses and new services are all derived views that can be built, rebuilt or added by consuming the log from the start. Change data capture turns an existing database into such a source without rewriting applications. This is the basis of "turning the database inside out" and of the derived-data architecture in sc8 — and it depends on replay, which queues can't provide.

Event sourcing and CQRS, and their costs

Event sourcing takes the log idea to the application's core: instead of storing an order's current state and overwriting it, store the sequence of events (created, item added, paid, shipped) as the source of truth, and compute the current state by replaying them. It gives a complete audit history, the ability to answer "what did we know at time T?", and the freedom to build new read models later. CQRS (command-query responsibility segregation) often accompanies it: writes go to the event-sourced model, and reads are served from separate, denormalised read models kept up to date from the events. The costs are real: schema evolution of years of stored events, replay time for long histories (mitigated with snapshots), eventual consistency between write and read models, and a steep learning curve. It fits domains where history is intrinsically important — ledgers, audit-heavy workflows — and is overkill for ordinary CRUD.

Kafka rebalancing, in depth

Rebalances are the main source of latency spikes and duplicate processing in Kafka consumers. In the original "eager" protocol, every rebalance revoked all partitions from all members, reassigned them and restarted consumption — a stop-the-world pause for the whole group, triggered by any member joining, leaving, crashing or simply taking too long to poll. Cooperative incremental rebalancing (and the new broker-driven consumer protocol that became generally available in Kafka 4.0) moves only the partitions that need to move, so most members keep working. Static membership gives each consumer instance a persistent ID, so a restarting instance (during a rolling deploy) gets its partitions back without a rebalance if it returns within a session timeout. And committing offsets correctly around rebalances — committing processed offsets when partitions are revoked — limits how much is reprocessed. Understanding these is the difference between a consumer that stutters on every deploy and one that doesn't.

Choosing partition counts

The partition count sets the maximum consumer parallelism per group, and changing it later remaps keys (breaking per-key order during the change), so it's chosen with growth in mind. A common method: estimate the peak throughput the topic must sustain, measure the throughput one consumer can achieve per partition for the slowest consumer group, and divide, then add headroom — for example, 500 messages per second needed and 20 per second per consumer for the slowest group gives at least 25 partitions; choose 48. Too many partitions has costs: more open files and memory on brokers, longer leader elections and recovery after broker failures, more consumer overhead, and small batches. Hot keys don't benefit from more partitions at all, since one key always maps to one partition. For queues-style workloads that need more parallelism than partitions, consumers can process messages concurrently within a partition, keyed by message key to preserve per-key order, and the newer "share groups" feature in Kafka 4.x adds queue-like consumption where many consumers share a partition's messages with per-message acknowledgement.

Choreography versus orchestration

In an event-driven system, a multi-step business process can be coordinated two ways. With choreography, each service reacts to events and emits its own — payment emits PaymentCaptured, fulfilment reacts and emits ShipmentCreated — with no central coordinator. It's loosely coupled and easy to extend, but the overall flow exists only implicitly, spread across services, which makes it hard to see, change and debug ("why is this order stuck?"). With orchestration, a coordinator (a workflow engine like Temporal, AWS Step Functions or a dedicated saga orchestrator) explicitly drives the steps, calls services or sends commands, tracks state, and handles timeouts and compensation. It's easier to reason about and monitor at the cost of a central component. Many systems use choreography for loosely related reactions (notifications, analytics) and orchestration for business-critical multi-step processes with compensation (sc11 covers sagas).

Delay, scheduling and priority in logs

Queues make delayed delivery ("process this in 15 minutes") and priorities easy; logs don't, because a partition is strictly ordered and consumers read it sequentially. Common patterns in Kafka: retry topics with fixed delays, where a consumer reads a message, checks its due time, and pauses the partition until then; a separate scheduler service that stores due items in a database and publishes them when due; or keeping delay-sensitive work in a queue (SQS delay queues, RabbitMQ delayed exchanges) and using the log for the event stream. Priorities are handled by separate topics per priority with consumers that favour the high-priority one. Recognising which features a workload needs is how you decide between a queue, a log, or both — which is the most common answer in practice.

How asynchronous systems fail

Silent backlog. A consumer slows (a dependency degraded, a bad deploy) and lag grows for hours while producers report success. The first signal is often a customer: "my order confirmation never arrived". Alert on lag in time, per consumer group, with thresholds that match each consumer's business needs.

Duplicate side effects. Customers receive two emails, loyalty points are credited twice, or a payment is attempted twice, after a rebalance, a visibility-timeout expiry or a redeploy. The cause is a non-idempotent consumer; the fix is idempotency keys and processed-message tables.

Poison message loops. One malformed message fails, is retried, fails again, and in a FIFO queue or a single partition blocks everything behind it. Symptoms: lag on one partition grows while others are fine, and the same error repeats in logs. Fix with bounded retries, dead-lettering and per-key parking.

Rebalance storms. Consumers that take too long per poll are kicked out, triggering rebalances, during which nobody makes progress, and then they time out again. Symptoms: frequent rebalance logs, lag that grows in steps. Fix by bounding work per poll, tuning timeouts and using cooperative rebalancing and static membership.

Broker capacity. Disks filling up because retention is too long for the write rate, an under-replicated partition count that stays above zero (brokers can't keep up or one is down), or an in-memory broker running out of memory under a backlog.

What to watch

Per consumer group: lag per partition in messages and seconds, processing rate, error rate, retry and dead-letter rates, rebalance frequency. Per topic: produce rate, bytes in and out, partition skew (is one partition much busier?). Per broker: disk usage and growth, under-replicated partitions, offline partitions, request latency, and controller health. For queues: approximate queue depth, age of the oldest message, number of in-flight (received but not deleted) messages, DLQ depth. Also track end-to-end latency with a timestamp in each event, from when it was produced to when each consumer finished, because that's what the business actually experiences.

Knobs

Kafka producer: acks, idempotence, batching (linger.ms, batch.size) and compression. Topic: partition count, replication factor, min.insync.replicas, retention time and size, compaction. Consumer: max.poll.records, max.poll.interval.ms, session timeout, commit strategy, assignment strategy, static membership. SQS: visibility timeout, maxReceiveCount before dead-lettering, long polling (WaitTimeSeconds, which reduces empty receives and cost), batch sizes, and message retention (4 days by default, up to 14). Everywhere: retry counts and backoff, consumer autoscaling thresholds on lag.

A real incident: Slack's job queue

Slack's asynchronous work — every message post, push notification, link unfurl, reminder and billing calculation — ran through a job queue built on Redis. Web servers hashed each job to a Redis host and pushed it onto a list; workers popped jobs, moved them to an in-flight list, and removed them when done. At peak the system handled over 1.4 billion jobs a day, around 33,000 per second. During one incident, database contention made job processing slow down sharply. Jobs kept arriving faster than workers finished them, so the Redis lists grew until Redis neared its memory limit. At that point the system was stuck: dequeuing a job (moving it to the in-flight list) itself needed free memory, so workers couldn't even take jobs off the queue. Even after the database recovered, the queue stayed locked up and needed extensive manual intervention. Slack's redesign put Kafka in front of Redis: web servers write jobs through a small stateless service into Kafka, whose disk-based, replicated log can absorb huge backlogs, and a relay moves jobs from Kafka into Redis at a controlled, configurable rate for the existing workers to execute. The lessons are the ones in section 9: the buffer must be able to hold a large backlog without failing, an in-memory broker has a cliff when it fills, and decoupling enqueue from execution with a rate-limited relay gives you back-pressure you can control.

A two-minute simulation of at-least-once delivery, showing why duplicates happen and how an idempotent consumer neutralises them. It needs only Python 3.

import random
random.seed(7)
messages = [{"id": f"evt-{i}", "user": "u1", "points": 10} for i in range(100)]

def run(idempotent):
    queue, points, processed = list(messages), 0, set()
    while queue:
        msg = queue.pop(0)
        if idempotent and msg["id"] in processed:
            continue                               # seen it: skip, just acknowledge
        points += msg["points"]                    # the side effect
        processed.add(msg["id"])                   # (in real life: same DB transaction)
        if random.random() < 0.1:                  # 10%: crash before the ack...
            queue.append(msg)                      # ...so the broker redelivers it
    return points

print("at-least-once, naive consumer:      ", run(False), "points (expected 1000)")
print("at-least-once, idempotent consumer: ", run(True), "points (expected 1000)")

Output:

at-least-once, naive consumer:       1140 points (expected 1000)
at-least-once, idempotent consumer:  1000 points (expected 1000)

What it shows. Each message's side effect happens, and then 10% of the time the consumer "crashes" before acknowledging, so the broker redelivers the message. The naive consumer applies those redeliveries again and credits 140 extra points — a real bug in real loyalty systems. The idempotent consumer records each message ID when it applies the effect and skips IDs it has seen, so redeliveries are harmless and the total is exactly right.

Think it through. (1) Move processed.add to after a simulated crash point: why must the dedup record and the effect be committed together, in one database transaction? (2) Swap the order so the "ack" happens before the effect (at-most-once): what goes wrong now? (3) The consumer also sends an email per message through an external provider. Your dedup table can't be in the provider's transaction — what do you send the provider instead?

Find the bugs

An SQS consumer processes payment-captured events and sends a receipt email and credits loyalty points:

while True:
    for msg in sqs.receive(max=10, visibility_timeout=30):
        sqs.delete(msg)                      # acknowledge first
        event = json.loads(msg.body)
        email.send_receipt(event["order_id"])        # ~1 s
        db.execute("UPDATE users SET points = points + %s WHERE id = %s",
                   (event["points"], event["user_id"]))
        # large orders also generate a PDF invoice, ~45 s
        if event["total"] > 1000:
            make_invoice(event["order_id"])
Answer
  • Deleting before processing = at-most-once: a crash after delete loses the receipt and the points forever. Delete after successful processing.
  • Once you switch to at-least-once, the points update is not idempotent: a redelivery credits points twice. Record processed event IDs in the same transaction (INSERT INTO processed_events (id) … ON CONFLICT DO NOTHING, and only credit if the insert happened), or make it a conditional write.
  • Visibility timeout (30 s) is shorter than processing for a batch of 10, and certainly for the 45 s invoice: the message reappears and another consumer processes it concurrently. Extend the timeout (or heartbeat with ChangeMessageVisibility) and move invoice generation to its own queue with its own timeout and workers.
  • No failure handling: one poison message raises and kills the loop. Catch errors per message, let failed messages return to the queue (don't delete them), and configure a redrive policy to a DLQ after a few receives, with an alert on DLQ depth.
  • Email is a side effect outside the database: duplicates are still possible; pass the event ID as an idempotency key to the email provider, or record "receipt sent" and check it first.
  • Processing a batch of 10 sequentially with 1 s emails caps throughput at a few messages per second per consumer; process concurrently within the batch or scale consumers on queue depth and message age.
