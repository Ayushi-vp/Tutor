A team runs its API on six virtual machines that someone set up by hand three years ago. Deploying means SSH-ing into each machine, pulling the new code, restarting the process and hoping nothing goes wrong; it takes an hour and happens every two weeks. The machines have slowly drifted apart — different library versions, a config file edited on one of them during an incident — so "works on server 3" is a real phrase. When traffic doubles on Black Friday, adding capacity means ordering new machines days ahead. When a machine dies at night, someone is paged to rebuild it. When a release breaks something, rolling back is another hour of SSH.

The modern answer comes in layers. Containers package an application with everything it needs into an immutable image, so the exact same artefact runs on a laptop, in testing and in production. An orchestrator — overwhelmingly, Kubernetes — runs those containers across a fleet of machines and keeps them in the state you declare: six replicas, spread across three zones, restarted if they crash, replaced if their machine dies. Autoscaling adds and removes replicas and machines as load changes. Deployment strategies — rolling updates, blue-green switches, canary releases — change the running version safely, with rollback in seconds. And infrastructure as code keeps all of it in version control, reviewed and reproducible.

Each layer also brings its own failure modes, which is why they come up so often in interviews. A container killed for exceeding its memory limit restarts in a loop. A liveness probe that checks the database restarts every pod the moment the database blips. A CPU limit throttles a service into latency spikes even though the machine is idle. Autoscaling responds in minutes to a spike that peaked in seconds. A rolling update without graceful shutdown throws errors at users on every deploy. A cluster upgrade removes a label that an undocumented networking configuration depended on, and a major website goes down for five hours — which is what happened to Reddit in 2023.

This lesson builds the platform from the bottom up: what a container really is, how Kubernetes' control loops work, the core objects and how traffic reaches pods, probes and graceful shutdown, requests and limits, the three layers of autoscaling and their delays, deployment strategies and feature flags, safe database changes during rollouts, and infrastructure as code with GitOps — ending with a complete setup for a latency-sensitive API.

The analogy: shipping containers and a port authority

Before standard shipping containers, cargo was loaded piece by piece — sacks, barrels, crates of every shape — and every port handled it differently. The standard container changed everything: whatever is inside, the box has the same shape, so every crane, ship, train and truck can handle it the same way. A software container image does the same for applications: whatever language or libraries are inside, it's started, stopped and moved the same way everywhere.

Now picture a port authority managing thousands of containers across many ships and docks. You don't tell it which crane lifts which box; you tell it what you want — "these 60 containers must reach the warehouse by Friday" — and it works out placement, routes around broken cranes, and re-plans when a ship is late. That's Kubernetes: you declare the desired state ("run six copies of this image with this much memory, reachable as api"), and its controllers continuously work to make reality match, placing containers on machines, replacing failed ones and routing traffic.

The analogy breaks in two ways. Software containers aren't sealed steel boxes: they share the host machine's kernel, so their isolation is much thinner than a VM's. And the port authority in software never stops re-checking: Kubernetes doesn't act once and walk away, it compares desired and actual state in a loop, forever.

The layers of a modern platform

Reading the diagram top to bottom: continuous integration builds an immutable image from the code and pushes it to a registry, tagged with a version. The desired state — which image, how many replicas, how much CPU and memory, which probes — is written as manifests in Git. A GitOps agent applies them to the Kubernetes control plane, whose scheduler places pods on nodes spread across availability zones. Autoscalers adjust the number of pods and nodes as load changes. A Service gives the pods one stable name for callers (sc2). To deploy a new version, you change the image tag in Git; the platform does the rest, gradually and reversibly.

The payoff compared with the hand-built VMs: every environment runs the same artefact; a crashed process or a dead machine is repaired automatically in seconds or minutes, without a page; capacity follows load; deploys take minutes, many times a day, with rollback by reverting a commit. The cost is a genuinely complex platform that must be understood and operated — which is why most of this lesson is about the details that decide whether it helps or hurts.

A few terms will recur, so here they are up front. A node is a machine in the cluster. A pod is the unit Kubernetes runs — one or more containers scheduled together. A probe is a periodic health check the platform runs against a container. Requests and limits are the CPU and memory a container reserves and may not exceed. A rollout is the process of replacing one version with another. Each gets a full section below; the point for now is that every one of them is something you declare, and the platform enforces.

1. What a container really is

A container isn't a special kind of machine. It's an ordinary Linux process that the kernel treats specially in two ways.

Namespaces give the process its own view of the system. In its own PID namespace, it sees itself as process 1 and can't see other processes. In its own network namespace, it has its own network interfaces, IP address and ports. In its own mount namespace, it sees its own root filesystem. There are also namespaces for users, hostnames and inter-process communication. Nothing is emulated; the kernel simply filters what the process can see.

cgroups (control groups) limit and measure what the process can use: CPU time, memory, I/O bandwidth, number of processes. If a container exceeds its memory limit, the kernel kills it (you'll see OOMKilled); if it tries to use more CPU than its quota, the kernel throttles it.

The container's filesystem comes from an image: a stack of read-only layers, each recording the changes made by one build step (install the OS packages, install Python dependencies, copy the application). Layers are content-addressed and shared, so a hundred images built on the same base layer store it once, and pushing a new version usually only uploads the top layer. When a container starts, a thin writable layer is added on top; anything written there disappears when the container is removed, which is why containers are treated as disposable and state lives elsewhere (sc1).

Because containers share the host's kernel, they start in milliseconds, add almost no overhead and pack densely onto machines. The same fact means weaker isolation than a virtual machine, which runs its own kernel on virtualised hardware: a kernel vulnerability can let a container escape to the host. Multi-tenant platforms that run untrusted code therefore add sandboxing — gVisor intercepts system calls in user space; Firecracker and Kata Containers run each workload in a lightweight VM with its own kernel.

A good production image is small (a minimal or "distroless" base), built with a multi-stage build (compile in one stage, copy only the result into a clean final stage, so compilers and build tools don't ship), pins dependency versions, runs as a non-root user, runs one main process, reads configuration from environment variables or mounted files rather than baking it in, and is tagged with an immutable version (never deployed as :latest, which makes it impossible to know or roll back what's running).

2. Kubernetes as a set of control loops

Kubernetes has a control plane and a set of worker nodes. The control plane consists of the API server (the front door: every read and write of cluster state goes through it), etcd (the consensus-replicated key-value store holding all cluster state, sc9), the scheduler (which decides which node each new pod runs on) and controllers (which implement the behaviour of each kind of object). Each node runs the kubelet (an agent that starts and monitors the containers assigned to its node, through a container runtime such as containerd) and a network proxy or equivalent plugin (sc2).

The central idea is reconciliation. You never tell Kubernetes "start three containers on these machines". You write an object describing desired state — "a Deployment named api with 6 replicas of image api:1.42.0" — and store it via the API server. Controllers watch for changes and, in a loop, compare desired with actual state and act to close the gap. Here's a trace of what happens when you apply that Deployment:

  1. The Deployment controller sees a new Deployment and creates a ReplicaSet (an object that keeps a fixed number of identical pods running) for version 1.42.0 with 6 replicas.
  2. The ReplicaSet controller sees it needs 6 pods and has 0, so it creates 6 pod objects, each without a node assigned.
  3. The scheduler sees unassigned pods, picks a node for each (filtering nodes without enough unreserved CPU and memory, then scoring the rest — spreading across zones, packing efficiently), and records the choice.
  4. Each chosen node's kubelet sees pods assigned to it, pulls the image if needed, starts the containers, runs their probes, and reports status.
  5. When a pod becomes ready, the endpoint controller adds its IP to the Service's endpoints, and it starts receiving traffic.

Later, a node dies. Its kubelet stops reporting; after timeouts, the node is marked not ready and its pods are evicted. The ReplicaSet controller now sees 4 running pods where 6 are desired and creates 2 more; the scheduler places them on healthy nodes. Nobody was paged. That self-healing falls out naturally from control loops: they don't care why actual state differs from desired, they just fix it.

3. The core objects

Pod: the smallest unit Kubernetes schedules — one or more containers that share a network identity (one IP address, reachable from each other on localhost) and can share storage volumes. Usually one main container, sometimes plus sidecars (a service-mesh proxy, a log shipper). Kubernetes now supports native sidecars that start before and stop after the main container (stable since version 1.33). Pods are disposable: they're never repaired or moved, only replaced, and a replacement gets a new IP.

Deployment: the standard way to run stateless services. It manages ReplicaSets and performs rolling updates between versions (section 7).

StatefulSet: for workloads where each replica needs a stable identity and its own storage — databases, Kafka brokers, ZooKeeper or etcd. Pods get stable names (kafka-0, kafka-1), stable DNS entries through a headless Service (sc2), and each its own persistent volume that follows it when it's rescheduled. They're started and updated in order.

DaemonSet: one pod on every node (or every matching node), for node-level agents: log collectors, monitoring agents, network plugins.

Job and CronJob: run pods to completion, once or on a schedule, for batch work and migrations.

Service gives a set of pods a stable virtual IP and DNS name and load-balances connections across the ready ones; Ingress and its successor the Gateway API route HTTP traffic from outside into Services (sc2 covers these in depth).

ConfigMap and Secret hold configuration and credentials, mounted into pods as files or environment variables. Kubernetes Secrets are only base64-encoded by default, so production clusters enable encryption at rest in etcd and often source secrets from an external manager (a cloud secret store or Vault) through an operator.

Namespace (the Kubernetes kind, not the Linux kind) groups resources for a team or environment, and is the unit for access control, resource quotas and network policies.

4. Probes and graceful shutdown

Kubernetes can only route traffic well and restart the right things if it knows the state of each container, which it learns from three probes (HTTP requests, TCP connections or commands, run periodically by the kubelet).

Readiness: "should this pod receive traffic now?" While it fails, the pod is removed from Service endpoints but left running. Use it during startup and warm-up, and optionally when the pod is temporarily overloaded. Liveness: "is this container stuck beyond recovery?" After several consecutive failures, the kubelet restarts the container. It should test only that the process can make progress — respond on a local endpoint — and never external dependencies: if liveness checks the database, a database blip fails every pod's liveness and Kubernetes restarts the entire fleet, turning a partial problem into a total outage while caches go cold. Startup: "has this slow starter finished starting?" Until it succeeds, liveness and readiness aren't checked, so a JVM application that needs 40 seconds to start isn't killed by a liveness probe after 5.

Probe settings matter: periodSeconds (how often), timeoutSeconds, and failureThreshold (consecutive failures before acting). A liveness probe with a threshold of 1 restarts a pod after a single slow garbage-collection pause; 3 or more is typical.

Graceful shutdown is the other half of zero-downtime operation. When a pod is deleted — during a deploy, a scale-down or node maintenance — two things happen at once: the kubelet sends the container a SIGTERM signal, and the pod is removed from Service endpoints, a change that propagates to load balancers and every node's routing rules over the next second or so. If the application exits immediately on SIGTERM, requests routed to it during that window fail, and in-flight requests are cut off. The standard recipe:

  • A preStop hook that sleeps a few seconds (commonly 5-10), so endpoint removal propagates before the application starts shutting down.
  • On SIGTERM, stop accepting new connections, finish in-flight requests, close connections and exit.
  • A terminationGracePeriodSeconds (30 s by default) longer than the preStop sleep plus the longest request; after it, the container is killed with SIGKILL.

With readiness probes on the way in and graceful shutdown on the way out, deploys and scale-downs become invisible to users.

5. Resources: requests, limits and quality of service

Each container declares requests and limits for CPU (in cores or millicores: 500m is half a core) and memory. A request is a reservation used by the scheduler: a node can only accept pods whose requests fit in its unreserved capacity. A limit is a cap enforced by the kernel through cgroups.

The two resources behave very differently when a container goes over. Memory can't be taken back from a process, so a container that exceeds its memory limit is killed (OOMKilled) and restarted; if it keeps happening, you see CrashLoopBackOff. CPU can be shared, so a container that exceeds its CPU limit isn't killed but throttled: it may use its quota within each scheduling period (100 ms by default) and then waits for the next period. For a request handler, that shows up as latency spikes — a request that needed 60 ms of CPU in a burst waits for the next period — even when the node has idle CPU. Throttling is a very common, confusing cause of poor tail latency.

Common practice therefore is: set memory request equal to limit, based on measured usage plus headroom, so the container's memory is guaranteed and its behaviour predictable; set CPU requests accurately, from load tests, so scheduling and fair sharing work; and leave CPU limits off or generous for latency-sensitive services (in shared clusters, namespace quotas and requests prevent abuse). Requests also determine a pod's quality-of-service class — Guaranteed (requests equal limits for all containers), Burstable, or BestEffort (none set) — which decides eviction order when a node runs short of memory: BestEffort pods go first.

Language runtimes must be told about container limits: a JVM, a Node.js process or a pool of Python workers sized from the host's total memory or CPU count will overcommit and be OOM-killed or throttled. Modern JVMs read cgroup limits (set -XX:MaxRAMPercentage), and worker counts should come from the container's CPU request, not the machine's core count.

Getting requests right is also the biggest lever on cost: requests far above real usage waste nodes (you pay for reserved but idle capacity), while requests far below it overpack nodes and cause contention. The Vertical Pod Autoscaler recommends requests from observed usage, and since Kubernetes 1.35, a running pod's CPU and memory can be resized in place, often without restarting its containers.

6. Autoscaling at three layers

Autoscaling in Kubernetes happens at three independent layers, and understanding how they interact explains both what they can do and why they're slow.

Replicas: the Horizontal Pod Autoscaler (HPA). The HPA adjusts a Deployment's replica count from a metric averaged across pods. Every 15 seconds by default, it computes:

desired replicas = ceil( current replicas × current metric ÷ target metric )

If pods target 100 requests per second each and 4 pods are handling 150 each, desired = ceil(4 × 150/100) = 6. If the ratio is within 10% of 1, it does nothing, to avoid flapping. Scale-down is deliberately cautious: by default the HPA uses the highest recommendation of the last 5 minutes before removing pods, because removing capacity during a brief dip and re-adding it moments later is worse than holding it. Minimum and maximum replica counts bound it.

The metric matters more than anything else. CPU utilisation (relative to requests) is the default and works for CPU-bound services. For I/O-bound services — waiting on databases, other services or external APIs — CPU can be low while the service is saturated, so scale on requests per second per pod, in-flight requests, or latency. For queue consumers, scale on queue length or consumer lag (sc10); KEDA (Kubernetes Event-Driven Autoscaling) makes this easy, reading metrics from Kafka, SQS, Prometheus and many other sources, and can scale to zero when there's no work.

Pod size: vertical scaling. The Vertical Pod Autoscaler recommends or applies better CPU and memory requests based on observed usage, and in-place resize lets it adjust running pods. It's mostly used to right-size workloads over days rather than to react to spikes, and shouldn't fight the HPA on the same metric.

Nodes: Cluster Autoscaler and Karpenter. When pods can't be scheduled because no node has enough unreserved capacity, the Cluster Autoscaler adds nodes to a node group; when nodes are underused and their pods fit elsewhere, it removes them. Karpenter (originally from AWS) provisions nodes directly, choosing instance types to fit the pending pods, which is faster and more flexible.

Why it takes minutes. Add up the chain for a traffic spike: metrics are scraped every 15-30 seconds and often averaged over a minute; the HPA evaluates every 15 seconds; new pods are scheduled — and if nodes are full, a new node must be created and join the cluster, typically one to several minutes; the image must be pulled (seconds to minutes for large images); the application starts and warms up (JIT compilation, caches, connection pools) before passing readiness. End to end, two to five minutes is common. A flash crowd peaks in seconds. So autoscaling is excellent for daily traffic curves and poor for spikes, which need: headroom (target 50-70% utilisation, sc1); pre-scaling for known events (a scheduled scale-up before a launch or a sale); fast startup and small images; overprovisioning with low-priority placeholder pods that reserve spare node capacity and are instantly preempted by real pods; and load shedding (sc12) for what nobody predicted.

You'll trace the HPA's arithmetic through a traffic ramp in the lab.

7. Deployment strategies

Changing the running version is where most incidents start (sc13), so how you deploy matters as much as what you deploy.

Rolling update (the Deployment default). A new ReplicaSet is created and scaled up while the old one is scaled down, a few pods at a time. Two settings control the pace: maxSurge (how many extra pods may exist above the desired count during the rollout) and maxUnavailable (how many pods may be unavailable). With 10 replicas, maxSurge: 25% and maxUnavailable: 0, Kubernetes adds up to 3 new pods, waits until they're ready, removes 3 old ones, and repeats — capacity never drops below 10. It's cheap and simple. Its weaknesses: old and new versions serve traffic side by side for the duration, and a bad version keeps rolling out unless something stops it.

Blue-green. Run the new version (green) as a complete second deployment alongside the current one (blue), test it, then switch all traffic at once by changing the Service's selector or the load balancer's target. Rollback is instant: switch back. The costs are double capacity during the switch and all users moving to the new version at the same moment, so a bug that testing missed hits everyone.

Canary. Send a small fraction of real traffic — 1% or 5% — to the new version while the rest stays on the old, compare the two versions' error rates and latency, and increase the fraction in steps (5%, 25%, 50%, 100%) only while the canary stays healthy. If it degrades, traffic goes back to the old version automatically. This limits the blast radius of a bad version to a small slice of users for a few minutes. It needs traffic splitting (a service mesh, an ingress controller that supports weights, or replica ratios) and automated analysis; tools like Argo Rollouts and Flagger run canaries against Prometheus metrics, gating each step on SLO-style checks (sc13).

A PodDisruptionBudget complements all of these: it limits how many pods of an application voluntary disruptions — node drains during upgrades, autoscaler scale-down — may take down at once ("at most 1 unavailable", or "at least 80% available"), so routine maintenance never removes too much capacity.

8. Feature flags: separating deploy from release

A feature flag is a runtime switch that turns a code path on or off — globally, per user segment, or for a percentage of users — without deploying. It separates two things that are otherwise welded together: deploying code (putting a new build into production, which can now happen continuously with new paths switched off) and releasing a feature (exposing it to users, gradually, by changing the flag).

The benefits are large. A new checkout flow can be enabled for employees, then 1% of users, then 10%, watched at each step, and turned off in seconds if its metrics worsen — much faster and less risky than a rollback. Incomplete work can be merged and deployed behind an off flag, avoiding long-lived branches. Kill switches — flags that disable expensive, non-essential features — give operators a way to shed load during incidents (sc12's degraded modes).

Flags have costs. Every flag is a branch in the code, so combinations multiply and testing gets harder; stale flags that are always on clutter the code, so every flag needs an owner and a removal date. And flag changes are production changes: they need an audit log, review for risky flags, and gradual rollout — a flag flipped to 100% globally is exactly as dangerous as a global deploy. Conversely, the absence of a flag can hurt: Google Cloud's June 2025 outage (sc13) involved a new code path shipped enabled everywhere with no flag to switch it off.

9. Database changes during rolling deploys

Every strategy above runs old and new application versions at the same time — during the rollout, and again if you roll back. So database schema changes must work with both versions at once. The technique is expand-contract (also called parallel change), which swe9 introduced and which applies to APIs too (sc14). Renaming a column zip to postal_code safely takes several releases:

  1. Expand: add the nullable column postal_code. Old code ignores it.
  2. Deploy code that writes both columns and still reads zip.
  3. Backfill postal_code for existing rows in small batches (so the migration doesn't lock the table or flood replication, sc6).
  4. Deploy code that reads postal_code (still writing both, so a rollback to the previous version works).
  5. Deploy code that stops writing zip.
  6. Contract: drop zip once no running or rollback-able version uses it.

At every step, every version that might be running works. The DDL itself must also be safe on a live database: adding a nullable column is usually instant; adding a column with a default, changing a type or adding a constraint can rewrite or lock the table in some databases; indexes are built concurrently (sc4); and migrations set a lock_timeout so that, if they can't get their lock quickly, they fail instead of queueing every query behind them. Migrations run as a separate, controlled pipeline step — not automatically inside every replica's startup, where replicas would race and a rollback wouldn't undo them.

10. Infrastructure as code and GitOps

Infrastructure as code (IaC) defines infrastructure — networks, load balancers, databases, Kubernetes clusters, DNS records, permissions — in files kept in version control and applied by tools: Terraform or its open-source fork OpenTofu, Pulumi (using general-purpose languages), AWS CloudFormation and others. The benefits are the same as for application code: changes are reviewed in pull requests, the history shows who changed what and why, environments can be recreated identically, and drift — differences between the declared and actual state, from someone clicking in a console — can be detected. Terraform works by computing a plan (the changes needed to make reality match the files), which is reviewed, then applied; it records what it manages in a state file, which must be stored remotely with locking so two people can't apply conflicting changes.

GitOps applies the same idea continuously to what runs in Kubernetes. The desired state of every application — manifests or Helm charts with image versions, replica counts, configuration — lives in a Git repository. An agent in the cluster, such as Argo CD or Flux, continuously compares the cluster with the repository and applies any difference, and reverts manual changes made outside Git. Deploying means merging a change to the repository (often automated by CI bumping the image tag); rolling back means reverting the commit; the Git history is the audit log. The OpenGitOps principles summarise it: declarative, versioned and immutable, pulled automatically, continuously reconciled — the same reconciliation idea as Kubernetes itself, one level up.

The discipline matters most for exactly the configuration people are tempted to set by hand, once, and forget: network plugin settings, cluster add-ons, IAM policies. That's where the Reddit outage in the prod section came from.

11. A real-world walk-through: running a latency-sensitive API

A payments-adjacent API must keep p99 latency under 200 ms and 99.95% availability, handles 2,000 requests per second at peak with daily swings of 4×, and has occasional marketing-driven spikes. Here's the platform setup, piece by piece.

Image. A multi-stage build produces a 90 MB distroless image running as a non-root user, tagged with the Git commit hash. Startup, including warm-up of connection pools and caches, takes 8 seconds.

Sizing from a load test. One pod sustains 250 requests per second within the latency target at about 1.5 CPU cores and 700 MiB of memory. Requests are set to 1.5 CPU and 1 GiB memory, memory limit 1 GiB, and no CPU limit, avoiding throttling-induced tail latency (the namespace has a quota to keep the team honest).

Placement. Topology spread constraints spread pods evenly across three zones; a PodDisruptionBudget allows at most one pod unavailable at a time during maintenance.

Probes and shutdown. A startup probe allows up to 30 seconds; readiness checks the pod's own ability to serve (it has loaded configuration and warmed its pools); liveness is a trivial local endpoint with a failure threshold of 3. A preStop hook sleeps 10 seconds; the application drains in-flight requests on SIGTERM; the grace period is 45 seconds.

Scaling. The HPA scales on requests per second per pod, targeting 150 (60% of the measured 250), At peak, 2,000 ÷ 150 ≈ 14 pods are needed; to survive losing a zone at peak, the two remaining zones must still hold 14, so 21 pods are needed across three zones. A scheduled scale-up (a simple CronJob raising the HPA minimum) sets the minimum to 21 during peak hours and relaxes it to 6 at night, when traffic is a quarter of peak. Maximum 60. Scale-up policy allows doubling every 30 seconds; scale-down waits 5 minutes. Karpenter provisions nodes, and a few low-priority placeholder pods keep one node's worth of headroom warm. Before announced marketing campaigns, the minimum is raised an hour ahead.

Deploys. Argo Rollouts runs canaries: 5% for 10 minutes, then 25%, 50%, 100%, with each step gated on the canary's error rate being below 0.1% and its p99 below 200 ms compared with the stable version; failure triggers automatic rollback. Risky features ship behind flags with gradual percentage rollout. Schema changes follow expand-contract, run as a separate migration Job with a lock timeout.

Everything in Git. Terraform manages the cluster, node pools, database and networking; Argo CD syncs application manifests from Git; manual changes are reverted automatically.

What each piece buys. A crashed pod is replaced in seconds without traffic loss; a node or zone failure is absorbed by spread and headroom; the daily curve is handled by the HPA; marketing spikes by pre-scaling and headroom; bad releases reach 5% of users for ten minutes at most; and any engineer can see, in Git, exactly what's running and why. The team gets paged for what actually needs a human.

How the scheduler decides, and why requests are the whole game

The scheduler works in two phases for each pod. Filtering removes nodes that can't run it: not enough unreserved CPU or memory (based on requests, not actual usage), missing required labels, taints the pod doesn't tolerate, volume or topology constraints it can't satisfy. Scoring ranks the rest — spreading replicas across zones and nodes, packing efficiently, preferring nodes that already have the image. Because filtering uses requests, a cluster can be "full" while its CPUs sit mostly idle (requests inflated beyond real usage), or overcommitted and contended (requests too low). Controls on top: taints and tolerations reserve nodes for specific workloads (GPU nodes only for GPU jobs), affinity and anti-affinity co-locate or separate pods, topology spread constraints enforce even spreading across zones, and priority classes let critical pods preempt lower-priority ones when the cluster is full — which is also how overprovisioning placeholders work.

CPU throttling in detail

CPU limits are enforced by the kernel's CFS bandwidth control: a container with a limit of 1 CPU gets a quota of 100 ms of CPU time per 100 ms period, across all its threads. A multi-threaded process with 8 threads doing work can consume its entire 100 ms quota in the first 12.5 ms of the period and then be frozen for the remaining 87.5 ms. Average utilisation looks modest — perhaps 40% of the limit — while individual requests stall for tens of milliseconds, producing p99 latency spikes that correlate with nothing obvious. The metric that reveals it is the throttled-periods counter (container_cpu_cfs_throttled_periods_total in cAdvisor metrics). This is why many performance-focused teams remove CPU limits for latency-sensitive services while keeping accurate requests, which still guarantee each container its share under contention because CPU shares are proportional to requests.

Multi-tenancy and security in clusters

A shared cluster is a multi-tenant system, and its defaults are permissive. Hardening involves: RBAC (role-based access control) with least privilege for people and for the service accounts pods run as; Pod Security Standards enforced by admission control — no privileged containers, non-root users, read-only root filesystems, no host networking; network policies that restrict which pods may talk to which (by default every pod can reach every other); resource quotas and limit ranges per namespace so one team can't consume the cluster; image provenance — scanning images for vulnerabilities, signing them, and admitting only signed images from trusted registries; and secrets encrypted at rest and preferably sourced from an external manager. For truly untrusted tenants, namespaces aren't a strong boundary; separate clusters or sandboxed runtimes are.

Operators: encoding operational knowledge

Kubernetes can be extended with custom resource definitions (CRDs) — new object types such as PostgresCluster or KafkaTopic — and operators, controllers that reconcile them using domain knowledge: create a primary and replicas, configure replication, handle failover, take backups, perform version upgrades in the right order. Mature operators (for PostgreSQL, Kafka, Elasticsearch, Prometheus) make running stateful systems on Kubernetes practical. The trade-off is that the operator becomes critical infrastructure with its own bugs, upgrade path and failure modes; a buggy operator can do damage at machine speed. Teams evaluate operators like databases: maturity, community, and whether they understand what it does during failures. Many still prefer managed database services outside the cluster for the most critical data.

Progressive delivery as a feedback loop

Canary analysis is statistics, and doing it well requires care. Comparing a canary's error rate with the whole baseline fleet is biased (different traffic mix, cold caches on new pods), so good setups compare the canary with a baseline of the same size started at the same time (Netflix's Kayenta approach). Small canaries receive little traffic, so a 5% canary on a low-traffic service may take a long time to show a statistically meaningful difference; analysis windows and step sizes are tuned per service. Metrics must include business signals where possible (checkouts completed, not just HTTP 200s), because many bugs return successful responses with wrong content. And progressive delivery extends beyond a single cluster: roll out to one cell or one region first, bake, then expand — the same pattern applied to blast radius at larger scale (sc17).

Cluster upgrades and the case for replaceable clusters

Kubernetes releases a minor version roughly every four months and supports each for about a year, so clusters must be upgraded regularly, and upgrades remove deprecated APIs and behaviours. In-place upgrades of a critical cluster carry risk that can't be rolled back — the control plane can't be downgraded, as Reddit discovered. Teams mitigate this by testing upgrades on non-critical clusters first, scanning manifests for removed APIs (tools like pluto or kubent), reading release notes for deprecated labels and fields, and increasingly by treating clusters themselves as replaceable: build a new cluster on the new version from code, move workloads and traffic gradually, and retire the old one. That's blue-green deployment applied to the platform, and it's only practical when everything about the cluster is defined in code.

How platform problems show up

CrashLoopBackOff. A container starts, dies, and restarts with increasing back-off delays. Causes: OOMKilled because the memory limit is too low; a liveness probe killing a slow starter; a missing configuration value or secret; a dependency unavailable at startup with no retry. kubectl describe pod shows the last termination reason and events; container logs from the previous run (kubectl logs --previous) show why.

Pending pods. Pods stay unscheduled because no node satisfies their requests or constraints — requests too large, all nodes tainted, a zone constraint unsatisfiable, or the node autoscaler at its maximum. Events on the pod say which filter failed.

Latency spikes with low CPU. CPU throttling from limits; noisy neighbours on the same node; garbage-collection pauses from memory pressure. Check throttled-period metrics and node-level contention.

Errors during every deploy. Missing readiness probes, no graceful shutdown or preStop delay, maxUnavailable reducing capacity during peaks, or long-lived connections cut abruptly.

Mass restarts. Liveness probes that check dependencies restart every pod when a dependency blips; or a node pool upgrade drains too many nodes at once without PodDisruptionBudgets.

Autoscaling too slow or flapping. Scaling on the wrong metric, image pulls taking minutes, no node headroom, or aggressive scale-down removing capacity just before the next peak.

What to watch

Per workload: restarts and their reasons, OOM kills, readiness failures, CPU throttling, requests versus actual usage (for right-sizing and cost), replica count versus HPA desired count, and deploy success and rollback rates. Per cluster: pending pods and their age, node utilisation by requests and by actual usage, autoscaler activity and errors, control-plane health (API server latency and errors, etcd latency and database size), and certificate expiry. For delivery: deployment frequency, lead time, change failure rate and time to restore — the four DORA metrics widely used to measure delivery performance.

Knobs

Requests and limits; probe periods, timeouts and thresholds; terminationGracePeriodSeconds and preStop delay; maxSurge and maxUnavailable; PodDisruptionBudgets; topology spread constraints; HPA metrics, targets, minimum and maximum replicas and scale-up/scale-down behaviour; node autoscaler limits and instance types; canary steps, durations and analysis thresholds; priority classes.

A real incident: Reddit's Pi-Day outage (March 2023)

On 14 March 2023, Reddit was down for about 314 minutes. The trigger was a routine upgrade of one of its most critical Kubernetes clusters from version 1.23 to 1.24. Kubernetes 1.24 removed a long-deprecated node label, node-role.kubernetes.io/master, in favour of the more neutral control-plane label. Reddit's cluster networking used Calico with route reflectors — components that distribute routing information between nodes — and the route reflectors were selected by a configuration that matched nodes with the old label. That configuration had been set up years earlier by engineers who had since moved on, was edited by hand inside Calico's own settings, and wasn't in version control or documentation, so nobody knew to update it. After the upgrade, the selector matched no nodes, the route reflectors vanished, and pod-to-pod networking in the cluster stopped. Because a Kubernetes control plane can't be downgraded, rolling back meant restoring the cluster from backup, following an old procedure that had never been tested for that situation and had to be adapted on the fly under pressure. The lessons map directly onto this lesson: keep every piece of cluster configuration in code and review; check release notes and search for every use of removed APIs and labels before upgrading; upgrade less critical clusters first; rehearse restore procedures; and prefer building replacement clusters over upgrading the only production cluster in place.

A one-minute simulation of the Horizontal Pod Autoscaler's formula through a traffic ramp. It needs only Python 3.

import math

def hpa(current_replicas, current_metric, target_metric, tolerance=0.1, lo=2, hi=50):
    ratio = current_metric / target_metric
    if abs(ratio - 1) <= tolerance:                  # within 10%: do nothing
        return current_replicas
    return max(lo, min(hi, math.ceil(current_replicas * ratio)))

# a traffic ramp: requests per second per pod, target 100 rps per pod
replicas, total_rps = 4, 350
for minute, total_rps in enumerate([350, 420, 600, 900, 1500, 1500, 800, 400]):
    per_pod = total_rps / replicas
    new = hpa(replicas, per_pod, 100)
    print(f"min {minute}: {total_rps:5d} rps, {replicas:2d} pods -> {per_pod:5.0f} rps/pod -> desired {new}")
    replicas = new

Output:

min 0:   350 rps,  4 pods ->    88 rps/pod -> desired 4
min 1:   420 rps,  4 pods ->   105 rps/pod -> desired 4
min 2:   600 rps,  4 pods ->   150 rps/pod -> desired 6
min 3:   900 rps,  6 pods ->   150 rps/pod -> desired 9
min 4:  1500 rps,  9 pods ->   167 rps/pod -> desired 15
min 5:  1500 rps, 15 pods ->   100 rps/pod -> desired 15
min 6:   800 rps, 15 pods ->    53 rps/pod -> desired 8
min 7:   400 rps,  8 pods ->    50 rps/pod -> desired 4

What it shows. The formula is proportional: 4 pods at 150 rps each become 6, which would bring each back to 100. Minute 1's 5% overshoot is inside the tolerance, so nothing happens. During the ramp, the autoscaler is always one step behind: pods run at 150-167 rps for several evaluations while replacements start, which is exactly why targets are set well below real capacity (here, if a pod's real limit were 150 rps, users would already be suffering). On the way down, this simulation drops from 15 to 8 to 4 immediately; the real HPA would hold the higher count for its 5-minute stabilisation window, because traffic that dips often comes back.

Think it through. (1) If a new pod takes 3 minutes to become ready, how many minutes of overload does the ramp above cause, and what target would you pick to absorb it? (2) The service is I/O-bound: CPU stays at 20% while latency doubles. Which metric would you give the HPA instead? (3) A campaign will send 5,000 rps at 9:00 sharp. What do you do at 8:30?

Debug the manifest 
containers:
- name: api
  image: registry/api:latest
  resources:
    limits: { cpu: "500m", memory: "256Mi" }
  livenessProbe:
    httpGet: { path: /health, port: 8080 }   # /health checks DB and Redis
    initialDelaySeconds: 5
    periodSeconds: 5
    failureThreshold: 1

The app is a JVM service that takes ~40 s to start and uses ~400 MB. Traffic spikes hit 500 errors during deploys. List the problems.

Answer
  • :latest tag: non-reproducible; nodes may run different code; rollback is meaningless. Pin an immutable tag or digest.
  • Memory limit 256Mi for a ~400 MB process: constant OOMKills. Set memory request = limit ≈ 512Mi-768Mi and configure the JVM to size its heap from the container limit (-XX:MaxRAMPercentage).
  • No requests: when only limits are set, requests default to the limits — but make them explicit so scheduling and the HPA are reasoned about deliberately. A 500m CPU limit on a JVM also causes heavy throttling during start-up, JIT compilation and GC, lengthening startup and hurting tail latency.
  • Liveness probe kills it during boot: 5 s initial delay and 1 failure versus a 40 s start → a restart loop (CrashLoopBackOff). Add a startupProbe allowing about 60-90 s.
  • Liveness checks DB and Redis: a Redis blip fails every pod's liveness and Kubernetes restarts the whole fleet, turning a partial outage into a total one with cold caches. Liveness should check only the process itself.
  • failureThreshold: 1: a single slow GC pause restarts the pod. Use 3 or more.
  • No readiness probe and no graceful shutdown: new pods receive traffic before they can serve it, and terminating pods keep receiving it while endpoint removal propagates → the 500s during deploys. Add readiness on the pod's own serving ability, handle SIGTERM by draining in-flight requests, add a short preStop sleep, and configure maxUnavailable: 0 with maxSurge so capacity never dips during rollouts.
