A payments company collects every card transaction its merchants process: tens of thousands per second, from web checkouts, point-of-sale terminals and mobile apps. Three teams want something from that data. The merchant dashboard team wants each merchant's revenue for the current minute, updated every few seconds. The billing team wants exact monthly invoices, where every transaction counts exactly once, including the ones from a terminal that was offline for six hours and uploaded its backlog at midnight. And the fraud team wants to flag a card used at five different shops within ten minutes, before the sixth purchase is approved.

None of these can be done by querying the transactional database: it's busy serving payments, the data is too large to scan on every request, and the questions are about aggregates over time. They need data processing pipelines. But the three needs pull in different directions. Invoices need completeness and exactness: wait until all the data is in, then compute carefully, once. The dashboard needs freshness: results within seconds, even if a few late events are missing and have to be corrected later. Fraud needs low latency and memory: keep a running picture of each card's recent activity and react to each new event immediately.

Those are the two families of data processing. Batch processing runs over a bounded, complete dataset — all of yesterday's transactions — in bulk, for exact results with simple, rerunnable jobs. Stream processing runs continuously over an unbounded flow of events, producing results as data arrives. Batch grew from Google's MapReduce into Apache Spark and cloud warehouses; streaming grew into engines like Apache Flink and Kafka Streams, built on logs like Kafka (sc10).

Both come with traps that interviewers love. In batch: the shuffle that moves terabytes across the network, the one hot key that makes a job take eight hours, the rerun that doubles revenue because the job appended instead of overwriting. In streaming: events that arrive late and out of order, the difference between when something happened and when you saw it, deciding when a minute is "finished", keeping state correct through crashes, and what "exactly once" really promises. And across both, the quietest failure of all: a pipeline that runs green every day while silently dropping data — which is how England's public-health reporting lost nearly 16,000 Covid test results in 2020.

This lesson covers both families from the ground up, the architectures that combine them, the orchestration and data-quality practices that keep pipelines trustworthy, and a complete design for the dashboard and the invoices.

The analogy: counting votes on election night

Think of an election count. News channels want a live picture: as each polling station reports, they update the running totals and show them on screen within seconds. Those numbers are provisional — some stations report late, some ballots arrive by post days afterwards, recounts happen — and the channels revise their projections as more comes in. That's stream processing: continuous, fresh, approximate results over data that keeps arriving.

The official result is different. Officials wait until the deadline for postal votes has passed, gather every ballot, count them carefully, check totals against the number of ballots issued, and declare a final number once. If a mistake is found, they recount from the ballots, which are kept. That's batch processing: bounded input, complete and exact results, and the ability to recompute from immutable originals.

The election also shows the key streaming problem. A ballot cast in the morning at a remote station may be counted in the evening; the time the vote was cast (event time) differs from the time it's counted (processing time). To report "votes cast before noon", you must decide when you've waited long enough for the morning's ballots to arrive — that decision is a watermark. The analogy breaks in one way: an election happens once, while a data stream never ends, so streaming systems must make these decisions continuously, automatically, and survive crashes without losing or double-counting anything.

Two shapes of the same pipeline

A useful way to think about both: a pipeline is a function from input data to output data. Batch applies the function to a bounded chunk of input — all of 27 September — and produces the output for that chunk in one run. Streaming applies it incrementally as input arrives, keeping intermediate results in memory (state) and emitting outputs as soon as it decides they're ready. With the right design, both compute the same answer; they differ in when it's available and how much effort goes into handling time, failures and late data.

Two principles run through everything below. Keep inputs immutable and replayable: raw events kept in a retained log or archived as files mean any output can be recomputed after a bug fix. Make outputs idempotent: running a job twice, or replaying a stream, must give the same result, never double-counting. Together they make pipelines recoverable, which matters more than making them fast.

A third principle is easy to forget: check the data, not just the job. A web service that fails returns errors that someone notices; a pipeline that fails often keeps running and publishes wrong numbers. Counting records in and out of each stage, comparing totals with an independent source, and failing loudly when they disagree is what turns a pipeline from "it ran" into "it's right". The lesson builds all three principles into the batch path, the streaming path, and the design that combines them at the end.

1. Batch processing and the MapReduce model

Batch processing takes a bounded dataset — a day of logs, a month of orders, a snapshot of a database — and processes all of it in one run. The modern era began with Google's MapReduce paper (2004), which showed how to process petabytes on thousands of unreliable commodity machines with a simple programming model. It's still the best way to understand what distributed batch engines do.

A MapReduce job has three phases. Take the classic example, counting words across a billion documents:

  1. Map: many workers each read a slice of the input and, for each record, emit key-value pairs — for each word in a document, emit (word, 1).
  2. Shuffle: the system groups all pairs by key, moving them across the network so that every ("scale", 1) pair, from every mapper, ends up at the same reducer. Keys are assigned to reducers by hashing (sc7).
  3. Reduce: each reducer processes one key's values at a time — summing the ones — and writes results to the output.

Fault tolerance came from immutability. Inputs were files in a distributed file system that never changed; each task's output was written to disk. If a machine died, its tasks were simply run again elsewhere on the same input, producing the same output. On thousands of machines, failures during every big job were normal, and the model shrugged them off.

MapReduce's weakness was that every step wrote to disk and multi-step pipelines were chains of separate jobs. Apache Spark generalised it: a job is a graph (a DAG, directed acyclic graph) of transformations — filter, map, join, group, aggregate — executed in stages, keeping intermediate data in memory where possible. If a partition is lost, Spark recomputes it from its lineage (the recorded transformations from the input). Spark's DataFrame and SQL APIs let users describe what to compute, and a query optimiser (Catalyst) decides how, much like a database planner (sc4). The same pattern underlies cloud warehouses such as BigQuery and Snowflake, which run distributed SQL over columnar storage (sc8); for SQL-shaped batch work they're often simpler than running Spark.

2. Performance in batch: the shuffle, skew and file layout

Most slow batch jobs are slow for one of three reasons.

The shuffle. Any operation that groups by a key — joins, group-bys, distinct, sorting — needs a shuffle: every worker sends some of its data to every other worker over the network, writing to local disk along the way. It's usually the most expensive part of a job. The main remedies are to shuffle less data: filter and project (drop unneeded columns) early; pre-aggregate on each worker before the shuffle (a combiner: sum counts locally, then send one number per key rather than millions of ones); and avoid shuffling big tables at all when joining with small ones by using a broadcast join, which sends a copy of the small table (say, 50 MB of merchant details) to every worker so the large table is joined where it already sits.

Skew. The shuffle sends all records for a key to one task. If one key has far more records than the others — one merchant with 30% of transactions, a default country code, a null user ID — that task processes a huge share of the data while the other tasks finish early and wait. The job runs as long as its slowest task, and the hot task may run out of memory. You recognise it in the job's stage view: one task taking ten times longer than the median. Fixes: handle nulls and default values separately; salt hot keys — append a random number from 0 to N−1 to the key so its records spread over N tasks, aggregate those partial results, then combine them in a second, much smaller step (sc7's write sharding, applied to computation); and use engine features such as Spark's adaptive query execution, which detects skewed join partitions at runtime and splits them. Adding machines doesn't fix skew.

File layout. Batch jobs read files from object storage (sc8), and how those files are laid out decides how much must be read. Columnar formats like Parquet let a query read only the columns it needs, compressed. Partitioning the files by a column that queries filter on — typically date — lets engines skip everything outside the requested range (partition pruning); a query for one day reads one day. Parquet files also store min and max values per column chunk, so engines can skip chunks that can't match a filter. And file size matters: thousands of tiny files (a common result of streaming writes) make every job spend its time opening files, so tables are compacted periodically into files of a few hundred megabytes.

3. Making batch jobs safe to rerun

Batch jobs fail partway, get retried by the orchestrator, and get rerun over historical data when a bug is fixed or a new column is added (a backfill). So every job must be idempotent: running it twice over the same input produces the same output as running it once.

The standard pattern: the job is parameterised by the data interval it processes (for example, 2026-09-27), reads immutable inputs for that interval, computes the complete output for it, and atomically replaces that interval's output partition. It never appends to an existing output and never increments counters in place. Running the job for 27 September on 28 September or on 10 October gives the same result, because it reads 27 September's data, not "the last 24 hours". Atomic replacement matters too: writing into the live partition directly means a failure halfway leaves half-written data that readers might see. Writing to a new location and swapping, or using a table format's atomic overwrite (section 9), means readers see either the old complete output or the new complete output, never a mix.

Side effects — sending emails, calling APIs, publishing messages — don't belong inside batch computations, because reruns would repeat them. If a batch result must trigger actions, write the result, then have a separate, idempotent step act on it (with idempotency keys, sc11).

4. Orchestration

Real pipelines are graphs of many jobs: extract from sources, load raw data, clean it, join, aggregate, publish tables, train models, export reports. An orchestrator — Apache Airflow, Dagster, Prefect, or a cloud equivalent — schedules this graph: it runs each task when its upstream tasks have succeeded (or when its input data has arrived), retries failures with backoff, records every run's status and duration, and alerts when something fails or runs late. Because tasks are parameterised by data interval, a backfill is simply "run this part of the graph for these past intervals", which the orchestrator can parallelise.

Good orchestration practice mirrors good service practice: keep business logic in tested code (SQL models, Python modules) rather than inside the orchestration definitions; make every task idempotent; add data-quality checks as tasks that block downstream publication (section 10); set expectations for when each output must be ready and alert on lateness, not just failure; and make lineage visible — which tasks read and write which tables — so the impact of a change or a failure is clear.

A common modern pattern is ELT: extract and load raw data into the warehouse or lakehouse first, then transform it there with SQL (often using dbt, a tool that manages SQL transformations as versioned, tested models). The older ETL pattern transformed data before loading it. ELT keeps the raw data available for reprocessing and uses the warehouse's scalable engine for the transformations.

5. Stream processing: the basic model

Stream processing handles an unbounded flow of events — there's no "end of the input" — and produces results continuously. The input is usually a log such as Kafka (sc10), which provides ordering within partitions, retention and replay. Engines include Apache Flink (a dedicated, stateful stream processor), Kafka Streams (a library embedded in ordinary applications, reading and writing Kafka), Spark Structured Streaming (streaming as a sequence of small batches or continuous processing on Spark), and Apache Beam (a unified programming model that runs on several engines, including Google Cloud Dataflow).

A stream job is also a graph of operators — sources, transformations, keyed aggregations, joins, sinks — running continuously and in parallel. Stateless operations (filter this event, reformat that field) are easy: each event is processed on its own. The interesting problems start with operations that involve time and state: "revenue per merchant per minute", "cards used more than five times in ten minutes", "join each payment with the latest merchant details". The next sections take those in turn.

6. Event time, processing time and out-of-order data

Every event has two times. Event time is when it actually happened, recorded in the event by its source: the moment the card was tapped. Processing time is when the stream job handles it. The gap between them varies from milliseconds to hours: a network retry adds seconds, a Kafka consumer that fell behind adds minutes, a point-of-sale terminal or phone that was offline uploads its buffered events hours later, and different Kafka partitions are read at slightly different speeds, so events from different partitions interleave out of order.

If you aggregate by processing time — "count what arrived this minute" — late events are counted in the wrong minute, results depend on how busy the pipeline was, and replaying the same data gives different answers. For anything meant to describe reality (revenue at 14:03, sign-ups per hour), you aggregate by event time, which gives the same answer however and whenever the data is processed. The price is that you must decide how long to wait for late events before you declare a time period complete. That's what windows and watermarks are for.

7. Windows and watermarks

Windows cut an unbounded stream into finite groups for aggregation, per key, usually by event time.

  • Tumbling windows: fixed length, non-overlapping, aligned — each calendar minute. "Revenue per merchant per minute."
  • Sliding (hopping) windows: fixed length, overlapping, starting at regular intervals — the last 5 minutes, recomputed every minute. Useful for smoothed rates and alerting.
  • Session windows: variable length, grouping a key's events separated by gaps shorter than a timeout — a user's visit, ending after 30 minutes without activity.

With event-time windows, the engine must decide when a window is complete enough to emit its result. It can't know for certain — an event for 14:03 might still arrive at 17:00 — so it uses a watermark: a moving estimate that says "I don't expect any more events with event time earlier than T". A common way to compute it is the highest event time seen so far minus a fixed allowed delay (say, 2 minutes), tracked per input partition and combined by taking the minimum across partitions, so the slowest partition holds it back. When the watermark passes the end of a window, the engine emits that window's result.

The watermark's delay is a direct trade-off between latency and completeness. A short delay emits results quickly but treats more events as late; a long delay waits for stragglers and emits later. Engines soften the trade-off in two ways. Allowed lateness keeps a window's state for a while after it's been emitted, and a late event within that period updates the result, which is emitted again — so a dashboard shows a provisional number quickly and a corrected one when stragglers arrive, as long as the output store accepts updates (upserts by window and key). Side outputs catch events later than that, sending them to a separate stream or table where they can be reconciled or counted in a later period, rather than silently dropped. One more practical detail: if one input partition goes quiet, its watermark stops advancing and holds back every window; engines detect idle sources and exclude them. You'll trace a watermark closing a window, and a late event missing it, in the lab.

8. State, checkpoints and exactly-once

Windows, counts, deduplication and joins all require the job to remember things between events: the running total for merchant 812's current minute, the last ten timestamps for card 4417, the set of event IDs seen in the last hour. That's state, kept per key and partitioned across the job's parallel workers along with the data (sc7). Flink stores large state in an embedded key-value store (RocksDB, an LSM engine from sc4) on local disk, or in newer versions in remote storage, so state can be far larger than memory. State must be bounded: windows are cleaned up after their allowed lateness, and deduplication sets need time-to-live settings, or state grows forever.

The hard question is what happens when a worker crashes. Its in-memory and local state is gone, and events it was processing may have been partly applied. Flink's answer is checkpoints: consistent snapshots of all state across all workers, taken periodically (every few seconds to minutes), together with the input positions (such as Kafka offsets) that the snapshot corresponds to. To take a consistent snapshot without stopping the job, Flink injects checkpoint barriers into the input streams; as a barrier flows through each operator, the operator snapshots its state, so the snapshot reflects exactly the events before the barrier everywhere — an application of the Chandy-Lamport distributed snapshot algorithm. After a failure, Flink restores every operator's state from the last completed checkpoint and rewinds the sources to the recorded offsets, then replays. Every event affects the state exactly once: events after the checkpoint are replayed, but their earlier effects were rolled back with the restore.

That gives exactly-once state. Exactly-once output depends on the sink, because results written to the outside world between the checkpoint and the crash will be written again on replay. Two sink designs make that safe:

  • Transactional sinks write output inside a transaction that's committed only when the checkpoint completes (a two-phase commit between the job and the sink, sc11). Kafka's transactional producers work this way; consumers reading with read_committed never see output from a failed attempt. The cost is that output becomes visible only at checkpoint intervals.
  • Idempotent sinks write outputs keyed so that replays overwrite rather than duplicate — an upsert of (merchant, minute) → total into a key-value store or database. A replayed write produces the same row.

Anything else — sending an email, calling a payment API — is at least once, and needs idempotency keys (sc10, sc11). Kafka Streams offers a similar exactly-once mode for jobs that read from and write to Kafka, using Kafka transactions to commit output and consumer offsets together.

9. Joins in streams

Joins in streaming come in two main forms. A stream-table join enriches each event with the current value of reference data: attach the merchant's name and category to each payment. The table side is itself a stream of changes (often from change data capture on the merchants table, sc8) materialised as state, so the join sees the latest merchant details as of when each payment is processed. A stream-stream join matches events from two streams within a time bound: pair each payment authorisation with its capture if the capture arrives within 7 days, or each ad click with an impression from the previous hour. Both sides must be buffered in state for the join's time range, so the time bound directly determines state size, and watermarks decide when unmatched events can be discarded or emitted as unmatched.

10. Architectures: Lambda, Kappa, CDC and the lakehouse

How do batch and streaming fit together in a whole system? Several patterns have emerged.

Lambda architecture. Proposed by Nathan Marz, it runs two paths over the same input: a batch layer that periodically recomputes accurate results from all historical data, and a speed layer that processes recent events in a stream for fresh, approximate results; queries merge the two. It delivers both freshness and correctness, but the same logic is implemented and maintained twice, often in different frameworks, and the two implementations drift and disagree.

Kappa architecture. Jay Kreps, one of Kafka's creators, proposed dropping the batch layer: use one streaming pipeline for everything, and when logic changes or a bug is fixed, deploy a new version of the job that replays the retained log from the beginning into a new output table, then switch readers to it. One codebase, one model. It became practical because logs retain history and stream engines became reliable. Its limits: replaying years of history through a stream job can be slow and expensive, and inputs that arrive days late fit awkwardly.

In practice, many systems use a pragmatic mix: streaming for freshness, batch for authority. The streaming path produces provisional results quickly; a periodic batch job recomputes authoritative results from the complete archived data after a cut-off, and the two are reconciled. That's the design in the walk-through below.

Change data capture pipelines. Operational databases publish their committed changes as streams (Debezium reading the write-ahead log into Kafka, sc8, sc10), which feed caches, search indexes, warehouses and other services. This makes the transactional database the source of truth and everything else derived and rebuildable, and it's how most analytics data flows from production systems today.

The lakehouse. Analytical data is stored as Parquet files in object storage, organised by an open table format — Apache Iceberg, Delta Lake or Apache Hudi — that tracks which files make up each version of a table. That adds what plain files lack: atomic commits (a write or overwrite becomes visible all at once, which is what makes idempotent batch overwrites safe), schema evolution (adding or renaming columns without rewriting data), time travel (querying a table as of an earlier version, useful for reproducing a report or rolling back a bad write), and support for both streaming appends and batch overwrites on the same table. Many engines — Spark, Flink, Trino, warehouses, DuckDB — can read and write the same tables, so batch and streaming meet in one place.

11. Data quality: pipelines fail silently

A web service that breaks returns errors; a data pipeline that breaks often keeps running and produces wrong numbers. Upstream teams rename a field and a column fills with nulls; an inner join silently drops records whose key is now missing; a source stops sending data and the pipeline processes an empty day without complaint; a retry duplicates a file and revenue doubles; a tool's limit truncates input. Downstream, dashboards, invoices and machine-learning models consume the bad data confidently.

So pipelines need explicit, automated data-quality checks that run as part of the pipeline and block publication when they fail:

  • Freshness: did today's data arrive, and is the latest event recent?
  • Volume: is the row count within the expected range compared with the same day last week?
  • Schema: are the expected columns present with the expected types?
  • Validity: null rates on key columns, values within ranges, allowed categories.
  • Uniqueness: no duplicate event IDs or primary keys.
  • Reconciliation: totals and counts match an independent source — records in versus records out of each stage, revenue versus the payment provider's settlement files.

Tools such as dbt tests, Great Expectations and data-observability platforms automate these. Organisationally, data contracts — versioned, agreed schemas and guarantees for datasets that producing teams commit to, with breaking changes caught automatically — move quality upstream to where data is produced, the same idea as API contracts between services (sc14). The Public Health England case in the prod section is a vivid reminder of why the reconciliation check matters most.

12. A real-world walk-through: live revenue and exact invoices

A payments platform needs revenue per merchant per minute on a live dashboard, and exact end-of-day totals for invoices. Payment events come from web checkouts, point-of-sale terminals and mobile SDKs; most arrive within seconds, some up to 10 minutes late, and some hours late when terminals or phones were offline. SDK retries sometimes send the same event twice. Three merchants produce 30% of the volume. Here's the design and the reasoning.

Ingest. Every event gets a unique event ID at its source and carries its event time. Events land in a Kafka topic partitioned by merchant ID (so each merchant's events are ordered within a partition), with seven days' retention. A separate job continuously archives the raw topic to the lakehouse as Parquet in an Iceberg table partitioned by event date, keeping an immutable, replayable record for batch.

Streaming path for the dashboard. A Flink job reads the topic. It first deduplicates by event ID using keyed state with a 24-hour time-to-live, so SDK retries don't double-count. It then aggregates into one-minute tumbling event-time windows per merchant. The watermark trails the highest event time by 2 minutes, so most minutes are emitted about two minutes after they end; allowed lateness of 10 minutes means late events within that period update the minute's total and re-emit it; events later than that go to a side output table. Results are written as upserts keyed by (merchant, minute) into a low-latency store behind the dashboard, so both late updates and replays after failures are idempotent. Checkpoints every 30 seconds give exactly-once state.

Skew. The three largest merchants would each overload one parallel task. The job first aggregates on a salted key — (merchant, random bucket 0-15) — then combines the 16 partial sums per merchant per minute in a second, cheap step, spreading the heavy merchants' work across 16 tasks.

Batch path for invoices. Invoices must include events arriving hours late and must be exact, so the streaming numbers aren't authoritative. Each day, after a cut-off of 06:00 the following morning (chosen so that more than 99.99% of late events have arrived, based on the measured lateness distribution), an orchestrated batch job recomputes per-merchant daily totals from the raw events in the lakehouse: deduplicate by event ID, filter by event date, aggregate, and atomically overwrite that date's partition in the invoice table. The job is parameterised by date, so re-running it or backfilling after a bug fix is safe. Events arriving after the cut-off are captured by a small daily adjustment job and appear as adjustments on the next invoice, per the business rule.

Data quality and reconciliation. Before the invoice table is published, checks run: the day's raw event count is within expected bounds; no duplicate event IDs remain; no null merchant IDs; and — the most important — each merchant's daily total matches the payment provider's settlement file within a small tolerance. A second check compares the dashboard's streaming totals with the batch totals per merchant per day; a divergence above 0.5% raises an alert, which catches bugs in either path.

What each part buys. Merchants see live revenue within about two minutes, clearly labelled provisional, and corrected automatically as late events arrive. Invoices are exact, reproducible, and auditable, because they're computed from immutable archived events with idempotent jobs and reconciled against an external source. When a bug is found in the streaming logic, the fix is deployed and the job replays from Kafka into a new output; when a bug is found in the batch logic, the affected days are backfilled. Neither path ever silently drops or double-counts data, and when something goes wrong, a check fails loudly. That combination — fresh-and-provisional plus complete-and-exact, over replayable inputs with idempotent outputs and explicit quality checks — is the shape of a strong answer to almost any pipeline design question.

The Dataflow model: what, where, when, how

Tyler Akidau and colleagues at Google formalised stream processing in the Dataflow model (the basis of Apache Beam), organised around four questions. What results are computed? — the transformations and aggregations. Where in event time? — the windowing. When in processing time are results emitted? — triggers, driven by watermarks, element counts or processing-time timers, including early speculative results before the watermark and late updates after it. How do successive results for the same window relate? — accumulation modes: discard previous results, accumulate (each emission includes everything so far), or accumulate and retract (emit the new value plus a retraction of the old one, so downstream sums stay correct). Framing a design in these four questions makes the latency-completeness trade-offs explicit and is a strong way to structure an interview answer about a streaming pipeline.

Watermarks are heuristics, and choosing them is a business decision

A watermark is a guess about completeness, and a wrong guess has consequences either way. Too aggressive, and many events are late: results are wrong until corrected, and events beyond allowed lateness are dropped or diverted. Too conservative, and results are delayed and state is held longer, consuming memory. Good practice is to measure the actual lateness distribution per source — how late is the 99th and 99.99th percentile event? — and set watermark delay and allowed lateness from it and from the business cost of lateness. Sources differ enormously: server-side events are seconds late at worst, mobile events can be days late. Pipelines often handle them differently, and some sources provide their own watermarks (for example, a file-based source knows when a day's files are complete). The same measurement also informs the batch cut-off for authoritative results.

State at scale

Large stateful stream jobs hold terabytes of state: deduplication sets, long windows, join buffers, per-user profiles. Keeping it on local disk (RocksDB) makes checkpoints incremental (only changed files are uploaded) and reads fast, but makes rescaling and recovery slower because state must be moved or downloaded to new workers. Newer designs, such as disaggregated state in Flink 2.0, keep state primarily in remote object storage with local caching, trading some latency for faster rescaling and recovery. Operationally, state size is managed through time-to-live settings, compact encodings, and choosing designs that don't require unbounded state — for example, bounding stream-stream joins by time. State schema evolution (changing the type of stored state between job versions) needs care, since a savepoint written by one version must be readable by the next.

Backpressure and throughput in stream jobs

A stream job is a pipeline of operators; if one is slower than its input — a sink writing to a slow database, a skewed key, an expensive enrichment call — its input buffers fill, and it pushes back on upstream operators, which slow down, until the source reads from Kafka more slowly and consumer lag grows (sc10). This backpressure is healthy — it prevents memory exhaustion — but it means the whole job runs at the speed of its slowest operator. Diagnosing it means finding the operator with full input buffers and empty output buffers (Flink's web UI shows backpressure per operator). Fixes follow sc16's method: find the bottleneck, then batch sink writes, make enrichment lookups asynchronous or cached, split hot keys, or scale the parallelism of that operator. Checkpoints also interact: under heavy backpressure, barriers move slowly and checkpoints take longer, which Flink addresses with unaligned checkpoints that let barriers overtake buffered data.

Batch versus streaming economics

Streaming isn't free freshness. A continuously running job reserves resources around the clock, holds state, needs on-call support, and handles the complexity of late data and checkpoints. A batch job runs for an hour, then releases its resources, and can use cheaper spot or preemptible capacity (sc16) because a failed task is simply re-run. For many use cases, a middle ground — micro-batches every 5 or 15 minutes over an incrementally updated lakehouse table — gives "fresh enough" results at batch cost and complexity. The senior move is to ask how fresh the result really needs to be and what a minute of latency is worth, before choosing an always-on streaming system.

Machine learning pipelines: the training-serving consistency problem

For AI engineering, batch and streaming meet in feature pipelines. Models are trained on features computed in batch over historical data, and served using features computed online from recent events. If the two computations differ — slightly different logic, different handling of late events, a different time boundary — the model sees different inputs in production than in training (training-serving skew, ml14), and quality degrades silently. Point-in-time correctness is the batch-side requirement: training features for an event at time T must use only data that was available at T, never later data, or the model learns from the future and performs worse in production than in evaluation. Feature stores and unified batch-streaming feature definitions exist to enforce these properties; the underlying concepts — event time, windows, late data, idempotent backfills — are exactly the ones in this lesson.

How pipelines fail in production

Silent data loss or duplication. Joins that drop unmatched rows after an upstream schema change, filters that exclude a new category, truncation by a tool or format limit, retries that double-append, deduplication with too short a window. The pipeline is green; the numbers are wrong. Only reconciliation and data-quality checks catch these.

Late or missing data. A source stops sending, or sends late, and the pipeline processes an incomplete interval as if it were complete; or one idle Kafka partition holds the watermark back and every streaming window stalls. Freshness checks and idle-source handling address both.

Skewed and stuck jobs. A batch job runs for hours because one task holds a hot key; a stream job's lag grows because one operator is backpressured by a slow sink or a hot key. Stage and operator metrics reveal the one slow task.

State explosions. Deduplication or join state without a time-to-live grows until checkpoints take minutes and workers run out of disk.

Reprocessing surprises. A backfill of non-idempotent jobs duplicates data; a replayed stream job re-sends notifications; a logic change is deployed without replaying history, so old and new results are inconsistent.

What to watch

For batch: run success and duration against expectations, data arrival times (freshness service levels), row counts and quality-check results per run, stage-level skew, and cost per run. For streaming: consumer lag in time per source (sc10), watermark lag behind processing time, checkpoint duration, size and failures, state size, backpressure per operator, the volume of late events and side outputs, and end-to-end latency from event time to result. Across both: reconciliation differences between pipelines and against external sources, and lineage so that a failing source's downstream impact is visible immediately.

Knobs

Batch: parallelism and partition counts, broadcast thresholds, skew handling (salting, adaptive query execution), file sizes and compaction, partitioning schemes, and orchestration retries and timeouts. Streaming: watermark delay, allowed lateness, window types and sizes, checkpoint interval and mode, state backend and time-to-live, operator parallelism, and sink batching and transactional settings.

A real incident: England's lost Covid test results (2020)

On 4 October 2020, Public Health England announced that 15,841 positive Covid-19 test results had been left out of the UK's daily case reports between 25 September and 2 October. Test results from commercial laboratories arrived as files that an automated process loaded into Excel templates before the data moved on to the national reporting systems and to contact tracers. The templates used Excel's old XLS format, which holds at most 65,536 rows. Because each test result took several rows, a template filled up after roughly 1,400 cases; when a day's file exceeded the limit, the extra rows were simply cut off — no error, no alert. The pipeline "succeeded" every day while silently dropping thousands of positive cases, and because the missing people weren't passed to contact tracers for several days, their contacts weren't told to isolate in time. The immediate fix was splitting data across smaller files; the lasting lessons are general: every format and tool in a pipeline has limits that must be known and tested at production volume; silent truncation is far worse than a crash; every stage should reconcile records in against records out and fail loudly on a mismatch; and critical data flows shouldn't depend on tools that were never designed for production data processing.

A one-minute simulation of event-time windows and a watermark, showing a late event missing its window. It needs only Python 3.

from collections import defaultdict

# (event_time_seconds, amount) in ARRIVAL order: some events arrive late
events = [(5, 10), (12, 20), (61, 5), (58, 7), (70, 3), (125, 8), (40, 50), (130, 2)]
WINDOW, WATERMARK_DELAY = 60, 15

windows, closed, late = defaultdict(int), {}, []
max_seen = 0
for t, amount in events:
    max_seen = max(max_seen, t)
    watermark = max_seen - WATERMARK_DELAY        # "no events older than this expected"
    start = t // WINDOW * WINDOW
    if start in closed:
        late.append((t, amount))                  # window already emitted: too late
    else:
        windows[start] += amount
    for s in sorted(windows):                     # emit windows the watermark has passed
        if s + WINDOW <= watermark:
            closed[s] = windows.pop(s)
            print(f"watermark {watermark:3d}s -> emit window [{s},{s+WINDOW}) total {closed[s]}")
print("still open:", dict(windows), " dropped as late:", late)

Output:

watermark 110s -> emit window [0,60) total 37
still open: {60: 8, 120: 10}  dropped as late: [(40, 50)]

What it shows. Events arrive out of order: the event from second 58 arrives after one from second 61, and it's still counted correctly in the first minute's window because windows are assigned by event time, not arrival order. The first window is emitted only when the watermark (highest event time seen, minus 15 seconds) passes its end, at 110 seconds, with a total of 37. Then an event from second 40 worth 50 arrives — after its window was emitted — and is dropped as late. That's the latency-completeness trade-off in miniature: the window was declared complete too early for that straggler.

Think it through. (1) Raise WATERMARK_DELAY to 90: when is the first window emitted now, and does the late event make it in? (2) Instead of dropping late events, implement allowed lateness: keep closed windows for another 60 seconds and re-emit an updated total. What must the output store support for that to work? (3) Add a duplicate of the event (12, 20): how would you deduplicate, and how long must you remember event IDs?

Design it

Build "revenue per merchant per minute" for a live dashboard and for accurate end-of-day invoices. Payment events come from mobile SDKs and can arrive up to 10 minutes late (sometimes hours, when phones are offline); events can be duplicated by SDK retries; three merchants produce 30% of volume.

Answer
  • Ingest: events into Kafka partitioned by merchant ID; each event carries a unique event ID and an event-time timestamp. Archive the raw topic to the lakehouse (Parquet plus Iceberg, partitioned by event date) as an immutable record for batch.
  • Streaming path (dashboard): a Flink job with 1-minute tumbling event-time windows keyed by merchant; a watermark lagging about 2 minutes for timely results; allowed lateness of 10 minutes that emits updated results for a window when late events arrive; events later than that go to a side output. Deduplicate by event ID using keyed state with a TTL. Write results as upserts keyed by (merchant, minute) so updates and replays are idempotent; checkpoint for exactly-once state.
  • Hot merchants: the three big merchants create skewed partitions — pre-aggregate with a salted key (merchant + random bucket) and combine in a second stage.
  • Batch path (invoices): invoices must be exact and include events that arrive hours late, so a daily batch job, run after a cut-off chosen from the measured lateness distribution, recomputes from the complete, deduplicated raw events in the lakehouse and atomically overwrites that day's partition; that result is authoritative. The dashboard is labelled as provisional. Events after the cut-off become adjustments on the next invoice.
  • Checks: data-quality tests before publishing invoices (counts, duplicates, nulls), reconciliation against the payment provider's settlement files, and a daily comparison of streaming totals with batch totals that alerts on divergence above a threshold — it catches bugs in either path.
