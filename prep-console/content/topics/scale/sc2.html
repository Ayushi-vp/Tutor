Imagine an online shop that has grown from one server to a few dozen services: products, carts, orders, payments, search, recommendations, users. Each runs as several copies, and those copies change all the time. The platform starts extra copies of the search service at lunchtime and removes them at night. A deploy replaces every order-service instance with a new version over ten minutes. A machine dies and the platform restarts its services elsewhere, with new IP addresses. On a typical day, hundreds of instances appear and disappear.

Now try to answer three simple questions. When a customer's phone opens the app, which of all these machines should its request go to, and who checks that the machine is actually working? When the order service needs to charge a card, how does it know the current addresses of the payment instances, given that they changed five minutes ago? And who checks that the phone's request comes from a logged-in customer, that a partner isn't exceeding its paid quota, and that a bot isn't hammering the login page? If every service answers these questions for itself, you get thirty slightly different implementations of authentication, thirty rate limiters, and addresses hard-coded in config files that are wrong by the next deploy.

That's the problem this topic solves. Load balancing spreads requests across many identical instances and routes around broken ones. An API gateway is a single front door that applies the same cross-cutting rules — authentication, rate limits, routing — to every external request before it reaches a service. Service discovery is a live address book: it always knows which instances of each service exist, where they are and whether they're healthy, so callers never rely on stale addresses. A service mesh takes the same ideas inside the system, handling security and reliability for service-to-service traffic.

You'll follow a request's journey from a user's phone to a specific instance deep in the system, layer by layer. On the way you'll see what a gateway does on every request, how registries and heartbeats keep the address book correct, exactly how Kubernetes routes traffic to pods, what a mesh adds and costs, and the failure modes — stale addresses, over-eager health checks, idle new instances, a discovery system whose outage took down a platform with 50 million daily players — that interviewers love to ask about.

The analogy: a hotel's front desk and internal phone directory

Think of a large hotel. Guests arriving from outside go to the front desk. The desk checks who they are, decides which department they need, stops people who shouldn't be there, and sends each guest onwards. That's the API gateway: one place where every outside request is identified, checked and routed.

If one front-desk clerk would be overwhelmed, the hotel opens several desks and a greeter at the door sends each new arrival to whichever desk is free. That greeter is a load balancer: it doesn't care what the guest wants, it just spreads guests across identical desks and avoids any desk whose clerk has gone home.

Inside, staff call each other all the time — housekeeping calls maintenance, the restaurant calls the kitchen. Staff change shifts constantly, so nobody memorises phone numbers. Instead, there's an internal directory that always lists who is on duty in each department right now. Staff who start a shift add themselves; staff who leave are removed; if someone stops answering their phone, the directory drops them. That's service discovery.

The analogy breaks in one place: in a hotel, a slightly out-of-date directory means a wasted phone call. In software, a stale address means a failed request, possibly thousands per second, so the directory must update in seconds and callers must cope gracefully when it's still wrong. Keep that in mind: much of this topic is about living with information that is a few seconds out of date.

The journey of one request

Here's the path a request takes from a phone to a service instance in a typical large system. Each hop exists for a reason, and each has its own way of noticing failures and routing around them.

Step 1: the client looks up the domain name. DNS (or an anycast address announced from many places) sends it to the nearest healthy region — a group of datacentres in one geographic area. Step 2: in that region, an L4 load balancer spreads incoming connections across a fleet of gateway instances. Step 3: a gateway decrypts the request, checks who's calling, applies limits and decides which service should handle it. Step 4: the request reaches one instance of that service. Step 5: that service calls other services, finding their current instances through service discovery.

Two kinds of traffic appear in that picture, and the vocabulary is worth learning because interviewers use it. North-south traffic crosses the system's edge: users and partners coming in, responses going out. The gateway is the north-south front door. East-west traffic flows between services inside the system, like orders calling payments. Service discovery, internal load balancing and service meshes are the east-west machinery. In a microservice system, east-west traffic is typically many times larger than north-south, because each external request fans out into several internal calls.

1. Load balancing essentials, from the system's point of view

The networking track (net10) covered how a load balancer works in detail. Here's the part you need for system design, with the reasoning that decides choices.

A load balancer accepts traffic on one stable address and forwards it to one of several backends (the instances behind it). Two families exist. An L4 balancer (named after layer 4, the transport layer) forwards TCP or UDP connections using only addresses and ports; it never reads the HTTP request. That makes it extremely cheap per packet and able to carry any protocol, but it can only make one decision per connection. An L7 balancer (layer 7, the application layer) terminates the connection, reads each HTTP request, and makes a decision per request: route /api/search to the search service, retry a failed request, add headers. It costs more CPU per request and must hold the TLS keys, because it has to decrypt traffic to read it.

The backend is picked by an algorithm. Round robin cycles through backends in order and is fine when every request costs about the same. Least outstanding requests sends to the backend with the fewest requests in progress, which adapts when some requests are slow or some backends are slower. Power of two choices picks two backends at random and sends to the less busy one, which gets most of the benefit of least-requests without every balancer needing a global view. Consistent hashing sends the same key (a user ID, a cache key) to the same backend, and moves only a small share of keys when backends are added or removed, which is what caches and stateful routing need.

Two points matter most at system level. First, know what unit is being balanced. An L4 balancer balances connections. If clients open a few long-lived connections and send thousands of requests down each — which HTTP/2 and gRPC do by design — the balancer's decision is made once per connection, and load can be wildly uneven. Second, health checks decide everything. A balancer that keeps sending traffic to a dead backend turns one failure into a stream of errors; a balancer whose health check is too strict removes healthy backends. Both mistakes are common, and section 7 returns to them.

2. Traffic enters in layers

No single load balancer handles all traffic for a large system. Traffic is routed in stages, each narrowing the choice, and each layer uses a mechanism suited to its scale.

Global layer: choose a region. DNS-based global load balancing answers the domain lookup with the address of a nearby, healthy region. Alternatively, anycast announces the same IP address from many locations, and the internet's routing delivers packets to the nearest one (net12 explains anycast and CDNs). DNS-based steering reacts to failures only as fast as clients' cached answers expire — often minutes — while anycast reacts as fast as routing changes, usually seconds. Static files (images, scripts) are usually served by a CDN at this layer and never reach your region at all.

Regional L4 layer: spread connections. Inside the region, an L4 balancer (a cloud network load balancer, or a software one like Google's Maglev) spreads connections across a fleet of L7 proxies or gateways. Because it does little work per packet, a small number of L4 machines can carry enormous traffic, and it removes whole failed proxies or zones from rotation.

L7 layer: route requests. The gateway or L7 proxy fleet decrypts traffic and routes each request to the right service based on host, path, headers or the caller's identity.

Service layer: pick an instance. Finally, the request needs one healthy instance of the chosen service. That's where service discovery and internal load balancing come in.

Why not one giant L7 balancer? Because L7 work is expensive and must scale horizontally, and something has to spread traffic across the L7 fleet itself. Layering also contains failures: a dead instance is handled by the service-level balancer in milliseconds, a dead zone by the regional balancer, and only a dead region involves the slow global layer.

3. What an API gateway does on every request

An API gateway is a reverse proxy that serves as the single entry point for external API traffic. Its value is that concerns every service would otherwise reimplement are applied once, consistently, before the request reaches any service. Here's what happens to one request — a mobile app calling POST /v2/orders — as it passes through the gateway's pipeline of filters.

1. TLS termination. The gateway decrypts the HTTPS connection using the site's certificate (net9 covers TLS). Certificates are managed in one place instead of on every service. Traffic onwards to the service may be re-encrypted, often with mutual TLS inside the system.

2. Authentication. The gateway establishes who is calling. For end users this is usually a JWT (JSON Web Token): a token issued at login, containing claims like the user ID and an expiry time, and signed by the identity service. The gateway checks the signature with the identity service's public key and checks the expiry, without calling anyone — a few microseconds of work. For partners it might be an API key looked up in a cache, or an OAuth access token. Unauthenticated requests are rejected with 401. The gateway then passes the verified identity to the backend in a header, so services don't each re-verify tokens.

3. Rate limiting and quotas. Each caller has a budget, for example 100 requests per second for a free-tier partner and 2,000 for a paid one. The usual model is a token bucket: a bucket holds up to B tokens and refills at R tokens per second; each request removes one token, and a request that finds the bucket empty is rejected with 429 Too Many Requests. The bucket size B allows short bursts while R caps the sustained rate. Quotas are the same idea over longer periods (a million calls per month) and are tied to billing. sc12 covers rate-limiting algorithms in depth.

4. Routing. The gateway maps the request to a service: /v2/orders to the order service's version-2 deployment, /v1/orders to the old one while clients migrate. Routing can also use headers (send internal staff to a canary version) or weights (send 5% of traffic to a new version). This is also where API versioning lives, so backend services can be reorganised without clients noticing — clients see one stable API surface while services behind it split, merge and move.

5. Transformation. The gateway may add a request ID for tracing, strip internal headers from responses, translate between protocols (JSON over HTTP from clients to gRPC for internal services), or compress responses.

Around all of this, the gateway records observability data — request counts, latencies, status codes per route and per client — giving one consistent view of everything entering the system. Some gateways also cache responses to public, repeated requests.

What it costs: one extra network hop (typically well under a millisecond inside a region, plus the processing time of the filters), one more component that must be scaled and made highly available, and a shared piece of configuration that many teams touch. The gateway is on the path of every external request, so its availability caps the availability of everything behind it. It must run as a horizontally scaled fleet behind an L4 balancer, across zones, like any other stateless tier.

4. Keeping the gateway thin: BFFs and aggregation

A tempting mistake is to keep adding logic to the gateway: "the mobile home screen needs data from five services, so let the gateway call all five and merge the results". Do that for every screen and every client, and the gateway becomes a monolith that every team must modify and redeploy together, full of business rules that belong to the services that own the data.

The standard answer is the backend for frontend (BFF) pattern: a small service per client type — one for the iOS and Android apps, one for the website — owned by the team that builds that client. The mobile BFF calls the product, cart, recommendation and promotion services in parallel, and returns exactly the fields the home screen needs in one response. That matters on mobile networks, where each extra round trip can cost 100 ms or more. The gateway stays thin and generic: it authenticates, limits and routes to the BFF. GraphQL, a query language where the client describes the exact shape of data it wants from one schema, is an alternative way to get the same benefit with one generic service instead of several BFFs (swe7 compares REST, gRPC and GraphQL).

A simple rule for what belongs where: if a concern is the same for every service and has nothing to do with the business (who is this caller, are they over their limit, which service handles this path), it goes in the gateway. If it's specific to one client's needs, it goes in a BFF. If it's a business rule, it goes in the owning service.

5. Service discovery: the live address book

Behind the gateway, services call each other. In a static world you could write addresses in config files. In a dynamic world — autoscaling, rolling deploys, containers rescheduled onto other machines — addresses change every few minutes, and any hard-coded list is wrong almost immediately. Service discovery is the mechanism that answers "where are the healthy instances of service X right now?"

Every discovery system has the same three parts.

A registry: a database of instances, keyed by service name, holding each instance's address, port and metadata (version, zone). It must itself be highly available, so it's usually a replicated cluster: Consul, etcd, ZooKeeper, Netflix's Eureka, or the Kubernetes API server backed by etcd.

Registration: getting instances into the registry and out again. With self-registration, each instance registers itself on startup and deregisters on clean shutdown. With third-party registration, the platform that starts instances (Kubernetes, Nomad, a cloud autoscaling group) registers them, so application code doesn't need to know. Third-party registration is now the norm, because it works for any language and the platform knows exactly when instances start and stop.

Liveness: instances that crash don't deregister, so the registry needs to notice. There are two approaches. With heartbeats and leases, each registration is a lease valid for a limited time (say 10 seconds) that the instance must renew with periodic heartbeats; if the heartbeats stop, the lease expires and the instance disappears automatically. With health checks, the registry or an agent actively probes each instance's health endpoint and marks it unhealthy after several failures.

Here's a registration and failure trace with a 10-second lease and 3-second heartbeats:

The trace shows the unavoidable fact about discovery: the address book is always slightly stale. Between a crash and every caller learning about it, there's a window of several seconds (lease timeout plus cache refresh) in which some requests go to a dead instance. Shorter leases shrink the window but multiply heartbeat traffic and cause false removals when a healthy instance is briefly slow. So callers must be built to cope with dead addresses: short connection timeouts, retrying idempotent requests on a different instance, and outlier ejection — dropping an instance locally after a few consecutive failures without waiting for the registry. You'll see this window happen in the lab.

6. Client-side versus server-side discovery

Once the registry knows the instances, how does a caller use it? There are two models, and interviewers often ask you to compare them.

In client-side discovery, the calling service fetches the instance list from the registry (usually subscribing to changes rather than asking every time), keeps it in memory and picks an instance itself with a load-balancing algorithm. There's no extra hop, and the client can use smart algorithms such as least-requests or latency-aware choice, because it sees every one of its own requests. The costs: every client needs a discovery library for its language, and upgrading the logic means upgrading every service. Netflix's early stack (Eureka plus a client library) and gRPC with its xDS support work this way.

In server-side discovery, the caller sends the request to a stable name or address, and something in between — a load balancer, a proxy or kernel rules — looks up the instances and forwards the request. Clients stay simple and language-neutral; the cost is an extra hop or component and less information for balancing. Cloud load balancers and Kubernetes Services work this way.

A service mesh blurs the line: each service gets a local proxy that does client-side discovery and balancing on its behalf, so the application code sees server-side simplicity while the traffic gets client-side intelligence.

Plain DNS is the simplest discovery system of all: register instances as DNS records and let clients resolve the name. It works everywhere, but has two weaknesses in dynamic environments. Answers are cached by resolvers for the record's TTL (net6), and often by the language runtime too — some Java configurations historically cached lookups forever. And clients that hold long-lived connections never re-resolve at all. DNS discovery works well when endpoints change slowly or sit behind a stable virtual IP, which is exactly how Kubernetes uses it.

7. How Kubernetes does it

Kubernetes, the most common container platform (sc15 covers it in full), builds discovery in. The pieces, in the order a request meets them:

A Pod is one or more containers running together with their own IP address. Pods are disposable: when one is replaced, the new one has a different IP. A Service is a stable front for a set of pods, selected by labels (for example app=payments). Each Service gets a ClusterIP — a virtual IP address that doesn't belong to any machine — and a DNS name like payments.default.svc.cluster.local, which stays the same while the pods behind it come and go.

Readiness probes decide which pods count. Each pod declares a check (an HTTP endpoint, a TCP port, a command); while it passes, the pod is ready and belongs in the Service; when it fails, the pod is removed from the Service but not restarted. A separate liveness probe decides whether a stuck container should be restarted. The control plane records the IPs of ready pods in EndpointSlice objects — chunked lists (up to 100 endpoints per slice by default) so that a change to one pod in a 5,000-pod Service doesn't resend the whole list.

On every node, kube-proxy watches Services and EndpointSlices and programs the Linux kernel's packet-rewriting rules — iptables (still the default), or nftables (stable since Kubernetes 1.33 and the recommended replacement; the older IPVS mode, which used the kernel's built-in load balancer, was deprecated in 1.35). When a container connects to the ClusterIP, the kernel on the calling node rewrites the destination to one of the ready pod IPs, chosen at random. Some networking plugins (such as Cilium, using eBPF programs in the kernel) replace kube-proxy with the same behaviour.

Put together, a new pod joining looks like this: the pod starts; its readiness probe begins passing; the control plane adds its IP to the EndpointSlice; every node's kube-proxy sees the update and adds a rule; new connections to the ClusterIP can now land on it. The whole chain usually takes about a second or two. Removal runs the same chain backwards, which matters during deploys: a terminating pod may keep receiving new connections for a moment after it has been told to stop, which is why pods commonly sleep a few seconds on shutdown (a preStop hook) before closing their listener, and why graceful shutdown finishes in-flight requests.

Two variations are worth knowing. A headless Service (clusterIP: None) has no virtual IP; its DNS name returns the individual pod IPs, which lets clients do their own balancing — this is how gRPC clients get per-request balancing, and how databases in StatefulSets give each replica a stable name. And for traffic from outside, Kubernetes has the Ingress resource and its newer successor, the Gateway API, which configure an L7 proxy at the cluster's edge. (The widely used ingress-nginx controller was retired in March 2026, and the Kubernetes project now recommends the Gateway API for new work.)

Note that ClusterIP balancing happens per connection, in the kernel, once. That's the root of the classic gRPC problem in the drill below.

8. Service meshes: moving the network logic into proxies

As the number of services grows, every one of them needs the same things for its outgoing calls: discovery, load balancing, timeouts, retries, encryption and identity (mutual TLS so services can prove who they are to each other), and metrics for every call. Implementing that in libraries for five languages, and keeping them consistent, is a lot of work. A service mesh moves it into infrastructure.

A mesh has two halves. The data plane is a set of proxies (usually Envoy, or a purpose-built one) that intercept every service's incoming and outgoing traffic. The classic design runs one proxy as a sidecar container in every pod: the application sends a plain request to payments, the local sidecar intercepts it, picks a healthy payments instance, opens a mutual-TLS connection to that instance's sidecar, applies the timeout and retry policy, and records metrics. The control plane (for example Istio's istiod) watches the platform's service registry, turns policies into proxy configuration, issues short-lived certificates for service identity, and streams all of it to the proxies over the xDS APIs.

What you get: every service-to-service call encrypted and authenticated without code changes; consistent timeouts and retries; traffic splitting for canary deploys (send 1% of calls to the new version); and uniform metrics and traces for every call, which is often the biggest win for debugging.

What it costs: each hop now passes through two proxies, typically adding around a millisecond or less per hop, plus memory and CPU for a proxy in every pod — which adds up across thousands of pods. It's a complex system to upgrade and debug, and badly chosen defaults (retries at every layer) can make overload worse. To reduce the cost, Istio's ambient mode (generally available since Istio 1.24 in late 2024) drops per-pod sidecars: a shared per-node proxy called ztunnel handles encryption and identity, and optional "waypoint" proxies handle L7 features only for services that need them. Linkerd uses a small purpose-built proxy to keep per-pod overhead low.

When to adopt a mesh: when you have many services in several languages, need encryption and identity between all of them (often a compliance requirement), and struggle with inconsistent retries and missing metrics. With a handful of services, a good HTTP client library and Kubernetes Services are usually enough.

9. A real-world walk-through: traffic for a growing e-commerce platform

Here's how the pieces come together for a concrete system, and why each decision is made. The shop serves 5 million daily users on web and mobile plus 200 partner integrations (marketplaces that sync inventory and orders). Peak traffic is about 20,000 external requests per second, and each external request fans out into four internal calls on average, so east-west traffic peaks around 80,000 calls per second.

Edge. The domain resolves through a managed global load balancer with anycast addresses, so users reach the nearest of two regions and a failed region is routed around in seconds. A CDN serves product images and the website's static files, removing most bytes before they reach the region. Basic abuse protection — per-IP limits, bot detection, DDoS absorption — also runs at the edge, because it's cheapest to drop bad traffic furthest from your servers.

Regional entry. In each region, a cloud L4 load balancer spreads connections across a gateway fleet running on Kubernetes. Sizing: if one gateway instance handles about 4,000 requests per second at 60% CPU, peak needs 20,000 / 4,000 = 5 instances per region; the team runs 9 across three zones so that losing a zone leaves 6, still above peak, and autoscaling adds more for spikes. The gateway validates user JWTs locally, looks up partner API keys in a local cache refreshed from the key service, enforces per-partner quotas with a token bucket per key (local buckets, synchronised through Redis every second), and routes: /app/* to the mobile BFF, /web/* to the web BFF, /partner/v1/* and /partner/v2/* to the partner API service's two versions.

Inside. Services run on Kubernetes and find each other through Services and DNS. Most internal calls are HTTP/1.1 JSON, which works well with ClusterIP balancing. The search service uses gRPC, so its clients use a headless Service with client-side round robin, and its servers set a maximum connection age of five minutes. After a security review requiring encryption between services, the team adopts a mesh in ambient mode, which adds mutual TLS and per-call metrics without sidecars.

Health and failure handling. Readiness probes check only that each pod has loaded its configuration and can accept work — not the database — so a database blip degrades responses instead of emptying every Service. Callers use short timeouts, retry idempotent GETs once on a different instance, and eject instances locally after five consecutive errors. Pods sleep five seconds in a preStop hook before shutting down, so deploys produce no errors.

What each layer handles when things break. A crashed pod: removed by readiness and outlier ejection in seconds, users unaffected. A bad zone: the L4 balancer and the zone-spread gateway fleet absorb it. A bad region: global load balancing moves traffic to the other region, which is sized to carry it. A bad deploy of the orders service: the gateway's weighted routing had sent only 5% of traffic to the new version, and the rollout is stopped automatically when its error rate rises. Every layer of the diagram in the primer has a job in that list — that's the design argument an interviewer wants to hear.

Registry consistency: why discovery usually prefers availability

A registry is a replicated database, so it faces the trade-off covered in sc9: during a network partition, it can refuse requests on one side to stay consistent, or keep answering with possibly stale data. Registries built on consensus — ZooKeeper, etcd, and Consul's servers, all of which replicate through a majority-vote protocol (Raft or ZooKeeper's equivalent) — choose consistency: on the minority side of a partition, writes fail, so instances can't register or renew, and depending on settings reads may fail too. Netflix built Eureka to choose availability instead: every node keeps serving whatever it knows, and when a node sees an unusually large share of heartbeats disappear at once, it enters "self-preservation mode" and stops expiring instances, reasoning that a sudden mass loss of heartbeats is much more likely to be a network problem than a mass crash. For discovery, stale data is survivable — clients already have to handle dead addresses — but an empty answer means no calls at all. Consistency still matters for the other jobs registries do, like locks and leader election, which is why the choice depends on which job you're using the system for.

Static stability: keep working when the control plane doesn't

The most important design principle for discovery and meshes is that the data plane must never depend on the control plane for each request. Proxies, kube-proxy rules and client libraries should cache the last known good state and keep using it when the registry or control plane is unreachable. Then a control-plane outage stops changes — new instances aren't added, removed ones linger — but existing traffic keeps flowing. AWS calls this property static stability. The corollary is that certificates issued by the control plane need lifetimes long enough to ride out a control-plane outage of hours, and that monitoring must not depend on the thing it monitors. The Roblox outage (in prod) is what happens when these rules are broken.

Subsetting: when every client can't talk to every server

With client-side balancing, each client keeps connections to backend instances. If 1,000 client instances each connect to all 1,000 backend instances, that's a million connections, each costing memory and health-check traffic. Subsetting gives each client a subset (say 50 backends) chosen so that every backend gets roughly the same number of clients. Random subsets produce uneven load, so Google's SRE book describes deterministic subsetting, which shuffles backends with a per-round seed and hands out non-overlapping slices to clients. It's the kind of problem you only meet at scale, and a good example of balancing trade-offs: fewer connections versus smaller pools that are more sensitive to one slow backend.

Connection-level versus request-level balancing

HTTP/1.1 sends one request at a time per connection, so clients open many connections and per-connection balancing works out roughly even. HTTP/2 and gRPC multiplex hundreds of concurrent requests over one connection, so a client with one connection sends everything to one backend. Kernel-level balancing (ClusterIP) and L4 balancers only ever see connections. There are three ways out: balance per request in a proxy (L7 balancer or mesh), balance in the client across all backend addresses (headless Service plus client load-balancing policy, or xDS), or force periodic reconnection with a maximum connection age plus jitter. The same issue shows up with WebSockets and database connection pools: after a scale-out, new instances receive no traffic until connections are recycled.

Health check design is a distributed-systems problem

A health check is a vote on whether an instance should get traffic, and correlated votes are dangerous. Deep checks that include shared dependencies make every instance fail together, emptying the pool. Well-designed balancers include a panic threshold: if more than, say, half the backends look unhealthy, the balancer assumes the health checking is wrong and sends traffic to all of them anyway (Envoy has exactly this setting). Outlier ejection uses real traffic rather than synthetic probes, which catches instances that pass probes but fail real requests, and caps how much of the pool can be ejected at once for the same reason. And liveness probes should almost never check dependencies, because restarting a container can't fix a remote database, and mass restarts reduce capacity at the worst possible moment.

Gateway scaling and tenant isolation

Because every external request goes through the gateway, one noisy client can hurt everyone: a partner sending huge payloads or slow uploads can tie up connections that others need. Mature gateways apply per-client concurrency limits as well as rate limits, cap request sizes and upload times, and sometimes run separate gateway pools (cells) for large tenants or for partner versus consumer traffic, so a problem in one pool can't take down the others. Configuration is the other scaling problem: with hundreds of routes owned by many teams, a bad route change can break unrelated APIs, so gateway configuration deserves the same review, validation and progressive rollout as code.

Characteristic failures

Errors during every deploy. A pod is told to stop, closes its listener immediately, but the endpoint removal hasn't reached every node or proxy yet, so for a second or two new connections still arrive and get refused — users see 502 or 503 errors at every rollout. Fix: a short preStop sleep before shutting down, graceful handling of in-flight requests, and a termination grace period longer than the longest request.

Stale addresses. A client runtime caches DNS answers far longer than the TTL, or holds pooled connections to instances that have been replaced, and keeps failing against addresses that no longer exist. Symptoms: connection timeouts or refused connections from one caller only, often after a migration. Fix: respect TTLs in the runtime, bound connection lifetimes, and use outlier ejection.

Idle new instances. After scaling out, new instances get little traffic because long-lived connections (gRPC, HTTP/2, WebSockets, database pools) stay pinned to old instances. Symptoms: uneven CPU across instances that should be identical. Fix: request-level balancing or a maximum connection age.

The health check that emptied the pool. A readiness check that queries the database fails everywhere during a brief database slowdown; the balancer removes every instance, and a partial degradation becomes a total outage. Fix: shallow readiness checks, panic thresholds, caps on ejection.

Gateway as the bottleneck. A gateway fleet sized for average traffic saturates at a launch, or an expensive filter (calling an external auth service on every request, or a slow plugin) adds latency to everything. Watch gateway p99 latency separately from backend latency, cache auth decisions, and load-test the gateway as its own tier.

What to watch

For balancers and gateways: request rate, error rate by status code (distinguishing 502 — backend refused or reset the connection, 503 — no healthy backend or overload, 504 — backend too slow), and latency split between time spent in the proxy and time waiting on the backend. Per-backend request distribution shows imbalance. Health-check flapping (instances repeatedly marked unhealthy and healthy) signals thresholds that are too tight. For discovery: registry cluster health and write latency, the number of registered versus expected instances, and update propagation time. For a mesh: control-plane push latency and errors, certificate expiry times, and sidecar resource usage.

Knobs

Health-check interval, timeout and failure threshold (for example every 5 s, 2 s timeout, 3 failures to remove, 2 successes to re-add); outlier ejection thresholds and the maximum percentage of the pool that can be ejected; connection draining or deregistration delay; slow-start ramp for new instances with cold caches; lease duration and heartbeat interval; maximum connection age; per-route timeouts and retry policies; per-client rate limits and burst sizes.

A real incident: Roblox, October 2021

Roblox was down for 73 hours, affecting a platform with about 50 million daily players. At the centre was their Consul cluster, which provided service discovery, health checks, locks and a key-value store for the whole platform, and which their workload scheduler (Nomad) and secrets store (Vault) depended on. A day earlier, Consul's new streaming feature had been enabled on high-traffic services along with a large increase in nodes. Under very high read and write load, that feature caused contention that blocked writes. At the same time, Consul's storage layer (BoltDB) had accumulated a pathological free-page list: a 4.2 GB database holding about 489 MB of live data wrote a 7.8 MB free list with every small append, producing multi-second write times on the leader. With Consul degraded, nothing that needed discovery or configuration could work. Worse, the monitoring systems themselves depended on Consul, which delayed diagnosis by more than a day. The lessons map directly onto this topic: keep the data plane statically stable when the registry fails, isolate the registry's workloads so one feature can't take it all down, and never let monitoring depend on the system it monitors.

In this lab you'll run a tiny service registry with heartbeats, three backends, and a client that does client-side discovery and round-robin balancing. Then you'll watch a backend crash and a new one join, and measure the staleness window. It needs only Python 3 and runs in one terminal in about 15 seconds.

  1. Save this as sc2_lab.py:

    import json, threading, time, urllib.request
from collections import Counter
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler

TTL = 3.0                       # an instance is dead if no heartbeat for 3 s
registry = {}                   # "host:port" -> time of last heartbeat
lock = threading.Lock()

class RegistryHandler(BaseHTTPRequestHandler):
    def do_POST(self):          # POST /heartbeat/<addr>: register or renew
        addr = self.path.split("/")[-1]
        with lock:
            registry[addr] = time.time()
        self.send_response(204); self.end_headers()
    def do_GET(self):           # GET /instances: only those with a fresh heartbeat
        now = time.time()
        with lock:
            live = [a for a, t in registry.items() if now - t < TTL]
        body = json.dumps(live).encode()
        self.send_response(200); self.send_header("Content-Length", str(len(body)))
        self.end_headers(); self.wfile.write(body)
    def log_message(self, *a): pass

def backend(port, stop_at=None):
    alive = threading.Event(); alive.set()
    class H(BaseHTTPRequestHandler):
        def do_GET(self):
            if not alive.is_set():                  # a crashed process doesn't answer
                self.close_connection = True; return
            self.send_response(200); self.send_header("Content-Length", "0"); self.end_headers()
        def log_message(self, *a): pass
    srv = ThreadingHTTPServer(("127.0.0.1", port), H)
    threading.Thread(target=srv.serve_forever, daemon=True).start()
    def heartbeat():
        while alive.is_set():
            urllib.request.urlopen(urllib.request.Request(
                f"http://127.0.0.1:9000/heartbeat/127.0.0.1:{port}", method="POST"))
            time.sleep(1)
    threading.Thread(target=heartbeat, daemon=True).start()
    if stop_at:
        threading.Timer(stop_at, alive.clear).start()   # simulate a crash

threading.Thread(target=ThreadingHTTPServer(("127.0.0.1", 9000), RegistryHandler).serve_forever,
                 daemon=True).start()
backend(8001); backend(8002); backend(8003, stop_at=4)            # 8003 "crashes" at t=4 s
threading.Timer(8, backend, args=(8004,)).start()                  # 8004 joins at t=8 s
time.sleep(0.5)

# The client: refresh the instance list every 2 s, round-robin across it
instances, refreshed, i = [], 0.0, 0
start = time.time()
for second in range(14):
    counts = Counter()
    while time.time() - start < second + 1:
        if time.time() - refreshed > 2:
            instances = json.load(urllib.request.urlopen("http://127.0.0.1:9000/instances"))
            refreshed = time.time()
        addr = instances[i % len(instances)]; i += 1
        try:
            urllib.request.urlopen(f"http://{addr}/", timeout=0.5)
            counts[addr[-4:]] += 1
        except Exception:
            counts["ERR " + addr[-4:]] += 1
        time.sleep(0.05)
    print(f"t={second:2d}s  known={sorted(a[-4:] for a in instances)}  {dict(sorted(counts.items()))}")

t= 5s  known=['8001', '8002', '8003']  {'8001': 5, '8002': 5, 'ERR 8003': 5}
t= 6s  known=['8001', '8002']  {'8001': 7, '8002': 8, 'ERR 8003': 1}
t= 7s  known=['8001', '8002']  {'8001': 8, '8002': 7}

What to look for. Before the crash, round robin spreads requests evenly across three backends. When 8003 crashes, the client keeps sending it a third of the traffic for about three seconds — every one of those is an error — because the registry still lists it until its heartbeat lease expires (3 s), and the client only refreshes its cached list every 2 s. The staleness window is roughly the lease timeout plus the cache refresh interval, exactly as in the trace in the body. When 8004 starts heartbeating, it appears within one refresh and immediately takes its share. Nobody edited a config file.

Try next. (a) Set TTL = 1.5 and the refresh to 0.5 s and watch the error window shrink, then think about what happens to heartbeat traffic with 10,000 instances. (b) Make the client smarter: on an error, immediately retry the request on the next instance, and remember failed addresses for 5 seconds (outlier ejection). You should see the errors disappear from the user's point of view even though the registry is just as stale — which is the real-world fix.

Diagnose it

After scaling a service from 4 to 12 instances behind an L4 load balancer, 3 of the new instances sit nearly idle while the originals stay overloaded. Clients are 5 internal services using gRPC. Why, and what do you change?

Answer

Why: gRPC runs over HTTP/2, which multiplexes all requests over a few long-lived connections. An L4 balancer (like Kubernetes' ClusterIP rules) balances connections, not requests — it makes its choice once, when a connection opens. The five client services opened their connections to the original 4 instances before the scale-out, and those connections never move. New instances only get connections from clients that happen to reconnect. The same effect appears with any keep-alive connection pooling.

Fixes, in order of how much they change:

  • As an immediate mitigation, set a maximum connection age on the server (MAX_CONNECTION_AGE in gRPC, a few minutes with jitter) so clients periodically reconnect and their new connections spread across all 12.
  • Use client-side load balancing: expose the service through a headless Service so DNS returns every instance's address (or use xDS), and configure the gRPC client's round-robin policy so it opens connections to all instances and spreads individual requests across them.
  • Or put an L7, HTTP/2-aware proxy in the path — an Envoy-based gateway or a service-mesh proxy — which balances each request independently.

The general lesson: know what unit your balancer balances — connections or requests — and whether your protocol reuses connections.

Design it

You're asked to add partner API access to an existing consumer app: 200 partners, each with a paid tier that sets a request-per-second limit and a monthly quota, and you must be able to see each partner's usage. Where does each piece go?

Answer

Put partner traffic through the API gateway on its own route prefix (/partner/v1), ideally on a separate gateway pool so a misbehaving partner can't affect consumer traffic. Authenticate each partner with an API key (or OAuth client credentials) that the gateway looks up in a local cache refreshed from a key service. Enforce the per-second limit with a token bucket per key — local to each gateway instance with periodic synchronisation, or in a shared store like Redis for exactness — and return 429 with a Retry-After header when exceeded. Count usage per key into a metering pipeline (asynchronously, so billing never slows requests) that enforces the monthly quota and feeds a usage dashboard. The gateway routes to a partner API service that owns partner-specific logic and versioning; nothing business-specific lives in the gateway. Keep coarse abuse protection (per-IP limits, bot filtering) at the edge, before identity is even known.
