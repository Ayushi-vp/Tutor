A product page on a busy shopping site shows the product's name, description, photos, price, rating and stock level. Building it takes six database queries, about 30 milliseconds in total. At 100 visitors a second that's fine. On a sale day, 50,000 people a second open product pages — and a large share of them are looking at the same few hundred products on the front page. The database is being asked the same six questions, with the same answers, tens of thousands of times a second. It can handle about 5,000 queries a second. It falls over.

The wasteful part is obvious once you see it: the answers barely change. A product's description changes a few times a year; its price perhaps a few times a day. Recomputing them from scratch for every visitor is like a librarian walking to the basement archive for every request for today's newspaper, when they could keep a copy on the front desk.

That copy on the front desk is a cache: a store that keeps a copy of data somewhere faster or closer, so repeated requests skip the slow work. Caching is the single most effective tool for scaling read-heavy systems, and it appears at every layer — in the browser, at the CDN, in front of the application, inside it, and in the database itself.

But caches bring their own problems, and they're the ones interviewers ask about. A copy can be wrong: if the price changes and the cache still holds the old one, customers see a price you no longer honour. A copy can disappear: if the cache restarts, all that traffic lands on the database at once. And a cache can create brand-new failure modes, like thousands of requests rebuilding the same expired entry at the same moment. Phil Karlton's well-known joke — that there are only two hard things in computer science, cache invalidation and naming things — is about exactly this.

This lesson builds caching up from first principles: why caches work at all, the arithmetic of hit ratios, the layers where caches live, the standard read and write patterns with code, how to choose TTLs, the races that make invalidation hard and how real systems close them, eviction and sizing, how distributed caches spread data across nodes, and the failure modes that have caused real outages — ending with a full design for a news site.

The analogy: a desk, a shelf and the archive

Imagine a researcher who needs documents all day. The originals live in an archive across town (the database, or more generally the origin: the authoritative source). Fetching one takes an hour. So the researcher keeps a shelf of copies in the office, and the handful used constantly sit on the desk. Most requests are answered from the desk in seconds, some from the shelf, and only a few need the trip across town.

Three rules make this work. First, the researcher only benefits if the same documents are needed repeatedly — a cache helps only when requests repeat. Second, the desk is small, so when it's full, something has to go back to the shelf; choosing what is eviction. Third, the archive's originals sometimes get updated, and the researcher's copies become out of date; deciding when to throw a copy away is invalidation, and giving each copy an expiry date — "re-check after a week" — is a TTL (time to live).

The analogy breaks in one way: a real researcher knows when they've made a copy. In software, many servers make copies at the same time, in parallel, and the order in which things happen can leave a wrong copy in place. That's where most caching bugs come from.

Why caches work at all

Two facts make caching powerful. The first is skew: in nearly every real system, a small fraction of items gets most of the requests. The front-page products, today's news articles, celebrity profiles and popular videos dominate. Popularity often follows a Zipf distribution, in which the k-th most popular item gets traffic roughly proportional to 1/k, so a cache holding only the top few percent of items can serve the large majority of requests. The second fact is the latency gap from sc1: reading from memory takes around 100 nanoseconds, a lookup in a cache server over the network about half a millisecond, and a database query several milliseconds or more. A hit can be ten to a thousand times cheaper than a miss.

The key measure is the hit ratio: the fraction of lookups that find the data in the cache. Two formulas follow from it:

average latency = hit ratio × hit cost + (1 − hit ratio) × miss cost
origin load     = total requests × (1 − hit ratio)

Worked example: 50,000 reads per second, hits cost 0.5 ms, misses cost 10 ms.

Hit ratioReads reaching the databaseAverage latency
0% (no cache)50,000/s10 ms
90%5,000/s1.45 ms
95%2,500/s0.98 ms
99%500/s0.60 ms

Notice the database column. Going from 95% to 99% looks like a small improvement, but it cuts database load by five times. For the origin, it's the miss ratio that matters, and every point of it is precious. The same table read backwards is a warning: if the cache is lost, the database's load jumps from 500 to 50,000 per second — a hundredfold. A cache that high-performing has quietly become something the system can't live without.

The core pattern in six lines

The most common way to use a cache is called cache-aside (or lazy loading): the application checks the cache first and only goes to the database on a miss, filling the cache afterwards.

def get_product(pid):
    data = redis.get(f"product:{pid}")
    if data is not None:
        return json.loads(data)                              # hit
    row = db.fetch_product(pid)                              # miss: go to the source
    redis.set(f"product:{pid}", json.dumps(row), ex=300)     # keep for 5 minutes
    return row

Everything else in this lesson is about the questions this code raises: what happens when the product changes, what if the cache is full, what if a thousand requests miss at once, and what if Redis is down.

1. The layers where caches live

A request from a user can be answered by a cache at any of several layers. The closer to the user, the faster and the more load it removes — and the less control you have over invalidating it.

Browser. The user's browser caches responses according to HTTP headers such as Cache-Control: max-age=3600 (net7 covers these). A hit here costs nothing, not even a request. But you can't reach into a user's browser to delete a cached file, so for static assets the standard trick is to put a hash of the content in the file name (app.3f9a1c.js) and cache it "forever": a new version is simply a new URL.

CDN. A CDN's edge servers cache responses near users (net12). Static files are the classic use, but API responses that are the same for many users — a product's public details, an article — can be cached at the edge too, with short TTLs and purge APIs that remove an object within seconds.

Reverse proxy. A cache like Varnish or NGINX in front of your application can store whole HTTP responses, useful for pages that are identical for many users.

In-process cache. A dictionary-like structure in the application's own memory (in Java, a library like Caffeine; in Python, functools.lru_cache or a TTL dictionary). It's the fastest possible cache — no network — but every application instance has its own copy, so 50 instances hold 50 copies that can disagree, and invalidating all of them requires broadcasting a message. It's excellent for small, very hot, slowly changing data (configuration, feature flags, the top 100 products) with short TTLs.

Distributed cache. A separate cluster of in-memory servers — Redis, Memcached, or Redis's open-source fork Valkey — shared by all application instances. One copy per key, so invalidation is a single delete, at the cost of a network round trip (roughly a quarter to one millisecond inside a datacentre). This is what most people mean by "adding a cache".

The database itself. Databases keep recently used pages of data in memory (the buffer pool), so a query on hot data never touches the disk. This is why sizing database memory to fit the working set matters so much (sc4). Databases can also store precomputed query results as materialised views.

A request may pass several of these layers, and each hit at a higher layer means every layer below never sees that request.

2. Cache-aside, step by step

Cache-aside is the default pattern because it's simple, only caches data that's actually read, and keeps working (slowly) if the cache is down. Here's the full cycle for reads and writes.

The write path deserves attention, because both steps and their order matter. The database is updated first because it's the source of truth; if the process crashes after the update but before the delete, the cache is stale only until its TTL expires. If you deleted the key first and then updated the database, a reader could slip in between — miss, read the old row, and re-cache it — and the stale value would sit there for a full TTL. And the key is deleted rather than overwritten with the new value, for a reason section 5 explains.

Three details make cache-aside robust in practice. Always set a TTL, even if you also invalidate explicitly, so any bug in invalidation is bounded in time. Treat the cache as optional: wrap cache calls in a short timeout (a few milliseconds) and on error or timeout go straight to the database, because a slow cache is worse than a miss. And design cache keys carefully: include everything the value depends on (product:42:en-GB:v3 for a localised, versioned rendering), and for anything user-specific or permission-dependent include the user or tenant, or you'll serve one customer's data to another.

3. The other read and write patterns

Cache-aside puts the logic in the application. Other patterns move it into the cache layer or change when the cache is written. (In the table, DB is short for database.)

PatternHow it worksGood atCosts
Cache-asideApp reads cache; on miss reads DB and fills cache; on write updates DB, deletes keySimple, caches only what's read, survives cache outageFirst read after write is a miss; invalidation races
Read-throughApp asks only the cache; the cache loads from DB on a missKeeps loading logic in one place; easy single-flightCache must know how to query the DB
Write-throughEvery write goes to cache and DB together before it's acknowledgedCache is always fresh for written keysSlower writes; caches data that may never be read
Write-behind (write-back)Write goes to cache, acknowledged, flushed to DB later in batchesVery fast writes; absorbs write burstsData loss if cache fails before flush; DB lags
Write-aroundWrites go only to DB; reads fill the cacheDoesn't pollute cache with write-once dataRecently written data always misses first

In practice, most systems use cache-aside for reads, with delete-on-write. Read-through appears in caching libraries (for example a loading cache that takes a function to call on a miss), and write-behind appears where writes are frequent and slightly lossy is acceptable — counters, view statistics, session activity timestamps. Write-through fits when data is read immediately after being written, like a user's own profile after they edit it.

4. Choosing TTLs: how stale is acceptable?

A TTL bounds how long an entry can be wrong. The question to ask for each kind of data is not "how often does this change?" but "what's the cost of showing an old value, and for how long is that cost acceptable?"

DataCost of stalenessTypical TTL
Product description, article bodyLowHours, plus explicit invalidation
Price shown on a product pageMedium (must honour or correct at checkout)Seconds to a minute
Stock display ("in stock / low / out")Low if checkout re-checks5-10 seconds
Account balance, permissions revokedHighDon't cache, or invalidate synchronously
Feature flags, configurationLow-mediumSeconds, in-process

A useful principle is to cache for display, verify for action. The product page can show a price or a stock level up to 30 seconds old, as long as checkout reads the authoritative value from the database before charging. That lets the high-volume path use aggressive caching while correctness lives on the low-volume path.

Two TTL techniques matter at scale. Jitter: if a million keys are loaded at the same moment with the same 300-second TTL (after a deploy or a cache restart), they all expire at the same moment too. Adding a random ±10% to each TTL spreads the expiries out. Stale-while-revalidate: keep two times per entry, a soft expiry after which the entry should be refreshed and a hard expiry after which it must not be served. Between the two, serve the old value immediately and refresh it in the background. Users never wait for a rebuild, and the origin sees one refresh instead of a burst.

5. Invalidation and its races

Invalidation means removing a cached entry because its source changed. It's hard because many clients read and write concurrently, and the order in which their operations reach the database and the cache can differ.

Race 1: why delete beats update. Suppose writers update the cache with the new value instead of deleting it. Writer A sets the price to 20 in the database; writer B sets it to 25 just after. A is slow, so B's cache write lands first (25) and then A's (20). Now the database says 25 and the cache says 20, and it'll stay that way until the TTL. With delete-on-write, both writers just delete the key; whatever order the deletes happen in, the next reader loads 25 from the database. Deleting is idempotent (doing it twice has the same effect as once), and that's what makes it safe.

Race 2: the stale set. Delete-on-write still has a gap, and it's the one senior interviewers probe.

The reader missed, read the old value (20), and stalled — a garbage-collection pause or a slow network is enough. Meanwhile the writer updated the database to 25 and deleted the key. Then the reader woke up and wrote 20 into the cache. Nobody made a mistake, yet the cache is wrong. The window is small, but at thousands of requests per second small windows are hit every day.

The fixes, from simplest to strongest:

A TTL as the backstop. It doesn't prevent the race, but bounds how long the wrong value lives. Always have one.

Delayed double delete. The writer deletes the key, then deletes it again a short time later (say 500 ms), catching most late stale sets. Cheap, but it's a heuristic: a reader stalled longer than the delay still wins.

Leases. Facebook's memcache (see refs) gives a reader a lease token when it misses. The reader must present the token when it sets the value. If the key is deleted in the meantime, the token is invalidated, so the reader's late set is rejected. Leases also limit stampedes: the cache hands out a token for a key at most once every few seconds, and other readers who miss in that window are told to wait briefly and retry, by which time the value is usually there.

Versioned values. Store a version number (such as the row's last-updated counter) with the cached value, and only allow a set if its version is newer than what's there. A stale reader's version is older, so its set loses. Redis can do this atomically with a small script.

Invalidate from the database's change stream. Instead of application code deleting keys, a separate process reads the database's log of committed changes — change data capture (CDC), using tools like Debezium, or the database's own replication stream — and deletes the affected keys. This catches every write, including ones from scripts and other services that forgot to invalidate, and it happens in commit order. Facebook's memcache deployment invalidates this way across regions.

An alternative that sidesteps invalidation entirely is versioned keys: include a version in the key itself (product:42:v17) and bump the version on each change. Old keys are never invalidated; they just stop being read and are evicted eventually. This is the database equivalent of hashed static file names.

6. Eviction and sizing

Memory is finite, so a full cache must drop something to make room. The eviction policy decides what.

LRU (least recently used) drops the entry that has gone longest without being read. It's a good default because recently used data tends to be used again. Its weakness is scans: a batch job or crawler that touches a million rarely used keys once each pushes the genuinely popular entries out. LFU (least frequently used) drops entries with the fewest accesses, which resists scans but is slow to forget items that were popular yesterday unless counts decay over time. Random eviction is surprisingly competitive when access is uniform and costs nothing to track. TTL-based policies drop the entries closest to expiry. Modern libraries use admission policies such as TinyLFU (used by Java's Caffeine): a new entry is only admitted if a compact frequency estimate says it will be used more than the entry it would evict, which gives near-optimal hit ratios across many workloads.

Redis's maxmemory-policy setting offers these choices: noeviction (refuse writes when full, the default), allkeys-lru, allkeys-lfu, allkeys-random, their volatile-* versions that only consider keys with a TTL, volatile-ttl, and, since Redis 8.6, least-recently-modified variants. For a pure cache, allkeys-lru or allkeys-lfu is the usual choice; the default noeviction will start failing writes when memory fills, which surprises people. Redis doesn't track exact recency for every key; it samples a few keys (5 by default) and evicts the best candidate, which closely approximates true LRU with far less memory.

Sizing starts from the working set: the data requested often enough to be worth keeping. Worked example: a catalogue of 10 million products where 20% of products get about 90% of views. Caching the top 2 million, at 2 KB each plus roughly 100 bytes of per-key overhead, needs about 4.2 GB. Add room for replication buffers and memory fragmentation (say 25%) and you're at about 5-6 GB, comfortably one or two cache nodes, for an expected hit ratio around 90%. After launch, measure: if the hit ratio keeps rising when you add memory, the cache was too small; if it plateaus, the remaining misses are first-time or rare reads that no amount of memory will fix.

7. Distributed caches: spreading keys across nodes

One cache server has limits — memory, network bandwidth, and in Redis's case one main thread executing commands. A cache cluster spreads keys across many nodes, and every client must agree on which node holds which key.

The naive way — node = hash(key) mod N — breaks badly when N changes: going from 10 to 11 nodes remaps about 91% of keys, which is effectively a full cache flush and an avalanche on the database. Consistent hashing (net10) places nodes and keys on a ring so that adding or removing a node moves only about 1/N of the keys. Memcached clients traditionally do this themselves. Redis Cluster uses a related scheme: the key space is divided into 16,384 hash slots, each node owns a range of slots, and moving slots between nodes rebalances the cluster without a global reshuffle. Proxies such as Twemproxy or Facebook's mcrouter can do the routing so clients stay simple.

For availability, each cache node can have replicas that take over if it fails. Note the trade-off: a cache replica is a second copy of memory, so it doubles cost; many teams accept losing a cache node (and the brief extra database load) rather than replicating everything, and replicate only critical or hot data.

A very common and effective layout is two tiers, named like CPU caches: a small in-process cache (L1, level one) in each application instance, with a TTL of a second or a few seconds, in front of the shared distributed cache (L2, level two). The L1 absorbs extremely hot keys without any network traffic, and its short TTL keeps staleness bounded; the L2 provides the bulk of capacity and a single place to invalidate.

8. Failure modes and their fixes

Caches create failure modes that don't exist without them. Each has a name, and interviewers expect you to know them.

Stampede (thundering herd). A popular key expires, and in the next few milliseconds thousands of requests miss and all query the database to rebuild it. The database sees a sudden burst of identical expensive queries. Fixes: single-flight (also called request coalescing) — the first request that misses rebuilds the value while other requests for the same key wait for its result, so the database sees one query (within one process this is a lock per key; across many instances it needs a lock or lease in the shared cache); stale-while-revalidate, serving the old value while one request refreshes; and probabilistic early refresh, where each request, as expiry approaches, has a small and rising chance of refreshing the value early, so one request refreshes it before it ever expires.

Avalanche. Many keys miss at once — because they were loaded together with the same TTL, or because a cache node or the whole cluster restarted. The database gets the full, unfiltered traffic. Fixes: TTL jitter; restarting cache nodes one at a time; warming a new cache before it takes traffic; and, crucially, protecting the database with a concurrency limit so that when the cache is cold, excess requests wait or fail fast rather than overloading the database into collapse.

Penetration. Requests for keys that don't exist anywhere — a mistyped product ID, or an attacker requesting random IDs — miss the cache and hit the database every time, because there's nothing to cache. Fixes: negative caching (cache "not found" for a short time, say 30-60 seconds), and a Bloom filter of all valid IDs in front of the database: a compact structure that can answer "definitely doesn't exist" without a query.

Hot keys. One key — a viral post, a flash-sale product — gets so many requests that the single cache node holding it saturates its CPU or network, even though the cluster as a whole is idle. Fixes: an in-process L1 cache; replicating the key under several names on different nodes (post:99#1 … post:99#8) with readers picking one at random; and splitting large values.

Big keys. A single huge value (a 5 MB JSON blob, a set with a million members) is slow to transfer and, on Redis, blocks the main thread while it's read or deleted, stalling every other client on that node. Keep values small, split large collections, and delete big keys asynchronously (Redis's UNLINK).

You'll reproduce the stampede and the single-flight fix in the lab.

9. A real-world walk-through: caching a news site

A news site's article API serves 30,000 reads per second at peak, mostly for a few hundred recent articles, with a long tail of older ones. Articles are edited occasionally, and a correction to breaking news must be visible within 10 seconds. The database handles about 3,000 queries per second comfortably. Here's a design and the reasoning for each piece.

Layer 1: the CDN. Article responses are the same for every reader, so they're cacheable at the edge. The API sends Cache-Control: public, max-age=10, stale-while-revalidate=30. The 10-second max-age meets the freshness requirement on its own, even if every other invalidation mechanism fails. Stale-while-revalidate lets the edge serve a slightly old copy while it fetches a new one, so a popular article's expiry never causes a visible wait. The publishing system also calls the CDN's purge API on every edit, so most corrections appear in a second or two. With a few hundred hot articles and tens of thousands of requests per second per article at the top, the CDN hit ratio is around 90%, leaving about 3,000 requests per second for the origin.

Layer 2: Redis. Origin requests check a Redis cluster holding rendered article data under keys like article:8812:v, with a TTL of 10 minutes plus random jitter. Invalidation is driven by CDC: a small service reads the database's change stream and deletes the key for any article row that changes, whichever tool made the change. Sizing: 50,000 articles in the working set at about 20 KB each is 1 GB — trivially one node, run as a primary plus replica for availability. With a 95% hit ratio at this layer, the database sees about 150 queries per second.

Layer 3: in-process. Each API instance keeps a 1-second in-process cache of the 500 hottest articles. During a breaking-news spike, when one article gets most of the origin traffic, this stops a single Redis node from becoming a hot spot.

Protecting the database. Misses go through single-flight per article (a short-lived lock key in Redis, SET lock:article:8812 NX EX 5, so only one instance rebuilds while others briefly serve stale or wait), and database access goes through a concurrency limit of, say, 50 queries in flight per instance. If Redis is lost entirely, requests queue at that limit and latency rises, but the database stays healthy and the CDN keeps absorbing most traffic.

The homepage. The list of latest articles is a separate cached object with a 5-second TTL, rebuilt by the publishing pipeline whenever an article is published, rather than recomputed on reads.

Checking it against the requirements. Freshness: the worst case for a correction is the CDN's 10-second max-age; the usual case is the purge, about a second. Load: 30,000 → ~3,000 → ~150 queries per second at the database, 5% of its capacity, leaving room for a cold cache. Failure: losing Redis raises database load to about 3,000 per second — at capacity but survivable because of the concurrency limit and the CDN. That last check — "what happens when each cache disappears?" — is the question that separates a caching design from a caching accident.

Consistency strategies, compared

There are four broad ways to keep a cache consistent with its source, and a senior engineer picks per data type. TTL only is the simplest: never invalidate, just expire; staleness is bounded by the TTL, and there are no races to reason about. Explicit invalidation from application code gives fresher data but is race-prone and easy to bypass — a script or another service that writes directly to the database won't delete the key. Versioned keys avoid races entirely by never modifying a key, only creating new ones, at the cost of needing to know the current version (often stored in a small, frequently read key or derived from the data). CDC-driven invalidation ties invalidation to what the database actually committed, in commit order, catching every writer; its costs are an extra pipeline to run and a small delay (usually well under a second). Strict read-your-writes for the writer — a user sees their own edit immediately — can be layered on top by reading from the database for a short time after a user's own write, or by writing through for that user's keys.

How Facebook's memcache handles it at scale

The "Scaling Memcache at Facebook" paper is the classic reference and worth being able to summarise. Leases, described in the body, solve both stale sets and stampedes: the paper reports that leases cut the peak database query rate for a stampede-prone workload from about 17,000 to 1,300 queries per second. Invalidations are driven from the database: a daemon called mcsqueal reads the MySQL commit log and broadcasts deletes, batched through routers to keep packet rates manageable. When a memcached server fails, clients send its traffic to a small pool of spare servers called the gutter (about 1% of the fleet) with short TTLs, rather than rehashing keys onto other live servers — rehashing could move a hot key onto a healthy server and overload it too, cascading the failure. Across regions, a key that's been updated in a non-primary region is marked so that reads go to the primary region's database until replication catches up, avoiding stale reads of the user's own writes.

Probabilistic early expiration (XFetch)

Locks and leases prevent stampedes by coordination; probabilistic early expiration prevents them without any coordination. Each cached value stores how long it took to compute (delta) and its expiry time. On every read, a request decides to refresh early if now − delta × beta × ln(random()) ≥ expiry, where random() is uniform between 0 and 1 (so its logarithm is negative and the term pushes "now" forward) and beta is a tuning knob, usually 1. Far from expiry the chance is negligible; as expiry approaches, and especially for values that are slow to compute, the chance rises, so one request almost always refreshes the value shortly before it expires, while every other request keeps getting hits. The paper by Vattani and colleagues shows this rule is optimal in a precise sense, and it's a dozen lines of code.

Negative caching, Bloom filters and their trade-offs

Caching "not found" protects the database from repeated lookups of missing keys, but it creates its own staleness: if the item is created, readers keep seeing "not found" until the negative entry expires. So negative TTLs are short, and creation should delete any negative entry. A Bloom filter goes further: it's a bit array plus several hash functions, where adding an ID sets a few bits and checking an ID tests them. If any bit is unset, the ID definitely isn't present; if all are set, it probably is (false positives happen at a tunable rate, about 1% with roughly 10 bits per item). Deletions aren't supported without variants such as counting Bloom filters, so the filter is rebuilt periodically. It's the right tool against deliberate penetration attacks with random IDs, where negative caching would just fill the cache with junk.

The cache as a dependency

A cache that serves 99% of reads has become load-bearing, whatever the architecture diagram says. Senior designs acknowledge this explicitly. Cache calls get tight timeouts and circuit breakers, because a slow cache that holds threads can take down a healthy application (Little's Law from sc1). The origin is capacity-planned for some cold-cache scenario — perhaps losing one of ten cache nodes, rather than all of them — and protected by admission control for anything worse. Cache clusters are upgraded and restarted node by node. And someone owns the cache's hit ratio as an operational metric, because a slow drift from 99% to 95% is a fivefold increase in database load that no one deployed.

Caching and security

A cache key that doesn't include everything the response depends on is a data leak waiting to happen. If a response differs by user, tenant, permission level, language or feature flag, that dimension must be in the key, or one user will be served another's data. At the HTTP layer this is the cache-deception and poisoning risk covered in net7: responses containing personal data must be marked private or no-store so shared caches never keep them. Permission checks deserve particular care: caching "user 7 may view document 12" means revoking access takes effect only when that entry expires, so authorisation caches use short TTLs or explicit invalidation on permission changes.

Caching expensive computation, not just data

In AI systems, caches hold computed results that are expensive to produce: embeddings of documents, answers to repeated prompts, retrieval results for popular queries. Exact-match caching of large language model (LLM) responses is straightforward (key on the normalised prompt, model and parameters). Semantic caching — reusing an answer for a similar prompt found by embedding similarity — raises hit ratios but risks returning a subtly wrong answer, so it needs a strict similarity threshold and is only safe where near-duplicate questions really do deserve the same answer. Model providers also offer prompt caching, which reuses the model's internal computation for a repeated prompt prefix; lm13 covers that.

What to watch

The core metrics for any cache: hit ratio, broken down by key class (a global 95% can hide a critical key type at 40%); origin load — the requests or queries actually reaching the database, which is what the cache exists to reduce; cache latency at p50 and p99, since a cache that's slow at the tail drags every request; evictions per second (high evictions with a falling hit ratio means the cache is too small or being flushed by scans); memory usage and fragmentation; and connection counts, since thousands of application instances each opening many connections can exhaust a cache node. On Redis, INFO stats gives keyspace_hits, keyspace_misses, evicted_keys and expired_keys, and the slow log shows commands that blocked the main thread. Per-key hotness can be sampled with redis-cli --hotkeys (with an LFU policy) or from client-side metrics.

Characteristic failures in production

The cold restart. A cache cluster is upgraded or restarted all at once, the hit ratio drops to zero, the database is hit with twenty to a hundred times its usual load, and slow queries cause timeouts and retries that keep it down. This is the most common cache-related outage. Rolling restarts, warm-up and database concurrency limits prevent it.

Stale data bugs. A code path that writes to the database without invalidating — a bulk import, an admin script, a second service sharing the table — leaves stale entries until their TTL. Users report "my change didn't save", and it fixes itself later, which makes it hard to reproduce. CDC-driven invalidation fixes the class of bug.

Hot-key saturation. One node's CPU or network is at 100% during a viral event while the rest of the cluster is idle. Latency rises for every key on that node, not just the hot one.

Memory full with noeviction. Redis's default policy refuses new writes when memory is full, so a cache that was never configured for eviction starts returning errors on every set once it fills up.

Slow cache, sick application. A cache node under memory pressure or blocked by a big key responds in 200 ms instead of 0.5 ms; without a tight timeout, application threads pile up waiting for it and the application stops responding, even though the database is fine.

Knobs

TTLs per data type and their jitter; stale-while-revalidate windows; memory limit and eviction policy; negative-cache TTL; L1 in-process cache size and TTL; client timeouts and connection pool sizes for the cache; the database concurrency limit behind the cache; and the number of replicas for hot keys.

A real incident: Facebook, September 2010

Facebook was down for about two and a half hours — its worst outage in four years at the time. An automated system checked configuration values in the cache and, when it found one it considered invalid, deleted it from the cache and fetched the value again from the persistent store. That day, someone changed the persistent copy of a configuration value to something the clients interpreted as invalid. Every client saw the invalid value, deleted the cache entry and queried the database to "fix" it — hundreds of thousands of queries per second against one database cluster, which was overwhelmed. Worse, when a query failed with an error, clients interpreted the error as another invalid value and deleted the cache key again, generating more queries. The system was in a feedback loop that persisted even after the bad value was corrected. The only way out was to stop all traffic to the database cluster — which meant turning off the site — let it recover, and let users back in gradually. The lessons are directly about caching: a cache-refill path is a load multiplier, errors must never be interpreted as "refill now", refills need rate limiting and single-flight, and systems need a way to shed load that isn't "turn everything off".

In this lab you'll build cache-aside with a simulated database, watch the hit ratio climb under a skewed workload, and then reproduce a stampede and fix it with single-flight. It needs only Python 3 and takes about 5 minutes.

  1. Save this as sc3_lab.py:

    import random, threading, time

db_calls = 0
db_lock = threading.Lock()

def slow_db_read(key, delay=0.05):         # pretend database: 50 ms per query
    global db_calls
    with db_lock:
        db_calls += 1
    time.sleep(delay)
    return f"value-of-{key}"

class TTLCache:
    def __init__(self, ttl):
        self.ttl, self.data, self.lock = ttl, {}, threading.Lock()
    def get(self, key):
        with self.lock:
            item = self.data.get(key)
            if item and item[1] > time.time():
                return item[0]
            return None
    def set(self, key, value):
        with self.lock:
            self.data[key] = (value, time.time() + self.ttl)

# Part 1: hit ratio with a skewed (Zipf-like) workload over 10,000 keys
cache = TTLCache(ttl=60)
keys = list(range(10_000))
weights = [1 / (k + 1) for k in keys]      # key 0 is most popular, key 9999 least
hits = misses = 0
for n, key in enumerate(random.choices(keys, weights, k=100_000), start=1):
    v = cache.get(key)
    if v is None:
        misses += 1
        cache.set(key, slow_db_read(key, delay=0))  # cache-aside: miss -> read DB -> fill
    else:
        hits += 1
    if n in (100, 1_000, 10_000, 100_000):
        print(f"part 1: after {n:>7,} requests  hit ratio {hits/n:.0%}  "
              f"keys cached {len(cache.data):,}")

# Part 2: 200 concurrent requests for one hot key that has just expired
def run_stampede(single_flight):
    global db_calls
    db_calls = 0
    cache = TTLCache(ttl=60)
    inflight, inflight_lock = {}, threading.Lock()
    def get(key):
        v = cache.get(key)
        if v is not None:
            return v
        if not single_flight:
            v = slow_db_read(key); cache.set(key, v); return v
        with inflight_lock:                # is someone already loading this key?
            ev = inflight.get(key)
            leader = ev is None
            if leader:
                ev = inflight[key] = threading.Event()
        if leader:
            v = slow_db_read(key); cache.set(key, v)
            with inflight_lock:
                del inflight[key]
            ev.set()                       # wake everyone who waited
            return v
        ev.wait()                          # followers wait for the leader's result
        return cache.get(key)
    threads = [threading.Thread(target=get, args=("hot",)) for _ in range(200)]
    for t in threads: t.start()
    for t in threads: t.join()
    return db_calls

print(f"part 2: stampede without single-flight -> {run_stampede(False)} DB queries")
print(f"part 2: stampede with single-flight    -> {run_stampede(True)} DB query")

  2. Run it with python sc3_lab.py. Typical output:

    part 1: after     100 requests  hit ratio 24%  keys cached 76
part 1: after   1,000 requests  hit ratio 49%  keys cached 508
part 1: after  10,000 requests  hit ratio 72%  keys cached 2,803
part 1: after 100,000 requests  hit ratio 91%  keys cached 8,556
part 2: stampede without single-flight -> 200 DB queries
part 2: stampede with single-flight    -> 1 DB query

What to look for in part 1. The cache starts cold, so early requests mostly miss; that's the cost every cache pays after a restart. As popular keys get cached, the hit ratio climbs to about 91% — while less than 10% of requests ever needed the database. Skew is what makes this work: the most popular keys are cached after their first request and then serve thousands of hits. Change the weights to uniform (weights = [1] * 10_000) and rerun: the hit ratio climbs much more slowly, because no small set of keys dominates.

What to look for in part 2. Without single-flight, all 200 concurrent requests miss at once and each queries the database: a 200x burst for one key. With single-flight, the first request becomes the "leader" and loads the value while the other 199 wait on an event, then read the freshly cached value: one query. That's the whole idea behind request coalescing, and the same idea (implemented with a lock or lease in Redis rather than in one process) protects a database from real stampedes.

Design the caching

A product page API serves 50,000 requests/s; each page combines product details (changes a few times a day), price (changes several times an hour, must never be more than 60 s stale), and stock (changes constantly, but "in stock / low / out" is enough). The database handles 5,000 queries/s. Design the caching, and say what happens if the cache is lost.

Answer
  • Split by volatility rather than caching the whole page as one blob, so the fast-changing parts don't force the slow-changing parts to be refetched.
  • Product details: cache-aside in Redis with a long TTL (hours) plus explicit delete on edit (or CDC-driven invalidation); also cacheable at the CDN with Cache-Control: max-age and purge-on-change — this absorbs most of the traffic.
  • Price: TTL of 30 s with jitter (±5 s), which meets the 60 s bound even if invalidation fails completely; delete on price change too, for faster updates. Use stale-while-revalidate or single-flight so an expiry of a popular product produces one database query, not thousands. Checkout reads the price from the database ("cache for display, verify for action").
  • Stock: serve the coarse bucket from cache with a short TTL (5-10 s), updated by stock-change events; the authoritative check happens at checkout against the database, so the cache only affects display.
  • Load math: with a 99% combined hit rate, the database sees about 500 queries/s — 10% of capacity. If Redis is lost, 50,000 requests/s would overwhelm a 5,000 QPS database tenfold, so add a small in-process cache (1-2 s TTL) on each instance for the hottest products, single-flight on misses, and a concurrency limit on database queries so a cold cache degrades latency instead of causing an outage. Restart cache nodes one at a time.
