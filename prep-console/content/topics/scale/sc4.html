A startup's orders table had 50,000 rows when the "My orders" page was written. The query was simple — fetch this customer's 20 most recent orders — and it returned in 2 milliseconds. Three years later the table has 400 million rows. The same page now takes 40 seconds, times out, and customers complain that their order history is broken. No code changed. What changed is that the database, to answer "which orders belong to customer 4242?", reads every one of the 400 million rows — about 80 gigabytes — checks each one, sorts the matches and returns 20.

A few minutes later an engineer adds one line — CREATE INDEX ON orders (customer_id, created_at) — and the page loads in under a millisecond again. Same data, same query, same hardware, forty thousand times faster. Understanding why that one line has such an effect, when it doesn't help, and what it costs, is the core of this topic.

It matters for scaling because the database is usually the first thing to break (sc1): the application tier scales by adding stateless servers, but the database holds the state everyone shares. Before you reach for replicas, caches or sharding — each of which adds real complexity — you should be sure the database is doing the minimum work per query. Very often it isn't: a missing index, a query that can't use the index that exists, a page that runs 101 queries instead of 2, or pagination that gets slower with every page. These are cheap to fix, and fixing them can be worth a 10x or 100x gain.

This lesson opens the database up. You'll see how rows are stored in pages and cached in memory, how a B-tree index finds one row among billions in about four reads, how inserts keep it balanced, how composite, covering, partial and expression indexes work and when an index can't be used, how the query planner chooses a plan and how to read EXPLAIN, why write-heavy systems use LSM trees instead, and the access patterns that quietly destroy performance. It ends with a real debugging walk-through, from a latency alert to a fix in production.

The analogy: a library, its catalogue and its reading room

A database table is like a library's stacks: millions of books (rows) on numbered shelves. Finding every book by one author without help means walking every shelf and looking at every spine — a full table scan. A library solves this with a catalogue: a separate, alphabetically sorted list of authors, each entry saying which shelf the books are on. Look up the author, walk straight to the right shelves. That catalogue is an index.

The analogy covers the costs too. Every new book means updating the catalogue — possibly several catalogues (by author, by title, by subject) — so more catalogues means slower cataloguing of new arrivals. Catalogues take space. And a catalogue sorted by author is useless if you want books by publication year: you need a different catalogue for that, or you walk the stacks.

One more piece: the library has a small reading room near the entrance where the most-requested books are kept on a table. Fetching from the reading room takes seconds; fetching from the stacks takes minutes. Databases have the same thing — an in-memory cache of recently used data called the buffer pool — and whether the data you need is already in it matters as much as whether you have an index.

Where the analogy breaks: a librarian can glance at a shelf and see all its books at once. A database reads data in fixed-size blocks called pages, and its cost is measured in how many pages it must read and whether they come from memory or disk. That's the key to everything below.

The big picture in three moves

Data lives in pages. A database stores rows in fixed-size pages — 8 KB in PostgreSQL, 16 KB in MySQL's InnoDB engine. A page holds dozens of rows. Reading one row means reading its whole page, from memory if it's in the buffer pool, or from disk if it isn't.

An index is a sorted structure that points to pages. Almost always a B-tree: a tree of pages where each page holds hundreds of sorted keys. Because each level multiplies the reachable rows by hundreds, even billions of rows need only three or four levels, so a lookup reads three or four pages.

A planner decides how to run each query. You write what you want in SQL; the database's query planner decides how: scan the table, or use this index, or that one; which join method; in what order. It chooses by estimating the cost of each option from statistics about the data. EXPLAIN shows you its choice.

CREATE INDEX idx_orders_customer_created ON orders (customer_id, created_at);

EXPLAIN ANALYZE
SELECT id, total FROM orders
WHERE customer_id = 4242 ORDER BY created_at DESC LIMIT 20;
--  Limit (actual time=0.03..0.09 rows=20)
--    -> Index Scan Backward using idx_orders_customer_created on orders
--         Index Cond: (customer_id = 4242)

That plan says: jump into the index at customer 4242, read entries backwards (newest first, because the index is sorted by created_at within each customer), fetch 20 rows, stop. No sort, no scan. Without the index, the plan would say Seq Scan on orders followed by a Sort, and the time would be seconds.

1. How rows are stored: pages, heaps and the buffer pool

A database doesn't store a table as one long file of rows it can jump around in freely. It divides storage into pages of a fixed size, and every read or write works on whole pages. A page has a small header, an array of pointers to the rows it holds, and the rows themselves. With 200-byte rows, an 8 KB page holds about 40 of them.

Databases differ in how rows are arranged across pages. PostgreSQL stores a table as a heap: rows go wherever there's free space, in no particular order, and each row is identified by its physical location (page number and slot). InnoDB instead stores the table as a clustered index: a B-tree ordered by the primary key whose leaf pages contain the rows themselves, so rows with nearby keys are physically together. This difference matters for key design, as the deep section explains.

Pages are cached in the buffer pool, a large region of memory (often most of the machine's RAM) holding recently used pages. When a query needs a page, the database checks the buffer pool first — a buffer hit costs about a microsecond — and only reads from disk on a miss, which costs tens to hundreds of microseconds on an SSD. When the buffer pool is full, the least useful pages are evicted, exactly like the caches in sc3.

This gives you the mental model for query cost: cost ≈ number of pages touched, weighted by whether they're in memory. Now the full table scan from the opening makes sense. 400 million rows at about 200 bytes each is about 80 GB, or 10 million 8 KB pages. Even reading sequentially at 1 GB per second, that's 80 seconds, and it evicts everything useful from the buffer pool on the way. Finding the 20 rows you need should cost a handful of pages. The job of an index is to make that possible.

The working set idea from sc3 applies directly: if the pages your queries use most fit in the buffer pool, the database mostly works from memory and is fast; when data growth pushes the working set past memory size, the same queries start hitting disk and latency can jump several-fold overnight. That's one of the classic reasons a query gets slow "without any change".

2. The B-tree: finding one row in four reads

A B-tree is a balanced tree of pages that keeps keys in sorted order. (Databases actually use a variant called a B+tree, where all the row pointers live in the leaf level; everyone just says B-tree.) There are three kinds of page. The root page at the top holds a sorted list of keys that divide the key space into ranges, each with a pointer to a child page. Internal pages do the same for narrower ranges. Leaf pages at the bottom hold the actual index entries — each key with a pointer to its row — in sorted order, and each leaf also points to the next leaf, so the database can walk along them in order.

A lookup, traced. To find customer 4242: read the root page; its keys say 3000 ≤ 4242 < 6000, so follow the middle pointer. Read that internal page; 4000 ≤ 4242 < 5000, follow that pointer. Read the leaf page; find the entries for 4242, each pointing to a row's location. Read those rows' pages. Three index pages plus the row pages, and in practice the root and internal pages of a busy index are always in the buffer pool, so often only the leaf and row pages might need disk reads.

Why so shallow? A page holds hundreds of keys — for an 8-byte integer key plus a pointer, several hundred per 8 KB page. Call the fan-out 300. One level reaches 300 leaves; two levels reach 300 × 300 = 90,000; three reach 27 million; four reach 8.1 billion. The height grows with the logarithm of the row count in base 300, so going from a million rows to a billion adds about one level. That's why an index lookup costs roughly the same on a small table and a huge one.

Range scans. Because leaves are sorted and linked, a query like WHERE customer_id BETWEEN 4000 AND 4999 or ORDER BY created_at finds the first matching leaf and walks sideways, reading entries in order until the range ends. A sorted index can therefore replace a sort step entirely, and read in either direction (the "Index Scan Backward" in the primer).

Inserts and page splits. Inserting a key means finding the leaf where it belongs and adding it there. If the leaf is full, it's split: half its entries move to a new page, and the parent gains a key and pointer for the new page. If the parent is full, it splits too, and occasionally the split propagates up to the root, which is the only way a B-tree grows taller. This keeps the tree perfectly balanced — every leaf is at the same depth — at the cost of extra writes during splits. Inserts in increasing key order (a sequence, a timestamp) always go to the rightmost leaf, which stays in memory; inserts in random order (a random UUID) land on random leaves across the whole index, which is much more expensive.

3. What indexes cost, and when the planner won't use them

An index is not free. Every write pays: each insert and delete updates every index on the table, and each update does so for every index containing a changed column. A table with six indexes does about seven structure updates per inserted row, each needing its own pages in memory and its own log records. Space and memory: indexes often total as much disk space as the table, and their hot pages compete with table pages for the buffer pool. So an index must earn its keep with the reads it speeds up.

Even when an index exists, the planner uses it only if it's cheaper. An index lookup that returns N rows (from a non-covering index) costs roughly N random page reads into the table. A sequential scan costs reading every page, but in order, which is several times cheaper per page. So there's a crossover: for a condition that matches a tiny fraction of rows — a highly selective condition — the index wins by a mile; for one that matches, say, 20% of rows, reading everything sequentially is cheaper than 80 million random reads. An index on a boolean column with half the rows true is nearly useless for that reason. Cardinality — the number of distinct values — is a rough guide: high-cardinality columns such as email or user ID make excellent indexes.

A middle ground is the bitmap scan: the database first reads the index to collect the locations of all matching rows into a bitmap, sorts them by page, and then reads each needed table page once, in physical order. It also lets the database combine two indexes (rows matching index A AND index B) by combining bitmaps. You'll see "Bitmap Index Scan" and "Bitmap Heap Scan" in PostgreSQL plans for medium-selectivity queries.

4. Composite indexes and the leftmost-prefix rule

A composite index covers several columns. It's sorted by the first column, then by the second among rows with equal first values, and so on — exactly like a phone book sorted by surname, then first name. Here's an index on (customer_id, created_at), as its leaf entries would appear in order:

customer_idcreated_at→ row
42412026-01-03row 88,120
42422025-11-20row 12,004
42422026-02-14row 301,555
42422026-09-01row 998,410
42432024-06-30row 5,771

This ordering explains the leftmost-prefix rule. The index can efficiently answer WHERE customer_id = 4242 (the entries are together), WHERE customer_id = 4242 AND created_at > '2026-01-01' (together and sorted by date within the customer), and WHERE customer_id = 4242 ORDER BY created_at DESC LIMIT 20 (jump to the end of customer 4242's block and read backwards). It cannot efficiently answer WHERE created_at > '2026-01-01' alone, because rows for a given date are scattered across every customer's block — like finding everyone named "Mei" in a phone book sorted by surname.

The ordering rule for columns follows directly: equality columns first, then the range or sort column. With equality on customer and a range on date, (customer_id, created_at) gives one contiguous stretch of the index to read. The reverse order, (created_at, customer_id), would make the database walk every entry in the date range, across all customers, checking customer IDs as it goes. Among several equality columns, the order matters less for that query; choose the order that lets the same index serve other queries too.

Some databases can partly get around the rule with a skip scan: for a query on only the second column, they probe the index once per distinct value of the first column. MySQL 8 and PostgreSQL 18 support this. It's efficient only when the first column has few distinct values (such as a status column), so it's a helpful fallback, not a design strategy.

5. Covering, partial and expression indexes — and when indexes can't be used

Covering indexes. After finding entries in an index, the database normally reads each matching row from the table to get the other columns — one extra page read per row. If the index already contains every column the query needs, it can skip the table entirely: an index-only scan. You can add non-key columns to an index purely to cover a query: in PostgreSQL, CREATE INDEX ON orders (customer_id, created_at) INCLUDE (total, status). This is worth it for hot queries that return many rows; it's a bad habit for everything, because every included column makes the index bigger and must be kept up to date. It's also a reason to avoid SELECT *: asking for every column makes a covering index impossible.

Partial indexes. An index can include only the rows matching a condition: CREATE INDEX ON orders (created_at) WHERE status = 'pending'. If only 2,000 of 400 million orders are pending, this index is tiny, always in memory and cheap to maintain, and it serves exactly the query that looks for old pending orders. Partial indexes are ideal for "work queue" queries over a small active subset, and for uniqueness rules that apply only to some rows (a unique email among non-deleted users).

Expression indexes. An index stores column values. If the query applies a function to the column — WHERE lower(email) = 'mei@example.com' — the stored values don't match what's being compared, so the index is useless. The fix is an index on the expression itself: CREATE INDEX ON customers (lower(email)).

That last point generalises into a list of things that silently prevent index use, all of which you'll meet in code reviews:

  • A function or arithmetic on the indexed column (WHERE date(created_at) = '2026-09-01'; rewrite it as a range: created_at >= '2026-09-01' AND created_at < '2026-09-02').
  • A leading wildcard (LIKE '%smith'); a B-tree can use a fixed prefix (LIKE 'smi%') but not a fixed suffix. Full-text search needs a different index type.
  • Comparing mismatched types (a text column compared with a number), which forces a conversion on every row.
  • Filtering on a later column of a composite index without the leading one (the leftmost-prefix rule).
  • OR across different columns, which often can't use one index (bitmap scans can combine two).

B-trees handle equality, ranges and sorting on ordinary values, which covers most needs. Other structures exist for other data shapes. PostgreSQL's names are the ones you'll hear most:

7. The query planner and how to read EXPLAIN

SQL says what result you want. The query planner (or optimiser) decides how to compute it. For each query it considers possible plans — which table to read first, whether to scan or use an index (and which), which join algorithm, where to sort — estimates the cost of each, and picks the cheapest. Its estimates come from statistics the database keeps about every column: the number of distinct values, the most common values and their frequencies, and a histogram of the rest, gathered by sampling the table (ANALYZE in PostgreSQL, run automatically in the background).

There are three join algorithms to recognise. A nested loop join takes each row from one side and looks up matches on the other, ideally through an index; it's best when the outer side is small. A hash join reads the smaller side into an in-memory hash table and then streams the larger side through it; it's best for large, unsorted inputs joined on equality. A merge join walks two inputs already sorted on the join key side by side; it's best when both come sorted from indexes.

Here's a realistic EXPLAIN ANALYZE from PostgreSQL for a slow query, and how to read it:

EXPLAIN ANALYZE
SELECT c.name, o.total FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending' AND o.created_at < now() - interval '1 hour';

Hash Join  (cost=31.2..1843021.5 rows=1900 width=40)
           (actual time=12.1..18522.7 rows=2113 loops=1)
  Hash Cond: (o.customer_id = c.id)
  -> Seq Scan on orders o  (cost=0.0..1842900.0 rows=1900 width=16)
                          (actual time=0.1..18519.9 rows=2113 loops=1)
        Filter: ((status = 'pending') AND (created_at < ...))
        Rows Removed by Filter: 399997887
  -> Hash  (actual time=11.8..11.8 rows=100000 loops=1)
        -> Seq Scan on customers c  (actual time=0.0..6.2 rows=100000 loops=1)
Planning Time: 0.3 ms
Execution Time: 18523.4 ms

Read from the most indented nodes outward, because inner nodes feed outer ones. Each node shows the planner's estimate (cost, in arbitrary units, and rows) and, with ANALYZE, what really happened (actual time in milliseconds, actual rows, and loops — how many times the node ran). Here the story is obvious once you know where to look: the Seq Scan on orders took 18.5 of the 18.5 seconds, and Rows Removed by Filter: 399997887 says it read 400 million rows to keep 2,113. The estimate of 1,900 rows was close to the actual 2,113, so statistics are fine — the problem is simply that no index can serve this condition. The partial index from section 5, CREATE INDEX ON orders (created_at) WHERE status = 'pending', turns this into an index scan over a few thousand entries and the query into a few milliseconds.

The checklist when reading any plan: find the node with the most time; look for sequential scans of big tables that return few rows; compare estimated and actual rows (a big mismatch — estimated 10, actual 2 million — means the planner chose based on wrong information, often stale statistics or correlated columns); look for nodes with huge loops counts (a nested loop running an inner lookup a million times); and look for sorts or hashes that "spill to disk" because they exceeded their memory allowance. EXPLAIN alone shows the plan without running the query, which is safe for slow queries; EXPLAIN ANALYZE runs it, so be careful with writes (wrap in a transaction and roll back).

8. The write-ahead log: how databases survive crashes

Before looking at the other major storage design, you need one more building block. When a transaction commits, the database must guarantee the change survives a crash. Writing every modified page to its place on disk immediately would mean many random writes per transaction. Instead, the database first appends a description of the change to a sequential file called the write-ahead log (WAL; InnoDB calls it the redo log) and forces that append to disk. Once the log record is durable, the commit is safe: if the machine crashes, the database replays the log on restart to reapply any changes that hadn't reached the data pages yet. The modified pages themselves are written back lazily, in the background, in batches.

Sequential appends are much cheaper than scattered page writes, so the WAL makes commits fast and durable at once. The same log is also what replication streams to replicas (sc6) and what change-data-capture tools read to see every committed change (sc3, sc10). Keep it in mind: it appears everywhere.

9. LSM trees: trading read cost for write speed

B-trees update pages in place, and random inserts mean random page writes. For write-heavy workloads — messaging, event logging, metrics, IoT — there's an alternative that turns all writes into sequential ones: the log-structured merge tree (LSM tree), used by Cassandra, ScyllaDB, RocksDB, LevelDB and many others.

Writes. A write is appended to the write-ahead log (for durability) and inserted into the memtable, a sorted structure in memory. That's it — no disk pages are searched or modified, which is why LSM writes are so fast. When the memtable reaches a size limit (tens to hundreds of megabytes), it's written to disk in one sequential pass as an SSTable (sorted string table): an immutable file of key-sorted entries with a small index. Updates and deletes don't modify old files either; an update is just a newer entry for the same key, and a delete writes a marker called a tombstone.

Reads. To find a key, check the memtable, then the SSTables from newest to oldest, and return the first entry found (the newest version). Checking many files would be slow, so each SSTable has a Bloom filter — a compact structure that answers "definitely not in this file" or "maybe in this file" — so most files are skipped without reading them. Range scans must merge results from several files, which is costlier than walking one B-tree.

Compaction. Files accumulate, so background compaction merges several SSTables into one larger sorted file, keeping only the newest version of each key and discarding deleted ones once their tombstones are old enough. Two common strategies: leveled compaction organises files into levels, each about ten times bigger than the last, with non-overlapping key ranges within a level, which keeps reads cheap (few files per key) at the cost of rewriting data many times; size-tiered compaction merges files of similar size, writing less but leaving more overlapping files for reads to check and needing more temporary disk space.

The trade-off is often described as three kinds of amplification that can't all be minimised at once: write amplification (bytes written to disk per byte of data — compaction rewrites data repeatedly), read amplification (files or pages consulted per read) and space amplification (disk used per byte of live data — old versions linger until compacted). B-trees sit at one point in that space (low read amplification, moderate write amplification from page rewrites), and LSM configurations let you pick others.

Operationally, compaction is the part that bites: it consumes disk bandwidth and CPU in the background, and if writes arrive faster than compaction can keep up, files pile up, reads slow down and disk fills. Tombstone-heavy workloads (queues built on Cassandra, for example) can make reads scan through thousands of deleted entries. The Discord story in the prod section shows both problems.

10. Access patterns that sink real systems

Many database performance problems aren't about indexes at all; they're about how the application talks to the database.

N+1 queries. Code fetches 50 orders with one query, then loops over them and fetches each order's customer with another query: 51 queries. Each costs a network round trip (say 0.5 ms) plus parsing and planning, so the page takes 30 ms even though each query takes 0.2 ms. It's usually invisible in code, because an ORM (object-relational mapper: a library that maps database rows to objects in your code) makes order.customer look like a field access. Fix it with a join, one batched query (SELECT … FROM customers WHERE id IN (…) for all 50 IDs), or the ORM's eager-loading option.

OFFSET pagination. ORDER BY created_at DESC LIMIT 20 OFFSET 100000 makes the database find and discard 100,000 rows to return 20, so deep pages get slower linearly, and rows inserted between requests shift the pages (duplicates or skipped items). Keyset pagination remembers where the last page ended and asks for what comes after: WHERE (created_at, id) < (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20. With a matching index, every page costs the same, however deep. The id is a tie-breaker so rows with equal timestamps aren't skipped.

SELECT *. Fetching every column moves more data than needed, prevents covering indexes, and breaks code when columns are added. Name the columns.

Long transactions. A transaction that stays open — a user editing a form, a batch job doing slow work between queries — holds its locks the whole time, blocking other writers. In databases that keep multiple row versions (MVCC, multi-version concurrency control, covered in sc5), an old open transaction also prevents cleanup of old versions everywhere, so tables and indexes bloat and queries slow down. Keep transactions short and never wait on users or external calls inside one.

Too many connections. Each database connection costs memory and, in PostgreSQL, a whole process; performance degrades well before the connection limit is reached. With 200 application instances each holding a pool of 20 connections, the database faces 4,000 connections. A connection pooler such as PgBouncer (net13 covers pooling) multiplexes many client connections onto a few dozen real ones. Little's Law (sc1) sizes the real pool: 5,000 queries per second at 4 ms each needs about 20 busy connections.

11. A real-world walk-through: from latency alert to fix

Here's how this knowledge is used in practice, as one debugging session on a PostgreSQL-backed service.

The alert. The p99 latency of the order-history endpoint has risen from 80 ms to 2.4 seconds over two weeks, and database CPU has climbed from 35% to 70%. No deploys touched that endpoint.

Find the expensive queries. The pg_stat_statements extension records, for every distinct query shape, how many times it ran and its total and mean time. Sorting by total time shows the top offender: the "recent orders for a customer" query, called 1,200 times per second, mean time 45 ms, accounting for 55% of all database time. A query that runs constantly and got slow is exactly what a two-week creep looks like.

Look at the plan. EXPLAIN (ANALYZE, BUFFERS) on a typical call shows an Index Scan using idx_orders_customer followed by a Sort, reading about 1,900 buffers, many of them from disk (BUFFERS reports pages found in memory versus read from disk). The index is on customer_id alone, so for each call the database fetches all of the customer's orders — heavy customers now have thousands — reads each one from the table, sorts them by date and throws away all but 20. As the table grew past the buffer pool size, those table reads started going to disk, which explains the timing.

Design the fix. The query is WHERE customer_id = $1 ORDER BY created_at DESC LIMIT 20 selecting id, total, status. The ideal index has the equality column first, then the sort column, and includes the selected columns: (customer_id, created_at DESC) INCLUDE (total, status). The database can then jump to the customer, read 20 entries in order, and never touch the table.

Apply it safely. The table has 400 million rows and takes writes constantly, so a plain CREATE INDEX, which blocks writes for the whole build, isn't an option. CREATE INDEX CONCURRENTLY builds without blocking writes, at the cost of taking longer. The team checks there's enough free disk space for the new index, runs it during the quietest hours while watching replication lag and I/O, and confirms afterwards that the index is valid (a failed concurrent build leaves an invalid index behind that must be dropped).

Verify and clean up. The new plan shows Index Only Scan using idx_orders_customer_created, 5 buffers, 0.1 ms. The endpoint's p99 returns to 60 ms and database CPU drops to 30%. The old single-column index is now redundant — the new one's leftmost prefix serves the same queries — so after confirming via pg_stat_user_indexes that it's no longer used, it's dropped, which also recovers some write throughput. Finally, the team adds a test that counts queries per request on this endpoint and a dashboard alert on per-query mean time from pg_stat_statements, so the next slow creep is caught in days, not weeks.

That sequence — measure, find the top query by total time, read the plan, design the index from the query's shape, apply without blocking, verify, remove what's redundant, add a guard — is the standard playbook and a strong answer to "how would you fix a slow database?"

Clustered versus heap storage, and what it means for keys

In InnoDB, the table is the primary-key B-tree: leaf pages hold full rows in key order. Secondary indexes don't store row locations; they store the primary key, so a secondary-index lookup does a second B-tree traversal of the primary key to find the row. Two consequences follow. First, the primary key's size is copied into every secondary index entry, so a 16-byte UUID key makes every index bigger than an 8-byte integer would. Second, insert order into the clustered index is insert order on disk: monotonically increasing keys append to the rightmost page, while random keys cause page splits throughout the table, leaving pages half-empty and thrashing the buffer pool. PostgreSQL stores tables as heaps with rows placed anywhere there's room and every index pointing to physical locations, so random keys hurt less for the table but still scatter inserts in the primary-key index. It pays for this design differently: an update creates a new row version at a new location, which normally means updating every index too, unless the update qualifies as a heap-only tuple (HOT) update — no indexed column changed and there's room on the same page — in which case indexes are left alone. That's a concrete reason not to index columns that change constantly, and to leave some free space in pages of heavily updated tables (the fillfactor setting).

Why the planner gets it wrong

The planner's estimates rest on assumptions that fail in predictable ways. It usually assumes columns are independent, so for WHERE city = 'Paris' AND country = 'France' it multiplies the two selectivities and badly underestimates the matches, because every Paris row is also a France row. PostgreSQL's extended statistics (CREATE STATISTICS … (dependencies)) teach it such correlations. Statistics are samples, so rare values in skewed columns can be misestimated, and after a bulk load the statistics may describe a table that no longer exists until the next analyze runs. Prepared statements add another trap: after several executions, the database may switch to a generic plan that ignores the actual parameter, which is fine when all values behave alike and terrible when one tenant has 10 million rows and the rest have 100. Underestimates are particularly dangerous because they lead to nested loops over what turns out to be millions of rows. Understanding these failure modes lets you explain a plan flip instead of just forcing a hint.

Index maintenance and bloat

Indexes degrade. In PostgreSQL, deleted and updated rows leave dead versions that vacuum later marks reusable; indexes accumulate dead entries too, and pages emptied by deletes are not always reclaimed, so an index on a queue-like table can grow far larger than its live data. Symptoms are indexes much larger than expected and slower scans. The fix is REINDEX CONCURRENTLY, which rebuilds without blocking writes. B-tree deduplication (PostgreSQL 13 and later) stores repeated keys once, shrinking indexes on low-cardinality columns considerably. Operationally, teams track index size, index usage counts (pg_stat_user_indexes.idx_scan) to find indexes that are never used and only cost writes, and duplicate indexes whose columns are a prefix of another index.

Amplification in B-trees and LSM trees, quantitatively

A B-tree insert of a 100-byte row modifies at least one 8 KB leaf page, which is written to the log (often as a full page image the first time it changes after a checkpoint, to protect against torn writes) and later written back to its place on disk — tens of times more bytes than the row itself, plus the same for every index. An LSM tree writes the row to the log and the memtable, then rewrites it at each compaction level: with leveled compaction and a size ratio of 10, a byte may be rewritten roughly 10 times per level over its life, so write amplification of 10-30 is common, but all of those writes are large and sequential. Reads go the other way: a B-tree point read is one path of pages, while an LSM read may consult the memtable, several level-0 files and one file per deeper level, with Bloom filters (around 1% false positives at 10 bits per key) keeping most of those consultations to a memory check. That's the real reason for the rule of thumb "B-trees for read-heavy, LSM for write-heavy", and why SSD endurance (which depends on bytes written) enters LSM tuning discussions.

Row stores versus column stores

Everything above assumes a row store: each page holds complete rows, which is ideal for transactional work — fetch or update one order with all its fields. Analytical queries are different: "total revenue per country for 2025" touches two columns of a billion rows. A column store (ClickHouse, BigQuery, Snowflake, Redshift, Parquet files) stores each column separately and compresses it heavily, so that query reads only the two columns it needs, often compressed by 10x, and processes values in tight vectorised loops. Column stores are poor at single-row updates and point lookups. That's why transactional (OLTP, online transaction processing) and analytical (OLAP, online analytical processing) workloads usually live in different systems, connected by replication or CDC pipelines; sc8 and sc18 pick this up.

ORMs, query counting and the N+1 at scale

ORMs deserve a senior-level view rather than a blanket judgement. They remove boilerplate and prevent SQL injection by construction, but they hide round trips: lazy-loaded relationships turn attribute access into queries, and serialising a list of objects with nested relationships can fire hundreds of queries per request. Good teams make query behaviour visible: they log query counts per request in development, assert them in tests of hot endpoints, use eager loading deliberately (a join for to-one relationships, a separate batched query for to-many ones to avoid multiplying rows), and read the generated SQL for anything on a hot path. At scale, the fix for N+1 is sometimes not SQL at all but a batching layer (the DataLoader pattern in GraphQL services) that collects all the IDs requested during one tick and fetches them in one query.

How database problems show up

Slow creep. Latency rises gradually over weeks as a table grows, until a query that fitted in memory starts reading from disk or an unselective index starts returning thousands of rows per call. Watch per-query mean time, not just overall averages.

Sudden plan flip. A query goes from milliseconds to seconds overnight with no deploy: statistics changed after growth or a bulk load, or a new data distribution made the planner pick a different plan. Compare plans before and after; refresh statistics; add an index that makes the good plan clearly cheapest.

Write slowdown after adding indexes. Insert latency and replication lag climb after a round of "performance" indexes. Each index costs every write; check for unused and duplicate indexes.

Lock pile-ups. A migration (ALTER TABLE taking a strong lock) or a long transaction blocks writers; everything queued behind it waits, connection pools exhaust, and the application stalls. Watch lock waits and the oldest open transaction's age; set lock_timeout on migrations so they fail fast instead of queueing the world behind them.

Connection exhaustion. Autoscaling the application multiplies connections until the database hits its limit or slows under the load of thousands of processes. Use a pooler and size pools with Little's Law.

Tools and metrics

In PostgreSQL: pg_stat_statements for per-query calls, total and mean time (sort by total time to find what matters); EXPLAIN (ANALYZE, BUFFERS) for plans with page counts; auto_explain to log plans of slow queries automatically; pg_stat_user_indexes and pg_stat_user_tables for index usage, sequential-scan counts and dead-row counts; pg_stat_activity and pg_locks for what's running and what's waiting. In MySQL: the slow query log, performance_schema and the sys schema, and EXPLAIN ANALYZE (MySQL 8.0.18+). Key metrics: buffer cache hit ratio (a sustained drop means the working set outgrew memory), queries per second, p99 query latency, rows read versus rows returned (a big ratio means scans), replication lag, connection count and disk I/O utilisation.

Knobs

Buffer pool size (shared_buffers plus the OS cache in PostgreSQL, innodb_buffer_pool_size in MySQL — typically most of RAM for a dedicated server); per-operation sort and hash memory (work_mem), which decides whether sorts spill to disk; autovacuum and autoanalyze thresholds for large tables; statistics targets for skewed columns; fillfactor for heavily updated tables; statement_timeout and lock_timeout to stop runaway queries and migrations; and pool sizes in the connection pooler. For LSM stores: compaction strategy, memtable size, Bloom filter bits per key and compaction throughput limits.

A real-world story: Discord's messages

Discord stored its messages in Cassandra, an LSM-based database, growing from 12 nodes in 2017 to 177 nodes holding trillions of messages by 2022. Two problems described in this lesson dominated. First, partitions (all messages of one channel in a time bucket) were wildly uneven: a huge public server's channel received vastly more traffic than a small group chat, and because reads in an LSM store are more expensive than writes — a read may consult several SSTables — heavily read hot partitions slowed their nodes and the latency spread to everything else on them. Second, compaction and Java garbage-collection pauses required constant operational work: the team regularly took nodes out of rotation to let compaction catch up. They migrated to ScyllaDB, a Cassandra-compatible LSM database written in C++ (no garbage collector, one shard per CPU core), on 72 nodes, and added a data-service layer that coalesces identical concurrent requests into one database query — the single-flight idea from sc3. Their reported p99 latency for historical message reads went from 40-125 ms to 15 ms, and for inserts from 5-70 ms to 5 ms. The lesson isn't "Cassandra bad": it's that storage engine behaviour (read amplification, compaction, pauses) and access-pattern skew drive production performance, and that protecting the database from duplicate work is often as effective as making it faster.

Line 3's composite index removes the sort step: rows come out of the index already in date order, so the database reads 20 and stops. Line 4 says COVERING INDEX: every needed column is in the index, so the table isn't read at all. Index it

An orders table has 400M rows. These queries are slow:

-- (1) the customer's recent orders, 50 per page
SELECT id, total, status FROM orders
WHERE customer_id = $1 ORDER BY created_at DESC LIMIT 50;

-- (2) the ops dashboard: pending orders older than 1 hour (about 2,000 rows)
SELECT id FROM orders WHERE status = 'pending' AND created_at < now() - interval '1 hour';

-- (3) search by email, case-insensitively
SELECT * FROM customers WHERE lower(email) = lower($1);
Answer

(1) CREATE INDEX ON orders (customer_id, created_at DESC) INCLUDE (total, status); — the equality column first, then the sort column, so the database jumps to the customer's block and reads the first 50 entries already in the right order, then stops; INCLUDE makes it an index-only scan with no table reads. For later pages use keyset pagination (AND created_at < $last_created_at, with the id as a tie-breaker), not OFFSET, so page 100 costs the same as page 1.

(2) A partial index: CREATE INDEX ON orders (created_at) WHERE status = 'pending'; — it contains only the few thousand pending rows instead of 400M, so it's tiny, always in memory, and cheap to maintain (rows leave it when their status changes). An index on status alone would be unselective, since most rows share a few status values.

(3) The function call on email prevents use of a plain index on that column, because the index stores the original values, not their lowercase form. Create an expression index CREATE UNIQUE INDEX ON customers (lower(email)); (or use a case-insensitive type such as citext) — and it also enforces case-insensitive uniqueness, which the application almost certainly wanted.

In every case: build with CREATE INDEX CONCURRENTLY on a live table so writes aren't blocked, check disk space first, confirm the new plan with EXPLAIN ANALYZE, and drop any index the new one makes redundant.

Diagnose it

An endpoint that lists a user's notifications got slow after a feature launch. Logs show it runs 1 query to fetch 30 notifications and then 30 queries to fetch the actor (the user who triggered each notification), each taking 0.3 ms. The page takes 45 ms of database time. What's wrong and what do you change?

Answer

It's the N+1 pattern: 31 queries for one page. The queries themselves are fast; the cost is 30 extra round trips, each paying network latency, parsing, planning and connection time (about 1.5 ms each end to end here), and it scales with page size. Fix it by fetching all actors in one query — collect the 30 actor IDs and run SELECT id, name, avatar_url FROM users WHERE id = ANY($1) — or join users into the notification query, or turn on the ORM's eager loading for the actor relationship. That's 2 queries (or 1) regardless of page size, bringing database time down to a couple of milliseconds. Then add a test that asserts the query count for this endpoint so the next feature doesn't reintroduce it.
