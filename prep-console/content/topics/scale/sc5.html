A concert has one ticket left. Two fans click "Buy" within the same millisecond. Two copies of the checkout code run in parallel on two servers. Each asks the database "how many tickets are left?", each is told "1", each charges its customer's card, and each writes "0 tickets left". Two people now hold tickets for one seat. Nobody wrote a bug in the usual sense — each request, run on its own, is perfectly correct. The problem is that they ran at the same time, and their steps interleaved.

Now a different failure. A bank transfer moves £100 from Alice to Bob: subtract from Alice, add to Bob. The server crashes after the first step. Alice has lost £100 and Bob hasn't received it. Again, each step was correct; the problem is that the pair was interrupted halfway.

These are the two enemies of correct data: concurrency (many operations interleaving) and failure (operations stopping halfway). Every system that handles money, inventory, bookings or anything else where the numbers must add up faces both, and they get worse with scale — more servers, more parallel requests, more chances for an unlucky interleaving. At a thousand requests a second, a race with a one-in-a-million chance happens several times a day.

A transaction is the database's answer to both problems: a group of operations that either all happen or none do, and that runs as if it were alone — to a degree you choose. That last part is where most real bugs live. Databases offer several isolation levels, and the defaults are weaker than most developers assume. Code that "uses transactions" can still double-sell tickets, lose updates or double-book rooms.

This lesson makes all of that concrete. You'll see what ACID actually promises and how the database delivers each letter, the specific anomalies that weak isolation allows (each traced step by step), how databases implement isolation with locks and multiple row versions, what each isolation level really prevents in PostgreSQL and MySQL, and the practical tools engineers use to make concurrent code correct. It ends with a design for selling the last hundred tickets to five thousand people at once.

The analogy: a shared ledger in a busy office

Picture an office where many clerks update one big ledger. To keep it correct, the office adopts rules. A clerk making a transfer writes both lines — the debit and the credit — or neither; if they're interrupted, they cross out what they started. That's atomicity. Before writing anything in the ledger, they note it in a separate diary that survives a fire, so work can be redone after a disaster. That's durability, and the diary is the write-ahead log from sc4.

The hard rule is about clerks working at the same time. The safest policy would be one clerk at a time: whoever holds the ledger works, everyone else queues. Always correct, but painfully slow. So offices relax it: clerks can read while others write, or work from photocopies of the ledger taken when they started. Each relaxation lets more clerks work at once, and each allows a specific kind of mix-up. The rules about what one clerk can see of another's unfinished work are isolation, and the named policies are isolation levels.

The analogy breaks in one way: human clerks notice when something looks odd. A database only prevents the mix-ups its isolation level is designed to prevent, silently, thousands of times a second.

What a transaction looks like

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'alice';
UPDATE accounts SET balance = balance + 100 WHERE id = 'bob';
COMMIT;      -- both changes become visible together; ROLLBACK would undo both

BEGIN starts the transaction, COMMIT makes all its changes permanent and visible at once, and ROLLBACK (or a crash, or an error) discards them all. Without an explicit BEGIN, most databases run each statement as its own tiny transaction (autocommit).

The ideal, and why databases don't give it by default

The strongest guarantee is serializability: however the transactions actually interleave, the result is the same as if they had run one at a time, in some order. If each transaction is correct on its own, a serializable database keeps everything correct under any amount of concurrency. You'd think every database would provide this by default. They don't, because the traditional ways to achieve it make transactions wait for each other or abort more often, and that costs throughput. So the default is usually a weaker level, and it's your job to know which mix-ups it allows and to guard against them.

The mix-ups have names — dirty reads, lost updates, phantoms, write skew — and each isolation level is defined by which ones it prevents. The ticket race from the opening is a lost update, and here is the simplest possible fix: make the check and the change a single statement, so nothing can happen in between.

UPDATE tickets SET remaining = remaining - 1
WHERE event_id = 7 AND remaining > 0;
-- 1 row updated → you got a ticket; 0 rows updated → sold out

The database runs that statement atomically against the current value, so two buyers can't both see "1". Most concurrency bugs are fixed by some version of this idea: don't read a value into your application, decide, and write it back while someone else does the same.

1. ACID, mechanism by mechanism

Each letter of ACID is delivered by a different mechanism, and knowing which is which clears up a lot of confusion.

Atomicity — all or nothing — is really about being able to abort. If a transaction fails halfway (an error, a constraint violation, a crash, or an explicit ROLLBACK), everything it did must be undone. Databases achieve this with their logs: they know which changes belong to which transaction, so they can undo uncommitted ones and, after a crash, recognise that a transaction never committed and ignore its changes. With MVCC (section 5), an aborted transaction's new row versions are simply never considered visible.

Durability — committed data survives crashes — comes from the write-ahead log (sc4): the commit is acknowledged only after the log record describing it has been flushed to stable storage. In replicated systems, durability often also means "copied to at least one other machine" before acknowledging (sc6).

Consistency — data moves from one valid state to another — is the odd one out. The database enforces only rules you declare: primary keys, NOT NULL, unique, foreign-key, check and exclusion constraints. Every other rule ("balance can't go negative unless the account has an overdraft", "a doctor must be on call") holds only if each transaction is written correctly and transactions are isolated enough not to break the rule together. So consistency is mostly the application's responsibility, supported by the other three letters.

Isolation — concurrent transactions don't interfere — is the one with a dial. The rest of this lesson is about that dial.

2. The anomalies, one at a time

An anomaly is a result that couldn't happen if transactions ran one at a time. Here are the ones every engineer should recognise, each with a concrete interleaving.

Dirty read. Transaction A updates Alice's balance from £500 to £400 but hasn't committed. Transaction B reads £400 and uses it. Then A rolls back. B acted on a value that never officially existed. Almost every database prevents this at its default level.

Non-repeatable read (read skew). A transaction reads the same data twice and gets different answers because another transaction committed in between. The dangerous version involves two related values: a report reads Alice's account (£500), then a transfer of £100 from Alice to Bob commits, then the report reads Bob's account (now £100 higher). The report's total is £100 too high — money appears to have been created, because it saw Alice before the transfer and Bob after it.

Phantom. A transaction runs a query for a range or condition — "bookings for room 5 on Friday" — and another transaction inserts a new row that matches. Re-running the query returns an extra "phantom" row, and any decision made on the first result may now be wrong. Phantoms are special because the conflict is with a row that didn't exist when you looked, so you can't lock it in advance.

Lost update. Two transactions read the same value, each computes a new value from it, and each writes it back; the second write overwrites the first.

Write skew. The subtlest one. Two transactions read overlapping data, each decides something based on what it read, and each writes a different row. Neither overwrote the other, yet together they break a rule. The textbook example: a hospital requires at least one doctor on call. Alice and Bob are both on call and both feel ill. Each opens the app at the same moment. Alice's transaction counts on-call doctors (2), decides it's safe, and sets Alice off call. Bob's transaction counts (also 2, from its own view), decides it's safe, and sets Bob off call. Both commit. Nobody is on call.

Write skew appears whenever a decision is based on a check across rows: double-booking a room (both check "no overlapping booking", both insert), overspending across accounts, claiming the same username in two tables, or exceeding a quota counted across many rows. Many write-skew bugs involve phantoms, because the rows that would reveal the conflict don't exist yet.

The SQL standard defines four levels by the anomalies they must prevent. Real databases implement them differently, and the standard's wording is ambiguous (the refs include the classic paper explaining why), so treat this table as a map and always check your database's documentation.

*PostgreSQL treats read uncommitted as read committed, so dirty reads never happen there.

Read committed is the default in PostgreSQL, SQL Server and Oracle. Each statement sees a snapshot of data committed before it started, so you never see uncommitted work, but two statements in the same transaction can see different data. A single statement like UPDATE … SET stock = stock - 1 is safe, because when it has to wait for another transaction's lock on the row, it re-reads the row's latest committed version before applying the change. A separate SELECT followed by an UPDATE with a value computed in the application is not.

Snapshot isolation gives the whole transaction one snapshot, taken at its first statement. Every read sees the database as it was at that moment, so reports are internally consistent (no read skew) and repeated queries return the same rows. In PostgreSQL (where it's called repeatable read), if two concurrent transactions update the same row, the second one to write is aborted with "could not serialize access due to concurrent update", which prevents lost updates. What it doesn't catch is write skew, because the two transactions wrote different rows.

MySQL's repeatable read (InnoDB's default) looks similar but behaves differently in a way that matters. Plain reads use a snapshot, but updates and locking reads operate on the latest committed version of the row and don't abort when that version has changed since the snapshot. Jepsen's 2023 analysis of MySQL 8.0.34 showed that its repeatable read allows lost updates and write skew: the common ORM pattern of loading an object, changing it in memory and saving it back inside a transaction can silently discard a concurrent committed change. In MySQL, protect read-modify-write with SELECT … FOR UPDATE, atomic updates or version checks.

Serializable prevents every anomaly: the result must match some serial order. How it's implemented determines its cost, which is the subject of the next section.

4. How databases implement isolation: locks

The classic way to get serializability is two-phase locking (2PL). A transaction takes a shared lock on everything it reads and an exclusive lock on everything it writes. Shared locks are compatible with each other (many readers at once); an exclusive lock conflicts with everything. The "two phases" are that a transaction only acquires locks while it runs and releases none until it commits or aborts. To prevent phantoms it must also lock the ranges it searched, not just the rows it found, so nobody can insert a new matching row; InnoDB does this with gap locks and next-key locks on index ranges.

2PL is correct but expensive: readers block writers and writers block readers. A long report holding shared locks on a big table stops every update to it. And transactions that lock in different orders deadlock (section 8). That cost is why databases looked for another way.

5. How databases implement isolation: MVCC and snapshots

Multi-version concurrency control (MVCC) keeps several versions of each row instead of overwriting in place. In PostgreSQL, every row version carries two hidden fields: xmin, the ID of the transaction that created it, and xmax, the ID of the transaction that deleted or replaced it (empty if it's still current). An update doesn't modify the row; it marks the old version's xmax and writes a new version with a new xmin.

A snapshot records which transactions had committed at the moment it was taken. A row version is visible to a snapshot if its creator had committed by then and its deleter (if any) hadn't. Under read committed, a new snapshot is taken for each statement; under repeatable read / snapshot isolation, one snapshot is taken at the start of the transaction and used throughout.

The benefit is huge: readers never block writers and writers never block readers. A long analytical query reads a consistent snapshot while updates continue around it. Writers still block other writers on the same row: if two transactions update the same row, the second waits for the first to commit or abort.

The cost is cleanup. Old versions accumulate, and they can only be removed once no running transaction's snapshot could still need them. PostgreSQL's vacuum (run automatically by autovacuum) removes them and makes the space reusable; InnoDB keeps old versions in undo logs cleaned by a purge thread. A single transaction left open for hours — a forgotten session "idle in transaction", a stuck replication slot — holds back cleanup for the whole database, so dead versions pile up, tables and indexes bloat, and queries slow down. Keeping transactions short isn't just about locks.

6. Serializable snapshot isolation (SSI)

PostgreSQL's serializable level uses serializable snapshot isolation (SSI), added in version 9.1. It keeps MVCC's non-blocking snapshots and adds conflict detection. As transactions run, PostgreSQL records what each one read using lightweight predicate locks, which block nobody; they just remember "transaction T read rows matching this condition". When a transaction writes something that a concurrent transaction read, the database records a read-write dependency between them.

The insight behind SSI is that under snapshot isolation, every non-serializable execution contains a specific pattern: two consecutive read-write dependencies among concurrent transactions (T1 read something T2 wrote, and T2 read something T3 wrote, where T3 may be T1). When PostgreSQL detects that "dangerous structure", it aborts one transaction with SQLSTATE 40001, "could not serialize access due to read/write dependencies among transactions". In the doctors example, Alice's transaction read Bob's row (in its count) and Bob's transaction wrote it, and vice versa, so one of them fails.

Two practical consequences. First, SSI sometimes aborts transactions that would actually have been fine (false positives), but never lets a real anomaly through. Second, and most important: the application must retry. Any serializable transaction can fail with 40001 through no fault of its own, and the correct response is to run it again from the start:

import psycopg
from psycopg import errors

def transfer(conn, src, dst, amount, attempts=5):
    for attempt in range(attempts):
        try:
            with conn.transaction():
                conn.execute("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
                (bal,) = conn.execute("SELECT balance FROM accounts WHERE id = %s",
                                      (src,)).fetchone()
                if bal < amount:
                    raise ValueError("insufficient funds")
                conn.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (amount, src))
                conn.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (amount, dst))
            return                                   # committed
        except (errors.SerializationFailure, errors.DeadlockDetected):
            continue                                 # rolled back; run it again
    raise RuntimeError("gave up after retries")

Retries are only safe if the transaction has no effects outside the database — no emails sent, no payment API called inside it — because an aborted attempt's database changes are rolled back but external actions aren't. Do those after the commit, or through an outbox (sc11).

7. The practical toolkit

Most production systems run at read committed and protect specific invariants with specific tools. Choosing the right one is the real skill.

Atomic single statements. Push the read-decide-write into one statement so the database does it against the current row: UPDATE accounts SET balance = balance - 100 WHERE id = 'alice' AND balance >= 100. The row count tells you whether it happened. This is the cheapest and most robust fix for counters, balances and stock, and works at any isolation level. INSERT … ON CONFLICT DO NOTHING/UPDATE (an "upsert") is the equivalent for create-if-absent.

Pessimistic row locks. SELECT … FROM accounts WHERE id = 'alice' FOR UPDATE locks the row until commit, so any other transaction that wants to lock or update it waits. Use it when the logic between read and write is too complex for one statement. Variants: FOR UPDATE NOWAIT fails immediately instead of waiting; FOR UPDATE SKIP LOCKED skips rows others have locked, which is how job queues on SQL tables let many workers each grab different jobs; FOR SHARE takes a shared lock that stops others from changing the row while you rely on it.

Optimistic concurrency. Add a version column. Read the row and its version without locking; when writing, include the version in the condition and bump it: UPDATE documents SET body = :body, version = version + 1 WHERE id = :id AND version = :v. If zero rows were updated, someone else changed it first: re-read, re-apply and retry (or show the user a conflict). This is ideal when conflicts are rare and the gap between read and write is long — a user editing a form for five minutes — where holding a lock would be absurd. HTTP APIs expose the same idea with ETags and If-Match (net7).

Constraints. The most reliable guard is one the database enforces on every write, from every code path, at every isolation level. A unique index prevents two accounts with the same email even if two sign-ups race. A CHECK (balance >= 0) constraint makes an overdraft impossible. PostgreSQL's exclusion constraints can forbid overlapping ranges, which solves double booking outright: EXCLUDE USING gist (room WITH =, tstzrange(start_at, end_at) WITH &&). When a rule can be expressed as a constraint, express it that way.

Serializable plus retries. When an invariant spans many rows and can't be a constraint — "total on-call doctors ≥ 1", "sum of allocations ≤ budget" — run those transactions at serializable and retry on 40001. You write straightforward code and the database does the reasoning.

Advisory locks. PostgreSQL's pg_advisory_xact_lock(key) locks an arbitrary number you choose (such as a hash of a customer ID) until the transaction ends. Useful for serialising work that doesn't correspond to a single row, like "only one billing run per customer at a time".

A quick guide: counter or balance → atomic update. Unique thing → unique constraint. Non-overlap → exclusion constraint. Complex read-modify-write on one row → FOR UPDATE (high contention) or version check (low contention, long think time). Rule across many rows → serializable with retries, or lock a parent row.

8. Deadlocks

Locks create the possibility of deadlock. Transaction A transfers from account 1 to account 2: it locks row 1, then asks for row 2. At the same moment, transaction B transfers from 2 to 1: it locks row 2, then asks for row 1. Each waits for the other, forever.

Databases detect this. PostgreSQL, after a transaction has waited for a lock for deadlock_timeout (one second by default), checks the graph of who waits for whom; if there's a cycle, it aborts one transaction with a deadlock error (SQLSTATE 40P01), releasing its locks so the other proceeds. InnoDB detects deadlocks immediately and rolls back the transaction that has done the least work.

Handling them is straightforward: treat deadlock errors as retryable, like serialization failures. Preventing most of them is also straightforward: acquire locks in a consistent order. If every transfer locks the lower account ID first, the cycle above can't form. Keeping transactions short shrinks the window, and locking everything you need up front (one SELECT … FOR UPDATE for both rows, ordered by ID) is better than locking incrementally.

9. A real-world walk-through: selling the last 100 tickets to 5,000 people

A popular event goes on sale. 100 tickets remain; 5,000 buyers click at once. Here's how the design evolves, and why each naive version fails.

Version 1: read, check, write. Each request runs SELECT remaining, checks it's positive, charges the card, then writes remaining - 1. At read committed this is a textbook lost update: hundreds of requests read the same value and oversell badly. Wrapping it in a transaction at the default level changes nothing.

Version 2: lock the row. SELECT … FOR UPDATE, check, charge the card, update, commit. Now it's correct — but each transaction holds the lock on the one hot row while calling the payment provider, say 800 ms. Only one transaction can hold the lock at a time, so throughput is about 1 / 0.8 s ≈ 1.25 purchases per second. 5,000 buyers queue on one row lock, connections pile up, the pool exhausts, and the whole site slows. The lesson: throughput on a hot row is 1 divided by how long you hold its lock.

Version 3: shrink the critical section to one statement. Separate reserving a ticket from paying for it:

-- reserve: one atomic statement, holds the row lock for microseconds
UPDATE events SET remaining = remaining - 1
WHERE id = 7 AND remaining > 0
RETURNING remaining;
-- 1 row → create a reservation (expires in 10 minutes) and send the buyer to payment
-- 0 rows → sold out

The row lock is now held only for the statement itself — tens of microseconds plus the commit's log flush — so one row can sustain thousands of reservations per second. Payment happens outside any transaction on the inventory row. When payment succeeds, the reservation is confirmed; a background job returns expired, unpaid reservations to remaining with the same kind of atomic update. A unique constraint on (event, buyer, idempotency_key) makes retried requests safe: a buyer whose network glitched can't reserve twice.

Version 4: when one row is still too hot. For a sale with millions of buyers, even microsecond locks on one row, plus the durable commit each needs, become the limit. Two standard techniques: split the counter into, say, 10 rows (buckets) of 10 tickets each and have each request pick a random bucket with stock, spreading lock contention ten ways; or put a queue in front of the database — a virtual waiting room — so buyers are admitted at a rate the database handles comfortably and everyone else sees their place in line (sc1's Eras Tour story is what happens without one).

Checking correctness. Can it oversell? No: every decrement is conditional on remaining > 0 and atomic, and a CHECK (remaining >= 0) constraint backs it up. Can one buyer get two tickets by retrying? No: the idempotency key's unique constraint. Can a crash lose a sale? The reservation and decrement commit together in one transaction; payment confirmation is idempotent. Each invariant is protected by a named mechanism, which is exactly how an interviewer wants to hear it argued.

The formal anomaly names, and why they matter

The SQL standard defines isolation levels by three "phenomena" in informal prose, and the 1995 paper by Berenson and colleagues showed the definitions are ambiguous and miss anomalies such as lost update and write skew. Atul Adya's later work defined isolation precisely in terms of dependency graphs between transactions, and his names are what you'll see in Jepsen reports: G0 (dirty write: a cycle of write-write dependencies), G1 (dirty and intermediate reads, and cycles of write and read dependencies), and G2 (anti-dependency cycles, where one transaction's read is overwritten by another's write — write skew and phantoms). G-single is a cycle with exactly one anti-dependency, which includes read skew and lost update; snapshot isolation forbids G-single but allows G2, which is precisely why it permits write skew. Knowing this vocabulary lets you read a database's isolation claims critically rather than trusting the level's name.

Why SSI's rule works

Fekete and colleagues proved that under snapshot isolation, every non-serializable history contains a cycle in the dependency graph with two consecutive anti-dependency (read-write) edges between concurrent transactions — the "dangerous structure" T1 →rw T2 →rw T3. PostgreSQL tracks rw-dependencies using SIREAD predicate locks (on relations, pages or tuples, promoted to coarser granularity when there are too many) and, when a transaction would complete a dangerous structure, aborts one of the participants, preferring one that can be safely retried. Because it checks for the structure rather than a full cycle, it has false positives; declaring transactions READ ONLY, keeping them short, and using indexes (so predicate locks are on tuples rather than whole relations) all reduce them. A read-only transaction can even be made to wait for a "safe snapshot" (SERIALIZABLE READ ONLY DEFERRABLE) that guarantees it can never be aborted, which is ideal for long reports.

Hot rows and the throughput ceiling

Any design where many transactions must update the same row serialises on that row's lock, and its throughput ceiling is roughly 1 / (lock hold time). With synchronous commit, the hold time includes flushing the commit record to disk (and to a replica, if replication is synchronous), so even a single-statement update on one row tops out in the low thousands per second on good hardware. Techniques to go beyond that all avoid funnelling through one row: splitting a counter into N sub-counters summed on read; accumulating increments in a log table and aggregating asynchronously; reserving blocks of IDs or stock (a worker takes 100 at once and hands them out from memory); and group commit, where the database flushes many transactions' commit records in one disk write. Recognising a hot row in a design, and its throughput ceiling, is a very senior signal.

MVCC cleanup and transaction ID wraparound

PostgreSQL transaction IDs are 32-bit counters, compared with wraparound arithmetic: each ID sees about two billion IDs as "in the past" and two billion as "in the future". A row created by a very old transaction would eventually appear to be from the future and vanish. To prevent that, vacuum freezes old rows, marking them as visible to everyone regardless of IDs. If vacuum falls far enough behind — because autovacuum is too slow for the write rate, a long transaction blocks it, or an abandoned replication slot pins old rows — the database warns, and eventually stops accepting new transaction IDs (effectively refusing writes) until a vacuum completes, which on a huge table can take many hours. PostgreSQL has added 64-bit counters internally in places and made freezing more efficient over releases, but monitoring age(datfrozenxid) remains essential. The Mandrill incident in prod shows what happens when it's missed.

Isolation in distributed databases

Everything above concerns one database node. When data is spread across machines, providing serializability needs coordination across them: distributed databases such as Google Spanner, CockroachDB and YugabyteDB run transactions over consensus-replicated shards and use timestamps to order them. Spanner offers strict serializability (serializable plus real-time order: if T1 commits before T2 starts, T2 sees T1), using tightly synchronised clocks with bounded uncertainty and waiting out that uncertainty at commit. CockroachDB defaults to serializable and retries transactions that conflict. The costs are cross-node round trips on every commit, which is why sc9 (consistency models) and sc11 (distributed transactions) treat these separately. When a single database is enough, it is always simpler and faster.

Trust, but verify: what Jepsen keeps finding

Jepsen tests databases by running concurrent transactions under faults and checking the histories for anomalies. Repeatedly, databases turn out to provide weaker isolation than documented: MySQL's repeatable read allowing lost updates (2023), a PostgreSQL 12 serializable bug that allowed G2-item anomalies in certain conditions (found in 2020 and fixed), and many distributed databases losing writes during network partitions. The lesson for an engineer isn't cynicism but defence in depth: protect critical invariants with constraints the database checks directly, test concurrency behaviour you depend on, and prefer simple, well-understood patterns (atomic updates, unique constraints) over reasoning that depends on subtle isolation semantics.

How transaction problems show up

Data that doesn't add up. Inventory goes negative, a coupon is redeemed twice, two users get the same username, a room is double-booked. Rare and timing-dependent, these often appear only under load. Look for read-then-write code paths without a lock, version check or constraint.

Lock waits and pile-ups. Latency spikes while CPU is low: transactions are waiting for locks. A migration taking a strong table lock, or a transaction that holds a row lock while calling an external service, can block hundreds of others. In PostgreSQL, pg_stat_activity shows sessions with wait_event_type = 'Lock', and pg_blocking_pids(pid) shows who's blocking whom.

Deadlock and serialization-failure spikes. A rising rate of 40P01 or 40001 errors after a deploy usually means a new code path locks in a different order or a transaction got longer. Track these as metrics and make sure the application retries them rather than surfacing errors to users.

Idle in transaction. A session that began a transaction and then stopped sending queries — often an application that opened a transaction, called a slow API, or crashed mid-request without closing it — holds locks and blocks vacuum. Visible in pg_stat_activity as state idle in transaction with an old xact_start.

Bloat and wraparound risk. Tables growing without more rows, rising dead-tuple counts, and a climbing oldest-transaction age mean cleanup is blocked or falling behind.

Metrics and knobs

Watch: deadlocks and serialization failures per minute, lock wait time, the age of the oldest running transaction, the number of sessions idle in transaction, dead tuples per table and autovacuum activity, and age(datfrozenxid) per database with alerts well before the danger zone. Useful PostgreSQL settings: statement_timeout (stop runaway statements), lock_timeout (fail fast instead of queueing forever — essential for migrations), idle_in_transaction_session_timeout (kill abandoned transactions), deadlock_timeout, default_transaction_isolation, and autovacuum aggressiveness for large, busy tables. In MySQL: innodb_lock_wait_timeout, the deadlock log (SHOW ENGINE INNODB STATUS), and transaction_isolation.

A real incident: Mandrill, February 2019

Mandrill, Mailchimp's transactional email service, was down or degraded for more than a day and a half. It ran on several sharded PostgreSQL instances. Months earlier, engineers had noticed transaction IDs reaching about half their limit at peak and filed a ticket for better monitoring. Then one shard, which the load-balancing hash already favoured, saw a large spike in writes. Its autovacuum fell behind (and may have failed), the transaction ID age reached PostgreSQL's safety limit, and the database stopped accepting writes to protect itself from wraparound. Recovery required a long vacuum of large tables while the service queued email. The fixes were the ones this lesson points to: monitoring and alerting on transaction ID age, tuning autovacuum for busy tables, and not letting one hot shard carry disproportionate write load. It's a reminder that MVCC's cleanup is not an optional background detail but part of the database's availability.

A second, very common pattern has no single famous post-mortem because it happens everywhere: a flash sale or promotion oversells because the purchase path reads stock, checks it in application code and writes it back. It passes every test (which run one request at a time) and fails the first time real concurrency arrives. The fix is almost always the atomic conditional update from the walk-through, backed by a check constraint.

In this lab you'll make 20 threads sell tickets concurrently and watch updates get lost, then fix it three ways: an atomic update, optimistic concurrency with a version column, and a lock taken before reading. It uses SQLite, which ships with Python. An optional second part uses PostgreSQL to show write skew and serializable isolation.

        # 0 rows: the version moved on, so our read was stale; try again

def locked(conn):                     # FIX 3: take the write lock before reading
    conn.execute("BEGIN IMMEDIATE")     # SQLite's equivalent of SELECT ... FOR UPDATE
    (sold,) = conn.execute("SELECT sold FROM tickets WHERE event = 7").fetchone()
    time.sleep(0.001)
    conn.execute("UPDATE tickets SET sold = ? WHERE event = 7", (sold + 1,))
    conn.commit()

def run(fn, workers=20, each=25):
    reset()
    def worker():
        conn = sqlite3.connect(DB, timeout=30, isolation_level=None if fn is locked else "")
        for _ in range(each):
            fn(conn)
        conn.close()
    threads = [threading.Thread(target=worker) for _ in range(workers)]
    t0 = time.perf_counter()
    for t in threads: t.start()
    for t in threads: t.join()
    (sold,) = setup.execute("SELECT sold FROM tickets WHERE event = 7").fetchone()
    print(f"{fn.__name__:<18} expected {workers*each}, got {sold:4d}  "
          f"({time.perf_counter()-t0:.1f}s)")

for fn in (read_modify_write, atomic_update, optimistic, locked):
    run(fn)

  2. Run python sc5_lab.py. A typical run:

    read_modify_write  expected 500, got   25  (2.2s)
atomic_update      expected 500, got  500  (2.1s)
optimistic         expected 500, got  500  (2.4s)
locked             expected 500, got  500  (2.8s)

What to look for. The buggy version loses most of its updates — the exact number varies from run to run, which is the signature of a race. Many threads read the same value of sold during the 1 ms gap and all write the same "sold + 1". Each fix gets exactly 500, for a different reason: the atomic update never brings the value into the application; the optimistic version detects that its read went stale (zero rows updated) and retries; the locked version takes SQLite's write lock with BEGIN IMMEDIATE before reading, so nobody else can write in between. Notice the locked version is slowest: every thread waits its turn, including through the 1 ms of "work" — that's the hot-row throughput ceiling from the walk-through, in miniature.

Optional part 2 (PostgreSQL, two terminals). This part wasn't run on the machine that wrote this lesson; it's the standard write-skew demonstration and the behaviour below is what PostgreSQL documents. With PostgreSQL available (for example docker run -e POSTGRES_PASSWORD=pw -p 5432:5432 postgres), create CREATE TABLE doctors (name text PRIMARY KEY, on_call boolean); INSERT INTO doctors VALUES ('alice', true), ('bob', true);. Open two psql sessions and run, alternating between them:

-- session A                                   -- session B
BEGIN ISOLATION LEVEL REPEATABLE READ;         BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors WHERE on_call;    SELECT count(*) FROM doctors WHERE on_call;
-- both see 2
UPDATE doctors SET on_call = false             UPDATE doctors SET on_call = false
  WHERE name = 'alice';                          WHERE name = 'bob';
COMMIT;                                        COMMIT;

Both commit and SELECT * FROM doctors shows nobody on call: write skew under snapshot isolation. Reset the rows and repeat with BEGIN ISOLATION LEVEL SERIALIZABLE: now the second session fails (at its update or its commit) with ERROR: could not serialize access due to read/write dependencies among transactions — the error your retry loop must catch. Finally, try both sessions updating the same row at repeatable read to see "could not serialize access due to concurrent update", PostgreSQL's lost-update protection.

Identify the anomaly

A meeting-room booking service runs at PostgreSQL's default isolation. Booking logic: BEGIN; SELECT count(*) FROM bookings WHERE room = $1 AND overlaps($2, $3); if 0: INSERT the booking; COMMIT;. Two users book the same room for overlapping times simultaneously, and both succeed. (a) Name the anomaly. (b) Would REPEATABLE READ fix it? (c) Give two correct fixes.

Answer

(a) This is write skew driven by a phantom: both transactions read "no overlapping booking", then each inserts a different new row. Neither overwrote the other's row, so it isn't a lost update, and there was no existing row either could have locked.

(b) No. Under PostgreSQL's REPEATABLE READ (snapshot isolation) each transaction sees its own snapshot with no conflicting row, and they write different rows, so no write-write conflict is detected. Only SERIALIZABLE (SSI) tracks the read of the range and the other transaction's insert into it, and aborts one.

(c)

  • Exclusion constraint (best): ALTER TABLE bookings ADD EXCLUDE USING gist (room WITH =, tstzrange(start_at, end_at) WITH &&); (needs the btree_gist extension for the equality on room) — the database itself rejects any overlapping booking, regardless of isolation level, code path or future bugs.
  • SERIALIZABLE isolation with a retry loop on serialization failure (SQLSTATE 40001).
  • Alternatively, lock a parent row: SELECT … FROM rooms WHERE id = $1 FOR UPDATE before checking, so bookings for the same room are serialised — simple, but it reduces concurrency and every code path that books must remember to do it.
Fix the code

An ORM-based wallet service does: w = Wallet.get(id); w.balance -= amount; w.save() inside a transaction, on MySQL with default settings. Under load, balances occasionally end up higher than they should. Why, and what are two fixes?

Answer

It's a lost update. Two concurrent withdrawals both load the same balance (from their snapshots), subtract in application memory, and save; the second save overwrites the first, so one withdrawal disappears and the balance ends up too high. MySQL's default repeatable read doesn't prevent this — its updates don't abort when the row changed after the snapshot, as Jepsen demonstrated. Fixes: (1) an atomic conditional update, UPDATE wallets SET balance = balance - :amt WHERE id = :id AND balance >= :amt, checking the affected row count (and a CHECK (balance >= 0) constraint as a backstop); or (2) lock the row when loading it, SELECT … FOR UPDATE (most ORMs have a select_for_update or with_for_update option); or (3) a version column with optimistic retries, if contention on a single wallet is low.
