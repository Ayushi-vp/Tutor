A fast-growing note-taking app keeps everything in one PostgreSQL database: every page, every paragraph, every comment for every workspace. The team has already done the sensible things. They tuned indexes, moved to the biggest machine their cloud provider rents, added read replicas for reads and a cache for hot pages. It worked for two years. Now the database is several dozen terabytes and growing by more every month, and the problem is writes: every keystroke saved by millions of users is a write, and writes can only go to the one leader. Its CPU sits above 80% at peak, vacuum can't keep up with the churn, and there's no bigger machine to buy.

Replicas can't help here, because every replica has to apply every write too (sc6). Caching can't help, because the problem isn't reads. The only way forward is to stop having one database hold everything: split the data so that each machine holds and writes only part of it. That's partitioning, usually called sharding when the pieces live on different machines. This isn't hypothetical — it's almost exactly what Notion did in 2021, splitting its database into 480 logical shards on 32 machines.

The idea is simple; the consequences aren't. How do you decide which rows go where, so that load is even and most requests touch only one machine? What happens when one customer is a thousand times bigger than the rest, or one post goes viral? When you add machines next year, how do you move data without moving all of it — and without taking the product offline? And what happens to everything that used to be easy in one database: a query across all users, a unique email constraint, a transaction that touches two customers, an auto-incrementing ID?

This lesson answers those questions. You'll learn the three ways to partition (range, hash and directory), how to choose a shard key from your access patterns, how skew and hot keys break even distribution and how to fix them, why modulo hashing is a trap and what consistent hashing and logical partitions do instead, how requests find the right shard, what becomes hard after sharding and the standard answers, and how real companies reshard a live system. It ends with a full design for a multi-tenant SaaS product.

The analogy: splitting a phone book into volumes

A city's phone book grows until it's too heavy to print or carry. So the publisher splits it into volumes: A-F, G-M, N-S, T-Z. Each volume is smaller, can be printed on a different press, and a reader looking for "Patel" opens only one volume. That's range partitioning: each partition (volume) holds a contiguous range of the key (the surname).

Problems appear quickly. Surnames aren't evenly spread — the volume containing "S" is much thicker than the one containing "X" — and if everyone suddenly wants to call people named "Smith", that one volume gets all the traffic. The publisher could instead assign entries to volumes by a scrambled code computed from the name, which spreads them evenly but means you can no longer find "all names starting with Pat" in one volume. That's hash partitioning. Or the publisher could keep a small index card saying exactly which volume each family is in, so a huge family can get a volume of its own — directory partitioning.

The analogy breaks in one way: a phone book is printed once a year. A database's partitions must keep taking writes and serving reads while data grows and while it's moved between machines, which is where most of the difficulty lives.

The big picture

In a sharded system, each shard is an independent database holding a subset of the rows — for example, all data for a subset of customers. Each shard is usually replicated for availability, so "shard" means a small replicated cluster, not one machine. A shard key, such as tenant_id, decides which shard each row lives on. A router uses the key and a map of partitions to send each request to the right shard.

Sharding scales two things replication can't: data size (each shard stores only its share) and write throughput (each shard's leader handles only its share of writes). Four shards give roughly four times the write capacity; forty give forty. The price is that anything needing data from several shards gets harder, which is why the choice of shard key — deciding what lives together — is the most important decision in the whole design. A good key makes the common requests single-shard and leaves only rare ones, like company-wide reports, to be handled some other way. A bad key makes the common requests cross shards, and no amount of hardware fixes that.

A quick rule of thumb for when to shard: estimate data size and peak write rate for the next two or three years (sc1). If the largest machine you'd comfortably run, with a replica for failover, can hold the data and sustain the writes at around 50-60% utilisation, don't shard yet. If not, plan sharding before you're forced into it, because resharding under pressure is how outages happen. Planned early, it's a project; forced late, it's an emergency.

1. What sharding buys, and what it costs

Before any mechanics, be clear about the trade. A single database gives you a lot for free: any query can join any tables, a transaction can touch any rows atomically, a unique constraint covers the whole table, an auto-increment counter hands out IDs, and one backup captures everything consistently. Sharding gives up some of each in exchange for scaling data and writes horizontally.

That's why sharding comes after the cheaper steps in sc1's list. A well-tuned relational database on a large machine, with caching and read replicas, handles tens of thousands of transactions per second and many terabytes. When you do need to shard, the goal of the design is to keep as much of the left-hand column as possible for the queries that matter, by making sure they only need one shard.

2. Range partitioning

With range partitioning, each partition owns a contiguous range of key values: users with IDs 1-1,000,000 on partition 1, 1,000,001-2,000,000 on partition 2, and so on; or surnames A-F, G-M. Keys stay sorted across partitions, so a range scan — all events between 09:00 and 10:00 for a device, all users whose name starts with "Pat" — touches only the partitions covering that range, often just one.

Its weakness is hot ranges. If the key increases over time — an auto-increment ID, a timestamp — every new row goes into the last partition. That one partition takes 100% of the write traffic while the others take none, which defeats the purpose of sharding writes. Uneven key distributions cause the same thing more slowly: if most user names start with a few letters, those partitions are bigger and busier.

Range-partitioned systems deal with this by splitting: when a range grows too large or too busy, it's divided into two ranges, and one half can move to another machine. Google's Bigtable, HBase and CockroachDB all split ranges automatically (CockroachDB splits a range when it exceeds a size threshold, and can also split by load). Splitting rebalances size and gradually spreads load, but it can't fix a single hot key, and a strictly increasing key still sends all new writes to whichever range currently holds the end. The standard advice for range-partitioned systems is therefore to avoid monotonically increasing leading keys — prefix them with something that spreads writes, like a device ID or a hashed bucket.

Range partitioning inside a single database is also common and useful for a different reason: PostgreSQL's declarative partitioning by month lets you drop a whole month of old data instantly by detaching its partition, instead of deleting billions of rows. That's partitioning for data lifecycle, not for spreading load.

3. Hash partitioning

With hash partitioning, each key is run through a hash function — which turns any value into a number that looks random but is always the same for the same input — and the number decides the partition. Neighbouring keys (user 1001 and user 1002) land on unrelated partitions. Keys, and usually load, spread evenly, and monotonically increasing keys stop being a problem.

The cost is that order is gone. A range query on the key must ask every partition, because the keys in any range are scattered everywhere. For many workloads that's fine: most requests are point lookups ("this user's profile", "this tenant's documents"), not ranges over the key.

A powerful combination is a compound key that hashes the first part and sorts by the rest. Cassandra's primary key does exactly this: the partition key (say channel_id) is hashed to choose the partition, and the clustering columns (say message_id) sort rows within it. So "latest 50 messages in channel 7" is one partition, read in order — the even spread of hashing plus the cheap range scan of sorting, as long as the range is within one partition key.

How to turn a hash into a partition number is where many designs go wrong; section 6 covers why hash(key) % N is a trap.

4. Directory-based partitioning

With directory-based partitioning, a lookup table records which partition each key (or each tenant) lives on: tenant 812 → shard 2, tenant 813 → shard 5. The router consults the directory (usually cached) for every request.

The directory adds a component that must be fast and highly available, but it gives something neither range nor hash does: control over individual placements. You can put a huge tenant on a dedicated shard, move one noisy customer without touching anyone else, place European customers' data on European shards for data-residency laws, or move a tenant to a shard running a new database version as a canary. Multi-tenant SaaS products very often end up here, sometimes combined with hashing: small tenants are hashed into shared logical partitions, and the directory holds exceptions for large or special tenants.

5. Choosing the shard key

This is the decision that matters most, because changing it later means moving every row. A good shard key has four properties.

Many distinct values. A key with 50 possible values (US states) can never be spread across more than 50 shards, and some values will be far bigger than others. User IDs, tenant IDs and device IDs have millions.

Even spread of data and traffic. Not just rows, but requests. Hashing spreads rows; it doesn't help if one key gets most of the traffic (section 7).

Matches the dominant access pattern. The most frequent and most latency-sensitive queries should include the shard key, so they go to one shard. Write down the top queries and check each. For a multi-tenant business product, almost every query is "within this tenant", so tenant_id is natural. For a social app, "this user's posts" and "this user's settings" suggest user_id. For Notion, every block belongs to one workspace and users work within one workspace at a time, so workspace ID was chosen.

Keeps transactional units together. Data that must be updated atomically should share a shard key, so transactions stay on one shard. An order and its line items should live together (shard by customer or by order, not by product).

Here's a worked example of the reasoning for a food-delivery app's orders table, with three candidates:

That pattern is common: pick the shard key for the most important access path, and serve other access paths from derived copies partitioned differently. It's a direct application of "data that's read differently can be stored differently" (sc8).

6. Assigning keys to shards: modulo, consistent hashing and logical partitions

The obvious way to map a hash to one of N shards is hash(key) % N. It spreads keys evenly and needs no map at all. The trouble comes when N changes. Going from 4 shards to 5, a key stays put only if hash % 4 happens to equal hash % 5, which is true for about 1 key in 5. The other 80% of keys — and their data — must move. Adding one machine means migrating most of the database, and for a cache it means losing most of the cached entries at once (sc3's avalanche). You'll measure exactly this in the lab.

Consistent hashing fixes this. Imagine the hash space bent into a circle (a ring). Each node is hashed to a position on the ring, and each key belongs to the first node found going clockwise from the key's own position. When a node is added, it takes over only the keys between its position and the previous node's — about 1/N of all keys — and every other key stays where it was. When a node leaves, only its keys move, to its clockwise neighbour.

With one position per node, the arcs vary a lot in size by chance, so some nodes own much more than others, and a new node relieves only one neighbour. The fix is virtual nodes: each physical node takes many positions on the ring (often 100 or more). Arcs average out, and a new node takes small slices from every existing node. Amazon's Dynamo, Cassandra and many caches use this.

The other widely used approach avoids rings entirely: a fixed number of logical partitions. Choose a number much larger than the number of machines you'll ever have — 256, 1,024, 4,096 — and hash every key into one of them, once and forever: partition = hash(key) % 1024. Then keep a small map from partitions to physical nodes. With 8 nodes, each holds 128 partitions. Adding a ninth node means moving about 114 whole partitions to it, updating the map, and never rehashing any key. Kafka topics, Elasticsearch indexes, Couchbase buckets, Vitess keyspaces and Instagram's and Notion's Postgres shards all work this way. Notion chose 480 logical shards specifically because 480 divides evenly by many numbers (8, 10, 12, 16, 20, 24, 30, 32, 40, 48…), so they could run it on many different physical host counts. The only limit is that you can never have more machines than logical partitions, so you choose the number with decades of growth in mind.

7. Skew and hot keys

Even a perfect hash spreads keys evenly, not load. Real traffic is skewed (sc3's Zipf distribution): a celebrity with 100 million followers, a viral post, a flash-sale product, the one enterprise customer with half the data. The shard holding that key is overloaded while the rest are idle, and adding shards doesn't help, because the hot key still lives on one of them. Managed stores make this concrete: a DynamoDB partition serves at most 3,000 reads and 1,000 writes per second, so any single key hotter than that is throttled no matter how large the table's total capacity is.

The fixes depend on what's hot:

Hot reads: cache the key in front of the database, including in-process caches for extreme cases (sc3), and coalesce identical concurrent requests. Reads of a viral post's content almost never need to reach the shard.

Hot writes to one key (a like counter, a view counter): write sharding, also called key salting. Store the logical key as several physical keys — likes:post99#0 to likes:post99#9 — have each write pick one at random, and have reads fetch all ten and add them up. Writes spread across up to ten partitions; reads get ten times more expensive, so apply it only to the few keys that need it, ideally automatically when a key is detected as hot.

A huge tenant: give it dedicated capacity (its own shard or shards) through the directory, and partition within the tenant by a second key, such as a hashed document ID, if it outgrows one machine. Its queries then scatter across its own shards, which is acceptable because they're only its shards.

A hot range from time-ordered keys: add a leading component that spreads writes (device ID, a small hashed bucket number) so "now" is spread across partitions.

Detecting skew is part of operating a sharded system: track requests and bytes per shard and per top key, and alert when one shard's load diverges from the rest.

8. Routing: how requests find their shard

Every request must be sent to the shard that owns its key. That requires a partition map — key → partition → node — and something that uses it. There are three common placements.

In the client. The application links a library that holds the map and connects directly to shards. It's the fastest (no extra hop), but every service, in every language, needs the library, and all must learn about map changes promptly.

In a routing tier. Clients connect to a proxy that looks like an ordinary database; the proxy parses each query, finds the shard key, and forwards it — or scatters it and merges results. Vitess's vtgate for MySQL and Citus's coordinator for PostgreSQL work this way. Clients stay simple; the tier adds a hop and must scale and stay available.

In the database itself. Any node accepts any request and forwards it internally to the owner. Cassandra nodes, CockroachDB and most distributed databases do this, often with smart clients that learn the map to skip the extra hop.

Wherever it lives, the map itself is stored in a consensus-backed system (etcd, ZooKeeper, or the database's own metadata ranges) and carries a version. During a move, a router with a stale map may send a request to the old owner; the old owner answers with a "wrong shard" or "moved" error, and the router refreshes its map and retries. This is how rebalancing happens without every client being updated at the same instant.

9. What gets harder after sharding, and the standard answers

Queries without the shard key. "Find the user with this email" when data is sharded by user ID must ask every shard and merge the answers: scatter-gather. It works, but its latency is set by the slowest shard (sc1's tail latency effect: with 64 shards, the query waits for the worst of 64), its cost grows with every shard added, and one unavailable shard fails the whole query. Keep scatter-gather off hot paths. For frequent lookups by another key, maintain a separate mapping partitioned by that key (email → user ID), or a global secondary index.

Secondary indexes. A local index lives inside each shard and covers only its rows: writes stay on one shard, but queries on the indexed column must scatter. A global index is itself partitioned by the indexed value: a lookup by email goes to exactly one index partition, but every write to a user may need to update an index partition on another machine, which means a cross-shard write. Most systems maintain global indexes asynchronously — DynamoDB's global secondary indexes are eventually consistent — so a lookup may briefly miss a just-written row.

Joins. Joins within a shard work normally, which is another reason to keep related data together (a customer's orders with the customer). Small, rarely changing tables (countries, currencies, plans) are often copied to every shard as reference tables so joins against them stay local. Joins between large tables on different keys move to the application, to a derived copy partitioned the other way, or to an analytics system.

Transactions. A transaction on one shard is an ordinary local transaction. One that spans shards — transfer money between two customers on different shards — needs a distributed protocol: two-phase commit, where a coordinator asks every shard to prepare and then to commit, or a saga, a sequence of local transactions with compensating actions if a later step fails. Both are slower and more complex (sc11). The best strategy is design: choose keys so that the transactions that matter are single-shard.

Uniqueness. A unique constraint on each shard only guarantees uniqueness within that shard. Global uniqueness for a column other than the shard key (usernames, emails) needs a separate table sharded by that column, written as part of registration — which is itself a cross-shard operation, often handled by writing the claim first and then the user.

IDs. An auto-increment counter per shard would produce duplicates across shards, and one global counter would be a bottleneck. Common schemes: random UUIDs (unique without coordination but unordered, hurting index locality, sc4); time-ordered UUIDv7; and Snowflake-style IDs, 64-bit numbers built from a millisecond timestamp (41 bits in Twitter's original design), a machine number (10 bits) and a per-millisecond sequence (12 bits), so each machine can generate about four million IDs per second, locally, roughly in time order. Instagram's variant replaced the machine number with a logical shard number, so an ID alone tells you which shard holds the row.

Operations. Every schema migration must be applied to every shard, tolerate shards being temporarily at different versions, and be retried where it fails. Backups are per shard and aren't consistent with each other at the same instant unless you coordinate them. Monitoring, capacity planning and failover all happen per shard. This operational multiplication is the cost teams most often underestimate.

10. Resharding a live system

Whether you're sharding a monolith for the first time or splitting shards that have grown, the data has to move while the product keeps running. The standard playbook has five phases, each designed to be reversible.

  1. Prepare. Create the new shards and the routing logic, with the new placement not yet active. Make sure every query path carries the shard key.
  2. Copy and keep in sync. Backfill existing data into the new shards in the background, throttled so it doesn't hurt production. Meanwhile capture every new change so the copy stays current, either by double-writing from the application (write to old and new) or by streaming changes from the old database's log with change data capture. Log-based capture is usually safer, because application double writes aren't atomic and can diverge when one side fails. Notion used an audit log of changes because logical replication couldn't keep up with their write volume, and their backfill took about three days.
  3. Verify. Compare row counts and checksums per range. Run dark reads: serve users from the old system while also querying the new one and comparing results, logging any difference. Notion had the verification written by different engineers from the migration, so the same mistake couldn't hide in both.
  4. Cut over. Switch routing to the new shards, range by range or tenant by tenant, pausing writes briefly for each switch (or fencing old writes with a version check) so no write lands in the old place after the switch. Notion's final cutover took five minutes of scheduled maintenance. Keep replicating in reverse (new → old) for a while so you can roll back.
  5. Clean up. After a confidence period, stop the reverse sync, delete the moved data from the old shards, and remove the old routing.

Tools increasingly automate this — Vitess's resharding workflows, Citus's shard rebalancer, and distributed SQL databases that move ranges continuously in the background — but the phases are the same, and interviewers expect you to name them: copy, sync, verify, switch, clean up, with rollback at every step.

11. A real-world walk-through: sharding a multi-tenant SaaS database

A B2B document product has 20,000 tenants and 30 TB of data growing by 1 TB a month; the largest 10 tenants hold 40% of the data; nearly every query is within one tenant; administrators occasionally need cross-tenant reports; and the single primary is at its write limit. Here's the design and the reasoning.

Shard key: tenant ID. Almost every query and every transaction is within one tenant, so they stay on one shard with full SQL, joins and transactions. Tenant data can also be exported, deleted or moved as a unit, which helps with contracts and data-protection requests.

Placement: logical partitions plus a directory. Small and medium tenants are hashed into 512 logical partitions, placed at first on 8 physical shards (64 partitions each), each shard a PostgreSQL leader with two replicas. A directory — a small table in a replicated store, cached in every router — overrides the hash for special tenants. That combination gives even spreading for the long tail without a directory entry per tenant, and explicit control where it's needed.

The skew. The 10 largest tenants each hold about 1.2 TB on average, with 4% of all data each — together more than several whole shards. Each gets a dedicated shard through the directory. The biggest two, growing fastest, are sub-partitioned by a hash of document ID across two shards each; their queries that span documents scatter across only their own shards, which is acceptable.

Capacity math. The long tail is 60% of 30 TB, 18 TB, over 8 shards: about 2.3 TB each, comfortable for one PostgreSQL server with room to grow. At 1 TB a month overall, the pooled shards gain about 75 GB each per month, so the plan adds shards when any reaches about 4 TB, roughly every two years, by moving whole logical partitions — about one-ninth of them when going from 8 to 9 shards.

Routing. A thin data-access layer in the application resolves tenant → partition → shard using the cached map, versioned, with a "moved" error from the database layer triggering a refresh. Connection pooling runs per shard.

IDs. Documents use UUIDv7, so IDs are unique across shards, generated without coordination, and roughly time-ordered for index locality.

Cross-tenant reports. They never scatter-gather against production shards. Change data capture streams every shard's changes into a columnar warehouse, where reports run without affecting the product (sc18).

Operations. Schema migrations run through a tool that applies them shard by shard, tolerates mixed versions for a while, and reports progress. Moving a tenant uses the resharding playbook at tenant granularity: copy, sync by CDC, verify, a few seconds of write pause while the directory entry flips, then clean up. The same mechanism handles data-residency moves when a customer requires EU hosting.

What it costs, stated plainly. A routing layer in every query path, tooling for migrations and moves, per-shard monitoring and backups, and a warehouse. Before building it, the team should evaluate Citus (sharded PostgreSQL) or a distributed SQL database, which provide much of this plumbing; the key design decisions — tenant ID as the key, isolation for giant tenants, reports off the transactional path — stay the same either way.

Why consistent hashing moves 1/N of keys, and when it isn't enough

On a ring, each node owns the arc between its predecessor and itself. When a new node is inserted, it splits exactly one arc (or, with virtual nodes, many small arcs), taking only the keys in the part it now owns; no other key's "next node clockwise" changes. With N nodes of roughly equal share, the new node's share, and therefore the fraction of keys that move, is about 1/(N+1). The variance matters: with one position per node, arc sizes follow an exponential-like distribution and the largest can be several times the average, so load is uneven; with V virtual nodes per server, the imbalance shrinks roughly with the square root of V. Two refinements are worth knowing. Rendezvous (highest-random-weight) hashing scores every node for a key — hash(key, node) — and picks the highest; it moves the same minimal set of keys and needs no ring, which suits small node counts. Jump consistent hash maps a key to one of N numbered buckets with a tiny, memory-free algorithm, ideal when nodes are numbered and only added or removed at the end. And consistent hashing with bounded loads (used by Google and in HAProxy) caps each node at a multiple of the average load, spilling excess keys to the next node, which directly attacks skew.

The celebrity problem and precomputed fan-out

Social feeds are the classic case where the natural shard key creates unavoidable skew. If a user's timeline is precomputed by writing each new post into every follower's feed (fan-out on write), a post by an account with 100 million followers triggers 100 million writes spread across every shard — a write storm. If timelines are assembled at read time (fan-out on read), every follower's feed request reads the celebrity's recent posts, making that user's shard a read hot spot. Large social networks use a hybrid: fan-out on write for ordinary accounts, and fan-out on read for the few accounts above a follower threshold, merged at read time and heavily cached. The general lesson is that when the distribution of work per key has a very long tail, the head of the tail gets a different code path.

Partitioning secondary indexes and the cost of global uniqueness

A global secondary index turns every indexed write into a potential distributed transaction: the base row lives on one shard and its index entry on another. Doing both atomically needs two-phase commit, which adds latency and blocks on failures, so most systems update global indexes asynchronously and accept that index reads can lag. Spanner and CockroachDB do maintain global indexes transactionally, paying a cross-range commit on writes to indexed columns, which is why write-heavy tables in those systems are designed with few global indexes. Global uniqueness is a special case of the same problem: enforcing "email is unique" when data is sharded by user ID requires a global index or lookup table on email, updated in the same distributed transaction, or a claim-first protocol where the email reservation is written (conditionally) before the user row and cleaned up if registration fails.

Partition sizing and the number of partitions

How big should partitions be? Too few and large, and each move transfers a huge amount of data, rebalancing is coarse, and recovery of one partition takes long. Too many and small, and per-partition overhead dominates: Kafka pays in file handles and metadata per partition, Elasticsearch in memory per shard (its guidance is to keep shards to tens of gigabytes), and every scatter-gather query touches more pieces. Range-partitioned systems sidestep the choice by splitting and merging dynamically based on size and load, at the cost of more complex metadata and background activity. A practical rule for fixed schemes is to choose enough partitions for the largest cluster you can imagine, with each partition small enough to move in minutes, and to prefer numbers with many divisors.

Transactions across shards: why design beats protocol

Two-phase commit gives atomicity across shards, but at a price: an extra round trip of prepare messages, locks held on every participant until the coordinator's decision arrives, and the blocking problem — if the coordinator crashes after participants have prepared, they must hold their locks until it recovers. Sagas avoid blocking by committing each step locally and running compensating actions on failure, but they give up isolation: other transactions can see the intermediate states. Distributed SQL databases implement efficient variants (parallel commits, deterministic ordering) but still pay extra latency. This is why sharding design starts from the transactional boundaries of the domain: if "a tenant's documents" or "a customer's orders" is the unit that must change atomically, make it the shard key, and cross-shard transactions become rare exceptions rather than the normal path.

Hierarchical keys in distributed SQL

Distributed SQL databases store rows in ranges ordered by primary key, so the primary key is the partitioning decision. Designing it well means putting the locality key first: a primary key of (tenant_id, document_id) keeps each tenant's rows contiguous, so most queries hit one or a few ranges, while (document_id) with a random ID would scatter a tenant's rows across the whole cluster. Conversely, a primary key starting with a timestamp or a sequence recreates the hot-range problem, which is why these databases recommend UUIDs or hash-sharded indexes (CockroachDB can add a hidden hashed bucket column to spread sequential keys). Some also support pinning ranges to regions by a column value, which turns partitioning into a data-residency tool.

How sharding problems show up

One hot shard. One shard's CPU, I/O or latency is far above the others while the fleet average looks fine. Causes: a hot key, a tenant that grew enormously, or a range receiving all new writes. Dashboards must show per-shard metrics; fleet averages hide exactly this.

Scatter-gather creep. A feature adds a query without the shard key; it works in testing with 4 shards and gets slower and more fragile as shards grow to 64, until one slow shard makes the feature time out. Track the fraction of queries that are single-shard and review any new scatter-gather on a hot path.

Rebalancing hurting production. Moving partitions consumes disk and network on source and destination; unthrottled, it raises latency for everyone on those shards. Moves are throttled and scheduled, and paused automatically if latency rises.

Stale routing. After a move, a client with an old map writes to the old owner. Well-built systems reject these with a "moved" error and the client refreshes; badly built ones accept them, and data silently lands in the wrong place.

Migrations half-applied. A schema change succeeds on 60 shards and fails on 4, and code that assumes the new schema breaks on those four. Migration tooling must track per-shard state and code must tolerate both versions until all shards are done.

What to watch and tune

Per shard: request rate, p99 latency, CPU, disk usage and growth rate, replication lag, and connection count. Per key: the top keys by requests and bytes, sampled continuously, to catch hot keys early. For the system: the single-shard query ratio, scatter-gather latency, rebalance progress and throughput, and routing error ("moved") rates. Knobs include the number of logical partitions (chosen once, carefully), placement rules in the directory, split thresholds in range-partitioned systems, rebalance throttles, and hot-key mitigations such as salting and caching.

Real-world stories

Notion, 2021. Notion's single PostgreSQL database was hitting CPU limits, and vacuum was stalling on huge tables. They chose workspace ID as the partition key (every block belongs to one workspace, and users work within one workspace at a time), created 480 logical shards — 15 schemas on each of 32 physical databases — and migrated live: double-writing through an audit log, backfilling for about three days using all 96 CPUs of a large instance, verifying with dark reads using logic written by different engineers from the migration, and cutting over with five minutes of scheduled maintenance. The choice of 480, divisible by many numbers, was deliberately made so they could later change the number of physical hosts without awkward splits — which they did when they later expanded the fleet.

Discord. Messages are partitioned by channel and a time bucket, so a channel's recent history is one partition read. The failure mode was skew: huge public servers made some partitions far hotter than others, and in their LSM-based store (sc4) hot reads slowed whole nodes. Moving to a different database helped, but so did putting a service in front that coalesces identical concurrent requests for the same channel — a hot-key mitigation at the application layer.

Instagram. Early Instagram created thousands of logical shards as PostgreSQL schemas on a handful of physical servers, so they could move shards to new machines as they grew without rehashing. Their 64-bit IDs combined 41 bits of milliseconds, 13 bits of logical shard ID and 10 bits of sequence, generated inside PostgreSQL itself, so every ID was unique, time-sortable, and told the application exactly which shard held the row.

A two-minute experiment that shows why modulo sharding is a trap and consistent hashing isn't. It needs only Python 3.

import bisect, hashlib
h = lambda s: int(hashlib.md5(s.encode()).hexdigest(), 16)
keys = [f"user:{i}" for i in range(100_000)]

# 1. modulo sharding: 4 shards -> 5 shards
moved = sum(h(k) % 4 != h(k) % 5 for k in keys)
print(f"mod N, 4 -> 5 shards:         {moved/len(keys):.0%} of keys move")

# 2. consistent hashing with 100 virtual nodes per shard
def ring(shards, vnodes=100):
    points = sorted((h(f"{s}#{v}"), s) for s in shards for v in range(vnodes))
    return [p for p, _ in points], [s for _, s in points]
def owner(r, key):
    pts, owners = r
    return owners[bisect.bisect(pts, h(key)) % len(pts)]
r4, r5 = ring(["A", "B", "C", "D"]), ring(["A", "B", "C", "D", "E"])
moved = sum(owner(r4, k) != owner(r5, k) for k in keys)
print(f"consistent hashing, 4 -> 5:   {moved/len(keys):.0%} of keys move")

Output:

mod N, 4 -> 5 shards:         80% of keys move
consistent hashing, 4 -> 5:   20% of keys move

What it shows. Adding one shard to a modulo scheme moves four out of five keys — effectively a full data migration, or a near-total cache flush. With consistent hashing, only the keys the new shard takes over move: 20%, which is exactly its fair share (1/5). Every other key stays put.

Think it through. (1) Set vnodes=1 and count how many keys each shard owns: why is the distribution so uneven, and why do virtual nodes fix it? (2) Replace the ring with 1,024 logical partitions (h(k) % 1024) assigned round-robin to shards, then move partitions to a fifth shard: how many partitions must move, and how many keys get rehashed? (3) Make one key receive 30% of all requests: does any partitioning scheme spread that load?

Design it

A B2B SaaS stores documents: 20,000 tenants; the largest 10 tenants hold 40% of all data; total 30 TB, growing 1 TB/month; almost every query is within one tenant; admins occasionally need cross-tenant reports. Propose a sharding design.

Answer
  • Shard key: tenant_id — nearly all queries and transactions stay within one shard, and tenant data can be exported, deleted or moved as a unit.
  • Placement: logical partitions plus a directory. Hash ordinary tenants into a fixed, generous number of logical partitions (for example 512) placed on physical shards; keep a small, cached directory for exceptions. This spreads the long tail evenly and lets you place or move individual tenants deliberately.
  • Handle the skew: the 10 largest tenants get dedicated shards through the directory, and any that outgrow a node are sub-partitioned by a hash of document_id across several shards of their own. The long tail is packed many-per-shard.
  • Growth: at 1 TB/month, add shards and move whole logical partitions or individual tenants online using the playbook: copy, keep in sync via CDC, verify with checksums and dark reads, flip the directory entry during a brief write pause, clean up.
  • IDs: UUIDv7 or Snowflake-style IDs so documents never collide across shards and stay roughly time-ordered.
  • Cross-tenant reports: never scatter-gather against production shards; stream changes into a warehouse and run reports there.
  • Name the costs: routing in every query path, per-shard migrations, backups and monitoring, rebalancing tooling — which is why a managed option (Citus, Vitess or a distributed SQL database) is worth evaluating before building it yourself.
Diagnose it

A sensor platform range-partitions its readings on the compound key (timestamp, sensor_id). Writes are slow and one node is at 100% CPU while the rest idle. What's wrong and how do you fix it?

Answer

With timestamp as the leading key, all current readings from every sensor fall into the same "now" range, so every write goes to whichever partition holds the end of the key space — a hot range. Range splits don't help, because the new end of the range is always hot. Fix: lead with a key that spreads writes, (sensor_id, timestamp) in that order (or a hashed bucket of sensor ID first), so concurrent writes from different sensors land in different ranges while each sensor's readings stay sorted by time for efficient per-sensor range queries. Queries across all sensors for a time window become scatter-gather, so serve those from a time-partitioned analytics store or pre-aggregated rollups.
