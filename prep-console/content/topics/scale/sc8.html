A startup building an online marketplace puts everything in one PostgreSQL database: users, listings, orders, payments, chat messages between buyers and sellers, product photos stored as binary columns, a search box implemented with LIKE '%term%', and a sales dashboard that runs big aggregate queries every few minutes. It works at launch. A year later, several things hurt at once. Searching for "wireles hedphones" finds nothing, because LIKE has no idea about typos or relevance, and each search scans millions of rows. The dashboard queries make the whole site slow every time they run. The database has grown to terabytes, most of it photos, so backups take all night. And the chat feature writes so many messages that it competes with checkout for the same machine.

Each problem is a workload that one kind of database handles badly and another handles well. Search wants an inverted index built for relevance ranking. The dashboard wants a columnar store that can scan billions of rows in seconds. Photos want object storage that costs a fraction as much and never touches the database. Chat wants a store that partitions by conversation and absorbs huge write volumes. Checkout wants exactly what PostgreSQL already gives it: transactions and constraints.

That's the lesson of this topic: different data stores are built on different data layouts, and each layout makes some access patterns fast and others slow. There's no best database, only a best fit for a given set of queries. The opposite mistake is just as real, though: a team that adds five fashionable databases on day one pays for five sets of backups, upgrades, on-call rotations and consistency problems, often for workloads one good database could have handled.

This lesson gives you a way to choose. You'll learn to describe a workload by its access patterns, then walk through each family of stores — relational, key-value, document, wide-column, graph, time-series, search, vector, columnar analytics and object storage — seeing why each is fast at what it does by looking at how it lays out data. You'll see the OLTP/OLAP split, what distributed SQL offers, how to keep several stores consistent without dual-write bugs, and a full storage architecture for a real product.

The analogy: a kitchen's storage

A restaurant kitchen doesn't keep everything in one cupboard. The walk-in fridge holds perishable ingredients organised by type, so the chef can find anything and check stock precisely — that's the carefully organised, rule-enforcing relational database. A rack of labelled bins by the stove holds the things grabbed hundreds of times an hour — salt, oil, chopped onions — where speed matters more than organisation: the key-value store or cache. A binder of recipes, each page self-contained, is the document store. The long-term records of every delivery and sale sit in filing cabinets by date, for the accountant's monthly analysis — the analytics warehouse. Bulky things — spare pans, crates — go in a cheap storage unit down the road: object storage. And the index at the back of the recipe binder, listing every page that mentions "garlic", is the search index.

Each storage place is organised for how it's used. Asking the accountant's filing cabinets "how much salt do we have right now?" is slow; asking the salt bin "what did we spend on produce last quarter?" is impossible. The analogy breaks in one important way: in a kitchen, putting the same onion in two places is harmless. In software, the same fact stored in two stores can disagree, and keeping copies consistent is one of the main costs of using several stores.

Start from access patterns

An access pattern is a specific way the application reads or writes data, with its frequency and latency needs. Before choosing any store, write them down. For a marketplace:

  • "Place an order: decrement stock, create order and payment records atomically" — thousands per minute, must be correct.
  • "Show a listing page by ID" — tens of thousands per second, must be fast.
  • "Search listings by words with typos, filtered by price and category, ranked by relevance" — thousands per second.
  • "Latest 50 messages in a conversation" — very frequent, huge total volume of writes.
  • "Revenue by category by day for three years" — a few times an hour, can take seconds.
  • "Store and serve listing photos" — petabytes over time.

For each, ask five questions. What's the query shape — lookup by key, range, full-text, aggregation, traversal, similarity? What consistency does it need — must it see the latest write, must it be transactional? What's the read-to-write ratio and volume? How big is the data and how fast does it grow? Is the query known in advance, or will people ask new questions (ad-hoc queries)? The answers point to a store almost mechanically, as you'll see.

1. Relational databases: the default, and why

A relational database stores data in tables of rows with a declared schema, and lets you query them with SQL: filter, join, group and sort any way you like. Its storage is a row store with B-tree indexes (sc4), its concurrency control provides transactions (sc5), and its schema enforces types and constraints on every write (schema-on-write).

What makes it the right default for most business data is the combination. Transactions let you change several rows atomically — the order, the stock level and the payment together. Constraints — unique, foreign keys, checks — protect invariants no matter which code path writes. Joins and ad-hoc queries let you answer questions nobody planned for when designing the schema, which in a growing product happens every week. Normalisation — storing each fact once and referencing it — means updates happen in one place.

Relational databases also scale further than many people assume. One well-tuned server with replicas and a cache carries a large share of successful products (sc1). Modern PostgreSQL covers many "specialised" needs too: JSONB columns store and index flexible documents, built-in full-text search handles simple search, the pgvector extension does vector similarity, and partitioning handles time-based retention. When a single node isn't enough, sharding tools (Vitess, Citus) and distributed SQL (section 10) extend it.

Where relational databases struggle: write volumes beyond one machine without sharding; data shaped very differently per record; relevance-ranked full-text search at scale; analytical scans over billions of rows; and huge binary objects. Those are exactly the jobs the other families exist for.

Engine internals can matter too. In 2016 Uber publicly explained moving from PostgreSQL to MySQL for a large workload: PostgreSQL's design at the time meant an update to any column created a new row version requiring every index to be updated, its physical replication stream was very verbose for cross-datacentre links, and major-version upgrades required long downtime. The specific points have since been addressed to varying degrees, but the lesson stands: at scale, the storage engine's write path, replication format and upgrade story are part of the choice, not just the query language.

2. Key-value stores: fast because they do almost nothing

A key-value store supports three operations: get a value by key, put a value under a key, delete a key. The value is often opaque to the store. Because the store never has to understand the value or support queries across keys, it can partition data by hashing the key (sc7) and serve lookups in well under a millisecond at almost any scale.

Two very different kinds share the name. In-memory key-value stores such as Redis, Valkey and Memcached keep everything in RAM for microsecond access: caches (sc3), sessions, rate-limit counters, leaderboards (Redis's sorted sets), short-lived locks and queues. Their durability is limited or optional. Durable, partitioned key-value stores such as Amazon DynamoDB persist data across replicas and scale to enormous tables: user profiles by user ID, shopping carts, device state, anything accessed by a known key at high volume.

DynamoDB is worth understanding in a little more depth because it shows the key-value trade-off clearly. Each item has a partition key (hashed to pick the partition) and optionally a sort key (ordering items within a partition), so it's really "key-value with sorted ranges inside a key". A query must name one partition key; anything else is a full-table scan or needs a secondary index maintained asynchronously. Items are limited to 400 KB, and each partition serves at most about 3,000 reads and 1,000 writes per second, so hot keys are throttled no matter the table's total capacity. That's why DynamoDB design starts by listing access patterns and designing keys for them — often storing several entity types in one table with composite keys (single-table design), so that "a customer and their recent orders" is one query. It's extremely scalable and operationally simple for known patterns, and awkward for new questions.

3. Document databases: aggregates with their own shape

A document database such as MongoDB or Couchbase stores self-contained, JSON-like documents. A document can nest arrays and sub-objects, and different documents in the same collection can have different fields. Queries can filter on any field and use secondary indexes, so it's more flexible than key-value.

The sweet spot is the aggregate: data that's read and written as a unit. A product in a catalogue where a laptop has CPU and RAM fields, a shirt has sizes and fabrics, and a book has an author and ISBN, fits naturally as one document per product with category-specific fields, instead of an entity-attribute-value table or dozens of nullable columns. A content page made of nested blocks, or a user profile with optional sections, is similar. Reading one document replaces several joins, and a document can be sharded by its ID easily.

The weaknesses come from relationships. Many-to-many data (students and courses, users and groups) has to be either duplicated inside documents — which then must be updated in many places — or referenced by ID and joined in the application or with slower lookup stages. Multi-document transactions exist (MongoDB has supported them since version 4.0 in 2018) but cost more than in a relational database. And "schemaless" really means schema-on-read: the structure still exists, but every reader must handle every shape a document has ever had. Mature teams validate documents on write, version their shapes and migrate old documents, which narrows the gap with relational databases.

The choice between a document database and PostgreSQL with JSONB is often closer than it looks. If most data is relational with some flexible parts, JSONB inside PostgreSQL gives both. If almost all data is independent aggregates with varying shape and needs easy horizontal scaling, a document database fits better.

4. Wide-column stores: built for writes

Wide-column stores — Apache Cassandra, ScyllaDB, Google Bigtable, HBase — organise data into partitions identified by a partition key, with rows inside each partition sorted by clustering columns (sc7's compound key). They're built on LSM trees (sc4), so writes are sequential appends, and they partition and replicate automatically across many machines, often leaderless (sc6). The result is enormous, linearly scalable write throughput and fast reads of a slice of one partition.

Messaging is the classic fit. With a partition key of (conversation_id, month) and messages sorted by a time-ordered message ID, "the latest 50 messages in this conversation" is a single sequential read from one partition, and billions of messages per day spread across a large cluster. IoT readings (partition by device and day), activity feeds, event logs and time-ordered histories fit the same shape.

The rules are strict, though. Queries must follow the partition key; there are no joins and usually no ad-hoc queries. Data is denormalised into one table per query pattern: if you need messages by conversation and also by user, you write them to two tables. Deletes create tombstones that slow reads until compaction removes them, which makes queue-like workloads a known anti-pattern. And consistency is tunable per request with quorums, which you must understand to use correctly. When the access patterns are known, stable and write-heavy, wide-column stores are hard to beat; when they're not, they're painful.

5. Search engines: inverted indexes and relevance

Searching text with WHERE title LIKE '%headphones%' scans every row (a leading wildcard can't use a B-tree, sc4), understands nothing about word forms or typos, and can't rank results. Search engines such as Elasticsearch, OpenSearch and Solr (all built on the Lucene library) solve this with an inverted index.

When a document is indexed, its text is analysed: split into words, lowercased, and usually reduced to a root form (stemming: "headphones" → "headphone"), with synonyms added if configured. The index then maps each term to the list of documents containing it (a posting list), with positions and frequencies. A query is analysed the same way, and matching becomes looking up a few terms and intersecting their lists — fast regardless of how many documents there are. Typo tolerance comes from fuzzy matching (terms within an edit distance of the query term) or n-gram indexes. Results are ranked by relevance, usually with the BM25 formula, which scores a document higher when query terms appear often in it, are rare across the collection, and appear in shorter fields. Search engines also excel at facets (counts per category, price range, brand for the current results) and filtered queries, using column-oriented structures alongside the inverted index.

Why not use the search engine as the main database? Indexing is near-real-time: Elasticsearch makes new documents searchable after a periodic refresh, one second by default, not instantly. There are no multi-document transactions. Changing how a field is analysed usually means reindexing everything. And its durability and consistency model is designed for a rebuildable index, not a ledger. So the standard architecture keeps the source of truth in a database and feeds the search index from it with change data capture (section 11), and keeps the ability to rebuild the index from scratch. For simpler needs, PostgreSQL's built-in full-text search with GIN indexes, or trigram indexes for fuzzy matching, may be enough without a separate system.

6. Vector search: finding similar meanings

AI applications add another query shape: "find the stored items most similar in meaning to this one". Text, images and other content are turned into embeddings — vectors of hundreds or thousands of numbers produced by a model, where similar meanings give nearby vectors. A vector index finds the nearest vectors to a query vector (lm10 covers embeddings and vector search in depth). Exact search compares against every vector, which is too slow at scale, so indexes are approximate: HNSW builds a layered graph where each vector links to its near neighbours and a search greedily walks the graph toward the query; IVF clusters vectors and only searches the clusters nearest the query. Both trade a little recall (sometimes missing a true nearest neighbour) for large speed-ups.

The storage decision is mostly about scale and integration. For up to millions of vectors, pgvector inside an existing PostgreSQL database is often the best choice: the vectors live in the same transaction as the rows they describe, so a deleted document's embedding disappears with it, and similarity search can be combined with ordinary SQL filters ("only this tenant's documents from this year"). Dedicated vector databases (Pinecone, Milvus, Weaviate, Qdrant) and search engines with vector support earn their place at hundreds of millions of vectors, very high query rates, or when filtered search, hybrid keyword-plus-vector ranking and tiered storage at that scale matter more than keeping everything in one database.

7. Graph and time-series stores

Graph databases (Neo4j, Amazon Neptune) store nodes and relationships as first-class data, with each node pointing directly to its neighbours. A traversal — "accounts connected to this one through shared devices or cards, up to four hops" — follows those pointers, so its cost depends on the part of the graph visited, not the size of the whole dataset. In SQL, the same query is a recursive query or a chain of self-joins, each hop another join over large tables, which becomes slow and awkward as depth grows. Graph databases fit fraud-ring detection, recommendation by connection, network and dependency analysis, and permission inheritance through nested groups. If relationships are only one or two levels deep, a relational database with indexes is simpler; if the graph analysis is periodic rather than per-request, a batch job over a warehouse may do.

Time-series databases (TimescaleDB, InfluxDB, Prometheus for metrics) are built for timestamped measurements arriving continuously: server metrics, sensor readings, prices. The data is almost always appended, rarely updated, queried by time range, and loses value with age. So these stores optimise for fast appends, compress similar consecutive values heavily, partition by time automatically, downsample old data (keep one-second resolution for a week, one-minute for a year), and drop expired partitions cheaply. TimescaleDB is itself a PostgreSQL extension, which again shows how far a relational base can stretch.

8. OLTP versus OLAP, and why columnar stores win analytics

Two workloads look similar ("queries on data") but are opposites. OLTP (online transaction processing) is the operational workload: many small transactions, each touching a few rows by key, with millisecond latency — place an order, update a profile. OLAP (online analytical processing) is the analytical workload: fewer, much larger queries that scan millions or billions of rows but only a few columns, aggregate them, and can take seconds — revenue by country by month for three years.

Row stores (sc4) keep each row's fields together, which is perfect for OLTP: fetching or updating one order touches one page. For OLAP, they're wasteful: summing one column means reading every column of every row. Columnar databases — BigQuery, Snowflake, Amazon Redshift, ClickHouse, DuckDB, and files in the Parquet format — store each column's values together, which gives three compounding advantages. They read only the columns a query uses, often a tenth of the data or less. Each column holds similar values, so it compresses extremely well: dictionary encoding replaces repeated strings like country names with small integer codes, run-length encoding stores "UK × 5,000" instead of 5,000 copies, delta encoding stores differences between sorted numbers. And the engine processes a column in batches of thousands of values using vectorised CPU instructions rather than row by row. Together these commonly make aggregations 10 to 100 times faster than on a row store, on far less hardware.

The price is that single-row inserts and updates are expensive (a new row touches every column's file), and point lookups are slower. Columnar stores are therefore loaded in bulk, in batches or micro-batches, from the operational databases. That's why systems separate the two workloads: OLTP in a relational database, OLAP in a warehouse, connected by batch ETL/ELT pipelines or continuous change data capture (sc18 covers these pipelines). Running heavy analytics directly on the production database, or even on a read replica, causes the slowdowns and replication problems of sc6.

9. Object storage and the lakehouse

Object storage — Amazon S3, Google Cloud Storage, Azure Blob Storage — stores files as objects addressed by a key (like photos/2026/09/abc123.jpg) over HTTP. It's built to be enormous and durable: S3 is designed for 99.999999999% (eleven nines) durability by storing data redundantly across several facilities, and it's far cheaper per gigabyte than database storage. Since 2020, S3 also provides strong read-after-write consistency: once a write succeeds, every read sees it. What it doesn't do is query: you get, put, list and delete objects, and each object is replaced whole.

The standard pattern for user content is: store the bytes in object storage, store the metadata (owner, size, content type, processing status, the object key) in the database, and serve the bytes through a CDN (net12). Uploads usually go directly from the client to object storage using a pre-signed URL — a time-limited, signed permission the server generates — so large files never pass through application servers.

Object storage has also become the foundation of analytics. A data lake stores raw and processed data as files, usually Parquet, in object storage, where many engines (Spark, Trino, DuckDB, warehouses) can read them. Plain files lack transactions and schema management, so table formats such as Apache Iceberg and Delta Lake add a metadata layer that tracks which files make up a table at each version, giving atomic commits, schema evolution and "time travel" to earlier versions. This combination — cheap object storage plus transactional table formats, queried by several engines — is called a lakehouse.

10. Distributed SQL

Sometimes you need relational semantics — SQL, secondary indexes, transactions — beyond what one machine can hold, or across regions. Distributed SQL (sometimes called NewSQL) databases — Google Spanner, CockroachDB, YugabyteDB, TiDB — split tables into ranges by primary key, replicate each range with a consensus protocol (sc9) across machines or zones, move and split ranges automatically, and run distributed transactions across them. To the application, it looks like one large SQL database that survives machine and zone failures without manual failover.

The costs are physical. Every write must be acknowledged by a majority of a range's replicas, so write latency is a few milliseconds within a region and tens to hundreds across regions. Transactions touching many ranges pay extra coordination. Primary keys still need designing to avoid hot ranges (sc7's deep section). And operational or licensing costs can be higher than a single PostgreSQL server. Distributed SQL is a strong choice when a relational workload truly outgrows one node, needs multi-region writes with strong consistency, or when the team would rather pay those costs than build and operate sharding themselves.

11. Using several stores without them drifting apart

Most real systems end up with two to four stores — typically a relational database, a cache, a search index and a warehouse, plus object storage. This is polyglot persistence, and its hidden cost is consistency: the same fact now lives in several places, and they must agree well enough.

The tempting approach is the dual write: when a product changes, the application writes to the database, then to the search index, then invalidates the cache. It works in testing and fails in production, because any step can fail after the previous ones succeeded — a timeout, a crash, a deploy mid-request — and nothing notices. At millions of writes a day, "rarely" means every day, and the stores drift apart permanently. Worse, concurrent updates can reach the two stores in different orders.

The reliable approach has three rules:

One source of truth. For each piece of data, exactly one store is authoritative — almost always the transactional database. Every other store is derived from it and can be thrown away and rebuilt from it.

Propagate changes from the source, not from the application. Either use change data capture — read the database's write-ahead log (sc4, sc6) with a tool like Debezium and publish each committed change as an event, typically into Kafka (sc10) — or use the transactional outbox: in the same transaction as the business change, insert an event row into an outbox table; a separate process publishes outbox rows and marks them sent. Either way, an event exists if and only if the change committed, and events for one key come out in commit order.

Idempotent, replayable consumers. Each derived store's updater applies events so that applying the same event twice has the same result (for example, by upserting the full current state with a version number and ignoring older versions). Then the pipeline can retry freely, and a derived store can be rebuilt by replaying from the start or re-exporting a snapshot.

Derived stores lag the source slightly — typically well under a second for CDC — so the product must tolerate that: a seller who edits a listing sees the change on the listing page (read from the database) immediately, while search results may catch up a moment later. Designing for that lag, rather than pretending it doesn't exist, is part of the choice to add a store.

12. A real-world walk-through: storage for a marketplace

Back to the marketplace from the opening: 2 million daily users, 5 million active listings, 50,000 orders a day, buyer-seller chat, search, analytics. Here's how each access pattern maps to a store, and why.

Orders, payments, users, listings (core records): PostgreSQL. Placing an order must decrement stock, create the order and record the payment atomically, with constraints that prevent overselling and duplicate payments (sc5). Listings and users are relational too, and new business questions appear weekly. Volume — 50,000 orders a day, a few hundred writes per second at peak including listing edits — is well within one primary with replicas; listing pages are served mostly from cache. This is the source of truth for everything except photos and chat.

Listing pages and sessions: Redis. Listing pages get tens of thousands of reads per second with a heavy skew toward popular listings; a cache-aside layer with TTLs and CDC-driven invalidation (sc3) keeps them fast and the database calm. Sessions and rate-limit counters live there too.

Search: OpenSearch, fed by CDC. Buyers need typo-tolerant, relevance-ranked search with filters and facets (category, price range, condition, location) over 5 million listings, thousands of times per second. That's an inverted index's job. Debezium reads PostgreSQL's log and publishes listing changes to Kafka; an indexer consumes them and upserts documents with a version number, so replays are harmless. A new analyser configuration is rolled out by building a new index from a snapshot plus the change stream and switching an alias.

Photos: object storage plus CDN. Sellers upload directly to object storage with pre-signed URLs; a worker creates thumbnails; PostgreSQL stores the object keys. At an average of 5 photos per listing and 2 MB each, 5 million listings are about 50 TB — trivial and cheap in object storage, and absurd in a database.

Chat: start in PostgreSQL, plan for a wide-column store. Chat volume at launch — say 5 million messages a day, about 60 per second on average — fits comfortably in a partitioned PostgreSQL table (partitioned by month for retention, indexed by conversation and time). The team designs the access pattern as "latest N messages in a conversation, then older pages by keyset" so that, if volume grows 50-fold, moving chat to Cassandra or ScyllaDB with a (conversation_id, month) partition key is a contained migration rather than a redesign. Adding a store now would be premature.

Analytics: a columnar warehouse. Revenue, conversion and seller performance over years of data run in BigQuery or Snowflake (or ClickHouse), fed continuously from the same CDC stream plus event data, so dashboards never touch production.

Fraud: batch graph features, not a graph database yet. Detecting rings of accounts sharing devices and cards is a graph problem, but it runs well as a nightly job computing connected components in the warehouse, with results written back for online checks. A graph database becomes worth it only if investigators need interactive multi-hop exploration.

The result is four stores (PostgreSQL, Redis, OpenSearch, a warehouse) plus object storage, each justified by an access pattern with numbers, one source of truth, one propagation mechanism, and explicit decisions about what not to add yet. That last part — resisting stores the workload doesn't need — is as much a signal of seniority as knowing what each store does.

Data layout is destiny

Every family in this lesson is a choice about physical layout, and the layout determines which operations are cheap. Row stores co-locate a record's fields, so point reads and updates are cheap and full-column scans expensive. Column stores invert that. B-trees keep keys sorted for range scans and in-place updates; LSM trees turn writes into sequential appends at the cost of read and compaction work. Inverted indexes co-locate, for each term, the documents containing it. Graph stores co-locate a node with pointers to its neighbours ("index-free adjacency"). Partitioned stores co-locate everything sharing a partition key on one machine. When you evaluate an unfamiliar database, the fastest way to understand it is to ask "what does it put next to what on disk, and how is it partitioned?" — the answers predict its strengths, its weaknesses and the query patterns that will hurt.

The modelling mindset differs: normalise-then-query versus query-then-model

Relational modelling normalises first — each fact in one place, relationships by key — and trusts the query planner, indexes and joins to answer questions later, including ones nobody anticipated. Access-pattern-first stores (DynamoDB, Cassandra, and to a degree document stores) invert the process: enumerate the queries, then shape the data so each is a single-partition read, duplicating data across tables or items as needed. The consequences are concrete. Writes in the second world often update several denormalised copies, which must be kept consistent (often via streams); new query patterns may need a new table and a backfill; and data-model reviews are really query reviews. This is why a senior engineer asks "how stable are the access patterns?" before recommending a NoSQL store: stable, known, high-volume patterns favour it; evolving products favour relational flexibility.

Consistency guarantees vary more than marketing suggests

Stores differ not just in query model but in what they promise about concurrent and failed writes. Relational databases give transactions with configurable isolation (sc5). DynamoDB offers eventually consistent reads by default, strongly consistent reads on request (from the leader of the partition), and transactions across up to 100 items at extra cost. Cassandra's consistency is tunable per query with quorums and has no multi-partition transactions, with lightweight transactions (Paxos-based compare-and-set) for special cases. MongoDB's guarantees depend on read and write concern settings. Search engines are near-real-time. Object storage is strongly consistent for individual objects but has no multi-object transactions. When an architecture spreads one business operation across stores with different guarantees, the weakest link sets the guarantee for the whole operation, which is why critical invariants should live inside one store's transaction.

Cost models shape architecture

Managed stores price by different dimensions, and those prices push designs. DynamoDB on-demand charges per request, so chatty access patterns and large items cost money directly; provisioned capacity rewards steady load. Warehouses like BigQuery charge by data scanned (on-demand) or by reserved compute, which rewards partitioned and clustered tables and punishes SELECT * over years of data. Object storage charges little for storage but for requests and especially for egress, which is why CDNs and same-region processing matter. Relational databases on provisioned instances cost the same whether idle or busy, which favours consolidation. Being able to estimate the monthly cost of a storage design from its access patterns (sc1's estimation applied to money) is a practical senior skill and a frequent interview follow-up.

Licences and ecosystems are part of the decision

Several popular data stores have changed licences in recent years: MongoDB to the Server Side Public License in 2018, Elasticsearch in 2021 (prompting Amazon's OpenSearch fork; Elastic later added an AGPL option in 2024), and Redis in 2024 (prompting the Linux Foundation's Valkey fork; Redis 8 added an AGPL option in 2025). For most users of managed services this changes little day to day, but it affects which cloud offerings exist, what you can embed or redistribute, and the long-term health of forks. Senior engineers include licence, the breadth of the ecosystem (drivers, tooling, hosting options) and the availability of expertise in the decision alongside features and performance.

The case for boring technology

Dan McKinley's widely cited essay "Choose Boring Technology" argues that every team has a small budget of "innovation tokens", and each new, unfamiliar technology spends one: its failure modes are unknown, its operational practices must be learned under pressure, and its integration with everything else is new. Mature technologies have well-known failure modes and a large body of experience. Applied to storage, this argues for extending the database you already operate well until a workload clearly demands something else, and for adding one new store at a time with a clear owner. It's not an argument against specialised stores — search engines and warehouses are themselves boring, mature technology now — but against adding them speculatively.

How storage choices go wrong in production

The wrong tool for a new access pattern. A wide-column or key-value store chosen for its scale meets a new product requirement ("show all orders over £100 this week, across users") that doesn't follow the partition key; the team ends up running full scans or bolting on an index that lags. Symptoms: slow, expensive scan queries and growing read costs. Prevention: review access patterns with product owners before choosing an access-pattern-first store, and keep a relational or analytical copy for ad-hoc needs.

Drift between stores. Search results show items that were deleted hours ago, or prices that no longer match; a cache holds data the database no longer has. The cause is almost always dual writes or a propagation pipeline without retries, ordering or monitoring. Watch pipeline lag, dead-letter queues and periodic reconciliation jobs that compare counts and checksums between source and derived stores.

Analytics hurting production. A dashboard or data-science notebook runs large scans against the primary or a serving replica; latency spikes and replication lag grows. Route analytics to a warehouse or a dedicated replica, and give analysts no credentials to production.

Database as file store. Binary columns balloon the database; backups, restores and replica rebuilds take hours; memory is wasted on blob pages. Migrate blobs to object storage and keep keys.

Operational sprawl. Each store needs backups that are tested, upgrades, security patches, monitoring, capacity planning and people who understand its failure modes at 3 a.m. Teams that adopt many stores quickly often discover that one of them has no working backup or no one who can debug it.

What to monitor per store

For every store: request rate, latency percentiles, error rate, saturation (CPU, memory, disk, connections) and the age of the last successful backup and restore test. Store-specific: replication lag for databases; hit ratio and evictions for caches; indexing lag, refresh time and rejected requests for search clusters; throttled requests and consumed capacity for DynamoDB; compaction backlog and tombstone counts for wide-column stores; bytes scanned and slot usage for warehouses; request and egress costs for object storage. For the pipelines connecting them: end-to-end lag from commit to derived-store visibility, and reconciliation mismatches.

Real-world story: Uber, PostgreSQL and MySQL (2016)

Uber's engineering blog described moving a major workload from PostgreSQL to MySQL (with their own schemaless layer on top), and the reasons are a good example of engine internals driving a choice at scale. In the PostgreSQL version they ran, an update created a new row version at a new location, so every index on the table had to be updated even when no indexed column changed, multiplying writes. Physical replication shipped these low-level changes, making the replication stream very verbose and hard to push across data centres. A replication bug in that version could cause replicas to apply the log incorrectly. Long-running queries on replicas conflicted with log replay. And major-version upgrades required hours of downtime, which kept them stuck on an old version. MySQL's InnoDB, with secondary indexes pointing to primary keys and logical (row-based) replication, suited that workload better. PostgreSQL has since improved in several of these areas (logical replication, HOT updates and faster upgrade paths), and many companies run PostgreSQL at very large scale. The durable lessons are that "which database" at scale is really "which write path, replication format and upgrade story", and that a choice should be revisited as workloads and engines evolve.

A second, very common pattern has no single famous post-mortem: a team uses Elasticsearch as the primary store for something important because it's convenient to query, and later loses data or consistency during a cluster incident or a mapping change that requires reindexing, with no authoritative copy to rebuild from. The fix is the architecture in section 11: keep the source of truth in a database and make the search index rebuildable.

A short experiment showing why search engines use inverted indexes. SQLite ships with Python and includes FTS5, a small full-text search engine, so there's nothing to install.

import random, sqlite3, time
words = "red blue green wireless noise cancelling headphones speaker cable charger laptop stand usb mouse keyboard".split()
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE products (id INTEGER PRIMARY KEY, title TEXT)")
db.execute("CREATE VIRTUAL TABLE products_fts USING fts5(title)")   # an inverted index
rows = [(i, " ".join(random.choices(words, k=6)) + (" titanium" if i % 1000 == 0 else ""))
        for i in range(300_000)]                     # 1 product in 1,000 is "titanium"
db.executemany("INSERT INTO products VALUES (?, ?)", rows)
db.executemany("INSERT INTO products_fts(rowid, title) VALUES (?, ?)", rows)

def timed(sql):
    t0 = time.perf_counter(); n = db.execute(sql).fetchone()[0]
    return n, (time.perf_counter() - t0) * 1000

print("LIKE scan: %d rows in %.1f ms" % timed(
    "SELECT count(*) FROM products WHERE title LIKE '%titanium%'"))
print("FTS index: %d rows in %.1f ms" % timed(
    "SELECT count(*) FROM products_fts WHERE products_fts MATCH 'titanium'"))

Typical output:

LIKE scan: 300 rows in 37.3 ms
FTS index: 300 rows in 0.2 ms

What it shows. The LIKE '%titanium%' query must read and check all 300,000 titles, because a leading wildcard can't use a B-tree index. The FTS table looks up the term "titanium" in its inverted index and gets the list of matching rows directly — about 200 times faster here, and the gap grows with the table. That's the core of every search engine.

Think it through. (1) Search for a common word such as headphones with both methods: why does the advantage shrink when a term matches a large fraction of rows? (2) Try MATCH 'titaniu*' (a prefix query): what can an inverted index do cheaply, and what would true typo tolerance need? (3) If products live in PostgreSQL and search in a separate engine, how would you keep the index up to date without writing to both from application code?

Choose

For each, choose a primary store and justify it in one line: (a) an e-commerce order and payment system; (b) a chat app storing billions of messages, read as "the latest 50 in this conversation"; (c) product search with typo tolerance and filters; (d) a dashboard of revenue by country by day over 3 years of orders; (e) user-uploaded videos; (f) detecting rings of accounts that share devices and cards; (g) semantic search over 2 million support articles for a RAG assistant.

Answer

(a) Relational (PostgreSQL): multi-row transactions, constraints and ad-hoc queries; correctness requirements dominate. (b) Wide-column (Cassandra/ScyllaDB): partition by conversation (plus a time bucket), cluster by a time-ordered message ID — each read is one partition slice, and writes scale horizontally. (c) A search engine (Elasticsearch/OpenSearch) as a secondary index fed by CDC from the product database, which stays the source of truth. (d) A columnar warehouse (BigQuery/Snowflake/ClickHouse) fed from the orders database — aggregations over a few columns of millions of rows. (e) Object storage behind a CDN for the bytes, with metadata (owner, title, encoding status) in the relational database. (f) A graph database — or graph features computed in batch — because multi-hop relationship traversal is the core query. (g) pgvector in the existing PostgreSQL database: two million vectors is comfortably within its range, and keeping embeddings next to the articles makes filtering and consistency simple; move to a dedicated vector store only if scale or query rate demands it.

The meta-point to make: most systems need two or three of these, synchronised by change data capture from one source of truth, rather than trying to make one store do everything — or adding every store at once.
