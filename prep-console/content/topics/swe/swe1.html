Imagine a small online shop's billing code. It started as one class, InvoiceService, written in an afternoon: load an order's lines from the database, add 20% VAT (value-added tax, a sales tax), format a text invoice, email it. It worked, and for six months nobody touched it. Then three requests arrived in the same week. Finance wanted tax to depend on the customer's country. The design team wanted the invoice to show a company logo and a different column order. Operations wanted emails sent through a new provider because the old mail server was being retired.

Three engineers opened the same file. The finance change needed a new database query (to fetch the country), so it touched the loading code. The design change moved a line that also computed the total, and the tax change was merged on top of it; the merged result applied tax twice for one path. The operations change could not be tested without a real mail server, so its author tested it by hand and missed that the new provider needed the recipient address in a different format. Nothing about any single change was hard. The code was hard, because three unrelated reasons to change lived in one place and depended on each other's details.

That is the problem design principles exist to solve. Code is read and changed far more often than it is written, so the cost of a codebase is dominated by the cost of change — and that cost depends less on how clever each line is than on how the code is divided. When a requirement moves, does the edit stay in one small place, or does it ripple through five files owned by three teams? Can you check the change with a fast test, or only by deploying and hoping?

This lesson gives you two measures for that — cohesion and coupling — and then the five SOLID principles, which are five specific, named ways of improving those measures in code built from classes and interfaces. Each is explained from the problem it solves, traced through a worked refactor with real code, and paired with the violation you would see in code review. Then the senior layer: a finer vocabulary for coupling (connascence), how to measure design instead of arguing about it, and when the principles make code worse. The real-world case is NASA's Mars Climate Orbiter, lost in 1999 because two pieces of software disagreed about the unit of one number — the purest example of hidden coupling ever recorded.

The analogy: a kitchen

Think of a restaurant kitchen. Each station has one job: the grill cooks meat, the pastry station makes desserts, the pass assembles plates. Everything a station needs for its job is at that station — that is cohesion. Stations talk to each other through a narrow, agreed channel: tickets with a dish name and table number, and plates handed across the pass. The grill cook does not walk to the pastry station and adjust its oven — that would be coupling to another station's internals. Because of this arrangement, the restaurant can change its dessert menu without retraining the grill cook, and replace the grill cook with a new hire who only needs to understand tickets.

Now picture the opposite: one giant bench where everyone works, sharing one oven whose temperature anyone can change, with dishes passed by shouting whatever units each cook happens to use. Every menu change is a negotiation, and a pastry chef's oven tweak burns the steak.

The analogy breaks in one useful place. In a kitchen, the stations are physically separate, so coupling is visible. In code, a single import or a shared global variable creates a dependency as strong as a shared oven, and nothing in the room shows it. Much of software design is making those dependencies visible and deliberate.

Two measures

First, a word we will use constantly. A module here means any unit of code with an inside and an outside: a function, a class, a file, a package, even a whole service. The principles apply at every size.

Cohesion is how strongly the parts inside a module belong to one purpose. A PasswordHasher class that hashes and verifies passwords, using the same salt and algorithm settings in both methods, is highly cohesive. A Utils class holding date formatting, email sending and tax rules is not: its parts share nothing but a file.

Coupling is how much one module depends on, or knows about, another. If changing how Order stores its items forces edits in Invoice, Shipping and Reports, those modules are tightly coupled to Order's internals. If they only call order.lines() and the storage changes behind that method, they are loosely coupled.

The goal is high cohesion, low coupling. The two are linked: when unrelated things are forced into one module (low cohesion), the rest of the system must depend on that module for many reasons (high coupling). Split it into cohesive pieces, and each outsider depends only on the piece it needs.

SOLID in one line each

SOLID is an acronym collected by Robert C. Martin in the early 2000s for five principles of object-oriented design. Each is a specific way to raise cohesion or lower coupling:

  • S — Single Responsibility: a module should have one reason to change (one group of people whose requests drive it).
  • O — Open/Closed: add new behaviour by adding code, not by editing working code.
  • L — Liskov Substitution: any implementation of a type must work wherever that type is expected.
  • I — Interface Segregation: depend on small interfaces containing only what you use.
  • D — Dependency Inversion: high-level rules should depend on abstractions they own, not on low-level details like databases.

If you remember only one sentence: each principle is a way of making sure that when one thing changes, as little else as possible has to change with it. That is also how to decide when not to apply one — if nothing is likely to change along that axis, the extra structure costs more than it saves.

1. Why change is the thing to optimise

Most studies of software cost, and the lived experience of anyone who has worked on a codebase older than a year, agree: the majority of effort goes into modifying existing code, not writing new code. Every modification has three costs. You have to find the places that need to change, understand them well enough to change them safely, and verify that nothing else broke. All three grow with the number of places a change touches and with how much each place depends on others.

So the useful question about any design is not "is this elegant?" but "when the most likely requirement changes arrive, how many places do they touch, and can I check each one in isolation?" David Parnas put this at the centre of modular design in a 1972 paper: split a system into modules so that each module hides one design decision likely to change — a file format, an algorithm, a vendor — behind an interface. Everything in this lesson descends from that idea, which Parnas called information hiding.

2. Cohesion, level by level

Cohesion is not a yes/no property. The classic scale, from worst to best, describes why the parts of a module are together:

KindParts are together because…Example
Coincidentalno reason at allutils.py with dates, emails and tax
Logicalthey are the same kind of thingall "validators" in one file, for unrelated forms
Temporalthey run at the same timestartup() that opens the database, warms cache, sends a metric
Communicationalthey work on the same dataeverything that reads the orders table
Sequentialone's output is the next's inputparse → validate → normalise pipeline
Functionaltogether they do one well-defined jobPasswordHasher: hash and verify

A quick practical test: describe what the module does in one sentence without using "and" or "or". "Hashes and verifies passwords with the configured algorithm" passes — the "and" joins two halves of one job. "Loads orders and computes tax and renders invoices and sends email" fails four times. Another test is in the code: if the methods of a class use disjoint sets of attributes — load() uses only self.db, send() uses only self.smtp — the class is really several classes sharing a name. The lab turns that observation into a number.

3. Coupling, level by level

A dependency exists when module A needs module B to compile, import, run or be correct; we draw it as an arrow from A to B. Dependencies are unavoidable — code that depends on nothing does nothing. Coupling is about how many dependencies there are, how strong each is, and how visible. The classic scale, from worst to best:

KindA knows about B…Example
ContentB's internalsorder._items.append(x) from outside Order
Commonshared global stateboth read and write config.CURRENT_USER
Controla flag that steers B's logicrender(data, mode=3)
Stampa whole record, uses one fieldpassing user when only user.email is needed
Dataonly the values it needssend(to="a@b.com", body=text)

Two further measures come from counting arrows. Fan-out (efferent coupling) is how many modules this one depends on: high fan-out means it breaks when any of many things changes. Fan-in (afferent coupling) is how many modules depend on this one: high fan-in means a change here ripples widely, so it had better be stable. A module with high fan-in and high fan-out is the dangerous one — it is both fragile and load-bearing.

The most dangerous coupling is the kind nothing checks. If SM_FORCES writes a number to a file and another program reads it, there is no import between them and no type in common, yet both must agree on what the number means — its unit, its sign, its reference frame. We will come back to this in the production section, because it destroyed a spacecraft.

4. Single Responsibility: one actor per module

The Single Responsibility Principle (SRP) is usually quoted as "a class should have one reason to change". Martin later clarified what "reason" means: a reason to change is a person or group — an actor — whose requests drive edits. Finance owns tax rules. The design team owns how invoices look. Operations owns how mail is delivered. If one class answers to all three, then (a) their changes collide in the same file, (b) a change for one can break behaviour another relies on, and (c) you cannot test one concern without setting up the others.

Here is the class from the opening story, simplified:

import smtplib, sqlite3

class InvoiceService:
    def __init__(self):
        self.db = sqlite3.connect("shop.db")          # operations: where data lives
        self.smtp = smtplib.SMTP("mail.local")        # operations: how mail is sent
        self.vat = 0.20                               # finance: tax rule

    def send_invoice(self, order_id, to):
        rows = self.db.execute(
            "SELECT name, qty, price FROM lines WHERE order_id=?", (order_id,)).fetchall()
        total = sum(q * p for _, q, p in rows) * (1 + self.vat)       # finance
        body = "\n".join(f"{n} x{q} {p}" for n, q, p in rows)          # design
        body += f"\nTOTAL {total:.2f}"
        self.smtp.sendmail("shop@example.com", to, body)               # operations
        return total

Count the actors by asking "who would ask me to change this line?" — three different answers. Now the refactor, one small step at a time, each step keeping behaviour identical. (Keeping behaviour identical while changing structure is what refactoring means; the full technique gets its own topic in swe11.)

Step 0 — pin the behaviour. Before moving anything, write one test that calls send_invoice with a known order and checks the returned total and the email body. Right now this test needs a real SQLite file and a mail server stub, which is itself a symptom — but it is our safety net.

Step 1 — extract the finance rule. Move the tax calculation into its own class. Use Decimal, not float, for money (floats cannot represent 0.10 exactly, so sums drift by fractions of a cent):

from dataclasses import dataclass
from decimal import Decimal

@dataclass(frozen=True)
class Line:
    name: str
    qty: int
    unit_price: Decimal

class TaxPolicy:
    def __init__(self, rate: Decimal):
        self.rate = rate
    def total(self, lines: list[Line]) -> Decimal:
        net = sum((l.qty * l.unit_price for l in lines), Decimal("0"))
        return (net * (1 + self.rate)).quantize(Decimal("0.01"))

InvoiceService now calls self.tax.total(lines). Finance's next change — rate by country — happens entirely inside TaxPolicy, and it can be unit-tested with three Line objects and no database.

Step 2 — extract the design concern. A TextInvoice class with one method, render(lines, total) -> str. The design team's column reorder now edits only this class. It cannot accidentally touch the total, because it receives the total as an input rather than computing it.

Step 3 — extract the operations concerns. A class that knows how to fetch lines for an order, and a class that knows how to deliver a message (today over SMTP, the standard protocol for sending email). This is where the next principle, Dependency Inversion, will change the shape of the design — hold that thought for section 8.

Step 4 — what remains. InvoiceService is now an orchestrator: fetch lines, compute total, render, send. Its only reason to change is if the workflow itself changes (say, "also archive a copy"). Each actor's code lives in one class.

5. Open/Closed: add variants as new code

The Open/Closed Principle (OCP), coined by Bertrand Meyer in 1988 and reinterpreted by Martin, says a module should be open for extension (you can add behaviour) but closed for modification (you don't edit its tested code to do so). The violation is easy to spot: a branch on a type code that grows every quarter.

def shipping_cost(carrier: str, weight_kg: float) -> float:
    if carrier == "dhl":
        return 5.0 + 1.2 * weight_kg
    elif carrier == "ups":
        return 4.0 + 1.5 * weight_kg
    elif carrier == "local":
        return 3.0 if weight_kg < 2 else 6.0
    raise ValueError(carrier)

Every new carrier edits this function, re-risks the existing branches, and — if the same if carrier == chain also exists in the label printer and the tracking-URL builder, which it usually does — must be found and edited in three places. The OCP version gives each variant its own class behind one interface and selects it from a table. This shape is called the Strategy pattern (swe3 covers patterns properly):

from typing import Protocol

class Carrier(Protocol):
    def cost(self, weight_kg: float) -> float: ...
    def tracking_url(self, code: str) -> str: ...

class Dhl:
    def cost(self, weight_kg): return 5.0 + 1.2 * weight_kg
    def tracking_url(self, code): return f"https://dhl.example/track/{code}"

class LocalCourier:
    def cost(self, weight_kg): return 3.0 if weight_kg < 2 else 6.0
    def tracking_url(self, code): return f"https://local.example/{code}"

CARRIERS: dict[str, Carrier] = {"dhl": Dhl(), "local": LocalCourier()}

def shipping_cost(carrier: str, weight_kg: float) -> float:
    return CARRIERS[carrier].cost(weight_kg)

A new carrier is now a new class plus one line in the table. Nothing that already works is edited, and every per-carrier fact lives in one cohesive class instead of being spread across three if chains. That second benefit — grouping everything about one variant together — is often worth more than the first.

The cost is real, too: a reader must now follow an indirection to find the logic for DHL, and if there were only ever two carriers the table would be pure overhead. OCP pays off when variants keep arriving. With one variant, write the simple function; when the second or third arrives, refactor. This is the rule of three, and its companion is YAGNI ("you aren't gonna need it"): don't build extension points for variations nobody has asked for, because you will usually guess the wrong axis.

6. Liskov Substitution: honour the contract

To state this principle we need three words. A function's precondition is what must be true before you call it ("amount is positive"). Its postcondition is what it guarantees afterwards ("the returned list is sorted"). An invariant is something always true of an object between calls ("balance is never negative"). Together these form the type's contract — what callers are entitled to rely on, whether or not anyone wrote it down.

The Liskov Substitution Principle (LSP), from Barbara Liskov's 1987 keynote and a 1994 paper with Jeannette Wing, says: if code works with a type T, it must keep working when handed any subtype or implementation of T. Concretely, an implementation may not strengthen preconditions (demand more of callers), may not weaken postconditions (promise less), and must preserve the type's invariants.

The textbook trace is a Square that inherits from Rectangle — mathematically a square is a rectangle, so it feels right:

class Rectangle:
    def __init__(self, w, h): self._w, self._h = w, h
    def set_width(self, w): self._w = w
    def set_height(self, h): self._h = h
    def area(self): return self._w * self._h

class Square(Rectangle):
    def __init__(self, s): super().__init__(s, s)
    def set_width(self, w): self._w = self._h = w     # keep sides equal
    def set_height(self, h): self._w = self._h = h

def stretch(r: Rectangle) -> int:
    r.set_width(5)
    r.set_height(4)
    return r.area()

stretch(Rectangle(1, 1))   # 20
stretch(Square(1))         # 16  ← caller's assumption broken

Trace it line by line for the square. set_width(5) sets both sides to 5. set_height(4) sets both sides to 4. Area is 16. The caller relied on an unwritten postcondition of Rectangle.set_height — "width is unchanged" — and Square weakened it. No type checker complains, both classes are individually correct, and the bug appears only when a Square reaches code written for rectangles. The lesson is that "is-a" in the real world does not imply "is substitutable for" in code; substitutability is about behaviour under the operations the type offers. The fix is not a cleverer Square but a different hierarchy — for example an immutable Shape with area(), where neither class offers setters that the other can't honour.

Violations you will actually see in code review:

  • A subclass method that raises NotImplementedError for an inherited operation (ReadOnlyRepository.save). Callers typed against the parent crash at run time.
  • An override that rejects inputs the parent accepted — the parent handled empty lists, the override raises on them (strengthened precondition).
  • An implementation that returns something looser than promised — a cache that may return stale results where the interface said "current value" (weakened postcondition).
  • In AI systems: a large language model (LLM) provider adapter behind a shared ChatModel interface that silently ignores temperature, or that counts "tokens" in a different tokenizer so budgets computed upstream are wrong.

LSP matters because it is what makes the other principles safe. OCP and DIP both work by letting callers depend on an abstraction and receive any implementation; if implementations do not honour the contract, that flexibility becomes a source of bugs.

7. Interface Segregation: small interfaces for each client

The Interface Segregation Principle (ISP) says clients should not be forced to depend on methods they do not use. Imagine a Storage interface with twenty methods — reads, writes, admin operations, bulk exports. A monthly-report generator that only needs orders_between(start, end) nonetheless depends on all twenty. Three costs follow. Its test fake must implement or stub all twenty methods. A change to an admin method's signature forces the report module to be re-checked and possibly redeployed. And a reader cannot tell from the signature what the report actually uses.

In Python the fix is cheap, because a typing.Protocol describes an interface structurally — any object with the right methods fits, with no inheritance needed (this is why py10 matters here):

class OrdersByDate(Protocol):
    def orders_between(self, start: date, end: date) -> list[Order]: ...

def monthly_report(orders: OrdersByDate, month: date) -> Report: ...

The big PostgresStorage class still satisfies OrdersByDate — it has that method — so production code passes it in unchanged. The test passes a five-line fake. The report's real dependency is now visible in its signature. ISP is really SRP applied to interfaces: one client role per interface.

8. Dependency Inversion: point the arrows at policy

Go back to step 3 of the SRP refactor. We extracted data loading and email sending. If InvoiceService simply imports and constructs SqliteLineSource and SmtpNotifier, then our high-level business workflow still depends on low-level details. Change databases and the workflow's module must change; test the workflow and you need a database.

The Dependency Inversion Principle (DIP) says: high-level modules should not depend on low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions. "High-level" means the code that encodes what the business wants (the invoice workflow, the tax rule); "low-level" means mechanisms that could be swapped (SQLite, SMTP, a specific model provider). The trick is who owns the abstraction. The workflow declares what it needs, in its own terms:

class LineSource(Protocol):
    def lines_for(self, order_id: int) -> list[Line]: ...

class Notifier(Protocol):
    def send(self, to: str, body: str) -> None: ...

class InvoiceService:
    def __init__(self, source: LineSource, tax: TaxPolicy,
                 renderer: TextInvoice, notifier: Notifier):
        self.source, self.tax = source, tax
        self.renderer, self.notifier = renderer, notifier

    def send_invoice(self, order_id: int, to: str) -> Decimal:
        lines = self.source.lines_for(order_id)
        total = self.tax.total(lines)
        self.notifier.send(to, self.renderer.render(lines, total))
        return total

The SQLite and SMTP classes live in an infrastructure module that imports Line and implements LineSource and Notifier. The source-code arrow that used to run from workflow to database now runs from database adapter to the workflow's interface — that reversal is the "inversion".

Now the test that was painful in step 0 becomes trivial. The fakes are plain classes:

class FakeSource:
    def lines_for(self, order_id):
        return [Line("keyboard", 2, Decimal("45.00")), Line("mouse", 1, Decimal("20.00"))]

class RecordingNotifier:
    def __init__(self): self.sent = []
    def send(self, to, body): self.sent.append((to, body))

n = RecordingNotifier()
svc = InvoiceService(FakeSource(), TaxPolicy(Decimal("0.20")), TextInvoice(), n)
assert svc.send_invoice(42, "ana@example.com") == Decimal("132.00")   # (90 + 20) × 1.2
assert "TOTAL" in n.sent[0][1]

This test runs in microseconds, needs no network, and fails only if the workflow or tax rule is wrong. Supplying collaborators through the constructor like this is dependency injection; the next topic (swe2) covers it in depth, including where the real objects get built. Note that the two ideas are separate: DIP is about which way the arrows point, injection is about how the objects get wired.

9. The five together, and where to stop

Look at what the refactor achieved in terms of the two measures. Cohesion went up: each class holds one actor's concern, and its methods use the same few attributes. Coupling went down and became explicit: the workflow depends on three small interfaces it owns plus one value class, and every concrete dependency is visible in a constructor signature. The principles reinforced each other — SRP found the seams, DIP pointed the arrows the right way, ISP kept the interfaces narrow, OCP let a new notifier (SMS, Slack) arrive as a new class, and LSP is the rule every such new class must obey.

The cost: one class became six small ones, and a reader following send_invoice now jumps between files. For a shop where tax, layout and delivery really do change independently, the trade is clearly worth it. For a one-off migration script, it is not. The honest senior position is that the principles are tools for managing anticipated or evidenced change. Apply them where the version-control history shows collisions, where tests are painful, or where the product roadmap names the next variant. Elsewhere, simple, direct code that is easy to delete beats flexible code that is hard to read.

Connascence: a sharper vocabulary for coupling

"Coupling" is too coarse to act on — it tells you two modules are entangled but not how. Meilir Page-Jones's connascence (from Latin, "born together") names what must stay in agreement. Two pieces of code are connascent if changing one requires changing the other to keep the system correct. The static forms, weakest to strongest: name (both use the method name lines_for), type (both agree the argument is an int), meaning (both agree that -1 means "not found", or that a float is in newtons), position (both agree argument two is the height), and algorithm (both hash passwords the same way). Dynamic forms, visible only at run time, include execution order (call open() before read()), timing, value (two replicas must hold the same number) and identity (both must refer to the same object).

Three rules make it practical. First, convert strong forms to weak ones: replace a magic value with a named constant or enum (meaning → name), replace positional arguments with keyword arguments or a dataclass (position → name), replace a bare float with a type that carries its unit (meaning → type, which a checker enforces). Second, locality: strong connascence is acceptable inside a function or class but dangerous across module, team or service boundaries, where nobody sees both sides at once. Third, degree: connascence among two call sites is manageable; among two hundred it is a migration project.

Measuring design instead of debating it

Design discussions stall on taste. Numbers help. Change coupling (also called logical or temporal coupling) mines version-control history for files committed together: if billing.py and email_templates.py change in the same commit 80% of the time, they are coupled regardless of what the import graph says, and either belong together or have a hidden contract. Tools like CodeScene compute this, but a twenty-line script over git log --name-only gets you most of the value. The import graph gives fan-in and fan-out; a module with both high is a hotspot. Dependency rules enforced in CI — Python's import-linter, Java's ArchUnit — turn "the domain layer must not import the database layer" from a wiki page into a failing build. And LCOM-style metrics, which count method pairs sharing no attributes (the lab computes one), flag classes that are several classes in disguise. None of these metrics is a target — optimising LCOM mechanically produces nonsense — but each is a good prompt for a conversation.

The Stable Dependencies and Stable Abstractions principles

Martin extended SOLID to the level of packages. A module is stable if it is hard to change — because many others depend on it (high fan-in) and it depends on little (low fan-out). The Stable Dependencies Principle says depend in the direction of stability: volatile code (UI, integrations, experiments) may depend on stable code (domain model, core rules), never the other way round, or every volatile change ripples into the core. The Stable Abstractions Principle adds that stable modules should be abstract (mostly interfaces and pure rules), so being hard to change doesn't mean being hard to extend. DIP is the move that reconciles the two: when stable core code needs a volatile detail, it declares an abstraction and the detail depends on that. In a machine-learning platform this is why the feature definitions and model interface should be the stable centre and specific training frameworks, vector databases and model vendors the volatile edge.

LSP beyond classes: contracts at every boundary

The Liskov-Wing paper frames subtyping purely in terms of behaviour, which means it applies to anything with multiple implementations behind one contract: several storage backends behind one repository interface, several deployments of one HTTP API, several LLM providers behind one client wrapper, a new model version replacing an old one behind the same endpoint. Their paper adds a history constraint beyond pre- and postconditions: a subtype must not allow state changes the supertype forbids — a mutable subtype of an immutable type breaks callers who cached values. The practical tool is the contract test: a single test suite, parameterised over every implementation, that pins the behaviours callers rely on. When a new adapter joins, it must pass the suite. For model upgrades, the equivalent is an evaluation set that checks the output properties downstream code depends on (valid JSON, required fields, refusal behaviour), run against the new version before it takes traffic.

Abstractions have a cost, and the wrong abstraction costs most

Every interface is a bet that variation will occur along that axis. Sandi Metz's widely quoted observation is that "duplication is far cheaper than the wrong abstraction": once an abstraction exists, later developers bend it with parameters and flags to fit cases it was never designed for, until it is harder to change than the duplicated code would have been. The remedy is to inline the abstraction back into its callers, then re-extract along the axis the real cases reveal. Practical heuristics: an interface with one implementation and no test double is suspect; a boolean parameter that selects between two behaviours (control coupling) usually means two functions; an abstraction named after its mechanism (AbstractManagerFactory) rather than its role is usually speculative.

SOLID outside object orientation

None of the principles needs classes. In functional code, SRP is small pure functions; OCP is passing functions as arguments (a sorting key is a strategy); ISP is functions taking exactly the data they need; DIP is higher-order functions and dependency parameters. At service scale, SRP becomes "one team, one service, one reason to deploy", ISP becomes narrow, client-specific API endpoints, and DIP becomes the business service owning an event schema that integrations consume, rather than calling each integration directly. The vocabulary transfers because the underlying goal — keep each change local — does.

How poor cohesion and coupling show up in real teams

Design problems rarely announce themselves as "an SRP violation". They show up as symptoms you can observe. Shotgun surgery: a single business change needs small edits in many files — the "add a carrier" change that touches the cost function, the label printer and the tracking builder. Divergent change, the mirror image: one file edited for many unrelated reasons, visible as a long git log of unrelated ticket numbers and frequent merge conflicts between teams. Slow, brittle tests: unit tests that need a database, network or clock because the logic under test constructs its own dependencies. Fear of deletion: nobody removes an old code path because nobody knows what depends on it. Each has a matching measurement — files per change, commit-author diversity per file, test runtime and flakiness, fan-in of the path in question — and tracking one of them before and after a refactor is the most persuasive way to justify design work.

Case: the Mars Climate Orbiter and connascence of meaning

NASA's Mars Climate Orbiter launched on 11 December 1998 and was lost on 23 September 1999 during its orbit-insertion burn. The Mishap Investigation Board's Phase I report is short, public and worth reading as a software design document. During the nine-month cruise, the spacecraft periodically fired small thrusters to unload momentum from its reaction wheels. Ground software called SM_FORCES computed the impulse of each firing and wrote it to a file; the navigation team's software read that file to model how each firing nudged the trajectory. A Software Interface Specification required the impulse in newton-seconds. SM_FORCES wrote pound-force-seconds. The navigation software, which had no way to tell, therefore underestimated every firing's effect by a factor of 4.45.

Several design facts made the error both invisible and cumulative. The two programs were written by different organisations (Lockheed Martin Astronautics on the spacecraft operations side, NASA's Jet Propulsion Laboratory, JPL, for navigation), so nobody saw both sides of the interface. The only coupling between them was a data file — no shared type, no import, no compiler to object — so the contract lived only in a document the report says "was not followed". The spacecraft's asymmetric solar array caused these momentum-unloading firings 10–14 times more often than the navigators expected, multiplying the per-firing error. And the operations navigation team had not taken part in testing the ground software. Navigators saw discrepancies from April 1999 and reported them only informally. On arrival, the estimated closest approach was 150–170 km, the minimum survivable altitude was 80 km, and post-loss reconstruction put the actual periapsis at about 57 km.

In this lesson's terms, SM_FORCES and the navigation software had connascence of meaning — they had to agree on what a number meant — across the widest possible boundary: two organisations and a file. The fixes the board recommended map directly onto design practice: audit every data transfer against its specification, test the interface end to end, and make the contract checkable. In code, that means types that carry units (Python libraries such as pint, or simply field names like impulse_newton_seconds), schemas validated at the boundary, and contract tests that run the producer's real output through the consumer's parser.

The same failure in ML and LLM systems

Machine-learning pipelines are full of connascence of meaning across file and service boundaries, and it fails the same way — silently. A feature computed in dollars at training time and in cents at serving time; images normalised to [0, 1] in training and [0, 255] in production; a tokenizer version mismatch between the service that counts prompt tokens and the model that enforces the limit; a model output parser that assumes a JSON field the new prompt version renamed. None of these raises an error; each shifts outputs. The design responses are the same as for the orbiter: a single shared definition (a feature store or shared preprocessing module both sides import), schemas validated at every boundary (Pydantic models for LLM outputs), and contract tests that pass real producer output through the real consumer.

Tools and knobs

For Python codebases: import-linter contracts in CI to forbid imports that point the wrong way ("domain may not import infrastructure"); mypy or pyright so Protocol-based interfaces are actually checked; a change-coupling report from git history before any large refactor, to find what really changes together; and a rule of thumb in review that every new interface either has two implementations or a test double that justifies it. When a service calls model providers, keep one adapter per provider behind a small interface the application owns, run a shared contract test suite against each adapter, and treat a model or prompt version change like a new implementation of the interface — it must pass the contract before it takes traffic.

def lcom(cls: ast.ClassDef) -> tuple[int, int]:
    """LCOM (Chidamber-Kemerer): method pairs sharing no self.attribute minus pairs sharing one (floor 0)."""
    uses = {}
    for m in cls.body:
        if isinstance(m, ast.FunctionDef) and m.name != "__init__":
            uses[m.name] = {n.attr for n in ast.walk(m)
                            if isinstance(n, ast.Attribute) and isinstance(n.value, ast.Name) and n.value.id == "self"}
    p = q = 0
    for a, b in combinations(uses.values(), 2):
        if a & b: q += 1
        else: p += 1
    return max(p - q, 0), len(uses)

def fan_out(tree: ast.Module) -> set[str]:
    return {a.name for n in ast.walk(tree) if isinstance(n, ast.Import) for a in n.names}

for label, src in (("BEFORE", BEFORE), ("AFTER", AFTER)):
    tree = ast.parse(src)
    print(f"== {label}: imports (concrete dependencies) = {sorted(fan_out(tree)) or 'none'}")
    for cls in (n for n in tree.body if isinstance(n, ast.ClassDef)):
        score, methods = lcom(cls)
        print(f"   {cls.name:15} methods={methods}  LCOM={score}")
