Every company has one: the module nobody wants to touch. It's 4,000 lines, written by people who left years ago, with a function called calc2 and comments like # don't change this, breaks month-end. It has no tests. Every change to it takes three times the estimate, and about one in four causes an incident. So people route around it — copying logic into new places, adding special cases at the edges, leaving flags and dead branches behind — which makes it worse. Eventually someone proposes rewriting it from scratch, and the rewrite is still "80% done" a year later while the old module keeps running the business.

This is the everyday reality of software engineering: most work is changing existing code, and much existing code is hard to change. The skills that make it safe are learnable and mechanical. Refactoring improves structure in small steps that provably don't change behaviour. Legacy-code techniques — characterisation tests, seams, sprouting new code beside old — get untested code under control before you change it. Incremental replacement — the strangler fig and branch by abstraction — swaps out whole components without a big-bang rewrite. And thinking about technical debt as a business trade-off, measured in interest paid, tells you where any of this is worth doing.

This lesson covers all four. The case study is Knight Capital, a firm that handled around a tenth of US equity trading and, on 1 August 2012, lost more than $460 million in about 45 minutes. The SEC's order describes the cause in plain terms: code for a feature called Power Peg had been unused since 2003 but left on the servers; a new deployment reused the flag that used to switch it on; one of eight servers didn't receive the new code; and on that server the old code woke up. It's the most expensive lesson on record about dead code, reused flags and unverified deployments. The same pattern, as a 2015 Google paper pointed out, is endemic in machine-learning systems. The lab pins down a legacy pricing function with a 10,000-case characterisation test, refactors it safely, catches a plausible-looking "cleanup" that changes behaviour in 192 cases, and ranks modules by where refactoring pays.

The analogy: renovating a house you live in

You can't move out while renovating, so you work room by room. Before knocking anything down you check which walls are load-bearing and where the pipes run, because the builders who knew are gone. You keep the water and electricity working every day. You don't demolish the house to build a better one on the same spot while living in a tent — that's the rewrite, and it always takes longer than planned. And some shortcuts from the last renovation — a cable run along the outside, a room without proper insulation — cost you a little every month in heating bills and inconvenience. That monthly cost is interest on technical debt: sometimes worth paying off, sometimes cheaper to live with.

The analogy breaks helpfully: in software, you can build a complete safety net before touching anything — tests that tell you instantly if the water stopped running — and you can make changes in steps so small that each is obviously safe. That's what makes renovating software far less risky than renovating a house, when it's done properly.

Four ideas

Refactoring: changing structure without changing behaviour, in small steps that each keep the tests green. It's how design improves continuously, and it's safe only because it's small and verified.

Legacy code: in Michael Feathers's influential definition, simply code without tests. The first job with legacy code is to get it under test without breaking it — which usually means recording what it does today before deciding what it should do.

Incremental replacement: when a component must be replaced, do it gradually behind a stable interface or routing layer, moving one slice at a time, with the ability to go back at every step — never as a big-bang switch after years of parallel development.

Technical debt: the extra cost of future change caused by earlier shortcuts. Ward Cunningham, who coined the metaphor, meant it as a prudent trade: ship with the understanding you have now, learn, and pay back by refactoring. Not all debt is like that, and Martin Fowler's quadrant sorts it by two questions — was it deliberate, and was it prudent?

All four ideas share one principle: small, reversible, verified steps. A refactoring is a sequence of tiny steps with tests run after each. Legacy-code work adds tests before changes. Incremental replacement moves one slice at a time with a way back. Paying debt continuously beats a heroic rewrite. The lesson's case study is what happens when every one of those principles is skipped in the same system on the same morning.

Before starting, it's worth being honest about why teams get into this state, because the causes shape the cures. Deadlines reward adding features over improving the code they sit in. Knowledge leaves with people, so the reasons behind strange code are lost. Tests weren't written early, so every later change is risky, so people make the smallest possible change in the most local place — a special case here, a copied function there — which is exactly how structure decays. None of that is solved by a single clean-up project. It's solved by making improvement part of ordinary work, which is only possible when each improvement is small and safe.

1. Refactoring: small steps, behaviour preserved

Martin Fowler's definition is precise: a refactoring is "a change made to the internal structure of software to make it easier to understand and cheaper to modify without changing its observable behaviour". The discipline is in the steps. Each named refactoring is small and mechanical: rename variable, extract function (turn a fragment into a named function), inline function (the reverse), move function to the class whose data it uses, introduce parameter object (group arguments that travel together into a dataclass), replace conditional with polymorphism (swe3's Strategy), replace magic number with named constant. After each step, run the tests. If they fail, the last step was wrong, and it was tiny, so it's easy to see why — undo it rather than debug. A sequence of twenty such steps can transform a function completely while never leaving it broken for more than a minute.

Three habits make this work in practice. Use automated refactorings where your editor offers them (rename, extract, move): they're faster and don't make typos. Keep refactoring separate from behaviour change, in separate commits and ideally separate pull requests — Kent Beck's advice is "make the change easy (warning: this may be hard), then make the easy change". A reviewer can check a pure refactor for "nothing changed" and a behaviour change for "the right thing changed", but a mix of the two can't be reviewed well (swe6). And refactor where you're working: the best time to improve code is just before changing it, when you have to understand it anyway and the improvement pays off immediately.

Code smells tell you where to start. The classic list includes long functions, long parameter lists, duplicated code, a class that changes for many unrelated reasons (divergent change — swe1's SRP), a change that requires edits in many classes (shotgun surgery), feature envy (a method more interested in another class's data), primitive obsession (bare strings for money and IDs), data clumps (the same three arguments always passed together), and speculative generality (hooks nobody uses). Each maps to named refactorings that remove it.

2. Legacy code: the dilemma and the way out

Michael Feathers, in Working Effectively with Legacy Code, defined legacy code as "code without tests" — whatever its age, it's code you can't change with confidence. He also named its central dilemma: to change code safely you need tests; to add tests you often need to change the code, because it constructs its own database connections, reads the clock, calls global singletons (swe3) or is buried in a 500-line function. The way out is to make the smallest, safest possible changes that let you get tests in, then use those tests to protect bigger changes.

The tool for that is the seam: "a place where you can alter behaviour in your program without editing in that place". An injected dependency is a seam (swe2). A default parameter is a seam: change def charge(order): that calls stripe.charge(...) into def charge(order, gateway=stripe): — production behaviour is identical, but a test can pass a fake. An overridable method is a seam: a test subclass can replace the one method that sends email. In Python, even module attributes can serve as seams in an emergency (patching, swe5), though an explicit parameter is better. The typical first moves on legacy code are exactly these: extract a dependency into a parameter with the old behaviour as default; use an automated extract-function refactoring to pull a testable piece out of a giant function; then write tests around what you exposed.

3. Characterisation tests: pin what it does, not what it should do

Before changing legacy code, you need to know when you've changed its behaviour — including behaviour that's wrong but that other code or customers depend on (Hyrum's law, swe7). A characterisation test records what the code actually does today. The simplest form is a golden master: run the code on many inputs, save the outputs, and after every change compare. The lab does this for a small legacy pricing function with nested conditions, coupon codes and country-specific tax:

golden = [(args, legacy_price(*args)) for args in inputs(10_000)]   # record what it DOES
for name, candidate in (("refactor", price), ("cleanup with slip", price_slip)):
    diffs = [(a, want, candidate(*a)) for a, want in golden if candidate(*a) != want]

The inputs come from a seeded random generator covering quantities, prices, member and guest customers, valid and invalid coupons, and several countries, so the 10,000 cases exercise every branch many times. The careful refactor — named discount rules, a tax table, guard clauses — matches on all 10,000. A second "cleanup" that looks equivalent but writes net >= 100 where the original had t > 100 differs on 192 cases; the first one printed is a member buying 4 items at 25, a total of exactly 100: the original charges 100 (no member discount at exactly 100), the cleanup charges 90. Nobody reviewing the diff would reliably catch that. The golden master catches it instantly.

Two refinements matter. When the characterisation test reveals behaviour that looks like a bug, don't fix it during the refactor — note it, finish the behaviour-preserving work, then fix it as a separate, deliberate change that updates the expected output and tells whoever depends on it. And once the code is understood and refactored, replace the golden master with ordinary, named tests of the rules ("members get 10% off orders over 100"), which document intent rather than just freezing outputs.

4. Sprout and wrap: adding to legacy code without growing it

Sometimes you must add a feature to legacy code before you can afford to get all of it under test. Two techniques keep the new code clean and tested. Sprout method or class: write the new behaviour as a new function or class, developed with full tests, and add one line to the legacy code that calls it. The legacy function gains a single, obvious call instead of thirty tangled lines. Wrap method: when new behaviour must happen before or after an existing function (log, validate, notify), rename the old function, create a new function with the old name that does the new thing and calls the renamed original. The original is untouched, and the new behaviour is tested separately. Both leave the legacy code no worse and every new line tested, which over time shifts the balance.

5. The strangler fig: replacing a system gradually

When a whole system or large component must be replaced, the tempting approach is a rewrite: build the new system in parallel until it matches the old, then switch. It almost always goes badly. The old system encodes years of fixes and edge cases no one remembers, so reaching "parity" takes far longer than planned; meanwhile the old system still needs changes, which the rewrite must chase; and nothing reaches users until the end, when a big-bang switch meets every unknown at once. Joel Spolsky's classic essay used Netscape as the cautionary example: the rewrite that became Netscape 6 meant almost three years with no major release while the market moved on — "the single worst strategic mistake that any software company can make", in his words.

Martin Fowler's strangler fig, named after vines that seed in a tree's branches and grow down around it until they replace it, delivers the replacement incrementally:

  1. Intercept: put a routing layer — a reverse proxy, an API gateway or an in-code façade — in front of the legacy system, initially passing everything through unchanged.
  2. Pick a slice: a capability with a clear boundary (a bounded context from swe10) and real value — invoices, search.
  3. Build and verify: implement the slice anew, with tests; verify it against the old one on real traffic by shadowing (send requests to both, return the old response, compare) or a parallel run for batch jobs.
  4. Route: move that slice's traffic to the new implementation, gradually if possible (swe9's canary), keeping the ability to route back.
  5. Repeat, and when a legacy capability receives no traffic, delete it. Finish by deleting the legacy system.

Data is usually the hard part: the new implementation needs data the old system owns, so each slice typically involves an expand–contract style migration (swe9) or synchronisation between old and new stores until the slice is fully moved. The pattern's big advantage is that value ships after each slice, risk is limited to one slice at a time, and the project can pause or stop at any point with a working system.

6. Branch by abstraction: the same idea inside a codebase

To replace a component inside one codebase — swap an ORM, a logging library, a payment provider, a model provider — without a long-lived branch (swe8), use branch by abstraction: (1) introduce an abstraction (an interface, swe2) over the current implementation and move callers to use it, in small commits; (2) build the new implementation behind the same abstraction, merging to main continuously with it switched off; (3) switch callers over, gradually behind a flag if you can; (4) delete the old implementation, and the abstraction if it no longer earns its keep. Every step merges to main and the system always works. It's the in-process version of the strangler fig, and the hexagonal architecture from swe10 makes it easy, because the ports are already there.

7. Dead code, flags and why deletion is a feature

Deleting code is one of the most valuable refactorings, and the most neglected. Dead code — functions nothing calls, branches whose condition can't be true, flags stuck in one position, experiments that ended — costs every reader time, confuses searches and refactors, and inflates the apparent complexity of the system. Worse, "can't be called" is a claim about today's configuration, not a property of the code. A flag, a configuration value or a partial deployment can make dead code live again, and dead code is by definition untested against the current system. The case study is the extreme example. Practical rules: delete code as soon as it's unused (version control keeps it); give feature flags owners and expiry dates and remove them after rollout (swe9); never reuse a flag, configuration key or message type for a new meaning; and before deleting, prove deadness with runtime evidence (a counter or log on the path, observed over a full business cycle), not just a text search.

8. Technical debt: measuring interest and choosing what to pay

Ward Cunningham introduced the debt metaphor in 1992 to explain refactoring to non-programmers: shipping code before the design fully reflects your understanding is like borrowing money — fine if you pay it back, ruinous if the interest compounds. The interest is the extra effort every future change in that area costs, plus the incidents it causes. The principal is the effort to fix it. Debt is worth repaying when the interest you'll pay over the relevant horizon exceeds the principal.

That framing points straight at how to prioritise. Interest is only paid when code is changed or fails. Complex code that nobody touches costs almost nothing; simple code that changes weekly is fine. The expensive combination is complex code that changes often — a hotspot. Adam Tornhill's approach, which tools like CodeScene automate, multiplies churn (commits touching a file over, say, a year, from git log) by a complexity measure (lines, indentation depth, or cyclomatic complexity):

In the lab's example, billing/pricing.py (41 commits, complexity 15) scores 615 — nearly ten times the next module — while invoice_pdf.py, which is even more complex, scores only 57 because it rarely changes. Add incident data (which modules appear in post-mortems) and lead-time data (how long changes in each area take), and the priority list writes itself.

Making the case. "The code is ugly" persuades nobody outside engineering. Evidence does: lead time for changes in the hotspot versus elsewhere ("pricing changes take three times longer"), incidents traced to it, on-call hours, and — most persuasive — upcoming roadmap items that go through it ("the next three pricing features will each take six weeks; after this refactor, about three"). Then a plan that delivers in stages, each measurable. Paying it. Most debt is best paid continuously: the "boy scout rule" of leaving code cleaner than you found it, and preparatory refactoring before each feature. Some teams reserve a fixed share of capacity for debt. Large debts — an unsupported framework version, a schema that blocks every feature — need dedicated, strangler-style projects with explicit milestones.

9. Debt in ML and LLM systems

In 2015, D. Sculley and colleagues at Google published "Hidden Technical Debt in Machine Learning Systems", arguing that ML systems have all of ordinary software's debt plus kinds of their own. Glue code: a mature system might be at most 5% ML code and at least 95% glue that moves data into and out of general-purpose packages. Pipeline jungles: data preparation that grows organically into scrapes, joins and intermediate files that nobody can test end to end. Dead experimental code paths: experiments implemented as conditional branches in production code, which accumulate and make interactions untestable — the paper cites Knight Capital as the famous example. And entanglement, which they summarised as CACE, "Changing Anything Changes Everything": in a model, changing one input feature's distribution, adding a feature or tweaking a hyperparameter can change how every other feature is used, so improvements can't be isolated. LLM applications have direct descendants: prompt variants forked per customer and never retired, special cases patched into templates, retrieval glue between vector store, reranker and parser, evaluation sets that drift away from real traffic, and experiment flags for models and prompts left in code long after the experiment. The remedies are this lesson's: delete dead paths and flags promptly, keep glue behind clean ports (swe10), version data and prompts, and treat evaluation sets as maintained assets.

Refactoring safety without tests: leaning on tools and types

When there are no tests yet, the safest changes are those whose correctness doesn't depend on tests. Automated refactorings in an IDE (rename symbol, extract method, inline variable) are behaviour-preserving by construction in statically analysable code, which is why Feathers recommends them as the first moves on legacy code. In dynamic languages like Python, automation is less complete — a rename can miss a name built from a string or accessed via getattr — so type hints and a type checker (py10) become part of the safety net: once code is annotated, mypy or pyright will flag call sites a refactoring broke. Approval testing libraries generalise the golden master by storing outputs as reviewable files. And mutation testing (swe5) tells you whether your characterisation tests would actually notice a change, before you rely on them.

Parallel runs and dark launches for replacements

For a replacement whose correctness matters — a new pricing engine, a new ranking model, a rewritten tax calculation — the strongest verification is to run old and new side by side on real inputs. GitHub open-sourced a Ruby library called Scientist for exactly this: the old code path runs as the "control", the new one as the "candidate"; both execute, the control's result is returned, and any mismatch is recorded with its inputs for investigation. Only when mismatches have been explained or fixed does traffic move to the new code. The same idea appears as shadow traffic in deployment (swe9) and as offline replays of logged requests. The key design questions: the candidate must have no side effects (no writes, no emails) or they must be sandboxed; comparison must tolerate legitimate differences (timestamps, ordering); and the extra load must be affordable, often by sampling.

Behavioural code analysis

Version-control history holds information that static analysis can't see. Beyond hotspots, change coupling finds files that change together without any code dependency — a sign of hidden coupling such as duplicated logic or a shared implicit contract (swe1). Knowledge distribution — who has committed to each file — finds code whose only author has left, which is a risk even if the code is clean. Complexity trends show whether a hotspot is getting better or worse over time. These analyses turn debt discussions from opinion into data, and they're cheap: a script over git log --numstat goes a long way.

Large-scale automated changes

Some refactorings must touch thousands of files — renaming a widely used API, migrating a logging library, upgrading a language version. Doing these by hand is error-prone and blocks everyone. Large organisations use codemods: programs that transform source code through its syntax tree (in Python, LibCST or Bowler-style tools; Google's Rosie and ClangMR for C++), applied in batches small enough to review and deploy safely, often generated and submitted automatically per owning team. The pattern is the strangler fig applied to code itself: add the new API alongside the old, migrate callers in automated batches, then delete the old API once no callers remain. LLMs are increasingly used to draft such migrations, which makes the characterisation and review safeguards above more important, not less.

Refactoring in a team: conflicts, ownership and timing

Refactoring is easy alone and harder in a busy codebase. A rename or file move touches lines other people are editing, so a large refactor sitting in a branch for a week will conflict with everyone. The remedies follow from trunk-based development (swe8): make refactors small and merge them quickly; land mechanical changes (renames, moves, formatting) as separate, clearly labelled pull requests that reviewers can approve on sight; announce sweeping mechanical changes in advance and land them at a quiet time, or apply them with a codemod that others can rerun on their branches. Coordinate with the owners of the code (swe6's CODEOWNERS), since refactoring code another team maintains without them is how surprises reach production. And resist refactoring code you aren't otherwise changing and don't understand: the risk is real and the payoff, by the hotspot logic above, is low.

Why systems accumulate debt: incentives and entropy

Lehman's laws of software evolution, from studies of large systems in the 1970s and 80s, observed that a system in use must continually change or become less useful, and that as it changes its complexity increases unless work is done to reduce it. Debt isn't a failure of discipline so much as the default outcome of change without investment. Incentives amplify it: features are visible and rewarded, while the cost of debt is diffuse and delayed. Sustainable teams make the invisible visible — hotspot dashboards, lead-time trends by area, incident tags for "caused or worsened by debt" — and budget for maintenance explicitly, the same way SRE teams budget for reliability with error budgets (sc13). The goal isn't zero debt, which would mean never shipping before the design is perfect, but debt that is chosen, tracked and repaid where it charges the most interest.

How legacy and debt problems show up

The symptoms are consistent. Estimates balloon for anything touching certain modules. Change failure rate (swe9) is concentrated in a few areas. Fear-driven workarounds: logic copied rather than changed, special cases bolted onto edges, "don't touch" comments. Knowledge islands: one person must review every change to a component. Stale flags and dead code that nobody can confidently remove. Stalled rewrites: a replacement project a year in with no traffic. The measurements that make these visible are the ones already mentioned — lead time and change failure rate by area, hotspot rankings, incident tags, flag age — and they're what turn a vague "we have debt" into a prioritised plan.

Case: Knight Capital, 1 August 2012

Knight Capital was one of the largest US equity market makers; according to the SEC, its trading generally represented about 10% of all trading in listed US equities, and its automated order router, SMARS, alone around 1% or more. SMARS received large "parent" orders and sent smaller "child" orders to exchanges until each parent was filled. On 1 August 2012 the New York Stock Exchange launched a Retail Liquidity Program (RLP), and Knight had developed new code in SMARS to support it. The SEC's 2013 order describes what happened next, and every step is a lesson from this track.

The dead code. The new RLP code "was intended to replace unused code in the relevant portion of the order router". That unused code had implemented a feature called "Power Peg", which Knight had stopped using in 2003 — but, in the SEC's words, "the Power Peg functionality remained present and callable". Worse, in 2005 Knight had moved Power Peg's cumulative-quantity function, which counted executed shares so the code would stop sending child orders once a parent was filled, to an earlier point in the code, and "did not retest the Power Peg code after moving the cumulative quantity function to determine whether Power Peg would still function correctly if called."

The reused flag. "The new RLP code also repurposed a flag that was formerly used to activate the Power Peg code." Knight intended to delete Power Peg, so that when the flag was set to "yes", RLP rather than Power Peg would engage.

The unverified deployment. Beginning on 27 July 2012, Knight deployed the RLP code to SMARS in stages, a few servers each day. "One of Knight's technicians did not copy the new code to one of the eight SMARS computer servers. Knight did not have a second technician review this deployment" and had "no written procedures that required such a review."

The morning. Starting at about 8:01 a.m., pre-market RLP orders caused an internal system to send automated emails referencing SMARS with the error "Power Peg disabled" — 97 of them before the 9:30 open — but they weren't designed as alerts and staff generally didn't review them. At the open, orders carrying the repurposed flag reached all eight servers. The seven with new code handled them correctly. On the eighth, the flag activated Power Peg, which — its fill-counting having been moved in 2005 — "continuously sent child orders, in rapid sequence, for each incoming parent order without regard to the number of share executions". For 212 parent orders, SMARS sent millions of child orders: over 4 million executions in 154 stocks, more than 397 million shares, in about 45 minutes. Knight accumulated a net long position of about $3.5 billion in 80 stocks and a net short position of about $3.15 billion in 74 stocks, and realised a loss of more than $460 million.

The response made it worse. With no incident procedures, Knight's technology staff tried to diagnose the problem live while the system kept trading. In one attempt, they "uninstalled the new RLP code from the seven servers where it had been deployed correctly" — a rollback — which caused incoming orders on those servers to activate Power Peg as well, because the flag was still set and the old code was still there. Knight also lacked automated controls to stop sending orders when capital thresholds were exceeded, or to compare orders leaving SMARS with those entering it. The SEC censured Knight and fined it $12 million, and the firm, needing emergency capital, was soon acquired.

Read the incident against this lesson and the rest of the track. Dead code kept "just in case" was live the moment configuration allowed it. A refactoring in 2005 — moving a function — changed the behaviour of code no one ran and no test covered. A reused flag gave old and new code the same trigger, so any server with the old code would do the wrong thing. An unverified manual deployment (swe9) left one server different, with no automated check that all servers ran the same artefact. Unread signals — 97 emails — went unnoticed because they weren't alerts (swe14). Rollback without understanding made things worse. And there was no kill switch or output limit. The SEC's own summary of the fix is modest: "a written procedure requiring a simple double-check of the deployment of the RLP code could have identified that a server had been missed and averted the events of August 1." Deleting Power Peg in 2003 would have averted them too.

The ML angle

Sculley and colleagues cited Knight in their ML technical-debt paper under "dead experimental codepaths" for a reason: ML systems accumulate exactly this pattern. Experiments are added as conditional branches in production code — "if model_version == 'v3-exp'", "if customer in PILOT_CUSTOMERS: use_new_retriever" — and when experiments end, the branches stay. Months later, a configuration change, a customer list edit or a reused experiment name reactivates a path trained on stale data or wired to a retired feature. The practices that would have saved Knight are the ones that keep ML codebases safe: delete experiment branches when experiments conclude; give every flag and experiment an owner and expiry; never reuse identifiers; verify that every serving replica runs the same model and configuration version; and turn unexplained warnings (a spike in fallback-path counters, a parse-failure email) into real alerts.

Tools and knobs

IDE automated refactorings; type checkers to make Python refactors safer; golden-master or approval tests for legacy code; vulture and coverage reports to find dead code candidates, confirmed with runtime counters; flag management with owners and expiry; hotspot and change-coupling analysis from git history (CodeScene, or a script); codemod tools such as LibCST for large mechanical changes; a routing layer (gateway, proxy, façade) for strangler migrations; and Scientist-style parallel runs for replacements that must match.

"""swe11 lab: (1) pin legacy behaviour with a golden-master characterisation test, refactor, and catch a subtle slip;
(2) rank refactoring targets by churn x complexity (hotspots)."""
import ast
import random

# ---------- 1. legacy code nobody fully understands ----------
def legacy_price(qty, unit, member, coupon, country):
    t = qty * unit
    if member:
        if t > 100:
            t = t * 0.9
        else:
            if coupon == "SAVE5":
                t = t - 5
    else:
        if coupon == "SAVE5" and t > 20:
            t = t - 5
        elif coupon == "HALF":
            t = t / 2
    if country == "DE":
        t = t * 1.19
    elif country == "FR":
        t = t * 1.2
    if t < 0:
        t = 0
    return round(t, 2)

# refactored: named rules, a tax table, guard clauses — same behaviour (we hope)
VAT = {"DE": 1.19, "FR": 1.2}

def member_discount(total, coupon):
    if total > 100:
        return total * 0.9
    return total - 5 if coupon == "SAVE5" else total

def guest_discount(total, coupon):
    if coupon == "SAVE5" and total > 20:
        return total - 5
    return total / 2 if coupon == "HALF" else total

def price(qty, unit, member, coupon, country):
    net = qty * unit
    net = member_discount(net, coupon) if member else guest_discount(net, coupon)
    gross = net * VAT.get(country, 1.0)
    return round(max(gross, 0), 2)

# a plausible-looking "cleanup" with a subtle slip: >= instead of >
def price_slip(qty, unit, member, coupon, country):
    net = qty * unit
    if member:
        net = net * 0.9 if net >= 100 else (net - 5 if coupon == "SAVE5" else net)
    else:
        net = guest_discount(net, coupon)
    return round(max(net * VAT.get(country, 1.0), 0), 2)

def inputs(n, seed=42):
    rng = random.Random(seed)
    for _ in range(n):
        yield (rng.randint(0, 12), rng.choice([0.5, 1, 4.99, 8.33, 10, 12.5, 25, 50]),
               rng.random() < 0.5, rng.choice([None, "SAVE5", "HALF", "BOGUS"]), rng.choice(["DE", "FR", "US", "UK"]))

golden = [(args, legacy_price(*args)) for args in inputs(10_000)]          # record what the legacy code DOES
for name, candidate in (("refactor", price), ("cleanup with slip", price_slip)):
    diffs = [(a, want, candidate(*a)) for a, want in golden if candidate(*a) != want]
    print(f"{name:18}: {len(diffs):4} of {len(golden)} cases differ", f"e.g. {diffs[0]}" if diffs else "")

FILES = {   # module -> (commits in the last 12 months, source)
    "billing/pricing.py": (41, "def f(a):\n" + "".join(f"    if a == {i}:\n        a += 1\n" for i in range(14)) + "    return a\n"),
    "billing/invoice_pdf.py": (3, "def f(a):\n" + "".join(f"    if a == {i}:\n        a += 1\n" for i in range(18)) + "    return a\n"),
    "api/handlers.py": (35, "def f(a):\n    if a:\n        return 1\n    return 0\n"),
    "utils/dates.py": (2, "def f(a):\n    return a\n"),
}
def complexity(src):                       # cyclomatic complexity: 1 + decision points
    return 1 + sum(isinstance(n, (ast.If, ast.For, ast.While, ast.BoolOp, ast.ExceptHandler, ast.IfExp))
                   for n in ast.walk(ast.parse(src)))
print(f"\n{'module':24}{'commits':>8}{'complexity':>12}{'hotspot':>9}")
for mod, (churn, src) in sorted(FILES.items(), key=lambda kv: -kv[1][0] * complexity(kv[1][1])):
    c = complexity(src)
    print(f"{mod:24}{churn:>8}{c:>12}{churn * c:>9}")
Rescue it

You inherit a 3,000-line billing.py with no tests. It changes almost weekly, and about a quarter of changes cause incidents. Product wants a new discount type next sprint, and a senior colleague proposes a three-month rewrite. What do you do?

Answer

Don't rewrite; get it under control incrementally. A rewrite would have to rediscover every edge case the old code encodes, deliver nothing for months, and still need the discount feature built twice.

  1. Confirm it's worth it: it's a hotspot — high churn, high complexity, frequent incidents — so the interest is real. Pull the numbers (commits, incidents, lead time) for the conversation with product.
  2. Characterisation tests first: build a golden master over many generated inputs (and a sample of real anonymised invoices), covering boundaries deliberately. Don't fix bugs you find yet — record them.
  3. Create seams: turn hard-wired dependencies (database, clock, tax service) into parameters with defaults, using small, safe edits.
  4. Preparatory refactoring in the area the discount touches: extract the discount rules into named functions or a Strategy registry (swe3), with the golden master green after each step.
  5. Add the feature as a new, fully tested strategy — a sprout, not more branches in the old function.
  6. Repeat with each subsequent feature; track change failure rate and lead time for billing to show the trend. If a larger replacement is ever justified, do it strangler-style behind a façade, with a parallel run comparing old and new invoices.

Also delete any dead code and stale flags you prove unused — Knight Capital is the reason not to leave them.
