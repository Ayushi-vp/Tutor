A team adds a spending limit to their LLM-powered assistant: each customer has a monthly budget of tokens, and a request is refused if it would exceed it. The code is three lines — check the remaining budget, call the model, subtract what was used — and the tests pass. In production, heavy users routinely overshoot their budgets by 50% or more. Nothing crashes and no error is logged. What happened is that a single chat session fires several model calls at once, each call checks the budget before any of them has subtracted, and they all see enough money left. Each line is correct. The combination, when several copies run at the same time, is not.

That is the whole subject of concurrency in one example. Modern software is concurrent everywhere: web servers handle many requests at once on many threads, processes and machines; async code juggles hundreds of in-flight network calls; background workers retry jobs; users double-click. Whenever two of these touch the same data, their steps can interleave in ways the author never pictured, and code that is obviously right one step at a time becomes wrong. These bugs are among the hardest in software: they depend on timing, so they appear rarely, under load, on some machines and not others, and disappear when you add logging to look for them.

This lesson makes the problem concrete and the fixes mechanical. It traces a lost update line by line through two interleaved threads, explains what Python's GIL does and doesn't protect, shows the check-then-act pattern in threads, in asyncio and across servers, covers locks, deadlock and its four conditions, and then the designs that avoid most of these bugs in the first place — immutability, single ownership, message passing, and letting the database arbitrate. The case study is the Therac-25, a radiation therapy machine whose software, between 1985 and 1987, was involved in six known massive overdoses, several fatal; two of its bugs were exactly the kinds of concurrency error this lesson describes. The lab reproduces a lost update, an overspent token budget and a deadlock on purpose, and fixes each.

The analogy: two cooks and one recipe card

Two cooks share a kitchen and a whiteboard that says "eggs left: 6". Each needs three eggs. Cook A glances at the board (6), turns to crack eggs, and meanwhile Cook B glances too (still 6), cracks three, and writes 3. Cook A finishes, computes 6 − 3, and writes 3 as well. Six eggs were used; the board says three are left. Nobody made an arithmetic mistake; they just read, thought and wrote at overlapping times. That's a lost update. Now imagine the board says "one soufflé dish free", both cooks check it, both see "free", and both start a soufflé: that's check-then-act. The fix in a kitchen is obvious — only the person holding the marker may read and update the board, and they hold it for the whole read-think-write — and that marker is a lock. And if Cook A holds the marker and waits for the oven while Cook B holds the oven and waits for the marker, neither moves: deadlock.

The analogy breaks on speed and invisibility. Cooks see each other; threads don't. And a computer can switch between tasks after any tiny step, millions of times a second, so a window of a few microseconds that "never" gets hit in testing gets hit many times a day in production.

The core idea: interleavings

A task here is any independent flow of execution: a thread, a process, an asyncio coroutine, a request on another server. Concurrency means the steps of several tasks can interleave — any step of one can happen between any two steps of another. Parallelism, steps happening at literally the same instant on different cores, makes it worse, but isn't required: a single core switching between threads is enough to produce every bug in this lesson.

A race condition is any bug whose outcome depends on which interleaving happens. The trouble is that the number of interleavings explodes: two tasks of ten steps each can interleave in 184,756 ways, and tests exercise a tiny, timing-dependent sample. So correctness can't come from testing alone; it has to come from design — making the steps that must go together atomic (indivisible from other tasks' point of view), or making sure there's no shared mutable state to race on.

That gives a simple checklist to carry through the rest of the lesson. For every piece of state, ask three questions. Is it shared? — can more than one task reach it, including other processes or servers? Is it mutable? — can anyone change it after creation? If both, what guarantees that the multi-step operations on it happen atomically? If the answer to the third question is "nothing", or "it's fast so it'll be fine", there is a race waiting for the right load. Most of the techniques that follow are ways of making one of the three answers "no".

1. Where concurrency comes from

Concurrency isn't only something you opt into with threading. A Python web service typically runs several worker processes, each maybe with several threads or an event loop, on several machines — so two requests from the same user can run at the same time in different processes on different servers. Background job workers run in parallel with web requests. Clients retry after timeouts, so the same operation may arrive twice (swe7's idempotency). Scheduled jobs overlap with themselves if a run takes longer than the interval. And async code (py9) interleaves coroutines at every await. The first skill is noticing the concurrency you already have.

2. Read-modify-write: the lost update, traced

The simplest race is incrementing a shared counter from two threads. It looks like one step. It isn't: Python's dis module shows counter += 1 compiles to four bytecodes in 3.12 — LOAD_GLOBAL (read), LOAD_CONST, BINARY_OP (add), STORE_GLOBAL (write). CPython can switch threads between any two bytecodes. Trace it with the counter at 5:

StepThread AThread Bcounter
1read counter → 55
2(switched out)read counter → 55
3compute 5 + 1 = 65
4write 66
5compute 5 + 1 = 66
6write 66

Two increments ran; the counter rose by one. That's a lost update. The lab makes the window wider with a time.sleep(0) between read and write (standing in for any work, I/O or scheduler switch), and eight threads each incrementing 500 times end up with a counter somewhere around 800 instead of 4,000 — a different number each run.

This is also the answer to the most common Python misconception. The global interpreter lock (GIL) lets only one thread execute Python bytecode at a time, which makes each bytecode atomic, but it says nothing about sequences of bytecodes. Without the artificial sleep, the race is rarer in CPython (threads switch only every few milliseconds by default), which makes it worse, not better: it slips through tests and appears under production load. And CPython's free-threaded build, added in 3.13 and officially supported from 3.14, removes the GIL entirely, so code that leans on it becomes unsafe even at the bytecode level.

The same shape appears everywhere data is read, changed in application code and written back: a Python process reading a row, computing a new balance and saving it; two browser tabs saving a document; two services updating the same cache entry. The database version of the lost update is the swe4 drill's user.balance -= total; db.save(user).

3. Critical sections and locks

The fix is to make the read-modify-write a critical section — a sequence that no other task touching the same state may interleave with — and enforce that with a lock (mutex): an object at most one task can hold at a time.

lock = threading.Lock()

def safe_increment():
    global counter
    with lock:                 # acquire; others block here until release
        seen = counter
        counter = seen + 1     # read and write can no longer be split by another holder

With the lock, the lab's eight threads reach exactly 4,000 every time. Three rules make locks work. Every access to the protected state must take the same lock — one unprotected read or write reopens the race. Hold it for the whole invariant: locking the read and the write separately is still a race. And keep critical sections short, never calling slow or unknown code (a network request, a callback) while holding a lock, both for performance and to avoid deadlock. Python's with statement guarantees release even on exceptions (py7). Related primitives: RLock (re-entrant: the same thread may acquire it again), Semaphore (at most n holders — useful to cap concurrent model calls), Condition and Event (wait for a state change), and thread-safe queues.

4. Check-then-act, in threads, async and files

The second classic shape is check-then-act: decide based on a condition, then act, while another task can change the condition in between. The introduction's token budget, reduced to its essentials in asyncio:

async def request(cost):
    if budget["left"] >= cost:                 # check
        used = await call_model(cost)          # await: other coroutines run here
        budget["left"] -= used                 # act on a check that may now be stale
        return used
    return 0

asyncio runs one coroutine at a time and switches only at await — which is why people assume it can't race. But the await sits exactly between check and act. Six concurrent requests for 300 tokens against a budget of 1,000 all pass the check before any subtracts; the lab shows 1,800 tokens spent. The fix is to make check-and-reserve one step with no await inside, then do the slow work, then settle:

async with guard:                              # asyncio.Lock, or no await between check and update
    if budget["left"] < cost:
        return 0
    budget["left"] -= cost                     # reserve first
result = await call_model(cost)                 # slow part outside the critical section
# optionally refund unused tokens afterwards

Now exactly three requests succeed and 900 tokens are spent. The same bug appears as a cache stampede (if key not in cache: cache[key] = await fetch(key) makes a hundred concurrent requests all fetch), as "if the file doesn't exist, create it" (a TOCTOU — time-of-check-to-time-of-use — race, fixed by an atomic operation such as opening with exclusive-create mode "x"), and as "if the user has no subscription, create one" across two servers.

5. Across processes and servers: let the database arbitrate

A threading.Lock coordinates threads inside one process. A web service with four worker processes on each of five servers has twenty separate locks, which is the same as none. Cross-process correctness needs a shared arbiter, and the best one is usually already there: the database. Take the concert with one ticket left and two buyers on different servers.

Atomic conditional update — the default choice. Put the check inside the write, and let the database apply it atomically to the row:

UPDATE events SET sold = sold + 1
 WHERE id = :event AND sold < capacity;
-- rows affected = 1 → you got the ticket; 0 → sold out

No read in application code, no lock held across a network round trip, and correct under any number of servers. Pessimistic locking: SELECT … FOR UPDATE inside a transaction locks the row; the second buyer waits until the first commits, then sees the updated count. Correct and simple for multi-step logic, but it serialises everyone on hot rows. Optimistic concurrency control: read the row with a version column, then UPDATE … SET …, version = version + 1 WHERE id = :id AND version = :v_read; if zero rows change, someone else won — re-read and retry. No waiting, but wasted work under heavy contention. Unique constraints turn "check it doesn't exist, then insert" into "insert and catch the duplicate-key error", which is atomic by construction — ideal for "one subscription per user" or "one seat per ticket". And idempotency keys (swe7) make retried requests safe. Transaction isolation levels, which decide which anomalies the database itself prevents, are covered in sc5.

6. Deadlock, livelock and starvation

Locks create a new failure: deadlock, where tasks each hold something the other needs. Two transfers run at once — one from account A to B, one from B to A — and each locks the source account first. The first holds A and waits for B; the second holds B and waits for A. Neither can proceed, forever.

Coffman and colleagues showed in 1971 that deadlock requires four conditions at once: mutual exclusion (a resource has one holder), hold and wait (holding one resource while waiting for another), no pre-emption (resources aren't taken away), and circular wait. Break any one and deadlock is impossible. The standard fix breaks circular wait: acquire locks in one global order — for transfers, always lock the lower account ID first, whichever direction the money moves. Other tools: acquire everything you need at once; use timeouts (lock.acquire(timeout=0.5)) and back off, which turns a silent hang into a detectable failure — the lab uses one to report the deadlock instead of freezing; and never hold a lock while calling code that might take other locks. Databases detect deadlocks between transactions and abort one of them with an error, so application code must be ready to retry. Two cousins: livelock, where tasks keep reacting to each other without progress (two retry loops that back off by the same fixed amount), fixed by randomised backoff; and starvation, where a task never gets the resource because others always win, fixed by fair queuing.

7. Designing so there's less to lock

Every race needs shared and mutable state. Remove either and the problem disappears, which is why the most robust concurrent designs minimise shared mutable state rather than locking it cleverly.

  • Immutability: data that can't change can be shared freely. Frozen dataclasses, tuples and frozenset; build a new version instead of mutating (a new configuration object swapped in with one atomic reference assignment).
  • Confinement / single ownership: each piece of mutable state belongs to exactly one task — one thread, one coroutine, one actor, one service — and nobody else touches it. Others ask the owner to make changes.
  • Message passing: tasks communicate by sending immutable messages through thread-safe queues (queue.Queue, asyncio.Queue, or a message broker between services, sc10). A worker pool reading jobs from a queue needs no locks around the jobs because each job is owned by the worker that took it. Go's proverb puts it well: "Don't communicate by sharing memory; share memory by communicating."
  • Processes instead of threads for CPU-bound work in Python (multiprocessing, concurrent.futures.ProcessPoolExecutor): no shared memory by default, so results come back as messages.
  • Atomic primitives at the right level: the database's conditional update, a unique constraint, Redis's INCR — let a system built for atomicity do it.

8. Finding and testing concurrency bugs

Ordinary tests are nearly useless against races because they run one interleaving, usually the lucky one. What works: reason with invariants — write down what must always be true ("stock ≥ 0", "debits = credits") and walk through every read-modify-write and check-then-act on shared state asking "what if another task ran here?". Stress with real concurrency: many threads or processes against a real database, with delays injected between check and act to widen windows, asserting invariants at the end (the swe5 drill's "50 parallel transfers never overdraw"). Control the interleaving to make a race reproducible: barriers, events or a deterministic scheduler that forces the bad order, as the lab's sleep(0) does crudely. Use detectors where the ecosystem has them — ThreadSanitizer for C and C++ (and C extensions), Go's -race flag, Java's jcstress; in Python, run suites repeatedly under load and in random order. And treat an intermittent failure (swe5's flaky test) as a possible race in the product, not just in the test.

Memory models and visibility

In languages with truly parallel threads — Java, C, C++, Go, Rust, and free-threaded Python — there's a subtler problem than interleaving: visibility. Compilers reorder instructions, CPUs execute out of order and keep values in per-core caches, so one thread can see another's writes late, in a different order, or not at all, unless the two synchronise. A memory model defines which orderings are guaranteed through happens-before relationships: releasing a lock happens-before the next acquisition of it; starting a thread happens-before its first action; a write to an atomic variable happens-before a read that observes it. Only accesses connected by such chains are guaranteed to see each other. Code that "works" without synchronisation on an x86 laptop, whose memory ordering is relatively strong, can fail on ARM servers, whose ordering is weaker. The practical rule is the same as before — every access to shared mutable data goes through a synchronisation operation — but the reason is stronger: without it, you can't even rely on seeing the other thread's writes.

Lock-free programming and atomics

Hardware provides atomic instructions such as compare-and-swap (CAS): "set this memory location to new only if it currently holds expected, and tell me whether it did". Lock-free algorithms build counters, queues and stacks from CAS loops — read, compute, CAS, retry if someone else changed it — which is optimistic concurrency at the CPU level. They avoid lock waiting and deadlock but are notoriously hard to get right (the "ABA problem": a value changes from A to B and back to A, fooling the CAS), and they're rarely the right tool in application code. Knowing CAS is useful because the same pattern — conditional write, retry on conflict — appears in databases (the version-column update), in object stores (conditional PUT with an ETag), and in distributed coordination systems.

Distributed locks and fencing tokens

Sometimes a task that spans systems needs mutual exclusion across machines — only one worker should run the nightly billing job. Lock services (Redis with a lease, ZooKeeper, etcd) grant a lock with an expiry so a crashed holder doesn't block everyone forever. The expiry is also the danger, as Martin Kleppmann described: the holder pauses (a long garbage-collection pause, a VM migration, a slow network) past its lease; the lock is granted to another worker; then the first resumes, still believing it holds the lock, and both write. No choice of timeout fixes this, because pauses are unbounded. The fix is a fencing token: a number that increases every time the lock is granted, sent with every write, and checked by the resource being protected, which rejects writes carrying a token lower than one it has already seen. The broader lesson: prefer arbiters that are also the storage (a conditional update in the database) over separate lock services whenever possible.

Structured concurrency and cancellation

Concurrency bugs aren't only about shared state; they're also about lifetimes. A task started and forgotten can outlive the request that created it, keep holding resources, or fail silently. Structured concurrency — Python 3.11's asyncio.TaskGroup, Trio's nurseries — ties child tasks to a scope: the scope doesn't exit until all children finish, and if one fails, the others are cancelled and the errors are reported together (swe4's exception groups). Cancellation itself needs care: an await can be interrupted by CancelledError, so code that reserved a resource (a budget, a lock, a database connection) must release it in finally or a context manager, or cancellations will leak reservations. For LLM applications that fan out to many model and tool calls per request, structured concurrency with timeouts is what prevents runaway spend when a user disconnects.

Concurrency in the data layer

Databases are concurrency engines, and their guarantees are configurable. Isolation levels (sc5) decide which anomalies a transaction may see: read committed allows lost updates on read-modify-write in application code; repeatable read and snapshot isolation prevent some anomalies but still allow write skew (two transactions each check a condition over several rows and write different rows, jointly breaking an invariant — two doctors both going off call because each saw the other on call); serializable prevents all of them at the cost of aborts that must be retried. Many real bugs come from assuming a stronger level than the database defaults to (Postgres and many others default to read committed). The patterns in section 5 — conditional updates, row locks, unique constraints — are how application code gets correctness without depending on the highest isolation level everywhere.

How concurrency bugs show up in production

They rarely announce themselves. Silent wrong numbers: counters that drift, inventory that goes negative, budgets overspent, duplicate emails or charges — found by reconciliation jobs or customers, not alerts. Load-dependent failures: bugs that appear only during peaks, sales or retries after an outage, when interleavings become likely. Hangs: a service that stops responding with no errors — a deadlock or a lock held across a slow call — visible as requests piling up and thread dumps showing blocked threads. Heisenbugs: problems that vanish when you add logging, because the logging changes the timing. The defences: invariant checks and reconciliation jobs that compare derived totals with sources; metrics for lock-wait time, database deadlocks and serialization failures; timeouts on every lock and external call; and post-incident reviews that ask "what other read-modify-writes look like this one?"

Case: the Therac-25, 1985–1987

The Therac-25 was a medical linear accelerator built by Atomic Energy of Canada Limited (AECL) that treated cancer with either a low-current electron beam or a high-energy X-ray mode, in which a far more intense beam strikes a metal target that converts it into X-rays. Between June 1985 and January 1987, six known accidents involved massive overdoses, with deaths and serious injuries. Nancy Leveson and Clark Turner's 1993 investigation in IEEE Computer remains the standard account, and it's explicit that "most accidents are system accidents" with many contributing factors. Two of those factors are textbook concurrency bugs.

The design context matters first. Earlier models, the Therac-6 and Therac-20, had independent hardware interlocks that physically prevented dangerous configurations; the Therac-25 relied on software for safety and dropped many of them. Its software, written largely by one programmer in PDP-11 assembly and partly derived from the earlier machines' code, ran several concurrent tasks under a custom real-time scheduler — among them a keyboard handler and a treatment monitor task called Treat — that communicated through shared variables without proper synchronisation.

The Tyler race. On 21 March 1986, at the East Texas Cancer Center in Tyler, an experienced operator entered a prescription, noticed she had typed "x" (X-ray) instead of "e" (electron), used the cursor-up key to correct it, and started the treatment. The machine stopped with "Malfunction 54", a message the documentation didn't explain, and a display suggesting an underdose; she resumed treatment, as operators routinely did after pauses. The patient, who felt what he described as an electric shock, had in fact received a massive overdose — after-the-fact simulations suggested 16,500 to 25,000 rads in less than a second over about 1 cm², against a prescribed 180 rads per treatment. He died five months later. Three weeks after the first accident, the same operator made the same kind of quick edit for a second patient, who died three weeks after that. The hospital physicist, Fritz Hager, worked with the operator until he could reproduce "Malfunction 54" at will — and found that data-entry speed was the key: the fault appeared only if the edit was made fast.

The mechanism, as the paper reconstructs it: the treatment task's data-entry routine used a shared "data entry complete" flag, set by the keyboard handler, to decide the prescription was final, and it then called a routine to set the bending magnets, which took about eight seconds. Checks for further edits happened only during the first pass through that routine. An edit completed within the eight seconds was reflected on the screen and in part of a shared mode/energy variable, but the setup had already been computed from the old values and never noticed the change, leaving the machine in an inconsistent configuration. It was a check-then-act race on shared state with an eight-second window — too long for "impossible", too short for new operators, who typed slowly. Only an operator fast from repetition could hit it, which is why testing never did.

The Yakima counter. On 17 January 1987, at Yakima Valley Memorial Hospital, a different bug overdosed a patient with an estimated 8,000 to 10,000 rads instead of 86. During setup, a routine was scheduled repeatedly, hundreds of times, and on each pass incremented a one-byte shared variable, Class3, whose non-zero value meant "check the upper collimator position before treatment". A one-byte variable holds at most 255, so on every 256th pass it overflowed to zero — which meant "no check needed". If the operator pressed "set" at exactly that moment, the collimator check was skipped and the beam could fire at full energy with the turntable in the wrong position. AECL's fix was to set Class3 to a fixed non-zero value instead of incrementing it. It's the same class of bug as swe4's Ariane conversion — an integer overflowing silently — made deadly by sitting inside unsynchronised shared state that acted as a safety flag.

Leveson and Turner's broader lessons map directly onto this track. Don't rely on software alone for safety when an independent hardware interlock is possible — defence in depth. Design concurrent software with explicit synchronisation on shared state, and keep safety checks out of timing windows. Make error messages meaningful ("Malfunction 54" told operators nothing, so they resumed). Take user reports seriously: the manufacturer initially said an overdose was impossible. Test the software as it will actually be used, including fast expert use, and re-test after every modification. And don't assume reused code (partly from the Therac-6 and Therac-20, where hardware masked its flaws) is safe in a new context — Ariane 5's lesson again.

Concurrency in AI systems

LLM applications are highly concurrent by nature — a single user request fans out to retrieval, several model calls, tool calls and streaming — and most of their shared state is exactly the kind that races: per-user token budgets and rate limits, conversation histories appended to by parallel steps, caches of embeddings and completions, and agent state machines (swe3) driven by concurrent tool results. The patterns in this lesson apply directly: reserve budgets atomically before calling models; give each conversation or agent run a single owner (a queue or actor) that serialises state changes; use idempotency keys on side-effecting tools so a retried or duplicated step doesn't refund twice; prevent cache stampedes with a per-key lock or a "single flight" pattern; and use structured concurrency with timeouts so cancelled requests stop spending. Where the system has safety checks — content filters, approval gates for dangerous tools — make sure no concurrent path can reach the action without passing the check, the Therac-25's most important lesson.

Tools and knobs

Databases: conditional updates, SELECT … FOR UPDATE (with SKIP LOCKED for job queues), version columns, unique constraints, and monitoring of deadlocks and serialization failures. Across services: idempotency keys, fencing tokens for any distributed lock, and reconciliation jobs that check invariants.

lock = threading.Lock()

def unsafe_worker(n):
    global counter
    for _ in range(n):
        seen = counter             # read
        time.sleep(0)              # yield: widens the window a real scheduler would hit occasionally
        counter = seen + 1         # write back a stale value

def safe_worker(n):
    global counter
    for _ in range(n):
        with lock:                 # read-modify-write is now one critical section
            seen = counter
            time.sleep(0)
            counter = seen + 1

    counter = 0
    threads = [threading.Thread(target=worker, args=(500,)) for _ in range(8)]

    return tokens

    async def request(cost):
        if safe:
            async with guard:                          # reserve atomically, then call

                    return 0
                budget["left"] -= cost
            return await fake_llm_call(cost)
        if budget["left"] >= cost:                     # check ...

            return used
        return 0
    spent = await asyncio.gather(*(request(300) for _ in range(6)))
    return sum(spent)

        time.sleep(0.05)                               # both threads now hold one lock each

Bug: check-then-act and read-modify-write across processes. Many requests read stock = 300 concurrently, all pass the check, and each writes its own computed value — the last write wins, so decrements are lost and the product oversells. It's a lost update; no in-process lock helps because there are 20 servers with many workers each.

Fix 1 — atomic conditional update (best):

UPDATE items SET stock = stock - :qty WHERE sku = :sku AND stock >= :qty
-- rows_affected == 1 → reserved, 0 → out of stock

The database performs the check and the write atomically on the row. No read needed, no lock held across a round trip.

Fix 2 — pessimistic locking: SELECT stock … FOR UPDATE inside a transaction, then update and commit. Correct, but it serialises all buyers of a hot item behind a row lock — worse under a flash sale.

Fix 3 — optimistic locking: add a version column; UPDATE … WHERE sku = :s AND version = :v, retry on 0 rows. Good under low contention; under a flash sale most attempts conflict and retry.

Add an idempotency key so a retried reservation isn't applied twice, and a test: fire 1,000 concurrent reservations against a real database and assert stock never goes negative and successful reservations equal the initial stock.
