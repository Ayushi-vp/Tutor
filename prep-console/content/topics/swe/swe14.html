At 3 a.m. the on-call engineer is paged: "checkout slow". They open the logs and find millions of lines like INFO Processing request across forty machines, none saying which request, for which customer, or how long it took. The dashboard shows average latency, which looks almost normal. They restart a few servers, which seems to help for ten minutes, then doesn't. By morning, three people have spent six hours; the cause turns out to be one customer whose unusually long product names trigger a slow code path — something anyone could have seen in minutes with a latency percentile broken down by customer, a trace of one slow request, and a log line carrying that request's ID.

Software in production fails in ways nobody predicted, under load and data that don't exist on a laptop, across dozens of services owned by different teams. Debugging it is a different skill from debugging code in an editor: you can't pause the program or add a print statement and rerun, and while you think, users are affected. What you can do depends almost entirely on what the system tells you about itself — its telemetry — and on having a method for turning that telemetry into an answer quickly. The combination is what's meant by observability.

This lesson builds both halves. First the telemetry: structured logs with request IDs, metrics and the RED and USE methods for choosing them, distributed traces and how to read a waterfall, and OpenTelemetry, the standard that ties them together. Then the method: mitigate first, ask what changed, narrow down by comparison, test hypotheses, and confirm — plus profilers for looking inside a process. Then learning: blameless postmortems. The case study is Cloudflare's 2 July 2019 outage, when a single regular expression in a firewall rule consumed the CPUs serving HTTP traffic across its global network for 27 minutes; its postmortem is one of the best public examples of both debugging under pressure and honest analysis. Throughout, and in its own section, the lesson covers what's different about observing LLM systems. The lab instruments a toy service and uses the signals to find a slow regex behind a bad p99.

The analogy: flight instruments, the black box, and the flight path

A pilot relies on three kinds of information. The instrument panel shows a few numbers continuously — airspeed, altitude, fuel — cheap to display, instantly readable, and the thing that tells you something is wrong. The flight path record traces where one particular flight went, leg by leg, with times. The black-box recorder captures detailed events — every control input, every warning — which investigators read after the fact to understand exactly what happened. In software these are metrics (the panel), traces (one request's path) and logs (the detailed event record). Each answers a different question, and investigations move between them: the panel says something is wrong, the path shows where, the recorder explains why.

Where the analogy breaks: a plane is one vehicle; a production system handles thousands of "flights" a second, across many services, and the interesting one is usually the rare flight that went wrong. So software telemetry has to be sliceable — by endpoint, customer, version, region — and linked, so you can jump from "p99 is bad" to the specific slow requests and their details.

Three signals, linked

Two words are often used interchangeably but mean different things. Monitoring watches things you knew to watch — CPU above 90%, error rate above 1% — and alerts when they cross thresholds. Observability is the property of being able to answer questions you didn't anticipate: "why are requests from this one customer, on the new app version, in Brazil, slow only when the cart has more than 50 items?" That's only possible if telemetry keeps enough detail (which customer, which version, which region, which cart size) and can be sliced after the fact. Monitoring tells you that something is wrong; observability lets you find out what, including for failure modes nobody has seen before — which, in complex systems, is most of the interesting ones.

A useful way to judge any system's observability is to time three things in the next incident: how long until someone knew there was a problem (time to detect), how long until they knew which component and change caused it (time to diagnose), and how long until users stopped being affected (time to mitigate). Good telemetry shortens the first two; good deployment practice — rollback, flags, kill switches — shortens the third. The case study later in this lesson is worth reading with those three clocks in mind, because each was affected by a different engineering decision made long before the incident.

The rest of the lesson makes each signal concrete, then turns to method. One idea to carry through: telemetry is designed, not accumulated. The questions you'll need to answer during an incident — which requests, which users, which version, which dependency — decide what every log line, metric label and span attribute should carry, and it's far cheaper to decide that while writing the code than at 3 a.m.

1. Structured logs

A log records a discrete event: a request handled, an error raised, a job started. The single biggest improvement to most logging is making it structured — one machine-readable record per event, usually a JSON object per line — instead of free text:

# free text: readable, but unsearchable except by regex
INFO Processing request for user 4411 took 842ms

# structured: every field can be filtered, grouped and joined
{"ts": "2026-09-29T03:12:07.412Z", "level": "info", "msg": "request completed",
 "request_id": "8b5cf8f5", "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
 "endpoint": "POST /checkout", "status": 200, "duration_ms": 842, "user_tier": "free",
 "version": "2026.09.28-3f9c2d1"}

With structured logs, "all errors for request 8b5cf8f5 across every service" and "count of 5xx by endpoint and version in the last hour" are simple queries. Four practices make them work. Put a request or trace ID on every line, set once when the request enters the service and carried automatically. In Python, contextvars does this correctly across threads and asyncio tasks (the lab sets a context variable per request and every log call reads it). Use levels deliberately: ERROR for things someone must look at, WARNING for degraded but handled conditions, INFO for significant business events, DEBUG off in production by default. Log once, at the boundary that handles a failure (swe4), with the full context and stack trace, rather than logging and re-raising at every layer. And never log secrets or unnecessary personal data: passwords, tokens, card numbers, full prompts containing customer data — redact at the logging layer so a mistake elsewhere can't leak them.

Logs are the most expensive signal per event, so volume matters: sample high-volume success logs, keep all errors, and set retention by value (seven days of debug-level detail, longer for audit events). The Python standard library's logging module supports structured output through a JSON formatter; libraries such as structlog make it convenient.

2. Metrics, and choosing them with RED and USE

A metric is a number sampled or aggregated over time, identified by a name and a set of labels: http_requests_total{endpoint="/search", status="5xx"}. Metrics are cheap because they aggregate — a counter increments in memory and is scraped every few seconds, regardless of traffic — so they're ideal for dashboards and alerts. Three types cover nearly everything. A counter only goes up (requests, errors, bytes sent); the useful view is its rate. A gauge goes up and down (queue depth, memory in use, open connections). A histogram counts observations into buckets (requests taking 0–10 ms, 10–25 ms, …), from which percentiles are estimated across all instances — which is why latency should be recorded as a histogram, never as an average.

Choosing what to measure is easier with two methods. The RED method, from Tom Wilkie, is for request-driven services: Rate (requests per second), Errors (failed requests per second, or as a share) and Duration (the latency distribution). The USE method, from Brendan Gregg, is for resources — CPU, memory, disks, network links, connection pools, thread pools, queues: Utilisation (share of time busy, or share of capacity used), Saturation (work waiting because the resource is full) and Errors. RED says whether a service is healthy; USE on its resources says which resource is the bottleneck. Google's "four golden signals" — latency, traffic, errors, saturation — combine the two.

A worked example. A search service reports RED: 1,200 requests per second, 0.4% errors, p50 duration 45 ms, p99 380 ms — p99 has tripled since yesterday while p50 is flat. USE on its resources:

ResourceUtilisationSaturationErrors
CPU65%run queue 0.3 per core—
Memory70%no swapping—
DB connection pool (size 20)95% (19 busy)12 requests waiting3 checkout timeouts/min
Reranker model callsconcurrency 40 of 64none0.1% timeouts

The connection pool is saturated: requests queue for a database connection, which adds latency to the unlucky ones (p99 up, p50 flat) and occasionally times out (the errors). The next question is why connections are held longer than yesterday — a slower query after a deploy, perhaps — which is a question for traces.

One trap deserves emphasis: cardinality. Each distinct combination of label values is a separate time series. Labels such as endpoint template, status class, region and version have a handful of values each. A label with user ID, request ID or raw URL (with IDs in it) has millions, and a 30-bucket histogram multiplies that by 30. That's how metrics bills explode and metrics systems fall over. Per-user and per-request detail belongs in traces and logs.

3. Distributed traces and the waterfall

A trace records one request's journey through the system as a tree of spans. Each span is one timed operation — the HTTP handler, a database query, a cache lookup, a call to another service, a model call — with a name, a start time, a duration, a parent span, and attributes (the SQL statement's shape, the model name, the number of rows). All spans in a trace share a trace ID. Viewed as a waterfall, with time running left to right and each span as a bar under its parent, a trace shows immediately where a request's time went.

For a trace to span services, each hop must carry the trace context. The W3C Trace Context standard defines an HTTP header, traceparent, of the form 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01: a version, the 32-hex-digit trace ID, the 16-hex-digit ID of the calling span, and flags (including whether this trace is sampled). The callee reads it and creates its spans as children. Context must also flow through message queues (as message headers), background jobs and async tasks — the most common reason traces "break" into disconnected pieces. Traces are expensive per request, so they're sampled: head sampling decides at the start (keep 1% of traces), which is cheap but may drop the rare slow one; tail sampling decides after the request completes (keep all errors and everything slower than p99, plus 1% of the rest), which keeps the interesting traces at the cost of buffering.

4. OpenTelemetry: one standard for all three

Historically each vendor had its own agents and formats. OpenTelemetry (OTel), a Cloud Native Computing Foundation project, standardises how telemetry is produced and exported: an API and SDKs for each language to create spans, metrics and logs; automatic instrumentation for common libraries (web frameworks, HTTP clients, database drivers, and increasingly LLM client libraries); a wire protocol (OTLP); and a Collector that receives, processes (sampling, redaction) and forwards telemetry to any backend. Its most useful property is correlation: the same trace and span IDs appear in spans, in log records emitted during those spans, and as exemplars on metrics, so the jump from a dashboard spike to the exact slow request's logs is a click. Instrumenting with OTel also avoids lock-in, since backends can be swapped by reconfiguring the Collector.

5. A method for debugging production

Telemetry is only half the skill. The other half is a method that converges quickly under pressure instead of flailing:

  1. Mitigate first. If users are affected, stop the bleeding before understanding it: roll back the most recent deploy or config change (swe9), flip the feature flag off, fail over, shed load. Most incidents start with a change, so rollback is usually the fastest fix, and it's reversible.
  2. Define the symptom with data. Which metric, since exactly when, for which requests or users, how big? "p99 of /search from 90 ms to 400 ms since 14:05, all regions, only web clients" is a problem statement; "checkout is slow" isn't.
  3. Ask what changed. Deploys, configuration, feature flags, traffic mix, dependency versions, data volume, certificates, the calendar (month-end jobs). Overlay change events on the metric graph.
  4. Narrow by comparison. Split along every dimension you have — version, host, region, endpoint, customer, input size — and compare the bad slice with a good one. Bisect in space (half the hosts?), in time (which minute?), in versions (swe8's bisect), in the request path (which span grew?).
  5. Form a specific hypothesis and test it with a query, a trace comparison, a controlled experiment or a reproduction. A good hypothesis predicts something you haven't looked at yet: "if the connection pool is the bottleneck, pool wait time rose at 14:05 and requests that don't touch the database are unaffected".
  6. Fix and confirm with the same signal that showed the problem, then look for other instances of the same class of bug.

Two habits help throughout. Write a running log of what you checked and found (it becomes the postmortem timeline), and resist fixing the first anomaly you see: production systems always have some odd-looking graphs, and the one you notice may be unrelated.

6. Looking inside a process: profilers and friends

When telemetry points at one service and one operation but not why, look inside the process. A profiler measures where time or memory goes. Deterministic profilers like Python's cProfile instrument every function call — precise but slow, fine for reproductions. Sampling profilers like py-spy take stack snapshots many times a second from outside the process, with low overhead and no code changes, so they're safe on live production processes: py-spy top --pid 1234 for a live view, py-spy record -o profile.svg --pid 1234 for a flame graph, in which each box is a function and its width is the share of samples in it — look for the widest plateaus. Distinguish CPU time from wall-clock time: a request can take two seconds while using 20 ms of CPU, because it's waiting on a lock, a pool or the network, which traces and wall-clock profiles show and CPU profiles don't. Other tools earn their place: strace (which system calls is it making, and which are slow?), tcpdump and the network tools from net15, memory profilers such as tracemalloc for leaks, and core dumps for crashes. Cloudflare's team used live CPU data and strace to confirm their culprit, as the case study describes.

7. Alerts, and a word on SLOs

Telemetry becomes action through alerts, and alerting well is mostly about restraint. Page on symptoms users feel — error rate, latency percentiles, failing synthetic checks — ideally expressed against a service-level objective (an SLO, such as 99.9% of requests succeeding under 300 ms over 30 days) and its error-budget burn rate; send causes (high CPU, a restarted pod, a full disk that isn't yet affecting anyone) to dashboards and tickets. Every page should be urgent, actionable and linked to a runbook. Synthetic checks — scripted requests from outside the system — catch total failures that internal metrics miss because nothing is reaching the service; Cloudflare's first page in 2019 came from exactly such a test, three minutes after the bad change. SLOs, burn-rate alerting and incident roles are covered in depth in sc13.

8. Observing LLM systems

LLM features need everything above plus signals that ordinary services don't. Cost and tokens: input and output tokens per request, per model, per feature and per customer tier, because cost is a production metric that can spike from a prompt change or an abusive user. Latency shape: time to first token (what users perceive in streaming UIs) separately from total generation time. Versions on every span: model name and version, prompt template version, retrieval index version, so a change in behaviour, cost or latency can be attributed to a rollout exactly like a code deploy (swe9). Pipeline spans: retrieval, reranking, each model call, each tool call, each retry and fallback, so a slow or failed answer can be read as a waterfall. Quality signals as metrics: parse failures, schema-validation failures, refusals, fallbacks to a simpler model, user feedback, escalations to humans, and online evaluation scores. And privacy: prompts and responses are the richest debugging data and the most sensitive, so log them with redaction, sampling, restricted access and short retention, or store them separately from general logs. OpenTelemetry has published semantic conventions for generative-AI spans, so these attributes can be recorded consistently across libraries.

Telemetry economics

Observability costs real money — often a noticeable share of infrastructure spend — and the three signals have very different cost curves. Metrics cost roughly per time series, independent of traffic, so they scale well with volume but badly with label cardinality. Logs and traces cost per event, so they scale linearly with traffic. That shapes design. Put high-volume, low-detail questions (rates, percentiles) in metrics; keep high-detail data in traces and logs but sample it — tail-sample traces to keep all errors and slow requests; sample success logs aggressively while keeping every error; and set retention by value. "Wide events" — one rich structured event per request per service, carrying dozens of attributes — are an increasingly popular middle ground: a single record supports both aggregation and drill-down, if the backend can query it efficiently.

Percentiles don't average

A frequent analytical mistake is averaging percentiles: taking each server's p99 and averaging them, or averaging per-minute p99s into an hourly p99. Percentiles aren't additive, and the result can be far from the true p99 of the combined traffic — one server with a terrible tail disappears into the average of forty healthy ones. The correct approach is to aggregate the underlying distributions — sum the histogram bucket counts across servers and time, then compute the percentile — which is why histograms, not pre-computed percentiles, should be what services export. A related trap is coordinated omission in load testing: a load generator that waits for each response before sending the next under-samples exactly the slow periods, reporting latencies that are far too optimistic.

Debugging as science, and its failure modes

The method in section 5 is the scientific method under time pressure, and its failure modes are cognitive. Anchoring: the first plausible explanation ("it's the database again") gets locked in and contrary evidence ignored — the antidote is to write down a hypothesis and what it predicts, then check a prediction you haven't looked at. Correlation mistaken for cause: every incident has several graphs that moved at the same time; ask which came first and which are effects. Changing several things at once during mitigation, so nobody knows which helped. Too many investigators on one question, a problem incident command structures (an incident commander, a communications lead, and investigators working distinct hypotheses) exist to solve. Cloudflare's postmortem notes that the team initially considered an attack before the evidence pointed to the WAF; good process is what turns that into a few minutes rather than an hour.

Catastrophic backtracking, and why engines differ

The case study's bug is worth understanding mechanically. Engines such as PCRE, Python's re, JavaScript's and Java's use backtracking: when part of a pattern fails, they go back and try the alternatives. A pattern like .*.*=.* gives the engine many ways to divide the input between the two leading .*s, and on a failing match it tries all of them; the count grows polynomially with input length, and with nested quantifiers like (a+)+ it grows exponentially. Cloudflare's post walks through it: .*.*=.* takes 23 steps to match x=x, 33 for x=xx, 45 for x=xxx, 555 with twenty x's, and 4,067 steps to fail on twenty x's with no equals sign. The lab's Python timing shows the same shape — roughly eight times slower each time the input doubles. Engines such as RE2 and Rust's regex use automata-based matching with guaranteed linear time, at the cost of some features (backreferences). Defences: avoid nested and adjacent unbounded quantifiers; anchor patterns; use a linear-time engine for patterns applied to untrusted input; bound input length; and put a time or CPU limit around matching. Denial of service by crafted input to such patterns has its own name — ReDoS.

Continuous profiling and eBPF

Profiling used to be something done during an investigation. Continuous profiling samples every instance all the time at a low rate and stores the results, so you can ask "what was this service doing at 14:05?" after the fact, and compare flame graphs before and after a deploy to see exactly which functions got more expensive. On Linux, eBPF lets tools run small, verified programs inside the kernel to observe system calls, network activity, scheduling and function calls across all processes with low overhead and no application changes — the basis of many modern profilers and network observability tools. Both extend the principle of this lesson: have the evidence before you need it.

How observability gaps show up

The gaps become obvious during incidents: time to detect is long because alerts watch causes, not symptoms, or there's no external check; time to diagnose is long because logs lack request IDs, traces break at a queue, metrics average away the tail or can't be sliced by version; and time to mitigate is long because rollback is slow or the tools needed are themselves down. The measurements that drive improvement come straight from postmortems: time to detect, time to diagnose, time to mitigate, how the problem was noticed (alert, customer, luck), and which missing signal would have shortened each phase. A good practice is to ask at the end of each incident, "what telemetry would have made this a five-minute diagnosis?", and build it.

Case: Cloudflare, 2 July 2019

Cloudflare runs a global network that proxies HTTP traffic for millions of websites, including a web application firewall (WAF) that inspects requests and blocks attack patterns. Its WAF Managed Rules are updated frequently, and can be deployed globally within seconds — a deliberate capability, used for example to protect customers against a serious vulnerability quickly. On 2 July 2019, as Cloudflare's CTO John Graham-Cumming wrote in the postmortem, that speed turned against them.

At 13:42 UTC an engineer on the firewall team deployed a minor change to rules for detecting cross-site scripting, through the normal automated process. The rule contained a regular expression — (?:(?:\"|'|\]|\}|\\|\d|(?:nan|infinity|true|false|null|undefined|symbol|math)|\`|\-|\+)+[)]*;?((?:\s|-|~|!|{}|\|\||\+)*.*(?:.*=.*))) — whose tail, .*(?:.*=.*), is the .*.*=.* shape from the deep section. Cloudflare's WAF ran rules through PCRE, a backtracking engine with no protection against runaway expressions, and on some requests the pattern backtracked enormously. The CPUs dedicated to serving HTTP and HTTPS traffic climbed to nearly 100% across Cloudflare's network, taking down its core proxying, CDN and WAF functions — the company's first global outage in six years.

Detection was quick. Three minutes after the change, the first page arrived from a synthetic test that checks WAF functionality from outside Cloudflare — one of hundreds of such tests — followed rapidly by failures of other end-to-end tests, a global traffic-drop alert, widespread 502 errors, and reports of CPU exhaustion from points of presence worldwide. At one point Cloudflare had lost about 80% of its traffic. SRE declared the highest-severity incident and pulled in engineering teams.

Diagnosis: the early hypothesis was an attack, which the evidence ruled out. By 14:00 the WAF had been identified: the Performance Team pulled live CPU data from a machine that "clearly showed the WAF was responsible", another engineer confirmed with strace, and another team saw WAF error logs — three independent signals converging. At 14:02 the team proposed a "global terminate", a built-in mechanism to disable a single component worldwide.

Mitigation was delayed by a dependency loop: Cloudflare uses its own products, and with its Access service down, engineers couldn't authenticate to the internal control panel or reach tools like Jira and the build system; they had to use a rarely used bypass. The global WAF kill executed at 14:07, and by 14:09 traffic and CPU were back to normal worldwide — 27 minutes from the change. The team then verified the fix in a single city with paying customers' traffic removed, running both negative tests ("was it really that change?") and positive tests (does the rollback work?), and re-enabled the WAF globally at 14:52.

The postmortem is exemplary for what it doesn't do: it doesn't stop at "an engineer wrote a bad regex". It lists contributing factors. The regular expression could backtrack enormously. A protection that would have limited regex CPU use had been removed by mistake during a WAF refactoring weeks earlier — ironically, a refactoring meant to make the WAF use less CPU. The regex engine had no complexity guarantees. The test suite couldn't detect excessive CPU consumption. The standard operating procedure allowed a non-emergency rule change to go global without a staged rollout (swe9). The rollback plan required running the complete WAF build twice. The first alert for the global traffic drop took too long to fire. The status page was updated too slowly. And the team had difficulty reaching its own systems. The remediations followed: re-introduce the CPU protection, inspect all 3,868 managed rules for excessive backtracking, add performance profiling for every rule to the test suite, switch to the re2 or Rust regex engine (both have run-time guarantees), stage rule rollouts like other software while keeping an emergency fast path, and fix emergency access to internal tools.

Every section of this lesson appears in it: synthetic checks for detection, independent signals converging on a diagnosis, profiling (CPU data, strace) to look inside the process, a kill switch for mitigation, careful confirmation before restoring, and a blameless, specific postmortem whose action items change the system. The lab reproduces the technical core: a toy service with a .*.*=.*; rule has a 6 ms median but a 175 ms p99, the trace waterfall of the slowest request shows the validation span taking 169 ms, and replacing the rule with an equivalent linear-time pattern brings p99 back to about 10 ms.

AI systems in production

LLM products fail in ways that ordinary dashboards miss: answers get worse without any error, costs double after a prompt change, latency grows because a model provider is rate-limiting, a retrieval index silently stops updating. Teams that catch these quickly treat quality and cost as first-class telemetry alongside RED: dashboards of tokens and cost per request by feature, time to first token, fallback and refusal rates, parse failures, feedback scores and online evaluation results, each broken down by model and prompt version, with alerts on sudden changes. Traces with retrieval, model and tool spans make individual bad answers debuggable ("which documents did it retrieve? which tool returned what?"). And the practices from the case study transfer directly: synthetic "canary prompts" run continuously from outside to detect total failures, kill switches to disable a feature or fall back to a simpler model, and blameless postmortems when a model or prompt rollout goes wrong.

Tools and knobs

Python: logging with a JSON formatter or structlog, contextvars for request IDs, the OpenTelemetry SDK with auto-instrumentation for your framework, HTTP client and database driver, Prometheus client libraries for metrics, and py-spy for live profiling. Infrastructure: an OpenTelemetry Collector for sampling and redaction, a metrics store (Prometheus-compatible), a trace backend, a log store, dashboards with deploy and flag-change annotations, synthetic checks from outside, SLO-based alerting, and a postmortem template with tracked action items.

Goal: instrument a toy service with the three signals and use them to find why its p99 latency is bad, then fix it and confirm with the same signal. Stdlib only, Python 3.12, about three seconds.

  1. Save the script as swe14_lab.py and run python swe14_lab.py.
  2. The service handles 150 requests. Each runs three spans — validate (a WAF-style regex scan over the query string), db.query and llm.rerank — logs a structured JSON line carrying a request ID set via contextvars, and records its duration. About 3% of requests carry a long, unusual query string.
  3. Before the fix, the RED summary shows a p50 around 6 ms but a p99 around 175 ms. The script then prints the waterfall of the slowest trace: validate takes about 169 ms of the 175, while the database and model spans take a few milliseconds each. It also prints one structured log line.
  4. After the fix — replacing .*.*=.*; with ^[^=]*=[^;]*;, which matches exactly the same strings (an equals sign followed later by a semicolon) without nested unbounded quantifiers — p99 drops to about 10 ms. Exact numbers vary by machine.

What it shows: the average would barely move (3% of requests are slow), the median doesn't move at all, and only the tail percentile exposes the problem; the trace waterfall turns "p99 is bad" into "this span, on these inputs"; and confirmation uses the same p99 that revealed the issue. That's the Cloudflare investigation in miniature.

"""swe14 lab: instrument a toy service with structured logs, RED metrics and trace spans, then use them to
find why p99 latency is bad — a backtracking regex, Cloudflare-2019 style — fix it, and measure again."""
import contextvars
import json
import random
import re
import statistics
import time
import uuid
from contextlib import contextmanager

request_id = contextvars.ContextVar("request_id", default="-")
spans: list[dict] = []
log_lines: list[str] = []

def log(level, msg, **fields):                        # structured: one JSON object per line, with the request ID
    log_lines.append(json.dumps({"level": level, "msg": msg, "request_id": request_id.get(), **fields}))

@contextmanager
def span(name, parent=None):                          # a minimal tracer: name, parent, start, duration
    start = time.perf_counter()
    rec = {"trace": request_id.get(), "name": name, "parent": parent, "start": start}
    try:
        yield name
    finally:
        rec["ms"] = (time.perf_counter() - start) * 1e3
        spans.append(rec)

SLOW_RULE = re.compile(r".*.*=.*;")                   # looks harmless; backtracks catastrophically on long inputs
FAST_RULE = re.compile(r"^[^=]*=[^;]*;")              # matches exactly the same strings, in linear time

def handle(query: str, rule) -> int:
    request_id.set(uuid.uuid4().hex[:8])
    with span("GET /search") as root:
        with span("validate", root):
            suspicious = bool(rule.search(query))    # WAF-style scan: try every position
        if suspicious:
            log("warn", "blocked", reason="rule matched")
            return 403
        with span("db.query", root):
            time.sleep(random.uniform(0.001, 0.003))
        with span("llm.rerank", root):
            time.sleep(random.uniform(0.002, 0.004))
    log("info", "ok", status=200)
    return 200

def run(rule, n=150, seed=7):
    random.seed(seed); spans.clear(); log_lines.clear()
    durations, errors = [], 0
    for i in range(n):
        q = "x=" + "x" * 700 if i % 30 == 0 else f"q={i}&lang=en"   # ~3% of requests carry a long, odd query string
        t = time.perf_counter()
        status = handle(q, rule)
        durations.append((time.perf_counter() - t) * 1e3)
        errors += status >= 500
    qs = statistics.quantiles(durations, n=100)
    print(f"  RED: rate={n} req, errors={errors}, duration p50={qs[49]:.1f} ms  p95={qs[94]:.1f} ms  p99={qs[98]:.1f} ms  max={max(durations):.1f} ms")
    return durations

def waterfall(trace_id):
    rows = [s for s in spans if s["trace"] == trace_id]
    t0 = min(s["start"] for s in rows); total = max(s["start"] - t0 + s["ms"] / 1e3 for s in rows) * 1e3
    for s in sorted(rows, key=lambda s: s["start"]):
        off = (s["start"] - t0) * 1e3
        bar = " " * int(40 * off / total) + "#" * max(1, int(40 * s["ms"] / total))
        print(f"  {s['name']:12} {s['ms']:8.1f} ms |{bar}")

print("before the fix")
run(SLOW_RULE)
slowest = max((s for s in spans if s["name"] == "GET /search"), key=lambda s: s["ms"])
print(f"  slowest trace {slowest['trace']}:"); waterfall(slowest["trace"])

At 14:05, p99 latency of the checkout API jumps from 300 ms to 4 s; error rate rises from 0.1% to 3% (timeouts). p50 barely moves. A deploy of the recommendations service went out at 14:00. CPU on checkout hosts is normal. Walk through what you do.

Answer

Read the signals: p99 up and p50 flat means a subset of requests is slow — a slow dependency or a code path, not general overload (normal CPU agrees). Timeouts suggest waiting on something.

  1. Mitigate: the recommendations deploy at 14:00 is the prime suspect. If checkout calls recommendations, roll it back or disable the recommendations widget via its flag — cheap and reversible — and watch p99.
  2. Confirm with traces: filter slow checkout traces after 14:05 and compare with fast ones; see which span dominates. If it's the recommendations call taking ~4 s, that matches a client timeout set too high.
  3. Explain the errors with USE: slow calls hold worker threads and connections; the pool saturates (utilisation near 100%, requests waiting), so unrelated requests queue and time out — the failure spreads beyond the slow path.
  4. Root-cause the deploy afterwards (a new query without an index, a cache disabled) — with a flame graph or traces from the recommendations service.

Action items for the postmortem: checkout's call to a non-critical dependency needs a tight timeout (for example 200 ms), a circuit breaker and a fallback (render without recommendations); a canary for the recommendations service that watches its consumers' latency (swe9); an alert on p99 and error-budget burn, not just averages. The deeper lesson: a non-critical dependency took down a critical path — that's the design flaw to fix.
