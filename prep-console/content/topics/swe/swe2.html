A payments team inherits a Checkout class. Its constructor reads an API key from the environment and creates a client for the payment provider; its pay() method calls the provider over the network. To test a discount rule, you need a network connection, a sandbox account and patience: each test takes two seconds and fails whenever the sandbox is down. Someone patches the provider module in tests with a mocking library; the patch path is a string like "checkout.stripe.Client", and when the import is moved during a refactor, every test silently patches the wrong thing and starts hitting the network again.

A second team wanted a logged, retrying version of their EmailNotifier, so they subclassed it: RetryingEmailNotifier. Then SMS arrived, so SmsNotifier and RetryingSmsNotifier. Then logging: LoggingRetryingEmailNotifier… Six classes for two channels and two features, and a bug fix to retry logic has to be made twice. Meanwhile someone subclassed Python's dict to count writes to a cache, tested cache[k] = v, shipped it — and the dashboard undercounted by 90%, because most writes went through update(), which never calls the overridden method.

All three stories are about how objects get their collaborators and how code is reused. Object-oriented languages offer two reuse mechanisms — inheritance (become a kind of the other class) and composition (hold an instance of the other class and call it) — and two ways for an object to get what it needs: build it itself, or be handed it. The choices look like style, but they decide whether code can be tested in milliseconds, whether a vendor can be swapped in an afternoon, and whether a change in one class breaks another you've never read.

This lesson traces the fragile base class problem in real Python behaviour, builds the same feature both ways, then covers interfaces (Protocols and abstract base classes), dependency injection and the composition root, and the anti-patterns — service locators and global state. The real-world case is the Toyota electronic throttle trial, where an expert witness counted more than 11,000 global variables in one car's engine-control code. The lab builds a cached, retrying LLM client whose tests run with no network and no sleeping.

The analogy: a band versus a clone

You want a band that plays jazz. Inheritance is like cloning an existing rock guitarist and then retraining the clone for jazz: you get all their skills for free, but also every habit, and if the original guitarist's technique changes (say you swap which guitar all clones are born with), every clone changes too. You can't make a clone of two musicians at once. Composition is hiring: the band has a guitarist, a bassist and a drummer. Each musician is replaceable as long as they can play the parts — the "interface". A sick drummer is replaced by a substitute for one night. And the band leader doesn't train the musicians; an agent sends them — the band just says what roles it needs. That last idea, being handed your collaborators instead of creating them, is dependency injection.

The analogy breaks in one direction: real musicians adapt on their own when the substitute plays differently. Objects don't. A substitute object must honour exactly the contract the caller relies on — the Liskov Substitution Principle from swe1 — or the swap introduces bugs.

Two ways to reuse code

Inheritance means a subclass acquires its parent's methods and attributes and may override some of them. It's called white-box reuse because the subclass sees and depends on the parent's internals. Composition means an object holds a reference to another object and delegates — forwards — work to it through its public methods. It's called black-box reuse, because the holder knows only the other object's interface.

Two ways to get a collaborator

An object that needs a database client, a clock or a model provider can construct it (self.db = Postgres(os.environ["DB_URL"])), look it up in a global place (registry.get("db")), or be given it (def __init__(self, db)). Being given it is dependency injection (DI). The class then depends only on the interface — the set of operations it calls — and whoever builds it decides which implementation to supply: the real database in production, an in-memory fake in tests.

Somebody still has to build the real objects. Good designs do that in one place, near the program's entry point, called the composition root. Everything else in the codebase receives what it needs and never constructs infrastructure itself.

Why this matters more, not less, in AI systems

An application built around a large language model (LLM) has an unusual number of collaborators that are slow, cost money per call, and give different answers each time: the model provider, an embedding service, a vector database, a reranker. It also depends heavily on time (rate limits, cache expiry, retry backoff) and randomness (sampling). If each class constructs its own provider client from an environment variable, every test either calls a real model — slow, costly and non-deterministic — or relies on fragile patching. If instead the provider arrives through a small interface, a test can hand in a fake that returns canned text instantly, including the malformed outputs your parser must survive, and switching providers or models becomes a change to one wiring function. Keep this picture in mind: the lab builds exactly that.

The rest of the lesson makes each of those ideas precise, traces where they break, and shows the patterns that combine them — wrappers that add behaviour to any implementation of an interface, and the handful of dependencies (time, randomness, network, model calls) that are always worth injecting.

1. What inheritance really couples you to

When class B inherits from class A, every B object is an A object with some methods replaced. That gives you three things at once: B gets A's code (reuse), B can be used wherever A is expected (substitutability), and B is bound to A's implementation. The third is the one people forget. B depends not only on A's public method signatures but on A's self-use — which of A's methods call which others internally. If B overrides a method that A's other methods call, B's override changes A's behaviour; if A's other methods don't call it, B's override is bypassed. Either way, B's correctness depends on facts about A's internals that A's documentation rarely states and A's authors may change.

That's the fragile base class problem, and you can see it in plain Python 3.12. Suppose you want a dictionary that counts how many writes it receives, to measure a cache:

class CountingDict(dict):
    def __init__(self, *a, **k):
        super().__init__(*a, **k)
        self.writes = 0
    def __setitem__(self, key, value):
        self.writes += 1
        super().__setitem__(key, value)

d = CountingDict()
d["a"] = 1                      # goes through __setitem__: writes = 1
d.update({"b": 2, "c": 3})      # CPython's dict.update writes directly
d.setdefault("d", 4)            # so does setdefault
print(d.writes, len(d))         # 1 4   ← four keys, one counted write

Trace it. The first line calls CountingDict.__setitem__, which counts and delegates — correct. update is inherited from dict; CPython implements it in C and inserts entries directly into the hash table without looking up __setitem__ on the subclass. Same for setdefault. Three of four writes are invisible. Nothing errored; the dashboard is simply wrong. The same thing happens with list: override append to count, and extend and += bypass it.

The standard library knows this, which is why collections.UserDict and UserList exist: they are written in Python on top of a wrapped dict/list, and their update and setdefault are implemented by calling self[key] = value. A UserDict subclass with the same override counts all four writes. Notice what that means: whether your subclass works depends on a documented-by-convention detail of the parent's implementation. Java programmers know the mirror-image example from Effective Java: an InstrumentedHashSet that counts additions in both add and addAll double-counts, because HashSet.addAll happens to call add. Too little self-use in one language, too much in the other; the root cause is the same.

Inheritance has two further costs. It fixes a single taxonomy at design time: a class has one parent chain, so a FlyingRobotDog can't cleanly be both a Robot and a Dog (Python's multiple inheritance allows it, but the method resolution order from py6 then decides which override wins, which is one more implicit rule to get right). And it can't change at run time: an object is born a RetryingEmailNotifier and stays one.

2. The same feature with composition

Now build the counter by holding a dict instead of being one:

class CountingStore:
    def __init__(self, inner: dict | None = None):
        self._d = {} if inner is None else inner
        self.writes = 0
    def set(self, key, value):
        self.writes += 1
        self._d[key] = value
    def set_many(self, items: dict):
        for k, v in items.items():
            self.set(k, v)          # routed through the one counting path
    def get(self, key, default=None):
        return self._d.get(key, default)
    def __len__(self):
        return len(self._d)

CountingStore exposes only the operations its callers need, and every write goes through set, so the count is right by construction. It depends on the dict's public interface only; if CPython changed how dict.update works tomorrow, nothing here would change. The costs are also visible: you write small forwarding methods (get, __len__) for anything callers need, and the object is no longer usable where a real dict is expected. That second point is often a feature — callers can't bypass your rule by calling a dict method you forgot about — but when you truly need drop-in compatibility, inherit from the base class designed for extension (UserDict, collections.abc.MutableMapping) rather than from the optimised concrete one.

Rule of thumb: inherit interfaces freely, inherit implementation reluctantly. Implementation inheritance is still the right tool when the relationship is a genuine, substitutable is-a, the base class is designed for extension (documented hooks, template methods), and you own it or it is a framework hook such as unittest.TestCase, whose authors promise which methods you may override and when they're called.

3. Subclass explosion versus wrappers

The notification story from the introduction shows the combinatorial cost. With two channels (email, SMS) and two optional features (retry, logging), inheritance needs a class per combination: 2 channels × 4 feature combinations = 8 classes, and a third feature doubles it to 16. Each feature's logic is duplicated across channel subclasses.

Composition handles it with wrappers: objects that implement the same interface as the thing they wrap, add their behaviour, and delegate. This is the object form of the Decorator pattern (swe3), and the same idea as Python's function decorators from py4:

from typing import Protocol

class Notifier(Protocol):
    def send(self, to: str, body: str) -> None: ...

class EmailNotifier:
    def __init__(self, smtp): self.smtp = smtp
    def send(self, to, body): self.smtp.sendmail("noreply@shop.example", to, body)

class Retrying:
    def __init__(self, inner: Notifier, attempts: int = 3):
        self.inner, self.attempts = inner, attempts
    def send(self, to, body):
        for i in range(self.attempts):
            try:
                return self.inner.send(to, body)
            except ConnectionError:
                if i == self.attempts - 1:
                    raise

class Logging:
    def __init__(self, inner: Notifier, log): self.inner, self.log = inner, log
    def send(self, to, body):
        self.log.info("sending to %s", to)
        self.inner.send(to, body)

notifier = Logging(Retrying(EmailNotifier(smtp)), log)   # stack chosen at wiring time

Now it's channels plus features: 2 + 2 classes, and each feature is written and tested once against a fake. The stack is data, assembled where the application is wired, and can differ per environment (no retries in tests, extra logging in staging).

4. Interfaces: saying what you depend on

An interface is the set of operations — with their contracts — that a caller relies on. Some languages make it a keyword; Python gives you two ways to write one down.

Abstract base classes (the abc module) are nominal: a class satisfies the interface only if it inherits from the ABC (or is registered with it). You get isinstance checks at run time, an error at instantiation if an abstract method is missing, and a place to put shared helper methods:

from abc import ABC, abstractmethod

class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, cents: int, token: str) -> str: ...     # returns a charge id

Protocols (typing.Protocol) are structural: any class with matching method signatures satisfies the interface, whatever it inherits from. The type checker verifies it; nothing needs to inherit. That suits dependency injection especially well, because test fakes and third-party classes fit without modification, and the interface can live next to the code that uses it (the dependency inversion principle from swe1 says the high-level side should own it):

class PaymentGateway(Protocol):
    def charge(self, cents: int, token: str) -> str: ...

Rule of thumb: Protocols for the dependencies your code receives; ABCs when you are publishing an extension point for others to subclass, or need run-time checks.

5. Dependency injection, step by step

Here is the Checkout from the introduction, with its dependencies created inside:

import os, time

class Checkout:
    def __init__(self):
        self.gateway = StripeGateway(api_key=os.environ["STRIPE_KEY"])   # network
    def pay(self, cart, token):
        if time.time() > cart.expires_at:                                  # real clock
            raise CartExpired()
        return self.gateway.charge(cart.total_cents(), token)

Three hidden dependencies: an environment variable, a network service and the wall clock. To test "an expired cart is rejected" you must fake time, and to test "a valid cart is charged the right amount" you must either hit the payment sandbox or patch the StripeGateway name in this module. Patching works, but it couples the test to where the name is imported, which is an implementation detail.

Constructor injection makes every dependency a parameter:

from typing import Callable

class Checkout:
    def __init__(self, gateway: PaymentGateway, clock: Callable[[], float]):
        self.gateway, self.clock = gateway, clock
    def pay(self, cart, token):
        if self.clock() > cart.expires_at:
            raise CartExpired()
        return self.gateway.charge(cart.total_cents(), token)

# test: no network, no real time
class FakeGateway:
    def __init__(self): self.charges = []
    def charge(self, cents, token):
        self.charges.append(cents); return "ch_test_1"

gw = FakeGateway()
Checkout(gw, clock=lambda: 1_000.0).pay(Cart(total=4999, expires_at=2_000.0), "tok")
assert gw.charges == [4999]

What changed: the constructor signature now documents exactly what Checkout needs; the test controls time by passing a function; and the fake is a five-line class with no mocking library. A function is a perfectly good dependency — clock: Callable[[], float] is an interface with one operation. Two other forms exist and occasionally help: setter injection (assign an optional collaborator after construction — useful for optional hooks, dangerous because the object may be used before it's set) and method injection (pass the dependency to the one method that needs it, e.g. render(report, formatter), when it varies per call). Constructor injection is the default because a required dependency can't be forgotten.

6. The composition root

If nothing constructs its own infrastructure, something must. The composition root is that one place, at the entry point:

def main():
    settings = Settings.from_env()                      # read environment once
    gateway = StripeGateway(api_key=settings.stripe_key)
    if settings.payments_retry:
        gateway = RetryingGateway(gateway, attempts=3)
    checkout = Checkout(gateway, clock=time.time)
    app = build_app(checkout=checkout, orders=PostgresOrders(settings.db_url))
    app.run()

This buys four things. Configuration is read in one place, so there are no scattered os.environ lookups deep in the code. Swapping an implementation — a new payment provider, an in-memory store for local development — is a change to this function only. The dependency graph of the whole application is readable top to bottom. And tests build their own small graphs the same way, with fakes, without touching global state.

7. What to inject — the sources of non-determinism

Not everything should be injected. A tax calculator, a formatter or a value object is pure and fast: tests should use the real thing, and injecting it adds indirection for nothing. Inject collaborators that are slow, external, non-deterministic or likely to vary:

  • Time — time.time, datetime.now, time.sleep. Anything with timeouts, expiry, rate limits or backoff is untestable without controlling the clock (and waiting for real sleeps makes tests slow).
  • Randomness — pass a random.Random(seed) instance rather than calling module-level random, so sampling and jitter are reproducible.
  • I/O — databases, file systems, HTTP clients, message queues.
  • Model providers — an LLM or embedding client is slow, costs money per call and is non-deterministic. Behind a small ChatModel protocol, a test can use a fake that returns canned text.
  • Configuration and feature flags — pass values or a flag reader in rather than reading globals, so tests can exercise both branches.

The lab puts these together: a CachedModel wrapper with a time-to-live and an injected clock, and a RetryingModel wrapper with exponential backoff and an injected sleep. The tests advance a fake clock by 59 and then 61 seconds to check expiry, and record the sleep durations (0.5 s, then 1 s) instead of sleeping, so the whole suite runs in milliseconds.

8. Anti-patterns: service locators and global state

A service locator is a global registry that code pulls dependencies from: gateway = Registry.get("payments") inside pay(). It looks like decoupling — the class no longer names StripeGateway — but the dependency is still there, now hidden in a method body. You can't tell from the constructor what the class needs; a test must remember to populate the registry and reset it afterwards; and two tests that populate it differently can interfere when run in the same process. Martin Fowler's 2004 article that named dependency injection compared the two and concluded locators are acceptable only where you can't control construction; Mark Seemann later argued they're an anti-pattern outright.

Global mutable state is the extreme form: any function can read or write a module-level variable, so every reader is coupled to every writer, invisibly. Python's module-level singletons (db = connect() at import time, a mutable CONFIG dict) are the common version. The fix is the same as for everything in this lesson: make the dependency an argument, build it once in the composition root, and pass it down. The production section below shows what global coupling looks like at its worst.

Why "composition over inheritance" is a design-for-change argument

The Gang of Four's 1994 Design Patterns book stated the principle as "favour object composition over class inheritance", and its reasoning is about change, not taste. Inheritance is decided at compile time and exposes a parent's implementation to its subclasses, so the subclass is bound to decisions the parent's authors will want to change. Composition is decided at run time and goes through interfaces, so each object's implementation can change, and objects can be recombined, without the others noticing. The deeper claim is that the number of ways things can vary should determine the structure: one axis of variation fits a hierarchy; several independent axes (channel, retry policy, logging, rate limit) should each be a separate composable object.

Designing a class for inheritance, if you must

When you publish a class others will subclass, the self-use contract becomes part of your public API. Joshua Bloch's rule is "design and document for inheritance or else prohibit it". Designing for it means: document which overridable methods each public method calls and when (Java's docs call this "implementation requirements"); provide explicit, narrow hooks — the Template Method pattern, where a base class's algorithm calls a few named, overridable steps — rather than letting subclasses override arbitrary methods; never call overridable methods from a constructor (the subclass's override would run before the subclass has initialised its own fields); and test the class by writing subclasses. Python's typing.final decorator marks a class or method as not to be overridden, which type checkers enforce, and is a reasonable default for classes not designed for extension.

Mixins, multiple inheritance and the MRO

Python's multiple inheritance supports mixins: small classes that add one capability (JsonSerializableMixin) and are combined in a class statement. Mixins can work well when each is stateless, depends only on a documented interface of the host, and cooperates via super(). But the C3 linearisation that computes the method resolution order means a method call's target depends on the order bases are listed and on every class in the hierarchy — an implicit, global rule. Mixin stacks that override the same method and call super() form a chain whose order you can only learn by printing Class.__mro__. Composition expresses the same stacking explicitly (Logging(Retrying(x))) where the order is visible at the call site.

Dependency injection versus patching

Python lets tests replace any name at run time with unittest.mock.patch, so some argue injection is unnecessary. Patching is valuable for legacy code you can't restructure yet, but it has three structural costs. It targets where a name is looked up, not the dependency itself — patch payments.stripe.Client while the code imported it as from stripe import Client into another module, and the patch misses; a refactor that moves an import silently disables the test double. It hides the dependency from the reader, just like a locator. And it tends to spread: once patching is normal, tests patch internal helpers too, freezing implementation details into the test suite. Injection makes the seam part of the design: the dependency is visible in the signature, and the substitution survives refactoring. A good working rule is to patch only at the boundary of code you don't control, and to inject everything you design.

Lifetimes and scopes

Once objects are wired in a composition root, you must decide how long each lives. Singleton (one per process): connection pools, HTTP clients, model clients — expensive to create, safe to share if thread-safe. Per-request: a database session or transaction, a request-scoped logger carrying a request ID, a user context. Transient: a new instance per use. The classic bug is a captive dependency: a singleton that holds a per-request object — a service built once at start-up that stores the first request's database session and then uses it for every later request, leaking data across users or failing when the session closes. Frameworks encode scopes (FastAPI's Depends resolves per request; yield dependencies clean up after the response), and in hand-wired code the rule is simply that a longer-lived object may only hold shorter-lived ones through a factory it calls each time.

Adapters at the edges, and the anti-corruption idea

When a dependency's API doesn't match the interface your code wants — a vendor SDK with twelve parameters and its own exception types — write an adapter: a small class that implements your interface by translating calls. The adapter is the only code that imports the vendor SDK, translates vendor exceptions into your own (ProviderTimeout, RateLimited), and converts vendor data types into yours. This keeps vendor concepts from leaking through the codebase and makes switching vendors a matter of writing one new adapter that passes the same contract tests. For LLM applications this matters a great deal: provider SDKs change monthly, and an adapter layer means the application's prompt logic, retry policy and evaluation code never import a provider package directly.

What bad dependency structure costs in production teams

The symptoms are consistent across codebases. Tests that need the world: a unit test run requires a database container, network access and environment variables, so the suite takes minutes, is run rarely, and fails for reasons unrelated to the change. Patch-heavy tests that break whenever an import moves, and pass silently when a patch target goes stale. Vendor lock-in by accident: a provider SDK imported in forty files, so evaluating a second provider is a quarter-long project. Captive dependencies causing data leaks between requests. And fear of change around base classes with dozens of subclasses across teams, where no one can predict which override depends on which internal call. The measurements that expose these are test-suite runtime and flake rate, the count of files importing each vendor package, and fan-in on base classes.

Case: global state in the Toyota electronic throttle trial

Between 2009 and 2011, reports of unintended acceleration in Toyota vehicles led to recalls and to a review by NASA engineers for the US road-safety regulator, NHTSA. NASA's 2011 study did not find an electronic cause, though it did not rule one out. In October 2013, in Bookout v. Toyota, an Oklahoma jury found Toyota liable for a fatal 2007 crash, after testimony from embedded-software expert Michael Barr, whose team had spent many months reviewing the engine-control source code. His trial slides are public, and several of his findings are about exactly this lesson's subject.

Barr reported that the 2005 Camry's engine-control code had more than 11,000 global variables — a figure first counted by NASA — and presented the count explicitly as a metric of "tangledness": every global is shared state that any task or function can read and write, so any function's behaviour can depend on any other's. He reported 67 functions with a cyclomatic complexity above 50, a common threshold for "untestable" (cyclomatic complexity counts independent paths through a function; above about 50, covering them all with tests is impractical), and a throttle-angle function scoring over 100. He described how many fail-safes and much of the throttle logic ran inside a single operating-system task, so if that one task died, the fail-safes it hosted died with it — a failure of isolation. The expert testimony was contested and courts, not engineers, decided liability; what matters here is the engineering vocabulary. The case is often cited because it shows at full scale what hidden coupling does: with thousands of globals, you cannot reason locally about any function, and you cannot test a unit in isolation because there are no units, only one entangled state space.

The same principles apply to a Python service. Module-level mutable state — a global cache dict, a mutable settings object, a lazily-initialised client stored in a module variable — creates exactly this coupling at smaller scale, and makes tests order-dependent when one test mutates it. Injecting such state from a composition root turns it back into ordinary, visible dependencies.

ML and LLM systems

AI services have more non-deterministic dependencies than most: model providers, vector databases, rerankers, tokenizers, clocks for rate limits and caches, and random seeds for sampling. Teams that inject them get four concrete benefits. Fast deterministic tests with fake models returning canned outputs, including malformed ones to test parsers. Record-and-replay: an adapter that records real provider responses to files once, then replays them in continuous integration (CI), so integration tests are realistic without cost or flakiness. Provider and model switching behind a flag in the composition root, which is how a new model is rolled out to a percentage of traffic (swe9 covers rollouts). And consistent cross-cutting policy — retries with backoff, timeouts, token accounting, caching — written once as wrappers around any provider rather than repeated per call site.

Tools and knobs

Use typing.Protocol plus mypy or pyright to check that adapters and fakes match the interfaces. Keep a single composition root per entry point (web app, worker, CLI). In FastAPI, use Depends for per-request resources and app.dependency_overrides in tests; in pytest, use fixtures to build test graphs. Add an import-linter contract so only the adapter package may import each vendor SDK. Mark classes not designed for extension with @typing.final. And watch for the smell of over-injection: a constructor with eight parameters usually means the class has more than one responsibility (swe1), not that it needs a container.

import time
import unittest
from typing import Callable, Protocol


class ChatModel(Protocol):
    def complete(self, prompt: str) -> str: ...


class CachedModel:
    """Wraps any ChatModel; answers repeated prompts from memory for ttl seconds."""
    def __init__(self, inner: ChatModel, ttl: float, clock: Callable[[], float] = time.monotonic):
        self.inner, self.ttl, self.clock = inner, ttl, clock
        self._cache: dict[str, tuple[float, str]] = {}

    def complete(self, prompt: str) -> str:
        hit = self._cache.get(prompt)
        if hit and self.clock() - hit[0] < self.ttl:
            return hit[1]
        answer = self.inner.complete(prompt)
        self._cache[prompt] = (self.clock(), answer)
        return answer


class RetryingModel:
    """Wraps any ChatModel; retries transient errors, sleeping through an injected function."""
    def __init__(self, inner: ChatModel, attempts: int, sleep: Callable[[float], None] = time.sleep):
        self.inner, self.attempts, self.sleep = inner, attempts, sleep

    def complete(self, prompt: str) -> str:
        for i in range(self.attempts):
            try:
                return self.inner.complete(prompt)
            except TimeoutError:
                if i == self.attempts - 1:
                    raise
                self.sleep(0.5 * 2 ** i)          # 0.5 s, 1 s, 2 s ...


# ---------- test doubles: plain classes, no mocking library ----------
class FakeModel:
    def __init__(self, failures: int = 0):
        self.calls, self.failures = 0, failures
    def complete(self, prompt: str) -> str:
        self.calls += 1
        if self.calls <= self.failures:
            raise TimeoutError("provider timed out")
        return f"answer#{self.calls} to {prompt!r}"


class FakeClock:
    def __init__(self): self.now = 1000.0
    def __call__(self) -> float: return self.now


class Tests(unittest.TestCase):
    def test_cache_hit_then_expiry(self):
        model, clock = FakeModel(), FakeClock()
        cached = CachedModel(model, ttl=60, clock=clock)
        a1 = cached.complete("capital of France?")
        clock.now += 59                                   # still fresh
        self.assertEqual(cached.complete("capital of France?"), a1)
        clock.now += 2                                    # 61 s old: expired
        self.assertNotEqual(cached.complete("capital of France?"), a1)
        self.assertEqual(model.calls, 2)

    def test_retry_backoff_without_sleeping(self):
        slept: list[float] = []
        model = FakeModel(failures=2)
        r = RetryingModel(model, attempts=3, sleep=slept.append)
        self.assertTrue(r.complete("hi").startswith("answer#3"))
        self.assertEqual(slept, [0.5, 1.0])

Design it

You are building notifications: email now, SMS next quarter, Slack maybe later. A teammate proposes class Notifier with subclasses EmailNotifier, SmsNotifier, and then RetryingEmailNotifier, RetryingSmsNotifier, LoggingRetryingEmailNotifier… Each class also constructs its own SMTP or SMS client from environment variables. What is wrong, and what do you propose?

Answer

Two problems. First, subclass explosion: every orthogonal feature (retry, logging, rate limiting) multiplies the class count — channels × feature combinations — and each feature's logic is duplicated per channel. Inheritance is being used to combine independent behaviours, which it does badly. Second, hidden dependencies: each class builds its own client from the environment, so nothing can be tested without real credentials and network, and configuration is scattered.

Proposal: composition with wrappers, plus constructor injection. One small interface, a Notifier Protocol with send(to, body). Channel classes implement it and receive their client: EmailNotifier(smtp_client), SmsNotifier(sms_client). Cross-cutting behaviour wraps any notifier and is itself a notifier:

notifier = Logging(Retrying(SmsNotifier(sms_client), attempts=3), log)

Channels + features instead of channels × features. Each wrapper is unit-tested once against a fake notifier with an injected sleep. Clients and the stack are built in the composition root from configuration, so a new channel is one class plus one line of wiring, and calling code only knows Notifier. Name the pattern — Decorator — and note Python function decorators are the same idea for functions. Mention that wrapper order matters (retry inside or outside rate limiting) and should be tested as assembled.
