Three engineers are each stuck on a problem they think is unique. The first has a checkout function with an if chain for "regular", "member", "black friday" and "clearance" pricing, and marketing wants a new rule every month. The second has order-status checks — if order.status == "paid" and not order.shipped — scattered across twelve files, and last week a cancelled order was shipped because one of them was wrong. The third needs "undo" in a document editor and is considering saving a full copy of the document after every keystroke.

None of these problems is new. Each has been solved thousands of times, and the solutions have names: Strategy for the pricing rules, State for the order lifecycle, Command for undo. A design pattern is exactly that — a named, proven solution to a recurring design problem, with known costs. The names were popularised in 1994 by the "Gang of Four" book Design Patterns, which catalogued 23 of them, borrowing the idea from the architect Christopher Alexander's pattern language for buildings.

The value of knowing patterns is not reciting diagrams. It is recognition and vocabulary. Recognition: when you see status ifs spreading, you know a state machine is the cure, and you know its pitfalls before you hit them. Vocabulary: "put an adapter in front of the vendor SDK and a caching proxy in front of that" is a complete design communicated in one sentence to anyone who knows the words. Interviewers use patterns the same way — not to check memorisation, but to see whether you recognise a problem and know its standard solution and when it's overkill.

This lesson covers the dozen patterns that matter in practice, each introduced by its problem, traced in Python, and paired with its costs, including how Python's first-class functions shrink many of them to a few lines. It explains why Singleton went from pattern to anti-pattern, using Google's well-known testing-blog case, lists the smells reviewers name, and shows where each pattern appears in LLM and ML systems — provider adapters, agent tool calls as commands, workflows as state machines. The lab implements State, Command and Observer and tests them.

The analogy: recipes and techniques

A cook doesn't invent how to thicken a sauce each time; they know "make a roux" or "reduce it". Those technique names carry a whole method plus its trade-offs (a roux clouds a clear sauce; reducing concentrates salt). A recipe is specific; a technique is reusable across recipes. Design patterns are techniques: "Strategy" isn't a piece of code you copy, it's a way of arranging code that works in pricing, compression, retrieval and a hundred other places. And like techniques, they're used when the dish needs them — nobody makes a roux for a salad.

Where the analogy breaks: cooking techniques are stable, but patterns depend on the language. Several classic patterns exist mainly to work around missing language features; in Python, with first-class functions, generators and modules, some of them shrink to a line or disappear.

How a pattern is described

Every pattern has four parts. The problem (and its context): what keeps going wrong. The forces: the competing pressures (flexibility versus simplicity, speed versus safety). The solution: an arrangement of objects or functions and how they collaborate. The consequences: what you gain and what you pay. When you use a pattern in an interview, say all four briefly — "the pricing rules change monthly (problem), so I'd use Strategy (solution); the cost is one more indirection, worth it because variants keep arriving (consequences)".

The three families

The Gang of Four grouped patterns by what they organise:

  • Creational — how objects get created: Factory, Builder, Singleton.
  • Structural — how objects are combined: Adapter, Decorator, Proxy, Facade, Composite.
  • Behavioural — how objects divide work and communicate: Strategy, Observer, Command, State, Template Method, Chain of Responsibility, Iterator.

The structural ones are the easiest to confuse because they all wrap something. The distinguishing question is always: what happens to the interface?

Which patterns actually matter

The Gang-of-Four catalogue has 23 patterns, and several (Flyweight, Interpreter, Memento, Visitor, Bridge) come up rarely in application code. The dozen this lesson covers are the ones you will meet weekly in real services and in interviews: Strategy, Factory and Builder for choosing and constructing things; Adapter, Decorator, Proxy, Facade and Composite for combining them; and Observer, Command, State, Template Method, Chain of Responsibility and Iterator for dividing up behaviour. Add Singleton, which you need to know mainly so you can explain why to avoid it.

In an interview, a good pattern answer has three beats. Name the problem you see in the requirements ("new pricing rules arrive monthly"), name the pattern and sketch its shape in a sentence ("a strategy per rule in a registry keyed by name"), and state the consequence and the alternative ("one more indirection; if there were only two stable rules, an if statement would be clearer"). The third beat is what separates engineers who apply patterns from those who collect them.

The one rule that matters more than any individual pattern: start from the problem, not the pattern. "Pricing rules change every month" leads to Strategy. "I read about Strategy, where can I use it?" leads to code that's harder to read for no benefit.

1. Strategy: interchangeable algorithms

Problem. One step of a process has several variants, chosen at run time, and new variants keep arriving: pricing rules, compression codecs, retry policies, ranking functions. Written as an if/elif chain, every new variant edits tested code and the variants' logic is tangled together (the Open/Closed problem from swe1).

Solution. Give each variant the same interface and let the caller hold one. In Java that means an interface and a class per variant. In Python, where functions are values (py3), a strategy is usually just a function:

from decimal import Decimal

def regular(total: Decimal) -> Decimal:      return total
def member(total: Decimal) -> Decimal:       return total * Decimal("0.95")
def black_friday(total: Decimal) -> Decimal: return max(total - Decimal("20"), total * Decimal("0.7"))

PRICING = {"regular": regular, "member": member, "black_friday": black_friday}

def checkout_total(cart_total: Decimal, rule: str) -> Decimal:
    return PRICING[rule](cart_total).quantize(Decimal("0.01"))

checkout_total(Decimal("100"), "black_friday")   # max(80, 70) = 80.00

When a strategy needs configuration — a discount percentage read from a database — use a closure or functools.partial (partial(percent_off, pct=Decimal("0.1"))), or a small class with a __call__ method. The registry dictionary doubles as a factory: it maps a name from configuration or an experiment bucket to the implementation.

Consequences. New rules are new functions plus one registry line; each is unit-tested alone. The cost is one indirection. With two stable variants, an if is clearer. In ML systems, Strategy is everywhere: the loss function, the retrieval method, the reranker and the decoding method (greedy, top-k, nucleus) are all strategies chosen by configuration.

2. Factory and Builder: controlling construction

Factory. Problem: code must create one of several classes depending on input, and that decision is repeated wherever objects are built. Solution: put the decision in one function (a factory function) or a classmethod (Parser.for_format("json")). Python's alternative constructors like datetime.fromisoformat and dict.fromkeys are factory methods. A typical AI example:

def make_chat_model(cfg: ModelConfig) -> ChatModel:
    match cfg.provider:
        case "anthropic": return AnthropicAdapter(cfg.model, cfg.timeout_s)
        case "openai":    return OpenAIAdapter(cfg.model, cfg.timeout_s)
        case "fake":      return FakeModel(cfg.canned_responses)
        case _:           raise ValueError(f"unknown provider {cfg.provider!r}")

This is the only match on provider in the codebase; everything else receives a ChatModel. It usually lives in or near the composition root (swe2).

Builder. Problem: an object has many optional parts and must be valid when finished — an SQL query, an HTTP request, a prompt with system text, few-shot examples, retrieved context and output-format instructions. A constructor with twelve optional arguments is error-prone. Solution: a builder object with chainable methods and a final build() that validates:

prompt = (PromptBuilder(system="You are a support assistant.")
          .with_examples(few_shots[:3])
          .with_context(retrieved_chunks, max_tokens=2_000)
          .require_json(schema=Answer)
          .build())            # raises if context overflows the budget

In Python, keyword arguments with defaults and dataclasses remove most of the need for Builder; reach for it when construction has steps, validation across fields, or several representations (the same prompt rendered for two providers' message formats).

3. Adapter, Facade, Proxy, Decorator, Composite

Adapter — problem: a class you can't change (a vendor SDK, a legacy module) has the wrong interface for your code. Solution: a wrapper implementing your interface by translating calls, arguments, return types and exceptions. It's the standard way to isolate vendors, and swe2 showed why it belongs at every external edge.

class AnthropicAdapter:                       # implements our ChatModel protocol
    def __init__(self, client, model: str):
        self.client, self.model = client, model
    def complete(self, prompt: str) -> str:
        try:
            r = self.client.messages.create(model=self.model, max_tokens=1024,
                                            messages=[{"role": "user", "content": prompt}])
        except TimeoutError as e:
            raise ProviderTimeout(str(e)) from e      # vendor error → our error type
        return r.content[0].text

Facade — problem: callers must coordinate several objects in the right order to do one common thing (reserve stock, charge a card, create a shipment). Solution: one object with a simple method (OrderFacade.place(cart, card)) that does the coordination. It reduces coupling from "every caller knows five subsystems" to "every caller knows one facade". Risk: it grows into a god object if every new operation is added to it.

Proxy — problem: access to an object must be controlled without the caller knowing. Solution: a stand-in with the same interface. Kinds: a virtual proxy delays creating an expensive object until first use (load a 4 GB model only when the first request arrives); a caching proxy returns stored results; a protection proxy checks permissions; a remote proxy makes a network service look like a local object (every RPC client stub, swe7). Remote proxies are also the pattern's biggest trap: a call that looks local can take 200 ms and fail, so treat them as network calls with timeouts.

Decorator — covered in swe2: same interface, added behaviour, stackable. Composite — problem: a tree of objects where leaves and branches should be handled the same way (a folder's size is the sum of its children's sizes; a UI panel contains widgets and other panels). Solution: leaves and containers share an interface, and containers delegate to their children recursively.

4. Observer: reacting to events without naming the reactors

Problem. When an order is placed, several things should happen — send a confirmation email, reserve stock, update analytics — and the list grows. If place_order calls each directly, it is coupled to all of them, and each new reaction edits it.

Solution. The publisher keeps a list of subscribers (callbacks) per event and notifies them all; subscribers register themselves. The publisher knows only "an event happened".

class EventBus:
    def __init__(self):
        self.subs: dict[str, list[Callable[[dict], None]]] = {}
    def subscribe(self, topic, fn):
        self.subs.setdefault(topic, []).append(fn)
    def publish(self, topic, payload):
        for fn in self.subs.get(topic, []):
            try:
                fn(payload)
            except Exception:
                log.exception("subscriber %s failed", fn.__name__)   # isolate failures

bus.subscribe("order_placed", send_confirmation)
bus.subscribe("order_placed", reserve_stock)
bus.publish("order_placed", {"order": 9, "sku": "sku1"})

Consequences — the traps. Trace a naive version without the try: subscribers run in order send_confirmation, analytics, reserve_stock; the analytics service is down and raises; the loop aborts, so reserve_stock never runs, and the exception propagates into place_order, which may roll back an order the customer already saw confirmed. Hence the isolation above. Other traps: a slow subscriber adds its latency to every publish; subscribers can come to depend on running after one another (an implicit ordering nobody wrote down); and a subscription that is never removed keeps its object alive — the lapsed listener memory leak. When reactions are slow, must survive a crash, or live in another service, the in-process bus becomes a message queue or pub/sub system — the same pattern across a network, covered in sc10.

5. Command: actions as objects

Problem. You need to do something with an action other than just perform it: undo it, queue it for later, retry it, log it for audit, send it to another process, or ask a human to approve it first.

Solution. Represent each action as an object holding everything needed to perform it — and, for undo, to reverse it. Undo/redo is then two stacks. Trace an editor whose document is a list of lines:

The same idea runs through production systems. A job queue holds serialised commands ({"type": "send_invoice", "order_id": 42}) that workers execute; because a queue may deliver a job twice, commands should be idempotent — safe to run more than once, often via an idempotency key. An audit log is a list of commands. And an LLM agent's tool call is a command: the model emits a tool name plus JSON arguments; the application validates them against a schema, may ask a human to approve risky ones, executes, logs, and can replay the sequence when debugging. Treating tool calls as data rather than letting the model trigger side effects directly is what makes agents auditable.

6. State: make the lifecycle explicit

Problem. An object's allowed actions depend on where it is in a lifecycle. Written as scattered checks — if order.status == "paid" and not order.cancelled in twelve files — each check encodes part of the rules, some encode them wrongly, and nothing prevents an illegal jump like shipping a cancelled order.

Solution. A state machine: a finite set of states, a set of events, and a table of which event moves which state to which next state. Anything not in the table is illegal. The simplest Python implementation is the table itself:

TRANSITIONS = {
    ("pending", "pay"): "paid",
    ("pending", "cancel"): "cancelled",
    ("paid", "ship"): "shipped",
    ("paid", "cancel"): "refunding",
    ("refunding", "refund_done"): "cancelled",
    ("shipped", "deliver"): "delivered",
}

def apply(order, event):
    nxt = TRANSITIONS.get((order.state, event))
    if nxt is None:
        raise IllegalTransition(f"cannot {event!r} when {order.state!r}")
    order.state = nxt

Trace the bug from the introduction: the code tried apply(order, "ship") on a cancelled order. ("cancelled", "ship") isn't in the table, so it raises instead of shipping. The rules now live in one place that a product manager can read. The classic Gang-of-Four version uses one class per state with a method per event, each returning the next state object; that's worth it when states carry very different behaviour, but a table is clearer for most business workflows. The same shape models deployments (queued → running → succeeded/failed/rolled back), ML training jobs, and an agent loop (plan → call tool → observe → plan … → answer), where an explicit machine with a step limit prevents infinite loops.

7. Template Method and Chain of Responsibility

Template Method — problem: several processes share a fixed skeleton but differ in some steps. Solution: a base class method runs the skeleton and calls overridable "hook" methods for the varying steps. unittest.TestCase is the canonical example: the framework runs setUp, the test method, then tearDown, and you override the steps. It is inheritance-based, so it carries the coupling costs from swe2; it's right when the framework must control the order of calls. In Python, context managers (with) and passing functions often replace it.

Chain of Responsibility — problem: a request must pass through a sequence of independent checks or transformations — authentication, rate limiting, logging, compression — and each may stop it. Solution: a chain of handlers, each of which handles the request, modifies it, or passes it to the next. Web middleware (in Python, layered around the ASGI/WSGI interfaces that connect web servers to applications; in Node, Express) is exactly this, as are Python's logging handlers and the guardrail stages around an LLM call (input moderation → redaction of personal data, often called PII → model → output validation). Order matters: rate limiting before authentication lets unauthenticated floods consume your quota.

Iterator is the last of the everyday dozen, and in Python it's part of the language: any object with __iter__/__next__, and every generator (py5).

8. Singleton, and why it became an anti-pattern

Singleton restricts a class to one instance and gives it a global access point: Database.instance(). It solves a real need — one connection pool, one configuration — but the "global access point" half causes the trouble. Any code can call Database.instance() from inside any method, so a class's constructor no longer tells you what it depends on. Tests can't substitute it without patching, and because the instance lives for the whole process, state written by one test leaks into the next, making results depend on test order. Every user is coupled to one concrete class, and lazy initialisation (if cls._instance is None: cls._instance = cls()) can run twice if two threads race through it. The fix keeps the good half: create exactly one instance in the composition root and pass it to everything that needs it. The production section tells the story that made this argument famous.

9. Anti-patterns and smells worth naming in review

An anti-pattern is a common solution that causes more problems than it solves; a smell is a surface sign that one may be present. The ones reviewers actually name:

  • God object — one class (OrderManager, Utils) that knows and does everything; most changes touch it (swe1's low cohesion).
  • Primitive obsession — money as float, emails and IDs as bare str; a UserId and a ProductId can be swapped silently. Small value types (NewType, frozen dataclasses) fix it.
  • Shotgun surgery — one change needs edits in many files; feature envy — a method more interested in another class's data than its own, which usually means it belongs there.
  • Speculative generality — factories with one product, interfaces with one implementation and no test double, hooks nobody uses.
  • Anaemic domain model — data-only classes with every rule in "service" classes; the rules about an order drift away from the order.
  • Boolean flag arguments — render(data, True, False): control coupling (swe1) that usually means two functions.

Patterns are language-dependent

Peter Norvig's 1996 talk "Design Patterns in Dynamic Languages" argued that 16 of the 23 Gang-of-Four patterns become invisible or simpler in languages with first-class functions, dynamic types and macros. The reason is that many patterns encode, in classes, a capability the language lacks. Strategy and Command exist in 1994 C++ because you couldn't pass a function with its captured data; in Python a closure is both. Iterator exists because the language lacked generators. Singleton exists because there were no modules with one-time initialisation. Visitor — a double-dispatch dance to add operations to a class hierarchy — is largely replaced in Python 3.10+ by structural pattern matching (match node: case BinOp(left, op, right): …) or functools.singledispatch. The senior move in an interview is to name the problem and then give the idiomatic form for the language: "that's a Strategy; in Python I'd pass a function".

The patterns that dominate business and distributed systems

The GoF book is about objects inside one program. In services, a second family matters more, and each deserves its own study. Repository presents stored entities as an in-memory collection (orders.get(id), orders.add(o)), hiding the database behind an interface the domain owns — Dependency Inversion applied to persistence. Unit of Work tracks every object changed in a business operation and commits them in one transaction. Specification expresses a business rule as a combinable object (overdue & high_value) usable both for in-memory checks and for generating queries. At the service level: outbox (write an event into the same database transaction as the state change, then publish it, so state and event can't diverge — sc11), saga (a multi-step business transaction across services, each step with a compensating action — sc11), circuit breaker and bulkhead for resilience (sc12), and strangler fig for replacing legacy systems gradually (swe11). Each of these is a GoF idea scaled up: the outbox is a Command log, a saga is a State machine with compensations, a circuit breaker is a Proxy with a State machine inside.

State machines deserve more use than they get

Of all patterns, explicit state machines probably prevent the most production bugs in business systems, because lifecycles are where invariants live ("never ship an unpaid order", "never charge twice"). Three techniques make them robust. First, persist transitions atomically: store the state in the database and apply events as conditional updates — UPDATE orders SET state='paid' WHERE id=:id AND state='pending' — and check the affected row count. If two workers process the same payment webhook concurrently, only one update matches; the other sees zero rows and stops. Second, record history: an append-only table of transitions (who, when, from, to, why) is the audit trail support will need. Third, side effects as reactions: emails and webhooks subscribe to transition events rather than living inside transition code, often via an outbox, so a failed email can't roll back a payment. Workflow engines (Temporal, AWS Step Functions) are state machines with durable execution built in; agent frameworks increasingly model agents as graphs of states for the same reasons — bounded steps, resumability, and inspectable history.

Observer at scale: from callbacks to event-driven architecture

In-process observers have a hidden cost the moment they're used for business logic: the flow of control is no longer visible in the code. "What happens when an order is placed?" can only be answered by searching for every subscription. The same is true, amplified, when the event bus is a message broker across services: event-driven systems are loosely coupled at build time and tightly coupled at run time through event schemas and implicit ordering. Mature teams mitigate this with an event catalogue (every event, its schema, its publishers and subscribers), schema versioning with compatibility rules, idempotent consumers, and tracing that follows a request across asynchronous hops. Use events for reactions that are genuinely independent of the publisher's success (notifications, analytics, cache invalidation); keep steps that must succeed together as direct calls within one transaction.

Patterns in ML and LLM codebases

Machine-learning frameworks are built out of patterns, and recognising them speeds up reading unfamiliar code. PyTorch's nn.Module is a Composite (modules contain modules, and parameters() recurses) with a Template Method (__call__ runs hooks around your forward). Training-loop callbacks in Keras, Lightning or Hugging Face's Trainer are Observers. Hugging Face's AutoModel.from_pretrained is a Factory keyed by configuration. Data transforms composed with Compose([...]) are a Chain. In LLM applications, the most valuable are: Adapter per provider; Decorator for retry, cache, and cost accounting; Command for tool calls; State for agent loops and multi-turn workflows; and Strategy for retrieval, chunking and reranking choices under experiment. A design that names these seams is one where a new model, a new tool or a new retrieval method is a new class, not an edit across the codebase.

How pattern misuse shows up in production code

Two opposite failure modes are common, and a senior reviewer watches for both. Missing patterns show up as repeated conditionals: the same if provider == … in eight files (a missing Factory/Strategy); status checks everywhere (a missing State machine) — which is how orders get shipped after cancellation or charged twice; vendor SDK types leaking through the codebase (a missing Adapter), which turns a vendor change into a migration. Excess patterns show up as indirection without variation: an AbstractNotificationServiceFactory producing one class; a five-layer call path where four layers forward arguments; a plugin system with one plugin. Both are measurable in review: count the branches on the same discriminator across the codebase, and count interfaces with a single implementation and no test double.

Case: "Singletons are Pathological Liars"

In August 2008 Miško Hevery, then a Google engineer coaching teams on testability (he later created AngularJS), published a Google Testing Blog post that became the standard argument against singletons. It is written as a scenario every engineer recognises rather than a single outage. You join a project with a large, mature codebase and write an exploratory test: construct a CreditCard with a number and expiry date, call charge(100). The test passes when run as part of the suite, throws a null-pointer exception when run alone — and every run charges a real card $100.

Both symptoms come from hidden global state. Asking around, you learn that CreditCard secretly uses a CreditCardProcessor singleton that must be initialised first; you add CreditCardProcessor.init() and get a different error, because the processor needs an OfflineQueue; that needs a Database. With Database.init(), OfflineQueue.init() and CreditCardProcessor.init() in the right order, the test passes in isolation — and you are another $100 poorer. In the suite it had "worked" only because some earlier test happened to initialise the globals, which is exactly the test-order dependence described in section 8. Hevery's phrase for these APIs is "pathological liars": the CreditCard constructor claims it needs a number and an expiry date, while in reality it needs a whole initialised system reachable through globals, and none of the credentials or URLs involved appear anywhere in the test.

The post's remedy is swe2's lesson: make dependencies explicit by passing them in — a CreditCard that receives its processor, a processor that receives its queue, a queue that receives its database — so the constructors tell the truth, the order of initialisation is enforced by what must exist before what, and a test passes a fake processor that charges nothing. The case is worth knowing because it isn't a dramatic outage; it is the everyday cost of the pattern: hidden dependencies, order-dependent set-up, and tests with real side effects.

Patterns and incidents

Several recurring production failures trace to how a pattern was implemented rather than whether it was used. Observer without isolation: an analytics subscriber's exception rolls back the order it was observing, or a slow subscriber adds seconds to checkout. Commands without idempotency: a queue redelivers "charge customer" after a worker crash, and the customer is charged twice; the fix is an idempotency key recorded with the first execution. Proxies that hide the network: a remote proxy called in a loop turns one page view into 300 RPCs (the "N+1" problem); remote calls should look remote. State without atomic transitions: two webhook deliveries both move an order from pending to paid and trigger two fulfilments. Singletons in tests: a suite that passes alone and fails in parallel because a shared client or cache leaks state. Each fix is a known refinement of the pattern, which is the practical reason to learn patterns with their consequences, not just their shapes.

Tools and knobs

Python gives you most patterns with little code: functools.partial and closures for configured strategies; functools.singledispatch and match for type-based dispatch; typing.Protocol for the interfaces behind adapters and proxies; functools.cache/lru_cache as a ready-made caching proxy for pure functions; weakref.WeakMethod for observers that shouldn't keep subscribers alive; and enum.Enum for state names. For state machines with persistence, a conditional UPDATE … WHERE state = … is the essential knob; libraries such as transitions help when machines get large. In review, ask two questions of any pattern: what variation or problem does it address today, and what would the simplest version look like?

import unittest
from dataclasses import dataclass, field
from typing import Callable, Protocol

# ---------- State: an order's lifecycle as an explicit transition table ----------
TRANSITIONS = {
    ("pending", "pay"): "paid",
    ("pending", "cancel"): "cancelled",
    ("paid", "ship"): "shipped",
    ("paid", "cancel"): "refunding",
    ("refunding", "refund_done"): "cancelled",
    ("shipped", "deliver"): "delivered",
}

class IllegalTransition(Exception):
    pass

@dataclass
class Order:
    id: int
    state: str = "pending"
    history: list[str] = field(default_factory=list)

    def apply(self, event: str) -> None:
        nxt = TRANSITIONS.get((self.state, event))
        if nxt is None:
            raise IllegalTransition(f"order {self.id}: cannot {event!r} when {self.state!r}")
        self.history.append(f"{self.state} --{event}--> {nxt}")
        self.state = nxt

# ---------- Command: edits as objects with do/undo ----------
class Command(Protocol):
    def do(self, doc: list[str]) -> None: ...
    def undo(self, doc: list[str]) -> None: ...

@dataclass
class Insert:
    pos: int
    text: str
    def do(self, doc): doc.insert(self.pos, self.text)
    def undo(self, doc): del doc[self.pos]

@dataclass
class Delete:
    pos: int
    removed: str = ""
    def do(self, doc): self.removed = doc.pop(self.pos)
    def undo(self, doc): doc.insert(self.pos, self.removed)

class Editor:
    def __init__(self):
        self.doc: list[str] = []
        self.undo_stack: list[Command] = []
        self.redo_stack: list[Command] = []
    def run(self, cmd: Command):
        cmd.do(self.doc); self.undo_stack.append(cmd); self.redo_stack.clear()
    def undo(self):
        cmd = self.undo_stack.pop(); cmd.undo(self.doc); self.redo_stack.append(cmd)
    def redo(self):
        cmd = self.redo_stack.pop(); cmd.do(self.doc); self.undo_stack.append(cmd)

# ---------- Observer: an event bus where one bad subscriber can't break the others ----------
class EventBus:
    def __init__(self):
        self.subs: dict[str, list[Callable[[dict], None]]] = {}
        self.errors: list[str] = []
    def subscribe(self, topic: str, fn: Callable[[dict], None]):
        self.subs.setdefault(topic, []).append(fn)
    def publish(self, topic: str, payload: dict):
        for fn in self.subs.get(topic, []):
            try:
                fn(payload)
            except Exception as e:                      # isolate: log and continue
                self.errors.append(f"{fn.__name__}: {e}")


class Tests(unittest.TestCase):
    def test_happy_path_and_illegal_transition(self):
        o = Order(7)
        for ev in ("pay", "ship", "deliver"):
            o.apply(ev)

    def test_observer_isolates_failures(self):
        bus, sent, stock = EventBus(), [], {"sku1": 5}
        def send_email(e): sent.append(e["order"])
        def broken_analytics(e): raise ConnectionError("analytics down")
        def reserve_stock(e): stock[e["sku"]] -= 1
        for fn in (send_email, broken_analytics, reserve_stock):
            bus.subscribe("order_placed", fn)
        bus.publish("order_placed", {"order": 9, "sku": "sku1"})
        self.assertEqual((sent, stock["sku1"]), ([9], 4))
        self.assertEqual(bus.errors, ["broken_analytics: analytics down"])

Match the pattern

Name the pattern for each, in one line, and say what could go wrong: (a) wrap the Twilio SDK so your code depends on SmsSender; (b) HTTP middleware for auth, logging and rate limiting; (c) an editor that supports undo/redo; (d) an order that behaves differently in Pending, Paid, Shipped and Cancelled; (e) choose between three recommendation algorithms per A/B bucket; (f) cache results of an expensive remote client transparently; (g) an LLM agent that can call "search", "send_email" and "refund" tools.

Answer

(a) Adapter — translate a vendor interface and its exceptions into yours; risk: leaking vendor types through the adapter's return values. (b) Chain of Responsibility (each middleware handles or passes on); a stack of decorators is an equally good answer; risk: wrong order, e.g. rate limiting after expensive authentication. (c) Command — each edit is an object with do/undo, kept on two stacks; risk: a command that doesn't store enough to reverse itself. (d) State — a transition table or one class per state; illegal actions raise; risk: concurrent events, so persist transitions as conditional updates. (e) Strategy selected by a Factory keyed by bucket; risk: bucket assignment and logging drift so you can't attribute results. (f) Proxy (caching proxy) — same interface as the client, checks the cache first; the follow-up to anticipate is invalidation and staleness — the pattern is easy, the cache semantics are the real design. (g) Command for each tool call (name + validated arguments, logged and replayable), wrapped in a protection proxy or approval step for dangerous tools like refund, inside a State machine with a step limit for the agent loop.
