A support engineer is paged at 2 a.m.: customers say orders are "stuck". The logs show nothing — no errors at all. After an hour they find a function called process with a try around forty lines and an except Exception: print(e) at the bottom; the print went to a console nobody reads. The database had been timing out since midnight, and every order since then had quietly returned False, which the caller had interpreted as "card declined". Nothing was wrong with any single line. The code was simply written so that a failure looked exactly like a normal outcome, and so that nobody could see either.

Most production incidents are not caused by exotic algorithms; they're caused by ordinary code that is hard to read and handles failure badly — a name that meant something different to its author and its caller, a function that does five things so one of them gets missed in review, an error swallowed where it should have propagated, a crash where the system should have carried on with reduced function. Code is read many more times than it is written, and it spends most of its life being changed by someone who didn't write it. "Clean code" is simply code optimised for that reader: it says what it means, has one obvious flow, and fails in ways that are loud, specific and easy to trace.

This lesson has two halves. The first covers readability — names, function shape, guard clauses, comments — with a before-and-after refactor. The second, larger half builds a complete model of failure: the four kinds of error and how each should be handled, exceptions versus result values, exception chaining, validating untrusted input at the boundary, where to catch, when to retry, and when to fail fast versus degrade. The case study is Ariane 5 Flight 501, which in 1996 destroyed itself 40 seconds into its first flight because of one unprotected number conversion and an error-handling policy that turned a harmless overflow into a total loss. The lab applies the same ideas to an LLM classifier whose output can't be trusted.

The analogy: a well-run hospital ward

On a good ward, every drug is labelled with its name, dose and units — nobody guesses whether "5" means milligrams or millilitres. Each chart entry says what was done and, when it's unusual, why. And failures are triaged: a patient who needs a routine test that's delayed waits (a transient problem — retry later); a patient allergic to a drug gets a different drug (an expected outcome with a known alternative); a machine giving obviously impossible readings is taken out of service and reported (a bug — don't trust it); a fire evacuates the ward (unrecoverable — stop and escalate). What a good ward never does is treat every problem the same way — either ignoring them all or evacuating for each one.

Code needs the same two things: labels a stranger can read correctly, and triage. The analogy breaks at speed and scale: a program meets thousands of failures a minute and must triage them automatically, so the categories have to be designed into the code in advance.

Readable code in three rules

First, names carry meaning. A reader should know what a variable holds, in what units, and what a function does, from the names alone. t = 30 says nothing; request_timeout_s = 30 says everything. Second, functions have one job at one level of detail. A function that validates input, computes a price and sends an email mixes three levels of detail; a reader must understand all of them to change any. Third, comments explain why, not what. The code already says what; only a comment can say "we round down here because the tax authority requires it".

Failure in four kinds

Every error-handling decision starts with one question: what kind of failure is this?

A bug (a programmer error) is a violated assumption in the code — a missing dictionary key, a wrong type, an impossible state. Retrying won't help and hiding it is dangerous; it should fail loudly so someone fixes it. An expected outcome is a normal non-success result — user not found, card declined, model output invalid — that the caller must handle, so it belongs in the function's contract. A transient fault is an operational failure likely to succeed if tried again — a timeout, a rate limit, a dropped connection — so it's retried, carefully. An environment failure — full disk, missing configuration, revoked credentials — won't fix itself; the operation should stop and a human be alerted. The rest of the lesson is about implementing that triage in Python.

One more framing helps. Error handling isn't a layer you add at the end; it's part of each function's contract, as much as its arguments and return type. A reader should be able to tell from a signature and its docstring which failures a function can report and how — raised, returned, or retried inside. When that contract is explicit, reviewers can check it, tests can exercise it (swe5), and a caller can't mistake one kind of failure for another. When it's implicit, every caller guesses, and the guesses differ.

1. Names

A name is the cheapest documentation there is and the one most read. Five rules cover most cases.

Say what it means, not how it's stored. d, data, info, tmp, val2 tell the reader nothing. days_since_last_login, unpaid_invoices, retry_delay_s do. The length of a name should grow with its scope: i is fine for a three-line loop, not for a module-level variable.

Put units in names. A number without units invites the Mars Climate Orbiter error from swe1. timeout=30 — seconds or milliseconds? timeout_s=30 or timeout_ms=30_000 removes the question. Money gets a unit too: price_cents as an integer, or a Decimal with a currency.

Booleans read as questions: is_expired, has_access, should_retry. flag and status don't say which answer is True.

Functions that act get verbs; functions that return values get nouns or questions: send_invoice(), monthly_total(), is_eligible(). A function called get_user should not also update the user — which leads to the next rule.

One word per concept. If the codebase says fetch, get, load and retrieve for the same operation, readers will assume they differ. Pick one and use the domain's words: if the business says "shipment", don't call it delivery in code.

2. Functions: one job, one level, flat flow

Here is a function in the style of the introduction's incident, slightly simplified:

def process(order):
    try:
        user = db.get_user(order["user_id"])
        if user != None:
            if user.balance >= order["total"]:
                user.balance -= order["total"]
                db.save(user)
                email.send(user.email, "ok")
                return True
    except Exception as e:
        print(e)
    return False

Count the problems a reader must untangle: the name says nothing; the happy path is nested three levels deep; a missing user, insufficient funds, a database timeout and a typo in a key all return the same False; the email is sent inside the money-moving path; and every failure is printed and forgotten. Refactor in steps.

Guard clauses. Handle special cases first and leave early, so the main path isn't nested:

def charge_order(order: Order) -> Receipt:
    user = users.get(order.user_id)
    if user is None:
        raise UserNotFound(order.user_id)
    if user.balance_cents < order.total_cents:
        raise InsufficientFunds(needed=order.total_cents, available=user.balance_cents)
    receipt = ledger.debit(user.id, order.total_cents)     # atomic, in one transaction
    events.publish("order_charged", receipt)               # email reacts to this, after commit
    return receipt

Now the function reads top to bottom as a list of rules followed by the action. Each failure is a specific, named outcome the caller can handle differently ("ask for another card" versus "show 404"). Database errors are no longer caught here at all: this function can't do anything useful about them, so they propagate to a layer that can.

One level of abstraction. charge_order talks in business terms — users, balances, ledger, events. The SQL for ledger.debit and the SMTP details for the email live elsewhere. Mixing levels ("check the balance, then build an SQL string, then format an email header") forces readers to switch context every line.

Command-query separation. A function should either change state (a command, like debit) or answer a question (a query, like balance_of), not both. Queries are then safe to call anywhere — in a log statement, an assertion, a debugger — without side effects. The classic violation is a get_user() that also updates last_seen_at; someone adds it to a debug log and every page view now writes to the database.

Few parameters, no flag arguments. Three or four parameters is plenty; more usually means a missing type (group them into a dataclass). A boolean that switches behaviour — render(report, True) — is unreadable at the call site and usually means two functions: render_summary(report) and render_detailed(report). If a flag must exist, make it keyword-only: def render(report, *, detailed: bool = False).

Size. There's no magic line count. The test is whether the name describes everything the function does and whether its body is at one level of detail. Cyclomatic complexity — roughly one plus the number of decision points (if, for, and, except) — is a useful alarm: past 10 to 15, a function has too many paths to test or hold in your head.

3. Comments and docstrings

A comment that restates the code (# increment i) is noise, and worse, it rots: someone changes the code and not the comment. Good comments record what the code can't say: the reason for a non-obvious choice ("round half-even: required by the 2023 tax guidance"), a rejected alternative ("a set would be faster but ordering matters for the audit export"), an assumption ("safe: upstream guarantees at most 500 items"), or a warning ("this is O(n²) but n ≤ 20"). Docstrings on public functions state the contract: what it needs, what it returns, what it raises. Commented-out code should be deleted — version control remembers it.

Assumptions deserve special care, because the code will outlive the context in which they were true. Keep that thought for the Ariane case.

4. Exceptions done well

Python's exceptions (py7) are the default mechanism for failures a caller can't be expected to handle inline. Five practices separate robust code from the introduction's incident.

Raise specific exceptions. raise ValueError("bad") tells the caller nothing it can branch on. Define a small hierarchy for your service, organised by how callers must respond:

class AppError(Exception): ...
class NotFound(AppError): ...
class InvalidInput(AppError): ...
class Conflict(AppError): ...
class TransientError(AppError): ...          # retry logic keys on this
class Timeout(TransientError): ...
class RateLimited(TransientError): ...

Catch specific exceptions, as narrowly as possible. Wrap only the line that can fail with the error you expect, not forty lines:

try:
    cfg = json.loads(raw)
except json.JSONDecodeError as e:
    raise InvalidInput(f"config is not valid JSON at char {e.pos}") from e

Chain when translating. raise … from e keeps the original exception as __cause__, and the traceback prints both: the domain meaning ("config is not valid JSON") and the low-level reason. Adapters around vendor libraries should translate every vendor exception this way, so the rest of the code only sees your types (swe2's adapter idea).

Never swallow. An except that neither handles the problem nor re-raises converts a failure into silent wrong behaviour. If you catch something only to log it, re-raise it (raise with no argument keeps the original traceback) — or, better, don't catch it and let the top-level handler log it once.

Clean up with context managers. with open(...), with conn.transaction(), with lock: guarantee release even when an exception passes through, which is what makes letting exceptions propagate safe.

Python's style is EAFP — "easier to ask forgiveness than permission": try the operation and handle the specific exception — rather than LBYL, "look before you leap". EAFP avoids race conditions where the world changes between the check and the action (the file you checked exists is deleted before you open it; swe12 covers such races), and in CPython 3.11+ a try that doesn't raise costs almost nothing.

5. Result values for expected outcomes

Some failures are so normal that an exception hides them. A model returning malformed JSON, a lookup that finds nothing, a validation that fails — the caller must decide what to do, and a type that forces the decision is clearer than an exception the caller might forget to catch. Languages like Rust (Result<T, E>) and Go (value, err) make this the norm. In Python, a union of small dataclasses does the job and a type checker enforces it:

@dataclass(frozen=True)
class Answer:
    label: str
    confidence: float

@dataclass(frozen=True)
class ParseError:
    reason: str

def parse_answer(raw: str) -> Answer | ParseError: ...

match parse_answer(model_output):
    case Answer(label, conf) if conf >= 0.7:
        route_to(label)
    case Answer():
        send_to_human_review()
    case ParseError(reason):
        metrics.increment("llm.parse_failure"); retry_with_repair(reason)

If a caller writes parse_answer(x).label without checking, mypy reports that ParseError has no attribute label. For simple absence, Optional[T] (T | None) is enough — but only when "why" doesn't matter. None can't distinguish "not found" from "database down", which is exactly the introduction's bug.

The rule of thumb: exceptions for failures the immediate caller usually can't handle, result values for outcomes it must handle. The boundary is a judgement call, and consistency within a codebase matters more than the choice.

6. Validate at the boundary, then trust

A boundary is where data enters your code from somewhere you don't control: an HTTP request, a file, a message queue, a database written by another service, a model's output. Inside the boundary, code should work with values whose properties are guaranteed. The technique — sometimes summarised as "parse, don't validate" — is to convert raw input once, at the boundary, into typed values that can only exist if valid:

@dataclass(frozen=True)
class Percentage:
    value: float
    def __post_init__(self):
        if not 0.0 <= self.value <= 100.0:
            raise InvalidInput(f"percentage {self.value} outside [0, 100]")

Any function that receives a Percentage knows it's in range, so it needs no defensive checks, and the error message is produced at the entry point, where the context to explain it exists. Pydantic models do this for whole request bodies and model outputs. Scattered if x < 0 checks deep in the code are the alternative, and they're always incomplete.

Conversions between numeric types are boundaries too, and a subtle one. Python's own int never overflows, but values leave Python constantly — into a binary protocol, a NumPy array, a database SMALLINT column, a C extension — and there the target type has a range. What happens at the edge of that range is a design decision with three options:

  • Raise: struct.pack("<h", 40000) raises struct.error: 'h' format requires -32768 <= number <= 32767.
  • Wrap around silently: in 16 bits, 40,000 becomes 40,000 − 65,536 = −25,536. NumPy's np.array([40000.0]).astype(np.int16) produced exactly −25,536 on our test machine (NumPy 2.5), with no error — out-of-range float casts are undefined in C, so the result can vary by platform.
  • Saturate: clamp to 32,767, a bounded and documented approximation.

Wrap-around is almost never what you want: a large positive number becomes a large negative one. Raising is right when a bad value means the input is wrong; saturating is right when an approximate value is safer than none. That choice, and its absence, is at the centre of this lesson's case.

7. Where to handle: catch where you can act

An exception should be caught at the first level that can do something useful with it. In a typical service there are only three such places. Adapters at the edges translate vendor and driver exceptions into your own types. Policy wrappers retry transient errors or fall back. The top-level handler — the web framework's error handler, the job runner's loop — logs the error once with full context, maps it to a response (404 for NotFound, 409 for Conflict, 503 for exhausted TransientError, 500 for anything else) and alerts if needed.

Two anti-patterns follow from this. Log and rethrow at every layer produces the same error five times in the logs with slightly different messages, which makes incidents harder to read. And catch-all in the middle — an except Exception in a service method — is where bugs get reclassified as outcomes, as in the introduction.

8. Retries: only transient, only idempotent, always bounded

Retrying is the right response to exactly one kind of failure, the transient fault, and only under conditions. The operation must be idempotent — safe to perform more than once — or carry an idempotency key the server uses to deduplicate; otherwise a retry after a timeout (where the first attempt may have succeeded) charges the card twice. Attempts must be bounded, and the delay should grow exponentially with random jitter (0.5 s, 1 s, 2 s, each randomised) so thousands of clients don't retry in lockstep. The whole operation needs a deadline, so retries can't run past the point where the answer is useful. And retries should live at one layer: if the client library, your service and the caller's service each retry three times, one user action becomes 3 × 3 × 3 = 27 attempts against a dependency that is already struggling. Retrying a bug, by contrast, just repeats the bug — which is why the retry wrapper must key on TransientError, not Exception. (sc12 treats timeouts, retries and circuit breakers in depth.)

9. Fail fast versus degrade

Fail fast means detecting a problem as close to its cause as possible and refusing to continue with bad data. Graceful degradation means continuing to provide reduced but safe service when a part fails. They aren't opposites; they apply at different scopes. Fail the operation fast — reject the request with a clear error rather than processing garbage. Degrade the system — if the recommendation service is down, show popular items; if the reranker times out, serve results in retrieval order. The design question is always "for this user, which is worse: a wrong answer, or no answer?" For a payment, stop. For a product carousel, degrade. For a safety classifier in front of an LLM, don't serve the unchecked answer. The case study below is what happens when a system is designed to stop in a situation where continuing with a best estimate was the safe choice.

Making invalid states unrepresentable

The strongest form of error handling is designing types so the error can't happen. If an order can be pending or paid, and only paid orders have a paid_at timestamp, then a single class with an optional paid_at permits the invalid state "paid with no timestamp" and every consumer must check for it. Two types — PendingOrder and PaidOrder(paid_at: datetime) — make the invalid state impossible to construct. The same idea gives NewType("UserId", int) so a user ID can't be passed where a product ID is expected, Enum instead of free strings for states, and frozen dataclasses whose constructor validates. Each check moved into a type is a check no caller can forget. Alexis King's "parse, don't validate" frames it as: a validation function returns None and throws away what it learned; a parsing function returns a more precise type that carries the proof forward.

Exception safety and invariants

When an exception passes through a function, what state does it leave behind? C++ programmers formalised three levels, and they apply to any language. The basic guarantee: no resources leak and objects remain valid, though their contents may have changed. The strong guarantee: the operation either completes or has no effect at all, as if it never started — transactions provide this. The no-throw guarantee: the operation can't fail. The practical Python rules are: acquire resources with with so they're released; mutate state only after every step that can fail has succeeded (compute the new value, then assign it); and wrap multi-step changes to external state in a transaction. The introduction's function, which debited a balance and then sent an email, gave no guarantee: an email failure after the debit left money taken and the order marked failed.

Exception groups and concurrent failures

When work runs concurrently — several model calls with asyncio.TaskGroup, several validations of one form — more than one thing can fail at once, and raising only the first loses information. Python 3.11 added ExceptionGroup and the except* syntax: a task group that has two tasks fail raises one group containing both, and except* TimeoutError handles the timeouts in the group while letting others propagate. For validation, collecting all errors and reporting them together (as Pydantic does) is far friendlier than failing on the first. The design point: decide whether callers need the error or all errors, and choose the mechanism accordingly.

Error budgets for error handling: what to log, count and alert on

Each kind of failure deserves a different observability treatment. Bugs should be logged with full tracebacks and alerted on, since every one is a defect; they should also be counted by type so a new one stands out after a deploy. Expected outcomes should be counted (metrics like orders_declined_total) but not logged as errors — logging every declined card at ERROR trains everyone to ignore the error log. Transient faults should be counted by dependency, with retries and final failures separated, because a rising retry rate is an early warning before users see anything. Environment failures should page. Structured logs with a request ID on every line make it possible to reconstruct one failure end to end (swe14 covers this). A mature codebase can answer "how many requests failed, of which kind, since the last deploy" from a dashboard, which is only possible if the code classified failures in the first place.

Systematic versus random failures, and why redundancy isn't enough

Hardware fails randomly and independently: two identical sensors rarely fail in the same millisecond, so a backup covers a failure. Software fails systematically: identical code given the same input fails the same way every time. Duplicating a software component therefore protects against hardware faults in its host but not against its own bugs — both copies fail together. This is the single most important lesson of the Ariane case, and it generalises: running three replicas of a service doesn't help if the bad input or bad deploy reaches all three; a failover region running the same code with the same poison message fails the same way. Defences against systematic failure are different in kind — diversity (a different implementation or a simpler fallback path), input validation and bounds, staged rollouts that expose a change to a small fraction first (swe9), and error policies that keep a degraded but safe function running instead of stopping.

Readability as a measurable property

Readability sounds subjective, but several signals are measurable and correlate with defect rates in studies of large codebases: cyclomatic complexity per function, nesting depth, function length, number of parameters, and churn (how often a file changes). Linters enforce the cheap ones — Ruff can flag functions above a complexity threshold (C901), bare except: clauses (E722), broad except Exception that swallows (BLE001) and raise inside except without from (B904). The value isn't the score; it's that the conversation in code review moves from taste to specifics.

How error handling fails in production

The same handful of patterns cause most error-handling incidents. Swallowed errors turn outages into silent data loss, discovered days later by a customer. Misclassified errors tell users the wrong thing — "declined" for a timeout, "not found" for a permissions failure — and send them away. Retry storms keep a recovering dependency down. Non-idempotent retries duplicate charges, emails and orders. Partial updates leave state half-changed when an exception interrupts a multi-step operation. Log floods — every expected outcome logged at ERROR — hide the one real error. And error paths that were never executed: code in an except block that has a typo in it, found only when the error finally happens. Studies of distributed-system failures have repeatedly found that a large share of catastrophic failures come from incorrect handling of errors that were explicitly signalled — the error was detected, then handled wrongly. Testing error paths deliberately (swe5) and injecting faults in staging are the countermeasures.

Case: Ariane 5 Flight 501

On 4 June 1996, the first Ariane 5 rocket veered off course about 40 seconds after the flight sequence began, at an altitude of about 3,700 m, broke up and exploded. The European Space Agency and the French space agency CNES appointed an inquiry board chaired by Jacques-Louis Lions, whose report is public and remains one of the best-written software failure analyses ever produced. Its chain of events, traced backwards from the explosion, reads like a lesson in this topic.

The rocket had two identical inertial reference systems (SRIs, from the French Système de Référence Inertielle) — the units that measure the rocket's attitude and motion, one active and one hot standby. About 37 seconds after main-engine ignition, both declared failure: the backup first, the active unit one 72-millisecond data cycle later. Each had raised an exception while converting a 64-bit floating-point value to a 16-bit signed integer. The value was BH, the "horizontal bias", related to the horizontal velocity sensed by the platform. On Ariane 4, whose software the SRI reused almost unchanged, BH stayed small. Ariane 5's early trajectory was different and produced considerably higher horizontal velocity, so BH exceeded 32,767 and the conversion raised an operand error.

The details make it an error-handling case rather than a mere bug. The developers had analysed every conversion that could overflow and found seven variables at risk. They protected four. The other three, including BH, were left unprotected on the reasoning that they were physically limited or had a large safety margin — a reasonable judgement for Ariane 4. The report says the SRI computer had a maximum workload target of 80%, which is why not every conversion was protected, and that no justification for the decision was found in the source code itself, so the assumption was "essentially obscured" from later review. Nobody re-checked it against Ariane 5's trajectory data, which was not included in the SRI's requirements.

Worse, the code that overflowed didn't matter. It belonged to an alignment function that computes meaningful results only before lift-off; on Ariane 4 it kept running for about 40 seconds of flight to allow a quick restart after a late countdown hold, a requirement Ariane 5 didn't have. And then the error policy turned a harmless fault into a total loss. The specification said that on any exception the SRI should report the failure, store the context, and shut its processor down — a policy designed, the board wrote, for a culture of "only addressing random hardware failures", where the backup unit takes over. But the backup ran the same software on the same data; it had already failed the same way. Finally, the on-board computer read the active unit's diagnostic bit pattern as if it were flight data and commanded full nozzle deflections.

Map it to this lesson. A narrowing conversion at a boundary with no policy for out-of-range values. An assumption recorded nowhere near the code it constrained. An error policy that treated a software exception like a hardware fault, when the board noted the SRIs "could have continued to provide their best estimates" — graceful degradation. Redundancy that couldn't help against a systematic failure. And a consumer that didn't validate its input. The board's recommendations included turning the alignment function off after lift-off, reviewing all flight software including its assumptions, and designing the SRI to keep providing best-estimate data rather than shutting down on such faults.

The same shape in ML and LLM systems

AI systems have more untrusted boundaries than most software, and they fail the Ariane way: silently wrong rather than loudly broken. Model output is untrusted input — JSON that doesn't parse, a label outside the allowed set, a confidence of 1.7, a refusal where an answer was expected — and belongs behind a parser that returns typed failures. Numeric conversions bite in serving: embeddings quantised to int8 or float16 saturate or overflow when a new model's output range differs from the old one's; token counts computed with one tokenizer are enforced by a model using another. Reused components carry assumptions: a preprocessing function written for one model's input normalisation, reused for a new model, like the SRI reused from Ariane 4. And the fail-fast versus degrade decision appears constantly: if retrieval fails, answer without context or refuse? If the safety filter times out, block or pass? Each should be an explicit, reviewed policy, and each failure kind should have its own metric — parse failures, repair retries, fallbacks — so a change in model or prompt that shifts them is visible the day it ships.

"""swe4 lab: validate at the boundary, return expected failures as values, raise on bugs, retry only transient errors."""
import json
import struct
import unittest
from dataclasses import dataclass


# ---------- 1. an Ariane-style narrowing conversion, three ways ----------
def to_int16_unchecked(x: float) -> int:          # what a C cast might do: wrap silently
    return ((int(x) + 2**15) % 2**16) - 2**15

def to_int16_strict(x: float) -> int:             # fail loudly at the boundary
    return struct.unpack("<h", struct.pack("<h", int(x)))[0]   # raises struct.error if out of range

def to_int16_saturating(x: float) -> int:         # degrade: clamp to the representable range
    return max(-32768, min(32767, int(x)))


# ---------- 2. parsing untrusted model output into a typed value ----------
@dataclass(frozen=True)
class Answer:
    label: str
    confidence: float

@dataclass(frozen=True)
class ParseError:
    reason: str

LABELS = {"refund", "shipping", "other"}

def parse_answer(raw: str) -> Answer | ParseError:
    """Expected failures (the model returned junk) come back as values the caller must handle."""
    try:
        data = json.loads(raw)
    except json.JSONDecodeError as e:
        return ParseError(f"not JSON: {e.msg} at char {e.pos}")
    if not isinstance(data, dict):
        return ParseError("top level is not an object")
    label, conf = data.get("label"), data.get("confidence")
    if label not in LABELS:
        return ParseError(f"label {label!r} not in {sorted(LABELS)}")
    if isinstance(conf, bool) or not isinstance(conf, (int, float)) or not 0.0 <= conf <= 1.0:
        return ParseError(f"confidence {conf!r} not a number in [0, 1]")
    return Answer(label, float(conf))


# ---------- 3. retry transient errors only ----------
class TransientError(Exception): ...
class ProviderTimeout(TransientError): ...

def classify(call, prompt: str, attempts: int = 3) -> Answer:
    last: ParseError | None = None
    for _ in range(attempts):
        try:
            raw = call(prompt)
        except TransientError:
            continue                                   # retryable: try again
        result = parse_answer(raw)
        match result:
            case Answer():
                return result
            case ParseError():
                last = result                          # model gave junk: ask again
                prompt += f"\nYour last reply was invalid ({result.reason}). Reply with JSON only."
    raise RuntimeError(f"no valid answer after {attempts} attempts; last problem: {last}")


class Tests(unittest.TestCase):
    def test_conversion_policies(self):
        bh = 40_000.7                                  # a horizontal-bias value too big for int16
        self.assertEqual(to_int16_unchecked(bh), -25536)       # silently wrong, sign flipped

List what you would raise in code review, in priority order, and sketch the fixed version.

Answer
  • Swallowed exceptions: except Exception: print hides bugs and outages alike, and returns False for a database timeout exactly as for insufficient funds. Callers cannot tell "retry later" from "declined", and nobody sees the error.
  • Boolean return loses information. Raise specific exceptions (UserNotFound, InsufficientFunds) or return a typed result, and let infrastructure errors propagate to the top-level handler, which logs once.
  • Not atomic / race condition: read-check-write of the balance without a transaction or conditional update — two concurrent orders can both pass the check (swe12). Use UPDATE … SET balance = balance - :t WHERE id = :u AND balance >= :t and check rows affected.
  • Side effect inside the money path: the email is sent before we know the whole operation committed, and an email failure after the save reports the order as failed with money taken. Publish an event after commit, ideally via an outbox, and send the email from a subscriber.
  • Money type: check the type of balance — use integer cents or Decimal, and name it balance_cents.
  • Minor: != None should be is not None; deep nesting — use guard clauses; print instead of structured logging; the name process says nothing — charge_order.

def charge_order(order: Order) -> Receipt:
    if (user := users.get(order.user_id)) is None:
        raise UserNotFound(order.user_id)
    receipt = ledger.debit_if_sufficient(user.id, order.total_cents)   # conditional UPDATE in a transaction
    if receipt is None:
        raise InsufficientFunds(order.total_cents)
    events.publish("order_charged", receipt)                           # email subscribes; runs after commit
    return receipt
