A team ships a checkout service with 2,000 tests and 94% coverage. On a Friday a small refactor to the discount code goes out; every test passes. On Saturday, customers with two coupons are charged negative shipping. The bug was in a branch every test executed, but no test checked its result — the tests had been written to raise coverage, calling functions and asserting only that nothing crashed. Meanwhile, the test suite takes 40 minutes, so engineers batch their changes, and about one run in three fails on something unrelated — a test that depends on the time of day, another that fails only when run after a particular neighbour. Everyone has learned to click "rerun". When the real failure appeared in CI two weeks earlier, it was rerun too.

This is the state many test suites drift into, and it's worse than having fewer tests: the suite costs time, gives false confidence, and trains people to ignore it. Testing well isn't about the number of tests or the coverage figure. It's about one question: does this suite let us change the code quickly and know whether we broke something? That requires tests at the right level for the risks, tests that check behaviour rather than execution, doubles that don't lie, and — above all — tests that are deterministic, because a test people don't trust is worse than no test.

This lesson builds that up from the beginning: what a test is for and what makes a good one; the levels (unit, integration, end-to-end) and the long-running pyramid-versus-trophy debate about the mix; the five kinds of test double and when mocks mislead; what coverage does and doesn't measure; property, contract and snapshot tests; and flaky tests — how they arise, why they compound, how to trace one to its root cause. The real-world case is Google's published data on flakiness across millions of tests. And because this is an AI-engineering track, the final part covers testing non-deterministic model output: what to test with fakes, what to measure with evaluation sets, and how to tell a real regression from noise.

The analogy: safety checks in a car factory

A car factory checks quality at several levels. Each bolt is torque-tested as it's fitted — instant, cheap, done thousands of times a day, and when it fails you know exactly which bolt. Each assembled engine is run on a test bench — slower, needs fuel and a rig, catches problems in how parts fit together. A few finished cars are driven round a test track — slow and expensive, the only check that the whole car works, but when one pulls to the left it could be a hundred things. No factory relies only on test drives, and none relies only on bolt checks. And if the torque wrench gave a random reading one time in fifty, workers would soon stop believing it — and the one real loose bolt would go through.

Software testing has the same three levels and the same economics. The analogy breaks in one helpful way: software checks are nearly free to repeat, so a good suite runs every check on every change, many times a day — which only works if every check is fast and trustworthy.

What a test is

A test is code that runs other code and checks the result automatically. Most follow arrange-act-assert: set up inputs and state, perform one action, check the outcome.

def test_member_discount_applies_five_percent():
    cart = Cart(items=[Item("book", Decimal("40.00"))], member=True)   # arrange
    total = checkout_total(cart)                                        # act
    assert total == Decimal("38.00")                                    # assert

A good test has five properties. It's fast, so it runs on every change. It's deterministic: same code, same result, every time. It's isolated: it doesn't depend on other tests or leave state behind. It checks behaviour, not implementation: it goes through the public interface, so a refactor that keeps behaviour keeps the test green. And it fails for one clear reason, with a name that says what broke.

Three levels, two shapes

A unit test checks one piece of logic in memory. An integration test checks your code working with a real collaborator — a database, a queue, an HTTP service. An end-to-end (E2E) test drives the whole deployed system as a user would. Moving up, tests become more realistic but slower, costlier and flakier, and a failure says less about where the bug is. A useful habit: when a bug escapes to production, write the test that would have caught it at the lowest level where it's possible, and ask why it didn't exist. Over time, that habit shapes the suite around your real risks rather than around a diagram.

The rest of the lesson explains the trade-offs in each shape, then the tools — doubles, coverage, other test kinds — and the thing that ruins suites of any shape: flakiness.

1. What tests are for

Tests do three jobs. They catch regressions — behaviour that used to work and a change broke. They enable change: with a fast, trusted suite, a developer can refactor, upgrade a library or restructure a module and know within minutes whether behaviour survived. And they document behaviour in executable form: a test named test_cancel_after_shipping_is_rejected is a specification that can't drift from the code. The second job is the one that justifies the investment. A codebase without trusted tests becomes a codebase nobody dares change, which is how systems ossify.

From that follows the most useful principle in the whole topic: test behaviour through public interfaces, not implementation details. A test that asserts a private helper was called twice, or checks the exact SQL string a repository generates, breaks on every refactor even when the behaviour is identical. Tests coupled to implementation make change harder, which inverts their purpose. Ask of each assertion: would a user or caller notice if this changed?

2. The levels, and Google's sizes

Unit tests run a small piece of logic in memory — a function, a class, a small group of classes — with any slow or external collaborator replaced. They take milliseconds and pinpoint failures. Their weakness: they can't find bugs in how pieces fit together — a wrong SQL query, a misconfigured serializer, a mismatch with another service.

Integration tests run your code against real collaborators: a real Postgres in a container, a real Redis, a real HTTP server. They catch the bugs units can't — transactions that aren't atomic, queries that don't use the right index, serialisation round trips — at the cost of seconds per test and more set-up.

End-to-end tests drive the deployed system through its real interface — a browser clicking through checkout, a client calling the public API. They are the only tests that prove the whole thing works, and they're slow, fragile (any component can fail them) and poor at localising bugs.

Google's engineering book adds a useful distinction between a test's scope (how much code it exercises) and its size (what resources it may use). A small test runs in a single process with no sleeping, no I/O and no network; a medium test may use multiple processes on one machine, including a local database; a large test may span machines. Size predicts speed and flakiness better than scope does, which is why Google pushes for small tests — and why, as the production section shows, flakiness climbs with size.

3. Pyramid, trophy, and choosing the mix

The test pyramid, popularised by Mike Cohn and Martin Fowler, says most tests should be unit tests, fewer integration tests, and very few end-to-end tests, because lower tests are faster, more stable and more precise. The testing trophy, from Kent C. Dodds, argues that for typical application code — web handlers that validate input, call a database and return JSON — the logic worth testing is in the wiring, unit tests with mocked dependencies prove little, and most effort should go into integration tests, with static checks (type checkers and linters) as a cheap base.

Both are right about different codebases. A pricing engine, a parser or a scheduling algorithm is rich in pure logic: the pyramid fits, and property tests shine. A CRUD service — one that mostly creates, reads, updates and deletes records — has its bugs in queries and serialisation, and is trophy-shaped. The honest procedure is empirical: look at the last ten bugs that reached production and ask at which level a test would have caught each one. Put tests there. Everyone agrees on one thing: end-to-end tests should be few — a handful of smoke tests over the critical user journeys (sign up, pay, core feature) — because each one is expensive and flaky.

4. Test doubles: five kinds

A test double is any object standing in for a real collaborator (the term, from Gerard Meszaros, comes from stunt doubles in film). They come in five kinds, and the distinctions matter because they lead to different kinds of test:

DoubleWhat it doesExample
DummyFills a parameter; never usedCheckout(gateway, logger=None)
StubReturns canned answersrate provider that always returns 1.1
SpyRecords calls for later inspectionnotifier that appends to self.sent
MockPre-programmed expectations; fails if not metmock.assert_called_once_with(...)
FakeWorking, simplified implementationin-memory repository; model returning canned text

Two testing styles follow. State-based testing runs the code with stubs or fakes and checks the resulting state or return value: "after the transfer, account A has 50 and B has 150". Interaction-based testing uses mocks to check the code made particular calls: "the gateway's charge was called once with 5,000 cents". Interaction tests are necessary when the call is the behaviour — sending an email, publishing an event — but they couple the test to how the code does its job. Here's the contrast on one example:

from unittest.mock import Mock

# interaction-based: checks HOW
def test_transfer_calls_repo_mock():
    repo = Mock()
    repo.balance.return_value = 100
    transfer(repo, "A", "B", 50)
    repo.debit.assert_called_once_with("A", 50)
    repo.credit.assert_called_once_with("B", 50)

# state-based with a fake: checks WHAT
def test_transfer_moves_money_fake():
    repo = InMemoryAccounts({"A": 100, "B": 100})
    transfer(repo, "A", "B", 50)
    assert repo.balances() == {"A": 50, "B": 150}

If transfer is refactored to call a single repo.move("A", "B", 50), the mock test fails although behaviour is unchanged; the fake test still passes. Worse, mocks can lie in the other direction: Mock() accepts any method name, so a test that stubs repo.get_balance passes even if the real class calls it balance. Python's create_autospec (or patch(..., autospec=True)) makes the mock reject calls the real object wouldn't accept, which removes the worst of this.

The rules that follow: prefer real objects for your own pure code; prefer fakes and stubs for your own infrastructure interfaces; use mocks for outgoing commands where the call is the behaviour; and don't mock types you don't own — wrap a third-party client in an adapter (swe2) and fake the adapter, then test the adapter itself against the real service in a few integration tests. The injection from swe2 is what makes all this possible without patching.

5. Coverage and what it doesn't measure

Line coverage is the fraction of lines executed during the test run; branch coverage is the fraction of decision outcomes (each side of each if) executed. Tools like coverage.py report both. Coverage is excellent at one thing: finding code no test runs at all — usually error handling, which swe4 showed is where many incidents start.

It measures nothing about whether results were checked. Consider:

def shipping_cost(weight_kg: float, coupons: int) -> Decimal:
    base = Decimal("5.00") + Decimal("1.20") * Decimal(str(weight_kg))
    discount = Decimal("3.00") * coupons
    return base - discount                      # bug: can go negative

def test_shipping_cost_runs():
    shipping_cost(2.0, 1)                        # 100% line and branch coverage, no assertion

Full coverage, bug intact. A meaningful test would check shipping_cost(1.0, 3) >= 0 — which fails, since 5 + 1.2 − 9 = −2.80. The stronger measure is mutation testing: a tool (such as mutmut for Python) makes small changes to the code — flips - to +, < to <=, deletes a line — reruns the tests, and reports mutants that survive. A surviving mutant is a behaviour no test checks. Mutation testing is slow, so teams run it on critical modules or on changed files only. The practical policy most teams land on: report coverage, look at uncovered lines in review, don't gate merges on a number.

6. Other kinds of test worth knowing

Property-based tests state a rule and check it on many generated inputs instead of hand-picked examples: "for any list of transfers, total money is conserved", "parsing the output of format returns the original value", "sorting twice equals sorting once". Libraries such as Hypothesis generate inputs, including nasty edge cases (empty lists, huge numbers, unicode), and shrink a failing input to a minimal example. Contract tests check that a service and its consumers agree on request and response shapes without running them together — essential when services deploy independently (swe10). Golden or snapshot tests compare output with a stored known-good copy — useful for rendered reports or prompts, dangerous if people approve snapshot updates without reading them. Characterisation tests pin down what legacy code currently does before you change it (swe11).

7. Flaky tests: definition, causes and the arithmetic

A flaky test passes and fails on the same code. Almost every flake comes from one of five sources:

  • Ordering and concurrency: the test assumes an order the code never promised — threads finishing in sequence, a set iterating a certain way, async tasks completing in submission order.
  • Time: real clocks (tests that fail at midnight or month-end), sleep-based waiting, and assertions on elapsed wall-clock time that a slow or busy machine exceeds.
  • Shared state: module-level caches, singletons, database rows or files left by one test and read by another, so the result depends on which tests ran before — and runners may reorder or shard tests.
  • External dependencies: real network calls, third-party sandboxes, DNS.
  • Resources: port collisions, memory or CPU limits in CI, timeouts tuned on a fast laptop.

Flakiness compounds. If each test independently flakes on 1.5% of runs, the probability that a suite of n such tests is fully green is 0.985n: about 0.86 for 10 tests, 0.22 for 100, and 0.9851000 = e1000 × ln 0.985 ≈ e−15.1 ≈ 2.7 × 10−7 for 1,000 — essentially never. Real suites aren't made entirely of flaky tests, but the lesson holds: even rare flakiness per test makes a large suite untrustworthy, so flakes must be treated as bugs, not background noise.

8. A flaky test traced to its root cause

A service fetches several documents for a retrieval step in parallel:

from concurrent.futures import ThreadPoolExecutor, as_completed

def fetch_all(ids):
    with ThreadPoolExecutor(max_workers=4) as ex:
        futs = [ex.submit(fetch_one, i) for i in ids]
        return [f.result() for f in as_completed(futs)]

def test_fetch_all():
    assert fetch_all(range(5)) == ["doc0", "doc1", "doc2", "doc3", "doc4"]

It passed for months on CI, then started failing "randomly" after a network change. Step 1: reproduce and measure. Rerun it many times (the lab does 200): locally it fails about 90% of the time; on the old CI runners, where the stub server answered in strict order, almost never. A test whose failure rate depends on the machine is a strong hint that timing or ordering is involved. Step 2: find the non-deterministic input. Log the order in which futures complete: it varies run to run, following each request's latency.

Step 3: decide whose bug it is. Does the caller need results in input order? If yes, the code is wrong and the test was right to fail: use ex.map(fetch_one, ids), which returns results in input order regardless of completion order. If no, the test over-specified: compare as a set or sort before comparing. Here the reranker downstream paired results with scores by position, so this was a latent production bug that the flaky test had been reporting all along — exactly why "just rerun it" is dangerous. Step 4: confirm. Rerun the fixed test hundreds of times: 0 failures.

The lab reproduces this flake and two others. The timing flake asserts that a function finishes in under 8 ms; the work takes 4–9 ms depending on load, so it fails about a quarter of the time; the fix injects a fake clock and asserts on the computed duration, not the wall clock. The shared-state flake has three tests using a module-level cache; in some orders a test sees counts left by another, so about half of the random orderings fail; the fix gives each test its own state. Each fix removes the non-determinism rather than hiding it.

The general cures follow the causes: inject clocks and randomness (swe2) and seed generators; wait on conditions with a timeout instead of sleeping (wait_until(lambda: job.done, timeout=5)); give every test fresh state (fixtures, transactions rolled back, unique temporary directories and ports); never call real external services in the blocking suite; and make assertions order-independent unless order is part of the contract. Running tests in random order (the pytest-randomly plugin) and in parallel (pytest-xdist) exposes shared-state flakes early, on purpose.

9. Testing systems with non-deterministic models

An LLM feature looks untestable because the model gives different answers to the same prompt. Split it into two layers and it isn't.

Layer one: the deterministic code around the model — building the prompt from templates and retrieved context, parsing and validating output, retries and fallbacks, routing by label, caching. This is ordinary code and gets ordinary unit and integration tests with a fake model (swe2) that returns scripted outputs, including the malformed ones swe4's parser must reject. Most bugs in LLM features live here, and these tests are fast and exact.

Layer two: the model's behaviour, tested against the real model with an evaluation set: representative inputs with expected labels or grading rules. Three techniques keep it meaningful. Assert properties, not strings: the output parses, the label is allowed, the answer cites one of the retrieved documents, it doesn't contain the system prompt. Use invariance tests: paraphrasing a question, or changing a customer's name, shouldn't change the label. Respect sampling noise: with 200 examples at about 90% accuracy, the standard error is √(0.9 × 0.1 / 200) ≈ 0.021, so a 95% interval is about ±4.2 percentage points; a hard gate of "accuracy ≥ 90%" will flap. Compare the new prompt or model against the old one on the same examples (a paired comparison), and size the set to the change you care about. Setting temperature to 0 reduces variation but doesn't make outputs identical across runs or model versions, so tests shouldn't depend on exact text. For integration tests, record and replay real responses once and replay them in CI, refreshing the recordings deliberately.

Test design that survives refactoring

The tests that cost teams most aren't the missing ones; they're the brittle ones that break on every harmless change, so each refactor also means rewriting dozens of tests. Brittleness has a common root: the test knows something about the implementation that callers don't. Heuristics that prevent it: test through the narrowest public interface that exposes the behaviour; assert on outcomes (return values, persisted state, published events) rather than on internal calls; build test data with small factory functions (make_order(status="paid")) so a new required field changes one helper, not two hundred tests; and name tests after behaviours (test_refund_is_rejected_after_30_days) rather than methods (test_refund_2). Google's testing book frames the goal as tests that are "unchanging": a test should need to change only when the requirement it checks changes.

The London and Detroit schools

Two long-standing approaches to unit testing differ on doubles. The classicist ("Detroit") school tests a unit together with its real collaborators, doubling only awkward ones like databases and clocks, and verifies state. The mockist ("London") school, associated with Growing Object-Oriented Software, Guided by Tests, isolates each class, mocks its collaborators and verifies interactions, using tests to drive the design of the interfaces between objects. Mockist tests localise failures precisely and encourage small interfaces; classicist tests survive refactoring better and catch integration mistakes between your own classes. Most experienced teams end up classicist for domain logic and mockist only at the edges (outgoing commands to other systems), which is the policy in the body. Knowing the names helps in interviews because the debate comes up.

Test-driven development, briefly and honestly

TDD is the practice of writing a failing test before the code that makes it pass, in short red-green-refactor cycles. Its real benefits are design pressure (code written to be tested first tends to have injectable dependencies and small interfaces), a suite that tests behaviour (because it was written before the implementation existed) and very short feedback loops. Its costs are real too: it's awkward for exploratory work where the interface isn't known, and dogmatic TDD can produce the over-mocked, implementation-coupled suites described above. Controlled studies of TDD's effect on quality are mixed. A pragmatic position for interviews: write tests first when the behaviour is well specified (a bug fix — first reproduce the bug in a failing test — or a parser with known cases), and write them alongside the code when exploring.

Hermetic tests and the flakiness budget

A test is hermetic if everything it depends on is created by the test itself and torn down afterwards: its own database schema, its own ports, fixed seeds, fake clocks, no network outside the test's sandbox. Hermetic tests are the structural cure for most flakiness because they remove the shared environment where flakes live. Large organisations enforce it with build systems that sandbox tests (Bazel's network-blocked sandboxes) and with tooling that tracks each test's flake rate over time, automatically quarantines a test whose rate exceeds a threshold, and files a bug to its owner. The quarantine matters: a quarantined test keeps running and reporting, so its signal isn't lost, but it no longer blocks merges. What should never happen is automatic retry-until-green as a blanket policy, which converts every intermittent product bug into a silently passing test.

Evaluating models: from unit tests to statistical tests

Model evaluation borrows from testing but is really measurement. Three refinements matter at senior level. Paired comparisons: when comparing a candidate prompt or model with the baseline on the same examples, what matters is the examples that changed — say 14 flipped from right to wrong and 8 from wrong to right. McNemar's test on those 22 discordant pairs asks whether a 14/8 split is surprising under "no difference" (it isn't: a two-sided p-value is about 0.29), which is far more sensitive than comparing two accuracies with independent intervals. Multiple samples per example estimate each example's pass probability and separate "the model can't do this" from "the model sometimes does this". Slices: an overall score can stay flat while a critical slice (a language, a customer tier, long inputs) regresses badly, so evaluation sets should be tagged and reported per slice. LLM-as-judge grading, where a model scores outputs, needs its own validation against human labels, because the judge has biases (favouring longer answers, or answers resembling its own style).

Testing the tests

How do you know a suite is good? Mutation score on critical modules tells you whether behaviours are checked. The escaped-defect rate — bugs found in production that a test should have caught — tells you whether tests are at the right level. Time to feedback (the p90 duration of the merge-blocking suite) tells you whether people will run it. And flake rate tells you whether people will believe it. A suite that's fast, believed, and catches the bugs that matter is the goal; line coverage is at best a weak proxy for the first of those.

How test suites decay in production teams

Suites rarely start bad; they decay. The merge-blocking run creeps from 5 minutes to 40 as end-to-end tests accumulate, so developers batch changes and CI becomes a queue. A few flaky tests appear, "rerun" becomes a reflex, and soon a red build carries no information. Coverage gates are introduced, and tests are written to hit lines rather than check behaviour. Mocks of vendor APIs drift from reality, so the suite is green while production integrations break. The signals to watch are measurable: p50 and p90 duration of the blocking suite, the fraction of CI runs that fail and then pass on rerun with no code change (the observable flake rate), the number of quarantined tests and their age, and escaped defects by the level at which a test would have caught them.

Case: flaky tests at Google

Google has published unusually detailed data on flakiness. In a 2016 Google Testing Blog post, John Micco, who led work on Google's continuous-integration system, reported that across Google's entire corpus of tests there was "a continual rate of about 1.5% of all test runs reporting a 'flaky' result", defined as a test that "exhibits both a passing and a failing result with the same code". Almost 16% of tests had some level of flakiness — more than one in seven. Most strikingly, about 84% of the transitions from pass to fail that the CI system observed involved a flaky test. That last number is the one that destroys trust: when a test goes red, the most likely explanation is flakiness, not your change, so people stop investigating — and the post notes that it's common to ignore legitimate failures in flaky tests.

The post also works through the arithmetic this lesson used. The average project contains about 1,000 tests, all of which must pass to release; with 1.5% of results flaky, around 15 tests will fail by chance, each needing investigation. Google's mitigations included rerunning only failing tests to confirm flakiness, a tool that monitors flakiness and quarantines tests above a threshold, filing bugs to owners, and detecting code changes that introduce flakiness.

A 2017 follow-up by Jeff Listfield analysed where flakes come from. Google then had about 4.2 million tests in CI, of which about 63,000 had a flaky run over a week — under 2%, but a significant drag. The strongest predictor was test size: flakiness correlated with a test's binary size (r² = 0.82) and memory use (r² = 0.76), and tests built on heavyweight tools such as WebDriver browser automation and the Android emulator were flakier, largely because they tended to be large. That's the empirical foundation for "keep most tests small and hermetic": each dependency a test pulls in is another source of non-determinism.

The same problems in ML and LLM teams

ML codebases add their own flake sources: non-deterministic GPU kernels that change a loss in the fifth decimal place, data loaders whose shuffling isn't seeded, tests that download a model or dataset from the internet, and tests that call a hosted model and assert on its exact wording. The cures are the same principles: seed everything and use tolerance-based comparisons for floating point (math.isclose, torch.testing.assert_close); keep tiny fixture models and datasets in the repository; replace hosted-model calls in the blocking suite with fakes or recorded responses; and move real-model checks into a separate evaluation job whose results are tracked over time rather than treated as pass/fail gates on every commit. When a model or prompt version changes, the evaluation job is what decides whether it ships — with a sample size that makes the decision meaningful.

Tools and knobs

For Python: pytest with fixtures and parametrize; unittest.mock.create_autospec so mocks match real signatures; coverage.py with branch coverage to find untested error paths; mutmut for mutation testing on critical modules; Hypothesis for property tests; Testcontainers to start real Postgres, Redis or Kafka for integration tests; pytest-randomly and pytest-xdist to run in random order and in parallel, exposing shared-state flakes; freezegun or an injected clock for time; and a flake tracker (many CI systems have one) with automatic quarantine and ownership.

"""swe5 lab: reproduce three flaky tests by re-running them, find each root cause, and show the fix is 0% flaky."""
import random
import time
from concurrent.futures import ThreadPoolExecutor, as_completed

RUNS = 200

# ---------- code under test ----------
def fetch_one(i: int) -> str:
    time.sleep(random.uniform(0, 0.002))           # network latency varies
    return f"doc{i}"

def fetch_all_as_completed(ids):                   # returns results in COMPLETION order
    with ThreadPoolExecutor(max_workers=4) as ex:
        futs = [ex.submit(fetch_one, i) for i in ids]
        return [f.result() for f in as_completed(futs)]

def fetch_all_ordered(ids):                        # executor.map preserves INPUT order
    with ThreadPoolExecutor(max_workers=4) as ex:
        return list(ex.map(fetch_one, ids))

def slow_summarise(clock=time.perf_counter) -> float:
    start = clock()
    time.sleep(random.uniform(0.004, 0.009))       # real work takes 4-9 ms, depending on the machine
    return clock() - start

_CACHE: dict[str, int] = {}                        # module-level state shared between tests
def count_word(word: str, cache=_CACHE) -> int:
    cache[word] = cache.get(word, 0) + 1
    return cache[word]

# ---------- flaky tests and their fixed versions ----------
def flaky_order():
    assert fetch_all_as_completed(range(5)) == [f"doc{i}" for i in range(5)]
def fixed_order():
    assert fetch_all_ordered(range(5)) == [f"doc{i}" for i in range(5)]

def flaky_timing():
    assert slow_summarise() < 0.008                # asserts on wall-clock speed
def fixed_timing():
    ticks = iter([100.0, 100.5])                   # fake clock: the test controls time
    assert slow_summarise(clock=lambda: next(ticks)) == 0.5

def flaky_shared_state():
    tests = [lambda: count_word("llm") == 1, lambda: count_word("gpu") == 1, lambda: count_word("llm") >= 1]
    random.shuffle(tests)                          # runners may reorder tests (random-order plugins, parallel shards)
    try:
        assert all(t() for t in tests)
    finally:
        _CACHE.clear()                             # without this, one failure would poison every later run
def fixed_shared_state():
    tests = [lambda c: count_word("llm", c) == 1, lambda c: count_word("gpu", c) == 1, lambda c: count_word("llm", c) >= 1]
    random.shuffle(tests)
    assert all(t({}) for t in tests)               # each test gets its own fresh state

def failure_rate(test) -> float:
    fails = 0
    for _ in range(RUNS):
        try:
            test()
        except AssertionError:
            fails += 1
    return fails / RUNS

Plan the tests

A TransferService.transfer(from_id, to_id, amount) moves money between accounts in Postgres, charges a fee from a FeePolicy, and publishes a TransferCompleted event to Kafka. Which tests do you write, at which level, with which doubles?

Answer

Unit tests (fast, many) with a fake in-memory repository and a spy event publisher: happy path moves amount + fee correctly; insufficient funds raises and changes nothing; negative or zero amount rejected; same-account transfer rejected; fee policy injected so fee edge cases are tested separately on FeePolicy; event published once with the right payload, and not published on failure. Use state-based assertions on balances, not mock call sequences.

Integration tests against a real Postgres (Testcontainers), each in a transaction rolled back afterwards: the transfer is atomic — kill it between debit and credit and assert no partial state; concurrency — 50 parallel transfers from one account never overdraw it (this is where lost-update bugs live, and no unit test can find them; swe12 covers why); the SQL uses the right isolation level or a conditional update.

Contract test for the event: the published message matches the schema consumers depend on (schema registry compatibility check or a consumer-driven contract).

Property test: for random sequences of transfers, total money across all accounts changes only by the fees collected, and no balance goes negative.

Not: mocking the Postgres driver, or an E2E test for every edge case. One E2E smoke test through the API is enough. Also flag the dual-write problem: a database commit plus a Kafka publish is not atomic — use a transactional outbox, and test that a crash after commit still publishes exactly once (or at least once, with an idempotent consumer).
