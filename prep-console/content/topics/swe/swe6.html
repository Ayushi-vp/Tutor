Two reviews of the same pull request. The first reviewer leaves 38 comments: rename this variable, add a blank line there, prefer a list comprehension, this docstring has a typo. The author spends a day addressing them, resentfully. Nobody notices that the new endpoint returns another customer's invoice if you change the ID in the URL, because the ownership check was never written. The second reviewer leaves four comments. One is marked blocking: "This endpoint loads the invoice by ID without checking it belongs to the caller — anyone can read any invoice. Could we scope the query by customer_id, and add a test that a different customer gets 404?" Two are suggestions with reasons. One says the retry logic is nicely done. The change merges the same afternoon, safer.

Code review is one of the few practices nearly every software team shares, and one of the most variable in quality. Done badly, it's a bottleneck that adds days of latency, a venue for style arguments, and a ritual that approves what nobody read. Done well, it catches the defects tests miss, spreads knowledge of the system across the team, keeps a codebase coherent as dozens of people change it, and is the main way engineers learn from each other. The difference is rarely talent; it's a set of learnable habits on both sides of the review.

This lesson covers those habits: what review is actually for, backed by Google's published study of nine million reviewed changes; how authors make changes easy to review, including splitting large work into stacks of small changes; what reviewers look for, in what order, and what they should leave to tools; how to write feedback that lands and handle disagreement; and how to keep review fast. The case study is Apple's 2014 "goto fail" bug — one duplicated line in the code that verifies secure connections, which silently disabled a crucial check on hundreds of millions of devices, and which is the canonical example of what a careful read of a diff can catch. The lab builds a tiny review bot that flags the same shape of bug automatically. Because this is an AI-engineering track, it also covers reviewing changes that aren't code in the usual sense: prompts, model versions and evaluation results.

The analogy: a co-pilot's cross-check

In a cockpit, the pilot flying sets the altimeter or enters a route, and the co-pilot independently checks it and calls it out. The check isn't an insult to the pilot's skill; it's a system that assumes anyone can make a slip, and it works because it's routine, quick and focused on what matters — altitude, heading, fuel — not on how neatly the pilot wrote the flight plan. Both pilots also learn from each other's habits over thousands of flights. Code review is the same cross-check: routine, focused, fast, and a source of shared knowledge.

The analogy breaks on timing. A co-pilot's check takes seconds and happens in the moment; a code review is asynchronous, and a check that waits two days in someone's queue has a real cost — the author has moved on, context is lost, and changes pile up. Speed is part of the practice, not an afterthought.

What review is for

Ask engineers why they review code and "finding bugs" comes first. It's real, but the evidence says review does several jobs at once. Google's 2018 study of its own review process — interviews, a survey, and logs of about 9 million reviewed changes by more than 25,000 engineers — found reviewers doing education (teaching and learning the codebase and conventions), maintaining norms (consistency and readability), gatekeeping (owners of code seeing changes to it), and accident prevention (catching bugs and design mistakes). The educational effect showed up in the data: engineers in their first year received more than twice as many comments per change as experienced ones, and the number of files engineers had seen through review grew steadily with seniority.

The lifecycle of a change

A change's path from idea to production has a few steps, and most of the leverage is in the early ones:

Notice where the leverage is. By the time a human reviewer opens the diff, three things should already be settled: the change is small enough to read carefully in one sitting, its description tells the reviewer what to look for, and every mechanical question — formatting, lint, types, whether the tests pass — has been answered by a machine. A reviewer who has to reconstruct the intent of a 1,400-line change from its code, or who spends the first twenty minutes on indentation, has been set up to miss the one line that matters. Most bad reviews are caused upstream of the reviewer.

A change is usually submitted as a pull request (PR) — also called a merge request, or at Google a changelist (CL): the diff, a description, and a discussion thread. The author writes and describes it; one or more reviewers read it and comment; the author iterates; a reviewer approves ("LGTM", looks good to me); the change merges. Everything that follows is about making each step cheap and effective: authors doing the work that makes review easy, tools doing the work that doesn't need a human, and reviewers spending their attention where it matters most.

1. The author's job: small, single-purpose, well described

The most effective review improvement is made before anyone reviews: making the change small. Review quality drops as size rises — reviewers skim, useful comments per line fall, and latency grows — and a small change can be reverted on its own if it breaks something. Google's numbers show what "small" means in a healthy process: across roughly 9 million changes, the median modified 24 lines, over 35% touched a single file, and about 90% touched fewer than 10 files. That's not because Google's features are small; it's because features are delivered as sequences of small changes.

Three rules keep changes small and reviewable. One purpose per change: a refactor that changes no behaviour, a behaviour change, a dependency upgrade and a formatting sweep are four changes, because a reviewer reads each differently — a pure refactor is checked for "nothing changed", a behaviour change for "the right thing changed". Separate mechanical from meaningful: a rename touching 80 files goes in its own change, clearly labelled, so the 30-line logic change isn't hidden in it. Stack dependent work: when a feature needs several steps, submit them as a stack of small changes, each reviewable and mergeable on its own.

The description does half the reviewer's orientation. A good one answers five questions: what changes (one or two sentences), why (the problem or ticket, and why this approach over alternatives), how it was tested (tests added, manual checks, evaluation results), risk (what could break, who's affected), and rollback (revert safely? behind a flag?). For UI changes add screenshots; for performance changes, before-and-after numbers; for prompt or model changes, evaluation results.

Self-review is the cheapest review there is: read your own diff in the review tool, as a reviewer would, before asking anyone. Authors routinely catch debugging leftovers, commented-out code, missing tests, and accidental changes this way. Leave comments on your own diff where a reviewer will need context ("this looks redundant but X relies on it").

2. Let machines do what machines can

Every comment a tool could have made is wasted human attention and a source of friction. Before human review, CI should run a formatter (Black or Ruff's formatter — formatting is then not a topic), a linter (Ruff: unused imports, bare except, mutable default arguments, complexity), a type checker (mypy or pyright), the tests, and scanners for secrets and known-vulnerable dependencies. Automated review comments can also flag things like unreachable code, which, as the case study shows, is sometimes a critical bug. The rule: if a comment could be written by a rule, write the rule instead, once.

3. The reviewer's job: attention in order of importance

Review time is limited, so spend it in order of what costs most if missed. A practical sequence:

  1. Is this the right change? Read the description first. Does the change solve the stated problem? Is the approach sound, or is there a simpler design? Does the code belong in this module (swe1)? A design problem found here saves the author polishing code that will be rewritten; if the design is wrong, say so first and stop — line comments can wait.
  2. Is it correct? Edge cases (empty input, zero, maximum sizes, unicode), error paths (swe4), concurrency — two requests at once, retries, ordering (swe12) — and compatibility: will this work while old and new versions run side by side during a deploy? Will this migration lock a large table?
  3. Do the tests prove it? Would the new tests fail if the behaviour were wrong? Do they assert outcomes, cover the error paths, avoid timing and order dependence (swe5)? Is there a test for the bug being fixed?
  4. Is it secure and operable? Authorisation on every data access, input validation, secrets out of code, sensitive data out of logs (swe13); timeouts on external calls, useful logs and metrics, a way to roll back or turn it off.
  5. Is it readable? Names, function size, comments explaining why (swe4). Important, but last, and mostly suggestions rather than blockers.

Two habits make the sequence work. Read the tests early — they're the author's statement of intended behaviour, and gaps in them point to gaps in thinking. And read the whole diff, line by line, for anything that controls security or money. The case study is a single line.

4. A worked review

Here's a small diff adding an endpoint that returns an invoice, and a review of it.

+@app.get("/invoices/{invoice_id}")
+def get_invoice(invoice_id: int, user: User = Depends(current_user)):
+    try:
+        inv = db.query(Invoice).get(invoice_id)
+    except Exception:
+        return {"error": "not found"}
+    return inv.to_dict()

A focused review, using labels in the style of conventional comments (a label plus whether it blocks):

  • issue (blocking): "This loads any invoice by ID and never checks it belongs to user, so any logged-in user can read any invoice by changing the number. Could we query with customer_id=user.customer_id and return 404 when it doesn't match? And a test that another customer gets 404."
  • issue (blocking): "except Exception turns a database outage into a 'not found' with status 200. .get() returns None when there's no row, so we can drop the try, check for None and raise HTTPException(404); let real errors reach the error handler."
  • question: "Does to_dict() include the internal fraud_score field? If so we probably don't want it in the response — maybe a response model with explicit fields?"
  • praise: "Nice use of the current_user dependency — keeps auth consistent with the other routes."

Four comments, two blocking, each with a reason and a concrete suggestion, the most serious first. No comments on naming, since nothing was confusing. The reviewer found the two defects that matter by asking the step-2 and step-4 questions: what if the caller isn't the owner? and what happens when the database is down?

5. Writing feedback that lands

A review comment's job is to change the code, and that depends on the author accepting it. The practices that help are simple and consistently effective:

  • Comment on the code, not the person. "This function reads the balance and writes it back without a lock" rather than "you forgot about concurrency".
  • Explain why. "Prefer X" teaches nothing and invites argument; "X, because under two concurrent requests this read-then-write loses an update" teaches and persuades.
  • Label severity. Authors can't read minds: say what blocks merging and what's a take-it-or-leave-it nit. Conventional comments (issue, suggestion, question, nit, praise, with (blocking) or (non-blocking)) make this explicit.
  • Ask when you're unsure. "What happens if the list is empty here?" is honest when you don't know, and invites the author to explain or discover the bug themselves.
  • Say it once. If a pattern repeats, comment once and note "same in 6 other places", rather than 7 identical comments.
  • Note what's good. Specific praise ("the retry wrapper is cleanly separated") reinforces practices you want repeated and makes the critical comments easier to receive.
  • Escalate the medium, not the tone. After two rounds of back-and-forth on the same point, talk — a five-minute call resolves what twenty comments won't.

6. Receiving feedback, and disagreement

For authors, the useful stance is that comments are about the code and the reviewer is on the same side. Reply to every comment — with a fix, a question, or a reasoned disagreement — so the reviewer knows it was seen. Don't take nits personally; accept cheap ones even if you mildly prefer your version, and save your disagreement for things that matter. When you disagree, bring evidence (a benchmark, a link to the team standard, a failing case) rather than repeating your position. If a disagreement is purely taste and there's no team rule, defer to the code's owner, and if it keeps recurring, propose a rule so it's decided once. If it's substantive and unresolved, write down both options and ask a tech lead — a decision recorded in an architecture decision record (swe15) stops it being relitigated in every review.

7. Speed: review latency is a team metric

Slow review is expensive in ways that don't show up on a dashboard: authors context-switch to other work, changes pile up and conflict, and the temptation grows to batch changes into large PRs — which are slower to review, which makes the problem worse. Google's study found the median time from sending a change for review to approval was under four hours across all sizes, with a median wait for first feedback under an hour for small changes, and over 80% of changes needing at most one round of revisions; 70% of changes were committed within 24 hours of being sent. That speed comes from habits, not heroics: small changes, style automated away, and a norm that responding to a review takes priority over starting new work. Google's public guidance sets one business day as the maximum for a first response. Useful team measures are time to first review, time to approval, rounds per change and change size — not comment counts, which reward nitpicking.

Reviewer count matters too. At Google, the median change had exactly one reviewer, fewer than 25% had more than one — typically because a second approval was needed for ownership of files in another area. One knowledgeable reviewer who reads carefully beats three who each assume another read carefully.

8. Reviewing what isn't ordinary code

Some changes need a different lens. Schema migrations: will they lock a large table, and are they compatible with the version currently running (expand–contract, swe9)? Configuration and infrastructure: a one-line config change can take down every service; ask what the blast radius is and how it rolls out. Dependency upgrades: read the changelog for breaking changes and check the lockfile diff is what you expect. Deletions: is anything still calling this? And, increasingly, prompts and model configuration. A prompt template is behaviour: a changed instruction can shift outputs across every request. Keep prompts in version-controlled files so diffs are readable, require evaluation results in the description (the standard evaluation set, old versus new, with examples of changed outputs), check cost and latency effects, and make sure the change is versioned or behind a flag so it can be rolled back. "It looked better on the three examples I tried" is the prompt equivalent of "it works on my machine".

9. A reviewer's checklist for ML and LLM code

Machine-learning code has failure modes that ordinary review habits miss, so it's worth a few extra questions. Leakage: does any feature, normalisation statistic or tokenizer vocabulary get computed on data that includes the test set (ml9)? Train–serve consistency: is preprocessing shared between training and serving code, or duplicated so that it can drift (ml14)? Seeds and determinism: can the result be reproduced? Silent shape and dtype changes: a broadcast that turns a (32,) vector into a (32, 32) matrix trains without error and produces nonsense. Untrusted model output: is every model response parsed and validated before it reaches business logic or a database (swe4)? Cost: does the change add a model call inside a loop, multiplying spend and latency? And evaluation: is there evidence, on a fixed evaluation set, that the change helps — and is that set itself unchanged in this PR? None of these needs deep ML expertise to ask; all of them catch real incidents.

10. Beyond review: collaboration that makes review easier

Code review is late in the process; some problems are cheaper to catch earlier. A design review of a short document before a large change (swe15) catches wrong approaches before hundreds of lines are written. Pair programming — two people, one keyboard — is continuous review, and for tricky or unfamiliar code often faster than write-then-review. Ownership files (CODEOWNERS) route changes to people who know an area and make responsibility explicit. And team conventions written down — a style guide, a list of what reviewers look for, comment labels — turn review from personal preference into shared practice, which is what lets it scale.

What the research says review actually finds

Studies of review at Microsoft, Google and in open source converge on a picture that surprises people who think of review as bug-hunting. A large share of review comments concern maintainability — naming, structure, documentation, simpler alternatives — rather than functional defects, and reviewers who know the code well give markedly more useful comments than those who don't. That has practical consequences. Reviewer selection matters more than reviewer count: route changes to people who have recently edited or reviewed the same files (Google's tool does exactly this). Defect detection is strongest on small changes and falls off sharply with size. And because review is a relatively weak detector of deep functional bugs, it should be one layer among several — types, tests, static analysis, staged rollout — not the primary defence. The Google paper also found review is valued for "accident prevention" and "gatekeeping" even when few defects are found, because the knowledge that someone else will read the code changes how carefully it's written.

Ownership and readability: Google's two gates

Google's process has two explicit requirements beyond "someone approved it". Ownership: every directory has owners listed in a file, and a change needs approval from an owner of each affected directory, so the people accountable for an area see every change to it. Readability: a certification, per language, that an engineer writes idiomatic code; a change needs approval from someone with readability in its language. Usually one reviewer satisfies both, which is why the median reviewer count is one. The general principles transfer: make accountability explicit (CODEOWNERS on GitHub and GitLab implement ownership), and make style standards a thing that's taught and certified once rather than argued in every review.

Review as a security control, and its limits

Review is good at a specific class of security issue: logic flaws a tool can't see. Missing authorisation checks (the "insecure direct object reference" in the worked example), trusting client-supplied prices or roles, logging tokens, building SQL or shell commands from input, and in LLM applications, prompt-injection paths where retrieved documents or tool results are treated as instructions. It's weak at subtle memory-safety bugs, timing side channels and cryptographic misuse, which need specialised tooling and expert reviewers. The 2021 incident in which malicious commits were pushed to the PHP project's source repository under two maintainers' names (swe8 covers it) shows review has an adversarial dimension too: the commits were noticed and reverted by maintainers, and the project responded by retiring its self-hosted Git server and making its GitHub repositories canonical, with organisation membership and two-factor authentication required. A mature approach assigns security-owner review to sensitive paths, runs automated scanners in CI, and uses threat modelling at design time (swe13), rather than assuming generalist reviewers will catch everything.

Stacked changes and trunk-based development

Small changes only stay small if the workflow supports shipping incomplete features. Two techniques make it possible. Stacked changes let an author submit change 2 that builds on unmerged change 1, and change 3 on 2, each reviewed independently; tools such as Graphite, Sapling, git-branchless and Gerrit's relation chains manage the rebasing when an early change is revised. Feature flags let incomplete functionality merge to the main branch while switched off, so a feature can arrive in ten small changes rather than one branch that lives for weeks. Together they enable trunk-based development (swe8), in which everyone integrates into one main branch at least daily — which in turn makes every change small enough to review well. Review practice and branching strategy are two halves of the same system.

AI-assisted review, used well

LLM-based review assistants can summarise a change, flag likely bugs and suggest tests, and they're increasingly common in review tools. Used well, they handle the mechanical layer — "this except swallows everything", "this variable is unused", "this function lacks a test for the empty case" — so human reviewers can focus on design and intent. Their limits follow from how they work: they don't know the system's history, the business rules behind a design, or which of their plausible-sounding comments are false positives, and their suggestions can be confidently wrong. Treat their comments as a linter with unusually broad coverage and a high false-positive rate: helpful input to the author, never a substitute for an accountable human approval. And when the code itself was generated by a model, review matters more, not less — the author may understand it less well than code they typed, so the description should say which parts were generated and how they were verified.

How review breaks down in real teams

The failure modes are predictable. Latency spirals: reviews wait days, so authors batch work into large PRs, which take longer to review, so latency grows further. Rubber-stamping: large or unfamiliar changes get "LGTM" after a skim, especially under deadline pressure, and approvals stop meaning anything. Nit storms: dozens of style comments, often inconsistent between reviewers, that frustrate authors and bury real issues. Gatekeeping bottlenecks: one senior engineer must approve everything in an area and becomes a queue. Review as the only safety net: teams that skip tests or staged rollouts because "it was reviewed". Each is visible in data most review tools expose: time to first review, time to merge, change size distribution, rounds per change, and reviewer load per person. Watching those numbers, and discussing them in retrospectives, fixes more than exhortation does.

Case: Apple's "goto fail" (CVE-2014-1266)

In February 2014 Apple shipped an unusual security update for iOS — 7.0.6, plus 6.1.6 for older devices — with a terse note that it fixed a problem verifying secure connections, followed days later by OS X 10.9.2. The bug, published by Google engineer Adam Langley the next day, was in Apple's SecureTransport library, which implements TLS (the protocol that encrypts HTTPS connections and proves a server's identity, net9) for most software on Apple's platforms. In the function that checks the server's signature over its key-exchange parameters, the code read:

if ((err = SSLHashSHA1.update(&hashCtx, &serverRandom)) != 0)
    goto fail;
if ((err = SSLHashSHA1.update(&hashCtx, &signedParams)) != 0)
    goto fail;
    goto fail;
if ((err = SSLHashSHA1.final(&hashCtx, &hashOut)) != 0)
    goto fail;
/* ... the signature is actually verified here ... */

fail:
    SSLFreeBuffer(&signedHashes);
    SSLFreeBuffer(&hashCtx);
    return err;

The second goto fail; is indented as if it belonged to the if, but in C an if without braces governs only one statement. So after the second hash update succeeded, the duplicated line jumped unconditionally to the clean-up code, with err still 0 — success — skipping the rest of the hash computation and the actual signature check. As Langley explained, this broke the link between the server's certificate and the key used for the connection: an attacker positioned on the network (on public Wi-Fi, say) could present a genuine server's valid certificate chain but sign the handshake with a different key, or not sign it properly at all, and the client would accept it. Most software on iOS and OS X that used SecureTransport was affected; browsers such as Chrome and Firefox, which used a different TLS library, were not. The vulnerability is recorded as CVE-2014-1266.

Langley's analysis is a small lesson in defence in depth, and he was careful not to blame an individual — "I believe that it's just a mistake and I feel very bad for whoever might have slipped in an editor". He listed what could have caught it. A compiler warning: Clang had -Wunreachable-code, which flags the code after the unconditional jump, but it wasn't part of the commonly used -Wall set. Coding style: mandatory braces around if bodies make this particular slip much harder (he noted indentation can mislead with braces too). A test: a negative test that presents a handshake signed with the wrong key — hard to write because it needs a deliberately misbehaving TLS peer, which is exactly why such tests are often missing. And code review: "Code review can be effective against these sorts of bug. Not just auditing, but review of each change as it goes in." A reviewer reading the diff that introduced the duplicated line would have seen two identical goto fail; lines in a row — the kind of anomaly that a careful line-by-line read of security-critical code exists to catch. The lab's review bot catches the Python equivalent automatically.

The AI-engineering angle

LLM systems add review surfaces that many teams leave unguarded. Prompt templates edited directly in a dashboard, bypassing version control and review, are the goto-fail of AI features: a one-line change with global effect and no diff. Model version bumps in configuration change behaviour everywhere at once. Evaluation sets can be changed in the same PR as the prompt they evaluate, quietly moving the goalposts. Good practice is to treat all of these as code: prompts and model configurations in the repository, changes reviewed with evaluation results attached, evaluation-set changes reviewed separately from the prompts they grade, and rollouts behind flags (swe9). And as code generation by models becomes common, review is where a human takes responsibility for code they didn't type.

Tools and knobs

Branch protection requiring an approval and passing CI before merge; CODEOWNERS for routing and ownership; pull-request templates prompting for what, why, testing, risk and rollback; formatters, linters, type checkers and secret scanners in CI so humans never comment on style; review-latency and change-size dashboards; stacked-change tooling for large features; and a short written guide to what reviewers look for and how comments are labelled. For C and C++ codebases, treat compiler warnings like -Wunreachable-code as errors; in Python, linters flag unreachable statements, and type checkers such as mypy can report them with --warn-unreachable.

Goal: build a tiny "review bot" that does what CI should do before a human looks: measure the size of a change, and flag the goto-fail shape of bug — code that can never run — plus two other review smells. Stdlib only (ast, difflib, re), Python 3.12, runs instantly.

  1. Save the script as swe6_lab.py and run python swe6_lab.py.
  2. It diffs a BEFORE and AFTER version of a small module. In AFTER, a "bad merge" left a stray return True in verify_server_key — the Python analogue of Apple's duplicated goto fail;: the signature check below it can never run, so the function accepts anything that hashes correctly. A new load_config also swallows every exception and hard-codes an API key.
  3. Expected output: the unified diff (+8 / -0 lines), then three findings:

  - line 6: unreachable after 'return True'
  - line 13: broad exception swallowed (except ...: pass)
  - line 15: possible hard-coded secret

What it shows. The unreachable-code check walks every block in the syntax tree and reports any statement that follows a return, raise, continue or break in the same block. It needs no understanding of cryptography to find a critical bug — which is exactly why such checks belong in CI, freeing human reviewers for the questions only they can answer, like "does this endpoint check the caller owns the invoice?"

Try next: (1) Delete the stray line from AFTER; the unreachable finding disappears and the assertion len(findings) == 3 fails, telling you to update it. (2) Add a rule that flags a changed source file with no corresponding test file changed. (3) Run the real tools on your own code: ruff check --select B,BLE,E722,S105 and mypy --warn-unreachable.

"""swe6 lab: a tiny review bot — size a change, then flag unreachable code (the 'goto fail' shape) and other review smells."""
import ast
import difflib
import re

BEFORE = '''
def verify_server_key(msg, sig, key):
    if not hash_ok(msg):
        return False
    if not check_signature(msg, sig, key):
        return False
    return True
'''

AFTER = '''
def verify_server_key(msg, sig, key):
    if not hash_ok(msg):
        return False
    return True                      # left behind by a bad merge
    if not check_signature(msg, sig, key):
        return False
    return True

def load_config(path):
    try:
        return json.load(open(path))
    except Exception:
        pass
    api_key = "sk-live-4f9c2d0e8b7a61"
'''

def diff_stats(before: str, after: str) -> tuple[int, int, list[str]]:
    diff = list(difflib.unified_diff(before.splitlines(), after.splitlines(), "before.py", "after.py", lineterm="", n=1))
    added = sum(1 for l in diff if l.startswith("+") and not l.startswith("+++"))
    removed = sum(1 for l in diff if l.startswith("-") and not l.startswith("---"))
    return added, removed, diff

def unreachable(tree: ast.AST) -> list[str]:
    """Statements that follow return/raise/continue/break in the same block can never run."""
    found = []
    for node in ast.walk(tree):
        for field in ("body", "orelse", "finalbody", "handlers"):
            block = getattr(node, field, None)
            if not isinstance(block, list):
                continue
            for stmt, nxt in zip(block, block[1:]):
                if isinstance(stmt, (ast.Return, ast.Raise, ast.Continue, ast.Break)):
                    found.append(f"line {nxt.lineno}: unreachable after '{ast.unparse(stmt)}'")
    return found

def smells(tree: ast.AST, src: str) -> list[str]:
    out = []
    for node in ast.walk(tree):
        if isinstance(node, ast.ExceptHandler):
            broad = node.type is None or (isinstance(node.type, ast.Name) and node.type.id in {"Exception", "BaseException"})
            if broad and all(isinstance(s, ast.Pass) for s in node.body):
                out.append(f"line {node.lineno}: broad exception swallowed (except ...: pass)")
    for i, line in enumerate(src.splitlines(), 1):
        if re.search(r"""(api_key|secret|password|token)\s*=\s*["'][^"']{8,}["']""", line, re.I):
            out.append(f"line {i}: possible hard-coded secret")
    return out

if __name__ == "__main__":
    added, removed, diff = diff_stats(BEFORE, AFTER)
    print(f"change size: +{added} / -{removed} lines")
    print("\n".join(diff))
    tree = ast.parse(AFTER)
    findings = unreachable(tree) + smells(tree, AFTER)
    print("\nreview bot findings:")
    for f in findings:
        print("  -", f)
    assert any("unreachable" in f for f in findings)
    assert len(findings) == 3
Handle it

A teammate's 1,400-line PR adds a new payments endpoint. It includes a refactor of the shared HTTP client, a schema migration, the endpoint, and tests. You spot that the migration drops a column the old service version still reads. How do you respond?

Answer

Blocking issue first, clearly labelled: dropping a column that the currently deployed version reads will break production during the rollout, when old and new versions run side by side. Propose expand–contract (swe9): this PR stops reading and writing the column; a later PR drops it after the old version is gone. Link to the team's migration guidelines if you have them.

Structure: ask to split into (1) the HTTP client refactor with no behaviour change, (2) the migration, (3) the endpoint behind a flag. Explain it's about review quality and safe rollback — each piece can be reverted independently — not about style. Offer to help split it or to pair on it if it's urgent.

Then the normal review on the endpoint, in priority order: authorisation (can one customer act on another's payment?), idempotency-key handling for payment retries, timeouts on the provider call, error handling that doesn't turn provider outages into "declined", and logging without card data.

Tone: a short summary comment or a call rather than 40 line comments; acknowledge the work and anything done well. This is the answer shape interviewers want: protect production, improve the process, keep the relationship.
