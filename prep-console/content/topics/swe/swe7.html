A mobile banking app sends "transfer £25" over a train's patchy connection. The request reaches the server and the transfer happens, but the response is lost in a tunnel. The app, seeing a timeout, retries. The customer is charged twice. The same month, the platform team renames a response field from verified to status because the new name is clearer; three partner integrations break overnight, because their code checked verified. And a support dashboard that pages through transactions with ?offset=20 shows some transactions twice and silently skips others whenever new ones arrive while an agent is scrolling.

None of these is a bug in the usual sense. Each is an API design decision — or a missing one. An API (application programming interface) is the contract through which other code talks to yours: which operations exist, what they accept, what they return, how they fail, and how all of that may change over time. Internal code can be refactored freely because you can update every caller in one change; an API's callers are in other teams, other companies, and apps installed on phones you'll never update. Once one client depends on a behaviour, changing it has a cost you don't control. That makes API design one of the few areas of software where getting it right up front really matters.

This lesson covers the design decisions that come up in every API and every interview about one: modelling resources and methods; status codes and machine-readable errors; idempotency keys that make retries safe; cursor pagination that doesn't skip or duplicate; long-running operations; and versioning and compatibility, using Stripe's published approach as the case study — a company that has kept every version of its API working since 2011. Then the three main styles, REST, gRPC and GraphQL, compared on the same call, down to the bytes on the wire. Finally, what's different about APIs that serve or call large language models (LLMs): streaming, pinned model versions, tool schemas and agents that retry. The lab encodes one response both ways by hand and simulates pagination and retries.

The analogy: a restaurant's menu and ordering system

A restaurant's menu is its API. It lists what you can order (operations), what you must specify (parameters: size, how cooked), and what you'll get back. The kitchen can change freely behind the pass — new ovens, new staff, a new supplier — as long as the dish that arrives matches the menu. But change the menu carelessly and regulars are upset: remove a dish, and people who came for it leave; quietly change what "large" means, and everyone who ordered large feels cheated. Good restaurants add new dishes freely, announce removals well in advance, and never change what an existing item means. And a good ordering system is safe to repeat: if a waiter isn't sure the kitchen got an order, they can check the ticket number rather than placing the order again and serving two meals.

The analogy breaks on scale and memory. A restaurant's regulars can be told about changes; an API may have thousands of clients whose authors have moved on, running code nobody will touch for years. They can't adapt, so the API must.

What happens when a request is sent twice? How does a client walk through a million records? And how will this contract change over the next five years without breaking anyone? Those questions, not the choice of style, decide whether an API is good. Get them right and switching the transport later is a manageable project; get them wrong and no transport will save you, because every client has already written code against the mistakes.

It also helps to know who the client is, because that shapes almost every choice. A public API used by other companies must be conservative: universal tooling, generous compatibility, careful deprecation, documentation good enough that nobody needs to ask you. A partner or mobile API has fewer clients, but ones you can't force to upgrade — apps stay installed for years. An internal service-to-service API has clients you can find and update, so it can use stricter contracts and more efficient transports, and breaking changes can be coordinated, though they still need care. The same endpoint design can be excellent for one audience and wrong for another; a senior answer to any API design question starts by asking who will call it and how hard they are to change.

One principle underlies all of them: design from the client's use cases, not from your database. An API that mirrors your tables leaks your internal structure into every client, so any schema change becomes an API change. An API designed around what clients need to do — "list a customer's unpaid invoices", "pay this invoice" — lets the implementation change behind it, exactly the information hiding from swe1.

1. Resources, identifiers and methods

Resource-oriented design, the backbone of REST and of Google's API guidelines, starts by naming the resources — the nouns — and arranging them in a hierarchy that reflects ownership: /customers/{customer_id}/invoices/{invoice_id}. Collections are plural nouns; individual resources are addressed by ID. Operations then use a small set of standard methods with the semantics HTTP already defines (net7): GET to read, POST to a collection to create, PUT to replace, PATCH to partially update, DELETE to remove. A client that knows the pattern for one resource knows it for all.

Identifiers should be opaque, stable strings, not database row numbers the client might do arithmetic on. Stripe's IDs carry a type prefix (cus_, ch_, in_), so a customer ID pasted into an invoice field fails fast with a clear message, and logs are readable. Sequential integer IDs also leak information (how many invoices you have) and invite enumeration attacks, where an attacker increments the ID to read other customers' data — so every read must check the caller owns the resource (swe13).

Some operations don't fit create-read-update-delete: send an invoice, cancel a job, refund a payment. Model them as custom methods on the resource — POST /invoices/{id}:send in Google's style, or POST /invoices/{id}/send — rather than contorting them into a PATCH of a status field, which hides the side effects (an email is sent) behind what looks like a data update. A related trick: when an action creates something with its own lifecycle, make that a resource — a refund is POST /refunds with a charge field, and the refund then has its own ID and status.

Two design details prevent whole classes of bugs. Money is an integer in minor units with a currency — {"amount": 129900, "currency": "EUR"} means €1,299.00 — because floating-point numbers can't represent most decimal fractions exactly (swe1, swe4). Timestamps are ISO 8601 in UTC with an explicit offset (2026-09-29T14:03:00Z). Names carry units wherever a number has them (timeout_ms, size_bytes).

A status code's main job is to tell the client — and every proxy, load balancer and library between them — what kind of outcome this is and therefore what to do next:

Returning 200 with {"error": ...} in the body, or 500 for a validation failure, breaks every generic client and retry library that relies on the status class. Note the 404-for-403 choice: if revealing that invoice 48213 exists would leak information to a caller who can't see it, respond as if it doesn't.

The body needs a machine-readable contract too. RFC 9457 "problem details" standardises it as application/problem+json:

{
  "type": "https://api.example.com/errors/insufficient-funds",
  "title": "Insufficient funds",

Clients branch on type or a stable code, never on the human-readable detail, which you should be free to reword. For validation errors, list every invalid field at once rather than failing on the first. Include a request ID so support can find the logs, and never include stack traces or internal hostnames.

3. Idempotency: making retries safe

Recall the doubled transfer. The client can't distinguish "the request never arrived" from "it arrived, succeeded, and the response was lost"; both look like a timeout. GET, PUT and DELETE are idempotent — repeating them has the same effect as doing them once — so retrying is safe. POST isn't. The standard fix is the idempotency key: the client generates a unique value (a random UUID) once per logical operation — per tap of the "Send" button, not per HTTP attempt — and sends it with the request and every retry.

POST /v1/transfers
Idempotency-Key: 5f0c7a8e-2b41-4d0e-9c7e-1b2f3a4d5e6f
{"from": "acc_1", "to": "acc_9", "amount": 2500, "currency": "GBP"}

Trace the server's side. First attempt: the key is new. In one database transaction the server creates the transfer and stores (key, hash(request body), response). It sends 201, which is lost. Retry with the same key: the server finds the key, checks the body hash matches, and returns the stored 201 response without creating anything. The client now has its answer and exactly one transfer exists. Three edge cases need rules. Same key, different body: almost certainly a client bug — reject it (Stripe compares parameters and errors if they differ). A retry arriving while the first attempt is still running: return 409 and let the client retry later, rather than running both. Retention: keys can't be kept forever; Stripe's documentation says keys may be pruned after they're at least 24 hours old, after which reuse creates a new request. Stripe stores the first response for a key whether it succeeded or failed — including 500 errors — but not failures that happen before execution begins, such as validation errors, which can simply be retried. The key must be stored in the same transaction as the side effect; otherwise a crash between the two leaves a transfer without a key, and the retry duplicates it.

4. Pagination: offset versus cursor

No list endpoint should return unbounded results. Offset pagination (?offset=40&limit=20) is easy to implement and allows jumping to page 7, but has two problems. It's slow for deep pages, because the database must find and discard every skipped row. And it's unstable when data changes between requests. The lab traces it. Ten orders are listed newest first, four per page. The client fetches page 1 (orders 1–4). Two new orders arrive, which go to the top. The client fetches page 2 with offset=4 — but the first four rows are now the two new orders plus orders 1 and 2, so rows 5–8 are orders 3, 4, 5 and 6. Orders 3 and 4 appear twice. Had two orders been deleted instead, two unseen orders would have been skipped silently.

Cursor pagination (also called keyset pagination) fixes both problems. The response includes an opaque next_cursor that encodes the sort key of the last item — for "newest first", its (created_at, id), with the ID as a tie-breaker — and the next query asks for rows after that key: WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 20. With an index on (created_at, id), every page is equally fast, and inserts or deletes elsewhere don't shift it. The cursor should be opaque to clients (base64-encoded, perhaps signed) so you can change its contents later. The trade-offs: no jumping to page 7, and exact total counts, which require scanning everything, should be optional or approximate.

5. Long-running operations

Some operations take longer than a client can sensibly hold a request open: fine-tuning a model, generating a large report, a bank transfer that settles in a minute. Holding the HTTP request open for minutes ties up connections, fails on every proxy timeout, and loses the result if the client disconnects. The pattern is to return 202 Accepted immediately with a resource representing the job:

POST /v1/reports   (Idempotency-Key: ...)
202 Accepted
Location: /v1/reports/rep_42
{"id": "rep_42", "status": "queued"}

GET /v1/reports/rep_42   →  {"status": "running", "progress": 0.6}
GET /v1/reports/rep_42   →  {"status": "succeeded", "result_url": "..."}

The job has explicit states (queued, running, succeeded, failed, cancelled — a state machine, swe3), and clients either poll with backoff or register a webhook: a URL the provider calls when the job changes state. Webhooks need their own care: sign them so receivers can verify the sender, retry until acknowledged, include an event ID so receivers can deduplicate, and provide an events endpoint so a receiver that was down can catch up. Streaming (below) suits results produced incrementally, but the job itself should survive a disconnected client.

6. Versioning and compatibility

Every change to an API is either backward compatible — existing clients keep working — or breaking. Compatible, for well-behaved clients: adding an endpoint, adding an optional request parameter, adding a response field, relaxing a validation. Breaking: removing or renaming a field, changing its type or format (an integer ID becoming a string), changing a default, making an optional parameter required, tightening validation, changing an error's status code, and — the sneakiest — changing what a field means while keeping its shape. Enum values sit in between: adding "disputed" to a status field is compatible only if clients were told to handle unknown values.

Clients help by being tolerant readers: ignore fields you don't recognise, handle unknown enum values with a default branch, and don't depend on field order. Providers help by documenting that they will add fields and values, and by testing compatibility automatically — diffing the OpenAPI or protobuf schema in CI with a breaking-change detector.

When a breaking change is truly needed, a versioning scheme decides how it's delivered. The common one is a major version in the URL (/v1/, /v2/) or a header. Its weakness, as Stripe's engineers put it, is that changes between major versions are so big that upgrading is almost as painful as integrating from scratch, so many clients never upgrade and the provider maintains old versions indefinitely. The case study below describes Stripe's alternative: many small, date-named versions. Whatever the scheme, deprecation needs process: announce the change, give a timeline, measure who still uses the old behaviour (per-client usage metrics), contact them, and signal it in responses (the Deprecation and Sunset HTTP headers exist for this).

One law makes all of this harder than the contract suggests. Hyrum's law, named after Google engineer Hyrum Wright: "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody." The order of results you never promised, the wording of an error message, a response that happened to arrive in 50 ms — somebody depends on it. Defences: make the contract explicit (stable error codes, not messages), avoid accidental observable behaviour (sort results deliberately or randomise what isn't promised), and roll out even "compatible" changes gradually, watching error rates by client.

7. REST, gRPC and GraphQL compared on the wire

REST over JSON is the default for public APIs. It works from any language and any browser, debugs with curl, and uses HTTP caching (Cache-Control, ETag) and every proxy and gateway built for it. Its weaknesses are a loose contract unless you add a schema (OpenAPI), verbose payloads, and fixed response shapes that over-fetch (fields the client doesn't need) or under-fetch (requiring extra round trips).

gRPC defines services and messages in Protocol Buffers and generates client and server code in many languages. Calls travel over HTTP/2 (net8), which multiplexes many calls on one connection and supports streaming in both directions. To see where its efficiency comes from, encode the invoice from the primer. As compact JSON — {"id":48213,"customer_id":"cus_9f2k","amount_cents":129900,"currency":"EUR","status":"PAID"} — it is 92 bytes. The protobuf schema numbers each field:

message Invoice {
  int64  id           = 1;
  string customer_id  = 2;
  int64  amount_cents = 3;
  string currency     = 4;
  Status status       = 5;   // enum Status { DRAFT = 0; OPEN = 1; PAID = 2; }
}

On the wire, each field is a tag — the field number shifted left three bits, OR'd with a 3-bit wire type (0 for varint integers, 2 for length-delimited strings and bytes) — followed by the value. Integers use varints: seven bits per byte, least-significant group first, with the top bit set on every byte except the last.

The encoding is about a quarter of the size, and parsing binary integers is cheaper than parsing decimal text. That matters for high-volume internal traffic; for most APIs, database time dominates and compressed JSON narrows the gap. gRPC's bigger wins are the typed contract (a .proto file is the single source of truth, and breaking changes can be detected mechanically), generated clients, streaming, and deadlines: a client says "I need an answer within 300 ms", and the deadline propagates through every downstream call, so servers stop working on requests nobody is waiting for. Its costs: browsers can't call gRPC directly (gRPC-Web and a proxy are needed), binary traffic is harder to inspect, and HTTP caching doesn't apply. Protobuf's evolution rules follow from the encoding: never reuse or renumber a field (mark removed ones reserved), new fields are optional and old readers skip unknown ones, and renaming a field is safe on the wire but not in JSON mappings or generated code.

GraphQL exposes a typed schema through a single endpoint, and the client sends a query naming exactly the fields and related objects it wants. A mobile screen that needs an invoice's amount and its customer's email gets both in one round trip and nothing else. That flexibility moves work to the server: each field has a resolver, and a naive query for 100 invoices with their customers runs 1 + 100 database queries — the N+1 problem — unless resolvers batch (the DataLoader pattern). Public GraphQL APIs need query depth and cost limits, since a client can write an arbitrarily expensive query, and HTTP caching is harder because everything is a POST to one URL. GraphQL typically evolves without versions: add fields freely, mark old ones @deprecated, and remove them once usage tracking shows no one queries them.

8. APIs for and around LLMs

Model-serving APIs follow every principle above, with a few twists worth knowing. Streaming: generating a long answer takes seconds, so responses are streamed token by token, most often as server-sent events (a long-lived HTTP response carrying a sequence of data: lines), with a final event carrying token usage and a stop reason. Pinned model versions: model behaviour changes between releases, so providers publish dated snapshots and deprecation schedules, and serious clients pin a specific version and upgrade deliberately after evaluation — the same logic as Stripe's pinned API versions. Schemas as contracts: tool (function) definitions and structured-output formats are JSON Schemas, and changing a tool's parameters is an API change for the model that calls it; version them. Rate limits in tokens as well as requests, returned with 429 and headers saying when capacity resets. And idempotency for agents: when a model-driven agent calls your API to take an action — issue a refund, send an email — it may retry after a timeout just like a flaky mobile client, so actions with side effects need idempotency keys, and dangerous ones a confirmation step.

Designing from use cases: the API review

The cheapest time to fix an API is before its first client. Mature organisations run a lightweight API design review: a short document with the resources, methods, request and response examples, error cases and pagination, reviewed by people who've designed many APIs, against written guidelines (Google's AIPs, Microsoft's REST guidelines or an internal equivalent). Stripe describes exactly this: outgoing changes are written up in a brief document and sent to an internal mailing list, so errors and inconsistencies are caught before they ship. The review's questions are mostly about consistency and future change. Does this look like our other APIs? Are the nouns right — would a second use case fit without a new endpoint? Which fields might need to become lists later (a single email that should have been emails is a breaking change to fix)? Which booleans should be enums (is_paid can't grow a "partially refunded" state; status can)? What happens at 10× the data?

Consistency beats local elegance

An API surface with 200 endpoints designed by 30 people is only usable if it's consistent: the same pagination parameters everywhere, the same error shape, the same naming conventions (snake_case or camelCase, never both), the same way of expanding related objects, the same timestamp format. Each inconsistency is a small tax on every client developer, forever. That's why large API programmes enforce style mechanically — OpenAPI linters such as Spectral, Google's api-linter for protobuf — and why a slightly awkward convention applied everywhere beats a locally nicer one used in one place.

Authorisation is part of the API design

The most common serious API vulnerability, top of the OWASP API Security list, is broken object-level authorisation: an endpoint that checks the caller is logged in but not that the object they asked for is theirs — the GET /invoices/{id} from swe6. Resource-oriented APIs make it easy to miss because every endpoint takes IDs. Defences are structural: scope every query by the caller's tenant (WHERE customer_id = :caller) in a shared data-access layer rather than in each handler; use unguessable IDs as defence in depth (never as the only defence); return 404 rather than 403 for objects the caller can't see; and add tests that call every endpoint with another tenant's IDs. Related design points: rate limits per client and per operation, and field-level controls so a response model never serialises internal fields by accident (swe13 covers these).

Retries, deadlines and backpressure across API boundaries

API design decides how failures propagate. A 503 with Retry-After: 30 lets well-behaved clients back off together; a 500 without guidance invites immediate retries that amplify an overload. gRPC deadlines make timeouts part of every call's contract: a caller's remaining budget shrinks as the call passes through services, and a service receiving a request with 5 ms left should fail fast instead of starting a 200 ms query. Clients should use exponential backoff with jitter, cap retries, and respect Retry-After; servers should shed load early with 429 or 503 rather than queueing work that will time out anyway (sc12 covers these resilience patterns). For LLM providers, where capacity is expensive and bursty, these signals — 429s with reset times, per-model quotas — are a large part of the practical API.

Schema evolution in practice: protobuf, JSON and events

The same compatibility logic applies to every schema that crosses a boundary: API payloads, messages on queues, and events. Two directions matter. Backward compatibility means new code can read old data (a new consumer reading last month's events). Forward compatibility means old code can read new data (an un-upgraded consumer reading events from a newer producer), which is why tolerant readers matter. Protobuf gives both if you follow its rules: new fields get new numbers, removed fields are reserved, and readers ignore unknown fields. JSON gives both only by convention. Schema registries for event streams (for example with Avro or protobuf on Kafka) enforce a chosen compatibility mode on every new schema version, rejecting breaking changes at publish time — the event-stream equivalent of a breaking-change check in CI.

REST's original constraints, and why hypermedia rarely caught on

Fielding's REST includes a constraint most "REST APIs" skip: hypermedia as the engine of application state (HATEOAS) — responses contain links to the actions available next, so clients discover the API by following links rather than hard-coding URLs, as a browser does with a website. In principle this lets servers change URLs and workflows without breaking clients. In practice, API clients are programs written against documentation, not users exploring, so few APIs go beyond including a next link for pagination and Location headers for created resources. It's worth knowing the term for interviews, and knowing that the parts of REST that deliver most value in practice are stateless requests, correct method semantics, cacheability and stable resource identifiers.

How API problems show up in production

API failures are rarely dramatic outages; they're slow leaks of trust and cost. Duplicate side effects from retries without idempotency: double charges, duplicate orders, emails sent twice — visible as support tickets and refund volume. Accidental breaking changes: a serialiser upgrade that changes date formats, a new validation rule, a field that becomes nullable — visible as a spike in 4xx errors from particular clients right after a deploy, if you break errors down by client ID and API version. Pagination anomalies in exports and syncs. Retry storms after an outage, when every client retries at once with no backoff. Deep-offset queries that slow the database as datasets grow. The observability that catches them: request metrics by endpoint, status class, client and API version; logs with request and idempotency IDs; alerts on 4xx rate changes per client after deploys; and a breaking-change check in CI on every schema diff.

Case: Stripe's API versioning

Stripe provides payment infrastructure that many businesses call directly from their own code, which makes it an unusually strict test of API evolution: a breaking change can stop other companies taking money. In a 2017 post, engineer Brandur Leach described how Stripe handles it. The starting point is a firm commitment: "we've maintained compatibility with every version of our API since the company's inception in 2011." The post gives a concrete example of the kind of change that would break clients: in 2014 Stripe replaced a bank account's boolean verified field with a status field that might contain the value "verified". Code that checked bank_account[:verified] would break, so the change was delivered as a new version rather than imposed on everyone.

The scheme has three parts. First, date-named rolling versions (for example 2017-05-24) instead of big v1/v2 releases: each contains a small set of breaking changes, so upgrading one version at a time is easy. Second, pinning: the first time an account makes an API request, it's pinned to the latest version, and every later request gets that version implicitly, so no one receives a breaking change by accident; any single request can override it with a Stripe-Version header, and accounts upgrade deliberately. Third, version-change modules: every response is described by an "API resource" class written for the current version; each breaking change is encapsulated in a module with a description, a transformation and the resource types it affects, and the modules are listed by version. To answer a request, the API renders the response at the current version and walks backwards through the list, applying each transformation until it reaches the target version — taken from the Stripe-Version header if present, then an OAuth application's version, then the account's pinned version. Old versions therefore live at the edge, not in business logic.

The post is candid about costs. Changes with side effects beyond reshaping a response (such as a different transfers behaviour) can't be encapsulated and leave checks scattered through the code, so Stripe avoids them. Every version adds code to maintain. So Stripe tries hard not to need versioning at all, through the design review described in the deep section, and the modules double as data: the public changelog and per-user documentation annotations are generated from them. The result, by the time of the post: almost a hundred backwards-incompatible upgrades over six years without breaking a single pinned integration. The same idea — pin to a dated version, upgrade deliberately, transform at the edge — is now how LLM providers publish models, and how teams should consume them.

AI systems: the API is also a model

For AI engineers, API design shows up in two directions. Serving: a model endpoint needs versioned model identifiers, streaming, clear errors for context-length overflow (a 400 with a machine-readable code, not a 500), token-based quotas, and idempotency for any endpoint that triggers side effects. Consuming: pin model versions and treat a version bump like a dependency upgrade that goes through evaluation (swe5); wrap provider SDKs in an adapter (swe2) that translates rate-limit and overload errors into your own retryable types; respect Retry-After; and when you expose tools to an agent, design them as carefully as a public API — narrow operations, explicit schemas, idempotency keys and confirmation for anything irreversible — because the model is a client that will send unexpected inputs and retry without being asked.

"""swe7 lab: (1) one API response as JSON vs protobuf wire format, encoded by hand;
(2) offset vs cursor pagination while rows are being inserted; (3) idempotency keys under retries."""
import json
import uuid

# ---------- 1. JSON vs protobuf wire format ----------
# message Invoice { int64 id = 1; string customer_id = 2; int64 amount_cents = 3; string currency = 4; Status status = 5; }
invoice = {"id": 48213, "customer_id": "cus_9f2k", "amount_cents": 129900, "currency": "EUR", "status": "PAID"}
STATUS = {"DRAFT": 0, "OPEN": 1, "PAID": 2}

def varint(n: int) -> bytes:                      # 7 bits per byte, low bits first, high bit = "more bytes follow"
    out = bytearray()
    while True:
        b = n & 0x7F
        n >>= 7
        if n:
            out.append(b | 0x80)
        else:
            out.append(b)
            return bytes(out)

def field(num: int, value) -> bytes:
    if isinstance(value, int):                     # wire type 0 = varint
        return varint(num << 3 | 0) + varint(value)
    data = value.encode()                          # wire type 2 = length-delimited
    return varint(num << 3 | 2) + varint(len(data)) + data

pb = (field(1, invoice["id"]) + field(2, invoice["customer_id"]) + field(3, invoice["amount_cents"])
      + field(4, invoice["currency"]) + field(5, STATUS[invoice["status"]]))
js = json.dumps(invoice, separators=(",", ":")).encode()
print(f"JSON     {len(js):3} bytes  {js.decode()}")

# ---------- 2. offset vs cursor pagination while new rows arrive ----------
rows = [{"id": i, "created": 1000 - i} for i in range(1, 11)]        # newest first: id 1 is newest
def page_offset(data, offset, limit):
    return data[offset:offset + limit]
def page_cursor(data, after_id, limit):                               # "items older than the last one I saw"
    start = 0 if after_id is None else next(i for i, r in enumerate(data) if r["id"] == after_id) + 1
    page = data[start:start + limit]
    return page, (page[-1]["id"] if page else None)

seen_offset, seen_cursor = [], []
table = list(rows)
p1 = page_offset(table, 0, 4); seen_offset += [r["id"] for r in p1]
c1, cur = page_cursor(table, None, 4); seen_cursor += [r["id"] for r in c1]
table.insert(0, {"id": 99, "created": 2000}); table.insert(0, {"id": 98, "created": 2001})   # two new orders arrive
p2 = page_offset(table, 4, 4); seen_offset += [r["id"] for r in p2]
c2, cur = page_cursor(table, cur, 4); seen_cursor += [r["id"] for r in c2]
print(f"\noffset pages: {seen_offset}   duplicates: {sorted({i for i in seen_offset if seen_offset.count(i) > 1})}")
print(f"cursor pages: {seen_cursor}   duplicates: none")
assert seen_offset == [1, 2, 3, 4, 3, 4, 5, 6] and seen_cursor == [1, 2, 3, 4, 5, 6, 7, 8]

# ---------- 3. idempotency keys: a retry after a lost response must not charge twice ----------
class PaymentAPI:
    def __init__(self):
        self.charges, self.seen = [], {}
    def create_charge(self, amount_cents: int, idempotency_key: str | None = None) -> dict:
        if idempotency_key in self.seen:
            return self.seen[idempotency_key]          # replay the stored response, do nothing new
        charge = {"id": f"ch_{len(self.charges) + 1}", "amount": amount_cents}
        self.charges.append(charge)
        if idempotency_key:
            self.seen[idempotency_key] = charge
        return charge

def client_with_retry(api, amount, use_key: bool):
    key = str(uuid.uuid4()) if use_key else None        # ONE key per logical operation, reused on every retry
    for attempt in range(3):
        resp = api.create_charge(amount, key)
        if attempt < 2:
            continue                                   # simulate: response lost to a timeout, client retries
        return resp

for use_key in (False, True):
    api = PaymentAPI()
    client_with_retry(api, 4999, use_key)
    print(f"\nidempotency key={'yes' if use_key else 'no '}: charges created = {len(api.charges)}")
    assert len(api.charges) == (1 if use_key else 3)
Design it

Design the API for creating a money transfer from a mobile app on flaky networks. Requirements: the user must never be charged twice; the app needs the transfer's final status, which can take up to a minute; users list their transfers newest first.

Answer 
POST /v1/transfers
Idempotency-Key: 7c1f…        (client-generated UUID per user action)
{ "from_account": "acc_1", "to_account": "acc_9", "amount": 2500, "currency": "GBP" }

202 Accepted
Location: /v1/transfers/tr_123
{ "id": "tr_123", "status": "pending", ... }

GET /v1/transfers/tr_123          -> 200 { "status": "completed" | "failed", "failure_reason": ... }
GET /v1/transfers?limit=20&after=<cursor>   -> newest first, keyset-paginated
  • Idempotency key generated once per tap, reused on every retry. The server stores key + request hash + response in the same transaction as creating the transfer; the same key and body return the original response; the same key with a different body returns 422; a retry while the first is still processing gets 409.
  • 202 + polling (or a webhook or push notification) because completion is asynchronous; never hold a request open for a minute. The transfer is a state machine: pending → completed | failed.
  • Amounts as integer minor units with a currency code, never floats; prefixed opaque IDs.
  • Errors as problem details with stable codes: 400 malformed, 401/403 auth, 404 unknown account (also for accounts the caller can't see), 409 conflict, 422 business rule (insufficient funds), 429 with Retry-After.
  • Cursor pagination on (created_at, id) because new transfers arrive constantly — offset paging would duplicate or skip rows.
  • Authorisation on every read: a transfer is visible only to its account's owner.
