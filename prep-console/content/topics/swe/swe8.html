It's Friday afternoon. An engineer finishes a feature on a branch that has lived for three weeks, and the merge into main produces 47 conflicts across files they've never touched. Resolving them takes the evening, and one resolution quietly drops a teammate's bug fix. Elsewhere, someone tidies their branch with a rebase and force-pushes it — not realising two colleagues had already built on it — and their next pull turns into a mess of duplicated commits. A third engineer runs git reset --hard to "start again" and believes a day of work is gone. And somewhere, a test that passed a month ago now fails, with 400 commits in between and nobody sure which one broke it.

All four problems have standard solutions, but only if you understand what Git actually does. Most people learn Git as a set of incantations — add, commit, push, and a search engine for everything else — and the incantations work until something unusual happens. Underneath, Git has a small, elegant model: every version of your project is a snapshot, every snapshot points to the one before it, everything is named by a hash of its content, and branches are just movable labels. Once that model is clear, merge, rebase, reset, revert and reflog stop being magic words and become obvious operations on a graph — and the recoveries become obvious too.

This lesson builds that model from the ground up, then uses it: merge versus rebase drawn commit by commit; branching workflows and why high-performing teams converged on trunk-based development; git bisect as binary search over history; recovering from every common mistake; and what makes history trustworthy. The real-world case is the 2021 incident in which two backdoored commits were pushed to the PHP language's source repository in the names of its core developers — a lesson in what a commit's author field does and doesn't prove. The last part covers version control for ML systems, where data, model weights and prompts need versioning alongside code. The lab drives real Git from Python: it builds merge and rebase histories, bisects 32 commits in 5 test runs, and rescues "lost" work from the reflog.

The analogy: a photo album with sticky notes

Imagine keeping a project as an album of photographs. Each time you reach a point worth saving, you photograph the whole project — every file, exactly as it is — and write on the back which photo came before it. Photos are never altered once taken. To remember where you are, you put sticky notes on photos: "main" on the latest approved photo, "my-feature" on the photo you're working from. Taking a new photo while "my-feature" is your current note means: photograph, write "previous: the photo my note was on", and move the note to the new photo. Two people can start from the same photo and each take their own sequence; the album then has a fork, like a family tree.

That is almost exactly Git. The photos are commits (full snapshots, never edited), the "previous" writing is the parent pointer, and the sticky notes are branches. Where the analogy breaks: Git doesn't store thousands of full copies of unchanged files. Each file's content is stored once and named by a hash of its bytes, so a snapshot that changes one file shares everything else with its parent — which is why snapshots are cheap.

The model in one picture

Three more words complete the model. HEAD is Git's pointer to what you have checked out — normally a branch label. A remote is another copy of the repository, usually named origin, on a server; remote-tracking branches like origin/main are read-only labels recording where the remote's branches pointed the last time you fetched. And content addressing: every object is named by a hash of its content, so identical content always has the same name, and any change — even to a commit's parent — produces a different name.

With that, the common commands become simple to state. commit adds a circle and moves the current label to it. branch x adds a label; switch x moves HEAD to it. fetch downloads new circles and updates the origin/ labels; pull is fetch followed by a merge or rebase. merge and rebase are two ways of combining forked lines, and reset moves a label. One consequence of the model is worth stating before anything else, because it removes most Git anxiety: almost nothing you do in Git destroys committed work. Commits are immutable and stay in the object database even when no label points at them; operations that look destructive — reset, rebase, amend, deleting a branch — create new commits or move labels, and Git records every label movement in a local log. The one thing Git can't give back is an edit you never committed. So commit early and often on your own branch, and tidy up before sharing; the rest of the lesson shows how.

Keep this picture in mind for the rest of the lesson; nearly every Git question in an interview, and nearly every Git emergency at work, is answered by drawing it.

1. Objects and hashes: why history is tamper-evident

Git's database contains three main kinds of object. A blob holds the bytes of one file. A tree represents a directory: a list of entries, each a name, a mode and the ID of a blob or another tree. A commit records the ID of the top-level tree (the snapshot), the IDs of its parent commit(s), the author and committer with timestamps, and the message. Every object's ID is a cryptographic hash of its content (SHA-1 by default, with SHA-256 repositories supported in newer versions), written as 40 hexadecimal characters and usually abbreviated to 7.

That design has three consequences worth remembering. Deduplication: an unchanged file in the next commit has the same content and so the same blob ID; the new tree simply points at the existing blob. Integrity: a commit's ID covers its tree and its parents' IDs, which cover their trees and parents, all the way back. Change one byte anywhere in history and every later commit ID changes, so history can't be silently altered — it can only be replaced with different history. New identity on any change: rewording a message, changing an author, or giving a commit a different parent produces a new commit with a new ID, even if the file changes are identical. That last point is the key to understanding rebase.

2. Three places your changes live

At any moment, a file can differ between three places. The working tree is the files on disk you edit. The index (or staging area) is the snapshot being assembled for the next commit. The repository holds committed history. git add copies changes from the working tree into the index; git commit turns the index into a commit; git restore file discards working-tree changes; git restore --staged file unstages. git status shows differences between all three, git diff shows working tree versus index, and git diff --staged shows index versus last commit. The index exists so you can build a commit deliberately — staging two related changes from a file with ten edits (git add -p) — which is how atomic commits get made.

3. Merge: joining two lines

Take the primer's picture: main at C, feature at F2, forked at B. To integrate feature into main there are two cases.

If main hadn't moved since the fork — if main were still at B — Git would do a fast-forward: move the main label forward to F2. No new commit, linear history.

Main has moved (C exists), so Git does a three-way merge. It finds the merge base — the most recent commit both branches share, here B — and compares each side's version of every file against it. Where only one side changed something, Git takes that change; where both sides made the same change, it takes it once; where both changed the same region differently, it has a conflict and writes both versions into the file between markers (<<<<<<<, =======, >>>>>>>) for a person to resolve. The result is recorded as a merge commit M with two parents, C and F2. Nothing existing is changed: the feature's commits keep their IDs, and the graph records exactly how development happened, including that it was parallel. The cost is a history with forks and joins that can be hard to read when there are many of them.

4. Rebase: replaying commits on a new base

Rebase takes a different approach: instead of joining the lines, it moves your work so that it starts from the latest main, as if you'd begun your feature today. git rebase main while on feature does this, step by step:

  1. Find the commits on feature that aren't on main: F1 and F2.
  2. Temporarily set them aside, and move to C, the tip of main.
  3. Replay F1's changes on top of C, creating a new commit F1′ whose parent is C.
  4. Replay F2's changes on top of F1′, creating F2′.
  5. Move the feature label to F2′.

F1′ and F2′ have the same file changes as F1 and F2 but different parents, so they have different IDs — the lab prints both, for example "F1 was abe56ef before the rebase, 59593b7 after". Now main can be fast-forwarded to F2′, giving a straight line A–B–C–F1′–F2′. The old F1 and F2 still exist until garbage collection, reachable through the reflog.

Rebase gives linear history that's easy to read and bisect, and lets you resolve conflicts one commit at a time. Its danger follows directly from the new IDs. If a colleague had already pulled F1 and F2 and built on them, and you force-push F1′ and F2′, their history and yours now contain different commits for the same work. Their next pull merges the two versions, producing duplicates and conflicts. Hence the golden rule of rebasing: rebase only commits that exist only on your machine or that nobody else has built on. Tidy private work freely; never rewrite shared history. (When you must overwrite your own remote branch — say, a pull-request branch after addressing review — use git push --force-with-lease, which refuses if the remote has commits you haven't seen.)

Interactive rebase (git rebase -i main) extends the idea: before replaying, it lets you reorder commits, squash fixups into the commits they fix, reword messages, or drop commits — turning "WIP", "fix typo", "actually fix it" into two clean, reviewable commits. Hosting platforms also offer squash merge, which collapses a whole pull request into one commit on main; it keeps main linear and each change revertible as a unit, at the cost of losing the individual commits (fine for small PRs, less so for large ones whose steps are worth keeping). Cherry-pick replays a single commit onto another branch — the usual way to backport a fix to a release branch.

5. Branching workflows

A workflow is a team's agreement about which branches exist, how long they live and how work reaches production. Three are common.

GitFlow, popularised in 2010, uses two long-lived branches — main for released code and develop for integration — plus feature branches off develop, release branches for stabilising a version, and hotfix branches off main. It fits software shipped in discrete, versioned releases with several versions supported at once: installed desktop software, mobile apps, libraries, firmware. For a web service deployed many times a day, its long-lived branches add ceremony and delay integration; even its author later added a note recommending simpler workflows for continuously delivered software.

GitHub flow is the simple version: main is always deployable; create a branch, open a pull request, review, merge, deploy. Trunk-based development tightens it: branches live hours to a day or two, everyone integrates into main (the trunk) at least daily, and main stays releasable because every change passes CI before merging. Work that takes weeks is split into small changes (swe6's stacks), and incomplete features merge while switched off behind feature flags — runtime switches that decide whether a code path runs, independently of deployment (swe9). Research on software delivery performance, such as the annual reports of the DORA programme (DevOps Research and Assessment), has repeatedly associated trunk-based development with higher delivery performance, and it's the workflow continuous delivery assumes.

The underlying trade-off is integration frequency. Every divergence between branches is a merge you'll pay for later, and the cost grows faster than the divergence: two branches that each changed 20 files for three weeks conflict far more than two that changed 2 files for a day. Integrating often keeps each merge small, keeps everyone working on nearly the same code, and surfaces conflicts while the context is fresh. Long-lived branches don't avoid integration problems; they postpone and concentrate them.

6. Bisect: binary search over history

A test passes on a commit from last month and fails today, with 400 commits between. Reading them all is hopeless; git bisect makes it mechanical. You tell Git one bad commit and one good one. It checks out the commit halfway between; you test it and say git bisect good or git bisect bad; it halves the remaining range; repeat. Each step halves the candidates, so finding the first bad commit among n takes about log2(n) steps: 5 for 32 commits, 9 for 400, 10 for 1,000, 20 for a million.

The best part is git bisect run <script>: give it a command that exits 0 for good and non-zero for bad, and Git runs the whole search unattended. The lab does exactly this over 32 synthetic commits and finds commit 23 in 5 runs. Bisect has preconditions, and they're the practical argument for the habits in this lesson: every commit should build and pass (so a midpoint isn't broken for unrelated reasons — git bisect skip exists but costs steps), commits should be small and atomic (so the answer points at a few lines, not a 2,000-line merge), and the test must be deterministic (a flaky test, swe5, sends bisect down the wrong half). The lab hit a nice real-world gotcha: checkouts within the same second can leave a source file with the same modification time and size, and Python then reuses a stale compiled .pyc, testing the wrong code — so the bisect script runs Python with -B.

7. Undoing things safely

Most Git fear comes from not knowing which undo to use. Match the tool to whether the history is shared:

SituationToolRewrites history?
Discard uncommitted edits to a filegit restore fileno (edits are lost)
Fix the last commit, not yet pushedgit commit --amendyes (local only)
Throw away local commitsgit reset --hard <sha>moves the label
Undo a commit already on a shared branchgit revert <sha>no — adds an inverse commit
Recover "lost" commitsgit reflog + git branchno
Overwrite your own remote branchgit push --force-with-leaseyes (remote)

reset moves the current branch label to another commit; with --hard it also makes the working tree match, discarding uncommitted edits (the only thing Git can't give back). The commits it moved away from aren't deleted — they're unreferenced. The reflog is Git's safety net: a local log of every commit HEAD and each branch have pointed to. The lab resets away a commit called "important work", then shows the reflog:

e420656 HEAD@{0}: reset: moving to HEAD~1
a4b2225 HEAD@{1}: commit: important work
e420656 HEAD@{2}: commit (initial): keep 1

git branch rescued a4b2225 brings it back. Unreferenced commits are kept until garbage collection prunes reflog entries, which by default takes weeks. On shared branches, the safe undo is always revert: it records a new commit that applies the inverse change, so everyone who pulled just gets one more commit, and history shows both the mistake and its correction.

8. Commits and history people can use

History is only useful if it can be read, reverted and bisected. That depends on commit hygiene. A good commit is atomic: one logical change that builds and passes tests on its own. Its message has a short imperative summary line ("Fix rounding in VAT calculation") and a body that explains why — the bug, the reasoning, the alternative rejected — because the diff already shows what. Refactors and formatting go in separate commits from behaviour changes, so a reviewer (swe6) and a future bisect can tell them apart. Generated files, build artefacts and secrets stay out, enforced by .gitignore and pre-commit hooks. Tags mark releases (git tag -a v2.3.0), giving a stable name to the exact commit that shipped.

9. Version control for ML systems

Git is designed for text source files. It stores every version of every file in full (compressed), so committing a 2 GB dataset or a 14 GB model checkpoint bloats every clone forever, and binary files can't be diffed or merged meaningfully. ML projects therefore split what they version. Code, configuration, prompts and small evaluation sets go in Git, where review and history work. Large data and model weights go in object storage, referenced from Git by content hash — via Git LFS (which replaces large files with small pointer files) or a data-versioning tool such as DVC (which tracks datasets and pipeline outputs by hash in small metadata files). A Git commit then pins exact data and model versions without containing them. On top of that, an experiment tracker or model registry records, for every training run and deployed model, the commit, data hashes, hyperparameters and evaluation results. The payoff is traceability: for any model in production you can answer "which code, which data, which prompt?" — the question every model incident starts with. Notebooks deserve care too: their JSON includes outputs and execution counts, so strip outputs before committing (tools like nbstripout) or diffs become unreadable.

Why Git's model won: distributed, content-addressed, cheap branches

Earlier centralised systems such as Subversion recorded changes per file on a central server; branching copied directories on that server, merging was painful, and every operation needed the network. Git, written by Linus Torvalds in 2005 for Linux kernel development, made three different choices. Every clone is a full repository with all history, so commits, branches, logs and bisects are local and fast, and there's no single point of failure. Content addressing makes objects immutable and deduplicated, and makes integrity checks free. And branches as movable labels make branching and merging cheap enough to do constantly. Those properties enabled the pull-request workflow that platforms like GitHub built on, and the review culture of swe6.

Hash functions, SHA-1 and trust

Git's integrity guarantee rests on its hash function. Git originally used SHA-1, and in 2017 researchers demonstrated a practical SHA-1 collision (two different PDFs with the same hash). Git responded by switching to a hardened SHA-1 implementation that detects the known collision-attack pattern, and added support for SHA-256 repositories, though adoption has been slow because hosting platforms and tools must support both. The practical point for most teams: the hash protects against accidental corruption and makes tampering evident, but it doesn't say who made a commit. That's what signatures are for.

Signing, identity and protecting the path to main

A commit's author and committer fields are whatever the committer's configuration says. Anyone with push access can create a commit "by" anyone. A signed commit carries a cryptographic signature (GPG, SSH or S/MIME) over the commit object, which a host can verify against the public key registered for that person, marking it "Verified". Signatures only help if something enforces them: branch protection rules that require signed commits, and reviewers who notice an unverified commit from someone who always signs. In practice, most organisations get more protection from controlling the path to main than from signatures alone: strong authentication for pushes (SSH keys or tokens with two-factor authentication, not passwords), protected branches that can't be pushed to directly or force-pushed, required pull-request review, required CI status checks that commit messages can't skip, and audit logs. The case study shows each of these mattering.

Merge queues and "semantic" conflicts

Git's merge detects textual conflicts — overlapping edits. It can't detect semantic conflicts: PR 1 renames a function and updates all its callers; PR 2, written in parallel, adds a new call to the old name. Each passes CI against the main it branched from; merged together, main no longer builds. With dozens of merges a day, this happens regularly. A merge queue (GitHub's merge queue, GitLab's merge trains, Bors, Google's presubmit-on-latest) fixes it by testing each PR on top of the current main plus every PR ahead of it in the queue, merging only if that combination passes. It's the mechanism that keeps a busy trunk green, and it's why trunk-based development scales to hundreds of engineers.

Monorepos and polyrepos

Organisations choose between one repository for everything (a monorepo, used by Google, Meta and many others) and one per service or library (polyrepo). A monorepo makes atomic cross-cutting changes possible (change an API and every caller in one commit), gives one version of every dependency, and makes code search and refactoring global; it needs tooling to scale — sparse checkouts, build systems that test only what a change affects, ownership files (swe6). Polyrepos give teams independence and simpler tooling, at the cost of versioned dependencies between repositories and "diamond dependency" conflicts when two libraries need different versions of a third. Neither is universally better; the deciding factors are how often changes cross boundaries and how much you can invest in build tooling.

Recovering from the truly bad cases

Some mistakes need more than a revert. A secret committed and pushed: revoke and rotate it first (bots scan public pushes within minutes), check logs for misuse, then remove it from history with git filter-repo and force-push, coordinating with everyone to re-clone — and accept the old history may survive in forks and caches. A huge file committed: remove it from history the same way, or the repository stays bloated forever. A bad force-push to a shared branch: someone's reflog or clone still has the old tip; push it back. A merge resolved wrongly: revert the merge commit with git revert -m 1 (keeping the first parent's side), but note that re-merging the same branch later won't bring the reverted changes back unless you revert the revert. Knowing that these recoveries exist, and that nearly everything committed is recoverable, removes most Git fear.

How version-control problems show up in real teams

The recurring patterns are workflow problems more than tool problems. Integration hell: long-lived branches, huge merges, and bugs introduced while resolving conflicts — visible as large merge commits and spikes in defects after merges. A red trunk: main frequently broken, so nobody can tell whether their change broke it — usually semantic conflicts without a merge queue, or flaky tests. History nobody can use: giant commits named "wip", so bisect and blame point at 2,000-line changes. Force-push accidents on shared branches. Secrets in history, found by scanners months later. And weak control of the path to production: direct pushes to main, reviews that can be skipped, CI that a commit message can switch off. Measures that expose them: branch age at merge, lines changed per merge, the fraction of time main is red, and alerts on direct or forced pushes to protected branches.

Case: the 2021 php-src malicious commits

PHP is the language behind a large share of the web's server-side code, so its source repository is a high-value target. On 28 March 2021, two commits appeared in the php-src repository, one in the name of Rasmus Lerdorf, PHP's creator, and one in the name of Nikita Popov, a core developer. The first was titled "[skip-ci] Fix typo", with the message "Fixes minor typo." and a Signed-off-by: Rasmus Lerdorf line. It didn't fix a typo. It added eleven lines to ext/zlib/zlib.c that looked for an HTTP request header named User-Agentt (with two t's) and, if its value contained the string zerodium, passed the rest of the header to zend_eval_string — executing arbitrary PHP code sent by whoever knew the trigger. Because the code ran before the function even checked whether compression was switched on, a server running a PHP build containing it could have been taken over with a single crafted HTTP request. The commits were noticed and reverted before reaching a release.

Popov's announcement that day, and his follow-up on 6 April, are a compact lesson in what Git history does and doesn't prove. Every piece of the commit's apparent legitimacy was forgeable text: the author name, the Signed-off-by line (a convention, not a cryptographic signature), a harmless-sounding message, and a [skip-ci] tag asking the continuous-integration system not to build it. Popov's first reaction was to revoke Rasmus's account — which, he wrote in hindsight, "didn't really make sense", because "any account with access to the php-src repository could have performed the push under a false name". Investigation found that the pushes bypassed the project's SSH-based access control entirely: the self-hosted server also accepted pushes over HTTPS with password authentication against the project's user database, whose passwords were stored in a format "essentially a plain md5 hash". The follow-up concluded the server itself probably wasn't compromised, but the user database may have leaked.

The responses map onto this lesson's controls. PHP retired its self-hosted Git server and made its GitHub repositories canonical, with write access requiring membership of the PHP organisation and two-factor authentication. Passwords were reset and re-stored with bcrypt, the old password-based push path went away, and the authentication system was moved to parameterised SQL queries. The general lessons: authenticate pushes with keys and 2FA rather than passwords; treat commit metadata as unverified unless signatures are required and checked; never let a commit message disable required checks on the protected branch; require review for every change to main; and keep an eye on history — the malicious change was caught because people read what landed.

Version control in ML and LLM teams

AI teams add version-control failure modes of their own. A model in production that nobody can trace to its training commit and data snapshot, so an incident can't be reproduced. Prompts edited in a dashboard outside Git, with no history, review or rollback. Evaluation sets changed in the same commit as the prompt they grade. Notebooks with embedded outputs, including sometimes customer data or API keys, committed to shared repositories. And multi-gigabyte checkpoints committed directly, bloating every clone. The practices that prevent them are the ones in section 9: prompts and configs in Git and reviewed; data and weights in versioned storage referenced by hash; a registry linking every deployed model to its commit, data and evaluation; outputs stripped from notebooks; and secret scanning on every push.

Tools and knobs

Branch protection on main (no direct pushes, no force-pushes, required reviews and status checks, optionally required signed commits); a merge queue for busy repositories; pull.rebase=true or pull.ff=only to avoid accidental merge commits when pulling; push --force-with-lease instead of --force; rerere to remember conflict resolutions; git bisect run with a deterministic test; pre-commit hooks and server-side secret scanning; Git LFS or DVC for large files; and nbstripout for notebooks.

Goal: watch Git's model in action by driving real Git from a Python script: build the same history by merging and by rebasing, bisect 32 commits to find a bug, and rescue work "lost" to reset --hard. Needs Python 3.12 and git on your PATH; everything happens in a temporary directory that's deleted afterwards. Takes a few seconds.

  1. Save the script as swe8_lab.py and run python swe8_lab.py.
  2. Merge vs rebase. The merge history shows the fork and join (* M: merge feature with |\ and |/); the rebase history is a straight line. The script prints F1's ID before and after the rebase — they differ, because rebase creates new commits.
  3. Bisect. It makes 32 commits of a tiny add() function, breaks it at commit 23, writes a check script, and runs git bisect run. Expect bisect over 32 commits: 5 test runs and the first bad commit matching commit 23.
  4. Reflog. It commits "important work", resets it away with --hard, prints the reflog showing the lost commit at HEAD@{1}, and recreates it as a branch named rescued.

What to notice: the bisect check runs Python with -B. Without it, checkouts made within the same second can leave calc.py with an identical modification time and size, Python reuses the stale .pyc from a previous checkout, and bisect confidently blames the wrong commit — a real example of how a non-deterministic test misleads bisect.

"""swe8 lab: drive real git in a throwaway directory — merge vs rebase history, bisect, and reflog recovery.
Needs git on PATH. Everything happens in a temp dir that is deleted at the end."""
import os
import subprocess
import sys
import tempfile

def git(*args, cwd, check=True) -> str:
    env = {**os.environ, "GIT_AUTHOR_NAME": "Lab", "GIT_AUTHOR_EMAIL": "lab@example.com",
           "GIT_COMMITTER_NAME": "Lab", "GIT_COMMITTER_EMAIL": "lab@example.com"}
    r = subprocess.run(["git", *args], cwd=cwd, env=env, capture_output=True, text=True)
    if check and r.returncode != 0:
        sys.exit(f"git {' '.join(args)} failed:\n{r.stderr}")
    return r.stdout.strip()

def commit(repo, fname, text, msg):
    with open(os.path.join(repo, fname), "w") as f:
        f.write(text)
    git("add", fname, cwd=repo)
    git("commit", "-q", "-m", msg, cwd=repo)
    return git("rev-parse", "--short", "HEAD", cwd=repo)

def fresh_repo(root, name):
    repo = os.path.join(root, name)
    os.makedirs(repo)
    git("init", "-q", "-b", "main", cwd=repo)
    git("config", "commit.gpgsign", "false", cwd=repo)
    return repo

with tempfile.TemporaryDirectory() as root:
    # ---------- 1. the same work, merged vs rebased ----------
    for strategy in ("merge", "rebase"):
        repo = fresh_repo(root, strategy)
        commit(repo, "app.py", "v1\n", "A: initial")
        commit(repo, "app.py", "v2\n", "B: add endpoint")
        git("switch", "-q", "-c", "feature", cwd=repo)
        f1 = commit(repo, "feature.py", "f1\n", "F1: start feature")
        commit(repo, "feature.py", "f2\n", "F2: finish feature")
        git("switch", "-q", "main", cwd=repo)
        commit(repo, "README", "docs\n", "C: docs on main")
        if strategy == "merge":
            git("merge", "-q", "--no-ff", "feature", "-m", "M: merge feature", cwd=repo)
        else:
            git("switch", "-q", "feature", cwd=repo)
            git("rebase", "-q", "main", cwd=repo)
            new_f1 = git("rev-parse", "--short", "HEAD~1", cwd=repo)
            git("switch", "-q", "main", cwd=repo)
            git("merge", "-q", "--ff-only", "feature", cwd=repo)
        print(f"== {strategy} ==")
        print(git("log", "--graph", "--oneline", "--format=%h %s", cwd=repo))
        if strategy == "rebase":
            print(f"F1 was {f1} before the rebase, {new_f1} after: rebase makes NEW commits")
        print()

    # ---------- 2. bisect: find the commit that broke the build among 32 ----------
    repo = fresh_repo(root, "bisect")
    shas = []
    for i in range(1, 33):
        broken = i >= 23                                     # commit 23 introduced the bug
        shas.append(commit(repo, "calc.py", f"# version {i}\ndef add(a, b):\n    return a {'-' if broken else '+'} b\n", f"commit {i}"))
    with open(os.path.join(repo, "check.py"), "w") as f:     # the test bisect runs at each step (untracked, so it survives checkouts)
        f.write("import sys; sys.path.insert(0, '.')\nfrom calc import add\nsys.exit(0 if add(2, 2) == 4 else 1)\n")
    git("bisect", "start", "HEAD", shas[0], cwd=repo)       # HEAD is bad, commit 1 is good
    out = git("bisect", "run", sys.executable, "-B", "check.py", cwd=repo)   # -B: never reuse a stale .pyc
    steps = sum(1 for line in out.splitlines() if line.startswith("running"))
    first_bad = [l for l in out.splitlines() if "is the first bad commit" in l][0].split()[0][:7]
    git("bisect", "reset", cwd=repo)
    print(f"== bisect over 32 commits: {steps} test runs ==\nfirst bad commit {first_bad} (expected {shas[22]} = commit 23)\n")
    assert first_bad == shas[22]

    # ---------- 3. 'I lost my work': reset --hard, then recover with the reflog ----------
    repo = fresh_repo(root, "reflog")
    commit(repo, "notes.txt", "one\n", "keep 1")
    lost = commit(repo, "notes.txt", "one\ntwo\n", "important work")

Recover it

(a) A test started failing on main sometime in the last 400 commits; nobody knows why. (b) You ran git reset --hard HEAD~3 on your feature branch and lost three commits you needed. (c) A bad commit was merged to main and deployed an hour ago; others have pulled since. (d) You accidentally committed an AWS key and pushed it.

Answer

(a) git bisect start; git bisect bad HEAD; git bisect good <known-good-sha>; git bisect run pytest tests/test_x.py — about 9 steps (log₂ 400 ≈ 8.6). Make sure the test is deterministic first, or bisect will converge on the wrong commit. This is why every commit on main should build and pass.

(b) git reflog shows the commit before the reset (e.g. HEAD@{1}); git reset --hard HEAD@{1} or git branch rescued <sha>. The commits were never deleted — reset only moved the label — and unreachable commits survive for weeks.

(c) git revert <sha> — a new commit that undoes it, safe for everyone who pulled. Do not reset or force-push shared history. Roll back the deployment first if that's faster — deploy rollback and code revert are separate levers — then merge the revert so the next deploy doesn't reintroduce the bug.

(d) Revoke and rotate the key immediately — assume it was scraped within minutes (bots scan public pushes). Then check the provider's logs for misuse, remove it from history with git filter-repo if policy requires (coordinating a re-clone), and add secret scanning and pre-commit hooks so it can't recur. Rewriting history alone fixes nothing.
