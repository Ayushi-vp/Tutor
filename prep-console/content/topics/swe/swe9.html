For years, a mid-sized company released software once a month. Each release bundled several hundred changes, took a weekend, and was preceded by a week-long "code freeze" and followed by a week of firefighting. When something broke, nobody could tell which of the 300 changes caused it, so rolling back meant losing a month of everyone's work. Releases became scarier, so the company made them rarer, so each one got bigger and scarier still. Meanwhile a competitor deployed 30 times a day, each deployment one small change, each exposed first to a sliver of users, each reversible in a minute. Its releases were boring. That was the point.

The discipline that turns the first company into the second is continuous integration and continuous delivery (CI/CD) together with progressive deployment: every change is built and tested automatically as it merges; the tested artefact is deployed in stages that expose it to a small share of traffic first; and each stage is watched and rolled back automatically if it misbehaves. Its central insight, backed by years of industry research, is that speed and safety aren't a trade-off. Small, frequent, reversible changes are both faster and safer than large, rare ones, because each one is easier to understand, test, observe and undo.

This lesson covers the machinery: pipelines and artefacts; rolling, blue-green and canary deployments, including the statistics that decide how big and how long a canary must be and the error-budget arithmetic that makes the case for staging; feature flags, which separate deploying code from releasing behaviour; rollback and why it has to be designed in; and database migrations that stay compatible while old and new versions run side by side. The case study is CrowdStrike's July 2024 outage, in which a content update pushed to every online Windows sensor at once crashed about 8.5 million machines worldwide in 78 minutes — the clearest recent demonstration of what staged rollout exists to prevent. The final part applies all of it to rolling out a new model or prompt behind a flag. The lab runs an expand–contract migration against SQLite with two app versions live at every step, and computes the canary maths.

The analogy: how new medicines reach patients

A new drug isn't given to everyone the day it's made. It's manufactured once, in a controlled batch, and the same batch is what gets tested. It's tried first on a small group, closely monitored against a control group taking the existing treatment. Only if the small group shows no harm and some benefit is it given to a larger group, then more widely. At any stage, if something alarming appears, the trial stops and patients return to the old treatment. Regulators insist on this not because they expect every drug to be dangerous, but because the cost of being wrong at full scale is so much higher than at small scale.

Deployment works the same way. The artefact is the batch — built once. The canary is the small trial group, compared against a control. Widening in stages with bake time is the phased trial. Rollback is returning patients to the old treatment. Where the analogy breaks: software stages take minutes, not years, and can be automated end to end — which is what makes it possible to do this dozens of times a day.

The pipeline

A few words recur throughout. Continuous integration (CI) builds and tests every change as it merges. Continuous delivery keeps the result always releasable; continuous deployment releases every passing change automatically. An artefact is the built output — a container image, a Python wheel — tagged with the commit it came from. A deployment strategy decides how the new artefact replaces the old: all at once, a few servers at a time, or to a small share of traffic first. The blast radius is how many users a bad change can reach before it's stopped. And rollback returns to the last good version — which, as this lesson will show, is only possible if every change was designed to be compatible with the version before it.

It helps to be precise about what "a change" includes, because the most damaging incidents often come from the changes teams don't think of as deployments. A new version of the code is one. So is a new container base image, a dependency upgrade, a database migration, a runtime configuration value, a feature flag flipped from 5% to 100%, a security rule, a content file pushed to clients, a new prompt template or a new model version. Each changes the behaviour of a running system, each can break it, and each deserves the same path: versioned, reviewed, tested against the real consumer, rolled out in stages, and reversible in one step.

One idea connects all of it: reduce the batch size. A deployment containing one small change is easy to test, easy to watch, easy to attribute a problem to, and easy to undo. A deployment containing three hundred changes is none of those things. Nearly every practice in this lesson — trunk-based development, feature flags, canaries, expand–contract migrations — is a way of making each unit of change smaller, so that each one carries less risk and more of them can flow safely.

1. Continuous integration: every change, built and tested

Continuous integration means that every change merged into the main branch is automatically built and tested, and the team treats a failing main as an emergency. It rests on trunk-based development (swe8): if everyone integrates daily, the CI system is testing the code everyone is actually working on. A typical pipeline for a pull request runs formatting and lint checks, a type checker, unit tests, integration tests against real dependencies in containers, and a build of the artefact, in parallel where possible. The target is fast feedback — under about ten minutes — because a slow pipeline makes people batch changes, and batching is exactly what CI exists to prevent. The suite must also be trustworthy: a flaky test (swe5) that fails one run in twenty teaches everyone to click "rerun", and then a real failure gets rerun too.

Two practices keep main green as the team grows. A merge queue tests each change on top of the latest main plus the changes ahead of it, catching semantic conflicts between individually passing PRs (swe8). And hermetic, reproducible builds — pinned dependency versions (lockfiles), pinned base images, no network access during tests — make "it passed in CI" mean the same thing every time.

2. Build once, promote the artefact

The pipeline's output is an artefact: for a web service, usually a container image tagged with the commit hash (app:3f9c2d1). The rule is build once, deploy many: the exact image that passed tests is the one deployed to staging and then production, with environment differences (database URLs, credentials, flag defaults) injected as configuration at run time. Rebuilding for each environment risks shipping something that wasn't tested — a dependency that resolved to a newer version, a build flag that differs. Tagging by commit also makes every running version traceable to its source, and makes rollback trivial: deploy the previous tag.

From there, continuous delivery means every artefact that passes is releasable, and deploying is a routine, automated operation anyone on the team can trigger. Continuous deployment removes the manual trigger. Whichever a team chooses, the research programme DORA (DevOps Research and Assessment) measures how well delivery works with five metrics: change lead time (commit to production), deployment frequency, failed deployment recovery time, change fail rate (the share of deployments needing immediate intervention) and deployment rework rate (unplanned deployments caused by production incidents). Its repeated finding is that these metrics move together: teams that deploy most often also have the lowest failure rates and fastest recovery.

3. Deployment strategies

Once an artefact is ready, a deployment strategy decides how it replaces the running version. Four are common, and they trade speed, cost and blast radius differently.

Recreate: stop all old instances, start new ones. Simple, but there's downtime; acceptable only for batch jobs or internal tools.

Rolling: replace instances a few at a time — Kubernetes' default (sc15). Capacity stays up and no extra infrastructure is needed. During the rollout, old and new versions serve traffic simultaneously, so they must be compatible with each other and with the shared database. Rollback is another rolling deploy, taking as long as the rollout did.

Blue-green: run the current version (blue) and a full copy of the new version (green) side by side, test green, then switch the load balancer to send all traffic to green at once. Switching back is equally instant, which is its great strength. Its costs: double infrastructure during the switch, and every user moves to the new version in the same instant, so a bug that tests missed hits everyone until someone notices and switches back.

Canary: route a small share of traffic — 1%, 5% — to the new version while the rest stays on the old, compare the two, and widen in stages (for example 5% → 25% → 50% → 100%) with bake time at each. The name comes from the canaries miners carried as early warnings. Canaries give the smallest blast radius, at the price of needing good metrics, traffic-splitting infrastructure and the discipline to wait. A variant, ring deployment, rolls out to groups rather than traffic percentages: employees first, then a small set of customers, then a region, then everyone. Shadow traffic (or dark launch) goes further back: copy real requests to the new version, compare its responses with the old version's, but return only the old version's responses to users.

4. Canary analysis: the statistics and the error budget

A canary is only as good as its ability to tell a bad release from noise. Suppose the current version fails 0.1% of requests and you want to catch any release that pushes that to 1%. During the canary window the new version serves 1,000 requests. If it's healthy, you expect 0.1% × 1,000 = 1 error; if it's bad, 10. Error counts in a window are well modelled by a Poisson distribution, so you can choose a rollback threshold and compute both kinds of mistake. With "roll back if there are 5 or more errors": for a healthy release, P(X ≥ 5 | mean 1) ≈ 0.0037 — a false alarm about once in 270 releases; for the bad release, P(X ≥ 5 | mean 10) ≈ 0.97 — caught 97% of the time. With only 100 canary requests, the means would be 0.1 and 1, and no threshold separates them well: the canary would be theatre. That's why canary size and duration should be derived from traffic and the smallest regression you care about, not picked by habit.

Two refinements matter in practice. Compare against a control, not a constant. Error rates vary with time of day, upstream incidents and traffic mix. Google's SRE guidance is to compare the canary with a control group of old-version instances receiving the same kind of traffic at the same time, so shared effects cancel. Watch more than errors: latency percentiles, saturation (CPU, memory, queue depth), and business metrics such as checkout completions; a release can return 200s while doing the wrong thing.

The error budget (sc13) turns staging into arithmetic. A service with a 99.9% monthly SLO and 50 million requests a month may fail 50,000 of them. Averaged over a 30-day month, it serves about 69,400 requests an hour. Now imagine a release that fails 20% of requests and stays live for an hour before someone notices. At 100% of traffic it fails about 13,900 requests — 27.8% of the whole month's budget in one hour. On a 5% canary it fails about 690 — 1.4% of the budget. Same bug, same detection time, twenty times less damage. That calculation is the business case for progressive delivery, and it's why a well-run team pauses risky deploys when the budget runs low.

5. Feature flags: separating deploy from release

A feature flag is a runtime switch around a code path:

if flags.enabled("new_checkout", user=user):
    return new_checkout(cart)
return old_checkout(cart)

Flags split two events that used to be one. Deploying puts code on servers; releasing exposes behaviour to users. With flags, code is deployed dark — merged and running, switched off — and released later, gradually and reversibly: 1% of users, then employees, then 10%, then everyone, each step a configuration change taking effect in seconds, and turned off just as fast if something goes wrong. Pete Hodgson's taxonomy distinguishes release flags (hide unfinished work; short-lived), experiment flags (assign users to A/B variants), operational flags or kill switches (turn off an expensive feature or a failing dependency during an incident; long-lived), and permission flags (features by plan or customer).

Flags have real costs. Every flag doubles the code paths through its region, and tests usually cover only one position. Flags that are never removed accumulate into flag debt: dead branches nobody dares delete, and switches whose meaning has been forgotten. Worst is reusing a flag's name or bit for a new purpose, which is how Knight Capital reactivated code that had been unused since 2003 and lost more than $460 million in about 45 minutes — the case study for swe11. The hygiene rules: every flag has an owner and an expiry date, release flags are deleted once fully rolled out, flag changes are logged and reviewed like deployments, and flag evaluation fails safe (to the old behaviour) if the flag service is unreachable.

6. Rollback, roll forward, and backward compatibility

When a release misbehaves, the fastest remedy is usually rollback: redeploy the previous artefact or flip the flag back. Roll forward — deploying a fix — is sometimes right, when the fix is small and certain or rollback isn't possible, but it's slower and riskier under pressure. The default in a mature team is "roll back first, investigate later".

Rollback only works if the new version didn't do anything the old version can't cope with. During any rolling or canary deployment, and after any rollback, two versions share the same database, message queues, caches and clients. So every change must be backward compatible (the new version works with data and messages the old one produced) and forward compatible (the old version tolerates data and messages the new one produced). Dropping a column, changing a message format, writing a new enum value the old code doesn't recognise, or sending emails in a new flow can all make rollback impossible or harmful. The discipline that solves this for schemas — expand–contract — generalises to APIs (swe7) and event formats.

7. Database migrations: expand–contract

Suppose you want to rename users.fullname to users.display_name in a table serving thousands of requests a second. The obvious migration — ALTER TABLE users RENAME COLUMN fullname TO display_name — breaks every running instance of the old code the moment it executes; the lab shows the old version's reads failing with no such column: fullname. And if the new code then has a problem, rolling it back breaks again, because the old code expects the old name.

Expand–contract (also called parallel change) makes the change in steps, each compatible with the versions running beside it:

  1. Expand: add display_name as a nullable column with no default — a fast metadata change in most databases.
  2. Dual-write: deploy code that writes both columns and reads COALESCE(display_name, fullname). Old instances keep working; they just don't populate the new column.
  3. Backfill: copy fullname into display_name for existing rows, in batches of a few thousand by primary-key range, pausing between batches and watching replication lag, resumable if interrupted. Run it again after the old version is fully gone, to catch rows it wrote late.
  4. Switch reads: deploy code that reads only the new column but still writes both, so rolling back one step stays safe. Verify there are no mismatches.
  5. Stop writing the old column, then — days later, when nothing and no rollback target reads it — contract: drop it.

Database-specific traps sit inside those steps. In Postgres, most ALTER TABLE forms need an exclusive lock; if a long-running transaction holds a conflicting lock, the ALTER waits — and every query that arrives after it queues behind it, so a "fast" migration can stall the whole table. Set a short lock_timeout and retry. Build indexes with CREATE INDEX CONCURRENTLY. Add constraints as NOT VALID and validate them separately. Adding a column with a constant default has been fast since Postgres 11, but rewriting every row (changing a column's type) is not. For very large MySQL tables, online schema-change tools (gh-ost, pt-online-schema-change) copy the table in the background. The honest cost of expand–contract is several deploys for one rename, which is why teams avoid cosmetic schema changes.

8. Configuration, content and data are deployments too

Many organisations have strong controls for code and none for everything else. But feature-flag changes, runtime configuration, security rules, routing tables, content files, prompt templates and model versions all change a running system's behaviour, often more abruptly than code, because they're designed to take effect instantly everywhere. They deserve the same pipeline: version control, review, validation that loads the change into the real consumer (not just a schema check), staged rollout with bake time, monitoring, and one-step rollback to the last known-good version. The case study is what happens when a content update skips those steps.

9. Rolling out models and prompts

A new model version or prompt is a deployment whose failures are usually quality regressions rather than errors, which changes the verification but not the shape of the pipeline. Offline evaluation first: run the fixed evaluation set (swe5) and compare quality, safety refusals, cost and latency with the current version. Shadow: send a copy of real traffic to the new version, log its outputs without showing them, and compare — including with an automated grader or human review of disagreements. Canary behind a flag: release to a small percentage of users, compared with a control group on online signals — task success, user ratings, escalations to humans, retries, latency and cost per request. Widen in stages with bake time long enough to see slower signals. And keep instant rollback: the old model or prompt stays deployed and the flag flips back, with model versions pinned so nothing changes underneath. The statistics from section 4 apply with more force, because quality metrics are noisier than error rates, so canaries for models need larger samples or longer windows to detect meaningful regressions.

Why small batches are safer: the arithmetic of change risk

If each change independently has a small probability p of causing an incident, a deployment of n changes fails with probability 1 − (1 − p)n, which grows almost linearly for small np: at p = 1%, a one-change deploy fails 1% of the time, a 100-change deploy about 63% of the time. More importantly, the cost of a failure grows with batch size too: diagnosing which of 100 changes is at fault takes far longer, rolling back discards 99 good changes, and a fix must be tested against all of them. Frequent small deployments convert rare, large, hard-to-diagnose failures into more frequent, tiny, obvious ones — the reason DORA finds throughput and stability correlated rather than traded off.

Automated canary analysis

At scale, humans can't watch every canary, so organisations automate the judgement. Netflix and Google's open-source Kayenta, used with Spinnaker, is the best-known example: for each canary it collects metrics from the canary and control groups, runs a statistical test per metric (for example the Mann–Whitney U test, which compares distributions without assuming normality), classifies each metric as pass, high or low, and combines them into a score that decides promotion or rollback. The design issues are statistical: control and canary should be the same size and started at the same time (a freshly started baseline avoids comparing warm old instances with cold new ones), each metric needs a direction (latency up is bad, throughput down may be), and testing dozens of metrics at once inflates false alarms unless thresholds account for multiple comparisons.

Cells and blast-radius engineering

Traffic percentages bound how many requests a bad release affects, but not which customers or which infrastructure. Cell-based architecture (sc17) goes further: split the service into independent copies (cells), each serving a fixed subset of customers with its own infrastructure, and deploy cell by cell. A bad release, or a poison input that crashes the software, then takes down one cell's customers rather than everyone. Large cloud providers deploy in waves — a single host first, then progressively larger slices of their infrastructure, one location at a time — with bake time between waves, precisely because a problem that appears in one place can be stopped before it reaches the next. The same thinking underlies rings for client software and staged rollouts for configuration.

Deploying clients you don't control

Server deployments can be rolled back in minutes; software on customers' devices is harder. Mobile apps go through app-store review and users update at their own pace, so old versions stay in use for months — which makes server APIs' backward compatibility (swe7) essential and pushes risky behaviour behind server-side flags. Endpoint agents like CrowdStrike's run with deep privileges on customer machines, and a crash loop may leave the machine unable to receive the fix, so recovery can require manual work on each device. For such software, staged rollout, customer-controlled update timing, and defensive handling of bad updates (validate, fall back to the last good version, never crash on bad content) are the only effective protections.

Migrations at the data layer beyond schemas

Some migrations move data between systems — from one database to another, from a monolith's tables into a new service. Stripe's account of migrating hundreds of millions of subscription objects describes the standard four steps, which are expand–contract at system level: dual-write to the old and new stores; change reads to the new store (verifying against the old); change writes to go only to the new store; remove the old data. Each step is deployed and verified separately, with the old path available until the new one is proven, and comparison tooling that reads both and reports mismatches. The pattern recurs in ML platforms when moving a feature store, changing an embedding model (which requires re-embedding the whole corpus: dual-index, backfill, switch queries, drop the old index) or migrating a vector database.

Supply-chain integrity in the pipeline

The pipeline itself is an attack surface: anything that can modify an artefact between commit and production can compromise every deployment. Practices to know: build in isolated, ephemeral environments; pin dependencies by hash; generate a software bill of materials (SBOM) listing every component; sign artefacts and verify signatures at deploy time (Sigstore's cosign is common); record build provenance (which source, which builder, which inputs), as described by the SLSA framework; and restrict who can change pipeline definitions. The 2020 SolarWinds compromise, in which attackers inserted code into a vendor's build process so that signed updates carried a backdoor, is the usual cautionary example (swe13 covers supply-chain security).

How delivery fails in production

Deployment-related incidents follow recognisable patterns. Global, instant changes — a configuration push, a feature flag flipped to 100%, a content update — bypass the staging that code gets. Incompatible changes break during the window when two versions coexist, or make rollback impossible. Canaries that can't see: too little traffic, too short, the wrong metrics, or a regression that only appears for one customer segment. Slow rollback: rebuilding instead of redeploying the previous artefact, or a rollback that must also undo a migration. Deploy fatigue: manual steps that someone skips at 6 p.m. on a Friday. The signals worth tracking are DORA's five metrics, the share of incidents that began with a change (commonly a majority), time from detection to rollback, and the fraction of changes — including configuration — that went through progressive rollout.

Case: CrowdStrike Channel File 291, 19 July 2024

CrowdStrike's Falcon sensor is security software that runs on customers' Windows machines with a kernel driver, so it can observe system activity and block attacks. Alongside sensor releases, which ship code, CrowdStrike delivers Rapid Response Content: detection rules sent from the cloud as "channel files" and interpreted by the sensor, designed to reach every sensor quickly to respond to new threats. In the company's words, this content is "configuration data; it is not code or a kernel driver." That distinction turned out to matter a great deal, because configuration was not treated with the same rollout caution as code.

The root-cause analysis CrowdStrike published in August 2024 describes a chain of latent issues. In February 2024, sensor version 7.11 introduced a new "IPC Template Type" for detecting attacks that abuse Windows inter-process communication, delivered through Channel File 291. The template type's definition declared 21 input fields, but the sensor code that invoked the content interpreter supplied only 20 values. Nothing noticed, because every test and every template instance deployed until July used a wildcard — "match anything" — for the 21st field, so the interpreter never actually read it. The automated tests used a static set of 12 test cases whose channel file, chosen by hand, had a wildcard in field 21 for every instance. The Content Validator, which checks new content before release, had a logic error: it evaluated the instances assuming 21 inputs would be provided.

On Friday 19 July 2024 at 04:09 UTC, CrowdStrike released two new template instances, one of which used a non-wildcard criterion for the 21st field. The validator passed it. The update went to every online Windows sensor running 7.11 or later. At the next inter-process communication event on each machine, the interpreter tried to read the 21st element of a 20-element array, read an invalid pointer, and crashed the Windows kernel. Machines rebooted into the same crash. CrowdStrike reverted the content at 05:27 UTC — 78 minutes later — but machines already crashing couldn't stay up long enough to receive the fix, and many needed manual intervention, some with encrypted disks requiring recovery keys. Microsoft estimated that 8.5 million Windows devices were affected, less than 1% of all Windows machines, but concentrated in airlines, hospitals, banks and broadcasters, which is why flights were grounded and surgeries postponed around the world.

The incident is a textbook of this track's lessons failing together. A contract mismatch between two components (swe1) — the definition said 21, the code passed 20. Tests that never exercised the risky input (swe5): every test used the wildcard. A validator that checked against the definition, not the real consumer. A consumer that crashed instead of rejecting bad input (swe4) — in kernel mode, where a crash takes down the machine. And the decisive one for this lesson: no staged rollout for content. CrowdStrike's remediation list maps onto each: an input-count check at compile time, bounds checking in the interpreter, tests with non-wildcard criteria for every field, fixes to the validator, testing every new template instance, and — for deployment — "staged deployment" in which new template instances pass canary testing and are "successively promoted to wider deployment rings or rolled back if problems are detected", with bake time between rings, plus giving customers control over when content updates reach their machines. With a 1% canary ring and a short bake, the same bug would have crashed tens of thousands of machines instead of millions — still an incident, but not a global one.

The same lessons for AI systems

AI platforms push many things that behave like CrowdStrike's content: prompt templates, safety-filter rules, retrieval configuration, model routing tables, feature definitions and new model versions. They're often changed through dashboards precisely so they can take effect instantly everywhere — which is the property that made Channel File 291 dangerous. The defences are the same: version and review them; validate them by loading them into the real serving path in CI; roll them out behind flags to a small share of traffic with automated comparison against a control; bake long enough to see quality signals; and keep the previous version one flag-flip away. And make the consumer defensive: a malformed prompt config or tool schema should be rejected with the last good version kept, not crash the service.

Tools and knobs

CI systems (GitHub Actions, GitLab CI, Buildkite) with caching and parallelism; merge queues; container registries with images tagged by commit; progressive-delivery controllers such as Argo Rollouts or Flagger on Kubernetes, and Spinnaker with Kayenta for automated canary analysis; feature-flag platforms (LaunchDarkly, Unleash, OpenFeature-compatible SDKs) with audit logs and expiry; migration tools (Alembic for Python, Flyway, Liquibase) with lock_timeout and concurrent index creation; deploy freezes tied to error-budget policy; and dashboards of DORA metrics per service.

"""swe9 lab: (1) rename a column with expand-contract while old and new app versions run side by side;
(2) canary maths: how many requests you need to tell a bad release from noise, and what it costs in error budget."""
import math
import sqlite3

# ---------- 1. expand / contract: rename users.fullname -> users.display_name ----------
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, fullname TEXT)")
db.executemany("INSERT INTO users (fullname) VALUES (?)", [("Ada Lovelace",), ("Alan Turing",)])

def v1_write(name):  db.execute("INSERT INTO users (fullname) VALUES (?)", (name,))
def v1_read(uid):    return db.execute("SELECT fullname FROM users WHERE id=?", (uid,)).fetchone()[0]
def v2_write(name):  db.execute("INSERT INTO users (fullname, display_name) VALUES (?, ?)", (name, name))   # dual-write
def v2_read(uid):    return db.execute("SELECT COALESCE(display_name, fullname) FROM users WHERE id=?", (uid,)).fetchone()[0]
def v3_write(name):  db.execute("INSERT INTO users (display_name) VALUES (?)", (name,))
def v3_read(uid):    return db.execute("SELECT display_name FROM users WHERE id=?", (uid,)).fetchone()[0]

def works(fn, *args) -> str:
    try:
        fn(*args); return "ok"
    except sqlite3.OperationalError as e:
        return f"FAIL ({e})"

# the tempting one-step version, while v1 is still serving traffic:
big_bang = sqlite3.connect(":memory:")
big_bang.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, fullname TEXT)")
big_bang.execute("ALTER TABLE users RENAME COLUMN fullname TO display_name")
try:
    big_bang.execute("SELECT fullname FROM users")
except sqlite3.OperationalError as e:
    print(f"big-bang rename while v1 still runs -> v1 read fails: {e}\n")

phases = [
    ("0 start           (v1 only)",       None,                                                        [("v1", v1_write, v1_read)]),
    ("1 expand          (+ nullable col)", "ALTER TABLE users ADD COLUMN display_name TEXT",           [("v1", v1_write, v1_read), ("v2", v2_write, v2_read)]),
    ("2 backfill        (copy old rows)",  "UPDATE users SET display_name = fullname WHERE display_name IS NULL",
                                                                                                         [("v1", v1_write, v1_read), ("v2", v2_write, v2_read)]),
    ("3 switch          (v3 reads new)",   "UPDATE users SET display_name = fullname WHERE display_name IS NULL",  # catch rows v1 wrote late
                                                                                                         [("v2", v2_write, v2_read), ("v3", v3_write, v3_read)]),
    ("4 contract        (drop old col)",   "ALTER TABLE users DROP COLUMN fullname",                    [("v3", v3_write, v3_read)]),
]
for label, ddl, versions in phases:
    if ddl:
        db.execute(ddl)
    results = [f"{v}: write {works(w, 'Grace Hopper')}, read {works(r, 1)}" for v, w, r in versions]
    print(f"phase {label}: " + " | ".join(results))
print("final read of user 1 via v3:", v3_read(1))
print("sqlite", sqlite3.sqlite_version)

# ---------- 2. canary maths ----------
def poisson_tail(k: int, lam: float) -> float:           # P(X >= k) for X ~ Poisson(lam)
    return 1 - sum(math.exp(-lam) * lam ** i / math.factorial(i) for i in range(k))

base_rate, bad_rate, n = 0.001, 0.01, 1000             # healthy 0.1% errors; a bad release 1%; 1,000 canary requests
threshold = 5                                           # roll back if >= 5 errors in the canary window
print(f"\ncanary of {n} requests, rollback at >= {threshold} errors:")
print(f"  false alarm on a healthy release  P = {poisson_tail(threshold, base_rate * n):.4f}")
print(f"  catches a 1%-error release        P = {poisson_tail(threshold, bad_rate * n):.4f}")

monthly_requests, slo = 50_000_000, 0.999
budget = monthly_requests * (1 - slo)                   # failures allowed per 30 days
per_hour = monthly_requests / (30 * 24)
for share in (0.05, 1.0):
    failed = per_hour * share * 0.20                    # a release that fails 20% of requests, live for one hour
    print(f"  bad release (20% errors) on {share:>4.0%} of traffic for 1 h: {failed:>7,.0f} failures = {failed / budget:5.1%} of the monthly budget")
Plan the migration

Rename users.name to users.full_name in a Postgres table with 80M rows, serving 5,000 requests/s, with zero downtime and rolling deploys.

Answer

A direct RENAME COLUMN breaks every running instance of the old code the moment it runs, and rollback breaks again. Expand–contract instead:

  1. Migration 1: ALTER TABLE users ADD COLUMN full_name text — nullable, no default, so it's a fast metadata change. Run it with a short lock_timeout and retries, so it can't queue behind a long transaction and block the table.
  2. Deploy A: write both name and full_name; read coalesce(full_name, name).
  3. Backfill in batches of ~10k by primary-key range with pauses (UPDATE … SET full_name = name WHERE id BETWEEN … AND full_name IS NULL), monitoring replication lag; resumable. At 80M rows that's ~8,000 batches — hours, deliberately.
  4. Deploy B: read only full_name, still write both (so rolling back to A stays safe). Verify with a count of mismatches.
  5. Deploy C: stop writing name.
  6. Migration 2, days later: drop name; if full_name must be NOT NULL, add a CHECK (full_name IS NOT NULL) NOT VALID constraint and validate it separately, to avoid a long exclusive lock.

Every step can be rolled back independently, and at every step old and new code versions coexist safely. Name the cost honestly: five or six deploys for a rename — which is why teams avoid renames that are only cosmetic.
