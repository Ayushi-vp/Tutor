Imagine a NumPy-fluent engineer on day one of a PyTorch codebase. They write attn = q @ k.transpose(-2, -1), then try to flatten something with .view(batch, -1) and get an error about a view size "not compatible with input tensor's size and stride". They switch to .reshape because a forum post said so. It works. A week later a teammate's code writes into the result of a reshape, expecting the change to reach the original tensor, and it silently does not — because this time reshape made a copy. Elsewhere, an evaluation loop appends logits[:, -1] to a list and the process's memory climbs by hundreds of megabytes per batch until it dies, even though each saved item "only" has one position. And when they feed a NumPy array to the model, they get "mat1 and mat2 must have the same dtype, but got Double and Float".

None of these are exotic. They all come from one fact that a NumPy-shaped intuition hides: a PyTorch tensor is not a box of numbers. It is a small description — what type of number, on which device, what shape, and how to walk through memory — that points into a separate block of bytes. Several tensors can point into the same block. Some operations make a new description and move nothing; some move every byte. Some modify memory that other tensors, and the autograd engine, are still relying on.

In an ML-debugging interview, these are the first bugs planted, because they produce wrong results or crashes far from their cause. The interviewer wants to hear you reason from the memory model: "this is a view, so this write changes the original", "this slice keeps the whole storage alive", "this in-place op overwrote a tensor autograd saved".

This lesson builds that model from the ground up: storage and metadata, the stride formula with worked examples, which operations make views and which copy, what contiguous() really does, dtypes and the memory arithmetic they imply, devices, in-place operations and the version counter that protects autograd, and the zero-copy bridge to NumPy. Everything is checked against PyTorch 2.14, the current release on 8 October 2026.

Start with a bookshelf. A storage is one long shelf of numbered slots, each holding one number of the same type: slot 0, slot 1, slot 2 and so on. The shelf lives in one room — the CPU's main memory or a particular GPU's memory. A tensor is a reading guide for that shelf: "start at slot 0; my data is 3 rows by 4 columns; to go to the next row, skip 4 slots; to go to the next column, skip 1 slot". Two different reading guides can describe the same shelf in different ways. One says "3 rows of 4"; another says "4 rows of 3, where moving down a row skips 1 slot and moving along a row skips 4". The second guide is the transpose of the first, and producing it required writing a new guide, not rearranging the shelf.

That reading guide is the tensor's metadata. It has five parts:

  • dtype — the type of number in every slot (float32, bfloat16, int64, bool…), which fixes how many bytes each slot takes.
  • device — which room the shelf is in: cpu, cuda:0, mps (Apple GPUs) or meta (no shelf at all, just the guide).
  • shape (also called size) — how many entries along each dimension, such as (3, 4).
  • strides — for each dimension, how many slots to skip to take one step along it, such as (4, 1).
  • storage offset — which slot holds the first element.

With those five numbers, the position of any element is simple arithmetic: slot = offset + i × stride[0] + j × stride[1] + …. For a fresh 3×4 tensor with strides (4, 1) and offset 0, element [2, 1] is at slot 0 + 2·4 + 1·1 = 9.

Three consequences follow, and the rest of the lesson unpacks each one. First, many operations — transpose, permute, slicing, adding a dimension — only write a new reading guide. They are free, and they create views: tensors that share a storage, so writing through one changes what the others see. Second, some reading guides describe memory that is jumbled relative to plain row-major order (non-contiguous), and some operations need it unjumbled, which forces a real copy. Third, because several tensors can see the same bytes, writing into a tensor in place is risky: something else, including the autograd engine that computes gradients, may still need the old value.

Where the analogy breaks: a real shelf is either in one room or another, but a PyTorch storage on a GPU is not readable from the CPU at all without an explicit copy, and that copy costs time. Also, the slots are all exactly the same width — you cannot mix float32 and int64 on one shelf; changing dtype means a new shelf (or, rarely, reinterpreting the same bytes, which view(dtype) does on purpose).

If you remember one sentence: a tensor is a view onto storage, described by dtype, device, shape, strides and offset; ask of every operation whether it changes the description or the bytes.

1. Making tensors, and the dtype you get by default

You create tensors from Python data, from NumPy, or with a factory function. The dtype you get depends on how:

import torch, numpy as np
torch.tensor([1, 2]).dtype            # torch.int64   (Python ints → int64)
torch.tensor([1.0, 2]).dtype          # torch.float32 (Python floats → the default float dtype)
torch.zeros(3, 4).dtype               # torch.float32
torch.from_numpy(np.arange(3.0)).dtype  # torch.float64 (NumPy's default float)
torch.get_default_dtype()             # torch.float32

The default float dtype is float32. Factory functions such as zeros, ones, randn and empty use it unless you pass dtype=. Python integers become int64, the 8-byte integer, because indices into large tensors can exceed 231. NumPy arrays keep their own dtype, and NumPy's default float is float64 — that single fact causes a large share of "expected Float but found Double"-style errors.

torch.empty deserves a word: it allocates storage without initialising it, so it contains whatever bytes were there. It is the fastest constructor and the right one when you will overwrite every element; it is a bug when you forget to.

2. dtype: bytes per element, range and precision

The dtype fixes three things: how many bytes each element takes (its element size), the range of values it can hold, and how finely it can distinguish nearby values. The ones you will meet constantly:

dtypeBytesWhat it is forWatch out for
float324Default parameters, optimiser state, safe reductionsTwice the memory and much slower matmuls than 16-bit on modern GPUs
bfloat162Training and inference activations and weightsOnly about 3 significant decimal digits: 257 rounds to 256
float162Inference, older GPUs, training with loss scalingOverflows above 65,504
float648Scientific code, gradient checksVery slow on most GPUs; usually arrives by accident from NumPy
int64 (long)8Indices, token ids, class labelsLoss functions expect int64 targets
int32, int8, uint84, 1, 1Compact ids, quantised weights, image bytesuint8 arithmetic wraps around: 250 + 10 = 4
bool1MasksOne byte per element, not one bit

Memory arithmetic follows directly: bytes = number of elements × element size. A 7-billion-parameter model's weights need 7×109 × 4 = 28 GB in float32, 14 GB in bfloat16, 7 GB in int8. A batch of 32 sequences × 2,048 tokens × vocabulary 50,257 of float32 logits is 32 × 2,048 × 50,257 × 4 bytes ≈ 13.2 GB — which is why logits are a classic out-of-memory culprit and why careful code never materialises them in float32 at full size (pt7 returns to this).

Precision matters too. bfloat16 keeps float32's 8-bit exponent, so it covers the same range (up to about 3.4×1038), but has only 8 bits of significand precision, so between 256 and 512 it can only represent even numbers. Running it here: torch.tensor(257., dtype=torch.bfloat16) prints 256. float16 is the opposite trade: 11 bits of precision but a maximum of 65,504, so summing 70,000 ones in float16 gives inf. The general rule, which gpu4 covers in depth: store and multiply in 16 bits, accumulate sums in 32.

3. Type promotion: what dtype comes out when you mix them

When an operation receives different dtypes, PyTorch picks a result dtype by type promotion. The rules are ordered by category — bool, then integer, then floating point, then complex — and by whether the operand is a "real" tensor with dimensions, a zero-dimensional tensor, or a plain Python number.

  1. If the categories differ, the result takes the higher category. int64 tensor + 0.5 is float; since the float side is a Python scalar, PyTorch uses the default float dtype, float32.
  2. Within one category, a dimensioned tensor's dtype beats zero-dimensional tensors and Python scalars. A float16 activation times 2.0 stays float16, which is what you want — a Python constant should not double your memory.
  3. Among dimensioned tensors of the same category, the wider type wins: float16 + float32 → float32.
  4. If a zero-dimensional tensor is of a higher category than every dimensioned operand, the result is wide enough for it: an int32 tensor times a float64 zero-dimensional tensor gives float64 (checked on 2.14).

Two everyday consequences. Division with / is always true division, so torch.tensor([3]) / torch.tensor([2]) is a float tensor holding 1.5; use // for floor division, which stays integer. And in-place operations cannot change a tensor's dtype: int_tensor.add_(0.5) raises, because the result would have to be float but the storage is int.

4. Converting dtypes: .to(), .float(), .long() and view(dtype)

Changing dtype is always a new tensor with new storage, because the bytes per element change: x.float(), x.half(), x.bfloat16(), x.long() and x.to(torch.bfloat16) all allocate and convert every element. If the tensor already has that dtype they return it unchanged, with no copy — which means code like y = x.float(); y.add_(1) modifies x when x was already float32 and leaves it alone when it was float16. That is the same "sometimes a view, sometimes a copy" trap as reshape, and the fix is the same: never rely on which one happened, and clone() when you need ownership.

Conversions round. Float to integer truncates toward zero (torch.tensor([2.7, -2.7]).long() is [2, -2]); float32 to bfloat16 rounds to the nearest representable value, which is how 257 became 256. Converting back does not restore lost digits. .to() can change dtype and device in one call, x.to("cuda", torch.bfloat16), and x.to(other) matches another tensor's dtype and device — handy in a module that must create a tensor "like" its input.

One conversion does not copy on purpose: x.view(torch.int32) on a float32 tensor reinterprets the same bytes as integers (1.0 becomes 1065353216, its IEEE-754 bit pattern). That is used for bit tricks and packed quantised formats; used by accident, it produces garbage with no error, so when you see view with a dtype argument, slow down.

5. Device: where the storage lives

A tensor's device names the memory holding its storage. cpu is main memory. cuda:0, cuda:1 are NVIDIA GPUs (AMD GPUs under ROCm also appear as cuda). mps is Apple's GPU. meta is special: it records dtype, shape and strides but allocates nothing, so you can build a 70-billion-parameter model on the meta device in milliseconds to inspect its shapes, and materialise the real weights later — pt8 and pt11 use this.

Operations require all tensor inputs on the same device (zero-dimensional CPU tensors are an allowed exception). Mixing raises "Expected all tensors to be on the same device". x.to("cuda") or x.cuda() copies to the GPU and returns a new tensor; if x is already there, it returns x itself.

The cost model is the important part. A GPU runs operations asynchronously: the CPU queues work and moves on. Anything that needs a GPU value on the CPU — .item(), print(x), .cpu(), .tolist(), an if on a tensor — forces the CPU to wait until the GPU has finished everything queued before. That wait is called a host–device synchronisation, and pt12 shows how one stray .item() per step can cost 10-30% of throughput. Copies from CPU to GPU can overlap with compute only if the CPU memory is pinned (locked so the GPU can read it directly) and you pass non_blocking=True; pt5 covers that.

6. Shape, strides and the address formula

Now the heart of it. A stride is, for each dimension, how many elements to skip in storage to move one step along that dimension. For a freshly allocated tensor in row-major (C) order, the last dimension has stride 1 and each earlier stride is the product of all the sizes after it. A tensor of shape (2, 3, 4) has strides (12, 4, 1): one step along dimension 0 skips a whole 3×4 block of 12, one step along dimension 1 skips a row of 4.

The position in storage of element (i0, i1, …) is

slot = storage_offset + i0*stride[0] + i1*stride[1] + ...
byte address = storage_base + slot * element_size

Strides are counted in elements, not bytes (NumPy counts bytes, a frequent confusion when moving between the two). A worked trace on the tensor x = torch.arange(12.).reshape(3, 4), checked on 2.14:

ExpressionShapeStridesOffsetContiguous?
x(3, 4)(4, 1)0yes
x.t()(4, 3)(1, 4)0no
x[1] (one row)(4,)(1,)4yes
x[:, 1] (one column)(3,)(4,)1no
x[:, ::2](3, 2)(4, 2)0no
x.unsqueeze(0)(1, 3, 4)(12, 4, 1)0yes

Read the column slice: to get x[:, 1] = [1, 5, 9], start at slot 1 and step 4 each time. No data moved; the tensor just describes "every fourth slot starting at 1". All of these share the same 48-byte storage, which you can confirm with x[:, 1].data_ptr() pointing 4 bytes past x.data_ptr() or with x.untyped_storage().data_ptr() being equal for all of them.

7. Views: which operations share storage

A view is a tensor that shares storage with another (its base) and differs only in metadata. The PyTorch docs list the view operations; the ones you use daily are:

  • Basic indexing — integers, slices a:b:c, None and ....
  • view, unflatten, flatten (when possible), unsqueeze, squeeze.
  • t, transpose, permute, mT, movedim.
  • expand, narrow, select, split, chunk, unbind, diagonal, unfold, as_strided.
  • detach — a view that shares data but is cut off from autograd (pt3).

Operations that always copy: advanced indexing (an integer tensor or list, x[[0, 2]], or a boolean mask x[x > 0]), clone, repeat, arithmetic that produces new values, and .to() with a different dtype or device. Operations that sometimes copy: reshape, contiguous, flatten. Treat "sometimes" as a warning label — code should never rely on whether they did.

Writes go through views both ways:

x = torch.zeros(3, 4)
row = x[1]          # view
row.fill_(7.0)      # x[1] is now all 7s
col = x[:, 0]
col += 1            # in-place on a view: x[:, 0] is now 1, 8, 1

Advanced indexing on the left of an assignment is different: x[[0, 2]] = 5 is translated into an in-place index_put_ on x and does modify it, but y = x[[0, 2]]; y += 5 modifies a copy and leaves x unchanged. This asymmetry is a favourite planted bug.

8. Contiguity, view() versus reshape(), and the cost of contiguous()

A tensor is contiguous when its elements, read in row-major order, sit one after another in storage with no gaps or jumps — equivalently, its strides equal the row-major strides for its shape. x is contiguous; x.t() is not, because reading it row by row visits slots 0, 4, 8, 1, 5, 9, …

view(new_shape) must express the new shape with strides over the same memory. For x.t().view(12) it would need one stride that walks 0, 4, 8, 1, … — impossible — so PyTorch raises "view size is not compatible with input tensor's size and stride (at least one dimension spans across two contiguous subspaces). Use .reshape(...) instead." (the exact 2.14 message). reshape tries a view first and, failing that, copies into new contiguous storage. contiguous() returns the tensor itself when it is already contiguous and a row-major copy otherwise.

What does the copy cost? It is a read and a write of every byte. For the 13.2 GB logits tensor above, a contiguous() moves 26 GB of memory traffic; on a GPU with about 3 TB/s of memory bandwidth that is roughly 9 ms, every time. That is why you want to know whether your reshapes copy, and why attention code arranges its permutes so that the expensive matmuls receive layouts they like.

The pattern you will see in every transformer (and in pt10):

# x: (B, T, C) → split heads → (B, nh, T, hs)
q = q.view(B, T, nh, hs).transpose(1, 2)        # view, then free transpose
y = attention(q, k, v)                           # (B, nh, T, hs)
y = y.transpose(1, 2).contiguous().view(B, T, C) # undo: needs the copy

The last line is where the copy happens: after transposing back, heads and time are interleaved in memory, so the merge into C channels needs contiguous() before view.

9. Stride 0 and expand(); memory formats

A stride can be zero. torch.tensor([1., 2., 3.]).expand(4, 3) has shape (4, 3) and strides (0, 1): moving down a row skips nothing, so all four rows read the same three numbers. This is how broadcasting (pt2) works without copying. Reading is fine; writing is not, because four logical elements share one memory slot: expanded.add_(1) raises "more than one element of the written-to tensor refers to a single memory location. Please clone() the tensor before performing the operation." repeat(4, 1) makes a real 12-element copy you can write.

Strides also let one logical shape have different physical orders. Image tensors are logically NCHW (batch, channels, height, width). The channels_last memory format keeps that logical shape but stores the data NHWC: an 8×3×32×32 tensor converted with .to(memory_format=torch.channels_last) has strides (3072, 1, 96, 3) — channel varies fastest. Convolution kernels on NVIDIA tensor cores are often faster in that layout, and pt12 measures it. Because the logical shape did not change, the rest of the model's code does not change either.

10. In-place operations and the version counter

An in-place operation writes its result into an existing tensor's storage instead of allocating new memory. By convention its name ends in an underscore: add_, mul_, relu_, zero_, copy_. Augmented assignment on tensors (x += 1) and slice assignment (x[0] = 5) are in place too. They save an allocation, which matters for very large activations.

The danger comes from the autograd engine — the part of PyTorch that records operations during the forward pass and runs them backwards to compute gradients (pt3 teaches it properly; for now, think of it as "the forward pass leaves a trail of saved tensors that the backward pass reads"). Many backward formulas need values from the forward pass. Sigmoid's derivative is σ(x)(1 − σ(x)), so sigmoid saves its output. If you then modify that output in place, the backward pass would read the wrong numbers and produce a silently wrong gradient.

PyTorch prevents this with a version counter. Every tensor carries one (views share their base's counter), and every in-place write increments it. When an operation saves a tensor for backward, it records the current version. At backward time it compares. A trace, run on 2.14:

a = torch.randn(4, requires_grad=True)
b = a.sigmoid()          # sigmoid saves b, at version 0
b._version               # 0
b.mul_(2)                # in place: version 1
b.sum().backward()
# RuntimeError: one of the variables needed for gradient computation has been
# modified by an inplace operation: [torch.FloatTensor [4]], which is output 0
# of Sigmoid, is at version 1; expected version 0 instead.

The error names the operation (Sigmoid), the tensor's shape and both versions — read it, and you know exactly which tensor to stop modifying. Not every in-place op breaks: after y = a * 2; z = y * 3, doing y.add_(1) is fine, because multiplication by a constant has gradient 3 regardless of y, so y was never saved. Whether a tensor is saved depends on the backward formula of each operation that consumed it, which is why "in-place is fine here" is a judgement call you verify by running backward once.

A second rule: a leaf tensor that requires gradients — a parameter or an input you created with requires_grad=True — cannot be modified in place at all, because autograd would lose track of what its gradient refers to. w.add_(1) raises "a leaf Variable that requires grad is being used in an in-place operation". Optimisers update parameters in place, so they do it inside torch.no_grad(), which tells autograd not to record the update (pt3 and pt6).

The PyTorch paper (Paszke et al., NeurIPS 2019) describes this as a deliberate design: a versioning system that detects unsafe mutation, rather than copy-on-write, which would have made every program pay for hidden copies to protect the rare program that mutates saved data.

11. The NumPy bridge

PyTorch and NumPy can share memory on the CPU:

a = np.arange(3.0)          # float64
t = torch.from_numpy(a)     # no copy: t and a share the buffer
a[0] = 100                  # t[0] is now 100
n = t.numpy()               # no copy back either
n[2] = -1                   # t[2] and a[2] are now -1
c = torch.tensor(a)         # copy: later writes to a do not reach c

Rules to remember: from_numpy and .numpy() share memory; torch.tensor, torch.as_tensor with a different dtype or device, and np.array(t) copy. .numpy() only works on CPU tensors that do not require grad — otherwise you get "Can't call numpy() on Tensor that requires grad. Use tensor.detach().numpy() instead." For a GPU tensor the idiom is t.detach().cpu().numpy(), which is a device-to-host copy and a synchronisation.

Shared memory is a feature (zero-copy loading of a large dataset) and a hazard: a data pipeline that returns torch.from_numpy(buffer) and then reuses buffer for the next batch hands the model a tensor whose contents change underneath it. And because the dtype is kept, the boundary is where you cast: torch.from_numpy(a.astype(np.float32)) for features, .long() for class labels.

12. Memory lifetime: a small view keeps a big storage alive

PyTorch frees a storage the moment no tensor refers to it — the PyTorch paper calls out this reference counting, which piggybacks on CPython's own, as a deliberate choice over garbage collection so memory is released exactly when it stops being needed. The flip side is that a view is a reference. A run on 2.14:

big = torch.empty(1024, 1024, 256)   # 268 M float32 = 1.0 GiB
v = big[:1]                          # a 1 MiB slice, as a view
del big
v.untyped_storage().nbytes() / 2**30 # 1.0  — the whole GiB is still held
v = v.clone()                        # now only 1 MiB is held

In a training loop this shows up as memory that climbs and never falls: a list of per-step slices, a cache of "last hidden state" views, or a tensor kept for logging that still has an autograd graph attached (which keeps every saved activation of that step alive — pt3). The fix is .clone() for the data, .detach() to drop the graph, and .item() or .cpu() for logging scalars — remembering that those last two synchronise.

as_strided, unfold and the power and danger of hand-made strides

Because a tensor is just metadata over storage, you can write the metadata yourself with torch.as_strided(x, size, stride, offset). x.unfold(0, 128, 64) is the safe special case: it returns overlapping windows of a 1-D signal, shape (n_windows, 128) with strides (64, 1), each window starting 64 elements after the previous, with zero copying. im2col for convolutions (mc14) can be written the same way. The danger is that nothing checks your strides are sensible: as_strided can produce views that read past the logical end of the tensor into other data in the same storage, and overlapping views make in-place writes ambiguous. PyTorch detects the most common case — "unsupported operation: some elements of the input tensor and the written-to tensor refer to a single memory location", which is what x += x.t() raises on 2.14 — but only when it can prove the overlap. Use as_strided for read-only tricks and clone before writing.

Dense, non-overlapping and the kernels that care

Most element-wise kernels do not require contiguity; PyTorch's internal iterator (TensorIterator) computes addresses from strides and can even reorder dimensions so the innermost loop runs over the smallest stride. What kernels do care about is whether a tensor is non-overlapping and dense — every slot used exactly once, in some order. Then an element-wise op can process storage as one flat array and preserve the input's memory format in the output, which is why torch.relu(x_channels_last) returns channels_last. Matmul is pickier: cuBLAS (NVIDIA's dense linear-algebra library) accepts a matrix whose last dimension or second-to-last dimension has stride 1 — that is, row-major or column-major — so a @ b.t() needs no copy, but a matrix sliced with a step on both dimensions gets copied first. Custom C++ or Triton kernels often assume contiguity outright; a missing .contiguous() before one gives wrong numbers rather than an error, the worst possible failure.

The version counter is shared by views, and .data bypasses it

Views share their base's version counter, so an in-place write through any view invalidates saved tensors that alias the same storage: h = x.sigmoid(); h[:, 0].zero_() breaks backward exactly like modifying h. The legacy .data attribute returns a tensor that shares storage but has a separate version counter and no autograd history, so writing through .data silently corrupts saved tensors with no error. .detach() also drops history but shares the counter, so misuse is caught. This is the practical reason modern code uses detach() and with torch.no_grad(): and treats .data as a code smell.

Reductions and accumulation dtype

Summing many 16-bit numbers in 16 bits loses information long before it overflows: once the running sum is large, adding a small value rounds to no change (in bfloat16, 256 + 1 is 256). PyTorch's reduction kernels on CUDA accumulate half and bfloat16 sums in float32 internally and round the final result; the output dtype is still the input's. That protects a single sum(), but not a running total you build yourself across steps (total = total + loss with a bfloat16 total), not a cumulative sum whose intermediate values are stored, and not the case where the final result itself exceeds the format — the 70,000-ones float16 sum is inf on 2.14 CPU. Keep accumulators, loss tallies and metrics in float32; autocast (pt7) does this for loss computations by running softmax and reductions in float32.

Integer dtypes and indices

Indexing, gather, embedding and loss targets expect int64 by default (some accept int32). Token ids stored as int32 or uint16 to halve dataset size must be converted with .long() before use; uint16 data cast to int16 instead wraps ids above 32,767 to negative numbers, which then index from the end of the embedding table without any error. A vocabulary of 50,257 does not fit int16 but does fit uint16 — the conversion order matters. Integer overflow is silent in PyTorch, as in C: int32 element counts overflow at 2.1 billion, which a 70,000 × 32,768 attention score matrix exceeds.

Freed is not returned: the caching allocator

On the GPU, asking the driver for memory (cudaMalloc) and giving it back (cudaFree) are slow and make the CPU wait, so PyTorch keeps freed blocks in its own cache and hands them to the next allocation of a suitable size; the PyTorch paper shows the first iteration of ResNet-50 stalling on these calls and later iterations running smoothly once the cache is warm. The consequence for reasoning about tensors: when the last view of a storage dies, PyTorch's allocated counter (torch.cuda.memory_allocated()) drops at once, but the reserved counter (torch.cuda.memory_reserved()) and what nvidia-smi shows do not, because the block stays in the cache. A "leak" that shows only in nvidia-smi is usually the cache, not a leak; a leak shows in the allocated counter. The cache can also fragment: many free blocks of the wrong sizes, so a large allocation fails even though plenty is free in total. pt7 covers the allocator statistics and the expandable_segments setting that reduces fragmentation.

Tensor subclasses: why the metadata model generalises

Because a tensor is an interface (shape, dtype, device, strides) rather than a concrete buffer, PyTorch lets other objects behave as tensors. __torch_function__ and __torch_dispatch__ let a subclass intercept every operation. That is how DTensor represents a tensor sharded across many GPUs (FSDP2 in pt11 stores parameters as DTensors), how fake tensors run a model with shapes but no data to trace it for torch.compile (pt12), and how quantised weight formats in torchao (pt13) present packed integers as if they were floating-point weights. When you see a stride or dtype you did not expect in a modern codebase, check whether you are looking at a subclass.

Failure mode: memory that climbs and never comes back

Symptom: process or GPU memory grows by a fixed amount per step or per evaluation batch until an out-of-memory error, often hours in. Causes, in order of frequency: views of large tensors stored in a list (logits[:, -1], hidden[-1]); tensors stored for logging that still carry an autograd graph (losses.append(loss) instead of loss.item() or loss.detach()), which keeps every activation of that step alive; and caches keyed by tensors. To find it, compare torch.cuda.memory_allocated() before and after a step (pt7 shows the memory snapshot tool that names the allocation site), and check suspicious objects with t.untyped_storage().nbytes() versus t.numel() * t.element_size(): a large gap means a view pinning a bigger storage.

Failure mode: float64 creep

Symptom: training is several times slower than a reference, memory is about double, or a "same dtype" error appears at the first layer. A NumPy array, a pandas column, or a class-weight vector computed with NumPy enters as float64. If someone "fixed" the error by calling model.double(), everything runs in float64 — on consumer and many data-centre GPUs float64 throughput is a small fraction of float32. Guard the data boundary with an assertion in the first batch (assert x.dtype == torch.float32) and cast labels to int64 explicitly.

Failure mode: silent aliasing

Symptom: values change "by themselves", or a test passes on CPU and fails with workers or on GPU. Typical sources: a DataLoader collate function returns torch.from_numpy of a buffer it later reuses; a module stores a view of its input and the caller later modifies the input in place; or code relies on reshape having returned a view. Diagnose by comparing a.untyped_storage().data_ptr() == b.untyped_storage().data_ptr(). Fix by cloning at ownership boundaries: when data passes from one component to another that will keep it, clone it.

Failure mode: in-place errors after a refactor

Symptom: "modified by an inplace operation" appears after someone replaced x = x + y with x += y or switched an activation to inplace=True to save memory. Read the error: it names the operation whose saved tensor changed (for example "output 0 of SigmoidBackward" or "ReluBackward") and the expected and actual versions. If the forward is long, torch.autograd.set_detect_anomaly(True) attaches the forward stack trace to the error (pt9 shows the full workflow). The fix is almost always to revert to the out-of-place form; the memory saved by an in-place activation is one activation tensor, which activation checkpointing (pt7) handles more systematically.

Knobs and tools

  • t.stride(), t.is_contiguous(), t.storage_offset(), t.untyped_storage().nbytes() and t._base (the base tensor of a view, or None) — the five calls that answer "is this a view, and of what?".
  • t._version — the version counter, useful when bisecting an in-place error.
  • torch.set_default_dtype — changes the default float for all factory functions; almost never what you want globally, and libraries may assume float32.
  • torch.device("meta") and torch.empty(..., device="meta") — shape checks for huge models with no allocation.

The design decision behind all of this

The PyTorch paper (Paszke et al., NeurIPS 2019) is worth reading for the reasoning: PyTorch chose eager, imperative execution with mutable tensors because that is how Python programmers write code, and then made mutation safe with version counters, and memory predictable with reference counting and a caching allocator that reuses freed GPU blocks without calling the slow cudaFree. Every failure in this section is the cost side of those choices — views make reshaping free but let small tensors pin big storages; mutation is allowed but can be refused at backward time. Knowing the design tells you what kind of bug to look for.

Find the bug: the cache that never fills and the memory that never frees

This evaluation helper collects the final hidden state of each batch and normalises it in place. Users report two problems: memory grows by about 1.5 GB per batch until the process dies, and the "normalised" vectors in feats differ from what model.hidden holds afterwards, even though the code looks like it normalises both. Find the bugs.

feats = []
model.eval()
for x in loader:                       # x: (64, 512) token ids
    out = model(x)                     # out: (64, 512, 768) float32 hidden states
    last = out[:, -1]                  # (64, 768)
    sel = last[[0, 1, 2, 3]]           # first four rows, for a preview
    sel /= sel.norm(dim=-1, keepdim=True)
    feats.append(last)
    model.hidden = last
Answer

Bug 1 — the view pins the whole activation, with its graph. out[:, -1] is a basic slice, so last is a view of the full 64 × 512 × 768 float32 tensor: 64 × 512 × 768 × 4 bytes ≈ 100 MB. Worse, the loop runs with autograd on (eval() only changes dropout and normalisation behaviour; it does not stop graph recording — pt3 and pt4), so out carries a graph that keeps every saved activation of the forward pass alive: that is where the ~1.5 GB per batch comes from. Symptom: steady growth per batch. Fix: run under with torch.inference_mode(): and append last.clone() (or last.cpu()), so only 64 × 768 × 4 bytes ≈ 197 KB per batch is kept.

Bug 2 — advanced indexing copies, so the in-place normalisation hits a copy. last[[0, 1, 2, 3]] uses a list index, which is advanced indexing and always copies. sel /= … then normalises the copy; last, feats and model.hidden are untouched. Symptom: "normalised" features are not normalised. Fix: if the intent is to normalise the stored features, normalise last itself out of place (last = torch.nn.functional.normalize(last, dim=-1)) before appending; if the intent was only a preview, the line is dead code and should be removed.

Bug 3 (latent) — shared aliasing between the list and the model attribute. feats[-1] and model.hidden are the same tensor. Any later in-place change to model.hidden (for example a model.hidden.zero_() reset) rewrites the last saved feature. Fix: store a clone in one place. In an interview, say how you would confirm each: compare untyped_storage().nbytes() of feats[0] with its numel() * element_size(), and compare data_ptr() of sel and last.

Estimate: will the logits fit?

A model has a 128,256-token vocabulary. You run a batch of 8 sequences of 8,192 tokens and compute logits in float32 for the whole sequence. How much memory do the logits take, and what is the cheapest change that cuts it?

Answer

8 × 8,192 × 128,256 × 4 bytes ≈ 33.6 GB (31.3 GiB) — more than the whole activation budget of most single-GPU runs, and the softmax inside the loss can need another copy of the same size. The cheapest changes: compute the loss in chunks of the sequence so only one chunk's logits exist at once (cuts memory by the number of chunks); keep logits in bfloat16 and let the loss upcast internally (halves it); and at inference compute logits only for the last position (hidden[:, -1] before the output layer), which turns 8,192 positions into 1.
