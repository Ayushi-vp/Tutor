"Implement a small GPT in PyTorch" is one of the most common coding exercises in ML-engineer interviews, and its debugging twin — "here is someone's GPT, it trains but generation is broken" — is one of the most common ML-debugging prompts. You may already have built one in NumPy (mc18), where every matrix multiply and every backward pass was explicit. In PyTorch the arithmetic is easy; the difficulty moves into the places where PyTorch's conveniences have semantics you must know: the axis bookkeeping of splitting heads, what F.scaled_dot_product_attention does with masks and dropout, how the causal mask is aligned when queries and keys have different lengths, how weight tying and initialisation interact, and how a KV cache must handle position indices.

The bugs here are expensive because they are invisible during training. A causal-mask alignment mistake that only appears in the cached decode path produces a model whose training loss is perfect and whose generations are nonsense. Attention dropout left on at inference makes generation randomly worse. Position embeddings that restart at zero for each new token make the cache "work" while silently feeding the model the wrong positions. Each of these is a single line, and each is a classic planted bug.

This lesson builds a complete GPT-2-style model in about 100 lines — the same architecture as Karpathy's nanoGPT, which follows OpenAI's GPT-2 paper — and checks it the way a careful engineer would: the parameter count matches GPT-2 small's 124,439,808 exactly, the loss at initialisation is close to ln V, and generation with a KV cache produces exactly the same tokens as generation without it. Along the way it explains every design choice: why pre-norm, why the final layer norm, why the residual projections get a smaller initialisation, what SDPA dispatches to, and why the decode step must not use is_causal=True. All code was run on PyTorch 2.14.

A GPT is an assembly line that reads a sequence of tokens and, at every position, predicts the next token. Picture a long shared whiteboard — the residual stream — with one column per position, each column C numbers tall. The line works like this:

  1. Embedding. Each token id is looked up in a table to get a C-dimensional vector, and a second table adds a vector for its position. These sums are written on the whiteboard.
  2. Blocks. L identical stations each read the whiteboard and add something to it. Each station has two workers. The attention worker lets each column look at earlier columns (never later ones — that is the causal mask) and writes a summary of what it found. The MLP worker processes each column on its own and writes its result. Before reading, each worker normalises what it sees (pre-norm); what they write is added to the whiteboard unnormalised.
  3. Output. The final whiteboard is normalised once more and each column is compared against every token's embedding (the same table as step 1 — weight tying) to score how likely each token is to come next.

Training shows the model whole sequences and asks every position to predict the next token at once. Generation is different: it runs one step at a time, appending the chosen token and running again. Since columns never look forward, earlier columns' intermediate results never change when a token is appended — so a KV cache keeps each layer's keys and values for past positions and computes only the new column.

Training and generation use the same model very differently, and most of this lesson's bugs live in the difference. In training, a batch of B sequences of length T goes through once; every position computes its prediction in parallel, the causal mask stops positions from cheating, and the loss averages over all B × T predictions. The work is dominated by large matrix multiplications and is compute-bound — the GPU is busy multiplying. In generation, the prompt is processed once in parallel (the prefill), and then the model runs one position at a time (each a decode step), each step reading every weight and every cached key and value to produce a single token per sequence. Decode is memory-bound — the GPU mostly waits for memory — and it is the path that training never exercises. Code that is perfect for training can still be wrong in decode, so decode needs its own tests.

Where the whiteboard analogy breaks: the attention worker does not "look at" earlier columns directly; it computes from each column a query, a key and a value, and each column's summary is a weighted average of earlier columns' values, weighted by how well its query matches their keys. That is precisely why the cache stores keys and values — the quantities later queries need — and not the columns themselves.

If you remember one sentence: embeddings in, L pre-norm blocks each adding attention and MLP outputs to a residual stream, a final norm and a tied head out — and generation reuses each layer's cached keys and values so each new token costs one column of work.

1. Configuration and the model skeleton

GPT-2 small is fixed by five numbers: vocabulary V = 50,257, context length 1,024, width C = 768, H = 12 heads (head size 64), L = 12 layers. A dataclass keeps them together:

@dataclass
class Config:
    vocab: int = 50257
    ctx: int = 1024
    C: int = 768
    H: int = 12
    L: int = 12
    dropout: float = 0.0

The model has five parts, each registered properly (pt4): wte (token embedding, V × C), wpe (position embedding, ctx × C), blocks (an nn.ModuleList of L blocks), ln_f (final LayerNorm) and head (a bias-free nn.Linear(C, V) whose weight is tied to wte).

2. Attention with SDPA

class Attention(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.H, self.hs = cfg.H, cfg.C // cfg.H
        self.qkv = nn.Linear(cfg.C, 3 * cfg.C)        # one matmul for q, k, v
        self.proj = nn.Linear(cfg.C, cfg.C)           # writes into the residual stream
        self.p = cfg.dropout

    def forward(self, x, cache=None):                 # x: (B, T, C)
        B, T, C = x.shape
        q, k, v = self.qkv(x).split(C, dim=-1)         # 3 × (B, T, C), views
        q, k, v = (t.view(B, T, self.H, self.hs).transpose(1, 2)
                   for t in (q, k, v))                  # (B, H, T, hs)
        ...                                            # cache handling: section 6
        y = F.scaled_dot_product_attention(q, k, v, is_causal=True,
                                           dropout_p=self.p if self.training else 0.0)
        y = y.transpose(1, 2).contiguous().view(B, T, C)   # merge heads
        return self.proj(y)

Three details. First, the head split is view then transpose and the merge is transpose, contiguous, view — pt2 explains why each is a view or a copy, and why using view(B, H, T, hs) directly would mix heads with time. Second, F.scaled_dot_product_attention (SDPA) computes softmax(QKᵀ/√hs + mask)·V. Its documentation includes a reference implementation in plain PyTorch, and on CUDA it dispatches to a fused kernel when inputs allow — FlashAttention-2, a memory-efficient kernel, or cuDNN attention — falling back to the C++ "math" implementation otherwise; fused kernels never materialise the T × T score matrix, which is where pt7's activation savings come from. On CPU, as on this machine, the math path is used. Third, dropout: the docs warn that SDPA "always applies dropout according to the specified dropout_p argument" and show exactly the self.p if self.training else 0.0 idiom. A constant dropout_p=0.1 leaves attention dropout on at evaluation and generation — a planted-bug favourite.

3. The block: pre-norm residuals

class Block(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.ln1, self.ln2 = nn.LayerNorm(cfg.C), nn.LayerNorm(cfg.C)
        self.attn = Attention(cfg)
        self.mlp = nn.Sequential(nn.Linear(cfg.C, 4 * cfg.C), nn.GELU(),
                                 nn.Linear(4 * cfg.C, cfg.C))
        self.drop = nn.Dropout(cfg.dropout)

    def forward(self, x, cache=None):
        x = x + self.drop(self.attn(self.ln1(x), cache))   # normalise the input, add raw output
        return x + self.drop(self.mlp(self.ln2(x)))

This is pre-norm: LayerNorm is applied to each sublayer's input, and the sublayer's output is added to the unnormalised stream. The original transformer used post-norm — x = ln(x + attn(x)) — which normalises the stream itself after every addition. Post-norm places a normalisation on every path from input to output, so gradients to early layers pass through many of them; deep post-norm stacks are known to need careful learning-rate warmup to train at all. Pre-norm leaves an identity path through the whole network, which is why the GPT-2 paper moved layer normalisation "to the input of each sub-block" and added "an additional layer normalization ... after the final self-attention block" — the ln_f in our model. Without ln_f, the head would see a residual stream whose scale grows with depth.

4. Embeddings, head, tying and initialisation

class GPT(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.cfg = cfg
        self.wte, self.wpe = nn.Embedding(cfg.vocab, cfg.C), nn.Embedding(cfg.ctx, cfg.C)
        self.blocks = nn.ModuleList(Block(cfg) for _ in range(cfg.L))
        self.ln_f = nn.LayerNorm(cfg.C)
        self.head = nn.Linear(cfg.C, cfg.vocab, bias=False)
        self.head.weight = self.wte.weight              # weight tying
        self.apply(self._init)
        for n, p in self.named_parameters():            # residual projections
            if n.endswith("attn.proj.weight") or n.endswith("mlp.2.weight"):
                nn.init.normal_(p, 0.0, 0.02 / math.sqrt(2 * cfg.L))

    def _init(self, m):
        if isinstance(m, (nn.Linear, nn.Embedding)):
            nn.init.normal_(m.weight, 0.0, 0.02)
        if isinstance(m, nn.Linear) and m.bias is not None:
            nn.init.zeros_(m.bias)

Weight tying is one assignment (pt4): head.weight and wte.weight become the same Parameter. Initialisation follows GPT-2 and nanoGPT: N(0, 0.02) for every linear and embedding weight, zero biases, and N(0, 0.02/√(2L)) for the two projections that write into the residual stream in each block (attn.proj and the MLP's second linear, mlp.2). The GPT-2 paper describes it as scaling "the weights of residual layers at initialization by a factor of 1/√N where N is the number of residual layers"; with 2 residual additions per block, N = 2L. The reason (pt4): the stream is a sum of 2L contributions, and scaling each by 1/√(2L) keeps its variance from growing with depth. Note that the tied weight is initialised twice by apply (as an Embedding and as a Linear), harmlessly, with the same distribution.

5. The forward pass and the loss

    def forward(self, idx, targets=None, caches=None, start=0):
        B, T = idx.shape
        pos = torch.arange(start, start + T, device=idx.device)
        x = self.wte(idx) + self.wpe(pos)               # (B, T, C) + (T, C) broadcasts
        for i, blk in enumerate(self.blocks):
            x = blk(x, None if caches is None else caches[i])
        x = self.ln_f(x)
        if targets is None:
            return self.head(x[:, -1:]), None           # inference: last position only
        logits = self.head(x)                           # (B, T, V)
        loss = F.cross_entropy(logits.view(-1, logits.size(-1)), targets.view(-1))
        return logits, loss

Positions are created on the input's device (a bare torch.arange(T) breaks on GPU, pt4) and start at start, which matters for the cache. Training passes targets = the input shifted by one (pt9's bug 2) and gets the mean token-level cross-entropy over raw logits (pt9's bug 6). At inference the head is applied to the last position only, cutting the head's cost and the (B, T, V) allocation by a factor of T.

6. The KV cache, and the mask alignment trap

During generation, at step n the model needs logits for position n only. Keys and values of positions 0…n−1 were already computed in previous steps and have not changed (later tokens cannot affect earlier positions in a causal model). So each attention layer keeps them:

        if cache is not None:                         # inside Attention.forward
            if "k" in cache:
                k = torch.cat([cache["k"], k], dim=2)   # (B, H, N, hs): past + new
                v = torch.cat([cache["v"], v], dim=2)
            cache["k"], cache["v"] = k, v
        Tk = k.shape[2]
        if T == Tk:                                   # training or prefill: square
            y = F.scaled_dot_product_attention(q, k, v, is_causal=True,
                                               dropout_p=self.p if self.training else 0.0)
        elif T == 1:                                  # decode: one query sees every key
            y = F.scaled_dot_product_attention(q, k, v)
        else:                                         # a chunk of T new queries after a cache
            mask = torch.ones(T, Tk, dtype=torch.bool, device=x.device).tril(diagonal=Tk - T)
            y = F.scaled_dot_product_attention(q, k, v, attn_mask=mask)

Why three cases? SDPA's is_causal=True builds a causal mask aligned to the upper-left corner of the score matrix: query i may see keys 0…i. When queries and keys have the same length that is exactly right. At a decode step, there is one query and N keys; upper-left alignment lets that single query see only key 0. Checked on 2.14: with one query and five keys, is_causal=True gives attention weights [1, 0, 0, 0, 0]. The correct behaviour — the newest token sees everything cached plus itself — is "no mask". For a chunk of T new tokens after N − T cached ones (chunked prefill, speculative decoding), query i (absolute position N − T + i) must see keys 0…N − T + i: a lower-right aligned mask, which is tril(diagonal=N − T), or the causal_lower_right(T, N) helper from torch.nn.attention.bias. The SDPA docs describe the upper-left convention; the bias module documents both.

The generation loop:

    @torch.inference_mode()
    def generate(self, idx, n_new, temperature=1.0):
        caches = [dict() for _ in self.blocks]
        logits, _ = self(idx, caches=caches)               # prefill the prompt
        for _ in range(n_new):
            probs = F.softmax(logits[:, -1] / temperature, dim=-1)
            nxt = torch.multinomial(probs, 1)              # or argmax for greedy
            idx = torch.cat([idx, nxt], dim=1)
            logits, _ = self(nxt, caches=caches, start=idx.shape[1] - 1)
        return idx

Two lines carry the correctness: start=idx.shape[1] - 1 gives the new token its true position (restarting at 0 is a classic bug that the cache hides: generation "works" but every new token believes it is at position 0), and the model is run on nxt alone, not on the whole sequence. The test of the implementation is decisive: greedy generation with and without the cache must produce identical tokens. On 2.14, with a small configuration of this exact code (V = 100, C = 64, 2 layers), cached and uncached greedy generation of 10 tokens are identical, and the chunk path's logits match the full forward pass to 1e-5.

7. Checking the implementation: parameter count, loss at init, cache equality

Build the model on the meta device and count:

with torch.device("meta"):
    g = GPT(Config())
sum(p.numel() for p in g.parameters())    # 124439808 on 2.14

That is exactly GPT-2 small (pt4 derives it: 7,087,872 per block × 12, plus 38,597,376 token and 786,432 position embedding parameters, plus 1,536 for ln_f, with the head tied). A different number points at a missing bias, an untied head (+38.6M), or a wrong MLP width. The meta device makes the check instant and allocation-free, and nn.init functions are no-ops on meta tensors, so the constructor runs unchanged.

Next, the loss at initialisation: for random tokens the loss should be close to ln V. With the small test configuration (V = 100) the measured initial loss was 4.53 against ln 100 = 4.61 — close, as expected from small N(0, 0.02) logits. For GPT-2 small the target is ln 50,257 ≈ 10.82. Then the dependency test from pt9 for causality, the cache-equality test from section 6, and overfitting one batch. These five checks take seconds and catch nearly every bug in this lesson's catalogue.

8. Memory and compute of the cache

The cache stores, per token, a key and a value per layer per KV head: 2 × L × Hkv × hs × bytes. For GPT-2 small in fp16: 2 × 12 × 12 × 64 × 2 = 36,864 bytes per token; a batch of 32 sequences of 1,024 tokens needs 32 × 1,024 × 36,864 ≈ 1.2 GB. For a 32-layer model with 32 heads of size 128 it is 524,288 bytes — half a megabyte — per token; grouped-query attention with 8 KV heads cuts that to 128 KB (lm5). Passing enable_gqa=True lets SDPA consume k and v with fewer heads than q directly (pt2 explains why repeat_interleave, not repeat, is the right expansion if you do it by hand).

Compute: without a cache, generating token n re-runs the whole prefix — O(n) work per layer for the MLP and O(n²) for attention, so a 1,000-token generation does on the order of 500,000 token-positions of MLP work. With the cache, each step processes one position: O(1) MLP work and O(n) attention reads. The decode step then becomes memory-bound: it reads every weight and the whole cache to produce one token per sequence, which is why serving batches many sequences together (gpu10, lm13, pt13).

The implementation above grows the cache with torch.cat, which allocates a new tensor every step — fine for clarity, wasteful at scale. Production code preallocates a (B, H, ctx, hs) buffer per layer and writes into it with index assignment, which also gives static shapes for torch.compile and CUDA graphs (pt12), and serving engines manage the cache in fixed-size pages so that sequences of different lengths share memory without fragmentation.

9. Training it: a minimal loop

The model plugs into the loop of pt6 with two GPT-specific details. Batches are random windows of a token array with targets shifted by one (pt5, pt9). And the optimiser uses two parameter groups, as nanoGPT's configure_optimizers does: weight decay on matrices (every parameter with two or more dimensions — linear weights and the tied embedding) and none on biases and LayerNorm weights.

decay = [p for p in model.parameters() if p.dim() >= 2]
no_decay = [p for p in model.parameters() if p.dim() < 2]
opt = torch.optim.AdamW([{"params": decay, "weight_decay": 0.1},
                         {"params": no_decay, "weight_decay": 0.0}],
                        lr=6e-4, betas=(0.9, 0.95))
for step in range(max_steps):
    x, y = get_batch("train")                          # (B, T) and (B, T) shifted by one
    with torch.autocast("cuda", dtype=torch.bfloat16):
        _, loss = model(x, targets=y)
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step(); sched.step(); opt.zero_grad(set_to_none=True)

Because model.parameters() de-duplicates the tied weight, it appears once, in the decay group. With AdamW betas (0.9, 0.95), a learning rate around 6e-4 for a model this size, warmup and cosine decay (pt6), and bf16 autocast (pt7), this is essentially the configuration nanoGPT uses to reproduce GPT-2 small.

10. Batched generation with prompts of different lengths

Serving many prompts at once means prompts of different lengths in one batch. Two conventions exist. With left padding, shorter prompts are padded at the start so every prompt's last real token sits at the same column, and generation appends new tokens in the same column for all sequences; the attention mask must then also exclude the padding keys (a key-padding mask combined with the causal mask), and position indices must count only real tokens, or each padded sequence's positions are shifted by its padding length. With right padding, the last real token is at a different column per sequence, so the logits must be gathered at each sequence's own last position — and appending new tokens after padding breaks the sequence. Decoder-only generation therefore uses left padding (pad_sequence(..., padding_side="left"), pt5) with explicit masks and per-sequence positions, while serving engines avoid padding altogether by packing variable-length sequences and tracking each one's cache separately.

11. Precision inside the GPT

Under bf16 autocast (pt7) most of this model runs in bf16: the QKV and output projections, the MLP and the head are matmuls on the autocast list, and SDPA's fused kernels take bf16 inputs while accumulating in float32 internally. Three places deserve float32. The LayerNorms: on CUDA autocast runs layer_norm in float32 automatically, but a hand-written RMSNorm must upcast itself (pt4). The loss: F.cross_entropy runs in float32 under CUDA autocast, which matters because a log-softmax over 50,257 classes in bf16 loses the small probabilities that dominate the loss on hard tokens; if you compute log-probabilities yourself for evaluation, call .float() first. And sampling: softmax over bf16 logits divided by a small temperature can underflow most probabilities to zero, so production samplers upcast the last position's logits before temperature, top-k and top-p. The KV cache itself can stay in bf16 (or lower, with cache quantisation), since every read is followed by float32 accumulation inside the attention kernel.

What SDPA dispatches to, and why it sometimes does not

On CUDA, SDPA chooses among FlashAttention-2, a memory-efficient attention kernel, cuDNN attention and the math fallback, based on dtype (fused kernels require fp16 or bf16), head size, mask type, dropout and hardware. An arbitrary dense boolean or float mask rules out the FlashAttention kernel, because its tiling assumes either no mask or a causal one; the memory-efficient kernel accepts additive masks. So the explicit chunk mask in section 6 may fall back to a slower kernel, while is_causal=True and "no mask" both keep the fast paths — another reason serving code prefers structured masks (the bias module's causal_lower_right is recognised as causal) over materialised ones. To insist on a backend while debugging, wrap the call in torch.nn.attention.sdpa_kernel([SDPBackend.FLASH_ATTENTION]); if it cannot run, PyTorch reports why. Different kernels round differently, so small numerical differences between CPU and GPU runs, or between backends, are expected; the docs say so explicitly.

Fusing QKV and why the split is a view

One nn.Linear(C, 3C) instead of three nn.Linear(C, C) does the same arithmetic as one larger matmul, which uses the GPU better than three small launches. split(C, dim=-1) returns three views of its output, so the split itself costs nothing; the subsequent view and transpose produce non-contiguous q, k, v that SDPA accepts directly. When converting published checkpoints, the fused weight is where errors hide: GPT-2's original weights store c_attn as a Conv1D with shape (C, 3C), transposed relative to nn.Linear, and some other models store Q, K and V interleaved per head rather than concatenated — a mapping error produces a model that loads, runs and generates nonsense.

Weight tying and the gradient on the embedding

With tying, the shared matrix receives two gradients: a dense one from the head (every vocabulary row gets a gradient at every position, through the softmax) and a sparse one from the embedding lookup (only rows of tokens present in the batch). Autograd sums them (pt3). The head's gradient dominates, so rare tokens' embeddings are shaped mainly by their role as output classes. Practical consequences: the embedding's effective learning dynamics differ from an untied model's, weight decay applies to a matrix that is both an input table and an output layer (nanoGPT's optimiser groups decay all 2-D parameters, including this one), and tools that shard or quantise the model must keep the two uses on the same tensor.

Learned positions versus RoPE

GPT-2's learned position table has exactly ctx rows, so the model cannot process position 1,024 at all: generation must stop or slide a window and recompute. Most current models use rotary position embeddings (lm4, mc17), which rotate each head's queries and keys by position-dependent angles inside attention, so scores depend on relative position. In code, RoPE removes wpe, registers cos/sin tables as non-persistent buffers (pt4), and rotates q and k after the head split — in float32, cast back afterwards. With a cache, keys are stored already rotated, and each new query is rotated with its absolute position start + t; getting start wrong is the RoPE version of the restarting-positions bug.

A static cache for torch.compile and CUDA graphs

The torch.cat cache changes shape every step, so a compiled model would recompile (or fall back to dynamic shapes) and a CUDA graph (pt12) could not be captured at all. A static cache preallocates k_cache and v_cache of shape (B, H, ctx, hs) per layer, writes the new position with k_cache[:, :, pos] = k, and attends over the full buffer with a mask that hides positions not yet written. Every decode step then has identical shapes and can be captured once and replayed, removing Python and kernel-launch overhead that dominates small-batch decode. The cost is memory for the full context from the start and attention over masked, unused positions — which kernels designed for this case skip.

Grouped-query attention in the module

To turn this attention into grouped-query attention (lm5), the QKV projection produces H query heads but only Hkv key and value heads: nn.Linear(C, (H + 2·H_kv) · hs), split into sizes H·hs, Hkv·hs, Hkv·hs. The cache stores only the Hkv heads — that is the whole point, a factor of H/Hkv less memory — and SDPA with enable_gqa=True matches each group of H/Hkv consecutive query heads with one KV head. If the backend does not support it, expand with repeat_interleave on the head axis, never repeat, which pairs queries with the wrong keys (pt2). Parameter count and attention cost both drop slightly; quality is close to full multi-head attention at the head ratios used in practice.

Sampling details that change outputs

The generation loop's sampling line hides several decisions (lm8, mc20). Temperature divides logits before softmax; temperature 0 must be special-cased as argmax, since dividing by zero gives inf. Top-k and top-p truncate the distribution by setting logits outside the kept set to −∞ before softmax. Sampling uses torch.multinomial on probabilities, which needs a generator for reproducibility. And numerics: computing softmax over 50k logits in bf16 is fine for sampling but not for computing exact log-probabilities for evaluation, which should upcast to float32 (pt7).

Why the scores are divided by √hs

If the components of q and k are roughly independent with unit variance, their dot product over hs dimensions has variance hs, so with hs = 64 the raw scores have a standard deviation around 8. Softmax over scores that large is nearly one-hot, and its gradient is nearly zero for all but one key, which slows learning and makes training brittle. Dividing by √hs brings the standard deviation back to about 1. SDPA applies this scale by default (scale=None means 1/√E); passing scores that you have already scaled, or adding your own division before calling SDPA, scales twice — a subtle planted bug whose symptom is attention that stays nearly uniform and a model that learns more slowly than it should.

Failure mode: training is fine, generation is garbage

The signature of decode-path bugs: validation loss is normal, but sampled text is repetitive or incoherent. Causes, in order: is_causal=True in the decode step (the new token sees only the first key); positions restarting at 0 for each new token; the cache concatenated along the wrong axis (dim 1 is heads, dim 2 is time); attention dropout active at inference; logits taken from the wrong position (index 0 instead of −1, or the head applied before ln_f). The cached-versus-uncached greedy comparison localises every one of these in seconds.

Failure mode: a model that trains suspiciously well

Training loss far below the expected curve points to a causal leak: a mask applied wrongly, softmax over the wrong dimension, or targets not shifted (pt9). For a GPT the dependency test is cheap: backpropagate from position t and assert the input gradient is zero for later positions.

Failure mode: slow attention

Symptom: attention dominates the profile and memory grows quadratically with sequence length. Causes: hand-written attention instead of SDPA; SDPA falling back to the math kernel because inputs are float32, the mask is a dense arbitrary tensor, or the head size is unsupported; a cache grown with torch.cat every step. Check which backend runs (the profiler shows kernel names such as flash or efficient attention, pt12), cast to bf16 under autocast, use structured causal masks, and preallocate the cache.

Failure mode: a checkpoint that loads but generates nonsense

When loading published weights into your implementation, every mapping step is a chance for a silent error: transposed Conv1D weights, fused QKV in a different order, a missing tie, layer norm epsilon (GPT-2 uses 1e-5, the PyTorch default), GELU variant (GPT-2 uses the tanh approximation; nn.GELU() defaults to the exact form, a small difference), or a vocabulary padded to a multiple of 64 (nanoGPT pads 50,257 to 50,304 for efficiency). Compare logits on a fixed input against a reference implementation before trusting any downstream number.

Evaluating the model: perplexity done right

Language models are compared by validation loss or its exponential, perplexity. Two details make the number trustworthy. First, compute it over tokens, with sums and counts (pt6), in eval mode, on a fixed validation set split by position from the training data (pt9). Second, mind the context: evaluating a long document in non-overlapping windows of 1,024 tokens gives the first tokens of each window almost no context, inflating the loss; a sliding window with stride smaller than the context (evaluating only the last part of each window) gives each token more context and a lower, more representative number. Report which method you used, because the difference can be larger than the gap between two models you are comparing.

The reference to check against

nanoGPT's model.py is the public implementation this lesson mirrors: its attention uses SDPA when available with a masked fallback, its blocks are pre-norm, it ties wte and lm_head, applies the GPT-2 initialisation with the 1/√(2·n_layer) residual scaling, crops the context in generate, and loads OpenAI's GPT-2 weights with the Conv1D transposes. Reading it after writing your own version is the fastest way to find the differences that matter.

Measuring training throughput: tokens per second and MFU

Once the model is correct, its training speed is reported in tokens per second and in model FLOPs utilisation (MFU): the fraction of the GPU's peak arithmetic the training actually achieves. A standard approximation counts about 6N floating-point operations per token for a forward and backward pass of an N-parameter model (2N forward, 4N backward), plus an attention term that grows with sequence length (gpu3). For GPT-2 small, 6 × 124M ≈ 0.75 GFLOP per token; at 200,000 tokens per second that is 1.5 × 1014 FLOP/s, which on a GPU with a bf16 dense peak of about 1015 FLOP/s is an MFU near 15%. Small models rarely exceed 30–40% because kernel launches, memory-bound operations and the optimiser step take a larger share; nanoGPT prints an MFU estimate during training for exactly this comparison. MFU is the number to watch when you apply pt12's speed-ups.

Find the bug: a GPT whose generations degrade after the first token

A team's GPT reaches the expected validation loss, but sampled text is fluent for the first token after the prompt and then degrades into repetition. Their attention and generation code is below. Find the bugs.

def forward(self, x, cache=None):                          # Attention
    B, T, C = x.shape
    q, k, v = self.qkv(x).split(C, dim=-1)
    q, k, v = (t.view(B, self.H, T, self.hs) for t in (q, k, v))
    if cache is not None and "k" in cache:
        k = torch.cat([cache["k"], k], dim=1); v = torch.cat([cache["v"], v], dim=1)
    if cache is not None:
        cache["k"], cache["v"] = k, v
    y = F.scaled_dot_product_attention(q, k, v, is_causal=True, dropout_p=0.1)
    return self.proj(y.view(B, T, C))

@torch.no_grad()
def generate(self, idx, n):
    caches = [dict() for _ in self.blocks]
    logits, _ = self(idx, caches=caches)
    for _ in range(n):
        nxt = torch.multinomial(F.softmax(logits[:, -1], -1), 1)
        idx = torch.cat([idx, nxt], 1)
        logits, _ = self(nxt, caches=caches)                # start defaults to 0
Answer

Bug 1 — heads split with view alone. t.view(B, self.H, T, self.hs) reinterprets the (B, T, C) memory as (B, H, T, hs) without moving the head axis, so each "head" contains a mixture of time steps and channels (pt2). The merge y.view(B, T, C) has the same problem. Training still learns something (the model adapts to the scrambled layout during training), which is why validation loss looks normal. Fix: view(B, T, H, hs).transpose(1, 2) and y.transpose(1, 2).contiguous().view(B, T, C).

Bug 2 — cache concatenated on the wrong axis. With (B, H, T, hs) tensors, time is dim 2; dim=1 concatenates along heads, so the cached keys become extra heads. After fixing bug 1 this raises a shape error in SDPA or silently mismatches heads. Fix: dim=2.

Bug 3 — is_causal=True in the decode step. At each generation step there is one query and N keys; upper-left alignment lets it attend only to key 0 — the first prompt token. The first generated token comes from the prefill (square, correct), which is why the first token is fine and later ones degrade. Fix: no mask when T == 1, lower-right mask for chunks.

Bug 4 — positions restart at 0. start is not passed, so every generated token gets position embedding 0. Fix: start=idx.shape[1] - 1.

Bug 5 — attention dropout at inference. dropout_p=0.1 is constant, so generation randomly drops attention weights. Fix: dropout_p=self.p if self.training else 0.0 (and generate should also ensure eval mode). Verification after fixing: greedy generation with and without the cache is identical, and the dependency test passes.

Estimate: how many concurrent users fit?

You serve a 32-layer model with 8 KV heads of size 128 in bf16 on an 80 GB GPU; weights take 16 GB. Each request uses up to 8,192 tokens. Ignoring activations and fragmentation, how many requests fit at full length?

Answer

KV bytes per token = 2 × 32 × 8 × 128 × 2 = 131,072 (128 KB). Per request at 8,192 tokens: 8,192 × 128 KB = 1 GiB (1.07 GB). Free memory ≈ 80 − 16 = 64 GB, minus some headroom: about 55–60 concurrent full-length requests. Without GQA (32 KV heads) the cache would be 4 GiB per request — only about 15 requests — which is why GQA matters so much for serving. Paged caches let shorter requests use proportionally less, raising the real concurrency.
