Single-GPU training is a loop; multi-GPU training is a distributed system that happens to contain a loop. The step from one to eight GPUs is usually three lines — launch with torchrun, call init_process_group, wrap the model in DistributedDataParallel — and it works, which is exactly why many engineers never learn what those lines do. Then the problems arrive. Eight GPUs train only five times faster than one. A model with a conditional branch hangs forever at the first step. Gradient accumulation makes the job slower per sample than without it. A 7B model will not fit even though "the memory is split across eight GPUs" (with DDP, it is not). A 256-GPU job sits idle for six hours because one rank crashed and the others are waiting politely for it inside a collective.

The ideas behind data-parallel training — averaging gradients, sharding states — are covered in dl9, gpu8 and gpu9. This lesson is the API side: what each PyTorch call does on the wire, in what order, and how much it costs. The two canonical sources are the papers the PyTorch team wrote about its own systems: "PyTorch Distributed: Experiences on Accelerating Data Parallel Training" (Li et al., VLDB 2020), which explains DDP's gradient buckets, the overlap of communication with backward, and the no_sync and find_unused_parameters options, and reports near-linear scaling on 256 GPUs when configured well; and "PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel" (Zhao et al., VLDB 2023), which does the same for sharding. The current API for sharding, fully_shard (FSDP2), is a redesign built on DTensor; this lesson uses its 2.14 documentation.

Interviewers ask about distributed training at every senior ML level: "what does DDP do during backward?", "why does this job hang?", "how would you train a 13B model on 16 GPUs?", "where does the time go at 64 GPUs?". Answering well means being able to draw the timeline — which collective runs when, how big it is, and what it overlaps with. By the end of this lesson you will be able to: launch and initialise a job correctly, explain DDP's buckets and hooks with numbers, use no_sync and DistributedSampler correctly, apply fully_shard to a transformer and say what it does in forward and backward, estimate communication and memory for both, and debug the hangs and slowdowns that distributed jobs are known for.

Picture a team of eight chefs, each with an identical kitchen and an identical copy of a recipe book (the model). Every round, each chef cooks a different batch of dishes (a different slice of the data), tastes the results and writes notes on how to adjust every recipe (the gradients). Before anyone edits their book, the chefs compare notes and agree on the average adjustment (an all-reduce). Then each edits their own book in exactly the same way, so the eight books stay identical. That is data parallelism, and DistributedDataParallel (DDP) is PyTorch's implementation of it.

Two refinements make it fast. The chefs do not wait until all notes are written before comparing: as soon as a page of notes is finished — the last recipes in the book are reviewed first — they compare that page while still writing the next. That is DDP's bucketing and overlap. And when the recipe book becomes too big for any one kitchen shelf, each chef keeps only one eighth of the book and borrows the pages they need from colleagues just before cooking each recipe, returning them afterwards. That is fully sharded data parallelism (FSDP): less memory per kitchen, more passing of pages.

All of this needs a way to start the chefs and connect them, and a vocabulary for the comparisons:

  • torchrun starts one process per GPU and tells each its rank (its number), its local rank (its GPU on that machine) and the world size (how many there are).
  • init_process_group connects them into a process group using a backend — NCCL for GPUs.
  • Collectives are operations that every rank calls together: all-reduce (everyone ends with the sum), all-gather (everyone ends with all the pieces), reduce-scatter (everyone ends with the sum of one piece), broadcast (everyone ends with rank 0's copy).

For any distributed setup, three questions describe it completely, and they are a good way to structure an interview answer. What does each GPU hold? Under DDP, a full copy of weights, gradients and optimiser state; under FSDP, a 1/n slice of each, plus whatever is temporarily gathered. What is communicated, and how big is it? Under DDP, one all-reduce of all gradients per optimiser step; under FSDP, all-gathers of parameters and reduce-scatters of gradients, about one and a half times as much. When does the communication happen, and what does it overlap with? Under DDP, during backward, bucket by bucket; under FSDP, layer by layer in both forward and backward, prefetched one layer ahead. With those three answers you can estimate memory, step time and scaling for any model and cluster before running anything.

Where the kitchen analogy breaks: real chefs who disagree can talk it over; ranks cannot. If one rank skips a comparison — takes a different branch, runs out of data, crashes — the others wait for it forever, because a collective only completes when every member has joined. Most distributed bugs are a rank doing something different from its peers.

If you remember one sentence: every rank runs the same program on different data; DDP keeps identical replicas by all-reducing gradients in buckets during backward, FSDP shards everything and gathers each layer just in time, and every collective must be called by every rank in the same order.

1. Launching: torchrun and the environment

A distributed PyTorch job is N copies of the same script, usually one per GPU. torchrun starts them:

torchrun --nproc_per_node=8 train.py --config cfg.yaml                      # one node
torchrun --nnodes=4 --nproc_per_node=8 --rdzv_backend=c10d \
         --rdzv_endpoint=node0:29500 train.py                              # four nodes

For each process it sets environment variables: RANK (0…31 across all nodes), LOCAL_RANK (0…7 on each node), WORLD_SIZE (32), and the rendezvous address (MASTER_ADDR, MASTER_PORT). It also supervises the workers: if one fails, torchrun can stop the others and restart the group (elastic launch), which together with checkpoints (pt8) turns a crash into a restart instead of a hang.

The script's side:

import os, torch, torch.distributed as dist
dist.init_process_group(backend="nccl", timeout=datetime.timedelta(minutes=30))
rank, world = dist.get_rank(), dist.get_world_size()
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)                  # before any CUDA allocation
device = torch.device("cuda", local_rank)
...
dist.destroy_process_group()

init_process_group reads the environment, connects all ranks and creates the default process group. The backend is NCCL for GPU tensors (Gloo for CPU tensors, as in tests on a laptop). Setting the device by local rank is essential: forgetting it puts all eight processes' tensors on GPU 0, which runs out of memory or, worse, works slowly. The timeout turns a hang in a collective into an error after the given time.

2. Collectives: the rules

The collectives in torch.distributed operate on tensors in place or into output tensors: all_reduce(t) replaces t on every rank with the sum over ranks (or average with ReduceOp.AVG); all_gather_into_tensor(out, t) concatenates every rank's t into out; reduce_scatter_tensor(out, t) sums the inputs and gives each rank one slice; broadcast(t, src=0) copies rank 0's t to everyone. Two rules govern them:

  1. Every rank in the group must call the same collectives in the same order with compatible shapes. Collectives are matched by order, not by name. If rank 3 calls an all_reduce that the others skip, rank 3 waits forever, and the next collective the others call pairs with the wrong one.
  2. Collectives are asynchronous with respect to the CPU on GPU. They are queued on CUDA streams like kernels; a later use of the result waits for them automatically, and async_op=True returns a handle you can wait on to overlap other work.

A metric reduction for logging is the standard example: loss_t = loss.detach().clone(); dist.all_reduce(loss_t, op=dist.ReduceOp.AVG) — called on every rank, then printed only on rank 0. Putting the all_reduce inside if rank == 0: hangs the job.

Costs, per GPU, for a ring algorithm over n ranks and a tensor of S bytes (gpu8): reduce-scatter and all-gather each move about (n−1)/n × S in and out; all-reduce about 2(n−1)/n × S. Within a node, NVLink provides hundreds of GB/s per GPU; across nodes, InfiniBand or Ethernet provides tens of GB/s per GPU — which is why cross-node communication usually dominates.

3. DistributedDataParallel: construction

model = GPT(cfg).to(device)
model = torch.nn.parallel.DistributedDataParallel(model, device_ids=[local_rank])

At construction, DDP (following Algorithm 1 in the DDP paper) does three things. It broadcasts rank 0's parameters and buffers to every rank, so all replicas start bit-identical regardless of how each rank initialised them. It assigns parameters to buckets: on 2.14 the default bucket capacity is 25 MB (bucket_cap_mb=None resolves to 25), with a smaller first bucket of 1 MB, and parameters are assigned in roughly the reverse order of model.parameters(), because backward produces the last layers' gradients first. And it registers an autograd hook on every parameter that fires when that parameter's gradient is ready.

The wrapper stores your model as model.module; save model.module.state_dict() to avoid the module. prefix in checkpoints (pt4).

4. DDP during forward and backward

On each forward, DDP by default broadcasts buffers (such as BatchNorm running statistics) from rank 0 so all replicas agree. On 2.14 the flag controlling this is forward_sync_buffers (default None, meaning True); it replaced broadcast_buffers, deprecated in 2.13. Models without buffers that change (most transformers) pay nothing.

During backward, each parameter's hook copies its gradient into its slot in the bucket. When every gradient in a bucket has arrived, DDP launches an asynchronous all-reduce of the whole bucket on a separate communication stream, then continues; backward keeps computing earlier layers' gradients in parallel. When backward finishes, DDP waits for the remaining all-reduces, divides by world size, and writes the averaged values back to each parameter's .grad (or, with gradient_as_bucket_view=True, the .grad tensors are already views into the buckets, saving a copy and memory). The optimiser step then runs locally and identically on every rank.

Why buckets? An all-reduce has a fixed overhead per call — launching, synchronising, latency — so 300 separate all-reduces of small gradient tensors are slow. One giant all-reduce of all gradients after backward has no overhead problem but cannot overlap with anything. Buckets of tens of megabytes balance the two. The DDP paper's measurements put a number on it: bucket size alone changed iteration time by more than 2× in their experiments, and with good settings DDP reached near-linear scaling on 256 GPUs.

A worked example for a 1.3B-parameter model in bf16 autocast with float32 gradients: 5.2 GB of gradients, about 208 buckets of 25 MB. On 8 GPUs in one node, an all-reduce moves 2 × 7/8 × 5.2 ≈ 9.1 GB per GPU; at an effective 300 GB/s that is about 30 ms. If backward takes 200 ms, all but the last bucket's all-reduce (25 MB, well under 1 ms) can hide behind it, and DDP's overhead is nearly zero. Across 4 nodes connected at an effective 40 GB/s per GPU, the same all-reduce takes over 200 ms and can no longer hide — the regime where gradient compression, larger batches per step, or sharded strategies with hierarchical communication become worthwhile.

5. Unused parameters, static graphs and no_sync

DDP's bucket logic assumes every parameter receives a gradient every iteration. If some do not — a mixture-of-experts expert that received no tokens, a branch taken only on some inputs, an auxiliary head used every other step — their buckets never fill, and backward ends waiting for gradients that never come; DDP reports an error about parameters that did not receive gradients (or hangs, depending on timing). find_unused_parameters=True fixes it by traversing the autograd graph after each forward to find parameters that will not be reached and marking them ready. The cost is that traversal on every iteration; the DDP paper describes it and recommends it only when needed. If the set of used parameters is the same every iteration, static_graph=True lets DDP record it once.

Gradient accumulation (pt6) needs no_sync(), the DDP paper's "skipping synchronization" optimisation:

for i, (x, y) in enumerate(loader):
    last = (i + 1) % k == 0
    ctx = contextlib.nullcontext() if last else model.no_sync()
    with ctx:
        loss = loss_fn(model(x), y) / k
        loss.backward()                      # no all-reduce unless last
    if last:
        opt.step(); opt.zero_grad()

Inside no_sync(), the hooks accumulate gradients locally without communicating; the backward of the last micro-batch all-reduces the accumulated sums once. Without it, accumulation over k micro-batches communicates k times as much — the reason "accumulation made DDP slower".

6. Data: DistributedSampler and per-rank randomness

Each rank must see different data. DistributedSampler(dataset, num_replicas=world, rank=rank, shuffle=True, seed=0) gives each rank every world-th index of a permutation seeded by seed + epoch, which is why sampler.set_epoch(epoch) is required each epoch (pt5) and why the sampler pads to an even split. With an IterableDataset, shard by rank and worker yourself. Randomness has two kinds: parameter initialisation must be the same everywhere (DDP's initial broadcast guarantees this even if seeds differ, but FSDP and manual setups rely on it), while dropout masks and augmentations should differ by rank — seed those with base_seed + rank. The effective batch per optimiser step is per-rank batch × world size × accumulation.

7. FSDP2: fully_shard

DDP replicates everything: weights, gradients and optimiser state, 16 bytes per parameter in float32 with AdamW (pt7), on every GPU. A 7B model needs 112 GB per GPU before activations. Fully sharded data parallelism shards all three across the ranks. In PyTorch 2.14 the API is torch.distributed.fsdp.fully_shard (FSDP2):

from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy
mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
model = GPT(cfg)                                   # often built on the meta device
for block in model.blocks:
    fully_shard(block, mp_policy=mp)               # one communication group per block
fully_shard(model, mp_policy=mp)                   # root: embeddings, ln_f, tied head
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)   # built AFTER sharding

What happens, per the 2.14 docstring. At initialisation, each wrapped module's parameters become DTensors sharded on dimension 0 across the mesh: each rank stores 1/n of every parameter, and the optimiser, built over these sharded parameters, keeps state only for the local shard. Before a module's forward, a forward pre-hook all-gathers its parameters into full tensors (cast to param_dtype); after forward, a forward hook frees them if reshard_after_forward is True — the default (None) means True for non-root modules and False for the root, because the root is needed again immediately when backward starts. In backward, hooks all-gather again (if resharded), compute gradients, free the full parameters, and reduce-scatter the gradients so each rank receives the summed gradient for its own shard (in reduce_dtype). The optimiser step then updates only local shards; no further communication is needed.

Two rules from the docstring matter in practice. Call fully_shard bottom-up: each call groups the parameters of that module not already grouped by an earlier call on a submodule, and "users generally should not call fully_shard only on the topmost root module", because the whole model would then be one group — gathered all at once, with no memory saving at peak and no overlap. And prefetching: while block i computes, FSDP can issue the all-gather for block i+1 (configurable with set_modules_to_forward_prefetch and its backward counterpart), so communication overlaps compute just as DDP's buckets do.

Gradient accumulation under FSDP2 uses model.set_requires_gradient_sync(False) for all but the last micro-batch, the counterpart of no_sync; the trade-off is that unsharded gradients are then kept between micro-batches, costing memory.

8. DDP or FSDP: the numbers

For a 7B-parameter model on 8 GPUs of 80 GB each, with AdamW and float32 master state:

DDPFSDP2 (full sharding)
Training state per GPU16 × 7B = 112 GB (does not fit)112 / 8 = 14 GB
Extra transient memorygradient bucketsone gathered block in bf16 (≈ 0.4 GB for a 4,096-wide block) plus prefetch
Communication per stepall-reduce of gradients ≈ 2 × 7/8 × size2 all-gathers of params + 1 reduce-scatter of grads ≈ 3 × 7/8 × size
When it winsmodels whose state fits on one GPUmodels that do not fit, or to free memory for larger batches

With bf16 parameters and gradients on the wire (param_dtype=bfloat16; a float32 reduce_dtype is safer numerically but doubles the reduce-scatter's size), each all-gather of 7B parameters moves about 12 GB per GPU — around 40 ms on NVLink at an effective 300 GB/s, small next to a multi-second step for a large batch. The FSDP paper reports FSDP matching DDP on models that fit in DDP and scaling near-linearly in TFLOPS up to 512 A100 GPUs for larger models. Across many nodes, HSDP — shard within a node, replicate across nodes, using a two-dimensional device mesh — keeps the frequent all-gathers on NVLink and sends only a gradient all-reduce across the network.

9. Putting it together: a minimal DDP training script

def main():
    dist.init_process_group("nccl")
    local_rank = int(os.environ["LOCAL_RANK"]); torch.cuda.set_device(local_rank)
    rank, world = dist.get_rank(), dist.get_world_size()
    torch.manual_seed(0)                                   # same init everywhere
    model = DDP(GPT(cfg).cuda(), device_ids=[local_rank])
    opt = torch.optim.AdamW(model.parameters(), lr=3e-4)
    sampler = DistributedSampler(ds, num_replicas=world, rank=rank, shuffle=True)
    loader = DataLoader(ds, batch_size=16, sampler=sampler, num_workers=4, pin_memory=True)
    for epoch in range(epochs):
        sampler.set_epoch(epoch)
        for x, y in loader:
            x, y = x.cuda(non_blocking=True), y.cuda(non_blocking=True)
            with torch.autocast("cuda", dtype=torch.bfloat16):
                _, loss = model(x, y)
            loss.backward()                                # all-reduces overlap here
            opt.step(); opt.zero_grad(set_to_none=True)
        if rank == 0:
            torch.save(model.module.state_dict(), f"ckpt_{epoch}.pt")
        dist.barrier()                                     # every rank, outside the if
    dist.destroy_process_group()

if __name__ == "__main__":
    main()

Every line answers a failure mode from this lesson: device set by local rank, identical seeds, DDP wrapping before the optimiser, DistributedSampler with set_epoch, non-blocking copies, rank-0-only saving of the unwrapped module, and a barrier called by every rank.

10. Mixed precision, evaluation and checkpoints in a distributed job

Mixed precision composes with both wrappers but in different places. With DDP you use torch.autocast around the forward as on one GPU (pt7); parameters and gradients stay float32, so the gradient all-reduce moves float32 unless you register a compression hook. With FSDP2, precision is part of the sharding: MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32) all-gathers parameters in bf16 (halving that traffic), computes in bf16, and reduce-scatters gradients in float32 for accuracy; the sharded master parameters and optimiser state stay float32. Choosing reduce_dtype=torch.bfloat16 halves the reduce-scatter too, at some risk to accuracy when many ranks' gradients are summed.

Evaluation must be distributed with the same care as training. Either every rank evaluates a disjoint shard and the sums and counts are all-reduced (remembering that DistributedSampler pads, pt5), or rank 0 evaluates alone while the others wait at a barrier — simpler, but under FSDP rank 0 cannot run the model alone, because every forward needs all ranks to all-gather parameters. Checkpoints follow pt8: under DDP, rank 0 saves the unwrapped module; under FSDP, every rank saves its shards with torch.distributed.checkpoint and get_state_dict, and a later job — possibly with a different number of GPUs — reshards on load.

11. Beyond data parallelism, from the API side

When a single layer's computation or activations are too large, or when data parallelism alone stops scaling because the global batch would become too large, models also split within layers. Tensor parallelism (dl9) splits a linear layer's weight across GPUs: a column-parallel layer gives each rank a slice of the output features, a row-parallel layer a slice of the input features, and pairing them (attention's QKV column-parallel, its output projection row-parallel; the MLP's first layer column-parallel, its second row-parallel) needs only one all-reduce per pair in forward. In PyTorch this is expressed with torch.distributed.tensor.parallel.parallelize_module and styles such as ColwiseParallel and RowwiseParallel, which convert the chosen weights to DTensors with Shard(0) or Shard(1) placements on one dimension of a device mesh. Combined with FSDP on another dimension (init_device_mesh("cuda", (dp, tp))), this is "2-D parallelism": tensor parallelism inside a node over NVLink, where its frequent per-layer all-reduces are cheap, and FSDP across nodes. Pipeline parallelism, which assigns consecutive layers to different GPUs and streams micro-batches through them, has its own API (torch.distributed.pipelining) and is the third axis for the largest models. For interviews, the important skill is placement: put the most communication-hungry parallelism on the fastest links.

What DDP's reducer does when graphs differ between ranks

DDP's buckets assume all ranks produce gradients in the same order. Within a bucket order is irrelevant, but buckets are all-reduced in the order they become ready on each rank; if different ranks finish buckets in a different order, the collectives mismatch. DDP handles this by launching bucket all-reduces in a fixed order (it waits to launch bucket i until all earlier buckets have launched), and by rebuilding buckets after the first iteration based on the order gradients actually arrived. Data-dependent control flow that changes which parameters get gradients on different ranks in the same step is the dangerous case — the reason for find_unused_parameters, and the reason mixture-of-experts layers often use dedicated expert-parallel communication rather than plain DDP.

Communication hooks

DDP lets you replace the per-bucket all-reduce with your own function through register_comm_hook. Built-in hooks compress gradients to fp16 or bf16 before the all-reduce (halving traffic) or implement PowerSGD low-rank compression (cutting it by orders of magnitude for large matrices at some cost in convergence). They matter when the network, not computation, limits scaling — typically many nodes on Ethernet — and the DDP paper's analysis that "communication is the dominant training latency contributor, and its impact increases with model sizes" is the motivation. Validate any compression by comparing loss curves against uncompressed training.

DTensor and device meshes: the general mechanism

FSDP2 is built on DTensor, which describes one logical tensor laid out over a device mesh with a placement per mesh dimension: Shard(0), Replicate() or Partial() (pending a reduction). A 2-D mesh of shape (nodes, GPUs per node) with placements (Replicate, Shard(0)) is HSDP; a mesh of (data parallel, tensor parallel) with FSDP on one dimension and tensor parallelism (row- or column-sharded linear layers) on the other is how large models combine sharding with intra-layer parallelism in PyTorch. Because the same object describes all of these, distributed checkpoints (pt8) can reshard between them: DCP reads the placements and offsets and plans the reads.

Initialising large sharded models

A 70B model cannot be built on one GPU and then sharded. The FSDP2 pattern is to construct the model on the meta device (no memory), apply fully_shard to every block and the root (which creates sharded meta DTensors), then call model.to_empty(device="cuda") to allocate only each rank's shards, and run an initialisation function or load a sharded checkpoint with DCP. Initialisation functions must then be shard-aware: a random initialisation must give the same full tensor regardless of sharding (DTensor's random operations handle this by offsetting the RNG per shard), or the model differs from a single-GPU run.

Overlap and memory in FSDP: prefetching and rate limiting

FSDP hides communication by issuing the all-gather for the next unit while the current unit computes, in forward and in backward. Prefetching too eagerly has a cost: every prefetched unit's full parameters occupy memory, and if the CPU races ahead issuing all-gathers, many units can be gathered at once, raising peak memory and fragmenting the allocator. The FSDP paper describes a rate limiter that caps the number of in-flight all-gathers for this reason, and studies how prefetching and wrapping granularity trade memory against overlap. FSDP2 exposes the same decisions explicitly: which modules to prefetch (set_modules_to_forward_prefetch, set_modules_to_backward_prefetch) and whether to reshard after forward. Wrapping granularity matters too: units too small mean many small collectives with high per-call overhead; units too large mean large gathered buffers and coarse overlap. One transformer block per unit is the usual sweet spot.

Process groups beyond the default

The default process group contains every rank, but collectives can run on subgroups created with dist.new_group(ranks=[...]) — or, more conveniently, the groups a device mesh creates for each of its dimensions. HSDP uses one group per node for sharding and one group per GPU index across nodes for replication; tensor parallelism uses a group of the GPUs inside a node. Two rules carry over from the default group and are stricter here: every rank must call new_group with the same arguments in the same order (group creation is itself collective), even ranks that are not members; and every member of a group must call each collective on that group in the same order. Mismatched subgroup collectives are a common source of hangs in hand-written parallel code, which is one reason the device-mesh API, which creates all groups at once, is preferred.

Stragglers, and why scaling stops being linear

Every synchronous collective runs at the speed of the slowest rank. Small per-rank variations — a slower GPU, a data loader stall on one rank (pt5), thermal throttling, a noisy neighbour on a shared network link — become everyone's waiting time, and with thousands of ranks the expected maximum of many small delays grows. The DDP paper notes that its 256-GPU measurements came from a shared cluster, where such variance is visible. Mitigations: balance data loading so no rank waits on I/O, monitor per-rank step time and remove persistent stragglers, keep collectives large enough to amortise latency, and overlap communication thoroughly so that small delays are absorbed by computation rather than exposed.

Why averaging gradients equals training on the big batch

DDP's correctness rests on one identity. With a mean-reduced loss, the gradient over a global batch of n·b examples is the average of the n per-rank gradients over b examples each, as long as every rank's batch has the same size and the loss is a mean over examples. That is why DDP divides the all-reduced sum by the world size, and why identical replicas stay identical: each applies the same averaged gradient with the same optimiser state. The identity breaks in exactly the places this track has flagged: unequal per-rank batch sizes (the last batch, uneven shards), token-level losses with different token counts per rank (the accumulation bug of pt6, now across ranks — all-reduce the token count and divide by the global total), and BatchNorm, whose statistics are per rank unless synchronised. Knowing the identity lets you predict which changes keep a distributed run equivalent to a single-GPU run and which do not.

Failure mode: the hang

Symptom: no progress, no error, GPUs at 0% or stuck at 100% in a spin. Cause: ranks disagree about the next collective — an exception on one rank, a branch that skips a collective on some ranks (logging reductions inside if rank == 0, early exit on an empty batch), uneven data so one rank finishes its epoch first, or different numbers of micro-batches. Tools: a finite timeout in init_process_group; stack dumps from all ranks (py-spy) or PyTorch's NCCL flight recorder, which records recent collectives per rank so mismatches are visible; the environment variable TORCH_DISTRIBUTED_DEBUG=DETAIL while developing, which checks that collectives match across ranks.

Failure mode: poor scaling

Symptom: 8 GPUs give 5× rather than ~7.5×; 64 GPUs give 30×. Diagnose with the profiler (pt12): is the all-reduce exposed after backward (bucket sizes, too little compute per step — increase the per-GPU batch or use accumulation with no_sync), are some ranks waiting on others (stragglers, data loading), is the job crossing a slow network (consider HSDP or gradient compression), or is find_unused_parameters adding a traversal every step? Compute the expected communication time from the formulas in the body and compare with the measured gap.

Failure mode: replicas that drift apart

Symptom: ranks report different losses on the same data, or evaluation differs by which rank runs it. Causes: a parameter updated outside the optimiser on some ranks (a rank-dependent buffer update, an EMA computed differently), a rank that skipped a step (a GradScaler on one rank finding inf when others did not — normally prevented because inf checks are synchronised — or custom logic), non-deterministic kernels compounding over many steps (tiny, usually harmless). Check by computing a checksum of parameters on every rank periodically and all-gathering it.

Failure mode: OOM only in the distributed job

Symptom: the model fits on one GPU but not under DDP or FSDP. Causes: all ranks placing tensors on GPU 0 (missing set_device), DDP's gradient buckets adding a gradient-sized buffer (use gradient_as_bucket_view=True), FSDP wrapped only at the root (the whole model gathered at once), or set_requires_gradient_sync(False) holding unsharded gradients across many micro-batches. Check torch.cuda.max_memory_allocated() per rank and the memory snapshot (pt7).

What to log in a distributed run

Per rank: step time, data-wait time and peak memory; globally: tokens per second and MFU (pt10), the fraction of step time spent in exposed communication (from periodic profiles), and the number of restarts. A rank whose step time is consistently higher than the median by more than a few percent is a straggler worth investigating; a rising exposed-communication fraction as you add nodes says the network is becoming the bottleneck.

Failures at scale, and elastic restarts

At hundreds or thousands of GPUs, hardware failures are routine rather than exceptional: a GPU with uncorrectable memory errors, a network link that flaps, a node that reboots. Because synchronous data parallelism needs every rank, any single failure stops the job. The operational answer combines several pieces from this track: frequent, asynchronous, sharded checkpoints (pt8) so little work is lost; torchrun's elastic mode or a cluster scheduler that detects the failure, replaces or excludes the bad node, and restarts all ranks from the latest checkpoint; health checks before a job starts (a short all-reduce benchmark that exposes slow links and bad GPUs); and alerting on hangs via collective timeouts rather than waiting for a human to notice a flat loss curve. The time from failure to resumed training — detection, restart, checkpoint load, data-loader warm-up — is itself a metric worth tracking, because at scale it can cost more than the lost work.

Runs on CPU with the Gloo backend in gpt_env — no GPUs needed — to watch DDP's behaviour with two processes on one machine. About 20 minutes. Save as pt11_lab.py and run python -m torch.distributed.run --nproc_per_node=2 pt11_lab.py (the module form of torchrun).

import os, torch, torch.distributed as dist, torch.nn as nn
from torch.nn.parallel import DistributedDataParallel as DDP

def main():
    dist.init_process_group("gloo")
    rank, world = dist.get_rank(), dist.get_world_size()
    torch.manual_seed(rank)                        # deliberately different init per rank
    net = nn.Sequential(nn.Linear(8, 16), nn.ReLU(), nn.Linear(16, 2))
    model = DDP(net)                               # broadcasts rank 0's weights
    w = model.module[0].weight.detach().clone()
    allw = [torch.zeros_like(w) for _ in range(world)]
    dist.all_gather(allw, w)
    print(rank, "weights identical after DDP init:", torch.equal(allw[0], allw[1]))

    x = torch.randn(4, 8) + rank                   # different data per rank
    model(x).sum().backward()
    g = model.module[0].weight.grad.clone()
    allg = [torch.zeros_like(g) for _ in range(world)]
    dist.all_gather(allg, g)
    print(rank, "grads identical after backward:", torch.allclose(allg[0], allg[1]))

    model.zero_grad()
    with model.no_sync():
        model(x).sum().backward()                  # local only
    gl = model.module[0].weight.grad.clone()
    dist.all_gather(allg, gl)
    print(rank, "grads identical under no_sync:", torch.allclose(allg[0], allg[1]))

    t = torch.tensor([float(rank + 1)])
    dist.all_reduce(t)                             # every rank must call this
    print(rank, "all_reduce sum:", t.item())
    dist.destroy_process_group()

if __name__ == "__main__":
    main()
  1. Both ranks print True for identical weights: DDP broadcast rank 0's parameters despite different seeds.
  2. Gradients are identical after a normal backward (averaged by DDP) even though each rank saw different data.
  3. Under no_sync() they differ: no communication happened.
  4. The all_reduce prints 3.0 on both ranks. Now wrap it in if rank == 0: and run again: the job hangs — stop it with Ctrl+C. That is the classic distributed hang.
  5. Needs CUDA GPUs: repeat with the NCCL backend and a GPT block wrapped with fully_shard; print a parameter's type (DTensor) and its local shard shape (dim 0 divided by world size).
Find the bug: a DDP script that is slow, hangs and saves the wrong thing

This script trains on 2 nodes × 8 GPUs. Throughput is lower than on one node, one in ten runs hangs near the end of an epoch, and checkpoints cannot be loaded into a plain model. Find the bugs.

dist.init_process_group("nccl")
model = DDP(GPT(cfg).cuda(), find_unused_parameters=True)
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)
loader = DataLoader(ShardStream(files), batch_size=8)       # IterableDataset, sharded by rank
for step, (x, y) in enumerate(loader):
    for micro in range(4):                                   # gradient accumulation
        _, loss = model(x[micro::4].cuda(), y[micro::4].cuda())
        (loss / 4).backward()
    opt.step(); opt.zero_grad()
    if dist.get_rank() == 0 and step % 100 == 0:
        dist.all_reduce(loss)
        print(step, loss.item() / dist.get_world_size())
torch.save(model.state_dict(), "final.pt")
Answer

Bug 1 — no device set per rank. Without torch.cuda.set_device(LOCAL_RANK), .cuda() puts every process's model on GPU 0 of its node; eight processes share one GPU. Symptom: very low throughput, possible OOM. Fix: set the device from LOCAL_RANK before building the model, and pass device_ids=[local_rank].

Bug 2 — find_unused_parameters=True on a model that uses every parameter. It adds an autograd-graph traversal every iteration for nothing. Fix: remove it (default False).

Bug 3 — gradient accumulation without no_sync. Each of the 4 micro-batch backward passes all-reduces all gradients: 4× the communication, much of it across the slow inter-node link — the main reason two nodes are slower than one. Fix: wrap the first three micro-batches in model.no_sync().

Bug 4 — a collective inside a rank-0-only branch. dist.all_reduce(loss) runs only on rank 0, which waits forever for the others. (Every 100 steps it would hang — unless other collectives happen to pair with it, which corrupts both.) Fix: call the all_reduce on every rank on a detached copy, print on rank 0. The "one in ten runs" hang near the epoch end is a second cause: the rank-sharded IterableDataset gives ranks different numbers of batches, so one rank finishes and stops calling DDP's collectives while others wait. Fix by balancing shards or capping steps per epoch so every rank runs the same number of iterations.

Bug 5 — saving the wrapper from every rank. model.state_dict() has keys prefixed with module. (so a plain model cannot load it strictly), and all 16 ranks write the same file concurrently, which can corrupt it. Fix: if rank == 0: torch.save(model.module.state_dict(), "final.pt.tmp"); os.replace(...), followed by dist.barrier() on every rank (pt8).

Estimate: DDP or FSDP for a 13B model?

You have 16 GPUs with 80 GB each (2 nodes of 8, NVLink inside each node, 50 GB/s per GPU between nodes). Can you train a 13B model with DDP? With FSDP? Estimate the per-step communication for FSDP.

Answer

DDP: 16 bytes × 13B = 208 GB of state per GPU — impossible. FSDP over 16 GPUs: 208/16 = 13 GB per GPU plus a gathered block and activations — fits comfortably. Communication with bf16 on the wire: parameters are 26 GB; each all-gather moves about 15/16 × 26 ≈ 24 GB per GPU, twice per step, plus a reduce-scatter of bf16 gradients ≈ 24 GB: ≈ 73 GB per GPU per step. If those rings cross the 50 GB/s inter-node links, that is about 1.5 s per step of communication to hide. HSDP (shard within each node of 8, replicate across the 2 nodes) needs 26 GB per GPU of state, still fits, keeps the all-gathers on NVLink, and sends only a gradient all-reduce of each rank's shard across nodes — a much better fit for this network.
