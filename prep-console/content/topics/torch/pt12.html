Two teams train the same 350M-parameter model on the same eight GPUs. One finishes in four days, the other in nine. Nothing about the model differs. The slower team's loop prints the loss with .item() every step, computes an accuracy with a boolean mask and a Python if, uses the default optimiser implementation that launches thousands of tiny kernels, keeps matmuls in full float32, and never looked at a profiler trace. Each habit costs 5–30%; together they cost more than half the run. At cloud prices for eight top-end GPUs, the difference is tens of thousands of dollars for one model.

Performance work in PyTorch has a reputation for being black magic, but most of it follows from one fact covered in pt1: the CPU queues GPU work asynchronously, and the GPU is only busy if the CPU stays ahead of it with enough large kernels. Everything that makes the CPU wait (synchronisations), everything that makes it fall behind (Python overhead, thousands of tiny kernel launches), and everything that wastes the GPU's time (unfused memory-bound operations, slow precision modes, idle gaps while waiting for data or communication) shows up as lost throughput. PyTorch gives you tools for each: a profiler that shows the timeline, a sync-debugging mode, torch.compile to capture and fuse graphs, CUDA graphs to eliminate launch overhead, and fused optimisers.

torch.compile deserves particular attention because it is both powerful and opaque. The PyTorch 2 paper (Ansel et al., ASPLOS 2024) describes how TorchDynamo captures graphs from ordinary Python by analysing bytecode, and how TorchInductor generates fused kernels, reporting geometric-mean speed-ups of 2.27× for inference and 1.41× for training on an NVIDIA A100 across more than 180 real-world models. Getting that speed-up in your own code requires understanding graph breaks, recompiles and modes — which is what interviewers probe when they ask "you added torch.compile and it got slower, why?".

This lesson gives a method: measure correctly, profile and read the trace, remove synchronisations, compile and debug the compilation, use CUDA graphs where launch overhead dominates, and take the cheap wins. Numbers and APIs are checked against PyTorch 2.14; GPU-only experiments are marked.

Picture the CPU as a restaurant's order desk and the GPU as the kitchen. The desk writes orders (kernel launches) onto a rail; the kitchen cooks them in order, as fast as it can. When the desk writes faster than the kitchen cooks, orders pile up on the rail and the kitchen never waits — that is the healthy state. Three things break it:

  • The desk walks into the kitchen to ask a question. "How did the last dish turn out?" — .item(), print(tensor), an if on a tensor's value. The desk must wait until every dish on the rail is finished. Meanwhile it writes no new orders, so when it returns, the rail is empty and the kitchen waits for the next order. This is a host–device synchronisation.
  • The orders are tiny and many. Writing an order takes the desk a few microseconds. If each dish takes the kitchen even less time — adding a bias, applying an activation to a small tensor — the kitchen finishes faster than the desk can write, and waits between every order. This is being launch-bound.
  • The kitchen does wasteful work. Every separate small step fetches ingredients from the store room and puts the result back (reads and writes GPU memory). Combining steps into one — fusion — fetches once. Using faster appliances — tensor cores in bf16 or TF32 — cooks the big dishes faster.

The tools map onto these: the profiler draws the rail and the kitchen on a timeline so you can see waits; the sync debug mode catches the desk's trips into the kitchen; torch.compile merges many small orders into fewer fused ones and removes Python overhead; CUDA graphs let the desk hand over an entire pre-written order book with one action; precision settings and fused optimisers make the kitchen's work cheaper.

Every performance problem in this lesson can be placed in one of four regimes, and naming the regime is the first step of any answer. Idle-bound: the GPU waits for something outside it — data loading, a synchronisation, communication. Overhead-bound (or launch-bound): the GPU runs, but in kernels so small that the time to launch them dominates. Memory-bound: kernels are large, but each does little arithmetic per byte it reads or writes, so memory bandwidth limits them (element-wise operations, normalisation, softmax). Compute-bound: large matmuls running near the tensor cores' peak. The remedies differ completely — fix the pipeline, fuse or replay with graphs, fuse to cut memory traffic, or use faster precision and better shapes — and applying the wrong one wastes effort. A profiler trace tells you the regime in minutes.

Some orders of magnitude make the regimes concrete. Launching one kernel from PyTorch costs the CPU roughly 5–20 microseconds. A large matmul in a transformer layer takes hundreds of microseconds to milliseconds on the GPU. An element-wise operation over a few million values takes tens of microseconds. A host–device synchronisation costs whatever work was queued — possibly the rest of the step. So a step built from big matmuls with a few hundred kernels is comfortably compute-bound; the same model at batch 1 in decode, where every kernel shrinks to microseconds, becomes launch-bound; and one sync per step can cost more than all the kernels of the optimiser together. Keeping these numbers in mind lets you predict from the model and batch size which regime you are in before you open a profiler.

Where the restaurant analogy breaks: a real kitchen can cook several orders at once, and so can a GPU — but only across separate streams or within one large kernel, not across a single stream's queue, which runs in order. That is why fusion (one big kernel instead of ten small ones) and overlapping communication on a separate stream (pt11) matter as much as they do.

If you remember one sentence: keep the CPU ahead of the GPU — no synchronisations, few and large kernels — and measure with a timeline before and after every change.

1. Measuring correctly

Because GPU calls are asynchronous, time.perf_counter() around a GPU operation measures how long it took to queue it, not to run it. Two correct ways:

# 1. synchronise around the timed region
torch.cuda.synchronize(); t0 = time.perf_counter()
for _ in range(20): step()
torch.cuda.synchronize(); dt = (time.perf_counter() - t0) / 20

# 2. CUDA events (no global stall inside the loop)
start, end = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
start.record()
for _ in range(20): step()
end.record(); torch.cuda.synchronize()
ms_per_step = start.elapsed_time(end) / 20

Always warm up first — the first iterations include allocator growth (pt7), cuDNN algorithm selection and, with torch.compile, compilation — and time enough steps to average out noise. Report throughput in the unit that matters (tokens or samples per second) and, for training, MFU (pt10): achieved model FLOPs per second divided by the GPU's peak. MFU tells you how much headroom is left in a way that utilisation percentages do not.

2. The profiler

from torch.profiler import profile, ProfilerActivity, schedule, record_function
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             schedule=schedule(wait=1, warmup=1, active=3),
             record_shapes=True, with_stack=True,
             on_trace_ready=lambda p: p.export_chrome_trace(f"trace_{p.step_num}.json")) as prof:
    for step in range(5):
        with record_function("forward"):
            loss = model(x, y)
        with record_function("backward"):
            loss.backward()
        opt.step(); opt.zero_grad()
        prof.step()
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))

The schedule skips one step, warms up for one, and records three — profiling every step of a run is too slow. record_function labels regions so they appear on the timeline. Open the exported trace in Perfetto (ui.perfetto.dev) or Chrome's trace viewer. Reading it, in order:

  1. GPU stream rows. Are kernels back to back, or are there gaps? Gaps mean the GPU waited — for the CPU, for data, for a synchronisation or for communication.
  2. CPU rows during the gaps. What was the CPU doing? aten::item or cudaStreamSynchronize is a sync; enumerate(DataLoader)…__next__ is data loading (pt5); long Python stretches between operator calls are framework or user overhead.
  3. Kernel sizes. Many kernels of a few microseconds each signal a launch-bound regime; a few long kernels signal compute- or memory-bound work.
  4. The operator table. Only now sort by self CUDA time to see which operations to make cheaper.

Memory profiling (profile_memory=True) and the snapshot tool from pt7 complement the timeline.

3. Host–device synchronisations: find and remove them

Operations that synchronise, because they need a GPU value on the CPU or need to know a data-dependent size:

  • .item(), .tolist(), .cpu(), .numpy(), print(tensor), float(tensor), int(tensor).
  • Python control flow on tensor values: if loss > 10:, while not converged:, assert (x > 0).all().
  • Operations with data-dependent output sizes: boolean indexing x[mask], nonzero, unique, masked_select (pt2).
  • Copies from GPU to pageable host memory, and explicit torch.cuda.synchronize().

torch.cuda.set_sync_debug_mode("warn") (or "error") makes PyTorch report synchronising calls as they happen; run a few steps with it to get a list. Replacements: log every N steps; accumulate metrics in GPU tensors (running_loss += loss.detach()) and read them occasionally; replace data-dependent selection with masks ((loss * mask).sum() / mask.sum()); replace Python branches with torch.where; move checks such as NaN detection to every N steps. The cost of one sync depends on the overlap it destroys. Suppose a step's kernels take 150 ms of GPU time and launching them takes 100 ms of CPU time. Without syncs, launching step n+1 overlaps with executing step n, so a step costs about 150 ms. With a sync at the end of every step, the CPU only starts launching step n+1 after step n has finished, and the first kernels of each step wait for Python: the GPU idles for a good part of every launch phase, and the step stretches toward 150 + 100 ms in the worst case.

4. torch.compile: what it does

model = torch.compile(model) (or decorating a function) returns a wrapper. On the first call, TorchDynamo intercepts the Python frame, symbolically executes its bytecode, and records every PyTorch operation into an FX graph, stopping where it meets something it cannot represent. It attaches guards — conditions on input shapes, dtypes, devices and the Python values the graph depended on. TorchInductor then compiles the graph: it decomposes operations into a smaller set of primitives, fuses chains of element-wise and reduction operations into single kernels (generated in Triton on GPU or C++ on CPU), chooses matmul implementations, and plans memory. Later calls check the guards and run the compiled code directly. The PyTorch 2 paper reports that TorchDynamo captures a whole-program graph most of the time and that TorchInductor achieved geometric-mean speed-ups of 2.27× (inference) and 1.41× (training) on an A100 over more than 180 real-world models — the gains come mostly from fusing memory-bound operations and removing Python overhead (gpu6).

What it does not do: change your model's mathematics, make large matmuls much faster than cuBLAS already does, or help code that is dominated by data loading or synchronisations outside the compiled region.

5. Graph breaks

When Dynamo meets an unsupported construct, it ends the current graph, runs the construct in normal Python, and starts a new graph afterwards — a graph break. A function on 2.14:

def f(x):
    y = x.sin()
    if y.sum() > 0:          # branch on a tensor value
        y = y * 2
    print("hi")              # unsupported builtin
    return y.cos() + float(x.mean())   # .item()-style scalar read
ex = torch._dynamo.explain(f)(torch.randn(8))
ex.graph_count, ex.graph_break_count    # (4, 3)

The three reasons reported are exactly the three marked lines: a jump on a tensor value, "Failed to trace builtin operator print", and "Unsupported Tensor.item() call with capture_scalar_outputs=False". In real models, the paper lists the most common causes as calls to non-PyTorch libraries such as NumPy, data-dependent control flow, and printing or logging. Find them with TORCH_LOGS="graph_breaks" python train.py or torch._dynamo.explain. Fixes:

  • Move logging and metrics out of the compiled function (compile the model, not the whole loop body with prints).
  • Replace tensor-dependent branches with torch.where (both sides computed) or torch.cond (a captured conditional).
  • Keep NumPy out of the forward; use torch equivalents.
  • Set torch._dynamo.config.capture_scalar_outputs = True when scalar reads are intended inside the graph.
  • Compile with fullgraph=True to turn breaks into errors in code that must compile as one graph (export paths, CUDA graphs).

6. Recompiles and dynamic shapes

If a later call fails a guard — a different sequence length, a different dtype, a Python attribute that changed — Dynamo compiles a new version. With automatic_dynamic_shapes (True on 2.14), the first time a dimension changes, Dynamo recompiles once with that dimension marked dynamic (symbolic), so subsequent sizes reuse the graph. recompile_limit (8 on 2.14) caps recompiles per code object; past it, the function falls back to eager execution, silently losing the speed-up. Diagnose with TORCH_LOGS="recompiles", which prints the failed guard (for example a size that changed). Common causes and fixes: variable sequence lengths (bucket them to a few sizes, or mark the dimension dynamic with torch._dynamo.mark_dynamic); a smaller last batch (drop_last=True); Python scalars that change each step read inside the compiled code (pass them as tensors — the learning rate in a compiled optimiser step is the classic case); toggling model.train()/eval(), which changes guarded attributes (expected: one compile per mode).

The 2.14 docstring documents four modes:

Other useful arguments: fullgraph=True, dynamic=True/False to force or forbid dynamic shapes, and backend="eager" or "aot_eager" to check whether a problem comes from capture (Dynamo) or code generation (Inductor) — the standard bisection when a compiled model gives different results.

Compile regionally when the model repeats a block: for b in model.blocks: b.compile() compiles one block's code once and reuses it for all layers, cutting compile time compared with compiling the whole model as one graph.

8. CUDA graphs

A CUDA graph records a sequence of kernel launches with their arguments and replays them with one launch call. On a small model where launching 500 kernels takes 2 ms of CPU time but running them takes 1 ms of GPU time, replaying a graph cuts the step to about the GPU time. mode="reduce-overhead" applies this automatically to compiled regions; the manual API is torch.cuda.CUDAGraph with torch.cuda.graph(g): capture blocks. Requirements follow from "replay exactly the same launches": static shapes; static memory addresses for inputs and outputs (copy new data into the same input buffers before each replay); no CPU synchronisation inside the region; no data-dependent control flow or allocation sizes. The KV-cache decode step (pt10) is the textbook use: preallocate the cache, give every step identical shapes, and capture once.

9. Cheap wins outside the compiler

  • Precision. bf16 autocast (pt7). For code that stays in float32, torch.set_float32_matmul_precision("high") allows TF32 on Ampere and later — float32 range with a 10-bit mantissa, several times faster for matmuls. The default on 2.14 is "highest" (no TF32).
  • Fused and foreach optimisers. AdamW(..., fused=True) updates many parameters per kernel; foreach (the default on CUDA when available) groups tensors. A model with 300 parameter tensors goes from thousands of optimiser kernels per step to a handful.
  • channels_last for convolutional networks: model.to(memory_format=torch.channels_last) and inputs likewise (pt1). Tensor-core convolution kernels prefer NHWC; gains of 10–30% are common for CNNs in mixed precision.
  • Shapes that suit the hardware. Dimensions that are multiples of 8 (fp16/bf16) or 64 tile well; nanoGPT pads the vocabulary from 50,257 to 50,304 for this reason (pt10).
  • Larger batches, when memory allows and the optimisation tolerates them, raise arithmetic intensity and amortise per-step overhead.
  • cudnn.benchmark = True for convolutional models with fixed input sizes lets cuDNN pick the fastest algorithm (at the cost of determinism, pt6).

10. A worked optimisation of one training step

To see how the pieces combine, follow a realistic sequence on a 125M-parameter GPT at batch 16 and sequence length 1,024 on one modern GPU. The numbers are illustrative of typical proportions rather than a benchmark of a specific card, but each step's reasoning is the one you would use.

  1. Baseline. Eager float32, default optimiser, loss.item() printed every step, num_workers=0. Measured with CUDA events: 420 ms per step, about 39,000 tokens per second. The trace shows gaps between steps (data loading and the sync) and long float32 matmuls.
  2. Remove the idle time. Four DataLoader workers with pinned memory and non-blocking copies; log every 50 steps. The gaps disappear: 340 ms. Nothing about the model changed.
  3. Use the tensor cores. bf16 autocast (pt7). Matmuls run several times faster and activations halve: 150 ms. The trace now shows matmuls taking under half the step; the rest is many short element-wise and normalisation kernels plus the optimiser.
  4. Fuse and cut overhead. torch.compile (default mode) fuses the element-wise chains; AdamW(fused=True) collapses the optimiser to a few kernels: 105 ms. The first steps are slower while compiling.
  5. Use the fused attention kernel. If attention was hand-written, switching to F.scaled_dot_product_attention (pt10) removes the T × T intermediates: a further 10–20% at this sequence length, and much less memory, which in turn allows a larger batch.

The overall improvement, about 4× in this illustration, came from five changes, none of which touched the model's mathematics. The order matters: removing idle time first makes later measurements meaningful, and precision before compilation means the compiler fuses the kernels you will actually run. At each step, the trace said what to do next.

11. Inference-specific speed

Inference changes the bottlenecks. Run under torch.inference_mode() (pt3), which removes autograd bookkeeping, with weights in bf16 (pt7). For batch prediction, larger batches raise throughput until memory or latency limits are hit. For autoregressive generation, the decode step is small and launch-bound at low batch, so the biggest wins are a static KV cache (pt10) with torch.compile(mode="reduce-overhead") or a manual CUDA graph, and batching many sequences into each decode step so each weight read serves more tokens. Prefill, in contrast, is compute-bound like training. Serving stacks (pt13) build on exactly these mechanisms — static caches, CUDA graphs per batch-size bucket and continuous batching — which is why understanding them in plain PyTorch makes those systems legible.

12. Streams: overlapping copies and compute yourself

All the work in a simple training loop runs on one CUDA stream, in order. A second stream lets independent work overlap: copying the next batch to the GPU while the current batch computes, or offloading tensors to the host during backward (pt7). The pattern for prefetching a batch:

copy_stream = torch.cuda.Stream()
def prefetch(batch):
    with torch.cuda.stream(copy_stream):
        return [t.to("cuda", non_blocking=True) for t in batch]     # needs pinned memory
nxt = prefetch(next(it))
for _ in range(steps):
    torch.cuda.current_stream().wait_stream(copy_stream)            # order: copy before use
    cur = nxt
    for t in cur: t.record_stream(torch.cuda.current_stream())      # tell the allocator
    nxt = prefetch(next(it))                                        # overlaps with compute below
    loss = model(*cur); loss.backward(); opt.step(); opt.zero_grad()

Two rules make it correct. wait_stream inserts a dependency so the compute stream does not read a tensor before its copy finishes — without it, the model can read half-copied data with no error. And record_stream tells the caching allocator that a tensor allocated on one stream is used on another, so its memory is not reused while still in use. Most code never needs this, because pinned memory with non_blocking=True copies on the default stream already overlap with earlier queued work; explicit streams matter when copies are large, as in offloading, or when you build infrastructure such as FSDP's communication streams.

How Dynamo captures Python without rewriting it

Earlier capture approaches had a fundamental problem, which the PyTorch 2 paper describes: torch.jit.trace records one execution and silently bakes in its control flow, and torch.jit.script requires a restricted subset of Python that real models rarely fit. TorchDynamo instead uses CPython's frame evaluation hook (PEP 523) to intercept each function call before it runs, analyses the function's bytecode, and symbolically executes it, building a graph of tensor operations while tracking Python values it depends on as guards. Anything it cannot handle becomes a graph break with the original bytecode as a fallback, so correctness is preserved. That design explains its behaviour: it is robust (fallback, not failure), guarded (it re-checks assumptions every call) and sensitive to Python-level values (constants become guards).

AOTAutograd: compiling the backward pass

Training needs the backward pass compiled too. AOTAutograd traces the forward graph through PyTorch's autograd to produce a joint forward-and-backward graph ahead of time, then partitions it into a forward graph and a backward graph, choosing which intermediates to save and which to recompute (a min-cut over the joint graph, similar in spirit to selective activation checkpointing, pt7). Inductor compiles both. This is why compiled training can also use less memory than eager: cheap element-wise intermediates are recomputed in the fused backward kernels instead of being stored.

Why fusion helps: memory traffic

An element-wise operation on a tensor of N float32 elements reads 4N bytes and writes 4N bytes and does one arithmetic operation per element — far below what a GPU can compute per byte moved, so it is memory-bound (gpu2). A chain of five such operations (bias, GELU, dropout, residual add, scale) unfused moves 40N bytes; fused into one kernel it reads the inputs once and writes the output once, about 8N–12N bytes, a 3–5× reduction for that chain. Transformers have many such chains around their matmuls (normalisation, activations, residuals, masking), which is where Inductor's fused kernels win. The matmuls themselves already run in cuBLAS at close to peak, which is why whole-model speed-ups are 1.3–2× rather than 5×.

Compile and distributed training

torch.compile composes with DDP and FSDP, with caveats. DDP's bucket all-reduces are triggered by autograd hooks; a whole-model compiled graph would hide those boundaries, so Dynamo splits graphs at bucket boundaries (DDPOptimizer) to keep overlap. FSDP2 is designed to be traced, and compiling per block keeps its all-gathers and reduce-scatters at block granularity. Compiled autograd extends capture to the backward hooks themselves. The practical rule: compile per block (regional compilation) in distributed jobs, measure overlap in a trace, and expect the first steps to be slow while every rank compiles.

Kernel launch overhead in numbers

Launching a CUDA kernel from PyTorch costs on the order of 5–20 microseconds of CPU time including Python and dispatcher overhead. A GPT-style layer in eager mode issues dozens of kernels in forward and more in backward; a 24-layer model can issue a few thousand per step, plus thousands more in a non-fused optimiser. At 10 µs each, 5,000 launches cost 50 ms of CPU time per step — negligible next to a 500 ms step at large batch, dominant next to a 20 ms step at small batch or in decode. This is the quantitative reason CUDA graphs and fusion matter most for small batches and inference, and why the same model can be compute-bound in training and overhead-bound in serving.

Compile caches and cold starts

Compilation cost is paid per process: every new training job, every restarted rank and every inference replica recompiles unless it can reuse earlier work. Inductor keeps on-disk caches of generated kernels and compiled graphs keyed by the graph and environment, so a second run of the same code on the same machine compiles much faster; PyTorch also provides ways to package compiled artefacts and carry them to other machines with the same software and hardware. For services that scale out frequently, cold-start time — model load plus compilation plus CUDA-graph capture — becomes a product metric, and teams warm caches at build time or keep replicas warm rather than compiling on the first user request.

When the compiler is not enough: custom kernels

Some operations are not expressible as a fusion of standard ops with good performance — a novel attention variant, a quantised matmul with an unusual packing, a fused cross-entropy over a huge vocabulary that never materialises the logits. Then teams write a kernel in Triton (Python-like GPU kernel language, gpu6) or CUDA and register it as a custom operator with torch.library, providing a fake (shape-only) implementation so torch.compile can trace through it without breaking the graph and an autograd formula if it is used in training. FlexAttention, in PyTorch itself, is a middle path for attention variants: you write the score modification as a small Python function, and the compiler generates a fused attention kernel for it.

Reading MFU honestly

MFU (model FLOPs utilisation) counts only the FLOPs the model mathematically needs — about 6N per token for training plus the attention term — divided by the hardware's peak. It deliberately ignores recomputation from activation checkpointing (which makes the GPU do more work than the model needs) and does not reward running extra FLOPs. A related number, hardware FLOPs utilisation, counts everything the GPU executes, including recomputation, so it is higher whenever checkpointing is on. When comparing optimisations, use MFU: turning on checkpointing to fit a larger batch is a win only if MFU, not hardware utilisation, goes up. Typical well-tuned large-model training reports MFU in the range of roughly 40–55% on recent GPUs; small models, short sequences and small batches land far lower because overheads and memory-bound operations take a larger share of each step.

A performance investigation, step by step

The order that works in practice: establish a baseline (tokens per second, MFU, step time with proper synchronisation); check data-wait time (pt5) and exposed communication (pt11) first, because no amount of kernel work fixes them; profile three steps and classify the time as idle gaps, launch-bound, memory-bound or compute-bound; fix the biggest category; re-measure. Keep a log of each change and its effect, because performance changes interact and some regress others (CUDA graphs can raise memory, max-autotune lengthens start-up, larger batches change the optimisation).

Failure mode: compile made it slower

Causes: recompiles on every new shape (variable sequence lengths, the last batch), possibly hitting the recompile limit and falling back to eager; many graph breaks inside the hot path; compile time not amortised over a short job; CUDA graphs re-recorded because inputs change addresses or shapes. Diagnose with TORCH_LOGS="recompiles,graph_breaks" and a trace; fix shapes first.

Failure mode: compiled results differ from eager

Small differences (in the last few bits) are expected, because fused kernels change the order of floating-point operations. Larger differences need bisection: run with backend="eager" (Dynamo capture only), then "aot_eager" (plus AOTAutograd), then "inductor"; the first backend that changes results localises the problem. Inductor's minifier tools can shrink a failing graph to a small reproduction for a bug report.

Failure mode: hidden synchronisations in libraries

Some synchronisations do not look like it: a metric library computing accuracy with boolean indexing, a logging callback calling .item() on several tensors every step, gradient clipping with error_if_nonfinite=True (which must read the norm), a learning-rate scheduler reading a tensor. set_sync_debug_mode("warn") for one step names them all.

The public case: the PyTorch 2 evaluation

The PyTorch 2 paper is the reference for what to expect from torch.compile: whole-graph capture most of the time, graph breaks caused mainly by non-PyTorch library calls, data-dependent control flow and printing, and geometric-mean speed-ups of 2.27× for inference and 1.41× for training on an A100 across 180+ models from TorchBench, Hugging Face and TIMM. Its ablation study shows that removing fusion or inlining loses much of the gain — confirming that the speed comes from memory traffic and overhead, not from faster matmuls. Quoting a geometric mean, not a promise, is the honest way to set expectations for a team adopting it.

Guarding performance in CI

Performance regressions are as real as correctness bugs and harder to notice: a refactor that adds a .item() in a helper, a new layer that causes a graph break, a dependency upgrade that changes a kernel choice. Teams that care run a short benchmark in continuous integration on the target hardware — a few hundred steps of a reduced model, timed with CUDA events after warm-up — and fail the build when throughput drops by more than a set margin. Logging the number of graph breaks and recompiles (from TORCH_LOGS or torch._dynamo.utils.counters) in the same job catches compiler regressions before they reach a long run.

Profiling distributed jobs

In multi-GPU training, profile one rank (or a few) for a handful of steps and look for three things on the timeline: communication kernels (NCCL all-reduce, all-gather, reduce-scatter) and whether they overlap with compute or sit exposed at the end of backward (pt11); differences between ranks' step times (stragglers); and waits inside collectives, which mean some other rank arrived late. Exposed communication is fixed with overlap, bucket and wrapping choices, or topology-aware parallelism; waiting in collectives is fixed by finding what delays the slow rank — often data loading or a synchronisation unique to that rank, such as rank 0's logging.

When to stop optimising

Performance work has diminishing returns, and a senior answer says when to stop. Compute what the remaining headroom is worth: if a run costs 2,000 GPU-hours and the next optimisation might save 5%, that is 100 GPU-hours — worth an afternoon, not a week, and not worth any risk to correctness. Prefer changes that are general (precision, fused optimisers, removing syncs, compile) over ones that are fragile (hand-tuned kernels for one shape), and keep every optimisation behind a flag with a correctness check, so it can be turned off when it breaks after an upgrade.

CPU parts run on PyTorch 2.14 in gpt_env; about 15 minutes. GPU steps are marked. Save as pt12_lab.py.

import time, torch, torch.nn as nn, torch._dynamo as dynamo

        y = y * 2
    print("side effect")
    return y.cos() + float(x.mean())

Find the bug: a training loop that wastes half the GPU

A 125M-parameter GPT trains on one GPU at batch 8, reaching 18% MFU. The team compiled the model and saw no improvement. Find the performance bugs.

model = torch.compile(GPT(cfg).cuda())
opt = torch.optim.AdamW(model.parameters(), lr=6e-4)        # foreach/fused not set
for step, (x, y) in enumerate(loader):                       # num_workers=0
    x, y = x.cuda(), y.cuda()
    logits, loss = model(x, y)
    if torch.isnan(loss):                                     # NaN guard every step
        raise RuntimeError("nan")
    loss.backward()
    norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step(); opt.zero_grad()
    for g in opt.param_groups:                                # schedule
        g["lr"] = lr_at(step)
    acc = (logits.argmax(-1)[y != -100] == y[y != -100]).float().mean()
    print(step, loss.item(), norm.item(), acc.item())
Answer

Bug 1 — four synchronisations per step. if torch.isnan(loss) is a Python branch on a GPU value; boolean indexing [y != -100] has a data-dependent size; and three .item() calls in the print. Each forces the CPU to wait for the GPU, so the CPU never runs ahead and the GPU idles between steps. Fix: check for NaN every N steps (or with error_if_nonfinite occasionally), compute accuracy with a mask (((pred == y) & valid).sum() / valid.sum()) kept on the GPU, and log every 50 steps.

Bug 2 — compile cannot help a sync-bound loop. The compiled forward is faster, but the step time is dominated by the gaps the syncs create and by data loading; compiling the model does not touch either. Measure with a trace before compiling.

Bug 3 — data loading in the main process, synchronous copies. num_workers=0 and blocking .cuda() copies serialise data preparation with training. Fix: workers, pin_memory=True, non_blocking=True (pt5).

Bug 4 — a slow optimiser step and a Python learning rate. At batch 8 the step is short, so the optimiser's per-parameter kernels matter: use fused=True. Writing a new Python float into param_groups each step is fine in eager mode, but if the optimiser step is later compiled, the changing float becomes a guard and forces recompiles; store the learning rate as a tensor. Also consider mode="reduce-overhead" at this small batch once the syncs are gone, and a larger batch if memory allows. Expected result: MFU roughly doubling, verified with CUDA-event timing and a before/after trace.

Estimate: is this step launch-bound?

A decode step of a 24-layer model at batch 1 launches about 30 kernels per layer, each taking about 8 µs of GPU time; PyTorch's launch overhead is about 10 µs per kernel. What limits the step, and what would CUDA graphs save?

Answer

Kernels: 24 × 30 = 720 per step. GPU time ≈ 720 × 8 µs ≈ 5.8 ms; CPU launch time ≈ 720 × 10 µs ≈ 7.2 ms. The CPU cannot launch faster than the GPU executes, so the step takes about 7.2 ms — launch-bound, with the GPU idle about 20% of the time. A CUDA graph replays all 720 kernels with one launch, so the step falls to roughly the GPU time, ≈ 5.8 ms (about 20% faster), and fusion with torch.compile can cut the kernel count — and the GPU time — further.
