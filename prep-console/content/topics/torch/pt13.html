A model that reaches its target accuracy in a notebook is perhaps half of the work. It still has to answer requests with predictable latency, on hardware someone pays for every hour, often from a service that does not run the training code at all — a C++ server, a mobile app, an inference engine maintained by another team. The gap between "it works in my training script" and "it serves 2,000 requests per second within budget" is where many ML projects stall, and where senior engineers are expected to know the options.

PyTorch's inference story has changed substantially over the last few releases, and some of what is still widely taught is out of date. TorchScript (torch.jit) was the way to get a model out of Python; today the path is torch.export, which produces a single, complete graph that can be compiled ahead of time (AOTInductor), translated to ONNX (the ONNX exporter now goes through torch.export by default), or lowered to mobile runtimes. Quantisation was torch.ao.quantization; on PyTorch 2.14 calling it prints a deprecation warning that points to torchao, a separate library with a different API. TorchServe was the default model server; its README now carries a "Limited Maintenance" notice saying there are no planned updates, bug fixes or security patches. Interviewers who work on inference notice immediately when a candidate's knowledge stops in 2022.

The engineering is also subtle. Export fails on models that run perfectly in eager mode, because a branch depends on a tensor's value; or it succeeds while silently narrowing the batch sizes the exported model accepts, because a branch depends on a tensor's shape. Quantisation can make inference faster or slower depending on whether the workload is memory-bound or compute-bound. Batching can multiply throughput or blow the latency budget.

This lesson covers the path from trained model to served model in current PyTorch: the basics of inference mode and batching, torch.export with dynamic shapes and its two characteristic errors (both reproduced on 2.14), ONNX export, AOTInductor, quantisation with torchao and when it pays, and what a serving stack expects you to hand over.

Think of moving a recipe from a home kitchen to a restaurant chain. At home (eager PyTorch in Python) the cook can improvise: taste, decide, adjust — data-dependent decisions, Python logic, anything goes. A chain needs a written, fixed procedure that any franchise can follow without the original cook present. Writing that procedure is export: you watch the cook make the dish once, with placeholders for the quantities that vary (batch size, sequence length), and write down every step. If the cook ever said "if it looks too salty, add water", the procedure must either include both branches explicitly or the step cannot be written down at all — that is why value-dependent decisions break export.

From the written procedure, you can go to different kitchens:

  • AOTInductor — pre-compile the procedure into machine-specific steps (kernels) packaged for a PyTorch-based runtime, in Python or C++.
  • ONNX — translate the procedure into a standard language that many restaurant chains (runtimes) understand.
  • Mobile and edge runtimes — lower it to a compact form for small kitchens.

Two orthogonal choices apply wherever you deploy. Precision: serving in bf16 is usual; quantisation to int8, int4 or float8 shrinks weights and can speed up the memory-bound parts. And batching: cooking many orders at once uses the kitchen far better than one at a time, at the cost of making the first order wait.

Two numbers frame every inference decision, and you should be able to estimate both from the model's size and the hardware before writing code. The first is latency: how long one request takes, which for an LLM splits into time to first token (the prefill, compute-bound, growing with prompt length) and time per output token (the decode step, memory-bound at small batch, about weight bytes ÷ memory bandwidth). The second is cost per request, which is the GPU's hourly price divided by requests served per hour — and requests per hour depend almost entirely on how many requests share each step, i.e. on batching. Most of the techniques in this lesson move one of these numbers: inference mode and bf16 shave both; batching trades a little latency for a lot of throughput; quantisation cuts decode latency and frees memory for bigger batches; export and ahead-of-time compilation remove start-up and Python overhead and make deployment possible where Python is not.

Where the recipe analogy breaks: a written procedure from one cooking session normally covers every order, but an export covers only the shapes you declared and the branches that were taken while it was traced. The exported program checks its inputs at run time and refuses those outside its declared ranges — on 2.14, a batch of 100 against a declared maximum of 64 fails with "Guard failed: x.size()[0] <= 64". That is a feature: it fails loudly instead of computing garbage.

If you remember one sentence: serve in eval and inference mode with batching; export to one complete graph with declared dynamic shapes for non-Python targets; quantise with torchao where inference is memory-bound; and hand serving engines standard weights plus a precise contract.

It also helps to notice how the engineering mindset changes from training to inference. Training optimises one long job: throughput is what matters, a few minutes of start-up are irrelevant, memory goes to activations and optimiser state, and the model is a Python object you can edit. Inference optimises many short requests: tail latency and cost per request matter, start-up time is paid on every scale-out, memory goes to weights and caches, and the model is an artefact that someone else's system loads — so its interface (shapes, dtypes, preprocessing, maximum lengths) becomes a contract that must be explicit and tested. Most mistakes in this area come from carrying training habits into serving: leaving dropout on, padding everything to the maximum length, accepting a slow first request, or treating "it runs in my notebook" as a deployment.

1. The inference basics

model.eval()
model.to("cuda", dtype=torch.bfloat16)
with torch.inference_mode():
    out = model(batch.to("cuda", non_blocking=True))

Each line removes a training-time behaviour: eval() switches dropout and BatchNorm (pt4); bf16 weights halve memory and use tensor cores — safe at inference because no updates need float32's precision (pt7); inference_mode() stops graph recording and the version-counter bookkeeping (pt3). Outputs are inference tensors; clone them if anything downstream will use them in training. For classifiers and embedders, that plus batching is most of the job. For generative models add the KV cache and last-position logits (pt10).

2. Batching and padding

A GPU processing one request at a time is mostly idle: each forward reads every weight to produce one result. Processing B requests together reads the weights once for B results, so throughput rises almost linearly with B until the work becomes compute-bound. A worked example: a 7B model in bf16 has 14 GB of weights; on a GPU with about 3 TB/s of memory bandwidth, one decode step must read them all, about 4.7 ms, whether the batch is 1 or 32. At batch 1 that is about 210 tokens per second; at batch 32, about 6,800 — for nearly the same step time, until the KV cache reads and arithmetic grow enough to matter.

Batching costs latency (a request may wait for others) and memory (activations and KV cache per request), and with variable-length inputs it costs padding (pt5). Static batching pads a group to its longest member and waits for the slowest request to finish; continuous batching, used by LLM serving engines, adds new requests to the running batch at every decode step and removes finished ones, keeping the batch full. For encoders, sorting requests into length buckets cuts padding waste. The batch size to use comes from a latency budget: measure latency and throughput at several batch sizes and pick the largest that meets the target percentile.

3. torch.export: capturing one complete graph

torch.export.export(model, args, dynamic_shapes=…) traces the model with symbolic inputs and returns an ExportedProgram. For a small module (a Linear followed by ReLU) on 2.14 the graph reads:

def forward(self, p_l_weight, p_l_bias, x):
    linear = torch.ops.aten.linear.default(x, p_l_weight, p_l_bias)
    relu = torch.ops.aten.relu.default(linear)
    return (relu,)

Three properties are visible. The graph is in terms of ATen operators (PyTorch's core operator set), not your Python. Parameters are lifted to explicit inputs (p_l_weight, p_l_bias), so the program is a pure function and its weights can be swapped or serialised separately. And there is no Python control flow: what was traced is all there is.

Dynamic dimensions are declared with Dim:

from torch.export import export, Dim
ep = export(model.eval(), (x,), dynamic_shapes={"x": {0: Dim("batch", min=1, max=64)}})
ep.range_constraints          # {s77: VR[1, 64]}
ep.module()(torch.randn(16, 8))   # works
ep.module()(torch.randn(100, 8))  # AssertionError: Guard failed: x.size()[0] <= 64
torch.export.save(ep, "model.pt2"); ep2 = torch.export.load("model.pt2")

All of these were run on 2.14. In non-strict mode — the default (strict=False) on 2.14 — export runs your Python normally while tracing tensors symbolically, which supports more Python than the strict, Dynamo-based mode. Export the model in eval mode, or the graph will contain training behaviour such as dropout.

4. The two characteristic export errors

Shape-dependent branches narrow your ranges. Add if x.shape[0] > 2: return self.l(x).relu() to the module and export with batch declared as 1–64. To follow the branch, export must decide which side applies; with a symbolic batch it assumes the side taken by the example (batch 4) and records the condition batch ≥ 3 as a guard. That contradicts the declared range, and on 2.14 export stops with:

ConstraintViolationError: Constraints violated (batch)!
  - Not all values of batch = L['x'].size()[0] in the specified range batch <= 64
    satisfy the generated guard 3 <= L['x'].size()[0] and L['x'].size()[0] <= 64
Suggested fixes:
  batch = Dim('batch', min=3, max=64)

Either accept the narrower range if batches of 1–2 never occur, or remove the branch so the graph is valid for every declared size. The error is a gift: without it, an exported model would silently use the wrong branch for small batches.

Value-dependent branches cannot be exported at all. if x.sum() > 0: return x * 2 depends on data, which is unknown at export time. On 2.14 export fails with GuardOnDataDependentSymNode: Could not guard on data-dependent expression. Rewrite with a captured conditional, torch.cond(x.sum() > 0, lambda x: x * 2, lambda x: x - 1, (x,)), which records both branches in the graph, or with torch.where when both branches are cheap. The same applies to loops whose trip count depends on values, and to .item() used for anything but simple size arithmetic.

5. ONNX export

onnx_program = torch.onnx.export(model.eval(), (x,), dynamic_shapes={"x": {0: Dim("batch")}})
onnx_program.save("model.onnx")

On 2.14 torch.onnx.export takes dynamo=True by default: it captures the model with torch.export (so section 4's rules apply) and translates the ATen graph into ONNX operators; the translation library in this version targets ONNX opset 18. Large models are written with external data files (external_data=True by default) because a single protobuf file cannot exceed 2 GB. Verify any exported model by running ONNX Runtime and PyTorch on the same inputs and comparing outputs within a tolerance (about 1e-4 relative for float32); the verify option automates a basic check. ONNX makes sense when the deployment target is ONNX Runtime (including CPU and edge targets), a vendor engine that consumes ONNX, or a non-Python environment where a PyTorch runtime is unwelcome.

6. AOTInductor

AOTInductor compiles an ExportedProgram ahead of time with Inductor — the same code generator torch.compile uses — and packages the compiled kernels, weights and a small runner into a .pt2 archive:

path = torch._inductor.aoti_compile_and_package(ep, package_path="model_aoti.pt2")
runner = torch._inductor.aoti_load_package(path)       # Python; a C++ loader also exists
out = runner(x)

The benefit is torch.compile-level kernels without Python model code or just-in-time compilation at serving time — useful for C++ services and fleets that cannot afford warm-up compiles. The constraints: the package is compiled for a device type and software stack, and for the dynamic ranges declared at export. (Compiling needs a working compiler toolchain for the target; GPU packages need CUDA — not available on this machine.)

7. Quantisation with torchao

Quantisation stores numbers in fewer bits with scale factors (lm12). In current PyTorch it is done with torchao. The old torch.ao.quantization APIs still exist on 2.14 but warn on use: "torch.ao.quantization is deprecated and will be removed in 2.10. For migrations of users: 1. Eager mode quantization (torch.ao.quantization.quantize, torch.ao.quantization.quantize_dynamic), please migrate to use torchao eager mode quantize_ API…" — a removal date that has already passed by version number, so treat the migration as overdue. The torchao README's examples:

from torchao.quantization import quantize_, Int4WeightOnlyConfig, Int8WeightOnlyConfig
quantize_(model, Int8WeightOnlyConfig())                    # int8 weights, bf16 activations
quantize_(model, Int4WeightOnlyConfig(group_size=32))       # int4 weights in groups of 32
from torchao.quantization import Float8DynamicActivationFloat8WeightConfig, PerRow
quantize_(model, Float8DynamicActivationFloat8WeightConfig(granularity=PerRow()))

quantize_ replaces the weights of matching nn.Linear layers in place with quantised tensor subclasses (pt1's "tensor subclasses" in action) that know how to run their matmul. Which config to use depends on where time goes:

  • Weight-only int8 or int4 — weights stored small, dequantised inside the matmul, activations in bf16. Helps memory-bound workloads (small-batch LLM decoding), where step time ≈ weight bytes ÷ bandwidth: int4 moves roughly a quarter of bf16's bytes. Group-wise scales (one per 32–128 weights) keep 4-bit accuracy acceptable.
  • Dynamic activation + weight quantisation (int8 or float8) — both operands of the matmul in low precision, using faster tensor-core math. Helps compute-bound workloads: large batches, prefill, encoders. The README reports, for example, 1.5–1.6× speed-ups for float8 dynamic quantisation of a 27B model on H100 with preserved quality.
  • Quantisation-aware training — torchao's QAT configs insert fake quantisation during fine-tuning (prepare), then convert, recovering accuracy that post-training quantisation loses, typically for aggressive schemes on small models or mobile.

Always re-measure accuracy on a real evaluation (not only perplexity) and speed at your batch sizes; a 4-bit model can be slower than bf16 at large batch if its kernels dequantise inefficiently.

8. Handing a model to a serving stack

For LLMs, the common destination is a dedicated serving engine — vLLM, SGLang, TensorRT-LLM — that implements the architecture itself with paged KV caches, continuous batching, CUDA graphs and fused kernels. What they need from you: weights in safetensors with the architecture's standard tensor names (pt8), the model config (layers, heads, KV heads, RoPE parameters, vocabulary), tokenizer files and chat template, generation settings (stop tokens, maximum context), and the precision or quantisation format. A custom architecture means implementing it in the engine's model framework. For other models — classifiers, embedders, rankers — a lightweight service (a FastAPI or gRPC process, or Triton Inference Server) around an eager, compiled, exported or AOTInductor model, with dynamic batching, is typical. Whichever you choose, write the contract down: input shapes and maximums, precision, expected latency at given batch sizes, and the evaluation numbers the served model must reproduce.

9. Exporting a model with a cache: decode as a pure function

Generative models are the hardest to export because generation is a Python loop with growing state. The pattern that works is to export one decode step as a pure function: inputs are the new token ids, their positions, and preallocated cache tensors of fixed maximum length; outputs are logits and the updated caches. Inside, the attention reads only the valid part of the cache through a mask built from the position (pt10), so every shape is static except perhaps the batch dimension. The generation loop — sampling, stopping criteria, appending tokens — stays in the host program (Python, C++ or the serving engine) and calls the exported step repeatedly. Prefill is exported separately with a dynamic sequence dimension. This split mirrors what serving engines do internally and is what makes ahead-of-time compilation and CUDA graphs possible for decoding.

10. A checklist before shipping an exported or quantised model

Before a model leaves your hands, run a short, scripted acceptance test. Outputs match the reference: the exported or quantised model against the eager bf16 model on a fixed set of inputs, within a tolerance you chose deliberately (tight for export, task-metric-based for quantisation). Shapes: inputs at the minimum, a middle value and the maximum of every declared dynamic dimension run successfully, and one outside the range is rejected. Performance: latency and throughput at the batch sizes the service will use, measured with proper GPU timing (pt12), recorded alongside the hardware and software versions. Artefacts: the weights (safetensors), the exported or compiled package, tokenizer and config, and the evaluation results are versioned together. Each check takes minutes and each catches a class of failure that otherwise appears only in production.

11. Measuring inference properly

Inference benchmarks are easy to get wrong in the same ways as training benchmarks (pt12) and a few more. Warm up first: the first requests pay for CUDA context creation, cuDNN and cuBLAS heuristics, allocator growth, and compilation or CUDA-graph capture if used. Time with synchronisation or CUDA events. Report distributions, not averages: users experience p95 and p99 latency, and batching policies that improve the mean can hurt the tail. Separate the phases for LLMs: time to first token (prefill) and time per output token (decode) behave differently with prompt length and batch size. Measure under realistic load — a closed loop that sends the next request only when the previous returns hides queueing, while an open loop with arrival rates from production shows how latency grows as the server saturates. And record the configuration — model, precision, quantisation, batch policy, hardware, driver and library versions — because a benchmark without them cannot be compared next month.

12. Precision choices beyond bf16

bf16 is the default serving precision on modern GPUs because it needs no calibration and rarely changes outputs meaningfully. fp16 works for most models trained in bf16 but can overflow in models with large activations, so check for infinities in a validation pass. Float8 weights and activations, on GPUs with float8 tensor cores, roughly double matmul throughput again and halve weight memory relative to bf16; they need per-tensor or per-row scales chosen from the data (dynamic, computed per batch, or static, calibrated once), and accuracy must be verified per model. Int8 and int4 weight-only formats trade a little accuracy for large memory savings, as section 7 described. A useful mental model: each halving of bits halves memory and memory-bound time, while compute-bound speed improves only if the hardware has native arithmetic for that format.

What export guarantees, and the role of guards

An ExportedProgram is sound only under the assumptions recorded while tracing: input shapes within the range constraints, dtypes and devices as traced, and the branches the trace took. Export makes those assumptions explicit — the range constraints you saw, and run-time assertions in the unlifted module — so the program refuses inputs that would invalidate them. This is the same guard mechanism torch.compile uses (pt12), but where compile can fall back by recompiling, an exported artefact cannot, so failing loudly is the only safe behaviour. Designing a model for export means avoiding hidden assumptions: Python constants that should be inputs, branches on shapes that could vary, and module state read at trace time.

Weights, state and mutation in exported programs

Because parameters and buffers are lifted to inputs, an ExportedProgram separates computation from state. That enables swapping weights without re-exporting (fine-tuned variants of one architecture), sharing weights across programs, and quantisation passes that rewrite the graph. Buffers mutated during forward — a KV cache, running statistics — appear as explicit outputs that the runtime writes back, which makes stateful inference such as decoding explicit rather than hidden in module attributes. Export a decode step with a preallocated, static cache (pt10) and a position input, and the program is a pure function of (token, position, cache, weights) — exactly what ahead-of-time compilation and CUDA graphs need.

Why quantisation speed depends on the regime

A matmul of a (B × C) activation by a (C × C) weight does 2BC² operations and, at batch 1, reads C² weights: about 2 operations per weight byte in bf16 — far below the hundreds of operations per byte a GPU can do, so it is memory-bound, and halving or quartering weight bytes speeds it up nearly proportionally. At batch 256 the same weights serve 256 rows, the arithmetic intensity rises 256-fold, and the matmul becomes compute-bound: now what matters is how fast the tensor cores can multiply, which favours formats with native tensor-core support (bf16, float8, int8) and penalises formats that must be dequantised to bf16 first (int4 weight-only, unless the kernel overlaps dequantisation cleverly). This is the roofline argument from gpu2 applied to quantisation, and it is why the same model may want weight-only int4 for a chat endpoint at small batch and float8 for an offline batch job.

Accuracy checks that catch real problems

Quantisation and export can both change outputs. The checks that matter: compare logits or outputs on a fixed evaluation set against the bf16 eager model, per layer if needed (the error usually concentrates in a few layers with outlier activations, which is why some schemes keep those layers in higher precision); measure task metrics, not only perplexity, because small perplexity changes can hide large drops on specific tasks; and test edge inputs — maximum length, unusual tokens, batch sizes at the ends of the declared ranges. For generative models, compare greedy outputs token by token on a set of prompts; divergence after the first few tokens is expected with quantisation, but systematic quality drops are not.

Mobile and edge: ExecuTorch

For phones and embedded devices, PyTorch's path is ExecuTorch, which consumes programs captured by torch.export, lowers them through delegate backends for specific hardware (mobile GPUs, NPUs, optimised CPU kernels), and runs them with a small C++ runtime. torchao's README cites a quantised 4B-parameter model running on an iPhone 15 Pro through ExecuTorch with int8 activations and int4 weights. The constraints are tighter — memory in single-digit gigabytes, integer-friendly hardware, no Python — which is why export-compatibility and quantisation-aware training matter most here.

Static versus dynamic: why serving likes fixed shapes

Every runtime optimisation that removes per-request work — CUDA graphs, ahead-of-time compiled kernels specialised for sizes, preallocated memory pools — works best with a small set of known shapes. Serving systems therefore impose them: they pad or bucket batch sizes to a few values (1, 2, 4, 8, 16, …), capture a CUDA graph per bucket, preallocate KV-cache memory in fixed-size pages rather than per-request tensors, and cap sequence lengths. The design question for a model you hand over is which of its dimensions can be fixed without hurting users, and which must stay dynamic; answering it explicitly is part of a good export.

Quantising the KV cache

For long-context or high-concurrency serving, the KV cache, not the weights, dominates memory (pt10: about 0.5 MB per token for a 32-layer, 32-head model in bf16). Storing keys and values in 8 bits halves it, doubling the number of concurrent tokens that fit, and reduces the bytes read per decode step. The risk is precision loss in attention scores, especially for keys with outlier channels; engines typically use per-head or per-channel scales and keep the most recent tokens in higher precision. As with weight quantisation, the decision is empirical: measure long-context task quality, not just perplexity on short inputs.

Speculative decoding, seen from PyTorch

Decode at small batch wastes the GPU's arithmetic because each step produces one token per sequence. Speculative decoding (lm13) uses a cheap draft — a small model, extra heads, or n-gram lookup — to propose several tokens, then runs the large model once on all of them as a short chunk, accepting the longest prefix that matches what the large model would have produced (with a sampling correction that keeps the output distribution exact). In PyTorch terms it is a prefill-like chunk of T new queries attending to a cache, which is exactly the lower-right-aligned mask case from pt10 and a dynamic-shape case for export and CUDA graphs (pt12). The speed-up depends on the acceptance rate: if the large model accepts on average three drafted tokens per verification step, decoding takes roughly a third as many large-model steps.

What changes with mixture-of-experts and other irregular models

Models whose computation depends on the data — mixture-of-experts layers routing tokens to a few experts, early-exit networks — are harder to export and to batch. Routing is data-dependent control flow, which torch.export handles only if expressed with operators that compute all paths or with captured control flow, and expert computation per token varies with the batch, so the step time depends on how evenly tokens spread across experts. Serving engines implement such layers with grouped matmul kernels that process all experts' token groups in one launch, and with expert parallelism across GPUs. For an interview, the key point is that sparsity reduces FLOPs per token but not the memory needed to hold all experts' weights, so memory, not compute, usually sets the hardware requirement.

Calibration data for static quantisation

Static schemes that quantise activations with fixed scales need a calibration set: a few hundred representative inputs run through the model while observers record activation ranges, from which scales are chosen. The calibration set must look like production traffic — the same languages, lengths and domains — because scales fitted to short English prompts clip the activations of long code inputs, and the accuracy drop appears only on that traffic. Outliers are the other trap: a few channels with very large activations (common in transformer residual streams) force a large scale that wastes precision for every other channel, which is why per-channel scales, outlier-aware methods and keeping sensitive layers in higher precision exist. Dynamic quantisation sidesteps calibration by computing scales per batch at run time, at a small cost per step.

Failure mode: export works, production inputs fail

Symptom: the exported model rejects real requests with guard failures. Causes: dynamic ranges declared too narrowly (maximum sequence length lower than real traffic), a shape-dependent branch that narrowed the range, or a dimension left static because it was not declared dynamic (the traced example's size becomes the only valid size). Prevention: declare every variable dimension explicitly with realistic minimum and maximum values, export with an example in the middle of the range, and test the exported artefact at the extremes before shipping.

Failure mode: quantised model slower or worse

Slower: the workload is compute-bound at the serving batch size and the quantised kernel dequantises inefficiently; or quantised kernels are not available for the GPU and a slow fallback runs. Worse: aggressive quantisation (4-bit without groups, activation quantisation with outliers), or evaluation on the wrong metric. Prevention: benchmark speed at production batch sizes, evaluate on task metrics, and keep a bf16 baseline in the same harness.

Failure mode: train/serve skew

Symptom: offline metrics are good, production quality is not. Causes: different preprocessing in the service (tokenizer version, normalisation, image resizing), different precision, dropout left on (no eval()), a different maximum length truncating inputs, or batching that pads in a way the model never saw. Prevention: run the serving path on the validation set and compare with the training path's outputs; log inputs and outputs from production samples and replay them offline.

Failure mode: unmaintained serving dependencies

TorchServe's README states that the project "is no longer actively maintained… there are no planned updates, bug fixes, new features, or security patches. Users should be aware that vulnerabilities may not be addressed." Services built on it carry that risk. The same scrutiny applies to any serving dependency: check maintenance status, pin versions, and prefer formats (safetensors, ONNX, exported programs) that keep you portable between runtimes.

What to monitor in production inference

Latency percentiles (p50, p95, p99) by request size, throughput, batch size actually achieved, GPU memory (especially KV cache usage for LLMs), queue length, error rates including guard failures and timeouts, and — sampled — output quality against a reference. For LLMs, time to first token (dominated by prefill) and inter-token latency (decode) are reported separately because they depend on different bottlenecks.

Rolling out a new model version

A new checkpoint, quantisation or export path should reach users gradually. Shadow traffic first: run the new model on copies of real requests without returning its outputs, comparing latency, errors and output agreement with the current model. Then a canary: send a small percentage of real traffic to it, watch the monitoring from the previous section and business metrics, and widen in steps. Keep the previous artefact deployable for a fast rollback, which is easier when artefacts (weights, exported packages, tokenizer, config) are immutable and versioned together. These are ordinary deployment practices, but ML adds one twist: a new model can be "healthy" by every system metric while its outputs are worse, so output-quality checks belong in the rollout gates, not just in offline evaluation.

Cost per request, worked

A rough cost model ties this lesson together. A GPU at $4 an hour serving a 7B model in bf16 at an achieved 2,000 output tokens per second across all sequences produces 7.2 million tokens an hour, so about $0.56 per million output tokens before overheads. Doubling throughput with better batching or int4 weights halves that; running at 30% average utilisation because traffic is spiky triples it. That is why serving teams care as much about autoscaling, batching policy and utilisation as about kernel speed.

import torch, torch.nn as nn
from torch.export import export, Dim

class M(nn.Module):
    def __init__(self): super().__init__(); self.l = nn.Linear(8, 4)
    def forward(self, x): return self.l(x).relu()

m, x = M().eval(), torch.randn(4, 8)
ep = export(m, (x,), dynamic_shapes={"x": {0: Dim("batch", min=1, max=64)}})
print(ep.graph_module.code)
print("ranges:", ep.range_constraints)
print("batch 16:", ep.module()(torch.randn(16, 8)).shape)
try: ep.module()(torch.randn(100, 8))
except Exception as e: print("batch 100 rejected:", str(e)[:60])
torch.export.save(ep, "m.pt2"); print("reloaded:", torch.export.load("m.pt2").module()(x).shape)

class ShapeBranch(M):
    def forward(self, x): return self.l(x).relu() if x.shape[0] > 2 else self.l(x)
try: export(ShapeBranch().eval(), (x,), dynamic_shapes={"x": {0: Dim("batch", min=1, max=64)}})
except Exception as e: print("shape branch:", str(e).splitlines()[0][:70])

class ValueBranch(nn.Module):
    def forward(self, x): return x * 2 if x.sum() > 0 else x - 1
try: export(ValueBranch(), (x,))

Find the bug: an inference service that is slow, wrong and fragile

This service wraps a fine-tuned text classifier. Latency is high, results differ slightly between identical requests, memory grows under load, and a deployment to a C++ service failed because "export didn't work". Find the bugs.

model = load_model().cuda()                    # trained with dropout 0.1

def predict(texts):                            # called once per request, one text each
    ids = tokenizer(texts, padding="max_length", max_length=512, return_tensors="pt")
    out = model(ids["input_ids"].cuda(), ids["attention_mask"].cuda())
    probs = out.softmax(-1)
    if probs.max() < 0.5:                      # low-confidence fallback
        return "unknown"
    return LABELS[probs.argmax().item()]

ep = torch.export.export(model, (ids["input_ids"], ids["attention_mask"]))
Answer

Bug 1 — no eval() and no inference_mode(). Dropout is active, so identical requests give slightly different results; autograd records a graph for every request, raising memory and latency. Fix: model.eval() once at load, and wrap predict's body in torch.inference_mode().

Bug 2 — one request at a time, padded to 512. Each call runs a batch of one, padded to 512 tokens even if the text has 20 — wasting more than 95% of the compute on padding and leaving the GPU mostly idle. Fix: batch concurrent requests (dynamic batching with a few milliseconds of wait), pad to the longest in the batch or to a few bucket lengths, and run bf16.

Bug 3 — the export call is wrong in three ways. The model is exported in training mode (dropout in the graph); no dynamic shapes are declared, so the program accepts only batch 1 and length 512 exactly; and if the confidence check were inside the model it would be a value-dependent branch. Fix: export the model in eval mode with dynamic_shapes declaring batch and sequence dimensions with realistic ranges, keep the confidence logic outside the exported graph (or express it with torch.where), and test the artefact at the extremes of the ranges.

Smaller issues: probs.max() < 0.5 and .item() synchronise per request (acceptable at the end of a request, but do it once per batch); and the tokenizer and labels must be versioned with the model to avoid train/serve skew.

Estimate: int4 or bf16 for this endpoint?

A 13B-parameter chat model runs on one 80 GB GPU with about 3 TB/s of memory bandwidth. Most traffic is batch 1–4 decoding. Estimate decode tokens per second per sequence in bf16 and with int4 weight-only quantisation, and say what else changes.

Answer

bf16 weights: 26 GB. Each decode step reads them once: 26 GB ÷ 3 TB/s ≈ 8.7 ms, so about 115 tokens per second per sequence at batch 1 (ignoring KV-cache reads and overhead). Int4 with group scales: roughly 26/4 ≈ 6.5 GB plus scales, about 7 GB; ≈ 2.3 ms per step, up to about 430 tokens per second — in practice less, because dequantisation and the KV cache cost time, so perhaps 2–3× faster. Memory freed (about 19 GB) goes to KV cache, allowing more concurrent conversations. Accuracy must be re-checked on the chat evaluation set; for batch 64 offline jobs the advantage shrinks or reverses as decode becomes compute-bound.
