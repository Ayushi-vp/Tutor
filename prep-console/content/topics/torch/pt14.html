Sooner or later a PyTorch engineer meets JAX: a research paper's reference code, a model trained on TPUs, a team that uses it for large-scale pretraining, or an interview question — "you know PyTorch; how would this look in JAX?", or simply "PyTorch or JAX, and why?". Reading JAX code with PyTorch instincts goes badly. You try to update an array in place and get an error. You add a print inside a training step and it prints once, during the first call, never again. You call a random function twice and get the same numbers. You put an if loss > 5: inside a function and get a cryptic message about concretisation. You look for loss.backward() and optimizer.zero_grad() and find neither.

None of this is arbitrary. JAX is built on one design decision that PyTorch did not make: programs are pure functions of their inputs, transformed by composable operations — jit to compile, grad to differentiate, vmap to vectorise, and sharding to distribute. PyTorch is eager and mutable: tensors change, modules hold state, autograd records as you go (pt3), and compilation was added later through torch.compile (pt12). JAX is functional and compiler-first: state is passed in and returned, randomness is an explicit key, and every performance-critical function is traced and compiled by XLA. Once you see JAX through that lens, its rules become predictable, and you can translate fluently between the two.

The two frameworks have also been converging. PyTorch's torch.func offers JAX-style grad and vmap over functions of parameters; its DTensor and device meshes (pt11) describe sharding the way JAX's meshes and PartitionSpecs do; and on the JAX side, Flax NNX — released in 2024 and now the main Flax API, succeeding Linen — gives PyTorch-like modules with ordinary Python reference semantics. Knowing both lets you reason about the ideas rather than the syntax.

This lesson covers JAX for someone fluent in PyTorch: pure functions and immutable arrays, how jit traces and what breaks it, grad and vmap, explicit PRNG keys, pytrees, a complete training step with optax, sharding with meshes, Flax NNX versus Linen, and a structured answer to "PyTorch or JAX?". JAX is not installed on this machine, so code is marked "Needs JAX"; APIs were checked against the current JAX (0.11.2) and Flax (0.12.10) documentation in October 2026.

Think of PyTorch as a workshop where tools change the material in place: you pick up a tensor, modify it, keep a module on the bench that remembers its weights, and the autograd notebook writes down every action so it can be replayed backwards. Think of JAX as a factory blueprint system: every station is a pure function that receives materials and returns new ones, never altering what it received. Because each station is pure, the factory can do powerful things to the blueprints themselves:

  • jit — read the blueprint once with dummy materials of the right shape (tracing), and build a specialised, optimised production line (an XLA program) that runs without consulting the blueprint again.
  • grad — derive a new blueprint that computes how the output changes with the input — the gradient — automatically.
  • vmap — turn a blueprint for one item into one for a whole batch, without editing it.
  • sharding — spread the production line over many machines by annotating how each material is split.

These transformations compose — jit(vmap(grad(f))) is meaningful and efficient — precisely because the functions are pure. The price is that everything a function depends on must be an input: parameters, optimiser state, random keys, even the "training" flag. Nothing is hidden in a module or in global state.

A quick translation table helps while reading JAX code for the first time. A PyTorch tensor is a JAX array (immutable). Module parameters are a pytree of arrays you pass in (or, in Flax NNX, attributes of a module again). Autograd and .grad become jax.grad returning gradients. The optimiser object becomes an optax transformation plus an explicit optimiser-state pytree. torch.manual_seed becomes a key you split. model.train()/eval() becomes an argument. torch.compile becomes jax.jit, and DDP/FSDP become shardings on arrays. Every row is the same idea with the hidden state made explicit, and every row has a corresponding bug when the explicit state is forgotten: unassigned updates, reused keys, stale constants captured at trace time.

Where the factory analogy breaks: JAX does not literally copy every array on every operation. Under jit, the XLA compiler sees the whole program and reuses buffers whenever an old value is dead, so functional code compiles to memory-efficient, in-place machine code. The purity is a property of the code you write and of what the compiler may assume, not of what the hardware does.

If you remember one sentence: JAX code is pure functions over immutable arrays and explicit keys, transformed by jit, grad, vmap and sharding; everything PyTorch hides in objects — parameters, gradients, optimiser state, randomness, mode flags — is an argument and a return value.

1. Arrays and pure functions

jax.numpy (imported as jnp) mirrors NumPy: jnp.zeros, jnp.dot, @, broadcasting (the same rules as pt2), reductions. JAX arrays live on a device (CPU, GPU or TPU) and are immutable:

import jax, jax.numpy as jnp                      # Needs JAX
x = jnp.arange(5.0)
# x[0] = 10.0                                     # TypeError: JAX arrays are immutable
x = x.at[0].set(10.0)                             # returns a new array
x = x.at[1:3].add(1.0)                            # functional "in-place" ops: set, add, mul, min, max

A pure function returns a value that depends only on its arguments and has no side effects: no mutation of inputs or globals, no printing, no reading of hidden state. JAX's transformations assume purity. If a function reads a global variable, jit captures its value at trace time as a constant and will not see later changes; if it appends to a list, the append happens once, during tracing. These are not bugs in JAX — they are what tracing a pure function means.

Two behaviours differ from NumPy and PyTorch in ways that matter for debugging. Out-of-bounds indexing does not raise: under jit there is no way to raise an error from inside a compiled kernel, so gathers clamp indices and scatters drop out-of-range updates. And the default floating type is float32 (64-bit types must be enabled explicitly), which is what you want for ML and different from NumPy's float64 default.

2. jit: tracing and compiling

@jax.jit
def f(x, w):
    print("tracing!", x.shape)          # runs only while tracing
    return jnp.tanh(x @ w)

f(jnp.ones((4, 8)), jnp.ones((8, 2)))   # prints "tracing! (4, 8)", compiles, runs
f(jnp.ones((4, 8)), jnp.ones((8, 2)))   # no print: cached compiled code
f(jnp.ones((16, 8)), jnp.ones((8, 2)))  # new shape: traces and compiles again

On the first call, jit runs your Python with tracers — abstract values that carry a shape and dtype but no data — and records every jnp operation into a jaxpr, JAX's small intermediate language (jax.make_jaxpr(f)(x, w) prints it). XLA compiles the jaxpr into fused kernels for the target device, and the result is cached by the input shapes and dtypes (and static arguments). Later calls with the same signature skip Python entirely. That explains the three rules every JAX user learns:

  1. Side effects happen at trace time. A print runs once per compilation. Use jax.debug.print("{}", x) to print runtime values from inside compiled code.
  2. Python control flow cannot depend on traced values. if x.sum() > 0: needs a concrete boolean, but a tracer has no value; JAX raises a concretisation error. Use jnp.where (both branches computed), jax.lax.cond (one branch executed), jax.lax.while_loop or jax.lax.scan (loops compiled into the graph). Control flow on shapes or on static arguments (static_argnums) is fine, because those are known at trace time.
  3. New shapes mean new compilations. Variable sequence lengths retrace every time; pad or bucket them, exactly as with torch.compile recompiles (pt12).

Compared with torch.compile: both trace and cache per input signature, and both specialise on shapes. The difference is the fallback: torch.compile splits the graph and runs unsupported code eagerly (a graph break); inside jax.jit there is no eager fallback — the whole function must be traceable. In practice, JAX code is written from the start to be traceable, while PyTorch code is written eagerly and compiled afterwards.

3. grad and value_and_grad

def loss(params, x, y):                            # Needs JAX
    pred = x @ params["w"] + params["b"]
    return jnp.mean((pred - y) ** 2)

grad_fn = jax.grad(loss)                           # gradient w.r.t. the first argument
g = grad_fn(params, x, y)                          # same structure as params: {"w": ..., "b": ...}
l, g = jax.value_and_grad(loss)(params, x, y)      # loss value and gradient together

jax.grad(f) returns a new function that computes the gradient of the scalar-valued f with respect to its first argument (or the arguments named in argnums). It is reverse-mode automatic differentiation (pt3) packaged as a transformation: no graph is recorded on tensors, no .grad attributes exist, nothing accumulates. The gradient is a return value with the same nested structure as the parameters. Consequences for a PyTorch user: there is no zero_grad, because nothing accumulates; gradient accumulation means adding gradient pytrees yourself (or using optax's MultiSteps); and higher-order derivatives are just nested transformations — jax.grad(jax.grad(f)), jax.hessian, jax.jvp for forward mode.

4. vmap: vectorising without batch axes

def predict_one(params, x):                        # x: (8,) — one example
    return jnp.tanh(x @ params["w"] + params["b"])

batched = jax.vmap(predict_one, in_axes=(None, 0)) # params shared, x mapped over axis 0
batched(params, jnp.ones((32, 8)))                 # (32, 1)

per_example_grads = jax.vmap(jax.grad(loss), in_axes=(None, 0, 0))(params, xs, ys)
# each leaf gains a leading batch axis: per_example_grads["w"].shape == (32, 8, 1)

vmap takes a function written for one example and produces one that works on a batch, by pushing the batch axis through every primitive operation. You write simpler code (no batch dimension to thread through, the source of many pt2 bugs), and you get things that are awkward in plain PyTorch, such as per-example gradients for differential privacy or influence estimates. PyTorch's torch.func.vmap and torch.func.grad are direct counterparts and work on modules through torch.func.functional_call (pt4).

5. Explicit randomness: PRNG keys

key = jax.random.key(0)                            # typed key (new style)
key, k1, k2 = jax.random.split(key, 3)             # derive independent keys
w = jax.random.normal(k1, (8, 2)) * 0.02
mask = jax.random.bernoulli(k2, 0.9, (32, 8))      # e.g. a dropout keep-mask
jax.random.normal(k1, (2,)) == jax.random.normal(k1, (2,))   # always True: same key, same numbers

PyTorch has a global generator that advances invisibly every time you sample (pt6). JAX random functions are pure: a key fully determines the output, so reusing a key reproduces the same numbers — the classic bug is passing the same key to every layer's dropout, making their masks identical. Keys are split to derive independent streams and folded with data (jax.random.fold_in(key, step)) to derive a per-step key without threading state. The JAX documentation distinguishes new-style typed keys created with jax.random.key() from legacy uint32 key arrays created with jax.random.PRNGKey(), with converters between them; new code uses key(). The payoff of explicit keys is reproducibility under transformations: a vmapped or sharded random function produces the same numbers regardless of how it is batched or which device runs it, something hidden global state cannot promise.

6. Pytrees: parameters as plain data

A pytree is any nesting of lists, tuples, dicts (and registered classes) with arrays at the leaves. JAX transformations accept and return pytrees, which is how a model with hundreds of parameter arrays fits through grad and jit:

params = {"layer1": {"w": w1, "b": b1}, "layer2": {"w": w2, "b": b2}}
grads = jax.grad(loss)(params, x, y)                     # same structure
params = jax.tree.map(lambda p, g: p - 0.01 * g, params, grads)   # SGD, leaf by leaf
n_params = sum(p.size for p in jax.tree.leaves(params))

Pytrees replace what nn.Module registration does in PyTorch (pt4): the structure is the registry. Optimiser states, model states and sharding specifications are pytrees with the same shape as the parameters, which makes per-parameter policies (no weight decay on biases) a matter of mapping over the tree.

7. A complete training step with optax

import optax                                             # Needs JAX + optax
tx = optax.chain(optax.clip_by_global_norm(1.0), optax.adamw(3e-4, weight_decay=0.1))
opt_state = tx.init(params)

@jax.jit
def train_step(params, opt_state, key, x, y):
    def loss_fn(p):
        pred = model_apply(p, x, key=key, train=True)     # dropout uses key
        return jnp.mean(optax.softmax_cross_entropy_with_integer_labels(pred, y))
    loss, grads = jax.value_and_grad(loss_fn)(params)
    updates, opt_state = tx.update(grads, opt_state, params)
    params = optax.apply_updates(params, updates)
    return params, opt_state, loss

for step, (x, y) in enumerate(batches):
    key, sub = jax.random.split(key)
    params, opt_state, loss = train_step(params, opt_state, sub, x, y)

Line by line against pt6's PyTorch loop: value_and_grad replaces forward, backward and the .grad fields; optax gradient transformations replace the optimiser object and clip_grad_norm_ (clipping is just another transformation in the chain); opt_state is passed in and returned rather than living inside an optimiser; the learning-rate schedule is a function of the step count inside optax; the dropout key is split every step outside the jitted function and passed in. There is no zero_grad and no model.train(): the mode is an argument. Adding donate_argnums=(0, 1) to jax.jit lets XLA write the new parameters and optimiser state into the old buffers, roughly halving peak memory for them — the counterpart of PyTorch's in-place optimiser updates.

8. Sharding: meshes, PartitionSpecs and automatic parallelism

from jax.sharding import NamedSharding, PartitionSpec as P   # Needs JAX + several devices
mesh = jax.make_mesh((4, 2), ("data", "model"))            # 8 devices as a 4 × 2 grid
x = jax.device_put(x, NamedSharding(mesh, P("data", None)))          # batch split 4 ways
w = jax.device_put(w, NamedSharding(mesh, P(None, "model")))         # columns split 2 ways
y = jax.jit(lambda x, w: x @ w)(x, w)                                # result sharded ("data", "model")

A mesh names the axes of a device grid. A PartitionSpec says, for each array dimension, which mesh axis splits it (None means replicated). When a jitted function receives sharded inputs, the XLA compiler propagates shardings through every operation and inserts the collectives needed — this partitioner (GSPMD) is what makes data, tensor and fully-sharded parallelism mostly a matter of annotations. Data parallelism is "shard the batch over 'data', replicate parameters", and gradients are all-reduced automatically; FSDP-style training shards parameters over 'data' too, and XLA inserts all-gathers and reduce-scatters (pt11's patterns, chosen by the compiler). When you want explicit control, jax.shard_map runs a function per device on its local shard with collectives you call yourself (jax.lax.psum, all_gather), much like writing DDP's all-reduce by hand. PyTorch's DTensor and device mesh express the same placements (Shard, Replicate); the difference is that in JAX the compiler schedules the communication for the whole program.

9. Flax NNX: modules again

Writing every model as nested dicts of arrays is laborious, so JAX has neural-network libraries. Flax's current API, NNX, which the Flax README says was "released in 2024" and "evolved from the Flax Linen API", adds "first class support for Python reference semantics": modules are ordinary Python objects that own their parameters, much like nn.Module.

from flax import nnx                                      # Needs JAX + Flax
class MLP(nnx.Module):
    def __init__(self, din, dmid, dout, *, rngs: nnx.Rngs):
        self.linear1 = nnx.Linear(din, dmid, rngs=rngs)
        self.dropout = nnx.Dropout(rate=0.1, rngs=rngs)
        self.linear2 = nnx.Linear(dmid, dout, rngs=rngs)
    def __call__(self, x):
        return self.linear2(nnx.gelu(self.dropout(self.linear1(x))))

model = MLP(8, 32, 1, rngs=nnx.Rngs(0))
optimizer = nnx.Optimizer(model, optax.adamw(1e-3), wrt=nnx.Param)

@nnx.jit
def train_step(model, optimizer, x, y):
    def loss_fn(model):
        return jnp.mean((model(x) - y) ** 2)
    loss, grads = nnx.value_and_grad(loss_fn)(model)
    optimizer.update(model, grads)                        # updates the model in place
    return loss

This looks almost like PyTorch: a module class, layers as attributes, an optimiser that updates the model in place, random streams owned by the module (nnx.Rngs) rather than threaded by hand. Underneath, nnx.jit and nnx.value_and_grad split the module into a pure state pytree and a static graph definition, apply JAX's transformations, and merge the results back — so the functional machinery is still there, hidden behind reference semantics. Linen, the earlier API, separates a module's definition from its parameters explicitly: params = model.init(key, x) then model.apply(params, x). Large existing codebases use Linen, which is now documented on its own site; new code uses NNX.

10. PyTorch or JAX, and why?

A useful answer is structured, not tribal. Compare along five axes:

PyTorchJAX
Programming modelEager, mutable, objects; compile added with torch.compilePure functions, immutable arrays; compile (jit) central
DebuggingOrdinary Python debugging in eager modeTracing semantics; jax.debug tools; errors at trace time
EcosystemMost open models, hubs, serving engines, quantisation tools, research codeStrong in large-scale TPU training and some research groups; smaller ecosystem
HardwareNVIDIA and AMD GPUs first-class; other accelerators via backendsTPUs first-class through XLA; GPUs supported
ScalingDDP, FSDP2, tensor/pipeline parallel APIs, DTensorShardings with compiler-scheduled collectives (GSPMD), shard_map

Then apply it to the situation. Fine-tuning and serving open models on GPUs: PyTorch, because the models, tools and engines are there. Training a large model from scratch on TPUs, or a team already fluent in functional style: JAX, because XLA on TPUs and sharding-by-annotation are its strengths. In both cases, team experience and existing code often outweigh benchmark differences, since both frameworks reach high hardware utilisation when used well. The concepts transfer: autograd and grad, torch.func and vmap, DTensor and NamedSharding, torch.compile and jit — a strong engineer can explain each pair's trade-offs, which is what the question is really testing.

11. The rest of a real training loop: accumulation, precision, checkpoints

Several things that PyTorch handles with wrappers or flags are ordinary functions in JAX. Gradient accumulation: optax.MultiSteps(tx, every_k_schedule=4) wraps an optimiser so updates are applied every fourth call, accumulating gradients in its state; or sum gradient pytrees yourself with jax.tree.map and divide — the same token-weighting care as pt6 applies. Mixed precision: there is no autocast context; you choose dtypes explicitly, typically keeping parameters in float32, casting them to bfloat16 for the forward computation, and computing losses and reductions in float32 (Flax layers take dtype for computation and param_dtype for storage). Because the cast is explicit, its placement is visible in the code — and so are mistakes. Checkpointing: parameters and optimiser state are pytrees, so saving them is saving a tree of arrays; the JAX ecosystem's Orbax library handles sharded, asynchronous checkpoints analogous to PyTorch's DCP (pt8), and the PRNG key and step count are saved like any other array. Data loading is outside JAX: pipelines built with tf.data, Grain or even a PyTorch DataLoader feed NumPy arrays into the jitted step, with the same throughput concerns as pt5.

12. The pt10 block, in Flax NNX

To see the translation at the scale of a real layer, here is pt10's pre-norm transformer block in Flax NNX (Needs JAX + Flax):

class Block(nnx.Module):
    def __init__(self, C, H, *, rngs: nnx.Rngs):
        self.H = H
        self.ln1, self.ln2 = nnx.LayerNorm(C, rngs=rngs), nnx.LayerNorm(C, rngs=rngs)
        self.qkv, self.proj = nnx.Linear(C, 3 * C, rngs=rngs), nnx.Linear(C, C, rngs=rngs)
        self.fc1, self.fc2 = nnx.Linear(C, 4 * C, rngs=rngs), nnx.Linear(4 * C, C, rngs=rngs)

    def __call__(self, x):                                   # x: (B, T, C)
        B, T, C = x.shape
        q, k, v = jnp.split(self.qkv(self.ln1(x)), 3, axis=-1)
        q, k, v = (t.reshape(B, T, self.H, C // self.H) for t in (q, k, v))   # (B, T, H, hs)
        y = jax.nn.dot_product_attention(q, k, v, is_causal=True)            # (B, T, H, hs)
        x = x + self.proj(y.reshape(B, T, C))
        return x + self.fc2(jax.nn.gelu(self.fc1(self.ln2(x))))

Three differences from the PyTorch version are worth noticing. The layout: JAX's dot_product_attention takes (batch, time, heads, head size), so there is no transpose to put heads before time and no contiguous() — memory layout is the compiler's business, not a stride question (pt1). The constructor takes an explicit rngs object for parameter initialisation instead of relying on a global seed. And there is no dropout_p if self.training line because this block has no dropout; with an nnx.Dropout layer, model.eval() (which NNX modules provide) switches it off, much as in PyTorch. The training step is then the NNX step from section 9; under nnx.jit the whole forward and backward pass, including the attention, is compiled by XLA as one program.

How grad and jit compose: everything is a jaxpr transformation

JAX's transformations are interpreters over the same traced representation. grad traces the function into a jaxpr, applies the reverse-mode rules of each primitive (each JAX primitive has a defined JVP, from which JAX derives the transpose for reverse mode), and returns a new function; vmap applies each primitive's batching rule; jit hands the jaxpr to XLA. Because each takes a function and returns a function, they nest in any order: jit(grad(f)) compiles the gradient computation as one program, which lets XLA fuse the forward and backward passes and decide what to recompute — comparable to what AOTAutograd plus Inductor do for torch.compile training (pt12). jax.checkpoint (also called remat) marks a function whose intermediates should be recomputed in the backward pass, the counterpart of PyTorch's activation checkpointing (pt7).

Loops: scan instead of Python for

A Python loop inside a jitted function is unrolled at trace time: a 96-layer transformer written as a Python loop over layers produces a jaxpr 96 times longer, with compile time to match. jax.lax.scan compiles the loop body once and iterates it, carrying state between iterations — the idiomatic way to write layer stacks (with parameters stacked along a leading axis), recurrent models and sampling loops. It is the functional counterpart of PyTorch's regional compilation of a repeated block (pt12), and it constrains the body to have the same shapes on every iteration.

Static and dynamic arguments

Arguments to a jitted function are traced unless marked static (static_argnums or static_argnames). Static arguments must be hashable, are part of the compilation cache key, and can be used in Python control flow — a train flag, a number of layers, a configuration object. Marking something static that changes often (a step number) recompiles every call; leaving something dynamic that Python code branches on raises a concretisation error. Choosing which is which is the main skill in writing jit-friendly code, and it mirrors the guard behaviour of torch.compile (pt12), where Python values read inside the compiled region become guards.

XLA versus Inductor, and custom kernels

JAX compiles through XLA, a whole-program compiler that fuses operations, plans memory and, with GSPMD, partitions programs across devices; PyTorch's Inductor generates Triton kernels for captured graphs. Both fuse memory-bound chains and call vendor libraries for large matmuls, so typical models reach similar utilisation; differences show up at the edges — compile time, support for dynamic shapes (XLA strongly prefers static ones), and how communication is scheduled. When the compiler is not enough, both offer a kernel language: JAX's Pallas lets you write custom kernels for GPUs and TPUs from Python, as Triton does for PyTorch (pt12), and libraries in both ecosystems ship hand-written FlashAttention-style kernels. Knowing that both stacks have the same three layers — a tracing front end, a fusing compiler, and an escape hatch for hand-written kernels — makes it easy to map performance discussions from one to the other.

Randomness under vmap and sharding

Explicit keys pay off most when computations are transformed. Under vmap, a function that draws random numbers from a key passed in unbatched draws the same numbers for every example — usually a bug; passing a batch of keys (jax.random.split(key, B), mapped with in_axes=0) gives each example its own stream. Under sharding, the question "which device draws which part of a random tensor?" has a defined answer: the random bits are a function of the key and the logical position, so a dropout mask over a sharded activation is the same no matter how many devices compute it. PyTorch's DTensor had to add special machinery (offsetting the RNG per shard, pt11) to give the same guarantee for sharded initialisation; in JAX it follows from the design.

Interoperating with PyTorch

Arrays can cross between the frameworks without copying through DLPack (torch.from_dlpack(jax_array) and jnp.from_dlpack(torch_tensor)) when they live on the same device. Weights move through formats both understand: safetensors files load into both (pt8), with parameter names and layouts mapped by a conversion script (PyTorch linear weights are (out, in), many JAX libraries store (in, out) — the same transpose trap as GPT-2's Conv1D weights in pt10). Mixed codebases are rare beyond such conversions; teams pick one framework for training and convert at the boundary to whatever the serving stack needs.

What PyTorch borrowed, and what JAX borrowed

The two ecosystems have converged on several ideas. PyTorch's torch.func (from the earlier functorch project) brought JAX-style composable grad, vmap, jvp and jacrev to PyTorch; DTensor and DeviceMesh adopted the mesh-and-placement model for sharding; torch.compile and torch.export introduced tracing with guards and single-graph capture. JAX's ecosystem, in turn, moved toward PyTorch-like ergonomics with Flax NNX's reference semantics and stateful modules. Understanding both through the common concepts — transformations over functions, sharding as placement, compilation with guards — matters more for a senior engineer than memorising either API.

Where the functional style shines in research

Some research patterns are markedly easier when models are pure functions of parameter pytrees. Ensembles: stack the parameters of ten models along a new axis and vmap the forward pass over it, training ten models in one compiled program. Meta-learning: differentiate through an inner training loop with grad of a function that itself calls grad, with no hooks or retained graphs to manage. Per-example gradient methods for privacy or data attribution: vmap(grad(loss)) as shown earlier. Hyperparameter sweeps over learning rates or regularisation strengths: vmap over a vector of hyperparameters. PyTorch can express all of these through torch.func, but in JAX they are the native idiom, which is one reason the framework is popular with research groups that do this kind of work.

Failure mode: silent recompilation

Symptom: a JAX training loop is much slower than expected and CPU usage spikes. Cause: retracing and recompiling on every step — variable batch or sequence shapes, a Python value that changes passed as a static argument, or a new Python object (for example a fresh closure) passed where a static argument is expected. Diagnose by logging compilations (jax.config.update("jax_log_compiles", True)) and by timing the first and later calls. Fix by padding to fixed shapes and keeping static arguments stable.

Failure mode: identical randomness

Symptom: dropout masks or augmentations repeat every step, or are identical across layers or devices. Cause: reusing a key instead of splitting it, or splitting once outside the loop. Fix: split a new subkey every step (or fold in the step number), and give each use its own key; Flax NNX's nnx.Rngs streams handle this inside modules.

Failure mode: errors at trace time that look like nonsense

Symptom: a ConcretizationTypeError or "TracerBoolConversionError" pointing at an if or int() in your code. Cause: Python needing a concrete value from a traced array inside jit. Fix: jnp.where, lax.cond, lax.while_loop, or making the argument static if it is genuinely configuration. The JAX "Common Gotchas" page (the "sharp bits") is the reference for these, and it is worth reading once in full before writing serious JAX.

Failure mode: out-of-memory without obvious reason

Symptom: a jitted step uses more memory than the PyTorch equivalent. Causes: no buffer donation, so old and new parameters and optimiser states coexist; a Python loop unrolled instead of lax.scan, which can keep more intermediates live; missing jax.checkpoint on large blocks; or JAX's default GPU memory preallocation (it reserves a large fraction of GPU memory at start-up, configurable with environment variables), which looks like usage in monitoring tools. Check the compiled program's memory analysis and donate the state arguments.

What teams actually do

In practice, framework choice is rarely revisited mid-project. Organisations training frontier-scale models on TPUs tend to use JAX end to end; organisations building on open models on GPUs tend to use PyTorch end to end, with JAX appearing in reference implementations from papers. The engineering skill that transfers is the mental model: state passed explicitly, compilation with guards, sharding as placement, and measurement before optimisation. An interviewer asking "PyTorch or JAX?" is usually checking that you can articulate those trade-offs calmly and connect them to the project's constraints.

Debugging tools you will need

Because jitted code runs as compiled programs, JAX provides specific tools. jax.debug.print prints runtime values from inside jit, vmap and grad; jax.debug.breakpoint() pauses with the runtime values available. jax.disable_jit() as a context manager runs everything eagerly, so ordinary Python debugging works — the first thing to try when a jitted function misbehaves, just as running a torch.compile model with backend="eager" isolates compiler problems (pt12). NaN hunting has a counterpart of PyTorch's anomaly mode (pt9): enabling the jax_debug_nans configuration option makes JAX re-run the failing operation without compilation and raise at the first NaN. And jax.experimental.checkify adds functional error checks (such as out-of-bounds indexing, which otherwise silently clamps) to jitted code. Learn these before you need them; the default behaviour of compiled code is to hide where things went wrong.

Migrating a team between frameworks

Occasionally a team does switch. The cost is rarely the model code — a transformer is a few hundred lines in either framework — but everything around it: data pipelines, checkpoint formats and conversion scripts, evaluation harnesses, distributed launch and fault tolerance, profiling habits, and the serving path. A sensible migration ports the evaluation first (so both implementations can be compared on identical inputs), then converts weights and checks logits match to a tight tolerance, then ports training and verifies loss curves match for a few thousand steps, and only then retires the old path. The checks are the same ones this track uses within PyTorch — parameter counts, loss at initialisation, overfitting one batch, exact output comparison — applied across the framework boundary.

Reading JAX code in a PyTorch interview

Even in a PyTorch-focused loop you may be handed JAX code to read — a paper's reference implementation, or a debugging exercise. Read it in this order: find the pure functions (apply or __call__, the loss, the step) and the state they take and return (params, optimiser state, keys); find where keys are split, and check each random use gets its own; find the jit boundaries and ask which arguments are static and whether shapes vary; find where updates are assigned, since an unassigned apply_updates or .at[].set is a silent no-op; and find the shardings, which tell you the parallelism strategy. Then translate each piece into the PyTorch concept from this track. Interviewers are not looking for JAX syntax recall; they want to see that you can map the ideas reliably.

Needs JAX (not installed in gpt_env; do not install it there). On a machine where you can install packages, use a fresh virtual environment with jax, flax and optax; CPU is enough. About 20 minutes. Save as pt14_lab.py.

import jax, jax.numpy as jnp, optax
key = jax.random.key(0)

# 1. jit traces once per shape
@jax.jit
def f(x):
    print("tracing", x.shape)
    return jnp.tanh(x).sum()
f(jnp.ones(3)); f(jnp.ones(3)); f(jnp.ones(4))      # prints twice: shapes (3,) and (4,)

# 2. control flow on traced values
def g(x):
    return jnp.where(x.sum() > 0, x * 2, x - 1)     # works under jit; a Python if would not
print(jax.jit(g)(jnp.array([1.0, -3.0])))

# 3. keys: same key, same numbers
k1, k2 = jax.random.split(key)
print(jax.random.normal(k1, (2,)), jax.random.normal(k1, (2,)), jax.random.normal(k2, (2,)))

# 4. linear regression with grad, optax and jit
kx, kw = jax.random.split(k2)
X = jax.random.normal(kx, (256, 3)); true_w = jnp.array([1.0, -2.0, 0.5]); y = X @ true_w
params = {"w": jnp.zeros(3)}
tx = optax.sgd(0.1); st = tx.init(params)
loss = lambda p, X, y: jnp.mean((X @ p["w"] - y) ** 2)
@jax.jit
def step(p, st, X, y):
    l, gr = jax.value_and_grad(loss)(p, X, y)
    up, st = tx.update(gr, st, p)
    return optax.apply_updates(p, up), st, l
for i in range(100): params, st, l = step(params, st, X, y)
print("learned w:", params["w"], "loss", l)

# 5. per-example gradients with vmap
pe = jax.vmap(jax.grad(loss), in_axes=(None, 0, 0))(params, X[:4, None], y[:4, None])
print("per-example grad shape:", pe["w"].shape)       # (4, 3)
  1. Step 1 prints "tracing" twice: once per new shape, not once per call.
  2. Step 2 returns [2, -6]; replace jnp.where with a Python if and read the concretisation error.
  3. Step 3: the first two vectors are identical, the third differs.
  4. Step 4 recovers w ≈ [1, −2, 0.5] with a loss near 0.
  5. Step 5 shows one gradient per example. Compare with torch.func.vmap(torch.func.grad(...)) in PyTorch.
Find the bug: a JAX training loop ported from PyTorch

A colleague ported a PyTorch training loop to JAX. It runs, but the loss barely improves, every step takes as long as the first, and dropout behaves identically every step. Find the bugs.

key = jax.random.key(0)
losses = []

@jax.jit
def train_step(params, opt_state, x, y, step):
    def loss_fn(p):
        logits = apply(p, x, dropout_key=key)                  # global key
        return cross_entropy(logits, y)
    loss, grads = jax.value_and_grad(loss_fn)(params)
    updates, opt_state = tx.update(grads, opt_state, params)
    optax.apply_updates(params, updates)                        # result discarded
    losses.append(loss)                                         # side effect
    if step % 100 == 0:
        print("step", step, loss)
    return params, opt_state

for step, (x, y) in enumerate(batches):                         # batches of varying length
    params, opt_state = train_step(params, opt_state, x, y, step)
Answer

Bug 1 — the update result is discarded. optax.apply_updates returns new parameters; arrays are immutable, so calling it without assigning changes nothing. The function returns the old params while opt_state advances — the model never learns (the loss "barely improves" only because of noise). Fix: params = optax.apply_updates(params, updates).

Bug 2 — the same dropout key every step. key is a global captured at trace time as a constant, so every step uses identical dropout masks. Fix: split a fresh subkey each step outside the jitted function and pass it as an argument.

Bug 3 — side effects and Python control flow inside jit. losses.append(loss) runs only during tracing and appends a tracer, not values; if step % 100 == 0 branches on step, a traced integer, which raises a concretisation error — unless step was passed in a way that made it static, in which case every new step value triggers a recompile. Fix: return the loss and log it outside; use jax.debug.print if you must print inside; do not pass the step count at all unless needed (and then as a traced array, never static).

Bug 4 — varying batch shapes. Batches of varying length cause a new trace and compilation for every new shape, so many steps take as long as the first. Fix: pad or bucket to a few fixed lengths and drop or pad the last batch. Bonus improvement: add donate_argnums=(0, 1) so new parameters and optimiser state reuse the old buffers.

Translate: PyTorch to JAX, concept by concept

Give the JAX (or Flax NNX) counterpart of each: loss.backward(), optimizer.zero_grad(), torch.manual_seed(0), model.eval(), torch.compile(model), DistributedDataParallel, torch.utils.checkpoint.

Answer

loss.backward() → jax.value_and_grad(loss_fn)(params, …) returning gradients; zero_grad() → nothing (gradients are returned, not accumulated); torch.manual_seed(0) → key = jax.random.key(0), then split per use; model.eval() → a train/deterministic argument passed to the apply function (in NNX, model.eval() exists and sets that flag on modules such as Dropout); torch.compile → jax.jit (with no eager fallback); DistributedDataParallel → shard the batch over a mesh axis with NamedSharding(mesh, P("data")), replicate parameters, and let jit insert the gradient all-reduce; torch.utils.checkpoint → jax.checkpoint (remat).
