A team trains a sequence model. Somewhere in the encoder, a tensor of shape (batch, time, channels) needs to become (time, batch, channels) for a layer that expects time first. Someone writes x.view(T, B, C). The shape is right, nothing raises, the loss goes down, and the model ships with validation numbers a few points worse than the paper they were replicating. Months later someone notices that each "example" the layer sees is a patchwork of several real examples. Andrej Karpathy describes exactly this in his widely read "A Recipe for Training Neural Networks": people "use view instead of transpose/permute somewhere and inadvertently mix information across the batch dimension", and "it is a depressing fact that your network will typically still train okay because it will learn to ignore data from the other examples".

That is the character of shape bugs in PyTorch. The loud ones — "The size of tensor a (4) must match the size of tensor b (3) at non-singleton dimension 1" — cost you five minutes. The quiet ones cost weeks, because PyTorch's shape machinery is designed to make many different shapes compatible. Broadcasting will happily turn a prediction of shape (32, 1) and a target of shape (32,) into a 32 × 32 matrix of every-prediction-minus-every-target. An integer tensor used where a boolean mask was meant selects elements 0 and 1 instead of "where true". A loss called with the class axis in the wrong place runs fine whenever two dimensions happen to be equal.

In an ML-debugging interview these are the bread-and-butter planted bugs, and fluent candidates catch them by reading shapes the way a compiler would: "this is (B, 1) minus (B,), so it broadcasts to (B, B)". This lesson gives you that fluency. It covers the broadcasting rules and their two classic traps, the semantic difference between view, reshape, permute and transpose, the rules of basic and advanced indexing (including where PyTorch differs from NumPy), gather and scatter for picking and accumulating by index, boolean masks and the opposite polarity conventions of PyTorch's two attention APIs, einsum as a way to make axis bookkeeping explicit, and a step-by-step method for hunting shape errors — ending with the gradient trick Karpathy recommends for catching the bugs that shapes alone cannot reveal.

Think of every tensor dimension as a labelled axis, not a number. A batch of token embeddings is not "a 32 × 512 × 768 tensor"; it is "B examples × T time steps × C channels". Almost every shape bug is an axis that got the wrong label: time treated as batch, channels treated as classes, a per-row statistic applied per column. The habit that prevents them is to name every dimension in a comment and to read each operation as a statement about named axes.

With that frame, the main tools of this lesson each answer one question:

  • Broadcasting — "how do two tensors with different axes combine?" Line their shapes up from the right; wherever one has size 1 (or the axis is missing), it is stretched to match the other.
  • view / reshape — "how do I regroup the same sequence of numbers into different axes?" Merge or split adjacent axes without changing the order of elements.
  • permute / transpose — "how do I reorder the axes?" Swap which axis is which, keeping each element attached to its labels.
  • Indexing, gather, scatter — "how do I pick or place elements by position?" Slices for regular patterns; index tensors for arbitrary ones.
  • Masks — "how do I exclude some positions?" A bool tensor that says where, and a fill value (often −∞) that makes them vanish after a softmax.
  • einsum — "which axes are multiplied together and which are summed?" Written out as letters, so a mismatch is visible.

It helps to sort shape bugs into three kinds, because each is caught differently. Loud bugs are shapes that cannot combine: a matmul whose inner sizes differ, a broadcast where neither size is 1. PyTorch raises at the exact line, and the message names both sizes; these cost minutes. Accepted-wrong-shape bugs are shapes that combine into something you did not intend: (32, 1) minus (32,) becoming (32, 32), a reduction without keepdim on a square matrix, a bare squeeze() that removes the batch axis when the batch has one example. The result has a different shape than you meant, so a single assert on the result catches them. Right-shape-wrong-meaning bugs are the dangerous ones: a view where a permute was needed, a mask of the right shape with inverted polarity, an index tensor that is int where bool was meant. Every shape is exactly what the comment says, and only a test of what depends on what catches them — the gradient-dependency check at the end of the body. A strong candidate in a debugging round names which of the three kinds they are looking for, because it decides the tool: read the traceback, assert the shape, or test the dependency.

An analogy for the difference between view and permute: a deck of cards dealt into rows. view re-deals the same sequence of cards into rows of a different length — the order of cards in the deck never changes, only where the row breaks fall. permute is turning the table 90 degrees so columns become rows — each card keeps its neighbours, you just read them the other way. If you need "the first card of each row" to become a row, re-dealing gives you the wrong cards with the right count. The analogy breaks for higher dimensions, where permute can reorder any number of axes at once, but the test stays the same: does each element keep its labels? If yes, it is a permute; if you only regroup adjacent axes in their current order, view is safe.

The rest of the lesson makes each tool precise, shows the planted-bug version of each, and ends with a procedure you can run under interview pressure.

1. Name your axes

Production model code is full of comments like # (B, T, C) and # (B, nh, T, hs), and for good reason: shapes are the type system of tensor code, and Python will not check them. The convention used through this track: B batch, T time or sequence length, C channels or model width, V vocabulary, H or nh number of heads, D or hs head size. A line such as

scores = q @ k.transpose(-2, -1)   # (B, H, T, D) @ (B, H, D, T) -> (B, H, T, T)

tells the reader — and you, three weeks later — exactly what each axis is. When a shape bug appears, the first question is "where does the actual shape stop matching the comment?"

2. Broadcasting, precisely

Broadcasting lets an element-wise operation combine tensors of different shapes. The rule, from the PyTorch docs: compare sizes starting from the trailing (rightmost) dimension; for each pair, the sizes must be equal, or one of them must be 1, or one of them must not exist. The result takes the larger size at each position.

Worked example: a of shape (8, 1, 6, 1) and b of shape (7, 1, 5).

  1. Rightmost pair: 1 and 5 → 5.
  2. Next: 6 and 1 → 6.
  3. Next: 1 and 7 → 7.
  4. Next: 8 and (missing, treated as 1) → 8.

Result (8, 7, 6, 5), which torch.broadcast_shapes confirms. Nothing is copied: internally each operand is expanded with stride 0 along its stretched dimensions (pt1), so a (1, C) bias added to a (B, C) activation reads the same C numbers for every row.

When the rule fails you get a loud error naming the dimension: torch.zeros(3, 4) + torch.zeros(3) raises "The size of tensor a (4) must match the size of tensor b (3) at non-singleton dimension 1", because the trailing sizes 4 and 3 differ. The intent was almost certainly "add a per-row value", which needs the vector as a column, v[:, None] or v.unsqueeze(1), shape (3, 1).

3. The two broadcasting traps

Trap 1: (N, 1) against (N,). A regression head usually outputs (N, 1); targets usually arrive as (N,). Aligned from the right, (N,) is (1, N), so the pair becomes (N, N):

pred = model(x)          # (32, 1)
y = batch["target"]      # (32,)
loss = ((pred - y) ** 2).mean()   # (32, 32) -> scalar. Wrong.

The loss is finite and decreasing: minimising it pushes every prediction toward the mean of the batch's targets, so the curve looks like learning. F.mse_loss catches this one with a warning ("Using a target size (torch.Size([32])) that is different to the input size (torch.Size([32, 1])). This will likely lead to incorrect results due to broadcasting.") — warnings that scroll past in logs. A hand-written loss gives no warning at all. The fix is one character of intent: pred.squeeze(-1), and an assert pred.shape == y.shape before every loss.

Trap 2: reductions without keepdim. To centre each row of a (4, 3) matrix, v - v.mean(dim=1) computes a (4,) vector of row means, aligns it on the right as (1, 4), and fails against the 3 columns — good, it is loud. But for a (3, 3) matrix the (3,) means align with the columns and broadcast without complaint: you subtract row i's mean from column i. Always write v.mean(dim=1, keepdim=True), which keeps the reduced axis as size 1, shape (3, 1), so it broadcasts down the rows. The same applies to sum, max, norm and logsumexp. Square shapes — T equal to C, batch equal to classes in a toy test — are where these traps hide, which is why test shapes should be distinct.

4. view, reshape, flatten, permute, transpose: semantics, not just shapes

pt1 explained the memory side: view never copies, reshape may, permute only changes strides. The meaning is what matters for correctness.

  • view / reshape / flatten / unflatten keep the row-major order of elements and regroup them. They are correct when you merge or split adjacent axes: (B, T, C) → (B·T, C) to feed a linear layer, or (B, T, C) → (B, T, H, D) to split channels into heads.
  • permute / transpose / movedim / .mT change which axis is which; every element keeps its (b, t, c) coordinates under new positions.

The canonical bug, run on 2.14 with B=2, T=3, C=4 and x = torch.arange(24).reshape(2, 3, 4):

good = x.permute(1, 0, 2)   # (T, B, C)
bad  = x.view(3, 2, 4)      # (T, B, C) by shape only
good[0]  # [[0, 1, 2, 3], [12, 13, 14, 15]]  -> time 0 of example 0 and example 1
bad[0]   # [[0, 1, 2, 3], [4, 5, 6, 7]]      -> times 0 and 1 of example 0

In bad, what a downstream layer believes is "the batch at time 0" contains example 0 at time 1. A recurrent layer or a per-time normalisation now mixes examples. Nothing errors.

The rule of thumb: to move an axis, use permute or transpose; to merge or split neighbouring axes, use view or reshape; and when you need both, permute first, then (contiguous and) view — the head-merge line y.transpose(1, 2).contiguous().view(B, T, C) from pt1 is exactly that pattern.

5. Adding and removing size-1 axes

unsqueeze(d), or indexing with None (x[:, None]), inserts a size-1 axis — the standard way to set up broadcasting: mask[:, None, None, :] turns a (B, T) padding mask into (B, 1, 1, T) so it broadcasts over heads and query positions in a (B, H, T, T) score tensor. squeeze(d) removes a size-1 axis at d.

Call squeeze() with no argument and it removes every size-1 axis. That is a latent bug: a (B, 1) prediction becomes (B,) as intended — until the last batch of an epoch has B = 1 and the prediction becomes a 0-dimensional scalar, which then broadcasts against the target in a new and wrong way, or a (1, 5, 1) tensor becomes (5,) when you wanted (1, 5). Always pass the dimension: squeeze(-1).

6. Basic and advanced indexing

Basic indexing uses integers, slices (start:stop:step), None and ... (Ellipsis, meaning "all remaining axes"). It returns a view. An integer removes its axis: x[0] on (B, T, C) is (T, C); x[0:1] keeps it as (1, T, C).

Advanced indexing uses an integer tensor or list, or a boolean tensor. It copies, and it has its own placement rules, which PyTorch takes from NumPy with one exception:

  1. All advanced index tensors are broadcast against each other. x[[0, 1], [0, 2]] on (2, 3, 4) picks (0, 0, :) and (1, 2, :): result (2, 4).
  2. If the advanced indices are adjacent, the broadcast index dimensions replace them in place: x[:, [0, 2], [1, 3]] is (2, 2) — the batch axis, then the pairs.
  3. If they are separated by a slice, the broadcast index dimensions move to the front: x[[0, 1], :, [1, 2]] is (2, 3), not (3, 2).
  4. The exception: in PyTorch a plain Python integer counts as basic indexing. x[0, :, [1, 2]] is (3, 2) in PyTorch, while NumPy, which treats the integer as an advanced index separated by a slice, returns (2, 3). Both were checked on this machine (PyTorch 2.14, NumPy 2.5). Code ported from NumPy can silently transpose here.

A boolean mask of the same shape selects the elements where it is True and returns them flattened: x[x > 10] on 24 elements returns a 1-D tensor of 13. A bool tensor matching only the leading axes selects whole slices: x[torch.tensor([True, False])] on (2, 3, 4) is (1, 3, 4). The output size depends on the data, which is why boolean indexing forces a host–device synchronisation on GPU (the CPU must learn how many elements were selected) and breaks torch.compile graphs (pt12).

The int-mask bug: a mask computed with .long() or loaded from a file as int64 and then used for indexing.

s = torch.tensor([0.54, 0.19, 0.7, 0.1])
keep = torch.tensor([1, 1, 0, 0])     # int64, intended as a mask
s[keep]       # tensor([0.19, 0.19, 0.54, 0.54]) -> elements 1, 1, 0, 0. No error.
s[keep.bool()]  # tensor([0.54, 0.19])

7. gather: pick one element per row by index

torch.gather(input, dim, index) reads, along dimension dim, the position given by index, for every other coordinate. For 2-D input and dim=1: out[i][j] = input[i][index[i][j]]. The index must have the same number of dimensions as the input, and the output has the index's shape.

The everyday use is reading each row's target log-probability, which is exactly what cross-entropy does:

logits = torch.tensor([[2.0, 1.0, 0.1],
                       [0.5, 2.5, 0.3]])      # (N=2, V=3)
target = torch.tensor([0, 1])                 # (N,)
logp = logits.log_softmax(dim=-1)             # (N, V)
picked = logp.gather(1, target.unsqueeze(1))  # (N, 1): logp[0,0], logp[1,1]
loss = -picked.mean()                         # 0.3185, same as F.cross_entropy

Checked on 2.14: both give 0.3185. The advanced-index equivalent is logp[torch.arange(N), target], which returns (N,). gather generalises cleanly to more dimensions — picking the target token at every position of a (B, T, V) tensor is logp.gather(-1, targets.unsqueeze(-1)).squeeze(-1) — and it states the dimension explicitly, so the reader does not need the advanced-indexing placement rules.

8. scatter, index_add and the duplicate-index trap

scatter is gather's inverse: out[i][index[i][j]] = src[i][j]. A one-hot encoding is torch.zeros(N, V).scatter_(1, target.unsqueeze(1), 1.0). When two writes land on the same position, plain scatter keeps one of them (which one is unspecified). The accumulating forms add them all:

  • scatter_add_(dim, index, src) — sums colliding writes. Counting labels [0, 2, 2, 3, 2] into 4 bins gives [1, 0, 3, 1].
  • index_add_(dim, index, source) — adds whole slices: emb_grad.index_add_(0, token_ids, row_grads) is how an embedding's gradient is formed.
  • scatter_reduce(dim, index, src, reduce=…) — combines with "sum", "prod", "mean", "amax" or "amin"; include_self=False ignores the output's initial values. This is the building block of graph neural network message passing and segment reductions.

The trap is the innocent-looking augmented assignment with advanced indexing. z[idx] += 1 is executed as "gather z[idx], add 1, write back to z[idx]". With idx = [0, 0] both writes put 1 into position 0, and z becomes [1, 0, 0], not [2, 0, 0] (checked on 2.14). z.index_put_((idx,), torch.tensor(1.), accumulate=True) gives [2, 0, 0]. Use torch.bincount for counting and an accumulating op for everything else.

9. Masks: dtype, fill values, polarity

A mask is a bool tensor broadcastable to the data it filters. The standard attention pattern fills disallowed scores with −∞ before softmax, so they receive exactly zero probability:

scores = q @ k.transpose(-2, -1) / math.sqrt(D)          # (B, H, T, T)
causal = torch.tril(torch.ones(T, T, dtype=torch.bool))  # True = may attend
scores = scores.masked_fill(~causal, float("-inf"))
attn = scores.softmax(dim=-1)

Three things go wrong with masks:

  1. Dtype. masked_fill rejects non-bool masks ("masked_fill_ only supports boolean masks, but got mask with dtype __int64" on 2.14), which is helpful; multiplying by a 0/1 float mask after softmax is accepted and wrong, because the remaining probabilities no longer sum to 1, and multiplying scores by 0 before softmax gives masked positions score 0, not −∞ — they still get probability.
  2. Fully masked rows. If every key in a row is masked, softmax computes 0/0 and returns NaN for the whole row (checked: a row of four −∞ gives four NaNs). Padded query positions are the usual source. The NaN then flows into every gradient. Make sure each query can see at least one key (usually itself), or zero those rows and exclude them from the loss.
  3. Polarity. PyTorch has two attention APIs with opposite conventions. In F.scaled_dot_product_attention, a boolean attn_mask True means "this element takes part in attention". In nn.MultiheadAttention, a boolean True in attn_mask or key_padding_mask means "ignore it". The SDPA documentation says so explicitly and tells you to invert the mask when migrating. Tokenisers add a third convention: Hugging Face's attention_mask is 1 for real tokens and 0 for padding.

torch.where(cond, a, b) is the general masked select — element-wise "a where cond else b" with broadcasting — and is often clearer than masked_fill for non-attention uses, such as clamping a loss only where a label is valid.

10. einsum: axis bookkeeping you can read

torch.einsum takes a subscript string that names each input's axes and the output's. Any letter missing from the output is summed over; letters shared by inputs are matched. Three examples you should be able to write without thinking:

torch.einsum("bij,bjk->bik", A, B)        # batched matmul, same as A @ B
torch.einsum("bhqd,bhkd->bhqk", q, k)     # attention scores, same as q @ k.mT
torch.einsum("bhqk,bhkd->bhqd", p, v)     # attention output, same as p @ v
torch.einsum("bd,bd->b", x, y)            # per-row dot product
torch.einsum("...d,ed->...e", x, W)       # a linear layer over any leading axes

Checked on 2.14: the first matches A @ B to floating-point tolerance, and the second returns (2, 4, 8, 8) for q and k of shape (2, 4, 8, 16). Under the hood einsum permutes and reshapes the operands into a batched matmul, so the speed is the same as hand-written code; with more than two operands, PyTorch picks a contraction order (using the opt_einsum package if installed). The real benefit is readability and loud failure: if you write "bhqd,bhdk" when k is actually (B, H, T, D), einsum raises on the size mismatch of d, whereas a wrong transpose might happen to produce a valid shape.

11. Reading shapes through a whole attention block

Putting the pieces together, here is the shape story of one causal self-attention layer with B=2, T=5, C=12 and 3 heads of size 4 — distinct numbers on purpose. Every line is one of the tools above.

x                                   # (2, 5, 12)      input, (B, T, C)
qkv = x @ W_qkv                     # (2, 5, 36)      one matmul for q, k, v
q, k, v = qkv.split(12, dim=-1)     # 3 × (2, 5, 12)  views, no copy
q = q.view(2, 5, 3, 4)              # (2, 5, 3, 4)    split C into heads: neighbours, so view is right
q = q.transpose(1, 2)               # (2, 3, 5, 4)    move heads before time: an axis move, so transpose
scores = q @ k.transpose(-2, -1)    # (2, 3, 5, 5)    (B, H, T, D) @ (B, H, D, T)
scores = scores / 4 ** 0.5          # scale by √D
causal = torch.ones(5, 5, dtype=torch.bool).tril()   # (5, 5)  True = may attend
scores = scores.masked_fill(~causal, float("-inf"))  # broadcast (5, 5) over (2, 3)
p = scores.softmax(-1)              # (2, 3, 5, 5)    each row sums to 1 over keys
y = p @ v                           # (2, 3, 5, 4)
y = y.transpose(1, 2)               # (2, 5, 3, 4)    heads back after time
y = y.contiguous().view(2, 5, 12)   # (2, 5, 12)      merge heads: neighbours again, needs contiguous
out = y @ W_o                       # (2, 5, 12)

Read the pattern: split and merge of neighbouring axes use view; moving heads in front of time uses transpose; the (T, T) mask broadcasts over the leading (B, H) axes because broadcasting aligns from the right; the softmax runs over the last axis, the keys. Change any one of these to its look-alike — view for the transpose, softmax over dim −2, the mask without ~ — and every shape in the right-hand column stays identical. That is why the dependency check exists. pt10 builds this block for real with F.scaled_dot_product_attention, which does the middle five lines in one fused call.

12. A method for debugging shape errors

Under interview pressure, follow the same steps every time.

  1. Read the message. PyTorch shape errors name the sizes and the dimension: "size of tensor a (4) must match … at non-singleton dimension 1", "mat1 and mat2 shapes cannot be multiplied (64x512 and 768x10)", "Expected target size [2, 10], got [2, 7]". For a matmul, the inner numbers (512 vs 768) are the mismatch.
  2. Reproduce small, with distinct sizes. Use B=2, T=3, C=5, H=7 (or other unequal sizes) so that every axis is identifiable and no accidental equality hides a swap. Many silent bugs only exist because T == C in the original config.
  3. Find the first divergence. Write the expected shape next to each line (or check with asserts such as assert x.shape == (B, T, C), x.shape) and find the first line where reality differs. In a model you cannot edit, register a forward hook on every module that prints its class name and output shape (pt4 covers hooks).
  4. Check semantics at each view, reshape and permute. For each, ask: "is this merging or splitting neighbouring axes in their current order (view), or moving an axis (permute)?"
  5. Check losses specially. Assert prediction and target shapes are equal (regression) or that logits are (N, V) and targets (N,) after flattening (classification).
  6. Run the dependency check. Shapes cannot catch batch mixing or causal leaks. Karpathy's test: make the loss depend on example i only, backpropagate to the input, and confirm the gradient is non-zero only on example i. For a causal model, make the loss the output at position t and confirm the input gradient is zero for all positions after t.
x = torch.randn(2, 3, 5, requires_grad=True)   # (B, T, C), distinct sizes
out = model(x)                                  # (B, T, C')
out[1, 2].sum().backward()                      # loss uses example 1, position 2
print(x.grad[0].abs().sum())                    # must be 0: no batch mixing
print(x.grad[1, 3:].abs().sum() if x.shape[1] > 3 else "n/a")  # future: must be 0

Remember to put the model in eval mode for this check (pt4): BatchNorm in training mode legitimately mixes examples through batch statistics, and dropout adds noise.

Broadcasting in backward: gradients are summed over stretched axes

If a tensor of shape (1, C) was broadcast to (B, C) in the forward pass, its gradient must still have shape (1, C). Autograd handles this by summing the incoming (B, C) gradient over the broadcast axis (internally a sum_to_size). Two consequences matter. First, cost: a bias broadcast across a (B, T, C) activation means a full reduction over B·T rows in the backward pass — cheap per element, but it is memory-bandwidth-bound work that fusion (pt12) tries to merge with neighbouring ops. Second, a classic modelling bug: a learnable tensor created with the batch size baked in, such as a (B, C) "bias", receives a separate gradient per row, learns per-position nonsense, and breaks when the batch size changes. Parameters that should be shared across the batch must have a 1 (or no axis) there.

Indexing in backward, determinism and atomics

The backward of gather, advanced indexing and embedding lookups is a scatter-add of gradients into the source positions. With duplicate indices (the same token appearing many times in a batch) those adds collide. On CUDA they are performed with atomic additions, whose order varies between runs, so the gradients are not bitwise reproducible: floating-point addition is not associative, and different orders round differently. torch.use_deterministic_algorithms(True) makes PyTorch pick deterministic implementations (often by sorting indices first) or raise if none exists — the price is speed. pt6 returns to determinism. Note the asymmetry with the forward trap: in backward, duplicate indices are accumulated correctly; it is only user-level x[idx] += v that drops them.

Data-dependent shapes and why compilers hate them

Most shapes in a model depend only on input shapes: a linear layer maps (B, T, C) to (B, T, C'). Boolean indexing, nonzero, unique and masked_select produce outputs whose size depends on the values. On GPU, PyTorch must copy the count back to the CPU to allocate the output, which is a synchronisation (pt12). For torch.compile and torch.export (pt12, pt13) these ops create "unbacked" symbolic sizes that the compiler cannot reason about and may break the graph. The idiom that avoids both is to keep shapes static and use masks arithmetically — torch.where(mask, x, 0) and a masked mean (x * m).sum() / m.sum().clamp(min=1) — instead of selecting a variable-length subset.

Advanced indexing versus index_select, take_along_dim and gather

Advanced indexing is the most general and the hardest to read: its placement rules depend on whether index tensors are adjacent and on whether integers are present, and PyTorch and NumPy disagree on one case. The explicit alternatives each do one thing. index_select(dim, idx) picks whole slices along one axis with a 1-D index (an embedding lookup is weight.index_select(0, ids)). gather(dim, idx) picks one element per position along one axis with an index of full rank. take_along_dim(x, idx, dim) is the NumPy-compatible gather that also broadcasts the index. In production code, preferring these makes the result layout obvious, and they map to simpler kernels.

einsum contraction order matters for three or more operands

For two operands, einsum is one matmul. For three or more, the order of pairwise contractions can change the cost by orders of magnitude: contracting "ij,jk,kl->il" as (A·B)·C versus A·(B·C) depends on the sizes, exactly like matrix-chain multiplication. PyTorch optimises the order when the opt_einsum package is available (configurable through torch.backends.opt_einsum) and otherwise contracts left to right. If an einsum over several tensors is unexpectedly slow or memory-hungry, check whether an intermediate is huge: an intermediate of shape (B, T, T, D) materialised by a bad order is the usual culprit.

expand, repeat and repeat_interleave: the grouped-query attention trap

Grouped-query attention (lm5) has fewer key/value heads than query heads — say 8 query heads sharing 2 KV heads — and each group of 4 consecutive query heads uses one KV head: query heads 0–3 use KV head 0, heads 4–7 use KV head 1. To compute it with ordinary matmuls you must make k and v look like 8 heads. k.repeat_interleave(4, dim=1) produces KV order 0, 0, 0, 0, 1, 1, 1, 1 — correct, and it is exactly what the SDPA documentation's reference code does for enable_gqa=True. k.repeat(1, 4, 1, 1) produces 0, 1, 0, 1, 0, 1, 0, 1 — the same shape, a different pairing, and a model whose pretrained weights now meet the wrong keys. Both copy memory; k[:, :, None].expand(B, 2, 4, T, D).reshape(B, 8, T, D) gives the interleaved order and copies only at the reshape. The cleanest option on 2.14 is to skip the expansion and pass enable_gqa=True to SDPA, which handles the grouping inside the kernel on backends that support it.

Making shapes checkable

Python's type system does not see tensor shapes, so teams add checks. The lightweight approach is asserts at module boundaries and in loss functions, which cost nothing compared with a matmul. torch._check and torch._check_is_size express shape conditions in a way torch.compile understands. Libraries such as jaxtyping let you annotate functions with shapes like Float[Tensor, "batch seq dim"] and check them at runtime with a type checker. Whatever the mechanism, the value comes from writing down the intended axes once and having the machine compare.

torch.func.vmap: writing per-example code without manual batch axes

Many shape bugs come from threading a batch axis through code that is conceptually per-example. torch.func.vmap(f) takes a function written for one example and runs it over a batch axis, inserting the batching itself; it is the PyTorch counterpart of JAX's vmap (pt14). It is especially handy for per-example gradients (vmap(grad(loss_fn))), ensembles, and Jacobians. The trade-off: not every operation supports vmap, and a vmapped function cannot have data-dependent Python control flow on the batched values.

Silent shape bugs seen in real training code

The incidents rarely look like "shape bug" from the outside. They look like a model that is a few points worse than expected, a loss that plateaus at a suspicious value, or a metric that does not move. The usual culprits, roughly in order of frequency:

  • Loss broadcasting — (N, 1) predictions against (N,) targets in a custom loss; symptom: predictions collapse toward the batch mean, so per-example metrics are flat.
  • Class axis in the wrong place — cross-entropy called on (B, T, V) without flattening, which only runs when T happens to equal V or in square test shapes; symptom: loss value plausible, accuracy near chance.
  • view instead of permute — batch or time mixed; symptom: a few points below the reference, still trains (Karpathy's observation).
  • Mask polarity or dtype — inverted causal mask or padding mask; symptom: suspiciously low training loss with a causal mask inverted (the model sees the future), or outputs that change when only padding changes.
  • Bare squeeze() — breaks only when a batch of size 1 appears, typically the last batch of an epoch; symptom: an error or a wrong loss once per epoch.
  • Integer masks used as indices — silently selects elements 0 and 1; symptom: wildly wrong metrics on a subset.

Guard rails teams actually use

Shape asserts at every module boundary and before every loss are cheap and catch most of the above. A "smoke test" that runs one forward and backward pass on CPU with distinct tiny sizes (B=2, T=3, C=5) in continuous integration catches square-shape luck. The gradient-dependency test from the Recipe belongs in the same test file for any model with a causal or per-example structure. Finally, training code should log a per-example sanity metric (accuracy, or a prediction histogram) from the first steps, because the loss value alone is consistent with many of these bugs.

Performance consequences of shape choices

Shape decisions also show up in step time. Boolean indexing inside the training step forces a synchronisation per call. Advanced indexing allocates and copies, so gathering a large subset repeatedly can dominate a step; index_select on a contiguous axis or a static mask is cheaper. Permutes are free but feed non-contiguous tensors to the next op, which may then copy; profiling (pt12) shows these as aten::copy_ or aten::contiguous entries. And einsum with a poor contraction order can materialise a huge intermediate — a memory spike that looks like an out-of-memory bug in an unrelated place.

Find the bug: a token-classification head that "learns"

A named-entity tagger trains with this loss code. Loss falls from 2.2 to 1.6 and stalls; token accuracy is near the majority-class rate. Shapes: h is (B, T, C) from the encoder, there are V = 9 tags, tags is (B, T) int64 with −100 at padding, and pad is (B, T) int64 with 1 for real tokens. Find the bugs, give the symptom of each, and fix them.

logits = head(h)                                # (B, T, 9)
logits = logits.view(T, B, 9)                    # "loss wants time first"
keep = pad.view(-1)                              # 1 = real token
flat_logits = logits.reshape(-1, 9)[keep]
flat_tags = tags.reshape(-1)[keep]
loss = F.cross_entropy(flat_logits, flat_tags)
acc = (flat_logits.argmax(-1) == flat_tags).float().mean()
Answer

Bug 1 — view instead of permute. logits.view(T, B, 9) re-deals the (B, T) order into (T, B) rows, so after the next reshape, row r of flat_logits is no longer the token that row r of flat_tags describes: predictions are compared with the tags of other tokens (often from the other example). Symptom: the model can only learn the tag distribution, so accuracy sits at the majority-class rate and the loss stalls near the entropy of the tag frequencies. Fix: delete the line — cross_entropy wants (N, C) after flattening, and logits.reshape(-1, 9) with tags.reshape(-1) keeps token order aligned. If time-first really were needed elsewhere, it would be permute(1, 0, 2), applied to both logits and tags.

Bug 2 — integer mask used as an index. keep is int64 of 0s and 1s, so [keep] selects rows 0 and 1 over and over instead of "rows where real". Every "example" in the loss is token 0 or token 1 of the batch. Symptom: loss and accuracy computed on two tokens repeated thousands of times. Fix: keep = pad.view(-1).bool().

Bug 3 (redundant, but a smell) — double masking. The tags already contain −100 at padding, which F.cross_entropy ignores by default (ignore_index=-100), so the mask is unnecessary for the loss. Keeping both conventions invites them to disagree. The minimal correct code: loss = F.cross_entropy(logits.reshape(-1, 9), tags.reshape(-1)); for accuracy, mask with valid = tags != -100. Verify with the dependency check: a loss on token (1, 2) must give zero gradient on h[0].

Find the bug: the padding mask that leaks

Someone migrates an encoder from nn.MultiheadAttention to F.scaled_dot_product_attention for speed. They pass the same boolean key_padding_mask (True at padding), reshaped to (B, 1, 1, T), as attn_mask. Training loss now goes NaN within the first steps on batches that contain padding. Why, and what is the fix?

Answer

The polarities are opposite: MHA's True means "ignore", SDPA's True means "take part". After the migration each query in a padded sequence attends only to padding keys, which is garbage but finite. Any sequence with no padding — and every batch has at least one, the longest — gets a mask that is all False, so every score in its rows is masked: softmax of a fully masked row is NaN, and the NaN propagates into the loss and every gradient. Fix: pass ~key_padding_mask, and add a unit test that compares the old and new layers' outputs on a padded batch with the same weights.
