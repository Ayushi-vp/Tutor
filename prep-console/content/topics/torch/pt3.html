In the NumPy implementations of this app (mc11, mc13) you wrote backward passes by hand: for every layer, a function that takes the gradient of the loss with respect to the layer's output and returns the gradients with respect to its inputs and weights, plus the bookkeeping to keep the forward values those formulas need. That is fine for a two-layer network. For a transformer with rotary embeddings, grouped-query attention, a mixture-of-experts router and a custom loss, hand-written backward code would be thousands of lines, and every change to the forward pass would need a matching change to the backward pass — the perfect breeding ground for gradient bugs that do not crash but quietly make the model worse.

PyTorch's autograd removes that work. You write only the forward pass in ordinary Python, and PyTorch records what you did and differentiates it. It feels like magic, which is exactly why engineers who only know the surface get stuck when it misbehaves: gradients that double every step because nobody zeroed them, memory that explodes during evaluation because a graph was still being recorded, "Trying to backward through the graph a second time" in a recurrent model, NaN gradients from a forward pass that contains no NaN, a frozen layer that keeps moving, or an intermediate tensor whose .grad is mysteriously None.

In ML-debugging interviews, autograd questions sort candidates quickly. "Why is the evaluation loop out of memory?" "Why does this RNN crash on the second batch?" "Why is this gradient NaN?" Each has a crisp answer if you know what the engine records, when it frees things, and which flags change its behaviour.

This lesson opens the box. It starts from what happens on every operation when a tensor requires gradients, traces a backward pass by hand with real numbers, and then covers the rules you need in practice: leaves and accumulation, saved tensors and retain_graph, the three ways to turn tracking off (no_grad, inference_mode, detach) and how they differ, non-scalar outputs and vector–Jacobian products, hooks, higher-order gradients, and writing and testing your own torch.autograd.Function. It finishes with the NaN-gradient traps and the anomaly detector that finds them.

Think of autograd as a flight recorder. When the forward pass runs, every operation that touches a tensor marked requires_grad=True writes an entry: "I was a multiplication; my inputs came from these two places; to compute my gradients later I will need these two values, so I have kept them". Each entry is a node, and each node points back to the nodes that produced its inputs. When you call loss.backward(), PyTorch plays the recording in reverse, starting at the loss: each node takes the gradient arriving from above, applies its local derivative rule using the values it kept, and passes the results to the nodes it points to. When the playback reaches a tensor you created yourself — a parameter — it adds the result into that tensor's .grad.

Four facts fall out of that picture:

  • The graph is rebuilt every forward pass. The recording is made while your Python runs, so loops, ifs and recursion simply produce whatever graph they produced this time. This is the "dynamic" or "define-by-run" graph.
  • Recording costs memory. The values nodes keep — saved tensors — are mostly activations, and they are the main memory cost of training. They are released as the backward playback passes each node.
  • Gradients accumulate. The playback adds into .grad; it never overwrites. Clearing them is your job.
  • You can switch the recorder off. Inside torch.no_grad() nothing is recorded, which is what evaluation and parameter updates need.

It helps to hold a rough cost model from the start, because most autograd questions in interviews are really cost questions. The forward pass does the work you wrote. The backward pass does roughly twice that work in arithmetic, because for every matrix multiplication in the forward it needs two — one for the gradient with respect to the input, one for the gradient with respect to the weight. Memory is dominated not by the graph's nodes, which are small objects, but by the saved tensors those nodes hold: for a transformer that means the inputs of every linear layer, the attention probabilities or their compact substitutes, the outputs of activations and normalisations. Weights and their gradients have a fixed size; saved activations grow with batch size and sequence length. So when someone asks "why is this using so much memory?" the first suspect is "what is autograd keeping alive, and for how long?", and when someone asks "how do I make evaluation cheaper?" the first answer is "stop recording".

It also helps to know what autograd is not. It is not symbolic differentiation: it never produces a formula for the derivative, only numbers for this particular input. It is not numerical differentiation either: no small perturbations, no finite-difference error — each node applies an exact derivative rule. It is reverse-mode automatic differentiation by operator overloading: the PyTorch paper (Paszke et al., NeurIPS 2019) describes it as building "a representation of the computed function every time it is executed", chosen because Python is too dynamic for ahead-of-time source transformation.

Where the flight-recorder analogy breaks: a real recorder captures everything, while autograd records only operations whose inputs require gradients — operations on plain data tensors are not recorded at all, which is why loading data costs no graph memory. And a real recorder can be replayed many times; autograd's playback discards what it has used, so by default you get one backward pass per forward.

If you remember one sentence: the forward pass builds a graph of nodes that keep what their derivative needs; backward replays it once, in reverse, adding into the leaves' .grad, and freeing as it goes.

1. requires_grad and how it spreads

Every tensor has a flag, requires_grad. Parameters created by nn.Module layers have it set to True; data tensors do not. The rule for results is simple: the output of an operation requires grad if any of its inputs does (and recording is enabled). So w * x requires grad because w does, even though x is data.

x = torch.tensor(2.0, requires_grad=True)
w = torch.tensor(3.0, requires_grad=True)
b = torch.tensor(1.0, requires_grad=True)
y = w * x + b       # requires_grad=True, grad_fn=<AddBackward0>
z = y.relu()        # grad_fn=<ReluBackward0>
L = z ** 2          # grad_fn=<PowBackward0>

Each result has a grad_fn: the graph node that produced it. The node points to the nodes of its inputs through next_functions; on 2.14 L.grad_fn.next_functions is ((<ReluBackward0>, 0),). Following those links from the loss visits the whole graph. A leaf that requires grad appears in the graph as an AccumulateGrad node, whose only job is to add the arriving gradient into the leaf's .grad.

2. Leaf and non-leaf tensors

A leaf tensor is one that autograd did not compute: you created it, or it is a parameter. x.is_leaf is True; y.is_leaf is False. A tensor that does not require grad is also a leaf, trivially. The distinction matters because:

  • Only leaves that require grad receive .grad after backward. For an intermediate such as y, y.grad is None and 2.14 warns that "The .grad attribute of a Tensor that is not a leaf Tensor is being accessed". If you need it, call y.retain_grad() before backward.
  • Leaves that require grad cannot be modified in place outside no_grad (pt1), because their identity is what .grad refers to.
  • Operations such as .to(device) or .float() on a leaf produce a non-leaf. A common bug: w = torch.randn(3, requires_grad=True).cuda() creates a leaf on the CPU and a non-leaf copy on the GPU; the model uses the copy, the optimiser holds the copy, and .grad on it is always None. Create tensors on the right device directly — torch.randn(3, device="cuda", requires_grad=True) — or use nn.Parameter inside a module and move the module.

3. Running backward by hand

Calling L.backward() on the graph above (checked on 2.14):

  1. Start with dL/dL = 1.
  2. PowBackward (L = z²) saved z = 7; it returns 1 · 2z = 14 for z.
  3. ReluBackward saved its output; since the output is positive it passes 14 through (it would pass 0 where the output is 0).
  4. AddBackward (y = (w·x) + b) has local derivative 1 for both inputs: it sends 14 to the Mul node and 14 to b's AccumulateGrad. b.grad = 14.
  5. MulBackward saved w and x; it returns 14 · x = 28 for w and 14 · w = 42 for x. w.grad = 28, x.grad = 42.

The engine visits nodes in an order where each node runs only after all gradients flowing into it have arrived (a reverse topological order), so a tensor used twice — a residual connection, a shared embedding — gets the sum of the gradients from both uses before its node runs. That summing is the chain rule's "add over paths", done for you.

4. What each node computes: vector–Jacobian products

For a function from n inputs to m outputs, the Jacobian J is the m × n matrix of partial derivatives. The chain rule says the gradient of a scalar loss with respect to the inputs is v · J, where v is the gradient with respect to the outputs. That product is a vector–Jacobian product (VJP), and it is what every backward node computes — without ever building J. For an element-wise ReLU over a million elements, J would be a million × million diagonal matrix; the VJP is just "multiply v by 1 where the output was positive, 0 elsewhere". For a matmul Y = X W, the VJPs are dX = dY Wᵀ and dW = Xᵀ dY, two matmuls of the same size as the forward. This is why a backward pass costs about twice the forward in FLOPs: each matmul in the forward becomes two in the backward.

It also explains an error you will see: (v * 2).backward() on a 3-element output raises "grad can be implicitly created only for scalar outputs". For a scalar loss, v is simply 1; for a vector output PyTorch does not know which v you want. Pass one explicitly — out.backward(torch.ones_like(out)) gives the gradient of out.sum() — or reduce to a scalar first. If you truly need the full Jacobian, that is one VJP per output row; torch.func.jacrev does it with vmap.

5. Accumulation into .grad

AccumulateGrad adds. Run this on 2.14:

w = torch.tensor(3.0, requires_grad=True)
for _ in range(3):
    (w * 2).backward()
w.grad    # tensor(6.)  — 2 + 2 + 2

This is a feature. Gradient accumulation — running several small batches and stepping once — is just "call backward k times, then step", because the gradients sum. (Each micro-batch loss must be divided by k to get the average; pt6 shows the bug when it is not.) It also means every training loop must clear gradients once per optimiser step. optimizer.zero_grad() and model.zero_grad() both default to set_to_none=True on 2.14, which sets .grad = None instead of filling it with zeros: cheaper, and the next backward allocates fresh. Code that reads p.grad after zero_grad must handle None.

6. Saved tensors, freeing, and retain_graph

Each node saves what its backward formula needs: exp saves its result (d/dx eˣ = eˣ), sigmoid its output, mul both inputs, a linear layer its input (to compute dW = Xᵀ dY). On 2.14 you can peek: a.exp().grad_fn._saved_result. These saved tensors are the activations whose memory dominates training (pt7 does the arithmetic: for a transformer they often exceed the weights many times over).

To keep memory down, backward frees each node's saved tensors as soon as it has used them. Calling backward again on the same graph then fails:

RuntimeError: Trying to backward through the graph a second time (or directly
access saved tensors after they have already been freed). Saved intermediate
values of the graph are freed when you call .backward() or autograd.grad().
Specify retain_graph=True if you need to backward through the graph a second time ...

Two situations produce it. The legitimate one: two losses that share part of a forward pass and are backpropagated separately; pass retain_graph=True to the first backward (or, better, sum the losses and backpropagate once). The common bug: a tensor kept across iterations still references the previous iteration's graph — an RNN hidden state carried from batch to batch, a running "memory" in a model, an exponential moving average computed without no_grad. The second iteration's backward walks into the first iteration's freed graph. The fix is hidden = hidden.detach() at the start of each batch, which is exactly truncated backpropagation through time.

7. Turning recording off: no_grad, inference_mode, set_grad_enabled, detach

Recording costs time and memory, so you switch it off whenever you do not need gradients.

  • with torch.no_grad(): — operations are not recorded; outputs have requires_grad=False. Used for evaluation and for updates to parameters (optimisers do their in-place updates under no_grad, which is also why that is allowed on leaves).
  • with torch.inference_mode(): — like no_grad, plus tensors created inside skip version counting and view tracking. Outputs are inference tensors: on 2.14, c.is_inference() is True for them, and using one in a later autograd computation raises "Inference tensors cannot be saved for backward…", while modifying one in place outside the mode raises "Inplace update to inference tensor outside InferenceMode is not allowed". Use it for serving and evaluation; clone outputs if they must feed training.
  • torch.set_grad_enabled(flag) — a context manager or function that turns recording on or off by a boolean, handy for one loop that does both training and evaluation: with torch.set_grad_enabled(phase == "train"):.
  • t.detach() — not a mode but a per-tensor cut: returns a tensor that shares storage (and version counter) with t but has no grad_fn. Gradients do not flow through it. Used for targets computed from the model itself (a teacher's output in distillation, the stop-gradient in a target network), for carrying RNN state across batches, and before logging.

And remember the myth: model.eval() is none of these. It changes how dropout and BatchNorm behave (pt4); the graph is still recorded. An evaluation loop that calls model.eval() without no_grad or inference_mode keeps every activation of every batch alive until the outputs are dropped, and if those outputs are appended to a list, they never are.

8. Freezing parameters

To fine-tune only part of a model, set p.requires_grad_(False) on the parameters you want frozen. Autograd then computes no gradient for them — their .grad stays None, as you can check with a frozen nn.Linear weight while its bias still gets a gradient — and if no tensor upstream needs a gradient, it skips recording that part of the graph entirely, saving activation memory. Two traps: an optimiser built over model.parameters() still holds the frozen tensors (harmless for SGD and AdamW, which skip parameters with grad is None, but wasteful for optimiser state if they were ever unfrozen); and freezing by wrapping a submodule's forward in no_grad blocks gradients to everything before it as well, which is right for a frozen encoder at the start of the model and wrong for a frozen layer in the middle.

9. torch.autograd.grad and higher-order gradients

loss.backward() accumulates into leaves. torch.autograd.grad(outputs, inputs) instead returns the gradients with respect to the inputs you name, leaf or not, and touches no .grad. It is the functional way to ask for a gradient, used inside losses and in research code.

With create_graph=True, the backward computation is itself recorded, so the returned gradient has a grad_fn and can be differentiated again. For y = x³ at x = 2 (checked on 2.14): the first grad returns 12 (3x²) with a grad_fn, and a second grad of that returns 12 (6x). Uses include gradient penalties (a GAN discriminator penalised on the norm of its input gradient), Hessian–vector products for second-order analysis, and meta-learning. Cost: the backward pass's own intermediates are stored, so memory roughly doubles, and every operation on the path needs a differentiable backward.

10. Hooks

A hook is a function you register to be called during backward (or forward), with the power to observe or replace values.

  • t.register_hook(fn) — fn(grad) is called with the gradient flowing into tensor t; return a tensor to replace it. On 2.14, a hook returning g * 10 on a leaf makes its .grad ten times larger. Uses: per-tensor gradient clipping, gradient reversal layers, logging activation-gradient norms.
  • p.register_post_accumulate_grad_hook(fn) — fn(p) runs after p.grad has been accumulated for this backward. Its flagship use is fusing the optimiser step into backward: update p and set p.grad = None immediately, so gradients for the whole model never exist at once. The PyTorch tutorial on this technique reports large peak-memory savings for big models.
  • Module hooks — register_forward_hook, register_forward_pre_hook and register_full_backward_hook on an nn.Module see the module's inputs and outputs, or the gradients with respect to them. pt4 uses forward hooks to capture activations.

Every register_* returns a handle; call handle.remove() when done, or the hook stays forever — a quiet source of slowdowns and memory leaks in notebooks.

11. Writing your own autograd.Function

Sometimes you need a backward that is not the true derivative of the forward, or is cheaper or more stable than what autograd would derive. You subclass torch.autograd.Function. The current recommended style separates the forward from the context setup:

class RoundSTE(torch.autograd.Function):
    @staticmethod
    def forward(x):                      # no ctx: pure computation
        return x.round()

    @staticmethod
    def setup_context(ctx, inputs, output):
        pass                             # nothing to save for an STE

    @staticmethod
    def backward(ctx, grad_out):
        return grad_out                  # straight-through: pretend d(round)/dx = 1

y = RoundSTE.apply(x)                    # always call .apply, never forward()

Rules: backward returns one value per input of forward, with None for inputs that are not tensors or do not need gradients. Save tensors with ctx.save_for_backward(...) (which participates in the version check from pt1) and non-tensors as attributes on ctx. If forward modifies an input in place, declare it with ctx.mark_dirty. The older style — forward(ctx, x) doing both — still works.

Test every custom Function whose backward is meant to be exact with torch.autograd.gradcheck, which compares your backward with finite differences — in float64. On 2.14 a correct x² Function passes gradcheck in float64 and fails in float32 with "Jacobian mismatch", because finite differences in float32 lose too many digits; gradcheck also warns when inputs are not double precision. A straight-through estimator deliberately fails gradcheck, so test it by asserting that its backward returns the input gradient unchanged.

12. Python control flow, shared weights and non-differentiable points

Because the graph is recorded as the code runs, ordinary Python control flow just works. A loop that runs a layer a data-dependent number of times records that many nodes; an if on a Python value records only the branch taken; a recursive tree model records the tree it walked. Gradients flow only through the operations that actually ran this time. The flip side is that an if on a tensor value (if loss > 5:) needs that value on the CPU, which is a synchronisation on GPU (pt12), and the branch decision itself has no gradient — autograd differentiates the path taken, never the choice of path.

A parameter used in several places — a tied input embedding and output projection (pt4, pt10), a layer applied twice — appears once as a leaf with several outgoing edges. Backward sums the gradients arriving along every edge before the leaf's AccumulateGrad node runs, so the tied weight receives the total gradient of both uses. Nothing special is needed, which is why weight tying in PyTorch is one assignment.

Some operations have no useful gradient at all. Integer tensors cannot require gradients ("Only Tensors of floating point and complex dtype can require gradients"), so argmax, round, comparisons, indexing with computed indices and sampling from a categorical distribution all cut the gradient: the output of argmax has requires_grad=False. That is why discrete choices need tricks — the straight-through estimator, Gumbel-softmax relaxations, or policy-gradient estimators in reinforcement learning. At points where a function has a kink, PyTorch picks a convention, checked on 2.14: the derivative of relu at 0 is 0, of abs at 0 is 0, and when max() or amax() has ties the gradient is split evenly between the tied elements (each of two equal maxima gets 0.5), whereas max(dim=…) sends the whole gradient to the single index it returned. These conventions rarely matter for training, but they explain otherwise puzzling gradient values in tests.

13. NaN gradients from finite forwards

Some functions are finite where their derivatives are not. On 2.14:

q = torch.tensor([0.0], requires_grad=True)
(q.sqrt() * 0).sum().backward()
q.grad          # tensor([nan]): d sqrt/dq at 0 is inf, and 0 · inf = nan

The same happens with log(0), x / x.norm() at a zero vector, acos(±1) and pow(x, 0.5). A particularly sneaky version uses torch.where to "avoid" the bad region:

x = torch.tensor([-1.0, 4.0], requires_grad=True)
y = torch.where(x > 0, x.sqrt(), torch.zeros_like(x))   # forward is finite
y.sum().backward(); x.grad      # tensor([nan, 0.2500])

The forward never uses sqrt(-1), but backward computes the sqrt gradient for every element and then multiplies the unselected one by 0, and 0 · NaN is NaN. The fix is the "double where": make the dangerous input safe first, safe = torch.where(x > 0, x, torch.ones_like(x)), then apply the function to safe; the gradient becomes [0, 0.25]. Adding a small epsilon (sqrt(x + 1e-12), x / (x.norm() + eps)) is the other standard guard. To locate the first NaN in a large model, wrap the step in torch.autograd.detect_anomaly(): on 2.14 it raises "Function 'SqrtBackward0' returned nan values in its 0th output" and prints the forward line that created that node. It slows everything down noticeably, so use it only while debugging (pt9 builds the full NaN-hunting workflow).

How the engine schedules backward

The autograd engine is C++. When you call backward, it first walks the graph from the root to count, for every node, how many gradients will flow into it (its dependencies). It then runs a ready queue: a node becomes ready when all its incoming gradients have arrived and been summed. On CPU the work runs on the calling thread; for CUDA tensors there is a worker thread per device, and each backward op is queued on the same CUDA stream its forward ran on, so the backward pass is as asynchronous as the forward. Because nodes run as soon as they are ready, gradients for the last layers become available first — which is exactly what DDP exploits to start all-reducing gradient buckets while earlier layers are still computing (pt11).

Memory over time: why peak memory is at the start of backward

During the forward pass, saved tensors accumulate layer by layer, so memory climbs to its peak at the end of the forward and start of backward. As backward proceeds, each node releases its saved tensors after use while gradients for parameters are allocated. For a deep network the activation release dominates, and memory falls through the backward. This shape — a ramp up and a ramp down per step — is what you see in a memory timeline (pt7), and it is why activation checkpointing (saving fewer tensors in forward and recomputing them in backward) attacks the peak directly.

Saved-tensor hooks: deciding where activations live

torch.autograd.graph.saved_tensors_hooks(pack, unpack) lets you intercept every tensor autograd saves. pack is called at save time and can return anything — a CPU copy, a compressed form, a file handle; unpack turns it back into a tensor in backward. The built-in torch.autograd.graph.save_on_cpu(pin_memory=True) uses this to offload activations to host memory during forward and bring them back in backward, trading PCIe bandwidth for GPU memory. Activation checkpointing in its non-reentrant form (pt7) is also built on this mechanism: pack stores nothing but a recipe, and unpack recomputes.

The reentrant problem in custom Functions and checkpointing

A custom Function's backward runs inside the engine. If it calls autograd itself — running a forward under enable_grad and calling backward — that nested ("reentrant") backward runs as a separate graph traversal. The older reentrant implementation of activation checkpointing works this way and has real limitations: it does not support torch.autograd.grad, needs at least one input that requires grad, and recomputes the whole segment. That is why the docs recommend use_reentrant=False; on 2.14 calling checkpoint without the argument still only warns ("should be passed explicitly"), even though the warning text says that from 2.9 it would raise — pass it explicitly anyway.

Forward-mode AD and torch.func

Reverse mode computes v·J in one backward pass per output direction; forward mode computes J·u in one forward pass per input direction, carrying a tangent alongside each value. Forward mode wins when there are few inputs and many outputs — a Jacobian–vector product for sensitivity analysis, or one directional derivative. PyTorch supports it through torch.autograd.forward_ad and, more conveniently, torch.func.jvp. The torch.func module (formerly functorch) offers JAX-style composable transforms — grad, vjp, jvp, vmap, jacrev, hessian — over pure functions of parameters, which is the cleanest way to get per-example gradients (vmap(grad(f))) or Hessians. pt14 compares this style with JAX, where it is the only style.

Multiple losses, multiple backward calls, and partial graphs

When a model has several losses — a main loss and an auxiliary loss, or a generator and discriminator — the cheapest correct pattern is usually to sum them and call backward once: (loss_a + 0.1 * loss_b).backward() runs one traversal and frees the graph once. Calling backward on each loss separately needs retain_graph=True on all but the last, traverses the shared part twice, and keeps the shared saved tensors alive in between. torch.autograd.backward([loss_a, loss_b], [None, None]) runs several roots in one traversal. When different losses must update different parameter sets (as in a GAN), use torch.autograd.grad(loss, params_subset) or inputs= on backward to restrict which leaves receive gradients, and detach the tensors that cross the boundary so one loss does not push gradients into the other network.

When autograd's derivative is the wrong one

Autograd differentiates the code you wrote, not the mathematical function you meant. torch.norm(x) written as x.pow(2).sum().sqrt() has a NaN gradient at zero; a log-sum-exp written naively overflows in forward and backward; a softmax followed by log has a backward that underflows where log_softmax does not. Library functions such as F.cross_entropy, torch.logsumexp and F.normalize (which clamps the norm with an epsilon) exist precisely because their forward and backward were written for stability. Prefer them, and when you write a custom formula, consider a custom Function whose backward uses the stable analytic form — that is how FlashAttention-style kernels (gpu7) and fused cross-entropy implementations save both memory and accuracy.

Failure mode: evaluation runs out of memory

Symptom: training fits, but the evaluation loop OOMs or memory grows per batch. Cause: no no_grad/inference_mode, so every batch builds a graph; combined with appending outputs (or a loss tensor) to a list, every graph stays alive. Fix: wrap evaluation in torch.inference_mode(), call model.eval(), and log Python numbers (loss.item(), accepting the sync) or detached CPU tensors.

Failure mode: gradients that grow or are stale

Symptom: loss behaves as if the learning rate were rising, then diverges; or gradient norms grow linearly with steps. Cause: zero_grad missing or in the wrong place — after backward instead of before it, or once per epoch instead of per step. With gradient accumulation the bug is the opposite placement: zeroing inside the micro-batch loop throws away all but the last micro-batch. pt6 lays out the correct loop. A quick check: log the global gradient norm for the first few steps; it should not trend upward on a stable model.

Failure mode: "backward through the graph a second time"

Symptom: crash on the second iteration, typically in recurrent models, models with persistent state (memory tokens, running statistics you wrote yourself), or exponential-moving-average teachers. Cause: a tensor carried across iterations still holds last iteration's graph. Fix: detach() carried state at iteration boundaries; update EMA weights under no_grad. Resist the forum fix of retain_graph=True: it hides the bug and grows memory every step, because each iteration's graph now links to all previous ones.

Failure mode: frozen layers that move, trainable layers that don't

Symptom: a "frozen" backbone's weights change, or a newly added head never learns. Causes: freezing set after the optimiser captured parameter groups with weight decay (decoupled weight decay in AdamW only touches parameters with gradients, but momentum from earlier steps keeps moving them), a parameter re-created after the optimiser was built (the optimiser updates the old tensor), a tensor moved to the device after creation so it is not the leaf the optimiser holds, or a detach() left in the forward that cuts the head off from the loss. Diagnose by checking which parameters have non-None .grad after one backward, and by comparing parameter checksums before and after a step.

Failure mode: NaN gradients with finite loss

Symptom: loss is finite at step n, NaN at step n+1 because the update was NaN. Causes from the body: sqrt/log/norm at zero, where-masking an unsafe branch, division by a sum that can be zero (masked means over empty masks), and in mixed precision overflow in backward (pt7). Tools: detect_anomaly to locate the op; a hook on each parameter that asserts torch.isfinite(grad).all() to locate the layer; and clip_grad_norm_(..., error_if_nonfinite=True) to stop on the first bad step rather than training on garbage.

Observability

Teams that train large models log the global gradient norm every step (the value clip_grad_norm_ returns), per-layer gradient norms periodically, and the fraction of steps where clipping engaged. A gradient-norm spike that precedes a loss spike is the standard early warning in large-model training, discussed in pt9. These metrics are nearly free: the norm is computed anyway if you clip.

L.backward(); print("grads w x b:", w.grad.item(), x.grad.item(), b.grad.item())

class Cube(torch.autograd.Function):
    @staticmethod
    def forward(ctx, t): ctx.save_for_backward(t); return t ** 3
    @staticmethod
    def backward(ctx, g): (t,) = ctx.saved_tensors; return 3 * t ** 2 * g
t64 = torch.randn(5, dtype=torch.float64, requires_grad=True)
print("gradcheck:", torch.autograd.gradcheck(Cube.apply, (t64,)))
  1. Step 1 prints the chain PowBackward0 → ReluBackward0 → AddBackward0 → MulBackward0 → AccumulateGrad, and grads 28, 42, 14 — matching the body's trace.
  2. Step 2: w.grad accumulates (the 28 from step 1 plus two more backward passes of 2·(w·x)·x = 24); the third backward fails because the second freed the graph.
  3. Step 3: only the inference-mode tensor reports is_inference() == True, and it is rejected by autograd.
  4. Step 4: naive gives [nan, 0.25]; safe gives [0, 0.25].
  5. Step 5 prints True. Break the backward (return 2 * t * g) and watch gradcheck fail; switch to float32 and watch even the correct version fail.
Find the bug: an RNN language model that crashes, then leaks, then stops learning

This truncated-BPTT loop trains a small LSTM language model. Version 1 crashed on the second batch with "Trying to backward through the graph a second time". Someone "fixed" it. Now memory grows every batch and, after a few hundred steps, loss stops improving even though the learning rate is fine. Find every bug.

hidden = model.init_hidden(batch_size)
for x, y in loader:
    out, hidden = model(x, hidden)
    loss = F.cross_entropy(out.view(-1, V), y.view(-1))
    loss.backward(retain_graph=True)      # the "fix"
    optimizer.step()
    history.append(loss)
    if step % 100 == 0:
        model.eval()
        val = evaluate(model)             # evaluate() runs the val loader and returns a float
    optimizer.zero_grad()
Answer

Bug 1 — hidden state carries the graph across batches. hidden returned by this batch is the input to the next, so batch 2's graph links back into batch 1's. The original crash was backward walking into batch 1's freed graph. retain_graph=True stopped the crash by keeping every batch's graph alive, so each backward now traverses the entire history (slower every step) and memory grows without bound. Fix: hidden = tuple(h.detach() for h in hidden) at the start of each iteration (truncated BPTT), and remove retain_graph=True.

Bug 2 — the history list keeps graphs alive. history.append(loss) stores the loss tensor with its grad_fn, which references every saved activation of that step. Even after fixing bug 1, memory grows by one step's activations per iteration. Fix: history.append(loss.item()) (a sync per step; acceptable here, or log every N steps) or loss.detach().

Bug 3 — eval() is never undone. After the first evaluation the model stays in eval mode, so dropout is off for the rest of training; if the model had BatchNorm it would also stop updating its statistics. Symptom: training loss improves faster for a while (no dropout noise) and validation stalls, read as "stops learning". Fix: call model.train() after evaluate, and make evaluate itself run under torch.inference_mode() and restore the previous mode.

Not a bug, but worth saying: zero_grad() at the end of the loop is fine — it runs before the next backward. The common form puts it first; both are correct as long as exactly one zero_grad happens between consecutive steps.

Find the bug: the cosine-similarity loss that produces NaN on step 1

A contrastive loss computes sim = (a * b).sum(-1) / (a.pow(2).sum(-1).sqrt() * b.pow(2).sum(-1).sqrt()). Some rows of a are all zeros (padding embeddings). The loss is finite, but the first update makes every parameter NaN. Why, and what is the minimal fix?

Answer

For a zero row the norm is sqrt(0), whose derivative is infinite; the forward also divides 0 by 0, giving NaN similarity for that row — if the row is then masked out of the loss with a multiplication by 0 or a where, the forward loss becomes finite again but backward still computes the gradient through the NaN and the infinite sqrt derivative, and 0 · NaN = NaN reaches every parameter that fed a. Minimal fix: use F.cosine_similarity(a, b, dim=-1, eps=1e-8) or F.normalize, which clamp the norm away from zero, and drop padding rows before computing the similarity rather than masking afterwards. Confirm with detect_anomaly, which will name SqrtBackward0 or DivBackward0.
