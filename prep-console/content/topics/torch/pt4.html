A team adds a stack of adapter layers to a pretrained model. They write self.adapters = [Adapter(d) for _ in range(n_layers)], train for a day, and evaluation looks exactly like the base model. It is exactly the base model: the adapters lived in a Python list, so model.parameters() never returned them, the optimiser never touched them, and the checkpoint did not even contain them. Another team fine-tunes a vision model with batch size 2 per GPU and watches validation accuracy collapse, because BatchNorm in training mode computes statistics from two images. A third loads a checkpoint with strict=False "because of some prefix issue" and ships a model in which every attention layer silently kept its random initial weights.

All three are failures of the same piece of machinery: nn.Module. It looks like a thin base class — you subclass it, assign layers in __init__, write forward — but it does a lot behind the scenes. It registers parameters, buffers and submodules so that optimisers, device moves, checkpoints and mode switches can find them. It names every tensor with a dotted path that becomes the key in a saved file. It carries a training flag that changes what dropout and normalisation layers compute. It lets you attach hooks that see inputs, outputs and gradients. And its default initialisation is a specific formula that transformer code almost always replaces.

ML-debugging interviews lean on this because the bugs are realistic and silent: the model runs, the loss even goes down, and the problem is invisible unless you know what registration, state dicts and modes do. "Which of these layers will be trained?", "why is this checkpoint loading half the model?", "why is the eval loss different from what you get on the training data in eval mode?", "count the parameters of this model" — each has a precise answer.

This lesson covers how registration works and its pitfalls (plain tensors, Python lists, ModuleDict rules), parameters versus buffers, state_dict and the load-time mismatches you will meet, exactly what train() and eval() change (with BatchNorm traced by hand), forward and backward hooks, default and GPT-style initialisation and how to check it, weight tying, and counting parameters correctly — using GPT-2 small, worked through to the last parameter, and nanoGPT's model file as the real code to compare with.

Think of an nn.Module as a filing cabinet with three labelled drawers and a switch on the front. Whenever you assign something in __init__, the cabinet looks at it and decides which drawer it belongs in:

  • an nn.Parameter — a tensor you want trained — goes into the parameters drawer;
  • another nn.Module — a layer, a block — goes into the submodules drawer, and is itself a cabinet with its own drawers;
  • a tensor you register with register_buffer — state that is not trained, such as BatchNorm's running averages or a causal mask — goes into the buffers drawer.

Anything else — a plain tensor, a Python list of layers, a number — is left on top of the cabinet. Every whole-model operation opens the drawers, recursively, and ignores what is on top: parameters() collects the parameters drawer of every cabinet for the optimiser; .to("cuda") moves parameters and buffers; state_dict() writes out parameters and buffers under their drawer paths (blocks.3.attn.proj.weight); train() and eval() flip the switch on every cabinet.

The switch is the training flag, self.training. Layers that behave differently while learning read it: dropout drops only when it is True; BatchNorm uses the current batch's statistics and updates its running averages only when it is True. It has nothing to do with gradients — that is autograd's recorder from pt3, switched with no_grad.

Here is a small module and what each line does to the cabinet:

class MLP(nn.Module):
    def __init__(self, C):
        super().__init__()                       # creates the three empty drawers
        self.up = nn.Linear(C, 4 * C)             # submodule "up" (with its own up.weight, up.bias)
        self.down = nn.Linear(4 * C, C)           # submodule "down"
        self.gain = nn.Parameter(torch.ones(C))   # parameter "gain"
        self.register_buffer("calls", torch.zeros((), dtype=torch.long))  # buffer "calls"
        self.note = "relu MLP"                    # plain attribute: ignored
    def forward(self, x):                         # x: (B, T, C)
        self.calls += 1                           # buffers can be updated in forward
        return self.down(self.up(x).relu()) * self.gain

list(MLP(8).state_dict()) is ['gain', 'calls', 'up.weight', 'up.bias', 'down.weight', 'down.bias'] — the module's own parameters and buffers first, then each submodule's under its prefix. MLP(8).to("cuda") moves all six tensors. MLP(8).parameters() yields five tensors (not calls). MLP(8).eval() flips training on the MLP and on up and down. And note is just a Python attribute — fine for configuration strings, wrong for tensors.

Where the analogy breaks: a filing cabinet does not care where the same document is filed twice, but a module can hold one Parameter in two drawers — that is weight tying — and then parameters() de-duplicates it while state_dict() lists it under both paths. And unlike a cabinet, a module has behaviour: its forward method, which you call by calling the module itself (model(x), never model.forward(x), because calling the module also runs any hooks).

If you remember one sentence: nn.Module only knows about Parameters, buffers and submodules you registered; every optimiser, device move, checkpoint and mode switch works through that registry, and the training flag changes layer behaviour, not gradient recording.

1. How registration works

nn.Module overrides Python's attribute assignment (__setattr__). When you write self.proj = nn.Linear(768, 768), it sees a Module and stores it in an internal ordered dictionary, self._modules["proj"]. self.gain = nn.Parameter(torch.ones(768)) goes into self._parameters["gain"]. self.register_buffer("mask", torch.tril(torch.ones(T, T))) goes into self._buffers["mask"]. Everything else goes into the ordinary instance dictionary. You must call super().__init__() before assigning any of these, or the internal dictionaries do not exist yet and the assignment raises.

Every recursive operation walks those three dictionaries and builds dotted names from the path: a parameter weight inside proj inside the third element of blocks is blocks.2.proj.weight. Those names are what named_parameters() yields, what keys the state_dict, and what optimiser parameter groups and FSDP wrapping policies (pt11) match on.

A run on 2.14 with a module that has a registered Linear, a Python list of two Linears, a plain tensor attribute, two buffers (one non-persistent) and a BatchNorm:

named_parameters: ['lin.weight', 'lin.bias', 'bn.weight', 'bn.bias']
named_buffers:    ['mask', 'cache', 'bn.running_mean', 'bn.running_var',
                   'bn.num_batches_tracked']
state_dict keys:  ['mask', 'lin.weight', 'lin.bias', 'bn.weight', 'bn.bias',
                   'bn.running_mean', 'bn.running_var', 'bn.num_batches_tracked']

The two Linears in the list and the plain scale tensor appear nowhere. The non-persistent buffer cache is a buffer (it moves with .to()) but is not in the state_dict.

2. Containers: ModuleList, ModuleDict, Sequential

To hold a variable number of layers, use a container that registers its contents:

  • nn.ModuleList([...]) registers each element under its index (blocks.0, blocks.1, …). It has no forward; you loop over it yourself, which is what transformers do.
  • nn.ModuleDict({...}) registers each value under its key. Keys must be strings and cannot contain a dot (on 2.14: "module name can't contain \".\", got: a.b"), because dots are the path separator. Iteration order is insertion order.
  • nn.Sequential(...) registers its elements and has a forward that applies them in order — good for simple stacks, awkward when a layer needs more than one input.
  • nn.ParameterList and nn.ParameterDict do the same for bare Parameters.

Pitfalls beyond the plain-list bug: replacing a ModuleList element in place (self.blocks[3] = NewBlock()) works, but an optimiser built earlier still holds the old block's parameters; and building the list inside forward creates new, unregistered, randomly initialised layers on every call.

3. Parameters versus buffers

A parameter is an nn.Parameter, a tensor subclass with requires_grad=True by default; model.parameters() hands it to the optimiser. A buffer is model state that must travel with the model but is not trained by gradient descent:

  • BatchNorm's running_mean, running_var and num_batches_tracked — updated by the layer itself in training mode.
  • A precomputed causal mask, as in nanoGPT's non-flash attention path (self.register_buffer("bias", torch.tril(...))).
  • Rotary-embedding frequency tables or cached sin/cos values — usually persistent=False, since they can be recomputed and should not bloat or constrain checkpoints.
  • Exponential-moving-average statistics, quantisation scales, vocab masks.

Why not just use a Parameter with requires_grad=False? Because the optimiser would still hold it, weight decay code that iterates over parameter groups might touch it, and parameter counts would include it. Buffers say "state, not weights".

4. state_dict, and loading it safely

model.state_dict() returns an ordered dictionary from dotted names to tensors (parameters and persistent buffers), detached from autograd. It is the unit of saving: torch.save(model.state_dict(), path) rather than pickling the whole model object, so the file contains tensors and names, not your class definitions (pt8 covers why that matters for security and refactoring).

model.load_state_dict(sd, strict=True) copies values into existing tensors by name. With the default strict=True, any mismatch raises, as on 2.14:

Error(s) in loading state_dict for M:
    Missing key(s) in state_dict: "lin.bias".
    Unexpected key(s) in state_dict: "extra.weight".

With strict=False it loads what matches and returns _IncompatibleKeys(missing_keys=['lin.bias'], unexpected_keys=['extra.weight']). Shape mismatches raise either way. Rules that prevent most loading bugs:

  • Prefixes. DistributedDataParallel and DataParallel wrap your model as .module, so a state_dict saved from the wrapper has keys like module.encoder.weight. torch.compile returns a wrapper whose state_dict keys start with _orig_mod.. Save the unwrapped model's state_dict, or strip the prefix with a dictionary comprehension at load time.
  • Never ignore the return value of strict=False. Assert that missing_keys contains only what you expect (a new head) and log unexpected_keys.
  • Dtype and device. load_state_dict copies into the model's existing tensors, converting dtype and device to match them. To load onto the meta device or adopt the checkpoint's tensors directly, use assign=True (pt8).

5. train() and eval(): exactly what changes

model.train() sets self.training = True on the model and all submodules; model.eval() is model.train(False). On 2.14, after m.eval(), m.training, m.bn.training and m.lin.training are all False. The modules that care:

Dropout in training mode zeroes each element with probability p and multiplies survivors by 1/(1−p) — with p = 0.5, a vector of ones becomes something like [0, 0, 2, 0, 0, 0]. In eval mode it returns its input unchanged. Because of the scaling during training, no rescaling is needed at inference ("inverted dropout", dl8).

BatchNorm in training mode normalises each channel with the current batch's mean and (biased) variance, and updates its running statistics: running = (1 − momentum) · running + momentum · batch_statistic, with momentum 0.1 by default and the unbiased batch variance used for the running estimate. A hand-checked trace on 2.14 with a fresh BatchNorm1d(2) (running mean 0, running variance 1) and the batch [[1, 10], [3, 30]]:

ChannelBatch meanUnbiased batch varianceNew running meanNew running variance
0220.9·0 + 0.1·2 = 0.20.9·1 + 0.1·2 = 1.1
1202000.9·0 + 0.1·20 = 2.00.9·1 + 0.1·200 = 20.9

In eval mode BatchNorm uses those running values and does not update them. That is why the same input gives different outputs in the two modes, why evaluating in training mode quietly corrupts the running statistics with evaluation data, and why tiny batches are a problem: statistics from two samples are noise, and with one sample per channel training mode refuses outright ("Expected more than 1 value per channel when training"). LayerNorm and RMSNorm normalise each example on its own and behave identically in both modes, which is one reason transformers use them.

Other modules check the flag too. nn.MultiheadAttention uses an inference fast path only when not training; F.scaled_dot_product_attention, being a function, does not know the mode, so its dropout_p must be set to 0 in eval by the calling module — the docs show dropout_p=(self.p if self.training else 0.0), and forgetting it is a planted bug in pt10. Any custom module can branch on self.training.

6. Modules versus torch.nn.functional

Almost every layer has a stateless functional twin in torch.nn.functional (imported as F): nn.Linear and F.linear, nn.Dropout and F.dropout, nn.LayerNorm and F.layer_norm, nn.CrossEntropyLoss and F.cross_entropy. The module version owns its parameters and knows the training flag; the functional version takes everything as arguments. The rule: if it has learnable weights or mode-dependent behaviour, use the module so registration and train/eval work; if it is a pure function of its inputs (F.relu, F.softmax, F.cross_entropy), the functional form is simpler.

The trap sits exactly on that boundary. F.dropout(x, p=0.1) has a training argument that defaults to True — it does not read any module's flag — so a model that calls F.dropout(x, 0.1) in its forward keeps dropping out during evaluation. Write F.dropout(x, 0.1, training=self.training) or use an nn.Dropout submodule. F.scaled_dot_product_attention's dropout_p has the same property, as noted above. Likewise F.batch_norm needs you to pass the running statistics and the training flag yourself. When reviewing code for a debugging round, every functional call with a mode-dependent behaviour is a place to look.

7. Walking a model: modules, children, apply

Four methods let you visit the tree. children() yields direct submodules; modules() and named_modules() yield every module recursively, starting with the model itself, with dotted names; apply(fn) calls fn on every submodule (children first, then the parent) and is the standard way to run an init function. Typical uses: count layers of a type (sum(isinstance(m, nn.Linear) for m in model.modules())), swap all nn.GELU for another activation by assigning to the parent's attribute, freeze every normalisation layer, or attach a forward hook to each block. Swapping must be done on the parent (setattr(parent, name, new)), since assigning to the loop variable changes nothing. print(model) shows the registered tree — another quick registration check: a layer that does not appear in the printout is not registered.

8. Moving and casting modules

model.to(device), .cuda(), .half(), .bfloat16() and .to(dtype) on a module modify its parameters and buffers in place and return the module itself (on 2.14, m.to(torch.float64) is m is True) — unlike tensor.to, which returns a new tensor. Two consequences: build the optimiser after moving the model (on older versions moving could replace parameter tensors; today the parameter objects are kept, but the habit costs nothing), and casting a module to float16 also casts BatchNorm's running statistics and every buffer, which is often not what you want — mixed precision (pt7) keeps weights in float32 and casts per operation instead.

Tensors created inside forward must follow the input: torch.arange(T, device=x.device), torch.zeros_like(x), x.new_zeros(shape). A bare torch.arange(T) works on CPU and fails on GPU with "Expected all tensors to be on the same device".

9. Hooks on modules

Modules accept three kinds of hook (pt3 covered tensor-level hooks):

  • register_forward_pre_hook(fn) — fn(module, args) runs before forward and may return modified inputs.
  • register_forward_hook(fn) — fn(module, args, output) runs after forward and may return a replacement output.
  • register_full_backward_hook(fn) — fn(module, grad_input, grad_output) runs when gradients with respect to the module's inputs have been computed.

Hooks let you instrument a model you do not want to edit: capture activations for analysis or distillation, record per-layer activation statistics to check initialisation, log output shapes to debug a shape error (pt2's method), or add a steering vector to a layer's output. Each call returns a RemovableHandle; keep it and call .remove() when done. Store output.detach(), not output, or the hook keeps the graph alive. Hooks run only when you call the module (model(x)); calling model.forward(x) directly skips them.

10. Initialisation: the defaults and what transformers use

PyTorch initialises layers in their constructor via reset_parameters(). For nn.Linear on 2.14 the code is init.kaiming_uniform_(self.weight, a=math.sqrt(5)), with a comment noting this equals U(−1/√in_features, 1/√in_features); the bias uses the same bound. For a 768-input layer the bound is 1/√768 ≈ 0.0361, and the standard deviation of a uniform distribution on ±b is b/√3 ≈ 0.0208 (measured: 0.0208). Convolutions use the same rule with fan_in = in_channels × kernel area. nn.Embedding uses N(0, 1) — standard deviation 1 (measured: 0.99), about fifty times larger than a typical transformer weight. Normalisation layers start with weight 1 and bias 0.

GPT-2-style models replace these. nanoGPT's _init_weights, applied with self.apply(...), sets every Linear weight and every Embedding to N(0, 0.02) and biases to zero, then walks named_parameters() and re-initialises every parameter whose name ends in c_proj.weight — the projections that write into the residual stream — with standard deviation 0.02/√(2·n_layer), "per GPT-2 paper". The reasoning: the residual stream is a sum of 2·n_layer contributions (attention and MLP in each block); if each has variance σ², the sum has variance 2·n_layer·σ², so scaling σ by 1/√(2·n_layer) keeps the stream's scale independent of depth.

The quickest check that an initialisation is sane is the loss at step 0. For a V-way softmax with small logits, the predicted distribution is close to uniform and the cross-entropy is ln V: ln 50,257 ≈ 10.82 for GPT-2's vocabulary, ln 10 ≈ 2.30 for a 10-class classifier. Karpathy's Recipe calls this "verify loss @ init". A step-0 loss well above ln V means the logits are too large — confident random guesses — and the first hundred steps are spent undoing the initialisation.

11. Weight tying

A language model maps token ids to vectors with an embedding matrix of shape (V, C) and maps final hidden states back to vocabulary logits with an output projection nn.Linear(C, V, bias=False), whose weight is also (V, C). Weight tying makes them the same tensor. In nanoGPT it is one line:

self.transformer.wte.weight = self.lm_head.weight   # assign the same Parameter

Both modules now refer to one Parameter. In the forward pass it is used twice; in backward, autograd sums the two gradient contributions before accumulating into its .grad (pt3). It saves V × C parameters — 38.6M for GPT-2 small — and, empirically, tends to help small and medium language models. Bookkeeping consequences, checked on 2.14: g.head.weight is g.wte.weight is True; parameters() yields the tensor once; state_dict() contains both wte.weight and head.weight, pointing at the same storage. Tying must be re-established if you re-create either module after construction, and some tools need special handling for shared tensors: safetensors refuses to save them unless deduplicated (pt8), and FSDP needs both uses wrapped in the same unit (pt11).

12. Writing a custom layer correctly: RMSNorm

Putting the rules together, here is a custom layer written the way reviewers expect. RMSNorm (dl4) divides each feature vector by its root-mean-square and multiplies by a learned per-channel gain:

class RMSNorm(nn.Module):
    def __init__(self, dim: int, eps: float = 1e-6):
        super().__init__()
        self.eps = eps                                 # plain float: config, not state
        self.weight = nn.Parameter(torch.ones(dim))    # registered, trained, saved
    def forward(self, x):                              # x: (..., dim)
        xf = x.float()                                 # compute the statistic in float32
        rms = xf.pow(2).mean(dim=-1, keepdim=True).add(self.eps).rsqrt()
        return (xf * rms).to(x.dtype) * self.weight
    def extra_repr(self):
        return f"{self.weight.shape[0]}, eps={self.eps}"

Each line answers one of the lesson's questions. The gain is an nn.Parameter, so it trains, moves and saves; eps is a Python float because it is configuration. The mean uses keepdim=True so it broadcasts over the last axis (pt2). The statistic is computed in float32 and cast back, because a mean of squares in bfloat16 loses precision (pt1, pt7). There is no hidden state and no mode-dependent behaviour, so train and eval give identical outputs — test that. extra_repr makes print(model) show RMSNorm(768, eps=1e-06). And it initialises its gain to 1 so that, at step 0, the layer is a pure normalisation. On 2.14 PyTorch also ships nn.RMSNorm, so in real code prefer the built-in; writing it yourself is a common interview exercise precisely because it touches registration, broadcasting and dtype at once.

__call__, hooks and why you never call forward directly

model(x) goes through nn.Module.__call__, which runs global and per-module forward pre-hooks, then forward, then forward hooks, and sets up backward hooks when any are registered. Libraries rely on this path: FSDP2 (pt11) uses pre-forward hooks to all-gather a layer's sharded parameters just before it runs and post-forward hooks to free them; activation-checkpointing wrappers and quantisation observers attach the same way; torch.compile traces through __call__. Calling model.forward(x) bypasses all of it — in a distributed model that means running on unmaterialised shards. Treat forward as an implementation detail you define but never call.

The meta device, deferred initialisation and assign=True

Constructing a 70-billion-parameter model normally allocates and randomly initialises 280 GB of float32 before you load a checkpoint that overwrites every value. The meta device avoids this: with torch.device("meta"): model = Model(cfg) creates parameters with shapes and dtypes but no storage, in milliseconds (that is how the parameter counts above were computed). You then either call model.to_empty(device="cuda") and run an init function, or load real tensors with model.load_state_dict(sd, assign=True), which replaces the meta parameters with the checkpoint's tensors instead of copying into them (copying into meta tensors is impossible). With assign=True the model adopts the checkpoint's dtype and device, so it must already be what you want. Weight tying must be re-done after assigning, since assignment replaces the shared Parameter object in one module only.

Parameter groups and what "a parameter" means to the optimiser

Optimisers receive parameters, not modules, so per-parameter policy is expressed by grouping names. The standard transformer recipe excludes biases, normalisation weights and often embeddings from weight decay: iterate over named_parameters(), put tensors with p.dim() < 2 in a group with weight_decay=0.0, and the rest in the decayed group (nanoGPT's configure_optimizers does this by dimension). Bugs appear when a parameter ends up in two groups (the optimiser raises), in no group (it is silently never trained), or when tied weights are counted twice by a name-based rule. Logging the number of tensors and elements in each group at start-up catches all three.

Re-entrancy of train(): keeping parts in eval mode

model.train() recursively sets every submodule's flag, so a frozen BatchNorm you put in eval mode is flipped back the next time the training loop calls model.train(). The robust pattern overrides train on the parent: call super().train(mode), then set the frozen submodules to eval. The same issue affects frozen encoders in multimodal models and teacher networks embedded inside a student wrapper. A related trap: requires_grad_(False) freezes weights but BatchNorm's running statistics still update in training mode, because they are buffers changed in forward, not by gradients — "frozen" BatchNorm needs both eval mode and frozen parameters.

Initialisation through the lens of signal propagation

Kaiming initialisation chooses weight variance 2/fan_in so that, for ReLU networks, each layer's output has about the same variance as its input; Xavier chooses 2/(fan_in + fan_out) for tanh-like activations. PyTorch's a = √5 default yields variance 1/(3·fan_in), smaller than Kaiming's 2/fan_in — fine for shallow networks and for architectures with normalisation layers, which rescale activations anyway. Transformers with pre-norm blocks (pt10) are robust to the exact choice inside blocks but sensitive at the edges: the embedding scale sets the initial residual stream, and the output layer's scale sets the initial loss. That is why GPT-style init is a single small standard deviation plus a residual-specific scale, and why some recent recipes (such as the μP parameterisation) scale initialisation and learning rates by width so that hyperparameters transfer across model sizes.

functional_call: running a module with someone else's parameters

torch.func.functional_call(model, params_and_buffers, args) runs a module's forward with a dictionary of tensors substituted for its registered ones, without modifying the module. It turns an nn.Module into a pure function of its parameters, which is what torch.func.grad and vmap need for per-example gradients, ensembles of models evaluated in one batched call, and meta-learning inner loops (pt14 contrasts this with JAX, where it is the only style). Tied weights complicate it: the dictionary has two names for one tensor, and if the caller supplies different values under the two names, which one should win? That is the source of the "functional_call was passed multiple values for tied weights" warning nanoGPT's author noted under torch.compile; passing tie_weights=True (the default) makes functional_call keep tied parameters tied and insist the values agree.

Buffers and distributed training

Buffers raise questions parameters do not. Under DDP (pt11), buffers such as BatchNorm statistics are broadcast from rank 0 at the start of each forward by default, so ranks agree, at a communication cost — on 2.14 the flag is forward_sync_buffers (default None, meaning True), which replaced broadcast_buffers, deprecated in 2.13; parameters instead stay in sync because their gradients are averaged. A non-persistent buffer is recomputed on every rank and never saved, which is ideal for deterministic tables such as RoPE frequencies. Mutable buffers updated in forward — running averages, step counters — are also the main obstacle to torch.compile graph capture and CUDA graphs (pt12), because they make the forward pass mutate state.

Failure mode: layers that never train

Symptom: part of the model does not change, or a newly added component has no effect. Causes: layers in a Python list or dict; a parameter created in forward; parameters replaced after the optimiser was built; an accidental detach() or no_grad in forward. Detection: after one training step, compare a checksum of every named parameter before and after (p.detach().float().sum()), and check that every parameter that should train has a non-None .grad after backward. Log len(list(model.parameters())) and the parameter count at start-up and compare with what the architecture implies.

Failure mode: the checkpoint that loads half a model

Symptom: a fine-tuned or restored model performs like a random one in some component. Cause: load_state_dict(..., strict=False) with renamed layers or a prefix mismatch (module., _orig_mod., model. from a framework wrapper), with the return value ignored. Prevention: strict loading by default; when non-strict is necessary, assert on the missing keys; keep a unit test that saves and reloads the model and compares outputs on a fixed input.

Failure mode: train/eval mode mix-ups

Symptom: validation metrics noisy or slightly off; training metrics too good after the first evaluation; results that change with evaluation batch size. Causes: evaluating without model.eval() (dropout active, BatchNorm using and updating batch statistics); never returning to train() after evaluation; a frozen BatchNorm flipped back to training mode by a later model.train(). Prevention: an evaluate() function that records was_training = model.training, calls eval(), runs under inference_mode, and restores the previous mode in a finally block.

Failure mode: initialisation at the wrong scale

Symptom: step-0 loss far above ln V, a long "hockey stick" plateau, or exploding activations in deeper models. Causes: default nn.Embedding init N(0, 1) left in place next to N(0, 0.02) weights; a custom init applied only to top-level modules (forgetting apply recurses, or calling it before submodules exist); re-initialising after loading pretrained weights. Detection: print the step-0 loss and compare with ln V; register forward hooks that log each block's output standard deviation on the first batch.

Failure mode: buffers that drift

Symptom: a model's outputs at inference slowly differ from those at the end of training, or two replicas disagree. Causes: a mutable buffer updated in forward (a running average, a step counter, a cache) that keeps changing during evaluation because the module does not check self.training; or, in multi-GPU training without buffer synchronisation, each replica's BatchNorm statistics drifting apart so the saved rank-0 copy does not represent the others. Prevention: guard buffer updates with if self.training:, keep caches that must not be saved as persistent=False, and in distributed runs keep buffer syncing on or use SyncBatchNorm.

Guard rails in CI and at start-up

Cheap automated checks catch most module bugs before they cost a training run. At start-up, log the parameter count (total and trainable), the number of tensors in each optimiser group, and the model's printed structure; compare the count with a hand calculation like the GPT-2 table in the body — a drift of exactly one layer's worth of parameters is a registration bug. In continuous integration, run a save → load → compare-outputs round trip with strict=True, a one-step training test that asserts every trainable parameter changed, and an eval-mode determinism test (two forward passes in eval mode on the same input must agree exactly, which fails if dropout is still active somewhere, for instance via a functional call). These take seconds on CPU with a tiny configuration.

Find the bug: a fine-tuning wrapper with three silent failures

This wrapper adds a classification head to a pretrained encoder and a learnable temperature. After fine-tuning, accuracy equals the baseline linear probe, the temperature never moves from 1.0, and reloading the saved checkpoint gives different predictions from the in-memory model. Find the bugs.

class Classifier(nn.Module):
    def __init__(self, encoder, n_classes):
        super().__init__()
        self.encoder = encoder
        self.heads = {"main": nn.Linear(768, n_classes)}
        self.temp = torch.ones(1, requires_grad=True)
    def forward(self, x):
        with torch.no_grad():
            h = self.encoder(x)[:, 0]          # CLS token, (B, 768)
        return self.heads["main"](h) / self.temp

model = Classifier(encoder, 5)
opt = torch.optim.AdamW(model.parameters(), lr=2e-5)
...
torch.save(model.state_dict(), "ckpt.pt")
Answer

Bug 1 — the head is in a plain dict. self.heads is a Python dict, so the Linear is not registered: it is not in model.parameters() (the optimiser never updates it, so the head keeps its random initial weights), it would not be moved by model.to(device), and it is not in the state_dict. On reload, a fresh randomly initialised head is created, hence different predictions. Fix: self.heads = nn.ModuleDict({"main": nn.Linear(768, n_classes)}).

Bug 2 — the temperature is a plain tensor. torch.ones(1, requires_grad=True) gets gradients but is not a registered parameter, so AdamW never sees it (it stays at 1.0), a device move would leave it behind, and it is not saved. Fix: self.temp = nn.Parameter(torch.ones(1)). (A temperature also usually wants a positive parameterisation, such as self.log_temp with exp().)

Bug 3 — no_grad around the encoder. The intent was full fine-tuning (lr 2e-5 is a fine-tuning rate), but no_grad stops all gradients into the encoder, so only the head could ever learn — which is why accuracy matches the linear probe. If freezing was intended, write it explicitly with encoder.requires_grad_(False) and exclude its parameters from the optimiser; otherwise remove the no_grad. Also check that a frozen encoder with BatchNorm or dropout is in the mode you intend. Verification after fixing: one training step should change a checksum of the encoder's, the head's and the temperature's parameters, and a save/load round trip should reproduce outputs exactly.

Estimate: what does this model cost to train?

A decoder-only model has width 2,048, 24 layers, vocabulary 32,000, tied embeddings and no biases. Estimate the parameter count and the memory for weights, gradients and AdamW states in float32.

Answer

Per block about 12·C² = 12 × 2,048² ≈ 50.3M; × 24 ≈ 1.21B. Tied embedding 32,000 × 2,048 ≈ 65.5M. Norm weights are negligible (2 × 2,048 per block). Total ≈ 1.27B parameters. At 16 bytes per parameter (FP32 weights, gradients, two Adam moments): ≈ 20.4 GB before activations — so it fits on an 80 GB GPU with room for activations, but not on a 24 GB card without sharding (pt11), mixed-precision tricks (pt7) or a lower-memory optimiser.
