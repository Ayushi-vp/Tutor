A team rents eight top-end GPUs for a fine-tuning run. The training script is borrowed from a tutorial: a Dataset that opens an image file, decodes it, resizes and augments it, and a DataLoader with the default settings. The first epoch takes six hours. nvidia-smi shows GPU utilisation flickering between 0% and 100%, averaging about 20%. Nothing is wrong with the model; the GPUs are simply waiting. With num_workers=0, every image is decoded on the one Python thread that also drives the GPUs, and the GPUs finish each batch in a quarter of the time it takes to prepare the next. They paid for eight GPUs and are using about two.

The fix sounds like one argument — num_workers=8 — and it does make the job four times faster. Then new problems appear. Memory on the host climbs every hour until the kernel's out-of-memory killer ends the run, because the dataset kept a Python list of twelve million file paths and every worker gradually copied it. In a Docker container the workers die with "bus error", because shared memory is 64 MB by default. The augmentation random crops are identical across workers, because an RNG was created in the dataset's constructor. And when the team switches to a streaming IterableDataset to read from cloud storage, every sample shows up eight times per epoch, once per worker.

Input pipelines are the least glamorous part of training and one of the most common reasons expensive hardware sits idle. In interviews they appear in two forms: design questions ("how would you feed 64 GPUs from object storage?") and debugging questions ("GPU utilisation is 30% — what do you check?", "why is memory growing?", "why does each epoch see the same order?"). Strong answers depend on knowing the machinery underneath: what runs in the main process versus the workers, why workers are processes, how they start and what they copy, how batches travel back, and where the time goes.

This lesson builds that picture. It covers the two dataset types, the DataLoader's arguments and their defaults on PyTorch 2.14, the worker pipeline step by step, the GIL and the fork/forkserver/spawn story (which changed with Python 3.14), seeding and sharding, the reference-count memory trap from PyTorch issue #13246, pinned memory and non-blocking copies, collate functions and padding, samplers including the distributed one, and a method — with real numbers — for proving whether your input pipeline is the bottleneck and fixing it.

Think of training as a restaurant kitchen. The GPU is the head chef: extraordinarily fast, but only at cooking. Each batch is a set of plates that must be prepped — ingredients fetched from the store room (disk or network), washed and chopped (decoding, tokenising, augmenting), and arranged on a tray (collating into tensors). If the head chef also does all the prep, they spend most of the night chopping. The DataLoader is the kitchen's prep team: a manager (the main process) decides which ingredients go into which tray (the sampler), hands the orders to several prep cooks (worker processes), and the cooks place finished trays on a pass (a queue) where the chef can grab them. Pinned memory is a dedicated conveyor belt to the chef's station; non-blocking copies mean the chef does not stop cooking while the next tray rides the belt.

The design follows from three constraints:

  • Prep is mostly Python, and Python threads cannot run Python code in parallel because of the GIL (py8). So the cooks must be separate processes, each with its own interpreter.
  • Processes do not share Python objects. Each worker has its own copy of the dataset object, its own random number generators, and its own memory. Finished batches come back to the main process through shared memory rather than by copying through a pipe.
  • The GPU should never wait. So several batches are prepared ahead of time (prefetching), and the copy to GPU memory should overlap with computation.

Three numbers decide whether an input pipeline keeps up, and you can estimate all of them before writing code. The first is the GPU step time — how long one forward, backward and optimiser step takes for a batch; this is the rate at which batches are consumed. The second is the per-sample CPU cost — reading, decoding and transforming one example on one core — multiplied by the batch size, which gives the CPU time to produce one batch. The third is the number of cores you can devote to loading per GPU. Workers needed ≈ (per-sample cost × batch size) ÷ step time, rounded up with some headroom; if that exceeds the cores available, no DataLoader setting will save you and the work itself has to get cheaper (pre-processing offline, lighter decoding, GPU augmentation). The rest of the lesson is about making those workers actually run in parallel, start correctly, see the right data, not waste memory, and hand their batches to the GPU without stalling it.

Where the kitchen analogy breaks: real prep cooks share a pantry, but worker processes do not share Python objects — each starts with its own copy of the dataset, which is the root of both the memory trap and the duplicated-RNG trap. And unlike cooks, workers cannot be told "skip ahead"; with an IterableDataset each worker produces its own stream, and dividing the work is your job.

If you remember one sentence: the main process hands out indices, worker processes turn them into batches in parallel and ahead of time, and pinned, non-blocking copies hide the transfer — so the GPU should never wait, and when it does, you measure the wait and fix the slowest stage.

1. Dataset: map-style and iterable

A map-style dataset is any object with __getitem__(i) returning sample i and __len__ returning the count. It supports random access, so shuffling is just permuting indices.

class TokenFile(torch.utils.data.Dataset):
    def __init__(self, path, T):
        self.data = np.memmap(path, dtype=np.uint16, mode="r")   # no Python objects
        self.T = T
    def __len__(self):
        return (len(self.data) - 1) // self.T
    def __getitem__(self, i):
        chunk = self.data[i * self.T : (i + 1) * self.T + 1].astype(np.int64)
        x = torch.from_numpy(chunk[:-1]); y = torch.from_numpy(chunk[1:])
        return x, y                        # (T,), (T,): inputs and next-token targets

This is the pattern nanoGPT-style training uses: a memory-mapped array of token ids, slices for inputs and targets shifted by one, and an explicit cast from uint16 to int64 because embeddings and losses want int64 (pt1). Note the comment on the first line of __init__; it will matter in section 6.

An iterable-style dataset subclasses IterableDataset and implements __iter__. Use it when random access is impossible or expensive: a stream from a message queue, compressed shards in object storage read sequentially, or generated data. You cannot shuffle it by index; you shuffle by reading shards in a random order and keeping a shuffle buffer. And, as section 5 shows, it must split its work across workers itself.

3. What happens when you iterate: the worker pipeline

With num_workers=0, for batch in loader is a simple loop in the main process: get a batch of indices from the batch sampler, call dataset[i] for each, call collate_fn, optionally pin, yield. Everything is serial with your training step.

With num_workers=4, creating the iterator (the for statement, or iter(loader)) starts four worker processes, each holding a copy of the dataset, collate_fn and worker_init_fn. Then, step by step:

  1. The main process's batch sampler produces a list of B indices.
  2. The loader puts that list on one worker's index queue, round-robin across workers, and keeps doing so until prefetch_factor × num_workers = 8 batches are outstanding.
  3. Each worker loops: take an index list, call dataset[i] for each index, call collate_fn on the samples, and put the resulting batch on the shared result queue. Tensors in the batch are moved into shared memory first, so only a small handle is pickled through the queue.
  4. If pin_memory=True, a thread in the main process takes batches from the result queue and copies them into pinned memory.
  5. The training loop's next() returns the next batch in sampler order (with in_order=True), and the loader sends another index list to the worker that produced it, keeping the pipeline full.
  6. At the end of the iterator the workers shut down — unless persistent_workers=True, in which case they wait for the next epoch, keeping their dataset copies and any state they built (open files, caches).

Two consequences. Worker start-up is paid per epoch without persistent workers; for datasets with expensive constructors or many workers this adds seconds to every epoch. And the first batch of every epoch has to wait for a worker to produce it from scratch, so the GPU idles at each epoch boundary — another reason for persistent workers.

4. Why processes, and how they start: fork, forkserver, spawn

The GIL (py8) lets only one thread at a time execute Python bytecode. Decoding a JPEG with a C library releases it, but tokenising in Python, building dicts, applying Python-level augmentations, and running __getitem__ itself do not. Threads would serialise; processes run truly in parallel.

How a worker process starts depends on the platform and, since Python 3.14, on the Python version. The 2.14 docs state it directly: on Unix the default start method is forkserver for Python ≥ 3.14 and fork for Python < 3.14; on Windows and macOS it is spawn.

  • fork clones the parent process. The child sees the parent's memory — the dataset, imported modules, everything — immediately, shared copy-on-write. Start-up is fast. The danger is threads: if the parent has other threads (a CUDA context, a logging thread, an OpenMP pool) holding locks at the moment of the fork, the child inherits locked locks with no thread to release them, and can deadlock. CUDA cannot be used in a forked child at all if the parent initialised it.
  • forkserver starts one clean helper process early, and forks workers from that helper rather than from your (possibly multi-threaded) training process. It is safer with threads, still fairly fast, but the dataset and functions must be picklable because they are sent to the new process.
  • spawn starts a fresh interpreter, re-imports your main module, and unpickles the dataset, collate_fn and worker_init_fn. It is the slowest and the strictest: lambdas and locally defined functions cannot be pickled ("Can't pickle local object"), and your script must guard its top level with if __name__ == "__main__":, or each worker will re-run the training script as it imports it. This is what you get on Windows — including this machine — and on macOS.

Practical rule: write datasets and collate functions as top-level, picklable classes and functions, keep heavy state lazy (open files in the worker, not in __init__), and always use the __main__ guard. Then the same code works under all three start methods.

5. Seeds and shards: per-worker state

Each worker is seeded on start. Reading the 2.14 worker source: the worker computes seed = base_seed + worker_id, calls random.seed(seed) and torch.manual_seed(seed), and, if NumPy is installed, seeds NumPy's global RNG with a state derived from base seed and worker id through a SeedSequence-style hash. base_seed is drawn from the main process's RNG (or the generator you pass) each time an iterator is created. So augmentations that use torch.rand, random or np.random.* differ across workers and across epochs. (Older PyTorch versions did not seed NumPy, and identical augmentations across workers were a famous bug; it was fixed years ago, but the advice persists.)

What is not handled: RNG objects you create yourself in the dataset's __init__. self.rng = np.random.default_rng(0) is copied into every worker by fork or pickle, so every worker draws the same sequence. Create such generators per worker, seeded from torch.utils.data.get_worker_info().seed, either in worker_init_fn or lazily on first use in __getitem__.

Sharding an IterableDataset is the other per-worker duty. Every worker gets a full replica, and the DataLoader just interleaves what they yield, so without sharding, four workers produce every sample four times. The standard pattern:

class ShardStream(torch.utils.data.IterableDataset):
    def __init__(self, files):
        self.files = files                                  # list of shard paths
    def __iter__(self):
        info = torch.utils.data.get_worker_info()
        wid, nw = (info.id, info.num_workers) if info else (0, 1)
        rank, world = get_rank_and_world_size()             # 0, 1 when not distributed
        shard, nshards = rank * nw + wid, world * nw
        for f in self.files[shard::nshards]:                # this worker's files only
            yield from read_records(f)

With 2 GPUs and 4 workers each there are 8 shards; rank 1's worker 2 is shard 6 and reads files 6, 14, 22, … Uneven shard sizes make some ranks finish early; in DDP that leaves the others blocked in a gradient all-reduce (pt11), so either balance shards, cap the number of steps per epoch, or use DDP's uneven-input support.

6. The memory trap: reference counts break copy-on-write

With fork, a worker shares the parent's memory pages until it writes to one, at which point the operating system copies that page — copy-on-write. It sounds like reading a dataset in a worker is free. In CPython it is not: every Python object carries a reference count in its header, and simply touching an object (indexing a list, passing a string to a function) increments and decrements it. That is a write, so the page holding the object is copied into the worker. The 2.14 docs warn that "after several iterations, the loader worker processes will consume the same amount of CPU memory as the parent process for all Python objects in the parent process which are accessed from the worker processes", so total memory becomes about "number of workers × size of parent process", and recommend replacing Python objects "with non-refcounted representations such as Pandas, Numpy or PyArrow objects", pointing to PyTorch issue #13246, a long thread of reports and workarounds.

A worked number: 12 million file paths averaging 60 characters, as a Python list of str. Each str object is about 49 bytes of header plus its characters, roughly 110 bytes, plus an 8-byte pointer in the list: about 1.4 GB in the parent. With 16 workers the copies grow, over the first epoch, toward 16 × 1.4 ≈ 22 GB of extra host memory — the steady climb that ends in the out-of-memory killer. The same paths in a NumPy array of fixed-width bytes (dtype="S96") take 12M × 96 ≈ 1.15 GB in one buffer with a single object header; workers read slices of it without writing anything, so the pages stay shared. A memory-mapped token file like TokenFile above is better still: the pages belong to the OS page cache and are shared by every process that maps the file.

Under spawn and forkserver the trap looks different: each worker unpickles its own copy at start-up, so you pay the full multiple immediately instead of gradually. Either way, the fix is the same — keep big metadata out of Python objects.

7. Shared memory and how batches come back

A worker cannot hand a tensor to the main process by reference; they are different processes. PyTorch moves each tensor's storage into shared memory — on Linux a file in /dev/shm — and sends a small handle through the queue; the main process maps the same memory. No bulk copy through a pipe happens. The limit is the size of that shared-memory file system. Docker gives containers 64 MB of /dev/shm by default; a batch of 256 RGB images at 224 × 224 in float32 is 256 × 3 × 224 × 224 × 4 bytes ≈ 154 MB, so a single prefetched batch does not fit, and workers die with "bus error" or "DataLoader worker (pid …) is killed by signal: Bus error". Start containers with --shm-size=8g or --ipc=host, or mount a memory-backed volume at /dev/shm in Kubernetes. Returning uint8 images and converting to float on the GPU also cuts the shared-memory and transfer volume by four.

8. collate_fn and padding

default_collate receives the list of B samples and builds one batch: tensors are stacked along a new first dimension (so they must have equal shapes), NumPy arrays and Python numbers become tensors, and tuples, lists and dicts are collated element-wise. For text, sequences have different lengths and stacking fails with "stack expects each tensor to be equal size". A custom collate pads and builds a mask:

from torch.nn.utils.rnn import pad_sequence
def collate_pad(samples, pad_id=0):
    ids = [s["input_ids"] for s in samples]                  # list of (L_i,) int64
    lengths = torch.tensor([len(x) for x in ids])
    batch = pad_sequence(ids, batch_first=True, padding_value=pad_id)  # (B, L_max)
    mask = torch.arange(batch.shape[1])[None, :] < lengths[:, None]    # (B, L_max) True = real token
    labels = batch.masked_fill(~mask, -100)                  # ignored by cross_entropy
    return {"input_ids": batch, "attention_mask": mask, "labels": labels}

Each line uses something from pt2: broadcasting to build the mask, bool masks with an explicit polarity (here True = real token; convert as needed for the attention API you call), and −100 as the label for positions F.cross_entropy should ignore. pad_sequence on 2.14 also takes padding_side="left", which decoder-only generation needs so that the last real token of every row is at the same position.

Padding costs compute. The waste in a batch is 1 − Σ lengths / (B × Lmax). Lengths 12, 50, 512 and 30 padded to 512 use 604 of 2,048 positions — 70.5% of the batch's attention and MLP work is spent on padding. Bucketing fixes most of it: a batch sampler that groups samples of similar length, shuffling within buckets and shuffling the order of batches so training does not see a length curriculum. Token-budget batching goes further, choosing the batch size per batch so that B × Lmax stays near a fixed token count; packing concatenates several short sequences into one row with a document mask; and nested (jagged) tensors avoid storing padding at all.

9. Samplers

A sampler yields indices; a batch sampler yields lists of indices. The built-ins: SequentialSampler (what shuffle=False uses), RandomSampler (shuffle=True; with a generator it is reproducible), SubsetRandomSampler, WeightedRandomSampler (draws index i with probability proportional to weights[i], usually with replacement, the standard way to oversample a rare class) and BatchSampler.

DistributedSampler gives each data-parallel rank a disjoint slice of the index list. Two behaviours bite. First, its shuffle is seeded with seed + epoch, and the epoch only changes when you call sampler.set_epoch(epoch) before creating each epoch's iterator; the 2.14 docs carry a warning that otherwise "the same ordering will be always used". Second, with the default drop_last=False it makes the index list evenly divisible by the number of ranks by adding extra indices (repeating some samples), so a distributed evaluation over 10,001 samples on 8 ranks scores 10,008 — some examples twice. Exact evaluation needs de-duplication or a non-padding sampler.

10. Pinned memory and non-blocking copies

Normal host memory is pageable: the operating system may move or swap it. The GPU's copy engine uses direct memory access (DMA) and needs physical addresses that will not change, so a copy from pageable memory is done in two hops: the driver copies into an internal pinned staging buffer, then DMA copies to the GPU, and the calling thread waits. Pinned (page-locked) memory skips the staging hop and can be copied asynchronously.

loader = DataLoader(ds, batch_size=256, num_workers=8, pin_memory=True)
for x, y in loader:
    x = x.to("cuda", non_blocking=True)    # queued on the copy engine, returns at once
    y = y.to("cuda", non_blocking=True)
    loss = model(x, y)                     # queued after the copies on the same stream

With both pieces, the copy is queued on the current CUDA stream and Python moves on to queue the forward pass, which the GPU will run after the copy; meanwhile the previous step's work can still be executing. Numbers to reason with: a 154 MB float32 image batch over PCIe 4.0 ×16 (about 25 GB/s in practice) takes about 6 ms; as uint8 it is 38.5 MB and about 1.5 ms. Against a 250 ms training step either is small — if overlapped. Token batches are tiny: 32 × 2,048 int64 ids are 512 KB. Pinning everything is not free: pinned pages cannot be swapped, and allocating pinned memory is slow, which is why the DataLoader reuses a pinning thread rather than you calling .pin_memory() on every tensor yourself. The PyTorch tutorial on pin_memory and non_blocking measures cases where naive pinning makes things slower.

11. Finding and fixing an input-pipeline bottleneck

Measure before tuning. The simplest instrument splits each step into "waiting for data" and "everything else":

t0 = time.perf_counter()
for step, (x, y) in enumerate(loader):
    t1 = time.perf_counter()                      # data wait = t1 - t0
    x, y = x.to(dev, non_blocking=True), y.to(dev, non_blocking=True)
    loss = model(x, y); loss.backward(); opt.step(); opt.zero_grad()
    torch.cuda.synchronize()                      # make GPU time visible to the clock
    t0_next = time.perf_counter()
    log(data_wait=t1 - t0, compute=t0_next - t1)
    t0 = t0_next

(The synchronize is only for measurement; remove it afterwards, since it stops the CPU from queuing ahead — pt12.) A worked example: an image model where one core decodes and augments an image in 3.75 ms, batch size 128, and the GPU step takes 240 ms. One core needs 128 × 3.75 = 480 ms per batch, so with num_workers=0 each step takes about 480 + 240 = 720 ms and the GPU is busy a third of the time. Two workers would exactly match the GPU; four gives headroom for slow images and jitter, and the step drops to about 240 ms — three times faster. Beyond about four, nothing improves, because the GPU is now the bottleneck.

A second check isolates the pipeline: cache one batch on the GPU and train on it repeatedly. If throughput jumps far above the real run, data is the bottleneck. Then work down the list of fixes, cheapest first:

  1. num_workers up to roughly the number of physical cores available per GPU (minus one or two for the training process), with persistent_workers=True and pin_memory=True.
  2. Do less work per sample: decode at lower resolution, return uint8 and normalise on the GPU, tokenise offline once rather than every epoch.
  3. Change the storage format: many small files on a network file system are slow to open; sequential shard formats (tar-based WebDataset-style shards, Arrow, Parquet, memory-mapped token files) turn random small reads into large sequential ones.
  4. Move augmentation to the GPU (batched transforms on device tensors), or use a GPU-accelerated decoding pipeline.
  5. Cache: if the dataset fits in RAM after decoding, decode once.

Head-of-line blocking and in_order=False

With in_order=True, the loader must return batch k before batch k + 1, even if a worker finished k + 1 first. One slow sample — a huge image, a network read that hit a slow server, a long document in a tokeniser — stalls delivery of every batch behind it, and the GPU idles even though ready batches sit in the queue. in_order=False (added in recent releases and present on 2.14) lets the loader hand over whatever is ready. The cost is reproducibility of batch order: two runs with the same seed may see batches in different orders, which matters for exact resumption (pt8) and determinism (pt6). Many large-scale pipelines accept that trade for throughput and record which samples were consumed instead of relying on order.

CUDA and forked workers do not mix

If the parent process has initialised CUDA (by touching a GPU tensor) before workers are forked, a worker that tries to use CUDA fails with "Cannot re-initialize CUDA in forked subprocess". This is why the docs recommend returning CPU tensors from workers and letting pin_memory and the main process handle the transfer, and why GPU-based decoding inside workers requires spawn or forkserver. It is also one reason Python 3.14 moved the POSIX default away from fork: forking a multi-threaded process is inherently unsafe, and a training process with CUDA, NCCL and logging threads is very multi-threaded.

Worker count, CPU threads and oversubscription

Each worker is a full process, and libraries inside it may spawn their own thread pools: PyTorch's intra-op OpenMP threads, OpenCV's, NumPy's BLAS. Sixteen workers each starting sixteen threads on a 32-core machine produce 256 runnable threads competing for 32 cores, and throughput collapses. The DataLoader sets torch.set_num_threads(1) inside workers, but other libraries need their own settings (environment variables such as OMP_NUM_THREADS, or cv2.setNumThreads(0) in worker_init_fn). On multi-GPU nodes, divide the cores among the ranks: eight GPUs on a 96-core node leave about ten cores per rank for workers.

Streaming from object storage at scale

At the scale of hundreds of GPUs, the bottleneck often moves from CPU decoding to storage: small random reads from S3-style object stores have high latency (tens of milliseconds per request), so a map-style dataset that opens one object per sample cannot keep up. The standard answer is to reorganise data into large shards (hundreds of megabytes each), read them sequentially with an IterableDataset sharded by rank and worker as in the body, shuffle with a buffer plus random shard order, and prefetch shards ahead of use. The trade-off is weaker shuffling (only within the buffer and across shards) and harder exact resumption, because "where am I in the data" is now a per-worker position in a stream; pt8 shows how to checkpoint it with a stateful loader.

Multi-epoch randomness and generators

The DataLoader draws a new base_seed from the main process's RNG — or from the generator you pass — every time you create an iterator. Passing a seeded torch.Generator makes the shuffle order and worker seeds reproducible across runs; using the global RNG makes them depend on everything else that consumed random numbers before the loop (model init, dropout in a warm-up step). For exact reproducibility, give the loader its own generator, seed it, and use persistent_workers with care: persistent workers keep their RNG state from the previous epoch rather than being re-seeded, which is fine for randomness but means the per-epoch seeds differ from the non-persistent case.

Resumable data pipelines

A training run that restarts from a checkpoint should continue with the next unseen batch, not replay the epoch from the start (which over-trains on early data) or skip to a new epoch (which drops data). For a map-style dataset with a seeded sampler, the position is just "epoch e, batch b": recreate the sampler with the same seed and epoch and skip b batches of indices — cheap, because only indices are skipped, not samples loaded. For streaming IterableDatasets the position is per worker and per rank (which shard, which offset, the shuffle buffer's contents), so the dataset itself must expose a state_dict. PyTorch's torchdata project provides a StatefulDataLoader for this purpose, which asks each worker for its dataset state when you checkpoint; pt8 covers what a truly exact resume needs, including the RNG states that drive augmentation.

Free-threaded Python and the future of workers

CPython 3.13 introduced an optional free-threaded build without the GIL, and 3.14 continued that work. With it, thread-based data loading could run Python transforms in parallel without the process machinery — no pickling, no copy-on-write trap, shared caches. As of PyTorch 2.14, the DataLoader still uses processes, and most of the ecosystem (image libraries, tokenisers) needs to be verified as thread-safe without the GIL before thread-based loading becomes the default. The underlying lesson stays: the input pipeline is a parallel program, and its constraints come from how the interpreter runs parallel code.

Failure mode: low GPU utilisation

Symptom: nvidia-smi utilisation fluctuates or averages well below 90%, step time varies, and the profiler timeline shows gaps between steps. First suspect: the input pipeline. Check data-wait time per step, then the cached-batch test. Other causes that look the same: host–device synchronisation in the training loop (pt12), very small batches (launch overhead dominates), and in multi-GPU jobs a slow rank that everyone waits for. A data-bound job usually shows high CPU usage across worker processes; a sync-bound job shows a single busy core.

Failure mode: host memory growth and OOM kills

Symptom: resident memory of the training job climbs through the first epoch and the kernel's OOM killer ends it, often with no Python traceback. Causes: Python-object datasets copied into every worker (issue #13246), large prefetch buffers (prefetch_factor × num_workers × batch size), caches inside workers that grow per epoch with persistent workers, and pinned-memory pools. Measure per-process memory (each worker shows up as a separate process) rather than just the total; if every worker's memory grows similarly, it is copy-on-read.

Failure mode: workers that die or hang

"DataLoader worker (pid X) is killed by signal: Bus error" — shared memory exhausted (Docker's 64 MB default). "Killed by signal: Killed" — the OOM killer. A hang with no error — often a deadlock in a forked worker (a library lock held at fork time), an exception swallowed in a custom IterableDataset, or uneven shards in DDP leaving one rank in a collective. Set timeout to a finite value (for example 600 seconds) in production so a hung worker becomes an error with a stack trace, and debug with num_workers=0, which turns worker errors into ordinary tracebacks in the main process.

Failure mode: duplicated or missing data

Symptom: epoch length in samples is a multiple of what it should be, or validation metrics are suspiciously good. Causes: an unsharded IterableDataset (every worker and rank yields everything), a DistributedSampler without set_epoch (same order every epoch), padding from DistributedSampler in evaluation, or train/validation splits computed per worker with different random states. Detection: log the count of unique sample ids seen per epoch on each rank, at least in a short test run.

Knobs, in the order teams usually tune them

  • num_workers: start at 4–8 per GPU and measure; cap at the cores per rank.
  • persistent_workers=True when the epoch is short or worker start-up is expensive.
  • pin_memory=True with non_blocking=True copies.
  • prefetch_factor: raise it (4–8) when per-batch time is bursty; lower it when host memory or shared memory is tight.
  • in_order=False when a few slow samples cause stalls and exact order does not matter.
  • timeout finite in production; num_workers=0 while debugging.

The public case: issue #13246

PyTorch issue #13246, "DataLoader num_workers > 0 causes CPU memory from parent process to be replicated in all worker processes", is the canonical record of the reference-count trap: users reporting memory that grows with the number of workers on datasets held as Python lists and dicts, maintainers explaining copy-on-read through reference counts, and workarounds (NumPy arrays of strings, serialising each item to bytes, pandas, PyArrow). The DataLoader documentation now carries a warning that links to it. It is a good example of a framework behaviour that is not a bug in PyTorch at all but an interaction between the operating system's fork and CPython's memory model — exactly the kind of cross-layer reasoning interviewers look for.

CPU, PyTorch 2.14 in gpt_env on Windows (so workers use spawn); about 15 minutes. Save as pt5_lab.py and keep everything under the __main__ guard.

import time, numpy as np, torch
from torch.utils.data import Dataset, IterableDataset, DataLoader, get_worker_info

class SlowDS(Dataset):                       # simulates 4 ms of Python work per sample
    def __len__(self): return 512
    def __getitem__(self, i):
        t = time.perf_counter()
        while time.perf_counter() - t < 0.004: pass
        return torch.randn(3, 32, 32), i % 10

class Stream(IterableDataset):
    def __init__(self, n, shard=True): self.n, self.shard = n, shard
    def __iter__(self):
        info = get_worker_info()
        wid, nw = (info.id, info.num_workers) if info and self.shard else (0, 1)
        yield from range(wid, self.n, nw)

def rate(loader, steps=16):
    it = iter(loader); next(it)              # exclude start-up
    t = time.perf_counter()
    for _ in range(steps): next(it)
    return steps / (time.perf_counter() - t)

if __name__ == "__main__":
    for w in (0, 2, 4):
        dl = DataLoader(SlowDS(), batch_size=32, num_workers=w, persistent_workers=w > 0)
        print(f"workers={w}: {rate(dl):.1f} batches/s")
    for shard in (False, True):
        seen = [int(x) for b in DataLoader(Stream(12, shard), batch_size=4, num_workers=3) for x in b]
        print("shard" if shard else "no shard", sorted(seen))
    lens = [12, 50, 512, 30]
    print("padding waste:", 1 - sum(lens) / (len(lens) * max(lens)))

Find the bug: an input pipeline that is slow, repetitive and leaky

This pipeline feeds a 4-GPU DDP job (one process per GPU). GPU utilisation is about 35%, every epoch's loss curve looks identical, host memory grows by several GB per hour, and the dataset's random crops look the same across workers. Find the bugs and their symptoms.

class CropDS(Dataset):
    def __init__(self, index_file):
        self.items = [json.loads(l) for l in open(index_file)]   # 9M dicts: path, label
        self.rng = np.random.default_rng(1234)
    def __len__(self): return len(self.items)
    def __getitem__(self, i):
        item = self.items[i]
        img = decode_and_resize(item["path"])                    # ~5 ms
        x0 = self.rng.integers(0, 32)

Answer

Bug 1 — too few workers for the work. 64 images × 5 ms = 320 ms of decoding per batch, split over 2 workers is 160 ms per batch per rank; if the GPU step is about 60 ms, the GPU waits most of the time — matching 35% utilisation. Fix: raise num_workers (6–8 per rank if the cores exist), add persistent_workers=True, pin_memory=True and x.cuda(non_blocking=True). Measure data-wait time to confirm.

Bug 2 — no set_epoch. DistributedSampler shuffles with seed + epoch, and the epoch never changes, so every epoch sees the same order on every rank — identical loss curves per epoch. Fix: sampler.set_epoch(epoch) at the top of the epoch loop.

Bug 3 — 9 million Python dicts in the dataset. Each worker touches the dicts, reference counting writes to their pages, and copy-on-write copies them into every worker (2 workers × 4 ranks = 8 copies today, and more after fixing bug 1) — the steady memory growth (PyTorch issue #13246). Fix: load the index into NumPy arrays (fixed-width byte strings for paths, an int array for labels) or a PyArrow table, or a memory-mapped file.

Bug 4 — the RNG is created in __init__. np.random.default_rng(1234) is copied into every worker (and identical on every rank), so all of them draw the same crop sequence. The DataLoader's per-worker seeding covers NumPy's global RNG, not Generator objects you create. Fix: create the generator per worker in worker_init_fn or lazily in __getitem__, seeded from get_worker_info().seed (which already differs by worker and epoch); include the rank if seeds must differ across ranks.

Smaller issue: x.cuda().float() / 255 transfers uint8 (good — four times less than float32) but synchronously; with pinning and non_blocking=True the copy overlaps compute.

Estimate: how many workers?

A speech model trains at 0.4 s per step with batch 48. Loading and featurising one utterance takes 22 ms on one core. The node has 64 cores and 8 GPUs. How many workers per GPU, and is the node CPU-bound?

Answer

Per batch: 48 × 22 ms = 1.06 s of CPU work. To deliver one batch per 0.4 s needs at least 1.06 / 0.4 ≈ 2.6 workers; with headroom for variance, 4 per GPU. Across 8 GPUs that is 32 worker processes plus 8 training processes on 64 cores — comfortable, about 60% of the cores. If featurisation were twice as slow, 6 per GPU would push the node to 56 processes and close to saturation; then move featurisation offline or to the GPU rather than adding workers.
