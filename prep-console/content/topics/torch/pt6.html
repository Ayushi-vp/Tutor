In October 2024, Unsloth, a company that builds fine-tuning tools, reported something odd to Hugging Face: training a causal language model with gradient accumulation — running several small batches and stepping the optimiser once, a standard trick to fit a larger batch into memory — did not give the same loss curve as training with one big batch. It was supposed to be mathematically identical. The cause, which Hugging Face explained in a post titled "Fixing Gradient Accumulation" on 16 October 2024, was one line of loss arithmetic: each micro-batch's loss was a mean over its own non-padding tokens, and those means were averaged. Micro-batches with few real tokens got as much weight as those with many. The fix: divide the total loss over all micro-batches by the total number of non-padding tokens. Millions of fine-tuning runs had been slightly wrong because of where a division happened.

That is the nature of training-loop bugs. The loop is ten lines long, everyone has written it, and nearly every line has a way to be subtly wrong that does not crash: zero_grad in the wrong place, a scheduler stepped before the optimiser or per epoch instead of per step, clipping applied to the wrong gradients, a loss reduced over the wrong thing, an evaluation loop that averages per-batch means or forgets to switch modes, seeds that make you believe a change helped when it was noise. The model trains, the loss goes down, and the result is a few percent worse than it should be — or a few percent better on paper than it really is.

In an ML-debugging round, the training loop is where interviewers plant half the bugs, because candidates who have only used high-level trainers have never had to think about the order of operations. This lesson takes every line of a correct step and explains why it is where it is: gradients and when to clear them, loss reduction and what it means for the learning rate, warmup and decay schedules and how PyTorch's schedulers work, gradient clipping and what its return value tells you, gradient accumulation done correctly (including the token-weighting fix), an evaluation loop that produces numbers you can trust, and seeding and determinism — what PyTorch can and cannot make reproducible.

Think of one training step as a short assembly line with a strict order, where each station reads what the previous one produced:

  1. Forward: run the model on a batch to get predictions (and, through autograd, record the graph — pt3).
  2. Loss: compare predictions with targets and reduce to one number. How you reduce (mean over what?) decides how big the gradient is.
  3. Backward: compute the gradient of that number with respect to every parameter, adding it into each parameter's .grad.
  4. Clip (optional but standard): if the gradient as a whole is unusually large, shrink it.
  5. Optimiser step: use .grad (and the optimiser's memory of past gradients) to update every parameter.
  6. Scheduler step: move the learning rate to its next value.
  7. Zero the gradients, so the next backward starts from nothing.

The analogy to an assembly line is useful because the bugs are all "a station ran at the wrong time": clearing gradients after backward but before the step (the step sees nothing), stepping the schedule before the optimiser (the first update uses the wrong learning rate), clipping after the step (too late to matter). Gradient accumulation is the one deliberate exception — stations 1–3 run several times before stations 4–7 run once — which is why it needs extra care with the loss arithmetic.

It is worth knowing what each station costs and what it protects you from, because that is how you judge a change to the loop. Forward and backward are almost all of the time — backward roughly twice forward (pt3). The loss is cheap unless the vocabulary is huge, in which case the logits and their softmax are a large slice of memory. Clipping costs one pass over all gradients to compute a norm — a few milliseconds even for large models — and protects against the single bad batch that would otherwise wreck the run. The optimiser step reads and writes every parameter and its state: for AdamW that is the weight, the gradient and two moments, about 16 bytes per parameter of memory traffic in float32, which is why fused optimiser kernels exist (pt12). The scheduler and zero_grad are essentially free. Logging is free unless it synchronises the GPU on every step.

The other thing to hold in mind is that every station has a "mode" question. The forward pass behaves differently in train and eval mode (dropout, BatchNorm — pt4); autograd records or does not (pt3); the loss averages over examples, tokens or something else. Most training-loop bugs are not wrong code in a station but a station running in the wrong mode or averaging over the wrong thing. When you read someone else's loop in an interview, check each line for when it runs and what it averages.

Where the assembly-line picture breaks: the optimiser has memory. Adam's update depends not only on this step's gradient but on running averages of past gradients and squared gradients, so a single bad step (a huge gradient, a wrong learning rate) can affect many later steps. That is why clipping and warmup matter more than the one-step picture suggests, and why the optimiser's state must be saved with checkpoints (pt8).

If you remember one sentence: forward, loss, backward as often as you accumulate; then clip, step, schedule, and zero exactly once — and make the loss arithmetic say precisely what average you mean.

1. The reference loop

Here is a complete, correct single-device loop, which the rest of the lesson takes apart line by line.

model.train()
for step, (x, y) in enumerate(train_loader):
    x, y = x.to(dev, non_blocking=True), y.to(dev, non_blocking=True)
    logits = model(x)                                   # (B, V)
    loss = F.cross_entropy(logits, y)                   # mean over B
    loss.backward()                                     # .grad += dloss/dθ
    gnorm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    optimizer.step()
    scheduler.step()
    optimizer.zero_grad(set_to_none=True)               # the 2.14 default
    if step % 50 == 0:
        log(step=step, loss=loss.item(), lr=scheduler.get_last_lr()[0], gnorm=gnorm.item())
    if step % eval_every == 0:
        evaluate(model, val_loader)                     # restores train mode itself

Logging uses .item(), which synchronises with the GPU (pt1, pt12); doing it every 50 steps rather than every step keeps the cost negligible.

2. Clearing gradients

Because backward adds into .grad (pt3), gradients must be cleared once per optimiser step. optimizer.zero_grad() clears the parameters that optimiser manages; model.zero_grad() clears every parameter in the model. On 2.14 both default to set_to_none=True: they set .grad = None rather than filling it with zeros. That skips a memory write per parameter, lets the allocator reuse the memory until backward needs it, and lets optimisers skip parameters that received no gradient this step. The behavioural difference: code that reads p.grad after zeroing (custom logging, a gradient penalty) gets None instead of zeros and must handle it.

Correct placements are "at the top of the loop, before forward" or "after optimizer.step()". Wrong placements, each a planted bug you should recognise instantly:

  • Between backward and step — the step sees no gradients (with set_to_none, the optimiser skips every parameter), and the model never trains. The loss stays flat at its initial value.
  • Missing — gradients accumulate forever. Each step's update includes every previous gradient, so updates grow, the loss falls fast for a few steps and then explodes.
  • Inside an accumulation loop — only the last micro-batch survives; you train with a k-times smaller batch than you think.

3. Loss reduction: what are you averaging over?

Losses in torch.nn take reduction="mean" (default), "sum" or "none" (return one loss per element). The choice sets the gradient's scale:

  • mean divides by the number of elements, so the gradient is an average and does not grow with batch size. A learning rate tuned at batch 32 is roughly sensible at batch 64 (larger batches usually want somewhat larger learning rates, but not twice as large).
  • sum makes the gradient grow linearly with the number of elements; doubling the batch doubles the effective learning rate. It is useful as a building block when you normalise yourself.
  • none returns per-element losses for weighting, masking or per-example logging.

"Elements" depends on the loss. For F.cross_entropy(logits.view(-1, V), targets.view(-1)) on a language model, the mean is over tokens, and positions whose target equals ignore_index (default −100) are excluded from both the numerator and the denominator. So the mean is over real tokens in this batch. A model whose loss is "mean over examples of the mean over tokens" weights a 10-token example as much as a 1,000-token one; "mean over all tokens" weights every token equally. Neither is wrong, but they are different objectives, and mixing them — the pattern behind the accumulation bug in section 7 — is wrong.

Two smaller reduction traps. label_smoothing in F.cross_entropy changes the minimum achievable loss, so a smoothed loss never reaches 0 and is not comparable to an unsmoothed one. And class weights (weight=) change the mean's denominator to the sum of the weights of the targets present, so the loss value changes with the batch's class mix.

4. Optimiser step and parameter groups

optimizer.step() applies the update rule to every parameter it manages that has a non-None .grad. AdamW on 2.14 defaults to lr=1e-3, betas=(0.9, 0.999), eps=1e-8, weight_decay=0.01, and accepts foreach and fused options that change speed, not results (pt12). It keeps two state tensors per parameter (the first and second moment estimates, dl5) — the reason AdamW costs 8 extra bytes per parameter in float32.

Parameter groups let different tensors use different hyperparameters: a list of dicts, each with "params" and any overrides, such as no weight decay for biases and normalisation weights, or a smaller learning rate for a pretrained backbone than for a new head. The scheduler scales each group's learning rate by the same factor, so their ratio is preserved.

5. Learning-rate schedules and warmup

A scheduler wraps an optimiser and changes each group's lr when you call scheduler.step(). Since PyTorch 1.1 the order is fixed: optimizer.step() then scheduler.step(). Reversing them triggers, on 2.14, "Detected call of `lr_scheduler.step()` before `optimizer.step()`. In PyTorch 1.1.0 and later, you should call them in the opposite order… Failure to do this will result in PyTorch skipping the first value of the learning rate schedule."

Warmup exists because the start of training is fragile. Adam divides each gradient by the square root of a running average of squared gradients; at step 1 that average is based on one gradient, so the normalised update is large and noisy. Activations and gradients in a freshly initialised transformer are also poorly scaled. Starting with a full-size learning rate can produce early loss spikes or divergence; ramping it over the first hundreds or thousands of steps lets the statistics settle. Toward the end, decay (cosine or linear) reduces the step size so the model settles into a minimum.

Two ways to write warmup + cosine. Composing built-ins:

from torch.optim.lr_scheduler import LinearLR, CosineAnnealingLR, SequentialLR
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
sched = SequentialLR(opt, [
    LinearLR(opt, start_factor=0.01, total_iters=4),        # 1e-5 → 1e-3 over 4 steps
    CosineAnnealingLR(opt, T_max=6, eta_min=1e-5)],          # then down over 6 steps
    milestones=[4])

Or one LambdaLR whose function returns a multiplier of the base learning rate:

def lr_mult(s, warmup=4, total=10):
    if s < warmup:
        return (s + 1) / warmup
    return 0.5 * (1 + math.cos(math.pi * (s - warmup) / (total - warmup)))
sched = torch.optim.lr_scheduler.LambdaLR(opt, lr_mult)

Run on 2.14 for 10 steps, reading the learning rate before each step: the SequentialLR version gives 1.0e-5, 2.58e-4, 5.05e-4, 7.53e-4, 1.0e-3, 9.34e-4, 7.53e-4, 5.05e-4, 2.58e-4, 7.6e-5; the LambdaLR version gives 2.5e-4, 5.0e-4, 7.5e-4, 1.0e-3, 1.0e-3, 9.33e-4, 7.5e-4, 5.0e-4, 2.5e-4, 6.7e-5. Same shape, slightly different details — exactly why you should print the first few learning rates of any schedule rather than trust that you configured it correctly.

Granularity is the other classic bug: a schedule defined in optimiser steps must be stepped once per optimiser step. Stepping per epoch stretches a 2,000-step warmup over 2,000 epochs; stepping per micro-batch with accumulation compresses it by k. Schedulers have state (last_epoch, which despite its name counts calls to step()), so save scheduler.state_dict() with checkpoints.

6. Gradient clipping

torch.nn.utils.clip_grad_norm_(params, max_norm) treats the gradients of all the given parameters as one long vector, computes its L2 norm, and if the norm exceeds max_norm, multiplies every gradient by max_norm / norm. The direction of the update is unchanged; only its length is capped. It returns the norm before clipping. On 2.14, gradients [3, 4, 0, 0] with max_norm 1.0 return a norm of 5 and become [0.6, 0.8, 0, 0].

Clipping is insurance against rare huge gradients — a pathological batch, an attention logit that blew up — which would otherwise take one enormous step and undo hours of training. A max_norm of 1.0 is a common default for transformers. The returned norm is the single most useful health metric in a training log: steady and slowly declining is normal; a spike before a loss spike is the classic warning (pt9); a norm permanently above max_norm means clipping is engaged on every step, so you are effectively training with a smaller, varying learning rate. clip_grad_value_ clamps each element instead and changes the direction; it is rarely the right choice. Pass error_if_nonfinite=True to fail immediately on a NaN or inf norm rather than clipping garbage.

7. Gradient accumulation, and getting the weighting right

Gradient accumulation runs k micro-batches before one optimiser step. Since .grad accumulates, the only question is how to scale each micro-batch's loss so that the summed gradient equals the gradient of the full-batch loss.

When every micro-batch has the same number of loss elements (images, fixed-length examples, no padding), dividing each mean loss by k is exact:

for i, (x, y) in enumerate(loader):
    loss = F.cross_entropy(model(x), y) / k     # each micro-batch: mean over B
    loss.backward()
    if (i + 1) % k == 0:
        clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step(); scheduler.step(); optimizer.zero_grad()

When micro-batches have different numbers of real tokens, that is not exact. A worked example: micro-batch A has 1,000 real tokens with mean loss 2.0; micro-batch B has 10 real tokens with mean loss 4.0. The full-batch token-level loss is (1,000 × 2.0 + 10 × 4.0) / 1,010 = 2,040 / 1,010 ≈ 2.02. Averaging the two means gives (2.0 + 4.0) / 2 = 3.0 — B's ten tokens weigh as much as A's thousand. The gradient is distorted in the same way. This is the bug Hugging Face described: "the correct loss should be computed by the total loss across all batches in a gradient accumulation step divided by the total number of all non padding tokens in those batches. This is not the same as the average of the per-batch loss values."

The fix is to know the token count for the whole accumulation step before backward, and to use a sum reduction:

micro = [next(it) for _ in range(k)]                        # pre-fetch k micro-batches
n_tok = sum((b["labels"] != -100).sum() for b in micro)      # real tokens in the step
for b in micro:
    logits = model(b["input_ids"])
    loss = F.cross_entropy(logits.view(-1, V), b["labels"].view(-1),
                           reduction="sum") / n_tok          # weight by tokens
    loss.backward()
clip_grad_norm_(model.parameters(), 1.0)
optimizer.step(); scheduler.step(); optimizer.zero_grad()

In data-parallel training the denominator should be the token count across all ranks too (an all-reduce of n_tok, pt11), and DDP's no_sync() avoids synchronising gradients on every micro-batch. Two things accumulation cannot reproduce: BatchNorm statistics, which are computed per micro-batch, and anything that depends on the batch as a whole (in-batch negatives in contrastive learning see only the micro-batch).

8. Combining several losses

Real loops often optimise a weighted sum: a main loss plus an auxiliary one (a mixture-of-experts load-balancing loss, a distillation term, a regulariser). Three rules keep it correct. Sum the terms and call backward once (pt3): loss = main + 0.01 * aux; loss.backward(), rather than two backward passes with retain_graph=True. Make sure each term is reduced over the same thing — a per-token main loss plus a per-example auxiliary loss changes their relative weight whenever sequence length changes. And log each term separately as a Python number, because a total that looks healthy can hide an auxiliary term that has exploded or collapsed to zero. With gradient accumulation, every term needs the same weighting treatment as the main loss.

Two common modifiers also live in the loss line. label_smoothing=0.1 in F.cross_entropy mixes the one-hot target with a uniform distribution, which regularises over-confident classifiers but raises the minimum achievable loss (so a smoothed training loss and an unsmoothed validation loss are not comparable). weight=class_weights rebalances classes, and with reduction="mean" it divides by the sum of the weights of the targets present rather than by the count — so the loss value shifts with the class mix of each batch, which shows up as extra noise in the curve.

9. The evaluation loop

A trustworthy evaluation function:

def evaluate(model, loader):
    was_training = model.training
    model.eval()
    total_loss, total_tok = 0.0, 0
    try:
        with torch.inference_mode():
            for b in loader:
                logits = model(b["input_ids"].to(dev))
                labels = b["labels"].to(dev)
                total_loss += F.cross_entropy(logits.view(-1, V), labels.view(-1),
                                              reduction="sum").item()
                total_tok += (labels != -100).sum().item()
    finally:
        model.train(was_training)
    return total_loss / total_tok

Each detail answers a bug: eval() turns off dropout and freezes BatchNorm (pt4); inference_mode stops graph recording and saves memory (pt3); sums and counts give the true mean over tokens, whereas averaging per-batch means is biased when the last batch is smaller or lengths vary; finally restores the previous mode even if evaluation raises, so training never silently continues in eval mode. The validation loader must not shuffle, must not drop the last batch, and in distributed runs must not repeat examples (pt5).

Comparing training and validation loss needs care. The logged training loss is usually a running mean over recent steps, computed in train mode with dropout active and on each batch before the update for that batch, while validation runs in eval mode. A small gap in either direction is normal; a validation loss consistently below training loss often just means dropout is strong, not that something is wrong.

10. Early stopping and choosing the checkpoint

The evaluation loop's output usually drives two decisions: whether to stop, and which checkpoint to keep. Early stopping stops when the validation metric has not improved for a set number of evaluations (the "patience"). Implemented carelessly it has three failure modes. Noise: a single evaluation that is lucky or unlucky by chance moves the "best" checkpoint, so the validation set must be large enough that the metric's run-to-run spread is smaller than the improvements you care about. Selection bias: picking the best of many evaluations on the same validation set makes that number optimistic, so report a separate test set. And schedule interaction: with cosine decay, the loss often improves fastest near the end as the learning rate falls, so stopping early can stop just before the best part; many large-scale runs therefore train for a fixed budget and keep the last (or the EMA) checkpoint rather than early-stopping.

11. Seeding and determinism

Random numbers enter training through parameter initialisation, data shuffling, augmentation, dropout and sampling. Each has a generator:

  • torch.manual_seed(s) seeds PyTorch's CPU generator and every CUDA device's generator.
  • random.seed(s) and np.random.seed(s) seed Python's and NumPy's global generators.
  • The DataLoader's shuffle and worker seeds come from the main process's torch RNG unless you pass generator=torch.Generator().manual_seed(s) (pt5).

Seeding makes a run repeatable only if every operation is deterministic, and some GPU operations are not: index_add, scatter_add and the backward passes of embedding, gather and advanced indexing use atomic additions whose order varies (pt2); cuDNN may choose convolution algorithms by benchmarking at run time (torch.backends.cudnn.benchmark=True). torch.use_deterministic_algorithms(True) makes PyTorch select deterministic implementations or raise an error naming the operation that has none; for CUDA matmuls it also requires the environment variable CUBLAS_WORKSPACE_CONFIG=:4096:8 (or :16:8). Set cudnn.benchmark=False as well.

Even then, results are reproducible only on the same hardware and software: a different GPU model, CUDA version, number of GPUs or PyTorch version can change kernel choices and summation orders. The practical uses of determinism are debugging (a bug that appears every time is far easier to find) and regression testing (proving a refactor changed nothing). For the science, the honest approach is several seeds and error bars: a change that improves a metric by less than the seed-to-seed spread has not been shown to help.

12. A pre-flight check you can run in five minutes

Before launching a long run, a short scripted check catches most of this lesson's bugs. Run 20 steps on a tiny configuration and assert the following. The step-0 loss is close to ln of the number of classes (pt4), so initialisation and the loss line are sane. The learning rate printed before each step follows the intended warmup values, so the scheduler is stepped at the right granularity and in the right order. The gradient norm is finite, non-zero and not growing step over step, so zero_grad is in place and backward reaches the parameters. Every trainable parameter's checksum changes after the first step, so the optimiser holds the right tensors. The accumulated gradient over k micro-batches equals the gradient of the concatenated batch (the lab's test), so the loss weighting is right. Two evaluations of the same weights return identical numbers, so the evaluation loop is in eval mode and deterministic. And the model can overfit a single small batch to near-zero loss within a few hundred steps — Karpathy's "overfit one batch", which pt9 builds on — so the whole pipeline, from data to update, can actually learn. Each check takes seconds; together they cost less than one minute of a real run.

Why warmup works: Adam's early updates and the scale of the residual stream

Adam's update for a parameter is roughly lr × m / (√v + ε), where m and v are running averages of the gradient and its square with bias correction. At step 1, bias correction makes m/√v equal to g/|g| — a unit-size step in every coordinate, regardless of how small the gradient was. With a full learning rate, every weight moves by lr at once, which in a deep transformer can push activations far from the range normalisation layers were calibrated for. Warmup keeps those early steps small until v has averaged over enough gradients to reflect the true scale. Empirically, the needed warmup grows with model size and learning rate, and a too-short warmup shows up as loss spikes in the first few thousand steps.

Batch size, learning rate and the noise scale

Increasing the batch size (through accumulation or more GPUs) reduces gradient noise. Up to a point — sometimes called the critical batch size — a larger batch lets you take proportionally larger steps and reach the same loss in fewer steps; beyond it, extra examples per step mostly waste compute. For SGD a linear scaling rule (double the batch, double the learning rate) with warmup works up to fairly large batches; for Adam the relationship is closer to square-root scaling and saturates earlier. The practical consequence for loop design: when you change the effective batch size — more GPUs, different accumulation — retune or at least rescale the learning rate, and keep the token budget fixed when comparing runs.

The step and the GPU: foreach, fused and capturable optimisers

A naive optimiser step loops over parameters in Python and launches several small CUDA kernels per parameter — for a model with 500 parameter tensors that is thousands of launches per step. foreach=True (the default on CUDA when available) groups tensors and uses multi-tensor kernels; fused=True goes further, doing the whole update for many tensors in one kernel. They change speed, not mathematics (up to floating-point order). capturable=True keeps the step count on the GPU so the step can be captured in a CUDA graph (pt12). The learning rate can be passed as a tensor for the same reason — a Python float changed by the scheduler would otherwise force recompilation or re-capture.

Skipping bad steps

Large-scale runs often add a guard after computing the gradient norm: if it is non-finite, or an outlier (say, more than several times its recent moving average), skip the optimiser step for this batch and log the batch's data indices. Mixed-precision training already does the first part automatically, because GradScaler skips steps whose gradients contain inf or NaN (pt7). The second part is a policy decision: it prevents a single pathological batch from damaging Adam's moment estimates, at the cost of training on slightly less data and possibly hiding a systematic problem — so count and alert on skips rather than skipping silently.

Exponential moving averages of weights

Many training recipes keep an EMA copy of the weights, updated after every optimiser step as θema ← d·θema + (1 − d)·θ with d around 0.999–0.9999, and evaluate or ship the EMA weights, which are smoother than the raw ones. Implementation details are where the bugs live: the update must run under torch.no_grad() (or it records a graph every step, pt3); buffers such as BatchNorm statistics need copying, not averaging; with very high d the EMA lags far behind early in training, so implementations warm d up; and the EMA copy doubles weight memory unless it is kept on the CPU or sharded. torch.optim.swa_utils.AveragedModel with an EMA averaging function implements the pattern.

Reading a noisy loss curve

A per-step training loss is noisy because each step sees a different batch: with batch size B, the standard error of the batch-mean loss shrinks only as 1/√B. That noise is why logs show a smoothed loss (a running mean or an exponential moving average of the per-step values) and why judging "is it still improving?" from a few hundred raw steps is unreliable. Two practical consequences. First, compare runs on smoothed curves plotted against tokens seen, not steps, when batch sizes differ. Second, distinguish noise from signal by the shape: a sharp single-step spike that recovers immediately is usually one hard batch; a spike that takes thousands of steps to recover means the weights or the optimiser state were damaged, which is when clipping, a lower learning rate or skipping bad steps are worth considering (pt9).

What determinism cannot fix: chaotic sensitivity

Training a neural network is a long iterated computation, and tiny differences grow: two runs that differ in the last bit of one gradient on step 1 will, after thousands of steps, have measurably different weights and, often, final metrics that differ by a few tenths of a percent. That is not a bug; it is the variance of the procedure. It is why "same seed, same result" is a debugging tool and not a scientific claim, and why a careful comparison of two training-loop variants uses several seeds per variant.

The four lines to log

Loss, learning rate, gradient norm and throughput (tokens or samples per second), every few steps. Most training-loop bugs are visible there: a learning rate that does not change (scheduler never stepped) or changes once per epoch (stepped at the wrong granularity); a loss that never moves (zero_grad between backward and step); a gradient norm that grows steadily (missing zero_grad) or sits at max_norm (clipping always engaged); throughput that drops (synchronisations, data stalls, memory fragmentation). Log the evaluation metric with the step count and the number of tokens seen, so runs with different batch sizes can be compared.

Failure mode: the accumulation that does not match

Symptom: a run with gradient accumulation behaves differently from the same effective batch without it — a slightly higher loss, a different curve. Causes: per-micro-batch means averaged with padded or variable-length data (the Hugging Face case), zero_grad inside the accumulation loop, the scheduler stepped per micro-batch, BatchNorm seeing small micro-batches, or in distributed runs each rank dividing by its own token count. Test: on a small model, compare the gradient after k accumulated micro-batches with the gradient of one concatenated batch; they should match to floating-point tolerance.

Failure mode: evaluation numbers that move when nothing changed

Symptom: the validation metric of the same checkpoint varies between evaluations, or changes with the evaluation batch size. Causes: dropout active (no eval()), BatchNorm in training mode updating its statistics with validation data, shuffled validation data with a mean of per-batch means, a DistributedSampler padding the validation set, or non-deterministic kernels. Fix with the evaluate() pattern in the body and a regression test that evaluates one checkpoint twice and asserts equality.

Failure mode: resumed runs that drift

Symptom: after a restart from a checkpoint, the loss jumps or the learning rate is wrong. Causes: optimiser state not saved (Adam restarts with zero moments — effectively a new warmup-free start), scheduler state not saved (the learning rate restarts the warmup or jumps to the end), data position not restored (the run re-trains on the first part of the epoch), or GradScaler state lost. pt8 lists everything a checkpoint must contain.

The public case: Hugging Face's October 2024 fix

The gradient accumulation issue is worth knowing in detail because it happened in the most widely used training library and was found by comparing two configurations that should have been identical. Hugging Face's post explains that each model's default loss was a mean over the non-padding tokens in its own batch, and that the Trainer's accumulation averaged those, so "losses did not match between training runs where the setting was toggled on and off". The fix passes the total number of items in the accumulation step into the loss so that it sums and divides by the global count. The lesson for your own loops is the test they implicitly ran: whenever you implement accumulation, data parallelism or any other way of splitting a batch, check that the split and unsplit versions produce the same loss and gradient.

CPU, PyTorch 2.14 in gpt_env; about 15 minutes. Save as pt6_lab.py.

import math, torch, torch.nn.functional as F
torch.manual_seed(0)
V = 5
model = torch.nn.Linear(4, V)
def make(n_tok):                                   # a micro-batch with n_tok real tokens of 8
    x = torch.randn(8, 4); y = torch.randint(0, V, (8,)); y[n_tok:] = -100
    return x, y
micro = [make(8), make(1)]                         # 8 real tokens, then 1

def grad_of(loss_fn):
    model.zero_grad(); loss_fn().backward()
    return model.weight.grad.clone()

# reference: one concatenated batch, mean over all real tokens
X = torch.cat([m[0] for m in micro]); Y = torch.cat([m[1] for m in micro])
g_ref = grad_of(lambda: F.cross_entropy(model(X), Y))

# naive accumulation: mean per micro-batch, divided by k
model.zero_grad()
for x, y in micro: (F.cross_entropy(model(x), y) / len(micro)).backward()
g_naive = model.weight.grad.clone()

# token-weighted accumulation
n_tok = sum((y != -100).sum() for _, y in micro)
model.zero_grad()
for x, y in micro: (F.cross_entropy(model(x), y, reduction="sum") / n_tok).backward()
g_tok = model.weight.grad.clone()
print("naive  max diff:", (g_naive - g_ref).abs().max().item())
print("tokens max diff:", (g_tok - g_ref).abs().max().item())

# schedule: print lr before each step
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
sched = torch.optim.lr_scheduler.LambdaLR(
    opt, lambda s: (s + 1) / 4 if s < 4 else 0.5 * (1 + math.cos(math.pi * (s - 4) / 6)))
for s in range(10):
    print(s, f"{opt.param_groups[0]['lr']:.2e}"); opt.step(); sched.step()

# clipping returns the pre-clip norm
p = torch.nn.Parameter(torch.zeros(4)); p.grad = torch.tensor([3., 4., 0., 0.])
print("norm", torch.nn.utils.clip_grad_norm_([p], 1.0).item(), p.grad.tolist())
  1. The naive difference is clearly non-zero (the 1-token micro-batch is over-weighted); the token-weighted difference is about 1e-8 — floating-point noise.
  2. The learning rates match the body's LambdaLR list: 2.5e-4 rising to 1e-3, then cosine decay.
  3. Clipping prints norm 5.0 and gradients [0.6, 0.8, 0, 0].
  4. Swap opt.step() and sched.step() and read the warning PyTorch prints; note the first learning rate actually used.
Find the bug: a fine-tuning loop with accumulation

This loop fine-tunes a language model with padded batches, micro-batch 4, accumulation 8. Its loss curve is noisier and worse than a reference run with batch 32 and no accumulation; the learning rate in the logs reaches its peak after about 250 steps although warmup was set to 2,000 steps; and the validation loss changes when the validation batch size changes. Find the bugs.

sched = get_warmup_cosine(opt, warmup=2000, total=50000)
for i, b in enumerate(train_loader):
    out = model(b["input_ids"])
    loss = F.cross_entropy(out.view(-1, V), b["labels"].view(-1)) / 8
    loss.backward()
    sched.step()
    if (i + 1) % 8 == 0:
        opt.step()
        clip_grad_norm_(model.parameters(), 1.0)
        opt.zero_grad()

def validate():
    model.eval()
    with torch.no_grad():
        losses = [F.cross_entropy(model(b["input_ids"]).view(-1, V),
                                  b["labels"].view(-1)).item() for b in val_loader]
    return sum(losses) / len(losses)
Answer

Bug 1 — the scheduler steps per micro-batch. sched.step() runs 8 times per optimiser step, so the 2,000-step warmup completes after 2,000 / 8 = 250 optimiser steps, and the whole cosine decay finishes 8 times too early. Symptom: peak learning rate at ~250 steps, as observed. Fix: move sched.step() inside the if, after opt.step().

Bug 2 — clipping after the step. clip_grad_norm_ runs after opt.step(), so it rescales gradients that are about to be zeroed; the update itself was never clipped. Symptom: noisier training, occasional spikes. Fix: clip, then step.

Bug 3 — mean-of-means accumulation with padding. Each micro-batch's loss is a mean over its own real tokens, divided by 8, so micro-batches with few real tokens are over-weighted — the bug Hugging Face fixed in October 2024. Fix: compute the total real-token count for the 8 micro-batches, use reduction="sum", and divide by that count.

Bug 4 — validation is a mean of per-batch means and leaves the model in eval mode. Averaging per-batch means weights the last (smaller) batch and short-sequence batches wrongly, so the result depends on batch size; sum the losses and count tokens instead. And validate() never calls model.train(), so training continues without dropout after the first validation. (Using no_grad rather than inference_mode is fine.)

Estimate: how long is warmup in tokens?

A run uses 64 GPUs, micro-batch 8 sequences of 4,096 tokens, accumulation 4, and 2,000 warmup steps. How many tokens does warmup cover, and what happens to warmup if the team moves to 128 GPUs with accumulation 2 and keeps 2,000 warmup steps?

Answer

Tokens per optimiser step = 64 × 8 × 4,096 × 4 = 8,388,608 ≈ 8.4M. Warmup = 2,000 × 8.4M ≈ 16.8B tokens. With 128 GPUs and accumulation 2, tokens per step are unchanged (128 × 8 × 4,096 × 2 = 8.4M), so the same 2,000 steps still cover 16.8B tokens — the change is safe for the schedule. Had they kept accumulation 4, the global batch would double to 16.8M tokens; warmup in tokens would double and the learning rate would need retuning.
