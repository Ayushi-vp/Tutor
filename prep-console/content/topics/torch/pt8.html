A team trains on cloud spot instances, which are cheap because the provider can take them back at short notice. Their script saves model.state_dict() every hour. After a preemption, the job restarts from the latest file — and the loss, which had been falling smoothly, jumps back up and takes thousands of steps to recover. The run that finally finishes is measurably worse than an uninterrupted run with the same budget. Nothing crashed. The checkpoint simply did not contain the optimiser's moment estimates, the learning-rate scheduler's step count (so the run went back into warmup), the gradient scaler's state, the random number generator states, or the position in the data. Each restart was a slightly different, slightly worse training run.

Elsewhere, an engineer downloads a fine-tuned model from a public hub and loads it with torch.load. The file is a pickle, and pickles can run code. For years that was the default way PyTorch weights were shared. In PyTorch 2.6 the default of torch.load changed to a restricted mode, weights_only=True, that refuses arbitrary objects — and then a vulnerability was published, CVE-2025-32434, showing that in 2.5.1 and earlier even that restricted mode could be abused for remote code execution. A checkpoint is not just data; it is a file format with a security model.

And at scale, a checkpoint is a distributed systems problem. A 70B-parameter model's full training state is over a terabyte; written by one process it would take far too long, and written by 512 processes it must be consistent across all of them, survive a crash in the middle, and be loadable later on a different number of GPUs.

Interviewers ask about checkpoints because resuming correctly is where training-loop knowledge, systems knowledge and security knowledge meet: "what exactly do you save?", "why did the loss jump after resume?", "how do you load a 70B model on a machine with 128 GB of RAM?", "design checkpointing for a run on 512 GPUs that gets preempted daily". This lesson answers them: the full list of state a training run has, how torch.save and torch.load work underneath, the weights_only change and the CVE, safetensors, loading big models without copying, atomic writes, distributed and asynchronous checkpoints with resharding, and how to test that a resume is truly exact.

Think of a training run as a long journey in a car with a navigator. If you have to stop and continue tomorrow, writing down only where the car is (the weights) is not enough. You also need the navigator's notes on how fast you have been going and in which direction (the optimiser's momentum and variance estimates), the planned speed for each stretch of road (the learning-rate schedule and where you are on it), the gearbox setting (the gradient scaler's current scale), the next pages of the route you were about to drive (the data position), and the dice you roll for detours (random number generators). Restart with only the car's position and you will drive on — but a different journey.

That gives the first half of the picture: a checkpoint is a snapshot of all the state that determines the future of the run. The second half is how it is stored:

  • torch.save / torch.load — PyTorch's native format: a zip file holding a pickle of the Python structure plus raw bytes for each tensor storage. Flexible (any Python object) and therefore dangerous (loading a pickle can run code). Since 2.6, loading is restricted to tensors and simple types by default.
  • safetensors — a simple format with a JSON header and raw bytes, for weights only. Cannot run code; can be read lazily. The standard for publishing models.
  • torch.distributed.checkpoint (DCP) — for multi-GPU runs: every rank writes its own pieces in parallel, with metadata that lets a different number of GPUs load them later.

Every checkpoint design answers three questions, and interview answers are clearest when they take them in order. What to save: the complete list of state that affects future steps — not just weights — in types that can be loaded safely. How to store it: one file or many, which format, how to make the write atomic, and how the file can be loaded later on different hardware or a different number of GPUs. When to save and how many to keep: frequently enough that a failure costs little, rarely enough that saving does not slow training, with old checkpoints retained until new ones are verified. A fourth question appears as soon as anyone else will use the weights: who loads it — your own job, which can trust its own files, or the outside world, which must never need to trust a pickle.

Where the car analogy breaks: on a real journey, small differences in where you restart do not change the destination much. In training they can: neural network training is chaotic in the sense that tiny differences grow (pt6), so "approximately the same state" gives a run that is statistically similar but not identical. Exact resumption is achievable on fixed hardware with deterministic settings, and it is the only way to be sure a resume did not silently change something.

If you remember one sentence: checkpoint everything that determines the future of the run — weights, optimiser, schedules, scaler, RNGs and data position — write it atomically, load untrusted weights only from safe formats, and test that a resumed run matches an uninterrupted one.

A resumable checkpoint must capture every piece of state whose value affects future steps:

The optimiser's state_dict has two parts, as printed for an AdamW on 2.14: "state", keyed by parameter index (0, 1, …) with step, exp_avg and exp_avg_sq per parameter; and "param_groups" with the hyperparameters (lr, betas, eps, weight_decay, flags such as foreach and fused) and the list of parameter indices in each group. Keying by index rather than by name means the optimiser must be rebuilt with parameters in the same order before load_state_dict; adding or reordering parameters between save and load silently pairs moments with the wrong tensors if the shapes happen to match. The distributed helpers in section 7 key by name, which avoids this.

A minimal single-device save and load:

def save_ckpt(path, model, opt, sched, scaler, step, loader_state):
    state = {
        "model": model.state_dict(), "opt": opt.state_dict(),
        "sched": sched.state_dict(), "scaler": scaler.state_dict() if scaler else None,
        "step": step, "loader": loader_state,
        "rng": {"torch": torch.get_rng_state(),
                "cuda": torch.cuda.get_rng_state_all() if torch.cuda.is_available() else [],
                "numpy": np_state_as_lists(), "python": list(random.getstate()[1])},
        "config": cfg_dict,
    }
    tmp = path + ".tmp"
    torch.save(state, tmp)
    os.replace(tmp, path)              # atomic on POSIX: never a half-written file

def load_ckpt(path, model, opt, sched, scaler):
    state = torch.load(path, map_location="cpu", weights_only=True)
    model.load_state_dict(state["model"]); opt.load_state_dict(state["opt"])
    sched.load_state_dict(state["sched"])
    if scaler: scaler.load_state_dict(state["scaler"])
    torch.set_rng_state(state["rng"]["torch"])
    ...                                 # restore the rest, then rebuild the loader at state["loader"]
    return state["step"]

Restore RNG states last, after building the model, optimiser and data loader, because constructing objects (random initialisation) consumes random numbers and would move the generators past the restored point.

2. What torch.save writes

torch.save(obj, f) writes a zip archive. Inside: data.pkl, a pickle of the object structure in which each tensor is replaced by a reference to a storage key; one file per storage containing its raw bytes; and small records for the byte order and format version. Three consequences follow from "one file per storage":

  • Shared storages are saved once and stay shared. Tied weights (pt4) cost nothing extra: on 2.14, saving a dict holding both the tied embedding and head weight produced exactly the same file size as saving one of them. After loading, the two entries again share a storage.
  • Views save their whole storage. Saving the first two elements of a 1,000-element float32 tensor wrote 5,545 bytes on 2.14 — the full 4,000-byte storage plus overhead. Saving a slice of a large activation for debugging can write gigabytes. Clone slices before saving.
  • Device is recorded. A tensor saved from cuda:3 loads onto cuda:3 by default, which fails on a machine with fewer GPUs and puts every rank's tensors on the same GPU if you are careless. Use map_location.

map_location takes a device ("cpu"), a dict remapping device names ({"cuda:3": "cuda:0"}) or a function. The usual patterns: load onto the CPU and let load_state_dict copy into a model that already lives on the right device (safe, costs host memory); or, in a multi-GPU job, load each rank's file with map_location=f"cuda:{local_rank}" so it lands directly on that rank's GPU. Loading every rank's checkpoint without map_location puts them all on the device recorded at save time — typically cuda:0 — and the first GPU runs out of memory while the others sit empty.

3. torch.load, weights_only, and why the default changed

Pickle reconstructs objects by calling functions named in the file. A malicious pickle can name os.system with any argument, so loading it executes code. For years PyTorch loaded checkpoints with the full unpickler, and sharing .pt files on public hubs carried that risk.

PyTorch 2.6 changed the default of torch.load to weights_only=True. The restricted unpickler only reconstructs tensors, storages, primitive types (int, float, str, bool, None), containers (dict, list, tuple, OrderedDict) and classes you explicitly allow. Try to load anything else and, on 2.14, you get:

Weights only load failed. This file can still be loaded, to do so you have two options,
do those steps only if you trust the source of the checkpoint.
    (1) In PyTorch 2.6, we changed the default value of the `weights_only` argument in
    `torch.load` from `False` to `True`. Re-running `torch.load` with `weights_only` set
    to `False` will likely succeed, but it can result in arbitrary code execution. ...

The second option in the message is allow-listing: torch.serialization.add_safe_globals([MyConfig]) (or the torch.serialization.safe_globals context manager) lets the restricted loader rebuild that class. A practical trap shows up immediately in checkpoint code: np.random.get_state() returns a tuple containing a NumPy array and NumPy type objects, and a checkpoint containing it fails to load under the default on 2.14. Store NumPy's state as plain Python lists and ints (or as a tensor) so the whole checkpoint loads with weights_only=True.

The restricted loader is a large improvement, not a guarantee. CVE-2025-32434, recorded in the US National Vulnerability Database, describes a remote command execution vulnerability "when loading a model using torch.load with weights_only=True" in PyTorch 2.5.1 and earlier, patched in 2.6.0. Two lessons: keep PyTorch current on any machine that loads third-party checkpoints, and do not use pickle-based formats for weights from sources you do not control.

4. safetensors

safetensors, from Hugging Face, is the standard for distributing weights. Its README specifies the whole format: the first 8 bytes are N, an unsigned little-endian 64-bit integer giving the header size; the next N bytes are a UTF-8 JSON header mapping each tensor name to its dtype, shape and data_offsets (begin and end within the data buffer), plus an optional __metadata__ map of strings; then the raw bytes of all tensors. There is nothing to execute. A reader can parse the header, then memory-map the file and create tensors pointing straight into the mapped bytes (zero-copy), or read only the tensors it needs (lazy loading) — useful when each GPU needs only its shard of a huge model.

The limits follow from the design: only tensors and string metadata, so optimiser state with nested Python structures and RNG tuples needs flattening, and shared tensors are a problem — the format stores each named tensor's bytes separately, so the library refuses to save tensors that share memory (such as tied weights) unless you deduplicate them, for which its PyTorch helpers provide functions (save_model / load_model) that drop the duplicate name and restore the tie on load. Use safetensors for release and inference weights; training checkpoints can stay in torch.save format (or DCP) as long as only your own jobs load them.

5. Loading big models without copying everything

A naive load of a 70B-parameter bf16 model — 140 GB — allocates the model with random weights (140 GB), reads the checkpoint into RAM (another 140 GB), copies into the model, and then moves to GPUs. Three tools remove the duplicates:

  • Meta-device construction: with torch.device("meta"): model = Model(cfg) builds the module tree with shapes but no storage (pt4), in milliseconds.
  • Memory-mapped loading: torch.load(path, mmap=True, map_location="cpu", weights_only=True) maps the file and creates tensors that read from it on access, instead of reading the whole file into RAM.
  • Assigning instead of copying: model.load_state_dict(sd, assign=True) makes the model's parameters be the loaded tensors, rather than copying into existing ones (which is impossible on meta tensors anyway).
with torch.device("meta"):
    model = GPT(cfg)
sd = torch.load("model.pt", mmap=True, map_location="cpu", weights_only=True)
model.load_state_dict(sd, assign=True)    # parameters now map the file
model.tie_weights()                         # re-tie: assign replaced each Parameter separately
model.to("cuda", dtype=torch.bfloat16)      # pages are read from disk as they are copied

With safetensors the same pattern is shard-by-shard: open each file, read only the tensors this rank needs, and place them directly on the right device. That is how inference servers load models larger than host RAM.

6. Atomic writes, retention and verification

Jobs die mid-write. A preempted spot instance gets a short warning (seconds to minutes) and is terminated; an OOM kill or node failure gives none. If the checkpoint is written directly to its final name, the latest checkpoint may be truncated exactly when you need it. Write to a temporary path and os.replace it into place: on POSIX file systems the rename is atomic, so readers see either the old complete file or the new complete file. On object storage, upload the checkpoint under a new key and then update a small pointer object ("latest → step_120000") only after every piece has been uploaded; resumption reads the pointer.

Keep the last few checkpoints (and periodic milestones), delete older ones only after a newer one has been verified, and verify by loading: at minimum check the file's size and that it opens; better, have a background process load it on CPU and compare a few tensor checksums with values logged at save time. Corrupt checkpoints are discovered at the worst possible moment otherwise.

7. Distributed checkpoints and resharding

With data parallelism (DDP), every rank has a full copy of the model, and the simple approach — rank 0 saves, everyone else waits at a barrier — works for small models. With sharded training (FSDP, tensor parallelism; pt11), no rank holds the full state, and gathering it onto one rank would need a full copy of the model in one GPU's or host's memory and serialise the write through one process. torch.distributed.checkpoint (DCP) instead has every rank write its own shards in parallel, plus a metadata file recording, for each tensor, its global shape and which chunks each file contains.

import torch.distributed.checkpoint as dcp
from torch.distributed.checkpoint.state_dict import get_state_dict, set_state_dict

model_sd, optim_sd = get_state_dict(model, optimizer)       # sharded, keyed by FQN
dcp.save({"model": model_sd, "optim": optim_sd, "step": step},
         checkpoint_id=f"ckpt/step_{step}")

# later, possibly on a different number of GPUs
model_sd, optim_sd = get_state_dict(model, optimizer)
state = {"model": model_sd, "optim": optim_sd, "step": 0}
dcp.load(state, checkpoint_id=f"ckpt/step_{step}")         # fills state in place, resharding
set_state_dict(model, optimizer, model_state_dict=state["model"], optim_state_dict=state["optim"])

get_state_dict and set_state_dict hide the differences between plain modules, DDP and FSDP, and key optimiser state by fully qualified parameter name rather than index. Load is "in place": you pass a state dict whose tensors already have the new layout, and DCP's load planner reads, for each local shard, the byte ranges of the saved chunks that overlap it. That is resharding: a checkpoint written by 64 ranks loads on 32, or on one for conversion to a release format. On 2.14 DCP also includes storage readers and writers for the Hugging Face safetensors layout, so a distributed checkpoint can be written in, or read from, the format used for publishing.

8. Asynchronous checkpointing

Writing 1 TB of training state to network storage at, say, 10 GB/s aggregate takes 100 seconds; stalling every GPU for that long every 30 minutes wastes about 5% of the run. dcp.async_save splits the work: first each rank copies its state to host memory (fast — GPU to pinned host memory runs at tens of GB/s per GPU, so seconds), then training resumes while a background thread or process writes the host copy to storage, returning a future you check before the next save. The costs are host memory for the staged copy (the size of each rank's state) and some contention for network and CPU during the write. Large training runs combine async saving with frequent checkpoints so a failure costs minutes of compute rather than hours.

9. The data position

For a map-style dataset with a seeded sampler, the position is "epoch e, next batch b". On resume, call sampler.set_epoch(e) (pt5) and skip the first b batches of indices — iterating the batch sampler, not the DataLoader, so no samples are loaded and skipping is nearly free. For a DataLoader with workers and an IterableDataset, the position is spread across processes: which shard each worker was reading, at what offset, and the contents of any shuffle buffer. The torchdata project's StatefulDataLoader is a drop-in replacement for torch.utils.data.DataLoader that provides state_dict() and load_state_dict(), asking each worker for its dataset's state when you checkpoint. Your IterableDataset must implement state_dict/load_state_dict itself for this to be exact.

10. Fine-tuning and adapter checkpoints

Fine-tuning changes the calculus. With full fine-tuning the checkpoint is as large as for pretraining, but the base model is usually available elsewhere, so the release artefact can be the full fine-tuned weights or, for parameter-efficient methods such as LoRA (lm11), only the adapter matrices — often a few megabytes to a few hundred megabytes instead of tens of gigabytes. The adapter checkpoint is useless without the exact base weights it was trained against, so it must record which base model (name, revision or a checksum of the weights) and the adapter configuration (rank, target modules, scaling). A common failure is loading an adapter onto a different revision of the "same" base model: everything loads, shapes match, and quality drops. Training state for adapter runs is small too — optimiser moments only for the adapter parameters — which makes frequent checkpoints cheap.

11. Versioning, compatibility and key mapping

Checkpoints outlive the code that wrote them. A month later, someone renames self.attn to self.attention, fuses Q, K and V into one projection, or upgrades a library whose module names changed, and every old checkpoint fails strict loading. Three habits keep checkpoints loadable. Store a format version and the code version (a git commit hash) in every checkpoint. Keep a small, tested function that maps old state-dict keys and shapes to new ones — splitting a fused QKV weight into three, renaming prefixes — and run it automatically based on the stored version. And add a test that loads a stored checkpoint from each old format and checks outputs on a fixed input. This is the same discipline databases apply to schema migrations, and for the same reason: data lives longer than code.

12. Testing that resume is exact

The only convincing test is a comparison. Under deterministic settings (pt6) on one fixed machine, run N + M steps uninterrupted and record the loss at every step. Separately, run N steps, checkpoint, start a fresh process, resume, and run M steps. The two loss sequences should match bitwise, or within floating-point noise if some kernels are non-deterministic. If they diverge, the step where they first differ tells you what was missed: immediately (model or optimiser state), at the first dropout (RNG), at the next learning-rate change (scheduler), at the first skipped fp16 step (scaler), or at the data-dependent step (loader position). Run this test in CI on a tiny model; it catches the most expensive class of silent training bugs for the cost of a few seconds.

Why the optimiser state is keyed by index, and what that breaks

torch.optim.Optimizer.state_dict() identifies parameters by their position in the order the optimiser received them, because an optimiser has no access to parameter names. Loading pairs saved state with parameters by position. If between save and load you add a parameter, freeze one and leave it out of the optimiser, wrap the model differently, or construct parameter groups in a different order, the moments attach to the wrong tensors. When shapes differ, the load or the first step fails; when shapes coincide (two layers of the same size), it silently succeeds with swapped moments. The distributed state-dict helpers key optimiser state by fully qualified parameter name, and many training frameworks do the same conversion even for single-GPU runs, which makes checkpoints robust to refactors.

Consistency across ranks

A distributed checkpoint is only valid if every rank saved state from the same step. If one rank is preempted after writing step 1,200 while others wrote step 1,180's shards and crashed, a naive "latest" directory mixes steps. Robust schemes write each checkpoint to a directory named by step, have each rank write its shards, synchronise with a barrier, and only then have rank 0 write a completion marker (DCP's metadata file plays a similar role: it is written after the shards). Resumption ignores any directory without the marker. With asynchronous saving, the marker must wait until every rank's background write has finished, not just staged.

Checkpoint frequency as an optimisation problem

Checkpointing costs time; not checkpointing risks losing work. A classic first-order answer, Young's approximation, sets the interval to about √(2 × C × M), where C is the cost of one checkpoint (the stall it causes) and M the mean time between failures. With a 30-second effective stall and one failure every 24 hours (86,400 seconds), √(2 × 30 × 86,400) ≈ 2,280 seconds — about 38 minutes. Asynchronous saving shrinks C, which pushes the optimum toward more frequent checkpoints. At thousands of GPUs, failures become frequent (the mean time between failures of the whole job falls roughly in proportion to the number of components), which is why large runs checkpoint every few minutes and invest heavily in fast, async, sharded saving.

Format conversions and the release path

Training checkpoints and release artefacts differ: training state in float32 with optimiser moments and sharded by rank; release weights in bf16, consolidated or split into evenly sized safetensors shards with an index file mapping tensor names to files, and with tied weights deduplicated. The conversion is a separate, tested step: load the DCP checkpoint (resharding to one process or to a few CPU processes), cast, rename keys to the public architecture's names, save as safetensors, then load the result into a fresh model and compare outputs against the training model on a fixed batch. Errors here — a missed transpose in a fused QKV weight, a forgotten tie — produce models that load without complaint and generate nonsense.

Averaging checkpoints

Saved checkpoints are not only for resuming. Averaging the weights of the last few checkpoints of a run (or keeping an exponential moving average, pt6) often gives a slightly better model than any single one, because the average sits nearer the centre of the region the optimiser was bouncing around in at the end of training. Averaging fine-tuned models that share a base ("model soups") can combine their strengths. Mechanically it is simple — load state dicts and average tensors key by key, in float32, skipping integer buffers such as BatchNorm's num_batches_tracked — but it only works for checkpoints in the same basin: averaging two independently trained models from different random initialisations generally produces garbage, because their hidden units are permuted relative to each other.

Resuming with a different configuration

Sometimes a resume deliberately changes things: more GPUs, a different micro-batch size or accumulation, a new learning-rate schedule for a continued-training phase, or a new dataset mixture. Each needs a decision about which saved state to keep. The weights and optimiser moments carry over (DCP reshards them); the scheduler is usually rebuilt with an explicit starting step; the data position may no longer mean anything if the dataset changed, so continued training logs the tokens seen per source rather than an index. When the global batch size changes, the effective learning rate changes too (pt6), and continuing with the old schedule unmodified is a common cause of a loss bump right after an "upgrade" restart.

Pickle risk beyond torch.load

Many formats in the ML ecosystem are pickles in disguise: joblib and pickle files for scikit-learn models, NumPy's np.load(..., allow_pickle=True), and older PyTorch tooling that unpickles configs or tokenizers. The defences are the same: treat any pickle from outside your organisation as code, scan model repositories for pickle opcodes that import dangerous modules, and prefer data-only formats (safetensors, JSON, Arrow, ONNX's protobuf). Inside your organisation, the restricted loader and allow-listing still help: they catch accidental dependence on classes that will not exist after a refactor.

Failure mode: the loss jumps after resume

Symptom: a visible spike or plateau right after every restart. Diagnose by what the run looks like in the first steps after resume: a large jump that decays over a few hundred steps is fresh optimiser state; the learning rate in the logs dropping back toward warmup is scheduler state; several "skipped step" messages with fp16 is GradScaler state; a change in the training curve's noise pattern without a jump is RNG or data order. Fix by saving the full state and adding the resume-equivalence test to CI.

Failure mode: the checkpoint will not load

"Weights only load failed" after upgrading to PyTorch 2.6 or later — the checkpoint contains arbitrary objects (config dataclasses, NumPy RNG state, an argparse Namespace); convert them to plain types, allow-list them, or load trusted legacy files with weights_only=False once and re-save. "Missing key(s) … Unexpected key(s)" — prefixes from DDP or torch.compile (pt4), or a refactor that renamed modules; a key-mapping function in the loader, tested against old checkpoints, solves it permanently. "CUDA error: invalid device ordinal" — saved on more GPUs than the loading machine has; use map_location.

Failure mode: corrupt or inconsistent checkpoints

Symptom: resume fails with a zip or unpickling error, or loads but produces NaNs. Causes: a write interrupted by preemption (no atomic rename), a full disk, a distributed checkpoint mixing steps across ranks, or a background async write not finished when the job exited. Prevention: atomic rename or completion markers, waiting on async save futures before exit (and on preemption notice), retention of several checkpoints, and a verifier that loads each new checkpoint off the critical path.

Failure mode: checkpoints that are far too big or too slow

Symptom: checkpoint size is several times the expected 12–16 bytes per parameter, or saving stalls training for minutes. Causes: views of large tensors saved with their whole storages (debug tensors, cached activations attached to the model), saving every rank's full DDP replica instead of rank 0's, float32 copies of things that could be bf16, or synchronous writes to slow storage. Fixes: audit the state dict's tensor sizes, save once per replica group, use DCP with async saving, and write to fast local disk first if the cluster has it, uploading in the background.

Handling the preemption notice

Cloud providers and cluster schedulers usually announce a preemption before killing a job — by sending the process SIGTERM and waiting a grace period, or through a metadata endpoint the job can poll. A training script can install a signal handler that sets a flag; the training loop checks the flag at the end of each step and, if set, writes an emergency checkpoint (or waits for an in-flight async save to finish) and exits cleanly. The handler itself should only set the flag: doing I/O or touching CUDA inside a signal handler is unsafe. In distributed jobs every rank must agree to stop at the same step, so the decision is shared with an all-reduce of the flag before saving. The grace period bounds what you can write: if it is 30 seconds and a synchronous checkpoint takes 60, the emergency save must be an async stage-to-host that a sidecar finishes, or the job must rely on its last periodic checkpoint.

Observability for checkpoints

Treat checkpoints as a monitored service. Emit metrics for checkpoint age (time since the last successful, verified checkpoint — alert if it exceeds two intervals), save duration and training stall per save, checkpoint size (a sudden increase usually means something unintended is being saved), and verification results. Log at resume time which checkpoint was loaded, its step, and the learning rate and GradScaler scale after loading, so a bad resume is visible in the first lines of the log rather than in a loss curve a day later.

The public case: CVE-2025-32434

The NVD entry for CVE-2025-32434 is short and worth quoting in an interview: in PyTorch 2.5.1 and prior, "a Remote Command Execution (RCE) vulnerability exists in PyTorch when loading a model using torch.load with weights_only=True", patched in 2.6.0 — the same release that made weights_only=True the default. It is a precise illustration of defence in depth: the restricted loader was the right mitigation for pickle's design, it had an implementation flaw, and the robust position for production systems is to load third-party weights only from a format with no code path at all (safetensors), keep frameworks patched, and run model-loading services with least privilege.

CPU, PyTorch 2.14 in gpt_env; about 15 minutes. Save as pt8_lab.py. It checks that a resume is exact, then shows the weights_only behaviour.

import os, io, random, numpy as np, torch, torch.nn as nn, torch.nn.functional as F
torch.use_deterministic_algorithms(True)
def build(seed=0):
    torch.manual_seed(seed)
    m = nn.Sequential(nn.Linear(16, 32), nn.ReLU(), nn.Dropout(0.1), nn.Linear(32, 4))
    o = torch.optim.AdamW(m.parameters(), lr=1e-2)
    s = torch.optim.lr_scheduler.LinearLR(o, start_factor=0.1, total_iters=20)
    return m, o, s
data = [(torch.randn(8, 16, generator=torch.Generator().manual_seed(i)),
         torch.randint(0, 4, (8,), generator=torch.Generator().manual_seed(1000 + i))) for i in range(40)]
def run(m, o, s, steps):
    out = []
    for x, y in steps:
        loss = F.cross_entropy(m(x), y); loss.backward(); o.step(); s.step(); o.zero_grad()
        out.append(loss.item())
    return out

Find the bug: a checkpoint routine for preemptible training

This routine runs every 2,000 steps on a single-GPU fp16 job on spot instances. After each preemption the loss jumps, the learning rate in the logs restarts at the warmup value, and once the job could not restart at all because the checkpoint file was "not a zip archive". Find the bugs.

def save(step):
    torch.save({"model": model.state_dict(), "step": step,
                "np_rng": np.random.get_state(), "cfg": cfg},     # cfg is a dataclass
               "/ckpt/latest.pt")

def resume():
    st = torch.load("/ckpt/latest.pt", weights_only=False)
    model.load_state_dict(st["model"])
    torch.manual_seed(st["step"])
    return st["step"]
Answer

Bug 1 — the optimiser, scheduler and GradScaler are not saved. Adam restarts with empty moments (the loss jump), the scheduler restarts at step 0 (the learning rate back at its warmup value), and the GradScaler restarts at 65,536 (skipped steps). Fix: save and restore optimizer.state_dict(), scheduler.state_dict() and scaler.state_dict(), plus the data position.

Bug 2 — non-atomic write to a single file. A preemption during torch.save left a truncated latest.pt — "not a zip archive" — and there was no older checkpoint to fall back on. Fix: write to latest.pt.tmp and os.replace it, keep the last few checkpoints, and verify after writing.

Bug 3 — RNG "restore" by reseeding. torch.manual_seed(step) creates a new stream rather than continuing the old one, and the CUDA and NumPy states are not restored at all (NumPy's is saved but never set). Fix: save torch.get_rng_state() and torch.cuda.get_rng_state_all() and restore them, together with NumPy and Python's states, after building all objects.

Bug 4 — the checkpoint needs weights_only=False. The dataclass config and NumPy RNG tuple force full unpickling. It works for this team's own files, but it makes the checkpoint loadable only with the unsafe loader and fragile under refactors (the dataclass's import path is baked in). Fix: store dataclasses.asdict(cfg) and NumPy's state as plain lists and ints, and load with the default weights_only=True.

Estimate: how long does a checkpoint take?

A 13B-parameter model trains with AdamW and float32 master weights, sharded with FSDP across 64 GPUs. Storage sustains 20 GB/s aggregate writes; GPU-to-host copies run at about 20 GB/s per GPU. How big is a full training checkpoint, how long does a synchronous save stall training, and how long with async saving?

Answer

State ≈ 12 bytes per parameter for weights and Adam moments (gradients need not be saved): 13×10⁹ × 12 ≈ 156 GB, about 2.4 GB per GPU. Synchronous write: 156 GB ÷ 20 GB/s ≈ 7.8 s of stall plus coordination — call it 10 s. Async: the stall is only the device-to-host staging, 2.4 GB ÷ 20 GB/s ≈ 0.12 s per GPU in parallel, plus overhead; the 8 s of writing then overlaps with training. With saves every 15 minutes, synchronous saving costs about 1.1% of training time, async under 0.1%, at the price of 2.4 GB of extra host memory per GPU.
