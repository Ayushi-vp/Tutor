The ML-debugging round has become a fixture of senior ML and AI-engineer interviews, and some frontier labs build entire rounds around it. The format is usually the same: you are given a short, realistic training script — a small transformer on character-level text, an image classifier, a fine-tuning loop — and told something like "the loss never gets good", "the validation numbers look too good to be true", or "it goes NaN after a while". The script runs. Nothing crashes. Somewhere in eighty lines there are four to eight planted bugs, each of which degrades training silently, and you have forty-five minutes to find as many as you can and explain, for each one, the symptom it causes, the root cause and the minimal fix.

Candidates fail this round in two ways. Some read the code top to bottom hoping to spot errors, and run out of time after finding the two obvious ones. Others guess — "maybe the learning rate is too high?" — and tune hyperparameters on a broken pipeline. What interviewers want is the third approach: a fixed sequence of cheap experiments, each of which tests one hypothesis, combined with targeted reading of the lines the failing experiment points at. It is the same method that works in real projects, where the bug is not planted but a model that is "a few points worse than the paper" has cost a team weeks.

Andrej Karpathy's widely cited essay "A Recipe for Training Neural Networks" gives most of the experiments: verify the loss at initialisation, train an input-independent baseline, overfit one batch, and "use backprop to chart dependencies". This lesson turns them into a procedure and applies it to one complete buggy script — a character-level transformer language model with eight planted bugs drawn from the catalogue every interviewer uses: labels not shifted, a mask applied multiplicatively instead of with −∞, softmax over the wrong dimension, BatchNorm in a sequence model, a double softmax before cross-entropy, a loss broadcast to the wrong shape, a forgotten eval(), and a train/validation split that leaks. For each bug you will see the symptom it produces, the check that exposes it, and the fix. The lesson ends with the tools for the hardest category — NaNs and instabilities that appear after hours — and with how to talk through all of this under time pressure.

Think of ML debugging as a doctor's examination rather than proofreading. A patient's symptoms (the loss curve, the validation numbers, a NaN) are compatible with many causes. A good doctor does not read the whole medical textbook; they run a short sequence of tests, each ruling a group of causes in or out, and only then examine the organ the tests point to. In training code the tests are cheap — seconds to minutes on a CPU — and the same ones work for nearly every model.

The examination, in order:

  1. Read the vital signs. Run the script and look at what it prints: the loss at step 0, how fast it falls, where it ends, how validation compares with training. Each has an expected value you can compute.
  2. Loss at initialisation. For a V-way classifier with small initial logits, the first loss is about ln V. For 65 characters that is 4.17.
  3. Overfit one batch. Train on one fixed small batch. A correct pipeline drives the loss near zero; a broken loss, broken gradient flow or broken label alignment cannot — or does so suspiciously fast.
  4. Dependency test. Backpropagate from one output position and see which inputs receive gradient. For a causal model, only the same sequence and earlier positions may.
  5. Mode and data checks. Compare train-mode and eval-mode outputs; check that validation data is disjoint from training data.
  6. Gradient health. Per-layer gradient norms show where gradients vanish, explode or are missing; anomaly detection finds the first NaN.

Where the doctor analogy breaks: patients have one illness at a time far more often than planted scripts do. Bugs interact — a leaking mask can hide unshifted labels, a double softmax can hide a bad initialisation — so after each fix, rerun the earlier checks. And unlike a patient, a script can be changed and rerun in seconds; the fastest debuggers are the ones who turn every hypothesis into a two-line experiment.

If you remember one sentence: compute what each signal should be, run the cheap checks in a fixed order, let the first failing check tell you where to read, and after every fix run the checks again.

One more framing helps under pressure: sort what you see into "cannot learn", "learns the wrong thing" and "measured wrongly". Cannot learn — flat or capped loss — points at loss wiring, gradient flow and the optimiser. Learns the wrong thing — too-good training loss, poor generation — points at leaks and label alignment. Measured wrongly — validation that is unstable or too close to training — points at evaluation mode, aggregation and the data split. The script in this lesson has bugs in all three groups, which is typical of the interview format.

1. The script

Here is the kind of script you will be handed: a character-level transformer language model on Shakespeare (65 distinct characters), with an auxiliary head that predicts the fraction of spaces in the window. It is 80 lines, it runs on a CPU, it prints a decreasing training loss and a validation loss that looks excellent. It contains eight planted bugs, marked here with the numbers used below — in an interview they are not marked.

import torch, torch.nn as nn, torch.nn.functional as F
torch.manual_seed(0)
text = open("shakespeare.txt").read()
chars = sorted(set(text)); V = len(chars)                  # V = 65
stoi = {c: i for i, c in enumerate(chars)}
data = torch.tensor([stoi[c] for c in text])
T, B = 64, 32

starts = torch.randperm(len(data) - T - 1)                  # [1] random split of
n_val = len(starts) // 10                                   #     overlapping windows
val_starts, train_starts = starts[:n_val], starts[n_val:]

def get_batch(starts):
    idx = starts[torch.randint(len(starts), (B,))]
    x = torch.stack([data[i:i + T] for i in idx])
    y = torch.stack([data[i:i + T] for i in idx])          # [2] labels not shifted
    return x, y

class Block(nn.Module):
    def __init__(self, C, H):
        super().__init__()
        self.H = H
        self.qkv, self.proj = nn.Linear(C, 3 * C), nn.Linear(C, C)
        self.norm1 = nn.LayerNorm(C)
        self.norm2 = nn.BatchNorm1d(C)                      # [3] BatchNorm in a causal LM
        self.mlp = nn.Sequential(nn.Linear(C, 4 * C), nn.GELU(), nn.Linear(4 * C, C))
        self.register_buffer("mask", torch.tril(torch.ones(T, T)))

    def forward(self, x):                                   # x: (B, T, C)
        Bx, Tx, C = x.shape
        q, k, v = self.qkv(self.norm1(x)).split(C, dim=-1)
        q, k, v = (t.view(Bx, Tx, self.H, C // self.H).transpose(1, 2) for t in (q, k, v))
        att = (q @ k.transpose(-2, -1)) / (C // self.H) ** 0.5
        att = att * self.mask[:Tx, :Tx]                     # [4] multiplicative mask
        att = att.softmax(dim=-2)                           # [5] softmax over queries
        y = (att @ v).transpose(1, 2).contiguous().view(Bx, Tx, C)
        x = x + self.proj(y)
        h = self.norm2(x.transpose(1, 2)).transpose(1, 2)
        return x + self.mlp(h)

class LM(nn.Module):
    def __init__(self, C=128, H=4, L=4):
        super().__init__()
        self.tok, self.pos = nn.Embedding(V, C), nn.Embedding(T, C)
        self.blocks = nn.Sequential(*[Block(C, H) for _ in range(L)])
        self.ln, self.head = nn.LayerNorm(C), nn.Linear(C, V)
        self.aux = nn.Linear(C, 1)                          # predicts fraction of spaces

    def forward(self, x):
        h = self.tok(x) + self.pos(torch.arange(x.shape[1]))
        h = self.ln(self.blocks(h))
        return F.softmax(self.head(h), dim=-1), self.aux(h[:, -1])   # [6] double softmax

model = LM()
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)
space = stoi[" "]

for step in range(5001):
    x, y = get_batch(train_starts)
    probs, space_pred = model(x)                            # space_pred: (B, 1)
    loss = F.cross_entropy(probs.view(-1, V), y.view(-1))
    frac = (x == space).float().mean(dim=1)                 # (B,)
    loss = loss + 0.1 * ((space_pred - frac) ** 2).mean()   # [7] (B,1) - (B,) -> (B,B)
    opt.zero_grad()
    loss.backward()
    opt.step()
    if step % 500 == 0:
        with torch.no_grad():                               # [8] model never put in eval()
            xv, yv = get_batch(val_starts)
            vprobs, _ = model(xv)
            vloss = F.cross_entropy(vprobs.view(-1, V), yv.view(-1))
        print(f"step {step}: train {loss.item():.3f}  val {vloss.item():.3f}")

Before reading any line closely, apply the procedure. Each section below takes one bug, gives the symptom it would produce on its own, the check that exposes it, the root cause, and the minimal fix.

2. Vital signs and the loss at initialisation

For 65 classes, a model with small initial logits should start near ln 65 = 4.17. Two of the bugs distort this. With bug 6 (double softmax), the step-0 loss is still near 4.17 — the probabilities are all about 1/65, which as "logits" are nearly equal — so the init check passes, but the next check will not. With bug 2 (unshifted labels) the step-0 loss is also 4.17; the problem shows in how fast it falls. That is the general lesson: one number rarely identifies a bug, but every number has an expected value, and comparing is free.

The double-softmax ceiling is worth computing because it gives a crisp signature. F.cross_entropy applies log_softmax to its input. If the input is probabilities in [0, 1], the best the model can do is put probability 1 on the target and 0 elsewhere, which cross_entropy sees as logits (1, 0, 0, …). The loss is then −log(e¹ / (e¹ + 64·e⁰)) = log(e + 64) − 1 ≈ 3.20 (confirmed on 2.14: 3.2005). So a training curve that drops from 4.17 and flattens around 3.3 — no matter how long you train or how big the model — is the fingerprint of bug 6.

3. Overfit one batch

Fix one batch and train on it for a few hundred steps:

xb, yb = get_batch(train_starts)
for i in range(300):
    probs, _ = model(xb)
    l = F.cross_entropy(probs.view(-1, V), yb.view(-1))
    opt.zero_grad(); l.backward(); opt.step()
    if i % 50 == 0: print(i, l.item())

A correct 4-layer model memorises 32 × 64 characters easily: the loss should approach zero. Here two outcomes are possible, and each is informative. With the double softmax, the loss stalls above 3.2 — the pipeline cannot express confidence, so the check fails, and you look at what goes into the loss: bug 6. Fix: return raw logits from the model (return self.head(h), …) and let F.cross_entropy do the log-softmax; use softmax only for sampling.

After fixing bug 6, rerun the check and the loss collapses to near zero in a few dozen steps — far faster than memorisation should allow, and the full training run now shows a training loss falling below 0.1 within a few hundred steps. That is "too good", and too good means the answer is in the input. Read the data code with that hypothesis: y is built from data[i:i + T], exactly like x. Position t is asked to predict the character it is looking at: bug 2, unshifted labels. A language model must predict the next token: y = data[i + 1:i + T + 1], so y[:, t] == x[:, t + 1]. A one-line assertion catches it forever: assert torch.equal(y[:, :-1], x[:, 1:]). Symptom summary: training loss near zero, generation that is garbage because at sampling time the next character is not available to copy.

4. The dependency test finds three bugs at once

Even with labels shifted, a causal model can cheat by looking at future positions. Shapes cannot reveal this; gradients can. Put the model in eval mode, feed embeddings that require grad, and ask which input positions influence the output at position t:

model.eval()
x, _ = get_batch(train_starts)
emb = (model.tok(x) + model.pos(torch.arange(T))).detach().requires_grad_(True)
h = model.ln(model.blocks(emb))
h[0, 10].sum().backward()                     # output at example 0, position 10
g = emb.grad.abs().sum(-1)                    # (B, T) influence of each input position
print("future positions:", g[0, 11:].sum().item())   # must be 0
print("other examples:", g[1:].sum().item())         # must be 0

Run it on the buggy model and the future-position gradient is clearly non-zero. Now read the attention code with the hypothesis "something lets position 10 see position 11", and three lines qualify:

Bug 4 — multiplicative mask. att * mask sets future scores to 0, not −∞. After softmax, a score of 0 still gets weight e⁰ = 1 relative to the others, so every position attends to the future. Fix: att = att.masked_fill(self.mask[:Tx, :Tx] == 0, float("-inf")) — the mask must remove positions before the softmax, with −∞, so they receive exactly zero probability (pt2).

Bug 5 — softmax over the wrong dimension. The score tensor is (B, H, Tquery, Tkey); each query's weights over keys must sum to 1, so softmax runs over the last dimension. softmax(dim=-2) normalises each key's column across queries instead. Even with a correct −∞ mask, the weight query 0 gives key 0 then depends on the scores of all later queries for key 0 — a leak — and rows no longer sum to 1, so the output's scale varies by position. (Run on 2.14 with a correct mask and dim −2, row 0's weight for key 0 was 0.994 and the last row's weights summed to well above 1.) Fix: softmax(dim=-1).

Bug 3 — BatchNorm in a sequence model. nn.BatchNorm1d(C) applied to the (B, C, T) transpose computes each channel's mean and variance over the batch and all T positions. In training mode, the normalised value at position 10 therefore depends on positions 11 to 63 and on the other 31 sequences — future information leaks through the statistics (on 2.14, a tiny (2, 6, 4) example gives a future-position gradient sum of about 1.3 in training mode). In eval mode BatchNorm uses running statistics, so the leak disappears at inference — but the model was trained relying on it, so it does worse than training suggested. With small micro-batches the statistics are also noisy (pt4). Fix: nn.LayerNorm(C) applied to (B, T, C) directly, which normalises each position on its own. Note that the dependency test above runs in eval mode, so to see bug 3's leak specifically, repeat the test in train mode.

After fixing all three, the future-position gradient is exactly zero, and it should stay that way: keep the test in your test suite.

5. Shapes in the loss: the broadcast bug

Next, check every loss line for shapes (pt2). space_pred is (B, 1) — the auxiliary head outputs one number per sequence — and frac is (B,). space_pred - frac broadcasts to (32, 32): every prediction minus every target. The mean is finite, so nothing complains, and the auxiliary head learns to predict the batch-average space fraction for every input: bug 7. Symptom: the auxiliary loss falls to the variance of the targets and stops; predictions do not depend on the input. Check: assert space_pred.squeeze(-1).shape == frac.shape. Fix: (space_pred.squeeze(-1) - frac), or use F.mse_loss, which would at least have warned about the size mismatch.

6. Modes: the evaluation that is not

The evaluation block uses torch.no_grad() but never calls model.eval(): bug 8. With BatchNorm present (bug 3), the validation forward runs in training mode, normalising with the validation batch's own statistics and updating the running statistics with validation data. Even after replacing BatchNorm, any dropout would stay active. Check: run the same validation batch twice in training mode and once in eval mode; outputs differ (and with dropout differ between the two training-mode runs). Symptom: validation numbers that depend on batch composition and size. Fix: the evaluate() pattern from pt6 — model.eval(), torch.inference_mode(), sums and counts, and model.train() afterwards. In this script, also evaluate more than one random batch; a single batch of 32 windows gives a noisy number.

7. The split: validation that is mostly training data

Even after all the model fixes, the validation loss sits almost exactly on the training loss — on a model large enough to overfit 1 MB of text. That should not happen, and the data code explains it: bug 1. The script lists every possible window start (stride 1), shuffles the starts, and puts 10% of them in validation. A validation window starting at position 1,000 covers characters 1,000–1,063; the training windows starting at 999 and 1,001 cover 63 of the same 64 characters. Almost every validation window is a one-character shift of training windows, so "validation" measures memorisation of training text. Check: for a sample of validation windows, test whether a training window overlaps them; or compute validation loss on a genuinely separate text. Fix: split the raw character sequence by position first — the first 90% for training, the last 10% for validation — and draw windows within each split, as nanoGPT-style data preparation does. Leakage of this kind — overlapping samples, duplicates, preprocessing on the full dataset — is the most common reason published ML results fail to replicate, as Kapoor and Narayanan's survey across 17 fields documents.

8. The fixed script, and checking that it is fixed

The minimal fixes, in diff form:

- starts = torch.randperm(len(data) - T - 1) ...            [1]
+ n = int(0.9 * len(data)); train_data, val_data = data[:n], data[n:]
-     y = torch.stack([data[i:i + T] for i in idx])          [2]
+     y = torch.stack([split[i + 1:i + T + 1] for i in idx])   # split = train_data or val_data
-         self.norm2 = nn.BatchNorm1d(C)                     [3]
+         self.norm2 = nn.LayerNorm(C)                       (and drop the transposes)
-         att = att * self.mask[:Tx, :Tx]                    [4]
+         att = att.masked_fill(self.mask[:Tx, :Tx] == 0, float("-inf"))
-         att = att.softmax(dim=-2)                          [5]
+         att = att.softmax(dim=-1)
-         return F.softmax(self.head(h), dim=-1), ...        [6]
+         return self.head(h), ...
-     ((space_pred - frac) ** 2).mean()                      [7]
+     ((space_pred.squeeze(-1) - frac) ** 2).mean()
-         with torch.no_grad(): ...                          [8]
+         model.eval(); with torch.inference_mode(): ...; model.train()

Then rerun the whole procedure: step-0 loss ≈ 4.17; overfit one batch to near zero in a few hundred steps (not a few dozen); dependency test zero on future positions and other examples, in both train and eval mode; eval-mode validation stable across batch sizes; and a validation loss that now rises above training loss as the model starts to overfit. For reference, nanoGPT's README reports a best validation loss of 1.4697 for its 6-layer, 384-channel character-level Shakespeare model; this smaller model should land somewhat above that. Expected values like this are worth knowing for the datasets you discuss.

9. Per-layer gradient norms

Some bugs do not show in any of the checks above but in how gradients are distributed. After a backward pass:

norms = {n: p.grad.norm().item() for n, p in model.named_parameters() if p.grad is not None}
missing = [n for n, p in model.named_parameters() if p.requires_grad and p.grad is None]

Read them as a profile. Parameters in missing are disconnected from the loss: a detach() or no_grad in forward, an unused branch, a layer stored in a Python list (pt4). Norms that shrink by orders of magnitude from the output toward the input mean vanishing gradients (missing residual connections, saturating activations, missing normalisation). One layer with norms orders of magnitude above its neighbours is where instability will start. Over time, log the global norm every step (it is returned by clip_grad_norm_, pt6) and the per-layer profile every few hundred steps; a rising global norm or a spike just before a loss spike is the standard early warning in large-model training.

10. NaN hunting

NaN is the bug class that appears hours in and destroys the run. NaN propagates through every arithmetic operation and, once the optimiser applies a NaN gradient, into the weights; the loss you see as NaN is usually several operations — or a step — downstream of the cause. The procedure:

  1. Make it reproducible. Log the data indices of every step and checkpoint regularly (pt8), so you can restore the state just before the failure and replay the same batches.
  2. Find the first non-finite value in time. Wrap the replayed step in torch.autograd.detect_anomaly(): it raises at the first backward function that returns NaN — on 2.14, "Function 'SqrtBackward0' returned nan values in its 0th output" — and prints the forward line that created it (pt3). For forward NaNs, register forward hooks on every module that assert torch.isfinite(output).all() and report the module name.
  3. Classify the cause. Typical sources: a fully masked attention row (softmax of all −∞ is 0/0, pt2), log of zero (a probability that underflowed — use log_softmax), division by a zero count (a masked mean over an empty mask — clamp the denominator), sqrt or norm at zero in backward (pt3), fp16 overflow (pt7), and genuinely exploding activations from a learning rate that is too high.
  4. Fix and guard. Use the stable formulation; add clip_grad_norm_(..., error_if_nonfinite=True) or a skip-step guard on non-finite gradients; alert on skipped steps.

Anomaly detection slows training heavily, so it belongs in the replay, not in the production run.

11. A catalogue of silent bugs to recognise on sight

The eight bugs in the script are the most common plants, but interviewers draw from a wider catalogue. Each of these runs without error; learn the symptom so you can name the bug quickly.

  • Inputs and labels shuffled independently — two separate shuffle calls or two DataLoaders zipped together. The model can only learn the label distribution: loss stalls at the label entropy, accuracy at the majority class. Check: decode a few examples and look at them.
  • Padding counted in the loss — labels at padded positions left as the pad token id instead of −100. The model gets rewarded for predicting padding; loss looks good, quality is poor on long sequences. Check: count positions contributing to the loss versus real tokens.
  • Augmentation applied to the input but not the label — a segmentation image flipped while its mask is not, or a crop that cuts off the box a detection label refers to. Training caps at a mediocre accuracy. Check: visualise augmented inputs with their labels, as the Recipe advises.
  • F.dropout(x, p) inside forward — the functional form defaults to training=True (pt4), so dropout stays on at evaluation. Check: two eval-mode forwards on the same input differ.
  • Teacher gradients — a distillation target computed from a teacher (or the model itself) without no_grad or detach(), so gradients flow into the teacher, which then drifts toward the student. Check: teacher parameters change after a step.
  • Train/serve preprocessing mismatch — a different tokenizer version, a missing beginning-of-sequence token, different normalisation constants or image resizing at inference. Offline metrics are fine and production quality is not. Check: run the serving path on validation examples and compare with the training-path outputs.
  • Wrong class order or label mapping — class indices built from set() iteration order, which differs between processes, or a mapping saved in one order and loaded in another. Check: assert the mapping is stored with the checkpoint (pt8).
  • Evaluation on the training transform or the training split — as in the drill below; numbers too good to be true.

Two habits catch a surprising number of these: look at actual decoded examples (text, images with their labels) straight from the batch the model receives, not from the raw dataset; and for every number the script prints, write down what value you expect before you run it.

Why leaks make the loss look better and the model worse

A model trained with access to information it will not have at inference learns to rely on it, because it is the easiest path to low loss. With unshifted labels the model learns an identity map; with a future-leaking mask it learns to read the next token from attention; with BatchNorm statistics over time it learns subtler correlations between the normalisation and future content. Training loss falls below what any honest model could achieve — for character-level Shakespeare, well below the roughly 1.47 nats per character that nanoGPT's README reports for a small correct model. At inference the information is gone, and the model's behaviour is undefined. This is why "suspiciously good" deserves more scrutiny than "disappointing": an honest bug makes things worse and gets fixed; a leak makes things better and gets shipped.

The input-independent baseline

Karpathy's Recipe recommends training once with the inputs zeroed. That baseline can only learn the output distribution's marginal (for characters, the unigram frequencies, which for English text gives a loss of roughly 3 nats per character). If the real model does not beat it clearly, the model is not using its inputs — a detached input path, a broadcasting bug that averages over the batch (like bug 7), or data and labels shuffled independently. The baseline also calibrates expectations: the gap between it and the real model is the amount of signal you are extracting.

Bugs that interact, and the order of fixing

Planted bugs mask one another. In the script above, the double softmax caps the loss at 3.2, hiding how much the leaks would otherwise lower it; fixing bug 6 first reveals bug 2 by making the loss collapse. Fixing bug 2 first while bugs 4 and 5 remain still leaves a model that can read the next character through attention, so the loss stays too low — the dependency test then finds them. A useful order is: fix whatever stops the model from learning at all (loss wiring, gradient flow), then whatever makes results too good (leaks), then whatever makes evaluation wrong (modes, split), then shape bugs in auxiliary paths. Rerun all checks after each fix; a check that passed earlier can start failing once another bug is gone.

Loss spikes in large runs: what the training loop can and cannot tell you

Large-model training logs often show sudden loss spikes that partly recover. The training-loop signals (pt6) — a gradient-norm spike just before, the learning rate at that point, whether particular batches recur — separate data-driven spikes (a corrupted or highly unusual batch; replay it) from optimisation instability (growing norms, often in attention logits or in parameters that are updated rarely, whose Adam second-moment estimates have decayed). Model-side mitigations that published large-scale runs have reported include normalising queries and keys (QK-norm), lower β₂ in Adam, a smaller learning rate, z-loss regularisation of the output softmax's normaliser, and skipping or rolling back past bad batches. In a debugging interview, saying which signal would distinguish these hypotheses is worth more than naming the mitigations.

Building the checks into the codebase

Every check in this lesson can be an automated test on a tiny configuration that runs in seconds on a CPU: loss at init within a tolerance of ln V; overfitting a fixed batch below a threshold within N steps; the dependency test in train and eval mode; label alignment (y[:, :-1] == x[:, 1:]); disjoint train and validation indices; eval determinism; and a save/resume equivalence test (pt8). Teams that keep these in continuous integration catch most of this lesson's bugs at review time, when they cost minutes, instead of after a multi-day run.

How these bugs appear in real projects

Outside interviews, bugs arrive one at a time and without markers, usually as "the new model is a bit worse than the old one" or "we cannot reproduce the paper". The most expensive ones in practice are leaks (they inflate offline metrics and are discovered only in production or by an external evaluation), mode bugs in evaluation (they make comparisons between checkpoints unreliable for weeks), and silent loss-scaling or accumulation bugs (pt6, pt7) that degrade every run a little. Kapoor and Narayanan's survey of leakage across 17 scientific fields catalogues how often the first category affects published work — overlapping samples, duplicates, and preprocessing fitted on the whole dataset are among the recurring types.

Signals to log so that debugging is possible at all

A run that logged only the training loss is almost impossible to debug after the fact. Log, at minimum: training loss (smoothed) and its value at step 0; validation loss in eval mode on a fixed set; learning rate; global gradient norm and the number of clipped or skipped steps; throughput; the data indices or shard offsets of each step; and every few hundred steps a per-layer gradient-norm profile and a few sampled generations or predictions. Store the config and code version with the run. Then, when something goes wrong at step 40,000, you can restore, replay and bisect.

Talking through it in the interview

Interviewers grade the process as much as the findings. State each hypothesis and its check before running it ("if the labels were not shifted, overfitting one batch would be suspiciously fast — let me check"); when you find a bug, give its symptom, root cause and minimal fix in one breath; prefer minimal fixes over rewrites; rerun the checks after each fix; and keep a running list of what you have verified, so that when time runs out you can say what remains unchecked. If you cannot run code, do the same on paper with small distinct sizes, tracing shapes and dtypes line by line.

From one bug to a team habit

After a bug like these costs a team a week, the useful response is not only the fix but a check that would have caught it. Add the failing check to the test suite on a tiny configuration; add the signal that would have shown it to the training dashboard (a per-example metric for a broadcasting bug, train-versus-eval loss on the same batch for a mode bug, an overlap count for a split bug); and write the symptom down in a short internal catalogue, so the next person who sees "loss collapses to zero in 300 steps" recognises it in minutes. Over time that catalogue becomes the team's version of this lesson — and the interview round is, in effect, testing whether you would bring one with you.

Find the bug: an image classifier with five planted bugs

A ResNet-style CIFAR-10 classifier trains with this loop. Training accuracy reaches 99%, reported validation accuracy is 97% (published small ResNets reach about 93–95%), and the deployed model performs at about 70% on new photos. Find the bugs, with symptom, root cause and fix.

full = CIFAR10Dataset(root, transform=train_tf)               # random crop + flip
mean, std = full.data.mean(0), full.data.std(0)                # per-pixel stats, all 60k images
full.normalise(mean, std)
train, val = random_split(full, [55000, 5000])
loader = DataLoader(train, batch_size=4, shuffle=True)
for epoch in range(30):
    for x, y in loader:
        out = model(x)
        loss = F.nll_loss(out, y)                              # model ends with nn.Linear
        opt.zero_grad(); loss.backward(); opt.step()
    acc = evaluate(model, val)                                 # val uses train_tf, model in train mode
Answer

Bug 1 — the test images are in the split. CIFAR-10 has 50,000 training and 10,000 test images; a dataset built from all 60,000 and split at random puts test images into training and leaves no untouched test set. Symptom: the 97% "validation" accuracy, above published numbers. Fix: use the official training set for train/validation and keep the test set untouched.

Bug 2 — normalisation statistics computed on all the data. Mean and standard deviation from all 60,000 images (including validation and test) leak a little information and, more importantly here, per-pixel statistics normalise away image structure and do not match deployment. Fix: compute per-channel statistics on the training split only and apply the same fixed transform everywhere.

Bug 3 — nll_loss on raw logits. F.nll_loss expects log-probabilities; given raw logits it computes minus the target's logit, which can be driven to −∞ by inflating logits. Training "accuracy" can still rise, but the loss is meaningless and calibration is broken. Fix: F.cross_entropy(out, y), or F.nll_loss(F.log_softmax(out, 1), y).

Bug 4 — batch size 4 with BatchNorm. BatchNorm statistics from 4 images are noisy, and running statistics converge to values that do not match evaluation (pt4). Symptom: a large gap between train-mode and eval-mode accuracy once evaluation is fixed. Fix: batch 64–256, or GroupNorm if memory forces tiny batches.

Bug 5 — evaluation in training mode with training augmentation. The model is not put in eval mode (BatchNorm uses validation batch statistics and updates the running ones) and validation images get random crops and flips. Fix: a validation transform without augmentation and the evaluate() pattern with model.eval() and inference_mode. The 70% on new photos is the honest number once all five are fixed and the test set is held out — plus whatever domain shift exists between CIFAR images and real photos.

Diagnose: NaN at step 31,207

A transformer with padding masks trains for 31,206 steps and then the loss is NaN. Gradient norms in the preceding thousand steps are flat. What do you suspect, and how do you confirm it quickly?

Answer

Flat gradient norms argue against gradual instability and for a data-triggered failure in one batch: most likely a sequence that is entirely padding (or a query row with every key masked), whose attention softmax is 0/0, or a masked mean over an empty mask. Confirm by restoring the last checkpoint before 31,207, replaying the logged batch indices up to that step, and running the failing step under detect_anomaly with forward finiteness hooks: the first NaN will appear in the softmax of the attention layer (or the division in the masked mean), and inspecting the batch will show the empty sequence. Fix by filtering empty examples in the data pipeline, letting every query attend to at least itself, and clamping mask counts with .clamp(min=1); add a non-finite skip guard so one bad batch cannot destroy the run again.
