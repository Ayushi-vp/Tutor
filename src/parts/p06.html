How BPE builds a vocabulary

Start from bytes. Count adjacent pairs across the corpus, merge the most frequent pair into a new token, repeat until the vocabulary reaches its target (32k–256k). Frequent words become single tokens; rare words decompose into pieces; anything unseen still encodes because the base alphabet is all 256 bytes, so there is no out-of-vocabulary case. Variants: WordPiece (BERT) merges by likelihood gain rather than raw frequency; SentencePiece/Unigram starts large and prunes, and treats the input as a raw byte stream so it needs no pre-tokeniser — important for languages without spaces.

Consequences you will be asked about

  • Counting and spelling fail because the model never sees characters — "strawberry" may be three tokens, so counting its r's is a task about token internals the model has no access to.
  • Arithmetic is fragile: number splitting is inconsistent, so 1234 and 1235 may tokenise into different shapes. Modern tokenisers split digits into fixed groups to reduce this.
  • Non-English costs more. The same sentence in Hindi or Thai can take 2–4× the tokens of English, which is both a latency and a billing issue for a global product.
  • Rule of thumb: English is roughly 4 characters or 0.75 words per token. Code is denser in tokens per character because of punctuation and indentation.
  • Glitch tokens — rare vocabulary entries that appeared in the tokeniser corpus but barely in training — produce bizarre behaviour when prompted.

The computation

Project each token's embedding three ways: Q = XW_q (what am I looking for), K = XW_k (what do I offer), V = XW_v (what do I pass on). Then Attention(Q,K,V) = softmax(QKᵀ / √d_k) · V. The QKᵀ product is an n×n matrix of similarity scores; softmax turns each row into weights summing to 1; multiplying by V gives each position a weighted blend of every other position's value.

Why divide by √d_k

If q and k have independent unit-variance components, their dot product has variance d_k. Without scaling, at d_k = 128 the logits reach ±11 or more, softmax saturates to a one-hot, and the gradient through it vanishes. Dividing by √d_k restores unit variance and keeps the softmax in its responsive range. This is a favourite question because it has an exact answer.

Multi-head, and the masks

Split d_model into h heads of size d_model/h, attend independently, concatenate, project. Different heads specialise — syntactic dependencies, coreference, positional offsets, induction heads that copy earlier patterns. The parameter count is unchanged; what you buy is several representation subspaces instead of one averaged one.

A causal mask sets the upper triangle of the score matrix to −∞ before softmax, so position t can only see ≤ t. That single mask is the difference between BERT-style bidirectional encoding and GPT-style generation. A padding mask does the same for padded positions in a batch.

Complexity

O(n²·d) time and O(n²) memory in the naive form — the reason long context is hard. FlashAttention does not change the asymptotics; it tiles the computation so the n×n matrix is never written to HBM, turning a memory-bound kernel into a compute-bound one and giving a 2–4× speedup with exact results.

One decoder block

Pre-norm residual structure, twice:

# x: (batch, seq, d_model)
x = x + Attention(RMSNorm(x))      # mix across positions
x = x + FFN(RMSNorm(x))            # mix across features

That alternation is the whole idea: attention is the only operation that moves information between positions; the feed-forward network processes each position independently. Everything else — normalisation, residuals — exists to make the stack trainable.

Per layer, attention holds 4·d² (Q, K, V, O projections) and the FFN holds 2·d·d_ff with d_ff = 4d — so 8d². Roughly two thirds of a transformer's parameters are in the feed-forward layers, which is why MoE replaces the FFN rather than attention, and why FFN quantisation buys the most memory.   • Decoder-only (GPT, LLaMA, Claude): causal, next-token pretraining. Generation, and in practice everything else too.
  • Encoder–decoder (T5, BART): cross-attention from decoder to encoder. Translation and summarisation, though decoder-only models have largely absorbed these.

Why it is needed

Self-attention is a weighted sum over a set. Shuffle the tokens and the output is shuffled identically — the mechanism has no notion of order. Position must be added explicitly.

The four approaches

  • Sinusoidal (original transformer) — fixed sin/cos at geometrically spaced frequencies, added to the embedding. Deterministic, extrapolates in principle, weak in practice.
  • Learned absolute (BERT, GPT-2) — a trainable vector per position. Simple, but hard-capped at the trained length.

What the cache is

During generation each new token attends to all previous tokens. Their keys and values do not change, so recomputing them every step would be quadratic waste. The KV cache stores them, turning each decode step into O(n) instead of O(n²). The price is memory:

bytes = 2 (K and V) × layers × kv_heads × head_dim × seq_len × batch × dtype_bytes

For a 70B-class model with 80 layers, 64 heads, head dim 128, in fp16, at 8k context: about 40 GB per sequence. That number is why the next two ideas exist.

MQA and GQA

Multi-Query Attention keeps many query heads but a single shared K/V head — cache shrinks by the head count, at some quality cost. Grouped-Query Attention is the compromise now used almost everywhere (LLaMA-2 70B, Mistral): 8 KV heads shared across 64 query heads, giving an 8× cache reduction with quality indistinguishable from full MHA. If asked how to make inference cheaper, GQA is the architectural answer and PagedAttention is the systems answer.

Serving consequences

  • Decoding is memory-bandwidth bound, not compute bound — you read the whole weight matrix to produce one token. This is why batching helps so much: the weights are read once for the whole batch.
  • PagedAttention (vLLM) stores the cache in fixed-size blocks like OS virtual memory, eliminating fragmentation and allowing prefix sharing between requests with a common system prompt.
  • Prefill (processing the prompt) is compute-bound and parallel; decode is sequential and bandwidth-bound. They have different bottlenecks, which is why some stacks disaggregate them onto different hardware.

The empirical law

Test loss falls as a power law in model size, dataset size and compute: L(C) ≈ L_∞ + (C_c/C)^α. The lines are straight on a log–log plot over many orders of magnitude, which is what makes them useful — you can fit on small runs and extrapolate the big one before committing the budget.

Kaplan vs Chinchilla

The 2020 Kaplan work suggested pouring most extra compute into parameters. The 2022 Chinchilla work re-ran the sweep with properly tuned learning-rate schedules and found the compute-optimal ratio is roughly 20 tokens per parameter. A 70B model should see about 1.4T tokens. By that standard GPT-3 (175B, 300T tokens) was substantially undertrained: Chinchilla at 70B beat it while being 2.5× smaller.

The inference-aware correction

Compute-optimal is only optimal for training. If a model serves billions of requests, it is rational to overtrain a smaller model far past 20:1 — LLaMA-3 8B saw 15T tokens, roughly 1,800 tokens per parameter — because every inference is cheaper forever. When asked "how big should our model be", the expected answer weighs training FLOPs against lifetime serving FLOPs.

Useful arithmetic to have memorised: training FLOPs ≈ 6ND (N parameters, D tokens); a forward pass is ≈ 2N FLOPs per token.

The knobs

  • Greedy — always take the argmax. Deterministic, repetitive, often degenerate for long text.
  • Temperature T divides the logits before softmax. T < 1 sharpens toward greedy; T > 1 flattens toward uniform; T → 0 is greedy exactly.
  • Top-k keeps the k highest-probability tokens and renormalises. Fixed budget, but a bad fit when the distribution is very peaked (wastes) or very flat (truncates).
  • Top-p (nucleus) keeps the smallest set whose cumulative probability exceeds p. Adaptive: narrow where the model is confident, wide where it is not. The usual default at p ≈ 0.9–0.95.
  • Min-p keeps tokens above a fraction of the top token's probability — more robust than top-p at high temperature.
  • Repetition / frequency / presence penalties subtract from logits of tokens already generated.
  • Beam search keeps b partial hypotheses by cumulative log-probability. Good for translation and other tasks with one right answer; it makes open-ended text bland, because the highest-probability continuation is usually the most generic one.

Why RAG instead of fine-tuning

Fine-tuning teaches behaviour and form; retrieval supplies facts. If the knowledge changes weekly, must be cited, must respect per-user permissions, or is too large to memorise, you retrieve. The pipeline

  5. Generate — a prompt that instructs the model to answer only from context, cite chunk ids, and say "not in the provided documents" when it is not.

  • Lost in the middle — models attend most to the start and end of a long context; put the best chunk first.
  • Stale index — no re-embedding on document change, or worse, an embedding-model upgrade without a full re-index.

What an embedding is

A learned map from text to a dense vector where semantic similarity becomes geometric proximity. Trained contrastively: pull (query, relevant passage) pairs together, push unrelated pairs apart, with in-batch negatives — so batch size matters enormously for embedding quality. The intuition behind LoRA

Fine-tuning updates a weight matrix by ΔW. Empirically, that update has low intrinsic rank — the model is adapting along a handful of directions, not all d² of them. LoRA freezes W and learns ΔW = BA where A is r×d and B is d×r, with r typically 8–64. For d = 4096, r = 16 that is 131k parameters instead of 16.8M — a 128× reduction per matrix.

What it buys

  • Optimiser states shrink with the trainable parameters, which is the real memory win (Adam keeps two fp32 moments per trainable parameter).
  • Adapters are a few dozen MB, so one base model can serve many tenants with hot-swapped adapters.
  • The base model is untouched, so catastrophic forgetting is bounded.
  • At inference, BA can be merged into W — zero added latency.

QLoRA

Quantise the frozen base to 4-bit NF4, keep LoRA adapters in bf16, and add paged optimiser states plus double quantisation. A 65B model fine-tunes on a single 48 GB GPU at essentially full-fine-tune quality. Practical settings: target the attention projections and (if budget allows) the FFN, r = 16–64, alpha = 2r, dropout 0.05, learning rate around 1e-4 — an order of magnitude higher than full fine-tuning because far fewer parameters move.

Decide before you tunePrompting → few-shot → RAG → LoRA → full fine-tune, in that order of cost. Reach for fine-tuning when you need a consistent format, a domain vocabulary, a latency win from a smaller model, or behaviour that no prompt reliably produces. Not for teaching facts — that is retrieval's job.

The arithmetic to have ready

Weights alone: params × bytes_per_param. A 7B model is 28 GB in fp32, 14 GB in fp16/bf16, 7 GB in int8, 3.5 GB in int4. Then add KV cache and activations, and multiply by a safety factor. Being able to do this instantly is a standard filter question.

Two phases, two bottlenecks

Prefill processes the whole prompt in parallel — compute-bound, and it sets time-to-first-token. Decode emits one token at a time — memory-bandwidth bound, and it sets tokens-per-second. Optimising the wrong phase is the classic mistake; measure TTFT and inter-token latency separately.

Agent loops multiply calls_per_request and are where budgets quietly die — a 12-step agent at 4k context per step is 48k input tokens for one user action.

Levers, highest impact first

  1. Route by difficulty. Sending the easy majority to a small model routinely cuts spend by 60–80%.
  2. Cache. Exact-match plus semantic caching typically removes 20–40% of traffic in products with repetitive questions; provider prefix caching cuts the input cost of long system prompts by most of their value.
  3. Shrink the context. Rerank to 5 chunks instead of stuffing 20. Better answers and cheaper — the rare case where the two align.
  4. Cap output. Set max_tokens deliberately and ask for concise formats.
  5. Batch anything asynchronous — batch endpoints are typically half price.
  6. Self-host only above the crossover point. A GPU at roughly £2/hour is about £1,400/month; below steady high utilisation, an API is cheaper and far less work.

Four layers of monitoring

  1. System — latency percentiles, error rate, throughput, GPU utilisation, queue depth. Table stakes.
  2. Data — input distribution shifts (PSI or KL against the training snapshot), null rates, new categorical levels, schema violations. This catches most incidents first because labels have not arrived yet.
  3. Model — prediction distribution, confidence distribution, and once labels land, the real metric. Delayed labels are the norm; track the delay explicitly.
  4. Business — the metric the model exists to move. If it diverges from the model metric, the model metric is wrong.

Drift, named properly

Covariate shift: P(X) changes, P(Y|X) does not — often recoverable by reweighting. Concept drift: P(Y|X) itself changes — fraud tactics, user behaviour after a UI change — and only new labels fix it. Label shift: the class prior moves, which recalibration can handle. Naming which one you are facing is the diagnostic.

Closing the loop

Retrain on a schedule and on a trigger (drift beyond a threshold, or metric degradation). Keep a champion/challenger setup with shadow scoring, and always keep a rollback path — a model registry with versioned artefacts, the exact training data snapshot, and the feature transformations that went with it. For LLM products the equivalent is a versioned prompt plus eval-set scores per version, and traffic-sampled human review feeding a growing regression set.

Techniques, strongest first

  • Constrained decoding — a grammar or JSON-schema mask over the logits so invalid tokens cannot be sampled. Validity becomes a guarantee rather than a hope. Available as structured outputs / tool schemas on major APIs and via Outlines or XGrammar when self-hosting.

  • Schema in the prompt + few-shot — the fallback when neither is available. Show the exact shape, including an example of the empty/unknown case.
  • Repair pass — on a parse failure, send the error back with the malformed output and ask for a correction. One retry fixes most of it; cap at two.

Design details that matter

  • Keep schemas flat and shallow. Deep nesting and long enums degrade accuracy noticeably.
  • Give every optional field an explicit null/unknown value so the model has a legal way to express absence instead of inventing one.
  • Validate semantics after syntax: schema-valid JSON can still carry a product id that does not exist. Check against your own data.
  • Log every failure with the prompt version — a rising parse-failure rate is usually the first sign a model or prompt change broke something.

Data handling

  • Redact before the model sees it where the task allows — named-entity detection plus deterministic pseudonymisation, so you can re-insert real values in the response.
  • Data residency and retention — know whether your provider trains on your data, where it is processed, and how long logs live. Contractual, not technical, but you are expected to raise it.
  • Permission-aware retrieval — filter the index by the requesting user's ACL at query time. A shared vector store with no permission filter is a data breach waiting for its first curious employee.
  • Right to erasure — deleting a source document must remove its chunks and its embeddings; plan this before you need it.

Fairness and transparency

Measure per-slice performance (by protected attribute where it is lawful to hold one, by proxy segment otherwise) — an aggregate metric hides a group the model fails. Decide which fairness definition applies: demographic parity, equal opportunity and calibration are mutually incompatible in general, so the choice is a product decision to be documented, not a technical one to be optimised. Keep a model card: intended use, training data provenance, known limitations, evaluation results per slice.

For generative products, add: disclosure that output is AI-generated, a reporting path for harmful output, and a human escalation route for any decision with legal or material effect on a person.
