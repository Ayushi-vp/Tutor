Training a 32-layer transformer: batch 8, sequence 2,048, d_model 4,096, bf16. One tensor of shape (batch, seq, d_model) is 134 MB. A block caches roughly ten such tensors for its backward pass. Estimate activation memory, then what gradient checkpointing at block boundaries costs and saves.

Answer

One tensor: 8 × 2048 × 4096 × 2 bytes = 134 MB.

Without checkpointing: ~10 cached tensors per block × 32 blocks = ≈ 43 GB of activations alone — before weights, gradients or optimiser state. This is why activation memory, not parameter count, is usually what OOMs you.

With checkpointing at block boundaries: store only each block's input — 32 × 134 MB = 4.3 GB, a 10× reduction. During backward, each block's internals are recomputed from its stored input, costing one extra forward pass overall: about +33% compute.

The follow-up to volunteer: activation memory scales with batch × sequence, while weights, gradients and optimiser states do not. So halving the batch when you OOM only halves one of four terms — if the fixed terms already exceed your VRAM, no batch size will fit and you need sharding, offload or LoRA instead.

How a ReLU dies: its derivative is exactly 0 for z < 0. If a large gradient step pushes the bias so negative that the unit outputs 0 for every input in the data, then every future gradient through it is also 0 — including the gradient with respect to its own bias. A 50-layer network where each layer's Jacobian has typical singular value s. Compute the gradient scale reaching layer 1 for s = 0.8 and s = 1.2. Then say what a residual connection changes.

Answer

The gradient at layer 1 is a product of 49 Jacobians, so it scales as s⁴⁹.

s = 0.8: 0.8⁴⁹ = 1.8 × 10⁻⁵. Early layers receive a gradient ~55,000× smaller than late ones — with a shared learning rate they effectively never train.

s = 1.2: 1.2⁴⁹ = 7.5 × 10³. The gradient explodes; in fp16 this overflows to NaN within a few steps.

Note how narrow the survivable band is: a 20% deviation from 1.0 in either direction is fatal at 50 layers. Depth turns a small multiplicative bias into an exponential one.

What residuals change: with x + f(x), each layer's Jacobian becomes I + J_f. The identity term guarantees a path where the product stays order 1 no matter how small J_f is — the gradient can always flow straight to the input. This is why 100+ layer networks became trainable at all, and it is the single highest-value thing to say on this topic.

Gradient clipping does not help here. It caps explosion; it does nothing for vanishing. Different problem, different fix.

A BatchNorm layer sees activations [2, 4, 6, 8] across a batch of 4, with γ = 1, β = 0. Compute the output. Then say what happens at batch size 1 in training mode, and in evaluation mode.

Answer

Mean = 5, variance = ((−3)² + (−1)² + 1² + 3²)/4 = 5, so σ = 2.236.

Output = (x − 5)/2.236 → [−1.342, −0.447, 0.447, 1.342]. Zero mean, unit variance, then scaled by γ and shifted by β.

Batch size 1, training mode: the batch mean is the single value, so x − μ = 0 and the variance is 0. Output is 0/√ε = 0, then γ·0 + β = β. Every input produces the same output — the layer has destroyed all information.

Batch size 1, evaluation mode: perfectly fine. BN uses the running mean and variance accumulated during training, so the computation no longer depends on the batch at all.

Why transformers use LayerNorm instead: LN normalises across features within each example, so it is batch-independent, behaves identically in train and eval, and works with variable-length padded sequences — where a batch statistic would be computed over padding tokens. RMSNorm goes further and drops the mean-centring entirely, keeping only the scale division: nearly identical quality, measurably cheaper.

A layer has 100 units all outputting 1.0, with dropout p = 0.5. Compute the expected output sum during training (with inverted dropout) and at evaluation. Then say what breaks if you forget model.eval().

Answer

Training, inverted dropout: each unit survives with probability 0.5, and survivors are scaled by 1/(1−p) = 2. Expected sum = 100 × 0.5 × 1.0 × 2 = 100.

Evaluation: dropout is off, no scaling. Sum = 100 × 1.0 = 100.

They match by construction — that is the entire point of scaling during training rather than at test time, so inference needs no special handling.

Forgetting model.eval(): two things break at once, and the second is worse.

  • Dropout stays on, so predictions become stochastic — the same input gives different answers, and the expected value is right but the variance is large.
  • BatchNorm keeps updating its running statistics from your validation batches, and normalises using batch statistics rather than the running ones. Your validation data is now silently influencing the model, and the corruption persists into later training.

The symptom is validation metrics that are noisy and slightly worse than they should be, which is easy to misread as a regularisation problem. Pair it with torch.no_grad(), which is a separate concern — memory, not correctness.

Pipeline parallelism across 4 stages with 8 micro-batches. Compute the bubble fraction, then for 32 micro-batches. Finally, sketch a parallelism plan for a 70B model on 64 A100-80GB.

Answer

Bubble fraction = (stages − 1) / (micro-batches + stages − 1).

  • 8 micro-batches: 3/11 = 27% of GPU time idle while the pipeline fills and drains.
  • 32 micro-batches: 3/35 = 8.6%.

More micro-batches shrink the bubble, but each is smaller, so per-kernel efficiency drops and activation memory for in-flight micro-batches rises. Interleaved (virtual-stage) schedules cut it further at the cost of more communication.

70B on 64 GPUs — 3D parallelism. Weights alone in bf16 are 140 GB, so it cannot fit on one card.

  • Tensor parallel = 8, within each node. Splits individual matrices; needs an all-reduce per block, so it must stay on NVLink and never cross the network.
  • Pipeline parallel = 4, across node groups. Only activations cross stage boundaries, so it tolerates slower interconnect. Use enough micro-batches to keep the bubble under ~10%.
  • Data parallel = 2 (64 ÷ 8 ÷ 4), with ZeRO stage 1 sharding optimiser states across the replicas.
  • Plus: bf16 with fp32 master weights, gradient checkpointing, global batch in the low millions of tokens, warmup then cosine decay.

Finish with operations, because it is what distinguishes a real answer: at 64 GPUs something fails weekly, so checkpoint every ~30 minutes to fast storage, make the job resumable, and monitor loss spikes with an automatic rollback to the last good checkpoint.
