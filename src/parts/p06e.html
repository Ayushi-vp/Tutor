A request passes through gateway → retrieval → reranker → LLM → post-processing. Each component is independently 99.9% available. What is the end-to-end availability, and what would each need to be for a 99.9% overall SLO?

Answer

Serial dependencies multiply: 0.999⁵ = 0.99501 — 99.50%, which is 3.6 hours of downtime a month, not the 43 minutes each component's own SLO suggests.

For 99.9% overall, each needs 0.999^(1/5) = 0.99980 — 99.98% each, a 5× tighter budget per component. Chains are expensive.

The way out is to break the multiplication, not to chase four nines everywhere:

  • Make components optional. If the reranker times out, serve the un-reranked top-5 — slightly worse answers, not an error. It drops out of the availability product entirely.
  • Fall back. Two independent LLM providers at 99.9% each give 1 − 0.001² = 99.9999% for that link, if the failures really are independent.
  • Cache. A semantic cache answering 30% of traffic means 30% of requests never touch the fragile path.

The latency version of the same trap: p95 latencies do not add. If each stage is independently p95 = 200 ms, the chain's p95 is well above 1 s, because a request only needs one slow stage to be slow. Budget with tail latencies and measure the chain end to end, never by summing component medians.

PSI = Σ (live − train) × ln(live / train), over buckets:

  • (0.10 − 0.25) × ln(0.40) = −0.15 × −0.916 = 0.137
  • (0.20 − 0.25) × ln(0.80) = −0.05 × −0.223 = 0.011

Why input monitoring earns its place: it fires before any label arrives. If your labels lag 30 days, a drift alert is the only signal you will get for a month.

A schema-in-the-prompt approach parses successfully 99.2% of the time. You add one repair retry that fixes 80% of failures. At 500,000 requests a day, how many still fail? Then compare with constrained decoding.

Answer

Failure rate after the retry: 0.008 × 0.20 = 0.0016 — 0.16%, which is 800 failed requests every day. Written as a percentage that looks like a rounding error; written as a daily count it is a support queue.

A second retry takes it to 0.032% (160/day) but adds latency and cost to the tail, and the third attempt tends to fail for the same structural reason as the first — retries are not independent when the prompt itself is the problem.

Constrained decoding is categorically different. A grammar or JSON-schema mask over the logits makes invalid tokens unsamplable, so syntactic validity goes to 100% by construction — not 99.998%. There is no failure rate to multiply, because the failure mode has been removed rather than made rare.

What it does not give you. Schema-valid output can still be semantically wrong: a correctly-typed product_id that does not exist, a date in the right format but the wrong year, an enum value that is legal but inappropriate. So validate in two stages — syntax by construction, semantics against your own data — and log failures with the prompt version, because a rising parse or validation rate is usually the first sign a model or prompt change broke something.

Design note: keep schemas flat and shallow, and give every optional field an explicit null or unknown value. Deep nesting and long enums measurably degrade accuracy, and without a legal way to express absence the model will invent one.

(a) 0.90 × 0.96 + 0.10 × 0.76 = 0.864 + 0.076 = 0.940. The aggregate is dominated by the majority group, so a 20-point gap is invisible in the headline number.

  • Source documents and their parsed copies
  • Every chunk derived from them, and every embedding vector in the index — note that ANN graph structures like HNSW do not delete cheaply, so plan tombstones plus periodic rebuild
