Start here — what "serving a model" actually means

Training is done once. Serving is the part that runs forever: a user sends text, a GPU turns it into more text, and you are billed for every second the GPU is awake. Almost every decision in this design exists because GPUs are expensive and generation is slow.

A single request runs in two phases, and confusing them is the most common beginner mistake:

${flow([{t:"Prefill",d:"read the whole prompt at once"},{t:"Decode",d:"emit one token, then the next…"}])}
  • Prefill processes every prompt token in parallel. It is compute-bound — the GPU's maths units are the bottleneck. A 2,000-token prompt costs roughly one big matrix multiply and finishes in tens of milliseconds.
  • Decode produces the answer one token at a time, and each token must wait for the previous one. It is memory-bandwidth-bound — the GPU spends its time reading the model's weights out of memory, not doing arithmetic. This is why a 500-token answer takes seconds while a 2,000-token prompt takes milliseconds.

The vocabulary you will be expected to use

  • KV cache — when the model reads token 50, it needs what it computed for tokens 1–49. Rather than recompute them, it keeps those intermediate vectors (the "keys" and "values") in GPU memory. The cache grows with every token generated, and it is the real constraint on how many users fit on one GPU. Weights are a fixed cost; KV cache is the variable cost per active conversation.
  • TTFT (time to first token) — how long before the user sees anything. Dominated by queueing plus prefill. This is the number users perceive as "is it broken?".
  • TPOT / ITL (time per output token, inter-token latency) — how fast text streams once started. Above roughly 20 tokens/s it reads faster than most people, so there is no benefit to going faster.
  • Throughput — total tokens per second across all users. This is what you are billed on, and it trades directly against per-user latency.
  • Multi-tenant — many separate customers share one pool of hardware. Cheaper than a pool each, but now one customer's traffic can hurt another's, which is the "noisy neighbour" problem the design has to solve.

The one mental model to keep

A GPU is a bus, not a taxi. Running one passenger costs almost the same as running twenty, because the expensive part — hauling the model weights from memory for every single token — is shared across everyone on board. Batching is therefore not an optimisation, it is the entire business model. Every serving design you will ever read is fundamentally about keeping the bus full without making any individual passenger's journey unacceptably slow.

The senior layer — what a staff-level answer adds

  • Prove the bottleneck with arithmetic intensity, do not assert it. During decode with batch size 1, the GPU reads every weight to produce one token: for a 13B fp16 model that is 26 GB of memory traffic for roughly 26 GFLOPs of work — a ratio of about 1 FLOP per byte. An A100 wants 100+ FLOPs per byte to stay busy, so it runs at a few percent of peak. Batching 32 requests reuses one weight read across 32 tokens and lifts that ratio by 32×. Saying this out loud tells the interviewer you understand why batching works, not just that it does.
  • Chunked prefill. A naive scheduler that admits a 30k-token prompt stalls every in-flight stream while it prefills — users mid-answer see their text freeze. Split the prefill into fixed-size chunks and interleave them with decode steps. This is the single highest-impact fix for tail latency in a mixed-traffic pool, and most candidates have never heard of it.
  • Prefill/decode disaggregation. The two phases want opposite hardware: prefill wants raw FLOPs, decode wants memory bandwidth and lots of it. Running them on separate pools lets you size and scale each independently and stops a prefill burst from destroying decode latency. The cost is shipping the KV cache across the network between pools, so it only pays above a certain scale — name that trade-off rather than presenting disaggregation as strictly better.
  • Speculative decoding. A small draft model proposes k tokens; the big model verifies all k in a single forward pass and accepts the longest correct prefix. Output is mathematically identical to the big model alone — this is not an approximation, and saying so is the point. Typical acceptance rates give 2–3× on latency. The catch: it burns extra compute per token, so it helps at low batch sizes (latency-bound) and can actively hurt at high batch sizes (throughput-bound). A good answer makes it a per-tier decision.
  • Prefix caching is a multi-tenant feature, not just a speed-up. If tenants share a system prompt, radix-tree prefix sharing means you prefill it once for everyone. But it also creates a cross-tenant timing side channel: cache-hit latency reveals that someone else recently sent the same prefix. In a regulated environment you may have to partition the cache by tenant and give up the saving. Volunteering this security angle is a strong senior signal.
  • Quotas belong on tokens and GPU-seconds, never on requests. A request-per-minute limit is meaningless when one request can be 100k tokens and another 20. Bill and throttle on the resource you actually sell.

What breaks in production that nobody designs for

KV cache exhaustion under a burst of long contexts causes preemption — the scheduler evicts a running sequence and must later recompute its cache from scratch, so a 2× traffic spike can produce a 10× latency spike. Mitigate with admission control that reserves cache for the sequence's maximum length, not its current one. Separately, a wedged CUDA context passes every TCP and HTTP health check while producing nothing; your readiness probe must actually generate a token. And on autoscaling: loading a 13B model from object storage takes minutes, so scale-out is far slower than traffic arrives — keep a warm standby pool and treat the autoscaler as a cost-recovery mechanism, not a latency defence.

Start here — what RAG is, and what it is not

A language model knows only what was in its training data, and it will confidently invent an answer when it does not know. Retrieval-augmented generation fixes this by looking things up first: find the handful of documents most likely to contain the answer, paste them into the prompt, and ask the model to answer using those documents.

${flow([{t:"Question",d:"user asks"},{t:"Retrieve",d:"find ~5 relevant chunks"},{t:"Augment",d:"paste into prompt"},{t:"Generate",d:"answer + citations"}])}

That is the whole idea. Everything hard about it lives in the word "relevant".

The vocabulary

  • Chunk — documents are too long to search or paste whole, so they are split into passages of a few hundred words. A chunk is the unit of retrieval. Chunking badly is the most common reason a RAG system gives poor answers, and it happens weeks before anyone notices.
  • Embedding — a model converts a chunk into a list of numbers (a vector, typically 768–1536 of them) positioned so that similar meaning lands in a similar place. "How do I reset my password?" and "I forgot my login" end up near each other even though they share no words.
  • Vector search / ANN — finding the nearest vectors to the question's vector. Comparing against all 500 million chunks exactly is too slow, so an approximate nearest neighbour index (usually HNSW) trades a small amount of accuracy for a thousandfold speed-up.
  • BM25 — classic keyword search, still unbeaten at exact matches: error codes, product SKUs, surnames, NullPointerException. Embeddings are bad at these because rare exact strings carry little semantic signal.
  • Reranking — a slower, more accurate model re-scores the top ~50 candidates to pick the best 5. It reads question and chunk together (a "cross-encoder"), which is far more accurate than comparing two independently-made vectors, but far too slow to run over the whole corpus. Retrieve wide and cheap, then rerank narrow and expensive.
  • ACL — access control list: who is allowed to see this document. In an enterprise this is not a feature, it is the constraint that dictates the architecture.

The mental model

RAG is a library, not a brain. The model is a fast, articulate researcher who has never read your documents and cannot remember anything between questions. Retrieval is the librarian who fetches the right five pages. If the librarian brings the wrong pages, no amount of prompt engineering saves the answer — which is why senior candidates spend their time on retrieval quality and juniors spend theirs on prompts.

The senior layer

  • Measure the two halves separately or you will debug blind. A wrong answer has exactly two causes: the right chunk was never retrieved, or it was retrieved and the model ignored or misread it. These need completely different fixes. Track retrieval recall@k (was the answer-bearing chunk in the context at all?) and faithfulness (did the answer follow from the context?) as separate numbers. Teams that track only end-to-end answer quality rewrite prompts for weeks to fix a chunking bug.
  • The context window is not the goal. Models degrade on long contexts — accuracy on facts placed in the middle of a long context drops measurably versus the same fact at either end ("lost in the middle"). Stuffing 50 chunks in because the window allows it usually scores worse than 5 well-ranked ones, while costing ten times as much. Retrieval quality beats retrieval quantity.
  • Contextual chunk augmentation. A chunk reading "Revenue grew 3% this quarter" is unretrievable — it names neither the company nor the quarter. Prepend a one-sentence, LLM-generated description of where the chunk sits in its parent document before embedding it. This is a one-time ingestion cost that reduces retrieval failures substantially, and it is currently the highest-leverage cheap trick in the field.
  • Permissions must be a pre-filter inside the ANN search, not a post-filter. Post-filtering retrieves the top 50 then drops what the user cannot see, which returns near-empty results for restricted users and, worse, leaks the existence of documents through result counts and latency. Pre-filtering means the graph traversal itself only visits permitted nodes. The engineering consequence is real: filtered HNSW degrades badly when the filter is very selective — if a user can see 0.1% of the corpus, graph traversal can fail to find any valid neighbours and you must fall back to brute force over that user's partition. Knowing this failure mode is the difference between a textbook answer and an experienced one.
  • Deletion and permission revocation are the operational nightmare. A document removed from SharePoint must vanish from the index, the reranker cache, any cached answers, and the logs — within minutes, not at the next reindex. Design the delete path explicitly and say that you have; most candidates design only the write path.
  • Know when RAG is the wrong answer. If questions require aggregating across thousands of documents ("how many contracts renew this quarter?"), retrieval of five chunks cannot work — that is a text-to-SQL or structured-extraction problem. If the corpus is small and stable, long-context prompting with prompt caching may be simpler and better. Naming the boundary of your own approach is a strong signal.

The evaluation set is the deliverable

Before writing any pipeline code, collect 200–300 real questions from real users with the documents that actually answer them. Without this you cannot tell whether a change helped, and every subsequent decision — chunk size, hybrid weighting, reranker choice, top-k — becomes an argument about taste instead of a measurement. Say this early in the interview; it reframes you from "engineer who builds pipelines" to "engineer who ships systems that work".

Start here — why recommenders are built in two stages

You have ten million items and 50 milliseconds. You cannot score ten million items in 50 ms with a good model, and a model cheap enough to score ten million items is not good enough to rank the top ten. So every large recommender in the world resolves this the same way: a cheap stage that is fast and roughly right, then an expensive stage that is slow and precise, applied only to what survived.

${flow([{t:"Candidates",d:"10M → 1000, ~10 ms"},{t:"Ranking",d:"1000 → 100, heavy model"},{t:"Re-ranking",d:"business rules, diversity"}])}

This "funnel" is the single most transferable idea in the design. It reappears in search, in ad serving, and — as retrieve-then-rerank — in RAG.

The vocabulary

  • Candidate generation / retrieval — narrowing millions to hundreds. Usually several independent sources in parallel: items similar to what you just watched, items popular with people like you, trending items, fresh items. Each source has different failure modes, so a union of them is more robust than one clever source.
  • Two-tower model — the standard retrieval architecture. One neural network turns the user into a vector, another turns each item into a vector, and relevance is their dot product. The crucial property: item vectors do not depend on the user, so all ten million can be computed offline and indexed for ANN search. Retrieval becomes a vector lookup.
  • Ranking model — sees user and item features together and can model their interaction properly ("this user watches cooking videos, but not at 8am"). Typically gradient-boosted trees or a deep network over hundreds of features. Too slow for millions of items; ideal for a thousand.
  • Feature store — the service that supplies feature values at request time with the same definitions used in training. See the feature-store design; the two questions are frequently asked together.
  • Implicit feedback — nobody rates anything. You infer preference from clicks, watch time and skips, all of which are noisy and biased.

The mental model — and the trap inside it

A recommender is a feedback loop, not a prediction problem. It is trained on what users clicked, but users could only click what it showed them. Items it never shows generate no data, so they look bad forever, so it never shows them. This is position bias and the feedback loop problem, and it is the deepest issue in the field. If you say nothing else senior in this interview, say this — and say that the fix is deliberate exploration plus logging the propensity (the probability the system had of showing that item), so you can correct for it during training.

The senior layer

  • Optimising click-through rate will wreck your product. CTR rewards thumbnails and outrage; it does not reward satisfaction. The standard fix is multi-task learning: one model head per objective (click, long watch, share, complete, report) combined at serving time with tunable weights. Those weights then become a product lever tuned by A/B test rather than a hyperparameter — and they let you respond to "engagement is up but complaints are up" without retraining. Volunteering this makes you sound like someone who has shipped a recommender rather than read about one.
  • Training/serving skew is the number-one production bug in this system. Training reads a warehouse table; serving reads Redis. Any difference — a different default for a missing value, a timezone, a feature computed with data that was not yet available at prediction time — degrades quality silently. Nothing crashes; the metrics just quietly get worse. The structural fix is one feature definition compiled to both paths, plus continuous comparison of logged serving-time features against recomputed training features.
  • Point-in-time correctness. If you build training data by joining today's user features to last month's clicks, you have leaked the future into the past — the model learns from information it will never have at serving time, scores brilliantly offline, and fails in the A/B test. Every training row must use feature values as of the moment of the impression.
  • Sampled softmax and the popularity correction. Training a two-tower retrieval model uses in-batch negatives — other items in the batch act as negatives. But batches are drawn from logged traffic, so popular items appear as negatives far more often and get systematically over-penalised. The standard correction subtracts the log of the item's sampling probability from the logit. This is a specific, checkable piece of knowledge that very few candidates have.
  • Cold start splits into three different problems with three different answers: a new user (fall back to popularity and context, and explore aggressively for their first sessions), a new item (rely on content features — text, thumbnails, category — since there is no interaction history, which is a strong argument for content-aware towers), and a new market (transfer from a similar market and accept a worse cold period). Treating them as one question is a junior tell.
  • Offline metrics do not predict online results. An AUC improvement translating to an engagement improvement is the exception, not the rule, because offline evaluation cannot capture the effect of showing users things they would never have seen. Plan for online A/B as the decision-maker, use offline metrics only to decide what is worth testing, and budget for the fact that most tests will be flat.

What the follow-up question usually is

"How do you stop it becoming a filter bubble?" The honest answer has three parts: measure it (intra-list diversity, catalogue coverage, and the Gini coefficient of impressions across the catalogue — you cannot manage what you do not instrument); intervene at the re-ranking stage with determinantal point processes or simple maximal-marginal-relevance, because diversity is a property of the list, not of any single item score; and accept the cost, since diversity nearly always costs short-term engagement and must be justified as a long-term retention investment. Say that last part — it is the part that shows judgement.

(b) Naively 800 × 60 = 48,000 individual Redis reads per request, which at even 0.2 ms each would be 9.6 s. The design must be: one pipelined multi-get of 800 item-feature blobs (items are shared across users, so these cache extremely well), plus one read of the user's feature vector, which is the same for all 800 items. That is 2 round trips, not 48,000. Recognising that user features are per-request and item features are per-item is the whole trick, and getting the read pattern wrong is how real systems fall over.

(c) Evaluate the proposal. Cost scales linearly: 10× candidates is 10× the ranking CPU, so ~£millions/year and a latency blow-out from 320 ms to 3.2 s of CPU per request. Quality does not scale linearly — it saturates fast, because candidate generation already ordered them roughly and items ranked 800–8,000 are mostly genuinely irrelevant. The right response is not "no" but "measure it": run an offline study of how often the finally-shown item came from position 400–800 of the candidate list. If almost nothing survives from the tail, widening it is pure cost. If a meaningful fraction does, the real fix is a better candidate generator, not a wider one — that gives the quality without the linear cost.

Start here — why fraud is unlike other classification

Fraud detection looks like a binary classifier and is not. Four properties break the standard playbook, and naming them early is how you show you understand the domain:

  • Extreme imbalance. Roughly 1 in 1,000 transactions is fraudulent. A model that predicts "never fraud" is 99.9% accurate and completely worthless. Accuracy is not merely a weak metric here, it is actively misleading, and the interviewer is waiting to see whether you say so.
  • An adversary. Spam filters face static spam; fraud faces people who actively probe your system and change tactics the week you deploy. Model decay is not gradual drift, it is a step function on the day a fraud ring finds a gap.
  • Delayed and partial labels. A chargeback arrives 30–90 days after the transaction. So today you do not know today's ground truth, and — worse — for transactions you blocked you never learn whether they were actually fraud. Your training data only contains the outcomes of decisions you allowed.
  • Deeply asymmetric costs. Missing fraud costs the transaction value. Blocking a legitimate customer costs their trust, possibly their lifetime value, and a support call. These are not comparable numbers, and the model cannot choose between them — the business must.

The vocabulary

  • Precision / recall — of the transactions we blocked, how many were actually fraud (precision); of all the fraud that happened, how much did we catch (recall). You trade one against the other by moving a threshold, and choosing that threshold is a business decision expressed in currency.
  • PR-AUC — the area under the precision-recall curve. Preferred to ROC-AUC under extreme imbalance because ROC-AUC is dominated by the huge negative class and looks reassuringly high even for a poor model.
  • Velocity features — counts over recent time windows: cards tried on this device in the last hour, transactions from this account in ten minutes. These are typically the strongest signals in the whole model, and they are why the design needs streaming infrastructure rather than a nightly batch job.
  • Calibration — whether a score of 0.7 actually means 70% of such cases are fraud. Required here, because the score feeds an expected-cost calculation. A well-ranked but badly-calibrated model is useless for thresholding.

The mental model

You are not building a fraud detector. You are building a cost-minimising decision system that happens to contain a model. The model outputs a probability; the decision — allow, challenge with step-up authentication, review, or block — comes from multiplying that probability by the money at stake. This reframing is the single most valuable thing you can bring to this interview, because it makes every subsequent trade-off answerable with arithmetic instead of opinion.

The senior layer

  • Threshold by expected cost, per transaction, not globally. Block when p × transaction_value > cost_of_false_positive. A £5 transaction and a £5,000 transaction should not share a threshold — the same probability implies a hundredfold difference in expected loss. This one line reframes the whole design, and it immediately explains why calibration matters more than raw discrimination.
  • The blocked-transaction blind spot is the hardest problem in the design, and most candidates never mention it. Because you never learn the outcome of what you blocked, your training data is censored by your own past decisions, and the model becomes increasingly confident about a region it no longer observes. The accepted answer is to deliberately allow a small random sample of high-risk transactions through — you are paying for labels with fraud losses. Size that budget explicitly (say, 0.1% of flagged volume, capped at a known monthly cost) and treat it as a line item. Framing exploration as a purchase rather than a leak is the senior move.
  • Rules and models are complements, not competitors. Rules give instant response to a new attack (minutes, not a retraining cycle), are auditable, and are what a regulator or fraud analyst can reason about. Models find patterns nobody wrote down. Ship both: rules as a hard override layer above the model, with every rule carrying an owner, an expiry date and measured precision — otherwise you accumulate hundreds of stale rules nobody dares delete, which is where most real fraud systems end up.
  • Graph features are the step change. Fraud rings share devices, IPs, shipping addresses and card BINs. Features computed over the entity graph — how many accounts touched this device in 30 days, is this account two hops from a known-fraud account — routinely outperform every per-transaction feature. They are also expensive to compute in under 100 ms, so precompute them in a streaming graph store and read them as features. Mentioning this shows you know where the actual signal lives.
  • Regulation constrains the model choice. An adverse-action decision may have to be explainable to the customer and to a regulator. That makes a gradient-boosted tree with SHAP attributions more deployable than a deep net that scores two points higher — and it makes "which model is most accurate" the wrong question. Also: never use protected attributes or their close proxies (postcode is a proxy for ethnicity), and measure false-positive rate by demographic slice even when you do not use those attributes, because the model will find proxies on its own.
  • Monitor score distributions, not just accuracy, because accuracy needs labels you will not have for 60 days. A sudden shift in the distribution of scores, or in the population's feature distributions, is your earliest available alarm — typically by weeks. Pair it with a small, manually-labelled daily sample for a fast, noisy accuracy estimate.

The question behind the question

"How do you know it is working?" is asking whether you understand that you cannot know quickly. The credible answer combines a champion/challenger setup with a holdout where the challenger's decisions are logged but not enforced, a cost dashboard in currency rather than F1, and an explicit statement that the true evaluation lags by a chargeback window — so the design must be safe to run while partly blind.

Start here — why inline completion is a latency problem first

An inline code assistant suggests the rest of the line or block as you type. Its defining constraint is not model quality, it is the typing gap: a developer pauses for roughly 200–300 ms between keystrokes, and a suggestion that arrives after they have resumed typing is not merely late, it is actively annoying. Miss the window and the feature is worse than nothing.

That single constraint produces the whole design. You cannot use the biggest model. You cannot do multi-step retrieval. You must cancel aggressively, because most requests are made obsolete by the next keypress.

${flow([{t:"Keystroke",d:"debounce ~150 ms"},{t:"Context",d:"assemble from repo"},{t:"Model",d:"small, FIM-trained"},{t:"Filter",d:"syntax, secrets, dedupe"},{t:"Ghost text",d:"accept with Tab"}])}

The vocabulary

  • FIM (fill-in-the-middle) — normal language models only continue text forwards, but code completion has text after the cursor too. FIM is a training-time trick: documents are split into prefix, middle and suffix and reordered with special tokens so the model learns to generate the middle given both sides. Nearly every serious code model is FIM-trained, and knowing this term is a reliable signal of familiarity with the area.
  • Context assembly — choosing what to put in the prompt. You have a 200-file repository and a few thousand tokens. Typical ingredients: the current file around the cursor, recently-opened files, the imports resolved to their definitions, and similar code found by lexical or embedding similarity.
  • Ghost text — the greyed-out inline suggestion accepted with Tab. It is deliberately low-commitment: unlike a popup, ignoring it costs the developer nothing, which changes the acceptable precision bar.
  • Acceptance rate — the fraction of shown suggestions accepted. The headline metric, and a partly misleading one (see below).
  • Debounce — waiting a short while after the last keystroke before firing a request, so you do not issue one per character.

The mental model

Think of it as a speculative system, like a CPU branch predictor. You will do far more work than you use — the majority of requests are cancelled or the suggestion is never accepted — and that is fine, provided the wasted work is cheap and never blocks the editor. Design for cancellation from the start: every request carries a token invalidated by the next keystroke, and the client must be able to throw away in-flight work without waiting for it.

`, deep:`

The senior layer

  • Acceptance rate is a trap if used alone. You can raise it to near 100% by only suggesting single closing brackets. What you actually want is accepted characters retained after N minutes — suggestions the developer took and then did not delete or rewrite. Distinguishing these two metrics unprompted is one of the strongest signals available in this interview, because it shows you have thought about what the feature is for rather than what is easy to count.
  • Know when not to suggest. A suggestion shown at a bad moment costs attention even when ignored. Suppress inside string literals and comments unless confidence is high, immediately after an explicit rejection at the same position, when the model's own probability is low, and when the completion merely duplicates text already present after the cursor. A small "should we suggest at all?" classifier running before the expensive model is a real production technique and it improves both cost and perceived quality.
  • Caching works far better than you would expect, because editing is repetitive: undo, retype, move the cursor back. Cache on a hash of the assembled context rather than the raw file, so that cosmetic changes elsewhere in the file still hit. Then go further — if a cached suggestion was foo(a, b) and the user has since typed fo, the cached result can be served immediately as a prefix match with zero latency. That trick alone removes a meaningful share of requests.
  • Context assembly is where the quality actually comes from, not model size. In an unfamiliar repository the model has no idea what your types, helpers or conventions are; give it the resolved definitions of the symbols in scope and quality changes more than swapping to a model twice the size. Say explicitly that you would invest in the retrieval side before the model side — it is the counterintuitive and correct answer.
  • Security and licensing are not optional extras. Scan generated output for credential-shaped strings before display (models trained on public code emit plausible API keys). Offer a public-code filter that suppresses suggestions matching long verbatim spans of known open-source code. And for an enterprise deployment, be explicit about whether prompts leave the customer's network — this question decides the deal far more often than accuracy does.
  • Cost per developer per month is the metric the buyer cares about. Requests fire on a timer, not on intent, so volume is enormous: a developer might trigger thousands of requests a day and accept a few dozen. That makes cancellation, debouncing, caching and a small model the difference between a viable product and one that loses money on every seat. Quote a number — suppress 60–70% of would-be requests and you have roughly tripled the gross margin without touching the model.

The follow-up you should expect

"How would you evaluate a new model before shipping it?" Offline: HumanEval-style functional benchmarks for a floor, plus a repository-level benchmark that reflects real context assembly, because single-function benchmarks do not predict in-repo behaviour. Then a shadow deployment scoring the candidate model's suggestions against what the developer actually typed next — the closest thing to ground truth available without exposing anyone to a worse model. Only then an A/B test on retained characters, with latency as a guardrail metric, since a better model that is 100 ms slower can easily lose.

Start here — moderation is a triage system, not a classifier

The naive framing is "build a model that detects bad content". The real system is a triage pipeline whose job is to spend scarce human attention where it matters, at a volume where reviewing everything is impossible and reviewing nothing is unacceptable.

${flow([{t:"Upload",d:"text · image · video"},{t:"Hash match",d:"known-bad, exact"},{t:"Classifiers",d:"cheap, parallel"},{t:"Policy engine",d:"thresholds by surface"},{t:"Human review",d:"queued by risk × reach"}])}

The vocabulary

  • Perceptual hashing — a fingerprint that survives resizing, recompression and light cropping, unlike a cryptographic hash. It lets you match against a database of previously-confirmed violating media in microseconds with essentially no false positives. This is the first stage in every real system, because it is enormously cheaper and more reliable than any model, and forgetting it is a common beginner omission.
  • Precision / recall, but per policy. Child-safety content demands maximum recall at almost any precision cost. Spam tolerates misses. A single global threshold across policies is always wrong.
  • Prevalence — the share of views (not posts) that are violating. The industry metric, because harm scales with reach: one violating post seen a million times matters more than a thousand seen twice.
  • Human-in-the-loop — moderators reviewing what models are unsure about. They are the label source, the appeals mechanism and the expensive constraint all at once.
  • Policy drift — the rules change weekly, faster than you can relabel and retrain. This is the property that makes the problem genuinely hard, and it drives the architectural choice below.

The mental model

Separate measurement from decision, and keep them in different systems. Models output stable, slowly-changing scores: "how violent is this", "how sexual is this", "how likely is this spam". A separate policy engine — configuration, not code, not model weights — maps those scores to actions per surface, per region, per user age. When the policy changes on Tuesday, you edit a threshold and deploy in minutes. If instead you trained a model to predict "violates policy", every policy change invalidates your labels and requires a retrain you cannot do weekly. Explaining this separation is the core insight of the design and is what the question is really testing.

The senior layer

  • Queue by expected harm, not by score. A borderline post from an account with 2M followers deserves review before a confidently-violating post seen four times. Rank the human review queue on p(violating) × projected_reach × policy_severity. This single change typically does more for measured prevalence than a model improvement, because it reallocates the genuinely scarce resource. Say it out loud; almost nobody does.
  • The enforcement ladder is wider than remove/allow. Real systems have: allow, demote (reduce distribution without telling anyone), age-gate, interstitial warning, remove, remove and strike the account, escalate to law enforcement. Demotion is the workhorse — it handles the enormous uncertain middle at low cost and low outrage, since a false positive that reduces reach is far cheaper than a false positive that deletes someone's post. Designing only a binary decision is the clearest junior tell in this question.
  • Sampled review is non-negotiable for measurement. Your model's own precision measured on its own flags is circular and tells you nothing about what it missed. You need a random sample of production traffic labelled by trained reviewers to estimate true prevalence and recall. That sample is a fixed operational cost, and it is the only honest number you will ever have — protect it from being cut.
  • Adversarial evasion is constant and cheap. Text: unicode homoglyphs, zero-width joiners, leetspeak, embedded in an image. Images: crop, flip, overlay noise, re-encode — each defeats naive hashing. The standard responses are normalisation before classification (NFKC, confusable folding, OCR on images), perceptual rather than exact hashing, and a fast path for newly-confirmed content so a viral violating item can be hash-blocked within minutes while a retrain would take weeks.
  • Moderator welfare is a real design constraint. Blur-by-default, greyscale, limited exposure duration, and routing the worst categories to a specialised, supported, rotating team. This has engineering consequences — the review UI needs progressive reveal, the queue needs category-aware routing — and mentioning it shows a maturity about the domain that interviewers in this field notice immediately.
  • Appeals close the loop and are your best label source. A successful appeal is a confirmed false positive, delivered free by a motivated human. Feed them back into training with high weight, and track appeal-overturn rate per policy as a leading indicator that a threshold has drifted or a model has regressed on a slice.
  • Zero-shot classifiers changed the new-policy problem. A new policy previously meant weeks to gather labels. Now an LLM with a well-written policy description gives a usable day-one classifier — poorer than a trained model, but available immediately — while labels accumulate for a distilled small model that replaces it once volume justifies the cost. Describing this two-stage path is the modern answer.

Where the real tension sits

Every threshold is simultaneously a free-expression decision, a legal-exposure decision and a cost decision, and they point in different directions. The engineering answer is not to resolve that tension in the model but to make it explicit, configurable and auditable: thresholds live in versioned config with a named owner, every enforcement writes an immutable record of which model version and which policy version produced it, and any decision can be reconstructed months later when a regulator asks. Saying "I would make every decision reproducible after the fact" is a genuinely senior answer to a question people usually answer with model architecture.

Start here — what makes an "agent" different from a chatbot

A chatbot takes a message and returns text. An agent takes a goal and runs a loop: think, call a tool, look at the result, think again, until it decides it is done. The tools are real functions — search a database, send an email, run code, call an API.

${flow([{t:"Goal",d:"from the user"},{t:"Plan",d:"model decides next action"},{t:"Act",d:"execute a tool"},{t:"Observe",d:"feed result back"},{t:"Repeat",d:"until done or capped"}])}

Two properties of that loop create every hard problem in the design:

  • The number of steps is unknown in advance. A task might take 3 tool calls or 300. So you cannot hold it in an HTTP request, you cannot predict its cost, and a bug produces an infinite loop that spends real money.
  • The model chooses the actions. Not you. Your code executes whatever the model asked for, which means an untrusted text generator is driving your infrastructure. Everything about sandboxing and permissions follows from this one sentence.

The vocabulary

  • Tool / function calling — you describe available functions in a schema; the model emits a structured request to call one; your code runs it and returns the result as another message. The model never executes anything itself.
  • ReAct — the interleaved reasoning-and-acting loop drawn above. Nearly all agent frameworks are variations on it.
  • Durable execution — the run survives process restarts and deploys. Because a run can take an hour, "the pod was recycled" must not lose the work. This is a workflow-engine problem, and recognising it as one is the key architectural insight.
  • Sandbox — an isolated environment where model-chosen code runs without reaching your network, filesystem or other tenants.
  • Prompt injection — text in a tool's output (a web page, an email, a document) that contains instructions the model then follows. The defining security problem of agents, and unlike SQL injection there is no known complete fix.

The mental model

An agent run is a distributed workflow with an unreliable, non-deterministic planner. Every instinct from durable workflow systems applies directly: checkpoint after each step, make steps idempotent, make retries safe, set a budget, emit a trace. Say this framing early. Candidates who treat it as "a loop calling an API" design something that cannot be operated; candidates who treat it as a workflow engine with a strange scheduler design something that can.

The senior layer

  • Prompt injection is not solvable by prompting, and you must say so. "Ignore previous instructions" hidden in a fetched web page is read by the model with the same status as your system prompt — there is no privileged channel.   • Evaluation must be end-to-end and adversarial. Component accuracy does not predict task success, because errors compound: 95% per-step reliability over 20 steps is 36% end-to-end.   • Human-in-the-loop is a design primitive, not a fallback. Classify tools as read-only, reversible-write, or irreversible, and require confirmation for the third class. Design the pause properly: the run must suspend durably, notify, and resume hours later without holding a connection — which is another reason the workflow-engine framing pays off.

What good observability looks like here

Every run emits a trace whose spans are steps, each recording the prompt, the model's chosen tool and arguments, the raw result, tokens and latency. You need this for three separate reasons, and it is worth naming all three: debugging (an agent did something strange and you must reconstruct why), cost attribution (which tenant, which tool, which step burns the budget), and evaluation data (real traces become the regression suite). Without step-level tracing an agent platform is unoperable — you will get reports of wrong behaviour you cannot reproduce or explain.

Start here — the problem a feature store exists to solve

A feature is any input to a model: "this user's average order value over 30 days", "seconds since last login", "is this merchant new". Computing one is easy. The problem is that you have to compute it twice, in two completely different places, and get the same answer.

${flow([{t:"Training",d:"months of history, batch SQL"},{t:"Serving",d:"one user, 10 ms, key-value read"}])}

Training reads years of data from a warehouse with a big SQL query. Serving needs one user's value in milliseconds from a cache. Two codebases, two teams, two definitions of "30 days" — and when they drift, nothing crashes. The model simply gets quietly worse, and it can take months to notice. This silent failure mode is called training/serving skew, and eliminating it is the entire purpose of a feature store.

The vocabulary

  • Offline store — the historical record, in a warehouse or lake. Large, slow, complete. Used to build training sets.
  • Online store — the latest value per entity, in Redis or DynamoDB. Small, fast, current-only. Used at prediction time.
  • Entity — the thing a feature is about: a user, a merchant, a device. The join key.
  • Materialisation — the job that pushes computed values from offline to online, so both stores hold the same numbers.
  • Point-in-time correctness — when building a training row for an event at 14:03 on 12 March, every feature must hold the value it had at that moment, not today's value. Getting this wrong is the most common and most damaging bug in applied ML.
  • Feature view / definition — the single declaration of a feature: its source, its transformation, its freshness, its owner. The artefact the whole system is built to make authoritative.

The mental model — and why the bug is so dangerous

Imagine training a churn model where one feature is "number of support tickets". You build the training set with a simple join against today's ticket table. But users who churned filed their tickets before churning, and your join counted tickets filed after the prediction date too. The model learns "many tickets ⇒ churn" from information that did not exist at prediction time. Offline AUC is superb. Production performance is near random.

This is label leakage through time travel, and it is invisible in every offline metric because it is baked into the data itself. A feature store's most important function is not caching or convenience — it is making the point-in-time join the default, so this bug becomes impossible rather than merely discouraged.

`, deep:`

The senior layer

  • The point-in-time join is an as-of join, and it is the technically interesting part. For each training row with an event timestamp, take the latest feature value whose own timestamp is less than or equal to it — per entity, per feature, over millions of rows. Two details separate a real answer from a hand-wave: you need a maximum lookback so a value from a year ago does not silently fill in as "current"; and you must use the feature's event time (when the fact became true) rather than its processing time (when your pipeline saw it), or you reintroduce leakage through pipeline lag.
  • Serving latency forces a specific read pattern. A model needing 80 features across 4 entities must not issue 80 reads. Group features by entity into a single stored value per entity, issue one multi-get per entity type, and fan out in parallel — 4 round trips rather than 80. This is precisely the mistake the recommender drill exposes, and it is worth stating as a general rule: the online store's schema is dictated by the read pattern, not by how the features were computed.
  • Three freshness tiers, chosen per feature, not per system. Batch (hours — aggregates over long windows); streaming (seconds — velocity counts, session behaviour); on-demand (request time — anything derived from the request payload itself, like the ratio of this transaction to the user's average, which cannot be precomputed because half the inputs arrive with the request). On-demand transformations are the tier candidates forget, and they must run identical code in training and serving or you have reinvented skew inside the thing built to prevent it.
  • Backfill is where the engineering time actually goes. A new feature is useless until it has history, so you must recompute it over months of past data — expensive, slow, and easy to get subtly wrong in ways that differ from the streaming path. Design the transformation once and run it in both batch and streaming modes over the same definition; if backfill and streaming are separate implementations you have two chances to disagree.
  • Feature monitoring belongs in the store, not in each model. Because features are shared, one broken upstream table degrades every model that uses it. Track per-feature null rate, distribution drift and staleness centrally, and expose which models consume which features so an alert can name the blast radius. That lineage graph is also what makes a feature safely deletable — without it, nobody ever removes anything and the store accumulates thousands of unused definitions.
  • Know when a feature store is overkill. With one model and a nightly batch score, a table and a cron job are correct and a feature store is expensive ceremony. It pays when several teams share features, when streaming freshness is required, or when point-in-time correctness has already bitten you. Naming the threshold rather than advocating the technology unconditionally is a senior signal — the interviewer is often checking whether you build infrastructure for its own sake.

The governance question that follows

"Two teams define active user differently — what happens?" The honest answer is that this is an organisational problem the system should surface rather than pretend to solve: features are namespaced and owned, each has a documented definition and an owner, discovery is searchable so duplication is visible before it is entrenched, and a deprecation path exists with consumer lineage so a definition can actually be retired. The failure mode to name is a store with 4,000 features, no owners, and nobody willing to delete anything — which is what happens when you solve the compute problem and skip the governance one.

`, drill:`Work it out

You are designing the online store for a fraud model: 40M users, 120 features per user averaging 8 bytes each, plus 30 merchant features across 2M merchants. Peak 12,000 predictions/s, each needing one user and one merchant. Latency budget for feature fetch: 15 ms at p99.

(a) How much memory? (b) What is the read pattern and QPS? (c) A colleague suggests one Redis key per feature for flexibility. Evaluate.

Answer

(a) Memory. Users: 40M × 120 × 8 = 38.4 GB of raw values. Merchants: 2M × 30 × 8 = 0.48 GB. Add key overhead and serialisation — Redis costs roughly 50–100 bytes per key beyond the value — so with one key per entity the overhead is 40M × ~80 B ≈ 3.2 GB. Call it ~45 GB, which needs a small cluster (3–6 nodes) for headroom and replication, not a single instance. Worth stating: this comfortably fits in memory, so the design is bounded by operations, not capacity.

(b) Read pattern. One user read plus one merchant read per prediction = 24,000 reads/s, issued as two parallel round trips so the latency is max of the two, not the sum. At ~1 ms per Redis round trip within a datacentre, you spend ~1–2 ms of the 15 ms budget, leaving plenty for deserialisation and the model. The merchant working set is tiny (0.5 GB) and heavily skewed toward popular merchants, so a process-local LRU cache in front of it removes most merchant reads entirely.

(c) One key per feature — evaluate. It sounds flexible and it is a serious mistake at this scale:

  • Reads explode. 150 keys per prediction instead of 2 → 1.8M reads/s rather than 24,000. Even pipelined, the per-key overhead and the cross-slot behaviour in a Redis cluster make p99 latency unpredictable, and a single slow shard now delays every prediction rather than one.
  • Memory nearly doubles. 40M × 120 = 4.8 billion keys at ~80 B of overhead each is hundreds of gigabytes of pure overhead, dwarfing the 38 GB of actual data.
  • Atomicity is lost. With one blob per entity the 120 features are written together and are mutually consistent. With 120 keys, a prediction can read a mix of pre- and post-update values — a skew bug that is nearly impossible to reproduce.

The right design: one key per entity holding a serialised struct of all its features, grouped by access pattern rather than by producer. If different models genuinely need disjoint feature subsets, split into a small number of column-family-style blobs (say "profile", "velocity", "risk") — two or three reads, not 150. And the flexibility the colleague wants is real but belongs at the definition layer: adding a feature should be a schema change to the blob, handled by versioning the serialisation, not a new key per feature.
