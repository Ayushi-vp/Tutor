Start here — what this round is really marking

Before the specific problem: a machine-coding round is not a harder LeetCode question. The interviewer is watching whether you can produce code someone else could maintain, in 45 minutes, under pressure. The marking weights are roughly: clarifying the requirements before typing (20%), a clean interface and sensible decomposition (30%), correctness including edge cases (30%), and how you discuss the extensions you did not have time to build (20%). Candidates who write brilliant, dense, uncommented code routinely fail.

Why LRU is the standard opener

A cache keeps a limited number of recently-used items so you do not have to fetch them again. When it is full, something must go. "Least recently used" is the eviction policy that discards whatever was accessed longest ago — a good default, because programs tend to reuse what they just used (this property is called temporal locality).

Work up from the naive solution — and say this out loud in the interview

  • Attempt 1: a dict plus a timestamp per entry. Eviction means scanning every entry to find the oldest — O(n) per eviction. Correct, simple, and too slow. Worth mentioning as the baseline.
  • Attempt 2: a dict plus a list, moving the key to the front on access. Removing a key from the middle of an array is O(n) because everything after it shifts. Still wrong.
  • Attempt 3: a dict plus a linked list. Now removal from the middle is O(1) — provided you can get to the node directly, which the dict gives you, and provided you can reach the previous node, which requires the list to be doubly linked. Both halves of that sentence are the insight the problem exists to test.

The vocabulary

  • Doubly linked list — each node knows both its neighbours, so unlinking it is four pointer assignments and no traversal.
  • Sentinel nodes — permanent dummy head and tail that are never removed. They exist purely so that no operation ever has to ask "is this the first node?" — every real node always has a real neighbour on both sides. This eliminates roughly half the bugs in a hand-written implementation and is a small, visible sign of experience.
  • Amortised vs worst-case O(1) — hash map lookup is amortised O(1) (a resize occasionally costs more). Say "amortised" if asked to be precise; it is a cheap accuracy point.
`, deep:`

The senior layer

  • Concurrency is the follow-up you should pre-empt. A single mutex around every operation is correct but makes the cache a global serialisation point — and note that even get must take the write lock, because it mutates the recency order. That surprises people. The standard fix is sharding: N independent caches selected by hash(key) % N. There is no invariant spanning shards, so there is no cross-shard locking, and contention drops by roughly N. The cost is that eviction becomes per-shard, so the global policy is approximate — one shard may evict while another has room. Naming that inaccuracy as an accepted trade-off is the senior move.
  • Real caches do not use exact LRU, and knowing why is a strong differentiator. Exact LRU is vulnerable to a scan: reading a large file once evicts your entire hot working set for data that will never be read again. Production systems use approximations that resist this — segmented LRU, CLOCK, or W-TinyLFU (what Caffeine uses), which keeps a compact frequency sketch and only admits a new item if it is more frequent than the victim it would replace. Redis goes further and uses sampled approximate LRU precisely because maintaining exact recency order costs memory per key.
  • TTL interacts with LRU in a way people get wrong. Adding an expiry per node means an entry can be present but logically absent. Check expiry lazily on read (cheap, but expired entries occupy capacity), and sweep in the background (bounded work per tick, never a full scan while holding the lock). The subtle bug: an expired entry sitting at the head of the recency list still counts toward capacity and will evict live entries — so the sweeper is a correctness feature, not just hygiene.
  • Memory accounting by bytes, not entries, is what production actually needs. "Capacity 1,000" is meaningless when values range from 10 bytes to 10 MB. Track a size per entry and evict until you are under a byte budget — which also means eviction may need to remove several entries for one insert, so the evict step becomes a loop rather than a single removal.
  • Test list to volunteer (saying this costs 20 seconds and reliably scores): capacity 1 and capacity 0; updating an existing key must not grow the size; get on a missing key must not change anything; the evicted item is genuinely the least recent after a mixed access sequence; and a fuzz test comparing against a naive O(n) reference implementation over random operations — that last one is the one that actually finds bugs.

What "distributed LRU" really means

If asked to make it distributed, resist scaling this data structure. The correct answer is that it stops being the same problem: you now need consistent hashing to place keys across nodes, a plan for cache invalidation (the genuinely hard part), and a decision about read-through versus write-through. LRU remains the local eviction policy inside each node and is no longer the interesting question. Saying that clearly is better than inventing a distributed doubly-linked list.

Start here — what a rate limiter is protecting

A rate limiter caps how many requests a caller may make in a period. It exists for three different reasons, and which one applies changes the design:

  • Protecting the service from overload — one runaway client must not exhaust capacity for everyone. Here you want to reject fast and cheaply.
  • Fairness between tenants on shared capacity. Here you want per-tenant accounting and possibly queueing rather than rejection.
  • Monetisation — the paid tier gets a higher limit. Here the limit is a product feature, must be exactly enforced, and must be explainable to the customer.

Ask which one it is. The answer changes whether you fail open or closed, whether you queue or reject, and how exact you must be.

The one question that picks the algorithm

"Are bursts acceptable?" A client that has been idle for an hour and then sends 50 requests at once — is that fine or not? If yes, token bucket. If no, sliding window. Everything else is detail. Asking this before writing code is worth more marks than the implementation.

The vocabulary and the mental model

  • Token bucket — picture a bucket that refills at a steady rate up to a maximum. Each request removes one token; no tokens means rejection. Idle time accumulates tokens, so a burst is permitted up to the bucket's capacity. Capacity controls burst size, refill rate controls sustained throughput — two independent knobs, which is why this is the usual choice for public APIs.
  • Leaky bucket — the mirror image: requests enter a queue and drain at a fixed rate. It smooths output instead of permitting bursts. Use it when the thing downstream cannot absorb spikes at all.
  • Fixed window — a counter reset every minute. Trivial and has the boundary problem: a client sending N requests at 11:59:59 and N more at 12:00:01 gets 2N in two seconds while never breaching the stated limit.
  • Sliding window counter — blends the current window's count with a fraction of the previous one, weighted by how far into the current window you are. O(1) memory, no boundary bug, slightly approximate. The usual production compromise.

The useful realisation: token bucket and leaky-bucket-as-a-meter are the same algorithm viewed from opposite ends. You do not need a background thread refilling buckets — you store the last timestamp and compute the refill lazily on each request. That lazy-refill trick is what makes the implementation short enough to write in an interview.

The senior layer

  • The distributed version is where the marks are, and Lua is the answer. A read-modify-write against Redis from several app servers races: two servers both read 1 remaining token and both allow. Wrapping the read, the arithmetic and the write in a Lua script makes it atomic, because Redis executes a script to completion without interleaving. Saying "I would do it in a Lua script so it is atomic" is a specific, checkable answer; saying "I would use a transaction" is not, because MULTI alone does not let you branch on a value you read.
  • The Redis round trip is the cost, and local leasing is the fix. Adding 1 ms to every request to protect against abuse that affects a fraction of a percent of traffic is a poor trade at high QPS. The standard pattern is a local token bucket holding a lease — each instance claims, say, 100 tokens from Redis at a time and serves them locally, refreshing when it is low. Accuracy becomes approximate (up to N × lease_size over the limit transiently, where N is the instance count), latency becomes zero for the common path. State the inaccuracy explicitly and size the lease so it is acceptable.
  • Decide fail-open or fail-closed, and say which. If Redis is unreachable: fail-open keeps the product working and abandons protection exactly when the system is already unhealthy; fail-closed protects the backend but turns a cache outage into a full outage. The mature answer is usually fail-open with a conservative local limit as a backstop, plus a loud alert — and for a monetisation limiter, fail-closed, because letting a free tier through unlimited is a revenue bug. Notice this answer depends on which of the three purposes applies, which is why the primer's first question matters.
  • Clock skew is the bug that bites in production. Different app servers have different clocks; a bucket refilled using server A's time and consumed using server B's can gain or lose tokens. Use Redis's own TIME command inside the Lua script as the single source of truth. Likewise use a monotonic clock locally — wall-clock time can jump backwards on NTP correction, and a negative elapsed time produces a negative refill and some very confusing behaviour.
  • Limit on a composite key with a hierarchy. Real systems limit per (api_key, endpoint_class) and per api_key overall and per IP for unauthenticated traffic. A single expensive endpoint gets its own smaller budget so it cannot consume the global one. Check the cheapest and most specific limit first and short-circuit — you do not want to make three Redis calls to reject one request.
  • The response is part of the API contract. Return 429 with Retry-After (a number the client can actually obey — you know exactly when the next token arrives, so compute it rather than guessing), plus RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset on every response, not just rejections, so a well-behaved client can pace itself and never hit the limit. Volunteering this shows you think about the caller, which is the whole point of the feature.
  • Cost-based limiting is the modern variant, and it is worth raising for an AI product: a request costing 100k tokens and one costing 200 should not both consume one unit. Charge the bucket by estimated cost up front and reconcile with actual cost after — which means the bucket can go negative, and you must decide whether that is allowed. This is exactly the quota problem from the LLM serving design, and connecting the two shows range.

A sliding-window-counter limiter allows 100 requests/minute. At 12:00:45 a client asks for permission. The 11:59–12:00 window recorded 90 requests; the 12:00–12:01 window so far has 42.

(a) Is the request allowed? (b) A fixed-window limiter with the same limit — what is the worst burst a client can achieve, and when? (c) Your token bucket has rate 2/s, capacity 10. A client idle for 30 seconds sends 15 requests instantly. How many succeed, and how long until the 15th?

Answer

(a) The estimate weights the previous window by the fraction of it still "in view". At 45 seconds into the current minute, 15 seconds (25%) of the previous window remains inside the trailing 60-second span. Estimated count = 42 + 90 × 0.25 = 42 + 22.5 = 64.5. That is below 100, so the request is allowed.

The approximation worth naming: this assumes the 90 requests were spread evenly through the previous minute. If they were all in its final second, the true trailing-60s count is 132 and the request should have been denied. The error is bounded and in practice small, which is why this algorithm is the standard compromise — but say that you know it is an estimate rather than presenting it as exact.

(b) Fixed window worst case: 200 requests in just over 0 seconds. 100 at 11:59:59.9 and 100 at 12:00:00.1. Both respect their own window's limit of 100; the client achieves 2× the intended rate across the boundary. This is the entire reason the sliding window exists, and it is the answer to "why not just use a counter?".

(c) Token bucket. Refill is 2/s but capacity caps accumulation at 10, so 30 idle seconds fills it to 10 tokens, not 60 — the cap is the whole point. The burst of 15 therefore succeeds 10 times immediately and the remaining 5 must wait for refill at 2/s: 0.5 s, 1.0 s, 1.5 s, 2.0 s, 2.5 s for the 15th.

The design point: capacity and rate are independent controls. If a 10-request burst is too generous, lower the capacity without touching the sustained rate; if sustained throughput is too low, raise the rate without changing burst tolerance. A fixed or sliding window conflates these into one number and cannot express "100/minute sustained but never more than 10 at once" — which is what most APIs actually want.

Start here — what a vector index does

An embedding model turns text into a list of numbers positioned so that similar meaning lands nearby. A vector index answers one question fast: given this query vector, which stored vectors are closest?

The naive version is three lines — compute the similarity to every stored vector and take the top k. That is exact search, it is O(n·d), and for 1,000 vectors it is genuinely the right answer. It stops being the right answer somewhere around a million vectors, which is why approximate methods exist. Say this: starting with brute force and knowing when to leave it is better than reaching for HNSW immediately.

The vocabulary

  • Cosine similarity — the angle between two vectors, ignoring their lengths. If you normalise every vector to unit length on insert, cosine similarity becomes a plain dot product, and the whole search collapses into one matrix multiply. Do the normalisation once at write time rather than on every query.
  • ANN (approximate nearest neighbour) — trades a small amount of accuracy for orders of magnitude in speed. You accept finding 95 of the true top 100 in exchange for searching a thousand times faster.
  • Recall@k — the fraction of the true top-k that the approximate search actually returned. This is the quality metric, and it is only measurable against an exact baseline — which is why the flat index in this design is not a toy, it is the measuring instrument.
  • HNSW — a navigable graph in layers: sparse long-range links at the top for coarse navigation, dense short-range links at the bottom for precision. Search descends from the top, greedily walking toward the query. The standard index in almost every vector database.
  • Metadata filtering — "nearest neighbours, but only documents this user can see, in English, from 2024". Deceptively hard, and the source of the most interesting failure in the design.

The mental model for the interview

This problem is testing interface design far more than algorithms. Nobody expects a correct HNSW in 45 minutes. They expect an abstract VectorIndex with a small, honest surface, a working flat implementation behind it, a stub or partial graph implementation, and a recall test that compares the two. If you deliver that, the fact that your HNSW is incomplete is fine — you have demonstrated exactly the engineering judgement the round is for.

`, deep:`

The senior layer

  • Deletion is the hardest part, and it is worth leading with. You cannot cheaply remove a node from an HNSW graph: other nodes link to it, and repairing those links means finding and re-searching for replacements. Every production system therefore uses tombstones — mark deleted, filter at query time, rebuild periodically. The consequences to name: search must over-fetch (ask for 2k to return k after filtering), recall silently degrades as tombstones accumulate, and you need a compaction trigger on the deleted fraction. A system with 40% tombstones is quietly returning bad results with no error anywhere.
  • Filtering breaks graph search in a specific, non-obvious way. Pre-filter and post-filter are both wrong at the extremes. Post-filtering retrieves the top 100 then drops non-matching, which returns almost nothing when the filter is selective. Pre-filtering during traversal means the greedy walk can reach a region where every neighbour fails the filter and the search dead-ends before finding the true nearest matches. The real rule: estimate the filter's selectivity, and if it passes less than roughly 1% of the corpus, abandon the graph and brute-force that subset — it is small, so exact search is fast. Knowing that the answer is "switch algorithms based on selectivity" rather than "tune the graph" is a genuine senior differentiator.
  • The three tuning knobs and what each costs. M (links per node): higher means better recall and more memory, fixed at build time. ef_construction: higher means a better graph and slower builds, fixed at build time. ef_search: higher means better recall and slower queries, and crucially it is adjustable per query at run time — so it is the knob you expose to callers who want to trade latency for accuracy on a particular request. Distinguishing build-time from query-time parameters is the thing to say.
  • Memory is usually the real constraint. 10M vectors × 768 dims × 4 bytes = 30 GB before the graph, which adds roughly another 30%. Scalar quantisation to int8 cuts it 4× for a small recall cost and is nearly free to implement; product quantisation goes much further but needs a trained codebook and hurts recall more. The standard production compromise is a compressed index for the search plus full-precision vectors on disk for reranking the top candidates exactly — cheap memory for the search, exact scoring where it matters.
  • Concurrency: reads are easy, writes are not. Graph construction mutates shared links, so concurrent inserts need locking or a single writer. The standard architecture is a small mutable buffer (brute-forced, since it is small) in front of a large immutable index, with periodic merges — searches query both and merge results. This is the LSM-tree pattern, and naming it as such is worth a mark, because it shows you recognise a known shape rather than inventing one.
  • The test that matters is not a unit test of the graph, it is: index 10,000 random vectors, run 100 queries through both the flat and the approximate index, and report mean recall@10. If it is 0.97 the implementation works; if it is 0.4 there is a bug no unit test would have caught. Building this measurement first, before the HNSW, is a strong move and demonstrates the point of the abstract interface.

Total ≈ 17 GB. Note the vectors dominate by more than 10×, so if memory is the problem, quantise the vectors — tuning M is attacking the small term.

(b) Recall fell from 0.95 to 0.72. The tombstones are the cause and the mechanism is specific: deleted nodes are still in the graph and still occupy slots in every neighbour list and every greedy traversal step. The search visits them, spends its ef_search budget on them, and discards them at the end — so the effective search effort on live nodes has dropped by roughly 30%. Worse, deleted nodes act as hubs the traversal routes through, and once enough are removed from the results the candidate set is simply too small.

Immediate mitigation: raise ef_search and over-fetch (request 3–4× k before filtering) — this buys back recall at a latency cost, today, with no rebuild. Real fix: compact the index, rebuilding without the tombstoned nodes. Prevention: alert on deleted fraction as a first-class operational metric, and trigger compaction at a threshold — 10% is a reasonable default. The broader lesson to state: this failure produced no errors, no exceptions and no latency change. It was a pure silent quality regression, which is exactly why continuous recall measurement against a flat baseline must run in production, not just in tests.

(c) The 0.3% user. This is the filter-selectivity dead-end. Their ACL filter passes about 15,000 of 5M vectors, scattered arbitrarily across the graph. The greedy traversal starts at an entry point that is almost certainly not visible to them, walks toward the query through nodes they cannot see, and frequently terminates in a neighbourhood where no reachable node passes the filter — returning a handful of poor results or none, while a user who can see 80% of the corpus is unaffected.

The fix is to switch strategy on estimated selectivity: maintain approximate per-filter cardinality, and when the matching set is below roughly 1% of the corpus, skip the graph entirely and brute-force the filtered subset. 15,000 vectors × 768 dims is one small matrix multiply — under a millisecond, and exact. The counterintuitive and correct conclusion: the user with the most restrictive permissions should get the fastest and most accurate search, not the worst. If instead you tried to fix this by tuning the graph, you would degrade everyone else's latency and still not fix it.

Start here — why this wrapper exists

Calling an LLM provider is a network call to a shared, heavily-loaded, occasionally-degraded service. It fails in more ways than a normal API, and the failures have unusual shapes:

  • Rate limits (429) are routine, not exceptional — you will hit them daily at any real volume.
  • Latency is enormous and highly variable. A p50 of 2 s and a p99 of 30 s is normal. A timeout tuned for a normal API will fire constantly.
  • Partial success exists. A stream can deliver 200 tokens then fail. You now hold half an answer and must decide what that means.
  • Failures are expensive. A retried request that already generated 500 tokens has already cost money. Naive retries multiply your bill as well as the load.

The vocabulary

  • Exponential backoff — wait 1 s, then 2 s, then 4 s. Gives a struggling service room to recover instead of hammering it.
  • Jitter — randomising each wait. Without it, every client that failed at the same moment retries at the same moment, producing a synchronised stampede that re-kills the service just as it recovers. This is the thundering herd, and jitter is not a refinement, it is the load-bearing part.
  • Circuit breaker — after N consecutive failures, stop calling entirely for a cooldown period and fail immediately. Then let one probe through; if it succeeds, resume. The three states are closed (normal), open (failing fast), half-open (probing).
  • Idempotency — whether doing it twice is the same as doing it once. Determines whether retrying is safe at all.
  • Fallback — a secondary provider or a smaller model used when the primary is unavailable.

The mental model — and the counterintuitive part

Retries help an individual request and hurt the system. When a provider is overloaded, every client retrying triples the load it is already failing to handle, which is congestion collapse. The circuit breaker exists precisely to resolve that contradiction: retries handle transient, uncorrelated failures, while the breaker handles sustained, correlated ones by removing load entirely. Explaining that the two mechanisms solve opposite problems — and that having retries without a breaker is actively dangerous — is the insight this question is designed to surface.

`, deep:`

The senior layer

  • Retry only what is retryable, and know the list. 429 and 503: yes, and obey Retry-After if present rather than using your own backoff — the server knows better than you do. 500 and 502: yes, cautiously. Connection errors and timeouts: yes, but only if the request is safe to duplicate. 400, 401 and 422: never — the request is malformed and will be malformed again; retrying a validation error is pure waste and a common bug. Context-length errors: never retry, but they are a good trigger for a fallback to a larger-context model.
  • Use decorrelated jitter, not "backoff plus a little randomness". The AWS formulation — sleep = min(cap, random(base, previous_sleep × 3)) — measurably outperforms both plain exponential backoff and simple full jitter on total work and completion time. Naming the specific algorithm rather than gesturing at randomness is a concrete, checkable signal.
  • A retry budget beats a retry count. Per-request limits ("3 attempts") still allow every request to retry three times during an outage, tripling load exactly when the dependency is dying. A budget caps retries as a fraction of total requests across the client — for example, retries may not exceed 10% of successful calls in a rolling window. When things are broken the budget is exhausted and retries stop automatically. This is what Google's SRE practice recommends and very few candidates mention it.
  • The breaker must be per-provider and per-model. One model being overloaded should not open the circuit for a different model at the same provider. It also needs a rolling error rate rather than consecutive failures: at high volume, five consecutive failures may never occur even at a 40% error rate, because successes keep interleaving and resetting the counter. Consecutive-failure counting is the textbook version and it quietly fails in production — say that.
  • The half-open state needs a concurrency limit of one. If the cooldown expires and you let all queued traffic through at once, you re-overload a service that has only just recovered and immediately trip the breaker again — an oscillation that looks like flapping. Exactly one probe, and only on its success do you close. Also apply gradual recovery if you can: allow 10% of traffic, then 50%, then all.
  • Timeouts must be layered and streaming-aware. A single overall timeout is wrong for LLMs, because a long legitimate generation is indistinguishable from a hang. Use three: connect timeout (fast, ~2 s), time-to-first-token timeout (the real health signal, ~10 s), and an inter-token idle timeout (~5 s between chunks). A stream producing tokens steadily for 90 seconds is healthy; a stream silent for 8 seconds is not — and only the layered version can tell them apart.
  • Fallback is a product decision disguised as an engineering one. Falling back from a large model to a small one keeps the service up but silently degrades quality, and the caller usually needs to know: mark the response with which model served it, log it, and let the product decide whether to show a notice. A silent quality drop that nobody can see in metrics is worse than a visible failure — and saying so is the mature position.
  • Partial streams need an explicit policy. Your service makes 500 LLM calls/s. The provider starts returning 503 for 40% of requests. Your client retries up to 3 times with exponential backoff and no jitter, and the circuit breaker opens after 5 consecutive failures.

And because there is no jitter, they arrive in synchronised waves at t+1 s, t+3 s and t+7 s — so the instantaneous peak is far worse than the average suggests. (b) Does the breaker open? Almost certainly not, and this is the important part of the question. With independent 40% failures, the chance of five consecutive failures on any given attempt is 0.4⁵ ≈ 1%. Successes keep interleaving and resetting the counter, so a consecutive-failure breaker sits closed through a sustained 40% error rate — precisely the situation it was installed to handle. (c) The changes, in order of impact:

  • Rolling error rate, not consecutive failures. Open when the error rate exceeds, say, 25% over a window with a minimum request count (so a single failure at low volume does not trip it). This alone makes the breaker actually function here.
  • Add decorrelated jitter so retries spread out instead of arriving as waves. Same total load, dramatically lower peaks.
  • Add a retry budget capping retries at ~10% of successful calls. Amplification falls from 1.62× to at most 1.1×, and it self-limits as things get worse rather than making them worse.
  • Reduce max attempts from 3 to 2. The third attempt's marginal success probability is low (0.4³ = 6.4% of requests reach it) while it costs a full extra unit of load on a struggling service.
  • Obey Retry-After when present, and shed load at the front door — under sustained provider degradation, rejecting some traffic immediately with a clear error is better for everyone than queueing it behind retries.

The lesson to state: the default configuration — retries plus a consecutive-failure breaker — is not merely inadequate here, it is harmful, because it amplifies load in exactly the scenario where the breaker was supposed to remove it. Resilience patterns must be tuned against the failure mode you actually expect, and "40% of requests fail" is far more common than "everything fails".

Start here — why chunking decides RAG quality

Chunking splits a document into passages small enough to embed and retrieve. It sounds like a text-processing chore and it is the highest-leverage decision in a retrieval system, because a chunk is the unit of retrieval: if the answer spans two chunks, no retriever can return it intact, and no prompt engineering downstream can recover it.

Why the obvious approach fails

The obvious approach is "split every 1,000 characters". Everything wrong with it is worth enumerating, because the enumeration is the design:

  • It splits mid-sentence, and often mid-word, producing chunks that embed poorly because they are not coherent text.
  • Characters are not tokens. 1,000 characters of English prose is ~250 tokens; 1,000 characters of minified JSON or dense code can be 500+. Your "fixed size" chunks vary by 2× in the thing that actually matters.
  • It destroys structure. A table's header ends up in one chunk and its rows in another, so neither is interpretable.
  • It strips context. A chunk reading "This must be filed within 30 days" is unusable — 30 days of what? The heading two levels up said "Appeals process", and that heading is now in a different chunk.

The vocabulary

  • Recursive splitting — try to split on the biggest structural boundary first (page breaks, then headings, then paragraphs, then sentences, then words). Only descend to a finer separator when a piece is still too large. This keeps chunks aligned to natural boundaries whenever possible.
  • Overlap — repeating the last ~15% of a chunk at the start of the next, so a sentence spanning a boundary appears complete in at least one of them. It costs storage and duplicate retrievals; it buys robustness at boundaries.
  • Heading path — the breadcrumb ("Employment ▸ Leave ▸ Parental") prepended to a chunk so it carries its own context. Cheap to compute, disproportionately effective.
  • Parent document retrieval — embed small, precise chunks for matching but return the larger surrounding section for generation. Small chunks retrieve better; large chunks answer better. This decoupling resolves the tension rather than compromising on a middle size.
`, deep:`

The senior layer

  • The size trade-off has a shape, and you should state it. Small chunks (100–200 tokens) are semantically focused so they match queries precisely, but they fragment answers and lose context. Large chunks (1,000+) carry context but dilute the embedding — one vector averaging six topics is close to nothing in particular. The empirical sweet spot for prose is 300–600 tokens, but the real answer is that it depends on the corpus and must be measured on your own evaluation set. Any confident universal number is a guess.
  • Different content types need different chunkers, and pretending otherwise is the main source of bad chunks. Code splits on function and class boundaries — use an AST or tree-sitter, never blank lines. Tables must be kept whole or split by rows with the header repeated on every piece. Transcripts split on speaker turns and topic shifts. Slides split per slide. Route by detected type and accept that you are writing several chunkers, because one general chunker is worse at all of them.
  • Contextual augmentation is the highest-value addition. Before embedding, prepend a one- or two-sentence description of where this chunk sits in its document — either the heading path (free) or an LLM-generated situating sentence (a one-time ingestion cost of roughly a cent per thousand chunks with a small model, and far cheaper with prompt caching over the parent document). This materially reduces retrieval failures and is currently the strongest cheap trick in RAG. Note the asymmetry that makes it obviously worth doing: it is paid once at ingestion and benefits every query forever.
  • Chunking must be idempotent and content-addressed. Re-ingesting an unchanged document must produce byte-identical chunks with identical ids, or every reindex churns your entire vector store and invalidates every cached embedding. Derive the chunk id from a hash of its content plus its position, never from an incrementing counter — a counter means inserting one paragraph at the top of a document renumbers and re-embeds everything below it.
  • The overlap bug nobody tests for: when a chunk is hard-cut because no separator was small enough, the overlap logic can produce a chunk that is entirely contained in its neighbour, or in a pathological case an infinite loop where the overlap is larger than the progress made per step. Always assert that each iteration advances the cursor by at least one token, and cap the overlap at a fraction of the chunk size. This is the single most common real bug in hand-written chunkers.
  • Evaluate the chunker directly, not only through end-to-end answers. Take your evaluation questions with their known answer spans, and measure what fraction of answer spans survive intact inside a single chunk. That number is an upper bound on your retrieval quality that no downstream component can exceed — and it is measurable in minutes, without an LLM in the loop. Building this measurement is more valuable than any particular chunking heuristic, because it turns the whole question from taste into experiment.
  • Tokeniser choice matters and is a coupling risk. Count with the tokeniser of the model that will actually consume the chunk; a chunker tuned against one tokeniser can overflow another's limit by 10–20%, especially on non-English text or code. Leave headroom rather than targeting the limit exactly, and keep the tokeniser name in the chunk metadata so you know what a stored chunk was sized against.

Start here — what problem batching solves

A GPU processing one request uses a few percent of its capacity, because the expensive work — moving model weights from memory — is the same whether you process one item or thirty-two. Batching amortises that fixed cost across many requests. The catch: a batch cannot start until it is assembled, so every request waits for the batch to fill, and the first request into an empty batch waits longest.

This problem is the purest concurrency exercise in the set. There is no model, no maths — just a queue, a timer, and the requirement that each of N concurrent callers gets their own result back.

The two triggers, and why you need both

  • Size trigger — flush when the batch reaches B items. Under high load this fires constantly and throughput is excellent.
  • Time trigger — flush when the oldest item has waited T milliseconds. Under low load, without this, a single request would wait forever for companions that never arrive.

Either alone is broken: size-only hangs at low traffic, time-only leaves throughput on the table at high traffic. Both together give a system that self-tunes across the load range, and the deadline belongs to the oldest item in the batch, not to the newest arrival — that detail is the most common bug in hand-written implementations.

The vocabulary

  • Future / promise — an object representing a result that does not exist yet. The caller awaits it; the batch loop resolves it when the result arrives. This is the mechanism that lets one worker serve many callers, and it is the core of the design.
  • Single-consumer queue — one loop drains the queue, so no locking is needed around batch assembly. Simpler and usually faster than many workers competing.
  • Backpressure — what happens when the queue grows faster than it drains. Ignoring this is the difference between a toy and a server.
  • Little's Law — L = λW: the average number of items in the system equals arrival rate × average time in system. It is how you size a queue and predict latency, and quoting it is a cheap credibility win.
`, deep:`

The senior layer

  • The unbounded queue is the bug that ends services. asyncio.Queue() with no maxsize accepts work forever: under overload, memory grows, latency grows without limit, and every request eventually times out after you have spent resources on it — the worst of all outcomes. Bound the queue and reject immediately when full, with a clear 503 and a Retry-After. Rejecting in 1 ms is strictly better for the caller than succeeding in 90 seconds, and saying that unprompted is one of the strongest signals in this question.
  • Drop work whose deadline has already passed. If a request arrived with a 2-second client timeout and has been queued for 3 seconds, executing it is pure waste — nobody is listening. Check the deadline at dequeue time and fail it immediately. Under overload this is what stops a queue from entering a death spiral where it only ever processes requests that have already been abandoned.
  • One failing item must not fail the batch. If the batched function raises, resolving every future in the batch with that exception is wrong when only one input was malformed — you have just failed 31 innocent requests. Where the underlying operation supports it, catch per item and resolve each future independently; where it does not, fall back to splitting the batch and retrying the halves to isolate the poison item. And always resolve every future on every path, including the exception path: a future that is never resolved hangs its caller until timeout, and this leak is invisible in tests that only check the happy path.
  • The timer implementation matters more than it looks. Creating a new timer task per item is expensive at high QPS and leaks tasks if not cancelled. The clean pattern is a single loop that computes the wait as deadline_of_oldest − now and waits on the queue with that timeout, so a new arrival can wake it early and the timer cost is one object regardless of batch size. Getting this right is the difference between a design that holds at 10,000 rps and one that spends its time on scheduling overhead.
  • Batching interacts badly with variable item cost, which is the LLM-specific wrinkle. If batching prompts of wildly different lengths, padding to the longest wastes compute proportional to the variance — a batch of one 4,000-token prompt and thirty-one 50-token prompts does 32× the necessary work. The fix is bucketing by size: separate queues for short, medium and long inputs, each batched independently. Naming this as the reason production servers batch by token count rather than request count shows you understand what is actually being batched.
  • Tune T from the latency budget, not by feel. T is pure added latency at low load, so it must be small relative to the SLA — typically 5–20 ms against a multi-second inference. Then reason with Little's Law: at arrival rate λ, a batch of size B fills in B/λ seconds, so if B/λ is already well under T the size trigger dominates and T is irrelevant; if B/λ exceeds T you never fill batches and your effective batch size is λT. That gives you the actual throughput as a function of load, and it is a much better answer than "I would tune it experimentally".
  • The tests that matter here are the concurrency ones: N concurrent callers each get their own correct result and never each other's (shuffle the inputs so an index bug is visible); a single request at low load returns after ~T, not after a hang; a full batch returns before T; an exception in the batched function does not leave any future unresolved; and a cancelled caller does not corrupt the batch. That last one is the one people forget — if the caller goes away, its future is cancelled, and resolving a cancelled future must not raise inside your loop and kill the consumer.

A batching server has max_batch=32 and max_wait=20 ms. The batched GPU call takes 40 ms regardless of batch size (from 1 to 32 items). Requests arrive as a Poisson process.

(a) At 100 rps, what is the average batch size and the average added latency? (b) At 2,000 rps? (c) At 2,000 rps the queue is growing. Diagnose and fix.

Answer

(a) At 100 rps. In 20 ms, 100 × 0.02 = 2 requests arrive on average — far short of 32, so the time trigger always fires. Average batch size ≈ 2. A request waits on average half the window, ~10 ms, plus the 40 ms call: ~50 ms total, of which 10 ms is batching overhead. Throughput capacity here is 2 items per 60 ms cycle ≈ 33 rps of work per consumer — already below the 100 rps arrival rate, which is a hint at part (c).

(b) At 2,000 rps. 32 requests arrive in 32/2,000 = 16 ms, which is under the 20 ms window, so the size trigger fires first. Average batch is the full 32, and average wait is ~8 ms plus 40 ms = ~48 ms. Note the pleasing property: latency is roughly the same at both loads, but throughput per batch is 16× better. That is the batching design working exactly as intended.

(c) Why the queue grows anyway. A single consumer processes one batch per cycle, and the cycle is 40 ms of GPU call plus up to 16 ms of assembly. If assembly and execution are serialised — the loop collects a batch, awaits the 40 ms call, then starts collecting again — the consumer can only complete 32 items every 56 ms, which is 571 rps. Against 2,000 rps arriving, the queue grows by roughly 1,430 items per second and is unbounded within seconds.

The fix has two parts. First, pipeline the assembly: the loop should dispatch the batch without awaiting it and immediately begin collecting the next one, so assembly overlaps with execution. That removes the 16 ms from the cycle, giving 32 per 40 ms = 800 rps. Still not enough. Second, run multiple concurrent batches in flight — with 3 batches executing concurrently, capacity is 3 × 800 = 2,400 rps, comfortably above arrival. This requires the underlying GPU worker to accept concurrent batches (or multiple replicas), which is the real constraint to surface.

And regardless of the fix, bound the queue. The diagnostic lesson is the general one: batching improves efficiency per unit of work, it does not add capacity. If arrival rate exceeds the service rate of the whole pipeline, no batching parameter saves you — you need more consumers, more replicas, or admission control. A candidate who responds to "the queue is growing" by tuning max_batch and max_wait has misdiagnosed it; the right move is to compute the service rate, compare it to λ, and see immediately that the two do not fit.

Start here — why this question survives

Parking lot looks dated and is asked constantly, because it is the cleanest available test of one thing: can you model a domain in objects without either over- or under-engineering it? There is no algorithm to discover and no trick. Everyone can solve it. The distribution of scores comes entirely from the quality of the modelling and the conversation around it.

The two failure modes, and both are common

  • Under-engineering: one ParkingLot class with a dictionary and a big park() method containing every fee rule as if-statements. Works, and demonstrates nothing.
  • Over-engineering: an abstract factory producing strategy builders, six interfaces with one implementation each, and no working park() after 40 minutes. This fails more candidates than under-engineering does, because it produces nothing runnable.

The target is in between: concrete classes for things that are things, and an interface only where you can name a second implementation someone would plausibly want. If you cannot name the second implementation, do not create the interface.

The vocabulary they are listening for

  • Entity vs value object — a Ticket has identity and a lifecycle (it is issued, then closed); Money or a TimeRange is defined entirely by its values and should be immutable. Mixing these up produces bugs around equality and mutation.
  • Strategy pattern — behaviour that varies independently of the objects it acts on, injected rather than inherited. Fee calculation and spot allocation are the two obvious ones here, and they are obvious precisely because you can immediately name alternatives: flat rate vs hourly vs progressive; nearest-to-entrance vs first-fit vs reserve-EV-last.
  • Anaemic domain model — classes that are bags of getters and setters while all behaviour lives in a service. The named anti-pattern, and worth using the term: ParkingSpot should know how to occupy(vehicle) and refuse if already taken, not expose a settable occupied_by field.
  • Invariant — something that must always be true: a spot holds at most one vehicle, a ticket has at most one open session, availability counts always match reality. Naming your invariants and saying where each is enforced is the single most senior-sounding thing you can do in this round.
`, deep:`

The senior layer

  • Concurrency is where this question actually gets interesting, and it is the follow-up you should steer toward. Two cars at two entrances, one remaining spot. A find_free_spot() followed by spot.occupy() is a check-then-act race and both cars get the same spot. The fixes, in ascending order: a lock around allocation (correct, and a bottleneck at one lot but perfectly fine at real scale — say that); an atomic compare-and-set on the spot's state so the loser retries with the next candidate (better, lock-free); or a database row-level update with a WHERE occupied_by IS NULL guard and a check that one row was affected (how you would actually build it). Mentioning that the naive version has a race before being asked is worth more than any class diagram.
  • Availability counts must not be a second source of truth. A cached free_count per floor is what you need for the display board, and it will drift from the actual spot states after any partial failure. Either derive it on read (simple, and fine at this scale), or update it inside the same transaction as the occupation, and add a periodic reconciliation that recomputes and alerts on drift. Volunteering that a denormalised count is a consistency risk shows you have maintained a system rather than only designed one.
  • Model the fee as a policy over a time range, not a number. Real requirements arrive as: first 30 minutes free, then hourly, capped at a daily maximum, with a different rate overnight and at weekends, plus validation stamps from shops. A single compute(ticket) that returns a number cannot express partial refunds, cannot explain itself to an angry customer, and cannot be tested piecewise. Return a breakdown — a list of line items with reasons — that sums to the total. This is the change that survives contact with a real product, and it costs nothing to design in from the start.
  • The spot-fitting rule is a real decision, not an afterthought. May a motorcycle take a large spot? Usually yes when nothing else is free, but only after all motorcycle spots are exhausted — otherwise you fill your large spots with motorcycles at 9am and turn away lorries all day. That makes allocation ordered preference with fallback, not a single lookup, and it is a nice example of a business rule that belongs in a strategy rather than scattered through park().
  • The EV charger is the requirement that breaks a naive model, and interviewers add it deliberately. A charging spot has state independent of occupancy (charging, full, faulted), the vehicle may stay after charging completes, and you probably want to bill charging separately from parking. If ParkingSpot is a single class with a type enum, this forces ugly conditionals everywhere. Either make the charger a separate collaborator the spot has, or accept a subclass — but notice out loud that composition handles "a spot that gains a charger later" and inheritance does not.
  • Where the state actually lives determines everything else. If it is in memory, you get a lock and lose everything on restart. If it is in a database, the invariants become constraints (a unique index on spot_id WHERE occupied enforces "one vehicle per spot" far more reliably than any application code) and concurrency becomes transactions. Saying "I would put the one-vehicle-per-spot invariant in a database constraint because application-level checks race" is a strong, concrete answer.
  • Talk about testing in domain terms. The tests that matter are: park into a full lot returns a clear failure rather than throwing; unpark an unknown or already-closed ticket is rejected; fee at exactly the free-period boundary and at exactly the daily cap; concurrent park of the last spot yields exactly one winner; and a spot occupied by a vehicle that never returns can be force-released by an operator with an audit record. That last one is a requirement nobody states and every real lot needs.

How to spend the 45 minutes

Roughly: 5 minutes clarifying (entrances, reservations, payment timing, EV), 10 minutes on the class model out loud with the interviewer, 25 minutes writing a working park/unpark/fee path with one allocation strategy and one fee strategy, and 5 minutes discussing what you would add next. Working code for the core path beats a complete design with nothing runnable, every time — and if you must choose, cut the number of spot types, not the working park().

        for floor in self.floors:
            for spot in floor.spots:
                if spot.occupied_by is None and spot.type == vehicle.type:
                    spot.occupied_by = vehicle
                    floor.free_count -= 1

Answer

There are more than three; here are the ones worth raising, in the order a reviewer would care about.

1 · A check-then-act race. Two threads can both see spot.occupied_by is None and both assign. The second silently overwrites the first, so one car is parked in a spot the system thinks belongs to another, and free_count is decremented twice for one spot. Fix: move the transition into the spot itself as an atomic operation — spot.try_occupy(vehicle) returning a boolean, implemented with a compare-and-set or under a lock — and have the loop continue to the next candidate on a false return. At the persistence layer, a conditional update with an affected-row check.

2 · free_count is a second source of truth and is never restored. park decrements it; unpark never increments it. Within a day the display board reads zero while the lot is half empty. Fix: derive it from the spots on read, or — if it must be cached for performance — change it in exactly the same atomic step as the occupancy, and add a reconciliation job. The deeper point: any denormalised counter needs a single owner and a repair path.

3 · Exact type matching means the lot fills wrongly and rejects cars unnecessarily. A motorcycle will never take a large spot even when the lot is otherwise full, so park returns None while spaces exist. Fix: an ordered preference list per vehicle type with fallback, expressed as an allocation strategy rather than an equality check.

4 · The fee calculation has three bugs in one line. .seconds on a timedelta discards whole days, so a car parked for 25 hours is billed for 1 hour — and the fee for 49 hours is less than for 2. It should be .total_seconds(). There is no free period, no daily cap and no rounding policy, so a 61-second stay costs 4.2 pence and nobody can explain the charge. And a float rate for money invites accumulation errors. Fix: a FeeStrategy returning an itemised breakdown, using total_seconds(), integer minor units for money, and an explicit rounding rule.

5 · Error handling assumes the happy path. self.tickets[plate] raises KeyError for an unknown plate; nothing prevents unparking the same ticket twice, which would free an already-free spot and could double-charge. Fix: look up and validate the ticket's state, and make the ticket's close transition idempotent.

6 · Keying tickets by plate is a modelling error. Plates are not unique over time and the same vehicle may re-enter after leaving; the dictionary also silently overwrites an open ticket if a plate parks twice. Tickets should have their own ids, with the plate as a searchable attribute, and the "one open session per spot" invariant enforced where it belongs.

7 · datetime.now() is called directly, which makes every fee rule untestable without sleeping or monkey-patching. Fix: inject a clock. This is a small change that makes the boundary tests — exactly at the free period, exactly at the daily cap — trivial to write, and interviewers notice when you can test your own fee logic.
