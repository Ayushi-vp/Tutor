Start here — why this easy question is asked so often

A URL shortener turns https://example.com/a/very/long/path?with=params into bit.ly/3xK9pQa, and redirects anyone who visits the short link back to the original. That is the whole product. It is asked constantly because it is the smallest problem that still forces you to talk about unique ID generation, read-heavy caching, database sharding and cache invalidation — and because the naive answer is wrong in an interesting way.

The naive answer and why it fails

"Hash the long URL with MD5 and take the first 7 characters." Two problems. First, collisions: different URLs can produce the same prefix, so you silently send users to the wrong place — and you must check for a collision on every write, which is an extra read. Second, it is not idempotent in the way people assume: the same URL always maps to the same short code, which sounds good until a customer wants their own custom alias or per-campaign analytics on the same destination.

The vocabulary

  • Base62 — encoding a number using [0-9a-zA-Z], 62 characters. Seven base62 characters give 627 ≈ 3.5 trillion codes, which is the arithmetic you will be asked to do out loud.
  • Read-heavy — this system has roughly 100 reads per write. Almost every design decision follows from that ratio, so establish it early and keep referring back to it.
  • 301 vs 302 — a permanent redirect is cached by the browser (fast, but you never see the second click) while a temporary one is not (slower, but you keep your analytics). This is a real product trade-off, not trivia.
  • Cache-aside — read from the cache; on a miss read the database and populate the cache. The default pattern, and the right one here.

The mental model

This is a distributed hash table with a business model attached. The core operation is a single key lookup, so the interesting engineering is not the lookup at all — it is generating keys without coordination, keeping the hot ones in memory, and deciding what happens when the database and the cache disagree.

5 · The deep dive — 30–46 min: generating the code

This is what the interview is actually about. Walk the options and pick one.

  • Hash and truncate. Simple, but needs a collision check on every write (an extra read, and a retry loop) and leaks nothing useful. Workable, not great.
  • Auto-increment then base62. Guarantees uniqueness with no check. But a single sequence is a global coordination point, and worse, the codes are sequential and guessable — anyone can enumerate every link in the system, which is a genuine privacy failure for links people assume are unlisted.
  • Counter ranges per server (the answer to give). A coordination service (ZooKeeper, etcd, or just a row in Postgres) hands each API instance a block of one million IDs. The instance serves them locally with zero coordination and asks for another block when it runs low. Throughput is effectively unbounded, and if an instance dies you lose an unused block — which is free, because the ID space is 3.5 trillion.
  • Make them unguessable. Do not emit the raw counter. Either pass it through a keyed pseudorandom permutation (a bijection, so it stays collision-free) before base62 encoding, or append a few random characters. Volunteering the enumeration problem before being asked is one of the strongest moves available in this question.

Custom aliases live in the same key space and must be checked for conflict — insert with a uniqueness constraint and let the database reject duplicates rather than doing read-then-write, which races.

(b) The expiry. The viral link lives on exactly one shard. When its cache entry expires, the 8,000 requests/s for that one code all miss simultaneously and land on a single shard that can take 1,500/s. That shard is now at 5× capacity, so it queues, then times out — and because it also serves a 1/8 slice of everything else, 12.5% of all links in the system stop resolving because one link went viral. This is a cache stampede turning into a hot-shard failure.

(c) The fixes, in order:

  • Single-flight on cache miss. The first request to miss takes a short lock and refills; the others wait a few milliseconds for it rather than each querying the database. This alone turns 8,000 database queries into 1. It is the single highest-value change and should be your first answer.
  • Do not let hot keys expire on a timer. Refresh-ahead: when a key is read and its TTL is nearly up, refresh it asynchronously while still serving the old value. Popular links then never have a miss window at all.
  • Serve stale on error. If the database is unavailable or slow, return the last known value rather than failing. For a redirect this is almost always correct — an out-of-date destination beats a broken link.
  • Push the hottest links to the CDN. A link taking 8,000 rps should be served as an edge-cached redirect and never reach your origin. Promote keys above a rate threshold automatically.

The lesson to state: a 94% hit rate sounds excellent and tells you almost nothing, because cache performance under skew is decided by what happens to the hot keys, not by the average. The failure here was not insufficient cache capacity — it was the absence of a policy for the miss.

Start here — why chat is harder than it looks

Sending a message sounds like a single database insert. The difficulty is that chat is the first system most people design where the server must push to the client rather than wait to be asked, and where the recipient is frequently not there.

Those two facts generate every hard problem: you need millions of persistent connections, you need to know which server holds each connection, you need somewhere to put messages for people who are offline, and you need to decide what "delivered" means when a phone is in a tunnel.

The vocabulary

  • WebSocket — an upgraded HTTP connection that stays open and allows either side to send at any time. The alternative, long polling, works and is worse: more overhead, higher latency, and the connection churn is brutal at scale.
  • Connection registry — the map from user id to "which chat server currently holds their socket". Every message delivery needs this lookup, so it is on the hot path and must be fast.
  • Fan-out — delivering one sent message to many recipients (a group of 500). The word appears in feed design too, and means the same thing.
  • At-least-once delivery — the guarantee you can actually provide. It means duplicates are possible, so clients must deduplicate by message id. Exactly-once across an unreliable network is not achievable, and claiming it is a red flag.
  • Ordering — messages must appear in a consistent order for everyone in the conversation. Wall-clock timestamps from client devices do not give you this, because clocks disagree.

The mental model

Chat is a per-conversation append-only log plus a delivery mechanism. The log is the source of truth and gives you ordering, history and replay after being offline. The socket is only an optimisation that makes delivery fast when the recipient happens to be connected. Separating those two — durable log first, real-time push second — is the framing that makes every subsequent question easy to answer.

5 · The deep dive — 32–48 min

The connection registry. Every delivery needs "which server holds user X?". Options: a Redis hash updated on connect and disconnect (simple, and the hot path is one lookup); or consistent hashing from user id to server (no lookup at all, but reconnections and rebalancing get awkward). Take Redis with a short TTL refreshed by heartbeat, so a server that dies without cleaning up expires naturally rather than black-holing messages forever.

The offline case, which is the majority. If the recipient has no socket, the message is already durably in the log — so delivery is simply "nothing more to do now". When they reconnect, the client sends its last known seq per conversation and the server replays everything after it. This is why the log-first framing pays off: offline delivery is not a separate mechanism, it is the same mechanism with a delay.

Ordering and duplicates. Server-assigned per-conversation sequence numbers give a total order within a conversation, which is all users actually perceive. Across conversations, no ordering is needed. Clients deduplicate on a client-generated message id, which also makes retries safe — a message sent twice because the ack was lost appears once.

Group fan-out. For 500 members, do not write 500 copies of the message. Write once to the conversation partition and fan out notifications, letting each client read from the shared log. Copy-per-recipient is only justified when recipients need independent retention or the per-user inbox must be independently queryable.

4 · Architecture — 20–30 min

${flow([{t:"Post API",d:"write + validate"},{t:"Fan-out workers",d:"queue, per-follower"},{t:"Timeline cache",d:"Redis, capped lists"},{t:"Read API",d:"merge + hydrate"},{t:"Ranker",d:"optional scoring"}])}

Write: persist the post, then enqueue a fan-out job. The job looks up followers, filters to the recently-active ones, and pushes the post id onto each of their capped timeline lists. The author's acknowledgement does not wait for fan-out.

Read: fetch the precomputed timeline, then fetch recent posts from the celebrities this user follows, merge by id, hydrate the top 50, and return.

5 · The deep dive — 30–48 min: the hybrid and the celebrity problem

Define the split concretely. An account above a follower threshold — say 100,000 — is marked pull. Its posts are never fanned out. At read time, the feed service fetches that user's pull-list (the celebrities they follow, usually a handful), reads each celebrity's recent posts from a small hot cache, and merges with the pushed timeline. Because a typical user follows very few such accounts, the read cost stays near constant.

Details that show depth:

  • Fan-out only to active users. Most accounts have not opened the app in months. Maintain a "seen in the last 30 days" set and skip everyone else; their timeline is built on demand at next login. This typically removes the majority of fan-out work.
  • A new follow must backfill: when you follow someone, their recent posts should appear. Either backfill their last N posts into your timeline, or accept that the feed fills in going forward. Pick one and say why.
  • Deletion is why you store ids and hydrate at read time. If you had denormalised full post bodies into 100M timelines, deleting a post would mean 100M updates. With ids, a deleted post simply fails hydration and is dropped from the response.
  • Ranking, if asked: this becomes the two-stage funnel from recommendation systems — retrieve a few hundred candidates (from follows, plus out-of-network suggestions), score them with a model over engagement features, then re-rank for diversity. Note that ranking breaks simple pagination, because the list is no longer stable between requests — use a cursor that pins the candidate set for a session.

6 · Scale and failure — 48–56 min

  • Fan-out lag is the visible failure: a queue backlog means posts appear late. Monitor queue depth and end-to-end propagation time, and shed by deprioritising fan-out to less-active followers first.
  • Redis loss must be survivable. Timelines are a cache, not a source of truth — on loss, rebuild from the posts table on demand, degraded but correct. Never treat the timeline store as durable.
  • Counters (likes, replies) are approximate and updated asynchronously. Exact counts on a viral post would be a hot-row write bottleneck for no user-visible benefit.
  • Thundering herd on a celebrity post: the pull path means every one of their followers hits the same small cache entry simultaneously. Serve it from a replicated read cache and allow slight staleness.

Candidates start designing databases and APIs. The two halves

${flow([{t:"Upload & transcode",d:"offline, minutes to hours"},{t:"Distribute to CDN",d:"push, ahead of demand"},{t:"Playback",d:"adaptive, from the edge"}])}

The control plane (browse, search, recommendations, accounts, billing) is a normal web application handling thousands of requests per second. 3 · The ingest and transcode pipeline — 14–26 min

${flow([{t:"Upload",d:"multipart to object store"},{t:"Split",d:"into GOP-aligned chunks"},{t:"Transcode",d:"parallel fleet, per profile"},{t:"Package",d:"HLS + DASH manifests"},{t:"QC + DRM",d:"validate, encrypt"},{t:"Publish",d:"push to CDN"}])}

Uploads go directly to object storage with pre-signed URLs, in parts, so a failure resumes rather than restarting. The master is then split at group-of-pictures boundaries — you cannot cut mid-GOP because segments must decode independently — and each chunk is transcoded independently into every profile. A DAG orchestrator tracks the fan-out and fan-in; chunks that fail are retried individually rather than restarting the film.

The output is written once to origin storage and pushed to edges ahead of demand for popular content, rather than waiting for a cache miss. Pre-positioning during off-peak hours is the key optimisation: you are trading cheap night-time bandwidth for expensive peak-hour bandwidth.

4 · The playback path — 26–36 min

The player requests the manifest, then selects a starting quality, then fetches segments. Its algorithm balances two signals: measured throughput (how fast did the last segments arrive?) and buffer occupancy (how many seconds do I have in hand?). Buffer-based control is more stable — throughput estimates are noisy on mobile networks and cause quality oscillation, which viewers find more annoying than a consistently lower quality.

Start-up is a separate problem from steady state. Time-to-first-frame dominates perceived quality, so players deliberately begin at a low bitrate and step up after the buffer fills. Say this; it explains why the first few seconds of a stream look soft.

Playback position is reported every 30 seconds or so to a lightweight service so you can resume on another device. This is high-volume and low-value per event — batch it, and never make it synchronous with playback.

5 · The deep dive — 36–48 min: where the video actually lives

Three tiers, and you should name all three:

  • ISP-embedded appliances. Servers physically installed inside internet providers. A viewer's bytes never cross the public internet — the ISP saves transit costs and the viewer gets the lowest possible latency, so both parties want this. This is Netflix's Open Connect model and it is why they can serve a third of peak internet traffic.
  • Internet exchange points. For ISPs too small to host hardware, appliances at peering points one hop away.
  • Origin (cloud object storage). The complete library, hit only on a cache miss. Should serve a small single-digit percentage of bytes.

What goes where is a prediction problem: popularity by region, by time of day, plus known releases. Fill appliances overnight based on predicted next-day demand. For user-generated content the same tiering applies but the tail is astronomically longer, so edges cache reactively on first request and only the head is pushed.

Per-title encoding is the optimisation worth mentioning: a fixed bitrate ladder wastes bits on simple content (an animated cartoon needs far less than a fast-moving action scene at the same perceived quality). Analysing each title and choosing its own ladder cuts bandwidth by a meaningful fraction across the whole catalogue — and bandwidth is the dominant cost, so this is a large number.

6 · Scale and failure — 48–56 min

  • A cache miss at the edge falls back to a regional tier, then origin. Quality degrades before playback fails, because the player will step down rather than stall.
  • A popular new release is the predictable spike — pre-position it everywhere before launch rather than discovering demand at 8pm.
  • Transcoding backlog delays publication but must never affect playback of existing content. Keep the pipelines fully separate, and prioritise the queue by scheduled release date.
  • Client-side resilience matters more than server-side here: the player retries segments, switches CDN on repeated failure, and drops quality before it stalls. Much of the availability story lives in the client, which is unusual and worth pointing out.

Start here — the query that defines the system

"Find the nearest available drivers to this point." That sounds like a database query and it is the hardest part of the design, for one reason: the data moves. Hundreds of thousands of drivers report a new position every few seconds, so this is a write-heavy index over constantly-changing geographic data, queried with low latency.

Why the obvious approaches fail

  • A SQL query with latitude and longitude ranges. A B-tree index on two independent columns cannot serve a 2D proximity query efficiently — the database picks one column, scans a stripe of the planet, and filters. It also computes distance for every candidate.
  • Keeping everything in one server's memory. Works until you have more drivers than fit, and gives you no failure story.

The answer is to convert two dimensions into one, so an ordinary index works. That is what geohashing, S2 and H3 all do.

The vocabulary

  • Geohash — interleave the bits of latitude and longitude to produce a single string. Nearby points share a prefix, so "find things near here" becomes a prefix scan. Simple, and it has an edge problem: two points either side of a cell boundary can be metres apart with completely different hashes, so you must always search the cell plus its eight neighbours.
  • S2 — Google's scheme, projecting the sphere onto a cube and using a space-filling curve. Cells are more uniform than geohash rectangles.
  • H3 — Uber's hexagonal grid. Hexagons have the useful property that all six neighbours are equidistant from the centre, which makes "expand the search radius" a clean, uniform operation. Squares have neighbours at two different distances (edge and corner), which distorts ring searches.
  • Supply and demand — the marketplace framing. This is a two-sided matching problem, not a search problem, and saying so changes how you discuss it.
  • ETA — estimated time of arrival, computed on a road graph, not as straight-line distance. A driver across a river is 200 m away and 15 minutes away.

The mental model

Two systems with different characteristics, glued by a matching service: a very high write, eventually consistent location index, and a low volume, strongly consistent trip state machine. Keep them separate in your head and in your diagram. Location can be a few seconds stale with no harm; a trip being assigned to two drivers is a catastrophe.

5 · The deep dive — 30–48 min

The geospatial index. Each driver's position maps to an H3 cell at a chosen resolution — roughly a cell a kilometre or so across in a city. The index is cell → set of drivers, sharded by cell id, so a city's load spreads across shards and a quiet region costs nothing. A search takes the rider's cell plus its ring of neighbours, unions the driver sets, and filters. If too few candidates, expand to the next ring — with hexagons every ring is uniformly further out, which makes this clean.

Why updates are cheap: a driver usually stays in the same cell between updates, so the common case is overwriting a value, not moving between sets. Only cell changes touch the index structure. Point that out — it is why 250,000 writes/s is affordable.

Matching is where the real difficulty is, and most candidates underplay it:

  • Rank by ETA on the road network, not straight-line distance. A driver 300 m away on the far side of a motorway may be 10 minutes out. This needs a routing service over a road graph with live traffic — a genuine subsystem, and worth naming as one.
  • Contention: at a busy time several riders want the same driver. Never let two matches claim one driver — the assignment must be an atomic compare-and-set on the driver's status, with losers falling through to their next candidate. This is the same race as the seat-booking problem, and saying so shows pattern recognition.
  • Offers, not assignments. A driver can decline or simply not respond, so matching offers with a timeout (typically seconds), then moves to the next candidate. The driver is soft-locked during the offer so they are not offered two trips at once.
  • Greedy nearest-driver is not optimal. Batching requests over a short window and solving an assignment problem across them reduces total wait time across the marketplace, at the cost of a few seconds of latency per rider. Mention it as the upgrade path — it signals you see this as a marketplace rather than a lookup.

6 · Scale and failure — 48–56 min

  • Shard by geography. A city is largely self-contained, so regional deployments are natural and a failure in one region does not affect others. Handle cross-boundary searches by querying both regions at the edges.
  • Location service loss: it is in-memory and it is a cache of a fast-changing truth — on restart it refills within one reporting interval, so a few seconds of degraded matching. Do not add replication complexity for data with a four-second lifetime; say that explicitly as a deliberate choice.
  • Network loss mid-trip is the common real failure. The driver app buffers locations locally and uploads on reconnect; the trip state machine tolerates gaps because it advances on explicit events, not on continuous location.
  • Surge pricing is computed per cell from the supply/demand ratio over a short window, smoothed and rate-limited so prices do not oscillate. It is also a fairness and regulatory question — acknowledge that rather than treating it as a pure optimisation.
  • The thundering herd when an event ends: thousands of requests in one cell at once. Batch matching, expand search radius adaptively, and communicate wait times honestly rather than failing requests.

7 · Close it — 56–60 min

Close on the split you opened with: a high-write, eventually-consistent location plane where staleness is harmless, and a low-volume, strongly-consistent trip plane where a race is a disaster — two completely different consistency budgets in one product. Then name the upgrade you would make next: batched assignment instead of greedy matching, because it improves the marketplace rather than any single request.

`, deep:`

The senior layer

  • Why hexagons genuinely matter, not as trivia. With square cells, the eight neighbours sit at two different distances — edge-adjacent and corner-adjacent — so an expanding ring search covers an uneven area and biases results diagonally. Hexagons have six equidistant neighbours, so ring k is a uniform annulus and "expand the radius" means what it says. It also makes supply/demand aggregation per cell comparable across cells, which matters for surge pricing. That second reason is the one candidates never give.
  • Cell resolution is a real tuning decision with a failure mode at each end. Cells too large and each search scans thousands of irrelevant drivers; too small and you must union many cells and still risk finding nobody in a sparse area. Dense city centres and empty rural areas want different resolutions, so mature systems use a hierarchy and pick the level by local density — which H3's nested resolutions support directly.
  • ETA prediction is a machine-learning system, not a graph algorithm. Shortest-path over a road graph gives a route; the time depends on live traffic, time of day, weather, the driver's behaviour and how long pickup actually takes at that specific building. Production ETA is a model over graph features, continuously retrained, and its error directly drives both matching quality and rider trust. Treating it as Dijkstra is the tell of someone who has not thought about the product.
  • The marketplace is a control system with feedback. Surge raises prices, which suppresses demand and attracts supply, which lowers surge — a loop that oscillates if tuned badly, exactly like any feedback controller. Smoothing, hysteresis and rate limits on price changes are not cosmetic; without them you get price flapping that erodes trust and is a regulatory problem. Framing surge as control theory rather than pricing is a genuinely senior move.
  • Idempotency across an unreliable mobile network is essential. A rider taps "request" on a flaky connection, the response is lost, they tap again. Without an idempotency key on the request you have created two trips and possibly two drivers en route. Every state-changing mobile API needs a client-generated key — the same mechanism as the payments design, which is worth connecting explicitly.
  • Safety and audit requirements shape the data model. Trip events are append-only and retained because they are evidence in disputes, insurance claims and investigations. Location history cannot simply be discarded for cost, and it cannot be freely queried either — it is precise movement data about real people, so access is controlled and audited. Raising privacy and retention unprompted distinguishes a senior answer in this domain particularly, because it is the part that has caused real-world harm.
`, drill:`Work it out

A city has 40,000 online drivers at peak, reporting every 4 seconds, spread over 2,000 H3 cells — but unevenly: the busiest 50 cells hold 30% of drivers. A rider request searches its cell plus 2 rings (19 cells total) and needs at least 20 candidates.

(a) What is the write rate and per-shard load if you have 16 shards? (b) What happens to matching in the busiest cells versus the quietest? (c) A concert ends and 3,000 riders request within 60 seconds from 3 adjacent cells. What breaks?

Answer

(a) Writes: 40,000 ÷ 4 = 10,000 location updates/s for the city. Across 16 shards that is 625/s each if evenly distributed — but it is not. The busiest 50 cells hold 12,000 drivers producing 3,000 writes/s, and if those cells hash unevenly, one shard could take several times its share. The fix is to shard on cell id with enough cells per shard that the law of large numbers helps, and to monitor per-shard write rate rather than assuming uniformity.

(b) Density asymmetry. In a busy cell, one cell alone holds ~240 drivers, so the 19-cell search returns hundreds of candidates — you scan and rank far more than the 20 you need, wasting work and ranking latency. In a quiet cell there may be 2 drivers across all 19 cells, so you fail to reach 20 candidates and must expand further, adding rings until you either find drivers or give up.

So the same search has opposite problems at the two extremes. The fix is adaptive: choose cell resolution by local density (finer cells downtown, coarser in the suburbs) and stop expanding as soon as you have enough candidates rather than always searching 19 cells. Volunteering that one fixed resolution cannot serve both is the insight here.

(c) The concert. 3,000 requests in 60 seconds = 50/s concentrated in 3 cells, against a citywide normal of maybe 5/s. Three things break, in order:

  • Supply exhaustion, not compute. Those cells plus their rings might hold 400 drivers. The first few hundred riders are matched; the rest have no candidates at any radius. The system is not overloaded — there are genuinely not enough cars. Recognising that this is a marketplace failure rather than an engineering one is the most important part of the answer.
  • Contention on every remaining driver. Dozens of riders race for the same few drivers, so the atomic claim rejects most attempts and each rider cycles through candidates, multiplying matching work at exactly the wrong moment. Batched assignment over a short window fixes this properly: solve the allocation once across all waiting riders instead of letting them fight.
  • Search amplification. As radius expands to find anyone, each request scans more cells, so per-request cost rises just as request rate rises — a superlinear load increase. Cap the radius and fail fast with an honest wait estimate rather than scanning the whole city.

What you would actually build: detect the demand spike per cell, switch those cells to batched matching, surge to pull drivers in from surrounding areas, and — the part that matters most for user experience — tell riders a realistic wait rather than spinning. Some of the answer here is not technical, and saying so is a strength rather than a dodge.
