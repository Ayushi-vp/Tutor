Start here — sync is not upload

Storing files is easy. The hard problem is that the same file exists on a laptop, a phone and a server, all of which can change it, some of which are offline, and all of which must eventually agree. That is a distributed consistency problem wearing a folder icon.

Why the naive version fails

"Watch the folder; when a file changes, upload it." Three failures, each of which drives a design decision:

  • You re-upload whole files. Changing one cell in a 50 MB spreadsheet re-sends 50 MB. Users on slow connections never finish.
  • You cannot resume. A dropped connection at 90% starts again from zero.
  • You have no answer for concurrent edits. Two devices edit the same file offline; whoever syncs last silently destroys the other's work.

The vocabulary

  • Chunking — splitting a file into pieces (typically ~4 MB) that are stored and transferred independently. Enables resume, parallel upload, and per-chunk deduplication.
  • Content-addressed storage — a chunk's identifier is the hash of its contents. Identical chunks are automatically the same object, so deduplication is free rather than a feature you build.
  • Content-defined chunking — choosing chunk boundaries based on a rolling hash of the content rather than at fixed offsets. Critical: with fixed offsets, inserting one byte at the start of a file shifts every boundary and changes every chunk. With content-defined boundaries, only the chunks around the edit change.
  • Delta sync — transferring only the chunks that differ, not the whole file.
  • Metadata vs block storage — two separate systems. Metadata (the namespace: names, paths, versions, permissions) is small, transactional and hot. Blocks are large, immutable and cheap. They have almost nothing in common.

The mental model

Think of it as git for consumers: immutable content-addressed blobs, plus a mutable pointer structure describing which blobs form which file at which version. Once you frame it that way, deduplication, versioning, resume and delta sync all fall out of the same design rather than each needing its own mechanism.

Deduplication has a security catch, and raising it unprompted is a strong move. Start here — why this looks easy and is not

A booking system has a small database, modest average traffic and a simple data model. It is asked because of one property: the inventory is finite, discrete and contested. Seat 14F either exists once or it does not. Sell it twice and you have a customer at the venue with no seat — a failure no retry, cache or eventual-consistency argument can repair.

And the load is pathological: a stadium tour goes on sale at 10:00 and 500,000 people arrive in the same second for 50,000 seats. Ninety percent of them will not get one. The system's real job is to disappoint 450,000 people fairly and without falling over.

Why the naive version fails

"Check if the seat is free, then mark it sold." Between the check and the write, another request does the same thing. Both see it free, both sell it. This is a check-then-act race, and at 500,000 requests/s it does not happen occasionally — it happens constantly.

The vocabulary

  • Optimistic concurrency — do not lock; write conditionally ("update seat where version = 7") and detect the conflict at write time. Cheap when conflicts are rare.
  • Pessimistic locking — take a lock before reading. Correct under heavy contention, but the lock is a serialisation point and holding it across a user's think-time is disastrous.
  • Hold / reservation — a seat is taken out of inventory for a few minutes while the user pays, then either confirmed or released. This is the mechanism that makes the product usable and the concurrency interesting.
  • Idempotency key — a client-generated id that makes a retried payment request safe. Without it, a lost response plus a retry charges twice.
  • Virtual waiting room — a queue in front of the whole system that admits users at a controlled rate. The industry-standard answer to the on-sale spike.

The mental model

Two systems with opposite requirements. Browsing events and viewing seat maps is read-heavy, cacheable, and perfectly happy being a few seconds stale. Claiming a seat is a tiny, strongly-consistent, transactional write. Most candidates design one system and try to make it do both. Separate them explicitly in your first diagram and the rest becomes tractable.

Why not a distributed lock? Because you would have to hold it across the user's payment — minutes of human time — and a lock held across a network call to a payment provider is a liveness disaster. The hold is the lock, but it lives in the database with a timeout and is therefore self-healing.

Hold expiry needs belt and braces: the conditional update treats expired holds as available (so correctness never depends on a background job), and a sweeper periodically resets them so the seat map shows them free again. Payment is the dangerous boundary. The hold expires in 8 minutes; the payment provider might take 30 seconds and then time out with an unknown outcome. Never release a hold while a payment is in flight — extend it, and reconcile against the provider. Every payment request carries an idempotency key so a retry cannot double-charge. If payment succeeds after the hold expired and the seat is gone, you must refund and apologise; design that path explicitly, because it will happen and an undesigned failure path is how people end up paying for nothing.

Worth naming: this is congestion collapse, the same failure as retry amplification in the resilient-client problem.

(b) Admission rate. Work backwards from what the inventory can absorb, not from what the service can process. 60,000 seats at an average 2 seats per order = 30,000 successful orders. If you admit faster than seats are actually claimed, you simply move the stampede inside the gate.

Each admitted user occupies a hold slot for up to 4 minutes. To sell out over roughly 20 minutes at a controlled pace, admit around 1,500–2,000 users/s — comfortably under the 3,000/s capacity, leaving headroom for retries and browsing. At that rate the 800,000-person queue drains in about 7–9 minutes, well before it matters, since the seats will be gone long before the queue is.

The key insight to state: the admission rate should be derived from inventory depletion, not from service capacity. Running at 3,000/s just to use the capacity would admit 180,000 people in a minute to compete for 60,000 seats, recreating the contention you built the queue to remove.

(c) Abandoned holds. At 1,500 admits/s with a 4-minute hold window, roughly 1,500 × 240 = 360,000 users are in-flight... which exceeds the 60,000 seats, so in practice inventory runs out first and admission should be throttled by available seats, not a fixed rate. Take the steady state instead: at most 60,000 seats can be held at once, and with 25% abandonment, about 15,000 seats are sitting in holds that will never convert.

That is a quarter of the stadium invisible to everyone else for up to 8 minutes. The consequences are real: the seat map shows sold out while 15,000 seats are unsold, users leave, and the seats only return in a wave when holds expire — producing a confusing second rush. Mitigations, in order: shorten the hold window (4 minutes is generous; 2–3 is usually enough and halves the locked inventory), release immediately on explicit abandonment rather than waiting for the timer, sweep aggressively so returns are continuous rather than bursty, and show "seats may become available" instead of a flat sold-out, with a refresh that surfaces returns as they happen.

Two people type in the same document at the same moment. There is no server round trip fast enough to serialise them without the editor feeling laggy, so both edits are applied locally first and exchanged afterwards.   • Awareness / presence — cursors, selections, who is here. Ephemeral, never persisted, and a completely separate channel from document state.

Start here — the property that makes payments different

In most systems, a bug means bad data and you fix it. In payments, a bug means someone's money is in the wrong place, possibly irreversibly, and there is a regulator, an auditor and an angry customer involved. So the design is dominated by one question that rarely matters elsewhere: what happens when you do not know whether something succeeded?

You call a bank. The connection drops. Did the charge happen? You cannot know, you cannot simply retry (that might charge twice), and you cannot ignore it (that might lose the money). Every architectural decision here descends from that single uncertainty.

The vocabulary

  • Idempotency key — a unique id the client generates and attaches to a request. Two requests with the same key produce one charge and the same response. This is the single most important concept in the design.
  • Authorisation vs capture — authorisation reserves funds on a card (it can be released); capture actually moves them. Separating them is why an online order can be authorised at checkout and captured at dispatch.
  • Double-entry ledger — the 500-year-old accounting technique where every transaction writes two entries that must sum to zero: money always comes from somewhere and goes to somewhere. It makes a whole class of bugs detectable, because the books simply stop balancing.
  • Settlement vs authorisation — the card network confirms in seconds; the actual money moves in days. Your system must represent both states, because the customer sees "paid" long before the funds exist.
  • Chargeback — the cardholder disputes a charge weeks or months later and the money is pulled back. Payments are therefore not final on success, which breaks most people's mental model.

The mental model

A payment system is an immutable append-only ledger with a state machine attached. You never update a balance — you append entries and derive the balance. You never delete or edit a transaction — you append a reversing one. If you take nothing else into the interview, take "the ledger is append-only and balances are derived", because it is the answer to a surprising number of follow-up questions.

Idempotency done properly. Naively "check if the key exists, then process" is a race — two concurrent retries both find nothing and both charge. Instead insert the key first with a unique constraint; the loser gets a constraint violation and knows to wait for and return the winner's result. The unknown-outcome problem, which is the heart of it. You call the acquirer and time out. Three possibilities: it never arrived, it succeeded, or it succeeded and the response was lost. You must not guess. The correct pattern:

  • Write your intent to the database before calling out, with a reference you generate. The record exists in pending with your idempotency key.
  • Pass your reference to the acquirer as their idempotency key, so a retry is safe at their end too.
  • On timeout, do not resolve it inline. Leave it pending and let a reconciliation worker query the acquirer for the true state and converge. The customer sees "processing", which is honest.
  • A daily file from the acquirer is compared against your ledger. Anything present on one side and not the other is an exception with a human workflow behind it. Reconciliation is not a safety net you add later; it is a core component, and saying so is a strong senior signal.

The dual-write problem. "Write to the database, then publish an event" is not atomic — a crash between them leaves the system inconsistent. Use the transactional outbox: write the event into an outbox table in the same transaction as the ledger entries, and a separate process publishes from the outbox. Multi-step flows — authorise, capture, split to merchant, deduct fees, schedule payout — cross service boundaries, so a single ACID transaction is unavailable. Use a saga: each step has a compensating action, and the orchestrator drives forward or compensates backward, durably, so it survives a crash mid-flow. It records intent durably, converges on the truth through reconciliation, and shows the customer an honest intermediate state in the meantime. Every alternative — optimistically marking success, or retrying blind — trades a small amount of user-facing latency for a small probability of losing or duplicating real money, and that trade is never worth making.

Start here — a crawler is a distributed BFS with manners

At its core: take a URL from a queue, download it, extract its links, add the new ones to the queue, repeat. That is breadth-first search over a graph with hundreds of billions of nodes. Every hard part comes from the scale and from the fact that the graph belongs to other people — you are consuming someone else's servers, and if you are impolite you will be blocked or you will take their site down.

The vocabulary

  • Frontier — the set of URLs discovered but not yet fetched. It is not one queue; it is a prioritised, per-host-partitioned structure, and its design is most of the crawler.
  • Politeness — never more than one request in flight per host, with a delay between them, and obeying robots.txt. This is a hard constraint, not a nicety: it is the difference between crawling and denial of service.
  • Inverted index — the map from term to the list of documents containing it, which is what makes search fast. A forward index (document → its words) is useless for querying; inverting it is the entire trick, and it is why the structure has that name.
  • Posting list — for one term, the sorted list of document ids containing it, plus positions and frequencies. Query processing is intersecting posting lists.
  • Shingling / SimHash — techniques for detecting near-duplicate pages. Exact hashing is useless because two copies of the same article differ by a timestamp or an advert.

The mental model

Two systems, separated by a batch boundary. The crawler is a politeness-constrained, I/O-bound producer running continuously. The indexer is a throughput-oriented batch job turning documents into an inverted index. The serving layer is a low-latency read system over an immutable index. They have different hardware profiles, different failure modes and different SLAs — and the batch boundary between crawling and serving is what makes the whole thing tractable.

3 · The frontier — 14–26 min

This is the heart of the crawler and where most candidates go thin. It must satisfy two conflicting goals simultaneously: fetch the most important URLs first, and never hit one host too fast.

The standard structure is two levels. A front set of priority queues where a URL's queue is chosen by its importance (a function of PageRank-like authority, update frequency, and how long since last fetch). A back set of per-host queues, each with a next-allowed-fetch timestamp, fed from the front queues. A heap over those timestamps tells a worker which host is ready next. The front layer decides what to crawl; the back layer decides when, and the separation is what lets you satisfy both constraints without either dominating.

URL-seen deduplication. You discover the same URL constantly and must not re-enqueue it. 50 billion URLs at even 16 bytes of hash is 800 GB — too large for one machine's memory, so it is a sharded key-value store, fronted by a bloom filter to absorb the overwhelming majority of "have I seen this?" queries without a network call. False positives mean occasionally skipping a genuinely new URL, which is acceptable at this scale; false negatives are impossible, which is the direction that matters.

Normalise before hashing or the dedup is worthless: lowercase the host, strip default ports and fragments, sort or strip tracking query parameters, resolve relative paths. Without this, one page appears as thousands of distinct URLs and the frontier fills with noise.

4 · Fetching, parsing and duplicate content — 26–34 min

Fetchers are I/O-bound, so a few thousand concurrent connections per machine is normal. Each checks and caches robots.txt per host, honours crawl-delay, follows a bounded number of redirects, and applies timeouts and size caps — a malicious or broken server will happily stream you infinite bytes.

Trap detection deserves a mention because it is the practical failure: calendar pages generate infinite unique URLs, session ids create infinite variants of one page, and some sites deliberately generate link mazes. Defend with per-host page budgets, URL depth limits, and detecting when a host produces many URLs that all yield near-identical content.

Near-duplicate detection. A large fraction of the web is duplicated — syndicated articles, mirrors, printer-friendly versions, the same page with a different advert. Exact hashing catches almost none of it. Use SimHash: produce a fingerprint such that similar documents have fingerprints within a small Hamming distance, then find near-neighbours among billions of fingerprints. Deduplicating here saves index space and, more importantly, stops the results page showing the same article eight times.

5 · Building and serving the index — 34–46 min

Indexing is a batch job over the document corpus, and it is the textbook MapReduce shape: map each document to (term, doc_id, positions) pairs, shuffle so all entries for a term land together, reduce into a sorted posting list. Compress aggressively — posting lists are sorted integers, so delta-encode the gaps and use variable-byte or similar. Compression here is not a nicety; it decides whether the index fits in memory, which decides query latency.

Shard by document, not by term. This is the decision to defend. Sharding by term means a two-word query hits exactly two shards but those shards are wildly unbalanced (common terms have colossal posting lists) and intersection requires shipping huge lists across the network. Sharding by document means every query goes to every shard, each searches its own slice and returns its local top k, and a coordinator merges. More total work per query, but perfectly balanced, trivially parallel, and each shard's intersection is local. Everyone at scale does the latter.

Serving: a query is parsed, terms are looked up, posting lists are intersected (skip lists let you jump rather than scanning), candidates are scored, and the top results are merged across shards and returned with snippets. Two-stage scoring mirrors the recommender funnel: a cheap scorer over many candidates, then an expensive model over the survivors.

Freshness is the awkward part: a batch-built index is immutable and rebuilt periodically, but news must appear in minutes. The standard answer is a small, frequently-rebuilt fresh index queried alongside the large base index, with results merged. Say this — "one index" is the naive answer and the tiered version is what actually ships.

6 · Scale and failure — 46–56 min

  • Crawler failures are routine and must be boring: workers are stateless, URLs are leased from the frontier with a timeout so a dead worker's URLs return automatically, and everything is retried with backoff. Losing a fetch is free — you will come back to that page anyway.
  • The index is immutable and versioned, so deployment is atomic: build a new version, verify it, swap traffic, keep the old one for rollback. This is a large operational advantage of the batch boundary.
  • Replicate index shards for both availability and query throughput — every replica can serve any query for its shard, so scaling reads is just adding replicas.
  • Adversarial content is a permanent condition: spam farms, cloaking (serving different content to crawlers than to users), and link schemes. This is why ranking cannot rely only on on-page signals and why link-graph authority mattered so much historically.
  • Legal and ethical obligations: obey robots.txt and noindex, honour removal requests, respect rate limits even when unenforced. A crawler that ignores these gets blocked network-wide, which is an availability problem as well as an ethical one.

The senior layer

  • Recrawl scheduling is an optimisation problem, not a fixed interval. You have a finite crawl budget and pages change at wildly different rates — a news homepage changes hourly, an archived paper never. Estimate each page's change rate from its own history and allocate crawls to maximise index freshness per fetch, which means some pages are visited hourly and others annually. Framing this as "allocate a scarce budget against predicted value" rather than "crawl everything monthly" is the senior version of this answer, and it is directly transferable to any ingestion pipeline.
  • The frontier is a distributed system in its own right, and it is where a naive design breaks. It holds tens of billions of URLs, takes writes from every parser and reads from every fetcher, and must maintain per-host ordering. It cannot be a queue in memory. Partition by host hash so all URLs for a host live on one partition (which also makes the politeness constraint local rather than requiring global coordination), persist it, and make leases the unit of work so failures self-heal.
  • JavaScript rendering changes the economics by an order of magnitude. Fetching HTML is a network request costing milliseconds; rendering a page in a headless browser costs seconds of CPU and hundreds of megabytes of memory. At 19,000 pages/s you cannot render everything — so you crawl cheaply, detect which pages have meaningful content only after rendering, and spend the expensive budget selectively. This two-tier approach, cheap-first then expensive-on-signal, is the same pattern as retrieve-then-rerank and candidate-then-rank, and pointing out that recurrence is a strong move.
  • Query latency is decided by tail behaviour, not average. Fanning out to 100 shards means a query is only as fast as the slowest shard, so a p99 of 200 ms per shard produces a p99 far worse than 200 ms overall — with 100 shards you hit the slow case almost every query.
