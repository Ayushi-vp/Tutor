Start here — the idea that makes Kafka different

A traditional queue (RabbitMQ, SQS) works like a to-do list: a consumer takes a message, and the message is removed. One message, one consumer, then it is gone.

Kafka does something else. It is an append-only log — a file you can only add to the end of. Messages are never removed when read. Each consumer keeps a bookmark (an offset) saying how far it has got. Ten different consumers can read the same log at their own pace, and a consumer can rewind its bookmark to reprocess last week's data.

${flow([{t:"Producer",d:"appends to the end"},{t:"Partition",d:"ordered, immutable log"},{t:"Consumer A",d:"offset 4,812"},{t:"Consumer B",d:"offset 91 (rewound)"}])}

That one change — the broker stores, the consumer tracks — is why Kafka scales: the broker does almost no bookkeeping per consumer, so adding consumers is nearly free.

The vocabulary

  • Topic — a named stream, like orders or clicks.
  • Partition — a topic is split into partitions, each an independent ordered log on one broker. Ordering is guaranteed within a partition and nowhere else. This single sentence answers half the follow-up questions.
  • Offset — a message's position in its partition. Monotonic, never reused, and it is the consumer's bookmark.
  • Consumer group — several consumers cooperating. Each partition is assigned to exactly one consumer in the group, so parallelism is capped by partition count. Different groups read independently.
  • Replication factor — how many brokers hold a copy of each partition. One is the leader and takes all reads and writes; the others follow.
  • ISR (in-sync replicas) — the replicas currently caught up with the leader. Durability is defined against this set, not against all replicas.
  • Retention — how long messages stay. Time-based (7 days), size-based, or compacted (keep only the latest value per key).

The mental model

Kafka is a distributed, replicated, partitioned commit log — not really a queue at all. Once you see it as "a database's write-ahead log, exposed as a product", the design decisions become obvious: sequential writes are fast, immutability makes replication easy, and letting consumers track their own position is what removes the broker's per-consumer state.

1 · Scope it — 0–5 min

  • In scope: producers publish to topics; consumers read at their own pace; messages survive broker failure; ordering guarantees; horizontal scale; replay.
  • Out of scope: stream processing (that is Flink or Kafka Streams on top), schema registry, connectors. Name them and set them aside.
  • Non-functional: millions of messages/s; sub-10 ms produce latency; no acknowledged message is ever lost; a broker failure costs seconds, not data.
  • The question to ask: "what ordering do you need?" Global ordering across a topic means one partition, which means no parallelism at all — so the honest answer is almost always per-key ordering, and that choice drives the entire partitioning scheme.

2 · Numbers — 5–12 min

  • 1M messages/s at 1 KB each = 1 GB/s ingest. With replication factor 3 that is 3 GB/s of disk writes and 2 GB/s of cross-broker network.
  • Retention 7 days: 1 GB/s × 604,800 s = ~600 TB per replica set, ~1.8 PB with replication. Large, but it is sequential on cheap spinning or NVMe disks, not random access.
  • Partitions: a single partition sustains perhaps 10–50 MB/s. At 1 GB/s you need at least ~50 partitions for throughput, and more for consumer parallelism — say 200. Note the constraint to state: consumer parallelism cannot exceed partition count, so partition count is a capacity decision you make early and cannot easily reduce.
  • Brokers: at ~200 MB/s of useful write throughput each, 3 GB/s needs 15–20 brokers plus headroom.

3 · The storage model — 12–24 min

This is where the performance comes from, so spend time on it.

Each partition is a directory of segment files. Writes append to the active segment; when it reaches a size or age limit it is closed and a new one starts. Closed segments are immutable, which makes them trivially safe to replicate, cache, delete or archive.

Why this is fast — three reasons, and naming all three is the point:

  • Sequential I/O. Appending to a file is the fastest thing a disk does. A spinning disk doing sequential writes outperforms random writes by orders of magnitude, and this is why Kafka can be disk-backed without being slow.
  • The page cache does the caching. Kafka does not maintain its own in-process cache. It writes to the OS page cache and lets the kernel flush. Recent messages — which is what consumers want — are served from memory without Kafka managing a byte of it.
  • Zero-copy. Sending a segment to a consumer uses sendfile, which moves bytes from page cache to socket inside the kernel, never copying into application memory. This is only possible because Kafka does not transform the message — it stores and returns the producer's exact bytes.

An index file per segment maps offset → byte position, so "start reading at offset 4,812" is a binary search over a small index plus a seek, not a scan.

4 · Replication and durability — 24–34 min

Each partition has one leader and N−1 followers. All reads and writes go to the leader; followers continuously fetch from it, exactly as a consumer would. Followers that are caught up form the ISR.

The producer chooses its durability with acks:

The subtlety worth volunteering: acks=all alone is not enough. If the ISR has shrunk to just the leader, "all" means "one", and you are back to acks=1 without noticing. You must also set a minimum in-sync replica count so the broker rejects writes when it cannot meet the durability you asked for. Failing loudly beats silently degrading — this pairing is the single most commonly missed detail in this design.

Consumers only ever see messages up to the high water mark — the highest offset replicated to all ISR members — so a consumer can never read a message that might be lost in a leader failover.

5 · Consumers and delivery semantics — 34–46 min

Group assignment. A coordinator assigns partitions to group members. When a member joins or dies, a rebalance redistributes them. Naive rebalancing stops all consumption briefly ("stop the world"), so real systems use incremental cooperative rebalancing that only moves the partitions that must move.

The three delivery semantics, and the mechanism behind each:

  • At-most-once: commit the offset before processing. A crash loses the message. Rarely what you want.
  • At-least-once: process, then commit the offset. A crash after processing but before committing means reprocessing. This is the default and the right default.
  • Exactly-once: achievable only within Kafka, via idempotent producers (sequence numbers per producer per partition, so the broker drops duplicates) plus transactions that atomically commit both the output messages and the consumed offsets. The moment your consumer writes to an external database, Kafka's transaction cannot cover it — you are back to at-least-once plus idempotent writes on your side.

Say that last point explicitly. "Exactly-once" in Kafka means exactly-once within a Kafka-to-Kafka pipeline, and candidates who claim it end-to-end have misunderstood the guarantee.

6 · Failure and operations — 46–56 min

  • Broker dies: the controller elects a new leader from the ISR for every partition that broker led. Producers and consumers discover the new leader via metadata refresh. Unavailability is seconds.
  • Unclean leader election: if the whole ISR is gone, you choose between staying unavailable, or promoting an out-of-date replica and losing acknowledged messages. This is CAP made concrete — name it as a configuration decision with a business owner.
  • Consumer lag is the metric that matters: how far behind the log end each group is. Rising lag means consumers cannot keep up, and it is your earliest warning of a downstream problem.
  • Hot partitions: a bad partition key (say, one tenant id dominating) sends most traffic to one broker. Monitor per-partition rate, and use a composite key or random suffix when a key is genuinely too hot — accepting that you lose ordering for that key.
  • Poison messages: a message that always fails blocks its partition forever under at-least-once. You need a retry topic and a dead-letter topic, with a bounded attempt count. Kafka does not give you this — you build it.

7 · Close it — 56–60 min

Close on the two ideas that define it: the broker stores an immutable ordered log and does no per-consumer bookkeeping, and ordering is a per-partition guarantee that you buy with reduced parallelism. Then name the trade-off you accepted — at-least-once with idempotent consumers, because true end-to-end exactly-once across systems does not exist.

You can add partitions, but adding them changes hash(key) % partitions, so existing keys move to different partitions and their ordering guarantee breaks across the boundary. You cannot reduce partitions at all. So over-provision modestly at creation — but not wildly, because every partition costs file handles, memory, and leader-election time on the controller. Being able to say why it is hard rather than just "pick a good number" is the senior version.

(a) Total group capacity is 4 × 6,000 = 24,000 messages/s against 60,000 arriving. Lag grows by 36,000 messages/s — the group falls behind immediately and unboundedly.

(b) Adding 8 consumers (total 12). Partitions are assigned one-per-consumer within a group, so 12 consumers each own exactly 1 partition. Nominal capacity is now 12 × 6,000 = 72,000/s, which looks sufficient. Going beyond 12 would be pointless: a 13th consumer gets zero partitions and sits idle, because partition count is the hard ceiling on group parallelism.

But the group still does not keep up, and this is the real question.

(c) The skew. The enterprise customer is 35% of 60,000 = 21,000 messages/s, and because partitioning is hash(customer_id) % 12, every one of those messages lands on one partition. That partition's consumer must process 21,000/s against a capacity of 6,000/s, so it falls behind at 15,000 messages/s while the other eleven consumers are at roughly 30% utilisation and idle much of the time.

Adding consumers cannot help. The partition is already owned by exactly one consumer, and that is a guarantee, not a tunable — it is what preserves per-key ordering.

The options, and the trade-off each carries:

  • Change the key to a composite such as customer_id + hash(order_id) % 8, spreading the hot customer across 8 partitions. Throughput problem solved — but you have given up ordering within that customer. Acceptable if the consumer's work is order-independent (say, independent enrichment); unacceptable if it is applying a sequence of state changes to one account.
  • Give the large customer their own topic with its own partition count and consumer group. Ordering is preserved, noisy-neighbour isolation is better, and it is operationally honest for a genuinely outsized tenant. The cost is per-tenant topology to manage.
  • Make the consumer faster — batch downstream writes, parallelise within the partition while preserving order by sub-key, or move work off the hot path. Often the cheapest real fix, and it changes nothing about the topology.
  • More partitions overall does not fix it. 100 partitions still hash that one customer id to exactly one of them.

The lesson to state: in a partitioned log, consumer parallelism is bounded by partition count, and per-partition throughput is bounded by key distribution. A capacity plan based on totals will look fine and fail in production, because the constraint is the hottest key, not the average. This is the same skew failure as the celebrity in a feed and the viral link in a shortener — worth naming the recurrence.

Start here — the two questions that define the design

You have more data than one machine can hold. So you must answer two questions, and everything else follows:

  1. Which machine holds this key? That is partitioning.
  2. What happens when that machine is down or disagrees with its copies? That is replication and consistency.

Why the obvious partitioning fails

hash(key) % N where N is the number of servers is simple and catastrophic: add one server and N changes, so almost every key maps somewhere new and the entire dataset must move. You need a scheme where adding a server moves only 1/N of the keys.

Consistent hashing does this. Imagine a circle of hash values. Each server is placed at several points on the circle (its "virtual nodes"). A key hashes to a point and belongs to the next server clockwise. Add a server and it takes over only the arcs immediately before its own positions — everything else is untouched.

${flow([{t:"hash(key)",d:"a point on the ring"},{t:"walk clockwise",d:"find the owner"},{t:"next N-1 nodes",d:"the replicas"}])}

The vocabulary

  • Virtual nodes — each physical server occupies many points on the ring rather than one. Without this, load is uneven (some arcs are much bigger than others) and a failing server dumps all its load onto exactly one neighbour instead of spreading it.
  • N, R, W — N replicas per key; a read waits for R of them; a write waits for W. You pick these per operation, and they decide your consistency.
  • Quorum — if R + W > N, any read set and any write set must overlap in at least one node, so a read is guaranteed to see the latest acknowledged write.
  • Eventual consistency — with R + W ≤ N you may read stale data, but you get lower latency and stay available when nodes are down.
  • Gossip — nodes periodically exchange membership and health information with random peers, so the cluster converges on who is alive without a central registry.
  • LSM tree — the on-disk structure: buffer writes in memory, flush sorted files to disk, merge them in the background. Optimised for writes, which is what these systems are for.

The mental model

Every hard question here is "what do you do when nodes disagree?" They will disagree — networks partition, nodes pause, writes arrive out of order. The design is not about preventing disagreement, which is impossible, but about defining precisely when you notice it, who resolves it, and what the caller is promised in the meantime.

1 · Scope it — 0–5 min

  • In scope: get and put by key; horizontal scale to petabytes; survive node and rack failure; tunable consistency; predictable latency.
  • Out of scope: joins, secondary indexes, transactions across keys, SQL. Say this deliberately — the restricted API is what buys the scale, and pointing that out is itself a design insight.
  • Non-functional: p99 under 10 ms for single-key reads; always writable, ideally even during a partition; linear scale-out by adding nodes.
  • The question to ask: "can we ever refuse a write?" If availability must be absolute, you are choosing AP and must handle conflicting versions. If correctness matters more, you choose CP and become unavailable during partitions. This is not a technical preference; it is a product decision and you should make the interviewer own it.

2 · Numbers — 5–11 min

  • 100 TB of data, replication factor 3 = 300 TB stored. At 2 TB usable per node that is ~150 nodes.
  • 500,000 reads/s and 100,000 writes/s. Spread over 150 nodes with RF 3, each node sees roughly 10,000 reads/s and 2,000 writes/s — comfortable for an LSM engine.
  • Virtual nodes: ~256 per physical node gives 150 × 256 ≈ 38,400 ring positions, which is enough that the arc sizes even out and a node failure spreads across many neighbours rather than one.
  • Say the key sizing insight out loud: you are sizing for the hot key as well as the average. A single key cannot be split, so a key taking 50,000 reads/s will saturate its 3 replicas no matter how many nodes you add.

3 · Partitioning — 11–24 min

Hash the key onto a 128-bit ring. Walk clockwise to find the coordinator node; the next N−1 distinct physical nodes are the replicas. Two refinements to state:

  • Virtual nodes, as above — and note the second benefit beyond load balance: when a node fails, its ranges are scattered across many peers, so recovery streaming is parallel rather than hammering one neighbour.
  • Rack and zone awareness. The replica walk must skip nodes in a failure domain you already used, or all three copies could land in one rack and a single power failure loses the data. This is a small rule with a large consequence and it is worth a sentence.

Membership is maintained by gossip: each node periodically exchanges a heartbeat and version vector with a few random peers, so information about a joining or failing node propagates in O(log n) rounds without any central coordinator to become a bottleneck or a single point of failure.

4 · Replication and consistency — 24–38 min

This is the heart of the interview. Work the quorum arithmetic explicitly:

NWRProperty
331Fast reads, writes fail if any replica is down
311Fastest, eventually consistent, stale reads possible
322Quorum. R+W>N so reads see the latest write; tolerates one node down

Why R+W > N works: a write touched W nodes, a read asks R nodes, and if R + W exceeds N the two sets must share at least one node — which has the latest value. Draw this; it takes ten seconds and it is the cleanest idea in the design.

When replicas disagree you need a resolution rule:

  • Last-write-wins by timestamp. Simple, and it silently discards a concurrent write. Requires synchronised clocks, which you do not have. Cassandra's default, and a known footgun.
  • Vector clocks. Track causality properly, so the system can distinguish "B happened after A" (take B) from "A and B are concurrent" (a genuine conflict). Then hand the conflict to the application, which is the only layer that knows what merging means. This is Dynamo's approach — the shopping cart that merges by union rather than picking a winner.
  • CRDTs. Use data types that merge deterministically, so conflicts cannot occur. Best when your values fit one of the shapes (counters, sets, registers).

Anti-entropy keeps replicas converging in the background: read repair fixes stale replicas noticed during a read, hinted handoff stores writes destined for a down node on a peer and replays them when it returns, and a Merkle tree comparison finds divergent ranges between replicas cheaply by comparing hashes rather than data.

5 · The storage engine — 38–46 min

Per node, an LSM tree: writes append to a commit log for durability and go into an in-memory sorted structure (the memtable). When it fills, it is flushed as an immutable sorted file (SSTable). Background compaction merges SSTables, discarding superseded values and tombstones.

Why this and not a B-tree: every write is sequential, so write throughput is very high. The cost is read amplification — a key may live in several SSTables, so a read must check them. Mitigate with a bloom filter per SSTable (skip files that certainly do not contain the key) and a sparse index. Being able to state the write-amplification versus read-amplification trade-off, and that compaction is where the hidden cost lives, is the mark of someone who has operated one of these.

Deletes are tombstones, not removals, because a delete must be replicated and must outlive any older value on a replica that was down. Tombstones then have to survive longer than the longest possible node outage before compaction removes them — get that wrong and deleted data resurrects.

6 · Failure — 46–56 min

  • Node down: quorum still satisfiable with N=3, W=2. Writes for the down node are stored as hints elsewhere and replayed on return.
  • Network partition: this is the CAP decision made real. An AP system lets both sides accept writes and reconciles later, which means conflicting versions. A CP system refuses writes on the minority side. Say which you chose and why, and note that in practice the choice is often per operation — a shopping cart is AP, a password change is CP.
  • Node permanently lost: a replacement takes over the ring positions and streams data from the surviving replicas. With virtual nodes this pulls in parallel from many peers, so rebuild time is a fraction of what it would be otherwise.
  • Hot key: the one problem this architecture cannot solve by scaling, since a key lives on exactly N nodes. Answer with a cache in front, or application-level key splitting with a known merge.
  • Correctness under stress is not testable by unit tests. Say you would use fault-injection testing that partitions the network and verifies the claimed consistency model, because these bugs only appear under specific interleavings.

Close on the three levers and their interaction: consistent hashing with virtual nodes gives you scale-out with minimal data movement; N, R and W let the caller choose consistency per operation rather than the system choosing once for everyone; and anti-entropy makes eventual consistency actually converge instead of merely hoping. Then state the price honestly — no multi-key transactions and no joins, which is exactly what makes the rest possible.

The senior layer

  • "Quorum" does not mean linearizable, and conflating them is the classic error. R+W>N guarantees a read set intersects the latest completed write set. It says nothing about a write that is still in flight, and it permits anomalies: a read can return a newer value than a subsequent read (no monotonicity), and a failed write may still be visible because it reached some replicas before failing. True linearizability needs consensus — Raft or Paxos per key range — which is what DynamoDB's strongly-consistent reads and Spanner actually do, at a latency cost. Knowing that quorum is weaker than strong consistency is a genuine dividing line between candidates.
  • Last-write-wins is a data-loss policy, not a conflict-resolution strategy. It relies on wall-clock timestamps across machines whose clocks disagree by milliseconds or worse, so the "winner" may be the older write. Two concurrent writes are silently reduced to one with no record that the other existed. It is chosen because it is cheap and stateless, and it is correct only when losing a concurrent update is genuinely acceptable. Say that explicitly rather than presenting it as the default answer.
  • Compaction is where operational pain lives. It is background work that competes with foreground traffic for disk and CPU, so a compaction storm shows up as a latency spike with no change in request rate. Size-tiered compaction gives cheap writes and bad read amplification and needs up to 50% free disk headroom for a merge; levelled compaction gives good reads and much higher write amplification. Choosing between them by workload — and knowing the disk-headroom requirement — is real operator knowledge.
  • Tombstone lifetime is a correctness parameter with a trap. Tombstones must be retained longer than the maximum time a node can be down and rejoin, or a returning node will re-replicate its old value and the deleted data comes back. So the retention window couples your delete semantics to your operational practices: if a node is down for longer than the window, you must rebuild it from scratch rather than let it rejoin. This is a genuinely surprising constraint and volunteering it is strong.
  • Secondary indexes are the feature that breaks the model. The whole design rests on knowing which node owns a key. An index on a non-key attribute either lives locally on every node (so a query must scatter-gather across all 150 nodes, with latency set by the slowest) or is a separate global table (which must be kept consistent with the base table, and you have no cross-partition transactions to do it with). This is why these systems either lack indexes or offer them with prominent caveats — recognising that the limitation is structural rather than missing effort is the point.
  • Know when you do not need this. A single Postgres with a read replica handles tens of thousands of QPS and terabytes of data, gives you transactions, joins and secondary indexes for free, and one person can operate it. A distributed KV store costs you all of those and a team. Reach for it when a single node genuinely cannot hold the data or the write rate, or when you need multi-region availability — and be able to say where that line is.
`, drill:`Work it out

A cluster runs N=3, W=2, R=2 across three availability zones, one replica per zone. A network partition isolates zone C from A and B for 90 seconds. Clients can reach all three zones.

(a) What happens to writes from a client talking to zone A? To zone C? (b) What happens after the partition heals? (c) The team proposes W=1, R=1 "for latency". Evaluate.

Answer

(a) During the partition. A client at zone A can reach A and B, which is 2 nodes — W=2 is satisfiable, so writes succeed and reads with R=2 succeed. A client at zone C can reach only C, which is 1 node — W=2 cannot be met, so writes fail and R=2 reads fail too.

This is the CAP trade-off in concrete form: the majority side stays fully available, the minority side becomes unavailable, and the system has chosen consistency over availability for zone C's clients. Note that this is a consequence of the quorum arithmetic, not a separate design decision — choosing W=2 with N=3 is choosing to sacrifice the minority partition.

(b) After healing. Zone C's replica is 90 seconds stale for every key written during the partition. Three mechanisms converge it, at different speeds:

  • Hinted handoff — writes during the partition were acknowledged by A and B, and the coordinator stored hints for C. On reconnection those hints replay, usually within seconds. This is the fast path and it handles most of it.
  • Read repair — any read that includes C notices the version mismatch and pushes the newer value. This fixes hot keys quickly and cold keys never.
  • Merkle tree anti-entropy — a scheduled comparison hashes ranges on each replica and streams only the differing ranges. This is the backstop that catches what hints and reads missed, and it is why hints are an optimisation rather than a correctness requirement.

Crucially, no data is lost and no conflict arises here, because the minority side never accepted a conflicting write. Had W=1 been configured, both sides would have accepted writes to the same key and you would have a genuine conflict to resolve.

(c) Evaluating W=1, R=1. Latency does improve — you wait for one node rather than two, removing the slowest-of-two effect, which at p99 is a substantial win. But R+W = 2, which is not greater than N = 3, so the read set and write set need not intersect, and the consequences are concrete:

  • Stale reads are routine, not exceptional. Write to node A, read immediately from node B, get the old value. A user changes a setting and sees it revert.
  • Both sides of a partition accept writes, so you now genuinely need conflict resolution — and if that is last-write-wins on unsynchronised clocks, one of the two writes is silently discarded.
  • An acknowledged write can be lost. W=1 means one node confirmed it; if that node dies before replicating, the write is gone despite having been acknowledged to the client.

The response to give: not "no", but "per operation". W=1/R=1 is right for high-volume, loss-tolerant, self-correcting data — telemetry, view counts, cache-like values. Quorum is right for anything a user would notice reverting. The strength of this design is that N, R and W are chosen per request, so the answer is to route the latency-sensitive tolerant traffic one way and everything else the other — and to measure how much latency the quorum path actually costs before trading away correctness for a number nobody has measured.

Start here — a cache is a bet, and sometimes it loses

A cache stores the results of expensive operations so you do not repeat them. The bet is that the same data will be asked for again soon. When the bet pays off you serve from memory in under a millisecond instead of querying a database in twenty. When it fails, you have added a network hop for nothing.

The interesting part of this design is not the happy path — it is that a cache failure is usually worse than having no cache. A system sized assuming a 95% hit rate sends 20× its expected load to the database the moment the cache goes away, and the database falls over. The cache you added for performance has become a single point of failure for availability.

The vocabulary

  • Cache-aside (lazy loading) — the application checks the cache, and on a miss reads the database and populates the cache. The default. The cache never talks to the database itself.
  • Write-through — writes go to cache and database together, so the cache is never stale. Slower writes, and you cache data nobody may read.
  • Write-behind — write to cache, flush to database asynchronously. Fast, and you can lose data if the cache dies before flushing.
  • TTL — an expiry per entry. The crudest and most effective staleness control.
  • Eviction policy — what to discard when memory is full: LRU, LFU, or random. Redis uses approximate LRU by sampling, because exact LRU costs memory per key.
  • Hot key — one key taking a disproportionate share of traffic. The failure mode that a distributed cache cannot solve by adding nodes, because a key lives on exactly one node.
  • Thundering herd / stampede — many requests missing the same key simultaneously and all hitting the database.

The mental model

Treat the cache as an optimisation that must be allowed to fail. Every design decision follows from asking "what happens when this is empty, or gone, or wrong?" A system that is correct but slow without its cache is well designed. A system that is down without its cache has a distributed database it is calling a cache.

1 · Scope it — 0–5 min

  • In scope: a shared cache tier for many application servers; sub-millisecond reads; horizontal scale; survive node failure; bounded staleness.
  • Out of scope: using it as a primary datastore, as a queue, or as a lock service — all things Redis can do and all separate designs. Naming them and declining is good scoping.
  • Non-functional: p99 under 1 ms; the origin must survive a total cache loss; adding capacity must not invalidate everything.
  • The question to ask: "how stale can this data be?" Seconds, minutes, or must-be-exact changes the answer completely — and "must be exact" usually means the thing should not be cached at all.

2 · Numbers — 5–12 min

  • 1M reads/s at a 95% hit rate → 950,000 served from cache, 50,000/s reaching the database. Note immediately: if the hit rate drops to 80%, database load quadruples to 200,000/s. Cache hit rate is a load-bearing parameter for the tier behind it, and that sentence frames the whole design.

  • Network: 950,000 × 2 KB = 1.9 GB/s ≈ 15 Gbps out of the cache tier. Worth checking, because cache tiers frequently become network-bound before they become CPU-bound.

3 · Topology — 12–24 min

${flow([{t:"App + local cache",d:"microseconds, per-process"},{t:"Cache tier",d:"sharded, consistent hashing"},{t:"Replicas",d:"read scale + failover"},{t:"Origin",d:"database"}])}

Two levels, and say why. A small in-process cache in front of the shared tier removes a network hop entirely for the very hottest keys — which is precisely the traffic that would otherwise create a hot shard. The cost is that each process has its own copy, so invalidation is harder and staleness is per-process. Accept short TTLs locally (seconds) and treat it as a shock absorber, not a source of truth.

Sharding by consistent hashing, for exactly the reason from the key-value design: hash(key) % N means adding a node remaps nearly every key, so scaling up would empty the cache and instantly send full traffic to the database — turning a capacity increase into an outage. Consistent hashing with virtual nodes moves only 1/N of keys.

Client-side or proxy routing? A smart client computes the shard itself and connects directly — one hop, but every client needs the topology and must handle rebalancing. A proxy centralises that at the cost of a hop and a component to run. For a large fleet, a proxy is usually worth it; say which you chose and why.

4 · Invalidation and staleness — 24–34 min

Cache invalidation is hard because it is a distributed consistency problem wearing a performance costume. Options, worst to best:

  • TTL only. Data is stale for up to the TTL. Crude, but it self-heals, requires no coordination, and is right far more often than people expect.
  • Delete on write. When the database is updated, delete the cache key; the next read repopulates. Delete, do not update — updating means two writers can interleave and leave the cache holding an older value than the database, permanently. Deleting is idempotent and the repopulation reads the truth.
  • Change-data-capture. Tail the database's replication log and invalidate from it. This catches writes that bypassed the application, and it removes the dual-write problem where the database commits but the invalidation is lost.

The race worth naming: reader A misses, reads the database, and is paused by the scheduler. Writer B updates the database and deletes the cache key. Reader A resumes and writes its now-stale value into the cache, where it lives until the TTL expires. Mitigate with a short TTL always present as a backstop, or with a versioned write that refuses to overwrite a newer entry. Volunteering this race unprompted is a strong signal — it is the reason "always set a TTL, even when you invalidate explicitly" is a rule.

5 · The failure modes — 34–48 min

This section is the interview. Four named failures, each with a specific fix:

  • Cache stampede. A popular key expires and thousands of concurrent requests all miss and hit the database. Fix with single-flight: the first miss takes a short lock and repopulates while the others wait briefly. Add TTL jitter so keys populated together do not all expire together, and refresh-ahead so hot keys are renewed asynchronously before they expire and never have a miss window at all.
  • Hot key. One key at 100,000 requests/s saturates its single shard while the rest of the tier is idle. Adding nodes does not help — the key still hashes to one place. Fix by replicating the key under several suffixed names and picking randomly, or by relying on the local in-process cache, which absorbs exactly this pattern for free.
  • Cache penetration. Requests for keys that do not exist anywhere miss the cache and the database every time, so the cache provides no protection at all — and this is an easy attack. Fix by caching the negative result (a short-TTL "does not exist" marker) and by a bloom filter in front for known-absent keys.
  • Cache avalanche. The cache tier restarts empty, or a large fraction of keys expire at once, and the database takes full traffic. This is the one that causes outages. Fix with jittered TTLs, gradual warming rather than serving cold, and — most importantly — a rate limiter or admission control in front of the database, so a cold cache degrades latency instead of destroying the origin.

6 · Operations — 48–56 min

  • Replication and failover: each shard has a replica. On primary failure, promote — accepting that asynchronous replication may lose the last few writes, which is fine for a cache and would not be for a database.
  • The metrics that matter: hit rate (per key pattern, not just globally — a global 95% can hide a 40% on your most expensive query), p99 latency, evictions per second (rising evictions mean the working set no longer fits), and memory fragmentation.
  • Sizing: the right memory is where the hit-rate curve flattens. Plot hit rate against memory and find the knee; beyond it you are paying for cold data.
  • Deployment: never restart the whole tier at once. Rolling restarts with warm-up, and if possible a persistence snapshot so a restarted node comes back warm instead of empty.

The senior layer

  • A cache that the system cannot run without is not a cache, it is an undeclared database. The test is simple: can you flush the entire tier during business hours and survive on degraded latency?   • Facebook's memcache paper is the reference for the hard parts, and two of its ideas are worth knowing by name. Gutter pools handle node failure: rather than rehashing the ring (which would move keys and cause a correctness problem with in-flight invalidations), traffic for a dead node goes to a small standby pool with short TTLs, containing the blast radius.

This is why memcache uses a fixed hash with a failover pool rather than continuous rebalancing, and knowing that the standard answer has a caveat is a strong differentiator.

The cache reports a 0.3 ms round trip while the application spends 4 ms deserialising a large JSON blob into objects. Cache the smallest useful representation, prefer a compact binary format, and measure end to end from the application rather than trusting the cache's own latency numbers.

Replicating a cache across regions means cross-region invalidation, which is slow and lossy, so you get windows where regions disagree. The usual approach is independent per-region caches with short TTLs, accepting that a write in one region is stale in another for the TTL duration — and routing users consistently to one region so a single user does not see values flip back and forth. A product page service does 800,000 reads/s with a 96% cache hit rate. The database sustains 60,000 reads/s before latency degrades. Cache TTL is 300 seconds, set uniformly when an entry is created. A deploy restarts the entire cache tier at 14:00.

(a) What is normal database load? (b) What happens at 14:00? (c) Suppose instead the tier survives, but a product goes viral at 400,000 requests/s for one key. What happens, and what do you do?

Answer

(a) 4% of 800,000 = 32,000 reads/s to the database, about half its capacity. Comfortable, with headroom for a hit rate dropping to roughly 7.5% before the database is in trouble.

(b) The restart. The cache is empty, so the hit rate is 0% and all 800,000 reads/s hit the database — 13× its capacity. It queues, latency climbs, connections exhaust, timeouts begin. Clients retry, adding more load. The database is effectively down, and because every request now misses, the cache cannot repopulate either: requests time out before returning a value to cache. The system cannot recover on its own, which is the defining property of an avalanche and why it is worse than it first looks.

Worse, even once you restore it, the uniform 300-second TTL means everything populated in the recovery minute expires together five minutes later, producing a second avalanche. The uniform TTL turned a one-off incident into a recurring one.

What should have been in place, in order of importance:

  • Admission control on the database. Cap concurrent origin queries at, say, 50,000/s and fail or queue the rest quickly. The result is degraded service — some requests fail fast — rather than a dead database, and critically the cache can refill from the requests that do succeed, so the system heals.
  • Rolling restart with warm-up. Never restart the whole tier. Take one shard at a time, so at most 1/8 of traffic misses and the database sees 132,000/s... which is still over capacity, so combine with admission control.
  • TTL jitter — 300 seconds ± 20% randomised — so expiry is spread rather than synchronised. This is a one-line change that removes an entire class of incident.
  • Persistence or a warm standby so a restarted node comes back populated instead of empty.

(c) The viral key. 400,000 requests/s for one key all hash to one shard. That shard must serve 400,000/s against a per-node capacity of perhaps 125,000/s, so it saturates — and because it also holds 1/8 of all other keys, those become slow too. One key has degraded 12.5% of the entire cache. Adding shards does not help at all: the key still hashes to exactly one of them.

The fixes, in order of how fast you can apply them:

  • Local in-process cache with a 1–5 second TTL. Each app server caches this key itself, so the shared tier sees one request per server per TTL instead of 400,000/s. If you have 200 app servers and a 2-second TTL, that is 100 requests/s reaching the shard. This is by far the most effective fix and it needs no topology change.
  • Key replication — store the value under key:0 through key:9, and have clients read a random one. Traffic spreads across up to 10 shards. Invalidation now means deleting 10 keys, which is the cost.
  • Promote to the CDN or edge if the content is public and cacheable. A key at 400,000/s should probably not be reaching your infrastructure at all.

The connecting observation: parts (b) and (c) are the same lesson from opposite directions. Sizing by aggregate hit rate and aggregate capacity hides both failures — one is about what happens when the cache is absent, the other about what happens when load is skewed. Neither appears in a spreadsheet of averages, and both are the normal way cache tiers fail.

Start here — the deceptively simple requirement

"Send the user a notification." The complexity is that send hides five decisions the system must make every time: should we send this (preferences, quiet hours, frequency caps), which channel (push, email, SMS, in-app), what content (templating, localisation), when (now, batched, scheduled in the user's timezone), and what if it fails (retry, fall back to another channel, give up).

Meanwhile every delivery channel is a third party you do not control, each with different rate limits, latencies, failure modes and cost.

The vocabulary

  • Channel — push (APNs, FCM), email, SMS, in-app, webhook. Each has its own provider, cost and guarantees. SMS costs real money per message; push is free but unreliable.
  • Template — the message body with placeholders, versioned, per locale. Never build message strings in application code, or you cannot change copy without a deploy.
  • Preference — the user's opt-in state per notification type per channel. Legally significant, not merely a setting.
  • Deduplication — the same logical event may be produced twice; the user must be notified once.
  • Dead-letter queue (DLQ) — where messages go after exhausting retries, so they are inspectable rather than silently lost.
  • Digest — batching many notifications into one ("12 people liked your post") rather than sending twelve.

Separate what happened from what to send from how to deliver it. Producers emit domain events and know nothing about channels. A rules layer turns events into delivery intents. Channel workers turn intents into provider API calls. Keeping those three apart is what lets you add a channel, change a policy or swap a provider without touching anything else — and mixing them is why most in-house notification systems become unmaintainable.

  • In scope: many services trigger notifications; route by user preference to the right channels; template and localise; deliver reliably; track outcomes; respect frequency caps and quiet hours.
  • Out of scope: the marketing campaign tool, the in-app inbox UI, analytics dashboards. Say so.

  • The question that splits the design: "transactional or marketing?" Transactional is low-volume, latency-critical and must not be deduplicated away. Marketing is high-volume, batchable, and must respect consent and frequency caps rigorously. Many teams build one system for both and it serves neither — flag that.

2 · Numbers — 5–12 min

  • 100M users, average 5 notifications/day = 500M/day ≈ 5,800/s average. But it is spiky: a broadcast to 50M users is 50M messages that must be produced in minutes, so design for peaks of 200,000/s with the queue absorbing the difference.

${flow([{t:"Producers",d:"emit domain events"},{t:"Event queue",d:"Kafka, durable"},{t:"Rules engine",d:"preferences, caps, dedup"},{t:"Renderer",d:"template + locale"},{t:"Channel queues",d:"one per channel"},{t:"Workers",d:"call provider, retry"}])}

Producers emit events, not notifications. The orders service publishes order.shipped; it does not decide that this means a push notification. That decision belongs to the rules layer, so a product manager can change it without a code change in the orders service. This separation is the main architectural point of the design.

A queue per channel, not one shared queue. Channels have wildly different rates, latencies and failure modes: a stuck SMS provider must not block push delivery. Separate queues give independent scaling, independent rate limiting, and independent backpressure.

4 · Preferences, caps and dedup — 26–36 min

Preferences are a matrix of user × notification type × channel, plus global switches (do not disturb, unsubscribe all). Two rules to state:

  • Default carefully and record consent. Marketing must be opt-in with an auditable record of when and how; transactional notifications generally cannot be disabled (you must be able to tell someone their password changed). Getting this wrong is a legal problem, not a bug.
  • Check preferences as late as possible — at dispatch, not at event time. A user who unsubscribes while a batch is queued must not receive the queued messages.

Frequency capping — no more than N notifications per user per hour or day, with priority so that a transactional message is never suppressed by a marketing cap. Implement as a per-user counter with a sliding window, which is exactly the rate-limiter design applied to a different resource.

Deduplication uses an idempotency key derived from the event: (user_id, event_type, entity_id) within a time window. Because the event queue gives at-least-once delivery, the same event will be processed twice, and without this the user gets two identical messages. Store keys in a short-TTL store and check before dispatch.

Digesting is the quality feature. Rather than twelve "someone liked your post" notifications, hold them in a short window and collapse into one. Implement as a per-user, per-type buffer with a flush timer — the same dual-trigger pattern as the batching queue: flush when the window closes or when the buffer is full.

5 · Delivery and tracking — 36–48 min

Each channel worker owns one provider integration and applies its own rate limit, retry policy and circuit breaker. Points to make:

  • Retries must distinguish permanent from transient. An invalid device token, an unsubscribed email or a disconnected number is permanent — retrying wastes quota and harms sender reputation. Mark the destination invalid and stop. A 429 or 503 is transient and should back off with jitter.
  • Token lifecycle: push tokens expire and rotate constantly. Providers report invalid tokens in their response or via a feedback channel, and you must prune them. A system that keeps sending to dead tokens degrades its own delivery rates with the provider.
  • Channel fallback — if push is not delivered within N minutes, try email. This needs a delivery receipt, which push does not reliably give you, so it is usually implemented as "no app-open event within the window" rather than true delivery confirmation. Be honest about that limitation.
  • Tracking is a funnel: accepted → sent to provider → provider accepted → delivered → opened → clicked. Each stage can fail and you need per-stage metrics per channel and per template to spot a broken template or a degraded provider quickly.

6 · Failure — 48–56 min

  • Provider outage: circuit-break, queue, and drain when it recovers. For transactional messages consider a secondary provider; for marketing, just wait. Never drop silently.
  • The dead-letter queue is a first-class component with an owner and an alarm. Messages arriving there must be inspectable and replayable, and a growing DLQ is an incident, not a statistic.
  • The broadcast spike: 50M messages produced in minutes. The queue absorbs it; workers drain at whatever rate providers allow. Crucially, keep a separate high-priority path for transactional messages so a marketing blast cannot delay a password reset behind 50M queued items. This is the single most important operational design decision here.
  • The duplicate storm: a producer bug replays an event topic and 10M users get a notification twice. Dedup keys catch it if the window is long enough; a global kill switch per notification type is the emergency control you want to have built beforehand.
  • Timezone correctness: "send at 9am local" for 100M users across every timezone means a scheduler that shards by timezone and runs continuously, not a nightly cron. Quiet hours have the same shape.

The real figure matters more: SMS is 5% of the campaign and takes more than twice as long as push, because the carrier limit is an external constraint you cannot scale around by adding workers.

(b) The password reset at 10:01 — this is the important part. If transactional and marketing share a queue, that password reset is behind roughly 27 million queued push messages. At 15,000/s it waits ~30 minutes. The user requested a reset, received nothing, requested again, received nothing, and has filed a support ticket before the first message arrives. The system is not down, no error was logged, and every metric looks healthy — throughput is at capacity and the queue is draining normally.

This is head-of-line blocking, and it is the most common real failure in notification systems. The fixes:

  • Separate priority queues per channel — a transactional push queue and a marketing push queue, with workers servicing transactional first and only draining marketing with spare capacity. A password reset then waits milliseconds regardless of what marketing is doing.
  • Separate provider connections or accounts, so transactional throughput is not consumed by the campaign and — for email — so marketing complaint rates cannot damage the sending reputation your password resets depend on.
  • Rate-limit the campaign to leave deliberate headroom, e.g. cap marketing at 12,000/s of the 15,000/s push capacity. The campaign takes 39 minutes instead of 31, which nobody notices, and transactional latency is protected.

(c) SMS cost. 2M × £0.028 = £56,000 for one campaign. Against push, which is free, and email at a fraction of a penny. SMS is 5% of the messages and essentially all of the cost.

What to change, in order:

  • Do not use SMS for marketing at all unless the user explicitly chose it and the message justifies the cost. Reserve SMS for transactional cases where reachability genuinely matters — two-factor codes, delivery arrival, fraud alerts.
  • Channel selection by value, with fallback. Send push first; fall back to SMS only for users with no active push token and only for high-value notifications. That might cut SMS volume by 90%.
  • Put a spend cap in the rules engine with a hard stop and an alert. A bug that routes 40M messages to SMS instead of push is a £1.1M incident that would complete before anyone noticed — the queue would drain for 22 hours at the carrier limit, which is your only accidental protection. Make it a deliberate control rather than a lucky one.

The lesson: in this design the two things that actually hurt you — head-of-line blocking of critical messages, and per-message cost on one channel — are both invisible in a throughput-oriented capacity plan. Priority separation and a spend cap are cheap to build beforehand and impossible to add during the incident.
