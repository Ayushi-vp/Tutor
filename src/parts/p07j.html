Start here — the problem in one sentence

Producers add items, consumers remove them, the queue has a maximum size. A producer facing a full queue must wait rather than fail or spin; a consumer facing an empty queue must do the same. Both must wake as soon as the situation changes.

This is the foundation under thread pools, batching servers, logging appenders and every pipeline in this section — so interviewers ask it directly, and they ask it because the obvious implementation is subtly wrong in three specific ways.

Why the naive versions fail

  • Busy-waiting — while queue.full(): pass. Correct and it burns a core doing nothing, starving the very consumer that would make room.
  • Sleeping — while full: sleep(10ms). Better, and it adds up to 10 ms of latency to every handoff while still waking pointlessly.
  • A plain lock — a mutex gives mutual exclusion but no way to wait for a condition. You need a condition variable: release the lock, sleep, and reacquire atomically when signalled.

The vocabulary

  • Condition variable — a wait queue attached to a lock. wait() atomically releases the lock and blocks; notify() wakes one waiter, notify_all() wakes all. The atomicity is the whole point: without it there is a window between checking the condition and sleeping in which a signal is lost.
  • Spurious wakeup — a thread can return from wait() without anyone signalling it. Permitted by the specification on most platforms, which is why you re-check the condition in a loop.
  • Lost wakeup — a signal sent while no one is waiting is discarded. Signalling without holding the lock is how you produce one.

Requirements

put(item) blocks while full, take() blocks while empty, both thread-safe with any number of producers and consumers, plus timed variants and a clean shutdown. Clarify: FIFO or priority? Must put be fair, or may a producer be starved? Is there a maximum wait?

The implementation

class BoundedQueue:
    def __init__(self, capacity):
        self.items = deque()
        self.capacity = capacity
        self.lock = threading.Lock()
        self.not_full  = threading.Condition(self.lock)
        self.not_empty = threading.Condition(self.lock)
        self.closed = False

    def put(self, item, timeout=None):
        with self.not_full:
            deadline = time.monotonic() + timeout if timeout else None
            while len(self.items) >= self.capacity and not self.closed:
                remaining = deadline - time.monotonic() if deadline else None
                if remaining is not None and remaining <= 0:
                    raise Timeout
                if not self.not_full.wait(remaining):
                    raise Timeout
            if self.closed: raise QueueClosed
            self.items.append(item)
            self.not_empty.notify()        # exactly one consumer can proceed

    def take(self, timeout=None):
        with self.not_empty:
            while not self.items and not self.closed:
                if not self.not_empty.wait(timeout): raise Timeout
            if not self.items: raise QueueClosed
            item = self.items.popleft()
            self.not_full.notify()
            return item

    def close(self):
        with self.lock:
            self.closed = True
            self.not_full.notify_all(); self.not_empty.notify_all()

The three decisions that matter

  • while, never if. Two reasons, and name both: spurious wakeups mean wait() can return unsignalled, and — more importantly — between being signalled and reacquiring the lock, another thread may have taken the item. The condition must be re-verified after waking, not assumed.
  • Two condition variables on one lock. One shared condition would mean waking producers when an item is added, which is pointless. Separate conditions wake only the threads that can actually make progress. With a single condition you must use notify_all, which produces a thundering herd of threads that check, fail and sleep again.
  • Signal while holding the lock. Releasing first opens a window in which a waiter checks the condition, finds it false, and sleeps just after the signal was sent — a lost wakeup that deadlocks both sides.

Extensions

  • Batch take: drain up to n items in one lock acquisition. For a consumer that processes in batches this cuts lock traffic by a factor of n and is what the batching-server design needs.
  • Priority: replace the deque with a heap. Note that put becomes O(log n) and FIFO fairness is gone — a low-priority item can starve indefinitely.
  • Lock-free via a ring buffer with atomic head and tail indices. Faster under extreme contention, far harder to get right, and it cannot block — so it needs a separate wait strategy. Mention it as an option, do not attempt it in 45 minutes.
`, deep:`

The senior layer

  • Shutdown is the part that separates a toy from something usable. A blocked consumer waiting on an empty queue will wait forever unless something wakes it. The closed flag plus notify_all is the mechanism, and the semantics need deciding: does close mean "drain what is queued then stop" (graceful) or "stop now" (abrupt)? The version above lets consumers drain remaining items and then raises — usually what you want, and worth stating as a deliberate choice rather than an accident.
  • Fairness is not free and usually not needed. Most condition variables wake an arbitrary waiter, so a producer can in principle be starved while others repeatedly win the race. A fair queue hands the lock to the longest waiter, at a measurable throughput cost because it forces a context switch rather than letting a running thread reacquire. Default to unfair, and say you would only make it fair if starvation were observed — this is the same trade as an unfair mutex and the reasoning transfers.
  • notify versus notify_all is a correctness question, not an optimisation. Single-notify is safe here only because every waiter on not_empty waits for the same condition and one item satisfies exactly one of them. The moment waiters wait for different conditions on the same variable — for instance a batch-take wanting n items while a single-take wants one — signalling one thread can wake the wrong one, which then sleeps again and the item sits untaken. That is a lost wakeup caused by an over-optimisation, and it is worth naming as the reason to be conservative.
  • The queue's capacity is a backpressure policy in disguise. Unbounded means producers never block and memory grows without limit under overload — the failure from the batching-server design. Bounded means producers block, which propagates backpressure up the pipeline to whatever is feeding them. That propagation is the feature: it is how a system slows down instead of falling over, and choosing the capacity is choosing how much burst you absorb before applying it.
  • Test it with a property, not an example. Run k producers and m consumers over random items, then assert that the multiset of items taken equals the multiset put, that the queue never exceeded capacity (check under the lock), and that the process terminates. Concurrency bugs appear under specific interleavings that no hand-written test reproduces, so randomised stress plus a thread sanitiser finds them and unit tests do not.

Consider this take:

There is one condition variable shared by producers and consumers. Find three distinct bugs and describe a failing interleaving for each.

Answer

Bug 1 — if instead of while.

Interleaving: consumers C1 and C2 both find the queue empty and wait. A producer adds one item and calls notify_all (or the runtime wakes both spuriously). C1 wakes, reacquires the lock, and pops the item. C2 then wakes, reacquires, and — because it used if — does not re-check. It calls popleft() on an empty deque and raises IndexError.

This is the canonical failure and it happens whenever more waiters wake than there are items. Even with single-notify, spurious wakeups alone can produce it. Fix: while not self.items: self.cond.wait().

Bug 2 — one condition variable for two different conditions.

Producers wait for "not full" and consumers wait for "not empty", but both sleep on self.cond. Interleaving: the queue is full, so producers P1 and P2 are waiting. A consumer takes an item and calls notify() on that same variable — which wakes one arbitrary waiter. If it wakes another consumer rather than a producer, that consumer finds the queue non-empty, takes an item, and signals again; but the producers may never be selected. With a single notify on a shared variable, a signal intended for a producer can be consumed by a consumer and the wakeup is lost — producers block forever although there is room.

Note the code compounds this by signalling self.not_full while waiters sleep on self.cond — a signal sent to a variable nobody is waiting on is simply discarded. Fix: two condition variables over one lock, each signalled by the operation that satisfies it.

Bug 3 — no shutdown path.

Interleaving: the application is stopping. Producers have finished and no more items will arrive. Every consumer is blocked inside wait() with no one left to signal them. They wait forever, the threads never exit, and if they are non-daemon threads the process never terminates. Nothing throws and nothing logs — the service simply hangs on shutdown, which is a genuinely common production symptom.

Fix: a closed flag checked in the wait predicate, and a close() that sets it and calls notify_all on both conditions so every blocked thread re-evaluates and exits.

A fourth worth mentioning: there is no timeout, so a consumer cannot be interrupted, cannot report that it is stuck, and cannot participate in a bounded shutdown. Timed variants are not a nicety — they are what makes the component observable and controllable from outside.

The pattern to carry away: every condition-variable use has the same skeleton — acquire the lock, loop while the predicate is false calling wait(), act, signal the condition you just made true, release. Deviating from that skeleton in any of the three ways above produces a bug that appears under load and not in testing.

Start here — why a pool rather than a thread per task

Creating a thread costs roughly a megabyte of stack and a system call, and a thousand runnable threads spend more time context-switching than working. A pool creates a fixed number of workers once and feeds them tasks through a queue, so thread creation cost is paid once and concurrency is bounded by design.

The bounded part matters as much as the reuse: a pool is a concurrency limiter. Ten workers means at most ten tasks touch the database at once, which is backpressure you get for free.

The vocabulary

  • Future / promise — a handle to a result that does not exist yet. The caller can wait on it, poll it, or attach a callback. It also carries the exception if the task threw, which is how errors cross the thread boundary.
  • Graceful shutdown — stop accepting new tasks, let queued and running ones finish, then exit.
  • Poison pill — a sentinel value placed on the queue that tells a worker to exit. One per worker.
  • Rejection policy — what submit does when the queue is full: block, throw, discard, or run the task on the caller's thread.

The thing that goes wrong

Exceptions. If a task throws and the worker does not catch it, the worker thread dies. Do that four times and your eight-thread pool silently becomes a four-thread pool, then zero, and tasks queue forever with no error anywhere. A worker loop must catch everything.

The implementation

class Future:
    def __init__(self):
        self._cond = threading.Condition()
        self._done, self._value, self._exc, self._cancelled = False, None, None, False
    def set_result(self, v):  self._finish(value=v)
    def set_exception(self, e): self._finish(exc=e)
    def _finish(self, value=None, exc=None):
        with self._cond:
            self._value, self._exc, self._done = value, exc, True
            self._cond.notify_all()
    def result(self, timeout=None):
        with self._cond:
            while not self._done:
                if not self._cond.wait(timeout): raise Timeout
        if self._exc: raise self._exc      # re-raise in the caller's thread
        return self._value

class ThreadPool:
    def __init__(self, n_workers, queue_size=1000, on_reject='block'):
        self.q = BoundedQueue(queue_size)
        self.on_reject, self.shutdown_flag = on_reject, False
        self.workers = [threading.Thread(target=self._run, daemon=False)
                        for _ in range(n_workers)]
        for w in self.workers: w.start()

    def submit(self, fn, *args):
        if self.shutdown_flag: raise RejectedExecution("pool is shut down")
        fut = Future()
        if not self.q.offer((fn, args, fut)):
            return self._reject(fn, args, fut)
        return fut

    def _run(self):
        while True:
            job = self.q.take()
            if job is POISON: return
            fn, args, fut = job
            try:
                fut.set_result(fn(*args))
            except BaseException as e:
                fut.set_exception(e)      # worker survives; caller sees it

The try/except around fn() is the most important line in the class. Catching BaseException rather than Exception is deliberate — a task raising something outside the normal hierarchy would otherwise kill the worker.

Shutdown

def shutdown(self, wait=True, timeout=None):
    self.shutdown_flag = True            # 1. reject new submissions
    for _ in self.workers:
        self.q.put(POISON)                # 2. one pill per worker
    if wait:
        for w in self.workers:
            w.join(timeout)               # 3. wait, bounded
            if w.is_alive(): log.warning("worker did not stop")

One poison pill per worker, placed at the back of the queue, so every queued task is processed before any worker sees a pill. That gives drain-then-stop semantics for free. An immediate shutdown instead drains the queue, cancels the pending futures, and signals running tasks to stop — which they can only honour if they check a cancellation flag.

Rejection policies

  • Block — the caller waits for room. Propagates backpressure; risks stalling a request thread.
  • Abort — throw immediately. Honest and lets the caller decide.
  • Caller-runs — the submitting thread executes the task itself. Elegant: it slows the producer by exactly the cost of the work, which is self-regulating backpressure.
  • Discard — drop the task. Only acceptable when the work is genuinely optional, such as metrics.

The senior layer

  • Pool size is set by the workload, and the formula is worth quoting. For CPU-bound work, roughly the number of cores — more threads just add context switches. For I/O-bound work, cores × (1 + wait_time / service_time): if a task spends 90 ms waiting and 10 ms computing, the ratio is 9, so ~10 threads per core keeps the CPU busy. Getting this backwards — 200 threads for CPU work, or 4 for I/O work — is the most common sizing mistake and each fails in a different way.
  • Non-daemon workers plus a shutdown hook, not daemon threads. Daemon threads let the process exit with tasks half-finished, which for anything writing data is a correctness problem. Non-daemon threads keep the process alive until they stop, which means you must implement shutdown properly — and that pressure is a feature. Register the shutdown at exit so it happens even on an unhandled error path.
  • Never submit a task that waits on another task in the same pool. If the pool has N workers and N tasks each block waiting for a subtask they submitted, every worker is blocked and no worker is free to run the subtasks. The pool deadlocks with an empty CPU and a full queue. This is thread-pool starvation, it is not detected by anything, and the fixes are a separate pool for nested work or a design that does not nest. Raising it unprompted is a strong signal.
  • Cancellation is cooperative and you should say so plainly. A future can be cancelled before it starts by removing it from the queue. Once a task is running, there is no safe way to stop it from outside — killing a thread mid-operation leaves locks held and state inconsistent. So a long task must periodically check a cancellation flag, and cancel() returning False for a running task is honest rather than a limitation.
  • Unbounded queues turn a thread pool into a memory leak. The default in several standard libraries is an unbounded queue, which means submit never blocks, backpressure never propagates, and under overload the queue grows until the process dies — having accepted work it will never complete. Bounding the queue and choosing a rejection policy is the single most important configuration decision, and it is the same lesson as the batching server and the logging appender.

A web service uses an 8-thread pool with an unbounded queue for outbound HTTP calls. Each call normally takes 50 ms. Traffic is 200 requests/s, one pool task each. The downstream service degrades and calls now take 5 seconds.

(a) What is the pool's throughput before and after? (b) What happens to the queue and to memory? (c) What should the configuration have been?

Answer

(a) Throughput. Little's Law: throughput = concurrency ÷ service time.

  • Normal: 8 ÷ 0.05 s = 160 tasks/s. Against 200/s arriving, the pool is already slightly undersized — the queue grows even in the healthy case, at 40/s. Worth noticing before the incident: this pool was on the edge and nobody could tell, because an unbounded queue absorbs the difference silently until memory runs out.
  • Degraded: 8 ÷ 5 s = 1.6 tasks/s. Throughput has fallen by a factor of 100 while arrivals are unchanged.

(b) Queue and memory. The queue grows at 200 − 1.6 ≈ 198 tasks/s. After one minute it holds ~12,000 tasks; after ten minutes, ~119,000. Each holds a closure, its arguments and a future, plus whatever request context they capture — if that is a kilobyte each, ten minutes is roughly 120 MB of tasks that will never usefully complete.

The insidious part is what happens to latency. A task submitted after ten minutes sits behind 119,000 others at 1.6/s — a queueing delay of over 20 hours. Every one of those requests has long since timed out at the client, so the pool is spending its entire capacity on work nobody is waiting for. Meanwhile the request threads that submitted them may still be blocked holding connections.

Outcome: memory climbs until the process is killed, and before that every request is failing by timeout. No error is raised by the pool itself — submit succeeds every time, which is exactly the problem.

(c) What it should have been.

  • A bounded queue sized to a few seconds of work — at 160/s and a 2-second tolerance, roughly 300 entries. Beyond that, reject. The pool then fails fast and visibly instead of accumulating.
  • Rejection policy: abort, not block. Throwing lets the calling request return a 503 immediately, which is a far better outcome than a request thread blocked for hours. Caller-runs would be wrong here, because it would push a 5-second downstream call onto a request thread.
  • A per-task timeout, so a 5-second call is abandoned at, say, 1 second. This alone restores throughput to 8 tasks/s and caps the damage.
  • Drop tasks whose deadline has passed at dequeue time — if the client gave up 20 hours ago, executing the task is pure waste. Same lesson as the batching-server queue.
  • A circuit breaker on the downstream service, so once it is clearly degraded you stop calling it entirely and fail fast rather than filling the pool.
  • Size the pool properly: this is I/O-bound with a 50 ms wait and negligible compute, so 8 threads was far too few. Even at 200/s with 50 ms service time you need ≥10 concurrent, and headroom suggests 20–30.

The principle: an unbounded queue converts a latency problem in a dependency into a memory and availability problem in your own service. Bounding it and rejecting early keeps the failure where it started and keeps it visible.

Start here — why pool connections at all

Opening a database connection costs a TCP handshake, a TLS negotiation and an authentication round trip — commonly 20–100 ms. If every query pays that, your 2 ms query takes 50 ms. Worse, databases cap concurrent connections, and a service that opens one per request will exhaust that cap and lock out everything else.

So: keep a set of open connections, hand them out, take them back. The pool is simultaneously a performance optimisation and a concurrency limit on the database, and the second is the more important one.

The failure that defines the design

Connection leaks. A caller borrows a connection and does not return it — an early return, an exception on a path without cleanup, a forgotten close(). Each leak permanently shrinks the pool. Nothing fails immediately; the pool just gets smaller until, some hours later, every request blocks waiting for a connection that will never come back. The symptom is a total outage with no obvious cause and no recent deploy.

The vocabulary

  • Borrow / return — the two operations. Enforced with a context manager or try/finally so the return cannot be skipped.
  • Validation — checking a connection still works before handing it out. Databases and load balancers close idle connections without telling you.
  • Max lifetime — retire a connection after a fixed age regardless of health, so the pool rotates rather than accumulating long-lived connections that a proxy may silently drop.
  • Leak detection — warn when a connection has been held longer than any legitimate operation should take.

The implementation

class PooledConn:
    conn, created_at, last_used_at, borrowed_by, borrowed_at

class ConnectionPool:
    def __init__(self, factory, max_size=20, min_idle=5,
                 max_lifetime=1800, idle_timeout=600, borrow_timeout=5,
                 leak_threshold=30, clock=time.monotonic):
        self.factory, self.max_size, self.clock = factory, max_size, clock
        self.idle = deque()                  # available PooledConns
        self.in_use = {}                     # id -> PooledConn
        self.total = 0
        self.lock = threading.Lock()
        self.available = threading.Condition(self.lock)

    def borrow(self):
        deadline = self.clock() + self.borrow_timeout
        with self.available:
            while True:
                while self.idle:
                    pc = self.idle.popleft()
                    if self._expired(pc) or not self._validate(pc):
                        self._destroy(pc); continue
                    self._mark_borrowed(pc); return pc
                if self.total < self.max_size:
                    pc = self._create()      # grow on demand
                    self._mark_borrowed(pc); return pc
                remaining = deadline - self.clock()
                if remaining <= 0: raise PoolExhausted
                self.available.wait(remaining)

    def release(self, pc, broken=False):
        with self.available:
            self.in_use.pop(id(pc), None)
            if broken or self._expired(pc):
                self._destroy(pc)
            else:
                pc.last_used_at = self.clock()
                self.idle.append(pc)
            self.available.notify()

    @contextmanager
    def connection(self):
        pc = self.borrow(); broken = False
        try:
            yield pc.conn
        except ConnectionError:
            broken = True; raise
        finally:
            self.release(pc, broken)

The context manager is the API you expose, and the raw borrow/release should be discouraged or private. A finally the caller cannot forget removes the entire leak class by construction, which is far better than detecting leaks after the fact.

Validation strategy

  • On borrow — safest, and it costs a round trip per borrow. Mitigate by skipping validation for connections used within the last few seconds.
  • On return — cheaper in the hot path, but a connection can die while idle afterwards.
  • Background — a keeper thread pings idle connections periodically and evicts dead ones. Best of both, and it also maintains min_idle.

Combine: background validation for idle connections, plus a cheap age check on borrow, plus honest error handling if a query fails on a connection that looked fine.

Leak detection

def _check_leaks(self):
    now = self.clock()
    for pc in list(self.in_use.values()):
        held = now - pc.borrowed_at
        if held > self.leak_threshold and not pc.leak_reported:
            log.warning("possible leak: held %.1fs by %s", held, pc.borrowed_by)
            pc.leak_reported = True

Capture a stack trace at borrow time (only when leak detection is enabled — it is expensive) so the warning points at the code that took the connection. That single feature turns an unreproducible 3am outage into a one-line fix.

The senior layer

  • Bigger pools are usually slower, which is counterintuitive and true. A database has a fixed number of cores and disks; beyond that, more concurrent connections cause context switching, lock contention and cache thrashing inside the database, so total throughput falls. The widely-cited starting formula is connections = cores × 2 + effective_spindles — often a pool of 10 to 20 for a machine that people instinctively give 200. Being able to say that a smaller pool frequently improves p99 latency is a genuinely counterintuitive, checkable piece of knowledge.
  • The pool size is your concurrency limit on the database, so treat it as a shared budget. Ten service instances each with a 50-connection pool present 500 connections to one database, which may exceed its limit and lock out migrations, monitoring and everyone else. Size pools by dividing the database's safe concurrency across all consumers, and reserve headroom for administrative connections. This is a capacity conversation between services, not a per-service setting.
  • Max lifetime exists because of things between you and the database. Load balancers, NAT gateways and firewalls silently drop idle TCP connections after a few minutes, and the client does not find out until the next query fails with a confusing error. Retiring connections after a lifetime shorter than the shortest infrastructure timeout means the pool rotates before anything else drops them. Set it to a few minutes less than the network idle timeout, and mention that this is why "the first query after lunch always fails" is a classic symptom.
  • Transactions turn a leak into a much worse problem. A connection returned with an open transaction carries locks and an uncommitted snapshot to the next borrower, causing bizarre cross-request behaviour and blocking other writers. The pool must roll back on return unless the caller explicitly committed — defensive, cheap, and it converts a silent corruption into a clean reset.
  • Test with an injected clock and a fake factory. Expiry, idle timeout and leak detection are all time-dependent, so a controllable clock lets you assert exact behaviour at the boundary without sleeping. A factory that can be told to produce broken connections lets you test the validate-and-replace path, which is otherwise only exercised during an incident.

  • Pool metrics as first-class monitoring: connections in use, idle, and pending borrows. A steadily rising in-use count with flat traffic is unmistakable and is visible from the first ten minutes. Most teams monitor the database and not the pool, which is why this class of incident is common.
  • Alert on borrow wait time, not just failures. Waits appear long before exhaustion.
  • A max lifetime would eventually retire leaked connections — but note it does not help here: max lifetime applies on return, and a leaked connection is never returned. Worth stating, because it is a plausible-sounding fix that does not work.

The lesson: resource pools fail slowly and then all at once, in a component nobody is watching, triggered by code unrelated to the symptom. Make the safe usage the only usage, and instrument the pool itself.

Start here — why a plain mutex is wasteful

A mutex serialises everything. But if a data structure is read far more than it is written — a configuration map, a routing table, a cache — then readers do not conflict with each other at all. Only a writer needs exclusivity.

A read-write lock encodes that: any number of readers, or exactly one writer, never both. With a 95% read workload this can be a large throughput win.

The problem you must solve, not avoid

Readers arrive continuously. A writer waits for the current readers to finish — but new readers keep arriving and keep being admitted, so the reader count never reaches zero and the writer waits forever. That is writer starvation, and it is not a corner case; it is the normal behaviour of the naive implementation under read-heavy load, which is exactly the load this lock is for.

The three policies

  • Reader-preferring — admit a reader whenever no writer holds the lock. Maximum read throughput, and writers can starve indefinitely.
  • Writer-preferring — once a writer is waiting, block new readers. Writers cannot starve; a stream of writers can starve readers.
  • Fair (FIFO) — serve in arrival order. Neither starves, and throughput is lower because a single waiting writer stops readers from batching.

There is no universally correct answer. Writer-preferring is the right default, because writes are usually rare and latency-sensitive, and a starved writer is a far worse outcome than slightly delayed readers.

Requirements

acquire_read, release_read, acquire_write, release_write, thread-safe, no starvation of writers, with context managers. Clarify: reentrant? Can a reader upgrade to a writer? Both answers have sharp edges and should be discussed rather than assumed.

Writer-preferring implementation

class ReadWriteLock:
    def __init__(self):
        self._lock = threading.Lock()
        self._ok_to_read  = threading.Condition(self._lock)
        self._ok_to_write = threading.Condition(self._lock)
        self._readers = 0          # currently reading
        self._writer = False       # a writer holds the lock
        self._waiting_writers = 0  # the key to writer preference

    def acquire_read(self):
        with self._lock:
            # yield to any waiting writer — this is the whole policy
            while self._writer or self._waiting_writers > 0:
                self._ok_to_read.wait()
            self._readers += 1

    def release_read(self):
        with self._lock:
            self._readers -= 1
            if self._readers == 0:
                self._ok_to_write.notify()      # exactly one writer

    def acquire_write(self):
        with self._lock:
            self._waiting_writers += 1
            try:
                while self._writer or self._readers > 0:
                    self._ok_to_write.wait()
                self._writer = True
            finally:
                self._waiting_writers -= 1

    def release_write(self):
        with self._lock:
            self._writer = False
            if self._waiting_writers > 0:
                self._ok_to_write.notify()      # next writer first
            else:
                self._ok_to_read.notify_all()   # let the herd of readers in

The three decisions

  • _waiting_writers in the reader's wait predicate is the entire writer-preference policy, in one clause. Remove it and you have a reader-preferring lock with the starvation bug.
  • notify for writers, notify_all for readers. Only one writer can proceed, so waking more is waste. All waiting readers can proceed together, which is the point of the lock — waking one at a time would serialise them and throw away the benefit.
  • Decrement _waiting_writers in a finally. If the wait is interrupted or times out and the counter is not decremented, readers are blocked forever by a writer that no longer exists. A permanent deadlock caused by an error path.

Extensions and their traps

  • Upgrade (read → write) is a deadlock generator: two readers both requesting an upgrade each wait for the other to release its read lock, and neither can. Either forbid it, or allow only one designated upgradeable reader at a time.
  • Reentrancy: a thread acquiring the read lock twice is fine unless a writer starts waiting in between — then the second acquire blocks on a lock the same thread already holds. Track per-thread hold counts if you must support it, and prefer to forbid it.
  • Timed acquisition so a caller can give up rather than block indefinitely, which also makes the lock debuggable.
`, deep:`

The senior layer

  • A read-write lock is often slower than a plain mutex, and knowing when is the mark of experience. It maintains more state, so acquisition is more expensive, and the reader counter is itself a contended cache line that every reader writes to — on a many-core machine that single line ping-pongs between caches and can cost more than the critical section it protects. The win only materialises when critical sections are long and reads genuinely dominate. For a short read of a few fields, a plain mutex is usually faster. Measure rather than assume.
  • Copy-on-write is frequently the better answer for read-heavy data. If writes are rare, keep an immutable structure behind an atomic reference: readers take the reference with no lock at all and no cache-line contention, and a writer builds a new copy and swaps the pointer. Readers holding the old version continue safely. Cost is the copy per write and a window where readers see slightly stale data. For a configuration map read millions of times a second and written once an hour, this is enormously better than any lock — and proposing it shows you are solving the problem rather than implementing the requested primitive.
  • Writer preference is the default, but the decision belongs to the workload. If writers are frequent, writer preference makes readers starve instead, and you have moved the problem. If both are frequent you probably want a fair lock — or, better, to reconsider whether a read-write lock is the right tool at all, since heavy contention on both sides suggests sharding the data so that different threads touch different locks.
  • Invariants worth asserting: readers and writer are never both non-zero; the writer flag is never true with readers greater than zero; waiting-writer count is never negative. Check them under the lock in a debug build and the classic bugs surface on the first stress test rather than in production.
  • Test for starvation explicitly, not just for correctness. A correctness test passes on the reader-preferring implementation. The test that matters runs a continuous stream of readers with one writer and asserts the writer acquires within a bounded time. Without that test, the starvation bug ships — and it is the reason the lock was written in the first place.
`, drill:`Work it out

A routing table is read on every request (200,000 reads/s, each holding the lock ~200 ns) and updated on config change (about 10 writes/hour, each taking ~50 µs). The team has implemented a reader-preferring read-write lock.

(a) Will the writer starve? (b) Is the read-write lock helping? (c) What would you use instead?

Answer

(a) Will the writer starve? Almost certainly yes, and the arithmetic shows why. Reads arrive every 5 µs on average and each holds the lock for 200 ns. For the reader count to reach zero, there must be a gap in arrivals longer than the current readers need to drain. With Poisson arrivals at 200,000/s the probability of a 200 ns window with no arrival is high in isolation — but with multiple reader threads overlapping, the count rarely hits zero, and every new arrival is admitted because the reader-preferring policy does not check for waiting writers.

In practice the writer waits an unbounded time, and the symptom is that a config change "sometimes doesn't take effect" — intermittent, unreproducible, and blamed on the config system rather than the lock. Adding the single _waiting_writers > 0 clause to the reader predicate fixes it and bounds the writer's wait to the drain time of readers already admitted.

(b) Is the lock helping? Almost certainly not, and this is the more interesting answer.

The critical section is 200 ns. Acquiring and releasing a read-write lock involves taking an internal mutex, checking two or three conditions, and incrementing a shared counter — plausibly 50–100 ns of uncontended work, and far more under contention. The reader counter is a single cache line written by every one of the 200,000 readers per second across every core, so it ping-pongs continuously between core caches; a cache-line transfer is on the order of 100 ns on its own.

So the lock overhead is comparable to or greater than the work it protects, and the coordination is worse than serialising — you have added contention on the counter in order to avoid contention on the data. A plain mutex would likely be faster here, because at least it involves one atomic operation rather than several plus condition-variable bookkeeping.

(c) What to use instead: copy-on-write. The workload is 200,000 reads/s against 10 writes per hour — a ratio of about 72 million to one. That is the textbook case for an immutable snapshot behind an atomic reference:

  • Readers load the reference and use it. No lock, no atomic write, no shared cache line being modified — just a read of a pointer that stays in every core's cache. Effectively free, and perfectly scalable across cores.
  • Writers build a complete new routing table, then atomically swap the reference. Takes 50 µs plus a copy, ten times an hour — utterly irrelevant.
  • Readers holding the old reference continue using it safely until they finish; it is garbage-collected (or reference-counted) once nobody holds it.

The cost is a brief window — bounded by the length of a read — in which some threads use the old table and some the new. For a routing table that is entirely acceptable, and it should be stated explicitly as the trade being made.

The general lesson: the question "which locking policy?" was the wrong question. When reads overwhelmingly dominate and the data can be replaced wholesale, the right move is to remove the coordination rather than optimise it. A read-write lock earns its keep with long critical sections and a genuine mix of reads and writes; for short reads of rarely-changed data it is a pessimisation dressed as an optimisation.

Start here — the smallest possible deadlock

Transfer money from account A to B. You must lock both, or another thread could read a half-completed transfer. So:

def transfer(a, b, amount):
    with a.lock:
        with b.lock:
            a.balance -= amount
            b.balance += amount

Correct, and it deadlocks. Thread 1 transfers A→B and takes A's lock. Thread 2 simultaneously transfers B→A and takes B's lock. Thread 1 now waits for B; thread 2 waits for A. Neither will ever proceed. No error, no timeout, no CPU usage — the two threads are simply gone, and if those are request threads, two requests hang forever.

The four conditions

A deadlock requires all four of these simultaneously, and breaking any one prevents it:

  • Mutual exclusion — the resource cannot be shared. (Rarely removable.)
  • Hold and wait — a thread holds one lock while requesting another.
  • No preemption — a lock cannot be taken away from its holder.
  • Circular wait — a cycle in the "waiting for" graph.

The practical fix attacks circular wait, and it is almost embarrassingly simple.

The answer

Impose a global ordering on locks and always acquire in that order. If every thread takes the lower-numbered account's lock first, a cycle is impossible: any two threads contending for the same pair agree on which to take first, so one of them gets both. One comparison removes an entire class of bug.

Requirements

Transfer between accounts atomically and thread-safely, with no deadlock under any interleaving, correct under self-transfer, and detectable insufficient funds. Clarify: must a failed transfer be retryable? Are multi-account transfers (three-way) required? Both change the approach.

Solution 1 — lock ordering (the default)

class Account:
    def __init__(self, id):
        self.id, self.balance, self.lock = id, 0, threading.Lock()

def transfer(a, b, amount):
    if a.id == b.id:
        raise ValueError("cannot transfer to self")   # else self-deadlock
    first, second = (a, b) if a.id < b.id else (b, a)
    with first.lock:
        with second.lock:
            if a.balance < amount:
                raise InsufficientFunds
            a.balance -= amount
            b.balance += amount

The self-transfer check is not decoration. Without it, a and b being the same account means acquiring the same non-reentrant lock twice from one thread, which deadlocks instantly and deterministically — a bug that shows up the first time a user transfers to themselves.

Ordering by a stable identity. Use a permanent account id, not a memory address or hash, which can vary between processes or runs. If no natural ordering exists, assign every lockable object a monotonically increasing sequence number at creation.

Solution 2 — try-lock with backoff

def transfer(a, b, amount, tries=100):
    for _ in range(tries):
        if a.lock.acquire(timeout=0.001):
            try:
                if b.lock.acquire(timeout=0.001):
                    try:
                        return self._apply(a, b, amount)
                    finally: b.lock.release()
            finally: a.lock.release()
        time.sleep(random.uniform(0, 0.001))   # jitter, or they re-collide
    raise CouldNotAcquire

Breaks hold and wait: if the second lock is unavailable, release the first and retry. Useful when no natural ordering exists. The random backoff is essential — without it, two threads retry in lockstep and livelock, each repeatedly grabbing and releasing, making no progress while burning CPU. That is arguably worse than a deadlock, because it looks like the system is working.

Solution 3 — a single coarse lock

One global lock for all transfers. Trivially deadlock-free and correct. It serialises every transfer in the system, which at low volume is entirely fine — and saying "I would start here and only shard the locking if measurement showed contention" is a legitimate, mature answer rather than a cop-out.

Extensions

  • Multi-account transactions: lock ordering generalises directly — sort all participating accounts by id and acquire in order. Try-lock does not generalise nearly as well.
  • Lock striping: with millions of accounts, a lock per account is a lot of objects. Hash accounts into N locks; ordering still works on lock index, but two accounts may share a lock, so you must handle "both map to the same lock" without double-acquiring.
  • The database version: the same problem exists in SQL, and the same fix applies — update rows in a consistent order (say, ascending primary key) or the database will detect a deadlock and abort one transaction, which you must then retry.

The senior layer

  • Lock ordering must be a documented, enforced invariant, not a local convention. It only works if every code path obeys it, so one function somewhere taking B before A reintroduces the cycle. Encode it: wrap multi-lock acquisition in a single helper that sorts, and make direct lock.acquire() on these objects private. Some teams go further and assert lock-ordering at runtime in debug builds, tracking which locks a thread holds and failing loudly on an out-of-order acquisition — which turns a rare production deadlock into a deterministic test failure.
  • Deadlocks are invisible in ordinary monitoring, which is why they are so damaging. The threads consume no CPU, throw nothing and log nothing; they simply stop. The service's error rate may not move at all — requests time out at the client instead. Detection therefore has to be deliberate: a watchdog that periodically checks for threads blocked beyond a threshold, lock acquisition timeouts so a wait becomes an exception rather than an eternity, and thread dumps on demand. Always prefer a timed acquire in production code, because a timeout converts an undiagnosable hang into a logged error with a stack trace.
  • The atomicity requirement is what forces two locks, so question it. If transfers were modelled as an append-only ledger — insert a debit row and a credit row in one transaction — you would not lock two mutable balances at all, and balances become derived. That is the payments-ledger design, and it sidesteps this entire problem. Raising it shows you can question the premise: the deadlock is a consequence of mutable per-account state, not an inherent property of transferring money.
  • Testing for deadlock needs stress plus a watchdog, not unit tests. Run many threads performing random transfers among a small set of accounts — a small set is essential, because it maximises contention — with a test-level timeout that fails if the run does not complete. Assert afterwards that the total balance across all accounts is unchanged, which catches both lost updates and partial transfers. Deterministic unit tests will never produce the interleaving.
  • Know which solution to pick and why. Lock ordering when a stable ordering exists, which is nearly always — it is deterministic, has no retry loop, and has no livelock risk. Try-lock when ordering is impossible, for example when the set of resources is discovered during the operation. A single coarse lock when contention is genuinely low; complexity you do not need is its own kind of bug.

A payments service processes 500 transfers/s among 10,000 accounts. It uses per-account locks with no ordering. One account — the platform's fee account — is a party to 40% of all transfers.

(a) What is the probability of a deadlock-prone pair, and how often will it happen? (b) What is the effect of the hot fee account? (c) Fix both problems.

Answer

(a) Deadlock frequency. A deadlock requires two concurrent transfers over the same pair of accounts in opposite directions, overlapping in the window between acquiring the first lock and the second — a window of perhaps a microsecond.

For two random accounts out of 10,000 the chance of any given pair colliding is minuscule. But the calculation that matters is not per-pair, it is over time: with 500 transfers/s over months, a rare interleaving is a certainty. This is the defining characteristic of the bug — it is vanishingly unlikely in testing and inevitable in production, so it surfaces as an unexplained hang weeks after release, typically under peak load when the windows widen.

And the fee account changes the arithmetic completely. 40% of 500/s = 200 transfers/s touch it, so at any moment there are typically several concurrent transfers involving that one account, many in opposite directions (fees in, payouts out). The pair (fee_account, X) and (X, fee_account) now collide frequently rather than rarely — deadlocks go from a monthly mystery to a daily incident.

(b) The hot account has a second, separate problem. Even with deadlocks fixed, every one of those 200 transfers/s must serialise on the fee account's single lock. If a transfer holds it for 50 µs, the maximum throughput through that lock is 20,000/s — fine at 200/s, but the lock is now a global serialisation point and any increase in critical-section duration (a slow disk write, a log line, a network call inside the lock) directly caps the whole platform. Never do I/O inside a lock is the practical rule this illustrates.

(c) The fixes.

  • Lock ordering by account id — one comparison, eliminates deadlock entirely and deterministically. Do this first; it is free.
  • Enforce it structurally: a single with_accounts_locked(*accounts) helper that sorts and acquires, with direct lock access made private. A convention that lives in developers' heads will be violated.
  • Timed acquisition so that even if something slips through, a thread raises after a second rather than hanging forever — and logs a stack trace identifying the participants.
  • Shard the hot account. Split the fee account into N sub-accounts (fee_00 … fee_15), pick one at random per transfer, and treat the logical balance as their sum. Contention drops by a factor of N, and the sum is computed on read. This is the same hot-key fix as the cache, the partitioned log and the feed — worth naming as the recurring pattern it is.
  • Or remove the mutable balance entirely — an append-only ledger with derived balances has no per-account lock to contend on, because appends to different rows do not conflict. This is the structurally best answer and the largest change.

What to say in the interview: lead with lock ordering because it is correct and costs one line, then immediately point out that ordering fixes the deadlock but not the contention, and that the hot account needs sharding or a different data model. Recognising that there are two problems here — a correctness bug and a scalability bottleneck, with different fixes — is what the question is designed to surface.
